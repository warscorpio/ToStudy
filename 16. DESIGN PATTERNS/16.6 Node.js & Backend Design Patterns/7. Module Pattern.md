# Module Pattern in NestJS — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Module Pattern in NestJS and what problem does it solve?**
A: In NestJS, a Module is the fundamental unit of application organisation. Every NestJS application is composed of modules — each module encapsulates a cohesive slice of functionality: its controllers, providers, and the dependencies it exposes to the rest of the application.

The Module Pattern solves three structural problems that emerge as backends grow:

- **Visibility sprawl** — without modules, every provider is globally accessible. There is no boundary between "loan application logic" and "payment gateway logic." Any service can reach any other service, creating invisible coupling.
- **Uncontrolled dependency graphs** — without explicit `imports` / `exports`, you cannot reason about what a feature depends on. Modules make the dependency graph explicit and visible at a glance.
- **Team ownership ambiguity** — in a lending platform, who owns the NACH mandate logic? Modules give teams a clear boundary: `NachModule` is owned by the collections team; `LoanOriginationModule` is owned by the credit team. Module boundaries align with team boundaries.

NestJS modules are built on top of its DI container. Every `@Module()` decorator creates a scoped injector — providers declared inside are private by default, exports are the public API, and imports are the declared dependencies on other modules.

**Q2. What are the four properties of the `@Module()` decorator and what does each do?**
A:

```typescript
@Module({
  imports:     [],   // other modules whose exports this module needs
  controllers: [],   // HTTP handlers registered in this module's scope
  providers:   [],   // services, repositories, guards, interceptors, pipes
  exports:     [],   // subset of providers made available to importing modules
})
```

| Property | What it contains | Effect |
|---|---|---|
| `imports` | Other `@Module` classes | Makes the imported module's `exports` available to providers in this module |
| `controllers` | `@Controller()` classes | Registers route handlers; NestJS maps HTTP routes to these at startup |
| `providers` | `@Injectable()` classes or provider descriptors | Registers with the DI container; available only within this module unless exported |
| `exports` | Subset of `providers` or re-exported imported modules | Makes listed providers available to any module that imports this one |

The key insight: **providers are private by default**. A service in `BureauModule` is invisible to `LoanModule` unless `BureauModule` explicitly exports it and `LoanModule` explicitly imports `BureauModule`. This enforced encapsulation is why the module system prevents invisible coupling.

**Q3. What is the difference between `providers` and `exports` in a module?**
A: `providers` declares what the module *owns and uses internally*. `exports` declares what the module *publishes* to the outside world — its public API.

```typescript
@Module({
  providers: [
    BureauService,          // public — exported below
    CibilHttpAdapter,       // private — internal implementation detail
    ExperianHttpAdapter,    // private — internal implementation detail
    BureauCacheService,     // private — internal caching layer
  ],
  exports: [
    BureauService,          // ONLY this is visible outside BureauModule
    // CibilHttpAdapter is invisible — callers depend on the abstraction, not the adapter
  ],
})
export class BureauModule {}
```

This is the **interface segregation** of the module system: a module exposes the minimum surface area needed by its consumers. `CibilHttpAdapter` and `ExperianHttpAdapter` are implementation details — swapping them requires zero changes in consuming modules because they were never exported.

An exported provider can also be an imported module:

```typescript
@Module({
  imports:  [HttpModule],   // HttpModule provides HttpService
  exports:  [HttpModule],   // re-export — consumers get HttpService too
  providers: [BureauService],
})
export class BureauModule {}
```

Re-exporting an entire module is useful when `BureauModule` acts as an aggregator — consumers import `BureauModule` and get everything they need without knowing the internal structure.

**Q4. What is the root module (`AppModule`) and what should it contain?**
A: `AppModule` is the entry point — the root of NestJS's module tree. NestJS bootstraps the application starting from `AppModule` and recursively discovers all imported modules.

```typescript
// app.module.ts — root module: composition root only
@Module({
  imports: [
    // Infrastructure / cross-cutting (global)
    CoreModule,           // Logger, ConfigService, EventEmitter, PrismaService
    DatabaseModule,       // TypeORM or Prisma connection
    CacheModule,          // Redis
    HealthModule,         // /health endpoint

    // Feature modules
    LoanModule,
    NachModule,
    KycModule,
    DisbursementModule,
    CollectionModule,
    NotificationModule,
  ],
})
export class AppModule {}
```

`AppModule` should be a **composition root** — it imports feature modules and infrastructure modules, but owns zero providers itself. Business logic, controllers, and repositories never live in `AppModule`. The moment you see a `@Injectable()` service in `AppModule`, it's a sign the module has not been properly extracted yet.

## Section 2: Module Types in Depth

**Q5. What are the four types of modules in a production NestJS application?**
A:

**1. Feature Modules** — encapsulate one bounded context or domain feature. The majority of modules in a codebase are feature modules.

```typescript
// loan/loan.module.ts
@Module({
  imports:     [DatabaseModule, BureauModule, NotificationModule],
  controllers: [LoanApplicationController],
  providers:   [LoanApplicationService, LoanRepository, LoanEligibilityService],
  exports:     [LoanApplicationService],   // exported for use by DisbursementModule, CollectionModule
})
export class LoanModule {}
```

**2. Shared Modules** — provide reusable infrastructure used by multiple feature modules. Shared modules are imported by many, and their exports are the shared contracts.

```typescript
// shared/bureau/bureau.module.ts
@Module({
  imports:   [HttpModule, ConfigModule],
  providers: [BureauService, CibilAdapter, ExperianAdapter, BureauCacheService],
  exports:   [BureauService],
})
export class BureauModule {}
// Imported by: LoanModule, KycModule, UnderwritingModule
```

**3. Global Modules** — cross-cutting infrastructure that every module in the application needs. Declared once; implicitly available everywhere. Use sparingly.

```typescript
// core/core.module.ts
@Global()
@Module({
  imports:  [ConfigModule.forRoot({ isGlobal: true }), EventEmitterModule.forRoot()],
  providers: [AppLogger, PrismaService, RequestContext],
  exports:   [AppLogger, PrismaService, RequestContext, ConfigService, EventEmitter2],
})
export class CoreModule {}
// AppModule imports CoreModule once; all other modules get its exports for free
```

**4. Dynamic Modules** — modules whose providers are configured at import time based on options passed by the caller. Used for reusable integrations that need runtime configuration.

```typescript
// integrations/razorpay/razorpay.module.ts
@Module({})
export class RazorpayModule {
  static forRootAsync(options: RazorpayAsyncOptions): DynamicModule { /* ... */ }
}
// PaymentModule imports: RazorpayModule.forRootAsync({ useFactory: ... })
```

**Q6. What is a Global Module and when is it appropriate to use `@Global()`?**
A: A `@Global()` module's exports are available to every module in the application without needing to be listed in their `imports` array. NestJS registers the global module's providers at the root injector level.

```typescript
@Global()
@Module({
  providers: [
    AppLogger,
    PrismaService,
    { provide: APP_FILTER, useClass: GlobalDomainExceptionFilter },
    { provide: APP_INTERCEPTOR, useClass: LoggingInterceptor },
  ],
  exports: [AppLogger, PrismaService],
})
export class CoreModule {}
```

**When to use `@Global()`:**
- ✅ Infrastructure used by literally every module: `Logger`, `ConfigService`, `PrismaService`, `EventEmitter2`
- ✅ `APP_FILTER`, `APP_INTERCEPTOR`, `APP_GUARD`, `APP_PIPE` — NestJS built-in multi-providers
- ✅ Request context holder used across all layers
- ❌ Domain services (`LoanApplicationService`, `KycService`) — these should be explicitly imported
- ❌ Integration adapters (`BureauService`, `SmsService`) — these belong in shared modules with explicit imports

The test: if a module is imported by 70% or more of your other modules, consider making it global. If it's imported by 2 modules, keep it a shared module. Global modules make implicit dependencies; use them only where the ubiquity is a feature, not a convenience.

**Q7. What is a Dynamic Module and how is the `forRoot` / `forRootAsync` convention used?**
A: A Dynamic Module is a module whose provider registrations are determined at import time based on a configuration object passed by the caller. It returns a `DynamicModule` object — a `@Module()` descriptor built at runtime.

The `forRoot` / `forRootAsync` convention:
- `forRoot(options)` — synchronous; options are known at module import time
- `forRootAsync(options)` — asynchronous; options come from `ConfigService` or another async source
- `forFeature(options)` — used by modules like `TypeOrmModule` that need both a root (connection) and per-feature registration (which entities to manage)

```typescript
// integrations/juspay/juspay.module.ts
export interface JusPayOptions {
  apiKey:      string;
  merchantId:  string;
  environment: 'sandbox' | 'production';
  timeoutMs:   number;
}

export const JUSPAY_OPTIONS = Symbol('JUSPAY_OPTIONS');
export const JUSPAY_CLIENT  = Symbol('JUSPAY_CLIENT');

@Module({})
export class JusPayModule {
  // Sync — config is available at import time (e.g., from a constant)
  static forRoot(options: JusPayOptions): DynamicModule {
    return {
      module: JusPayModule,
      providers: [
        { provide: JUSPAY_OPTIONS, useValue: options },
        {
          provide:    JUSPAY_CLIENT,
          useFactory: (opts: JusPayOptions) => new JusPayApiClient(opts),
          inject:     [JUSPAY_OPTIONS],
        },
        JusPayService,
      ],
      exports: [JusPayService],
    };
  }

  // Async — config comes from ConfigService loaded at runtime
  static forRootAsync(options: {
    imports?:    any[];
    useFactory:  (...args: any[]) => JusPayOptions | Promise<JusPayOptions>;
    inject?:     any[];
  }): DynamicModule {
    return {
      module:  JusPayModule,
      imports: options.imports ?? [],
      providers: [
        {
          provide:    JUSPAY_OPTIONS,
          useFactory: options.useFactory,
          inject:     options.inject ?? [],
        },
        {
          provide:    JUSPAY_CLIENT,
          useFactory: (opts: JusPayOptions) => new JusPayApiClient(opts),
          inject:     [JUSPAY_OPTIONS],
        },
        JusPayService,
      ],
      exports: [JusPayService],
    };
  }
}

// Usage in PaymentModule
@Module({
  imports: [
    JusPayModule.forRootAsync({
      imports:    [ConfigModule],
      useFactory: (config: ConfigService): JusPayOptions => ({
        apiKey:      config.get('JUSPAY_API_KEY')!,
        merchantId:  config.get('JUSPAY_MERCHANT_ID')!,
        environment: config.get<'sandbox' | 'production'>('JUSPAY_ENV', 'sandbox'),
        timeoutMs:   config.get<number>('JUSPAY_TIMEOUT_MS', 5000),
      }),
      inject: [ConfigService],
    }),
  ],
  providers:   [PaymentService],
  exports:     [PaymentService],
})
export class PaymentModule {}
```

## Section 3: Module Boundaries and Encapsulation

**Q8. How do you model module boundaries in a fintech microservice with multiple domains?**
A: Module boundaries should follow **domain cohesion** — group providers by what business capability they serve, not by technical role.

```
src/
├── core/                        # Global infrastructure
│   └── core.module.ts           # Logger, Prisma, Config, EventEmitter
│
├── loan/                        # Loan origination domain
│   ├── loan.module.ts
│   ├── controllers/
│   │   └── loan-application.controller.ts
│   ├── services/
│   │   ├── loan-application.service.ts
│   │   └── loan-eligibility.service.ts
│   └── repositories/
│       └── loan.repository.ts
│
├── nach/                        # NACH mandate domain
│   ├── nach.module.ts
│   ├── controllers/
│   │   └── mandate.controller.ts
│   ├── services/
│   │   ├── mandate-registration.service.ts
│   │   └── nach-presentation.service.ts
│   └── repositories/
│       └── mandate.repository.ts
│
├── kyc/                         # KYC domain
│   ├── kyc.module.ts
│   └── services/
│       ├── pan-verification.service.ts
│       └── aadhaar-verification.service.ts
│
├── collection/                  # Collections domain
│   ├── collection.module.ts
│   └── services/
│       ├── emi-collection.service.ts
│       └── bounce-handling.service.ts
│
└── integrations/                # External service adapters
    ├── bureau/
    │   ├── bureau.module.ts
    │   └── adapters/
    │       ├── cibil.adapter.ts
    │       └── experian.adapter.ts
    ├── sms/
    │   └── sms.module.ts
    └── juspay/
        └── juspay.module.ts
```

**Boundary rules:**
- Each domain module owns its own controllers, services, and repositories.
- Cross-domain calls go through exported services — never through shared repositories.
- Integration adapters live in `integrations/` — they are infrastructure, not domain logic.
- `CollectionModule` needing loan data imports `LoanModule` (which exports `LoanApplicationService`) — it never directly imports `LoanRepository`.

**Q9. How do you prevent a module from becoming a "god module" that everything imports?**
A: God modules emerge when a module accumulates providers that belong to different domains. The symptom: 80% of other modules import it. The fix is to split along domain lines.

```typescript
// ❌ God module — mixed responsibilities
@Module({
  providers: [
    LoanApplicationService,    // loan domain
    KycService,                // KYC domain
    NachService,               // NACH domain
    BureauService,             // integration
    SmsService,                // integration
    EmailService,              // integration
    PrismaService,             // infrastructure
    ConfigService,             // infrastructure
  ],
  exports: [ /* everything */ ],
})
export class SharedModule {}

// ✅ Split by responsibility
// Each domain has its own module; integrations have their own module
@Module({
  providers: [LoanApplicationService, LoanEligibilityService],
  exports:   [LoanApplicationService],
})
export class LoanModule {}

@Module({
  providers: [KycService, PanVerificationService],
  exports:   [KycService],
})
export class KycModule {}

@Module({
  providers: [BureauService, CibilAdapter, ExperianAdapter],
  exports:   [BureauService],
})
export class BureauModule {}

@Module({
  providers:  [SmsService, EmailService],
  exports:    [SmsService, EmailService],
})
export class NotificationModule {}

// Only PrismaService and ConfigService warrant @Global() — they ARE universally needed
@Global()
@Module({
  providers: [PrismaService, AppLogger],
  exports:   [PrismaService, AppLogger],
})
export class CoreModule {}
```

Test for a god module: open its `providers` array. If the providers don't all answer "yes" to the question "do these all serve the same business capability?", the module needs to be split.

**Q10. How do you handle cross-module communication without creating circular imports?**
A: Cross-module communication should flow in one direction. In a lending platform, the dependency direction should mirror the business flow:

```
LoanModule → BureauModule
LoanModule → KycModule
CollectionModule → LoanModule
CollectionModule → NachModule
DisbursementModule → LoanModule
DisbursementModule → PaymentModule
```

When two modules seem to need each other, it almost always means a third, shared concept should be extracted:

```typescript
// ❌ Circular — LoanModule imports CollectionModule, CollectionModule imports LoanModule
@Module({ imports: [CollectionModule] }) export class LoanModule {}     // needs EMI schedule
@Module({ imports: [LoanModule]       }) export class CollectionModule {} // needs loan details

// ✅ Extract the shared concept into a domain-events pattern
// LoanModule emits events; CollectionModule listens — no direct import

// loan/services/loan-application.service.ts
@Injectable()
export class LoanApplicationService {
  constructor(private readonly eventEmitter: EventEmitter2) {}

  async disburse(loanId: string): Promise<void> {
    // ... disbursement logic
    this.eventEmitter.emit('loan.disbursed', { loanId, sanctionedAmount, tenorMonths });
    // CollectionModule listens to this event — LoanModule does not import CollectionModule
  }
}

// collection/listeners/loan-disbursed.listener.ts
@Injectable()
export class LoanDisbursedListener {
  @OnEvent('loan.disbursed')
  async handleLoanDisbursed(payload: LoanDisbursedEvent): Promise<void> {
    await this.emiScheduleService.generateSchedule(payload.loanId, payload.tenorMonths);
  }
}
```

If a genuine circular import is unavoidable at the module level, NestJS provides `forwardRef`:

```typescript
@Module({
  imports: [forwardRef(() => CollectionModule)],
  providers: [LoanApplicationService],
})
export class LoanModule {}
```

But treat every `forwardRef` as a design smell — the circular dependency signals that the two modules are too tightly coupled and the event-driven approach above is almost always the correct fix.

## Section 4: Module Lifecycle and Hooks

**Q11. What lifecycle hooks does NestJS provide for modules and when do you use each?**
A: NestJS provides three lifecycle interfaces that modules (and providers) can implement:

```typescript
@Module({ /* ... */ })
export class NachModule implements OnModuleInit, OnApplicationBootstrap, OnModuleDestroy {

  constructor(
    private readonly nachClient: NachApiClient,
    private readonly redisClient: Redis,
    private readonly logger: AppLogger,
  ) {}

  // Called once all providers in this module are instantiated
  // Use for: one-time initialisation that depends on injected providers being ready
  async onModuleInit(): Promise<void> {
    await this.nachClient.ping(); // verify NACH API is reachable at startup
    this.logger.log('NachModule', 'NACH API connection verified');
  }

  // Called after ALL modules in the application have been initialised
  // Use for: startup tasks that require the full application to be ready
  // (e.g., start consuming a Kafka topic — don't start consuming until all modules are ready)
  async onApplicationBootstrap(): Promise<void> {
    await this.nachPresentationConsumer.startConsuming(); // Kafka consumer starts here
    this.logger.log('NachModule', 'NACH Kafka consumer started');
  }

  // Called when the application receives a shutdown signal (SIGTERM, SIGINT)
  // Use for: graceful shutdown — drain in-flight requests, close connections
  async onModuleDestroy(): Promise<void> {
    await this.nachPresentationConsumer.stop();  // stop consuming new messages
    await this.redisClient.quit();               // close Redis connection
    this.logger.log('NachModule', 'NachModule shut down gracefully');
  }
}
```

Enable shutdown hooks explicitly in `main.ts`:

```typescript
async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks(); // required for onModuleDestroy to fire on SIGTERM
  await app.listen(3000);
}
```

**Critical in fintech:** Without `enableShutdownHooks()` and `onModuleDestroy`, a Kubernetes pod termination (SIGTERM) kills the process immediately — in-flight NACH presentations and active Kafka message processing are interrupted without acknowledgment, leading to duplicate processing or data loss.

**Q12. What is the difference between `onModuleInit` and `onApplicationBootstrap`?**
A:

| Hook | When it fires | What's available | Use for |
|---|---|---|---|
| `onModuleInit` | After all providers in *this* module are resolved | This module's providers only | Module-local init: verify a DB connection, warm a cache for this feature |
| `onApplicationBootstrap` | After *all* modules across the app have initialised | Full application is ready | Start Kafka consumers, schedule cron jobs, register service with discovery |

The distinction matters when a startup task depends on another module being fully ready:

```typescript
// ❌ Wrong hook — CollectionModule's Kafka consumer may start before LoanModule is ready
async onModuleInit(): Promise<void> {
  await this.kafkaConsumer.subscribe('loan-disbursed');  // LoanModule might not be up yet
  await this.kafkaConsumer.run(/* handler that calls LoanApplicationService */);
}

// ✅ Correct hook — all modules including LoanModule are guaranteed ready
async onApplicationBootstrap(): Promise<void> {
  await this.kafkaConsumer.subscribe('loan-disbursed');
  await this.kafkaConsumer.run(/* handler safely calls LoanApplicationService */);
}
```

## Section 5: Testing Modules

**Q13. How do you unit test a module's providers in isolation?**
A: Use `Test.createTestingModule` to spin up a minimal NestJS context with only the providers needed for the test — mock everything external to the module under test:

```typescript
// Testing LoanApplicationService in isolation from BureauModule, NotificationModule
describe('LoanModule — LoanApplicationService', () => {
  let service: LoanApplicationService;
  let mockBureauService: jest.Mocked<IBureauService>;
  let mockLoanRepo: jest.Mocked<ILoanRepository>;

  beforeEach(async () => {
    mockBureauService = { fetchCreditReport: jest.fn(), fetchBankStatement: jest.fn() };
    mockLoanRepo      = { create: jest.fn(), findById: jest.fn(), updateStatus: jest.fn(), findByApplicant: jest.fn() };

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        LoanApplicationService,
        LoanEligibilityService,          // real — test its integration with the service
        { provide: BUREAU_SERVICE,   useValue: mockBureauService },
        { provide: LOAN_REPOSITORY,  useValue: mockLoanRepo },
        { provide: NotificationService, useValue: { sendApplicationReceived: jest.fn() } },
        { provide: EventEmitter2,       useValue: { emit: jest.fn() } },
        { provide: AppLogger,           useValue: { log: jest.fn(), warn: jest.fn(), error: jest.fn() } },
      ],
    }).compile();

    service = module.get(LoanApplicationService);
  });

  it('should reject when bureau score is below minimum', async () => {
    mockBureauService.fetchCreditReport.mockResolvedValue({ score: 600, overdueAccounts: 1 } as any);

    await expect(
      service.apply(validCreateLoanDto, 'USR-001'),
    ).rejects.toThrow(IneligibleApplicantException);

    expect(mockLoanRepo.create).not.toHaveBeenCalled();
  });
});
```

**Q14. How do you integration test a module against a real database?**
A: Import the full module (or a subset) into the test context and override only external integrations. Use Testcontainers to spin up a real PostgreSQL instance:

```typescript
describe('LoanModule — Integration', () => {
  let app: INestApplication;
  let prisma: PrismaService;

  beforeAll(async () => {
    const postgres = await new PostgreSqlContainer('postgres:15-alpine').start();

    const module: TestingModule = await Test.createTestingModule({
      imports: [
        CoreModule,
        ConfigModule.forRoot({
          load: [() => ({ DATABASE_URL: postgres.getConnectionUri() })],
        }),
        LoanModule,       // real module — real service + real repository
      ],
    })
      .overrideProvider(BUREAU_SERVICE)
      .useValue({ fetchCreditReport: jest.fn().mockResolvedValue({ score: 720, overdueAccounts: 0 }) })
      .overrideProvider(NotificationService)
      .useValue({ sendApplicationReceived: jest.fn() })
      .compile();

    app = module.createNestApplication();
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
    app.useGlobalFilters(new GlobalDomainExceptionFilter());
    await app.init();

    prisma = module.get(PrismaService);
    await prisma.$executeRawUnsafe(`-- run migrations`);
  });

  afterEach(async () => { await prisma.loan.deleteMany(); });
  afterAll(async () => { await app.close(); });

  it('should persist a loan application to the database', async () => {
    const service = app.get(LoanApplicationService);
    const loan    = await service.apply(validDto, 'USR-001');

    expect(loan.id).toBeDefined();
    const dbRecord = await prisma.loan.findUnique({ where: { id: loan.id } });
    expect(dbRecord?.status).toBe('PENDING');
  });
});
```

**Q15. How do you test a Dynamic Module (`forRootAsync`) in tests?**
A: Pass test-specific options directly via `forRoot` (synchronous version) in the test context — no `ConfigService` needed:

```typescript
describe('JusPayModule', () => {
  let service: JusPayService;

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      imports: [
        // Use forRoot (sync) in tests — avoid needing ConfigService
        JusPayModule.forRoot({
          apiKey:      'test-api-key',
          merchantId:  'test-merchant',
          environment: 'sandbox',
          timeoutMs:   1000,
        }),
      ],
    }).compile();

    service = module.get(JusPayService);
  });

  it('should have JusPayService available', () => {
    expect(service).toBeDefined();
  });
});
```

## Section 6: Common Anti-Patterns and Pitfalls

**Q16. What are the most common Module Pattern violations in a NestJS fintech codebase?**
A:

**Anti-pattern 1 — Importing a provider class directly from another module's file without the module system:**
```typescript
// ❌ LoanModule directly imports the BureauService class, bypassing BureauModule
import { BureauService } from '../bureau/bureau.service'; // ← wrong

@Module({
  providers: [LoanApplicationService, BureauService], // re-declares BureauService
})
export class LoanModule {}

// ✅ Import the module, not the class
@Module({
  imports:   [BureauModule],  // BureauModule exports BureauService
  providers: [LoanApplicationService],
})
export class LoanModule {}
```

**Anti-pattern 2 — Exporting everything from a module:**
```typescript
// ❌ Exports all internal providers — exposes implementation details
@Module({
  providers: [NachService, NachRepository, NpciHttpAdapter, NachRetryQueue],
  exports:   [NachService, NachRepository, NpciHttpAdapter, NachRetryQueue], // wrong
})
export class NachModule {}

// ✅ Export only the public API
@Module({
  providers: [NachService, NachRepository, NpciHttpAdapter, NachRetryQueue],
  exports:   [NachService],  // callers need the service; repository is an internal detail
})
export class NachModule {}
```

**Anti-pattern 3 — Business logic in `AppModule`:**
```typescript
// ❌ AppModule accumulates providers — no extraction into feature modules
@Module({
  providers: [
    LoanApplicationService,   // should be in LoanModule
    NachService,              // should be in NachModule
    KycService,               // should be in KycModule
    BureauService,            // should be in BureauModule
  ],
  controllers: [
    LoanController,           // should be in LoanModule
    NachController,           // should be in NachModule
  ],
})
export class AppModule {}

// ✅ AppModule is composition-only
@Module({
  imports: [CoreModule, LoanModule, NachModule, KycModule],
})
export class AppModule {}
```

**Anti-pattern 4 — Using `@Global()` on feature modules:**
```typescript
// ❌ Making a domain module global — now every module implicitly depends on LoanModule
@Global()   // wrong
@Module({
  providers: [LoanApplicationService, LoanRepository],
  exports:   [LoanApplicationService],
})
export class LoanModule {}

// ✅ Feature modules must be explicitly imported — keeps dependencies visible
@Module({
  providers: [LoanApplicationService, LoanRepository],
  exports:   [LoanApplicationService],
})
export class LoanModule {}

// CollectionModule explicitly declares its dependency on LoanModule
@Module({
  imports: [LoanModule],
  providers: [EmiCollectionService],
})
export class CollectionModule {}
```

**Anti-pattern 5 — Registering controllers in a shared module:**
```typescript
// ❌ Shared/infrastructure module owns a controller
@Module({
  providers: [BureauService],
  controllers: [BureauController],  // wrong — shared modules should not own HTTP routes
  exports: [BureauService],
})
export class BureauModule {}

// ✅ Controllers belong in feature modules that own the domain
@Module({
  imports:     [BureauModule],
  controllers: [BureauController],   // moved to a feature module
  providers:   [BureauApplicationService],
})
export class BureauFeatureModule {}
```

## Section 7: Scenario / System Design Questions

**Q17. "Your lending platform is growing — 3 teams now own different parts of the codebase. How do you structure your NestJS modules so teams don't step on each other?"**
A: Map module boundaries to team boundaries. Each team owns a set of modules; inter-team communication goes through exported service APIs.

```
Team: Credit                    Team: Payments                  Team: Operations
──────────────────────          ──────────────────────          ──────────────────────
LoanModule                      NachModule                      CollectionModule
  exports: [LoanService]          exports: [MandateService]       exports: [EmiService]
KycModule                       DisbursementModule              ReportingModule
  exports: [KycService]           exports: [DisbursementService]

Shared (Platform team):
  BureauModule  → exports: [BureauService]
  SmsModule     → exports: [SmsService]
  CoreModule    → @Global(); exports: [Logger, Prisma, Config]
```

Rules enforced via ESLint (`@nrwl/nx/enforce-module-boundaries` in an Nx monorepo):

```json
{
  "depConstraints": [
    { "sourceTag": "team:credit",     "onlyDependOnLibsWithTags": ["team:credit",     "team:platform"] },
    { "sourceTag": "team:payments",   "onlyDependOnLibsWithTags": ["team:payments",   "team:platform"] },
    { "sourceTag": "team:operations", "onlyDependOnLibsWithTags": ["team:operations", "team:credit", "team:payments", "team:platform"] }
  ]
}
```

Cross-team communication rules:
- A team may import the *exported service* of another team's module — never directly import another team's repository or internal adapter.
- For decoupled communication (e.g., CollectionModule reacting to loan disbursement), use domain events (`EventEmitter2`) so CollectionModule does not import LoanModule at all.

**Q18. "You need to add multi-tenancy — each tenant (NBFC partner) has different bureau provider, SMS vendor, and loan product rules. How do you use the Module Pattern to handle this?"**
A: Use the dynamic module pattern with a tenant context provider to swap implementations at request time:

```typescript
// Tenant-aware bureau service — routes to the right adapter per tenant
@Injectable({ scope: Scope.REQUEST })
export class TenantAwareBureauService implements IBureauService {
  constructor(
    @Inject(REQUEST) private readonly request: Request,
    @Inject('CIBIL_ADAPTER')    private readonly cibil: IBureauService,
    @Inject('EXPERIAN_ADAPTER') private readonly experian: IBureauService,
  ) {}

  async fetchCreditReport(pan: string): Promise<BureauReport> {
    const tenantId = this.request.headers['x-tenant-id'] as string;
    const adapter  = this.resolveAdapter(tenantId);
    return adapter.fetchCreditReport(pan);
  }

  private resolveAdapter(tenantId: string): IBureauService {
    // Tenant config loaded from DB or feature flag service at startup
    const tenantConfig = tenantConfigs.get(tenantId);
    return tenantConfig?.bureauProvider === 'EXPERIAN' ? this.experian : this.cibil;
  }
}

// BureauModule — registers both adapters; exposes tenant-aware facade
@Module({
  providers: [
    { provide: 'CIBIL_ADAPTER',    useClass: CibilBureauAdapter },
    { provide: 'EXPERIAN_ADAPTER', useClass: ExperianBureauAdapter },
    TenantAwareBureauService,
    { provide: BUREAU_SERVICE, useExisting: TenantAwareBureauService },
  ],
  exports: [{ provide: BUREAU_SERVICE, useExisting: TenantAwareBureauService }],
})
export class BureauModule {}
```

For tenant-specific loan product rules, use the dynamic module pattern — each tenant's rule set is registered as a named provider and the BRE service resolves the right ruleset from a registry:

```typescript
@Module({})
export class BREModule {
  static forRoot(tenantRulesets: Map<string, LoanRuleset>): DynamicModule {
    return {
      module: BREModule,
      providers: [
        { provide: 'TENANT_RULESETS', useValue: tenantRulesets },
        BREService,
      ],
      exports: [BREService],
    };
  }
}

// AppModule registers tenant rulesets at startup
@Module({
  imports: [
    BREModule.forRoot(new Map([
      ['NBFC_A', nbfcARuleset],
      ['NBFC_B', nbfcBRuleset],
    ])),
  ],
})
export class AppModule {}
```

**Q19. "Your `LoanModule` is imported by 6 other modules. Every time you add a new provider to `LoanModule`, all 6 break in tests because they now need to mock the new provider. How do you fix this?"**
A: This is the **over-importing problem** — modules importing `LoanModule` when they only need a specific slice of it. Two fixes:

**Fix 1 — Split `LoanModule` into focused sub-modules:**
```typescript
// Before: monolithic LoanModule
@Module({
  providers: [LoanApplicationService, LoanEligibilityService, LoanRepository, LoanReportingService],
  exports:   [LoanApplicationService, LoanEligibilityService, LoanRepository, LoanReportingService],
})
export class LoanModule {}

// After: split by capability
@Module({
  providers: [LoanApplicationService, LoanEligibilityService, LoanRepository],
  exports:   [LoanApplicationService],
})
export class LoanOriginationModule {}

@Module({
  providers: [LoanReportingService, LoanReportRepository],
  exports:   [LoanReportingService],
})
export class LoanReportingModule {}

// CollectionModule only needs loan status — imports only LoanOriginationModule
@Module({
  imports:   [LoanOriginationModule],   // no longer importing reporting providers
  providers: [EmiCollectionService],
})
export class CollectionModule {}
```

**Fix 2 — Expose an interface token; consuming modules mock the token, not the whole module:**
```typescript
// CollectionModule's test — mocks the token, not the entire LoanModule
const module = await Test.createTestingModule({
  providers: [
    EmiCollectionService,
    {
      provide: LOAN_APPLICATION_SERVICE,   // Symbol token
      useValue: { findById: jest.fn(), updateStatus: jest.fn() },
    },
  ],
}).compile();
// LoanModule is never imported in this test — zero exposure to its internal providers
```

The combination: export only service tokens (not concrete classes) and split modules along capability lines. Tests import only the tokens they need; adding a new provider to `LoanOriginationModule` doesn't break `CollectionModule`'s tests because the mock is the token, not the module.

## Quick Reference: Module Pattern Cheat Sheet

```
MODULE PATTERN — QUICK REFERENCE
──────────────────────────────────

MODULE ANATOMY
  imports     → other modules whose exports this module needs
  controllers → HTTP handlers (feature modules only)
  providers   → services, repositories, guards, interceptors (private by default)
  exports     → public API of this module; minimum necessary surface area

FOUR MODULE TYPES
  Feature Module     → one domain (LoanModule, NachModule, KycModule)
  Shared Module      → reusable infra (BureauModule, SmsModule, JusPayModule)
  Global Module      → @Global(); cross-cutting infra only (CoreModule)
  Dynamic Module     → forRoot/forRootAsync; configurable at import time

BOUNDARY RULES
  ✅ Providers are private by default — export only the public API
  ✅ Import modules, never provider classes directly across module boundaries
  ✅ Cross-domain calls go through exported services — never shared repositories
  ✅ AppModule is composition-only — zero business providers
  ✅ @Global() for infrastructure only: Logger, Prisma, Config, EventEmitter

CIRCULAR IMPORT FIXES
  → Extract shared concept to a third module
  → Use domain events (EventEmitter2) for decoupled cross-module communication
  → forwardRef(() => Module) — last resort; always a design smell

LIFECYCLE HOOKS
  onModuleInit          → module-local init (verify DB, warm cache)
  onApplicationBootstrap → app-wide init (start Kafka consumers, register services)
  onModuleDestroy       → graceful shutdown (drain consumers, close connections)
  app.enableShutdownHooks() → required for onModuleDestroy to fire on SIGTERM

DYNAMIC MODULE CONVENTION
  forRoot(options)        → sync; options known at import time
  forRootAsync(options)   → async; options from ConfigService
  forFeature(options)     → per-feature registration (TypeOrm entity list, etc.)

TESTING
  Unit  → Test.createTestingModule with only the providers under test; mock the rest
  Integration → import real module, overrideProvider() for external integrations
  Dynamic → use forRoot(testOptions) in tests; no ConfigService needed

ANTI-PATTERNS
  ❌ Importing provider class files across module boundaries (use the module)
  ❌ Exporting all providers (expose minimum surface)
  ❌ Business providers in AppModule (use feature modules)
  ❌ @Global() on feature/domain modules (implicit dependencies)
  ❌ Controllers in shared/infrastructure modules

FINTECH MODULE MAP
  CoreModule (Global)      → Logger, Prisma, Config, EventEmitter
  LoanModule               → LoanApplicationService, LoanRepository
  KycModule                → KycService, PanVerificationService
  NachModule               → MandateService, NachPresentationService
  CollectionModule         → EmiCollectionService, BounceHandlingService
  DisbursementModule       → DisbursementService
  BureauModule (Shared)    → BureauService (facade over CIBIL + Experian)
  NotificationModule       → SmsService, EmailService
  JusPayModule (Dynamic)   → JusPayService (forRootAsync)
  RazorpayModule (Dynamic) → RazorpayService (forRootAsync)
```
