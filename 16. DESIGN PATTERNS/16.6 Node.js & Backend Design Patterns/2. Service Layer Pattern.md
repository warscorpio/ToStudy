# JavaScript / TypeScript (Node.js & Backend Design Patterns): Service Layer Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Service Layer pattern?**
A: The Service Layer pattern, described by Martin Fowler in *Patterns of Enterprise Application Architecture* (2002), defines an application's boundary and its set of available operations from the perspective of interfacing client layers. It encapsulates the application's **business logic and coordination** in a dedicated layer of service classes that sit between the presentation layer (controllers, resolvers, CLI handlers) and the data access layer (repositories, ORMs, raw queries).

A service class defines what the application *can do* — the verifiable, transactional, auditable operations available to clients — while remaining ignorant of *how* those operations are triggered (HTTP, WebSocket, cron, message queue) or *how* data is stored (Postgres, MongoDB, Redis). This makes the service the stable, reusable core of the application: multiple delivery mechanisms can invoke the same service method, and multiple data stores can be swapped beneath it without the service knowing.

**Q2. What specific problems does the Service Layer solve?**
A: Without a service layer, two failure modes appear reliably:

**Fat Controller** — business logic creeps into route handlers because it is the most convenient place to write it. Each handler becomes a unique snowflake: validating input, querying the database, applying rules, formatting responses, all interleaved. Logic cannot be reused, cannot be tested without an HTTP server, and diverges across endpoints that should behave identically.

```ts
// Fat controller — validation, business logic, data access, formatting all in one place
app.post("/orders", async (req, res) => {
  if (!req.body.items?.length)     return res.status(400).json({ error: "No items" });
  if (!req.body.customerId)        return res.status(400).json({ error: "No customer" });

  const customer = await prisma.customer.findUnique({ where: { id: req.body.customerId } });
  if (!customer)                   return res.status(404).json({ error: "Customer not found" });
  if (customer.isBanned)           return res.status(403).json({ error: "Customer banned" });

  const total = req.body.items.reduce((sum: number, i: any) => sum + i.price * i.qty, 0);
  if (total > 100_000 && !req.body.managerApprovalCode)
    return res.status(422).json({ error: "Manager approval required" });

  const order = await prisma.order.create({ data: { /* ... */ } });
  await stripe.paymentIntents.create({ amount: total, currency: "inr" });
  await sendgrid.send({ to: customer.email, subject: "Order confirmed" });

  res.status(201).json({ orderId: order.id, total });
});
```

**Duplicated logic** — the same rules are copy-pasted across REST, GraphQL, and message consumer handlers. When the rule changes (e.g., the approval threshold moves from ₹1,00,000 to ₹50,000), every copy must be found and updated simultaneously.

The Service Layer fixes both: business logic lives in one class, called from every delivery mechanism. Controllers become thin adapters that parse input, call the service, and format output.

**Q3. What are the responsibilities of a service, and what does it explicitly NOT own?**
A:

**Service owns:**
- Orchestration — calling repositories, external gateways, and other services in the right order.
- Business rule enforcement — applying domain rules that span multiple entities or require external data.
- Transaction management — demarcating unit-of-work boundaries; rolling back on partial failure.
- Cross-cutting coordination — emitting events, sending notifications, scheduling tasks, writing audit logs.
- Input validation at the application level — validating that the operation makes sense given current state (not just that the input is well-formed — that belongs in the controller/DTO layer).

**Service does NOT own:**
- HTTP request/response handling — no `req`, `res`, `ctx`, or framework-specific objects.
- Serialisation and formatting — no `JSON.stringify`, no response shape decisions.
- Authentication — the service receives a verified identity, it does not verify tokens.
- Raw database queries — data access is delegated to repositories or ORMs.
- UI rendering or template generation.

**Q4. How is the Service Layer different from the Repository pattern?**
A: They operate at different levels of abstraction and have different responsibilities:

| Aspect | Repository | Service |
|---|---|---|
| **Focus** | Data access for one entity type | Business operation spanning multiple entities/resources |
| **Knows about** | One aggregate / table / collection | Multiple repositories, external APIs, event buses |
| **Returns** | Domain entities or raw records | Operation results, DTOs, or domain objects |
| **Transaction** | Single query or simple multi-query | May span multiple repositories in one transaction |
| **Business rules** | None — pure data access | Yes — enforces rules, coordinates operations |
| **Testability** | Mock the DB driver | Mock the repositories and external dependencies |
| **Example** | `OrderRepository.findById()` | `OrderService.placeOrder()` — validates customer, reserves inventory, charges payment, saves order, sends email |

The repository answers *how to persist/retrieve one entity*. The service answers *how to execute one business operation* that may involve multiple entities and external systems.

**Q5. What is the relationship between the Service Layer and Clean Architecture / Hexagonal Architecture?**
A: The Service Layer is the precursor concept that Clean Architecture formalises into Use Cases. They describe the same idea at different levels of rigor:

- **Service Layer (Fowler)** — a pragmatic pattern. One service class per domain concept, containing multiple related operation methods. Less prescriptive about internal structure.
- **Use Cases (Clean Architecture)** — one class per operation. Each use case has a single `execute()` method. Ports (interfaces) are explicitly defined. The Dependency Rule is explicitly enforced.

In practice, most Node.js backends implement the Service Layer pattern and call it "services." Clean Architecture codebases implement Use Cases and enforce stricter layer boundaries. Both are valid — the Service Layer is the right starting point for most teams, and the path toward Clean Architecture when complexity demands it:

```
Simple CRUD:      Controller → Service → Repository
Growing system:   Controller → Service (+ Repositories + Gateways + Events)
Complex domain:   Controller → Use Case → Domain Entities + Repositories + Ports
```

At 5 YOE, knowing where Service Layer ends and Clean Architecture begins — and being able to articulate when to make the transition — is the expected depth.

## Section 2: Implementing the Service Layer in TypeScript

**Q6. Show a complete, production-quality service implementation for an order placement flow.**
A:
```ts
// Dependencies — repository and gateway interfaces (not concrete implementations)
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<Order>;
}

interface CustomerRepository {
  findById(id: string): Promise<Customer | null>;
}

interface InventoryService {
  reserve(items: OrderItem[]): Promise<Reservation>;
  release(reservationId: string): Promise<void>;
}

interface PaymentGateway {
  charge(amount: number, currency: string, token: string): Promise<ChargeResult>;
}

interface EmailService {
  sendOrderConfirmation(to: string, order: Order): Promise<void>;
}

interface EventBus {
  publish(event: DomainEvent): Promise<void>;
}

// Input / Output DTOs — service contract, not tied to HTTP
interface PlaceOrderDto {
  customerId:   string;
  items:        Array<{ productId: string; quantity: number; unitPrice: number }>;
  paymentToken: string;
  currency:     string;
}

interface PlaceOrderResult {
  orderId:   string;
  status:    string;
  total:     number;
  currency:  string;
  createdAt: string;
}

// Service class — owns the operation, delegates everything else
class OrderService {
  constructor(
    private readonly orders:    OrderRepository,
    private readonly customers: CustomerRepository,
    private readonly inventory: InventoryService,
    private readonly payments:  PaymentGateway,
    private readonly email:     EmailService,
    private readonly events:    EventBus,
    private readonly logger:    Logger
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    this.logger.info("Placing order", { customerId: dto.customerId });

    // 1. Validate customer eligibility — application-level business rule
    const customer = await this.customers.findById(dto.customerId);
    if (!customer)        throw new NotFoundError(`Customer ${dto.customerId} not found`);
    if (customer.isBanned) throw new ForbiddenError("Customer account is suspended");

    // 2. Calculate total
    const total = dto.items.reduce((sum, i) => sum + i.unitPrice * i.quantity, 0);

    // 3. Business rule: high-value orders require approval
    if (total > 100_000) throw new ApprovalRequiredError(total);

    // 4. Reserve inventory — compensable action; must be released on failure
    let reservation: Reservation;
    try {
      reservation = await this.inventory.reserve(dto.items);
    } catch (err) {
      throw new InventoryError("Failed to reserve inventory", { cause: err });
    }

    // 5. Charge payment — if this fails, release the reservation
    let charge: ChargeResult;
    try {
      charge = await this.payments.charge(total, dto.currency, dto.paymentToken);
    } catch (err) {
      await this.inventory.release(reservation.id)
        .catch(releaseErr => this.logger.error("Failed to release reservation", releaseErr));
      throw new PaymentError("Payment failed", { cause: err });
    }

    // 6. Persist order
    const order = await this.orders.save({
      customerId: dto.customerId,
      items:      dto.items,
      total,
      currency:   dto.currency,
      chargeId:   charge.id,
      status:     "CONFIRMED",
      createdAt:  new Date(),
    });

    // 7. Non-critical side effects — log failures but don't fail the operation
    await Promise.allSettled([
      this.email.sendOrderConfirmation(customer.email, order)
        .catch(err => this.logger.warn("Confirmation email failed", { orderId: order.id, err })),
      this.events.publish({ type: "ORDER_PLACED", payload: { orderId: order.id, total } })
        .catch(err => this.logger.warn("Event publish failed", { orderId: order.id, err })),
    ]);

    this.logger.info("Order placed successfully", { orderId: order.id });

    return {
      orderId:   order.id,
      status:    order.status,
      total:     order.total,
      currency:  order.currency,
      createdAt: order.createdAt.toISOString(),
    };
  }

  async cancelOrder(orderId: string, requesterId: string, reason: string): Promise<void> {
    const order = await this.orders.findById(orderId);
    if (!order) throw new NotFoundError(`Order ${orderId} not found`);

    // Business rule: only order owner or admin can cancel
    if (order.customerId !== requesterId) {
      throw new ForbiddenError("Not authorised to cancel this order");
    }

    // Business rule: cannot cancel after shipping
    if (["SHIPPED", "DELIVERED"].includes(order.status)) {
      throw new ConflictError(`Cannot cancel order in ${order.status} status`);
    }

    await this.orders.save({ ...order, status: "CANCELLED", cancelReason: reason });

    // Refund if already charged
    if (order.chargeId) {
      await this.payments.refund(order.chargeId, order.total)
        .catch(err => this.logger.error("Refund failed — manual intervention required",
          { orderId, chargeId: order.chargeId, err }));
    }

    await this.events.publish({ type: "ORDER_CANCELLED", payload: { orderId, reason } });
  }
}
```

**Q7. How do you structure a service to avoid it becoming a god class over time?**
A: Services grow fat when they accumulate every operation related to an entity plus unrelated cross-domain concerns. Three structural techniques prevent this:

**Split by operation cohesion** — separate read operations (queries) from write operations (commands):
```ts
// ✗ — God service: reads, writes, reports, admin ops all in one class
class OrderService {
  placeOrder() {}
  cancelOrder() {}
  getOrderById() {}
  listOrdersByCustomer() {}
  generateOrderReport() {}
  bulkCancelOrders() {}    // admin
  exportOrdersToCsv() {}   // reporting
  archiveOldOrders() {}    // maintenance
}

// ✓ — Cohesive services split by responsibility
class OrderCommandService {     // write operations — modify state
  placeOrder() {}
  cancelOrder() {}
  confirmOrder() {}
}

class OrderQueryService {       // read operations — no side effects
  getOrderById() {}
  listOrdersByCustomer() {}
  searchOrders() {}
}

class OrderReportService {      // reporting — read-only, possibly different data source
  generateMonthlySummary() {}
  exportToCsv() {}
}

class OrderMaintenanceService { // admin / background ops
  bulkCancel() {}
  archiveOldOrders() {}
}
```

**Delegate to sub-services** — extract cohesive groups of steps into their own focused service:
```ts
class OrderService {
  constructor(
    private readonly pricingService:  PricingService,   // total + discount calculation
    private readonly fulfilmentService: FulfilmentService, // inventory + shipping
    private readonly notificationService: NotificationService
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    const pricing  = await this.pricingService.calculate(dto.items, dto.promoCode);
    const reserv   = await this.fulfilmentService.reserve(dto.items);
    // ... orchestrate; don't implement sub-domain logic inline
  }
}
```

**Use the Single Responsibility Principle as the test** — if you can describe the service's purpose without "and," it has appropriate scope.

**Q8. How do you handle transactions in the service layer — spanning multiple repository calls?**
A: Transactions must be coordinated at the service level, not inside individual repositories, because only the service knows which operations constitute a single unit of work:
```ts
// Approach 1 — Unit of Work / Transaction object passed through
interface UnitOfWork {
  begin(): Promise<void>;
  commit(): Promise<void>;
  rollback(): Promise<void>;
  orders:   OrderRepository;
  inventory: InventoryRepository;
}

class OrderService {
  constructor(private uow: UnitOfWork) {}

  async transferOrder(fromCustomerId: string, toCustomerId: string, orderId: string): Promise<void> {
    await this.uow.begin();
    try {
      const order = await this.uow.orders.findById(orderId);
      if (!order) throw new NotFoundError(orderId);

      await this.uow.orders.save({ ...order, customerId: toCustomerId });
      await this.uow.inventory.updateOwnership(orderId, toCustomerId);

      await this.uow.commit();
    } catch (err) {
      await this.uow.rollback();
      throw err;
    }
  }
}

// Approach 2 — Transaction callback / context pattern (Prisma-style)
class OrderService {
  constructor(private prisma: PrismaClient, private events: EventBus) {}

  async placeOrder(dto: PlaceOrderDto): Promise<Order> {
    return this.prisma.$transaction(async (tx) => {
      // All operations within this callback share the same DB transaction
      const customer = await tx.customer.findUniqueOrThrow({ where: { id: dto.customerId } });
      const order    = await tx.order.create({ data: { customerId: dto.customerId, /* ... */ } });

      for (const item of dto.items) {
        await tx.inventory.update({
          where: { productId: item.productId },
          data:  { reserved: { increment: item.quantity } },
        });
      }

      return order;
      // If any step throws, Prisma automatically rolls back the entire transaction
    });
  }
}

// Approach 3 — Saga pattern for distributed transactions (no single DB transaction)
class OrderSagaService {
  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    const saga = new OrderPlacementSaga();

    // Step 1 — with compensating action
    const reservation = await this.inventory.reserve(dto.items);
    saga.addCompensation(() => this.inventory.release(reservation.id));

    // Step 2 — with compensating action
    const charge = await this.payments.charge(dto.total, dto.paymentToken);
    saga.addCompensation(() => this.payments.refund(charge.id, dto.total));

    // Step 3 — persist (point of no return)
    try {
      const order = await this.orders.save({ /* ... */ });
      return { orderId: order.id };
    } catch (err) {
      await saga.compensate(); // undo steps 1 and 2 in reverse order
      throw err;
    }
  }
}
```

## Section 3: Service Layer Design Decisions

**Q9. Should services call other services — and how do you avoid circular dependencies?**
A: Services calling other services is common and often correct, but requires deliberate design to avoid coupling and circular dependencies:

**When inter-service calls are appropriate:**
```ts
// Notification flows through a dedicated service — OrderService calls NotificationService
class OrderService {
  constructor(private notifications: NotificationService) {}

  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    const order = await this.createAndPersistOrder(dto);
    await this.notifications.notifyOrderPlaced(order); // appropriate delegation
    return toResult(order);
  }
}
```

**When to use events instead** — if two services would need to know about each other (circular dependency risk) or the interaction is a side effect the primary service shouldn't coordinate:
```ts
// ✗ — Circular: OrderService → LoyaltyService → OrderService (for order history)
class OrderService {
  constructor(private loyalty: LoyaltyService) {} // would create circular dep
  async placeOrder(dto: PlaceOrderDto) {
    const order = await this.saveOrder(dto);
    await this.loyalty.awardPoints(dto.customerId, order.total); // tight coupling ✗
  }
}

// ✓ — Decouple via events; LoyaltyService listens, OrderService doesn't know
class OrderService {
  async placeOrder(dto: PlaceOrderDto) {
    const order = await this.saveOrder(dto);
    await this.events.publish({ type: "ORDER_PLACED", payload: { customerId: dto.customerId, total: order.total } });
    // LoyaltyService subscribes to ORDER_PLACED — OrderService is unaware
  }
}
```

**Detecting circular dependencies** — use `madge` or `dependency-cruiser` in CI:
```bash
npx madge --circular src/services/
npx depcruise --validate .dependency-cruiser.cjs src/services/
```

**Q10. How do services handle input validation — and how does that differ from DTO validation in the controller?**
A: There are two distinct validation layers, and conflating them causes either under-validation or over-coupling:

**Controller/DTO validation (structural)** — validates the *shape* and *format* of input before it reaches the service. Answers: "Is this a valid HTTP request?" Uses schema validators like Zod, class-validator, or Joi:
```ts
// Controller layer — validate structure and format
import { z } from "zod";

const PlaceOrderSchema = z.object({
  customerId:   z.string().uuid(),
  items:        z.array(z.object({
    productId: z.string().uuid(),
    quantity:  z.number().int().min(1).max(100),
    unitPrice: z.number().positive(),
  })).min(1).max(50),
  paymentToken: z.string().min(1),
  currency:     z.enum(["INR", "USD", "EUR"]),
});

app.post("/orders", async (req, res) => {
  const parsed = PlaceOrderSchema.safeParse(req.body);
  if (!parsed.success) return res.status(400).json({ errors: parsed.error.issues });
  const result = await orderService.placeOrder(parsed.data); // validated before service call
  res.status(201).json(result);
});
```

**Service validation (semantic / business)** — validates the *meaning* and *state* of input after structural validation passes. Answers: "Does this operation make sense given current system state?":
```ts
// Service layer — validate business semantics
class OrderService {
  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    // Semantic validation — not possible in schema validators
    const customer = await this.customers.findById(dto.customerId);
    if (!customer)          throw new NotFoundError("Customer not found");
    if (customer.isBanned)  throw new ForbiddenError("Account suspended");

    for (const item of dto.items) {
      const product = await this.products.findById(item.productId);
      if (!product)                  throw new NotFoundError(`Product ${item.productId}`);
      if (!product.isAvailable)      throw new ConflictError(`Product unavailable: ${item.productId}`);
      if (item.quantity > product.stock) throw new ConflictError(`Insufficient stock: ${item.productId}`);
    }

    // Business rule validation
    const total = dto.items.reduce((sum, i) => sum + i.unitPrice * i.quantity, 0);
    if (total > customer.creditLimit) throw new PaymentError("Exceeds customer credit limit");
  }
}
```

The rule: schema validators don't need a database; service validators do. Never mix them — keeping structural and semantic validation in separate layers makes each independently testable.

**Q11. How do you design service method return types — should services return domain entities or DTOs?**
A: This is a consequential design choice with real trade-offs:

**Return domain entities** — appropriate when the caller (controller or another service) needs to work with the entity's methods, or when you want to avoid duplicating the mapping logic:
```ts
// Service returns domain entity — controller maps to response
class CustomerService {
  async getById(id: string): Promise<Customer> {  // returns domain entity
    const customer = await this.repo.findById(id);
    if (!customer) throw new NotFoundError(id);
    return customer; // controller decides how to format
  }
}

// Controller does the mapping
app.get("/customers/:id", async (req, res) => {
  const customer = await customerService.getById(req.params.id);
  res.json({                              // controller formats for HTTP
    id:    customer.id,
    name:  customer.fullName(),           // domain method
    email: customer.email,
    tier:  customer.getLoyaltyTier(),     // domain method
  });
});
```

**Return DTOs** — appropriate when the service is the boundary between domain and delivery, and you want the controller to be completely thin:
```ts
// Service returns DTO — controller has nothing to do except send the response
interface CustomerDto {
  id:    string;
  name:  string;
  email: string;
  tier:  string;
}

class CustomerService {
  async getById(id: string): Promise<CustomerDto> {
    const customer = await this.repo.findById(id);
    if (!customer) throw new NotFoundError(id);
    return {                             // service does the mapping
      id:    customer.id,
      name:  customer.fullName(),
      email: customer.email,
      tier:  customer.getLoyaltyTier(),
    };
  }
}

app.get("/customers/:id", async (req, res) => {
  const dto = await customerService.getById(req.params.id);
  res.json(dto); // controller is trivially thin
});
```

**Practical guidance:**
- Services called by multiple delivery mechanisms (REST + GraphQL + WebSocket) — return DTOs. Each delivery mechanism needs different shapes; the service shouldn't know about those differences.
- Services called only by one controller layer — returning domain entities and mapping in the controller is acceptable and simpler.
- Read-only queries — always return DTOs; loading a full entity with all methods just to format a response is wasteful.
- Commands (write operations) — return only what the caller needs (the new ID, the updated status) — not the whole entity.

## Section 4: Service Layer in NestJS

**Q12. How does the Service Layer manifest in NestJS, and what are the architectural pitfalls specific to NestJS services?**
A:
```ts
// NestJS service — correct usage
// orders/order.service.ts
@Injectable()
export class OrderService {
  constructor(
    @InjectRepository(OrderEntity) private orderRepo: Repository<OrderEntity>,
    private readonly paymentService: PaymentService,  // NestJS injects this
    private readonly eventEmitter:   EventEmitter2,
    private readonly logger:         Logger
  ) {}

  async placeOrder(dto: PlaceOrderDto, userId: string): Promise<PlaceOrderResponseDto> {
    // Business logic lives here — NOT in the controller
    const order = this.orderRepo.create({
      userId,
      items:  dto.items,
      status: "PENDING",
      total:  this.calculateTotal(dto.items),
    });

    await this.orderRepo.manager.transaction(async (manager) => {
      await manager.save(order);
      await this.paymentService.chargeWithinTransaction(order.total, dto.paymentToken, manager);
    });

    this.eventEmitter.emit("order.placed", new OrderPlacedEvent(order));
    return OrderMapper.toResponseDto(order);
  }

  private calculateTotal(items: OrderItemDto[]): number {
    return items.reduce((sum, i) => sum + i.unitPrice * i.quantity, 0);
  }
}

// NestJS controller — delegate everything to service, handle HTTP concerns only
// orders/order.controller.ts
@Controller("orders")
@UseGuards(JwtAuthGuard)        // auth is a cross-cutting concern, not in service
export class OrderController {
  constructor(private readonly orderService: OrderService) {}

  @Post()
  @HttpCode(201)
  async placeOrder(
    @Body() dto: PlaceOrderDto,     // NestJS validates via class-validator + ValidationPipe
    @CurrentUser() user: JwtPayload // custom decorator extracts user from token
  ): Promise<PlaceOrderResponseDto> {
    return this.orderService.placeOrder(dto, user.sub); // thin controller
  }

  @Delete(":id")
  @HttpCode(204)
  async cancelOrder(
    @Param("id", ParseUUIDPipe) id: string,
    @Body() dto: CancelOrderDto,
    @CurrentUser() user: JwtPayload
  ): Promise<void> {
    return this.orderService.cancelOrder(id, user.sub, dto.reason);
  }
}
```

**Common NestJS service pitfalls:**
```ts
// ✗ Pitfall 1 — HTTP context bleeding into the service
@Injectable()
export class OrderService {
  async placeOrder(@Req() req: Request): Promise<Order> { // ← HTTP object in service ✗
    const userId = req.user.id;                           // now tied to HTTP context
  }
}

// ✓ Fix — extract what the service needs before calling it
@Injectable()
export class OrderService {
  async placeOrder(dto: PlaceOrderDto, userId: string): Promise<Order> { } // clean

// ✗ Pitfall 2 — response formatting in the service
@Injectable()
export class OrderService {
  async getOrder(id: string): Promise<{ statusCode: number; data: Order }> { // ← HTTP shape ✗
    return { statusCode: 200, data: order };
  }
}

// ✓ Fix — return domain data; controller/interceptor handles HTTP shape

// ✗ Pitfall 3 — business logic in the module (circular bypass)
@Module({
  providers: [OrderService, PaymentService],
  // Some devs put orchestration logic in module factories to avoid circular deps ✗
})

// ✓ Fix — restructure services; use events for circular communication
```

**Q13. How do you handle cross-module service calls in NestJS without creating tightly coupled modules?**
A:
```ts
// ✗ — Direct cross-module import creates tight coupling
@Module({
  imports: [PaymentModule, InventoryModule, NotificationModule], // all imported directly
  providers: [OrderService],
})
export class OrderModule {}

// Three strategies for loose coupling:

// Strategy 1 — Events (most decoupled)
// OrderService publishes; other modules subscribe — no imports needed
@Injectable()
export class OrderService {
  constructor(private eventEmitter: EventEmitter2) {}

  async placeOrder(dto: PlaceOrderDto): Promise<Order> {
    const order = await this.saveOrder(dto);
    this.eventEmitter.emit("order.placed", order); // no direct module dependency
    return order;
  }
}

@Injectable()
export class LoyaltyListener {
  @OnEvent("order.placed")
  async handleOrderPlaced(order: Order): Promise<void> {
    await this.loyaltyService.awardPoints(order.customerId, order.total);
  }
}

// Strategy 2 — Shared interfaces module
// Define interfaces in a shared contracts module; implement in feature modules
@Module({
  exports: [PAYMENT_GATEWAY_TOKEN], // exports an abstract token, not a concrete class
})
export class PaymentContractsModule {}

// OrderModule imports the interface token, not the concrete PaymentModule
@Module({
  imports: [PaymentContractsModule], // only the interface — not the full PaymentModule
  providers: [OrderService],
})
export class OrderModule {}

// Strategy 3 — Facade service at a higher module level
// A higher-level module orchestrates lower-level ones
@Module({
  imports: [OrderModule, PaymentModule, InventoryModule],
```

## Section 5: Testing the Service Layer

**Q14. How do you unit test a service class with multiple injected dependencies?**
A: Each dependency is replaced with a fake or a mock — the service's behavior is tested in complete isolation from infrastructure:
```ts
// Fakes — lightweight working implementations of interfaces
class InMemoryOrderRepository implements OrderRepository {
  private store = new Map<string, Order>();

  async findById(id: string): Promise<Order | null> {
    return this.store.get(id) ?? null;
  }

  async save(order: Order): Promise<Order> {
    const saved = { ...order, id: order.id ?? generateId() };
    this.store.set(saved.id, saved);
    return saved;
  }

  all(): Order[] { return [...this.store.values()]; }
}

class FakePaymentGateway implements PaymentGateway {
  private behavior: "succeed" | "fail" = "succeed";
  public calls: Array<{ amount: number; token: string }> = [];

  willSucceed() { this.behavior = "succeed"; }
  willFail()    { this.behavior = "fail";    }

  async charge(amount: number, currency: string, token: string): Promise<ChargeResult> {
    this.calls.push({ amount, token });
    if (this.behavior === "fail") throw new PaymentError("Card declined");
    return { id: `ch_${Date.now()}`, amount, currency };
  }
}

// Unit tests — no HTTP server, no database, no external APIs
describe("OrderService", () => {
  let service:     OrderService;
  let orderRepo:   InMemoryOrderRepository;
  let customerRepo: InMemoryCustomerRepository;
  let payments:    FakePaymentGateway;
  let inventory:   FakeInventoryService;
  let email:       FakeEmailService;
  let events:      InMemoryEventBus;

  beforeEach(() => {
    orderRepo    = new InMemoryOrderRepository();
    customerRepo = new InMemoryCustomerRepository();
    payments     = new FakePaymentGateway();
    inventory    = new FakeInventoryService();
    email        = new FakeEmailService();
    events       = new InMemoryEventBus();

    service = new OrderService(orderRepo, customerRepo, inventory, payments, email, events,
      new NullLogger());
  });

  describe("placeOrder", () => {
    it("creates and persists an order with correct total", async () => {
      const customer = buildCustomer({ isBanned: false });
      customerRepo.seed(customer);

      const result = await service.placeOrder({
        customerId:   customer.id,
        items:        [
          { productId: "prod-1", quantity: 2, unitPrice: 500 },
          { productId: "prod-2", quantity: 1, unitPrice: 300 },
        ],
        paymentToken: "tok_test",
        currency:     "INR",
      });

      expect(result.total).toBe(1300);          // 2×500 + 1×300
      expect(result.status).toBe("CONFIRMED");
      expect(orderRepo.all()).toHaveLength(1);
    });

    it("throws NotFoundError when customer does not exist", async () => {
      await expect(service.placeOrder({
        customerId: "non-existent",
        items: [{ productId: "p1", quantity: 1, unitPrice: 100 }],
        paymentToken: "tok",
        currency: "INR",
      })).rejects.toThrow(NotFoundError);
    });

    it("releases inventory reservation when payment fails", async () => {
      const customer = buildCustomer();
      customerRepo.seed(customer);
      payments.willFail();

      await expect(service.placeOrder({
        customerId: customer.id,
        items: [{ productId: "p1", quantity: 1, unitPrice: 100 }],
        paymentToken: "tok_fail",
        currency: "INR",
      })).rejects.toThrow(PaymentError);

      expect(inventory.releasedCount).toBe(1);  // compensation verified
      expect(orderRepo.all()).toHaveLength(0);   // order not saved
    });

    it("publishes ORDER_PLACED event on success", async () => {
      const customer = buildCustomer();
      customerRepo.seed(customer);

      await service.placeOrder({
        customerId: customer.id,
        items: [{ productId: "p1", quantity: 1, unitPrice: 500 }],
        paymentToken: "tok_test",
        currency: "INR",
      });

      const published = events.getPublished("ORDER_PLACED");
      expect(published).toHaveLength(1);
      expect(published[0].payload.total).toBe(500);
    });

    it("does not fail order when confirmation email fails", async () => {
      const customer = buildCustomer();
      customerRepo.seed(customer);
      email.willFail(); // email service is down

      // Email failure should NOT propagate — order still succeeds
      await expect(service.placeOrder({
        customerId: customer.id,
        items: [{ productId: "p1", quantity: 1, unitPrice: 100 }],
        paymentToken: "tok_test",
        currency: "INR",
      })).resolves.not.toThrow();

      expect(orderRepo.all()).toHaveLength(1); // order saved despite email failure
    });
  });
});
```

**Q15. What is the difference between unit testing and integration testing a service, and when do you use each?**
A:

| Aspect | Unit Test | Integration Test |
|---|---|---|
| **Dependencies** | All replaced with fakes/mocks | Real DB, real external service, or test container |
| **Speed** | Milliseconds | Seconds to minutes |
| **Isolation** | Complete — tests one service in isolation | Partial — tests service + repository + DB together |
| **What it catches** | Logic errors, edge cases, compensation flows | Query errors, schema mismatches, transaction behavior |
| **When to write** | For every business rule and edge case | For critical data persistence paths; complex queries |
| **Database** | None | SQLite in-memory, Docker Postgres, or test schema |

```ts
// Integration test — service + real Prisma + test database
describe("OrderService integration", () => {
  let prisma:   PrismaClient;
  let service:  OrderService;

  beforeAll(async () => {
    prisma  = new PrismaClient({ datasources: { db: { url: process.env.TEST_DB_URL } } });
    await prisma.$connect();
    service = buildServiceWithRealDeps(prisma); // real repositories, fake external gateways
  });

  afterEach(async () => {
    // Clean up in reverse FK order
    await prisma.orderItem.deleteMany();
    await prisma.order.deleteMany();
  });

  afterAll(async () => { await prisma.$disconnect(); });

  it("rolls back order AND inventory on payment failure", async () => {
    const customer = await prisma.customer.create({ data: buildCustomerData() });
    const product  = await prisma.product.create({ data: { stock: 5, ...buildProductData() } });

    const fakePayments = new FakePaymentGateway();
    fakePayments.willFail();
    service = buildServiceWithRealDeps(prisma, { payments: fakePayments });

    await expect(service.placeOrder({

      items:        [{ productId: product.id, quantity: 2, unitPrice: product.price }],

    // Verify database state — no order created, no stock decremented
    const orders  = await prisma.order.findMany();
    const updated = await prisma.product.findUnique({ where: { id: product.id } });
    expect(orders).toHaveLength(0);
    expect(updated!.stock).toBe(5); // stock unchanged — reservation released
  });
```

## Section 6: Advanced Service Layer Patterns

**Q16. How do you implement a service layer that supports multiple delivery mechanisms — REST, GraphQL, and message queue consumers — without duplicating logic?**
A: The service is the single implementation; each delivery mechanism is a thin adapter:

```ts
// The service — one implementation, no delivery-mechanism knowledge
class UserService {
  async register(dto: RegisterUserDto): Promise<RegisterUserResult> { /* ... */ }
  async login(dto: LoginDto): Promise<LoginResult> { /* ... */ }
  async updateProfile(userId: string, dto: UpdateProfileDto): Promise<UserProfile> { /* ... */ }
}

// REST adapter — maps HTTP → service → HTTP response
@Controller("users")
export class UserRestController {
  constructor(private users: UserService) {}

  @Post("register")
  @HttpCode(201)
  async register(@Body() dto: RegisterUserDto) {
    return this.users.register(dto); // service call — no business logic here
  }
}

// GraphQL adapter — maps GraphQL args → service → GraphQL response
@Resolver("User")
export class UserResolver {
  constructor(private users: UserService) {}

  @Mutation(() => RegisterUserResponse)
  async registerUser(@Args("input") input: RegisterUserInput): Promise<RegisterUserResponse> {
    const result = await this.users.register({
      email:    input.email,
      password: input.password,
      name:     input.name,
    });
    return { userId: result.userId, token: result.token };
  }
}

// Message queue consumer adapter — maps queue message → service
@Injectable()
export class UserEventConsumer {
  constructor(private users: UserService) {}

  @EventPattern("user.self_register_requested") // from a message queue
  async handleSelfRegistration(@Payload() message: SelfRegisterMessage): Promise<void> {
    await this.users.register({
      email:    message.email,
      password: message.temporaryPassword,
      name:     message.name,
    });
    // No response — fire and forget for async flows
  }
}

// CLI adapter — maps command-line args → service
async function registerUserCli(args: ParsedCliArgs): Promise<void> {
  const service = buildUserService();
  const result  = await service.register({
    email:    args.email,
    password: args.password,
    name:     args.name,
  });
  console.log(`User registered: ${result.userId}`);
}

// The register logic lives ONCE — in UserService.register()
// REST, GraphQL, queue consumer, and CLI all call the same method
```

**Q17. How does the Service Layer handle idempotency — preventing duplicate operations when a client retries?**
A: Idempotency must be implemented at the service level, not the HTTP layer, because it must protect the business operation regardless of how it is triggered:
```ts
interface IdempotencyStore {
  get(key: string): Promise<IdempotencyRecord | null>;
  set(key: string, result: unknown, ttlSeconds: number): Promise<void>;
}

class OrderService {
  constructor(
    private readonly orders:      OrderRepository,
    private readonly payments:    PaymentGateway,
    private readonly idempotency: IdempotencyStore
  ) {}

  async placeOrder(dto: PlaceOrderDto, idempotencyKey?: string): Promise<PlaceOrderResult> {
    // Idempotency check — return cached result if this key was seen before
    if (idempotencyKey) {
      const cached = await this.idempotency.get(idempotencyKey);
      if (cached) {
        this.logger.info("Returning cached result for idempotency key", { idempotencyKey });
        return cached.result as PlaceOrderResult;
      }
    }

    // Execute the operation
    const result = await this.executeOrderPlacement(dto);

    // Cache the result — 24 hours TTL
    if (idempotencyKey) {
      await this.idempotency.set(idempotencyKey, result, 86_400);
    }

    return result;
  }

  private async executeOrderPlacement(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    // ... full order placement logic
  }
}

// Redis-backed idempotency store — infrastructure implementation
class RedisIdempotencyStore implements IdempotencyStore {
  constructor(private redis: Redis) {}

  async get(key: string): Promise<IdempotencyRecord | null> {
    const raw = await this.redis.get(`idempotency:${key}`);
    return raw ? JSON.parse(raw) : null;
  }

  async set(key: string, result: unknown, ttlSeconds: number): Promise<void> {
    await this.redis.setex(
      `idempotency:${key}`,
      ttlSeconds,
      JSON.stringify({ result, createdAt: new Date().toISOString() })
    );
  }
}

// REST controller passes Idempotency-Key header to service
@Post("orders")
async placeOrder(@Body() dto: PlaceOrderDto, @Headers("Idempotency-Key") key?: string) {
  return this.orderService.placeOrder(dto, key); // controller passes through, service handles it
}
```

**Q18. How do you implement audit logging in the service layer without polluting every service method?**
A: Use the Decorator pattern to wrap services with audit logging — the service itself stays focused on business logic:
```ts
// Service interface — defines the contract
interface OrderServiceInterface {
  placeOrder(dto: PlaceOrderDto, userId: string): Promise<PlaceOrderResult>;
  cancelOrder(id: string, userId: string, reason: string): Promise<void>;
}

// Concrete service — no audit logging
class OrderService implements OrderServiceInterface {
  async placeOrder(dto: PlaceOrderDto, userId: string): Promise<PlaceOrderResult> {
    // business logic only
  }
  async cancelOrder(id: string, userId: string, reason: string): Promise<void> {
    // business logic only
  }
}

// Decorator — wraps the service, adds audit logging transparently
class AuditedOrderService implements OrderServiceInterface {
  constructor(
    private readonly inner: OrderServiceInterface,
    private readonly audit: AuditLogService
  ) {}

  async placeOrder(dto: PlaceOrderDto, userId: string): Promise<PlaceOrderResult> {
    const start = Date.now();
    try {
      const result = await this.inner.placeOrder(dto, userId);
      await this.audit.log({
        action:      "ORDER_PLACED",
        userId,
        resourceId:  result.orderId,
        metadata:    { total: result.total, itemCount: dto.items.length },
        durationMs:  Date.now() - start,
        outcome:     "SUCCESS",
      });
      return result;
    } catch (err) {
      await this.audit.log({
        action:     "ORDER_PLACED",
        userId,
        metadata:   { error: (err as Error).message },
        durationMs: Date.now() - start,
        outcome:    "FAILURE",
      });
      throw err;
    }
  }

  async cancelOrder(id: string, userId: string, reason: string): Promise<void> {
    try {
      await this.inner.cancelOrder(id, userId, reason);
      await this.audit.log({ action: "ORDER_CANCELLED", userId, resourceId: id,
        metadata: { reason }, outcome: "SUCCESS" });
    } catch (err) {
      await this.audit.log({ action: "ORDER_CANCELLED", userId, resourceId: id,
        metadata: { reason, error: (err as Error).message }, outcome: "FAILURE" });
      throw err;
    }
  }
}

// Composition root — wrap service with audit decorator
const baseService   = new OrderService(orderRepo, payments, events, logger);
const orderService  = new AuditedOrderService(baseService, auditLogService);
// All callers use orderService — they get audit logging automatically
```

## Section 7: Scenario / System Design Style Questions

**Q19. "A codebase has all its business logic split between controllers and Mongoose model hooks (pre-save, post-save middleware). What are the problems, and how do you introduce a service layer incrementally?"**
A: Name the specific problems first:

1. **Logic in controllers** — each endpoint reimplements rules. A rule change (e.g., new validation) requires finding and updating every controller that touches the entity.
2. **Logic in Mongoose hooks** — `pre-save` hooks run on every save, including administrative saves, test data seeding, and migration scripts that should bypass business rules. Hooks are invisible to callers and make behavior unpredictable.
3. **No single source of truth** — business logic is split across HTTP handlers and database middleware. There is no single place to read to understand what "saving an order" means.
4. **Untestable** — to test the logic, you need both an HTTP server (for controller logic) and a database connection (for hook logic).

Incremental migration:
```ts
// Phase 1 — Extract inline controller logic into service methods
// Before
app.post("/orders", async (req, res) => {
  const total = req.body.items.reduce(...); // business logic in controller
  if (total > 100_000) return res.status(422)...;
  const order = await Order.create({ ...req.body, total });
  res.json(order);
});

// After Phase 1 — controller delegates, service owns logic
class OrderService {
  async create(dto: CreateOrderDto): Promise<Order> {
    const total = this.calculateTotal(dto.items);    // moved from controller
    if (total > 100_000) throw new ApprovalRequiredError(total); // moved from controller
    return Order.create({ ...dto, total });
  }
}
app.post("/orders", async (req, res) => {
  const order = await orderService.create(req.body); // thin controller
  res.status(201).json(order);
});

// Phase 2 — Move Mongoose hook logic into the service
// Before — hook runs on every save, including seed scripts
OrderSchema.pre("save", function() {
  if (this.isNew) this.orderNumber = generateOrderNumber(); // always runs ✗
});

// After Phase 2 — service controls when this logic runs
class OrderService {
  async create(dto: CreateOrderDto): Promise<Order> {
    const orderNumber = generateOrderNumber(); // service controls this ✓
    return Order.create({ ...dto, orderNumber });
  }
}
// Remove the Mongoose hook — it no longer fires unexpectedly during seeding

// Phase 3 — replace Mongoose models with repository interfaces
//           (optional — if Clean Architecture is the target)
```

**Q20. "Design the service layer for a multi-tenant SaaS application where every operation must be scoped to a tenant, audit-logged, and rate-limited per tenant."**
A: Cross-cutting concerns (tenant scoping, audit, rate limiting) are applied through service decorators and a tenant context — the core service stays focused on business logic:

```ts
// Tenant context — established at the HTTP layer, propagated through the call chain
interface TenantContext {
  tenantId: string;
  userId:   string;
  plan:     "free" | "pro" | "enterprise";
}

// Base service — no tenant awareness; pure business logic
class DocumentService {
  constructor(private docs: DocumentRepository) {}

  async create(dto: CreateDocumentDto, tenantId: string): Promise<Document> {
    // tenantId scopes the operation — all repository calls use it
    return this.docs.create({ ...dto, tenantId });
  }

  async list(tenantId: string, filter: DocumentFilter): Promise<Document[]> {
    return this.docs.findByTenant(tenantId, filter);
  }
}

// Decorator 1 — Rate limiting per tenant
class RateLimitedDocumentService implements DocumentServiceInterface {
  constructor(
    private inner:      DocumentServiceInterface,
    private rateLimit:  RateLimitService
  ) {}

  async create(dto: CreateDocumentDto, ctx: TenantContext): Promise<Document> {
    await this.rateLimit.check(`create_document:${ctx.tenantId}`, {
      limit:   ctx.plan === "enterprise" ? 1000 : ctx.plan === "pro" ? 100 : 10,
      windowMs: 60_000, // per minute
    });
    return this.inner.create(dto, ctx);
  }

  // ... other methods similarly rate-limited
}

// Decorator 2 — Audit logging per operation
class AuditedDocumentService implements DocumentServiceInterface {
  constructor(
    private inner: DocumentServiceInterface,
    private audit: AuditService
  ) {}

  async create(dto: CreateDocumentDto, ctx: TenantContext): Promise<Document> {
    const doc = await this.inner.create(dto, ctx);
    await this.audit.record({
      tenantId:   ctx.tenantId,
      userId:     ctx.userId,
      action:     "DOCUMENT_CREATED",
      resourceId: doc.id,
      timestamp:  new Date(),
    });
    return doc;
  }
}

// Decorator 3 — Plan enforcement (feature gating)
class PlanGatedDocumentService implements DocumentServiceInterface {
  constructor(private inner: DocumentServiceInterface, private plans: PlanService) {}

  async create(dto: CreateDocumentDto, ctx: TenantContext): Promise<Document> {
    const currentCount = await this.plans.getDocumentCount(ctx.tenantId);
    const limit        = await this.plans.getDocumentLimit(ctx.plan);

    if (currentCount >= limit) {
      throw new PlanLimitError(`Document limit (${limit}) reached for ${ctx.plan} plan`);
    }

    return this.inner.create(dto, ctx);
  }
}

// Composition root — stack decorators; order matters (rate limit first, then plan gate, then audit)
const documentService = new AuditedDocumentService(
  new PlanGatedDocumentService(
    new RateLimitedDocumentService(
      new DocumentService(documentRepo),
      rateLimitService
    ),
    planService
  ),
  auditService
);

// Controller — extracts tenant context from JWT, passes to service
@Post("documents")
async createDocument(
  @Body() dto: CreateDocumentDto,
  @TenantContext() ctx: TenantContext // custom decorator reads from JWT
): Promise<Document> {
  return this.documentService.create(dto, ctx);
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Fat Controller | Service Layer | Clean Architecture Use Cases |
|---|---|---|---|
| **Business logic location** | Route handler | Service class | Use Case class (one per operation) |
| **Reusable across delivery mechanisms?** | No — tied to HTTP | Yes — plain class | Yes — pure dependency injection |
| **Testable without HTTP server?** | No | Yes | Yes |
| **Testable without database?** | No | Yes (with fakes) | Yes (with fakes + domain entities) |
| **Domain entities?** | Usually not | Optional | Mandatory — entities enforce invariants |
| **Framework coupling** | Full | Minimal | None in domain/application layers |
| **Transaction management** | Inline in handler | Service method | Use case method |
| **When to use** | Prototypes only | Most production systems | Complex domains, long-lived systems |

## Service Layer Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **Fat Service** | Service has 30+ methods spanning unrelated operations | Split by command/query; extract sub-services |
| **Anemic Service** | Service just forwards calls to repository with no logic | Move business logic back to the service; consider removing the indirection |
| **HTTP-aware Service** | Service parameters include `req`, `res`, or HTTP status codes | Accept DTOs only; let the controller handle HTTP concerns |
| **Service calls Service in a circle** | OrderService → LoyaltyService → OrderService | Use domain events; restructure to break the cycle |
| **Mongoose hook leakage** | Business rules in ORM hooks instead of service methods | Move hook logic to service; remove ORM hooks |
| **God Transaction** | One service method wraps 20 operations in a single DB transaction | Split into smaller operations; use saga for cross-service compensation |
| **Missing compensation** | Service reserves inventory then charges payment — no rollback on payment failure | Add compensation logic; implement saga pattern for multi-step flows |
| **Cross-cutting logic inline** | Audit logging, rate limiting copied into every method | Extract to decorator; apply at composition root |
| **Service returns `Response` shape** | Service returns `{ statusCode: 200, data: ... }` | Service returns domain data; controller formats response |

---

**Tip for the interview:** At the 5 YOE level, "what is the Service Layer" surfaces as: why is this controller impossible to test (business logic inside route handlers), how do you share the same order placement logic between a REST endpoint and a message queue consumer (service layer is the single implementation), how do you enforce that all operations are audit-logged without copy-pasting code (decorator pattern on the service interface), or how do you prevent a multi-step operation from leaving the system in a partial state (compensation logic in the service, saga pattern for distributed flows). The sharp answer immediately names the fat controller as the problem the pattern solves, shows the thin controller / focused service split, distinguishes structural validation (controller, schema validators) from semantic validation (service, checks against current system state), and addresses at least one cross-cutting concern (transactions, audit logging, or idempotency) using a concrete technique (decorator, Unit of Work, or idempotency store). Knowing the distinction between service layer and Clean Architecture use cases — "a service owns multiple related operations; a use case owns exactly one and has a single `execute()` method" — is the architectural depth that lands at 5 YOE.
