# JavaScript / TypeScript (Node.js & Backend Design Patterns): Unit of Work — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Unit of Work pattern?**
A: The Unit of Work pattern, described by Martin Fowler in *Patterns of Enterprise Application Architecture* (2002), maintains a list of objects affected by a business transaction and coordinates the writing out of changes and the resolution of concurrency problems. In practical terms, it acts as a **business-transaction-scoped context** that:

- Tracks which domain objects have been created, modified, or deleted during the course of a business operation.
- Defers all writes to the database until the operation is complete.
- Commits all changes atomically in a single database transaction — or rolls everything back if any step fails.
- Coordinates identity mapping, change detection, and concurrency control within a single operation.

The pattern answers a fundamental question in multi-step business operations: *how do you ensure that ten sequential operations either all succeed together or all fail together, without manually managing a database transaction in every caller?* The Unit of Work is the object that owns and manages that transaction boundary.

**Q2. What problem does the Unit of Work solve that a plain database transaction cannot?**
A: A plain database transaction handles atomicity at the *infrastructure* level — it ensures SQL statements succeed or fail together. But it does not address the *application* level coordination problem: which objects should be written, in what order, and how to avoid writing the same object twice or missing a write entirely.

Without Unit of Work, the problems are:

**Scattered transaction management** — each repository or service method opens its own connection or transaction, making it impossible to span multiple repositories in one atomic operation:
```ts
// Without UoW — each call is its own transaction; no atomicity across them
const order    = await orderRepo.save(newOrder);    // transaction 1 — commits
const payment  = await paymentRepo.save(newPayment); // transaction 2 — if this fails,
                                                     // order is already committed ✗
await inventoryRepo.decrement(items);               // transaction 3 — partial state if earlier fails
```

**Duplicate writes** — if the same entity is modified and saved by two different parts of the code within the same business operation, it gets written twice (or the second write overwrites the first):
```ts
// Without UoW — entity saved twice from different service methods
const order = await orderRepo.findById(id);
order.status = "CONFIRMED";
await orderRepo.save(order); // write 1

const updatedOrder = await anotherService.process(order);
await orderRepo.save(updatedOrder); // write 2 — duplicate, potential race ✗
```

**Missing writes** — an entity is modified in memory but never persisted because the developer forgot to call `save()`:
```ts
order.addItem(newItem); // in-memory change
await sendEmail(order); // email sent but order never saved ✗
```

Unit of Work solves all three: it owns the transaction, tracks all modified objects automatically, and flushes all changes in one atomic commit at the end of the business operation.

**Q3. What are the core responsibilities of a Unit of Work?**
A:
- **Transaction lifecycle** — begins a transaction when created (or lazily on first write), commits on `commit()`, rolls back on `rollback()` or unhandled exception.
- **Change tracking** — maintains three lists: *new* (entities to INSERT), *dirty* (entities to UPDATE), and *deleted* (entities to DELETE). Tracks entities as they are registered by repositories.
- **Identity map** — ensures that within one Unit of Work, each entity is loaded at most once. If two parts of the code ask for the same entity by ID, they get the same in-memory instance — not two separate copies that could diverge.
- **Ordered commit** — determines the correct order to flush changes (e.g., insert parent before child, delete child before parent) to respect foreign key constraints.
- **Concurrency control** — implements optimistic or pessimistic locking strategies to detect and handle concurrent modification of the same entity.

**Q4. How does Unit of Work relate to the Repository pattern?**
A: They are designed to work together — they are complementary, not alternatives:

- **Repository** — provides a domain-oriented interface for querying and persisting a single aggregate type. It hides the data access mechanism from the domain layer. A repository method retrieves or saves an entity.
- **Unit of Work** — provides the transaction boundary that spans across multiple repositories. It owns the database connection/transaction that all repositories in the current operation share.

The typical collaboration: a Unit of Work is created at the start of a business operation. Repositories receive the UoW (or are scoped to it) and use its shared connection for all queries and writes. The repositories register changed entities with the UoW. At the end of the operation, the service calls `uow.commit()`, which flushes all tracked changes atomically.

```ts
// UoW owns the transaction; repositories use the UoW's connection
interface UnitOfWork {
  orders:    OrderRepository;    // repos scoped to this UoW instance
  customers: CustomerRepository;
  inventory: InventoryRepository;
  commit():   Promise<void>;
  rollback(): Promise<void>;
}

// Service uses repos via UoW — all share one transaction
class OrderService {
  async placeOrder(dto: PlaceOrderDto, uow: UnitOfWork): Promise<Order> {
    const customer = await uow.customers.findById(dto.customerId);
    const order    = Order.create(customer, dto.items);
    await uow.orders.save(order);
    await uow.inventory.decrement(dto.items);
    await uow.commit(); // single atomic flush — all or nothing
    return order;
  }
}
```

**Q5. What is the relationship between Unit of Work and the Identity Map pattern?**
A: The Identity Map is a component *within* the Unit of Work — they are not separate patterns at this level:

The Identity Map maintains a dictionary of `{ entityType + id → entity instance }` within the scope of one Unit of Work. Its purpose is to guarantee that within a single business operation, each entity exists in memory exactly once:

```ts
class UnitOfWork {
  private identityMap = new Map<string, object>();

  // Called by repositories before loading from DB
  getFromIdentityMap<T>(type: string, id: string): T | undefined {
    return this.identityMap.get(`${type}:${id}`) as T | undefined;
  }

  // Called by repositories after loading from DB
  registerInIdentityMap<T extends { id: string }>(type: string, entity: T): void {
    this.identityMap.set(`${type}:${entity.id}`, entity);
  }
}

// Without Identity Map — two separate instances of the same entity
const order1 = await orderRepo.findById("ORD-1"); // instance A
const order2 = await orderRepo.findById("ORD-1"); // instance B — different object!
order1.confirm();   // modifies instance A
// order2 is stale — does not see the confirmation ✗

// With Identity Map — guaranteed same instance
const order1 = await orderRepo.findById("ORD-1"); // loads, caches in UoW
const order2 = await orderRepo.findById("ORD-1"); // returns cached instance
order1 === order2; // true — same object reference ✓
order1.confirm();   // modification visible through order2 reference too ✓
```

## Section 2: Implementing Unit of Work in TypeScript

**Q6. Show a complete, production-quality Unit of Work implementation using Prisma.**
A: Prisma's `$transaction` callback is the most idiomatic UoW implementation in the Node.js ecosystem — the callback receives a transaction-scoped client that all repositories share:

```ts
// Repository interfaces — defined in domain layer, no Prisma dependency
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<Order>;
  findByCustomerId(customerId: string): Promise<Order[]>;
}

interface InventoryRepository {
  findByProductId(productId: string): Promise<InventoryRecord | null>;
  decrement(productId: string, quantity: number): Promise<void>;
  increment(productId: string, quantity: number): Promise<void>;
}

// Prisma implementations — accept a transaction client (tx) for UoW scoping
class PrismaOrderRepository implements OrderRepository {
  constructor(private tx: Prisma.TransactionClient | PrismaClient) {}

  async findById(id: string): Promise<Order | null> {
    const record = await this.tx.order.findUnique({
      where:   { id },
      include: { items: true },
    });
    return record ? OrderMapper.toDomain(record) : null;
  }

  async save(order: Order): Promise<Order> {
    const data = OrderMapper.toPersistence(order);
    const saved = await this.tx.order.upsert({
      where:  { id: data.id ?? "" },
      update: data,
      create: data,
      include: { items: true },
    });
    return OrderMapper.toDomain(saved);
  }

  async findByCustomerId(customerId: string): Promise<Order[]> {
    const records = await this.tx.order.findMany({
      where:   { customerId },
      include: { items: true },
    });
    return records.map(OrderMapper.toDomain);
  }
}

class PrismaInventoryRepository implements InventoryRepository {
  constructor(private tx: Prisma.TransactionClient | PrismaClient) {}

  async findByProductId(productId: string): Promise<InventoryRecord | null> {
    return this.tx.inventory.findUnique({ where: { productId } });
  }

  async decrement(productId: string, quantity: number): Promise<void> {
    await this.tx.inventory.update({
      where: { productId },
      data:  { available: { decrement: quantity }, reserved: { increment: quantity } },
    });
  }

  async increment(productId: string, quantity: number): Promise<void> {
    await this.tx.inventory.update({
      where: { productId },
      data:  { available: { increment: quantity }, reserved: { decrement: quantity } },
    });
  }
}

// Unit of Work interface — service layer contract
interface UnitOfWork {
  orders:    OrderRepository;
  inventory: InventoryRepository;
  commit():   Promise<void>;
  rollback(): Promise<void>;
}

// Prisma Unit of Work — wraps $transaction callback
class PrismaUnitOfWork implements UnitOfWork {
  orders:    OrderRepository;
  inventory: InventoryRepository;

  private txClient: Prisma.TransactionClient | null = null;
  private resolveCommit!: () => void;
  private rejectCommit!:  (err: unknown) => void;
  private committed = false;

  private constructor(tx: Prisma.TransactionClient) {
    this.txClient = tx;
    this.orders    = new PrismaOrderRepository(tx);
    this.inventory = new PrismaInventoryRepository(tx);
  }

  // Factory — creates a UoW inside a Prisma transaction
  static async create(
    prisma:  PrismaClient,
    work:    (uow: UnitOfWork) => Promise<void>,
    options?: { timeout?: number; maxWait?: number }
  ): Promise<void> {
    await prisma.$transaction(async (tx) => {
      const uow = new PrismaUnitOfWork(tx);
      try {
        await work(uow);
        // If work() completes without calling rollback(), Prisma auto-commits
      } catch (err) {
        // If work() throws, Prisma auto-rolls back
        throw err;
      }
    }, {
      timeout: options?.timeout ?? 10_000, // 10s default
      maxWait: options?.maxWait ?? 5_000,
    });
  }

  async commit(): Promise<void> {
    // With Prisma $transaction callback, commit is implicit on function return
    // This method exists for interface compatibility and explicit intent signalling
    this.committed = true;
  }

  async rollback(): Promise<void> {
    // Force rollback by throwing — Prisma will roll back the $transaction
    throw new RollbackError("Explicit rollback requested");
  }
}

// Service — receives UoW factory, not a specific implementation
class OrderService {
  constructor(
    private readonly prisma:  PrismaClient,
    private readonly events:  EventBus,
    private readonly logger:  Logger
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    let orderId: string | undefined;

    await PrismaUnitOfWork.create(this.prisma, async (uow) => {
      // All operations inside this callback share one DB transaction
      const customer = await uow.orders.findByCustomerId(dto.customerId);

      // ... validation

      const order = buildOrder(dto);
      const saved  = await uow.orders.save(order);   // tracked in transaction
      orderId = saved.id;

      for (const item of dto.items) {
        await uow.inventory.decrement(item.productId, item.quantity); // same transaction
      }

      // commit() is implicit — if we reach here without throwing, Prisma commits
    });

    // Post-commit side effects — run AFTER the transaction commits
    if (orderId) {
      await this.events.publish({ type: "ORDER_PLACED", payload: { orderId } })
        .catch(err => this.logger.warn("Event publish failed", { orderId, err }));
    }

    return { orderId: orderId! };
  }
}
```

**Q7. How do you implement a Unit of Work with explicit change tracking — without relying on a framework's transaction callback?**
A: An explicit change-tracking UoW maintains its own lists of new, dirty, and deleted entities and flushes them in a single database transaction at commit time:

```ts
type EntityState = "new" | "dirty" | "deleted" | "clean";

// Change tracker — maintains state per entity
class ChangeTracker {
  private tracked = new Map<string, { entity: object; state: EntityState }>();

  private key(type: string, id: string): string { return `${type}:${id}`; }

  registerNew(type: string, entity: { id: string }): void {
    this.tracked.set(this.key(type, entity.id), { entity, state: "new" });
  }

  registerDirty(type: string, entity: { id: string }): void {
    const existing = this.tracked.get(this.key(type, entity.id));
    if (existing?.state === "new") return; // new trumps dirty
    this.tracked.set(this.key(type, entity.id), { entity, state: "dirty" });
  }

  registerDeleted(type: string, entity: { id: string }): void {
    this.tracked.set(this.key(type, entity.id), { entity, state: "deleted" });
  }

  getByState(state: EntityState): Array<{ type: string; entity: object }> {
    const result: Array<{ type: string; entity: object }> = [];
    for (const [key, value] of this.tracked) {
      if (value.state === state) {
        const type = key.split(":")[0];
        result.push({ type, entity: value.entity });
      }
    }
    return result;
  }

  clear(): void { this.tracked.clear(); }
}

// Explicit Unit of Work — manages connection + change tracking
class ExplicitUnitOfWork {
  private tracker   = new ChangeTracker();
  private client:   PoolClient | null = null;
  private committed = false;

  // Scoped repositories — receive UoW reference for registration
  public orders:    OrderRepository;
  public customers: CustomerRepository;
  public inventory: InventoryRepository;

  constructor(private pool: Pool) {
    this.orders    = new PostgresOrderRepository(this, pool);
    this.customers = new PostgresCustomerRepository(this, pool);
    this.inventory = new PostgresInventoryRepository(this, pool);
  }

  async begin(): Promise<void> {
    this.client = await this.pool.connect();
    await this.client.query("BEGIN");
  }

  // Called by repositories to register changes
  registerNew(type: string, entity: { id: string }): void {
    this.tracker.registerNew(type, entity);
  }
  registerDirty(type: string, entity: { id: string }): void {
    this.tracker.registerDirty(type, entity);
  }
  registerDeleted(type: string, entity: { id: string }): void {
    this.tracker.registerDeleted(type, entity);
  }

  getClient(): PoolClient {
    if (!this.client) throw new Error("UnitOfWork not started — call begin() first");
    return this.client;
  }

  async commit(): Promise<void> {
    if (!this.client) throw new Error("UnitOfWork not started");
    if (this.committed) throw new Error("UnitOfWork already committed");

    try {
      await this.flush();          // write all tracked changes
      await this.client.query("COMMIT");
      this.committed = true;
    } catch (err) {
      await this.rollback();
      throw err;
    } finally {
      this.cleanup();
    }
  }

  async rollback(): Promise<void> {
    if (!this.client) return;
    try   { await this.client.query("ROLLBACK"); }
    finally { this.cleanup(); }
  }

  private async flush(): Promise<void> {
    if (!this.client) throw new Error("No client");

    // Flush in correct order: inserts → updates → deletes (respects FK constraints)
    for (const { type, entity } of this.tracker.getByState("new")) {
      await this.flushInsert(type, entity as { id: string });
    }
    for (const { type, entity } of this.tracker.getByState("dirty")) {
      await this.flushUpdate(type, entity as { id: string });
    }
    for (const { type, entity } of this.tracker.getByState("deleted")) {
      await this.flushDelete(type, entity as { id: string });
    }

    this.tracker.clear();
  }

  private async flushInsert(type: string, entity: { id: string }): Promise<void> {
    // Delegate to type-specific mapper
    const sql = EntitySqlMapper.toInsertSql(type, entity);
    await this.client!.query(sql.text, sql.values);
  }

  private async flushUpdate(type: string, entity: { id: string }): Promise<void> {
    const sql = EntitySqlMapper.toUpdateSql(type, entity);
    await this.client!.query(sql.text, sql.values);
  }

  private async flushDelete(type: string, entity: { id: string }): Promise<void> {
    const sql = EntitySqlMapper.toDeleteSql(type, entity);
    await this.client!.query(sql.text, sql.values);
  }

  private cleanup(): void {
    this.client?.release();
    this.client = null;
    this.tracker.clear();
  }
}

// Repository — registers changes with the UoW instead of writing immediately
class PostgresOrderRepository implements OrderRepository {
  private identityMap = new Map<string, Order>();

  constructor(private uow: ExplicitUnitOfWork, private pool: Pool) {}

  async findById(id: string): Promise<Order | null> {
    // Check identity map first — ensures single instance per UoW
    if (this.identityMap.has(id)) return this.identityMap.get(id)!;

    const result = await this.uow.getClient().query(
      "SELECT * FROM orders WHERE id = $1", [id]
    );
    if (!result.rows[0]) return null;

    const order = OrderMapper.toDomain(result.rows[0]);
    this.identityMap.set(id, order); // cache in identity map
    return order;
  }

  async save(order: Order): Promise<void> {
    if (this.identityMap.has(order.id)) {
      this.uow.registerDirty("Order", order); // existing entity — mark dirty
    } else {
      this.uow.registerNew("Order", order);   // new entity — mark for insert
      this.identityMap.set(order.id, order);
    }
    // No DB write yet — deferred until uow.commit()
  }

  async delete(order: Order): Promise<void> {
    this.uow.registerDeleted("Order", order);
    this.identityMap.delete(order.id);
  }
}
```

**Q8. How do you implement a Unit of Work factory — so services receive a new UoW per business operation without knowing its concrete type?**
A: A factory interface in the application layer allows services to create UoW instances without knowing whether the implementation uses Prisma, pg, TypeORM, or an in-memory fake:

```ts
// Application layer — factory interface, no infrastructure knowledge
interface UnitOfWorkFactory {
  create(): Promise<UnitOfWork>;
}

// Infrastructure layer — Prisma implementation
class PrismaUnitOfWorkFactory implements UnitOfWorkFactory {
  constructor(private prisma: PrismaClient) {}

  async create(): Promise<UnitOfWork> {
    return new PrismaTransactionUnitOfWork(this.prisma);
  }
}

// Service — depends only on the factory interface
class OrderService {
  constructor(private readonly uowFactory: UnitOfWorkFactory) {}

  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    const uow = await this.uowFactory.create();
    try {
      const customer = await uow.customers.findById(dto.customerId);
      if (!customer) throw new NotFoundError(dto.customerId);

      const order = Order.create(customer, dto.items);
      await uow.orders.save(order);

      for (const item of dto.items) {
        await uow.inventory.decrement(item.productId, item.quantity);
      }

      await uow.commit();
      return { orderId: order.id, total: order.total };

    } catch (err) {
      await uow.rollback();
      throw err;
    }
  }
}
```

## Section 3: Unit of Work with ORMs

**Q9. How does TypeORM implement the Unit of Work pattern, and how do you use it correctly?**
A: TypeORM's `QueryRunner` is its explicit UoW implementation. The `EntityManager` returned by a query runner shares a single transaction:

```ts
// TypeORM Unit of Work via QueryRunner
class TypeORMUnitOfWork implements UnitOfWork {
  private queryRunner: QueryRunner;

  // Repositories scoped to the transaction
  public orders:    OrderRepository;
  public inventory: InventoryRepository;

  constructor(dataSource: DataSource) {
    this.queryRunner = dataSource.createQueryRunner();
  }

  async begin(): Promise<void> {
    await this.queryRunner.connect();
    await this.queryRunner.startTransaction();

    // Repos use the transaction-scoped manager — not the global EntityManager
    this.orders    = new TypeORMOrderRepository(this.queryRunner.manager);
    this.inventory = new TypeORMInventoryRepository(this.queryRunner.manager);
  }

  async commit(): Promise<void> {
    try {
      await this.queryRunner.commitTransaction();
    } catch (err) {
      await this.queryRunner.rollbackTransaction();
      throw err;
    } finally {
      await this.queryRunner.release();
    }
  }

  async rollback(): Promise<void> {
    try   { await this.queryRunner.rollbackTransaction(); }
    finally { await this.queryRunner.release(); }
  }
}

// TypeORM repository — uses the transactional manager
class TypeORMOrderRepository implements OrderRepository {
  constructor(private manager: EntityManager) {}

  async findById(id: string): Promise<Order | null> {
    const entity = await this.manager.findOne(OrderEntity, {
      where:    { id },
      relations: ["items"],
    });
    return entity ? OrderMapper.toDomain(entity) : null;
  }

  async save(order: Order): Promise<Order> {
    const entity = OrderMapper.toEntity(order);
    const saved  = await this.manager.save(OrderEntity, entity);
    return OrderMapper.toDomain(saved);
  }
}

// Usage — with proper cleanup
async function placeOrderWithTypeORM(
  dto:        PlaceOrderDto,
  dataSource: DataSource
): Promise<void> {
  const uow = new TypeORMUnitOfWork(dataSource);
  await uow.begin();

  try {
    const order = Order.create(dto);
    await uow.orders.save(order);
    await uow.inventory.decrement(dto.items);
    await uow.commit(); // commit and release
  } catch (err) {
    await uow.rollback(); // rollback and release
    throw err;
  }
}

// TypeORM also supports a shorter callback form — similar to Prisma
await dataSource.transaction(async (manager) => {
  const orderRepo    = manager.getRepository(OrderEntity);
  const inventoryRepo = manager.getRepository(InventoryEntity);

  await orderRepo.save(newOrderEntity);
  await inventoryRepo.decrement({ productId }, "quantity", 1);
  // Auto-commits if no exception; auto-rolls back on exception
});
```

**Q10. How does Prisma's `$transaction` differ from an explicit Unit of Work, and when do you use each?**
A:

| Aspect | Prisma `$transaction` | Explicit Unit of Work |
|---|---|---|
| **Change tracking** | None — you call each model method explicitly | Optional — can auto-detect dirty entities |
| **Identity map** | None — you manage entity instances | Can be implemented inside UoW |
| **Concurrency control** | Serialisation level set via `isolationLevel` | Custom — optimistic locking with version field |
| **API style** | Callback (`$transaction(async (tx) => {...})`) or array of promises | `begin()` / `commit()` / `rollback()` methods |
| **Timeout** | Configurable per call | Manual — implement as middleware |
| **Boilerplate** | Low — Prisma handles connection management | Higher — manual connection and release |
| **Testability** | Requires Prisma mock or real DB | Fully mockable with in-memory UoW |
| **When to use** | Services tightly coupled to Prisma; simple multi-model transactions | Framework-agnostic codebase; Clean Architecture; complex change tracking needs |

```ts
// Prisma $transaction — idiomatic for Prisma-first projects
const result = await prisma.$transaction(async (tx) => {
  const order = await tx.order.create({ data: orderData });
  await tx.inventory.update({
    where: { productId: orderData.productId },
    data:  { stock: { decrement: orderData.quantity } },
  });
  return order;
}, { isolationLevel: Prisma.TransactionIsolationLevel.Serializable });

// Explicit UoW — for framework-agnostic service layer
const uow = await uowFactory.create();
try {
  await uow.orders.save(newOrder);
  await uow.inventory.decrement(items);
  await uow.commit();
} catch (err) {
  await uow.rollback();
  throw err;
}
```

**Use Prisma `$transaction`** when the project is Prisma-first and Clean Architecture layering is not a strict requirement. **Use explicit UoW** when the service layer must be testable without a database, when the project follows Clean Architecture, or when change tracking and identity mapping are required features.

## Section 4: Advanced Unit of Work Patterns

**Q11. How do you implement optimistic concurrency control within a Unit of Work?**
A: Optimistic concurrency assumes that conflicts are rare — it allows multiple operations to read the same entity simultaneously but detects conflicts at commit time using a version field:

```ts
// Domain entity — carries a version for optimistic locking
class Order {
  constructor(
    public readonly id:       string,
    public          status:   OrderStatus,
    public readonly version:  number = 1, // incremented on each update
    // ... other fields
  ) {}

  withVersion(v: number): Order {
    return new Order(this.id, this.status, v);
  }
}

// Repository — uses version in UPDATE WHERE clause
class PostgresOrderRepository implements OrderRepository {
  async save(order: Order): Promise<Order> {
    const result = await this.uow.getClient().query(`
      UPDATE orders
      SET    status = $1, version = version + 1, updated_at = NOW()
      WHERE  id = $2 AND version = $3
      RETURNING *
    `, [order.status, order.id, order.version]);

    if (result.rowCount === 0) {
      // No rows updated — someone else modified this entity since we read it
      throw new OptimisticLockError(
        `Order ${order.id} was modified concurrently (expected version ${order.version})`
      );
    }

    return OrderMapper.toDomain(result.rows[0]);
  }
}

// Unit of Work — catches OptimisticLockError and wraps it
class ExplicitUnitOfWork {
  async commit(): Promise<void> {
    try {
      await this.flush();
      await this.client.query("COMMIT");
    } catch (err) {
      await this.rollback();
      if (err instanceof OptimisticLockError) {
        throw err; // caller decides whether to retry
      }
      throw new CommitError("Transaction commit failed", { cause: err });
    }
  }
}

// Service — retry on optimistic lock conflict (exponential backoff)
class OrderService {
  async confirmOrder(orderId: string, maxRetries = 3): Promise<void> {
    for (let attempt = 1; attempt <= maxRetries; attempt++) {
      try {
        const uow = await this.uowFactory.create();
        try {
          const order = await uow.orders.findById(orderId);
          if (!order) throw new NotFoundError(orderId);

          order.confirm(); // domain method — changes status + bumps version in memory
          await uow.orders.save(order);
          await uow.commit();
          return; // success

        } catch (err) {
          await uow.rollback();
          throw err;
        }

      } catch (err) {
        if (err instanceof OptimisticLockError && attempt < maxRetries) {
          const delayMs = Math.min(100 * Math.pow(2, attempt), 1000);
          this.logger.warn(`Optimistic lock conflict on Order ${orderId}, retry ${attempt}/${maxRetries} in ${delayMs}ms`);
          await new Promise(r => setTimeout(r, delayMs));
          continue; // retry
        }
        throw err; // max retries exceeded or different error
      }
    }
  }
}
```

**Q12. How do you publish domain events after a Unit of Work commits — ensuring events are only emitted when the transaction succeeds?**
A: Domain events must be published *after* the commit, not before. The UoW collects events during the operation and releases them post-commit:

```ts
// Domain entity — accumulates events during the operation
class Order {
  private domainEvents: DomainEvent[] = [];

  confirm(): void {
    if (this.status !== "PENDING") throw new DomainError("Invalid transition");
    this.status = "CONFIRMED";
    this.domainEvents.push(new OrderConfirmedEvent(this.id, this.total)); // staged
  }

  pullEvents(): DomainEvent[] {
    const events      = [...this.domainEvents];
    this.domainEvents = [];
    return events;
  }
}

// Unit of Work — collects events from all saved entities; publishes after commit
class EventAwareUnitOfWork implements UnitOfWork {
  private stagedEvents: DomainEvent[] = [];

  constructor(
    private readonly inner:    PrismaUnitOfWork,
    private readonly eventBus: EventBus,
    private readonly logger:   Logger
  ) {
    this.orders    = new EventCollectingOrderRepository(inner.orders, this);
    this.inventory = inner.inventory;
  }

  // Called by repositories when they save entities with pending events
  stageEvents(events: DomainEvent[]): void {
    this.stagedEvents.push(...events);
  }

  async commit(): Promise<void> {
    await this.inner.commit(); // DB transaction commits first

    // Publish events AFTER successful commit — they will not be published on rollback
    const events = [...this.stagedEvents];
    this.stagedEvents = [];

    await Promise.allSettled(
      events.map(event =>
        this.eventBus.publish(event).catch(err =>
          this.logger.error("Failed to publish domain event post-commit", { event, err })
        )
      )
    );
  }

  async rollback(): Promise<void> {
    this.stagedEvents = []; // discard staged events — transaction rolled back
    await this.inner.rollback();
  }
}

// Event-collecting repository — extracts events from entities on save
class EventCollectingOrderRepository implements OrderRepository {
  constructor(
    private inner: OrderRepository,
    private uow:   EventAwareUnitOfWork
  ) {}

  async save(order: Order): Promise<Order> {
    const saved  = await this.inner.save(order);
    const events = order.pullEvents();        // drain staged events from entity
    this.uow.stageEvents(events);             // hand to UoW for post-commit publishing
    return saved;
  }

  async findById(id: string): Promise<Order | null> {
    return this.inner.findById(id);
  }
}

// Usage — events are guaranteed to only publish after successful commit
const uow = new EventAwareUnitOfWork(new PrismaUnitOfWork(prisma), eventBus, logger);

const order = await uow.orders.findById(orderId);
order.confirm(); // stages OrderConfirmedEvent internally
await uow.orders.save(order); // event transferred to UoW
await uow.commit(); // 1. DB commits. 2. OrderConfirmedEvent published.
// If DB commit fails, no event is published — guaranteed consistency
```

**Q13. How do you implement the Unit of Work pattern in a multi-tenant application where each tenant has its own database schema?**
A: The UoW factory becomes schema-aware — it switches the search path or connection string based on tenant context before creating the transaction:

```ts
// Tenant-aware Unit of Work factory
class TenantAwarePrismaUnitOfWorkFactory implements UnitOfWorkFactory {
  constructor(
    private prisma:       PrismaClient,
    private tenantConfig: TenantConfigService
  ) {}

  async create(tenantId: string): Promise<UnitOfWork> {
    const config = await this.tenantConfig.getConfig(tenantId);

    if (config.isolationStrategy === "schema") {
      // Set schema search path for this transaction
      return new SchemaScopedUnitOfWork(this.prisma, config.schemaName);
    }

    if (config.isolationStrategy === "database") {
      // Connect to tenant-specific database
      const tenantPrisma = new PrismaClient({
        datasources: { db: { url: config.databaseUrl } }
      });
      return new PrismaCallbackUnitOfWork(tenantPrisma);
    }

    // Row-level tenant isolation — filter by tenantId column
    return new TenantFilteredUnitOfWork(this.prisma, tenantId);
  }
}

// Schema-per-tenant UoW — sets Postgres search_path before each transaction
class SchemaScopedUnitOfWork implements UnitOfWork {
  public orders:    OrderRepository;
  public inventory: InventoryRepository;

  constructor(
    private prisma:      PrismaClient,
    private schemaName:  string
  ) {}

  async create(work: (uow: UnitOfWork) => Promise<void>): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      // Set schema for this transaction
      await tx.$executeRawUnsafe(`SET search_path TO "${this.schemaName}", public`);

      const scopedUow = {
        orders:    new PrismaOrderRepository(tx),
        inventory: new PrismaInventoryRepository(tx),
        commit:    async () => { /* implicit in $transaction */ },
        rollback:  async () => { throw new Error("rollback"); },
      };

      await work(scopedUow);
    });
  }
}
```

## Section 6: Pitfalls, Anti-Patterns & Edge Cases

**Q15. What is the "long-running Unit of Work" anti-pattern, and why is it dangerous?**
A: A Unit of Work should span exactly one business operation — typically milliseconds to a few seconds. Keeping a UoW open for extended periods causes several serious problems:

```ts
// ✗ — Long-running UoW: opened at request start, committed at request end
class OrderController {
  private uow: UnitOfWork; // instance variable — UoW persists across methods

  async handleRequest(req: Request): Promise<void> {
    this.uow = await this.uowFactory.create(); // UoW created for the entire request
    await this.step1();
    await this.step2(); // HTTP call — takes 2 seconds
    await this.step3(); // Another HTTP call — takes 3 seconds
    await this.uow.commit(); // DB transaction open for 5+ seconds ✗
  }
}
```

**Problems with long-running UoW:**
- **Lock escalation** — rows locked for the duration of the UoW block other transactions, causing deadlocks and timeouts.
- **Connection exhaustion** — each UoW holds a DB connection. If requests are slow, the connection pool is exhausted.
- **Stale reads** — entities loaded at the start of a long UoW are stale by the time they're committed; other transactions have modified them in the meantime.
- **Cascading rollback** — a failure at step 5 of a 10-step operation rolls back all previous steps, even if they were independent and should have committed.

```ts
// ✓ — Short-lived UoW: one per business operation, milliseconds to seconds
class OrderService {
  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    // Fetch external data BEFORE opening the UoW (avoids holding DB locks during HTTP calls)
    const paymentToken = await this.payments.validate(dto.paymentToken);
    const shippingRate = await this.shipping.getRate(dto.address);

    // Open UoW only for the DB operations — keep it short
    const uow = await this.uowFactory.create();
    try {
      const order = buildOrder(dto, shippingRate);
      await uow.orders.save(order);
      await uow.inventory.decrement(dto.items);
      await uow.commit(); // DB work only — milliseconds
      return { orderId: order.id };
    } catch (err) {
      await uow.rollback();
      throw err;
    }
  }
}
```

**Q16. How do you handle the case where a Unit of Work must span a message queue publish — ensuring the DB write and the message are either both committed or both rolled back?**
A: This is the distributed transaction problem — a database transaction and a message queue publish cannot share a single ACID transaction. The pattern to use is **Transactional Outbox**:

```ts
// Transactional Outbox — write message to DB in same transaction, publish separately
class OutboxUnitOfWork implements UnitOfWork {
  public orders:  OrderRepository;
  public outbox:  OutboxRepository; // outbox table is in the same DB as orders

  async commit(): Promise<void> {
    // All DB writes — orders AND outbox messages — commit together atomically
    await this.inner.commit();
    // A separate OutboxPublisher process polls the outbox table and publishes to the queue
    // This ensures: if the DB commits, the message will eventually be published
    // If the DB rolls back, the outbox row is also rolled back — no phantom message
  }
}

// Service — writes to outbox table inside the same transaction as the order
class OrderService {
  async placeOrder(dto: PlaceOrderDto): Promise<PlaceOrderResult> {
    const uow = await this.uowFactory.create();
    try {
      const order = Order.create(dto);
      await uow.orders.save(order);
      await uow.inventory.decrement(dto.items);

      // Write to outbox inside the same DB transaction — not to the queue directly
      await uow.outbox.enqueue({
        id:        generateId(),
        type:      "ORDER_PLACED",
        payload:   JSON.stringify({ orderId: order.id, total: order.total }),
        createdAt: new Date(),
        published: false,
      });

      await uow.commit(); // order + inventory + outbox row all commit together
      return { orderId: order.id };
    } catch (err) {
      await uow.rollback(); // all three tables rolled back together
      throw err;
    }
  }
}

// Outbox publisher — separate process, polls and publishes, marks as published
class OutboxPublisher {
  async processOutbox(): Promise<void> {
    const messages = await this.outboxRepo.findUnpublished(batchSize: 100);
    for (const msg of messages) {
      try {
        await this.eventBus.publish({ type: msg.type, payload: JSON.parse(msg.payload) });
        await this.outboxRepo.markPublished(msg.id); // idempotent — safe to retry
      } catch (err) {
        this.logger.error("Failed to publish outbox message", { msgId: msg.id, err });
        // Will be retried on next poll cycle
      }
    }
  }
}
```

**Q17. What is the "Unit of Work scope" problem in dependency injection containers, and how do you solve it?**
A: In NestJS or other DI containers, a UoW must be scoped to a single request/operation — not shared across requests as a singleton:

```ts
// ✗ — Singleton scope: one UoW instance shared by all requests (race conditions!)
@Module({
  providers: [
    { provide: UnitOfWork, useClass: PrismaUnitOfWork } // singleton — catastrophic ✗
  ]
})

// ✗ — Transient scope with shared PrismaClient: each injection creates a new UoW,
//      but injecting into two services in the same request = two separate transactions
@Injectable({ scope: Scope.TRANSIENT })
class PrismaUnitOfWork { } // different instances per injection — no shared transaction ✗

// ✓ — Request scope: one UoW per HTTP request, shared across all services in that request
@Injectable({ scope: Scope.REQUEST })
class PrismaUnitOfWork implements UnitOfWork {
  private txClient: Prisma.TransactionClient | null = null;

  constructor(private prisma: PrismaClient) {}

  async ensureTransaction(): Promise<Prisma.TransactionClient> {
    if (!this.txClient) {
      // Lazy initialisation — transaction started on first use
      // (Implementation requires more complex setup for true lazy Prisma transactions)
    }
    return this.txClient!;
  }
}

// ✓ — Factory pattern (preferred for Clean Architecture): create UoW per operation
@Injectable()
class UnitOfWorkFactory {
  constructor(private prisma: PrismaClient) {}

  // Returns a new UoW for each business operation
  async run<T>(work: (uow: UnitOfWork) => Promise<T>): Promise<T> {
    return this.prisma.$transaction(async (tx) => {
      const uow = new PrismaTransactionUnitOfWork(tx);
      return work(uow);
    });
  }
}

// Service — receives factory, not a scoped UoW
@Injectable()
class OrderService {

      const order = Order.create(dto);
      await uow.orders.save(order);
      await uow.inventory.decrement(dto.items);
      return { orderId: order.id };
      // UoW commits on return, rolls back on throw
    });
  }
}
```

## Section 7: Scenario / System Design Style Questions

**Q18. "A microservice processes payment events from a queue. For each event, it must update the order status in the database, update the payment record, and emit an 'order-updated' domain event. How does Unit of Work ensure these three steps are atomic?"**
A: The UoW groups the two DB writes into one transaction; the Transactional Outbox pattern handles the domain event atomically:

```ts
// Message queue consumer — processes one payment event at a time
class PaymentEventConsumer {
  constructor(
    private readonly uowFactory: UnitOfWorkFactory,
    private readonly logger:     Logger
  ) {}

  @MessagePattern("payment.completed")
  async handlePaymentCompleted(event: PaymentCompletedEvent): Promise<void> {
    this.logger.info("Processing payment completed event", { paymentId: event.paymentId });

    await this.uowFactory.run(async (uow) => {
      // Step 1 — update order status
      const order = await uow.orders.findByPaymentId(event.paymentId);
      if (!order) {
        this.logger.warn("Order not found for payment", { paymentId: event.paymentId });
        return; // idempotent — skip silently
      }

      if (order.status === "CONFIRMED") {
        this.logger.info("Order already confirmed — duplicate event", { orderId: order.id });
        return; // idempotent — already processed
      }

      order.confirm(event.chargeId); // domain transition
      await uow.orders.save(order);  // UPDATE orders SET status = 'CONFIRMED'

      // Step 2 — update payment record
      const payment = await uow.payments.findById(event.paymentId);
      payment.markSucceeded(event.chargeId, event.processedAt);
      await uow.payments.save(payment); // UPDATE payments SET status = 'SUCCEEDED'

      // Step 3 — stage the domain event in the outbox (same transaction)
      await uow.outbox.enqueue({
        type:    "ORDER_CONFIRMED",
        payload: { orderId: order.id, paymentId: event.paymentId, total: order.total },
      }); // INSERT INTO outbox — same transaction as steps 1 and 2

      // All three DB writes commit together — or all roll back together
    });
    // Outbox publisher separately reads the outbox row and publishes to downstream queues
  }
}
```

**Q19. "Your team's OrderService has grown to span five different repositories — orders, payments, inventory, notifications, and audit logs — all in one Unit of Work. What are the warning signs, and how do you address them?"**
A: Five repositories in one UoW is a signal of two overlapping problems:

**Problem 1 — Transaction scope is too broad.** Not all five writes are equally critical. An audit log failure should not roll back an order. A notification failure should not reverse a payment. The UoW is conflating critical and non-critical operations:

```ts
// ✗ — Everything in one UoW: audit log failure rolls back the order
await uow.orders.save(order);
await uow.payments.save(payment);
await uow.inventory.decrement(items);
await uow.notifications.queue(notification); // non-critical!
await uow.auditLog.write(auditEntry);        // non-critical!
await uow.commit(); // if auditLog write fails, order is rolled back ✗

// ✓ — Separate critical and non-critical writes
// Critical: order + payment + inventory — one UoW
await this.uowFactory.run(async (uow) => {
  await uow.orders.save(order);
  await uow.payments.save(payment);
  await uow.inventory.decrement(items);
  // Outbox row for ORDER_PLACED also goes here — same critical transaction
});

// Non-critical: notifications and audit — outside the transaction, with error isolation
await Promise.allSettled([
  this.notifications.queue(notification)
    .catch(err => this.logger.warn("Notification queue failed", { err })),
  this.auditLog.write(auditEntry)
    .catch(err => this.logger.warn("Audit log write failed", { err })),
]);
```

**Problem 2 — The service is violating the Single Responsibility Principle.** Five repositories suggests the service is orchestrating too many bounded contexts. The long-term fix is event-driven decoupling:

```ts
// Target architecture — each context owns its own data; events propagate changes
// OrderService: owns orders + inventory (core domain)
await this.uowFactory.run(async (uow) => {
  await uow.orders.save(confirmedOrder);
  await uow.inventory.decrement(items);
  await uow.outbox.enqueue({ type: "ORDER_CONFIRMED", payload: { orderId } });
});

// PaymentService listens to ORDER_CONFIRMED → manages payments independently
// NotificationService listens to ORDER_CONFIRMED → sends emails independently
// AuditService listens to all domain events → writes audit log independently
// Each service has its own UoW — no cross-context transaction
```

**Q20. "How do you implement a Unit of Work in a serverless environment where each Lambda invocation is stateless and connection pooling is constrained?"**
A: Serverless changes the UoW lifetime and connection model — but not the pattern's purpose:

```ts
// Serverless UoW — short-lived, connection-pool-aware
class ServerlessUnitOfWork implements UnitOfWork {
  public orders:    OrderRepository;
  public inventory: InventoryRepository;

  private constructor(private tx: Prisma.TransactionClient) {
    this.orders    = new PrismaOrderRepository(tx);
    this.inventory = new PrismaInventoryRepository(tx);
  }

  // Static factory — used in Lambda handler
  static async run<T>(
    prisma: PrismaClient,
    work:   (uow: ServerlessUnitOfWork) => Promise<T>
  ): Promise<T> {
    // Short timeout — Lambdas have limited execution time
    return prisma.$transaction(async (tx) => {
      const uow = new ServerlessUnitOfWork(tx);
      return work(uow);
    }, {
      timeout: 5_000,  // 5 seconds max — Lambda executions are time-limited
      maxWait: 2_000,
    });
  }
}

// Lambda handler — one UoW per invocation
export const handler = async (event: SQSEvent): Promise<SQSBatchResponse> => {
  // Initialise connection pool once per Lambda container lifecycle
  const prisma = getPrismaClient(); // singleton per container, not per invocation

  const failures: SQSBatchItemFailure[] = [];

  for (const record of event.Records) {
    try {
      const message = JSON.parse(record.body) as OrderMessage;

      await ServerlessUnitOfWork.run(prisma, async (uow) => {
        const order = await uow.orders.findById(message.orderId);
        if (!order) return; // idempotent — already processed or never existed

        order.process(message.action);
        await uow.orders.save(order);
        await uow.inventory.update(message.items);
        // UoW commits on return from this callback
      });

    } catch (err) {
      this.logger.error("Failed to process message", { messageId: record.messageId, err });
      failures.push({ itemIdentifier: record.messageId }); // partial batch failure
    }
  }

  // Return failed items to SQS for retry — successful items are implicitly deleted
  return { batchItemFailures: failures };
};

// Connection configuration — optimised for serverless cold-start and pool limits
function getPrismaClient(): PrismaClient {
  if (globalThis.__prisma) return globalThis.__prisma;

  globalThis.__prisma = new PrismaClient({
    datasources: { db: { url: process.env.DATABASE_URL } },
    log: ["error"],
  });

  // Use connection pool sized for Lambda concurrency × connections per function
  // Typically: pgBouncer in transaction mode handles this at the infra level
  return globalThis.__prisma;
}
```

| **Testability** | Hard — requires real DB for any test | Requires Prisma mock or real DB | Fully testable with in-memory UoW fake |
| **Framework coupling** | Varies | Tight — Prisma-specific API | Low — depends only on UoW interface |
| **Boilerplate** | Low | Low | High |
| **Optimistic locking** | Manual per query | Manual per query | Centralised in UoW |
| **Domain event post-commit** | Manual and error-prone | Manual after `$transaction` | Centralised in UoW.commit() |
| **Best for** | Simple apps, small teams | Prisma-first projects | Clean Architecture, framework-agnostic services |

## Unit of Work Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **Long-running UoW** | UoW open during HTTP calls, user waits, queue polling | Do external calls before opening UoW; keep DB work to milliseconds |
| **Singleton UoW** | One UoW instance shared by all requests | Request scope or factory pattern — one UoW per operation |
| **Over-broad transaction** | Non-critical operations (email, audit log) included in UoW | Separate critical from non-critical; use `Promise.allSettled` for non-critical |
| **Event before commit** | Domain events published before UoW.commit() | Collect events in UoW; publish post-commit or use Transactional Outbox |
| **UoW in repository** | Repository opens its own transaction instead of using UoW's | Repositories receive the UoW's connection; they never manage transactions |
| **Missing rollback on error** | `uow.commit()` called inside `catch` — partial state committed | Always `rollback()` in `catch`; commit only in `try` |
| **UoW as god object** | UoW contains 10+ repositories and application logic | UoW contains only repos + commit/rollback; logic stays in service |
| **Nested UoW** | Creating a new UoW inside a method already called within a UoW | Detect active UoW via context propagation; join existing or error explicitly |

**Tip for the interview:** At the 5 YOE level, "what is Unit of Work" surfaces as: how do you ensure that saving an order and decrementing inventory either both succeed or both fail, why does your test suite need a real database just to test business logic, how do you publish a domain event only when the database transaction commits, or how do you avoid connection pool exhaustion in a high-traffic API. The sharp answer immediately names the three problems UoW solves (scattered transaction management, duplicate writes, missing writes), shows the commit/rollback lifecycle, explains the interaction with repositories (repos use the UoW's shared connection, not their own), and demonstrates the testability benefit (inject an in-memory UoW factory — no DB needed in service tests). Distinguishing the UoW from a plain `$transaction` call — "Prisma's `$transaction` gives you atomicity but not change tracking or identity mapping — the explicit UoW gives you all three, plus the testability of an in-memory fake" — is the architectural depth that lands at 5 YOE.
