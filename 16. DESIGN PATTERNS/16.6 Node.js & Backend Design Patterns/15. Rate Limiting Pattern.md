# Rate Limiting Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Rate Limiting Pattern and what problem does it solve?**
A: Rate limiting is a control mechanism that restricts how many requests a client, user, or tenant can make to a system within a defined time window. Requests that exceed the limit are either rejected immediately, queued, or throttled — depending on the strategy.

Without rate limiting, a backend faces four distinct threats that grow worse under scale:

- **Resource exhaustion** — a single client (malicious or misbehaving) issues thousands of requests per second, consuming CPU, database connections, and external API quota. Legitimate users are starved. In a lending platform, one NBFC partner hammering the bureau pull endpoint can exhaust your CIBIL API quota, blocking all other tenants' loan applications.
- **Credential stuffing / brute force** — attackers iterate through stolen credentials or PAN numbers at machine speed. Without a request limit, a `/kyc/verify-pan` endpoint becomes an enumeration tool.
- **Cost explosions** — external APIs (CIBIL bureau, JusPay, SMS gateways) charge per call. Uncapped usage from one misbehaving client generates unexpected bills.
- **Cascading overload** — an upstream spike in traffic fans out to downstream services (bureau, NACH, DB) that cannot absorb it. Rate limiting at the entry point is the first line of defence before bulkheads and circuit breakers.

Rate limiting is distinct from:
- **Bulkhead** — limits *concurrent* in-flight requests at a point in time. Rate limiting limits *total requests over a time window*.
- **Throttling** — slows down requests (adds delay) rather than rejecting them. Rate limiting typically rejects.
- **Circuit breaker** — reacts to *downstream failures*. Rate limiting reacts to *upstream demand*.

**Q2. What are the four main rate limiting algorithms and what are their trade-offs?**
A:

**1. Fixed Window Counter**

Divides time into fixed buckets (e.g., 0–59s, 60–119s). Counts requests per bucket. Resets at the boundary.

```
Window: 0s──────────59s | 60s──────────119s
Count:  [98 requests]   | [reset → 0]
          ↑ 2 more OK     ↑ 100 more OK immediately after reset
```

- ✅ Simple; cheap (one Redis `INCR` + `EXPIRE`)
- ❌ Boundary burst: a client can send 100 at 59s and 100 at 60s — 200 requests in 2 seconds, double the intended rate

**2. Sliding Window Log**

Stores a timestamp for every request. At each new request, evicts timestamps older than the window and counts what remains.

```
Window: last 60 seconds (slides with current time)
Log: [t-58s, t-45s, t-32s, t-10s, t-2s] → count=5 of 100 limit
New request at t: count=5 < 100 → allow; append t
```

- ✅ Exact; no boundary burst
- ❌ Memory-heavy: stores one entry per request; impractical at high volume (100k req/min = 100k log entries per user)

**3. Sliding Window Counter (hybrid)**

Combines fixed window counters with a weighted interpolation — approximates the sliding window without storing per-request logs.

```
Current window count:   80 requests (40s elapsed of 60s window)
Previous window count: 100 requests
Overlap fraction: (60 - 40) / 60 = 0.333 (20s of prev window still in scope)

Estimated count = (100 × 0.333) + 80 = 33.3 + 80 = 113.3 → over limit of 100
```

- ✅ Accurate approximation; memory-efficient (two counters per client)
- ✅ No boundary burst
- ✅ **Best choice for most production use cases**
- ❌ Approximation — can allow ~0.1% more or fewer requests than exact limit

**4. Token Bucket**

A bucket holds tokens up to a maximum. Tokens refill at a fixed rate. Each request consumes one token. If the bucket is empty, the request is rejected.

```
Capacity: 10 tokens
Refill: 1 token/second
State: 3 tokens remaining

Request arrives → consume 1 token → 2 remaining → allow
Request arrives → consume 1 token → 1 remaining → allow
10 rapid requests → bucket empty → reject until refill
Burst of 10 requests allowed (uses full bucket) → smooth requests after
```

- ✅ Allows controlled bursts up to bucket capacity
- ✅ Natural fit for APIs that want to allow short bursts but enforce long-term rate
- ❌ Two state values to maintain (tokens + last refill time); slightly more complex

**5. Leaky Bucket**

Requests enter a queue (the bucket). A worker drains the queue at a fixed rate. If the queue is full, new requests are rejected.

```
Incoming: burst of 20 requests → queue (capacity 10) → 10 rejected
Queue drains at 5 req/s → smooth output regardless of bursty input
```

- ✅ Smoothest output rate; protects downstream from bursts
- ❌ Adds latency (queued requests wait); complex to implement at distributed scale
- ❌ Not ideal for interactive APIs (user waits for queued request to drain)

**Production recommendation for a fintech lending API:** Sliding Window Counter for most endpoints (accurate, cheap, no burst vulnerability). Token Bucket for endpoints where short bursts are legitimate (batch submission, NACH mandate upload).

**Q3. What are the different dimensions on which rate limits are applied, and which matters most for each use case?**
A: Rate limits are applied per *key* — the identifier that distinguishes one consumer from another. Choosing the right key is as important as choosing the algorithm:

| Key dimension | What it limits | Best for |
|---|---|---|
| **Per IP** | All requests from one IP address | Unauthenticated endpoints; brute-force protection; anonymous users |
| **Per user ID** | All requests from one authenticated user | Authenticated API endpoints; prevents one user from overwhelming shared resources |
| **Per API key** | All requests from one NBFC partner or service account | B2B integrations; per-partner quota enforcement |
| **Per tenant** | All requests from one organisation/NBFC across all their users | Multi-tenant platforms; prevents one tenant from consuming shared bureau quota |
| **Per endpoint** | All requests to one route regardless of caller | Protect expensive operations (bureau pull, NACH registration) |
| **Per user + endpoint** | One user's requests to one specific route | Granular: user X can call `/loan-applications` 5 times/min but `/bureau-pull` only twice/min |

In a lending platform:

```
/auth/login               → per IP (brute force protection; user not yet authenticated)
/kyc/verify-pan           → per tenant (bureau quota shared across tenant's users)
/loan-applications POST   → per user (applicant cannot spam applications)
/nach/mandates POST       → per tenant (NPCI quota is per registered entity)
/reports/portfolio        → per user + endpoint (heavy query; limit per user)
/webhooks/juspay          → no limit (inbound webhook; throttling would lose events)
```

## Section 2: Implementing Rate Limiting in NestJS

**Q4. How do you implement a Fixed Window rate limiter using Redis in NestJS?**
A:

```typescript
// core/rate-limit/fixed-window.service.ts
import { Injectable } from '@nestjs/common';
import { Redis }       from 'ioredis';
import { Inject }      from '@nestjs/common';

export interface RateLimitResult {
  allowed:    boolean;
  limit:      number;
  remaining:  number;
  resetAt:    number;  // Unix timestamp (seconds)
  retryAfter: number;  // seconds to wait if rejected
}

@Injectable()
export class FixedWindowRateLimiter {
  constructor(@Inject('REDIS_CLIENT') private readonly redis: Redis) {}

  async check(
    key:           string,   // e.g. 'rl:loan-apply:USR-001'
    limit:         number,   // max requests per window
    windowSeconds: number,   // window duration in seconds
  ): Promise<RateLimitResult> {
    // Lua script — atomic INCR + EXPIRE in a single round trip
    // Prevents race conditions between INCR and EXPIRE
    const lua = `
      local current = redis.call('INCR', KEYS[1])
      if current == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[1])
      end
      local ttl = redis.call('TTL', KEYS[1])
      return {current, ttl}
    `;

    const [count, ttl] = await this.redis.eval(
      lua, 1, key, String(windowSeconds),
    ) as [number, number];

    const resetAt    = Math.floor(Date.now() / 1000) + ttl;
    const remaining  = Math.max(0, limit - count);
    const allowed    = count <= limit;

    return {
      allowed,
      limit,
      remaining,
      resetAt,
      retryAfter: allowed ? 0 : ttl,
    };
  }
}
```

**Q5. How do you implement the Sliding Window Counter algorithm using Redis?**
A: The sliding window counter maintains two fixed-window counters and interpolates between them — exact enough for production, cheap on Redis:

```typescript
// core/rate-limit/sliding-window.service.ts
@Injectable()
export class SlidingWindowRateLimiter {
  constructor(@Inject('REDIS_CLIENT') private readonly redis: Redis) {}

  async check(
    key:           string,
    limit:         number,
    windowSeconds: number,
  ): Promise<RateLimitResult> {
    const now          = Math.floor(Date.now() / 1000);
    const currentSlot  = Math.floor(now / windowSeconds); // current window bucket
    const prevSlot     = currentSlot - 1;                 // previous window bucket
    const elapsedInWindow = now % windowSeconds;          // seconds elapsed in current window
    const prevWeight   = (windowSeconds - elapsedInWindow) / windowSeconds;

    const currentKey   = `${key}:${currentSlot}`;
    const prevKey      = `${key}:${prevSlot}`;

    // Atomic: INCR current window + EXPIRE + GET previous window
    const lua = `
      local curr = redis.call('INCR', KEYS[1])
      if curr == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[1])
      end
      local prev = tonumber(redis.call('GET', KEYS[2])) or 0
      return {curr, prev}
    `;

    const [currentCount, prevCount] = await this.redis.eval(
      lua, 2,
      currentKey, prevKey,
      String(windowSeconds * 2), // keep previous window until it fully expires
    ) as [number, number];

    // Weighted estimate: fraction of prev window still in scope
    const estimatedCount = (prevCount * prevWeight) + currentCount;
    const allowed        = estimatedCount <= limit;
    const remaining      = Math.max(0, Math.floor(limit - estimatedCount));
    const resetAt        = (currentSlot + 1) * windowSeconds;

    return {
      allowed,
      limit,
      remaining,
      resetAt,
      retryAfter: allowed ? 0 : resetAt - now,
    };
  }
}
```

**Q6. How do you implement a Token Bucket rate limiter using Redis?**
A: The token bucket state (token count + last refill timestamp) is stored atomically in Redis using a Lua script:

```typescript
// core/rate-limit/token-bucket.service.ts
@Injectable()
export class TokenBucketRateLimiter {
  constructor(@Inject('REDIS_CLIENT') private readonly redis: Redis) {}

  async consume(
    key:          string,
    capacity:     number,   // max tokens in bucket
    refillRatePs: number,   // tokens added per second
    tokensNeeded: number = 1,
  ): Promise<RateLimitResult> {
    const now = Date.now() / 1000; // current time in seconds (float)

    // Lua: read current state, compute refill, consume tokens — all atomic
    const lua = `
      local key      = KEYS[1]
      local capacity = tonumber(ARGV[1])
      local rate     = tonumber(ARGV[2])
      local now      = tonumber(ARGV[3])
      local needed   = tonumber(ARGV[4])
      local ttl      = tonumber(ARGV[5])

      local data     = redis.call('HMGET', key, 'tokens', 'last_refill')
      local tokens   = tonumber(data[1]) or capacity
      local last     = tonumber(data[2]) or now

      -- Refill tokens based on elapsed time
      local elapsed  = math.max(0, now - last)
      tokens         = math.min(capacity, tokens + elapsed * rate)

      local allowed  = tokens >= needed
      if allowed then
        tokens = tokens - needed
      end

      redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
      redis.call('EXPIRE', key, ttl)

      -- Return: allowed (0/1), remaining tokens (floor), seconds until 1 token available
      local wait = allowed and 0 or ((needed - tokens) / rate)
      return {allowed and 1 or 0, math.floor(tokens), math.ceil(wait)}
    `;

    const ttl = Math.ceil(capacity / refillRatePs) * 2; // auto-expire idle buckets

    const [allowedInt, remaining, waitSeconds] = await this.redis.eval(
      lua, 1, key,
      String(capacity),
      String(refillRatePs),
      String(now),
      String(tokensNeeded),
      String(ttl),
    ) as [number, number, number];

    return {
      allowed:    allowedInt === 1,
      limit:      capacity,
      remaining,
      resetAt:    Math.floor(now + waitSeconds),
      retryAfter: waitSeconds,
    };
  }
}
```

**Q7. How do you build a NestJS Middleware that applies rate limiting with route-specific policies?**
A:

```typescript
// core/rate-limit/rate-limit.middleware.ts
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';
import { SlidingWindowRateLimiter } from './sliding-window.service';
import { AppLogger } from '../logger/app-logger.service';

// Route-specific policies — resolved by method + normalised path
export interface RateLimitPolicy {
  limit:         number;
  windowSeconds: number;
  keyStrategy:   'ip' | 'user' | 'tenant' | 'user+endpoint' | 'tenant+endpoint';
  algorithm:     'sliding-window' | 'token-bucket';
  // Token bucket specific
  capacity?:     number;
  refillRatePs?: number;
}

const POLICIES: Record<string, RateLimitPolicy> = {
  // Authentication — brute force protection
  'POST:/auth/login':                    { limit: 5,   windowSeconds: 60,   keyStrategy: 'ip',              algorithm: 'sliding-window' },
  'POST:/auth/refresh':                  { limit: 10,  windowSeconds: 60,   keyStrategy: 'ip',              algorithm: 'sliding-window' },

  // KYC — bureau quota is per tenant
  'POST:/kyc/verify-pan':                { limit: 100, windowSeconds: 60,   keyStrategy: 'tenant+endpoint', algorithm: 'sliding-window' },
  'POST:/kyc/verify-aadhaar':            { limit: 50,  windowSeconds: 60,   keyStrategy: 'tenant+endpoint', algorithm: 'sliding-window' },

  // Loan origination — per user to prevent spam
  'POST:/loan-applications':             { limit: 5,   windowSeconds: 3600, keyStrategy: 'user+endpoint',   algorithm: 'sliding-window' },

  // NACH — NPCI quota is per registered entity (tenant)
  'POST:/nach/mandates':                 { limit: 20,  windowSeconds: 3600, keyStrategy: 'tenant+endpoint', algorithm: 'sliding-window' },

  // Disbursement — high value; strict per-user
  'POST:/disbursements':                 { limit: 3,   windowSeconds: 3600, keyStrategy: 'user+endpoint',   algorithm: 'sliding-window' },

  // Reporting — heavy queries; per user
  'GET:/reports/portfolio':              { limit: 10,  windowSeconds: 60,   keyStrategy: 'user+endpoint',   algorithm: 'sliding-window' },

  // Batch uploads — token bucket to allow burst
  'POST:/nach/mandates/batch':           { limit: 0,   windowSeconds: 0,    keyStrategy: 'tenant',          algorithm: 'token-bucket',
                                           capacity: 5, refillRatePs: 0.083 }, // 5 burst; 1 batch per 12s

  // Default — broad limit for unlisted routes
  'DEFAULT':                             { limit: 300, windowSeconds: 60,   keyStrategy: 'ip',              algorithm: 'sliding-window' },
};

@Injectable()
export class RateLimitMiddleware implements NestMiddleware {
  constructor(
    private readonly slidingWindow: SlidingWindowRateLimiter,
    private readonly tokenBucket:   TokenBucketRateLimiter,
    private readonly logger:        AppLogger,
  ) {}

  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    const routeKey = `${req.method}:${this.normalisePath(req.path)}`;
    const policy   = POLICIES[routeKey] ?? POLICIES['DEFAULT'];
    const clientKey = this.buildClientKey(req, policy.keyStrategy, routeKey);

    let result: RateLimitResult;

    if (policy.algorithm === 'token-bucket') {
      result = await this.tokenBucket.consume(
        clientKey,
        policy.capacity!,
        policy.refillRatePs!,
      );
    } else {
      result = await this.slidingWindow.check(
        clientKey,
        policy.limit,
        policy.windowSeconds,
      );
    }

    // Always set rate limit headers — even on allowed requests
    res.setHeader('X-RateLimit-Limit',     policy.limit || policy.capacity!);
    res.setHeader('X-RateLimit-Remaining', result.remaining);
    res.setHeader('X-RateLimit-Reset',     result.resetAt);

    if (!result.allowed) {
      res.setHeader('Retry-After', result.retryAfter);

      this.logger.warn('RateLimitMiddleware', 'Rate limit exceeded', {
        clientKey,
        routeKey,
        limit:         policy.limit,
        retryAfter:    result.retryAfter,
        correlationId: req.headers['x-correlation-id'],
      });

      res.status(429).json({
        statusCode:  429,
        error:       'Too Many Requests',
        message:     'Rate limit exceeded. See Retry-After header.',
        retryAfter:  result.retryAfter,
        resetAt:     new Date(result.resetAt * 1000).toISOString(),
      });
      return;
    }

    next();
  }

  private buildClientKey(
    req:      Request,
    strategy: RateLimitPolicy['keyStrategy'],
    route:    string,
  ): string {
    const user     = (req as any).user;
    const tenantId = user?.tenantId ?? req.headers['x-tenant-id'] ?? 'unknown';
    const userId   = user?.id        ?? 'anonymous';
    const ip       = req.ip;

    const prefix = 'rl';
    switch (strategy) {
      case 'ip':               return `${prefix}:ip:${ip}`;
      case 'user':             return `${prefix}:user:${userId}`;
      case 'tenant':           return `${prefix}:tenant:${tenantId}`;
      case 'user+endpoint':    return `${prefix}:user+ep:${userId}:${route}`;
      case 'tenant+endpoint':  return `${prefix}:tenant+ep:${tenantId}:${route}`;
    }
  }

  private normalisePath(path: string): string {
    return path
      .replace(/[0-9a-f-]{36}/gi, ':id')  // UUID params
      .replace(/\/\d+/g, '/:id')           // numeric params
      .replace(/\?.*$/, '');               // strip query string
  }
}
```

## Section 3: NestJS Throttler Integration

**Q8. How do you use `@nestjs/throttler` for declarative rate limiting and when do you choose it over a custom middleware?**
A: `@nestjs/throttler` is NestJS's official rate limiting package. It applies rate limits via decorators on controllers and handlers — declarative and integrated with NestJS's guard system:

```typescript
// app.module.ts — configure ThrottlerModule globally
import { ThrottlerModule, ThrottlerGuard } from '@nestjs/throttler';
import { ThrottlerStorageRedisService } from 'nestjs-throttler-storage-redis';

@Module({
  imports: [
    ThrottlerModule.forRootAsync({
      imports:    [ConfigModule],
      useFactory: (config: ConfigService) => ({
        throttlers: [
          // Multiple named throttlers — applied in order; ALL must pass
          { name: 'short',  ttl: 1_000,    limit: 10  },  // 10 req/s burst protection
          { name: 'medium', ttl: 60_000,   limit: 100 },  // 100 req/min
          { name: 'long',   ttl: 3_600_000, limit: 1000 }, // 1000 req/hour
        ],
        storage: new ThrottlerStorageRedisService(
          new Redis({
            host:     config.get('REDIS_HOST'),
            port:     config.get<number>('REDIS_PORT'),
            password: config.get('REDIS_PASSWORD'),
          }),
        ),
      }),
      inject: [ConfigService],
    }),
  ],
  providers: [
    // Apply ThrottlerGuard globally — all routes rate-limited by default
    { provide: APP_GUARD, useClass: ThrottlerGuard },
  ],
})
export class AppModule {}

// Controller — override defaults per route
@Controller('loan-applications')
@Throttle({ medium: { limit: 5, ttl: 3_600_000 } }) // 5 loan applications per hour per user
export class LoanApplicationController {

  @Post()
  async apply(@Body() dto: CreateLoanApplicationDto): Promise<LoanApplicationResponseDto> {
    return this.loanService.apply(dto);
  }

  @Get()
  @Throttle({ medium: { limit: 60, ttl: 60_000 } }) // list endpoint: more lenient
  async list(@Query() query: ListQueryDto): Promise<PaginatedResponseDto<LoanApplicationResponseDto>> {
    return this.loanService.list(query);
  }

  @Get('health')
  @SkipThrottle()  // health check — never rate-limited
  health(): { status: string } {
    return { status: 'ok' };
  }
}

// Custom throttler key — use user ID instead of IP (default is IP)
@Injectable()
export class UserIdThrottlerGuard extends ThrottlerGuard {
  protected async getTracker(req: Record<string, any>): Promise<string> {
    // Use authenticated user ID as the rate limit key — not IP
    // Prevents IP-based limits from wrongly throttling users behind a NAT
    return req.user?.id ?? req.ip;
  }

  // Custom 429 response — include Retry-After header
  protected throwThrottlingException(context: ExecutionContext, throttlerLimitDetail: ThrottlerLimitDetail): Promise<void> {
    const res = context.switchToHttp().getResponse();
    res.setHeader('Retry-After', Math.ceil(throttlerLimitDetail.ttl / 1000));
    return super.throwThrottlingException(context, throttlerLimitDetail);
  }
}
```

**When to use `@nestjs/throttler` vs custom middleware:**

| `@nestjs/throttler` | Custom Middleware |
|---|---|
| Standard rate limiting on most routes | Complex multi-dimensional policies (per tenant + per endpoint simultaneously) |
| Declarative `@Throttle()` per handler | Token bucket algorithm (throttler only supports fixed/sliding window) |
| Works with NestJS guards pipeline | Pre-authentication rate limiting (throttler runs after guards; middleware runs before) |
| Rapid setup; community-maintained | Detailed custom metrics per route + algorithm |
| Multiple named throttlers per route | Graceful degradation when Redis is down (fail-open logic) |

In a production fintech platform, a common pattern is to use both: `@nestjs/throttler` for standard authenticated-user limits on most routes, and custom Redis middleware at the gateway layer for pre-auth brute-force protection and tenant-level quota enforcement.

## Section 4: Distributed Rate Limiting

**Q9. Why does rate limiting require Redis in a multi-instance deployment, and what are the failure modes?**
A: In-memory rate limiting (a `Map` inside the Node.js process) maintains a counter per process. In a multi-instance deployment, each instance has its own counter — a client can exceed the intended limit by a factor of N (number of instances):

```
Limit: 100 req/min per user
Running: 4 instances

User sends 100 requests → round-robin → 25 req to each instance
Each instance sees 25 of 100 → none triggers the limit
Effective limit: 400 req/min (4× intended) — completely ineffective
```

Redis centralises the counter — every instance increments the same key:

```
User sends 400 requests → round-robin across 4 instances
All instances increment the same Redis key
Redis counter reaches 100 → all instances return 429 from that point
Effective limit: exactly 100 req/min — correct
```

**Redis failure modes and strategies:**

```typescript
@Injectable()
export class ResilientRateLimiter {
  constructor(
    private readonly redis:  Redis,
    private readonly logger: AppLogger,
  ) {}

  async check(key: string, limit: number, windowSeconds: number): Promise<RateLimitResult> {
    try {
      return await this.checkWithRedis(key, limit, windowSeconds);
    } catch (err) {
      // Redis is down — decide: fail-open or fail-closed
      this.logger.error('RateLimiter', 'Redis unavailable — applying fallback strategy', {
        error: err.message, key,
      });

      return this.failOpenFallback(limit);
      // OR: return this.failClosedFallback(); // reject all requests when Redis is down
    }
  }

  // Fail-open: allow requests when Redis is unavailable
  // Appropriate for: most API endpoints where availability > strict limiting
  private failOpenFallback(limit: number): RateLimitResult {
    return { allowed: true, limit, remaining: limit, resetAt: 0, retryAfter: 0 };
  }

  // Fail-closed: reject all requests when Redis is unavailable
  // Appropriate for: security-critical endpoints (login, PAN verification)
  private failClosedFallback(): RateLimitResult {
    return { allowed: false, limit: 0, remaining: 0, resetAt: 0, retryAfter: 60 };
  }

  // In-process fallback for non-critical routes — imprecise but better than nothing
  private readonly localCounters = new Map<string, { count: number; resetAt: number }>();

  private localFallback(key: string, limit: number, windowSeconds: number): RateLimitResult {
    const now  = Math.floor(Date.now() / 1000);
    const entry = this.localCounters.get(key);

    if (!entry || entry.resetAt <= now) {
      this.localCounters.set(key, { count: 1, resetAt: now + windowSeconds });
      return { allowed: true, limit, remaining: limit - 1, resetAt: now + windowSeconds, retryAfter: 0 };
    }

    entry.count++;
    const allowed = entry.count <= limit;
    return {
      allowed,
      limit,
      remaining:  Math.max(0, limit - entry.count),
      resetAt:    entry.resetAt,
      retryAfter: allowed ? 0 : entry.resetAt - now,
    };
  }
}
```

**Q10. How do you implement rate limiting at the API Gateway level vs at the individual service level, and when do you need both?**
A:

```
Client
  │
  ▼
API Gateway ── Rate Limit Layer 1:
                 - Per IP (brute force / unauthenticated)
                 - Per tenant (global quota across all services)
                 - Per API key (B2B partner quota)
                 ↓ (if allowed)
  ▼
Individual Service ── Rate Limit Layer 2:
                        - Per user + per endpoint (granular business rules)
                        - Per operation (bureau pull limit independent of API quota)
                        - Guards expensive downstream calls
```

**Gateway-level rate limiting** — coarse-grained; protects the entire platform:
- ✅ Applied before the request reaches any service — cheapest rejection
- ✅ Tenant quota: one NBFC partner cannot consume resources intended for another
- ✅ Unauthenticated traffic: protect login and public endpoints before auth runs
- ❌ Cannot enforce per-endpoint limits accurately if one gateway handles multiple services
- ❌ Gateway does not know business rules (e.g., "applicant can only submit 5 loan applications per month")

**Service-level rate limiting** — fine-grained; enforces business rules:
- ✅ Endpoint-specific limits tied to downstream costs (bureau API charges per call)
- ✅ Business policy limits (5 loan applications per applicant per month)
- ✅ Survives if the gateway is bypassed (internal service-to-service calls)
- ❌ Every service must implement its own Redis-backed limiter — duplication
- ❌ Per-tenant quota is harder to enforce consistently across all services

**When you need both:** A fintech lending platform serving NBFC partners needs gateway-level tenant quota (NBFC-A gets 10,000 API calls/day total) AND service-level limits (each applicant can submit 5 loan applications per month, regardless of which NBFC partner sponsors them). These are orthogonal constraints — neither layer can enforce both.

## Section 5: Advanced Patterns

**Q11. How do you implement tiered rate limits — different limits for different subscription tiers or partner types?**
A:

```typescript
// core/rate-limit/tiered-rate-limit.service.ts
export interface TenantRateLimitTier {
  name:              string;
  loanApplications:  { limit: number; windowSeconds: number };
  bureauPulls:       { limit: number; windowSeconds: number };
  nachMandates:      { limit: number; windowSeconds: number };
  apiCallsPerDay:    number;
}

const TIERS: Record<string, TenantRateLimitTier> = {
  STARTER: {
    name:             'Starter',
    loanApplications: { limit: 100,  windowSeconds: 3600  },
    bureauPulls:      { limit: 200,  windowSeconds: 3600  },
    nachMandates:     { limit: 50,   windowSeconds: 3600  },
    apiCallsPerDay:   5_000,
  },
  GROWTH: {
    name:             'Growth',
    loanApplications: { limit: 1_000,  windowSeconds: 3600 },
    bureauPulls:      { limit: 2_000,  windowSeconds: 3600 },
    nachMandates:     { limit: 500,    windowSeconds: 3600 },
    apiCallsPerDay:   50_000,
  },
  ENTERPRISE: {
    name:             'Enterprise',
    loanApplications: { limit: 10_000, windowSeconds: 3600 },
    bureauPulls:      { limit: 20_000, windowSeconds: 3600 },
    nachMandates:     { limit: 5_000,  windowSeconds: 3600 },
    apiCallsPerDay:   500_000,
  },
};

@Injectable()
export class TieredRateLimitService {
  constructor(
    private readonly slidingWindow:   SlidingWindowRateLimiter,
    private readonly tenantService:   TenantConfigService,
    private readonly redis:           Redis,
    private readonly logger:          AppLogger,
  ) {}

  async checkLoanApplication(tenantId: string, userId: string): Promise<RateLimitResult> {
    const tier   = await this.resolveTier(tenantId);
    const policy = TIERS[tier].loanApplications;

    // Check both tenant-level AND user-level limits — both must pass
    const [tenantResult, userResult] = await Promise.all([
      this.slidingWindow.check(
        `rl:loan-apply:tenant:${tenantId}`,
        policy.limit,
        policy.windowSeconds,
      ),
      this.slidingWindow.check(
        `rl:loan-apply:user:${userId}`,
        5,           // individual applicant limit — 5 applications per hour regardless of tier
        3_600,
      ),
    ]);

    // Most restrictive wins — if either limit is exceeded, reject
    if (!tenantResult.allowed) return tenantResult;
    if (!userResult.allowed)   return userResult;

    return tenantResult; // both passed; return tenant result (lower remaining)
  }

  async checkDailyApiQuota(tenantId: string): Promise<RateLimitResult> {
    const tier   = await this.resolveTier(tenantId);
    const limit  = TIERS[tier].apiCallsPerDay;

    // Daily window aligned to midnight IST
    const nowIst       = new Date(Date.now() + 5.5 * 60 * 60 * 1000);
    const midnightIst  = new Date(nowIst);
    midnightIst.setHours(24, 0, 0, 0);
    const windowSeconds = Math.floor((midnightIst.getTime() - Date.now()) / 1000);

    return this.slidingWindow.check(
      `rl:daily-quota:tenant:${tenantId}`,
      limit,
      windowSeconds,
    );
  }

  private async resolveTier(tenantId: string): Promise<string> {
    // Cache tier resolution — avoids DB round trip per request
    const cacheKey = `tenant_tier:${tenantId}`;
    const cached   = await this.redis.get(cacheKey);
    if (cached) return cached;

    const tier = await this.tenantService.getTier(tenantId);
    await this.redis.setex(cacheKey, 300, tier); // cache 5 minutes
    return tier;
  }
}
```

**Q13. How do you implement rate limit bypass for internal service-to-service calls?**
A: Internal services must be able to call each other without hitting client-facing rate limits — a Kafka consumer processing NACH events should not be throttled by the same limit applied to an NBFC partner:

```typescript
// Approach 1 — Service token header; middleware checks and skips
@Injectable()
export class RateLimitMiddleware implements NestMiddleware {
  async use(req: Request, res: Response, next: NextFunction): Promise<void> {
    // Internal service-to-service calls carry a service token
    const serviceToken = req.headers['x-service-token'] as string;
    if (serviceToken && await this.validateServiceToken(serviceToken)) {
      // Bypass rate limiting for authenticated internal services
      return next();
    }

    // External clients — apply rate limiting as normal
    await this.applyRateLimit(req, res, next);
  }

  private async validateServiceToken(token: string): Promise<boolean> {
    // Service tokens are short-lived JWTs signed with an internal secret
    try {
      const payload = this.jwtService.verify(token, { secret: this.config.get('INTERNAL_JWT_SECRET') });
      return payload.type === 'SERVICE';
    } catch {
      return false;
    }
  }
}

// Approach 2 — Separate internal route namespace; rate limiting only on /v1/external/*
configure(consumer: MiddlewareConsumer): void {
  // Rate limiting applied only to external-facing routes
  consumer
    .apply(RateLimitMiddleware)
    .exclude(
      { path: 'internal/(.*)', method: RequestMethod.ALL }, // internal routes exempt
      { path: 'health/(.*)',   method: RequestMethod.ALL },
    )
    .forRoutes('*');
}
```

```typescript
export class RateLimitMetricsService {
  constructor(private readonly metrics: MetricsService) {}

  recordCheck(params: {
    policy:    string;
    tenantId:  string;
    allowed:   boolean;
    remaining: number;
    algorithm: string;
  }): void {
    // Count all checks — gives total request volume per policy

      algorithm: params.algorithm,
      allowed:   String(params.allowed),
    });

        policy:   params.policy,
        tenantId: params.tenantId,
      });
    }

    // Gauge: how full is the window for top consumers
    this.metrics.setGauge('rate_limit_utilisation', params.remaining, {
      policy:   params.policy,
      tenantId: params.tenantId,
    });
  }
}
```

## Section 8: Common Anti-Patterns and Pitfalls

**Q17. What are the most common Rate Limiting mistakes in a NestJS fintech backend?**
A:

**Anti-pattern 1 — In-process rate limiting in a multi-instance deployment:**
```typescript
// ❌ Map-based counter in the process — each instance has its own counter
@Injectable()
export class RateLimiter {
  private readonly counters = new Map<string, { count: number; resetAt: number }>();

  check(key: string, limit: number): boolean {
    const entry = this.counters.get(key);
    if (!entry || Date.now() > entry.resetAt) {
      this.counters.set(key, { count: 1, resetAt: Date.now() + 60_000 });
      return true;
    }
    return ++entry.count <= limit;
  }
  // With 4 running instances: effective limit = 4× intended — completely ineffective
}

// ✅ Redis-backed counter — shared across all instances
```

**Anti-pattern 2 — Using IP address as the rate limit key for authenticated endpoints:**
```typescript
// ❌ IP-based rate limiting for authenticated users
// Users behind corporate NAT share one IP — one user's burst throttles all colleagues
// VPN exit nodes share IP — all users through the VPN share one limit

const key = `rl:${req.ip}`;  // wrong for authenticated endpoints

// ✅ Use user ID for authenticated endpoints; IP only for unauthenticated
const key = req.user?.id
  ? `rl:user:${req.user.id}`
  : `rl:ip:${req.ip}`;
```

**Anti-pattern 3 — INCR without EXPIRE — counters never reset:**
```typescript
// ❌ INCR without EXPIRE — counter grows forever; limit triggers permanently
await this.redis.incr(key);
const count = await this.redis.get(key);
if (parseInt(count) > limit) { /* reject */ }
// First time key is set: no EXPIRE → counter never resets → user is permanently blocked

// ✅ Atomic INCR + EXPIRE via Lua — ensures expiry is always set
const lua = `
  local count = redis.call('INCR', KEYS[1])
  if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
  end
  return count
`;
```

**Anti-pattern 4 — Applying rate limiting after authentication for login endpoints:**
```typescript
// ❌ Login endpoint rate limited per user ID — but attacker doesn't know valid user IDs
@Post('/auth/login')
@UseGuards(ThrottlerGuard)  // ThrottlerGuard runs after routing — too late for pre-auth
async login(@Body() dto: LoginDto): Promise<TokenResponse> { /* ... */ }

// ✅ Login rate limit must be per IP and run in middleware — before auth guard
configure(consumer: MiddlewareConsumer): void {
  consumer
    .apply(LoginRateLimitMiddleware)  // runs before guards; key = IP address
    .forRoutes({ path: 'auth/login', method: RequestMethod.POST });
}
```

**Anti-pattern 5 — Rate limiting webhook inbound endpoints:**
```typescript
// ❌ Rate limiting inbound webhooks from JusPay / Razorpay
// Payment gateway fires webhooks for every payment event
// Throttling them causes missed payment confirmations — financial inconsistency

@Post('/webhooks/juspay')
@UseGuards(ThrottlerGuard)  // wrong — this throttles JusPay's event delivery
async handleWebhook(@Body() payload: JusPayWebhookDto): Promise<void> { /* ... */ }

// ✅ Webhook endpoints must never be rate-limited; protect them by IP allowlist instead
@Post('/webhooks/juspay')
@SkipThrottle()
@UseGuards(WebhookIpAllowlistGuard)  // only JusPay's IP ranges can call this
async handleWebhook(@Body() payload: JusPayWebhookDto): Promise<void> { /* ... */ }
```

**Q19. "Your monitoring shows 40% of CIBIL bureau API calls are being rejected with 429s from CIBIL. How does rate limiting at your end prevent this and what changes do you make?"**
A:

```
Root cause analysis:
  CIBIL allows: 100 bureau pulls per minute per registered entity
  You are sending: 250+ concurrent bureau pulls during loan origination peaks
  CIBIL rejects 150 of them with 429 → your service gets BureauApiException
  → Loan applications fail → customer-facing errors

Current gap:
  No rate limit on outbound calls to CIBIL
  No bulkhead on concurrent bureau calls
  Multiple loan origination instances each firing independently

Fix — rate limit outbound calls to CIBIL:
```

```typescript
// Rate limit outbound bureau calls — not inbound client calls
@Injectable()
export class CibilBureauAdapter implements IBureauService {
  // Outbound rate limiter — 90 calls/min (10% headroom below CIBIL's 100/min limit)
  private readonly outboundLimiter = new TokenBucketRateLimiter(this.redis);

  async fetchCreditReport(pan: string): Promise<BureauReport> {
    // Check outbound rate limit before calling CIBIL
    const result = await this.outboundLimiter.consume(
      'outbound:cibil:global',   // global key — shared across all service instances
      90,                         // capacity: 90 tokens
      1.5,                        // refill: 1.5 tokens/second = 90/minute
    );

    if (!result.allowed) {
      // Don't fail the loan application — queue for retry
      this.logger.warn('CibilAdapter', 'Outbound rate limit reached — queuing for retry', {
        retryAfter: result.retryAfter,
      });
      throw new BureauOutboundRateLimitException(result.retryAfter);
    }

    return this.callCibil(pan);
  }
}

// LoanApplicationService — handles BureauOutboundRateLimitException
async apply(dto: CreateLoanApplicationDto, userId: string): Promise<LoanApplication> {
  try {
    const bureauReport = await this.bureauService.fetchCreditReport(dto.pan);
    // ...
  } catch (err) {
    if (err instanceof BureauOutboundRateLimitException) {
      // Queue for deferred processing — don't reject the applicant
      await this.deferredBureauQueue.enqueue({ dto, userId, retryAfter: err.retryAfter });
      return this.loanRepo.create({ ...dto, userId, status: LoanStatus.BUREAU_PENDING });
    }
    throw err;
  }
}
```

The outbound rate limiter protects your CIBIL quota. The deferred queue ensures applicants don't get rejected — their bureau pull is processed when quota becomes available again.

## Quick Reference: Rate Limiting Pattern Cheat Sheet

```
RATE LIMITING — QUICK REFERENCE
──────────────────────────────────

ALGORITHMS
  Fixed Window       → simple; boundary burst vulnerability; use for daily quotas
  Sliding Window Log → exact; memory-heavy; avoid at scale
  Sliding Window     → accurate approximation; 2 Redis keys; BEST DEFAULT CHOICE
  Token Bucket       → allows bursts up to capacity; good for batch/upload endpoints
  Leaky Bucket       → smoothest output; adds latency; rarely used in REST APIs

KEY STRATEGY BY ENDPOINT TYPE
  Unauthenticated (login, register) → per IP
  Authenticated user endpoints      → per user ID (NOT IP — NAT issue)
  Per-feature business limits       → per user + endpoint
  B2B partner quota                 → per tenant
  Shared downstream quota (bureau)  → per tenant + endpoint
  Outbound calls to 3rd party APIs  → global key (shared across all instances)
  Webhooks inbound                  → NEVER rate limit; use IP allowlist instead

SLIDING WINDOW COUNTER (production default)
  Two Redis keys: current window slot + previous window slot
  Estimated count = (prevCount × prevWeight) + currentCount
  prevWeight = (windowSeconds - elapsed) / windowSeconds
  Atomic via Lua script — one round trip

TOKEN BUCKET (batch / burst endpoints)
  State: {tokens, last_refill} in Redis HMSET
  On request: tokens += elapsed × refillRate; tokens = min(tokens, capacity)
  Consume 1 token per request; reject if tokens < 1
  Atomic via Lua script

RESPONSE HEADERS (set on all responses)
  X-RateLimit-Limit:     {limit}        max requests in window
  X-RateLimit-Remaining: {remaining}    requests left
  X-RateLimit-Reset:     {unix_ts}      when window resets
  Retry-After:           {seconds}      429 responses only (RFC 7231)

REDIS FAILURE HANDLING
  Fail-open  → allow when Redis is down (most endpoints; availability > strict limiting)
  Fail-closed → reject when Redis is down (login, PAN verify; security > availability)
  Local fallback → in-process counter (imprecise; better than nothing)

TIERED LIMITS (NBFC partner tiers)
  STARTER:    5_000  req/day  |  100 bureau/hr  |  50  NACH/hr
  GROWTH:    50_000  req/day  | 2000 bureau/hr  | 500  NACH/hr
  ENTERPRISE: 500_000 req/day | 20_000 bureau/hr | 5_000 NACH/hr
  Cache tier resolution in Redis — avoid DB round trip per request

MULTI-LAYER STRATEGY
  Layer 1 (Gateway): per-IP global; login brute-force; pre-authentication
  Layer 2 (Gateway): per-tenant daily quota; post-authentication
  Layer 3 (Service): per-user+endpoint business rules; outbound API limits
  Internal bypass: x-service-token header → skip client-facing limits

OUTBOUND RATE LIMITING
  Rate limit your OWN calls to CIBIL, NPCI, JusPay — not just inbound
  Key: 'outbound:{service}:global' — shared across all your instances
  On limit: queue for retry (deferred bureau pull) — don't reject applicant

@nestjs/throttler
  Use for standard authenticated-user limits via @Throttle() decorators
  Custom guard: override getTracker() to use user ID instead of IP
  Combine with custom middleware for pre-auth and tenant-level limits

ANTI-PATTERNS
  ❌ In-process Map counter in multi-instance deployment (N× bypass)
  ❌ IP key for authenticated endpoints (NAT / VPN collapses many users)
  ❌ INCR without EXPIRE (counter never resets → permanent block)
  ❌ Rate limiting login per user ID (attacker doesn't know valid IDs)
  ❌ Rate limiting inbound webhooks (missed payment events)
  ❌ No outbound rate limit to 3rd party APIs (their 429s become your errors)
  ❌ maxQueue too large (turns rate limit into slow queue)
  ❌ Fail-closed on all endpoints when Redis is down (availability collapse)
```
