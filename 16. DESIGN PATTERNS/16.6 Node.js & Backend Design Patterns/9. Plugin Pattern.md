# Node.js & Backend Design Patterns: Plugin Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Plugin Pattern?**
A: The Plugin Pattern is an architectural pattern that allows **new behaviour to be added to a system at runtime or compile time without modifying the core application code**. The core system defines extension points — well-defined interfaces, hooks, or registries — and plugins (also called extensions or add-ons) conform to those contracts to inject new behaviour. The core is unaware of specific plugins; plugins are unaware of each other. The system discovers, loads, and wires plugins dynamically.

The three defining elements:
- **Plugin interface / contract** — what the core system expects from any plugin (the shape it must implement).
- **Plugin registry** — the central store that maps plugin names or keys to their implementations; the lookup mechanism.
- **Extension points** — specific moments or hooks in the core flow where registered plugins are invoked.

**Q2. What problem does the Plugin Pattern solve? When should you reach for it?**
A: The Plugin Pattern solves the **extension without modification** problem — the need to let a system grow in capabilities over time without every new feature requiring changes to the core codebase. It's the architectural-level expression of the Open/Closed Principle: the core is closed for modification, open for extension via plugins.

Reach for it when:
- **Third-party or team extensibility** — you're building a platform that other teams (or customers) should be able to extend without access to your core code.
- **Feature variability per tenant/environment** — different deployments need different capabilities (premium features enabled for some tenants, disabled for others; region-specific compliance checks).
- **Growing family of interchangeable implementations** — payment gateways, bureau providers, notification channels, KYC vendors — each is a plugin conforming to the same interface.
- **Runtime feature toggling** — plugins can be loaded or unloaded based on feature flags without restarting or redeploying the system.
- **Avoiding a monolithic service** — instead of one service that handles every integration, each integration is its own plugin registered against the core.

Do NOT apply it when: there is only one implementation and no realistic prospect of a second; the team is small and the overhead of plugin infrastructure isn't justified; or when a simpler Strategy pattern (injecting one algorithm) already solves the problem.

**Q3. How does the Plugin Pattern relate to Strategy, Chain of Responsibility, and Decorator?**
A:

| Pattern                    | Relationship to Plugin                                               | Key difference                                                        |
|----------------------------|----------------------------------------------------------------------|-----------------------------------------------------------------------|
| **Strategy**               | Plugin is Strategy at an architectural scale                        | Strategy swaps one algorithm; Plugin registers many, discovered dynamically |
| **Chain of Responsibility**| CoR chain can be built from plugins registered in order             | CoR has defined pass/stop semantics; Plugin is a broader registration concept |
| **Decorator**              | Plugins can be implemented as decorators wrapping a core behaviour  | Decorator always wraps one object; Plugin is discovered from a registry |
| **Observer/Event Emitter** | Plugins often subscribe to hooks via an event system               | Plugins are more structured — they conform to an interface, not just a callback |

The Plugin Pattern is more of an architectural strategy than a single design pattern — it combines several design patterns (Registry, Strategy, Observer, Factory) into a system-level extension mechanism. Strategy answers "how do I swap one algorithm?" Plugin answers "how do I let the system grow without touching its core?"

**Q4. What are the two main plugin discovery mechanisms?**
A:

**Static registration** — plugins are known at compile/startup time and registered explicitly in code or configuration:
```typescript
// Explicit registration in a module or bootstrap
pluginRegistry.register('CIBIL', new CibilBureauPlugin());
pluginRegistry.register('EXPERIAN', new ExperianBureauPlugin());
pluginRegistry.register('KARZA', new KarzaBureauPlugin());
```

**Dynamic discovery** — the system scans a directory, reads a config file, or queries a registry at startup and loads plugins it finds:
```typescript
// Dynamic discovery — scan /plugins directory at startup
const pluginFiles = fs.readdirSync('./plugins').filter(f => f.endsWith('.plugin.js'));
for (const file of pluginFiles) {
  const plugin = require(`./plugins/${file}`);
  pluginRegistry.register(plugin.name, plugin);
}
```

In NestJS backends, **static registration via the DI container** (using `multi` providers or custom tokens) is the dominant approach — it preserves TypeScript's type safety while achieving plugin extensibility. Dynamic discovery is more common in CLI tools, build systems, and frameworks (Webpack, Babel, ESLint) where plugins are npm packages installed separately.

**Q5. What is the difference between a Plugin and a Module in a NestJS context?**
A: The terms overlap but have different scopes:

- **NestJS Module** — the fundamental unit of organisation in NestJS. Encapsulates related controllers, services, and repositories. Wired at application startup via `imports`. Modules are always known to the application at compile time.
- **Plugin (in the Plugin Pattern sense)** — a unit of extension that conforms to a contract and is registered against an extension point. May be implemented as a NestJS module internally, but the Plugin Pattern adds the registration/discovery/invocation mechanics on top.

In practice, a "plugin" in a NestJS lending platform often means: a NestJS module that implements a specific interface (e.g., `IBureauPlugin`) and registers itself (or is registered externally) against a plugin registry. The registry is the extra layer that makes it a Plugin Pattern rather than plain module composition.

## Section 2: Implementation

**Q6. What does a canonical Plugin Pattern implementation look like in NestJS/TypeScript?**
A: A bureau integration plugin system — multiple bureau providers, each a plugin:

```typescript
// Plugin contract — what every bureau plugin must implement
interface IBureauPlugin {
  readonly name: string;                              // unique identifier
  readonly supportedSegments: CustomerSegment[];      // which segments this plugin handles

  fetchCreditReport(pan: string): Promise<CreditReport>;
  fetchCreditScore(pan: string): Promise<number>;
  isAvailable(): Promise<boolean>;                    // health check
}

// Plugin registry — the central store
@Injectable()
export class BureauPluginRegistry {
  private readonly plugins = new Map<string, IBureauPlugin>();

  register(plugin: IBureauPlugin): void {
    if (this.plugins.has(plugin.name)) {
      throw new Error(`Bureau plugin '${plugin.name}' is already registered`);
    }
    this.plugins.set(plugin.name, plugin);
  }

  getByName(name: string): IBureauPlugin {
    const plugin = this.plugins.get(name);
    if (!plugin) throw new PluginNotFoundException(`No bureau plugin registered for: ${name}`);
    return plugin;
  }

  getForSegment(segment: CustomerSegment): IBureauPlugin {
    const plugin = [...this.plugins.values()].find(p => p.supportedSegments.includes(segment));
    if (!plugin) throw new PluginNotFoundException(`No bureau plugin for segment: ${segment}`);
    return plugin;
  }

  getAll(): IBureauPlugin[] {
    return [...this.plugins.values()];
  }

  async getHealthy(): Promise<IBureauPlugin[]> {
    const checks = await Promise.allSettled(
      [...this.plugins.values()].map(async p => ({ plugin: p, available: await p.isAvailable() })),
    );
    return checks
      .filter((r): r is PromiseFulfilledResult<{ plugin: IBureauPlugin; available: boolean }> =>
        r.status === 'fulfilled' && r.value.available,
      )
      .map(r => r.value.plugin);
  }
}
```

```typescript
// NestJS module — registers all plugins via DI multi-provider
export const BUREAU_PLUGIN = 'BUREAU_PLUGIN';

@Module({
  providers: [
    BureauPluginRegistry,
    CibilBureauPlugin,
    ExperianBureauPlugin,
    KarzaBureauPlugin,
    // Multi-provider — NestJS injects all three as an array
    { provide: BUREAU_PLUGIN, useClass: CibilBureauPlugin, multi: true },
    { provide: BUREAU_PLUGIN, useClass: ExperianBureauPlugin, multi: true },
    { provide: BUREAU_PLUGIN, useClass: KarzaBureauPlugin, multi: true },
  ],
  exports: [BureauPluginRegistry],
})
export class BureauPluginModule implements OnModuleInit {
  constructor(
    private readonly registry: BureauPluginRegistry,
    @Inject(BUREAU_PLUGIN) private readonly plugins: IBureauPlugin[],
  ) {}

  onModuleInit(): void {
    // Self-registration at startup — plugins announce themselves to the registry
    for (const plugin of this.plugins) {
      this.registry.register(plugin);
    }
  }
}

// Consumer — depends only on the registry, unaware of specific plugins
@Injectable()
export class UnderwritingService {
  constructor(private readonly bureauRegistry: BureauPluginRegistry) {}

  async assessCredit(applicant: Applicant): Promise<CreditAssessment> {
    const plugin = this.bureauRegistry.getForSegment(applicant.segment);
    const report = await plugin.fetchCreditReport(applicant.pan);
    return this.evaluateReport(report);
  }
}
```

**Q7. How do you implement a hook-based Plugin Pattern where plugins intercept lifecycle events?**
A: Rather than direct invocation, hooks allow plugins to react to events at defined extension points:

```typescript
// Hook interface — plugins implement the hooks they care about
interface ILoanLifecyclePlugin {
  readonly name: string;
  readonly priority: number;  // determines execution order when multiple plugins have the same hook

  onApplicationSubmitted?(application: LoanApplication): Promise<void>;
  onApplicationSanctioned?(application: LoanApplication, sanctionedBy: string): Promise<void>;
  onDisbursementInitiated?(loan: ActiveLoan, amount: number): Promise<void>;
  onEmiDefaulted?(loan: ActiveLoan, dpd: number): Promise<void>;
}

// Hook executor — the engine that calls registered plugins at each extension point
@Injectable()
export class LoanLifecycleHookExecutor {
  private readonly plugins: ILoanLifecyclePlugin[] = [];

  register(plugin: ILoanLifecyclePlugin): void {
    this.plugins.push(plugin);
    // Keep sorted by priority for deterministic ordering
    this.plugins.sort((a, b) => a.priority - b.priority);
  }

  async executeHook<K extends keyof ILoanLifecyclePlugin>(
    hookName: K,
    ...args: Parameters<Required<ILoanLifecyclePlugin>[K]>
  ): Promise<void> {
    const applicablePlugins = this.plugins.filter(p => typeof p[hookName] === 'function');

    for (const plugin of applicablePlugins) {
      try {
        await (plugin[hookName] as Function)(...args);
      } catch (err) {
        // Plugin failures should not break the core flow
        this.logger.error(`Plugin '${plugin.name}' hook '${hookName}' failed`, err);
      }
    }
  }
}

@Injectable()
export class NachSetupPlugin implements ILoanLifecyclePlugin {

  async onApplicationSanctioned(application: LoanApplication, _sanctionedBy: string): Promise<void> {
    await this.nachService.initiateMandate(application.id, application.applicantId);
  }
}

@Injectable()
export class FraudMonitoringPlugin implements ILoanLifecyclePlugin {

// Core service — calls hooks at extension points; unaware of specific plugins
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepository: LoanRepository,
    private readonly hookExecutor: LoanLifecycleHookExecutor,
  ) {}

  async sanction(loanId: string, dto: SanctionDto, officerId: string): Promise<LoanApplication> {
    const loan = await this.loanRepository.findById(loanId);
    // ... business logic ...
    const updated = await this.loanRepository.updateStatus(loanId, 'SANCTIONED', { /* ... */ });

    // Extension point — all plugins with onApplicationSanctioned are called
    await this.hookExecutor.executeHook('onApplicationSanctioned', updated, officerId);

    return updated;
  }
}
```

**Q8. How do you implement a middleware-style Plugin Pattern where plugins can transform data in a pipeline?**
A: Each plugin in the pipeline processes and optionally transforms the request/response:

```typescript
// Middleware-style plugin interface — transform the context
interface IKycEnrichmentPlugin {
  readonly name: string;
  readonly order: number;
  enrich(context: KycEnrichmentContext): Promise<KycEnrichmentContext>;
}

interface KycEnrichmentContext {
  applicant: Applicant;
  enrichments: Record<string, unknown>;  // each plugin adds to this map
  warnings: string[];
}

// Plugin pipeline executor
@Injectable()
export class KycEnrichmentPipeline {
  private readonly plugins: IKycEnrichmentPlugin[] = [];

  register(plugin: IKycEnrichmentPlugin): void {
    this.plugins.push(plugin);
    this.plugins.sort((a, b) => a.order - b.order);
  }

  async run(applicant: Applicant): Promise<KycEnrichmentContext> {
    let context: KycEnrichmentContext = {
      applicant,
      enrichments: {},
      warnings: [],
    };

    for (const plugin of this.plugins) {
      try {
        context = await plugin.enrich(context);
      } catch (err) {
        context.warnings.push(`Plugin '${plugin.name}' failed: ${(err as Error).message}`);
        // Continue pipeline despite plugin failure (soft failure policy)
      }
    }

    return context;
  }
}

// Plugins — each adds one enrichment to the context
@Injectable()
export class PanVerificationPlugin implements IKycEnrichmentPlugin {
  readonly name = 'PAN_VERIFICATION';
  readonly order = 1;

  async enrich(ctx: KycEnrichmentContext): Promise<KycEnrichmentContext> {
    const result = await this.nsdlService.verify(ctx.applicant.pan, ctx.applicant.name);
    return {
      ...ctx,
      enrichments: { ...ctx.enrichments, panVerification: result },
    };
  }
}

@Injectable()
export class AadhaarVerificationPlugin implements IKycEnrichmentPlugin {
  readonly name = 'AADHAAR_VERIFICATION';
  readonly order = 2;

  async enrich(ctx: KycEnrichmentContext): Promise<KycEnrichmentContext> {
    const result = await this.uidaiService.verify(ctx.applicant.aadhaar, ctx.applicant.aadhaarOtp);
    return { ...ctx, enrichments: { ...ctx.enrichments, aadhaarVerification: result } };
  }
}

@Injectable()
export class GstinVerificationPlugin implements IKycEnrichmentPlugin {
  readonly name = 'GSTIN_VERIFICATION';
  readonly order = 3;

  async enrich(ctx: KycEnrichmentContext): Promise<KycEnrichmentContext> {
    // Only applicable for MSME — skip gracefully for other segments
    if (!ctx.applicant.gstin) return ctx;

    const result = await this.gstnService.verify(ctx.applicant.gstin);
    return { ...ctx, enrichments: { ...ctx.enrichments, gstinVerification: result } };
  }
}
```

## Section 3: Plugin Pattern in Real-World Fintech Contexts

**Q9. How would you use the Plugin Pattern for a multi-payment-gateway disbursement system?**
A: Each payment gateway (Razorpay, PayU, Cashfree) is a plugin; the disbursement engine selects and invokes the right one:

```typescript
interface IPaymentGatewayPlugin {
  readonly name: string;
  readonly supportedModes: PaymentMode[];  // NEFT, RTGS, IMPS, UPI
  readonly maxTransactionAmount: number;   // in paise

  isAvailable(): Promise<boolean>;
  initiatePayout(request: PayoutRequest): Promise<PayoutResult>;
  checkPayoutStatus(gatewayPayoutId: string): Promise<PayoutStatus>;
  parseWebhook(payload: unknown, signature: string): DomainPaymentEvent;
}

@Injectable()
export class PaymentGatewayRegistry {
  private readonly plugins = new Map<string, IPaymentGatewayPlugin>();
  private primaryGateway: string = 'RAZORPAY';
  private fallbackOrder: string[] = ['PAYU', 'CASHFREE'];

  register(plugin: IPaymentGatewayPlugin): void {
    this.plugins.set(plugin.name, plugin);
  }

  // Primary gateway — used by default
  getPrimary(): IPaymentGatewayPlugin {
    return this.plugins.get(this.primaryGateway)!;
  }

  // Failover — returns the first available gateway from fallback list
  async getAvailableForAmount(amount: number, mode: PaymentMode): Promise<IPaymentGatewayPlugin> {
    // Try primary first
    const primary = this.plugins.get(this.primaryGateway);
    if (primary
      && primary.supportedModes.includes(mode)
      && amount <= primary.maxTransactionAmount
      && await primary.isAvailable()) {
      return primary;
    }

    // Fallback chain
    for (const name of this.fallbackOrder) {
      const plugin = this.plugins.get(name);
      if (plugin
        && plugin.supportedModes.includes(mode)
        && amount <= plugin.maxTransactionAmount
        && await plugin.isAvailable()) {
        return plugin;
      }
    }

    throw new NoPaymentGatewayAvailableException(mode, amount);
  }

  // Route webhook to correct plugin for signature verification
  getByName(name: string): IPaymentGatewayPlugin {
    const plugin = this.plugins.get(name);
    if (!plugin) throw new PluginNotFoundException(name);
    return plugin;
  }
}

// Concrete plugin — Razorpay
@Injectable()
export class RazorpayPlugin implements IPaymentGatewayPlugin {
  readonly name = 'RAZORPAY';
  readonly supportedModes: PaymentMode[] = ['NEFT', 'IMPS', 'UPI'];
  readonly maxTransactionAmount = 50_000_000_00; // ₹5Cr in paise

  async isAvailable(): Promise<boolean> {
    try {
      await this.razorpayClient.accounts.fetch(process.env.RAZORPAY_ACCOUNT_ID!);
      return true;
    } catch { return false; }
  }

  async initiatePayout(request: PayoutRequest): Promise<PayoutResult> {
    const response = await this.razorpayClient.payouts.create({
      account_number: process.env.RAZORPAY_SOURCE_ACCOUNT,
      amount: request.amount,
      currency: 'INR',
      mode: request.mode.toLowerCase(),
      purpose: 'payout',
      fund_account: {
        account_type: 'bank_account',
        bank_account: {
          name: request.beneficiaryName,
          ifsc: request.ifsc,
          account_number: request.accountNumber,
        },
      },
      reference_id: request.referenceId,
    });
    return {
      gatewayPayoutId: response.id,
      status: 'INITIATED',
      gatewayName: this.name,
    };
  }

  async checkPayoutStatus(gatewayPayoutId: string): Promise<PayoutStatus> {
    const payout = await this.razorpayClient.payouts.fetch(gatewayPayoutId);
    return this.mapStatus(payout.status);
  }

  parseWebhook(payload: unknown, signature: string): DomainPaymentEvent {
    this.verifySignature(payload, signature, process.env.RAZORPAY_WEBHOOK_SECRET!);
    const event = payload as RazorpayWebhookPayload;
    return {
      gatewayName: this.name,
      referenceId: event.payload.payout.entity.reference_id,
      status: event.event === 'payout.processed' ? 'SUCCESS' : 'FAILED',
      processedAt: new Date(event.payload.payout.entity.processed_at * 1000),
    };
  }
}

// Disbursement service — plugin-unaware
@Injectable()
export class DisbursementService {
  constructor(private readonly gatewayRegistry: PaymentGatewayRegistry) {}

  async disburse(loan: SanctionedLoan, bankDetails: BankDetails): Promise<DisbursementResult> {
    const mode = this.selectPaymentMode(loan.disbursedAmount);
    const gateway = await this.gatewayRegistry.getAvailableForAmount(loan.disbursedAmount, mode);

    const result = await gateway.initiatePayout({
      amount: loan.disbursedAmount,
      mode,
      beneficiaryName: bankDetails.accountHolderName,
      ifsc: bankDetails.ifsc,
      accountNumber: bankDetails.accountNumber,
      referenceId: `DISB-${loan.id}`,
    });

    return { loanId: loan.id, gatewayName: gateway.name, gatewayPayoutId: result.gatewayPayoutId };
  }
}
```

**Q10. How would you use the Plugin Pattern for a configurable loan fee calculator?**
A: Each fee type (processing fee, prepayment penalty, late fee, CGTMSE fee) is a plugin; the fee engine discovers and applies all applicable ones:

```typescript
interface IFeePlugin {
  readonly feeType: FeeType;
  readonly name: string;
  isApplicable(loan: Loan, event: FeeCalculationEvent): boolean;
  calculate(loan: Loan, event: FeeCalculationEvent): FeeCalculationResult;
}

enum FeeType {
  PROCESSING = 'PROCESSING',
  PREPAYMENT = 'PREPAYMENT',
  LATE_PAYMENT = 'LATE_PAYMENT',
  CGTMSE = 'CGTMSE',
  FORECLOSURE = 'FORECLOSURE',
}

interface FeeCalculationEvent {
  type: FeeType;
  triggerDate: Date;
  relatedAmount?: number;   // for prepayment — amount being prepaid
  daysPastDue?: number;     // for late payment
}

interface FeeCalculationResult {
  feeType: FeeType;
  feeAmount: number;        // in paise
  gstAmount: number;        // in paise
  totalAmount: number;
  description: string;
  waiverEligible: boolean;
}

@Injectable()
export class FeePluginRegistry {
  private readonly plugins: IFeePlugin[] = [];

  register(plugin: IFeePlugin): void {
    this.plugins.push(plugin);
  }

  calculateAllFees(loan: Loan, event: FeeCalculationEvent): FeeCalculationResult[] {
    return this.plugins
      .filter(p => p.isApplicable(loan, event))
      .map(p => p.calculate(loan, event));
  }
}

// Processing fee plugin — product-specific rules
@Injectable()
export class ProcessingFeePlugin implements IFeePlugin {
  readonly feeType = FeeType.PROCESSING;
  readonly name = 'PROCESSING_FEE';

  isApplicable(loan: Loan, event: FeeCalculationEvent): boolean {
    return event.type === FeeType.PROCESSING;
  }

  calculate(loan: Loan, _event: FeeCalculationEvent): FeeCalculationResult {
    let feeRate: number;
    let maxFee: number;

    if (loan.productCode.startsWith('HL')) {
      feeRate = loan.isAffordableHousing ? 0 : 0.005;   // waived for PMAY
      maxFee = 25_000_00;                                  // ₹25K cap
    } else if (loan.productCode.startsWith('PL')) {
      feeRate = 0.02;
      maxFee = Infinity;
    } else { // MSME
      feeRate = 0.01;
      maxFee = Infinity;
    }

    const feeAmount = Math.min(loan.sanctionedAmount * feeRate, maxFee);
    const gstAmount = feeAmount * 0.18;

    return {
      feeType: this.feeType,
      feeAmount,
      gstAmount,
      totalAmount: feeAmount + gstAmount,
      description: `Processing fee @ ${(feeRate * 100).toFixed(2)}% + 18% GST`,
      waiverEligible: loan.isAffordableHousing,
    };
  }
}

// Prepayment penalty plugin — RBI guidelines
@Injectable()
export class PrepaymentPenaltyPlugin implements IFeePlugin {
  readonly feeType = FeeType.PREPAYMENT;
  readonly name = 'PREPAYMENT_PENALTY';

  isApplicable(loan: Loan, event: FeeCalculationEvent): boolean {
    return event.type === FeeType.PREPAYMENT;
  }

  calculate(loan: Loan, event: FeeCalculationEvent): FeeCalculationResult {
    const prepayAmount = event.relatedAmount ?? 0;

    // RBI: Floating rate home loans — no prepayment penalty for individuals
    if (loan.productCode.startsWith('HL') && loan.rateType === 'FLOATING') {
      return this.zeroPenalty('RBI mandate: No prepayment penalty for floating rate home loans');
    }

    // Fixed rate / personal loans: 2% of prepayment amount
    const feeAmount = prepayAmount * 0.02;
    return {
      feeType: this.feeType,
      feeAmount,
      gstAmount: feeAmount * 0.18,
      totalAmount: feeAmount * 1.18,
      description: `Prepayment penalty @ 2% + 18% GST`,
      waiverEligible: false,
    };
  }

  private zeroPenalty(description: string): FeeCalculationResult {
    return { feeType: this.feeType, feeAmount: 0, gstAmount: 0, totalAmount: 0, description, waiverEligible: false };
  }
}

// CGTMSE fee plugin — only for MSME loans
@Injectable()
export class CgtmseFeePlugin implements IFeePlugin {
  readonly feeType = FeeType.CGTMSE;
  readonly name = 'CGTMSE_GUARANTEE_FEE';

  isApplicable(loan: Loan, event: FeeCalculationEvent): boolean {
    return event.type === FeeType.PROCESSING && loan.productCode.startsWith('MSME');
  }

  calculate(loan: Loan, _event: FeeCalculationEvent): FeeCalculationResult {
    const guaranteeFee = loan.sanctionedAmount * 0.015; // 1.5% annual CGTMSE fee
    return {
      feeType: this.feeType,
      feeAmount: guaranteeFee,
      gstAmount: 0,   // CGTMSE fee is GST-exempt
      totalAmount: guaranteeFee,
      description: 'CGTMSE Credit Guarantee Fee @ 1.5% p.a.',
      waiverEligible: false,
    };
  }
```

**Q11. How do you use the Plugin Pattern for compliance and regulatory rule engines?**
A: Compliance rules vary by RBI circular, product, and customer segment — each rule is a plugin checked in sequence:

```typescript
interface ICompliancePlugin {
  readonly name: string;
  readonly ruleCode: string;
  readonly applicableFrom: Date;       // RBI circulars have effective dates
  readonly applicableTo?: Date;        // some rules are time-limited
  readonly priority: number;

  isApplicable(context: ComplianceCheckContext): boolean;
  check(context: ComplianceCheckContext): ComplianceCheckResult;
}

interface ComplianceCheckContext {
  loan: LoanApplication;
  applicant: Applicant;
  bureauReport: BureauReport;
  checkDate: Date;
}

interface ComplianceCheckResult {
  passed: boolean;
  ruleCode: string;
  message: string;
  severity: 'BLOCK' | 'WARNING' | 'INFO';
}

@Injectable()
export class ComplianceRuleEngine {
  private readonly plugins: ICompliancePlugin[] = [];

  register(plugin: ICompliancePlugin): void {
    this.plugins.push(plugin);
    this.plugins.sort((a, b) => a.priority - b.priority);
  }

  checkCompliance(context: ComplianceCheckContext): ComplianceReport {
    const activePlugins = this.plugins.filter(p => {
      const now = context.checkDate;
      return now >= p.applicableFrom && (!p.applicableTo || now <= p.applicableTo);
    });

    const results = activePlugins
      .filter(p => p.isApplicable(context))
      .map(p => p.check(context));

    const blockers = results.filter(r => !r.passed && r.severity === 'BLOCK');
    const warnings = results.filter(r => !r.passed && r.severity === 'WARNING');

    return {
      compliant: blockers.length === 0,
      blockers,
      warnings,
      allChecks: results,
    };
  }
}

// RBI LTV circular — home loan LTV cap
@Injectable()
export class RbiLtvCapPlugin implements ICompliancePlugin {
  readonly name = 'RBI_LTV_CAP_HOME_LOAN';
  readonly ruleCode = 'RBI/2023-24/HLC-001';
  readonly applicableFrom = new Date('2023-04-01');
  readonly priority = 10;

  isApplicable(ctx: ComplianceCheckContext): boolean {
    return ctx.loan.productCode.startsWith('HL');
  }

  check(ctx: ComplianceCheckContext): ComplianceCheckResult {
    const ltv = ctx.loan.requestedAmount / ctx.loan.propertyValue;
    const maxLtv = ctx.loan.requestedAmount <= 3_000_000_00 ? 0.90 : 0.80;

    return {
      passed: ltv <= maxLtv,
      ruleCode: this.ruleCode,
      message: ltv > maxLtv
        ? `LTV ${(ltv * 100).toFixed(1)}% exceeds RBI limit of ${maxLtv * 100}% for this loan amount`
        : `LTV ${(ltv * 100).toFixed(1)}% within RBI limits`,
      severity: 'BLOCK',
    };
  }
}

// RBI cooling-off period — recently rejected applicants

export class CoolingOffPeriodPlugin implements ICompliancePlugin {

  readonly ruleCode = 'RBI/2024-25/COOLING-001';
```

**Q12. How do you use the Plugin Pattern for notification channel routing?**
A: Each notification channel (SMS, Email, WhatsApp, Push) is a plugin; the notification engine routes based on applicant preferences and message type:

```typescript
interface INotificationPlugin {
  readonly channel: NotificationChannel;
  readonly name: string;

  isAvailable(): Promise<boolean>;
  canSend(recipient: NotificationRecipient, template: string): boolean;
  send(recipient: NotificationRecipient, template: string, vars: Record<string, string>): Promise<NotificationResult>;
}

@Injectable()
export class NotificationPluginRegistry {
  private readonly plugins = new Map<NotificationChannel, INotificationPlugin>();

  register(plugin: INotificationPlugin): void {
    this.plugins.set(plugin.channel, plugin);
  }

  async sendWithFallback(
    recipient: NotificationRecipient,
    template: string,
    vars: Record<string, string>,
    preferredChannels: NotificationChannel[],
  ): Promise<NotificationResult> {
    for (const channel of preferredChannels) {
      const plugin = this.plugins.get(channel);
      if (!plugin) continue;
      if (!plugin.canSend(recipient, template)) continue;
      if (!await plugin.isAvailable()) continue;

      try {
        return await plugin.send(recipient, template, vars);
      } catch (err) {
        this.logger.warn(`Notification plugin '${plugin.name}' failed — trying fallback`, err);
      }
    }
    throw new AllNotificationChannelsFailedException(template, recipient.id);
  }
}
```

## Section 4: Plugin Lifecycle and Management

**Q13. How do you handle plugin versioning and backward compatibility?**
A: Plugin interfaces must be versioned when contracts change — existing plugins should not break:

```typescript
// Version the interface explicitly
interface IBureauPluginV1 {
  readonly apiVersion: '1.0';
  fetchCreditReport(pan: string): Promise<CreditReport>;
}

interface IBureauPluginV2 extends IBureauPluginV1 {
  readonly apiVersion: '2.0';
  fetchCreditReport(pan: string): Promise<CreditReport>;
  fetchCreditReportWithConsent(pan: string, consentToken: string): Promise<CreditReport>; // new in v2
}

// Registry supports both versions
@Injectable()
export class BureauPluginRegistry {
  private readonly plugins = new Map<string, IBureauPluginV1 | IBureauPluginV2>();

  isV2Plugin(plugin: IBureauPluginV1 | IBureauPluginV2): plugin is IBureauPluginV2 {
    return plugin.apiVersion === '2.0';
  }

  async fetchReport(name: string, pan: string, consentToken?: string): Promise<CreditReport> {
    const plugin = this.getByName(name);

    // Use v2 API if available and consent token is provided
    if (consentToken && this.isV2Plugin(plugin)) {
      return plugin.fetchCreditReportWithConsent(pan, consentToken);
    }

    return plugin.fetchCreditReport(pan);
  }
}
```

**Q14. How do you implement plugin health monitoring and automatic failover?**
A:

```typescript
@Injectable()
export class PluginHealthMonitor {
  private readonly healthStatus = new Map<string, PluginHealth>();

  constructor(
    @Inject(BUREAU_PLUGIN) private readonly plugins: IBureauPlugin[],
    private readonly alertService: AlertService,
  ) {}

  @Cron('0 */5 * * * *') // every 5 minutes
  async checkAllPlugins(): Promise<void> {
    await Promise.allSettled(
      this.plugins.map(async plugin => {
        const available = await plugin.isAvailable();
        const previous = this.healthStatus.get(plugin.name);

        this.healthStatus.set(plugin.name, {
          name: plugin.name,
          available,
          lastChecked: new Date(),
          consecutiveFailures: available ? 0 : (previous?.consecutiveFailures ?? 0) + 1,
        });

        // Alert on state change
        if (previous?.available && !available) {
          await this.alertService.sendCritical(`Plugin '${plugin.name}' became UNAVAILABLE`);
        } else if (!previous?.available && available) {
          await this.alertService.sendInfo(`Plugin '${plugin.name}' recovered`);
        }
      }),
    );
  }

  isHealthy(pluginName: string): boolean {
    return this.healthStatus.get(pluginName)?.available ?? false;
  }
}
```

## Section 6: Anti-patterns and Pitfalls

**Q16. What are the most common Plugin Pattern mistakes?**
A:

**Mistake 1 — Plugin that calls back into the core:**
```typescript
// ❌ Plugin has a reference to the core service — circular dependency
class CrmSyncPlugin implements ILoanLifecyclePlugin {
  constructor(private readonly loanService: LoanApplicationService) {} // ← wrong

  async onApplicationSubmitted(app: LoanApplication): Promise<void> {
    const fullApp = await this.loanService.findById(app.id); // plugin reaching into core
    await this.crmClient.create(fullApp);
  }
}

// ✅ Fix — pass enough data in the hook argument; plugin should not need core
async onApplicationSubmitted(app: LoanApplication): Promise<void> {
  // app already contains all needed data — no core call needed
  await this.crmClient.create({ id: app.id, pan: app.pan, amount: app.requestedAmount });
}
```

**Mistake 2 — Core that depends on specific plugin implementations:**
```typescript
// ❌ Core imports specific plugin — defeats the purpose
import { CibilBureauPlugin } from './cibil-bureau.plugin'; // ← core tied to specific plugin

@Injectable()
export class UnderwritingService {
  constructor(private readonly cibil: CibilBureauPlugin) {} // ← not using the registry
}

// ✅ Fix — always use registry; core never imports concrete plugins
@Injectable()
export class UnderwritingService {
  constructor(private readonly bureauRegistry: BureauPluginRegistry) {} // ← uses registry
}
```

**Mistake 3 — Plugin failures that crash the core flow:**
```typescript
// ❌ Plugin failure propagates and breaks the primary operation
async executeHook(hookName: string, ...args: any[]): Promise<void> {
  for (const plugin of this.plugins) {
    await plugin[hookName]?.(...args); // if one plugin throws, everything after is skipped
  }
}

// ✅ Fix — isolate plugin failures; log but continue
async executeHook(hookName: string, ...args: any[]): Promise<void> {
  for (const plugin of this.plugins) {
    try {
      await plugin[hookName]?.(...args);
    } catch (err) {
      this.logger.error(`Plugin '${plugin.name}' hook '${hookName}' failed — continuing`, err);
      // Core operation is not affected
    }
  }
}
```

**Mistake 4 — Plugin interface that's too broad (leaks core internals):**
```typescript
// ❌ Plugin interface exposes ORM entities and HTTP request objects
interface ILoanPlugin {
  onCreated(prismaLoanRecord: PrismaLoan, httpRequest: Request): Promise<void>; // ← wrong
}

// ✅ Fix — plugin interface uses domain objects only
interface ILoanPlugin {
  onCreated(loan: LoanApplication): Promise<void>; // ← clean domain object
}
```

**Mistake 5 — No plugin isolation — plugin state leaks between calls:**
```typescript
// ❌ Plugin accumulates state across invocations — not safe for singleton scope
class StatefulPlugin implements ILoanLifecyclePlugin {
  private readonly processedIds: string[] = []; // mutable state — grows forever

  async onApplicationSubmitted(app: LoanApplication): Promise<void> {
    this.processedIds.push(app.id); // memory leak in singleton
  }
}

// ✅ Fix — plugins should be stateless; use external store for state
class StatelessPlugin implements ILoanLifecyclePlugin {
  async onApplicationSubmitted(app: LoanApplication): Promise<void> {
    await this.redis.sadd('processed:applications', app.id); // state in Redis
  }
}
```

**Q17. "Design a multi-tenant lending platform where different enterprise clients (NBFCs) need different bureau providers, different KYC rules, and different fee structures. How do you use the Plugin Pattern?"**
A: Tenant-aware plugin resolution — each tenant has a configured set of plugins:

```typescript
// Tenant plugin configuration — stored in DB / config service
interface TenantPluginConfig {
  tenantId: string;
  bureauPlugins: string[];       // ['CIBIL', 'EXPERIAN'] — priority ordered
  kycPlugins: string[];          // ['AADHAAR_OTP', 'VIDEO_KYC']
  feePlugins: string[];          // ['PROCESSING_FEE', 'CGTMSE_FEE']
  compliancePlugins: string[];   // ['RBI_LTV_CAP', 'TENANT_CUSTOM_LTV']
}

@Injectable()
export class TenantPluginResolver {
  constructor(
    private readonly bureauRegistry: BureauPluginRegistry,
    private readonly feeRegistry: FeePluginRegistry,
    private readonly tenantConfigService: TenantConfigService,
  ) {}

  async resolveBureauPlugins(tenantId: string): Promise<IBureauPlugin[]> {
    const config = await this.tenantConfigService.getPluginConfig(tenantId);
    return config.bureauPlugins.map(name => this.bureauRegistry.getByName(name));
  }

  async resolveFeePlugins(tenantId: string): Promise<IFeePlugin[]> {
    const config = await this.tenantConfigService.getPluginConfig(tenantId);
    return config.feePlugins.map(name => this.feeRegistry.getByName(name));
  }
}

// Tenant-specific custom plugin — registered alongside the standard ones
```

**Q18. "A new regulatory requirement mandates that all lenders must run a CERSAI check before sanctioning home loans. The check must be added across all product flows without modifying existing service code. How do you implement this using the Plugin Pattern?"**
A: Add a new compliance plugin — no existing code changes:

```typescript
// New plugin — implements the existing ICompliancePlugin interface
@Injectable()
export class CersaiEncumbrancePlugin implements ICompliancePlugin {
  readonly name = 'CERSAI_ENCUMBRANCE_CHECK';
  readonly ruleCode = 'RBI/2024-25/CERSAI-001';
  readonly applicableFrom = new Date('2025-01-01'); // effective date per circular
  readonly priority = 8;

  constructor(private readonly cersaiService: CersaiService) {}

  isApplicable(ctx: ComplianceCheckContext): boolean {
    // Only home loans with a property
    return ctx.loan.productCode.startsWith('HL') && !!ctx.loan.propertyId;
  }

  async check(ctx: ComplianceCheckContext): Promise<ComplianceCheckResult> {
    const encumbranceResult = await this.cersaiService.checkEncumbrance(ctx.loan.propertyId!);
    return {
      passed: !encumbranceResult.hasEncumbrance,
      ruleCode: this.ruleCode,
      message: encumbranceResult.hasEncumbrance
        ? `Property encumbered on CERSAI: ${encumbranceResult.encumbranceSummary}`
        : 'No encumbrance found on CERSAI',
      severity: 'BLOCK',
    };
  }
}

// Module — register the new plugin; nothing else changes
@Module({
  providers: [
    // Existing plugins...
    CersaiEncumbrancePlugin,
    { provide: COMPLIANCE_PLUGIN, useClass: CersaiEncumbrancePlugin, multi: true },
  ],
})
export class ComplianceModule {}
```

The compliance rule engine picks it up automatically via the `multi` provider. All product flows that call `complianceEngine.checkCompliance(context)` now include the CERSAI check — without touching `LoanSanctionService`, `HomeLoanService`, or any existing compliance plugin. The regulatory mandate is implemented in one new class.

## Quick Reference: Plugin Pattern Checklist

| Signal                                                                         | Decision                                                                   |
|--------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| Adding a new integration (bureau, payment gateway, SMS vendor) requires touching core code | Extract to Plugin — core calls registry; new integration is a new plugin |
| Different tenants/environments need different implementations of the same capability | Plugin registry with tenant-aware resolution                              |
| A new regulatory rule must be applied across all flows without modifying services | Compliance plugin — register it; engine discovers and applies it          |
| Plugin has a reference to a core service                                       | Circular dependency smell — plugin should receive enough data in its args  |
| Core service imports a specific plugin class                                   | Remove — core should only import the registry                             |
| Plugin failure crashes the primary operation                                   | Wrap all plugin invocations in try/catch; plugins are best-effort         |
| Plugin interface includes ORM entities or HTTP objects                         | Redesign — interface must use domain objects only                         |
| Feature can be toggled on/off per tenant or environment                        | Plugin with `isApplicable()` gated by feature flag or config              |
| Simple Strategy (one algorithm, one caller) suffices                           | Skip Plugin infrastructure — Strategy is simpler                          |

---

**Tip for the interview:** At the 5 YOE level, Plugin Pattern questions surface as system design problems: "how do you add a new payment gateway without touching the disbursement service," "how do you add a new RBI compliance rule across all loan flows," or "design a multi-tenant platform where each NBFC has different bureau and KYC rules." The answer that lands at the senior level doesn't just name the pattern — it demonstrates the three-part mechanics: **interface** (what every plugin must implement), **registry** (the lookup and selection mechanism), and **extension points** (where the core invokes registered plugins). The senior differentiator is knowing the failure isolation rule (plugin failures must never crash the core), the anti-pattern of plugins reaching back into the core, and the practical NestJS implementation using `multi` providers for self-registration at startup. In a fintech domain, the bureau/gateway/compliance/KYC scenarios are the most compelling — have one concrete story ready about adding a new integration as a plugin with zero changes to the consuming service, because that specificity is what separates a pattern description from production experience.
