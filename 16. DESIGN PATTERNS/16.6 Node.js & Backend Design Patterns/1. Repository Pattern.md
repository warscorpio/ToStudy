# Node.js & Backend Design Patterns: Repository Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Repository pattern?**
A: The Repository pattern is a data access abstraction that mediates between the domain layer and the data mapping layer. It presents the domain with a collection-like interface for accessing domain objects — the domain asks the repository for objects by identity or criteria, and receives fully constructed domain objects back, with no knowledge of how those objects are stored, fetched, or mapped. Martin Fowler defines it as "a mechanism for encapsulating storage, retrieval, and search behavior which emulates a collection of objects." The key word is *collection* — from the domain's perspective, a repository behaves like an in-memory set of domain objects, not like a database query interface. The domain says "give me all active loans for customer X"; it does not say "run this SQL query on the loans table."

**Q2. What problem does the Repository pattern solve, and what breaks without it?**
A: It solves the *data access coupling* problem — when business logic knows how and where data is stored, the codebase becomes rigid in several concrete ways:

- **Untestable business logic** — a service that instantiates `TypeOrmRepository` directly cannot be tested without a live database. Every unit test becomes an integration test.
- **Database vendor lock-in at the business layer** — SQL dialects, ORM-specific query builders, and schema details leak into services and use cases. Switching from PostgreSQL to MongoDB, or from TypeORM to Prisma, requires editing business logic files.
- **Query duplication** — the same filter criteria (active loans, overdue accounts, KYC-pending customers) are written multiple times across controllers, services, and cron jobs — each with subtle variations that diverge over time.
- **No single place to enforce access patterns** — pagination defaults, soft-delete filters, tenant scoping, and read-replica routing are applied inconsistently because each caller implements them independently.
- **Impossible to swap data sources** — replacing a database query with a cache hit, or a live API call with a test double, requires modifying every caller.

Without Repository, the data access layer and the business layer are one entangled mass. With Repository, the business layer is a client of a well-defined interface and the data access layer is an interchangeable implementation.

**Q3. What are the core responsibilities of a Repository?**
A: Three clear responsibilities:

1. **Object retrieval** — find domain objects by identity (`findById`), by criteria (`findByStatus`, `findActiveByCustomer`), or in bulk (`findAll`, `findByIds`). Return fully constructed domain objects, not raw rows or ORM entities.

2. **Object persistence** — accept domain objects and persist them (`save`, `insert`, `update`, `delete`). The repository translates domain objects into the storage format (SQL rows, MongoDB documents, Redis hashes) and back. The caller never sees a connection, a statement, or a cursor.

3. **Query encapsulation** — own all query logic for a given aggregate. No query for the `Loan` aggregate should exist outside `ILoanRepository` and its implementation. Complex queries (multi-table joins, aggregations, full-text search) are named methods that describe *intent*, not mechanics.

What the Repository is *not* responsible for:
- Business rules (those belong in the domain entity or domain service).
- Transaction management (the caller, typically a use case, owns the transaction boundary).
- Response serialisation (the repository returns domain objects; the controller maps them to DTOs).

**Q4. What is the difference between a Repository and a DAO (Data Access Object)?**
A: Both abstract data access, but at different levels and with different contracts:

| Dimension              | DAO                                                             | Repository                                                          |
|------------------------|-----------------------------------------------------------------|---------------------------------------------------------------------|
| Abstraction level      | Close to the database — methods often mirror table operations   | Close to the domain — methods mirror domain collection semantics    |
| Return type            | Raw rows, DTOs, or ORM entities                                 | Fully constructed domain objects                                    |
| Query language         | SQL / ORM queries are often visible in method names             | Method names describe domain intent, hide query details             |
| Aggregate awareness    | None — usually one DAO per table                                | One Repository per aggregate root — spans tables if needed          |
| Domain coupling        | Low — DAO doesn't know about domain invariants                  | High — Repository reconstructs domain objects faithfully            |
| Typical use            | Simple CRUD applications, legacy codebases                      | Domain-driven design, Onion/Clean Architecture                      |

Example contrast:
```typescript
// DAO — thin database wrapper, table-oriented
class LoanDao {
  async getById(id: string): Promise<LoanRow> { /* SELECT * FROM loans WHERE id = $1 */ }
  async updateStatus(id: string, status: string): Promise<void> { /* UPDATE loans ... */ }
}

// Repository — domain-oriented, returns rich objects
class LoanRepository {
  async findById(loanId: LoanId): Promise<Loan | null> { /* returns Loan aggregate */ }
  async findOverdueLoans(asOf: Date): Promise<Loan[]> { /* domain concept, hides SQL */ }
  async save(loan: Loan): Promise<void> { /* persists the full aggregate */ }
}
```

**Q5. What is a Generic Repository, and why is it controversial?**
A: A Generic Repository is a base class or interface parameterised by the entity type, exposing CRUD methods for any type:

```typescript
interface IRepository<T, ID> {
  findById(id: ID): Promise<T | null>;
  findAll(): Promise<T[]>;
  save(entity: T): Promise<void>;
  delete(id: ID): Promise<void>;
}
```

**Arguments for it:** eliminates boilerplate for simple entities; a concrete base class (`TypeOrmBaseRepository<T>`) implements common methods once; new repositories inherit for free.

**Arguments against it (the stronger side at 5 YOE):**
- It leaks infrastructure contracts into the domain — `findAll()` and `delete()` are rarely meaningful for a domain aggregate; they're CRUD verbs, not domain verbs.
- It encourages lazy query design — callers use `findAll()` and filter in memory instead of adding a named, indexed query.
- It makes it impossible to vary the interface per aggregate — a `LoanRepository` might need `findOverdueLoans(asOf: Date)` while an `AuditLogRepository` might need `findByDateRange(from, to, type)`. A generic base cannot express these without extension.
- Generic base classes expose `delete()` on aggregates that should never be hard-deleted (soft-delete only), creating a footgun.

The practical consensus: use a generic base class *internally* in the infrastructure implementation to share boilerplate (`TypeOrmBaseRepository` that provides `findById` and `save` via TypeORM), but expose a *specific* domain interface (`ILoanRepository`) at the boundary. The domain depends on the specific interface; the infrastructure class inherits from the generic base. Both worlds: no boilerplate duplication, no leaking of CRUD verbs.

## Section 2: Structure & Implementation

**Q6. Walk through a complete TypeScript Repository implementation for a loan aggregate in a NestJS backend.**
A:

```typescript
// ─── Domain interface — defined in the domain layer ───────────────────────────

// src/domain/repositories/loan-repository.interface.ts

export interface ILoanRepository {
  // Identity-based retrieval
  findById(loanId: LoanId): Promise<Loan | null>;
  findByIds(loanIds: LoanId[]): Promise<Loan[]>;

  // Domain-concept queries
  findActiveByCustomer(customerId: CustomerId): Promise<Loan[]>;
  findOverdue(asOf: Date, limit?: number): Promise<Loan[]>;
  findDueForEmiCollection(date: Date): Promise<Loan[]>;
  findByStatus(status: LoanStatus, pagination: Pagination): Promise<PagedResult<Loan>>;

  // Existence checks
  existsActiveForCustomer(customerId: CustomerId): Promise<boolean>;

  // Persistence
  save(loan: Loan): Promise<void>;
  saveAll(loans: Loan[]): Promise<void>;

  // Soft delete — hard delete deliberately omitted for financial records
  archive(loanId: LoanId, reason: string): Promise<void>;
}

export const LOAN_REPOSITORY = Symbol("ILoanRepository");

// src/infrastructure/persistence/typeorm/mappers/loan.orm-mapper.ts
import { Injectable }  from "@nestjs/common";
import { Loan }         from "../../../../domain/entities/loan.entity";
import { LoanOrmEntity } from "../entities/loan.orm-entity";
import { LoanId }       from "../../../../domain/value-objects/loan-id.value-object";
import { CustomerId }   from "../../../../domain/value-objects/customer-id.value-object";
import { Money }        from "../../../../domain/value-objects/money.value-object";
import { InterestRate } from "../../../../domain/value-objects/interest-rate.value-object";

@Injectable()
export class LoanOrmMapper {
  toDomain(orm: LoanOrmEntity): Loan {
    return Loan.reconstitute({
      id:                   LoanId.of(orm.id),
      customerId:           CustomerId.of(orm.customerId),
      status:               orm.status as LoanStatus,
      principal:            Money.ofPaise(Number(orm.principalInPaise), orm.currency as Currency),
      interestRate:         InterestRate.ofAnnual(Number(orm.annualInterestRate)),
      tenureMonths:         orm.tenureMonths,
      emisPaid:             orm.emisPaid,
      outstandingPrincipal: Money.ofPaise(Number(orm.outstandingPrincipalInPaise), orm.currency as Currency),
      nextEmiDueAt:         orm.nextEmiDueAt,
      createdAt:            orm.createdAt,
      updatedAt:            orm.updatedAt,
    });
  }

  toOrm(domain: Loan): LoanOrmEntity {
    const orm                           = new LoanOrmEntity();
    orm.id                              = domain.id.value;
    orm.customerId                      = domain.customerId.value;
    orm.status                          = domain.status;
    orm.principalInPaise                = domain.principal.amountInPaise;
    orm.currency                        = domain.principal.currency;
    orm.annualInterestRate              = domain.interestRate.annual;
    orm.tenureMonths                    = domain.tenureMonths;
    orm.emisPaid                        = domain.emisPaid;
    orm.outstandingPrincipalInPaise     = domain.outstandingPrincipal.amountInPaise;
    orm.nextEmiDueAt                    = domain.nextEmiDueAt;
    return orm;
  }
}

// ─── Concrete Repository implementation ──────────────────────────────────────

// src/infrastructure/persistence/typeorm/repositories/typeorm-loan.repository.ts
import { Injectable }         from "@nestjs/common";
import { InjectRepository }   from "@nestjs/typeorm";
import { Repository, In, LessThanOrEqual, IsNull } from "typeorm";
import { ILoanRepository }    from "../../../../domain/repositories/loan-repository.interface";
import { Loan }               from "../../../../domain/entities/loan.entity";
import { LoanId }             from "../../../../domain/value-objects/loan-id.value-object";
import { CustomerId }         from "../../../../domain/value-objects/customer-id.value-object";
import { LoanOrmEntity }      from "../entities/loan.orm-entity";
import { LoanOrmMapper }      from "../mappers/loan.orm-mapper";

@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  constructor(
    @InjectRepository(LoanOrmEntity)
    private readonly ormRepo: Repository<LoanOrmEntity>,
    private readonly mapper:  LoanOrmMapper,
  ) {}

  async findById(loanId: LoanId): Promise<Loan | null> {
    const orm = await this.ormRepo.findOne({
      where: { id: loanId.value, archivedAt: IsNull() },
    });
    return orm ? this.mapper.toDomain(orm) : null;
  }

  async findByIds(loanIds: LoanId[]): Promise<Loan[]> {
    if (loanIds.length === 0) return [];
    const orms = await this.ormRepo.find({
      where: { id: In(loanIds.map(id => id.value)), archivedAt: IsNull() },
    });
    return orms.map(o => this.mapper.toDomain(o));
  }

  async findActiveByCustomer(customerId: CustomerId): Promise<Loan[]> {
    const orms = await this.ormRepo.find({
      where: {
        customerId: customerId.value,
        status:     "ACTIVE",
        archivedAt: IsNull(),
      },
      order: { createdAt: "DESC" },
    });
    return orms.map(o => this.mapper.toDomain(o));
  }

  async findOverdue(asOf: Date, limit = 1000): Promise<Loan[]> {
    // A loan is overdue if it's ACTIVE and nextEmiDueAt is in the past
    const orms = await this.ormRepo.find({
      where: {
        status:      "ACTIVE",
        nextEmiDueAt: LessThanOrEqual(asOf),
        archivedAt:  IsNull(),
      },
      order: { nextEmiDueAt: "ASC" },
      take:  limit,
    });
    return orms.map(o => this.mapper.toDomain(o));
  }

  async findDueForEmiCollection(date: Date): Promise<Loan[]> {
    // Custom query: loans whose next EMI is due on the given calendar date
    const startOfDay = new Date(date); startOfDay.setHours(0, 0, 0, 0);
    const endOfDay   = new Date(date); endOfDay.setHours(23, 59, 59, 999);

    const orms = await this.ormRepo
      .createQueryBuilder("loan")
      .where("loan.status = :status", { status: "ACTIVE" })
      .andWhere("loan.nextEmiDueAt BETWEEN :start AND :end", { start: startOfDay, end: endOfDay })
      .andWhere("loan.archivedAt IS NULL")
      .orderBy("loan.nextEmiDueAt", "ASC")
      .getMany();

    return orms.map(o => this.mapper.toDomain(o));
  }

  async findByStatus(status: LoanStatus, pagination: Pagination): Promise<PagedResult<Loan>> {
    const [orms, total] = await this.ormRepo.findAndCount({
      where:  { status, archivedAt: IsNull() },
      order:  { createdAt: "DESC" },
      skip:   (pagination.page - 1) * pagination.pageSize,
      take:   pagination.pageSize,
    });

    return {
      items:      orms.map(o => this.mapper.toDomain(o)),
      total,
      page:       pagination.page,
      pageSize:   pagination.pageSize,
      totalPages: Math.ceil(total / pagination.pageSize),
    };
  }

  async existsActiveForCustomer(customerId: CustomerId): Promise<boolean> {
    const count = await this.ormRepo.count({
      where: { customerId: customerId.value, status: "ACTIVE", archivedAt: IsNull() },
    });
    return count > 0;
  }

  async save(loan: Loan): Promise<void> {
    const orm = this.mapper.toOrm(loan);
    await this.ormRepo.save(orm);   // upsert — TypeORM handles insert vs update
  }

  async saveAll(loans: Loan[]): Promise<void> {
    if (loans.length === 0) return;
    const orms = loans.map(l => this.mapper.toOrm(l));
    await this.ormRepo.save(orms);
  }

  async archive(loanId: LoanId, reason: string): Promise<void> {
    await this.ormRepo.update(
      { id: loanId.value },
      { archivedAt: new Date(), archiveReason: reason },
    );
  }
}
```

**Q7. How do you implement an in-memory repository for unit testing?**
A: The in-memory repository implements the same domain interface but stores objects in a `Map`. It is the primary testing tool — no database, no migrations, no test containers:

```typescript
// src/test/doubles/in-memory-loan.repository.ts

import { ILoanRepository }  from "../../domain/repositories/loan-repository.interface";
import { Loan }              from "../../domain/entities/loan.entity";
import { LoanId }            from "../../domain/value-objects/loan-id.value-object";
import { CustomerId }        from "../../domain/value-objects/customer-id.value-object";

export class InMemoryLoanRepository implements ILoanRepository {
  // Deep-clone on store/retrieve — prevents tests from sharing mutable state
  private store = new Map<string, Loan>();

  async findById(loanId: LoanId): Promise<Loan | null> {
    return this.store.get(loanId.value) ?? null;
  }

  async findByIds(loanIds: LoanId[]): Promise<Loan[]> {
    return loanIds
      .map(id => this.store.get(id.value))
      .filter((l): l is Loan => l !== undefined);
  }

  async findActiveByCustomer(customerId: CustomerId): Promise<Loan[]> {
    return [...this.store.values()].filter(
      l => l.customerId.equals(customerId) && l.status === "ACTIVE"
    );
  }

  async findOverdue(asOf: Date, limit = 1000): Promise<Loan[]> {
    return [...this.store.values()]
      .filter(l => l.status === "ACTIVE" && l.isOverdue(asOf))
      .slice(0, limit);
  }

  async findDueForEmiCollection(date: Date): Promise<Loan[]> {
    const start = new Date(date); start.setHours(0, 0, 0, 0);
    const end   = new Date(date); end.setHours(23, 59, 59, 999);
    return [...this.store.values()].filter(l =>
      l.status === "ACTIVE" &&
      l.nextEmiDueAt !== null &&
      l.nextEmiDueAt >= start &&
      l.nextEmiDueAt <= end
    );
  }

  async findByStatus(status: LoanStatus, pagination: Pagination): Promise<PagedResult<Loan>> {
    const all    = [...this.store.values()].filter(l => l.status === status);
    const start  = (pagination.page - 1) * pagination.pageSize;
    const items  = all.slice(start, start + pagination.pageSize);
    return {
      items, total: all.length,
      page: pagination.page, pageSize: pagination.pageSize,
      totalPages: Math.ceil(all.length / pagination.pageSize),
    };
  }

  async existsActiveForCustomer(customerId: CustomerId): Promise<boolean> {
    return [...this.store.values()].some(
      l => l.customerId.equals(customerId) && l.status === "ACTIVE"
    );
  }

  async save(loan: Loan): Promise<void> {
    this.store.set(loan.id.value, loan);
  }

  async saveAll(loans: Loan[]): Promise<void> {
    loans.forEach(l => this.store.set(l.id.value, l));
  }

  async archive(loanId: LoanId, _reason: string): Promise<void> {
    this.store.delete(loanId.value);
  }

  // ── Test helpers — not on the interface ───────────────────────────────────

  seed(loan: Loan): void { this.store.set(loan.id.value, loan); }
  seedAll(loans: Loan[]): void { loans.forEach(l => this.seed(l)); }
  clear(): void { this.store.clear(); }
  size(): number { return this.store.size; }
  getAll(): Loan[] { return [...this.store.values()]; }
  getById(id: string): Loan | undefined { return this.store.get(id); }
}
```

**Q8. How does the Repository pattern handle transactions — who owns the transaction boundary?**
A: The Repository does *not* own transactions. Transactions are a unit-of-work concern that belongs to the application layer (use case). A use case that must persist multiple aggregates atomically manages the transaction; repositories participate in it:

```typescript
// ─── Unit of Work pattern — wraps transaction management ──────────────────────

// src/application/ports/unit-of-work.port.ts
export interface IUnitOfWork {
  begin(): Promise<void>;
  commit(): Promise<void>;
  rollback(): Promise<void>;
  getLoanRepository(): ILoanRepository;
  getEmiRepository(): IEmiRepository;
}

// ─── TypeORM implementation ───────────────────────────────────────────────────

// src/infrastructure/persistence/typeorm/typeorm-unit-of-work.ts
@Injectable()
export class TypeOrmUnitOfWork implements IUnitOfWork {
  private manager: EntityManager | null = null;

  constructor(private readonly dataSource: DataSource) {}

  async begin(): Promise<void> {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();
    this.manager = queryRunner.manager;
  }

  async commit(): Promise<void> {
    await this.manager!.queryRunner!.commitTransaction();
    await this.manager!.queryRunner!.release();
    this.manager = null;
  }

  async rollback(): Promise<void> {
    await this.manager!.queryRunner!.rollbackTransaction();
    await this.manager!.queryRunner!.release();
    this.manager = null;
  }

  getLoanRepository(): ILoanRepository {
    return new TypeOrmLoanRepository(
      this.manager!.getRepository(LoanOrmEntity),
      new LoanOrmMapper(),
    );
  }

  getEmiRepository(): IEmiRepository {
    return new TypeOrmEmiRepository(
      this.manager!.getRepository(EmiOrmEntity),
      new EmiOrmMapper(),
    );
  }
}

// ─── Use case owns the transaction boundary ───────────────────────────────────

class DisburseLoanUseCase {
  constructor(private readonly uow: IUnitOfWork) {}

  async execute(command: DisburseLoanCommand): Promise<void> {
    await this.uow.begin();
    try {
      const loanRepo = this.uow.getLoanRepository();
      const emiRepo  = this.uow.getEmiRepository();

      const loan = await loanRepo.findById(LoanId.of(command.loanId));
      if (!loan) throw new NotFoundException(command.loanId);

      loan.disburse();  // domain method

      // Generate EMI schedule
      const emiSchedule = EmiSchedule.generate(loan);

      await loanRepo.save(loan);
      await emiRepo.saveSchedule(emiSchedule);   // atomic with loan save

      await this.uow.commit();
    } catch (err) {
      await this.uow.rollback();
      throw err;
    }
  }
}
```

Alternatively, in NestJS with TypeORM's `@Transaction()` decorator or `dataSource.transaction()` callback, the transaction can be passed as a context. The principle is the same: the repository accepts and operates within the transaction context; it does not create or own it.

**Q9. How do you add a caching layer to a Repository without modifying the domain interface or the concrete implementation?**
A: Use the Decorator pattern — wrap the concrete repository in a caching decorator that implements the same interface:

```typescript
// src/infrastructure/persistence/decorators/cached-loan.repository.ts

import { ILoanRepository } from "../../../domain/repositories/loan-repository.interface";
import { Loan }             from "../../../domain/entities/loan.entity";
import { LoanId }           from "../../../domain/value-objects/loan-id.value-object";

export class CachedLoanRepository implements ILoanRepository {
  private readonly TTL_SECONDS = 60;

  constructor(
    private readonly inner: ILoanRepository,   // the real TypeORM repository
    private readonly redis: RedisClient,
  ) {}

  async findById(loanId: LoanId): Promise<Loan | null> {
    const cacheKey = `loan:${loanId.value}`;

    // 1. Cache read
    const cached = await this.redis.get(cacheKey);
    if (cached) {
      return this.deserializeLoan(cached);
    }

    // 2. Cache miss — fetch from DB
    const loan = await this.inner.findById(loanId);

    // 3. Populate cache (only if found)
    if (loan) {
      await this.redis.setex(cacheKey, this.TTL_SECONDS, this.serializeLoan(loan));
    }

    return loan;
  }

  async save(loan: Loan): Promise<void> {
    await this.inner.save(loan);
    // Invalidate cache on write — stale-while-revalidate strategy
    await this.redis.del(`loan:${loan.id.value}`);
  }

  async archive(loanId: LoanId, reason: string): Promise<void> {
    await this.inner.archive(loanId, reason);
    await this.redis.del(`loan:${loanId.value}`);
  }

  // Non-cacheable queries — delegate directly (list queries are hard to cache correctly)
  async findActiveByCustomer(customerId: CustomerId): Promise<Loan[]> {
    return this.inner.findActiveByCustomer(customerId);
  }

  async findOverdue(asOf: Date, limit?: number): Promise<Loan[]> {
    return this.inner.findOverdue(asOf, limit);
  }

  async findDueForEmiCollection(date: Date): Promise<Loan[]> {
    return this.inner.findDueForEmiCollection(date);
  }

  async findByStatus(status: LoanStatus, pagination: Pagination): Promise<PagedResult<Loan>> {
    return this.inner.findByStatus(status, pagination);
  }

  async findByIds(ids: LoanId[]): Promise<Loan[]> {
    return this.inner.findByIds(ids);
  }

  async existsActiveForCustomer(customerId: CustomerId): Promise<boolean> {
    return this.inner.existsActiveForCustomer(customerId);
  }

  async saveAll(loans: Loan[]): Promise<void> {
    await this.inner.saveAll(loans);
    await Promise.all(loans.map(l => this.redis.del(`loan:${l.id.value}`)));
  }

  // ── Serialization ─────────────────────────────────────────────────────────

  private serializeLoan(loan: Loan): string {
    // Serialize to a stable JSON format — same as the ORM entity fields
    return JSON.stringify({
      id: loan.id.value,
      customerId: loan.customerId.value,
      status: loan.status,
      principalInPaise: loan.principal.amountInPaise,
      currency: loan.principal.currency,
      annualInterestRate: loan.interestRate.annual,
      tenureMonths: loan.tenureMonths,
      emisPaid: loan.emisPaid,
      outstandingPrincipalInPaise: loan.outstandingPrincipal.amountInPaise,
    });
  }

  private deserializeLoan(json: string): Loan {
    const data = JSON.parse(json);
    return Loan.reconstitute({
      id:                   LoanId.of(data.id),
      customerId:           CustomerId.of(data.customerId),
      status:               data.status,
      principal:            Money.ofPaise(data.principalInPaise, data.currency),
      interestRate:         InterestRate.ofAnnual(data.annualInterestRate),
      tenureMonths:         data.tenureMonths,
      emisPaid:             data.emisPaid,
      outstandingPrincipal: Money.ofPaise(data.outstandingPrincipalInPaise, data.currency),
      nextEmiDueAt:         data.nextEmiDueAt ? new Date(data.nextEmiDueAt) : null,
      createdAt:            new Date(data.createdAt),
      updatedAt:            new Date(data.updatedAt),
    });
  }
}

// ─── NestJS wiring — swap between cached and uncached via config ──────────────

{
```

## Section 3: Repository in Node.js / TypeScript / Fintech Context

**Q11. How does the Repository pattern handle multi-tenancy in a SaaS fintech platform?**
A: Multi-tenant repositories enforce tenant isolation transparently — callers never pass a tenant ID explicitly; the repository resolves it from context and injects it into every query:

```typescript
// src/infrastructure/persistence/typeorm/repositories/tenant-scoped-loan.repository.ts

@Injectable()
export class TenantScopedLoanRepository implements ILoanRepository {
  constructor(
    @InjectRepository(LoanOrmEntity)
    private readonly ormRepo: Repository<LoanOrmEntity>,
    private readonly mapper:  LoanOrmMapper,
    private readonly tenantContext: TenantContextService,  // request-scoped
  ) {}

  private get tenantId(): string {
    const id = this.tenantContext.getCurrentTenantId();
    if (!id) throw new Error("No tenant context — repository cannot be used outside a request");
    return id;
  }

  async findById(loanId: LoanId): Promise<Loan | null> {
    const orm = await this.ormRepo.findOne({
      where: {
        id:         loanId.value,
        tenantId:   this.tenantId,      // ← always injected — cannot be bypassed
        archivedAt: IsNull(),
      },
    });
    return orm ? this.mapper.toDomain(orm) : null;
  }

  async findActiveByCustomer(customerId: CustomerId): Promise<Loan[]> {
    const orms = await this.ormRepo.find({
      where: {
        customerId: customerId.value,
        tenantId:   this.tenantId,
        status:     "ACTIVE",
        archivedAt: IsNull(),
      },
    });
    return orms.map(o => this.mapper.toDomain(o));
  }

  async save(loan: Loan): Promise<void> {
    const orm     = this.mapper.toOrm(loan);
    orm.tenantId  = this.tenantId;    // ← always stamped on write
    await this.ormRepo.save(orm);
  }

  // ... remaining methods all include this.tenantId in every query/write
}

// ─── TenantContextService — request-scoped service that carries tenant ID ─────

@Injectable({ scope: Scope.REQUEST })
export class TenantContextService {
  private tenantId: string | null = null;

  setTenantId(id: string): void { this.tenantId = id; }
  getCurrentTenantId(): string | null { return this.tenantId; }
}

// ─── Middleware sets tenant from JWT ─────────────────────────────────────────

@Injectable()
export class TenantResolutionMiddleware implements NestMiddleware {
  constructor(private readonly tenantContext: TenantContextService) {}

  use(req: Request, _res: Response, next: NextFunction): void {
    const tenantId = (req as any).user?.tenantId;
    if (tenantId) this.tenantContext.setTenantId(tenantId);
    next();
  }
}
```

Cross-tenant data leaks become architecturally impossible — the repository constructor requires a `TenantContextService` and every query includes `this.tenantId`. An accidental cross-tenant query would require deliberately passing the wrong context.

**Q12. How do you implement a Repository for an event-sourced aggregate, where state is derived from events rather than stored directly?**
A:

```typescript
// src/domain/repositories/loan-event-repository.interface.ts
export interface ILoanEventRepository {
  // Append new events for an aggregate
  appendEvents(loanId: LoanId, events: DomainEvent[], expectedVersion: number): Promise<void>;

  // Load all events for an aggregate and replay them to build current state
  loadEvents(loanId: LoanId): Promise<DomainEvent[]>;

  // Snapshot support — store a state snapshot to speed up replay
  saveSnapshot(loanId: LoanId, snapshot: LoanSnapshot, version: number): Promise<void>;
  loadLatestSnapshot(loanId: LoanId): Promise<{ snapshot: LoanSnapshot; version: number } | null>;
}

// ─── Concrete implementation ──────────────────────────────────────────────────

@Injectable()
export class PostgresLoanEventRepository implements ILoanEventRepository {
  constructor(private readonly db: DataSource) {}

  async appendEvents(
    loanId: LoanId,
    events: DomainEvent[],
    expectedVersion: number,
  ): Promise<void> {
    await this.db.transaction(async manager => {
      // Optimistic concurrency — verify version before insert
      const currentVersion = await manager.query(
        `SELECT COALESCE(MAX(version), 0) AS version FROM loan_events WHERE loan_id = $1`,
        [loanId.value],
      );
      if (Number(currentVersion[0].version) !== expectedVersion) {
        throw new OptimisticConcurrencyException(loanId.value, expectedVersion, currentVersion[0].version);
      }

      // Insert all new events
      let version = expectedVersion;
      for (const event of events) {
        version++;
        await manager.query(
          `INSERT INTO loan_events (id, loan_id, event_type, payload, version, occurred_at)
           VALUES ($1, $2, $3, $4, $5, $6)`,
          [event.eventId, loanId.value, event.eventType, JSON.stringify(event), version, event.occurredAt],
        );
      }
    });
  }

  async loadEvents(loanId: LoanId): Promise<DomainEvent[]> {
    // Load from snapshot version if available
    const snapshot = await this.loadLatestSnapshot(loanId);
    const fromVersion = snapshot?.version ?? 0;

    const rows = await this.db.query(
      `SELECT payload, event_type FROM loan_events
       WHERE loan_id = $1 AND version > $2
       ORDER BY version ASC`,
      [loanId.value, fromVersion],
    );

    return rows.map((row: any) => JSON.parse(row.payload));
  }

  async saveSnapshot(loanId: LoanId, snapshot: LoanSnapshot, version: number): Promise<void> {
    await this.db.query(
      `INSERT INTO loan_snapshots (loan_id, snapshot, version, created_at)
       VALUES ($1, $2, $3, NOW())
       ON CONFLICT (loan_id) DO UPDATE SET snapshot = $2, version = $3, created_at = NOW()`,
      [loanId.value, JSON.stringify(snapshot), version],
    );
  }

  async loadLatestSnapshot(loanId: LoanId): Promise<{ snapshot: LoanSnapshot; version: number } | null> {
    const rows = await this.db.query(
      `SELECT snapshot, version FROM loan_snapshots WHERE loan_id = $1`,
      [loanId.value],
    );
    if (rows.length === 0) return null;
    return { snapshot: JSON.parse(rows[0].snapshot), version: rows[0].version };
  }
}

// ─── Event-sourced Loan aggregate repository ──────────────────────────────────

@Injectable()
export class EventSourcedLoanRepository {
  constructor(private readonly eventRepo: ILoanEventRepository) {}

  async findById(loanId: LoanId): Promise<Loan | null> {
    const snapshot = await this.eventRepo.loadLatestSnapshot(loanId);
    const events   = await this.eventRepo.loadEvents(loanId);

    if (!snapshot && events.length === 0) return null;

    // Reconstitute from snapshot + subsequent events
    let loan = snapshot
      ? Loan.fromSnapshot(snapshot.snapshot)
      : Loan.createEmpty(loanId);

    for (const event of events) {
      loan = loan.apply(event);   // pure state transition
    }

    return loan;
  }

  async save(loan: Loan): Promise<void> {
    const uncommittedEvents = loan.pullUncommittedEvents();
    if (uncommittedEvents.length === 0) return;

    await this.eventRepo.appendEvents(loan.id, uncommittedEvents, loan.version - uncommittedEvents.length);

    // Snapshot every 50 events to bound replay time
    if (loan.version % 50 === 0) {
      await this.eventRepo.saveSnapshot(loan.id, loan.toSnapshot(), loan.version);
    }
  }
}
```

**Q13. How do you implement repository-level soft delete consistently across all repositories in a fintech system?**
A: Fintech systems rarely hard-delete records — regulatory requirements (RBI, SEBI) mandate audit trails. Soft delete should be enforced in the repository, not scattered across callers:

```typescript
// ─── Base repository with soft delete built in ────────────────────────────────

abstract class SoftDeletableTypeOrmRepository<TOrm extends SoftDeletableOrmEntity, TDomain> {
  constructor(protected readonly ormRepo: Repository<TOrm>) {}

  // All base queries automatically exclude soft-deleted rows
  protected get baseWhere(): FindOptionsWhere<TOrm> {
    return { deletedAt: IsNull() } as FindOptionsWhere<TOrm>;
  }

  protected mergeWhere(where: FindOptionsWhere<TOrm>): FindOptionsWhere<TOrm> {
    return { ...this.baseWhere, ...where };
  }

  // Soft delete — sets deletedAt; never removes the row
  async softDelete(id: string, deletedBy: string, reason: string): Promise<void> {
    await this.ormRepo.update(
      { id } as FindOptionsWhere<TOrm>,
      {
        deletedAt: new Date(),
        deletedBy,
        deleteReason: reason,
      } as QueryDeepPartialEntity<TOrm>,
    );
  }

  // Audit query — returns soft-deleted records for compliance review
  async findDeleted(fromDate: Date, toDate: Date): Promise<TOrm[]> {
    return this.ormRepo.find({
      where: {
        deletedAt: Between(fromDate, toDate),
      } as FindOptionsWhere<TOrm>,
      withDeleted: true,
    });
  }
}

// Concrete repository — inherits soft delete
@Injectable()
export class TypeOrmCustomerRepository
  extends SoftDeletableTypeOrmRepository<CustomerOrmEntity, Customer>
  implements ICustomerRepository
{
  constructor(
    @InjectRepository(CustomerOrmEntity) ormRepo: Repository<CustomerOrmEntity>,
    private readonly mapper: CustomerOrmMapper,
  ) {
    super(ormRepo);
  }

  async findById(customerId: CustomerId): Promise<Customer | null> {
    const orm = await this.ormRepo.findOne({
      where: this.mergeWhere({ id: customerId.value }),   // auto-excludes deleted
    });
    return orm ? this.mapper.toDomain(orm) : null;
  }

  async save(customer: Customer): Promise<void> {
    await this.ormRepo.save(this.mapper.toOrm(customer));
  }

  // Soft delete is inherited from base — cannot be hard-deleted
}
```

**Q14. How do you handle optimistic concurrency control in a Repository to prevent lost updates in concurrent financial operations?**
A:

```typescript
// Domain entity tracks version
export class Loan {
  private _version: number;

  // ... other fields

  get version(): number { return this._version; }

  // Version incremented on every state change
  private incrementVersion(): void { this._version++; }

  repayEmi(emiAmount: Money): void {
    // ... business logic
    this.incrementVersion();
  }
}

// ORM entity has version column
@Entity("loans")
@VersionColumn()   // TypeORM built-in optimistic lock
export class LoanOrmEntity {
  @Column()
  version: number;

  // ... other columns
}

// Repository enforces optimistic lock
@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  async save(loan: Loan): Promise<void> {
    const orm = this.mapper.toOrm(loan);
    try {
      // TypeORM @VersionColumn throws OptimisticLockVersionMismatchError on conflict
      await this.ormRepo.save(orm);
    } catch (err: any) {
      if (err.name === "OptimisticLockVersionMismatchError") {
        throw new ConcurrentModificationException(
          `Loan ${loan.id.value} was modified concurrently. Please retry.`
        );
      }
      throw err;
    }
  }
}

// Manual optimistic lock using WHERE clause (for raw queries)
async saveWithLock(loan: Loan, expectedVersion: number): Promise<void> {
  const result = await this.ormRepo
    .createQueryBuilder()
    .update(LoanOrmEntity)
    .set(this.mapper.toOrmFields(loan))
    .where("id = :id AND version = :expectedVersion", {
      id:              loan.id.value,
      expectedVersion,
    })
    .execute();

  if (result.affected === 0) {
    throw new ConcurrentModificationException(
      `Loan ${loan.id.value} was modified by another process.`
    );
  }
}
```

## Section 4: Pitfalls & Anti-patterns

**Q16. What is the "leaky repository" anti-pattern — when ORM details escape through the interface?**
A: A leaky repository exposes its underlying technology through the interface, coupling callers to implementation details:

```typescript
// ❌ Leaky — exposes TypeORM QueryBuilder to the domain
interface IBadLoanRepository {
  getQueryBuilder(): SelectQueryBuilder<LoanOrmEntity>;  // caller writes ORM queries
  findWithRelations(options: FindManyOptions<LoanOrmEntity>): Promise<LoanOrmEntity[]>;
  executeRaw(sql: string, params: any[]): Promise<any[]>;
}

// ❌ Leaky — returns ORM entities instead of domain objects
interface IBadLoanRepository {
  findById(id: string): Promise<LoanOrmEntity | null>;   // caller gets ORM entity with @Column decorators
}

// ❌ Leaky — caller must know about pagination being TypeORM-specific
interface IBadLoanRepository {
  findAll(options: FindManyOptions<LoanOrmEntity>): Promise<[LoanOrmEntity[], number]>;
}

// ✅ Sealed — domain-oriented interface, domain objects only
interface ILoanRepository {
  findById(loanId: LoanId): Promise<Loan | null>;
  findByStatus(status: LoanStatus, pagination: Pagination): Promise<PagedResult<Loan>>;
}
```

The signal that a repository is leaky: callers import ORM types (`FindManyOptions`, `SelectQueryBuilder`, `EntityManager`) from the domain or application layer.

**Q17. What is the "repository as service" anti-pattern?**
A: This occurs when repositories accumulate business logic, validation, and orchestration that belongs in the domain or application layer:

```typescript
// ❌ Repository as service — contains business rules, orchestration, and events
class LoanRepository {
  async createLoan(command: CreateLoanCommand): Promise<string> {
    // Business rule — belongs in domain
    if (command.amount > 1_500_000_00) throw new Error("Amount exceeds maximum");

    // Eligibility check — belongs in use case
    const creditScore = await this.creditBureau.check(command.pan);
    if (creditScore < 700) throw new Error("CIBIL too low");

    // Domain event — belongs in domain entity
    await this.eventBus.publish(new LoanCreatedEvent(...));

    // Notification — belongs in application layer / event handler
    await this.notificationService.sendApprovalSms(command.customerId);

    const orm = this.mapper.toOrm({ ...command });
    return (await this.ormRepo.save(orm)).id;
  }
}
```

A repository should have exactly three concerns: retrieve, persist, and encapsulate query logic. Any method that makes a decision, calls an external service, or coordinates multiple operations belongs elsewhere.

**Q18. What is the "N+1 query problem" in repositories, and how do you address it?**
A: N+1 occurs when the repository fetches a list of N aggregates individually (N queries) after an initial list query (1 query), instead of fetching them together:

```typescript
// ❌ N+1 — fetches loans, then fetches each customer separately
async function buildLoanDashboard(): Promise<DashboardRow[]> {
  const loans = await loanRepo.findOverdue(new Date());   // 1 query
  return Promise.all(
    loans.map(async loan => ({
      ...loan,
      customer: await customerRepo.findById(loan.customerId),  // N queries
    }))
  );
}

// ✅ Batch load — one query for all customers
async function buildLoanDashboard(): Promise<DashboardRow[]> {
  const loans       = await loanRepo.findOverdue(new Date());
  const customerIds = [...new Set(loans.map(l => l.customerId.value))];
  const customers   = await customerRepo.findByIds(customerIds.map(CustomerId.of));  // 1 query
  const customerMap = new Map(customers.map(c => [c.id.value, c]));

  return loans.map(loan => ({
    ...loan,
    customer: customerMap.get(loan.customerId.value) ?? null,
  }));
}

// ✅ Dedicated query method — for read models that naturally span aggregates
// src/infrastructure/read-models/overdue-loan-dashboard.query.ts
@Injectable()
export class OverdueLoanDashboardQuery {
  async execute(asOf: Date): Promise<OverdueDashboardRow[]> {
    // Single JOIN query — not a domain repository concern
    return this.dataSource.query(`
      SELECT
        l.id, l.outstanding_principal_in_paise, l.next_emi_due_at,
        c.name AS customer_name, c.phone AS customer_phone
      FROM loans l
      JOIN customers c ON c.id = l.customer_id
      WHERE l.status = 'ACTIVE'
        AND l.next_emi_due_at < $1
        AND l.archived_at IS NULL
      ORDER BY l.next_emi_due_at ASC
    `, [asOf]);
  }
}
```

The key insight: repositories are for aggregate access (one aggregate at a time, by identity or criteria). Read models that span aggregates or join tables belong in dedicated query objects, not in domain repositories.

**Q19. How do you prevent repositories from becoming God objects that know about every aggregate?**
A: Enforce one repository per aggregate root — a strict structural discipline:

```typescript
// ❌ God repository — knows about every aggregate
class FinancialRepository {
  findLoanById(id: string): Promise<Loan | null> { ... }
  findCustomerById(id: string): Promise<Customer | null> { ... }
  findEmiScheduleByLoan(loanId: string): Promise<EmiSchedule | null> { ... }
  findTransactionById(id: string): Promise<Transaction | null> { ... }
  findKycByCustomer(customerId: string): Promise<KycRecord | null> { ... }
}

// ✅ Separate repository per aggregate root
class ILoanRepository { findById(loanId: LoanId): Promise<Loan | null>; ... }
class ICustomerRepository { findById(customerId: CustomerId): Promise<Customer | null>; ... }
class IEmiRepository { findByLoan(loanId: LoanId): Promise<EmiSchedule | null>; ... }
class ITransactionRepository { findById(txnId: TransactionId): Promise<Transaction | null>; ... }
class IKycRepository { findByCustomer(customerId: CustomerId): Promise<KycRecord | null>; ... }
```

The rule of thumb: if you find yourself passing a `loanId` to a `CustomerRepository`, you've blurred aggregate boundaries. A repository should only retrieve and persist the aggregate it's named for. Cross-aggregate access is a use case responsibility, resolved by calling multiple repositories.

**Q20. What are the pitfalls of the Generic Repository, and how do you get the benefits without the downsides?**
A:

```typescript
// ❌ Problematic generic repository exposed to the domain
interface IRepository<T, ID> {
  findAll(): Promise<T[]>;       // always dangerous — no pagination, no filter
  findOne(id: ID): Promise<T | null>;
  create(entity: T): Promise<T>;
  update(id: ID, partial: Partial<T>): Promise<T>;
  delete(id: ID): Promise<void>; // hard delete — never acceptable for financial records
}

// ✅ Generic base used only in the infrastructure layer — not exposed to the domain
abstract class TypeOrmBaseRepository<TOrm, TDomain, TId> {
  constructor(protected readonly ormRepo: Repository<TOrm>) {}

  // Shared ORM plumbing — reusable internally
  protected async findOrmById(id: string): Promise<TOrm | null> {
    return this.ormRepo.findOne({ where: { id } as any });
  }

  protected async saveOrm(orm: TOrm): Promise<void> {
    await this.ormRepo.save(orm as any);
  }

  // Abstract — each concrete repo defines its domain mapping
  protected abstract toDomain(orm: TOrm): TDomain;
  protected abstract toOrm(domain: TDomain): TOrm;
}

// Concrete repo: inherits plumbing, exposes domain-specific interface
@Injectable()
export class TypeOrmLoanRepository
  extends TypeOrmBaseRepository<LoanOrmEntity, Loan, LoanId>
  implements ILoanRepository  // ← the only interface the domain sees
{
  async findById(loanId: LoanId): Promise<Loan | null> {
    const orm = await this.findOrmById(loanId.value);
    return orm ? this.toDomain(orm) : null;
  }

  async findOverdue(asOf: Date): Promise<Loan[]> { /* ... */ }
  async save(loan: Loan): Promise<void> {
    await this.saveOrm(this.toOrm(loan));
  }

  protected toDomain(orm: LoanOrmEntity): Loan { return this.mapper.toDomain(orm); }
  protected toOrm(domain: Loan): LoanOrmEntity { return this.mapper.toOrm(domain); }
}
```

The domain sees `ILoanRepository` — a specific, intentional interface. The infrastructure reuses `TypeOrmBaseRepository` for the plumbing. No `findAll()`, no `delete()`, no `Partial<T>` leaking into the domain.

## Section 5: Scenario / System Design Style Questions

**Q21. "You're building a loan EMI collection system. EMI collection runs nightly across 100,000 active loans. The collection logic involves fetching the loan, checking NACH mandate status, debiting via NACH, updating the loan, and publishing an event. How do you structure the Repository to support this efficiently?"**
A:

```typescript
// ─── Repository methods designed for bulk processing ──────────────────────────

interface ILoanRepository {
  // Chunked retrieval — avoids loading 100K loans into memory simultaneously
  findDueForEmiCollectionCursor(date: Date, chunkSize: number): AsyncIterable<Loan[]>;

  // Bulk status update after processing — one UPDATE statement for the chunk
  markCollectionAttempted(loanIds: LoanId[], attemptedAt: Date): Promise<void>;

  // Bulk save — one transaction per chunk, not one per loan
  saveAll(loans: Loan[]): Promise<void>;
}

// ─── Implementation with cursor-based streaming ───────────────────────────────

@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  async *findDueForEmiCollectionCursor(
    date: Date,
    chunkSize: number,
  ): AsyncIterable<Loan[]> {
    const start = new Date(date); start.setHours(0, 0, 0, 0);
    const end   = new Date(date); end.setHours(23, 59, 59, 999);

    let offset = 0;
    while (true) {
      const orms = await this.ormRepo.find({
        where: {
          status:       "ACTIVE",
          nextEmiDueAt: Between(start, end),
          archivedAt:   IsNull(),
        },
        order: { id: "ASC" },   // stable ordering for cursor
        skip: offset,
        take: chunkSize,
      });

      if (orms.length === 0) break;

      yield orms.map(o => this.mapper.toDomain(o));
      offset += chunkSize;

      if (orms.length < chunkSize) break;   // last page
    }
  }

  async markCollectionAttempted(loanIds: LoanId[], attemptedAt: Date): Promise<void> {
    await this.ormRepo
      .createQueryBuilder()
      .update(LoanOrmEntity)
      .set({ lastCollectionAttemptAt: attemptedAt })
      .whereInIds(loanIds.map(id => id.value))
      .execute();
  }
}

// ─── Use case consumes the cursor ────────────────────────────────────────────

@Injectable()
export class NightlyEmiCollectionUseCase {
  constructor(
    private readonly loanRepo:    ILoanRepository,
    private readonly nachService: INachMandatePort,
    private readonly publisher:   IEventPublisher,
    private readonly metrics:     MetricsService,
  ) {}

  async execute(date: Date): Promise<EmiCollectionSummary> {
    let processed = 0, succeeded = 0, failed = 0;

    for await (const chunk of this.loanRepo.findDueForEmiCollectionCursor(date, 500)) {
      const results = await Promise.allSettled(
        chunk.map(loan => this.collectEmi(loan))
      );

      const successfulLoans = chunk.filter((_, i) =>
        results[i].status === "fulfilled"
      );

      if (successfulLoans.length > 0) {
        await this.loanRepo.saveAll(successfulLoans);  // batch save
      }

      await this.loanRepo.markCollectionAttempted(
        chunk.map(l => l.id), new Date()
      );

      processed += chunk.length;
      succeeded += results.filter(r => r.status === "fulfilled").length;
      failed    += results.filter(r => r.status === "rejected").length;

      this.metrics.recordChunkProcessed(chunk.length, succeeded, failed);
    }

    return { processed, succeeded, failed };
  }

  private async collectEmi(loan: Loan): Promise<void> {
    const mandate = await this.nachService.checkMandate(loan.id);
    if (!mandate.isActive) throw new Error(`Mandate inactive for loan ${loan.id.value}`);

    await this.nachService.debit(mandate.mandateId, loan.calculateCurrentEmi());
    loan.repayEmi(loan.calculateCurrentEmi());

    const events = loan.pullDomainEvents();
    await Promise.all(events.map(e => this.publisher.publish(e)));
  }
}
```

**Q22. "Your team inherits a NestJS codebase where controllers call TypeORM EntityManager directly, SQL queries are scattered across 30 files, and unit tests require a live database. How do you migrate to the Repository pattern incrementally?"**
A: A strangler-fig migration — introduce the Repository interface without breaking existing code:

**Phase 1 — Define interfaces, introduce test doubles:**
```typescript
// Create ILoanRepository without touching existing code
// Create InMemoryLoanRepository for new tests
// New features use the interface; old code still uses EntityManager directly
```

**Phase 2 — Introduce the concrete repository alongside existing code:**
```typescript
// TypeOrmLoanRepository implements ILoanRepository
// Wraps EntityManager internally — reuses existing queries
@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  constructor(private readonly manager: EntityManager) {}

  async findById(loanId: LoanId): Promise<Loan | null> {
    // Lift existing scattered query into the repository
    const row = await this.manager.query(
      "SELECT * FROM loans WHERE id = $1 AND deleted_at IS NULL", [loanId.value]
    );
    return row[0] ? this.mapper.toDomain(row[0]) : null;
  }
}
```

**Phase 3 — Migrate one service at a time:**
```typescript
// Before:
@Injectable()
class LoanService {
  constructor(private readonly manager: EntityManager) {}

  async getLoan(id: string) {
    return this.manager.query("SELECT * FROM loans WHERE id = $1", [id]);
  }
}

// After:
@Injectable()
class LoanService {
  constructor(
    @Inject(LOAN_REPOSITORY) private readonly loanRepo: ILoanRepository
  ) {}

  async getLoan(id: string) {
    return this.loanRepo.findById(LoanId.of(id));
  }
}
```

**Phase 4 — Remove duplicate queries:**
As services are migrated, the scattered SQL queries are consolidated into the repository. Enable a lint rule that flags direct `EntityManager` or TypeORM `Repository` usage outside the infrastructure layer. Each migration also unlocks unit tests: replace the live DB test with an `InMemoryLoanRepository` test.

**Phase 5 — Add the caching and replica-routing decorators:**
Now that everything goes through the interface, add caching and read-replica routing without touching any service or controller.

**Q23. "Two concurrent HTTP requests try to approve the same loan simultaneously. How does the Repository prevent the lost update?"**
A:

```typescript
// ─── Option 1: Database-level optimistic locking (preferred) ──────────────────

// The ORM entity has a @VersionColumn
// TypeORM increments it on every save and verifies it in the WHERE clause:
// UPDATE loans SET status='APPROVED', version=2 WHERE id=$1 AND version=1
// If 0 rows affected → version mismatch → throw OptimisticLockVersionMismatchError

@Injectable()
export class ApproveLoanUseCase {
  async execute(command: ApproveLoanCommand): Promise<void> {
    try {
      const loan = await this.loanRepo.findById(LoanId.of(command.loanId));
      if (!loan) throw new NotFoundException(command.loanId);

      loan.approve();             // sets status = APPROVED, increments version
      await this.loanRepo.save(loan);  // TypeORM verifies version in WHERE
    } catch (err: any) {
      if (err instanceof ConcurrentModificationException) {
        // Return 409 Conflict — caller retries
        throw new ConflictException("Loan was modified concurrently. Please retry.");
      }
      throw err;
    }
  }
}

// ─── Option 2: Pessimistic locking (for critical financial operations) ─────────

@Injectable()
export class TypeOrmLoanRepository implements ILoanRepository {
  async findByIdForUpdate(loanId: LoanId): Promise<Loan | null> {
    // SELECT ... FOR UPDATE — holds a row-level lock until transaction commits
    const orm = await this.ormRepo
      .createQueryBuilder("loan")
      .where("loan.id = :id", { id: loanId.value })
      .setLock("pessimistic_write")
      .getOne();
    return orm ? this.mapper.toDomain(orm) : null;
  }
}

// Use case acquires the lock before reading and modifying
async execute(command: ApproveLoanCommand): Promise<void> {
  await this.uow.begin();
  try {
    // Lock acquired — no other transaction can modify this row until commit
    const loan = await this.loanRepo.findByIdForUpdate(LoanId.of(command.loanId));
    loan.approve();
    await this.loanRepo.save(loan);
    await this.uow.commit();
  } catch (err) {
    await this.uow.rollback();
    throw err;
  }
}
```

For a loan approval, pessimistic locking is usually correct — the operation is rare, high-stakes, and the lock duration is short (one DB round-trip). For EMI status updates, optimistic locking is sufficient — conflicts are rare and the retry cost is low.

**Q24. "The data team wants to run complex analytics queries (cohort analysis, vintage curves, delinquency rates) on loan data. They're asking the backend team to add methods to the LoanRepository. How do you respond?"**
A: Analytics queries do not belong in the domain repository — they are a different access pattern for a different consumer. A clear architectural response:

> "The `ILoanRepository` interface is designed for the loan domain — it fetches and persists `Loan` aggregates for business operations. Analytics cohort queries join multiple tables, return denormalised results, and have no use for a `Loan` domain object. Adding them to `ILoanRepository` would violate the interface's single responsibility and force the in-memory test double to implement complex aggregation logic.

> The right structure is a separate read model query:

```typescript
// src/infrastructure/analytics/loan-analytics.query.ts

@Injectable()
export class LoanAnalyticsQuery {
  constructor(private readonly readReplicaDataSource: DataSource) {}

  // Always runs on read replica — never on primary
  async getVintageCurve(cohortMonth: string): Promise<VintageCurveRow[]> {
    return this.readReplicaDataSource.query(`
      SELECT
        months_since_disbursement,
        COUNT(*) AS total_loans,
        SUM(CASE WHEN status = 'OVERDUE' THEN 1 ELSE 0 END) AS overdue_count,
        SUM(CASE WHEN status = 'OVERDUE' THEN 1 ELSE 0 END)::FLOAT / COUNT(*) AS dpd_rate
      FROM (
        SELECT
          l.id,
          l.status,
          EXTRACT(MONTH FROM AGE(NOW(), l.disbursed_at)) AS months_since_disbursement
        FROM loans l
        WHERE DATE_TRUNC('month', l.disbursed_at) = $1
          AND l.archived_at IS NULL
      ) sub
      GROUP BY months_since_disbursement
      ORDER BY months_since_disbursement
    `, [cohortMonth]);
  }

  async getDelinquencyByProductCode(asOf: Date): Promise<DelinquencyRow[]> {
    return this.readReplicaDataSource.query(`
      SELECT
        product_code,
        COUNT(*) FILTER (WHERE status = 'ACTIVE')  AS active_count,
        COUNT(*) FILTER (WHERE status = 'OVERDUE') AS overdue_count,
        SUM(outstanding_principal_in_paise) / 100  AS total_outstanding_rupees
      FROM loans
      WHERE archived_at IS NULL AND created_at <= $1
      GROUP BY product_code
    `, [asOf]);
  }
}
```

> For the data team's direct access, we'll provision a read replica with a read-only role. They can query it directly via their BI tool without going through our API or our domain repository."

**Q25. "How do you explain the Repository pattern — and specifically why it's different from just injecting a TypeORM repository — to a junior engineer joining the team?"**
A: A practical, concrete explanation:

> "When you inject TypeORM's `Repository<LoanEntity>` directly into a service, you're tying that service to three things at once: the database (PostgreSQL), the ORM (TypeORM), and the table schema (the LoanEntity columns). If we ever want to test that service — say, to verify that it rejects a loan when the customer has two active loans — we need a running PostgreSQL database with the right schema. That's slow, brittle, and overkill for testing a business rule.
>
> The Repository pattern is a layer between the service and TypeORM. The service says 'give me active loans for customer X' — it talks to an interface. In production, that interface is backed by TypeORM and PostgreSQL. In tests, it's backed by a plain `Map` in memory — a few lines of TypeScript, no database.
>
> The practical difference: a test suite with in-memory repositories runs in 8 seconds. The same test suite hitting a real database runs in 3 minutes and fails if the database isn't running. Over 200 tests, that compounds into a 22-minute difference on every CI run.
>
> The second benefit: last year we migrated from TypeORM to Prisma. Because our domain and application layers only reference the `ILoanRepository` interface, we changed exactly one file per aggregate — the infrastructure implementation. The domain entity, the use cases, and the tests were untouched. Without the Repository pattern, that would have required editing every service that called TypeORM directly.
>
> So the pattern isn't ceremony — it's the architectural decision that makes your tests fast and your infrastructure swappable."

**Tip for the Interview:** At the 5 YOE level, Repository questions rarely surface as "what is the Repository pattern" — they appear as "how do you make your business logic testable without a database," "how did you handle the ORM migration," "how do you prevent N+1 in a bulk processing job," or "the data team wants analytics methods on your repository — how do you respond?" The answers that land demonstrate four things: (1) you can articulate the interface-in-domain, implementation-in-infrastructure separation precisely — the domain defines what it needs, the infrastructure decides how to provide it; (2) you've built and used an in-memory repository as a test double, and you can quote the test speed difference; (3) you know where the Repository ends and other patterns begin — transactions belong to Unit of Work, analytics belong to read-model queries, caching belongs to a decorator; and (4) you can defend the pattern against the "it's just boilerplate" objection with a concrete migration or ORM-swap story. In fintech specifically, the soft-delete, audit trail, and optimistic concurrency stories are the ones that demonstrate domain-aware thinking rather than generic CRUD application of the pattern.
