# Node.js & Backend Design Patterns: Controller-Service-Repository Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Controller-Service-Repository (CSR) architecture?**
A: Controller-Service-Repository is the most prevalent architectural pattern for Node.js/NestJS backends — a practical, three-layer application of Layered Architecture tailored to REST API development. It separates the application into three collaborating layers, each with a strict and distinct responsibility:

- **Controller** — the HTTP boundary. Receives requests, validates input shape, delegates to the service, formats the response. Knows about HTTP; knows nothing about business rules or databases.
- **Service** — the business logic layer. Orchestrates use cases, enforces domain rules, coordinates between repositories and external services. Knows about the business; knows nothing about HTTP or SQL.
- **Repository** — the data access layer. Abstracts all database interactions. Returns domain objects to the service; translates domain objects to database-compatible formats for persistence. Knows about the database; knows nothing about HTTP or business rules.

The dependency direction is always downward: Controller → Service → Repository. No layer ever calls a layer above it.

**Q2. Why is CSR the default architecture for most Node.js backends? What does it solve?**
A: CSR solves the three most common structural problems that emerge as Node.js backends grow:

- **The monolithic handler** — without structure, Express/Fastify route handlers accumulate everything: input parsing, validation, DB queries, business logic, response formatting. A single handler grows to 200 lines and becomes untestable.
- **Coupled concerns** — without layers, changing a DB query requires understanding the HTTP layer; changing a response format requires understanding the DB schema. Every change ripples unpredictably.
- **Untestable code** — when a controller directly queries the database, you cannot unit test the business logic without spinning up a real database. CSR gives you seams at every layer boundary where dependencies can be mocked.

CSR is the default because it's the minimum viable architecture — it enforces just enough structure to keep medium-sized backends maintainable without the added complexity of DDD aggregates, CQRS, or event sourcing.

**Q3. What does each layer own exclusively? What is it forbidden to do?**
A:

| Layer          | Owns exclusively                                                              | Forbidden from doing                                              |
|----------------|-------------------------------------------------------------------------------|-------------------------------------------------------------------|
| **Controller** | HTTP parsing, input DTO validation, auth guard enforcement, response shaping  | Business rules, DB queries, direct ORM access                    |
| **Service**    | Business rule enforcement, use case orchestration, transaction coordination   | HTTP response objects, `req`/`res` references, raw SQL/ORM queries |
| **Repository** | All SQL/ORM queries, DB connection management, domain ↔ persistence mapping   | Business logic, HTTP concerns, calling service methods           |

The golden rule: if you see `res.json()` or `@Res()` in a service, something is wrong. If you see `prisma.loan.findMany()` in a controller, something is wrong. If you see `if (income < 25000)` in a repository, something is wrong.

**Q4. How does NestJS's module system enforce CSR structure?**
A: NestJS uses its `@Module` decorator to organise providers and enforces the dependency direction through its DI container. A well-structured NestJS module mirrors CSR explicitly:

```typescript
@Module({
  imports: [
    TypeOrmModule.forFeature([LoanEntity]),  // or PrismaModule
    BureauModule,                             // external service dependency
    NotificationModule,
  ],
  controllers: [LoanController],             // presentation layer
  providers: [
    LoanService,                             // service layer
    LoanRepository,                          // repository layer
  ],
  exports: [LoanService],                    // what other modules may use
})
export class LoanModule {}
```

NestJS makes the anti-pattern hard: a Controller cannot directly inject a Repository (it could — DI doesn't enforce architecture — but the module boundary signals it's wrong). Code reviews and linting rules (`@typescript-eslint/no-restricted-imports`) enforce the layer boundary programmatically.

**Q5. What is the difference between CSR and a full Layered Architecture / DDD?**
A: CSR is a practical subset of Layered Architecture, and Layered Architecture is a subset of DDD:

- **CSR** — three named layers, typically in one module per feature. Repositories return ORM entities or plain objects. Services contain both orchestration *and* business rules. No separate domain model concept. Good for CRUD-heavy systems with moderate business logic.
- **Layered Architecture** — same three layers but with more rigour: DTOs at every boundary, domain exceptions translated by filters, possibly a domain model layer distinct from the service layer. Better separation of concerns.
- **DDD** — adds strategic design (Bounded Contexts), rich domain model (Aggregates, Value Objects, Domain Events), and strict infrastructure isolation (ports and adapters). The repository interface lives in the domain layer; the implementation in the infrastructure layer. Business logic lives on the aggregate, not in services. For complex, evolving domains.

In practice, a NestJS fintech codebase typically starts as CSR, evolves to proper Layered Architecture as it grows, and applies selected DDD patterns (aggregates, value objects, domain events) to the most complex bounded contexts (loan origination, underwriting, collections).

## Section 2: Controller Layer in Depth

**Q6. What does a well-written NestJS Controller look like? What is its complete responsibility set?**
A:

```typescript
@Controller('loan-applications')
@UseGuards(JwtAuthGuard)          // auth at the controller level — applies to all routes
@UseInterceptors(LoggingInterceptor, AuditInterceptor)
export class LoanApplicationController {
  constructor(private readonly loanApplicationService: LoanApplicationService) {}

  @Post()
  @Roles(Role.APPLICANT, Role.LOAN_OFFICER)
  @HttpCode(HttpStatus.CREATED)
  async apply(
    @Body() dto: CreateLoanApplicationDto,  // validated by global ValidationPipe
    @CurrentUser() user: AuthenticatedUser, // extracted by decorator from JWT
  ): Promise<LoanApplicationResponseDto> {
    // ← delegates immediately; no logic here
    const result = await this.loanApplicationService.apply(dto, user.id);
    return LoanApplicationResponseDto.fromDomain(result); // response shaping here
  }

  @Get(':id')
  @Roles(Role.APPLICANT, Role.LOAN_OFFICER, Role.CREDIT_MANAGER)
  async getById(
    @Param('id', ParseUUIDPipe) id: string,
    @CurrentUser() user: AuthenticatedUser,
  ): Promise<LoanApplicationResponseDto> {
    const result = await this.loanApplicationService.findById(id, user);
    return LoanApplicationResponseDto.fromDomain(result);
  }

  @Get()
  @Roles(Role.LOAN_OFFICER, Role.CREDIT_MANAGER)
  async list(
    @Query() query: ListLoanApplicationsQueryDto, // pagination + filters
    @CurrentUser() user: AuthenticatedUser,
  ): Promise<PaginatedResponseDto<LoanApplicationResponseDto>> {
    const result = await this.loanApplicationService.list(query, user);
    return PaginatedResponseDto.from(result, LoanApplicationResponseDto.fromDomain);
  }

  @Patch(':id/sanction')
  @Roles(Role.CREDIT_MANAGER, Role.BRANCH_MANAGER)
  @HttpCode(HttpStatus.OK)
  async sanction(
    @Param('id', ParseUUIDPipe) id: string,
    @Body() dto: SanctionLoanDto,
    @CurrentUser() user: AuthenticatedUser,
  ): Promise<LoanApplicationResponseDto> {
    const result = await this.loanApplicationService.sanction(id, dto, user);
    return LoanApplicationResponseDto.fromDomain(result);
  }
}
```

Notice: no `if` statements, no ORM imports, no business conditions. Every method is: parse → delegate → format. The controller is testable by mocking `loanApplicationService` alone — no real business logic to verify here.

**Q7. How do you handle input validation at the controller layer in NestJS?**
A: Use `class-validator` + `class-transformer` with NestJS's `ValidationPipe` globally:

```typescript
// main.ts — enable globally
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,          // strip unknown properties — security
    forbidNonWhitelisted: true, // reject requests with unknown properties
    transform: true,          // auto-transform to DTO class instances
    transformOptions: { enableImplicitConversion: true },
  }),
);

// DTO — all validation at the DTO level
export class CreateLoanApplicationDto {
  @IsUUID()
  productCode: string;

  @IsInt()
  @Min(10_000_00)       // ₹10,000 minimum in paise
  @Max(10_000_000_00)   // ₹1 Cr maximum in paise
  requestedAmount: number;

  @IsInt()
  @Min(6)
  @Max(360)
  tenorMonths: number;

  @IsString()
  @Matches(/^[A-Z]{5}[0-9]{4}[A-Z]{1}$/, { message: 'Invalid PAN format' })
  pan: string;

  @IsEnum(EmploymentType)
  employmentType: EmploymentType;

  @IsInt()
  @Min(0)
  monthlyIncome: number; // in paise
}
```

Validation at the DTO/controller level: is the input well-formed? (type, format, range). This is **not** business validation — "is the applicant eligible?" is a business rule enforced in the service, not a DTO validation. The distinction: DTO validation can be evaluated without any business context; business validation requires domain knowledge.

**Q8. How do you properly handle errors across the CSR layers?**
A: Define domain exceptions in the service layer; translate them to HTTP at the controller boundary using NestJS Exception Filters:

```typescript
// Service layer — throws domain exceptions (no HTTP awareness)
export class LoanApplicationService {
  async findById(id: string, user: AuthenticatedUser): Promise<LoanApplication> {
    const loan = await this.loanRepository.findById(id);
    if (!loan) throw new LoanApplicationNotFoundException(id);        // domain exception
    if (loan.applicantId !== user.id && !user.hasRole(Role.OFFICER)) {
      throw new UnauthorisedLoanAccessException(id, user.id);        // domain exception
    }
    return loan;
  }
}

// Domain exceptions — no HTTP imports
export class LoanApplicationNotFoundException extends Error {
  constructor(public readonly loanId: string) {
    super(`Loan application ${loanId} not found`);
    this.name = 'LoanApplicationNotFoundException';
  }
}

export class UnauthorisedLoanAccessException extends Error {
  constructor(public readonly loanId: string, public readonly userId: string) {
    super(`User ${userId} is not authorised to access loan ${loanId}`);
    this.name = 'UnauthorisedLoanAccessException';
  }
}

export class IneligibleApplicantException extends Error {
  constructor(public readonly reasons: string[]) {
    super(`Applicant ineligible: ${reasons.join('; ')}`);
    this.name = 'IneligibleApplicantException';
  }
}

// Exception Filter — presentation layer; translates domain → HTTP
@Catch()
export class GlobalDomainExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): void {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();

    if (exception instanceof LoanApplicationNotFoundException) {
      return response.status(404).json({
        statusCode: 404,
        error: 'Not Found',
        message: exception.message,
        loanId: exception.loanId,
        timestamp: new Date().toISOString(),
        path: request.url,
      });
    }

    if (exception instanceof UnauthorisedLoanAccessException) {
      return response.status(403).json({ statusCode: 403, error: 'Forbidden', message: exception.message });
    }

    if (exception instanceof IneligibleApplicantException) {
      return response.status(422).json({
        statusCode: 422,
        error: 'Unprocessable Entity',
        message: 'Applicant does not meet eligibility criteria',
        reasons: exception.reasons,
      });
    }

    if (exception instanceof HttpException) {
      return response.status(exception.getStatus()).json(exception.getResponse());
    }

    // Unexpected error — don't leak internals
    response.status(500).json({ statusCode: 500, error: 'Internal Server Error', message: 'An unexpected error occurred' });
  }
}
```

## Section 3: Service Layer in Depth

**Q9. What does a well-written Service look like in a NestJS lending platform?**
A:

```typescript
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepository: LoanRepository,
    private readonly bureauService: BureauService,             // external integration
    private readonly eligibilityService: LoanEligibilityService, // domain service
    private readonly notificationService: NotificationService,
    private readonly eventEmitter: EventEmitter2,
  ) {}

  async apply(dto: CreateLoanApplicationDto, applicantId: string): Promise<LoanApplication> {
    // 1. Business rule — eligibility check (not in controller, not in repository)
    const eligibility = await this.eligibilityService.assess({
      employmentType: dto.employmentType,
      monthlyIncome: dto.monthlyIncome,
      pan: dto.pan,
    });
    if (!eligibility.eligible) {
      throw new IneligibleApplicantException(eligibility.reasons);
    }

    // 2. External service coordination — bureau pull (not in controller, not in repo)
    const bureauReport = await this.bureauService.fetchCreditReport(dto.pan);
    if (bureauReport.score < 650) {
      throw new IneligibleApplicantException([`Bureau score ${bureauReport.score} below minimum 650`]);
    }

    // 3. Persistence — delegates entirely to repository
    const loan = await this.loanRepository.create({
      applicantId,
      productCode: dto.productCode,
      requestedAmount: dto.requestedAmount,
      tenorMonths: dto.tenorMonths,
      pan: dto.pan,
      bureauScore: bureauReport.score,
      status: LoanStatus.PENDING,
    });

    // 4. Side effects — notification and events (not in controller)
    await this.notificationService.sendApplicationReceived(loan.applicantId, loan.id);
    this.eventEmitter.emit('loan.application.submitted', { loanId: loan.id, applicantId });

    return loan; // returns domain object — controller handles HTTP formatting
  }

  async sanction(
    loanId: string,
    dto: SanctionLoanDto,
    officer: AuthenticatedUser,
  ): Promise<LoanApplication> {
    const loan = await this.loanRepository.findById(loanId);
    if (!loan) throw new LoanApplicationNotFoundException(loanId);

    // Business rule — only PENDING_REVIEW loans can be sanctioned
    if (loan.status !== LoanStatus.PENDING_REVIEW) {
      throw new InvalidLoanStatusException(loan.status, 'SANCTION');
    }

    // Business rule — officer authority limit
    if (dto.sanctionedAmount > officer.authorityLimit) {
      throw new ExceedsAuthorityLimitException(officer.id, dto.sanctionedAmount, officer.authorityLimit);
    }

    const updated = await this.loanRepository.updateStatus(loanId, LoanStatus.SANCTIONED, {
      sanctionedAmount: dto.sanctionedAmount,
      sanctionedBy: officer.id,
      sanctionedAt: new Date(),
      conditions: dto.conditions,
    });

    await this.notificationService.sendSanctionLetter(loan.applicantId, updated);
    this.eventEmitter.emit('loan.sanctioned', { loanId, officerId: officer.id, amount: dto.sanctionedAmount });

    return updated;
  }

  async findById(id: string, requestor: AuthenticatedUser): Promise<LoanApplication> {
    const loan = await this.loanRepository.findById(id);
    if (!loan) throw new LoanApplicationNotFoundException(id);

    // Business rule — access control (who can see which loans)
    if (loan.applicantId !== requestor.id && !requestor.hasRole(Role.OFFICER)) {
      throw new UnauthorisedLoanAccessException(id, requestor.id);
    }

    return loan;
  }
}
```

**Q10. How do you handle database transactions in the Service layer without leaking ORM details?**
A: Transactions are a business concern (what must be atomic) but their mechanics are infrastructure. The service declares atomicity; the repository or a transaction manager handles the ORM specifics:

```typescript
// Option A — Prisma interactive transaction passed through as context
@Injectable()
export class LoanDisbursementService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly loanRepository: LoanRepository,
    private readonly ledgerRepository: LedgerRepository,
    private readonly disbursementRepository: DisbursementRepository,
  ) {}

  async disburse(loanId: string, bankDetails: BankDetailsDto): Promise<DisbursementResult> {
    // Service declares: "these three operations must be atomic"
    const result = await this.prisma.$transaction(async (tx) => {
      const loan = await this.loanRepository.findById(loanId, tx);
      if (!loan) throw new LoanApplicationNotFoundException(loanId);
      if (loan.status !== LoanStatus.SANCTIONED) {
        throw new InvalidLoanStatusException(loan.status, 'DISBURSE');
      }

      await this.loanRepository.updateStatus(loanId, LoanStatus.DISBURSED, {
        disbursedAt: new Date(),
        disbursedAmount: loan.sanctionedAmount,
      }, tx);

      await this.ledgerRepository.creditBorrower(loanId, loan.sanctionedAmount, tx);
      await this.disbursementRepository.create({
        loanId,
        amount: loan.sanctionedAmount,
        bankDetails,
        initiatedAt: new Date(),
      }, tx);

      return { loanId, disbursedAmount: loan.sanctionedAmount };
    });

    // Post-transaction side effects (outside the transaction — they're not atomic with it)
    await this.notificationService.sendDisbursementConfirmation(result.loanId);
    return result;
  }
}

// Repository accepts optional transaction client
@Injectable()
export class LoanRepository {
  async updateStatus(
    id: string,
    status: LoanStatus,
    extra: Partial<LoanUpdateData> = {},
    tx?: PrismaTransactionClient,
  ): Promise<LoanApplication> {
    const client = tx ?? this.prisma;
    const record = await client.loan.update({
      where: { id },
      data: { status, ...extra },
    });
    return this.toDomain(record);
  }
}
```

**Q11. How should a Service handle calls to multiple external services, and what happens when one fails?**
A: The service must handle partial failures explicitly — circuit breakers, fallbacks, and clear error semantics:

```typescript
@Injectable()
export class LoanApplicationService {
  async apply(dto: CreateLoanApplicationDto, applicantId: string): Promise<LoanApplication> {
    // Bureau pull — required; application cannot proceed without it
    let bureauReport: BureauReport;
    try {
      bureauReport = await this.bureauService.fetchCreditReport(dto.pan);
    } catch (err) {
      if (err instanceof BureauServiceUnavailableException) {
        // Bureau down — queue for manual processing rather than failing the customer
        await this.manualReviewQueue.enqueue({ dto, applicantId, reason: 'BUREAU_UNAVAILABLE' });
        throw new BureauUnavailableException('Application queued for review — bureau temporarily unavailable');
      }
      throw err; // unexpected error — rethrow
    }

    const loan = await this.loanRepository.create({ /* ... */ });

    // Notification — not required; failure should not roll back the loan
    try {
      await this.notificationService.sendApplicationReceived(applicantId, loan.id);
    } catch (err) {
      // Log but don't fail — loan is already created; notification can retry
      this.logger.error(`Failed to send application notification for loan ${loan.id}`, err);
    }

    return loan;
  }
}
```

The pattern: required external calls fail the whole operation (and may trigger fallback flows); optional side effects (notification, analytics) are best-effort and never roll back the primary operation.

## Section 4: Repository Layer in Depth

**Q12. What does a well-written Repository look like using Prisma in a NestJS app?**
A:

```typescript
@Injectable()
export class LoanRepository {
  constructor(private readonly prisma: PrismaService) {}

  // Always return domain objects, never Prisma entities
  async findById(id: string, tx?: PrismaTransactionClient): Promise<LoanApplication | null> {
    const client = tx ?? this.prisma;
    const record = await client.loan.findUnique({
      where: { id },
      include: {
        applicant: true,      // join needed for domain object construction
        conditions: true,
      },
    });
    return record ? this.toDomain(record) : null;
  }

  async findByApplicant(
    applicantId: string,
    filters: LoanListFilters,
  ): Promise<PaginatedResult<LoanApplication>> {
    const { page = 1, limit = 20, status, productCode } = filters;

    const [records, total] = await Promise.all([
      this.prisma.loan.findMany({
        where: {
          applicantId,
          ...(status && { status }),
          ...(productCode && { productCode }),
        },
        orderBy: { createdAt: 'desc' },
        skip: (page - 1) * limit,
        take: limit,
        include: { conditions: true },
      }),
      this.prisma.loan.count({
        where: {
          applicantId,
          ...(status && { status }),
          ...(productCode && { productCode }),
        },
      }),
    ]);

    return {
      data: records.map(r => this.toDomain(r)),
      total,
      page,
      limit,
      totalPages: Math.ceil(total / limit),
    };
  }

  async create(data: CreateLoanData, tx?: PrismaTransactionClient): Promise<LoanApplication> {
    const client = tx ?? this.prisma;
    const record = await client.loan.create({
      data: {
        applicantId: data.applicantId,
        productCode: data.productCode,
        requestedAmount: data.requestedAmount,  // stored in paise
        tenorMonths: data.tenorMonths,
        pan: data.pan,
        bureauScore: data.bureauScore,
        status: data.status,
      },
      include: { conditions: true },
    });
    return this.toDomain(record);
  }

  async updateStatus(
    id: string,
    status: LoanStatus,
    extra: Partial<LoanUpdateData> = {},
    tx?: PrismaTransactionClient,
  ): Promise<LoanApplication> {
    const client = tx ?? this.prisma;
    const record = await client.loan.update({
      where: { id },
      data: { status, ...this.toUpdatePersistence(extra) },
      include: { conditions: true },
    });
    return this.toDomain(record);
  }

  // --- Mapping methods — the translation responsibility ---
  private toDomain(record: PrismaLoanWithRelations): LoanApplication {
    return {
      id: record.id,
      applicantId: record.applicantId,
      productCode: record.productCode,
      requestedAmount: record.requestedAmount,
      tenorMonths: record.tenorMonths,
      pan: record.pan,
      bureauScore: record.bureauScore,
      status: record.status as LoanStatus,
      sanctionedAmount: record.sanctionedAmount ?? undefined,
      sanctionedBy: record.sanctionedBy ?? undefined,
      sanctionedAt: record.sanctionedAt ?? undefined,
      conditions: record.conditions.map(c => ({ id: c.id, description: c.description })),
      createdAt: record.createdAt,
      updatedAt: record.updatedAt,
    };
  }

  private toUpdatePersistence(extra: Partial<LoanUpdateData>): Partial<PrismaLoanUpdate> {
    return {
      ...(extra.sanctionedAmount !== undefined && { sanctionedAmount: extra.sanctionedAmount }),
      ...(extra.sanctionedBy !== undefined && { sanctionedBy: extra.sanctionedBy }),
      ...(extra.sanctionedAt !== undefined && { sanctionedAt: extra.sanctionedAt }),
      ...(extra.disbursedAmount !== undefined && { disbursedAmount: extra.disbursedAmount }),
    };
  }
}
```

**Q13. What is the Repository Interface pattern, and when should you use it?**
A: A Repository Interface (also called a Port) defines the contract that the service layer depends on, with the implementation in the infrastructure layer. This enables Dependency Inversion — the service depends on an abstraction, not a concrete class:

```typescript
// Interface — lives in the domain/application layer; no Prisma imports
export interface ILoanRepository {
  findById(id: string): Promise<LoanApplication | null>;
  findByApplicant(applicantId: string, filters: LoanListFilters): Promise<PaginatedResult<LoanApplication>>;
  create(data: CreateLoanData): Promise<LoanApplication>;
  updateStatus(id: string, status: LoanStatus, extra?: Partial<LoanUpdateData>): Promise<LoanApplication>;
}

export const LOAN_REPOSITORY = Symbol('ILoanRepository');

// Implementation — lives in the infrastructure layer; imports Prisma
@Injectable()
export class PrismaLoanRepository implements ILoanRepository {
  // ... (as shown in Q12)
}

// Module binding
@Module({
  providers: [
    { provide: LOAN_REPOSITORY, useClass: PrismaLoanRepository },
    LoanApplicationService,
  ],
})
export class LoanModule {}

// Service — depends on the interface via injection token
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject(LOAN_REPOSITORY) private readonly loanRepository: ILoanRepository,
  ) {}
}
```

**When to use it:** when you need to unit test services without a real database (inject an in-memory implementation), when you might switch database or ORM, or when building a codebase that respects DDD-style infrastructure isolation. For smaller projects or early-stage codebases, a direct `LoanRepository` class injection without an interface is acceptable — introduce the interface when you feel the pain of needing to mock the repository in tests.

**Q14. How do you prevent N+1 query problems in the Repository layer?**
A: N+1 is one of the most common repository-layer performance bugs. Identify and fix with eager loading:

```typescript
// ❌ N+1 problem — one query for loans, then N queries for each loan's conditions
async findByApplicant(applicantId: string): Promise<LoanApplication[]> {
  const loans = await this.prisma.loan.findMany({ where: { applicantId } });
  // Now iterating and calling findMany for each loan — N additional queries
  return Promise.all(loans.map(async loan => ({
    ...loan,
    conditions: await this.prisma.loanCondition.findMany({ where: { loanId: loan.id } }),
  })));
}

// ✅ Eager load with include — single query with JOIN
async findByApplicant(applicantId: string): Promise<LoanApplication[]> {
  const loans = await this.prisma.loan.findMany({
    where: { applicantId },
    include: {
      conditions: true,  // single JOIN query — no N+1
      applicant: { select: { name: true, pan: true } },
    },
  });
  return loans.map(this.toDomain);
}

// ✅ For complex scenarios — select only needed fields
async findSummariesByApplicant(applicantId: string): Promise<LoanSummary[]> {
  return this.prisma.loan.findMany({
    where: { applicantId },
    select: {
      id: true,
      status: true,
      requestedAmount: true,
      createdAt: true,
      // Deliberately exclude heavy fields (bureauReport, fullConditions)
    },
  });
}
```

## Section 5: Testing the CSR Stack

**Q15. How do you unit test each layer of the CSR stack?**
A: Each layer is tested in complete isolation — mock the layer below:

```typescript
// Unit test — Controller layer
// Mock the service; test that the controller routes and formats correctly
describe('LoanApplicationController', () => {
  let controller: LoanApplicationController;
  let mockService: jest.Mocked<LoanApplicationService>;

  beforeEach(async () => {
    mockService = {
      apply: jest.fn(),
      findById: jest.fn(),
      list: jest.fn(),
      sanction: jest.fn(),
    } as any;

    const module = await Test.createTestingModule({
      controllers: [LoanApplicationController],
      providers: [{ provide: LoanApplicationService, useValue: mockService }],
    }).compile();

    controller = module.get(LoanApplicationController);
  });

  it('should call service.apply and return the formatted response', async () => {
    const dto: CreateLoanApplicationDto = {
      productCode: 'HL-STD', requestedAmount: 4_500_000_00, tenorMonths: 180,
      pan: 'ABCDE1234F', employmentType: EmploymentType.SALARIED, monthlyIncome: 150_000_00,
    };
```

## Section 6: Common Anti-patterns and Pitfalls

**Q17. What are the most common CSR violations in a NestJS fintech codebase?**
A:

**Anti-pattern 1 — Fat Controller:**
```typescript
// ❌ Controller doing eligibility, bureau pull, and DB operations
@Post()
async apply(@Body() dto: CreateLoanApplicationDto, @CurrentUser() user: User) {
  if (dto.monthlyIncome < 25_000_00) throw new BadRequestException('Income too low'); // business rule
  const bureau = await this.bureauService.fetchCreditReport(dto.pan); // should be in service
  if (bureau.score < 650) throw new BadRequestException('Score too low'); // business rule
  const loan = await this.prisma.loan.create({ data: { ...dto, applicantId: user.id } }); // direct DB
  return loan; // returns ORM entity — no DTO
}
```

**Anti-pattern 2 — Service returning HTTP response objects:**
```typescript
// ❌ Service imports HTTP concerns
import { HttpException, HttpStatus } from '@nestjs/common'; // ← wrong in service layer
export class LoanApplicationService {
  async apply(dto, userId): Promise<Response> { // ← HTTP Response in service
    throw new HttpException('Score too low', HttpStatus.UNPROCESSABLE_ENTITY); // ← HTTP in service
  }
}
```

**Anti-pattern 3 — Business logic in the Repository:**
```typescript
// ❌ Repository deciding who can access data
async findByApplicant(applicantId: string, requestorRole: string): Promise<Loan[]> {
  if (requestorRole !== 'OFFICER') {
    // This is an access control decision — belongs in the service
    return this.prisma.loan.findMany({ where: { applicantId, status: { not: 'REJECTED' } } });
  }
  return this.prisma.loan.findMany({ where: { applicantId } });
}
```

**Anti-pattern 4 — Service directly calling another service's repository:**
```typescript
// ❌ LoanService imports ApplicantRepository directly — bypasses the Applicant service
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly applicantRepo: ApplicantRepository, // ← wrong cross-service repo access
  ) {}
}

// ✅ Fix — call the Applicant service API instead
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly applicantService: ApplicantService, // ← correct cross-service access
  ) {}
}
```

**Anti-pattern 5 — The "god service" accumulating all operations:**
```typescript
// ❌ One service that handles application, underwriting, disbursement, collections
export class LoanService {
  apply() { /* 50 lines */ }
  underwrite() { /* 80 lines */ }
  disburse() { /* 60 lines */ }
  collectEmi() { /* 70 lines */ }
  handleNachFailure() { /* 90 lines */ }
  generateRbiReport() { /* 100 lines */ }
  // ... 450+ lines and growing
}
```

**Q18. How do you enforce CSR layer boundaries automatically in a codebase?**
A: Use ESLint import rules and NestJS module boundaries to make violations a CI failure:

```javascript
// .eslintrc.js — enforce layer boundaries
module.exports = {
  rules: {
    'no-restricted-imports': ['error', {
      patterns: [
        {
          // Controllers must not import from repositories
          group: ['**/repositories/**'],
          importNamePattern: 'Repository',
          message: 'Controllers must not directly import repositories. Use services.',
        },
        {
          // Services must not import from @nestjs/common HTTP exceptions
          // (they should use domain exceptions)
          group: ['@nestjs/common'],
          importNamePattern: 'HttpException|BadRequestException|NotFoundException',
          message: 'Services must throw domain exceptions, not HTTP exceptions.',
        },
        {
          // Repositories must not import from services
          group: ['**/services/**'],
          importNamePattern: 'Service',
          message: 'Repositories must not import from services (circular dependency).',
        },
      ],
    }],
  },
};
```


## Section 7: Scenario / System Design Questions

**Q19. "You're onboarding a junior developer who asks: 'Should the CIBIL bureau pull happen in the controller, service, or repository? And what if the bureau is down — where does the retry logic live?' Walk them through the reasoning."**
A: A structured answer that demonstrates understanding of each layer's responsibility:

**Where does the bureau pull happen?** The Service layer — unambiguously. The reasoning at each layer:
- **Not the controller** — controllers know nothing about external APIs. If you put the bureau call in the controller, changing from CIBIL to Experian requires touching the HTTP layer. Controllers also can't be tested without the bureau API being available.
- **Not the repository** — repositories talk to *your* database. A bureau API is an external service with its own contract, rate limits, and failure modes — entirely different concern from persistence.
- **The service** — the service orchestrates business operations. The bureau pull is part of the "apply for a loan" use case: validate eligibility → pull bureau → assess score → create application. This orchestration lives in the service.

**Where does retry logic live?** The retry logic has two homes depending on what it's retrying:
- **Infrastructure-level retry** (transient network failures, 503s) — wraps the bureau HTTP client at the **infrastructure/adapter layer**, not the service. The bureau adapter handles retries transparently; the service just calls `bureauService.fetchCreditReport()` and either gets a result or a terminal exception.
- **Business-level retry** (bureau is down — queue for manual review) — the service handles this because it's a business decision: "when bureau is unavailable, we queue for manual review rather than failing the application."

```typescript
// Service — business decision about what happens when bureau is unavailable
async apply(dto, userId): Promise<LoanApplication> {
  let bureauReport: BureauReport;
  try {
    bureauReport = await this.bureauService.fetchCreditReport(dto.pan);
  } catch (e) {
    if (e instanceof BureauUnavailableException) {
      await this.manualReviewQueue.enqueue({ dto, userId });
      throw new ApplicationQueuedForReviewException();
    }
    throw e;
  }
  // ...
}

// BureauService (infrastructure adapter) — technical retry for transient errors
class CibilBureauAdapter implements BureauService {
  async fetchCreditReport(pan: string): Promise<BureauReport> {
    return retry(
      () => this.httpClient.get(`/report/${pan}`),
      { retries: 3, delay: 200, factor: 2 }, // exponential backoff
    );
  }
}
```

**Q20. "Your loan service currently has a single `LoanService` class with 800 lines. You're tasked with refactoring it. What's your approach?"**
A: Refactor by splitting along use case / business capability boundaries — not by technical concerns:

**Step 1 — Identify the use cases** (read through the service methods):
- `apply`, `withdraw` → loan origination
- `sendForReview`, `requestAdditionalDocs`, `sanction`, `reject` → loan underwriting
- `disburse`, `confirmDisbursement` → disbursement
- `recordEmiCollection`, `recordEmiFailure`, `scheduleRetry` → collections
- `generateStatement`, `exportPortfolio` → reporting

**Step 2 — Extract into focused services:**
```
loan/
  services/
    loan-origination.service.ts     (apply, withdraw)
    loan-underwriting.service.ts    (review, sanction, reject)
    loan-disbursement.service.ts    (disburse, confirm)
    loan-collection.service.ts      (collectEmi, handleFailure)
    loan-reporting.service.ts       (statement, export)
```

**Step 3 — Extract shared domain logic** into helper services or domain objects:
- Eligibility rules → `LoanEligibilityService`
- EMI calculation → `EmiCalculator` (pure function / domain service)
- Status transition validation → `LoanStatusMachine` (or on the domain entity)

**Step 4 — Update controllers** to inject the specific service they need:
```typescript
@Controller('loan-applications')
export class LoanApplicationController {
  constructor(
    private readonly originationService: LoanOriginationService,
    private readonly underwritingService: LoanUnderwritingService,
  ) {}
  // ...
}
```

Each service is now 100–150 lines, has one set of injected dependencies, and is owned by one team (Originations team owns `LoanOriginationService`; Credit team owns `LoanUnderwritingService`).

**Q21. "A performance review shows the `GET /loans` endpoint for an ops dashboard takes 800ms. The controller calls the service, which calls the repository, which runs a complex multi-join query. Where is the bottleneck and how do you fix it?"**
A: Diagnose first, then fix at the right layer:

**Diagnosis:**
```typescript
// Add timing at each layer boundary
async list(filters: LoanListFilters): Promise<PaginatedResult<LoanApplication>> {
  const t1 = Date.now();
  const result = await this.loanRepository.findAll(filters); // this is the suspect
  this.logger.debug(`Repository query: ${Date.now() - t1}ms`); // if 780ms → DB is the bottleneck
  return result;
}
```

**Common causes and fixes at the repository layer:**
```typescript
// Fix 1 — Missing index
// Run EXPLAIN ANALYZE on the query — missing index on (applicant_id, status, created_at)
// Add: CREATE INDEX CONCURRENTLY idx_loans_applicant_status ON loans(applicant_id, status, created_at);

// Fix 2 — Loading all relations when only IDs are needed (over-fetching)
// ❌ Loading all conditions for list view
const loans = await this.prisma.loan.findMany({
  include: { conditions: true, applicant: true, emiSchedule: true }, // too much for a list
});

// ✅ Use select for list views; include only for detail views
const loans = await this.prisma.loan.findMany({
  select: {
    id: true, status: true, requestedAmount: true, createdAt: true,
    applicant: { select: { name: true } }, // minimal join — name only
  },
});

// Fix 3 — If the query is fundamentally a reporting query (cross-domain aggregation)
// → Move to a dedicated read model / CQRS query side (not a service/repo fix)
// → Pre-aggregate into a projection table; the repository query becomes trivial
```

If the fix requires a separate read model, introduce a lightweight CQRS read query alongside the existing CSR stack — you don't need to convert the entire service.

## Quick Reference: CSR Responsibility Matrix

| Concern                                     | Controller | Service | Repository |
|---------------------------------------------|:----------:|:-------:|:----------:|
| Parse HTTP request body                     | ✅         | ❌       | ❌         |
| Validate input format (email, PAN, UUID)    | ✅         | ❌       | ❌         |
| Authenticate / authorise (JWT, roles)       | ✅         | ❌       | ❌         |
| Format HTTP response / status codes         | ✅         | ❌       | ❌         |
| Enforce business rules (LTV, income limits) | ❌         | ✅       | ❌         |
| Orchestrate multiple repos/services         | ❌         | ✅       | ❌         |
| Manage transaction boundaries               | ❌         | ✅       | ❌         |
| Call external APIs (bureau, SMS, payment)   | ❌         | ✅       | ❌         |
| Publish domain events                       | ❌         | ✅       | ❌         |
| Write SQL / ORM queries                     | ❌         | ❌       | ✅         |
| Map ORM entities to domain objects          | ❌         | ❌       | ✅         |
| Handle pagination at the DB level           | ❌         | ❌       | ✅         |
| Manage DB connection / transaction client   | ❌         | ❌       | ✅         |

---

**Tip for the interview:** At the 5 YOE level, CSR questions come as code review scenarios ("what's wrong with this controller?"), refactoring tasks ("this service is 800 lines — how do you split it?"), or design questions ("where does the CIBIL pull go?"). The differentiating answer isn't just knowing the three layers — it's demonstrating boundary discipline: knowing that `HttpException` in a service is a smell, that `prisma.loan.findMany` in a controller is a smell, and that `if (income < 25000)` in a repository is a smell. The senior signal is explaining *why* each violation matters — not just "it's in the wrong layer" but "it means I can't unit test the service without an HTTP server, I can't change the eligibility rule without touching the data layer, I can't swap from REST to gRPC without rewriting business logic." In a fintech codebase specifically, the patterns that land are around the bureau pull (service layer, with infrastructure-level retry in the adapter), transaction coordination for disbursement (service declares atomicity, repository accepts an optional transaction client), and splitting a god service into use-case-aligned focused services.
