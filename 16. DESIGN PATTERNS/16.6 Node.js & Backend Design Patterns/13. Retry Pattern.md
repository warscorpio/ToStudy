# Node.js & Backend Design Patterns: Retry Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Retry Pattern?**
A: The Retry Pattern is a resilience pattern that **automatically re-attempts a failed operation** after a brief delay, on the assumption that the failure is transient — caused by a momentary network blip, a temporarily overloaded service, or a brief infrastructure hiccup — and will not be present on the next attempt. Rather than surfacing the failure immediately to the caller, the system transparently tries again up to a configured maximum, then gives up and propagates the final failure if all attempts are exhausted.

The three configurable dimensions of any retry implementation:
- **Max attempts** — how many total tries (including the first) before giving up.
- **Delay strategy** — how long to wait between attempts (fixed, linear backoff, exponential backoff).
- **Retry predicate** — which failure conditions are retryable and which are not (a 503 is retryable; a 401 Unauthorized is not).

**Q2. What is the core assumption behind the Retry Pattern, and when does it break down?**
A: The core assumption is **transience** — the failure is temporary and self-healing. The pattern breaks down when this assumption is violated:

- **Retrying a non-transient error** — a 400 Bad Request or 422 Unprocessable Entity means the request itself is malformed or violates business rules. Retrying it 3 times produces the same error 3 times; you've wasted time and made 3 unnecessary API calls.
- **Retrying a non-idempotent operation** — if the operation has side effects (charging a card, creating a NACH debit record, disbursing money) and you can't confirm whether the first attempt succeeded before retrying, you may execute the operation multiple times. This is the most dangerous Retry mistake in fintech.
- **Amplifying an overloaded downstream** — if a service is down because it's overloaded, retrying without a delay (or with many callers retrying simultaneously) makes it worse. This is why exponential backoff with jitter is essential.
- **Retrying after a circuit is open** — if the downstream has been failing consistently, retrying blindly is futile. The Circuit Breaker pattern complements Retry by stopping retries when a service is definitively down.

**Q3. What is exponential backoff, and why is it preferred over fixed-delay retry?**
A: Exponential backoff increases the wait time between retries geometrically — each delay is a multiple of the previous one:

```
Attempt 1: fails  → wait 200ms
Attempt 2: fails  → wait 400ms
Attempt 3: fails  → wait 800ms
Attempt 4: fails  → wait 1600ms
...give up
```

versus fixed delay:
```
Attempt 1: fails  → wait 200ms
Attempt 2: fails  → wait 200ms
Attempt 3: fails  → wait 200ms
```

Why exponential backoff wins:
- **Adaptive to recovery time** — a service recovering from a restart needs a few seconds, not a few hundred milliseconds. Exponential backoff gives the downstream progressively more time.
- **Reduced load on recovering services** — fixed-delay retries hit a recovering service with constant pressure; exponential backoff reduces the retry rate as the service takes longer to recover.
- **Bounded total retry time** — exponential backoff with a cap makes the worst-case total wait predictable: `initialDelay * (2^maxAttempts - 1)`.

**Q4. What is jitter, and why is it critical in distributed systems?**
A: Jitter is **randomness added to the retry delay** to prevent multiple clients from retrying at exactly the same time (the "thundering herd" or "retry storm" problem).

Without jitter: if 1,000 requests hit a service simultaneously, all fail at t=0, all retry at t=200ms, all fail again at t=200ms, all retry at t=400ms... The load spike is synchronized and the service never gets a clear recovery window.

With jitter: retries are spread randomly across the delay window, staggering the load:

```typescript
// Fixed backoff — every caller retries at exactly the same time
const delay = baseDelay * 2 ** attempt;

// Full jitter — retry time is random within [0, delay]
const delay = Math.random() * baseDelay * 2 ** attempt;

// Equal jitter (balanced — keeps some backoff while adding spread)
const halfDelay = baseDelay * 2 ** attempt / 2;
const delay = halfDelay + Math.random() * halfDelay;

// Decorrelated jitter (AWS recommendation)
let prevDelay = baseDelay;
const delay = Math.min(maxDelay, Math.random() * (prevDelay * 3 - baseDelay) + baseDelay);
prevDelay = delay;
```

In a fintech platform where hundreds of concurrent loan applications all hit the bureau API, a CIBIL outage without jitter produces synchronized retry storms that keep CIBIL overloaded. With jitter, the retry load is smoothed across time.

**Q5. What is the difference between retrying at the infrastructure layer vs the application layer?**
A:

| Aspect               | Infrastructure-level retry                              | Application-level retry                                |
|----------------------|---------------------------------------------------------|--------------------------------------------------------|
| Location             | HTTP client config, Axios interceptor, cloud SDK        | Service method, use-case code                          |
| Scope                | All calls through that HTTP client                      | Specific operations explicitly configured              |
| Idempotency awareness| None — retries blindly                                  | Can check idempotency before retrying                  |
| Business logic       | None — retries on any transient HTTP error              | Can implement custom retry predicates                  |
| Transparency         | Invisible to calling code                               | Visible — calling code controls retry behaviour        |
| Best for             | Transient network errors (timeout, 503)                 | Complex retry logic, idempotency keys, fallback flows  |

In practice, both are used together: an Axios interceptor handles low-level network retries transparently, while the service layer handles higher-level retries with idempotency awareness for critical operations like NACH debit or disbursement.

## Section 2: Implementation

**Q6. How do you implement a reusable retry utility in TypeScript?**
A:

```typescript
// Retry configuration
interface RetryConfig {
  maxAttempts: number;
  initialDelayMs: number;
  backoffFactor: number;       // 2 = exponential; 1 = fixed
  maxDelayMs: number;          // cap on delay regardless of backoff
  jitter: boolean;
  retryOn?: (error: Error) => boolean; // custom predicate; default: retry all
  onRetry?: (error: Error, attempt: number, delayMs: number) => void; // hook for logging
}

const DEFAULT_RETRY_CONFIG: RetryConfig = {
  maxAttempts: 3,
  initialDelayMs: 200,
  backoffFactor: 2,
  maxDelayMs: 10_000,
  jitter: true,
};

async function withRetry<T>(
  operation: () => Promise<T>,
  config: Partial<RetryConfig> = {},
): Promise<T> {
  const cfg = { ...DEFAULT_RETRY_CONFIG, ...config };
  let lastError: Error;

  for (let attempt = 1; attempt <= cfg.maxAttempts; attempt++) {
    try {
      return await operation();
    } catch (err) {
      lastError = err as Error;

      // Check if error is retryable
      if (cfg.retryOn && !cfg.retryOn(lastError)) {
        throw lastError; // non-retryable — fail immediately
      }

      // Last attempt — don't delay; just throw
      if (attempt === cfg.maxAttempts) break;

      // Compute delay with exponential backoff + optional jitter
      const baseDelay = Math.min(
        cfg.initialDelayMs * cfg.backoffFactor ** (attempt - 1),
        cfg.maxDelayMs,
      );
      const delay = cfg.jitter
        ? Math.random() * baseDelay  // full jitter
        : baseDelay;

      cfg.onRetry?.(lastError, attempt, delay);
      await sleep(delay);
    }
  }

  throw lastError!;
}

const sleep = (ms: number) => new Promise(res => setTimeout(res, ms));

// Usage
const report = await withRetry(
  () => bureauClient.fetchReport(pan),
  {
    maxAttempts: 3,
    initialDelayMs: 300,
    backoffFactor: 2,
    jitter: true,
    retryOn: isTransientError,
    onRetry: (err, attempt, delay) =>
      logger.warn(`Bureau retry attempt ${attempt}: ${err.message} — waiting ${delay.toFixed(0)}ms`),
  },
);
```

**Q7. How do you implement a retry predicate that correctly classifies retryable vs non-retryable errors?**
A: The retry predicate is the most critical part of any retry implementation — retrying the wrong errors wastes time and causes side effects:

```typescript
// HTTP-level retry predicate — for Axios/HTTP client errors
function isRetryableHttpError(error: Error): boolean {
  if (error instanceof AxiosError) {
    const status = error.response?.status;

    // Never retry these — they indicate a fundamental problem with the request
    const NON_RETRYABLE = [
      400, // Bad Request — malformed request; retrying won't help
      401, // Unauthorized — auth token expired; retry won't fix, need new token
      403, // Forbidden — no permission; retrying won't help
      404, // Not Found — resource doesn't exist; retrying won't help
      409, // Conflict — duplicate/state conflict; retrying may create duplicates
      410, // Gone — resource permanently deleted
      422, // Unprocessable Entity — business validation failure
      429, // Too Many Requests — rate limited; retry requires waiting much longer
    ];

    if (status && NON_RETRYABLE.includes(status)) return false;

    // Retry these — server-side transient errors
    const RETRYABLE = [
      408, // Request Timeout
      500, // Internal Server Error (sometimes transient)
      502, // Bad Gateway
      503, // Service Unavailable
      504, // Gateway Timeout
    ];

    if (status && RETRYABLE.includes(status)) return true;

    // Network-level errors (no response received)
    if (!error.response) return true; // ECONNRESET, ETIMEDOUT, ENOTFOUND

    return false;
  }

  // Non-HTTP errors — retry on transient-sounding ones
  const RETRYABLE_CODES = ['ECONNRESET', 'ETIMEDOUT', 'ECONNREFUSED', 'EPIPE'];
  return RETRYABLE_CODES.includes((error as NodeJS.ErrnoException).code ?? '');
}

// Domain-level retry predicate — bureau-specific error codes
function isCibilRetryableError(error: Error): boolean {
  if (error instanceof CibilApiException) {
    const RETRYABLE_CODES = [
      'TIMEOUT',
      'SERVICE_UNAVAILABLE',
      'GATEWAY_ERROR',
      'INTERNAL_ERROR',
    ];
    const NON_RETRYABLE_CODES = [
      'INVALID_PAN',           // data problem — retrying won't fix
      'CONSUMER_NOT_FOUND',    // legitimate no-data response — not an error
      'AUTHENTICATION_FAILED', // credentials problem — retrying won't fix
      'RATE_LIMIT_EXCEEDED',   // need to back off much longer than normal retry
    ];
    if (NON_RETRYABLE_CODES.includes(error.code)) return false;
    if (RETRYABLE_CODES.includes(error.code)) return true;
  }
  return isRetryableHttpError(error);
}
```

**Q8. How do you implement retry using Axios interceptors for all HTTP calls through a client?**
A: An Axios interceptor applies retry transparently to all calls through a specific Axios instance:

```typescript
import axios, { AxiosInstance, AxiosRequestConfig } from 'axios';

// Extend AxiosRequestConfig to track retry state
interface RetryableAxiosConfig extends AxiosRequestConfig {
  _retryCount?: number;
  _retryConfig?: Partial<RetryConfig>;
}

function createRetryableAxiosClient(baseConfig: AxiosRequestConfig, retryConfig: Partial<RetryConfig> = {}): AxiosInstance {
  const client = axios.create(baseConfig);
  const cfg = { ...DEFAULT_RETRY_CONFIG, ...retryConfig };

  client.interceptors.response.use(
    response => response, // pass through on success
    async (error: AxiosError) => {
      const config = error.config as RetryableAxiosConfig;

      if (!config) throw error;

      config._retryCount = config._retryCount ?? 0;

      // Check if we should retry
      const shouldRetry =
        config._retryCount < cfg.maxAttempts - 1 &&
        (cfg.retryOn ? cfg.retryOn(error) : isRetryableHttpError(error));

      if (!shouldRetry) throw error;

      config._retryCount++;

      const baseDelay = Math.min(
        cfg.initialDelayMs * cfg.backoffFactor ** (config._retryCount - 1),
        cfg.maxDelayMs,
      );
      const delay = cfg.jitter ? Math.random() * baseDelay : baseDelay;

      cfg.onRetry?.(error, config._retryCount, delay);
      await sleep(delay);

      return client.request(config); // re-issue the request
    },
  );

  return client;
}

// Create bureau-specific HTTP client with retry pre-configured
@Injectable()
export class CibilHttpClient {
  private readonly client: AxiosInstance;

  constructor(private readonly logger: Logger) {
    this.client = createRetryableAxiosClient(
      {
        baseURL: process.env.CIBIL_BASE_URL,
        timeout: 10_000,
        headers: { Authorization: `Bearer ${process.env.CIBIL_API_KEY}` },
      },
      {
        maxAttempts: 3,
        initialDelayMs: 500,
        backoffFactor: 2,
        jitter: true,
        retryOn: isCibilRetryableError,
        onRetry: (err, attempt, delay) =>
          this.logger.warn(`CIBIL retry ${attempt}: ${err.message} — ${delay.toFixed(0)}ms`),
      },
    );
  }

  async get<T>(path: string): Promise<T> {
    const response = await this.client.get<T>(path);
    return response.data;
  }
}
```

**Q9. How do you implement retry with idempotency keys for non-idempotent financial operations?**
A: For operations with side effects (NACH debit, payment disbursement), retry requires an idempotency key to ensure the operation executes at most once even if the request is sent multiple times:

```typescript
interface IdempotentRetryConfig extends RetryConfig {
  idempotencyKey: string;
  idempotencyStore: IIdempotencyStore;
}

// Idempotent retry — check store before each attempt
async function withIdempotentRetry<T>(
  operation: (idempotencyKey: string) => Promise<T>,
  config: IdempotentRetryConfig,
): Promise<T> {
  const { idempotencyKey, idempotencyStore, ...retryConfig } = config;

  // Check if a previous attempt already succeeded
  const stored = await idempotencyStore.get(idempotencyKey);
  if (stored?.status === 'SUCCESS') {
    return stored.result as T; // return the stored result — operation already completed
  }

  let lastError: Error;

  for (let attempt = 1; attempt <= retryConfig.maxAttempts; attempt++) {
    try {
      // Pass idempotency key to the operation — the downstream uses it to deduplicate
      const result = await operation(idempotencyKey);

      // Store success result — future retries return this immediately
      await idempotencyStore.set(idempotencyKey, {
        status: 'SUCCESS',
        result,
        completedAt: new Date(),
      }, { ttlSeconds: 86400 });

      return result;
    } catch (err) {
      lastError = err as Error;

      if (!(retryConfig.retryOn?.(lastError) ?? true)) throw lastError;
      if (attempt === retryConfig.maxAttempts) break;

      const delay = computeDelay(retryConfig, attempt);
      await sleep(delay);
    }
  }

  // Store failure — allows caller to inspect the final state
  await idempotencyStore.set(idempotencyKey, {
    status: 'FAILED',
    error: lastError!.message,
    failedAt: new Date(),
  }, { ttlSeconds: 3600 });

  throw lastError!;
}

// Usage — NACH debit with idempotency
@Injectable()
export class NachDebitService {
  async debitEmi(loanId: string, emiMonth: string, amount: number): Promise<NachDebitResult> {
    // Idempotency key uniquely identifies this specific debit attempt
    // Format: loan + month + attempt number (from retry schedule)
    const idempotencyKey = `NACH:${loanId}:${emiMonth}`;

    return withIdempotentRetry(
      async (key: string) => this.npciClient.initiateDebit({
        umrn: await this.getMandateUrn(loanId),
        amount,
        purpose: `EMI ${emiMonth} - Loan ${loanId}`,
        idempotencyKey: key,  // NPCI uses this to deduplicate on their side
      }),
      {
        idempotencyKey,
        idempotencyStore: this.idempotencyStore,
        maxAttempts: 2,           // conservative — financial operations retry less
        initialDelayMs: 1000,
        backoffFactor: 2,
        jitter: true,
        retryOn: isNachRetryableError,
      },
    );
  }
}
```

## Section 3: Retry in a Fintech/Lending Platform

**Q10. How do you apply the Retry Pattern to CIBIL bureau API calls in a lending platform?**
A: Bureau API calls are classic retry candidates — they're read-only (idempotent), transient failures are common, and the consequence of failure (not approving a loan application) is significant:

```typescript
@Injectable()
export class CibilBureauAdapter implements IBureauAdapter {
  constructor(
    private readonly httpClient: CibilHttpClient,
    private readonly logger: Logger,
    private readonly metrics: MetricsService,
  ) {}

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const start = Date.now();

    try {
      const raw = await withRetry(
        () => this.httpClient.get<CibilRawResponse>(`/report/${pan}`),
        {
          maxAttempts: 3,
          initialDelayMs: 500,
          backoffFactor: 2,
          maxDelayMs: 5_000,
          jitter: true,
          retryOn: isCibilRetryableError,
          onRetry: (err, attempt, delay) => {
            this.logger.warn({
              message: 'CIBIL API retry',
              pan: pan.slice(0, 5) + '****', // masked for logs
              attempt,
              delayMs: Math.round(delay),
              error: err.message,
            });
            this.metrics.increment('bureau.cibil.retry', { attempt: String(attempt) });
          },
        },
      );

      this.metrics.record('bureau.cibil.latency', Date.now() - start);
      return this.mapToDomain(raw);
    } catch (err) {
      this.metrics.increment('bureau.cibil.failure');
      this.logger.error({ message: 'CIBIL API permanently failed', pan: pan.slice(0, 5) + '****', error: (err as Error).message });
      throw new BureauUnavailableException('CIBIL', err as Error);
    }
  }
}
```

**Q11. How do you apply Retry to NACH debit operations safely?**
A: NACH debits are the most dangerous retry scenario in lending — retrying a successful debit that just timed out before the response arrived causes a double debit. The pattern requires NPCI-side idempotency, careful failure classification, and conservative retry counts:

```typescript
@Injectable()
export class NachDebitAdapter {
  // Failure codes that are DEFINITELY safe to retry (operation definitively failed on NPCI's side)
  private readonly SAFE_TO_RETRY = new Set([
    'TIMEOUT',             // NPCI didn't process it
    'GATEWAY_ERROR',       // NPCI gateway rejected before processing
    'NETWORK_ERROR',       // never reached NPCI
  ]);

  // Failure codes that are AMBIGUOUS — may or may not have been processed
  private readonly AMBIGUOUS_FAILURES = new Set([
    'CONNECTION_RESET',    // request may have reached NPCI — check status before retrying
    'RESPONSE_TIMEOUT',    // NPCI processed it but response was lost — NEVER retry directly
  ]);

  async debitEmi(mandate: NachMandate, emi: EmiSchedule): Promise<NachDebitResult> {
    const idempotencyKey = `${mandate.umrn}-${emi.month}-${emi.year}`;

    // Step 1 — check if this debit was already initiated (idempotency check)
    const existing = await this.npciClient.checkStatus(idempotencyKey);
    if (existing?.status === 'SUCCESS') {
      return { success: true, rrn: existing.rrn, idempotent: true };
    }

    let lastError: Error;

    for (let attempt = 1; attempt <= 2; attempt++) { // max 2 attempts for financial ops
      try {
        const result = await this.npciClient.initiateDebit({
          umrn: mandate.umrn,
          amount: emi.amount,
          purpose: `EMI ${emi.month}/${emi.year}`,
          idempotencyKey,  // NPCI honours this — safe to resend
        });
        return { success: result.status === 'SUCCESS', rrn: result.rrn };
      } catch (err) {
        lastError = err as NachApiException;

        if (this.AMBIGUOUS_FAILURES.has((lastError as NachApiException).code)) {
          // Ambiguous — check NPCI's status before deciding to retry
          const statusCheck = await this.npciClient.checkStatus(idempotencyKey);
          if (statusCheck?.status === 'SUCCESS') {
            return { success: true, rrn: statusCheck.rrn, recovered: true };
          }
          // Confirmed not processed — safe to retry IF it's the first attempt
        }

        if (!this.SAFE_TO_RETRY.has((lastError as NachApiException).code)) {
          throw lastError; // non-retryable NACH failure — surface immediately
        }

        if (attempt < 2) {
          await sleep(2000 + Math.random() * 1000); // 2–3 seconds, jittered
        }
      }
    }

    throw lastError!;
  }
}
```

**Q12. How do you apply Retry to disbursement operations (NEFT/RTGS/IMPS) via payment gateways?**
A: Disbursement retries require distinguishing between "definitely failed" (safe to retry with same idempotency key) and "unknown" (must check gateway status before retrying):

```typescript
@Injectable()
export class DisbursementAdapter {
  async initiateDisbursement(

    bankDetails: BankDetails,
  ): Promise<DisbursementResult> {
    const referenceId = `DISB-${loan.id}-${Date.now()}`; // unique per disbursement attempt

          return await this.razorpayClient.payouts.create({
            amount: loan.sanctionedAmount,
            currency: 'INR',

            reference_id: referenceId,  // Razorpay deduplicates on reference_id
            fund_account: { /* bank details */ },

            const existing = await this.razorpayClient.payouts.fetchByReferenceId(referenceId);

        maxAttempts: 2,         // conservative for money movement
        initialDelayMs: 2000,   // longer initial delay for payment systems

  }
```

**Q14. How do you apply Retry to Redis/database operations in a lending platform?**

```typescript
@Injectable()
export class RateLimiterService {
  private readonly KEY_PREFIX = 'rate:bureau:';

  async checkAndIncrement(pan: string): Promise<{ allowed: boolean; remaining: number }> {
    const key = `${this.KEY_PREFIX}${pan}`;

    return withRetry(
      async () => {
        const pipeline = this.redis.pipeline();
        pipeline.incr(key);
        pipeline.ttl(key);
        const results = await pipeline.exec();

        if (!results) throw new Error('Redis pipeline returned null');

        const count = results[0][1] as number;
        const ttl = results[1][1] as number;

        // Set expiry on first call
        if (ttl === -1) await this.redis.expire(key, 60);

        return { allowed: count <= 10, remaining: Math.max(0, 10 - count) };
      },
      {
        maxAttempts: 3,
        initialDelayMs: 10,   // very short — Redis failure is unusual; resolve fast
        backoffFactor: 2,
        maxDelayMs: 100,
        jitter: true,
        retryOn: (err) => {
          const code = (err as NodeJS.ErrnoException).code;
          return ['ECONNRESET', 'ETIMEDOUT', 'ECONNREFUSED'].includes(code ?? '');
        },
      },
    );
  }
}
```

## Section 4: Retry with Circuit Breaker

**Q15. How do Retry and Circuit Breaker work together, and why is Circuit Breaker needed?**
A: Retry and Circuit Breaker solve different problems and work as complementary patterns:

- **Retry** — handles occasional transient failures by re-attempting. Assumes failure is the exception.
- **Circuit Breaker** — stops retrying when a service is persistently unavailable. Assumes failure is now the norm (circuit "open"); allows the service to recover without being hammered.

Without a Circuit Breaker, Retry during a prolonged outage means every request generates `maxAttempts` calls to the failing service, multiplying the load instead of reducing it. With a Circuit Breaker:

```
Normal → CLOSED state: all requests pass through (retry on transient errors)
Failure threshold hit → OPEN state: all requests fail fast (no calls to downstream)
After recovery timeout → HALF-OPEN: allow one probe request
Probe succeeds → back to CLOSED
Probe fails → back to OPEN
```

```typescript
type CircuitState = 'CLOSED' | 'OPEN' | 'HALF_OPEN';

@Injectable()
export class CibilCircuitBreaker {
  private state: CircuitState = 'CLOSED';
  private failureCount = 0;
  private lastFailureAt = 0;

  private readonly FAILURE_THRESHOLD = 5;    // open after 5 consecutive failures
  private readonly RECOVERY_TIMEOUT = 30_000; // try again after 30 seconds

  async call<T>(operation: () => Promise<T>): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureAt < this.RECOVERY_TIMEOUT) {
        throw new CircuitOpenException('CIBIL circuit breaker is OPEN');
      }
      this.state = 'HALF_OPEN';
    }

    try {
      const result = await operation();
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure();
      throw err;
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureAt = Date.now();
    if (this.failureCount >= this.FAILURE_THRESHOLD) {
      this.state = 'OPEN';
      this.logger.error(`CIBIL circuit breaker OPENED after ${this.failureCount} failures`);
      this.alertService.sendCritical('CIBIL circuit breaker OPEN — bureau calls failing fast');
    }
  }
}

// Combining Retry + Circuit Breaker
@Injectable()
export class CibilBureauService {
  async fetchReport(pan: string): Promise<CreditReport> {
    // Circuit breaker wraps retry — if circuit is open, no retry attempts are made
    return this.circuitBreaker.call(
      () => withRetry(
        () => this.httpClient.get(`/report/${pan}`),
        {
          maxAttempts: 3,
          initialDelayMs: 500,
          backoffFactor: 2,
          jitter: true,
          retryOn: isCibilRetryableError,
        },
      ),
    );
  }
}
```

**Q16. What is the difference between retry at the call site vs retry in the adapter/infrastructure layer?**
A: The placement determines what the retry applies to and who controls it:

**Retry in the adapter/infrastructure layer (preferred for external integrations):**
```typescript
// CibilBureauAdapter handles retry transparently
@Injectable()
export class CibilBureauAdapter implements IBureauAdapter {
  async fetchCreditReport(pan: string): Promise<CreditReport> {
    // Retry is an infrastructure concern — hidden from the service layer

      () => this.httpClient.get(`/report/${pan}`),
      { maxAttempts: 3, /* ... */ },
    );
  }
}

// Service layer has no retry logic — it just calls the adapter
@Injectable()
export class LoanApplicationService {
  async apply(dto: CreateLoanApplicationDto): Promise<LoanApplication> {
    const report = await this.bureauAdapter.fetchCreditReport(dto.pan); // clean; no retry noise
    // ...
  }
}
```

**Retry at the call site (appropriate for complex, business-decision-driven retry):**
```typescript
// Service layer controls retry when it needs to make business decisions mid-retry
@Injectable()
export class CollectionsService {
  async retryFailedNachDebit(loan: DelinquentLoan): Promise<void> {
    // Business decision: retry schedule is based on failure code — not just transience
    const retryConfig = this.retryPolicyFactory.for(loan.lastFailureCode);

    await withRetry(
      () => this.nachAdapter.debitEmi(loan.mandateUrn, loan.emiDue),
      {
        maxAttempts: retryConfig.maxAttempts,
        initialDelayMs: retryConfig.delayMs,
        retryOn: isNachRetryableError,
        onRetry: async (err, attempt) => {
          // Business side effect on each retry — update DPD, notify customer
          await this.loanRepository.incrementRetryCount(loan.id);

            await this.notificationService.sendSecondRetryWarning(loan.applicantId);
          }
        },
      },
    );
  }
}
```

```typescript
describe('withRetry', () => {
```

## Section 6: Anti-patterns and Pitfalls

**Q19. What are the most dangerous Retry Pattern mistakes in a fintech codebase?**
A:

**Mistake 1 — Retrying non-idempotent operations without idempotency keys:**
```typescript
// ❌ Retrying a NACH debit without any deduplication — may double-debit the customer
await withRetry(
  () => this.npciClient.initiateDebit({ umrn, amount, purpose }),
  { maxAttempts: 3 }, // NEVER retry financial operations without idempotency keys
);

// ✅ Fix — always use an idempotency key
await withRetry(
  () => this.npciClient.initiateDebit({ umrn, amount, purpose, idempotencyKey: `${umrn}-${emiMonth}` }),
  { maxAttempts: 2, retryOn: isDefinitelySafeToRetry },
);
```

**Mistake 2 — Retrying all errors without a predicate:**
```typescript
// ❌ Retry everything — wastes time on 400/404/422/401
await withRetry(
  () => this.bureauService.fetchReport(pan),
  { maxAttempts: 3 }, // no retryOn predicate — retries validation errors
);

// ✅ Fix — always provide a predicate
await withRetry(
  () => this.bureauService.fetchReport(pan),
  { maxAttempts: 3, retryOn: isCibilRetryableError },
);
```

**Mistake 3 — Retry without backoff (hammering a recovering service):**
```typescript
// ❌ Fixed zero delay — hammers the service immediately
await withRetry(operation, { maxAttempts: 5, initialDelayMs: 0 });

// ✅ Fix — always use exponential backoff + jitter
await withRetry(operation, { maxAttempts: 5, initialDelayMs: 500, backoffFactor: 2, jitter: true });
```

**Mistake 4 — Retry inside a database transaction:**
```typescript
// ❌ Retry wraps a DB transaction — if the transaction failed and rolled back,
// retrying creates a new transaction but doesn't know if the first committed
await this.prisma.$transaction(async (tx) => {
  await withRetry( // ← wrong place for retry
    () => tx.loan.update({ where: { id }, data: { status: 'SANCTIONED' } }),
    { maxAttempts: 3 },
  );
});

// ✅ Fix — retry wraps the ENTIRE transaction, not operations inside it
await withRetry(
  () => this.prisma.$transaction(async (tx) => {
    await tx.loan.update({ where: { id }, data: { status: 'SANCTIONED' } });
  }),
  { maxAttempts: 3, retryOn: isTransientDbError },
);
```

**Mistake 5 — Infinite or excessive retry counts for synchronous user-facing operations:**
```typescript
// ❌ 10 retries on a user-facing API — user waits up to 10 * 5s = 50 seconds
await withRetry(operation, { maxAttempts: 10, initialDelayMs: 5_000 });

// ✅ Fix — for user-facing: 2–3 attempts, short delays; queue for async retry if needed
await withRetry(operation, {
  maxAttempts: 2,
  initialDelayMs: 200,
  // After exhausting retries: queue for background retry, not block the user
  onMaxAttemptsExhausted: () => this.retryQueue.enqueue({ operation: 'BUREAU_FETCH', pan }),
});
```

**Q20. What is a "retry storm," and how do you prevent it?**
A: A retry storm occurs when many clients simultaneously retry a failing service, turning a brief outage into a sustained overload:

1. Service goes down at t=0
2. 1,000 in-flight requests fail simultaneously at t=0
3. All 1,000 retry at t=200ms — service still recovering, 1,000 more failures
4. All retry at t=400ms — still recovering, 1,000 more failures
5. Service never gets a quiet recovery window

Prevention strategies:
- **Jitter** — spreads retries across the delay window; already discussed.
- **Circuit Breaker** — after N failures, stop retrying entirely; give the service 30s to recover.
- **Exponential backoff cap** — even if jitter reduces individual load, the cap ensures the total retry window is bounded.
- **Concurrency limits** — limit how many in-flight retries can happen simultaneously:

```typescript
// Semaphore-limited retry pool — max 10 concurrent bureau retries across the system
class RetryPool {
  private readonly semaphore = new Semaphore(10); // max 10 concurrent

  async execute<T>(operation: () => Promise<T>): Promise<T> {
    return this.semaphore.run(() =>
      withRetry(operation, { maxAttempts: 3, initialDelayMs: 500, jitter: true }),
    );
  }
}
```

## Section 7: Scenario / System Design Questions

**Q21. "Your CIBIL bureau calls are failing intermittently — 15% error rate, mostly 503s during peak hours. Loan applications are failing immediately. How do you fix this?"**
A: A systematic resilience upgrade in three layers:

**Layer 1 — Add retry with backoff + jitter to the bureau adapter:**
```typescript
// Before: single attempt, throws on 503
const report = await this.httpClient.get(`/report/${pan}`);

// After: 3 attempts with exponential backoff
const report = await withRetry(
  () => this.httpClient.get(`/report/${pan}`),
  { maxAttempts: 3, initialDelayMs: 500, backoffFactor: 2, jitter: true, retryOn: isRetryableHttpError },
);
```

**Layer 2 — Add a Circuit Breaker to stop hammering CIBIL when it's down:**
A 15% error rate means CIBIL is struggling. After 5 consecutive failures, open the circuit; stop retrying for 30s; probe with one request; re-close if it succeeds.

**Layer 3 — Add a fallback flow for when CIBIL is unavailable:**
```typescript
async fetchReport(pan: string): Promise<CreditReport> {
  try {
    return await this.circuitBreaker.call(() =>
      withRetry(() => this.cibilAdapter.fetchReport(pan), retryConfig),
    );
  } catch (err) {
    if (err instanceof CircuitOpenException || err instanceof BureauUnavailableException) {
      // Fallback — use Experian if CIBIL is down
      try {
        return await this.experianAdapter.fetchReport(pan);
      } catch {
        // Both down — queue application for manual review
        await this.manualReviewQueue.enqueue({ pan, reason: 'BUREAU_UNAVAILABLE' });
        throw new ApplicationQueuedException('Bureau temporarily unavailable — application queued');
      }
    }
    throw err;
  }
}
```

After this: the 15% error rate is absorbed by retry (most 503s resolve on the second attempt), peak-hour congestion doesn't cascade into application failures, and prolonged outages gracefully fall back to Experian or manual review.

**Q22. "A junior developer asks: 'Our NACH debit is failing sometimes due to timeouts. Can I just wrap it in a retry loop?' How do you respond?"**
A: This is the most important Retry conversation in fintech. The answer is: **it depends entirely on whether the timeout happened before or after NPCI processed the request.**

Walk through the risk:
- A NACH debit initiates a real bank debit from the customer's account.
- If NPCI processed the debit but the response timed out (a "lost response" scenario), the debit has happened. Retrying sends a second debit request — the customer is debited twice.
- Unlike a bureau pull (which is read-only), a NACH debit is irreversible.

Safe approach:
1. **Use an idempotency key** — NPCI supports this. Format: `{UMRN}-{EMI month/year}`. Before retrying, check if NPCI has already processed a debit with this key.
2. **Check status before retrying** — after a timeout, call `npciClient.checkStatus(idempotencyKey)` before issuing a second debit request.
3. **Classify the failure carefully** — `NETWORK_ERROR` (request never reached NPCI) is safe to retry. `RESPONSE_TIMEOUT` (request may have reached NPCI) requires status check first.
4. **Limit retry to 1 extra attempt** — not 3. Financial operations fail conservatively.
5. **Never retry `INSUFFICIENT_FUNDS`** — it's not a transient error; retrying wastes time and may change the customer's DPD computation.

```typescript
// Safe NACH retry — never retry blindly
async debitEmi(mandate: NachMandate, emi: EmiSchedule): Promise<void> {
  const key = `${mandate.umrn}-${emi.month}-${emi.year}`;

  try {
    await this.npciClient.initiateDebit({ ...params, idempotencyKey: key });
  } catch (err) {
    if (isDefinitelyNotProcessed(err)) {          // NETWORK_ERROR, GATEWAY_REJECTION
      await sleep(2000);
      await this.npciClient.initiateDebit({ ...params, idempotencyKey: key }); // retry once
    } else if (isAmbiguous(err)) {                // RESPONSE_TIMEOUT
      const status = await this.npciClient.checkStatus(key);
      if (!status || status.status === 'PENDING') {
        await this.npciClient.initiateDebit({ ...params, idempotencyKey: key }); // safe — not processed
      }
      // If status is SUCCESS — do NOT retry — it already ran
    }
    // INSUFFICIENT_FUNDS, ACCOUNT_CLOSED etc — don't retry at all
  }
}
```

## Quick Reference: Retry Pattern Checklist

| Signal                                                                        | Decision                                                                       |
|-------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| External API call fails with 503/504/timeout                                  | Retry with exponential backoff + jitter                                        |
| External API call fails with 400/401/403/422                                  | Do NOT retry — non-transient; fix the request or auth                          |
| Financial operation (NACH debit, disbursement) fails                          | Check idempotency first; retry only if definitively not processed              |
| Multiple callers retrying simultaneously causing load spikes                  | Add jitter; consider Circuit Breaker                                           |
| Retry inside a DB transaction                                                 | Move retry to wrap the entire transaction, not operations inside it            |
| Service has been failing for 30+ seconds consistently                         | Circuit Breaker — stop retrying; fail fast; wait for recovery                  |
| User-facing API (customer submitting application) fails on retry              | Max 2 attempts, short delay; queue for async retry; don't block the user       |
| Retry predicate not defined                                                   | Always define one — retrying validation errors wastes time and hides bugs      |
| Retry wrapping a non-idempotent operation without idempotency key             | Most dangerous mistake in fintech — add idempotency key or do not retry        |
| No logging/metrics on retry                                                   | Always log retries with attempt number, error, and delay; alert on exhaustion  |

**Tip for the interview:** At the 5 YOE level, Retry Pattern questions always have a fintech edge — "our bureau calls are failing, should we retry?", "our NACH debit timed out, can we retry it?", "how do you prevent retries from making a downstream outage worse?" The answer that lands at the senior level leads with **idempotency** — before asking whether to retry, you ask whether the operation can safely be retried if the previous attempt may have partially succeeded. For read-only operations (bureau pull, status check), retry freely with exponential backoff and jitter. For write operations (NACH debit, disbursement), retry only with an idempotency key and only after confirming the previous attempt definitively failed. The architectural differentiators are knowing that Retry and Circuit Breaker are complementary (not alternatives), that retry without jitter creates thundering herds, and that retrying inside a database transaction has different semantics from retrying the whole transaction. Have the CIBIL 503 scenario and the NACH timeout scenario ready as concrete stories — they're the two most common fintech retry discussions.
