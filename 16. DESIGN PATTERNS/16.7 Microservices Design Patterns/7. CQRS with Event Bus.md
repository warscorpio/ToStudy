# Microservices & Data Patterns: CQRS with Event Bus — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is CQRS with Event Bus, and how does it differ from basic CQRS?**
A: CQRS with Event Bus is an architectural pattern that **combines Command Query Responsibility Segregation with an asynchronous event bus** to connect the command side (write stack) to the query side (read stack). In basic CQRS, the read model is often updated synchronously — either within the same database transaction as the write, or via a direct method call in the same process. In CQRS with Event Bus, the connection is fully asynchronous:

1. A command handler processes a command, mutates aggregate state, and publishes a **domain event** to an event bus.
2. The event bus delivers the event to **projectors** — specialized handlers that update one or more read models in response.
3. Queries read from those pre-built read models — no aggregate loading, no business logic, just optimised data retrieval.

The key difference from basic CQRS:
- **Basic CQRS** — command and query sides often share the same process; read model updates may be synchronous.
- **CQRS with Event Bus** — command side and query side are fully decoupled through events; they can run in separate services, scale independently, and use different database technologies.

```
Command Side                    Event Bus                    Query Side
─────────────                   ─────────                    ──────────
Controller                          │
    │                               │
CommandBus.execute()                │
    │                               │
CommandHandler                      │
    │                               │
  Aggregate.doOperation() ──► publishes DomainEvent ──► Projector updates ReadModel
    │                               │                            │
Repository.save(aggregate)          │                     Redis / Postgres / ES
                                    │
                                    └──► Another Projector ──► Another ReadModel
                                    └──► Notification Handler ──► SMS/Email
                                    └──► Audit Handler ──► Audit trail
```

**Q2. What problems does CQRS with Event Bus solve beyond what basic CQRS provides?**
A: The event bus adds three capabilities that basic CQRS doesn't provide:

- **Service decoupling** — the command service (LoanOrigination) doesn't know about the query service (ReportingService). The command side publishes events; any number of query-side projectors in any number of services can subscribe. Adding a new read model requires no changes to the command side.
- **Cross-service read model construction** — a projector in the Reporting service can subscribe to events from *multiple* upstream services (LoanOrigination, Collections, NACH) and build a cross-domain read model — something impossible with synchronous CQRS.
- **Replay and rebuild** — since events are persisted in the bus (Kafka with retention, or an outbox table), a projector can be rebuilt from scratch by replaying historical events. A new read model for a new reporting requirement can be populated with historical data without touching any aggregate or write-side code.

**Q3. What is the full data flow in CQRS with Event Bus?**
A: Walking through a loan sanction:

```
HTTP Request
    │
    ▼
LoanController.sanction(dto)            [Presentation Layer]
    │
    ▼
CommandBus.execute(SanctionLoanCommand) [Application Layer]
    │
    ▼
SanctionLoanCommandHandler              [Command Handler]
    ├─ loanAppRepo.findById(id)          → loads aggregate from write DB
    ├─ aggregate.sanction(amount, conds) → domain logic; appends LoanSanctionedEvent
    ├─ loanAppRepo.save(aggregate)       → persists new state to write DB
    └─ eventBus.publish(LoanSanctionedEvent) → async delivery to event bus
    │
    ▼ (returns immediately; downstream is async)

Event Bus delivers LoanSanctionedEvent to all subscribers:
    │
    ├──► LoanPortfolioProjector
    │       └─ updates loan_portfolio_projection table  [Read Model 1]
    │
    ├──► LoanTrackingProjector
    │       └─ updates loan_tracking_projection table   [Read Model 2]
    │
    ├──► NachSetupHandler
    │       └─ initiates NACH mandate registration
    │
    ├──► NotificationHandler
    │       └─ sends sanction letter SMS/email
    │
    └──► AuditTrailProjector
            └─ writes audit entry                       [Read Model 3]

Query Request (from dashboard, mobile app, ops UI):
    │
    ▼
QueryBus.execute(GetLoanStatusQuery)    [Query Handler]
    └─ reads from loan_tracking_projection (no aggregate, no business logic)
    └─ returns LoanStatusDto in < 10ms
```

**Q4. What is the relationship between CQRS with Event Bus and Event Sourcing?**
A: They are independent patterns that are commonly combined:

| Pattern               | Core idea                                                          | Requires the other?      |
|-----------------------|--------------------------------------------------------------------|--------------------------|
| **CQRS + Event Bus**  | Commands write via aggregates; events update read models via bus   | No — can use state store |
| **Event Sourcing**    | Aggregate state derived by replaying domain events (event log)     | No — can use single model |
| **ES + CQRS + Bus**   | Event log is the write store; bus distributes events to projectors | Full combination          |

**CQRS with Event Bus without Event Sourcing** (most common in practice): the write side persists current aggregate state to a relational database; the command handler also publishes events (via Outbox or direct); projectors consume these events and update read models. The aggregate state is not stored as a sequence of events.

**CQRS with Event Bus with Event Sourcing**: the write side stores events as the source of truth (append-only event log); the aggregate is reconstructed by replaying events; projectors consume the same events. This gives full auditability, time-travel queries, and the ability to rebuild any projection from day one.

For most fintech backends: use **CQRS + Event Bus without Event Sourcing** for operational services (loan origination, collections); consider **Event Sourcing** selectively for domains where full history matters most (active loan repayment history, audit-critical operations).

**Q6. What does a complete command handler with event bus publishing look like?**
A:

```typescript
// Command
export class SanctionLoanCommand {
  constructor(
    public readonly loanApplicationId: string,
    public readonly sanctionedAmount: number,     // in paise
    public readonly conditions: string[],
    public readonly officerId: string,
    public readonly correlationId: string,
  ) {}
}

// Domain Event
export class LoanSanctionedEvent implements IEvent {
  public readonly occurredAt = new Date();

  constructor(
    public readonly applicationId: string,
    public readonly applicantId: string,
    public readonly sanctionedAmount: number,
    public readonly sanctionedBy: string,
    public readonly conditions: string[],
    public readonly correlationId: string,
  ) {}
}

// Command Handler
@CommandHandler(SanctionLoanCommand)
export class SanctionLoanCommandHandler
  implements ICommandHandler<SanctionLoanCommand> {

  constructor(
    @Inject(LOAN_APPLICATION_REPOSITORY)
    private readonly loanRepo: ILoanApplicationRepository,
    private readonly officerRepo: IOfficerRepository,
    private readonly eventBus: EventBus,
    private readonly logger: Logger,
  ) {}

  async execute(command: SanctionLoanCommand): Promise<void> {
    this.logger.log({
      message: 'Executing SanctionLoanCommand',
      loanId: command.loanApplicationId,
      officerId: command.officerId,
      correlationId: command.correlationId,
    });

    // 1. Load aggregate
    const application = await this.loanRepo.findById(
      LoanApplicationId.from(command.loanApplicationId),
    );
    if (!application) {
      throw new LoanApplicationNotFoundException(command.loanApplicationId);
    }

    // 2. Load officer for authority check
    const officer = await this.officerRepo.findById(OfficerId.from(command.officerId));
    if (!officer) throw new OfficerNotFoundException(command.officerId);

    // 3. Domain operation — enforces invariants, appends events to aggregate
    application.sanction(
      Money.inPaise(command.sanctionedAmount),
      command.conditions.map(SanctionCondition.from),
      officer,
    );

    // 4. Persist aggregate state
    await this.loanRepo.save(application);

    // 5. Publish domain events via Event Bus
    // pullAndClearEvents() returns events appended by aggregate.sanction()
    const domainEvents = application.pullAndClearEvents();
    domainEvents.forEach(event => {
      // Enrich with correlation ID before publishing
      const enriched = { ...event, correlationId: command.correlationId };
      this.eventBus.publish(enriched);
    });

    this.logger.log({
      message: 'SanctionLoanCommand executed',
      loanId: command.loanApplicationId,
      eventsPublished: domainEvents.length,
    });
  }
}
```

A:

```typescript
// Read model schema — pre-joined, optimised for query
// CREATE TABLE loan_tracking_projection (
//   application_id    UUID PRIMARY KEY,
//   applicant_id      UUID NOT NULL,
//   applicant_name    TEXT,                     -- denormalised from KYC
//   product_code      TEXT NOT NULL,
//   product_name      TEXT,                     -- denormalised from Products
//   requested_amount  BIGINT NOT NULL,
//   sanctioned_amount BIGINT,
//   current_status    TEXT NOT NULL,
//   submitted_at      TIMESTAMPTZ NOT NULL,
//   sanctioned_at     TIMESTAMPTZ,
//   sanctioned_by     TEXT,
//   disbursed_at      TIMESTAMPTZ,
//   timeline          JSONB,                    -- array of {status, changedAt, changedBy}
//   last_updated_at   TIMESTAMPTZ NOT NULL,
//   version           INT NOT NULL DEFAULT 0
// );

@EventsHandler(
  LoanApplicationSubmittedEvent,
  LoanApplicationSentForReviewEvent,
  LoanSanctionedEvent,
  LoanApplicationRejectedEvent,
  LoanDisbursedEvent,
)
@Injectable()
export class LoanTrackingProjector
  implements IEventHandler<
    | LoanApplicationSubmittedEvent
    | LoanApplicationSentForReviewEvent
    | LoanSanctionedEvent
    | LoanApplicationRejectedEvent
    | LoanDisbursedEvent
  > {

  constructor(
    private readonly prisma: PrismaService,
    private readonly logger: Logger,
    private readonly metrics: MetricsService,
  ) {}

  async handle(event: IEvent): Promise<void> {
    const start = Date.now();

    try {
      if (event instanceof LoanApplicationSubmittedEvent) {
        await this.onSubmitted(event);
      } else if (event instanceof LoanApplicationSentForReviewEvent) {
        await this.onSentForReview(event);
      } else if (event instanceof LoanSanctionedEvent) {
        await this.onSanctioned(event);
      } else if (event instanceof LoanApplicationRejectedEvent) {
        await this.onRejected(event);
      } else if (event instanceof LoanDisbursedEvent) {
        await this.onDisbursed(event);
      }

      this.metrics.record('projector.loan_tracking.latency', Date.now() - start);
    } catch (err) {
      this.logger.error({
        message: 'LoanTrackingProjector failed',
        event: event.constructor.name,
        error: (err as Error).message,
      });
      throw err; // re-throw so the event bus can retry
    }
  }

  private async onSubmitted(event: LoanApplicationSubmittedEvent): Promise<void> {
    await this.prisma.loanTrackingProjection.create({
      data: {
        applicationId: event.applicationId,
        applicantId: event.applicantId,
        productCode: event.productCode,
        requestedAmount: event.requestedAmount,
        currentStatus: 'SUBMITTED',
        submittedAt: event.occurredAt,
        lastUpdatedAt: event.occurredAt,
        timeline: JSON.stringify([{
          status: 'SUBMITTED',
          changedAt: event.occurredAt,
          changedBy: event.applicantId,
        }]),
        version: 1,
      },
    });
  }

  private async onSanctioned(event: LoanSanctionedEvent): Promise<void> {
    // Read current state first for timeline append
    const current = await this.prisma.loanTrackingProjection.findUnique({
      where: { applicationId: event.applicationId },
    });

    if (!current) {
      this.logger.warn({
        message: 'LoanTrackingProjector: no record for sanction event',
        applicationId: event.applicationId,
      });
      return;
    }

    const timeline = JSON.parse(current.timeline as string) as TimelineEntry[];
    timeline.push({
      status: 'SANCTIONED',
      changedAt: event.occurredAt,
      changedBy: event.sanctionedBy,
      notes: `₹${event.sanctionedAmount / 100} sanctioned`,
    });

    await this.prisma.loanTrackingProjection.update({
      where: {
        applicationId: event.applicationId,
        version: current.version, // optimistic concurrency — prevents out-of-order updates
      },
      data: {
        currentStatus: 'SANCTIONED',
        sanctionedAmount: event.sanctionedAmount,
        sanctionedAt: event.occurredAt,
        sanctionedBy: event.sanctionedBy,
        timeline: JSON.stringify(timeline),
        lastUpdatedAt: event.occurredAt,
        version: { increment: 1 },
      },
    });
  }

  private async onSentForReview(event: LoanApplicationSentForReviewEvent): Promise<void> { /* ... */ }
  private async onRejected(event: LoanApplicationRejectedEvent): Promise<void> { /* ... */ }
  private async onDisbursed(event: LoanDisbursedEvent): Promise<void> { /* ... */ }
}
```

```typescript
    return {
      applicationId: record.applicationId,
      currentStatus: record.currentStatus,
      productCode: record.productCode,
      requestedAmount: Number(record.requestedAmount),
      sanctionedAmount: record.sanctionedAmount ? Number(record.sanctionedAmount) : null,
      submittedAt: record.submittedAt,
      timeline: JSON.parse(record.timeline as string),
      pendingActions: this.resolvePendingActions(record.currentStatus),
    };
  }

  private resolvePendingActions(status: string): string[] {
    const map: Record<string, string[]> = {
      SUBMITTED: ['SEND_FOR_REVIEW', 'REQUEST_ADDITIONAL_DOCS'],
      UNDER_REVIEW: ['SANCTION', 'REJECT', 'REQUEST_DOCS'],
      SANCTIONED: ['DISBURSE', 'LAPSE'],
      DISBURSED: [],
      REJECTED: [],
    };
    return map[status] ?? [];
  }
}
```

## Section 3: External Event Bus Integration

**Q9. How do you connect the NestJS EventBus to an external message broker (SNS/SQS) for cross-service events?**
A: NestJS's built-in `EventBus` is in-process only — it cannot communicate across service boundaries. For cross-service event delivery, you need a bridge that publishes events to an external broker:

```typescript
// Event Bus Bridge — intercepts NestJS EventBus publications and forwards to SNS
@Injectable()
export class SnsEventBusBridge implements OnModuleInit {
  constructor(
    private readonly eventBus: EventBus,                  // NestJS in-process EventBus
    private readonly snsPublisher: SnsEventPublisher,     // AWS SNS client
    private readonly logger: Logger,
  ) {}

  onModuleInit(): void {
    // Subscribe to ALL events on the in-process bus
    // and forward cross-service events to SNS
    this.eventBus.subject$.pipe(
      filter(event => this.isCrossServiceEvent(event)),
    ).subscribe(async event => {
      try {
        await this.snsPublisher.publish(event);
        this.logger.debug({ message: 'Event forwarded to SNS', event: event.constructor.name });
      } catch (err) {
        this.logger.error({ message: 'Failed to forward event to SNS', event: event.constructor.name, err });
        // Outbox pattern handles reliability — this is a best-effort bridge
      }
    });
  }

  private isCrossServiceEvent(event: IEvent): boolean {
    // Only these events need to leave the service boundary
    const CROSS_SERVICE_EVENTS = new Set([
      'LoanApplicationSubmittedEvent',
      'LoanSanctionedEvent',
      'LoanDisbursedEvent',
      'EmiCollectedEvent',
      'EmiDefaultedEvent',
    ]);
    return CROSS_SERVICE_EVENTS.has(event.constructor.name);
  }
}

// SNS Publisher — serialises and publishes to the right topic
@Injectable()
export class SnsEventPublisher {
  private readonly snsClient = new SNSClient({ region: process.env.AWS_REGION });

  private readonly topicArns: Record<string, string> = {
    LoanApplicationSubmittedEvent: process.env.LOAN_ORIGINATION_TOPIC_ARN!,
    LoanSanctionedEvent: process.env.LOAN_ORIGINATION_TOPIC_ARN!,
    LoanDisbursedEvent: process.env.LOAN_ORIGINATION_TOPIC_ARN!,
    EmiCollectedEvent: process.env.EMI_EVENTS_TOPIC_ARN!,
    EmiDefaultedEvent: process.env.EMI_EVENTS_TOPIC_ARN!,
  };

  async publish(event: IEvent): Promise<void> {
    const topicArn = this.topicArns[event.constructor.name];
    if (!topicArn) return; // not a cross-service event

    await this.snsClient.send(new PublishCommand({
      TopicArn: topicArn,
      Message: JSON.stringify(event),
      MessageAttributes: {
        eventType: { DataType: 'String', StringValue: event.constructor.name },
        correlationId: {
          DataType: 'String',
          StringValue: (event as any).correlationId ?? uuid(),
        },
      },
    }));
  }
}
```

For intra-service events (projector updates within the same service), the in-process NestJS `EventBus` is sufficient and adds no network overhead. For cross-service events, the bridge forwards to SNS.

**Q10. How do you consume external events from SQS and dispatch them through the NestJS EventBus?**
A:

```typescript
// SQS Consumer — receives messages from SQS, reconstructs events, dispatches to EventBus
@Injectable()
export class SqsEventConsumer implements OnModuleInit, OnModuleDestroy {
  private readonly sqsClient = new SQSClient({ region: process.env.AWS_REGION });
  private pollingActive = false;

  constructor(
    private readonly eventBus: EventBus,
    private readonly eventRegistry: EventRegistry,  // maps event type string → class
    private readonly logger: Logger,
  ) {}

  onModuleInit(): void {
    this.pollingActive = true;
    this.startPolling();
  }

  onModuleDestroy(): void {
    this.pollingActive = false;
  }

  private async startPolling(): Promise<void> {
    while (this.pollingActive) {
      await this.pollAndProcess();
      await sleep(1000); // 1s between poll batches
    }
  }

  private async pollAndProcess(): Promise<void> {
    const response = await this.sqsClient.send(new ReceiveMessageCommand({
      QueueUrl: process.env.LOAN_EVENTS_QUEUE_URL,
      MaxNumberOfMessages: 10,
      WaitTimeSeconds: 20,    // long polling — reduces empty responses
      VisibilityTimeout: 60,  // 60s to process before re-delivery
    }));

    if (!response.Messages?.length) return;

    await Promise.allSettled(
      response.Messages.map(msg => this.processMessage(msg)),
    );
  }

  private async processMessage(message: Message): Promise<void> {
    try {
      // SNS wraps messages — unwrap
      const snsWrapper = JSON.parse(message.Body!);
      const payload = JSON.parse(snsWrapper.Message);
      const eventType = snsWrapper.MessageAttributes?.eventType?.Value;

      // Reconstruct the typed event object
      const EventClass = this.eventRegistry.get(eventType);
      if (!EventClass) {
        this.logger.warn({ message: 'Unknown event type received', eventType });
        await this.deleteMessage(message); // unknown types are discarded
        return;
      }

      const event = Object.assign(new EventClass(), payload);

      // Dispatch through NestJS EventBus — projectors and handlers will receive it
      await this.eventBus.publish(event);

      // Acknowledge successful processing
      await this.deleteMessage(message);
    } catch (err) {
      this.logger.error({
        message: 'SQS message processing failed',
        messageId: message.MessageId,
        error: (err as Error).message,
      });
      // Do NOT delete message — SQS will redeliver after visibility timeout
      // After maxReceiveCount failures → DLQ
    }
  }

  private async deleteMessage(message: Message): Promise<void> {
    await this.sqsClient.send(new DeleteMessageCommand({
      QueueUrl: process.env.LOAN_EVENTS_QUEUE_URL,
      ReceiptHandle: message.ReceiptHandle!,
    }));
  }
}

// Event Registry — maps event type strings to classes
@Injectable()
export class EventRegistry {
  private readonly registry = new Map<string, new (...args: any[]) => IEvent>([
    ['LoanApplicationSubmittedEvent', LoanApplicationSubmittedEvent],
    ['LoanSanctionedEvent', LoanSanctionedEvent],
    ['LoanDisbursedEvent', LoanDisbursedEvent],
    ['EmiCollectedEvent', EmiCollectedEvent],
    ['EmiDefaultedEvent', EmiDefaultedEvent],
  ]);

  get(eventType: string): (new (...args: any[]) => IEvent) | undefined {
    return this.registry.get(eventType);
  }
}
```

## Section 4: Projection Rebuild and Event Replay

**Q11. How do you rebuild a projection from scratch by replaying events?**
A: Projection rebuild is one of CQRS with Event Bus's most powerful capabilities — add a new read model shape and populate it with full historical data without touching any write-side code:

```typescript
// Projection Rebuild Service
@Injectable()
export class ProjectionRebuildService {
  constructor(
    private readonly eventStore: IEventStore,     // ordered event log
    private readonly eventBus: EventBus,
    private readonly prisma: PrismaService,
    private readonly logger: Logger,
  ) {}

  async rebuildLoanTrackingProjection(): Promise<void> {
    this.logger.log('Starting LoanTrackingProjection rebuild');
    const startTime = Date.now();

    // Step 1 — clear the stale projection
    await this.prisma.loanTrackingProjection.deleteMany();
    this.logger.log('Cleared existing LoanTrackingProjection data');

    // Step 2 — replay all relevant events in chronological order
    const events = await this.eventStore.findByTypes(
      [
        'LoanApplicationSubmittedEvent',
        'LoanApplicationSentForReviewEvent',
        'LoanSanctionedEvent',
        'LoanApplicationRejectedEvent',
        'LoanDisbursedEvent',
      ],
      { orderBy: 'occurredAt ASC' },
    );

    this.logger.log({ message: 'Replaying events', count: events.length });

    // Step 3 — dispatch each event through the EventBus
    // The projector handles them exactly as it would in production
    let processed = 0;
    for (const storedEvent of events) {
      const EventClass = this.eventRegistry.get(storedEvent.eventType);
      if (EventClass) {
        const event = Object.assign(new EventClass(), storedEvent.payload);
        await this.eventBus.publish(event);

        processed++;
        if (processed % 1000 === 0) {
          this.logger.log({ message: 'Rebuild progress', processed, total: events.length });
        }
      }
    }

    this.logger.log({
      message: 'LoanTrackingProjection rebuild complete',
      processed,
      durationMs: Date.now() - startTime,
    });
  }
}

// Event Store — persists all domain events for replay
// CREATE TABLE domain_events (
//   id          UUID PRIMARY KEY,
//   event_type  TEXT NOT NULL,
//   aggregate_id TEXT NOT NULL,
//   payload     JSONB NOT NULL,
//   occurred_at TIMESTAMPTZ NOT NULL,
//   correlation_id TEXT,
//   sequence    BIGSERIAL   -- global ordering
// );

@Injectable()
export class PostgresEventStore implements IEventStore {
  constructor(private readonly prisma: PrismaService) {}

  async append(event: IEvent): Promise<void> {
    await this.prisma.domainEvent.create({
      data: {
        id: uuid(),
        eventType: event.constructor.name,
        aggregateId: (event as any).applicationId ?? (event as any).loanId,
        payload: event as any,
        occurredAt: (event as any).occurredAt ?? new Date(),
        correlationId: (event as any).correlationId,
      },
    });
  }

  async findByTypes(
    eventTypes: string[],
    options: { orderBy: 'occurredAt ASC' | 'occurredAt DESC'; fromDate?: Date },
  ): Promise<StoredEvent[]> {
    return this.prisma.domainEvent.findMany({
      where: {
        eventType: { in: eventTypes },
        ...(options.fromDate && { occurredAt: { gte: options.fromDate } }),
      },
      orderBy: { sequence: options.orderBy === 'occurredAt ASC' ? 'asc' : 'desc' },
    });
  }
}
```

**Q12. How do you implement a command handler that also persists to the event store?**
A: The command handler writes to both the aggregate's write store and the event store in one transaction:

```typescript
@CommandHandler(SanctionLoanCommand)
export class SanctionLoanCommandHandler implements ICommandHandler<SanctionLoanCommand> {
  constructor(
    @Inject(LOAN_APPLICATION_REPOSITORY)
    private readonly loanRepo: ILoanApplicationRepository,
    private readonly eventStore: PostgresEventStore,
    private readonly eventBus: EventBus,
    private readonly prisma: PrismaService,
  ) {}

  async execute(command: SanctionLoanCommand): Promise<void> {
    const application = await this.loanRepo.findById(LoanApplicationId.from(command.loanApplicationId));
    if (!application) throw new LoanApplicationNotFoundException(command.loanApplicationId);

    application.sanction(Money.inPaise(command.sanctionedAmount), command.conditions.map(SanctionCondition.from), officer);

    const domainEvents = application.pullAndClearEvents();

    // Atomically: save aggregate state + write events to event store
    await this.prisma.$transaction(async (tx) => {
      // Save aggregate current state
      const aggregateData = LoanApplicationMapper.toPersistence(application);
      await tx.loanApplication.update({ where: { id: aggregateData.id }, data: aggregateData });

      // Save events to event store (enables replay)
      for (const event of domainEvents) {
        await tx.domainEvent.create({
          data: {
            id: uuid(),
            eventType: event.constructor.name,
            aggregateId: command.loanApplicationId,
            payload: event as any,
            occurredAt: (event as any).occurredAt ?? new Date(),
            correlationId: command.correlationId,
          },
        });
      }
    });

    // After transaction commits — publish to in-process and external bus
    domainEvents.forEach(event => this.eventBus.publish(event));
  }
}
```

**Q14. How do you handle the "read your own writes" problem when using an asynchronous event bus?**
A: With an async event bus, a user who submits a command and immediately queries may not see the projection updated yet. Several mitigation strategies:

**Strategy 1 — Return result directly from the command handler:**
```typescript
// Controller — returns enough for optimistic UI update
@Post('loan-applications/:id/sanction')
async sanction(
  @Param('id') id: string,
  @Body() dto: SanctionLoanDto,
  @CurrentUser() officer: AuthenticatedUser,
): Promise<SanctionResultDto> {
  await this.commandBus.execute(new SanctionLoanCommand(id, dto.sanctionedAmount, dto.conditions, officer.id, uuid()));

  // Return what the command side knows — not from projection
  return {
    applicationId: id,
    newStatus: 'SANCTIONED',     // the client shows this immediately
    sanctionedAmount: dto.sanctionedAmount,
    processedAt: new Date(),
    note: 'Full details available in 2–3 seconds',
  };
}
```

**Strategy 2 — Version-based polling:**
```typescript
// Query handler with version gate
@QueryHandler(GetLoanApplicationStatusQuery)
export class GetLoanApplicationStatusQueryHandler {
  async execute(query: GetLoanApplicationStatusQuery): Promise<LoanStatusDto> {
    // If caller provides minimum expected version, wait for projection to catch up
    if (query.minimumVersion) {
      const maxAttempts = 5;
      for (let i = 0; i < maxAttempts; i++) {
        const record = await this.prisma.loanTrackingProjection.findUnique({
          where: { applicationId: query.applicationId },
        });
        if (record && record.version >= query.minimumVersion) {
          return this.toDto(record);
        }
        await sleep(100 * 2 ** i); // 100, 200, 400, 800, 1600ms
      }
    }

    // Fall back to current state without waiting
    const record = await this.prisma.loanTrackingProjection.findUnique({
      where: { applicationId: query.applicationId },
    });
    return record ? this.toDto(record) : null;
  }
}
```

**Strategy 3 — Direct write-side read for consistency-critical queries:**
```typescript
// Special query that reads from the aggregate (write store) when freshen is required
@QueryHandler(GetCurrentLoanStatusQuery)
export class GetCurrentLoanStatusQueryHandler {
  async execute(query: GetCurrentLoanStatusQuery): Promise<LoanStatusDto> {
    if (query.requiresStrongConsistency) {
      // Load from write side — accurate but heavier
      const aggregate = await this.loanAppRepo.findById(LoanApplicationId.from(query.applicationId));
      return { applicationId: query.applicationId, status: aggregate?.status ?? 'NOT_FOUND' };
    }
    // Default — read from projection
    const projection = await this.prisma.loanTrackingProjection.findUnique({
      where: { applicationId: query.applicationId },
    });
    return projection ? this.toDto(projection) : null;
  }
}
```

**Q15. How do you handle projector failures without losing events?**
A:

```typescript
// Resilient projector — failure handling and metrics
@EventsHandler(LoanSanctionedEvent)
export class ResilientLoanSanctionedProjector implements IEventHandler<LoanSanctionedEvent> {
  constructor(
    private readonly prisma: PrismaService,
    private readonly projectionFailureStore: ProjectionFailureStore,
    private readonly alertService: AlertService,
    private readonly logger: Logger,
  ) {}

  async handle(event: LoanSanctionedEvent): Promise<void> {
    try {
      await this.updateProjection(event);
    } catch (err) {
      this.logger.error({
        message: 'Projection update failed — storing for retry',
        event: event.constructor.name,
        applicationId: event.applicationId,
        error: (err as Error).message,
      });

      // Store the failed event for manual inspection / automated retry
      await this.projectionFailureStore.record({
        eventType: event.constructor.name,
        eventPayload: event,
        failedAt: new Date(),
        error: (err as Error).message,
        retryCount: 0,
      });

      await this.alertService.sendCritical(
        `Projection failure: ${event.constructor.name} for loan ${event.applicationId}`,
      );

      // Re-throw so the event bus retries the delivery
      throw err;
    }
  }

  private async updateProjection(event: LoanSanctionedEvent): Promise<void> {
    await this.prisma.loanTrackingProjection.update({
      where: { applicationId: event.applicationId },
      data: {
        currentStatus: 'SANCTIONED',
        sanctionedAmount: event.sanctionedAmount,
        sanctionedAt: event.occurredAt,
        lastUpdatedAt: event.occurredAt,
        version: { increment: 1 },
      },
    });
  }
}

// Projection Failure Recovery — scheduled job to retry failed projections
@Injectable()
export class ProjectionFailureRecoveryJob {
  @Cron('0 */15 * * * *') // every 15 minutes
  async retryFailedProjections(): Promise<void> {
    const failed = await this.projectionFailureStore.findRetryable({ maxRetries: 5 });

    for (const failure of failed) {
      try {
        const EventClass = this.eventRegistry.get(failure.eventType);
        const event = Object.assign(new EventClass(), failure.eventPayload);
        await this.eventBus.publish(event);
        await this.projectionFailureStore.markResolved(failure.id);
      } catch (err) {
        await this.projectionFailureStore.incrementRetryCount(failure.id);
      }
    }
  }
}
```

## Section 7: Anti-patterns and Scenario Questions

**Q17. What are the most common CQRS + Event Bus anti-patterns?**
A:

**Anti-pattern 1 — Querying read models from command handlers:**
```typescript
// ❌ Command handler reads from the projection — defeats the separation
@CommandHandler(SanctionLoanCommand)
async execute(command: SanctionLoanCommand): Promise<void> {
  // Reading a read model for a write operation — wrong side
  const existingData = await this.prisma.loanTrackingProjection.findUnique({
    where: { applicationId: command.loanApplicationId },
  });
  // Command handlers should load from the write-side repository (aggregate)
}

// ✅ Fix — command handler loads from repository (write side)
const application = await this.loanRepo.findById(LoanApplicationId.from(command.loanApplicationId));
```

**Anti-pattern 2 — Projectors with business logic:**
```typescript
// ❌ Projector making business decisions
@EventsHandler(LoanSanctionedEvent)
async handle(event: LoanSanctionedEvent): Promise<void> {
  // Business logic in the projector — wrong layer
  if (event.sanctionedAmount > 10_000_000_00) {
    await this.triggerHighValueAlert(event); // side effect in projector
  }
  await this.prisma.loanProjection.update({ /* ... */ });
}

// ✅ Fix — projectors only update read models
// Side effects live in separate event handlers
@EventsHandler(LoanSanctionedEvent)
async handle(event: LoanSanctionedEvent): Promise<void> {
  await this.prisma.loanProjection.update({ /* ... simple update only */ });
}

// Separate handler for the side effect
@EventsHandler(LoanSanctionedEvent)
class HighValueLoanAlertHandler implements IEventHandler<LoanSanctionedEvent> {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    if (event.sanctionedAmount > 10_000_000_00) {
      await this.alertService.sendHighValueAlert(event);
    }
  }
}
```

**Anti-pattern 3 — Publishing events before the transaction commits:**
```typescript
// ❌ Event published before DB commit — projector may read stale data
async execute(command: SanctionLoanCommand): Promise<void> {
  this.eventBus.publish(new LoanSanctionedEvent(...)); // BEFORE save!
  await this.loanRepo.save(application);
}

// ✅ Fix — save first, then publish
await this.loanRepo.save(application);
domainEvents.forEach(e => this.eventBus.publish(e)); // AFTER save
```

**Anti-pattern 4 — Non-idempotent projectors:**
```typescript
// ❌ insert() without deduplication — duplicate events corrupt data
await this.prisma.loanTrackingProjection.create({
  data: { applicationId: event.applicationId, currentStatus: 'SANCTIONED' },
}); // fails or duplicates on event redelivery

// ✅ upsert() — safe for any number of event deliveries
await this.prisma.loanTrackingProjection.upsert({
  where: { applicationId: event.applicationId },
  create: { applicationId: event.applicationId, currentStatus: 'SANCTIONED', /* ... */ },
  update: { currentStatus: 'SANCTIONED', /* ... */ },
});
```

**Q18. "A new business requirement needs a read model showing all loans that took more than 48 hours from submission to sanction. You have historical data but all in the write database. How do you build this without touching the write side?"**
A: Build a new projector and replay historical events:

```typescript
// Step 1 — new read model table
// CREATE TABLE slow_sanction_projection (
//   application_id  UUID PRIMARY KEY,
//   applicant_id    UUID NOT NULL,
//   submitted_at    TIMESTAMPTZ NOT NULL,
//   sanctioned_at   TIMESTAMPTZ,
//   hours_to_sanction DECIMAL(10,2),
//   status          TEXT NOT NULL     -- 'PENDING' | 'SANCTIONED_FAST' | 'SANCTIONED_SLOW'
// );

// Step 2 — new projector
@EventsHandler(LoanApplicationSubmittedEvent, LoanSanctionedEvent)
export class SlowSanctionProjector implements IEventHandler<IEvent> {
  async handle(event: IEvent): Promise<void> {
    if (event instanceof LoanApplicationSubmittedEvent) {
      await this.prisma.slowSanctionProjection.create({
        data: {
          applicationId: event.applicationId,
          applicantId: event.applicantId,
          submittedAt: event.occurredAt,
          status: 'PENDING',
        },
      });
    } else if (event instanceof LoanSanctionedEvent) {
      const record = await this.prisma.slowSanctionProjection.findUnique({
        where: { applicationId: event.applicationId },
      });
      if (!record) return;

      const hoursToSanction = differenceInHours(event.occurredAt, record.submittedAt);
      await this.prisma.slowSanctionProjection.update({
        where: { applicationId: event.applicationId },
        data: {
          sanctionedAt: event.occurredAt,
          hoursToSanction,
          status: hoursToSanction > 48 ? 'SANCTIONED_SLOW' : 'SANCTIONED_FAST',
        },
      });
    }
  }
}

// Step 3 — register the projector and replay historical events
// (no write-side changes; no aggregate changes; no migration of existing data)
await this.projectionRebuildService.rebuild(
  ['LoanApplicationSubmittedEvent', 'LoanSanctionedEvent'],
  'SlowSanctionProjection',
);

// Step 4 — new query handler
@QueryHandler(GetSlowSanctionLoansQuery)
export class GetSlowSanctionLoansQueryHandler {
  async execute(query: GetSlowSanctionLoansQuery): Promise<SlowSanctionDto[]> {
    return this.prisma.slowSanctionProjection.findMany({
      where: { status: 'SANCTIONED_SLOW', sanctionedAt: { gte: query.fromDate } },
      orderBy: { hoursToSanction: 'desc' },
    });
  }
}
```

Write side untouched. Historical data populated by replay. New query ready in hours.

## Quick Reference: CQRS with Event Bus Checklist

| Signal                                                                          | Decision                                                                   |
|---------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| Command handler reading from projection (read model) for write operations       | Anti-pattern — load from repository (write side) in command handlers       |
| Projector with business logic / side effects                                    | Extract side effects to separate event handlers; projectors update only    |
| Event published before DB transaction commits                                   | Save aggregate first, then publish events (or use Outbox Pattern)          |
| Projector fails on event redelivery (duplicate event causes error)              | Make projector idempotent — upsert with natural unique key                 |
| Query reads full aggregate for a dashboard that only needs 5 fields             | Build a dedicated read model projection — one row per query shape          |
| New business reporting requirement needs historical data                        | Build projector + replay historical events from event store                |
| User queries immediately after command — sees stale projection                  | Return result from command; optimistic UI update; poll with version gate   |
| Cross-service read model (data from 3 services in one view)                     | Reporting service subscribes to all relevant events; builds unified projection |
| NestJS EventBus needs to reach another service                                  | SNS/SQS bridge; in-process EventBus for intra-service, SNS for cross-service |
| Projector consistently fails on specific events                                 | DLQ + projection failure store + retry job; alert on failure               |

---

**Tip for the interview:** At the 5 YOE level, CQRS with Event Bus is the pattern that connects everything else — DDD (domain events from aggregates), EDA (events flowing between services), CQRS (separate read models), and Outbox (reliable publishing). The differentiating answer shows understanding of the full data flow: command → aggregate → domain event → event store + in-process bus → projector updates read model → query handler reads projection. The three most important implementation details to name: events are published *after* the transaction commits (or via Outbox), projectors must be idempotent (upsert, not insert), and the event store enables projection rebuild — the ability to add a new read model shape and populate it with all historical data by replaying events. In a lending context, the cross-service ops dashboard scenario (building a single projection from Origination + Collections + NACH + KYC events) and the "new reporting requirement using historical event replay" scenario are the most compelling demonstrations of why the pattern exists.
