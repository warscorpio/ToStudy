# JavaScript / TypeScript (Microservices Design Patterns): Distributed Transactions — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a distributed transaction, and why is it fundamentally harder than a local transaction?**
A: A distributed transaction is a business operation that must span multiple independent data stores, services, or systems — each with its own transaction boundary — and must maintain atomicity across all of them: either all changes commit or all changes roll back. The key word is *independent*: each participant manages its own ACID transaction, has its own failure mode, and communicates over an unreliable network.

A local database transaction is straightforward: one system, one coordinator, one commit protocol. The database's own engine guarantees atomicity through its write-ahead log, locks, and rollback mechanisms. Nothing else needs to agree.

A distributed transaction is hard because:

**The fundamental impossibility** — there is no way to atomically commit two independent systems simultaneously. Even if Service A commits and Service B commits nanoseconds later, there is a window between the two where one has committed and the other has not. A crash in that window produces an inconsistent state.

**The network is unreliable** — messages between services can be delayed, duplicated, or lost. A coordinator cannot distinguish between "participant B is slow" and "participant B has crashed."

**The CAP theorem** — a distributed system cannot simultaneously guarantee Consistency, Availability, and Partition tolerance. Under a network partition, a coordinator must choose: block waiting for participants (sacrificing availability) or proceed without confirmation (potentially sacrificing consistency).

**No shared clock** — services cannot agree on a precise ordering of events without additional coordination, making conflict detection complex.

```
Local transaction:
  BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
    UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
  COMMIT;
  // Atomically guaranteed by the DB engine ✓

Distributed transaction — naive approach:
  Service A: debit account A ($100) → commit
  [network delay, crash, timeout...]
  Service B: credit account B ($100) → never receives the message
  // Account A debited, Account B never credited — split state ✗
```

**Q2. What is the CAP theorem, and how does it shape the design of distributed transactions?**
A: The CAP theorem (Eric Brewer, 2000; proved by Gilbert and Lynch, 2002) states that a distributed data system can guarantee at most two of three properties simultaneously:

- **Consistency (C)** — every read receives the most recent write or an error. All nodes see the same data at the same time.
- **Availability (A)** — every request receives a response (not necessarily the most recent data). The system is always operational.
- **Partition Tolerance (P)** — the system continues to operate despite arbitrary network partitions (message loss or delay between nodes).

**Network partitions are not optional** — in any real distributed system, you must tolerate partitions (networks fail). So the real choice is between CP and AP:

- **CP systems** — sacrifice availability during a partition. Block or return errors until the partition heals and consistency is restored. Examples: Zookeeper, Etcd, HBase. Traditional two-phase commit (2PC) is CP — the coordinator blocks all participants until it hears back from everyone.
- **AP systems** — sacrifice consistency during a partition. Remain available but may return stale or conflicting data. Examples: Cassandra, DynamoDB (with eventual consistency), CouchDB. The Saga pattern is AP — each service commits independently and inconsistencies are resolved by compensating transactions.

The CAP theorem fundamentally explains why distributed transactions are either slow/unavailable (if you pursue strong consistency via 2PC) or eventually consistent (if you pursue availability via Saga). There is no free lunch.

**Q3. What is the difference between strong consistency and eventual consistency in distributed systems?**
A: The choice between them is the central design decision for distributed transactions:

**Strong consistency** — after a transaction commits, all subsequent reads from any node in the system will see the committed data. The system appears as if all operations execute on a single machine. Achieved via protocols like 2PC, Paxos, or Raft.

**Eventual consistency** — after an update, the system will *eventually* converge to a consistent state if no further updates are made. Different nodes may temporarily see different versions of the data. The "eventually" is usually milliseconds to seconds in practice.

```
Strong consistency (2PC):
  T=0: Order placed
  T=1: All participants (inventory, payment, shipping) lock their records
  T=2: Coordinator sends COMMIT to all
  T=3: All participants commit atomically
  ← Any reader from any service sees consistent state immediately after T=3
  Cost: high latency (multiple round trips), lock contention, blocking

Eventual consistency (Saga):
  T=0: Order placed — inventory reserved (committed locally)
  T=1: Payment charged (committed locally)
  T=2: Shipping scheduled (committed locally)
  ← Between T=0 and T=2, inventory shows reserved but payment not yet charged
  ← This intermediate state is visible to other readers during this window
  ← Eventually (T=2+) all services reflect a consistent picture
  Cost: compensating logic, idempotency, intermediate inconsistency visible
```

The practical choice: **use eventual consistency by default in microservices** (Saga, Outbox pattern, event-driven coordination). Reserve strong consistency (2PC) for cases where the cost of intermediate inconsistency is truly unacceptable — typically financial ledgers or regulatory-requirement systems where you have control over both participants.

**Q4. What are the main patterns for handling distributed transactions in microservices, and when do you use each?**
A: Four main approaches exist, ordered from strongest consistency to weakest:

| Pattern | Consistency | Availability | Complexity | When to use |
|---|---|---|---|---|
| **Two-Phase Commit (2PC)** | Strong | Low (blocking) | High | Same-org controlled services; financial ledgers; rarely practical |
| **Three-Phase Commit (3PC)** | Strong | Medium | Very high | Theoretical improvement on 2PC; rarely implemented in practice |
| **Saga (choreography)** | Eventual | High | Medium | Most microservice use cases; services independently deployable |
| **Saga (orchestration)** | Eventual | High | Medium-high | Complex workflows; visibility into state required |
| **Try-Confirm/Cancel (TCC)** | Near-strong | Medium | High | Payment and inventory; explicit reservation phase needed |

The default for greenfield microservices is the **Saga pattern** (orchestration or choreography). 2PC is an anti-pattern for most microservice architectures because it requires a distributed lock that couples service availability, reintroduces the monolithic coordination problem, and blocks all participants until the slowest one responds.

**Q5. What is the Two-Phase Commit (2PC) protocol, and why is it considered an anti-pattern in microservices?**
A: Two-Phase Commit is a distributed protocol that attempts to provide atomic commit across multiple independent participants through a central coordinator:

**Phase 1 — Prepare (Voting):**
- Coordinator sends `PREPARE` to all participants.
- Each participant checks if it can commit: acquires locks, writes to its WAL, ensures resources are available.
- Each participant responds `VOTE-COMMIT` (can commit) or `VOTE-ABORT` (cannot commit).
- Participants are now in a blocked state — holding locks, waiting for the coordinator's decision.

**Phase 2 — Commit or Abort:**
- If all participants voted COMMIT → coordinator sends `COMMIT` to all; participants release locks and finalize.
- If any participant voted ABORT → coordinator sends `ROLLBACK` to all; participants undo changes.

```
Coordinator: PREPARE order-service, inventory-service, payment-service
  Order:     VOTE-COMMIT (lock held, WAL written)
  Inventory: VOTE-COMMIT (stock decremented in buffer, lock held)
  Payment:   VOTE-COMMIT (charge authorised, lock held)

Coordinator: COMMIT all
  Order:     ACK — committed, lock released
  Inventory: ACK — committed, lock released
  Payment:   ACK — committed, lock released
```

**Why 2PC is an anti-pattern in microservices:**

```
Problem 1 — Coordinator is a single point of failure:
  If the coordinator crashes after sending PREPARE but before COMMIT,
  all participants are stuck holding locks indefinitely — the system is frozen.
  No participant can proceed without the coordinator's decision.

Problem 2 — Blocking protocol:
  All participants hold locks from Phase 1 until Phase 2 completes.
  If any participant is slow, ALL participants are blocked.
  Under high load, this creates lock cascades and deadlocks.

Problem 3 — Network partition during Phase 2:
  Coordinator sends COMMIT to participant A (received), then network partitions.
  Participant B never receives COMMIT — uncertain state.
  Even 3PC cannot fully resolve this (FLP impossibility theorem).

Problem 4 — Tight coupling:
  All participants must be available simultaneously.
  One service going down blocks the entire business operation.
  This reintroduces the availability coupling that microservices exist to eliminate.

Problem 5 — Database X/A protocol support required:
  Not all databases support XA transactions.
  JPA/Hibernate XA is notoriously fragile and slow.
  Prisma, TypeORM, and most modern Node.js ORMs do not support XA.
```

## Section 2: The Saga Pattern

**Q6. What is the Saga pattern, and how does it provide distributed transaction semantics without 2PC?**
A: The Saga pattern, introduced by Hector Garcia-Molina and Kenneth Salem (1987), decomposes a long-lived distributed transaction into a sequence of **local transactions**, each of which updates a single service and publishes an event or message. If a step fails, a series of **compensating transactions** are executed in reverse order to undo the effects of the preceding successful steps — restoring the system to a semantically consistent state without requiring a distributed lock.

A Saga is NOT a distributed transaction in the 2PC sense — it provides **ACD** without Isolation (the I in ACID):
- **Atomicity** — via compensating transactions (not rollback).
- **Consistency** — eventual; intermediate states are visible.
- **Durability** — each step commits locally to a durable store.
- **Isolation** — **absent**; other sagas can read intermediate state.

```
Business operation: Place Order
  Step 1: Reserve inventory         → compensating: Release inventory reservation
  Step 2: Charge payment            → compensating: Issue refund
  Step 3: Create order record       → compensating: Cancel order
  Step 4: Schedule shipping         → compensating: Cancel shipment

Happy path:
  Reserve inventory ✓ → Charge payment ✓ → Create order ✓ → Schedule shipping ✓
  → All committed, system consistent

Failure at Step 3 (payment succeeded, order creation failed):
  Reserve inventory ✓ → Charge payment ✓ → Create order ✗
  → Compensate Step 2: Issue refund ✓
  → Compensate Step 1: Release inventory reservation ✓
  → System back to pre-saga state (eventually consistent)
```

**Critical property** — compensating transactions must be **idempotent** (safe to run multiple times) and **commutative** where possible (order shouldn't matter). A compensation that fails must be retried — the saga cannot be "half compensated."

**Q7. What are the two coordination styles of the Saga pattern — Choreography and Orchestration — and what are their trade-offs?**
A:

**Saga Choreography — event-driven, no central coordinator:**
Each service listens for events from other services and decides what to do next. Services are decoupled — they know their own step and which events trigger their action, but no service has a global view.

```
OrderService publishes "order.created"
  → InventoryService listens → reserves stock → publishes "inventory.reserved"
  → PaymentService listens → charges card → publishes "payment.completed"
  → ShippingService listens → schedules delivery → publishes "shipment.scheduled"

Failure — PaymentService fails to charge → publishes "payment.failed"
  → InventoryService listens for "payment.failed" → releases reservation
  → OrderService listens for "payment.failed" → marks order as failed
```

**Saga Orchestration — central orchestrator coordinates all steps:**
A dedicated orchestrator service (or use case class) explicitly calls each participant in sequence, handles failures, and triggers compensations. The orchestrator has full visibility into the saga's state.

```
OrderSagaOrchestrator:
  1. Call InventoryService.reserve()  → success
  2. Call PaymentService.charge()     → success
  3. Call OrderService.createOrder()  → FAILURE
  → Trigger compensation:
  4. Call PaymentService.refund()     → success
  5. Call InventoryService.release()  → success
  → Saga failed; state = COMPENSATED
```

| Aspect | Choreography | Orchestration |
|---|---|---|
| **Coupling** | Loose — services only know their event contracts | Tighter — orchestrator knows all participants |
| **Visibility** | Hard — must trace events across services to understand flow | Easy — orchestrator's state machine = the flow |
| **Debugging** | Hard — distributed event trail; requires distributed tracing | Easier — orchestrator logs show full saga state |
| **Single point of failure** | None — each service is independent | Orchestrator is critical — must be HA |
| **Complexity** | Lower per-service, higher overall system complexity | Higher per-orchestrator, lower per-service |
| **Cyclic dependencies** | Risk — services can inadvertently create event cycles | Prevented — orchestrator is the only caller |
| **Adding a step** | Modify event contracts — can break existing listeners | Modify orchestrator — contained change |
| **Best for** | Simple, well-defined flows with few steps | Complex workflows, many steps, frequent changes, auditability required |

**Q8. How do you implement a Saga Orchestrator in TypeScript?**
A:
```ts
// Saga state — persisted so orchestrator can resume after crash
type SagaStatus =
  | "STARTED"
  | "INVENTORY_RESERVED"
  | "PAYMENT_COMPLETED"
  | "ORDER_CREATED"
  | "COMPLETED"
  | "COMPENSATING"
  | "COMPENSATED"
  | "FAILED";

interface OrderSagaState {
  sagaId:        string;
  status:        SagaStatus;
  orderId?:      string;
  reservationId?: string;
  chargeId?:     string;
  shipmentId?:   string;
  failureReason?: string;
  createdAt:     Date;
  updatedAt:     Date;
}

interface PlaceOrderSagaInput {
  customerId:   string;
  items:        OrderItem[];
  paymentToken: string;
  address:      ShippingAddress;
}

// Orchestrator — owns the saga state machine
class PlaceOrderSagaOrchestrator {
  constructor(
    private readonly sagaRepo:   SagaRepository,
    private readonly inventory:  InventoryService,
    private readonly payment:    PaymentService,
    private readonly orders:     OrderService,
    private readonly shipping:   ShippingService,
    private readonly events:     EventBus,
    private readonly logger:     Logger
  ) {}

  async execute(input: PlaceOrderSagaInput): Promise<{ orderId: string }> {
    // Initialise saga state — persisted before any step executes
    const state = await this.sagaRepo.create({
      sagaId:    crypto.randomUUID(),
      status:    "STARTED",
      createdAt: new Date(),
      updatedAt: new Date(),
    });

    this.logger.info("Saga started", { sagaId: state.sagaId });

    try {
      // Step 1 — Reserve inventory
      state.status = "INVENTORY_RESERVED"; // optimistic — set before calling
      const reservation = await this.inventory.reserve(input.items);
      state.reservationId = reservation.id;
      await this.sagaRepo.update(state);

      // Step 2 — Charge payment
      state.status = "PAYMENT_COMPLETED";
      const charge = await this.payment.charge(
        this.calculateTotal(input.items),
        input.paymentToken
      );
      state.chargeId = charge.id;
      await this.sagaRepo.update(state);

      // Step 3 — Create order record
      state.status = "ORDER_CREATED";
      const order = await this.orders.create({
        customerId:    input.customerId,
        items:         input.items,
        chargeId:      charge.id,
        reservationId: reservation.id,
      });
      state.orderId = order.id;
      await this.sagaRepo.update(state);

      // Step 4 — Schedule shipping (non-critical — don't compensate on failure)
      try {
        const shipment = await this.shipping.schedule(order.id, input.address);
        state.shipmentId = shipment.id;
      } catch (err) {
        this.logger.warn("Shipping scheduling failed — order still complete", {
          sagaId: state.sagaId, err
        });
        // Non-critical: shipping can be scheduled later; don't compensate
      }

      // Saga complete
      state.status = "COMPLETED";
      await this.sagaRepo.update(state);

      await this.events.publish({
        type:    "order.saga.completed",
        payload: { sagaId: state.sagaId, orderId: order.id },
      });

      this.logger.info("Saga completed", { sagaId: state.sagaId, orderId: order.id });
      return { orderId: order.id };

    } catch (err) {
      const reason = (err as Error).message;
      this.logger.error("Saga step failed — starting compensation", {
        sagaId: state.sagaId, status: state.status, reason
      });

      state.failureReason = reason;
      await this.compensate(state);
      throw new SagaFailedError(`Order placement saga failed: ${reason}`, state.sagaId);
    }
  }

  private async compensate(state: OrderSagaState): Promise<void> {
    state.status = "COMPENSATING";
    await this.sagaRepo.update(state);

    const errors: Error[] = [];

    // Compensate in reverse order — only steps that completed
    if (state.orderId) {
      await this.orders.cancel(state.orderId, "Saga compensation")
        .catch(err => { errors.push(err); this.logger.error("Order cancel compensation failed", { err }); });
    }

    if (state.chargeId) {
      await this.payment.refund(state.chargeId)
        .catch(err => { errors.push(err); this.logger.error("Payment refund compensation failed", { err }); });
    }

    if (state.reservationId) {
      await this.inventory.release(state.reservationId)
        .catch(err => { errors.push(err); this.logger.error("Inventory release compensation failed", { err }); });
    }

    if (errors.length > 0) {
      // Compensation partially failed — requires manual intervention
      state.status = "FAILED";
      state.failureReason = `Compensation failures: ${errors.map(e => e.message).join("; ")}`;
      await this.sagaRepo.update(state);
      await this.alerting.trigger("saga_compensation_failed", { sagaId: state.sagaId, errors });
    } else {
      state.status = "COMPENSATED";
      await this.sagaRepo.update(state);
    }

    this.logger.info("Saga compensation complete", {
      sagaId: state.sagaId, status: state.status
    });
  }

  private calculateTotal(items: OrderItem[]): number {
    return items.reduce((sum, i) => sum + i.price * i.quantity, 0);
  }
}
```

**Q9. How do you implement a Saga using Choreography — event-driven, no central orchestrator?**
A:
```ts
// Each service listens to events and reacts — no central coordinator

// Order Service — initiates the saga by publishing an event
class OrderService {
  async createPendingOrder(dto: PlaceOrderDto): Promise<{ orderId: string }> {
    // Create order in PENDING state — not yet confirmed
    const order = await this.orderRepo.create({
      ...dto,
      status: "PENDING",
    });

    // Publish the saga-initiating event
    await this.outbox.enqueue({
      eventType:   "order.placement.started",
      aggregateId: order.id,
      payload:     JSON.stringify({
        orderId:    order.id,
        customerId: dto.customerId,
        items:      dto.items,
        total:      dto.total,
        sagaId:     order.id, // use orderId as sagaId for simplicity
      }),
    });

    return { orderId: order.id };
  }

  // Listens for saga outcomes — updates order status
  @EventPattern("inventory.reservation.failed")
  async onInventoryFailed(event: InventoryReservationFailedEvent): Promise<void> {
    await this.orderRepo.update(event.orderId, { status: "FAILED" });
    logger.warn("Order failed — inventory unavailable", { orderId: event.orderId });
  }

  @EventPattern("payment.charged")
  async onPaymentCharged(event: PaymentChargedEvent): Promise<void> {
    await this.orderRepo.update(event.orderId, {
      status: "CONFIRMED",
      chargeId: event.chargeId,
    });
    // Publish order confirmed — shipping service listens
    await this.outbox.enqueue({
      eventType:   "order.confirmed",
      aggregateId: event.orderId,
      payload:     JSON.stringify({ orderId: event.orderId, chargeId: event.chargeId }),
    });
  }

  @EventPattern("payment.charge.failed")
  async onPaymentFailed(event: PaymentChargeFailedEvent): Promise<void> {
    await this.orderRepo.update(event.orderId, { status: "FAILED" });
    // Request inventory compensation
    await this.outbox.enqueue({
      eventType:   "order.compensation.requested",
      aggregateId: event.orderId,
      payload:     JSON.stringify({
        orderId:       event.orderId,
        reservationId: event.reservationId,
      }),
    });
  }
}

// Inventory Service — listens and reserves; knows its own compensation
class InventoryService {
  @EventPattern("order.placement.started")
  async onOrderStarted(event: OrderPlacementStartedEvent): Promise<void> {
    try {
      const reservation = await this.inventoryRepo.reserve(event.items, event.orderId);
      await this.outbox.enqueue({
        eventType:   "inventory.reserved",
        aggregateId: event.orderId,
        payload:     JSON.stringify({
          orderId:       event.orderId,
          reservationId: reservation.id,
          items:         event.items,
          total:         event.total,
        }),
      });
    } catch (err) {
      await this.outbox.enqueue({
        eventType:   "inventory.reservation.failed",
        aggregateId: event.orderId,
        payload:     JSON.stringify({
          orderId: event.orderId,
          reason:  (err as Error).message,
        }),
      });
    }
  }

  // Compensating transaction — triggered by downstream failure
  @EventPattern("order.compensation.requested")
  async onCompensationRequested(event: CompensationRequestedEvent): Promise<void> {
    if (!event.reservationId) return; // nothing to release
    await this.inventoryRepo.release(event.reservationId);
    logger.info("Inventory reservation released as compensation", {
      orderId:       event.orderId,
      reservationId: event.reservationId,
    });
  }
}

// Payment Service — listens for inventory.reserved, charges card
class PaymentService {
  @EventPattern("inventory.reserved")
  async onInventoryReserved(event: InventoryReservedEvent): Promise<void> {
    try {
      const charge = await this.paymentGateway.charge(event.total, event.paymentToken);
      await this.outbox.enqueue({
        eventType:   "payment.charged",
        aggregateId: event.orderId,
        payload:     JSON.stringify({
          orderId:       event.orderId,
          chargeId:      charge.id,
          reservationId: event.reservationId,
        }),
      });
    } catch (err) {
      await this.outbox.enqueue({
        eventType:   "payment.charge.failed",
        aggregateId: event.orderId,
        payload:     JSON.stringify({
          orderId:       event.orderId,
          reservationId: event.reservationId, // needed for compensation
          reason:        (err as Error).message,
        }),
      });
    }
  }
}
```

## Section 3: Try-Confirm/Cancel (TCC)

**Q10. What is the Try-Confirm/Cancel (TCC) pattern, and how does it differ from Saga?**
A: TCC (also called Two-Phase Business Transaction) is a distributed transaction pattern that provides near-strong consistency by introducing an explicit **reservation phase** before finalising. It has three operations per participant:

- **Try** — reserves resources tentatively without committing. Creates a "pending" or "reserved" state that other transactions can see but cannot consume. All participants must succeed in the Try phase before any Confirm is issued.
- **Confirm** — finalises the reservation. Converts "pending" state to "committed". Must be idempotent — the coordinator retries until all Confirms succeed.
- **Cancel** — releases the reservation. Undoes the Try. Must also be idempotent.

```ts
// TCC — explicit three-phase per participant
class InventoryTCCParticipant {
  // Phase 1: Try — reserve without committing
  async try(orderId: string, items: OrderItem[]): Promise<TryResult> {
    // Check availability and create a tentative reservation
    for (const item of items) {
      const stock = await this.stockRepo.findByProductId(item.productId);
      if (stock.available < item.quantity) {
        return { success: false, reason: `Insufficient stock for ${item.productId}` };
      }
    }

    // Decrement available, mark as "tentatively reserved" — others cannot use this stock
    const reservation = await this.reservationRepo.create({
      orderId,
      items,
      status:    "TENTATIVE",
      expiresAt: new Date(Date.now() + 30_000), // auto-cancel after 30s if no Confirm
    });

    await this.stockRepo.decrementAvailable(items); // reduce available stock
    return { success: true, reservationId: reservation.id };
  }

  // Phase 2a: Confirm — finalise the reservation
  async confirm(reservationId: string): Promise<void> {
    const reservation = await this.reservationRepo.findById(reservationId);
    if (!reservation || reservation.status === "CONFIRMED") return; // idempotent
    if (reservation.status === "CANCELLED") throw new Error("Cannot confirm cancelled reservation");

    await this.reservationRepo.update(reservationId, { status: "CONFIRMED" });
    // Stock already decremented in Try — nothing more to do
  }

  // Phase 2b: Cancel — release the tentative reservation
  async cancel(reservationId: string): Promise<void> {
    const reservation = await this.reservationRepo.findById(reservationId);
    if (!reservation || reservation.status === "CANCELLED") return; // idempotent
    if (reservation.status === "CONFIRMED") throw new Error("Cannot cancel confirmed reservation");

    await this.reservationRepo.update(reservationId, { status: "CANCELLED" });
    await this.stockRepo.incrementAvailable(reservation.items); // restore available stock
  }
}

// TCC Coordinator — orchestrates Try phase, then Confirm or Cancel
class TCCCoordinator {
  async execute(input: PlaceOrderInput): Promise<{ orderId: string }> {
    // Phase 1: Try all participants simultaneously
    const [inventoryTry, paymentTry] = await Promise.all([
      this.inventory.try(input.orderId, input.items),
      this.payment.try(input.orderId, input.amount, input.paymentToken),
    ]);

    if (!inventoryTry.success || !paymentTry.success) {
      // Cancel any successful Tries — order independent (both can proceed in parallel)
      await Promise.allSettled([
        inventoryTry.success ? this.inventory.cancel(inventoryTry.reservationId!) : Promise.resolve(),
        paymentTry.success   ? this.payment.cancel(paymentTry.authorizationId!)  : Promise.resolve(),
      ]);
      throw new BusinessError(`Order cannot proceed: ${inventoryTry.reason ?? paymentTry.reason}`);
    }

    // Phase 2: Confirm all participants — must retry until all succeed
    await this.confirmWithRetry(inventoryTry.reservationId!, paymentTry.authorizationId!);

    return { orderId: input.orderId };
  }

  private async confirmWithRetry(reservationId: string, authorizationId: string): Promise<void> {
    // Confirm must succeed — retry indefinitely (within reasonable bounds)
    // A failed Confirm is a critical error requiring manual intervention
    for (let attempt = 1; attempt <= 10; attempt++) {
      try {
        await Promise.all([
          this.inventory.confirm(reservationId),
          this.payment.confirm(authorizationId),
        ]);
        return; // success
      } catch (err) {
        if (attempt === 10) {
          await this.alerting.trigger("tcc_confirm_failed", { reservationId, authorizationId });
          throw new CriticalError("TCC Confirm failed after 10 attempts — manual intervention required");
        }
        await new Promise(r => setTimeout(r, 1000 * attempt));
      }
    }
  }
}
```

**TCC vs Saga comparison:**

| Aspect | Saga | TCC |
|---|---|---|
| **Consistency window** | Wider — intermediate states visible until compensation | Narrower — Try phase hides reservations from other sagas |
| **Compensation** | After-the-fact rollback (may have real-world effects) | Before-commit cancel (reservation simply released) |
| **Isolation** | None — dirty reads possible | Partial — Try resources are reserved (not shared) |
| **Complexity** | Lower per-service | Higher — each service needs Try/Confirm/Cancel APIs |
| **Timeout handling** | Compensation saga | Reservation expiry (auto-cancel after timeout) |
| **Best for** | Most use cases; complex workflows | Financial transactions; seat/hotel/ticket booking |

## Section 4: Handling Compensating Transactions

**Q11. What makes a compensating transaction different from a rollback, and what properties must it have?**
A: A database rollback undoes changes as if they never happened — it is invisible. A compensating transaction is a real, new transaction that creates a semantic inverse of a previously committed transaction — it is visible and auditable.

```
Database rollback (local):
  BEGIN; UPDATE balance SET amount = amount - 100; ROLLBACK;
  // The debit never happened — no trace, no audit log ✓ (for the DB itself)

Compensating transaction (distributed):
  T=0: Charge $100 from account A → committed, visible, in audit log
  T=1: Payment service crashes
  T=2: Compensation: Credit $100 back to account A → new committed transaction
  // Both the debit AND the credit appear in the audit log
  // The net effect is zero, but both operations are visible ✓
```

**Properties a compensating transaction must have:**

**Idempotency** — the compensation must be safe to execute multiple times. If the compensating transaction itself fails and is retried, retrying it must not produce incorrect results:
```ts
// Non-idempotent compensation — dangerous
async function refund(chargeId: string, amount: number): Promise<void> {
  await paymentGateway.createRefund({ chargeId, amount }); // creates a NEW refund each call ✗
}

// Idempotent compensation — correct
async function refund(chargeId: string, amount: number): Promise<void> {
  const existing = await refundRepo.findByChargeId(chargeId);
  if (existing) return; // already refunded — skip ✓

  await paymentGateway.createRefund({ chargeId, amount, idempotencyKey: chargeId });
  await refundRepo.create({ chargeId, amount, refundedAt: new Date() });
}
```

**Semantic correctness, not technical rollback** — the compensation achieves the business intent of undoing the action, not a technical rewind:
```ts
// Inventory compensation — release reservation, restore available count
async function releaseReservation(reservationId: string): Promise<void> {
  const reservation = await reservationRepo.findById(reservationId);
  if (!reservation || reservation.status === "RELEASED") return; // idempotent

  await inventoryRepo.incrementAvailable(reservation.items); // restore stock
  await reservationRepo.update(reservationId, {
    status:     "RELEASED",
    releasedAt: new Date(),
    reason:     "saga_compensation",
  });
  // Audit trail: both the reservation AND the release are recorded
}
```

**Not always possible** — some actions cannot be compensated (sending an email, printing a physical label). For these, the system must:
- Note them as "completed but uncompensatable" in the saga state.
- Design the process so uncompensatable actions happen last (after all compensatable steps succeed).
- Or use a "countermeasure" — sending a follow-up email saying "your order was cancelled."

**Q12. How do you handle a failing compensating transaction — when compensation itself fails?**
A: A failed compensation is a critical situation — the system is in an inconsistent state that cannot resolve itself. The response is:

```ts
class SagaCompensationHandler {
  async compensate(state: SagaState): Promise<CompensationResult> {
    const failures: CompensationFailure[] = [];

    // Attempt each compensation step — collect failures, don't stop
    for (const step of state.completedSteps.reverse()) {
      try {
        await this.executeCompensation(step, state);
        this.logger.info("Compensation step succeeded", { step: step.name, sagaId: state.sagaId });
      } catch (err) {
        failures.push({ step: step.name, error: (err as Error).message });
        this.logger.error("Compensation step failed", {
          step:   step.name,
          sagaId: state.sagaId,
          err
        });
      }
    }

    if (failures.length > 0) {
      // Mark saga as requiring manual intervention
      await this.sagaRepo.update(state.sagaId, {
        status:            "COMPENSATION_FAILED",
        compensationErrors: failures,
        requiresIntervention: true,
      });

      // Alert immediately — this needs a human
      await this.alerting.critical("saga_compensation_failed", {
        sagaId:   state.sagaId,
        failures,
        message:  "Saga compensation failed — system is in inconsistent state. Manual intervention required.",
      });

      // Publish event for other systems to freeze related entities
      await this.events.publish({
        type:    "saga.compensation.failed",
        payload: { sagaId: state.sagaId, failures },
      });

      return { success: false, failures };
    }

    return { success: true, failures: [] };
  }

  private async executeCompensation(step: CompletedStep, state: SagaState): Promise<void> {
    // Retry with exponential backoff before declaring failure
    for (let attempt = 1; attempt <= 5; attempt++) {
      try {
        switch (step.name) {
          case "inventory.reserve":
            await this.inventory.release(step.result.reservationId);
            break;
          case "payment.charge":
            await this.payment.refund(step.result.chargeId);
            break;
          case "order.create":
            await this.orders.cancel(step.result.orderId, "saga_compensation");
            break;
        }
        return; // success
      } catch (err) {
        if (attempt === 5) throw err; // all retries exhausted
        await new Promise(r => setTimeout(r, 500 * Math.pow(2, attempt)));
      }
    }
  }
}
```

**Q13. How do you implement a durable saga state machine that survives service restarts?**
A: The saga state must be persisted after every step — the orchestrator must be able to resume a saga from exactly where it left off after a crash:

```ts
// Saga state persisted in DB — resumed on restart
class DurableSagaOrchestrator {
  // On startup — find and resume any in-progress sagas
  async resumeInProgressSagas(): Promise<void> {
    const inProgressSagas = await this.sagaRepo.findByStatus([
      "STARTED",
      "INVENTORY_RESERVED",
      "PAYMENT_COMPLETED",
      "ORDER_CREATED",
      "COMPENSATING",
    ]);

    this.logger.info(`Resuming ${inProgressSagas.length} in-progress sagas`);

    for (const saga of inProgressSagas) {
      this.resumeSaga(saga).catch(err =>
        this.logger.error("Failed to resume saga", { sagaId: saga.sagaId, err })
      );
    }
  }

  private async resumeSaga(state: SagaState): Promise<void> {
    this.logger.info("Resuming saga from checkpoint", {
      sagaId: state.sagaId,
      status: state.status
    });

    // Reconstruct input from saved state
    const input = state.input as PlaceOrderSagaInput;

    try {
      // Resume from the last successfully persisted step
      switch (state.status) {
        case "STARTED":
          // Nothing committed — restart from Step 1
          await this.executeFromStep1(state, input);
          break;

        case "INVENTORY_RESERVED":
          // Step 1 done — resume from Step 2 (payment)
          await this.executeFromStep2(state, input);
          break;

        case "PAYMENT_COMPLETED":
          // Steps 1+2 done — resume from Step 3 (order creation)
          await this.executeFromStep3(state, input);
          break;

        case "ORDER_CREATED":
          // Steps 1-3 done — resume from Step 4 (shipping)
          await this.executeFromStep4(state, input);
          break;

        case "COMPENSATING":
          // Crash during compensation — resume compensation
          await this.compensate(state);
          break;
      }
    } catch (err) {
      this.logger.error("Saga resume failed — starting compensation", {
        sagaId: state.sagaId, err
      });
      await this.compensate(state);
    }
  }

  // Persist state BEFORE executing each step (write-ahead logging principle)
  private async persistAndExecute<T>(
    state:     SagaState,
    newStatus: SagaStatus,
    operation: () => Promise<T>
  ): Promise<T> {
    // Write intended state BEFORE executing — if we crash after the write but before
    // the operation, we'll retry the operation on resume (idempotent operations handle this)
    await this.sagaRepo.update(state.sagaId, {
      status:    newStatus,
      updatedAt: new Date(),
    });

    return operation();
  }
}

// Saga timeout — detect and compensate stuck sagas
class SagaTimeoutMonitor {
  async checkForStuckSagas(): Promise<void> {
    const SAGA_TIMEOUT_MINUTES = 15;
    const cutoff = new Date(Date.now() - SAGA_TIMEOUT_MINUTES * 60 * 1000);

    const stuckSagas = await this.sagaRepo.findMany({
      where: {
        status:    { in: ["STARTED", "INVENTORY_RESERVED", "PAYMENT_COMPLETED"] },
        updatedAt: { lt: cutoff },
      },
    });

    for (const saga of stuckSagas) {
      this.logger.warn("Stuck saga detected — triggering compensation", {
        sagaId:    saga.sagaId,
        status:    saga.status,
        stuckSince: saga.updatedAt,
      });
      await this.orchestrator.compensate(saga);
    }
  }
}
```

```ts
// Temporal workflow — durable, resumable, handles timeouts and retries automatically
import * as workflow from "@temporalio/workflow";
import type * as activities from "./activities";

const { reserveInventory, chargePayment, createOrder, scheduleShipping,
        releaseInventory, refundPayment, cancelOrder } =
  workflow.proxyActivities<typeof activities>({
    startToCloseTimeout: "30 seconds",
    retry: { maximumAttempts: 3 },
  });

// Temporal workflow — automatically persisted, resumable after crash
export async function placeOrderWorkflow(input: PlaceOrderInput): Promise<{ orderId: string }> {
  let reservationId: string | undefined;
  let chargeId:      string | undefined;
  let orderId:       string | undefined;

  try {
    // Temporal automatically retries failed activities
    // Workflow state is durably persisted in Temporal's event sourced journal
    const reservation = await reserveInventory(input.items);
    reservationId = reservation.id;

    const charge = await chargePayment(input.amount, input.paymentToken);
    chargeId = charge.id;

    const order = await createOrder({ ...input, chargeId, reservationId });
    orderId = order.id;

    await scheduleShipping(order.id, input.address);

    return { orderId };
  } catch (err) {
    // Compensate — Temporal retries each compensation until it succeeds
    if (orderId)       await cancelOrder(orderId).catch(() => {});
    if (chargeId)      await refundPayment(chargeId).catch(() => {});
    if (reservationId) await releaseInventory(reservationId).catch(() => {});
    throw err;
  }
}

}
```

## Section 7: Scenario / System Design Style Questions

**Q16. "A junior dev suggests using 2PC to guarantee that when an order is placed, the inventory and payment databases are updated atomically. You're the senior engineer. What is your response?"**
A: Acknowledge the intent, then explain why 2PC is the wrong tool for this context:

> "The goal — atomic consistency across inventory and payment — is absolutely right. The issue is that 2PC achieves it at a cost that's unacceptable for most microservice architectures.
>
> First, 2PC requires all participants to be available simultaneously. If the inventory service is doing a deploy and takes 10 seconds to restart, the entire order placement operation is blocked — with locks held — for those 10 seconds. One slow service brings down the whole flow. That's the availability coupling that microservices exist to eliminate.
>
> Second, the coordinator is a single point of failure. If it crashes after sending PREPARE but before COMMIT, all participants are stuck holding locks indefinitely. Recovery requires manual intervention or a complex recovery protocol.
>
> Third, Prisma, TypeORM, and most modern Node.js database clients don't support XA transactions — the distributed transaction protocol 2PC uses. We'd need to fall back to lower-level driver APIs.
>
> The better approach is the Saga pattern with the Outbox Pattern for event publishing. The order and inventory reservation commit locally and atomically within their own services. If payment fails, a compensating transaction releases the inventory reservation. Yes, there's a brief window of inconsistency — the inventory shows reserved but payment is pending — but that's a real business state we can model and handle."

Then sketch the Saga:
```ts
// Instead of 2PC — Saga with compensation
// Step 1: Reserve inventory (commits locally)
// Step 2: Charge payment (commits locally)
//   → If fails: release inventory reservation (compensating transaction)
// Step 3: Create order record
// Net effect: either all three complete, or compensation restores initial state
// Intermediate state is brief and modelled — not a database error
```

**Q17. "Design the distributed transaction strategy for a flight booking system where a customer must pay for a seat, and the seat must be reserved on the plane — both or neither."**
A: This is a classic TCC use case — the reservation must be exclusive (no double-booking) but the payment must not be charged before the seat is confirmed:

```ts
// TCC is ideal here:
// - Try: tentatively reserve the seat (other customers cannot book it)
// - Try: authorise the payment (card auth, not capture)
// - Confirm: finalise seat reservation + capture payment
// - Cancel: release seat + void card auth

// Why TCC over Saga here:
// - Saga with choreography risks "dirty reads":
//   Customer A sees Seat 14A available → Saga Step 1 commits reservation
//   Between Step 1 and Step 2, Customer B reads inventory → seat appears available → double book
// - TCC prevents this: seat is in TENTATIVE state during Try phase
//   Customer B cannot book TENTATIVE seats

class FlightBookingTCCOrchestrator {
  async bookFlight(dto: BookFlightDto): Promise<{ bookingId: string }> {
    // Phase 1 — Try: both must succeed
    const [seatTry, paymentTry] = await Promise.all([
      this.seats.try({
        flightId:  dto.flightId,
        seatNumber: dto.seatNumber,
        bookingId:  dto.bookingId, // idempotency key
      }),
      this.payment.try({
        amount:       dto.amount,
        cardToken:    dto.paymentToken,
        bookingId:    dto.bookingId,
        expiresIn:    30, // card auth valid for 30 minutes
      }),
    ]);

    if (!seatTry.success) {
      if (paymentTry.success) {
        await this.payment.cancel(paymentTry.authId); // void the card auth
      }
      throw new SeatUnavailableError(dto.seatNumber, dto.flightId);
    }

    if (!paymentTry.success) {
      await this.seats.cancel(seatTry.holdId); // release seat hold
      throw new PaymentDeclinedError(paymentTry.reason);
    }

    // Phase 2 — Confirm: both must succeed (retry until they do)
    await this.confirmBothWithRetry(seatTry.holdId, paymentTry.authId, dto.bookingId);

    return { bookingId: dto.bookingId };
  }

  private async confirmBothWithRetry(
    holdId:    string,
    authId:    string,
    bookingId: string
  ): Promise<void> {
    const MAX_ATTEMPTS = 10;
    for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
      try {
        await Promise.all([
          this.seats.confirm(holdId),    // idempotent
          this.payment.confirm(authId),  // idempotent (capture)
        ]);

        // Record confirmed booking
        await this.bookings.create({ bookingId, holdId, authId, status: "CONFIRMED" });
        return;
      } catch (err) {
        if (attempt === MAX_ATTEMPTS) {
          // Cannot confirm — seat is tentatively held, payment is authorised
          // This is a critical inconsistency — alert immediately
          await this.alerting.critical("tcc_confirm_failed", { holdId, authId, bookingId });
          throw new CriticalBookingError("Booking confirmation failed — manual intervention required");
        }
        await new Promise(r => setTimeout(r, 500 * attempt));
      }
    }
  }
}

// Seat hold expiry — cron job releases expired tentative holds
// Prevents holds from blocking seats indefinitely if coordinator crashes

  async run(): Promise<void> {
    const expired = await this.seatHolds.findExpired();
```

**Q18. "Your team is running an e-commerce platform and the CTO asks: 'Should we use Saga or TCC for our order placement flow?' How do you answer?"**
A: Frame the answer around the specific consistency requirement and operational cost:

> **Saga is the right default** for most e-commerce order flows. Here's why:
>
> The brief inconsistency window in a Saga (inventory reserved, payment not yet charged) maps to a real business state — 'order pending payment' — which the business already models. This window is typically 200ms–2s. In practice, customers don't browse inventory in that window for the same item.
>
> Saga is simpler to implement and operate: each service owns its step and its compensating transaction. Adding a new step (e.g., loyalty points) means adding a new listener — no changes to existing services.
>
> **TCC makes sense if** we have high-volume SKUs where the inventory window matters (flash sales, limited-edition drops, concert tickets). In those cases:
> - Multiple customers see the same low-stock item simultaneously
> - Without TCC's Try phase, two customers can both see "1 item available" and both try to purchase — one will fail at the inventory step after payment authorisation
> - TCC's tentative reservation prevents this: once Customer A's Try locks the last item, Customer B's Try fails immediately with "sold out"
>
> **Recommendation**: Use Saga as the default. Implement TCC only for specific high-contention scenarios (flash sales, limited inventory). The operational cost of TCC (every service needs Try/Confirm/Cancel APIs, plus expiry handling for tentative holds) is only justified when the business impact of double-booking is significant.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | 2PC | Saga (Choreography) | Saga (Orchestration) | TCC |
|---|---|---|---|---|
| **Consistency** | Strong (ACID) | Eventual | Eventual | Near-strong |
| **Isolation** | Full | None | None | Partial (Try-phase) |
| **Availability** | Low (blocking) | High | High | Medium |
| **Coordinator** | Required (blocking) | None | Required (non-blocking) | Required |
| **Compensating tx** | None (rollback) | Required | Required | Cancel (before commit) |
| **Failure recovery** | Coordinator restart | Event replay | Orchestrator resume | Hold expiry |
| **Intermediate states** | Hidden | Visible | Visible | Partially hidden (holds) |
| **Services need** | XA support | Event contracts | No specific API | Try/Confirm/Cancel APIs |
| **Ordering guarantee** | Full | Depends on broker | Orchestrator ensures it | Coordinator ensures it |
| **Tooling** | XA libraries | Kafka, RabbitMQ | Temporal, Conductor | Custom |
| **Best for** | Same-org, controlled DBs | Simple event-driven flows | Complex workflows | Financial, reservation systems |

## Distributed Transaction Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **2PC in microservices** | Using XA distributed transactions across independently deployed services | Replace with Saga pattern; accept eventual consistency |
| **Compensations without idempotency** | Retrying a compensation that creates duplicate refunds, releases, or cancels | All compensating transactions must check if already applied before executing |
| **Saga without outbox** | Publishing events from the saga directly to the broker — dual-write problem | Use Outbox Pattern; events committed atomically with saga state |
| **Choreography without dead-letter** | Events that fail processing are silently dropped | All event consumers must have a DLQ and alert on DLQ growth |
| **Missing saga timeout** | Stuck sagas hold resources indefinitely — reservation never released | Run a timeout monitor; auto-compensate sagas stuck beyond threshold |
| **Compensation after non-compensatable step** | Sending a physical confirmation email, then trying to "uncancel" it | Non-compensatable steps must be last; use countermeasures (e.g., cancellation email) |
| **Dirty reads in Saga** | Another transaction reads intermediate state as if it were final | Document acceptable intermediate states; add guard checks; or switch to TCC for high-contention |
| **Missing saga state persistence** | Orchestrator crashes — saga cannot be resumed | Persist saga state after every step before executing the next |
| **Compensation as synchronous call** | Blocking the compensation on a slow service — compensation chain stalls | Compensations should be asynchronous or via Outbox; orchestrator retries independently |
| **No saga monitoring** | Stuck, failed, and compensating sagas accumulate silently | Dashboard and alerts for saga status distribution; alert on FAILED or old COMPENSATING |

**Tip for the interview:** At the 5 YOE level, "what is a distributed transaction" surfaces as: how do you guarantee that placing an order updates inventory and payment atomically when they are separate services, why did the engineer suggest 2PC and why is that wrong for microservices, how do you design the saga for a flight booking where double-booking is catastrophic, or what happens when the compensating transaction fails and how do you recover. The sharp answer immediately names the dual-write impossibility as the root problem, explains why 2PC trades availability for consistency and is therefore an anti-pattern for independently deployable services (any participant going down blocks the whole operation), describes the Saga pattern with both its happy path and its compensation chain, explains that compensation is not rollback (it's a new committed transaction — both original and compensation are in the audit log), addresses the case where compensation fails (saga enters FAILED state, alert fires, human intervenes), and names the operational properties compensations must have (idempotent, retry-safe). Distinguishing when Saga is sufficient from when TCC is needed — "Saga is the default; TCC is for high-contention reservation scenarios where the brief inconsistency window causes real double-booking problems" — is the design depth that lands at 5 YOE.
