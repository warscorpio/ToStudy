# Microservices Design Patterns: Strangler Fig Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Strangler Fig pattern?**
A: The Strangler Fig pattern is an incremental migration strategy for replacing a legacy system — typically a monolith — with a new system, by gradually building the replacement alongside the existing system and routing traffic to it piece by piece until the legacy system can be decommissioned entirely. The pattern was named and described by Martin Fowler in 2004, drawing an analogy from the strangler fig tree: a tropical plant that grows around a host tree, gradually replacing it over years until the host tree rots away and the fig stands independently.

The defining characteristic of the pattern is that the migration is *incremental and reversible at every step*. At no point is there a "big bang" cutover where the old system is replaced all at once. Instead, individual capabilities — one endpoint, one feature, one domain — are extracted and replaced one by one, with the façade (typically an API gateway or reverse proxy) routing each request to either the old or new system. The monolith shrinks as the new system grows, until the monolith handles nothing and can be deleted.

**Q2. What problem does the Strangler Fig pattern solve, and why is a big-bang rewrite dangerous?**
A: It solves the *replacement risk* problem — how to modernise or replace a working system without stopping the world, betting the company on a single cutover, or losing business functionality during the transition.

**Why big-bang rewrites fail:**
- **The system is never fully understood** — a legacy monolith accumulated years of behaviour, edge cases, and implicit contracts that no one fully documented. A full rewrite starts with an incomplete understanding and discovers missing behaviour only when production traffic exposes it.
- **The target moves** — during the 18 months it takes to rewrite the system, the business continues adding features to the old system. By the time the rewrite is "done," it's already behind.
- **No reversibility** — a big-bang cutover is a binary event. If it goes wrong, rolling back means switching the entire system back — often impossible after users have accumulated data in the new system.
- **Integration complexity compounds** — when everything is replaced simultaneously, every dependency, integration, and data migration must be solved at once. Each dependency is a potential failure mode on launch day.
- **Joel Spolsky's Law** — in 2000, Joel Spolsky described the big-bang rewrite as "the single worst strategic mistake that any software company can make." The observation holds: Netscape's rewrite of the browser codebase, the second system effect in flight control systems, and countless enterprise ERP replacements validate this empirically.

The Strangler Fig's answer: replace the system incrementally, keep the old system running in parallel, route traffic gradually, and validate each increment independently. At every point in the migration, the system works — either on the old code or the new code or both. Risk is bounded to each small increment rather than accumulated across the entire migration.

**Q3. What are the three phases of the Strangler Fig pattern?**
A: Fowler identifies three phases, applied iteratively to each capability being extracted:

**Phase 1 — Transform:**
Build the new capability alongside the existing system. The new microservice (or module) is developed, tested, and deployed, but receives no production traffic yet. The existing system continues to handle all requests. This phase produces a deployable new system that can be validated against the old one.

**Phase 2 — Coexist:**
Route a portion of traffic for this capability to the new system while the old system continues to handle the rest. Both systems run simultaneously. Traffic can be split by percentage (10% → new, 90% → old), by user segment (internal users → new, external → old), by feature flag, or by request attribute. Monitoring compares the behaviour of both systems. Issues in the new system are mitigated by routing traffic back to the old system — no data is lost, no customers are blocked.

**Phase 3 — Eliminate:**
Once confidence is established — the new system handles 100% of traffic for the extracted capability without errors, performance degradation, or data inconsistency — the corresponding code in the old system is deleted and the routing rule is updated to send all traffic to the new system. The monolith shrinks.

These three phases are applied repeatedly to each capability in priority order until the monolith handles no traffic and can be decommissioned.

**Q4. What is the Strangler Fig façade, and what technologies implement it?**
A: The façade is the routing layer that sits between clients and the coexisting systems. It intercepts every request and decides whether to forward it to the old system or the new system based on configurable routing rules. The façade is the key enabling technology — without it, clients would need to know about both systems and manage the routing themselves.

The façade must be:
- **Transparent to clients** — the client's URL, headers, and request format do not change regardless of which system handles the request.
- **Independently configurable** — routing rules must be changeable without deploying either the old or new system.
- **Observable** — every routing decision must be logged so the team knows exactly which system handled which requests.

Common façade implementations:

**Managed API gateways:** AWS API Gateway, GCP API Gateway, Azure API Management — path-based routing rules direct traffic to either the monolith or the new microservice.

**Reverse proxies:** Nginx, Caddy, or Traefik with routing rules in configuration files. Simple and effective for path-based or header-based routing.

**Service meshes:** Istio or Linkerd with VirtualService rules — support traffic splitting by percentage, header matching, and canary policies.

**Custom NestJS / Express gateway:** For fine-grained routing logic (business-rule-based routing, database-state-based routing) that static config cannot express.

**Feature flag services:** LaunchDarkly, Unleash — route traffic based on user segment, account type, or feature flag state rather than just path matching.

**Q5. How does the Strangler Fig pattern relate to other migration and modernisation patterns?**
A: The Strangler Fig is the macro strategy; several other patterns are frequently used as tactical tools within it:

- **Branch by Abstraction** — introduce an abstraction layer in the monolith (an interface) that the monolith and new service both implement. The old concrete implementation sits behind the interface; the new service is wired in behind the same interface. Swap implementations without changing callers. Used when the extraction involves shared code rather than an HTTP boundary.

- **Anti-Corruption Layer (ACL)** — when the new service's domain model differs from the monolith's, an ACL translates between them. The façade or the new service wraps the monolith's API and translates requests/responses, preventing the old system's concepts from leaking into the new domain model.

- **Parallel Run (Dark Launch)** — both systems process every request, but only one's response is returned to the client. The new system's output is compared against the old system's output in the background. Used in Phase 2 to verify correctness before committing to the new system.

- **Feature Toggle** — the routing rule in the façade is controlled by a feature flag rather than a hard-coded configuration. Enables instant rollback by flipping a flag without a deployment.

- **Canary Release** — a specific traffic-splitting strategy (1% → 10% → 50% → 100%) used during Phase 2 to ramp traffic to the new service while monitoring error rates and latency.

- **Event Interception** — for event-driven systems, the façade intercepts events published by the monolith and routes them to the new service's consumer, rather than routing HTTP traffic.

## Section 2: Implementation

**Q6. Walk through a complete Strangler Fig implementation for migrating a loan management monolith to microservices, using Nginx as the façade.**
A:

```
Monolith handles:
  POST /loans/apply          ← being strangled (new Loan Application Service)
  GET  /loans/:id            ← being strangled (new Loan Query Service)
  POST /loans/:id/repay      ← not yet started
  GET  /customers/:id        ← not yet started
  POST /payments/upi         ← not yet started
  GET  /reports/portfolio    ← not yet started

Migration state: Loan Application Service is in Phase 2 (Coexist)
                 Loan Query Service is in Phase 3 (Eliminate — being ramped to 100%)
                 All others: Phase 1 (not started — still on monolith)
```

```nginx
# /etc/nginx/conf.d/strangler-facade.conf

upstream monolith {
    server monolith.internal:3000;
    keepalive 32;
}

upstream loan_application_service {
    server loan-application-svc.internal:3001;
    keepalive 32;
}

upstream loan_query_service {
    server loan-query-svc.internal:3002;
    keepalive 32;
}

# Lua-based split for loan application (10% → new service, 90% → monolith)
# Using nginx-lua module or OpenResty
split_clients "${remote_addr}${request_id}" $loan_apply_upstream {
    10%     loan_application_service;
    *       monolith;
}

server {
    listen 443 ssl;
    server_name api.finapp.in;

    # ── Loan Application — Phase 2: 10% canary to new service ─────────────

    location = /v1/loans/apply {
        # Route based on split_clients decision
        proxy_pass         http://$loan_apply_upstream;
        proxy_set_header   X-Real-IP          $remote_addr;
        proxy_set_header   X-Forwarded-For    $proxy_add_x_forwarded_for;
        proxy_set_header   X-Routing-Target   $loan_apply_upstream;  # for observability
        proxy_connect_timeout 5s;
        proxy_read_timeout    30s;

        # If new service returns 5xx, fall back to monolith
        proxy_intercept_errors on;
        error_page 502 503 504 = @loan_apply_fallback;
    }

    location @loan_apply_fallback {
        proxy_pass http://monolith;
        add_header X-Fallback-Used "true";
    }

    # ── Loan Query — Phase 3: 100% to new service ─────────────────────────

    location ~ ^/v1/loans/([a-f0-9-]{36})$ {
        proxy_pass         http://loan_query_service;
        proxy_set_header   X-Real-IP       $remote_addr;
        proxy_set_header   X-Loan-ID       $1;         # extracted path param
        proxy_connect_timeout 3s;
        proxy_read_timeout    10s;
    }

    # ── EMI repayment — Phase 1: 100% monolith ────────────────────────────

    location ~ ^/v1/loans/([a-f0-9-]{36})/repay$ {
        proxy_pass         http://monolith;
        proxy_set_header   X-Real-IP $remote_addr;
    }

    # ── Everything else — monolith ────────────────────────────────────────

    location / {
        proxy_pass         http://monolith;
        proxy_set_header   X-Real-IP $remote_addr;
    }

    # ── Access log with routing decision ──────────────────────────────────

    log_format strangler '$remote_addr - $remote_user [$time_local] '
                         '"$request" $status $body_bytes_sent '
                         'upstream=$upstream_addr '
                         'routing_target=$sent_http_x_routing_target '
                         'fallback=$sent_http_x_fallback_used';

    access_log /var/log/nginx/strangler-access.log strangler;
}
```

**Q7. How do you implement a feature-flag-driven Strangler Fig façade in NestJS for granular, per-user routing control?**
A:

```typescript
// src/facade/strangler-facade.controller.ts

// A custom NestJS façade is appropriate when:
// - Routing depends on user attributes (role, tier, tenant) that a static proxy can't inspect
// - A/B testing requires user-sticky routing (same user always goes to same system)
// - Business rules determine routing (e.g., "route VIP customers to new service first")
// - Parallel run comparison logic is needed

@Controller()
export class StranglerFacadeController {
  private readonly logger = new Logger(StranglerFacadeController.name);

  constructor(
    private readonly proxyService:      ProxyService,
    private readonly featureFlags:      FeatureFlagService,
    private readonly routingMetrics:    RoutingMetricsService,
    private readonly parallelRunner:    ParallelRunService,
  ) {}

  // ── Loan Application — feature-flag-driven routing ────────────────────────

  @Post("v1/loans/apply")
  @UseGuards(JwtAuthGuard)
  async applyForLoan(
    @Req()  req: AuthenticatedRequest,
    @Res()  res: Response,
  ): Promise<void> {
    const target = await this.resolveTarget("loan-application-service", req.user);

    this.logger.log({
      type:         "routing_decision",
      endpoint:     "POST:/v1/loans/apply",
      userId:       req.user.customerId,
      target,
      flagSource:   "feature-flag",
    });

    this.routingMetrics.record("POST:/v1/loans/apply", target);

    await this.proxyService.forward(req, res, {
      target,
      fallbackTarget: process.env.MONOLITH_URL!,
      timeoutMs:      15_000,
    });
  }

  // ── Loan Query — parallel run (Phase 2 shadow mode) ──────────────────────

  @Get("v1/loans/:id")
  @UseGuards(JwtAuthGuard)
  async getLoan(
    @Param("id") loanId: string,
    @Req()       req:    AuthenticatedRequest,
    @Res()       res:    Response,
  ): Promise<void> {
    const shadowEnabled = await this.featureFlags.isEnabled(
      "loan-query-shadow-run", req.user.customerId
    );

    if (shadowEnabled) {
      // Parallel run: primary response from monolith, shadow from new service
      await this.parallelRunner.run(req, res, {
        primary:   process.env.MONOLITH_URL!,
        shadow:    process.env.LOAN_QUERY_SERVICE_URL!,
        compareFn: this.compareLoanResponses.bind(this),
      });
    } else {
      // Standard routing: feature flag decides which system responds
      const target = await this.resolveTarget("loan-query-service", req.user);
      await this.proxyService.forward(req, res, {
        target,
        fallbackTarget: process.env.MONOLITH_URL!,
        timeoutMs:      5_000,
      });
    }
  }

  // ── Routing resolution logic ──────────────────────────────────────────────

  private async resolveTarget(
    serviceName: string,
    user:        AuthenticatedUser,
  ): Promise<string> {
    const serviceUrls: Record<string, string> = {
      "loan-application-service": process.env.LOAN_APPLICATION_SERVICE_URL!,
      "loan-query-service":       process.env.LOAN_QUERY_SERVICE_URL!,
    };

    // Priority 1: User is in the new-service cohort via feature flag
    const isInNewServiceCohort = await this.featureFlags.isEnabled(
      `${serviceName}-new-system`, user.customerId
    );
    if (isInNewServiceCohort) return serviceUrls[serviceName];

    // Priority 2: User is internal (employees get new service for testing)
    if (user.role === "internal") return serviceUrls[serviceName];

    // Priority 3: Percentage rollout via consistent hash
    const rolloutPercent = await this.featureFlags.getNumber(
      `${serviceName}-rollout-percent`, 0
    );
    const userBucket = this.consistentHash(user.customerId) % 100;
    if (userBucket < rolloutPercent) return serviceUrls[serviceName];

    // Default: monolith
    return process.env.MONOLITH_URL!;
  }

  private compareLoanResponses(primary: unknown, shadow: unknown): boolean {
    const p = primary as LoanResponse;
    const s = shadow  as LoanResponse;
    // Compare semantically significant fields — ignore timestamps, formatting differences
    return (
      p.loanId             === s.loanId &&
      p.status             === s.status &&
      p.outstandingPaise   === s.outstandingPaise &&
      p.emisPaid           === s.emisPaid
    );
  }

  private consistentHash(input: string): number {
    let hash = 5381;
    for (let i = 0; i < input.length; i++) {
      hash = ((hash << 5) + hash) + input.charCodeAt(i);
      hash |= 0;
    }
    return Math.abs(hash);
  }
}
```

**Q8. How do you implement the Parallel Run pattern — shadow traffic comparison — to verify correctness of the new service before cutover?**
A:

```typescript
// src/facade/parallel-run.service.ts

// Parallel run: both systems process every request.
// Primary response is returned to the client.
// Shadow response is compared in the background — discrepancies logged for investigation.

@Injectable()
export class ParallelRunService {
  private readonly logger = new Logger(ParallelRunService.name);

  constructor(
    private readonly http:    HttpService,
    private readonly metrics: MetricsService,
    private readonly diffLog: DifferenceLogService,
  ) {}

  async run(
    req:     Request,
    res:     Response,
    params: {
      primary:    string;
      shadow:     string;
      compareFn:  (primary: unknown, shadow: unknown) => boolean;
      timeoutMs?: number;
    },
  ): Promise<void> {
    const timeout = params.timeoutMs ?? 5000;

    // Fire both requests simultaneously
    const [primaryResult, shadowResult] = await Promise.allSettled([
      this.makeRequest(params.primary, req, timeout),
      this.makeRequest(params.shadow,  req, timeout * 1.5),  // shadow gets more time
    ]);

    // Primary response always goes to the client
    if (primaryResult.status === "fulfilled") {
      const { status, headers, data } = primaryResult.value;
      Object.entries(headers).forEach(([k, v]) => res.setHeader(k, v as string));
      res.status(status).json(data);
    } else {
      // Primary failed — do not fall back to shadow (we don't trust it yet)
      this.logger.error(`Primary upstream failed: ${primaryResult.reason}`);
      res.status(502).json({ errorCode: "UPSTREAM_ERROR", message: "Service unavailable" });
    }

    // Shadow comparison — async, does not block the client response
    setImmediate(async () => {
      try {
        if (primaryResult.status === "rejected" || shadowResult.status === "rejected") {
          this.metrics.increment("parallel_run.shadow_error", {
            endpoint: `${req.method}:${req.path}`,
            reason:   shadowResult.status === "rejected" ? "shadow_failed" : "primary_failed",
          });
          return;
        }

        const primary = primaryResult.value.data;
        const shadow  = shadowResult.value.data;

        const matches = params.compareFn(primary, shadow);

        this.metrics.increment("parallel_run.comparison", {
          endpoint: `${req.method}:${req.path}`,
          result:   matches ? "match" : "mismatch",
        });

        if (!matches) {
          // Log the difference — do not alert on every mismatch initially
          // Review the log to understand the gap before setting up alerts
          await this.diffLog.record({
            endpoint:      `${req.method}:${req.path}`,
            requestBody:   this.sanitiseBody(req.body),
            primaryStatus: primaryResult.value.status,
            shadowStatus:  shadowResult.value.status,
            primaryBody:   this.sanitiseBody(primary),
            shadowBody:    this.sanitiseBody(shadow),
            traceId:       req.headers["x-trace-id"] as string,
            occurredAt:    new Date(),
          });

          this.logger.warn({
            type:     "parallel_run_mismatch",
            endpoint: `${req.method}:${req.path}`,
            traceId:  req.headers["x-trace-id"],
          });
        }
      } catch (err: any) {
        this.logger.error(`Parallel run comparison failed: ${err.message}`);
      }
    });
  }

  private async makeRequest(
    baseUrl:   string,
    req:       Request,
    timeoutMs: number,
  ): Promise<{ status: number; headers: Record<string, string>; data: unknown }> {
    const url = `${baseUrl}${req.path}`;
    const { data, status, headers } = await firstValueFrom(
      this.http.request({
        method:  req.method,
        url,
        data:    req.body,
        params:  req.query,
        headers: {
          ...req.headers,
          host: new URL(baseUrl).host,  // rewrite Host header for the upstream
        },
      }).pipe(timeout(timeoutMs)),
    );
    return { status, headers: headers as Record<string, string>, data };
  }

  // Remove sensitive fields before logging
  private sanitiseBody(body: unknown): unknown {
    if (!body || typeof body !== "object") return body;
    const REDACTED_FIELDS = new Set(["pan", "aadhaar", "password", "otp", "cardNumber"]);
    return Object.fromEntries(
      Object.entries(body as Record<string, unknown>).map(([k, v]) =>
        REDACTED_FIELDS.has(k.toLowerCase()) ? [k, "[REDACTED]"] : [k, v]
      )
    );
  }
}
```

**Q9. How do you handle data consistency between the monolith's database and the new service's database during the Coexist phase?**
A: Data consistency is the hardest problem in any Strangler Fig migration. Several strategies apply depending on whether the monolith database and new service database can be temporarily shared:

```typescript
// ─── Strategy 1: Shared database (temporary) ──────────────────────────────────

// During early Phase 2, the new service reads and writes to the SAME database
// as the monolith. No data synchronisation problem — both see the same data.
// The new service uses its own schema (separate tables) or a view over monolith tables.
//
// Risk: tight schema coupling between new service and monolith.
//       The monolith's schema changes break the new service.
// Exit condition: new service has its own database by the end of Phase 2.

// ─── Strategy 2: Change Data Capture (CDC) for database replication ───────────

// New service has its own database (PostgreSQL).
// Monolith's database changes are streamed to the new service via CDC (Debezium).
// New service's Kafka consumer updates its own read model.

// Debezium connector configuration (runs as a Kafka Connect connector):
const debeziumConfig = {
  "connector.class":                  "io.debezium.connector.postgresql.PostgresConnector",
  "database.hostname":                "monolith-db.internal",
  "database.port":                    "5432",
  "database.user":                    "debezium_user",
  "database.dbname":                  "monolith",
  "table.include.list":               "public.loans,public.emi_payments",
  "plugin.name":                      "pgoutput",
  "publication.name":                 "strangler_fig_pub",
  "topic.prefix":                     "monolith",
  "transforms":                       "unwrap",
  "transforms.unwrap.type":           "io.debezium.transforms.ExtractNewRecordState",
};

// Loan Query Service consumes CDC events and maintains its own read model
@Injectable()
export class LoanCdcConsumer {
  @EventPattern("monolith.public.loans")
  async handleLoanChange(@Payload() event: DebeziumLoanEvent): Promise<void> {
    if (event.op === "d") {
      // Soft delete in new service — financial records are never hard-deleted
      await this.loanReadDao.markDeleted(event.before.id);
    } else {
      // Insert or update
      const row = event.after;
      await this.loanReadDao.upsert({
        id:                    row.id,
        customerId:            row.customer_id,
        status:                row.status,
        principalInPaise:      row.principal_in_paise,
        outstandingInPaise:    row.outstanding_principal_paise,
        emisPaid:              row.emis_paid,
        nextEmiDueAt:          row.next_emi_due_at,
        updatedAt:             row.updated_at,
      });
    }
  }
}

// ─── Strategy 3: Dual writes with reconciliation ──────────────────────────────

// During Phase 2, writes go to BOTH the monolith database and the new service's database.
// A background reconciliation job detects and resolves discrepancies.

@Injectable()
export class DualWriteLoanService {
  async updateLoanStatus(loanId: string, status: LoanStatus): Promise<void> {
    // Write 1: Monolith (primary — always succeeds first)
    await this.monolithLoanDao.updateStatus(loanId, status);

    // Write 2: New service database (secondary — failure here is non-fatal during migration)
    try {
      await this.newLoanDao.updateStatus(loanId, status);
    } catch (err: any) {
      // Log and enqueue for reconciliation — do not fail the primary write
      this.logger.warn(`Dual write to new service failed for loan ${loanId}: ${err.message}`);
      await this.reconciliationQueue.add({ loanId, status, failedAt: new Date() });
    }
  }
}

// ─── Reconciliation job ───────────────────────────────────────────────────────

@Injectable()
export class DataReconciliationJob {
  @Cron("0 */4 * * *")   // every 4 hours
  async reconcile(): Promise<void> {
    // Compare checksums of critical tables
    const monolithChecksum = await this.computeChecksum("monolith", "loans");
    const newChecksum      = await this.computeChecksum("loan_service", "loans");

    if (monolithChecksum !== newChecksum) {
      const discrepancies = await this.findDiscrepancies();

      for (const diff of discrepancies) {
        // Monolith is the source of truth during migration
        await this.newLoanDao.upsert(this.mapFromMonolith(diff.monolithRow));
        this.logger.warn(`Reconciled loan ${diff.loanId}: ${diff.field} differed`);
      }

      this.metrics.gauge("strangler.reconciliation.discrepancies", discrepancies.length);
    }
  }
}
```

**Q10. How do you manage the strangler migration of asynchronous event-driven flows — not just HTTP endpoints?**
A:

```typescript
// Monolith publishes domain events on its Kafka topics.
// New services need to consume these events during migration.
// After migration, new services publish their own events and monolith stops publishing.

// ─── Phase 1: New service taps existing monolith events ──────────────────────

// The new Loan Application Service subscribes to monolith Kafka topics
// and builds its own read model from them.
// The monolith continues to publish to its existing topics.

// Monolith publishes to: "monolith.loan.created"
// New service subscribes to: "monolith.loan.created" → updates own DB

// ─── Phase 2: Event interception — fork events to both systems ───────────────

// A Kafka Streams or Kafka Mirror Maker job duplicates events:
// "monolith.loan.created" → both "monolith.loan.created" (old consumers) 
//                         and "loan.application.created" (new consumers)

// Kafka Streams event interception:
builder
  .stream<string, LoanCreatedEvent>("monolith.loan.created")
  .peek((key, value) => metrics.increment("strangler.event.intercepted"))
  .to("loan.application.created");  // also publish to new topic

// ─── Phase 3: New service becomes the publisher ───────────────────────────────

// After the Loan Application Service handles POST /loans/apply (100% traffic):
// The new service publishes to "loan.application.created"
// The monolith's publication of "monolith.loan.created" is redundant
// A bridge consumer subscribes to "loan.application.created" and 
// publishes to "monolith.loan.created" to keep old consumers working during transition

@Injectable()
export class EventBridgeConsumer {
  // Bridge: new topic → old topic (keeps old consumers alive during migration)
  @EventPattern("loan.application.created")
  async bridgeToMonolithTopic(@Payload() event: LoanApplicationCreatedEvent): Promise<void> {
    // Translate new event schema to old schema
    await this.legacyEventPublisher.publish("monolith.loan.created", {
      loan_id:       event.loanId,      // new: loanId → old: loan_id
      customer_id:   event.customerId,
      amount:        event.principalInPaise / 100,  // paise → rupees (old format)
      created_at:    event.occurredAt,
    });
  }
}

// ─── Phase 4: Old consumers migrated — bridge decommissioned ─────────────────

// Once all consumers of "monolith.loan.created" have been migrated
// to consume "loan.application.created", the bridge consumer is deleted.
// The old topic is left for a deprecation window, then deleted.
```

## Section 3: Strangler Fig in Node.js / TypeScript / Fintech Context

**Q11. How do you prioritise which parts of a monolith to strangle first?**
A:

```typescript
// Prioritisation framework — evaluate each capability on four dimensions

interface CapabilityMigrationScore {
  capability:        string;
  businessValue:     number;  // 1–5: high value = extract sooner (unblocks new features)
  extractionRisk:    number;  // 1–5: high risk = extract later (complex dependencies)
  changeFrequency:   number;  // 1–5: high frequency = extract sooner (development bottleneck)
  teamOwnership:     number;  // 1–5: clear ownership = extract sooner (known scope)
  priority:          number;  // composite score
}

function scoreCapability(cap: Omit<CapabilityMigrationScore, "priority">): CapabilityMigrationScore {
  // Formula: value × frequency × ownership / risk
  // High value, high change frequency, clear ownership = extract first
  // High extraction risk = defer
  const priority = (cap.businessValue * cap.changeFrequency * cap.teamOwnership) / cap.extractionRisk;
  return { ...cap, priority };
}
```

**Q13. How do you handle the strangler migration of database-level shared state — when the monolith and new services write to the same tables during the Coexist phase?**
A:

```typescript
// The shared database problem during Phase 2:
// Both monolith and new service write to the same loans table.
// Each has its own schema expectations.
// Monolith adds a column → breaks new service's ORM mapping.
// New service adds a column → monolith's queries fail if column has NOT NULL without default.

// ─── Solution 1: Expand-contract pattern for schema changes ───────────────────

// Expanding (backward-compatible) changes are safe:
// - ADD COLUMN with a DEFAULT or NULL-able → OK
// - ADD INDEX → OK
// - ADD TABLE → OK

// Contracting (breaking) changes require coordination:
// - DROP COLUMN, RENAME COLUMN, CHANGE TYPE → both systems must be updated together

// Step-by-step rename example:
// 1. ADD new column: ALTER TABLE loans ADD COLUMN outstanding_paise BIGINT;
// 2. Write to BOTH columns in both monolith and new service
// 3. Backfill: UPDATE loans SET outstanding_paise = outstanding_principal_paise WHERE outstanding_paise IS NULL
// 4. Read from NEW column in both systems
// 5. Remove writes to OLD column
// 6. DROP old column: ALTER TABLE loans DROP COLUMN outstanding_principal_paise;

// ─── Solution 2: Schema-per-service with a view layer ────────────────────────

// Monolith writes to the canonical schema.
// New service writes to its own schema (different tables), reads via a database view.

// CREATE SCHEMA loan_service;
// CREATE VIEW loan_service.loans AS
//   SELECT
//     id,
//     customer_id          AS "customerId",
//     status,
//     principal_in_paise   AS "principalInPaise",
//     outstanding_principal_paise AS "outstandingInPaise",
//     emis_paid            AS "emisPaid",
//     next_emi_due_at      AS "nextEmiDueAt",
//     created_at           AS "createdAt"
//   FROM public.loans
//   WHERE deleted_at IS NULL;

// New service uses the view → insulated from column naming changes.
// Monolith owns the underlying tables → schema migrations are backward-compatible.

// ─── Solution 3: Strangler fig database proxy ────────────────────────────────

// A thin database proxy (PgBouncer + query rewriting) routes queries:
// - Queries from the new service → new service's DB
// - Queries from the monolith → monolith's DB
// - Reads that cross the boundary → federated query or join view

// This is complex to implement but enables full database independence during Phase 2.

// ─── Practical fintech approach ───────────────────────────────────────────────

// For financial data, the safest approach:
// 1. New service starts with a READ-ONLY connection to the monolith's DB
// 2. New service builds its own write DB from CDC events (as in Q9)
// 3. Once the new service handles 100% of traffic, it becomes the writer
// 4. Monolith is updated to read from the new service via API (not direct DB)
// 5. Monolith's DB tables for this domain are deprecated and eventually dropped

// This sequence ensures:
// - No period where two services write to the same table
// - New service's DB evolves independently from the start
// - Data consistency is maintained through CDC → no dual writes
```

**Q18. What is the "data synchronisation debt" anti-pattern — when dual writes create silent inconsistencies?**
A:

```typescript

// are a common shortcut. They create a category of bugs that are hard to detect

async updateOutstandingBalance(loanId: string, newBalance: number): Promise<void> {

  await this.monolithPool.query(
    "UPDATE loans SET outstanding_principal_paise = $1 WHERE id = $2",

// (see Q9 — Strategy 2)

// If dual writes are unavoidable (CDC infrastructure not available yet):

async updateOutstandingBalance(loanId: string, newBalance: number): Promise<void> {
  // Write 1: monolith DB — source of truth
  await this.monolithPool.query(
    "UPDATE loans SET outstanding_principal_paise = $1, updated_at = NOW() WHERE id = $2",
    [newBalance, loanId]
  );

  // Write 2: new service DB — best effort, with explicit retry queue on failure
  try {
    await this.newServicePool.query(
      "UPDATE loans SET outstanding_paise = $1, monolith_updated_at = NOW() WHERE id = $2",
      [newBalance, loanId]
    );
  } catch (err: any) {

    await this.syncQueue.add({
      table:   "loans",
      loanId,
      field:   "outstanding_paise",
      value:   newBalance,
      failedAt: new Date(),
    });
    this.metrics.increment("strangler.dual_write.failed");
  }

}
```

**Q19. What is the "never-ending migration" anti-pattern, and what organisational factors cause it?**
A: The strangler fig migration that began 3 years ago and the monolith still handles 40% of traffic. The causes are structural:

```typescript
// ─── Common causes of never-ending migration ──────────────────────────────────

// 1. No deadline, no decommission pressure
// The monolith continues to work — there's no immediate pain from not finishing.
// Teams deprioritise migration work when new features compete for sprint capacity.

// Solution: add the monolith decommission date to the team's OKRs.
// Create artificial pressure: announce to the business that the monolith
// will be shut down on DATE X. Work backward from that date.

// 2. New features added to the monolith during migration
// While team A migrates the loan service, team B adds a new feature directly to
// the monolith ("it's faster"). The new feature must now be migrated too.

// Solution: freeze the monolith. Any new feature must go into a new service,
// even if that service is small. The monolith is in maintenance mode only.

// 3. The "last 20%" problem
// The easy capabilities (read-only, low-traffic) are migrated first.
// The hard capabilities (writes, high-traffic, complex dependencies) remain.
// The team loses momentum when they hit the hard parts.

// Solution: explicitly plan the hard migrations before starting the easy ones.
// If you can't see a path to migrating EMI collection, don't start with Loan Query.

// 4. Data migration is indefinitely deferred
// The new services work, but the databases are still shared.
// "We'll separate the databases later" becomes "later" for 18 months.

// Solution: set a firm deadline for database separation per capability.
// A migrated service that shares the monolith's database is not done.

// ─── Leading indicators of a stalled migration ────────────────────────────────

interface MigrationHealthIndicators {
  monolithTrafficPercent:        number;  // should be decreasing month-over-month
  capabilitiesInPhase2Over90Days: number; // stuck in coexist = never finishing
  newFeaturesAddedToMonolith:    number;  // should be 0
  dualWriteTablesCount:          number;  // should be decreasing
  reconciliationAlerts30Days:    number;  // silent inconsistency accumulating
}

// Alert: migration stalled
function isMigrationStalled(h: MigrationHealthIndicators): boolean {
  return (
    h.monolithTrafficPercent > 10 && h.capabilitiesInPhase2Over90Days > 2 ||
    h.newFeaturesAddedToMonolith > 0 ||
    h.reconciliationAlerts30Days > 50
  );
}
```

**Q21. "Your company has a 5-year-old Node.js monolith (Express + Sequelize + PostgreSQL) that handles loan origination, EMI collection, KYC, payments, and reporting. The engineering team of 30 is blocked because every feature requires touching the same codebase. Design a 12-month Strangler Fig migration plan."**
A:

```
Month 1-2: Infrastructure and Foundation
─────────────────────────────────────────
Goals:
  - Deploy Nginx façade in front of the monolith (zero routing change initially)
  - Set up Kafka cluster for CDC and event streaming
  - Set up Debezium CDC connector from monolith PostgreSQL
  - Establish shared monitoring dashboard for monolith and all new services
  - Define routing rule governance: only Platform team can change routing rules

Success criteria: façade in production; all traffic still goes to monolith; CDC events flowing

Month 3-5: Loan Query Service (Phase 1 → Phase 3)
────────────────────────────────────────────────────
Rationale: read-only; zero write risk; easy to verify via parallel run
Steps:
  - Month 3: Build Loan Query Service (reads from CDC-fed replica DB) — Phase 1
  - Month 4: Parallel run — both systems process every GET /loans/* request
              Shadow comparison: 7 days of 0 discrepancies required before proceeding
  - Month 5: 10% → 50% → 100% canary ramp (1 week per step with monitoring)
              Delete GET /loans/* from monolith — Phase 3

Month 6-9: Loan Application Service (Phase 1 → Phase 3)
─────────────────────────────────────────────────────────
Rationale: highest business value; most frequent changes; moderate risk
Steps:
  - Month 6: Build Loan Application Service with its own PostgreSQL DB
              Shared DB read for customer data (KYC not yet migrated)
  - Month 7: Phase 2 — 5% canary; dual write to both DBs; reconciliation daily
  - Month 8: Ramp to 50%; address all reconciliation discrepancies
  - Month 9: 100%; delete loan application code from monolith

Month 10-11: KYC Service (Phase 1 → Phase 3)
──────────────────────────────────────────────
Month 12: Payment Processing Service (Phase 1 → Phase 2)
──────────────────────────────────────────────────────────
(Full Phase 3 in Month 13-14 — beyond this plan's scope)

What's NOT in this plan (deferred):
  - EMI Collection (NACH) — highest risk; requires Payment Service to be stable first
  - Ledger Service — most complex data migration; needs dedicated quarter
  - Reporting Service — not blocking any team; low priority

Monolith decommission target: 18 months from start
(After Payments, EMI Collection, and Ledger migrate in months 13-18)
```

**Q22. "Your team is 6 months into a Strangler Fig migration. 70% of traffic has moved to new services. A critical regulatory requirement arrives: all loan data must be encrypted at rest within 60 days. The monolith's database does not support column-level encryption. How do you handle this without stopping the migration?"**
A:

```typescript
// Two problems:
// 1. Regulatory deadline: 60 days
// 2. Migration in progress: monolith and new services share some data

// ─── Option A: Encrypt new services first; monolith emergency patch ───────────

// New services (70% of traffic) use their own databases — easy to enable encryption.
// For the monolith (30% of traffic): implement emergency column-level encryption
// using application-layer encryption (encrypt in the app layer, store ciphertext).

// This is a TEMPORARY patch, not a permanent solution.
// The monolith will be decommissioned by month 18 — the patch just needs to last.

// ─── Implementation: application-layer encryption for the monolith ────────────

@Injectable()
export class MonolithEncryptionAdapter {
  private readonly key: Buffer;

  constructor() {
    this.key = Buffer.from(process.env.ENCRYPTION_KEY_HEX!, "hex");
  }

  // Called before INSERT/UPDATE in Sequelize hooks
  encrypt(value: string): string {
    const iv         = randomBytes(16);
    const cipher     = createCipheriv("aes-256-gcm", this.key, iv);
    const encrypted  = Buffer.concat([cipher.update(value, "utf8"), cipher.final()]);
    const authTag    = cipher.getAuthTag();
    return `${iv.toString("hex")}:${authTag.toString("hex")}:${encrypted.toString("hex")}`;
  }

  decrypt(ciphertext: string): string {
    const [ivHex, authTagHex, encryptedHex] = ciphertext.split(":");
    const iv        = Buffer.from(ivHex, "hex");
    const authTag   = Buffer.from(authTagHex, "hex");
    const encrypted = Buffer.from(encryptedHex, "hex");
    const decipher  = createDecipheriv("aes-256-gcm", this.key, iv);
    decipher.setAuthTag(authTag);
    return decipher.update(encrypted).toString("utf8") + decipher.final("utf8");
  }
}

// Sequelize model hooks — transparent encryption
LoanModel.addHook("beforeCreate", (instance) => {
  instance.panNumber     = encryptionAdapter.encrypt(instance.panNumber);
  instance.aadhaarNumber = encryptionAdapter.encrypt(instance.aadhaarNumber);
});

LoanModel.addHook("afterFind", (instances) => {
  for (const instance of Array.isArray(instances) ? instances : [instances]) {
    instance.panNumber     = encryptionAdapter.decrypt(instance.panNumber);
    instance.aadhaarNumber = encryptionAdapter.decrypt(instance.aadhaarNumber);
  }
});

// ─── New services: use PostgreSQL column-level encryption or AWS RDS encryption ─

// New services' databases: enable encryption at rest via AWS RDS Encryption
// (KMS-managed keys) — one checkbox in infrastructure config; zero code change.
// AWS RDS Encryption covers all data including backups and snapshots.

// ─── Migration impact: unchanged ──────────────────────────────────────────────

// The encryption implementation is in the data layer — invisible to the façade
// and to the migration routing rules. Migration continues as planned.
// The monolith patch is removed automatically when the monolith is decommissioned.
```

**Q23. "You're presenting the Strangler Fig migration plan to the CTO who asks: 'Why not just rewrite the monolith from scratch in 12 months? It would be cleaner.' How do you respond?"**
A: A structured, evidence-based argument:

> "I appreciate the appeal of a clean slate — and I want to give you an honest assessment of both paths.
>
> The rewrite argument has real merits: we'd eliminate all the accumulated technical debt, design the new system with everything we now know, and avoid the complexity of running two systems in parallel. I'm not dismissing it.
>
> But here's what the evidence shows. The largest fintech rewrite I'm aware of at scale — and this pattern repeats — took 24 months instead of 12, shipped 60% of the original system's functionality, and required 18 months of parallel operation anyway because the rewrite was incomplete. That's not a hypothetical; it's the modal outcome for big-bang rewrites above a certain complexity threshold.
>
> The specific risks for our system: our monolith has processed 3 years of production loans. It has undocumented behaviour in edge cases — what happens when a customer partially repays and then the NACH mandate fails, and the refund crosses the EMI due date? That logic is in the monolith. A rewrite team discovers it when the first production customer hits it, not before. With the Strangler Fig, we discover it because the old system is still running and we're comparing outputs.
>
> The second risk is the moving target. We have a regulatory requirement arriving in 60 days. With a rewrite, we either delay the rewrite until after the deadline (now 14 months) or we implement the requirement twice — once in the monolith for now, once in the rewrite. With the Strangler Fig, the new services implement it correctly from day one; the monolith gets a temporary patch.
>
> What I'm proposing is that in 12 months, we have 80% of traffic on new services, all new features shipping 3× faster, and a clear path to decommissioning. In 18 months, the monolith is gone. That's the same timeline as the optimistic rewrite estimate, with dramatically lower risk at every point. At month 6, if the new loan service has a critical bug, we flip a feature flag and 100% of traffic is back on the monolith in 10 seconds. If the rewrite has a critical bug at month 6, we have nothing to fall back to."

**Q24. "A junior engineer on your team asks: 'The Strangler Fig seems like it takes twice as long because we have to build and maintain two systems. Why not just fix the monolith?'"**
A: A direct and honest answer:

> "It's a fair question — and the short answer is: it depends on how broken the monolith is.
>
> If the monolith is mostly fine but has one or two messy modules, you probably don't need a Strangler Fig. Refactor those modules in place. The Strangler Fig is for when the monolith's architecture is the blocker — when 30 engineers are all touching the same codebase, every deployment requires coordinating across all teams, automated testing is impossible because everything is tangled together, and the monolith cannot be scaled independently per service.
>
> You're right that during Phase 2, we do run two systems. But consider the alternative: we spend 6 months trying to 'fix' the monolith while 30 engineers are fighting each other in the same codebase. The fixes are local — we clean up the loan module, but the payment module immediately degrades it again because they share 4 database tables. You can't fix a monolith by cleaning it up if the fundamental problem is that everything is tangled.
>
> The 'twice as long' concern is also empirically backwards. The teams that have extracted even 2–3 services from our monolith are already shipping features 3× faster in those areas — because they don't have to coordinate with anyone else. The strangler fig doesn't slow down development; it's the path out of the slowdown we're already in.
>
> Where you're right: the Strangler Fig adds operational complexity — two systems to monitor, two databases to maintain, a façade to operate. That's a real cost. We mitigate it by keeping the façade thin, making each extraction quick (4–6 weeks per capability), and being disciplined about decommissioning — the old code is deleted, not left running forever. A Strangler Fig that never eliminates the old code is just a bloated system. The 'eliminate' phase is non-negotiable."

**Q25. "Walk me through how you would use the Strangler Fig pattern to migrate a synchronous monolith to an event-driven microservices architecture — not just splitting services, but changing the fundamental communication style."**
A:

```typescript
// Current: monolith with synchronous function calls between modules
// Target:  event-driven microservices communicating via Kafka

// The challenge: you can't change synchronous → async all at once.
// The Strangler Fig solves this incrementally.

// ─── Phase 1: Extract service with synchronous API (not yet event-driven) ──────

// The Loan Application Service starts as a synchronous REST service.
// The façade routes HTTP POST /loans/apply to it.
// Internally, it calls the monolith synchronously for data it still needs
// (customer data, KYC status — not yet extracted).

// ─── Phase 2: Introduce events alongside synchronous calls ───────────────────

// The Loan Application Service starts publishing events when it makes changes.
// These events are consumed by new services as they are extracted.
// The monolith still exists and receives synchronous calls for unchanged capabilities.

// Loan Application Service publishes:
await this.publisher.publish<LoanApplicationSubmitted>({
  eventType:    "loan.application.submitted",
  loanId:       result.loanId,
  customerId:   command.customerId,
  amountInPaise: command.amountInPaise,
  occurredAt:   new Date().toISOString(),
});

// ─── Phase 3: Replace synchronous calls with event consumption ────────────────

// As each capability is extracted to a new service,
// the new service subscribes to events instead of being called synchronously.
// The Loan Application Service no longer calls Customer Service synchronously —
// it listens to "customer.kyc.verified" events and caches the KYC state.

@EventPattern("customer.kyc.verified")
async handleKycVerified(@Payload() event: KycVerifiedEvent): Promise<void> {
  // Cache the KYC status so Loan Application Service doesn't need to call KYC Service
  await this.kycStatusCache.set(event.customerId, {
    status:    "VERIFIED",
    verifiedAt: event.occurredAt,
  });
}

// Now when processing a loan application:
async applyForLoan(command: ApplyForLoanCommand): Promise<void> {
  // No synchronous call to KYC Service — reads from local cache
  const kycStatus = await this.kycStatusCache.get(command.customerId);
  if (!kycStatus || kycStatus.status !== "VERIFIED") {
    throw new PreconditionFailedException("KYC not verified");
  }
  // ... rest of loan application logic
}

// ─── Phase 4: Monolith adapts to events ──────────────────────────────────────

// For capabilities still in the monolith, introduce an Event Bridge:
// New service publishes events → Event Bridge consumer calls monolith's internal functions.
// This is a temporary adapter — removed when the monolith capability is extracted.

@Injectable()
export class LoanApplicationEventBridge {
  @EventPattern("loan.application.submitted")
  async handleLoanSubmitted(@Payload() event: LoanApplicationSubmitted): Promise<void> {
    // Bridge: Kafka event → monolith internal call
    // This is TEMPORARY — exists only until the receiving capability is extracted
    await this.monolithLedgerService.reserveFundsForLoan({
      loanId:        event.loanId,
      amountInPaise: event.amountInPaise,
    });
  }
}

// ─── Final state: fully event-driven, no monolith ────────────────────────────

// All services communicate via events.
// No synchronous HTTP calls between services (only client → API gateway).
// Monolith is decommissioned.
// Event Bridge adapters are all deleted.

// Migration path summary:
// 1. Extract services as synchronous REST services (familiar pattern)
// 2. Add event publication to each new service as it's extracted
// 3. Replace synchronous inter-service calls with event consumption as dependencies extract
// 4. Event Bridge adapters bridge to monolith capabilities still being extracted
// 5. Delete bridges as monolith capabilities extract
// 6. Delete monolith
// 7. Full event-driven architecture achieved — one service at a time
```

## Quick Reference Table

| Dimension                           | Strangler Fig Pattern                                                              |
|-------------------------------------|------------------------------------------------------------------------------------|
| Category                            | Microservices Design Patterns / Migration Strategies                               |
| Origin                              | Martin Fowler, 2004 — analogy from the strangler fig tree                          |
| Intent                              | Incrementally replace a legacy system with a new system without a big-bang cutover |
| Three phases                        | Transform (build), Coexist (route partial traffic), Eliminate (delete old code)    |
| Key enabling component              | Façade (API gateway, reverse proxy, or custom service) that controls routing       |
| Façade implementations              | Nginx, AWS API Gateway, Istio VirtualService, custom NestJS gateway                |
| Traffic routing strategies          | Path-based, percentage split, feature flag, user segment, consistent hash          |
| Parallel run definition             | Both systems process every request; primary responds to client; shadow is compared |
| Data consistency strategies         | Shared DB (temp), CDC via Debezium, dual writes + reconciliation                   |
| Rollback mechanism                  | Feature flag flip → 100% traffic back to monolith in seconds; no deployment needed |
| Priority order                      | Read-only endpoints first (low risk), write endpoints later, highest risk last     |
| Decommission criteria               | 0 monolith traffic for 7+ days, data reconciled, all events migrated, code deleted |
| Façade lifecycle                    | Temporary component — removed after migration; routing rules have planned end dates |
| Event-driven migration              | Event Bridge adapters bridge new events to monolith; removed as capabilities extract |
| Database migration order            | Shared DB → CDC read model → new service owns writes → monolith DB deprecated      |
| Common pitfalls                     | Big-bang within Strangler Fig, fat façade, silent dual-write inconsistency, stalled migration |
| "Never-ending migration" causes     | No decommission deadline, new features added to monolith, data migration deferred  |
| vs. Big-bang rewrite                | Strangler Fig: reversible at every step, risk bounded per increment; rewrite: all-or-nothing |
| vs. Branch by abstraction           | Branch by abstraction: internal code seam; Strangler Fig: external HTTP routing seam |
| vs. Canary release                  | Canary: same code, different user % (risk mitigation); Strangler Fig: different code (migration) |
| Related patterns used within it     | Branch by Abstraction, Anti-Corruption Layer, Parallel Run, Feature Toggle, CDC    |
| Testing approach                    | Mock both systems; test routing decisions per flag state; test fallback on 5xx; test header injection |
| Organisational requirements         | Monolith freeze for new features; team ownership per extracted service; decommission OKR |
| Fintech canonical examples          | Loan origination, KYC, payment processing, EMI collection, ledger, reporting      |
| Regulatory constraint handling      | New services get correct implementation; monolith gets temporary patch; patch removed on decommission |

**Tip for the Interview:** At the 5 YOE level, Strangler Fig questions surface as architecture and organisational problems — "your monolith is a bottleneck for 30 engineers — how do you migrate to microservices," "how do you handle a critical regulatory requirement that arrives mid-migration," or "how do you prevent the migration from taking 3 years?" The answers that land demonstrate five things: (1) you understand that the façade is the enabling mechanism and know its implementation options cold — Nginx, Istio VirtualService, feature-flag-driven NestJS gateway; (2) you've thought through the data consistency problem specifically — shared DB as a temporary measure, CDC via Debezium as the scalable path, and reconciliation as a mandatory safety net for dual writes; (3) you know the three phases precisely and can articulate when each ends — Phase 2 ends when you have 7 days of 0 discrepancies in parallel run, not just "when it feels ready"; (4) you can articulate the rollback mechanism convincingly — "feature flag flip, seconds to 100% monolith, no deployment" is the answer that separates someone who's thought about this from someone reciting a pattern; and (5) you can defend the pattern against the "just rewrite it" objection with specific evidence and risk framing, not just "big-bang rewrites are bad." In fintech specifically, the regulatory compliance mid-migration scenario and the data consistency in dual-write scenarios are where concrete domain knowledge demonstrates real-world experience with the pattern rather than textbook familiarity.
