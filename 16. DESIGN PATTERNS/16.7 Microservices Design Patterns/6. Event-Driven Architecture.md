# Microservices & Data Patterns: Event-Driven Architecture — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Event-Driven Architecture?**
A: Event-Driven Architecture (EDA) is an architectural style in which components communicate by **producing and consuming events** — immutable records of something significant that happened in the system. Rather than components calling each other directly (synchronous, point-to-point coupling), producers publish events to a shared channel (event bus, message broker, or message queue) and consumers subscribe to the events they care about. The producer has no knowledge of who consumes its events, and consumers have no knowledge of what produced the event.

The three core participants:
- **Producer (Publisher)** — detects a significant occurrence and emits an event. "I observed that a loan application was submitted." Knows nothing about downstream consumers.
- **Event / Message** — an immutable, timestamped record of what happened. Contains the data consumers need to react. Named in past tense.
- **Consumer (Subscriber / Handler)** — receives events and reacts to them. Each consumer independently decides what action to take. One event can trigger many consumers.

**Q2. What problem does EDA solve? What does it replace?**
A: EDA solves the **synchronous coupling problem** in complex, multi-service systems. The alternative — synchronous point-to-point calls — creates:

- **Tight coupling** — LoanOriginationService must know the URLs, APIs, and availability of NotificationService, NachService, CRMService, and every other downstream system it must trigger.
- **Synchronous dependency chain** — if one downstream service is slow or unavailable, the primary operation (loan application) is blocked or fails.
- **Cascading failures** — if the notification service throws, the loan application fails even though the loan record was saved successfully.
- **Change friction** — adding a new downstream action (send WhatsApp, update CRM, trigger credit insurance) requires modifying LoanOriginationService.

```
❌ Synchronous coupling:
LoanService.apply()
  ├─ await notificationService.sendConfirmation()   ← blocks if notification is slow
  ├─ await nachService.initiateMandateSetup()        ← blocks if NACH is unavailable
  ├─ await crmService.createLead()                   ← blocks if CRM is down
  └─ await fraudService.submitForAnalysis()           ← blocks if fraud service is slow
Total latency: sum of all downstream calls

✅ Event-driven:
LoanService.apply()
  └─ eventBus.publish(new LoanApplicationSubmittedEvent(...))  ← returns immediately
  LoanService is done. Downstream services react asynchronously.
```

**Q3. What is the difference between an Event, a Command, and a Message?**
A: These three terms are related but carry different intent:

| Aspect              | Event                                              | Command                                             | Message (generic)                                |
|---------------------|----------------------------------------------------|-----------------------------------------------------|--------------------------------------------------|
| Meaning             | Something that happened ("Loan was sanctioned")    | Request to do something ("Disburse this loan")      | Generic data unit — could be either              |
| Tense               | Past tense — already occurred                      | Imperative — instruction for future action          | Neutral                                          |
| Sender intent       | Announcing a fact; doesn't care who reacts         | Directing a specific recipient to act               | Varies                                           |
| Consumers           | Many (any interested subscriber)                   | One (the designated handler)                        | Varies                                           |
| Naming example      | `LoanSanctionedEvent`, `EmiDefaultedEvent`         | `DisburseLoanCommand`, `CollectEmiCommand`          | —                                                |
| Can be ignored?     | Yes — if no consumer is interested                 | No — must be handled exactly once                   | Depends                                          |

In a message queue context: **events** go to a topic (pub/sub — all subscribers receive); **commands** go to a queue (point-to-point — exactly one consumer processes each).

**Q4. What is the difference between a message queue and a pub/sub (publish-subscribe) system?**
A:

| Aspect            | Message Queue (Point-to-point)                        | Pub/Sub (Topic-based)                                      |
|-------------------|-------------------------------------------------------|------------------------------------------------------------|
| Delivery          | One message → one consumer (competing consumers)      | One message → all subscribers (fan-out)                    |
| Use case          | Task distribution, work queues, commands              | Event notification, CQRS projections, multi-consumer events |
| AWS equivalent    | SQS                                                   | SNS (topics), EventBridge                                  |
| If consumer down  | Message stays in queue until consumer recovers        | Message may be lost unless backed by a queue (SNS→SQS)    |
| Scaling           | Add more consumers to increase throughput             | Each subscriber independently scales                       |
| Examples          | Process one NACH debit at a time; send one SMS        | Loan sanctioned → NACH setup + CRM update + notification  |

In practice, most production systems use **SNS → SQS fan-out**: SNS distributes one event to multiple SQS queues (one per subscriber), each queue provides durable buffering and delivery to its consumer. This gives you pub/sub fan-out with queue durability and at-least-once delivery guarantees.

**Q5. What is at-least-once delivery, and what does it require from consumers?**
A: At-least-once delivery is the guarantee most message brokers provide: **a message will be delivered to its consumer at least once, but possibly more than once**. Exactly-once delivery is extremely hard to achieve in distributed systems and is not guaranteed by SQS, Kafka, RabbitMQ, or EventBridge in standard configurations.

The implication: **every event consumer must be idempotent** — processing the same event twice must produce the same result as processing it once. If the consumer processes an event successfully but crashes before acknowledging receipt, the broker will redeliver the event. Without idempotency, this double-delivery causes duplicate processing.

```typescript
// ❌ Non-idempotent handler — processes duplicate events cause double credits
@EventHandler(EmiCollectedEvent)
async handle(event: EmiCollectedEvent): Promise<void> {
  // If this succeeds but the acknowledgement fails, re-delivery credits EMI twice
  await this.prisma.emiPayments.create({
    data: { loanId: event.loanId, amount: event.amount, collectedOn: event.collectedOn },
  });
}

// ✅ Idempotent handler — safe to process the same event multiple times
@EventHandler(EmiCollectedEvent)
async handle(event: EmiCollectedEvent): Promise<void> {
  await this.prisma.emiPayments.upsert({
    where: {
      // Natural unique key — same event always has the same reference
      unique_collection_ref: { loanId: event.loanId, collectionReference: event.reference },
    },
    create: {
      loanId: event.loanId,
      amount: event.amount,
      collectedOn: event.collectedOn,
      collectionReference: event.reference,
    },
    update: {}, // nothing to update — upsert is the idempotency mechanism
  });
}
```

## Section 2: Event Infrastructure

**Q6. What are the main message broker options, and when do you choose each in a Node.js/AWS fintech context?**
A:

| Broker           | Strengths                                                                | Best for in fintech                                        |
|------------------|--------------------------------------------------------------------------|------------------------------------------------------------|
| **AWS SQS**      | Fully managed, at-least-once delivery, DLQ, simple operations           | Task queues, NACH batch processing, EMI collection jobs    |
| **AWS SNS**      | Fan-out pub/sub, HTTP/SQS/Lambda endpoints, simple                      | Broadcasting loan lifecycle events to multiple consumers   |
| **SNS→SQS**      | Fan-out + durability + per-consumer backpressure                        | Most EDA patterns in AWS — the default go-to pattern       |
| **AWS EventBridge** | Schema registry, event rules/routing, cross-account                  | Service-to-service events in AWS; RBI event routing        |
| **Apache Kafka** | Very high throughput, ordered partitions, long retention, replay        | High-volume NACH debits, real-time fraud scoring streams   |
| **RabbitMQ**     | Flexible routing, exchange types, self-hosted control                   | Complex routing logic; lower volume; on-prem / self-hosted |
| **Redis Pub/Sub**| In-memory, ultra-low latency, no persistence                            | Real-time notifications, in-process fan-out — NOT durable  |

For a NestJS fintech platform on AWS: **SNS→SQS** for most service-to-service events, **SQS alone** for job queues (EMI collection, NACH batch), **EventBridge** for cross-account regulatory event routing. Kafka if you need replay, ordered event streams, or very high throughput (10k+ events/second).

**Q7. What is the Outbox Pattern, and why is it essential for reliable event publishing?**
A: The Outbox Pattern solves a critical distributed systems problem: **how do you atomically save a domain state change and publish its event** when the database and the message broker are two separate systems?

The failure scenario without Outbox:
```typescript
// ❌ Two separate operations — not atomic
async function sanctionLoan(loanId: string): Promise<void> {
  await this.prisma.loan.update({ where: { id: loanId }, data: { status: 'SANCTIONED' } });
  // Crash HERE → loan is sanctioned in DB but event never published
  // Collections and NACH services never find out — loan is stuck
  await this.eventBus.publish(new LoanSanctionedEvent(loanId));
}
```

The Outbox Pattern stores the event in the same database transaction as the state change — ensuring they succeed or fail together:

```typescript
// ✅ Outbox Pattern — event stored atomically with the state change
async function sanctionLoan(loanId: string): Promise<void> {
  await this.prisma.$transaction(async (tx) => {
    // State change
    await tx.loan.update({ where: { id: loanId }, data: { status: 'SANCTIONED' } });

    // Event written to outbox table — same transaction
    await tx.outboxEvent.create({
      data: {
        id: uuid(),
        aggregateId: loanId,
        eventType: 'LoanSanctionedEvent',
        payload: JSON.stringify({ loanId, sanctionedAt: new Date() }),
        status: 'PENDING',
        createdAt: new Date(),
      },
    });
    // Either both succeed or neither does — guaranteed atomicity
  });
}

// Outbox relay — a separate process polls pending events and publishes them
@Cron('*/5 * * * * *')   // every 5 seconds
async relayOutboxEvents(): Promise<void> {
  const pending = await this.prisma.outboxEvent.findMany({
    where: { status: 'PENDING' },
    orderBy: { createdAt: 'asc' },
    take: 100,
  });

  for (const outboxEvent of pending) {
    try {
      await this.eventBus.publish(outboxEvent.eventType, JSON.parse(outboxEvent.payload));
      await this.prisma.outboxEvent.update({
        where: { id: outboxEvent.id },
        data: { status: 'PUBLISHED', publishedAt: new Date() },
      });
    } catch (err) {
      // Log; the event stays PENDING and will be retried on the next poll
      this.logger.error(`Failed to relay outbox event ${outboxEvent.id}`, err);
    }
  }
}
```

With the Outbox Pattern:
- If the application crashes after the transaction commits, the outbox relay will pick up and publish the event on the next poll.
- If the event broker is temporarily unavailable, events queue up in the outbox table and are published when it recovers.
- If publishing fails partway, only unpublished events remain PENDING — already-published ones are marked and won't be re-sent.

**Q8. What is a Dead Letter Queue (DLQ), and how do you use it?**
A: A Dead Letter Queue (DLQ) is a secondary queue to which messages are automatically moved when they **cannot be successfully processed after a configured number of retry attempts**. Rather than losing failed messages or retrying them forever, they're parked in the DLQ for investigation, alerting, and manual or automated remediation.

```typescript
// AWS SQS with DLQ — configured via CloudFormation/CDK
const emiCollectionQueue = new sqs.Queue(this, 'EmiCollectionQueue', {
  visibilityTimeout: Duration.seconds(30),
  retentionPeriod: Duration.days(14),
  deadLetterQueue: {
    queue: new sqs.Queue(this, 'EmiCollectionDlq', {
      retentionPeriod: Duration.days(14),
    }),
    maxReceiveCount: 3,  // after 3 failed processing attempts → DLQ
  },
});

// DLQ monitoring — alert on any messages landing in DLQ
const dlqAlarm = new cloudwatch.Alarm(this, 'EmiCollectionDlqAlarm', {
  metric: emiCollectionDlq.metricApproximateNumberOfMessagesVisible(),
  threshold: 1,
  evaluationPeriods: 1,
  comparisonOperator: cloudwatch.ComparisonOperator.GREATER_THAN_OR_EQUAL_TO_THRESHOLD,
  alarmDescription: 'EMI collection messages in DLQ — investigate immediately',
  actionsEnabled: true,
  alarmActions: [pagerdutyArn],
});

// DLQ consumer — analyse and replay
@Injectable()
export class DlqInspectionService {
  async reprocessMessage(dlqMessageId: string): Promise<void> {
    const message = await this.dlqClient.receiveMessage(dlqMessageId);
    const payload = JSON.parse(message.body);

    this.logger.info({ message: 'Reprocessing DLQ message', payload, dlqMessageId });

    // Fix the underlying issue first, then replay
    await this.originalQueue.sendMessage(JSON.stringify(payload));
    await this.dlqClient.deleteMessage(dlqMessageId);
  }
}
```

DLQs are critical in fintech because a failed NACH debit event, an unprocessed EMI collection confirmation, or a missed sanction event can have real financial consequences. The DLQ ensures no event is silently dropped.

**Q10. How do you implement event publishing in NestJS using AWS SQS/SNS?**
A:

```typescript
// Event bus abstraction — the service layer publishes to this interface
interface IEventBus {
  publish(event: DomainEvent): Promise<void>;
  publishAll(events: DomainEvent[]): Promise<void>;
}

// AWS SNS implementation — publishes to a topic; SNS delivers to all subscribed SQS queues
@Injectable()
export class SnsEventBus implements IEventBus {
  private readonly snsClient: SNSClient;
  private readonly topicArnMap: Record<string, string>;

  constructor(private readonly configService: ConfigService) {
    this.snsClient = new SNSClient({ region: process.env.AWS_REGION });
    this.topicArnMap = {
      LoanApplicationSubmittedEvent: configService.get('LOAN_ORIGINATION_TOPIC_ARN'),
      LoanSanctionedEvent: configService.get('LOAN_ORIGINATION_TOPIC_ARN'),
      EmiCollectedEvent: configService.get('EMI_COLLECTION_TOPIC_ARN'),
      EmiDefaultedEvent: configService.get('EMI_COLLECTION_TOPIC_ARN'),
    };
  }

  async publish(event: DomainEvent): Promise<void> {
    const topicArn = this.topicArnMap[event.constructor.name];
    if (!topicArn) throw new Error(`No SNS topic configured for event: ${event.constructor.name}`);

    await this.snsClient.send(new PublishCommand({
      TopicArn: topicArn,
      Message: JSON.stringify(event),
      MessageAttributes: {
        eventType: {
          DataType: 'String',
          StringValue: event.constructor.name, // for SNS filter policies
        },
        correlationId: {
          DataType: 'String',
          StringValue: event.correlationId ?? uuid(),
        },
      },
    }));
  }

  async publishAll(events: DomainEvent[]): Promise<void> {
    await Promise.all(events.map(e => this.publish(e)));
  }
}

// Consumer — SQS polling handler
@Injectable()
export class SqsEmiDefaultedConsumer {
  constructor(
    @InjectSqsConsumer('emi-defaulted-queue') private readonly sqsConsumer: SqsConsumer,
    private readonly collectionsCaseService: CollectionsCaseService,
    private readonly notificationService: NotificationService,
  ) {
    this.sqsConsumer.on('message', this.handleMessage.bind(this));
  }

  private async handleMessage(message: SQSRecord): Promise<void> {
    // SNS wraps the message — unwrap
    const snsWrapper = JSON.parse(message.body);
    const event: EmiDefaultedEvent = JSON.parse(snsWrapper.Message);

    try {
      await this.collectionsCaseService.openCase(event);
      await this.notificationService.sendEmiFailureAlert(event);
      // Successful processing — SQS auto-deletes the message
    } catch (err) {
      this.logger.error('Failed to process EmiDefaultedEvent', { event, err });
      throw err; // Re-throw → SQS increments receive count → eventually → DLQ
    }
  }
}
```

**Q11. How do you implement an event consumer that is robust against failures in NestJS?**
A:

```typescript
@Injectable()
export class LoanSanctionedConsumer implements OnModuleInit {
  constructor(
    private readonly nachService: NachSetupService,
    private readonly notificationService: NotificationService,
    private readonly logger: Logger,
    private readonly metrics: MetricsService,
  ) {}

  async processEvent(event: LoanSanctionedEvent): Promise<void> {
    const start = Date.now();
    this.logger.info({ message: 'Processing LoanSanctionedEvent', loanId: event.applicationId });

    // 1. Idempotency check — avoid double-processing
    const alreadyProcessed = await this.idempotencyStore.has(
      `loan-sanctioned:${event.applicationId}`,
    );
    if (alreadyProcessed) {
      this.logger.info({ message: 'Idempotent skip', loanId: event.applicationId });
      return; // safe to delete message
    }

    // 2. Process each concern independently — failure of one doesn't block others
    const results = await Promise.allSettled([
      this.nachService.initiateMandate(event.applicationId, event.applicantId),
      this.notificationService.sendSanctionLetter(event.applicantId, event.applicationId),
      this.documentService.generateSanctionLetterPdf(event),
    ]);

    // 3. Handle partial failures
    const failures = results.filter(r => r.status === 'rejected');
    if (failures.length > 0) {
      failures.forEach(f =>
        this.logger.error({
          message: 'Partial processing failure on LoanSanctionedEvent',
          loanId: event.applicationId,
          error: (f as PromiseRejectedResult).reason,
        }),
      );
      // Throw if any CRITICAL step failed (NACH is critical; notification is not)
      const nachFailed = results[0].status === 'rejected';
      if (nachFailed) throw new Error('Critical: NACH setup failed'); // → SQS retry
    }

    // 4. Mark as processed (idempotency)
    await this.idempotencyStore.set(
      `loan-sanctioned:${event.applicationId}`,
      { processedAt: new Date() },
      { ttlSeconds: 86400 },
    );

    this.metrics.record('event.loan_sanctioned.processing_time', Date.now() - start);
    this.logger.info({ message: 'LoanSanctionedEvent processed', loanId: event.applicationId });
  }
}
```

**Q12. How does EDA enable the NACH EMI collection flow in a lending platform?**
A: EMI collection is an excellent EDA use case — it involves many coordinated steps across services, with significant retry and failure-handling complexity:

```
Trigger: Scheduled job (daily at 6am) → produces CollectEmiCommand messages to SQS

For each active loan with EMI due today:
  CollectEmiConsumer processes:
    1. Looks up mandate from NACH service
    2. Initiates NACH debit via NPCI
    3. Publishes EmiDebitInitiatedEvent

NPCI processes debit and sends callback (async, 2-4 hours later):
  NachCallbackController receives NPCI webhook
  → Parses and validates signature
  → Routes to SQS based on outcome:
      Success → EmiSuccessQueue
      Failure → EmiFailureQueue

EmiSuccessConsumer:
  → Publishes EmiCollectedEvent
    → ActiveLoansConsumer: updates outstanding principal, marks EMI paid
    → NotificationConsumer: sends "EMI collected" SMS
    → AccountingConsumer: records ledger entry
    → RiskProjectorConsumer: resets DPD to 0

EmiFailureConsumer:
  → Classifies failure code
  → Publishes EmiDefaultedEvent
    → CollectionsConsumer: opens/updates collection case
    → NotificationConsumer: sends failure notification
    → NachRetryConsumer: schedules retry based on failure code:
        INSUFFICIENT_FUNDS → schedule retry at salary credit date
        TECHNICAL_ERROR → schedule retry in 2 hours
        MANDATE_INACTIVE → trigger re-registration flow
    → RiskProjectorConsumer: increments DPD
```

**Q13. How do you handle event ordering in an EDA system?**
A: Event ordering matters when the processing of one event assumes a prior event has already been processed. Three strategies:

**Strategy 1 — Accept eventual ordering (most common):**
Design consumers to be order-independent by using idempotent operations. If `EmiCollectedEvent` and `EmiDefaultedEvent` for the same loan-month both arrive, the idempotency key prevents double-processing:
```typescript
// Use a version/sequence to detect out-of-order delivery
async processEmiEvent(event: EmiEvent): Promise<void> {
  const current = await this.activeLoansRepo.findById(event.loanId);
  if (event.sequence <= current.lastProcessedSequence) {
    return; // older event — skip
  }
  // Process...
  await this.activeLoansRepo.updateSequence(event.loanId, event.sequence);
}
```

**Strategy 2 — Partition by entity ID (Kafka):**
Kafka partitions guarantee that all events for a given partition key (e.g., `loanId`) are delivered to the same consumer in order:
```typescript
// Kafka producer — partition by loanId
await this.kafkaProducer.send({
  topic: 'loan-events',
  messages: [{ key: event.loanId, value: JSON.stringify(event) }],
  // All events with the same key go to the same partition — in order
});
```

**Strategy 3 — FIFO queues (SQS FIFO):**
SQS FIFO queues guarantee order within a message group:
```typescript
await this.sqs.send(new SendMessageCommand({
  QueueUrl: process.env.LOAN_EVENTS_FIFO_QUEUE_URL,
  MessageBody: JSON.stringify(event),
  MessageGroupId: event.loanId,         // order preserved within this group
  MessageDeduplicationId: event.eventId, // deduplication within 5 minutes
}));
```

**Q14. How do you implement event schema versioning and backward compatibility?**
A: Event schemas evolve over time — consumers must handle multiple versions gracefully:

```typescript
// Version the event envelope
interface EventEnvelope {
  eventId: string;
  eventType: string;
  eventVersion: number;   // 1, 2, 3...
  correlationId: string;
  occurredAt: string;     // ISO 8601
  payload: unknown;       // version-specific payload
}

// Consumer handles multiple versions
@EventHandler('LoanSanctionedEvent')
async handleLoanSanctioned(envelope: EventEnvelope): Promise<void> {
  let event: LoanSanctionedEventV2;

  if (envelope.eventVersion === 1) {
    // Upcast from v1 to v2 — fill in new fields with defaults
    const v1 = envelope.payload as LoanSanctionedEventV1;
    event = {
      ...v1,
      sanctionedAmountInPaise: v1.sanctionedAmountInRupees * 100, // new field in v2
      conditions: v1.conditions ?? [], // previously optional, now required
    };
  } else if (envelope.eventVersion === 2) {
    event = envelope.payload as LoanSanctionedEventV2;
  } else {
    this.logger.error(`Unknown event version: ${envelope.eventVersion}`);
    // Don't throw — unknown version shouldn't crash the consumer
    return;
  }

  await this.processV2(event);
}
```

**Rules for backward-compatible event schema evolution:**
- **Adding fields**: always safe — existing consumers ignore unknown fields if using lenient JSON parsing.
- **Removing fields**: breaking — existing consumers that depend on the removed field will fail. Deprecate first, remove only after all consumers are updated.
- **Renaming fields**: breaking — treat as remove + add. Use aliases during migration.
- **Changing field types**: breaking. Avoid; use a new field alongside the old one during transition.

## Section 4: Event Choreography vs Orchestration

**Q15. What is the difference between event choreography and event orchestration?**
A:

**Choreography** — services react to each other's events without a central coordinator. Each service knows what events to listen for and what to do; no single service has the full picture:

```
LoanSanctionedEvent published by LoanOriginationService
  ↓
NachService reacts → publishes NachMandateInitiatedEvent
  ↓
NotificationService reacts to NachMandateInitiatedEvent → sends SMS
  ↓
DocumentService reacts to LoanSanctionedEvent → generates PDF
```

No service calls another; each responds to events.

**Orchestration** — a central coordinator (the orchestrator/saga) directs each step, explicitly calling each participant and tracking state:

```
LoanOriginationSaga.orchestrate():
  → calls NachService.initiateMandate()
  → if success: calls NotificationService.sendSanctionLetter()
  → if success: calls DocumentService.generatePdf()
  → if any step fails: calls compensating operations
```

| Aspect                | Choreography                                             | Orchestration                                              |
|-----------------------|----------------------------------------------------------|------------------------------------------------------------|
| Coupling              | Services coupled to event schemas only                   | Services coupled to orchestrator; orchestrator knows all   |
| Visibility            | Hard to see the full flow — distributed across services  | Full flow visible in one place                             |
| Adding a new step     | Add a new consumer — no other service changes            | Modify the orchestrator                                    |
| Failure handling      | Each service handles its own failures                    | Orchestrator manages compensation — clearer control        |
| Debugging             | Correlation ID needed to trace across services           | Orchestrator state is the audit trail                      |
| Best for              | Simple, independent reactions to events                  | Complex multi-step workflows with compensation logic        |

In a lending platform: **choreography** for simple reactions (send notification, update CRM on every sanctioned loan); **orchestration** for complex workflows (multi-step loan disbursal across NBFC + partner bank with compensation if any step fails).

## Section 6: Anti-patterns and Pitfalls

**Q17. What are the most common EDA mistakes in a fintech backend?**
A:

**Mistake 1 — Publishing events before the DB transaction commits (lost event problem):**
```typescript
// ❌ Event published before transaction commits
async sanctionLoan(loanId: string): Promise<void> {
  await this.eventBus.publish(new LoanSanctionedEvent(loanId)); // publishes BEFORE DB write
  await this.prisma.loan.update({ where: { id: loanId }, data: { status: 'SANCTIONED' } });
  // If DB update fails → event is published but state change didn't happen
}

// ✅ Fix — Outbox Pattern or publish after commit
async sanctionLoan(loanId: string): Promise<void> {
  await this.prisma.$transaction(async (tx) => {
    await tx.loan.update({ where: { id: loanId }, data: { status: 'SANCTIONED' } });
    await tx.outboxEvent.create({ data: { eventType: 'LoanSanctionedEvent', payload: { loanId } } });
  });
  // Outbox relay publishes the event after the transaction commits
}
```

**Mistake 2 — Non-idempotent consumers causing double processing:**
```typescript
// ❌ Inserting without deduplication — duplicate event causes duplicate record
await this.prisma.emiPayments.create({
  data: { loanId: event.loanId, amount: event.amount },
}); // Will throw on duplicate or silently insert twice

// ✅ Upsert with natural unique key
await this.prisma.emiPayments.upsert({
  where: { collectionRef: event.collectionReference },
  create: { loanId: event.loanId, amount: event.amount, collectionRef: event.collectionReference },
  update: {}, // no-op — already exists
});
```

**Mistake 3 — Fat events (carrying too much data):**
```typescript
// ❌ Fat event — carries entire loan object, all related entities
class LoanSanctionedEvent {
  loan: FullLoanObject;        // 50 fields
  applicant: FullApplicant;    // 30 fields
  bureauReport: FullReport;    // 100 fields — most consumers don't need this
}

// ✅ Lean event — carries only what happened + IDs for consumers to fetch if needed
class LoanSanctionedEvent {
  applicationId: string;
  applicantId: string;
  sanctionedAmount: number;
  sanctionedBy: string;
  occurredAt: Date;
  // Consumers who need more data fetch from the owning service via API
}
```

**Mistake 4 — Consumers that make synchronous calls to the publishing service:**
```typescript
// ❌ Consumer calls back to the publisher — defeats loose coupling; creates circular dependency
@EventHandler(LoanSanctionedEvent)
async handle(event: LoanSanctionedEvent): Promise<void> {
  // NACH service calling back to LoanOrigination to get full application details
  const fullApplication = await this.loanOriginationClient.getApplication(event.applicationId);
  await this.initiateMandateSetup(fullApplication);
}

// ✅ Fix — either include needed data in the event (if small),
// or NACH service maintains its own replica via earlier events
```

**Mistake 5 — Missing correlation IDs for distributed tracing:**
```typescript
// ❌ No way to trace a request across multiple services and events
class LoanApplicationSubmittedEvent {
  applicationId: string;
  applicantId: string;
  // No correlation/trace ID — impossible to link logs across services
}

// ✅ Always include correlation ID
class LoanApplicationSubmittedEvent {
  applicationId: string;
  applicantId: string;
  correlationId: string;  // propagated from the original HTTP request
  causationId: string;    // ID of the event that caused this event (event chain)
  occurredAt: Date;
}
```

**Q18. How do you handle "poison pill" messages that consistently fail processing?**
A: A poison pill is a message that cannot be processed regardless of retry count — it causes every consumer attempt to fail, eventually landing in the DLQ:

```typescript
// Structured DLQ processing — don't replay blindly
@Injectable()
export class DlqProcessingService {
  async investigateDlqMessage(messageId: string): Promise<DlqAnalysis> {
    const message = await this.dlqClient.getMessage(messageId);
    const payload = JSON.parse(message.body);

    return {
      messageId,
      eventType: payload.eventType,
      receiveCount: message.attributes.ApproximateReceiveCount,
      firstReceived: message.attributes.ApproximateFirstReceiveTimestamp,
      payload,
      // Suggest action based on error pattern
      recommendedAction: await this.classifyFailure(payload),
    };
  }

  async replayWithFix(messageId: string, fixedPayload: unknown): Promise<void> {
    // Validate the fixed payload before replaying
    await this.schemaValidator.validate(fixedPayload);

    // Send to original queue for reprocessing
    await this.originalQueue.send(JSON.stringify(fixedPayload));

    // Remove from DLQ
    await this.dlqClient.deleteMessage(messageId);

    this.logger.info({ message: 'DLQ message replayed', messageId });
  }

  async discardPoisonPill(messageId: string, reason: string): Promise<void> {
    await this.dlqClient.deleteMessage(messageId);
    await this.auditLog.record('DLQ_MESSAGE_DISCARDED', { messageId, reason });
    // Alert if the discarded message had financial significance
  }
}
```

## Section 7: Scenario / System Design Questions

**Q19. "Design the event-driven architecture for a NACH mandate registration flow. The loan is sanctioned, mandate must be registered with NPCI, confirmed, then the loan moves to active status."**
A:

```
Events and flow:

1. LoanSanctionedEvent (LoanOriginationService)
   ↓
2. NachMandateService consumes:
   - Creates mandate record in DB (status: REGISTRATION_INITIATED)
   - Calls NPCI registration API
   - Publishes NachRegistrationSubmittedEvent

3. NPCI processes registration (async, minutes to hours)
   - Sends callback to NachCallbackController
   - NachCallbackController validates signature, routes to SQS

4a. If NPCI approves:
   - NachCallbackConsumer processes NachApprovedCallback
   - Updates mandate status to REGISTERED
   - Publishes NachMandateRegisteredEvent

4b. If NPCI rejects:
   - NachCallbackConsumer processes NachRejectedCallback
   - Publishes NachMandateRejectionEvent
   - NotificationConsumer sends "action required" to borrower
   - NachRetryConsumer schedules re-registration with corrected details

5. NachMandateRegisteredEvent consumed by:
   - LoanActivationConsumer: moves loan from SANCTIONED to ACTIVE, generates EMI schedule
   - NotificationConsumer: sends "mandate registered, first EMI on [date]" SMS
   - EmiSchedulerConsumer: registers first EMI collection date in scheduler
```

```typescript
// NACH service consumer — handles LoanSanctionedEvent
@EventHandler(LoanSanctionedEvent)
export class InitiateNachRegistrationConsumer {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    // Idempotency — don't register twice
    const existing = await this.mandateRepo.findByLoanId(event.applicationId);
    if (existing) return;

    // Register with NPCI
    const registrationRef = await this.npciClient.submitRegistration({
      customerName: await this.getApplicantName(event.applicantId),
      amount: event.sanctionedAmount,
      // ... other NACH fields
    });

    // Save mandate with outbox event
    await this.prisma.$transaction(async (tx) => {
      await tx.nachMandate.create({
        data: { loanId: event.applicationId, status: 'SUBMITTED', registrationRef },
      });
      await tx.outboxEvent.create({
        data: {
          eventType: 'NachRegistrationSubmittedEvent',
          payload: JSON.stringify({ loanId: event.applicationId, registrationRef }),
        },
      });
    });
  }
}
```

**Q20. "Your loan sanctioned notifications are sometimes delayed by up to 10 minutes. On investigation, you find the notification service is processing events slowly because it handles too many event types on one consumer. How do you fix this?"**
A: Consumer specialisation — split the overloaded consumer into separate, focused consumers per event type or per notification channel:

```
❌ Current:
One notification consumer processes:
  LoanApplicationSubmittedEvent (100/day)
  LoanSanctionedEvent (80/day — HIGH PRIORITY)
  EmiCollectedEvent (5000/day — HIGH VOLUME)
  EmiDefaultedEvent (200/day)
  LoanDisbursedEvent (80/day — HIGH PRIORITY)
→ EmiCollectedEvent floods the queue, delays high-priority LoanSanctionedEvent

✅ Fix: Separate queues per event type + separate consumer instances

SanctionNotificationQueue → 5 consumer instances (critical path — must be fast)
  Processes only: LoanSanctionedEvent, LoanDisbursedEvent

EmiNotificationQueue → 2 consumer instances (high volume but not urgent)
  Processes only: EmiCollectedEvent, EmiDefaultedEvent

ApplicationNotificationQueue → 2 consumer instances
  Processes only: LoanApplicationSubmittedEvent
```

```typescript
// Separate SQS queues with appropriate concurrency settings
const sanctionQueue = new sqs.Queue(this, 'SanctionNotificationQueue', {
  visibilityTimeout: Duration.seconds(30),
});

const emiQueue = new sqs.Queue(this, 'EmiNotificationQueue', {
  visibilityTimeout: Duration.seconds(60), // longer — EMI processing is heavier
});

// SNS filter policies — route events to the right queue
sanctionTopic.addSubscription(new sqs.SqsSubscription(sanctionQueue, {
  filterPolicy: {
    eventType: sns.SubscriptionFilter.stringFilter({
      allowlist: ['LoanSanctionedEvent', 'LoanDisbursedEvent'],
    }),
  },
}));

emiTopic.addSubscription(new sqs.SqsSubscription(emiQueue, {
  filterPolicy: {
    eventType: sns.SubscriptionFilter.stringFilter({
      allowlist: ['EmiCollectedEvent', 'EmiDefaultedEvent'],
    }),
  },
}));
```

After this change, `LoanSanctionedEvent` has its own dedicated queue — EMI volume can't delay it. Each consumer type can be independently scaled.

## Quick Reference: EDA Checklist

| Signal                                                                            | Decision                                                                         |
|-----------------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| LoanService must call 5 downstream services synchronously                         | Extract to events — publish LoanSanctionedEvent; let consumers react             |
| Event published, then DB transaction fails — inconsistent state                   | Outbox Pattern — store event in DB transactionally; relay separately             |
| Consumer fails after processing but before acknowledging — event redelivered      | Idempotent consumers — upsert with natural unique key                            |
| Event delivered to 6 different consumers                                          | SNS topic → 6 SQS queues (fan-out with durability)                              |
| High-volume events (EMI) delaying high-priority events (sanction) on same queue   | Separate queues per event type; separate consumer pools                          |
| Message consistently fails processing — DLQ alert fires                           | Investigate poison pill; fix payload or discard with audit log                   |
| Need full audit trail of all loan state transitions                               | Consume all domain events → write to append-only audit log projection            |
| Complex multi-step flow with compensation (co-lending disbursement)               | Orchestration-based Saga with explicit state machine                             |
| Simple independent reactions to events (notification, CRM update)                 | Choreography — each consumer reacts independently                                |
| Consumer needs data beyond what's in the event                                    | Include in event (if small), or consumer fetches via API, or event-driven replica |

**Tip for the interview:** At the 5 YOE level, EDA questions come as system design ("design the loan sanctioned event flow"), debugging ("notifications are delayed — why?"), or reliability ("what happens if the event broker is down during sanctioning?"). The answers that land at the senior level go straight to the production concerns: the Outbox Pattern for ensuring events are published atomically with state changes (the most important EDA reliability pattern in fintech), idempotent consumers as the universal answer to at-least-once delivery, and DLQs as the safety net for unprocessable messages. The differentiating answer names the Outbox Pattern by name, explains why publishing before the transaction commits is dangerous (especially for financial operations), describes the SNS→SQS fan-out pattern for multi-consumer events, and can articulate when to use choreography (simple independent reactions) vs orchestration (complex flows with compensation). In a lending context, the NACH mandate registration flow and the EMI collection flow are the two most compelling EDA stories — have one of them ready as a concrete end-to-end example with event names, consumer responsibilities, and failure handling.
