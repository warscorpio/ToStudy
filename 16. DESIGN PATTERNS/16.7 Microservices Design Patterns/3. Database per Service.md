# Microservices & Data Patterns: Database per Service — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Database per Service pattern?**
A: Database per Service is a microservices data management pattern that dictates that **each service owns its own database exclusively** — no other service may directly access that database. The database is a private implementation detail of the service, not a shared infrastructure resource. Services share data only through well-defined APIs (REST, gRPC, events) — never through direct database connections, shared schemas, or cross-database JOINs.

The rule is absolute: if Service A needs data owned by Service B, Service A calls Service B's API. It never queries Service B's database directly. Service B is the sole authority over its own data.

**Q2. What problem does Database per Service solve?**
A: It solves the **shared database coupling** problem that emerges when multiple services (or teams) share a single database:

- **Schema coupling** — any schema change (adding a column, renaming a table, changing a data type) in the shared database requires coordination across all services that query that schema. A migration becomes a multi-team, multi-service deployment event.
- **Deployment coupling** — if Service A's migration breaks Service B's queries, both services must be deployed together. Independent deployment — a core microservices benefit — becomes impossible.
- **Technology lock-in** — a shared PostgreSQL database means every service must use PostgreSQL, even if Service B would benefit from a document store or a time-series database.
- **Performance coupling** — a slow, heavy query from Service A can degrade the database performance experienced by Service B. Resources aren't isolated.
- **Ownership ambiguity** — with a shared database, it's unclear who owns which table, who is responsible for a schema change, and who to contact when data is inconsistent.

**Q3. What is the "shared database" anti-pattern, and what does it look like in a lending platform?**
A: The shared database anti-pattern means multiple services or teams directly query the same database tables:

```
❌ Shared Database Anti-pattern:

  LoanOriginationService ──┐
  CollectionsService      ──┤──► Shared PostgreSQL ──► loans, applicants,
  KYCService              ──┤                          emi_schedules, nach_mandates,
  BureauService           ──┤                          kyc_docs, repayments...
  ReportingService        ──┘

Consequences:
- Origination team adds a column to loans → breaks Collections' query
- Collections team adds an index → slows Origination's writes
- KYC team changes applicant table structure → requires coordinating with 4 other teams
- Can't deploy any service independently
- Can't choose different DB tech per service need
```

In a monolith this is acceptable — it's a single application. In a microservices architecture with separate teams, it collapses independence and negates the benefits of microservices.

**Q4. Does Database per Service mean one physical database server per service?**
A: No — it means one logical database (schema isolation) per service, though the physical infrastructure can be shared or separate depending on operational needs:

| Isolation Level               | Description                                                                  | When appropriate                                   |
|-------------------------------|------------------------------------------------------------------------------|----------------------------------------------------|
| Separate tables in one DB     | Same Postgres server and DB; different table prefixes/ownership              | Development, small teams, low operational maturity |
| Separate schemas in one DB    | Same Postgres server; service owns a schema (`loan_origination.*`)           | Medium scale; shared Postgres ops team             |
| Separate databases on one server | Same Postgres server; `loan_db`, `kyc_db`, `collections_db`             | Cost-optimised production; ops team manages one server |
| Separate database servers     | Each service has its own RDS/Cloud SQL instance                              | Large scale; strict isolation; independent scaling  |
| Mixed technology              | Loan service: Postgres; Notification: DynamoDB; Analytics: Redshift          | Each team chooses best tool for their access pattern |

The pattern is about **access isolation** — no service accesses another service's data directly — not necessarily physical server separation. Start with schema-level isolation; separate servers when you have a specific operational or scaling reason.

**Q5. What are the different database-per-service isolation strategies available in PostgreSQL?**
A:

```sql
-- Strategy 1 — Schema per service (recommended starting point)
-- Each service owns one schema; cross-schema foreign keys are forbidden
CREATE SCHEMA loan_origination;
CREATE SCHEMA kyc;
CREATE SCHEMA collections;
CREATE SCHEMA nach;

-- Tables within each schema are owned by that service
CREATE TABLE loan_origination.loan_applications (
  id UUID PRIMARY KEY,
  applicant_id UUID NOT NULL,   -- reference by ID only; no FK to kyc.applicants
  pan TEXT NOT NULL,
  status TEXT NOT NULL,
  requested_amount BIGINT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE kyc.applicants (
  id UUID PRIMARY KEY,
  pan TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  kyc_status TEXT NOT NULL,
  verified_at TIMESTAMPTZ
);

-- Enforce isolation via Postgres roles — service DB user can only access its own schema
CREATE ROLE loan_origination_svc LOGIN PASSWORD '...';
GRANT USAGE ON SCHEMA loan_origination TO loan_origination_svc;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA loan_origination TO loan_origination_svc;
-- Crucially: NO grants on kyc.* or collections.* to loan_origination_svc

CREATE ROLE kyc_svc LOGIN PASSWORD '...';
GRANT USAGE ON SCHEMA kyc TO kyc_svc;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA kyc TO kyc_svc;
-- No grants on loan_origination.* or collections.* to kyc_svc
```

This database-level enforcement means even if a developer accidentally writes a cross-schema query, it will fail at runtime — a hard technical boundary, not just a code convention.

## Section 2: Data Ownership and Cross-Service Data Access

**Q6. How does a service access data owned by another service?**
A: Only through the owning service's published API — never by querying its database. The three standard mechanisms:

**Mechanism 1 — Synchronous API call (REST/gRPC):**
```typescript
// LoanOriginationService needs applicant name for the sanction letter
// ❌ Direct DB query — forbidden
const applicant = await this.prisma.kycApplicants.findUnique({ where: { id: applicantId } });

// ✅ API call to KYC service
@Injectable()
export class KycServiceClient {
  async getApplicant(applicantId: string): Promise<ApplicantDto> {
    const response = await this.httpClient.get<ApplicantDto>(
      `${process.env.KYC_SERVICE_URL}/applicants/${applicantId}`,
    );
    return response.data;
  }
}

// LoanOriginationService
async generateSanctionLetter(loanId: string): Promise<void> {
  const loan = await this.loanRepository.findById(loanId);
  const applicant = await this.kycServiceClient.getApplicant(loan.applicantId); // API call
  await this.documentService.generate(loan, applicant);
}
```

**Mechanism 2 — Asynchronous events (domain events / message queue):**
```typescript
// KYC service publishes events when applicant data changes
// LoanOrigination service subscribes and maintains its own copy of needed data

// KYC Service publishes
this.eventBus.publish(new ApplicantKycVerifiedEvent({
  applicantId: applicant.id,
  pan: applicant.pan,
  name: applicant.name,
  verifiedAt: new Date(),
}));

// LoanOrigination Service maintains a local read model of applicant summary
@EventHandler(ApplicantKycVerifiedEvent)
class ApplicantKycVerifiedHandler {
  async handle(event: ApplicantKycVerifiedEvent): Promise<void> {
    // Store minimum needed data locally — avoids runtime API calls for read-heavy operations
    await this.prisma.applicantSummaryCache.upsert({
      where: { applicantId: event.applicantId },
      create: { applicantId: event.applicantId, pan: event.pan, name: event.name },
      update: { name: event.name },
    });
  }
}
```

**Mechanism 3 — Saga / choreography (for multi-step writes):**
When a business operation spans multiple services (create loan + run KYC + register NACH mandate), a saga coordinates the workflow through events, with each service completing its own step and publishing a result event.

**Q7. What data does each service in a lending platform own, and what does it NOT own?**
A:

| Service                 | Owns                                                                      | References (by ID, not direct query)                     |
|-------------------------|---------------------------------------------------------------------------|----------------------------------------------------------|
| **KYC / Identity**      | `applicants`, `kyc_documents`, `kyc_verifications`, `kyc_status`         | — (foundational service, others reference it)            |
| **Loan Origination**    | `loan_applications`, `sanction_conditions`, `bureau_reports`              | `applicant_id` (from KYC), `product_code` (from Products)|
| **Products / Catalogue**| `loan_products`, `interest_rate_bands`, `fee_schedules`                  | — (reference data, others read via API)                  |
| **Active Loans**        | `active_loans`, `emi_schedules`, `repayments`, `prepayments`             | `applicant_id`, `application_id`, `product_code`         |
| **NACH / Mandate**      | `nach_mandates`, `mandate_presentations`, `debit_attempts`               | `loan_id`, `applicant_id`                                |
| **Collections**         | `collection_cases`, `collection_actions`, `dpd_history`                  | `loan_id`, `applicant_id`                                |
| **Notification**        | `notification_logs`, `notification_templates`, `delivery_receipts`       | `applicant_id`, `loan_id`                                |
| **Ledger / Accounting** | `ledger_entries`, `gl_accounts`, `journal_entries`                       | `loan_id`, `applicant_id`                                |
| **Regulatory Reporting**| `rbi_reports`, `submission_logs`, `psl_classifications`                  | Reads from other services via events/API at report time  |

Each service keeps its own copy of the data it needs from other services — referenced by ID and fetched via API or received via event.

**Q8. What is data denormalisation in the context of Database per Service, and is it acceptable?**
A: Data denormalisation — storing copies of data from other services locally — is not just acceptable in a microservices architecture, it is **necessary and expected**. Each service stores the subset of external data it needs for its own operations, rather than joining across service boundaries at query time.

```typescript
// LoanOrigination service's loan_applications table stores
// the applicant's PAN — even though PAN is "owned" by KYC service
// This is intentional denormalisation, not a violation
CREATE TABLE loan_origination.loan_applications (
  id UUID PRIMARY KEY,
  applicant_id UUID NOT NULL,       -- reference to KYC service's applicant
  applicant_pan TEXT NOT NULL,      -- denormalised copy — needed for bureau pull
  applicant_name TEXT NOT NULL,     -- denormalised copy — needed for sanction letter
  -- ... rest of application data
);
```

The applicant's PAN is the KYC service's data, but LoanOrigination needs it at application creation time (for the bureau pull). Storing it locally means:
- No synchronous dependency on KYC service at underwriting time
- The loan record carries the PAN that was submitted at application — even if the applicant changes their legal name later, the historical application is accurate
- LoanOrigination can operate independently even if KYC service is temporarily unavailable

The trade-off: if a PAN changes (rare but possible — name corrections, re-issuance), the denormalised copy may become stale. This is acceptable for historical records and managed through domain events.

## Section 3: Challenges and Solutions

**Q9. What is the distributed transaction problem, and how does it arise with Database per Service?**
A: In a monolith with a shared database, a loan application creation can be wrapped in a single ACID transaction: create the application record, update the applicant's KYC status, register the NACH mandate, create the first EMI schedule — all atomically. Either everything succeeds or nothing does.

With Database per Service, these operations span three different databases (LoanOrigination DB, KYC DB, NACH DB). **A single ACID transaction is impossible across database boundaries** — there's no global transaction coordinator. The distributed transaction problem:

```
Step 1: Create loan application in LoanOrigination DB → SUCCESS
Step 2: Update KYC status in KYC DB → SUCCESS
Step 3: Register NACH mandate in NACH DB → FAILURE (NPCI unavailable)

What happens to steps 1 and 2? They already committed.
There's no global rollback.
```

This is the fundamental challenge that replaces ACID transactions with **eventual consistency** in a microservices world. The accepted solution is the Saga pattern.

**Q10. What is the Saga pattern, and how does it address the distributed transaction problem?**
A: A Saga is a sequence of local transactions, one per service, where each step publishes an event to trigger the next step. If a step fails, compensating transactions undo the work of preceding steps.

Two implementation styles:

**Choreography-based Saga** — services react to events from each other; no central coordinator:

```typescript
// LoanOrigination publishes event after creating application
this.eventBus.publish(new LoanApplicationSubmittedEvent({
  applicationId, applicantId, pan, amount, productCode,
}));

// KYC service reacts
@EventHandler(LoanApplicationSubmittedEvent)
class UpdateKycStatusForNewApplicationHandler {
  async handle(event: LoanApplicationSubmittedEvent): Promise<void> {
    await this.kycService.flagActiveApplication(event.applicantId, event.applicationId);
    this.eventBus.publish(new KycFlaggedForApplicationEvent({ applicationId: event.applicationId }));
  }
}

// NACH service reacts
@EventHandler(LoanSanctionedEvent)
class InitiateNachMandateOnSanctionHandler {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    await this.nachService.initiateMandateRegistration(event.applicationId, event.applicantId);
  }
}
```

**Orchestration-based Saga** — a central coordinator directs each service step:

```typescript
// Saga orchestrator — in the LoanOrigination service
@Injectable()
export class LoanOriginationSaga {
  async execute(command: InitiateLoanApplicationCommand): Promise<void> {
    const sagaId = uuid();

    // Step 1 — create application (local)
    const application = await this.loanAppService.create(command);
    await this.sagaLog.recordStep(sagaId, 'APPLICATION_CREATED', application.id);

    try {
      // Step 2 — trigger KYC verification (remote)
      await this.kycServiceClient.verifyApplicant(command.applicantId);
      await this.sagaLog.recordStep(sagaId, 'KYC_TRIGGERED');

      // Step 3 — trigger bureau pull (remote)
      await this.bureauServiceClient.pullReport(command.pan, application.id);
      await this.sagaLog.recordStep(sagaId, 'BUREAU_TRIGGERED');

    } catch (err) {
      // Compensate — roll back what we can
      await this.compensate(sagaId, application.id);
      throw new SagaFailedException(sagaId, err);
    }
  }

  private async compensate(sagaId: string, applicationId: string): Promise<void> {
    const completedSteps = await this.sagaLog.getCompletedSteps(sagaId);

    // Compensate in reverse order
    if (completedSteps.includes('KYC_TRIGGERED')) {
      await this.kycServiceClient.cancelVerification(applicationId);
    }
    if (completedSteps.includes('APPLICATION_CREATED')) {
      await this.loanAppService.cancel(applicationId, 'SAGA_COMPENSATION');
    }
  }
}
```

**Q11. How do you handle cross-service queries (joins) without a shared database?**
A: Cross-service joins — "show me all active loans with their applicant KYC status" — are one of the trickiest challenges. Four approaches:

**Approach 1 — API Composition (client-side join):**
```typescript
// Gateway or BFF aggregates data from multiple services
@Injectable()
export class LoanDashboardAggregator {
  async getDashboard(applicantId: string): Promise<LoanDashboardDto> {
    // Parallel calls to independent services
    const [loans, kycStatus, nachStatus] = await Promise.all([
      this.loanService.getActiveLoans(applicantId),
      this.kycService.getKycStatus(applicantId),
      this.nachService.getMandateStatus(applicantId),
    ]);

    return {
      applicantId,
      kycStatus: kycStatus.status,
      loans: loans.map(loan => ({
        ...loan,
        mandateActive: nachStatus.find(m => m.loanId === loan.id)?.active ?? false,
      })),
    };
  }
}
```
Suitable for: low data volume, acceptable latency from multiple sequential/parallel calls.

**Approach 2 — CQRS Read Model (cross-service projection):**
```typescript
// A dedicated reporting/read service subscribes to events from all services
// and maintains a pre-joined view
@Injectable()
export class LoanPortfolioReadModelProjector {
  @OnEvent('LoanApplicationSubmittedEvent')
  async onApplicationCreated(event: LoanApplicationSubmittedEvent): Promise<void> {
    await this.prisma.portfolioView.create({
      data: { applicationId: event.applicationId, applicantId: event.applicantId, status: 'SUBMITTED' },
    });
  }

  @OnEvent('ApplicantKycVerifiedEvent')
  async onKycVerified(event: ApplicantKycVerifiedEvent): Promise<void> {
    await this.prisma.portfolioView.updateMany({
      where: { applicantId: event.applicantId },
      data: { kycStatus: 'VERIFIED', applicantName: event.name },
    });
  }

  @OnEvent('NachMandateRegisteredEvent')
  async onMandateRegistered(event: NachMandateRegisteredEvent): Promise<void> {
    await this.prisma.portfolioView.updateMany({
      where: { applicationId: event.loanId },
      data: { mandateStatus: 'REGISTERED', mandateUrn: event.umrn },
    });
  }
}

// Query — fast single-table read against the denormalised view
@QueryHandler(GetPortfolioDashboardQuery)
export class GetPortfolioDashboardQueryHandler {
  async execute(query: GetPortfolioDashboardQuery): Promise<PortfolioDashboardDto[]> {
    return this.prisma.portfolioView.findMany({
      where: { applicantId: query.applicantId },
      orderBy: { createdAt: 'desc' },
    });
  }
}
```
Suitable for: high-read dashboard queries, complex multi-service joins, near-real-time consistency acceptable.

**Approach 3 — Data Replication via Events:**
Each service subscribes to events from other services and maintains a local replica of the foreign data it needs:
```typescript
// NACH service subscribes to LoanOrigination events to get loan data it needs
@EventHandler(LoanSanctionedEvent)
class ReplicateLoanDataForNachHandler {
  async handle(event: LoanSanctionedEvent): Promise<void> {
    // NACH service stores only what it needs locally
    await this.prisma.loanReplica.upsert({
      where: { loanId: event.applicationId },
      create: {
        loanId: event.applicationId,
        applicantId: event.applicantId,
        sanctionedAmount: event.sanctionedAmount,
        productCode: event.productCode,
      },
      update: { sanctionedAmount: event.sanctionedAmount },
    });
  }
}
```

**Approach 4 — Separate Analytics/Reporting Database:**
A dedicated analytics service or data warehouse (Redshift, BigQuery) consumes events or CDC (Change Data Capture) streams from all service databases and maintains a unified view for reporting:
```
Each service DB → CDC (AWS DMS / Debezium) → Kafka → Analytics DB
Analytics service → complex joins across all data → RBI reports, dashboards
```

**Q12. How do you manage data consistency in an eventually consistent system?**
A: Eventual consistency means accepting a window during which different services may have slightly stale views of shared data. Manage it explicitly:

**Technique 1 — Accept and communicate the lag:**
```typescript
// API response includes data freshness metadata
return {
  loans: dashboardData.loans,
  kycStatus: dashboardData.kycStatus,
  _meta: {
    dataAsOf: dashboardData.lastUpdatedAt,
    staleIfOlderThan: '5 minutes',
    // Frontend shows "Last updated 2 minutes ago" rather than pretending it's real-time
  },
};
```

**Technique 2 — Strong consistency for critical paths via synchronous API calls:**
```typescript
// For the sanction decision — KYC status must be accurate
// Use synchronous API call, not cached event-driven replica
async sanctionLoan(loanId: string): Promise<void> {
  const loan = await this.loanRepository.findById(loanId);

  // Critical: call KYC service synchronously — don't use local replica
  const kycStatus = await this.kycServiceClient.getKycStatus(loan.applicantId);
  if (kycStatus.status !== 'VERIFIED') {
    throw new KycNotVerifiedException(loan.applicantId);
  }
  // ...proceed with sanction
}
```

**Technique 3 — Idempotent event processing:**
```typescript
// Projectors must be idempotent — events may be delivered more than once
@EventHandler(EmiCollectedEvent)
async onEmiCollected(event: EmiCollectedEvent): Promise<void> {
  await this.prisma.portfolioView.update({
    where: { loanId: event.loanId },
    data: {
      // Use MAX/comparison so replaying the event doesn't corrupt data
      lastEmiDate: event.collectedOn,
      outstandingPrincipal: { decrement: event.principalComponent },
      version: { increment: 1 },
    },
  });
}
```

**Q14. How do you implement a cross-service API client in NestJS for the Database per Service pattern?**
A:

```typescript
// KYC service client — used by LoanOrigination service
@Injectable()
export class KycServiceClient {
  private readonly httpClient: AxiosInstance;

  constructor(private readonly configService: ConfigService) {
    this.httpClient = axios.create({
      baseURL: configService.get('KYC_SERVICE_URL'),
      timeout: 5000,
      headers: {
        'X-Service-Name': 'loan-origination',
        'X-Service-Token': configService.get('INTER_SERVICE_TOKEN'),
      },
    });
  }

  async getApplicant(applicantId: string): Promise<ApplicantDto | null> {
    try {
      const response = await this.httpClient.get<ApplicantDto>(`/applicants/${applicantId}`);
      return response.data;
    } catch (err) {
      if ((err as AxiosError).response?.status === 404) return null;
      throw new KycServiceUnavailableException(err as Error);
    }
  }

  async getKycStatus(applicantId: string): Promise<KycStatusDto> {
    const response = await this.httpClient.get<KycStatusDto>(`/applicants/${applicantId}/kyc-status`);
    return response.data;
  }

  async verifyPan(pan: string, name: string, dob: Date): Promise<PanVerificationResult> {
    const response = await this.httpClient.post<PanVerificationResult>('/verifications/pan', {
      pan, name, dob: dob.toISOString(),
    });
    return response.data;
  }
}

// Service client registered as a provider in LoanOriginationModule
@Module({
  providers: [
    KycServiceClient,
    LoanApplicationService,
    // ...
  ],
})
export class LoanOriginationModule {}
```

**Q15. How do you handle database migrations in a Database per Service architecture?**
A: Each service owns and manages its own migrations independently — no coordination needed with other services:

```typescript
// Each service has its own migration scripts
// loan-origination/prisma/migrations/
//   20240101000000_initial_schema/migration.sql
//   20240215000000_add_sanction_conditions/migration.sql
//   20240301000000_add_bureau_score_index/migration.sql

// Deployment pipeline — each service migrates its own DB
// loan-origination Dockerfile:
// RUN npx prisma migrate deploy  ← runs only this service's migrations

// In CI/CD
async function deployLoanOriginationService() {
  // 1. Run loan origination's migrations only
  await runCommand('npx prisma migrate deploy', { cwd: './services/loan-origination' });

  // 2. Deploy the new service version
  await deployContainer('loan-origination', newVersion);

  // Other services deploy on their own schedule — completely independent
}
```

The critical benefit: the Collections team can add a column to their `collection_cases` table without:
- Telling the Origination team
- Coordinating a joint deployment
- Worrying about breaking Origination's queries
- Running a company-wide migration script

Each team moves at its own pace.

**Q16. How do you choose what type of database each service should use?**
A: Database per Service enables polyglot persistence — choosing the best database technology for each service's access patterns:

| Service                 | Recommended DB              | Reason                                                                          |
|-------------------------|-----------------------------|---------------------------------------------------------------------------------|
| **KYC / Identity**      | PostgreSQL                  | Relational data, ACID transactions, complex queries across applicant + docs      |
| **Loan Origination**    | PostgreSQL                  | Complex domain model, strict consistency for financial records                  |
| **Active Loans / EMI**  | PostgreSQL                  | Strong ACID guarantees for financial calculations; complex joins within service  |
| **NACH / Mandate**      | PostgreSQL                  | Financial records, audit trail requirements                                     |
| **Collections**         | PostgreSQL                  | Relational (loan + action + agent assignment)                                   |
| **Notification**        | PostgreSQL + Redis           | Postgres for logs; Redis for real-time notification queue and delivery tracking  |
| **Session / Auth**      | Redis                       | High-speed key-value; TTL-based expiry for sessions/tokens                      |
| **Regulatory Reporting**| PostgreSQL + Redshift        | OLTP for submission tracking; Redshift/BigQuery for analytical queries           |
| **Audit Trail**         | Append-only PostgreSQL or S3 | Immutable audit log; chronological; rarely queried by primary key               |
| **Search**              | Elasticsearch               | Full-text search over loan applications, applicants                             |

## Section 5: Anti-patterns and Pitfalls

**Q17. What are the most common Database per Service violations?**
A:

**Violation 1 — Cross-service JOIN via shared database:**
```typescript
// ❌ LoanOriginationService querying KYC's applicants table directly
const result = await this.prisma.$queryRaw`
  SELECT la.*, a.name, a.kyc_status
  FROM loan_origination.loan_applications la
  JOIN kyc.applicants a ON a.id = la.applicant_id  -- ← cross-schema JOIN
  WHERE la.status = 'PENDING_REVIEW'
`;
// This works today but silently couples the two services
```

**Violation 2 — Shared sequence/ID generation across services:**
```typescript
// ❌ Both services share the same sequence for generating loan numbers
// If LoanOrigination uses `loan_number_seq` from a shared DB,
// and Collections also uses it, they're coupled to the same DB
CREATE SEQUENCE shared_db.loan_number_seq;
// Each service should generate its own IDs independently (UUID, NanoID, Snowflake)
```

**Violation 3 — "Convenience" foreign keys across service boundaries:**
```prisma
// ❌ Collections service Prisma schema with a foreign key to KYC's table
model CollectionCase {
  id          String    @id
  loanId      String
  applicant   Applicant @relation(fields: [applicantId], references: [id])
  // ↑ This creates a DB-level FK constraint to KYC service's table — forbidden
  applicantId String
}
```

**Violation 4 — Service that reads another service's event store for queries:**
```typescript
// ❌ Reporting service reads directly from LoanOrigination's event store table
const events = await this.prisma.$queryRaw`
  SELECT * FROM loan_origination.domain_events
  WHERE event_type = 'LoanSanctioned'
  AND occurred_at > NOW() - INTERVAL '1 day'
`;
// This is still a shared database violation — even if it's "just" the event store
// The correct approach: LoanOrigination publishes events to a shared message bus
```

**Violation 5 — Distributed monolith (microservices in shape only):**
```typescript
// Services look separate but share the same Prisma client instance
// connected to the same database with access to all tables
@Module({
  imports: [PrismaModule], // single shared PrismaModule with access to ALL tables
  providers: [LoanService, KycService, CollectionsService], // all in same module!
})
export class AppModule {}
// This is a monolith with microservice naming conventions, not actual isolation
```

**Q18. How do you detect shared database coupling during a code review?**
A: Look for these signals:

```typescript
// Signal 1 — Prisma schema contains models "owned" by another service
model KycApplicant {   // ← This model lives in KYC service's DB — why is it here?
  id     String
  pan    String
  status String
}

// Signal 2 — SQL query references another service's schema
await this.prisma.$queryRaw`SELECT * FROM kyc.applicants WHERE id = ${applicantId}`;

// Signal 3 — Repository imports another service's entity
import { KycApplicantEntity } from '../../kyc/entities/kyc-applicant.entity'; // ← wrong

// Signal 4 — Service constructor injects another service's repository
constructor(
  private readonly loanRepo: LoanRepository,
  private readonly kycApplicantRepo: KycApplicantRepository, // ← should be a client, not repo
) {}

// Signal 5 — DATABASE_URL environment variable shared across multiple services
// in a monorepo .env file — may indicate same DB
DATABASE_URL=postgresql://shared-user:pass@shared-db:5432/shared_db
// Should be:
LOAN_ORIGINATION_DATABASE_URL=postgresql://loan-svc:pass@db:5432/loan_db
KYC_DATABASE_URL=postgresql://kyc-svc:pass@db:5432/kyc_db
```

## Section 6: Trade-offs and When Not to Apply

**Q19. What are the real costs of Database per Service?**
A:

- **Operational complexity** — instead of managing one database, you manage N databases, N connection pools, N backup schedules, N monitoring dashboards, N migration pipelines.
- **No cross-service transactions** — replacing ACID transactions with Sagas and compensating transactions is significantly more complex to implement, reason about, and debug.
- **Data duplication and eventual consistency** — the same data (applicant name, PAN) is stored in multiple places. Updates require propagation via events; inconsistency windows must be accepted and designed around.
- **Higher query latency for cross-service data** — API calls between services add network latency; a multi-service dashboard may require 4–5 sequential or parallel calls instead of one DB query.
- **Harder debugging** — a bug that corrupts data across multiple services is harder to trace than a bug in a shared database with consistent state.
- **Team overhead** — each team must define, publish, and version their service's API contract. Changing a data structure requires coordinating with all consumer teams.

**Q20. When should you NOT use Database per Service?**
A:

- **Small team with one codebase** — a team of 3–5 engineers doesn't benefit from the overhead of distributed databases. A modular monolith with schema-level isolation achieves much of the same benefit without the operational complexity.
- **Early-stage product with evolving domain boundaries** — if you're still figuring out what the bounded contexts are, splitting databases prematurely makes refactoring painful. Establish domain boundaries first, then split.
- **Operations team not ready** — managing multiple databases requires mature DevOps/platform engineering. If your ops team struggles with one database, ten databases will be overwhelming.
- **Strong consistency requirements everywhere** — some domains require strict cross-entity consistency (ledger debits and credits must always balance; regulatory reports must reflect exact snapshot state). If eventual consistency is unacceptable across all data, the pattern fights your requirements.
- **The "join" is genuinely within one bounded context** — if two tables are always queried together and represent one cohesive concept (loan application + sanction conditions), they belong in the same service's database, not in separate services.

The practical path: start with a well-structured monolith (or modular monolith), identify team and domain boundaries via DDD, enforce schema-level isolation within the monolith first, and extract to separate databases/services when a clear scaling or team independence need emerges.

## Section 7: Scenario / System Design Questions

**Q21. "Your lending platform is a monolith with a single PostgreSQL database. The KYC team and the Collections team are constantly blocking each other's migrations. How do you introduce Database per Service incrementally?"**
A: Incrementally via the Strangler Fig pattern — introduce isolation without a big-bang rewrite:

**Phase 1 — Enforce schema-level isolation in the monolith (weeks):**
```sql
-- Move tables into service-specific schemas
ALTER TABLE applicants SET SCHEMA kyc;
ALTER TABLE kyc_documents SET SCHEMA kyc;
ALTER TABLE collection_cases SET SCHEMA collections;
ALTER TABLE collection_actions SET SCHEMA collections;

-- Create service-specific DB users with restricted access
CREATE ROLE kyc_svc LOGIN;
GRANT USAGE, SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA kyc TO kyc_svc;
-- No grants to collections schema

CREATE ROLE collections_svc LOGIN;
GRANT USAGE, SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA collections TO collections_svc;
-- No grants to kyc schema

-- Update application DB connections to use the restricted users
```

**Phase 2 — Replace cross-schema queries with service API calls (weeks to months):**
```typescript
// Find all cross-schema queries in code — grep/eslint rule
// Replace each with an API call

// Before
const applicant = await prisma.kycApplicants.findUnique({ where: { id: applicantId } });

// After
const applicant = await this.kycServiceClient.getApplicant(applicantId);
```

**Phase 3 — Separate databases (when ready):**
```
KYC schema → migrate to kyc_db (separate database, same server initially)
Collections schema → migrate to collections_db
KYC service now uses KYC_DATABASE_URL → kyc_db
Collections service uses COLLECTIONS_DATABASE_URL → collections_db
```

**Phase 4 — Separate servers (when scaling requires it):**
Each service DB moves to its own RDS instance. This is now a purely operational change — the application code already uses isolated connections and service APIs.

At each phase, team independence increases. The KYC team's Phase 3 migration doesn't block the Collections team's schema changes.

**Q22. "Design the data architecture for a new co-lending feature where your NBFC and a partner bank jointly fund each loan. What data belongs to which service, and how do you handle the cross-service consistency requirement that both lenders must disburse before the loan is considered active?"**
A:

**Data ownership:**

```
LoanOrigination Service DB:
  co_lending_loans (id, base_loan_id, partner_bank_id, ratio, total_amount, status)

NBFC Disbursement Service DB:
  nbfc_disbursements (id, co_lending_loan_id, amount, payment_reference, disbursed_at, status)

Partner Bank Integration Service DB:
  partner_bank_disbursements (id, co_lending_loan_id, amount, partner_reference, confirmed_at, status)

Active Loans Service DB:
  active_loans (id, co_lending_loan_id, borrower_id, total_disbursed_amount, activated_at)
```

**Cross-service consistency via Saga:**

```typescript
// Choreography-based Saga — no central coordinator needed

// LoanOrigination publishes on sanction
eventBus.publish(new CoLendingLoanSanctionedEvent({ coLendingLoanId, nbfcAmount, partnerAmount }));

// NBFC Disbursement Service reacts
@EventHandler(CoLendingLoanSanctionedEvent)
async onSanctioned(event: CoLendingLoanSanctionedEvent): Promise<void> {
  await this.nbfcDisbursementService.initiateDisbursement(event.coLendingLoanId, event.nbfcAmount);
  eventBus.publish(new NbfcDisbursedEvent({ coLendingLoanId: event.coLendingLoanId, reference: result.rrn }));
}

// Partner Bank Integration Service reacts
@EventHandler(CoLendingLoanSanctionedEvent)
async onSanctioned(event: CoLendingLoanSanctionedEvent): Promise<void> {
  await this.partnerApiClient.requestDisbursement(event.coLendingLoanId, event.partnerAmount);
  // Partner bank confirms async via webhook → triggers PartnerBankDisbursedEvent
}

// LoanOrigination Service — coordinates activation
// Maintains a simple state machine — tracks which side has disbursed
@EventHandler(NbfcDisbursedEvent)
async onNbfcDisbursed(event: NbfcDisbursedEvent): Promise<void> {
  await this.coLendingRepo.markNbfcDisbursed(event.coLendingLoanId, event.reference);
  await this.checkAndActivate(event.coLendingLoanId);
}

@EventHandler(PartnerBankDisbursedEvent)
async onPartnerDisbursed(event: PartnerBankDisbursedEvent): Promise<void> {
  await this.coLendingRepo.markPartnerDisbursed(event.coLendingLoanId, event.reference);
  await this.checkAndActivate(event.coLendingLoanId);
}

private async checkAndActivate(coLendingLoanId: string): Promise<void> {
  const loan = await this.coLendingRepo.findById(coLendingLoanId);
  if (loan.nbfcDisbursed && loan.partnerDisbursed) {
    // Both sides have disbursed — activate the loan
    await this.coLendingRepo.updateStatus(coLendingLoanId, 'ACTIVE');
    eventBus.publish(new CoLendingLoanActivatedEvent({ coLendingLoanId }));
    // ActiveLoans service reacts to create the repayment schedule
  }
}
```

The consistency requirement ("both must disburse") is handled through event-driven coordination — no cross-database transaction needed. If either side fails to disburse within a timeout, a compensation event (triggered by a scheduled job checking for stuck sagas) can reverse the other side's disbursement.

## Quick Reference: Database per Service Checklist

| Signal                                                                          | Decision                                                                       |
|---------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Two teams regularly conflict on database migrations                             | Enforce schema-level isolation; plan service database separation               |
| Service A imports Service B's Prisma models or TypeORM entities                 | Violation — replace with service API client                                    |
| SQL query has cross-schema JOIN (loan_origination.loans JOIN kyc.applicants)    | Violation — use API call or event-driven read model                            |
| Complex dashboard query needs data from 5 services                              | CQRS read model projector or API composition at gateway level                   |
| Business operation must be atomic across two services                           | Saga pattern (choreography or orchestration); not a shared transaction          |
| Need to change database technology for one service                              | Only possible if each service has its own DB — polyglot persistence benefit    |
| Service is a startup/early-stage with unclear domain boundaries                 | Don't split databases yet — use schema isolation in a modular monolith first   |
| Two services always query the same tables together                              | Those tables may belong in the same service — reconsider boundaries            |
| One service's heavy queries degrade another service's performance               | Physical database separation resolves the resource contention                  |
| Regulatory audit requires complete data isolation between NBFC and partner bank | Separate databases per entity — physical isolation, not just schema             |

**Tip for the interview:** At the 5 YOE level, Database per Service questions come as system design problems — "design a lending platform's data architecture" or as debugging scenarios — "why can't the Collections team deploy independently?" The answer that lands at the senior level starts with the core principle (each service owns its data exclusively; access only via API), then names the real costs (no distributed transactions, eventual consistency, operational overhead of multiple databases), and demonstrates knowing the spectrum (schema isolation → separate databases → separate servers → polyglot persistence). The differentiators: understanding the Saga pattern as the replacement for ACID transactions, knowing that data duplication is intentional (not a mistake) in this architecture, and being able to describe the incremental migration path from a shared-database monolith using schema-level isolation as the first step. In a fintech context, the NACH/disbursement cross-service consistency scenario is the most compelling — showing that "both lenders must disburse before activation" is solved with event-driven saga coordination, not a shared transaction, demonstrates real production-level understanding.
