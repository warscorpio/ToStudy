# JavaScript / TypeScript (Microservices Design Patterns): Outbox Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Outbox Pattern?**
A: The Outbox Pattern (also called the Transactional Outbox) is a microservices messaging pattern that **guarantees reliable event publishing** by eliminating the dual-write problem between a database write and a message broker publish. Instead of writing to the database and publishing to a message broker in two separate operations — either of which can fail independently — the pattern stores outgoing messages in a dedicated `outbox` table within the **same database transaction** as the business data change. A separate background process (the relay) then reads from the outbox table and publishes to the message broker, marking each message as published once confirmed.

The pattern rests on one fundamental guarantee: **a single ACID transaction cannot span a relational database and an external message broker simultaneously**. The outbox sidesteps this impossibility by making the message broker publish eventually consistent, while keeping the business data and the intent to publish atomically consistent within the database.

**Q2. What is the dual-write problem, and why is it the root cause that the Outbox Pattern solves?**
A: The dual-write problem occurs when a service must write to two independent systems (e.g., a database and a message broker) and has no way to make both writes atomic. Every naive implementation has a failure window:

```ts
// Approach 1 — Write DB first, then publish: DB committed, publish fails
async function placeOrder(dto: PlaceOrderDto): Promise<Order> {
  const order = await db.orders.create(dto);        // ✓ DB committed
  await messageBroker.publish("order.placed", order); // ✗ network failure — event never sent
  // order exists in DB, downstream services never know ✗
  return order;
}

// Approach 2 — Publish first, then write DB: event sent, DB write fails
async function placeOrder(dto: PlaceOrderDto): Promise<Order> {
  await messageBroker.publish("order.placed", dto);  // ✓ event sent
  const order = await db.orders.create(dto);         // ✗ DB write fails
  // downstream services process an order that doesn't exist ✗
  return order;
}

// Approach 3 — Wrap in a "transaction" spanning both: not possible
// Databases and message brokers do not share a distributed transaction protocol
// (XA transactions exist but are impractical — slow, poorly supported, fragile)
await db.transaction(async (tx) => {
  await tx.orders.create(dto);
  await messageBroker.publish("order.placed", dto); // not part of the DB transaction ✗
});
// If messageBroker.publish fails after db.transaction commits → same as Approach 1 ✗
```

The dual-write problem has no correct solution without either a distributed transaction protocol (impractical) or the Outbox Pattern (practical and widely adopted):

```ts
// Outbox Pattern — atomic: both the order AND the intent to publish commit together
await db.transaction(async (tx) => {
  const order = await tx.orders.create(dto);         // ✓ business write
  await tx.outbox.create({                           // ✓ message intent — same transaction
    eventType:   "order.placed",
    aggregateId: order.id,
    payload:     JSON.stringify(order),
    createdAt:   new Date(),
    published:   false,
  });
  // Either BOTH commit or BOTH roll back — no split state ✓
});
// Outbox relay reads unpublished rows and sends to broker — eventually ✓
```

**Q3. What are the two components of the Outbox Pattern, and what does each do?**
A:

**Component 1 — The Outbox Table:**
A database table that lives in the same database as the business data. It stores the messages to be published, written atomically alongside the business data in the same transaction. Schema typically contains:

| Column | Type | Purpose |
|---|---|---|
| `id` | UUID | Unique message identifier (idempotency key for the relay) |
| `event_type` | VARCHAR | Message type / topic (`order.placed`, `payment.failed`) |
| `aggregate_type` | VARCHAR | Domain entity type (`Order`, `Payment`) |
| `aggregate_id` | UUID | ID of the entity that raised the event |
| `payload` | JSONB / TEXT | Serialised event data |
| `created_at` | TIMESTAMP | When the event was created |
| `published_at` | TIMESTAMP NULL | When successfully published; NULL = unpublished |
| `attempts` | INT | Number of publish attempts (for retry tracking) |
| `error` | TEXT NULL | Last error message (for debugging) |

**Component 2 — The Outbox Relay (Message Relay):**
A background process (or scheduled job) that continuously polls the outbox table for unpublished messages, publishes them to the message broker, and marks them as published. The relay is the only writer to the message broker — it decouples the business operation from the broker publish latency.

```
Business Operation:
  Service → [DB Transaction] → orders table + outbox table (atomic) → COMMIT

Relay (background process):
  Relay → [SELECT unpublished FROM outbox] → Publish to broker → [UPDATE outbox SET published_at = NOW()]
```

**Q4. What delivery guarantee does the Outbox Pattern provide — at-least-once or exactly-once?**
A: The Outbox Pattern provides **at-least-once delivery** — not exactly-once. The relay may publish a message more than once in specific failure scenarios:

```
Failure scenario — message published but relay crashes before marking as published:
T=0: Relay reads message M from outbox
T=1: Relay publishes M to Kafka ✓
T=2: Relay crashes before executing UPDATE outbox SET published_at = NOW()
T=3: Relay restarts — M is still marked unpublished in the outbox
T=4: Relay publishes M to Kafka again ✗ (duplicate)
```

This is unavoidable without exactly-once semantics at the broker level (Kafka transactions with idempotent producers, or exactly-once deduplication in the consumer). The correct complementary pattern is **idempotent consumers**: each downstream consumer must handle duplicate messages gracefully — typically by tracking the message's `id` in a `processed_messages` table and skipping messages whose ID has already been processed.

```ts
// Idempotent consumer — handles duplicate messages safely
async function handleOrderPlaced(message: KafkaMessage): Promise<void> {
  const event   = JSON.parse(message.value!.toString()) as OrderPlacedEvent;
  const eventId = event.id; // the outbox row's UUID

  await db.transaction(async (tx) => {
    // Check if already processed
    const alreadyProcessed = await tx.processedMessages.findUnique({
      where: { id: eventId },
    });
    if (alreadyProcessed) {
      logger.info("Duplicate message — skipping", { eventId });
      return; // idempotent — safe to skip
    }

    // Process the event
    await tx.inventory.reserve(event.items);
    await tx.notifications.enqueue(event.customerId, "order-confirmed");

    // Mark as processed — within the same transaction
    await tx.processedMessages.create({
      data: { id: eventId, processedAt: new Date() },
    });
  });
}
```

**Q5. What is the difference between the Outbox Pattern and Change Data Capture (CDC)?**
A: Both solve the dual-write problem, but they differ in *how* they detect and relay changes:

| Aspect | Outbox Pattern (polling relay) | Change Data Capture (CDC) |
|---|---|---|
| **Detection mechanism** | Application writes to outbox table; relay polls it | Database transaction log (WAL / binlog) is tailed |
| **Application awareness** | Application explicitly writes to outbox | Application writes only business data; CDC detects changes |
| **Coupling** | Application coupled to outbox schema | Application decoupled — only DB logs monitored |
| **Latency** | Polling interval (100ms–5s typical) | Near real-time (sub-second) |
| **Database support** | Any ACID database | Postgres (logical replication), MySQL (binlog), MongoDB (oplog) |
| **Infrastructure** | Simple — just a table + background job | Requires Debezium, Kafka Connect, or similar CDC tool |
| **Ordering guarantee** | Depends on relay implementation | Guaranteed by WAL order |
| **Failure recovery** | Relay restarts and re-reads unpublished rows | CDC resumes from last confirmed log offset |
| **Best for** | Simple setups, teams without CDC infrastructure | Large-scale systems, many services, low latency requirements |

```
Outbox polling:
  Application → [TX] → orders + outbox → Relay polls → Kafka

CDC / Debezium:
  Application → [TX] → orders → Postgres WAL → Debezium connector → Kafka
  (outbox table optional — CDC can watch the orders table directly)
```

## Section 2: Implementing the Outbox Pattern

**Q6. Show a complete implementation of the Outbox Pattern using Prisma and Node.js.**
A:
```ts
// Prisma schema — outbox table alongside business tables
// schema.prisma
/*
model Order {
  id          String       @id @default(uuid())
  customerId  String
  status      String       @default("PENDING")
  total       Decimal
  createdAt   DateTime     @default(now())
  updatedAt   DateTime     @updatedAt
}

model OutboxMessage {
  id            String    @id @default(uuid())
  eventType     String
  aggregateType String
  aggregateId   String
  payload       String    // JSON string
  createdAt     DateTime  @default(now())
  publishedAt   DateTime?
  attempts      Int       @default(0)
  lastError     String?

  @@index([publishedAt, createdAt]) // index for relay query performance
}
*/

// Domain event types
interface OrderPlacedEvent {
  id:          string;
  type:        "order.placed";
  aggregateId: string;
  occurredAt:  string;
  data: {
    orderId:    string;
    customerId: string;
    total:      number;
    items:      OrderItem[];
  };
}

// Service — writes order + outbox message in one transaction
class OrderService {
  constructor(
    private readonly prisma:  PrismaClient,
    private readonly logger:  Logger
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<{ orderId: string }> {
    const result = await this.prisma.$transaction(async (tx) => {
      // Business write
      const order = await tx.order.create({
        data: {
          customerId: dto.customerId,
          status:     "CONFIRMED",
          total:      dto.items.reduce((sum, i) => sum + i.price * i.qty, 0),
        },
      });

      // Outbox write — same transaction, guaranteed atomic with business write
      const event: OrderPlacedEvent = {
        id:          crypto.randomUUID(),  // stable event ID for idempotency
        type:        "order.placed",
        aggregateId: order.id,
        occurredAt:  new Date().toISOString(),
        data: {
          orderId:    order.id,
          customerId: dto.customerId,
          total:      Number(order.total),
          items:      dto.items,
        },
      };

      await tx.outboxMessage.create({
        data: {
          id:            event.id,
          eventType:     event.type,
          aggregateType: "Order",
          aggregateId:   order.id,
          payload:       JSON.stringify(event),
        },
      });

      return order;
    });

    this.logger.info("Order placed — outbox message enqueued", { orderId: result.id });
    return { orderId: result.id };
  }

  async cancelOrder(orderId: string, reason: string): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      const order = await tx.order.update({
        where: { id: orderId },
        data:  { status: "CANCELLED" },
      });

      await tx.outboxMessage.create({
        data: {
          id:            crypto.randomUUID(),
          eventType:     "order.cancelled",
          aggregateType: "Order",
          aggregateId:   orderId,
          payload:       JSON.stringify({
            id:          crypto.randomUUID(),
            type:        "order.cancelled",
            aggregateId: orderId,
            occurredAt:  new Date().toISOString(),
            data:        { orderId, reason, customerId: order.customerId },
          }),
        },
      });
    });
  }
}
```

**Q7. How do you implement the Outbox Relay — the background process that reads unpublished messages and publishes them?**
A:
```ts
import { Kafka, Producer, KafkaMessage } from "kafkajs";

interface OutboxRelayConfig {
  pollIntervalMs:    number;  // how often to check for unpublished messages
  batchSize:         number;  // messages per poll cycle
  maxAttempts:       number;  // max publish attempts before marking as dead-letter
  lockTimeoutMs:     number;  // prevent concurrent relays from processing same message
}

class OutboxRelay {
  private producer:   Producer;
  private running     = false;
  private pollTimer:  NodeJS.Timeout | null = null;

  constructor(
    private readonly prisma:  PrismaClient,
    private readonly kafka:   Kafka,
    private readonly config:  OutboxRelayConfig,
    private readonly logger:  Logger,
    private readonly metrics: MetricsClient
  ) {
    this.producer = this.kafka.producer({
      idempotent:            true,   // Kafka idempotent producer — prevents broker duplicates
      maxInFlightRequests:   1,
      transactionalId:       `outbox-relay-${process.env.INSTANCE_ID ?? "default"}`,
    });
  }

  async start(): Promise<void> {
    await this.producer.connect();
    this.running = true;
    this.logger.info("Outbox relay started");
    this.scheduleNextPoll();
  }

  async stop(): Promise<void> {
    this.running = false;
    if (this.pollTimer) clearTimeout(this.pollTimer);
    await this.producer.disconnect();
    this.logger.info("Outbox relay stopped");
  }

  private scheduleNextPoll(): void {
    if (!this.running) return;
    this.pollTimer = setTimeout(async () => {
      await this.poll().catch(err =>
        this.logger.error("Outbox relay poll error", { err })
      );
      this.scheduleNextPoll(); // schedule next poll after current one completes
    }, this.config.pollIntervalMs);
  }

  private async poll(): Promise<void> {
    const pollStart = Date.now();

    // Fetch a batch of unpublished messages — ordered by createdAt for ordering guarantee
    const messages = await this.prisma.outboxMessage.findMany({
      where: {
        publishedAt: null,                                    // not yet published
        attempts:    { lt: this.config.maxAttempts },        // not exceeded max retries
        // Claim messages not recently attempted — prevents relay stampede on retries
        OR: [
          { lockedAt: null },
          { lockedAt: { lt: new Date(Date.now() - this.config.lockTimeoutMs) } },
        ],
      },
      orderBy: { createdAt: "asc" },                        // preserve creation order
      take:    this.config.batchSize,
    });

    if (messages.length === 0) return; // nothing to do

    this.logger.debug("Outbox relay processing batch", { count: messages.length });
    this.metrics.gauge("outbox.pending_messages", messages.length);

    // Claim the batch — set lockedAt to prevent concurrent relays
    await this.prisma.outboxMessage.updateMany({
      where: { id: { in: messages.map(m => m.id) } },
      data:  { lockedAt: new Date(), attempts: { increment: 1 } },
    });

    // Publish each message
    let published = 0; let failed = 0;
    for (const message of messages) {
      try {
        await this.publishMessage(message);
        published++;
      } catch (err) {
        failed++;
        this.logger.error("Failed to publish outbox message", {
          messageId: message.id,
          eventType: message.eventType,
          attempts:  message.attempts + 1,
          err,
        });
        await this.prisma.outboxMessage.update({
          where: { id: message.id },
          data:  {
            lastError: (err as Error).message,
            lockedAt:  null, // release lock so it can be retried
          },
        });
      }
    }

    this.metrics.increment("outbox.published", published);
    this.metrics.increment("outbox.failed",    failed);
    this.metrics.histogram("outbox.poll_duration_ms", Date.now() - pollStart);
  }

  private async publishMessage(message: OutboxMessage): Promise<void> {
    const topic = this.topicFor(message.eventType);

    // Use Kafka transactions for exactly-once semantics at the broker level
    await this.producer.sendBatch({
      topicMessages: [{
        topic,
        messages: [{
          key:   message.aggregateId,  // partition by aggregate ID — ordering per entity
          value: message.payload,
          headers: {
            "event-id":        message.id,
            "event-type":      message.eventType,
            "aggregate-type":  message.aggregateType,
            "aggregate-id":    message.aggregateId,
            "created-at":      message.createdAt.toISOString(),
          },
        }],
      }],
    });

    // Mark as published — only after broker confirms receipt
    await this.prisma.outboxMessage.update({
      where: { id: message.id },
      data:  { publishedAt: new Date(), lockedAt: null, lastError: null },
    });

    this.logger.debug("Outbox message published", {
      messageId: message.id,
      eventType: message.eventType,
      topic,
    });
  }

  private topicFor(eventType: string): string {
    // Map event types to Kafka topics
    const topicMap: Record<string, string> = {
      "order.placed":      "orders",
      "order.cancelled":   "orders",
      "order.shipped":     "orders",
      "payment.completed": "payments",
      "payment.failed":    "payments",
    };
    return topicMap[eventType] ?? eventType.replace(".", "-");
  }
}

// Bootstrap — start relay alongside the main service
const relay = new OutboxRelay(prisma, kafka, {
  pollIntervalMs: 500,   // poll every 500ms — balance between latency and DB load
  batchSize:      100,   // process up to 100 messages per poll
  maxAttempts:    5,     // give up after 5 failed attempts
  lockTimeoutMs:  30_000, // release lock after 30s if relay crashes mid-processing
}, logger, metrics);

await relay.start();

// Graceful shutdown
process.on("SIGTERM", async () => {
  await relay.stop();
  process.exit(0);
});
```

**Q8. How do you implement the Outbox Pattern using PostgreSQL's `LISTEN/NOTIFY` instead of polling — reducing latency to near-real-time?**
A: `LISTEN/NOTIFY` eliminates the polling interval — the database notifies the relay immediately when a new outbox row is inserted:

```ts
import { Pool, Client } from "pg";

class PostgresNotifyOutboxRelay {
  private listenClient: Client | null = null;
  private processing   = false;

  constructor(
    private pool:     Pool,
    private producer: Producer,
    private logger:   Logger
  ) {}

  async start(): Promise<void> {
    // Dedicated client for LISTEN — cannot be from a pool (pools reuse connections)
    this.listenClient = new Client({ connectionString: process.env.DATABASE_URL });
    await this.listenClient.connect();

    // Listen for notifications on the outbox channel
    await this.listenClient.query("LISTEN outbox_new_message");

    this.listenClient.on("notification", async (msg) => {
      if (msg.channel === "outbox_new_message" && !this.processing) {
        this.processing = true;
        await this.processOutbox().finally(() => { this.processing = false; });
      }
    });

    this.listenClient.on("error", (err) => {
      this.logger.error("LISTEN client error — reconnecting", { err });
      this.reconnect();
    });

    // Initial drain — process any messages that arrived before relay started
    await this.processOutbox();
    this.logger.info("Outbox relay started with LISTEN/NOTIFY");
  }

  private async processOutbox(): Promise<void> {
    const client = await this.pool.connect();
    try {
      const { rows } = await client.query<OutboxRow>(`
        SELECT * FROM outbox_messages
        WHERE  published_at IS NULL
          AND  attempts < 5
        ORDER  BY created_at ASC
        LIMIT  100
        FOR    UPDATE SKIP LOCKED  -- skip rows being processed by another relay instance
      `);

      for (const row of rows) {
        await this.publishRow(client, row);
      }
    } finally {
      client.release();
    }
  }

  private async publishRow(client: PoolClient, row: OutboxRow): Promise<void> {
    await this.producer.send({
      topic:    this.topicFor(row.event_type),
      messages: [{
        key:     row.aggregate_id,
        value:   row.payload,
        headers: { "event-id": row.id },
      }],
    });

    await client.query(
      "UPDATE outbox_messages SET published_at = NOW() WHERE id = $1",
      [row.id]
    );
  }

  private async reconnect(): Promise<void> {
    await this.listenClient?.end().catch(() => {});
    await new Promise(r => setTimeout(r, 2000));
    await this.start();
  }
}

// Database trigger — fires NOTIFY on every outbox insert
// Run this migration once:
/*
CREATE OR REPLACE FUNCTION notify_outbox_insert()
RETURNS TRIGGER AS $$
BEGIN
  PERFORM pg_notify('outbox_new_message', NEW.id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER outbox_insert_trigger
AFTER INSERT ON outbox_messages
FOR EACH ROW EXECUTE FUNCTION notify_outbox_insert();
*/
```

**Q9. How do you implement the Outbox Pattern with TypeORM?**
A:
```ts
import { DataSource, EntityManager } from "typeorm";
import { Entity, Column, PrimaryGeneratedColumn, CreateDateColumn, Index } from "typeorm";

// TypeORM entity for outbox table
@Entity("outbox_messages")
@Index(["publishedAt", "createdAt"])
export class OutboxMessage {
  @PrimaryGeneratedColumn("uuid")
  id: string;

  @Column({ name: "event_type" })
  eventType: string;

  @Column({ name: "aggregate_type" })
  aggregateType: string;

  @Column({ name: "aggregate_id" })
  aggregateId: string;

  @Column({ type: "text" })
  payload: string;

  @CreateDateColumn({ name: "created_at" })
  createdAt: Date;

  @Column({ name: "published_at", type: "timestamp", nullable: true })
  publishedAt: Date | null;

  @Column({ default: 0 })
  attempts: number;

  @Column({ name: "last_error", type: "text", nullable: true })
  lastError: string | null;
}

// Service — uses TypeORM transaction manager
class OrderService {
  constructor(private dataSource: DataSource) {}

  async placeOrder(dto: PlaceOrderDto): Promise<{ orderId: string }> {
    return this.dataSource.transaction(async (manager: EntityManager) => {
      // Business write using the transactional manager
      const order = manager.create(Order, {
        customerId: dto.customerId,
        status:     "CONFIRMED",
        total:      dto.items.reduce((sum, i) => sum + i.price * i.qty, 0),
      });
      await manager.save(Order, order);

      // Outbox write — same transactional manager = same transaction
      const outbox = manager.create(OutboxMessage, {
        id:            crypto.randomUUID(),
        eventType:     "order.placed",
        aggregateType: "Order",
        aggregateId:   order.id,
        payload:       JSON.stringify({
          id:          crypto.randomUUID(),
          type:        "order.placed",
          aggregateId: order.id,
          occurredAt:  new Date().toISOString(),
          data:        { orderId: order.id, customerId: dto.customerId, items: dto.items },
        }),
      });
      await manager.save(OutboxMessage, outbox);

      return { orderId: order.id };
    });
  }
}
```

## Section 3: Change Data Capture (CDC) as an Alternative

**Q10. How does Debezium implement the Outbox Pattern via CDC, and what are the trade-offs?**
A: Debezium is a CDC platform that reads the Postgres Write-Ahead Log (WAL) or MySQL binary log and streams row-level changes to Kafka. When combined with the Outbox Pattern, it eliminates the relay process entirely — Debezium becomes the relay:

```
Traditional Outbox:
  Service → [TX] → orders + outbox table → Relay polls outbox → Kafka

Debezium Outbox CDC:
  Service → [TX] → orders + outbox table → Debezium tails Postgres WAL → Kafka
                                            (no relay process needed)
```

```yaml
# Debezium connector configuration — Kafka Connect plugin
{
  "name": "order-service-outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.user": "debezium",
    "database.password": "debezium",
    "database.dbname": "orderdb",
    "database.server.name": "orderdb",

    # Outbox Event Router — Debezium SMT that routes outbox rows to correct topics
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.table.field.event.id": "id",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.type": "event_type",
    "transforms.outbox.table.field.event.payload": "payload",
    "transforms.outbox.table.field.event.payload.id": "aggregate_id",
    "transforms.outbox.route.by.field": "aggregate_type",
    "transforms.outbox.route.topic.replacement": "outbox.order.${routedByValue}",

    # Only watch the outbox table — not the entire database
    "table.include.list": "public.outbox_messages",

    # Mark rows as processed (tombstone delete) after routing
    "tombstones.on.delete": "false",
  }
}
```

```ts
// With Debezium — service code is simpler, no relay to maintain
// The outbox write is identical — Debezium handles the rest
class OrderService {
  async placeOrder(dto: PlaceOrderDto): Promise<{ orderId: string }> {
    return this.prisma.$transaction(async (tx) => {
      const order = await tx.order.create({ data: { ...dto } });

      // Still write to outbox — Debezium reads it from WAL
      await tx.outboxMessage.create({
        data: {
          id:            crypto.randomUUID(),
          eventType:     "order.placed",
          aggregateType: "Order",
          aggregateId:   order.id,
          payload:       JSON.stringify({ orderId: order.id, ...dto }),
        },
      });

      return { orderId: order.id };
    });
    // No relay needed — Debezium picks up the WAL change and routes to Kafka
  }
}
```

**CDC trade-offs in practice:**

| Concern | Polling Relay | Debezium CDC |
|---|---|---|
| **Operational complexity** | Low — just a Node.js process | High — Kafka Connect + Debezium cluster |
| **Latency** | Polling interval (100ms–5s) | Sub-second (WAL is near-real-time) |
| **Infrastructure cost** | Minimal | Kafka Connect workers |
| **Schema coupling** | Application controls outbox schema | Debezium reads raw WAL — schema changes need connector update |
| **Database support** | Any ACID DB | Postgres, MySQL, MongoDB, SQL Server |
| **Failure recovery** | Relay restarts, re-reads unpublished | Kafka Connect stores offset — resumes from last position |
| **Message ordering** | Application-controlled | WAL order — guaranteed per-partition |

## Section 4: Outbox Relay Operational Concerns

**Q11. How do you prevent multiple relay instances from processing the same outbox message — the concurrent relay problem?**
A: Running multiple relay instances for high availability without deduplication causes duplicate publishes. Two approaches handle this correctly:

**Approach 1 — `SELECT FOR UPDATE SKIP LOCKED` (preferred for SQL):**
```ts
// PostgreSQL — SKIP LOCKED ensures each relay claims a distinct set of messages
async function fetchAndLockBatch(tx: PrismaTransaction): Promise<OutboxMessage[]> {
  // Raw query needed for SKIP LOCKED — Prisma doesn't support it natively in v5
  return tx.$queryRaw<OutboxMessage[]>`
    SELECT * FROM outbox_messages
    WHERE  published_at IS NULL
      AND  attempts < 5
    ORDER  BY created_at ASC
    LIMIT  100
    FOR    UPDATE SKIP LOCKED
  `;
}
// Each relay instance claims different rows — zero overlap ✓
// If relay A claims rows 1-100 and crashes, lock is released on transaction end
// Relay B picks them up on next poll ✓
```

**Q12. How do you handle outbox messages that repeatedly fail to publish — dead-letter handling?**

```ts
class OutboxRelayWithDeadLetter {
  async processMessage(message: OutboxMessage): Promise<void> {
    if (message.attempts >= this.config.maxAttempts) {
      await this.sendToDeadLetter(message);
      return;
    }

    try {
      await this.publishToKafka(message);
      await this.markPublished(message.id);
    } catch (err) {
      await this.recordFailure(message.id, err as Error);
      // Next poll will retry — with exponential backoff based on attempts
    }
  }

  private async sendToDeadLetter(message: OutboxMessage): Promise<void> {
    await this.prisma.$transaction(async (tx) => {
      // Move to dead-letter table for manual review
      await tx.$executeRaw`
        INSERT INTO outbox_dead_letters
        SELECT *, NOW() as dead_lettered_at, 'max_attempts_exceeded' as reason
        FROM   outbox_messages
        WHERE  id = ${message.id}
      `;

      await tx.$executeRaw`
        DELETE FROM outbox_messages WHERE id = ${message.id}
      `;
    });

    this.logger.error("Outbox message dead-lettered", {
      messageId: message.id,
      eventType: message.eventType,
      attempts:  message.attempts,
    });

    // Alert on-call
    this.alerting.trigger("outbox_dead_letter", {
      messageId: message.id,
      eventType: message.eventType,
      lastError: message.lastError,
    });

    this.metrics.increment("outbox.dead_lettered", { eventType: message.eventType });
  }

  // Exponential backoff — prevent relay from hammering a struggling broker
  private nextRetryAt(attempts: number): Date {
    const delayMs = Math.min(1000 * Math.pow(2, attempts), 60_000); // max 60s
    return new Date(Date.now() + delayMs);
  }

  private async recordFailure(messageId: string, err: Error): Promise<void> {
    const message = await this.prisma.outboxMessage.findUnique({ where: { id: messageId } });
    if (!message) return;

    await this.prisma.outboxMessage.update({
      where: { id: messageId },
      data: {
        lastError:    err.message,
        lockedAt:     null,                                // release lock
        nextRetryAt:  this.nextRetryAt(message.attempts), // backoff
      },
    });
  }
}
```

**Q17. "You're reviewing a PR where a developer implemented the Outbox Pattern but the relay uses a global `SELECT *` without `FOR UPDATE SKIP LOCKED`. You're deploying two instances of this relay for HA. What is the problem and how do you fix it?"**
A: Without `FOR UPDATE SKIP LOCKED`, both relay instances can read and attempt to publish the same outbox rows simultaneously — producing duplicate messages in the broker:

```ts
// ✗ — Vulnerable relay: two instances race to publish the same messages
async function poll() {
  const messages = await prisma.outboxMessage.findMany({
    where:   { publishedAt: null },
    orderBy: { createdAt: "asc" },
    take:    100,
  });
  // Relay A reads: [msg-1, msg-2, msg-3]
  // Relay B reads: [msg-1, msg-2, msg-3]  ← same rows!
  for (const msg of messages) {
    await publishToKafka(msg);          // Relay A publishes msg-1
    await markPublished(msg.id);        // Relay A marks msg-1 published
    // Relay B also publishes msg-1 — DUPLICATE ✗
  }
}

// ✓ — Fix: FOR UPDATE SKIP LOCKED + atomic claim
async function poll() {
  await prisma.$transaction(async (tx) => {
    // Claim rows exclusively — other relay instances skip these rows
    const messages = await tx.$queryRaw<OutboxMessage[]>`
      SELECT * FROM outbox_messages
      WHERE  published_at IS NULL
        AND  attempts < 5
      ORDER  BY created_at ASC
      LIMIT  100
      FOR    UPDATE SKIP LOCKED
    `;

    if (messages.length === 0) return;

    // Mark as in-progress atomically within the same transaction as the lock
    await tx.$executeRaw`
      UPDATE outbox_messages
      SET    locked_at = NOW(), attempts = attempts + 1
      WHERE  id = ANY(${messages.map(m => m.id)})
    `;

    return messages;
  });
  // Lock is released when transaction ends — rows are now claimed by this relay
  // Publish outside the transaction — lock held only during claim, not during publish

  for (const msg of claimedMessages) {
    try {
      await publishToKafka(msg);
      await markPublished(msg.id);
    } catch (err) {
      await releaseLock(msg.id); // allow other relay or next poll to retry
    }
  }
}
```

**Q18. "A microservice is experiencing high database load during peak hours. The team wants to reduce outbox polling frequency but is worried about increased event latency. How do you design a system that has near-real-time event latency without constant polling?"**
A: Combine `LISTEN/NOTIFY` (for low-latency wakeup) with a fallback poll (for reliability):

```ts
class HybridOutboxRelay {
  private listenClient: Client | null = null;
  private pollTimer:    NodeJS.Timeout | null = null;

  // LISTEN/NOTIFY for low-latency wakeup (typically < 50ms end-to-end)
  // Fallback polling every 30s for messages missed due to LISTEN failures
  constructor(
    private pool:           Pool,
    private producer:       Producer,
    private config: {
      fallbackPollIntervalMs: number; // 30_000 — safety net polling
      batchSize:              number;
    }
  ) {}

  async start(): Promise<void> {
    await this.startListening();
    this.startFallbackPolling();
    await this.processOutbox(); // drain existing messages on startup
  }

  private async startListening(): Promise<void> {
    this.listenClient = new Client({ connectionString: process.env.DATABASE_URL });
    await this.listenClient.connect();
    await this.listenClient.query("LISTEN outbox_new_message");

    this.listenClient.on("notification", async () => {
      // Triggered immediately on INSERT — near-real-time
      await this.processOutbox().catch(err =>
        logger.error("NOTIFY-triggered processing failed", { err })
      );
    });

    this.listenClient.on("error", async (err) => {
      logger.error("LISTEN connection lost — relying on fallback poll", { err });
      await this.listenClient?.end().catch(() => {});
      // Reconnect after delay
      setTimeout(() => this.startListening(), 5_000);
    });
  }

  private startFallbackPolling(): void {
    // Low-frequency safety net — catches messages missed if LISTEN was down
    this.pollTimer = setInterval(async () => {
      await this.processOutbox().catch(err =>
        logger.warn("Fallback poll failed", { err })
      );
    }, this.config.fallbackPollIntervalMs);
  }

  private processing = false;

  private async processOutbox(): Promise<void> {
    if (this.processing) return; // prevent concurrent processing
    this.processing = true;
    try {
      // Process with SKIP LOCKED — safe for concurrent relay instances
      const client = await this.pool.connect();
      try {
        const { rows } = await client.query<OutboxMessage>(`
          SELECT * FROM outbox_messages
          WHERE  published_at IS NULL AND attempts < 5
          ORDER  BY created_at ASC LIMIT ${this.config.batchSize}
          FOR    UPDATE SKIP LOCKED
        `);
        for (const row of rows) {
          await this.publishRow(client, row);
        }
      } finally {
        client.release();
      }
    } finally {
      this.processing = false;
    }
  }
}

// Database trigger fires on every outbox INSERT — zero polling overhead
/*
CREATE OR REPLACE FUNCTION notify_outbox()
RETURNS TRIGGER AS $$
BEGIN
  PERFORM pg_notify('outbox_new_message', NEW.id::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER outbox_notify_trigger
AFTER INSERT ON outbox_messages
FOR EACH ROW EXECUTE FUNCTION notify_outbox();
*/
// Result:
// - LISTEN: event latency < 100ms during normal operation
// - Fallback poll: safety net every 30s if LISTEN connection drops
// - DB load: near-zero during normal operation (no polling)
// - Reliability: matches pure polling (fallback catches anything LISTEN misses)
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Fire-and-forget publish | Two-phase commit (XA) | Outbox Pattern (polling) | Outbox + CDC (Debezium) |
|---|---|---|---|---|
| **Atomicity with DB write** | No ✗ | Yes | Yes ✓ | Yes ✓ |
| **Message delivery guarantee** | At-most-once | Exactly-once | At-least-once | At-least-once |
| **Duplicate risk** | Low (but messages can be lost) | None | Yes (relay crash) | Yes (connector restart) |
| **Event latency** | Milliseconds | Milliseconds | Polling interval (100ms–5s) | Sub-second |
| **Operational complexity** | Low | Very high (coordinator) | Medium (relay process) | High (Kafka Connect) |
| **Failure modes** | Lost messages | Coordinator failure, slow | Relay down (delay), DB load | Connector failure, WAL lag |
| **Database requirement** | Any | XA-capable | Any ACID | Postgres WAL / MySQL binlog |
| **Infrastructure** | None | Distributed tx coordinator | Background process | Debezium + Kafka Connect |
| **Best for** | Non-critical events | Rarely practical | Most microservice use cases | Large scale, low latency |

## Outbox Pattern Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **Outbox outside the transaction** | Outbox row created after `tx.commit()` — back to dual-write problem | Outbox write must be inside the same transaction as business write |
| **No idempotent consumer** | Downstream service processes duplicate messages — at-least-once without idempotency = data corruption | Track processed message IDs in a `processed_messages` table |
| **Global relay without SKIP LOCKED** | Multiple relay instances publish same message concurrently | Use `FOR UPDATE SKIP LOCKED` or leader election |
| **Unbounded outbox table** | Outbox table grows forever — published rows never cleaned | Purge published rows older than N days via a scheduled job |
| **Payload too large** | Embedding full entity in outbox payload — large blobs degrade DB performance | Store event reference (IDs) not full data; consumer fetches current state |
| **No dead-letter handling** | Permanently failing messages block the relay queue | Dead-letter after N attempts; alert; provide manual replay |
| **Liveness check on broker** | Relay marks unhealthy if broker is down — cascades into service restart | Relay should degrade (stop publishing) not crash; service liveness independent of relay |
| **Polling too aggressively** | Poll every 10ms — DB connection pool exhausted | Use LISTEN/NOTIFY for wakeup; fall back to 5–30s polling |
| **No monitoring** | Outbox builds up silently — events delayed for hours without anyone noticing | Alert on oldest_pending_age_ms > threshold; alert on dead_letter_count > 0 |
| **Synchronous relay in request path** | Waiting for relay to publish before returning response — defeats the purpose | Relay is always asynchronous; return response after DB commit, not after publish |

---

**Tip for the interview:** At the 5 YOE level, "what is the Outbox Pattern" surfaces as: how do you guarantee that an event is published to Kafka when an order is placed without losing the event if the broker is temporarily down, how do you prevent two relay instances from publishing the same message twice, why does the downstream service keep receiving duplicate order events and what is the correct fix, or how do you design a system where a new service can subscribe to all past order events without the order service knowing about it. The sharp answer immediately names the dual-write problem as the root cause, shows the two-failure-mode code examples, explains why a DB transaction cannot span a message broker, describes the outbox table as the atomic intermediary, explains that delivery is at-least-once (not exactly-once) and therefore consumers must be idempotent, and covers `FOR UPDATE SKIP LOCKED` for the concurrent relay problem. Distinguishing the polling relay from Debezium CDC — "both solve the same problem; Debezium reads the WAL directly so it's faster and needs no relay process, but requires Kafka Connect infrastructure; the polling relay is simpler to operate and works on any ACID database" — is the architectural depth that lands at 5 YOE.
