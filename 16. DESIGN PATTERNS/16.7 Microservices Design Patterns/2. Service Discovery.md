# JavaScript / TypeScript (Microservices Design Patterns): Service Discovery — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Service Discovery?**
A: Service Discovery is the mechanism by which services in a distributed system **locate each other at runtime** without hardcoding network addresses. In a microservices architecture, service instances are ephemeral — they start, scale, crash, and restart continuously, each time potentially getting a new IP address and port. Service Discovery solves the fundamental question: *given that I need to call the order service right now, where is it?*

The pattern has two components working together:
- **Service Registry** — a database of currently available service instances and their network locations (host, port, health status, metadata). Acts as a phone book for the cluster.
- **Discovery Mechanism** — the process by which a client finds a service instance from the registry, either by querying it directly (client-side) or by routing through an intermediary that queries it (server-side).

Without Service Discovery, microservices communicate via hardcoded IP addresses or DNS names pointing to static infrastructure — an approach that breaks the moment instances scale horizontally, deploy to new hosts, or move across cloud availability zones.

**Q2. Why is Service Discovery necessary in microservices, and why doesn't traditional DNS solve the problem?**
A: Traditional DNS was designed for long-lived, infrequently changing infrastructure. Microservices invalidate all of its assumptions:

**DNS limitations in microservices:**
- **TTL propagation delay** — DNS records have a Time-To-Live, typically 30–300 seconds. A crashed instance's address stays in DNS caches long after the instance is gone. During this window, clients route traffic to a dead endpoint.
- **No health awareness** — DNS returns all registered addresses regardless of health status. A returning poisoned address is indistinguishable from a healthy one.
- **No load balancing metadata** — DNS cannot express weights, circuit breaker state, or geographic affinity.
- **Port inflexibility** — DNS resolves hostnames, not ports. Multiple services on the same host (common in containerised deployments) require additional coordination.
- **JVM/OS caching** — many runtimes aggressively cache DNS results beyond the TTL, causing stale resolution for minutes or hours.

```
// Traditional DNS — static, unaware of instance health
ORDER_SERVICE_URL = "https://order-service.internal:3000"
// If this instance crashes, DNS still returns the same IP for up to TTL seconds
// If two instances exist, DNS round-robins — but dead instances stay in rotation ✗

// Service Discovery — dynamic, health-aware
const instance = await serviceRegistry.discover("order-service");
// Returns: { host: "10.0.1.42", port: 3001, healthy: true, version: "2.3.1" }
// Only healthy, currently-registered instances are returned ✓
// Instance list updates within seconds of a crash or scale event ✓
```

**Q3. What are the two primary patterns of Service Discovery — Client-Side and Server-Side — and what are their trade-offs?**
A:

**Client-Side Discovery:**
The client queries the service registry directly, retrieves a list of available instances, and applies its own load-balancing logic to choose one. The client is responsible for the full discovery and selection pipeline.

```
Client → [query] → Service Registry → [returns instance list]
Client → [chooses instance using LB algorithm]
Client → [calls directly] → Chosen Service Instance
```

**Server-Side Discovery (Gateway/Load Balancer Discovery):**
The client makes a request to a stable router (load balancer, API gateway, or service mesh sidecar). The router queries the service registry and forwards the request to an appropriate instance. The client knows only the router's address.

```
Client → [calls stable address] → Load Balancer / API Gateway
                                         ↓ [queries]
                                    Service Registry
                                         ↓ [returns instance]
                                    Load Balancer → Service Instance
```

| Aspect | Client-Side | Server-Side |
|---|---|---|
| **Who queries registry** | The client directly | The load balancer / gateway |
| **Client complexity** | High — client has discovery logic | Low — client knows only the gateway |
| **Network hops** | 1 (direct to service) | 2 (client → gateway → service) |
| **Language coupling** | Client needs a registry SDK | Language-agnostic — gateway handles it |
| **Load balancing** | Client-controlled — flexible | Router-controlled — centralised |
| **Failure domain** | Client fails independently | Gateway is a single point of failure (mitigated by HA) |
| **Typical implementations** | Netflix Eureka + Ribbon, Consul + client library | AWS ALB, Nginx + Consul Template, Kubernetes Service, Istio |

**Q4. What is the Self-Registration vs Third-Party Registration distinction?**
A: Services must register themselves in the registry — but who initiates and manages that registration?

**Self-Registration:**
The service instance itself calls the registry API on startup to register its location, and calls the deregister API on graceful shutdown. It also sends periodic heartbeats to maintain its registration.

```ts
// Service registers itself on startup
class ServiceRegistrar {
  constructor(
    private readonly registry: ServiceRegistryClient,
    private readonly config:   ServiceConfig
  ) {}

  async register(): Promise<void> {
    await this.registry.register({
      serviceId:   `${this.config.name}-${this.config.instanceId}`,
      serviceName: this.config.name,
      host:        this.config.host,
      port:        this.config.port,
      tags:        ["api", `version:${this.config.version}`],
      healthCheck: {
        http:     `http://${this.config.host}:${this.config.port}/health`,
        interval: "10s",
        timeout:  "5s",
      },
    });

    // Heartbeat — keeps registration alive
    this.heartbeatInterval = setInterval(async () => {
      await this.registry.heartbeat(this.config.instanceId)
        .catch(err => logger.error("Heartbeat failed", { err }));
    }, 5_000);
  }

  async deregister(): Promise<void> {
    clearInterval(this.heartbeatInterval);
    await this.registry.deregister(this.config.instanceId);
  }
}
```

**Third-Party Registration:**
An external system (the deployment platform, an orchestrator, or a dedicated registrar service) registers instances on their behalf. The service itself has no registry awareness — the orchestrator (Kubernetes, ECS, Nomad) knows when a pod starts or dies and updates the registry accordingly.

| Aspect | Self-Registration | Third-Party Registration |
|---|---|---|
| **Service awareness** | Service must import registry SDK | Service is unaware of registry |
| **Coupling** | Service coupled to registry technology | Service decoupled — platform concern |
| **Graceful shutdown** | Service can deregister cleanly | Platform detects death via health checks |
| **Implementation** | Developer responsibility | Ops / platform responsibility |
| **Failure handling** | Service must handle heartbeat failures | Platform handles all registration lifecycle |
| **Typical environment** | VMs, bare metal, non-containerised | Kubernetes, ECS, Docker Swarm |

**Q5. What is a Service Registry, and what are the most widely used implementations?**
A: A Service Registry is a highly available, strongly consistent (or eventually consistent) database that stores the current network location and health status of every service instance in the cluster. It must be:
- **Highly available** — if the registry goes down, services cannot discover each other. It must run in a cluster with consensus-based replication.
- **Health-aware** — it actively monitors instances (or receives heartbeats) and removes unhealthy ones from its advertised list automatically.
- **Fast** — discovery happens on every service call; registry reads must be low-latency.
- **Watchable** — clients and routers must be notified of changes in real time (or near real time) rather than polling constantly.

**Major implementations:**

| Registry | Consistency model | Native support | Health check | Notable feature |
|---|---|---|---|---|
| **Consul** (HashiCorp) | Raft consensus (strong) | DNS + HTTP API | TCP, HTTP, gRPC, script | KV store, service mesh, multi-datacenter |
| **Etcd** (CNCF) | Raft consensus (strong) | HTTP/gRPC API | Lease-based TTL | Kubernetes backing store; watches |
| **Zookeeper** (Apache) | ZAB consensus (strong) | Custom API | Session heartbeat | Mature; used by Kafka, Hadoop |
| **Eureka** (Netflix) | Eventual (AP) | HTTP REST API | Client heartbeat | Self-preserving mode; AWS-native |
| **Kubernetes Services** | Etcd-backed (strong) | DNS + kube-proxy | Readiness probes | Built-in to K8s; no extra infra |
| **AWS Cloud Map** | AWS-managed | Route 53 + API | Route 53 health checks | Native AWS integration |

## Section 2: Client-Side Discovery in Node.js

**Q6. How do you implement client-side discovery in a Node.js service using Consul?**
A:
```ts
import Consul from "consul";

// Service instance shape returned by registry
interface ServiceInstance {
  id:       string;
  name:     string;
  host:     string;
  port:     number;
  tags:     string[];
  healthy:  boolean;
  metadata: Record<string, string>;
}

// Load balancing strategies
type LoadBalancingStrategy = "round-robin" | "random" | "least-connections";

// Client-side service discovery with Consul
class ConsulServiceDiscovery {
  private consul:      Consul.Consul;
  private cache:       Map<string, ServiceInstance[]> = new Map();
  private roundRobinIdx = new Map<string, number>();
  private watchers:    Map<string, Consul.Watch> = new Map();

  constructor(
    private readonly consulHost: string = "127.0.0.1",
    private readonly consulPort: number = 8500,
    private readonly cacheTtlMs: number = 5_000
  ) {
    this.consul = new Consul({ host: consulHost, port: String(consulPort) });
  }

  // Discover a healthy instance of a named service
  async discover(
    serviceName: string,
    strategy:   LoadBalancingStrategy = "round-robin"
  ): Promise<ServiceInstance> {
    const instances = await this.getHealthyInstances(serviceName);

    if (instances.length === 0) {
      throw new ServiceDiscoveryError(`No healthy instances of "${serviceName}" found`);
    }

    return this.selectInstance(serviceName, instances, strategy);
  }

  // Discover all healthy instances (for fan-out, broadcasting)
  async discoverAll(serviceName: string): Promise<ServiceInstance[]> {
    return this.getHealthyInstances(serviceName);
  }

  private async getHealthyInstances(serviceName: string): Promise<ServiceInstance[]> {
    // Return cached instances if fresh
    const cached = this.cache.get(serviceName);
    if (cached) return cached;

    // Query Consul for healthy instances
    const result = await this.consul.health.service({
      service: serviceName,
      passing: true,  // only return instances passing all health checks
    });

    const instances: ServiceInstance[] = result[0].map((entry: any) => ({
      id:      entry.Service.ID,
      name:    entry.Service.Service,
      host:    entry.Service.Address || entry.Node.Address,
      port:    entry.Service.Port,
      tags:    entry.Service.Tags ?? [],
      healthy: true,
      metadata: entry.Service.Meta ?? {},
    }));

    // Cache the result with TTL
    this.cache.set(serviceName, instances);
    setTimeout(() => this.cache.delete(serviceName), this.cacheTtlMs);

    return instances;
  }

  private selectInstance(
    serviceName: string,
    instances:   ServiceInstance[],
    strategy:    LoadBalancingStrategy
  ): ServiceInstance {
    switch (strategy) {
      case "random":
        return instances[Math.floor(Math.random() * instances.length)];

      case "round-robin": {
        const idx  = (this.roundRobinIdx.get(serviceName) ?? 0) % instances.length;
        this.roundRobinIdx.set(serviceName, idx + 1);
        return instances[idx];
      }

      case "least-connections":
        // Would require tracking active connections per instance — simplified here
        return instances[0];

      default:
        return instances[0];
    }
  }

  // Watch for changes — updates cache in real time instead of polling
  watchService(serviceName: string): void {
    if (this.watchers.has(serviceName)) return; // already watching

    const watcher = this.consul.watch({
      method: this.consul.health.service,
      options: { service: serviceName, passing: true },
    });

    watcher.on("change", (data: any[]) => {
      const instances: ServiceInstance[] = data.map((entry: any) => ({
        id:      entry.Service.ID,
        name:    entry.Service.Service,
        host:    entry.Service.Address || entry.Node.Address,
        port:    entry.Service.Port,
        tags:    entry.Service.Tags ?? [],
        healthy: true,
        metadata: entry.Service.Meta ?? {},
      }));
      this.cache.set(serviceName, instances);
      logger.info(`Service registry updated for "${serviceName}"`, { count: instances.length });
    });

    watcher.on("error", (err: Error) => {
      logger.error(`Service watcher error for "${serviceName}"`, { err });
    });

    this.watchers.set(serviceName, watcher);
  }

  stopWatching(serviceName: string): void {
    this.watchers.get(serviceName)?.end();
    this.watchers.delete(serviceName);
  }

  destroy(): void {
    this.watchers.forEach(w => w.end());
    this.watchers.clear();
    this.cache.clear();
  }
}

// HTTP client that uses service discovery for every call
class ServiceClient {
  constructor(
    private readonly discovery: ConsulServiceDiscovery,
    private readonly http:      typeof fetch = fetch
  ) {}

  async call<T>(
    serviceName: string,
    path:        string,
    options?:    RequestInit
  ): Promise<T> {
    const instance = await this.discovery.discover(serviceName);
    const url      = `http://${instance.host}:${instance.port}${path}`;

    const response = await this.http(url, {
      ...options,
      signal: AbortSignal.timeout(10_000),
    });

    if (!response.ok) throw new HttpError(response.status, await response.text());
    return response.json() as T;
  }
}

// Usage — service name instead of hard-coded URL
const discovery    = new ConsulServiceDiscovery();
const orderClient  = new ServiceClient(discovery);

// Start watching commonly-used services for real-time updates
discovery.watchService("order-service");
discovery.watchService("inventory-service");

const order = await orderClient.call<Order>("order-service", `/orders/${orderId}`);
```

**Q7. How do you implement service registration and heartbeating in a Node.js service?**
A:
```ts
import Consul from "consul";
import os     from "os";

interface RegistrationConfig {
  name:       string;
  port:       number;
  version:    string;
  tags?:      string[];
  metadata?:  Record<string, string>;
  healthPath: string;
}

class ConsulServiceRegistrar {
  private consul:            Consul.Consul;
  private instanceId:        string;
  private heartbeatTimer:    NodeJS.Timeout | null = null;
  private registered         = false;

  constructor(
    private readonly config:    RegistrationConfig,
    consulHost:  string = process.env.CONSUL_HOST ?? "127.0.0.1",
    consulPort:  number = Number(process.env.CONSUL_PORT ?? 8500)
  ) {
    this.consul     = new Consul({ host: consulHost, port: String(consulPort) });
    this.instanceId = `${config.name}-${os.hostname()}-${config.port}`;
  }

  async register(): Promise<void> {
    const host = this.resolveHost();

    await this.consul.agent.service.register({
      id:   this.instanceId,
      name: this.config.name,
      address: host,
      port: this.config.port,
      tags: [
        ...(this.config.tags ?? []),
        `version:${this.config.version}`,
      ],
      meta: {
        version:  this.config.version,
        hostname: os.hostname(),
        ...(this.config.metadata ?? {}),
      },
      check: {
        http:                           `http://${host}:${this.config.port}${this.config.healthPath}`,
        interval:                       "10s",
        timeout:                        "5s",
        deregisterCriticalServiceAfter: "30s", // auto-deregister if critical for 30s
      },
    });

    this.registered = true;
    logger.info("Service registered with Consul", {
      instanceId: this.instanceId,
      host,
      port: this.config.port,
    });

    // Graceful shutdown hooks
    this.registerShutdownHandlers();
  }

  async deregister(): Promise<void> {
    if (!this.registered) return;
    await this.consul.agent.service.deregister(this.instanceId);
    this.registered = false;
    logger.info("Service deregistered from Consul", { instanceId: this.instanceId });
  }

  private resolveHost(): string {
    // In containers: use the container's advertised IP, not localhost
    // Prefer POD_IP (Kubernetes) or HOST_IP (Docker) env vars
    return (
      process.env.POD_IP   ||
      process.env.HOST_IP  ||
      this.getLocalIp()    ||
      "127.0.0.1"
    );
  }

  private getLocalIp(): string | undefined {
    const nets = os.networkInterfaces();
    for (const interfaces of Object.values(nets)) {
      for (const iface of (interfaces ?? [])) {
        if (iface.family === "IPv4" && !iface.internal) {
          return iface.address;
        }
      }
    }
  }

  private registerShutdownHandlers(): void {
    const shutdown = async (signal: string) => {
      logger.info(`Received ${signal} — deregistering from Consul`);
      await this.deregister();
      process.exit(0);
    };

    process.once("SIGTERM", () => shutdown("SIGTERM"));
    process.once("SIGINT",  () => shutdown("SIGINT"));
  }
}

// Bootstrap — register on startup, deregister on shutdown
async function bootstrap(): Promise<void> {
  const registrar = new ConsulServiceRegistrar({
    name:       "order-service",
    port:       3000,
    version:    process.env.APP_VERSION ?? "1.0.0",
    tags:       ["api", "orders"],
    healthPath: "/health/live",
  });

  await registrar.register();

  const app = buildExpressApp();
  app.listen(3000, () => logger.info("Order service started on port 3000"));
}
```

## Section 3: Server-Side Discovery — Kubernetes

**Q8. How does Kubernetes implement Service Discovery, and how does it differ from explicit registry patterns like Consul?**
A: Kubernetes implements service discovery as a **first-class platform primitive** via its `Service` object and built-in DNS — developers rarely interact with the registry directly:

**How Kubernetes Service Discovery works:**
1. A `Service` object is created with a selector matching pods by label.
2. Kubernetes creates a stable virtual IP (ClusterIP) and DNS name for the Service.
3. `kube-proxy` on each node maintains iptables/IPVS rules that route traffic from the ClusterIP to healthy pod IPs.
4. The DNS name `<service-name>.<namespace>.svc.cluster.local` resolves to the ClusterIP.
5. `Endpoints` (or `EndpointSlices`) objects are automatically updated as pods start, stop, or fail readiness probes.

```yaml
# Kubernetes Service — the registry entry, created declaratively
apiVersion: v1
kind: Service
metadata:
  name: order-service          # DNS name: order-service.default.svc.cluster.local
  namespace: default
spec:
  selector:
    app: order-service         # selects pods with this label
    tier: backend
  ports:
    - protocol: TCP
      port: 80                 # service port (stable)
      targetPort: 3000         # container port (may vary)
  type: ClusterIP              # internal only; use LoadBalancer for external

---
# The pods that get selected
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3                  # 3 instances — all registered automatically
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
        tier: backend
    spec:
      containers:
        - name: order-service
          image: order-service:2.3.1
          ports:
            - containerPort: 3000
          readinessProbe:       # only healthy pods receive traffic
            httpGet:
              path: /health/ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
```

```ts
// Node.js service — uses Kubernetes DNS, zero discovery SDK needed
const ORDER_SERVICE_URL = process.env.ORDER_SERVICE_URL
  ?? "http://order-service.default.svc.cluster.local";

// kube-proxy handles load balancing across all healthy pods transparently
const response = await fetch(`${ORDER_SERVICE_URL}/orders/${orderId}`);
```

**Kubernetes vs explicit registry (Consul):**

| Aspect | Kubernetes Services | Consul |
|---|---|---|
| **Developer experience** | Zero — DNS name, no SDK | Requires registry SDK or template |
| **Scope** | Kubernetes cluster only | Multi-cluster, multi-cloud, hybrid |
| **Health checks** | Readiness/liveness probes | HTTP, TCP, gRPC, script |
| **Service mesh** | Needs Istio/Linkerd for advanced features | Built-in service mesh |
| **Non-K8s services** | Cannot register VMs or external services | Can register anything |
| **KV store** | Not included | Built-in — config distribution |
| **Multi-datacenter** | Via federation (complex) | Native, first-class |

**Q9. How do you perform service discovery across multiple Kubernetes namespaces or clusters?**
A:
```ts
// Cross-namespace discovery — use fully qualified DNS name
// Services in the same namespace: http://order-service
// Services in a different namespace: http://order-service.payments.svc.cluster.local

const PAYMENT_SERVICE_URL = "http://payment-service.payments.svc.cluster.local";
const ORDER_SERVICE_URL   = "http://order-service.orders.svc.cluster.local";

// Cross-cluster discovery — requires a service mesh (Istio) or external registry (Consul)
// Istio multi-cluster: services addressable via ServiceEntry
// Consul federation: services registered across clusters, discoverable by name
```

```yaml
# Istio ServiceEntry — registers an external or cross-cluster service
apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: external-payment-service
spec:
  hosts:
    - payment-service.external.example.com
  ports:
    - number: 443
      name: https
      protocol: HTTPS
  resolution: DNS
  location: MESH_EXTERNAL

---
# ExternalName Service — maps to an external DNS name
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: orders
spec:
  type: ExternalName
  externalName: payment-service.payments.svc.cluster.local
  # Allows orders namespace to call "payment-service" without knowing the namespace
```

## Section 4: Service Meshes

**Q10. What is a service mesh, and how does it relate to service discovery?**
A: A service mesh is an infrastructure layer that handles all service-to-service communication transparently — service discovery, load balancing, retries, circuit breaking, mTLS, observability — **without any service code changes**. It achieves this by injecting a sidecar proxy (Envoy, in the case of Istio and Linkerd2) alongside every service instance. All inbound and outbound traffic passes through the sidecar.

```
Without service mesh:
Service A code → [discovery SDK] → Registry → [picks instance] → Service B

With service mesh:
Service A code → Envoy sidecar → [discovers via control plane] → Envoy sidecar → Service B code
                 (transparent to Service A and Service B — neither knows the other's address)
```

**Service mesh components:**
- **Data plane** — the sidecar proxies (Envoy). Handle actual traffic. Implement service discovery, load balancing, retries, circuit breaking, mTLS.
- **Control plane** — the management layer (Istiod, Linkerd control plane). Distributes service registry data, policies, and certificates to all sidecars via xDS protocol.

```yaml
# Istio — service discovery is automatic after enabling injection
apiVersion: v1
kind: Namespace
metadata:
  name: orders
  labels:
    istio-injection: enabled  # all pods in this namespace get Envoy sidecar injected

---
# No discovery SDK in the service code — Envoy handles everything
# Traffic routing, retry, circuit breaking, mTLS, metrics — all in the sidecar
```

```ts
// Service code with service mesh — identical to without mesh
// No registry SDK, no discovery code, no circuit breaker code
const response = await fetch("http://payment-service/charge", {
  method: "POST",
  body:   JSON.stringify({ amount, token }),
});
// Envoy sidecar intercepts this call, discovers the payment-service pod IPs from Istiod,
// applies mTLS, load balancing, retries, and circuit breaking transparently
```

**Q11. How does Istio implement service discovery, and what is the xDS protocol?**
A: Istio's control plane (Istiod) maintains a service registry by watching the Kubernetes API server for Service, Endpoint, and ServiceEntry objects. It distributes this registry to all Envoy sidecars via the **xDS (extensible Discovery Service) protocol** — a gRPC streaming API that pushes updates to sidecars in real time:

```
Kubernetes API Server
        ↓ watches
    Istiod (control plane)
        ↓ distributes via xDS gRPC streaming
    Envoy sidecar (data plane) — on every pod

xDS APIs:
- LDS (Listener Discovery Service)   — what ports to listen on
- RDS (Route Discovery Service)      — how to route requests
- CDS (Cluster Discovery Service)    — what upstream clusters exist (= service instances)
- EDS (Endpoint Discovery Service)   — which IPs/ports are in each cluster (= instances)
- SDS (Secret Discovery Service)     — TLS certificates
```

When a new pod starts, Istiod receives the endpoint update from Kubernetes and immediately pushes an EDS update to all Envoy sidecars — service discovery propagation is sub-second in a healthy cluster.

```yaml
# Istio VirtualService — advanced traffic routing built on service discovery
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: order-service
spec:
  hosts:
    - order-service
  http:
    # Canary: 90% to v1, 10% to v2 — Envoy uses EDS to find instances of each version
    - route:
        - destination:
            host:   order-service
            subset: v1
          weight: 90
        - destination:
            host:   order-service
            subset: v2
          weight: 10
      retries:
        attempts:       3
        perTryTimeout:  5s
      timeout: 10s
```

## Section 5: Health Checks and Failure Handling

**Q12. What health check endpoints should a Node.js service expose for service discovery to work correctly?**
A: A service needs at minimum two distinct health endpoints — conflating them causes incorrect behaviour in service discovery:

```ts
import express from "express";

const app = express();

// Liveness probe — "Is the process alive and not deadlocked?"
// Kubernetes: if this fails, the pod is RESTARTED
// Rule: only return 503 if the process is in a state it cannot recover from
// NEVER include dependency checks (DB, external services) here — if DB is down,
// don't restart the pod (it won't help); just stop serving traffic via readiness
app.get("/health/live", (req, res) => {
  // Check: is the event loop responsive? (if this responds, the process is alive)
  // Optional: check for obvious process-level issues (memory threshold exceeded)
  const memUsageMb = process.memoryUsage().heapUsed / 1024 / 1024;
  if (memUsageMb > 512) {
    return res.status(503).json({ status: "unhealthy", reason: "Memory threshold exceeded" });
  }
  res.status(200).json({ status: "alive", uptime: process.uptime() });
});

// Readiness probe — "Is the service ready to receive traffic?"
// Kubernetes: if this fails, the pod is REMOVED FROM SERVICE (not restarted)
//             Load balancer stops sending requests; service stays running
// Consul: if health check fails, instance removed from healthy pool
// Rule: include dependency checks — if DB is down, don't accept new requests
app.get("/health/ready", async (req, res) => {
  const checks: Record<string, { healthy: boolean; latencyMs?: number; error?: string }> = {};

  // Database connectivity
  const dbStart = Date.now();
  try {
    await db.query("SELECT 1");
    checks.database = { healthy: true, latencyMs: Date.now() - dbStart };
  } catch (err) {
    checks.database = { healthy: false, error: (err as Error).message };
  }

  // Redis connectivity
  const redisStart = Date.now();
  try {
    await redis.ping();
    checks.redis = { healthy: true, latencyMs: Date.now() - redisStart };
  } catch (err) {
    checks.redis = { healthy: false, error: (err as Error).message };
  }

  const healthy = Object.values(checks).every(c => c.healthy);

    timestamp:  new Date().toISOString(),
  });
});
```

**Q13. How do you implement graceful shutdown to ensure clean deregistration from the service registry?**
A: Graceful shutdown is the critical link between the service lifecycle and service discovery — without it, deregistered or in-flight requests get dropped:

```ts
class GracefulShutdown {
  private isShuttingDown = false;
  private activeRequests  = 0;

  constructor(
    private readonly server:     http.Server,
    private readonly registrar:  ConsulServiceRegistrar,
    private readonly db:         DatabaseClient,
    private readonly shutdownTimeoutMs = 30_000
  ) {}

  async shutdown(signal: string): Promise<void> {
    if (this.isShuttingDown) return; // prevent duplicate shutdown
    this.isShuttingDown = true;

    logger.info(`Received ${signal} — starting graceful shutdown`);

    // Step 1 — deregister from service registry IMMEDIATELY
    // New requests stop being routed to this instance right away
    await this.registrar.deregister()
      .catch(err => logger.error("Deregistration failed", { err }));

    logger.info("Deregistered from service registry — no new requests will be routed here");

    // Step 2 — stop accepting new HTTP connections
    this.server.close(() => logger.info("HTTP server closed — no new connections accepted"));

    // Step 3 — wait for in-flight requests to complete (with timeout)
    const shutdownStart = Date.now();
    while (this.activeRequests > 0) {
      if (Date.now() - shutdownStart > this.shutdownTimeoutMs) {
        logger.warn(`Shutdown timeout — ${this.activeRequests} requests still in flight, forcing exit`);
        break;
      }
      await new Promise(r => setTimeout(r, 100));
    }

    // Step 4 — close infrastructure connections
    await Promise.allSettled([
      this.db.disconnect(),
      redis.quit(),
      messageQueue.close(),
    ]);

    logger.info("Graceful shutdown complete");
    process.exit(0);
  }

  // Middleware — tracks active requests for graceful shutdown
  trackRequests(): express.RequestHandler {
    return (req, res, next) => {
      if (this.isShuttingDown) {
        res.setHeader("Connection", "close");
        res.status(503).json({ error: "Service is shutting down" });
        return;
      }

      this.activeRequests++;
      res.on("finish", () => { this.activeRequests--; });
      res.on("close",  () => { this.activeRequests--; });
      next();
    };
  }

  register(): void {
    process.on("SIGTERM", () => this.shutdown("SIGTERM"));
    process.on("SIGINT",  () => this.shutdown("SIGINT"));
    process.on("uncaughtException", async (err) => {
      logger.error("Uncaught exception — initiating emergency shutdown", { err });
      await this.shutdown("uncaughtException");
    });
  }
}

// Bootstrap
const shutdown = new GracefulShutdown(server, registrar, db);
app.use(shutdown.trackRequests());
shutdown.register();
```

## Section 6: Advanced Patterns

**Q14. How do you implement client-side caching and cache invalidation for discovered service instances?**
A: Querying the registry on every service call is too slow — but a stale cache routes to dead instances. The solution is a **short TTL cache with real-time watch invalidation**:

```ts
class CachedServiceDiscovery implements ServiceDiscovery {
  private cache = new Map<string, {
    instances:  ServiceInstance[];
    fetchedAt:  number;
    watching:   boolean;
  }>();

  private readonly CACHE_TTL_MS     = 5_000;   // 5s default TTL
  private readonly STALE_WHILE_REVALIDATE = 30_000; // serve stale for up to 30s while refreshing

  constructor(
    private readonly registry: ServiceRegistry,
    private readonly logger:   Logger
  ) {}

  async discover(serviceName: string): Promise<ServiceInstance> {
    const instances = await this.getInstances(serviceName);
    if (instances.length === 0) {
      throw new ServiceDiscoveryError(`No healthy instances: "${serviceName}"`);
    }
    return this.roundRobin(serviceName, instances);
  }

  private async getInstances(serviceName: string): Promise<ServiceInstance[]> {
    const cached = this.cache.get(serviceName);
    const now    = Date.now();

    if (cached) {
      const age = now - cached.fetchedAt;

      if (age < this.CACHE_TTL_MS) {
        return cached.instances; // fresh — serve directly
      }

      if (age < this.STALE_WHILE_REVALIDATE) {
        // Stale but within SWR window — serve stale, refresh in background
        this.refreshInBackground(serviceName);
        return cached.instances;
      }
      // Too stale — must refresh synchronously
    }

    return this.refresh(serviceName);
  }

  private async refresh(serviceName: string): Promise<ServiceInstance[]> {
    const instances = await this.registry.getHealthyInstances(serviceName);
    this.cache.set(serviceName, { instances, fetchedAt: Date.now(), watching: false });
    this.startWatching(serviceName); // begin watching for real-time updates
    return instances;
  }

  private refreshInBackground(serviceName: string): void {
    this.refresh(serviceName).catch(err =>
      this.logger.warn("Background refresh failed", { serviceName, err })
    );
  }

  private startWatching(serviceName: string): void {
    const cached = this.cache.get(serviceName);
    if (cached?.watching) return;

    this.registry.watch(serviceName, (instances) => {
      const existing = this.cache.get(serviceName);
      this.cache.set(serviceName, {
        instances,
        fetchedAt: Date.now(),
        watching:  existing?.watching ?? true,
      });
      this.logger.info(`Discovery cache updated for "${serviceName}"`, { count: instances.length });
    });

    if (cached) cached.watching = true;
  }

  // Called after a failed request — evict specific instance from cache
  reportFailure(serviceName: string, instance: ServiceInstance): void {
    const cached = this.cache.get(serviceName);
    if (!cached) return;

    cached.instances = cached.instances.filter(i => i.id !== instance.id);
    this.logger.warn("Instance removed from local discovery cache after failure", {
      serviceName, instanceId: instance.id
    });

    // Refresh in background to restore the instance if it recovers
    this.refreshInBackground(serviceName);
  }
}
```

**Q15. How do you implement weighted load balancing and affinity routing in client-side discovery?**
A:
```ts
// Weighted load balancing — route more traffic to instances with higher capacity
function selectWeighted(instances: ServiceInstance[]): ServiceInstance {
  const weights = instances.map(i => Number(i.metadata.weight ?? "1"));
  const total   = weights.reduce((a, b) => a + b, 0);
  let   random  = Math.random() * total;

  for (let i = 0; i < instances.length; i++) {
    random -= weights[i];
    if (random <= 0) return instances[i];
  }
  return instances[instances.length - 1];
}

// Zone/region affinity — prefer instances in the same availability zone
function selectWithZoneAffinity(
  instances: ServiceInstance[],
  currentZone: string
): ServiceInstance {
  const sameZone = instances.filter(i => i.metadata.zone === currentZone);

  if (sameZone.length > 0) {
    // Prefer same zone — reduces cross-AZ data transfer costs and latency
    return sameZone[Math.floor(Math.random() * sameZone.length)];
  }

  // Fall back to any zone if no same-zone instances exist
  return instances[Math.floor(Math.random() * instances.length)];
}

// Version-aware routing — route to specific version for canary / A/B testing
function selectByVersion(
  instances: ServiceInstance[],
  targetVersion?: string
): ServiceInstance {
  if (!targetVersion) {
    return instances[Math.floor(Math.random() * instances.length)];
  }

  const matching = instances.filter(i =>
    i.tags.includes(`version:${targetVersion}`)
  );

  return matching.length > 0
    ? matching[Math.floor(Math.random() * matching.length)]
    : instances[Math.floor(Math.random() * instances.length)]; // fallback
}

// Combined smart load balancer
class SmartLoadBalancer {
  private connectionCounts = new Map<string, number>();

  select(
    instances:  ServiceInstance[],
    options:    { strategy: string; zone?: string; version?: string }
  ): ServiceInstance {
    switch (options.strategy) {
      case "weighted":
        return selectWeighted(instances);

      case "zone-affinity":
        return selectWithZoneAffinity(instances, options.zone ?? "default");

      case "version":
        return selectByVersion(instances, options.version);

      case "least-connections":
        return instances.reduce((min, inst) => {
          const minConn  = this.connectionCounts.get(min.id)  ?? 0;
          const instConn = this.connectionCounts.get(inst.id) ?? 0;
          return instConn < minConn ? inst : min;
        });

      default:
        return instances[Math.floor(Math.random() * instances.length)];
    }
  }

  trackRequest(instanceId: string): () => void {
    this.connectionCounts.set(instanceId,
      (this.connectionCounts.get(instanceId) ?? 0) + 1
    );
    return () => {
      this.connectionCounts.set(instanceId,
        Math.max(0, (this.connectionCounts.get(instanceId) ?? 1) - 1)
      );
    };
  }
}
```

**Q16. How does Service Discovery integrate with the Circuit Breaker pattern?**
A: Service Discovery and Circuit Breaker integrate at the instance level — each discovered instance gets its own circuit breaker, allowing fine-grained failure isolation:

```ts
// Per-instance circuit breakers — don't open the breaker for the whole service
// when only one instance is failing
class ResilientServiceDiscovery {
  private discovery:  CachedServiceDiscovery;
  private breakers:   Map<string, CircuitBreaker> = new Map();

  constructor(registry: ServiceRegistry) {
    this.discovery = new CachedServiceDiscovery(registry);
  }

  private getBreakerFor(instance: ServiceInstance): CircuitBreaker {
    const key = `${instance.host}:${instance.port}`;
    if (!this.breakers.has(key)) {
      this.breakers.set(key, new CircuitBreaker(`instance-${key}`, {
        failureThreshold: 3,
        timeout:          30_000,
        halfOpenMaxCalls: 1,
      }));
    }
    return this.breakers.get(key)!;
  }

  async call<T>(serviceName: string, path: string): Promise<T> {
    const instances = await this.discovery.discoverAll(serviceName);

    // Filter out instances with open circuit breakers — don't even try them
    const availableInstances = instances.filter(inst => {
      const stats = this.getBreakerFor(inst).getStats();
      return stats.state !== "OPEN";
    });

    if (availableInstances.length === 0) {
      throw new ServiceDiscoveryError(`All instances of "${serviceName}" have open circuit breakers`);
    }

    // Try available instances with their individual circuit breakers
    for (const instance of availableInstances) {
      const breaker = this.getBreakerFor(instance);
      try {
        return await breaker.execute(async () => {
          const url      = `http://${instance.host}:${instance.port}${path}`;
          const response = await fetch(url, { signal: AbortSignal.timeout(5_000) });
          if (!response.ok) throw new HttpError(response.status);
          return response.json() as T;
        });
      } catch (err) {
        if (err instanceof CircuitBreakerOpenError) continue; // try next instance
        // For other errors, circuit breaker handles counting — try next instance
        logger.warn("Instance call failed — trying next", {
          instance: `${instance.host}:${instance.port}`, err
        });
        this.discovery.reportFailure(serviceName, instance); // evict from local cache
      }
    }

    throw new ServiceUnavailableError(`All instances of "${serviceName}" failed`);
  }
}
```

**Q18. "An incident report shows that during a deployment, 10% of requests to a service received 503 errors for about 30 seconds. The deployment was a rolling update. What caused this, and how do you fix it with service discovery?"**
A: This is the **classic rolling update race condition** between service discovery propagation delay and pod termination:

**Root cause:**
```
T=0:  Rolling update starts — pod A marked for termination
T=1:  Kubernetes sends SIGTERM to pod A
T=2:  Pod A stops responding to readiness probe → K8s removes from Endpoints
T=3:  Endpoint update propagates to kube-proxy (iptables rules update) — ~2-5 seconds
T=4:  During T=2 to T=3, kube-proxy still routes traffic to pod A's IP
T=5:  Pod A has already exited (SIGTERM default handler = immediate exit in Node.js)
      → 503 errors for requests routed to pod A during T=2–T=4
```

**Fix — multiple layers:**

```ts
// Fix 1 — Graceful shutdown: handle SIGTERM with a drain period
process.on("SIGTERM", async () => {
  logger.info("SIGTERM received — starting graceful shutdown");

  // Step 1: stop accepting new requests (but DON'T exit yet)
  // This makes readiness probe fail → K8s removes from Endpoints
  appState.isShuttingDown = true;

  // Step 2: wait for kube-proxy propagation (~5 seconds before pod stops receiving traffic)
  // This is the "pre-stop sleep" — gives the LB time to drain
  const DRAIN_WAIT_MS = 10_000;
  logger.info(`Waiting ${DRAIN_WAIT_MS}ms for load balancer drain`);
  await new Promise(r => setTimeout(r, DRAIN_WAIT_MS));

  // Step 3: finish in-flight requests
  await drainActiveRequests(30_000);

  // Step 4: close connections and exit
  await closeConnections();
  process.exit(0);
});
```

```yaml
# Fix 2 — Kubernetes lifecycle hook: pre-stop sleep in pod spec
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60  # give enough time for drain
      containers:
        - name: order-service
          lifecycle:
            preStop:
              exec:
                # Sleep before SIGTERM — gives kube-proxy time to drain connections
                command: ["/bin/sh", "-c", "sleep 10"]
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 3000
            # These settings control how quickly a pod is removed from the LB
            periodSeconds:    5
            failureThreshold: 1  # remove from LB after first readiness failure
```

**Q19. "A service is experiencing high latency calling a downstream service. You suspect service discovery is part of the problem — the client is querying the registry on every request. How do you diagnose and fix this?"**
A:
```ts
// Diagnosis — add instrumentation to measure discovery latency
class InstrumentedServiceDiscovery implements ServiceDiscovery {
  constructor(
    private inner:   ServiceDiscovery,
    private metrics: MetricsClient
  ) {}

  async discover(serviceName: string): Promise<ServiceInstance> {
    const start = Date.now();
    const source = this.inner.isCached(serviceName) ? "cache" : "registry";

    try {
      const instance = await this.inner.discover(serviceName);
      this.metrics.histogram("service_discovery.latency_ms", Date.now() - start, {
        service: serviceName, source,
      });
      return instance;
    } catch (err) {
      this.metrics.increment("service_discovery.error", { service: serviceName });
      throw err;
    }
  }
}

// Likely findings:
// - discovery.latency_ms{source="registry"} p99 = 50ms  (registry query = slow)
// - discovery.latency_ms{source="cache"}    p99 = 0.1ms (cache hit = fast)
// - cache hit rate = 10% (cache is expiring too quickly or not being populated)

// Fix — enable request-level caching and background watch
class FixedServiceDiscovery {
  private cache = new Map<string, ServiceInstance[]>();
  private lastFetchAt = new Map<string, number>();
  private readonly TTL = 30_000; // 30 seconds — long enough to avoid per-request queries

  async discover(serviceName: string): Promise<ServiceInstance> {
    const now    = Date.now();
    const cached = this.cache.get(serviceName);
    const age    = now - (this.lastFetchAt.get(serviceName) ?? 0);

    // Serve from cache if less than TTL old
    if (cached && age < this.TTL) {
      return this.pickInstance(cached);
    }

    // Refresh synchronously if no cache, or async if stale
    if (!cached) {
      return this.refreshAndPick(serviceName);
    }

    // Stale — serve from cache, refresh in background
    this.refreshAsync(serviceName);
    return this.pickInstance(cached);
  }

  private async refreshAndPick(name: string): Promise<ServiceInstance> {
    const instances = await this.registry.getHealthyInstances(name);
    this.cache.set(name, instances);
    this.lastFetchAt.set(name, Date.now());
    return this.pickInstance(instances);
  }

  private refreshAsync(name: string): void {
    this.refreshAndPick(name).catch(err =>
      logger.warn("Async refresh failed", { name, err })
    );
  }

  private pickInstance(instances: ServiceInstance[]): ServiceInstance {
    return instances[Math.floor(Math.random() * instances.length)];
  }
}
```

## Service Discovery Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **Hardcoded IPs** | Service URLs hard-coded in config — breaks on scale/redeploy | Use service registry or K8s DNS |
| **Registry on every call** | Querying Consul/Eureka on every outbound request — 50ms+ overhead per call | Cache with TTL + watch-based invalidation |
| **Missing health check** | Service registered but not health-checked — dead instances stay in pool | Always configure health checks; test them |
| **Liveness checks dependencies** | DB down → liveness probe fails → pod restarts in a loop | Only readiness should check dependencies |
| **No graceful shutdown** | Pod exits immediately on SIGTERM — in-flight requests dropped | Pre-stop sleep + drain in-flight requests |
| **Global circuit breaker** | One breaker per service — one bad instance opens breaker for all traffic | Per-instance circuit breakers in client-side discovery |
| **Single registry** | Non-HA registry — single point of failure for entire cluster | Run registry in HA mode (3+ nodes, Raft consensus) |
| **No deregistration on crash** | Service crashes without deregistering — stale entry in registry for TTL period | `deregisterCriticalServiceAfter` in Consul; readiness probe in K8s |
| **DNS caching too aggressive** | JVM/OS caches DNS beyond TTL — routes to dead instances | Set `networkaddress.cache.ttl=5` in JVM; use service registry SDK |
| **Sync registry queries in hot path** | Discovery blocking the request thread | Background refresh with stale-while-revalidate |

**Tip for the interview:** At the 5 YOE level, "what is Service Discovery" never arrives as a definition question — it surfaces as: how does service A find service B's address when B can have 20 instances and scales up and down continuously, why did you get 503 errors during a rolling deployment and how do you fix it (graceful shutdown + pre-stop sleep + readiness probe coordination), how do you integrate Kubernetes services with legacy VMs in a unified discovery system (Consul with catalog sync), or how do you prevent service discovery from adding 50ms of latency to every request (cache with watch-based invalidation, stale-while-revalidate). The sharp answer immediately names the two components (service registry + discovery mechanism), contrasts client-side vs server-side with concrete trade-offs (network hops, language coupling, load balancing control), explains Kubernetes Services as an invisible third-party registration implementation, addresses the rolling deployment 503 problem with the pre-stop sleep pattern, and integrates circuit breakers at the per-instance level — "if one pod is failing, open that pod's circuit breaker, not the entire service's." Knowing that the liveness probe should never check external dependencies — "if the database is down, restarting the pod won't help; stop routing traffic to it via readiness, but keep the pod alive" — is the operational depth that lands at 5 YOE.
