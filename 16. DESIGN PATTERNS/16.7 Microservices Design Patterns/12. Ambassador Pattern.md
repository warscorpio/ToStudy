# JavaScript / TypeScript (Microservices Design Patterns): Ambassador Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Ambassador pattern?**
A: The Ambassador pattern is a structural microservices design pattern that places a **helper service or process alongside a client service** to handle all outbound network communication on the client's behalf. The ambassador acts as an out-of-process proxy that intercepts and enriches every outbound request from the client — adding cross-cutting concerns like retry logic, circuit breaking, authentication, observability, TLS termination, and service discovery — without the client service itself knowing about or implementing any of these concerns.

The name comes from the diplomatic role: an ambassador acts as a representative that handles the complexity of foreign-country communication so the home government (the client service) can focus on policy (business logic) rather than protocol. The client service talks to its ambassador as if it were talking directly to the downstream service; the ambassador handles everything else.

The pattern is distinct from other proxy patterns in its **co-location** — the ambassador runs as a sidecar container in the same pod (Kubernetes) or on the same host as the client service, communicating over localhost. This co-location ensures ultra-low latency between the client and its ambassador (sub-millisecond), making the interception transparent from the client's perspective.

**Q2. What problem does the Ambassador pattern solve — and why can't it be solved by a library inside the service?**
A: The core problem is **cross-cutting network concerns duplicated across every service in a polyglot microservices ecosystem**. Without the Ambassador pattern:

```
Without Ambassador — every service re-implements the same concerns:
  OrderService (Node.js):
    - Manually implements retry with exponential backoff
    - Manually implements circuit breaker (opossum)
    - Manually adds distributed tracing headers
    - Manually handles mTLS certificate rotation
    - Manually implements service discovery

  InventoryService (Python):
    - Reimplements retry (tenacity library)
    - Reimplements circuit breaker (pybreaker)
    - Different distributed tracing header format
    - Manual mTLS handling
    - Different service discovery SDK

  PaymentService (Java):
    - Reimplements retry (Resilience4j)
    - Reimplements circuit breaker (Hystrix)
    - Yet another tracing implementation
    - Manual mTLS
    - Yet another service discovery client

  → 3 services × 5 concerns = 15 independent implementations
  → When the retry policy changes, 3 codebases must be updated
  → Policy enforcement is inconsistent — Python service has different retry behaviour
  → Each service upgrade requires coordinated releases across multiple teams
```

**Why a shared library doesn't fully solve it:**
- **Language barrier** — a Node.js library cannot be used by the Java or Python service.
- **Library upgrade coupling** — updating the retry policy requires redeploying every service that uses the library, in a coordinated release.
- **Version drift** — services naturally end up on different library versions, producing inconsistent behaviour.
- **Invasive instrumentation** — the library is tightly coupled to the service's code; changing the library's API requires code changes in the service.

The Ambassador pattern solves this by extracting all these concerns into a dedicated sidecar process that is deployed and upgraded independently of the service:

```
With Ambassador — concerns centralised in the sidecar:
  OrderService (Node.js)  → Ambassador sidecar → downstream services
  InventoryService (Python) → Ambassador sidecar → downstream services
  PaymentService (Java)   → Ambassador sidecar → downstream services

  All three services get:
  ✓ Identical retry policy (configured in ambassador, not in service code)
  ✓ Identical circuit breaker behaviour
  ✓ Identical distributed tracing
  ✓ Automatic mTLS (ambassador handles certs)
  ✓ Service discovery (ambassador queries registry)

  Policy change → update ambassador config → zero service code changes
```

**Q3. How is the Ambassador pattern related to the Sidecar pattern and the Service Mesh?**
A: They exist on a spectrum of the same fundamental idea — offloading network concerns from the service into a co-located proxy:

- **Sidecar pattern** — the general principle: a secondary container runs alongside the primary container in the same pod/host and extends its functionality. The sidecar can handle logging, monitoring, configuration, or networking. It is the *structural* pattern.
- **Ambassador pattern** — a *specific application* of the Sidecar pattern where the sidecar's responsibility is specifically **outbound proxy** — handling all outbound calls from the primary service. The ambassador intercepts, enriches, and routes requests going *out* of the service.
- **Service Mesh** — an *infrastructure-level* implementation of the Ambassador (and Sidecar) pattern at scale, across an entire cluster. Tools like Istio, Linkerd, and Consul Connect inject an Envoy (or similar) sidecar into *every* pod automatically. The service mesh is essentially "Ambassador pattern applied universally and managed by the platform."

```
Sidecar pattern (general):
  [Primary container] | [Sidecar container — any co-located helper]
                          e.g., log shipper, config watcher, proxy

Ambassador pattern (specific sidecar for outbound proxy):
  [Primary container] | [Ambassador sidecar — outbound network proxy]
                          intercepts all outbound calls

Service Mesh (Ambassador at infrastructure scale):
  Every pod: [Primary container] | [Envoy sidecar — auto-injected]
                                    all traffic (in + out) intercepted
  Control plane: Istiod distributes config to all sidecars
```

The practical difference at 5 YOE: you implement the Ambassador pattern yourself when you need a targeted solution for one or a few services in a non-mesh environment. You get the Ambassador pattern for free when you adopt a service mesh — the mesh *is* the ambassador, universally applied.

**Q4. What is the difference between an Ambassador and an API Gateway?**
A: Both are proxies, but they serve opposite directions and different scopes:

| Aspect | Ambassador | API Gateway |
|---|---|---|
| **Direction** | Outbound — proxies calls *from* the service to other services | Inbound — proxies calls *to* the service from clients |
| **Co-location** | Co-located with the client service (same pod/host) | Centralised — one gateway for many services |
| **Scope** | One service's outbound traffic | All services' inbound traffic |
| **Concerns** | Retry, circuit breaking, service discovery, mTLS, tracing | Authentication, rate limiting, routing, SSL termination, response aggregation |
| **Configuration** | Per-service (the ambassador's config is specific to one service's needs) | Cluster-wide (shared rules across all upstream services) |
| **Failure domain** | Per-service — if one ambassador fails, only that service is affected | Shared — gateway failure affects all services |
| **Typical implementations** | Envoy sidecar, custom Node.js proxy, Nginx sidecar | Kong, AWS API Gateway, Nginx, Traefik, Istio Ingress Gateway |

They frequently work together: an API Gateway handles inbound traffic from external clients; Ambassador sidecars handle outbound traffic between services internally.

**Q5. What specific responsibilities does an Ambassador typically handle?**
A:

**Retry and timeout** — automatically retries failed requests with configurable backoff, applies per-request timeouts without the service needing to manage `AbortController` instances:
```
Service → Ambassador → [call fails with 503] → Ambassador retries (1s, 2s, 4s backoff)
                                               → success on retry 2
         ← response ← Ambassador
```

**Circuit breaking** — tracks failure rates per downstream service, opens circuit to fail-fast when a service is unhealthy, probes during half-open state. The service never needs to import `opossum` or similar:
```
Service → Ambassador → [circuit OPEN for payment-service] → immediate rejection
         ← CircuitOpenError ← Ambassador
```

**Service discovery** — resolves service names to actual network addresses by querying Consul, Kubernetes DNS, or a service registry. The service calls `http://payment-service/charge`; the ambassador resolves it to `http://10.0.1.42:3001/charge`:
```
Service → Ambassador ["payment-service"] → [queries Consul] → 10.0.1.42:3001
```

**Distributed tracing** — injects and propagates trace context headers (`traceparent`, `X-B3-TraceId`, `X-Trace-Id`) so requests can be traced across service boundaries without any tracing code in the service:
```
Service → Ambassador → [injects: traceparent: 00-abc123-def456-01] → downstream
```

**mTLS** — handles mutual TLS handshake, certificate rotation, and validation. The service communicates with its ambassador over plaintext localhost; the ambassador communicates with downstream services over mTLS:
```
Service → (localhost, plaintext) → Ambassador → (mTLS) → downstream Ambassador → downstream service
```

**Authentication** — attaches JWT tokens, API keys, or service-to-service credentials to outbound requests:
```
Service → Ambassador → [attaches: Authorization: Bearer <service-token>] → downstream
```

**Rate limiting** — enforces outbound rate limits to protect downstream services from being overwhelmed by this service:
```
Service → Ambassador → [100 req/s limit for payment-service] → queued or rejected
```

## Section 2: Implementing the Ambassador Pattern in Node.js

**Q6. How do you implement a basic Ambassador as a Node.js HTTP proxy process?**
A: An ambassador running as a separate Node.js process on the same host/pod, listening on a local port and forwarding to downstream services with added cross-cutting concerns:

```ts
// ambassador.ts — runs as a separate process alongside the main service
import http        from "http";
import httpProxy   from "http-proxy-middleware";
import express     from "express";
import CircuitBreaker from "opossum";

interface AmbassadorConfig {
  listenPort:    number;           // port the service calls (e.g., 8080)
  routes:        ServiceRoute[];   // mapping of path prefix → downstream
}

interface ServiceRoute {
  prefix:      string;             // e.g., "/payment"
  target:      string;             // e.g., "http://payment-service:3001"
  retry:       RetryConfig;
  timeout:     number;
  circuitBreaker?: CircuitBreakerConfig;
}

interface RetryConfig {
  attempts:   number;
  delayMs:    number;
  backoff:    "fixed" | "exponential";
  retryOn:    number[];            // HTTP status codes to retry
}

const config: AmbassadorConfig = {
  listenPort: 8080,
  routes: [
    {
      prefix:  "/payment",
      target:  process.env.PAYMENT_SERVICE_URL ?? "http://payment-service:3001",
      timeout: 10_000,
      retry: { attempts: 3, delayMs: 200, backoff: "exponential", retryOn: [502, 503, 504] },
      circuitBreaker: { failureThreshold: 5, timeout: 30_000 },
    },
    {
      prefix:  "/inventory",
      target:  process.env.INVENTORY_SERVICE_URL ?? "http://inventory-service:3002",
      timeout: 5_000,
      retry: { attempts: 2, delayMs: 100, backoff: "exponential", retryOn: [502, 503] },
    },
  ],
};

// Retry helper — wraps a fetch with retry + backoff
async function fetchWithRetry(
  url:     string,
  options: RequestInit,
  config:  RetryConfig,
  logger:  Logger
): Promise<Response> {
  let lastError: Error | undefined;

  for (let attempt = 1; attempt <= config.attempts; attempt++) {
    try {
      const response = await fetch(url, options);

      if (config.retryOn.includes(response.status) && attempt < config.attempts) {
        const delay = config.backoff === "exponential"
          ? config.delayMs * Math.pow(2, attempt - 1)
          : config.delayMs;

        logger.warn("Request failed — retrying", {
          url, status: response.status, attempt, nextDelayMs: delay,
        });
        await new Promise(r => setTimeout(r, delay));
        continue;
      }

      return response;
    } catch (err) {
      lastError = err as Error;
      if (attempt < config.attempts) {
        const delay = config.backoff === "exponential"
          ? config.delayMs * Math.pow(2, attempt - 1)
          : config.delayMs;
        logger.warn("Request threw — retrying", { url, attempt, err, nextDelayMs: delay });
        await new Promise(r => setTimeout(r, delay));
      }
    }
  }
  throw lastError ?? new Error(`All ${config.attempts} attempts failed for ${url}`);
}

// Ambassador server
function buildAmbassador(config: AmbassadorConfig, logger: Logger): http.Server {
  const app      = express();
  const breakers = new Map<string, CircuitBreaker>();

  // Middleware — add distributed tracing headers to all outbound requests
  app.use((req, _res, next) => {
    // Propagate incoming trace context or generate a new one
    if (!req.headers["traceparent"]) {
      req.headers["traceparent"] = generateTraceParent();
    }
    next();
  });

  // Build a route handler per service route
  for (const route of config.routes) {
    // Circuit breaker per route
    let breaker: CircuitBreaker | undefined;
    if (route.circuitBreaker) {
      breaker = new CircuitBreaker(
        async (reqOptions: { url: string; options: RequestInit; retryConfig: RetryConfig }) =>
          fetchWithRetry(reqOptions.url, reqOptions.options, reqOptions.retryConfig, logger),
        {
          timeout:              route.timeout,
          errorThresholdPercentage: 50,
          resetTimeout:         route.circuitBreaker.timeout,
          volumeThreshold:      route.circuitBreaker.failureThreshold,
        }
      );

      breaker.on("open",     () => logger.warn("Circuit breaker OPEN",     { route: route.prefix }));
      breaker.on("halfOpen", () => logger.info("Circuit breaker HALF-OPEN", { route: route.prefix }));
      breaker.on("close",    () => logger.info("Circuit breaker CLOSED",    { route: route.prefix }));
      breakers.set(route.prefix, breaker);
    }

    // Route handler — proxies all requests matching the prefix
    app.all(`${route.prefix}*`, async (req, res) => {
      const path      = req.path;
      const targetUrl = `${route.target}${path}${req.search ?? ""}`;
      const start     = Date.now();

      // Forward all headers from the service, plus ambassador-added headers
      const headers: Record<string, string> = {
        ...Object.fromEntries(
          Object.entries(req.headers).filter(([, v]) => typeof v === "string")
        ) as Record<string, string>,
        "X-Forwarded-By": "ambassador",
        "X-Ambassador-Route": route.prefix,
      };

      const fetchOptions: RequestInit = {
        method:  req.method,
        headers,
        body:    ["GET", "HEAD", "DELETE"].includes(req.method) ? undefined : req,
        signal:  AbortSignal.timeout(route.timeout),
      };

      try {
        const execute = async () =>
          fetchWithRetry(targetUrl, fetchOptions, route.retry, logger);

        const response = breaker
          ? await breaker.fire({ url: targetUrl, options: fetchOptions, retryConfig: route.retry })
          : await execute();

        // Log the proxied request
        logger.info("Ambassador proxied request", {
          method:    req.method,
          path,
          target:    targetUrl,
          status:    response.status,
          durationMs: Date.now() - start,
        });

        // Forward response headers and body back to the service
        res.status(response.status);
        response.headers.forEach((value, key) => res.setHeader(key, value));
        const body = await response.arrayBuffer();
        res.send(Buffer.from(body));

      } catch (err) {
        const isCircuitOpen = (err as Error).message?.includes("EOPENBREAKER");
        logger.error("Ambassador request failed", {
          path, target: targetUrl, err, durationMs: Date.now() - start,
        });

        res.status(isCircuitOpen ? 503 : 502).json({
          error:  isCircuitOpen ? "Service temporarily unavailable" : "Bad gateway",
          route:  route.prefix,
          target: route.target,
        });
      }
    });
  }

  // Health endpoint — ambassador's own health (not the services it proxies)
  app.get("/ambassador/health", (_req, res) => {
    const breakerStates = Object.fromEntries(
      [...breakers.entries()].map(([name, b]) => [name, {
        state:   b.opened ? "OPEN" : b.halfOpen ? "HALF_OPEN" : "CLOSED",
        stats:   b.stats,
      }])
    );
    res.json({ status: "healthy", circuitBreakers: breakerStates });
  });

  return http.createServer(app);
}

// Start the ambassador
const logger    = new Logger();
const ambassador = buildAmbassador(config, logger);
ambassador.listen(config.listenPort, "127.0.0.1", () => {
  logger.info(`Ambassador listening on localhost:${config.listenPort}`);
});

// Graceful shutdown
process.on("SIGTERM", () => {
  ambassador.close(() => {
    logger.info("Ambassador shut down");
    process.exit(0);
  });
});

function generateTraceParent(): string {
  const traceId  = crypto.randomUUID().replace(/-/g, "");
  const parentId = crypto.randomBytes(8).toString("hex");
  return `00-${traceId}-${parentId}-01`;
}
```

**Q7. How does the service communicate with its ambassador — what changes in the service code?**
A: Almost nothing changes in the service code — that is the point. The service replaces its downstream service URL with the ambassador's localhost address. All retry, circuit breaking, tracing, and mTLS logic disappears from the service:

```ts
// Before Ambassador — service has retry, circuit breaker, tracing in its own code
import CircuitBreaker from "opossum";
import { trace }      from "@opentelemetry/api";

class PaymentServiceClient {
  private breaker = new CircuitBreaker(this.callPaymentApi, {
    timeout: 10_000, errorThresholdPercentage: 50,
  });

  async charge(amount: number, token: string): Promise<ChargeResult> {
    const span = trace.getTracer("order-service").startSpan("payment.charge");
    try {
      return await this.breaker.fire(amount, token);
    } finally { span.end(); }
  }

  private async callPaymentApi(amount: number, token: string): Promise<ChargeResult> {
    let lastError: Error | undefined;
    for (let attempt = 0; attempt < 3; attempt++) {
      try {
        const res = await fetch(`${PAYMENT_SERVICE_URL}/charge`, {
          method:  "POST",
          headers: {
            "Content-Type":  "application/json",
            "Authorization": `Bearer ${await this.getServiceToken()}`,
            "traceparent":   span.spanContext().traceId,
          },
          body: JSON.stringify({ amount, token }),
          signal: AbortSignal.timeout(10_000),
        });
        if (!res.ok) throw new HttpError(res.status);
        return res.json();
      } catch (err) {
        lastError = err as Error;
        await new Promise(r => setTimeout(r, 200 * Math.pow(2, attempt)));
      }
    }
    throw lastError;
  }
}

// After Ambassador — service code is trivially simple
class PaymentServiceClient {
  // AMBASSADOR_URL = "http://localhost:8080" — the ambassador's local port
  private readonly baseUrl = process.env.AMBASSADOR_URL ?? "http://localhost:8080";

  async charge(amount: number, token: string): Promise<ChargeResult> {
    // Ambassador handles: retry, circuit breaking, tracing, mTLS, service discovery
    const res = await fetch(`${this.baseUrl}/payment/charge`, {
      method:  "POST",
      headers: { "Content-Type": "application/json" },
      body:    JSON.stringify({ amount, token }),
    });
    if (!res.ok) throw new HttpError(res.status, await res.text());
    return res.json();
  }
}
```

The service's `fetch` call goes to `localhost:8080/payment/charge`. The ambassador receives it, adds tracing headers, applies retry logic, manages the circuit breaker state, handles mTLS with the downstream payment service, and forwards the request. From the service's perspective, it's just an HTTP call.

**Q8. How do you configure an Ambassador using Envoy Proxy — the most widely used ambassador implementation?**
A: Envoy is the proxy used by Istio, Consul Connect, and many Ambassador implementations. It is configured via a YAML file and handles all network concerns declaratively:

```yaml
# envoy.yaml — ambassador sidecar configuration
static_resources:
  listeners:
    # Listen on localhost — only the service on this host can reach this listener
    - name:    outbound_listener
      address:
        socket_address:
          address:    127.0.0.1
          port_value: 8080           # service calls localhost:8080

      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                stat_prefix: outbound
                access_log:
                  - name: envoy.access_loggers.stdout
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.access_loggers.stream.v3.StdoutAccessLog

                # HTTP filters — applied to every proxied request
                http_filters:
                  # Retry filter — applied per-route
                  - name: envoy.filters.http.router
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.filters.http.router.v3.Router

                route_config:
                  name:          outbound_routes
                  virtual_hosts:
                    - name:    all
                      domains: ["*"]
                      routes:
                        # Route 1 — Payment service
                        - match: { prefix: "/payment" }
                          route:
                            cluster:        payment_service
                            timeout:        10s
                            retry_policy:
                              retry_on:       "5xx,gateway-error,connect-failure"
                              num_retries:    3
                              per_try_timeout: 3s
                              retry_back_off:
                                base_interval: 0.2s
                                max_interval:  5s

                        # Route 2 — Inventory service
                        - match: { prefix: "/inventory" }
                          route:
                            cluster:        inventory_service
                            timeout:        5s
                            retry_policy:
                              retry_on:       "5xx,gateway-error"
                              num_retries:    2
                              per_try_timeout: 2s

  clusters:
    # Payment service cluster — with circuit breaking
    - name:                   payment_service
      connect_timeout:        1s
      type:                   STRICT_DNS
      load_assignment:
        cluster_name: payment_service
        endpoints:
          - lb_endpoints:
              - endpoint:
                  address:
                    socket_address:
                      address:    payment-service   # Kubernetes DNS resolves this
                      port_value: 3001

      circuit_breakers:
        thresholds:
          - priority:              DEFAULT
            max_connections:       100
            max_pending_requests:  50
            max_requests:          100
            max_retries:           3

      # Outlier detection — automatically eject unhealthy hosts
      outlier_detection:
        consecutive_5xx:           5

      transport_socket:
        name: envoy.transport_sockets.tls
```

## Section 3: Real-World Applications

**Q9. How does the Ambassador pattern handle authentication — specifically service-to-service token injection?**
A: The ambassador intercepts outbound requests and attaches the appropriate authentication credential, so the service never manages tokens:

```ts
// Ambassador with service-to-service JWT injection
class AuthenticatingAmbassador {
  private tokenCache = new Map<string, { token: string; expiresAt: number }>();

  async proxyRequest(
    req:     IncomingMessage,
    target:  string,
    service: string
  ): Promise<Response> {
    // Get or refresh a service-to-service token for the target service
    const token = await this.getServiceToken(service);

    const headers = new Headers({
      ...(req.headers as Record<string, string>),
      "Authorization": `Bearer ${token}`,
      "X-Service-Name": process.env.SERVICE_NAME ?? "unknown",
    });

    return fetch(target, {
      method:  req.method,
      headers,
      body:    req,
      signal:  AbortSignal.timeout(10_000),
    });
  }

  private async getServiceToken(targetService: string): Promise<string> {
    const cached = this.tokenCache.get(targetService);

    // Return cached token if it has more than 60 seconds before expiry
    if (cached && cached.expiresAt > Date.now() + 60_000) {
      return cached.token;
    }

    // Fetch a new token from the identity provider
    const response = await fetch(`${process.env.IDENTITY_URL}/token`, {
      method:  "POST",
      headers: { "Content-Type": "application/json" },
      body:    JSON.stringify({
        grant_type:    "client_credentials",
        client_id:     process.env.SERVICE_CLIENT_ID,
        client_secret: process.env.SERVICE_CLIENT_SECRET,
        audience:      targetService,
      }),
    });

    const { access_token, expires_in } = await response.json();
    const expiresAt = Date.now() + expires_in * 1000;

    this.tokenCache.set(targetService, { token: access_token, expiresAt });
    return access_token;
  }
}
```

**Q10. How does the Ambassador pattern add distributed tracing without any tracing code in the service?**
A:
```ts
// Ambassador — injects and propagates W3C Trace Context headers
import { context, propagation, trace, SpanKind } from "@opentelemetry/api";
import { W3CTraceContextPropagator }              from "@opentelemetry/core";

const propagator = new W3CTraceContextPropagator();
const tracer     = trace.getTracer("ambassador");

class TracingAmbassador {
  async proxyRequest(req: IncomingMessage, targetUrl: string, route: string): Promise<Response> {
    // Extract trace context from incoming request (propagated from upstream service)
    const incomingHeaders = new Headers(req.headers as Record<string, string>);
    const parentContext   = propagation.extract(context.active(), incomingHeaders);

    // Start a new span for this outbound call
    const span = tracer.startSpan(
      `ambassador.${route}`,
      {
        kind:       SpanKind.CLIENT,
        attributes: {
          "http.method":     req.method ?? "GET",
          "http.url":        targetUrl,
          "ambassador.route": route,
        },
      },
      parentContext
    );

    // Inject trace context into outbound headers
    const outboundHeaders: Record<string, string> = {
      ...(req.headers as Record<string, string>),
    };
    propagation.inject(trace.setSpan(context.active(), span), outboundHeaders);

    const start = Date.now();
    try {
      const response = await fetch(targetUrl, {
        method:  req.method,
        headers: outboundHeaders,
        body:    req,
      });

      span.setAttributes({
        "http.status_code": response.status,
        "http.duration_ms": Date.now() - start,
      });
      span.setStatus({ code: response.ok ? SpanStatusCode.OK : SpanStatusCode.ERROR });

      return response;
    } catch (err) {
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      span.recordException(err as Error);
      throw err;
    } finally {
      span.end();
    }
  }
}

// The service sends a request with no trace headers:
//   POST http://localhost:8080/payment/charge
//   Content-Type: application/json
//
// The ambassador forwards with trace context automatically injected:
//   POST http://payment-service:3001/charge
//   Content-Type: application/json
//   traceparent: 00-abc123def456...-00112233-01
//   tracestate:  vendor=value
//
// The payment service receives the trace context and propagates it further
// → full distributed trace assembled in Jaeger / Zipkin / Datadog without any service code changes
```

**Q11. How does the Ambassador pattern implement adaptive load balancing — choosing the best instance based on current performance?**
A:
```ts
// Ambassador with latency-aware load balancing
interface ServiceInstance {
  host:      string;
  port:      number;
  weight:    number;
  latencyP99: number; // rolling p99 latency in ms
  errorRate:  number; // 0–1
}

class AdaptiveLoadBalancingAmbassador {
  private instances    = new Map<string, ServiceInstance[]>();
  private latencyTrack = new Map<string, number[]>(); // rolling window

  async proxyRequest(serviceName: string, path: string, options: RequestInit): Promise<Response> {
    const instances = await this.resolveInstances(serviceName);
    const instance  = this.selectInstance(instances);
    const url       = `http://${instance.host}:${instance.port}${path}`;

    const start = Date.now();
    try {
      const response = await fetch(url, { ...options, signal: AbortSignal.timeout(10_000) });
      const latency  = Date.now() - start;
      this.recordLatency(instance, latency, response.ok ? 0 : 1);
      return response;
    } catch (err) {
      this.recordLatency(instance, Date.now() - start, 1);
      throw err;
    }
  }

  // Power-of-two-choices — pick the better of two randomly chosen instances
  private selectInstance(instances: ServiceInstance[]): ServiceInstance {
    if (instances.length === 1) return instances[0];

    const [a, b] = this.pickTwo(instances);

    // Score: lower is better — penalise high latency and high error rate
    const scoreA = a.latencyP99 * (1 + a.errorRate * 10);
    const scoreB = b.latencyP99 * (1 + b.errorRate * 10);

    return scoreA <= scoreB ? a : b;
  }

  private pickTwo<T>(arr: T[]): [T, T] {
    const idxA = Math.floor(Math.random() * arr.length);
    let   idxB = Math.floor(Math.random() * (arr.length - 1));
    if (idxB >= idxA) idxB++;
    return [arr[idxA], arr[idxB]];
  }

  private recordLatency(instance: ServiceInstance, latencyMs: number, error: 0 | 1): void {
    const key = `${instance.host}:${instance.port}`;
    const window = this.latencyTrack.get(key) ?? [];

    window.push(latencyMs);
    if (window.length > 100) window.shift(); // keep last 100 samples
    this.latencyTrack.set(key, window);

    // Update instance stats
    const sorted    = [...window].sort((a, b) => a - b);
    instance.latencyP99 = sorted[Math.floor(sorted.length * 0.99)] ?? 0;
    instance.errorRate  = instance.errorRate * 0.95 + error * 0.05; // EWMA
  }

  private async resolveInstances(serviceName: string): Promise<ServiceInstance[]> {
    // Query service registry (Consul, K8s endpoints, etc.)
    const cached = this.instances.get(serviceName);
    if (cached) return cached;

    const instances = await this.serviceDiscovery.getHealthyInstances(serviceName);
    this.instances.set(serviceName, instances);
    setTimeout(() => this.instances.delete(serviceName), 5_000); // cache for 5s
    return instances;
  }
}
```

## Section 4: Ambassador vs Related Patterns

**Q13. How does the Ambassador pattern differ from the Proxy pattern and the Decorator pattern?**
A:

| Aspect | Proxy (GoF) | Decorator (GoF) | Ambassador |
|---|---|---|---|
| **Location** | Same process | Same process | Separate process / container |
| **Protocol** | In-language method calls | In-language method calls | Network (HTTP, gRPC) |
| **Concern** | Access control, lazy init, caching | Add behaviour to one object | Network cross-cutting concerns at infrastructure level |
| **Transparency** | Implements same interface | Implements same interface | Different address (localhost:8080 vs real service URL) |
| **Language** | Same language as client | Same language as client | Language-agnostic |
| **Upgradeability** | Tied to client release | Tied to client release | Deployed independently |

```ts
// Proxy — in-process, same language, method-level interception
class RetryingPaymentGateway implements PaymentGateway {
  constructor(private inner: PaymentGateway) {}
  async charge(amount: number, token: string): Promise<ChargeResult> {
    // retry logic — same process
    return retry(() => this.inner.charge(amount, token), { attempts: 3 });
  }
}

// Decorator — in-process, adds behaviour to one object
class TracingPaymentGateway implements PaymentGateway {
  constructor(private inner: PaymentGateway) {}
  async charge(amount: number, token: string): Promise<ChargeResult> {
    const span = tracer.startSpan("payment.charge");
    const result = await this.inner.charge(amount, token);
    span.end();
    return result;
  }
}

// Ambassador — out-of-process, network-level, language-agnostic
// Service calls localhost:8080/payment/charge (plain HTTP)
// Ambassador (separate process) handles: retry + tracing + circuit breaking + mTLS
// Service has zero retry/tracing/circuit-breaking code
```

**Q14. When should you choose the Ambassador pattern over a shared library?**
A: The decision hinges on three factors:

**Choose the Ambassador pattern when:**
- **Polyglot environment** — services are written in multiple languages. A shared library cannot span Node.js, Python, and Java simultaneously.
- **Operational uniformity required** — all services must behave identically under load (same retry policy, same circuit breaker thresholds). A shared library version-drifts across teams.
- **Concerns change frequently** — retry policies, timeout values, and circuit breaker thresholds need to be updated without redeploying the services. Ambassador config can be updated independently.
- **Service mesh is not yet adopted** — the Ambassador pattern is the step before a full service mesh; it prepares you for one.
- **Regulatory or security requirements** — mTLS between services must be enforced; the ambassador handles certificate rotation without service changes.

**Choose a shared library when:**
- **Single language** — all services use the same language; a well-maintained library is simpler.
- **Simple concerns** — only retry is needed; introducing a sidecar process for one concern adds operational overhead.
- **Small team / low service count** — the coordination overhead of deploying ambassador sidecars everywhere exceeds the benefit when there are fewer than 5–10 services.
- **Performance-critical path** — the ambassador adds a network hop (localhost, sub-millisecond, but non-zero). For extremely latency-sensitive paths, in-process is faster.

```
Decision matrix:
  Polyglot?          → Ambassador (library can't span languages)
  Policy change freq? → Ambassador if high (deploy independently)
  Service count?     → Library if < 5, Ambassador if > 10
  mTLS required?     → Ambassador (cert rotation without code changes)
  Full mesh planned? → Ambassador now (preparatory step)
  Single lang, few   → Library (lower operational cost)
  services, rare
  policy changes?
```

## Section 6: Scenario / System Design Style Questions

**Q16. "Your Node.js services need to communicate with three downstream services. Each service team has different retry policies, and mTLS between services is a compliance requirement. How does the Ambassador pattern address this?"**
A:
```ts
// Without Ambassador — each team implements their own retry + mTLS
// OrderService: uses opossum + node-forge for mTLS manually
// PaymentService: uses axios-retry + a different TLS library
// InventoryService: uses got (with retry plugin) + yet another mTLS approach
// → 3 different retry implementations, 3 different mTLS implementations
// → Compliance team cannot audit or enforce a uniform mTLS policy

const ambassadorConfig: AmbassadorConfig = {
  listenPort: 8080,
  routes: [
    {
      prefix:  "/payment",
      target:  "http://payment-service:3001",
      timeout: 10_000,
      // Payment team's policy: 3 retries, exponential backoff
      retry: { attempts: 3, delayMs: 200, backoff: "exponential", retryOn: [502, 503, 504] },
      tls: { certFile: "/certs/payment-client.pem", keyFile: "/certs/payment-client-key.pem" },
    },
    {
      prefix:  "/inventory",
      target:  "http://inventory-service:3002",
      timeout: 5_000,
      // Inventory team's policy: 2 retries, fixed delay (idempotent reads only)
      retry: { attempts: 2, delayMs: 100, backoff: "fixed", retryOn: [503] },
      tls: { certFile: "/certs/inventory-client.pem", keyFile: "/certs/inventory-client-key.pem" },
    },
    {
      prefix:  "/notification",
      target:  "http://notification-service:3003",
      timeout: 3_000,
      // Notification team's policy: no retry (idempotency not guaranteed for notifications)
      retry: { attempts: 1, delayMs: 0, backoff: "fixed", retryOn: [] },
      tls: { certFile: "/certs/notification-client.pem", keyFile: "/certs/notification-client-key.pem" },
    },
  ],
};

// Compliance requirements satisfied:
// ✓ mTLS for all outbound calls — configured in ambassador, not in service code
// ✓ Certificate rotation — update the mounted secret, ambassador picks it up on reload
// ✓ Auditable policy — single ambassador config file per service, in version control
// ✓ Uniform retry policies — enforced by ambassador, consistent across all service versions
// ✓ Service code is unchanged — no compliance-coupled code in business logic
```

**Q17. "A team wants to migrate from a monolith to microservices. They are worried about the complexity of implementing retry, circuit breaking, and service discovery in every new microservice. How does the Ambassador pattern reduce this migration risk?"**
A: The Ambassador pattern lets teams extract microservices without solving the resilience problem from scratch each time:

```
Migration strategy with Ambassador:

Phase 1 — Extract first microservice (OrderService)
  - Deploy OrderService with a pre-configured ambassador sidecar
  - Ambassador handles: retry, circuit breaking, service discovery, tracing
  - OrderService code focuses purely on order domain logic
  - No resilience library needed in the new service

Phase 2 — Extract second microservice (InventoryService)
  - Deploy same ambassador sidecar configuration (adjusted for InventoryService's callers)
  - InventoryService code has zero network resilience code
  - New team gets all the same resilience behaviour as OrderService immediately

Phase 3 — Each new microservice
  - Provision: add ambassador sidecar to pod spec (2 YAML lines)
  - Configure: add route entries to ambassador config (the service's outbound routes)
  - Zero additional code in each new service

Result:
  20 microservices extracted over 12 months
  Each has: retry, circuit breaking, mTLS, distributed tracing
  Total resilience code in business services: zero lines
  All policies managed in one place (ambassador config in config management)
  Policy change (e.g., increase retry attempts): update config, rolling restart ambassadors
  No service code changes needed for the policy update
```

```ts
// Template for a new microservice — zero resilience code
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | In-process Library | Ambassador (Sidecar) | Service Mesh |
|---|---|---|---|
| **Language support** | One language per library | Any language | Any language |
| **Coupling to service** | Tight — library imported | Loose — network interface | Loose — transparent |
| **Policy update** | Redeploy service | Redeploy ambassador only | Update mesh control plane |
| **Operational complexity** | Low | Medium | High |
| **Latency overhead** | None (in-process) | Sub-millisecond (localhost) | Sub-millisecond (localhost) |
| **Visibility** | Per-service metrics | Per-service + per-route | Cluster-wide unified metrics |
| **mTLS** | Manual per service | Ambassador manages | Automatic, zero-config |
| **Circuit breaker** | Per-service config | Per-ambassador config | Per-mesh config (VirtualService) |
| **Service discovery** | SDK per service | Queried by ambassador | Envoy via xDS |
| **Best for** | Single lang, small teams | Polyglot, medium scale | Large scale, org-wide policy |

## Ambassador Pattern Anti-Patterns at a Glance

| Anti-pattern | Description | Fix |
|---|---|---|
| **Business logic in ambassador** | Ambassador makes routing decisions based on request payload content | Ambassador is for network concerns only; routing by content = API Gateway responsibility |
| **One ambassador per downstream** | Deploying a separate ambassador sidecar for each downstream service | One ambassador per service instance — it proxies to all downstreams via route config |
| **Ambassador on the ingress path** | Using an ambassador to handle inbound traffic from external clients | Use an API Gateway for inbound; Ambassador is for outbound service-to-service calls |
| **Service bypassing ambassador** | Service calls downstream directly for "performance" — ambassador is bypassed | All outbound calls must go through ambassador; enforce via network policy (Kubernetes NetworkPolicy) |
| **Ambassador as a bottleneck** | All services share one ambassador instance — single point of failure | Ambassador is per-service (co-located sidecar), never shared |
| **No ambassador health check** | Ambassador crashes silently — service continues sending requests to localhost:8080 with no response | Ambassador exposes its own health endpoint; Kubernetes probes it; pod restarts if ambassador is unhealthy |
| **Ignoring ambassador metrics** | Ambassador emits metrics that nobody watches — failures go undetected | Scrape ambassador metrics (Envoy admin endpoint, custom /metrics); alert on circuit breaker state, error rates |
| **Static config, dynamic world** | Ambassador config has hardcoded IPs — breaks when services scale | Use service names (Kubernetes DNS) or dynamic discovery integration (Consul Template) |

**Tip for the interview:** At the 5 YOE level, "what is the Ambassador pattern" surfaces as: how do you enforce uniform retry and circuit breaking across a polyglot microservices fleet without duplicating code in every service, how do you implement mTLS between services without each team managing certificates, how does your service discovery and load balancing work when you're not using a full service mesh, or how do you add distributed tracing to every outbound service call without modifying any service code. The sharp answer immediately names the co-location distinction (ambassador is a sidecar on localhost, not a centralised gateway), explains the language-agnostic benefit (one Node.js service and one Python service get identical retry behaviour without any library), contrasts it with a shared library (library version-drifts; ambassador is upgraded independently), places it on the spectrum between DIY library and full service mesh (ambassador is the pragmatic middle ground), and explains what the service code looks like after (just `fetch("http://localhost:8080/payment/charge")` — nothing else). Noting that an ambassador is a specific application of the Sidecar pattern, and that a service mesh is the Ambassador pattern applied universally by the platform, shows the architectural depth that lands at 5 YOE.
