# Behavioral Design Patterns: Visitor — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Visitor pattern?**
A: Visitor is a behavioral design pattern that lets you **add new operations to an object structure without modifying the classes of the objects** in that structure. Instead of adding a new method to each class, you encapsulate the new operation in a separate "visitor" object. Each element in the structure "accepts" a visitor, then calls back the visitor's method that corresponds to the element's own type — a technique called **double dispatch**.

The four roles in every Visitor implementation:
- **Visitor interface** — declares one `visit` method per concrete element type in the structure (e.g., `visitHomeLoan`, `visitPersonalLoan`, `visitMsmeLoan`).
- **Concrete Visitors** — each implements the visitor interface, providing one distinct operation across all element types (e.g., `TaxCalculatorVisitor`, `RiskReportVisitor`, `ComplianceAuditVisitor`).
- **Element interface** — declares an `accept(visitor)` method that every element in the structure must implement.
- **Concrete Elements** — each calls back the visitor method that matches its own type: `visitor.visitHomeLoan(this)`.

**Q2. What problem does the Visitor pattern solve?**
A: Visitor solves the **operation proliferation problem** in a stable object hierarchy. When you have a fixed set of element types (different loan types, different transaction types, different document types) and you need to add many different operations across all of them, the alternatives are painful:

- **Adding methods to each element class** — every new operation requires modifying every element class. With 8 loan types and 10 operations, that's 80 method additions across 8 classes. Each modification risks breaking existing behaviour and mixes unrelated concerns in the same class.
- **Type-checking with `instanceof`** — a single method that does `if (loan instanceof HomeLoan) ... else if (loan instanceof PersonalLoan) ...` is an OCP violation. Adding a new loan type requires finding every such switch and updating it.

Visitor moves each operation into its own class. Adding the 11th operation means writing one new Visitor class — zero changes to any element class. It's the inverse trade-off from Strategy: Visitor makes it easy to add new operations but hard to add new element types; Strategy makes it easy to add new algorithms but keeps element types stable.

**Q3. What is double dispatch, and why is it fundamental to the Visitor pattern?**
A: **Single dispatch** — the mechanism in most OO languages — selects the method to call based on the *runtime type of the receiver* only. If you call `loan.calculateTax()`, the runtime resolves which `calculateTax` to call based on what `loan` actually is. But if you pass a visitor to a method: `processLoan(visitor, loan)` — the runtime only knows the declared types at the call site, not the concrete types of both arguments.

**Double dispatch** selects the method based on the runtime types of *two* objects — both the element and the visitor:

```typescript
// Step 1 — first dispatch: runtime picks HomeLoan.accept()
loan.accept(visitor);

// Step 2 — second dispatch: inside accept(), runtime picks visitor.visitHomeLoan()
class HomeLoan implements Loan {
  accept(visitor: LoanVisitor): void {
    visitor.visitHomeLoan(this); // 'this' is typed as HomeLoan — second dispatch
  }
}
```

Without double dispatch, you'd need to know which concrete visitor method to call at the call site — which defeats the purpose. The `accept` → `visit` callback is the double dispatch mechanism: the element resolves itself (first dispatch), then calls the visitor method specific to its own type (second dispatch). The visitor then receives the correctly-typed element reference.

**Q4. What is the Visitor pattern's fundamental trade-off?**
A: Visitor optimises along one axis and sacrifices the other:

| Axis                         | Visitor                                          | Alternative (adding methods to elements)         |
|------------------------------|--------------------------------------------------|--------------------------------------------------|
| Adding a new **operation**   | ✅ Easy — one new Visitor class; elements untouched | ❌ Hard — modify every element class            |
| Adding a new **element type** | ❌ Hard — must add a method to every Visitor     | ✅ Easy — add a new class, implement the interface |
| Cohesion                     | Operations cohesive — all types in one Visitor   | Types cohesive — all operations in one class     |
| Coupling                     | Visitor tightly knows all element types          | Elements know nothing about operations           |

The implication: **use Visitor when your element hierarchy is stable and closed (you won't add new types often), but you need to add new operations frequently**. If element types are added regularly, Visitor becomes a maintenance burden — every new type requires updating every existing Visitor.

**Q5. How does Visitor differ from Strategy and Iterator?**
A:

| Pattern       | Intent                                                      | What varies?               | Who knows element type?     |
|---------------|-------------------------------------------------------------|----------------------------|-----------------------------|
| **Visitor**   | Add operations to a stable object structure                 | The operation (visitor)    | The visitor — explicitly    |
| **Strategy**  | Swap algorithms for a single context                        | The algorithm              | The context — passes itself |
| **Iterator**  | Traverse elements of a collection sequentially              | The traversal mechanism    | Nobody — elements are opaque|

The sharpest distinction: **Visitor vs Strategy** — both encapsulate behaviour in a separate object, but Visitor works across a *heterogeneous* structure of different element types, calling different visit methods per type. Strategy works on a *single* context type, replacing the algorithm wholesale. A `TaxCalculatorVisitor` calculates tax differently for home loans vs personal loans vs MSME loans — the visitor is type-aware. A `TaxCalculationStrategy` would be one algorithm for one loan type.

## Section 2: Implementation

**Q6. What does a canonical TypeScript Visitor implementation look like for a loan hierarchy?**
A:

```typescript
// Element interface — every loan type must implement accept()
interface Loan {
  id: string;
  amount: number;
  accept(visitor: LoanVisitor): void;
}

// Visitor interface — one visit method per concrete element type
interface LoanVisitor {
  visitHomeLoan(loan: HomeLoan): void;
  visitPersonalLoan(loan: PersonalLoan): void;
  visitMsmeLoan(loan: MsmeLoan): void;
}

// Concrete Elements — each calls back the right visitor method
class HomeLoan implements Loan {
  constructor(
    public readonly id: string,
    public readonly amount: number,
    public readonly propertyValue: number,
    public readonly ltv: number,
    public readonly isAffordableHousing: boolean,
  ) {}

  accept(visitor: LoanVisitor): void {
    visitor.visitHomeLoan(this); // double dispatch — second step
  }
}

class PersonalLoan implements Loan {
  constructor(
    public readonly id: string,
    public readonly amount: number,
    public readonly interestRate: number,
    public readonly tenorMonths: number,
    public readonly employmentType: string,
  ) {}

  accept(visitor: LoanVisitor): void {
    visitor.visitPersonalLoan(this);
  }
}

class MsmeLoan implements Loan {
  constructor(
    public readonly id: string,
    public readonly amount: number,
    public readonly gstin: string,
    public readonly turnover: number,
    public readonly collateralType: string,
  ) {}

  accept(visitor: LoanVisitor): void {
    visitor.visitMsmeLoan(this);
  }
}
```

```typescript
// Concrete Visitor 1 — RBI Regulatory Reporting
class RbiRegulatoryReportVisitor implements LoanVisitor {
  private entries: ReportEntry[] = [];

  visitHomeLoan(loan: HomeLoan): void {
    this.entries.push({
      loanId: loan.id,
      category: loan.isAffordableHousing ? 'PSL_HOUSING' : 'HOUSING',
      amount: loan.amount,
      ltv: loan.ltv,
      reportingCode: loan.ltv > 80 ? 'HL_HIGH_LTV' : 'HL_STANDARD',
    });
  }

  visitPersonalLoan(loan: PersonalLoan): void {
    this.entries.push({
      loanId: loan.id,
      category: 'CONSUMER_CREDIT',
      amount: loan.amount,
      reportingCode: loan.amount > 500_000 ? 'PL_LARGE' : 'PL_STANDARD',
    });
  }

  visitMsmeLoan(loan: MsmeLoan): void {
    this.entries.push({
      loanId: loan.id,
      category: 'PRIORITY_SECTOR_MSME',  // PSL classification
      amount: loan.amount,
      reportingCode: loan.amount <= 1_000_000 ? 'MSME_MICRO' : 'MSME_SMALL',
      gstin: loan.gstin,
    });
  }

  getReport(): ReportEntry[] { return this.entries; }
}

// Concrete Visitor 2 — Provisioning Calculation (NPA/ECL)
class ProvisioningVisitor implements LoanVisitor {
  private totalProvision = 0;

  visitHomeLoan(loan: HomeLoan): void {
    // Home loans: lower provisioning — collateralised
    const rate = loan.ltv > 80 ? 0.015 : 0.010;
    this.totalProvision += loan.amount * rate;
  }

  visitPersonalLoan(loan: PersonalLoan): void {
    // Personal loans: higher provisioning — unsecured
    const rate = loan.interestRate > 18 ? 0.05 : 0.035;
    this.totalProvision += loan.amount * rate;
  }

  visitMsmeLoan(loan: MsmeLoan): void {
    // MSME loans: collateral-dependent
    const rate = loan.collateralType === 'NONE' ? 0.04 : 0.02;
    this.totalProvision += loan.amount * rate;
  }

  getTotalProvision(): number { return this.totalProvision; }
}

// Concrete Visitor 3 — Compliance Audit
class ComplianceAuditVisitor implements LoanVisitor {
  private violations: ComplianceViolation[] = [];

  visitHomeLoan(loan: HomeLoan): void {
    if (loan.ltv > 90) {
      this.violations.push({
        loanId: loan.id,
        rule: 'RBI_CIRCULAR_2023_LTV',
        message: `LTV ${loan.ltv}% exceeds maximum 90% for home loans`,
        severity: 'HIGH',
      });
    }
  }

  visitPersonalLoan(loan: PersonalLoan): void {
    if (loan.amount > 5_000_000) {
      this.violations.push({
        loanId: loan.id,
        rule: 'PL_AMOUNT_CAP',
        message: `Personal loan ₹${loan.amount} exceeds regulatory cap`,
        severity: 'MEDIUM',
      });
    }
  }

  visitMsmeLoan(loan: MsmeLoan): void {
    if (!loan.gstin) {
      this.violations.push({
        loanId: loan.id,
        rule: 'MSME_GSTIN_MANDATORY',
        message: 'MSME loan disbursed without GSTIN — UDYAM compliance failure',
        severity: 'HIGH',
      });
    }
  }

  getViolations(): ComplianceViolation[] { return this.violations; }
}
```

```typescript
// Usage — apply multiple visitors to the same loan portfolio
const portfolio: Loan[] = [
  new HomeLoan('L001', 4_500_000, 5_000_000, 90, false),

const provisioner = new ProvisioningVisitor();

  loan.accept(provisioner);

console.log(provisioner.getTotalProvision());
console.log(auditor.getViolations());
```

Adding a fourth visitor (e.g., `PslClassificationVisitor` for Priority Sector Lending reporting) requires writing one new class — zero changes to `HomeLoan`, `PersonalLoan`, or `MsmeLoan`.

**Q7. How do you implement a Visitor that returns a value (rather than accumulating into state)?**
A: The visitor interface can be made generic to return values from each `visit` call:

```typescript
// Generic visitor interface — each visit returns a value
interface LoanVisitor<T> {
  visitHomeLoan(loan: HomeLoan): T;
  visitPersonalLoan(loan: PersonalLoan): T;
  visitMsmeLoan(loan: MsmeLoan): T;
}

// Element interface — accept returns the visitor's return type
interface Loan {
  accept<T>(visitor: LoanVisitor<T>): T;
}

class HomeLoan implements Loan {
  accept<T>(visitor: LoanVisitor<T>): T {
    return visitor.visitHomeLoan(this); // returns T
  }
}

// Stateless visitor — computes and returns, no accumulation
class TaxLiabilityVisitor implements LoanVisitor<number> {
  visitHomeLoan(loan: HomeLoan): number {
    // Home loan interest: Section 24(b) deduction ₹2L p.a. — tax on excess
    const annualInterest = loan.amount * 0.085;
    const taxableInterest = Math.max(0, annualInterest - 200_000);
    return taxableInterest * 0.30; // 30% tax slab
  }

  visitPersonalLoan(loan: PersonalLoan): number {
    // Personal loan: no tax deduction — full interest is taxable income for lender
    return loan.amount * (loan.interestRate / 100) * 0.30;
  }

  visitMsmeLoan(loan: MsmeLoan): number {
    // MSME: interest taxable as business income for lender
    return loan.amount * 0.12 * 0.25; // 25% corporate tax
  }
}

// Usage — per-loan computation
const taxVisitor = new TaxLiabilityVisitor();
const taxOnHomeLoan = homeLoan.accept(taxVisitor); // returns number directly
```

**Q8. How do you handle a Visitor over a composite/tree structure (hierarchical loan portfolio)?**
A: When the object structure is a tree (portfolio → loan accounts → sub-accounts → transactions), the Visitor traverses the tree by having composite elements visit their children:

```typescript
interface PortfolioElement {
  accept(visitor: PortfolioVisitor): void;
}

interface PortfolioVisitor {
  visitPortfolio(p: LoanPortfolio): void;
  visitLoanAccount(a: LoanAccount): void;
  visitTransaction(t: LoanTransaction): void;
}

class LoanPortfolio implements PortfolioElement {
  constructor(
    public readonly id: string,
    public readonly accounts: LoanAccount[],
  ) {}

  accept(visitor: PortfolioVisitor): void {
    visitor.visitPortfolio(this);
    // Composite visits its children — traversal is built into the structure
    for (const account of this.accounts) {
      account.accept(visitor);
    }
  }
}

class LoanAccount implements PortfolioElement {
  constructor(
    public readonly id: string,
    public readonly outstandingPrincipal: number,
    public readonly transactions: LoanTransaction[],
  ) {}

  accept(visitor: PortfolioVisitor): void {
    visitor.visitLoanAccount(this);
    for (const txn of this.transactions) {
      txn.accept(visitor);
    }
  }
}

class LoanTransaction implements PortfolioElement {
  constructor(
    public readonly id: string,
    public readonly type: 'EMI' | 'PREPAYMENT' | 'PENALTY' | 'DISBURSEMENT',
    public readonly amount: number,
    public readonly date: Date,
  ) {}

  accept(visitor: PortfolioVisitor): void {
    visitor.visitTransaction(this); // leaf node — no children to visit
  }
}

// Visitor that computes total penalty income across the entire portfolio tree
class PenaltyIncomeVisitor implements PortfolioVisitor {
  private totalPenalty = 0;

  visitPortfolio(_p: LoanPortfolio): void { /* no action at portfolio level */ }
  visitLoanAccount(_a: LoanAccount): void { /* no action at account level */ }
  visitTransaction(txn: LoanTransaction): void {
    if (txn.type === 'PENALTY') {
      this.totalPenalty += txn.amount;
    }
  }

  getTotalPenalty(): number { return this.totalPenalty; }
}
```

The Visitor doesn't control traversal — the composite structure does. The visitor only defines what to do at each node type. This separation allows the traversal order to change independently of the operations.

**Q9. How does TypeScript's type system help enforce Visitor exhaustiveness?**
A: TypeScript can enforce that a Visitor handles all element types at compile time, using discriminated unions as an alternative implementation:

```typescript
// Discriminated union — TypeScript's native way to encode the element hierarchy
type LoanUnion =
  | { kind: 'HOME_LOAN'; id: string; amount: number; ltv: number; isAffordable: boolean }
  | { kind: 'PERSONAL_LOAN'; id: string; amount: number; rate: number; tenor: number }
  | { kind: 'MSME_LOAN'; id: string; amount: number; gstin: string; collateral: string };

// Visitor as a function — TypeScript switch guarantees exhaustiveness
function applyVisitor<T>(loan: LoanUnion, visitor: {
  onHomeLoan: (loan: Extract<LoanUnion, { kind: 'HOME_LOAN' }>) => T;
  onPersonalLoan: (loan: Extract<LoanUnion, { kind: 'PERSONAL_LOAN' }>) => T;
  onMsmeLoan: (loan: Extract<LoanUnion, { kind: 'MSME_LOAN' }>) => T;
}): T {
  switch (loan.kind) {
    case 'HOME_LOAN': return visitor.onHomeLoan(loan);
    case 'PERSONAL_LOAN': return visitor.onPersonalLoan(loan);
    case 'MSME_LOAN': return visitor.onMsmeLoan(loan);
    default: {
      const _exhaustive: never = loan; // compile error if a case is missing
      throw new Error(`Unhandled loan type: ${JSON.stringify(_exhaustive)}`);
    }
  }
}

// Usage — TypeScript errors if any loan kind is unhandled
const provisioning = applyVisitor(loan, {
  onHomeLoan: (l) => l.ltv > 80 ? l.amount * 0.015 : l.amount * 0.010,
  onPersonalLoan: (l) => l.amount * 0.04,
  onMsmeLoan: (l) => l.collateral === 'NONE' ? l.amount * 0.04 : l.amount * 0.02,
});
```

When a new loan type (`GOLD_LOAN`) is added to the union, TypeScript immediately errors at every `applyVisitor` call site that doesn't handle it — compile-time safety that the traditional OOP Visitor pattern achieves only at runtime (when the new `visitGoldLoan` method is missing from existing visitors).

## Section 3: Visitor in Real-World Fintech Contexts

**Q10. How would you use Visitor for RBI regulatory reporting across a heterogeneous loan portfolio?**
A: RBI mandates different reporting requirements per loan category — Priority Sector Lending (PSL) classification, LTV reporting for secured loans, asset classification for NPA computation. A single Visitor traverses the portfolio and generates the correct report entry per loan type:

```typescript
class PslClassificationVisitor implements LoanVisitor {
  private readonly pslBuckets: Record<string, number> = {
    AGRICULTURE: 0, MSME: 0, HOUSING_AFFORDABLE: 0, EDUCATION: 0, OTHER: 0,
  };

  visitHomeLoan(loan: HomeLoan): void {
    if (loan.isAffordableHousing && loan.amount <= 3_500_000) {
      // PMAY — affordable housing qualifies as PSL
      this.pslBuckets['HOUSING_AFFORDABLE'] += loan.amount;
    }
    // Standard home loans: NOT PSL — no entry
  }

  visitPersonalLoan(loan: PersonalLoan): void {
    if (loan.purpose === 'EDUCATION' && loan.amount <= 2_000_000) {
      // Education loans up to ₹20L — PSL
      this.pslBuckets['EDUCATION'] += loan.amount;
    }
    // Other personal loans: NOT PSL
  }

  visitMsmeLoan(loan: MsmeLoan): void {
    // All MSME loans qualify as PSL
    this.pslBuckets['MSME'] += loan.amount;
  }

  visitAgricultureLoan(loan: AgricultureLoan): void {
    this.pslBuckets['AGRICULTURE'] += loan.amount;
  }

  getPslReport(): PslReport {
    const total = Object.values(this.pslBuckets).reduce((a, b) => a + b, 0);
    const adjustedNetBankCredit = this.calculateAdjustedNetBankCredit();
    return {
      buckets: this.pslBuckets,
      totalPsl: total,
      pslPercentage: (total / adjustedNetBankCredit) * 100,
      rbiTarget: 40, // RBI mandates 40% PSL of ANBC
      compliant: (total / adjustedNetBankCredit) >= 0.40,
    };
  }
}
```

**Q11. How would you use Visitor for ECL (Expected Credit Loss) provisioning under Ind AS 109?**
A: ECL computation under Ind AS 109 (India's IFRS 9 equivalent) requires computing Stage 1/2/3 provisions differently for each loan type based on collateral, LTV, and credit quality. Visitor encapsulates each asset class's ECL formula in one place:

```typescript
interface EclStage {
  stage: 1 | 2 | 3;
  dpd: number;
}

class EclProvisioningVisitor implements LoanVisitor {
  private provisions: EclEntry[] = [];

  visitHomeLoan(loan: HomeLoan): void {
    const { stage } = this.classifyStage(loan.dpd);
    const lgd = 1 - Math.min(loan.propertyValue * 0.9 / loan.amount, 1); // LGD from collateral
    const pd = this.pdTable['HOME_LOAN'][stage];
    const ead = loan.outstandingPrincipal;

    this.provisions.push({
      loanId: loan.id,
      stage,
      provision: pd * lgd * ead,
      method: 'COLLATERAL_ADJUSTED',
    });
  }

  visitPersonalLoan(loan: PersonalLoan): void {
    const { stage } = this.classifyStage(loan.dpd);
    const pd = this.pdTable['PERSONAL_LOAN'][stage];
    const lgd = 0.85; // unsecured — high LGD
    const ead = loan.outstandingPrincipal;

    this.provisions.push({
      loanId: loan.id,
      stage,
      provision: pd * lgd * ead,
      method: 'UNSECURED_STANDARD',
    });
  }

  visitMsmeLoan(loan: MsmeLoan): void {
    const { stage } = this.classifyStage(loan.dpd);
    const collateralCoverage = loan.collateralValue / loan.outstandingPrincipal;
    const lgd = collateralCoverage >= 1 ? 0.25 : 0.65; // binary LGD by collateral coverage
    const pd = this.pdTable['MSME'][stage];

    this.provisions.push({
      loanId: loan.id,
      stage,
      provision: pd * lgd * loan.outstandingPrincipal,
      method: 'MSME_COLLATERAL',
    });
  }

  private classifyStage(dpd: number): EclStage {
    if (dpd === 0) return { stage: 1, dpd };
    if (dpd <= 90) return { stage: 2, dpd };
    return { stage: 3, dpd };
  }

  getTotalProvision(): number {
    return this.provisions.reduce((sum, e) => sum + e.provision, 0);
  }
  getProvisionsByStage(): Record<1 | 2 | 3, number> { /* group and sum */ }
}
```

**Q12. How would you use Visitor to generate multiple export formats from a loan application object graph?**
A: Loan data must be exported in different formats — JSON for API responses, XML for bureau submission, PDF for customer-facing documents, CSV for internal reporting. Each format is a Visitor:

```typescript
interface ApplicationElement {
  accept(visitor: ApplicationExportVisitor): void;
}

interface ApplicationExportVisitor {
  visitApplicantProfile(profile: ApplicantProfile): void;
  visitEmploymentDetails(emp: EmploymentDetails): void;
  visitLoanRequest(req: LoanRequestDetails): void;
  visitDocument(doc: SubmittedDocument): void;
  visitBureauReport(bureau: BureauReportSummary): void;
}

// XML export — for CERSAI/bureau submission
class XmlExportVisitor implements ApplicationExportVisitor {
  private xml = new XMLBuilder();

  visitApplicantProfile(profile: ApplicantProfile): void {
    this.xml.startElement('Applicant')
      .addAttribute('PAN', profile.pan)
      .addElement('Name', profile.name)
      .addElement('DOB', profile.dob.toISOString().split('T')[0])
      .addElement('Gender', profile.gender)
      .endElement();
  }

  visitEmploymentDetails(emp: EmploymentDetails): void {
    this.xml.startElement('Employment')
      .addElement('Type', emp.type)
      .addElement('Employer', emp.employerName)
      .addElement('MonthlyIncome', emp.monthlyIncome.toString())
      .addElement('VintageMonths', emp.vintageMonths.toString())
      .endElement();
  }

  visitLoanRequest(req: LoanRequestDetails): void {
    this.xml.startElement('LoanDetails')
      .addElement('Amount', req.amount.toString())
      .addElement('Tenor', req.tenorMonths.toString())
      .addElement('Product', req.productCode)
      .endElement();
  }

  visitDocument(doc: SubmittedDocument): void {
    // XML export only references documents by type/ID — no file content
    this.xml.startElement('Document')
      .addAttribute('type', doc.type)
      .addElement('DocumentId', doc.id)
      .addElement('VerificationStatus', doc.status)
      .endElement();
  }

  visitBureauReport(bureau: BureauReportSummary): void {
    this.xml.startElement('CreditInfo')
      .addElement('Score', bureau.score.toString())
      .addElement('ActiveAccounts', bureau.activeAccounts.toString())
      .endElement();
  }

  getXml(): string { return this.xml.build(); }
}

// CSV export — for internal ops dashboard
class CsvExportVisitor implements ApplicationExportVisitor {
```

**Q13. How would you use Visitor to implement a loan fee calculator across multiple fee types and loan products?**
A: Fee structures vary by both loan type and fee category (processing fee, prepayment penalty, late payment charge). Visitor can model this cleanly as a two-dimensional grid:

```typescript
interface FeeElement {
  accept(visitor: FeeCalculatorVisitor): number; // returns fee amount
}

interface FeeCalculatorVisitor {
  visitProcessingFee(loan: HomeLoan | PersonalLoan | MsmeLoan): number;
  visitPrepaymentPenalty(loan: HomeLoan | PersonalLoan | MsmeLoan, prepayAmount: number): number;
  visitLatePenalty(loan: HomeLoan | PersonalLoan | MsmeLoan, daysLate: number): number;
}

// Processing fee schedule — each loan type has different rates
class ProcessingFeeVisitor implements LoanVisitor<number> {
  visitHomeLoan(loan: HomeLoan): number {
    // Home loans: 0.5% of loan, max ₹25,000, waived for PMAY
    if (loan.isAffordableHousing) return 0;
    return Math.min(loan.amount * 0.005, 25_000);
  }

  visitPersonalLoan(loan: PersonalLoan): number {
    // Personal loans: 2% + 18% GST
    const fee = loan.amount * 0.02;
    return fee + fee * 0.18;
  }

  visitMsmeLoan(loan: MsmeLoan): number {
    // MSME: CGTMSE guarantee fee + processing fee
    const processingFee = loan.amount * 0.01;
    const cgtmseFee = loan.amount * 0.015; // CGTMSE annual guarantee fee
    return processingFee + cgtmseFee;
  }
}

// Prepayment penalty — RBI guidelines differ per loan type
class PrepaymentPenaltyVisitor implements LoanVisitor<number> {
  constructor(private readonly prepayAmount: number) {}

  visitHomeLoan(_loan: HomeLoan): number {
    // RBI: floating rate home loans — no prepayment penalty for individuals
    return 0;
  }

  visitPersonalLoan(_loan: PersonalLoan): number {
    // Fixed rate personal loans: 2% of prepayment amount within lock-in
    return this.prepayAmount * 0.02;
  }

  visitMsmeLoan(loan: MsmeLoan): number {
    // MSME: 1% of prepayment after 12 months
    return loan.tenorCompletedMonths > 12 ? this.prepayAmount * 0.01 : this.prepayAmount * 0.02;
  }
}
```

**Q16. How do you test that all element types are handled by a new Visitor at compile time?**
A: TypeScript enforces this if the visitor interface is well-typed. If you add a `visitGoldLoan` method to `LoanVisitor` without implementing it in `EclProvisioningVisitor`, TypeScript errors immediately:

```typescript
// After adding GoldLoan to the hierarchy:
interface LoanVisitor {
  visitHomeLoan(loan: HomeLoan): void;
  visitPersonalLoan(loan: PersonalLoan): void;
  visitMsmeLoan(loan: MsmeLoan): void;
  visitGoldLoan(loan: GoldLoan): void;  // ← added
}

// TypeScript now errors on every class that implements LoanVisitor
// without visitGoldLoan — compile-time exhaustiveness
class EclProvisioningVisitor implements LoanVisitor {
  // ERROR: Property 'visitGoldLoan' is missing in type 'EclProvisioningVisitor'
  // but required in type 'LoanVisitor'
}
```

This is the TypeScript Visitor's key advantage over runtime-only OOP dispatch — you can't accidentally deploy a visitor that silently ignores a new element type.

## Section 5: Anti-patterns & Pitfalls

**Q17. What are the most common mistakes when implementing the Visitor pattern?**
A:

- **Using Visitor when the hierarchy isn't stable** — if new element types are added frequently (new loan products every quarter), every new type requires updating every existing visitor. This is Visitor's core weakness. If you have 8 visitors and add a new loan type, you must update 8 files. Consider discriminated unions + exhaustiveness checking as an alternative.
- **Putting traversal logic in the visitor** — the visitor should define *what to do at each node*, not *how to traverse*. Traversal (walking children, iterating collections) belongs in the `accept` methods of composite elements. A visitor that knows the internal structure of elements to walk them manually is over-coupled.
- **Visitor that breaks encapsulation** — since `accept()` passes `this` to the visitor, the visitor accesses all public fields of the element. This is intentional — the visitor needs the element's data. But it means elements should expose the data the visitor needs as public properties. Using `private` fields that visitors then access via getters creates awkward APIs. Design elements with visitor access in mind.
- **Accumulating mutable state across visitors** — if you run multiple visitors on the same portfolio (reporter, provisioner, auditor) and they share mutable state through a shared context, you've coupled independent operations. Each visitor should maintain its own isolated state.
- **Not implementing all visit methods** — in a dynamically typed language (JavaScript pre-TypeScript), forgetting to implement one `visit` method means that element type silently does nothing. Always use TypeScript's interface enforcement to catch missing implementations at compile time.
- **Using Visitor for a single element type** — if the `LoanVisitor` interface has only `visitLoan()` and all loans are the same class, there's no double dispatch benefit. Strategy is simpler. Visitor earns its complexity only when you have a genuine *heterogeneous* structure of multiple concrete types.

**Q18. When should you use a discriminated union + switch instead of the classical OOP Visitor?**
A: For TypeScript/JavaScript codebases, discriminated unions with exhaustiveness checking are often cleaner and more idiomatic than classical OOP Visitor:

**Use classical OOP Visitor when:**
- Element types are *classes* with methods and behaviour (not just data shapes).
- You need to pass visitors across module boundaries (the visitor is a first-class object passed around).
- The structure is a tree/composite that controls its own traversal.
- You want polymorphic behaviour (visitors can be swapped at runtime without changing call sites).

**Use discriminated union + switch when:**
- Elements are primarily *data containers* (DTOs, value objects, plain objects).
- Operations are co-located with the data (same module/file).
- You want TypeScript's native exhaustiveness checking without the `accept`/`visit` ceremony.
- The hierarchy is small and the indirection of double dispatch adds more complexity than it solves.

```typescript
// Discriminated union — idiomatic TypeScript, no accept/visit boilerplate
type LoanType =
  | { kind: 'HOME'; amount: number; ltv: number; isAffordable: boolean }
  | { kind: 'PERSONAL'; amount: number; rate: number }
  | { kind: 'MSME'; amount: number; gstin: string };

function calculateProvision(loan: LoanType): number {
  switch (loan.kind) {
    case 'HOME': return loan.ltv > 80 ? loan.amount * 0.015 : loan.amount * 0.010;
    case 'PERSONAL': return loan.amount * 0.04;
    case 'MSME': return loan.amount * 0.02;
    // TypeScript errors here if a case is missing — exhaustiveness built in
  }
}
```

## Section 6: Scenario / System Design Questions

**Q19. "Your fintech platform needs to generate four different regulatory reports (RBI Basic Statistical Return, PSL classification, NPA return, CERSAI filing) from the same loan portfolio. Each report needs different fields and calculations per loan type. How do you design this?"**
A: Four Visitor classes — one per report — applied to the same portfolio:

```typescript
// Each report is one Visitor; the portfolio is traversed once per report (or once total)
const portfolio: Loan[] = await loanRepo.findAllActive();

const bsrVisitor = new RbiBsrVisitor();          // RBI Basic Statistical Return
const pslVisitor = new PslClassificationVisitor(); // Priority Sector Lending
const npaVisitor = new NpaReturnVisitor();         // NPA classification
const cersaiVisitor = new CersaiFilingVisitor();   // CERSAI mortgage registration

// Single traversal — apply all visitors in one pass (performance optimisation)
for (const loan of portfolio) {
  loan.accept(bsrVisitor);
  loan.accept(pslVisitor);
  loan.accept(npaVisitor);
  loan.accept(cersaiVisitor);
}

// Each visitor independently generates its report
await submitToRbi(bsrVisitor.getReport());
await submitPslReturn(pslVisitor.getPslReport());
await submitNpaReturn(npaVisitor.getNpaReturn());
await submitToCersai(cersaiVisitor.getCersaiPayload());
```

When RBI introduces a fifth return next year, write one new Visitor class — zero changes to `HomeLoan`, `PersonalLoan`, `MsmeLoan`, or the portfolio traversal loop.

**Q20. "A compliance audit reveals that your provisioning calculation for MSME loans has been wrong for six months. How does having a Visitor-based provisioning system make the fix safer compared to having the logic embedded in each loan class?"**
A: The Visitor pattern localises the fix to a single class:

**With Visitor:**
- The bug is in `EclProvisioningVisitor.visitMsmeLoan()` — one method, one class.
- Fix it, write a regression test for `visitMsmeLoan()`, deploy.
- `HomeLoan`, `PersonalLoan`, and `MsmeLoan` classes are untouched — no risk of regression on working loan types.
- Historical recalculation: instantiate the fixed visitor, run it against the last 6 months of MSME loans — the corrected figures are computed without touching any loan data.

**Without Visitor (logic embedded in MsmeLoan.calculateProvision()):**
- Fix is in `MsmeLoan` — but now every test for `MsmeLoan` must be re-run, including tests for unrelated methods (eligibility, repayment schedule, KYC).
- Risk of merge conflicts if `MsmeLoan` was also being worked on for another feature.
- Recomputation requires instantiating `MsmeLoan` objects for historical data that may have changed shape since origination.

The Visitor's separation of element structure from operation means **bugs in operations are isolated to Visitor classes, not spread across element classes**. This is the audit/compliance scenario where Visitor's design pays off concretely.

**Q21. "You're building a loan document processing pipeline. Uploaded documents can be Aadhaar cards, PAN cards, income proofs, bank statements, or property documents — each requires different OCR fields, validation rules, and storage routing. How do you use Visitor here?"**
A: Each document type is an element; each processing concern (OCR field extraction, validation, storage routing) is a Visitor:

```typescript
interface KycDocument {
  documentId: string;
  fileUrl: string;
  accept(visitor: DocumentProcessingVisitor): void;
}

interface DocumentProcessingVisitor {
  visitAadhaar(doc: AadhaarDocument): void;
  visitPan(doc: PanDocument): void;
  visitIncomeProof(doc: IncomeProofDocument): void;
  visitBankStatement(doc: BankStatementDocument): void;
  visitPropertyDoc(doc: PropertyDocument): void;
}

// OCR Visitor — extracts different fields per document type
class OcrExtractionVisitor implements DocumentProcessingVisitor {
  visitAadhaar(doc: AadhaarDocument): void {
    // Extract: name, DOB, address, aadhaar number (last 4 unmasked)
    doc.extractedData = this.ocr.extract(doc.fileUrl, {
      fields: ['name', 'dob', 'address', 'uid_last4'],
      template: 'AADHAAR_TEMPLATE_V3',
    });
  }

  visitPan(doc: PanDocument): void {
    // Extract: name, DOB, PAN number, father's name
    doc.extractedData = this.ocr.extract(doc.fileUrl, {
      fields: ['name', 'dob', 'pan_number', 'fathers_name'],
      template: 'PAN_TEMPLATE_V2',
    });
  }

  visitBankStatement(doc: BankStatementDocument): void {
    // Extract: account number, IFSC, transactions table, average balance
    doc.extractedData = this.ocr.extract(doc.fileUrl, {
      fields: ['account_no', 'ifsc', 'transactions', 'avg_balance_6m'],
      template: 'BANK_STATEMENT_GENERIC',
      multiPage: true,
    });
  }

  visitIncomeProof(doc: IncomeProofDocument): void { /* salary slip fields */ }
  visitPropertyDoc(doc: PropertyDocument): void { /* property details */ }
}

// Storage routing Visitor — different buckets/retention per document type
class StorageRoutingVisitor implements DocumentProcessingVisitor {
  visitAadhaar(doc: AadhaarDocument): void {
    // Aadhaar: encrypted storage, 7-year retention, India-only (data localisation)
    this.storage.store(doc, { bucket: 'kyc-sensitive', encrypt: true, retentionYears: 7, region: 'ap-south-1' });
  }

  visitBankStatement(doc: BankStatementDocument): void {
    // Bank statements: 7 years financial records retention
    this.storage.store(doc, { bucket: 'financial-docs', encrypt: true, retentionYears: 7 });
  }

  visitPropertyDoc(doc: PropertyDocument): void {
    // Property docs: 30 years (loan term + tail)
    this.storage.store(doc, { bucket: 'collateral-docs', encrypt: false, retentionYears: 30 });
  }

  visitPan(doc: PanDocument): void { /* ... */ }
  visitIncomeProof(doc: IncomeProofDocument): void { /* ... */ }
}
```

Adding a new document type (e.g., `UdyamCertificate` for MSME loans) means: add the class, add `visitUdyamCertificate` to the visitor interface, implement in each existing visitor. TypeScript immediately flags every visitor that doesn't handle it — no silent gaps in processing.

## Quick Reference: Visitor Pattern Checklist

| Signal                                                                         | What to Do                                                                    |
|--------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| Need to add many operations to a fixed set of element types                    | Visitor — each operation is one Visitor class; elements untouched             |
| Adding a new operation requires touching every element class                   | Extract to Visitor — the operation becomes one class                          |
| Element hierarchy changes frequently (new types added often)                   | Reconsider Visitor — it makes adding new types expensive; use discriminated union |
| `instanceof` checks scattered across operation methods                         | Replace with Visitor + double dispatch — type-safe, no casting                |
| Multiple reports/exports needed from the same object graph                     | One Visitor per report — apply multiple visitors in a single traversal pass   |
| Discriminated unions with TypeScript — stateless, data-only elements           | Use switch + exhaustiveness check (`never`) instead of classical Visitor      |
| A bug in one operation type (e.g., MSME provisioning) is risky to fix         | Visitor localises the fix to one method in one class — minimal blast radius   |
| New regulatory requirement needs a new report from existing loan data          | New Visitor class — zero changes to any element class or existing visitors    |

**Tip for the interview:** At the 5 YOE level, Visitor is one of the harder patterns to be asked about — but in a fintech domain it's highly relevant. Interviewers won't ask you to recite it; they'll describe a regulatory reporting problem ("we need three new RBI returns from the same loan portfolio") or a compliance scenario ("our provisioning calculation was wrong for MSME loans — how do we fix and audit it safely?"). The answer is Visitor. The differentiating answer explains **double dispatch** clearly (why `loan.accept(visitor)` instead of just `visitor.process(loan)` — the runtime type of `loan` resolves which `visit` method is called), names the **trade-off** (easy to add operations, hard to add element types), and connects it to **TypeScript's discriminated unions** as the idiomatic alternative when elements are data-only. In a fintech context, the PSL classification, ECL provisioning, and multi-format export scenarios are real problems every lending platform faces — having a concrete story for one of them lands at the senior level.
