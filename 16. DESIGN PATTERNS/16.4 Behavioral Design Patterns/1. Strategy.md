# Behavioral Design Patterns: Strategy — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Strategy pattern?**
A: Strategy is a behavioral design pattern that defines a **family of algorithms**, encapsulates each one in its own class, and makes them **interchangeable at runtime** through a common interface. The object that uses a strategy (the "Context") holds a reference to a strategy interface — not a concrete implementation — and delegates the variable part of its behaviour to whichever strategy is currently set. The Context doesn't know or care which strategy it's using; it just calls the interface.

The three roles in every Strategy implementation:
- **Strategy interface** — the contract all algorithm variants implement (e.g., `EligibilityStrategy`, `InterestRateStrategy`).
- **Concrete Strategies** — individual algorithm implementations, each encapsulating one variant (e.g., `SalariedEligibilityStrategy`, `SelfEmployedEligibilityStrategy`).
- **Context** — the object that owns a reference to the current strategy and delegates to it. The context is the stable part; the strategy is the variable part.

**Q2. What problem does Strategy solve? When should you reach for it?**
A: Strategy solves the **conditional branching explosion** problem — when a class has a method that does fundamentally different things based on a type, flag, or enum, and the number of variants keeps growing:

```typescript
// ❌ What Strategy replaces — fragile, closed, growing
class LoanEligibilityService {
  assess(applicant: Applicant): boolean {
    if (applicant.employmentType === 'SALARIED') {
      // 15 lines of salaried logic
    } else if (applicant.employmentType === 'SELF_EMPLOYED') {
      // 20 lines of self-employed logic
    } else if (applicant.employmentType === 'NRI') {
      // 18 lines of NRI logic
    } else if (applicant.employmentType === 'MSME') {
      // 25 lines of MSME logic — added last sprint
    }
    // Next sprint: FARMER, GIG_WORKER...
  }
}
```

Every new variant requires touching a working, tested class — violating OCP. Testing requires exercising the entire method for each path. Reach for Strategy when:
- A class has multiple **variants of an algorithm** selected by a type or flag.
- Variants need to be **swappable at runtime** — selected based on input data, config, or feature flags.
- Each variant has **non-trivial logic** that deserves its own class and test suite.
- You anticipate **adding new variants** over time (open for extension, closed for modification).
- You want to **test each variant in complete isolation**.

**Q3. What is the difference between Strategy and a simple `if/else` or `switch` statement?**
A: A `switch` is an inline algorithm selector — all variants live in one method, the selector is hardcoded, and adding a variant means modifying the method. Strategy externalises the selection:

| Aspect                    | `switch` / `if-else`                                | Strategy                                              |
|---------------------------|-----------------------------------------------------|-------------------------------------------------------|
| Adding a new variant      | Modify existing method — OCP violation              | Add a new class — existing code untouched             |
| Testing each variant      | Must exercise the whole method with different inputs | Each strategy class tested independently              |
| Selecting the algorithm   | Hardcoded inside the method                         | Resolved externally — via factory, DI, or config      |
| Runtime swapping          | Hard — need to refactor the branch                  | Natural — swap the strategy reference                 |
| SRP compliance            | One method has N responsibilities                   | One class per responsibility                          |

The heuristic: if the `switch` has two cases and will never grow, keep it inline. If it has four or more cases, is growing, or each branch has significant logic — Strategy is the right move.

**Q4. How does Strategy differ from State, Template Method, and Command?**
A: All four deal with variable behaviour, but with different mechanics and intents:

| Pattern            | Who holds the variant?        | What changes?                                | Key difference                                              |
|--------------------|-------------------------------|----------------------------------------------|-------------------------------------------------------------|
| **Strategy**       | Context holds a strategy ref  | Algorithm / computation                      | Context delegates to strategy; context doesn't change       |
| **State**          | Context holds a state ref     | Context's *own behaviour* based on lifecycle | State transitions happen inside the state objects themselves |
| **Template Method**| Subclass overrides steps      | One or more steps of a fixed algorithm       | Skeleton in base class; uses inheritance, not composition   |
| **Command**        | Invoker holds command objects | An *action* to be executed, possibly queued  | Commands are objects encapsulating an operation + its params |

The sharpest distinction: **Strategy vs Template Method** — both vary an algorithm, but Template Method uses inheritance (subclass fills in steps), Strategy uses composition (inject the algorithm object). Favour Strategy — composition is more flexible and testable than inheritance.

**Q5. Is Strategy the same as dependency injection?**
A: They're related but not identical. DI is a mechanism for supplying dependencies to an object from outside; Strategy is a design pattern with specific intent — making an algorithm interchangeable. Strategy *uses* DI as its preferred delivery mechanism (inject the strategy through the constructor), but DI is broader. You can inject a repository, a logger, or a config service via DI — none of those are strategies. The distinguishing mark of Strategy: the injected object is chosen from a **family of interchangeable algorithm implementations** all conforming to the same interface, and the Context treats them as equivalent alternatives.

## Section 2: Implementation

**Q6. What does a canonical TypeScript Strategy implementation look like?**
A:

```typescript
// Strategy interface — the contract all variants implement
interface EligibilityStrategy {
  assess(applicant: Applicant): EligibilityResult;
}

interface EligibilityResult {
  eligible: boolean;
  maxLoanAmount: number;
  reasons: string[];
}

// Concrete Strategy 1 — salaried applicants
@Injectable()
export class SalariedEligibilityStrategy implements EligibilityStrategy {
  assess(applicant: Applicant): EligibilityResult {
    const reasons: string[] = [];

    if (applicant.cibilScore < 700) reasons.push('CIBIL score below 700');
    if (applicant.monthlyIncome < 25000) reasons.push('Monthly income below ₹25,000');
    if (applicant.employmentTenureMonths < 6) reasons.push('Employment tenure below 6 months');

    const eligible = reasons.length === 0;
    const maxLoanAmount = eligible ? applicant.monthlyIncome * 60 : 0; // 5-year EMI cap

    return { eligible, maxLoanAmount, reasons };
  }
}

// Concrete Strategy 2 — self-employed applicants
@Injectable()
export class SelfEmployedEligibilityStrategy implements EligibilityStrategy {
  assess(applicant: Applicant): EligibilityResult {
    const reasons: string[] = [];

    if (applicant.cibilScore < 680) reasons.push('CIBIL score below 680');
    if (applicant.itrAnnualIncome < 300000) reasons.push('ITR income below ₹3L p.a.');
    if (applicant.businessVintagYears < 2) reasons.push('Business vintage below 2 years');
    if (!applicant.gstRegistered) reasons.push('GST registration required');

    const eligible = reasons.length === 0;
    const maxLoanAmount = eligible ? (applicant.itrAnnualIncome / 12) * 48 : 0;

    return { eligible, maxLoanAmount, reasons };
  }
}

// Concrete Strategy 3 — NRI applicants
@Injectable()
export class NriEligibilityStrategy implements EligibilityStrategy {
  assess(applicant: Applicant): EligibilityResult {
    const reasons: string[] = [];

    if (applicant.cibilScore < 720) reasons.push('CIBIL score below 720 for NRI');
    if (!applicant.nreAccountVerified) reasons.push('NRE account not verified');
    if (applicant.overseasEmploymentYears < 1) reasons.push('Overseas employment below 1 year');

    const eligible = reasons.length === 0;
    const maxLoanAmount = eligible ? applicant.monthlyIncome * 48 : 0; // lower multiplier for NRI

    return { eligible, maxLoanAmount, reasons };
  }
}

// Context — stable, delegates the variable part
@Injectable()
export class LoanEligibilityService {
  constructor(private readonly strategy: EligibilityStrategy) {}

  assess(applicant: Applicant): EligibilityResult {
    return this.strategy.assess(applicant);
  }
}
```

**Q7. How do you select and inject the right strategy at runtime in a NestJS application?**
A: Use a factory that maps the discriminating field to its strategy, then inject via the DI container:

```typescript
// Strategy factory — maps employment type → strategy
@Injectable()
export class EligibilityStrategyFactory {
  constructor(
    private readonly salaried: SalariedEligibilityStrategy,
    private readonly selfEmployed: SelfEmployedEligibilityStrategy,
    private readonly nri: NriEligibilityStrategy,
  ) {}

  for(employmentType: EmploymentType): EligibilityStrategy {
    const strategies: Record<EmploymentType, EligibilityStrategy> = {
      SALARIED: this.salaried,
      SELF_EMPLOYED: this.selfEmployed,
      NRI: this.nri,
    };

    const strategy = strategies[employmentType];
    if (!strategy) throw new BadRequestException(`No eligibility strategy for: ${employmentType}`);
    return strategy;
  }
}

// Eligibility service uses the factory to select per-request
@Injectable()
export class LoanEligibilityService {
  constructor(private readonly strategyFactory: EligibilityStrategyFactory) {}

  assess(applicant: Applicant): EligibilityResult {
    const strategy = this.strategyFactory.for(applicant.employmentType);
    return strategy.assess(applicant);
  }
}
```

```typescript
// Module wiring — all strategies registered as providers
@Module({
  providers: [
    SalariedEligibilityStrategy,
    SelfEmployedEligibilityStrategy,
    NriEligibilityStrategy,
    EligibilityStrategyFactory,
    LoanEligibilityService,
  ],
  exports: [LoanEligibilityService],
})
export class EligibilityModule {}
```

Adding a new employment type (e.g., `GIG_WORKER`) now means: write `GigWorkerEligibilityStrategy`, register it in the module, add it to the factory's map — zero changes to `LoanEligibilityService`.

**Q8. How do you implement a Strategy registry pattern for more dynamic or config-driven selection?**
A: Instead of a hardcoded factory map, use a self-registering registry — each strategy declares the key it handles:

```typescript
// Discriminator — strategy declares what it handles
interface EligibilityStrategy {
  readonly employmentType: EmploymentType; // self-identifying key
  assess(applicant: Applicant): EligibilityResult;
}

// Registry — collects all strategies at bootstrap via DI injection token
const ELIGIBILITY_STRATEGIES = 'ELIGIBILITY_STRATEGIES';

@Injectable()
export class EligibilityStrategyRegistry {
  private readonly registry = new Map<EmploymentType, EligibilityStrategy>();

  constructor(
    @Inject(ELIGIBILITY_STRATEGIES) strategies: EligibilityStrategy[],
  ) {
    for (const strategy of strategies) {
      this.registry.set(strategy.employmentType, strategy);
    }
  }

  for(type: EmploymentType): EligibilityStrategy {
    const strategy = this.registry.get(type);
    if (!strategy) throw new BadRequestException(`No strategy for: ${type}`);
    return strategy;
  }
}

// Module — multi-provider injection collects all strategies into an array
@Module({
  providers: [
    { provide: ELIGIBILITY_STRATEGIES, useClass: SalariedEligibilityStrategy, multi: true },
    { provide: ELIGIBILITY_STRATEGIES, useClass: SelfEmployedEligibilityStrategy, multi: true },
    { provide: ELIGIBILITY_STRATEGIES, useClass: NriEligibilityStrategy, multi: true },
    EligibilityStrategyRegistry,
    LoanEligibilityService,
  ],
})
export class EligibilityModule {}
```

This is the most scalable approach — adding a new strategy requires only registering it in the module. The registry and service are completely unaware of the new variant until it appears in the injected array.

**Q9. How do you implement a Strategy that is selected based on runtime data, not just a type field?**
A: Some strategy selection logic is conditional on multiple fields or business rules — use a predicate-based selector:

```typescript
interface EligibilityStrategy {
  canHandle(applicant: Applicant): boolean; // predicate — does this strategy apply?
  assess(applicant: Applicant): EligibilityResult;
  readonly priority: number; // resolve ambiguity when multiple strategies match
}

@Injectable()
export class AffiliatePartnerEligibilityStrategy implements EligibilityStrategy {
  readonly priority = 10; // higher priority — checked before generic strategies

  canHandle(applicant: Applicant): boolean {
    // Applies when applicant came via an affiliate partner with a pre-approved offer
    return applicant.sourceChannel === 'AFFILIATE' && applicant.preApprovedOfferId != null;
  }

  assess(applicant: Applicant): EligibilityResult {
    // Pre-approved — relaxed rules, fixed offer amount
    return { eligible: true, maxLoanAmount: applicant.preApprovedOfferAmount!, reasons: [] };
  }
}

@Injectable()
export class EligibilityStrategySelector {
  constructor(
    @Inject(ELIGIBILITY_STRATEGIES) private readonly strategies: EligibilityStrategy[],
  ) {
    // Sort by descending priority at construction time
    this.strategies.sort((a, b) => b.priority - a.priority);
  }

  select(applicant: Applicant): EligibilityStrategy {
    const match = this.strategies.find(s => s.canHandle(applicant));
    if (!match) throw new BadRequestException('No eligible strategy found for applicant');
    return match;
  }
}
```

This is the **Chain-of-Responsibility meets Strategy** pattern — commonly needed in fintech where special-case rules (partner pre-approvals, government scheme eligibility, whitelist applicants) need to take precedence over standard rules without polluting the standard strategies.

## Section 3: Strategy in Real-World Fintech Contexts

**Q10. How would you use Strategy for interest rate calculation across different loan products?**
A: Interest rate is one of the most variant-heavy calculations in a lending system — flat vs reducing, fixed vs floating, product-specific overrides, promotional rates:

```typescript
interface InterestRateStrategy {
  calculate(principal: number, ratePercent: number, tenorMonths: number): AmortizationSchedule;
}

interface AmortizationSchedule {
  emi: number;
  totalInterest: number;
  schedule: { month: number; principal: number; interest: number; balance: number }[];
}

// Reducing balance — standard home/personal loans
@Injectable()
export class ReducingBalanceStrategy implements InterestRateStrategy {
  calculate(principal: number, ratePercent: number, tenorMonths: number): AmortizationSchedule {
    const monthlyRate = ratePercent / 12 / 100;
    const emi = (principal * monthlyRate * (1 + monthlyRate) ** tenorMonths)
              / ((1 + monthlyRate) ** tenorMonths - 1);

    let balance = principal;
    const schedule = Array.from({ length: tenorMonths }, (_, i) => {
      const interest = balance * monthlyRate;
      const principalPart = emi - interest;
      balance -= principalPart;
      return { month: i + 1, principal: principalPart, interest, balance: Math.max(0, balance) };
    });

    return { emi, totalInterest: emi * tenorMonths - principal, schedule };
  }
}

// Flat rate — used in some MSME and two-wheeler loans
@Injectable()
export class FlatRateStrategy implements InterestRateStrategy {
  calculate(principal: number, ratePercent: number, tenorMonths: number): AmortizationSchedule {
    const totalInterest = principal * (ratePercent / 100) * (tenorMonths / 12);
    const emi = (principal + totalInterest) / tenorMonths;

    const principalPerMonth = principal / tenorMonths;
    const interestPerMonth = totalInterest / tenorMonths;
    let balance = principal;
    const schedule = Array.from({ length: tenorMonths }, (_, i) => {
      balance -= principalPerMonth;
      return { month: i + 1, principal: principalPerMonth, interest: interestPerMonth, balance: Math.max(0, balance) };
    });

    return { emi, totalInterest, schedule };
  }
}

// Step-up EMI — for young professionals expecting income growth
@Injectable()
export class StepUpEmiStrategy implements InterestRateStrategy {
  calculate(principal: number, ratePercent: number, tenorMonths: number): AmortizationSchedule {
    // EMI increases by 5% every 12 months
    // Complex calculation omitted for brevity — same output shape
    return computeStepUpSchedule(principal, ratePercent, tenorMonths, 0.05);
  }
}

// Context — loan offer generator selects strategy by product
@Injectable()
export class LoanOfferService {
  constructor(private readonly strategyFactory: InterestRateStrategyFactory) {}

  generateOffer(product: LoanProduct, applicant: Applicant): LoanOffer {
    const strategy = this.strategyFactory.for(product.rateType);
    const schedule = strategy.calculate(
      applicant.requestedAmount,
      product.interestRate,
      applicant.requestedTenorMonths,
    );
    return { ...product, emi: schedule.emi, totalInterest: schedule.totalInterest, schedule };
  }
}
```

**Q11. How would you apply Strategy to EMI collection and delinquency handling logic?**
A: Collections strategy varies by days-past-due (DPD) bucket, loan product, and customer risk tier — a classic Strategy application:

```typescript
interface CollectionsStrategy {
  readonly dpd: DpdBucket; // which bucket this strategy handles
  execute(loan: DelinquentLoan): Promise<CollectionsAction>;
}

type DpdBucket = 'DPD_0_30' | 'DPD_31_60' | 'DPD_61_90' | 'DPD_90_PLUS';

// Early delinquency — soft touch, self-cure focus
@Injectable()
export class EarlyDelinquencyStrategy implements CollectionsStrategy {
  readonly dpd = 'DPD_0_30' as const;

  async execute(loan: DelinquentLoan): Promise<CollectionsAction> {
    return {
      actions: ['SEND_SMS_REMINDER', 'SEND_EMAIL', 'IVR_CALL'],
      escalate: false,
      writeOff: false,
      agentAssignment: null,
    };
  }
}

// Mid delinquency — agent outreach
@Injectable()
export class MidDelinquencyStrategy implements CollectionsStrategy {
  readonly dpd = 'DPD_31_60' as const;

  async execute(loan: DelinquentLoan): Promise<CollectionsAction> {
    return {
      actions: ['AGENT_OUTBOUND_CALL', 'FIELD_VISIT_SCHEDULE', 'LEGAL_NOTICE_WARNING'],
      escalate: true,
      writeOff: false,
      agentAssignment: await this.assignCollectionsAgent(loan),
    };
  }
}

// Severe delinquency — legal and write-off evaluation
@Injectable()
export class SevereDelinquencyStrategy implements CollectionsStrategy {
  readonly dpd = 'DPD_90_PLUS' as const;

  async execute(loan: DelinquentLoan): Promise<CollectionsAction> {
    const npaEligible = await this.checkNpaEligibility(loan);
    return {
      actions: ['LEGAL_NOTICE', 'SARFAESI_INITIATION', 'CREDIT_BUREAU_UPDATE'],
      escalate: true,
      writeOff: npaEligible,
      agentAssignment: await this.assignLegalTeam(loan),
    };
  }
}

// Context — collections engine selects strategy by DPD bucket
@Injectable()
export class CollectionsEngine {
  private readonly registry: Map<DpdBucket, CollectionsStrategy>;

  constructor(
    @Inject(COLLECTIONS_STRATEGIES) strategies: CollectionsStrategy[],
  ) {
    this.registry = new Map(strategies.map(s => [s.dpd, s]));
  }

  async processLoan(loan: DelinquentLoan): Promise<void> {
    const bucket = this.classifyDpdBucket(loan.daysPastDue);
    const strategy = this.registry.get(bucket)!;
    const action = await strategy.execute(loan);
    await this.applyAction(loan, action);
  }

  private classifyDpdBucket(dpd: number): DpdBucket {
    if (dpd <= 30) return 'DPD_0_30';
    if (dpd <= 60) return 'DPD_31_60';
    if (dpd <= 90) return 'DPD_61_90';
    return 'DPD_90_PLUS';
  }
}
```

**Q12. How would you use Strategy for KYC verification flow selection based on customer type and channel?**
A: KYC requirements differ significantly — retail vs MSME, online vs branch, resident vs NRI — and the verification steps, accepted document types, and bureau checks vary for each combination:

```typescript
interface KycVerificationStrategy {
  canHandle(context: KycContext): boolean;
  readonly priority: number;
  verify(applicant: Applicant, docs: SubmittedDocument[]): Promise<KycVerificationResult>;
}

interface KycContext {
  customerType: 'RETAIL' | 'MSME' | 'NRI';
  channel: 'ONLINE' | 'BRANCH' | 'DSA';
  productType: 'HOME_LOAN' | 'PERSONAL_LOAN' | 'MSME_LOAN';
}

// Video KYC — online retail customers for personal loans
@Injectable()
export class VideoKycStrategy implements KycVerificationStrategy {
  readonly priority = 20;

  canHandle(ctx: KycContext): boolean {
    return ctx.channel === 'ONLINE'
      && ctx.customerType === 'RETAIL'
      && ctx.productType === 'PERSONAL_LOAN';
  }

  async verify(applicant: Applicant, docs: SubmittedDocument[]): Promise<KycVerificationResult> {
    const aadhaarOk = await this.uidaiOtpVerification(applicant.aadhaar);
    const panOk = await this.panVerification(applicant.pan);
    const faceMatch = await this.videoSessionFaceMatch(applicant.id);
    return { verified: aadhaarOk && panOk && faceMatch, method: 'VIDEO_KYC', docs: [] };
  }
}

// Full KYC — MSME loans requiring physical document verification
@Injectable()
export class FullKycStrategy implements KycVerificationStrategy {
  readonly priority = 10;

  canHandle(ctx: KycContext): boolean {
    return ctx.productType === 'MSME_LOAN' || ctx.channel === 'BRANCH';
  }

  async verify(applicant: Applicant, docs: SubmittedDocument[]): Promise<KycVerificationResult> {
    const required = ['PAN', 'AADHAAR', 'GSTIN', 'UDYAM', 'BANK_STATEMENT'];
    const missing = required.filter(type => !docs.find(d => d.type === type));
    if (missing.length > 0) {
      return { verified: false, method: 'FULL_KYC', missingDocs: missing };
    }
    const allVerified = await Promise.all(docs.map(d => this.verifyDocument(d)));
    return { verified: allVerified.every(Boolean), method: 'FULL_KYC', docs };
  }
}
```

**Q13. How does Strategy apply to NACH debit retry policies in a collections system?**
A: Different retry policies apply based on failure reason — insufficient funds (retry at month-end salary credit) vs technical failure (retry immediately) vs mandate inactive (trigger re-registration):

```typescript
interface NachRetryStrategy {
  canHandle(failureCode: NachFailureCode): boolean;
  readonly priority: number;
  getRetrySchedule(loan: Loan, failedAt: Date): RetrySchedule;
}

interface RetrySchedule {
  shouldRetry: boolean;
  retryAt?: Date;
  maxRetries: number;
  notifyCustomer: boolean;
  action: 'RETRY' | 'RE_REGISTRATION' | 'ESCALATE' | 'ABANDON';
}

// Insufficient funds — retry around expected salary credit dates
@Injectable()
export class InsufficientFundsRetryStrategy implements NachRetryStrategy {
  readonly priority = 10;

  canHandle(code: NachFailureCode): boolean {
    return ['INSUFFICIENT_FUNDS', 'ACCOUNT_BALANCE_LOW'].includes(code);
  }

  getRetrySchedule(loan: Loan, failedAt: Date): RetrySchedule {
    // Retry on 1st, 5th, and 10th of next month — typical salary credit windows
    const nextRetry = this.nextSalaryCreditDate(failedAt);
    return {
      shouldRetry: true,
      retryAt: nextRetry,
      maxRetries: 3,
      notifyCustomer: true,
      action: 'RETRY',
    };
  }
}

// Technical failure — retry after short delay
@Injectable()
export class TechnicalFailureRetryStrategy implements NachRetryStrategy {
  readonly priority = 20;

  canHandle(code: NachFailureCode): boolean {
    return ['TIMEOUT', 'NETWORK_ERROR', 'GATEWAY_UNAVAILABLE'].includes(code);
  }

  getRetrySchedule(_loan: Loan, failedAt: Date): RetrySchedule {
    return {
      shouldRetry: true,
      retryAt: new Date(failedAt.getTime() + 2 * 60 * 60 * 1000), // 2 hours
      maxRetries: 5,
      notifyCustomer: false, // transparent retry — customer unaware
      action: 'RETRY',
    };
  }
}

// Mandate inactive — re-registration flow
@Injectable()
export class MandateInactiveRetryStrategy implements NachRetryStrategy {
  readonly priority = 30;

  canHandle(code: NachFailureCode): boolean {
    return ['MANDATE_CANCELLED', 'MANDATE_EXPIRED', 'ACCOUNT_CLOSED'].includes(code);
  }

  getRetrySchedule(_loan: Loan, _failedAt: Date): RetrySchedule {
    return {
      shouldRetry: false,
      maxRetries: 0,
      notifyCustomer: true,
      action: 'RE_REGISTRATION', // trigger NACH mandate re-registration flow
    };
  }
}
```

**Q14. How would you use Strategy for credit bureau selection in an underwriting pipeline?**
A: Bureau selection strategy can encode business rules about which bureau to pull based on product, applicant segment, and existing bureau history — without polluting the underwriting service:

```typescript
interface BureauSelectionStrategy {
  select(applicant: Applicant, product: LoanProduct): BureauProvider[];
}

type BureauProvider = 'CIBIL' | 'EXPERIAN' | 'CRIF' | 'KARZA';

// Standard retail — CIBIL primary, Experian for thin-file
@Injectable()
export class RetailBureauSelectionStrategy implements BureauSelectionStrategy {
  select(applicant: Applicant, _product: LoanProduct): BureauProvider[] {
    if (applicant.cibilScore == null) {
      // No CIBIL history — try alternate bureau
      return ['EXPERIAN', 'CRIF'];
    }
    return ['CIBIL'];
  }
}

// MSME — Karza for GST/MCA data + CIBIL for promoter
@Injectable()
export class MsmeBureauSelectionStrategy implements BureauSelectionStrategy {
  select(applicant: Applicant, _product: LoanProduct): BureauProvider[] {
    return ['KARZA', 'CIBIL']; // Karza for business data; CIBIL for personal promoter bureau
  }
}

// NRI — Experian international + CIBIL for India history
@Injectable()
export class NriBureauSelectionStrategy implements BureauSelectionStrategy {
  select(_applicant: Applicant, _product: LoanProduct): BureauProvider[] {
    return ['EXPERIAN', 'CIBIL'];
  }
}
```

## Section 4: Testing Strategies

**Q15. How does Strategy dramatically simplify unit testing in a lending system?**
A: Each strategy is a standalone class with one responsibility — test it in complete isolation, no mocking of unrelated dependencies:

```typescript
describe('SalariedEligibilityStrategy', () => {
  let strategy: SalariedEligibilityStrategy;

  beforeEach(() => {
    strategy = new SalariedEligibilityStrategy(); // no DI needed — self-contained
  });

  it('should approve applicant meeting all criteria', () => {
    const result = strategy.assess({
      cibilScore: 720,
      monthlyIncome: 80000,
      employmentTenureMonths: 12,
      employmentType: 'SALARIED',
    } as Applicant);

    expect(result.eligible).toBe(true);
    expect(result.maxLoanAmount).toBe(80000 * 60);
    expect(result.reasons).toHaveLength(0);
  });

  it('should reject and list all failing reasons', () => {
    const result = strategy.assess({
      cibilScore: 640,           // below 700
      monthlyIncome: 20000,      // below ₹25K
      employmentTenureMonths: 3, // below 6 months
      employmentType: 'SALARIED',
    } as Applicant);

    expect(result.eligible).toBe(false);
    expect(result.reasons).toHaveLength(3);
    expect(result.reasons).toContain('CIBIL score below 700');
    expect(result.reasons).toContain('Monthly income below ₹25,000');
    expect(result.reasons).toContain('Employment tenure below 6 months');
  });
});

// Context test — verifies it delegates correctly, not the algorithm
describe('LoanEligibilityService', () => {
  it('should delegate to the selected strategy', () => {
    const mockStrategy: EligibilityStrategy = {
      assess: jest.fn().mockReturnValue({ eligible: true, maxLoanAmount: 500000, reasons: [] }),
    };
    const mockFactory = { for: jest.fn().mockReturnValue(mockStrategy) };
    const service = new LoanEligibilityService(mockFactory as any);

    const result = service.assess({ employmentType: 'SALARIED' } as Applicant);

    expect(mockFactory.for).toHaveBeenCalledWith('SALARIED');
    expect(mockStrategy.assess).toHaveBeenCalled();
    expect(result.eligible).toBe(true);
  });
});
```

The context test is thin — it only verifies delegation. All the logic lives in strategy tests. Adding `GigWorkerEligibilityStrategy` means writing one new test file, touching nothing else.

## Section 5: Anti-patterns & Pitfalls

**Q16. What are the most common mistakes when implementing Strategy?**
A:

- **Leaking the strategy selection into the Context** — if `LoanEligibilityService` contains `if (employmentType === 'SALARIED') use strategyA else...`, you've just moved the switch inside the context. Selection must be fully external — factory, registry, or DI.
- **Too-granular strategies** — a `HighIncomeHighScoreSalariedStrategy` and `MediumIncomeHighScoreSalariedStrategy` as separate classes means the selection logic explodes. Strategies should vary on one meaningful dimension at a time; handle fine-grained variation inside the strategy via parameters.
- **Stateful strategies in singleton scope** — if a strategy accumulates state across calls (e.g., a running counter) and it's singleton-scoped in NestJS, that state bleeds across applicants. Strategies should be stateless — pure functions of their input. If state is needed, it should be passed in or scoped per-request.
- **Strategy interface that's too wide** — if `EligibilityStrategy` has eight methods but most strategies only implement two, you're forcing strategies to implement irrelevant behaviour. Split into narrower interfaces or use the Interface Segregation Principle.
- **Forgetting to handle unknown strategies** — the factory or registry must handle a discriminant it doesn't recognise. Throw early with a clear message rather than returning `undefined` and causing a null-dereference deep in the pipeline.
- **Putting infrastructure concerns inside strategies** — a strategy should contain the algorithm, not database calls or HTTP requests. If `SalariedEligibilityStrategy` queries the DB for employment verification, it's mixing concerns. Inject a repository or pass pre-fetched data into `assess()`.

**Q17. When should you NOT use Strategy?**
A:
- **When there are only two variants that will never grow** — a simple ternary or early return is cleaner than three files for two cases.
- **When the variants differ only in a configuration value** — if `SalariedStrategy` and `NriStrategy` are identical except for one threshold number, parameterise a single strategy class instead of creating two.
- **When the selection logic itself is trivial** — if the strategy is always the same (no runtime variation), there's no "strategy" — it's just a service.
- **When the algorithm boundary isn't clear** — Strategy works when you can draw a clean boundary around "the part that varies." If the variable part is entangled with the stable part, extraction produces an awkward interface. Refactor to clarify the boundary first.

## Section 6: Scenario / System Design Questions

**Q18. "Your underwriting engine currently has a 200-line method with eight `if/else` branches for different loan products. A new product needs to be added next sprint. How do you refactor this using Strategy?"**
A: A concrete three-step migration:

**Step 1 — Identify the interface**: Look at all eight branches. What inputs do they share? What do they all return? That's your strategy interface.

```typescript
interface UnderwritingStrategy {
  evaluate(application: LoanApplication, bureauReport: CreditReport): UnderwritingDecision;
}
```

**Step 2 — Extract one strategy at a time** (strangler fig approach — keep the system working throughout):
```typescript
// Start with the most complex branch — biggest win
class HomeLoanUnderwritingStrategy implements UnderwritingStrategy {
  evaluate(app: LoanApplication, bureau: CreditReport): UnderwritingDecision {
    // extract the home loan branch exactly as-is first
    // refactor it in the next PR once it's isolated and tested
  }
}
```
Replace the home loan branch in the original method with a delegation call. Run existing tests — they should all pass. Repeat for each branch.

**Step 3 — Replace the 200-line method with a factory + delegation**:
```typescript
evaluate(application: LoanApplication, bureau: CreditReport): UnderwritingDecision {
  const strategy = this.strategyFactory.for(application.productCode);
  return strategy.evaluate(application, bureau);
}
```

When the new product is needed next sprint: write `NewProductUnderwritingStrategy`, register it — the original method is untouched. The migration from 200 lines to extensible design is done in parallel with normal sprint work, one branch at a time.

**Q19. "Your collections team wants to A/B test two different SMS reminder strategies (aggressive vs gentle) for DPD 1–30 loans. How do you implement this using Strategy?"**
A: Wrap the strategy selection in a feature-flag-aware router — the A/B routing is itself a strategy (or a factory that selects between strategies):

```typescript
@Injectable()
export class AbTestingEarlyCollectionsStrategy implements CollectionsStrategy {
  readonly dpd = 'DPD_0_30' as const;

  constructor(
    private readonly aggressive: AggressiveReminderStrategy,
    private readonly gentle: GentleReminderStrategy,
    private readonly featureFlags: FeatureFlagService,
    private readonly abService: AbTestingService,
  ) {}

  async execute(loan: DelinquentLoan): Promise<CollectionsAction> {
    const variant = await this.abService.getVariant('collections-sms-v2', loan.id);

    if (variant === 'aggressive') {
      await this.abService.track(loan.id, 'collections-sms-v2', 'aggressive');
      return this.aggressive.execute(loan);
    }

    await this.abService.track(loan.id, 'collections-sms-v2', 'gentle');
    return this.gentle.execute(loan);
  }
}
```

The A/B router is itself an `EarlyDelinquencyStrategy` — it slots into the same registry with `dpd = 'DPD_0_30'` and replaces the previous strategy. Once the experiment concludes, swap back to the winning concrete strategy — one line in the module. No changes to `CollectionsEngine`.

**Q20. "Design the eligibility and pricing engine for a new Buy Now Pay Later (BNPL) product that needs to support five merchant partner variants with different credit rules and pricing. How do you structure it using Strategy?"**
A: Two strategy families — one for eligibility, one for pricing — selected by merchant partner:

```typescript
// Two strategy interfaces — independent variation axes
interface BnplEligibilityStrategy {
  assess(applicant: Applicant, orderAmount: number): BnplEligibilityResult;
}

interface BnplPricingStrategy {
  price(approvedAmount: number, tenorDays: number, merchantTier: string): BnplOffer;
}

// Per-merchant strategy pairs — each merchant has both
const MERCHANT_STRATEGIES: Record<MerchantId, {
  eligibility: BnplEligibilityStrategy;
  pricing: BnplPricingStrategy;
}> = {
  'MERCHANT_A': { eligibility: new LenientEligibilityStrategy(), pricing: new ZeroCostEmiStrategy() },
  'MERCHANT_B': { eligibility: new StrictEligibilityStrategy(), pricing: new StandardPricingStrategy() },
  'MERCHANT_C': { eligibility: new ScoreBasedEligibilityStrategy(), pricing: new DynamicPricingStrategy() },
};

// BNPL engine — composes both strategy families
@Injectable()
export class BnplEngine {
  constructor(private readonly strategyRegistry: BnplStrategyRegistry) {}

  async processOrder(order: BnplOrder, applicant: Applicant): Promise<BnplDecision> {
    const { eligibility, pricing } = this.strategyRegistry.for(order.merchantId);

    const eligibilityResult = eligibility.assess(applicant, order.amount);
    if (!eligibilityResult.eligible) {
      return { approved: false, reasons: eligibilityResult.reasons };
    }

    const offer = pricing.price(
      eligibilityResult.approvedAmount,
      order.requestedTenorDays,
      order.merchantTier,
    );

    return { approved: true, offer };
  }
}
```

Adding a sixth merchant variant is: implement two strategy classes, register the pair in the registry — `BnplEngine` doesn't know a new merchant was added.

## Quick Reference: Strategy Pattern Checklist

| Signal                                                                    | What to Do                                                                  |
|---------------------------------------------------------------------------|-----------------------------------------------------------------------------|
| Method with 4+ `if/else` or `switch` branches on a type field             | Extract each branch into a Strategy class                                   |
| "We need to add a new X type next sprint" is a recurring complaint        | Strategy + registry — new type = new class, no existing code touched        |
| Two services doing the same thing differently based on a config or flag   | Strategy — inject the right implementation; context is identical            |
| Algorithm selection depends on multiple runtime fields                    | Predicate-based strategy selector (`canHandle()` + priority)                |
| Strategies are stateful across requests                                   | Make them stateless — pass state in; or scope per-request if truly needed   |
| Selection logic creeping back into the Context                            | Move it to a factory or registry — Context must only delegate               |
| A/B testing two algorithm variants                                        | A/B router strategy wraps both; slots in as the current strategy            |
| Writing a new strategy requires changing existing classes                 | Registry pattern with `multi` providers — open for extension, closed for mod |

---

**Tip for the interview:** At the 5 YOE level, Strategy is one of the patterns where the interviewer will describe a real codebase smell — a God method with a sprawling `switch`, a service that keeps growing as new product types are added — and ask how you'd fix it. The answer is Strategy, but the *differentiating* answer names the full picture: the interface, the factory or registry for selection, why the Context must not contain selection logic, and how each strategy maps to one team or one business rule owner (connecting back to SRP). In a fintech context, lead with a real example — eligibility assessment per employment type, collections action per DPD bucket, interest rate calculation per rate type — because these are problems every lending platform has and every interviewer in the domain will immediately recognise.
