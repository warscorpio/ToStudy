# JavaScript / TypeScript (Design Patterns — Behavioral): State Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the State pattern?**
A: The State pattern is a behavioral design pattern that allows an object to **alter its behavior when its internal state changes** — making it appear as though the object's class itself has changed. Instead of encoding every possible state as a branch in a giant `if/else` or `switch` block inside a single class, the pattern extracts each state into its own class that implements a common interface. The context object holds a reference to the current state object and delegates all behavior to it. When a transition occurs, the context simply swaps the state object — and with it, the entire behavior profile of the context.

The pattern is rooted in the concept of **Finite State Machines (FSM)**: a system with a finite number of states, well-defined transitions between them, and behavior that is entirely determined by which state it currently occupies.

**Q2. What problem does the State pattern solve that a plain `switch` statement cannot?**
A: A `switch`-based state machine works at small scale but degrades badly as the system grows:
```ts
// Switch-based FSM — grows out of control
class TrafficLight {
  private state: "red" | "yellow" | "green" = "red";

  next(): void {
    switch (this.state) {
      case "red":    this.state = "green";  break;
      case "green":  this.state = "yellow"; break;
      case "yellow": this.state = "red";    break;
    }
  }

  canGo(): boolean {
    switch (this.state) {
      case "green":  return true;
      case "red":    return false;
      case "yellow": return false;
    }
  }

  getDuration(): number {
    switch (this.state) {
      case "red":    return 60;
      case "green":  return 45;
      case "yellow": return 5;
    }
  }
}
```
Every new state adds a case to *every* `switch`. Every new behavior adds a new `switch` with cases for *every* state. The class violates OCP (every change requires modifying the existing class) and SRP (one class encodes all state-specific logic for all states). At five states and ten behaviors, the class is a 200-line tangle where every line is about the intersection of one state and one behavior — impossible to reason about in isolation.

The State pattern fixes this by making each state a class, each behavior a method on the state interface. Adding a new state is a new class. Adding a new behavior is a new method on the interface — each state implements it independently. The context class never changes.

**Q3. What are the three participants in the State pattern?**
A:
- **Context** — the object whose behavior varies based on state. It holds a reference to the current `State` object and delegates all state-dependent method calls to it. It exposes a `setState()` method (called by states or externally) to trigger transitions. Clients interact only with the Context.
- **State (interface / abstract class)** — declares the interface for all state-specific behavior. One method per operation the Context exposes. Each method receives the Context as a parameter (enabling transitions).
- **ConcreteState** — one class per state. Implements the State interface with the behavior appropriate for that state. Knows which transitions are valid and triggers them by calling `context.setState(new NextState())`.

**Q4. Who is responsible for state transitions — the Context or the State?**
A: Either can own transitions, and the choice is a deliberate design decision:

- **State-driven transitions (preferred in most cases)** — each ConcreteState knows its own valid transitions and triggers them by calling `context.setState(new NextState())`. Keeps transition logic close to the state that initiates it. Simple to understand: each state class encodes "what can happen next from here."
- **Context-driven transitions** — the Context itself decides the next state based on conditions. Useful when transitions depend on external data the State shouldn't know about, or when transition logic is shared across multiple states.
- **Hybrid** — States trigger transitions for simple cases (timed expiry, event-driven); Context manages transitions for complex decision logic involving external inputs.

```ts
// State-driven transition — State calls context.setState()
class IdleState implements VendingMachineState {
  insertCoin(context: VendingMachine, coin: Coin): void {
    context.addCredit(coin.value);
    context.setState(new HasCreditState()); // State triggers its own transition
  }
  dispense(context: VendingMachine): void {
    console.log("Insert a coin first.");
  }
}

// Context-driven transition — Context reads state + external data, decides next state
class VendingMachine {
  selectProduct(product: Product): void {
    if (this.credit >= product.price && this.inventory.has(product)) {
      this.setState(new DispensingState(product)); // Context decides
    } else if (this.credit < product.price) {
      console.log("Insufficient credit.");
    } else {
      console.log("Out of stock.");
    }
  }
}
```

**Q5. What is the relationship between the State pattern and Finite State Machines?**
A: The State pattern is the object-oriented implementation of a Finite State Machine. An FSM has:
- A finite set of **states** — modeled as ConcreteState classes.
- An **initial state** — the state the Context is initialized with.
- **Transitions** — triggered by events/methods, encoded as `context.setState(...)` calls inside state methods.
- **Actions** — behavior that executes during a transition or while in a state, encoded as method bodies in ConcreteState classes.

The State pattern adds OOP structure on top of raw FSM theory: states are encapsulated in classes (so each state is independently testable and modifiable), transitions are explicit method calls (not a table lookup), and new states/transitions are additive (new classes, no edits to existing ones).

## Section 2: Implementing the State Pattern in TypeScript

**Q6. Show a complete, production-quality State pattern implementation for an order lifecycle.**
A:
```ts
// State interface — one method per operation the Order exposes
interface OrderState {
  confirm(order: Order): void;
  ship(order: Order): void;
  deliver(order: Order): void;
  cancel(order: Order): void;
  getLabel(): string;
}

// Context — delegates all behavior to its current state
class Order {
  private state: OrderState;
  public readonly id: string;
  private history: string[] = [];

  constructor(id: string) {
    this.id    = id;
    this.state = new PendingState(); // initial state
    this.log(`Order ${id} created`);
  }

  // Delegation — every public method goes through the state
  confirm():  void { this.state.confirm(this); }
  ship():     void { this.state.ship(this);    }
  deliver():  void { this.state.deliver(this); }
  cancel():   void { this.state.cancel(this);  }

  // State transition — called by ConcreteStates
  setState(state: OrderState): void {
    this.log(`Transition: ${this.state.getLabel()} → ${state.getLabel()}`);
    this.state = state;
  }

  getStatus(): string { return this.state.getLabel(); }
  getHistory(): string[] { return [...this.history]; }

  log(message: string): void {
    const entry = `[${new Date().toISOString()}] ${message}`;
    this.history.push(entry);
    console.log(entry);
  }
}

// ConcreteStates — one class per state, independent behavior
class PendingState implements OrderState {
  getLabel(): string { return "PENDING"; }

  confirm(order: Order): void {
    order.log("Payment confirmed — order is now confirmed.");
    order.setState(new ConfirmedState());
  }
  ship(order: Order): void {
    order.log("Cannot ship: order not yet confirmed.");
  }
  deliver(order: Order): void {
    order.log("Cannot deliver: order not yet confirmed.");
  }
  cancel(order: Order): void {
    order.log("Order cancelled from pending state.");
    order.setState(new CancelledState());
  }
}

class ConfirmedState implements OrderState {
  getLabel(): string { return "CONFIRMED"; }

  confirm(order: Order): void { order.log("Order already confirmed."); }
  ship(order: Order): void {
    order.log("Order dispatched to shipping.");
    order.setState(new ShippedState());
  }
  deliver(order: Order): void {
    order.log("Cannot deliver: order not yet shipped.");
  }
  cancel(order: Order): void {
    order.log("Order cancelled — initiating refund.");
    order.setState(new CancelledState());
  }
}

class ShippedState implements OrderState {
  getLabel(): string { return "SHIPPED"; }

  confirm(order: Order): void { order.log("Order already confirmed."); }
  ship(order: Order): void    { order.log("Order already shipped."); }
  deliver(order: Order): void {
    order.log("Order delivered successfully.");
    order.setState(new DeliveredState());
  }
  cancel(order: Order): void {
    order.log("Cannot cancel: order already shipped. Initiate return instead.");
  }
}

class DeliveredState implements OrderState {
  getLabel(): string { return "DELIVERED"; }

  confirm(order: Order): void { order.log("Order already delivered."); }
  ship(order: Order): void    { order.log("Order already delivered."); }
  deliver(order: Order): void { order.log("Order already delivered."); }
  cancel(order: Order): void  { order.log("Cannot cancel: order already delivered. Initiate return instead."); }
}

class CancelledState implements OrderState {
  getLabel(): string { return "CANCELLED"; }

  confirm(order: Order): void { order.log("Cannot confirm: order is cancelled."); }
  ship(order: Order): void    { order.log("Cannot ship: order is cancelled."); }
  deliver(order: Order): void { order.log("Cannot deliver: order is cancelled."); }
  cancel(order: Order): void  { order.log("Order already cancelled."); }
}

// Client — interacts only with Order (the Context)
const order = new Order("ORD-001");
order.ship();     // Cannot ship: not yet confirmed
order.confirm();  // Payment confirmed
order.ship();     // Dispatched
order.deliver();  // Delivered
order.cancel();   // Cannot cancel: already delivered

console.log(order.getStatus());    // DELIVERED
console.log(order.getHistory());   // Full audit trail
```

**Q7. How do you implement the State pattern using a functional / object-literal approach instead of classes?**
A: For simpler cases or functional-style codebases, states can be plain objects rather than class instances:
```ts
// Functional State pattern — states as object literals
type TrafficLightState = {
  label:       string;
  canGo:       () => boolean;
  duration:    () => number;
  next:        () => TrafficLightState;
};

// Forward declarations for circular references
const RedState:    TrafficLightState = {
  label:    "RED",
  canGo:    () => false,
  duration: () => 60,
  next:     () => GreenState,   // forward reference — resolved at runtime
};

const GreenState: TrafficLightState = {
  label:    "GREEN",
  canGo:    () => true,
  duration: () => 45,
  next:     () => YellowState,
};

const YellowState: TrafficLightState = {
  label:    "YELLOW",
  canGo:    () => false,
  duration: () => 5,
  next:     () => RedState,
};

// Context — holds current state, delegates
class TrafficLight {
  private current: TrafficLightState = RedState;

  advance():       void    { this.current = this.current.next(); }
  canGo():         boolean { return this.current.canGo(); }
  getDuration():   number  { return this.current.duration(); }
  getLabel():      string  { return this.current.label; }
}

const light = new TrafficLight();
console.log(light.getLabel());   // RED
light.advance();
console.log(light.getLabel());   // GREEN
light.advance();
console.log(light.getLabel());   // YELLOW
```

**Q8. How do you persist and restore a state machine's state — for example, across server restarts or database persistence?**
A: States must be serialisable. The pattern uses a label/name to identify states and a factory to restore them:
```ts
type OrderStateLabel = "PENDING" | "CONFIRMED" | "SHIPPED" | "DELIVERED" | "CANCELLED";

// State factory — maps persisted label back to live state object
const stateFactory: Record<OrderStateLabel, () => OrderState> = {
  PENDING:   () => new PendingState(),
  CONFIRMED: () => new ConfirmedState(),
  SHIPPED:   () => new ShippedState(),
  DELIVERED: () => new DeliveredState(),
  CANCELLED: () => new CancelledState(),
};

class Order {
  private state: OrderState;

  constructor(id: string, persistedState?: OrderStateLabel) {
    this.id    = id;
    // Restore from persisted label, or start fresh
    this.state = persistedState
      ? stateFactory[persistedState]()
      : new PendingState();
  }

  // Serialise — store only the label (not the object)
  toJSON(): object {
    return {
      id:     this.id,
      status: this.state.getLabel() as OrderStateLabel,
    };
  }

  // Restore from database
  static fromRecord(record: { id: string; status: OrderStateLabel }): Order {
    return new Order(record.id, record.status);
  }
}

// Repository usage
const record = await db.query("SELECT id, status FROM orders WHERE id = $1", [orderId]);
const order  = Order.fromRecord(record);
order.ship(); // correct behavior based on restored state
await db.query("UPDATE orders SET status = $1 WHERE id = $2",
  [order.getStatus(), order.id]);
```

**Q9. How do you implement guard conditions — transitions that are only allowed if certain preconditions hold?**
A: Guards are implemented as conditional checks inside the state method before triggering a transition:
```ts
class ConfirmedState implements OrderState {
  ship(order: Order): void {
    // Guard condition — check preconditions before allowing transition
    if (!order.hasShippingAddress()) {
      order.log("Cannot ship: no shipping address on record.");
      return; // guard blocks the transition
    }
    if (!order.hasInventoryReservation()) {
      order.log("Cannot ship: inventory not reserved.");
      return;
    }
    order.log("Order dispatched.");
    order.setState(new ShippedState());
  }
  // ...
}

// For complex guards, extract to a separate method or validator
class PaymentState implements OrderState {
  private readonly MAX_RETRY_ATTEMPTS = 3;

  retry(order: Order): void {
    const guard = this.validateRetry(order);
    if (!guard.allowed) {
      order.log(`Retry blocked: ${guard.reason}`);
      return;
    }
    order.incrementRetryCount();
    order.log(`Retry attempt ${order.retryCount} of ${this.MAX_RETRY_ATTEMPTS}`);
    // ... trigger payment retry
  }

  private validateRetry(order: Order): { allowed: boolean; reason?: string } {
    if (order.retryCount >= this.MAX_RETRY_ATTEMPTS)
      return { allowed: false, reason: "Maximum retry attempts reached" };
    if (order.isExpired())
      return { allowed: false, reason: "Order session expired" };
    return { allowed: true };
  }
}
```

**Q10. How do you handle entry and exit actions — behavior that should run whenever a state is entered or left?**
A: Entry and exit actions are hooks added to the State interface and called by the Context's `setState` method:
```ts
interface State {
  onEnter(context: Context): void; // runs when this state becomes active
  onExit(context: Context): void;  // runs when this state is being left
  handle(context: Context, event: Event): void;
}

abstract class BaseState implements State {
  // Default no-ops — override only what's needed
  onEnter(_context: Context): void {}
  onExit(_context: Context): void  {}
  abstract handle(context: Context, event: Event): void;
}

class Context {
  private state: State = new InitialState();

  setState(nextState: State): void {
    this.state.onExit(this);      // exit action on current state
    this.state = nextState;
    this.state.onEnter(this);     // entry action on new state
  }

  handle(event: Event): void { this.state.handle(this, event); }
}

// Concrete state — uses entry/exit actions
class ProcessingPaymentState extends BaseState {
  onEnter(context: Order): void {
    context.log("Payment processing started — showing spinner");
    context.startPaymentTimeout(30_000); // start a 30s timeout
  }

  onExit(context: Order): void {
    context.log("Payment processing ended — hiding spinner");
    context.clearPaymentTimeout(); // always clear the timeout
  }

  handle(context: Order, event: Event): void {
    if (event.type === "PAYMENT_SUCCESS") context.setState(new PaidState());
    if (event.type === "PAYMENT_FAILURE") context.setState(new PaymentFailedState());
    if (event.type === "TIMEOUT")         context.setState(new PaymentTimedOutState());
  }
}
```

## Section 3: Real-World Applications

**Q11. How does the State pattern apply to a document editing workflow (Draft → Review → Published → Archived)?**
A:
```ts
interface DocumentState {
  submit(doc: Document): void;
  approve(doc: Document): void;
  reject(doc: Document, reason: string): void;
  publish(doc: Document): void;
  archive(doc: Document): void;
  getLabel(): string;
  canEdit(): boolean;
}

abstract class BaseDocumentState implements DocumentState {
  // Default: operation not allowed in this state
  submit(doc: Document):              void { doc.log(`Cannot submit from ${this.getLabel()}`); }
  approve(doc: Document):             void { doc.log(`Cannot approve from ${this.getLabel()}`); }
  reject(doc: Document, _r: string):  void { doc.log(`Cannot reject from ${this.getLabel()}`); }
  publish(doc: Document):             void { doc.log(`Cannot publish from ${this.getLabel()}`); }
  archive(doc: Document):             void { doc.log(`Cannot archive from ${this.getLabel()}`); }
  canEdit(): boolean { return false; }
  abstract getLabel(): string;
}

class DraftState extends BaseDocumentState {
  getLabel(): string  { return "DRAFT"; }
  canEdit(): boolean  { return true; } // only drafts are editable

  submit(doc: Document): void {
    if (!doc.hasContent()) { doc.log("Cannot submit empty document."); return; }
    doc.log("Document submitted for review.");
    doc.setState(new UnderReviewState());
  }
  archive(doc: Document): void {
    doc.log("Draft archived.");
    doc.setState(new ArchivedState());
  }
}

class UnderReviewState extends BaseDocumentState {
  getLabel(): string { return "UNDER_REVIEW"; }

  approve(doc: Document): void {
    doc.log("Document approved — ready for publishing.");
    doc.setState(new ApprovedState());
  }
  reject(doc: Document, reason: string): void {
    doc.log(`Document rejected: ${reason}. Returned to draft.`);
    doc.addReviewComment(reason);
    doc.setState(new DraftState());
  }
}

class ApprovedState extends BaseDocumentState {
  getLabel(): string { return "APPROVED"; }

  publish(doc: Document): void {
    doc.setPublishedAt(new Date());
    doc.log("Document published.");
    doc.setState(new PublishedState());
  }
}

class PublishedState extends BaseDocumentState {
  getLabel(): string { return "PUBLISHED"; }

  archive(doc: Document): void {
    doc.log("Published document archived.");
    doc.setState(new ArchivedState());
  }
}

class ArchivedState extends BaseDocumentState {
  getLabel(): string { return "ARCHIVED"; }
  // Terminal state — no transitions out (or add restore() if needed)
}
```

**Q12. How does the State pattern apply to a network connection (Disconnected → Connecting → Connected → Reconnecting)?**
A:
```ts
interface ConnectionState {
  connect(conn: Connection): Promise<void>;
  disconnect(conn: Connection): Promise<void>;
  send(conn: Connection, data: Buffer): Promise<void>;
  onError(conn: Connection, error: Error): Promise<void>;
  getLabel(): string;
}

class DisconnectedState implements ConnectionState {
  getLabel(): string { return "DISCONNECTED"; }

  async connect(conn: Connection): Promise<void> {
    conn.setState(new ConnectingState());
    try {
      await conn.openSocket();
      conn.resetRetryCount();
      conn.setState(new ConnectedState());
    } catch (err) {
      conn.setState(new DisconnectedState());
      throw err;
    }
  }

  async disconnect(conn: Connection): Promise<void> { /* already disconnected */ }
  async send(conn: Connection, _data: Buffer): Promise<void> {
    throw new Error("Cannot send: not connected.");
  }
  async onError(_conn: Connection, _err: Error): Promise<void> { /* no-op */ }
}

class ConnectedState implements ConnectionState {
  getLabel(): string { return "CONNECTED"; }

  async connect(_conn: Connection): Promise<void> { /* already connected */ }
  async disconnect(conn: Connection): Promise<void> {
    await conn.closeSocket();
    conn.setState(new DisconnectedState());
  }
  async send(conn: Connection, data: Buffer): Promise<void> {
    await conn.writeToSocket(data); // direct send — we're connected
  }
  async onError(conn: Connection, error: Error): Promise<void> {
    conn.log(`Connection error: ${error.message} — attempting reconnect`);
    conn.setState(new ReconnectingState());
  }
}

class ReconnectingState implements ConnectionState {
  private readonly MAX_RETRIES = 5;
  private readonly BACKOFF_MS  = [1000, 2000, 4000, 8000, 16000];

  getLabel(): string { return "RECONNECTING"; }

  async connect(conn: Connection): Promise<void> {
    const attempt = conn.incrementRetryCount();

    if (attempt > this.MAX_RETRIES) {
      conn.log("Max reconnect attempts reached.");
      conn.setState(new DisconnectedState());
      return;
    }

    const delay = this.BACKOFF_MS[attempt - 1] ?? 16000;
    conn.log(`Reconnect attempt ${attempt}/${this.MAX_RETRIES} in ${delay}ms`);
    await new Promise(r => setTimeout(r, delay));

    try {
      await conn.openSocket();
      conn.resetRetryCount();
      conn.setState(new ConnectedState());
    } catch {
      conn.setState(new ReconnectingState()); // retry again
    }
  }

  async disconnect(conn: Connection): Promise<void> {
    conn.cancelReconnect();
    conn.setState(new DisconnectedState());
  }
  async send(_conn: Connection, _data: Buffer): Promise<void> {
    throw new Error("Cannot send: reconnecting.");
  }
  async onError(conn: Connection, _err: Error): Promise<void> {
    await this.connect(conn); // keep trying
  }
}
```

**Q13. How does the State pattern apply to a UI form wizard (Step1 → Step2 → Step3 → Submitted)?**
A:
```ts
interface WizardState {
  next(wizard: FormWizard): void;
  back(wizard: FormWizard): void;
  submit(wizard: FormWizard): void;
  canGoBack(): boolean;
  canGoNext(): boolean;
  canSubmit(): boolean;
  getStepNumber(): number;
  getTitle(): string;
}

abstract class BaseWizardStep implements WizardState {
  back(wizard: FormWizard): void   { /* default no-op — overridden by non-first steps */ }
  submit(wizard: FormWizard): void { wizard.log("Not on final step yet."); }
  canGoBack(): boolean  { return false; }
  canSubmit(): boolean  { return false; }
  abstract next(wizard: FormWizard): void;
  abstract canGoNext(): boolean;
  abstract getStepNumber(): number;
  abstract getTitle(): string;
}

class PersonalDetailsStep extends BaseWizardStep {
  getStepNumber(): number { return 1; }
  getTitle(): string      { return "Personal Details"; }
  canGoNext(): boolean    { return true; } // determined by form validation

  next(wizard: FormWizard): void {
    if (!wizard.isStepValid(1)) { wizard.showErrors(1); return; }
    wizard.setState(new AddressStep());
  }
}

class AddressStep extends BaseWizardStep {
  getStepNumber(): number { return 2; }
  getTitle(): string      { return "Shipping Address"; }
  canGoBack(): boolean    { return true; }
  canGoNext(): boolean    { return true; }

  next(wizard: FormWizard): void {
    if (!wizard.isStepValid(2)) { wizard.showErrors(2); return; }
    wizard.setState(new PaymentStep());
  }
  back(wizard: FormWizard): void { wizard.setState(new PersonalDetailsStep()); }
}

class PaymentStep extends BaseWizardStep {
  getStepNumber(): number { return 3; }
  getTitle(): string      { return "Payment Details"; }
  canGoBack(): boolean    { return true; }
  canGoNext(): boolean    { return false; }
  canSubmit(): boolean    { return true; }

  next(wizard: FormWizard): void { /* no next from final step */ }
  back(wizard: FormWizard): void { wizard.setState(new AddressStep()); }
  submit(wizard: FormWizard): void {

}
```

**Q14. How does the State pattern apply to a media player (Idle → Loading → Playing → Paused → Stopped → Error)?**
A:
```ts
interface PlayerState {
  load(player: MediaPlayer, url: string): void;
  play(player: MediaPlayer): void;
  pause(player: MediaPlayer): void;
  stop(player: MediaPlayer): void;
  onLoadComplete(player: MediaPlayer): void;
  onError(player: MediaPlayer, error: Error): void;
  getLabel(): string;
}

class IdleState implements PlayerState {
  getLabel(): string { return "IDLE"; }

  load(player: MediaPlayer, url: string): void {
    player.setUrl(url);
    player.setState(new LoadingState());
    player.beginLoad(); // triggers async load → onLoadComplete or onError
  }
  play(player: MediaPlayer): void  { player.log("No media loaded."); }
  pause(player: MediaPlayer): void { player.log("No media loaded."); }
  stop(player: MediaPlayer): void  { /* already idle */ }
  onLoadComplete(player: MediaPlayer): void { /* should not happen in Idle */ }
  onError(player: MediaPlayer, _err: Error): void { /* should not happen in Idle */ }
}

class LoadingState implements PlayerState {
  getLabel(): string { return "LOADING"; }

  load(player: MediaPlayer, url: string): void { player.log("Already loading."); }
  play(player: MediaPlayer): void  { player.log("Still loading — please wait."); }
  pause(player: MediaPlayer): void { player.log("Still loading."); }
  stop(player: MediaPlayer): void  {
    player.cancelLoad();
    player.setState(new IdleState());
  }
  onLoadComplete(player: MediaPlayer): void {
    player.log("Media loaded successfully.");
    player.setState(new StoppedState());
    player.play(); // auto-play after load — delegates to new state
  }
  onError(player: MediaPlayer, error: Error): void {
    player.log(`Load error: ${error.message}`);
    player.setState(new ErrorState(error));
  }
}

class PlayingState implements PlayerState {
  getLabel(): string { return "PLAYING"; }

  load(player: MediaPlayer, url: string): void {
    player.stop(); // stop current, then load new
    player.load(url);
  }
  play(player: MediaPlayer): void  { player.log("Already playing."); }
  pause(player: MediaPlayer): void {
    player.pausePlayback();
    player.setState(new PausedState());
  }
  stop(player: MediaPlayer): void {
    player.stopPlayback();
    player.setState(new StoppedState());
  }
  onLoadComplete(player: MediaPlayer): void { /* irrelevant while playing */ }
  onError(player: MediaPlayer, error: Error): void {
    player.stopPlayback();
    player.setState(new ErrorState(error));
  }
}

class PausedState implements PlayerState {
  getLabel(): string { return "PAUSED"; }

  load(player: MediaPlayer, url: string): void { player.stop(); player.load(url); }
  play(player: MediaPlayer): void {
    player.resumePlayback();

  stop(player: MediaPlayer): void  {

    player.setState(new StoppedState());

  onError(player: MediaPlayer, error: Error): void { player.setState(new ErrorState(error)); }
```

## Section 4: State Pattern with Other Patterns

**Q15. How does the State pattern combine with the Command pattern to build an undoable state machine?**
A: Each transition becomes a Command that knows how to execute and undo itself, giving the state machine full undo/redo capability:
```ts
interface TransitionCommand {
  execute(): void;
  undo(): void;
  description: string;
}

class OrderTransitionCommand implements TransitionCommand {
  private previousState: OrderState;

  constructor(
    private order:     Order,
    private nextState: OrderState,
    public description: string
  ) {
    this.previousState = order.getCurrentState();
  }

  execute(): void { this.order.setState(this.nextState); }
  undo():    void { this.order.setState(this.previousState); }
}

class OrderHistory {
  private executed: TransitionCommand[] = [];
  private undone:   TransitionCommand[] = [];

  execute(cmd: TransitionCommand): void {
    cmd.execute();
    this.executed.push(cmd);
    this.undone = []; // clear redo stack on new action
  }

  undo(): void {
    const cmd = this.executed.pop();
    if (!cmd) return;
    cmd.undo();
    this.undone.push(cmd);
  }

  redo(): void {
    const cmd = this.undone.pop();
    if (!cmd) return;
    cmd.execute();
    this.executed.push(cmd);
  }

  getHistory(): string[] { return this.executed.map(c => c.description); }
}

// Usage
const order   = new Order("ORD-001");
const history = new OrderHistory();

history.execute(new OrderTransitionCommand(order, new ConfirmedState(), "Confirm order"));
history.execute(new OrderTransitionCommand(order, new ShippedState(),   "Ship order"));
console.log(order.getStatus()); // SHIPPED

history.undo();
console.log(order.getStatus()); // CONFIRMED

history.redo();
console.log(order.getStatus()); // SHIPPED
```

**Q16. How does the State pattern combine with the Observer pattern to notify subscribers on state changes?**
A: The Context emits events whenever its state changes, allowing external systems to react without coupling to the state machine:
```ts
type StateChangeEvent = {
  context:   string;
  fromState: string;
  toState:   string;
  timestamp: Date;
};

type StateChangeHandler = (event: StateChangeEvent) => void;

class Order {
  private state: OrderState = new PendingState();
  private observers: StateChangeHandler[] = [];

  onStateChange(handler: StateChangeHandler): () => void {
    this.observers.push(handler);
    return () => { // unsubscribe function
      this.observers = this.observers.filter(h => h !== handler);
    };
  }

  setState(nextState: OrderState): void {
    const event: StateChangeEvent = {
      context:   this.id,
      fromState: this.state.getLabel(),
      toState:   nextState.getLabel(),
      timestamp: new Date(),
    };
    this.state = nextState;
    this.observers.forEach(h => h(event)); // notify all observers
  }
}

// Observers — react to state changes without knowing the state machine internals
const order = new Order("ORD-001");

// Audit log observer
const unsubAudit = order.onStateChange(e =>
  auditService.log(`Order ${e.context}: ${e.fromState} → ${e.toState}`)
);

// Analytics observer
order.onStateChange(e =>
  analytics.track("order_state_changed", { orderId: e.context, to: e.toState })
);

// Email notification observer
order.onStateChange(async e => {
  if (e.toState === "SHIPPED") {
    await emailService.sendShippingNotification(e.context);
  }
});

order.confirm(); // triggers all observers
order.ship();    // triggers all observers

unsubAudit(); // cleanup
```

**Q17. How does the State pattern combine with the Strategy pattern, and how do you tell them apart?**
A: Both replace conditional logic with polymorphism, but they serve different purposes and have different lifecycles:

| Aspect | State | Strategy |
|---|---|---|
| **Intent** | Object changes behavior as its *internal state* changes | Client selects an *algorithm* to inject at construction or use time |
| **Awareness** | States know about each other (trigger transitions) | Strategies are unaware of each other |
| **Lifecycle** | State changes over the lifetime of the Context | Strategy is typically set once or per operation |
| **Initiator** | State itself or the Context triggers changes | Client chooses and sets the strategy |
| **Self-replacement** | States replace themselves via `context.setState()` | Strategies don't replace themselves |

```ts
// Strategy — client injects the algorithm; SortStrategy doesn't change itself
class DataProcessor {
  constructor(private sort: SortStrategy) {} // set at creation
  process(data: number[]): number[] { return this.sort.sort(data); }
}

// State — object changes its own behavior profile as events happen
class Connection {
  private state: ConnectionState = new DisconnectedState();
  // State changes itself: DisconnectedState → ConnectingState → ConnectedState
  async connect(): Promise<void> { await this.state.connect(this); }
}

// The tell: does the behavior change because the CLIENT chose differently (Strategy)
//           or because something HAPPENED TO THE OBJECT (State)?
```

## Section 5: Pitfalls, Anti-Patterns & Edge Cases

**Q18. What is the "state explosion" problem, and how do you manage it?**
A: As a system grows, the number of states and transitions grows combinatorially — especially when multiple orthogonal dimensions of state exist. A document that tracks `editingMode × approvalStatus × visibilityStatus` has 2 × 4 × 3 = 24 possible combinations, most of which are invalid. Encoding each as a ConcreteState class produces an unmanageable explosion.

Mitigations:
```ts
// Problem — 24 ConcreteState classes for one document
class DraftPrivateEditingState implements DocumentState { /* ... */ }
class DraftPrivateViewingState  implements DocumentState { /* ... */ }
class DraftPublicEditingState   implements DocumentState { /* ... */ }
// ... 21 more ✗

// Mitigation 1 — Hierarchical / Nested State Machines
// Top-level FSM handles approval lifecycle; nested FSM handles editing mode
class DraftState implements DocumentState {
  private editingFSM: EditingStateMachine = new EditingStateMachine();
  // Delegates editing-related events to inner FSM
}

// Mitigation 2 — Parallel (orthogonal) state machines
class Document {
  private approvalState:   ApprovalState   = new DraftApprovalState();
  private visibilityState: VisibilityState = new PrivateVisibilityState();
  private editingState:    EditingState    = new EditingModeState();
  // Each dimension is an independent state machine
}

// Mitigation 3 — State with data (parameterised states)
class RetryingState implements ConnectionState {
  constructor(private attempt: number, private maxRetries: number) {}
  // Encodes "which retry attempt" as data, not as separate classes
  // RetryingState(1) and RetryingState(3) are the same class, different data
}
```

**Q19. How do you prevent illegal transitions and make them visible at compile time in TypeScript?**
A: TypeScript's type system can encode the valid state graph, making invalid transitions compile-time errors:
```ts
// Type-level state machine — valid transitions are encoded in types
type OrderStatus = "PENDING" | "CONFIRMED" | "SHIPPED" | "DELIVERED" | "CANCELLED";

// Each state maps to the states it can transition to
type ValidTransitions = {
  PENDING:   "CONFIRMED" | "CANCELLED";
  CONFIRMED: "SHIPPED"   | "CANCELLED";
  SHIPPED:   "DELIVERED";
  DELIVERED: never;        // terminal — no valid transitions
  CANCELLED: never;        // terminal — no valid transitions
};

// Type-safe transition function — only compiles for valid (from, to) pairs
function transition<S extends OrderStatus>(
  order: Order & { status: S },
  nextStatus: ValidTransitions[S]
): void {
  order.setState(stateFactory[nextStatus]());
}

const pendingOrder = { status: "PENDING" as const, ...order };
transition(pendingOrder, "CONFIRMED");  // ✓ compiles
transition(pendingOrder, "SHIPPED");    // ✗ TypeScript error — PENDING can't go to SHIPPED
transition(pendingOrder, "DELIVERED"); // ✗ TypeScript error

// Runtime guard — for cases where transitions come from external input
function isValidTransition(from: OrderStatus, to: OrderStatus): boolean {
  const valid: Record<OrderStatus, OrderStatus[]> = {
    PENDING:   ["CONFIRMED", "CANCELLED"],
    CONFIRMED: ["SHIPPED",   "CANCELLED"],
    SHIPPED:   ["DELIVERED"],
    DELIVERED: [],
    CANCELLED: [],
  };
  return valid[from].includes(to);
}
```

**Q20. What is the "context bloat" problem in the State pattern, and how do you resolve it?**
A: Because States call methods on the Context to read data and trigger transitions, the Context must expose a wide interface — sometimes more than it should. Every piece of data or operation a State needs must be accessible on the Context, which can lead to a Context class with dozens of methods, many of which are only relevant to one state:
```ts
// Context bloat — Context exposes everything any state might need
class Order {
  // Business data — fine
  id: string; total: Money; items: OrderItem[];

  // Transition method — fine
  setState(state: OrderState): void { this.state = state; }

  // Methods only needed by ShippedState
  getShippingLabel(): string { /* ... */ }
  notifyCarrier(): Promise<void> { /* ... */ }

  // Methods only needed by PaymentFailedState
  getFailureCount(): number { /* ... */ }
  scheduleRetry(delayMs: number): void { /* ... */ }

  // Methods only needed by RefundState
  calculateRefundAmount(): Money { /* ... */ }
  issueRefundToGateway(): Promise<void> { /* ... */ }
  // ... 40 more methods, each for a different state ✗
}
```

Resolutions:
```ts
// Resolution 1 — pass subsystems to State methods, not the entire Context
interface OrderState {
  ship(order: Order, carrier: CarrierService, notifier: NotificationService): void;
}

// Resolution 2 — split Context into a lean Context + a richer StateContext DTO
interface StateContext {
  id: string; total: Money; items: OrderItem[];
  setState(state: OrderState): void;
  log(message: string): void;
}

// States receive StateContext — only what they need for transitions and logging
// Subsystem calls go through injected services, not Context methods

// Resolution 3 — use double dispatch: State calls a service directly
class ShippedState implements OrderState {
  constructor(private carrier: CarrierService) {} // injected at state creation
  async enter(order: StateContext): Promise<void> {
    await this.carrier.notifyShipment(order.id); // service called directly
  }
}
```

**Q21. How do you test individual state classes in isolation?**
A: Each ConcreteState is independently testable by constructing it directly and passing a mock Context:
```ts
// Testing PendingState in isolation — no real Order needed
describe("PendingState", () => {
  let mockOrder: jest.Mocked<Order>;
  let state: PendingState;

  beforeEach(() => {
    mockOrder = {
      id:       "ORD-001",
      log:      jest.fn(),
      setState: jest.fn(),
      hasShippingAddress:    jest.fn().mockReturnValue(true),
      hasInventoryReservation: jest.fn().mockReturnValue(true),
    } as unknown as jest.Mocked<Order>;

    state = new PendingState();
  });

  it("transitions to ConfirmedState on confirm()", () => {
    state.confirm(mockOrder);
    expect(mockOrder.setState).toHaveBeenCalledWith(expect.any(ConfirmedState));
  });

  it("transitions to CancelledState on cancel()", () => {
    state.cancel(mockOrder);
    expect(mockOrder.setState).toHaveBeenCalledWith(expect.any(CancelledState));
  });

  it("does not transition on ship()", () => {
    state.ship(mockOrder);
    expect(mockOrder.setState).not.toHaveBeenCalled();
    expect(mockOrder.log).toHaveBeenCalledWith(expect.stringContaining("Cannot ship"));
  });

  it("does not transition on deliver()", () => {
    state.deliver(mockOrder);
    expect(mockOrder.setState).not.toHaveBeenCalled();
  });
});
```

## Section 6: Scenario / System Design Style Questions

**Q22. "A junior dev has written a 300-line OrderService with nested switch statements for every operation. How do you explain the refactor to the State pattern and make the case for it?"**
A: Anchor the argument in concrete change scenarios rather than theory:

> "Let's say we need to add a 'Refund Requested' state next sprint. With the current `switch`, we add a new case to the `confirm` switch, the `ship` switch, the `cancel` switch, the `getLabel` switch, and every other switch — maybe eight places to touch. And we have to understand how Refund Requested interacts with every other state across every operation. It's easy to miss one.
>
> With the State pattern, adding Refund Requested means adding one class: `RefundRequestedState`. We implement each method — confirming is not allowed, shipping is not allowed, cancelling triggers the refund flow. Every rule for that state lives in one file. We touch zero existing classes. And we can test `RefundRequestedState` in complete isolation with a mock Order."

Then show the before/after structure:
```ts
// Before — 300 lines, every new state touches existing code
switch (this.status) {
  case "pending":   /* ... */; break;
  case "confirmed": /* ... */; break;
  case "shipped":   /* ... */; break;
  // Adding "refund_requested" = touching this switch and 7 others ✗
}

// After — adding a state = adding a class, touching nothing else
class RefundRequestedState implements OrderState {
  confirm(order: Order):  void { order.log("Cannot confirm: refund requested."); }
  ship(order: Order):     void { order.log("Cannot ship: refund requested."); }
  cancel(order: Order):   void {
    order.log("Refund approved — cancelling order.");
    order.setState(new CancelledState()); // ✓ handles its own transitions
  }
  deliver(order: Order):  void { order.log("Order in refund process."); }
  getLabel(): string { return "REFUND_REQUESTED"; }
}
```

**Q23. "You're designing a subscription billing system with states: Trial → Active → PastDue → Suspended → Cancelled (and potentially Reactivated). How do you model this with the State pattern, including time-based automatic transitions?"**
A:
```ts
interface SubscriptionState {
  charge(sub: Subscription): Promise<void>;
  cancel(sub: Subscription): Promise<void>;
  reactivate(sub: Subscription): Promise<void>;
  onPaymentSuccess(sub: Subscription): Promise<void>;
  onPaymentFailure(sub: Subscription): Promise<void>;
  onTrialEnd(sub: Subscription): Promise<void>;
  getLabel(): string;
  canAccessService(): boolean;
}

class TrialState implements SubscriptionState {
  getLabel(): string         { return "TRIAL"; }
  canAccessService(): boolean { return true; }

  async charge(_sub: Subscription): Promise<void> { /* No charge during trial */ }
  async cancel(sub: Subscription): Promise<void>  {
    sub.log("Trial cancelled.");
    sub.setState(new CancelledState());
  }
  async reactivate(_sub: Subscription): Promise<void> { /* already active */ }
  async onPaymentSuccess(_sub: Subscription): Promise<void> { /* no payment in trial */ }
  async onPaymentFailure(_sub: Subscription): Promise<void> { /* no payment in trial */ }

  async onTrialEnd(sub: Subscription): Promise<void> {
    sub.log("Trial ended — initiating first charge.");
    sub.setState(new ActiveState());
    await sub.getCurrentState().charge(sub); // immediately attempt billing
  }
}

class ActiveState implements SubscriptionState {
  getLabel(): string         { return "ACTIVE"; }
  canAccessService(): boolean { return true; }

  async charge(sub: Subscription): Promise<void> {
    sub.log("Charging subscription...");
    await sub.processPayment(); // triggers onPaymentSuccess or onPaymentFailure
  }
  async cancel(sub: Subscription): Promise<void> {
    sub.log("Subscription cancelled.");
    sub.setState(new CancelledState());
  }
  async reactivate(_sub: Subscription): Promise<void> { /* already active */ }
  async onPaymentSuccess(sub: Subscription): Promise<void> {
    sub.log("Payment successful — renewing subscription.");
    sub.extendBillingPeriod();
  }
  async onPaymentFailure(sub: Subscription): Promise<void> {
    sub.log("Payment failed — marking as past due.");
    sub.setState(new PastDueState());
  }
  async onTrialEnd(_sub: Subscription): Promise<void> { /* not in trial */ }
}

class PastDueState implements SubscriptionState {
  private readonly GRACE_PERIOD_DAYS = 7;
  getLabel(): string         { return "PAST_DUE"; }
  canAccessService(): boolean { return true; } // grace period — still accessible

  async charge(sub: Subscription): Promise<void> {
    sub.log("Retrying payment for past-due subscription...");
    await sub.processPayment();
  }
  async cancel(sub: Subscription): Promise<void> {
    sub.setState(new CancelledState());
  }
  async reactivate(_sub: Subscription): Promise<void> { /* charge first */ }
  async onPaymentSuccess(sub: Subscription): Promise<void> {
    sub.log("Past-due payment received — reactivating.");
    sub.setState(new ActiveState());
    sub.extendBillingPeriod();
  }
  async onPaymentFailure(sub: Subscription): Promise<void> {
    if (sub.daysSinceLastPayment() >= this.GRACE_PERIOD_DAYS) {
      sub.log("Grace period expired — suspending subscription.");
      sub.setState(new SuspendedState());
    } else {
      sub.log(`Payment failed — ${this.GRACE_PERIOD_DAYS - sub.daysSinceLastPayment()} days left in grace period.`);
      sub.scheduleRetry(24 * 60 * 60 * 1000); // retry in 24h
    }
  }
  async onTrialEnd(_sub: Subscription): Promise<void> { }
}

// Time-based automatic transitions via a scheduler
class SubscriptionScheduler {
  async processDailyTransitions(subscriptions: Subscription[]): Promise<void> {
    for (const sub of subscriptions) {
      if (sub.isInTrial() && sub.trialEndsToday()) {
        await sub.getCurrentState().onTrialEnd(sub);
      }
      if (sub.isPastDue() && sub.isRetryDue()) {
        await sub.getCurrentState().charge(sub);
      }
    }
  }
}
```

**Q24. "An interview asks: 'How is the State pattern different from just using a bunch of boolean flags on a class?' Give a clear, structured answer."**
A: A structured answer that names four specific problems with flags:

> **1. Invalid combinations are possible.** With flags `isShipped`, `isDelivered`, `isCancelled` on a single Order, nothing prevents `isShipped = true` and `isCancelled = true` simultaneously — a state the system was never designed to handle. ConcreteState classes make invalid combinations structurally impossible: there is no `ShippedState` that is also a `CancelledState`.
>
> **2. Every operation needs to check every flag.** A `canRefund()` method must check `!isCancelled && !isDelivered && isShipped && daysSinceShipment < 30` — and this same fan-out of conditions appears in every method. With State, `canRefund()` is a one-liner in each ConcreteState: `return true` in `ShippedState`, `return false` in `DeliveredState`.
>
> **3. Adding a new state requires modifying every method.** Adding `isRefundRequested` means adding `&& !isRefundRequested` to every conditional in the class. Adding a `RefundRequestedState` class touches zero existing code.
>
> **4. Behavior is not co-located with state.** With flags, you have to read the entire class to understand what "shipped" means for each operation. With State, `ShippedState` tells you everything that's true, allowed, and disallowed when the order is shipped — in one file, independently readable and testable.

```ts
// Flags — invalid states possible, conditions scattered
class Order {
  isPending    = true;
  isConfirmed  = false;
  isShipped    = false;
  isDelivered  = false;
  isCancelled  = false;

  cancel(): void {
    if (this.isDelivered) throw new Error("Can't cancel delivered order");
    if (this.isCancelled) throw new Error("Already cancelled");
    if (this.isShipped)   { /* different logic */ }
    else { /* different logic */ }
    // ... and so on in every method ✗
  }
}

// State pattern — one class per state, behavior is self-contained
class ShippedState implements OrderState {
  cancel(order: Order): void {
    order.log("Cannot cancel shipped order — initiate return instead.");
    // No flags to check. This state IS the answer.
  }
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Switch / If-Else | Boolean Flags | State Pattern |
|---|---|---|---|
| **Adding a new state** | Edit every switch in every method | Add a flag, update every condition | Add one new class |
| **Adding a new operation** | Add a new switch with all cases | Add a new method with all flag checks | Add a method to interface + implement in each state |
| **Invalid state combinations** | Possible — no enforcement | Possible — many invalid flag combos | Impossible — one class = one valid state |
| **Behavior co-location** | Scattered across methods | Scattered across methods | All state behavior in one class |
| **Testability** | Must test the whole class | Must test all flag combinations | Each state tested in isolation |
| **OCP compliance** | Violates — edit existing methods | Violates — edit existing methods | Complies — new state = new class |
| **Readability** | Degrades with state count | Degrades with flag count | Constant — each state is readable alone |
| **Transition safety** | No enforcement | No enforcement | Guard conditions in state methods |

## State Pattern Variants at a Glance

| Variant | Key characteristic | Best used for |
|---|---|---|
| **Classic (class-per-state)** | Each state is a class implementing a State interface | Complex FSMs with many behaviors per state |
| **Functional (object literal)** | States as plain objects with function properties | Simple FSMs; functional-style codebases |
| **Hierarchical / Nested FSM** | States contain inner FSMs for sub-behaviors | States with their own independent sub-states |
| **Parallel / Orthogonal** | Multiple independent state machines on one context | Objects with independent behavioral dimensions |
| **Statechart (XState-style)** | Declarative state config with guards, entry/exit, parallel | Complex UI flows, protocol handling, React/Vue apps |
| **Parameterised state** | State carries data (`RetryingState(attempt)`) | States that vary in degree, not kind |
| **Persistent state** | State serialised to DB; restored via factory | Long-running business processes across restarts |

**Tip for the interview:** At the 5 YOE level, "what is the State pattern" surfaces as: how do you clean up a god-class service full of switch statements, how do you model an order lifecycle that must enforce business rules at each stage, how do you add a new subscription tier without touching existing billing code, or how do you build a reconnecting WebSocket client. The sharp answer names the specific failure mode of the switch-based approach (OCP violation — every new state touches every existing switch), shows the three-participant structure (Context delegating to ConcreteState), mentions entry/exit actions and guard conditions for depth, addresses persistence (serialize the label, restore via factory), and connects it to at least one composing pattern (Observer for state change notifications, Command for undo/redo). Distinguishing State from Strategy clearly — "Strategy is chosen by the client and stays fixed; State changes itself in response to events" — is the precision that lands at 5 YOE.
