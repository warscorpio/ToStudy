# Design Patterns — Behavioral: Mediator — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Mediator pattern?**
A: The Mediator pattern is a behavioral design pattern that defines an object — the *mediator* — that encapsulates how a set of objects interact. Instead of objects referring to each other directly (creating a tightly coupled web), they communicate exclusively through the mediator. Objects no longer need to know about each other; they only need to know about the mediator. The GoF definition: *"Define an object that encapsulates how a set of objects interact. Mediator promotes loose coupling by keeping objects from referring to each other explicitly, and it lets you vary their interaction independently."*

The essential mental model: replace a mesh network of N×(N-1) direct connections between N components with a hub-and-spoke model where every component connects only to the central mediator. Complexity drops from O(N²) to O(N).

**Q2. What problem does the Mediator pattern solve?**
A: It solves the problem of *communication complexity* in systems where many objects need to interact with many other objects. Without a mediator, each component must hold references to every other component it might communicate with:

```ts
// WITHOUT Mediator — every component knows about every other
class LoanApprovalService {
  constructor(
    private readonly creditService: CreditService,       // direct ref
    private readonly kycService: KycService,             // direct ref
    private readonly nachService: NachService,           // direct ref
    private readonly notificationService: NotificationService, // direct ref
    private readonly auditService: AuditService,         // direct ref
    private readonly disbursementService: DisbursementService, // direct ref
  ) {}

  async approve(loanId: string): Promise<void> {
    await this.creditService.check(loanId);
    await this.kycService.verify(loanId);
    await this.nachService.register(loanId);
    await this.notificationService.notify(loanId);
    await this.auditService.log(loanId);
    await this.disbursementService.schedule(loanId);
  }
}
```

Adding a new step (e.g., fraud detection) means modifying `LoanApprovalService`. Changing the order of steps means modifying `LoanApprovalService`. Testing `LoanApprovalService` requires mocking all six dependencies. The service accumulates orchestration logic that has nothing to do with loan approval business rules.

With a Mediator, each service sends a request or signal to the mediator and responds to signals from it — knowing nothing about who else participates in the workflow.

**Q3. What are the participants in the Mediator pattern?**
A:
- **Mediator** — the interface that defines how components communicate with the mediator (`notify(sender, event)`).
- **ConcreteMediator** — implements the interaction logic. Knows about all components and coordinates their communication. This is where the workflow lives.
- **Colleague** — a component that interacts with other components only through the mediator. Each colleague holds a reference to the mediator, not to other colleagues.
- **ConcreteColleague** — a specific component (e.g., `CreditService`, `KycService`) that sends events to and receives instructions from the mediator.

**Q4. What is the core structural difference between Mediator and Observer?**
A: They are frequently confused because both decouple senders from receivers. The distinction is in *direction and control*:

| Aspect                  | Mediator                                               | Observer                                                  |
|---                      |---                                                     |---                                                        |
| Communication direction | Bidirectional — mediator coordinates all participants  | Unidirectional — subject pushes to observers              |
| Who controls flow?      | Mediator — it decides what happens in response to events | Subject — it notifies; observers react independently    |
| Coupling                | Colleagues know the mediator; mediator knows everyone  | Subject knows observers; observers know the subject       |
| Interaction type        | Many-to-many, coordinated workflow                     | One-to-many, independent reactions                        |
| Centralization          | Explicitly centralized in the mediator                 | Decentralized — each observer reacts on its own           |
| Best for                | Orchestrated workflows with sequencing and conditions  | Broadcast notifications with independent side effects     |

Mediator is about *orchestration* — the mediator directs traffic. Observer is about *notification* — the subject broadcasts and observers react as they see fit. In a loan workflow: the Mediator decides that after KYC completes, NACH registration must happen next, then disbursement. With Observer, KYC completing would emit an event and NACH, disbursement, and audit would all subscribe — with no central coordination of order or conditions.

**Q5. What is the difference between Mediator and Facade?**
A: Both introduce a central point that simplifies interactions with a subsystem, but they serve different purposes:

| Aspect               | Mediator                                                   | Facade                                                     |
|---                   |---                                                         |---                                                         |
| Intent               | Coordinate *communication between* components              | Simplify *external access to* a subsystem                  |
| Who uses it?         | The components themselves communicate through it           | External clients use it to access the subsystem            |
| Component awareness  | Components know about the mediator                         | Components don't know about the facade                     |
| Direction of coupling| Bidirectional — components ↔ mediator                      | Unidirectional — client → facade → subsystem               |
| Interaction type     | Internal coordination between peers                        | External simplification of a complex API                   |
| Example              | Loan workflow coordinator that sequences KYC, NACH, credit | `LoanServiceFacade` that combines repo, gateway, notifier behind one method |

Facade hides complexity from the *outside*; Mediator manages complexity *between* insiders.

## Section 2: Implementation

**Q6. What does a canonical Mediator implementation look like in TypeScript?**
A:
```ts
// Mediator interface
interface LoanWorkflowMediator {
  notify(sender: LoanWorkflowColleague, event: string, context: LoanContext): Promise<void>;
}

// Colleague base — knows only the mediator
abstract class LoanWorkflowColleague {
  constructor(protected mediator: LoanWorkflowMediator) {}

  setMediator(mediator: LoanWorkflowMediator): void {
    this.mediator = mediator;
  }
}

// ConcreteColleagues — each does its job and signals the mediator
class CreditCheckColleague extends LoanWorkflowColleague {
  async runCreditCheck(context: LoanContext): Promise<void> {
    const score = await creditBureau.getScore(context.userId);
    context.creditScore = score;
    const passed = score >= 650;
    await this.mediator.notify(this, passed ? "credit.passed" : "credit.failed", context);
  }
}

class KycColleague extends LoanWorkflowColleague {
  async verifyKyc(context: LoanContext): Promise<void> {
    const verified = await kycProvider.verify(context.userId, context.panNumber);
    context.kycVerified = verified;
    await this.mediator.notify(this, verified ? "kyc.passed" : "kyc.failed", context);
  }
}

class NachColleague extends LoanWorkflowColleague {
  async registerNach(context: LoanContext): Promise<void> {
    const mandateId = await nachGateway.register(context.userId, context.bankAccountId);
    context.nachMandateId = mandateId;
    await this.mediator.notify(this, "nach.registered", context);
  }
}

class DisbursementColleague extends LoanWorkflowColleague {
  async disburse(context: LoanContext): Promise<void> {
    const txnId = await disbursementGateway.transfer(context.loanId, context.amount);
    context.disbursementTxnId = txnId;
    await this.mediator.notify(this, "disbursement.completed", context);
  }
}

class NotificationColleague extends LoanWorkflowColleague {
  async sendApprovalSms(context: LoanContext): Promise<void> {
    await smsService.send(context.userId, `Loan ₹${context.amount} approved`);
    await this.mediator.notify(this, "notification.sent", context);
  }
}

// ConcreteMediator — where ALL orchestration logic lives
class LoanApprovalMediator implements LoanWorkflowMediator {
  constructor(
    private readonly credit: CreditCheckColleague,
    private readonly kyc: KycColleague,
    private readonly nach: NachColleague,
    private readonly disbursement: DisbursementColleague,
    private readonly notification: NotificationColleague,
  ) {
    // Register self with all colleagues
    [credit, kyc, nach, disbursement, notification]
      .forEach(c => c.setMediator(this));
  }

  async start(context: LoanContext): Promise<void> {
    await this.credit.runCreditCheck(context); // Step 1 — kicks off the chain
  }

  async notify(
    sender: LoanWorkflowColleague,
    event: string,
    context: LoanContext,
  ): Promise<void> {
    // ALL workflow logic is here — colleagues are completely unaware of each other
    switch (event) {
      case "credit.passed":
        await this.kyc.verifyKyc(context);
        break;

      case "credit.failed":
        await this.notification.sendRejectionSms(context);
        break;

      case "kyc.passed":
        await this.nach.registerNach(context);
        break;

      case "kyc.failed":
        await this.notification.sendRejectionSms(context);
        break;

      case "nach.registered":
        await this.disbursement.disburse(context);
        break;

      case "disbursement.completed":
        await this.notification.sendApprovalSms(context);
        break;

      case "notification.sent":
        console.log(`Loan workflow completed for ${context.loanId}`);
        break;
    }
  }
}

// Usage — LoanController or service kicks it off
const context: LoanContext = {
  loanId: "L001",
  userId: "U123",
  amount: 50000,
  panNumber: "ABCDE1234F",
  bankAccountId: "ACC789",
};

const mediator = new LoanApprovalMediator(
  new CreditCheckColleague(null!),
  new KycColleague(null!),
  new NachColleague(null!),
  new DisbursementColleague(null!),
  new NotificationColleague(null!),
);

await mediator.start(context);
```

**Q7. What is a "context object" in Mediator workflows and why is it important?**
A: A context object (sometimes called a workflow context, shared state, or payload) is a mutable object passed through the mediator workflow that accumulates state as each step completes. It solves the problem of how colleagues share results without knowing about each other:

```ts
interface LoanContext {
  // Input — set at workflow start
  loanId: string;
  userId: string;
  amount: number;
  panNumber: string;
  bankAccountId: string;

  // Accumulated by colleagues as steps complete
  creditScore?: number;           // set by CreditCheckColleague
  kycVerified?: boolean;          // set by KycColleague
  nachMandateId?: string;         // set by NachColleague
  disbursementTxnId?: string;     // set by DisbursementColleague

  // Outcome
  approved?: boolean;
  rejectionReason?: string;
  completedAt?: Date;
}
```

The context object keeps colleagues decoupled — `DisbursementColleague` reads `context.nachMandateId` without knowing it was set by `NachColleague`. The mediator owns the context lifecycle; colleagues only read/write their own slice of it.

Design considerations:
- Keep context serializable — if workflow state needs to survive process restarts (for durable workflows), it must be JSON-serializable and persistable.
- Treat context as append-only — a step should not overwrite results written by a previous step unless explicitly correcting.
- Validate completeness in the mediator before each step — don't assume context fields are set; check and throw meaningful errors if prerequisites are missing.

**Q8. How do you handle errors and compensating transactions in a Mediator workflow?**
A: The mediator is the ideal place to handle failures and trigger compensating actions — it has the full picture of which steps completed and what needs to be reversed:

```ts
class LoanApprovalMediator implements LoanWorkflowMediator {
  private completedSteps: string[] = [];

  async notify(sender: LoanWorkflowColleague, event: string, context: LoanContext): Promise<void> {
    this.completedSteps.push(event);

    switch (event) {
      case "nach.registered":
        try {
          await this.disbursement.disburse(context);
        } catch (err) {
          // Disbursement failed after NACH registered — compensate
          await this.compensate(context, err as Error);
        }
        break;

      // ... other cases
    }
  }

  private async compensate(context: LoanContext, err: Error): Promise<void> {
    logger.error({ loanId: context.loanId, err, steps: this.completedSteps },
      "Loan workflow failed — beginning compensation"
    );

    // Reverse completed steps in reverse order — Saga compensation
    if (this.completedSteps.includes("nach.registered") && context.nachMandateId) {
      try {
        await nachGateway.cancel(context.nachMandateId);
        logger.info({ mandateId: context.nachMandateId }, "NACH mandate cancelled");
      } catch (compensationErr) {
        logger.error({ compensationErr }, "NACH cancellation failed — manual intervention required");
        // Alert ops team, raise incident
      }
    }

    context.approved = false;
    context.rejectionReason = `Disbursement failed: ${err.message}`;
    await this.notification.sendFailureSms(context);
  }
}
```

This is the Mediator pattern implementing a *Saga* — the mediator both orchestrates the happy path and owns the compensation logic. Each compensation step is also mediated; colleagues don't know they're being compensated.

**Q9. How does the CQRS pattern relate to Mediator?**
A: CQRS (Command Query Responsibility Segregation) separates write operations (commands) from read operations (queries). The Mediator pattern is almost universally used to implement CQRS because it provides the dispatch mechanism — commands and queries are sent to the mediator, which routes them to the correct handler:

```ts
// Command — an intent to change state
interface Command {
  readonly type: string;
}

class ApproveLoanCommand implements Command {
  readonly type = "ApproveLoan";
  constructor(
    public readonly loanId: string,
    public readonly approverId: string,
  ) {}
}

// Query — a request for data with no side effects
interface Query<TResult> {
  readonly type: string;
}

class GetLoanQuery implements Query<LoanDto> {
  readonly type = "GetLoan";
  constructor(public readonly loanId: string) {}
}

// Handlers
interface CommandHandler<TCommand extends Command> {
  handle(command: TCommand): Promise<void>;
}

interface QueryHandler<TQuery extends Query<TResult>, TResult> {
  handle(query: TQuery): Promise<TResult>;
}

// Mediator — the CQRS dispatcher
class CqrsMediator {
  private commandHandlers = new Map<string, CommandHandler<any>>();
  private queryHandlers = new Map<string, QueryHandler<any, any>>();

  registerCommand<T extends Command>(type: string, handler: CommandHandler<T>): void {
    this.commandHandlers.set(type, handler);
  }

  registerQuery<T extends Query<R>, R>(type: string, handler: QueryHandler<T, R>): void {
    this.queryHandlers.set(type, handler);
  }

  async send<T extends Command>(command: T): Promise<void> {
    const handler = this.commandHandlers.get(command.type);
    if (!handler) throw new Error(`No handler registered for command: ${command.type}`);
    return handler.handle(command);
  }

  async query<TResult>(query: Query<TResult>): Promise<TResult> {
    const handler = this.queryHandlers.get(query.type);
    if (!handler) throw new Error(`No handler registered for query: ${query.type}`);
    return handler.handle(query);
  }
}

// Handlers are registered independently
class ApproveLoanCommandHandler implements CommandHandler<ApproveLoanCommand> {
  constructor(private readonly loanRepo: LoanRepository) {}

  async handle(command: ApproveLoanCommand): Promise<void> {
    const loan = await this.loanRepo.findById(command.loanId);
    loan.approve(command.approverId);
    await this.loanRepo.save(loan);
  }
}

class GetLoanQueryHandler implements QueryHandler<GetLoanQuery, LoanDto> {
  constructor(private readonly loanReadRepo: LoanReadRepository) {}

  async handle(query: GetLoanQuery): Promise<LoanDto> {
    return this.loanReadRepo.findById(query.loanId);
  }
}

// Controller — depends only on the mediator
class LoanController {
  constructor(private readonly mediator: CqrsMediator) {}

  async approve(loanId: string, approverId: string): Promise<void> {
    await this.mediator.send(new ApproveLoanCommand(loanId, approverId));
  }

  async getLoan(loanId: string): Promise<LoanDto> {
    return this.mediator.query(new GetLoanQuery(loanId));
  }
}
```

**Q10. How does NestJS's built-in CQRS module implement the Mediator pattern?**
A: NestJS's `@nestjs/cqrs` is a first-class implementation of CQRS via Mediator. The `CommandBus` and `QueryBus` are the mediators; `@CommandHandler` and `@QueryHandler` are the registered handlers:

```ts
// Setup
@Module({
  imports: [CqrsModule],
  providers: [
    ApproveLoanCommandHandler,
    GetLoanQueryHandler,
    LoanApprovalSaga,       // for event-driven side effects
  ],
})
export class LoanModule {}

// Command
export class ApproveLoanCommand {
  constructor(
    public readonly loanId: string,
    public readonly approverId: string,
  ) {}
}

// Handler — registered automatically via @CommandHandler decorator
@CommandHandler(ApproveLoanCommand)
export class ApproveLoanCommandHandler
  implements ICommandHandler<ApproveLoanCommand> {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly eventBus: EventBus,
  ) {}

  async execute(command: ApproveLoanCommand): Promise<void> {
    const loan = await this.loanRepo.findById(command.loanId);
    loan.approve(command.approverId);
    await this.loanRepo.save(loan);

    // Publish domain event — picked up by Sagas and EventHandlers
    this.eventBus.publish(new LoanApprovedEvent(loan.id, loan.userId, loan.amount));
  }
}

// Query
export class GetLoanQuery {
  constructor(public readonly loanId: string) {}
}

@QueryHandler(GetLoanQuery)
export class GetLoanQueryHandler implements IQueryHandler<GetLoanQuery, LoanDto> {
  constructor(private readonly loanReadRepo: LoanReadRepository) {}

  async execute(query: GetLoanQuery): Promise<LoanDto> {
    return this.loanReadRepo.findById(query.loanId);
  }
}

// Controller — dispatches via CommandBus and QueryBus (the mediators)
@Controller("loans")
export class LoanController {
  constructor(
    private readonly commandBus: CommandBus,
    private readonly queryBus: QueryBus,
  ) {}

  @Post(":id/approve")
  async approve(@Param("id") loanId: string, @Body() dto: ApproveDto): Promise<void> {
    await this.commandBus.execute(new ApproveLoanCommand(loanId, dto.approverId));
  }

  @Get(":id")
  async getLoan(@Param("id") loanId: string): Promise<LoanDto> {
    return this.queryBus.execute(new GetLoanQuery(loanId));
  }
}
```
The controller has zero business logic and zero dependency on any service — only on `CommandBus` and `QueryBus`. Adding a new command means adding a handler class and registering it; the controller never changes.

## Section 3: Mediator as Pipeline / Middleware

**Q11. How does Express.js middleware implement the Mediator pattern?**
A: Express's middleware chain is a linear Mediator where the `app` object is the mediator and each middleware is a colleague. Middleware components don't call each other directly — they call `next()` to signal the mediator (Express's internal dispatch) to move to the next step:

```ts
// Express app = the Mediator
const app = express();

// Colleagues — each does its job and calls next() to signal completion
app.use((req, res, next) => {
  req.id = uuid();              // RequestId colleague
  next();                       // notify mediator: move to next
});

app.use((req, res, next) => {
  const token = req.headers.authorization;
  if (!token) return res.status(401).json({ error: "Unauthorized" });
  req.user = jwt.verify(token, SECRET); // Auth colleague
  next();
});

app.use((req, res, next) => {
  const key = `ratelimit:${req.user.id}`;
  rateLimiter.check(key)        // RateLimit colleague
    .then(() => next())
    .catch(() => res.status(429).json({ error: "Too many requests" }));
});

app.post("/loans/:id/approve", async (req, res) => {
  // Route handler — the final "colleague"
  await loanService.approve(req.params.id, req.user.id);
  res.json({ success: true });
});
```
Each middleware is completely unaware of other middleware. The Express `app` (mediator) owns the routing and sequencing. Adding a new middleware step — say, an audit logging middleware — is inserting a new colleague into the chain, not modifying existing middleware.

**Q12. How does NestJS's request pipeline implement the Mediator pattern?**
A: NestJS's request pipeline — Guards → Interceptors (before) → Pipes → Controller → Interceptors (after) → Exception Filters — is a structured Mediator with typed phases. Each component in the pipeline communicates through NestJS's execution context (the mediator's shared context object):

```ts
// Guard — colleague that controls access
@Injectable()
export class JwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();
    const token = req.headers.authorization?.split(" ")[1];
    if (!token) return false;
    req.user = this.jwtService.verify(token);
    return true;
  }
}

// Pipe — colleague that transforms/validates input
@Injectable()
export class ParseLoanIdPipe implements PipeTransform {
  transform(value: string): string {
    if (!isUUID(value)) throw new BadRequestException("Invalid loan ID format");
    return value;
  }
}

// Interceptor — colleague that wraps execution
@Injectable()
export class AuditInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const req = context.switchToHttp().getRequest();
    const start = Date.now();
    return next.handle().pipe(
      tap(() => this.auditLog(req, Date.now() - start))
    );
  }
}

// Controller — end colleague; knows nothing about guards, pipes, interceptors
@UseGuards(JwtAuthGuard)
@UseInterceptors(AuditInterceptor)
@Controller("loans")
export class LoanController {
  @Post(":id/approve")
  async approve(
    @Param("id", ParseLoanIdPipe) loanId: string,
    @Request() req: AuthenticatedRequest,
  ): Promise<void> {
    await this.commandBus.execute(new ApproveLoanCommand(loanId, req.user.id));
  }
}
```
NestJS itself is the ConcreteMediator — it orchestrates which components run, in what order, and with what shared context. Individual components (guards, pipes, interceptors, controllers) are colleagues that never reference each other.

**Q13. How is the Chain of Responsibility pattern different from Mediator, and when do they overlap?**
A: Both patterns route requests through a sequence of handlers, but the locus of control differs:

| Aspect                  | Chain of Responsibility                              | Mediator                                              |
|---                      |---                                                   |---                                                    |
| Flow control            | Each handler decides whether to pass to the next    | Mediator decides the entire routing logic             |
| Handler coupling        | Each handler knows the next handler                 | Handlers (colleagues) know only the mediator          |
| Routing logic location  | Distributed across handlers                         | Centralized in the mediator                           |
| Termination             | Any handler can stop the chain                      | Mediator determines termination conditions            |
| Modification            | Adding a step = inserting into the chain            | Adding a step = registering with the mediator         |
| Best for                | Sequential validation with early exit               | Complex multi-party workflows with conditional paths  |

They overlap in middleware pipelines: Express middleware behaves like Chain of Responsibility (each middleware calls `next()` itself) but also has characteristics of Mediator (the `app` owns the middleware stack). NestJS's pipeline is more Mediator-like because NestJS owns the sequencing entirely — individual components don't call `next()`. In loan approval BRE (Business Rules Engine), a Chain of Responsibility runs validations in sequence where any rule can reject; a Mediator orchestrates the post-approval workflow where each step triggers different branches.

## Section 4: Mediator in Distributed Systems — Saga Orchestration

**Q14. How does the Saga Orchestration pattern implement Mediator?**
A: In microservices, the Saga pattern manages distributed transactions across services. There are two implementations: *choreography* (Observer-based — each service reacts to events) and *orchestration* (Mediator-based — a central saga orchestrator directs each service). The orchestrator is the Mediator; each microservice is a colleague:

```ts
// Saga Orchestrator — the Mediator for a distributed loan disbursement transaction
@Injectable()
export class LoanDisbursementSagaOrchestrator {
  constructor(
    private readonly creditServiceClient: CreditServiceClient,    // Remote Proxy colleague
    private readonly kycServiceClient: KycServiceClient,          // Remote Proxy colleague
    private readonly nachServiceClient: NachServiceClient,        // Remote Proxy colleague
    private readonly paymentServiceClient: PaymentServiceClient,  // Remote Proxy colleague
    private readonly sagaRepo: SagaStateRepository,
  ) {}

  async execute(sagaId: string, loanId: string, userId: string): Promise<void> {
    const state = await this.sagaRepo.create({
      sagaId,
      loanId,
      userId,
      step: "STARTED",
      completedSteps: [],
    });

    try {
      // Step 1 — Credit check
      await this.sagaRepo.update(sagaId, { step: "CREDIT_CHECK" });
      const creditResult = await this.creditServiceClient.check(userId);
      if (!creditResult.passed) throw new CreditCheckFailedError(creditResult.reason);
      await this.sagaRepo.update(sagaId, {
        completedSteps: [...state.completedSteps, "CREDIT_CHECK"],
        creditScore: creditResult.score,
      });

      // Step 2 — KYC verification
      await this.sagaRepo.update(sagaId, { step: "KYC_VERIFICATION" });
      await this.kycServiceClient.verify(userId, loanId);
      await this.sagaRepo.update(sagaId, {
        completedSteps: [...state.completedSteps, "CREDIT_CHECK", "KYC_VERIFICATION"],
      });

      // Step 3 — NACH registration
      await this.sagaRepo.update(sagaId, { step: "NACH_REGISTRATION" });
      const nachResult = await this.nachServiceClient.register(userId, loanId);
      await this.sagaRepo.update(sagaId, {
        completedSteps: [...state.completedSteps, "CREDIT_CHECK", "KYC_VERIFICATION", "NACH_REGISTRATION"],
        nachMandateId: nachResult.mandateId,
      });

      // Step 4 — Payment disbursement
      await this.sagaRepo.update(sagaId, { step: "DISBURSEMENT" });
      const paymentResult = await this.paymentServiceClient.disburse(loanId, userId);
      await this.sagaRepo.update(sagaId, {
        step: "COMPLETED",
        completedSteps: [...state.completedSteps, "CREDIT_CHECK", "KYC_VERIFICATION", "NACH_REGISTRATION", "DISBURSEMENT"],
        disbursementTxnId: paymentResult.transactionId,
      });

    } catch (err) {
      await this.compensate(sagaId, err as Error);
      throw err;
    }
  }

  private async compensate(sagaId: string, err: Error): Promise<void> {
    const state = await this.sagaRepo.findById(sagaId);
    await this.sagaRepo.update(sagaId, { step: "COMPENSATING", failureReason: err.message });

    // Reverse completed steps in reverse order
    const compensations: Record<string, () => Promise<void>> = {
      NACH_REGISTRATION: async () => {
        if (state.nachMandateId) {
          await this.nachServiceClient.cancel(state.nachMandateId);
        }
      },
      KYC_VERIFICATION: async () => {
        await this.kycServiceClient.rollback(state.loanId);
      },
    };

    for (const step of [...state.completedSteps].reverse()) {
      if (compensations[step]) {
        try {
          await compensations[step]();
        } catch (compensationErr) {
          logger.error({ step, compensationErr, sagaId },
            "Compensation failed — requires manual intervention"
          );
          // Write to dead-letter store for ops team
        }
      }
    }

    await this.sagaRepo.update(sagaId, { step: "COMPENSATED" });
  }
}
```

**Q15. What is the difference between Saga Choreography and Saga Orchestration, and how does Mediator relate to each?**
A:

| Aspect               | Choreography (Observer-based)                              | Orchestration (Mediator-based)                              |
|---                   |---                                                         |---                                                          |
| Pattern              | Observer / Pub-Sub                                         | Mediator                                                    |
| Control              | Decentralized — each service reacts to events              | Centralized — orchestrator directs each service             |
| Coupling             | Services coupled to event schemas                          | Services coupled only to orchestrator's interface           |
| Visibility           | Workflow is implicit — pieced together from event flow     | Workflow is explicit — visible in orchestrator code         |
| Debugging            | Hard — must trace events across services                   | Easier — single place to trace the workflow                 |
| Failure handling     | Each service must handle its own compensation              | Orchestrator manages compensation centrally                 |
| Scalability          | High — no central bottleneck                               | Central orchestrator can be a bottleneck                    |
| Best for             | Simple, independent side effects (notify, audit, index)    | Complex workflows with conditions, retries, compensation    |

For a NACH payment + KYC + credit check workflow with compensating transactions, orchestration (Mediator) is the correct choice — the workflow has conditional branches, specific ordering requirements, and compensation logic that is tightly interdependent. For broadcasting a `LoanApproved` event to an SMS service, an analytics service, and an audit service that react independently, choreography (Observer) is sufficient and simpler.

## Section 5: Pitfalls & Anti-patterns

**Q16. What is the "God Mediator" anti-pattern?**
A: The God Mediator is when the mediator accumulates so much logic that it becomes a monolithic class that knows everything and controls everything — essentially a distributed God Object:

```ts
// ANTI-PATTERN — mediator that has grown into a God class
class ApplicationMediator {
  // 15 colleague references
  async notify(sender: any, event: string, context: any): Promise<void> {
    // 500-line switch statement handling every possible event
    // in the entire application
    switch (event) {
      case "loan.approved":     /* ... */ break;
      case "loan.rejected":     /* ... */ break;
      case "user.created":      /* ... */ break;
      case "repayment.due":     /* ... */ break;
      case "kyc.verified":      /* ... */ break;
      // ... 40 more cases
    }
  }
}
```

Signs your mediator has become a God Mediator:
- The mediator's `notify` method has more than 10–15 cases.
- The mediator holds references to more than 6–8 colleagues.
- The mediator's business logic cannot be described in one sentence.
- Changing any one workflow requires reading the entire mediator.

Fix: split the mediator by bounded context or workflow. `LoanApprovalMediator`, `RepaymentWorkflowMediator`, `UserOnboardingMediator` — each mediates one cohesive workflow. They may communicate with each other via events (Observer), not by one mediator directly calling another.

**Q17. How do you keep the Mediator testable as it grows?**
A: The mediator concentrates complexity — which makes it the most important class to test thoroughly. Strategies:

```ts
describe("LoanApprovalMediator", () => {
  let mediator: LoanApprovalMediator;
  let credit: jest.Mocked<CreditCheckColleague>;
  let kyc: jest.Mocked<KycColleague>;
  let nach: jest.Mocked<NachColleague>;
  let disbursement: jest.Mocked<DisbursementColleague>;
  let notification: jest.Mocked<NotificationColleague>;

  beforeEach(() => {
    credit = { runCreditCheck: jest.fn(), setMediator: jest.fn() } as any;
    kyc = { verifyKyc: jest.fn(), setMediator: jest.fn() } as any;
    nach = { registerNach: jest.fn(), setMediator: jest.fn() } as any;
    disbursement = { disburse: jest.fn(), setMediator: jest.fn() } as any;
    notification = { sendApprovalSms: jest.fn(), sendRejectionSms: jest.fn(), setMediator: jest.fn() } as any;

    mediator = new LoanApprovalMediator(credit, kyc, nach, disbursement, notification);
  });

  it("triggers KYC after credit check passes", async () => {
    const context = buildLoanContext();
    await mediator.notify(credit, "credit.passed", context);
    expect(kyc.verifyKyc).toHaveBeenCalledWith(context);
    expect(notification.sendRejectionSms).not.toHaveBeenCalled();
  });

  it("sends rejection SMS when credit check fails", async () => {
    const context = buildLoanContext();
    await mediator.notify(credit, "credit.failed", context);
    expect(notification.sendRejectionSms).toHaveBeenCalledWith(context);
    expect(kyc.verifyKyc).not.toHaveBeenCalled();
  });

  it("triggers disbursement after NACH registration", async () => {
    const context = buildLoanContext({ nachMandateId: "mandate-123" });
    await mediator.notify(nach, "nach.registered", context);
    expect(disbursement.disburse).toHaveBeenCalledWith(context);
  });

  it("compensates NACH on disbursement failure", async () => {
    disbursement.disburse.mockRejectedValue(new Error("Payment gateway timeout"));
    const context = buildLoanContext({ nachMandateId: "mandate-123" });
    await mediator.notify(nach, "nach.registered", context);
    expect(notification.sendFailureSms).toHaveBeenCalled();
    // assert NACH cancellation was attempted
  });
});
```
Each test exercises one transition in the mediator's state machine — one event → one expected next action. This keeps tests focused and makes every workflow branch visible in the test suite.

**Q18. What is the "anemic mediator" anti-pattern?**
A: The anemic mediator is the opposite of the God Mediator — a mediator so thin it adds no value:

```ts
// ANTI-PATTERN — mediator that does nothing useful
class ThinMediator {
  async notify(sender: Colleague, event: string, context: LoanContext): Promise<void> {
    // Just forwards to a service that has all the logic anyway
    await this.loanWorkflowService.handle(event, context);
  }
}
```

If the mediator is just a pass-through to another class that contains all the real orchestration logic, the mediator adds an indirection layer without benefit. The workflow logic belongs *in* the mediator. If the mediator is too thin, you haven't applied the pattern — you've just renamed an existing class.

**Q19. What happens when colleagues need to query state from the mediator, not just send events?**
A: The mediator interface can be extended to support queries — but this must be done carefully to avoid making the mediator a God Object:

```ts
interface LoanWorkflowMediator {
  notify(sender: LoanWorkflowColleague, event: string, context: LoanContext): Promise<void>;
  getContext(): Readonly<LoanContext>; // read-only view — colleagues can't mutate via mediator
  isStepCompleted(step: string): boolean;
}

// A colleague that needs to make a conditional decision based on prior steps
class NachColleague extends LoanWorkflowColleague {
  async registerNach(context: LoanContext): Promise<void> {
    // Check if KYC already verified before proceeding
    if (!this.mediator.isStepCompleted("kyc.passed")) {
      throw new Error("KYC must be completed before NACH registration");
    }
    // ... proceed with registration
  }
}
```
Expose only read-only state through the mediator query interface — never allow colleagues to mutate the mediator's state directly. The mediator remains the single writer; colleagues are readers only.

## Section 6: Scenario / System Design Style Questions

**Q20. "Your loan approval process has grown to include 8 sequential steps across 6 services. A new regulation requires adding a fraud detection step between credit check and KYC. How do you handle this without breaking existing steps?"**
A: With a Mediator, this is a single change in one place — the `notify` method:

```ts
// BEFORE — credit.passed triggers KYC directly
case "credit.passed":
  await this.kyc.verifyKyc(context);
  break;

// AFTER — credit.passed now triggers fraud detection first
case "credit.passed":
  await this.fraudDetection.check(context); // new colleague, inserted here
  break;

// New event added to handle fraud check result
case "fraud.cleared":
  await this.kyc.verifyKyc(context);        // KYC now triggered after fraud check
  break;

case "fraud.flagged":
  context.rejectionReason = "Fraud risk detected";
  await this.notification.sendRejectionSms(context);
  await this.auditService.logFraudFlag(context); // extra step for compliance
  break;
```

The key points to make:
- Only the mediator changed — none of `CreditCheckColleague`, `KycColleague`, or any other existing colleague was modified.
- The new `FraudDetectionColleague` is written in isolation and registered with the mediator.
- The mediator's change is a surgical addition to the `switch` — existing cases are untouched.
- Every new path is a new test case — the test suite for the mediator grows, not changes.

**Q21. "Your team debates whether to use Saga Choreography (Kafka events between services) or Saga Orchestration (a central orchestrator) for the NACH payment + KYC + credit check workflow. How do you argue for Orchestration?"**
A: Make the argument on four dimensions:

**1. Observability** — with choreography, tracing a failed loan disbursement means correlating events across 4 Kafka topics, 4 consumer groups, and 4 service logs. With orchestration, the saga state table tells you exactly where it failed: `step: "NACH_REGISTRATION", failureReason: "Gateway timeout"`. One query, full picture.

**2. Compensation complexity** — compensating a distributed transaction with choreography requires each service to handle its own rollback and emit compensation events that other services must react to. The compensation logic is spread across every service. With orchestration, the orchestrator knows which steps completed (it persisted that state) and executes compensations in reverse order from one place.

**3. Conditional branching** — if credit score is below 700 but above 600, apply a reduced loan amount and re-route to a manual review step. This conditional logic is trivial in an orchestrator (`if (score < 700) { ... }`) and extremely messy in choreography (credit service emits `credit.marginal`, review service picks it up, emits `review.required`, approval service picks that up...).

**4. Visibility for non-engineers** — the orchestrator's code reads like a workflow specification. Product managers and compliance officers can review the exact approval sequence. Choreography's flow is emergent and invisible without dedicated tooling.

Counter: choreography scales better because there's no central bottleneck. For simple, independent side effects (send email, update analytics, write audit log), choreography wins. For a stateful, compensatable, conditional workflow like NACH + KYC + credit, orchestration wins.

**Q22. "A junior developer on your team has a `LoanController` with 12 injected services — it directly calls each service for a loan approval flow. How do you explain the problem and propose the Mediator as a fix?"**
A: Frame it around three concrete costs:

**Cost 1 — Coupling surface:**
```ts
// Current — controller is coupled to 12 services
class LoanController {
  constructor(
    private creditService: CreditService,
    private kycService: KycService,
    private nachService: NachService,
    // ... 9 more
  ) {}
}
// Adding a step = modifying LoanController
// Reordering steps = modifying LoanController
// Testing = mocking 12 dependencies per test
```

**Cost 2 — Wrong responsibility:** The controller's job is to parse HTTP requests and return HTTP responses. Sequencing a 12-step loan approval workflow is not an HTTP concern — it's a business workflow concern. The controller has accumulated responsibilities it shouldn't own.

**Cost 3 — Testability:** A test for `approveLoan` must set up 12 mocks. Any new mock needed by a new step breaks existing tests. With a mediator, the controller test needs one mock: the mediator.

**The fix:**
```ts
// After — controller depends only on the mediator
class LoanController {
  constructor(private readonly mediator: LoanWorkflowMediator) {} // one dependency

  async approveLoan(loanId: string): Promise<void> {
    await this.mediator.start(buildContext(loanId)); // delegates entirely
  }
}

// Workflow logic now lives in LoanApprovalMediator
// Controller test: mock mediator.start(), verify it was called — done
```

**Q23. "How would you design a BRE (Business Rules Engine) for NACH payment eligibility using the Mediator pattern? The rules change quarterly and must be auditable."**
A:
```ts
// Each rule is a colleague — knows only the mediator
abstract class EligibilityRuleColleague {
  constructor(protected mediator: EligibilityMediator) {}
  abstract evaluate(context: EligibilityContext): Promise<void>;
}

class MinimumIncomeRule extends EligibilityRuleColleague {
  async evaluate(context: EligibilityContext): Promise<void> {
    const passed = context.monthlyIncome >= 15_000;
    context.ruleResults.push({
      rule: "MinimumIncome",
      passed,
      detail: `Income ₹${context.monthlyIncome} vs threshold ₹15,000`,
    });
    await this.mediator.notify(this, passed ? "rule.passed" : "rule.failed", context);
  }
}

class BureauScoreRule extends EligibilityRuleColleague {
  async evaluate(context: EligibilityContext): Promise<void> {
    const passed = context.bureauScore >= 650;
    context.ruleResults.push({
      rule: "BureauScore",
      passed,
      detail: `Score ${context.bureauScore} vs threshold 650`,
    });
    await this.mediator.notify(this, passed ? "rule.passed" : "rule.failed", context);
  }
}

// Mediator — orchestrates rule execution; audit trail is built-in
class EligibilityMediator {
  private ruleQueue: EligibilityRuleColleague[];
  private currentIndex = 0;

  constructor(rules: EligibilityRuleColleague[]) {
    this.ruleQueue = rules;
    rules.forEach(r => r.setMediator(this)); // if using setMediator pattern
  }

  async start(context: EligibilityContext): Promise<EligibilityResult> {
    context.ruleResults = [];
    context.startedAt = new Date();
    await this.runNext(context);
    return this.buildResult(context);
  }

  async notify(
    sender: EligibilityRuleColleague,
    event: string,
    context: EligibilityContext,
  ): Promise<void> {
    if (event === "rule.failed" && context.failFast) {
      // Short-circuit — stop on first failure
      context.eligible = false;
      return;
    }
    this.currentIndex++;
    await this.runNext(context);
  }

  private async runNext(context: EligibilityContext): Promise<void> {
    if (this.currentIndex >= this.ruleQueue.length) {
      context.eligible = context.ruleResults.every(r => r.passed);
      return;
    }
    await this.ruleQueue[this.currentIndex].evaluate(context);
  }

  private buildResult(context: EligibilityContext): EligibilityResult {
    return {
      eligible: context.eligible ?? false,
      ruleResults: context.ruleResults, // full audit trail of every rule and outcome
      evaluatedAt: context.startedAt!,
      completedAt: new Date(),
    };
  }
}

// Adding a new rule next quarter — zero changes to existing code
const eligibilityEngine = new EligibilityMediator([
  new MinimumIncomeRule(null!),
  new BureauScoreRule(null!),
  new DeduplicationRule(null!),
  new AccountAggregatorRule(null!), // Q4 addition
]);

const result = await eligibilityEngine.start(applicantContext);
// result.ruleResults contains full audit trail for compliance
```

**Q24. "Your team wants to add cross-cutting concerns — timing metrics, error logging, and circuit breaking — to every step in the Mediator workflow. How do you do this without modifying each colleague?"**
A: Apply the Decorator pattern to the mediator itself — wrap the concrete mediator with a decorator that adds cross-cutting behavior:

```ts
// Observability decorator wraps the mediator — adds metrics and logging to every notify() call
class ObservableMediator implements LoanWorkflowMediator {
  constructor(
    private readonly inner: LoanWorkflowMediator,
    private readonly metrics: MetricsService,
    private readonly logger: Logger,
  ) {}

  async notify(
    sender: LoanWorkflowColleague,
    event: string,
    context: LoanContext,
  ): Promise<void> {
    const start = Date.now();
    const step = sender.constructor.name;

    this.logger.info({ step, event, loanId: context.loanId }, "Workflow step started");
    this.metrics.increment(`workflow.step.${event}`);

    try {
      await this.inner.notify(sender, event, context);
      const duration = Date.now() - start;
      this.metrics.histogram(`workflow.step.duration`, duration, { event });
      this.logger.info({ step, event, duration, loanId: context.loanId }, "Workflow step completed");
    } catch (err) {
      this.metrics.increment(`workflow.step.errors`, 1, { event });
      this.logger.error({ step, event, err, loanId: context.loanId }, "Workflow step failed");
      throw err;
    }
  }
}

// Circuit breaker wraps the observable mediator
class CircuitBreakerMediator implements LoanWorkflowMediator {
  private failures = 0;
  private openUntil = 0;

  constructor(private readonly inner: LoanWorkflowMediator) {}

  async notify(sender: LoanWorkflowColleague, event: string, context: LoanContext): Promise<void> {
    if (Date.now() < this.openUntil) {
      throw new WorkflowCircuitOpenError("Loan workflow circuit breaker open");
    }
    try {
      await this.inner.notify(sender, event, context);
      this.failures = 0;
    } catch (err) {
      this.failures++;
      if (this.failures >= 5) this.openUntil = Date.now() + 30_000;
      throw err;
    }
  }
}

// Wired in NestJS module — decorator chain around the real mediator
const mediator = new CircuitBreakerMediator(
  new ObservableMediator(
    new LoanApprovalMediator(credit, kyc, nach, disbursement, notification),
    metricsService,
    logger,
  )
);
```
Colleagues are entirely unaware of observability or circuit breaking. The mediator chain is assembled at the composition root.

**Q25. "When would you choose NOT to use the Mediator pattern for a multi-step workflow?"**
A: Mediator is not always the right tool. Avoid it when:

**The workflow is truly sequential with no branching:** If the steps always run in the same fixed order with no conditions — `A → B → C → D` — a simple service method or pipeline is clearer than a full Mediator:
```ts
// Simple pipeline — more readable than a mediator for linear flows
async approveLoan(loanId: string): Promise<void> {
  await this.creditService.check(loanId);
  await this.kycService.verify(loanId);
  await this.nachService.register(loanId);
  await this.disbursementService.disburse(loanId);
}
```

**The number of steps is small and stable:** If the workflow has 3 steps and hasn't changed in two years, introducing a Mediator adds complexity with no real benefit. Apply the pattern when you have evidence the workflow will grow or branch.

**The team isn't familiar with the pattern:** A Mediator with a non-obvious `notify` + `switch` dispatch is harder to onboard than a sequential service call chain. At small team scale, readability can outweigh the coupling benefits.

**A process manager / workflow engine is the right tool:** For very long-running, durable workflows (loan approval that spans days, requires human intervention steps, or must survive process restarts), a dedicated workflow engine (Temporal, AWS Step Functions, Conductor) is a better fit than a hand-rolled Mediator. These tools provide persistence, retry, timeout management, and observability out of the box. The Mediator pattern is their conceptual foundation — the workflow engine IS the mediator — but implementing it yourself is reinventing the wheel at that scale.

## Quick Comparison Table

| Aspect                   | Mediator                                       | Observer                                    | Facade                                       | Chain of Responsibility                      |
|---                       |---                                             |---                                          |---                                           |---                                           |
| Intent                   | Centralize communication between many objects  | Broadcast state changes to dependents       | Simplify external access to a subsystem      | Pass request through a chain of handlers     |
| Communication            | Many-to-many, coordinated                      | One-to-many, independent reactions          | One-way: client → facade → subsystem         | Sequential: handler → next handler           |
| Control location         | Centralized in mediator                        | Decentralized — each observer reacts        | External to subsystem                        | Distributed across handler chain             |
| Component coupling       | Components know only the mediator              | Subject knows observers; observers decouple | Subsystem components unaware of facade       | Each handler knows the next                  |
| Flow control             | Mediator decides all routing                   | Subject notifies; observers decide reaction | No flow — just delegation                    | Each handler decides pass or stop            |
| Modification ease        | Add colleague + update mediator                | Add subscriber — existing code untouched    | Facade changes when subsystem interface does | Insert handler into chain                    |
| Best for                 | Orchestrated workflows, CQRS dispatch          | Event notifications, reactive systems       | Simplifying complex APIs for external use    | Sequential validation with early exit        |
| NestJS expression        | `CommandBus`, `QueryBus`, request pipeline     | `EventEmitter2`, `@OnEvent`                 | Service layer wrapping repos + gateways      | Guards → Pipes → Controller pipeline         |
| Distributed version      | Saga Orchestration                             | Saga Choreography, Kafka consumers          | API Gateway                                  | Middleware proxy chain                       |
| Risk                     | God Mediator if not bounded by workflow scope  | Lapsed listeners, observer avalanche        | God Facade if too broad                      | Long chains become hard to debug             |

The pattern name may never come up — but the pattern is the answer. The strongest answers position Mediator in its ecosystem: know when Observer (choreography, event-driven, independent side effects) is the better tool and when Mediator (orchestration, conditional branching, compensation) is correct. Know the CQRS + Mediator pairing cold — `CommandBus` and `QueryBus` in NestJS are what you'll use in practice.
