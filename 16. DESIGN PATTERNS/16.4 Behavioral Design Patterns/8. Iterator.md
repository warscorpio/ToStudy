# JavaScript / TypeScript (Design Patterns — Behavioral): Iterator Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Iterator pattern?**
A: The Iterator pattern is a behavioral design pattern that provides a way to **sequentially access elements of a collection without exposing its underlying representation** — whether it is an array, linked list, tree, graph, database cursor, or any other structure. The pattern separates the *traversal algorithm* from the *collection*, encapsulating the traversal state (current position, what's been visited, what remains) in a dedicated iterator object. Clients use a uniform interface (`next()`, `hasNext()`, `done`) regardless of how the collection is structured internally.

The pattern has two complementary motivations: it protects a collection's internal structure from exposure, and it allows multiple independent traversals of the same collection to proceed simultaneously without interfering with each other — since each iterator carries its own traversal state.

**Q2. What problem does the Iterator pattern solve?**
A: Without the Iterator pattern, a collection must either expose its internal structure (breaking encapsulation) or duplicate traversal logic across every client that needs to iterate:
```ts
// Without Iterator — client must know the internal structure
class UserCollection {
  users: User[] = []; // forced to expose raw array for clients to iterate ✗
}

// Or — traversal logic duplicated at every call site
function printUsers(collection: UserCollection): void {
  for (let i = 0; i < collection.users.length; i++) { // client knows it's array-indexed ✗
    console.log(collection.users[i].name);
  }
}

function findAdmins(collection: UserCollection): User[] {
  const result: User[] = [];
  for (let i = 0; i < collection.users.length; i++) { // duplicated traversal ✗
    if (collection.users[i].role === "admin") result.push(collection.users[i]);
  }
  return result;
}
```
When the internal structure changes from an array to a linked list or a tree, every client that traverses it must be updated. The Iterator pattern fixes this by giving the collection a single `iterator()` method that returns an object encapsulating the traversal. Clients use the iterator's uniform interface — the internal structure can change freely.

**Q3. What are the participants in the Iterator pattern?**
A:
- **Iterator (interface)** — declares the traversal interface: `next(): IteratorResult<T>`, `hasNext(): boolean`, or in JavaScript's protocol, `next(): { value: T; done: boolean }`. May also include `reset()`, `peek()`, or `skip(n)` for richer traversal.
- **ConcreteIterator** — implements the Iterator interface for a specific collection type. Maintains the current traversal position and knows how to advance through the collection's internal structure.
- **IterableCollection (interface)** — declares a method that returns an Iterator: `iterator(): Iterator<T>` or `[Symbol.iterator](): Iterator<T>`.
- **ConcreteCollection** — implements IterableCollection. Returns a ConcreteIterator configured for its internal structure.
- **Client** — uses only the Iterator interface. Never accesses the collection's internals directly.

**Q4. How does the JavaScript/TypeScript built-in iteration protocol work, and how does it relate to the Iterator pattern?**
A: JavaScript formalised the Iterator pattern into the language itself via two protocols:

- **The Iterator Protocol** — an object is an iterator if it has a `next()` method that returns `{ value: T; done: boolean }`. When `done` is `true`, `value` is `undefined` (or a final return value).
- **The Iterable Protocol** — an object is iterable if it has a `[Symbol.iterator]()` method that returns an iterator. Built-in iterables include `Array`, `Map`, `Set`, `String`, `NodeList`, generator functions.

These protocols are what make `for...of`, array destructuring, spread syntax, and `Array.from()` work:
```ts
// Any object implementing [Symbol.iterator]() works with all native iteration syntax
const range = {
  from: 1,
  to:   5,
  [Symbol.iterator](): Iterator<number> {
    let current = this.from;
    const last  = this.to;
    return {
      next(): IteratorResult<number> {
        return current <= last
          ? { value: current++, done: false }
          : { value: undefined as any, done: true };
      }
    };
  }
};

// All of these work because range implements [Symbol.iterator]
for (const n of range)           console.log(n); // 1 2 3 4 5
const arr = [...range];                           // [1, 2, 3, 4, 5]
const [first, second] = range;                    // first = 1, second = 2
Array.from(range);                                // [1, 2, 3, 4, 5]
```

**Q5. What is the difference between an Iterator and a Generator in JavaScript?**
A: A generator is a language feature that *produces* iterators with significantly less boilerplate. Every generator function returns an object that implements both the Iterator Protocol and the Iterable Protocol simultaneously:

| Aspect | Manual Iterator | Generator |
|---|---|---|
| **Definition** | Class or object with `next()` method | Function with `function*` syntax and `yield` |
| **State management** | Explicit — tracked as instance variables | Implicit — paused execution context holds state |
| **Boilerplate** | High — class, constructor, state variables, return shape | Low — just `yield` values |
| **Lazy evaluation** | Manual — must implement explicitly | Automatic — `yield` pauses execution |
| **Early termination** | Requires `return()` method | Handled by generator protocol automatically |
| **Composability** | Requires explicit delegation | `yield*` delegates to another iterable |

```ts
// Manual iterator — explicit state management
class RangeIterator implements Iterator<number> {
  private current: number;
  constructor(private from: number, private to: number) {
    this.current = from;
  }
  next(): IteratorResult<number> {
    return this.current <= this.to
      ? { value: this.current++, done: false }
      : { value: undefined as any, done: true };
  }
}

// Generator — same behavior, fraction of the code
function* range(from: number, to: number): Generator<number> {
  for (let i = from; i <= to; i++) yield i;
}

// Both work identically with for...of, spread, destructuring
for (const n of range(1, 5)) console.log(n);
```

## Section 2: Implementing the Iterator Pattern in TypeScript

**Q6. How do you implement a custom Iterator for a tree structure using the class-based approach?**
A:
```ts
// The tree node
class TreeNode<T> {
  constructor(
    public value:    T,
    public left:     TreeNode<T> | null = null,
    public right:    TreeNode<T> | null = null
  ) {}
}

// Iterator interface
interface Iterator<T> {
  next():    IteratorResult<T>;
  hasNext(): boolean;
}

// Concrete iterator — in-order traversal (left → root → right)
class InOrderIterator<T> implements Iterator<T> {
  private stack:   TreeNode<T>[] = [];
  private current: TreeNode<T> | null;

  constructor(root: TreeNode<T> | null) {
    this.current = root;
  }

  hasNext(): boolean {
    return this.current !== null || this.stack.length > 0;
  }

  next(): IteratorResult<T> {
    // Push left children onto the stack
    while (this.current !== null) {
      this.stack.push(this.current);
      this.current = this.current.left;
    }

    if (this.stack.length === 0) {
      return { value: undefined as any, done: true };
    }

    const node    = this.stack.pop()!;
    this.current  = node.right; // move to right subtree
    return { value: node.value, done: false };
  }
}

// Pre-order traversal (root → left → right) — different ConcreteIterator, same interface
class PreOrderIterator<T> implements Iterator<T> {
  private stack: TreeNode<T>[] = [];

  constructor(root: TreeNode<T> | null) {
    if (root) this.stack.push(root);
  }

  hasNext(): boolean { return this.stack.length > 0; }

  next(): IteratorResult<T> {
    if (!this.hasNext()) return { value: undefined as any, done: true };
    const node = this.stack.pop()!;
    if (node.right) this.stack.push(node.right); // right first (LIFO)
    if (node.left)  this.stack.push(node.left);
    return { value: node.value, done: false };
  }
}

// Collection — returns different iterator types on demand
class BinarySearchTree<T> {
  constructor(private root: TreeNode<T> | null = null) {}

  inOrder():  InOrderIterator<T>  { return new InOrderIterator(this.root); }
  preOrder(): PreOrderIterator<T> { return new PreOrderIterator(this.root); }

  // Native protocol — default to in-order
  [Symbol.iterator](): InOrderIterator<T> { return this.inOrder(); }
}

// Build a BST: 4 as root, 2 and 6 as children, 1/3 and 5/7 as leaves
const tree = new BinarySearchTree(
  new TreeNode(4,
    new TreeNode(2, new TreeNode(1), new TreeNode(3)),
    new TreeNode(6, new TreeNode(5), new TreeNode(7))
  )
);

// In-order: 1, 2, 3, 4, 5, 6, 7 (sorted order for BST)
const it = tree.inOrder();
while (it.hasNext()) process.stdout.write(String(it.next().value) + " ");

// Works with for...of because of [Symbol.iterator]
for (const val of tree) process.stdout.write(String(val) + " ");
```

**Q7. How do you implement the same tree traversal using generators — and when should you prefer generators over classes?**
A:
```ts
// Generator-based traversals — dramatically less boilerplate
function* inOrder<T>(node: TreeNode<T> | null): Generator<T> {
  if (!node) return;
  yield* inOrder(node.left);   // recurse left
  yield node.value;            // visit root
  yield* inOrder(node.right);  // recurse right
}

function* preOrder<T>(node: TreeNode<T> | null): Generator<T> {
  if (!node) return;
  yield node.value;
  yield* preOrder(node.left);
  yield* preOrder(node.right);
}

function* postOrder<T>(node: TreeNode<T> | null): Generator<T> {
  if (!node) return;
  yield* postOrder(node.left);
  yield* postOrder(node.right);
  yield node.value;
}

// Breadth-first traversal — not naturally recursive, uses explicit queue
function* breadthFirst<T>(root: TreeNode<T> | null): Generator<T> {
  if (!root) return;
  const queue: TreeNode<T>[] = [root];
  while (queue.length > 0) {
    const node = queue.shift()!;
    yield node.value;
    if (node.left)  queue.push(node.left);
    if (node.right) queue.push(node.right);
  }
}

// Collection with generator-backed [Symbol.iterator]
class BinarySearchTree<T> {
  constructor(private root: TreeNode<T> | null = null) {}

  [Symbol.iterator](): Generator<T> { return inOrder(this.root); }
  inOrder():     Generator<T> { return inOrder(this.root); }
  preOrder():    Generator<T> { return preOrder(this.root); }
  postOrder():   Generator<T> { return postOrder(this.root); }
  breadthFirst():Generator<T> { return breadthFirst(this.root); }
}

// All native syntax works
const sorted = [...tree.inOrder()];               // [1, 2, 3, 4, 5, 6, 7]
const [min]  = tree.inOrder();                    // min = 1
const levels = [...tree.breadthFirst()];          // [4, 2, 6, 1, 3, 5, 7]
```

**Prefer generators when:**
- The traversal algorithm is naturally recursive (`yield*` replaces manual stack management).
- Low boilerplate is a priority — generators are dramatically more concise.
- The iterator will be used with native `for...of`, spread, or `Array.from`.

**Prefer class-based iterators when:**
- You need `reset()`, `peek()`, `skip(n)`, or other rich traversal operations beyond `next()`.
- You need multiple simultaneous traversal strategies encapsulated in a class hierarchy.
- The iterator maintains complex state that benefits from being a named, testable class.

**Q8. How do you implement a lazy, infinite iterator — for example, a Fibonacci sequence or a paginated API cursor?**
A:
```ts
// Infinite Fibonacci generator — lazy, never materialises the full sequence
function* fibonacci(): Generator<number> {
  let [a, b] = [0, 1];
  while (true) {         // infinite — yields forever
    yield a;
    [a, b] = [b, a + b];
  }
}

// Take only what you need — iterator never computes more
function take<T>(iter: Iterable<T>, n: number): T[] {
  const result: T[] = [];
  for (const val of iter) {
    result.push(val);
    if (result.length >= n) break; // early termination
  }
  return result;
}

take(fibonacci(), 8); // [0, 1, 1, 2, 3, 5, 8, 13] — only computed 8 values

// Paginated API cursor — lazy fetching of remote data
async function* paginatedUsers(pageSize = 20): AsyncGenerator<User> {
  let cursor: string | null = null;

  while (true) {
    const page = await api.getUsers({ pageSize, cursor });
    for (const user of page.items) yield user; // yield one at a time
    if (!page.nextCursor) break;               // no more pages
    cursor = page.nextCursor;
  }
}

// Caller gets a flat stream — pagination is invisible
for await (const user of paginatedUsers(50)) {
  await processUser(user); // fetches next page only when needed
}

// Lazy range — no array allocation
function* range(start: number, end: number, step = 1): Generator<number> {
  for (let i = start; i < end; i += step) yield i;
}

// Sum of first 1,000,000 even numbers — no array of 1M items created
let sum = 0;
for (const n of range(0, 2_000_000, 2)) sum += n;
```

**Q9. How do you build iterator combinators — `map`, `filter`, `take`, `zip` — that work lazily over any iterable?**
A: Iterator combinators transform iterables into new iterables without materialising intermediate arrays — the core idea behind lazy evaluation pipelines:
```ts
// Lazy map — applies fn to each element without creating an intermediate array
function* map<T, U>(iterable: Iterable<T>, fn: (item: T) => U): Generator<U> {
  for (const item of iterable) yield fn(item);
}

// Lazy filter — yields only elements matching the predicate
function* filter<T>(iterable: Iterable<T>, pred: (item: T) => boolean): Generator<T> {
  for (const item of iterable) if (pred(item)) yield item;
}

// Lazy take — yields at most n elements
function* take<T>(iterable: Iterable<T>, n: number): Generator<T> {
  let count = 0;
  for (const item of iterable) {
    if (count++ >= n) break;
    yield item;
  }
}

// Lazy flatMap — maps and flattens one level
function* flatMap<T, U>(iterable: Iterable<T>, fn: (item: T) => Iterable<U>): Generator<U> {
  for (const item of iterable) yield* fn(item);
}

// Zip — combines two iterables element-wise
function* zip<A, B>(a: Iterable<A>, b: Iterable<B>): Generator<[A, B]> {
  const iterA = a[Symbol.iterator]();
  const iterB = b[Symbol.iterator]();
  while (true) {
    const { value: va, done: da } = iterA.next();
    const { value: vb, done: db } = iterB.next();
    if (da || db) break;
    yield [va, vb];
  }
}

// Chain — concatenates iterables
function* chain<T>(...iterables: Iterable<T>[]): Generator<T> {
  for (const it of iterables) yield* it;
}

// Usage — pipeline: no intermediate arrays anywhere
const result = [
  ...take(
    filter(
      map(range(1, Infinity), n => n * n),   // infinite: 1, 4, 9, 16, 25 ...
      n => n % 2 !== 0                        // filter odd squares: 1, 9, 25 ...
    ),
    5                                          // take first 5: [1, 9, 25, 49, 81]
  )
];
// Only 9 values were ever computed — the pipeline is fully lazy

// Fluent iterator wrapper — chains combinators in readable order
class LazyIterator<T> implements Iterable<T> {
  constructor(private source: Iterable<T>) {}

  map<U>(fn: (item: T) => U): LazyIterator<U> {
    return new LazyIterator(map(this.source, fn));
  }
  filter(pred: (item: T) => boolean): LazyIterator<T> {
    return new LazyIterator(filter(this.source, pred));
  }
  take(n: number): LazyIterator<T> {
    return new LazyIterator(take(this.source, n));
  }
  toArray(): T[] { return [...this.source]; }
  [Symbol.iterator](): Iterator<T> { return this.source[Symbol.iterator](); }
}

// Readable pipeline
const topSquares = new LazyIterator(range(1, Infinity))
  .map(n => n * n)
  .filter(n => n % 2 !== 0)
  .take(5)
  .toArray(); // [1, 9, 25, 49, 81]
```

## Section 3: Real-World Applications

**Q10. How does the Iterator pattern apply to database query cursors and ORM result sets?**
A: Database result sets are a natural fit — they may be too large to load into memory at once, and each `next()` call maps to fetching the next row or batch from the database:
```ts
// Async iterator for a database cursor — fetches rows on demand
class DatabaseCursorIterator<T> implements AsyncIterator<T> {
  private buffer:   T[]     = [];
  private cursor:   string | null = null;
  private exhausted = false;

  constructor(
    private db:        DatabaseClient,
    private query:     string,
    private params:    unknown[],
    private batchSize: number = 100
  ) {}

  async next(): Promise<IteratorResult<T>> {
    // Refill buffer when empty
    if (this.buffer.length === 0 && !this.exhausted) {
      const result = await this.db.query<T>(this.query, {
        params:   this.params,
        cursor:   this.cursor,
        limit:    this.batchSize,
      });
      this.buffer = result.rows;
      this.cursor = result.nextCursor ?? null;
      if (!result.nextCursor) this.exhausted = true;
    }

    if (this.buffer.length === 0) {
      return { value: undefined as any, done: true };
    }

    return { value: this.buffer.shift()!, done: false };
  }

  async return(): Promise<IteratorResult<T>> {
    await this.db.closeCursor(this.cursor); // cleanup on early exit
    return { value: undefined as any, done: true };
  }

  [Symbol.asyncIterator](): this { return this; }
}

// Collection that returns a cursor iterator
class UserRepository {
  constructor(private db: DatabaseClient) {}

  iterateAll(batchSize = 100): DatabaseCursorIterator<User> {
    return new DatabaseCursorIterator<User>(
      this.db,
      "SELECT * FROM users ORDER BY created_at",
      [],
      batchSize
    );
  }

  iterateByCountry(country: string): DatabaseCursorIterator<User> {
    return new DatabaseCursorIterator<User>(
      this.db,
      "SELECT * FROM users WHERE country = $1 ORDER BY created_at",
      [country]
    );
  }
}

// Client — processes millions of rows without loading them into memory
for await (const user of userRepo.iterateAll()) {
  await sendMarketingEmail(user); // processes one at a time, fetches 100 at a time
}

// Early exit — cursor is properly closed via return()
for await (const user of userRepo.iterateByCountry("IN")) {
  if (await isVIPUser(user)) { break; } // triggers cursor cleanup
}
```

**Q11. How does the Iterator pattern apply to file system traversal?**
A:
```ts
import * as fs   from "fs";
import * as path from "path";

// Async generator — walks directory tree lazily, depth-first
async function* walkDirectory(
  dir: string,
  options: { extensions?: string[]; maxDepth?: number } = {},
  depth = 0
): AsyncGenerator<string> {
  if (options.maxDepth !== undefined && depth > options.maxDepth) return;

  const entries = await fs.promises.readdir(dir, { withFileTypes: true });

  for (const entry of entries) {
    const fullPath = path.join(dir, entry.name);

    if (entry.isDirectory()) {
      yield* walkDirectory(fullPath, options, depth + 1); // recurse
    } else if (entry.isFile()) {
      // Filter by extension if specified
      if (!options.extensions ||
          options.extensions.includes(path.extname(entry.name))) {
        yield fullPath;
      }
    }
  }
}

// Client — flat stream of file paths, directory structure invisible
for await (const filePath of walkDirectory("./src", { extensions: [".ts"] })) {
  const content = await fs.promises.readFile(filePath, "utf-8");
  console.log(`${filePath}: ${content.split("\n").length} lines`);
}

// Collect all TypeScript files in project
const tsFiles = [];
for await (const f of walkDirectory(".", { extensions: [".ts"], maxDepth: 5 })) {
  tsFiles.push(f);
}
console.log(`Found ${tsFiles.length} TypeScript files`);
```

**Q12. How does the Iterator pattern apply to event streams and message queues?**
A: Message queues and event streams can be consumed as async iterables — the iterator fetches messages on demand and the caller processes them sequentially or in batches:
```ts
// Async iterator over a message queue (RabbitMQ / SQS pattern)
class MessageQueueIterator<T> implements AsyncIterator<T> {
  private buffer:   T[]       = [];
  private running   = true;
  private resolver: ((value: IteratorResult<T>) => void) | null = null;

  constructor(private queue: MessageQueue, private batchSize = 10) {
    this.startConsuming();
  }

  private async startConsuming(): Promise<void> {
    while (this.running) {
      const messages = await this.queue.receive({ maxMessages: this.batchSize });
      for (const msg of messages) {
        if (this.resolver) {
          this.resolver({ value: msg.body as T, done: false });
          this.resolver = null;
          await msg.ack();
        } else {
          this.buffer.push(msg.body as T);
          await msg.ack();
        }
      }
      if (messages.length === 0) {
        await new Promise(r => setTimeout(r, 100)); // short poll delay
      }
    }
  }

  async next(): Promise<IteratorResult<T>> {
    if (this.buffer.length > 0) {
      return { value: this.buffer.shift()!, done: false };
    }
    return new Promise(resolve => { this.resolver = resolve; });
  }

  async return(): Promise<IteratorResult<T>> {
    this.running = false;
    await this.queue.close();
    return { value: undefined as any, done: true };
  }

  [Symbol.asyncIterator](): this { return this; }
}

// SQS-style async iterable
async function* sqsMessages<T>(queueUrl: string, sqs: SQSClient): AsyncGenerator<T> {
  while (true) {
    const response = await sqs.receiveMessage({
      QueueUrl:            queueUrl,
      MaxNumberOfMessages: 10,
      WaitTimeSeconds:     20, // long polling
    });

    for (const msg of response.Messages ?? []) {
      yield JSON.parse(msg.Body!) as T;
      await sqs.deleteMessage({ QueueUrl: queueUrl, ReceiptHandle: msg.ReceiptHandle! });
    }
  }
}

// Consumer — flat stream, queue mechanics invisible
for await (const order of sqsMessages<Order>("https://sqs.../orders", sqsClient)) {
  await processOrder(order);
}
```

**Q13. How does the Iterator pattern apply to data processing pipelines in Node.js streams?**
A: Node.js `Readable` streams implement the async iterable protocol — `for await...of` works natively:
```ts
import { createReadStream }   from "fs";
import { createInterface }    from "readline";
import { Transform, pipeline } from "stream";
import { promisify }          from "util";

const pipelineAsync = promisify(pipeline);

// Async generator — reads a CSV file line by line (never loads full file)
async function* readCsvLines(filePath: string): AsyncGenerator<string[]> {
  const fileStream = createReadStream(filePath, { encoding: "utf-8" });
  const rl = createInterface({ input: fileStream, crlfDelay: Infinity });

  let isHeader = true;
  for await (const line of rl) {          // rl is async iterable
    if (isHeader) { isHeader = false; continue; } // skip header row
    yield line.split(",").map(f => f.trim());
  }
}

// Async generator — parse CSV rows into domain objects
async function* parseUsers(lines: AsyncIterable<string[]>): AsyncGenerator<User> {
  for await (const [id, name, email, role] of lines) {
    yield { id, name, email, role: role as User["role"] };
  }
}

// Async generator — validate and filter
async function* validUsers(users: AsyncIterable<User>): AsyncGenerator<User> {
  for await (const user of users) {
    if (user.email.includes("@") && user.name.length > 0) yield user;
  }
}

// Compose pipeline — data flows through lazily, constant memory regardless of file size
async function importUsers(filePath: string, repo: UserRepository): Promise<number> {
  let count = 0;
  const pipeline = validUsers(parseUsers(readCsvLines(filePath)));

  for await (const user of pipeline) {
    await repo.save(user);
    count++;
  }
  return count;
}

// Import 10 million users from a CSV — memory usage stays constant
const imported = await importUsers("./users.csv", userRepo);
console.log(`Imported ${imported} users`);
```

## Section 4: Advanced Iterator Techniques

**Q14. How do you implement a bidirectional iterator — one that supports both `next()` and `prev()`?**
A:
```ts
// Bidirectional iterator interface
interface BidirectionalIterator<T> {
  next():    IteratorResult<T>;
  prev():    IteratorResult<T>;
  hasNext(): boolean;
  hasPrev(): boolean;
  reset():   void;
  current(): T | undefined;
}

// Concrete bidirectional iterator for an array-backed collection
class ArrayBidirectionalIterator<T> implements BidirectionalIterator<T> {
  private index: number;

  constructor(private items: T[], startIndex = 0) {
    this.index = startIndex;
  }

  hasNext(): boolean { return this.index < this.items.length; }
  hasPrev(): boolean { return this.index > 0; }

  next(): IteratorResult<T> {
    if (!this.hasNext()) return { value: undefined as any, done: true };
    return { value: this.items[this.index++], done: false };
  }

  prev(): IteratorResult<T> {
    if (!this.hasPrev()) return { value: undefined as any, done: true };
    return { value: this.items[--this.index], done: false };
  }

  current(): T | undefined {
    return this.index > 0 ? this.items[this.index - 1] : undefined;
  }

  reset(): void { this.index = 0; }

  // Jump to arbitrary position
  seek(index: number): void {
    if (index < 0 || index > this.items.length) throw new RangeError("Index out of bounds");
    this.index = index;
  }
}

// Application — undo/redo history navigation
class EditHistory {
  private snapshots: DocumentSnapshot[] = [];
  private iterator: ArrayBidirectionalIterator<DocumentSnapshot>;

  constructor() {
    this.iterator = new ArrayBidirectionalIterator(this.snapshots);
  }

  save(snapshot: DocumentSnapshot): void {
    // Discard future history when a new edit is made (standard undo behavior)
    this.snapshots.splice(this.iterator["index"]);
    this.snapshots.push(snapshot);
    this.iterator = new ArrayBidirectionalIterator(this.snapshots, this.snapshots.length);
  }

  undo(): DocumentSnapshot | undefined {
    return this.iterator.hasPrev() ? this.iterator.prev().value : undefined;
  }

  redo(): DocumentSnapshot | undefined {
    return this.iterator.hasNext() ? this.iterator.next().value : undefined;
  }

  canUndo(): boolean { return this.iterator.hasPrev(); }
  canRedo(): boolean { return this.iterator.hasNext(); }
}
```

**Q15. How do you implement a filtered / decorating iterator that adds behavior without modifying the underlying collection?**
A: Decorator iterators wrap an existing iterator and add behavior — they implement the same interface, so callers don't know they're wrapped:
```ts
// Decorator iterator — adds logging to any iterator
class LoggingIterator<T> implements Iterator<T> {
  private count = 0;

  constructor(
    private inner:  Iterator<T>,
    private label:  string,
    private logger: Logger
  ) {}

  next(): IteratorResult<T> {
    const result = this.inner.next();
    if (!result.done) {
      this.count++;
      this.logger.debug(`[${this.label}] Item ${this.count}: ${JSON.stringify(result.value)}`);
    } else {
      this.logger.info(`[${this.label}] Iteration complete after ${this.count} items`);
    }
    return result;
  }

  [Symbol.iterator](): this { return this; }
}

// Decorator iterator — adds rate limiting (yields one item per interval)
async function* rateLimited<T>(
  source: AsyncIterable<T>,
  delayMs: number
): AsyncGenerator<T> {
  for await (const item of source) {
    yield item;
    await new Promise(r => setTimeout(r, delayMs));
  }
}

// Decorator iterator — adds retry logic for async iteration
async function* withRetry<T>(
  factory: () => AsyncIterable<T>,
  maxAttempts = 3
): AsyncGenerator<T> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      yield* factory();
      return; // success — done
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      console.warn(`Iteration failed (attempt ${attempt}/${maxAttempts}), retrying...`);
      await new Promise(r => setTimeout(r, 1000 * attempt)); // exponential backoff
    }
  }
}

// Compose decorators freely — stack any combination
const pipeline = withRetry(
  () => rateLimited(
    paginatedUsers(50),   // underlying source
    100                    // 100ms between items
  ),
  3                        // up to 3 retry attempts
);

for await (const user of pipeline) {
  await processUser(user);
}
```

**Q16. How does `Symbol.asyncIterator` work, and when do you use async iterators vs synchronous ones?**
A: `Symbol.asyncIterator` is the async counterpart of `Symbol.iterator`. An object implementing `[Symbol.asyncIterator]()` returning an object with `async next()` is an **async iterable**, consumed with `for await...of`:

```ts
// Sync iterator — use when: data is already in memory, traversal is CPU-bound
class NumberRange implements Iterable<number> {
  constructor(private start: number, private end: number) {}

  [Symbol.iterator](): Iterator<number> {
    let current = this.start;
    const end   = this.end;
    return {
      next(): IteratorResult<number> {
        return current <= end
          ? { value: current++, done: false }
          : { value: undefined as any, done: true };
      }
    };
  }
}

// Async iterator — use when: data requires I/O (network, disk, queue)
class AsyncNumberRange implements AsyncIterable<number> {
  constructor(private start: number, private end: number) {}

  [Symbol.asyncIterator](): AsyncIterator<number> {
    let current = this.start;
    const end   = this.end;
    return {
      async next(): Promise<IteratorResult<number>> {
        await new Promise(r => setTimeout(r, 10)); // simulate async I/O
        return current <= end
          ? { value: current++, done: false }
          : { value: undefined as any, done: true };
      }
    };
  }
}

// Decision guide:
// Use sync   [Symbol.iterator]  when: arrays, in-memory trees, linked lists, generators over local data
// Use async  [Symbol.asyncIterator] when: network requests, file I/O, database queries, message queues
// Generators are the easiest way to implement both — function* for sync, async function* for async

// Sync generator
function* syncRange(start: number, end: number): Generator<number> {
  for (let i = start; i <= end; i++) yield i;
}

// Async generator  
async function* asyncRange(start: number, end: number): AsyncGenerator<number> {
  for (let i = start; i <= end; i++) {
    await new Promise(r => setTimeout(r, 10));
    yield i;
  }
}
```

## Section 5: Pitfalls, Anti-Patterns & Edge Cases

**Q17. What is iterator invalidation, and how do you prevent it?**
A: Iterator invalidation occurs when the underlying collection is modified during iteration — the iterator's position becomes invalid, causing skipped elements, double-visits, or crashes:
```ts
// Iterator invalidation — modifying collection during iteration
const users = new Map([["1", userA], ["2", userB], ["3", userC]]);

for (const [id, user] of users) {
  if (!user.isActive) {
    users.delete(id); // ✗ — Map iterator in JavaScript is actually safe for delete,
                      // but adding new entries during iteration may or may not be seen
  }
}

// Arrays are NOT safe to splice during forEach or for...of
const arr = [1, 2, 3, 4, 5];
for (const item of arr) {
  if (item === 3) arr.splice(arr.indexOf(item), 1); // ✗ — skips element 4
}

// Prevention 1 — collect then modify (snapshot the collection)
const toDelete = [...users.entries()]
  .filter(([, user]) => !user.isActive)
  .map(([id]) => id);
toDelete.forEach(id => users.delete(id)); // safe — modification after iteration

// Prevention 2 — snapshot iterator (iterate over a copy)
for (const [id, user] of new Map(users)) { // iterate over a copy
  if (!user.isActive) users.delete(id);    // safe to modify original
}

// Prevention 3 — immutable iterator (iterator over snapshot at creation time)
class SnapshotIterator<T> {
  private snapshot: T[];
  private index = 0;

  constructor(source: Iterable<T>) {
    this.snapshot = [...source]; // snapshot at iterator creation
  }

  next(): IteratorResult<T> {
    return this.index < this.snapshot.length
      ? { value: this.snapshot[this.index++], done: false }
      : { value: undefined as any, done: true };
  }
}
```

**Q18. How do you handle early termination — what happens when a `for...of` loop `break`s out of a generator?**
A: When a `for...of` loop is terminated early (`break`, `return`, `throw`), JavaScript calls the iterator's `return()` method — giving it a chance to clean up resources. Generators handle this automatically; manual iterators must implement `return()` explicitly:
```ts
// Generator — early termination is handled automatically
async function* databaseRows(query: string): AsyncGenerator<Row> {
  const connection = await db.connect();
  try {
    const cursor = await connection.query(query);
    for await (const row of cursor) yield row;
  } finally {
    await connection.release(); // always runs — even on break, return, throw
  }
}

// The finally block runs when the consumer breaks
for await (const row of databaseRows("SELECT * FROM orders")) {
  if (row.id === targetId) break; // finally block runs, connection released ✓
}

// Manual iterator — must implement return() for resource cleanup
class ResourceIterator<T> implements Iterator<T> {
  private resource: ExpensiveResource;
  private done = false;

  constructor(config: ResourceConfig) {
    this.resource = ExpensiveResource.open(config);
  }

  next(): IteratorResult<T> {
    if (this.done) return { value: undefined as any, done: true };
    const value = this.resource.readNext();
    if (!value) {
      this.done = true;
      this.resource.close();
      return { value: undefined as any, done: true };
    }
    return { value: value as T, done: false };
  }

  // Called by for...of on break/return/throw
  return(_value?: unknown): IteratorResult<T> {
    if (!this.done) {
      this.done = true;
      this.resource.close(); // cleanup on early exit
    }
    return { value: undefined as any, done: true };
  }

  [Symbol.iterator](): this { return this; }
}
```

**Q19. How do you make an iterator reusable — and what is the difference between an Iterator and an Iterable?**
A: This is a subtle but important distinction that trips up many developers:
- **Iterator** — stateful, single-use. Once exhausted, it returns `done: true` on every subsequent `next()` call. Most iterators cannot be rewound.
- **Iterable** — a factory for iterators. Each time `[Symbol.iterator]()` is called, it returns a *fresh* iterator. Arrays, Maps, Sets are iterable — they produce a new iterator on each `for...of`.

```ts
// Iterator — single-use
const iter = [1, 2, 3][Symbol.iterator]();
console.log([...iter]); // [1, 2, 3]
console.log([...iter]); // [] — exhausted, done: true on every next()

// Iterable — produces fresh iterators
const arr = [1, 2, 3];
console.log([...arr]); // [1, 2, 3]
console.log([...arr]); // [1, 2, 3] — new iterator each time

// Common mistake — generator functions vs generator objects
function* gen() { yield 1; yield 2; yield 3; }

const genObj = gen(); // generator OBJECT — iterator, single-use
console.log([...genObj]); // [1, 2, 3]
console.log([...genObj]); // [] — exhausted

const genFn = gen;        // generator FUNCTION — iterable factory
console.log([...genFn()]); // [1, 2, 3]
console.log([...genFn()]); // [1, 2, 3] — fresh generator each time

// Making a custom generator reusable — return an iterable, not an iterator
class ReusableRange implements Iterable<number> {
  constructor(private from: number, private to: number) {}

  // Returns a NEW iterator each time — making the range reusable
  [Symbol.iterator](): Iterator<number> {
    let current = this.from;
    const to    = this.to;
    return {
      next(): IteratorResult<number> {
        return current <= to
          ? { value: current++, done: false }
          : { value: undefined as any, done: true };
      }
    };
  }
}

const range = new ReusableRange(1, 3);
console.log([...range]); // [1, 2, 3]
console.log([...range]); // [1, 2, 3] — fresh iterator, works again
```

**Q20. What are the performance trade-offs between iterators/generators and array methods like `map`, `filter`, `reduce`?**
A:

| Aspect | Array methods (`map`/`filter`) | Iterators / Generators |
|---|---|---|
| **Intermediate allocation** | Each chained method creates a new array | No intermediate arrays — one item at a time |
| **Memory** | O(n) per chain step — `map` then `filter` uses 2× array | O(1) — only current item in memory |
| **Short-circuit** | No early exit on `map`/`filter`; `find`/`some` do | `break` exits immediately, no more items computed |
| **Infinite sequences** | Impossible — arrays must be finite | Natural — `while(true)` with `yield` |
| **Async** | Not applicable | `async function*` for async data sources |
| **Readability** | High — fluent, familiar | High with generators; lower with manual iterators |
| **JIT optimisation** | Well-optimised by engines (V8) | Generally slightly slower per item for simple cases |
| **Best for** | Finite, in-memory, simple transformations | Large/infinite data, I/O sources, lazy pipelines |

```ts
// 10 million numbers — array methods
const bigArray = Array.from({ length: 10_000_000 }, (_, i) => i);
const result1  = bigArray
  .map(n => n * 2)          // allocates 10M array
  .filter(n => n % 3 === 0) // allocates ~3.3M array
  .slice(0, 5);             // [0, 6, 12, 18, 24]

// Same result with generators — ~O(1) memory, stops after 5 items
function* naturals(): Generator<number> {
  let n = 0; while (true) yield n++;
}

const result2 = [...take(filter(map(naturals(), n => n * 2), n => n % 3 === 0), 5)];
// Computed exactly 9 values of naturals() — nothing more

// Rule of thumb:
// < 10K items, no early exit, simple transforms → array methods (simpler, fast enough)
// > 100K items, I/O source, early exit, infinite, or memory-sensitive → iterators/generators
```

## Section 6: Scenario / System Design Style Questions

**Q21. "You need to process a 50 GB CSV file of transactions. The file doesn't fit in memory. How do you use iterators to handle this?"**
A: Stream the file line by line through a composed async generator pipeline — memory usage stays constant regardless of file size:
```ts
import { createReadStream } from "fs";
import { createInterface }  from "readline";

// Layer 1 — async generator: raw lines from file (never loads full file)
async function* readLines(filePath: string): AsyncGenerator<string> {
  const rl = createInterface({
    input:     createReadStream(filePath, { encoding: "utf-8" }),
    crlfDelay: Infinity
  });
  for await (const line of rl) yield line;
}

// Layer 2 — async generator: parse CSV rows (skip header)
async function* parseTransactions(lines: AsyncIterable<string>): AsyncGenerator<Transaction> {
  let isHeader = true;
  for await (const line of lines) {
    if (isHeader) { isHeader = false; continue; }
    const [id, accountId, amount, currency, type, timestamp] = line.split(",");
    yield {
      id, accountId,
      amount:    parseFloat(amount),
      currency,
      type:      type as Transaction["type"],
      timestamp: new Date(timestamp),
    };
  }
}

// Layer 3 — async generator: validate and filter
async function* validTransactions(txns: AsyncIterable<Transaction>): AsyncGenerator<Transaction> {
  for await (const txn of txns) {
    if (txn.amount > 0 && txn.accountId && txn.currency.length === 3) yield txn;
  }
}

// Layer 4 — async generator: batch for bulk DB insert
async function* batch<T>(source: AsyncIterable<T>, size: number): AsyncGenerator<T[]> {
  let current: T[] = [];
  for await (const item of source) {
    current.push(item);
    if (current.length >= size) { yield current; current = []; }
  }
  if (current.length > 0) yield current; // flush remaining
}

// Compose pipeline and process
async function importTransactions(filePath: string): Promise<ImportResult> {
  const pipeline = batch(
    validTransactions(
      parseTransactions(
        readLines(filePath)
      )
    ),
    500 // insert 500 rows per batch
  );

  let total = 0; let inserted = 0; let skipped = 0;

  for await (const batchItems of pipeline) {
    total    += batchItems.length;
    const result = await db.bulkInsert("transactions", batchItems);
    inserted += result.inserted;
    skipped  += result.skipped; // duplicates
  }

  return { total, inserted, skipped };
}

// Memory usage: ~constant — only one batch in memory at any time
// Throughput: ~50K rows/sec with batched inserts
const result = await importTransactions("./transactions_50gb.csv");
```

**Q22. "Design an iterator for a social network's friend-of-friend recommendation system that lazily traverses the graph up to N degrees of separation."**
A: Breadth-first graph traversal with lazy generation — the iterator yields candidates and stops when depth is exceeded:
```ts
type UserId = string;

interface SocialGraph {
  getFriends(userId: UserId): Promise<UserId[]>;
}

// Async generator — BFS traversal up to maxDepth degrees of separation
async function* friendRecommendations(
  graph:    SocialGraph,
  userId:   UserId,
  maxDepth: number = 2
): AsyncGenerator<{ userId: UserId; degree: number }> {
  const visited = new Set<UserId>([userId]); // don't revisit or recommend self
  const queue:  { id: UserId; depth: number }[] = [{ id: userId, depth: 0 }];

  while (queue.length > 0) {
    const { id: currentId, depth } = queue.shift()!;
    if (depth >= maxDepth) continue; // don't go deeper than maxDepth

    const friends = await graph.getFriends(currentId);

    for (const friendId of friends) {
      if (visited.has(friendId)) continue;
      visited.add(friendId);

      // Direct friends (degree 1) are not recommendations — they're already friends
      if (depth + 1 >= 1) {
        yield { userId: friendId, degree: depth + 1 };
      }

      queue.push({ id: friendId, depth: depth + 1 });
    }
  }
}

// Client — lazy: only fetches graph data as recommendations are consumed
async function getTopRecommendations(
  userId: UserId,
  graph:  SocialGraph,
  limit:  number = 10
): Promise<UserId[]> {
  const recommendations: UserId[] = [];

  for await (const rec of friendRecommendations(graph, userId, 2)) {
    recommendations.push(rec.userId);
    if (recommendations.length >= limit) break; // stops traversal early
  }

  return recommendations;
}

// Decorator — score and rank recommendations lazily
async function* scoredRecommendations(
  recs:    AsyncIterable<{ userId: UserId; degree: number }>,
  scorer:  (userId: UserId) => Promise<number>
): AsyncGenerator<{ userId: UserId; score: number }> {
  for await (const rec of recs) {
    const activityScore = await scorer(rec.userId);
    const degreeScore   = 1 / rec.degree; // closer = higher score
    yield { userId: rec.userId, score: activityScore * degreeScore };
  }
}
```

**Q23. "A teammate says 'We should just use `Array.map().filter()` — iterators are over-engineering for our use case.' How do you evaluate this claim?"**
A: Acknowledge the valid cases, then name the specific conditions where iterators earn their place:

> "For most everyday transformations — filtering a list of 200 users, mapping API response fields — `map`/`filter` is the right choice. It's readable, well-optimised by the engine, and the overhead is negligible. The claim is correct in those cases.
>
> But there are three specific situations where array methods genuinely become the wrong tool. First, **large or unbounded data**: if the source is a 50GB file, a database with 10M rows, or a paginated API, loading it into an array first isn't just inefficient — it's impossible. An async generator processes each item as it arrives.
>
> Second, **early termination**: `map` and `filter` always process the full array. If you need only the first 5 items matching a predicate from a million-item dataset, a generator stops immediately on `break` — array methods compute all million transformations first.
>
> Third, **async sources**: array methods are synchronous. If the data comes from a message queue, a WebSocket, or a database cursor, `async function*` is the natural fit — it's a first-class language feature for exactly this pattern."

Then make it concrete:
```ts
// Array methods — correct for this case
const activeUserNames = users             // 200 in-memory users
  .filter(u => u.isActive)
  .map(u => u.name);                     // ✓ simple, readable, fast

// Generator — correct for this case
async function* activeUserStream() {
  for await (const user of userRepo.iterateAll()) { // 10M rows in DB
    if (user.isActive) yield user.name;
  }
}
// Takes only what the caller needs — no 10M array ever built
for await (const name of activeUserStream()) {
  if (count++ > 100) break; // stops DB traversal after 100 items
}
```

**Q24. "How would you implement a resumable iterator — one that can be paused, serialised to disk, and resumed after a process restart?"**
A: The key is making all iterator state serialisable — cursor position, page token, or offset that can be stored and restored:
```ts
interface ResumableIteratorState {
  cursor:       string | null;
  processedIds: string[];
  totalSeen:    number;
}

class ResumableUserMigrator {
  private state: ResumableIteratorState;
  private stateFile: string;

  constructor(stateFile: string) {
    this.stateFile = stateFile;
    this.state     = this.loadState();
  }

  private loadState(): ResumableIteratorState {
    try {
      return JSON.parse(fs.readFileSync(this.stateFile, "utf-8"));
    } catch {
      return { cursor: null, processedIds: [], totalSeen: 0 };
    }
  }

  private async saveState(): Promise<void> {
    await fs.promises.writeFile(this.stateFile, JSON.stringify(this.state));
  }

  async* resumableMigration(): AsyncGenerator<MigrationResult> {
    while (true) {
      // Resume from saved cursor — or start from beginning
      const page = await legacyDb.getUsers({
        cursor:   this.state.cursor,
        pageSize: 100,
      });

      for (const user of page.items) {
        // Skip already-processed items (idempotency)
        if (this.state.processedIds.includes(user.id)) continue;

        const result = await migrateUser(user);
        this.state.processedIds.push(user.id);
        this.state.totalSeen++;

        // Checkpoint every 10 items
        if (this.state.totalSeen % 10 === 0) {
          await this.saveState(); // persist progress
        }

        yield result;
      }

      if (!page.nextCursor) break; // no more pages
      this.state.cursor = page.nextCursor;
      await this.saveState(); // save cursor after each page
    }

    // Final save
    await this.saveState();
  }
}

// Usage — resumable across process restarts
const migrator = new ResumableUserMigrator("./migration-state.json");

for await (const result of migrator.resumableMigration()) {
  console.log(`Migrated user ${result.id}: ${result.status}`);
  // If process crashes here, next run resumes from saved cursor
}
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Manual Iterator (class) | Generator function | Array methods |
|---|---|---|---|
| **Boilerplate** | High — class, state vars, `next()` shape | Low — `function*`, `yield` | None |
| **Lazy evaluation** | Manual | Automatic | No — full array computed |
| **Infinite sequences** | Possible | Natural | Impossible |
| **Async support** | `AsyncIterator` interface | `async function*` | No |
| **Early termination** | Via `return()` method | `finally` block in generator | `find`/`some` only |
| **Custom operations** | `reset()`, `peek()`, `seek()` | Limited — only `yield` | `map`, `filter`, `reduce` |
| **Reusability** | `reset()` or new instance | New call to generator fn | New call to method |
| **Resource cleanup** | `return()` method | `finally` block | N/A |
| **Best for** | Rich traversal API, testable state | Pipelines, recursion, lazy sequences | In-memory, finite, simple |

## Iterator Variants at a Glance

| Variant | Key characteristic | Best used for |
|---|---|---|
| **Forward iterator** | `next()` only | Most collections — arrays, sets, queues |
| **Bidirectional iterator** | `next()` and `prev()` | Doubly-linked lists, history navigation, undo/redo |
| **Random access iterator** | `seek(index)` | Arrays, indexed collections |
| **Filtered iterator** | Wraps another iterator, skips non-matching | Lazy `filter` without intermediate array |
| **Transforming iterator** | Wraps another iterator, maps values | Lazy `map` without intermediate array |
| **Composite iterator** | Chains multiple iterables | Merging streams, `chain()` combinator |
| **Async iterator** | `async next()` / `for await...of` | I/O-bound sources — DB, network, queue |
| **Infinite iterator** | Never returns `done: true` | Fibonacci, natural numbers, event streams |
| **Resumable iterator** | Serialisable cursor position | Long-running migrations, crash recovery |
| **Snapshot iterator** | Iterates over copy of collection at creation | Safe iteration despite concurrent modification |
