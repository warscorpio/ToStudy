# Design Patterns — Behavioral: Interpreter (Concept) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Interpreter pattern?**
A: The Interpreter pattern is a behavioral design pattern that defines a grammar for a language and provides an interpreter to deal with that grammar. For each rule in the grammar, you define a class. An abstract syntax tree (AST) composed of these classes represents a sentence in the language, and calling `interpret()` on the root of the tree evaluates the sentence. The GoF definition: *"Given a language, define a representation for its grammar along with an interpreter that uses the representation to interpret sentences in the language."*

In practical terms: you have a domain-specific language (DSL) — a set of rules, expressions, or instructions meaningful to your domain — and you need to parse strings or structured input into that language and evaluate them. The Interpreter pattern gives you the object model for representing and evaluating those expressions. Every token type in the grammar becomes a class; every expression becomes an object; every evaluation becomes a method call on that object graph.

**Q2. What problem does the Interpreter pattern solve?**
A: It solves the problem of evaluating a language or rule system that is too complex for hardcoded `if/else` chains but not complex enough to justify a full compiler or parser generator. The key signals that you need an Interpreter:

- **Rules change frequently** — business rules for loan eligibility, discount calculations, or fraud scoring that are updated by product/compliance teams, not engineers. Hardcoding rules means redeployment on every change; an interpreter lets rules be stored as strings and evaluated at runtime.
- **Rules come from external sources** — a database, a configuration file, an admin panel. The rules are data, not code.
- **Users define expressions** — a query builder, a filter system, a formula editor where users construct expressions that the system must evaluate.
- **The language has recursive structure** — expressions contain sub-expressions, which contain sub-expressions. This recursive composition maps naturally to the Interpreter's class hierarchy.

Without Interpreter, evaluating dynamic rules usually degrades into a `switch` statement that grows with every new rule type, a regular expression that becomes unmaintainable, or a call to `eval()` which is a security vulnerability.

**Q3. What are the participants in the Interpreter pattern?**
A:
- **AbstractExpression** — declares the `interpret(context)` method that all concrete expression classes implement.
- **TerminalExpression** — implements `interpret()` for terminal symbols in the grammar — the leaves of the AST. Examples: a literal value (`42`, `"APPROVED"`), a variable reference (`creditScore`, `loanAmount`), a constant (`MIN_INCOME`).
- **NonTerminalExpression** — implements `interpret()` for rules in the grammar that contain other expressions. Examples: `AND`, `OR`, `NOT`, `>`, `+`, function calls. NonTerminalExpressions hold references to child expressions and recursively call `interpret()` on them.
- **Context** — holds global state accessible during interpretation: variable bindings (`creditScore = 720`), environment config, lookup tables, input data.
- **Client** — builds the AST (either manually or by parsing a string) and calls `interpret(context)` on the root.

**Q4. What is the difference between a Terminal Expression and a Non-Terminal Expression?**
A: The distinction maps directly to formal grammar theory:

- **Terminal symbols** are the atomic units of the language — they cannot be decomposed further. In a rule language, these are literal values (`50000`, `"ACTIVE"`), variable names (`creditScore`, `panVerified`), and constants. A `TerminalExpression.interpret(context)` simply looks up or returns a value — it has no child expressions.
- **Non-terminal symbols** are composed of other symbols — they define the structure of the language. In a rule language, these are operators (`AND`, `OR`, `>`, `+`), functions (`MAX(a, b)`, `CONTAINS(list, value)`), and groupings. A `NonTerminalExpression.interpret(context)` evaluates its children recursively and combines their results.

```
Rule: creditScore > 650 AND loanAmount <= 500000

AST:
        AND (NonTerminal)
       /               \
  GT (NonTerminal)    LTE (NonTerminal)
  /      \            /           \
creditScore  650   loanAmount   500000
(Terminal) (Terminal) (Terminal) (Terminal)
```

Calling `interpret(context)` on the `AND` node triggers `interpret` on `GT` and `LTE`; each of those triggers `interpret` on their children — the variable lookups and literal values. The result bubbles up to produce `true` or `false`.

**Q5. When should you NOT use the Interpreter pattern?**
A: The GoF themselves note that Interpreter is best applied to simple grammars. It breaks down in several situations:

- **Complex grammars** — a grammar with 30+ rules and deep nesting produces a class explosion (one class per grammar rule) and an AST that is expensive to build and traverse. At this point, use a proper parser generator (ANTLR, PEG.js, `chevrotain`) or an existing expression evaluator library.
- **Performance-critical paths** — AST traversal via virtual dispatch (calling `interpret()` on every node) is slower than compiled evaluation. For rules evaluated millions of times per second, compile the AST to bytecode or a function at parse time; only interpret at evaluation time.
- **Grammar changes frequently in structure** — if the grammar itself (not just the rules) changes often, every structural change requires adding new expression classes. A data-driven approach (JSON rule schema + generic evaluator) may be more maintainable.
- **Security-sensitive input** — never interpret user-supplied strings with direct code execution (`eval`, `Function()`). The Interpreter pattern with a defined AST class hierarchy is safe — users can only construct expressions from the defined grammar, not inject arbitrary code.

## Section 2: Implementation

**Q6. What does a canonical Interpreter implementation look like in TypeScript for a loan eligibility rule engine?**
A:
```ts
// Context — holds all variable values for the current evaluation
interface EvaluationContext {
  variables: Map<string, number | string | boolean>;
  get(name: string): number | string | boolean;
}

class LoanEligibilityContext implements EvaluationContext {
  variables = new Map<string, number | string | boolean>();

  constructor(applicantData: {
    creditScore: number;
    monthlyIncome: number;
    loanAmount: number;
    existingEmi: number;
    panVerified: boolean;
    employmentType: string;
  }) {
    Object.entries(applicantData).forEach(([k, v]) => this.variables.set(k, v));
  }

  get(name: string): number | string | boolean {
    if (!this.variables.has(name)) {
      throw new Error(`Unknown variable in rule: "${name}"`);
    }
    return this.variables.get(name)!;
  }
}

// AbstractExpression
interface Expression {
  interpret(ctx: EvaluationContext): number | string | boolean;
}

// --- Terminal Expressions ---

// Variable lookup — reads from context
class VariableExpression implements Expression {
  constructor(private readonly name: string) {}

  interpret(ctx: EvaluationContext): number | string | boolean {
    return ctx.get(this.name);
  }
}

// Numeric literal
class NumberLiteral implements Expression {
  constructor(private readonly value: number) {}
  interpret(_ctx: EvaluationContext): number { return this.value; }
}

// String literal
class StringLiteral implements Expression {
  constructor(private readonly value: string) {}
  interpret(_ctx: EvaluationContext): string { return this.value; }
}

// Boolean literal
class BooleanLiteral implements Expression {
  constructor(private readonly value: boolean) {}
  interpret(_ctx: EvaluationContext): boolean { return this.value; }
}

// --- NonTerminal Expressions — Comparison ---

class GreaterThanExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    return (this.left.interpret(ctx) as number) > (this.right.interpret(ctx) as number);
  }
}

class LessThanOrEqualExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    return (this.left.interpret(ctx) as number) <= (this.right.interpret(ctx) as number);
  }
}

class EqualsExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    return this.left.interpret(ctx) === this.right.interpret(ctx);
  }
}

// --- NonTerminal Expressions — Logical ---

class AndExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    // Short-circuit evaluation
    return (this.left.interpret(ctx) as boolean) && (this.right.interpret(ctx) as boolean);
  }
}

class OrExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    return (this.left.interpret(ctx) as boolean) || (this.right.interpret(ctx) as boolean);
  }
}

class NotExpression implements Expression {
  constructor(private readonly operand: Expression) {}

  interpret(ctx: EvaluationContext): boolean {
    return !(this.operand.interpret(ctx) as boolean);
  }
}

// --- NonTerminal Expressions — Arithmetic ---

class AddExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): number {
    return (this.left.interpret(ctx) as number) + (this.right.interpret(ctx) as number);
  }
}

class DivideExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(ctx: EvaluationContext): number {
    const divisor = this.right.interpret(ctx) as number;
    if (divisor === 0) throw new Error("Division by zero in rule expression");
    return (this.left.interpret(ctx) as number) / divisor;
  }
}

// --- Building and evaluating rules ---

// Rule: creditScore > 650 AND monthlyIncome > 15000 AND loanAmount <= 500000
const eligibilityRule: Expression = new AndExpression(
  new AndExpression(
    new GreaterThanExpression(
      new VariableExpression("creditScore"),
      new NumberLiteral(650),
    ),
    new GreaterThanExpression(
      new VariableExpression("monthlyIncome"),
      new NumberLiteral(15_000),
    ),
  ),
  new LessThanOrEqualExpression(
    new VariableExpression("loanAmount"),
    new NumberLiteral(500_000),
  ),
);

// Rule: FOIR = (existingEmi + proposedEmi) / monthlyIncome <= 0.5
const foirRule: Expression = new LessThanOrEqualExpression(
  new DivideExpression(
    new AddExpression(
      new VariableExpression("existingEmi"),
      new VariableExpression("proposedEmi"),
    ),
    new VariableExpression("monthlyIncome"),
  ),
  new NumberLiteral(0.5),
);

// Evaluate
const ctx = new LoanEligibilityContext({
  creditScore: 720,
  monthlyIncome: 50_000,
  loanAmount: 300_000,
  existingEmi: 5_000,
  panVerified: true,
  employmentType: "SALARIED",
});
ctx.variables.set("proposedEmi", 10_000);

console.log(eligibilityRule.interpret(ctx)); // true
console.log(foirRule.interpret(ctx));         // true — (5000 + 10000) / 50000 = 0.3 ≤ 0.5
```

**Q7. How do you build an AST from a string rule rather than constructing it manually?**
A: Manual AST construction is useful for hardcoded rules, but the real power of Interpreter comes when rules are stored as strings in a database and parsed at runtime. A simple recursive descent parser converts a rule string to an AST:

```ts
class RuleParser {
  private tokens: string[] = [];
  private pos = 0;

  parse(rule: string): Expression {
    this.tokens = this.tokenize(rule);
    this.pos = 0;
    return this.parseOr(); // Start with lowest precedence
  }

  private tokenize(rule: string): string[] {
    // Simple tokenizer — splits on spaces and captures operators and parentheses
    return rule
      .replace(/\(/g, " ( ")
      .replace(/\)/g, " ) ")
      .trim()
      .split(/\s+/)
      .filter(Boolean);
  }

  private peek(): string | undefined {
    return this.tokens[this.pos];
  }

  private consume(): string {
    return this.tokens[this.pos++];
  }

  // OR has lowest precedence — parsed first, sits highest in AST
  private parseOr(): Expression {
    let left = this.parseAnd();
    while (this.peek() === "OR") {
      this.consume(); // consume "OR"
      left = new OrExpression(left, this.parseAnd());
    }
    return left;
  }

  private parseAnd(): Expression {
    let left = this.parseNot();
    while (this.peek() === "AND") {
      this.consume(); // consume "AND"
      left = new AndExpression(left, this.parseNot());
    }
    return left;
  }

  private parseNot(): Expression {
    if (this.peek() === "NOT") {
      this.consume();
      return new NotExpression(this.parseComparison());
    }
    return this.parseComparison();
  }

  private parseComparison(): Expression {
    const left = this.parsePrimary();
    const op = this.peek();

    if (op === ">") {
      this.consume();
      return new GreaterThanExpression(left, this.parsePrimary());
    }
    if (op === "<=") {
      this.consume();
      return new LessThanOrEqualExpression(left, this.parsePrimary());
    }
    if (op === "==") {
      this.consume();
      return new EqualsExpression(left, this.parsePrimary());
    }
    return left;
  }

  private parsePrimary(): Expression {
    const token = this.peek();
    if (!token) throw new Error("Unexpected end of rule expression");

    // Parenthesized sub-expression
    if (token === "(") {
      this.consume(); // consume "("
      const expr = this.parseOr();
      if (this.consume() !== ")") throw new Error("Expected closing parenthesis");
      return expr;
    }

    this.consume();

    // Boolean literals
    if (token === "true") return new BooleanLiteral(true);
    if (token === "false") return new BooleanLiteral(false);

    // String literals: "SALARIED"
    if (token.startsWith('"') && token.endsWith('"')) {
      return new StringLiteral(token.slice(1, -1));
    }

    // Numeric literals
    if (!isNaN(Number(token))) return new NumberLiteral(Number(token));

    // Variable reference
    return new VariableExpression(token);
  }
}

// Rules stored in database as strings — parsed at runtime
const ruleStrings = [
  "creditScore > 650 AND monthlyIncome > 15000",
  "loanAmount <= 500000 AND NOT employmentType == \"UNEMPLOYED\"",
  "creditScore > 700 OR (creditScore > 650 AND panVerified == true)",
];

const parser = new RuleParser();
const rules = ruleStrings.map(r => ({ rule: r, expr: parser.parse(r) }));

// Cache parsed ASTs — parsing is expensive; evaluation is cheap
const results = rules.map(({ rule, expr }) => ({
  rule,
  passed: expr.interpret(ctx) as boolean,
}));
```

**Q8. How do you cache parsed ASTs for performance?**
A: Parsing a rule string into an AST is CPU-intensive — tokenization, recursive descent, object allocation. Evaluating the AST against a context is fast. Rules change infrequently; evaluations happen on every request. Cache the AST, not the result:

```ts
class RuleCache {
  private cache = new Map<string, Expression>();
  private readonly parser = new RuleParser();

  getOrParse(ruleString: string): Expression {
    if (!this.cache.has(ruleString)) {
      const ast = this.parser.parse(ruleString);
      this.cache.set(ruleString, ast);
    }
    return this.cache.get(ruleString)!;
  }

  invalidate(ruleString: string): void {
    this.cache.delete(ruleString);
  }

  invalidateAll(): void {
    this.cache.clear();
  }
}

// In NestJS — RuleCache as a singleton provider
@Injectable()
export class EligibilityRuleEngine {
  private readonly cache = new RuleCache();

  constructor(private readonly ruleRepo: EligibilityRuleRepository) {}

  async evaluate(applicant: ApplicantData): Promise<EligibilityResult> {
    // Load rules from DB (or a hot-reload cache)
    const rules = await this.ruleRepo.findActiveRules();

    const ctx = new LoanEligibilityContext(applicant);
    const results: RuleResult[] = [];

    for (const rule of rules) {
      // Parse once, evaluate many times
      const expr = this.cache.getOrParse(rule.expression);
      const passed = expr.interpret(ctx) as boolean;

      results.push({
        ruleId: rule.id,
        ruleName: rule.name,
        expression: rule.expression,
        passed,
        evaluatedAt: new Date(),
      });

      if (!passed && rule.isBlockingRule) {
        // Short-circuit on blocking rule failure
        return { eligible: false, results, blockedBy: rule.name };
      }
    }

    return {
      eligible: results.every(r => r.passed),
      results,
    };
  }
}
```

**Q9. How do you implement function-call expressions in the Interpreter pattern?**
A: Function calls are NonTerminalExpressions where the operator is a named function and the operands are its arguments:

```ts
// Function call expression — interprets named functions with evaluated arguments
class FunctionCallExpression implements Expression {
  constructor(
    private readonly name: string,
    private readonly args: Expression[],
  ) {}

  interpret(ctx: EvaluationContext): number | string | boolean {
    const evaluatedArgs = this.args.map(arg => arg.interpret(ctx));
    return this.callFunction(this.name, evaluatedArgs, ctx);
  }

  private callFunction(
    name: string,
    args: (number | string | boolean)[],
    ctx: EvaluationContext,
  ): number | string | boolean {
    switch (name) {
      case "MAX":
        return Math.max(...(args as number[]));
      case "MIN":
        return Math.min(...(args as number[]));
      case "ROUND":
        return Math.round(args[0] as number);
      case "ABS":
        return Math.abs(args[0] as number);
      case "CONTAINS":
        return (args[0] as string).includes(args[1] as string);
      case "LENGTH":
        return (args[0] as string).length;
      case "BETWEEN": {
        const [value, low, high] = args as number[];
        return value >= low && value <= high;
      }
      case "FOIR": {
        // Domain-specific: Fixed Obligation to Income Ratio
        const emi = ctx.get("existingEmi") as number;
        const proposed = ctx.get("proposedEmi") as number;
        const income = ctx.get("monthlyIncome") as number;
        return (emi + proposed) / income;
      }
      default:
        throw new Error(`Unknown function in rule expression: "${name}"`);
    }
  }
}

// Usage: BETWEEN(creditScore, 650, 750) AND FOIR() <= 0.5
const rangeRule: Expression = new AndExpression(
  new FunctionCallExpression("BETWEEN", [
    new VariableExpression("creditScore"),
    new NumberLiteral(650),
    new NumberLiteral(750),
  ]),
  new LessThanOrEqualExpression(
    new FunctionCallExpression("FOIR", []),
    new NumberLiteral(0.5),
  ),
);
```

**Q10. How do you add a new expression type without modifying existing expressions?**
A: Add a new class implementing `AbstractExpression` — existing expression classes are untouched (OCP compliance):

```ts
// New requirement: support IN operator — "employmentType IN [SALARIED, SELF_EMPLOYED]"
class InExpression implements Expression {
  constructor(
    private readonly value: Expression,
    private readonly allowedValues: Expression[],
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    const val = this.value.interpret(ctx);
    return this.allowedValues.some(allowed => allowed.interpret(ctx) === val);
  }
}

// New requirement: conditional expression — "IF condition THEN trueValue ELSE falseValue"
class IfThenElseExpression implements Expression {
  constructor(
    private readonly condition: Expression,
    private readonly thenExpr: Expression,
    private readonly elseExpr: Expression,
  ) {}

  interpret(ctx: EvaluationContext): number | string | boolean {
    return (this.condition.interpret(ctx) as boolean)
      ? this.thenExpr.interpret(ctx)
      : this.elseExpr.interpret(ctx);
  }
}

// Usage — graded loan amount based on credit score tier
const maxLoanRule: Expression = new IfThenElseExpression(
  new GreaterThanExpression(new VariableExpression("creditScore"), new NumberLiteral(750)),
  new NumberLiteral(1_000_000),  // high credit — up to 10L
  new IfThenElseExpression(
    new GreaterThanExpression(new VariableExpression("creditScore"), new NumberLiteral(650)),
    new NumberLiteral(500_000),  // medium credit — up to 5L
    new NumberLiteral(200_000),  // low credit — up to 2L
  ),
);
```

## Section 3: Interpreter in Real-World Systems

**Q11. How is the Interpreter pattern used in query languages and search engines?**
A: Every SQL database, NoSQL query API, and search engine uses the Interpreter pattern internally. When you write a SQL `WHERE` clause or an Elasticsearch `bool` query, you're writing in a language that the engine interprets via an AST:

```ts
// Elasticsearch DSL as Interpreter — queries are composed expressions
interface QueryExpression {
  toElasticQuery(): object;
}

class TermQuery implements QueryExpression {
  constructor(
    private readonly field: string,
    private readonly value: string | number,
  ) {}

  toElasticQuery(): object {
    return { term: { [this.field]: this.value } };
  }
}

class RangeQuery implements QueryExpression {
  constructor(
    private readonly field: string,
    private readonly gte?: number,
    private readonly lte?: number,
  ) {}

  toElasticQuery(): object {
    return { range: { [this.field]: { gte: this.gte, lte: this.lte } } };
  }
}

class BoolQuery implements QueryExpression {
  constructor(private readonly clauses: {
    must?: QueryExpression[];
    should?: QueryExpression[];
    must_not?: QueryExpression[];
    filter?: QueryExpression[];
  }) {}

  toElasticQuery(): object {
    return {
      bool: {
        must:     this.clauses.must?.map(q => q.toElasticQuery()),
        should:   this.clauses.should?.map(q => q.toElasticQuery()),
        must_not: this.clauses.must_not?.map(q => q.toElasticQuery()),
        filter:   this.clauses.filter?.map(q => q.toElasticQuery()),
      },
    };
  }
}

// Build a loan search query compositionally
const query = new BoolQuery({
  must: [
    new TermQuery("status", "ACTIVE"),
    new TermQuery("employmentType", "SALARIED"),
  ],
  filter: [
    new RangeQuery("creditScore", 650),
    new RangeQuery("loanAmount", undefined, 500_000),
  ],
  must_not: [
    new TermQuery("flagged", true),
  ],
});

const esQuery = query.toElasticQuery();
// Produces the correct nested bool/must/filter/must_not structure
```
TypeORM's `QueryBuilder`, Mongoose's query chaining, and Knex's builder all implement this same pattern — each method call builds up a node in the query AST; the terminal call (`.getQuery()`, `.toSQL()`) interprets the AST into a string.

**Q12. How does the Interpreter pattern apply to template engines?**
A: Template engines (Handlebars, Mustache, Nunjucks, EJS) parse a template string into an AST and interpret it against a data context. Each template construct is an expression type:

```ts
// Simplified template interpreter
interface TemplateNode {
  render(context: Record<string, unknown>): string;
}

// Terminal — literal text segment
class TextNode implements TemplateNode {
  constructor(private readonly text: string) {}
  render(_ctx: Record<string, unknown>): string { return this.text; }
}

// Terminal — variable interpolation {{variableName}}
class VariableNode implements TemplateNode {
  constructor(private readonly name: string) {}

  render(ctx: Record<string, unknown>): string {
    const value = ctx[this.name];
    return value !== undefined ? String(value) : "";
  }
}

// NonTerminal — conditional {{#if condition}}...{{/if}}
class IfNode implements TemplateNode {
  constructor(
    private readonly condition: string,
    private readonly body: TemplateNode[],
    private readonly elseBody: TemplateNode[] = [],
  ) {}

  render(ctx: Record<string, unknown>): string {
    const value = ctx[this.condition];
    const branch = value ? this.body : this.elseBody;
    return branch.map(n => n.render(ctx)).join("");
  }
}

// NonTerminal — iteration {{#each items}}...{{/each}}
class EachNode implements TemplateNode {
  constructor(
    private readonly collection: string,
    private readonly body: TemplateNode[],
  ) {}

  render(ctx: Record<string, unknown>): string {
    const items = ctx[this.collection] as unknown[];
    if (!Array.isArray(items)) return "";
    return items.map(item =>
      this.body.map(n => n.render({ ...ctx, this: item })).join("")
    ).join("");
  }
}

// NonTerminal — root template is a sequence of nodes
class TemplateRoot implements TemplateNode {
  constructor(private readonly children: TemplateNode[]) {}
  render(ctx: Record<string, unknown>): string {
    return this.children.map(n => n.render(ctx)).join("");
  }
}

// Usage — render a loan approval email template
const template = new TemplateRoot([
  new TextNode("Dear "),
  new VariableNode("userName"),
  new TextNode(",\n"),
  new IfNode("approved", [
    new TextNode("Your loan of ₹"),
    new VariableNode("amount"),
    new TextNode(" has been approved.\n"),
    new TextNode("Disbursement details:\n"),
    new EachNode("disbursements", [
      new TextNode("  - ₹"),
      new VariableNode("this"),
      new TextNode("\n"),
    ]),
  ], [
    new TextNode("Unfortunately, your loan application has been rejected.\n"),
    new TextNode("Reason: "),
    new VariableNode("rejectionReason"),
    new TextNode("\n"),
  ]),
]);

const output = template.render({
  userName: "Rahul Sharma",
  approved: true,
  amount: "50,000",
  disbursements: ["25,000", "25,000"],
});
```

**Q13. How is the Interpreter pattern used in the context of a Business Rules Engine (BRE)?**
A: A BRE is the most common real-world application of the Interpreter pattern in fintech. Rules are stored in a database as strings, loaded at runtime, parsed into ASTs, cached, and evaluated against applicant data — enabling non-engineers to modify loan eligibility criteria, pricing tiers, and fraud flags without code deployments:

```ts
// Rule stored in DB — product/compliance team edits via admin panel
// expression: "creditScore > 700 AND FOIR() <= 0.4 AND NOT employmentType == \"UNEMPLOYED\""
// ruleType: "ELIGIBILITY"
// priority: 1
// isBlocking: true
// effectiveFrom: "2026-01-01"

@Injectable()
export class NachPaymentBRE {
  constructor(
    private readonly ruleRepo: BRERepository,
    private readonly ruleCache: RuleCache,
  ) {}

  async evaluateEligibility(applicant: NachApplicant): Promise<BREResult> {
    const rules = await this.ruleRepo.findActiveRules({
      type: "NACH_ELIGIBILITY",
      effectiveAt: new Date(),
    });

    const ctx = new LoanEligibilityContext({
      creditScore: applicant.creditScore,
      monthlyIncome: applicant.monthlyIncome,
      loanAmount: applicant.requestedAmount,
      existingEmi: applicant.existingEmi,
      panVerified: applicant.panVerified,
      employmentType: applicant.employmentType,
    });
    ctx.variables.set("proposedEmi", applicant.proposedEmi);

    const ruleResults: BRERuleResult[] = [];
    let eligible = true;

    for (const rule of rules.sort((a, b) => a.priority - b.priority)) {
      let passed: boolean;
      let error: string | undefined;

      try {
        const expr = this.ruleCache.getOrParse(rule.expression);
        passed = expr.interpret(ctx) as boolean;
      } catch (err) {
        // Rule parsing or evaluation error — treat as blocking failure
        passed = false;
        error = (err as Error).message;
        logger.error({ rule: rule.id, err }, "BRE rule evaluation error");
      }

      ruleResults.push({
        ruleId: rule.id,
        ruleName: rule.name,
        expression: rule.expression,
        passed,
        error,
        evaluatedAt: new Date(),
      });

      if (!passed && rule.isBlocking) {
        eligible = false;
        if (rule.failFast) break; // short-circuit remaining rules
      }
    }

    return {
      eligible,
      ruleResults,
      applicantId: applicant.id,
      evaluatedAt: new Date(),
    };
  }
}
```

**Q14. How does the Visitor pattern complement Interpreter for AST traversal?**
A: The Interpreter pattern puts evaluation logic *inside each expression class* (`interpret()` method). This works well but creates a problem: adding a new *operation* on the AST (not a new expression type, but a new thing to *do* with the AST — pretty-printing, serialization, optimization, type-checking) requires modifying every expression class.

The Visitor pattern solves this: separate the operations from the AST node classes. Each visitor implements the operation for every node type:

```ts
// Visitor interface — one visit method per expression type
interface ExpressionVisitor<T> {
  visitNumber(expr: NumberLiteral): T;
  visitVariable(expr: VariableExpression): T;
  visitAnd(expr: AndExpression): T;
  visitOr(expr: OrExpression): T;
  visitGreaterThan(expr: GreaterThanExpression): T;
  // ... one per expression type
}

// Modified AbstractExpression — accepts visitors
interface Expression {
  interpret(ctx: EvaluationContext): number | string | boolean;
  accept<T>(visitor: ExpressionVisitor<T>): T; // new: accept visitor
}

// Pretty-printer visitor — converts AST back to readable string
class PrettyPrintVisitor implements ExpressionVisitor<string> {
  visitNumber(expr: NumberLiteral): string { return String(expr.value); }
  visitVariable(expr: VariableExpression): string { return expr.name; }

  visitAnd(expr: AndExpression): string {
    return `(${expr.left.accept(this)} AND ${expr.right.accept(this)})`;
  }
  visitOr(expr: OrExpression): string {
    return `(${expr.left.accept(this)} OR ${expr.right.accept(this)})`;
  }
  visitGreaterThan(expr: GreaterThanExpression): string {
    return `${expr.left.accept(this)} > ${expr.right.accept(this)}`;
  }
}

// SQL-generation visitor — converts AST to a SQL WHERE clause
class SqlWhereVisitor implements ExpressionVisitor<string> {
  visitNumber(expr: NumberLiteral): string { return String(expr.value); }
  visitVariable(expr: VariableExpression): string { return expr.name; }
  visitAnd(expr: AndExpression): string {
    return `(${expr.left.accept(this)} AND ${expr.right.accept(this)})`;
  }
  visitGreaterThan(expr: GreaterThanExpression): string {
    return `${expr.left.accept(this)} > ${expr.right.accept(this)}`;
  }
}

// Optimization visitor — simplifies constant sub-expressions
class ConstantFoldingVisitor implements ExpressionVisitor<Expression> {
  visitNumber(expr: NumberLiteral): Expression { return expr; }
  visitAnd(expr: AndExpression): Expression {
    const left = expr.left.accept(this);
    const right = expr.right.accept(this);
    // If both are literals, fold at parse time
    if (left instanceof BooleanLiteral && right instanceof BooleanLiteral) {
      return new BooleanLiteral(left.value && right.value);
    }
    return new AndExpression(left, right);
  }
  // ...
}
```
Use Interpreter alone when you have one operation (evaluate). Add Visitor when you need multiple operations on the same AST (evaluate + pretty-print + serialize + optimize + type-check).

## Section 4: Interpreter vs. Related Patterns

**Q15. When should you use Interpreter vs. a strategy-based rule engine?**
A: Both can evaluate business rules, but they differ in flexibility and complexity:

| Aspect                  | Interpreter Pattern                                   | Strategy-based Rule Engine                          |
|---                      |---                                                    |---                                                  |
| Rule definition         | String expression parsed into AST                    | Code — each rule is a function/class                |
| Rule storage            | Database, config file, admin panel                   | Source code — requires deployment to change          |
| Runtime rule changes    | Yes — parse new rule string, evaluate immediately    | No — requires code change + deployment              |
| Complexity of grammar   | Can support any expressible grammar                  | Limited to what the strategy interface supports     |
| Performance             | AST traversal — slower per evaluation                | Direct function call — faster                       |
| Type safety             | Runtime type errors if rule is malformed             | Compile-time type safety                            |
| Non-engineer access     | Yes — product/compliance can write rules             | No — developers only                                |
| Best for                | Frequently changing, externally defined rules        | Stable rules defined by developers                  |

In fintech: use Strategy for rules that are architectural (e.g., which credit bureau to call) and use Interpreter for rules that are business policy (e.g., minimum credit score thresholds that change with RBI guidelines).

**Q16. When should you use a library like `json-rules-engine` instead of implementing Interpreter yourself?**
A: Implement Interpreter yourself when: the grammar is specific to your domain, you need custom function types (FOIR, EMI calculations), the team wants full control over parsing and evaluation, or the grammar is genuinely simple.

Use a library when: the grammar follows standard boolean logic over JSON-structured facts (which most BREs do), time-to-market matters more than customization, or you need built-in features like rule prioritization, event emission on rule trigger, and async condition evaluation:

```ts
import { Engine } from "json-rules-engine";

const engine = new Engine();

// Rules defined as JSON — stored in DB, loaded at runtime
engine.addRule({
  name: "NACH Eligibility — Credit Score",
  priority: 10,
  conditions: {
    all: [
      { fact: "creditScore",    operator: "greaterThan",         value: 650 },
      { fact: "monthlyIncome",  operator: "greaterThan",         value: 15000 },
      { fact: "loanAmount",     operator: "lessThanInclusive",   value: 500000 },
      { fact: "employmentType", operator: "notIn",               value: ["UNEMPLOYED", "STUDENT"] },
    ],
  },
  event: { type: "ELIGIBLE_FOR_NACH", params: { tier: "STANDARD" } },
});

engine.addRule({
  name: "NACH Eligibility — Premium Tier",
  priority: 5,
  conditions: {
    all: [
      { fact: "creditScore",   operator: "greaterThan", value: 750 },
      { fact: "monthlyIncome", operator: "greaterThan", value: 50000 },
    ],
  },
  event: { type: "ELIGIBLE_FOR_NACH", params: { tier: "PREMIUM" } },
});

// Evaluate
const { events } = await engine.run({
  creditScore: 720,
  monthlyIncome: 50000,
  loanAmount: 300000,
  employmentType: "SALARIED",
});

const eligibleEvent = events.find(e => e.type === "ELIGIBLE_FOR_NACH");
```
`json-rules-engine` implements the Interpreter pattern internally — each condition type (`greaterThan`, `lessThanInclusive`, `notIn`) is a TerminalExpression; `all`/`any` are NonTerminalExpressions. Knowing the pattern helps you understand and extend any library built on it.

## Section 5: Pitfalls & Anti-patterns

**Q17. What are the most common Interpreter pattern mistakes?**
A:
- **No input validation at parse time** — accepting any string as a rule expression and failing at evaluation time with a cryptic error. Parse the rule fully at insertion time (when a product manager saves a rule in the admin panel), validate the AST, and store only valid rules. Never fail at evaluation time for a rule that should have been caught at parse time.
- **Mutable context shared between concurrent evaluations** — if the `EvaluationContext` is mutated during evaluation (variables set mid-evaluation) and the same context instance is shared between concurrent requests, rule results become non-deterministic. Contexts must be per-request and created fresh for each evaluation.
- **No maximum expression depth** — a malicious or misconfigured rule can create deeply recursive ASTs that overflow the call stack during evaluation. Enforce a max depth at parse time: `if (depth > 50) throw new Error("Rule expression too deeply nested")`.
- **Evaluating untrusted strings with `eval()`** — never substitute the Interpreter pattern with `eval(ruleString)` or `new Function(ruleString)`. The Interpreter's explicit AST class hierarchy is the security boundary — users can only express what the grammar allows.
- **Class explosion** — a grammar with 40 operator types produces 40 expression classes. Group related operators into a single parameterized class when practical: `ComparisonExpression(op: ">"|"<"|">="|"<="|"=="|"!=")` instead of six separate comparison classes.

**Q18. How do you handle errors gracefully in a rule interpreter?**
A: Three layers of error handling:

```ts
// Layer 1 — Parse-time validation: catch malformed expressions before storing
class SafeRuleParser extends RuleParser {
  parseAndValidate(rule: string): { ast: Expression; errors: string[] } {
    const errors: string[] = [];
    try {
      const ast = this.parse(rule);
      this.validateAst(ast, errors, 0);
      return { ast, errors };
    } catch (err) {
      errors.push(`Parse error: ${(err as Error).message}`);
      return { ast: null!, errors };
    }
  }

  private validateAst(node: Expression, errors: string[], depth: number): void {
    if (depth > 50) {
      errors.push("Expression too deeply nested (max depth: 50)");
      return;
    }
    // Validate children recursively
  }
}

// Layer 2 — Evaluation-time error isolation: one rule failing must not crash others
for (const rule of rules) {
  try {
    const result = this.cache.getOrParse(rule.expression).interpret(ctx) as boolean;
    ruleResults.push({ ruleId: rule.id, passed: result });
  } catch (err) {
    // Log and treat as failed — don't crash the entire eligibility check
    logger.error({ ruleId: rule.id, err }, "Rule evaluation error");
    ruleResults.push({ ruleId: rule.id, passed: false, error: (err as Error).message });
  }
}

// Layer 3 — Unknown variable handling: meaningful error with context
class StrictEvaluationContext implements EvaluationContext {
  get(name: string): number | string | boolean {
    if (!this.variables.has(name)) {
      throw new RuleEvaluationError(
        `Rule references unknown variable: "${name}". ` +
        `Available variables: ${[...this.variables.keys()].join(", ")}`
      );
    }
    return this.variables.get(name)!;
  }
}
```

**Q19. How do you test an Interpreter implementation?**
A: Test three layers independently:

```ts
// Layer 1 — Individual expression types in isolation
describe("GreaterThanExpression", () => {
  it("returns true when left > right", () => {
    const expr = new GreaterThanExpression(new NumberLiteral(720), new NumberLiteral(650));
    expect(expr.interpret(emptyCtx)).toBe(true);
  });

  it("returns false when left == right", () => {
    const expr = new GreaterThanExpression(new NumberLiteral(650), new NumberLiteral(650));
    expect(expr.interpret(emptyCtx)).toBe(false);
  });
});

// Layer 2 — Composite expressions (AST correctness)
describe("AndExpression", () => {
  it("short-circuits on false left operand", () => {
    const rightSpy = jest.fn().mockReturnValue(true);
    const rightExpr = { interpret: rightSpy } as unknown as Expression;
    const expr = new AndExpression(new BooleanLiteral(false), rightExpr);

    expect(expr.interpret(emptyCtx)).toBe(false);
    expect(rightSpy).not.toHaveBeenCalled(); // short-circuit verified
  });
});

// Layer 3 — Parser round-trips (parse → evaluate)
describe("RuleParser", () => {
  const parser = new RuleParser();

  const cases = [
    { rule: "creditScore > 650", vars: { creditScore: 720 }, expected: true },
    { rule: "creditScore > 650", vars: { creditScore: 600 }, expected: false },
    { rule: "creditScore > 650 AND monthlyIncome > 15000",
      vars: { creditScore: 720, monthlyIncome: 20000 }, expected: true },
    { rule: "creditScore > 650 AND monthlyIncome > 15000",

    });
  });
```

**Q21. "How would you design the Interpreter to support multi-tenant rule sets, where different lenders on your platform have different eligibility criteria?"**
A:
```ts
// Tenant-scoped rule cache — partition by tenantId
class TenantAwareRuleCache {
  private cache = new Map<string, Map<string, Expression>>();
  // key: tenantId → Map<ruleExpression, parsedAST>

  getOrParse(tenantId: string, expression: string): Expression {
    if (!this.cache.has(tenantId)) {
      this.cache.set(tenantId, new Map());
    }
    const tenantCache = this.cache.get(tenantId)!;

    if (!tenantCache.has(expression)) {
      tenantCache.set(expression, this.parser.parse(expression));
    }
    return tenantCache.get(expression)!;
  }

  invalidateTenant(tenantId: string): void {
    this.cache.delete(tenantId);
  }
}

// Tenant-aware rule evaluator
@Injectable()
export class MultiTenantBRE {
  constructor(
    private readonly ruleRepo: TenantRuleRepository,
    private readonly cache: TenantAwareRuleCache,
  ) {}

  async evaluate(tenantId: string, applicant: ApplicantData): Promise<BREResult> {
    const rules = await this.ruleRepo.findActiveRules(tenantId);

    // Each tenant gets their own context variable set
    // (different tenants may use different variable names or scoring models)
    const ctx = this.buildContext(tenantId, applicant);

    const results = await Promise.all(rules.map(async (rule) => {
      try {
        const expr = this.cache.getOrParse(tenantId, rule.expression);
        return { ruleId: rule.id, passed: expr.interpret(ctx) as boolean };
      } catch (err) {
        return { ruleId: rule.id, passed: false, error: (err as Error).message };
      }
    }));

    return {
      tenantId,
      eligible: results.filter(r => r.passed).length === results.length,
      results,
    };
  }
}
```

**Q22. "Your NACH eligibility BRE needs to support a new 'LOOKUP' function that checks whether a PAN number appears in a government watchlist. How do you add this without modifying existing expression classes?"**
A: Extend the `FunctionCallExpression` registry with an async-capable lookup:

```ts
// Extend FunctionCallExpression to support async functions
class AsyncFunctionCallExpression implements Expression {
  // Async interpret — returns a Promise, must be awaited by the evaluator
  async interpretAsync(ctx: AsyncEvaluationContext): Promise<number | string | boolean> {
    const evaluatedArgs = await Promise.all(
      this.args.map(arg =>
        arg instanceof AsyncFunctionCallExpression
          ? arg.interpretAsync(ctx)
          : arg.interpret(ctx)
      )
    );
    return ctx.callAsyncFunction(this.name, evaluatedArgs);
  }

  // Sync interpret — throws for async functions
  interpret(_ctx: EvaluationContext): never {
    throw new Error(`Function "${this.name}" requires async evaluation — use interpretAsync()`);
  }

  constructor(
    private readonly name: string,
    private readonly args: Expression[],
  ) {}
}

// AsyncEvaluationContext — supports async function calls
class AsyncLoanEvaluationContext extends LoanEligibilityContext {
  constructor(
    data: ApplicantData,
    private readonly watchlistService: WatchlistService,
    private readonly accountAggregator: AccountAggregatorService,
  ) {
    super(data);
  }

  async callAsyncFunction(name: string, args: (number | string | boolean)[]): Promise<boolean> {
    switch (name) {
      case "LOOKUP_WATCHLIST": {
        const pan = args[0] as string;
        return this.watchlistService.isOnWatchlist(pan); // external API call
      }
      case "VERIFY_BANK_STATEMENT": {
        const accountId = args[0] as string;
        const months = args[1] as number;
        const result = await this.accountAggregator.fetchStatements(accountId, months);
        return result.averageBalance > 10_000;
      }
      default:
        throw new Error(`Unknown async function: "${name}"`);
    }
  }
}

// Rule: NOT LOOKUP_WATCHLIST(panNumber) AND creditScore > 650
// The LOOKUP_WATCHLIST call is transparent in the rule string
// No existing expression classes were modified
```

**Q23. "How would you explain the Interpreter pattern to a junior developer who asks why you don't just use `eval()` to evaluate rule strings?"**
A: Frame the answer around three concrete risks and one structural benefit:

**Risk 1 — Security (Code Injection):**
```ts
// eval() treats rule strings as executable JavaScript
const rule = `process.exit(1)`; // stored by a malicious admin
eval(rule); // crashes the Node.js process

// Or worse:
const rule = `require("child_process").execSync("rm -rf /")`;
eval(rule); // arbitrary OS command execution
```
The Interpreter pattern's AST class hierarchy is a security boundary — a user can only construct expressions the grammar allows. There is no path from `VariableExpression` or `AndExpression` to executing OS commands.

**Risk 2 — No validation:**
`eval()` fails at runtime, inside a request, with a JavaScript syntax error. The Interpreter pattern's parser validates at rule-save time — the admin panel rejects malformed rules before they ever reach production.

**Risk 3 — Performance:**
`eval()` in Node.js runs in the V8 interpreter without JIT optimization for dynamically evaluated strings. A well-implemented Interpreter can be optimized (constant folding, short-circuit evaluation, cached ASTs) in ways `eval()` cannot.

**Structural benefit — Visibility and tooling:**
Every operation on `eval()` output is a black box. An AST built from Interpreter classes can be visited (pretty-printed, serialized to JSON, converted to SQL, type-checked) using Visitors. You can build an admin panel that shows the rule's parsed structure, highlights which conditions failed for a given applicant, and explains the evaluation trace — none of which is possible with `eval()`.

**Q24. "Your rule engine needs to produce an explanation of why an applicant was rejected — which specific rules failed and what the actual values were. How do you implement this?"**
A: Add an explanation-collecting context that records evaluation details alongside results:

```ts
interface ExplainedResult {
  expression: string;
  result: boolean | number | string;
  children?: ExplainedResult[];
}

// Extend Expression with explain capability
interface ExplainableExpression extends Expression {
  explain(ctx: EvaluationContext): ExplainedResult;
}

class ExplainableGreaterThan implements ExplainableExpression {
  constructor(
    private readonly left: ExplainableExpression,
    private readonly right: ExplainableExpression,
  ) {}

  interpret(ctx: EvaluationContext): boolean {
    return (this.left.interpret(ctx) as number) > (this.right.interpret(ctx) as number);
  }

  explain(ctx: EvaluationContext): ExplainedResult {
    const leftResult = this.left.explain(ctx);
    const rightResult = this.right.explain(ctx);
    const result = (leftResult.result as number) > (rightResult.result as number);

    return {
      expression: `${leftResult.expression} > ${rightResult.expression}`,
      result,
      children: [leftResult, rightResult],
    };
  }
}

class ExplainableVariable implements ExplainableExpression {
  constructor(private readonly name: string) {}

  interpret(ctx: EvaluationContext): number | string | boolean {
    return ctx.get(this.name);
  }

  explain(ctx: EvaluationContext): ExplainedResult {
    const value = ctx.get(this.name);
    return {
      expression: `${this.name} (= ${value})`, // shows actual value
      result: value,
    };
  }
}

// Produces human-readable rejection explanation
const explanation = eligibilityRule.explain(ctx);
// {
//   expression: "(creditScore (= 580) > 650) AND (monthlyIncome (= 20000) > 15000)",
//   result: false,
//   children: [
//     { expression: "creditScore (= 580) > 650", result: false, ... },
//     { expression: "monthlyIncome (= 20000) > 15000", result: true, ... }
//   ]
// }
```
This explanation can be shown to loan officers in the admin panel, stored in the audit log for compliance, and surfaced to applicants as a rejection reason — all without changing any business logic.

**Q25. "How does the Interpreter pattern scale when you have hundreds of rules evaluated for thousands of applicants per minute in a NACH payment processing pipeline?"**
A: Raw Interpreter pattern has performance ceilings — AST traversal via virtual method dispatch is slower than direct evaluation. At scale, apply three optimizations:

**Optimization 1 — Parse once, evaluate many times (Q8):**
Rule strings → AST parsing happens at rule save time or on first use. Cache the AST per rule string. The cache is a `Map<ruleString, Expression>` — lookup is O(1). At 1000 rules, 1000 cached ASTs, zero re-parsing overhead per applicant.

**Optimization 2 — Compile AST to a function at parse time:**
```ts
class CompilingRuleParser {
  parseToFunction(rule: string): (ctx: EvaluationContext) => boolean {
    const ast = this.parse(rule);
    // Compile the AST to a JavaScript closure — avoids virtual dispatch at eval time
    return this.compile(ast);
  }

  private compile(node: Expression): (ctx: EvaluationContext) => boolean {
    if (node instanceof AndExpression) {
      const left = this.compile(node.left);
      const right = this.compile(node.right);
      return (ctx) => left(ctx) && right(ctx); // direct function call — no virtual dispatch
    }
    if (node instanceof GreaterThanExpression) {
      const left = this.compile(node.left);
      const right = this.compile(node.right);
      return (ctx) => (left(ctx) as number) > (right(ctx) as number);
    }
    if (node instanceof VariableExpression) {
      const name = node.name;
      return (ctx) => ctx.get(name) as boolean;
    }
    // ... other types
    return (ctx) => node.interpret(ctx) as boolean;
  }
}
// Result: a plain JS function — V8 can JIT-compile and inline it
// Evaluation is 10–100x faster than virtual dispatch on the AST
```

**Optimization 3 — Parallel evaluation with worker threads:**
```ts
// For CPU-bound rule evaluation at high volume — use worker thread pool (Q15 from Object Pool guide)
const workerPool = createPool({ create: () => new Worker("./rule-evaluator.worker.js") }, { min: 2, max: os.cpus().length });

async function evaluateBatch(applicants: ApplicantData[], rules: CompiledRule[]): Promise<BREResult[]> {
  const worker = await workerPool.acquire();
  try {
    return await dispatchToWorker(worker, { applicants, rules });
  } finally {
    await workerPool.release(worker);
  }
}
```
At 5000 applicants/minute with 20 rules each (100,000 rule evaluations/minute), compiled functions + worker threads handle the load comfortably on a 4-core Node.js pod.
