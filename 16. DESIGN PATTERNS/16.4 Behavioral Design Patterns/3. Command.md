# Design Patterns (Behavioral): Command — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Command pattern?**
A: Command is a behavioral design pattern that turns a request or action into a standalone object — encapsulating everything needed to perform, delay, queue, log, or undo the action. Instead of a caller invoking a method on a receiver directly, it creates a `Command` object that knows what to do (the operation), who to do it to (the receiver), and what arguments are needed. The caller then triggers execution by calling a uniform `execute()` method on the command, without knowing anything about the receiver or the specific operation. The command object is a first-class value — it can be stored, serialized, queued, passed around, and executed at any point in time.

**Q2. What problem does Command solve? When does a direct method call break down?**
A: A direct method call couples the invoker tightly to the receiver — the caller must know the receiver's type, the method name, and the argument list. This breaks down when:
- **Delayed or scheduled execution** — you need to store "what to do" and execute it later (task queues, job schedulers, deferred operations).
- **Undo / redo** — you need to reverse an operation, which requires the operation to be representable as a reversible object, not a one-shot call.
- **Queueing and batching** — you need to collect operations and execute them as a group, possibly in a different thread or process.
- **Logging and auditing** — you need a persistent record of what operations were performed, in what order, with what arguments — an audit trail that survives a process restart.
- **Macro recording** — you need to record a sequence of user actions and replay them.
- **Transactional rollback** — a sequence of operations must be reversible as a unit if any step fails.

In all these cases, a method call is ephemeral — once it returns, the intent is gone. Command preserves the intent as a first-class object.

**Q3. What are the five participants in the Command pattern?**
A: The GoF define five:
1. **Command** — declares the interface for executing an operation, minimally `execute()`. Often also declares `undo()` for reversibility.
2. **ConcreteCommand** — implements `Command`; binds a specific `Receiver` to an action; stores any arguments needed to invoke the action; implements `execute()` by calling the appropriate method(s) on the receiver. Optionally stores pre-execution state for `undo()`.
3. **Receiver** — the object that actually performs the work when `execute()` is called. The receiver contains the real business logic; the command is the wiring.
4. **Invoker** — asks the command to carry out a request by calling `execute()`. Knows nothing about the `ConcreteCommand` or the `Receiver`. May maintain a command history for undo/redo.
5. **Client** — creates a `ConcreteCommand` and sets its `Receiver`. Wires everything together at the composition root.

**Q4. What is the minimal Command interface, and what extensions are commonly added?**
A: The minimal interface is a single method:

```typescript
interface Command {
  execute(): void;
}
```

Common extensions depending on the use case:

```typescript
interface Command {
  execute(): Promise<void> | void;   // async for I/O-bound commands
  undo(): Promise<void> | void;      // for undo/redo stacks
  redo(): Promise<void> | void;      // sometimes distinct from execute() after undo
  canExecute(): boolean;             // guard — allows invoker to check before calling
  canUndo(): boolean;                // guard for undo stack
  serialize(): string;               // for persistence / audit log
  readonly id: string;               // for tracking and idempotency
  readonly createdAt: Date;          // for ordering and TTL
}
```

Add only what the use case demands — every method added to the interface must be implemented by every `ConcreteCommand`, so an over-specified interface increases maintenance burden.

**Q5. How does Command relate to other behavioral patterns?**
A: Command is frequently confused with or combined with several:
- **Strategy** — both encapsulate behaviour in an object. Strategy varies the *algorithm* used in a single step; Command encapsulates an entire *request* — including its receiver, arguments, and optionally its inverse. Strategy objects are stateless algorithms; Command objects carry state (arguments, receiver reference, pre-execution snapshot for undo).
- **Chain of Responsibility** — commands can be passed along a chain of handlers. CoR decides *who* handles; Command decides *what* is done. A pipeline of middleware is CoR; each action a middleware performs can be a Command.
- **Memento** — used with Command for undo. The Memento captures the receiver's state *before* `execute()` is called; `undo()` restores from the Memento. Command decides *what* to undo; Memento stores the *state* to restore.
- **Observer** — commands can be queued and dispatched to observers. An event bus often wraps domain events as Commands dispatched to subscribers.
- **Composite** — a `MacroCommand` (composite of commands) lets multiple commands be executed as one, with a single `execute()` / `undo()` call triggering each child in sequence or reverse.

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript implementation of the Command pattern with undo support.**
A:

```typescript
// ─── Command interface ────────────────────────────────────────────────────────

interface Command {
  execute(): void;
  undo(): void;
}

// ─── Receiver — the object that does the real work ───────────────────────────

class BankAccount {
  private balance: number;

  constructor(initialBalance: number) {
    this.balance = initialBalance;
  }

  deposit(amount: number): void {
    this.balance += amount;
    console.log(`Deposited ₹${amount / 100}. Balance: ₹${this.balance / 100}`);
  }

  withdraw(amount: number): void {
    if (amount > this.balance) throw new Error("Insufficient funds");
    this.balance -= amount;
    console.log(`Withdrew ₹${amount / 100}. Balance: ₹${this.balance / 100}`);
  }

  get currentBalance(): number { return this.balance; }
}

// ─── Concrete Commands ────────────────────────────────────────────────────────

class DepositCommand implements Command {
  constructor(
    private readonly account:      BankAccount,
    private readonly amountInPaise: number,
  ) {}

  execute(): void {
    this.account.deposit(this.amountInPaise);
  }

  undo(): void {
    // Deposit undo = withdraw the same amount
    this.account.withdraw(this.amountInPaise);
  }
}

class WithdrawCommand implements Command {
  private executedSuccessfully = false;

  constructor(
    private readonly account:       BankAccount,
    private readonly amountInPaise: number,
  ) {}

  execute(): void {
    this.account.withdraw(this.amountInPaise);
    this.executedSuccessfully = true;
  }

  undo(): void {
    if (!this.executedSuccessfully) return;  // nothing to undo if execute failed
    this.account.deposit(this.amountInPaise);
  }
}

// ─── Invoker — maintains history, knows nothing about BankAccount ─────────────

class TransactionManager {
  private history: Command[] = [];
  private undoStack: Command[] = [];

  execute(command: Command): void {
    command.execute();
    this.history.push(command);
    this.undoStack = [];   // branching: clear redo stack on new action
  }

  undo(): void {
    const command = this.history.pop();
    if (!command) { console.log("Nothing to undo"); return; }
    command.undo();
    this.undoStack.push(command);
  }

  redo(): void {
    const command = this.undoStack.pop();
    if (!command) { console.log("Nothing to redo"); return; }
    command.execute();
    this.history.push(command);
  }
}

// ─── Client ───────────────────────────────────────────────────────────────────

const account = new BankAccount(100000);   // ₹1000 initial balance
const manager = new TransactionManager();

manager.execute(new DepositCommand(account, 50000));   // +₹500
manager.execute(new WithdrawCommand(account, 20000));  // -₹200
manager.undo();                                        // reverses the ₹200 withdrawal
manager.undo();                                        // reverses the ₹500 deposit
manager.redo();                                        // re-applies the ₹500 deposit
```

The `TransactionManager` (invoker) is entirely decoupled from `BankAccount` (receiver). Adding new operations (a `TransferCommand`, an `InterestCommand`) requires no changes to `TransactionManager`.

**Q7. How do you implement a MacroCommand (Composite Command) that executes and undoes a sequence atomically?**
A:

```typescript
class MacroCommand implements Command {
  private executed: Command[] = [];

  constructor(private readonly commands: Command[]) {}

  execute(): void {
    this.executed = [];
    for (const command of this.commands) {
      try {
        command.execute();
        this.executed.push(command);
      } catch (err) {
        // Partial execution — roll back everything that succeeded
        console.error("MacroCommand failed mid-sequence, rolling back...");
        this.rollback();
        throw err;
      }
    }
  }

  undo(): void {
    this.rollback();
  }

  private rollback(): void {
    // Undo in reverse order of execution
    for (const command of [...this.executed].reverse()) {
      try {
        command.undo();
      } catch (err) {
        console.error(`Rollback failed for a command: ${err}`);
        // Continue rolling back remaining commands despite individual failure
      }
    }
    this.executed = [];
  }
}

// Usage: a fund transfer as an atomic macro
const transfer = new MacroCommand([
  new WithdrawCommand(sourceAccount, 100000),   // ₹1000 from source
  new DepositCommand(targetAccount, 100000),    // ₹1000 to target
]);

manager.execute(transfer);
manager.undo();   // reverses both atomically: re-deposits to source, re-withdraws from target
```

**Q8. How do you make a Command serializable for persistence and audit logging?**
A: Commands must carry enough data to be reconstructed from a serialized form. The key is that commands are value objects from a serialization perspective — all state needed to re-execute or display the action must be self-contained:

```typescript
interface SerializableCommand extends Command {
  readonly commandId:  string;
  readonly commandType: string;
  readonly createdAt:  Date;
  readonly actorId:    string;   // who initiated
  toJSON(): CommandRecord;
}

interface CommandRecord {
  commandId:    string;
  commandType:  string;
  createdAt:    string;   // ISO 8601
  actorId:      string;
  payload:      Record<string, unknown>;
}

class TransferCommand implements SerializableCommand {
  readonly commandId:   string;
  readonly commandType  = "TransferCommand";
  readonly createdAt:   Date;

  constructor(
    private readonly ledger:            LedgerService,
    private readonly fromAccountId:     string,
    private readonly toAccountId:       string,
    private readonly amountInPaise:     number,
    readonly actorId:                   string,
    commandId?: string,
  ) {
    this.commandId = commandId ?? crypto.randomUUID();
    this.createdAt = new Date();
  }

  execute(): void {
    this.ledger.transfer(this.fromAccountId, this.toAccountId, this.amountInPaise);
  }

  undo(): void {
    this.ledger.transfer(this.toAccountId, this.fromAccountId, this.amountInPaise);
  }

  toJSON(): CommandRecord {
    return {
      commandId:   this.commandId,
      commandType: this.commandType,
      createdAt:   this.createdAt.toISOString(),
      actorId:     this.actorId,
      payload: {
        fromAccountId:  this.fromAccountId,
        toAccountId:    this.toAccountId,
        amountInPaise:  this.amountInPaise,
      },
    };
  }
}

// Factory to reconstruct from persisted record
class CommandFactory {
  static fromRecord(record: CommandRecord, services: ServiceLocator): SerializableCommand {
    switch (record.commandType) {
      case "TransferCommand":
        return new TransferCommand(
          services.ledger,
          record.payload.fromAccountId as string,
          record.payload.toAccountId  as string,
          record.payload.amountInPaise as number,
          record.actorId,
          record.commandId,
        );
      default:
        throw new Error(`Unknown command type: ${record.commandType}`);
    }
  }
}
```

**Q9. How does the Command pattern support idempotency, and why does it matter in distributed fintech systems?**
A: Idempotency means executing the same command multiple times has the same effect as executing it once — critical when network retries, duplicate webhook deliveries, or at-least-once message queue semantics can cause a command to be received more than once. Command IDs enable idempotency:

```typescript
class IdempotentCommandInvoker {
  private executedIds = new Set<string>();   // in-memory; use Redis in production

  async execute(command: SerializableCommand): Promise<void> {
    if (this.executedIds.has(command.commandId)) {
      console.log(`[idempotent] Command ${command.commandId} already executed — skipping`);
      return;
    }

    await command.execute();
    this.executedIds.add(command.commandId);
    await this.persistToAuditLog(command);
  }

  private async persistToAuditLog(command: SerializableCommand): Promise<void> {
    await auditLogStore.insert(command.toJSON());
  }
}
```

In production, `executedIds` should be backed by Redis with a TTL matching the idempotency window (e.g., 24 hours for payment commands). The `commandId` should be deterministically derived from the business intent (e.g., a hash of `orderId + amount + timestamp`) rather than randomly generated, so that client-side retries produce the same ID and are naturally deduplicated.

**Q10. How do async commands work, and what are the failure handling considerations?**
A:

```typescript
interface AsyncCommand {
  execute(): Promise<void>;
  undo(): Promise<void>;
  canUndo(): boolean;
}

class AsyncPaymentCommand implements AsyncCommand {
  private transactionId: string | null = null;

  constructor(
    private readonly gateway:        PaymentGatewayDriver,
    private readonly orderId:        string,
    private readonly amountInPaise:  number,
  ) {}

  async execute(): Promise<void> {
    const result = await this.gateway.initiateTransaction({
      orderId: this.orderId, amountInPaise: this.amountInPaise, currency: "INR",
    });
    this.transactionId = result.transactionId;
    // Store transactionId — needed for undo (refund)
  }

  canUndo(): boolean { return this.transactionId !== null; }

  async undo(): Promise<void> {
    if (!this.transactionId) throw new Error("Cannot undo: command was never executed");
    await this.gateway.initiateRefund(this.transactionId, this.amountInPaise);
    this.transactionId = null;
  }
}

// Async invoker: handles partial failures in async macro commands
class AsyncTransactionManager {
  private history: AsyncCommand[] = [];

  async execute(command: AsyncCommand): Promise<void> {
    await command.execute();
    this.history.push(command);
  }

  async undoLast(): Promise<void> {
    const command = this.history.pop();
    if (!command) return;
    if (!command.canUndo()) {
      console.warn("Last command is not undoable");
      return;
    }
    await command.undo();
  }
}
```

Key failure handling considerations:
- **Network failures during `execute()`** — the command may have partially applied. Store enough state (e.g., `transactionId`) before the failure point to attempt cleanup.
- **Network failures during `undo()`** — undo itself can fail. Compensating actions should be retried with exponential backoff; irrecoverable failures must be escalated to a human review queue.
- **Non-undoable commands** — some operations (email sent, SMS delivered) have no meaningful inverse. Model these as fire-and-forget commands without `undo()`, and ensure `canUndo()` returns `false`.

## Section 3: Command in Node.js / TypeScript / Fintech Context

**Q11. Show a Command-based job queue implementation for asynchronous payment processing in NestJS.**
A:

```typescript
// ─── Command interface ────────────────────────────────────────────────────────

interface PaymentCommand {
  readonly commandId:   string;
  readonly commandType: string;
  execute(): Promise<PaymentCommandResult>;
  toJobPayload(): Record<string, unknown>;
}

interface PaymentCommandResult {
  success:       boolean;
  transactionId?: string;
  errorCode?:    string;
  message:       string;
}

// ─── Concrete Command ─────────────────────────────────────────────────────────

class UpiPaymentCommand implements PaymentCommand {
  readonly commandId:   string;
  readonly commandType = "UpiPaymentCommand";

  constructor(
    private readonly gateway:        PaymentGatewayDriver,
    private readonly orderId:        string,
    private readonly amountInPaise:  number,
    private readonly vpa:            string,
    private readonly customerId:     string,
    commandId?: string,
  ) {
    this.commandId = commandId ?? crypto.randomUUID();
  }

  async execute(): Promise<PaymentCommandResult> {
    try {
      const result = await this.gateway.initiateTransaction({
        orderId: this.orderId, amountInPaise: this.amountInPaise,
        currency: "INR", method: "upi", vpa: this.vpa,
      });
      return { success: true, transactionId: result.transactionId, message: "Payment initiated" };
    } catch (err: any) {
      return { success: false, errorCode: err.code ?? "UNKNOWN", message: err.message };
    }
  }

  toJobPayload(): Record<string, unknown> {
    return {
      commandId: this.commandId, commandType: this.commandType,
      orderId: this.orderId, amountInPaise: this.amountInPaise,
      vpa: this.vpa, customerId: this.customerId,
    };
  }
}

// ─── NestJS BullMQ queue — Invoker ───────────────────────────────────────────

@Injectable()
class PaymentCommandQueue {
  constructor(
    @InjectQueue("payment-commands") private readonly queue: Queue,
    private readonly commandFactory: PaymentCommandFactory,
  ) {}

  async enqueue(command: PaymentCommand, opts?: JobsOptions): Promise<void> {
    await this.queue.add(
      command.commandType,
      command.toJobPayload(),
      {
        jobId:    command.commandId,    // idempotency — BullMQ deduplicates by jobId
        attempts: 3,
        backoff:  { type: "exponential", delay: 2000 },
        ...opts,
      },
    );
  }
}

// ─── BullMQ Worker — executes commands from the queue ────────────────────────

@Processor("payment-commands")
class PaymentCommandProcessor {
  constructor(private readonly commandFactory: PaymentCommandFactory) {}

  @Process()
  async process(job: Job<Record<string, unknown>>): Promise<PaymentCommandResult> {
    const command = this.commandFactory.fromJobPayload(job.data);
    const result  = await command.execute();

    if (!result.success) {
      // Non-retryable errors: don't throw — mark as failed without retry
      if (["INVALID_VPA", "ACCOUNT_BLOCKED"].includes(result.errorCode ?? "")) {
        await job.discard();
        return result;
      }
      throw new Error(result.message);   // retryable — BullMQ will retry
    }

    return result;
  }
}
```

**Q12. How does Command implement an event sourcing pattern for a loan origination system?**
A: In event sourcing, every state change is stored as an immutable command (event). The current state is derived by replaying the command history from the beginning (or from a snapshot). Commands are the source of truth:

```typescript
// ─── Commands as domain events ────────────────────────────────────────────────

type LoanCommandType =
  | "LoanApplicationSubmitted"
  | "CreditBureauCheckPassed"
  | "LoanApproved"
  | "LoanDisbursed"
  | "EmiRepaid"
  | "LoanPreclosed";

interface LoanCommand {
  readonly commandId:   string;
  readonly commandType: LoanCommandType;
  readonly loanId:      string;
  readonly actorId:     string;
  readonly timestamp:   Date;
  readonly payload:     Record<string, unknown>;
  apply(state: LoanState): LoanState;   // pure function — no side effects
}

// ─── Concrete Commands ────────────────────────────────────────────────────────

class LoanApprovedCommand implements LoanCommand {
  readonly commandType = "LoanApproved" as const;

  constructor(
    readonly commandId:          string,
    readonly loanId:             string,
    readonly actorId:            string,
    readonly timestamp:          Date,
    readonly payload: {
      sanctionedAmountInPaise:  number;
      annualInterestRate:       number;
      tenureMonths:             number;
      approvedBy:               string;
    },
  ) {}

  apply(state: LoanState): LoanState {
    return {
      ...state,
      status:                  "APPROVED",
      sanctionedAmountInPaise: this.payload.sanctionedAmountInPaise,
      annualInterestRate:      this.payload.annualInterestRate,
      tenureMonths:            this.payload.tenureMonths,
      approvedAt:              this.timestamp,
    };
  }
}

class EmiRepaidCommand implements LoanCommand {
  readonly commandType = "EmiRepaid" as const;

  constructor(
    readonly commandId:  string,
    readonly loanId:     string,
    readonly actorId:    string,
    readonly timestamp:  Date,
    readonly payload: {
      amountInPaise:     number;
      emiNumber:         number;
      outstandingAfter:  number;
    },
  ) {}

  apply(state: LoanState): LoanState {
    return {
      ...state,
      outstandingPrincipalInPaise: this.payload.outstandingAfter,
      lastEmiPaidAt:               this.timestamp,
      emisPaid:                    (state.emisPaid ?? 0) + 1,
    };
  }
}

// ─── Event Store + Projection ─────────────────────────────────────────────────

class LoanEventStore {
  // Commands persisted in append-only fashion
  private events = new Map<string, LoanCommand[]>();

  async append(command: LoanCommand): Promise<void> {
    const existing = this.events.get(command.loanId) ?? [];
    this.events.set(command.loanId, [...existing, command]);
    // In production: INSERT INTO loan_events (command_id, loan_id, type, payload, timestamp)
  }

  async replay(loanId: string): Promise<LoanState> {
    const commands = this.events.get(loanId) ?? [];
    return commands.reduce(
      (state, command) => command.apply(state),
      initialLoanState(loanId),
    );
  }

  async replayUpTo(loanId: string, commandId: string): Promise<LoanState> {
    const commands = this.events.get(loanId) ?? [];
    const slice    = commands.slice(0, commands.findIndex(c => c.commandId === commandId) + 1);
    return slice.reduce((state, command) => command.apply(state), initialLoanState(loanId));
  }
}
```

Every `LoanCommand` is immutable, stored permanently, and purely functional (`apply` is side-effect free). The current loan state is always derivable from the command log — full audit trail and time-travel debugging come for free.

**Q13. How does the Command pattern structure a bulk payment disbursement system with rollback?**
A:

```typescript
// ─── Domain ───────────────────────────────────────────────────────────────────

class DisbursementCommand implements AsyncCommand {
  private disbursementId: string | null = null;

  constructor(
    private readonly loanService:     LoanService,
    private readonly accountId:       string,
    private readonly amountInPaise:   number,
    private readonly loanId:          string,
    readonly commandId = crypto.randomUUID(),
  ) {}

  async execute(): Promise<void> {
    const result = await this.loanService.disburse(this.loanId, this.accountId, this.amountInPaise);
    this.disbursementId = result.disbursementId;
  }

  canUndo(): boolean { return this.disbursementId !== null; }

  async undo(): Promise<void> {
    if (!this.disbursementId) throw new Error("Cannot undo — never executed");
    await this.loanService.reverseDisbursement(this.disbursementId);
    this.disbursementId = null;
  }
}

// ─── Bulk Macro Command with partial-rollback ─────────────────────────────────

class BulkDisbursementCommand {
  private succeeded: DisbursementCommand[] = [];

  constructor(
    private readonly disbursements: DisbursementCommand[],
    private readonly alertService:  AlertService,
  ) {}

  async execute(): Promise<BulkDisbursementResult> {
    this.succeeded = [];
    const failed: { commandId: string; error: string }[] = [];

    for (const cmd of this.disbursements) {
      try {
        await cmd.execute();
        this.succeeded.push(cmd);
      } catch (err: any) {
        failed.push({ commandId: cmd.commandId, error: err.message });
      }
    }

    if (failed.length > 0) {
      await this.alertService.notify(
        `Bulk disbursement: ${failed.length} of ${this.disbursements.length} failed`,
      );
    }

    return {
      totalCommands:    this.disbursements.length,
      successCount:     this.succeeded.length,
      failureCount:     failed.length,
      failures:         failed,
    };
  }

  async rollbackSucceeded(): Promise<void> {
    // Reverse only the ones that succeeded — don't attempt to undo failures
    for (const cmd of [...this.succeeded].reverse()) {
      try {
        await cmd.undo();
      } catch (err) {
        console.error(`Rollback failed for ${cmd.commandId}:`, err);
        // Alert ops team — manual intervention required
        await this.alertService.escalate(cmd.commandId, "Rollback failed");
      }
    }
    this.succeeded = [];
  }
}
```

**Q14. How do you implement a Command-based undo/redo stack for a financial configuration editor (e.g., editing loan product rules in a backoffice tool)?**

```typescript
// ─── Commands for config edits ────────────────────────────────────────────────

class UpdateInterestRateCommand implements Command {

  constructor(
    private readonly productConfig:    LoanProductConfig,

// ─── Bounded undo/redo stack — Invoker ───────────────────────────────────────

class ConfigEditorHistory {
  private undoStack: Command[] = [];
  private redoStack: Command[] = [];
  private readonly maxHistory:   number;

  constructor(maxHistory = 50) {
    this.maxHistory = maxHistory;
  }

  execute(command: Command): void {
    command.execute();
    this.undoStack.push(command);
    if (this.undoStack.length > this.maxHistory) {
      this.undoStack.shift();   // evict oldest when at capacity
    }
    this.redoStack = [];        // clear redo on new action
  }

  undo(): void {
    const command = this.undoStack.pop();
    if (!command) throw new Error("Nothing to undo");
    command.undo();
    this.redoStack.push(command);
  }

  redo(): void {
    const command = this.redoStack.pop();
    if (!command) throw new Error("Nothing to redo");
    command.execute();
    this.undoStack.push(command);
  }

  get canUndo(): boolean { return this.undoStack.length > 0; }
  get canRedo(): boolean { return this.redoStack.length > 0; }
  get historyDepth(): number { return this.undoStack.length; }
}
```

**Q15. How does Command integrate with CQRS (Command Query Responsibility Segregation)?**
A: CQRS is an architectural pattern that explicitly separates write operations (Commands — change state) from read operations (Queries — return state without side effects). The Command pattern provides the object model that makes the Command side of CQRS concrete:

```typescript
// ─── CQRS Command (write side) ────────────────────────────────────────────────

interface CqrsCommand {
  readonly commandId:   string;
  readonly commandType: string;
  readonly timestamp:   Date;
}

interface CqrsCommandHandler<T extends CqrsCommand> {
  handle(command: T): Promise<void>;
}

// Concrete command
class InitiateKycCommand implements CqrsCommand {
  readonly commandId   = crypto.randomUUID();
  readonly commandType = "InitiateKyc";
  readonly timestamp   = new Date();

  constructor(
    readonly customerId:      string,
    readonly panNumber:       string,
    readonly bureauConsent:   boolean,
  ) {}
}

// Command handler — the Receiver in Command pattern terms
@Injectable()
class InitiateKycCommandHandler implements CqrsCommandHandler<InitiateKycCommand> {
  constructor(
    private readonly kycService:    KycService,
    private readonly eventStore:    LoanEventStore,
    private readonly eventEmitter:  EventEmitter2,
  ) {}

  async handle(command: InitiateKycCommand): Promise<void> {
    // 1. Execute the domain operation
    const result = await this.kycService.initiate(command.customerId, command.panNumber);

    // 2. Persist to event store (if event-sourced)
    await this.eventStore.append({
      commandId:   command.commandId,
      commandType: "KycInitiated",
      loanId:      command.customerId,
      actorId:     "system",
      timestamp:   command.timestamp,
      payload:     { panNumber: command.panNumber, kycId: result.kycId },
      apply:       (state) => ({ ...state, kycStatus: "INITIATED", kycId: result.kycId }),
    });

    // 3. Emit domain event for read-side projections to update their view models
    this.eventEmitter.emit("kyc.initiated", { customerId: command.customerId, kycId: result.kycId });
  }
}

// ─── CQRS Query (read side — no Command pattern involvement) ─────────────────

interface CqrsQuery<TResult> {
  readonly queryId: string;
}

class GetLoanStatusQuery implements CqrsQuery<LoanStatusDto> {
  readonly queryId = crypto.randomUUID();
  constructor(readonly loanId: string) {}
}

@Injectable()
class GetLoanStatusQueryHandler {
  constructor(private readonly readDb: ReadModelDb) {}

  // Pure read — no state change, no Command involvement
  async handle(query: GetLoanStatusQuery): Promise<LoanStatusDto> {
    return this.readDb.loanStatusView.findByLoanId(query.loanId);
  }
}
```

In NestJS, `@nestjs/cqrs` provides `CommandBus` and `QueryBus` as the invokers, `@CommandHandler` as the decorator for receivers, and `@QueryHandler` for read-side handlers — a full CQRS infrastructure built on the Command pattern.

## Section 4: Pitfalls & Anti-patterns

**Q16. What is the "fat command" anti-pattern, and how do you avoid it?**
A: A fat command is one that contains not just the intent and parameters for an operation, but also business logic that belongs in the receiver (domain service or entity). It happens when the command starts making decisions:

```typescript
// ❌ Fat Command — contains business logic
class WithdrawCommand implements Command {
  execute(): void {
    // Business logic in the command — wrong layer
    if (this.account.balance < this.amount) {
      if (this.account.hasOverdraftFacility) {
        this.account.balance -= this.amount;
        this.account.overdraftUsed += this.amount;
        this.notificationService.sendOverdraftAlert(this.account.id);
      } else {
        throw new Error("Insufficient funds and no overdraft facility");
      }
    } else {
      this.account.balance -= this.amount;
    }
  }
}

// ✅ Thin Command — delegates all logic to the receiver
class WithdrawCommand implements Command {
  execute(): void {
    this.account.withdraw(this.amount);   // all business logic in BankAccount
  }

  undo(): void {
    this.account.deposit(this.amount);
  }
}
```

The rule: a Command should be a thin wiring layer — it knows *who* to call and *what* to call them with, not *how* the operation is performed. Business logic lives in the receiver (domain service, aggregate). A command that grows conditional logic is pulling responsibility away from where it belongs.

**Q17. What is the "command as data transfer object" confusion, and why does it matter?**
A: In CQRS, a "Command" is often used loosely to mean a DTO that carries request data from the API layer to the handler — a plain data bag with no `execute()` method:

```typescript
// CQRS "Command" as DTO — no execute(), not a GoF Command
class CreateLoanApplicationDto {
  customerId:        string;
  requestedAmount:   number;
  purpose:           string;
}

// GoF Command — has execute(), encapsulates receiver + action
class CreateLoanApplicationCommand implements Command {
  constructor(
    private readonly loanService: LoanService,
    private readonly dto: CreateLoanApplicationDto,
  ) {}

  execute(): void {
    this.loanService.createApplication(this.dto);
  }
}
```

The confusion matters when someone expects a CQRS Command DTO to support `undo()` or queuing, or when someone builds a GoF Command with no `execute()` and just uses it as a DTO. They're different things using the same name. At 5 YOE, being precise about which meaning is in use — and why the distinction matters for the current design — is what separates clear architecture thinking from cargo-culting.

**Q18. How does the Command pattern interact with database transactions, and what are the failure modes?**
A: Commands that span multiple database operations must be wrapped in a transaction to preserve atomicity. The failure modes are subtle:

```typescript
class TransferFundsCommand implements AsyncCommand {
  private snapshotBefore: TransferSnapshot | null = null;

  constructor(
    private readonly db:              DataSource,
    private readonly fromAccountId:   string,
    private readonly toAccountId:     string,
    private readonly amountInPaise:   number,
  ) {}

  async execute(): Promise<void> {
    await this.db.transaction(async (manager) => {
      // Snapshot before changes — for undo
      this.snapshotBefore = await this.captureSnapshot(manager);

      await manager.decrement(
        AccountEntity, { id: this.fromAccountId }, "balanceInPaise", this.amountInPaise,
      );
      await manager.increment(
        AccountEntity, { id: this.toAccountId }, "balanceInPaise", this.amountInPaise,
      );
      await manager.insert(JournalEntry, {
        fromAccountId: this.fromAccountId, toAccountId: this.toAccountId,
        amountInPaise: this.amountInPaise, timestamp: new Date(),
      });
    });
  }

  canUndo(): boolean { return this.snapshotBefore !== null; }

  async undo(): Promise<void> {
    if (!this.snapshotBefore) throw new Error("Nothing to undo");
    // Compensating transaction — reverse the transfer
    await this.db.transaction(async (manager) => {
      await manager.increment(
        AccountEntity, { id: this.fromAccountId }, "balanceInPaise", this.amountInPaise,
      );
      await manager.decrement(
        AccountEntity, { id: this.toAccountId }, "balanceInPaise", this.amountInPaise,
      );
      await manager.insert(JournalEntry, {
        fromAccountId: this.toAccountId, toAccountId: this.fromAccountId,
        amountInPaise: this.amountInPaise, timestamp: new Date(),
        isReversal: true,
      });
    });
    this.snapshotBefore = null;
  }

  private async captureSnapshot(manager: EntityManager): Promise<TransferSnapshot> {
    const [from, to] = await Promise.all([
      manager.findOne(AccountEntity, { where: { id: this.fromAccountId } }),
      manager.findOne(AccountEntity, { where: { id: this.toAccountId } }),
    ]);
    return { fromBalance: from!.balanceInPaise, toBalance: to!.balanceInPaise };
  }
}
```

**Failure modes to address:**
- **execute() succeeds, undo() fails** — the compensating transaction must be retried. If retries are exhausted, the discrepancy must be flagged for manual reconciliation. This is the "dual-write problem" in distributed systems.
- **Snapshot captured, execute() fails mid-transaction** — DB transaction rollback handles this automatically; the snapshot is stale and should be cleared.
- **undo() called concurrently from two places** — guard with `canUndo()` and nullify `snapshotBefore` atomically to prevent double-undo.

**Q19. Why is Command history (undo stack) a potential security and compliance risk in a fintech system?**
A: The undo stack holds live command objects in memory — each containing receiver references, operation arguments, and potentially pre-execution state snapshots. Risks:

- **Sensitive data in memory** — command payloads may include account numbers, PAN numbers, UPI VPAs, or transaction amounts. If the process is heap-dumped (for debugging or by an attacker), this data is exposed.
- **Unbounded stack growth** — without a cap, a long session of operations accumulates an unbounded list of command objects, each holding strong references to receivers (services, DB connections). This is both a memory leak and an implicit long-lived object graph.
- **Compliance misuse** — in regulated fintech, "undo a completed transaction" is almost always the wrong abstraction. Real-world financial systems use *compensating transactions* (a new debit/credit entry that reverses the original), not literal undo. Regulators require an immutable audit trail — every action, including reversals, must be recorded as new events, not erased.

Mitigations: cap the undo stack size; clear sensitive fields from commands after execution; in production financial systems, prefer compensating commands (which produce audit records) over true undo (which erases history).

**Q20. What is the "command explosion" anti-pattern and how do you manage it at scale?**
A: Command explosion occurs when every small variation in a use case gets its own concrete command class, producing hundreds of near-identical classes:

```typescript
// ❌ Explosion: one class per field update
class UpdateLoanInterestRateCommand implements Command { /* ... */ }
class UpdateLoanTenureCommand implements Command { /* ... */ }
class UpdateLoanProcessingFeeCommand implements Command { /* ... */ }
class UpdateLoanPrepaymentPenaltyCommand implements Command { /* ... */ }
class UpdateLoanMaxAmountCommand implements Command { /* ... */ }
// ... 40 more
```

Mitigations:

1. **Parameterised generic command** — for structurally identical operations that differ only in the field being updated:
```typescript
class UpdateLoanProductFieldCommand<K extends keyof LoanProductConfig> implements Command {
  private previousValue: LoanProductConfig[K] | null = null;

  constructor(
    private readonly store:       LoanProductStore,
    private readonly productCode: string,
    private readonly field:       K,
    private readonly newValue:    LoanProductConfig[K],
  ) {}

  execute(): void {
    this.previousValue = this.store.getField(this.productCode, this.field);
    this.store.updateField(this.productCode, this.field, this.newValue);
  }

  undo(): void {
    if (this.previousValue === null) throw new Error("Not yet executed");
    this.store.updateField(this.productCode, this.field, this.previousValue);
  }
}
```

2. **Command grouping** — combine logically related fields into one `UpdateLoanProductCommand` that carries a partial config object.
3. **DSL / builder** — a fluent builder that constructs the right command type from a high-level description, hiding the class proliferation from callers.

## Section 5: Scenario / System Design Style Questions

**Q21. "You're designing a backoffice tool for ops agents to manage customer loan accounts. Operations include freezing accounts, adjusting interest rates, waiving late fees, and forcing EMI schedules. All actions must be auditable and reversible. How do you structure this with Command?"**
A: The Command pattern is the natural fit — each operation becomes a command with `execute()`, `undo()`, and `toAuditRecord()`:

```typescript
// ─── Base class with audit record built-in ────────────────────────────────────

abstract class OpsCommand implements Command {
  readonly commandId: string = crypto.randomUUID();
  readonly executedAt: Date  = new Date();
  abstract readonly commandType: string;
  abstract readonly actorId:     string;
  abstract readonly resourceId:  string;   // the loanId / accountId being acted on

  abstract execute(): void;
  abstract undo(): void;

  toAuditRecord(): AuditRecord {
    return {
      commandId:    this.commandId,
      commandType:  this.commandType,
      actorId:      this.actorId,
      resourceId:   this.resourceId,
      executedAt:   this.executedAt.toISOString(),
      payload:      this.auditPayload(),
    };
  }

  protected abstract auditPayload(): Record<string, unknown>;
}

class FreezeLoanAccountCommand extends OpsCommand {
  readonly commandType = "FreezeLoanAccount";
  private wasAlreadyFrozen = false;

  constructor(
    private readonly loanService: LoanService,
    private readonly loanId:      string,
    readonly actorId:             string,
    private readonly reason:      string,
  ) { super(); }

  get resourceId(): string { return this.loanId; }

  execute(): void {
    this.wasAlreadyFrozen = this.loanService.isFrozen(this.loanId);
    if (!this.wasAlreadyFrozen) this.loanService.freeze(this.loanId, this.reason);
  }

  undo(): void {
    if (!this.wasAlreadyFrozen) this.loanService.unfreeze(this.loanId);
  }

  protected auditPayload(): Record<string, unknown> {
    return { loanId: this.loanId, reason: this.reason, wasAlreadyFrozen: this.wasAlreadyFrozen };
  }
}

// ─── OpsCommandInvoker persists audit log before returning ───────────────────

@Injectable()
class OpsCommandInvoker {
  private history: OpsCommand[] = [];

  constructor(private readonly auditLogService: AuditLogService) {}

  async execute(command: OpsCommand): Promise<void> {
    command.execute();
    this.history.push(command);
    await this.auditLogService.persist(command.toAuditRecord());
  }

  async undo(): Promise<void> {
    const command = this.history.pop();
    if (!command) throw new Error("Nothing to undo");
    command.undo();
    // Persist the reversal as a new audit record
    await this.auditLogService.persist({
      ...command.toAuditRecord(),
      commandId:   crypto.randomUUID(),
      commandType: `${command.commandType}Reversed`,
      executedAt:  new Date().toISOString(),
    });
  }
}
```

**Q22. "Your team receives a requirement to add a 'dry run' mode to all payment processing commands — execute the full validation logic but commit no changes. How do you implement this without modifying every command?"**
A: The clean solution is a `DryRunCommand` decorator that wraps any command, intercepts `execute()`, runs in a transaction that it always rolls back, and returns a report:

```typescript
class DryRunCommand implements AsyncCommand {
  private dryRunReport: DryRunReport | null = null;

  constructor(
    private readonly inner:  AsyncCommand,
    private readonly db:     DataSource,
  ) {}

  async execute(): Promise<void> {
    const errors:   string[] = [];
    const warnings: string[] = [];
    let   succeeded           = false;

    try {
      // Run inside a transaction — always roll back regardless of outcome
      await this.db.transaction(async () => {
        await this.inner.execute();
        succeeded = true;
        // Rollback: throw after capturing success — transaction never commits
        throw new DryRunRollbackSignal();
      });
    } catch (err) {
      if (err instanceof DryRunRollbackSignal) {
        // Expected — dry run completed without committing
      } else {
        errors.push((err as Error).message);
      }
    }

    this.dryRunReport = { wouldSucceed: succeeded, errors, warnings };
  }

  canUndo(): boolean { return false; }   // dry run has no state to undo
  async undo(): Promise<void> {}

  get report(): DryRunReport | null { return this.dryRunReport; }
}

class DryRunRollbackSignal extends Error {}

// Usage — no change to the wrapped command
const payment     = new UpiPaymentCommand(gateway, "ord_1", 50000, "user@upi", "cust_1");
const dryRun      = new DryRunCommand(payment, dataSource);
await dryRun.execute();
console.log(dryRun.report); // { wouldSucceed: true, errors: [], warnings: [] }
```

Zero modification to `UpiPaymentCommand` — the decorator intercepts at the invoker level.

**Q23. "A production incident: a batch EMI deduction job processed 10,000 accounts, but a bug caused 500 accounts to be double-debited. How does a Command-based architecture help you recover?"**
A: A Command-based audit log makes this recoverable systematically rather than through ad-hoc SQL patches:

**Recovery steps:**

1. **Query the command log** — filter `commandType = "EmiDeductionCommand"` and `batchId = <affected_batch>` where the same `accountId` appears more than once.

```typescript
const duplicates = await commandLogRepo.findDuplicatesByBatch(affectedBatchId);
// Returns: [{ accountId: "acc_1", commandIds: ["cmd_a", "cmd_b"] }, ...]
```

2. **Reconstruct commands from the log** — the command log stores enough payload to recreate each command object.

```typescript
const undoCommands = duplicates.map(({ commandIds }) => {
  // The second (duplicate) command is the one to undo
  const duplicateRecord = commandLogRepo.findById(commandIds[1]);
  return CommandFactory.fromRecord(duplicateRecord, services);
});
```

3. **Execute compensating commands** — each duplicate deduction is reversed by a `EmiDeductionReversalCommand` which credits the account and creates a new audit record (not erasing the original — the original deduction record stays in the log for regulatory traceability).

```typescript
const bulkReversal = new BulkDisbursementCommand(
  undoCommands.map(cmd => new EmiDeductionReversalCommand(cmd.accountId, cmd.amountInPaise)),
  alertService,
);
await bulkReversal.execute();
```

4. **Cross-check** — replay the command log for the affected accounts to verify current balances match expected balances.

Without a Command log, recovery would require manual reconciliation across the transactions table, the EMI schedule table, and potentially customer-reported discrepancies — error-prone and slow. With a Command log, the audit trail is the recovery mechanism.

**Q24. "You need to implement a scheduled payment system where customers can set up future-dated transfers. Transfers must execute exactly once, survive process restarts, and support cancellation. How do you design this?"**
A: Commands as durable, scheduled jobs — each scheduled transfer is a serialized command stored persistently:

```typescript
// ─── Scheduled Command entity — persisted ─────────────────────────────────────

interface ScheduledCommand {
  commandId:      string;
  commandType:    string;
  payload:        Record<string, unknown>;
  scheduledFor:   Date;
  status:         "PENDING" | "EXECUTING" | "EXECUTED" | "CANCELLED" | "FAILED";
  attempts:       number;
  lastAttemptAt:  Date | null;
  errorMessage:   string | null;
}

// ─── Scheduler service — Invoker for scheduled commands ──────────────────────

@Injectable()
class ScheduledCommandService {
  constructor(
    private readonly commandRepo:    ScheduledCommandRepository,
    private readonly commandFactory: CommandFactory,
    private readonly db:             DataSource,
  ) {}

  async schedule(command: SerializableCommand, scheduledFor: Date): Promise<string> {
    await this.commandRepo.insert({
      commandId:    command.commandId,
      commandType:  command.commandType,
      payload:      command.toJSON().payload,
      scheduledFor,
      status:       "PENDING",
      attempts:     0,
      lastAttemptAt: null,
      errorMessage: null,
    });
    return command.commandId;
  }

  async cancel(commandId: string, requestorId: string): Promise<void> {
    const cmd = await this.commandRepo.findById(commandId);
    if (!cmd) throw new NotFoundException(commandId);
    if (cmd.status !== "PENDING") throw new Error(`Cannot cancel — status is ${cmd.status}`);
    await this.commandRepo.updateStatus(commandId, "CANCELLED");
    await this.auditLog.record({ action: "ScheduledCommandCancelled", commandId, actorId: requestorId });
  }

  // Run by a cron / BullMQ repeatable job every minute
  @Cron("* * * * *")
  async processDue(): Promise<void> {
    const dueCommands = await this.commandRepo.findDue(new Date());

    for (const scheduled of dueCommands) {
      // Optimistic lock: set status to EXECUTING before processing — prevents double-execution
      const claimed = await this.commandRepo.claimForExecution(scheduled.commandId);
      if (!claimed) continue;   // another instance already claimed it

      try {
        const command = this.commandFactory.fromRecord({
          commandId:   scheduled.commandId,
          commandType: scheduled.commandType,
          payload:     scheduled.payload,
          actorId:     "scheduler",
          createdAt:   scheduled.scheduledFor.toISOString(),
        });

        await command.execute();
        await this.commandRepo.updateStatus(scheduled.commandId, "EXECUTED");
      } catch (err: any) {
        await this.commandRepo.recordFailure(
          scheduled.commandId, err.message, scheduled.attempts + 1,
        );
        if (scheduled.attempts + 1 >= 3) {
          await this.alertService.escalate(scheduled.commandId, "Scheduled command max retries exceeded");
        }
      }
    }
  }
}
```

Key guarantees:
- **Exactly-once** — optimistic lock (`claimForExecution`) prevents two instances from executing the same command simultaneously.
- **Survives restarts** — commands are in the database; on restart, `processDue` picks up any `PENDING` or stuck `EXECUTING` commands.
- **Cancellable** — `PENDING` commands can be cancelled by setting status; the cron skips non-PENDING records.
- **Audit trail** — every status transition is recorded; failures are preserved with error messages.

**Q25. "How would you explain the Command pattern to a junior engineer who is asking why you're wrapping every database operation in a command object instead of just calling the service method directly?"**
A: A practical, concrete explanation:

> "Direct service method calls work fine for simple CRUD — but imagine we're building the backoffice tool where an ops agent can freeze a loan account. Three problems immediately come up.
>
> First, the ops manager wants to see a log of every action: who froze account X, at what time, and why. If we call `loanService.freeze(accountId)` directly, that information is gone the moment the call returns. The Command wraps the call along with who did it, when, and with what arguments — and we can persist that wrapper to an audit table before we even execute anything.
>
> Second, the agent makes a mistake — they freeze the wrong account. With a direct call, 'undo' means writing a new piece of code to reverse whatever `freeze()` did, probably a year later when no one remembers the details. With Command, `undo()` is defined right next to `execute()`, implemented by the person who knew the operation's semantics when they wrote it.
>
> Third, next month a requirement comes in: some freeze operations need to be scheduled for a future date, and some need to be queued up for bulk processing overnight. A direct method call executes immediately and is gone. A Command object is a value — we can serialize it to a queue, store it in the DB with a `scheduledFor` timestamp, and execute it later with the exact same code path as the immediate case.
>
> So the wrapper isn't ceremony — it's the thing that makes operations a first-class concept instead of fire-and-forget calls."
