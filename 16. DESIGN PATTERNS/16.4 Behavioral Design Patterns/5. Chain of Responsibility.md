# Behavioral Design Patterns: Chain of Responsibility — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Chain of Responsibility pattern?**
A: Chain of Responsibility (CoR) is a behavioral design pattern that passes a request along a **chain of handlers**, where each handler decides either to process the request, pass it to the next handler, or do both. The sender doesn't know which handler will ultimately handle the request — it just fires it into the chain. The chain is assembled independently of the sender, so handlers can be added, removed, or reordered without touching the sender or other handlers.

The three defining characteristics:
- **Decoupled sender and receiver** — the sender holds only a reference to the first handler, not to any specific handler that "owns" the request.
- **Each handler decides** — process-and-stop, process-and-pass, or pass-without-processing. Not all handlers need to act on every request.
- **Chain is composable** — handlers are linked at runtime, not hardcoded in the sender.

**Q2. What problem does Chain of Responsibility solve?**
A: CoR solves three related problems:

- **Sequential conditional processing** — when a request must pass through a series of checks or transformations in order, and each step can independently decide to halt or continue, embedding all that logic in one place creates a monolith that violates SRP and OCP.
- **Dynamic pipeline construction** — when the set of processing steps varies by environment, configuration, or request type, CoR allows assembling the right pipeline at runtime.
- **Decoupling who sends from who handles** — the sender shouldn't need to know which step in a pipeline is responsible for a given aspect of processing.

A classic non-CoR smell: a service method with sequential `if (!validate()) return; if (!checkFraud()) return; if (!checkLimit()) return; if (!approve()) return;` — each check coupled to the same method body. CoR extracts each check into its own handler class.

**Q3. How does Chain of Responsibility differ from Strategy, Decorator, and Middleware?**
A:

| Pattern                    | Intent                                                | Handlers see the request? | Can stop the chain? | Who assembles?       |
|----------------------------|-------------------------------------------------------|---------------------------|---------------------|----------------------|
| **CoR**                    | Pass request through handlers; each may handle/pass  | Yes — in sequence         | Yes                 | External / framework |
| **Strategy**               | Select one algorithm from a family                   | Only the chosen one       | N/A — one runs      | Factory / DI         |
| **Decorator**              | Add behaviour to every call transparently             | All — always delegates    | No (normally)       | Composition root     |
| **Middleware (e.g. Express)** | Request/response pipeline; early exit allowed     | Yes — in sequence         | Yes                 | Framework            |

Key distinctions:
- **CoR vs Decorator** — both chain objects, but Decorator always delegates to the next (additive, transparent); CoR handlers may stop the chain (selective, conditional).
- **CoR vs Strategy** — Strategy picks *one* algorithm; CoR passes through *many* handlers, each potentially acting.
- **CoR vs Middleware** — middleware IS the web-framework implementation of CoR. NestJS guards, interceptors, pipes, and middleware are all CoR participants.

**Q4. What are the two structural variants of Chain of Responsibility?**
A:

**Variant 1 — Pure Chain (stop-or-pass):** Each handler either fully handles the request OR passes it on — only one handler ultimately processes it. Classic use: approval hierarchies (loan officer → branch manager → credit committee), where the first handler with authority approves and stops.

**Variant 2 — Pipeline (process-and-pass):** Every handler in the chain processes the request and passes it on — all handlers run on every request. Each handler transforms, enriches, or validates the request/response. Classic use: HTTP middleware stacks, loan application validation pipelines, KYC enrichment chains.

Both are valid CoR — the distinction is whether `next()` is called conditionally (stop-or-pass) or always (pipeline). In practice, fintech systems use both: the validation pipeline always runs all checks but may halt on the first failure; the approval chain stops at the first approver with sufficient authority.

**Q5. What is the Handler interface's contract, and what does `next` represent?**
A: Every handler implements the same interface, which has two responsibilities: process the request and optionally call the next handler in the chain:

```typescript
interface Handler<TRequest, TResponse = void> {
  setNext(handler: Handler<TRequest, TResponse>): Handler<TRequest, TResponse>;
  handle(request: TRequest): TResponse | Promise<TResponse>;
}

// Base abstract class — manages the next-handler link
abstract class AbstractHandler<TRequest, TResponse = void>
  implements Handler<TRequest, TResponse> {

  private nextHandler: Handler<TRequest, TResponse> | null = null;

  setNext(handler: Handler<TRequest, TResponse>): Handler<TRequest, TResponse> {
    this.nextHandler = handler;
    return handler; // enables fluent chaining: a.setNext(b).setNext(c)
  }

  async handle(request: TRequest): Promise<TResponse> {
    if (this.nextHandler) {
      return this.nextHandler.handle(request);
    }
    return undefined as TResponse; // end of chain — no handler claimed it
  }
}
```

`setNext` returns the handler it receives — this enables fluent chain construction:

```typescript
handlerA.setNext(handlerB).setNext(handlerC).setNext(handlerD);
// Chain: A → B → C → D
```

`next` represents the remainder of the chain — calling it says "I'm done with my part; carry on." Not calling it says "I'm stopping here; nothing downstream runs."

## Section 2: Implementation

**Q6. How do you implement a loan application validation pipeline using Chain of Responsibility?**
A: A validation pipeline where every handler runs and each can halt processing on failure:

```typescript
interface LoanValidationRequest {
  application: LoanApplication;
  errors: string[];   // accumulated by handlers
  halt: boolean;      // set to true by a handler to stop the chain
}

abstract class LoanValidationHandler extends AbstractHandler<LoanValidationRequest> {
  async handle(req: LoanValidationRequest): Promise<void> {
    if (req.halt) return; // chain already stopped upstream

    await this.validate(req);

    if (!req.halt) {
      await super.handle(req); // pass to next handler
    }
  }

  protected abstract validate(req: LoanValidationRequest): Promise<void>;
}

// Handler 1 — basic eligibility (income, age)
class BasicEligibilityHandler extends LoanValidationHandler {
  protected async validate(req: LoanValidationRequest): Promise<void> {
    const { application: app } = req;
    if (app.applicantAge < 21 || app.applicantAge > 65) {
      req.errors.push('Applicant age must be between 21 and 65');
      req.halt = true; // hard stop — no point running further checks
    }
    if (app.monthlyIncome < 15000) {
      req.errors.push('Monthly income below minimum threshold of ₹15,000');
      req.halt = true;
    }
  }
}

// Handler 2 — CIBIL score check
class CibilScoreHandler extends LoanValidationHandler {
  constructor(private readonly bureauService: BureauService) { super(); }

  protected async validate(req: LoanValidationRequest): Promise<void> {
    const report = await this.bureauService.fetchCreditReport(req.application.pan);
    if (report.score < 650) {
      req.errors.push(`CIBIL score ${report.score} is below minimum 650`);
      req.halt = true;
    }
    if (report.overdueAccounts > 0) {
      req.errors.push(`${report.overdueAccounts} overdue account(s) found`);
      req.halt = true;
    }
  }
}

// Handler 3 — loan-to-income ratio
class LoanToIncomeHandler extends LoanValidationHandler {
  protected async validate(req: LoanValidationRequest): Promise<void> {
    const { requestedAmount, monthlyIncome } = req.application;
    const ratio = requestedAmount / (monthlyIncome * 12);
    if (ratio > 5) {
      req.errors.push(`Loan-to-income ratio ${ratio.toFixed(1)}x exceeds maximum of 5x`);
      req.halt = true;
    }
  }
}

// Handler 4 — fraud check (runs only if no prior hard stops)
class FraudCheckHandler extends LoanValidationHandler {
  constructor(private readonly fraudService: FraudDetectionService) { super(); }

  protected async validate(req: LoanValidationRequest): Promise<void> {
    const isFlagged = await this.fraudService.check(req.application.pan);
    if (isFlagged) {
      req.errors.push('Application flagged by fraud detection system');
      req.halt = true;
    }
  }
}
```

```typescript
// Chain assembly — NestJS module useFactory
@Module({
  providers: [
    BasicEligibilityHandler,
    CibilScoreHandler,
    LoanToIncomeHandler,
    FraudCheckHandler,
    {
      provide: 'VALIDATION_CHAIN',
      useFactory: (basic, cibil, lti, fraud): LoanValidationHandler => {
        basic.setNext(cibil).setNext(lti).setNext(fraud);
        return basic; // entry point of the chain
      },
      inject: [BasicEligibilityHandler, CibilScoreHandler, LoanToIncomeHandler, FraudCheckHandler],
    },
  ],
})
export class ValidationModule {}

// Usage in LoanApplicationService
@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject('VALIDATION_CHAIN') private readonly validationChain: LoanValidationHandler,
  ) {}

  async apply(application: LoanApplication): Promise<ApplicationResult> {
    const req: LoanValidationRequest = { application, errors: [], halt: false };
    await this.validationChain.handle(req);

    if (req.errors.length > 0) {
      return { approved: false, reasons: req.errors };
    }
    return { approved: true };
  }
}
```

**Q7. How do you implement a pure stop-or-pass approval hierarchy using Chain of Responsibility?**
A: A loan sanction approval chain where authority level determines who can approve — lower handlers pass up if the amount exceeds their authority:

```typescript
interface LoanApprovalRequest {
  loanId: string;
  amount: number;
  riskScore: number;
  applicantSegment: CustomerSegment;
}

interface ApprovalDecision {
  approved: boolean;
  approvedBy: string;
  conditions?: string[];
}

abstract class ApprovalHandler extends AbstractHandler<LoanApprovalRequest, ApprovalDecision> {
  abstract readonly authorityLimit: number;
  abstract readonly role: string;

  async handle(request: LoanApprovalRequest): Promise<ApprovalDecision> {
    if (request.amount <= this.authorityLimit && this.meetsRiskCriteria(request)) {
      return this.approve(request); // within authority — handle and stop
    }
    // Exceeds authority or risk — pass up the chain
    const next = await super.handle(request);
    if (!next) {
      // Reached end of chain without approval
      throw new LoanApprovalException(`No approver has authority for ₹${request.amount}`);
    }
    return next;
  }

  protected abstract meetsRiskCriteria(request: LoanApprovalRequest): boolean;

  private approve(request: LoanApprovalRequest): ApprovalDecision {
    return { approved: true, approvedBy: this.role };
  }
}

// Loan Officer — up to ₹5L
class LoanOfficerApprovalHandler extends ApprovalHandler {
  readonly authorityLimit = 500_000;
  readonly role = 'LOAN_OFFICER';

  protected meetsRiskCriteria(req: LoanApprovalRequest): boolean {
    return req.riskScore <= 40; // low risk only
  }
}

// Branch Manager — up to ₹25L
class BranchManagerApprovalHandler extends ApprovalHandler {
  readonly authorityLimit = 2_500_000;
  readonly role = 'BRANCH_MANAGER';

  protected meetsRiskCriteria(req: LoanApprovalRequest): boolean {
    return req.riskScore <= 65;
  }
}

// Regional Credit Manager — up to ₹1Cr
class RegionalCreditManagerApprovalHandler extends ApprovalHandler {
  readonly authorityLimit = 10_000_000;
  readonly role = 'REGIONAL_CREDIT_MANAGER';

  protected meetsRiskCriteria(req: LoanApprovalRequest): boolean {
    return req.riskScore <= 80;
  }
}

// Credit Committee — unlimited, all risk levels
class CreditCommitteeApprovalHandler extends ApprovalHandler {
  readonly authorityLimit = Infinity;
  readonly role = 'CREDIT_COMMITTEE';

  protected meetsRiskCriteria(_req: LoanApprovalRequest): boolean {
    return true;
  }
}
```

  .setNext(branchManager)
  .setNext(regionalCM)

// LoanOfficer: 800K > 500K limit → passes up
// BranchManager: 800K ≤ 2.5M, riskScore 55 ≤ 65 → approves

**Q8. How do you build a CoR pipeline that enriches a request object as it moves through the chain?**
A: Each handler adds data to a shared context object — all handlers run, each contributes:

```typescript
interface KycEnrichmentContext {
  applicant: Applicant;
  // Populated progressively as the chain runs
  aadhaarData?: AadhaarVerificationResult;
  panData?: PanVerificationResult;
  bureauData?: CreditReport;
  gstnData?: GstnData;
  bankData?: BankVerificationResult;
  completedSteps: string[];
}

abstract class KycEnrichmentHandler extends AbstractHandler<KycEnrichmentContext> {
  async handle(ctx: KycEnrichmentContext): Promise<void> {
    await this.enrich(ctx);
    ctx.completedSteps.push(this.constructor.name);
    await super.handle(ctx); // always pass — all handlers run
  }
  protected abstract enrich(ctx: KycEnrichmentContext): Promise<void>;
}

class AadhaarEnrichmentHandler extends KycEnrichmentHandler {
  constructor(private readonly uidai: UidaiService) { super(); }
  protected async enrich(ctx: KycEnrichmentContext): Promise<void> {
    ctx.aadhaarData = await this.uidai.verify(ctx.applicant.aadhaar);
  }
}

class PanEnrichmentHandler extends KycEnrichmentHandler {
  constructor(private readonly nsdl: NsdlService) { super(); }
  protected async enrich(ctx: KycEnrichmentContext): Promise<void> {
    ctx.panData = await this.nsdl.verify(ctx.applicant.pan);
  }
}

class BureauEnrichmentHandler extends KycEnrichmentHandler {
  constructor(private readonly bureau: BureauService) { super(); }
  protected async enrich(ctx: KycEnrichmentContext): Promise<void> {
    ctx.bureauData = await this.bureau.fetchCreditReport(ctx.applicant.pan);
  }
}

class GstnEnrichmentHandler extends KycEnrichmentHandler {
  constructor(private readonly gstn: GstnService) { super(); }
  protected async enrich(ctx: KycEnrichmentContext): Promise<void> {
    if (ctx.applicant.gstin) { // only for business applicants
      ctx.gstnData = await this.gstn.fetch(ctx.applicant.gstin);
    }
  }
}
```

After the chain runs, `ctx` is fully populated — the underwriting engine reads from a single rich object without knowing which service provided each piece.

**Q9. How do you handle errors and partial failures in a Chain of Responsibility pipeline?**
A: Three strategies depending on the use case:

**Strategy A — Halt on first error (validation chains):**
```typescript
async handle(req: ValidationRequest): Promise<void> {
  try {
    await this.validate(req);
  } catch (err) {
    req.errors.push((err as Error).message);
    req.halt = true;
    return; // don't call super.handle — chain stops
  }
  await super.handle(req);
}
```

**Strategy B — Collect all errors (exhaustive validation):**
```typescript
async handle(req: ValidationRequest): Promise<void> {
  try {
    await this.validate(req);
  } catch (err) {
    req.errors.push((err as Error).message); // collect but continue
  }
  await super.handle(req); // always pass — discover all errors
}
```

**Strategy C — Soft failure with degraded mode (enrichment chains):**
```typescript
class BureauEnrichmentHandler extends KycEnrichmentHandler {
  protected async enrich(ctx: KycEnrichmentContext): Promise<void> {
    try {
      ctx.bureauData = await this.bureau.fetchCreditReport(ctx.applicant.pan);
    } catch (err) {
      // Bureau unavailable — flag it but don't halt KYC
      ctx.bureauUnavailable = true;
      ctx.warnings.push('Bureau data unavailable — manual review required');
    }
  }
}
```

Choose the strategy at the handler level — different handlers in the same chain can use different strategies. A critical fraud check might halt on failure; a credit score enrichment might continue with a warning.

## Section 3: Chain of Responsibility in Real-World Fintech Contexts

**Q10. How does NestJS implement Chain of Responsibility natively in its request lifecycle?**
A: NestJS's entire HTTP request processing pipeline is CoR. The chain, in order:

```
Middleware → Guards → Interceptors (pre) → Pipes → Handler (Controller method) → Interceptors (post) → Exception Filters
```

Each participant is a CoR handler:

```typescript
// Guard — stop-or-pass: returns true to continue, false to halt with 403
@Injectable()
export class JwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token = request.headers.authorization?.split(' ')[1];
    if (!token) return false; // stops chain — 403 returned
    request.user = this.jwtService.verify(token);
    return true; // passes to next handler
  }
}

// Pipe — transform/validate request data; throws to stop chain
@Injectable()
export class LoanAmountPipe implements PipeTransform {
  transform(value: unknown): number {
    const amount = Number(value);
    if (isNaN(amount) || amount < 10000) {
      throw new BadRequestException('Loan amount must be a number ≥ ₹10,000');
    }
    return amount; // transformed value passed forward
  }
}

// Interceptor — wraps the handler execution (process-and-pass)
@Injectable()
export class AuditLogInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const req = ctx.switchToHttp().getRequest();
    return next.handle().pipe(
      tap(() => this.auditLog.record(req.user.id, req.url)),
    );
  }
}
```

Understanding NestJS's CoR chain is practically important: guards run before pipes; interceptors wrap the entire handler; exception filters catch anything that escapes. Misplacing a concern (e.g., putting auth logic in a pipe instead of a guard) puts it in the wrong position in the chain.

**Q11. How would you implement a multi-step KYC approval pipeline as a Chain of Responsibility in a lending platform?**
A: KYC for a loan application typically requires sequential checks — each step depends on prior steps passing. A CoR pipeline makes each step independently testable and the overall flow configurable:

```typescript
interface KycApprovalRequest {
  applicant: Applicant;
  documents: SubmittedDocument[];
  outcome: {
    passed: boolean;
    failedStep?: string;
    failureReason?: string;
    completedChecks: string[];
  };
}

abstract class KycCheckHandler extends AbstractHandler<KycApprovalRequest> {
  abstract readonly checkName: string;

  async handle(req: KycApprovalRequest): Promise<void> {
    const passed = await this.check(req);
    req.outcome.completedChecks.push(this.checkName);

    if (!passed) {
      req.outcome.passed = false;
      req.outcome.failedStep = this.checkName;
      return; // halt — KYC failed at this step
    }

    await super.handle(req); // pass to next check
  }

  protected abstract check(req: KycApprovalRequest): Promise<boolean>;
}

// Step 1 — PAN validation via Income Tax dept
class PanValidationHandler extends KycCheckHandler {
  readonly checkName = 'PAN_VALIDATION';
  constructor(private readonly nsdl: NsdlService) { super(); }
  protected async check(req: KycApprovalRequest): Promise<boolean> {
    const result = await this.nsdl.verify(req.applicant.pan, req.applicant.name, req.applicant.dob);
    if (!result.valid) req.outcome.failureReason = `PAN mismatch: ${result.reason}`;
    return result.valid;
  }
}

// Step 2 — Aadhaar OTP verification (UIDAI)
class AadhaarOtpHandler extends KycCheckHandler {
  readonly checkName = 'AADHAAR_OTP';
  constructor(private readonly uidai: UidaiService) { super(); }
  protected async check(req: KycApprovalRequest): Promise<boolean> {
    const result = await this.uidai.verifyOtp(req.applicant.aadhaar, req.applicant.aadhaarOtp);
    if (!result.verified) req.outcome.failureReason = 'Aadhaar OTP verification failed';
    return result.verified;
  }
}

// Step 3 — Face liveness and PAN-photo match
class FaceMatchHandler extends KycCheckHandler {
  readonly checkName = 'FACE_MATCH';
  constructor(private readonly faceAi: FaceMatchService) { super(); }
  protected async check(req: KycApprovalRequest): Promise<boolean> {
    const selfie = req.documents.find(d => d.type === 'SELFIE');
    if (!selfie) { req.outcome.failureReason = 'Selfie document missing'; return false; }
    const score = await this.faceAi.match(req.applicant.pan, selfie.fileUrl);
    if (score < 0.85) req.outcome.failureReason = `Face match score ${score} below threshold 0.85`;
    return score >= 0.85;
  }
}

// Step 4 — PEP/Sanction screening (PMLA requirement)
class PepScreeningHandler extends KycCheckHandler {
  readonly checkName = 'PEP_SCREENING';
  constructor(private readonly screening: PepScreeningService) { super(); }
  protected async check(req: KycApprovalRequest): Promise<boolean> {
    const result = await this.screening.check(req.applicant.name, req.applicant.dob);
    if (result.flagged) req.outcome.failureReason = `PEP match: ${result.matchedList}`;
    return !result.flagged;
  }
}
```

**Q12. How do you use Chain of Responsibility for fraud detection in loan applications?**
A: Fraud detection is naturally a CoR problem — multiple independent signals checked in order of computational cost, halting early on a definitive hit:

```typescript
interface FraudCheckContext {
  application: LoanApplication;
  riskScore: number;          // accumulated across handlers
  flags: FraudFlag[];
  decision: 'PASS' | 'REVIEW' | 'REJECT' | 'PENDING';
}

abstract class FraudCheckHandler extends AbstractHandler<FraudCheckContext> {
  async handle(ctx: FraudCheckContext): Promise<void> {
    if (ctx.decision === 'REJECT') return; // hard reject — stop processing

    await this.check(ctx);
    await super.handle(ctx);
  }
  protected abstract check(ctx: FraudCheckContext): Promise<void>;
}

// Check 1 — device fingerprint (cheap, in-memory)
class DeviceFingerprintHandler extends FraudCheckHandler {
  protected async check(ctx: FraudCheckContext): Promise<void> {
    const isKnownFraudDevice = await this.deviceStore.isBlacklisted(ctx.application.deviceId);
    if (isKnownFraudDevice) {
      ctx.decision = 'REJECT';
      ctx.flags.push({ type: 'BLACKLISTED_DEVICE', severity: 'HIGH' });
      ctx.riskScore += 100;
    }
  }
}

// Check 2 — PAN/Aadhaar duplicate detection
class DuplicateApplicantHandler extends FraudCheckHandler {
  protected async check(ctx: FraudCheckContext): Promise<void> {
    const existing = await this.loanRepo.findActiveByPan(ctx.application.pan);
    if (existing.length >= 3) {
      ctx.flags.push({ type: 'MULTIPLE_ACTIVE_LOANS', severity: 'MEDIUM' });
      ctx.riskScore += 40;
      if (ctx.riskScore >= 80) ctx.decision = 'REVIEW';
    }
  }
}

// Check 3 — velocity check (applications per hour from same IP)
class VelocityCheckHandler extends FraudCheckHandler {
  protected async check(ctx: FraudCheckContext): Promise<void> {
    const recentApps = await this.redis.get(`velocity:${ctx.application.ipAddress}`);
    if (Number(recentApps) > 5) {
      ctx.flags.push({ type: 'HIGH_VELOCITY_IP', severity: 'HIGH' });
      ctx.riskScore += 60;
      ctx.decision = 'REJECT';
    }
  }
}

// Check 4 — ML model scoring (expensive — runs last)
class MlFraudModelHandler extends FraudCheckHandler {
  protected async check(ctx: FraudCheckContext): Promise<void> {
    if (ctx.decision !== 'PENDING') return; // skip if already decided
    const mlScore = await this.mlClient.score(ctx.application);
    ctx.riskScore += mlScore;
    if (mlScore > 70) ctx.decision = 'REVIEW';
  }
}
```

Order matters: cheap synchronous checks first (device fingerprint), then DB lookups, then external APIs, then the expensive ML call last — early exits avoid paying the ML cost for obvious rejections.

**Q13. How would you implement a document validation pipeline for loan applications using Chain of Responsibility?**
A: Document validation involves sequential checks — existence, format, authenticity, expiry — where each check is independently maintainable:

```typescript
interface DocumentValidationContext {
  document: SubmittedDocument;
  applicant: Applicant;
  validationErrors: string[];
  isValid: boolean;
}

abstract class DocumentValidationHandler extends AbstractHandler<DocumentValidationContext> {
  async handle(ctx: DocumentValidationContext): Promise<void> {
    if (!ctx.isValid) return; // prior handler invalidated — short-circuit

    await this.validate(ctx);
    await super.handle(ctx);
  }
  protected abstract validate(ctx: DocumentValidationContext): Promise<void>;
}

// Step 1 — file format and size
class FileFormatHandler extends DocumentValidationHandler {
  protected async validate(ctx: DocumentValidationContext): Promise<void> {
    const allowed = ['application/pdf', 'image/jpeg', 'image/png'];
    if (!allowed.includes(ctx.document.mimeType)) {
      ctx.validationErrors.push(`Invalid file format: ${ctx.document.mimeType}`);
      ctx.isValid = false;
    }
    if (ctx.document.sizeBytes > 5 * 1024 * 1024) {
      ctx.validationErrors.push('File size exceeds 5MB limit');
      ctx.isValid = false;
    }
  }
}

// Step 2 — virus/malware scan
class MalwareScanHandler extends DocumentValidationHandler {
  constructor(private readonly scanner: AvScanner) { super(); }
  protected async validate(ctx: DocumentValidationContext): Promise<void> {
    const clean = await this.scanner.scan(ctx.document.fileUrl);
    if (!clean) {
      ctx.validationErrors.push('Malware detected in uploaded document');
      ctx.isValid = false;
    }
  }
}

// Step 3 — OCR + content verification
class OcrVerificationHandler extends DocumentValidationHandler {
  constructor(private readonly ocr: OcrService) { super(); }
  protected async validate(ctx: DocumentValidationContext): Promise<void> {
    const extracted = await this.ocr.extract(ctx.document.fileUrl, ctx.document.type);
    if (!extracted.nameMatcher(ctx.applicant.name)) {
      ctx.validationErrors.push('Document name does not match applicant name');
      ctx.isValid = false;
    }
  }
}

// Step 4 — expiry check
class DocumentExpiryHandler extends DocumentValidationHandler {
  protected async validate(ctx: DocumentValidationContext): Promise<void> {
    if (ctx.document.expiryDate && ctx.document.expiryDate < new Date()) {
      ctx.validationErrors.push(`Document expired on ${ctx.document.expiryDate.toDateString()}`);
      ctx.isValid = false;
    }
  }
}
```

**Q14. How do you build a configurable, product-specific validation chain where different loan products require different handler sequences?**
A: Use a chain builder that assembles different sequences based on product type — CoR's composability shines here:

```typescript
@Injectable()
export class ValidationChainBuilder {
  constructor(
    private readonly basicEligibility: BasicEligibilityHandler,
    private readonly cibilCheck: CibilScoreHandler,
    private readonly loanToIncome: LoanToIncomeHandler,
    private readonly fraudCheck: FraudCheckHandler,
    private readonly gstVerification: GstVerificationHandler,
    private readonly itrCheck: ItrVerificationHandler,
    private readonly propertyValuation: PropertyValuationHandler,
  ) {}

  buildFor(productCode: string): LoanValidationHandler {
    switch (productCode) {
      case 'HL-STD': // Home Loan — full chain with property check
        return this.chain([
          this.basicEligibility,
          this.cibilCheck,
          this.loanToIncome,
          this.propertyValuation,
          this.fraudCheck,
        ]);

      case 'PL-STD': // Personal Loan — no property, faster
        return this.chain([
          this.basicEligibility,
          this.cibilCheck,
          this.loanToIncome,
          this.fraudCheck,
        ]);

      case 'MSME-STD': // MSME Loan — GST + ITR added
        return this.chain([
          this.basicEligibility,
          this.gstVerification,
          this.itrCheck,
          this.cibilCheck,
          this.fraudCheck,
        ]);

      default:
        throw new BadRequestException(`No validation chain for product: ${productCode}`);
    }
  }

  private chain(handlers: LoanValidationHandler[]): LoanValidationHandler {
    for (let i = 0; i < handlers.length - 1; i++) {
      handlers[i].setNext(handlers[i + 1]);
    }
    return handlers[0];
  }
}
```

Handlers are reused across chains — `FraudCheckHandler` is in both HL and PL chains, maintained in one place. Adding a new product means adding a new case to `buildFor()` composing existing handlers — no handler class changes.

**Q15. How do you unit test individual handlers in isolation?**

## Section 5: Anti-patterns & Pitfalls

**Q17. What are the most common mistakes when implementing Chain of Responsibility?**
A:

- **Handlers that always pass AND always process** — if every handler always processes AND always passes, you may want Decorator (which is additive and always delegates) rather than CoR. CoR's value is conditional passing.
- **Hardcoding the chain inside handlers** — a handler that `new`s its own successor couples itself to a concrete class. The chain must be assembled externally — by a factory, builder, or DI container.
- **No termination handling** — if the chain ends without a handler claiming the request, what happens? Silently returning `undefined` is a hidden bug. Always define what happens at the end of the chain — throw an exception, return a default value, or use a terminal "catch-all" handler.
- **Mutable shared state race conditions** — enrichment chains that write to a shared context object are safe in synchronous chains. In parallel async execution (running handlers concurrently with `Promise.all`) they'll race. If you parallelise, ensure each handler writes to its own isolated field on the context.
- **Overly long chains** — a chain of 15 handlers is hard to reason about, test as a whole, and debug when a request doesn't reach the expected handler. If the chain grows beyond 6–8 handlers, split it into sub-chains or grouped steps.
- **Treating CoR as a replacement for domain logic** — handlers should contain cross-cutting checks, not complex domain logic. If a handler has 100 lines of business rules, it's doing too much — it should delegate to a domain service.

**Q18. What is the difference between Chain of Responsibility and a simple sequential function call list?**
A: A sequential function call list (`validate(); checkFraud(); enrich(); approve()`) is static and tightly coupled — the caller knows every step, their order, and their existence. CoR provides:

- **Dynamic composition** — the chain can be assembled differently for different products, environments, or feature flags without changing the caller.
- **Handler autonomy** — each handler decides independently whether to pass the request forward, without the caller orchestrating that decision.
- **Extensibility without modification** — inserting a new step between existing steps doesn't require modifying the caller or any existing handler — just re-wire the chain in the composition root.
- **Handler reuse** — the same `FraudCheckHandler` can appear in multiple chains assembled for different contexts.

If the sequence is always fixed, all steps always run, and you never add/remove steps — a sequential call list is simpler and perfectly correct. Use CoR when you need the dynamic composition and per-handler control flow.

## Section 6: Scenario / System Design Questions

**Q19. "Design the request processing pipeline for a new BNPL (Buy Now Pay Later) checkout flow. The pipeline must validate the customer, check credit limit, detect fraud, and generate an offer — but some steps can be skipped for returning customers with a clean history. How do you structure this?"**
A: Use a CoR pipeline with context-aware short-circuiting in handlers. A `CustomerTier` field on the context allows handlers to skip their work for qualified returning customers:

```typescript
interface BnplCheckoutContext {
  customer: Customer;
  order: BnplOrder;
  customerTier: 'NEW' | 'RETURNING_CLEAN' | 'RETURNING_FLAGGED';
  creditLimit: number;
  offer?: BnplOffer;
  errors: string[];
  halt: boolean;
}

class CreditLimitHandler extends AbstractHandler<BnplCheckoutContext> {
  async handle(ctx: BnplCheckoutContext): Promise<void> {
    if (ctx.customerTier === 'RETURNING_CLEAN' && ctx.customer.preApprovedLimit) {
      // Skip full re-evaluation for clean returning customers
      ctx.creditLimit = ctx.customer.preApprovedLimit;
      return super.handle(ctx);
    }
    // Full evaluation for new or flagged customers
    ctx.creditLimit = await this.creditEngine.evaluate(ctx.customer);
    await super.handle(ctx);
  }
}

class FraudCheckHandler extends AbstractHandler<BnplCheckoutContext> {
  async handle(ctx: BnplCheckoutContext): Promise<void> {
    if (ctx.customerTier === 'RETURNING_CLEAN' && ctx.order.amount < 5000) {
      // Skip fraud check for clean customers on small orders — latency optimisation
      return super.handle(ctx);
    }
    const isFraud = await this.fraudService.check(ctx.customer, ctx.order);
    if (isFraud) { ctx.halt = true; return; }
    await super.handle(ctx);
  }
}
```

The chain is the same for all customers; individual handlers decide whether to fast-path based on tier. This avoids maintaining separate chains per tier while still optimising latency for returning customers.

**Q20. "Your loan origination system currently runs validation sequentially — each check waits for the prior one to finish. Bureau pull (2–3s), fraud check (1–2s), and property valuation (3–5s) all run one after another. Total: 6–10 seconds. How do you redesign this while keeping the CoR structure?"**
A: Split the chain into sequential groups and parallelise within each group:

```typescript
// Phase 1 — fast, synchronous, local checks (no external calls)
// Run sequentially — each can halt early before expensive Phase 2
const phase1 = new chain([basicEligibility, loanToIncome, documentCompleteness]);

// Phase 2 — expensive, independent external calls
// Run in parallel — none depends on another's result
async function runPhase2(application: LoanApplication): Promise<Phase2Results> {
  const [bureauReport, fraudResult, propertyValuation] = await Promise.allSettled([
    bureauService.fetchCreditReport(application.pan),
    fraudService.check(application),
    propertyService.valuate(application.propertyId),
  ]);
  return {
    bureauReport: bureauReport.status === 'fulfilled' ? bureauReport.value : null,
    fraudResult: fraudResult.status === 'fulfilled' ? fraudResult.value : null,
    propertyValuation: propertyValuation.status === 'fulfilled' ? propertyValuation.value : null,
    failures: [bureauReport, fraudResult, propertyValuation]
      .filter(r => r.status === 'rejected')
      .map(r => (r as PromiseRejectedResult).reason),
  };
}

// Phase 3 — decision synthesis — runs after Phase 2 results are available
const phase3 = new chain([bureauDecisionHandler, fraudDecisionHandler, underwritingDecisionHandler]);

// Orchestrator
async function processApplication(application: LoanApplication): Promise<LoanDecision> {
  // Phase 1 — fast checks first
  const phase1Req = makeValidationRequest(application);
  await phase1.handle(phase1Req);
  if (phase1Req.halt) return { approved: false, reasons: phase1Req.errors };

  // Phase 2 — parallel external calls
  const phase2Results = await runPhase2(application); // ~3-5s instead of 6-10s

  // Phase 3 — synthesise decisions
  const phase3Ctx = makeDecisionContext(application, phase2Results);
  await phase3.handle(phase3Ctx);

  return phase3Ctx.decision;
}
```

Total latency: Phase 1 (synchronous, ~200ms) + Phase 2 (parallel, ~3–5s max of the three) + Phase 3 (synthesise, ~100ms) = **~3.3–5.3s** instead of 6–10s. CoR is preserved within each phase; parallelism is applied *between* independent external calls.

**Q21. "A new RBI circular mandates that a 'Cooling-Off Period Check' must be inserted between the CIBIL check and the fraud check in your loan validation pipeline for all personal loan products. How do you implement this change?"**
A: This is CoR's core value proposition — open/closed extension:

```typescript
// New handler — no existing handler is modified
@Injectable()
export class CoolingOffPeriodHandler extends LoanValidationHandler {
  readonly checkName = 'RBI_COOLING_OFF_CHECK';
  constructor(private readonly loanRepo: LoanRepository) { super(); }

  protected async validate(req: LoanValidationRequest): Promise<void> {
    const recentRejection = await this.loanRepo.findRecentRejection(
      req.application.pan,
      90, // 90-day cooling-off period per RBI circular
    );
    if (recentRejection) {
      req.errors.push(
        `Application rejected: RBI cooling-off period active until ${recentRejection.coolingOffEndsAt.toDateString()}`
      );
      req.halt = true;
    }
  }
}

// Chain builder — re-wire for personal loans; home loan chain unchanged
buildFor('PL-STD'): LoanValidationHandler {
  return this.chain([
    this.basicEligibility,
    this.cibilCheck,
    this.coolingOffPeriod,   // ← inserted here; no other handler touched
    this.fraudCheck,
  ]);
}
```

Changes required: one new handler class, one updated chain builder case. `CibilScoreHandler`, `FraudCheckHandler`, `BasicEligibilityHandler` — all untouched. The test suite for existing handlers doesn't need a single change.

## Quick Reference: Chain of Responsibility Checklist

| Signal                                                                   | What to Do                                                                     |
|--------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| Sequential `if (!check1()) return; if (!check2()) return;` pattern        | Extract each check to a handler — assemble as CoR chain                        |
| Multiple steps that must run in order, each can halt processing          | Stop-or-pass CoR chain                                                          |
| Multiple steps that all run and each enriches the request                | Pipeline CoR — always calls `super.handle()`                                   |
| Different products/segments need different validation step sequences     | Chain builder that assembles product-specific chains from shared handler pool  |
| Adding a new validation step between existing ones                       | New handler class + re-wire in builder — no existing class modified            |
| NestJS Guards / Pipes / Interceptors                                     | Already CoR — understand position in the request lifecycle chain               |
| Expensive external calls running sequentially                            | Group independent calls in a parallel phase; CoR within each phase             |
| Chain ends without a handler processing the request                      | Add a terminal catch-all handler or throw a descriptive exception              |
| Handler hardcodes its own successor via `new`                            | Externalize — wire chain in factory, builder, or NestJS `useFactory`           |
| Chain of 10+ handlers getting hard to reason about                       | Split into named sub-chains or grouped phases                                   |

---

**Tip for the interview:** At the 5 YOE level, Chain of Responsibility surfaces as "how do you structure a validation pipeline," "how do you handle the loan approval hierarchy," or "how would you add a new mandatory check mandated by a regulator." The right answer names the pattern, demonstrates the handler interface, and — critically — shows the chain is assembled externally (in a factory or builder), not hardcoded inside handlers. The differentiators: knowing the two variants (stop-or-pass vs pipeline/enrichment), understanding why order matters (cheap synchronous checks before expensive external calls), recognising that NestJS Guards/Pipes/Interceptors are CoR in the framework layer, and being able to explain how inserting a new mandatory step (the RBI cooling-off scenario is a real example) is a configuration/composition change, not a modification of existing tested code.
