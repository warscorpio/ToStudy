# Design Patterns (Behavioral): Memento — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Memento pattern?**
A: Memento is a behavioral design pattern that captures and externalizes an object's internal state — at a specific point in time — so that the object can be restored to that state later, without violating encapsulation. The critical constraint is that the state is captured and restored *through* the originator itself: the object whose state is being saved is the only one that reads or writes its own private fields. External objects (the caretaker) hold the memento but treat it as an opaque token — they cannot inspect or modify the saved state, preserving the originator's encapsulation invariant.

**Q2. What problem does Memento solve, and when does a simpler approach break down?**
A: Memento solves two problems simultaneously: (1) you need to externalize an object's state for later restoration, and (2) you cannot expose the object's internal structure to do so. A simpler approach — just making all state public or adding a `getState()` that returns a raw copy — breaks encapsulation and creates coupling: every piece of code that stores or restores the object now depends on its internal structure. When the internal representation changes, every caller breaks. Memento breaks down this coupling by making the captured state opaque — callers hold a snapshot but cannot poke inside it.

The pattern becomes necessary when:
- An undo/redo stack must store object snapshots without exposing private internals.
- A transaction-like mechanism must checkpoint state before a risky operation and roll back on failure.
- A wizard / multi-step form must allow stepping backward to an earlier state.
- A game or simulation must support save/load of arbitrary state.
- An editor must allow "revert to last saved" semantics.

**Q3. What are the three participants in the Memento pattern?**
A: The GoF define three:
1. **Originator** — the object whose state is worth saving. Creates a memento containing a snapshot of its current internal state (`createMemento()`). Restores its state from a memento (`restoreFromMemento(memento)`). Is the *only* object that accesses the memento's content — the memento's state is private to the originator.
2. **Memento** — stores a snapshot of the originator's internal state. Has two interfaces: a *wide* interface for the originator (full access to read and write stored state) and a *narrow* interface for the caretaker (no access — just hold and return it). In languages without friend classes, this is approximated by keeping memento fields private and only the originator can construct/read them.
3. **Caretaker** — manages the collection of mementos (e.g., a stack for undo, a list for history). Requests a memento from the originator before a potentially destructive operation. Passes the memento back to the originator when rollback is needed. Never inspects or modifies the memento's content.

**Q4. What is the "wide vs. narrow interface" distinction in Memento, and how is it implemented in TypeScript?**
A: The GoF Memento defines two distinct interfaces for the same memento object:
- **Wide interface** — exposes the full stored state; used exclusively by the originator to create and restore from the memento.
- **Narrow interface** — exposes nothing (or just metadata like a timestamp or label); used by the caretaker, which only needs to store and return it.

TypeScript approximates this without friend classes using one of three approaches:

```typescript
// ─── Approach 1: Opaque type via closure / symbol-keyed private data ──────────

const MEMENTO_STATE = Symbol("MEMENTO_STATE");

class LoanApplicationMemento {
  private readonly [MEMENTO_STATE]: Readonly<LoanApplicationState>;

  // Only the originator can construct it — and only it has access to the symbol
  constructor(state: LoanApplicationState) {
    this[MEMENTO_STATE] = Object.freeze({ ...state });
  }

  // Intentionally no public getters — caretaker sees an opaque object
}

class LoanApplication {
  private state: LoanApplicationState = initialState();

  createMemento(): LoanApplicationMemento {
    return new LoanApplicationMemento(this.state);
  }

  restoreFromMemento(memento: LoanApplicationMemento): void {
    // Originator accesses the symbol-keyed data — caretaker cannot
    this.state = { ...memento[MEMENTO_STATE] };
  }
}

// ─── Approach 2: Nested class (originator as factory + reader) ────────────────

class LoanApplicationV2 {
  private state: LoanApplicationState = initialState();

  // Nested class — TypeScript does not enforce private access across classes,
  // but the pattern communicates intent clearly
  createMemento(): LoanApplicationV2.Memento {
    return new LoanApplicationV2.Memento(this.state);
  }

  restoreFromMemento(m: LoanApplicationV2.Memento): void {
    this.state = m.getState();   // only originator calls getState()
  }
}

namespace LoanApplicationV2 {
  export class Memento {
    private readonly state: LoanApplicationState;
    constructor(state: LoanApplicationState) { this.state = Object.freeze({ ...state }); }
    getState(): LoanApplicationState { return this.state; }   // originator-facing only
  }
}

// ─── Approach 3: Opaque token via branding ────────────────────────────────────

type MementoToken = { readonly __brand: "MementoToken" };

class LoanApplicationV3 {
  private state: LoanApplicationState = initialState();
  private snapshots = new WeakMap<MementoToken, LoanApplicationState>();

  createMemento(): MementoToken {
    const token = Object.freeze({ __brand: "MementoToken" as const });
    this.snapshots.set(token, { ...this.state });
    return token;
  }

  restoreFromMemento(token: MementoToken): void {
    const saved = this.snapshots.get(token);
    if (!saved) throw new Error("Invalid or expired memento token");
    this.state = { ...saved };
  }
}
```

Approach 3 (WeakMap-backed token) is the most encapsulation-safe in TypeScript: the caretaker holds a branded token that carries no state — the state lives inside the originator's own WeakMap, inaccessible to anything else.

**Q5. How does Memento relate to Command, and how do they work together for undo/redo?**
A: Memento and Command are frequently combined and sometimes confused:
- **Command** encapsulates *what* to do and *how to undo it* — it knows the inverse operation.
- **Memento** captures *what state existed before* — it knows the snapshot to restore.

They are complementary answers to undo:
- **Command-based undo** — each command implements `undo()` as the logical inverse (a debit is undone by a credit). Works when the inverse is clean and computable. Fails when the operation is irreversible, has side effects outside the system, or when computing the exact inverse is complex.
- **Memento-based undo** — each command saves a snapshot of the originator *before* executing; `undo()` simply restores the snapshot. Works when state is bounded in size and the full snapshot is cheaper than computing an inverse. Fails when state is very large or when the snapshot must be serialized across processes.

In practice, they combine naturally: the `ConcreteCommand` holds a `Memento` captured before `execute()`, and `undo()` restores from it. Command decides *when* to capture; Memento decides *what* was captured and *how* to restore it:

```typescript
class RiskyConfigChangeCommand implements Command {
  private snapshot: ConfigMemento | null = null;

  constructor(
    private readonly config: LoanProductConfig,
    private readonly changes: Partial<LoanProductConfigState>,
  ) {}

  execute(): void {
    this.snapshot = this.config.createMemento();   // Memento captures before
    this.config.applyChanges(this.changes);        // Command executes after
  }

  undo(): void {
    if (!this.snapshot) throw new Error("Command not yet executed");
    this.config.restoreFromMemento(this.snapshot); // Memento restores on undo
  }
}
```

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript implementation of the Memento pattern.**
A:

```typescript
// ─── State type ───────────────────────────────────────────────────────────────

interface EditorState {
  content:    string;
  cursorPos:  number;
  selection:  { start: number; end: number } | null;
  isDirty:    boolean;
}

// ─── Memento ──────────────────────────────────────────────────────────────────

class EditorMemento {
  // State is private — caretaker holds this object but cannot read it
  private readonly state: Readonly<EditorState>;
  readonly savedAt: Date = new Date();
  readonly label:   string;

  constructor(state: EditorState, label = "") {
    this.state = Object.freeze({ ...state, selection: state.selection ? { ...state.selection } : null });
    this.label = label;
  }

  // Wide interface — only the originator should call this
  getState(): Readonly<EditorState> { return this.state; }
}

// ─── Originator ───────────────────────────────────────────────────────────────

class TextEditor {
  private state: EditorState = {
    content:   "",
    cursorPos: 0,
    selection: null,
    isDirty:   false,
  };

  type(text: string): void {
    const before = this.state.content.slice(0, this.state.cursorPos);
    const after  = this.state.content.slice(this.state.cursorPos);
    this.state = {
      ...this.state,
      content:   before + text + after,
      cursorPos: this.state.cursorPos + text.length,
      isDirty:   true,
    };
  }

  delete(count: number): void {
    const pos  = this.state.cursorPos;
    const content = this.state.content.slice(0, Math.max(0, pos - count))
                  + this.state.content.slice(pos);
    this.state = { ...this.state, content, cursorPos: Math.max(0, pos - count), isDirty: true };
  }

  moveCursor(pos: number): void {
    this.state = { ...this.state, cursorPos: Math.min(pos, this.state.content.length) };
  }

  select(start: number, end: number): void {
    this.state = { ...this.state, selection: { start, end } };
  }

  // Originator creates a Memento — caretaker receives an opaque token
  createMemento(label = ""): EditorMemento {
    return new EditorMemento(this.state, label);
  }

  // Originator restores from Memento — caretaker cannot do this
  restoreFromMemento(memento: EditorMemento): void {
    const saved = memento.getState();
    this.state  = {
      content:   saved.content,
      cursorPos: saved.cursorPos,
      selection: saved.selection ? { ...saved.selection } : null,
      isDirty:   saved.isDirty,
    };
  }

  get content():    string  { return this.state.content; }
  get cursorPos():  number  { return this.state.cursorPos; }
  get isDirty():    boolean { return this.state.isDirty; }
}

// ─── Caretaker ────────────────────────────────────────────────────────────────

class EditorHistory {
  private undoStack: EditorMemento[] = [];
  private redoStack: EditorMemento[] = [];
  private readonly maxDepth: number;

  constructor(maxDepth = 100) { this.maxDepth = maxDepth; }

  save(memento: EditorMemento): void {
    this.undoStack.push(memento);
    if (this.undoStack.length > this.maxDepth) this.undoStack.shift();
    this.redoStack = [];   // new action clears redo stack
  }

  undo(editor: TextEditor): boolean {
    if (this.undoStack.length === 0) return false;
    // Save current state to redo stack before restoring
    this.redoStack.push(editor.createMemento("redo-checkpoint"));
    const memento = this.undoStack.pop()!;
    editor.restoreFromMemento(memento);
    return true;
  }

  redo(editor: TextEditor): boolean {
    if (this.redoStack.length === 0) return false;
    this.undoStack.push(editor.createMemento("undo-checkpoint"));
    const memento = this.redoStack.pop()!;
    editor.restoreFromMemento(memento);
    return true;
  }

  get canUndo(): boolean { return this.undoStack.length > 0; }
  get canRedo(): boolean { return this.redoStack.length > 0; }
  get historyDepth(): number { return this.undoStack.length; }
}

// ─── Client ───────────────────────────────────────────────────────────────────

const editor  = new TextEditor();
const history = new EditorHistory(50);

// Checkpoint before each meaningful edit
history.save(editor.createMemento("initial"));
editor.type("Hello");

history.save(editor.createMemento("after-hello"));
editor.type(", World");

history.save(editor.createMemento("after-world"));
editor.type("!");

console.log(editor.content);       // "Hello, World!"
history.undo(editor);
console.log(editor.content);       // "Hello, World"
history.undo(editor);
console.log(editor.content);       // "Hello"
history.redo(editor);
console.log(editor.content);       // "Hello, World"
```

**Q7. How do you implement incremental (delta) mementos to reduce memory cost when full snapshots are expensive?**
A: Full snapshots copy the entire state on every save — for large objects this is prohibitive. Incremental mementos store only what changed:

```typescript
// ─── Delta Memento ────────────────────────────────────────────────────────────

type Delta<T> = Partial<{ [K in keyof T]: { from: T[K]; to: T[K] } }>;

class DeltaMemento<T extends object> {
  readonly savedAt = new Date();

  constructor(private readonly delta: Delta<T>) {
    Object.freeze(this.delta);
  }

  getDelta(): Delta<T> { return this.delta; }
}

class LoanProductConfig {
  private state: LoanProductConfigState;

  constructor(initial: LoanProductConfigState) {
    this.state = { ...initial };
  }

  update(changes: Partial<LoanProductConfigState>): DeltaMemento<LoanProductConfigState> {
    // Compute delta before applying
    const delta: Delta<LoanProductConfigState> = {};
    for (const key of Object.keys(changes) as (keyof LoanProductConfigState)[]) {
      if (this.state[key] !== changes[key]) {
        delta[key] = { from: this.state[key], to: changes[key]! } as any;
      }
    }

    this.state = { ...this.state, ...changes };
    return new DeltaMemento(delta);
  }

  restoreFromDelta(memento: DeltaMemento<LoanProductConfigState>): void {
    const delta = memento.getDelta();
    const restored: Partial<LoanProductConfigState> = {};
    for (const key of Object.keys(delta) as (keyof LoanProductConfigState)[]) {
      restored[key] = delta[key]!.from as any;
    }
    this.state = { ...this.state, ...restored };
  }

  getState(): Readonly<LoanProductConfigState> { return this.state; }
}

// Usage: only changed fields are stored — not the full 40-field config
const config   = new LoanProductConfig(defaultLoanConfig);
const snapshot = config.update({ annualInterestRate: 0.20, processingFeePercent: 0.015 });
// snapshot.getDelta() = { annualInterestRate: { from: 0.18, to: 0.20 }, processingFeePercent: ... }

config.update({ maxTenureMonths: 84 });
config.restoreFromDelta(snapshot);   // restores only interest rate and processing fee
```

Delta mementos shine when: state objects have many fields but only a few change per operation; history is deep (hundreds of snapshots); the originator has a large embedded object graph.

**Q8. How do you serialize Mementos for persistence across process restarts?**
A: A memento stored only in memory is lost when the process dies. Durable mementos require serialization to a persistent store (DB, Redis, file system). The challenge is that mementos often hold rich domain objects — these must be serializable to a plain data format:

```typescript
// ─── Serializable Memento ─────────────────────────────────────────────────────

interface SerializedMemento {
  mementoId:    string;
  originatorId: string;     // identifies which object this belongs to
  savedAt:      string;     // ISO 8601
  label:        string;
  version:      number;     // schema version — for migration
  stateJson:    string;     // JSON-serialized state
}

class PersistableEditorMemento {
  readonly mementoId:    string = crypto.randomUUID();
  readonly savedAt:      Date   = new Date();

  private readonly state: EditorState;

  constructor(state: EditorState, readonly label = "", readonly version = 1) {
    this.state = Object.freeze({ ...state });
  }

  getState(): Readonly<EditorState> { return this.state; }

  // Serialize to plain object for DB/Redis storage
  toSerializable(originatorId: string): SerializedMemento {
    return {
      mementoId:    this.mementoId,
      originatorId,
      savedAt:      this.savedAt.toISOString(),
      label:        this.label,
      version:      this.version,
      stateJson:    JSON.stringify(this.state),
    };
  }

  // Reconstruct from persisted record
  static fromSerializable(record: SerializedMemento): PersistableEditorMemento {
    const state = JSON.parse(record.stateJson) as EditorState;
    // Migrate if version differs
    const migrated = PersistableEditorMemento.migrate(state, record.version);
    return new PersistableEditorMemento(migrated, record.label, record.version);
  }

  private static migrate(state: EditorState, fromVersion: number): EditorState {
    // Version 1 → 2: added `isDirty` field
    if (fromVersion < 2 && !("isDirty" in state)) {
      return { ...state, isDirty: false };
    }
    return state;
  }
}

// ─── Persistent Caretaker ─────────────────────────────────────────────────────

@Injectable()
class PersistentEditorHistory {
  constructor(private readonly mementoRepo: MementoRepository) {}

  async save(editorId: string, memento: PersistableEditorMemento): Promise<void> {
    await this.mementoRepo.insert(memento.toSerializable(editorId));
  }

  async loadHistory(editorId: string): Promise<PersistableEditorMemento[]> {
    const records = await this.mementoRepo.findByOriginatorId(editorId, { orderBy: "savedAt" });
    return records.map(PersistableEditorMemento.fromSerializable);
  }

  async undo(editorId: string, editor: TextEditor): Promise<boolean> {
    const records = await this.mementoRepo.findByOriginatorId(editorId, { orderBy: "savedAt DESC", limit: 1 });
    if (records.length === 0) return false;
    const memento = PersistableEditorMemento.fromSerializable(records[0]);
    editor.restoreFromMemento(memento);
    await this.mementoRepo.delete(records[0].mementoId);
    return true;
  }
}
```

**Q9. How does Memento handle deep vs. shallow copying of state, and what are the risks of getting it wrong?**
A: The memento must capture a *true* snapshot — any reference to a mutable object that the originator can later modify will silently corrupt the saved state. Shallow copies are only safe when the state is flat (primitive values only):

```typescript
// ❌ Shallow copy — nested objects are shared references
class BadMemento {
  readonly state: LoanApplicationState;
  constructor(state: LoanApplicationState) {
    this.state = { ...state };   // spreads top-level but NOT nested objects
  }
}

// Problem:
const app     = new LoanApplication();
app.addDocument({ type: "PAN", url: "https://cdn.example.com/pan.pdf" });
const badSnap = new BadMemento(app.state);
app.documents.push({ type: "Aadhar", url: "https://cdn.example.com/aadhar.pdf" });
// badSnap.state.documents is the SAME array — now has both documents ❌

// ✅ Deep copy — all nested objects cloned
class GoodMemento {
  private readonly state: LoanApplicationState;
  constructor(state: LoanApplicationState) {
    // Deep clone — safe for serializable state
    this.state = JSON.parse(JSON.stringify(state));
  }
  getState(): LoanApplicationState { return JSON.parse(JSON.stringify(this.state)); }
}

// ✅ Structured clone (Node.js 17+ / browser) — faster than JSON roundtrip
class BestMemento {
  private readonly state: LoanApplicationState;
  constructor(state: LoanApplicationState) {
    this.state = structuredClone(state);
  }
  getState(): LoanApplicationState { return structuredClone(this.state); }
}
```

`structuredClone` is the preferred approach for non-trivial state in modern Node.js: it handles circular references, typed arrays, `Map`, `Set`, `Date`, and `RegExp` — all of which `JSON.parse(JSON.stringify(...))` mangles or loses.

**Q10. When should you use Memento versus simply re-fetching state from the database?**
A: Both achieve "restore to a previous state" but for different scenarios:

| Dimension              | Memento (in-memory / local snapshot)                   | Re-fetch from database                                   |
|------------------------|--------------------------------------------------------|----------------------------------------------------------|
| Speed                  | Sub-millisecond — no I/O                               | Network + query latency                                  |
| Durability             | Lost on process restart (unless serialized)            | Survives restarts and crashes                            |
| Granularity            | Any arbitrary point in time, any sub-operation         | Only what was committed to the DB                        |
| Scope                  | Single session / single object graph                   | Any client, any session, any time                        |
| Use case               | In-session undo/redo, wizard back-navigation, dry run  | Cross-session restore, audit replay, disaster recovery   |
| Memory cost            | Proportional to snapshot size × history depth          | Zero in-memory (state lives in DB)                       |
| Encapsulation          | Preserved — caretaker cannot inspect state             | Exposed — DB schema is public to the data layer          |

Use Memento for: in-session operations where sub-millisecond rollback matters, transient state that hasn't been committed yet, or state not represented in the DB (e.g., UI state, in-flight wizard progress). Use DB re-fetch for: cross-session undo, regulatory audit replay, disaster recovery, or any scenario where the state must survive a process restart.

## Section 3: Memento in Node.js / TypeScript / Fintech Context

**Q11. Show a Memento implementation for a multi-step loan application wizard that supports back-navigation without data loss.**
A: A loan application wizard typically has 5–7 steps. Navigating back must restore the exact form state from when that step was completed — Memento is the natural model:

```typescript
// ─── Wizard state ─────────────────────────────────────────────────────────────

interface WizardState {
  currentStep:             number;
  personalDetails:         PersonalDetails | null;
  employmentDetails:       EmploymentDetails | null;
  loanRequirements:        LoanRequirements | null;
  documentUploadStatus:    Record<string, boolean>;
  bureauConsentGiven:      boolean;
  kycVerificationStatus:   "PENDING" | "IN_PROGRESS" | "VERIFIED" | null;
  applicantId:             string | null;
}

// ─── Memento ──────────────────────────────────────────────────────────────────

class WizardMemento {
  readonly stepNumber: number;
  readonly savedAt    = new Date();
  private readonly state: WizardState;

  constructor(state: WizardState) {
    this.stepNumber = state.currentStep;
    this.state      = structuredClone(state);
  }

  getState(): WizardState { return structuredClone(this.state); }
}

// ─── Originator ───────────────────────────────────────────────────────────────

class LoanApplicationWizard {
  private state: WizardState = {
    currentStep:           1,
    personalDetails:       null,
    employmentDetails:     null,
    loanRequirements:      null,
    documentUploadStatus:  {},
    bureauConsentGiven:    false,
    kycVerificationStatus: null,
    applicantId:           null,
  };

  // Step 1: Personal details
  submitPersonalDetails(details: PersonalDetails): void {
    this.state = { ...this.state, personalDetails: details, currentStep: 2 };
  }

  // Step 2: Employment
  submitEmploymentDetails(details: EmploymentDetails): void {
    this.state = { ...this.state, employmentDetails: details, currentStep: 3 };
  }

  // Step 3: Loan requirements
  submitLoanRequirements(requirements: LoanRequirements): void {
    this.state = { ...this.state, loanRequirements: requirements, currentStep: 4 };
  }

  // Step 4: Document upload (incremental updates)
  markDocumentUploaded(docType: string): void {
    this.state = {
      ...this.state,
      documentUploadStatus: { ...this.state.documentUploadStatus, [docType]: true },
    };
  }

  // Step 5: Bureau consent
  giveConsentAndStartKyc(): void {
    this.state = { ...this.state, bureauConsentGiven: true, kycVerificationStatus: "IN_PROGRESS", currentStep: 5 };
  }

  // Snapshot — caretaker calls this before each step transition
  createMemento(): WizardMemento {
    return new WizardMemento(this.state);
  }

  // Restore — caretaker calls this on back-navigation
  restoreFromMemento(memento: WizardMemento): void {
    this.state = memento.getState();
  }

  get currentStep():   number       { return this.state.currentStep; }
  get isComplete():    boolean       { return this.state.kycVerificationStatus === "VERIFIED"; }
  get progressSummary(): string {
    return `Step ${this.state.currentStep} | KYC: ${this.state.kycVerificationStatus ?? "Not started"}`;
  }
}

// ─── Caretaker ────────────────────────────────────────────────────────────────

class WizardNavigationHistory {
  private stepSnapshots: Map<number, WizardMemento> = new Map();

  // Called when the user successfully completes a step
  saveStep(wizard: LoanApplicationWizard): void {
    const memento = wizard.createMemento();
    this.stepSnapshots.set(memento.stepNumber, memento);
  }

  // Called when the user clicks "Back"
  navigateBackTo(step: number, wizard: LoanApplicationWizard): boolean {
    const memento = this.stepSnapshots.get(step);
    if (!memento) return false;
    wizard.restoreFromMemento(memento);
    return true;
  }

  canNavigateTo(step: number): boolean {
    return this.stepSnapshots.has(step);
  }

  get completedSteps(): number[] {
    return [...this.stepSnapshots.keys()].sort((a, b) => a - b);
  }
}

// ─── Usage (NestJS controller / service orchestration) ────────────────────────

class WizardSessionService {
  private wizards   = new Map<string, LoanApplicationWizard>();
  private histories = new Map<string, WizardNavigationHistory>();

  getOrCreate(sessionId: string): { wizard: LoanApplicationWizard; history: WizardNavigationHistory } {
    if (!this.wizards.has(sessionId)) {
      this.wizards.set(sessionId, new LoanApplicationWizard());
      this.histories.set(sessionId, new WizardNavigationHistory());
    }
    return { wizard: this.wizards.get(sessionId)!, history: this.histories.get(sessionId)! };
  }

  submitStep(sessionId: string, stepData: StepData): void {
    const { wizard, history } = this.getOrCreate(sessionId);
    // Save snapshot BEFORE applying step — so navigating back returns to this state
    history.saveStep(wizard);
    wizard.submitStep(stepData);
  }

  navigateBack(sessionId: string, targetStep: number): boolean {
    const { wizard, history } = this.getOrCreate(sessionId);
    return history.navigateBackTo(targetStep, wizard);
  }
}
```

**Q12. How does Memento implement a checkpoint / rollback system for a risky bulk configuration change in a lending platform?**
A:

```typescript
// ─── Originator: RiskEngineConfig ─────────────────────────────────────────────

interface RiskEngineConfigState {
  scoringModel:           string;
  minimumCibilScore:      number;
  maximumLoanToValue:     number;
  maxExposurePerSectorPct: Record<string, number>;
  blacklistedEmployers:   string[];
  autoApprovalThreshold:  number;
  manualReviewThreshold:  number;
  featureFlags:           Record<string, boolean>;
}

class RiskEngineConfigMemento {
  private readonly state: RiskEngineConfigState;
  readonly savedAt   = new Date();
  readonly savedBy:  string;
  readonly changeReason: string;

  constructor(state: RiskEngineConfigState, savedBy: string, changeReason: string) {
    this.state        = structuredClone(state);
    this.savedBy      = savedBy;
    this.changeReason = changeReason;

  private readonly maxCheckpoints = 10;

  constructor(
    private readonly config:         RiskEngineConfig,
    private readonly auditService:   AuditService,
    private readonly alertService:   AlertService,
  ) {}

  // Called before any bulk change session starts
  checkpoint(actorId: string, reason: string): void {
    const memento = this.config.createMemento(actorId, reason);
    this.checkpoints.push(memento);
    if (this.checkpoints.length > this.maxCheckpoints) this.checkpoints.shift();
    console.log(`[checkpoint] Saved config snapshot at ${memento.savedAt.toISOString()}`);
  }

  // Called if the bulk change caused problems (e.g., spike in rejection rates)
  async rollbackToLastCheckpoint(actorId: string): Promise<void> {
    const memento = this.checkpoints.pop();
    if (!memento) throw new Error("No checkpoint to roll back to");

    this.config.restoreFromMemento(memento);

    await this.auditService.record({
      action:     "RiskConfigRolledBack",
      actorId,
      rolledBackTo: memento.savedAt.toISOString(),
      reason:     memento.changeReason,
    });

    await this.alertService.notifyRiskTeam(
      `Risk config rolled back to ${memento.savedAt.toISOString()} by ${actorId}`,
    );
  }

  // Dry-run: apply changes, evaluate impact, then restore checkpoint
  async dryRun<T>(
    actorId: string,
    changes: (config: RiskEngineConfig) => void,
    evaluate: (config: RiskEngineConfig) => T,
  ): Promise<T> {
    const snapshot = this.config.createMemento(actorId, "dry-run");
    try {
      changes(this.config);
      return evaluate(this.config);
    } finally {
      this.config.restoreFromMemento(snapshot);
    }
  }
}
```

**Q14. How does Memento implement a transactional "saga" checkpoint for a multi-step KYC onboarding process?**
A: In a saga (a distributed transaction without a two-phase commit), each step is executed sequentially; if a later step fails, earlier completed steps must be compensated. Memento captures the state *before* each saga step so that partial rollback is possible without re-fetching from external systems:

```typescript

@Injectable()
class KycSagaOrchestrator {
  constructor(
    private readonly panService:      PanVerificationService,
    private readonly aadharService:   AadharVerificationService,
    private readonly faceMatchService: FaceMatchService,
    private readonly bureauService:   CreditBureauService,
    private readonly sagaRepo:        KycSagaRepository,
  ) {}

  async execute(customerId: string): Promise<KycSaga> {
    const saga      = new KycSaga(customerId);
    const checkpoints: KycSagaMemento[] = [];

    // Helper: checkpoint → execute step → catch → rollback
    const step = async (
      name: string,
      action: () => Promise<void>,
      compensate: () => Promise<void>,
    ): Promise<void> => {
      checkpoints.push(saga.createMemento(name));
      try {
        await action();
      } catch (err) {
        console.error(`KYC saga step "${name}" failed:`, err);
        // Restore to the state before this step failed
        const lastCheckpoint = checkpoints[checkpoints.length - 1];
        saga.restoreFromMemento(lastCheckpoint);
        saga.markFailed();
        // Compensate all previously completed steps in reverse
        await this.compensateAll(compensations.slice().reverse());
        throw err;
      }
    };

    const compensations: Array<() => Promise<void>> = [];

    try {
      await step(
        "PAN_VERIFICATION",
        async () => {
          const result = await this.panService.verify(customerId);
          saga.applyPanVerification(result.ref);
          compensations.push(() => this.panService.reverify(customerId));
        },
        async () => { /* no meaningful compensation for PAN */ },
      );

      await step(
        "AADHAR_VERIFICATION",
        async () => {
          const result = await this.aadharService.verify(customerId);
          saga.applyAadharVerification(result.ref);
          compensations.push(() => this.aadharService.cancel(result.ref));
        },
        async () => {},
      );

      await step(
        "FACE_MATCH",
        async () => {
          const result = await this.faceMatchService.match(customerId);
          saga.applyFaceMatch(result.score);
          if (result.score < 0.85) throw new Error("Face match score below threshold");
        },
        async () => {},
      );

      await step(
        "BUREAU_PULL",
        async () => {
          const result = await this.bureauService.pullReport(customerId);
          saga.applyBureauReport(result.ref, result.riskScore);
          compensations.push(() => this.bureauService.markEnquiryStale(result.ref));
        },
        async () => {},
      );

      saga.complete();
    } catch (err) {
      saga.markRolledBack();
    }

    await this.sagaRepo.save(saga);
    return saga;
  }

  private async compensateAll(compensations: Array<() => Promise<void>>): Promise<void> {
    for (const compensate of compensations) {
      try { await compensate(); }
      catch (e) { console.error("Compensation failed:", e); }
    }
  }
}
```

**Q15. How does Memento combine with the Observer pattern to build a real-time collaborative document editor with conflict resolution?**
A: In a collaborative editor (multiple ops agents editing the same loan offer document), each client maintains its own Memento history. When a remote change arrives, the client may need to roll back local un-synced changes, apply the remote change, and re-apply local changes on top — a mini operational transform using Memento for rollback:

```typescript
class CollaborativeEditSession {
  private committedSnapshot: LoanOfferDocumentMemento;
  private localUndoStack:    LoanOfferDocumentMemento[] = [];

  constructor(
    private readonly doc:      LoanOfferDocument,
    private readonly wsClient: WebSocketClient,
    private readonly userId:   string,
  ) {
    this.committedSnapshot = doc.createMemento("initial");
    // Subscribe to remote changes
    wsClient.on("remoteChange", this.handleRemoteChange.bind(this));
  }

  // Local edit: checkpoint before every change
  localEdit(mutation: (doc: LoanOfferDocument) => void): void {
    this.localUndoStack.push(this.doc.createMemento(`local-${Date.now()}`));
    mutation(this.doc);
    this.wsClient.broadcast({ type: "localChange", userId: this.userId, state: this.doc.createMemento("sync") });
  }

  // Remote change arrives from another user
  private handleRemoteChange(remoteMemento: LoanOfferDocumentMemento): void {
    // 1. Save current local state
    const localState = this.doc.createMemento("pre-merge");

    // 2. Roll back to last committed (server-confirmed) state
    this.doc.restoreFromMemento(this.committedSnapshot);

    // 3. Apply the remote (authoritative) change
    this.doc.restoreFromMemento(remoteMemento);
    this.committedSnapshot = remoteMemento;

    // 4. Re-apply local changes on top (simplified — real OT is more complex)
    // For this example, local changes that conflict are discarded (last-write-wins per field)
    this.localUndoStack = [];   // local history invalidated by remote change

    // 5. Notify UI of the merged state
    this.wsClient.emit("stateUpdated", this.doc.createMemento("post-merge"));
  }

  undoLocalEdit(): boolean {
    const memento = this.localUndoStack.pop();
    if (!memento) return false;
    this.doc.restoreFromMemento(memento);
    return true;
  }
}
```

## Section 4: Pitfalls & Anti-patterns

**Q16. What are the most common mistakes when implementing Memento?**
A: Five recurring mistakes:

1. **Shallow copy of nested state** — the memento shares mutable references with the originator. The originator mutates "its" copy, silently corrupting the snapshot. Fix: use `structuredClone` or a recursive deep-copy for any non-primitive state.

2. **Caretaker inspecting memento internals** — the caretaker adds logic like `if (memento.state.currentStep > 3)` — coupling to the originator's structure and breaking encapsulation. Fix: all decisions about state must live in the originator; the caretaker only stores and returns mementos.

3. **Unbounded history growth** — a deep undo stack with full snapshots of large state objects causes gradual memory leak in long-running sessions. Fix: cap the stack at a meaningful depth; use delta mementos for large state; or evict oldest snapshots with a sliding window.

4. **Not clearing redo stack on new action** — after undoing, a new action should invalidate the redo history (branching would create a non-linear history the caretaker cannot manage simply). Fix: `this.redoStack = []` whenever `execute()` is called on a new action.

5. **Restoring from a memento created by a different version of the originator** — the state schema evolves (new fields added, old fields renamed) but old mementos still exist in the DB. Fix: version-stamp every memento and implement migration logic in `fromSerializable()`.

**Q17. How does Memento interact with immutable state patterns, and can it be simplified when the originator uses immutability?**
A: When the originator manages state as an immutable value (a plain object it replaces rather than mutates), Memento simplifies dramatically — the "snapshot" is just a reference to the old immutable value:

```typescript
// ─── Immutable-state originator ───────────────────────────────────────────────

type ImmutableLoanState = Readonly<{
  principalInPaise:   number;
  tenureMonths:       number;
  interestRate:       number;
  status:             "DRAFT" | "SUBMITTED" | "APPROVED" | "DISBURSED";
}>;

class ImmutableLoanApplication {
  private currentState: ImmutableLoanState;
  private history:      ImmutableLoanState[] = [];   // history IS the memento stack

  constructor(initial: ImmutableLoanState) {
    this.currentState = Object.freeze({ ...initial });
  }

  // "Memento" is just the old reference — no copy needed; it's already immutable
  update(changes: Partial<ImmutableLoanState>): void {
    this.history.push(this.currentState);   // old reference is the snapshot
    this.currentState = Object.freeze({ ...this.currentState, ...changes });
  }

  undo(): boolean {
    const previous = this.history.pop();
    if (!previous) return false;
    this.currentState = previous;   // restore reference — no copying needed
    return true;
  }

  get state(): ImmutableLoanState { return this.currentState; }
}
```

With immutable state, the caretaker pattern collapses into the originator itself — the history *is* the array of past immutable state values. No separate Memento or Caretaker class is needed. This is the approach used by Redux, Immer, and similar libraries — the pattern's *intent* is preserved (state capture and restoration without exposing internals) but the *structure* simplifies because immutability eliminates the deep-copy problem entirely.

**Q18. When does Memento violate encapsulation instead of preserving it?**
A: Memento can violate the very encapsulation it's meant to preserve in three ways:

1. **Memento with public getters** — if the memento exposes its stored state via public methods, the caretaker can inspect and potentially reconstruct or manipulate the originator's internal structure. The memento should have zero public data-access methods callable by the caretaker.

2. **Memento subclassed to access state** — a malicious or careless caretaker subclasses the memento and overrides the private-access mechanism. Fix: mark memento classes `final` (or avoid inheritance in the memento hierarchy entirely).

3. **Serialized mementos in an accessible format** — if mementos are serialized to JSON and stored in a Redis key that other services can read, those services gain access to the originator's internal state schema. Fix: encrypt serialized mementos at rest, or store only the key fields and rehydrate from the canonical DB state on restore.

**Q19. How do you handle Memento in a NestJS service that is a singleton — where multiple concurrent requests share the same originator instance?**
A: A NestJS singleton service (`scope: Scope.DEFAULT`) is shared across all requests — concurrent requests racing to modify and snapshot state will produce interleaved, corrupt mementos. Three approaches:

1. **Move the originator to request scope** — annotate with `@Injectable({ scope: Scope.REQUEST })`. Each request gets its own originator instance with its own history. Appropriate for session-scoped workflows (wizards, draft editors).

2. **Separate the mutable originator from the singleton service** — the service is stateless; it creates and returns a fresh originator per operation, with the caller responsible for managing its lifecycle:

```typescript
@Injectable()
class LoanWizardService {
  // Stateless singleton — originators are per-session, not per-service
  createSession(sessionId: string): LoanApplicationWizard {
    return new LoanApplicationWizard();   // caller holds this
  }

  submitStep(wizard: LoanApplicationWizard, history: WizardNavigationHistory, data: StepData): void {
    history.saveStep(wizard);
    wizard.submitStep(data);
  }
}
```

3. **Session store pattern** — originator state (and its memento history) lives in a session store (Redis, DB), serialized on each request end and deserialized on next request start. The service is stateless; state is per-session in the store.

**Q20. How do you test an originator that uses Memento, and what are the common test blind spots?**
A:

```typescript
describe("LoanApplicationWizard with Memento", () => {
  let wizard:  LoanApplicationWizard;
  let history: WizardNavigationHistory;

  beforeEach(() => {
    wizard  = new LoanApplicationWizard();
    history = new WizardNavigationHistory();
  });

  // ─── Core contract ────────────────────────────────────────────────────────

  it("should restore state to the snapshot taken before an edit", () => {
    wizard.submitPersonalDetails({ name: "Ravi", pan: "ABCDE1234F" });
    const memento = wizard.createMemento();
    wizard.submitEmploymentDetails({ employer: "TCS", income: 80000 });

    wizard.restoreFromMemento(memento);

    expect(wizard.currentStep).toBe(2);
    // Employment details should be gone — we restored before submitting them
  });

  // ─── Encapsulation ────────────────────────────────────────────────────────

  it("should not allow external mutation of memento state to affect originator", () => {
    wizard.submitPersonalDetails({ name: "Ravi", pan: "ABCDE1234F" });
    const memento = wizard.createMemento();

    // Attempt to mutate the state returned by getState() (if exposed)
    // The originator should be unaffected
    const state = (memento as any).getState?.();
    if (state) state.currentStep = 999;

    wizard.submitEmploymentDetails({ employer: "TCS", income: 80000 });
    wizard.restoreFromMemento(memento);

    expect(wizard.currentStep).toBe(2);   // not 999
  });

  // ─── Deep copy correctness ─────────────────────────────────────────────────

  it("should not share mutable references between originator and memento", () => {
    wizard.submitPersonalDetails({ name: "Ravi", pan: "ABCDE1234F" });
    wizard.markDocumentUploaded("PAN");
    const memento = wizard.createMemento();

    // Mutate originator state after snapshot
    wizard.markDocumentUploaded("Aadhar");

    wizard.restoreFromMemento(memento);
    const restoredState = (wizard as any).state;

    // Aadhar upload should NOT be in the restored state
    expect(restoredState.documentUploadStatus["Aadhar"]).toBeUndefined();
  });

  // ─── Redo stack cleared on new action ─────────────────────────────────────

  it("should clear redo stack when a new action is taken after undo", () => {
    history.saveStep(wizard);
    wizard.submitPersonalDetails({ name: "Ravi", pan: "ABCDE1234F" });
    history.saveStep(wizard);
    wizard.submitEmploymentDetails({ employer: "TCS", income: 80000 });

    history.navigateBackTo(1, wizard);   // undo
    // New action — redo should no longer be available
    wizard.submitPersonalDetails({ name: "Priya", pan: "XYZAB5678G" });

    expect(history.canNavigateTo(2)).toBe(false);
  });
});
```

Common test blind spots:
- Not testing that **mutations after snapshot** don't affect the memento (the deep-copy correctness test above).
- Not testing **restoration from an empty history** (edge case — should return false or throw gracefully, not crash).
- Not testing **schema migration** for mementos deserialized from older versions.
- Testing only the happy path without verifying that the originator's state is *exactly* the pre-snapshot state, not just approximately correct.

## Section 5: Scenario / System Design Style Questions

**Q21. "You are designing a financial model builder tool — a backoffice app where analysts build loan pricing models by specifying formulas, coefficients, and risk weights. The tool must support unlimited undo, named checkpoints ('save as draft'), and the ability to compare two named checkpoints side by side. How do you design this with Memento?"**
A:

```typescript
// Named checkpoint = labelled memento stored persistently
class ModelCheckpoint {
  readonly checkpointId = crypto.randomUUID();
  private readonly state: PricingModelState;
  readonly createdAt = new Date();

  constructor(
    state: PricingModelState,
    readonly name:      string,
    readonly createdBy: string,
    readonly notes:     string,
  ) {
    this.state = structuredClone(state);
    Object.freeze(this);
  }

  getState(): PricingModelState { return structuredClone(this.state); }
}

class PricingModelEditor {
  private state: PricingModelState;
  private undoStack:    PricingModelState[] = [];  // immutable-style: states directly
  private checkpoints:  Map<string, ModelCheckpoint> = new Map();

  constructor(initial: PricingModelState) { this.state = structuredClone(initial); }

  // Every edit pushes the old state onto the undo stack
  updateCoefficient(name: string, value: number): void {
    this.undoStack.push(this.state);
    this.state = { ...this.state, coefficients: { ...this.state.coefficients, [name]: value } };
  }

  undo(): boolean {
    const previous = this.undoStack.pop();
    if (!previous) return false;
    this.state = previous;
    return true;
  }

  // Named checkpoint — persisted separately from undo stack
  saveCheckpoint(name: string, createdBy: string, notes: string): ModelCheckpoint {
    const checkpoint = new ModelCheckpoint(this.state, name, createdBy, notes);
    this.checkpoints.set(checkpoint.checkpointId, checkpoint);
    return checkpoint;
  }

  restoreCheckpoint(checkpointId: string): void {
    const cp = this.checkpoints.get(checkpointId);
    if (!cp) throw new Error(`Checkpoint ${checkpointId} not found`);
    this.undoStack.push(this.state);  // allow undoing the restore itself
    this.state = cp.getState();
  }

  // Side-by-side comparison: returns diff between two checkpoints
  compareCheckpoints(idA: string, idB: string): PricingModelDiff {
    const stateA = this.checkpoints.get(idA)?.getState();
    const stateB = this.checkpoints.get(idB)?.getState();
    if (!stateA || !stateB) throw new Error("One or both checkpoints not found");
    return computeDiff(stateA, stateB);
  }

  listCheckpoints(): ModelCheckpoint[] {
    return [...this.checkpoints.values()].sort((a, b) => a.createdAt.getTime() - b.createdAt.getTime());
  }
}
```

**Q22. "During a prod incident, a risk configuration change caused a spike in auto-approval rates. The change was applied 3 days ago across a rolling deploy. How does a Memento-based checkpoint system help you recover, and what are its limits?"**
A: If the risk config system used persistent Mementos (serialized to DB with timestamps), recovery is:

1. **Identify the pre-change checkpoint** — query `SELECT * FROM config_mementos WHERE originator_id = 'risk-engine-config' AND saved_at < '<deploy-timestamp>' ORDER BY saved_at DESC LIMIT 1`.
2. **Deserialize and restore** — `CommandFactory.fromRecord(record)` reconstructs the memento; `riskConfig.restoreFromMemento(memento)` applies the rollback.
3. **Audit** — the restoration is itself recorded as a new checkpoint with `reason: "Incident rollback — auto-approval spike"` so the audit trail is unbroken.

**Limits of Memento-based recovery in this scenario:**
- **Three days of approvals are already committed** — the Memento restores the configuration, but the 3 days of auto-approved loans exist in the DB. Memento rolls back configuration state, not downstream side effects. Each over-approved loan must be reviewed separately.
- **Multiple config changes may have occurred in 3 days** — the checkpoint immediately before the bad deploy is the correct target; restoring to an arbitrary past checkpoint could revert *other* valid changes made in between. Checkpoints must be granular and well-labeled.
- **Cross-service state** — if the risk score service, the approval service, and the notification service each cached the config, restoring the Memento in the config service does not automatically flush those caches. A cache invalidation broadcast must accompany the restore.

The lesson: Memento is a surgical tool for state rollback, not a full incident recovery mechanism. Pair it with event sourcing (to replay only the valid downstream decisions) and proper cache invalidation.

**Q23. "A junior engineer proposes storing the entire loan application object (including a 2 MB document metadata array) in the Memento on every keystroke in a 50-step wizard. What do you advise?"**
A: This is the unbounded-snapshot anti-pattern — a full 2 MB snapshot per keystroke in a long-form wizard will exhaust the heap rapidly and cause GC pauses. Walk through the advice:

1. **Separate high-frequency from low-frequency state** — keystrokes affect text fields, not document metadata. Split the originator into a `FormFieldsOriginator` (snapshots on keystroke — small) and a `DocumentMetadataOriginator` (snapshots only on document add/remove — rare and large). Apply Memento selectively.

2. **Coalesce rapid snapshots** — don't snapshot on every keystroke; snapshot on meaningful boundaries (focus-out, step completion, a debounced 2-second idle timer). A text field going from "Ravi" to "Ravi K" to "Ravi Ku" to "Ravi Kumar" only needs one snapshot at "Ravi Kumar" for undo to be useful.

3. **Use delta mementos for text fields** — store the cursor position and the character(s) added/deleted per operation, not the full field content. For a 1000-character field, the delta is 1–5 bytes per keystroke; the full snapshot is 1000 bytes.

4. **Cap the undo stack** — at most 50 undo steps is meaningful for a wizard; beyond that, evict the oldest snapshot. Store the cap in the caretaker, not the originator.

5. **For document metadata** — never store the file content in the Memento. Store only the metadata record (filename, MIME type, upload reference ID). The actual file lives in object storage (S3 / GCS); the reference is a small string.

**Q24. "You're building a trading strategy backtester. Analysts run simulations over 10 years of historical data. Mid-simulation, they want to 'branch' — try two different parameter sets from the same point and compare results. How does Memento support this?"**
A: Branching from a mid-point is Memento's sweet spot — the simulation state at the branch point is captured once; two separate simulation continuations run from clones of that state:

```typescript
class BacktestSimulation {
  private state: SimulationState;

  constructor(initial: SimulationState) { this.state = structuredClone(initial); }

  tick(marketData: MarketTick): void {
    // Advance simulation by one tick — update positions, P&L, drawdown, etc.
    this.state = advanceSimulation(this.state, marketData);
  }

  createBranchPoint(): SimulationMemento {
    return new SimulationMemento(this.state);
  }

  restoreFromBranchPoint(memento: SimulationMemento): void {
    this.state = memento.getState();
  }

  get currentState(): Readonly<SimulationState> { return this.state; }
}

class SimulationMemento {
  private readonly state: SimulationState;
  readonly capturedAt = new Date();

  constructor(state: SimulationState) {
    this.state = structuredClone(state);   // deep copy — simulation state is complex
    Object.freeze(this);
  }

  getState(): SimulationState { return structuredClone(this.state); }
}

// ─── Branching orchestration ─────────────────────────────────────────────────

class BacktestOrchestrator {
  async runWithBranch(
    baseSimulation: BacktestSimulation,
    marketData:     MarketTick[],
    branchAt:       number,   // index in marketData
    paramSetA:      StrategyParams,
    paramSetB:      StrategyParams,
  ): Promise<{ branchA: SimulationState; branchB: SimulationState }> {
    // Run base simulation up to the branch point
    for (let i = 0; i < branchAt; i++) {
      baseSimulation.tick(marketData[i]);
    }

    // Capture branch point — one snapshot
    const branchPoint = baseSimulation.createBranchPoint();

    // Branch A: continue from branch point with paramSetA
    const simA = new BacktestSimulation(branchPoint.getState());
    simA.applyParams(paramSetA);
    for (let i = branchAt; i < marketData.length; i++) simA.tick(marketData[i]);

    // Branch B: restore branch point and continue with paramSetB
    const simB = new BacktestSimulation(branchPoint.getState());
    simB.applyParams(paramSetB);
    for (let i = branchAt; i < marketData.length; i++) simB.tick(marketData[i]);

    return { branchA: simA.currentState, branchB: simB.currentState };
  }
}
```

The single `branchPoint` memento enables two diverging simulation runs without running the common prefix twice, without copying the full simulation at the start, and without coupling the two branches to each other.

**Q25. "How would you explain the Memento pattern to a new engineer joining a fintech team, using an example they'll see in the codebase on day one?"**
A: A grounded, practical explanation:

> "You know how in our loan application wizard, users can go back to Step 2 even after filling out Step 5, and all the Step 2 data is still there exactly as they left it? That's Memento.
>
> The `LoanApplicationWizard` class owns all the application data — PAN details, employment info, document uploads. We deliberately don't make those fields public, because other parts of the codebase should not be able to poke around in them. But we still need to be able to save where the user was and restore it on back-navigation.
>
> So the wizard has two methods: `createMemento()` — which packages up a private snapshot of its current state into an opaque object — and `restoreFromMemento(memento)` — which unpacks that snapshot and resets itself. The wizard is the only thing that can read inside that snapshot. The navigation controller just holds onto the snapshot like a sealed envelope — it doesn't open it, it just hands it back.
>
> That's the whole pattern: the object that owns the state creates the snapshot, the caller stores it without inspecting it, and when you need to go back, you hand the envelope to the object and it restores itself. The data stays protected, the back-navigation works perfectly, and neither side needs to know the other's implementation details.
>
> You'll see it in three places in our codebase: the wizard back-navigation, the risk config checkpoint/rollback system, and the CMS draft/publish editor. Same idea, three different shapes."
