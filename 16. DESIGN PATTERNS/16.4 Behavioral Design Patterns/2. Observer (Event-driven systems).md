# Design Patterns — Behavioral: Observer (Event-Driven Systems) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Observer pattern?**
A: The Observer pattern is a behavioral design pattern that defines a one-to-many dependency between objects so that when one object (the *subject* or *publisher*) changes state, all its dependents (the *observers* or *subscribers*) are notified and updated automatically. The subject doesn't know *who* its observers are or *what* they'll do with the notification — it just broadcasts the event. Observers register interest and react independently. The GoF definition: *"Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically."*

It is the foundational pattern behind every event-driven system: DOM events, Node.js `EventEmitter`, reactive streams, message queues, WebSocket broadcasts, and microservice event buses.

**Q2. What problem does the Observer pattern solve?**
A: It solves the problem of *tight coupling between a producer of state changes and the consumers of those changes*. Without Observer, a `LoanService` that approves a loan must explicitly call every downstream system that cares:

```ts
// WITHOUT Observer — LoanService knows about every downstream concern
async approveLoan(loanId: string): Promise<void> {
  const loan = await this.loanRepo.save(approved);
  await this.notificationService.sendApprovalSms(loan.userId);   // coupled
  await this.auditService.logApproval(loan);                      // coupled
  await this.analyticsService.trackConversion(loan);              // coupled
  await this.disbursementService.scheduleDisbursement(loan);      // coupled
}
```

Every new downstream requirement means editing `LoanService`. It accumulates unrelated responsibilities, its test setup requires every downstream mock, and a failure in `analyticsService` can abort the entire approval flow.

With Observer, `LoanService` emits `LoanApproved` and stops. Every downstream system subscribes independently — `LoanService` has no knowledge of them, no dependency on them, and no responsibility for their behavior.

**Q3. What are the four participants in the Observer pattern?**
A:
- **Subject (Publisher/Observable)** — maintains a list of observers, provides `subscribe`/`unsubscribe` methods, and notifies all registered observers when state changes.
- **Observer (Subscriber/Listener)** — defines the update interface that subjects call when notifying. Each concrete observer implements its own reaction.
- **ConcreteSubject** — the actual object whose state changes trigger notifications. Stores state and calls `notify()` on state change.
- **ConcreteObserver** — a specific observer that reacts to the subject's notifications in a particular way (send SMS, write audit log, trigger disbursement, etc.).

**Q4. What is the difference between Push and Pull notification models in Observer?**
A: The two models describe how observers receive data when notified:

- **Push model** — the subject passes event data directly to the observer's update method. Observers receive everything the subject decides to send, whether they need it or not.
  ```ts
  interface Observer {
    onLoanApproved(event: LoanApprovedEvent): void; // data pushed in
  }
  ```
- **Pull model** — the subject notifies observers with a minimal signal (often just a reference to itself), and observers pull the specific data they need from the subject.
  ```ts
  interface Observer {
    update(subject: LoanSubject): void; // observer pulls: subject.getLoan(), subject.getStatus()
  }
  ```

| Aspect              | Push                                        | Pull                                              |
|---                  |---                                          |---                                                |
| Coupling            | Observers coupled to event shape            | Observers coupled to subject's query interface    |
| Efficiency          | May send unwanted data                      | Observers fetch only what they need               |
| Stale data risk     | Low — data is current at notify time        | Higher — subject state may change before pull     |
| Flexibility         | Lower — event schema is fixed               | Higher — observers choose what to read            |
| Common in practice  | Event-driven systems, message queues, DOM   | Legacy Observer, some reactive streams            |

Modern event-driven systems almost universally use the **push model** — the event payload carries all the data observers need. This avoids re-querying a potentially changed subject and keeps observers stateless.

**Q5. What is the difference between Observer pattern and Pub/Sub pattern?**
A: They solve the same problem but at different levels of coupling:

| Aspect               | Observer (GoF)                                    | Pub/Sub                                              |
|---                   |---                                                |---                                                   |
| Coupling             | Subject knows its observers (holds references)    | Publishers and subscribers don't know each other     |
| Intermediary         | None — subject calls observer directly            | Message broker / event bus mediates all communication |
| Sync / Async         | Typically synchronous                             | Typically asynchronous                               |
| Cross-process?       | Same process only                                 | Cross-process, cross-service, cross-network          |
| Example              | Node.js `EventEmitter`, DOM `addEventListener`    | Kafka, RabbitMQ, AWS SNS/SQS, Redis Pub/Sub          |
| Filtering            | All observers get all events from subject         | Subscribers filter by topic/queue/routing key        |

Observer is the in-process, synchronous version. Pub/Sub is the distributed, asynchronous version with a broker in between. Kafka topics, NestJS `EventEmitter2`, and Redis Pub/Sub are all Pub/Sub — they implement the Observer *concept* but with a decoupling intermediary that the GoF pattern doesn't include. In practice at 5 YOE, you work with both and should know the distinction.

## Section 2: Implementation

**Q6. What does a canonical Observer implementation look like in TypeScript?**
A:
```ts
// Event types — the "push" payload
interface LoanApprovedEvent {
  loanId: string;
  userId: string;
  amount: number;
  approvedAt: Date;
  approvedBy: string;
}

// Observer interface
interface LoanEventObserver {
  onLoanApproved(event: LoanApprovedEvent): Promise<void>;
}

// Subject — manages observers and emits events
class LoanEventSubject {
  private observers: LoanEventObserver[] = [];

  subscribe(observer: LoanEventObserver): void {
    this.observers.push(observer);
  }

  unsubscribe(observer: LoanEventObserver): void {
    this.observers = this.observers.filter(o => o !== observer);
  }

  async notify(event: LoanApprovedEvent): Promise<void> {
    await Promise.allSettled(
      this.observers.map(o => o.onLoanApproved(event))
    );
    // allSettled — one observer failing doesn't abort others
  }
}

// ConcreteSubject — business logic that emits events
class LoanApprovalService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly events: LoanEventSubject,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    loan.approve(approverId);
    await this.loanRepo.save(loan);

    await this.events.notify({
      loanId: loan.id,
      userId: loan.userId,
      amount: loan.amount,
      approvedAt: new Date(),
      approvedBy: approverId,
    });
    // LoanApprovalService has zero knowledge of what happens next
  }
}

// ConcreteObserver 1 — sends SMS notification
class SmsNotificationObserver implements LoanEventObserver {
  constructor(private readonly smsService: SmsService) {}

  async onLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.smsService.send(event.userId,
      `Your loan of ₹${event.amount} has been approved!`
    );
  }
}

// ConcreteObserver 2 — writes audit log
class AuditObserver implements LoanEventObserver {
  constructor(private readonly auditRepo: AuditRepository) {}

  async onLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.auditRepo.log({
      action: "LOAN_APPROVED",
      entityId: event.loanId,
      performedBy: event.approvedBy,
      timestamp: event.approvedAt,
    });
  }
}

// ConcreteObserver 3 — schedules disbursement
class DisbursementObserver implements LoanEventObserver {
  constructor(private readonly disbursementService: DisbursementService) {}

  async onLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.disbursementService.schedule(event.loanId, event.amount);
  }
}

// Wired at composition root
const events = new LoanEventSubject();
events.subscribe(new SmsNotificationObserver(smsService));
events.subscribe(new AuditObserver(auditRepo));
events.subscribe(new DisbursementObserver(disbursementService));

const approvalService = new LoanApprovalService(loanRepo, events);
```

**Q7. Why use `Promise.allSettled` instead of `Promise.all` when notifying observers?**
A: `Promise.all` fails fast — if any observer throws, the remaining observers are not awaited and their results are discarded. In an event notification context this is almost always wrong: a failure in `SmsNotificationObserver` should not prevent `AuditObserver` and `DisbursementObserver` from running. The loan was approved — every downstream system should be notified regardless of individual failures.

`Promise.allSettled` runs all observers to completion (fulfilled or rejected) and returns an array of results. The subject can inspect results and log failures without blocking others:

```ts
async notify(event: LoanApprovedEvent): Promise<void> {
  const results = await Promise.allSettled(
    this.observers.map(o => o.onLoanApproved(event))
  );

  results.forEach((result, i) => {
    if (result.status === "rejected") {
      logger.error({
        observer: this.observers[i].constructor.name,
        event,
        error: result.reason,
      }, "Observer failed during loan approval notification");
    }
  });
}
```
One observer's failure is logged and monitored but doesn't cascade into a loan approval failure. This is the correct production behavior for event notifications.

**Q8. How do you implement a typed, generic EventEmitter in TypeScript?**
A:
```ts
type EventMap = Record<string, unknown>;
type EventHandler<T> = (payload: T) => Promise<void> | void;

class TypedEventEmitter<Events extends EventMap> {
  private handlers = new Map<keyof Events, Set<EventHandler<unknown>>>();

  on<K extends keyof Events>(event: K, handler: EventHandler<Events[K]>): () => void {
    if (!this.handlers.has(event)) {
      this.handlers.set(event, new Set());
    }
    this.handlers.get(event)!.add(handler as EventHandler<unknown>);

    // Return unsubscribe function
    return () => this.off(event, handler);
  }

  off<K extends keyof Events>(event: K, handler: EventHandler<Events[K]>): void {
    this.handlers.get(event)?.delete(handler as EventHandler<unknown>);
  }

  async emit<K extends keyof Events>(event: K, payload: Events[K]): Promise<void> {
    const handlers = this.handlers.get(event);
    if (!handlers) return;

    const results = await Promise.allSettled(
      [...handlers].map(h => h(payload))
    );

    results.forEach((result, i) => {
      if (result.status === "rejected") {
        logger.error({ event: String(event), error: result.reason }, "Event handler failed");
      }
    });
  }
}

// Define event schema — fully type-safe
type LoanEvents = {
  "loan.approved":  { loanId: string; userId: string; amount: number; approvedAt: Date };
  "loan.rejected":  { loanId: string; userId: string; reason: string };
  "loan.disbursed": { loanId: string; transactionId: string; disbursedAt: Date };
  "repayment.due":  { loanId: string; userId: string; dueDate: Date; amountDue: number };
};

const emitter = new TypedEventEmitter<LoanEvents>();

// TypeScript enforces payload shape per event — wrong shape is a compile error
const unsubscribe = emitter.on("loan.approved", async ({ loanId, userId, amount }) => {
  await smsService.send(userId, `Loan ${loanId} of ₹${amount} approved`);
});

await emitter.emit("loan.approved", {
  loanId: "L001", userId: "U123", amount: 50000, approvedAt: new Date()
});

unsubscribe(); // clean removal — returned from .on()
```
The returned unsubscribe function (closure) is cleaner than passing the handler reference to `.off()` — callers don't need to keep a reference to the handler just to unsubscribe later.

**Q9. What is the "lapsed listener" problem, and how do you prevent it?**
A: The lapsed listener problem (also called observer memory leak) occurs when an observer registers with a subject but is never unsubscribed, even after it's no longer needed. The subject holds a reference to the observer, preventing it from being garbage collected. In long-running Node.js services, this causes memory growth over time.

Common scenarios:
- A per-request observer registered at request start but not removed at request end.
- UI components that subscribe to global events but don't clean up on unmount (React `useEffect` without a cleanup function).
- Test suites that register handlers but don't tear them down between tests — causing cross-test interference.

Defenses:
```ts
// 1. Return unsubscribe from subscribe (Q8 approach) — enforces cleanup
const unsubscribe = emitter.on("loan.approved", handler);
// Later:
unsubscribe();

// 2. WeakRef observers — subject holds weak references; GC can collect observers
class WeakObserverSubject {
  private observers: WeakRef<LoanEventObserver>[] = [];

  subscribe(observer: LoanEventObserver): void {
    this.observers.push(new WeakRef(observer));
  }

  async notify(event: LoanApprovedEvent): Promise<void> {
    this.observers = this.observers.filter(ref => ref.deref() !== undefined);
    await Promise.allSettled(
      this.observers.map(ref => ref.deref()?.onLoanApproved(event))
    );
  }
}

// 3. One-time subscription — auto-unsubscribes after first notification
emitter.once("loan.approved", async (event) => {
  // fires once, then automatically removed
});

// 4. Scoped subscriptions — tied to a lifecycle
class RequestScopedEventManager {
  private unsubscribers: Array<() => void> = [];

  on<K extends keyof LoanEvents>(event: K, handler: EventHandler<LoanEvents[K]>): void {
    this.unsubscribers.push(emitter.on(event, handler));
  }

  dispose(): void {
    this.unsubscribers.forEach(fn => fn()); // clean all at once
    this.unsubscribers = [];
  }
}
```

## Section 3: Observer in Node.js — EventEmitter

**Q10. How does Node.js `EventEmitter` implement the Observer pattern?**
A: `EventEmitter` is Node.js's built-in Observer implementation. Every event-driven Node.js API — HTTP server, file streams, database clients — extends it:

```ts
import { EventEmitter } from "events";

// Subject — extends EventEmitter
class LoanApprovalService extends EventEmitter {
  constructor(private readonly loanRepo: LoanRepository) {
    super();
  }

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    loan.approve(approverId);
    await this.loanRepo.save(loan);

    // Notify all observers
    this.emit("loan:approved", {
      loanId: loan.id,
      userId: loan.userId,
      amount: loan.amount,
      approvedAt: new Date(),
      approvedBy: approverId,
    });
  }
}

// Register observers
const approvalService = new LoanApprovalService(loanRepo);

approvalService.on("loan:approved", async (event) => {
  await smsService.send(event.userId, `Loan approved: ₹${event.amount}`);
});

approvalService.on("loan:approved", async (event) => {
  await auditRepo.log({ action: "LOAN_APPROVED", entityId: event.loanId });
});

// One-time listener
approvalService.once("loan:approved", (event) => {
  console.log("First loan approval since startup:", event.loanId);
});

// Cleanup
approvalService.removeListener("loan:approved", specificHandler);
approvalService.removeAllListeners("loan:approved");
```

Key `EventEmitter` behaviors to know for interviews:
- **`setMaxListeners(n)`** — default is 10 listeners per event; exceeding it logs a warning (memory leak suspicion). Increase for legitimate use cases.
- **`error` event is special** — if an `error` event is emitted with no listeners, Node.js throws an uncaught exception and the process crashes. Always `emitter.on("error", handler)`.
- **Listeners execute synchronously in registration order** — `emit()` calls each listener synchronously. For async listeners, the emitter doesn't await them — fire-and-forget.
- **`EventEmitter` is synchronous** — `this.emit("loan:approved", event)` returns only after all synchronous listeners have been called. Async listeners run but aren't awaited.

**Q11. What is the async listener problem with Node.js `EventEmitter` and how do you handle it?**
A: `EventEmitter.emit()` is synchronous — it calls each listener and returns. Async listeners (`async function`) are called but their returned `Promise` is neither awaited nor observed:

```ts
// PROBLEM — unhandled Promise, errors are silently swallowed
emitter.on("loan:approved", async (event) => {
  await smsService.send(event.userId, "Approved"); // if this throws, nobody knows
});

emitter.emit("loan:approved", event); // returns true immediately; async work is fire-and-forget
```

Three approaches to handle this correctly:

```ts
// 1. Wrap async listeners with error handling — simplest
emitter.on("loan:approved", (event) => {
  smsService.send(event.userId, "Approved")
    .catch(err => logger.error({ err, event }, "SMS notification failed"));
});

// 2. Custom async-aware emitter — awaits all listeners
class AsyncEventEmitter extends EventEmitter {
  async emitAsync(event: string, ...args: unknown[]): Promise<void> {
    const listeners = this.rawListeners(event);
    const results = await Promise.allSettled(
      listeners.map(listener => Promise.resolve(listener(...args)))
    );
    results.forEach(r => {
      if (r.status === "rejected") logger.error({ event, error: r.reason });
    });
  }
}

// 3. Use EventEmitter2 (NestJS default) or a typed emitter that handles async
// EventEmitter2 supports wildcards, namespaces, and async listeners natively
```

In production NestJS services, option 3 is the practical choice — NestJS's built-in `EventEmitter2` handles async listeners correctly and integrates with the DI container.

**Q12. How does NestJS `EventEmitter2` implement Observer pattern at the framework level?**
A: NestJS uses `EventEmitter2` (a superset of Node's `EventEmitter`) and exposes it through decorators that integrate with DI:

```ts
// Setup
@Module({
  imports: [EventEmitterModule.forRoot({
    wildcard: true,          // enables 'loan.*' pattern matching
    delimiter: ".",          // namespace separator
    maxListeners: 20,
    verboseMemoryLeak: true, // warns on listener accumulation
  })],
})
export class AppModule {}

// Publisher — inject EventEmitter2
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly eventEmitter: EventEmitter2,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    loan.approve(approverId);
    await this.loanRepo.save(loan);

    this.eventEmitter.emit("loan.approved", new LoanApprovedEvent(loan, approverId));
  }
}

// Subscribers — use @OnEvent decorator; NestJS handles registration/cleanup
@Injectable()
export class NotificationListener {
  constructor(private readonly smsService: SmsService) {}

  @OnEvent("loan.approved")
  async handleLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.smsService.send(event.userId, `Loan ₹${event.amount} approved`);
  }

  @OnEvent("loan.*")  // wildcard — handles loan.approved, loan.rejected, loan.disbursed
  async handleAnyLoanEvent(event: LoanApprovedEvent): Promise<void> {
    await this.auditRepo.log({ action: "LOAN_EVENT", entityId: event.loanId });
  }
}

@Injectable()
export class DisbursementListener {
  constructor(private readonly disbursementService: DisbursementService) {}

  @OnEvent("loan.approved", { async: true }) // explicitly async-aware
  async handleLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.disbursementService.schedule(event.loanId, event.amount);
  }
}
```
`@OnEvent` is NestJS's declarative observer registration — no manual `subscribe`/`unsubscribe` boilerplate. The DI container manages listener lifecycle, and `{ async: true }` ensures async handlers are properly awaited and errors are captured.

## Section 4: Observer in Distributed Systems — Kafka & Event Sourcing

**Q13. How does Kafka implement the Observer pattern at the distributed systems level?**
A: Kafka is the Observer pattern scaled to distributed, persistent, multi-consumer, multi-producer messaging. The mapping:

| Observer Pattern     | Kafka Equivalent                                             |
|---                   |---                                                           |
| Subject / Publisher  | Kafka Producer                                               |
| Observer / Subscriber| Kafka Consumer (within a Consumer Group)                     |
| Event / Notification | Kafka Message (in a Topic Partition)                         |
| `notify()` call      | `producer.send({ topic, messages: [{ value }] })`           |
| `subscribe()`        | Consumer group subscribes to a topic                         |
| Event bus / broker   | Kafka Broker (the intermediary — pure Pub/Sub)               |

Key differences from in-process Observer:
- **Persistence** — Kafka retains messages for a configurable retention period. Late-joining consumers can replay past events.
- **Consumer groups** — multiple consumers in the same group load-balance messages (each message goes to one consumer). Different groups each receive every message (fan-out).
- **Backpressure** — slow consumers fall behind their offset; they don't slow down the producer or other consumer groups.
- **Ordering** — guaranteed within a partition; no global ordering guarantee across partitions.

```ts
// Producer — the "subject" in distributed Observer
const producer = kafka.producer();
await producer.connect();

await producer.send({
  topic: "loan-events",
  messages: [{
    key: loanId,              // partitioning key — same loanId always goes to same partition
    value: JSON.stringify({
      type: "LOAN_APPROVED",
      loanId,
      userId,
      amount,
      approvedAt: new Date().toISOString(),
    }),
    headers: { "correlation-id": requestId },
  }],
});

// Consumer group A — notification service
const notificationConsumer = kafka.consumer({ groupId: "notification-service" });
await notificationConsumer.subscribe({ topic: "loan-events", fromBeginning: false });

await notificationConsumer.run({
  eachMessage: async ({ message }) => {
    const event = JSON.parse(message.value!.toString());
    if (event.type === "LOAN_APPROVED") {
      await smsService.send(event.userId, `Loan ₹${event.amount} approved`);
    }
  },
});

// Consumer group B — audit service (receives the SAME messages independently)
const auditConsumer = kafka.consumer({ groupId: "audit-service" });
// Each consumer group maintains its own offset — fully independent processing
```

**Q14. What is Event Sourcing and how does it relate to Observer?**
A: Event Sourcing is an architectural pattern where state changes are stored as a sequence of immutable events (the event log is the source of truth), and the current state is derived by replaying events. Observer is the mechanism by which those events are broadcast to interested parties.

They relate as follows:
- **Event Sourcing** answers: *how is state stored?* (as events, not as current state snapshots).
- **Observer / Pub/Sub** answers: *how are other systems notified of those events?*

```ts
// Event Sourcing — events are the source of truth
class LoanAggregate {
  private events: DomainEvent[] = [];
  private status: LoanStatus = "PENDING";
  private amount: number = 0;

  // Command — produces an event
  approve(approverId: string): void {
    const event = new LoanApprovedEvent(this.id, approverId, new Date());
    this.apply(event);      // update in-memory state
    this.events.push(event); // record for persistence
  }

  // Projection — how events rebuild state
  private apply(event: DomainEvent): void {
    if (event instanceof LoanApprovedEvent) {
      this.status = "APPROVED";
    }
  }

  // After saving events to the event store, publish to Observer/Pub-Sub
  getUnpublishedEvents(): DomainEvent[] {
    return [...this.events];
  }
}

// After persisting events, publish them — Observer subscribers react
await eventStore.save(loan.getUnpublishedEvents());
await eventBus.publishAll(loan.getUnpublishedEvents()); // triggers observers
```

The Outbox Pattern (Q22) addresses the gap: ensuring events are both saved to the DB and published to the event bus atomically.

**Q15. What is the difference between domain events and integration events?**
A:
- **Domain events** — events that are meaningful within a bounded context / service. They capture *something that happened* in the domain model: `LoanApproved`, `RepaymentReceived`, `UserDeactivated`. They're used within the same service (in-process Observer, NestJS `EventEmitter2`) to decouple internal components. They may contain rich domain objects.
- **Integration events** — events published *across* service boundaries (to Kafka, SNS, RabbitMQ). They must be stable, versioned contracts — other services depend on their schema. They contain only serializable, primitive data (no domain objects). They're explicitly versioned (`LoanApprovedV2`).

```ts
// Domain event — rich, internal, in-process
class LoanApprovedDomainEvent {
  constructor(
    public readonly loan: Loan,          // full domain object — OK internally
    public readonly approvedBy: User,    // domain object
    public readonly timestamp: Date,
  ) {}
}

// Integration event — serializable, versioned, cross-service contract
class LoanApprovedIntegrationEventV1 {
  readonly eventType = "loan.approved.v1";
  constructor(
    public readonly loanId: string,       // primitive — serializable
    public readonly userId: string,
    public readonly amountInPaise: number, // explicit unit to avoid ambiguity
    public readonly approvedAt: string,   // ISO string — no Date objects across wire
    public readonly approvedById: string, // ID only — not the User object
  ) {}
}
```

The translation layer between domain events and integration events is a critical design point: not every domain event should be published externally, and integration events may need to aggregate or reshape domain event data.

## Section 5: Reactive Observer — RxJS

**Q16. How does RxJS implement the Observer pattern, and when should you use it over EventEmitter?**
A: RxJS is a library for reactive programming built on the Observer pattern. Its core types map directly:

| Observer Pattern | RxJS Equivalent                                        |
|---               |---                                                     |
| Subject          | `Observable` — the stream of values                   |
| Observer         | `Observer` / `Subscriber` — `{ next, error, complete }` |
| `subscribe()`    | `observable.subscribe(observer)`                       |
| `notify()`       | `observer.next(value)` / `subject.next(value)`         |
| `unsubscribe()`  | `subscription.unsubscribe()`                           |

```ts
import { Subject, Observable, filter, map, debounceTime, switchMap } from "rxjs";

// Subject — both Observable and Observer (can emit and be subscribed to)
const loanEvents$ = new Subject<LoanApprovedEvent>();

// Subscribers with operators — the power over plain EventEmitter
loanEvents$.pipe(
  filter(event => event.amount > 100_000),     // only large loans
  debounceTime(500),                           // wait for burst to settle
  map(event => ({                              // transform
    ...event,
    amountInLakhs: event.amount / 100_000,
  }))
).subscribe({
  next: async (event) => {
    await riskTeam.alert(`Large loan approved: ₹${event.amount}`);
  },
  error: (err) => logger.error(err),
  complete: () => logger.info("Stream completed"),
});

// Emit events
loanEvents$.next({ loanId: "L001", userId: "U1", amount: 500_000, approvedAt: new Date() });
```

Use RxJS over EventEmitter when:
- You need **stream operators** — `filter`, `map`, `debounceTime`, `throttleTime`, `switchMap`, `mergeMap`, `combineLatest`.
- You need to **compose multiple event streams** — merge loan events and repayment events into a single notification stream.
- You need **backpressure handling** — control the rate at which events are processed.
- You're in **NestJS** — it uses RxJS Observables natively in interceptors, guards, and microservice message handlers.

Use plain EventEmitter when: the use case is simple (fire-and-forget events with no transformation), you don't want the RxJS dependency, or you're working in a non-NestJS Node.js context.

**Q17. What is an RxJS `Subject` vs a plain `Observable`, and when do you use each?**
A:
- **`Observable`** — a lazy, cold stream. It produces values only when subscribed to; each subscriber gets its own independent execution. Values are derived from a producer function, not pushed externally.
- **`Subject`** — a hot stream that is both an `Observable` and an `Observer`. You can call `.next(value)` to push values imperatively. All current subscribers receive the same value at the same time. Missed values (from before subscription) are lost.
- **`BehaviorSubject`** — a `Subject` that holds the current value and immediately emits it to new subscribers. Use for state (current loan status, current user).
- **`ReplaySubject(n)`** — buffers the last `n` values and replays them to new subscribers. Use when late subscribers need recent history.

```ts
// BehaviorSubject — holds current state
const loanStatus$ = new BehaviorSubject<LoanStatus>("PENDING");

loanStatus$.subscribe(status => console.log("Status:", status));
// Immediately prints: "Status: PENDING"

loanStatus$.next("APPROVED");
// Prints: "Status: APPROVED"

// Late subscriber gets current value immediately
loanStatus$.subscribe(status => console.log("Late subscriber:", status));
// Immediately prints: "Late subscriber: APPROVED"

// ReplaySubject — late subscribers get recent history
const recentEvents$ = new ReplaySubject<LoanApprovedEvent>(5); // buffer last 5
```

## Section 6: Pitfalls & Anti-patterns

**Q18. What is the "God Subject" anti-pattern?**
A: A God Subject is a single event subject that emits every type of event in the system, causing all observers to receive all events regardless of interest:

```ts
// ANTI-PATTERN — one emitter for everything
class ApplicationEventBus {
  emit(eventType: string, data: unknown): void { /* ... */ }
}

// All observers receive ALL events — must filter manually
eventBus.on("*", (eventType, data) => {
  if (eventType === "loan.approved") { /* handle */ }
  if (eventType === "repayment.received") { /* handle */ }
  if (eventType === "user.created") { /* ignore */ }
  // ... 20 more cases
});
```
Problems: observers are coupled to the event bus's entire event space; adding a new event type requires checking all observers for unintended matches; the bus becomes a bottleneck and single point of failure.

Fix: use bounded event subjects (one per domain / aggregate) or topic-based routing (Kafka topics, EventEmitter2 namespaces):
```ts
// Better — scoped emitters per domain
const loanEvents = new TypedEventEmitter<LoanEvents>();
const repaymentEvents = new TypedEventEmitter<RepaymentEvents>();
const userEvents = new TypedEventEmitter<UserEvents>();
// Observers subscribe to only what they care about
```

**Q19. What is "observer avalanche" and how do you prevent it?**
A: Observer avalanche (also called "cascading events") occurs when an observer, upon being notified, emits its own events — which trigger other observers — which emit more events — resulting in an uncontrolled cascade:

```ts
// DANGER — notification chain with no termination guarantee
loanEvents.on("loan.approved", async (event) => {
  await disbursementService.disburse(event.loanId);
  loanEvents.emit("loan.disbursed", { loanId: event.loanId }); // cascades
});

loanEvents.on("loan.disbursed", async (event) => {
  await notificationService.notify(event.userId);
  loanEvents.emit("notification.sent", { userId: event.userId }); // cascades further
});
```

Defenses:
- **Separate event types** — use distinct event buses for commands vs. domain events vs. integration events.
- **Maximum depth limits** — track event chain depth in metadata; refuse to process if depth exceeds threshold.
- **Avoid observers emitting to the same bus** — observers should have side effects (DB writes, SMS), not re-emit domain events. Use a command handler or saga for multi-step flows.
- **Sagas / Process Managers** — for complex multi-step workflows triggered by events, use a dedicated saga that explicitly orchestrates the steps rather than chaining observers.

**Q20. What are "hot" vs "cold" observables and why does it matter in practice?**
A:
- **Cold observable** — starts producing values when subscribed; each subscriber gets its own independent sequence from the beginning. A database query observable is cold — each subscriber triggers its own query. HTTP request observables are cold — each subscription makes its own HTTP call.
- **Hot observable** — produces values regardless of subscribers; subscribers share the same stream and only see values emitted after they subscribe. A WebSocket message stream is hot — missed messages are gone.

```ts
// COLD — each subscriber triggers its own HTTP call
const loan$ = new Observable(subscriber => {
  fetch(`/loans/${loanId}`)
    .then(r => r.json())
    .then(data => subscriber.next(data))
    .catch(err => subscriber.error(err));
});

loan$.subscribe(loan => console.log("Subscriber A:", loan)); // HTTP call 1
loan$.subscribe(loan => console.log("Subscriber B:", loan)); // HTTP call 2 — separate!

// Multicasting — share one execution among subscribers
const sharedLoan$ = loan$.pipe(shareReplay(1)); // HOT — one call, cached result
sharedLoan$.subscribe(loan => console.log("A:", loan));
sharedLoan$.subscribe(loan => console.log("B:", loan)); // same call, same result
```

In NestJS microservice message handlers, streams are hot — a message from Kafka arrives once and your handler processes it once. In contrast, a `from(promise)` observable is cold — useful when you want to retry a fetch per subscriber.

**Q21. What is the "missing unsubscribe" leak in NestJS and how do you prevent it?**
A: In NestJS, `EventEmitter2` listener registration via `@OnEvent` is managed by the framework — no manual unsubscription needed for class-based listeners. But when you subscribe programmatically (e.g., inside a service method or lifecycle hook), missing `unsubscribe` leaks memory and causes duplicate handler execution:

```ts
// LEAK — subscribes on every onModuleInit call; never unsubscribes
@Injectable()
export class LoanMetricsService implements OnModuleInit {
  private subscription: Subscription;

  onModuleInit() {
    // This runs once — but if the module reloads (e2e tests, hot reload), it runs again
    this.subscription = this.loanEvents$.subscribe(event => {
      this.metrics.increment("loan.approved");
    });
  }

  // FIX — clean up on module destroy
  onModuleDestroy() {
    this.subscription?.unsubscribe();
  }
}
```

For RxJS in NestJS services:
```ts
@Injectable()
export class LoanAnalyticsService implements OnModuleInit, OnModuleDestroy {
  private readonly destroy$ = new Subject<void>();

  onModuleInit(): void {
    this.loanEvents$.pipe(
      takeUntil(this.destroy$) // auto-unsubscribes when destroy$ emits
    ).subscribe(event => this.processAnalytics(event));
  }

  onModuleDestroy(): void {
    this.destroy$.next();
    this.destroy$.complete();
  }
}
```
The `takeUntil(this.destroy$)` pattern is idiomatic RxJS for lifecycle-scoped subscriptions — it ties the subscription lifetime to the component/service lifetime.

## Section 7: Scenario / System Design Style Questions

**Q22. "Your loan approval flow writes to PostgreSQL and publishes to Kafka. Sometimes the DB write succeeds but the Kafka publish fails (or vice versa), leaving systems out of sync. How do you fix this?"**
A: This is the dual-write problem — the Outbox Pattern is the canonical solution:

```ts
// 1. Write event to outbox table in the SAME DB transaction as the domain change
async approveLoan(loanId: string, approverId: string): Promise<void> {
  await this.dataSource.transaction(async (em) => {
    const loan = await em.findOne(LoanEntity, { where: { id: loanId } });
    loan.status = "APPROVED";
    loan.approvedBy = approverId;
    await em.save(loan); // domain write

    // Outbox write — same transaction, guaranteed atomicity
    await em.save(OutboxEventEntity, {
      id: uuid(),
      aggregateId: loanId,
      eventType: "loan.approved",
      payload: JSON.stringify({ loanId, userId: loan.userId, amount: loan.amount }),
      createdAt: new Date(),
      publishedAt: null, // null = not yet published
    });
  });
  // If transaction commits: both loan update and outbox entry exist
  // If transaction rolls back: neither exists — no partial state
}

// 2. Outbox poller — reads unpublished events and publishes to Kafka
@Injectable()
export class OutboxPublisher implements OnModuleInit {
  onModuleInit(): void {
    setInterval(() => this.publishPending(), 1000); // poll every second
  }

  private async publishPending(): Promise<void> {
    const pending = await this.outboxRepo.find({
      where: { publishedAt: IsNull() },
      take: 100,
      order: { createdAt: "ASC" },
    });

    for (const event of pending) {
      try {
        await this.kafkaProducer.send({
          topic: "loan-events",
          messages: [{ key: event.aggregateId, value: event.payload }],
        });
        await this.outboxRepo.update(event.id, { publishedAt: new Date() });
      } catch (err) {
        logger.error({ event, err }, "Failed to publish outbox event");
        // Will retry on next poll — at-least-once delivery
      }
    }
  }
}
```
The Outbox Pattern gives you **at-least-once delivery** (idempotency keys on consumers handle duplicates) with **transactional consistency** — the DB and the event bus cannot diverge.

**Q23. "Your notification service is slow, and loan approvals are blocking waiting for SMS/email to send. The product team says approvals must complete in under 200ms. How do you restructure this using Observer?"**
A: The blocking problem means `LoanApprovalService` is awaiting observer notifications synchronously. The fix is fire-and-forget in-process events (for immediate decoupling) combined with Kafka (for durability):

```ts
// BEFORE — synchronous, blocking
async approveLoan(loanId: string): Promise<void> {
  await this.loanRepo.save(approved);
  await this.smsService.send(userId, "Approved"); // 300ms SMS API call — blocks
  await this.emailService.send(userId, "Approved"); // 200ms email API call — blocks
}

// AFTER — approval completes in <50ms; notifications happen asynchronously
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly loanRepo: LoanRepository,
    private readonly eventEmitter: EventEmitter2,
  ) {}

  async approveLoan(loanId: string, approverId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId); // ~30ms
    loan.approve(approverId);
    await this.loanRepo.save(loan);                     // ~20ms

    // Fire-and-forget — emitter does NOT await async listeners
    this.eventEmitter.emit("loan.approved", new LoanApprovedEvent(loan));
    // Returns here — total ~50ms
  }
}

// Notification listeners run asynchronously after response is sent
@Injectable()
export class NotificationListener {
  @OnEvent("loan.approved", { async: true })
  async handleLoanApproved(event: LoanApprovedEvent): Promise<void> {
    await this.smsService.send(event.userId, `Loan ₹${event.amount} approved`);
    // Slow — but not blocking the approval response anymore
  }
}
```
For **durable** async processing (notifications survive pod restarts), push the event to Kafka and process in a dedicated notification consumer service. The loan approval service publishes to Kafka (via the Outbox Pattern from Q22) and returns. The notification service consumes at its own pace, with retry logic, dead-letter queues, and independent scaling.

**Q24. "You're designing a real-time loan dashboard that pushes status updates to browser clients. How would you implement this using Observer and WebSockets in NestJS?"**
A:
```ts
// Gateway — WebSocket server, acts as the Observer "subject" for connected clients
@WebSocketGateway({ cors: true, namespace: "loans" })
@Injectable()
export class LoanStatusGateway implements OnGatewayConnection, OnGatewayDisconnect {
  @WebSocketServer()
  private server: Server;

  private userSockets = new Map<string, Set<string>>(); // userId → Set<socketId>

  handleConnection(client: Socket): void {
    const userId = this.extractUserId(client);
    if (!this.userSockets.has(userId)) this.userSockets.set(userId, new Set());
    this.userSockets.get(userId)!.add(client.id);
    client.join(`user:${userId}`); // socket.io room — the "subscription"
  }

  handleDisconnect(client: Socket): void {
    const userId = this.extractUserId(client);
    this.userSockets.get(userId)?.delete(client.id);
  }

  // Called by the Observer listener when a loan event occurs
  pushLoanUpdate(userId: string, update: LoanStatusUpdate): void {
    this.server.to(`user:${userId}`).emit("loan:status-update", update);
  }
}

// Observer listener — bridges domain events to WebSocket pushes
@Injectable()
export class LoanWebSocketBridge {
  constructor(private readonly gateway: LoanStatusGateway) {}

  @OnEvent("loan.approved")
  async handleLoanApproved(event: LoanApprovedEvent): Promise<void> {
    this.gateway.pushLoanUpdate(event.userId, {
      loanId: event.loanId,
      status: "APPROVED",
      message: `Your loan of ₹${event.amount} has been approved`,
      timestamp: event.approvedAt,
    });
  }

  @OnEvent("loan.disbursed")
  async handleLoanDisbursed(event: LoanDisbursedEvent): Promise<void> {
    this.gateway.pushLoanUpdate(event.userId, {
      loanId: event.loanId,
      status: "DISBURSED",
      message: "Funds have been transferred to your account",
      timestamp: event.disbursedAt,
    });
  }
}
```
The event flow: `LoanApprovalService` emits `loan.approved` → `LoanWebSocketBridge` observes → calls `LoanStatusGateway.pushLoanUpdate()` → WebSocket server pushes to the connected browser client. Each layer has a single responsibility; they're connected via the Observer pattern without direct coupling.

**Q25. "A post-mortem reveals that when the audit service's observer threw an exception during loan approval, the entire approval transaction rolled back — loans were approved in the business logic but never saved. How do you redesign this?"**
A: This is the synchronous observer coupling problem — one observer's failure poisoned the approval transaction. Three layers of fix:

**Layer 1 — Decouple event emission from the transaction:**
```ts
// WRONG — events emitted inside the transaction
await this.dataSource.transaction(async (em) => {
  await em.save(loan);
  await this.eventEmitter.emitAsync("loan.approved", event); // observer throws → rollback
});

// RIGHT — emit AFTER the transaction commits
await this.dataSource.transaction(async (em) => {
  await em.save(loan);
  // No event emission inside the transaction
});
// Transaction committed — now emit
this.eventEmitter.emit("loan.approved", event); // observer failure cannot rollback loan
```

**Layer 2 — Use `Promise.allSettled` in the emitter (Q7):**
Even if emission is post-transaction, an observer throwing should not block or fail the approval response. Use `allSettled` to isolate failures.

**Layer 3 — Use the Outbox Pattern for critical observers (Q22):**
For the audit log specifically — a compliance-critical observer — write the audit event to an outbox table inside the approval transaction:
```ts
await this.dataSource.transaction(async (em) => {
  await em.save(loan);
  await em.save(outboxEvent); // audit event in outbox — same transaction
  // If this commits, audit is guaranteed to be published eventually
});
```
This gives you: loan and audit event are atomically consistent, the audit publisher retries independently, and a transient audit service failure doesn't fail the loan approval.

**Tip for the interview:** At the 5 YOE level, Observer questions arrive as distributed systems design, not pattern definition. "How do you decouple your loan approval from downstream effects?" is an Observer question. "How do you ensure your audit log is consistent with your DB write?" is the Outbox + Observer question. "How do you prevent one slow subscriber from blocking loan approvals?" is the async Observer decoupling question. The strongest answers move fluidly between layers — in-process Observer (NestJS `EventEmitter2`), distributed Pub/Sub (Kafka), and reactive streams (RxJS) — and know when each layer is appropriate.
