# Behavioral Design Patterns: Template Method — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Template Method pattern?**
A: Template Method is a behavioral design pattern that defines the **skeleton of an algorithm in a base class**, deferring certain steps to subclasses. The base class implements the invariant parts of the algorithm and declares abstract (or overridable) methods for the variable parts. Subclasses fill in those variable steps without changing the algorithm's overall structure or sequence.

The key insight: the algorithm's *shape* — what steps happen and in what order — is fixed in the base class. The *implementation* of individual steps varies per subclass. The pattern is named after the "template method" — the method in the base class that calls the steps in sequence.

Three types of methods in a Template Method implementation:
- **Template method** — the orchestrating method in the base class; calls the steps in order; usually `final` or non-overridable to protect the algorithm's structure.
- **Abstract steps** — declared in the base class, no implementation; subclasses *must* implement them (the mandatory variable parts).
- **Hook methods** — implemented in the base class with a default (often empty) body; subclasses *may* override them to extend behaviour at optional points.

**Q2. What problem does Template Method solve?**
A: Template Method solves **code duplication across variants of the same algorithm**. When multiple classes implement the same multi-step process — but each class implements one or two steps differently — the common steps are duplicated everywhere. This is the "copy-paste with small changes" problem:

```typescript
// ❌ What Template Method replaces — duplicated structure

class HomeLoanOriginator {
  async originate(application: LoanApplication): Promise<LoanResult> {
    await this.validateBasicEligibility(application);   // same in every loan type
    const bureauReport = await this.fetchBureauReport(application.pan); // same
    const propertyValue = await this.valuateProperty(application.propertyId); // HOME-SPECIFIC
    const decision = this.underwriteHomeLoan(bureauReport, propertyValue);    // HOME-SPECIFIC
    await this.generateSanctionLetter(decision);        // same
    await this.notifyApplicant(application, decision);  // same
    return decision;
  }
}

class PersonalLoanOriginator {
  async originate(application: LoanApplication): Promise<LoanResult> {
    await this.validateBasicEligibility(application);   // DUPLICATED
    const bureauReport = await this.fetchBureauReport(application.pan); // DUPLICATED
    // No property valuation — skipped entirely
    const decision = this.underwritePersonalLoan(bureauReport);          // PL-SPECIFIC
    await this.generateSanctionLetter(decision);        // DUPLICATED
    await this.notifyApplicant(application, decision);  // DUPLICATED
    return decision;
  }
}
```

Any change to the common steps (e.g., "add a fraud check before underwriting") requires modifying every originator class. Template Method collapses the duplicated structure into one base class.

**Q3. What is the Hollywood Principle, and how does Template Method embody it?**
A: The Hollywood Principle states: **"Don't call us — we'll call you."** In the context of Template Method: the base class (the "Hollywood studio") controls the overall flow and calls the subclass methods when needed — subclasses don't call the base class to drive execution, they just implement the steps the base class will invoke.

This is an **inversion of control** at the inheritance level. The subclass gives up control over *when* its methods are called; the base class orchestrates that. The subclass only decides *how* each step is implemented. This contrasts with a library-style approach where the caller drives the sequence.

**Q4. How does Template Method differ from Strategy? Which should you prefer?**
A:

| Aspect                        | Template Method                                      | Strategy                                              |
|-------------------------------|------------------------------------------------------|-------------------------------------------------------|
| Mechanism                     | Inheritance — subclass overrides base class steps    | Composition — inject a strategy object                |
| Algorithm structure           | Fixed in base class — subclasses fill in steps       | Encapsulated in strategy — whole algorithm varies     |
| Runtime flexibility           | Fixed at instantiation (which subclass you pick)     | Fully runtime — swap strategy on any instance         |
| Coupling                      | Tight — subclass must know base class internals      | Loose — context and strategy are independent          |
| Testing the variable step     | Must instantiate the subclass to test the step       | Can unit test strategy in complete isolation          |
| Adding a new variant          | New subclass                                         | New strategy class                                    |
| Granularity of variation      | Fine-grained — vary individual steps                 | Coarse-grained — vary the whole algorithm             |

**Prefer Strategy over Template Method** in most modern codebases — composition is more flexible than inheritance, strategies are independently testable, and they avoid the "fragile base class" problem. Template Method is appropriate when: the algorithm structure is so tightly coupled to the shared state in the base class that composition would require passing too much context through parameters; or when the framework/language convention naturally uses inheritance (e.g., NestJS lifecycle hooks, abstract service classes in a module system).

**Q5. What is a "hook method," and how does it differ from an abstract step?**
A: Both are defined in the base class and intended for subclass overriding, but they differ in whether overriding is mandatory:

- **Abstract step** — declared with no implementation (`abstract doUnderwriting()`); subclasses *must* implement it or TypeScript errors at compile time. It represents a step so variable that no sensible default exists.
- **Hook method** — has a default implementation, often empty, in the base class (`protected onPostDisbursement(): void {}`); subclasses *may* override it. It represents an optional extension point where some subclasses have additional work and others don't.

```typescript
abstract class LoanOriginationTemplate {

  // Template method — orchestrates the algorithm
  async originate(application: LoanApplication): Promise<LoanResult> {
    await this.validateEligibility(application);   // abstract — must override
    const report = await this.fetchBureauData(application); // abstract
    await this.beforeUnderwriting(application);    // hook — optional
    const decision = await this.underwrite(report, application); // abstract
    await this.afterUnderwriting(decision);        // hook — optional
    await this.notifyApplicant(application, decision);
    return decision;
  }

  // Abstract steps — mandatory variable parts
  protected abstract validateEligibility(app: LoanApplication): Promise<void>;
  protected abstract fetchBureauData(app: LoanApplication): Promise<BureauReport>;
  protected abstract underwrite(report: BureauReport, app: LoanApplication): Promise<LoanResult>;

  // Hook methods — optional extension points
  protected async beforeUnderwriting(_app: LoanApplication): Promise<void> {} // no-op default
  protected async afterUnderwriting(_decision: LoanResult): Promise<void> {}  // no-op default

  // Concrete steps — invariant, same for all subclasses
  private async notifyApplicant(app: LoanApplication, decision: LoanResult): Promise<void> {
    await this.notificationService.send(app.email, decision);
  }
}
```

## Section 2: Implementation

**Q6. What does a complete TypeScript Template Method implementation look like for a loan origination system?**
A:

```typescript
// Base class — the template
abstract class LoanOriginationTemplate {
  constructor(
    protected readonly bureauService: BureauService,
    protected readonly notificationService: NotificationService,
    protected readonly auditLog: AuditLogService,
  ) {}

  // THE template method — algorithm skeleton; do not override
  async originate(application: LoanApplication): Promise<OriginationResult> {
    this.auditLog.record(application.id, 'ORIGINATION_STARTED');

    // Step 1 — invariant: basic checks
    await this.validateBasicEligibility(application);

    // Step 2 — invariant: bureau pull
    const bureauReport = await this.bureauService.fetchCreditReport(application.pan);

    // Step 3 — variant: product-specific additional data
    const additionalData = await this.fetchAdditionalData(application);

    // Step 4 — hook: optional pre-underwriting enrichment
    await this.enrichBeforeUnderwriting(application, bureauReport, additionalData);

    // Step 5 — variant: product-specific underwriting decision
    const decision = await this.underwrite(application, bureauReport, additionalData);

    // Step 6 — hook: optional post-underwriting override (e.g., manual review)
    const finalDecision = await this.applyPostUnderwritingOverride(decision, application);

    // Step 7 — invariant: document generation and notification
    await this.generateSanctionLetter(finalDecision, application);
    await this.notificationService.sendDecision(application.email, finalDecision);

    this.auditLog.record(application.id, 'ORIGINATION_COMPLETED', finalDecision);
    return finalDecision;
  }

  // --- Abstract steps — subclasses MUST implement ---
  protected abstract validateBasicEligibility(app: LoanApplication): Promise<void>;
  protected abstract fetchAdditionalData(app: LoanApplication): Promise<AdditionalData>;
  protected abstract underwrite(
    app: LoanApplication,
    bureau: BureauReport,
    data: AdditionalData,
  ): Promise<OriginationResult>;

  // --- Hook methods — subclasses MAY override ---
  protected async enrichBeforeUnderwriting(
    _app: LoanApplication,
    _bureau: BureauReport,
    _data: AdditionalData,
  ): Promise<void> {} // default: no-op

  protected async applyPostUnderwritingOverride(
    decision: OriginationResult,
    _app: LoanApplication,
  ): Promise<OriginationResult> {
    return decision; // default: pass through unchanged
  }

  // --- Concrete (private) steps — invariant, shared ---
  private async generateSanctionLetter(
    decision: OriginationResult,
    app: LoanApplication,
  ): Promise<void> {
    if (decision.approved) {
      await this.documentService.generateSanctionLetter(app.id, decision);
    }
  }
}
```

```typescript
// Concrete subclass 1 — Home Loan
class HomeLoanOriginator extends LoanOriginationTemplate {
  constructor(
    bureauService: BureauService,
    notificationService: NotificationService,
    auditLog: AuditLogService,
    private readonly propertyValuationService: PropertyValuationService,
  ) {
    super(bureauService, notificationService, auditLog);
  }

  protected async validateBasicEligibility(app: LoanApplication): Promise<void> {
    if (app.monthlyIncome < 25_000) throw new IneligibleException('Income below ₹25K for home loans');
    if (app.applicantAge < 21 || app.applicantAge > 60) throw new IneligibleException('Age 21–60 required');
    if (!app.propertyId) throw new IneligibleException('Property details required for home loan');
  }

  protected async fetchAdditionalData(app: LoanApplication): Promise<AdditionalData> {
    // Home loan needs property valuation — not needed for personal loans
    const valuation = await this.propertyValuationService.valuate(app.propertyId!);
    return { propertyValuation: valuation };
  }

  protected async underwrite(
    app: LoanApplication,
    bureau: BureauReport,
    data: AdditionalData,
  ): Promise<OriginationResult> {
    const ltv = app.requestedAmount / data.propertyValuation!.marketValue;
    if (ltv > 0.80) return { approved: false, reason: 'LTV exceeds 80% — RBI limit for home loans' };
    if (bureau.score < 700) return { approved: false, reason: 'CIBIL score below 700 for home loan' };
    return {
      approved: true,
      sanctionedAmount: app.requestedAmount,
      interestRate: this.computeRate(bureau.score, ltv),
    };
  }

  // Hook override — home loans need CERSAI registration check post-underwriting
  protected async applyPostUnderwritingOverride(
    decision: OriginationResult,
    app: LoanApplication,
  ): Promise<OriginationResult> {
    if (decision.approved) {
      const cersaiClear = await this.cersaiService.checkEncumbrance(app.propertyId!);
      if (!cersaiClear) {
        return { ...decision, approved: false, reason: 'Property encumbered on CERSAI' };
      }
    }
    return decision;
  }
}

// Concrete subclass 2 — Personal Loan (simpler — no property)
class PersonalLoanOriginator extends LoanOriginationTemplate {
  protected async validateBasicEligibility(app: LoanApplication): Promise<void> {
    if (app.monthlyIncome < 15_000) throw new IneligibleException('Income below ₹15K for personal loan');
    if (app.employmentTenureMonths < 6) throw new IneligibleException('Employment tenure below 6 months');
  }

  protected async fetchAdditionalData(_app: LoanApplication): Promise<AdditionalData> {
    return {}; // Personal loans need no additional external data
  }

  protected async underwrite(
    app: LoanApplication,
    bureau: BureauReport,
    _data: AdditionalData,
  ): Promise<OriginationResult> {
    if (bureau.score < 650) return { approved: false, reason: 'CIBIL score below 650' };
    const maxAmount = Math.min(app.requestedAmount, app.monthlyIncome * 24); // 2-year income cap
    return { approved: true, sanctionedAmount: maxAmount, interestRate: this.computeRate(bureau.score) };
  }
  // Does NOT override hooks — defaults apply
}

// Concrete subclass 3 — MSME Loan
class MsmeLoanOriginator extends LoanOriginationTemplate {
  constructor(
    bureauService: BureauService,
    notificationService: NotificationService,
    auditLog: AuditLogService,
    private readonly gstnService: GstnService,
    private readonly itrService: ItrService,
  ) {
    super(bureauService, notificationService, auditLog);
  }

  protected async validateBasicEligibility(app: LoanApplication): Promise<void> {
    if (!app.gstin) throw new IneligibleException('GSTIN mandatory for MSME loans');
    if (app.businessVintageYears < 2) throw new IneligibleException('Business vintage below 2 years');
  }

  protected async fetchAdditionalData(app: LoanApplication): Promise<AdditionalData> {
    // MSME needs GST returns + ITR data
    const [gstData, itrData] = await Promise.all([
      this.gstnService.fetch(app.gstin!),
      this.itrService.fetchLast2Years(app.pan),
    ]);
    return { gstData, itrData };
  }

  protected async underwrite(
    app: LoanApplication,
    bureau: BureauReport,
    data: AdditionalData,
  ): Promise<OriginationResult> {
    const annualTurnover = data.gstData!.annualTurnover;
    const itrIncome = data.itrData!.averageAnnualIncome;
    if (bureau.score < 680) return { approved: false, reason: 'CIBIL score below 680 for MSME' };
    const maxAmount = Math.min(annualTurnover * 0.2, itrIncome * 3); // MSME eligibility formula
    return { approved: true, sanctionedAmount: Math.min(app.requestedAmount, maxAmount), interestRate: 12.5 };
  }

  // Hook override — MSME loans need GSTIN verification before underwriting
  protected async enrichBeforeUnderwriting(
    app: LoanApplication,
    _bureau: BureauReport,
    data: AdditionalData,
  ): Promise<void> {
    const gstnStatus = data.gstData!.status;
    if (gstnStatus !== 'ACTIVE') {
      throw new IneligibleException(`GSTIN ${app.gstin} is not ACTIVE (status: ${gstnStatus})`);
    }
  }
}
```

**Q7. How do you wire Template Method subclasses in NestJS's DI system?**
A: Register each concrete originator as a named provider — consumers select by product code:

```typescript
@Module({
  providers: [
    HomeLoanOriginator,
    PersonalLoanOriginator,
    MsmeLoanOriginator,
    {
      provide: 'LOAN_ORIGINATOR_MAP',
      useFactory: (home, personal, msme) => ({
        'HL-STD': home,
        'PL-STD': personal,
        'MSME-STD': msme,
      }),
      inject: [HomeLoanOriginator, PersonalLoanOriginator, MsmeLoanOriginator],
    },
  ],
  exports: ['LOAN_ORIGINATOR_MAP'],
})
export class OriginationModule {}

@Injectable()
export class LoanApplicationService {
  constructor(
    @Inject('LOAN_ORIGINATOR_MAP')
    private readonly originators: Record<string, LoanOriginationTemplate>,
  ) {}

  async apply(application: LoanApplication): Promise<OriginationResult> {
    const originator = this.originators[application.productCode];
    if (!originator) throw new BadRequestException(`Unknown product: ${application.productCode}`);
    return originator.originate(application); // calls the template method
  }
}
```

**Q8. What should and should not be made abstract vs concrete vs hook in a Template Method base class?**
A: The decision for each step follows a clear rule:

| Step characteristic                                                       | Make it…              |
|---------------------------------------------------------------------------|-----------------------|
| Identical in every subclass — same logic, same output                     | **Concrete (private)** — don't allow override |
| Required in every subclass but implementation differs completely           | **Abstract** — force subclass to implement |
| Needed in most subclasses but with a sensible no-op/pass-through default  | **Hook (protected)** — optional override |
| Should never be overridden — would break algorithm invariants             | **Concrete (final/non-virtual)** — TypeScript uses `private` for this |

A common mistake: making steps `protected` instead of `private` when they should be invariant — this invites subclasses to accidentally override shared behaviour and break the algorithm's guarantees. In TypeScript, `private` in the base class prevents subclass overriding.

## Section 3: Template Method in Real-World Fintech Contexts

**Q9. How does Template Method apply to KYC verification workflows across customer segments?**
A: KYC has a fixed sequence — collect, verify, enrich, score — but each segment uses different document sets and verification providers:

```typescript
abstract class KycVerificationTemplate {
  constructor(
    protected readonly auditService: KycAuditService,
    protected readonly riskScorer: KycRiskScorer,
  ) {}

  // Template method — always the same sequence
  async verify(applicant: Applicant, docs: SubmittedDocument[]): Promise<KycResult> {
    this.auditService.begin(applicant.id);

    await this.validateDocumentCompleteness(docs);       // abstract — required docs differ
    const identityResult = await this.verifyIdentity(applicant, docs);  // abstract
    const addressResult = await this.verifyAddress(applicant, docs);    // abstract

    // Hook — only some segments do enhanced due diligence
    await this.performEnhancedDueDiligence(applicant, docs);

    const score = this.riskScorer.compute(identityResult, addressResult);

    this.auditService.complete(applicant.id, score);
    return { passed: score >= 70, score, identityResult, addressResult };
  }

  protected abstract validateDocumentCompleteness(docs: SubmittedDocument[]): Promise<void>;
  protected abstract verifyIdentity(app: Applicant, docs: SubmittedDocument[]): Promise<IdentityResult>;
  protected abstract verifyAddress(app: Applicant, docs: SubmittedDocument[]): Promise<AddressResult>;

  // Hook — EDD only for high-risk segments
  protected async performEnhancedDueDiligence(
    _app: Applicant,
    _docs: SubmittedDocument[],
  ): Promise<void> {} // default: no-op
}

// Retail salaried — Aadhaar + PAN
class RetailKycVerification extends KycVerificationTemplate {
  protected async validateDocumentCompleteness(docs: SubmittedDocument[]): Promise<void> {
    const required = ['AADHAAR', 'PAN', 'SELFIE'];
    const missing = required.filter(t => !docs.find(d => d.type === t));
    if (missing.length > 0) throw new MissingDocumentsException(missing);
  }

  protected async verifyIdentity(app: Applicant, docs: SubmittedDocument[]): Promise<IdentityResult> {
    const pan = docs.find(d => d.type === 'PAN')!;
    return this.nsdlService.verify(app.pan, app.name, app.dob);
  }

  protected async verifyAddress(app: Applicant, docs: SubmittedDocument[]): Promise<AddressResult> {
    const aadhaar = docs.find(d => d.type === 'AADHAAR')!;
    return this.uidaiService.verifyOtp(app.aadhaar, app.aadhaarOtp);
  }
  // Does NOT override EDD hook — retail is standard KYC
}

// NRI — passport + overseas address proof; EDD required (FEMA/PMLA)
class NriKycVerification extends KycVerificationTemplate {
  protected async validateDocumentCompleteness(docs: SubmittedDocument[]): Promise<void> {
    const required = ['PASSPORT', 'VISA', 'OVERSEAS_ADDRESS_PROOF', 'NRE_STATEMENT', 'PAN'];
    const missing = required.filter(t => !docs.find(d => d.type === t));
    if (missing.length > 0) throw new MissingDocumentsException(missing);
  }

  protected async verifyIdentity(app: Applicant, docs: SubmittedDocument[]): Promise<IdentityResult> {
    const passport = docs.find(d => d.type === 'PASSPORT')!;
    return this.passportVerificationService.verify(passport, app.name);
  }

  protected async verifyAddress(app: Applicant, docs: SubmittedDocument[]): Promise<AddressResult> {
    const addressProof = docs.find(d => d.type === 'OVERSEAS_ADDRESS_PROOF')!;
    return this.internationalAddressVerifier.verify(addressProof);
  }

  // EDD hook override — NRI requires PEP screening and source-of-funds verification
  protected async performEnhancedDueDiligence(app: Applicant, docs: SubmittedDocument[]): Promise<void> {
    const pepResult = await this.pepScreeningService.check(app.name, app.dob);
    if (pepResult.flagged) throw new EddFailedException(`PEP match: ${pepResult.list}`);

    const nreStatement = docs.find(d => d.type === 'NRE_STATEMENT')!;
    const fundsResult = await this.fundsVerificationService.verify(nreStatement);
    if (!fundsResult.sourceClear) throw new EddFailedException('Source of funds unclear');
  }
}
```

**Q10. How does Template Method apply to EMI collection across different payment channels?**
A: EMI collection via NACH, UPI mandate, and manual payment follows the same lifecycle — check, attempt, record, notify — but each channel's execution step differs:

```typescript
abstract class EmiCollectionTemplate {
  // Template method — fixed lifecycle
  async collectEmi(loan: ActiveLoan, emiDue: EmiSchedule): Promise<CollectionResult> {
    // Step 1 — pre-checks (always the same)
    await this.validateMandateActive(loan);
    await this.checkSufficientNotice(emiDue);

    // Step 2 — hook: channel-specific pre-collection setup
    await this.prepareCollection(loan, emiDue);

    // Step 3 — variant: actual debit attempt
    const debitResult = await this.attemptDebit(loan, emiDue);

    // Step 4 — invariant: record the attempt
    await this.recordCollectionAttempt(loan, emiDue, debitResult);

    // Step 5 — hook: channel-specific post-processing
    await this.postProcess(loan, emiDue, debitResult);

    // Step 6 — invariant: notify applicant
    await this.notifyApplicant(loan, debitResult);

    return debitResult;
  }

  // Abstract — the actual debit differs per channel
  protected abstract attemptDebit(loan: ActiveLoan, emi: EmiSchedule): Promise<CollectionResult>;

  // Concrete invariants
  private async validateMandateActive(loan: ActiveLoan): Promise<void> {
    if (!loan.mandateActive) throw new MandateInactiveException(loan.id);
  }

  private async checkSufficientNotice(emi: EmiSchedule): Promise<void> {
    const daysBefore = differenceInDays(emi.dueDate, new Date());
    if (daysBefore < 1) throw new InsufficientNoticeException('EMI due date already passed');
  }

  private async recordCollectionAttempt(
    loan: ActiveLoan,
    emi: EmiSchedule,
    result: CollectionResult,
  ): Promise<void> {
    await this.collectionRepo.save({ loanId: loan.id, emiId: emi.id, result, attemptedAt: new Date() });
  }

  private async notifyApplicant(loan: ActiveLoan, result: CollectionResult): Promise<void> {
    const template = result.success ? 'EMI_SUCCESS' : 'EMI_FAILURE';
    await this.smsService.send(loan.mobileNumber, template, { amount: result.amount });
  }

  // Hook — override for channel-specific setup
  protected async prepareCollection(_loan: ActiveLoan, _emi: EmiSchedule): Promise<void> {}
  protected async postProcess(
    _loan: ActiveLoan,
    _emi: EmiSchedule,
    _result: CollectionResult,
  ): Promise<void> {}
}

// NACH debit — via NPCI NACH
class NachEmiCollection extends EmiCollectionTemplate {
  protected async attemptDebit(loan: ActiveLoan, emi: EmiSchedule): Promise<CollectionResult> {
    const response = await this.npciClient.initiateDebit({
      umrn: loan.mandateUrn,
      amount: emi.amount,
      purpose: `EMI ${emi.month}/${emi.year} - Loan ${loan.id}`,
    });
    return {
      success: response.status === 'SUCCESS',
      amount: emi.amount,
      referenceId: response.rrn,
      failureCode: response.errorCode,
    };
  }

  // Hook — NACH needs a 2-day advance presentation
  protected async prepareCollection(loan: ActiveLoan, emi: EmiSchedule): Promise<void> {
    const presentationDate = subDays(emi.dueDate, 2);
    await this.nachPresentationService.schedule(loan.mandateUrn, presentationDate, emi.amount);
  }
}

class UpiAutoPayEmiCollection extends EmiCollectionTemplate {
  protected async attemptDebit(loan: ActiveLoan, emi: EmiSchedule): Promise<CollectionResult> {
    const response = await this.upiClient.executeAutoDebit({

      amount: emi.amount,
      dueDate: emi.dueDate.toDateString(),
    });
  }
}
```

**Q11. How would you apply Template Method to RBI regulatory report generation?**
A: All RBI returns follow the same lifecycle — collect data, validate, format, submit, acknowledge — but each return requires different data and formatting:

```typescript
abstract class RbiReportTemplate {
  async generateAndSubmit(reportingPeriod: ReportingPeriod): Promise<SubmissionResult> {
    // Step 1 — invariant: validate reporting period
    this.validateReportingPeriod(reportingPeriod);

    // Step 2 — variant: collect report-specific data
    const rawData = await this.collectData(reportingPeriod);

    // Step 3 — invariant: apply data quality checks
    const dqIssues = this.runDataQualityChecks(rawData);
    if (dqIssues.length > 0) {
      await this.handleDataQualityIssues(dqIssues); // hook — alert vs auto-fix
    }

    // Step 4 — variant: format into RBI-mandated schema
    const formattedReport = this.formatReport(rawData, reportingPeriod);

    // Step 5 — invariant: sign and encrypt
    const signedReport = await this.signAndEncrypt(formattedReport);

    // Step 6 — variant: submit to the right RBI portal
    const ackId = await this.submitToPortal(signedReport);

    // Step 7 — invariant: store submission record
    await this.storeSubmissionRecord(ackId, reportingPeriod, formattedReport);

    return { ackId, period: reportingPeriod, submittedAt: new Date() };
  }

  protected abstract collectData(period: ReportingPeriod): Promise<RawReportData>;
  protected abstract formatReport(data: RawReportData, period: ReportingPeriod): FormattedReport;
  protected abstract submitToPortal(report: SignedReport): Promise<string>;

  // Hook — default: log DQ issues; some reports may auto-correct
  protected async handleDataQualityIssues(issues: DqIssue[]): Promise<void> {
    issues.forEach(i => this.logger.warn(`[DQ] ${i.field}: ${i.message}`));
  }

  private validateReportingPeriod(period: ReportingPeriod): void {
    if (period.endDate > new Date()) throw new Error('Cannot report for future period');
  }

  private async signAndEncrypt(report: FormattedReport): Promise<SignedReport> {
    return this.cryptoService.sign(report, this.config.rbiSigningKey);
  }

  private async storeSubmissionRecord(
    ackId: string,
    period: ReportingPeriod,
    report: FormattedReport,
  ): Promise<void> {
```

**Q12. How does Template Method apply to loan disbursement across different payment rails (NEFT, RTGS, IMPS, UPI)?**
A: Disbursement follows a fixed lifecycle — verify, initiate, track, confirm — but each rail uses a different API:

```typescript
abstract class DisbursementTemplate {
  async disburse(loan: SanctionedLoan, bankDetails: BankDetails): Promise<DisbursementResult> {
    // Invariant pre-checks
    await this.verifyBankAccount(bankDetails);
    await this.checkDisbursementLimit(loan);

    // Hook — some rails need pre-registration (NACH mandate, UPI mandate)
    await this.setupPaymentInstrument(loan, bankDetails);

    // Variant — initiate transfer via the rail
    const transferRef = await this.initiateTransfer(loan, bankDetails);

    // Invariant — record the initiation
    await this.recordDisbursementInitiation(loan, transferRef);

    // Variant — track and wait for settlement (RTGS: same day; NEFT: batch; IMPS: instant)
    const settled = await this.awaitSettlement(transferRef);

    // Invariant — update loan status and generate disbursement voucher
    await this.finaliseDisbursement(loan, settled);

    return settled;
  }

  protected abstract initiateTransfer(loan: SanctionedLoan, bank: BankDetails): Promise<string>;
  protected abstract awaitSettlement(transferRef: string): Promise<DisbursementResult>;

  protected async setupPaymentInstrument(
    _loan: SanctionedLoan,
    _bank: BankDetails,
  ): Promise<void> {} // hook: no-op for most rails

  private async verifyBankAccount(bank: BankDetails): Promise<void> {
    const pennydropResult = await this.pennydropService.verify(bank.accountNumber, bank.ifsc);
    if (!pennydropResult.valid) throw new InvalidBankAccountException(bank.accountNumber);
  }

  private async checkDisbursementLimit(loan: SanctionedLoan): Promise<void> {
    if (loan.amount > 200_000_000) { // RBI: RTGS mandatory above ₹2Cr
      if (this.paymentRail !== 'RTGS') throw new PaymentRailException('Amounts above ₹2Cr require RTGS');
    }
  }
}

// IMPS — instant, 24x7, up to ₹5L per transaction
class ImpsDisbursementService extends DisbursementTemplate {
  readonly paymentRail = 'IMPS';

  protected async initiateTransfer(loan: SanctionedLoan, bank: BankDetails): Promise<string> {
    const response = await this.impsClient.transfer({
      amount: loan.amount,
      beneficiaryAccount: bank.accountNumber,
      beneficiaryIfsc: bank.ifsc,
      remitterRef: loan.id,
    });
    return response.rrn; // RBI Reference Number
  }

  protected async awaitSettlement(rrn: string): Promise<DisbursementResult> {
    // IMPS: near-instant — poll for 2 minutes max
    for (let i = 0; i < 12; i++) {
      const status = await this.impsClient.checkStatus(rrn);
      if (status.settled) return { success: true, referenceId: rrn, settledAt: status.settledAt };
      await sleep(10_000); // 10 second intervals
    }
    throw new SettlementTimeoutException(rrn);
  }
}

// RTGS — large value, same-day, bank hours only
class RtgsDisbursementService extends DisbursementTemplate {
  readonly paymentRail = 'RTGS';

  protected async initiateTransfer(loan: SanctionedLoan, bank: BankDetails): Promise<string> {
    const response = await this.rtgsClient.submit({
      amount: loan.amount,
      beneficiaryAccount: bank.accountNumber,
      beneficiaryIfsc: bank.ifsc,
      paymentRef: `RTGS-${loan.id}`,
    });
    return response.uttNo;
  }

  protected async awaitSettlement(uttNo: string): Promise<DisbursementResult> {
    // RTGS: settled on same day — webhook-based, not polling
    return this.rtgsWebhookService.awaitConfirmation(uttNo, { timeoutMinutes: 240 });
  }
}
```

## Section 5: Anti-patterns & Pitfalls

**Q15. What are the most common mistakes when implementing Template Method?**
A:

- **Making the template method overridable** — if subclasses can override the template method itself, they can change the algorithm's structure, which defeats the pattern entirely. The template method should be `private` (TypeScript) or effectively `final`. If a subclass needs a slightly different sequence, it's a signal that you need a new base class or should switch to Strategy.
- **Too many abstract steps** — if every step is abstract, subclasses duplicate the assembly of steps that should be shared. The base class should implement as many concrete steps as possible, abstracting only the genuinely variable parts.
- **Calling abstract methods from the constructor** — in TypeScript/JavaScript, calling overridden methods in a base class constructor is dangerous because the subclass hasn't finished initialising. Template methods should be called explicitly (e.g., `originator.originate(app)`), never from `constructor`.
- **The "fragile base class" problem** — if the base class changes its implementation of a concrete step, all subclasses inherit that change. For chains of inheritance (grandchild subclasses), changes in the grandparent can unexpectedly affect grandchildren. Keep base classes focused and stable.
- **Hook proliferation** — adding a hook at every possible step "just in case" creates a base class that's impossible to understand. Add hooks only where you have a concrete, known need for optional extension. If you never actually override a hook in any subclass, remove it.
- **Business logic in the template method** — the template method should orchestrate, not decide. A template method that contains `if (product === 'HOME_LOAN')` is mixing concerns. Product-specific decisions belong in the abstract steps, which are resolved by the concrete subclass.

**Q16. When should you refactor Template Method to Strategy?**
A: Refactor when:
- You want to **test steps in complete isolation** without instantiating the full subclass hierarchy.
- Steps need to be **composed dynamically** at runtime, not fixed at class definition.
- The number of subclasses is growing combinatorially (HomeLoanSalariedOriginator, HomeLoanSelfEmployedOriginator, etc.) — this signals that two independent variation axes should be two Strategy objects composed together, not a subclass for every combination.
- **Multiple inheritance** would be needed — TypeScript doesn't support it; if you want a class to inherit from both `HomeLoanTemplate` and `NriLoanTemplate`, you can't. Strategy composition handles this cleanly.

```typescript
// Refactored: Template Method → Strategy composition
class LoanOriginator {
  constructor(
    private readonly eligibilityStrategy: EligibilityStrategy,
    private readonly dataEnrichmentStrategy: DataEnrichmentStrategy,
    private readonly underwritingStrategy: UnderwritingStrategy,
    // shared services injected directly
    private readonly bureauService: BureauService,
  ) {}

  async originate(application: LoanApplication): Promise<OriginationResult> {
    await this.eligibilityStrategy.validate(application); // replaces abstract validateBasicEligibility
    const data = await this.dataEnrichmentStrategy.enrich(application); // replaces fetchAdditionalData
    const bureau = await this.bureauService.fetchCreditReport(application.pan);
    return this.underwritingStrategy.underwrite(application, bureau, data); // replaces underwrite
  }
}
```

This allows NRI + MSME eligibility strategies to be combined without a `NriMsmeLoanOriginator` subclass.

## Section 6: Scenario / System Design Questions

**Q17. "Your team maintains six loan product originators, each with a separate `originate()` method. The risk team just mandated that a fraud check must be inserted before every underwriting step across all products. How do you implement this?"**
A: This is precisely the scenario Template Method is designed for — a cross-cutting change to a shared algorithm:

**Without Template Method** (current state): modify six originator classes, find the right insertion point in each, risk missing one or inserting it in the wrong position.

**With Template Method**: add the fraud check as a concrete step in the base class template method — one change propagates to all subclasses automatically:

```typescript
// ONE change in the base class template method
async originate(application: LoanApplication): Promise<OriginationResult> {
  await this.validateBasicEligibility(application);
  const bureauReport = await this.bureauService.fetchCreditReport(application.pan);
  const additionalData = await this.fetchAdditionalData(application);

  // ← INSERT ONCE HERE — inherited by all six subclasses
  await this.fraudCheckService.check(application.pan, application.deviceId);

  await this.enrichBeforeUnderwriting(application, bureauReport, additionalData);
  const decision = await this.underwrite(application, bureauReport, additionalData);
  // ... rest unchanged
}
```

All six originators (Home, Personal, MSME, Gold, Vehicle, LAP) now include the fraud check without any changes to those subclasses. The risk team's mandate is implemented in exactly one place.

**Q18. "You need a new 'Affordable Housing Loan' product that's identical to the standard Home Loan origination, except the property valuation step uses a government-approved valuer list instead of your standard panel. How do you add this using Template Method?"**
A: Subclass `HomeLoanOriginator`, override only the varying step:

```typescript
class AffordableHousingLoanOriginator extends HomeLoanOriginator {
  constructor(
    bureauService: BureauService,
    notificationService: NotificationService,
    auditLog: AuditLogService,
    private readonly govtApprovedValuationService: GovtApprovedPropertyValuationService,
    standardValuationService: PropertyValuationService, // still needed for super
  ) {
    super(bureauService, notificationService, auditLog, standardValuationService);
  }

  // Override only the data enrichment step — everything else inherited from HomeLoanOriginator
  protected async fetchAdditionalData(app: LoanApplication): Promise<AdditionalData> {
    // Use government-approved valuers (PMAY requirement)
    const valuation = await this.govtApprovedValuationService.valuate(app.propertyId!);
    // Validate PMAY eligibility
    if (valuation.marketValue > 4_500_000) {
      throw new IneligibleException('Property value exceeds PMAY affordable housing limit of ₹45L');
    }
    return { propertyValuation: valuation };
  }

  // Also override underwriting to apply PMAY-specific interest subsidy rules
  protected async underwrite(
    app: LoanApplication,
    bureau: BureauReport,
    data: AdditionalData,
  ): Promise<OriginationResult> {
    const baseResult = await super.underwrite(app, bureau, data); // reuse parent logic
    if (baseResult.approved) {
      baseResult.interestRate = Math.max(0, baseResult.interestRate! - 6.5); // CLSS subsidy
      baseResult.subsidyAmount = app.requestedAmount * 0.065; // subsidy credit to NHB
    }
    return baseResult;
  }
}
```

New product in three methods — all the shared logic (bureau fetch, notification, audit, CERSAI check hook) is fully inherited. The `validate` and `setup` steps didn't change — they're not overridden.

**Q19. "A new RBI circular requires all lenders to add a 'Re-KYC check' step for loan applications from customers last KYC'd more than 2 years ago. This applies across all loan products. How do you implement this using Template Method?"**
A: Add a concrete step (not abstract — it's the same for all) and a hook for product-specific exceptions:

```typescript
// In LoanOriginationTemplate — add once, inherited everywhere
async originate(application: LoanApplication): Promise<OriginationResult> {
  await this.validateBasicEligibility(application);

  // ← NEW: Re-KYC check per RBI circular — concrete step (same logic for all products)
  await this.checkReKycRequirement(application);

  const bureauReport = await this.bureauService.fetchCreditReport(application.pan);
  // ... rest unchanged
}

// Concrete (private) — applies uniformly
private async checkReKycRequirement(app: LoanApplication): Promise<void> {
  const lastKyc = await this.kycRepo.getLastVerifiedDate(app.applicantId);
  if (!lastKyc || differenceInYears(new Date(), lastKyc) >= 2) {
    throw new ReKycRequiredException(
      `Customer must complete Re-KYC before applying. Last KYC: ${lastKyc?.toDateString() ?? 'Never'}`,
    );
  }
}
```

Zero changes to `HomeLoanOriginator`, `PersonalLoanOriginator`, `MsmeLoanOriginator`, or any other subclass. The regulatory requirement is implemented and enforced in one method in one class.

## Quick Reference: Template Method Checklist

| Signal                                                                          | What to Do                                                                        |
|---------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| Multiple classes with same multi-step method, differing in 1–2 steps            | Extract shared steps to base class template; abstract the varying steps           |
| A regulatory/cross-cutting change must be applied to all product variants       | Add as concrete step in template method — one change propagates to all subclasses |
| A step is optional for some products (e.g., property valuation for home loans)  | Hook method with no-op default — subclasses that need it override; others don't  |
| Template method is being overridden by a subclass                               | Make it private — subclasses should override steps, not the template itself       |
| New product is near-identical to an existing one with one differing step        | Subclass the existing concrete class, override only the differing step            |
| Subclass hierarchy growing for every combination of features                    | Refactor to Strategy composition — Template Method doesn't handle cross-product combinations |
| Business logic (`if productType === 'HOME'`) appearing in template method       | Move to abstract step — let subclass resolve it                                  |
| Hook method never overridden in any subclass                                    | Remove the hook — unused extension points add noise                              |

---

**Tip for the interview:** At the 5 YOE level, Template Method comes up in disguise: "how do you handle regulatory changes that must apply to all loan products," "how do you structure your origination flow so adding a new product doesn't require touching existing ones," or "how do you avoid duplicating the same 8-step process across six loan originators." The right answer names Template Method, draws the base/abstract/hook distinction, and — critically — shows that the template method itself is *not overridable* (protected algorithm skeleton). The differentiating answer is the contrast with Strategy: Template Method uses inheritance and is right when the base class holds shared state the steps need access to; Strategy uses composition and is right when steps are independently reusable across different contexts. In a fintech domain, the recurring story — "RBI issued a circular mandating a new check across all products, and I added it in one place in the base class" — is the most compelling evidence that you understand why the pattern exists.
