# Publish-Subscribe (Pub/Sub) — Messaging & Event Patterns: Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Publish-Subscribe pattern and what core problem does it solve?**
A: Publish-Subscribe (Pub/Sub) is a messaging pattern where **publishers** emit events without knowing who will consume them, and **subscribers** receive events without knowing who produced them. The broker (or event bus) sits in between, routing messages from publishers to subscribers based on topic/channel subscriptions.

The core problem it solves is **tight coupling** in communication: without Pub/Sub, Service A must know about Service B to send it data. With Pub/Sub, A publishes to a topic and has zero knowledge of B, C, or D — which may subscribe, unsubscribe, or not exist yet. This decoupling enables:

- Independent scaling of producers and consumers
- Addition of new consumers without touching the publisher
- Resilience: publisher continues even if all subscribers are down
- Temporal decoupling: publisher and subscriber don't need to be alive at the same time (with a persistent broker)

```
Without Pub/Sub (tight coupling):
  LoanService ──calls──► KYCService
                ──calls──► CreditBureau
                ──calls──► NotificationService

With Pub/Sub (loose coupling):
  LoanService ──publishes──► [loan.application.created]
                                        │
                         ┌──────────────┼─────────────────┐
                         ▼              ▼                  ▼
                    KYCService   CreditBureau   NotificationService
```

**Q2. How does Pub/Sub differ from the Observer pattern?**
A: They solve the same problem — one producer, many consumers — but at different scopes:

| Dimension | Observer | Pub/Sub |
|---|---|---|
| Coupling | Observer holds a direct reference to the subject | Publisher and subscriber don't know each other — broker in between |
| Communication | In-process (same memory space) | Can be cross-process, cross-network, cross-service |
| Broker | None — subject manages its own listener list | Explicit message broker (Redis, Kafka, SNS, RabbitMQ) |
| Filtering | Subject notifies all observers; filtering is their problem | Broker filters by topic/channel; subscribers receive only what they subscribed to |
| Persistence | Events are lost if no observer is registered | Broker can persist messages (durable queues, Kafka offsets) |
| Scalability | Limited to in-process; observer list is synchronous | Broker enables fan-out to thousands of consumers across services |

```typescript
// Observer (in-process, tight reference):
class LoanSubject {
  private observers: Observer[] = [];
  notify(event: LoanEvent) {
    this.observers.forEach(o => o.update(event));  // direct call
  }
}

// Pub/Sub (no direct reference; broker-mediated):
await sns.publish({ TopicArn: TOPIC_ARN, Message: JSON.stringify(event) });
// Publisher has no idea who's listening
```

**Q3. What are the three core roles in a Pub/Sub system?**
A:
1. **Publisher (Producer)**: Creates and emits events/messages to a named topic or channel. Has no knowledge of who subscribes or how many subscribers exist. Its only responsibility is to publish well-formed messages.
2. **Broker (Event Bus / Message Bus)**: The intermediary that receives messages from publishers and routes them to the correct subscribers. Responsible for: topic management, message durability, delivery guarantees, and fan-out logic. Examples: AWS SNS, Google Pub/Sub, Redis Pub/Sub, Kafka, RabbitMQ.
3. **Subscriber (Consumer)**: Registers interest in one or more topics and receives messages routed by the broker. Processes messages independently of the publisher's lifecycle.

```
Publisher ──► [Broker: Topic "loan.created"] ──► Subscriber A (KYC Service)
                                              ──► Subscriber B (Credit Check)
                                              ──► Subscriber C (Audit Logger)
```

The broker is what makes Pub/Sub structurally different from a simple function call — it introduces asynchrony, durability, and the ability to fan out a single event to N consumers.

**Q4. What is a topic vs a channel vs a queue — how do these terms relate?**
A: These terms overlap and differ by system:

- **Topic**: A named category of messages. Publishers publish to a topic; subscribers subscribe to a topic. In SNS and Kafka, "topic" is the primary term. A topic is typically fan-out: one message goes to all subscribers. In Kafka, a topic is additionally partitioned and ordered within partitions.
- **Channel**: Used by Redis Pub/Sub and some other systems — functionally equivalent to a topic. `SUBSCRIBE payments` registers interest in the `payments` channel.
- **Queue**: Different from a topic in delivery semantics. A queue delivers each message to **exactly one consumer** (competing consumers model — for load distribution). A topic/channel delivers each message to **all subscribers** (fan-out model). AWS SNS (Pub/Sub fan-out) + SQS (queue) is the canonical combination: SNS fans out to multiple SQS queues, each queue load-balances across its consumer instances.

```
SNS Topic (fan-out)  ──► SQS Queue A ──► [Worker 1, Worker 2, Worker 3]  (compete)
                     ──► SQS Queue B ──► [Audit Service]
                     ──► SQS Queue C ──► [Notification Service]
```

## Section 2: Delivery Semantics & Guarantees

**Q5. What are the three message delivery guarantee levels, and when does each matter?**
A:
1. **At-most-once**: A message is delivered zero or one time — never retried if delivery fails. Lowest latency, highest throughput, data loss is acceptable. Used for: metrics, telemetry, non-critical analytics events, Redis Pub/Sub (fire-and-forget).
2. **At-least-once**: A message is delivered one or more times — the broker retries on failure, meaning duplicates are possible. Consumer must be idempotent. Most common in financial/critical systems. Used for: payment events, KYC triggers, NACH mandates, any event where data loss is unacceptable. Kafka (with acks=all), SQS standard queues, RabbitMQ with publisher confirms.
3. **Exactly-once**: A message is delivered exactly one time — no loss, no duplicates. Hardest to guarantee, highest overhead. Kafka transactions + idempotent producers + transactional consumers can achieve this within the Kafka ecosystem. Not natively available in SNS/SQS; must be simulated via idempotency keys at the consumer.

```typescript
// Consumer idempotency guard (simulates exactly-once from at-least-once):
async function processLoanEvent(event: LoanCreatedEvent): Promise<void> {
  const key = `processed:loan:${event.loanId}`;
  const alreadyProcessed = await redis.set(key, '1', 'NX', 'EX', 86400);
  if (!alreadyProcessed) {
    return;  // duplicate — skip
  }
  await kycService.trigger(event.loanId);
}
```

**Q6. What is message ordering, and when is it guaranteed vs not?**
A: Message ordering means consumers receive messages in the same sequence the producer sent them. This is non-trivial in distributed, partitioned, or multi-broker setups:

- **Redis Pub/Sub**: Messages on a channel are ordered within a single Redis node — FIFO per channel.
- **SQS Standard Queue**: No ordering guarantee — messages may arrive out of order. Use **SQS FIFO Queue** for strict ordering (at the cost of throughput: 300 TPS vs SQS Standard's effectively unlimited).
- **Kafka**: Ordering is guaranteed **within a partition**. A topic with multiple partitions delivers messages globally out of order but in-order per partition. To guarantee ordering for a specific entity (e.g., all events for `loanId=123`), publish with that entity ID as the partition key — Kafka routes all messages with the same key to the same partition.
- **SNS**: No ordering guarantee (standard SNS). SNS FIFO topics + SQS FIFO queues provide ordering for fan-out scenarios.

```typescript
// Kafka: ensure all events for a loan go to same partition → ordered
await producer.send({
  topic: 'loan-events',
  messages: [{
    key: loanId,          // partition key — same loan, same partition, ordered
    value: JSON.stringify(event)
  }]
});
```

**Q7. What is a Dead Letter Queue (DLQ) and why is it essential in production Pub/Sub systems?**
A: A Dead Letter Queue (DLQ) is a special destination for messages that fail to be processed after a configured number of retries. Instead of being discarded or blocking the queue indefinitely, failed messages are moved to the DLQ for investigation, alerting, and manual replay.

Without a DLQ, a poison-pill message (one that always causes a consumer crash) can block queue processing indefinitely or cause infinite retry loops. With a DLQ:
- The main queue stays healthy — poison pill is isolated after N retries
- Engineers can inspect failed messages, fix the consumer bug, and replay from DLQ
- Alerting on DLQ depth is a reliable signal that consumer code is broken

```typescript
// AWS CDK: wiring DLQ to an SQS queue
const dlq = new sqs.Queue(this, 'LoanEventsDLQ', {
  retentionPeriod: Duration.days(14),
});

const mainQueue = new sqs.Queue(this, 'LoanEventsQueue', {
  deadLetterQueue: {
    queue: dlq,
    maxReceiveCount: 3,   // after 3 failed attempts, move to DLQ
  },
});
```

In NestJS with `@nestjs/microservices`, configure the DLQ at the transport layer (SQS or RabbitMQ). Always set up CloudWatch alarm on `ApproximateNumberOfMessagesVisible` on the DLQ.

## Section 3: Implementation Patterns

**Q8. How do you implement a simple in-process Pub/Sub event bus in TypeScript/NestJS?**
A: Node.js's built-in `EventEmitter` is the foundation of in-process Pub/Sub. NestJS wraps this with `EventEmitter2` via `@nestjs/event-emitter`:

```typescript
// event-bus.ts — raw EventEmitter approach
import { EventEmitter } from 'events';

export const eventBus = new EventEmitter();
eventBus.setMaxListeners(50);  // avoid MaxListenersExceeded warning

// publisher
eventBus.emit('loan.created', { loanId: 'L001', amount: 50000 });

// subscriber
eventBus.on('loan.created', (payload) => {
  console.log('KYC triggered for loan:', payload.loanId);
});
```

```typescript
// NestJS idiomatic approach with @nestjs/event-emitter
// app.module.ts
import { EventEmitterModule } from '@nestjs/event-emitter';

@Module({
  imports: [EventEmitterModule.forRoot({ wildcard: true })],
})
export class AppModule {}

// loan.events.ts
export class LoanCreatedEvent {
  constructor(
    public readonly loanId: string,
    public readonly amount: number,
    public readonly applicantId: string,
  ) {}
}

// loan.service.ts (publisher)
@Injectable()
export class LoanService {
  constructor(private readonly eventEmitter: EventEmitter2) {}

  async createLoan(dto: CreateLoanDto): Promise<Loan> {
    const loan = await this.loanRepository.save(dto);
    this.eventEmitter.emit(
      'loan.created',
      new LoanCreatedEvent(loan.id, loan.amount, loan.applicantId),
    );
    return loan;
  }
}

// kyc.listener.ts (subscriber)
@Injectable()
export class KycListener {
  @OnEvent('loan.created')
  async handleLoanCreated(event: LoanCreatedEvent): Promise<void> {
    await this.kycService.initiate(event.applicantId, event.loanId);
  }
}
```

**Q9. How do you implement Pub/Sub with Redis in a Node.js/NestJS microservice?**
A: Redis Pub/Sub uses dedicated publisher and subscriber connections (you cannot use the same connection for both):

```typescript
// redis-pubsub.service.ts
import { Injectable, OnModuleInit } from '@nestjs/common';
import Redis from 'ioredis';

@Injectable()
export class RedisPubSubService implements OnModuleInit {
  private publisher: Redis;
  private subscriber: Redis;
  private handlers = new Map<string, ((msg: string) => void)[]>();

  onModuleInit() {
    this.publisher = new Redis({ host: process.env.REDIS_HOST });
    this.subscriber = new Redis({ host: process.env.REDIS_HOST });

    this.subscriber.on('message', (channel: string, message: string) => {
      const fns = this.handlers.get(channel) ?? [];
      fns.forEach(fn => fn(message));
    });
  }

  async publish(channel: string, payload: unknown): Promise<void> {
    await this.publisher.publish(channel, JSON.stringify(payload));
  }

  async subscribe(channel: string, handler: (msg: string) => void): Promise<void> {
    if (!this.handlers.has(channel)) {
      this.handlers.set(channel, []);
      await this.subscriber.subscribe(channel);
    }
    this.handlers.get(channel)!.push(handler);
  }
}
```

Key caveats with Redis Pub/Sub:
- **At-most-once**: if the subscriber is offline when a message is published, the message is lost.
- **No persistence**: Redis Pub/Sub has no message history. Use Redis Streams (`XADD`/`XREADGROUP`) for persistence + consumer groups — closer to Kafka semantics.
- **No DLQ**: fire-and-forget. Suitable for cache invalidation signals, real-time notifications, not for critical financial events.

**Q10. How does SNS + SQS fan-out work, and when do you choose this over Kafka?**
A: The SNS + SQS fan-out pattern uses SNS as the Pub/Sub broker and SQS queues as durable per-subscriber buffers:

```
Publisher ──► SNS Topic
              ├──► SQS Queue (KYC Service)         → KYC workers compete
              ├──► SQS Queue (Credit Bureau)        → Credit workers compete
              ├──► SQS Queue (Notification Service) → Notification workers compete
              └──► SQS Queue (Audit Log)            → Audit workers compete
```

```typescript
// Publishing to SNS (NestJS / AWS SDK v3)
import { SNSClient, PublishCommand } from '@aws-sdk/client-sns';

const sns = new SNSClient({ region: 'ap-south-1' });

await sns.send(new PublishCommand({
  TopicArn: process.env.LOAN_EVENTS_TOPIC_ARN,
  Message: JSON.stringify({
    eventType: 'LOAN_CREATED',
    loanId,
    applicantId,
    timestamp: new Date().toISOString(),
  }),
  MessageAttributes: {
    eventType: { DataType: 'String', StringValue: 'LOAN_CREATED' }
  }
}));

// SQS Consumer (NestJS microservice transport)
// main.ts
const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
  transport: Transport.SQS,
  options: {
    urls: [process.env.KYC_QUEUE_URL],
    region: 'ap-south-1',
  },
});
```

**SNS + SQS vs Kafka:**

| Factor | SNS + SQS | Kafka |
|---|---|---|
| Managed/Ops overhead | Fully managed, zero infra | Self-managed or MSK (more ops) |
| Message retention | SQS: up to 14 days | Kafka: configurable, unlimited (with compaction) |
| Replay | Not natively; need manual DLQ replay | Yes — replay from any offset |
| Throughput | Very high (SQS: unlimited) | Extremely high; optimized for streaming |
| Ordering | FIFO queues, limited TPS | Strong per-partition ordering, high TPS |
| Event streaming / complex routing | Basic filter policies | Rich — stream processing, joins, windowing |
| Cost model | Pay-per-message | Compute cost (broker instances) |

Choose SNS+SQS for: typical microservice eventing, straightforward fan-out, AWS-native stacks, RBI-compliant data residency in `ap-south-1`. Choose Kafka for: high-volume streaming, event sourcing, replay requirements, complex consumer group topology.

**Q11. How does Kafka implement Pub/Sub, and what is a consumer group?**
A: Kafka topics are the "channels." Producers publish to topics; consumers subscribe via **consumer groups**. A consumer group is a set of consumer instances that collectively process a topic's partitions:

- Each partition is assigned to **exactly one consumer** within the group at any time.
- Messages are load-balanced across the group (competing consumers for throughput).
- Multiple distinct consumer groups each get their **own independent copy** of every message (fan-out / Pub/Sub semantics).

```
Topic: loan-events (3 partitions: P0, P1, P2)

Consumer Group "kyc-service" (3 instances):
  Instance 1 → P0
  Instance 2 → P1
  Instance 3 → P2

Consumer Group "credit-bureau" (2 instances):
  Instance 1 → P0, P1
  Instance 2 → P2

Both groups receive ALL messages — fan-out across groups, load-balance within group.
```

```typescript
// Kafka consumer in NestJS
@Controller()
export class LoanEventConsumer {
  @MessagePattern('loan-events')
  @EventPattern('loan.created')
  async handleLoanCreated(
    @Payload() message: LoanCreatedEvent,
    @Ctx() context: KafkaContext,
  ): Promise<void> {
    const { offset, partition } = context.getMessage();
    this.logger.log(`Processing partition=${partition} offset=${offset}`);

    await this.kycService.initiate(message.loanId);

    // Manual commit after successful processing (for at-least-once)
    await context.getConsumer().commitOffsets([{
      topic: 'loan-events',
      partition,
      offset: String(Number(offset) + 1),
    }]);
  }
}
```

## Section 4: Message Design & Schema

**Q12. What should a well-designed Pub/Sub event payload look like?**
A: A good event payload is self-describing, versioned, and carries just enough context for consumers to act without additional lookups (fat events) or a pointer for consumers to fetch details themselves (thin events):

```typescript
// Recommended event envelope
interface LoanCreatedEvent {
  // Identity & routing
  eventId: string;           // UUID — for idempotency checks
  eventType: 'LOAN_CREATED'; // discriminant for multi-type topics
  eventVersion: '1.0';       // schema version — enables consumers to handle migrations
  topic: 'loan-events';      // self-documenting

  // Timing
  occurredAt: string;        // ISO 8601 — when the event happened (not when published)
  publishedAt: string;       // ISO 8601 — when it was put on the broker

  // Source
  sourceService: 'loan-origination-service';
  correlationId: string;     // trace ID — links this event to the originating HTTP request
  causationId?: string;      // ID of the event that caused this one (event chains)

  // Payload — fat event: includes what consumers need without extra DB calls
  payload: {
    loanId: string;
    applicantId: string;
    amount: number;
    currency: 'INR';
    product: 'PERSONAL_LOAN' | 'BUSINESS_LOAN' | 'GOLD_LOAN';
    status: 'PENDING_KYC';
  };
}
```

Fat vs Thin event trade-off:
- **Fat event**: payload has all the data a consumer needs. Pros: consumer autonomy, no coupling to the producer's API. Cons: larger message size, sensitive data propagation, stale data if consumer processes slowly.
- **Thin event** (notification event): payload is minimal — `{ loanId, eventType }`. Consumer fetches full data from the producer's API. Pros: always fresh data, smaller message. Cons: coupling to producer's API, extra network call per event, failure surface.

For fintech: use fat events but **never put PII/Aadhaar numbers/card data in events** — use tokens or IDs and let downstream services fetch sensitive data through secured APIs.

**Q13. What is schema evolution in Pub/Sub, and how do you handle it without breaking consumers?**
A: Schema evolution is the challenge of changing an event's shape without breaking existing consumers. In Pub/Sub, producers and consumers deploy independently — you cannot do a coordinated rename.

Rules for backward-compatible event changes:
1. **Adding fields**: always safe — consumers that don't know the field ignore it.
2. **Removing fields**: breaking — consumers that depend on the field will fail. Never remove; deprecate (keep the field, mark as optional, stop populating after consumers migrate).
3. **Renaming fields**: equivalent to adding new + removing old. Transition: add the new field alongside the old for N deployments, remove old after all consumers use the new.
4. **Changing types**: almost always breaking. Widen carefully (e.g., `int` → `float` may be safe; `string` → `object` is breaking).

```typescript
// Version strategy on the event envelope
interface LoanCreatedEventV1 {
  eventVersion: '1.0';
  payload: { loanId: string; amount: number; }
}

interface LoanCreatedEventV2 {
  eventVersion: '2.0';
  payload: {
    loanId: string;
    amount: number;
    currency: 'INR';         // new field — consumers on v1 ignore this safely
    product?: string;         // optional — not set in v1, set in v2
  }
}

// Consumer handles both versions:
async function handleLoanCreated(event: LoanCreatedEventV1 | LoanCreatedEventV2) {
  const currency = event.eventVersion === '2.0'
    ? event.payload.currency
    : 'INR';                  // default for v1 events
}
```

For large teams: use a schema registry (Confluent Schema Registry for Kafka, AWS Glue Schema Registry for SNS/SQS) to enforce compatibility rules at publish time — the broker rejects incompatible schema changes before they reach consumers.

## Section 5: Reliability & Error Handling

**Q14. How do you handle consumer failures and retries in a Pub/Sub system?**
A: The retry strategy depends on the broker:

**SQS (built-in retry + DLQ):**
```typescript
// SQS automatically retries failed messages up to maxReceiveCount
// Consumer signals failure by NOT deleting the message (throws exception)
// After maxReceiveCount retries, SQS moves message to DLQ

@SqsMessageHandler('loan-events-queue', false)  // false = manual ack
async handleMessage(message: SQS.Message): Promise<void> {
  try {
    const event = JSON.parse(message.Body!);
    await this.processEvent(event);
    // Explicitly delete on success:
    await this.sqsService.deleteMessage('loan-events-queue', message.ReceiptHandle!);
  } catch (error) {
    // Do NOT delete → SQS will redeliver → eventually routes to DLQ
    this.logger.error('Processing failed', error);
    throw error;
  }
}
```

**Kafka (manual offset commit):**
```typescript
// Do NOT commit offset on failure → same message will be redelivered
// For permanent failures: publish to a separate retry topic with backoff metadata
async handleWithRetry(event: LoanEvent, context: KafkaContext) {
  const receiveCount = event.__retryCount ?? 0;

  if (receiveCount >= 5) {
    await this.publishToDLQ(event);
    await this.commitOffset(context);   // commit to skip poison pill
    return;
  }

  try {
    await this.processEvent(event);
    await this.commitOffset(context);
  } catch (error) {
    // Publish to retry topic with incremented count + exponential delay metadata
    await this.retryProducer.send({
      topic: 'loan-events-retry',
      messages: [{ value: JSON.stringify({ ...event, __retryCount: receiveCount + 1 }) }]
    });
    await this.commitOffset(context);   // commit original — retry topic handles redeliver
  }
}
```

**Q15. What is the Outbox Pattern and why is it critical for reliable event publishing in fintech?**
A: The Outbox Pattern solves the dual-write problem: publishing an event to the broker must be atomic with writing to the database — otherwise, the DB write succeeds but the event publish fails (or vice versa), leaving the system in an inconsistent state.

```
Problem (without outbox):
  BEGIN TRANSACTION
    INSERT INTO loans (...)         ← succeeds
  COMMIT
  await sns.publish(...)            ← fails! Loan exists in DB but no event published.
  → KYC never triggered. Loan stuck.

Solution (with outbox):
  BEGIN TRANSACTION
    INSERT INTO loans (...)
    INSERT INTO outbox_events (topic, payload, status='PENDING')
  COMMIT                            ← both writes are atomic

  [Outbox Processor (separate job)]:
    SELECT * FROM outbox_events WHERE status = 'PENDING'
    await sns.publish(event.payload)
    UPDATE outbox_events SET status = 'PUBLISHED'
```

```typescript
// TypeORM transaction with outbox
@Injectable()
export class LoanService {
  async createLoan(dto: CreateLoanDto): Promise<Loan> {
    return this.dataSource.transaction(async manager => {
      const loan = await manager.save(Loan, dto);

      await manager.save(OutboxEvent, {
        id: uuid(),
        topic: 'loan-events',
        eventType: 'LOAN_CREATED',
        payload: JSON.stringify({
          loanId: loan.id,
          applicantId: loan.applicantId,
          amount: loan.amount,
        }),
        status: 'PENDING',
        createdAt: new Date(),
      });

      return loan;
    });
  }
}

// Outbox processor (runs every N seconds via @Cron)
@Injectable()
export class OutboxProcessor {
  @Cron('*/5 * * * * *')   // every 5 seconds
  async processOutbox(): Promise<void> {
    const pending = await this.outboxRepo.find({
      where: { status: 'PENDING' },
      take: 100,
      order: { createdAt: 'ASC' },
    });

    for (const event of pending) {
      try {
        await this.sns.publish({ TopicArn: TOPIC_MAP[event.topic], Message: event.payload });
        await this.outboxRepo.update(event.id, { status: 'PUBLISHED' });
      } catch (err) {
        await this.outboxRepo.update(event.id, {
          status: 'FAILED',
          retryCount: () => 'retry_count + 1',
        });
      }
    }
  }
}
```

In an RBI-regulated fintech context, the Outbox Pattern is non-negotiable for loan lifecycle events, NACH mandate events, and repayment webhooks — any event where a missed publish means a missed regulatory action.

**Q16. How do you implement message filtering in SNS, and when should filtering happen at the broker vs the consumer?**
A: SNS supports **filter policies** that prevent the broker from delivering messages to a subscriber unless the message attributes match the policy. This is broker-side filtering — the consumer never receives (or pays for) messages it would discard anyway.

```typescript
// SNS filter policy: KYC queue only receives LOAN_CREATED events
const subscriptionAttributes = {
  FilterPolicy: JSON.stringify({
    eventType: ['LOAN_CREATED', 'LOAN_RESUBMITTED'],
    product: ['PERSONAL_LOAN', 'BUSINESS_LOAN'],   // not GOLD_LOAN
  }),
};

await sns.send(new SubscribeCommand({
  TopicArn: LOAN_EVENTS_TOPIC_ARN,
  Protocol: 'sqs',
  Endpoint: KYC_QUEUE_ARN,
  Attributes: subscriptionAttributes,
}));
```

**Broker filtering vs Consumer filtering:**

| | Broker Filtering | Consumer Filtering |
|---|---|---|
| Where | SNS filter policy, Kafka header filtering | Consumer code checks and discards |
| Cost | Reduces SQS receives, Lambda invocations | Consumer pays for all messages |
| Latency | Lower — message never queued | Higher — message travels to consumer |
| Flexibility | Limited to message attributes/metadata | Can filter on payload content |
| Debugging | Harder — messages silently not delivered | Consumer logs filtered messages |

Rule of thumb: filter by event type and coarse category at the broker (SNS filter policy). Filter by payload content or business logic at the consumer.

## Section 6: Observability & Operations

**Q17. How do you trace a Pub/Sub event end-to-end in a distributed system?**
A: Because Pub/Sub is asynchronous, a standard synchronous request trace (parent → child spans) breaks at the queue boundary. The solution is **trace context propagation** via the event envelope:

```typescript
// Publisher: inject trace context into the event
import { trace, context, propagation } from '@opentelemetry/api';

async publishLoanEvent(loanId: string): Promise<void> {
  const carrier: Record<string, string> = {};
  propagation.inject(context.active(), carrier);   // injects traceparent, tracestate

  await sns.send(new PublishCommand({
    TopicArn: LOAN_EVENTS_TOPIC_ARN,
    Message: JSON.stringify({ loanId, traceContext: carrier }),
    MessageAttributes: {
      traceparent: { DataType: 'String', StringValue: carrier['traceparent'] }
    }
  }));
}

// Consumer: extract and continue the trace
async handleLoanCreated(message: SQSMessage): Promise<void> {
  const event = JSON.parse(message.Body!);
  const parentContext = propagation.extract(
    context.active(),
    event.traceContext ?? {},
  );

  await context.with(parentContext, async () => {
    const span = trace.getTracer('kyc-service').startSpan('kyc.initiate');
    try {
      await this.kycService.initiate(event.loanId);
      span.end();
    } catch (err) {
      span.recordException(err as Error);
      span.end();
      throw err;
    }
  });
}
```

Minimum observability checklist for production Pub/Sub:
- `correlationId` and `eventId` on every event
- Metrics: `messages_published_total`, `messages_consumed_total`, `consumer_lag`, `processing_duration_ms`, `dlq_depth`
- Alerts: DLQ depth > 0, consumer lag growing, processing error rate > threshold
- Structured logs with `eventId`, `eventType`, `topic`, `partition`, `offset` (Kafka) in every consumer log line

**Q18. How do you handle consumer lag, and what causes it?**
A: Consumer lag is the difference between the latest produced message offset and the latest consumed message offset. A growing lag means consumers are falling behind producers.

```
Producer writes at offset 10,000
Consumer has processed up to offset 8,000
Consumer lag = 2,000 messages
```

Common causes and fixes:

| Cause | Fix |
|---|---|
| Consumer is slow (heavy DB write per message) | Batch DB writes; optimize consumer logic |
| Consumer has too few instances | Scale out consumers (up to partition count for Kafka) |
| Downstream dependency is throttled (CIBIL rate limit) | Implement backoff + bulkhead; decouple via local queue |
| Message storm (burst of events) | Increase consumer instances; add concurrency; use SQS to buffer |
| Poison pill message (always fails, consuming retries) | Fix DLQ setup; the retry loop is consuming consumer threads |

const admin = kafka.admin();

const consumerOffsets = await admin.fetchOffsets({ groupId: 'kyc-service', topics: ['loan-events'] });
// lag per partition = latestOffset - committedOffset

## Section 7: Fintech & Indian Regulatory Context

**Q19. How does Pub/Sub apply to the Indian loan origination lifecycle?**
A: A loan application in an Indian fintech goes through a sequence of events naturally modelled as Pub/Sub:

```
[loan.application.submitted]
        │
        ├──► KYC Service         (UIDAI Aadhaar OTP / DigiLocker / VKYC)
        ├──► Bureau Pull Service (CIBIL / Experian / Equifax via Karza)
        └──► Fraud Check Service (device intelligence, blacklist)

[loan.kyc.completed] + [loan.bureau.pulled]
        │
        ▼ (orchestrated by Saga / state machine)
[loan.underwriting.triggered]
        │
        ├──► Decisioning Engine
        └──► Offer Engine

[loan.approved]
        │
        ├──► Disbursement Service (NACH mandate registration / UPI payout)
        ├──► Notification Service (SMS / WhatsApp via DLT-registered templates)
        ├──► Audit Logger         (RBI audit trail — immutable event log)
        └──► CRM Sync            (Salesforce / Leadsquared)
```

Each `→` is a topic. Events flow asynchronously; no service directly calls another. This satisfies RBI's requirement for audit trails — every state change is an immutable event on the broker, reconstructable at any time.

**Q20. What are the compliance considerations for Pub/Sub event data in an Indian fintech context?**
A: Key constraints under RBI and Indian data protection law:

1. **Data residency**: Event brokers (Kafka, SNS) must be in AWS `ap-south-1` (Mumbai) or equivalent India-region infrastructure. Cross-border transfer of Aadhaar-linked data is restricted.
2. **PII in events**: Never publish raw Aadhaar numbers, PAN, full card numbers, or bank account numbers in event payloads. Use references/tokens. Events are often logged in multiple places — a breach of the broker exposes all event history.
3. **Audit trail**: RBI mandates tamper-proof audit logs. Kafka (with topic-level retention + compaction and no deletion) serves as an immutable ledger. Alternatively, route all events to an append-only S3 bucket via Kinesis Firehose.
4. **Encryption**: Encrypt sensitive event payloads at the application layer (AWS KMS envelope encryption) before publishing — even if the broker enforces TLS in transit and encryption at rest.
5. **DLT-registered templates**: If the Pub/Sub event triggers an SMS notification, the message content must match a DLT-registered template (TRAI regulation). The Notification Service consumer must enforce template selection based on `eventType`.

**Q22. "What does this code output, and what is the bug?"**

```typescript
class PaymentService {
  private readonly amount = 1000;
  private readonly handlers: Map<string, Function[]> = new Map();

  on(event: string, handler: Function) {
    if (!this.handlers.has(event)) this.handlers.set(event, []);
    this.handlers.get(event)!.push(handler);
  }

  emit(event: string, data: unknown) {
    (this.handlers.get(event) ?? []).forEach(function(handler) {
      handler(data, this.amount);   // Bug here
    });
  }

  start() {
    this.on('payment.received', (data: unknown, amount: number) => {
      console.log(`Processing ₹${amount} payment`);
    });
    this.emit('payment.received', { txnId: 'TXN001' });
  }
}

new PaymentService().start();
```

A: The output is `Processing ₹undefined payment`, and the code throws no error because `undefined` is coerced. The bug is in `emit`: the `forEach` callback uses a regular `function`, so `this` inside it is determined by the call site — `forEach` invokes it as a plain function, making `this` the global object (or `undefined` in strict mode). `this.amount` is `undefined`, not `1000`.

Fix: replace the regular function with an arrow function:

```typescript
emit(event: string, data: unknown) {
  (this.handlers.get(event) ?? []).forEach((handler) => {   // arrow — captures PaymentService's this
    handler(data, this.amount);   // ✓ this = PaymentService instance
  });
}
```

This is the same implicit binding loss from Q6 of the `this` guide — classic `forEach` with a regular function callback.

**Q23. "Fix the three Pub/Sub bugs in this NestJS service."**

```typescript
@Injectable()
export class LoanEventService implements OnModuleInit {
  constructor(
    private readonly eventEmitter: EventEmitter2,
    private readonly kycService: KycService,
  ) {}

  onModuleInit() {
    // Bug 1
    this.eventEmitter.on('loan.created', this.handleLoanCreated);

    // Bug 2
    this.eventEmitter.on('loan.*', this.handleAnyLoanEvent);
  }

  async handleLoanCreated(event: LoanCreatedEvent) {
    await this.kycService.initiate(event.loanId);   // Bug 1 manifests here
  }

  handleAnyLoanEvent(event: unknown) {
    console.log('Received loan event:', event);     // Bug 2 manifests here
  }

  async publishLoanEvent(loanId: string) {
    this.eventEmitter.emit('loan.created', { loanId });
    this.eventEmitter.emit('loan.created', { loanId });   // Bug 3
  }
}
```

A:
- **Bug 1**: `this.handleLoanCreated` is passed as a callback — implicit binding loss. `this` inside `handleLoanCreated` will be `undefined` (strict mode), so `this.kycService` throws. Fix: `this.eventEmitter.on('loan.created', this.handleLoanCreated.bind(this))` or use a class field arrow.
- **Bug 2**: Wildcard `loan.*` requires `EventEmitter2` to be configured with `{ wildcard: true }` in `EventEmitterModule.forRoot()`. Without it, the wildcard is treated as a literal event name and will never match. Fix: `EventEmitterModule.forRoot({ wildcard: true, delimiter: '.' })`.
- **Bug 3**: The event is emitted twice with the same payload in the same synchronous flow. KYC will be initiated twice for the same loan — a dangerous duplicate in a fintech system. Fix: remove the duplicate emit; ensure the calling code is idempotent or that the outbox processor deduplicates by `eventId`.

## Quick Reference Table

| Broker | Delivery Guarantee | Ordering | Persistence | Fan-out | Best For |
|---|---|---|---|---|---|
| Redis Pub/Sub | At-most-once | Yes (per channel) | No | Yes | Cache invalidation, real-time signals |
| Redis Streams | At-least-once | Yes | Yes | Consumer groups | Lightweight event sourcing |
| SQS Standard | At-least-once | No | 14 days | No (1 consumer) | Task queues, worker distribution |
| SQS FIFO | At-least-once | Yes (300 TPS) | 14 days | No | Ordered task queues |
| SNS + SQS | At-least-once | Via FIFO | Via SQS | Yes | Microservice fan-out on AWS |
| Kafka | At-least-once / Exactly-once | Per partition | Configurable | Consumer groups | Streaming, event sourcing, high volume |
| RabbitMQ | At-least-once | Per queue | Configurable | Exchange routing | Complex routing, legacy integration |

| Pattern | Problem Solved | Key Mechanism |
|---|---|---|
| Outbox Pattern | Atomic DB write + event publish | Write event to DB table; separate publisher reads and forwards |
| Dead Letter Queue | Poison pill messages; consumer failures | Route failed messages after N retries; alert on DLQ depth |
| Consumer Group | Load-balance event processing | Multiple consumers share partitions; one partition → one consumer |
| Idempotency Key | At-least-once → effectively exactly-once | Store `eventId` in Redis/DB; skip if already processed |
| Filter Policy | Reduce noise; broker-side routing | SNS MessageAttributes; Kafka headers |
| Trace Propagation | End-to-end async tracing | Inject `traceparent` in event; extract in consumer |
| Schema Registry | Enforce backward compatibility | Confluent / Glue Schema Registry; reject breaking changes at publish |

---

**Tip for interviews:** Five things separate strong candidates on Pub/Sub: (1) articulating **why** Pub/Sub (temporal + spatial decoupling) — not just what it is; (2) immediately identifying the **dual-write problem** and naming the Outbox Pattern as the fix when asked about reliable event publishing in financial systems; (3) being precise about **delivery semantics** — at-most/at-least/exactly-once — and explaining why idempotent consumers are required in at-least-once systems; (4) knowing the **consumer group model** in Kafka — distinguishing fan-out across groups from load-balancing within a group — a high-signal question for streaming experience; and (5) tying everything back to **fintech constraints** — PII in event payloads (don't), RBI data residency (`ap-south-1`), and audit trail via immutable event log — this signals production domain depth that generic pattern knowledge doesn't.
