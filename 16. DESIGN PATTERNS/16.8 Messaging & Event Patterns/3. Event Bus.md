# Event Bus: Messaging & Event Patterns (Design Patterns) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an Event Bus, and what fundamental problem does it solve in software architecture?**
A: An Event Bus is a communication mechanism that allows different parts of a system — components, modules, or services — to communicate with each other without having direct references to one another. It implements the **publish/subscribe (pub/sub) pattern**: publishers emit events onto the bus; subscribers register interest in specific event types and are notified when those events occur. Neither side knows about the other.

The fundamental problem it solves: **tight coupling**. Without an event bus, component A that needs to notify component B must hold a direct reference to B, know B's API, and call B's methods explicitly. With an event bus, A only knows about the event ("something happened"), and B only knows what event it cares about — A and B are completely decoupled. This is the source of almost every scalability and maintainability benefit the pattern provides.

```javascript
// Without Event Bus — tight coupling
class OrderService {
  constructor(emailService, inventoryService, analyticsService) {
    this.emailService = emailService;
    this.inventoryService = inventoryService;
    this.analyticsService = analyticsService;
  }

  placeOrder(order) {
    // OrderService must know about and call every downstream service
    this.emailService.sendConfirmation(order);
    this.inventoryService.deduct(order);
    this.analyticsService.track('order_placed', order);
  }
}

// With Event Bus — decoupled
class OrderService {
  constructor(eventBus) {
    this.eventBus = eventBus;
  }

  placeOrder(order) {
    // OrderService only knows about the event — nothing downstream
    this.eventBus.emit('order:placed', order);
  }
}

// Subscribers register independently — OrderService doesn't know they exist
eventBus.on('order:placed', order => emailService.sendConfirmation(order));
eventBus.on('order:placed', order => inventoryService.deduct(order));
eventBus.on('order:placed', order => analyticsService.track('order_placed', order));
```

**Q2. What are the core components of an Event Bus and what role does each play?**
A: Every event bus implementation, regardless of language or scale, has four logical components:

1. **Event** — the unit of communication. Contains a type/name (a string identifier like `'user:created'`) and a payload (the data relevant to what happened). Events are typically plain data objects — they should not contain behavior.
2. **Publisher (Producer/Emitter)** — the component that detects something noteworthy happened and emits an event onto the bus. It has no knowledge of who (if anyone) is listening.
3. **Subscriber (Consumer/Listener/Handler)** — the component that registers interest in one or more event types and provides a callback to execute when a matching event is emitted. It has no knowledge of who published the event.
4. **Event Bus (Broker/Dispatcher)** — the central registry that maintains a mapping of event types to subscriber callbacks, routes emitted events to the correct subscribers, and manages subscription lifecycles (registration and removal).

```javascript
// The four components in a minimal implementation
class EventBus {
  constructor() {
    this.listeners = new Map();   // The registry: event type → [callbacks]
  }

  // Subscriber registers interest
  on(event, callback) {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, []);
    }
    this.listeners.get(event).push(callback);
    return this; // enable chaining
  }

  // Publisher emits an event with a payload
  emit(event, data) {
    if (!this.listeners.has(event)) return;
    this.listeners.get(event).forEach(cb => cb(data));
  }

  // Subscription lifecycle management
  off(event, callback) {
    if (!this.listeners.has(event)) return;
    const updated = this.listeners.get(event).filter(cb => cb !== callback);
    this.listeners.set(event, updated);
  }
}
```

**Q3. How does the Event Bus pattern relate to Observer, Mediator, and Pub/Sub — and what are the distinctions?**
A: These patterns are closely related and often conflated. Understanding their distinctions is a signal of real design depth:

- **Observer Pattern**: Subjects maintain a list of observers and notify them directly. There is a direct reference from subject to observer — the subject must know its observers exist and call them explicitly. This is still coupling at the reference level, just abstracted.
- **Mediator Pattern**: A central mediator object encapsulates how a set of objects interact. The mediator contains application logic about *how* components interact. This is explicitly aware of the participants.
- **Pub/Sub Pattern**: Publishers and subscribers are fully decoupled — neither knows the other. A message broker (the bus) handles routing. Pub/Sub is typically considered a superset of Observer that adds the indirection layer.
- **Event Bus**: A concrete implementation of the Pub/Sub pattern, often within a single process (in-memory). When the bus crosses process boundaries (network, message queues), it's typically called a **message broker** (RabbitMQ, Kafka, Redis Pub/Sub).

```
Observer:    Subject ─────────────────────► Observer(s)
             (direct reference, subject knows observers)

Mediator:    ComponentA ──► Mediator ◄── ComponentB
             (mediator knows everyone, contains logic)

Pub/Sub:     Publisher ──► [Bus] ──► Subscriber(s)
Event Bus:   (no direct reference in either direction)
```

The key differentiator: in an Event Bus / Pub/Sub, the publisher doesn't hold a reference to subscribers, and subscribers don't hold a reference to publishers. The bus is the only shared dependency, and even then, components only depend on the bus interface — not on each other.

**Q4. What is the difference between synchronous and asynchronous event buses, and when does each matter?**
A: In a **synchronous event bus**, when `emit()` is called, all subscriber callbacks are invoked immediately and sequentially before `emit()` returns. The publisher effectively blocks until all handlers complete. In an **asynchronous event bus**, `emit()` schedules handler invocations (via microtasks, macrotasks, or a dedicated queue) and returns immediately — handlers run later.

```javascript
// Synchronous: publisher blocks until all handlers finish
emit(event, data) {
  this.listeners.get(event)?.forEach(cb => cb(data));  // blocks
}

// Asynchronous (microtask queue via Promise):
emit(event, data) {
  this.listeners.get(event)?.forEach(cb =>
    Promise.resolve().then(() => cb(data))             // schedules, doesn't block
  );
}

// Asynchronous (macrotask via setTimeout):
emit(event, data) {
  this.listeners.get(event)?.forEach(cb =>
    setTimeout(() => cb(data), 0)
  );
}
```

| Concern | Synchronous | Asynchronous |
|---|---|---|
| Error propagation | One failing handler can block or crash others | Errors are isolated; bus continues |
| Execution order | Guaranteed — handlers run in registration order | Not guaranteed across macrotasks |
| Return values | Handlers can return values to publisher | Return values are impractical |
| Performance | Blocking — slow handlers stall publisher | Non-blocking — publisher continues immediately |
| Debugging | Easier — stack traces are contiguous | Harder — async stack traces are fragmented |

For UI state management (e.g., a frontend event bus), synchronous is often acceptable. For distributed or backend systems, or anywhere a slow handler must not stall the publisher, async is the right default.

## Section 2: Implementation Patterns

**Q5. Build a production-quality in-memory Event Bus from scratch in JavaScript.**
A: A production-quality implementation needs: typed events, one-time listeners, wildcard/namespaced events, error isolation between handlers, and memory leak prevention.

```javascript
class EventBus {
  #listeners = new Map();    // event → Set of { callback, once }
  #maxListeners = 10;        // warn on likely memory leaks

  on(event, callback, options = {}) {
    if (typeof callback !== 'function') {
      throw new TypeError(`Event handler for "${event}" must be a function`);
    }
    if (!this.#listeners.has(event)) {
      this.#listeners.set(event, new Set());
    }
    const handlers = this.#listeners.get(event);
    if (handlers.size >= this.#maxListeners) {
      console.warn(
        `EventBus: "${event}" has ${handlers.size} listeners. Possible memory leak.`
      );
    }
    const entry = { callback, once: Boolean(options.once) };
    handlers.add(entry);

    // Return an unsubscribe function (cleanup pattern)
    return () => this.off(event, callback);
  }

  once(event, callback) {
    return this.on(event, callback, { once: true });
  }

  off(event, callback) {
    if (!this.#listeners.has(event)) return;
    const handlers = this.#listeners.get(event);
    for (const entry of handlers) {
      if (entry.callback === callback) {
        handlers.delete(entry);
        break;
      }
    }
    if (handlers.size === 0) {
      this.#listeners.delete(event);   // prevent empty Set accumulation
    }
  }

  emit(event, data) {
    if (!this.#listeners.has(event)) return false;
    const handlers = [...this.#listeners.get(event)];  // snapshot before iteration
    for (const entry of handlers) {
      try {
        entry.callback(data);
      } catch (err) {
        // Isolate errors — one bad handler doesn't kill the others
        console.error(`EventBus: Error in handler for "${event}":`, err);
      }
      if (entry.once) {
        this.off(event, entry.callback);
      }
    }
    return true;  // signal: at least one handler ran
  }

  removeAllListeners(event) {
    if (event) {
      this.#listeners.delete(event);
    } else {
      this.#listeners.clear();
    }
  }

  listenerCount(event) {
    return this.#listeners.get(event)?.size ?? 0;
  }

  eventNames() {
    return [...this.#listeners.keys()];
  }
}

// Usage
const bus = new EventBus();
const unsubscribe = bus.on('user:created', user => console.log('New user:', user.name));
bus.once('app:init', () => console.log('App initialized — fires once only'));
bus.emit('user:created', { name: 'Alice', id: 1 });
unsubscribe();   // clean up without needing a reference to the callback
```

**Q6. What is the "unsubscribe" or cleanup problem, and what patterns solve it?**
A: A **memory leak** occurs when subscribers register on the bus but never unregister — their callbacks (and everything in their closure) remain in memory indefinitely. This is the Event Bus equivalent of a `removeEventListener` omission. Three patterns solve it:

```javascript
// Pattern 1: Return an unsubscribe function (modern, ergonomic)
const unsub = bus.on('data:updated', handler);
// ... when component unmounts or is destroyed:
unsub();

// Pattern 2: Explicit off() with stored reference (traditional)
const handler = (data) => { /* ... */ };
bus.on('data:updated', handler);
// ... cleanup:
bus.off('data:updated', handler);
// Pitfall: anonymous functions can't be removed — always store the reference

// Pattern 3: Namespaced/scoped buses with mass cleanup (framework pattern)
// Give each component its own subscriptions tracker
class Component {
  #subscriptions = [];

  subscribe(event, handler) {
    const unsub = globalBus.on(event, handler);
    this.#subscriptions.push(unsub);
  }

  destroy() {
    this.#subscriptions.forEach(unsub => unsub());
    this.#subscriptions = [];
  }
}

// Pattern 4: WeakRef-based auto-cleanup (advanced)
// Store WeakRef to subscriber object; during emit, check if alive
class WeakEventBus {
  #listeners = new Map();

  on(event, callback, owner) {
    const ref = new WeakRef(owner);
    const wrappedCallback = (data) => {
      if (ref.deref()) {          // owner still alive?
        callback.call(ref.deref(), data);
      } else {
        this.off(event, wrappedCallback);  // auto-clean
      }
    };
    // ... rest of registration
  }
}
```

The returning-unsubscribe pattern (Pattern 1) is the modern industry standard, used by RxJS (`subscription.unsubscribe()`), React (`useEffect` return), and most modern state management libraries.

**Q7. How do you implement typed events in TypeScript with an Event Bus?**
A: TypeScript's type system can enforce that event names and their payload types are consistent at compile time — eliminating a whole class of runtime bugs where a subscriber expects `{ userId: string }` but receives `{ id: number }`.

```typescript
// Define the event map: event name → payload type
interface AppEvents {
  'user:created': { id: string; name: string; email: string };
  'user:deleted': { id: string };
  'order:placed': { orderId: string; total: number; items: string[] };
  'app:error': Error;
}

class TypedEventBus<TEvents extends Record<string, unknown>> {
  private listeners = new Map<
    keyof TEvents,
    Set<(data: TEvents[keyof TEvents]) => void>
  >();

  on<K extends keyof TEvents>(
    event: K,
    callback: (data: TEvents[K]) => void
  ): () => void {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    const handlers = this.listeners.get(event)!;
    handlers.add(callback as (data: TEvents[keyof TEvents]) => void);
    return () => this.off(event, callback);
  }

  emit<K extends keyof TEvents>(event: K, data: TEvents[K]): void {
    this.listeners.get(event)?.forEach(cb => cb(data as TEvents[keyof TEvents]));
  }

  off<K extends keyof TEvents>(
    event: K,
    callback: (data: TEvents[K]) => void
  ): void {
    this.listeners.get(event)?.delete(
      callback as (data: TEvents[keyof TEvents]) => void
    );
  }
}

const bus = new TypedEventBus<AppEvents>();

// ✅ TypeScript knows the payload shape
bus.on('user:created', user => {
  console.log(user.name);    // typed: string ✓
  console.log(user.id);      // typed: string ✓
});

// ✅ Emit is type-checked
bus.emit('user:created', { id: '1', name: 'Alice', email: 'a@b.com' });

// ❌ Compile-time error: 'age' does not exist on user:created payload
bus.emit('user:created', { id: '1', name: 'Alice', age: 30 });

// ❌ Compile-time error: unknown event name
bus.on('user:updated', handler);
```

**Q8. What is event namespacing and wildcards, and how do you implement them?**
A: **Event namespacing** uses delimited names like `'user:created'`, `'order:placed'`, or `'api.response.success'` to group related events hierarchically. **Wildcards** let subscribers listen to a namespace or pattern rather than a single event — e.g., `'user:*'` to catch all user events.

```javascript
class NamespacedEventBus {
  #listeners = new Map();

  on(pattern, callback) {
    if (!this.#listeners.has(pattern)) {
      this.#listeners.set(pattern, new Set());
    }
    this.#listeners.get(pattern).add(callback);
    return () => this.off(pattern, callback);
  }

  emit(event, data) {
    for (const [pattern, handlers] of this.#listeners) {
      if (this.#matches(pattern, event)) {
        handlers.forEach(cb => {
          try { cb(data, event); }   // pass the actual event name too
          catch (err) { console.error(err); }
        });
      }
    }
  }

  #matches(pattern, event) {
    if (pattern === event) return true;            // exact match
    if (pattern === '*') return true;              // global wildcard
    if (pattern.endsWith(':*')) {
      // namespace wildcard: 'user:*' matches 'user:created', 'user:deleted'
      const ns = pattern.slice(0, -2);
      return event.startsWith(ns + ':');
    }
    // Regex pattern support
    if (pattern instanceof RegExp) return pattern.test(event);
    return false;
  }

  off(pattern, callback) {
    this.#listeners.get(pattern)?.delete(callback);
  }
}

const bus = new NamespacedEventBus();

bus.on('user:*', (data, eventName) => {
  console.log(`User event: ${eventName}`, data);   // catches any user:X event
});

bus.on('*', (data, eventName) => {
  console.log(`Any event: ${eventName}`);          // global catch-all (for logging)
});

bus.emit('user:created', { name: 'Alice' });   // matched by 'user:*' and '*'
bus.emit('order:placed', { total: 99 });       // matched by '*' only
```

## Section 3: Advanced Patterns

**Q9. What is event sourcing, and how does it relate to the Event Bus pattern?**
A: **Event Sourcing** is an architectural pattern where state changes are stored as an immutable, ordered sequence of events rather than as current state snapshots. The Event Bus is the *delivery mechanism* for events; Event Sourcing is about *persisting and replaying* those events as the source of truth.

```javascript
class EventSourcedBus extends EventBus {
  #eventLog = [];    // immutable append-only log

  emit(event, data) {
    const entry = {
      id: crypto.randomUUID(),
      event,
      data,
      timestamp: Date.now(),
      version: this.#eventLog.length + 1,
    };
    this.#eventLog.push(Object.freeze(entry));   // immutable entries
    super.emit(event, entry);                    // distribute with full metadata
    return entry.id;
  }

  // Replay all past events to rebuild state
  replay(fromVersion = 0) {
    const toReplay = this.#eventLog.filter(e => e.version > fromVersion);
    for (const entry of toReplay) {
      super.emit(entry.event, entry);
    }
  }

  getHistory(event) {
    return this.#eventLog.filter(e => !event || e.event === event);
  }

  // Rebuild state from events (like Redux's reducer pattern)
  getState(reducer, initialState, eventFilter) {
    const events = eventFilter
      ? this.#eventLog.filter(e => e.event === eventFilter)
      : this.#eventLog;
    return events.reduce((state, entry) => reducer(state, entry), initialState);
  }
}
```

This is how systems like Redux and CQRS (Command Query Responsibility Segregation) work: the event log is the source of truth, and current state is derived by replaying events through a pure reducer function. The Event Bus provides real-time delivery; event sourcing provides historical auditability and state reconstruction.

**Q10. What is the dead letter queue pattern, and how does it make an event bus resilient?**
A: A **dead letter queue (DLQ)** is a secondary queue/store where events are placed when they cannot be successfully delivered — either because no handler is registered, or because all handlers threw errors. Without a DLQ, undeliverable events are silently dropped, a dangerous failure mode in production systems.

```javascript
class ResilientEventBus extends EventBus {
  #dlq = [];          // dead letter queue
  #dlqHandlers = [];  // subscribers to DLQ events

  emit(event, data) {
    const hasListeners = this.listenerCount(event) > 0;
    let successCount = 0;

    if (!hasListeners) {
      this.#sendToDLQ({ event, data, reason: 'NO_LISTENERS', timestamp: Date.now() });
      return false;
    }

    const handlers = [...this.listeners.get(event)];
    for (const entry of handlers) {
      try {
        entry.callback(data);
        successCount++;
      } catch (err) {
        this.#sendToDLQ({
          event,
          data,
          reason: 'HANDLER_ERROR',
          error: err.message,
          timestamp: Date.now(),
        });
      }
    }
    return successCount > 0;
  }

  #sendToDLQ(deadLetter) {
    this.#dlq.push(deadLetter);
    this.#dlqHandlers.forEach(cb => {
      try { cb(deadLetter); }
      catch { /* DLQ handlers must not throw */ }
    });
  }

  onDeadLetter(callback) {
    this.#dlqHandlers.push(callback);
  }

  // Retry DLQ entries
  retryDLQ(filter) {
    const toRetry = filter
      ? this.#dlq.filter(filter)
      : [...this.#dlq];
    this.#dlq = this.#dlq.filter(e => !toRetry.includes(e));
    toRetry.forEach(({ event, data }) => this.emit(event, data));
  }

  getDLQ() {
    return [...this.#dlq];
  }
}

const bus = new ResilientEventBus();
bus.onDeadLetter(dl => console.error('Undelivered event:', dl));
```

**Q11. How do you implement request/reply (request-response) over an Event Bus?**
A: Standard pub/sub is fire-and-forget — the publisher doesn't expect a reply. But sometimes you need a response (e.g., "get the current user count"). This is implemented by including a **reply-to channel** and a **correlation ID** in the request event, and having the handler emit a response event on that channel.

```javascript
class RequestReplyBus extends EventBus {
  request(event, data, timeoutMs = 5000) {
    return new Promise((resolve, reject) => {
      const correlationId = crypto.randomUUID();
      const replyChannel = `__reply__:${correlationId}`;

      const timer = setTimeout(() => {
        this.off(replyChannel, handler);
        reject(new Error(`Request "${event}" timed out after ${timeoutMs}ms`));
      }, timeoutMs);

      const handler = (response) => {
        clearTimeout(timer);
        this.off(replyChannel, handler);
        if (response.error) {
          reject(new Error(response.error));
        } else {
          resolve(response.data);
        }
      };

      this.once(replyChannel, handler);
      this.emit(event, { ...data, replyChannel, correlationId });
    });
  }

  reply(replyChannel, data, error = null) {
    this.emit(replyChannel, { data, error, timestamp: Date.now() });
  }
}

// Usage
const bus = new RequestReplyBus();

// Handler registers a service
bus.on('users:count', async ({ replyChannel }) => {
  const count = await db.users.count();
  bus.reply(replyChannel, count);
});

// Caller uses it like RPC
const count = await bus.request('users:count', {});
console.log(`Total users: ${count}`);
```

This pattern is how message brokers like RabbitMQ implement RPC semantics — the correlation ID and reply-to address are standard AMQP concepts that map directly to this JavaScript implementation.

**Q12. How does middleware (event interceptors) work on an Event Bus?**
A: Middleware lets you intercept events before they reach subscribers — useful for logging, validation, transformation, authentication, rate limiting, or metrics without polluting individual handlers.

```javascript
class MiddlewareEventBus extends EventBus {
  #middleware = [];

  use(fn) {
    this.#middleware.push(fn);
    return this;
  }

  emit(event, data) {
    // Build middleware chain (like Express/Koa)
    const chain = [...this.#middleware];
    let index = 0;

    const next = (currentEvent, currentData) => {
      if (index >= chain.length) {
        // All middleware passed — deliver to actual handlers
        super.emit(currentEvent, currentData);
        return;
      }
      const middleware = chain[index++];
      middleware(currentEvent, currentData, next);
    };

    next(event, data);
  }
}

const bus = new MiddlewareEventBus();

// Logging middleware
bus.use((event, data, next) => {
  console.log(`[${new Date().toISOString()}] EVENT: ${event}`, data);
  next(event, data);   // pass through
});

// Validation middleware
bus.use((event, data, next) => {
  if (!event || typeof event !== 'string') {
    throw new Error('Event name must be a non-empty string');
  }
  next(event, data);
});

// Transformation middleware
bus.use((event, data, next) => {
  // Attach metadata to all events
  next(event, {
    ...data,
    __meta: { emittedAt: Date.now(), env: process.env.NODE_ENV }
  });
});

// Rate limiting middleware
const rateLimiter = (() => {
  const counts = new Map();
  return (event, data, next) => {
    const count = (counts.get(event) || 0) + 1;
    counts.set(event, count);
    if (count > 100) {
      console.warn(`EventBus: Rate limit exceeded for "${event}"`);
      return;  // drop the event — don't call next()
    }
    next(event, data);
  };
})();
bus.use(rateLimiter);
```

## Section 4: Real-World Application Patterns

**Q13. How is the Event Bus pattern used in frontend frameworks — React, Vue, and vanilla component architectures?**
A: Frontend Event Bus usage differs by framework philosophy:

```javascript
// === React: Context + useReducer as a typed event bus ===
// React discourages global mutable event buses; the idiomatic version
// is a Context-based dispatch system (which IS a typed event bus)

const EventContext = React.createContext(null);

function AppProvider({ children }) {
  const busRef = useRef(new TypedEventBus());
  return (
    <EventContext.Provider value={busRef.current}>
      {children}
    </EventContext.Provider>
  );
}

function useEventBus() { return useContext(EventContext); }

function OrderButton() {
  const bus = useEventBus();
  return (
    <button onClick={() => bus.emit('order:placed', { total: 99 })}>
      Place Order
    </button>
  );
}

function OrderNotification() {
  const bus = useEventBus();
  const [message, setMessage] = useState('');
  useEffect(() => {
    const unsub = bus.on('order:placed', data => {
      setMessage(`Order placed: $${data.total}`);
    });
    return unsub;   // cleanup on unmount — critical!
  }, [bus]);
  return <div>{message}</div>;
}

// === Vue 3: mitt library (recommended minimal Event Bus) ===
import mitt from 'mitt';
const emitter = mitt();

// In component A (emit)
emitter.emit('user:selected', { id: 1 });

// In component B (subscribe)
onMounted(() => emitter.on('user:selected', handler));
onUnmounted(() => emitter.off('user:selected', handler));   // critical cleanup

// === Vanilla: module singleton ===
// event-bus.js — export a singleton so all modules share one bus
export const eventBus = new EventBus();

// component-a.js
import { eventBus } from './event-bus.js';
eventBus.emit('tab:changed', { tab: 'settings' });

// component-b.js
import { eventBus } from './event-bus.js';
const unsub = eventBus.on('tab:changed', ({ tab }) => renderTab(tab));
// store unsub and call in component teardown
```

**Q14. How does the Event Bus pattern map to backend message brokers like RabbitMQ, Kafka, and Redis Pub/Sub?**
A: An in-memory Event Bus and a distributed message broker solve the same conceptual problem at different scales. Understanding how they map is critical for production architecture conversations:

| Concept | In-Memory Event Bus | RabbitMQ | Apache Kafka | Redis Pub/Sub |
|---|---|---|---|---|
| Publisher | `bus.emit()` | Producer sends to Exchange | Producer sends to Topic | `PUBLISH channel msg` |
| Subscriber | `bus.on()` | Consumer binds Queue to Exchange | Consumer Group reads Topic | `SUBSCRIBE channel` |
| Routing | Pattern matching | Exchange routing keys, bindings | Topic partitions, consumer groups | Channel name |
| Persistence | None (in-memory) | Queue durability (configurable) | Log retention (days/forever) | None (fire-and-forget) |
| Delivery guarantee | At-most-once | At-least-once / exactly-once | At-least-once / exactly-once | At-most-once |
| Replay | Via event log pattern (Q9) | Not native | Native (offset reset) | Not native |
| Scale | Single process | Multi-process, multi-server | Millions of events/sec | Multi-process |
| Dead letters | Manual DLQ (Q10) | Native Dead Letter Exchange | Custom via consumer logic | Not native |

```javascript
// The conceptual mapping is direct — this Redis pub/sub code
// follows the same interface as the in-memory bus

const redis = require('ioredis');
const pub = new redis();
const sub = new redis();

// Publish (equivalent to bus.emit)
pub.publish('user:created', JSON.stringify({ id: 1, name: 'Alice' }));

// Subscribe (equivalent to bus.on)
sub.subscribe('user:created');
sub.on('message', (channel, message) => {
  const data = JSON.parse(message);
  console.log(`Channel: ${channel}`, data);
});
```

The architectural decision: use an in-memory bus within a single service (for intra-service decoupling), and a message broker between services (for inter-service decoupling and resilience).

**Q15. How is the Event Bus pattern used in Micro Frontend architectures?**
A: Micro Frontends split a UI into independently deployable vertical slices, each owned by a different team. The Event Bus is the primary communication mechanism between micro frontends — it lets them share state and react to each other without creating hard dependencies on each other's codebases.

```javascript
// shell.js — the host application exposes a shared bus on window
window.__MFE_BUS__ = new EventBus();

// user-mfe/index.js — User micro frontend
const bus = window.__MFE_BUS__;
bus.emit('user:authenticated', { userId: '123', role: 'admin' });

// cart-mfe/index.js — Cart micro frontend (different team, different repo)
const bus = window.__MFE_BUS__;
bus.on('user:authenticated', ({ userId }) => {
  cartService.loadCartForUser(userId);
});

// Product MFE emits, Shell and Cart react — zero direct coupling
const bus = window.__MFE_BUS__;
bus.on('product:added-to-cart', ({ product, quantity }) => {
  analytics.track('add_to_cart', { sku: product.sku, qty: quantity });
});
```

Key concerns in Micro Frontend event buses:

1. **Event contract versioning** — when MFE-A changes its event payload, MFE-B must not break. Event schemas need versioning (`{ version: 2, ...payload }`).
2. **Event ownership** — document which MFE owns (publishes) each event type. Multiple publishers of the same event type create confusion.
3. **Iframe isolation** — for hard-isolated MFEs in iframes, use `window.postMessage` instead, with the same pub/sub semantics but crossing the iframe boundary.

## Section 5: Testing, Debugging, and Pitfalls

**Q16. How do you unit test code that uses an Event Bus?**
A: Testable event-bus code depends on the bus being injected (dependency injection) rather than imported as a global singleton — making it trivially replaceable in tests:

```javascript
// ✅ Testable: bus is injected
class NotificationService {
  constructor(eventBus) {
    this.eventBus = eventBus;
    this.notifications = [];
    this.eventBus.on('order:placed', this.handleOrder.bind(this));
  }
  handleOrder(order) {
    this.notifications.push(`Order ${order.id} placed — total: $${order.total}`);
  }
}

// Test with a real bus instance (integration-style)
test('NotificationService adds notification on order:placed', () => {
  const bus = new EventBus();
  const service = new NotificationService(bus);

  bus.emit('order:placed', { id: '42', total: 99 });

  expect(service.notifications).toHaveLength(1);
  expect(service.notifications[0]).toContain('Order 42 placed');
});

// Test with a mock bus (unit-style — fast, isolated)
test('NotificationService subscribes to order:placed on construction', () => {
  const mockBus = {
    on: jest.fn().mockReturnValue(jest.fn()),
    emit: jest.fn(),
  };
  new NotificationService(mockBus);
  expect(mockBus.on).toHaveBeenCalledWith('order:placed', expect.any(Function));
});

// Test that a component emits the right event
test('OrderService emits order:placed with correct payload', () => {
  const bus = new EventBus();
  const handler = jest.fn();
  bus.on('order:placed', handler);

  const orderService = new OrderService(bus);
  orderService.placeOrder({ id: '1', items: ['A'] });

  expect(handler).toHaveBeenCalledTimes(1);
  expect(handler).toHaveBeenCalledWith(expect.objectContaining({ id: '1' }));
});
```

**Q17. What are the most common Event Bus pitfalls and anti-patterns?**
A: Six pitfalls that appear repeatedly in production codebases:

```javascript
// ❌ Anti-pattern 1: Forgetting to unsubscribe (memory leak)
class UserWidget {
  init() {
    globalBus.on('user:updated', this.render.bind(this));
    // When UserWidget is destroyed, the handler stays in memory forever
  }
  destroy() {
    // Missing: globalBus.off('user:updated', ...) — leak!
  }
}

// ❌ Anti-pattern 2: Using anonymous functions (can't unsubscribe)
bus.on('data:loaded', data => this.setState(data));
// You can never call bus.off('data:loaded', ???) for this handler

// ❌ Anti-pattern 3: God bus — everything goes through one bus,
// creating invisible coupling between unrelated modules
bus.on('*', (event, data) => {   // one module listening to everything
  if (event === 'user:updated') { /* ... */ }
  if (event === 'order:placed') { /* ... */ }
  if (event === 'theme:changed') { /* ... */ }
  // This module now implicitly depends on every other module
});

// ❌ Anti-pattern 4: Events with side effects that must complete synchronously
bus.emit('save:before', document);
// Assuming all save logic ran before the next line — dangerous with async handlers

// ❌ Anti-pattern 5: Circular events (infinite loops)
bus.on('counter:increment', count => {
  bus.emit('counter:increment', count + 1);  // infinite loop!
});

// ❌ Anti-pattern 6: Putting logic in event names instead of payloads
// Bad: a separate event for every variant
bus.emit('user:created:admin');
bus.emit('user:created:readonly');
// Good: one event, differentiated by payload
bus.emit('user:created', { role: 'admin' });
```

**Q18. How do you add observability (logging, tracing, metrics) to an Event Bus?**
A: Observability is best added via middleware (Q12) or by wrapping the bus — never by polluting individual handlers:

```javascript
function createObservableEventBus(bus, options = {}) {
  const { logger = console, metrics } = options;

  return new Proxy(bus, {
    get(target, prop) {
      if (prop === 'emit') {
        return function(event, data) {
          const startTime = performance.now();
          logger.info({ event, data, timestamp: Date.now() }, 'Event emitted');
          const result = target.emit.call(target, event, data);
          const duration = performance.now() - startTime;
          metrics?.histogram('event_bus.emit.duration', duration, { event });
          metrics?.increment('event_bus.events_total', { event });
          return result;
        };
      }
      if (prop === 'on') {
        return function(event, callback) {
          metrics?.increment('event_bus.subscriptions_total', { event });
          return target.on.call(target, event, callback);
        };
      }
      return Reflect.get(target, prop);
    }
  });
}

const bus = createObservableEventBus(new EventBus(), {
  logger: pinoLogger,
  metrics: datadogMetrics,
});
```

## Section 6: Scenario-Based Questions

**Q19. "What does this output, and why?"**

```javascript
const bus = new EventBus();

bus.on('tick', data => console.log('A:', data));
bus.on('tick', data => console.log('B:', data));
bus.once('tick', data => console.log('C:', data));

bus.emit('tick', 1);
bus.emit('tick', 2);
```

A: Walking through each emission:

- **First `emit('tick', 1)`**: All three handlers are registered. They fire in registration order (A, B, C). After the `once` handler (C) fires, it is automatically removed. Output:
  ```
  A: 1
  B: 1
  C: 1
  ```
- **Second `emit('tick', 2)`**: Only A and B remain — C was removed after its first invocation. Output:
  ```
  A: 2
  B: 2
  ```

This tests understanding of `once()` semantics, registration order, and that `once` removal happens *after* the handler fires (not before).

**Q20. "There's a bug — this component leaks memory. Identify it and write three fixes."**

```javascript
class LiveFeed extends HTMLElement {
  connectedCallback() {
    globalBus.on('feed:update', data => {
      this.innerHTML = data.html;
    });
  }

  disconnectedCallback() {
    // runs when element is removed from DOM
  }
}
```

A: The bug: `connectedCallback` registers a new handler on `globalBus` every time the element is connected to the DOM (e.g., moved, re-inserted). `disconnectedCallback` never unregisters it. After 10 reconnections, 10 handlers are registered — each holding a reference to `this` (the element) and all its closures.

```javascript
// Fix 1: Store and remove (explicit off)
class LiveFeed extends HTMLElement {
  #handler = null;

  connectedCallback() {
    this.#handler = data => { this.innerHTML = data.html; };
    globalBus.on('feed:update', this.#handler);
  }

  disconnectedCallback() {
    if (this.#handler) {
      globalBus.off('feed:update', this.#handler);
      this.#handler = null;
    }
  }
}

// Fix 2: Use unsubscribe function pattern
class LiveFeed extends HTMLElement {
  #unsub = null;

  connectedCallback() {
    this.#unsub = globalBus.on('feed:update', data => {
      this.innerHTML = data.html;
    });
  }

  disconnectedCallback() {
    this.#unsub?.();
    this.#unsub = null;
  }
}

// Fix 3: AbortController for multi-subscription cleanup
class LiveFeed extends HTMLElement {
  #controller = null;

  connectedCallback() {
    this.#controller = new AbortController();
    const { signal } = this.#controller;
    globalBus.on('feed:update', data => {
      this.innerHTML = data.html;
    }, { signal });   // bus checks signal.aborted before calling handler
  }

  disconnectedCallback() {
    this.#controller?.abort();
  }
}
```

**Q21. "Refactor this tightly coupled code to use an Event Bus. What tradeoffs does the refactor introduce?"**

```javascript
// Before: tight coupling
class CheckoutService {
  constructor() {
    this.emailService = new EmailService();
    this.inventoryService = new InventoryService();
    this.loyaltyService = new LoyaltyService();
    this.analyticsService = new AnalyticsService();
  }

  async checkout(cart, user) {
    const order = await this.createOrder(cart, user);
    await this.emailService.sendReceipt(order, user);
    await this.inventoryService.reserve(order);
    await this.loyaltyService.awardPoints(order, user);
    this.analyticsService.track('checkout', order);
    return order;
  }
}
```

A:

```javascript
// After: Event Bus decoupling
class CheckoutService {
  constructor(eventBus) {
    this.eventBus = eventBus;
  }

  async checkout(cart, user) {
    const order = await this.createOrder(cart, user);
    this.eventBus.emit('order:completed', { order, user });
    return order;
  }
}

// Subscribers register independently — CheckoutService doesn't know they exist
eventBus.on('order:completed', ({ order, user }) =>
  emailService.sendReceipt(order, user));
eventBus.on('order:completed', ({ order }) =>
  inventoryService.reserve(order));
eventBus.on('order:completed', ({ order, user }) =>
  loyaltyService.awardPoints(order, user));
eventBus.on('order:completed', ({ order }) =>
  analyticsService.track('checkout', order));
```

Tradeoffs introduced by the refactor:

| Aspect | Before (Direct Calls) | After (Event Bus) |
|---|---|---|
| Flow traceability | Explicit — read `checkout()` to see all effects | Implicit — must trace bus subscriptions |
| Error handling | `try/catch` covers all operations | Each handler fails independently |
| Execution order | Guaranteed sequential | Determined by registration order |
| Testing | Mock each service individually | Test publisher and subscriber separately |
| Adding new reactions | Modify `CheckoutService` | Add new subscriber anywhere |
| Removing reactions | Modify `CheckoutService` | Remove subscriber registration |
| Transactionality | Can wrap in a DB transaction | Cannot atomically wrap all handlers |

The refactor wins when the set of reactions is open-ended or ownership is distributed. It is the wrong choice when transactionality, strict ordering, or immediate error feedback is required (e.g., payment processing — you need to know synchronously if the charge failed).

## Quick Reference Table

| Concept | Description | Key Method |
|---|---|---|
| Subscribe | Register handler for event type | `bus.on(event, handler)` |
| Unsubscribe | Remove registered handler | `bus.off(event, handler)` / `unsub()` |
| Publish | Emit event to all subscribers | `bus.emit(event, data)` |
| One-time subscribe | Fire once, then auto-remove | `bus.once(event, handler)` |
| Wildcard subscribe | Listen to event namespace | `bus.on('user:*', handler)` |
| Middleware | Intercept all events before delivery | `bus.use(fn)` |
| Dead letter queue | Catch undeliverable events | `bus.onDeadLetter(handler)` |
| Request/reply | Two-way communication over bus | `bus.request(event, data)` |

| Binding Rule | Memory Leak Risk | Mitigation |
|---|---|---|
| `bus.on()` without `off()` | High | Store unsubscribe fn; call in teardown |
| Anonymous function in `on()` | High | Named function or store reference |
| `once()` | None | Auto-removed after first fire |
| `bus.on()` in constructor | Medium | Ensure `off()` called in destructor |
| Global singleton bus | High | Per-component scoped bus or cleanup tracking |

| Scale | Solution | Persistence | Delivery |
|---|---|---|---|
| Single component | Module EventEmitter | None | Synchronous |
| Single app | Singleton EventBus | None | Sync or async |
| Multi-tab browser | BroadcastChannel API | None | Async |
| Multi-process | Redis Pub/Sub | None | Async |
| Multi-service | RabbitMQ / Kafka | Configurable | At-least-once |

**Tip for interviews:** Five things separate strong candidates on Event Bus: (1) articulating that the bus solves **coupling**, not just communication — explaining that without it, A and B must know each other is more precise than "it lets components talk"; (2) immediately flagging **memory leaks from missing unsubscribes** and knowing two or three unsubscribe patterns cold (return-unsubscribe-fn, WeakRef, AbortController); (3) distinguishing **in-memory Event Bus from distributed message brokers** (Kafka, RabbitMQ) — knowing when you outgrow the former and need the latter; (4) knowing the tradeoffs of **event-driven flow vs direct calls** — the bus makes reactions implicit and debugging harder, and being able to say *when not to use it* (transactional operations) shows real judgment; and (5) walking through the **TypeScript typed event map pattern** (Q7) — knowing that untyped string events create an invisible API boundary that breaks silently demonstrates production-level thinking beyond the basic pattern.
