# Structural Design Patterns: Adapter — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Adapter pattern?**
A: Adapter is a structural design pattern that allows two incompatible interfaces to work together by wrapping one object in an adapter that translates calls from the interface the client expects into calls the adaptee understands. It's the software equivalent of a power plug adapter — the wall socket (adaptee) and your device (client) haven't changed; the adapter bridges the mismatch between them.

The three roles in every Adapter implementation:
- **Client** — the code that expects a specific interface (`Target`).
- **Adaptee** — the existing class or external API with the incompatible interface.
- **Adapter** — the wrapper that implements `Target` and delegates to the `Adaptee`, translating between the two.

**Q2. What problem does Adapter solve? When should you reach for it?**
A: Adapter solves the **interface mismatch** problem — when you have a class or external API you want to use, but its interface doesn't match what your existing code expects. Reach for it when:
- Integrating a **third-party library or external API** whose interface you can't modify (bureau APIs, payment gateways, SMS vendors).
- **Reusing legacy code** that works correctly but has a different interface from what new code expects.
- Making **multiple providers** behind a uniform interface so the rest of the system doesn't care which one is active (CIBIL vs Experian, Razorpay vs PayU).
- Writing an **anti-corruption layer** in DDD — preventing an external system's data model from leaking into your domain model.

**Q3. What is the difference between a Class Adapter and an Object Adapter?**
A:

| Aspect                      | Class Adapter                                        | Object Adapter                                         |
|-----------------------------|------------------------------------------------------|--------------------------------------------------------|
| Mechanism                   | Inherits from both `Target` and `Adaptee`            | Implements `Target`, holds an `Adaptee` instance       |
| Language requirement        | Requires multiple inheritance (C++, not TypeScript)  | Works in any language — composition over inheritance   |
| Coupling                    | Tightly coupled to one specific `Adaptee` subclass   | Loosely coupled — accepts any `Adaptee` at runtime     |
| Overridability              | Can override `Adaptee` methods selectively           | Cannot override `Adaptee` internals                    |
| Preferred in TypeScript?    | Rarely — TypeScript has no true multiple inheritance | **Yes — this is the standard pattern in TS/JS**        |

TypeScript supports `implements` for multiple interfaces but not `extends` from multiple classes, making the Object Adapter (composition) the natural choice in practice.

**Q4. How does Adapter differ from Facade, Decorator, and Proxy?**
A: All four wrap another object, but their intent differs:

| Pattern       | Intent                                                                 | Changes interface? | Adds behaviour? |
|---------------|------------------------------------------------------------------------|--------------------|-----------------|
| **Adapter**   | Make an incompatible interface compatible with what the client expects | Yes — translates   | No              |
| **Facade**    | Simplify a complex subsystem behind a single, unified interface        | Yes — simplifies   | No              |
| **Decorator** | Add new behaviour to an object at runtime without changing its class   | No — same interface | Yes            |
| **Proxy**     | Control access to an object (lazy load, cache, auth, logging)         | No — same interface | Optionally     |

The clearest distinguishing question: *does the interface need to change?* Adapter: yes. Decorator/Proxy: no. Facade: yes, but to simplify a *subsystem*, not to reconcile two specific interfaces.

**Q5. What is an "anti-corruption layer" and how does it relate to Adapter?**
A: An anti-corruption layer (ACL) is a DDD concept — a translation layer that prevents an external system's domain model, terminology, and data structures from leaking into your bounded context. The Adapter pattern is the most common implementation mechanism for an ACL. Without it, your internal `Loan` domain model starts carrying fields like `CIBIL_SCORE_V2_BAND`, `BUREAU_INTERNAL_REF`, or `NPCI_MANDATE_URN` — vocabulary and structures that belong to external systems, not your domain.

The ACL/Adapter translates:
- External data shapes → internal domain objects
- Internal domain objects → external API request formats
- External error codes → internal domain exceptions

## Section 2: Implementation

**Q6. What does a canonical TypeScript Object Adapter look like?**
A: A clean three-part implementation — target interface, adaptee, adapter:

```typescript
// Target interface — what the rest of your system expects
interface BureauAdapter {
  fetchCreditReport(pan: string): Promise<CreditReport>;
}

// Internal domain type
interface CreditReport {
  pan: string;
  score: number;
  activeAccounts: number;
  overdueAccounts: number;
  enquiriesLast6Months: number;
}

// Adaptee — CIBIL's actual SDK / API client (interface you cannot change)
class CibilSdkClient {
  async getCibilReport(panNumber: string, memberRefNo: string): Promise<CibilRawResponse> {
    // Makes the actual CIBIL API call
    return cibilApiCall(panNumber, memberRefNo);
  }
}

interface CibilRawResponse {
  PANNumber: string;
  Score: { Value: number; Version: string };
  AccountSummary: { Active: number; Overdue: number };
  Enquiries: { Last6Months: number };
  ResponseCode: string;
  ErrorMessage?: string;
}

// Adapter — bridges CibilSdkClient → BureauAdapter
class CibilBureauAdapter implements BureauAdapter {
  constructor(
    private readonly client: CibilSdkClient,
    private readonly memberRefNo: string,
  ) {}

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const raw = await this.client.getCibilReport(pan, this.memberRefNo);

    if (raw.ResponseCode !== '00') {
      throw new BureauUnavailableException(`CIBIL error: ${raw.ErrorMessage}`);
    }

    // Translation: CIBIL's shape → your domain shape
    return {
      pan: raw.PANNumber,
      score: raw.Score.Value,
      activeAccounts: raw.AccountSummary.Active,
      overdueAccounts: raw.AccountSummary.Overdue,
      enquiriesLast6Months: raw.Enquiries.Last6Months,
    };
  }
}
```

```typescript
// Consumer — depends only on BureauAdapter, knows nothing of CibilSdkClient
@Injectable()
export class UnderwritingService {
  constructor(private readonly bureau: BureauAdapter) {}

  async assess(pan: string): Promise<RiskDecision> {
    const report = await this.bureau.fetchCreditReport(pan);
    if (report.score < 650) return { decision: 'REJECT', reason: 'LOW_SCORE' };
    if (report.overdueAccounts > 0) return { decision: 'REJECT', reason: 'OVERDUE_ACCOUNTS' };
    return { decision: 'APPROVE' };
  }
}
```

**Q7. How do you wire the Adapter in a NestJS dependency injection container?**
A: Register the adapter as the provider for the interface token. The consumer injects the token and never knows which concrete adapter is behind it:

```typescript
// bureau.module.ts
@Module({
  providers: [
    CibilSdkClient,
    {
      provide: 'BUREAU_ADAPTER',   // injection token for the interface
      useClass: CibilBureauAdapter,
    },
  ],
  exports: ['BUREAU_ADAPTER'],
})
export class BureauModule {}

// underwriting.service.ts — consumer
@Injectable()
export class UnderwritingService {
  constructor(
    @Inject('BUREAU_ADAPTER') private readonly bureau: BureauAdapter,
  ) {}
}
```

Swapping from CIBIL to Experian now requires one line change in `BureauModule` — `useClass: ExperianBureauAdapter` — with zero changes in `UnderwritingService` or any other consumer. This is the Open/Closed Principle in action via Adapter.

**Q8. How do you implement a two-way (bidirectional) Adapter that translates in both directions?**
A: Some integrations require translating both requests *to* the external system and responses *from* it. Structure the adapter with explicit inbound and outbound mapping methods:

```typescript
interface NachGatewayAdapter {
  // Outbound: domain → external
  registerMandate(mandate: DomainMandate): Promise<MandateRegistrationResult>;
  // Inbound: external → domain
  parseCallback(payload: unknown): DomainMandateCallback;
}

class NpciNachAdapter implements NachGatewayAdapter {
  async registerMandate(mandate: DomainMandate): Promise<MandateRegistrationResult> {
    // Outbound translation: domain shape → NPCI NACH API format
    const npciPayload: NpciMandateRequest = {
      UMRN: mandate.id,
      CustomerName: mandate.accountHolderName,
      IFSCCode: mandate.ifsc,
      AccountNumber: mandate.accountNumber,
      AccountType: mandate.accountType === 'savings' ? 'SB' : 'CA',
      Amount: mandate.maxAmount.toFixed(2),
      StartDate: formatNpciDate(mandate.startDate),
      FrequencyType: 'MNTH',
      SponsorBankCode: process.env.SPONSOR_BANK_CODE!,
    };

    const response = await this.npciClient.register(npciPayload);

    return {
      success: response.Status === 'SUCCESS',
      referenceId: response.UMRN,
      failureReason: response.ErrorDescription ?? null,
    };
  }

  parseCallback(payload: unknown): DomainMandateCallback {
    // Inbound translation: NPCI callback format → domain event
    const npci = payload as NpciCallbackPayload;
    return {
      mandateId: npci.UMRN,
      status: npci.TxnStatus === 'SUCCESS' ? 'ACTIVE' : 'FAILED',
      bankReferenceNumber: npci.BankRefNo,
      processedAt: parseNpciDate(npci.TxnDate),
    };
  }
}
```

**Q9. How do you handle versioning when an external API releases a breaking change?**
A: Create a new versioned adapter and swap at the DI level — existing consumers remain unchanged:

```typescript
// Original adapter for CIBIL v1
class CibilV1BureauAdapter implements BureauAdapter {
  async fetchCreditReport(pan: string): Promise<CreditReport> { /* v1 logic */ }
}

// New adapter for CIBIL v2 — score field moved, new enquiry structure
class CibilV2BureauAdapter implements BureauAdapter {
  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const raw = await this.client.getReportV2(pan);
    return {
      pan: raw.personal.pan,
      score: raw.creditProfile.cibilScore,      // moved in v2
      activeAccounts: raw.accounts.filter(a => a.active).length,
      overdueAccounts: raw.accounts.filter(a => a.overdue).length,
      enquiriesLast6Months: raw.enquiries.recent6m,  // renamed in v2
    };
  }
}

// bureau.module.ts — switch adapter version here only
{ provide: 'BUREAU_ADAPTER', useClass: CibilV2BureauAdapter }
```

The adapter acts as a versioning firewall — external API churn never reaches your domain code.

## Section 3: Adapter in Real-World Fintech Contexts

**Q10. How would you use Adapter to unify CIBIL, Experian, and Karza under one interface?**
A: Define one `BureauAdapter` interface and write a separate adapter for each provider. A strategy or factory selects the right adapter at runtime:

```typescript
interface BureauAdapter {
  fetchCreditReport(pan: string): Promise<CreditReport>;
  fetchCreditScore(pan: string): Promise<number>;
}

// Three independent adapters — each translates its provider's quirks
class CibilBureauAdapter implements BureauAdapter { /* ... */ }
class ExperianBureauAdapter implements BureauAdapter { /* ... */ }
class KarzaBureauAdapter implements BureauAdapter { /* ... */ }

// Factory — selects adapter by product/segment rule
@Injectable()
export class BureauAdapterFactory {
  constructor(
    private readonly cibil: CibilBureauAdapter,
    private readonly experian: ExperianBureauAdapter,
    private readonly karza: KarzaBureauAdapter,
  ) {}

  for(segment: CustomerSegment): BureauAdapter {
    if (segment === 'MSME') return this.karza;
    if (segment === 'NRI') return this.experian;
    return this.cibil; // default for retail salaried
  }
}

// Underwriting service — completely decoupled from which bureau is used
@Injectable()
export class UnderwritingService {
  constructor(private readonly bureauFactory: BureauAdapterFactory) {}

  async assess(applicant: Applicant): Promise<RiskDecision> {
    const bureau = this.bureauFactory.for(applicant.segment);
    const report = await bureau.fetchCreditReport(applicant.pan);
    return this.evaluate(report);
  }
}
```

Adding a fourth bureau (CRIF Highmark) requires writing one new adapter class — zero changes to `UnderwritingService` or any business logic.

**Q11. How would you use Adapter to integrate multiple payment gateways (Razorpay, PayU, Cashfree) for loan disbursement?**
A: Exactly the same structure — one target interface, multiple adapters, factory selection:

```typescript
interface PaymentGatewayAdapter {
  initiateTransfer(transfer: DisbursementTransfer): Promise<TransferResult>;
  checkTransferStatus(transferId: string): Promise<TransferStatus>;
  parseWebhook(payload: unknown, signature: string): DomainPaymentEvent;
}

interface DisbursementTransfer {
  referenceId: string;
  amount: number;          // in paise
  accountNumber: string;
  ifsc: string;
  beneficiaryName: string;
  purpose: 'LOAN_DISBURSEMENT';
}

// Razorpay adapter — translates to Razorpay's payout API
class RazorpayGatewayAdapter implements PaymentGatewayAdapter {
  async initiateTransfer(transfer: DisbursementTransfer): Promise<TransferResult> {
    const payload = {
      account_number: process.env.RAZORPAY_SOURCE_ACCOUNT,
      amount: transfer.amount,                        // Razorpay also uses paise
      currency: 'INR',
      mode: 'NEFT',
      purpose: 'payout',
      fund_account: {
        account_type: 'bank_account',
        bank_account: {
          name: transfer.beneficiaryName,
          ifsc: transfer.ifsc,
          account_number: transfer.accountNumber,
        },
      },
      reference_id: transfer.referenceId,
    };
    const result = await this.razorpayClient.payouts.create(payload);
    return {
      gatewayTransferId: result.id,
      status: result.status === 'processing' ? 'PENDING' : 'INITIATED',
    };
  }

  parseWebhook(payload: unknown, signature: string): DomainPaymentEvent {
    this.verifySignature(payload, signature); // Razorpay-specific HMAC check
    const event = payload as RazorpayWebhookPayload;
    return {
      referenceId: event.payload.payout.entity.reference_id,
      status: event.event === 'payout.processed' ? 'SUCCESS' : 'FAILED',
      gatewayRef: event.payload.payout.entity.id,
      processedAt: new Date(event.payload.payout.entity.processed_at * 1000),
    };
  }
}

// PayU adapter — completely different API shape, same output interface
class PayUGatewayAdapter implements PaymentGatewayAdapter {
  async initiateTransfer(transfer: DisbursementTransfer): Promise<TransferResult> {
    // PayU uses its own field names and formats — translated here
    const payload = {
      merchantKey: process.env.PAYU_KEY,
      txnId: transfer.referenceId,
      beneficiaryAccountNo: transfer.accountNumber,
      beneficiaryIFSC: transfer.ifsc,
      beneficiaryName: transfer.beneficiaryName,
      amount: (transfer.amount / 100).toFixed(2), // PayU uses rupees, not paise
      mode: 'NEFT',
    };
    const result = await this.payuClient.transfer(payload);
    return {
      gatewayTransferId: result.mihpayid,
      status: 'PENDING',
    };
  }

  parseWebhook(payload: unknown, signature: string): DomainPaymentEvent { /* ... */ }
}
```

`DisbursementService` calls `gateway.initiateTransfer(transfer)` and never knows if it's Razorpay or PayU.

**Q12. How does the Adapter pattern apply to SMS and notification providers (Twilio, AWS SNS, Kaleyra)?**
A: Notification providers have wildly different SDKs and API signatures. Adapter normalizes them:

```typescript
interface SmsAdapter {
  send(to: string, message: string, templateId?: string): Promise<SmsResult>;
}

interface SmsResult {
  messageId: string;
  status: 'SENT' | 'FAILED';
  failureReason?: string;
}

// Kaleyra adapter — common in Indian fintech for DLT-registered templates
class KaleyraSmsdapter implements SmsAdapter {
  async send(to: string, message: string, templateId?: string): Promise<SmsResult> {
    const response = await this.kaleyraClient.messages.create({
      to: `91${to}`,
      from: process.env.KALEYRA_SENDER_ID,
      body: message,
      type: 'TXN',
      template_id: templateId,
      dlt_te_id: templateId,          // DLT Template Entity ID — TRAI mandate
    });
    return {
      messageId: response.id,
      status: response.status === 'sent' ? 'SENT' : 'FAILED',
    };
  }
}

// AWS SNS adapter — used when already on AWS infra
class AwsSnsAdapter implements SmsAdapter {
  async send(to: string, message: string): Promise<SmsResult> {
    const command = new PublishCommand({
      PhoneNumber: `+91${to}`,
      Message: message,
      MessageAttributes: {
        'AWS.SNS.SMS.SMSType': { DataType: 'String', StringValue: 'Transactional' },
      },
    });
    const response = await this.snsClient.send(command);
    return {
      messageId: response.MessageId!,
      status: 'SENT',
    };
  }
}
```

**Q13. How would you build an Adapter for the DigiLocker API to normalize document verification across eKYC providers?**
A: DigiLocker returns documents in a government-specific format with Aadhaar XML, driving license data, etc. The adapter translates these into your domain's `VerifiedDocument` type:

```typescript
interface KycDocumentAdapter {
  fetchAadhaar(accessToken: string): Promise<VerifiedDocument>;
  fetchPanCard(accessToken: string): Promise<VerifiedDocument>;
  fetchDrivingLicense(accessToken: string): Promise<VerifiedDocument>;
}

interface VerifiedDocument {
  type: 'AADHAAR' | 'PAN' | 'DRIVING_LICENSE';
  holderName: string;
  idNumber: string;            // masked where applicable
  dateOfBirth: Date;
  isVerified: boolean;
  verifiedAt: Date;
  rawPayload?: Record<string, unknown>; // audit trail
}

class DigiLockerKycAdapter implements KycDocumentAdapter {
  async fetchAadhaar(accessToken: string): Promise<VerifiedDocument> {
    const xml = await this.digiLockerClient.getAadhaarXml(accessToken);
    const parsed = parseAadhaarXml(xml); // DigiLocker returns signed Aadhaar XML

    return {
      type: 'AADHAAR',
      holderName: `${parsed.POA.name}`,
      idNumber: `XXXX-XXXX-${parsed.uid.slice(-4)}`, // mask per UIDAI guidelines
      dateOfBirth: parseAadhaarDate(parsed.POI.dob),
      isVerified: parsed['@_status'] === '1',
      verifiedAt: new Date(),
      rawPayload: parsed,
    };
  }

  async fetchPanCard(accessToken: string): Promise<VerifiedDocument> {
    const data = await this.digiLockerClient.getIssuedDocument(accessToken, 'PAN');
    return {
      type: 'PAN',
      holderName: data.IssuedTo.Person.name,
      idNumber: data.PermanentAccountNumber,
      dateOfBirth: new Date(data.IssuedTo.Person.dob),
      isVerified: true,
      verifiedAt: new Date(),
    };
  }
}
```

Your KYC service works with clean `VerifiedDocument` objects. If DigiLocker changes its API schema (which it has, multiple times), only the adapter changes.

## Section 4: Adapter and Testing

**Q14. How does the Adapter pattern dramatically simplify testing of services that call external APIs?**
A: Because consumers depend on the `BureauAdapter` interface — not the concrete `CibilSdkClient` — tests inject a mock adapter instead of making real API calls:

```typescript
describe('UnderwritingService', () => {
  let service: UnderwritingService;
  let mockBureau: jest.Mocked<BureauAdapter>;

  beforeEach(async () => {
    mockBureau = {
      fetchCreditReport: jest.fn(),
      fetchCreditScore: jest.fn(),
    };

    const module = await Test.createTestingModule({
      providers: [
        UnderwritingService,
        { provide: 'BUREAU_ADAPTER', useValue: mockBureau },
      ],
    }).compile();

    service = module.get(UnderwritingService);
  });

  it('should reject applicant with score below threshold', async () => {
    mockBureau.fetchCreditReport.mockResolvedValue({
      pan: 'ABCDE1234F',
      score: 580,
      activeAccounts: 3,
      overdueAccounts: 0,
      enquiriesLast6Months: 2,
    });

    const result = await service.assess('ABCDE1234F');
    expect(result.decision).toBe('REJECT');
    expect(result.reason).toBe('LOW_SCORE');
  });

  it('should reject despite good score when overdue accounts exist', async () => {
    mockBureau.fetchCreditReport.mockResolvedValue({
      pan: 'ABCDE1234F', score: 740, activeAccounts: 4,
      overdueAccounts: 1, enquiriesLast6Months: 1,
    });

    const result = await service.assess('ABCDE1234F');
    expect(result.decision).toBe('REJECT');
    expect(result.reason).toBe('OVERDUE_ACCOUNTS');
  });
});
```

No network calls, no CIBIL credentials, no test account needed. The adapter interface is the seam — tests inject their own implementation of that seam.

**Q15. How do you write integration tests specifically for the Adapter itself?**
A: The adapter's job is translation — test it in isolation by feeding it known raw responses and asserting the translated output:

```typescript
describe('CibilBureauAdapter', () => {
  let adapter: CibilBureauAdapter;
  let mockClient: jest.Mocked<CibilSdkClient>;

  beforeEach(() => {
    mockClient = { getCibilReport: jest.fn() } as any;
    adapter = new CibilBureauAdapter(mockClient, 'TEST-MEMBER-REF');
  });

  it('should correctly translate CIBIL raw response to domain CreditReport', async () => {
    mockClient.getCibilReport.mockResolvedValue({
      PANNumber: 'ABCDE1234F',
      Score: { Value: 742, Version: 'V2' },
      AccountSummary: { Active: 3, Overdue: 0 },
      Enquiries: { Last6Months: 1 },
      ResponseCode: '00',
    });

    const report = await adapter.fetchCreditReport('ABCDE1234F');

    expect(report.pan).toBe('ABCDE1234F');
    expect(report.score).toBe(742);
    expect(report.activeAccounts).toBe(3);
    expect(report.overdueAccounts).toBe(0);
    expect(report.enquiriesLast6Months).toBe(1);
  });

  it('should throw BureauUnavailableException on non-zero response code', async () => {
    mockClient.getCibilReport.mockResolvedValue({
      PANNumber: 'ABCDE1234F',
      Score: { Value: 0, Version: '' },
      AccountSummary: { Active: 0, Overdue: 0 },
      Enquiries: { Last6Months: 0 },
      ResponseCode: '03',
      ErrorMessage: 'Consumer not found',
    });

    await expect(adapter.fetchCreditReport('ABCDE1234F'))
      .rejects.toThrow(BureauUnavailableException);
  });
});
```

Translation logic is complex and error-prone — it deserves its own test suite. When CIBIL ships a new response field or renames one, these tests catch the regression immediately.

## Section 5: Anti-patterns & Pitfalls

**Q16. What are the most common mistakes when implementing the Adapter pattern?**
A:

- **Leaking the adaptee's types into the consumer** — if your `UnderwritingService` imports `CibilRawResponse` directly, you've defeated the purpose. The adapter must be the *only* place that knows about the external type.
- **Fattening the adapter with business logic** — the adapter should translate, not decide. If you're writing `if (score > 700) return 'APPROVED'` inside `CibilBureauAdapter`, that business logic belongs in `UnderwritingService`.
- **One adapter for too many providers** — a `BureauAdapter` class with `if (provider === 'CIBIL') ... else if (provider === 'EXPERIAN')...` is not an adapter, it's a dispatcher. Each provider gets its own adapter class.
- **Forgetting error translation** — external APIs return provider-specific error codes. The adapter must translate these into your domain exceptions (`BureauUnavailableException`, `InvalidPanException`) — not let raw HTTP 422s or provider error objects escape into your business layer.
- **Not versioning the interface** — if your `BureauAdapter` interface changes every time a provider adds a new field, consumers break unnecessarily. Design the interface around *your domain's needs*, not the provider's capabilities. Add optional fields conservatively.

**Q17. How do you avoid the "adapter sprawl" problem when you have many external integrations?**
A: Adapter sprawl — dozens of small adapter files with no consistent structure — is managed by:

- **Consistent naming convention** — `{Provider}{Domain}Adapter` (e.g., `CibilBureauAdapter`, `RazorpayGatewayAdapter`, `KaleyraNotificationAdapter`).
- **Module-per-integration structure** — each external integration lives in its own NestJS module (`credit-bureau/`, `payment-gateway/`, `notification/`) with the adapter, the SDK client, its DTOs, and its tests co-located.
- **Shared interface package** — for monorepos, define all adapter interfaces in a shared `interfaces/` package that all modules import. The interface is the stable contract; adapter implementations are the volatile details.
- **Integration tests per adapter** — each adapter has its own test file that validates the translation contract, making it safe to refactor the internals.

```
src/
  credit-bureau/
    credit-bureau.module.ts
    adapters/
      cibil-bureau.adapter.ts
      experian-bureau.adapter.ts
      karza-bureau.adapter.ts
    interfaces/
      bureau-adapter.interface.ts
    dto/
      credit-report.dto.ts
  payment-gateway/
    adapters/
      razorpay-gateway.adapter.ts
      payu-gateway.adapter.ts
    interfaces/
      payment-gateway-adapter.interface.ts
```

**Q18. What is the difference between an Adapter and a simple wrapper/helper function? When does a wrapper become an Adapter?**
A: A wrapper function translates a call for convenience without the intent of interface compatibility. It becomes an Adapter when:
- It implements a **formally defined interface** (`implements BureauAdapter`) that the rest of the system depends on.
- It exists specifically to **reconcile two different interface shapes** — not just to add a utility layer.
- Its **output type is a domain type**, not the external type — the translation into domain vocabulary is what makes it an Adapter.

A function like `const report = cibil.getCibilReport(pan)` is a wrapper. A class that `implements BureauAdapter`, takes a `CibilSdkClient`, calls `getCibilReport`, and returns a `CreditReport` domain object — that's an Adapter.

## Section 6: Scenario / System Design Style Questions

**Q19. "Your fintech company is switching credit bureau providers from CIBIL to Experian for a specific loan product. How do you manage the migration using the Adapter pattern?"**
A: The Adapter pattern makes this a configuration change, not a code change:

```typescript
// Step 1 — write ExperianBureauAdapter (already structured identically)
class ExperianBureauAdapter implements BureauAdapter {
  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const raw = await this.experianClient.getReport({ pan, product: 'PERSONAL_LOAN' });
    return {
      pan: raw.applicantDetails.pan,
      score: raw.creditScore.experianScore,
      activeAccounts: raw.tradeLines.filter(t => t.active).length,
      overdueAccounts: raw.tradeLines.filter(t => t.defaulted).length,
      enquiriesLast6Months: raw.inquiries.last6MonthCount,
    };
  }
}

// Step 2 — feature-flag-controlled swap in BureauModule
{
  provide: 'BUREAU_ADAPTER',
  useFactory: (config: ConfigService, cibil: CibilBureauAdapter, experian: ExperianBureauAdapter) => {
    return config.get('BUREAU_PROVIDER') === 'EXPERIAN' ? experian : cibil;
  },
  inject: [ConfigService, CibilBureauAdapter, ExperianBureauAdapter],
}
```

Zero changes to `UnderwritingService`. The rollout is controlled by a feature flag. Both adapters coexist — rollback is a config change. A/B testing between providers becomes trivial.

**Q20. "You're reviewing a PR where a developer added a NACH debit method directly to `LoanService` by calling the NPCI client inline. What concerns do you raise and how do you refactor?"**
A: Multiple concerns:
- `LoanService` now has a direct dependency on `NpciClient` — an external SDK with a specific interface — creating coupling between your domain logic and an infrastructure detail.
- The NPCI-specific field names (`UMRN`, `SponsorBankCode`, `FrequencyType: 'MNTH'`) are now embedded in domain code, making future gateway changes require touching `LoanService`.
- The error handling is likely in NPCI terms (`NpciErrorCode.INVALID_ACCOUNT`) rather than domain terms (`InvalidBankAccountException`), forcing `LoanService` to understand NPCI's error model.
- Testing `LoanService` now requires mocking `NpciClient` — an integration detail that shouldn't appear in a domain service's test.

Refactoring:
```typescript
// Extract the adapter — one-time cost
class NpciNachAdapter implements NachAdapter {
  async debitEmi(debit: EmiDebitRequest): Promise<DebitResult> {
    // All NPCI-specific logic here — UMRN, field mapping, error translation
  }
}

// LoanService — back to domain language only
@Injectable()
export class LoanService {
  constructor(
    @Inject('NACH_ADAPTER') private readonly nach: NachAdapter,
  ) {}

  async collectEmi(loanId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    const result = await this.nach.debitEmi({ loanId, amount: loan.emiAmount });
    if (!result.success) throw new EmiCollectionFailedException(result.failureReason);
    await this.loanRepo.markEmiCollected(loanId);
  }
}
```

**Q21. "Design the integration layer for a new lending product that must support three SMS providers with automatic failover. How do you use Adapter here?"**
A: Adapter per provider, plus a failover orchestrator that the consumer sees as a single `SmsAdapter`:

```typescript
// Three adapters — each independently swappable
class KaleyraSmsdapter implements SmsAdapter { /* ... */ }
class AwsSnsAdapter implements SmsAdapter { /* ... */ }
class Msg91SmsAdapter implements SmsAdapter { /* ... */ }

// Failover adapter — itself implements SmsAdapter, wraps others
class FailoverSmsAdapter implements SmsAdapter {
  constructor(private readonly providers: SmsAdapter[]) {}

  async send(to: string, message: string, templateId?: string): Promise<SmsResult> {
    let lastError: Error | undefined;

    for (const provider of this.providers) {
      try {
        const result = await provider.send(to, message, templateId);
        if (result.status === 'SENT') return result;
      } catch (err) {
        lastError = err as Error;
        // log degraded provider, continue to next
      }
    }

    throw new SmsDeliveryFailedException(`All SMS providers failed. Last: ${lastError?.message}`);
  }
}

// NestJS wiring — consumer sees only SmsAdapter
{
  provide: 'SMS_ADAPTER',
  useFactory: (kaleyra, sns, msg91) =>
    new FailoverSmsAdapter([kaleyra, sns, msg91]),  // priority order
  inject: [KaleyraSmsdapter, AwsSnsAdapter, Msg91SmsAdapter],
}
```

`NotificationService` calls `this.sms.send(...)` — completely unaware of the failover logic or which provider is active. The `FailoverSmsAdapter` is itself an Adapter (implements the same interface) that composes three adapters. This is the Composite + Adapter combination — common in production notification systems.

## Quick Reference: Adapter Pattern Checklist

| Signal                                                                 | What to Do                                                                 |
|------------------------------------------------------------------------|----------------------------------------------------------------------------|
| Calling external SDK methods directly inside a domain service          | Extract an Adapter — push the external API behind an interface             |
| External API field names appearing in your domain models               | Anti-corruption layer needed — Adapter is the mechanism                    |
| Switching providers requires changing business logic files             | Your Adapter isn't isolating enough — move all provider logic into it      |
| Unit testing a service requires mocking an external SDK                | The service depends on a concrete class — introduce an interface + Adapter |
| Two providers with same capability but different API shapes            | One interface, two Adapter implementations, factory to select              |
| External API releases breaking changes regularly                       | Versioned Adapters — `CibilV1Adapter`, `CibilV2Adapter` — swap at DI level |
| Error codes from external system leaking into business layer           | Adapter must translate external errors to domain exceptions                |
| Business logic appearing inside an Adapter class                       | Move it out — Adapters translate, they don't decide                        |

---

**Tip for the interview:** At the 5 YOE level, Adapter is one of the patterns you're expected to have actually *shipped* — not just described. Interviewers in fintech roles will ask how you integrated a bureau API, a payment gateway, or a government identity provider, and the right answer describes an adapter layer even if you didn't call it that. Lead with the problem — "CIBIL's API shape and our domain model were incompatible, and we needed to swap providers without touching underwriting logic" — then walk through the interface, the concrete adapter, and the DI wiring. The senior differentiator is understanding the *three things* an Adapter must do that a simple wrapper doesn't: implement a formally defined target interface, translate error codes into domain exceptions, and act as the *only* place in the codebase that knows the external API's data shapes. If the external type leaks past the adapter, the adapter has failed its job.
