# JavaScript / TypeScript (Design Patterns — Structural): Composite Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Composite pattern?**
A: The Composite pattern is a structural design pattern that composes objects into **tree structures** to represent part-whole hierarchies, and lets clients treat individual objects (leaves) and compositions of objects (composites) **uniformly** — through the same interface. The pattern has one central insight: if a single item and a group of items can respond to the same operations, the caller never needs to know which it's dealing with.

The canonical example is a file system: a `File` and a `Folder` both support `getName()`, `getSize()`, and `delete()`. A `Folder`'s `getSize()` sums the sizes of its children recursively; a `File`'s `getSize()` returns its own size. The code that calls `getSize()` doesn't care whether it's looking at a file or a folder containing ten thousand files.

**Q2. What problem does the Composite pattern solve?**
A: Without the pattern, client code that operates on tree structures is littered with type checks and branching:
```ts
// Without Composite — client must distinguish between leaf and container everywhere
function getSize(node: File | Folder): number {
  if (node instanceof File) {
    return node.size;
  } else if (node instanceof Folder) {
    return node.children.reduce((sum, child) => sum + getSize(child), 0); // recursive, fragile
  }
  throw new Error("Unknown node type"); // breaks when a new type is added
}
```
Every operation on the tree — `getSize`, `render`, `delete`, `search` — must repeat this branching logic. Adding a new node type (e.g., `Symlink`) requires finding and updating every such branch across the codebase.

The Composite pattern eliminates the branching by giving both leaves and composites the same interface. Operations are polymorphic — each node type implements them appropriately, and the client calls the same method regardless.

**Q3. What are the three participants in the Composite pattern?**
A:
- **Component (interface / abstract class)** — declares the common interface for both leaves and composites. Every operation the client needs to perform on the tree lives here: `operation()`, `add()`, `remove()`, `getChildren()`. Whether `add`/`remove` belong on the Component or only on the Composite is a key design decision (covered in Q7).
- **Leaf** — a node with no children. Implements the Component interface for its own, singular behaviour. Calls to child-management methods (`add`, `remove`) typically throw or are no-ops on a Leaf.
- **Composite** — a node that *has* children (which are themselves Components — either Leaves or other Composites). Implements the Component interface by delegating to its children and aggregating results. Manages the child collection.

**Q4. What is the "uniformity vs safety" design tension in the Composite pattern, and how do you resolve it in TypeScript?**
A: The tension is about where child-management methods (`add`, `remove`, `getChildren`) live:

- **Uniformity approach** — put `add`, `remove`, `getChildren` on the `Component` interface. Clients can call them on any node without casting. Cost: Leaf implementations must either throw or provide meaningless no-ops for these methods — a potential LSP violation.
- **Safety approach** — put `add`, `remove`, `getChildren` only on the `Composite` class. Leaves never have meaningless methods. Cost: clients that need to manage children must cast to `Composite` first — losing some uniformity.

In TypeScript, the pragmatic resolution uses the safety approach but adds a type guard:
```ts
// Component — only shared operations
interface FileSystemNode {
  getName(): string;
  getSize(): number;
  print(indent?: string): void;
}

// Leaf — no child management
class File implements FileSystemNode {
  constructor(private name: string, private size: number) {}
  getName(): string { return this.name; }
  getSize(): number { return this.size; }
  print(indent = ""): void { console.log(`${indent}📄 ${this.name} (${this.size}B)`); }
}

// Composite — child management lives here, not on Component
class Folder implements FileSystemNode {
  private children: FileSystemNode[] = [];
  constructor(private name: string) {}

  add(node: FileSystemNode): this    { this.children.push(node); return this; }
  remove(node: FileSystemNode): this {
    this.children = this.children.filter(c => c !== node); return this;
  }
  getChildren(): FileSystemNode[]    { return [...this.children]; }

  getName(): string { return this.name; }
  getSize(): number { return this.children.reduce((sum, c) => sum + c.getSize(), 0); }
  print(indent = ""): void {
    console.log(`${indent}📁 ${this.name}/`);
    this.children.forEach(c => c.print(indent + "  "));
  }
}

// Type guard — safe narrowing when child management IS needed
function isFolder(node: FileSystemNode): node is Folder {
  return node instanceof Folder;
}

// Client — treats all nodes uniformly through FileSystemNode
function printTree(node: FileSystemNode): void { node.print(); }
function totalSize(node: FileSystemNode): number { return node.getSize(); }
```

**Q5. How does the Composite pattern relate to the tree data structure?**
A: The Composite pattern *is* the object-oriented encoding of a recursive tree:
- The **Component interface** is the node type.
- **Leaves** are terminal nodes (no children).
- **Composites** are internal nodes (have children, which are themselves nodes).
- Every operation on the tree (size, depth, search, render) is implemented as a method on the Component interface, with Composites delegating recursively to children and Leaves providing base cases.

The pattern's power comes from this recursive self-similarity: a `Folder` contains `FileSystemNode`s, and a `Folder` *is itself* a `FileSystemNode` — so trees can be nested to arbitrary depth without the client knowing or caring about depth.

## Section 2: Implementing the Composite Pattern in TypeScript

**Q6. Show a complete, production-quality Composite implementation for a UI component tree.**
A:
```ts
// Component interface — the shared contract
interface UIComponent {
  getId(): string;
  render(depth?: number): string;
  getChildCount(): number;
  find(id: string): UIComponent | null;
}

// Leaf — a single, non-container UI element
class Button implements UIComponent {
  constructor(private id: string, private label: string) {}

  getId(): string { return this.id; }
  getChildCount(): number { return 0; }

  render(depth = 0): string {
    return `${"  ".repeat(depth)}<button id="${this.id}">${this.label}</button>`;
  }

  find(id: string): UIComponent | null {
    return this.id === id ? this : null;
  }
}

class TextInput implements UIComponent {
  constructor(private id: string, private placeholder: string) {}

  getId(): string { return this.id; }
  getChildCount(): number { return 0; }

  render(depth = 0): string {
    return `${"  ".repeat(depth)}<input id="${this.id}" placeholder="${this.placeholder}" />`;
  }

  find(id: string): UIComponent | null {
    return this.id === id ? this : null;
  }
}

// Composite — a container that holds other UIComponents
class Panel implements UIComponent {
  private children: UIComponent[] = [];

  constructor(private id: string, private className: string) {}

  add(component: UIComponent): this {
    this.children.push(component);
    return this;
  }

  remove(component: UIComponent): this {
    this.children = this.children.filter(c => c !== component);
    return this;
  }

  getId(): string { return this.id; }
  getChildCount(): number {
    // Counts all descendants, not just direct children
    return this.children.reduce((sum, c) => sum + 1 + c.getChildCount(), 0);
  }

  render(depth = 0): string {
    const indent = "  ".repeat(depth);
    const inner  = this.children.map(c => c.render(depth + 1)).join("\n");
    return `${indent}<div id="${this.id}" class="${this.className}">\n${inner}\n${indent}</div>`;
  }

  find(id: string): UIComponent | null {
    if (this.id === id) return this;
    for (const child of this.children) {
      const found = child.find(id);
      if (found) return found;
    }
    return null;
  }
}

// Client code — works uniformly on any UIComponent regardless of depth
const form = new Panel("form", "login-form")
  .add(new TextInput("email",    "Email address"))
  .add(new TextInput("password", "Password"))
  .add(
    new Panel("actions", "form-actions")
      .add(new Button("submit", "Sign In"))
      .add(new Button("cancel", "Cancel"))
  );

console.log(form.render());
console.log(`Total components: ${form.getChildCount()}`);

const submitBtn = form.find("submit");  // searches entire tree uniformly
```

**Q7. How do you handle operations that only make sense on Composite nodes — such as `add()` and `remove()` — without breaking the uniform interface?**
A: Three approaches, each with trade-offs:
```ts
// Approach 1 — Optional methods on Component (uniformity, LSP risk)
interface FileSystemNode {
  getSize(): number;
  add?(child: FileSystemNode): void;    // optional — Leaf just doesn't implement
  remove?(child: FileSystemNode): void;
}

// Approach 2 — Throw on Leaf (explicit, runtime safety)
abstract class FileSystemNode {
  abstract getSize(): number;
  add(_child: FileSystemNode): void {
    throw new Error(`${this.constructor.name} does not support children`);
  }
  remove(_child: FileSystemNode): void {
    throw new Error(`${this.constructor.name} does not support children`);
  }
}

// Approach 3 — Type guard + separate Composite type (safety approach, TypeScript-idiomatic)
interface FileSystemNode { getSize(): number; }
interface ContainerNode extends FileSystemNode {
  add(child: FileSystemNode): this;
  remove(child: FileSystemNode): this;
  getChildren(): FileSystemNode[];
}

// Type guard narrows when child ops are needed
function isContainer(node: FileSystemNode): node is ContainerNode {
  return "add" in node && "remove" in node;
}

function addToParent(parent: FileSystemNode, child: FileSystemNode): void {
  if (!isContainer(parent)) throw new Error("Cannot add child to a leaf node");
  parent.add(child);
}
```
At 5 YOE, Approach 3 is the idiomatic TypeScript answer — it's type-safe, self-documenting, and avoids runtime errors from mistakenly calling `add()` on a leaf.

**Q8. How do you implement lazy loading of children in a Composite — for example, loading folder contents from an API only when accessed?**
A: The Composite's child collection becomes a deferred promise, resolved on first access:
```ts
interface TreeNode {
  getName(): string;
  getChildren(): Promise<TreeNode[]>;
  isLeaf(): boolean;
}

class RemoteFile implements TreeNode {
  constructor(private name: string) {}
  getName(): string { return this.name; }
  isLeaf(): boolean { return true; }
  async getChildren(): Promise<TreeNode[]> { return []; }
}

class RemoteFolder implements TreeNode {
  private cachedChildren: TreeNode[] | null = null;

  constructor(private name: string, private path: string, private api: FileSystemApi) {}

  getName(): string { return this.name; }
  isLeaf(): boolean { return false; }

  async getChildren(): Promise<TreeNode[]> {
    // Lazy load — fetch only on first access, cache thereafter
    if (!this.cachedChildren) {
      const entries = await this.api.listDirectory(this.path);
      this.cachedChildren = entries.map(e =>
        e.type === "file"
          ? new RemoteFile(e.name)
          : new RemoteFolder(e.name, `${this.path}/${e.name}`, this.api)
      );
    }
    return this.cachedChildren;
  }
}

// Client — uniform async traversal regardless of node type
async function printTree(node: TreeNode, indent = ""): Promise<void> {
  console.log(`${indent}${node.isLeaf() ? "📄" : "📁"} ${node.getName()}`);
  if (!node.isLeaf()) {
    const children = await node.getChildren();
    for (const child of children) {
      await printTree(child, indent + "  ");
    }
  }
}
```

**Q9. How do you traverse a Composite tree using the Visitor pattern to avoid polluting the Component interface with unrelated operations?**
A: As the number of operations on a tree grows (render, export, validate, search, count), adding each as a method on the Component interface causes interface bloat. The Visitor pattern separates tree traversal from the operations performed at each node:
```ts
// Visitor interface — one method per node type
interface FileSystemVisitor {
  visitFile(file: File): void;
  visitFolder(folder: Folder): void;
}

// Component accepts a visitor — the only tree-related method needed
interface FileSystemNode {
  getName(): string;
  accept(visitor: FileSystemVisitor): void;
}

class File implements FileSystemNode {
  constructor(public name: string, public size: number, public extension: string) {}
  getName(): string { return this.name; }
  accept(visitor: FileSystemVisitor): void { visitor.visitFile(this); }
}

class Folder implements FileSystemNode {
  public children: FileSystemNode[] = [];
  constructor(public name: string) {}
  getName(): string { return this.name; }
  add(node: FileSystemNode): this { this.children.push(node); return this; }
  accept(visitor: FileSystemVisitor): void {
    visitor.visitFolder(this);
    // Composite delegates to children — traversal is in the Composite, not the visitor
    this.children.forEach(child => child.accept(visitor));
  }
}

// Concrete visitors — new operations without touching FileSystemNode
class SizeCalculatorVisitor implements FileSystemVisitor {
  totalSize = 0;
  visitFile(file: File): void   { this.totalSize += file.size; }
  visitFolder(_folder: Folder): void { /* folders have no intrinsic size */ }
}

class FileSearchVisitor implements FileSystemVisitor {
  results: File[] = [];
  constructor(private extension: string) {}
  visitFile(file: File): void {
    if (file.extension === this.extension) this.results.push(file);
  }
  visitFolder(_folder: Folder): void {}
}

class HtmlRendererVisitor implements FileSystemVisitor {
  private depth = 0;
  output = "";
  visitFile(file: File): void {
    this.output += `${"  ".repeat(this.depth)}<li class="file">${file.name}</li>\n`;
  }
  visitFolder(folder: Folder): void {
    this.output += `${"  ".repeat(this.depth)}<li class="folder">${folder.name}<ul>\n`;
    this.depth++;
    // Note: traversal to children happens in Folder.accept() after this call
    // We'll close the tag in a post-visit — for simplicity, depth tracking is sufficient here
  }
}

// Client — add a new operation by writing a new Visitor class, not editing any node class
const root = new Folder("root")
  .add(new File("readme.md", 1024, "md"))
  .add(new Folder("src")
    .add(new File("index.ts", 2048, "ts"))
    .add(new File("utils.ts", 512,  "ts"))
  );

const sizeCalc = new SizeCalculatorVisitor();
root.accept(sizeCalc);
console.log(`Total size: ${sizeCalc.totalSize}B`); // 3584B

const search = new FileSearchVisitor("ts");
root.accept(search);
console.log(`TypeScript files: ${search.results.map(f => f.name)}`); // ["index.ts", "utils.ts"]
```

## Section 3: Real-World Applications

**Q10. How does the Composite pattern appear in React's component tree?**
A: React's entire rendering model is the Composite pattern — every component is either a leaf (renders HTML elements directly) or a composite (renders other components):
```tsx
// Leaf components — render DOM elements, no children to delegate to
const Avatar = ({ src, alt }: { src: string; alt: string }) => (
  <img src={src} alt={alt} className="avatar" />
);

const Badge = ({ count }: { count: number }) => (
  <span className="badge">{count}</span>
);

// Composite components — render other components, delegate to children
const UserCard = ({ user }: { user: User }) => (
  <div className="user-card">
    <Avatar src={user.avatarUrl} alt={user.name} />   {/* Leaf */}
    <span>{user.name}</span>
    {user.unreadCount > 0 && <Badge count={user.unreadCount} />} {/* Leaf */}
  </div>
);

const UserList = ({ users }: { users: User[] }) => (
  <div className="user-list">
    {users.map(u => <UserCard key={u.id} user={u} />)} {/* Composite */}
  </div>
);

const Sidebar = ({ users }: { users: User[] }) => (
  <aside className="sidebar">
    <h2>Team Members</h2>
    <UserList users={users} />  {/* Composite wrapping Composite */}
  </aside>
);

// React's reconciler traverses this tree uniformly — it doesn't know or care
// whether a node is a leaf or composite. Each component implements the same
// interface: (props) => ReactNode
```
React's `children` prop is the direct expression of the Composite pattern's child collection — a component can render any `ReactNode` (leaf or composite) through the same `children` prop, at arbitrary depth.

**Q11. How does the Composite pattern apply to a permissions / RBAC system?**
A: Permissions often form a hierarchy: individual permissions compose into roles, roles compose into role groups, and checks must work uniformly across all levels:
```ts
interface Permission {
  getName(): string;
  includes(permission: string): boolean;
}

// Leaf — a single atomic permission
class AtomicPermission implements Permission {
  constructor(private name: string) {}
  getName(): string { return this.name; }
  includes(permission: string): boolean { return this.name === permission; }
}

// Composite — a role that bundles multiple permissions (or other roles)
class Role implements Permission {
  private permissions: Permission[] = [];

  constructor(private name: string) {}

  grant(permission: Permission): this {
    this.permissions.push(permission);
    return this;
  }

  getName(): string { return this.name; }

  includes(permission: string): boolean {
    // Delegates to children — recursive, uniform
    return this.permissions.some(p => p.includes(permission));
  }

  listAll(): string[] {
    return this.permissions.flatMap(p =>
      p instanceof Role ? p.listAll() : [p.getName()]
    );
  }
}

// Build permission hierarchy
const readOrders   = new AtomicPermission("orders:read");
const writeOrders  = new AtomicPermission("orders:write");
const deleteOrders = new AtomicPermission("orders:delete");
const readUsers    = new AtomicPermission("users:read");
const writeUsers   = new AtomicPermission("users:write");

const orderManager = new Role("order-manager")
  .grant(readOrders)
  .grant(writeOrders);

const userManager = new Role("user-manager")
  .grant(readUsers)
  .grant(writeUsers);

// Composite role — includes other roles
const admin = new Role("admin")
  .grant(orderManager)   // Role inside Role — arbitrary depth
  .grant(userManager)
  .grant(deleteOrders);

// Client — uniform check regardless of whether permission is atomic or a role
function canAccess(role: Permission, action: string): boolean {
  return role.includes(action);
}

console.log(canAccess(admin, "orders:write"));  // true — via orderManager
console.log(canAccess(admin, "orders:delete")); // true — direct
console.log(canAccess(orderManager, "users:read")); // false
```

**Q12. How does the Composite pattern apply to expression trees (calculators, query ASTs, rule engines)?**
A: Mathematical expressions and query ASTs are naturally recursive — an expression is either a terminal value (leaf) or an operation on sub-expressions (composite):
```ts
// Component — every expression can be evaluated
interface Expression {
  evaluate(): number;
  toString(): string;
}

// Leaves — terminal values
class NumberLiteral implements Expression {
  constructor(private value: number) {}
  evaluate(): number { return this.value; }
  toString(): string { return String(this.value); }
}

class Variable implements Expression {
  constructor(private name: string, private context: Record<string, number>) {}
  evaluate(): number {
    if (!(this.name in this.context)) throw new Error(`Undefined variable: ${this.name}`);
    return this.context[this.name];
  }
  toString(): string { return this.name; }
}

// Composites — operations on sub-expressions
class AddExpression implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  evaluate(): number { return this.left.evaluate() + this.right.evaluate(); }
  toString(): string { return `(${this.left} + ${this.right})`; }
}

class MultiplyExpression implements Expression {
  constructor(private left: Expression, private right: Expression) {}
  evaluate(): number { return this.left.evaluate() * this.right.evaluate(); }
  toString(): string { return `(${this.left} * ${this.right})`; }
}

class NegateExpression implements Expression {
  constructor(private operand: Expression) {}
  evaluate(): number { return -this.operand.evaluate(); }
  toString(): string { return `(-${this.operand})`; }
}

// Build the expression: (x + 3) * (y + (-2))
const ctx   = { x: 5, y: 4 };
const expr  = new MultiplyExpression(
  new AddExpression(new Variable("x", ctx), new NumberLiteral(3)),
  new AddExpression(new Variable("y", ctx), new NegateExpression(new NumberLiteral(2)))
);

console.log(expr.toString()); // ((x + 3) * (y + (-2)))
console.log(expr.evaluate()); // (5 + 3) * (4 + (-2)) = 8 * 2 = 16
```
This same structure underlies SQL ASTs, ESLint rule checkers, React's virtual DOM diffing, and business rule engines — anywhere a recursive grammar is evaluated uniformly.

**Q13. How does the Composite pattern apply to menus and navigation trees in a UI?**
A: Nested menus — where a menu item is either a navigable link (leaf) or a sub-menu containing more items (composite) — are a direct Composite application:
```ts
interface MenuItem {
  getLabel(): string;
  isEnabled(): boolean;
  render(depth?: number): object;
}

// Leaf — a navigable link
class LinkItem implements MenuItem {
  constructor(
    private label: string,
    private href: string,
    private enabled = true,
    private icon?: string
  ) {}

  getLabel(): string  { return this.label; }
  isEnabled(): boolean { return this.enabled; }

  render(depth = 0): object {
    return { type: "link", label: this.label, href: this.href,
             icon: this.icon, depth, enabled: this.enabled };
  }
}

// Composite — a sub-menu
class SubMenu implements MenuItem {
  private items: MenuItem[] = [];

  constructor(private label: string, private icon?: string) {}

  add(item: MenuItem): this { this.items.push(item); return this; }

  getLabel(): string  { return this.label; }
  isEnabled(): boolean { return this.items.some(i => i.isEnabled()); } // enabled if any child is

  render(depth = 0): object {
    return {
      type:     "submenu",
      label:    this.label,
      icon:     this.icon,
      depth,
      children: this.items.map(i => i.render(depth + 1)),
    };
  }
}

// Assembling a navigation tree — unlimited nesting depth
const nav = new SubMenu("Main Navigation")
  .add(new LinkItem("Dashboard", "/dashboard", true, "home"))
  .add(
    new SubMenu("Orders", "shopping-cart")
      .add(new LinkItem("All Orders",    "/orders",          true))
      .add(new LinkItem("Create Order",  "/orders/new",      true))
      .add(new LinkItem("Bulk Import",   "/orders/import",   false)) // disabled feature
  )
  .add(
    new SubMenu("Settings", "settings")
      .add(new LinkItem("Profile",       "/settings/profile", true))
      .add(
        new SubMenu("Advanced")
          .add(new LinkItem("API Keys",  "/settings/api",     true))
          .add(new LinkItem("Webhooks",  "/settings/webhooks",true))
      )
  );

const menuTree = nav.render(); // serialises entire tree uniformly
```

**Q14. How does the Composite pattern apply to file system operations, build systems, and task runners like Gulp or webpack?**
A: Build pipelines and task runners model tasks as a Composite — a task is either an atomic operation (leaf) or a group of tasks that run sequentially or in parallel (composite):
```ts
interface BuildTask {
  getName(): string;
  run(): Promise<void>;
  getDuration(): number; // milliseconds, accumulated
}

// Leaf — a single build step
class CompileTask implements BuildTask {
  private duration = 0;
  constructor(private name: string, private compile: () => Promise<void>) {}
  getName(): string { return this.name; }
  getDuration(): number { return this.duration; }

  async run(): Promise<void> {
    const start = Date.now();
    console.log(`▶ Running: ${this.name}`);
    await this.compile();
    this.duration = Date.now() - start;
    console.log(`✓ Done: ${this.name} (${this.duration}ms)`);
  }
}

// Composite — sequential task group
class SequentialTaskGroup implements BuildTask {
  private tasks: BuildTask[] = [];
  constructor(private name: string) {}

  add(task: BuildTask): this { this.tasks.push(task); return this; }
  getName(): string { return this.name; }
  getDuration(): number { return this.tasks.reduce((sum, t) => sum + t.getDuration(), 0); }

  async run(): Promise<void> {
    console.log(`\n📦 ${this.name} (sequential)`);
    for (const task of this.tasks) { await task.run(); } // sequential
  }
}

// Composite — parallel task group
class ParallelTaskGroup implements BuildTask {
  private tasks: BuildTask[] = [];
  constructor(private name: string) {}

  add(task: BuildTask): this { this.tasks.push(task); return this; }
  getName(): string { return this.name; }
  getDuration(): number { return Math.max(...this.tasks.map(t => t.getDuration())); }

  async run(): Promise<void> {
    console.log(`\n⚡ ${this.name} (parallel)`);
    await Promise.all(this.tasks.map(t => t.run())); // parallel
  }
}

// Compose an entire build pipeline — client calls .run() on the root, uniformly
const build = new SequentialTaskGroup("Full Build")
  .add(new CompileTask("TypeScript", async () => { /* tsc */ }))
  .add(
    new ParallelTaskGroup("Assets")
      .add(new CompileTask("CSS",    async () => { /* sass */ }))
      .add(new CompileTask("Images", async () => { /* imagemin */ }))
  )
  .add(new CompileTask("Bundle", async () => { /* webpack */ }))
  .add(
    new ParallelTaskGroup("Checks")
      .add(new CompileTask("Tests",  async () => { /* jest */ }))
      .add(new CompileTask("Lint",   async () => { /* eslint */ }))
  );

await build.run();
console.log(`\nTotal build time: ${build.getDuration()}ms`);
```

## Section 4: Composite with Other Patterns

**Q15. How does the Composite pattern combine with the Iterator pattern for tree traversal?**
A: The tree structure the Composite builds is most naturally traversed with an Iterator that hides the recursive traversal logic from the client:
```ts
// Generator-based depth-first iterator over a Composite tree
function* depthFirstIterator(node: FileSystemNode): Generator<FileSystemNode> {
  yield node; // yield current node first (pre-order)
  if (isFolder(node)) {
    for (const child of node.getChildren()) {
      yield* depthFirstIterator(child); // recurse
    }
  }
}

function* breadthFirstIterator(root: FileSystemNode): Generator<FileSystemNode> {
  const queue: FileSystemNode[] = [root];
  while (queue.length > 0) {
    const node = queue.shift()!;
    yield node;
    if (isFolder(node)) {
      queue.push(...node.getChildren());
    }
  }
}

// Client — flat iteration over any tree, regardless of structure or depth
const root = new Folder("root")
  .add(new File("a.ts", 100))
  .add(new Folder("src").add(new File("b.ts", 200)).add(new File("c.ts", 300)));

// Collect all files using the iterator
const allFiles = [...depthFirstIterator(root)]
  .filter((n): n is File => n instanceof File);

console.log(allFiles.map(f => f.getName())); // ["a.ts", "b.ts", "c.ts"]
```

**Q16. How does the Composite pattern combine with the Decorator pattern?**
A: Both Composite and Decorator use recursive composition through a shared interface, but they serve different purposes:
- **Composite** assembles a *tree* of same-typed nodes to represent part-whole hierarchies.
- **Decorator** *wraps* a single node to add behaviour, with no tree structure.

They compose naturally when you need to add cross-cutting behaviour (logging, caching, access control) to nodes in a tree without modifying the node classes:
```ts
// Decorator adds caching to any FileSystemNode — leaf or composite
class CachedNode implements FileSystemNode {
  private cachedSize: number | null = null;

  constructor(private inner: FileSystemNode) {}

  getName(): string { return this.inner.getName(); }
  print(indent?: string): void { this.inner.print(indent); }

  getSize(): number {
    if (this.cachedSize === null) {
      this.cachedSize = this.inner.getSize(); // compute once
    }
    return this.cachedSize;
  }
}

// Decorator adds access control to any node
class AuthorizedNode implements FileSystemNode {
  constructor(private inner: FileSystemNode, private user: User) {}

  getName(): string { return this.inner.getName(); }
  print(indent?: string): void {
    if (!this.user.canRead(this.inner.getName())) {
      throw new Error(`Access denied: ${this.inner.getName()}`);
    }
    this.inner.print(indent);
  }
  getSize(): number { return this.inner.getSize(); }
}

// Apply decorators to any node — leaf, composite, or another decorator
const protectedFolder = new AuthorizedNode(
  new CachedNode(
    new Folder("secrets").add(new File("keys.pem", 2048))
  ),
  currentUser
);

protectedFolder.print(); // Auth check → Cache check → actual print
```

**Q17. How does the Composite pattern relate to the Chain of Responsibility pattern?**
A: Both patterns involve passing a request through a structure of objects, but they model different structures:
- **Composite** — a *tree*. Every node handles the request (or delegates to all children). The result is typically aggregated from the whole tree.
- **Chain of Responsibility** — a *linear chain*. The request passes along the chain until one handler handles it and stops propagation.

They combine in event propagation systems — a tree of UI components where events bubble up through parent composites (Composite structure) but are handled by the first interested ancestor (Chain of Responsibility logic):
```ts
interface EventHandler {
  handleEvent(event: UIEvent): boolean; // true = handled, stop propagation
  getParent(): EventHandler | null;
}

class UINode implements EventHandler {
  private children: UINode[] = [];
  private parent:   UINode | null = null;

  add(child: UINode): this {
    child.parent = this;
    this.children.push(child);
    return this;
  }

  getParent(): UINode | null { return this.parent; }

  // Chain of Responsibility: bubble event up the Composite tree
  handleEvent(event: UIEvent): boolean {
    if (this.onEvent(event)) return true;   // handled here
    return this.parent?.handleEvent(event) ?? false; // bubble up
  }

  // Override in subclasses to handle specific events
  protected onEvent(_event: UIEvent): boolean { return false; }
}
```

## Section 5: Pitfalls, Anti-Patterns & Edge Cases

**Q18. What is the "overly generic component" problem in the Composite pattern, and how do you avoid it?**
A: When the Component interface tries to accommodate every possible operation for both Leaves and Composites, it becomes bloated and forces meaningless implementations:
```ts
// Overly generic Component — Leaf must implement child-management methods it can't support
interface FileSystemNode {
  getName(): string;
  getSize(): number;
  add(child: FileSystemNode): void;    // meaningless on File
  remove(child: FileSystemNode): void; // meaningless on File
  getChildren(): FileSystemNode[];     // meaningless on File
  getParent(): FileSystemNode | null;  // adds tight upward coupling
  setPermissions(perms: Permissions): void; // not all nodes support this
}

class File implements FileSystemNode {
  add(_child: FileSystemNode): void    { throw new Error("File has no children"); }
  remove(_child: FileSystemNode): void { throw new Error("File has no children"); }
  getChildren(): FileSystemNode[]      { return []; } // meaningless empty array
  // ... forced to implement things it cannot support ✗
}
```
Fix: keep the Component interface minimal (only operations that genuinely apply to every node), put child-management on Composite only, and use type guards when composite-specific behaviour is needed. The interface should describe what *all* nodes share, not what *any* node might need.

**Q19. How do you prevent infinite loops in a Composite tree (circular references)?**
A: A Composite allows adding any Component as a child — including a parent node, creating a cycle. In a recursive operation (`getSize`, `print`), this causes a stack overflow:
```ts
// Circular reference — folder added to its own subtree
const a = new Folder("a");
const b = new Folder("b");
a.add(b);
b.add(a); // cycle! a → b → a → b ...
a.getSize(); // 💥 Maximum call stack size exceeded

// Prevention 1 — ancestor check in add()
class Folder implements FileSystemNode {
  add(child: FileSystemNode): this {
    if (child === this || this.isDescendantOf(child)) {
      throw new Error("Circular reference detected");
    }
    this.children.push(child);
    return this;
  }

  private isDescendantOf(node: FileSystemNode): boolean {
    if (!(node instanceof Folder)) return false;
    return node.getChildren().some(
      c => c === this || (c instanceof Folder && this.isDescendantOf(c))
    );
  }
}

// Prevention 2 — visited set in recursive operations
function getSize(node: FileSystemNode, visited = new Set<FileSystemNode>()): number {
  if (visited.has(node)) return 0; // cycle guard
  visited.add(node);
  if (node instanceof File) return node.size;
  return (node as Folder).getChildren()
    .reduce((sum, c) => sum + getSize(c, visited), 0);
}
```

**Q20. How do you handle the "parent reference" need — where a Composite node needs to know its parent — without tight coupling?**
A: Parent references are a common addition to Composite trees (for event bubbling, path calculation, removal from parent), but they introduce bidirectional coupling that complicates memory management and serialisation:
```ts
// Bidirectional reference — child knows parent, parent knows children
class TreeNode {
  private children: TreeNode[] = [];
  private parent:   TreeNode | null = null;

  add(child: TreeNode): this {
    if (child.parent) child.parent.remove(child); // detach from old parent
    child.parent = this;
    this.children.push(child);
    return this;
  }

  remove(child: TreeNode): this {
    this.children = this.children.filter(c => c !== child);
    child.parent  = null; // clear reference to prevent memory leak
    return this;
  }

  getParent(): TreeNode | null { return this.parent; }

  // Compute path from root — uses parent reference
  getPath(): string {
    const parts: string[] = [];
    let current: TreeNode | null = this;
    while (current) {
      parts.unshift(current.getName());
      current = current.parent;
    }
    return "/" + parts.join("/");
  }

  getName(): string { return "node"; } // override in subclasses
}

// Serialisation guard — avoid circular JSON.stringify
toJSON(): object {
  return {
    name:     this.getName(),
    children: this.children.map(c => c.toJSON()),
    // parent intentionally omitted — would create circular reference in JSON
  };
}
```

**Q21. What are the performance implications of deep Composite trees, and how do you mitigate them?**
A: Deep or wide trees with expensive recursive operations create performance problems:
- **Repeated traversal** — calling `getSize()` on a large tree recomputes from scratch every time.
- **Deep recursion** — very deep trees (thousands of levels) risk call stack exhaustion in synchronous traversal.
- **Serialisation cost** — `toJSON()` or `render()` on a large tree is O(n) per call.

Mitigations:
```ts
// 1. Memoisation — cache computed values, invalidate on mutation
class Folder implements FileSystemNode {
  private _cachedSize: number | null = null;

  add(child: FileSystemNode): this {
    this.children.push(child);
    this.invalidateCache(); // clear on mutation
    return this;
  }

  getSize(): number {
    if (this._cachedSize !== null) return this._cachedSize;
    this._cachedSize = this.children.reduce((sum, c) => sum + c.getSize(), 0);
    return this._cachedSize;
  }

  private invalidateCache(): void {
    this._cachedSize = null;
    // Propagate up if parent reference exists
  }
}

// 2. Iterative traversal — avoid call stack limits with explicit stack
function getSizeIterative(root: FileSystemNode): number {
  const stack: FileSystemNode[] = [root];
  let total = 0;
  while (stack.length > 0) {
    const node = stack.pop()!;
    if (node instanceof File) {
      total += node.size;
    } else if (node instanceof Folder) {
      stack.push(...node.getChildren()); // push children onto stack
    }
  }
  return total;
}

// 3. Lazy evaluation — compute subtree sizes on demand using generators
function* leafIterator(node: FileSystemNode): Generator<File> {
  if (node instanceof File) { yield node; return; }
  for (const child of (node as Folder).getChildren()) {
    yield* leafIterator(child);
  }
}

// Only materialises what's needed
const totalSize = [...leafIterator(root)].reduce((sum, f) => sum + f.size, 0);
```

## Section 6: Scenario / System Design Style Questions

**Q22. "You're building a pricing engine where discounts can be individual percentage discounts, fixed-amount discounts, or bundles of discounts applied together. How would you design this with the Composite pattern?"**
A: Discounts form a natural Composite — a bundle applies all its child discounts, a single discount applies itself:
```ts
interface Discount {
  apply(price: number): number;
  describe(): string;
}

// Leaf — percentage off
class PercentageDiscount implements Discount {
  constructor(private percent: number, private label: string) {}
  apply(price: number): number { return price * (1 - this.percent / 100); }
  describe(): string { return `${this.label} (${this.percent}% off)`; }
}

// Leaf — fixed amount off
class FixedDiscount implements Discount {
  constructor(private amount: number, private label: string) {}
  apply(price: number): number { return Math.max(0, price - this.amount); }
  describe(): string { return `${this.label} (₹${this.amount} off)`; }
}

// Composite — a bundle of discounts applied sequentially
class DiscountBundle implements Discount {
  private discounts: Discount[] = [];
  constructor(private label: string) {}

  add(discount: Discount): this { this.discounts.push(discount); return this; }

  apply(price: number): number {
    // Apply each discount in sequence — order matters
    return this.discounts.reduce((p, d) => d.apply(p), price);
  }

  describe(): string {
    return `${this.label}: [${this.discounts.map(d => d.describe()).join(", ")}]`;
  }
}

// Leaf — conditional discount (applies only if predicate holds)
class ConditionalDiscount implements Discount {
  constructor(
    private inner: Discount,
    private condition: (price: number) => boolean,
    private label: string
  ) {}

  apply(price: number): number {
    return this.condition(price) ? this.inner.apply(price) : price;
  }

  describe(): string { return `${this.label} (conditional)`; }
}

// Compose complex discount structures — uniform interface throughout
const blackFridayDeal = new DiscountBundle("Black Friday")
  .add(new PercentageDiscount(20, "Site-wide sale"))
  .add(new ConditionalDiscount(
    new FixedDiscount(500, "Loyalty bonus"),
    price => price > 2000,
    "Loyalty (orders > ₹2000)"
  ))
  .add(
    new DiscountBundle("Category promotions")
      .add(new PercentageDiscount(5,  "Electronics extra"))
      .add(new PercentageDiscount(10, "Clothing extra"))
  );

const originalPrice = 3000;
const finalPrice    = blackFridayDeal.apply(originalPrice);
console.log(blackFridayDeal.describe());
console.log(`₹${originalPrice} → ₹${finalPrice}`);
```

**Q23. "A reporting system needs to generate totals for individual line items, groups of items (categories), and the overall report. How do you apply the Composite pattern?"**
A:
```ts
interface ReportNode {
  getLabel(): string;
  getTotal(): number;
  render(indent?: number): void;
}

// Leaf — a single line item
class LineItem implements ReportNode {
  constructor(
    private label:    string,
    private quantity: number,
    private unitPrice: number

  getLabel(): string  { return this.label; }
  getTotal(): number  { return this.quantity * this.unitPrice; }

class ReportGroup implements ReportNode {
```

**Q24. "You're designing a workflow engine where a workflow step can be a single task or a group of tasks that run in parallel or sequentially. How does the Composite pattern help, and how would you add cancellation support?"**
A:
```ts
interface WorkflowStep {
  getName(): string;
  execute(ctx: WorkflowContext): Promise<StepResult>;
  cancel(): void;
}

// Leaf — a single executable task
class Task implements WorkflowStep {
  private abortController = new AbortController();

  constructor(
    private name: string,
    private handler: (ctx: WorkflowContext, signal: AbortSignal) => Promise<StepResult>
  ) {}

  getName(): string { return this.name; }
  cancel(): void    { this.abortController.abort(); }

  async execute(ctx: WorkflowContext): Promise<StepResult> {
    try {
      return await this.handler(ctx, this.abortController.signal);
    } catch (e) {
      if ((e as Error).name === "AbortError") return { status: "cancelled", name: this.name };
      return { status: "failed", name: this.name, error: e };
    }
  }
}

// Composite — sequential group
class SequentialGroup implements WorkflowStep {
  private steps: WorkflowStep[] = [];
  constructor(private name: string) {}

  add(step: WorkflowStep): this { this.steps.push(step); return this; }
  getName(): string { return this.name; }
  cancel(): void    { this.steps.forEach(s => s.cancel()); } // delegates to all children

  async execute(ctx: WorkflowContext): Promise<StepResult> {
    for (const step of this.steps) {
      const result = await step.execute(ctx);
      if (result.status !== "success") return result; // short-circuit on failure/cancel
    }
    return { status: "success", name: this.name };
  }
}

// Composite — parallel group
class ParallelGroup implements WorkflowStep {
  private steps: WorkflowStep[] = [];
  constructor(private name: string) {}

  add(step: WorkflowStep): this { this.steps.push(step); return this; }
  getName(): string { return this.name; }
  cancel(): void    { this.steps.forEach(s => s.cancel()); } // cancels all parallel tasks

  async execute(ctx: WorkflowContext): Promise<StepResult> {
    const results = await Promise.allSettled(this.steps.map(s => s.execute(ctx)));
    const failed  = results.find(r => r.status === "rejected");
    if (failed) {
      this.cancel(); // cancel remaining on any failure
      return { status: "failed", name: this.name };
    }
    return { status: "success", name: this.name };
  }
}

// Compose a workflow — cancel() works uniformly on any step
const onboarding = new SequentialGroup("User Onboarding")
  .add(new Task("Validate Input",   async (ctx) => validateInput(ctx)))
  .add(
    new ParallelGroup("Setup")
      .add(new Task("Create Account", async (ctx, sig) => createAccount(ctx, sig)))
      .add(new Task("Init Storage",   async (ctx, sig) => initStorage(ctx, sig)))
      .add(new Task("Send Welcome",   async (ctx, sig) => sendWelcome(ctx, sig)))
  )
  .add(new Task("Log Completion", async (ctx) => logEvent(ctx)));

// Cancellation propagates uniformly through the entire tree
setTimeout(() => onboarding.cancel(), 5000); // cancel after 5s if not done
const result = await onboarding.execute(workflowCtx);
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Leaf | Composite | Component (interface) |
|---|---|---|---|
| **Has children** | No | Yes | Optional (design decision) |
| **Child management** | No-op / throws | `add()`, `remove()`, `getChildren()` | Safety approach: excluded |
| **Operation implementation** | Direct — own behaviour | Delegates to children, aggregates | Declared — polymorphic |
| **Recursive depth** | Base case | Recursive case | N/A |
| **Examples** | `File`, `Button`, `LineItem`, `AtomicPermission` | `Folder`, `Panel`, `ReportGroup`, `Role` | `FileSystemNode`, `UIComponent`, `Discount` |

## Composite Pattern vs Related Patterns

| Pattern | Structure | Intent | Relationship to Composite |
|---|---|---|---|
| **Decorator** | Wraps a single node | Add behaviour to one object | Same recursive interface; Composite = tree, Decorator = chain of one |
| **Iterator** | Linear traversal | Sequential access to elements | Iterates over Composite's tree; hides traversal from client |
| **Visitor** | Separates operation from structure | Add operations without modifying nodes | Eliminates method bloat on Component; pairs naturally with Composite |
| **Chain of Responsibility** | Linear chain | Pass request until handled | Composite provides the tree; CoR provides the stop-propagation logic |
| **Flyweight** | Shared intrinsic state | Reduce memory for many similar objects | Optimise leaf nodes in large Composite trees |
| **Builder** | Step-by-step assembly | Construct complex objects | Builds the Composite tree itself (e.g., `.add().add().build()`) |
