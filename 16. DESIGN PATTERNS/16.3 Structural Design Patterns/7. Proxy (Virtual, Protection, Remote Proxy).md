# Design Patterns — Structural: Proxy (Virtual, Protection, Remote) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Proxy pattern?**
A: The Proxy pattern is a structural design pattern that provides a surrogate or placeholder object that controls access to another object — the "real subject." The proxy and the real subject implement the same interface, so callers can't distinguish between them. The proxy intercepts calls intended for the real subject and can add behavior before, after, or instead of forwarding them: lazy initialization, access control, logging, caching, remote communication, or rate limiting. The GoF definition: *"Provide a surrogate or placeholder for another object to control access to it."*

The word "control" is the distinguishing intent. A proxy's job is access control — *when*, *whether*, and *how* the real subject is reached. This separates it from the Decorator pattern, which has the same structure but different intent: a Decorator adds behavior; a Proxy controls access (Q5 covers this distinction in depth).

**Q2. What are the four participants in the Proxy pattern?**
A:
- **Subject** — the interface that both the Proxy and RealSubject implement. Ensures the proxy is substitutable for the real object.
- **RealSubject** — the actual object that does the real work. The proxy holds a reference to it (or creates it lazily).
- **Proxy** — holds a reference to the RealSubject, implements the Subject interface, and controls access. May create the RealSubject lazily, check permissions, communicate over a network, or cache results.
- **Client** — works through the Subject interface, unaware of whether it's talking to a Proxy or a RealSubject.

**Q3. What are the main types of Proxy, and what does each control?**
A: The GoF defines three primary variants — each controls a different *kind* of access:

- **Virtual Proxy** — controls *when* the real subject is created. Defers expensive initialization until the resource is actually needed (lazy initialization). The real object may never be created if the caller never uses it.
- **Protection Proxy** — controls *whether* the caller has permission to perform an operation. Checks authentication, authorization, or role-based rules before forwarding to the real subject.
- **Remote Proxy** — controls *how* the real subject is reached when it lives in a different process, machine, or network location. Handles serialization, network transport, and error mapping transparently.

Two additional common variants not in the original GoF but widely recognized:
- **Caching Proxy** — controls how often the real subject is called by returning cached results for repeated identical requests.
- **Smart Reference Proxy** — performs additional bookkeeping (reference counting, lock management, usage logging) when the real subject is accessed.

**Q4. What is the structural relationship between Proxy, RealSubject, and Client?**
A:
```
          «interface»
           Subject
          /        \
    Proxy           RealSubject
    - realSubject: RealSubject (reference, possibly lazy)
    + operation()  ──delegates──▶  + operation()

Client ──uses──▶ Subject (doesn't know if it's Proxy or RealSubject)
```
The proxy implements the Subject interface so the client's code never changes whether it talks to a proxy or the real object. The proxy holds a reference to the RealSubject — created eagerly, lazily, or retrieved from a remote source depending on the variant.

**Q5. What is the precise difference between a Proxy and a Decorator?**
A: They are structurally identical — both wrap an object behind the same interface. The difference is *intent*, and intent drives design decisions:

| Aspect                  | Proxy                                                  | Decorator                                              |
|---                      |---                                                     |---                                                     |
| Primary intent          | Control *access* to the real subject                   | Add *behavior* to the component                        |
| Does the client know?   | Usually no — proxy is transparent infrastructure       | Usually yes — decoration is an expected feature        |
| Real subject creation   | Often managed by the proxy (lazy, remote, guarded)     | Caller creates and passes in the component             |
| Composability           | Typically one proxy per concern                        | Explicitly designed to stack multiple decorators       |
| Feature examples        | Lazy init, auth checks, remote calls, rate limiting    | Caching, logging, retry, metrics                       |
| Replaces real subject?  | Yes — callers can't and shouldn't tell the difference  | Partially — callers know they have an enhanced version |
| GoF categorization      | Controls access                                        | Adds responsibilities                                  |

Practical rule: if you're deciding *whether or when* the real object is reached — that's a Proxy. If you're adding *what happens around* every call to an object the caller already has — that's a Decorator.

## Section 2: Virtual Proxy

**Q6. What is a Virtual Proxy and when should you use it?**
A: A Virtual Proxy defers the creation of an expensive real subject until the first time it is actually used. The client receives the proxy immediately — construction is instant — and the real object is created on first access. Use it when:
- The real subject is expensive to create (heavy DB connections, large file loads, SDK initialization).
- The real subject may never be needed in some code paths.
- You want to keep startup time fast and pay creation cost only when necessary.

Common real-world examples: lazy-loading ORM relations (a `User` object holds a proxy for its `loans` collection — the query runs only when `user.loans` is accessed), lazy service initialization, deferred SDK client creation.

**Q7. What does a Virtual Proxy look like in TypeScript?**
A:
```ts
interface ReportGenerator {
  generate(filters: ReportFilters): Promise<ReportData>;
  getMetadata(): ReportMetadata;
}

// RealSubject — expensive to create: loads large config, warms up ML model
class HeavyReportGenerator implements ReportGenerator {
  private readonly model: MLModel;
  private readonly config: ReportConfig;

  constructor() {
    console.log("Loading ML model and config..."); // expensive — 2-3 seconds
    this.model = MLModel.load("/models/credit-risk-v3");
    this.config = ReportConfig.loadFromDisk("/config/report-rules.json");
  }

  async generate(filters: ReportFilters): Promise<ReportData> {
    return this.model.predict(filters, this.config);
  }

  getMetadata(): ReportMetadata {
    return { version: "3.0", modelType: "credit-risk" };
  }
}

// Virtual Proxy — creates HeavyReportGenerator only on first use
class LazyReportGenerator implements ReportGenerator {
  private real: HeavyReportGenerator | null = null;

  private getInstance(): HeavyReportGenerator {
    if (!this.real) {
      this.real = new HeavyReportGenerator(); // deferred creation
    }
    return this.real;
  }

  async generate(filters: ReportFilters): Promise<ReportData> {
    return this.getInstance().generate(filters);
  }

  getMetadata(): ReportMetadata {
    // getMetadata is cheap — but still triggers creation
    // Alternatively: return hardcoded metadata without creating the real subject
    return this.getInstance().getMetadata();
  }
}

// Client — receives the proxy at startup (instant), pays creation cost only on first generate()
const generator: ReportGenerator = new LazyReportGenerator();
// ... time passes, server starts fast ...
const report = await generator.generate(filters); // HeavyReportGenerator created here
```

**Q8. How does a Virtual Proxy handle thread-safety / concurrent initialization in Node.js?**
A: Node.js is single-threaded for JS execution, so two synchronous checks of `this.real === null` cannot interleave — the naïve lazy initialization pattern is safe for synchronous construction. However, if construction is *asynchronous* (a DB query, an HTTP call, an async SDK init), two concurrent callers can both find `this.real === null` before either has finished initializing — causing duplicate initialization:

```ts
// PROBLEM — async initialization race condition
class LazyEsClientProxy implements SearchClient {
  private real: Client | null = null;

  async search(query: SearchQuery): Promise<SearchResult[]> {
    if (!this.real) {
      this.real = await this.initializeClient(); // two concurrent callers both enter here
    }
    return this.real.search(query);
  }
}

// SOLUTION — store the Promise itself, not just the result
class LazyEsClientProxy implements SearchClient {
  private initPromise: Promise<Client> | null = null;

  private getClient(): Promise<Client> {
    if (!this.initPromise) {
      this.initPromise = this.initializeClient(); // Promise is created once; shared by all callers
    }
    return this.initPromise; // subsequent callers await the same Promise
  }

  async search(query: SearchQuery): Promise<SearchResult[]> {
    const client = await this.getClient();
    return client.search(query);
  }
}
```
Storing the `Promise` rather than the resolved value is the idiomatic Node.js solution to async virtual proxy initialization. All concurrent callers await the same Promise — the real client initializes exactly once.

**Q9. How do ORMs implement the Virtual Proxy pattern for lazy-loaded relations?**
A: TypeORM, Sequelize, and Mongoose all use Virtual Proxies for lazy-loading associations. When you load a `User` entity, its `loans` relation isn't fetched immediately — you receive a proxy object that looks like a `Loan[]` but triggers a `SELECT` query when first accessed:

```ts
@Entity()
export class User {
  @PrimaryGeneratedColumn("uuid")
  id: string;

  @OneToMany(() => Loan, loan => loan.user, { lazy: true })
  loans: Promise<Loan[]>; // TypeORM wraps this in a proxy — query runs on await
}

// Usage
const user = await userRepo.findOne({ where: { id: userId } });
// No loan query yet — only user data was fetched

const loans = await user.loans; // TypeORM's Virtual Proxy fires the SELECT now
```
The `Promise<Loan[]>` type signals that accessing loans is deferred. TypeORM's internal proxy intercepts the property access and issues the query. This is Virtual Proxy at the ORM framework level — the pattern you'd implement manually for custom lazy-loading scenarios.

## Section 3: Protection Proxy

**Q10. What is a Protection Proxy and when should you use it?**
A: A Protection Proxy controls whether a caller has permission to access the real subject. Before forwarding a call, it checks authentication, authorization, role membership, rate limits, or IP allowlists — and either forwards the call or rejects it with an appropriate error. Use it when:
- The same service interface is used by callers with different permission levels.
- Access control logic should be enforced uniformly without requiring every caller to implement it.
- You want to separate the authorization concern from the business logic of the real subject.

Protection Proxy is the pattern behind API gateway authorization, service-level RBAC enforcement, and row-level security wrappers.

**Q11. What does a Protection Proxy look like in TypeScript for a fintech service?**
A:
```ts
interface LoanAdminService {
  approveLoan(loanId: string): Promise<void>;
  rejectLoan(loanId: string, reason: string): Promise<void>;
  disburseLoan(loanId: string): Promise<DisbursementResult>;
  viewLoanDetails(loanId: string): Promise<LoanDetails>;
}

type Role = "LOAN_OFFICER" | "RISK_MANAGER" | "AUDITOR" | "ADMIN";

const ROLE_PERMISSIONS: Record<keyof LoanAdminService, Role[]> = {
  approveLoan:     ["RISK_MANAGER", "ADMIN"],
  rejectLoan:      ["LOAN_OFFICER", "RISK_MANAGER", "ADMIN"],
  disburseLoan:    ["ADMIN"],
  viewLoanDetails: ["LOAN_OFFICER", "RISK_MANAGER", "AUDITOR", "ADMIN"],
};

class LoanAdminServiceProxy implements LoanAdminService {
  constructor(
    private readonly real: LoanAdminService,
    private readonly currentUser: { id: string; roles: Role[] },
  ) {}

  private checkPermission(method: keyof LoanAdminService): void {
    const allowed = ROLE_PERMISSIONS[method];
    const hasPermission = this.currentUser.roles.some(r => allowed.includes(r));
    if (!hasPermission) {
      throw new ForbiddenException(
        `User ${this.currentUser.id} lacks permission for ${method}. ` +
        `Required roles: ${allowed.join(", ")}. ` +
        `User roles: ${this.currentUser.roles.join(", ")}.`
      );
    }
  }

  async approveLoan(loanId: string): Promise<void> {
    this.checkPermission("approveLoan");
    return this.real.approveLoan(loanId);
  }

  async rejectLoan(loanId: string, reason: string): Promise<void> {
    this.checkPermission("rejectLoan");
    return this.real.rejectLoan(loanId, reason);
  }

  async disburseLoan(loanId: string): Promise<DisbursementResult> {
    this.checkPermission("disburseLoan");
    return this.real.disburseLoan(loanId);
  }

  async viewLoanDetails(loanId: string): Promise<LoanDetails> {
    this.checkPermission("viewLoanDetails");
    return this.real.viewLoanDetails(loanId);
  }
}

// Usage — wired per-request with the current user's roles
const adminService = new LoanAdminServiceProxy(
  new RealLoanAdminService(loanRepo, disbursementGateway),
  { id: req.user.id, roles: req.user.roles }
);
```
`RealLoanAdminService` has zero authorization code. Roles and permissions live entirely in the proxy. The real service is the same across all callers — the proxy enforces which callers can reach which methods.

**Q12. How does a Protection Proxy differ from middleware-level auth in NestJS?**
A: Both enforce authorization, but at different granularities:

| Aspect               | NestJS Guard / Middleware                          | Protection Proxy                                        |
|---                   |---                                                 |---                                                      |
| Granularity          | HTTP request / route handler level                 | Service method / object level                           |
| Authorization data   | JWT claims, session, HTTP headers                  | Domain roles, business rules, data ownership            |
| What it protects     | HTTP endpoints                                     | Service methods, domain operations                      |
| Bypassed by?         | Internal service calls (no HTTP)                   | Nothing — enforced at the object level                  |
| Use for              | Coarse-grained: authenticated vs. unauthenticated  | Fine-grained: role/resource-level access within a service |

In a well-layered architecture, you use both: NestJS Guards handle HTTP-level authentication and coarse authorization (is the user logged in? does their JWT have a valid tenant?). A Protection Proxy handles fine-grained domain authorization (can this specific user approve loans over ₹500,000? can an AUDITOR role call `disburseLoan`?). The proxy's rules are testable in pure unit tests — no HTTP stack required.

**Q13. How do you implement a rate-limiting Protection Proxy in Node.js?**
A:
```ts
interface PaymentGateway {
  initiatePayment(amount: number, orderId: string): Promise<PaymentIntent>;
  verifyPayment(transactionId: string): Promise<PaymentStatus>;
}

class RateLimitingPaymentGateway implements PaymentGateway {
  private callCounts = new Map<string, { count: number; windowStart: number }>();

  constructor(
    private readonly real: PaymentGateway,
    private readonly limits: { maxCallsPerWindow: number; windowMs: number }
  ) {}

  private checkRateLimit(key: string): void {
    const now = Date.now();
    const entry = this.callCounts.get(key);

    if (!entry || now - entry.windowStart > this.limits.windowMs) {
      this.callCounts.set(key, { count: 1, windowStart: now });
      return;
    }

    if (entry.count >= this.limits.maxCallsPerWindow) {
      const retryAfterMs = this.limits.windowMs - (now - entry.windowStart);
      throw new TooManyRequestsException(
        `Rate limit exceeded. Retry after ${Math.ceil(retryAfterMs / 1000)}s.`
      );
    }

    entry.count++;
  }

  async initiatePayment(amount: number, orderId: string): Promise<PaymentIntent> {
    this.checkRateLimit("initiatePayment");
    return this.real.initiatePayment(amount, orderId);
  }

  async verifyPayment(transactionId: string): Promise<PaymentStatus> {
    this.checkRateLimit("verifyPayment");
    return this.real.verifyPayment(transactionId);
  }
}

// Wired at composition root
const gateway = new RateLimitingPaymentGateway(
  new RazorpayGateway(config),
  { maxCallsPerWindow: 100, windowMs: 60_000 }
);
```
For distributed rate limiting (across multiple Node.js instances), replace the in-memory `Map` with Redis-backed counters using atomic `INCR` + `EXPIRE` commands — same proxy interface, different enforcement backend.

## Section 4: Remote Proxy

**Q14. What is a Remote Proxy and what problem does it solve?**
A: A Remote Proxy represents an object that lives in a different address space — a different process, a different machine, or a remote service. The client calls methods on the proxy as if the object were local; the proxy transparently handles serialization of the request, network transport, deserialization of the response, and mapping of network errors to local exceptions. The client's code is identical whether the service is local or remote.

Remote Proxy is the pattern behind:
- **gRPC client stubs** — generated code that looks like a local method call but serializes to Protobuf and sends over HTTP/2.
- **REST API client wrappers** — a `PaymentServiceClient` that wraps HTTP calls behind a `PaymentService` interface.
- **Message queue publishers as method calls** — a proxy that translates `userService.sendWelcomeEmail(userId)` into a Kafka message, making async messaging look synchronous to the caller.
- **Microservice SDK clients** — the SDKs your own internal services expose; the consumer calls `loanServiceClient.getLoan(id)` without knowing it's an HTTP call to another pod.

**Q15. What does a Remote Proxy look like for an internal microservice client?**
A:
```ts
// Subject interface — same contract used locally and remotely
interface LoanService {
  getLoan(id: string): Promise<Loan>;
  createLoan(data: CreateLoanDto): Promise<Loan>;
  updateLoanStatus(id: string, status: LoanStatus): Promise<void>;
}

// Remote Proxy — translates method calls to HTTP requests
class LoanServiceClient implements LoanService {
  private readonly httpClient: AxiosInstance;

  constructor(
    private readonly baseUrl: string,
    private readonly authToken: () => string, // dynamic token provider
  ) {
    this.httpClient = axios.create({
      baseURL: baseUrl,
      timeout: 5000,
      headers: { "Content-Type": "application/json" },
    });

    // Interceptor: inject auth token per-request
    this.httpClient.interceptors.request.use(config => {
      config.headers.Authorization = `Bearer ${this.authToken()}`;
      return config;
    });

    // Interceptor: map HTTP errors to domain exceptions
    this.httpClient.interceptors.response.use(
      res => res,
      err => {
        if (err.response?.status === 404) throw new LoanNotFoundException(err.config.url);
        if (err.response?.status === 403) throw new ForbiddenException("Loan service access denied");
        if (err.response?.status === 429) throw new RateLimitException("Loan service rate limit exceeded");
        if (err.code === "ECONNABORTED")  throw new ServiceTimeoutException("Loan service timed out");
        throw new ServiceUnavailableException(`Loan service error: ${err.message}`);
      }
    );
  }

  async getLoan(id: string): Promise<Loan> {
    const { data } = await this.httpClient.get<LoanDto>(`/loans/${id}`);
    return LoanMapper.toDomain(data); // deserialize DTO → domain object
  }

  async createLoan(dto: CreateLoanDto): Promise<Loan> {
    const { data } = await this.httpClient.post<LoanDto>("/loans", dto);
    return LoanMapper.toDomain(data);
  }

  async updateLoanStatus(id: string, status: LoanStatus): Promise<void> {
    await this.httpClient.patch(`/loans/${id}/status`, { status });
  }
}

// Consumer — uses LoanService interface, has no knowledge of HTTP
@Injectable()
export class RepaymentService {
  constructor(
    @Inject("LOAN_SERVICE") private readonly loanService: LoanService,
  ) {}

  async processRepayment(loanId: string, amount: number): Promise<void> {
    const loan = await this.loanService.getLoan(loanId); // looks local — is remote
    // ...
  }
}
```

**Q16. How does a Remote Proxy handle network failures, timeouts, and retries?**
A: The Remote Proxy is the correct layer to encapsulate resilience — the consumer shouldn't know or care that the network exists:

```ts
class ResilientLoanServiceClient implements LoanService {
  constructor(
    private readonly inner: LoanServiceClient, // the base remote proxy
    private readonly options: {
      maxRetries: number;
      retryDelayMs: number;
      retryOn: (err: Error) => boolean;
    }
  ) {}

  async getLoan(id: string): Promise<Loan> {
    return this.withRetry(() => this.inner.getLoan(id));
  }

  async createLoan(dto: CreateLoanDto): Promise<Loan> {
    // Don't retry non-idempotent operations unless you have idempotency keys
    return this.inner.createLoan(dto);
  }

  async updateLoanStatus(id: string, status: LoanStatus): Promise<void> {
    return this.withRetry(() => this.inner.updateLoanStatus(id, status));
  }

  private async withRetry<T>(fn: () => Promise<T>): Promise<T> {
    let lastErr: Error;
    for (let attempt = 1; attempt <= this.options.maxRetries; attempt++) {
      try {
        return await fn();
      } catch (err) {
        lastErr = err as Error;
        if (!this.options.retryOn(lastErr) || attempt === this.options.maxRetries) throw lastErr;
        await new Promise(r => setTimeout(r, this.options.retryDelayMs * attempt));
      }
    }
    throw lastErr!;
  }
}
```
Note the non-idempotent operation guard on `createLoan` — retrying a POST without an idempotency key can create duplicate loans. The Remote Proxy is where this nuance is encoded once, not scattered across every caller.

**Q17. How does gRPC implement the Remote Proxy pattern?**
A: gRPC's code generation produces a client stub that is a textbook Remote Proxy. For a `.proto` service definition:

```protobuf
service LoanService {
  rpc GetLoan (GetLoanRequest) returns (LoanResponse);
  rpc CreateLoan (CreateLoanRequest) returns (LoanResponse);
}
```

The generated TypeScript client stub:
```ts
// Auto-generated by protoc — this IS the Remote Proxy
const client = new LoanServiceClient(
  "loan-service:50051",
  grpc.credentials.createInsecure()
);

// Looks like a local method call
client.getLoan({ loanId: "abc123" }, (err, response) => {
  if (err) throw err;
  const loan = response.loan;
});
```
The stub handles: Protobuf serialization, HTTP/2 transport, connection management, deadline propagation, metadata (headers), and error mapping (gRPC status codes → exceptions). The consumer never writes network code. This is Remote Proxy applied at the framework level.

**Q18. How do you use a Remote Proxy to make Kafka message publishing look like a method call?**
A: This is a powerful application of Remote Proxy in event-driven architectures — it hides the async messaging infrastructure behind a synchronous-looking interface:

```ts
// Interface — looks synchronous to callers
interface NotificationService {
  sendWelcomeEmail(userId: string): Promise<void>;
  sendLoanApprovalSms(userId: string, loanId: string): Promise<void>;
  sendRepaymentReminder(userId: string, dueDate: Date): Promise<void>;
}

// Remote Proxy — translates method calls to Kafka messages
@Injectable()
export class KafkaNotificationProxy implements NotificationService {
  constructor(private readonly kafka: KafkaProducerService) {}

  async sendWelcomeEmail(userId: string): Promise<void> {
    await this.kafka.publish("notifications", {
      type: "WELCOME_EMAIL",
      payload: { userId },
      timestamp: new Date().toISOString(),
    });
  }

  async sendLoanApprovalSms(userId: string, loanId: string): Promise<void> {
    await this.kafka.publish("notifications", {
      type: "LOAN_APPROVAL_SMS",
      payload: { userId, loanId },
      timestamp: new Date().toISOString(),
    });
  }

  async sendRepaymentReminder(userId: string, dueDate: Date): Promise<void> {
    await this.kafka.publish("notifications", {
      type: "REPAYMENT_REMINDER",
      payload: { userId, dueDate: dueDate.toISOString() },
      timestamp: new Date().toISOString(),
    });
  }
}

// Consumer — calls a method, has no knowledge of Kafka
@Injectable()
export class LoanApprovalService {
  constructor(
    private readonly notifications: NotificationService, // injected as KafkaNotificationProxy
  ) {}

  async approveLoan(loanId: string): Promise<void> {
    const loan = await this.loanRepo.findById(loanId);
    loan.approve();
    await this.loanRepo.save(loan);
    await this.notifications.sendLoanApprovalSms(loan.userId, loanId); // fire-and-forget via Kafka
  }
}
```
Swapping from direct HTTP notification to Kafka is a DI wiring change — `LoanApprovalService` is untouched. In tests, inject a `MockNotificationService` that records calls — no Kafka needed.

## Section 5: JavaScript Proxy Object

**Q19. What is the JavaScript `Proxy` object and how does it relate to the GoF Proxy pattern?**
A: JavaScript's built-in `Proxy` object (ES2015) is a language-level mechanism for intercepting operations on *any* object — property access, assignment, function calls, `in` operator, `delete`, iteration, and more. It implements the GoF Proxy pattern as a first-class language feature:

```ts
const handler: ProxyHandler<LoanRepository> = {
  // Intercept property access (get trap)
  get(target, prop, receiver) {
    const original = Reflect.get(target, prop, receiver);

    if (typeof original !== "function") return original;

    // Wrap every method with logging
    return async function (...args: unknown[]) {
      console.log(`[Proxy] Calling ${String(prop)} with`, args);
      const result = await (original as Function).apply(target, args);
      console.log(`[Proxy] ${String(prop)} returned`, result);
      return result;
    };
  },

  // Intercept property assignment (set trap)
  set(target, prop, value) {
    console.log(`[Proxy] Setting ${String(prop)} =`, value);
    return Reflect.set(target, prop, value);
  },
};

const repo = new PostgresLoanRepository(pool);
const proxied = new Proxy(repo, handler);

// All method calls are intercepted — no interface changes needed
await proxied.findById("loan-123");
```

The JS `Proxy` is more powerful than the GoF pattern because it intercepts *any operation*, not just method calls. Use cases:
- **Validation proxies** — intercept `set` to validate values before assignment.
- **Observable objects** — intercept `set` to trigger reactive updates (Vue 3's reactivity system).
- **Auto-delegation** — intercept `get` to forward unknown methods to an inner object (universal Decorator/Proxy without explicit delegation).
- **Revocable proxies** — `Proxy.revocable()` creates a proxy that can be permanently disabled — useful for object capability security patterns.

**Q20. What is `Reflect` and why is it used alongside `Proxy`?**
A: `Reflect` is a built-in object that exposes the same interceptable operations as `Proxy` traps, but as functions. It's the idiomatic way to *forward* an operation to the original target inside a trap — ensuring correct `this` binding, prototype chain behavior, and receiver propagation:

```ts
const handler: ProxyHandler<object> = {
  get(target, prop, receiver) {
    // Naive forwarding — can break prototype chain and getter this-binding
    // return target[prop as keyof typeof target];

    // Correct forwarding with Reflect — preserves receiver, prototype, getters
    return Reflect.get(target, prop, receiver);
  },
  set(target, prop, value, receiver) {
    // Reflect.set returns boolean indicating success — required for strict mode
    return Reflect.set(target, prop, value, receiver);
  },
  has(target, prop) {
    return Reflect.has(target, prop);
  },
};
```
The `receiver` parameter matters for inherited getters: if a proxy wraps a class instance and a getter on a parent class uses `this`, passing `receiver` ensures `this` refers to the proxy, not the raw target. Without `Reflect`, subtle bugs appear when proxying objects with prototype chains or property getters.

## Section 6: Pitfalls, Anti-patterns & Best Practices

**Q21. What are the most common Proxy pattern mistakes?**
A:
- **Leaking the real subject** — if the proxy exposes the real subject via a public property (`proxy.realSubject`), callers bypass the proxy's access control. The real subject reference must be private/protected.
- **Breaking transparency** — the proxy must behave identically to the real subject for all operations the caller might use. A Protection Proxy that throws on unauthorized access is correct; one that returns `null` silently is dangerous — callers may interpret `null` as "not found" rather than "access denied."
- **Not forwarding all interface methods** — a proxy that implements 4 of 5 interface methods causes runtime errors when the 5th is called. TypeScript's `implements` check prevents this, but JS proxies using `Proxy` object are dynamic — all methods should be covered by the `get` trap or explicitly handled.
- **Async initialization race in Virtual Proxy** — creating the real subject multiple times because two concurrent callers both find `this.real === null` before either finishes. Fix: store the Promise (Q8).
- **Retrying non-idempotent operations in Remote Proxy** — retrying `POST /loans` without an idempotency key creates duplicate records. Always distinguish safe/idempotent methods from non-idempotent ones before adding retry (Q16).
- **Proxy chain confusion** — stacking a Protection Proxy on a Virtual Proxy on a Remote Proxy makes debugging extremely difficult. Each proxy in the chain should be independently testable and clearly named.

**Q23. What is a "Surrogate" and how does it relate to Proxy?**
A: "Surrogate" is an older name for the same pattern — used interchangeably with Proxy in some literature. The GoF book itself sometimes uses "surrogate." The nuance: "surrogate" emphasizes that the proxy *stands in for* the real subject in all situations (a full replacement that the client never distinguishes from the real thing). "Proxy" is broader and includes cases where the proxy's interception is visible or expected (like a rate-limiting proxy that throws `TooManyRequestsException`). In modern usage, "Proxy" is the dominant term; "surrogate" appears mostly in older object-oriented literature and some distributed systems contexts.

## Section 7: Scenario / System Design Style Questions

**Q24. "Your NACH payment service makes 3 calls to an Elasticsearch cluster per request (loan eligibility check, deduplication check, credit history lookup). The cluster is expensive and occasionally slow. How do you reduce load without changing the service code?"**
A: A Caching Proxy on the Elasticsearch client — transparently intercepts calls and returns cached results:

```ts
interface SearchClient {
  search(index: string, query: SearchQuery): Promise<SearchResult[]>;
  get(index: string, id: string): Promise<Document | null>;
}

class CachingSearchProxy implements SearchClient {
  private cache: Map<string, { result: unknown; expiresAt: number }> = new Map();

  constructor(
    private readonly real: SearchClient,
    private readonly ttlMs: number = 30_000,
  ) {}

  private cacheKey(method: string, ...args: unknown[]): string {
    return `${method}:${JSON.stringify(args)}`;
  }

  async search(index: string, query: SearchQuery): Promise<SearchResult[]> {
    const key = this.cacheKey("search", index, query);
    const hit = this.cache.get(key);
    if (hit && hit.expiresAt > Date.now()) return hit.result as SearchResult[];

    const result = await this.real.search(index, query);
    this.cache.set(key, { result, expiresAt: Date.now() + this.ttlMs });
    return result;
  }

  async get(index: string, id: string): Promise<Document | null> {
    const key = this.cacheKey("get", index, id);
    const hit = this.cache.get(key);
    if (hit && hit.expiresAt > Date.now()) return hit.result as Document | null;

    const result = await this.real.get(index, id);
    if (result) this.cache.set(key, { result, expiresAt: Date.now() + this.ttlMs });
    return result;
  }
}

// Wired at DI composition root — NACH service unchanged
const esClient: SearchClient = new CachingSearchProxy(
  new ElasticsearchClient({ node: process.env.ES_URL }),
  30_000 // 30s TTL for eligibility/dedup results
);
```
For distributed caching across multiple NACH service pods, replace the `Map` with a Redis-backed implementation — same proxy interface, same consumer code.

**Q25. "You have a `LoanReportService` that accesses a large, slow PDF generation library. The library takes 4 seconds to initialize and uses 200MB of RAM. Many requests don't generate reports at all. How would you design this?"**
A: Virtual Proxy — defer initialization to first use, handle async initialization safely:

```ts
interface PdfReportService {
  generateLoanStatement(loanId: string): Promise<Buffer>;
  generatePortfolioSummary(userId: string): Promise<Buffer>;
}

class LazyPdfReportService implements PdfReportService {
  private initPromise: Promise<RealPdfReportService> | null = null;

  private getInstance(): Promise<RealPdfReportService> {
    if (!this.initPromise) {
      // Store Promise — concurrent callers share this, not the result
      this.initPromise = RealPdfReportService.initialize()
        .catch(err => {
          this.initPromise = null; // Allow retry on initialization failure
          throw err;
        });
    }
    return this.initPromise;
  }

  async generateLoanStatement(loanId: string): Promise<Buffer> {
    const service = await this.getInstance();
    return service.generateLoanStatement(loanId);
  }

  async generatePortfolioSummary(userId: string): Promise<Buffer> {
    const service = await this.getInstance();
    return service.generatePortfolioSummary(userId);
  }
}
```

Key design decisions:
- **`initPromise = null` on failure** — if initialization fails (library missing, OOM), the next caller retries rather than getting a permanently broken proxy.
- **Registered as singleton in NestJS** — the proxy is created once; the 4-second init happens at most once per process lifetime, on first PDF request.
- **Memory benefit** — services that receive no PDF requests (common in non-report endpoints) never pay the 200MB cost.
- **Graceful degradation** — wrap `getInstance()` in a try/catch at the route handler level to return a 503 with a "report generation temporarily unavailable" message if the library fails to initialize.

## Quick Comparison Table

| Aspect                    | Virtual Proxy                          | Protection Proxy                          | Remote Proxy                                | Caching Proxy                             |
|---                        |---                                     |---                                        |---                                          |---                                        |
| Controls                  | *When* real subject is created         | *Whether* caller has permission           | *How* remote subject is reached             | *How often* real subject is called        |
| Real subject location     | Same process — just deferred           | Same process — access guarded             | Different process / network                 | Same or different process                 |
| Creation of real subject  | Lazy — on first use                    | Eager — always exists                     | Not held locally — calls go over network    | Eager — always exists                     |
| Primary benefit           | Faster startup, lower idle memory      | Separation of auth from business logic    | Location transparency, network abstraction  | Reduced latency, reduced load on real     |
| Failure mode              | Init errors on first call, not startup | `ForbiddenException` on unauthorized call | Network errors, timeouts, serialization     | Stale data, cache invalidation complexity |
| Node.js example           | Lazy ES client, lazy PDF library       | Role-based service method guard           | gRPC stub, REST API client, Kafka publisher | ES query cache, Redis-backed API cache    |
| Testability               | Mock the factory / init function       | Mock real subject, vary user roles        | Mock HTTP server (MSW, nock)                | Mock real subject, assert call count      |
| Decorator vs Proxy?       | Proxy — controls when                  | Proxy — controls whether                  | Proxy — controls how                        | Blurs into Decorator — adds behavior      |

---

**Tip for the interview:** At the 5 YOE level, Proxy questions arrive as architecture problems, not pattern definitions. "How do you protect service methods beyond route-level auth?" is a Protection Proxy question. "How do you abstract away which notification transport you're using?" is a Remote Proxy question. "How do you avoid initializing the ML model on every pod startup?" is a Virtual Proxy question. The strongest answers name the variant precisely (virtual / protection / remote — not just "proxy"), explain what *access* is being controlled and *why* that belongs in the proxy rather than the caller, and connect to real Node.js tools: JavaScript's built-in `Proxy` object for universal interception, gRPC stubs as textbook Remote Proxies, TypeORM lazy relations as Virtual Proxies the framework provides for you. Be ready to distinguish Proxy from Decorator with one crisp sentence: *"A Proxy controls whether and how the real subject is reached; a Decorator adds behavior around calls to a subject you already have access to."*
