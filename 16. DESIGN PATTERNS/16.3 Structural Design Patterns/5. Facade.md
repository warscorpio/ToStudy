# JavaScript / TypeScript (Design Patterns — Structural): Facade Pattern — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Facade pattern?**
A: The Facade pattern is a structural design pattern that provides a **simplified, unified interface** to a complex subsystem — a set of classes, libraries, or APIs whose direct use would require the caller to understand many moving parts, call things in the right order, and manage low-level details. The word "facade" is architectural: like the front face of a building that presents a clean exterior while hiding the structural complexity inside, the pattern gives clients one well-named entry point that hides everything behind it.

The Facade does not add new behaviour — it *orchestrates* existing behaviour in the subsystem and exposes only the operations callers actually need. The subsystem classes continue to exist and can still be used directly when necessary; the Facade is an additional convenience layer, not a replacement.

**Q2. What specific problem does the Facade solve?**
A: Without a Facade, client code that uses a complex subsystem must:
- Know which classes exist and which to call in what order.
- Manage low-level details (connection setup, encoding, error mapping) that are incidental to the caller's actual goal.
- Duplicate the same coordination logic across every call site.
- Be updated everywhere when the subsystem changes internally.

```ts
// Without Facade — client must orchestrate the entire video conversion subsystem
import { VideoFile }        from "./VideoFile";
import { OggCompressionCodec } from "./OggCompressionCodec";
import { MPEG4CompressionCodec } from "./MPEG4CompressionCodec";
import { CodecFactory }     from "./CodecFactory";
import { BitrateReader }    from "./BitrateReader";
import { AudioMixer }       from "./AudioMixer";
import { VideoConverter }   from "./VideoConverter";

const file      = new VideoFile("funny-cats.ogg");
const srcCodec  = new CodecFactory().extract(file);
const destCodec = file.name.endsWith(".mp4")
  ? new MPEG4CompressionCodec()
  : new OggCompressionCodec();
const buffer    = BitrateReader.read(file.name, srcCodec);
const result    = BitrateReader.convert(buffer, destCodec);
const mixed     = (new AudioMixer()).fix(result);
// ... every call site duplicates this sequence ✗
```
The Facade collapses this into one call: `videoConverter.convert("funny-cats.ogg", "mp4")`. Every call site is decoupled from the subsystem's internals.

**Q3. What are the participants in the Facade pattern?**
A:
- **Facade** — the simplified interface class. Knows which subsystem classes are responsible for which request. Delegates client calls to the appropriate subsystem objects and orchestrates their interactions.
- **Subsystem classes** — the complex internals. They implement actual functionality, are unaware of the Facade, and have no reference to it. They can be used directly or through the Facade.
- **Client** — uses only the Facade. Decoupled from the subsystem's details and internal structure.
- **Additional Facade (optional)** — a second Facade layered over the first, further simplifying or scoping access for a specific client type. Prevents a single Facade from growing into a god class by grouping related operations.

**Q4. What is the key difference between the Facade pattern and simply wrapping code in a function?**
A: A wrapper function simplifies a *single* operation. The Facade is a *class* (or module) that:
- Groups a *family* of related simplified operations under one cohesive entry point.
- Holds references to subsystem objects (managing their lifecycle or sharing instances across methods).
- Can maintain state across calls (e.g., keeping a shared connection or session open).
- Has a well-defined interface that can be mocked, swapped, or implemented differently.

A standalone `convertVideo()` function is a micro-Facade for one operation. When a subsystem has 5–10 related operations that clients need, grouping them in a Facade class makes the pattern explicit, testable, and replaceable:
```ts
// Wrapper function — fine for one operation
function convertVideo(filename: string, format: string): Buffer { /* ... */ }

// Facade class — multiple related operations, shared subsystem state
class VideoFacade {
  private mixer   = new AudioMixer();
  private factory = new CodecFactory();

  convert(filename: string, format: string): Buffer { /* ... */ }
  extractAudio(filename: string): Buffer { /* ... */ }
  generateThumbnail(filename: string, atSecond: number): Buffer { /* ... */ }
  getMetadata(filename: string): VideoMetadata { /* ... */ }
}
```

**Q5. How does the Facade pattern relate to the principle of least knowledge (Law of Demeter)?**
A: The Law of Demeter says a unit should talk only to its immediate collaborators — not to objects returned by those collaborators (no "train wrecks"). The Facade is the structural tool that enforces this:

```ts
// Law of Demeter violation — client reaches deep into subsystem internals
const thumbnail = videoSystem
  .getProcessor()           // client knows Processor
  .getFrameExtractor()      // client knows FrameExtractor
  .extractFrame(42)         // client knows extractFrame API
  .toBuffer();              // client knows Buffer conversion

// Facade — client talks to one surface only
const thumbnail = videoFacade.generateThumbnail("video.mp4", 42);
```
The Facade is what you build when you notice a Law of Demeter violation — it internalises the chain and gives the client a single, friendly interlocutor.

## Section 2: Implementing the Facade Pattern in TypeScript

**Q6. Show a complete, production-quality Facade implementation for a home theatre system.**
A:
```ts
// Subsystem classes — complex, independent, know nothing about the Facade
class Amplifier {
  private volume = 0;
  on():  void { console.log("Amplifier on"); }
  off(): void { console.log("Amplifier off"); }
  setVolume(level: number): void { this.volume = level; console.log(`Volume: ${level}`); }
  setSurroundSound(): void { console.log("Surround sound enabled"); }
}

class DVDPlayer {
  private currentMovie = "";
  on():  void { console.log("DVD Player on"); }
  off(): void { console.log("DVD Player off"); }
  play(movie: string): void { this.currentMovie = movie; console.log(`Playing: ${movie}`); }
  stop(): void { console.log(`Stopped: ${this.currentMovie}`); this.currentMovie = ""; }
  eject(): void { console.log("DVD ejected"); }
}

class Projector {
  on():  void { console.log("Projector on"); }
  off(): void { console.log("Projector off"); }
  wideScreenMode(): void { console.log("Projector in widescreen mode (16:9)"); }
}

class TheaterLights {
  dim(level: number): void { console.log(`Lights dimmed to ${level}%`); }
  on():  void { console.log("Lights on at 100%"); }
}

class Screen {
  down(): void { console.log("Screen going down"); }
  up():   void { console.log("Screen going up"); }
}

class PopcornPopper {
  on():  void { console.log("Popcorn popper on"); }
  off(): void { console.log("Popcorn popper off"); }
  pop(): void { console.log("Popping popcorn"); }
}

// Facade — simplified interface over all subsystem classes
class HomeTheaterFacade {
  constructor(
    private amp:      Amplifier,
    private dvd:      DVDPlayer,
    private projector: Projector,
    private lights:   TheaterLights,
    private screen:   Screen,
    private popper:   PopcornPopper
  ) {}

  // One method to rule them all — replaces 12+ sequential subsystem calls
  watchMovie(movie: string): void {
    console.log(`\n🎬 Get ready to watch ${movie}...`);
    this.popper.on();
    this.popper.pop();
    this.lights.dim(10);
    this.screen.down();
    this.projector.on();
    this.projector.wideScreenMode();
    this.amp.on();
    this.amp.setSurroundSound();
    this.amp.setVolume(5);
    this.dvd.on();
    this.dvd.play(movie);
  }

  endMovie(): void {
    console.log("\n🛑 Shutting down the home theater...");
    this.popper.off();
    this.lights.on();
    this.screen.up();
    this.projector.off();
    this.amp.off();
    this.dvd.stop();
    this.dvd.eject();
    this.dvd.off();
  }

  // Additional convenience operation
  listenToMusic(album: string): void {
    console.log(`\n🎵 Playing music: ${album}`);
    this.lights.dim(30);
    this.amp.on();
    this.amp.setVolume(8);
    // No projector or screen needed for music
  }
}

// Client — beautifully simple
const theater = new HomeTheaterFacade(
  new Amplifier(), new DVDPlayer(), new Projector(),
  new TheaterLights(), new Screen(), new PopcornPopper()
);

theater.watchMovie("Inception");
theater.endMovie();
```

**Q7. How do you make a Facade properly testable — and how do you mock one?**
A: The Facade should depend on abstractions (DIP), not concretions, so that subsystem components can be injected and faked in tests. The Facade itself should implement an interface so callers can mock it:
```ts
// Define an interface for the Facade — clients depend on this, not the concrete class
interface VideoProcessingFacade {
  convert(filename: string, targetFormat: string): Promise<Buffer>;
  extractAudio(filename: string): Promise<Buffer>;
  generateThumbnail(filename: string, atSecond: number): Promise<Buffer>;
}

// Concrete Facade — depends on injected abstractions, not hard-coded subsystem classes
class VideoProcessingFacadeImpl implements VideoProcessingFacade {
  constructor(
    private codec:   CodecService,
    private bitrate: BitrateService,
    private audio:   AudioService,
    private frames:  FrameService
  ) {}

  async convert(filename: string, targetFormat: string): Promise<Buffer> {
    const srcCodec  = await this.codec.detect(filename);
    const destCodec = await this.codec.forFormat(targetFormat);
    const bitstream = await this.bitrate.read(filename, srcCodec);
    const converted = await this.bitrate.convert(bitstream, destCodec);
    return this.audio.mix(converted);
  }

  async extractAudio(filename: string): Promise<Buffer> {
    const srcCodec = await this.codec.detect(filename);
    return this.audio.extract(filename, srcCodec);
  }

  async generateThumbnail(filename: string, atSecond: number): Promise<Buffer> {
    return this.frames.extractAt(filename, atSecond);
  }
}

// Test — mock the Facade interface, not the subsystem
const mockFacade: VideoProcessingFacade = {
  convert:           jest.fn().mockResolvedValue(Buffer.from("converted")),
  extractAudio:      jest.fn().mockResolvedValue(Buffer.from("audio")),
  generateThumbnail: jest.fn().mockResolvedValue(Buffer.from("thumbnail")),
};

// Test the client that uses the Facade — zero subsystem knowledge needed
const uploader = new VideoUploadService(mockFacade);
await uploader.processAndUpload("video.ogg", "mp4");
expect(mockFacade.convert).toHaveBeenCalledWith("video.ogg", "mp4");
```

**Q8. How does the Facade pattern handle error translation — mapping subsystem-specific errors to domain errors?**
A: Subsystems throw their own exceptions (library errors, HTTP status codes, driver errors). Without a Facade, those leak into the domain layer, coupling it to infrastructure details. The Facade is the natural place to catch and translate:
```ts
// Subsystem throws infrastructure-specific errors
class PaymentGatewayFacade {
  constructor(private stripe: Stripe, private logger: Logger) {}

  async charge(amount: Money, token: PaymentToken): Promise<ChargeResult> {
    try {
      const intent = await this.stripe.paymentIntents.create({
        amount:   amount.toCents(),
        currency: amount.currency.toLowerCase(),
        payment_method: token.value,
        confirm: true,
      });
      return ChargeResult.success(intent.id);

    } catch (err) {
      // Translate Stripe-specific errors to domain errors
      if (err instanceof Stripe.errors.StripeCardError) {
        throw new PaymentDeclinedError(err.decline_code ?? "unknown", err.message);
      }
      if (err instanceof Stripe.errors.StripeRateLimitError) {
        throw new PaymentServiceUnavailableError("Rate limit exceeded — retry later");
      }
      if (err instanceof Stripe.errors.StripeInvalidRequestError) {
        throw new InvalidPaymentTokenError(err.message);
      }
      // Log unexpected errors, rethrow as generic
      this.logger.error("Unexpected Stripe error", { err, amount, token });
      throw new PaymentProcessingError("An unexpected error occurred during payment");
    }
  }
}

// Domain layer catches only domain errors — never Stripe.errors.*
try {
  await paymentFacade.charge(order.total, paymentToken);
} catch (e) {
  if (e instanceof PaymentDeclinedError)          return res.status(402).json({ error: e.message });
  if (e instanceof PaymentServiceUnavailableError) return res.status(503).json({ error: e.message });
  throw e; // re-throw truly unexpected errors
}
```

**Q9. How do you implement a Facade that manages the lifecycle of expensive subsystem resources (connections, sessions, pools)?**
A: The Facade owns the resource lifecycle — clients are completely shielded from setup/teardown:
```ts
class DatabaseFacade {
  private pool: Pool | null = null;
  private isConnected = false;

  async connect(config: DbConfig): Promise<void> {
    if (this.isConnected) return; // idempotent
    this.pool = new Pool({
      host:     config.host,
      port:     config.port,
      database: config.database,
      user:     config.user,
      password: config.password,
      max:      config.maxConnections ?? 10,
      idleTimeoutMillis: 30_000,
    });
    // Verify the connection before marking as ready
    const client = await this.pool.connect();
    client.release();
    this.isConnected = true;
  }

  async query<T>(sql: string, params: unknown[] = []): Promise<T[]> {
    this.assertConnected();
    const { rows } = await this.pool!.query(sql, params);
    return rows as T[];
  }

  async transaction<T>(work: (tx: TransactionContext) => Promise<T>): Promise<T> {
    this.assertConnected();
    const client = await this.pool!.connect();
    try {
      await client.query("BEGIN");
      const result = await work(new TransactionContext(client));
      await client.query("COMMIT");
      return result;
    } catch (err) {
      await client.query("ROLLBACK");
      throw err;
    } finally {
      client.release();
    }
  }

  async disconnect(): Promise<void> {
    if (!this.isConnected || !this.pool) return;
    await this.pool.end();
    this.isConnected = false;
    this.pool = null;
  }

  private assertConnected(): void {
    if (!this.isConnected) throw new Error("DatabaseFacade: not connected. Call connect() first.");
  }
}

// Client — never touches Pool, Client, connection strings
const db = new DatabaseFacade();
await db.connect(config);
const users = await db.query<User>("SELECT * FROM users WHERE active = true");
await db.disconnect();
```

## Section 3: Real-World Applications

**Q10. How does the Facade pattern appear in third-party SDK wrappers?**
A: Every time you wrap a third-party SDK behind a domain interface, you're building a Facade. This is one of the most important practical applications — it decouples your domain from vendor churn:
```ts
// Raw AWS S3 SDK — client must know Bucket names, ACL, ContentType, error codes
import { S3Client, PutObjectCommand, GetObjectCommand,
         DeleteObjectCommand, HeadObjectCommand } from "@aws-sdk/client-s3";

// Facade — the only storage interface the domain layer ever sees
interface FileStorageFacade {
  upload(key: string, data: Buffer, mimeType: string): Promise<string>; // returns URL
  download(key: string): Promise<Buffer>;
  delete(key: string): Promise<void>;
  exists(key: string): Promise<boolean>;
}

class S3StorageFacade implements FileStorageFacade {
  private client: S3Client;

  constructor(private bucket: string, region: string) {
    this.client = new S3Client({ region });
  }

  async upload(key: string, data: Buffer, mimeType: string): Promise<string> {
    await this.client.send(new PutObjectCommand({
      Bucket:      this.bucket,
      Key:         key,
      Body:        data,
      ContentType: mimeType,
      ACL:         "public-read",
    }));
    return `https://${this.bucket}.s3.amazonaws.com/${key}`;
  }

  async download(key: string): Promise<Buffer> {
    const resp = await this.client.send(new GetObjectCommand({
      Bucket: this.bucket, Key: key,
    }));
    return Buffer.from(await resp.Body!.transformToByteArray());
  }

  async delete(key: string): Promise<void> {
    await this.client.send(new DeleteObjectCommand({ Bucket: this.bucket, Key: key }));
  }

  async exists(key: string): Promise<boolean> {
    try {
      await this.client.send(new HeadObjectCommand({ Bucket: this.bucket, Key: key }));
      return true;
    } catch { return false; }
  }
}

// Swapping S3 for GCS = new class implementing FileStorageFacade, zero domain changes
class GCSStorageFacade implements FileStorageFacade { /* ... */ }
class LocalStorageFacade implements FileStorageFacade { /* for dev/test */ }
```

**Q11. How does the Facade pattern apply to authentication and session management in an Express/Node.js application?**
A: Authentication involves many subsystems — JWT signing, token storage, session state, user lookup, password hashing. A Facade unifies them:
```ts
interface AuthFacade {
  register(email: string, password: string): Promise<AuthResult>;
  login(email: string, password: string): Promise<AuthResult>;
  logout(token: string): Promise<void>;
  validateToken(token: string): Promise<UserClaims>;
  refreshToken(refreshToken: string): Promise<AuthResult>;
}

class AuthFacadeImpl implements AuthFacade {
  constructor(
    private users:    UserRepository,
    private passwords: PasswordService,   // bcrypt wrapper
    private jwt:      JwtService,         // sign/verify wrapper
    private sessions: SessionStore,       // Redis token blacklist
    private events:   EventBus
  ) {}

  async register(email: string, password: string): Promise<AuthResult> {
    const existing = await this.users.findByEmail(email);
    if (existing) throw new EmailAlreadyInUseError(email);

    const hash = await this.passwords.hash(password);
    const user = await this.users.create({ email, passwordHash: hash });

    const tokens = this.jwt.issueTokenPair(user.id, user.role);
    await this.sessions.storeRefreshToken(user.id, tokens.refreshToken);
    await this.events.publish("user.registered", { userId: user.id });

    return { user: toPublicUser(user), ...tokens };
  }

  async login(email: string, password: string): Promise<AuthResult> {
    const user = await this.users.findByEmail(email);
    if (!user) throw new InvalidCredentialsError();

    const valid = await this.passwords.verify(password, user.passwordHash);
    if (!valid) throw new InvalidCredentialsError();

    const tokens = this.jwt.issueTokenPair(user.id, user.role);
    await this.sessions.storeRefreshToken(user.id, tokens.refreshToken);
    return { user: toPublicUser(user), ...tokens };
  }

  async logout(token: string): Promise<void> {
    const claims = this.jwt.verify(token);
    await this.sessions.blacklistToken(token, claims.exp);
  }

  async validateToken(token: string): Promise<UserClaims> {
    const blacklisted = await this.sessions.isBlacklisted(token);
    if (blacklisted) throw new TokenRevokedError();
    return this.jwt.verify(token);
  }

  async refreshToken(refreshToken: string): Promise<AuthResult> {
    const userId = await this.sessions.validateRefreshToken(refreshToken);
    if (!userId) throw new InvalidRefreshTokenError();

    const user   = await this.users.findById(userId);
    if (!user)   throw new UserNotFoundError(userId);

    await this.sessions.revokeRefreshToken(refreshToken);
    const tokens = this.jwt.issueTokenPair(user.id, user.role);
    await this.sessions.storeRefreshToken(user.id, tokens.refreshToken);
    return { user: toPublicUser(user), ...tokens };
  }
}

// Express middleware — uses only the Facade
app.post("/auth/login", async (req, res) => {
  const result = await authFacade.login(req.body.email, req.body.password);
  res.json(result);
});
```

**Q12. How does the Facade pattern apply to notification delivery in a multi-channel system?**
A: A notification system may involve email (SendGrid), SMS (Twilio), push (FCM), and in-app notifications (WebSocket/database). A Facade unifies channel selection, template rendering, and delivery:
```ts
interface NotificationFacade {
  notify(userId: string, event: NotificationEvent): Promise<void>;
  notifyBulk(userIds: string[], event: NotificationEvent): Promise<NotificationSummary>;
  markAsRead(notificationId: string): Promise<void>;
}

class NotificationFacadeImpl implements NotificationFacade {
  constructor(
    private prefs:     UserPreferenceService,
    private templates: TemplateEngine,
    private email:     EmailService,
    private sms:       SMSService,
    private push:      PushService,
    private inApp:     InAppNotificationStore,
    private logger:    Logger
  ) {}

  async notify(userId: string, event: NotificationEvent): Promise<void> {
    const userPrefs = await this.prefs.getNotificationPrefs(userId);
    const message   = await this.templates.render(event.templateId, event.data);

    // Always store in-app notification
    await this.inApp.store(userId, message);

    // Deliver via user's preferred channels in parallel
    const deliveries: Promise<void>[] = [];

    if (userPrefs.email.enabled) {
      deliveries.push(
        this.email.send(userPrefs.email.address, message)
          .catch(err => this.logger.warn("Email delivery failed", { userId, err }))
      );
    }
    if (userPrefs.sms.enabled && event.smsEligible) {
      deliveries.push(
        this.sms.send(userPrefs.sms.number, message.shortText)
          .catch(err => this.logger.warn("SMS delivery failed", { userId, err }))
      );
    }
    if (userPrefs.push.enabled && userPrefs.push.deviceToken) {
      deliveries.push(
        this.push.send(userPrefs.push.deviceToken, message)
          .catch(err => this.logger.warn("Push delivery failed", { userId, err }))
      );
    }

    await Promise.all(deliveries);
  }

  async notifyBulk(userIds: string[], event: NotificationEvent): Promise<NotificationSummary> {
    const results = await Promise.allSettled(
      userIds.map(id => this.notify(id, event))
    );
    const succeeded = results.filter(r => r.status === "fulfilled").length;
    const failed    = results.filter(r => r.status === "rejected").length;
    return { total: userIds.length, succeeded, failed };
  }

  async markAsRead(notificationId: string): Promise<void> {
    await this.inApp.markRead(notificationId);
  }
}
```

**Q13. How does the Facade pattern appear in data access layers — specifically the difference between a Facade and a Repository?**
A: They are related but distinct:
- **Repository** — abstracts *data access for a single domain entity* (`UserRepository`, `OrderRepository`). It translates between the domain model and the persistence layer. One repository per aggregate root.
- **Facade** — abstracts a *subsystem* which may include multiple repositories, services, and external calls. It coordinates *multiple* collaborators to execute a higher-level operation.

```ts
// Repository — single entity, data access only
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
  findByCustomer(customerId: string): Promise<Order[]>;
}

// Facade — orchestrates across multiple repositories and services
class OrderFacade {
  constructor(
    private orders:    OrderRepository,
    private inventory: InventoryService,
    private payments:  PaymentFacade,
    private shipping:  ShippingService,
    private events:    EventBus
  ) {}

  // One call coordinates inventory check, payment, order save, shipping, and event
  async placeOrder(dto: PlaceOrderDto): Promise<OrderConfirmation> {
    await this.inventory.reserve(dto.items);

    let order: Order;
    try {
      const charge = await this.payments.charge(dto.total, dto.paymentToken);
      order = Order.create({ ...dto, chargeId: charge.id });
      await this.orders.save(order);
    } catch (err) {
      await this.inventory.release(dto.items); // compensate on failure
      throw err;
    }

    const shipment = await this.shipping.schedule(order);
    await this.events.publish("order.placed", { orderId: order.id, shipmentId: shipment.id });

    return { orderId: order.id, estimatedDelivery: shipment.estimatedDelivery };
  }
}
```
The Repository handles "find and save order"; the Facade handles "place an order" — an operation involving many systems. Both use DIP; the Facade composes Repositories as part of its subsystem.

## Section 4: Facade vs Related Patterns

**Q14. What is the difference between the Facade and the Adapter pattern?**
A: Both produce a simpler or different interface, but they solve different problems:

| Aspect | Facade | Adapter |
|---|---|---|
| **Intent** | Simplify access to a complex subsystem | Make an incompatible interface work with an expected one |
| **Direction** | Reduces complexity; hides many classes behind one | Translates one interface to another |
| **Subsystem knowledge** | Knows and coordinates the subsystem | Wraps a single existing class |
| **New behaviour** | No — orchestrates existing behaviour | No — translates existing behaviour |
| **Replaces existing interface?** | No — subsystem still accessible directly | Yes — wraps a class the client can't change |
| **Typical trigger** | "Too many classes to use this subsystem" | "This library's interface doesn't match what I need" |

```ts
// Adapter — making a third-party logger match your LogService interface
interface LogService { log(level: string, message: string): void; }

class WinstonAdapter implements LogService { // wraps Winston to match LogService
  constructor(private winston: Logger) {}
  log(level: string, message: string): void { this.winston[level](message); }
}

// Facade — simplifying the entire logging subsystem
class LoggingFacade {
  constructor(private transport: LogService, private metrics: MetricsService) {}
  info(msg: string, ctx?: object): void  { this.transport.log("info",  msg); this.metrics.increment("log.info"); }
  error(msg: string, ctx?: object): void { this.transport.log("error", msg); this.metrics.increment("log.error"); }
  // ... groups transport + metrics + context under one surface
}
```

**Q15. What is the difference between the Facade and the Mediator pattern?**
A: Both centralise communication, but they differ in awareness:

| Aspect | Facade | Mediator |
|---|---|---|
| **Direction of knowledge** | Facade knows the subsystem; subsystem doesn't know the Facade | Mediator knows all components; components know the Mediator |
| **Communication flow** | One-directional — client → Facade → subsystem | Bidirectional — components communicate *through* the Mediator |
| **Purpose** | Simplify external access to a subsystem | Decouple components that would otherwise communicate directly |
| **Subsystem coupling** | Subsystem classes remain independent of Facade | Components are coupled to the Mediator interface |

```ts
// Facade — EmailService doesn't know it's being called by a Facade
class OrderFacade {
  constructor(private email: EmailService, private orders: OrderRepository) {}
  placeOrder(dto: PlaceOrderDto): Promise<Order> { /* orchestrates; subsystems unaware */ }
}

// Mediator — components send/receive through the Mediator and know about it
class AirTrafficControl { // Mediator
  notify(sender: Aircraft, event: string): void {
    if (event === "landing")  { /* coordinate other aircraft */ }
    if (event === "departing") { /* coordinate runway */ }
  }
}
class Aircraft { constructor(private atc: AirTrafficControl) {} } // knows the Mediator
```

**Q16. What is the difference between the Facade and the Proxy pattern?**
A: Both wrap another object, but their intent differs:

| Aspect | Facade | Proxy |
|---|---|---|
| **Interface** | Usually a *simpler* interface than what it hides | *Same* interface as the wrapped object |
| **What it wraps** | An entire subsystem (many classes) | A single object |
| **Purpose** | Simplify; hide complexity | Control access, add caching, lazy initialisation, logging |
| **Transparency** | Not transparent — clients know they're using a Facade | Transparent — clients don't know they're using a Proxy |

```ts
// Proxy — same interface as DatabaseService, adds caching transparently
class CachedDatabaseService implements DatabaseService {
  private cache = new Map<string, unknown>();
  constructor(private real: DatabaseService) {}

  async query<T>(sql: string, params: unknown[]): Promise<T[]> {
    const key = JSON.stringify({ sql, params });
    if (this.cache.has(key)) return this.cache.get(key) as T[];
    const result = await this.real.query<T>(sql, params);
    this.cache.set(key, result);
    return result;
  }
}

// Facade — different (simpler) interface, hides the entire database subsystem
class ReportingFacade {
  async getMonthlySales(month: string): Promise<SalesSummary> { /* hides SQL complexity */ }
  async getTopProducts(limit: number): Promise<Product[]>     { /* hides join complexity */ }
}
```

**Q17. What is the difference between the Facade and the Decorator pattern?**
A: Decorator adds behaviour to a single object through a shared interface; Facade simplifies access to an entire subsystem:

| Aspect | Facade | Decorator |
|---|---|---|
| **Interface** | Usually simpler than the subsystem | Same interface as the wrapped object |
| **What it wraps** | An entire subsystem | A single component |
| **Stacking** | Not stackable — single entry point | Stackable — decorators chain |
| **Purpose** | Simplify complexity | Add / modify behaviour incrementally |
| **Composition** | Composes multiple subsystem classes | Composes one component of the same type |

## Section 5: Pitfalls, Anti-Patterns & Misapplications

**Q18. What is the "God Facade" anti-pattern, and how do you prevent it?**
A: A God Facade grows to expose every operation of every subsystem class under one class — it becomes a 1,000-line monolith with no clear single responsibility. Every new subsystem capability gets added to the same Facade, and it ends up being the new "complex system" the Facade was supposed to hide:
```ts
// God Facade — one class, every operation in the entire application
class AppFacade {
  placeOrder(dto: PlaceOrderDto): Promise<Order> { /* ... */ }
  cancelOrder(id: string): Promise<void> { /* ... */ }
  registerUser(dto: RegisterDto): Promise<User> { /* ... */ }
  loginUser(email: string, password: string): Promise<AuthResult> { /* ... */ }
  uploadAvatar(userId: string, file: Buffer): Promise<string> { /* ... */ }
  generateReport(type: string, range: DateRange): Promise<Buffer> { /* ... */ }
  sendNotification(userId: string, msg: string): Promise<void> { /* ... */ }
  processRefund(orderId: string): Promise<void> { /* ... */ }
  // ... 50 more methods ✗
}
```
Fix — use *Additional Facades*: split by bounded context or domain capability:
```ts
class OrderFacade        { placeOrder(); cancelOrder(); processRefund(); }
class AuthFacade         { register(); login(); logout(); refreshToken(); }
class MediaFacade        { uploadAvatar(); deleteAvatar(); generateThumbnail(); }
class ReportingFacade    { generateReport(); scheduleReport(); exportReport(); }
class NotificationFacade { notify(); notifyBulk(); markAsRead(); }
```
Each Facade has a single responsibility — it simplifies one domain's subsystem, not all subsystems.

**Q19. When is the Facade pattern the wrong choice?**
A: The Facade is inappropriate when:
- **The subsystem is simple** — if the subsystem has two or three classes with obvious usage, a Facade adds indirection with no benefit.
- **You need full subsystem power** — a Facade's simplified interface inevitably hides options. If callers regularly need to escape the Facade and use the subsystem directly, the Facade boundary is in the wrong place or the abstraction is too lossy.
- **It becomes a pass-through** — if every Facade method does nothing but call a single subsystem method with the same parameters, it's not simplifying anything; it's just an indirection layer.

```ts
// Pass-through Facade — no value added
class UserFacade {
  constructor(private repo: UserRepository) {}
  findById(id: string): Promise<User | null> { return this.repo.findById(id); } // ✗ no facade value
  save(user: User): Promise<void>            { return this.repo.save(user);    } // ✗ no facade value
}
// The repository IS the simple interface — no Facade needed
```

**Q20. How does the Facade interact with the dependency graph — and what coupling does it introduce?**
A: The Facade *reduces* coupling for clients but *concentrates* it in itself. The Facade class imports and depends on all subsystem classes — it is the one place that knows about everything:
```
Client → Facade → [SubsystemA, SubsystemB, SubsystemC, SubsystemD]
```
This is a deliberate trade-off:
- **Positive** — every other class in the system depends on fewer things.
- **Risk** — the Facade becomes a high-efferent-coupling class. If it imports too many concrete classes, it becomes brittle to subsystem changes.
- **Mitigation** — apply DIP to the Facade's dependencies: inject subsystem collaborators via interfaces rather than constructing them internally. This makes the Facade's dependencies explicit, testable, and swappable.

```ts
// Facade that constructs its own dependencies — brittle
class OrderFacade {
  private repo     = new MySQLOrderRepository(); // hard-coded ✗
  private payments = new StripePaymentService(); // hard-coded ✗
}

// Facade with injected abstractions — flexible, testable ✓
class OrderFacade {
  constructor(
    private repo:     OrderRepository,
    private payments: PaymentGateway,
    private shipping: ShippingService
  ) {}
}
```

**Q21. What is "leaky Facade" and how do you detect it?**
A: A leaky Facade is one that exposes subsystem types in its public interface — forcing callers to import from the subsystem they were supposed to be shielded from:
```ts
// Leaky Facade — parameter and return types are subsystem types
import { Stripe }         from "stripe";
import { StripeCharge }   from "stripe/types";
import { PrismaClient }   from "@prisma/client";

class PaymentFacade {
  // Leaks Stripe types into the public interface ✗
  async charge(amount: number, stripeToken: Stripe.Token): Promise<StripeCharge> { /* ... */ }
}

// Client must import Stripe just to call the Facade — not shielded at all ✗
import { Stripe } from "stripe";
const charge = await paymentFacade.charge(100, stripeToken as Stripe.Token);

// Fixed Facade — all types are domain types
class PaymentFacade {
  async charge(amount: Money, token: PaymentToken): Promise<ChargeResult> { /* ... */ }
}
// Client imports only domain types — Stripe is invisible ✓
```
Detection heuristic: if a caller of the Facade must import anything from the subsystem's packages, the Facade is leaking.

## Section 6: Scenario / System Design Style Questions

**Q22. "A new engineer on your team says 'I just call the Stripe API directly in the controller — it's only a few lines.' What concerns do you raise, and how does a Facade help?"**
A: Surface the long-term risks:

1. **Coupling controller to Stripe** — the controller now knows Stripe's SDK types, error model, and API shape. A Stripe SDK major version bump requires touching every controller that calls Stripe directly.
2. **Duplicated error handling** — every controller that calls Stripe must handle `StripeCardError`, `StripeRateLimitError`, etc. This logic will be copy-pasted across files.
3. **Untestable controller** — testing the controller requires a real Stripe connection or complex module-level mocking. With a Facade, the test injects a fake `PaymentFacade`.
4. **No error translation** — Stripe errors leak to the HTTP response layer in Stripe's vocabulary, not the domain's.
5. **Impossible to swap providers** — switching from Stripe to Braintree means finding every direct Stripe call across the codebase.

Proposed resolution:
```ts
// Controller uses only the Facade interface — knows nothing about Stripe
class PaymentController {
  constructor(private payments: PaymentFacade) {}

  async chargeEndpoint(req: Request, res: Response): Promise<void> {
    try {
      const result = await this.payments.charge(
        Money.fromCents(req.body.amountCents, req.body.currency),
        new PaymentToken(req.body.token)
      );
      res.json({ chargeId: result.chargeId });
    } catch (e) {
      if (e instanceof PaymentDeclinedError) return res.status(402).json({ error: e.message });
      throw e;
    }
  }
}

// Test — no Stripe needed
const mockPayments: PaymentFacade = { charge: jest.fn().mockResolvedValue({ chargeId: "ch_test" }) };
const controller = new PaymentController(mockPayments);
```

**Q23. "You're building a new feature: 'place order' which must check inventory, charge payment, create the order record, schedule shipping, send a confirmation email, and emit a domain event. Where does the Facade fit in the architecture?"**
A: This is the canonical multi-subsystem coordination use case. The Facade sits at the application layer, orchestrating domain and infrastructure:

```
HTTP Layer (Controller)
      ↓  calls
Application Layer (OrderFacade)    ← Facade lives here
      ↓  coordinates
  ├── Domain (Order aggregate, domain events)
  ├── InventoryService (interface)
  ├── PaymentFacade (interface)
  ├── ShippingService (interface)
  ├── EmailService (interface)
  └── EventBus (interface)
      ↓  implemented by
Infrastructure Layer (Prisma, Stripe, SendGrid, RabbitMQ, ShipStation)
```

```ts
class OrderFacade {
  constructor(
    private orders:    OrderRepository,
    private inventory: InventoryService,
    private payments:  PaymentFacade,
    private shipping:  ShippingService,
    private email:     EmailService,
    private events:    EventBus,
    private logger:    Logger
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<OrderConfirmation> {
    // Step 1 — reserve inventory (can be rolled back)
    const reservation = await this.inventory.reserve(dto.items);

    let order: Order;
    let charge: ChargeResult;

    try {
      // Step 2 — charge payment
      charge = await this.payments.charge(dto.total, dto.paymentToken);

      // Step 3 — persist order
      order = Order.create({
        customerId: dto.customerId,
        items:      dto.items,
        total:      dto.total,
        chargeId:   charge.chargeId,
      });
      await this.orders.save(order);

    } catch (err) {
      // Compensate: release inventory on failure
      await this.inventory.release(reservation.id).catch(e =>
        this.logger.error("Failed to release inventory", { reservationId: reservation.id, e })
      );
      throw err;
    }

    // Steps 4-6 — non-critical: run in parallel, log but don't fail the order
    await Promise.allSettled([
      this.shipping.schedule(order)
        .then(s => this.orders.updateShipment(order.id, s.id))
        .catch(e => this.logger.error("Shipping schedule failed", { orderId: order.id, e })),

      this.email.sendOrderConfirmation(dto.customerEmail, order)
        .catch(e => this.logger.warn("Confirmation email failed", { orderId: order.id, e })),

      this.events.publish("order.placed", { orderId: order.id, customerId: dto.customerId })
        .catch(e => this.logger.error("Event publish failed", { orderId: order.id, e })),
    ]);

    return { orderId: order.id, total: order.total, estimatedDelivery: "3-5 business days" };
  }
}

// Controller — one line, zero subsystem knowledge
app.post("/orders", async (req, res) => {
  const confirmation = await orderFacade.placeOrder(req.body);
  res.status(201).json(confirmation);
});
```

**Q24. "A legacy codebase has a 3,000-line `Utils` class that every file in the project imports. How would you use the Facade pattern to begin untangling it?"**
A: The `Utils` god class is a low-cohesion, high-coupling hub. The Strangler Fig approach uses Facades to incrementally replace it:

1. **Audit usage** — use `dependency-cruiser` or grep to find which methods of `Utils` each module actually calls. Group by domain: formatting, auth helpers, date utilities, encryption, HTTP helpers.

2. **Extract domain Facades** — create a new focused module per group, implementing the same signatures:
```ts
// Before — everything in one place
import { Utils } from "./utils";
Utils.hashPassword(pw);
Utils.formatCurrency(amount, "INR");
Utils.parseJwt(token);

// Phase 1 — new Facades delegate to Utils internally (no behaviour change yet)
// security/PasswordFacade.ts
export class PasswordFacade {
  static hash(pw: string): Promise<string> { return Utils.hashPassword(pw); } // delegates
}

// Phase 2 — migrate callers to new Facades one module at a time
import { PasswordFacade } from "./security/PasswordFacade";
PasswordFacade.hash(pw); // same behaviour, new import

// Phase 3 — replace Utils internals with real implementations in each Facade
export class PasswordFacade {
  static hash(pw: string): Promise<string> { return bcrypt.hash(pw, 12); } // real impl
}

// Phase 4 — once no module imports Utils directly, delete it
```

3. **Enforce the boundary** — add an ESLint rule or `dependency-cruiser` constraint that prohibits new imports of `Utils`, forcing all new code to use the domain Facades.

**Q25. "Your team is integrating with five different logistics providers (FedEx, DHL, BlueDart, Delhivery, India Post), each with a completely different API. How do you design this with a Facade?"**
A: Each provider needs its own Adapter (to normalise its API to a common interface), and a single ShippingFacade sits above them all to route, retry, and aggregate:
```ts
// Common domain interface — what the application needs
interface ShippingProvider {
  getQuote(shipment: ShipmentDetails): Promise<ShippingQuote>;
  createShipment(shipment: ShipmentDetails, quoteId: string): Promise<Shipment>;
  trackShipment(trackingNumber: string): Promise<TrackingStatus>;
  cancelShipment(shipmentId: string): Promise<void>;
}

// Adapters — each normalises a provider API to ShippingProvider
class FedExAdapter    implements ShippingProvider { constructor(private sdk: FedExSDK) {} /* ... */ }
class DHLAdapter      implements ShippingProvider { constructor(private api: DHLApi) {} /* ... */ }
class BlueDartAdapter implements ShippingProvider { /* ... */ }
class DelhiveryAdapter implements ShippingProvider { /* ... */ }

// Facade — routes, retries, picks cheapest, aggregates across providers
class ShippingFacade {
  private providers: Map<string, ShippingProvider>;

  constructor(adapters: Record<string, ShippingProvider>) {
    this.providers = new Map(Object.entries(adapters));
  }

  // Get cheapest quote across all providers
  async getCheapestQuote(shipment: ShipmentDetails): Promise<{ provider: string; quote: ShippingQuote }> {
    const quotes = await Promise.allSettled(
      [...this.providers.entries()].map(async ([name, p]) => ({
        provider: name,
        quote: await p.getQuote(shipment),
      }))
    );
    const successful = quotes
      .filter((r): r is PromiseFulfilledResult<{ provider: string; quote: ShippingQuote }> =>
        r.status === "fulfilled"
      )
      .map(r => r.value);

    if (!successful.length) throw new NoShippingQuoteAvailableError(shipment);
    return successful.sort((a, b) => a.quote.price.amount - b.quote.price.amount)[0];
  }

  async shipWithProvider(
    providerName: string,
    shipment: ShipmentDetails,
    quoteId: string
  ): Promise<Shipment> {
    const provider = this.providers.get(providerName);
    if (!provider) throw new UnknownProviderError(providerName);
    return provider.createShipment(shipment, quoteId);
  }

  async trackShipment(trackingNumber: string, provider: string): Promise<TrackingStatus> {
    const p = this.providers.get(provider);
    if (!p) throw new UnknownProviderError(provider);
    return p.trackShipment(trackingNumber);
  }
}

// Client — one interface for all five providers
const { provider, quote } = await shippingFacade.getCheapestQuote(shipmentDetails);
const shipment = await shippingFacade.shipWithProvider(provider, shipmentDetails, quote.id);
```

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | Without Facade | With Facade |
|---|---|---|
| **Client knowledge** | Must know all subsystem classes and their order | Knows one class and a few methods |
| **Call sites** | Coordination logic duplicated everywhere | Coordination in one place |
| **Subsystem coupling** | Client coupled to every subsystem class | Client coupled to Facade only |
| **Error handling** | Each call site handles subsystem errors | Facade translates to domain errors |
| **Testability** | Test requires all subsystem dependencies | Mock the Facade interface |
| **Subsystem swappability** | Change subsystem → update every call site | Change subsystem → update Facade only |
| **Type leakage** | Subsystem types visible to client | Domain types only on Facade surface |
| **Learning curve** | Must understand entire subsystem | Must understand Facade's domain methods |

## Facade vs Structurally Similar Patterns (at a glance)

| Pattern | Wraps | Interface | Purpose | Subsystem aware of it? |
|---|---|---|---|---|
| **Facade** | An entire subsystem (many classes) | Simpler than subsystem | Simplify complex access | No |
| **Adapter** | A single incompatible class | Compatible with expected | Bridge interface mismatch | N/A (wraps one class) |
| **Proxy** | A single object | Same as wrapped | Control access, caching, lazy init | No |
| **Decorator** | A single object of same type | Same as wrapped | Add behaviour incrementally | No |
| **Mediator** | N/A — is a hub | Mediator interface | Decouple components from each other | Yes — components know Mediator |

---

**Tip for the interview:** At the 5 YOE level, "what is the Facade pattern" surfaces as: how do you decouple the controller from Stripe, how would you design an order placement flow that coordinates five subsystems, how do you prevent a legacy `Utils` class from spreading further, or how do you support five shipping providers without writing provider-specific logic everywhere. The sharp answer immediately names the problem being solved (complexity, coupling, duplication), shows the before/after interface contrast, explains the error translation role (subsystem exceptions become domain exceptions at the Facade boundary), and addresses the leaky Facade risk (domain types on the interface, never subsystem types). Distinguishing it clearly from Adapter (interface mismatch vs complexity) and Mediator (subsystem unaware vs components aware) at a whiteboard level is what lands at 5 YOE.
