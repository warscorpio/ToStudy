# Structural Design Patterns: Decorator — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Decorator pattern?**
A: Decorator is a structural design pattern that adds new behaviour to an object **dynamically at runtime** by wrapping it in a decorator object that implements the same interface. The decorator forwards calls to the wrapped object (the "component") and adds its own logic before or after — without modifying the original class and without subclassing. It's sometimes called a "wrapper" pattern because it literally wraps an object in successive layers, like nesting Russian dolls.

The four roles in every Decorator implementation:
- **Component interface** — the contract that both the real object and all decorators implement.
- **Concrete Component** — the real object being decorated; the base behaviour.
- **Base Decorator** — an abstract class that holds a reference to a component and delegates all calls to it. Concrete decorators extend this.
- **Concrete Decorators** — each adds one specific behaviour before/after delegating to the wrapped component.

**Q2. What problem does Decorator solve? When should you reach for it?**
A: Decorator solves the **combinatorial subclass explosion** problem. Suppose you have a `LoanService` and you want to add: logging, metrics, caching, retry logic, and rate limiting — in various combinations depending on the environment. Inheritance would require a separate subclass for every combination (`LoggingLoanService`, `CachingLoggingLoanService`, `RetryingCachingLoggingLoanService`, etc.) — exponential growth. Decorator stacks these behaviours composably at runtime:

```typescript
const service = new RetryDecorator(
  new RateLimitDecorator(
    new CachingDecorator(
      new LoggingDecorator(
        new ConcreteLoanService()
      )
    )
  )
);
```

Reach for it when:
- You need to add **cross-cutting concerns** (logging, caching, retry, auth, metrics) to an object without touching its class.
- You need **different combinations** of behaviours in different contexts (dev vs prod, free tier vs premium tier).
- You must **respect the Open/Closed Principle** — extend behaviour without modifying existing code.
- The alternative would be **inheritance that doesn't scale** — behaviours multiply combinatorially.

**Q3. What is the single most important structural rule of the Decorator pattern?**
A: The decorator must implement the **exact same interface** as the component it wraps. This is what makes stacking transparent — the client doesn't know whether it's talking to the real component or a chain of decorators. If the decorator adds new methods not on the interface, it's no longer a Decorator — it's just a wrapper class. The interface identity is the invariant that makes the pattern work.

**Q4. How does the Decorator pattern differ from inheritance for adding behaviour?**
A:

| Aspect                        | Inheritance                                      | Decorator                                         |
|-------------------------------|--------------------------------------------------|---------------------------------------------------|
| Time of composition           | Compile time — fixed in class hierarchy          | Runtime — assembled at startup or dynamically     |
| Combinations                  | Exponential subclass growth                      | Linear — N decorators cover all combinations      |
| Modifying the original class  | Must subclass — original class may not change    | Never touches the original class                  |
| Single Responsibility         | Subclass often mixes multiple concerns           | Each decorator has exactly one added concern      |
| Open/Closed compliance        | Adding behaviour often requires modifying base   | Always additive — never modifies existing code    |
| Transparency to client        | Client knows which subclass it has               | Client sees only the interface — unaware of layers |

**Q5. How does the Decorator pattern differ from Adapter and Proxy?**
A: All three wrap another object — the distinction is intent and interface:

| Pattern       | Same interface as wrapped object? | Intent                                              |
|---------------|-----------------------------------|-----------------------------------------------------|
| **Decorator** | Yes — must match exactly          | Add behaviour to an existing object transparently   |
| **Adapter**   | No — translates to a different interface | Reconcile two incompatible interfaces          |
| **Proxy**     | Yes — must match exactly          | Control *access* to an object (lazy load, auth, cache) |

Decorator and Proxy look structurally identical — both implement the same interface and wrap a component. Their intent differs: a Proxy controls access or lifecycle; a Decorator enriches behaviour. In practice, the lines blur — a caching proxy could be called a caching decorator. The pattern name signals *why* you're wrapping, not *how*.

## Section 2: Implementation

**Q6. What does a canonical TypeScript Decorator pattern implementation look like?**
A:

```typescript
// Component interface — the contract everything implements
interface BureauService {
  fetchCreditReport(pan: string): Promise<CreditReport>;
}

// Concrete Component — the real implementation
@Injectable()
export class CibilBureauService implements BureauService {
  constructor(private readonly httpClient: HttpService) {}

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const response = await this.httpClient.axiosRef.get(`/report/${pan}`);
    return mapToDomain(response.data);
  }
}

// Base Decorator — holds the wrapped component, delegates all calls
abstract class BureauServiceDecorator implements BureauService {
  constructor(protected readonly wrapped: BureauService) {}

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    return this.wrapped.fetchCreditReport(pan); // default: pure delegation
  }
}

// Concrete Decorator 1 — adds logging
class LoggingBureauDecorator extends BureauServiceDecorator {
  constructor(wrapped: BureauService, private readonly logger: Logger) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    this.logger.log(`[Bureau] Fetching report for PAN: ${pan}`);
    const start = Date.now();
    try {
      const result = await super.fetchCreditReport(pan);
      this.logger.log(`[Bureau] Report fetched in ${Date.now() - start}ms`);
      return result;
    } catch (err) {
      this.logger.error(`[Bureau] Failed for PAN ${pan}: ${(err as Error).message}`);
      throw err;
    }
  }
}

// Concrete Decorator 2 — adds in-memory caching
class CachingBureauDecorator extends BureauServiceDecorator {
  private readonly cache = new Map<string, { report: CreditReport; fetchedAt: number }>();
  private readonly ttlMs = 24 * 60 * 60 * 1000; // 24 hours — bureau reports don't change intraday

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const cached = this.cache.get(pan);
    if (cached && Date.now() - cached.fetchedAt < this.ttlMs) {
      return cached.report;
    }
    const report = await super.fetchCreditReport(pan);
    this.cache.set(pan, { report, fetchedAt: Date.now() });
    return report;
  }
}

// Concrete Decorator 3 — adds retry with exponential backoff
class RetryBureauDecorator extends BureauServiceDecorator {
  constructor(wrapped: BureauService, private readonly maxAttempts = 3) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    let lastError: Error;
    for (let attempt = 1; attempt <= this.maxAttempts; attempt++) {
      try {
        return await super.fetchCreditReport(pan);
      } catch (err) {
        lastError = err as Error;
        if (attempt < this.maxAttempts) {
          await this.delay(200 * 2 ** (attempt - 1)); // 200ms, 400ms, 800ms
        }
      }
    }
    throw lastError!;
  }

  private delay(ms: number) { return new Promise(res => setTimeout(res, ms)); }
}
```

```typescript
// Assembly — stacked at composition root (NestJS module)
const service: BureauService = new RetryBureauDecorator(
  new CachingBureauDecorator(
    new LoggingBureauDecorator(
      new CibilBureauService(httpClient),
      logger,
    )
  ),
  3,
);

// Consumer — sees only BureauService, unaware of the stack
const report = await service.fetchCreditReport('ABCDE1234F');
// Execution: Retry → Cache → Log → CibilBureauService → Log → Cache → Retry
```

**Q7. How do you wire Decorator chains in NestJS's dependency injection system?**
A: NestJS DI doesn't natively support decorator chains on the same token — you need to use `useFactory` to assemble the stack manually:

```typescript
@Module({
  providers: [
    CibilBureauService,
    Logger,
    {
      provide: 'BUREAU_SERVICE',
      useFactory: (
        cibil: CibilBureauService,
        logger: Logger,
      ): BureauService =>
        new RetryBureauDecorator(
          new CachingBureauDecorator(
            new LoggingBureauDecorator(cibil, logger)
          ),
          3,
        ),
      inject: [CibilBureauService, Logger],
    },
  ],
  exports: ['BUREAU_SERVICE'],
})
export class BureauModule {}

// Consumer
@Injectable()
export class UnderwritingService {
  constructor(
    @Inject('BUREAU_SERVICE') private readonly bureau: BureauService,
  ) {}
}
```

For simpler cases where each decorator wraps the previous one cleanly, you can chain `useFactory` providers — each providing the next decorator token that the subsequent `useFactory` injects.

**Q8. Does the order of decorator stacking matter? How do you reason about it?**
A: Order matters significantly — execution flows *inward* on the way in and *outward* on the way back. Think of it as a call stack:

```
Retry.fetchCreditReport()          // outermost — catches all errors from inner layers
  └─ Cache.fetchCreditReport()     // checks cache before going deeper
       └─ Log.fetchCreditReport()  // logs just before and after the real call
            └─ CibilBureauService  // actual HTTP call
```

The correct reasoning framework: **outermost decorator runs first on entry, last on exit**. Practical ordering rules:
- **Retry should wrap Cache** — you want to retry the entire operation including cache misses; retrying inside the cache is pointless.
- **Cache should wrap the real service** — on cache miss, only the inner layers (real service) are called; logging and metrics should sit between cache and real service to measure only actual API calls.
- **Auth/rate-limiter should be outermost** — fail fast before spending any resources on downstream calls.
- **Logging of final outcome** is usually outermost; logging of internal timing is innermost.

**Q9. How do TypeScript/JavaScript class decorators (the `@` syntax) relate to the Decorator design pattern?**
A: They share a name and philosophical ancestor but are distinct:

- **Decorator design pattern** — a runtime technique using object composition. Wraps an object in a chain of same-interface objects to add behaviour. Works at the *instance* level.
- **TypeScript/JavaScript `@Decorator` syntax** — a language feature (still Stage 3 proposal in JS; stable in TypeScript with `experimentalDecorators`) that applies a *function* to a class, method, property, or parameter *at class definition time*. Works at the *class metadata* level, not the instance level.

NestJS uses `@` decorators extensively (`@Injectable()`, `@Controller()`, `@Get()`) — these are metadata annotations that the NestJS framework reads at bootstrap to wire up its DI container and routing. They're not the Decorator *design pattern* — they're decorator *functions* that annotate rather than wrap. However, NestJS interceptors (`@UseInterceptors()`) *are* an implementation of the Decorator design pattern — they wrap handler execution transparently.

## Section 3: Decorator in Real-World Fintech Contexts

**Q10. How would you use Decorator to add Redis caching to a bureau report service in a lending platform?**
A: Replace the in-memory cache decorator with a Redis-backed one — same interface, different implementation:

```typescript
class RedisCachingBureauDecorator extends BureauServiceDecorator {
  private readonly CACHE_PREFIX = 'bureau:report:';
  private readonly TTL_SECONDS = 86400; // 24 hours

  constructor(
    wrapped: BureauService,
    private readonly redis: Redis,
  ) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const cacheKey = `${this.CACHE_PREFIX}${pan}`;

    const cached = await this.redis.get(cacheKey);
    if (cached) {
      return JSON.parse(cached) as CreditReport;
    }

    const report = await super.fetchCreditReport(pan);

    await this.redis.set(cacheKey, JSON.stringify(report), 'EX', this.TTL_SECONDS);
    return report;
  }
}
```

The key benefit: every service that injects `BureauService` gets Redis caching for free — no changes to `UnderwritingService`, `LoanEligibilityService`, or any consumer. Swapping from in-memory to Redis cache is a one-line change in the module's `useFactory`.

**Q11. How would you implement a rate-limiting Decorator for CIBIL API calls that enforces a per-minute cap?**
A: A rate-limiter decorator sits outermost in the chain — it gates access before any other layer runs:

```typescript
class RateLimitingBureauDecorator extends BureauServiceDecorator {
  private callTimestamps: number[] = [];

  constructor(
    wrapped: BureauService,
    private readonly maxCallsPerMinute: number,
    private readonly logger: Logger,
  ) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    this.enforceRateLimit();
    return super.fetchCreditReport(pan);
  }

  private enforceRateLimit(): void {
    const now = Date.now();
    const windowStart = now - 60_000;

    // Evict timestamps outside the window
    this.callTimestamps = this.callTimestamps.filter(ts => ts > windowStart);

    if (this.callTimestamps.length >= this.maxCallsPerMinute) {
      this.logger.warn(`[RateLimit] CIBIL rate limit reached (${this.maxCallsPerMinute}/min)`);
      throw new TooManyRequestsException('Bureau API rate limit exceeded');
    }

    this.callTimestamps.push(now);
  }
}

// Stacked — rate limiter is outermost, fails fast before retry or cache logic
const service: BureauService = new RateLimitingBureauDecorator(
  new RetryBureauDecorator(
    new RedisCachingBureauDecorator(
      new LoggingBureauDecorator(
        new CibilBureauService(httpClient),
        logger,
      ),
      redis,
    ),
    3,
  ),
  100, // 100 calls/minute CIBIL limit
  logger,
);
```

**Q12. How do you use Decorator to add PAN masking and audit logging to sensitive data access in a fintech app?**
A: Compliance requirements (RBI data localisation, PCI-DSS) often mandate that sensitive identifiers be masked in logs and that every access be recorded in an audit trail. A decorator enforces this without touching the core service:

```typescript
interface ApplicantRepository {
  findByPan(pan: string): Promise<Applicant>;
  findById(id: string): Promise<Applicant>;
}

class AuditLoggingApplicantDecorator implements ApplicantRepository {
  constructor(
    private readonly wrapped: ApplicantRepository,
    private readonly auditLog: AuditLogService,
    private readonly requestContext: RequestContextService,
  ) {}

  async findByPan(pan: string): Promise<Applicant> {
    const maskedPan = this.maskPan(pan); // ABCDE1234F → ABCDE****F
    await this.auditLog.record({
      action: 'APPLICANT_LOOKUP_BY_PAN',
      performedBy: this.requestContext.userId,
      resourceId: maskedPan,
      timestamp: new Date(),
      ipAddress: this.requestContext.ipAddress,
    });

    const applicant = await this.wrapped.findByPan(pan);

    // Mask PAN in the returned object before it leaves the repository layer
    return { ...applicant, pan: maskedPan };
  }

  async findById(id: string): Promise<Applicant> {
    await this.auditLog.record({
      action: 'APPLICANT_LOOKUP_BY_ID',
      performedBy: this.requestContext.userId,
      resourceId: id,
      timestamp: new Date(),
    });
    return this.wrapped.findById(id);
  }

  private maskPan(pan: string): string {
    return `${pan.slice(0, 5)}****${pan.slice(-1)}`;
  }
}
```

Every data access layer in the system gets audit logging by wrapping — no changes to `LoanRepository`, `UnderwritingService`, or anything downstream.

**Q13. How would you use Decorator to implement circuit-breaker behaviour around bureau API calls?**
A: A circuit-breaker decorator tracks consecutive failures and "opens" the circuit to prevent cascading failures when CIBIL is down:

```typescript
type CircuitState = 'CLOSED' | 'OPEN' | 'HALF_OPEN';

class CircuitBreakerBureauDecorator extends BureauServiceDecorator {
  private state: CircuitState = 'CLOSED';
  private failureCount = 0;
  private lastFailureTime = 0;

  constructor(
    wrapped: BureauService,
    private readonly failureThreshold = 5,
    private readonly recoveryTimeMs = 30_000,
  ) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureTime > this.recoveryTimeMs) {
        this.state = 'HALF_OPEN'; // allow one probe attempt
      } else {
        throw new ServiceUnavailableException('Bureau circuit breaker is OPEN');
      }
    }

    try {
      const result = await super.fetchCreditReport(pan);
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure();
      throw err;
    }
  }

  private onSuccess(): void {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure(): void {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= this.failureThreshold) {
      this.state = 'OPEN';
    }
  }
}
```

Stack ordering: `RateLimit → CircuitBreaker → Retry → Cache → Log → CibilBureauService`. The circuit breaker sits *outside* retry — no point retrying when the circuit is open.

**Q14. How do you use Decorator to add metrics/observability (latency, error rate) to any service in a NestJS app?**
A: A metrics decorator wraps any service and emits timing and error metrics without the service knowing:

```typescript
class MetricsBureauDecorator extends BureauServiceDecorator {
  constructor(
    wrapped: BureauService,
    private readonly metrics: MetricsService, // Prometheus / CloudWatch / Datadog client
  ) {
    super(wrapped);
  }

  async fetchCreditReport(pan: string): Promise<CreditReport> {
    const timer = this.metrics.startTimer('bureau.fetch_report.duration');
    try {
      const result = await super.fetchCreditReport(pan);
      this.metrics.increment('bureau.fetch_report.success');
      return result;
    } catch (err) {
      this.metrics.increment('bureau.fetch_report.error', {
        error_type: (err as Error).constructor.name,
      });
      throw err;
    } finally {
      timer.end(); // always record latency, success or failure
    }
  }
}
```

The same `MetricsDecorator` pattern can be genericised and applied to *any* service interface — `PaymentGatewayAdapter`, `NachAdapter`, `SmsAdapter` — giving you consistent p95/p99 latency dashboards across all external integrations with zero business logic changes.

## Section 4: NestJS Interceptors as Decorator Pattern

**Q15. How do NestJS Interceptors implement the Decorator pattern?**
A: NestJS `Interceptor` is a first-class implementation of the Decorator pattern at the HTTP handler level. An interceptor wraps the execution of a route handler — it runs logic before calling `next.handle()` (which calls the actual handler) and can transform, delay, or replace the response:

```typescript
// Logging interceptor — Decorator around every HTTP handler
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  constructor(private readonly logger: Logger) {}

  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const request = context.switchToHttp().getRequest();
    const { method, url } = request;
    const start = Date.now();

    this.logger.log(`[${method}] ${url} — started`);

    return next.handle().pipe(
      tap(() => this.logger.log(`[${method}] ${url} — ${Date.now() - start}ms`)),
      catchError(err => {
        this.logger.error(`[${method}] ${url} — failed: ${err.message}`);
        return throwError(() => err);
      }),
    );
  }
}

// Timeout interceptor — wraps every handler with a 5s timeout
@Injectable()
export class TimeoutInterceptor implements NestInterceptor {
  intercept(_: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(timeout(5000));
  }
}

// Applied globally — decorates all handlers
app.useGlobalInterceptors(
  new LoggingInterceptor(logger),
  new TimeoutInterceptor(),
);

// Or per-controller / per-route
@UseInterceptors(LoggingInterceptor)
@Controller('loans')
export class LoanController { ... }
```

`next.handle()` is the "component" call — calling the wrapped handler. Everything before it is "before advice"; everything in `pipe()` after it is "after advice". This is the Decorator pattern expressed idiomatically in the NestJS/RxJS ecosystem.

**Q16. How does the NestJS Interceptor pattern compare to manually stacked Decorator objects?**
A:

| Aspect                        | Manual Decorator Stack                            | NestJS Interceptors                               |
|-------------------------------|---------------------------------------------------|---------------------------------------------------|
| Granularity                   | Any service interface — not just HTTP             | HTTP handler execution only                       |
| Composition                   | Code — assembled in `useFactory`                  | Declarative — `@UseInterceptors()` or global      |
| RxJS integration              | Not required                                      | Required — `Observable`-based                     |
| Order control                 | Explicit — outermost first in constructor chain   | Explicit — array order in `useGlobalInterceptors` |
| Testing                       | Mock the component interface                      | `createTestingModule` with mock `CallHandler`     |
| Best for                      | Service-level cross-cutting concerns              | HTTP-level cross-cutting concerns                 |

Use interceptors for HTTP-level concerns (request logging, response transformation, timeout). Use manual decorator stacks for service-level concerns (caching, retry, circuit breaker, metrics on a bureau client).

## Section 5: Testing Decorators

**Q17. How do you unit test a single Decorator in isolation?**
A: Mock the wrapped component with the same interface — test only the decorator's added behaviour:

```typescript
describe('CachingBureauDecorator', () => {
  let decorator: CachingBureauDecorator;
  let mockInner: jest.Mocked<BureauService>;
  let redis: jest.Mocked<Redis>;

  beforeEach(() => {
    mockInner = { fetchCreditReport: jest.fn() };
    redis = {
      get: jest.fn(),
      set: jest.fn(),
    } as any;
    decorator = new RedisCachingBureauDecorator(mockInner, redis);
  });

  it('should return cached report on cache hit', async () => {
    const cached: CreditReport = { pan: 'ABCDE1234F', score: 720, activeAccounts: 3, overdueAccounts: 0, enquiriesLast6Months: 1 };
    redis.get.mockResolvedValue(JSON.stringify(cached));

    const result = await decorator.fetchCreditReport('ABCDE1234F');

    expect(result).toEqual(cached);
    expect(mockInner.fetchCreditReport).not.toHaveBeenCalled(); // inner never called
    expect(redis.set).not.toHaveBeenCalled();                   // no write on hit
  });

  it('should call inner service and populate cache on cache miss', async () => {
    redis.get.mockResolvedValue(null); // cache miss
    const report: CreditReport = { pan: 'ABCDE1234F', score: 740, activeAccounts: 4, overdueAccounts: 0, enquiriesLast6Months: 2 };
    mockInner.fetchCreditReport.mockResolvedValue(report);

    const result = await decorator.fetchCreditReport('ABCDE1234F');

    expect(result).toEqual(report);
    expect(mockInner.fetchCreditReport).toHaveBeenCalledWith('ABCDE1234F');
    expect(redis.set).toHaveBeenCalledWith(
      expect.stringContaining('ABCDE1234F'),
      JSON.stringify(report),
      'EX',
      86400,
    );
  });
});
```

Each decorator is tested independently — `LoggingBureauDecorator` tests verify that log calls are made; `RetryBureauDecorator` tests verify that the inner service is called up to `maxAttempts` times on failure. No decorator's test knows or cares what the others do.

**Q18. How do you integration-test the full decorator stack?**
A: Wire up the real stack (or a test double at the innermost layer) and assert the combined behaviour:

```typescript
describe('Bureau Service Stack (integration)', () => {
  let stack: BureauService;
  let mockCibil: jest.Mocked<CibilBureauService>;
  let redis: ReturnType<typeof createClient>;

  beforeAll(async () => {
    redis = createTestRedisClient(); // Testcontainers or fakeredis
    mockCibil = { fetchCreditReport: jest.fn() };

    stack = new RateLimitingBureauDecorator(
      new RetryBureauDecorator(
        new RedisCachingBureauDecorator(mockCibil, redis),
        3,
      ),
      100,
      logger,
    );
  });

  it('should only call CIBIL once for the same PAN within the cache TTL', async () => {
    mockCibil.fetchCreditReport.mockResolvedValue(mockReport());

    await stack.fetchCreditReport('ABCDE1234F');
    await stack.fetchCreditReport('ABCDE1234F'); // should hit cache
    await stack.fetchCreditReport('ABCDE1234F'); // should hit cache

    expect(mockCibil.fetchCreditReport).toHaveBeenCalledTimes(1);
  });

  it('should retry failed calls up to 3 times before throwing', async () => {
    mockCibil.fetchCreditReport
      .mockRejectedValueOnce(new Error('timeout'))
      .mockRejectedValueOnce(new Error('timeout'))
      .mockResolvedValueOnce(mockReport()); // succeeds on 3rd attempt

    const result = await stack.fetchCreditReport('XYZAB5678G');
    expect(result).toBeDefined();
    expect(mockCibil.fetchCreditReport).toHaveBeenCalledTimes(3);
  });
});
```

## Section 6: Anti-patterns & Pitfalls

**Q19. What are the most common mistakes when implementing the Decorator pattern?**
A:

- **Decorator that adds to the interface** — if `LoggingBureauDecorator` adds a `getLogs()` method not on `BureauService`, it's no longer transparent. Clients who hold it as `BureauService` can't reach `getLogs()`, and those who hold it as `LoggingBureauDecorator` are now coupled to the concrete decorator. Decorators must implement *only* the component interface.
- **Forgetting to delegate all interface methods** — if `BureauService` has three methods and your decorator overrides only one, the other two need to be explicitly delegated to `this.wrapped`. The base decorator class pattern solves this: put pure delegation in the base, override only what you enrich.
- **Wrapping the wrong layer** — caching at the HTTP controller level (caching raw request/response) instead of at the service level (caching domain objects) means the cache stores and parses HTTP payloads, not clean domain models. Decorate at the right abstraction level.
- **State leak between decorator instances** — if a decorator holds mutable state (a rate-limiter counter, circuit-breaker failure count), that state is shared across all callers that use the same decorator instance. In a singleton-scoped NestJS provider this is correct. If the decorator is accidentally request-scoped, each request gets a fresh counter — the rate limiter stops working.
- **Too many decorator layers** — a chain of 8 decorators is hard to reason about and debug. If the stack grows beyond 4–5 layers, consider whether some concerns can be co-located (e.g., logging + metrics in one decorator) or whether an interceptor or middleware layer is a better home.
- **Not considering error propagation** — a decorator that catches an error and doesn't rethrow it (or rethrows a different type) silently swallows failures. Every decorator must decide: does it handle this error, transform it, or let it propagate?

**Q20. When should you NOT use the Decorator pattern?**
A:
- **When there's only one variation** — if you'll never need a second decorator, a simple subclass or direct modification is less indirection.
- **When the behaviour is always required** — if logging is mandatory for *every* invocation of a service, put it directly in the service rather than forcing every composition site to remember to stack a `LoggingDecorator`.
- **When you need access to multiple methods simultaneously** — Decorator works method-by-method. If the added behaviour needs to coordinate across multiple interface methods (e.g., a transaction that spans `begin()`, `execute()`, and `commit()` on the same component), a different pattern (Template Method, Unit of Work) fits better.
- **When AOP (Aspect-Oriented Programming) tools are available** — in some frameworks, cross-cutting concerns like logging and metrics are better handled by AOP annotations or interceptors, which apply globally without requiring manual stack assembly per service.

## Section 7: Scenario / System Design Questions

**Q21. "Your team wants every external API call (bureau, NACH, payment gateway) in the lending platform to have consistent logging, retry, and metrics. How do you implement this without repeating the logic in every service?"**
A: Build a generic decorator factory that applies a standard cross-cutting stack to any service interface:

```typescript
// Generic decorator stack factory
function withStandardResilience<T extends object>(
  service: T,
  serviceName: string,
  deps: { logger: Logger; redis: Redis; metrics: MetricsService },
): T {
  // We can't use class-based decorators generically across arbitrary interfaces,
  // so use a Proxy to intercept all method calls
  return new Proxy(service, {
    get(target, prop: string) {
      const original = (target as any)[prop];
      if (typeof original !== 'function') return original;

      return async (...args: unknown[]) => {
        const key = `${serviceName}.${prop}`;
        const timer = deps.metrics.startTimer(`${key}.duration`);
        deps.logger.log(`[${key}] called`);

        let lastErr: Error;
        for (let attempt = 1; attempt <= 3; attempt++) {
          try {
            const result = await original.apply(target, args);
            deps.metrics.increment(`${key}.success`);
            deps.logger.log(`[${key}] success`);
            return result;
          } catch (err) {
            lastErr = err as Error;
            deps.metrics.increment(`${key}.error`);
            if (attempt < 3) await delay(200 * 2 ** (attempt - 1));
          } finally {
            if (attempt === 3 || /* success */) timer.end();
          }
        }
        throw lastErr!;
      };
    },
  });
}

// Applied once per service in NestJS module
{
  provide: 'BUREAU_SERVICE',
  useFactory: (cibil, logger, redis, metrics) =>
    withStandardResilience(cibil, 'bureau', { logger, redis, metrics }),
  inject: [CibilBureauService, Logger, Redis, MetricsService],
}
```

For a production system, prefer explicit typed decorator classes (better TypeScript inference, easier to test) over `Proxy`-based generic decorators. But the `Proxy` approach works well as a quick cross-cutting standard before individual decorators are written.

**Q22. "A junior developer asks why you don't just add a `try/catch` with retry logic directly inside `CibilBureauService.fetchCreditReport()` instead of creating a whole decorator class. How do you respond?"**
A: Several reasons:

- **Single Responsibility** — `CibilBureauService` is responsible for calling the CIBIL API and translating the response. Retry strategy is a separate, independently configurable concern. What if the NACH adapter also needs retry, but with different `maxAttempts` and backoff? Embedding retry in every service means duplicating and diverging the logic.
- **Open/Closed** — hardcoding retry in `CibilBureauService` means changing the retry policy (say, switching from exponential to fixed backoff, or adding jitter) requires modifying a tested, working class. The decorator approach changes only the decorator.
- **Testability** — to test the retry logic embedded in `CibilBureauService`, every test that mocks the HTTP client has to be aware of retry behaviour. To test retry in isolation, you'd need to deliberately trigger failures in a class that mixes retry with translation logic. With a decorator, `RetryDecorator` has its own test, `CibilBureauService` has its own test — clean separation.
- **Composability** — what if in staging you want retry but in dev you don't (to see failures immediately)? With embedded retry you'd need a flag inside the class. With decorators, you just don't stack `RetryDecorator` in the dev composition.
- **Reuse** — `RetryBureauDecorator` is generic enough to wrap *any* `BureauService` — including `ExperianBureauAdapter` and `KarzaBureauAdapter`. Embedding retry in `CibilBureauService` means writing it three times.

## Quick Reference: Decorator Pattern Checklist

| Signal                                                                 | What to Do                                                              |
|------------------------------------------------------------------------|-------------------------------------------------------------------------|
| Same cross-cutting concern (logging, retry, cache) needed across multiple services | Extract a Decorator for that concern — apply per service via composition |
| Subclass count growing for every combination of features               | Replace inheritance hierarchy with composable decorators                |
| Adding behaviour to a class you can't modify (third-party, sealed)     | Wrap it in a decorator implementing the same interface                  |
| Decorator adds methods not on the component interface                  | It's no longer a Decorator — remove or move those methods               |
| Decorator holds mutable state in a singleton-scoped NestJS provider    | Correct — state is intentionally shared; verify scope is singleton      |
| HTTP-level cross-cutting concerns (timeout, request logging)           | Use NestJS Interceptors — they're Decorators for HTTP handlers          |
| Service-level cross-cutting concerns (cache, retry, circuit breaker)   | Use explicit Decorator classes assembled in NestJS `useFactory`         |
| Can't remember which decorator order to use                            | Outermost = runs first and last; gate-keepers (auth, rate-limit) go outermost |

---

**Tip for the interview:** At the 5 YOE level, Decorator surfaces in two forms — the design pattern question and the "how do you add cross-cutting concerns" question, which is the same question in disguise. When asked how you handle retry, logging, or caching across bureau/payment integrations, describe the decorator stack — even if you called it "a wrapper service" in production. The differentiators at the senior level: knowing that *order matters* and being able to reason about why (rate limiter before retry before cache before the real call), explaining why you'd use NestJS Interceptors for HTTP-level concerns versus explicit decorator classes for service-level concerns, and connecting the pattern to SRP and OCP — each decorator has one reason to change, and adding a new concern means adding a new decorator, not modifying any existing class.
