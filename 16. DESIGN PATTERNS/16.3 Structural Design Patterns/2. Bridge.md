# Design Patterns (Structural): Bridge — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Bridge pattern?**
A: Bridge is a structural design pattern that decouples an abstraction from its implementation so that the two can vary independently. Instead of building a single class hierarchy that combines both dimensions of variation (e.g., shape × rendering platform), Bridge splits them into two separate hierarchies connected by a composition relationship — the abstraction holds a reference to an implementor and delegates the platform-specific work to it. The "bridge" is that reference: a stable interface through which the two hierarchies talk.

**Q2. What specific problem does Bridge solve? What breaks without it?**
A: Bridge solves the **Cartesian product explosion** problem in class hierarchies. Suppose you have two orthogonal dimensions of variation — say, `PaymentMethod` (UPI, Card, NetBanking) and `PaymentGateway` (Razorpay, Juspay, Cashfree). A naive single-hierarchy approach produces a class per combination: `RazorpayUpi`, `RazorpayCard`, `JuspayUpi`, `JuspayCard`, … — 3 × 3 = 9 classes today, 4 × 4 = 16 after the next round of additions. Every new method or gateway multiplies the existing count. Bridge replaces that M × N class explosion with M + N classes — one hierarchy per dimension — connected by composition. Without Bridge, each new variation forces changes across the entire cross-product; with Bridge, adding a new dimension entry (a new gateway) means adding one class, period.

**Q3. What are the four participants in the Bridge pattern?**
A: The GoF define four:
1. **Abstraction** — defines the abstraction's interface; holds a reference to the `Implementor`. May delegate all work to the implementor, or combine implementor calls with its own logic.
2. **RefinedAbstraction** — extends `Abstraction`; adds higher-level operations or varies the abstraction dimension. Clients typically use this.
3. **Implementor** — defines the interface for implementation classes. This interface doesn't need to match `Abstraction`'s interface exactly — it's typically more primitive/lower-level, and `Abstraction` builds higher-level operations out of it.
4. **ConcreteImplementor** — provides a concrete implementation of the `Implementor` interface.

**Q4. What is the core structural difference between Bridge and Adapter?**
A: Both involve a layer of indirection, but their intent and timing differ fundamentally:

| Dimension       | Bridge                                                        | Adapter                                                     |
|-----------------|---------------------------------------------------------------|-------------------------------------------------------------|
| Intent          | Decouple two dimensions so they can vary independently        | Make an existing incompatible interface work with a client  |
| Design timing   | Upfront — designed before the classes are built               | Retrofit — applied after a mismatch is discovered           |
| Relationship    | Abstraction *owns* the implementor (composition)              | Adapter *wraps* the adaptee (delegation or inheritance)     |
| Both sides      | Both hierarchies are designed together                        | Only one side (the adaptee) is foreign / pre-existing       |
| Cardinality     | Many abstractions × many implementors                         | Usually one adaptee being adapted for one target interface  |

Adapter is a rescue pattern; Bridge is a forward-looking architecture decision.

**Q5. How does Bridge relate to the SOLID principles?**
A: Bridge is a structural application of several:
- **OCP** — adding a new abstraction variant or a new implementor requires adding a new class, not modifying existing ones.
- **SRP** — the abstraction hierarchy handles high-level logic; the implementor hierarchy handles platform/provider specifics. Each class has one reason to change.
- **DIP** — the `Abstraction` depends on the `Implementor` interface (an abstraction), not on any `ConcreteImplementor`. High-level policy references a low-level abstraction, never a low-level detail.
- **Composition over inheritance** (not SOLID per se, but a core OOP principle) — Bridge replaces an explosive inheritance tree with explicit composition, making dependencies visible and swappable.

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript implementation of the Bridge pattern.**
A:

```typescript
// ─── Implementor ─────────────────────────────────────────────────────────────

interface Renderer {
  renderCircle(x: number, y: number, radius: number): void;
  renderRectangle(x: number, y: number, w: number, h: number): void;
}

// ─── Concrete Implementors ───────────────────────────────────────────────────

class SvgRenderer implements Renderer {
  renderCircle(x: number, y: number, radius: number): void {
    console.log(`<circle cx="${x}" cy="${y}" r="${radius}"/>`);
  }
  renderRectangle(x: number, y: number, w: number, h: number): void {
    console.log(`<rect x="${x}" y="${y}" width="${w}" height="${h}"/>`);
  }
}

class CanvasRenderer implements Renderer {
  renderCircle(x: number, y: number, radius: number): void {
    console.log(`ctx.arc(${x}, ${y}, ${radius}, 0, 2 * Math.PI)`);
  }
  renderRectangle(x: number, y: number, w: number, h: number): void {
    console.log(`ctx.fillRect(${x}, ${y}, ${w}, ${h})`);
  }
}

// ─── Abstraction ─────────────────────────────────────────────────────────────

abstract class Shape {
  constructor(protected renderer: Renderer) {}   // the bridge
  abstract draw(): void;
  abstract resize(factor: number): void;
}

// ─── Refined Abstractions ────────────────────────────────────────────────────

class Circle extends Shape {
  constructor(
    renderer: Renderer,
    private x: number,
    private y: number,
    private radius: number
  ) {
    super(renderer);
  }

  draw(): void {
    this.renderer.renderCircle(this.x, this.y, this.radius);
  }

  resize(factor: number): void {
    this.radius *= factor;
  }
}

class Rectangle extends Shape {
  constructor(
    renderer: Renderer,
    private x: number,
    private y: number,
    private width: number,
    private height: number
  ) {
    super(renderer);
  }

  draw(): void {
    this.renderer.renderRectangle(this.x, this.y, this.width, this.height);
  }

  resize(factor: number): void {
    this.width  *= factor;
    this.height *= factor;
  }
}

// ─── Client ──────────────────────────────────────────────────────────────────

const svg    = new SvgRenderer();
const canvas = new CanvasRenderer();

const circle    = new Circle(svg, 50, 50, 25);
const rectangle = new Rectangle(canvas, 10, 10, 100, 60);

circle.draw();     // <circle cx="50" cy="50" r="25"/>
rectangle.draw();  // ctx.fillRect(10, 10, 100, 60)

// Swap renderer at runtime — no class changes needed
const circleOnCanvas = new Circle(canvas, 50, 50, 25);
circleOnCanvas.draw(); // ctx.arc(50, 50, 25, 0, 2 * Math.PI)
```

Two dimensions — shapes and renderers — each with their own hierarchy. Adding a `Triangle` shape means one new class; adding a `WebGLRenderer` means one new class. Neither addition touches the other dimension.

**Q7. Can the implementor be swapped at runtime, and when is that useful?**
A: Yes — because the abstraction holds the implementor via a reference (composition), it can be replaced at any point during the object's lifetime:

```typescript
class Shape {
  constructor(protected renderer: Renderer) {}

  setRenderer(renderer: Renderer): void {
    this.renderer = renderer;   // runtime swap
  }
}

const circle = new Circle(svgRenderer, 50, 50, 25);
circle.draw();                         // SVG output

circle.setRenderer(canvasRenderer);
circle.draw();                         // Canvas output — same circle object
```

This is useful in scenarios like:
- A document editor that switches rendering backends (print vs. screen vs. export).
- A payment flow that falls back to a secondary gateway when the primary is unavailable.
- A feature-flagged A/B test where the implementor switches based on a runtime flag evaluated after construction.

**Q8. How does the Implementor interface differ from the Abstraction interface — do they need to mirror each other?**
A: No — and this is a key subtlety. The `Implementor` interface is typically *more primitive* than the `Abstraction`'s interface. The abstraction builds higher-level, business-meaningful operations by composing one or more implementor calls:

```typescript
// Implementor — low-level, platform-specific primitives
interface NotificationTransport {
  openConnection(endpoint: string): Promise<void>;
  sendRaw(payload: string): Promise<void>;
  closeConnection(): Promise<void>;
}

// Abstraction — high-level, business-facing operations
abstract class NotificationService {
  constructor(protected transport: NotificationTransport) {}

  // One business operation = multiple implementor calls
  async notify(recipient: string, message: string): Promise<void> {
    await this.transport.openConnection(recipient);
    await this.transport.sendRaw(JSON.stringify({ message }));
    await this.transport.closeConnection();
  }
}
```

The abstraction is what the *client* calls. The implementor is what the *abstraction* calls. Keeping them separate allows each to evolve without coupling: the business operation `notify()` can gain retry logic or logging without touching the transport; the transport can gain connection pooling without touching the notification semantics.

**Q9. What is a "degenerate Bridge" and when does it appear?**
A: A degenerate Bridge has only one `RefinedAbstraction` and one `ConcreteImplementor` — it looks like unnecessary indirection. This appears when the pattern is applied prematurely, before the second dimension of variation has actually emerged. The risk: if you build the Bridge before you know you need multiple variants on both sides, you add complexity without benefit. The right approach: start with a plain class; introduce the Bridge when you see — or can confidently predict — that *both* dimensions will have multiple variants. A single-axis variation is better served by a simple strategy or factory.

**Q10. How do you decide what belongs in the Abstraction hierarchy versus the Implementor hierarchy?**
A: Ask what the *two independent reasons to change* are:
- The **Abstraction hierarchy** captures variation in *what* the client wants to do — business domain concepts, use cases, high-level behaviour. Things that change when product requirements change.
- The **Implementor hierarchy** captures variation in *how* the work is done at a lower level — platform, technology, provider, protocol. Things that change when infrastructure or integration choices change.

A reliable heuristic: if a proposed subclass changes both *what* and *how*, you're mixing the two dimensions in one hierarchy — that's the signal to introduce Bridge and pull *how* into a separate implementor.

## Section 3: Bridge vs. Related Patterns

**Q11. How does Bridge differ from Strategy?**
A: They look structurally identical — both use composition to delegate behaviour to an injected object. The distinction is in intent and scope:

| Dimension          | Strategy                                                    | Bridge                                                              |
|--------------------|-------------------------------------------------------------|---------------------------------------------------------------------|
| Intent             | Make an algorithm interchangeable within one context object | Decouple two full class hierarchies so both can vary independently  |
| Scope              | One class with a swappable algorithm                        | Two parallel hierarchies (abstraction × implementor)                |
| Variation axes     | One (the algorithm)                                         | Two (abstraction + implementation)                                  |
| Inheritance used?  | Rarely — usually a single context class                     | Yes — both sides can have inheritance hierarchies                   |
| Typical trigger    | Multiple algorithms for one behaviour                       | Cartesian product explosion in a class hierarchy                    |

In practice: if you have one class that needs to swap a behaviour, use Strategy. If you have a hierarchy of classes that all need to swap a behaviour, and that behaviour itself forms its own hierarchy, use Bridge.

**Q12. How does Bridge differ from Decorator?**
A: Both wrap an object, but their purposes are different:
- **Decorator** adds responsibilities *transparently* — the wrapper and the wrapped object share the same interface, and decorators can be stacked arbitrarily at runtime. The client doesn't know or care about the decoration.
- **Bridge** connects two *different* interfaces — the abstraction's interface (client-facing) is distinct from the implementor's interface (internal). There's no stacking; the bridge is typically a single reference, not a chain.

You'd use Decorator to add logging, caching, or retry around a single object. You'd use Bridge to connect a domain concept (payment flow) to a platform (gateway SDK) where both have their own evolution trajectories.

**Q13. When should you combine Bridge with Abstract Factory?**
A: Abstract Factory is the natural companion to Bridge for selecting and injecting the implementor. When the implementor has multiple concrete variants that need to be chosen at the composition root, an Abstract Factory ensures the right implementor is created consistently:

```typescript
interface PaymentInfraFactory {
  createGatewayClient(): GatewayClient;          // Implementor product
  createWebhookValidator(): WebhookValidator;    // Another implementor product
}

// PaymentFlow (Abstraction) is injected with the factory
class PaymentFlow {
  private client: GatewayClient;
  private validator: WebhookValidator;

  constructor(factory: PaymentInfraFactory) {
    this.client    = factory.createGatewayClient();     // bridge to implementor
    this.validator = factory.createWebhookValidator();
  }
}
```

Abstract Factory handles *which* implementor family; Bridge handles *how* the abstraction uses it.

## Section 4: Bridge in Node.js / TypeScript / Fintech Context

**Q14. Show a real-world Bridge implementation for a payment processing system with multiple methods and gateways.**
A: Payment method (UPI, Card, NetBanking) is the abstraction dimension; payment gateway (Razorpay, Juspay) is the implementor dimension:

```typescript
// ─── Implementor — Gateway SDK interface ─────────────────────────────────────

interface PaymentGatewayDriver {
  initiateTransaction(
    payload: GatewayPayload
  ): Promise<{ transactionId: string; redirectUrl?: string }>;

  verifyTransaction(
    transactionId: string
  ): Promise<{ status: "success" | "failure" | "pending"; amountInPaise: number }>;

  initiateRefund(
    transactionId: string,
    amountInPaise: number
  ): Promise<{ refundId: string }>;
}

// ─── Concrete Implementors ───────────────────────────────────────────────────

class RazorpayDriver implements PaymentGatewayDriver {
  async initiateTransaction(payload: GatewayPayload) {
    const order = await razorpaySDK.orders.create({
      amount:   payload.amountInPaise,
      currency: payload.currency,
      receipt:  payload.orderId,
    });
    return { transactionId: order.id };
  }

  async verifyTransaction(transactionId: string) {
    const payment = await razorpaySDK.payments.fetch(transactionId);
    return {
      status:        payment.status === "captured" ? "success" : "failure",
      amountInPaise: payment.amount,
    } as const;
  }

  async initiateRefund(transactionId: string, amountInPaise: number) {
    const refund = await razorpaySDK.payments.refund(transactionId, { amount: amountInPaise });
    return { refundId: refund.id };
  }
}

class JuspayDriver implements PaymentGatewayDriver {
  async initiateTransaction(payload: GatewayPayload) {
    const session = await juspaySDK.sessions.create({
      order_id:     payload.orderId,
      amount:       (payload.amountInPaise / 100).toFixed(2),
      customer_id:  payload.customerId,
    });
    return { transactionId: session.order_id, redirectUrl: session.payment_links.web };
  }

  async verifyTransaction(transactionId: string) {
    const order = await juspaySDK.orders.status(transactionId);
    return {
      status:        order.status === "CHARGED" ? "success" : order.status === "PENDING_VBV" ? "pending" : "failure",
      amountInPaise: Math.round(parseFloat(order.amount) * 100),
    } as const;
  }

  async initiateRefund(transactionId: string, amountInPaise: number) {
    const refund = await juspaySDK.refunds.create({
      order_id:        transactionId,
      amount:          (amountInPaise / 100).toFixed(2),
      unique_request_id: `refund_${Date.now()}`,
    });
    return { refundId: refund.id };
  }
}

// ─── Abstraction — Payment Method ────────────────────────────────────────────

abstract class PaymentMethod {
  constructor(protected driver: PaymentGatewayDriver) {}

  // Template: subclasses specialise buildPayload(); orchestration lives here
  async pay(order: Order): Promise<PaymentResult> {
    const payload  = this.buildPayload(order);
    const txn      = await this.driver.initiateTransaction(payload);
    return { transactionId: txn.transactionId, redirectUrl: txn.redirectUrl };
  }

  async verify(transactionId: string): Promise<VerifyResult> {
    return this.driver.verifyTransaction(transactionId);
  }

  async refund(transactionId: string, amountInPaise: number): Promise<RefundResult> {
    return this.driver.initiateRefund(transactionId, amountInPaise);
  }

  protected abstract buildPayload(order: Order): GatewayPayload;
}

// ─── Refined Abstractions — Payment Method variants ──────────────────────────

class UpiPayment extends PaymentMethod {
  constructor(driver: PaymentGatewayDriver, private vpa: string) {
    super(driver);
  }

  protected buildPayload(order: Order): GatewayPayload {
    return {
      orderId:      order.id,
      amountInPaise: order.amountInPaise,
      currency:     "INR",
      customerId:   order.customerId,
      method:       "upi",
      vpa:          this.vpa,
    };
  }
}

class CardPayment extends PaymentMethod {
  constructor(driver: PaymentGatewayDriver, private cardToken: string) {
    super(driver);
  }

  protected buildPayload(order: Order): GatewayPayload {
    return {
      orderId:       order.id,
      amountInPaise: order.amountInPaise,
      currency:      "INR",
      customerId:    order.customerId,
      method:        "card",
      cardToken:     this.cardToken,
    };
  }

  // Card-specific extra: 3DS verification step
  async initiateThreeDSecure(transactionId: string): Promise<string> {
    // Card-specific logic not part of the base abstraction
    return `https://3ds.example.com/verify/${transactionId}`;
  }
}

class NetBankingPayment extends PaymentMethod {
  constructor(driver: PaymentGatewayDriver, private bankCode: string) {
    super(driver);
  }

  protected buildPayload(order: Order): GatewayPayload {
    return {
      orderId:       order.id,
      amountInPaise: order.amountInPaise,
      currency:      "INR",
      customerId:    order.customerId,
      method:        "netbanking",
      bankCode:      this.bankCode,
    };
  }
}

// ─── Client — PaymentOrchestrationService ────────────────────────────────────

class PaymentOrchestrationService {
  async processPayment(method: PaymentMethod, order: Order): Promise<PaymentResult> {
    // Works with any combination of method × driver — 0 conditional logic
    return method.pay(order);
  }
}

// ─── Composition root ─────────────────────────────────────────────────────────

const razorpay = new RazorpayDriver();
const juspay   = new JuspayDriver();

// Mix and match freely — 3 methods × 2 drivers, no extra classes
const upiOnRazorpay      = new UpiPayment(razorpay, "user@upi");
const cardOnJuspay       = new CardPayment(juspay, "tok_abc123");
const netbankingOnJuspay = new NetBankingPayment(juspay, "HDFC");
```

3 payment methods + 2 gateway drivers = 5 classes total, not 6. Adding Cashfree means one new `CashfreeDriver` class, zero changes to `UpiPayment`, `CardPayment`, or `NetBankingPayment`.

**Q15. How does Bridge enable a live gateway-fallback mechanism in a high-availability payment system?**
A: Because the implementor is held by reference, it can be swapped at runtime — making fallback a one-liner without any change to the payment method logic:

```typescript
class FallbackGatewayDriver implements PaymentGatewayDriver {
  private current: PaymentGatewayDriver;
  private fallback: PaymentGatewayDriver;
  private readonly failureThreshold = 3;
  private consecutiveFailures       = 0;

  constructor(primary: PaymentGatewayDriver, fallback: PaymentGatewayDriver) {
    this.current  = primary;
    this.fallback = fallback;
  }

  async initiateTransaction(payload: GatewayPayload) {
    try {
      const result = await this.current.initiateTransaction(payload);
      this.consecutiveFailures = 0;          // reset on success
      return result;
    } catch (err) {
      this.consecutiveFailures++;
      if (this.consecutiveFailures >= this.failureThreshold) {
        console.warn("Primary gateway unhealthy — switching to fallback");
        [this.current, this.fallback] = [this.fallback, this.current]; // swap
        this.consecutiveFailures = 0;
      }
      return this.current.initiateTransaction(payload);   // retry on fallback
    }
  }

  async verifyTransaction(transactionId: string) {
    return this.current.verifyTransaction(transactionId);
  }

  async initiateRefund(transactionId: string, amountInPaise: number) {
    return this.current.initiateRefund(transactionId, amountInPaise);
  }
}

// Usage — PaymentMethod is completely unaware of the fallback logic
const resilientDriver = new FallbackGatewayDriver(new RazorpayDriver(), new JuspayDriver());
const upi             = new UpiPayment(resilientDriver, "user@upi");
```

The `FallbackGatewayDriver` is itself a `ConcreteImplementor` — it wraps two drivers and presents the same `PaymentGatewayDriver` interface. The abstraction (`UpiPayment`) never changes.

**Q16. Show how Bridge structures a multi-channel notification system in a NestJS fintech backend.**
A: Notification type (TransactionAlert, KycReminder, MarketingOffer) is the abstraction; delivery channel (Email, SMS, WhatsApp, Push) is the implementor:

```typescript
// ─── Implementor ─────────────────────────────────────────────────────────────

interface NotificationChannel {
  deliver(recipient: string, content: ChannelContent): Promise<DeliveryReceipt>;
}

interface ChannelContent {
  subject?: string;      // email only
  body: string;
  templateId?: string;   // WhatsApp / push
  variables?: Record<string, string>;
}

// ─── Concrete Implementors ───────────────────────────────────────────────────

@Injectable()
class SendGridChannel implements NotificationChannel {
  constructor(private readonly sendgrid: SendGridService) {}

  async deliver(recipient: string, content: ChannelContent): Promise<DeliveryReceipt> {
    const result = await this.sendgrid.send({
      to:      recipient,
      subject: content.subject ?? "Notification",
      text:    content.body,
    });
    return { channelMessageId: result[0].headers["x-message-id"] };
  }
}

@Injectable()
class MSG91Channel implements NotificationChannel {
  constructor(private readonly msg91: MSG91Service) {}

  async deliver(recipient: string, content: ChannelContent): Promise<DeliveryReceipt> {
    const result = await this.msg91.sendSms({
      to:      recipient,
      message: content.body,
    });
    return { channelMessageId: result.request_id };
  }
}

@Injectable()
class InteraktWhatsAppChannel implements NotificationChannel {
  constructor(private readonly interakt: InteraktService) {}

  async deliver(recipient: string, content: ChannelContent): Promise<DeliveryReceipt> {
    const result = await this.interakt.sendTemplate({
      to:         recipient,
      templateId: content.templateId!,
      variables:  content.variables ?? {},
    });
    return { channelMessageId: result.message_id };
  }
}

// ─── Abstraction ─────────────────────────────────────────────────────────────

abstract class NotificationMessage {
  constructor(protected channel: NotificationChannel) {}

  async send(recipientId: string, data: NotificationData): Promise<DeliveryReceipt> {
    const content = this.buildContent(data);
    return this.channel.deliver(recipientId, content);
  }

  protected abstract buildContent(data: NotificationData): ChannelContent;
}

// ─── Refined Abstractions ────────────────────────────────────────────────────

class TransactionAlertNotification extends NotificationMessage {
  protected buildContent(data: NotificationData): ChannelContent {
    return {
      subject:    `Transaction ${data.status}: ₹${data.amountInPaise / 100}`,
      body:       `Your transaction of ₹${data.amountInPaise / 100} was ${data.status}.`,
      templateId: "txn_alert_v2",
      variables:  { amount: String(data.amountInPaise / 100), status: data.status },
    };
  }
}

class KycReminderNotification extends NotificationMessage {
  protected buildContent(data: NotificationData): ChannelContent {
    return {
      subject:    "Complete your KYC to continue transacting",
      body:       `Hi ${data.userName}, your KYC expires in ${data.daysRemaining} days.`,
      templateId: "kyc_reminder_v1",
      variables:  { name: data.userName, days: String(data.daysRemaining) },
    };
  }
}

class MarketingOfferNotification extends NotificationMessage {
  protected buildContent(data: NotificationData): ChannelContent {
    return {
      subject:    data.offerTitle,
      body:       data.offerBody,
      templateId: "offer_v3",
      variables:  { title: data.offerTitle, cta: data.ctaUrl },
    };
  }
}

// ─── NestJS module wiring ─────────────────────────────────────────────────────

@Module({
  providers: [
    SendGridChannel,
    MSG91Channel,
    InteraktWhatsAppChannel,
    {
      provide:  "TXN_ALERT_EMAIL",
      useFactory: (sg: SendGridChannel) => new TransactionAlertNotification(sg),
      inject:   [SendGridChannel],
    },
    {
      provide:  "TXN_ALERT_WHATSAPP",
      useFactory: (ia: InteraktWhatsAppChannel) => new TransactionAlertNotification(ia),
      inject:   [InteraktWhatsAppChannel],
    },
    {
      provide:  "KYC_REMINDER_SMS",
      useFactory: (m: MSG91Channel) => new KycReminderNotification(m),
      inject:   [MSG91Channel],
    },
  ],
})
export class NotificationModule {}
```

3 message types × 3 channels = 6 provider tokens in the DI container, backed by only 6 total classes (3 + 3). Adding a Push channel means one new `FirebasePushChannel` class — all three notification types can reuse it instantly.

**Q17. How does Bridge improve testability compared to a flat inheritance hierarchy?**
A: In a flat hierarchy (`RazorpayUpiPayment extends UpiPayment`), testing `UpiPayment` logic requires either a live Razorpay connection or monkey-patching the SDK. With Bridge, the `PaymentGatewayDriver` is an injected interface — replace it with a mock in one line:

```typescript
class MockGatewayDriver implements PaymentGatewayDriver {
  async initiateTransaction(payload: GatewayPayload) {
    return { transactionId: `mock_txn_${payload.orderId}` };
  }
  async verifyTransaction(transactionId: string) {
    return { status: "success" as const, amountInPaise: 50000 };
  }
  async initiateRefund(transactionId: string, amountInPaise: number) {
    return { refundId: `mock_refund_${transactionId}` };
  }
}

describe("UpiPayment", () => {
  const driver = new MockGatewayDriver();
  const upi    = new UpiPayment(driver, "test@upi");
  const order  = { id: "ord_001", amountInPaise: 50000, customerId: "cust_1" };

  it("should build UPI payload and return a transaction ID", async () => {
    const result = await upi.pay(order);
    expect(result.transactionId).toBe("mock_txn_ord_001");
  });
});
```

Two test axes become independently verifiable: test `UpiPayment` (abstraction) logic with a mock driver; test `RazorpayDriver` (implementor) behaviour with a mock HTTP layer. No full-stack setup required for either.

**Q18. How does Bridge apply to a loan origination system with multiple credit bureau integrations (CIBIL, Experian, CRIF)?**
A: Loan product type is the abstraction (PersonalLoan, HomeLoan, BNPL); credit bureau is the implementor:

```typescript
interface CreditBureauDriver {
  pullReport(pan: string, consent: ConsentToken): Promise<CreditReport>;
  submitEnquiry(pan: string, enquiry: BureauEnquiry): Promise<EnquiryId>;
}

class CibilDriver implements CreditBureauDriver {
  async pullReport(pan: string, consent: ConsentToken): Promise<CreditReport> {
    const raw = await cibilSDK.getReport({ panNumber: pan, consentId: consent.id });
    return normaliseCibilReport(raw);           // normalise to common CreditReport shape
  }
  async submitEnquiry(pan: string, enquiry: BureauEnquiry): Promise<EnquiryId> {
    return cibilSDK.submitEnquiry({ pan, ...enquiry });
  }
}

class ExperianDriver implements CreditBureauDriver {
  async pullReport(pan: string, consent: ConsentToken): Promise<CreditReport> {
    const raw = await experianSDK.fetchConsumerReport({ pan_card: pan, token: consent.token });
    return normaliseExperianReport(raw);
  }
  async submitEnquiry(pan: string, enquiry: BureauEnquiry): Promise<EnquiryId> {
    return experianSDK.createEnquiry({ pan_card: pan, product: enquiry.productType });
  }
}

abstract class LoanApplication {
  constructor(protected bureau: CreditBureauDriver) {}

  async evaluate(applicant: Applicant): Promise<CreditDecision> {
    const report = await this.bureau.pullReport(applicant.pan, applicant.bureauConsent);
    return this.applyUnderwritingRules(report, applicant);
  }

  protected abstract applyUnderwritingRules(
    report: CreditReport,
    applicant: Applicant
  ): CreditDecision;
}

class PersonalLoanApplication extends LoanApplication {
  protected applyUnderwritingRules(report: CreditReport, applicant: Applicant): CreditDecision {
    // Personal loan: CIBIL score > 720, low utilisation
    if (report.score < 720) return { approved: false, reason: "Low credit score" };
    if (report.creditUtilisation > 0.4) return { approved: false, reason: "High utilisation" };
    return { approved: true, sanctionedAmountInPaise: applicant.requestedAmountInPaise };
  }
}

class BnplApplication extends LoanApplication {
  protected applyUnderwritingRules(report: CreditReport, applicant: Applicant): CreditDecision {
    // BNPL: lighter check — any score above 650, short tenure
    if (report.score < 650) return { approved: false, reason: "Insufficient credit history" };
    return { approved: true, sanctionedAmountInPaise: Math.min(applicant.requestedAmountInPaise, 1500000) };
  }
}

// Composition: BNPL on CIBIL, PersonalLoan on Experian — mix freely
const bnplViaExperian        = new BnplApplication(new ExperianDriver());
const personalLoanViaCibil   = new PersonalLoanApplication(new CibilDriver());
```

## Section 5: Pitfalls & Anti-patterns

**Q19. What is the most common mistake engineers make when applying Bridge?**
A: Confusing Bridge with Strategy and applying it where only one axis varies. If you have `UpiPayment` with swappable retry strategies, that's Strategy — one class, one varying algorithm. You don't need a full Bridge hierarchy. The cost of Bridge (two parallel hierarchies, a composition reference, factory wiring) is justified only when *both* dimensions independently have multiple variants and will continue to grow. Applying Bridge for a single axis adds boilerplate without the M + N benefit.

**Q20. How can Bridge create hidden coupling if implemented carelessly?**
A: The coupling risk emerges when the `Abstraction` leaks knowledge of specific `ConcreteImplementors` in its logic:

```typescript
// ❌ Abstraction peeking at implementor type — Bridge coupling violation
class CardPayment extends PaymentMethod {
  async pay(order: Order): Promise<PaymentResult> {
    if (this.driver instanceof RazorpayDriver) {
      // Razorpay-specific pre-auth step
      await (this.driver as RazorpayDriver).preAuthCapture(order.id);
    }
    return super.pay(order);
  }
}
```

This `instanceof` check means `CardPayment` now has a hidden dependency on `RazorpayDriver` — the Bridge is broken. The fix: push the `preAuthCapture` behaviour into the `PaymentGatewayDriver` interface (or a specialised sub-interface), or use a strategy/decorator on the driver side to handle it transparently.

**Q21. What happens to Bridge when the Implementor interface grows too large?**
A: An oversized implementor interface forces every `ConcreteImplementor` to implement methods it may not naturally support, leading to:
- Hollow stub implementations (`return null`, `throw NotImplementedError`) that violate LSP.
- Concrete implementors that implement 80% of the interface meaningfully and 20% as no-ops.

Fix: apply ISP to the implementor side — split into focused sub-interfaces (`BasicGatewayDriver`, `RefundCapableDriver`, `RecurringPaymentDriver`), and compose only what's needed. Abstractions that need refund capability accept `RefundCapableDriver`; those that don't accept only `BasicGatewayDriver`.

```typescript
interface BasicGatewayDriver {
  initiateTransaction(payload: GatewayPayload): Promise<TransactionResult>;
  verifyTransaction(transactionId: string): Promise<VerifyResult>;
}

interface RefundCapableDriver extends BasicGatewayDriver {
  initiateRefund(transactionId: string, amountInPaise: number): Promise<RefundResult>;
}

interface RecurringPaymentDriver extends BasicGatewayDriver {
  createMandate(mandatePayload: MandatePayload): Promise<MandateResult>;
  debitMandate(mandateId: string, amountInPaise: number): Promise<TransactionResult>;
}

// CashfreeDriver only supports basic + refunds
class CashfreeDriver implements RefundCapableDriver { /* ... */ }

// RazorpayDriver supports everything
class RazorpayDriver implements RefundCapableDriver, RecurringPaymentDriver { /* ... */ }
```

**Q22. How does Bridge behave under serialization, and what problems can arise?**
A: If the abstraction is serialized (e.g., stored in Redis, sent as JSON over a queue), the implementor reference doesn't travel with it — an `UpiPayment` serialized to JSON loses its `driver`. When deserialized, the object is structurally present but behaviourally broken (the driver reference is `undefined`). Solutions:
- **Don't serialize the abstraction** — serialize only data (the `Order`, the `PaymentMethod` type name), and reconstruct the full Bridge object at the handling side using a factory.
- **Reconstruct at deserialization** — store a `driverKey` (e.g., `"razorpay"`) alongside the data; a factory rebuilds the `ConcreteImplementor` from the key on the receiving end.
- **Keep Bridge objects in-process** — use the Bridge for in-process orchestration; cross-process communication should use plain data transfer objects (DTOs), not domain objects with behaviour.

## Section 6: Scenario / System Design Style Questions

**Q23. "Your team is building a reporting engine. Reports can be Summary or Detailed, and can be exported as PDF, Excel, or CSV. A junior engineer proposes one class per combination. How do you redesign this?"**
A: The junior's proposal produces 2 × 3 = 6 classes today; 3 types × 4 formats = 12 next quarter. Walk through the Bridge refactor:

**Step 1 — Identify the two axes:**
- Abstraction: report *type* — what data is included and how it's structured (`SummaryReport`, `DetailedReport`).
- Implementor: export *format* — how the structured data is serialised (`PdfExporter`, `ExcelExporter`, `CsvExporter`).

**Step 2 — Design the implementor interface:**
```typescript
interface ReportExporter {
  writeHeader(columns: string[]): void;
  writeRow(values: (string | number)[]): void;
  writeSection(title: string): void;
  finalise(): Buffer;
}
```

**Step 3 — Design the abstraction:**
```typescript
abstract class Report {
  constructor(protected exporter: ReportExporter) {}

  export(data: ReportData): Buffer {
    this.buildReport(data);
    return this.exporter.finalise();
  }

  protected abstract buildReport(data: ReportData): void;
}
```

**Step 4 — Refined abstractions:**
```typescript
class SummaryReport extends Report {
  protected buildReport(data: ReportData): void {
    this.exporter.writeHeader(["Metric", "Value"]);
    data.summaryRows.forEach(r => this.exporter.writeRow([r.metric, r.value]));
  }
}

class DetailedReport extends Report {
  protected buildReport(data: ReportData): void {
    data.sections.forEach(section => {
      this.exporter.writeSection(section.title);
      this.exporter.writeHeader(section.columns);
      section.rows.forEach(r => this.exporter.writeRow(r));
    });
  }
}
```

Result: 2 + 3 = 5 classes. Adding a `JsonExporter` means one class; adding a `ReconciliationReport` type means one class. Neither touches the other dimension.

**Q24. "In a microservices setup, your NotificationService sends alerts via multiple channels. A new WhatsApp Business API provider (e.g., switching from Interakt to Gupshup) needs to be onboarded with zero downtime. How does Bridge help?"**
A: Bridge makes provider migration a composition-root change — the business logic of *what* to send (`TransactionAlertNotification`, `KycReminderNotification`) is completely isolated from *how* it's delivered:

1. **Build `GupshupWhatsAppChannel`** implementing `NotificationChannel` — adapts Gupshup's API to the shared interface. No changes to any notification message class.
2. **Write contract tests** against the `NotificationChannel` interface and run them for both `InteraktWhatsAppChannel` and `GupshupWhatsAppChannel`. Passing tests confirm LSP compliance.
3. **Feature-flag the swap** at the NestJS DI provider level:
   ```typescript
   {
     provide:    "WHATSAPP_CHANNEL",
     useFactory: (flags: FeatureFlagService, interakt: InteraktWhatsAppChannel, gupshup: GupshupWhatsAppChannel) =>
       flags.isEnabled("gupshup-wa") ? gupshup : interakt,
     inject: [FeatureFlagService, InteraktWhatsAppChannel, GupshupWhatsAppChannel],
   }
   ```
4. **Gradual rollout** — enable the flag for 1% of traffic, monitor delivery receipts, ramp up. Rollback = flip the flag. Zero code changes in `TransactionAlertNotification` or anywhere in the business logic.

**Q25. "You're designing a trade execution engine for a discount broker. Orders can be Equity, Futures, or Options. Execution venues can be NSE, BSE, or MCX. How do you structure this with Bridge, and what are the key interface design decisions?"**
A: Trade instrument type is the abstraction; execution venue is the implementor.

**Key interface design decisions:**

```typescript
// ─── Implementor — Venue API ──────────────────────────────────────────────────

interface ExchangeVenueDriver {
  // Primitive: place a raw order on the exchange
  submitOrder(order: ExchangeOrder): Promise<ExchangeAck>;

  // Primitive: cancel an unexecuted order
  cancelOrder(exchangeOrderId: string): Promise<CancelAck>;

  // Primitive: get current order book snapshot for an instrument
  getOrderBook(isin: string): Promise<OrderBook>;

  // Primitive: stream real-time price ticks
  subscribeTicks(isin: string, handler: (tick: PriceTick) => void): Unsubscribe;
}

class NseDriver implements ExchangeVenueDriver   { /* NSE FIX protocol adapter */ }
class BseDriver implements ExchangeVenueDriver   { /* BSE BOLT adapter */ }
class McxDriver implements ExchangeVenueDriver   { /* MCX commodity adapter */ }

// ─── Abstraction — Instrument type ───────────────────────────────────────────

abstract class TradeOrder {
  constructor(protected venue: ExchangeVenueDriver) {}

  async place(orderRequest: OrderRequest): Promise<TradeAck> {
    await this.validateInstrumentRules(orderRequest);        // domain rule — equity vs futures
    const exchangeOrder = this.buildExchangeOrder(orderRequest);
    const ack           = await this.venue.submitOrder(exchangeOrder);
    await this.postSubmissionHook(orderRequest, ack);        // e.g., F&O margin reserve
    return { brokerOrderId: ack.exchangeOrderId, timestamp: ack.timestamp };
  }

  async cancel(brokerOrderId: string): Promise<void> {
    await this.venue.cancelOrder(brokerOrderId);
  }

  protected abstract validateInstrumentRules(request: OrderRequest): Promise<void>;
  protected abstract buildExchangeOrder(request: OrderRequest): ExchangeOrder;
  protected async postSubmissionHook(_request: OrderRequest, _ack: ExchangeAck): Promise<void> {}
}

// ─── Refined Abstractions ────────────────────────────────────────────────────

class EquityOrder extends TradeOrder {
  protected async validateInstrumentRules(request: OrderRequest): Promise<void> {
    if (request.quantity < 1) throw new Error("Equity orders must have quantity ≥ 1");
    // Check circuit breaker limits, SEBI upper circuit
  }
  protected buildExchangeOrder(request: OrderRequest): ExchangeOrder {
    return { isin: request.isin, quantity: request.quantity, price: request.limitPrice, orderType: "LIMIT" };
  }
}

class FuturesOrder extends TradeOrder {
  protected async validateInstrumentRules(request: OrderRequest): Promise<void> {
    // Lot size validation — NIFTY lot = 50
    if (request.quantity % request.lotSize !== 0) throw new Error("Quantity must be a multiple of lot size");
    // Margin check
    await this.validateMargin(request);
  }
  protected buildExchangeOrder(request: OrderRequest): ExchangeOrder {
    return { isin: request.isin, quantity: request.quantity, price: request.limitPrice, orderType: "LIMIT", segment: "FO" };
  }
  protected async postSubmissionHook(request: OrderRequest, _ack: ExchangeAck): Promise<void> {
    await this.reserveMargin(request);   // Block margin post-order
  }
  private async validateMargin(request: OrderRequest): Promise<void> { /* ... */ }
  private async reserveMargin(request: OrderRequest): Promise<void>  { /* ... */ }
}

class OptionsOrder extends TradeOrder {
  protected async validateInstrumentRules(request: OrderRequest): Promise<void> {
    if (!request.strikePrice || !request.optionType) throw new Error("Strike and option type required");
    if (request.expiry < new Date()) throw new Error("Cannot place order on expired contract");
  }
  protected buildExchangeOrder(request: OrderRequest): ExchangeOrder {
    return {
      isin: request.isin, quantity: request.quantity, price: request.limitPrice,
      orderType: "LIMIT", segment: "FO",
      strikePrice: request.strikePrice, optionType: request.optionType, expiry: request.expiry,
    };
  }
}

// ─── Composition: 3 types × 3 venues — 9 combinations from 6 classes ─────────

const niftyFuturesOnNse  = new FuturesOrder(new NseDriver());
const relEquityOnBse     = new EquityOrder(new BseDriver());
const crudeoilOptionsOnMcx = new OptionsOrder(new McxDriver());
```

**Key design decisions explained:**
- The `ExchangeVenueDriver` interface exposes *primitives* (submit, cancel, book, ticks) — not business operations like "place a futures order." That keeps the implementor thin and reusable across all instrument types.
- `validateInstrumentRules` and `postSubmissionHook` are abstract/hookable in the abstraction, letting each instrument type enforce SEBI/exchange-specific rules without touching the venue driver.
- Margin reservation (`postSubmissionHook` in `FuturesOrder`) is instrument-specific logic that doesn't belong in the venue driver — the Bridge keeps this concern in the right hierarchy.
- A new MCX `CommodityOrder` type means one new class; a new SGX venue means one new driver — neither touches the other hierarchy.

## Quick Reference Table

| Dimension                         | Bridge                                                                    |
|-----------------------------------|---------------------------------------------------------------------------|
| Category                          | Structural                                                                |
| Intent                            | Decouple abstraction from implementation — let both vary independently    |
| Key participants                  | Abstraction, RefinedAbstraction, Implementor, ConcreteImplementor         |
| Problem solved                    | M × N class explosion when two dimensions vary independently              |
| Class count                       | M + N instead of M × N                                                   |
| Connection mechanism              | Composition — abstraction holds reference to implementor                  |
| Runtime swap?                     | Yes — implementor reference can be replaced at runtime                    |
| Abstraction vs. implementor APIs  | Different — implementor is more primitive; abstraction is higher-level    |
| Extension mechanism               | Add new subclass to either hierarchy independently                        |
| Primary benefit                   | Two dimensions vary independently; each class has one reason to change    |
| Primary trade-off                 | Upfront complexity; overkill when only one dimension varies               |
| Testing benefit                   | Each hierarchy testable in isolation with a mock of the other             |
| Confused with                     | Strategy (one axis), Adapter (retrofit), Decorator (stacked same interface) |
| Common misuse                     | Applying when only one axis varies; abstraction leaking implementor types |
| SOLID alignment                   | OCP, DIP, SRP, Composition over inheritance                               |

**Tip for the Interview:** At the 5 YOE level, Bridge rarely comes up as "name the participants" — it shows up as "we have 12 classes for 3 payment methods × 4 gateways, this is becoming unmaintainable, how do you fix it?" or "how do you swap a gateway provider with zero downtime?" The answers that land identify the two independent axes of variation, demonstrate that M + N beats M × N, and show the composition-root wiring. In fintech, the canonical examples are payment method × gateway, notification type × channel, and loan product × credit bureau — know one of these cold with real provider names, real interface design rationale, and a clear explanation of why the abstraction and implementor APIs deliberately differ.
