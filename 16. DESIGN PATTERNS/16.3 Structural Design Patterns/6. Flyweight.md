# Design Patterns (Structural): Flyweight — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Flyweight pattern?**
A: Flyweight is a structural design pattern that reduces memory consumption by sharing as much data as possible between a large number of fine-grained objects. Instead of each object storing all its data independently, a Flyweight object holds only the data that is *intrinsic* — shared, context-independent, and immutable — while the data that is *extrinsic* — unique to each context and variable — is supplied by the caller at the time of use. The pattern trades CPU time (a lookup to retrieve the shared object) for memory (avoiding thousands of duplicate object allocations).

**Q2. What is the distinction between intrinsic and extrinsic state? Why is it the central concept of the pattern?**
A: The entire pattern rests on this split:

- **Intrinsic state** — data that is context-independent and identical across many instances. It can be safely shared because it never changes relative to the object's identity. Examples: a glyph's font face and point size shared across thousands of characters in a document; a product's category metadata shared across thousands of order line items; a stock symbol's exchange and tick size shared across millions of trade records.

- **Extrinsic state** — data that is context-dependent and unique to each usage site. It cannot be shared; it is passed in by the client each time a flyweight operation is invoked. Examples: a character's position on the page; an order line item's quantity and price; a trade record's timestamp and executed quantity.

It is the central concept because it determines whether the pattern is applicable at all. If almost no state is shareable (everything is extrinsic), Flyweight offers no benefit and just adds indirection. If a large fraction of state is intrinsic, Flyweight can reduce memory by orders of magnitude.

**Q3. What are the five participants in the Flyweight pattern?**
A: The GoF define five:
1. **Flyweight** — declares the interface through which flyweights receive and act on extrinsic state.
2. **ConcreteFlyweight** — implements `Flyweight` and stores intrinsic state. Must be shareable; its state must be independent of the usage context.
3. **UnsharedConcreteFlyweight** — not all `Flyweight` subclasses need to be shared. Some may hold both intrinsic and extrinsic state (e.g., a composite node that contains shared leaves). Present in the GoF formulation but rarely used in practice.
4. **FlyweightFactory** — creates and manages flyweight objects. Ensures flyweights are shared properly — when a client requests a flyweight, the factory returns an existing instance or creates a new one if none exists. This is the canonical use of an object pool / cache keyed by intrinsic state.
5. **Client** — holds references to flyweights and computes or stores extrinsic state. Passes extrinsic state to flyweight operations when needed.

**Q4. What memory problem motivates Flyweight, and how large does the object count need to be before it matters?**
A: Flyweight is motivated by the memory cost of having millions of objects where each one redundantly stores the same large chunk of data. A Node.js object has a baseline overhead of roughly 32–64 bytes just for the V8 object header, before any properties. If 500,000 trade records each store a copy of a `StockMetadata` object containing exchange name, sector, ISIN, currency, and tick size (perhaps 200 bytes), that's ~100 MB of duplicated metadata alone — which could instead be a single shared object per unique stock, costing only a few kilobytes total.

The threshold is not a fixed number but a function of: (object count) × (size of shareable state). Rule of thumb: when profiling shows a large percentage of heap is occupied by objects with identical subsets of their data, and that count is in the tens of thousands or more, Flyweight is worth considering. Below that scale, the added complexity rarely pays off.

**Q5. How does Flyweight relate to the other structural patterns and SOLID principles?**
A: Structurally:
- **Flyweight + Composite** — the canonical GoF combination. In a Composite tree (e.g., a document's element tree), leaf nodes are Flyweights that share intrinsic state; the tree structure and position coordinates are extrinsic, stored by the parent Composite nodes.
- **Flyweight factory is a specialised Factory Method / object pool** — it checks a cache before creating a new instance, making it a memoised factory.
- **Flyweight vs. Singleton** — Singleton ensures one instance for a type; Flyweight ensures one instance per unique intrinsic state *value*. A Flyweight factory produces a family of singletons keyed by value.
- **Flyweight + Proxy** — sometimes a Proxy is placed in front of the Flyweight to control access or add lazy loading.

SOLID alignment:
- **SRP** — Flyweight objects have a narrow responsibility: encapsulate intrinsic state and perform operations given extrinsic state.
- **OCP** — adding new flyweight types means adding new `ConcreteFlyweight` classes, not modifying the factory or existing flyweights.
- **DIP** — clients depend on the `Flyweight` interface, not concrete classes; the factory resolves the concrete type.

## Section 2: Structure & Implementation

**Q6. Walk through a canonical TypeScript implementation of the Flyweight pattern.**
A:

```typescript
// ─── Flyweight — intrinsic state only ────────────────────────────────────────

interface GlyphFlyweight {
  // Extrinsic state (position, colour) passed in at render time
  render(x: number, y: number, colour: string): void;
}

// ─── Concrete Flyweight ───────────────────────────────────────────────────────

class CharacterGlyph implements GlyphFlyweight {
  // Intrinsic: shared across every occurrence of this character + font combo
  constructor(
    private readonly char:     string,
    private readonly fontFace: string,
    private readonly fontSize: number
  ) {}

  render(x: number, y: number, colour: string): void {
    console.log(
      `Rendering '${this.char}' [${this.fontFace} ${this.fontSize}pt] ` +
      `at (${x}, ${y}) in ${colour}`
    );
  }
}

// ─── Flyweight Factory ────────────────────────────────────────────────────────

class GlyphFactory {
  private cache = new Map<string, CharacterGlyph>();

  getGlyph(char: string, fontFace: string, fontSize: number): CharacterGlyph {
    const key = `${char}|${fontFace}|${fontSize}`;

    if (!this.cache.has(key)) {
      console.log(`[factory] Creating new glyph for key "${key}"`);
      this.cache.set(key, new CharacterGlyph(char, fontFace, fontSize));
    }

    return this.cache.get(key)!;
  }

  get cachedCount(): number { return this.cache.size; }
}

// ─── Client — stores extrinsic state externally ───────────────────────────────

interface CharacterContext {
  glyph:   GlyphFlyweight; // shared
  x:       number;         // extrinsic
  y:       number;         // extrinsic
  colour:  string;         // extrinsic
}

class Document {
  private characters: CharacterContext[] = [];
  private factory = new GlyphFactory();

  addCharacter(
    char: string, fontFace: string, fontSize: number,
    x: number, y: number, colour: string
  ): void {
    const glyph = this.factory.getGlyph(char, fontFace, fontSize); // shared
    this.characters.push({ glyph, x, y, colour });                 // context is unique
  }

  render(): void {
    this.characters.forEach(({ glyph, x, y, colour }) => glyph.render(x, y, colour));
  }

  get stats(): string {
    return `${this.characters.length} characters, ${this.factory.cachedCount} unique glyphs`;
  }
}

// ─── Usage ───────────────────────────────────────────────────────────────────

const doc = new Document();
doc.addCharacter("H", "Arial", 12, 0,  0,  "black");
doc.addCharacter("e", "Arial", 12, 8,  0,  "black");
doc.addCharacter("l", "Arial", 12, 16, 0,  "black");
doc.addCharacter("l", "Arial", 12, 24, 0,  "black"); // reuses 'l' glyph
doc.addCharacter("o", "Arial", 12, 32, 0,  "black");
doc.addCharacter("H", "Arial", 12, 0,  20, "red");   // reuses 'H' glyph

doc.render();
console.log(doc.stats); // "6 characters, 4 unique glyphs"
```

The document holds 6 character contexts but only 4 glyph objects are ever created. With a 10,000-character document using 80 distinct glyphs, memory savings are dramatic.

**Q7. How should the Flyweight factory handle concurrency in a multi-threaded environment?**
A: JavaScript is single-threaded (no true data races in a single Node.js process), so a simple `Map` cache in the factory is safe within one process. The race condition that would exist in Java/C++ — two threads simultaneously checking `cache.has(key)` and both creating a new instance — cannot occur in Node's event loop model.

However, concerns do arise in:
- **Worker threads** — each `Worker` has its own V8 heap; the factory cache is not shared across workers. Each worker maintains its own flyweight pool. If the shared state is large, consider using `SharedArrayBuffer` to hold serializable intrinsic data across workers, with a per-worker object cache wrapping it.
- **Cluster mode** — each Node.js cluster process has its own memory; the pool is per-process. If the flyweight pool must be application-wide (e.g., for a shared in-memory price cache), move it to a shared store (Redis) and use a local per-process LRU cache as a second layer.
- **`async` factory initialisation** — if creating a flyweight requires an async operation (e.g., fetching metadata from a DB), guard against the "thundering herd" problem: two concurrent requests for the same key both miss the cache and both trigger a DB fetch. Use a `Map<string, Promise<Flyweight>>` to cache the in-flight promise:

```typescript
class AsyncFlyweightFactory {
  private cache     = new Map<string, StockMetadata>();
  private inflight  = new Map<string, Promise<StockMetadata>>();

  async get(isin: string): Promise<StockMetadata> {
    if (this.cache.has(isin)) return this.cache.get(isin)!;

    if (!this.inflight.has(isin)) {
      const promise = fetchMetadataFromDb(isin).then(meta => {
        this.cache.set(isin, meta);
        this.inflight.delete(isin);
        return meta;
      });
      this.inflight.set(isin, promise);
    }

    return this.inflight.get(isin)!;
  }
}
```

**Q8. How do you choose the cache key for the Flyweight factory?**
A: The key must uniquely identify the full set of intrinsic state. All fields that contribute to the flyweight's identity must be included; any field omitted risks key collisions (returning the wrong flyweight). Common approaches:

```typescript
// ❌ Wrong — ignores fontFace; 'A' Arial and 'A' Times New Roman get the same key
const key = `${char}|${fontSize}`;

// ✅ Correct — all intrinsic fields included
const key = `${char}|${fontFace}|${fontSize}`;

// ✅ Structured key for complex intrinsic state — stable JSON or a hash
const key = JSON.stringify({ isin, exchange, currency }); // fine for small objects

// ✅ For large or deeply nested intrinsic state — use a deterministic hash
import { createHash } from "crypto";
const key = createHash("sha1").update(JSON.stringify(intrinsicState)).digest("hex");
```

For primitive-only intrinsic state (strings, numbers), template literals are clear and fast. For complex nested objects, prefer a hash — `JSON.stringify` key order can be inconsistent across serialization contexts unless the object is constructed in a canonical order.

**Q9. Should Flyweight objects be strictly immutable, and how do you enforce that in TypeScript?**
A: Yes — Flyweight objects **must** be immutable. If intrinsic state could be mutated, sharing would be catastrophically unsafe: one client changing the shared state would silently corrupt every other client holding a reference to the same flyweight. TypeScript enforcement:

```typescript
class StockMetadata {
  constructor(
    readonly isin:      string,   // readonly — compile-time immutability
    readonly symbol:    string,
    readonly exchange:  "NSE" | "BSE" | "MCX",
    readonly currency:  string,
    readonly tickSize:  number,
    readonly lotSize:   number,
  ) {}
}

// For objects built from plain data (e.g., from DB), use Object.freeze:
function createStockMetadata(data: StockMetadataDto): Readonly<StockMetadata> {
  return Object.freeze(new StockMetadata(
    data.isin, data.symbol, data.exchange,
    data.currency, data.tickSize, data.lotSize
  ));
}
```

`Object.freeze` provides runtime protection (attempted mutations silently fail in non-strict mode, throw in strict mode). `readonly` provides compile-time protection. Deep immutability (nested objects) requires recursive `Object.freeze` or libraries like `immer` — `Object.freeze` is shallow.

**Q10. What is the difference between Flyweight and an object pool?**
A: Related but distinct:

| Dimension            | Flyweight                                                     | Object Pool                                                   |
|----------------------|---------------------------------------------------------------|---------------------------------------------------------------|
| Primary goal         | Reduce memory by sharing identical objects                    | Reduce allocation cost by reusing objects across time         |
| State model          | Objects are immutable and shared concurrently                 | Objects are mutable; exclusively checked out, then returned   |
| Cardinality          | One instance per unique intrinsic state value                 | N instances, each used by one client at a time                |
| Lifecycle            | Factory creates once, never reclaims                          | Pool creates N, reclaims after each use                       |
| Identity             | Identity = intrinsic state (value semantics)                  | Identity = the object itself (reference semantics)            |
| Concurrency          | Safe to share — immutable                                     | Exclusive checkout required — mutable                         |

An object pool is appropriate for expensive-to-create resources (DB connections, threads, HTTP agents) where you can't share state but want to amortize allocation cost. Flyweight is appropriate for lightweight value objects where the shared data is immutable.

## Section 3: Flyweight in Node.js / TypeScript / Fintech Context

**Q11. Show a Flyweight implementation for a high-throughput stock market trade record system.**
A: In a trading platform, millions of `TradeRecord` objects are created per session. Each record references a stock, but the stock's metadata (symbol, exchange, sector, currency, tick size) is identical across all trades for that stock. Flyweight separates the shared metadata from the per-trade data:

```typescript
// ─── Flyweight — intrinsic: stock metadata ────────────────────────────────────

class StockMetadata {
  constructor(
    readonly isin:        string,
    readonly symbol:      string,
    readonly exchange:    "NSE" | "BSE" | "MCX",
    readonly sector:      string,
    readonly currency:    "INR" | "USD",
    readonly tickSize:    number,   // minimum price movement
    readonly lotSize:     number,   // minimum tradeable quantity
  ) {
    Object.freeze(this);
  }

  // Intrinsic operation: validate a price against tick size
  isValidPrice(price: number): boolean {
    return Math.round(price / this.tickSize) * this.tickSize === price;
  }

  // Intrinsic operation: compute brokerage cap for this exchange
  brokerageCap(): number {
    return this.exchange === "NSE" ? 2000000 : 1500000; // in paise
  }
}

// ─── Flyweight Factory ────────────────────────────────────────────────────────

class StockMetadataRegistry {
  private static instance: StockMetadataRegistry;
  private cache = new Map<string, StockMetadata>();

  static getInstance(): StockMetadataRegistry {
    if (!this.instance) this.instance = new StockMetadataRegistry();
    return this.instance;
  }

  register(meta: StockMetadata): void {
    this.cache.set(meta.isin, meta);
  }

  get(isin: string): StockMetadata {
    const meta = this.cache.get(isin);
    if (!meta) throw new Error(`Unknown ISIN: ${isin}`);
    return meta;
  }

  get size(): number { return this.cache.size; }
}

// ─── Client — TradeRecord holds extrinsic state + reference to flyweight ──────

class TradeRecord {
  constructor(
    // Extrinsic — unique per trade
    readonly tradeId:        string,
    readonly timestamp:      Date,
    readonly executedQty:    number,
    readonly executedPrice:  number,   // in paise
    readonly side:           "BUY" | "SELL",
    readonly traderId:       string,
    // Flyweight reference — shared across all trades for this stock
    private readonly stock:  StockMetadata
  ) {}

  get symbol(): string   { return this.stock.symbol; }
  get exchange(): string { return this.stock.exchange; }

  // Operation uses both intrinsic (tickSize) and extrinsic (executedPrice)
  validatePrice(): boolean {
    return this.stock.isValidPrice(this.executedPrice);
  }

  // Compute turnover: extrinsic qty × price
  turnoverInPaise(): number {
    return this.executedQty * this.executedPrice;
  }

  // Compute brokerage using intrinsic cap + extrinsic turnover
  brokerageInPaise(): number {
    const computed = this.turnoverInPaise() * 0.0003;   // 0.03%
    return Math.min(computed, this.stock.brokerageCap());
  }
}

// ─── Bootstrap: register stock metadata once ─────────────────────────────────

const registry = StockMetadataRegistry.getInstance();
registry.register(new StockMetadata("INE040A01034", "HDFCBANK", "NSE", "Banking",    "INR", 5,   1));
registry.register(new StockMetadata("INE002A01018", "RELIANCE", "NSE", "Energy",     "INR", 5,   1));
registry.register(new StockMetadata("INE467B01029", "ZOMATO",   "NSE", "Technology", "INR", 5,   1));

// ─── Usage: create millions of trades referencing shared metadata ─────────────

function createTradeRecord(dto: TradeDto): TradeRecord {
  const stock = registry.get(dto.isin);   // O(1) cache lookup
  return new TradeRecord(
    dto.tradeId, new Date(dto.timestamp),
    dto.executedQty, dto.executedPrice, dto.side, dto.traderId,
    stock   // shared flyweight
  );
}

// 1,000,000 trades for 3 stocks → 3 StockMetadata objects, 1M TradeRecord objects
```

Without Flyweight, each `TradeRecord` copies ~200 bytes of stock metadata → 200 MB for 1M trades. With Flyweight, stock metadata costs 3 × 200 bytes = 600 bytes total.

**Q12. How does Flyweight apply to a fee/charge configuration system in a lending platform?**
A: In a lending platform, thousands of active loans may reference the same loan product configuration (interest rate formula, processing fee percent, prepayment penalty rules, RBI regulatory parameters). The product config is intrinsic; the per-loan financial state is extrinsic:

```typescript
// ─── Flyweight: LoanProductConfig ────────────────────────────────────────────

class LoanProductConfig {
  constructor(
    readonly productCode:           string,
    readonly productName:           string,
    readonly annualInterestRate:    number,   // e.g., 0.18 for 18% p.a.
    readonly processingFeePercent:  number,
    readonly prepaymentPenalty:     number,
    readonly maxTenureMonths:       number,
    readonly regulatoryCategory:    "Priority" | "Non-Priority",
    readonly gstOnFees:             number,   // 0.18 for 18% GST
  ) {
    Object.freeze(this);
  }

  // Intrinsic operation: compute EMI given extrinsic principal and tenure
  computeEmi(principalInPaise: number, tenureMonths: number): number {
    const r = this.annualInterestRate / 12;
    const emi = (principalInPaise * r * Math.pow(1 + r, tenureMonths))
              / (Math.pow(1 + r, tenureMonths) - 1);
    return Math.round(emi);
  }

  // Intrinsic + extrinsic: compute processing fee for a given loan amount
  processingFeeInPaise(principalInPaise: number): number {
    const fee = principalInPaise * this.processingFeePercent;
    return Math.round(fee * (1 + this.gstOnFees));
  }

  // Intrinsic: prepayment penalty on outstanding principal (extrinsic)
  prepaymentPenaltyInPaise(outstandingInPaise: number): number {
    return Math.round(outstandingInPaise * this.prepaymentPenalty);
  }
}

// ─── Factory ──────────────────────────────────────────────────────────────────

class LoanProductRegistry {
  private configs = new Map<string, LoanProductConfig>();

  register(config: LoanProductConfig): void {
    this.configs.set(config.productCode, config);
  }

  get(productCode: string): LoanProductConfig {
    const config = this.configs.get(productCode);
    if (!config) throw new Error(`Unknown loan product: ${productCode}`);
    return config;
  }
}

// ─── Client: LoanAccount holds extrinsic state ───────────────────────────────

class LoanAccount {
  constructor(
    readonly loanId:             string,
    readonly customerId:         string,
    readonly principalInPaise:   number,    // extrinsic
    readonly tenureMonths:       number,    // extrinsic
    readonly disbursementDate:   Date,      // extrinsic
    private readonly product:    LoanProductConfig  // shared flyweight
  ) {}

  get monthlyEmi(): number {
    return this.product.computeEmi(this.principalInPaise, this.tenureMonths);
  }

  get processingFee(): number {
    return this.product.processingFeeInPaise(this.principalInPaise);
  }

  prepaymentPenalty(outstandingInPaise: number): number {
    return this.product.prepaymentPenaltyInPaise(outstandingInPaise);
  }
}
```

A lending platform with 500,000 active loans across 10 loan products holds 10 `LoanProductConfig` objects, not 500,000 copies.

**Q13. How do you apply Flyweight to reduce memory pressure from parsed JWT / session token payloads in a high-traffic API?**
A: In a high-traffic NestJS API, each incoming request carries a JWT whose payload is decoded into a session object. If many requests originate from the same user (or the same role / permission set), the decoded permission arrays and role metadata are repeated across every simultaneous in-flight request. A Flyweight session metadata cache avoids redundant allocations:

```typescript
// ─── Flyweight: shared role + permission metadata ────────────────────────────

interface RoleMetadata {
  readonly role:        string;
  readonly permissions: ReadonlySet<string>;
  readonly rateLimit:   number;              // requests/minute
  readonly tier:        "free" | "pro" | "enterprise";
}

class RoleMetadataRegistry {
  private cache = new Map<string, RoleMetadata>();

  getOrCreate(role: string, permissions: string[], tier: RoleMetadata["tier"], rateLimit: number): RoleMetadata {
    if (!this.cache.has(role)) {
      this.cache.set(role, Object.freeze({
        role,
        permissions: Object.freeze(new Set(permissions)),
        rateLimit,
        tier,
      }));
    }
    return this.cache.get(role)!;
  }
}

// ─── Client: RequestContext — per-request extrinsic state ────────────────────

interface RequestContext {
  userId:        string;        // extrinsic — unique per request
  sessionId:     string;        // extrinsic
  issuedAt:      Date;          // extrinsic
  expiresAt:     Date;          // extrinsic
  roleMetadata:  RoleMetadata;  // shared flyweight
}

// ─── Guard — builds RequestContext after JWT decode ───────────────────────────

@Injectable()
class JwtAuthGuard implements CanActivate {
  constructor(
    private readonly jwtService:      JwtService,
    private readonly roleRegistry:    RoleMetadataRegistry,
  ) {}

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const token   = this.extractToken(request);
    const payload = this.jwtService.verify(token);

    // Flyweight lookup — role metadata shared across all concurrent requests for this role
    const roleMetadata = this.roleRegistry.getOrCreate(
      payload.role,
      payload.permissions,
      payload.tier,
      payload.rateLimit,
    );

    // RequestContext: unique per request (extrinsic), references shared flyweight
    request.ctx = {
      userId:       payload.sub,
      sessionId:    payload.jti,
      issuedAt:     new Date(payload.iat * 1000),
      expiresAt:    new Date(payload.exp * 1000),
      roleMetadata,
    } satisfies RequestContext;

    return true;
  }

  private extractToken(req: Request): string { /* ... */ }
}
```

Under high concurrency (10,000 simultaneous requests), 10,000 `RequestContext` objects reference a handful of shared `RoleMetadata` flyweights (one per distinct role), rather than 10,000 separate allocations of permission arrays.

**Q14. How does Flyweight apply to a real-time market data feed with thousands of price tick objects per second?**
A: A market data feed may emit 50,000+ price ticks per second across 2,000 instruments. Each tick contains a small amount of unique data (price, volume, timestamp) plus the instrument's metadata (symbol, exchange, ISIN, tick size). Without Flyweight, every tick object allocates a fresh copy of the instrument metadata. With Flyweight, each instrument is represented by one shared object, and ticks carry only what changes:

```typescript
// ─── Flyweight: InstrumentDescriptor (intrinsic) ─────────────────────────────

class InstrumentDescriptor {
  constructor(
    readonly isin:          string,
    readonly symbol:        string,
    readonly exchange:      string,
    readonly instrumentType: "EQ" | "FUT" | "OPT",
    readonly tickSize:      number,
    readonly lotSize:       number,
    readonly currency:      string,
  ) { Object.freeze(this); }

  // Intrinsic utility: normalise a raw price from the feed
  normalisePrice(rawPrice: number): number {
    return Math.round(rawPrice / this.tickSize) * this.tickSize;
  }
}

// ─── Flyweight Factory ────────────────────────────────────────────────────────

class InstrumentRegistry {
  private descriptors = new Map<string, InstrumentDescriptor>();

  loadFromMasterData(instruments: InstrumentDescriptorDto[]): void {
    for (const dto of instruments) {
      this.descriptors.set(dto.isin, new InstrumentDescriptor(
        dto.isin, dto.symbol, dto.exchange,
        dto.instrumentType, dto.tickSize, dto.lotSize, dto.currency
      ));
    }
    console.log(`[InstrumentRegistry] Loaded ${this.descriptors.size} instruments`);
  }

  get(isin: string): InstrumentDescriptor {
    const d = this.descriptors.get(isin);
    if (!d) throw new Error(`Instrument not found: ${isin}`);
    return d;
  }
}

// ─── Client: PriceTick — extrinsic state only ────────────────────────────────

class PriceTick {
  constructor(
    readonly lastPrice:   number,      // extrinsic — changes every tick
    readonly volume:      number,      // extrinsic
    readonly timestamp:   bigint,      // extrinsic — nanosecond epoch
    readonly bidPrice:    number,      // extrinsic
    readonly askPrice:    number,      // extrinsic
    readonly instrument:  InstrumentDescriptor  // shared flyweight
  ) {}

  get symbol(): string     { return this.instrument.symbol; }
  get spread(): number     { return this.askPrice - this.bidPrice; }
  get normalisedLast(): number { return this.instrument.normalisePrice(this.lastPrice); }
}

// ─── Feed processor ───────────────────────────────────────────────────────────

class MarketDataProcessor {
  constructor(private readonly instruments: InstrumentRegistry) {}

  processFeedMessage(raw: RawFeedMessage): PriceTick {
    const instrument = this.instruments.get(raw.isin);  // O(1) — shared object
    return new PriceTick(
      raw.lastPrice, raw.volume, raw.timestamp,
      raw.bidPrice, raw.askPrice,
      instrument
    );
  }
}
```

At 50,000 ticks/second, 2,000 instruments: without Flyweight, each tick allocates ~300 bytes of instrument data → 50,000 × 300 = 15 MB/s of metadata allocation, generating enormous GC pressure. With Flyweight, instrument data is allocated once per unique instrument (2,000 × 300 = 600 KB total), and ticks hold only their ~80 bytes of unique data.

**Q15. How does Flyweight interact with Node.js garbage collection, and what are the memory management implications?**
A: Flyweights are held in the factory's cache map, which is a GC root — the factory keeps all created flyweights alive for the process lifetime (or as long as the factory is alive). This is intentional: the whole point is that flyweights persist and are shared. Implications:

- **Memory is not freed when all clients of a flyweight disappear.** If the set of valid flyweights is bounded and stable (e.g., all NSE-listed instruments), this is fine. If flyweights are created for transient keys (e.g., one per session ID), the cache becomes an unbounded memory leak.
- **Use `WeakRef` + `FinalizationRegistry` for optional sharing** — if you want flyweights that can be GC'd when no clients hold references:

```typescript
class WeakFlyweightFactory {
  private cache = new Map<string, WeakRef<StockMetadata>>();
  private registry = new FinalizationRegistry((key: string) => {
    this.cache.delete(key);   // clean up dead entry when GC collects the object
  });

  getOrCreate(isin: string, buildFn: () => StockMetadata): StockMetadata {
    const ref  = this.cache.get(isin);
    const meta = ref?.deref();

    if (meta) return meta;

    const newMeta = buildFn();
    this.cache.set(isin, new WeakRef(newMeta));
    this.registry.register(newMeta, isin);
    return newMeta;
  }
}
```

`WeakRef` is appropriate when the flyweight set is large and dynamic (e.g., millions of product SKUs in an e-commerce platform) and you don't want the cache to grow without bound. For a finite, stable set (stock instruments, loan product configs), a plain `Map` is simpler and correct.

## Section 4: Pitfalls & Anti-patterns

**Q16. What are the most common mistakes when implementing Flyweight?**
A: Four recurring mistakes:

1. **Storing extrinsic state in the flyweight.** If the flyweight holds data that varies per usage context, it can no longer be shared — one client's extrinsic state overwrites another's. The only fix is to move that data to the client context and pass it as a method argument.

2. **Mutable flyweights.** Even if the data is intrinsic, failing to freeze or lock the flyweight means a caller can inadvertently mutate shared state. Use `readonly` and `Object.freeze` uniformly.

3. **Unbounded factory cache.** Creating a flyweight per unique user ID, session, or timestamp turns the factory into a memory leak. Flyweight makes sense only when the number of distinct intrinsic state combinations is small relative to the number of client objects.

4. **Applying Flyweight prematurely.** Splitting state into intrinsic/extrinsic adds cognitive overhead and makes the API less natural (callers must pass extrinsic state explicitly). Without a measured memory problem, this complexity is pure cost. Profile first; introduce Flyweight when the heap snapshot shows the problem.

**Q17. How does Flyweight complicate debugging and observability?**
A: Several ways:

- **Object identity is misleading.** Two `TradeRecord` objects for different trades share the same `StockMetadata` reference. A debugger showing object identity for the metadata gives no indication that it's shared — it looks like a normal field. Developers unfamiliar with the pattern may mutate what they believe is a local field and silently corrupt other objects.
- **Stack traces are harder to attribute.** If a flyweight's method throws, the stack trace points to the shared object, not to any specific client. You must examine the extrinsic arguments passed to the method, which are not part of the flyweight's own state.
- **Memory profiling is less straightforward.** A heap snapshot shows many objects all holding a reference to the same flyweight — the "retained size" of each client object appears small, making it harder to see the actual footprint contribution at a glance.

Mitigation: document flyweight objects clearly in code comments and architecture documentation; add a `.toString()` or `toDebugString()` method to flyweights that makes their shared nature explicit.

**Q18. When does Flyweight make performance *worse*?**
A: Three cases:

1. **Extrinsic state is expensive to pass.** If the extrinsic state is a large object that must be passed on every method call (and cannot be retained anywhere), the per-call overhead of passing it may exceed the memory savings, especially in hot loops.

2. **Cache lookup overhead dominates.** Map lookups with string keys involve hashing and comparison. If the object count is not large enough to justify the savings, a direct allocation is faster than a factory lookup per operation.

3. **The intrinsic state is tiny.** If the shared data is a single integer or a short string, the memory savings are negligible and the added indirection is pure overhead. Flyweight is for non-trivial shared state — objects with meaningful size that justify the pattern's complexity.

**Q19. How does Flyweight interact with serialisation/deserialisation (e.g., JSON.stringify, Redis caching)?**
A: When a client object containing a flyweight reference is serialised to JSON, the flyweight's data is inlined — every serialised client gets a full copy of the intrinsic state in the output. On deserialisation, the client object has a plain embedded copy of what was the flyweight, not a reference to a shared object. The sharing is lost.

```typescript
const trade = new TradeRecord("T1", new Date(), 100, 150000, "BUY", "trader_1", registry.get("INE040A01034"));

// Serialisation inlines flyweight data — sharing lost
const json = JSON.stringify(trade);
// { "tradeId": "T1", ..., "stock": { "isin": "INE040A01034", "symbol": "HDFCBANK", ... } }

// Deserialisation: rebuild the flyweight reference, don't keep embedded copy
function deserialiseTradeRecord(json: string): TradeRecord {
  const dto   = JSON.parse(json);
  const stock = registry.get(dto.stock.isin);   // re-attach flyweight from registry
  return new TradeRecord(dto.tradeId, new Date(dto.timestamp), dto.executedQty,
    dto.executedPrice, dto.side, dto.traderId, stock);
}
```

The pattern for both serialisation and deserialisation is: **store only the flyweight key** (e.g., `isin`), not the full flyweight body. On deserialisation, use the key to retrieve the flyweight from the registry. This keeps serialised payloads smaller and restores sharing on the receiving end.

**Q20. Can Flyweight and Prototype coexist, and what is the risk?**
A: They can coexist but require care. The Prototype pattern clones objects — if you clone a client object that holds a flyweight reference, the clone shares the same flyweight, which is correct and safe (the flyweight is immutable). The risk arises if someone clones the *flyweight itself*:

```typescript
// ❌ Cloning a flyweight breaks sharing — clone is a separate object
const original = registry.get("INE040A01034");
const clone     = { ...original };   // shallow spread — a new, unregistered object
```

The clone is structurally identical but is a different object in memory — not registered in the factory, not shared with anyone else. Code that checks identity (`===`) will treat them as different; code that checks equality may not. Mitigation: seal flyweight classes (prevent spreading / cloning) and mark them clearly in code.

## Section 5: Scenario / System Design Style Questions

**Q21. "Your Node.js trading platform is processing 1 million trade records per session and the heap is growing to 4 GB. A heap snapshot shows 90% of the heap is `TradeRecord` objects, and each one stores a full `StockMetadata` copy. How do you fix this?"**
A: Classic Flyweight diagnosis and fix — walk through it systematically:

**Diagnosis:**
1. Heap snapshot confirms: 1M `TradeRecord` × ~4 KB per object (data + metadata copy) ≈ 4 GB.
2. Identify intrinsic state: `StockMetadata` fields (ISIN, symbol, exchange, sector, currency, tick size, lot size) are identical for all trades of the same stock.
3. Measure sharing ratio: 1M trades across (say) 500 unique stocks → 2,000× potential reduction in metadata allocation.

**Fix:**
1. Extract `StockMetadata` into a Flyweight class; add `Object.freeze`.
2. Build `StockMetadataRegistry` — loaded at startup from the NSE/BSE master data file, keyed by ISIN.
3. Refactor `TradeRecord` — replace the embedded `StockMetadata` copy with a reference field; update the constructor to accept a `StockMetadata` parameter.
4. Refactor the trade record factory / deserialiser — look up the flyweight from the registry before constructing each `TradeRecord`.
5. Verify: heap snapshot after fix shows 500 `StockMetadata` objects (one per unique stock) instead of 1M, regardless of trade volume.

**Expected outcome:** `TradeRecord` shrinks from ~4 KB to ~80 bytes of extrinsic data + an 8-byte reference. Total heap: 1M × 88 bytes ≈ 88 MB, down from 4 GB — a ~45× reduction in metadata-related memory.

**Q22. "You're building a rule engine for a KYC/AML compliance system. Each customer check runs the same set of rules, but the rule definitions (description, severity, regulatory reference, remediation steps) are loaded from the database. There will be 100,000 concurrent checks running. How does Flyweight apply?"**
A: The rule definitions are intrinsic — they're identical regardless of which customer is being checked. The check result and customer data are extrinsic:

```typescript
// ─── Flyweight: RuleDefinition ────────────────────────────────────────────────

class RuleDefinition {
  constructor(
    readonly ruleId:               string,
    readonly ruleName:             string,
    readonly description:          string,
    readonly severity:             "LOW" | "MEDIUM" | "HIGH" | "CRITICAL",
    readonly regulatoryReference:  string,   // e.g., "PMLA Section 12"
    readonly remediationSteps:     readonly string[],
    readonly category:             "KYC" | "AML" | "FRAUD",
  ) { Object.freeze(this); }
}

// ─── Factory: loaded once from DB at startup ─────────────────────────────────

class RuleDefinitionRegistry {
  private rules = new Map<string, RuleDefinition>();

  async loadFromDatabase(db: DbClient): Promise<void> {
    const rows = await db.query("SELECT * FROM compliance_rules WHERE active = TRUE");
    for (const row of rows) {
      this.rules.set(row.rule_id, new RuleDefinition(
        row.rule_id, row.rule_name, row.description,
        row.severity, row.regulatory_reference,
        Object.freeze(row.remediation_steps),
        row.category,
      ));
    }
    console.log(`[RuleRegistry] Loaded ${this.rules.size} rule definitions`);
  }

  get(ruleId: string): RuleDefinition {
    const r = this.rules.get(ruleId);
    if (!r) throw new Error(`Unknown rule: ${ruleId}`);
    return r;
  }

  getAll(): RuleDefinition[] { return [...this.rules.values()]; }
}

// ─── Client: ComplianceCheckResult — extrinsic per customer check ─────────────

class ComplianceCheckResult {
  constructor(
    readonly checkId:     string,          // extrinsic
    readonly customerId:  string,          // extrinsic
    readonly passed:      boolean,         // extrinsic
    readonly flaggedValue: string | null,  // extrinsic
    readonly checkedAt:   Date,            // extrinsic
    readonly rule:        RuleDefinition,  // shared flyweight
  ) {}

  get severity(): string  { return this.rule.severity; }
  get remediation(): readonly string[] { return this.rule.remediationSteps; }

  toAuditLog(): string {
    return `[${this.checkedAt.toISOString()}] Customer ${this.customerId} — ` +
           `Rule ${this.rule.ruleName} (${this.rule.regulatoryReference}): ` +
           `${this.passed ? "PASS" : "FAIL"} | Flagged: ${this.flaggedValue ?? "none"}`;
  }
}
```

100,000 concurrent checks × (say) 50 rules each = 5M `ComplianceCheckResult` objects, all referencing ~50 shared `RuleDefinition` flyweights instead of duplicating rule metadata across 5M objects.

**Q23. "A junior engineer on your team suggests caching the Flyweight factory itself in Redis so it can be shared across microservice instances. Is this a good idea?"**
A: Partially — but the proposal conflates two different concerns and introduces a subtle problem:

**What's correct about it:** the underlying data that the flyweight encapsulates (stock metadata, rule definitions) *should* be stored in a shared store (Redis, a database) so that all microservice instances use the same source of truth and stay consistent if the data changes.

**What's wrong about it:** the flyweight *objects* themselves — the in-memory instances with methods and `Object.freeze` — cannot live in Redis. Redis stores serialisable data; you cannot store a JavaScript class instance with methods in Redis and retrieve it as a live object. Attempting to do so loses all methods and prototype chain.

**Correct architecture:**
- Redis stores the *raw data* (ISIN → `{ symbol, exchange, tickSize, ... }` as JSON).
- Each microservice instance has its own in-process `InstrumentRegistry` / Flyweight factory, warm-loaded from Redis at startup.
- On data updates (e.g., a corporate action changes a stock's lot size), publish an invalidation event; each instance refreshes its local factory.

```typescript
// Startup bootstrap
async function bootstrapRegistry(redis: RedisClient, registry: InstrumentRegistry): Promise<void> {
  const keys = await redis.keys("instrument:*");
  const raws = await Promise.all(keys.map(k => redis.get(k)));
  const dtos  = raws.map(r => JSON.parse(r!) as InstrumentDescriptorDto);
  registry.loadFromMasterData(dtos);
}

// Invalidation subscriber
redis.subscribe("instrument:updated", async (message) => {
  const dto = JSON.parse(message) as InstrumentDescriptorDto;
  registry.update(dto.isin, new InstrumentDescriptor(...));
});
```

This gives per-process sharing (Flyweight benefit) plus cross-process consistency (Redis benefit) without conflating them.

**Q24. "You're doing a code review and see a NestJS service that constructs a new NotificationTemplate object (containing body text, subject, sender config, retry policy — ~2 KB) inside every request handler call, for what ends up being 8 static templates. There are 500 requests/second. What do you flag and how do you fix it?"**
A: Classic unnecessary allocation — 500 req/s × 2 KB × 8 template constructions per request = 8 MB/s of short-lived allocations driving GC. Flyweight (or simply a module-scoped cache) is the fix:

**Code review flags:**
- Template data is clearly intrinsic — body text, subject, sender config, retry policy are identical for every invocation of the same template type.
- There is no per-request variation in the template itself (only in who it's *sent* to, which is extrinsic).
- Constructing inside a request handler means the GC must collect 8 objects per request — 4,000 short-lived allocations per second for data that never changes.

**Fix — NestJS module-scoped Flyweight:**
```typescript
// ─── Flyweight: NotificationTemplate ─────────────────────────────────────────

class NotificationTemplate {
  constructor(
    readonly templateId:     string,
    readonly subject:        string,
    readonly bodyHtml:       string,
    readonly bodyText:       string,
    readonly senderAddress:  string,
    readonly senderName:     string,
    readonly retryPolicy:    Readonly<RetryPolicy>,
    readonly trackingEnabled: boolean,
  ) { Object.freeze(this); }

  // Extrinsic data (recipient, variables) passed in at render time
  render(recipient: string, variables: Record<string, string>): RenderedMessage {
    const body = this.bodyHtml.replace(
      /\{\{(\w+)\}\}/g,
      (_, key) => variables[key] ?? ""
    );
    return { to: recipient, subject: this.subject, bodyHtml: body, from: this.senderAddress };
  }
}

// ─── NestJS module-scoped registry — instantiated once per process ────────────

@Injectable()
class NotificationTemplateRegistry {
  private templates = new Map<string, NotificationTemplate>();

  onModuleInit(): void {
    // Registered once at startup — not per request
    this.register(new NotificationTemplate(
      "txn_success", "Transaction Successful", "<p>Your ₹{{amount}} payment...</p>",
      "Your ₹{{amount}} payment succeeded.", "noreply@finapp.in", "FinApp",
      { maxRetries: 3, backoffMs: 1000 }, true,
    ));
    this.register(new NotificationTemplate(
      "kyc_reminder", "Complete your KYC", "<p>Hi {{name}}, your KYC expires...</p>",
      "Hi {{name}}, your KYC expires in {{days}} days.", "kyc@finapp.in", "FinApp KYC",
      { maxRetries: 2, backoffMs: 500 }, false,
    ));
    // ... remaining 6 templates
  }

  register(t: NotificationTemplate): void { this.templates.set(t.templateId, t); }

  get(templateId: string): NotificationTemplate {
    const t = this.templates.get(templateId);
    if (!t) throw new Error(`Unknown template: ${templateId}`);
    return t;
  }
}

// ─── Request handler — uses flyweight, passes extrinsic data at render time ───

@Injectable()
class NotificationService {
  constructor(private readonly templates: NotificationTemplateRegistry) {}

  async sendTransactionAlert(userId: string, amountInPaise: number): Promise<void> {
    const template = this.templates.get("txn_success");  // O(1) — shared object
    const message  = template.render(userId, { amount: String(amountInPaise / 100) });
    await this.emailProvider.send(message);
  }
}
```

8 template objects created once at startup, shared across all 500 req/s. GC pressure for template objects: zero.

**Q25. "How would you explain the Flyweight pattern to a non-technical engineering manager who's asking why the memory usage went from 4 GB to 200 MB after your refactor?"**
A: An accessible analogy:

> "Imagine a library with 10,000 borrowers, and every borrower needs a copy of the library's catalogue — the full list of books, their authors, genres, and shelf locations. Before the refactor, we were printing a personal copy of the entire 500-page catalogue for every single borrower. That's 10,000 × 500 pages = 5 million pages of identical information sitting around.
>
> After the refactor, there's one master catalogue that everyone shares. When a borrower needs to find a book, they look at the shared catalogue and just carry a slip of paper with their own borrowing details — their name, which book they want, and when they want it.
>
> The 4 GB was us storing 10,000 copies of the catalogue. The 200 MB is us storing one catalogue plus 10,000 borrower slips. The catalogue is the Flyweight — shared, never changing. The borrower slip is what's unique to each person. Same information is accessible; dramatically less paper."

## Quick Reference Table

| Dimension                        | Flyweight                                                                 |
|----------------------------------|---------------------------------------------------------------------------|
| Category                         | Structural                                                                |
| Intent                           | Share fine-grained objects to reduce memory when many similar objects exist |
| Central concept                  | Intrinsic (shared, immutable) vs. extrinsic (unique, passed by caller) state |
| Key participants                 | Flyweight, ConcreteFlyweight, FlyweightFactory, Client                    |
| Memory model                     | M unique flyweight objects instead of N client objects × M duplicate copies |
| Class count impact               | Reduces object instances, not class count                                 |
| Factory role                     | Cache keyed by intrinsic state; returns existing or creates new           |
| Mutability requirement           | Flyweights must be immutable — shared state cannot be safely mutated      |
| Runtime behaviour                | Client passes extrinsic state as method arguments at call time            |
| When to use                      | Large number of objects (≥ tens of thousands) with significant shared state |
| When NOT to use                  | Object count is small; no meaningful shared state; premature optimisation  |
| GC implications                  | Factory holds strong references — flyweights live for factory lifetime     |
| Optional GC-friendly variant     | `WeakRef` + `FinalizationRegistry` for dynamic, unbounded key spaces      |
| Serialisation handling           | Store only the key; re-attach flyweight from registry on deserialisation  |
| Confused with                    | Object pool (mutable, exclusive checkout vs. shared, immutable)           |
| Common misuse                    | Storing extrinsic state in flyweight; mutable flyweights; unbounded cache |
| Node.js-specific note            | Single-threaded — no read race; async creation needs in-flight promise cache |
| SOLID alignment                  | SRP (narrow responsibility), OCP (add new types without modifying factory) |
