# Inter-Process Communication (IPC): Pipes, Message Queues, Shared Memory, Sockets — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why does IPC exist, and what problem does it fundamentally solve?**
A: IPC exists because processes are isolated by design — each has its own private virtual address space enforced by the MMU and OS. This isolation is the source of process stability and security: one process cannot accidentally (or maliciously) corrupt another's memory. But isolation creates a communication problem: two processes that need to cooperate — a web server and a cache daemon, a Node.js master and its cluster workers, a payment API and a NACH batch processor — cannot simply read each other's variables.

IPC is the set of OS-provided mechanisms that allow processes to exchange data, coordinate execution, and signal each other without violating memory isolation. Every IPC mechanism is a controlled exception to that isolation — the OS mediates the exchange, enforcing access control and memory safety that the processes themselves cannot.

The fundamental tension IPC mechanisms navigate:

- **Speed vs isolation:** Shared memory gives near-zero-copy speed but requires processes to synchronise themselves. Sockets are slower (kernel copies, network stack overhead) but provide full serialisation and can span machines.
- **Simplicity vs flexibility:** Pipes are simple (byte stream, two endpoints) but unidirectional and limited to related processes. Sockets are complex but work across networks and between unrelated processes.
- **Persistence vs ephemerality:** A pipe dies when its processes die. A message queue persists in the kernel until explicitly deleted. A socket connection dies when either end closes it.

**Q2. What are the five main IPC mechanisms and their primary use cases?**
A: The five canonical mechanisms, ordered from simplest to most flexible:

| Mechanism | Model | Direction | Scope | Persistence |
|---|---|---|---|---|
| **Pipes** | Byte stream | Unidirectional | Related processes (parent-child) | Lifetime of processes |
| **Named pipes (FIFOs)** | Byte stream | Unidirectional | Any processes on same host | Filesystem entry persists |
| **Message queues** | Discrete messages | Bidirectional | Any processes on same host | Kernel-managed; persists until deleted |
| **Shared memory** | Raw memory region | Read/write | Any processes on same host | Until explicitly unmapped/deleted |
| **Sockets** | Byte stream or datagram | Bidirectional | Same host or network | Connection lifetime |

Signals are sometimes listed as IPC but carry no data payload — only a signal number. Semaphores are a synchronisation primitive rather than a data transfer mechanism. Both are excluded from this guide's scope except where they interact with the above.

**Q3. What does "zero-copy" mean in IPC, and which mechanisms achieve it?**
A: A copy in IPC occurs when data moves from one memory region to another — specifically when the kernel copies data from the sender's address space to the receiver's. Each copy costs CPU time proportional to the data size and pollutes the CPU cache.

**Two copies (typical pipe / socket path):**
```
Sender user space → [copy 1] → Kernel buffer → [copy 2] → Receiver user space
```
The sender writes data into a kernel buffer; the kernel copies it out to the receiver. For small messages (< a few KB), this is negligible. For large data (MB/GB), the copies dominate.

**Zero-copy with shared memory:**
```
Sender writes to shared region → Receiver reads from same physical pages
                (no copy — same physical RAM)
```
The OS maps the same physical pages into both processes' virtual address spaces. No kernel involvement after setup; no copy at all. The sender and receiver access the same bytes.

**Partial zero-copy with `sendfile()` and `splice()`:**
These Linux syscalls move data between kernel buffers (file cache to socket buffer) without copying into user space at all — useful for serving files over HTTP but not for general IPC.

Only shared memory achieves true zero-copy for process-to-process communication. Everything else involves at least one kernel copy. This is the primary reason high-performance systems (databases, video pipelines, financial data feeds) use shared memory for their hottest data paths.

## Section 2: Pipes

**Q4. What is an anonymous pipe, how does it work at the kernel level, and what are its constraints?**
A: An anonymous pipe is a unidirectional, in-kernel byte stream buffer connecting two file descriptors — one for writing (the write end) and one for reading (the read end). It's the oldest and simplest IPC primitive on Unix.

```c
// Kernel-level: pipe creates two file descriptors
int fds[2];
pipe(fds);    // fds[0] = read end, fds[1] = write end

pid_t pid = fork();
if (pid == 0) {
  // Child — reader
  close(fds[1]);                  // close unused write end
  char buf[256];
  ssize_t n = read(fds[0], buf, sizeof(buf));
  // process buf...
  close(fds[0]);
} else {
  // Parent — writer
  close(fds[0]);                  // close unused read end
  write(fds[1], "hello", 5);
  close(fds[1]);                  // closing write end sends EOF to reader
}
```

How it works at the kernel level:
- `pipe(fds)` allocates a kernel buffer (the "pipe buffer") — on Linux, 64KB by default (`/proc/sys/fs/pipe-max-size` allows up to 1MB).
- The write end and read end are two file descriptors referencing this buffer.
- `write(fds[1], data, n)` copies data from user space into the kernel buffer. If the buffer is full, `write` blocks until the reader consumes some data.
- `read(fds[0], buf, n)` copies data from the kernel buffer into user space. If the buffer is empty, `read` blocks until the writer produces data.
- When the last file descriptor referencing the write end is closed, the reader receives EOF (`read` returns 0).

Constraints:
- **Unidirectional** — data flows one way only. Bidirectional communication requires two pipes.
- **Related processes only** — anonymous pipes exist only as file descriptors inherited across `fork()`. Unrelated processes cannot share an anonymous pipe.
- **No message boundaries** — pipes are byte streams. If the writer calls `write(fd, "hello", 5)` and `write(fd, "world", 5)`, the reader may receive `"helloworld"` in one `read` or in multiple partial reads. Application protocol must delimit messages.
- **In-kernel buffer is finite** — writes block when full; the pipe must be drained continuously for the writer to make progress (backpressure).

**Q5. What is a named pipe (FIFO), how does it differ from an anonymous pipe, and when is it the right choice?**
A: A named pipe (FIFO — First In, First Out) is a pipe with a name in the filesystem. Any process that knows the path can open it — not just relatives via `fork()`:

```bash
# Create a FIFO
mkfifo /tmp/payment-events.fifo

# Process A — writer (could be any process)
echo '{"event":"payment.complete","txnId":"txn_001"}' > /tmp/payment-events.fifo

# Process B — reader (a separate process, no ancestry required)
cat /tmp/payment-events.fifo
```

```c
// In C: open a FIFO like a file
int wfd = open("/tmp/payment-events.fifo", O_WRONLY);  // blocks until reader opens
int rfd = open("/tmp/payment-events.fifo", O_RDONLY);  // blocks until writer opens
```

Key difference from anonymous pipes:
- **Named** — accessible by filesystem path; survives across unrelated processes.
- **Rendezvous blocking** — `open()` on a FIFO blocks until both ends are open. The writer's `open(O_WRONLY)` blocks until someone opens the read end, and vice versa. Use `O_NONBLOCK` to open without waiting.
- **Still unidirectional** — same byte stream model; same lack of message boundaries; same kernel buffer limits.
- **Filesystem entry persists** — the FIFO entry remains after both processes disconnect. The FIFO must be manually removed (`unlink`/`rm`).

When FIFOs are the right choice:
- Simple log or event streaming from one producer to one consumer.
- Shell pipeline patterns between processes launched by different parts of a system.
- Legacy Unix tools integration (many CLI tools expect stdin/stdout; FIFOs connect them).

When FIFOs are the wrong choice:
- Multiple producers or consumers — FIFOs serialise all writes, but interleaved writes from multiple producers corrupt messages (no atomicity for writes > `PIPE_BUF` = 4096 bytes on Linux).
- Bidirectional communication — requires two FIFOs.
- High-throughput structured data — no message framing; application must implement its own protocol.

**Q6. How does Node.js use pipes for child process IPC, and what are the backpressure semantics?**
A:

```javascript
// Node.js child_process.spawn with stdio pipes
const { spawn } = require("child_process");

const child = spawn("python3", ["data_processor.py"], {
  stdio: ["pipe", "pipe", "pipe"],   // stdin, stdout, stderr all piped
});

// child.stdin is a Writable stream → the pipe write end
// child.stdout is a Readable stream → the pipe read end
// child.stderr is a Readable stream → the pipe read end

// Write to child's stdin
child.stdin.write(JSON.stringify({ mandates: batchData }));
child.stdin.end();   // signal EOF to child (close write end)

// Stream child's stdout
child.stdout.on("data", (chunk) => {
  // chunk is a Buffer — may be a partial message (pipe is a byte stream)
  accumulated += chunk.toString();
});

child.stdout.on("end", () => {
  const result = JSON.parse(accumulated);
  // ...
});

// Backpressure: if the child produces data faster than Node reads it,
// the pipe buffer fills. Node's stream implementation handles this:
const writable = fs.createWriteStream("output.json");
child.stdout.pipe(writable);   // automatic backpressure — pauses child.stdout
                               // when writable is slow
```

Backpressure in pipes:
- When the kernel pipe buffer (64KB) fills, `write()` in the child process blocks — the child is paused in the OS until Node.js reads from the pipe.
- Node.js `Readable` streams implement backpressure: `.pipe()` automatically calls `.pause()` on the source when the destination's internal buffer exceeds its high-water mark, and `.resume()` when it drains. Without `.pipe()`, reading with `on("data")` puts the stream in flowing mode — it reads as fast as it can, which may overwhelm a slow consumer downstream.
- The `child_process.fork()` IPC channel (accessible via `child.send()` / `process.on("message")`) is a separate serialised message channel built on top of a Unix socket (not a pipe), allowing structured JSON without framing concerns.

## Section 3: Message Queues

**Q7. What is a POSIX message queue, and how does it differ from a pipe?**
A: A POSIX message queue is a kernel-managed queue of discrete, typed messages with built-in priority ordering and message boundary preservation. Unlike a pipe's byte stream, each `mq_send()` call enqueues one message and each `mq_receive()` call dequeues exactly one message — no framing needed:

```c
#include <mqueue.h>

// Create or open a message queue
mqd_t mq = mq_open(
  "/payment-events",        // name — must start with /
  O_CREAT | O_RDWR,
  0644,
  &(struct mq_attr){
    .mq_maxmsg  = 100,      // max messages in queue
    .mq_msgsize = 4096,     // max message size in bytes
  }
);

// Sender
const char *msg = "{\"event\":\"payment.complete\",\"txnId\":\"txn_001\"}";
mq_send(mq, msg, strlen(msg), 5);   // priority 5

// Receiver
char buf[4096];
unsigned int priority;
ssize_t n = mq_receive(mq, buf, sizeof(buf), &priority);
// buf contains exactly one message; priority is 5
// Higher priority messages are delivered first regardless of insertion order

// Cleanup
mq_close(mq);
mq_unlink("/payment-events");   // remove the queue (persists until unlinked)
```

Differences from pipes:

| Dimension | Pipe | POSIX Message Queue |
|---|---|---|
| **Message boundaries** | None (byte stream) | Preserved (discrete messages) |
| **Priority** | FIFO only | Per-message priority |
| **Blocking semantics** | Block on empty read / full write | Same, plus `mq_timedreceive` |
| **Persistence** | Dies with process | Persists until `mq_unlink` |
| **Multiple readers** | One consumer at a time | Multiple consumers supported |
| **Notification** | `select`/`poll`/`epoll` | `mq_notify` — async SIGIO or new thread |
| **Max message size** | Unlimited (streaming) | Fixed at queue creation |

**Q8. What is the difference between POSIX message queues and SysV message queues?**
A: Both provide kernel-managed message queues but with different APIs, namespacing, and persistence models:

**SysV message queues (older, more portable):**
```c
#include <sys/msg.h>

// Create or get a queue by key (numeric, not a name)
key_t key = ftok("/var/myapp/lockfile", 'A');  // derive key from path+id
int msqid = msgget(key, IPC_CREAT | 0644);

struct msgbuf {
  long mtype;     // message type — used for selective receive
  char mtext[4096];
} msg = { .mtype = 1, .mtext = "payload" };

msgsnd(msqid, &msg, strlen(msg.mtext), 0);     // send
msgrcv(msqid, &msg, sizeof(msg.mtext), 1, 0);  // receive type=1 only

msgctl(msqid, IPC_RMID, NULL);  // delete queue
```

**Key differences:**

| Dimension | SysV | POSIX |
|---|---|---|
| **Naming** | Numeric key (`ftok`) | Filesystem path (`/name`) |
| **Typed receive** | Yes — `msgrcv` receives by `mtype` | Priority only; no typed receive |
| **API** | `msgget/msgsnd/msgrcv/msgctl` | `mq_open/mq_send/mq_receive/mq_unlink` |
| **`select`/`poll` support** | No — cannot be used with I/O multiplexing | Yes — `mqd_t` is a file descriptor |
| **Persistence** | Persists across reboots (on some systems) | Kernel-lifetime; disappears on reboot |
| **Visibility** | `ipcs -q` command | `/dev/mqueue` filesystem |

Practical recommendation: POSIX message queues for new code — they integrate with `epoll`/`select`, have cleaner naming, and are easier to inspect (`ls /dev/mqueue`). SysV for legacy systems or when typed receive by message type is specifically needed.

**Q9. How do Redis and RabbitMQ relate to OS-level message queues, and when do you use each?**
A: OS-level message queues (POSIX/SysV) live entirely in the kernel and are bounded by the host — they cannot span machines, have no persistence across reboots (POSIX), no consumer groups, no dead-letter queues, and no monitoring tooling. Redis and RabbitMQ are user-space message brokers that add:

- **Network transparency** — consumers can be on different machines.
- **Durability** — messages persist on disk (RabbitMQ with `durable: true`, Redis with AOF/RDB).
- **Consumer groups** — multiple consumers each get a subset of messages (Kafka-style with Redis Streams, RabbitMQ exchanges + queues).
- **Dead-letter queues** — messages that fail processing N times are routed to a DLQ.
- **Visibility timeout** — SQS / BullMQ pattern: message is "in flight" (invisible to other consumers) during processing; re-enqueued if the consumer crashes.
- **Monitoring** — queue depth, consumer lag, message rates visible in dashboards.

Decision framework:
- **Same-host, same-process lifecycle, no persistence needed:** OS pipe or POSIX message queue. Fastest; no network; zero configuration.
- **Same-host, persistence needed across process restarts:** Redis (on the same host). ~microsecond latency.
- **Cross-host, at-least-once delivery, consumer groups:** RabbitMQ or Redis Streams or BullMQ (Redis-backed).
- **Cross-host, at-least-once, high throughput (millions/sec), replay:** Kafka.
- **Cross-host, managed, serverless-friendly:** AWS SQS / AWS SNS.

For NACH mandate processing: the master process (API server) enqueues mandate jobs to BullMQ (Redis-backed). Worker processes on the same or different hosts dequeue and process mandates. The visibility timeout ensures a crashed worker's mandate is re-processed. The queue depth is monitored — if it grows, more workers are scaled in.

## Section 4: Shared Memory

**Q10. How does shared memory work at the OS level, and what makes it the fastest IPC mechanism?**
A: Shared memory works by mapping the same physical memory frames into the virtual address spaces of two or more processes. After setup, communication is just a memory write and read — no syscalls, no kernel involvement, no copies:

```
Process A virtual space       Physical RAM        Process B virtual space
┌──────────────┐             ┌──────────────┐    ┌──────────────┐
│  ...         │             │              │    │  ...         │
│  shm at 0x7f │────────────▶│  shared      │◀───│  shm at 0x8a │
│  (writable)  │             │  physical    │    │  (writable)  │
│  ...         │             │  pages       │    │  ...         │
└──────────────┘             └──────────────┘    └──────────────┘

Process A writes:  *shmPtr = value;   ← direct store to physical page
Process B reads:   x = *shmPtr;       ← direct load from same physical page
                   (no system call, no copy, no kernel transition)
```

POSIX shared memory setup:

```c
// Process A — creator
int fd = shm_open(
  "/payment-shm",            // name in /dev/shm
  O_CREAT | O_RDWR,
  0600
);
ftruncate(fd, sizeof(SharedPaymentData));

SharedPaymentData *data = mmap(
  NULL,
  sizeof(SharedPaymentData),
  PROT_READ | PROT_WRITE,
  MAP_SHARED,
  fd,
  0
);
close(fd);   // fd no longer needed after mmap

data->txnCount = 0;
data->totalAmount = 0;

// Process B — consumer (separate process, different virtual address)
int fd = shm_open("/payment-shm", O_RDWR, 0);
SharedPaymentData *data = mmap(
  NULL,
  sizeof(SharedPaymentData),
  PROT_READ | PROT_WRITE,
  MAP_SHARED,
  fd,
  0
);
// data->txnCount and data->totalAmount are the same physical bytes as in A
```

Why it's the fastest:
- **No system calls in the hot path** — after `mmap`, reads and writes are pure load/store instructions. A write by Process A is visible to Process B on the next read (with appropriate memory barriers/fences). No `write()`, no `read()`, no kernel mode transition.
- **No copies** — the same physical page is in both caches. On a single machine with cache coherency (MESI protocol on x86), a write by A and read by B only requires a cache-line invalidation, not a memory copy.
- **Bandwidth limited only by memory speed** — for large data (video frames, large lookup tables, financial tick data), shared memory bandwidth approaches DRAM bandwidth (~50 GB/s on modern servers), orders of magnitude faster than pipes or sockets.

**Q11. What synchronisation is required with shared memory, and what happens without it?**
A: Shared memory provides no synchronisation — it's raw memory. Without explicit synchronisation, concurrent reads and writes produce data races: corrupted data, torn reads (reading a partially-written value), and undefined behaviour. Three levels of synchronisation are needed:

**Level 1 — Memory ordering (CPU instruction reordering):**
Modern CPUs reorder loads and stores for performance. A write to `data->amount` followed by a write to `data->ready` may be observed in reverse order by another CPU. Memory barriers enforce ordering:

```c
// Writer
data->amount = 5000;
__atomic_store_n(&data->ready, 1, __ATOMIC_RELEASE);  // release barrier: all prior stores visible before this

// Reader
while (!__atomic_load_n(&data->ready, __ATOMIC_ACQUIRE))
  ;                    // acquire barrier: all subsequent loads see stores before the release
int amount = data->amount;   // guaranteed to see 5000
```

**Level 2 — Mutual exclusion (one writer at a time):**
If multiple processes may write concurrently, a mutex in shared memory (a POSIX process-shared mutex) serialises writes:

```c
// Initialise the mutex in the shared memory region itself
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);  // cross-process
pthread_mutex_init(&data->lock, &attr);

// Writer
pthread_mutex_lock(&data->lock);
data->txnCount++;
data->totalAmount += 5000;
pthread_mutex_unlock(&data->lock);

// Reader
pthread_mutex_lock(&data->lock);
int count = data->txnCount;
pthread_mutex_unlock(&data->lock);
```

**Level 3 — Higher-level coordination (producer-consumer):**
A process-shared semaphore or condition variable signals when new data is available, preventing busy-waiting:

```c
// Semaphore in shared memory — reader waits for writer to signal
sem_t *sem = mmap(NULL, sizeof(sem_t), PROT_READ|PROT_WRITE,
                  MAP_SHARED|MAP_ANONYMOUS, -1, 0);
sem_init(sem, 1, 0);   // pshared=1 for cross-process; initial value 0

// Writer
data->record = newRecord;
sem_post(sem);         // increment semaphore — signals reader

// Reader
sem_wait(sem);         // blocks until semaphore > 0
process(data->record);
```

Without any synchronisation: data races produce corrupted values (torn 64-bit integer reads on non-atomic platforms), infinite loops (a loop condition based on a flag that the CPU never sees update because it's cached in a register), and non-reproducible bugs (the race window may be microseconds wide — the bug only manifests under load).

**Q12. How does `SharedArrayBuffer` in Node.js worker threads relate to OS-level shared memory?**
A: `SharedArrayBuffer` is Node.js/browser's mechanism for sharing memory between JavaScript worker threads within the same process. It maps directly to OS-level shared memory concepts but operates within V8's heap management rather than via `shm_open`:

```javascript
// Main thread — creates the shared buffer
const sharedBuffer = new SharedArrayBuffer(4 * 1024);  // 4KB
const int32View   = new Int32Array(sharedBuffer);

// Pass to worker thread
const worker = new Worker("./worker.js", {
  workerData: { sharedBuffer },
});

// In worker.js — receives the same physical pages
const { workerData } = require("worker_threads");
const int32View = new Int32Array(workerData.sharedBuffer);

// Synchronisation with Atomics — required; same memory ordering problem as C
Atomics.store(int32View, 0, 5000);    // atomic store — release semantics
Atomics.notify(int32View, 0, 1);      // wake one waiter

// Main thread — waiting for worker
Atomics.wait(int32View, 0, 0);        // block until index 0 != 0
const amount = Atomics.load(int32View, 0);  // acquire semantics
```

The `Atomics` API is JavaScript's equivalent of `__atomic_store_n` / `__atomic_load_n` — it provides the same store-release / load-acquire semantics, and `Atomics.wait` / `Atomics.notify` are equivalent to a futex (fast userspace mutex) — sleeping without busy-waiting.

Key difference from OS shared memory: `SharedArrayBuffer` only works within the same Node.js process (between threads created by `worker_threads`). For cross-process sharing in Node.js, you need a native addon using `shm_open` + `mmap`, or an external medium (Redis, files).

Security note: `SharedArrayBuffer` was disabled in browsers in 2018 and selectively re-enabled because it enables high-resolution timing attacks (Spectre/Meltdown). It's safe in Node.js worker threads (same process, same trust level) but requires `Cross-Origin-Opener-Policy` headers in browsers.

## Section 5: Sockets

**Q13. What is a Unix domain socket, and how does it differ from a TCP socket on localhost?**
A: A Unix domain socket (UDS, also called a Unix socket or local socket) is a socket whose address is a filesystem path rather than an IP address and port. It provides the same `connect/accept/send/recv` API as TCP but communicates entirely through the kernel without the network stack:

```javascript
// Node.js Unix domain socket server
const net = require("net");

const server = net.createServer((socket) => {
  socket.on("data", (data) => {
    const request = JSON.parse(data);
    socket.write(JSON.stringify({ result: process(request) }));
  });
});

server.listen("/var/run/payment-service.sock");  // filesystem path, not port

// Client (separate Node.js process or any Unix process)
const client = net.createConnection("/var/run/payment-service.sock");
client.write(JSON.stringify({ txnId: "txn_001" }));
client.on("data", (response) => {
  console.log(JSON.parse(response));
});
```

Unix socket vs TCP localhost (`127.0.0.1`):

| Dimension | Unix Domain Socket | TCP Localhost |
|---|---|---|
| **Network stack** | Bypassed entirely | Full TCP/IP stack (with loopback) |
| **Latency** | ~5–10 µs | ~15–50 µs |
| **Throughput** | ~40% higher for small messages | Baseline |
| **Authentication** | OS file permissions + `SO_PEERCRED` | None (any process can connect) |
| **Kernel copies** | 2 (send buffer → recv buffer) | 2 + TCP header processing |
| **Portability** | Same host only | Works across network |
| **Credential passing** | Yes (`SCM_RIGHTS`, `SCM_CREDENTIALS`) | No |
| **Visible in tools** | `ls /var/run/*.sock` | `netstat`, `ss` |

When to use Unix sockets: communication between processes on the same host where latency matters and portability across hosts is not required. Canonical examples: PostgreSQL (`/var/run/postgresql/.s.PGSQL.5432`), Redis (`/var/run/redis/redis.sock`), Nginx upstream to Node.js, Docker daemon API, Node.js cluster IPC, PM2 process communication.

When to use TCP localhost: when the service must also be reachable from remote hosts (same config for local and remote), when the client is a language or framework that doesn't support Unix sockets, or in containers where the socket path isn't shared.

**Q14. What is `SO_PEERCRED`, and why does it matter for IPC security?**
A: `SO_PEERCRED` is a Unix socket option that lets the receiving process retrieve the PID, UID (user ID), and GID (group ID) of the process on the other end of the connection — without any application-level authentication:

```c
// Server: get credentials of the connected client
struct ucred cred;
socklen_t len = sizeof(cred);
getsockopt(clientFd, SOL_SOCKET, SO_PEERCRED, &cred, &len);

printf("Connected process: PID=%d, UID=%d, GID=%d\n",
       cred.pid, cred.uid, cred.gid);

// Authorisation: only allow connections from root or specific UID
if (cred.uid != 0 && cred.uid != ALLOWED_UID) {
  close(clientFd);  // reject
}
```

In Node.js (requires a native addon or child process with the correct privileges, or via the `unix-dgram` npm package):

```javascript
// Node.js doesn't expose SO_PEERCRED in the standard net module
// but pg (PostgreSQL client) uses it transparently when connecting via Unix socket:
const { Client } = require("pg");
const client = new Client({
  host: "/var/run/postgresql",  // Unix socket path
  // No password needed — peer authentication: PostgreSQL verifies the OS UID
  // matches the database user via SO_PEERCRED
});
```

This is "peer authentication" in PostgreSQL — the DB checks that the OS user connecting via the Unix socket matches the database user being requested. No password is exchanged; the kernel vouches for the client's identity.

`SCM_RIGHTS` (ancillary data) is the complementary mechanism — it allows passing open file descriptors from one process to another through a Unix socket. This is how `systemd` passes pre-opened listening sockets to services (socket activation), and how some privilege-separated designs pass a sensitive file descriptor from a privileged process to a sandboxed one without ever exposing the file path to the sandboxed process.

**Q15. Walk through the full lifecycle of a TCP socket from `bind` to `close`, and explain what happens in the kernel at each step.**
A:

```
Server side                              Client side
──────────────────                       ──────────────────
socket()                                 socket()
  ↓ creates socket fd                      ↓ creates socket fd
bind(ip, port)
  ↓ reserves port in kernel
listen(backlog)
  ↓ kernel allocates:
    - SYN queue (incomplete connections)
    - Accept queue (completed connections)
                                         connect(server_ip, port)
                                           ↓ kernel sends SYN
                  ← SYN ──────────────────
  ↓ kernel adds to SYN queue
  ↓ kernel sends SYN-ACK ─────────────────→
                                           ↓ receives SYN-ACK
                                           ↓ kernel sends ACK, completes connect()
                  ← ACK ──────────────────
  ↓ kernel moves to Accept queue
accept()
  ↓ dequeues one completed connection
  ↓ returns new fd for this connection
send/recv data
  ↓ kernel buffers data in:               ↓ kernel buffers data in:
    - TCP send buffer (per socket)           - TCP send buffer
    - TCP recv buffer (per socket)           - TCP recv buffer
  ↓ retransmission if no ACK               ↓ ACK sent on receipt
close()
  ↓ FIN sent ─────────────────────────────→
                                           ↓ FIN received, ACK sent
                                           ↓ close() → FIN sent
  ← FIN ──────────────────────────────────
  ↓ ACK sent
  ↓ TIME_WAIT (2×MSL = ~60-120s)
     (prevents old packets from being confused with new connections)
```

Key kernel data structures:
- **Socket buffer (sk_buff):** data in flight is stored in per-socket receive and send buffers in the kernel. `setsockopt(SO_RCVBUF, SO_SNDBUF)` tunes their sizes. If the receive buffer fills (reader isn't consuming), the kernel shrinks the TCP receive window in ACKs — telling the sender to slow down (TCP flow control).
- **SYN queue and Accept queue:** The SYN queue holds half-open connections (SYN received, SYN-ACK sent, awaiting client ACK). The Accept queue holds fully established connections waiting for `accept()`. The `listen(backlog)` argument caps the Accept queue. A SYN flood attack exhausts the SYN queue — SYN cookies mitigate this.
- **TIME_WAIT:** After `close()`, the active closer waits 2×MSL (Maximum Segment Lifetime) before releasing the port, ensuring delayed packets from the old connection don't corrupt a new connection on the same port. This is why a server that crashes and restarts immediately gets `EADDRINUSE` — the port is in TIME_WAIT. Fix: `SO_REUSEADDR` before `bind()`.

**Q16. What is the difference between stream sockets (SOCK_STREAM) and datagram sockets (SOCK_DGRAM) for IPC?**
A:

**SOCK_STREAM (TCP or Unix stream):**
- Connection-oriented — explicit `connect`/`accept` handshake.
- Reliable, ordered delivery — the kernel retransmits lost packets (for TCP); delivery is guaranteed.
- Byte stream — no message boundaries. Application must frame messages.
- Bidirectional on the same connection.
- Use for: persistent connections carrying structured data (HTTP, database protocol, JSON-RPC).

**SOCK_DGRAM (UDP or Unix datagram):**
- Connectionless — `sendto` specifies destination per message; no handshake.
- No guaranteed delivery for UDP (packets may be lost, reordered). Unix domain datagrams are reliable within the same host.
- **Message boundaries preserved** — each `sendto` produces exactly one `recvfrom`. Unlike pipes or stream sockets, if you send 100-byte and 200-byte messages, you receive a 100-byte and a 200-byte message — never merged.
- For UDP: no ordering guarantee; no flow control.
- Use for: low-latency telemetry where some loss is acceptable (metrics, logging), DNS, NTP; within a host: event notification where loss on message queue overflow is acceptable.

```javascript
// Node.js UDP datagram socket for metrics (fire-and-forget)
const dgram = require("dgram");
const client = dgram.createSocket("udp4");

function emitMetric(name, value) {
  const msg = Buffer.from(`${name}:${value}|g`);   // StatsD format
  client.send(msg, 8125, "127.0.0.1");             // no callback needed — fire-and-forget
}

// If the StatsD server is down, the UDP packet is silently lost — acceptable for metrics
emitMetric("payment.latency_ms", 145);
```

```javascript
// Unix datagram socket — message boundaries + fast local IPC
const dgram = require("dgram");
const server = dgram.createSocket("unix_dgram");

server.on("message", (msg, rinfo) => {
  // msg is exactly one message — no framing needed
  const event = JSON.parse(msg);
  processEvent(event);
});

server.bind("/var/run/events.sock");
```

## Section 6: Choosing and Combining IPC Mechanisms

**Q17. How do you decide which IPC mechanism to use given a set of requirements?**
A: Work through five dimensions:

**1. Same host or cross-host?**
- Cross-host → TCP sockets or a message broker (Redis, RabbitMQ, Kafka). All other mechanisms are host-local.
- Same host → evaluate the remaining dimensions.

**2. What is the data volume and latency requirement?**
- Large data (MB+), sub-millisecond latency → shared memory. No other mechanism competes.
- Small messages, microsecond latency → Unix domain socket or POSIX message queue.
- Small messages, millisecond latency acceptable → TCP localhost or named pipe.

**3. Are message boundaries important?**
- Message boundaries needed → POSIX message queue, datagram socket, or a framing protocol over a stream (length-prefix, newline delimited).
- Byte stream acceptable → pipe or stream socket.

**4. Do you need persistence across process restarts?**
- Yes → Redis / RabbitMQ / Kafka / SQS. POSIX message queues persist until `mq_unlink` (kernel lifetime, not disk). SysV queues can survive reboot on some systems.
- No → pipe, socket, POSIX message queue.

**5. Are the processes related (parent-child)?**
- Yes → anonymous pipe is simplest (`child_process.spawn` in Node.js).
- No → named pipe, Unix socket, message queue, shared memory.

Decision tree for the most common backend scenarios:

```
Need to pass data between Node.js child_process and parent?
  → Anonymous pipe (child_process.spawn stdio)

Need structured message passing between Node.js worker threads?
  → SharedArrayBuffer + Atomics for shared state
  → worker.postMessage() for structured messages (copies, not shared)

Need fast local IPC between Node.js processes (cluster workers to a shared service)?
  → Unix domain socket

Node.js process to database (PostgreSQL, Redis) on same host?
  → Unix domain socket (pg, ioredis support this)

High-throughput event queue between microservices on the same host?
  → Redis Streams (BullMQ) — persistence + monitoring
  → POSIX message queue if Redis is unavailable and no persistence needed

Cross-service IPC across hosts?
  → TCP socket (raw) or HTTP/gRPC
  → Redis / RabbitMQ / SQS for async queue

Sub-millisecond, high-throughput data sharing (financial tick data, video frames)?
  → Shared memory + POSIX semaphore for synchronisation
```

**Q18. How does Node.js `cluster` use IPC internally, and what are the performance implications?**
A: The `cluster` module forks worker processes and establishes an IPC channel between the master and each worker. The IPC channel is implemented as a Unix domain socket pair — not a pipe — because it needs to support `sendmsg` with ancillary data (`SCM_RIGHTS`) for passing file descriptors:

```javascript
// Master process
const cluster = require("cluster");
const os      = require("os");

if (cluster.isMaster) {
  for (let i = 0; i < os.cpus().length; i++) {
    const worker = cluster.fork();

    // Send a message to a specific worker
    worker.send({ type: "config", value: { rateLimit: 100 } });

    worker.on("message", (msg) => {
      if (msg.type === "metric") {
        aggregateMetric(msg.name, msg.value);
      }
    });
  }
} else {
  // Worker process
  process.on("message", (msg) => {
    if (msg.type === "config") applyConfig(msg.value);
  });

  // Report metrics to master
  setInterval(() => {
    process.send({ type: "metric", name: "req_count", value: requestCount });
  }, 5000);

  require("http").createServer(handleRequest).listen(3000);
  // The cluster module distributes connections via the master's listening socket
  // using the socket passing mechanism (SCM_RIGHTS over the IPC channel)
}
```

How incoming connections are distributed in cluster mode:
- The master process calls `listen()` and holds the listening socket.
- When a connection arrives, the master passes the connected socket file descriptor to a worker via the IPC channel using `sendmsg(SCM_RIGHTS)` — the actual file descriptor (not its content) is transferred.
- The worker receives the fd and calls `accept()` (or just reads/writes directly).
- This is load balancing via fd passing — no data is copied; the kernel transfers descriptor ownership.

Performance implications:
- `worker.send()` / `process.send()` serialises messages as JSON and writes to the Unix socket. This is fast for small messages but expensive for large payloads (serialisation cost + copy).
- The IPC channel is not suitable for high-frequency, high-volume data (e.g., sharing a 10MB lookup table between workers). For that, use a file-backed shared memory region or a Redis cache.
- Each `process.send()` crosses into the kernel (Unix socket write syscall) — fine for occasional config updates or metric reporting, not for per-request data sharing.

**Q19. How does PostgreSQL use multiple IPC mechanisms together?**
A: PostgreSQL is an instructive real-world example of layered IPC — it uses different mechanisms for different communication needs within the same system:

**Shared memory — buffer pool:**
The PostgreSQL shared buffer pool (default 128MB, configurable via `shared_buffers`) is a POSIX shared memory region. All backend processes (one per client connection) access the same buffer pool — reading cached data pages without any copy. A backend that needs page 42 of table `payments` reads directly from the shared buffer, not from disk.

**POSIX semaphores — buffer pool locking:**
Concurrent access to the buffer pool is protected by lightweight spinlocks and POSIX semaphores (one per buffer). A backend acquiring a buffer for a dirty write takes the lock, modifies the page, marks it dirty, releases the lock. Semaphores in shared memory, initialised with `PTHREAD_PROCESS_SHARED`, provide this synchronisation.

**Unix domain socket — client connections:**
Client applications (Node.js `pg`, psql) connect to PostgreSQL via a Unix domain socket (`/var/run/postgresql/.s.PGSQL.5432`). Peer authentication (`SO_PEERCRED`) allows password-free connection for local users whose OS username matches their PostgreSQL username.

**TCP socket — remote client connections:**
Remote connections (from application servers on different hosts) use TCP sockets (`postgresql.conf: listen_addresses = '*'`, port 5432).

**Pipes — postmaster to backend process:**
The postmaster (master process) creates backend processes via `fork()`. The `postmaster_alive_flags` uses a pipe to detect if the postmaster has died — backends exit cleanly when the postmaster's write end of the pipe is closed.

**Signals — backend coordination:**
`SIGHUP` tells all backend processes to reload `postgresql.conf`. `SIGUSR1`/`SIGUSR2` are used internally for lightweight signalling between processes (e.g., wakeup the WAL writer). These carry no data; they're pure event notifications.

This layered design is the canonical pattern: shared memory for hot data, semaphores for synchronisation, sockets for external communication, pipes for process lifecycle management, signals for lightweight events.

**API Server ↔ Redis (BullMQ):** Unix domain socket. The `ioredis` client connects via `/var/run/redis/redis.sock` — 40% lower latency than TCP for the high-frequency job enqueueing. Each payment initiation enqueues a mandate job.

**Mandate Processor ↔ Redis:** Same Unix socket connection. Workers dequeue mandate jobs via BullMQ's visibility timeout — a crashed worker's job reappears after `lockDuration` (e.g., 30 seconds) and is re-processed.

**Q21. "A Node.js service's `child_process.fork()` workers are consuming 4GB of memory total, even though each worker only uses 200MB of live data. What IPC-related change could reduce this, and what are the tradeoffs?"**
A: The root cause is that `fork()` creates separate address spaces — each worker has its own V8 heap. Even with copy-on-write, pages that are written to by the GC (mark bits in object headers, updated free lists) are copied to each worker. A 200MB heap with 500MB of module-level data (cached payment schemas, routing tables, in-memory rate-limit state) means each worker needs ~500MB RSS.

**Option 1 — Shared memory for read-only lookup data:**
Move immutable data (routing tables, bank IFSC lookup, PAN regex patterns) into a shared memory region loaded once by the master before `fork()`. Workers read from shared memory — CoW means these pages are never copied as long as workers only read:

```javascript
// Master: load large lookup table before forking
const shm = require("./shm-addon");   // native addon using shm_open + mmap
const IfscTable = shm.loadReadOnly("/dev/shm/ifsc-table", ifscData);

// fork workers — workers inherit the mapping, CoW; pages never dirtied
for (let i = 0; i < numCPUs; i++) cluster.fork();

// Workers: read from the shared mapping via the addon
const ifscDetails = IfscTable.lookup("HDFC0001234");   // zero-copy read
```

Tradeoff: requires a native addon; shared memory must be explicitly managed (size, lifecycle); workers cannot write to it without synchronisation.

**Option 2 — Redis for shared mutable state:**
Move per-worker state (rate-limit counters, session caches, deduplication sets) out of each worker's heap and into Redis. Each worker holds only the live request state:

```javascript
// Before: each worker caches rate-limit state in memory — 50MB per worker × 8 = 400MB
const rateLimitCache = new Map();

// After: Redis holds state — one copy, shared by all workers
const rateKey = `rate:${userId}:${Math.floor(Date.now() / 60_000)}`;
const count = await redis.incr(rateKey);   // atomic — no race between workers
```

Tradeoff: Redis round-trip (~0.1ms via Unix socket) per rate-limit check; Redis becomes a dependency. For hot paths called thousands of times per second, the latency adds up.

**Option 3 — Worker threads instead of worker processes:**
Switch from `cluster` (separate processes) to `worker_threads` (same process, shared heap). All threads share the same V8 heap — the lookup tables are loaded once:

```javascript
const { Worker, isMainThread, workerData } = require("worker_threads");
// All workers share the same module cache — lookup tables loaded once
// Total memory: 500MB (shared) + 200MB per thread (thread-local) × 8 = 2.1GB → much less
```

Tradeoff: no fault isolation — a crash in one thread kills all threads and the entire process. A segfault in a native addon crashes the server rather than one worker. Appropriate for CPU-bound work (mandate processing calculations) where crash isolation is less critical; not appropriate for the internet-facing API handler.

The right answer at 5 YOE level: use a combination — `cluster` for the API server (fault isolation, one process per core), Redis for shared mutable state, and a pre-fork shared memory mapping for large immutable lookup tables. Don't reach for `worker_threads` as a memory optimisation unless fault isolation is explicitly acceptable.

**Q22. "A Unix socket IPC channel between two processes is occasionally blocking for 500ms under load. Walk through the possible causes."**
A: A Unix socket `write()` or `send()` blocking means the socket's send buffer is full — the receiver isn't reading fast enough. Five layers to investigate:

**1. Receiver-side processing speed:**
The receiver's event loop is overloaded — it has data in the socket receive buffer but isn't calling `read()` / `recv()` frequently enough. In Node.js, if the receiver is doing synchronous CPU work between event loop iterations, new socket data accumulates in the kernel receive buffer. When the buffer fills, the kernel starts refusing new data → sender's socket send buffer fills → `write()` blocks.

Diagnosis: measure event loop lag (`perf_hooks.monitorEventLoopDelay()`) on the receiver. If p99 lag is > 50ms, the event loop is overloaded.

**2. Socket buffer size:**
Default socket buffer sizes on Linux: `SO_SNDBUF` = 212KB, `SO_RCVBUF` = 212KB (actual values depend on `net.core.wmem_default`). If message bursts exceed this, the sender blocks even if the receiver is fast on average.

Diagnosis: `ss -x` (Unix sockets) — look at `Send-Q` (bytes waiting in kernel send buffer). If consistently near the buffer max, increase buffer size:
```javascript
const client = net.createConnection("/var/run/service.sock");
client.socket.setSendBufferSize(1024 * 1024);  // 1MB send buffer
```

**3. Nagle's algorithm (TCP only, not Unix sockets):**
Unix domain sockets don't have Nagle's algorithm — this cause applies only to TCP. For Unix sockets, small messages are sent immediately.

**4. Thundering herd on the receiver:**
Multiple writers burst simultaneously at the same moment. The receiver's accept queue or read queue fills. Use `SO_REUSEPORT` on the receiver socket to distribute connections across multiple receiver threads/processes.

**5. Writer too fast for message protocol:**
If the writer sends large JSON blobs per message and the receiver parses them synchronously (blocking the event loop), the parse time creates back-pressure that propagates to the sender. Switch to binary protocol (msgpack, Protocol Buffers) to reduce parse time, or move message parsing to a worker thread.

**Fix pattern:** First instrument (event loop lag, socket buffer fill rate, message size distribution). Then address the bottleneck: if the receiver is CPU-bound, add worker threads for processing; if the buffer is small, increase it; if message size is large, compress or switch protocol.

## Quick Reference: IPC Mechanism Summary

```
Anonymous Pipe
  socket():        pipe(fds)
  Node.js:         child_process.spawn stdio
  Direction:       Unidirectional
  Boundary:        None (byte stream)
  Max throughput:  ~4–8 GB/s (kernel buffer)
  Scope:           Parent-child only
  Key limit:       64KB kernel buffer default

Named Pipe (FIFO)
  socket():        mkfifo("/path")
  Node.js:         fs.createReadStream("/tmp/fifo")
  Direction:       Unidirectional
  Boundary:        None (byte stream)
  Scope:           Same host, any processes
  Key limit:       Single producer for atomic writes

POSIX Message Queue
  socket():        mq_open("/name", ...)
  Node.js:         Native addon (no stdlib support)
  Direction:       Bidirectional (separate send/recv)
  Boundary:        Preserved (discrete messages)
  Priority:        Yes (per-message)
  Persistence:     Kernel lifetime
  Key limit:       Fixed max message size at creation

Shared Memory
  socket():        shm_open("/name") + mmap(MAP_SHARED)
  Node.js:         worker_threads SharedArrayBuffer (intra-process)
                   Native addon (inter-process)
  Direction:       Read/write (requires synchronisation)
  Boundary:        None (raw memory)
  Throughput:      Memory bandwidth (~50 GB/s)
  Key limit:       Requires explicit synchronisation (mutex/semaphore)

Unix Domain Socket
  socket():        socket(AF_UNIX, SOCK_STREAM, 0)
  Node.js:         net.createServer() / net.createConnection() with path
  Direction:       Bidirectional
  Boundary:        None for STREAM; preserved for DGRAM
  Latency:         ~5–10 µs
  Key feature:     SO_PEERCRED, SCM_RIGHTS (fd passing)
  Scope:           Same host

TCP Socket (localhost)
  socket():        socket(AF_INET, SOCK_STREAM, 0)
  Node.js:         net.createServer() / net.createConnection() with port
  Direction:       Bidirectional
  Latency:         ~15–50 µs
  Key feature:     Works cross-host; full TCP semantics
  Scope:           Same or different host
```
