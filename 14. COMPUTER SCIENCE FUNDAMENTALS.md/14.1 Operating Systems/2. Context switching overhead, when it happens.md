# Context Switching: Overhead & When It Happens — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a context switch, and what exactly does the OS save and restore during one?**
A: A context switch is the act of the operating system pausing one execution unit (a process or thread), saving its complete execution state, and restoring the saved state of another execution unit so it can resume running as if it was never paused. The CPU itself has no memory of "which program it is running" — it simply executes whatever instructions are pointed to by the instruction pointer. The OS is entirely responsible for the illusion of simultaneous execution.

What the OS saves and restores (the "context"):
- **CPU registers** — general-purpose registers (rax, rbx, … on x86-64), the instruction pointer (rip — where execution resumes), the stack pointer (rsp), the base pointer (rbp), and the flags register (condition codes from the last arithmetic operation).
- **Program counter** — the address of the next instruction to execute, which is part of rip on x86-64.
- **Stack pointer** — points to the top of the current thread's stack; each thread has its own stack.
- **Memory mapping (for process switches)** — the page table base register (CR3 on x86-64) is updated to point to the incoming process's virtual address space. This is the expensive part of a process context switch — it requires a TLB flush.
- **Floating-point and SIMD state** — the x87 FPU, SSE, and AVX register sets, if the thread used them.
- **Kernel state** — open file descriptor table references, signal masks, scheduling metadata.

Thread switches within the same process are cheaper than process switches because the page table (and therefore the TLB) doesn't change — threads share the same virtual address space.

**Q2. What is the difference between a voluntary and an involuntary context switch?**
A: The distinction determines *why* the switch happened and is tracked separately by the OS:

- **Voluntary context switch (vcsw)** — the running thread explicitly gives up the CPU before its time slice expires. This happens when the thread calls a blocking system call: `read()`, `write()`, `sleep()`, `wait()`, `recv()`, `futex_wait()`. The thread cannot proceed until the blocking condition resolves (data arrives, lock is released, timer fires), so it yields. Voluntary switches are expected and largely unavoidable in I/O-driven code — they are the mechanism by which the OS efficiently multiplexes the CPU while threads wait for slow resources.

- **Involuntary context switch (ivcsw)** — the OS preempts the running thread against its will, typically because its time quantum expired, a higher-priority thread became runnable, or a hardware interrupt required servicing. The thread was making progress and had more work to do, but the scheduler decided another thread should run instead. Involuntary switches are the ones that hurt performance — they interrupt computation mid-stream, potentially evicting hot data from caches.

Tools that expose this distinction: `getrusage()` in C returns `ru_nvcsw` and `ru_nivcsw`; `/proc/<pid>/status` shows `voluntary_ctxt_switches` and `nonvoluntary_ctxt_switches`; `perf stat` reports both.

**Q3. What is the direct CPU cost of a context switch, and what are the indirect costs that dwarf it?**
A: The direct cost — saving registers, updating the scheduler's data structures, restoring another thread's registers — is roughly **1–10 microseconds** on a modern x86-64 system. This is measurable but rarely the dominant cost.

The indirect costs are where real performance losses happen:

- **TLB invalidation (for process switches)** — the Translation Lookaside Buffer is a hardware cache of virtual-to-physical address translations. A process switch requires flushing the TLB (or tagging entries with an Address Space ID, ASID, on architectures that support it). After the switch, the incoming process pays a burst of TLB misses as it touches memory — each miss is a page table walk costing hundreds of nanoseconds.
- **CPU cache displacement** — L1 and L2 caches are small (32KB–256KB and 256KB–4MB typically). If the outgoing thread's working set occupied those caches, the incoming thread evicts it and the outgoing thread, when it resumes, must reload its data from L3 or main memory. This "cache thrashing" can cost milliseconds in aggregate for data-intensive workloads.
- **Branch predictor pollution** — the CPU's branch predictor and instruction cache are trained on the outgoing thread's code. After a switch, the predictor mispredicts more often for the incoming thread until it re-trains, adding pipeline stalls.
- **Pipeline flush** — the instruction pipeline (fetch, decode, execute stages) must be drained and refilled. On a deep out-of-order pipeline, this is tens of cycles.

The indirect costs mean that a process doing 10,000 context switches per second doesn't pay 10ms (10,000 × 1µs) — it pays far more because cache and TLB effects compound across every switch. This is why profiling tools report context switch *count* as a performance signal, not just total switch time.

**Q4. When does the operating system decide to perform a context switch?**
A: Context switches happen at several distinct trigger points:

- **System call that blocks** — the most common trigger. When a thread calls `read()` on a socket with no data, `futex_wait()` on a contested lock, or `nanosleep()`, the kernel moves the thread from "running" to "waiting" and picks another thread to run. The switch is synchronous with the blocking call.
- **Timer interrupt (preemption)** — the hardware timer fires at a regular interval (typically 250Hz–1000Hz on Linux, configurable via `CONFIG_HZ`). The interrupt handler checks whether the current thread has exhausted its time quantum. If so, the thread is preempted and another thread from the run queue is selected. This is the primary mechanism for fairness between CPU-bound threads.
- **Higher-priority thread becomes runnable** — when a sleeping thread is woken (its I/O completes, its mutex is released), the scheduler compares its priority to the currently running thread. If the woken thread has higher priority, the running thread is preempted immediately. This is the basis for real-time responsiveness.
- **Hardware interrupt** — a hardware event (network packet arrives, disk I/O completes, keyboard input) fires an interrupt, which runs an interrupt service routine (ISR) in kernel context. The ISR may wake a sleeping thread, triggering a scheduler evaluation.
- **Explicit yield** — a thread calls `sched_yield()` or `pthread_yield()`, voluntarily giving up the CPU. Rare in application code but used in spin-lock implementations and cooperative schedulers.
- **`SIGSTOP` / `SIGCONT`** — signals that stop and resume processes, effectively forcing a context switch.

**Q5. What is a thread, and why are thread context switches cheaper than process context switches?**
A: A thread is an execution unit within a process — it has its own stack, registers, and program counter, but shares the process's virtual address space, file descriptor table, and heap with all other threads in the same process.

Thread context switches within a process are cheaper because:
- **No TLB flush** — all threads share the same page table (same CR3 register value). Switching between threads in the same process does not invalidate TLB entries — the virtual-to-physical mappings remain valid. This eliminates the costliest indirect expense of a process switch.
- **Shared address space** — code, heap, and shared data segment are already mapped in the same virtual address space. Cache lines holding shared data remain valid after the switch.
- **Smaller register save/restore** — the kernel saves and restores fewer privilege-mode registers because the memory management context is unchanged.

That said, thread switches are not free. Stack data and thread-local registers still evict cache lines. If two threads have non-overlapping working sets (thread A does matrix math, thread B does string parsing), each switch still causes a burst of cache misses as the incoming thread's data is loaded.

The rough cost hierarchy: goroutine/green thread switch (sub-microsecond, user-space only) < OS thread switch within process (1–5µs) < process switch (5–50µs, depends on TLB flush strategy and address space size).

## Section 2: Context Switching in the Linux Scheduler

**Q6. How does the Linux CFS (Completely Fair Scheduler) decide when and to whom to context switch?**
A: The Completely Fair Scheduler (CFS), the default Linux scheduler since kernel 2.6.23, models CPU time as a shared resource and tries to give every runnable thread an equal share over time. Its mechanism:

- **Virtual runtime (`vruntime`)** — each thread has a `vruntime` counter that tracks how much CPU time it has consumed, weighted by priority (nice value). Lower nice value = higher priority = `vruntime` increases more slowly per real-time unit.
- **Red-black tree** — runnable threads are stored in a red-black tree keyed by `vruntime`. The leftmost node (lowest `vruntime`) is always the thread that has received the least CPU time and is the next to run.
- **Preemption point** — when a thread's `vruntime` exceeds the `vruntime` of the leftmost node by more than `sysctl_sched_latency_ns` (default ~6ms), it is preempted. The scheduler picks the leftmost node to run next.
- **Wakeup preemption** — when a sleeping thread wakes, CFS checks if its `vruntime` is lower than the currently running thread's. If so, the running thread is preempted in favour of the woken thread (`wakeup_preempt_entity`).

The result: CFS doesn't use fixed time quanta in the traditional sense. Instead, preemption happens at the boundary where fairness is violated — when one thread has significantly more CPU time than another. Threads that voluntarily yield (by blocking on I/O) accumulate less `vruntime` and are preferentially scheduled when they wake, giving I/O-bound threads naturally responsive scheduling without priority inversion.

**Q7. What is the difference between kernel threads, user threads, and green threads/goroutines in terms of context switching cost?**
A:

| Thread type | Scheduled by | Context switch mechanism | Relative cost |
|--|--|--|--|
| **Kernel thread (OS thread)** | OS kernel | Full kernel context switch — register save/restore, possible TLB flush | 1–10µs |
| **User thread (1:1 model, e.g. pthreads)** | OS kernel (1 kernel thread per user thread) | Same as kernel thread | 1–10µs |
| **Green thread / goroutine** | Language runtime (M:N model) | User-space register save/restore only; no kernel involvement unless blocking syscall | 100–300ns |
| **Async task (JavaScript event loop, Python asyncio)** | Runtime event loop | Stack frame swap only; cooperatively scheduled | ~50–100ns |

**Green threads / goroutines (Go)** maintain their own small stacks (starting at 2–8KB, growing as needed) and are multiplexed by the runtime onto a fixed pool of OS threads (GOMAXPROCS). Switching between goroutines that are both runnable on the same OS thread is entirely in user space — no `syscall`, no kernel involvement, no privilege mode change. Cost is essentially a function call. The switch only reaches the kernel when a goroutine makes a blocking system call (file I/O, network) — in which case the Go runtime parks the goroutine and hands the OS thread to another runnable goroutine.

**Async/await (Node.js, Python asyncio)** goes further: there is no stack to save. Each coroutine suspends at an `await` point by returning control to the event loop, which picks the next ready task. The "switch" is a function return followed by a function call — essentially free in CPU terms. The tradeoff: async coroutines must never block (a blocking call stalls the entire event loop), and the programming model requires explicit `await` at every suspension point.

**Q8. How does the Linux kernel distinguish between a voluntary and involuntary switch at the scheduler level?**
A: The kernel tracks the distinction via the `schedule()` function's call site. When a thread voluntarily gives up the CPU, it calls `schedule()` with its state already set to `TASK_INTERRUPTIBLE` or `TASK_UNINTERRUPTIBLE` (blocking states). The scheduler sees the thread is not runnable, increments `task_struct->nvcsw` (voluntary switch count), and picks the next thread.

When a thread is preempted by the timer interrupt or by a higher-priority wakeup, the scheduler runs with the outgoing thread still in `TASK_RUNNING` state — it is runnable but being preempted. In this case the scheduler increments `task_struct->nivcsw` (involuntary switch count) and the thread remains on the run queue to be rescheduled later.

These counters are exposed to user space via:
```bash
# Per-process counters
cat /proc/$(pidof node)/status | grep ctxt_switches
# voluntary_ctxt_switches:    1842
# nonvoluntary_ctxt_switches:   47

# Per-process, per-thread in detail
cat /proc/$(pidof node)/task/*/status | grep ctxt_switches

# System-wide context switch rate
vmstat 1
# cs column: context switches per second

# With perf
perf stat -p <pid> sleep 5
# context-switches: voluntary + involuntary combined
# cpu-migrations: switches to a different CPU core
```

A high `nonvoluntary_ctxt_switches` count relative to `voluntary_ctxt_switches` is a sign that a thread is frequently preempted — it is CPU-bound and fighting with other threads for time. A high `voluntary_ctxt_switches` count is expected for I/O-bound processes and is not inherently a problem.

## Section 3: Context Switching in Application Runtimes

**Q9. How does Node.js avoid context switching overhead, and what is the cost of that design?**
A: Node.js runs JavaScript on a single OS thread using an event loop backed by libuv. There are no context switches between JavaScript execution units — the event loop sequentially calls callbacks, resolves Promises, and runs microtasks all on the same thread. "Concurrency" in Node.js is cooperative: a callback runs to completion before the event loop picks the next one.

Why this avoids context switching:
- One OS thread means the OS never needs to switch between Node.js execution units — that decision is made entirely in user space by the event loop.
- No locks or mutexes are needed to protect shared JavaScript state — only one callback runs at a time.
- TLB and cache are never disrupted by switching execution contexts within the JavaScript layer.

The cost of this design:
- **A long-running synchronous operation blocks the entire event loop** — a 200ms CPU-bound computation (large JSON parse, cryptographic operation, tight loop) prevents every other callback from running for 200ms. For a 1000 RPS server, 200ms of event loop blockage means 200 requests wait.
- **No true parallelism for CPU-bound work** — a Node.js process uses one CPU core for JavaScript execution. A 32-core machine runs at 1/32 utilisation for pure CPU work.
- **Worker threads exist but have overhead** — `worker_threads` in Node.js spin up actual OS threads with their own V8 isolates. Communication between workers uses structured cloning (serialisation overhead) or SharedArrayBuffer (requires explicit synchronisation). Each worker thread is a full OS thread — context switching between them is subject to normal OS scheduler costs.

**Q10. How does Go's goroutine scheduler minimise context switching overhead?**
A: Go's runtime implements an M:N scheduler — M goroutines multiplexed onto N OS threads, where N = GOMAXPROCS (defaults to the number of CPU cores). The scheduler has three components:

- **G (goroutine)** — a lightweight execution unit with a small initial stack (2–8KB, growable).
- **M (machine)** — an OS thread. The goroutine runs on the M.
- **P (processor)** — a logical processor that holds a run queue of goroutines. An M must acquire a P to run goroutines.

Context switching minimisation strategies:

- **User-space switching** — when a goroutine blocks cooperatively (channel send/receive, `runtime.Gosched()`), the scheduler switches to the next goroutine on the same P in user space. No `syscall`, no privilege mode change, no kernel involvement. Cost: ~100–300ns.
- **Non-blocking syscall interception** — Go wraps system calls. For calls that would block (file I/O, network), Go uses non-blocking variants internally. When a goroutine's network read would block, the runtime parks the goroutine, hands the OS thread to another goroutine, and uses the network poller (epoll on Linux) to wake the goroutine when data arrives.
- **Work stealing** — when a P's local run queue is empty, it steals goroutines from other Ps' queues. This keeps OS threads busy without the goroutines ever touching the kernel scheduler.
- **Goroutine preemption** — since Go 1.14, goroutines are asynchronously preemptible via signals (SIGURG). A goroutine that is CPU-bound and never calls into the runtime can be preempted by the runtime, enabling fair scheduling without programmer intervention.

The practical result: a Go program handling 100,000 concurrent connections incurs user-space goroutine switches for most operations and only pays OS context switch cost when making blocking system calls — and even then, Go tries to reuse the same OS thread with a different goroutine, minimising the number of OS threads (and therefore OS context switches) needed.

**Q11. How does Python's GIL interact with context switching?**
A: CPython's Global Interpreter Lock (GIL) is a mutex that allows only one Python thread to execute Python bytecode at a time. Its interaction with context switching:

- **The GIL is released every `sys.getswitchinterval()` seconds** (default 5ms since Python 3.2, previously every 100 bytecodes). At each release point, other Python threads have an opportunity to acquire the GIL and run.
- **The GIL is released during blocking I/O** — when a thread calls `socket.recv()`, `file.read()`, or any other blocking I/O operation, it releases the GIL before entering the system call, allowing other Python threads to run Python code concurrently. This is why threading works for I/O-bound Python programs despite the GIL.
- **CPU-bound threads thrash** — two CPU-bound Python threads repeatedly fight over the GIL. Thread A holds the GIL for 5ms, releases, Thread B acquires it, runs for 5ms, releases — but both threads also incur OS context switch overhead as the OS scheduler switches between the two OS threads. The result is *more* overhead than running single-threaded: two threads doing CPU-bound work on one core are slower than one thread because of GIL contention and context switch cost combined.
- **`multiprocessing` bypasses the GIL** — separate processes have separate GILs (and separate address spaces). True parallelism for CPU-bound Python requires multiprocessing or native extensions that release the GIL (NumPy, PyTorch do this for their core operations).

## Section 4: Measuring & Diagnosing Context Switch Overhead

**Q12. What tools do you use to measure context switch rate and identify whether it is a performance problem?**
A: A layered diagnostic toolkit:

**System-wide rate:**
```bash
# vmstat — cs column shows context switches/sec
vmstat 1 10
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
# r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
# 3  0      0 4832156  12344 8473212   0    0     0    12  847 2341  8  4 88  0  0
#                                                               ↑    ↑
#                                                         interrupts cs/sec

# pidstat — per-process context switches
pidstat -w -p <pid> 1
# 14:23:01    UID    PID   cswch/s nvcswch/s  Command
# 14:23:02      0   1234     142.0      18.0  node

# perf stat — hardware counters including context switches
perf stat -p <pid> -e context-switches,cpu-migrations sleep 10
```

**Process-level breakdown:**
```bash
# /proc filesystem
cat /proc/<pid>/status | grep ctxt
# voluntary_ctxt_switches:    58234
# nonvoluntary_ctxt_switches:   312

# strace — see which system calls are causing voluntary switches
strace -c -p <pid>
# % time     seconds  usecs/call     calls    syscall
#  38.21    0.012453         213        58    futex       ← lock contention
#  22.14    0.007219          82        88    epoll_wait  ← I/O waiting
```

**Node.js specific:**
```javascript
// Track event loop lag — a proxy for blocked-event-loop contention
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  console.log('p99 loop delay:', h.percentile(99) / 1e6, 'ms');
  h.reset();
}, 5000);
```

**Go specific:**
```bash
# GODEBUG=schedtrace shows goroutine scheduler activity
GODEBUG=schedtrace=1000 ./myservice 2>&1 | head -5
# SCHED 1000ms: gomaxprocs=8 idleprocs=6 threads=10 spinningthreads=1
#               needspinning=0 idlethreads=3 runqueue=0 [1 0 0 0 0 0 0 0]

# pprof goroutine profile
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**Interpreting the numbers:**
- < 1,000 cs/sec — negligible, not worth investigating.
- 1,000–10,000 cs/sec — normal for a moderately loaded server with I/O concurrency.
- 10,000–100,000 cs/sec — investigate; check if involuntary switches are elevated (CPU saturation) or if lock contention is driving voluntary switches.
- > 100,000 cs/sec — likely a performance problem; profiling required to find the root cause.

**Q13. How does cache affinity relate to context switching, and what is CPU pinning?**
A: Cache affinity is the tendency for a thread to perform better when it runs on the same CPU core repeatedly — its working set (frequently accessed data) remains in that core's L1/L2 cache. Every time the OS schedules a thread on a different core, it pays the cost of loading the working set into the new core's cache from L3 or DRAM.

Linux's CFS has an affinity bias — it tries to reschedule a thread on the same core it last ran on (the `last_cpu` field in `task_struct`). But under load, the scheduler will migrate threads to underloaded cores for load balancing, sacrificing cache affinity for utilisation balance.

**CPU pinning** (`taskset`, `sched_setaffinity()`) restricts a thread or process to run only on a specific set of CPU cores:
```bash
# Pin process to cores 0 and 1 only
taskset -c 0,1 ./myservice

# Pin a running process
taskset -cp 0,1 <pid>

# In code (Linux)
cpu_set_t mask;
CPU_ZERO(&mask);
CPU_SET(0, &mask);
CPU_SET(1, &mask);
sched_setaffinity(0, sizeof(mask), &mask);
```

CPU pinning eliminates cross-core cache migration but introduces the risk of CPU saturation — if the pinned cores are overwhelmed, the process can't use idle cores elsewhere. It is appropriate for:
- **Latency-sensitive services** where consistent cache performance matters more than peak throughput (financial matching engines, real-time systems).
- **NUMA-aware applications** where memory access to a remote NUMA node (different CPU socket) is significantly slower than local memory — pinning ensures the thread stays on the same NUMA node as its allocated memory.
- **Isolation** — preventing a noisy-neighbour service from sharing CPU cache with a latency-sensitive one.

**Q14. What is the relationship between context switching and the thundering herd problem?**
A: The thundering herd problem occurs when many threads or processes are simultaneously woken from sleep in response to a single event, but only one can actually handle the event. All the awakened threads run, discover the event is already handled, and go back to sleep — each wakeup and subsequent sleep costs a context switch.

Classic example: multiple threads blocked on `accept()` on the same socket. When a connection arrives, the kernel wakes all threads. One claims the connection; the others find `accept()` returns `EAGAIN` and go back to sleep. N-1 context switches wasted.

This was the canonical `accept()` thundering herd problem in early multi-threaded servers. Linux's `SO_REUSEPORT` socket option solves it by allowing multiple sockets bound to the same port — the kernel load-balances incoming connections across sockets, waking only one thread per connection.

A similar pattern appears with `epoll` on older kernels (`EPOLLONESHOT` or `EPOLLET` vs level-triggered), `pthread_cond_broadcast` waking all waiters when only one can proceed, and `select()`/`poll()` on the same set of file descriptors from multiple threads.

The context switch impact: a thundering herd event at 10,000 connections/sec with 50 threads could cause 49 × 10,000 = 490,000 wasted context switches per second — each voluntary (the thread blocked on `accept()`), meaning `voluntary_ctxt_switches` will be abnormally high relative to actual connection rate.

## Section 5: Reducing Context Switch Overhead

**Q15. What are the primary strategies for reducing context switching overhead in a backend service?**
A: Strategies organised from architectural to implementation level:

**Reduce the number of OS threads**
Fewer threads = fewer scheduling decisions = fewer context switches. Use an async I/O model (Node.js event loop, Go goroutines, Java virtual threads, Python asyncio) that multiplexes many concurrent operations onto few OS threads. A Node.js server handling 10,000 concurrent connections uses one OS thread for JavaScript; the equivalent blocking thread-per-connection model uses 10,000 OS threads with 10,000-way context switching overhead.

**Reduce lock contention**
Every time a thread blocks on a mutex, it performs a voluntary context switch. High contention locks are therefore high context-switch generators:
- Use lock-free data structures (atomic operations, CAS loops) for hot paths.
- Reduce lock granularity — shard a global lock into N per-shard locks.
- Use read-write locks (`pthread_rwlock_t`) when reads dominate — multiple readers can proceed in parallel without switching.
- Avoid holding locks across I/O operations — never do `mutex.lock(); socket.read(); mutex.unlock()`.

**Tune the OS scheduler**
```bash
# Increase time quantum — fewer preemptions for CPU-bound threads
# (Linux: reduce timer interrupt frequency via CONFIG_HZ or PREEMPT settings)

# Set thread priority for latency-sensitive threads
nice -n -10 ./latency-sensitive-service     # higher scheduler priority
chrt -f 20 ./realtime-service               # SCHED_FIFO real-time scheduling

# Disable CPU frequency scaling for consistent performance
echo performance > /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
```

**Batch I/O operations**
Each I/O call is a potential context switch (voluntary, waiting for the kernel). Batching reduces the number of calls:
- `writev()` instead of multiple `write()` calls.
- `io_uring` on Linux (kernel 5.1+) — submit multiple I/O operations in a single system call via a shared ring buffer, reducing the total number of kernel entries.
- Database connection pools with query batching — fewer round trips = fewer blocking waits.

**Use spinning for ultra-short waits**
For locks expected to be held for nanoseconds, spinning (busy-waiting) avoids the context switch cost:
```c
// Spin-then-sleep mutex: spin for N iterations before blocking
// Used in Linux kernel mutexes, Java's AbstractQueuedSynchronizer
while (!try_lock()) {
  if (spin_count++ > SPIN_LIMIT) { futex_wait(); break; }
  cpu_relax(); // PAUSE instruction — reduces power and pipeline pressure
}
```
Spinning is only beneficial when the lock holder is running on another core and the critical section is short. Spinning on a single-core system or a heavily overloaded multicore system wastes CPU and makes things worse.

**Q16. What is `io_uring`, and how does it reduce context switches for I/O-heavy services?**
A: `io_uring` (Linux 5.1+) is a kernel interface for asynchronous I/O that minimises the number of system calls — and therefore the number of kernel mode transitions — needed to perform I/O operations. It uses two shared ring buffers (memory mapped between user space and kernel space):

- **Submission Queue (SQ)** — the application writes I/O operation descriptors (read from fd X into buffer Y, write buffer Z to fd W) into the SQ ring buffer.
- **Completion Queue (CQ)** — the kernel writes completion results back to the CQ ring buffer when operations finish.

The critical performance property: the application can submit hundreds of I/O operations and retrieve hundreds of completions with a **single system call** (`io_uring_enter()`), or with *zero* system calls if the kernel is in polling mode (`IORING_SETUP_SQPOLL` — a kernel thread continuously polls the SQ without the application needing to call `io_uring_enter()`).

Compare to the traditional path:
```
Traditional: read() → syscall → kernel → sleep → wakeup → return
             = 2 mode transitions + 1 context switch (voluntary)

io_uring:    write to SQ ring → (no syscall in poll mode) → read from CQ ring
             = 0 mode transitions + 0 context switches for the I/O submission
```

Real-world impact: high-throughput file servers and databases that were bottlenecked on syscall overhead (millions of small reads/writes per second) see 30–50% throughput improvements with `io_uring`. The database `PostgreSQL` added `io_uring` support in version 16; `liburing` is the userspace library for working with `io_uring` directly.

## Section 6: Scenario / System Design Style Questions

**Q17. "Our Node.js API has p99 latency of 800ms but p50 is 20ms. CPU utilisation is 30%. What role could context switching play, and how do you diagnose it?"**
A: The gap between p50 and p99 with low CPU utilisation is the signature of **event loop blocking** — not context switching in the OS sense, but the Node.js equivalent: a task occupying the event loop for hundreds of milliseconds, blocking all other callbacks.

In Node.js's single-threaded model, there is no OS context switching between request handlers. But the effect is the same: if one request's handler runs a 500ms synchronous operation, every other request queued behind it waits 500ms before its callback even starts.

Diagnosis:
```javascript
// Step 1: Measure event loop lag continuously
const { monitorEventLoopDelay } = require('perf_hooks');
const histogram = monitorEventLoopDelay({ resolution: 1 });
histogram.enable();
setInterval(() => {
  const p99 = histogram.percentile(99) / 1e6;
  if (p99 > 50) console.warn(`Event loop p99 lag: ${p99}ms`);
  histogram.reset();
}, 1000);

// Step 2: CPU profiling to find what's blocking the loop
// clinic.js flame graph, or:
node --cpu-prof --cpu-prof-interval=100 server.js
// Open chrome://inspect → Profiler to visualise

// Step 3: Check if specific routes correlate with p99 spikes
// Add timing middleware:
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on('finish', () => {
    const duration = Number(process.hrtime.bigint() - start) / 1e6;
    if (duration > 200) console.warn(`Slow handler: ${req.method} ${req.path} ${duration}ms`);
  });
  next();
});
```

Common culprits: large JSON serialisation (`JSON.stringify` on a 10MB object), synchronous crypto operations (`crypto.createHash` in a loop), `fs.readFileSync`, or a npm library that uses synchronous patterns internally.

Fix: offload the blocking work to a worker thread (`worker_threads`) or decompose into async operations. If the blocking is inherent (CPU-bound computation), use a worker thread pool.

**Q18. "A Go microservice has high CPU utilisation but lower-than-expected throughput. `GODEBUG=schedtrace` shows many goroutines in a runnable state but few running. What's wrong?"**
A: Goroutines in runnable state but not running means the goroutines are ready to execute but there aren't enough OS threads (Ps) to run them all simultaneously. The backlog of runnable goroutines is the run queue — its length is shown in the `schedtrace` output.

Common causes:

**1 — GOMAXPROCS too low**
```bash
GODEBUG=schedtrace=1000 ./service 2>&1
# SCHED 1000ms: gomaxprocs=1 idleprocs=0 threads=5 runqueue=847
#                          ↑
#                  Only one P — one goroutine runs at a time
```
Fix: `runtime.GOMAXPROCS(runtime.NumCPU())` or set via `GOMAXPROCS` env var. Default is correct for most cases; this usually isn't the issue unless the service is containerised with `GOMAXPROCS` set to 1 and there are multiple available cores.

**2 — Goroutines blocking on a shared lock**
```go
// Every goroutine serialised through one mutex
var mu sync.Mutex
func handleRequest() {
  mu.Lock()         // every handler blocks here
  defer mu.Unlock()
  // ... work ...
}
```
All goroutines are technically runnable (they've been scheduled) but immediately block on `mu.Lock()` — they descend into `futex_wait()` and become involuntary context switches. `perf stat` would show high `context-switches` count.
Fix: reduce lock scope, shard the lock, or use a channel-based worker pool with bounded concurrency.

**3 — Goroutine explosion — too many goroutines for available work**
If the service spawns a goroutine per request and receives a burst of 100,000 concurrent requests, the scheduler has 100,000 goroutines competing for GOMAXPROCS slots. Goroutines spend more time context-switching than working.
Fix: use a semaphore or bounded worker pool:
```go
sem := make(chan struct{}, runtime.NumCPU()*4)  // bounded parallelism
for req := range requests {
  sem <- struct{}{}
  go func(r Request) {
    defer func() { <-sem }()
    handle(r)
  }(req)
}
```

**Q19. "You're designing a high-frequency trading order matching engine in Java. Context switching is a key concern. What design decisions do you make?"**
A: An HFT matching engine requires sub-microsecond latency — a single involuntary context switch (1–10µs) is catastrophic. Every design decision centres on eliminating OS scheduler involvement:

**Thread model — one thread per role, pinned to a dedicated core**
```java
// Bind the matching thread to CPU core 3 — no other thread runs there
ProcessBuilder pb = new ProcessBuilder("taskset", "-c", "3", "java", "-jar", "engine.jar");
// Or via JNA/JNI: sched_setaffinity()
```
The matching thread runs indefinitely, never yielding, never sleeping. It is SCHED_FIFO (real-time scheduling class) so the OS never preempts it for another thread.

**Busy-wait / spin loop instead of blocking I/O**
```java
// Disruptor pattern — the consumer spins on the ring buffer cursor
while (true) {
  long nextSequence = sequence.get() + 1;
  long availableSequence = sequencer.getHighestPublishedSequence(nextSequence, ...);
  if (availableSequence >= nextSequence) {
    processOrder(ringBuffer.get(nextSequence));
    sequence.set(nextSequence);
  }
  // No sleep, no yield, no context switch — pure spin
}
```
The LMAX Disruptor is the canonical Java pattern for this: a lock-free ring buffer with spin-waiting consumers.

**Avoid JVM GC pauses** — a GC stop-the-world pause causes the same effect as a context switch. Use:
- `ZGC` or `Shenandoah` (sub-millisecond GC pauses).
- Pre-allocate all objects at startup; avoid allocation in the hot path.
- Use off-heap memory (`ByteBuffer.allocateDirect()`, `Chronicle Map`) for order books.

**Disable hyper-threading on the matching core** — the sibling logical core competes for L1 cache and execution units, introducing variable latency.

**Huge pages** — configure `vm.nr_hugepages` to use 2MB pages instead of 4KB for the order book memory. Reduces TLB entries needed, reducing TLB miss rate even when context switches do occur.

**Q20. "A Python web service is CPU-bound (image processing per request). It uses threading. Explain why it's not getting parallelism and what to fix."**
A: Threading in CPython does not provide parallelism for CPU-bound work because of the GIL. Here's the exact execution model:

Thread A (image processing) acquires the GIL → runs Python bytecode → releases GIL after `sys.getswitchinterval()` (5ms) → Thread B acquires GIL → runs → releases → repeat. The OS is indeed context-switching between Threads A and B (both are OS threads), but only one is executing Python bytecode at any instant. Two threads processing images simultaneously on a 2-core machine gets the same throughput as one thread — with additional context switch overhead.

What `top` shows: both threads appear to use CPU (they're competing for the GIL), but combined CPU usage is ~100% instead of ~200% on a 2-core machine.

Fixes in order of invasiveness:

**Fix 1 — Use `multiprocessing`** — each process has its own GIL and its own CPU core. N processes on N cores = true N× parallelism. Cost: inter-process communication overhead (pickling data to send between processes).
```python
from multiprocessing import Pool
with Pool(processes=os.cpu_count()) as pool:
    results = pool.map(process_image, images)
```

**Fix 2 — Use a C extension that releases the GIL** — libraries like `Pillow`, `OpenCV`, and `NumPy` release the GIL during their native operations. Wrapping the image processing in a C extension or using these libraries allows true threading parallelism for the compute-heavy parts.

**Fix 3 — Use a task queue with worker processes** — offload image processing to Celery workers (separate processes). The web service thread just enqueues the job and returns a job ID; the client polls or receives a webhook when processing is complete.

**Fix 4 — Use `concurrent.futures.ProcessPoolExecutor`** — same as multiprocessing pool but with a cleaner `Future`-based API compatible with `asyncio`.

**Q21. "Your service handles 50,000 requests per second. A profiling session shows 300,000 context switches per second. Is this a problem, and how do you decide?"**
A: 300,000 context switches / 50,000 RPS = **6 context switches per request**. Whether this is a problem depends on their type and cost:

**Step 1 — Split voluntary vs involuntary**
```bash
pidstat -w -p <pid> 1
# If cswch/s (voluntary) >> nvcswch/s (involuntary): the service is I/O-bound and blocking
# normally — expected and usually acceptable.
# If nvcswch/s is significant (> 10% of total): the service is being preempted — CPU-saturated.
```

**Step 2 — Calculate the time cost**
At 6 switches/request, 50,000 RPS, and 5µs per switch:
`6 × 5µs × 50,000 = 1,500,000µs = 1.5 seconds of CPU time consumed per second in context switches.`
If total CPU time available is 4 cores × 1,000,000µs = 4,000,000µs/sec, context switching consumes ~37.5% of CPU. That is a problem.

At 1µs per switch (optimistic): 375ms/sec = ~9.4% of CPU — borderline but worth investigating.

**Step 3 — Identify the source**
```bash
# Which system calls are causing the switches?
strace -c -p <pid> 2>&1 | sort -k4 -rn | head -20
# High futex count → lock contention
# High epoll_wait count → many I/O waits with short timeouts
# High read/write count → unbatched I/O
```

**Step 4 — Decide action threshold**
For most services: if context switch overhead accounts for > 10% of CPU budget and is growing with load → investigate and fix. If it's stable, < 5% of CPU, and p99 latency is within SLO → deprioritise.

For latency-sensitive services (p99 target < 10ms): any involuntary context switch is a concern — investigate regardless of percentage.

**Q22. "Explain context switching to a new engineer who just asked why their multi-threaded Python script is slower than the single-threaded version."**
A: The multi-threaded script is slower for two connected reasons — the GIL and context switch overhead:

Imagine the CPU is a single kitchen with one chef (the GIL). Your script hired three cooks (threads), but the kitchen rule says only one cook can use a knife at a time. So Cook A chops for 5ms, puts down the knife, Cook B picks it up and chops for 5ms, and so on. The total chopping time is the same as if one cook worked alone — but now you've added the overhead of cooks taking turns, arguing over the knife, and reorganising the kitchen every time someone new takes over (context switch cost: cache eviction, state save/restore).

The single-threaded version doesn't fight over the knife — one cook works continuously, keeping everything they need close at hand (in CPU cache).

The fix depends on what the script is doing:
- If it's spending most of its time waiting (downloading files, reading from disk) → threading *does* help, because cooks waiting for deliveries aren't using the knife, so others can work.
- If it's spending most of its time computing (parsing data, processing numbers) → use `multiprocessing` — hire three separate kitchen-and-chef combos (separate processes, separate GILs). Now all three chefs cook at the same time on separate stoves.

**Q23. "A service you deploy to Kubernetes is showing higher latency than on bare metal with the same code. Context switching is suspected. How do you investigate?"**
A: Kubernetes adds several layers that can inflate context switching:

**Layer 1 — CPU throttling (most common culprit)**
Kubernetes CPU limits use Linux cgroups and the CFS bandwidth controller. If a container's `cpu.limit` is set to 500m (0.5 cores) and the process uses more, the kernel throttles it — artificially pausing the process for the remainder of the 100ms CFS period. This looks like a context switch from the process's perspective (it gets paused and resumed) but appears in different metrics:
```bash
# Check for CPU throttling in the container
cat /sys/fs/cgroup/cpu/cpu.stat
# nr_throttled 1247         ← times throttled
# throttled_time 3847291874 ← nanoseconds spent throttled

# Or via kubectl:
kubectl top pod <pod-name>
# Compare CPU usage to CPU limit
```
Fix: increase CPU limit, remove limit entirely (use requests only), or reduce the process's CPU consumption.

**Layer 2 — noisy neighbours on the same node**
Multiple pods on the same node compete for CPU. Even if your pod isn't throttled, a noisy neighbour consuming CPU causes the OS scheduler to preempt your pod's threads (involuntary context switches) more frequently than on a dedicated bare-metal machine.
```bash
# Check node-level CPU saturation
kubectl describe node <node-name> | grep -A5 "Allocated resources"
# High allocatable CPU usage → contention likely

# On the node (if accessible):
perf stat -a -e context-switches sleep 5   # system-wide cs rate
```
Fix: use pod anti-affinity to spread pods across nodes, use a dedicated node pool for latency-sensitive services, or set `PodDisruptionBudget` + resource quotas to prevent over-provisioning.

**Layer 3 — NUMA effects in multi-socket nodes**
Large cloud VMs may span multiple NUMA nodes. If a pod's threads are scheduled across sockets, memory accesses to a remote NUMA node take 2–4× longer. This isn't context switching per se but has similar symptoms (variable latency, cache miss spikes).
```bash
numactl --hardware       # show NUMA topology
numastat -p <pid>        # show NUMA hit/miss ratio for a process
```

**Q24. "How does virtual thread adoption in Java 21 change the context switching story for a Java web service?"**
A: Java 21's virtual threads (Project Loom) change the threading model from 1:1 (one OS thread per Java thread) to M:N (many virtual threads multiplexed onto a small pool of carrier OS threads) — bringing Java's threading model closer to Go's goroutine model.

**Before virtual threads (platform threads):**
- A thread-per-request server (traditional Spring MVC) with 1,000 concurrent requests uses 1,000 OS threads.
- Each blocking operation (JDBC query, HTTP call) causes a voluntary OS context switch.
- Memory: ~1MB stack per OS thread = 1GB for 1,000 threads.
- Context switch rate: proportional to blocking I/O rate × thread count.

**After virtual threads:**
- 1,000 concurrent requests still create 1,000 Java threads, but these are virtual threads — lightweight objects in the JVM heap (~few KB each).
- When a virtual thread blocks on I/O, the JVM parks it and mounts a different virtual thread onto the carrier OS thread — a **user-space switch** (~microseconds), not an OS context switch.
- OS context switches only happen at the carrier thread level (e.g., 8 carrier threads = at most 8 simultaneous OS context switches in progress).
- The OS scheduler sees 8 threads, not 1,000 — scheduling overhead drops dramatically.

**The practical change for a web service:**
- Thread-per-request code (blocking JDBC, blocking HTTP client) becomes efficient without rewriting to reactive/async style.
- OS context switch rate drops from O(concurrent requests × I/O rate) to O(carrier threads × scheduler period).
- Throughput improves for I/O-bound services because threads no longer sit idle as OS threads waiting for I/O — they are parked as virtual threads and the carrier OS thread serves other requests.

**Q25. "Walk me through what happens at every level of the stack — from application code to hardware — when a Node.js service makes a PostgreSQL query."**
A: Tracing the full path reveals exactly where context switching does and does not occur:

```
1. Application code
   await db.query('SELECT * FROM orders WHERE user_id = $1', [userId])
   ↓ Promise created; execution reaches `await` — control returns to event loop

2. Node.js event loop (user space)
   Event loop is NOT blocked — it processes other callbacks while waiting.
   The `await` suspends this async function; no OS thread is blocked.
   No OS context switch at this point.

3. libuv (C library, user space)
   libuv manages the connection to PostgreSQL via a non-blocking TCP socket.
   It calls `send()` to write the query to the socket buffer — this is a syscall.
   ↓ syscall → kernel mode transition (not a context switch; same thread, just privilege level change)

4. Linux kernel — syscall handler
   `send()` copies data from user buffer to kernel socket send buffer.
   Returns immediately if the buffer has space (non-blocking socket).
   ↓ returns to user space (privilege level back to user mode)

5. libuv — epoll
   libuv registers the socket with epoll for EPOLLIN (data ready to read).
   The Node.js thread returns to its event loop — it is NOT sleeping.
   It processes other callbacks (other requests' handlers, timers, etc.)
   No context switch — the thread is running, just doing other work.

6. Linux kernel — network stack (async)
   The kernel's network stack receives the TCP response from PostgreSQL.
   It places the data in the socket's receive buffer.
   It marks the socket as readable and wakes epoll.
   This happens in a softirq (software interrupt) — potentially on a different CPU
   core, but no application thread context switch occurs here.

7. libuv — epoll_wait returns
   epoll_wait() (called in the event loop's I/O polling phase) returns,
   indicating the PostgreSQL socket is readable.
   libuv calls recv() to read the response — another syscall (kernel mode transition).
   The PostgreSQL protocol driver parses the response bytes.
   ↓ Promise resolves with query result rows

8. Node.js event loop — microtask queue
   The resolved Promise's `.then()` callback is enqueued in the microtask queue.
   After the current task finishes, the event loop drains microtasks.
   The `await db.query(...)` resumes — no OS context switch; same thread, same core,
   same cache state as before the await.

9. Application code resumes
   `const orders = result.rows;` — execution continues from where `await` paused.
```

**Where OS context switches did NOT happen**: between the query and its response. The Node.js thread stayed runnable the entire time, doing other work via the event loop. This is why Node.js scales to thousands of concurrent DB queries with a single OS thread and minimal OS context switch overhead.

**Where OS context switches CAN happen in this path**:
- If the event loop is processing many callbacks and the OS timer fires, the Node.js thread may be preempted (involuntary switch). Rare at normal load.
- If another process on the same machine is CPU-saturated and the OS scheduler preempts Node.js to give time to the other process (involuntary switch).
- Inside the PostgreSQL server process — it uses one OS thread per connection; it will context-switch as it waits for disk I/O to fetch the order rows.

The PostgreSQL side is where traditional blocking-thread context switching occurs — but those are in the PostgreSQL process, not in the Node.js process. From the Node.js side, the round-trip to PostgreSQL is entirely non-blocking.

## Quick Reference Table

| Trigger | Switch type | Who switches | Typical cost |
|--|--|--|--|
| Blocking syscall (`read`, `recv`, `futex_wait`) | Voluntary | OS thread → next runnable thread | 1–10µs + cache effects |
| Timer interrupt (time quantum expired) | Involuntary | OS preempts thread | 1–10µs + cache effects |
| Higher-priority thread wakeup | Involuntary | OS preempts thread | 1–10µs + cache effects |
| Goroutine blocks on channel | Voluntary | Go runtime (user space) | ~100–300ns |
| `async/await` suspension | Cooperative | Event loop (user space) | ~50–100ns |
| GIL release (Python CPU-bound thread) | OS-level | OS switches between Python OS threads | 1–10µs + GIL contention |
| Virtual thread parks (Java 21) | Voluntary | JVM runtime (user space) | ~microseconds |

| Metric | Tool | What high values indicate |
|--|--|--|
| `cs` (vmstat) | `vmstat 1` | High overall system context switch rate |
| `cswch/s` (pidstat) | `pidstat -w -p <pid>` | High voluntary switches — lots of blocking I/O |
| `nvcswch/s` (pidstat) | `pidstat -w -p <pid>` | High involuntary switches — CPU saturation |
| `voluntary_ctxt_switches` | `/proc/<pid>/status` | Total voluntary switches since process start |
| `context-switches` | `perf stat` | Combined switch count with hardware precision |
| Event loop lag (Node.js) | `monitorEventLoopDelay` | Event loop blocking — equivalent to context switch stall |
| `nr_throttled` | `/sys/fs/cgroup/cpu/cpu.stat` | Kubernetes CPU throttling — artificial pause |
