# Segmentation Fault Causes — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a segmentation fault, and what exactly triggers one at the hardware level?**
A: A segmentation fault (segfault, SIGSEGV) is the OS's response to a memory access violation — an attempt by a process to read from, write to, or execute a memory address it is not permitted to access. The mechanism is entirely hardware-enforced:

1. The CPU executes an instruction that accesses a memory address (a load, store, or instruction fetch).
2. The MMU (Memory Management Unit) walks the process's page table to translate the virtual address to a physical address.
3. One of two things goes wrong:
   - **The virtual address has no mapping** — no page table entry exists for this address. The MMU raises a page fault.
   - **The mapping exists but the permissions are violated** — the page is read-only and the instruction tried to write; or the page is non-executable and the CPU tried to fetch an instruction from it. The MMU raises a protection fault.
4. The CPU switches to kernel mode and invokes the OS page fault handler.
5. The OS determines it cannot satisfy the access (unlike a minor page fault, which it can fix by allocating a frame). It sends `SIGSEGV` to the offending process.
6. Unless the process has a custom `SIGSEGV` handler, the default action is termination — optionally with a core dump.

The signal name comes from the historical concept of "memory segments" in older architectures (x86 real mode, 286 protected mode). Modern OS use paging rather than segmentation, but the signal name stuck. On POSIX systems, two signals cover memory violations: `SIGSEGV` (invalid address or permission violation) and `SIGBUS` (valid address but hardware alignment error or mapping backed by a file that has been truncated).

**Q2. What is the difference between SIGSEGV and SIGBUS?**
A: Both signals terminate the process and indicate a memory access problem, but they have different root causes:

**SIGSEGV — Segmentation Violation:**
- Accessing an unmapped virtual address (null pointer, out-of-bounds past the heap/stack end).
- Writing to a read-only mapping (text segment, `mmap(PROT_READ)`).
- Executing from a non-executable page (NX/XD bit violation — stack execution attempt, W^X policy violation).
- The CPU simply could not translate or was denied the access.

**SIGBUS — Bus Error:**
- **Alignment fault** — accessing a multi-byte value at a misaligned address. On x86-64, most misaligned accesses are handled in hardware silently (with a performance penalty), but some SIMD instructions (`movaps`, `vmovaps`) require 16-byte or 32-byte alignment and raise SIGBUS on violation. On ARM, strict alignment is required — a misaligned 4-byte read raises SIGBUS by default.
- **`mmap` file-backed mapping beyond the file end** — if a file is truncated after being `mmap`'d, accessing the region beyond the new end of file raises SIGBUS (not SIGSEGV), because the address is mapped but the backing store no longer provides data.
- **Hardware error** — physical memory fault (rare; usually triggers a kernel panic rather than SIGBUS).

In Node.js native addons: a SIGBUS on ARM (e.g., AWS Graviton, Raspberry Pi) often means an unaligned pointer read in C++ code — a common porting bug when code assumes x86 tolerates misalignment.

**Q3. Why doesn't the OS simply let a process read any address if there's enough RAM?**
A: Four reasons rooted in security, stability, and correctness:

**Process isolation:** Without memory protection, any bug — a stray pointer, an off-by-one — could overwrite another process's memory. OS stability would be equivalent to running all programs in one address space with no protection. This was the reality in early cooperative multitasking OSes (DOS, Windows 3.x) and is why a single bad application could hang the entire system.

**Kernel protection:** The kernel's code and data are mapped at the top of every process's virtual address space (in many architectures) but marked inaccessible from user mode. Without this protection, a user-mode process could overwrite the scheduler, interrupt handlers, or system call tables. Ring 0/ring 3 separation and page table permissions enforce this in hardware.

**Security enforcement:** Modern systems use W^X (Write XOR Execute) — a memory page is either writable or executable, never both simultaneously. This prevents code injection attacks: an attacker who writes shellcode to a writable stack or heap cannot then execute it, because those pages are marked non-executable (NX/XD bit). A segfault on execution from a non-executable page is the defence working correctly.

**Detecting bugs early:** Crashing on an illegal access is better than silently returning garbage data. A segfault on a null pointer dereference exposes the bug immediately at the point of failure, rather than allowing corrupted data to propagate and produce a hard-to-trace wrong answer hours later.

## Section 2: Classic Causes in C/C++

**Q4. What is a null pointer dereference and why is address 0 unmapped?**
A: A null pointer dereference occurs when a pointer whose value is zero (NULL / `nullptr`) is used to access memory — dereferenced with `*ptr`, `ptr->field`, or `ptr[index]`. Since virtual address 0 is intentionally left unmapped by every modern OS, the MMU raises a page fault immediately.

```c
// Classic null dereference
char *buf = NULL;
buf[0] = 'A';         // SIGSEGV — writing to address 0

struct Payment *p = getPayment(txnId);
// getPayment returns NULL on not-found
printf("%d\n", p->amount);   // SIGSEGV — reading from NULL + offsetof(amount)

// Subtle: p is non-null but the field pointer within it is null
p->callback = NULL;
p->callback();        // SIGSEGV — calling function through null function pointer
```

Why address 0 is unmapped intentionally: if the OS mapped address 0, a null pointer dereference would silently read or write whatever happened to be there — potentially a valid but wrong value, or a writable zero page. Leaving it unmapped ensures the fault is caught immediately and loudly. On Linux, `mmap` refuses to map address 0 by default (`/proc/sys/vm/mmap_min_addr` is typically 65536); on some embedded systems, address 0 is writable (mapped BIOS area), making null dereferences silently dangerous.

In Node.js native addons: `node::ObjectWrap::Unwrap<T>(info.Holder())` returns nullptr if the JavaScript object has been GC'd or the native binding is misused. Dereferencing it without a null check produces a segfault that crashes the entire Node.js process — not just the request.

**Q5. What is a buffer overflow, and how does it cause a segfault?**
A: A buffer overflow occurs when a write (or read) extends beyond the allocated bounds of a buffer — past the end of an array, a stack-allocated buffer, or a heap allocation. Whether it causes a segfault depends on what lies beyond the buffer's end:

```c
// Stack buffer overflow
void processPayload(const char *input) {
  char buf[64];
  strcpy(buf, input);    // if input > 63 bytes, overwrites past buf[63]
  // Overwrites: adjacent local variables, saved frame pointer, return address
  // Result: either silent corruption, segfault on return (corrupt return address),
  //         or — worst case — arbitrary code execution (stack smashing exploit)
}

// Heap buffer overflow
uint8_t *packet = malloc(128);
memcpy(packet, data, dataLen);  // if dataLen > 128, overwrites heap metadata
// Result: heap corruption — allocator metadata overwritten.
// Next malloc() or free() may crash, or memory may be silently corrupted.

// Off-by-one — the most common form
char name[8];
for (int i = 0; i <= 8; i++) {  // ≤ instead of <
  name[i] = 'A';                 // name[8] writes one byte past the buffer
}
```

Three possible outcomes:
- **Segfault immediately** — the write crosses into an unmapped page (happens when the buffer is at the end of a mapped region).
- **Silent corruption** — the write hits a valid mapped page belonging to another variable. The program continues with corrupted state. Segfault (or wrong answer) happens later, far from the actual bug.
- **Security exploit** — carefully crafted overflow overwrites the return address or function pointer to redirect execution. Stack canaries (GCC `-fstack-protector`), ASLR, and NX exist specifically to detect/prevent this.

The "crash far from the cause" pattern is why buffer overflows are among the hardest bugs to debug — the segfault's stack trace points to `malloc` or `free` or some unrelated code, not the actual write that corrupted the heap.

**Q6. What is a use-after-free vulnerability, and what makes it particularly dangerous?**
A: Use-after-free (UAF) occurs when a pointer is used after the memory it points to has been freed. The freed memory may have been returned to the OS, reallocated to a different object, or zeroed — the access reads/writes memory it no longer owns:

```c
// Classic use-after-free
char *buf = malloc(64);
strcpy(buf, "payment_data");
free(buf);
printf("%s\n", buf);    // UAF read — buf points to freed memory

// More subtle — two pointers to the same object
Payment *p1 = createPayment();
Payment *p2 = p1;       // aliased pointer
freePayment(p1);
p2->amount = 5000;      // UAF write — modifying freed memory
```

Why it's dangerous:
- **Intermittent segfaults:** The freed memory may have been reallocated for a new object. Writing to it via the stale pointer corrupts the new object's data — the segfault (if any) happens when the new object's legitimate owner uses it, not at the write.
- **Security exploit:** Attackers can carefully control what gets allocated in the freed slot. A UAF write then overwrites the new object with attacker-controlled data — a common exploit class (type confusion via UAF).
- **Heap metadata corruption:** Some allocators put free-list metadata in the freed block itself. A UAF write to the first bytes of a freed block corrupts the allocator's free list, causing the next `malloc` to return a pointer to an arbitrary location.

Tools that catch UAF: AddressSanitizer (`-fsanitize=address`) — places red zones around allocations and poisons freed memory; any access to poisoned memory raises an immediate, precisely localised error with a full stack trace.

**Q7. What is a dangling pointer, and how does it differ from a null pointer?**
A: A null pointer explicitly holds the value zero — it points to nothing, and any dereference immediately segfaults (because address 0 is unmapped). A dangling pointer holds a non-zero address that was once valid but is no longer — it points to memory the program no longer owns:

```c
int *danglingStack(void) {
  int x = 42;
  return &x;         // returns pointer to local variable on the stack
  // After return, x's stack frame is popped — the address is now garbage
}

int *ptr = danglingStack();
printf("%d\n", *ptr); // dangling pointer dereference — undefined behaviour
                      // may read 42 (stack not yet overwritten), may segfault,
                      // may read garbage, may corrupt other data
```

Dangling pointers are far more dangerous than null pointers because:
- They don't reliably crash immediately. The address is often still readable (the stack frame or freed heap memory hasn't been overwritten yet), so the program may read stale data without crashing — producing wrong answers rather than clean crashes.
- The crash happens non-deterministically — it depends on what happened to occupy that memory after the pointer became stale.
- In threaded code: one thread frees an object while another thread holds a pointer to it. The second thread reads/writes through the stale pointer while the freed memory is being reused by a third object. This is a race condition + dangling pointer combined — some of the hardest bugs to reproduce.

Common dangling pointer sources: returning address of local variable (caught by compiler warnings), caching a pointer to a `std::vector` element (the vector may reallocate), storing a raw pointer to a `shared_ptr`-managed object and the `shared_ptr` goes out of scope.

**Q8. What causes a stack overflow and how does the OS detect it?**
A: A stack overflow occurs when the call stack grows beyond its allocated limit — typically through deep or infinite recursion, or through allocation of very large local variables. The stack grows downward (toward lower addresses) on x86-64. When it extends past the stack's bottom boundary, it enters a region that is either unmapped or protected:

```c
// Infinite recursion — guaranteed stack overflow
void infiniteRecurse(void) {
  char buf[1024];          // 1KB per frame
  infiniteRecurse();       // pushes a new frame on every call
}                          // stack exhausted after ~8000 calls (8MB / 1KB)

// Large local allocation — single-call stack overflow
void processImage(void) {
  uint8_t rawPixels[50 * 1024 * 1024]; // 50MB local array — immediate overflow
  // Stack is only 8MB; this allocation alone exceeds it
}
```

Detection mechanism: the OS places a **guard page** — a single unmapped (or `PROT_NONE`) page — just below the lowest valid stack page. When the stack overflows into the guard page, the CPU raises a page fault. The OS's fault handler recognises the faulting address as the guard page, maps a temporary page to run the signal handler, and sends `SIGSEGV` to the process. The signal handler can detect the stack overflow by checking that `info->si_addr` is near the bottom of the stack (using `sigaltstack` to run the handler on an alternate stack — because the main stack is exhausted).

In Node.js: `RangeError: Maximum call stack size exceeded` is V8's equivalent — V8 checks stack depth in software and throws before the OS guard page is hit. But native addons with deep C++ recursion can overflow the OS stack and crash the entire Node.js process with SIGSEGV (not a catchable JS error).

**Q9. What is a double-free and what does it corrupt?**
A: A double-free occurs when `free()` is called on the same pointer twice. The allocator's free list is a data structure tracking available memory blocks. Freeing the same block twice corrupts this list:

```c
char *buf = malloc(64);
free(buf);
free(buf);   // double-free — undefined behaviour

// More common: two paths both free the same object
Payment *p = createPayment(data);
if (condition) {
  handleError(p);   // handleError calls freePayment(p)
}
freePayment(p);     // also called unconditionally — double-free if condition was true
```

What happens in practice:
- **glibc malloc double-free detection:** modern glibc detects double-free by checking a corruption marker in the chunk header. If detected, it aborts with `free(): double free detected in tcache 2` and sends `SIGABRT`. This is the most common outcome.
- **Heap corruption (silent):** if the allocator doesn't detect it, the free list is corrupted. The same block is now on the free list twice. The next two `malloc` calls of the appropriate size return the same address — two different parts of the program think they own the same memory. Writes from one corrupt the other.
- **Exploit:** the double-free → same block returned twice → type confusion → arbitrary write is the classic heap exploitation technique (glibc tcache poisoning).

**Q10. What is an out-of-bounds array access and under what conditions does it segfault vs silently corrupt?**
A: An out-of-bounds access reads or writes past the valid range of an array. Whether it segfaults immediately or corrupts silently depends entirely on what virtual address the out-of-bounds index maps to:

```c
int arr[4] = {1, 2, 3, 4};

// These may or may not segfault:
printf("%d\n", arr[4]);    // one past end — reads adjacent memory (stack variable or padding)
printf("%d\n", arr[100]);  // further out — may still be mapped, reads garbage
printf("%d\n", arr[10000]); // far out — likely unmapped, SIGSEGV

// Write — always worse than read (corrupts adjacent data)
arr[4] = 99;   // overwrites the next variable on the stack
arr[-1] = 99;  // negative index — goes below the array (also valid mapped memory)
```

The MMU operates at page granularity (4KB). An access that goes slightly past an array end (1, 2, 4 bytes) is almost always still within the same 4KB page — the MMU does not know or care about array boundaries, only page boundaries. It grants the access, which reads/writes adjacent memory silently.

The segfault only occurs when the access crosses a page boundary into an unmapped page. For a stack-allocated array, the adjacent memory is other local variables and the frame pointer — overwriting them corrupts the program state but doesn't immediately crash.

This is why bounds checking (Rust's borrow checker, Java's array bounds checks, C's `__builtin_dynamic_object_size` + `-D_FORTIFY_SOURCE`) is valuable — the OS cannot catch intra-page violations.

## Section 3: Causes in Managed Runtimes and Native Addons

**Q11. Can Node.js JavaScript code cause a segfault? What actually causes Node.js process crashes?**
A: Pure JavaScript cannot cause a segfault — V8's garbage collector manages all JS object memory, and V8's bounds checking on `TypedArray`, `Buffer`, and property access prevents out-of-bounds memory access from the JS layer. A JavaScript bug produces an exception (`TypeError`, `RangeError`), not a segfault.

However, Node.js process crashes with SIGSEGV do occur in practice. The causes are always outside the JS layer:

**Native addons (N-API / NAN / raw V8 API):**
The most common source. C++ code in a native addon runs with no memory safety guarantees. Any of the classic C/C++ segfault causes apply: null dereference, UAF, buffer overflow, stack overflow in C++ code. The segfault kills the entire Node.js process — not just the addon — because they share the same address space and there's no hardware boundary between them.

```cpp
// N-API addon — null dereference crashes the Node.js process
napi_value MyFunction(napi_env env, napi_callback_info info) {
  MyObject *obj = nullptr;
  obj->Process();   // SIGSEGV — crashes Node.js process, not catchable in JS
  // ...
}
```

**`vm.runInNewContext()` with untrusted code running a native module:**
If untrusted code loads a native addon via `require` inside a VM context, the addon runs in the same process. A segfault in the addon crashes the parent process.

**Worker threads with shared native state:**
Two `worker_threads` accessing the same native C++ object concurrently without synchronisation — a data race in C++ can corrupt a vtable pointer and cause a segfault on the next virtual function call.

**V8 internal bugs:**
Rare but real — certain patterns of JS code (particularly around JIT optimisation, deoptimisation, and type assumptions) have historically triggered V8 internal assertions or null dereferences. These manifest as SIGSEGV or SIGABRT with `#0  0x... in v8::internal::...` in the stack trace.

**`--max-old-space-size` exceeded during GC:**
When V8 can't allocate memory for GC, it may call `abort()` → `SIGABRT` — not SIGSEGV, but equally fatal. The crash message is `FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed - JavaScript heap out of memory`.

**`Buffer.allocUnsafe()` used incorrectly:**
`Buffer.allocUnsafe(n)` allocates uninitialized memory. `Buffer.allocUnsafe(n).toString("utf8")` may read uninitialized bytes that happen to form invalid memory sequences — not a segfault, but a potential information disclosure. `Buffer` operations that write past the allocated size via native code can segfault.

**Q12. How do you debug a segfault in a Node.js native addon?**
A: A segfault in a Node.js process produces no JavaScript stack trace — the process dies before V8 can catch anything. The diagnosis requires native debugging tools:

**Step 1 — Enable core dumps:**
```bash
ulimit -c unlimited           # allow core dump files
export NODE_OPTIONS="--abort-on-uncaught-exception"

# Run the process
node server.js
# After crash: a core file appears in the current directory
```

**Step 2 — Analyse with GDB:**
```bash
gdb $(which node) core
# Inside GDB:
(gdb) bt               # backtrace — shows C++ call stack at crash point
(gdb) bt full          # full backtrace with local variable values
(gdb) frame 3          # switch to frame 3
(gdb) info locals      # show local variables in current frame
(gdb) p obj->field     # print a field value
```

**Step 3 — AddressSanitizer for development:**
Rebuild the native addon with ASan:
```bash
node-gyp rebuild --debug \
  CFLAGS="-fsanitize=address -g" \
  LDFLAGS="-fsanitize=address"

node --asan server.js   # run with ASan instrumentation
```
ASan reports the exact line of the bad access, the type of violation (use-after-free, heap-buffer-overflow), the allocation stack trace, and the free stack trace — far more informative than a raw segfault.

**Step 4 — `llnode` plugin for V8 heap inspection:**
```bash
npm install -g llnode
llnode $(which node) -c core
# Inside llnode:
(lldb) v8 bt        # Node.js-aware backtrace showing JS frames
(lldb) v8 inspect   # inspect V8 objects on the heap
```

**Step 5 — `node-report` / `--experimental-report` for production:**
```bash
node --report-on-signal --report-signal=SIGSEGV server.js
```
On SIGSEGV, Node.js writes a JSON diagnostic report containing: JS stack, native stack, heap statistics, open handles, environment variables. Useful when core dumps are impractical in production.

**Q13. What segfault causes are specific to multithreaded programs?**
A: Threading introduces a class of segfault causes that don't exist in single-threaded code — all rooted in unsynchronised concurrent access to shared state:

**Data race on a pointer:**
Thread A reads a pointer; Thread B frees the object and sets the pointer to NULL. Thread A dereferences the now-null or stale pointer:

```cpp
// Shared state — no lock
Payment *currentPayment = nullptr;

// Thread A
void processPayment() {
  if (currentPayment != nullptr) {     // check
    // Thread B runs here — frees currentPayment, sets to nullptr
    currentPayment->charge();           // SIGSEGV — race between check and use
  }
}

// Thread B
void cancelPayment() {
  delete currentPayment;
  currentPayment = nullptr;
}
```

This is TOCTOU (Time Of Check To Time Of Use) — a classic race. Fix: mutex around the read-check-use sequence, or atomic pointer with proper memory ordering.

**Concurrent container modification:**
Inserting into a `std::vector` while another thread iterates it. `vector::push_back` may reallocate the backing array — invalidating all iterators. The iterating thread holds a dangling pointer into the old allocation:

```cpp
std::vector<Connection*> connections;

// Thread A (acceptor)
connections.push_back(newConn);  // may reallocate — invalidates all iterators

// Thread B (cleanup)
for (auto *c : connections) {    // iterator is now dangling if reallocation happened
  c->close();                    // SIGSEGV — c points into freed old array
}
```

**Stack overflow from thread stack size:**
Each thread gets its own stack, typically 8MB on Linux (main thread) or 2MB (pthreads default for secondary threads). A recursive algorithm that works fine on the main thread may overflow a secondary thread's smaller stack.

**False sharing leading to cache corruption (rare):**
Two threads writing to different variables that happen to share a cache line cause the CPU to bounce the cache line between cores. This doesn't directly cause a segfault but can interact with lock-free algorithms in ways that corrupt state — eventually producing a segfault from a corrupted pointer.

**Signal delivery to wrong thread:**
On Linux, signals sent to a process (`kill(pid, sig)`) are delivered to an arbitrary thread in the process. A SIGSEGV signal handler that uses thread-local state may run in a thread that didn't allocate that state — using an uninitialized thread-local causes a fault inside the fault handler.

## Section 4: Memory Safety and Detection Tools

**Q14. What is AddressSanitizer (ASan), and how does it catch segfaults that the OS misses?**
A: The OS raises SIGSEGV only when an access crosses a page boundary into an unmapped or protected page. An out-of-bounds write of 4 bytes into the middle of a 4KB page — overwriting a neighboring variable — the OS never sees. ASan instruments every memory access at compile time to catch these intra-page violations:

ASan works by:
1. **Shadow memory:** For every 8 bytes of application memory, ASan maintains 1 byte of "shadow" metadata. The shadow byte encodes how many of those 8 bytes are valid (0 = all 8 valid, 1 = only first byte valid, -1 = entire 8 bytes are "poisoned" — freed or out-of-bounds).
2. **Instrumentation:** The compiler inserts a check before every load and store:
   ```c
   // Original:
   *ptr = value;
   // Instrumented:
   if (IsPoisoned(ptr)) ReportError(ptr);
   *ptr = value;
   ```
3. **Poisoning:** ASan marks freed memory as poisoned immediately. Red zones (8–128 bytes of poisoned memory) are placed around every heap allocation and stack variable.

What ASan catches that the OS misses:
- Heap buffer overflow by 1 byte (into the red zone).
- Stack buffer overflow that doesn't cross a page boundary.
- Use-after-free (freed memory is poisoned).
- Use-after-return (local variables' stack frame is poisoned after return).
- Double-free (poison check on the shadow byte).
- Heap use before allocation (red zone before the allocation).

Performance overhead: ~2× slower execution, ~3× more memory. Acceptable for development and CI; too heavy for production without sampling.

**Q15. What is Valgrind Memcheck, and how does it differ from ASan?**
A: Valgrind Memcheck is a dynamic analysis tool that runs the program inside a software emulation layer — every instruction is interpreted and every memory access checked. It detects:

- Reads from uninitialised memory (including heap allocations that weren't zeroed — `malloc` vs `calloc`).
- All of what ASan catches (overflow, UAF, double-free).
- Memory leaks (allocated but never freed by process exit).

How it differs from ASan:

| Dimension | ASan | Valgrind Memcheck |
|---|---|---|
| **Mechanism** | Compile-time instrumentation + shadow memory | Runtime binary instrumentation (emulation) |
| **Speed overhead** | ~2× | ~20–50× |
| **Requires recompilation** | Yes (`-fsanitize=address`) | No — runs any binary |
| **Uninitialised memory detection** | Partial (MSan for full coverage) | Yes — full coverage |
| **Memory leak detection** | Limited (LeakSanitizer, separate) | Yes — full coverage |
| **False positives** | Very rare | Occasional (system calls, custom allocators) |
| **Use case** | CI, development builds | Thorough post-build analysis, legacy code |

For native Node.js addons: ASan is preferred (faster, integrable into the build system). Valgrind is useful for analysing a pre-built binary without source, or for uninitialised memory reads (which ASan doesn't catch without MemorySanitizer / MSan).

**Q16. What is ASLR, and does it prevent segfaults or make them harder to debug?**
A: ASLR (Address Space Layout Randomisation) randomises the base addresses of the stack, heap, shared libraries, and executable (with PIE — Position Independent Executable) at process start. The same program gets different virtual addresses every run.

ASLR's purpose is security, not correctness: it makes it harder for an attacker to know where injected shellcode will land, where `libc` functions (like `system()`) are, or where to redirect a corrupt return address. It does not prevent segfaults — the memory access violations are the same regardless of where in virtual memory they occur.

ASLR makes debugging harder in one specific way: segfault addresses and stack traces differ between runs, making it harder to correlate a crash report from production with a local reproduction. But the relative address (offset within the binary or library) is stable. Tools handle this:

```bash
# Disable ASLR for a single process (for debugging reproducibility)
setarch $(uname -m) -R node server.js     # -R = disable ASLR

# Or in GDB:
(gdb) set disable-randomization on
(gdb) run

# In production crash reports: the binary's load address + offset = absolute address
# addr2line resolves offset to file + line number:
addr2line -e ./addon.node -f 0x1a3b   # 0x1a3b = crash address - load base
```

With PIE disabled (`-no-pie` at link time), the text segment loads at a fixed address — useful for reproducible debugging but reduces security. The production/debug tension: keep ASLR on in production, disable it selectively for crash reproduction.

## Section 5: Segfaults in Specific Contexts

**Q17. What causes SIGSEGV in signal handlers themselves?**
A: Signal handlers run asynchronously — they interrupt the normal flow of execution at any point. Three causes of segfaults inside signal handlers:

**Non-async-signal-safe functions:**
Only a small list of functions are safe to call inside a signal handler (defined by POSIX as "async-signal-safe": `write`, `read`, `_exit`, `kill`, `signal`). Calling `malloc`, `printf`, `mutex_lock`, or any function that acquires a lock is unsafe — the signal may have interrupted that very function while it held its internal lock. Calling it again in the signal handler causes deadlock or heap corruption:

```c
// Signal handler — called while malloc's internal lock is held
void segv_handler(int sig) {
  char *msg = malloc(128);   // DEADLOCK or heap corruption — malloc is NOT signal-safe
  printf("Caught SIGSEGV\n"); // printf is NOT signal-safe (uses malloc internally)
}
```

**Signal handler stack overflow:**
The signal handler runs on the process's main stack by default. If the stack is already exhausted (the SIGSEGV was caused by a stack overflow), the signal handler itself overflows the remaining guard page and causes a secondary fault — the process dies without running the handler. Fix: `sigaltstack` — allocate a separate signal handling stack:

```c
stack_t altStack;
altStack.ss_sp    = malloc(SIGSTKSZ);
altStack.ss_size  = SIGSTKSZ;
altStack.ss_flags = 0;
sigaltstack(&altStack, NULL);

struct sigaction sa = { .sa_handler = myHandler, .sa_flags = SA_ONSTACK };
sigaction(SIGSEGV, &sa, NULL);
// Now myHandler runs on altStack regardless of main stack state
```

**Recursive signal delivery:**
`SIGSEGV` is not blocked during its own handler by default on some configurations. If the handler itself causes a segfault (dereferences a bad pointer), SIGSEGV is delivered again — infinite recursion until stack exhaustion. Fix: in the signal action, use `SA_RESETHAND` (reset to default after first delivery) or `sigprocmask` inside the handler to block SIGSEGV.

**Q18. How does `mmap` misuse cause SIGBUS rather than SIGSEGV?**
A:

```c
// Scenario: mmap a file, then truncate the file
int fd = open("payments.dat", O_RDWR);
fstat(fd, &st);
void *map = mmap(NULL, st.st_size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

// Now truncate the file to half its size
ftruncate(fd, st.st_size / 2);

// Access the second half of the mapping — the file no longer backs these pages
char *ptr = (char *)map + st.st_size * 3 / 4;
*ptr = 'A';    // SIGBUS — address is mapped but backing file was truncated
               // SIGSEGV would mean the address is not mapped at all
```

The distinction: `mmap` creates a valid virtual-to-physical mapping promise. If the backing store (file) is later truncated, the mapping remains in the page table, but when the OS tries to satisfy a page fault for the truncated region, there is no file page to load. The OS delivers SIGBUS instead of SIGSEGV to distinguish "mapped but unavailable" from "not mapped at all."

In Node.js: this can occur in code that uses `mmap` via native addons for high-performance file processing (common in fintech for NACH mandate batch files). A race between a writer truncating and a reader accessing the same mapped file produces SIGBUS and crashes the process. Fix: use file locks or ensure the mapping covers only the portion the process has confirmed exists.

**Q19. What causes a segfault in a JIT-compiled code path?**
A: JIT (Just-In-Time) compilers generate machine code at runtime and execute it directly. Segfaults in JIT-generated code fall into two categories:

**JIT compiler bug — incorrect code generation:**
The JIT emits an instruction that loads from or stores to an invalid address — typically from a wrong optimisation assumption. In V8:
- **Speculative optimisation failure:** V8 assumes a variable is always a small integer and generates fast-path code that directly reads the value bits. If a deoptimisation guard is incorrect and the value is actually a pointer, the generated code treats a pointer as an integer and reads from the integer value as an address — likely unmapped.
- **Inline cache corruption:** V8 caches the layout of objects (hidden class / map). If two objects appear to have the same hidden class but one has a different backing store layout, the inline cache reads from a field offset that doesn't exist on the second object.

These are V8 bugs — rare and typically fixed quickly. Stack trace contains `v8::internal::compiler::` frames.

**W^X policy violation from JIT code emission:**
JIT requires write permission to generate code, then execute permission to run it. Modern systems enforce W^X — a page cannot be simultaneously writable and executable. JIT runtimes use `mprotect()` to transition:
1. Allocate code page: `mmap(PROT_READ | PROT_WRITE)` — writable, not executable.
2. Write machine code into the page.
3. `mprotect(page, size, PROT_READ | PROT_EXEC)` — executable, not writable.
4. Jump to the page.

A bug that attempts to execute before step 3 completes, or that tries to write new code after step 3 without first switching back to writable, causes SIGSEGV. On systems with strict W^X (`vm.mmap_min_prot` enforcement, iOS, systems with `MAP_JIT` requirement on macOS), this is enforced in hardware.

## Section 6: Prevention and Production Patterns

**Q20. How do you prevent segfaults in Node.js native addon development?**
A: A systematic set of practices from N-API / node-addon-api:

**1. Always check N-API return values:**
```cpp
// ❌ — ignores error; env may be in error state, further calls segfault
napi_get_value_int32(env, value, &result);

// ✅ — check status; bail out if error
napi_status status = napi_get_value_int32(env, value, &result);
if (status != napi_ok) {
  napi_throw_error(env, nullptr, "Expected integer argument");
  return nullptr;
}
```

**2. Validate argument count and types before accessing:**
```cpp
napi_value MyFunction(napi_env env, napi_callback_info info) {
  size_t argc = 2;
  napi_value argv[2];
  napi_get_cb_info(env, info, &argc, argv, nullptr, nullptr);

  if (argc < 2) {
    napi_throw_type_error(env, nullptr, "Expected 2 arguments");
    return nullptr;
  }
  // Now safe to access argv[0] and argv[1]
}
```

**3. Use `node::ObjectWrap` / `Napi::ObjectWrap` and check for nullptr:**
```cpp
MyObject *obj = Napi::ObjectWrap<MyObject>::Unwrap(info.This());
if (obj == nullptr) {
  Napi::TypeError::New(env, "Invalid native object").ThrowAsJavaScriptException();
  return env.Null();
}
```

**4. Use RAII and smart pointers — never raw `new`/`delete` in addon code:**
```cpp
// ❌ Raw pointer — easy to leak or double-free
MyData *data = new MyData();
processData(data);   // if this throws, data leaks
delete data;

// ✅ RAII — destructor runs even on exceptions
auto data = std::make_unique<MyData>();
processData(data.get());
// data automatically freed when it goes out of scope
```

**5. Test with ASan in CI:**
```json
// package.json
{
  "scripts": {
    "build:asan": "node-gyp rebuild --debug",
    "test:asan": "LD_PRELOAD=/usr/lib/libasan.so node test.js"
  }
}
```

**Q21. How do you isolate a native addon's crash so it doesn't kill the Node.js HTTP server?**
A: A segfault in a native addon kills the entire Node.js process — there's no try/catch that can prevent it at the JS level. The only isolation strategies operate at the process level:

**Strategy 1 — Run the addon in a child process:**
```javascript
// parent.js — the HTTP server
const { fork } = require("child_process");

function callNativeAddon(input) {
  return new Promise((resolve, reject) => {
    const child = fork("./addon-worker.js", [], { timeout: 5000 });
    child.send(input);
    child.on("message", resolve);
    child.on("error",   reject);
    child.on("exit", (code) => {
      if (code !== 0) reject(new Error(`Addon worker crashed (exit ${code})`));
    });
  });
}

// addon-worker.js — runs in a separate process; crash is contained
const addon = require("./build/Release/my_addon.node");
process.on("message", (input) => {
  const result = addon.process(input);  // if this segfaults, only this child dies
  process.send(result);
});
```

If the child segfaults, the parent receives the `exit` event with a non-zero code. The HTTP server continues serving other requests. The child is restarted for the next request (or pooled).

**Strategy 2 — Worker thread per request (partial isolation):**
`worker_threads` run in the same process — a segfault in a worker kills the entire process. However, V8 isolates are separate: a JS error in a worker doesn't propagate. For native addons, the only true isolation is the child process approach.

**Strategy 3 — Process pool with a supervisor:**
PM2, systemd, or a custom supervisor restarts the process on crash. The gap between crash and restart (typically < 1s with PM2) is the only downtime. Combined with a load balancer that health-checks and routes away from a crashing instance, this provides high availability:
```bash
# PM2 cluster mode — restarts individual workers on crash
pm2 start server.js --instances max --name api
```

## Section 7: Scenario / System Design Style Questions

**Q22. "A Node.js service crashes with SIGSEGV under load but not in development. What is your investigation process?"**
A: Load-dependent segfaults narrow the cause to either concurrency (race conditions in C++ code) or resource exhaustion (OOM, stack overflow under deep call stacks at high concurrency). Structured investigation:

**Step 1 — Capture the crash artefacts:**
```bash
# Enable core dumps in production
ulimit -c unlimited
echo "/var/cores/core.%e.%p.%t" > /proc/sys/kernel/core_pattern

# Enable Node.js diagnostic report
NODE_OPTIONS="--report-on-signal --report-signal=SIGSEGV \
              --report-filename=/var/logs/report.%p.%t.json" \
node server.js
```

**Step 2 — Examine the stack trace:**
Is the crash in V8 internals? In a named native addon? In glibc? The frame names in `gdb bt` localise the component:
```
#0  0x... in MyAddon::ProcessPayload  ← crash in the addon
#1  0x... in v8::internal::...        ← crash in V8 internals
#2  0x... in malloc_consolidate       ← heap corruption (crash in allocator)
```

Crash in `malloc_consolidate` or `free` means a heap corruption — the actual bad write happened earlier. Enable `MALLOC_CHECK_=3` (glibc) or rebuild with ASan to catch it at the point of corruption, not the delayed crash in the allocator.

**Step 3 — Reproduce with load locally:**
```bash
# Reproduce with wrk or k6 at the same RPS that triggers the crash
wrk -t4 -c100 -d30s http://localhost:3000/endpoint
```
Run under ASan or Valgrind — the controlled crash gives the precise location:
```bash
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libasan.so.6 node server.js
```

**Step 4 — Check for thread safety in the native addon:**
If the addon uses a global or static C++ object (a connection pool, a shared cache, a singleton), and concurrent requests access it without locks, a data race corrupts the object. Run with ThreadSanitizer (TSan):
```bash
node-gyp rebuild CFLAGS="-fsanitize=thread -g" LDFLAGS="-fsanitize=thread"
node --tsan server.js
```

**Step 5 — Check memory limits:**
```bash
# Watch RSS growth under load
watch -n 1 "ps -o pid,rss,vsz -p $(pgrep -n node)"

# If RSS grows until crash: memory leak or OOM → SIGKILL (not SIGSEGV)
# If RSS is stable but crash happens: race condition, not leak
```

**Q23. "You're reviewing a native Node.js addon that wraps a C payment library. What red flags do you look for that could cause segfaults in production?"**
A: A structured review checklist for native addon C/C++ code:

**Memory ownership — who frees what:**
- Does the addon ever call `free()` on memory returned by the C library? Or does the library own it? Mixed ownership → double-free.
- Does the addon store a pointer to C library memory in a JS object (via `ObjectWrap`)? If the library frees the memory before the JS object is GC'd → UAF.
- Look for: raw `new`/`delete` without RAII, manual `free()` in error paths that skip a complementary allocation.

**Error return codes never checked:**
Every C library function that can fail returns an error code or sets `errno`. Unchecked errors mean the subsequent code runs with invalid state:
```cpp
// ❌ — if initialize() fails, handle is invalid; next call is UAF
PaymentHandle *handle = payment_initialize(config);
payment_process(handle, data);   // handle may be NULL or garbage

// ✅
PaymentHandle *handle = payment_initialize(config);
if (!handle) { throw std::runtime_error("Init failed"); }
```

**Static / global mutable state shared across requests:**
```cpp
static PaymentContext *sharedCtx = nullptr;  // global — shared across all threads

// Thread A and Thread B both call processRequest simultaneously
// Both write to sharedCtx without locking → data race → SIGSEGV
```
Flag any `static` mutable variables in addon code that can be accessed from multiple threads.

**C string handling without bounds checking:**
```cpp
// ❌ — strcpy with no length check
char localBuf[64];
strcpy(localBuf, inputStr);   // if inputStr > 63 bytes → stack buffer overflow

// ✅
strncpy(localBuf, inputStr, sizeof(localBuf) - 1);
localBuf[sizeof(localBuf) - 1] = '\0';
```

**Callback retention without lifetime management:**
If the addon stores a JS callback (`napi_ref`) and calls it after the JS object is GC'd:
```cpp
// ❌ — storing a raw napi_value doesn't prevent GC
napi_value callback;
napi_get_cb_info(env, info, &argc, &callback, nullptr, nullptr);
storedCallback = callback;    // GC'd; calling it later → SIGSEGV

// ✅ — create a strong reference that prevents GC
napi_create_reference(env, callback, 1, &storedCallbackRef);
// Call it later:
napi_value cb;
napi_get_reference_value(env, storedCallbackRef, &cb);
napi_call_function(env, global, cb, argc, argv, nullptr);
```

**Missing thread safety for async operations:**
If the addon performs work asynchronously (via `napi_async_work` or `uv_queue_work`), the completion callback runs on the main V8 thread, but the work callback runs on the libuv thread pool. Any V8/napi API called from the work callback (not the completion callback) causes a segfault — V8 is not thread-safe:
```cpp
// ❌ — calling napi inside the work callback (runs on thread pool)
napi_async_work_execute(napi_env env, void *data) {
  napi_value result;
  napi_create_int32(env, 42, &result);  // SIGSEGV — V8 not accessible here
}

// ✅ — all napi calls must be in the complete callback (runs on main thread)
napi_async_work_complete(napi_env env, napi_status status, void *data) {
  napi_value result;
  napi_create_int32(env, 42, &result);  // safe — on main V8 thread
}
```

## Quick Reference: Segfault Cause Classification

| Cause | Immediate crash? | OS catches it? | Tool to detect |
|---|---|---|---|
| Null pointer dereference | Yes | Yes (addr 0 unmapped) | Compiler warnings (`-Wall`) |
| Out-of-bounds (page boundary) | Yes | Yes | OS page fault |
| Out-of-bounds (intra-page) | No — silent corruption | No | ASan, Valgrind |
| Buffer overflow (stack) | Delayed or immediate | No | ASan, stack canaries |
| Buffer overflow (heap) | Delayed (allocator) | No | ASan, Valgrind |
| Use-after-free | Non-deterministic | No | ASan, Valgrind |
| Double-free | Yes (glibc detection) | No | ASan, `MALLOC_CHECK_` |
| Dangling pointer | Non-deterministic | No | ASan, Valgrind |
| Stack overflow | Yes (guard page) | Yes (guard page) | Backtrace depth |
| Race condition on pointer | Non-deterministic | No | TSan (ThreadSanitizer) |
| SIGBUS (mmap truncation) | Yes | Yes | OS fault handler |
| Signal handler non-safe call | Non-deterministic | No | Code review |
| UAF in V8 native addon | Yes | No (same process) | ASan, GDB + core |
| V8 napi call off-main-thread | Yes | No | Code review, ASan |

**Tip for the interview:** At 5 YOE, segfault questions come in two forms: theoretical ("why does null dereference crash but out-of-bounds-by-one sometimes doesn't?") and practical ("a Node.js process crashes with SIGSEGV under load — walk me through your investigation"). The theoretical answer requires understanding the MMU/page table layer — the OS only catches page-boundary violations, not intra-page ones — which is why buffer overflows are so dangerous. The practical answer requires knowing the toolchain: core dumps, GDB backtraces, ASan for development, `node-report` for production, process isolation to contain addon crashes. Have a concrete story ready about a memory safety bug — preferably one you found with a tool like ASan or Valgrind — and trace from the tool output back to the root cause.
