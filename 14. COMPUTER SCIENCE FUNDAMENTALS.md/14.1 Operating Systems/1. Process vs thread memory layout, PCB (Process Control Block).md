# Process vs Thread: Memory Layout, PCB (Process Control Block) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a process, and what are its defining characteristics?**
A: A process is an instance of a program in execution — not the program itself (which is static code on disk), but the living, running entity the OS creates when that program is launched. It is the fundamental unit of resource ownership in an operating system.

A process has five defining characteristics:

- **Isolation** — each process has its own private virtual address space. One process cannot directly read or write another process's memory. A crash in one process does not corrupt another.
- **Resources** — a process owns file descriptors, network sockets, memory mappings, and device handles. These belong to the process; when it dies, the OS reclaims them.
- **At least one thread** — a process starts with one thread of execution (the main thread) and can create more. The process is the container; threads are the workers inside it.
- **Identity** — the OS assigns a unique Process ID (PID). The OS also tracks the parent PID (PPID) — the process that created it via `fork()` or equivalent.
- **State** — a process has a lifecycle: new → ready → running → waiting → terminated. The OS scheduler moves it between these states based on CPU availability and I/O events.

The conceptual model: a process is a box with walls (isolation), contents (resources and memory), and workers inside it (threads).

**Q2. What is a thread, and how does it relate to its parent process?**
A: A thread (sometimes called a lightweight process) is the unit of CPU scheduling — the actual sequence of instructions the processor executes. A thread exists inside a process and shares the process's resources:

- **Shared with sibling threads:** virtual address space (code, heap, globals), open file descriptors, signal handlers, working directory, user/group IDs.
- **Private to each thread:** program counter (PC), stack, stack pointer, register set, thread-local storage (TLS), signal mask, scheduling priority.

The relationship in one sentence: **a process owns resources; threads execute within those resources.** Multiple threads in the same process can read and write the same memory — which is both the source of their power (shared data structures, fast communication) and their danger (race conditions, data corruption without synchronisation).

```
Process (PID 1234)
├── Virtual Address Space
│   ├── Code segment     (shared by all threads — read-only)
│   ├── Data segment     (globals — shared, mutable)
│   ├── Heap             (shared, mutable — malloc/new allocations)
│   └── Stack            (one per thread — PRIVATE)
│       ├── Thread 1 Stack
│       ├── Thread 2 Stack
│       └── Thread 3 Stack
├── File descriptor table (shared)
├── Signal handlers       (shared)
└── Thread Control Blocks (one per thread — PC, registers, stack ptr)
```

**Q3. What is the Process Control Block (PCB), and what does it contain?**
A: The PCB (also called the process descriptor or task struct in Linux) is the kernel's data structure that represents a process — the authoritative record of everything the OS needs to know to manage, schedule, pause, resume, and terminate a process.

When the OS saves a process's state (during a context switch or interrupt), it writes to the PCB. When it resumes the process, it reads from the PCB to restore exactly where the process was.

A PCB contains:

**Process identity:**
- PID (Process ID) — unique identifier.
- PPID (Parent PID) — which process created this one.
- UID / GID — user and group identity for permission checks.

**CPU state (saved registers):**
- Program Counter (PC / IP) — the address of the next instruction to execute.
- Stack Pointer (SP) — top of the current stack.
- General-purpose registers (RAX, RBX, … on x86-64).
- Flags register (zero flag, carry flag, etc.).
- Floating-point / SIMD registers.

**Memory management:**
- Pointer to the page table (virtual-to-physical address mapping).
- Base and limit registers (on older systems without paging).
- Memory map (which virtual address ranges are mapped, with what permissions).

**Process state:**
- Current state: running / ready / blocked / zombie / stopped.
- Scheduling priority and scheduling class.
- CPU time consumed (user time + kernel time).
- Time quantum remaining.

**I/O information:**
- File descriptor table (array of open file handles).
- List of open sockets, pipes, devices.
- Current working directory.

**Inter-process communication:**
- Signal pending/blocked masks.
- Signal handler function pointers.
- IPC handles (message queues, semaphores, shared memory segments).

**Accounting:**
- CPU time used, page faults, context switch count — for scheduling and resource limits (ulimit).

In Linux, the PCB is `struct task_struct` in `kernel/sched.h` — over 700 fields in modern kernels. Every process and every thread has its own `task_struct`; threads share most fields but have independent stacks and register sets.

**Q4. What is a Thread Control Block (TCB), and how does it relate to the PCB?**
A: The Thread Control Block (TCB) is the per-thread equivalent of the PCB — the kernel's record of everything specific to one thread within a process.

In Linux (and most modern Unix-like systems), threads are implemented as tasks with shared state — there's no hard architectural distinction between a PCB and a TCB. Each thread gets its own `task_struct`, but threads within the same process share the same `mm_struct` (memory map), `files_struct` (file descriptor table), and `signal_struct`. The `CLONE_VM | CLONE_FILES | CLONE_SIGHAND` flags passed to the `clone()` syscall are precisely what distinguish thread creation from process creation.

The TCB (or thread-specific part of `task_struct`) contains:
- Thread ID (TID) — unique within the system.
- Stack pointer — each thread has its own stack.
- Program counter — where this thread is currently executing.
- Register set — full CPU state for this thread.
- Thread-local storage (TLS) pointer — thread-private global variables.
- State — running / ready / blocked.
- Signal mask — which signals this thread blocks.

The relationship: **PCB = process identity + shared resources; TCB = per-thread CPU state and stack.** When the scheduler switches between threads of the same process, it saves and restores TCB state (registers, PC, SP) but does not switch the memory map — which is why intra-process thread context switching is cheaper than inter-process switching.

**Q5. What is the difference between concurrency and parallelism, and where do processes and threads fit?**
A: 

- **Concurrency** — multiple tasks are in progress at the same time, but not necessarily executing simultaneously. A single-core CPU running multiple threads is concurrent: the CPU rapidly switches between threads, giving the illusion of simultaneous progress. No two instructions execute at exactly the same physical instant.
- **Parallelism** — multiple tasks execute simultaneously on multiple physical execution units (CPU cores, CPUs). A quad-core machine running four threads, one per core, achieves true parallelism.

Processes and threads both support concurrency. Parallelism requires:
- Multiple cores (or multiple CPUs).
- For threads: the OS scheduler must assign threads to different cores, and the language runtime must allow it (the Python GIL prevents true CPU parallelism for Python threads on a single interpreter, for example; Node.js's event loop is single-threaded — no CPU parallelism for JS code, only I/O concurrency).
- For processes: each process runs independently on any available core — no GIL issue.

For Node.js specifically: a single Node.js process uses one thread for the event loop. I/O operations are handled by libuv's thread pool (default 4 threads) and the OS, but JS execution is single-threaded. True CPU parallelism in Node.js requires `worker_threads` (shared memory within a process) or `child_process` / `cluster` (separate processes with separate memory spaces).

## Section 2: Memory Layout

**Q6. Describe the virtual memory layout of a process in detail.**
A: Every process sees its own private virtual address space — typically 48 bits on x86-64 Linux (128 TB user space). The layout from low to high addresses:

```
High addresses (kernel space — not accessible from user mode)
┌────────────────────────────────────────────────────────┐
│  Kernel space                                          │
│  (OS code, kernel stacks, page tables — always mapped, │
│   accessible only in kernel mode)                      │
├────────────────────────────────────────────────────────┤
│  Stack        (grows downward ↓)                       │
│  - Local variables, function call frames               │
│  - Return addresses, saved registers                   │
│  - One stack per thread                                │
│  - Default size: 8MB on Linux (ulimit -s)              │
├────────────────────────────────────────────────────────┤
│  (unmapped gap — stack overflow causes SIGSEGV here)   │
├────────────────────────────────────────────────────────┤
│  Memory-mapped region (mmap)                           │
│  - Shared libraries (.so / .dll) — mapped here         │
│  - File mappings (mmap(2) calls)                       │
│  - Anonymous mappings (large malloc allocations)       │
├────────────────────────────────────────────────────────┤
│  Heap         (grows upward ↑)                         │
│  - Dynamic allocations (malloc / new / Buffer.alloc)   │
│  - Managed by the allocator (glibc, tcmalloc, jemalloc)│
│  - Extended via brk(2) / sbrk(2) syscalls             │
├────────────────────────────────────────────────────────┤
│  BSS segment  (uninitialized globals)                  │
│  - Global and static variables not explicitly init'd   │
│  - Zero-initialized by the OS at process start         │
│  - No space in the executable file — the OS zeros it   │
├────────────────────────────────────────────────────────┤
│  Data segment (initialized globals)                    │
│  - Global and static variables with explicit values    │
│  - Read-write: const globals go in rodata (below)      │
├────────────────────────────────────────────────────────┤
│  rodata       (read-only data)                         │
│  - String literals, const globals                      │
│  - Write attempt → SIGSEGV (segment fault)             │
├────────────────────────────────────────────────────────┤
│  Text segment (code)                                   │
│  - Compiled machine instructions                       │
│  - Read-only + executable (enforced by page permissions)│
│  - Shared between threads — never duplicated           │
└────────────────────────────────────────────────────────┘
Low addresses (0x0 — NULL pointer, unmapped, SIGSEGV on access)
```

Key properties:
- **Virtual, not physical** — this is the process's view. The OS maps virtual pages to physical frames via the page table. Two processes can have the same virtual address pointing to different physical memory.
- **Copy-on-write for `fork()`** — after `fork()`, parent and child share the same physical pages. When either writes, the OS copies the page for the writer. This makes `fork()` cheap even for large processes.
- **Shared libraries mapped once** — the `.text` of `libc.so` is mapped into every process's virtual address space, but only one physical copy exists in RAM. Multiple processes share the same physical pages for read-only library code.

**Q7. What is the stack, and what exactly happens during a function call at the memory level?**
A: The stack is a contiguous region of virtual memory used for the function call mechanism — it stores stack frames. Each function call creates a new frame on top of the stack; each return removes it. The Stack Pointer (SP/RSP) always points to the top of the current frame.

What a stack frame contains:
- **Return address** — where to jump after the function returns (pushed by the `call` instruction).
- **Saved frame pointer** (RBP on x86-64) — the caller's base pointer, so the callee can restore it.
- **Local variables** — variables declared inside the function body.
- **Saved registers** — callee-saved registers the function uses and must restore.
- **Arguments** — on x86-64 System V ABI: first 6 integer args in registers (RDI, RSI, RDX, RCX, R8, R9); overflow args spill to the stack.

A function call sequence (x86-64):
```
caller:
  mov  rdi, arg1       ; first argument in register
  call myFunction      ; push return address, jump to myFunction

myFunction:
  push rbp             ; save caller's frame pointer
  mov  rbp, rsp        ; establish new frame pointer
  sub  rsp, 32         ; allocate space for local variables
  ; ... function body ...
  mov  rsp, rbp        ; restore stack pointer
  pop  rbp             ; restore caller's frame pointer
  ret                  ; pop return address, jump back to caller
```

Stack overflow: if a function recurses too deeply (or allocates a huge local array), the stack grows past its limit into the unmapped guard page. The CPU raises a page fault; the OS sends `SIGSEGV`. Default stack size on Linux: 8MB (`ulimit -s`). Node.js default V8 stack: ~10,000 frames (configurable with `--stack-size`).

**Q8. What is the heap, and how does dynamic memory allocation work at the OS level?**
A: The heap is the region for dynamic (runtime) allocations — memory whose size or lifetime isn't known at compile time. In C, `malloc()`; in C++, `new`; in Node.js, V8's heap manages JavaScript objects; the OS-level `Buffer.allocUnsafe()` allocates outside V8's heap using `malloc`.

Two layers of allocation:

**Layer 1 — OS primitives:**
- `brk(addr)` / `sbrk(size)` — extends the heap segment (data break) upward. Simple but forces sequential allocation.
- `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)` — allocates a new anonymous memory region anywhere in the virtual address space. Used for large allocations (glibc uses `mmap` for allocations > 128KB by default).

**Layer 2 — Allocator (glibc malloc / tcmalloc / jemalloc):**
The allocator sits between application code and the OS. It requests large chunks from the OS (via `brk` or `mmap`) and subdivides them into smaller allocations:
- Maintains free lists per size class (small, medium, large).
- On `malloc(n)`: find a free block of the right size class; if none, request more from OS.
- On `free(ptr)`: return the block to the free list; coalesce adjacent free blocks.
- Does NOT return memory to the OS immediately — retains it in the free list for future `malloc` calls. This is why RSS (Resident Set Size) stays high even after freeing large objects.

Node.js heap specifics: V8 manages its own heap for JS objects (separate from glibc's heap). The V8 heap is divided into spaces: new space (young generation, small, ~1-8MB), old space (survived GC cycles), code space (JIT-compiled code), large object space (objects > 512KB). `process.memoryUsage()` exposes these: `heapUsed`, `heapTotal`, `external` (C++ objects referenced from JS), `rss` (total physical memory used by the process).

**Q9. What is virtual memory, and why does each process get its own address space?**
A: Virtual memory is the OS abstraction that gives each process the illusion of having the entire address space to itself, regardless of how much physical RAM is available or how many other processes are running.

The hardware page table (walked by the MMU — Memory Management Unit) translates virtual addresses to physical addresses transparently on every memory access. The OS manages what's in the page table; the CPU uses it.

Why each process gets its own address space:

**Isolation and security:** Process A cannot access Process B's memory because Process B's physical pages are not mapped into Process A's page table. This is enforced in hardware — a stray pointer in one process causes a page fault in that process only, not corruption of another's data.

**Simplified programming model:** Every process can compile to the same virtual addresses (e.g., its text segment always starts at `0x400000` on Linux x86-64). No process needs to know where in physical RAM it will land.

**Overcommit and demand paging:** The OS can allocate more virtual memory than physical RAM exists. Pages are only brought into physical RAM when actually accessed (demand paging). `malloc(1GB)` succeeds immediately — physical pages are only allocated as the memory is written.

**Shared libraries with private data:** Multiple processes share the same physical pages for read-only code (`.text` of `libc.so`) while each having private physical pages for their writable data. The same virtual address in two processes can map to the same physical page (read-only code) or different physical pages (private data).

**Q10. What is a page fault, and what are the different types?**
A: A page fault is a hardware exception raised by the CPU's MMU when a memory access cannot be satisfied by the current page table — the virtual address either isn't mapped or is mapped with insufficient permissions. The CPU pauses the faulting instruction and transfers control to the OS page fault handler.

Three types:

**Minor page fault (soft fault):**
The page exists in physical RAM but isn't mapped in this process's page table. Common causes: first access to a demand-paged anonymous region (`mmap` or `malloc`), or a page that was unmapped but is still in the page cache (shared library accessed for the first time by a new process). Resolution: the OS updates the page table entry to point to the existing physical frame. No disk I/O. Fast (~microseconds).

**Major page fault (hard fault):**
The page is not in physical RAM — it's on disk (in swap or backing file). The OS must read the page from disk, find a physical frame for it (possibly evicting another page), update the page table, and resume the instruction. Disk I/O required. Slow (~milliseconds). A process that major-faults heavily is thrashing — causing significant latency.

**Invalid (segmentation fault — SIGSEGV):**
The virtual address is not mapped at all (null pointer dereference, out-of-bounds array access past the end of the heap) or the access violates permissions (write to read-only text segment, execute on non-executable page). The OS cannot satisfy the access. It sends `SIGSEGV` to the process, which terminates with "Segmentation fault (core dumped)" unless the signal is caught.

In Node.js / production systems: `ENOMEM` during `mmap` means the system ran out of virtual address space or has too many memory mappings (`vm.max_map_count` on Linux). OOM (Out of Memory) killer sends `SIGKILL` when physical RAM + swap is exhausted and the OS decides to kill the process rather than let the system grind to a halt.

## Section 3: Context Switching

**Q11. What is a context switch, and what exactly happens during one?**
A: A context switch is the OS operation of saving the complete CPU state of one thread (or process) and restoring the CPU state of another, so a different thread can run on the CPU. It is the fundamental mechanism that enables multitasking.

Steps during a context switch (thread A → thread B, same process):

```
1. Timer interrupt fires (or thread A blocks on I/O / calls yield)
   → CPU switches to kernel mode

2. Kernel saves Thread A's state into A's TCB / task_struct:
   - All general-purpose registers (RAX, RBX, RCX, ... R15)
   - Program Counter (RIP) — the instruction A was about to execute
   - Stack Pointer (RSP) — top of A's stack
   - Flags register (RFLAGS)
   - Floating-point / SSE / AVX registers (if used)
   - Kernel stack pointer

3. Scheduler runs: picks Thread B as next to run

4. Kernel restores Thread B's state from B's TCB:
   - Restores all registers from B's saved state
   - Restores RSP → now pointing to B's stack
   - Restores RIP → B's next instruction

5. CPU switches back to user mode, resumes executing at B's RIP
```

**Inter-process context switch (Thread A in Process X → Thread B in Process Y):**
All the above, plus:
- **Page table switch** — load Process Y's page table root (CR3 register on x86-64) into the MMU. This is the expensive part: it invalidates the Translation Lookaside Buffer (TLB), which is the CPU's cache of recent virtual-to-physical mappings. All subsequent memory accesses by Process Y must re-walk the page table until the TLB is re-warmed. With PCID (Process-Context Identifiers), modern CPUs can retain TLB entries per process — reducing (not eliminating) this cost.

Context switch costs:
- **Direct cost:** saving/restoring registers, calling the scheduler. ~1–10 microseconds.
- **Indirect cost (cache effects):** the switching thread's L1/L2 cache lines are now in the cache for the process that ran before it, not the current one. The resumed thread incurs cache misses until its working set is back in cache. This is often the dominant cost for CPU-bound workloads.
- **TLB flush cost** (inter-process only): ~hundreds of nanoseconds to milliseconds depending on TLB size and PCID support.

**Q12. What is the difference in context switch cost between threads of the same process vs threads of different processes?**
A: The difference is primarily in what the OS must do to switch memory contexts:

**Same-process thread switch:**
- Save/restore registers (mandatory for both cases).
- No page table switch — both threads share the same virtual address space. The MMU's page table base register (CR3) stays the same.
- No TLB flush — virtual-to-physical mappings are the same.
- The scheduler still runs to pick the next thread.
- Cost: ~1–5 microseconds on modern hardware.

**Different-process thread switch:**
- Save/restore registers (same as above).
- **Page table switch** — load the new process's page table root into CR3.
- **TLB flush** (full or partial with PCID) — invalidates cached virtual-to-physical translations.
- New process may have a cold CPU cache (its working set was evicted while it wasn't running).
- Cost: ~5–50 microseconds, dominated by TLB refill and cache warming.

Practical implication for backend architecture: this is why multi-threaded servers (Node.js cluster, NestJS with worker_threads) can achieve higher throughput than multi-process servers for request handling when requests share data — the cost of a context switch between threads serving two requests is lower than between processes. However, process isolation (crash in one process doesn't affect others) often outweighs the context switch cost difference for production systems.

**Q13. What is the difference between preemptive and cooperative (non-preemptive) scheduling?**
A:

**Preemptive scheduling:**
The OS can interrupt a running thread at any time (via a hardware timer interrupt) and context-switch to another thread, regardless of whether the running thread has yielded. The thread has no say in when it loses the CPU. Modern OS schedulers (Linux CFS, Windows scheduler) are preemptive.

Consequence: threads must use synchronisation primitives (mutexes, semaphores, atomic operations) to protect shared data, because the OS can interrupt at any point — even in the middle of a multi-step data structure update.

**Cooperative (non-preemptive) scheduling:**
A thread runs until it voluntarily yields the CPU — by calling `yield()`, blocking on I/O, or explicitly sleeping. The OS cannot forcibly interrupt it. Older OSes (classic Mac OS, Windows 3.x) used cooperative multitasking; so does the Node.js event loop for JS code.

Node.js event loop is cooperative: JavaScript callbacks run to completion before the next callback is started. The event loop cannot preempt a running callback. This means: a CPU-intensive synchronous computation in a callback blocks the entire event loop — no other callbacks, timers, or I/O events are processed while it runs. This is why `fs.readFileSync()` in a request handler is catastrophic for throughput — it blocks the event loop for all other requests.

The distinction matters for interview answers: when asked "why is long synchronous computation in Node.js bad?" — the answer is cooperative scheduling and the single-threaded event loop, not just "Node.js is single-threaded."

## Section 4: Process Creation and the Fork/Exec Model

**Q14. What is `fork()`, what does it create, and how does copy-on-write make it efficient?**
A: `fork()` is the Unix syscall that creates a new process by duplicating the calling process. The child is an almost exact copy of the parent: same memory contents, same open file descriptors, same signal handlers, same working directory. The differences: the child gets a new PID, `fork()` returns 0 in the child and the child's PID in the parent, and each subsequently runs independently.

```c
pid_t pid = fork();
if (pid == 0) {
  // Child process
  exec("new-program"); // replace this process image with a new program
} else if (pid > 0) {
  // Parent process
  wait(NULL); // optionally wait for child to finish
}
```

**Copy-on-write (CoW):** Naively, `fork()` would need to copy the entire process address space — potentially gigabytes. CoW makes this efficient: instead of copying, the OS marks all parent and child pages as read-only and shared. Both parent and child access the same physical pages. Only when either writes to a page does the OS: (1) allocate a new physical frame, (2) copy the page content into it, (3) update the page table of the writing process to point to the new frame, (4) restore the page as writable. Pages that are never written are never copied.

For Node.js `cluster` module: the master process calls `fork()` for each worker. Because the worker's V8 heap is copy-on-write at fork time, the actual RSS increase per worker is only the pages the worker writes to — shared read-only pages (V8 bytecode, native modules) are shared with zero memory overhead. In practice, each worker adds 20-50MB RSS rather than the full process memory.

**Q15. What is `exec()`, and how does it differ from `fork()`?**
A: `exec()` (a family of syscalls: `execve`, `execl`, `execlp`, etc.) replaces the current process's memory image with a new program — loaded from an executable file. The PID stays the same; everything else is replaced: code, data, heap, stack, and most signal handlers. Open file descriptors survive (unless `O_CLOEXEC` is set).

`fork()` creates a copy of the current process. `exec()` replaces the current process with a new program. The Unix convention for launching a new program is `fork()` + `exec()` (the "fork-exec" pattern):

```
Parent process
  │
  ├─ fork() ──────────────────────────────────────┐
  │                                                │
  │  Parent continues              Child (same PID's CoW copy)
  │                                    │
  │                                    └─ exec("python3 script.py")
  │                                       Child's memory replaced.
  │                                       Now running python3.
  │
  └─ wait() for child (optional)
```

In Node.js: `child_process.spawn("python3", ["script.py"])` does exactly this — forks the Node process, then execs `python3` in the child. `child_process.fork("worker.js")` is different — it forks and keeps running Node.js in the child, loading `worker.js` as the new entry point, with an IPC channel established between parent and child.

**Q16. What is a zombie process, and what causes it?**
A: A zombie process (defunct process) is a process that has terminated — its code is no longer running and its resources (memory, file descriptors) have been freed — but its entry in the process table still exists. The PCB is kept alive so the parent can call `wait()` to retrieve the child's exit status.

Zombie state: the process's `task_struct` remains, memory is freed, it shows as `Z` (zombie) in `ps aux`. It consumes a PID and a small amount of kernel memory for the PCB — no CPU, no memory for the child's address space.

Cause: the parent has not yet called `wait()` / `waitpid()`. Every process that exits normally becomes a zombie briefly. If the parent never calls `wait()`, the zombie persists indefinitely.

Consequences:
- Zombie accumulation exhausts the PID namespace (Linux default: 32,768 PIDs). When PIDs are exhausted, no new processes can be created — the system appears to hang.
- Zombies are not killed by `kill -9` — they're already dead. The fix is to fix the parent (make it call `wait()`), or kill the parent (the zombie is adopted by `init`/PID 1, which calls `wait()` automatically).

In Node.js: `child_process.spawn()` without listening to the `close` or `exit` event can cause zombie accumulation if the Node process doesn't call the equivalent of `wait()`. Node.js does this automatically when you listen to `child.on("exit", ...)` or `child.on("close", ...)` — these events trigger the underlying `wait()`. Unref'd child processes that exit without event listeners can linger as zombies until the Node parent exits.

## Section 5: Process vs Thread — Practical Tradeoffs

**Q17. What are the tradeoffs between multi-process and multi-threaded architectures?**
A: The choice shapes fault tolerance, memory efficiency, communication overhead, and CPU parallelism:

**Multi-process:**

Advantages:
- **Isolation** — a crash, memory corruption, or unhandled exception in one process doesn't affect others. The OS enforces the boundary in hardware.
- **Security** — separate processes can run with different user IDs, reduced capabilities (seccomp, namespaces). Compromise of one process doesn't automatically compromise others.
- **Independent restart** — a worker that crashes can be restarted by the supervisor without restarting the entire application.
- **No shared-state bugs** — no races, no mutex deadlocks from shared mutable state. Communication is explicit (IPC, sockets, pipes).

Disadvantages:
- **Memory overhead** — each process has its own copy of the heap, even if the data is logically the same. Node.js cluster: 8 workers × 100MB = 800MB RSS (though CoW reduces this in practice).
- **IPC cost** — processes communicate via pipes, sockets, or shared memory. Serialisation (JSON, msgpack, Protocol Buffers) and copying add latency that in-process shared memory avoids.
- **Context switch cost** — inter-process switches flush the TLB; intra-process thread switches don't.

**Multi-threaded:**

Advantages:
- **Shared memory** — threads communicate via shared data structures in the same heap. Zero-copy, low-latency.
- **Lower memory footprint** — one heap, one set of shared libraries, one set of file descriptors. 8 threads vs 8 processes: potentially 8× less memory.
- **Cheaper context switching** — no TLB flush; shared page table.

Disadvantages:
- **Shared-state bugs** — data races, deadlocks, priority inversion. Any thread can corrupt any other thread's data structures without hardware enforcement. These bugs are notoriously difficult to reproduce and debug.
- **Crash propagation** — a segfault in one thread kills the entire process (all threads die).
- **Synchronisation overhead** — mutex contention under high thread counts causes threads to block each other; the gains from parallelism erode.

For Node.js backends the decision is made for you architecturally:
- **Cluster** (multi-process): each worker is a full Node.js process with its own event loop and V8 heap. Fault isolation. Communication via IPC or Redis. Best for HTTP servers where requests are independent.
- **Worker threads** (multi-threaded): share the same process's memory space. Used for CPU-intensive work (image processing, cryptography, large data aggregation) that would otherwise block the event loop. Worker threads have independent event loops but can share memory via `SharedArrayBuffer`.

**Q18. How does the Linux kernel implement threads — are they truly different from processes?**
A: In Linux, threads are not a fundamentally different concept from processes at the kernel level. Both are implemented as tasks (instances of `task_struct`). The `clone()` syscall creates both processes and threads — the flags passed to `clone()` determine what is shared:

```c
// fork() is essentially:
clone(SIGCHLD, ...);                      // share nothing significant

// pthread_create() is essentially:
clone(
  CLONE_VM        |  // share virtual address space (heap, globals)
  CLONE_FS        |  // share filesystem state (cwd, root)
  CLONE_FILES     |  // share file descriptor table
  CLONE_SIGHAND   |  // share signal handlers
  CLONE_THREAD    |  // same thread group (same TGID = PID to user space)
  CLONE_SETTLS    |  // set up thread-local storage
  SIGCHLD,
  ...
);
```

Each thread gets its own `task_struct` with its own stack, PC, registers, and TID. The `CLONE_THREAD` flag puts all threads in the same thread group (TGID), which is what `getpid()` returns — so all threads in a process appear to have the same PID from user space, while each has a unique TID retrievable via `gettid()`.

The implication: Linux's scheduler sees processes and threads identically — they're all `task_struct` entries. The scheduler doesn't know or care that 8 tasks happen to share the same address space. This has a consequence: if a process spawns 8 threads, those 8 threads compete with threads of other processes for CPU time on an equal footing — there's no automatic "this process gets X% of CPU split across its threads" unless you use `cgroups` to enforce it.

**Q19. What is the difference between a process's virtual address space size and its physical memory usage (RSS)?**
A: Two important metrics:

**Virtual address space (VSZ / VIRT in `top`):** The total virtual address space allocated to the process — every page that has been `mmap`'d, `malloc`'d, or otherwise mapped, regardless of whether it's backed by physical RAM. A Node.js process might show 1.5GB VSZ because V8 reserves large virtual address regions upfront (for its heap and JIT code cache), even though most of those pages are never touched.

**Resident Set Size (RSS / RES in `top`):** The physical RAM currently occupied by this process — pages that are in physical memory right now. This excludes:
- Pages swapped out to disk.
- Pages that are mapped (in VSZ) but never accessed (demand paging — they don't get physical frames until first access).
- Pages mapped from files but not currently needed (the page cache can evict and reload them).

**Proportional Set Size (PSS):** Like RSS but divides shared pages by the number of processes sharing them. If `libc.so` occupies 1MB of RAM and is shared by 100 processes, each process's PSS includes 10KB for libc (1MB / 100). PSS is the most accurate measure of a process's true memory cost.

In Node.js: `process.memoryUsage()` returns:
```javascript
{
  rss:          50_331_648,   // total physical pages (RSS) in bytes
  heapTotal:    16_777_216,   // V8 heap: total allocated (committed)
  heapUsed:      9_126_320,   // V8 heap: actually in use by JS objects
  external:      1_134_216,   // C++ objects referenced from JS (Buffers, etc.)
  arrayBuffers:    524_288,   // SharedArrayBuffer + ArrayBuffer allocations
}
```
`rss > heapTotal + external` because RSS includes the V8 code space, stack, native modules, and other non-heap mappings.

## Section 6: Inter-Process Communication

**Q20. What are the main IPC mechanisms, and when do you choose each?**
A: IPC (Inter-Process Communication) is necessary because processes have isolated address spaces — sharing data requires going through the kernel or explicit shared memory:

**Pipes (anonymous pipes):**
- Unidirectional byte stream between parent and child (related processes).
- Created with `pipe(2)`; used implicitly by Node's `child_process.spawn()` for stdin/stdout/stderr.
- In-kernel buffer (~64KB on Linux); writes block when full.
- Use for: streaming command output, small data between parent and child.

```javascript
// Node.js: pipe between processes
const child = spawn("grep", ["error"], { stdio: ["pipe", "pipe", "pipe"] });
child.stdin.write(logData);
child.stdout.on("data", (chunk) => process.stdout.write(chunk));
```

**Named pipes (FIFOs):**
- Like pipes but with a filesystem path — unrelated processes can communicate.
- `mkfifo(1)` / `mkfifo(2)`. Persistent in the filesystem.
- Use for: simple unidirectional IPC between unrelated processes.

**Unix domain sockets:**
- Full-duplex, bidirectional byte stream or datagram channel via a filesystem path.
- Much faster than TCP localhost sockets (no network stack overhead, no IP headers).
- Support `sendmsg` with `SCM_RIGHTS` — can pass file descriptors between processes.
- Use for: Node.js cluster IPC, communication with local daemons (PostgreSQL socket, Redis socket, Docker daemon).

**Shared memory (`shm_open`, `mmap` with `MAP_SHARED`):**
- Map the same physical pages into multiple processes' virtual address spaces.
- Fastest IPC — zero-copy, no kernel involvement after setup.
- Requires explicit synchronisation (mutex, semaphore) — no automatic serialisation.
- In Node.js: `SharedArrayBuffer` enables shared memory between worker threads (same process). Cross-process shared memory requires native addons or external mapping.
- Use for: high-throughput data sharing between processes (video frames, real-time sensor data, large lookup tables).

**Message queues (POSIX `mq_open`, SysV `msgget`):**
- Kernel-managed queue of typed messages. Producer posts messages; consumer reads them.
- Persistent across process lifecycle.
- Use for: task queues between processes (though Redis/RabbitMQ are more common in practice for microservices).

**Signals:**
- Asynchronous notification from kernel or process to process (kill(2)).
- Very limited: signal number only (one integer). No data payload.
- Use for: `SIGTERM` for graceful shutdown, `SIGHUP` for config reload, `SIGUSR1`/`SIGUSR2` for custom application signals.
- Node.js: `process.on("SIGTERM", gracefulShutdown)`.

**Sockets (TCP/UDP over loopback):**
- Full network stack but on localhost. More overhead than Unix sockets.
- Use for: microservices communicating within a host (if Unix sockets aren't available), or when the communication must also work over a network.

## Section 7: Scenario / System Design Style Questions

**Q21. "Node.js is single-threaded, yet it handles thousands of concurrent connections. How? What are the limits?"**
A: Node.js achieves concurrency through the **event loop + non-blocking I/O** — not through thread-per-connection parallelism.

The mechanism:
1. A connection arrives; Node.js registers it with the OS's I/O event notification system (`epoll` on Linux, `kqueue` on macOS, `IOCP` on Windows).
2. The JS callback associated with this connection is queued but not run yet.
3. Node.js immediately handles the next event — another connection, a timer, whatever is ready.
4. When the OS signals that data has arrived (the socket is readable), the callback for that connection runs to completion, then yields back to the event loop.

No thread is blocked waiting for I/O. One OS thread handles the event loop; libuv's thread pool (default 4 threads) handles file I/O, DNS resolution, and a few other syscalls that lack async kernel support.

**The limits:**

- **CPU-bound work blocks the event loop.** A synchronous computation (sorting a 10MB array, bcrypt hash, image resize) holds the event loop thread. All other connections wait. Fix: `worker_threads` for CPU work; never do heavy CPU work synchronously in a request handler.
- **Thread pool exhaustion.** `fs.readFile` uses the libuv thread pool. If all 4 threads are busy with long disk reads, subsequent `fs.readFile` calls queue and wait. Fix: `UV_THREADPOOL_SIZE=8` (or more) environment variable; or use streams instead of reading entire files.
- **Single point of failure.** One unhandled exception kills the process and all connections. Fix: `cluster` module or process manager (PM2) to run multiple workers; `uncaughtException` handler as a last resort.
- **Memory limits.** One process, one V8 heap, one GC. Default heap limit is ~1.5GB on 64-bit systems (configurable with `--max-old-space-size`). Fix: multiple processes via `cluster`.
- **No true CPU parallelism for JS.** The event loop is one thread. On a 16-core machine, one Node.js process uses 1 core for JS execution. Fix: `cluster` (N processes, one per core) or `worker_threads` for parallelism within one process.

**Q22. "You're debugging a production Node.js service that's using 2GB of RAM on a machine with 4GB. RSS is high but heapUsed is only 200MB. What are the possible causes?"**
A: The gap between `heapUsed` (200MB) and RSS (2GB) points to memory outside the V8 heap:

**`external` (native/C++ memory):** `Buffer.alloc()` and `Buffer.allocUnsafe()` allocate outside the V8 heap using `malloc`. If the service processes large binary payloads (file uploads, NACH mandate batch files, payment gateway responses as raw buffers) and these are retained in memory (in a cache or global variable), external memory grows without appearing in `heapUsed`.

Check: `process.memoryUsage().external`. If this is large, look for global `Buffer` references and large `stream` buffers not being consumed.

**Memory-mapped files and shared libraries:** Every native module (`bcrypt`, `sharp`, database drivers with native bindings) maps its `.so` file into the process's virtual address space. These map-backed pages appear in RSS but not in the V8 heap. A service with 20 native modules can accumulate hundreds of MB in shared library mappings.

Check: `/proc/<pid>/maps` or `pmap -x <pid>` to see all memory mappings.

**V8 code space (JIT-compiled machine code):** V8 JIT-compiles hot JavaScript functions into machine code, which lives in the code space — counted in RSS but not in `heapUsed`. A large codebase with many hot paths can generate hundreds of MB of JIT code. `--max-old-space-size` doesn't cap the code space.

**Heap fragmentation:** The allocator holds free pages in its free list but hasn't returned them to the OS. `heapUsed` is 200MB but `heapTotal` (V8 committed heap) might be 800MB — 600MB is allocated but currently empty (holes from previous objects that were GC'd). This appears as RSS because the pages are still physically backed.

Check: `heapTotal - heapUsed` difference. If large, heap fragmentation is likely. Consider `--expose-gc` + manual `global.gc()` in a diagnostic context to see if RSS drops.

**Memory leak in native addon:** A native C++ addon that doesn't properly free its objects will grow `external` memory indefinitely. Harder to diagnose — requires heap profiling at the native layer.

Diagnostic approach: take heap snapshots at 10-minute intervals using `v8.writeHeapSnapshot()`, compare in Chrome DevTools Memory tab, and look for growing retained object counts.

**Q23. "You're designing a payment processing microservice that must handle NACH batch processing (1M mandates), real-time API requests, and async webhook delivery. How do you use processes and threads to structure this?"**
A: The three workloads have fundamentally different resource profiles — they should run in separate processes, not threads, for isolation:

**Process 1 — API server (Node.js cluster, N = CPU cores):**
Handles real-time HTTP requests (payment initiation, status queries). Stateless, I/O-bound. Multiple worker processes via `cluster`, one per CPU core. Each worker has an independent event loop. If one worker crashes, others continue. Load balancer (ALB or nginx) distributes connections. RSS per worker: ~150MB. For 8 cores: 8 × 150MB = 1.2GB.

**Process 2 — NACH batch processor (separate Node.js process or cluster):**
Processing 1M mandates is CPU- and I/O-intensive. Run as a separate process so a crash or OOM during batch processing doesn't kill the API server. Use `worker_threads` within this process for CPU-parallel mandate validation (PAN verification batching, BRE rule evaluation) since they share the mandate data in-memory via `SharedArrayBuffer`. The batch processor and API server should NOT share the same process — a batch OOM would kill real-time request handling.

**Process 3 — Webhook delivery worker:**
Async, retry-heavy, long-lived connections to external endpoints. Separate process means: webhook delivery failures (OOM, crash from a malformed payload) don't affect the API or batch. Uses its own connection pool to the DB (for idempotency checking) and its own outbound HTTP connection pool. Separate rate limiting per external endpoint without interfering with API rate limits.

**Cross-process communication:**
- API → batch: message via Redis (job queue — BullMQ). The API server enqueues a mandate batch job; the batch processor dequeues and processes.
- Batch → webhook: completed mandates written to DB; webhook worker polls or subscribes to DB events (pg NOTIFY / LISTEN).
- All processes → shared state: Redis for distributed rate limiting, idempotency keys, distributed locks. PostgreSQL for durable state.

**Supervisor (PM2 / systemd):**
Monitors all three process groups; restarts crashed workers; aggregates logs; enforces memory limits (`max_memory_restart` in PM2). Sends `SIGTERM` for graceful shutdown (drain in-flight requests, finish current mandate batch, flush in-flight webhooks).

This architecture isolates blast radius: a NACH batch OOM kills the batch worker but API requests continue uninterrupted.

## Quick Reference: Process vs Thread

| Dimension | Process | Thread |
|---|---|---|
| **Address space** | Private (isolated) | Shared with siblings |
| **Memory overhead** | Full copy (CoW-optimised at fork) | Stack only (~1-8MB each) |
| **Communication** | IPC: pipes, sockets, shared mem | Direct shared memory access |
| **Crash isolation** | Crash stays in process | Crash kills all threads in process |
| **Context switch cost** | High (TLB flush, page table switch) | Low (no address space switch) |
| **Creation cost** | High (fork + exec) | Low (clone with shared mm) |
| **Data races** | Not possible across processes | Possible — requires synchronisation |
| **PCB / TCB** | Full PCB (all resources) | TCB (registers, stack, PC only) |
| **Linux primitive** | `fork()` + `exec()` | `clone(CLONE_VM | CLONE_FILES …)` |
| **Node.js equivalent** | `child_process`, `cluster` | `worker_threads` |
| **When to use** | Fault isolation, multi-core HTTP | CPU-bound work sharing data |

**Tip for the interview:** At 5 YOE, process/thread questions don't come as "define PCB" — they come embedded in system design ("how would you scale this Node.js service?"), debugging ("why is RSS 2GB when heapUsed is 200MB?"), or correctness questions ("why is this shared global in a Node.js cluster not behaving as expected?"). The answers that land connect the fundamentals — separate address spaces, the PCB as the kernel's record of state, context switch costs, copy-on-write after fork — to real architectural decisions: why `cluster` gives fault isolation that `worker_threads` doesn't, why a NACH batch processor should be a separate process from the API server, and why a long synchronous computation in Node.js blocks all concurrent requests. Have one concrete story ready about a production memory or concurrency issue — and walk through it using the correct terminology.
