# Operating Systems / Computer Science: CPU Scheduling Algorithms — FCFS, SJF, Round Robin, Priority, Multilevel Queue — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is CPU scheduling, and why does it exist?**
A: CPU scheduling is the operating system mechanism that decides which process (or thread) in the ready queue gets to use the CPU next, and for how long. It exists because modern systems are multiprogrammed — many processes compete for a single CPU simultaneously — and the CPU can only execute one process at a time on a single core. Without scheduling:
- Short, interactive tasks would wait behind long batch jobs indefinitely.
- The CPU would sit idle during I/O waits even though other processes are ready to run.
- Response time, throughput, and fairness would be uncontrollable.

The scheduler runs whenever the CPU becomes free: when a process terminates, blocks on I/O, voluntarily yields, or (in preemptive systems) when a timer interrupt fires. Its job is to pick the next process from the ready queue according to the scheduling policy and hand the CPU to it.

**Q2. What is the difference between preemptive and non-preemptive scheduling?**
A: The distinction is whether the OS can forcibly remove the CPU from a running process:

- **Non-preemptive (cooperative)** — once a process is given the CPU, it runs until it voluntarily gives it up: by completing, blocking on I/O, or explicitly yielding. The scheduler only runs at these voluntary handoff points. Simple to implement; no mid-execution context switch overhead. Dangerous: a misbehaving or infinite-loop process starves everything else indefinitely.
- **Preemptive** — the OS can interrupt a running process at any time — typically via a hardware timer interrupt — and run the scheduler. The interrupted process is moved back to the ready queue; another process gets the CPU. Required for interactive systems where response time guarantees matter. Introduces complexity: shared data structures need synchronization because a process can be interrupted mid-update.

FCFS and non-preemptive SJF are non-preemptive. Round Robin, preemptive SJF (SRTF), and most Priority variants are preemptive.

**Q3. What are the key metrics used to evaluate a scheduling algorithm?**
A: Six standard metrics, each capturing a different aspect of scheduler quality:

- **CPU utilization** — percentage of time the CPU is doing useful work (not idle). Target: as high as possible (100% in theory; 40–90% in practice).
- **Throughput** — number of processes completed per unit time. Higher is better.
- **Turnaround time** — elapsed time from process submission to process completion: `completion time − arrival time`. Includes waiting, executing, and I/O time.
- **Waiting time** — total time a process spends in the ready queue waiting for the CPU: `turnaround time − burst time`. The primary metric most scheduling algorithms try to minimize.
- **Response time** — time from submission (or request) to the *first* response — not completion. Critical for interactive systems where the user needs to see *something* quickly even before the task finishes.
- **Fairness** — whether each process gets a proportional share of the CPU over time. Starvation — a process waiting indefinitely — is the failure mode of unfair schedulers.

No single algorithm optimizes all six simultaneously. The choice depends on the workload: batch systems favor throughput and turnaround; interactive systems favor response time and fairness; real-time systems favor deadline guarantees.

**Q4. What is a Gantt chart, and how do you use it to compute scheduling metrics?**
A: A Gantt chart is a horizontal timeline showing which process occupies the CPU at each moment in time. It's the standard tool for tracing scheduling algorithms by hand:

```
Process:  | P1  |  P2  |   P3   | P1  |
Time:     0     3      7        14    18
```

From the Gantt chart, compute per-process metrics:
- **Completion time** — the time the process finishes (last block's right edge).
- **Turnaround time** = completion time − arrival time.
- **Waiting time** = turnaround time − total CPU burst time.
- **Response time** = time of first CPU assignment − arrival time.

Average metrics are summed across all processes and divided by the process count. Working through a Gantt chart manually for a given process mix and algorithm is the standard interview question format for this topic.

## Section 2: First-Come, First-Served (FCFS)

**Q5. How does FCFS work?**
A: FCFS is the simplest scheduling algorithm: processes are served in the order they arrive in the ready queue — a pure first-in, first-out (FIFO) queue. The first process to arrive gets the CPU first; it runs to completion (non-preemptive); then the next process in the queue runs; and so on. No priority, no burst-time estimation, no preemption.

```
Arrival order: P1 (burst=24), P2 (burst=3), P3 (burst=3)

Gantt chart:
| P1                        | P2  | P3  |
0                           24   27   30

Waiting times: P1=0, P2=24, P3=27
Average waiting time: (0+24+27)/3 = 17ms
```

**Q6. What is the convoy effect, and why does it make FCFS unsuitable for time-sharing systems?**
A: The convoy effect is the phenomenon where many short processes pile up behind one long process, waiting for it to release the CPU. Every short process is effectively "convoyed" by the slow one — forced to travel at the speed of the slowest member.

In the example above: if P1 had arrived after P2 and P3 (FCFS with P2, P3, P1), average waiting time drops from 17ms to 3ms. The order of arrival — which has nothing to do with process importance or length — determines efficiency. In a time-sharing system with mixed interactive (short) and batch (long) workloads, the convoy effect means interactive users experience unpredictable, often terrible response times whenever a long batch job arrives first. FCFS gives no response-time guarantees, which disqualifies it for interactive use.

**Q7. When is FCFS actually appropriate?**
A: FCFS works well in three contexts:
- **Batch processing systems** with roughly uniform job lengths — the convoy effect is minimal when all jobs are similar in size.
- **Print spoolers and similar queues** — jobs naturally queue in submission order, and fairness-by-arrival is the expected behavior.
- **As a tiebreaker** within other algorithms — when two processes have equal priority or equal remaining burst time, FCFS among equals is a simple, unbiased tiebreaker.
- **Disk scheduling (FCFS variant)** — not CPU scheduling, but the same logic applies to I/O queues where simplicity matters more than optimal seek time.

**Q8. Walk through a FCFS example with non-zero arrival times.**
A: With non-zero arrival times, you must account for CPU idle periods when no process has arrived yet:

```
Process  Arrival  Burst
P1         0        5
P2         2        3
P3         4        8
P4         6        2

Gantt chart (processes run to completion in arrival order):
| P1  |  P2  |       P3       | P4 |
0     5      8               16   18

Completion times: P1=5, P2=8, P3=16, P4=18
Turnaround times: P1=5-0=5, P2=8-2=6, P3=16-4=12, P4=18-6=12
Waiting times:    P1=0, P2=3, P3=4, P4=10
Average waiting:  (0+3+4+10)/4 = 4.25ms
```

Note: if there were a gap where no process had arrived when the CPU became free, the CPU sits idle until the next arrival — FCFS is non-preemptive and has no mechanism to re-order.

## Section 3: Shortest Job First (SJF)

**Q9. How does SJF work, and what makes it optimal?**
A: SJF (also called Shortest Job Next, SJN) always picks the process with the *shortest next CPU burst* from the ready queue. Among all non-preemptive algorithms, SJF is provably optimal for minimizing average waiting time — it is the scheduling equivalent of the "shortest processing time first" rule in queueing theory.

Intuition: putting the shortest job first minimizes the waiting time accumulated by all subsequent jobs. If you have jobs of lengths 2, 5, and 10, serving them as [2, 5, 10] gives waiting times of [0, 2, 7] (average 3); serving them as [10, 5, 2] gives [0, 10, 15] (average 8.3). The short job "costs" little to everyone who waits behind it; the long job "taxes" every subsequent process with its full duration.

```
Process  Arrival  Burst
P1         0        6
P2         0        8
P3         0        7
P4         0        3

Gantt chart (all arrive at 0; pick shortest first):
| P4 | P1    |  P3   |    P2    |
0    3       9      16         24

Waiting times: P1=3, P2=16, P3=9, P4=0
Average waiting: (3+16+9+0)/4 = 7ms
(FCFS order P1,P2,P3,P4 would give average waiting: 10.25ms)
```

**Q10. What is the fundamental problem with SJF in practice?**
A: **Future burst time is unknown.** SJF requires knowing how long each process will run next — but the OS cannot know this in advance. A process could exit, block on I/O, or run for an arbitrary duration. SJF as described is a theoretical ideal, not a directly implementable algorithm.

The practical solution: **predict** the next burst length using an exponential average (aging formula) of past burst lengths:

```
τ(n+1) = α × t(n) + (1 - α) × τ(n)

where:
  τ(n+1) = predicted next burst
  t(n)   = actual most recent burst
  τ(n)   = previous prediction
  α      = smoothing factor (0 ≤ α ≤ 1), typically 0.5
```

With α = 0.5, recent bursts and historical average are weighted equally. With α close to 1, recent behavior dominates (fast adaptation); with α close to 0, history dominates (stable, slow to adapt). The prediction is never perfect, which means SJF implementations are approximations — optimal in theory, near-optimal in practice.

**Q11. What is Shortest Remaining Time First (SRTF), and how does it differ from SJF?**
A: SRTF is the preemptive version of SJF. Whenever a new process arrives in the ready queue, the scheduler compares its burst time to the *remaining* burst time of the currently running process. If the new process is shorter, it preempts the current process:

```
Process  Arrival  Burst
P1         0        8
P2         1        4
P3         2        9
P4         3        5

Gantt chart:
|P1|   P2   |    P4    |P1 (cont)      |        P3         |
0  1        5         10              17                   26

At t=1: P2 arrives with burst 4 < P1 remaining (7) → P2 preempts P1
At t=5: P2 finishes; P4 (burst 5) < P1 remaining (7) → P4 runs
At t=10: P4 finishes; P1 remaining (7) < P3 (burst 9) → P1 runs
At t=17: P1 finishes; P3 runs

Average waiting: P1=(17-1-7)=9... (computed from Gantt)
```

SRTF gives the minimum possible average waiting time among all preemptive algorithms for a given workload — but it starves long processes if short processes keep arriving, and its preemption overhead is high.

**Q12. What is starvation in SJF/SRTF, and how is it addressed?**
A: Starvation occurs when a long process waits indefinitely because a continuous stream of shorter processes keeps arriving and taking priority. The long process is perpetually skipped — it may never run if the system is always busy with shorter jobs.

The standard remedy is **aging**: gradually increase the effective priority (or decrease the effective burst estimate) of a process the longer it waits. After waiting long enough, even a long process becomes "short enough" to be scheduled. The aging increment is tuned so that a process that waits for a bounded time period will eventually be treated as the shortest available job, guaranteeing forward progress.

## Section 4: Round Robin (RR)

**Q13. How does Round Robin work?**
A: Round Robin is the standard scheduling algorithm for time-sharing systems. Each process is given a fixed time slice called a **quantum** (or time slice, typically 10–100ms). Processes are maintained in a circular FIFO queue. The scheduler picks the process at the front, runs it for one quantum, then:
- If the process finishes within the quantum → it exits; the next process runs.
- If the process needs more time → it is preempted and moved to the *back* of the ready queue; the next process runs.

```
Process  Arrival  Burst
P1         0        24
P2         0        3
P3         0        3
Quantum = 4

Gantt chart:
| P1 | P2  | P3  | P1 | P1 | P1 | P1 | P1 |
0    4     7    10   14   18   22   26   30

Completion: P2=7, P3=10, P1=30
Waiting: P1=(10-4)+(14-14)+(18-18)+(22-22)+(26-26)=6, P2=4, P3=7
Average waiting: (6+4+7)/3 = 5.67ms
```

**Q14. How does the quantum size affect Round Robin's behavior?**
A: The quantum is the single most important tuning parameter in Round Robin:

- **Very small quantum (→ 0)** — approaches ideal processor sharing: every process appears to run simultaneously at 1/N speed. Response time is excellent. But context-switch overhead dominates: most CPU time is spent saving and restoring registers rather than doing useful work. Throughput collapses.
- **Very large quantum (→ ∞)** — degenerates to FCFS: processes rarely get preempted, the queue drains in arrival order, and the convoy effect re-emerges. Response time for short processes becomes terrible.
- **Practical quantum** — should be large enough to make context switching overhead negligible (context switch costs ~1–10µs; quantum of 10–100ms means <1% overhead), but small enough that most interactive requests complete within one quantum (giving sub-quantum response time). The rule of thumb: the quantum should be larger than 80% of CPU bursts, so most processes complete in one slice without being preempted.

Modern Linux uses a variable quantum approach (Completely Fair Scheduler), but the classic Round Robin trade-off remains the conceptual foundation.

**Q15. What is the turnaround time paradox in Round Robin?**
A: Counterintuitively, Round Robin can have *worse* average turnaround time than SJF — even worse than FCFS in some cases — despite having better response time. The reason: short processes that would finish quickly under SJF are repeatedly interrupted and returned to the queue in RR, accumulating waiting time across multiple cycles.

```
Three processes, each with burst=10, quantum=1:
Under RR: all three finish at t=30.
Turnaround for each: 30-0=30. Average: 30.

Under FCFS: P1 finishes at 10, P2 at 20, P3 at 30.
Average turnaround: (10+20+30)/3 = 20.
```

The trade-off is explicit: RR optimizes *response time* (every process gets CPU quickly) at the cost of *turnaround time* (every process also waits repeatedly). For interactive systems where responsiveness matters, this is the right trade-off. For batch systems where you want jobs finished as fast as possible, FCFS or SJF is better.

**Q16. How does Round Robin handle processes that arrive mid-cycle?**
A: New arrivals are added to the back of the ready queue. If a process arrives while another is running its quantum, the new process waits until the running process's quantum expires (or it blocks). If the process arrives exactly when the current quantum expires, the implementation-specific policy determines whether the newly arrived process or the preempted process goes to the back of the queue — this edge case affects fairness subtly and is worth noting in implementation.

## Section 5: Priority Scheduling

**Q17. How does priority scheduling work?**
A: Each process is assigned a numeric priority. The scheduler always picks the highest-priority process from the ready queue. Priority can be defined as either "lower number = higher priority" (common in Unix/Linux, where priority 0 is highest) or "higher number = higher priority" (common in Windows) — the convention varies by system, and knowing which convention a question uses matters for correctness.

Priority scheduling can be either:
- **Non-preemptive** — a running process completes its burst; priority only affects which process is picked next.
- **Preemptive** — if a higher-priority process arrives while a lower-priority process is running, the lower-priority process is immediately preempted.

```
Process  Arrival  Burst  Priority (lower = higher)
P1         0        10      3
P2         0        1       1
P3         0        2       4
P4         0        1       5
P5         0        5       2

Gantt chart (non-preemptive, all arrive at 0):
| P2 | P5    | P1          | P3  | P4 |
0    1       6            16   18   19

Average waiting: (6+0+16+18+1)/5 = 8.2ms
```

**Q18. What are the two sources of priority — internal and external — and how does each arise?**
A: Priorities come from two sources:

- **Internal priorities** are computed by the OS based on measurable process characteristics:
  - Time limits and deadlines (real-time processes have high priority).
  - Memory requirements (processes needing less memory may get higher priority to keep utilization high).
  - Number of open files or I/O devices held.
  - Ratio of CPU burst to I/O burst (I/O-bound processes are often given higher priority because they release the CPU quickly anyway).

- **External priorities** are set by criteria outside the OS — human policy decisions:
  - Process importance to the organization (billing runs before report generation).
  - User or department priority (paid tier gets higher priority than free tier).
  - Explicit `nice` values in Unix (users can voluntarily lower their process priority; only root can raise it).
  - Real-time scheduling classes (`SCHED_FIFO`, `SCHED_RR` in Linux with real-time priorities 1–99 above normal processes).

**Q19. How does priority scheduling cause starvation, and what are the solutions?**
A: Starvation in priority scheduling is the same as in SJF: a steady stream of high-priority processes can indefinitely defer a low-priority process. Unlike SJF where the "priority" is burst length, here the priority is explicit — and if high-priority work never stops arriving, low-priority processes simply never run.

Two standard solutions:

**Aging** — periodically increment the priority of processes that have been waiting a long time. A process that starts at priority 127 (lowest) has its priority incremented every second; after 127 seconds, it has priority 0 (highest) and is guaranteed to run. Aging bounds the maximum waiting time.

```
effective_priority(p) = initial_priority(p) − aging_rate × waiting_time(p)
```

**Priority donation / inheritance** — used to address **priority inversion**: a high-priority process is blocked waiting for a resource held by a low-priority process. If a medium-priority process is running, the high-priority process is effectively blocked by the medium one — a priority inversion. The solution: temporarily donate the high-priority process's priority to the low-priority process so it can complete quickly and release the resource. Used in real-time systems (Mars Pathfinder's famous 1997 priority inversion bug was caused by the absence of this mechanism).

**Q20. What is priority inversion, and why does it matter for real-time systems?**
A: Priority inversion occurs when a high-priority process effectively has lower priority than a lower-priority process due to resource contention through a third process:

```
High-priority H:   waiting for mutex held by L
Medium-priority M: running (preempted L before it released the mutex)
Low-priority L:    waiting to run (was preempted by M), holds the mutex H needs

Result: M runs while H waits — H is effectively lower priority than M,
        even though H > M > L in the priority ordering.
```

In hard real-time systems (spacecraft, medical devices, industrial control), this can cause deadline misses — the high-priority task doesn't complete in time even though it has the highest priority. The NASA Mars Pathfinder mission experienced this in 1997: the spacecraft's software reset repeatedly because a high-priority meteorological task missed its deadline due to priority inversion involving a mutex held by a low-priority bus management task. Priority inheritance protocols (PIP) and priority ceiling protocols (PCP) are the standard defenses.

## Section 6: Multilevel Queue Scheduling

**Q21. What is multilevel queue scheduling?**
A: Multilevel queue scheduling partitions the ready queue into multiple separate queues, each with its own scheduling algorithm. Every process is permanently assigned to exactly one queue based on its type or characteristics — and it never moves between queues. The scheduler must first decide which queue to service (inter-queue scheduling), then pick a process within that queue (intra-queue scheduling).

```
Queue 0 (highest priority): System processes      → FCFS
Queue 1:                    Interactive processes  → Round Robin (quantum=8ms)
Queue 2:                    Interactive editing    → Round Robin (quantum=16ms)
Queue 3:                    Batch processes        → FCFS
Queue 4 (lowest priority):  Student/background     → FCFS
```

Inter-queue scheduling is typically **fixed priority preemptive**: Queue 0 always runs before Queue 1, which always runs before Queue 2, etc. A process in Queue 1 is preempted immediately if a process arrives in Queue 0. This means Queue 4 only gets CPU when all higher queues are empty.

**Q22. How does multilevel queue scheduling assign processes to queues, and what are the problems with fixed assignment?**
A: Assignment is typically based on process type at creation time — the OS categorizes the process and places it in the corresponding queue. Common classification criteria:
- Process origin: kernel/system vs. user-space.
- Interactive vs. batch: foreground processes (with a controlling terminal) vs. background processes.
- Priority: real-time vs. time-sharing vs. background.
- User identity: privileged users vs. standard users.

**Problems with fixed assignment:**
- **Starvation** — low-priority queues may never run if higher queues are always busy. A batch job that arrives when interactive load is high may wait indefinitely.
- **Misclassification** — a process's behavior can change over its lifetime. A program that starts as a CPU-intensive batch job may become interactive after its initialization phase. Fixed assignment locks it into the wrong queue permanently.
- **Inflexibility** — it's a policy decision baked into the scheduler: if the classification criteria are wrong for a workload, there's no corrective mechanism.

These problems motivate the extension to multilevel feedback queues.

**Q23. What is multilevel feedback queue (MLFQ) scheduling, and how does it solve fixed-assignment problems?**
A: Multilevel feedback queue (MLFQ) scheduling is the most general and widely-used CPU scheduling algorithm. Like multilevel queues, it has multiple queues with different priorities and scheduling algorithms. Unlike multilevel queues, **processes can move between queues** based on their observed behavior. The scheduler adapts dynamically:

- A process that uses its entire quantum without blocking is moved **down** to a lower-priority queue (it is behaving like a CPU-intensive batch job).
- A process that frequently blocks before its quantum expires is moved **up** to a higher-priority queue (it is behaving like an interactive I/O-bound job).
- Aging moves long-waiting processes **up** to prevent starvation.

```
Queue 0: quantum=8ms  (highest priority, Round Robin)
Queue 1: quantum=16ms (Round Robin)
Queue 2: FCFS         (lowest priority)

New process → enters Queue 0
If it uses full 8ms quantum without blocking → moves to Queue 1
If it uses full 16ms quantum → moves to Queue 2
If it blocks for I/O before quantum expires → stays in (or moves up to) Queue 0
```

**Q24. What are the five parameters that define an MLFQ configuration?**
A: MLFQ is not a single algorithm but a framework parameterized by:
1. **Number of queues** — more queues = finer-grained classification but more overhead.
2. **Scheduling algorithm within each queue** — typically RR for high-priority queues (low latency), FCFS for the lowest queue (high throughput for long jobs).
3. **Quantum size per queue** — increases as priority decreases: short quantum for interactive queues, longer for batch queues. This gives interactive processes quick turns and amortizes context-switch overhead for long batch jobs.
4. **Promotion criteria** — when and how a process moves up (aging threshold, I/O behavior score, explicit system call).
5. **Demotion criteria** — when and how a process moves down (used its full quantum N times consecutively; exceeded a CPU time budget in a window).

These parameters must be tuned for the target workload. The Linux Completely Fair Scheduler (CFS) is a modern evolution of these ideas, replacing discrete queues with a red-black tree ordered by "virtual runtime" — a continuous approximation of the same feedback principle.

**Q25. How does MLFQ handle a process that intentionally exploits the scheduler by yielding just before its quantum expires?**
A: This is a known attack on naive MLFQ implementations. A process that does just enough work then voluntarily yields (via a system call or by reading a tiny amount from a file) appears to be I/O-bound and is promoted to or stays in a high-priority queue — even though it's actually CPU-intensive. The process effectively games the scheduler to get more CPU time than its fair share.

Solutions:
- **Accounting over intervals, not per-burst** — instead of resetting a process's CPU usage counter each time it blocks, accumulate total CPU time used in the current queue across multiple bursts. When the accumulated time exceeds the quantum, demote — regardless of whether each individual burst was short.
- **Lottery scheduling** — randomize CPU allocation proportional to tickets; gaming is statistically unprofitable.
- **Stride scheduling** — a deterministic, game-resistant proportional share algorithm.
- **Linux CFS** — tracks "virtual runtime" (actual CPU time weighted by priority). A process cannot improve its vruntime by yielding; the scheduler picks the process with the lowest vruntime regardless.

## Section 7: Comparison and Selection

**Q26. How do you compare the five algorithms on the standard metrics?**
A:

| Algorithm        | Preemptive? | Waiting Time     | Response Time    | Throughput       | Starvation risk | Best for                          |
|---               |---          |---               |---               |---               |---              |---                                |
| FCFS             | No          | High (convoy)    | High             | Low-Medium       | No              | Simple batch; uniform job lengths |
| SJF              | No          | Optimal (theory) | Medium           | High             | Yes (long jobs) | Batch; known/predictable bursts   |
| SRTF             | Yes         | Optimal (theory) | Good             | High             | Yes (long jobs) | Theory; rarely used directly      |
| Round Robin      | Yes         | Medium           | Best             | Medium           | No              | Time-sharing; interactive systems |
| Priority         | Both        | Varies           | Good (high-pri)  | High (high-pri)  | Yes (low-pri)   | Real-time; differentiated service |
| Multilevel Queue | Yes         | Low-Medium       | Good             | Good             | Yes (low queues)| Mixed workloads; OS schedulers    |
| MLFQ             | Yes         | Low              | Best-Good        | Good-High        | Low (with aging)| General purpose; most modern OSes |

**Q27. How do you choose a scheduling algorithm for a given system type?**
A: Match the algorithm to the system's primary objective:

- **Batch system** (maximize throughput, minimize turnaround, no user interaction) → SJF or FCFS. SJF minimizes average waiting time for known workloads; FCFS is simpler when job lengths are similar.
- **Interactive / time-sharing system** (minimize response time, fairness) → Round Robin. Quantum tuned so most interactive requests complete in one slice; all processes make progress.
- **Real-time system** (meet deadlines, deterministic behavior) → Priority scheduling with priority inheritance. Hard real-time systems use `SCHED_FIFO` or `SCHED_RR` at the OS level with careful priority assignment. Rate Monotonic Scheduling (RMS) and Earliest Deadline First (EDF) are the theoretical foundations.
- **Mixed workload** (interactive + batch + system tasks) → Multilevel feedback queue. This is why MLFQ is the default in general-purpose OSes: it handles all workload types by adapting to observed behavior.
- **Fairness-critical** (guaranteed proportional CPU shares across users or containers) → Lottery scheduling or stride scheduling for proportional-share guarantees; Linux CFS for weighted fair queuing.

## Section 8: Scenario / System Design Style Questions

**Q28. "Walk through the scheduling of this process set under Round Robin with quantum=4, showing the Gantt chart and computing average waiting time."**
A:
```
Process  Arrival  Burst
P1         0        7
P2         2        4
P3         4        1
P4         5        4
Quantum = 4

Trace the ready queue at each decision point:

t=0:  P1 arrives → queue: [P1]
      P1 starts, runs 0→4 (uses full quantum)
t=4:  P1 used full quantum → preempt; P2 arrived at t=2, P3 at t=4 → queue: [P2, P3, P1]
      P2 starts, runs 4→8 (uses full quantum, burst=4 → done)
t=8:  P2 done; P4 arrived at t=5 → queue: [P3, P1, P4]
      P3 starts, runs 8→9 (burst=1 → done)
t=9:  P3 done → queue: [P1, P4]
      P1 starts, runs 9→13 (remaining=3, finishes in 3ms < quantum)
t=12: P1 done → queue: [P4]

Wait — P1 has 7-4=3 remaining after first quantum.
Corrected: P1 runs 9→12 (3ms remaining, burst=7, used 4 already)

t=12: P1 done → queue: [P4]
      P4 starts, runs 12→16 (burst=4 → done)

Gantt chart:
| P1  | P2  |P3| P1 | P4  |
0     4     8  9   12    16

Completion: P1=12, P2=8, P3=9, P4=16
Turnaround: P1=12-0=12, P2=8-2=6, P3=9-4=5, P4=16-5=11
Waiting:    P1=12-7=5, P2=6-4=2, P3=5-1=4, P4=11-4=7
Average waiting: (5+2+4+7)/4 = 4.5ms
```

**Q29. "A web server handles both API requests (short, latency-sensitive) and report generation jobs (long, background). What scheduling strategy do you apply, and why?"**
A: This is a classic mixed-workload problem — exactly what MLFQ was designed for. The design:

- **Two queues minimum**: a high-priority queue for API requests (interactive, latency-sensitive) and a low-priority queue for report generation (batch, throughput-sensitive).
- **High-priority queue**: Round Robin with a small quantum (1–10ms). API requests typically complete in microseconds to milliseconds; a small quantum ensures they get CPU immediately and complete in one or two slices.
- **Low-priority queue**: FCFS or Round Robin with a large quantum (100ms+). Report jobs are long-running; frequent preemption adds context-switch overhead without improving their completion time.
- **Inter-queue policy**: strict priority — the report queue only runs when the API queue is empty. This guarantees API latency is bounded regardless of report load.
- **Starvation prevention**: age report jobs if they've waited more than N seconds; temporarily promote them to the high-priority queue for one quantum so they make progress during idle API periods.

At the application level (separate from OS scheduling): use a process/thread pool per workload type, containerize with separate CPU quotas (Linux cgroups), or use a message queue to decouple report generation onto dedicated worker machines entirely — removing the competition for CPU at the OS level.

**Q30. "What is the completely fair scheduler (CFS) in Linux, and how does it relate to the classical algorithms?"**
A: CFS is the default Linux CPU scheduler (since kernel 2.6.23). It implements a weighted fair-queuing discipline using a **red-black tree** ordered by "virtual runtime" (`vruntime`) — the amount of CPU time a process has received, normalized by its weight (priority/niceness):

```
vruntime += actual_runtime × (NICE_0_WEIGHT / process_weight)
```

A lower-nice (higher-priority) process has a lower weight divisor, so its vruntime grows more slowly — it appears to have received less CPU time than it actually has. The scheduler always picks the process with the lowest vruntime (leftmost node in the red-black tree).

Relationship to classical algorithms:
- **Not RR**: there is no fixed quantum. A process runs for a "targeted latency" divided by the number of runnable processes — so as load increases, each process gets a shorter turn.
- **Not Priority (directly)**: priority is expressed as differential vruntime growth rates, not as queue ordering.
- **MLFQ inspiration**: CFS uses scheduling classes (`SCHED_FIFO`, `SCHED_RR`, `SCHED_NORMAL`, `SCHED_BATCH`, `SCHED_IDLE`) that are strict-priority ordered — real-time classes always preempt normal-class processes. Within each class, CFS or RR applies. This is a multilevel queue at the class level with CFS within the normal class.
- **No starvation**: because vruntime only ever increases, a process that hasn't run recently has a very low vruntime and will be scheduled next. Starvation is impossible by construction.

## Quick Reference — Algorithm Summary

```
FCFS — First-Come, First-Served
  Type:        Non-preemptive
  Queue:       FIFO
  Strength:    Simple, no starvation
  Weakness:    Convoy effect, poor response time for short jobs
  Metric won:  Nothing; worst average waiting time for mixed workloads

SJF — Shortest Job First
  Type:        Non-preemptive (SRTF = preemptive variant)
  Queue:       Priority by burst length
  Strength:    Optimal average waiting time (non-preemptive)
  Weakness:    Requires burst prediction; starves long jobs
  Metric won:  Minimum average waiting time

Round Robin
  Type:        Preemptive
  Queue:       Circular FIFO with quantum
  Strength:    Fair, best response time, no starvation
  Weakness:    High turnaround vs. SJF; quantum tuning critical
  Metric won:  Response time; fairness

Priority Scheduling
  Type:        Preemptive or non-preemptive
  Queue:       Priority queue (by assigned priority)
  Strength:    Flexible; models real-world importance
  Weakness:    Starvation; priority inversion
  Metric won:  Throughput for high-priority processes

Multilevel Queue
  Type:        Preemptive (inter-queue fixed priority)
  Queue:       Multiple queues, fixed process assignment
  Strength:    Different policies per process class
  Weakness:    Fixed assignment; starvation for low queues
  Metric won:  Mixed workload handling

MLFQ — Multilevel Feedback Queue
  Type:        Preemptive
  Queue:       Multiple queues, dynamic process movement
  Strength:    Adapts to behavior; balances all metrics
  Weakness:    Complex to configure; gameable without accounting
  Metric won:  General-purpose best; used in most real OSes
```

## Key Formulas

```
Turnaround time  = Completion time − Arrival time
Waiting time     = Turnaround time − Burst time
Response time    = First CPU assignment time − Arrival time

SJF burst prediction (exponential average):
  τ(n+1) = α × t(n) + (1 − α) × τ(n)    [α typically 0.5]

CPU utilization  = (Total time − Idle time) / Total time × 100%
Throughput       = Number of processes completed / Total time

Round Robin context switch overhead ≈ context_switch_cost / quantum
(keep quantum >> context_switch_cost; rule of thumb: quantum > 80th percentile of bursts)
```
