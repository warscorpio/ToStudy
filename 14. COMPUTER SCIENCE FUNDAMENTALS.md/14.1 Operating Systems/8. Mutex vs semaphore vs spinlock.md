# Operating Systems: Mutex vs Semaphore vs Spinlock — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a critical section, and why do concurrent programs need synchronisation primitives to protect it?**
A: A critical section is a region of code that accesses a shared resource — a variable, data structure, file, hardware register, or network connection — in a way that produces incorrect results if two or more threads execute it simultaneously. The need for synchronisation arises from three sources:

**Race condition:** Two threads read-modify-write a shared counter. Thread A reads `counter = 5`, Thread B reads `counter = 5`, Thread A writes `counter = 6`, Thread B writes `counter = 6`. The correct result after two increments is 7; both threads' writes clobber each other and the result is 6. The error is non-deterministic — it depends on the exact interleaving of the two threads' execution, which changes with CPU load, scheduler decisions, and clock speed.

**Visibility:** On modern CPUs with write buffers and per-core caches, a write to a variable by Thread A on core 0 may not be immediately visible to Thread B on core 1. Without a memory barrier (which synchronisation primitives provide), Thread B may read a stale cached value even after Thread A has "written" it.

**Atomicity:** Some operations that appear atomic in source code are not atomic in machine code. `counter++` compiles to load-add-store — three separate instructions. Another thread can interrupt between any two of them. A synchronisation primitive that guarantees mutual exclusion ensures the entire load-add-store sequence completes without interruption.

Synchronisation primitives — mutexes, semaphores, spinlocks — provide these three guarantees: mutual exclusion (at most one thread in the critical section at a time), visibility (memory barriers ensure writes are seen by other cores), and atomicity (the lock/unlock operations themselves are implemented with atomic CPU instructions).

**Q2. What is a mutex, and what are its defining properties?**
A: A mutex (mutual exclusion lock) is a synchronisation primitive with exactly two states — locked and unlocked — and a strict ownership model: the thread that acquires (locks) the mutex is the only thread that may release (unlock) it. Its defining properties:

**Ownership:** The mutex belongs to exactly one thread at a time — the owner. Only the owner can unlock it. Attempting to unlock a mutex from a non-owner thread is an error (undefined behaviour in POSIX pthreads; a panic or error code in higher-level languages). This ownership model is what distinguishes a mutex from a binary semaphore.

**Blocking on contention:** When Thread B tries to lock a mutex already held by Thread A, Thread B blocks — it is descheduled by the OS and placed in a wait queue. Thread B consumes no CPU while waiting. When Thread A unlocks the mutex, the OS wakes one waiting thread (Thread B), which is rescheduled and acquires the lock.

**Non-recursive by default:** Most mutex implementations are non-recursive — a thread that tries to lock a mutex it already holds will deadlock. Recursive mutexes (reentrant mutexes) exist (`PTHREAD_MUTEX_RECURSIVE` in pthreads, `std::recursive_mutex` in C++) but are considered a design smell — they often mask design flaws where the lock granularity is wrong.

**Memory ordering guarantees:** Lock acquisition is a load-acquire operation; unlock is a store-release. This means all memory writes before the unlock are visible to the next thread that acquires the lock. This is the mechanism that makes the mutex safe for sharing data across cores.

**Q3. What is a semaphore, and how does it differ from a mutex?**
A: A semaphore is a synchronisation primitive that maintains an integer counter and supports two atomic operations: **wait** (P / down / acquire — decrements the counter; blocks if the result would be negative) and **signal** (V / up / release — increments the counter; wakes a waiting thread if any). The key differences from a mutex:

**No ownership:** Any thread can signal a semaphore, regardless of which thread called wait. There is no concept of "the thread that owns this semaphore." This makes semaphores suitable for producer-consumer signalling — the producer signals, the consumer waits — where no single thread owns the synchronisation state.

**Integer counter (counting semaphore):** The counter can be initialised to any non-negative integer, not just 0 or 1. A semaphore initialised to N allows up to N threads to pass the wait simultaneously — modelling N available units of a resource (N database connections, N buffer slots). A binary semaphore (counter initialised to 1) provides mutual exclusion, but without ownership.

**Signalling vs mutual exclusion:** The mutex's primary purpose is to protect a critical section (mutual exclusion). The semaphore's primary purpose is to signal between threads — to coordinate ordering and resource availability. Using a semaphore as a mutex is possible but problematic because the lack of ownership enforcement means any thread can "release" the lock, which is a programming error that the primitive will not catch.

The precise practical distinction at 5 YOE: if you need "only one thread in this section at a time, and the same thread that entered must exit," use a mutex. If you need "thread A signals thread B that an event has occurred" or "at most N threads may access this pool simultaneously," use a semaphore.

**Q4. What is a spinlock, and when does spinning beat blocking?**
A: A spinlock is a lock that, when unavailable, causes the waiting thread to loop continuously — spinning — checking the lock state in a tight loop rather than blocking and being descheduled. Implemented with a single atomic compare-and-swap (CAS) or test-and-set instruction:

```c
// Conceptual spinlock
void spin_lock(atomic_int *lock) {
    while (atomic_exchange(lock, 1) == 1) {
        // spin — lock was already held, keep trying
        cpu_relax(); // PAUSE instruction on x86 — reduces power, avoids memory order violations
    }
    // lock acquired — atomic_exchange returned 0 (was unlocked)
}

void spin_unlock(atomic_int *lock) {
    atomic_store(lock, 0); // release
}
```

**Spinning beats blocking when:**
- The expected wait time is shorter than the cost of a context switch (typically 1–10 µs on modern Linux). If Thread A holds a spinlock for 500 ns, Thread B spinning for 500 ns is faster than paying the descheduling overhead.
- The lock is held only during a very short, bounded critical section — updating a single field, incrementing a counter, appending to a small list.
- The system is not oversubscribed — there are at least as many CPU cores as threads. A spinning thread on a single-core system holds the CPU, preventing the lock holder from running, causing a livelock.

**Blocking beats spinning when:**
- The lock is held for an unpredictable or long duration. A spinning thread consumes 100% of one CPU core for the entire wait — wasted power, wasted cycles that could run other work.
- The system is oversubscribed (more threads than cores). Spinning starves the lock holder of CPU time, making the situation worse.
- Battery life or power consumption matters (embedded, mobile).

## Section 2: Mutex in Depth

**Q5. How is a mutex implemented at the hardware level?**
A: A mutex implementation requires an atomic read-modify-write operation that no other core can interrupt. Modern CPUs provide several:

**Compare-and-Swap (CAS / CMPXCHG on x86):**
```c
// Pseudocode for CAS
bool cas(int *addr, int expected, int desired) {
    // Atomic: if *addr == expected, set *addr = desired and return true
    //         else return false (and leave *addr unchanged)
}

void mutex_lock(Mutex *m) {
    int expected = 0; // 0 = unlocked
    while (!cas(&m->state, 0, 1)) { // try to set to 1 (locked)
        // contention — block (futex_wait) rather than spin
        futex_wait(&m->state, 1); // sleep until state != 1
    }
}

void mutex_unlock(Mutex *m) {
    atomic_store(&m->state, 0); // release
    futex_wake(&m->state, 1);   // wake one waiting thread
}
```

**The futex (fast userspace mutex) on Linux:** A futex is the mechanism that makes mutex blocking efficient. The lock state is a single integer in userspace — the CAS operates entirely in userspace with no system call on the fast (uncontended) path. Only when the lock is contended does the thread make a `futex_wait()` system call to block. The `futex_wake()` system call on unlock wakes exactly one waiter. The common case (uncontended lock) has zero system call overhead — just an atomic CAS. This is why `pthread_mutex_lock` on Linux is extremely fast for uncontended locks (~20 ns) vs the naive implementation (a system call on every acquire/release).

**Load-linked / store-conditional (LL/SC on ARM, RISC-V):**
An alternative to CAS used on RISC architectures. `ldrex` (load exclusive) marks a memory location; `strex` (store exclusive) succeeds only if no other core has written to the location since the `ldrex`. Used in ARM's mutex implementation — conceptually equivalent to CAS but avoids the ABA problem.

**Q6. What is priority inversion, and how do mutexes address it?**
A: Priority inversion is a scheduling anomaly where a high-priority thread is blocked waiting for a resource held by a low-priority thread, while a medium-priority thread preempts the low-priority thread — effectively inverting the priority ordering. The high-priority thread is blocked not by the low-priority thread directly, but by the medium-priority thread that displaced it:

```
Thread H (high priority)  → blocked waiting for mutex held by L
Thread M (medium priority)→ running, preempted L
Thread L (low priority)   → cannot run (preempted by M), cannot release mutex
Thread H                  → waits indefinitely — bounded only by M's completion
```

This caused the famous Mars Pathfinder spacecraft resets in 1997 — a high-priority communications task was starved because a low-priority meteorological task held a shared bus mutex and was preempted by a medium-priority task.

**Priority inheritance:** A mutex protocol where the OS temporarily boosts the priority of the mutex owner to match the highest-priority thread waiting for that mutex. Thread L is elevated to H's priority, preempts M, completes its critical section, releases the mutex, returns to its original priority, and Thread H acquires the mutex. Available in POSIX via `pthread_mutexattr_setprotocol(attr, PTHREAD_PRIO_INHERIT)`. Used in real-time OS kernels and safety-critical systems.

**Priority ceiling:** A simpler protocol where each mutex is assigned a static ceiling priority — the maximum priority of any thread that will ever acquire it. A thread acquires the mutex only if its priority is higher than the ceilings of all currently held mutexes. Prevents inversion but requires knowing all potential users at design time.

**Q7. What is a deadlock, what conditions produce it, and how does mutex usage create it?**
A: A deadlock is a state where two or more threads are each waiting for a resource held by another, with no thread able to proceed. The four necessary conditions (Coffman conditions) — all must hold simultaneously for deadlock to occur:

- **Mutual exclusion:** Resources cannot be shared — only one thread holds the mutex at a time.
- **Hold and wait:** A thread holds at least one resource while waiting for additional resources.
- **No preemption:** Resources cannot be forcibly taken — a mutex must be released voluntarily by its owner.
- **Circular wait:** A cycle exists in the resource-wait graph (A waits for B's lock, B waits for A's lock).

Classic mutex deadlock:
```
Thread A: lock(mutex_1) → lock(mutex_2)
Thread B: lock(mutex_2) → lock(mutex_1)

Timeline:
A locks mutex_1 ✓
B locks mutex_2 ✓
A tries to lock mutex_2 → blocks (B holds it)
B tries to lock mutex_1 → blocks (A holds it)
→ Deadlock
```

Prevention strategies: **lock ordering** (always acquire mutex_1 before mutex_2 globally — eliminates circular wait), **try-lock with timeout** (`pthread_mutex_timedlock` — if the lock isn't acquired within the deadline, back off and retry), **lock hierarchy** (assign numeric levels to mutexes; threads may only lock mutexes at higher levels than any they currently hold), **deadlock detection** (runtime tools: Valgrind's Helgrind, ThreadSanitizer).

## Section 3: Semaphore in Depth

**Q8. What are the two canonical use cases for semaphores, and how does the implementation differ between them?**
A: Semaphores have two primary use cases that map to different initialisation values and semantics:

**Use case 1 — Resource counting (counting semaphore):**
A database connection pool has N=10 connections. A semaphore initialised to 10 gates access: each thread that acquires a connection calls `wait()` (decrement); each thread that releases a connection calls `signal()` (increment). When all 10 connections are in use, the semaphore's counter is 0 and further `wait()` calls block until a connection is returned. The semaphore ensures at most 10 concurrent users of the pool without a mutex protecting the entire pool.

```typescript
// Node.js connection pool with semaphore semantics
class ConnectionPool {
  private available: number;
  private waitQueue: Array<() => void> = [];

  constructor(private readonly size: number) {
    this.available = size;
  }

  async acquire(): Promise<Connection> {
    if (this.available > 0) {
      this.available--;
      return this.createConnection();
    }
    // Block (async-style) until a connection is released
    await new Promise<void>(resolve => this.waitQueue.push(resolve));
    return this.createConnection();
  }

  release(): void {
    if (this.waitQueue.length > 0) {
      const next = this.waitQueue.shift()!;
      next(); // wake one waiter — don't increment available
    } else {
      this.available++;
    }
  }
}
```

**Use case 2 — Thread signalling / event notification (binary semaphore at 0):**
Thread B must not proceed until Thread A completes a task. Initialise the semaphore to 0. Thread B calls `wait()` immediately and blocks (counter is 0, would go negative). Thread A completes its task and calls `signal()` (counter goes to 1). Thread B is woken and proceeds.

```
Semaphore sem = new Semaphore(0); // initialised to 0

Thread A:                     Thread B:
  doWork();                     sem.wait();  ← blocks here
  sem.signal(); ←──wakes B──→  processResult();
```

This pattern cannot be safely implemented with a mutex — a mutex locked by Thread A cannot be unlocked by Thread A to unblock Thread B if the unlock must come from A and the wait must be in B. The semaphore's lack of ownership is precisely what makes this pattern work.

**Q9. What is the producer-consumer problem, and how does a semaphore solve it?**
A: The producer-consumer problem (bounded buffer problem) involves two thread roles: producers that generate items and add them to a fixed-size buffer, and consumers that remove and process items. The constraints: producers must not add to a full buffer (wait until space is available); consumers must not remove from an empty buffer (wait until an item is available). A pair of semaphores and one mutex solve it cleanly:

```c
// Bounded buffer with capacity N
Semaphore empty = N;   // counts empty slots — producers wait on this
Semaphore full  = 0;   // counts full slots — consumers wait on this
Mutex    mutex;        // protects buffer access

// Producer
void produce(Item item) {
    empty.wait();       // wait for an empty slot (blocks if buffer full)
    mutex.lock();
    buffer.enqueue(item);
    mutex.unlock();
    full.signal();      // signal that a new item is available
}

// Consumer
Item consume() {
    full.wait();        // wait for a full slot (blocks if buffer empty)
    mutex.lock();
    Item item = buffer.dequeue();
    mutex.unlock();
    empty.signal();     // signal that a slot is now empty
    return item;
}
```

The two semaphores (`empty` and `full`) handle the blocking and waking without polling. The mutex protects the buffer data structure from concurrent modification. Note the order: semaphore wait before mutex lock (if reversed — mutex lock before semaphore wait — a producer holding the mutex while waiting on `empty` would deadlock a consumer that needs the mutex to signal `empty`).

**Q10. What is the ABA problem, and how does it affect lock-free programming with CAS?**
A: The ABA problem is a subtle correctness bug in lock-free (CAS-based) algorithms. A CAS checks that a value is still A before setting it to B — but a value that is currently A may have been changed to X and back to A by another thread in the interim. The CAS succeeds (A == A) even though the state has changed in a meaningful way:

```
Thread 1 reads stack top = A (pointer to node A)
Thread 2 pops A, pops B, pushes A back → stack top = A
Thread 1's CAS: "if top == A, set top = next(A)" → succeeds
But next(A) now points to a freed node — use-after-free
```

Solutions: **tagged pointers** (store a version counter in the upper bits of the pointer — CAS checks both the pointer and the counter; a cycle from A to X to A increments the counter, so A-v1 ≠ A-v2), **hazard pointers** (mark pointers as "in use" before dereferencing; garbage collect only when no hazard pointers reference a node), **RCU (Read-Copy-Update)** in the Linux kernel. The ABA problem is irrelevant for mutex-based code — the mutex prevents the intermediate A→X→A transition from happening concurrently — but surfaces whenever you use lock-free CAS-based data structures (queues, stacks, hash maps).

## Section 4: Spinlock in Depth

**Q11. How does a spinlock interact with the CPU's memory model, and what is the `PAUSE` instruction for?**
A: On x86, a spinlock is implemented with `LOCK CMPXCHG` (atomic compare-and-swap) or `LOCK XCHG` (atomic exchange). The `LOCK` prefix issues a full memory barrier — it ensures all prior writes are globally visible before the lock is acquired, and all subsequent reads see the latest values. This is required for correctness: without the barrier, the CPU could reorder the lock acquisition relative to the operations inside the critical section.

The `PAUSE` instruction (`rep nop` on older CPUs) is inserted in the spin loop:
```c
while (atomic_exchange(&lock, 1) == 1) {
    _mm_pause(); // PAUSE instruction
}
```

`PAUSE` does three things: (1) introduces a small delay (~40 cycles on modern Intel), reducing contention on the memory bus by slowing the rate of CAS attempts; (2) signals to the CPU's memory order buffer that this is a spin loop, allowing it to avoid a "memory order machine clear" — a pipeline flush that would occur if the CPU speculatively executed past the loop assuming the CAS would succeed; (3) reduces power consumption in the spin loop. Without `PAUSE`, a tight CAS loop saturates the memory bus, slows the lock holder (which is also making memory accesses), and can cause a 2–3× slowdown due to cache coherency traffic — a phenomenon called "lock convoy" or "bus thrashing."

**Q12. What is a "spinlock + sleep" hybrid (adaptive mutex), and why is it used in production systems?**
A: An adaptive mutex (used in glibc's `pthread_mutex_t` when the lock holder is running, and in Linux's kernel spinlocks with preemption) starts by spinning for a short bounded period, then transitions to blocking (sleeping) if the lock is not acquired within that window:

```
Attempt 1: CAS → lock acquired (fast path, no spin)
Attempt 2–N: Spin for K iterations → if lock acquired, done
After K spins: call futex_wait() → block (sleep)
On unlock: futex_wake() → one waiter woken
```

The spin phase exploits the observation that if the lock holder is currently executing on another core, the lock will likely be released very soon — spinning for a few hundred nanoseconds avoids the 1–10 µs overhead of descheduling. The sleep phase handles the case where the lock holder is not currently running (preempted, blocked on I/O) — spinning forever would waste CPU. The threshold K is typically set to the cost of a context switch in cycles — spin longer than a context switch would take, and you've wasted more CPU than the sleep would have cost.

In `glibc`, the adaptive mutex checks whether the lock-holding thread is currently running on any CPU core (via kernel assistance or a thread state flag). If it is running, spin; if it is not, sleep immediately. This adapts to the actual system load rather than using a fixed spin count.

**Q13. Why can't spinlocks be used safely in single-core systems or with preemptible kernels without additional precautions?**
A: On a single-core system with a preemptible scheduler, a spinlock causes livelock: Thread A holds the lock, Thread B is scheduled and starts spinning. Since there is only one core, Thread A cannot run while Thread B spins — Thread A can never release the lock, Thread B spins forever. Solution for single-core: disable preemption while holding a spinlock (the lock holder cannot be preempted, so it completes quickly and releases). This is exactly what Linux kernel spinlocks do — `spin_lock()` calls `preempt_disable()` on UP (uniprocessor) builds and on preemptible kernels.

In the Linux kernel:
- `spin_lock()` — disables preemption on the local CPU (prevents the kernel scheduler from preempting the current task while the spinlock is held).
- `spin_lock_irqsave()` — disables preemption AND disables interrupts on the local CPU (prevents an interrupt handler from trying to acquire the same spinlock, which would deadlock since the handler would spin forever on the same core that holds the lock).
- `spin_lock_bh()` — disables preemption and softirqs (bottom halves) — used when the spinlock is shared between process context and softirq handlers.

In user space, spinlocks are not typically used because the OS scheduler can preempt a spinlock holder at any time, causing all waiters to spin for the duration of the scheduling quantum — up to 10 ms on a default Linux system. This is why user-space synchronisation almost always uses mutexes (which integrate with the scheduler) rather than raw spinlocks.

## Section 5: Comparison and Selection

**Q14. How do mutex, semaphore, and spinlock compare across the key dimensions that matter for selecting one?**
A:

| Dimension                  | Mutex                                       | Semaphore                                      | Spinlock                                        |
|----------------------------|---------------------------------------------|------------------------------------------------|-------------------------------------------------|
| Ownership                  | Yes — only owner can unlock                 | No — any thread can signal                     | No — any thread can release (conceptually)      |
| Counter                    | Binary (locked/unlocked)                    | Integer ≥ 0 (counting or binary)               | Binary (locked/unlocked)                        |
| Wait behaviour             | Block (descheduled, zero CPU while waiting) | Block (descheduled, zero CPU while waiting)    | Spin (busy-wait, 100% CPU while waiting)        |
| System call on contention  | Yes — futex_wait()                          | Yes — futex_wait() or semaphore syscall        | No — pure userspace (user spinlocks)            |
| Best for                   | Protecting critical sections                | Counting resources, signalling between threads | Short critical sections on multicore, kernel    |
| Priority inversion risk    | Yes (mitigated by priority inheritance)     | Yes                                            | Yes                                             |
| Recursive locking          | Deadlocks (non-recursive) or allowed        | N/A                                            | Deadlocks                                       |
| Overhead (uncontended)     | ~20 ns (futex fast path)                    | ~20–100 ns                                     | ~5–10 ns (atomic CAS only)                      |
| Overhead (contended)       | ~1–10 µs (context switch)                   | ~1–10 µs (context switch)                      | Proportional to wait time × CPU cost            |
| Safe on single-core?       | Yes                                         | Yes                                            | Only with preemption disabled                   |
| Suitable for user-space?   | Yes — primary choice                        | Yes — for counting/signalling                  | Rarely — adaptive mutex preferred               |
| Suitable for kernel?       | Yes (kernel mutex)                          | Yes                                            | Yes — primary kernel synchronisation primitive  |

**Q15. When should you choose each primitive in a backend service context?**
A: The selection criteria for a Node.js/NestJS backend engineer (where true OS-level locking is rarely written directly, but the concepts appear in library design, database internals, and interview questions):

**Choose mutex when:**
- Protecting a shared data structure (a cache, a connection pool, an in-memory ledger) from concurrent modification.
- The critical section duration is unpredictable or potentially long (includes I/O).
- Correctness requires that the same caller that acquired the lock releases it.
- In language terms: JavaScript/Node.js is single-threaded with an event loop — you don't need mutexes between requests. But in a Go service, a `sync.Mutex` protects shared maps accessed by concurrent goroutines. In Java, `synchronized` blocks or `ReentrantLock`. In Rust, `Mutex<T>` from `std::sync`.

**Choose semaphore when:**
- Limiting concurrent access to a finite pool — database connections (`pg-pool`'s `max` parameter is a semaphore), HTTP connections, file handles, API rate limit slots.
- Coordinating ordering between threads — Thread B must wait for Thread A's result before proceeding (binary semaphore at 0).
- Implementing producer-consumer queues — bounded buffers where producers wait when full and consumers wait when empty.
- In Node.js terms: `p-limit` (limit concurrent async operations to N), `bottleneck` (rate limiting), and connection pool implementations are all semaphore patterns in async form.

**Choose spinlock when:**
- Writing kernel code or very low-level library code where the lock is held for nanoseconds and the overhead of a system call dwarfs the lock hold time.
- Implementing a lock-free data structure's internal synchronisation.
- You are certain the system is not oversubscribed and the lock holder is always running on another core.
- In practice for application engineers: you almost never write spinlocks directly — you choose an adaptive mutex or a lock-free data structure from a library instead.

## Section 6: Concurrency in Node.js and Backend Context

**Q16. Node.js is single-threaded. Does that mean you never need synchronisation primitives?**
A: Partially true, but with important nuances. Node.js's event loop is single-threaded — two event loop callbacks never run concurrently on the main thread. This means a plain JavaScript object shared between request handlers does not need a mutex — only one handler runs at a time. However, synchronisation problems still appear in three contexts:

**Worker threads (`worker_threads` module):** Node.js worker threads run JavaScript in parallel on separate V8 isolates. Data shared via `SharedArrayBuffer` between workers is subject to race conditions. `Atomics` — Node.js's exposure of hardware atomic operations — provides the equivalent of spinlock primitives:
```typescript
const shared = new SharedArrayBuffer(4);
const arr = new Int32Array(shared);

// Worker A — spinlock acquire
while (Atomics.compareExchange(arr, 0, 0, 1) !== 0) {
  Atomics.wait(arr, 0, 1); // block if value is still 1 (locked)
}
// critical section
Atomics.store(arr, 0, 0);   // release
Atomics.notify(arr, 0, 1);  // wake one waiter
```

**Async race conditions (logical concurrency):** A single Node.js thread can have multiple async operations in flight simultaneously. Two requests both check `if (!cache.has(key))`, both miss, both fetch from the DB, and both write to the cache — a logical race that doesn't need OS-level locking but does need async coordination (a promise-based mutex, a "single-flight" pattern, or an in-progress deduplication map).

**External shared state:** Multiple Node.js processes (cluster mode, multiple pods) share Redis, PostgreSQL, and Kafka. Race conditions between processes require distributed locks (Redis `SET NX EX`, PostgreSQL advisory locks) — these are semaphore and mutex patterns at the distributed system level.

**Q17. What is a "single-flight" pattern, and how does it relate to semaphore semantics in Node.js?**
A: The single-flight pattern (also called request coalescing or promise deduplication) ensures that multiple concurrent callers waiting for the same result all receive the same in-flight promise rather than each triggering a separate fetch. It is a binary semaphore pattern — the "lock" is whether a fetch is already in progress:

```typescript
class SingleFlight {
  private inflight = new Map<string, Promise<any>>();

  async do<T>(key: string, fn: () => Promise<T>): Promise<T> {
    // If a fetch for this key is already in progress, return that promise
    if (this.inflight.has(key)) {
      return this.inflight.get(key) as Promise<T>;
    }

    // First caller — start the fetch, store the promise
    const promise = fn().finally(() => {
      this.inflight.delete(key); // cleanup after completion
    });

    this.inflight.set(key, promise);
    return promise;
  }
}

// Usage — all concurrent callers for the same loanId share one DB fetch
const loanFlight = new SingleFlight();

async function getLoan(loanId: string): Promise<Loan> {
  return loanFlight.do(loanId, () => loanRepo.findById(loanId));
}
```

When 100 concurrent requests arrive for `loan-123`, only one DB query fires; 99 requests await the same promise. This is the async equivalent of a mutex protecting a cache-population critical section — the "lock" is the presence of the in-flight promise in the map.

**Q18. What is a distributed lock, and how does it relate to mutex semantics?**
A: A distributed lock is a mutex whose scope extends across multiple processes or machines — it provides mutual exclusion not just between threads in one process, but between independently running services. In a fintech backend (multiple NestJS pods behind a load balancer), a distributed lock prevents two pods from simultaneously processing the same loan application or debiting the same account.

**Redis-based distributed lock (Redlock algorithm, simplified):**
```typescript
async function acquireLock(redis: Redis, key: string, ttlMs: number): Promise<string | null> {
  const token = randomUUID(); // unique ownership token — like the mutex's "owner" field
  const result = await redis.set(
    `lock:${key}`,
    token,
    'PX', ttlMs,   // TTL prevents deadlock if the holder crashes
    'NX'           // only set if not exists — atomic CAS equivalent
  );
  return result === 'OK' ? token : null; // null = lock not acquired
}

async function releaseLock(redis: Redis, key: string, token: string): Promise<void> {
  // Lua script — atomic check-and-delete; only release if we own the lock
  const script = `
    if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('del', KEYS[1])
    else
      return 0
    end
  `;
  await redis.eval(script, 1, `lock:${key}`, token);
}
```

The `token` (UUID) implements ownership — only the holder that set the lock can release it (the Lua script checks the token before deleting). The TTL implements a maximum lock hold time (timeout instead of indefinite deadlock). This maps directly to mutex semantics: `NX` is the atomic acquire, Lua delete is the owned release, TTL is the watchdog timeout.

**PostgreSQL advisory locks** are another distributed mutex: `SELECT pg_try_advisory_lock(12345)` — session-scoped, automatically released on disconnect, no TTL needed (the DB connection is the ownership boundary).

## Section 7: Pitfalls and Anti-patterns

**Q19. What is lock contention, and what are the patterns to reduce it?**
A: Lock contention occurs when multiple threads frequently compete for the same lock, causing threads to block or spin and reducing parallelism. High contention is one of the most common causes of scalability ceilings — adding more threads or CPUs makes performance worse, not better, because the serialisation at the lock dominates. Detection: CPU profiling showing threads blocked on lock acquisition, low CPU utilisation despite high load, latency scaling linearly with concurrency.

Reduction patterns:

**Reduce lock scope:** Hold the lock for the minimum time — do not hold a mutex while doing I/O, network calls, or any blocking operation. Move computation outside the critical section; lock only for the data structure modification.

**Lock striping (sharding):** Instead of one lock protecting the entire data structure, use N locks each protecting 1/N of the structure (keyed by hash). `java.util.concurrent.ConcurrentHashMap` uses 16 lock stripes by default — concurrent writers to different buckets proceed in parallel. Contention falls by 1/N if accesses are uniformly distributed.

**Read-write locks (`RWLock`):** Multiple readers can hold the lock simultaneously; writers get exclusive access. For read-heavy workloads (caches, configuration), this dramatically reduces contention — readers never block each other. `pthread_rwlock_t`, `std::shared_mutex` (C++17), `sync.RWMutex` (Go). Trade-off: writers can starve if readers are continuous; implementations vary in writer vs reader preference.

**Lock-free data structures:** Use atomic operations (CAS) to implement data structures without locks. Contention manifests as CAS retry loops rather than blocking. Suitable for high-contention, short-operation cases (counters, queues, stacks). Standard library implementations: `java.util.concurrent.ConcurrentLinkedQueue`, `std::atomic`, Go channels.

**Optimistic locking:** Read without a lock, check a version counter before committing a write — if the counter changed (another writer modified the data), retry. Used in database transaction isolation (MVCC), Java's `AtomicStampedReference`. No blocking, but retries under high write contention.

**Q20. What is a livelock, and how does it differ from a deadlock?**
A: A deadlock is a state where threads are stuck permanently — each holds a resource and waits for another's resource, with no progress possible and no CPU consumed. A livelock is a state where threads are not stuck — they are actively running and responding to each other — but making no net progress because their responses continuously undo each other's work:

```
Thread A holds lock_1, tries lock_2 → fails → releases lock_1 → retries
Thread B holds lock_2, tries lock_1 → fails → releases lock_2 → retries
Both threads are running, releasing, retrying — forever
```

This can happen with "polite" deadlock-avoidance strategies: when a lock attempt fails, release all held locks and retry from scratch. If both threads do this simultaneously and in lockstep, they perpetually interfere with each other. Solutions: **randomised backoff** (wait a random amount before retrying — breaks lockstep), **priority-based retry** (lower-priority thread always backs off, higher-priority thread proceeds), **Ethernet's CSMA/CD protocol** uses randomised backoff for the same reason.

In distributed systems, livelocks appear in retry storms — multiple services simultaneously retrying failed requests to a downstream service, each retry failing because of the combined load, causing more retries. Circuit breakers and exponential backoff with jitter are the distributed livelock prevention mechanisms.

**Q21. What is the "lock then check" vs "check then lock" bug, and what produces it?**
A: The "check then lock" (check-then-act) bug is a TOCTOU (Time-Of-Check to Time-Of-Use) race condition: a condition is checked outside a lock, the lock is acquired, and the condition is assumed to still hold — but another thread may have changed it in the window between the check and the lock acquisition:

```typescript
// Bug — TOCTOU race
if (!connectionPool.isFull()) {      // check without lock — Thread A sees "not full"
  mutex.lock();                      // Thread B also sees "not full", also acquires lock
  connectionPool.addConnection();    // Both threads add — pool overflows
  mutex.unlock();
}

// Fix — lock then check
mutex.lock();
if (!connectionPool.isFull()) {      // check inside lock — atomic check-and-act
  connectionPool.addConnection();
}
mutex.unlock();
```

The same bug appears in file system operations (`access()` then `open()` — an attacker can replace the file between the two calls), database (check row existence then insert — another transaction inserts first, causing duplicate key error), and distributed lock patterns (check Redis key exists then set — another pod sets it first). The fix is always the same: the check and the act must be atomic — both inside the lock, or expressed as a single atomic operation (`SET NX` in Redis, `INSERT ... ON CONFLICT` in PostgreSQL, CAS in hardware).

## Section 8: Scenario / System Design Style Questions

**Q22. "Your NestJS loan processing service runs as 4 pods. Two pods simultaneously process the same loan application, causing a double disbursement. Walk through the locking strategy to prevent this."**
A: A double disbursement is a classic distributed mutual exclusion problem — the critical section is "check if loan is in APPROVED state, disburse, update state to DISBURSED" and it must execute atomically across all pods.

**Layer 1 — Database-level optimistic locking (preferred first line of defence):**
Use PostgreSQL's `UPDATE ... WHERE status = 'APPROVED' RETURNING *` — the update is atomic; only one pod's update can match the `WHERE` clause:
```sql
UPDATE loan
SET status = 'DISBURSING', updated_at = NOW()
WHERE id = $1 AND status = 'APPROVED'
RETURNING *;
```
If zero rows are returned, another pod already transitioned the status — abort. This is optimistic locking: no explicit lock acquisition, but the atomic `WHERE` clause prevents double execution. The database's row-level locking makes this safe.

**Layer 2 — Pessimistic row lock (`SELECT FOR UPDATE`):**
For multi-step operations that require reading data, computing, then writing, use `SELECT ... FOR UPDATE` inside a transaction — the row is locked for the duration of the transaction:
```sql
BEGIN;
SELECT * FROM loan WHERE id = $1 AND status = 'APPROVED' FOR UPDATE;
-- only one pod reaches here; others block at FOR UPDATE
UPDATE loan SET status = 'DISBURSING' WHERE id = $1;
COMMIT;
```

**Layer 3 — Distributed mutex (Redis) for cross-service coordination:**
When the operation spans services (loan service + payment gateway + Kafka), a Redis distributed lock ensures the entire multi-service flow is serialised per loan:
```typescript
const token = await acquireLock(redis, `disburse:${loanId}`, 30_000); // 30s TTL
if (!token) throw new ConflictException('Disbursement already in progress');
try {
  await disbursementService.execute(loanId);
} finally {
  await releaseLock(redis, `disburse:${loanId}`, token);
}
```

The TTL prevents a deadlock if the pod crashes mid-disbursement. The token prevents another pod from releasing the lock (ownership enforcement). Combined with an idempotency key at the payment gateway, this provides defence-in-depth: the distributed lock prevents concurrent disbursement attempts; the idempotency key at the gateway prevents double-charging even if the lock fails.

**Q23. "A Go microservice processes 10,000 concurrent requests. Each request reads from a shared in-memory cache (`map[string]Loan`). Reads are 99% of traffic; writes (cache invalidation) are 1%. You're seeing lock contention. How do you fix it?"**
A: The current setup likely uses a single `sync.Mutex` protecting the entire map — every read and write serialises through one lock. With 9,900 concurrent readers and a mutex, readers serialise needlessly since concurrent reads are safe.

**Fix 1 — `sync.RWMutex` (immediate, significant improvement):**
```go
var mu sync.RWMutex
var cache = make(map[string]Loan)

// Read path — multiple goroutines read concurrently
func getFromCache(key string) (Loan, bool) {
    mu.RLock()
    defer mu.RUnlock()
    loan, ok := cache[key]
    return loan, ok
}

// Write path — exclusive access
func setInCache(key string, loan Loan) {
    mu.Lock()
    defer mu.Unlock()
    cache[key] = loan
}
```
`RLock()` allows concurrent readers; `Lock()` for writes is exclusive. For a 99%/1% read/write split, contention drops by ~100× — readers no longer block each other.

**Fix 2 — Sharded cache with stripe locking (for extreme read + write throughput):**
```go
const shards = 256
type Shard struct {
    mu    sync.RWMutex
    cache map[string]Loan
}
var shardedCache [shards]Shard

func shard(key string) *Shard {
    h := fnv.New32a()
    h.Write([]byte(key))
    return &shardedCache[h.Sum32()%shards]
}

func getFromCache(key string) (Loan, bool) {
    s := shard(key)
    s.mu.RLock()
    defer s.mu.RUnlock()
    loan, ok := s.cache[key]
    return loan, ok
}
```
Write contention on any single shard is 1/256th of total write traffic. Reads on different shards are fully parallel.

**Fix 3 — `sync.Map` (Go standard library):**
`sync.Map` is optimised for the exact use case: high read, low write, keys once written are rarely deleted. It uses separate lock-free read and locked write paths internally. For a stable loan cache with rare invalidation, `sync.Map` is the simplest high-performance option.

**Q24. "You're reviewing a PR for a payment service. The code acquires a database lock, calls an external payment gateway (HTTP, 2–5 second response time), then releases the lock. What's wrong, and how do you fix it?"**
A: Holding a database lock during an external HTTP call is a severe anti-pattern with multiple failure modes:

**Problem 1 — Lock held for 2–5 seconds:** Every other thread or pod that needs the same data is blocked for up to 5 seconds per request. At moderate traffic (100 RPS), this creates a queue of hundreds of blocked transactions. Database connection pools exhaust quickly — threads waiting for locks hold open connections. The database's `max_connections` is reached, and new requests fail with "too many connections."

**Problem 2 — Lock held if gateway times out or crashes:** If the gateway takes 30 seconds or returns a timeout error, the lock is held for 30 seconds. If the application pod crashes mid-call, the lock may be held until the database session times out (`lock_timeout`, `statement_timeout`). Other transactions wait for the timeout duration.

**Problem 3 — Deadlock risk amplified:** The longer a lock is held, the higher the probability that another transaction acquires a related lock in a conflicting order. A 5-second hold window vs a 5-millisecond hold window is 1000× more likely to be involved in a deadlock cycle.

**Fix — Separate locking from external I/O:**
```typescript
// WRONG — lock held during external call
async function processPayment(paymentId: string): Promise<void> {
  await db.query('BEGIN');
  await db.query('SELECT ... FOR UPDATE WHERE id = $1', [paymentId]); // lock acquired
  await paymentGateway.charge(paymentId); // 2–5 seconds WHILE HOLDING LOCK
  await db.query('UPDATE payments SET status = $1 WHERE id = $2', ['PAID', paymentId]);
  await db.query('COMMIT'); // lock released
}

// CORRECT — state transition locks the row; external call is outside the lock
async function processPayment(paymentId: string): Promise<void> {
  // Step 1: Atomically transition to IN_PROGRESS — short lock, no I/O
  const result = await db.query(
    `UPDATE payments SET status = 'IN_PROGRESS'
     WHERE id = $1 AND status = 'PENDING' RETURNING *`,
    [paymentId]
  );
  if (result.rowCount === 0) return; // already processing — idempotent

  // Step 2: Call gateway OUTSIDE any lock — can take 2–5 seconds freely
  let gatewayResult;
  try {
    gatewayResult = await paymentGateway.charge(paymentId);
  } catch (err) {
    // Step 3a: Transition to FAILED — short lock
    await db.query(
      `UPDATE payments SET status = 'FAILED' WHERE id = $1`,
      [paymentId]
    );
    throw err;
  }

  // Step 3b: Transition to PAID — short lock
  await db.query(
    `UPDATE payments SET status = 'PAID', gateway_ref = $2 WHERE id = $1`,
    [paymentId, gatewayResult.reference]
  );
}
```

The lock duration collapses from 2–5 seconds to a single UPDATE statement (~1–5 ms). The `WHERE status = 'PENDING'` clause is the mutex — only one transaction can transition a given payment from PENDING to IN_PROGRESS. The idempotency key at the gateway prevents double charging if the pod retries after a crash.

## Quick Reference: Mutex vs Semaphore vs Spinlock

| Property                    | Mutex                          | Counting Semaphore              | Binary Semaphore               | Spinlock                        |
|-----------------------------|--------------------------------|---------------------------------|--------------------------------|---------------------------------|
| Ownership                   | Yes                            | No                              | No                             | Conceptually no                 |
| Counter range               | 0 or 1                         | 0 to N                          | 0 or 1                         | 0 or 1                          |
| Wait behaviour              | Block (sleep)                  | Block (sleep)                   | Block (sleep)                  | Busy-wait (spin)                |
| Primary use                 | Mutual exclusion               | Resource counting               | Thread signalling              | Very short kernel critical sections |
| Cross-thread signal         | No (owner must release)        | Yes                             | Yes                            | No                              |
| Priority inheritance        | Supported (PTHREAD_PRIO_INHERIT)| Not standard                   | Not standard                   | Not applicable                  |
| Kernel usage                | Yes (kernel mutex)             | Yes                             | Yes                            | Primary — spinlock              |
| User-space usage            | Primary choice                 | Resource pools, signals         | Producer-consumer              | Rare — adaptive mutex preferred |
| Deadlock if misused         | Yes (double lock, wrong order) | Less common                     | Less common                    | Livelock (single-core)          |
| Language examples           | `sync.Mutex`, `pthread_mutex_t`, `std::mutex`, `ReentrantLock` | `Semaphore` (Java), `asyncio.Semaphore`, `p-limit` | Same | `atomic_flag`, `Atomics.compareExchange` |
