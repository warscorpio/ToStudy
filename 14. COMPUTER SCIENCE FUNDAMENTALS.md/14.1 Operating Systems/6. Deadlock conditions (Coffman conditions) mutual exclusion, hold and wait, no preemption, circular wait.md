# Deadlock: Coffman Conditions, Detection & Prevention — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a deadlock, and how does it differ from a livelock and starvation?**
A: A deadlock is a state in which two or more execution units (threads, processes, transactions) are permanently blocked, each waiting for a resource held by another member of the same group. No member can ever make progress — the system is frozen.

The three related but distinct concepts:

- **Deadlock** — every thread in the cycle is *blocked*. No thread runs. CPU utilisation for those threads is zero. The system is stuck permanently unless an external agent intervenes (kill, timeout, rollback).
- **Livelock** — every thread is *running* but making no progress. Threads continuously react to each other's state changes without ever completing their work. A classic example: two people in a corridor stepping left and right in sync, perpetually blocking each other while both are actively moving. CPU utilisation is high; useful work done is zero. More insidious than deadlock because monitoring tools show active threads.
- **Starvation** — one or more threads never get access to a resource they need, but other threads do make progress. The system is not globally stuck — high-priority threads run and complete work — but low-priority threads are indefinitely postponed. Starvation is a fairness problem, not a safety problem.

The key distinction: deadlock requires a *cycle* of blocked threads; livelock requires a cycle of *running but non-progressing* threads; starvation requires only that some thread is never scheduled or never granted a resource.

**Q2. What are the four Coffman conditions, and why must all four hold simultaneously for a deadlock to occur?**
A: Edward Coffman Jr., Michael Elphick, and Arie Shoshani identified four necessary and sufficient conditions for deadlock in 1971. All four must hold simultaneously — removing any one condition prevents deadlock:

- **Mutual exclusion** — at least one resource is held in a non-shareable mode: only one thread can use it at a time. If all resources were freely shareable, no thread would ever need to wait for another to release one.
- **Hold and wait** — a thread holds at least one resource while waiting to acquire additional resources held by other threads. If threads had to acquire all resources atomically before doing any work, the "holding while waiting" combination could not occur.
- **No preemption** — resources cannot be forcibly taken from a thread; they must be voluntarily released. If the OS could revoke a resource from a thread (preempt it), a deadlock cycle could always be broken.
- **Circular wait** — there exists a set of threads {T1, T2, …, Tn} such that T1 is waiting for a resource held by T2, T2 is waiting for a resource held by T3, …, and Tn is waiting for a resource held by T1. Without a cycle, the wait-for graph has a topological order and every thread can eventually proceed.

The "necessary and sufficient" property is powerful: to *prevent* deadlock, you only need to guarantee that one of the four conditions can never hold. To *detect* an existing deadlock, you verify that all four hold simultaneously. To *recover* from deadlock, you break one condition (usually circular wait, by aborting a thread and releasing its resources).

**Q3. Describe each Coffman condition with a concrete code example.**
A:

**Mutual exclusion:**
```typescript
// A mutex around a shared resource — classic mutual exclusion
const mutex = new Mutex(); // only one thread can hold this at a time

async function writeToFile(data: string): Promise<void> {
  await mutex.acquire();          // thread blocks if another holds the mutex
  try {
    await fs.appendFile('log.txt', data); // exclusive access to file
  } finally {
    mutex.release();
  }
}
```
The file is the mutually exclusive resource. Two threads cannot both write simultaneously — one must wait.

**Hold and wait:**
```typescript
// Thread 1 holds mutex A and waits for mutex B
async function transferFunds(fromId: number, toId: number, amount: number): Promise<void> {
  await mutexA.acquire();          // holds A
  // ... reads fromAccount balance ...
  await mutexB.acquire();          // waits for B while holding A ← hold and wait
  // ... updates both accounts ...
  mutexB.release();
  mutexA.release();
}
```
The thread holds `mutexA` and then attempts to acquire `mutexB`. If another thread simultaneously holds `mutexB` and waits for `mutexA`, deadlock ensues.

**No preemption:**
```typescript
// There is no mechanism to forcibly take mutexA from Thread 1
// Thread 2 cannot call: mutexA.forceRelease() — no such operation
// Thread 2 must wait indefinitely if Thread 1 never calls mutexA.release()
```
Mutexes in POSIX, Java, and most language runtimes are non-preemptible by design — only the owning thread can release them.

**Circular wait:**
```
Thread 1: holds Lock A, waiting for Lock B
Thread 2: holds Lock B, waiting for Lock A
→ Circular dependency: T1 → B ← T2 → A ← T1
```
```typescript
// Thread 1
await lockA.acquire();
await lockB.acquire(); // blocks — Thread 2 holds B

// Thread 2 (concurrent)
await lockB.acquire();
await lockA.acquire(); // blocks — Thread 1 holds A
// ↑ Deadlock: neither can proceed
```

**Q4. What is a resource allocation graph, and how do you use it to detect deadlock?**
A: A resource allocation graph (RAG) is a directed bipartite graph with two types of nodes — threads (circles) and resources (rectangles) — and two types of edges:

- **Request edge** (thread → resource): thread T is waiting to acquire resource R.
- **Assignment edge** (resource → thread): resource R is currently held by thread T.

Reading a RAG:
- A resource rectangle may contain multiple dots, each representing one instance of that resource type (e.g., a semaphore with count 3 has 3 dots).
- If the graph contains a **cycle** and every resource in the cycle has exactly one instance, the cycle is a deadlock.
- If some resources in the cycle have multiple instances, a cycle is necessary but not sufficient for deadlock — some instances may be available to break the cycle.

```
Example deadlock RAG:

T1 ──request──► R1 ──assigned──► T2
↑                                  │
assigned                         request
│                                  ↓
R2 ◄──request── T2    T1 ──request──► R2

Simplified view:
T1 holds R2, waits for R1
T2 holds R1, waits for R2
Cycle: T1 → R1 → T2 → R2 → T1 ← deadlock confirmed (single-instance resources)
```

Detection algorithm:
1. Build the wait-for graph (collapse resources — just draw T_i → T_j if T_i waits for something held by T_j).
2. Run a cycle detection algorithm (DFS with a "currently in stack" visited set).
3. Any cycle in the wait-for graph is a deadlock.

**Q5. What is the difference between deadlock prevention, avoidance, detection, and recovery?**
A: Four strategies, each making a different tradeoff between safety, performance, and implementation complexity:

| Strategy | When it acts | Mechanism | Cost |
|--|--|--|--|
| **Prevention** | At design time | Eliminate one Coffman condition structurally | Reduced concurrency or throughput |
| **Avoidance** | At runtime, before granting resources | Check if granting a request keeps system in a "safe state" | Overhead per resource request; requires advance knowledge of max claims |
| **Detection** | At runtime, after deadlock occurs | Periodically run cycle detection on the wait-for graph | Overhead of detection algorithm; recovery cost |
| **Recovery** | After detection | Break the deadlock by aborting threads or preempting resources | Work lost; potential for cascading failures |

In practice:
- **OS-level resources** (memory, devices) — most OSes use detection + recovery (process termination, resource preemption).
- **Database transactions** — DBMSes use detection + recovery (deadlock victim selection, transaction rollback) or timeout-based recovery.
- **Application-level locks** — prevention is preferred (consistent lock ordering) because detection requires runtime infrastructure. Avoidance (Banker's algorithm) is too expensive for most application code.
- **Distributed systems** — prevention is impractical across network partitions; detection via edge-chasing or centralised wait-for graphs, recovery via saga rollback or timeout.

## Section 2: Prevention Strategies

**Q6. How do you prevent deadlock by eliminating the "mutual exclusion" condition?**
A: Eliminating mutual exclusion means making resources shareable — allowing multiple threads to use them simultaneously. This is applicable only for resources that are inherently shareable:

- **Read-only resources** — a configuration file, a compiled regex, a lookup table. Multiple readers can share without conflict. Use `ReadWriteLock` (`RwLock` in Rust, `sync.RWMutex` in Go, `ReentrantReadWriteLock` in Java) to allow concurrent reads while serialising writes:
```go
// Go — multiple readers, one writer
var mu sync.RWMutex
var cache map[string]string

func read(key string) string {
    mu.RLock()           // multiple goroutines can hold RLock simultaneously
    defer mu.RUnlock()
    return cache[key]
}

func write(key, value string) {
    mu.Lock()            // exclusive — waits for all RLocks to release
    defer mu.Unlock()
    cache[key] = value
}
```

- **Lock-free data structures** — replace mutual exclusion with atomic operations (CAS — compare-and-swap). The data structure is always accessible; threads contend only at the hardware level, never blocking:
```typescript
// Atomic counter — no mutex, no deadlock possible from mutual exclusion
const counter = new SharedArrayBuffer(4);
const view = new Int32Array(counter);
Atomics.add(view, 0, 1); // atomic increment — no lock acquired
```

- **Immutable data** — if data never changes after creation, it can be shared freely. Functional programming styles (immutable records, persistent data structures) eliminate the need for mutual exclusion on data that is only read.

Limitation: mutual exclusion cannot be eliminated for resources that are genuinely non-shareable (a physical printer, a DB row being updated, a write position in a file). Eliminating it is only possible when the resource's nature permits sharing.

**Q7. How do you prevent deadlock by eliminating the "hold and wait" condition?**
A: Two approaches, each with different tradeoffs:

**Approach 1 — Acquire all resources atomically before starting**
A thread must declare all resources it will ever need and acquire them all at once before doing any work. If any is unavailable, it acquires none and waits:

```typescript
// All-or-nothing resource acquisition
async function processTransaction(accountA: string, accountB: string): Promise<void> {
  const locks = [accountA, accountB].sort(); // consistent ordering too, for extra safety
  const acquired: Mutex[] = [];

  for (const lockId of locks) {
    const lock = getLock(lockId);
    const success = await lock.tryAcquire(timeout: 100); // non-blocking attempt
    if (!success) {
      // Failed to acquire all — release what we have and retry
      for (const held of acquired) held.release();
      throw new RetryableError('Could not acquire all locks');
    }
    acquired.push(lock);
  }

  try {
    await executeTransfer(accountA, accountB);
  } finally {
    for (const lock of acquired) lock.release();
  }
}
```

Cost: requires knowing all resource needs upfront (not always possible); reduces concurrency because threads hold resources longer than needed (they hold A while waiting for B, but here they hold both from the start even if they don't need both immediately).

**Approach 2 — Release all resources before requesting new ones**
A thread must release everything it currently holds before requesting additional resources:

```typescript
// Release before re-request
async function twoPhaseWork(): Promise<void> {
  const result1 = await withLock(lockA, async () => {
    return computePhase1(); // acquire A, do work, release A
  });
  // lockA is released here — thread holds nothing

  await withLock(lockB, async () => {
    await computePhase2(result1); // acquire B, do work, release B
  });
  // lockB is released — thread holds nothing
}
```

Cost: work from phase 1 may need to be redone if phase 2 fails; released resources may be grabbed by other threads, requiring re-acquisition.

**Q8. How do you prevent deadlock by eliminating the "no preemption" condition?**
A: Preemption means forcibly taking a resource from a thread that holds it. For some resources this is feasible; for others it is not.

**For CPU** — the OS already does this via preemptive scheduling. Not relevant to application-level deadlock.

**For DB transactions** — databases implement preemption via deadlock victim selection. When a deadlock cycle is detected, the DBMS picks a victim transaction (usually the one with least work done or lowest priority) and rolls it back, releasing all its locks. The victim's work is lost; it must retry:
```sql
-- PostgreSQL deadlock victim: transaction is automatically rolled back
-- ERROR: deadlock detected
-- DETAIL: Process 12345 waits for ShareLock on transaction 67890;
--         blocked by process 67890.
--         Process 67890 waits for ShareLock on transaction 12345;
--         blocked by process 12345.
-- HINT: See server log for query details.
```

**For application locks with timeouts** — `tryLock(timeout)` is a soft form of preemption. If a lock cannot be acquired within the timeout, the thread voluntarily releases its held resources and retries, simulating the effect of preemption:
```java
// Java — tryLock with timeout
boolean acquiredA = lockA.tryLock(100, TimeUnit.MILLISECONDS);
if (!acquiredA) return false; // give up rather than wait forever

boolean acquiredB = lockB.tryLock(100, TimeUnit.MILLISECONDS);
if (!acquiredB) {
  lockA.unlock(); // release held resource — simulates preemption
  return false;
}
// Both acquired — proceed
```

**For memory** — the OS can preempt memory from a process (swap to disk), but this is not relevant to application deadlock (mutexes, not memory pages, cause application deadlock).

True preemption is difficult for resources with state: revoking a mutex from a thread mid-write corrupts the protected data structure. This is why preemption via timeout + rollback is the practical approach — it restores consistency by undoing work rather than forcibly transferring an inconsistent resource.

**Q9. How do you prevent deadlock by eliminating the "circular wait" condition — and why is this the most practical prevention strategy?**
A: Circular wait is eliminated by imposing a **global total ordering on all lock acquisition**. If every thread always acquires locks in the same order, a cycle cannot form — the wait-for graph is a DAG (directed acyclic graph) and cannot have cycles:

```typescript
// Global lock ordering by resource ID
const LOCK_ORDER: Record<string, number> = {
  'accounts': 1,
  'ledger': 2,
  'notifications': 3,
  'audit_log': 4,
};

function acquireInOrder(locks: string[]): Promise<void[]> {
  const ordered = [...locks].sort((a, b) => LOCK_ORDER[a] - LOCK_ORDER[b]);
  return Promise.all(ordered.map(lockId => getLock(lockId).acquire()));
}

// Thread 1: transfers from account A to account B
// Acquires: accounts(1) → ledger(2) — always this order

// Thread 2: concurrent transfer, same locks
// Acquires: accounts(1) → ledger(2) — same order, no cycle possible
```

**Why circular wait prevention is most practical:**
- **No runtime overhead** — the ordering is enforced at design time in code. No runtime checks, no overhead per lock acquisition.
- **Simple to verify** — a code review can confirm that all lock acquisition follows the established order. No complex runtime machinery.
- **No reduced concurrency** — unlike hold-and-wait prevention (which forces all-or-nothing acquisition), ordering allows a thread to hold A while working before acquiring B — it just must acquire A before B everywhere.
- **Works for all resource types** — any lockable resource (mutexes, DB row locks, file locks) can be ordered.

The classic example: banking transfers. If transferring from account A to account B always locks the account with the lower ID first, two concurrent opposite-direction transfers cannot deadlock:
```typescript
async function transfer(fromId: number, toId: number, amount: number): Promise<void> {
  // Always lock lower ID first — eliminates circular wait
  const [first, second] = fromId < toId
    ? [fromId, toId]
    : [toId, fromId];

  await getLock(first).acquire();
  try {
    await getLock(second).acquire();
    try {
      await executeTransfer(fromId, toId, amount);
    } finally {
      getLock(second).release();
    }
  } finally {
    getLock(first).release();
  }
}
```

Thread 1: transfer(A=3, B=7) → locks 3, then 7.
Thread 2: transfer(A=7, B=3) → locks 3, then 7 (same order — 3 < 7).
Neither can hold 7 while waiting for 3 — the cycle is impossible.

**Q10. What is the Banker's Algorithm, and when is deadlock avoidance via it practical?**
A: The Banker's Algorithm (Dijkstra, 1965) is a deadlock avoidance algorithm. Before granting any resource request, the algorithm checks whether fulfilling the request leaves the system in a **safe state** — a state from which all threads can eventually complete, even if they request their maximum declared resources:

A state is safe if there exists a safe sequence: an ordering of all threads such that each thread's remaining resource needs can be satisfied by the currently available resources plus all resources held by threads earlier in the sequence.

```
Example with 3 resource types (A=10, B=5, C=7 total):

Process | Max     | Allocated | Need (Max-Alloc) | Available
P0      | 7,5,3   | 0,1,0     | 7,4,3            | 3,3,2
P1      | 3,2,2   | 2,0,0     | 1,2,2            |
P2      | 9,0,2   | 3,0,2     | 6,0,0            |
P3      | 2,2,2   | 2,1,1     | 0,1,1            |
P4      | 4,3,3   | 0,0,2     | 4,3,1            |

Safe sequence: P1 → P3 → P4 → P0 → P2
(each can be satisfied with available + previously finished threads' resources)
```

If a resource request would move the system to an unsafe state, the request is denied and the requesting thread must wait.

**Why it is rarely practical for application code:**
- **Requires advance declaration of maximum resource needs** — threads must declare upfront the maximum number of each resource type they might ever request. Real application code rarely knows this.
- **Static resource types** — the algorithm assumes a fixed set of resource types. Dynamic resource creation (new DB connections, new file handles) breaks the model.
- **Performance overhead** — every resource request requires running the safety check algorithm (O(n²) in number of threads and resource types). Too expensive for high-throughput systems.
- **Overly conservative** — the algorithm may deny a request that would not actually lead to deadlock, reducing concurrency unnecessarily.

Practical use: Banker's algorithm is taught as the theoretical foundation of avoidance, and it does appear in some real-time OS schedulers. For application development, lock ordering (circular wait prevention) gives most of the same safety with none of the runtime overhead.

## Section 3: Deadlock in Databases & Distributed Systems

**Q11. How do database engines detect and recover from deadlocks?**
A: Database engines maintain a wait-for graph of active transactions. Periodically (PostgreSQL: every `deadlock_timeout` milliseconds, default 1 second), a background process or the blocking transaction itself checks for cycles in the wait-for graph:

```sql
-- PostgreSQL: two transactions deadlock on row locks

-- Transaction 1:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- acquires row lock on id=1
-- (waiting for Transaction 2 to release lock on id=2)
UPDATE accounts SET balance = balance + 100 WHERE id = 2; -- BLOCKS

-- Transaction 2 (concurrent):
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 2; -- acquires row lock on id=2
UPDATE accounts SET balance = balance + 100 WHERE id = 1; -- BLOCKS → deadlock!

-- PostgreSQL detects the cycle after deadlock_timeout (1s by default):
-- ERROR 40P01: deadlock detected
-- Transaction 2 is chosen as victim and rolled back
-- Transaction 1 proceeds
```

**Victim selection criteria** (varies by DBMS):
- **PostgreSQL** — the transaction that was detected as "the blocker" in the deadlock cycle is typically chosen; the DBMS tries to minimise wasted work.
- **MySQL InnoDB** — the transaction that has modified the fewest rows (least work to undo) is chosen as victim.
- **SQL Server** — configurable via `DEADLOCK_PRIORITY`; lowest priority is victim; ties broken by least rollback cost.
- **Oracle** — detects the cycle and rolls back the statement (not the whole transaction) that caused it.

**Recovery:**
- The victim transaction receives an error (PostgreSQL: `ERROR 40P01`; MySQL: `ERROR 1213`).
- The application must catch this error and retry the transaction.
- All locks held by the victim are released, allowing the surviving transactions to proceed.

**Q12. What is a distributed deadlock, and why is it harder to detect than a local deadlock?**
A: A distributed deadlock occurs across multiple nodes in a distributed system — Thread T1 on Node A holds resource R1 and waits for resource R2 on Node B; Thread T2 on Node B holds R2 and waits for R1 on Node A. Neither node's local wait-for graph shows a cycle — the cycle only appears when the graphs are merged across nodes.

Detection challenges:

- **No global shared memory** — each node only sees its local wait-for graph. There is no single place to check for cycles without communication.
- **Network latency and partitions** — by the time a centralised deadlock detector has collected wait-for information from all nodes and identified a cycle, the deadlock may have already resolved (a timeout fired, a transaction was rolled back) or may not yet have fully formed (messages are in transit). This leads to **phantom deadlocks** (detecting a deadlock that no longer exists) and **missed deadlocks** (a real deadlock not detected because snapshot was taken between its formation and detection).
- **Message ordering** — in an asynchronous distributed system, messages from different nodes may arrive out of order, causing the assembled wait-for graph to be temporarily inconsistent.

**Detection approaches:**

- **Centralised detection** — all nodes periodically report their local wait-for edges to a central coordinator, which assembles the global graph and runs cycle detection. Simple but the coordinator is a single point of failure and a bottleneck.
- **Path-pushing (edge-chasing)** — each node propagates "probe" messages along wait-for edges. A probe that returns to its origin confirms a cycle. Used in systems like Google Spanner's distributed deadlock detection.
- **Timeout-based** — don't detect deadlocks at all; instead, time out any resource request that waits longer than a threshold. Simple, universal, but sacrifices some performance (legitimate long waits are treated as deadlocks).

**Q13. How do distributed sagas relate to deadlock, and what makes them a deadlock-free alternative to distributed transactions?**
A: A distributed saga is a sequence of local transactions, each within a single service, coordinated by a saga orchestrator or choreography. Instead of holding locks across services (which creates the conditions for distributed deadlock), a saga completes each step and either continues to the next or executes a compensating transaction to undo completed steps:

```
Saga: PlaceOrder
  Step 1: PaymentService.chargeCard()         → succeeds, lock released
  Step 2: InventoryService.reserveStock()     → succeeds, lock released
  Step 3: ShippingService.scheduleDelivery()  → fails
  Compensating:
  Step 2C: InventoryService.releaseReservation()
  Step 1C: PaymentService.refundCard()
```

Why sagas avoid deadlock:
- **Hold and wait is eliminated** — each service acquires and releases its local lock within a single local transaction. No service holds a lock while waiting for another service to respond over the network.
- **No cross-service lock scope** — there is no global distributed lock held for the duration of the saga. Each step completes (commits or compensates) before the next begins.
- **Network partition tolerance** — if a service is unavailable, the saga can retry or compensate without being permanently blocked (no "hold and wait" across a network partition).

The tradeoff: sagas provide **eventual consistency**, not strong ACID atomicity. Between steps, the system is in an intermediate state visible to other transactions. Compensating transactions must be idempotent and may not perfectly undo all effects (a sent email cannot be "unsent"). This is the price of deadlock freedom in distributed systems.

**Q14. How does optimistic locking relate to deadlock, and when do you choose it over pessimistic locking?**
A: Optimistic locking eliminates deadlock by never acquiring a lock during the read or compute phase — it only checks for conflicts at commit time. The Coffman conditions cannot be satisfied because "hold and wait" and "mutual exclusion" are never active during the main execution:

```typescript
// Optimistic locking with version column (TypeORM)
@Entity()
export class Account {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  balance: number;

  @VersionColumn()       // auto-incremented on every update
  version: number;
}

async function transfer(fromId: number, toId: number, amount: number): Promise<void> {
  // Read phase — no lock acquired
  const fromAccount = await accountRepo.findOneBy({ id: fromId });
  const toAccount = await accountRepo.findOneBy({ id: toId });

  fromAccount.balance -= amount;
  toAccount.balance += amount;

  // Write phase — version check at commit time
  // If version changed since read, throws OptimisticLockVersionMismatchError
  await accountRepo.save(fromAccount); // checks version column
  await accountRepo.save(toAccount);
}
// No locks held → no hold and wait → deadlock impossible
```

**When optimistic locking is better than pessimistic:**
- **Low write contention** — most transactions read and commit successfully without conflict. Pessimistic locking's lock overhead would be wasted.
- **Read-heavy workloads** — many concurrent readers, few writers. Optimistic locking allows all reads to proceed without blocking.
- **Short transactions** — the window for a version conflict is small; retry cost is low.

**When pessimistic locking is better:**
- **High write contention** — many concurrent writers on the same rows. Optimistic locking causes many retries (wasted work); a lock queue is more efficient.
- **Long transactions** — a long read-compute-write cycle means a high probability of a version conflict and an expensive retry.
- **Explicit serialisation required** — when the application logic requires that no other transaction reads the same row between read and write (e.g., "check then act" patterns like inventory reservation).

## Section 4: Deadlock in Real Systems

**Q15. How does Node.js avoid classical deadlocks, and what is its equivalent failure mode?**
A: Node.js's single-threaded event loop eliminates the classical Coffman conditions for mutexes:
- **No mutual exclusion on JavaScript state** — only one callback runs at a time; no two callbacks compete for a mutex on shared JS memory.
- **No hold and wait** — a callback cannot hold a lock and then suspend waiting for another lock; it either runs to completion or yields at an `await` point.
- **No circular wait** — with one execution unit, a cycle of threads waiting for each other is impossible.

Node.js's equivalent failure mode is the **deadlocked event loop** — not from locks, but from **circular Promise chains**:
```typescript
// Circular Promise dependency — event loop equivalent of deadlock
async function functionA(): Promise<void> {
  await functionB(); // waits for B
}

async function functionB(): Promise<void> {
  await functionA(); // waits for A → infinite recursion / stack overflow
}

// More subtle: Promise that never resolves
const hangingPromise = new Promise<void>(() => {}); // resolver never called
await hangingPromise; // event loop continues other work but this chain never resumes
```

A more operationally relevant failure: using `async_hooks` or manual Promise coordination to create a situation where Promise A resolves only when Promise B resolves, and Promise B resolves only when Promise A resolves. The event loop keeps running (other callbacks execute), but the specific async chain is permanently suspended — the Node.js equivalent of a blocked thread.

**Worker thread deadlock** does exist when using `worker_threads` with `SharedArrayBuffer` and `Atomics.wait()`:
```javascript
// Main thread
const sab = new SharedArrayBuffer(4);
const view = new Int32Array(sab);
worker.postMessage({ sab });
Atomics.wait(view, 0, 0); // main thread blocks — can't process messages!

// Worker
Atomics.notify(view, 0, 1); // tries to wake main thread
// But main thread is blocked in Atomics.wait — can't receive the postMessage
// that would trigger the notify → deadlock
```
`Atomics.wait()` on the main thread is forbidden in browsers for this reason; in Node.js it works but can deadlock if the notify path goes through the main thread's message handler.

**Q16. How does async/await in TypeScript/JavaScript create "logical deadlocks" without OS-level locking?**
A: Logical deadlocks in async code occur when two coroutines each await a Promise that the other is responsible for resolving:

```typescript
// Pattern 1: mutual await — each waits for the other's signal
class RequestCoordinator {
  private resolveA!: () => void;
  private resolveB!: () => void;

  readonly signalA = new Promise<void>(r => { this.resolveA = r; });
  readonly signalB = new Promise<void>(r => { this.resolveB = r; });

  async handlerA(): Promise<void> {
    await this.signalB; // waits for B to send signal
    this.resolveA();    // sends signal to B
  }

  async handlerB(): Promise<void> {
    await this.signalA; // waits for A to send signal — but A is waiting for B!
    this.resolveB();    // never reached
  }
}
// Both handlers suspend; neither resolveA nor resolveB is ever called → deadlock
```

```typescript
// Pattern 2: async mutex misuse in same event loop tick
class AsyncMutex {
  private locked = false;
  private queue: (() => void)[] = [];

  async acquire(): Promise<void> {
    if (!this.locked) { this.locked = true; return; }
    return new Promise(resolve => this.queue.push(resolve));
  }

  release(): void {
    const next = this.queue.shift();
    if (next) next(); else this.locked = false;
  }
}

// Reentrant acquisition — same "thread" (async context) acquires twice
async function process(): Promise<void> {
  await mutex.acquire();        // acquired
  await helperFunction();       // calls mutex.acquire() internally
  mutex.release();
}

async function helperFunction(): Promise<void> {
  await mutex.acquire();  // blocks — mutex already held by same async context
  // Node.js event loop is NOT blocked — other callbacks run
  // but this async chain is permanently suspended
  mutex.release();        // never reached
}
```

Detection: unlike OS deadlocks, logical async deadlocks don't show up in process monitors (`top` shows the process alive and event loop running). They appear as:
- Requests that never complete (no response, no timeout).
- `await` points that never resume (detectable with async stack traces or timeout wrappers).
- Promise leak detection tools (Node.js `--trace-warnings` shows unhandled rejections and pending Promises).

- **Interrupt a deadlocked thread** — `thread.interrupt()` works if the thread is blocked on an interruptible operation (`lockInterruptibly()`, `Thread.sleep()`, `Object.wait()`). Standard `synchronized` blocks are not interruptible.
- **Use `tryLock` with timeout** — `ReentrantLock.tryLock(timeout)` instead of `synchronized` to prevent permanent blocking.
- **Restart the service** — if deadlock detection is periodic and recovery is complex, restarting the JVM process is the simplest guaranteed recovery.

## Section 5: Tradeoffs, Pitfalls & Anti-patterns

**Q18. What are the most common real-world causes of deadlock in backend services?**
A: Ranked by frequency in production:

**1 — Inconsistent lock ordering across code paths**
The most common cause. Two code paths lock the same resources in different orders:
```typescript
// Path A (order creation): locks Account, then Inventory
// Path B (order cancellation): locks Inventory, then Account
// Concurrent execution → circular wait
```
Fix: enforce a canonical lock order, enforced via a `ResourceLockManager` that sorts locks before acquiring them.

**2 — Database lock escalation**
An ORM issues queries that acquire more locks than the developer realises. A `SELECT ... FOR UPDATE` on a table without an index causes a full table lock instead of a row lock — a transaction that expected to lock one row now locks the whole table, blocking unrelated concurrent transactions:
```sql
-- Without index on user_id — locks entire table
SELECT * FROM orders WHERE user_id = 42 FOR UPDATE;
-- Another transaction locking a different user's orders → deadlock
```
Fix: ensure columns used in `WHERE` clauses of locking queries are indexed.

**3 — Lock held across I/O or network call**
A thread acquires a lock, makes a slow network call (third-party API, downstream service), and holds the lock for the duration. Another thread tries to acquire the same lock while also holding a lock the first thread needs:
```typescript
await mutex.acquire();
const result = await fetch('https://slow-api.example.com'); // holds mutex for 2+ seconds
await processResult(result);
mutex.release();
```
Fix: never hold application locks across I/O. Release the lock, make the call, reacquire.

**4 — Missing lock on a code path**
99% of code paths use consistent lock ordering, but one rarely-executed path (an admin endpoint, a cron job, a migration script) doesn't acquire the lock in the right order — or doesn't acquire it at all, then escalates to a write that conflicts with a lock held elsewhere.
Fix: centralise lock acquisition in a single utility function; code review any direct lock access.

**5 — Connection pool exhaustion creating a "soft deadlock"**
Not a true Coffman deadlock, but has the same effect. All connections in a pool are held by threads waiting for other threads to complete their queries — which also need connections. The pool is exhausted; no new connections can be obtained; all threads block:
```
Thread 1: holds connection 1, waiting for response to query that needs connection 2
Thread 2: holds connection 2, waiting for connection 1 to become available
→ Connection pool deadlock
```
Fix: ensure max connections > max threads that can hold a connection while waiting; use `tryAcquire` with timeout on the pool; never nest connection acquisitions within the same thread.

**Q19. What is "lock convoy," and how does it relate to deadlock risk?**
A: A lock convoy is a performance anti-pattern where many threads accumulate in a queue waiting for the same frequently-held lock. While not deadlock (threads do eventually progress), lock convoys increase deadlock risk and reduce throughput:

Mechanism: Thread A releases the lock. The OS wakes the highest-priority waiter (Thread B). But before Thread B runs, Thread A re-acquires the lock (because it immediately needs it again). Thread B wakes, finds the lock taken, and goes back to sleep. This cycle repeats — the lock appears to transfer but Thread A retains it almost permanently.

The deadlock connection: a lock convoy concentrates resource ownership in one thread. If that thread then needs to acquire a second lock while holding the first, and other threads in the convoy hold the second lock, the conditions for deadlock form naturally from the convoy.

Fixes:
- **Reduce lock scope** — release the lock as soon as the critical section ends; don't re-acquire immediately.
- **Use `yield()` after release** — give waiting threads a genuine opportunity to run before the releaser re-acquires.
- **Lock-free algorithms** for the high-contention resource.
- **Sharding** — split one heavily contended lock into N per-shard locks; N threads can proceed in parallel.

**Q20. How do you design a system to be deadlock-free from the start, rather than fixing deadlocks after they occur?**
A: A design-time checklist:

**1 — Identify all shared mutable resources** — list every resource that multiple threads can write: DB tables (and their lock granularity), in-memory caches, queues, file handles, external API connection pools. Deadlock can only involve these.

**2 — Assign a canonical lock order** — number every resource type. Document the order in `ARCHITECTURE.md` or a code comment at the lock manager. Make violation a linting rule or CI check.

**3 — Encapsulate locking** — never acquire locks directly in business logic. Route all acquisitions through a `LockManager` or repository layer that enforces ordering:
```typescript
// Enforce ordering at the infrastructure layer — business logic never calls lock() directly
class LockManager {
  async withLocks<T>(resourceIds: string[], fn: () => Promise<T>): Promise<T> {
    const sorted = resourceIds.sort((a, b) => getLockOrder(a) - getLockOrder(b));
    return this.acquireInOrder(sorted, fn);
  }
}
```

**4 — Prefer lock-free patterns for high-contention paths** — use atomic operations, immutable data, and message-passing (channels, queues) instead of shared mutable state where throughput requirements make locking risky.

**5 — Use timeouts everywhere** — all lock acquisitions should have a timeout. A `tryLock` that fails is a deadlock symptom caught early, not a hung system.

**6 — Test with `ThreadSanitizer` / `go race` detector / Helgrind** — static race and deadlock detectors catch lock ordering violations before production:
```bash
go test -race ./...              # Go race detector — catches lock races and ordering issues
valgrind --tool=helgrind ./app   # POSIX thread deadlock and race detection
```

**Q21. "Two engineers report that the payments service occasionally freezes for 30 seconds before recovering. You suspect a database deadlock. Walk through your investigation."**

**Step 1 — Confirm deadlock in DB logs**
```bash
# PostgreSQL — check for deadlock errors
grep -i "deadlock" /var/log/postgresql/postgresql-*.log
# 2024-01-15 14:23:41 IST [12345] ERROR:  deadlock detected
# 2024-01-15 14:23:41 IST [12345] DETAIL:  Process 12345 waits for ShareLock on
#   transaction 67890; blocked by process 67890.

# Enable detailed deadlock logging
# In postgresql.conf:
# log_lock_waits = on
# deadlock_timeout = 1s
# log_min_duration_statement = 0   # log all queries during investigation
```

**Step 2 — Identify the query pair causing the cycle**
```sql
-- While deadlock is occurring, inspect pg_locks
SELECT
  l.pid,
  l.relation::regclass AS table,
  l.mode,
  l.granted,
  a.query,
  a.query_start,
  now() - a.query_start AS duration
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE NOT l.granted

```

**Step 3 — Reproduce in staging**

```bash
# Terminal 2
psql -c "BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 2; pg_sleep(1); UPDATE accounts SET balance = balance + 100 WHERE id = 1; COMMIT;"
```

Apply consistent lock ordering at the application layer:
```typescript
// In the payments service:

await db.transaction(async (trx) => {
  await trx.query('SELECT * FROM accounts WHERE id = $1 FOR UPDATE', [first]);
  await trx.query('SELECT * FROM accounts WHERE id = $1 FOR UPDATE', [second]);

  await trx.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toAccountId]);

```

```typescript
  }

}
```

**Q22. "Design a distributed lock service for a fintech platform where multiple services need to lock the same account for writes. How do you prevent deadlock?"**
A: A distributed lock service that is deadlock-free by design:

**Core design — lock ordering at the service boundary:**
```typescript
// Lock service API — enforces global ordering
class DistributedLockService {
  async withAccountLocks<T>(
    accountIds: string[],
    operation: () => Promise<T>,
    options = { timeout: 5000 }
  ): Promise<T> {
    // Enforce canonical ordering — alphabetical by accountId
    const ordered = [...new Set(accountIds)].sort();

    const locks: RedisLock[] = [];
    try {
      for (const accountId of ordered) {
        const lock = await this.redis.set(
          `lock:account:${accountId}`,
          this.nodeId,
          'NX', 'PX', options.timeout  // NX: only if not exists; PX: TTL in ms
        );
        if (!lock) throw new LockContentionError(accountId);
        locks.push({ key: `lock:account:${accountId}` });
      }
      return await operation();
    } finally {
      // Release in reverse order (convention)
      for (const lock of locks.reverse()) {
        await this.redis.eval(
          // Lua script: only release if we own the lock (prevents releasing another client's lock)
          `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`,
          1, lock.key, this.nodeId
        );
      }
    }
  }
}
```

**Why this is deadlock-free:**
- **Circular wait eliminated** — alphabetical ordering of accountIds means T1 acquiring locks [A, B] and T2 acquiring locks [B, A] both acquire A first — no cycle possible.
- **No preemption needed** — the Redis TTL is the preemption mechanism. If a service crashes while holding locks, TTL releases them automatically after `timeout` ms.
- **Hold and wait limited** — if any lock in the set cannot be acquired (another holder), all acquired locks are released immediately and the operation fails with `LockContentionError`, which the caller retries. The service never holds some locks while waiting indefinitely for others.

**Client retry with jitter:**
```typescript
async function transferWithRetry(fromId: string, toId: string, amount: number): Promise<void> {
  const maxRetries = 5;
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      await lockService.withAccountLocks([fromId, toId], () =>
        performTransfer(fromId, toId, amount)
      );
      return;
    } catch (err) {
      if (err instanceof LockContentionError && attempt < maxRetries - 1) {
        // Exponential backoff with jitter — prevents thundering herd on retry
        const delay = Math.min(100 * 2 ** attempt, 2000) + Math.random() * 100;
        await sleep(delay);
        continue;
      }
      throw err;
    }
  }
}
```

**Q23. "A Go microservice handling concurrent order processing is intermittently hanging. `GODEBUG=schedtrace` shows goroutines stuck in runnable state. You suspect a deadlock. How do you diagnose?"**
A: Go has a built-in deadlock detector for the simple case (all goroutines blocked) but doesn't detect partial deadlocks (some goroutines blocked, others running). Systematic diagnosis:

**Step 1 — Check for all-goroutine deadlock**
```bash
# If ALL goroutines are blocked, Go runtime prints and exits:
# fatal error: all goroutines are asleep - deadlock!
# goroutine 1 [chan receive]:
# main.main()
#     /app/main.go:15 +0x58

# If only SOME are blocked, use pprof:
curl http://localhost:6060/debug/pprof/goroutine?debug=2 > goroutines.txt
grep -A 20 "goroutine.*\[chan"  goroutines.txt  # blocked on channel ops
grep -A 20 "goroutine.*\[semacquire" goroutines.txt  # blocked on mutex
```

**Step 2 — Identify the blocking pattern**
```bash
# goroutine 47 [semacquire]:
# sync.runtime_SemacquireMutex(0xc000128068, 0x0, 0x1)
#     /usr/local/go/src/runtime/sema.go:71 +0x47
# sync.(*Mutex).lockSlow(0xc000128060)
#     /usr/local/go/src/runtime/mutex.go:138 +0x105
# main.(*OrderProcessor).Process(0xc000128060)
#     /app/processor.go:42 +0x89        ← blocked here — waiting for mutex
#
# goroutine 48 [semacquire]:
# ... (same mutex address 0xc000128060) ← both waiting for same mutex
# main.(*InventoryService).Reserve(0xc000128060)
#     /app/inventory.go:67 +0x72        ← held by goroutine 48 while it waits for another
```

**Step 3 — Look for channel deadlocks**
```go
// Common pattern: unbuffered channel send with no receiver ready
orders := make(chan Order)         // unbuffered
go func() {
  result := processOrder(order)
  orders <- result                 // blocks if no one is receiving
}()

// If the receiver is also waiting for the sender to finish first:
<-orders  // never reached because sender is blocked → deadlock
```

```bash
# goroutine 23 [chan send]:           ← sender blocked
# goroutine 24 [chan receive]:        ← receiver blocked on different channel
```

**Step 4 — Fix**
The most common Go deadlock cause is a goroutine that writes to a channel assuming a receiver exists, when the receiver goroutine has already exited (due to a timeout, error, or context cancellation):
```go
// Fix: always use context cancellation + select
func processWithTimeout(ctx context.Context, order Order) error {
  results := make(chan Result, 1) // buffered — sender never blocks
  go func() {
    results <- computeResult(order)
  }()

  select {
  case result := <-results:
    return handleResult(result)
  case <-ctx.Done():
    return ctx.Err() // timeout or cancellation — sender goroutine will eventually complete
  }
}
```

**Q24. "How would you explain the four Coffman conditions and deadlock prevention to a new engineer joining the team who has never encountered a production deadlock?"**
A: Use the bank vault analogy:

"Imagine our payments service as a bank with multiple vaults (resources). Four things have to all be true at the same time for a deadlock to happen — remove any one and you're safe.

**Mutual exclusion** — each vault can only be opened by one person at a time. That's a feature, not a bug — we need it to keep money safe. We can't eliminate this one for vaults, but we can for things like reading account balances (multiple people can read simultaneously).

**Hold and wait** — Engineer A has the key to Vault 1 and is standing at Vault 2 waiting for Engineer B to come out. B has the key to Vault 2 and is standing at Vault 1 waiting for A to come out. Both are holding a key and waiting. If neither lets go, nobody moves ever.

**No preemption** — nobody can take a key from an engineer who is holding it. They have to give it up voluntarily. If someone could reach in and take the key, the deadlock would break — but that's dangerous (what if they were mid-transfer?).

**Circular wait** — A waits for B, B waits for A. That's the cycle. It could be longer: A waits for B, B waits for C, C waits for A.

In our codebase, we prevent deadlocks by eliminating circular wait — the easiest condition to break. Every engineer must always lock accounts in order of account ID, lowest first. If A=account 3 and B=account 7, everyone locks 3 first, then 7. Nobody ever locks 7 first. With that rule, a cycle is mathematically impossible — you'd need someone to hold 7 while waiting for 3, but the rule says you can never acquire 3 after 7.

That single rule is the reason we haven't had a deadlock in this service. The `LockManager.withAccountLocks()` utility enforces it automatically — you never call the locks directly."

**Q25. "You're designing the order matching engine for a stock exchange. Orders can match against multiple partially-filled limit orders simultaneously. How do you design the locking strategy to prevent deadlock while maintaining high throughput?"**
A: An order matching engine is one of the hardest locking problems — an incoming order can match against N resting orders, requiring N row locks in a sequence that must be deterministic across concurrent matching threads:

**Core design — lock ordering by price-time priority:**
```
Matching rule: an incoming BUY order at price P locks all SELL orders
at price ≤ P in ascending price order, then ascending timestamp order.
This is the canonical order everyone in the system uses — circular wait impossible.
```

```go
type Order struct {
  ID        uint64
  Price     decimal.Decimal
  Timestamp time.Time
  Side      string // "BUY" or "SELL"
  Quantity  int64
}

// Global ordering for locking: price ASC, then timestamp ASC, then ID ASC
// All matching goroutines use this order — no circular wait possible
func lockingOrder(orders []Order) []Order {
  sorted := make([]Order, len(orders))
  copy(sorted, orders)
  sort.Slice(sorted, func(i, j int) bool {
    if sorted[i].Price.Equal(sorted[j].Price) {
      if sorted[i].Timestamp.Equal(sorted[j].Timestamp) {
        return sorted[i].ID < sorted[j].ID
      }
      return sorted[i].Timestamp.Before(sorted[j].Timestamp)
    }
    return sorted[i].Price.LessThan(sorted[j].Price)
  })
  return sorted
}
```

**Throughput — sharding the order book:**
A single global lock on the entire order book is a bottleneck. Shard by instrument (ticker symbol) — RELIANCE orders never interact with INFY orders, so their locks are independent:

```go
type OrderBook struct {
  mu      sync.RWMutex // per-instrument lock
  bids    *PriceLevel  // buy orders sorted desc by price
  asks    *PriceLevel  // sell orders sorted asc by price
}

type MatchingEngine struct {
  books map[string]*OrderBook // sharded by instrument
}

func (e *MatchingEngine) Match(incoming Order) []Trade {
  book := e.books[incoming.Instrument]
  book.mu.Lock() // only the relevant instrument's book is locked
  defer book.mu.Unlock()
  return book.match(incoming)
}
```

Within one instrument's book, the matching thread holds the book lock exclusively — no other goroutine can touch this book's orders. No second lock is needed, so hold-and-wait cannot occur for orders in the same book.

**Cross-instrument orders (index futures, pairs trading):**
For orders that span two instruments (buy RELIANCE, sell NIFTY simultaneously), enforce lock ordering by instrument name alphabetically:
```go
func (e *MatchingEngine) MatchPair(leg1, leg2 Order) []Trade {
  // Lock alphabetically — NIFTY before RELIANCE always
  instruments := []string{leg1.Instrument, leg2.Instrument}
  sort.Strings(instruments)

  book1 := e.books[instruments[0]]
  book2 := e.books[instruments[1]]

  book1.mu.Lock()
  defer book1.mu.Unlock()
  book2.mu.Lock()
  defer book2.mu.Unlock()

  // Both books locked in consistent order — no circular wait
  return e.executePair(leg1, leg2)
}
```

**Avoiding lock-held-across-I/O:** the matching engine is purely in-memory. DB persistence is async (write-ahead log, Kafka event stream). The match result is written to a channel; a separate goroutine persists it. The lock is never held while waiting for disk or network I/O.

Result: deadlock-free by construction (alphabetical instrument ordering eliminates circular wait), high-throughput (sharding by instrument eliminates inter-instrument contention), and low-latency (no I/O under locks).
