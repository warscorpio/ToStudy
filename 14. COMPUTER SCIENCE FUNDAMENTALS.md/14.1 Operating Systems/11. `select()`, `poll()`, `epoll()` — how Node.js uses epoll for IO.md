# Operating Systems: `select()`, `poll()`, `epoll()` — How Node.js Uses epoll for I/O — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do `select()`, `poll()`, and `epoll()` solve, and why is it non-trivial?**
A: All three are system calls that allow a single thread to monitor multiple file descriptors (FDs) simultaneously and be notified when any of them become ready for I/O — readable, writable, or in an error state — without blocking on any individual one. The problem they solve is I/O multiplexing: how do you handle many concurrent I/O sources (network sockets, files, pipes, timers) on a single thread without either blocking on one and missing the others, or spinning in a busy-wait loop polling each one in turn?

The naive alternatives are both wrong:

**Blocking I/O per thread:** Dedicate one thread per file descriptor; each thread calls `read()` and blocks until data arrives. Works but does not scale — a server handling 10,000 concurrent connections needs 10,000 threads, each consuming ~2–8 MB of stack space (80 GB–160 GB of RAM for stacks alone), plus the OS scheduler overhead of 10,000 context switches. The C10K problem (circa 1999) named this ceiling.

**Busy-wait polling:** Loop over all FDs calling `read()` with `O_NONBLOCK` — if no data, continue to the next FD. Wastes 100% CPU spinning through FDs with no data. Any delay between polling cycles creates latency.

I/O multiplexing with `select()`/`poll()`/`epoll()` solves both: the kernel monitors all FDs simultaneously, and the calling thread sleeps until at least one FD is ready — zero CPU while waiting, immediate wakeup when data arrives, one thread for any number of FDs. This is the foundation of every event-driven server architecture.

**Q2. What is a file descriptor in the context of I/O multiplexing, and what types of FDs can these system calls monitor?**
A: A file descriptor (FD) is a small non-negative integer — an index into the process's file descriptor table — that the kernel uses to represent an open I/O resource. Every open file, socket, pipe, timer, signal, eventfd, and device is represented as an FD. They are the universal I/O abstraction in Unix: everything is a file descriptor.

Types of FDs monitorable by `select()`/`poll()`/`epoll()`:
- **TCP/UDP sockets** — the primary use case for servers: readable when data arrives or a connection closes; writable when the send buffer has space.
- **Listening sockets** — readable when a new connection is pending (ready for `accept()`).
- **Pipes and FIFOs** — readable when data is written by another process; writable when there is buffer space.
- **`timerfd`** (Linux) — readable when the timer expires; used by libuv/Node.js for timer events without a separate timer thread.
- **`eventfd`** (Linux) — a lightweight integer counter used for inter-thread or inter-process signalling; readable when the counter is non-zero.
- **`signalfd`** (Linux) — readable when a signal is pending; allows signals to be handled in the event loop rather than in asynchronous signal handlers.
- **Regular files** — technically always considered ready by `select()`/`poll()`/`epoll()` (disk I/O is handled differently); this is a known limitation — `epoll` reports regular files as always readable, so actual disk reads are done in a thread pool, not via epoll.

**Q3. What is the difference between level-triggered and edge-triggered notification, and which do `select()`, `poll()`, and `epoll()` use?**
A: The trigger mode determines when the kernel notifies the application that an FD is ready:

**Level-triggered (LT):** The kernel notifies as long as the condition is true. If a socket has 1000 bytes available and you `read()` only 100, the next `select()`/`poll()`/`epoll_wait()` call will immediately return the socket as readable again — because the condition (data available) is still true. The kernel keeps notifying until the buffer is drained. This is the default for `select()`, `poll()`, and `epoll()` (epoll defaults to LT but supports ET).

**Edge-triggered (ET):** The kernel notifies only when the state transitions — from not-ready to ready. If a socket has 1000 bytes and you `read()` only 100, the next `epoll_wait()` will NOT return the socket again (no notification) until new data arrives — the transition has already been reported. To use ET correctly, you must read in a loop until `EAGAIN` (no more data) on every notification, otherwise unread data sits in the buffer silently until new data triggers another notification. ET is more complex but enables higher performance: fewer kernel-to-userspace transitions, no redundant wakeups.

**How each system call uses them:**
- `select()` — level-triggered only. No choice.
- `poll()` — level-triggered only. No choice.
- `epoll()` — level-triggered by default; edge-triggered by passing `EPOLLET` flag during `epoll_ctl()`. `epoll` also supports `EPOLLONESHOT` — the FD is disabled after one notification and must be explicitly re-armed; useful for multi-threaded event loops where you don't want two threads both woken for the same FD.

## Section 2: `select()` — The Original

**Q4. How does `select()` work, and what is its system call interface?**
A: `select()` takes three sets of file descriptors (readable, writable, error), a maximum FD number, and an optional timeout. It blocks until at least one FD in any set becomes ready, then returns with the sets modified to indicate only the ready FDs:

```c
#include <sys/select.h>

int select(
    int nfds,           // highest FD number + 1 (e.g., if monitoring FD 5, pass 6)
    fd_set *readfds,    // set of FDs to check for readability
    fd_set *writefds,   // set of FDs to check for writability
    fd_set *exceptfds,  // set of FDs to check for exceptions
    struct timeval *timeout // NULL = block forever; {0,0} = return immediately (poll)
);
// Returns: number of ready FDs, 0 on timeout, -1 on error

// Usage
fd_set readfds;
FD_ZERO(&readfds);          // clear the set
FD_SET(sock1, &readfds);    // add sock1
FD_SET(sock2, &readfds);    // add sock2

int ready = select(max_fd + 1, &readfds, NULL, NULL, NULL);
if (ready > 0) {
    if (FD_ISSET(sock1, &readfds)) { /* sock1 is readable */ }
    if (FD_ISSET(sock2, &readfds)) { /* sock2 is readable */ }
}
```

The `fd_set` is a fixed-size bitmask — one bit per possible FD. The kernel scans the bitmask to find which FDs to monitor, waits for any to become ready, then writes back which are ready. The application then iterates the bitmask to find the ready ones.

**Q5. What are `select()`'s fundamental limitations, and why did they necessitate `poll()` and then `epoll()`?**
A: `select()` has three hard limitations that make it unsuitable for high-connection-count servers:

**Limitation 1 — Fixed FD limit (`FD_SETSIZE`):**
`fd_set` is a fixed-size bitmask, typically 1024 bits — monitoring more than 1024 FDs requires recompiling the kernel or the application with a larger `FD_SETSIZE`. In practice, a server handling thousands of concurrent connections immediately hits this wall. This is a hard architectural limit, not a tunable.

**Limitation 2 — O(nfds) kernel scan on every call:**
The kernel scans all `nfds` bits in the bitmask to find monitored FDs, regardless of how many are ready. With 10,000 FDs monitored but only 10 active, the kernel scans 10,000 bits every time. The work is proportional to the number of monitored FDs, not the number of active ones.

**Limitation 3 — O(n) scan by the application after the call:**
After `select()` returns, the application must iterate all FDs and call `FD_ISSET()` on each to find which ones are ready — another O(nfds) scan. Combined with the kernel scan, every `select()` cycle costs O(nfds) in both kernel and user space.

**Limitation 4 — The fd_set is consumed (modified in place):**
`select()` overwrites the input `fd_set` with the output (ready FDs only). The application must rebuild the entire set before every call — an O(n) operation. This means the kernel and application re-register every FD on every call, even if the set of monitored FDs hasn't changed.

**Limitation 5 — Copying fd_sets across the kernel boundary:**
The bitmask is copied from userspace to kernel on every call and back again — proportional to `nfds / 8` bytes. For 1024 FDs, that's 128 bytes per call — small but multiplied by thousands of calls per second it accumulates.

## Section 3: `poll()` — The Incremental Improvement

**Q6. How does `poll()` improve on `select()`, and what limitations does it retain?**
A: `poll()` replaces `select()`'s fixed-size bitmask with a dynamically allocated array of `pollfd` structures, one per monitored FD:

```c
#include <poll.h>

struct pollfd {
    int   fd;        // file descriptor to monitor
    short events;    // events to watch for (POLLIN, POLLOUT, POLLERR, POLLHUP)
    short revents;   // events that actually occurred (filled by kernel on return)
};

int poll(
    struct pollfd *fds,  // array of pollfd structs
    nfds_t nfds,         // number of entries in the array
    int timeout          // milliseconds; -1 = block forever; 0 = return immediately
);

// Usage
struct pollfd fds[2];
fds[0].fd = sock1; fds[0].events = POLLIN;
fds[1].fd = sock2; fds[1].events = POLLIN | POLLOUT;

int ready = poll(fds, 2, -1);
if (fds[0].revents & POLLIN) { /* sock1 readable */ }
if (fds[1].revents & POLLOUT) { /* sock2 writable */ }
```

**Improvement over `select()`:**
- No `FD_SETSIZE` limit — the array can be as large as the process's open FD limit (`ulimit -n`, typically 1,048,576 on modern Linux).
- Separate `events` (input) and `revents` (output) fields — the application doesn't need to rebuild the array before each call; only `revents` is modified by the kernel.
- Richer event types — `POLLRDHUP` (remote peer closed), `POLLPRI` (urgent data), `POLLNVAL` (invalid FD).

**Retained limitations:**
- **O(nfds) kernel scan on every call:** The kernel still iterates the entire array to register interest, check readiness, and write back results. For 10,000 FDs with 10 active, 9,990 iterations are wasted per call.
- **O(n) application scan:** The application still iterates all `nfds` entries to check `revents` — another O(n) pass.
- **Full array copied across kernel boundary on every call:** Unlike `select()`'s bitmask, the `pollfd` array is copied from userspace to kernelspace on every `poll()` call and back again — proportional to `nfds * sizeof(struct pollfd)` (8 bytes per FD). For 10,000 FDs, that's 80 KB per call — significant at high call frequency.
- **Re-registration on every call:** Like `select()`, `poll()` is a one-shot call — all FD interest is re-registered on every call. The kernel builds no persistent data structure across calls.

The fundamental issue with both `select()` and `poll()` is the **O(n) per-call cost** — performance degrades linearly with the number of monitored FDs, not the number of active ones. For a server with 10,000 idle connections and 10 active ones, 99.9% of the work on each call is wasted scanning idle FDs.

## Section 4: `epoll()` — The Scalable Solution

**Q7. What is `epoll()`'s core design insight, and what are its three system calls?**
A: `epoll()`'s core insight is to separate registration from waiting. Instead of re-registering all FDs on every wait call, `epoll()` maintains a persistent kernel-side data structure (a red-black tree indexed by FD) that holds the set of monitored FDs. The application registers FDs once; the kernel retains the registration across multiple wait calls. On wakeup, only the ready FDs are returned — not the full monitored set.

Three system calls:

**`epoll_create1(flags)`** — creates the epoll instance; returns an FD representing the kernel data structure:
```c
int epfd = epoll_create1(EPOLL_CLOEXEC);
// Returns an FD for the epoll instance; EPOLL_CLOEXEC closes it on exec()
```

**`epoll_ctl(epfd, op, fd, event)`** — modifies the monitored set (add, modify, remove):
```c
struct epoll_event ev;
ev.events = EPOLLIN;          // watch for readability
ev.data.fd = sock;            // user data returned with the event

epoll_ctl(epfd, EPOLL_CTL_ADD, sock, &ev);  // register sock
epoll_ctl(epfd, EPOLL_CTL_MOD, sock, &ev);  // change events for sock
epoll_ctl(epfd, EPOLL_CTL_DEL, sock, NULL); // unregister sock
```

**`epoll_wait(epfd, events, maxevents, timeout)`** — wait for events; returns only ready FDs:
```c
struct epoll_event events[MAX_EVENTS];
int n = epoll_wait(epfd, events, MAX_EVENTS, -1); // block until ready
for (int i = 0; i < n; i++) {
    if (events[i].events & EPOLLIN) {
        int fd = events[i].data.fd; // only ready FDs are in this array
        read(fd, buf, sizeof(buf));
    }
}
```

The `epoll_wait()` return array contains only the ready FDs — if 10 of 10,000 FDs are ready, `n = 10` and the array has 10 entries. The application does O(n_ready) work, not O(n_total) — a fundamental change from `select()`/`poll()`.

**Q8. How does `epoll()` achieve O(1) scalability, and what data structures does the kernel use internally?**
A: `epoll()`'s O(1) scalability comes from two kernel-side data structures:

**Red-black tree (for the monitored set):** The kernel maintains a red-black tree of all registered FDs keyed by FD number. `epoll_ctl(ADD)` inserts into the tree in O(log n). `epoll_ctl(DEL)` removes in O(log n). The tree exists persistently in kernel memory — no re-registration on every `epoll_wait()` call.

**Ready list (for notification):** Each socket/pipe/device maintains a wait queue of processes/threads sleeping on it. When data arrives on a socket, the kernel's network stack calls the socket's wakeup function, which walks the socket's wait queue and finds the epoll instance registered there. The kernel adds the FD to the epoll instance's **ready list** — a linked list of FDs that have become ready since the last `epoll_wait()` call. The ready list is maintained in the kernel at interrupt time, with no scanning.

**`epoll_wait()` operation:**
1. If the ready list is non-empty: copy the ready events to userspace, clear (or retain for LT) the ready list entries, return immediately.
2. If the ready list is empty: add the calling thread to the epoll instance's wait queue and sleep. When any monitored FD becomes ready, the interrupt handler adds it to the ready list and wakes the sleeping thread.

The cost breakdown:
- `epoll_ctl(ADD)`: O(log n) — one tree insertion.
- `epoll_wait()`: O(n_ready) — copy only the ready events to userspace. No scan of inactive FDs.
- Kernel notification path (interrupt): O(1) — the epoll instance is directly in the socket's wait queue; the kernel doesn't search for it.

Compared to `select()`/`poll()` where `epoll_wait()` equivalent is O(n_total) on every call, `epoll()` is O(n_ready) per call — identical cost whether you monitor 100 FDs or 100,000 FDs, as long as the number of simultaneously ready FDs is small.

**Q9. What is the `epoll_event` union's `data` field, and how is it used to avoid an FD lookup?**
A: When registering an FD with `epoll_ctl()`, the `epoll_event.data` field is a union that stores application-defined data associated with the FD — returned verbatim in the `epoll_wait()` result alongside the event flags:

```c
union epoll_data {
    void    *ptr;   // pointer to application data (e.g., connection struct)
    int      fd;    // the FD itself
    uint32_t u32;
    uint64_t u64;
};
```

Common usage: store a pointer to the connection context struct directly in `data.ptr`. When `epoll_wait()` returns a ready event, the application has the connection struct immediately — no hash table lookup or array index required:

```c
// At registration
struct Connection *conn = allocate_connection(sock);
conn->fd = sock;

struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET;
ev.data.ptr = conn;  // store pointer to connection struct
epoll_ctl(epfd, EPOLL_CTL_ADD, sock, &ev);

// At epoll_wait() time
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int i = 0; i < n; i++) {
    struct Connection *conn = events[i].data.ptr; // O(1) — no lookup
    handle_connection(conn);
}
```

This design means the critical hot path — handling a ready event — touches no hash tables, no global arrays, and no secondary lookups. The kernel delivers exactly the context the application needs directly in the event.

## Section 5: How Node.js Uses `epoll`

**Q10. What is libuv, and how does it sit between Node.js and `epoll`?**
A: libuv is the cross-platform asynchronous I/O library that Node.js uses as its event loop and I/O backend. It abstracts platform differences — `epoll` on Linux, `kqueue` on macOS/BSD, `IOCP` (I/O Completion Ports) on Windows — behind a unified API. Node.js itself does not call `epoll_wait()` directly; the V8 engine executes JavaScript, and libuv handles all I/O. The relationship:

```
Node.js JavaScript (user code)
        ↓
  V8 (JavaScript engine — executes JS, calls C++ bindings)
        ↓
  Node.js C++ bindings (net, fs, crypto, http modules)
        ↓
  libuv (event loop, thread pool, timer management)
        ↓  (on Linux)
  epoll_create1 / epoll_ctl / epoll_wait
        ↓
  Linux kernel (network stack, file system, VFS)
```

libuv's event loop is a single infinite loop that calls `epoll_wait()` (with a computed timeout) on each iteration, processes the ready events, runs JavaScript callbacks, then calls `epoll_wait()` again. The JavaScript code never blocks the event loop — every async operation registers an FD or a callback with libuv and returns immediately.

**Q11. Walk through the exact sequence of what happens when a Node.js HTTP server receives a request.**
A: Step by step, from the kernel level up:

**Step 1 — Server socket creation:**
`net.createServer()` calls the OS to create a TCP socket (`socket(AF_INET, SOCK_STREAM, 0)`), bind it to a port (`bind()`), and mark it as passive (`listen()`). The listening socket FD is registered with epoll via `epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, {EPOLLIN})`.

**Step 2 — Event loop iteration (waiting):**
libuv calls `epoll_wait(epfd, events, MAX_EVENTS, timeout_ms)`. The calling thread (Node.js's main thread) sleeps in the kernel. Zero CPU consumed.

**Step 3 — Client connects:**
A client sends a SYN packet. The kernel's TCP stack completes the three-way handshake and places the new connection in the listening socket's accept queue. The listening socket becomes readable (a connection is pending). The kernel adds the listening socket FD to epoll's ready list and wakes the sleeping thread.

**Step 4 — `epoll_wait()` returns:**
`epoll_wait()` returns with `n = 1` and `events[0].data.fd = listen_fd`. libuv's event loop sees the listening socket is readable.

**Step 5 — `accept()`:**
libuv calls `accept(listen_fd, ...)` to accept the new connection — returns a new FD for the connected socket. This new FD is registered with epoll: `epoll_ctl(epfd, EPOLL_CTL_ADD, conn_fd, {EPOLLIN | EPOLLRDHUP | EPOLLET})`.

**Step 6 — JavaScript callback — `'connection'` event:**
libuv calls the C++ binding, which creates a Node.js `Socket` object and emits the `'connection'` event. The user's JavaScript callback runs (`server.on('connection', (socket) => { ... })`). This JavaScript executes synchronously — no `epoll_wait()` during JS execution.

**Step 7 — Data arrives:**
The client sends the HTTP request. The kernel's TCP stack receives the packets, assembles them, and adds the data to the socket's receive buffer. The socket FD becomes readable. The kernel adds it to epoll's ready list.

**Step 8 — Next `epoll_wait()` iteration:**
After the JavaScript callback returns (or after all pending microtasks drain), libuv calls `epoll_wait()` again. It returns with the connected socket's FD ready.

**Step 9 — `read()`:**
libuv calls `read(conn_fd, buf, ...)`, which copies data from the kernel's receive buffer to userspace. In edge-triggered mode, libuv reads in a loop until `EAGAIN` (no more data).

**Step 10 — JavaScript `'data'` event:**
libuv calls the C++ http_parser binding, which parses the HTTP request and emits the `'data'` and `'end'` events. The user's request handler runs.

**Q12. What is the libuv thread pool, and why is it needed alongside `epoll`?**
A: `epoll` works for I/O on sockets, pipes, timers, and other FDs that the kernel can monitor asynchronously. But some operations cannot be made non-blocking by the kernel:

**Regular file I/O:** Despite the filesystem VFS layer, `read()` on a regular file can block waiting for disk I/O even with `O_NONBLOCK` set. The POSIX spec allows regular files to always be "ready" — `epoll` reports them as always readable, but the actual `read()` blocks. Linux's `io_uring` (kernel 5.1+) genuinely supports async disk I/O, but libuv uses thread pool for compatibility.

**DNS resolution:** `getaddrinfo()` (the standard DNS lookup function) is synchronous and blocking — it can block for hundreds of milliseconds waiting for a DNS response. There is no standard non-blocking `getaddrinfo()` in POSIX (Linux's `c-ares` library provides one; Node.js uses c-ares for `dns.resolve()` which is genuinely async, but `dns.lookup()` uses the thread pool).

**CPU-intensive native modules:** Some C++ add-ons (compression, cryptographic operations, image processing) do CPU-bound work that would block the event loop if run synchronously.

libuv's thread pool (default: 4 threads, configurable via `UV_THREADPOOL_SIZE`) handles these operations. When Node.js calls `fs.readFile()`, libuv posts a work item to the thread pool. A worker thread calls the blocking `read()` system call. When the read completes, the worker signals the event loop thread (via a `eventfd` or pipe registered with epoll) and posts the completion callback to the event loop's queue. The callback runs in the next event loop iteration — back on the main thread, serialised, safe.

```
Main thread (event loop):          Thread pool:
  fs.readFile('data.csv', cb)  →   worker: open('data.csv')
  epoll_wait() → sleeps            worker: read() → blocks on disk
  ← eventfd becomes readable       worker: read completes
  epoll_wait() returns             worker: signals eventfd
  cb(null, data) ← runs on main
```

**Q13. How does libuv compute the timeout to pass to `epoll_wait()`?**
A: libuv computes the `epoll_wait()` timeout as the time until the next pending timer fires. Before each `epoll_wait()` call, libuv checks its timer heap (a min-heap ordered by expiry time) for the earliest-expiring timer. The timeout is `max(0, earliest_timer_expiry - now)`:

- If there are no pending timers and no I/O events pending: timeout = -1 (block indefinitely until I/O).
- If a timer fires in 50ms: timeout = 50 (block for at most 50ms).
- If a timer has already expired: timeout = 0 (return immediately from `epoll_wait()`, process ready I/O, then handle the expired timer).

After `epoll_wait()` returns (either on I/O readiness or timeout), libuv:
1. Runs all expired timers (`setTimeout`, `setInterval` callbacks).
2. Runs all pending I/O callbacks (network data, connection events).
3. Runs `setImmediate` callbacks.
4. Runs `process.nextTick` and resolved Promise microtasks (these run between every phase, not just here).
5. Computes the next timeout and calls `epoll_wait()` again.

This is the event loop tick. The `epoll_wait()` call is the only point where the main thread sleeps — everything else is synchronous JavaScript execution.

**Q14. How does Node.js handle multiple simultaneous I/O completions — does `epoll_wait()` return them all at once?**
A: Yes — `epoll_wait()` returns up to `maxevents` ready FDs in a single call, in an array. libuv processes all of them before calling `epoll_wait()` again:

```c
// libuv's event loop core (simplified)
while (loop_alive) {
    // Phase 1: Run expired timers
    uv__run_timers(loop);

    // Phase 2: epoll_wait — returns all currently ready FDs
    int nevents = epoll_wait(epfd, events, ARRAY_SIZE(events), timeout);
    for (int i = 0; i < nevents; i++) {
        uv__io_t *handle = events[i].data.ptr;
        handle->cb(loop, handle, events[i].events); // dispatch per-FD callback
    }

    // Phase 3: Run check handles (setImmediate)
    uv__run_check(loop);
}
```

If 500 sockets all become readable simultaneously (e.g., a broadcast triggers many responses at once), `epoll_wait()` returns all 500 in one call (subject to the `maxevents` limit — libuv uses 1024). libuv processes all 500 callbacks synchronously before the next `epoll_wait()`. This batch processing is more efficient than waking up 500 times — fewer kernel/userspace transitions.

The implication for Node.js: if 500 request handlers all complete simultaneously and enqueue callbacks, they all run in one event loop iteration. Long-running JavaScript in any one callback delays all others — the event loop is single-threaded and cooperative. This is why CPU-intensive work blocks all other I/O callbacks — `epoll_wait()` doesn't return until the current JavaScript execution completes.

## Section 6: Edge Cases and Advanced Behaviour

**Q15. What is the "thundering herd" problem with `epoll`, and how is it mitigated?**
A: The thundering herd problem occurs when a single event wakes many sleeping processes or threads simultaneously, causing them all to compete for the same resource — most will fail and go back to sleep, wasting CPU. With `epoll`, the classic case: multiple processes share an `epoll` FD (via `fork()`) and all call `epoll_wait()`. When a connection arrives on the listening socket, all processes are woken simultaneously. Only one can `accept()` the connection; the others return `EAGAIN` and go back to sleep.

**Linux mitigations:**

**`EPOLLEXCLUSIVE` (Linux 4.5+):** When added to `epoll_ctl()`, only one epoll waiter is woken per ready event, rather than all of them. This directly solves the thundering herd for multiple processes sharing an epoll FD:
```c
ev.events = EPOLLIN | EPOLLEXCLUSIVE;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
```

**`SO_REUSEPORT` (Linux 3.9+):** Multiple processes each create their own listening socket on the same port. The kernel's TCP stack distributes incoming connections across all sockets (load balancing in the kernel). Each process's epoll only wakes for its own connections — no shared listening socket, no thundering herd. Node.js cluster mode uses this in combination with its own connection distribution.

**Node.js cluster module:** Node.js cluster uses a different approach — the master process calls `accept()` and distributes accepted connections to worker processes via IPC (sending the connected socket FD). Only the master wakes on the listening socket; workers wake only when explicitly given a connection. This avoids the thundering herd at the cost of a round-trip through the master.

**Q16. What happens to an `epoll` registration when a file descriptor is duplicated with `dup()` or `dup2()`?**
A: `epoll` registrations are tied to the underlying **open file description** (the kernel-level struct), not to the file descriptor number (the userspace index). When you `dup()` an FD, the new FD shares the same open file description as the original. If the original FD is registered with epoll, the duplicate is automatically monitored too — the kernel watches the underlying file description, and both FDs trigger the same epoll event when ready.

The subtlety: calling `epoll_ctl(EPOLL_CTL_DEL, original_fd)` removes the registration from the epoll set, but only if the original FD's open file description has no other references. If `dup_fd` still references the same open file description, the registration persists and events continue to fire. This is a known footgun: closing `original_fd` does not unregister it from epoll if `dup_fd` is still open. The correct pattern is to call `EPOLL_CTL_DEL` before closing, or to close all duplicated FDs and let the reference count drop to zero.

This also explains a bug pattern in multiprocess servers: `fork()` duplicates all FDs. The child's copies of the parent's sockets all share the same open file descriptions. If the child calls `epoll_ctl(ADD)` on its inherited FDs, it's adding the same open file descriptions the parent monitors — events fire in both parent's and child's epoll instances.

**Q17. What is `io_uring`, and how does it compare to `epoll` for modern high-performance I/O?**
A: `io_uring` (Linux 5.1+, 2019) is a fundamentally different I/O model that eliminates the system call overhead per I/O operation by using a pair of shared-memory ring buffers between userspace and the kernel:

- **Submission Queue (SQ):** Userspace writes I/O requests (read, write, accept, send, recv) into the SQ ring buffer.
- **Completion Queue (CQ):** The kernel writes completed I/O results into the CQ ring buffer.

In `io_uring`'s `SQPOLL` mode, a kernel thread continuously polls the SQ and processes new requests — zero system calls for submitting I/O. Completions are read from CQ with zero system calls. For high-frequency I/O (millions of small operations per second), `io_uring` eliminates the `epoll_wait()` → `read()` → `epoll_ctl()` round trip entirely.

| Dimension                  | `epoll` + read()                            | `io_uring`                                   |
|----------------------------|---------------------------------------------|----------------------------------------------|
| System calls per operation | 2–3 (`epoll_wait`, `read`/`write`, `epoll_ctl`) | 0 (SQPOLL mode) or 1 (`io_uring_enter`)     |
| Regular file async I/O     | No — thread pool required                  | Yes — genuinely async disk I/O               |
| Kernel version             | 2.5.44 (2002)                               | 5.1+ (2019)                                  |
| Complexity                 | Low                                         | Higher — ring buffer management              |
| Node.js support            | Default (via libuv)                         | Experimental libuv backend (in progress)     |
| Best for                   | General async network I/O                   | Ultra-high-frequency I/O, disk I/O, batching |

libuv has experimental `io_uring` support in development. For most Node.js applications today, `epoll` via libuv remains the default and is sufficient for network I/O. `io_uring` becomes relevant for disk-intensive workloads (database engines, file servers) where the thread pool overhead is measurable.

## Section 7: Practical Implications for Node.js Engineers

**Q18. What causes the Node.js event loop to "block," and what does that mean at the `epoll` level?**
A: The event loop blocks when JavaScript code on the main thread runs for a long time without returning. At the `epoll` level: `epoll_wait()` has returned (I/O is ready), but libuv cannot call `epoll_wait()` again until all JavaScript callbacks from the current iteration complete. During this time, new network data is accumulating in kernel socket buffers, new connections are pending in the listen queue, and timers are expiring — but none of their callbacks can run.

The kernel continues receiving and buffering network data (bounded by `SO_RCVBUF`, typically 87 KB per socket). TCP's flow control (the receive window) eventually signals the sender to slow down if the application doesn't read fast enough. For Node.js servers, a blocked event loop means:
- Existing connections time out waiting for responses.
- New connections accumulate in the listen backlog (bounded by `listen(fd, backlog)`, typically 128 or 511).
- Timer callbacks fire late — `setTimeout(fn, 100)` may execute at 100ms + blocking_duration.

Diagnosis: `process.hrtime()` before and after suspected blocking code, Node.js's `--perf-basic-prof` flag with flame graph analysis, `clinic.js doctor` (detects event loop lag via a "canary" timer that should fire every ~100ms). The standard Node.js event loop lag metric: fire a `setTimeout(fn, 0)` at the start of a request, measure how long until it actually fires — lag above 10ms indicates blocking.

**Q19. How does `process.nextTick()` relate to the `epoll` event loop, and why does it have the highest priority?**
A: `process.nextTick()` callbacks run after the currently executing JavaScript completes but before `epoll_wait()` is called again — before any I/O callbacks, before timers, before `setImmediate`. libuv implements this by draining the `nextTick` queue (and the microtask queue — resolved Promises) between every phase of the event loop:

```
JavaScript executes synchronously
  → nextTick queue drains (all nextTick callbacks)
  → microtask queue drains (all resolved Promise .then callbacks)
  → back to event loop
     → timers phase (setTimeout, setInterval callbacks)
     → nextTick + microtasks drain
     → pending callbacks phase (I/O error callbacks)
     → nextTick + microtasks drain
     → idle/prepare phase (internal)
     → poll phase: epoll_wait()  ← THE ONLY PLACE NODE.JS SLEEPS
     → nextTick + microtasks drain
     → check phase: setImmediate callbacks
     → nextTick + microtasks drain
     → close callbacks phase
     → loop back to timers
```

The implication of `nextTick`'s priority: a recursive `process.nextTick()` — a callback that schedules another `nextTick` — starves all I/O and timer callbacks indefinitely. `epoll_wait()` is never reached; the event loop is stuck draining the `nextTick` queue. This is why recursive `nextTick` is a severe anti-pattern. `setImmediate` does not have this problem — it runs in the check phase after `epoll_wait()`, so I/O has a chance to be processed between iterations.

**Q20. What does `--max-old-space-size` have to do with `epoll`, and how does GC interact with the event loop?**
A: V8's garbage collector runs on the main thread (for stop-the-world phases) and interrupts JavaScript execution. During a major GC pause, the event loop is frozen: `epoll_wait()` is not called, I/O callbacks don't fire, timers don't run. From the kernel's perspective, the process is running (CPU is consumed by GC), but no `epoll_wait()` system call is issued. Network data accumulates in kernel buffers; timers expire silently.

When `--max-old-space-size` is set too low relative to actual heap usage, GC runs frequently and the pauses are long. When set too high, GC runs infrequently but each pause is very long (scanning a large heap). The sweet spot is headroom above the live heap size without excessive waste.

The `epoll` connection: after a major GC pause of, say, 500ms, `epoll_wait()` returns with a burst of ready FDs — all the sockets that received data during the pause. libuv processes them all at once. If 1,000 connections each sent a request during the GC pause, 1,000 callbacks fire in rapid succession, causing a latency spike for all of them. This is visible as periodic latency spikes correlated with GC events — diagnosable by correlating V8's `--trace-gc` output with p99 latency spikes.

## Section 8: Scenario / System Design Style Questions

**Q21. "You're building a high-throughput WebSocket server in Node.js. At 50,000 concurrent connections, CPU usage is high but actual message throughput is low. Walk through the epoll-level diagnosis."**
A: High CPU with low throughput on a WebSocket server is a sign that the event loop is spending its time on overhead rather than actual work. Diagnosis from the `epoll` level up:

**Step 1 — Measure where the CPU is spent:**
```bash
# System call profile — what fraction of time is in kernel vs userspace?
strace -c -p $(pgrep node)    # system call count and time (attach to running process)
perf stat -p $(pgrep node)    # hardware counters: IPC, cache misses, branch mispredictions
```

**Step 2 — Check `epoll_wait()` call frequency:**
```bash
strace -e trace=epoll_wait -p $(pgrep node) 2>&1 | head -100
```
If `epoll_wait()` is returning immediately (timeout=0) in a tight loop with very few ready FDs, the event loop is spinning on empty — possibly due to an `eventfd` being continuously signalled by the thread pool, or a `setImmediate`/`nextTick` loop generating artificial "work."

**Step 3 — Check per-connection overhead:**
50,000 connections × `epoll_ctl()` calls on state changes = high kernel entry rate. Profile with `perf top` — if `sys_epoll_ctl` appears high, the server is frequently adding/removing/modifying FD registrations. Switching from level-triggered to edge-triggered (`EPOLLET`) with `EPOLLONESHOT` reduces `epoll_ctl()` calls — re-arm only after processing rather than on every data arrival.

**Step 4 — Check message parsing overhead:**
WebSocket frames require per-message parsing and masking/unmasking. If messages are very small (many tiny frames) and frequent, the parsing overhead dominates. Profile V8 with `--prof` and `node --prof-process` to find the hot JavaScript functions. If the WebSocket library is pure JavaScript, switching to a native C++ WebSocket library (uWebSockets.js) moves parsing out of V8 into native code — significantly reducing CPU per message.

**Step 5 — Check for event loop blocking:**
```javascript
// Instrument event loop lag
let lastCheck = Date.now();
setInterval(() => {
    const lag = Date.now() - lastCheck - 1000;
    if (lag > 50) console.warn(`Event loop lag: ${lag}ms`);
    lastCheck = Date.now();
}, 1000);
```
Any lag above 10–20ms indicates blocking callbacks. Find them with `clinic.js flame`.

**Q22. "A junior developer suggests using `setInterval(checkForUpdates, 100)` to poll a Redis key every 100ms for changes in a Node.js service. Explain what this does to the event loop and `epoll`, and propose a better alternative."**
A: The `setInterval` polling approach has two problems at the event loop level:

**Problem 1 — Unnecessary `epoll_wait()` wakeups:**
`setInterval(fn, 100)` causes libuv to set `epoll_wait()`'s timeout to at most 100ms on every iteration. Even if no network I/O is pending, the event loop wakes up 10 times per second purely to fire the timer callback. Each wakeup incurs the overhead of a kernel return, timer processing, and a Redis command (which itself involves an FD registration, a write syscall, an `epoll_wait()` for the response, and a read syscall). At 10 polls/second with a 1ms Redis RTT, you consume 1% of the event loop's time just for polling — even when no updates exist.

**Problem 2 — Latency bounded by polling interval:**
An update that arrives 1ms after a poll will not be detected for 99ms. For a fintech service where a loan status change must propagate quickly (e.g., trigger a notification), 99ms latency is avoidable.

**Better alternatives:**

**Redis Pub/Sub (push, not poll):**
```typescript
const subscriber = new Redis();
subscriber.subscribe('loan-status-updates');
subscriber.on('message', (channel, loanId) => {
  // Notified immediately — epoll_wait returns when the Redis connection receives data
  handleStatusChange(loanId);
});
```
The Redis connection's FD is registered with epoll. When the Redis server sends a Pub/Sub message, the kernel wakes `epoll_wait()` immediately — zero polling overhead, zero latency beyond network RTT.

**Redis `WAIT` command or keyspace notifications:**
Enable keyspace notifications (`CONFIG SET notify-keyspace-events KEA`) and subscribe to specific key changes. Notification arrives at the exact moment the key changes.

**BullMQ / Kafka for durable event delivery:**
If the update must survive restarts or needs guaranteed delivery, use a message queue. The queue consumer's connection FD is epoll-monitored; new messages wake the event loop immediately.

The epoll insight: polling converts a push model (event-driven) into a pull model (timer-driven), defeating the purpose of `epoll`. Every `setInterval` that performs I/O is an unnecessary `epoll_wait()` wakeup. Prefer push-based notification via Pub/Sub, SSE, WebSockets, or message queues.

**Q23. "Your Node.js API service processes 100,000 requests/second and calls `fs.readFile()` for each request to read a configuration file. CPU is pegged on the thread pool. How do you fix this, and what does the fix do at the libuv/epoll level?"**
A: `fs.readFile()` offloads disk reads to libuv's thread pool (4 threads by default). At 100,000 RPS, 100,000 thread pool tasks per second are enqueued. The thread pool has 4 workers — each `readFile()` queues behind the others. The thread pool's queue grows unbounded; `fs.readFile()` callbacks run with increasing delay. CPU is consumed by context switching between the 4 worker threads and the main thread.

**Fix 1 — Cache the file in memory (eliminates thread pool entirely):**
```typescript
// Read once at startup; serve from memory on every request
let configCache: Config | null = null;

async function getConfig(): Promise<Config> {
  if (configCache) return configCache;
  const raw = await fs.promises.readFile('config.json', 'utf-8');
  configCache = JSON.parse(raw);
  return configCache;
}
```

At the libuv level: exactly one `fs.readFile()` → one thread pool task → one `eventfd` wakeup of the event loop. All subsequent requests are served without any thread pool involvement, no system calls, and no `epoll_wait()` wakeup — pure in-memory data access.

**Fix 2 — Use `fs.watch()` to invalidate the cache on file change:**
```typescript
fs.watch('config.json', () => {
  configCache = null; // invalidate on change — next request re-reads
});
```
`fs.watch()` uses `inotify` (Linux) — an `inotify_add_watch()` call that registers the file with the inotify subsystem. The inotify FD is registered with `epoll` (libuv does this internally). When the file changes, the kernel writes an event to the inotify FD, `epoll_wait()` returns with the inotify FD ready, libuv reads the event, and fires the `fs.watch()` callback. Zero polling, zero thread pool, immediate notification.

**Fix 3 — If the config must be freshly read on every request (external mutation):**
Increase `UV_THREADPOOL_SIZE` (`UV_THREADPOOL_SIZE=16 node server.js`) — more workers reduce the queue depth. But this is a stopgap; the correct fix is caching with invalidation.

At the epoll level, the cache fix eliminates the entire `fs.readFile()` → thread pool → `eventfd` → `epoll_wait()` → callback chain per request. The event loop is free to process network I/O (the actual work) without being interrupted 100,000 times per second by file read completions.

## Quick Reference: `select()` vs `poll()` vs `epoll()`

| Dimension                        | `select()`                        | `poll()`                          | `epoll()`                               |
|----------------------------------|-----------------------------------|-----------------------------------|-----------------------------------------|
| FD limit                         | 1024 (`FD_SETSIZE`)               | Unlimited (dynamic array)         | Unlimited (kernel red-black tree)       |
| Data structure                   | Fixed bitmask (`fd_set`)          | Array of `pollfd` structs         | Kernel-side red-black tree + ready list |
| Registration model               | One-shot — re-register every call | One-shot — re-register every call | Persistent — register once with `epoll_ctl` |
| Kernel scan on wait              | O(nfds) — all monitored FDs      | O(nfds) — all monitored FDs      | O(1) — kernel maintains ready list     |
| App scan after wait              | O(nfds) — check `FD_ISSET` each  | O(nfds) — check `revents` each   | O(n_ready) — only ready FDs returned   |
| Data copied to kernel per call   | bitmask (nfds/8 bytes)            | Full pollfd array (8×nfds bytes)  | Nothing — registration is persistent   |
| Trigger mode                     | Level-triggered only              | Level-triggered only              | Level-triggered (default) or edge-triggered (`EPOLLET`) |
| User data with event             | No                                | No                                | Yes — `epoll_event.data` union (ptr, fd, u64) |
| Timeout granularity              | Microseconds (`struct timeval`)   | Milliseconds (`int`)              | Milliseconds (`int`); nanoseconds via `epoll_pwait2` |
| Scalability                      | O(n) — unusable above ~1000 FDs  | O(n) — unusable above ~10,000 FDs | O(1) per call — scales to millions of FDs |
| Platform                         | POSIX universal                   | POSIX universal                   | Linux only                              |
| macOS/BSD equivalent             | `kqueue`                          | `kqueue`                          | `kqueue`                                |
| Windows equivalent               | `select()` (WinSock)              | `WSAPoll()`                       | IOCP (I/O Completion Ports)             |
| Node.js/libuv usage              | Not used                          | Not used                          | Primary I/O notification mechanism      |
| Introduced in kernel             | BSD 4.2 (1983)                    | SVR3 (1986)                       | Linux 2.5.44 (2002)                     |
