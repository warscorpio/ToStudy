# Operating Systems / Computer Science: File System Internals — Inodes, File Descriptors, `open()`, `read()`, `write()` Syscalls — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a file system, and what three problems does it solve?**
A: A file system is the OS subsystem responsible for organizing, storing, and retrieving data on persistent storage. Without it, a disk is a flat array of blocks with no structure. A file system solves three distinct problems:

- **Naming** — associating human-readable names with data locations. Users think in terms of `/home/alice/report.pdf`; the file system maps that path to a specific set of disk blocks.
- **Organization** — structuring the namespace into directories, supporting hierarchical paths, links, and permissions. The file system maintains the directory tree and enforces access control.
- **Space management** — tracking which disk blocks are free and which are in use, allocating blocks to files as they grow, and reclaiming blocks when files are deleted. Without this, writing a file would require knowing exactly which blocks are free — a task no application should handle.

At the interface level, a file system presents a uniform abstraction ("everything is a file") that hides whether the underlying storage is a spinning disk, SSD, network share, or a tmpfs in RAM. This is why `/proc/cpuinfo`, `/dev/null`, and a regular `.txt` file all respond to the same `open()`/`read()`/`write()` syscalls.

**Q2. What is the difference between a file's name, its inode, and its data blocks?**
A: These are three distinct layers that together represent a file:

- **Name** — a string stored in a directory entry that maps a human-readable label to an inode number. The name exists only in the parent directory; the same inode can have multiple names (hard links). The name is the least fundamental thing about a file — renaming a file changes only the directory entry, nothing in the inode or data blocks.
- **Inode (index node)** — a fixed-size metadata record stored on disk that describes everything about a file *except its name and data*: owner, permissions, timestamps, size, file type, and — critically — the locations of the file's data blocks. Every file and directory has exactly one inode; each inode has a unique number within the file system.
- **Data blocks** — the actual disk blocks containing the file's contents. The inode points to these blocks (directly or indirectly via block pointer trees). Reading a file means: look up the inode, find the block addresses, read those blocks from disk.

The separation between name, inode, and data is foundational. It enables hard links (multiple names → same inode → same data), allows renaming to be atomic and O(1) (just update a directory entry), and allows the OS to cache metadata and data independently.

**Q3. What is the difference between a block device and a file system?**
A: A block device (disk, SSD, NVMe drive) is a raw storage medium — the kernel can read and write fixed-size blocks (typically 512 bytes or 4 KB) by block address. It has no concept of files, directories, or names; it is a flat, addressable array of blocks.

A file system is a software layer that imposes structure on the block device. The file system decides:
- Which blocks store inodes (the inode table).
- Which blocks store directory data.
- Which blocks store file data.
- Which blocks are free (tracked in a free-block bitmap or free list).
- How to journal or log changes to survive crashes (journaling file systems: ext4, NTFS, APFS, XFS).

The OS kernel contains a **Virtual File System (VFS)** layer — an abstraction that presents a uniform interface (`open`, `read`, `write`, `stat`) regardless of the underlying file system type. ext4, FAT32, NTFS, ZFS, NFS, and tmpfs all register with the VFS and implement its interface; applications never call ext4-specific code directly.

## Section 2: Inodes

**Q4. What fields does an inode contain?**
A: An inode is a fixed-size on-disk structure (128 or 256 bytes in ext4). Its fields:

```
Inode fields (ext4 as representative):
  Mode:            file type (regular, directory, symlink, device, socket, pipe)
                   + permission bits (owner/group/other × read/write/execute)
                   + setuid, setgid, sticky bits
  UID / GID:       numeric owner user ID and group ID
  Size:            file size in bytes
  Timestamps:
    atime          last access time (read)
    mtime          last modification time (data write)
    ctime          last status change time (inode write — metadata change)
    crtime         creation time (ext4 extension)
  Link count:      number of hard links (directory entries) pointing to this inode
  Block count:     number of 512-byte blocks allocated to this file
  Block pointers:  addresses of data blocks (structure described in Q5)
  Flags:           immutable, append-only, no-atime, extent-based, etc.
  Extended attrs:  pointer to extended attribute block (ACLs, SELinux labels, etc.)
```

Notably absent: **the file name**. Names live in directory entries, not inodes. This is why an inode can be referenced by multiple names (hard links) — the inode doesn't know or care what it's called.

**Q5. How does an inode locate a file's data blocks on disk?**
A: Traditional Unix file systems (ext2/ext3) use a **multi-level block pointer** scheme inside the inode:

```
Inode block pointer region (e.g., 15 pointers in ext2):
  Pointers 0–11:   Direct pointers — each points directly to a data block.
                   12 blocks × 4KB = 48KB addressable directly.

  Pointer 12:      Indirect pointer — points to a block of pointers.
                   1 block of pointers × (4KB/4B per pointer) = 1024 pointers
                   → 1024 × 4KB = 4MB additional.

  Pointer 13:      Double indirect — pointer → block of pointers → data blocks.
                   1024 × 1024 × 4KB = 4GB additional.

  Pointer 14:      Triple indirect — three levels of indirection.
                   1024³ × 4KB = 4TB additional.
```

**Modern approach — extents (ext4, XFS, APFS):** instead of storing individual block addresses, the inode stores **extent descriptors**: (starting block, length) pairs. A single extent descriptor covers a contiguous run of blocks. A file stored in one contiguous run needs only one extent — far more efficient than 1024 individual block pointers. Ext4 stores up to four extents directly in the inode; larger files use an extent tree.

```
Extent descriptor: { logical_block_start, physical_block_start, length }
Example: { 0, 12345, 100 } means logical blocks 0–99 are stored in physical blocks 12345–12444.
```

**Q6. What is the inode table, and how does the OS find a specific inode?**
A: The inode table is a fixed-size region of the disk, allocated when the file system is formatted (`mkfs`). In ext4, the disk is divided into **block groups** — each block group contains its own inode table, data block bitmap, inode bitmap, and data blocks. This locality keeps inode and data close on disk, reducing seek time.

Finding inode N:
```
block_group     = (N − 1) / inodes_per_group
inode_index     = (N − 1) % inodes_per_group
inode_table_block = block_group_descriptor[block_group].inode_table_start
disk_offset     = inode_table_block × block_size + inode_index × inode_size
```

The OS reads that disk offset to get the inode structure. In practice, frequently accessed inodes are cached in the **inode cache** (part of the page cache in Linux's `dentry`/`inode` cache), so this calculation triggers a disk read only on a cache miss.

**Q7. What is the difference between `atime`, `mtime`, and `ctime`?**
A: Three timestamps with distinct semantics:

- **`atime` (access time)** — updated whenever the file's *data* is read. Used by backup tools (which files have been accessed recently?), cache eviction, and tools like `find -atime`. Traditionally updated on every `read()`, which caused significant write I/O just for reads. Modern Linux mounts filesystems with `relatime` by default: `atime` is updated only if the current `atime` is older than `mtime` or `ctime`, or if `atime` is more than 24 hours old — dramatically reducing unnecessary writes.

- **`mtime` (modification time)** — updated whenever the file's *data* changes (via `write()` or `truncate()`). Does not update when metadata changes (permissions, owner). This is what `make`, `rsync`, and `git` use to detect file changes.

- **`ctime` (change time)** — updated whenever the inode changes: data writes (like `mtime`), *and* metadata changes (permission changes, ownership changes, hard link additions/removals, rename). `ctime` cannot be set by a user — only the kernel updates it. This is why `cp` and `touch` can preserve `mtime` but not `ctime`.

The key distinction: `mtime` tracks data changes; `ctime` tracks inode changes (a superset). `atime` tracks reads.

**Q8. What are hard links and symbolic links, and how do they differ at the inode level?**
A: Both create alternative ways to refer to a file, but they work at different layers:

**Hard link** — a directory entry that maps a new name to an *existing inode number*. Multiple directory entries point to the same inode. The inode's link count (stored in the inode itself) is incremented. The file is deleted from the file system only when the link count reaches zero *and* no process has the file open (the inode is freed only then).

```
Before: dirA/file.txt → inode 42 (link_count=1)
ln dirA/file.txt dirB/alias.txt
After:  dirA/file.txt → inode 42 (link_count=2)
        dirB/alias.txt → inode 42
rm dirA/file.txt → link_count becomes 1; inode 42 still exists
```

Constraints: hard links cannot cross file system boundaries (inode numbers are only unique within one file system); hard links to directories are forbidden in most Unix systems (to prevent directory cycles in the path graph).

**Symbolic link (symlink)** — a special file whose *data* is a path string pointing to another file or directory. The symlink has its own inode and its own data blocks (containing the target path). Following a symlink causes the OS to re-resolve the path from the target string. Symlinks can cross file system boundaries, point to directories, and point to non-existent targets (dangling symlinks). Deleting the target leaves the symlink dangling — it still exists with its own inode, but following it returns `ENOENT`.

```
ln -s /etc/nginx/nginx.conf myconfig     → inode 99 (type=symlink, data="/etc/nginx/nginx.conf")
```

**Q9. When is an inode freed, and what is the role of the link count and open file count?**
A: An inode is freed only when *both* of the following are true:
1. The link count (number of directory entries pointing to it) is zero.
2. The open file count (number of processes that have the file open) is zero.

This is why deleting a file that a running process has open does not immediately free the inode or disk blocks — the process continues to use the file through its file descriptor, and the data remains accessible until the last file descriptor referring to it is closed. Only then does the OS free the inode and return the blocks to the free pool.

```
Process has fd 3 → inode 42 (link_count=1, open_count=1)
rm file.txt       → link_count becomes 0, but open_count=1 → inode NOT freed
                  → file disappears from directory; no new process can open it by name
                  → existing process can still read/write via fd 3
process closes fd 3 → open_count becomes 0, link_count=0 → inode freed, blocks reclaimed
```

This behavior is exploited in practice: create a temp file, immediately `unlink()` it, use it via the file descriptor — it disappears from the directory but remains usable until the process exits, at which point it is automatically cleaned up.

## Section 3: File Descriptors

**Q10. What is a file descriptor?**
A: A file descriptor (fd) is a small non-negative integer — an index into the **per-process open file table** — that identifies an open file (or socket, pipe, device, or any other kernel I/O object) from the process's perspective. It is the process's handle to an open file; all subsequent I/O operations (`read`, `write`, `lseek`, `close`) take the fd as their first argument.

File descriptors 0, 1, and 2 are reserved by convention:
- **0** — standard input (stdin)
- **1** — standard output (stdout)
- **2** — standard error (stderr)

A process inherits its parent's file descriptors across `fork()` unless they are marked close-on-exec (`O_CLOEXEC` / `FD_CLOEXEC`). After `exec()`, all non-close-on-exec file descriptors remain open in the new program — a frequent source of fd leaks in setuid programs.

**Q11. What are the three tables that connect a file descriptor to on-disk data?**
A: Three levels of indirection connect a process's integer fd to the inode on disk:

```
Process A          Kernel                              Disk
fd table           Open File Table (system-wide)       Inode table
─────────          ─────────────────────────────────   ───────────
fd 0 ──────────→  OFT entry 0:                        inode 7
                    flags: O_RDONLY                    (stdin terminal)
                    offset: 0
                    inode ptr ───────────────────────→ inode 7

fd 3 ──────────→  OFT entry 5:                        inode 42
                    flags: O_RDWR                      (regular file)
                    offset: 1024
                    inode ptr ───────────────────────→ inode 42

fd 4 ──────────→  OFT entry 5  (same OFT entry!)
                  (fd 4 is a dup of fd 3 — same offset, same inode)

Process B
fd table
─────────
fd 3 ──────────→  OFT entry 9:                        inode 42
                    flags: O_RDONLY                    (same inode, different OFT entry)
                    offset: 0                          (independent offset from Process A)
                    inode ptr ───────────────────────→ inode 42
```

- **Per-process file descriptor table** — one per process; maps fd numbers to Open File Table entries. Stored in the `task_struct` (Linux). Small integers; limited by `RLIMIT_NOFILE` (default 1024 per process, configurable to millions system-wide).
- **Open File Table (OFT)** — one entry per open file description (system-wide). Contains: file offset (current read/write position), status flags (`O_RDONLY`, `O_WRONLY`, `O_NONBLOCK`, etc.), and a pointer to the inode. Multiple fds (from the same or different processes) can point to the same OFT entry — this is what `dup()`, `dup2()`, and `fork()` produce. Shared OFT entry = shared offset.
- **Inode table (v-node table)** — the in-memory inode cache. The inode contains permissions, size, block pointers — all the metadata. Multiple OFT entries can point to the same inode (different processes opening the same file independently get separate OFT entries but share one inode).

**Q12. What happens to file descriptors across `fork()` and `exec()`?**
A: These two cases have critically different behaviors:

**After `fork()`:** the child gets a copy of the parent's fd table — same fd numbers mapping to the same OFT entries. Parent and child share OFT entries, which means they share file offsets. A `read()` in the child advances the offset seen by the parent (and vice versa). This is intentional for pipes (the shell uses it for `|` pipelines) but is often surprising in other contexts. The inode's open count is incremented for each fd copy.

```c
int fd = open("file.txt", O_RDWR);
// fd → OFT entry 5 → inode 42

pid_t pid = fork();
// Parent: fd 3 → OFT entry 5 (offset shared)
// Child:  fd 3 → OFT entry 5 (same entry, shared offset)
// Read in child advances offset seen by parent
```

**After `exec()`:** file descriptors marked `O_CLOEXEC` (close-on-exec) are automatically closed when `exec()` replaces the process image. Descriptors without `O_CLOEXEC` remain open in the new program — the new program inherits them even if it doesn't know about them. This is how shells redirect stdin/stdout (open the file, `dup2()` it to fd 0 or 1, then `exec()` the child — the child's stdin/stdout are the file). Best practice: always open file descriptors with `O_CLOEXEC` unless you specifically need them to survive `exec()`.

**Q13. What is the difference between `dup()`, `dup2()`, and `dup3()`?**
A: All three create a new file descriptor that refers to the same Open File Table entry as an existing one — they alias the OFT entry, sharing offset and flags:

```c
int dup(int oldfd);
// Returns the lowest-numbered available fd that refers to the same OFT entry as oldfd.
// dup(1) → typically returns 3 (next available fd after 0,1,2)

int dup2(int oldfd, int newfd);
// Makes newfd refer to the same OFT entry as oldfd.
// If newfd is already open, closes it atomically before duplicating.
// Used by shells for redirection: dup2(file_fd, STDOUT_FILENO)
// The shell can then close file_fd; stdout now writes to the file.

int dup3(int oldfd, int newfd, int flags);
// Like dup2, but accepts flags. Currently O_CLOEXEC is the only valid flag.
// Atomic equivalent of dup2() + fcntl(newfd, F_SETFD, FD_CLOEXEC).
```

The key property of all three: the original and the duplicate fd share one OFT entry — same offset, same open flags. Writing 100 bytes via `oldfd` advances the offset seen by `newfd` by 100. This is the mechanism behind shell output redirection and pipe setup in `fork()`/`exec()` patterns.

## Section 4: The `open()` Syscall

**Q14. What does `open()` do, step by step?**
A: `open(pathname, flags, mode)` takes a path string and returns a file descriptor. The kernel steps:

```
1. Path resolution (namei / path walk):
   - Split pathname into components: "/home/alice/report.pdf" → ["home", "alice", "report.pdf"]
   - Start at the root inode (or cwd inode for relative paths)
   - For each component: look up the name in the current directory's data blocks,
     find the inode number, load that inode, check execute (search) permission
   - Handle symlinks: if a component is a symlink, re-resolve the target path
   - Final component: look up "report.pdf" in the "alice" directory → inode N

2. Permission check:
   - Check the inode's permission bits against the process's UID/GID and the requested flags
   - O_RDONLY → check read permission; O_WRONLY → write; O_RDWR → both
   - If permission denied → return EACCES

3. O_CREAT handling:
   - If O_CREAT and file doesn't exist: allocate a new inode, initialize it,
     add a directory entry in the parent directory
   - If O_CREAT | O_EXCL and file exists → return EEXIST (atomic check-and-create)

4. O_TRUNC handling:
   - If O_TRUNC and file exists and is writable: truncate data to zero bytes,
     free data blocks, update inode size to 0

5. Allocate an Open File Table entry:
   - Initialize: flags = requested flags, offset = 0 (or file size if O_APPEND)
   - Store pointer to inode (increment inode's reference count)

6. Allocate a file descriptor:
   - Find the lowest unused fd number in the process's fd table
   - Point it to the new OFT entry
   - Return the fd number to the caller
```

The entire operation is performed in kernel space — the user program supplies the path string and flags, and the kernel does all the disk I/O (read directory blocks, load inodes) and data structure manipulation.

**Q15. What are the most important `open()` flags, and what do they do?**
A:

```c
// Access mode (exactly one required):
O_RDONLY    // open for reading only
O_WRONLY    // open for writing only
O_RDWR      // open for reading and writing

// Creation flags:
O_CREAT     // create file if it doesn't exist (requires mode argument)
O_EXCL      // with O_CREAT: fail with EEXIST if file already exists (atomic)
O_TRUNC     // truncate file to zero length on open (file must be writable)

// Status flags:
O_APPEND    // before each write, set offset to end of file (atomic for single writes)
O_NONBLOCK  // open in non-blocking mode (for FIFOs, sockets, devices)
O_SYNC      // each write waits for data AND metadata to be flushed to hardware
O_DSYNC     // each write waits for data (not metadata) to be flushed
O_DIRECT    // bypass page cache; I/O goes directly to/from user buffer and disk

// Safety:
O_CLOEXEC   // close fd automatically on exec() — should be used by default
O_NOFOLLOW  // fail with ELOOP if final path component is a symlink (TOCTOU defense)
O_PATH      // open the path itself, not the file (for directory fd, /proc/self/fd tricks)
O_DIRECTORY // fail with ENOTDIR if path is not a directory
O_TMPFILE   // create an unnamed temporary inode (no directory entry) — auto-cleaned up
```

`O_CREAT | O_EXCL` together is the atomic test-and-create idiom — it's the safe way to create a lock file or ensure a file is created by exactly one of many competing processes. `O_APPEND` makes log file writes safe from multiple writers only for writes smaller than the pipe buffer (POSIX guarantees atomicity for writes ≤ `PIPE_BUF` to pipes; for regular files, O_APPEND is atomic only for the seek-to-end, not the write itself on all systems).

**Q16. What is the `mode` argument to `open()`, and when is it used?**
A: The `mode` argument specifies the permission bits for a newly created file (used only when `O_CREAT` is in the flags; ignored otherwise). It is a bitmask:

```c
S_IRUSR = 0400  // owner read
S_IWUSR = 0200  // owner write
S_IXUSR = 0100  // owner execute
S_IRGRP = 0040  // group read
S_IWGRP = 0020  // group write
S_IXGRP = 0010  // group execute
S_IROTH = 0004  // others read
S_IWOTH = 0002  // others write
S_IXOTH = 0001  // others execute

// Common: 0644 = rw-r--r-- (owner rw, group r, others r)
int fd = open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
```

The actual permissions applied are `mode & ~umask`. The process's `umask` (typically 022) masks out bits that should never be set by default — `mode=0666` with `umask=022` yields `0644` actual permissions. The umask is a per-process setting inherited from the parent (set in shell via `umask 022`).

**Q17. What error codes can `open()` return, and what causes each?**
A:

```
ENOENT      — file doesn't exist and O_CREAT not set; or a directory component doesn't exist
EACCES      — permission denied (read/write/execute check failed on file or directory component)
EEXIST      — O_CREAT | O_EXCL and file already exists
EISDIR      — tried to open a directory with O_WRONLY or O_RDWR
ENOTDIR     — a non-directory component in the path is not a directory; or O_DIRECTORY and path is a file
ELOOP       — too many symbolic links encountered (symlink cycle); or O_NOFOLLOW and final component is symlink
EMFILE      — process has too many open file descriptors (hit RLIMIT_NOFILE)
ENFILE      — system-wide open file limit reached
ENOSPC      — no space to create a new file (O_CREAT)
EROFS       — tried to write to a read-only file system
ENAMETOOLONG — pathname or a component exceeds NAME_MAX (255 bytes) or PATH_MAX (4096 bytes)
ETXTBSY     — tried to open an executable that is currently being executed for writing
```

`EMFILE` vs `ENFILE` is a classic interview distinction: `EMFILE` is per-process (your process ran out of fds); `ENFILE` is system-wide (the entire OS ran out of file table entries). In production: `EMFILE` typically means a file descriptor leak — the process opens fds and never closes them.

## Section 5: The `read()` and `write()` Syscalls

**Q18. What does `read()` do, step by step?**
A: `read(fd, buf, count)` reads up to `count` bytes from the file referenced by `fd` into the buffer `buf`, starting at the current file offset. Returns the number of bytes actually read.

```
1. Validate arguments:
   - fd is a valid open file descriptor with read permission
   - buf is a valid user-space address of at least count bytes
   - count is non-negative (count=0 is a no-op; returns 0)

2. Determine the read range:
   - current_offset = OFT entry's offset field
   - bytes_to_read = min(count, file_size − current_offset)
   - If bytes_to_read == 0: at EOF, return 0

3. Translate logical offset to physical blocks (via inode):
   - Compute which data blocks contain bytes [current_offset, current_offset + bytes_to_read)
   - For extent-based inodes: find the extent covering current_offset
   - For pointer-based inodes: traverse the block pointer tree

4. Read from page cache:
   - Check if the required pages are in the kernel's page cache
   - Cache hit: copy data from kernel page cache to user buffer (no disk I/O)
   - Cache miss: allocate page cache pages, submit block I/O requests to the disk driver,
     wait for completion, then copy from page cache to user buffer

5. Update state:
   - Advance OFT offset by bytes_read
   - Update inode atime (if not relatime/noatime)

6. Copy to user space:
   - copy_to_user(buf, kernel_page, bytes_read)
   - Return bytes_read
```

**Q19. What are the possible return values of `read()`, and what does each mean?**
A:

```
> 0    — number of bytes read; may be less than count (short read — see Q20)
  0    — end of file reached; no more data (for regular files: current offset == file size)
 -1    — error; errno set to the specific error code

Key errno values:
  EAGAIN / EWOULDBLOCK  — fd is non-blocking and no data is available right now
  EINTR                 — read was interrupted by a signal before any data was read;
                          must retry (standard idiom: loop until bytes > 0 or errno ≠ EINTR)
  EBADF                 — fd is not a valid open file descriptor, or not open for reading
  EFAULT                — buf is not a valid address in the process's address space
  EIO                   — I/O error (disk failure, hardware fault)
  EISDIR                — fd refers to a directory (directories must be read with getdents)
```

`EINTR` requires special handling — a read interrupted by a signal before reading any bytes returns -1/EINTR, not a short read. The correct idiom is a retry loop:

```c
ssize_t safe_read(int fd, void *buf, size_t count) {
  ssize_t n;
  do {
    n = read(fd, buf, count);
  } while (n == -1 && errno == EINTR);
  return n;
}
```

**Q20. What is a short read, why does it happen, and how do you handle it?**
A: A short read is when `read()` returns a positive value less than the requested `count`. The call succeeded — it returned as many bytes as were available at that moment — but not as many as asked for. Causes:

- **Regular files**: only at EOF (trying to read past the end of file returns however many bytes remain). A mid-file short read on a regular file shouldn't happen under normal conditions.
- **Pipes and sockets**: very common. The write end may have written fewer bytes than the read end requested; `read()` returns what's available without waiting for more.
- **Network sockets**: TCP is a stream protocol; `recv()` (equivalent to `read()` on sockets) returns whatever the kernel has buffered, which may be a partial message.
- **Signals**: a `read()` that has read some data and is then interrupted returns the data read so far (not -1/EINTR — that only happens if interrupted before any data was transferred).
- **Terminals**: in canonical mode, `read()` returns one line at a time; if the line is shorter than `count`, you get a short read.

The correct handling is always a **read loop**:

```c
ssize_t read_fully(int fd, void *buf, size_t count) {
  size_t total = 0;
  while (total < count) {
    ssize_t n = read(fd, (char*)buf + total, count - total);
    if (n == 0) break;        // EOF
    if (n == -1) {
      if (errno == EINTR) continue; // interrupted, retry
      return -1;              // real error
    }
    total += n;
  }
  return (ssize_t)total;
}
```

This pattern is so common it appears in virtually every systems programming context. At 5 YOE, forgetting the read loop is a serious red flag in a code review.

**Q21. What does `write()` do, and when is data actually on disk?**
A: `write(fd, buf, count)` writes `count` bytes from `buf` to the file at the current offset. Returns the number of bytes written (possibly less than `count` — a short write).

```
1. Validate:
   - fd is valid and open for writing
   - buf is a valid user-space address

2. If O_APPEND: atomically seek to end of file (kernel holds i_mutex during seek+write)

3. Copy from user to page cache:
   - copy_from_user(kernel_page, buf, count)
   - The data is now in the kernel's page cache (in RAM) but NOT on disk
   - The page is marked "dirty"

4. Metadata update (in memory):
   - Update inode: size (if extended), mtime, ctime
   - The inode itself is now dirty in the inode cache

5. Return bytes_written to user
   — At this point, write() has returned but data may not be on disk

6. Writeback (asynchronous, by the kernel):
   - The kernel's pdflush / writeback threads periodically flush dirty pages to disk
   - Default: dirty pages are written back within 30 seconds (dirty_expire_centisecs)
   - Under memory pressure: dirty pages are flushed immediately to reclaim RAM
```

**When is data actually on disk?**
- After `write()` returns: data is in page cache (RAM). Power loss here loses the data.
- After `fsync(fd)`: data *and* metadata are flushed to the storage device's write cache.
- After `fdatasync(fd)`: data is flushed but metadata (like `mtime`) may not be.
- After `sync()`: all dirty pages system-wide are flushed.
- With `O_SYNC`: every `write()` call blocks until data and metadata reach the device.
- With `O_DSYNC`: every `write()` call blocks until data (not metadata) reaches the device.

Note: "on disk" with `fsync` means in the **device's write cache** — not necessarily on the physical magnetic surface or NAND cells. True persistence requires the device to flush its own volatile cache, which requires the device to support flush commands (`FUA` flag or explicit flush) and the OS to send them.

**Q22. What is the page cache, and how does it interact with `read()` and `write()`?**
A: The page cache (also called the buffer cache in older literature) is a region of kernel memory that caches file data in RAM. It is the central data structure for file I/O performance:

- **On `read()`**: the kernel checks the page cache first. If the requested file pages are cached (cache hit), data is copied from RAM to the user buffer — no disk I/O. If not cached (cache miss), the kernel reads the page from disk into the cache, then copies to the user buffer. Subsequent reads of the same data are served from cache.
- **On `write()`**: data is written to the page cache and the page is marked dirty. The `write()` syscall returns immediately without waiting for disk I/O. The dirty page is flushed to disk asynchronously (writeback). This is why `write()` appears fast — it's mostly a memory copy.
- **Read-ahead**: when the kernel detects sequential reads, it speculatively loads pages beyond what was requested, anticipating future `read()` calls. This hides disk latency for sequential access patterns.
- **Memory pressure**: when the system needs RAM, the kernel reclaims page cache pages. Clean pages (not modified) are simply discarded. Dirty pages must be written back first. The LRU (Least Recently Used) policy determines which pages are evicted.

`O_DIRECT` bypasses the page cache entirely — I/O goes directly between user buffers and disk. Used by databases (which manage their own caching) and benchmarking tools to measure raw disk performance without cache interference. Requires alignment: buffer address and size must be multiples of the disk's block size (typically 512 bytes or 4096 bytes).

**Q23. What is `lseek()`, and what are its uses?**
A: `lseek(fd, offset, whence)` repositions the file offset for the next `read()` or `write()` without doing any I/O. It modifies the offset field in the Open File Table entry. `whence` determines how `offset` is interpreted:

```c
lseek(fd, 0, SEEK_SET);    // rewind to beginning of file
lseek(fd, 0, SEEK_END);    // seek to end of file (returns file size)
lseek(fd, -100, SEEK_END); // 100 bytes before end
lseek(fd, 100, SEEK_CUR);  // 100 bytes forward from current position
lseek(fd, 0, SEEK_DATA);   // seek to next non-hole byte (for sparse files)
lseek(fd, 0, SEEK_HOLE);   // seek to next hole in a sparse file
```

Key uses:
- **Random access**: jump to any position in a file for reading or writing without reading through the intervening data.
- **Determine file size**: `lseek(fd, 0, SEEK_END)` returns the number of bytes.
- **Sparse files**: seeking past the end of a file and writing creates a "hole" — a range of logical offsets that contain zero bytes but consume no disk blocks. `du` reports the actual disk usage; `ls -l` reports the logical file size. Used by virtual machine disk images and database files.
- **`lseek()` fails on pipes, sockets, and FIFOs** — these are sequential streams with no seek position. Returns `-1` with `errno = ESPIPE`.

## Section 6: System Call Path and Performance

**Q24. What happens in the kernel when a process calls `read()`? Trace the full path.**
A: The transition from user space to kernel space and back:

```
User space:
  read(fd, buf, count)         // C library wrapper
  → mov rax, 0                 // syscall number for read (on x86-64)
  → mov rdi, fd
  → mov rsi, buf
  → mov rdx, count
  → syscall                    // CPU switches to kernel mode (ring 0)

Kernel space (syscall entry):
  → sys_read() in fs/read_write.c
  → Look up fd in current->files->fdt (per-process fd table)
  → Get struct file * (the OFT entry)
  → Check f_mode & FMODE_READ (fd opened for reading?)
  → Call file->f_op->read_iter() (the VFS method dispatch)

VFS layer:
  → generic_file_read_iter() for regular files
  → Check page cache for requested pages (page_cache_get_page())

Page cache hit:
  → copy_page_to_iter() — copy from kernel page to user buffer
  → Update f_pos (file offset)
  → Return bytes copied

Page cache miss:
  → Allocate page cache pages
  → Submit bio (block I/O) request to the block layer
  → Block layer → I/O scheduler → device driver → disk/SSD hardware
  → Hardware interrupt on completion → DMA transfers data to page cache
  → Wake up the sleeping process
  → copy_page_to_iter() — copy from now-populated page cache to user buffer
  → Return bytes copied

Return to user space:
  → syscall return instruction (sysret / iret)
  → C library wrapper checks return value
  → If < 0: set errno = -return_value, return -1
  → Else: return bytes_read
```

The key performance insight: a page cache hit involves one kernel entry, one memory copy, and one kernel exit. A page cache miss adds disk I/O — potentially milliseconds of latency for spinning disk, microseconds for NVMe. The ratio of cache hits to misses (the page cache hit rate) is the dominant factor in file I/O performance.

**Q25. What is the difference between buffered I/O (stdio) and unbuffered I/O (syscalls), and when does each matter?**
A: Two levels of buffering sit between application code and the disk:

**C stdio buffered I/O** (`fopen`, `fread`, `fwrite`, `fprintf`): the C library maintains a user-space buffer (typically 4KB–8KB) and batches syscalls. `fwrite()` copies data into the library's buffer; a `write()` syscall is issued only when the buffer is full, `fflush()` is called, or the `FILE*` is closed. This dramatically reduces syscall count for small writes.

```c
// 1,000 fwrite() calls → potentially 1 write() syscall (if data fits in stdio buffer)
for (int i = 0; i < 1000; i++) {
  fwrite(&record, sizeof(record), 1, fp); // copies to stdio buffer
}
fflush(fp);  // one write() syscall drains the buffer
```

**Unbuffered syscall I/O** (`open`, `read`, `write`): each call is a direct syscall. No user-space buffering. Each `write()` of even 1 byte triggers a full kernel entry/exit. For small, frequent writes, this is expensive (thousands of syscall round-trips per second).

```c
// 1,000 write() calls → 1,000 syscalls
for (int i = 0; i < 1000; i++) {
  write(fd, &record, sizeof(record)); // syscall on every iteration
}
```

**When to use which:**
- Use stdio (buffered) for text processing, logging, config file reading — typical "file as a sequence of records" workload. The buffering is free performance.
- Use direct syscalls when: you need precise control over when writes reach the kernel (flushing after each record), working with non-seekable streams (pipes, sockets) where stdio buffering can cause unexpected blocking, or when mixing syscall I/O and stdio I/O on the same fd (dangerous — buffer state gets out of sync).
- Both still go through the kernel page cache — "unbuffered" means no *user-space* buffer, not no *kernel* buffer.

**Q26. What is `mmap()`, and how does it differ from `read()`/`write()` for file I/O?**
A: `mmap(addr, length, prot, flags, fd, offset)` maps a file (or anonymous memory) into the process's virtual address space. Once mapped, the process accesses file data by reading and writing memory addresses — no `read()`/`write()` syscalls required for subsequent accesses.

```c
int fd = open("data.bin", O_RDWR);
struct Record *data = mmap(NULL, file_size, PROT_READ | PROT_WRITE,
                           MAP_SHARED, fd, 0);
// Now data[i] reads/writes directly to the file's page cache pages
data[42].value = 99; // write to the file — no write() syscall
msync(data, file_size, MS_SYNC); // flush to disk (like fsync)
munmap(data, file_size);
```

**Differences from `read()`/`write()`:**

| Dimension              | `read()`/`write()`                         | `mmap()`                                        |
|---                     |---                                         |---                                              |
| Data copy              | Kernel page → user buffer (extra copy)     | Process maps page cache directly (zero-copy)    |
| Syscall overhead       | One syscall per read/write                 | One syscall to set up; zero for subsequent access|
| Access pattern         | Sequential (offset advances)               | Random (any address dereference works)          |
| File size changes      | Works naturally                            | Problematic — mapping must be sized at `mmap()` |
| Page fault handling    | N/A                                        | Page faults on first access trigger disk reads  |
| Large file handling    | Works on 32-bit (with offsets)             | Requires address space (problematic on 32-bit)  |
| Best for               | Sequential streaming; large files          | Random access; IPC; database files; executables |

`mmap()` is zero-copy: the process's virtual pages are backed directly by page cache pages — no intermediate user buffer. This is why databases (PostgreSQL's shared buffer pool, SQLite's WAL mode), JVMs (memory-mapped class files), and the dynamic linker (`ld.so` maps shared libraries) use `mmap()` extensively.

## Section 7: Pitfalls and Real-World Considerations

**Q27. What is a file descriptor leak, how does it happen, and how do you find it?**
A: A file descriptor leak occurs when a process opens fds and never closes them, gradually exhausting its `RLIMIT_NOFILE` limit. When the limit is hit, all subsequent `open()`, `socket()`, `pipe()`, and `accept()` calls fail with `EMFILE`. At this point, the process cannot open new connections, files, or pipes — it is effectively broken.

Common causes:
- **Missing `close()` on error paths** — the happy path closes the fd; an early return on error skips the close.
- **Exception before `close()`** — in languages with exception handling, an exception between `open()` and `close()` leaves the fd open (use RAII, `finally`, `defer`, or `using` blocks).
- **Inherited fds across `fork()`/`exec()`** — child processes inherit parent fds without knowing about them.
- **`accept()` in a loop without `close()`** — every accepted connection that isn't closed leaks a socket fd.
- **`dup()` or `dup2()` creating aliases** — the original and duplicate must both be closed.

Detection:
```bash
# Count open fds for a process (Linux)
ls /proc/<pid>/fd | wc -l

# List all open fds with their targets
ls -la /proc/<pid>/fd

# lsof — list open files system-wide or per process
lsof -p <pid>

# Watch fd count over time (leak shows steady growth)
watch -n1 "ls /proc/<pid>/fd | wc -l"
```

In production: set `RLIMIT_NOFILE` conservatively, alert on processes using >80% of their fd limit, and review any code path that opens a fd in a loop.

**Q28. What are the atomicity guarantees of `write()`, and when can concurrent writes to the same file corrupt data?**
A: The POSIX standard guarantees that `write()` calls to a regular file are atomic only in specific circumstances:

- **Writes ≤ `PIPE_BUF` (typically 4096 bytes) to a pipe or FIFO** — guaranteed atomic (either the entire write appears in the pipe, or none of it does; writes from different processes don't interleave).
- **`O_APPEND` writes to a regular file** — POSIX guarantees that the seek-to-end and the write are performed atomically (no other writer can interleave between the seek and the write). Multiple processes appending to a log file with `O_APPEND` will not corrupt each other's records, but only if each write is a single `write()` call.
- **Large writes or multiple `write()` calls** — no atomicity guarantee. Two processes writing to the same offset in a file without locking can produce interleaved, corrupted data.

Coordination mechanisms:
```c
// Advisory file locking (POSIX) — cooperative; processes must all use flock/fcntl
flock(fd, LOCK_EX);   // acquire exclusive lock
write(fd, data, len);
flock(fd, LOCK_UN);   // release

// fcntl byte-range locking — lock a specific byte range
struct flock fl = { .l_type=F_WRLCK, .l_whence=SEEK_SET, .l_start=0, .l_len=0 };
fcntl(fd, F_SETLKW, &fl); // acquire write lock on entire file (l_len=0 means to EOF)
```

Note: `flock()` locks are per-open-file-description, not per-inode. Two processes that inherited the same fd via `fork()` share the same lock — they cannot lock each other out. Use `fcntl()` locks for inter-process locking (they are per-process-per-inode).

**Q29. What is `fsync()`, and why is it not enough for durable writes in all cases?**
A: `fsync(fd)` flushes all dirty pages for the file referenced by `fd` from the page cache to the storage device, and blocks until the device acknowledges the writes. It also flushes metadata (inode, timestamps). After `fsync()` returns successfully, the data and metadata are in the device's own cache.

Why `fsync()` alone may not be enough for true durability:
- **Storage device write cache**: many disks and SSDs have volatile write caches. Data acknowledged by the device may still be in the device's RAM, lost on power failure. Truly durable writes require the device to flush its own cache — either via the `FUA` (Force Unit Access) flag in the write command or an explicit cache flush command. Databases configure disks to disable the volatile write cache, or use NVMe drives that support power-loss protection.
- **Directory entry not synced**: creating a file and calling `fsync(fd)` on it ensures the file's data and inode are durable — but the directory entry pointing to the inode may not be synced. If the system crashes between the file write and the directory sync, the file data exists on disk but the directory doesn't point to it (a "lost" inode). The correct pattern for durable file creation:
  ```c
  int fd = open("new_file.txt", O_WRONLY | O_CREAT, 0644);
  write(fd, data, len);
  fsync(fd);          // flush file data and inode
  close(fd);
  int dir_fd = open(".", O_RDONLY);
  fsync(dir_fd);      // flush the directory entry to disk
  close(dir_fd);
  ```
- **Rename atomicity + durability**: `rename("tmp", "final")` is atomic (either the rename happened or it didn't), but not durable until the directory is `fsync`'d. Write-then-rename is the standard durable file update pattern: write to a temp file, `fsync` it, rename to the target name, `fsync` the directory.

## Section 8: Scenario / System Design Style Questions

**Q30. "A logging service writes thousands of small records per second to a file. Latency is spiking. What are the likely causes and how do you fix them?"**
A: Small, frequent writes to a file are a classic throughput and latency problem. Diagnose and fix in layers:

1. **User-space buffering (most impactful)** — if each record is written with a separate `write()` syscall, thousands of kernel entries per second add up. Buffer records in user space and flush as a batch. Stdio's `fwrite()` + periodic `fflush()` or a ring buffer with explicit `write()` of accumulated records. Target: one `write()` syscall per ~4KB of data.

2. **`fsync()` on every write** — if the code calls `fsync()` after each record, every write blocks until the disk acknowledges. For logging, this is almost never necessary. Batch `fsync()` calls: fsync every N records, or every T milliseconds, or only on clean shutdown. Accept that at most T milliseconds of log data is at risk on crash.

3. **`O_SYNC` on the fd** — same problem as per-write `fsync()`, built into the fd. Remove `O_SYNC` unless the log is a WAL (write-ahead log) that must be durable before the transaction commits.

4. **File system choice** — ext4 with `data=journal` mode makes every write go through the journal (slow). `data=ordered` (default) or `data=writeback` is faster for logging. XFS and ext4 with `data=writeback` have lower write latency.

5. **Log rotation locking** — if a log rotation script is acquiring an exclusive lock or truncating the file while the logger is writing, writes stall. Use `O_APPEND` (no locking needed for append) and logrotate's `copytruncate` mode (copy then truncate — logger keeps writing to the same inode).

6. **Async I/O or a separate writer thread** — move all file I/O to a dedicated writer goroutine/thread. The application enqueues log records (fast, non-blocking), the writer drains the queue to disk. Decouples application latency from disk latency entirely.

**Q31. "Explain what happens at the file system level when you run `cp source.txt dest.txt`."**
A: `cp` performs several file system operations:

```
1. open("source.txt", O_RDONLY)
   → path walk: resolve "source.txt" in cwd → inode N
   → check read permission on inode N
   → allocate OFT entry (offset=0), fd=3

2. open("dest.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644)
   → path walk: "dest.txt" in cwd
   → if exists: O_TRUNC truncates it to 0 bytes (frees old data blocks)
   → if not exists: allocate new inode M, add directory entry "dest.txt" → inode M
   → allocate OFT entry (offset=0), fd=4

3. Loop: read(3, buf, 65536) → write(4, buf, bytes_read)
   → read() loads source pages into page cache, copies to user buf
   → write() copies from user buf to dest's page cache pages (marks them dirty)
   → Repeat until read() returns 0 (EOF)

4. Dirty writeback:
   → dest.txt's page cache pages are dirty — will be written to disk by writeback
   → cp does NOT call fsync() — data may not reach disk before cp exits

5. close(3) → decrement source inode reference count
   close(4) → decrement dest inode reference count; if reference count > 0, inode stays
   
6. Inode updates:
   → source.txt: atime updated (relatime rules permitting)
   → dest.txt: mtime and ctime updated; size set to bytes written

What cp does NOT do:
   → It does not preserve ctime (cannot — ctime reflects this new inode)
   → It does not preserve hard links (cp creates a new inode; use rsync -H for hard links)
   → It does not call fsync() (use cp --no-preserve and then sync, or rsync with --fsync)
   → "cp -p" preserves mtime, atime, permissions, and owner (if root), but not ctime
```

**Q32. "You have a process that opens a file, another process deletes the file, and the first process continues reading. What happens?"**
A: The first process continues reading successfully — the file's data is not deleted until both the link count reaches zero AND the open file count reaches zero.

Step by step:
```
t=1: Process A: fd = open("data.txt", O_RDONLY)
     → inode 42: link_count=1, open_count=1
     → Directory: "data.txt" → inode 42

t=2: Process B: unlink("data.txt")
     → Directory entry removed: "data.txt" no longer appears in directory
     → inode 42: link_count becomes 0
     → But open_count=1 (Process A still has it open)
     → Kernel does NOT free inode 42 or its data blocks

t=3: Process A: read(fd, buf, 1024)
     → Kernel looks up fd → OFT entry → inode 42
     → inode 42 is still in memory with its data blocks intact
     → Read succeeds; Process A gets data normally

t=4: Process A: close(fd)
     → open_count becomes 0; link_count already 0
     → NOW: kernel frees inode 42, returns data blocks to free list
     → File data is truly gone
```

This behavior is exploited for temporary files: `open()` the file, `unlink()` it immediately, use it via the fd — it's invisible in the directory and automatically cleaned up when the fd is closed (even if the process crashes, the kernel closes all fds on exit). This is how `tmpfile()` in the C standard library works. It is also how you can delete a large log file on a busy server without restarting the process — the process keeps writing to the fd (now an orphaned inode), and the disk space is reclaimed only when the process is restarted and the fd is closed.

## Quick Reference

```
Inode: metadata record (NOT including name or data)
  Contains: type, permissions, UID/GID, size, timestamps, block pointers, link count
  Absent:   filename (lives in directory entry), data (lives in data blocks)

Link count rules:
  file created  → link_count = 1
  hard link     → link_count++
  unlink/rm     → link_count--; free inode only when link_count=0 AND open_count=0

Three-table structure:
  fd (int) → Open File Table entry (offset, flags, inode ptr) → inode → data blocks
  fork():  child copies fd table; parent+child share OFT entries (shared offset)
  dup():   two fds share one OFT entry (shared offset)
  Two processes open same file independently: separate OFT entries (independent offsets)

open() steps: path walk → permission check → O_CREAT/O_TRUNC → OFT alloc → fd alloc
read()  steps: validate → compute range → page cache check → (disk I/O) → copy_to_user
write() steps: validate → (O_APPEND seek) → copy_from_user → mark dirty → return
                         ↑ data is in RAM; not on disk until writeback or fsync()

Durability ladder (weakest → strongest):
  write()    → data in page cache (RAM); lost on power failure
  fdatasync()→ data on storage device; metadata may lag
  fsync()    → data + metadata on storage device
  fsync(dir) → directory entry durable (required for new file durability)
  O_SYNC     → every write() blocks until data+metadata on device

Atomicity:
  O_APPEND     → seek-to-end + write is atomic (safe for multi-process log appending)
  O_CREAT|O_EXCL → create-if-not-exists is atomic (safe lock file creation)
  rename()     → atomic directory entry swap (safe file replace pattern)

Common errno values:
  ENOENT  → file/path not found
  EACCES  → permission denied
  EMFILE  → process fd limit reached (fd leak)
  ENFILE  → system-wide fd limit reached
  EINTR   → interrupted by signal (retry read/write)
  EAGAIN  → non-blocking fd, no data available (retry later)
  ESPIPE  → lseek on pipe/socket (not seekable)
```

## Common Mistakes at a Glance

| Mistake                                                      | Symptom / Risk                                              | Fix                                                                 |
|---                                                           |---                                                          |---                                                                  |
| Not handling short reads                                     | Partial data silently treated as complete                   | Read loop until count bytes received or EOF                         |
| Not handling `EINTR` on `read()`/`write()`                   | Silent failure when signals are delivered                   | Retry loop: `while (n==-1 && errno==EINTR)`                         |
| Missing `close()` on error paths                             | File descriptor leak → eventual `EMFILE`                   | RAII / `defer` / `finally` / `goto cleanup` pattern                |
| Assuming `write()` means data is on disk                     | Data loss on power failure or crash                         | Call `fsync()` after critical writes; sync directory for new files  |
| Forgetting to `fsync()` the directory after creating a file  | File data durable but directory entry not → lost inode      | `fsync()` both the file fd and the parent directory fd              |
| Using `flock()` for inter-process locking after `fork()`     | Parent and child share the lock; can't lock each other out  | Use `fcntl()` locks (per-process-per-inode semantics)               |
| Mixing stdio (`fread`) and syscall (`read`) on the same fd   | stdio buffer and kernel offset desync; data skipped/doubled | Use one or the other; never mix on the same fd                      |
| Assuming `rename()` is durable without `fsync()`             | Rename is atomic but not durable; lost on crash             | `fsync()` the file, then `rename()`, then `fsync()` the directory   |
| Opening fds without `O_CLOEXEC`                              | fd leaks into child processes via `exec()`                  | Always use `O_CLOEXEC` unless intentionally passing fd to child      |
| Confusing `mtime` and `ctime`                                | Wrong file used in dependency tracking or backup            | `mtime` = data changed; `ctime` = inode changed (superset)         |
