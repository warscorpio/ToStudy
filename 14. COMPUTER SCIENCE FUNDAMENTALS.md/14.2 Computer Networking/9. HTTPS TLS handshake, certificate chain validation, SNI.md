# HTTPS: TLS Handshake, Certificate Chain Validation, SNI — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What does HTTPS provide over HTTP, and what are its three security properties?**
A: HTTPS is HTTP running over TLS (Transport Layer Security). It adds three security properties that plain HTTP cannot provide:

**Confidentiality:** Data in transit is encrypted. A network observer — an ISP, a man-in-the-middle attacker on a coffee shop Wi-Fi, a compromised router — sees only ciphertext. They cannot read the request body (which may contain a payment card number or authentication token), response body, or even the specific URL path and query string (the hostname is visible in DNS and TLS SNI, but the path and query are encrypted).

**Integrity:** TLS uses authenticated encryption (AEAD — Authenticated Encryption with Associated Data). Any modification to the ciphertext in transit is detected; the receiving end will discard the tampered data and tear down the connection. An attacker cannot silently alter a payment amount or inject a script into a response without the alteration being detected.

**Authentication:** TLS certificates allow the client to verify that it is communicating with the genuine server and not an impostor. When your browser connects to `api.bank.com`, TLS proves — through a chain of cryptographic trust — that the server holds the private key for a certificate issued by a trusted Certificate Authority (CA) for `api.bank.com`. A DNS hijack that redirects `api.bank.com` to an attacker's server will fail certificate validation (the attacker doesn't hold the private key for `api.bank.com`'s certificate).

Without all three: HTTP provides none of them. A plain HTTP connection can be eavesdropped (no confidentiality), modified in transit (no integrity), and the server cannot be verified (no authentication — you could be talking to anyone).

**Q2. What is TLS, and how does it relate to SSL?**
A: TLS (Transport Layer Security) is the cryptographic protocol that secures HTTPS connections. It is the successor to SSL (Secure Sockets Layer), which was developed by Netscape in the 1990s. The version history matters because interviewers sometimes ask about deprecated versions:

| Version | Year | Status |
|---|---|---|
| SSL 1.0 | 1994 | Never publicly released |
| SSL 2.0 | 1995 | Deprecated 2011 — broken |
| SSL 3.0 | 1996 | Deprecated 2015 — broken (POODLE) |
| TLS 1.0 | 1999 | Deprecated 2021 — prohibited by PCI DSS 3.2+ |
| TLS 1.1 | 2006 | Deprecated 2021 |
| TLS 1.2 | 2008 | Still widely used; secure with correct configuration |
| TLS 1.3 | 2018 | Current standard; recommended |

The name "SSL" persists colloquially — engineers say "SSL certificate," "SSL termination," and "OpenSSL" — but the actual protocol in use is TLS. When someone says "renew the SSL certificate," they mean a TLS certificate. When an AWS ALB offers "SSL/TLS termination," it's TLS. The distinction matters for precision: PCI DSS explicitly prohibits SSL 2.0, SSL 3.0, TLS 1.0, and TLS 1.1.

TLS sits between the transport layer (TCP) and the application layer (HTTP). From TCP's perspective, TLS is just application data — encrypted bytes. From HTTP's perspective, TLS provides a reliable encrypted byte stream just like TCP does for plain HTTP. TLS is transparent to HTTP itself.

**Q3. What is a cipher suite, and why does the choice of cipher suite matter?**
A: A cipher suite is a named combination of cryptographic algorithms used together in TLS — one algorithm for each cryptographic function needed during the handshake and data exchange:

```
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
│   │      │   │   │   │   │   │
│   │      │   │   │   │   └───── Hash for HMAC/PRF
│   │      │   │   │   └───────── Cipher mode (GCM = Galois/Counter Mode)
│   │      │   │   └───────────── Key size (256-bit AES)
│   │      │   └───────────────── Bulk encryption algorithm (AES)
│   │      └───────────────────── Authentication algorithm (RSA signature)
│   └──────────────────────────── Key exchange algorithm (ECDHE)
└──────────────────────────────── Protocol (TLS)
```

In TLS 1.3 the cipher suite format is simplified — key exchange and authentication are negotiated separately:
```
TLS_AES_256_GCM_SHA384      (bulk encryption + hash only)
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_GCM_SHA256
```

Key properties to look for in a cipher suite:

**Forward secrecy (PFS — Perfect Forward Secrecy):** Provided by ephemeral key exchange algorithms (ECDHE — Elliptic Curve Diffie-Hellman Ephemeral, DHE — Diffie-Hellman Ephemeral). With forward secrecy, each session uses a freshly generated ephemeral key pair. If an attacker records the ciphertext today and later steals the server's long-term private key, they still cannot decrypt the recorded sessions — because the ephemeral session keys were never stored and cannot be derived from the long-term key. Without forward secrecy (RSA key exchange — `TLS_RSA_WITH_...`), recording today's traffic and stealing the key later decrypts everything retroactively.

**AEAD (Authenticated Encryption with Associated Data):** GCM (Galois/Counter Mode) and CCM provide both encryption and authentication in one pass. Older modes (CBC — Cipher Block Chaining) required separate MAC (Message Authentication Code) which led to padding oracle attacks (BEAST, POODLE). All TLS 1.3 cipher suites use AEAD.

**Weak/broken algorithms to reject:** RC4 (stream cipher, statistically biased), DES/3DES (56-bit and 112-bit keys — too small), MD5/SHA-1 (for signatures — collision-vulnerable), RSA key exchange without forward secrecy (`TLS_RSA_WITH_...`), anonymous cipher suites (`_anon_` — no authentication).

## Section 2: The TLS 1.2 Handshake

**Q4. Walk through the complete TLS 1.2 handshake step by step.**
A: The TLS 1.2 handshake takes 2 RTTs (round trips) before any application data flows. Each step involves specific messages:

```
Client                                          Server
──────                                          ──────
ClientHello ─────────────────────────────────▶
  - TLS version: 1.2
  - Random: 28 bytes of entropy (client_random)
  - Session ID: empty (new session) or prior ID (resumption)
  - Cipher suites: [TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384, ...]
  - Extensions:
      - server_name: "api.payment.com" (SNI)
      - supported_groups: [x25519, secp256r1, ...]
      - signature_algorithms: [rsa_pss_sha256, ecdsa_sha256, ...]

                              ◀─────────────────── ServerHello
                                - TLS version: 1.2
                                - Random: 28 bytes (server_random)
                                - Session ID: (new or resumed)
                                - Cipher suite: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384

                              ◀─────────────────── Certificate
                                - Server's certificate chain
                                  (leaf cert + intermediates, no root)

                              ◀─────────────────── ServerKeyExchange
                                - ECDHE parameters:
                                    named curve: secp256r1
                                    server's ephemeral public key
                                - Signature over params (using private key)
                                - (Only for ECDHE/DHE — not RSA key exchange)

                              ◀─────────────────── ServerHelloDone
                                (signals end of server's handshake messages)

────── RTT 1 complete ──────

[Client validates certificate chain]
[Client verifies ServerKeyExchange signature]
[Client generates its own ECDHE ephemeral key pair]
[Client computes pre-master secret: ECDHE(client_private, server_public)]
[Both sides derive session keys from pre-master secret + randoms via PRF]

ClientKeyExchange ───────────────────────────▶
  - Client's ECDHE ephemeral public key

ChangeCipherSpec ────────────────────────────▶
  (signals: all subsequent messages encrypted with negotiated keys)

Finished ────────────────────────────────────▶
  - HMAC over entire handshake transcript
    (proves client has same keys; detects transcript tampering)

                              ◀─────────────────── ChangeCipherSpec

                              ◀─────────────────── Finished
                                - HMAC over entire handshake transcript

────── RTT 2 complete ──────

[Application data can now flow — encrypted with session keys]

GET /v1/payments HTTP/1.1 ───────────────────▶ (encrypted)
                              ◀─────────────────── HTTP/1.1 200 OK (encrypted)
```

**Key derivation:** The pre-master secret (output of ECDHE) is combined with `client_random + server_random` through the TLS PRF (Pseudorandom Function, based on HMAC-SHA256 or HMAC-SHA384) to derive four keys: client write key, server write key, client write IV (Initialization Vector), server write IV. Each direction of the connection uses separate keys, preventing replay attacks.

**Why two random values (client_random + server_random)?** Each side contributes fresh entropy. If the server's random were the only source, a server with a weak random number generator could produce predictable session keys. Both sides contributing entropy ensures at least one source is unpredictable.

**Q5. What is session resumption in TLS 1.2, and how does it reduce the handshake cost?**
A: A full TLS 1.2 handshake takes 2 RTTs plus certificate validation. For a client making many connections to the same server (API client, browser), this overhead accumulates. TLS 1.2 offers two resumption mechanisms:

**Session ID resumption:**
On the initial handshake, the server assigns a session ID (up to 32 bytes) stored in the ServerHello. The server caches the session state (keys, cipher suite, certificates) indexed by this ID. On a subsequent connection, the client includes the prior session ID in its ClientHello. If the server finds the ID in its cache, it responds with the same session ID and skips to ChangeCipherSpec + Finished — only 1 RTT:

```
Client                           Server
ClientHello (session_id=abc123) ─▶
                          ◀─── ServerHello (session_id=abc123) + ChangeCipherSpec + Finished
ChangeCipherSpec + Finished ─────▶
[Application data — 1 RTT total instead of 2]
```

Limitation: server-side state. With many servers behind a load balancer, a client connected to server 1 holds a session ID — but the next connection may land on server 2, which has no cache entry. Requires sticky sessions or a shared session cache (Redis) across the server pool.

**Session ticket resumption (stateless):**
The server encrypts the session state with a server-side ticket encryption key (TEK) and sends it to the client as a `NewSessionTicket` extension. The client stores the opaque ticket. On reconnection, the client presents the ticket in the ClientHello. The server decrypts it (using its TEK), recovers the session state, and resumes — without any server-side storage per client:

```
Initial connection (full handshake):
Server → Client: NewSessionTicket (encrypted session state)

Resumed connection:
Client → Server: ClientHello (SessionTicket = opaque_blob)
Server: decrypts ticket, recovers session → 1 RTT resumption
```

Limitation: if the TEK is compromised, all past tickets become decryptable — **session tickets undermine forward secrecy** unless the TEK is rotated frequently (NGINX recommends every 24 hours; `ssl_session_ticket_key` can be managed via a cron job or external key management). TLS 1.3 addresses this by making 0-RTT resumption explicitly conditional on forward-secrecy and replay protection.

## Section 3: The TLS 1.3 Handshake

**Q6. How does TLS 1.3 differ from TLS 1.2 in its handshake, and why is it considered more secure?**
A: TLS 1.3 redesigns the handshake from scratch, achieving 1-RTT for new connections and 0-RTT for resumptions, while simultaneously removing all legacy cryptography:

**TLS 1.3 full handshake (1-RTT):**
```
Client                                          Server
──────                                          ──────
ClientHello ─────────────────────────────────▶
  - TLS version: 1.3 (in supported_versions extension)
  - Random: 32 bytes
  - Legacy session ID: (ignored in 1.3)
  - Cipher suites: [TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256]
  - Extensions:
      - supported_versions: [TLS 1.3, TLS 1.2]
      - key_share: client's ECDHE key shares
          (x25519 public key — sent speculatively without waiting)
      - server_name: "api.payment.com" (SNI)
      - signature_algorithms: [rsa_pss_sha256, ecdsa_sha256]
      - psk_key_exchange_modes: [psk_dhe_ke] (for 0-RTT support)

                              ◀─────────────────── ServerHello
                                - supported_versions: TLS 1.3
                                - key_share: server's x25519 ephemeral public key
                                - [Handshake keys derived here — server encrypts from now]

                              ◀─────────────────── {EncryptedExtensions}
                                - (encrypted) additional extensions

                              ◀─────────────────── {Certificate}
                                - (encrypted) server certificate chain

                              ◀─────────────────── {CertificateVerify}
                                - (encrypted) signature over handshake transcript

                              ◀─────────────────── {Finished}
                                - (encrypted) HMAC over handshake transcript

────── 1 RTT complete ──────

[Client verifies Certificate and CertificateVerify]
[Client verifies Finished]
[Client derives application keys]

{Finished} ──────────────────────────────────▶ (encrypted)

{Application Data} ──────────────────────────▶ (encrypted)
                              ◀─────────────────── {Application Data}
```

**Key improvements over TLS 1.2:**

**1-RTT instead of 2-RTT:** The client includes its ECDHE key share speculatively in the ClientHello — without waiting for the server to confirm the cipher suite. If the server supports the client's preferred key exchange group (x25519 is universal), the server can complete the ECDHE immediately and derive handshake keys in the same round trip. The server's Finished message arrives in the same response as the certificate — the client can verify and send application data after just one round trip.

**Certificate and CertificateVerify are encrypted:** In TLS 1.2, the Certificate message is sent in plaintext — a network observer can see which certificate the server presented (and thus which domain/organisation). In TLS 1.3, Certificate and CertificateVerify are encrypted using the handshake keys derived from the ECDHE exchange. Only an entity that completes the ECDHE exchange can see the certificate — the server's identity is hidden from passive observers.

**All weak algorithms removed:** TLS 1.3 eliminates RSA key exchange (no forward secrecy), DH/ECDH static (no forward secrecy), RC4, DES, 3DES, MD5, SHA-1, export-grade cryptography, and CBC mode cipher suites. Every TLS 1.3 cipher suite uses ECDHE (forward secrecy) and AEAD encryption. There is no way to negotiate a weak cipher suite in TLS 1.3.

**Separate CertificateVerify message:** In TLS 1.2, the server proves possession of the private key implicitly (the ServerKeyExchange signature). TLS 1.3 makes this explicit — the server signs the entire handshake transcript using the private key corresponding to the certificate. This prevents transcript substitution attacks.

**Q7. What is 0-RTT in TLS 1.3, and what are its security implications?**
A: 0-RTT (zero round-trip time resumption, also called "early data") allows a client to send application data in the very first packet of a resumed TLS 1.3 connection — before the handshake completes — using a pre-shared key (PSK) derived from a previous session:

```
Resumed connection with 0-RTT:

Client                                          Server
ClientHello ─────────────────────────────────▶
  - psk_identity: (ticket from previous session)
  - key_share: new ECDHE key share
  - early_data extension: present

{Early Data (0-RTT)} ────────────────────────▶
  POST /v1/payments HTTP/1.1
  (encrypted with PSK-derived keys)
  (sent before server responds — no RTT wait)

                              ◀─────────────────── ServerHello
                                - psk: accepted
                                - key_share: server's ECDHE public key

                              ◀─────────────────── {EncryptedExtensions}
                                - early_data: accepted (or rejected)

                              ◀─────────────────── {Finished}

{Finished} ──────────────────────────────────▶
{Application Data (1-RTT)} ──────────────────▶

                              ◀─────────────────── {Application Data}
```

**The security problem with 0-RTT — replay attacks:**
0-RTT data is sent before the server's Finished message — before the client has proof that the server is alive and fresh. An attacker who captures the client's 0-RTT data can **replay** it to the server at a later time. The server cannot distinguish the original from the replay.

Example: A client sends a `POST /v1/payments/charge` as 0-RTT data. An attacker captures this datagram and replays it 10 minutes later to the same server. The server processes the charge twice.

Mitigation strategies:
- **Server-side replay cache:** The server maintains a cache of recently seen PSK identities and nonces. If a 0-RTT request matches a prior entry, it's rejected. But this reintroduces server-side state — defeating the statelessness of tickets — and is time-bounded (cache size limits how far back protection extends).
- **Anti-replay at the application layer:** For safe 0-RTT, only use it for idempotent requests: `GET`, `HEAD`, `OPTIONS`, or application-specific idempotent operations. Never for payment processing, state-changing actions, or any non-idempotent operation.
- **Selective 0-RTT:** The server can accept 0-RTT for certain paths and reject it (with `early_data_rejected`) for others. The client must then retransmit in the 1-RTT context.

In Node.js: `tls.createServer({ earlyData: true })` enables 0-RTT. For a payment API, 0-RTT should be disabled or strictly limited to safe idempotent endpoints. AWS ALB supports TLS 1.3 0-RTT; it can be configured to disable it for non-idempotent backend paths.

## Section 4: Certificate Chain Validation

**Q8. What is an X.509 certificate, and what fields are critical for validation?**
A: An X.509 certificate is a digitally signed data structure that binds a public key to an identity (domain name, organisation). It is the mechanism by which TLS authentication works — the server presents its certificate, and the client validates that it's genuine and covers the hostname being accessed.

**Critical X.509 fields:**

```
Certificate:
  Version: 3 (X.509 v3 — current standard)
  Serial Number: 0x1A2B3C4D (unique per CA — used for revocation)
  Signature Algorithm: sha256WithRSAEncryption

  Issuer: C=US, O=DigiCert Inc, CN=DigiCert TLS RSA SHA256 2020 CA1
    (who signed this certificate — the Certificate Authority)

  Validity:
    Not Before: 2024-01-01 00:00:00 UTC
    Not After:  2025-01-31 23:59:59 UTC
    (the certificate is only valid within this window)

  Subject: C=IN, ST=Karnataka, L=Bengaluru, O=Payment Corp Ltd,
           CN=api.payment.com
    (who this certificate is for)

  Subject Public Key Info:
    Algorithm: id-ecPublicKey (P-256)
    Public Key: 04:a1:b2:... (the server's public key — 65 bytes for P-256)

  Extensions (v3):
    Subject Alternative Name (SAN):
      DNS: api.payment.com
      DNS: *.payment.com
      (the actual domain names this cert is valid for — SAN overrides CN)

    Basic Constraints:
      CA: FALSE
      (this is an end-entity cert, not a CA — cannot sign other certs)

    Key Usage:
      Digital Signature, Key Encipherment
      (what operations the key is permitted for)

    Extended Key Usage:
      TLS Web Server Authentication (OID 1.3.6.1.5.5.7.3.1)
      (this cert is for TLS server use)

    Authority Information Access (AIA):
      OCSP: http://ocsp.digicert.com
      CA Issuers: http://cacerts.digicert.com/DigiCertTLSRSA...crt
      (where to check revocation status and download the CA cert)

    CRL Distribution Points:
      URI: http://crl3.digicert.com/DigiCertTLS...CA1.crl
      (alternative revocation mechanism — Certificate Revocation List)

    Certificate Transparency (CT) Logs:
      SCT List: [timestamps from CT log servers]
      (proof that this cert was submitted to public CT logs)

  Signature: 3a:4b:5c:... (signature over above fields, by Issuer's private key)
```

**Subject Alternative Name (SAN) vs Common Name (CN):**
Modern certificate validation uses the SAN extension, not the CN. If a SAN extension is present (required for any publicly trusted cert since 2017), the CN is ignored for hostname matching. Wildcard SANs (`*.payment.com`) match one label depth (`api.payment.com` but not `sub.api.payment.com`).

**Q9. What is the certificate chain of trust, and how does a client validate it?**
A: A single certificate is meaningless without trust — the client must verify that it was signed by someone it trusts. The certificate chain of trust is a hierarchy that links the server's certificate to a root CA that the client inherently trusts (because it's pre-installed in the OS or browser trust store):

```
Root CA Certificate (self-signed — trust anchor)
  └─ Intermediate CA Certificate (signed by Root CA)
       └─ Server (Leaf) Certificate (signed by Intermediate CA)
```

**Why three levels?**
Root CAs are extremely high-value targets — a compromised root CA can sign certificates for any domain, breaking the entire web's security. Root CA private keys are stored offline (air-gapped HSMs — Hardware Security Modules), never exposed to internet-connected systems. To issue certificates daily, Root CAs sign Intermediate CA certificates whose private keys can be kept online. If an Intermediate CA is compromised, only that intermediate's certificates need to be revoked — not the entire root.

**Certificate validation steps (what the TLS library does):**

**Step 1 — Build the chain:**
The server sends its leaf certificate and intermediate certificates (not the root — the client already has roots in its trust store). The client assembles the chain by matching each certificate's Issuer field to the next certificate's Subject field:
```
Server cert:    Subject=api.payment.com, Issuer=DigiCert TLS RSA SHA256 CA1
Intermediate:   Subject=DigiCert TLS RSA SHA256 CA1, Issuer=DigiCert Global Root CA
Root (in store):Subject=DigiCert Global Root CA, Issuer=DigiCert Global Root CA (self-signed)
```

**Step 2 — Verify each signature:**
Starting from the root and working down (or equivalently, starting from the leaf and working up):
- The root is self-signed — trusted because it's in the OS/browser trust store.
- Verify the intermediate's signature using the root's public key.
- Verify the leaf certificate's signature using the intermediate's public key.

Each `Signature` field is a digital signature over the certificate's `tbsCertificate` (to-be-signed certificate) data, created using the issuing CA's private key.

**Step 3 — Check validity period:**
Every certificate has `Not Before` and `Not After` dates. If the current time is outside this range, the certificate is invalid — even if all signatures check out. An expired certificate on a production server is one of the most common TLS failures in backend systems.

**Step 4 — Check the hostname (SNI match):**
The hostname in the connection request (from SNI or the URL) must match the SAN extension in the leaf certificate. Matching rules:
- `api.payment.com` matches `api.payment.com` exactly.
- `api.payment.com` matches `*.payment.com` (wildcard on the left label).
- `api.payment.com` does NOT match `*.com` (wildcard must cover only one label — public suffix rule).
- `sub.api.payment.com` does NOT match `*.payment.com` (wildcard covers only one label depth).

**Step 5 — Check revocation status:**
Certificates can be revoked before expiry (if the private key is compromised). Two mechanisms:
- **CRL (Certificate Revocation List):** A CA-signed list of serial numbers of revoked certificates. The client downloads the CRL from the URL in the cert's CRL Distribution Points extension. CRLs can be large and stale (published on a schedule).
- **OCSP (Online Certificate Status Protocol):** A real-time query to the OCSP Responder URL in the cert's AIA extension. The responder replies `good`, `revoked`, or `unknown` for a specific serial number. Latency concern: adds one more round trip per TLS connection.
- **OCSP Stapling:** The server queries OCSP at intervals, caches the signed OCSP response, and "staples" it to the TLS handshake (in the CertificateStatus message). The client verifies the stapled response — no additional round trip. The gold standard for revocation checking in TLS 1.2/1.3.

**Step 6 — Check Certificate Transparency (CT) logs:**
Modern browsers require that publicly trusted certificates be logged in public CT logs (RFC 6962). The certificate or the TLS handshake must include Signed Certificate Timestamps (SCTs) proving the certificate was submitted to at least two CT logs. This allows detection of mis-issued certificates (a CA issuing a cert for `google.com` without Google's knowledge would appear in public logs within 24 hours, allowing rapid detection and revocation).

**Q10. What happens when certificate validation fails, and what are the most common failure modes in production?**
A: Certificate validation failure aborts the TLS handshake. The client sends a `fatal` TLS alert (specific type depends on the failure), closes the connection, and the application receives an error. The most common production failures:

**Expired certificate:**
```
Error: certificate has expired or is not yet valid
Node.js: Error: CERT_HAS_EXPIRED
```
The `Not After` date has passed. Fix: renew before expiry. Automation: Let's Encrypt with `certbot renew` or ACM (AWS Certificate Manager, which auto-renews) eliminates manual renewals. Alert at 30 days remaining; hard deadline action at 7 days. In Node.js when connecting to a service:
```javascript
// Temporary bypass for testing ONLY — never in production
https.request({ rejectUnauthorized: false })
```
Never disable certificate validation in production. If the upstream service has an expired cert, contact the team to renew it.

**Hostname mismatch:**
```
Error: hostname/IP does not match certificate's altnames
Node.js: Error: ERR_TLS_CERT_ALTNAME_INVALID
```
The URL hostname doesn't match any SAN. Common causes: connecting by IP address when the cert has no IP SAN, using `localhost` when the cert is for `api.internal`, certificate issued for `www.payment.com` but the service is at `api.payment.com`.

**Unknown CA (self-signed or private CA):**
```
Error: self signed certificate in certificate chain
Node.js: Error: UNABLE_TO_VERIFY_LEAF_SIGNATURE / DEPTH_ZERO_SELF_SIGNED_CERT
```
The certificate chain leads to a root CA not in the client's trust store. Common in internal services using a private CA. Fix: distribute the private CA's root certificate to all clients:
```javascript
const fs   = require("fs");
const https = require("https");

https.request({
  ca: fs.readFileSync("/etc/ssl/certs/internal-ca.pem"), // add internal root CA
  // OR: use NODE_EXTRA_CA_CERTS=/etc/ssl/certs/internal-ca.pem environment variable
});
```
`NODE_EXTRA_CA_CERTS` is the cleanest solution — it adds CAs without replacing the built-in Mozilla CA bundle.

**Missing intermediate certificate:**
```
Error: unable to get local issuer certificate
```
The server sent only its leaf certificate without the intermediate. The client cannot build the chain. Fix: configure the server to send the complete chain (leaf + intermediates). In Nginx: `ssl_certificate` should point to a file containing both the leaf and intermediate certs concatenated. Test with:
```bash
openssl s_client -connect api.payment.com:443 -showcerts 2>/dev/null | \
  grep -E "s:|i:" 
# Should show three levels: leaf, intermediate, root
```

**Certificate pinning mismatch:**
The client is pinned to a specific certificate or public key hash, and the server rotated its certificate. Certificate pinning is rare for backend services but common in mobile apps. Not a TLS standard behaviour — an application-level policy implemented on top of TLS validation.

## Section 5: Server Name Indication (SNI)

**Q11. What is SNI, and what problem does it solve?**
A: SNI (Server Name Indication) is a TLS extension that allows the client to specify which hostname it is connecting to during the TLS handshake — before the server presents its certificate.

**The problem SNI solves:**
A server may host many domains on the same IP address (virtual hosting — standard in cloud deployments). Before SNI, the server had to choose which certificate to present before knowing which domain the client wanted. If `api.payment.com` and `api.lending.com` both resolve to the same IP, the server couldn't know which certificate to send. Options without SNI:
- One IP address per domain (not scalable at internet scale — IPv4 addresses are scarce).
- A single wildcard or multi-SAN certificate covering all domains (complex, security concern — compromise exposes all domains).
- Send a default certificate and hope (works only if the client isn't strict).

**How SNI works:**
The client includes the `server_name` extension in the ClientHello with the hostname it intends to connect to:
```
ClientHello:
  Extensions:
    server_name: "api.payment.com"  ← SNI extension
```

The server reads this extension before selecting a certificate — it uses the hostname to choose the correct certificate from its collection:
```
Server receives ClientHello:
  → reads SNI: "api.payment.com"
  → selects certificate for "api.payment.com"
  → proceeds with handshake presenting that certificate
```

In Nginx: `server_name api.payment.com;` in a server block — SNI routes to the matching block. In Node.js `tls.createServer()`:
```javascript
const tls  = require("tls");
const fs   = require("fs");

const server = tls.createServer({
  SNICallback: (serverName, callback) => {
    // Called with the SNI hostname; return the matching context
    if (serverName === "api.payment.com") {
      callback(null, tls.createSecureContext({
        key:  fs.readFileSync("./certs/payment.key"),
        cert: fs.readFileSync("./certs/payment.crt"),
      }));
    } else if (serverName === "api.lending.com") {
      callback(null, tls.createSecureContext({
        key:  fs.readFileSync("./certs/lending.key"),
        cert: fs.readFileSync("./certs/lending.crt"),
      }));
    } else {
      callback(new Error(`No certificate for ${serverName}`));
    }
  },
});
```

**Q12. What is Encrypted Client Hello (ECH), and why does SNI's plaintext leak matter?**
A: Standard SNI is sent in plaintext — in the ClientHello, before any encryption is established. A network observer (ISP, network firewall, a government-level deep packet inspection system) can see the SNI hostname even though the subsequent HTTP request and response are encrypted:

```
Network observer sees in ClientHello (plaintext):
  server_name: "api.censored-site.com"
  [All subsequent data is encrypted — observer cannot see request body or path]
```

This leaks the hostname — revealing which services a client is connecting to, which may itself be sensitive information (connecting to a mental health platform, a legal advice service, a political organisation's API).

**Encrypted Client Hello (ECH, RFC draft):** ECH encrypts the "inner" ClientHello (containing the real SNI) using a public key published in the domain's DNS record. The "outer" ClientHello contains a fake SNI (typically the ECH service provider's generic domain) and the encrypted inner ClientHello:

```
Outer ClientHello (visible to observer):
  server_name: "cloudflare-ech.com" (generic cover)
  encrypted_client_hello: [encrypted inner hello]

Inner ClientHello (decryptable only by the server with the ECH private key):
  server_name: "api.payment.com" (real target)
  [cipher suites, key shares, etc.]
```

The network observer only sees the outer ClientHello with the cover domain — the real destination is hidden. ECH is available in Chrome, Firefox, and Cloudflare supports it for domains behind their CDN. It is not yet universally deployed (2024).

**SNI-based routing in load balancers:**
The plaintext SNI is used by TLS-passthrough load balancers to route to the correct backend without terminating TLS — the load balancer reads SNI without decrypting the connection:

```
Client → NLB (TLS passthrough):
  Client sends ClientHello with SNI: "api.payment.com"
  NLB reads SNI (plaintext) → routes to PaymentService backend
  [NLB never decrypts — the backend handles TLS]

vs.

Client → ALB (TLS termination):
  ALB terminates TLS (decrypts)
  ALB routes based on Host header in HTTP request
  ALB establishes new TLS to backend
```

SNI-based routing enables TLS passthrough at the load balancer level — the end-to-end encrypted connection goes directly to the application server. This is used when the load balancer should not see the plaintext (e.g., mTLS between client and backend, or when end-to-end certificate validation is required).

**Q13. What happens when SNI is absent or mismatched?**
A: SNI absence is increasingly unusual — all modern TLS clients send SNI. But absence and mismatch both cause well-defined server behaviour:

**SNI absent:**
The server has no hint about which certificate to present. It falls back to a default certificate (the first configured `ssl_certificate` in Nginx, or the default context in Node.js `tls.createServer`). If the client's target hostname doesn't match the default certificate's SAN, certificate validation fails on the client side — the client receives a hostname mismatch error.

Modern context: all major browsers and HTTP clients send SNI. SNI absence typically indicates very old clients (IE 6, Windows XP before SP3, some embedded devices) or programmatic clients with misconfigured TLS. In AWS ALB, SNI absence causes the ALB to send its default certificate (configured in the HTTPS listener's default action).

**SNI present but no matching certificate:**
If a server receives an SNI for a hostname it has no certificate for, it may:
- Send the default certificate (client will likely get a mismatch error).
- Send a `TLS unrecognised_name` alert and close the connection (RFC 6066 allows this).
- In Nginx: returns a 421 Misdirected Request if the client reaches the wrong server block.

```bash
# Test what certificate a server returns for a specific SNI
openssl s_client -connect 10.0.1.45:443 -servername api.payment.com 2>/dev/null | \
  openssl x509 -noout -subject -issuer -dates
# If SNI is not specified, openssl uses the IP — server may return default cert
```

## Section 6: Mutual TLS (mTLS)

**Q14. What is mutual TLS (mTLS), and when is it used in backend systems?**
A: Standard TLS authenticates only the server — the client validates the server's certificate but not vice versa. Mutual TLS (mTLS) adds client authentication — the server also validates a certificate presented by the client. Both sides authenticate each other:

**mTLS handshake additions (TLS 1.2 example):**
```
Standard TLS:                    Mutual TLS additions:
Server → Client: Certificate     Same
                                 Server → Client: CertificateRequest
                                   (list of acceptable CA DNs)
Client → Server: (nothing)       Client → Server: Certificate
                                   (client's certificate)
                                 Client → Server: CertificateVerify
                                   (signature proving key possession)
```

In TLS 1.3, the server sends `CertificateRequest` in the encrypted handshake (after `EncryptedExtensions`), and the client responds with its Certificate and CertificateVerify — also encrypted.

**When mTLS is used:**

**Service-to-service authentication in microservices (zero-trust networks):**
In a zero-trust architecture, services cannot trust that network position (being on the internal VPC) means authentication. mTLS ensures that the PaymentService knows it's talking to the genuinely authenticated BREService — not a rogue process that somehow gained network access. Service meshes (Istio, Linkerd, Consul Connect) automate mTLS between services — each service gets a certificate from an internal CA (SPIFFE/SPIRE), and the sidecar proxy (Envoy) handles mTLS transparently.

**API authentication for machine-to-machine (M2M) clients:**
Payment gateways (JusPay, Razorpay) offer mTLS as an alternative to API keys. The merchant registers a client certificate with the gateway; subsequent API calls present this certificate. The gateway validates it without any shared secret — the private key never leaves the merchant's systems.

**Bank and regulatory APIs:**
The RBI's Account Aggregator framework, NPCI's payment APIs, and SWIFT API connections commonly require mTLS. Financial regulators mandate client certificates for API access to ensure that only authorised entities (registered banks, NBFCs) can call the API.

```javascript
// Node.js: making an mTLS request (client presents certificate)
const https = require("https");
const fs    = require("fs");

const agent = new https.Agent({
  cert: fs.readFileSync("./certs/client.crt"),  // client certificate
  key:  fs.readFileSync("./certs/client.key"),  // client private key
  ca:   fs.readFileSync("./certs/server-ca.crt"), // server's CA for validation
});

https.request({
  hostname: "api.bank.com",
  path:     "/v1/payments",
  method:   "POST",
  agent,    // agent carries the client cert for mTLS
}, (res) => {
  // ...
});

// Node.js: NestJS / Express mTLS server
const server = https.createServer({
  key:                fs.readFileSync("./certs/server.key"),
  cert:               fs.readFileSync("./certs/server.crt"),
  ca:                 fs.readFileSync("./certs/client-ca.crt"), // CA that signed client certs
  requestCert:        true,   // request client certificate
  rejectUnauthorized: true,   // reject if client cert is invalid
}, app);

// In Express middleware: access the verified client cert
app.use((req, res, next) => {
  const clientCert = req.socket.getPeerCertificate();
  if (!clientCert || !clientCert.subject) {
    return res.status(401).json({ error: "Client certificate required" });
  }
  // Extract identity from cert
  req.clientId = clientCert.subject.CN;  // e.g., "razorpay-merchant-001"
  next();
});
```

## Section 7: Certificate Lifecycle and Operational Concerns

**Q15. How does Let's Encrypt work, and what makes automated certificate management critical?**
A: Let's Encrypt is a free, automated CA that issues Domain Validated (DV) certificates with a 90-day validity period. Its automation is the key innovation — the ACME (Automated Certificate Management Environment) protocol replaces the manual CSR submission, email verification, and document review process of traditional CAs with a fully automated challenge-response system:

**ACME HTTP-01 challenge:**
```
1. Client (certbot/acme.sh/node's @acmejs) generates a key pair and CSR
2. Client registers with Let's Encrypt ACME server

3. Client asks Let's Encrypt to validate control of "api.payment.com"

4. Let's Encrypt issues a challenge:
   "Serve this token at http://api.payment.com/.well-known/acme-challenge/<token>"
   Expected content: "<token>.<account_key_thumbprint>"

5. Client creates the challenge response file at that path

6. Let's Encrypt fetches http://api.payment.com/.well-known/acme-challenge/<token>
   → Validates content matches expected response
   → Domain control confirmed

7. Let's Encrypt issues the certificate (valid for 90 days)
   → Signed by Let's Encrypt's intermediate CA
   → Client downloads and installs it
```

**ACME DNS-01 challenge:** Proves domain control by creating a TXT record `_acme-challenge.api.payment.com` in DNS. Required for wildcard certificates (`*.payment.com`) and for domains where HTTP challenge is impractical (internal services not publicly accessible).

**Why 90 days?**
Short-lived certificates reduce the window of exposure if a private key is compromised — a stolen key can be used for at most 90 days. They force automation (no sane team manually renews certificates every 90 days for every service) and incentivise infrastructure to support rapid rotation. The industry trend is toward even shorter lifetimes: 47-day certs are proposed (2024); some internal PKIs issue 24-hour certificates.

**Operational checklist for certificate management:**
```bash
# Check expiry of a running certificate
echo | openssl s_client -connect api.payment.com:443 2>/dev/null | \
  openssl x509 -noout -dates

# Check local certificate file expiry
openssl x509 -in /etc/ssl/certs/api.payment.com.crt -noout -dates

# Verify certificate chain is complete
openssl verify -CAfile /etc/ssl/certs/ca-bundle.crt \
  -untrusted intermediate.crt leaf.crt

# Test the full TLS handshake
curl -v --tlsv1.3 https://api.payment.com/health 2>&1 | \
  grep -E "TLS|certificate|expire"
```

**Node.js certificate expiry monitoring:**
```javascript
import tls from "tls";

function checkCertExpiry(host: string, port = 443): Promise<Date> {
  return new Promise((resolve, reject) => {
    const socket = tls.connect({ host, port, servername: host }, () => {
      const cert    = socket.getPeerCertificate();
      const expiry  = new Date(cert.valid_to);
      const daysLeft = (expiry.getTime() - Date.now()) / 86_400_000;

      socket.destroy();

      if (daysLeft < 14) {
        console.error(`ALERT: cert for ${host} expires in ${daysLeft.toFixed(0)} days`);
      }

      resolve(expiry);
    });
    socket.on("error", reject);
  });
}

// Run as a health check or scheduled job
checkCertExpiry("api.payment.com");
```

**Q16. What is HSTS, and how does it relate to HTTPS?**
A: HSTS (HTTP Strict Transport Security, RFC 6797) is an HTTP response header that instructs browsers (and HTTPS clients that support it) to always use HTTPS for a domain — even if the user types `http://` or a link is `http://`:

```
HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

**What each directive does:**
- `max-age=31536000`: For the next 31,536,000 seconds (1 year), the browser will not make plain HTTP connections to this domain — it automatically upgrades to HTTPS. If the server is unavailable over HTTPS, the browser will not fall back to HTTP.
- `includeSubDomains`: The HSTS policy applies to all subdomains (`*.payment.com`). If any subdomain uses HTTP, the browser will refuse to connect.
- `preload`: The domain has been submitted to browser preload lists (shipped in browsers). Even on first visit (before any HSTS header has been received), the browser uses HTTPS. Provides protection from the "first visit" attack (an attacker intercepts the first HTTP request before HSTS is established). Requires `includeSubDomains`.

**HSTS in Node.js / NestJS:**
```javascript
// Helmet middleware adds HSTS automatically
import helmet from "helmet";

app.use(helmet({
  hsts: {
    maxAge:            31_536_000,
    includeSubDomains: true,
    preload:           true,
  },
}));
```

**HSTS pitfall:** Once HSTS is set with a long `max-age`, it is very difficult to revert to HTTP — all clients that have seen the header refuse HTTP for the duration of `max-age`. If HTTPS is ever disrupted (certificate expires, misconfiguration), clients cannot fall back to HTTP to access the site. Always test HSTS on a non-production domain first, and start with a short `max-age` (300 seconds) before incrementally increasing.

## Section 8: Scenario / System Design Style Questions

**Q17. "A Node.js service makes HTTPS calls to an internal payment gateway and intermittently gets ECONNRESET. After investigation, you find TLS handshakes are timing out. Walk through the diagnostic process."**
A: TLS handshake timeouts have a specific set of causes that differ from general TCP connection issues. Work through them systematically:

**Step 1 — Confirm it's TLS-specific, not TCP:**
```bash
# Can we establish TCP at all?
nc -zv internal-gateway.svc 443         # TCP connect probe — no TLS

# Does TLS handshake succeed from this machine?
openssl s_client -connect internal-gateway.svc:443 \
  -servername internal-gateway.svc      # full TLS handshake
# If this hangs: TLS handshake issue
# If this succeeds: issue is in Node.js TLS configuration
```

**Step 2 — Certificate chain issues:**
```bash
openssl s_client -connect internal-gateway.svc:443 \
  -servername internal-gateway.svc \
  -showcerts 2>/dev/null

# Look for:
# - Verify return code: 0 (ok) — chain validates correctly
# - "verify error:num=20:unable to get local issuer certificate" — missing intermediate
# - "verify error:num=10:certificate has expired" — expired cert
# - Certificate chain should show 3 levels (leaf, intermediate, root)
```

**Step 3 — OCSP stapling check:**
Some TLS implementations wait for OCSP responses before completing the handshake. If the OCSP responder is unreachable from this network:
```bash
openssl s_client -connect internal-gateway.svc:443 \
  -status 2>/dev/null | grep -A 3 "OCSP response"
# "OCSP Response Status: successful" — stapling working
# "No OCSP response received" — server not stapling; client may be fetching directly
```

If OCSP stapling is absent and the client tries to do its own OCSP check but the OCSP server is unreachable from within the VPC (internal services often can't reach external OCSP servers), the check times out. Fix: enable OCSP stapling on the server, or configure Node.js to skip OCSP:
```javascript
// Disable OCSP check (acceptable for internal mTLS where CA is known)
process.env.NODE_TLS_REJECT_UNAUTHORIZED = "0"; // NEVER in production
// The correct approach: configure ca: with the internal CA
```

**Step 4 — Certificate mismatch with SNI:**
The service may be connecting by internal hostname (`internal-gateway.svc`) but the certificate covers only the public hostname. Check:
```bash
openssl s_client -connect 10.0.1.45:443 -servername internal-gateway.svc 2>/dev/null | \
  openssl x509 -noout -text | grep -A 3 "Subject Alternative"
```

**Step 5 — TLS version mismatch:**
The gateway may only support TLS 1.3 but the Node.js version or configuration uses TLS 1.2 maximum:
```javascript
// Node.js: specify TLS version range
https.request({
  minVersion: "TLSv1.2",
  maxVersion: "TLSv1.3",
});
```

**Step 6 — mTLS client certificate required but not provided:**
The gateway requires client certificates but Node.js isn't providing one — the server sends a `CertificateRequest`, Node.js sends an empty Certificate message, the server rejects with `certificate_required` or `bad_certificate`:
```javascript
// Fix: provide client certificate in the agent
const agent = new https.Agent({
  cert: fs.readFileSync("./certs/client.crt"),
  key:  fs.readFileSync("./certs/client.key"),
});
```

**Q18. "You're designing the TLS architecture for a fintech platform that must meet PCI DSS requirements and serve both public API clients and internal microservices. What are the key decisions?"**
A: Five architectural decisions with TLS implications:

**Decision 1 — TLS termination point:**
For public API: terminate TLS at the AWS ALB. The ALB handles certificate renewal (ACM), cipher suite negotiation, and HSTS headers. Backend-to-ALB is also TLS (ALB supports end-to-end encryption). For PCI DSS: the ALB must be in-scope (its TLS configuration is audited).

For internal microservices: use a service mesh (Istio) with automatic mTLS between all services. The mesh issues short-lived certificates (SPIFFE SVIDs — 1 hour TTL) from an internal CA (SPIRE). No human manages these certificates — fully automated. Every service-to-service call is mutually authenticated with no shared secrets or API keys.

**Decision 2 — Minimum TLS version:**
PCI DSS 4.0 requires TLS 1.2+ (TLS 1.0 and 1.1 explicitly prohibited). Configure:
```nginx
ssl_protocols TLSv1.2 TLSv1.3;  # TLS 1.3 preferred; 1.2 as fallback
ssl_prefer_server_ciphers on;
ssl_ciphers 'ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:...';
# Reject: SSLv2, SSLv3, TLSv1.0, TLSv1.1, RC4, DES, 3DES, NULL, EXPORT
```

**Decision 3 — Certificate type for public API:**
Use an OV (Organisation Validated) or EV (Extended Validation) certificate for the public API — provides organisational identity in addition to domain control. DV (Domain Validated, e.g., Let's Encrypt) is sufficient for encryption but provides weaker identity assurance for a payment API clients may want to inspect.

**Decision 4 — Certificate issuance for internal services:**
Use a private CA (AWS Private CA, Vault PKI, or SPIRE) for internal certificates. Do NOT use public CAs for internal service certificates — they're unnecessary (no public trust needed), expensive at scale (hundreds of services), and introduce operational complexity (ACME HTTP-01 challenge requires publicly accessible services).

**Decision 5 — OCSP stapling and revocation:**
For public-facing services: enable OCSP stapling. Configure Nginx/Node.js to cache and staple OCSP responses. For internal services with short-lived certificates (1-hour SPIFFE SVIDs): revocation is irrelevant — by the time revocation information propagates, the certificate has expired. This is a key reason short-lived certificates are preferred in zero-trust environments.

**Q19. "Explain what happens when `https://api.payment.com` redirects to itself but the redirect produces a certificate warning in the browser. What is the likely cause?"**
A: This is a classic misconfiguration with a few possible causes. The scenario: browser shows a padlock broken or certificate warning on `https://api.payment.com`, but the service is running:

**Cause 1 — Mixed content redirect (unlikely to produce a cert warning, but related):**
The page serves over HTTPS but includes HTTP resources. Not a certificate issue — a mixed content warning.

**Cause 2 — Self-signed or expired certificate:**
The most common cause. The server's certificate is self-signed (no CA signature — trust store doesn't recognise it) or expired. The browser shows "Your connection is not private." Test:
```bash
curl -I https://api.payment.com 2>&1 | head -20
# If output shows: "SSL certificate problem: certificate has expired"
# Or: "SSL certificate problem: self signed certificate"
```

**Cause 3 — Wrong certificate returned (SNI mismatch):**
The load balancer or reverse proxy isn't routing SNI correctly and returns the default certificate — which covers a different domain. The browser receives a certificate for `*.other-domain.com` when it requested `api.payment.com`. Certificate warning: hostname mismatch.
```bash
openssl s_client -connect api.payment.com:443 -servername api.payment.com 2>/dev/null | \
  openssl x509 -noout -subject
# If subject shows a different domain: SNI routing misconfiguration
```

**Cause 4 — Missing intermediate certificate:**
The server's TLS configuration (`ssl_certificate` in Nginx) points to only the leaf certificate, not the full chain. Modern browsers can sometimes fetch the intermediate via AIA (Authority Information Access) in the certificate — but curl and some older clients cannot. The browser shows an "incomplete chain" warning:
```bash
# Fix: concatenate leaf + intermediate in the cert file
cat api.payment.com.crt intermediate.crt > api.payment.com.chain.crt
# In Nginx: ssl_certificate /etc/nginx/ssl/api.payment.com.chain.crt;
```

**Cause 5 — Certificate pinning mismatch in a mobile app:**
If this is observed in a mobile app rather than a browser, the app has a pinned certificate (public key hash) that no longer matches the current certificate (after a rotation). The app rejects the new certificate even though it's CA-valid. Fix: update the pin in the app, or use pin-sets that include the backup key.

## Quick Reference: TLS Cheat Sheet

```
TLS 1.2 handshake:    2 RTT (ClientHello → ServerHello+Cert+SHD → CKE+CCS+Fin → CCS+Fin)
TLS 1.3 handshake:    1 RTT (ClientHello+KeyShare → SH+EE+Cert+CV+Fin → Fin)
TLS 1.3 0-RTT:        0 RTT (ClientHello+EarlyData → ... → use for idempotent only)

Key exchange:
  ECDHE (x25519, P-256) → forward secrecy → required for TLS 1.3
  RSA key exchange       → no forward secrecy → removed in TLS 1.3

Cipher suites (TLS 1.3, all mandatory AEAD + forward secrecy):
  TLS_AES_256_GCM_SHA384
  TLS_AES_128_GCM_SHA256
  TLS_CHACHA20_POLY1305_SHA256

Certificate chain:
  Root CA (in trust store) → Intermediate CA → Leaf cert (server)
  Server sends: leaf + intermediates (never the root — client has it)

Certificate validation steps:
  1. Build chain (Issuer → Subject matching)
  2. Verify signatures (Root → Intermediate → Leaf)
  3. Check validity period (Not Before / Not After)
  4. Check hostname (SAN match, not CN)
  5. Check revocation (OCSP stapling preferred; CRL fallback)
  6. Check CT logs (SCTs in cert or TLS extension)

SNI:
  - Sent in plaintext in ClientHello (visible to observers)
  - Allows multiple virtual-hosted TLS domains on one IP
  - Used by L4 load balancers for TLS passthrough routing
  - ECH (Encrypted Client Hello) encrypts SNI — draft standard

Common Node.js TLS options:
  ca:                    additional CA certificates (internal CA)
  cert + key:            client certificate for mTLS
  rejectUnauthorized:    true (always in production)
  minVersion:            "TLSv1.2"
  servername:            SNI hostname (for non-matching hostnames)
  NODE_EXTRA_CA_CERTS:   environment variable for additional CAs

Common TLS errors:
  CERT_HAS_EXPIRED            → certificate past Not After date
  ERR_TLS_CERT_ALTNAME_INVALID → hostname not in SANs
  UNABLE_TO_VERIFY_LEAF_SIGNATURE → CA not in trust store
  DEPTH_ZERO_SELF_SIGNED_CERT → self-signed leaf cert
  certificate verify failed   → general chain validation failure

Diagnostic commands:
  openssl s_client -connect host:443 -servername host
  openssl x509 -in cert.crt -noout -text
  openssl verify -CAfile ca-bundle.crt -untrusted intermediate.crt leaf.crt
  curl -v --tlsv1.3 https://host/path
```
