# Networking / Computer Science: HTTP/2 — Multiplexing, Server Push, HPACK Header Compression, Binary Framing — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problems does HTTP/2 solve that HTTP/1.1 could not?**
A: HTTP/2 was designed around a specific set of pathologies that HTTP/1.1 created or could not solve, all rooted in the fact that HTTP/1.1 is a textual, request-response protocol where one request occupies a connection until it completes:

- **Head-of-line (HOL) blocking** — in HTTP/1.1, requests on a single connection are processed in order. If a large resource stalls (slow server, large response), every subsequent request queues behind it regardless of how small or ready those responses are. Browsers worked around this by opening 6–8 parallel TCP connections per origin — an expensive hack.
- **Connection overhead** — 6–8 TCP connections per origin × 3-way handshake × TLS handshake × slow start per connection = enormous latency and bandwidth waste before any useful data flows. On mobile networks with 100–200ms RTT, this overhead dominates page load time.
- **Redundant headers** — HTTP/1.1 sends full headers on every request. A browser making 80 requests to load a page sends `Cookie`, `User-Agent`, `Accept`, `Accept-Encoding`, and `Authorization` on every single one — often 500–2000 bytes of headers per request that haven't changed since the last request.
- **No server initiative** — in HTTP/1.1, the server can only respond to requests; it cannot push resources the client will predictably need. The client must discover dependencies (CSS, JS, images referenced in HTML) by parsing the response and making additional round trips.
- **Inefficient text encoding** — HTTP/1.1 headers are ASCII text, parsed character by character. Status lines, header names, and header values are human-readable but computationally expensive to parse at scale.

HTTP/2 addresses all five with binary framing, multiplexing, HPACK compression, and server push — keeping HTTP semantics (methods, status codes, headers) identical while replacing the wire format entirely.

**Q2. What is the relationship between HTTP/2 and TLS? Is TLS required?**
A: HTTP/2 does not technically require TLS — the specification (RFC 7540) defines two connection schemes:
- **h2** — HTTP/2 over TLS (negotiated via ALPN, Application-Layer Protocol Negotiation, in the TLS handshake).
- **h2c** — HTTP/2 over cleartext TCP (via HTTP Upgrade mechanism or direct connection with prior knowledge).

In practice, every major browser (Chrome, Firefox, Safari, Edge) only implements HTTP/2 over TLS. `h2c` is supported for server-to-server communication, gRPC over cleartext, and internal service meshes, but browser-facing HTTP/2 is always encrypted. The reasoning: the `ALPN` extension in TLS is the cleanest negotiation mechanism; `h2c` requires an additional round trip for the HTTP Upgrade handshake; and shipping HTTP/2 only over TLS was the political compromise that got browser vendors to implement it.

**ALPN negotiation:**
```
TLS ClientHello → extension: ALPN = ["h2", "http/1.1"]  (client supports both)
TLS ServerHello → extension: ALPN = "h2"                (server selects HTTP/2)
```
The protocol is selected during the TLS handshake at no additional round-trip cost.

**Q3. How does an HTTP/2 connection start, and what is the connection preface?**
A: After the TLS handshake completes with ALPN selecting "h2", both sides exchange a **connection preface** — a fixed preamble that confirms both sides speak HTTP/2 and establishes initial settings:

**Client connection preface:**
```
PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n
```
This 24-byte magic string (chosen to be an invalid HTTP/1.1 request) is sent immediately, followed by a `SETTINGS` frame. Any server that doesn't understand HTTP/2 will reject it immediately, preventing protocol confusion.

**Server connection preface:**
A `SETTINGS` frame (possibly empty) sent immediately after the TLS handshake. The client must respond with a `SETTINGS` ACK.

After the preface exchange, both sides send their initial `SETTINGS` frames containing parameters like `HEADER_TABLE_SIZE`, `MAX_CONCURRENT_STREAMS`, `INITIAL_WINDOW_SIZE`, and `MAX_FRAME_SIZE`. The connection is then ready for streams.

## Section 2: Binary Framing

**Q4. What is binary framing, and how does it differ from HTTP/1.1's text format?**
A: HTTP/1.1 is a text protocol — requests and responses are sequences of ASCII characters with newlines as delimiters:

```
GET /index.html HTTP/1.1\r\n
Host: example.com\r\n
Accept: text/html\r\n
\r\n
```

Parsing this requires scanning byte-by-byte for `\r\n` delimiters, handling whitespace, and interpreting ASCII numbers as integers. It is flexible and human-readable but slow to parse and impossible to process out of order (you can't know where the headers end until you find the blank line).

HTTP/2 replaces this with a **binary framing layer** — all communication is a sequence of fixed-format binary frames. Every frame begins with a 9-byte header:

```
Binary frame structure:
┌─────────────────────────────────────────────────────┐
│ Length (24 bits): payload size in bytes (0–16383)   │
│ Type   (8 bits):  DATA, HEADERS, SETTINGS, etc.     │
│ Flags  (8 bits):  END_STREAM, END_HEADERS, PADDED…  │
│ Reserved (1 bit): must be 0                         │
│ Stream Identifier (31 bits): which stream this is   │
├─────────────────────────────────────────────────────┤
│ Payload (variable, 0 to Length bytes)               │
└─────────────────────────────────────────────────────┘
```

Advantages of binary framing:
- **No parsing ambiguity** — the frame length field tells you exactly where this frame ends; no delimiter scanning needed.
- **Efficient integer encoding** — numbers are native binary, not ASCII digits.
- **Multiplexing-ready** — the stream identifier in every frame is what enables multiple concurrent streams on one connection; each frame is self-describing about which stream it belongs to.
- **Extensibility** — new frame types can be added without breaking old implementations (unknown frame types are ignored).
- **Faster parsing** — modern benchmarks show HTTP/2 header parsing 30–50% faster than HTTP/1.1 despite the addition of HPACK decompression, because binary parsing avoids character-by-character scanning.

**Q5. What are the main HTTP/2 frame types, and what is each used for?**
A: HTTP/2 defines ten frame types in the base specification:

```
DATA         (0x0)  — carries request or response body payload
HEADERS      (0x1)  — carries HTTP headers (request or response), HPACK-compressed
PRIORITY     (0x2)  — sets stream priority/dependency (deprecated in HTTP/3)
RST_STREAM   (0x3)  — immediately terminates a stream (error or cancellation)
SETTINGS     (0x4)  — connection-level configuration parameters
PUSH_PROMISE (0x5)  — server announces a pushed resource (before sending it)
PING         (0x6)  — round-trip measurement and keepalive
GOAWAY       (0x7)  — graceful connection shutdown; reports last processed stream ID
WINDOW_UPDATE(0x8)  — increases flow control window (stream or connection level)
CONTINUATION (0x9)  — continuation of a HEADERS block if it doesn't fit in one frame
```

**Frame lifecycle for a typical request-response:**
```
Client → Server: HEADERS frame (END_HEADERS flag)          [request headers]
Client → Server: DATA frame(s) (END_STREAM on last)        [request body, if any]
Server → Client: HEADERS frame (END_HEADERS flag)          [response headers]
Server → Client: DATA frame(s) (END_STREAM on last one)    [response body]
```

`END_STREAM` on a frame signals the half-close of that direction — equivalent to TCP's FIN for a stream. A bare `HEADERS` frame with `END_STREAM` set (no `DATA` frames following) represents a request with no body (GET, HEAD) or a response with no body (204, 304).

**Q6. What is a stream in HTTP/2, and how does stream state work?**
A: A stream is a bidirectional sequence of frames within a single TCP connection. Each stream carries one request-response exchange. Streams are identified by a 31-bit integer — client-initiated streams use odd numbers (1, 3, 5, …); server-initiated push streams use even numbers (2, 4, 6, …). Stream 0 is reserved for connection-level frames (SETTINGS, PING, GOAWAY).

Stream state machine (simplified):
```
          open
         ╱    ╲
idle → half-closed (local) → closed
         ╲    ╱
          half-closed (remote)
```

- **idle** — the stream ID has been allocated but no frames sent yet.
- **open** — both sides can send frames; both sides are sending.
- **half-closed (local)** — the local side sent `END_STREAM`; it can no longer send DATA or HEADERS but can still receive.
- **half-closed (remote)** — the remote side sent `END_STREAM`; the local side can still send.
- **closed** — both sides have sent `END_STREAM` or a `RST_STREAM` was sent/received. Stream ID is retired.

Stream IDs are never reused within a connection. Once stream 1 closes, the next client-initiated stream is stream 3. The 31-bit space (over 1 billion values) is sufficient for the lifetime of any reasonable connection.

## Section 3: Multiplexing

**Q7. What is HTTP/2 multiplexing, and how does it eliminate HTTP/1.1 head-of-line blocking?**
A: Multiplexing means multiple streams coexist simultaneously on a single TCP connection. Frames from different streams are interleaved on the wire; the receiver uses the stream identifier in each frame header to reconstruct each stream independently.

```
HTTP/1.1 (one request at a time per connection):
Connection:  [Request 1 ──────────────────] [Request 2 ──] [Request 3 ────────────]
             ← HOL blocked waiting for R1 →

HTTP/2 (multiplexed streams on one connection):
Stream 1:    [H][D][D][D][D][D][D][D][D]  (large image)
Stream 3:    [H][D]                        (small CSS)
Stream 5:    [H][D][D]                     (medium JS)

Wire:  H1 H3 D3 H5 D5 D5 D1 D1 D1 D1 D1 D1 D1 D1 D1   (interleaved)
       ↑  ↑  ↑  ↑  ↑  ↑  ↑
       All streams progress simultaneously
```

The stream 3 response (small CSS) completes quickly even though stream 1 (large image) is still in progress. In HTTP/1.1, the CSS request would have to queue behind the image request on the same connection, or require a second connection.

**The critical nuance**: HTTP/2 eliminates application-layer HOL blocking (one HTTP request blocking others), but it does NOT eliminate TCP-layer HOL blocking. If a TCP segment carrying HTTP/2 data is lost, the entire connection stalls while TCP retransmits — all streams on the connection wait, even those whose data has already arrived out of order in the network stack. This TCP-level HOL blocking is the primary motivation for HTTP/3's switch to QUIC (which implements per-stream reliability at the transport layer, so a lost packet only stalls the stream it belongs to).

**Q8. How does HTTP/2 handle stream prioritization?**
A: HTTP/2 allows clients to express relative priorities between streams using a **dependency tree** and **weight values**. This lets the browser tell the server: "send the CSS and JS (render-blocking) before the images (below the fold)."

Each stream has:
- **Dependency**: which stream it depends on (default: stream 0, the root).
- **Weight**: 1–256, indicating relative share of bandwidth among siblings.

```
Stream dependency tree example:
        Stream 0 (root)
       /              \
  Stream 1            Stream 3
  (HTML, w=16)        (images, w=16)
      |
  Stream 5
  (CSS, w=32)   ← Stream 5 depends on Stream 1; must wait for 1 to complete(ish)
```

Servers are not required to honor priorities — they are hints, not mandates. In practice, priority implementation in servers has been inconsistent. Chrome removed explicit stream priority in HTTP/2 in 2022, moving priority signaling to the `Priority` HTTP header (RFC 9218 — Extensible Prioritization Scheme for HTTP) which works across HTTP versions. HTTP/3 deprecated the dependency-tree model entirely, replacing it with a simpler urgency + incremental flag scheme.

**Q9. What is the maximum number of concurrent streams, and what happens when the limit is hit?**
A: The `MAX_CONCURRENT_STREAMS` setting (in the SETTINGS frame) controls the maximum number of streams the sender will allow the receiver to open simultaneously. The default is unlimited if not set, but servers typically set it to 100–200. Chrome uses 100 as its default.

When the client wants to open a new stream but the server's `MAX_CONCURRENT_STREAMS` is already saturated:
- The client must wait until an existing stream closes before opening a new one.
- This is the HTTP/2 equivalent of connection pool exhaustion — application-level queuing replaces connection creation.
- Streams in the `idle` state (allocated ID but not yet sent) still count against the limit in some implementations.

A server can dynamically change `MAX_CONCURRENT_STREAMS` by sending a new SETTINGS frame during the connection. This is used for graceful load shedding: a server under load reduces the limit, causing clients to queue rather than creating new connections.

**Q10. How does HTTP/2 flow control differ from TCP flow control?**
A: HTTP/2 implements its own flow control *on top of* TCP's flow control, operating at two levels simultaneously:

- **Stream-level flow control** — each stream has its own receive window (`INITIAL_WINDOW_SIZE`, default 65,535 bytes). The sender may not send more than the window allows on that stream. When the receiver processes data and frees buffer space, it sends a `WINDOW_UPDATE` frame for that stream to grant more credit.
- **Connection-level flow control** — the connection as a whole has a window (also `INITIAL_WINDOW_SIZE` by default). A `WINDOW_UPDATE` with stream ID 0 updates the connection window. All stream windows together are also bounded by the connection window.

```
Actual bytes sendable on stream S = min(stream_window[S], connection_window)
```

Why HTTP/2 needs its own flow control when TCP already has it:

TCP flow control manages the rate between TCP endpoints — it prevents the sender's kernel send buffer from overflowing the receiver's kernel receive buffer. It has no concept of streams. HTTP/2 flow control manages at the application layer — it prevents a single fast-producing stream from starving all other streams on the connection by consuming the TCP receive buffer. A server streaming a large video on stream 1 could fill the TCP receive buffer, stalling streams 3 and 5 entirely. HTTP/2 stream-level windows let the receiver limit stream 1's consumption of the shared TCP buffer, preserving bandwidth for other streams.

HEADERS frames, SETTINGS frames, and control frames are not subject to HTTP/2 flow control — only DATA frames are.

## Section 4: HPACK Header Compression

**Q11. Why can't HTTP/2 use gzip or deflate for header compression?**
A: gzip and deflate were considered and rejected specifically because of the **CRIME attack** (2012) and its successor **BREACH** (2013). These attacks exploit the fact that compression algorithms (LZ77-based) produce shorter output when the input contains repeated strings. If an attacker can inject known plaintext into a request alongside a secret (like a cookie), they can observe the compressed size of the result and determine whether the secret contains specific substrings — leaking the secret byte by byte.

HTTP/1.1 header compression via TLS compression (`DEFLATE` at the TLS layer) was disabled after CRIME. HTTP/2 needed a compression scheme designed from the ground up to be CRIME-resistant:
- Huffman encoding (which HPACK uses) does not produce length-based side channels exploitable by CRIME because it doesn't exploit cross-request redundancy in the same way as LZ77 context-window compression.
- HPACK's reference header table is explicitly defined and controlled — no dynamic sliding window that an attacker can manipulate.
- HPACK's Huffman codes are static, not adaptive — the code for each character is fixed, not derived from the data being compressed.

**Q12. How does HPACK work?**
A: HPACK (RFC 7541) compresses HTTP/2 headers using two mechanisms: a **static table**, a **dynamic table**, and **Huffman encoding**. Together they exploit the fact that HTTP headers repeat across requests.

**Static table** — 61 pre-defined entries representing the most common HTTP headers and values, indexed 1–61:

```
Index | Header Name          | Header Value
──────┼──────────────────────┼──────────────
  1   | :authority           |
  2   | :method              | GET
  3   | :method              | POST
  4   | :path                | /
  5   | :path                | /index.html
  6   | :scheme              | http
  7   | :scheme              | https
  8   | :status              | 200
 ...  | ...                  | ...
 32   | content-type         |
 33   | content-encoding     |
 ...
 61   | www-authenticate     |
```

Sending `GET /` requires only two bytes: index 2 (`:method: GET`) and index 4 (`:path: /`).

**Dynamic table** — a FIFO table that grows during the connection. When a header is sent that isn't in the static table, it can be added to the dynamic table. Subsequent requests can reference it by its dynamic index, sending just 1–3 bytes instead of the full header string.

```
First request:  Authorization: Bearer eyJhbGci...  (sent in full — 250 bytes)
                → added to dynamic table at index 62

Second request: [62]  (1–2 bytes — references dynamic table index 62)
```

**Huffman encoding** — a canonical Huffman code defined in the HPACK spec (not derived from the data being compressed). Characters that appear frequently in HTTP headers get shorter bit codes. `a` = 00011 (5 bits), `t` = 00101 (5 bits), ` ` = 010100 (6 bits). The Huffman encoding typically achieves 30–40% compression on ASCII header strings independently of the table mechanism.

**Three HPACK representation types:**
```
Indexed header field:        [1][index]    — header+value in static or dynamic table
Literal with incremental indexing: [01][index/name][value] — add to dynamic table
Literal without indexing:    [0000][index/name][value]     — don't add to dynamic table
                             (used for sensitive headers like Authorization,
                              Set-Cookie — prevents value from being cached in
                              intermediary's dynamic table)
```

**Q13. Walk through what HPACK looks like for a realistic HTTP/2 request sequence.**
A:

```
Connection starts: both sides have static table (indices 1–61), dynamic table empty.

Request 1: GET https://example.com/index.html
  :method GET      → index 2 (static)     → 1 byte
  :scheme https    → index 7 (static)     → 1 byte
  :path /index.html → index 5 (static)    → 1 byte  (exact match!)
  :authority example.com → literal, index added at 62
                          → ~15 bytes (name index 1 + huffman value)
  accept-encoding gzip, deflate → literal, add at 63 → ~20 bytes
  user-agent Chrome/120.0...    → literal, add at 64 → ~30 bytes

  Total: ~70 bytes  (vs. ~300 bytes uncompressed)

Request 2: GET https://example.com/style.css
  :method GET      → index 2              → 1 byte
  :scheme https    → index 7              → 1 byte
  :path /style.css → literal (not in static table, add at 65)
                   → ~12 bytes
  :authority example.com → index 62 (dynamic) → 1–2 bytes
  accept-encoding gzip, deflate → index 63 (dynamic) → 1–2 bytes
  user-agent Chrome/120.0...    → index 64 (dynamic) → 1–2 bytes

  Total: ~20 bytes  (vs. ~300 bytes uncompressed; 93% compression)

Request 3–N: GET https://example.com/[varying paths]
  Only :path changes; all other headers → 1–2 bytes each from dynamic table
  Total per request: ~15 bytes for headers (vs. ~300 bytes)
```

This is why HPACK matters: on a page with 80 requests, HTTP/1.1 sends ~24,000 bytes of headers; HTTP/2 with HPACK sends ~1,200 bytes — a 20× reduction.

**Q14. What is HPACK's sensitivity to connection loss, and why is dynamic table state a risk?**
A: HPACK's dynamic table is connection-scoped — it is built up incrementally during the connection and cannot be persisted or transferred. If the TCP connection is lost, both sides discard their dynamic tables. The new connection starts fresh with only the static table. On a lossy network (mobile, VPN), frequent reconnections eliminate most of HPACK's compression benefit.

More critically, HPACK requires both sides to maintain **identical dynamic table state**. The sender and receiver must agree on exactly what is in the dynamic table at every point. If they get out of sync (due to a bug, a dropped update, or an implementation error), all subsequent header decompression will produce garbage. This is why HTTP/2 connections cannot be simply resumed after a pause — the dynamic table state must be rebuilt from scratch.

This synchronization requirement also means HPACK cannot be parallelized — headers for stream 3 cannot be processed before headers for stream 1 if stream 1's headers updated the dynamic table that stream 3 references. This is actually a subtle form of HOL blocking at the compression layer. HTTP/3 addresses this with QPACK — a redesign that allows headers to be decoded out of order while still using a shared dynamic table.

## Section 5: Server Push

**Q15. What is HTTP/2 server push, and what problem does it solve?**
A: Server push is a mechanism by which the server proactively sends resources to the client before the client explicitly requests them. It addresses the **discovery latency** problem inherent in HTTP: the browser must parse the HTML response to discover that it needs `style.css` and `app.js`, then make additional round trips to fetch them.

```
Without server push (HTTP/1.1 or HTTP/2 without push):

  t=0ms:  Client sends GET /index.html
  t=50ms: Server sends HTML response
  t=50ms: Client parses HTML, discovers it needs style.css and app.js
  t=50ms: Client sends GET /style.css and GET /app.js
  t=100ms: Server sends style.css and app.js

  Total time to have all resources: 100ms (2 round trips)

With server push:

  t=0ms:  Client sends GET /index.html
  t=50ms: Server sends HTML response
  t=50ms: Server also pushes style.css and app.js (proactively)
  t=50ms: Client receives style.css and app.js alongside HTML response
          (they were already in flight during the first round trip)

  Total time to have all resources: 50ms (1 round trip)
```

The server saves one round trip by pushing resources it knows the client will need. This is most valuable for render-blocking resources referenced in HTML.

**Q16. How does the server push mechanism work at the frame level?**
A: Server push uses two frame types — `PUSH_PROMISE` and `HEADERS`/`DATA`:

```
Server Push sequence:

1. Client sends HEADERS frame for GET /index.html (stream 1)

2. Server sends HEADERS frame (response for /index.html) on stream 1

3. Before or alongside the response, server sends PUSH_PROMISE on stream 1:
   ┌──────────────────────────────────────────────────┐
   │ Type: PUSH_PROMISE                               │
   │ Stream ID: 1  (associated with the request)      │
   │ Promised Stream ID: 2  (even — server-initiated) │
   │ Header Block: :method GET, :path /style.css,     │
   │               :scheme https, :authority …        │
   └──────────────────────────────────────────────────┘
   This tells the client: "I'm going to push /style.css on stream 2.
   Don't request it yourself."

4. Server sends HEADERS + DATA for /style.css on stream 2
   (interleaved with the /index.html response on stream 1)

5. Client receives stream 2 data, stores in push cache
   When the client encounters <link rel="stylesheet" href="/style.css">
   in the HTML, it checks the push cache first — finds it already there.
   No additional request needed.
```

**Key rules:**
- `PUSH_PROMISE` must be sent before the response that references the pushed resource (or before the client would request it).
- The client can refuse a push by sending `RST_STREAM` on the promised stream ID.
- Pushed responses are subject to the same cache semantics as regular responses — if the client already has the resource in its HTTP cache, it can reject the push with `RST_STREAM`.
- The server can only push resources that the client would be authorized to request — the push must be for the same origin or a delegated origin.

**Q17. Why did server push largely fail in practice, and what replaced it?**
A: Server push had a compelling theory but poor real-world results. Several problems:

- **Cache unawareness**: the server doesn't know what's in the client's HTTP cache. It pushes resources the client already has, wasting bandwidth. The browser has to receive the PUSH_PROMISE before it can check its cache and send RST_STREAM — by which time the push data may already be in flight. On a fast connection, the entire pushed resource arrives before the RST_STREAM, wasting the full bandwidth of the resource.
- **Timing is hard**: PUSH_PROMISE must arrive before the client requests the resource. If the server sends PUSH_PROMISE too late (after the client already sent the GET), the client ends up with two responses for one resource. Getting the timing right requires deep integration between the server and the HTML generator — difficult in practice.
- **No standardized push cache**: different browsers implemented the "push cache" differently. The push cache was ephemeral (tied to the HTTP/2 session) rather than the persistent HTTP cache — a pushed resource in the push cache couldn't be reused by a new connection.
- **Intermediaries**: CDN edge nodes and reverse proxies don't always pass through server push correctly — pushes are often dropped or duplicated.
- **Data shows poor outcomes**: studies from Mozilla (2017) and Cloudflare (2019) found server push frequently hurt performance by wasting bandwidth and crowding out more important data.

**What replaced it — `103 Early Hints` (RFC 8297):**
```
HTTP/1.1 103 Early Hints
Link: </style.css>; rel=preload; as=style
Link: </app.js>; rel=preload; as=script
```
The server sends a `103` informational response immediately, telling the browser to start prefetching resources while the server is still generating the `200` response. Unlike push, Early Hints work with the browser's existing cache — the browser checks the cache before fetching. Early Hints work over HTTP/1.1 and HTTP/2, don't require streaming the actual resources over the same connection, and play well with CDNs. Chrome and Firefox support it; Cloudflare and Fastly serve it. It is the practical successor to server push for the page-load latency use case.

Chrome removed HTTP/2 server push support in version 106 (September 2022). HTTP/3 retains the `PUSH_PROMISE` frame type but push is effectively deprecated in modern browser usage.

## Section 6: HTTP/2 in Practice

**Q18. How does HTTP/2 change best practices for web performance optimization that were developed for HTTP/1.1?**
A: Several HTTP/1.1 optimization techniques become unnecessary or counterproductive under HTTP/2:

**Domain sharding (multiple origins to bypass 6-connection limit):**
- HTTP/1.1: spread resources across `static1.example.com`, `static2.example.com` to get 12–18 parallel connections.
- HTTP/2: multiplexing means one connection handles all streams. Domain sharding creates *multiple* connections — each with its own HPACK dynamic table, its own slow start, its own TLS handshake. Sharding actively hurts HTTP/2 performance. Consolidate to one origin.

**Resource concatenation / bundling:**
- HTTP/1.1: combine 20 JS files into one `bundle.js` to reduce request count. A bug fix requires redownloading the entire bundle.
- HTTP/2: 20 separate JS files over one multiplexed connection incur no per-request connection overhead. Smaller, more granular files have better cache granularity — change one file, only that file needs redownloading. The request count no longer matters; the bytes transferred do.

**CSS/JS spriting (combining images into one sprite sheet):**
- HTTP/1.1: reduce 50 image requests to 1 sprite request.
- HTTP/2: 50 requests over one connection are fine. Sprites complicate CSS, increase initial payload (unused images), and make caching coarse. Avoid for new development.

**Inlining small resources:**
- HTTP/1.1: inline small CSS and images as `data:` URIs to save round trips.
- HTTP/2: the overhead of a separate request is minimal. Inlining prevents caching — inlined resources can't be cached separately. Avoid unless the resource is truly unique per page.

**What still matters under HTTP/2:**
- Total bytes transferred (compression, minification, image optimization).
- Number of TCP connections (limit sharding, use one origin when possible).
- Critical path rendering — render-blocking resources still matter; Early Hints and preload help.
- TLS session resumption — eliminates the TLS handshake on reconnect.

**Q19. What are HTTP/2 connection coalescing, and why does it matter for performance?**
A: Connection coalescing is HTTP/2's mechanism for reusing an existing connection to a different hostname, provided the hostnames resolve to the same IP address and share a TLS certificate.

```
Browser has existing HTTP/2 connection to www.example.com (IP: 93.184.216.34)

New request: GET https://static.example.com/image.png
  → DNS resolves static.example.com → 93.184.216.34  (same IP!)
  → TLS certificate for www.example.com covers *.example.com
  → Browser coalesces: reuses existing connection, sends request on new stream
  → No new TCP connection, no new TLS handshake
```

Coalescing is the legitimate HTTP/2 version of domain sharding — it allows CDNs to serve multiple subdomains from the same infrastructure without the cost of multiple connections. The browser coalesces automatically when the conditions are met (same IP, certificate covers both names). This is why CDNs use wildcard certificates and anycast routing — to maximize coalescing opportunities.

**Q20. How does gRPC use HTTP/2, and what does HTTP/2 provide to gRPC that HTTP/1.1 cannot?**
A: gRPC is a high-performance RPC framework (Google) that is entirely built on HTTP/2. Every gRPC call is an HTTP/2 stream. gRPC benefits from HTTP/2 in three specific ways:

- **Multiplexing**: a single gRPC channel (one TCP connection) carries thousands of concurrent RPCs, each on its own stream. HTTP/1.1 would require one connection per concurrent RPC — impractical at scale.
- **Streaming**: HTTP/2 streams are inherently bidirectional and can carry multiple messages. gRPC defines four call types based on this:
  - **Unary**: one request HEADERS+DATA → one response HEADERS+DATA.
  - **Server streaming**: one request → multiple response DATA frames on one stream.
  - **Client streaming**: multiple request DATA frames → one response.
  - **Bidirectional streaming**: both sides send multiple DATA frames simultaneously — a true real-time duplex channel. Impossible in HTTP/1.1 without WebSockets.
- **Header compression**: gRPC sends metadata (service name, method name, auth token, deadline, tracing headers) as HTTP/2 headers. HPACK compresses these aggressively, especially the repeated auth tokens and tracing headers that accompany every RPC.

gRPC uses HTTP/2 `h2c` (cleartext) for inter-service communication inside a data center, and `h2` (TLS) for external-facing APIs.

## Section 7: Pitfalls and Limits

**Q21. What is HTTP/2 connection-level head-of-line blocking, and how is it different from HTTP/1.1 HOL blocking?**
A: HTTP/2 eliminates *application-layer* HOL blocking (one HTTP request waiting for another to complete). But it introduces a new HOL blocking problem at the *TCP layer*:

Since all HTTP/2 streams share a single TCP connection, a single lost TCP packet stalls the entire connection — not just the stream whose data was lost. TCP's reliable delivery guarantee means the receiver cannot process any data beyond the lost packet until it is retransmitted and arrives in order. During retransmission (one RTT), all streams are frozen:

```
Stream 1 data: [A][B][C][D][E][F][G]
Stream 3 data: [X][Y][Z]
Stream 5 data: [M][N][O]

TCP segment carrying [D] from stream 1 is lost.

Receiver has: [A][B][C] ✓ | [?] ✗ | [E][F][G][X][Y][Z][M][N][O] ← buffered, unusable

All streams stall until [D] is retransmitted. Streams 3 and 5 have all their data
but cannot deliver it to the application — the TCP receive buffer is blocked at [D].
```

This TCP HOL blocking is particularly severe on lossy networks (mobile, satellite) with high RTT. On a 100ms RTT connection with 1% packet loss, a stall occurs roughly every 100ms, pausing all streams for ~100ms each time. HTTP/3 (QUIC) solves this by implementing per-stream reliability: a lost packet only stalls the stream it belongs to, because QUIC streams are independent at the transport layer.

**Q22. What is the HTTP/2 priority problem in practice, and why did browsers abandon the dependency tree model?**
A: HTTP/2's stream priority mechanism (dependency tree + weights) was theoretically powerful but practically broken for three reasons:

- **Server implementation inconsistency**: many popular HTTP servers (nginx, Apache) either ignored priorities entirely or implemented them incorrectly. A study by Patrick McManus (Mozilla, 2018) found most CDNs and servers did not honor HTTP/2 priorities correctly.
- **Middlebox interference**: CDN edge nodes and reverse proxies frequently stripped or mangled PRIORITY frames, making client-side priority signals meaningless by the time they reached the origin server.
- **Complexity and gaming**: the dependency tree model is complex to implement correctly and easy to abuse. Chrome changed its priority scheme multiple times, and different Chrome versions produced different priority signals.

Chrome's response (2022): stop sending PRIORITY frames. Use the new `Priority` HTTP header (RFC 9218) instead, which is a simple `urgency` (0–7) + `incremental` (boolean) scheme:
```
Priority: u=1         (urgency level 1 — very high; render-blocking CSS)
Priority: u=3         (urgency level 3 — high; above-fold images)
Priority: u=5, i      (urgency 5, incremental — streaming media chunks)
Priority: u=7         (urgency 7 — lowest; prefetch, background fetch)
```
This simpler model is adopted in HTTP/3 as the sole priority mechanism.

**Q23. What are HTTP/2 SETTINGS parameters, and why do they matter operationally?**
A: SETTINGS frames configure the behavior of an HTTP/2 connection. Each side sends its own SETTINGS; the other side must acknowledge with a SETTINGS ACK. Key parameters:

```
HEADER_TABLE_SIZE (0x1):    Maximum size of HPACK dynamic table (bytes)
                            Default: 4096. Higher = better compression but more memory.

ENABLE_PUSH (0x2):          0 = disable server push. Most clients send this now
                            since push is deprecated. Default: 1.

MAX_CONCURRENT_STREAMS (0x3): Maximum streams the peer may open simultaneously.
                              Server sets this to limit client concurrency.
                              Default: unlimited. Typical production: 100–200.

INITIAL_WINDOW_SIZE (0x4):  Initial flow control window for new streams (bytes).
                            Default: 65535. Increase for high-bandwidth, high-latency.
                            Must not exceed 2³¹−1 (2GB).

MAX_FRAME_SIZE (0x5):       Maximum payload size of a single frame (bytes).
                            Default: 16384 (16KB). Range: 16384–16777215 (16MB).
                            Larger frames reduce framing overhead; smaller frames
                            allow finer-grained interleaving.

MAX_HEADER_LIST_SIZE (0x6): Advisory maximum size of header list (sum of header
                            fields, including overhead). Not strictly enforced
                            but signals what the sender considers acceptable.
```

**Operational implications:**
- A server that sets `MAX_CONCURRENT_STREAMS = 1` forces HTTP/2 to behave like HTTP/1.1 — one request at a time. This is a common misconfiguration.
- `INITIAL_WINDOW_SIZE` below the BDP of the connection causes flow-control stalling on high-latency links — the sender runs out of window and must wait for WINDOW_UPDATE before sending more data.
- Mismatch between `MAX_FRAME_SIZE` settings can cause interoperability issues — the sender must not exceed the receiver's advertised maximum.

## Section 8: Scenario / System Design Style Questions

**Q24. "You're migrating a high-traffic website from HTTP/1.1 to HTTP/2. What changes do you make to the server configuration and the application's asset delivery strategy?"**
A: The migration touches both infrastructure and application layers:

**Infrastructure:**
- Enable HTTP/2 in the web server (`http2` directive in nginx, `Protocols h2 http/1.1` in Apache). HTTP/2 requires TLS; ensure a valid certificate is in place.
- Verify ALPN is configured in the TLS stack — OpenSSL 1.0.2+ supports it; ensure the server is built with ALPN support.
- Set `MAX_CONCURRENT_STREAMS` to an appropriate value (100–200 for most applications; higher for API servers with many parallel requests per page load).
- Increase `INITIAL_WINDOW_SIZE` if serving large files over high-latency connections: `INITIAL_WINDOW_SIZE = 1048576` (1MB) for intercontinental links.
- Set up TLS session resumption (session tickets or session IDs) — reduces reconnection cost to one RTT.

**Asset delivery strategy:**
- **Remove domain sharding**: consolidate `static1.example.com` and `static2.example.com` back to one origin. Sharding creates unnecessary connections.
- **Consider unbundling JS/CSS**: smaller, more granular files improve cache hit rates. Evaluate whether bundle splitting (already common in webpack/Rollup for code splitting) is sufficient.
- **Replace server push with `103 Early Hints`**: configure the server to send `Link: <resource>; rel=preload` hints for render-blocking resources. Test with WebPageTest to confirm the hints arrive before the HTML response completes.
- **Add `preload` link headers**: `Link: </style.css>; rel=preload; as=style` — the browser fetches these immediately without waiting for HTML parsing.
- **Keep sprite sheets and data URIs for small assets** that are referenced only once per page — the HTTP/2 request-count argument doesn't apply here since these save bandwidth, not just connections.
- **Monitor connection coalescing**: ensure CDN is configured with wildcard certificates so subdomains coalesce onto one connection.

**Q25. "A gRPC service is experiencing high latency on calls when the server is under load. Packet captures show many WINDOW_UPDATE frames and the congestion window appears small. What is happening and how do you fix it?"**
A: This is an HTTP/2 flow control starvation problem combined with congestion window pressure. The symptoms point to two issues:

**Flow control exhaustion**: the server is not sending WINDOW_UPDATE frames fast enough after processing data, causing the client to stall waiting for credit. On a heavily loaded server, the application may be slow to process incoming gRPC request data, so it doesn't return the receive buffer to the TCP/HTTP2 stack, so the stack doesn't send WINDOW_UPDATE, so the client stalls. Fixes:
- Profile the server's gRPC handler — is it blocking on database calls, doing CPU-intensive work, or waiting for I/O before reading the next frame? Move blocking work off the request handler thread.
- Increase `INITIAL_WINDOW_SIZE` on the server's SETTINGS — this gives clients more credit upfront before WINDOW_UPDATE is needed. But this only helps if the client has large requests; for small gRPC messages it won't matter.
- Use streaming RPCs instead of large unary RPCs — smaller messages allow finer-grained flow control and reduce stall duration.

**Congestion window pressure**: many gRPC streams on one TCP connection share the connection's congestion window. If the server is sending many streams simultaneously, `cwnd` may not grow fast enough to fill all streams. Each new HTTP/2 connection starts slow start; the first few RTTs have low throughput. Fixes:
- Enable BBR congestion control on the server (`net.ipv4.tcp_congestion_control = bbr`) — BBR maintains higher cwnd under load compared to CUBIC.
- Increase the initial congestion window: `ip route change default ... initcwnd 32` — starts new connections with 32 MSS instead of 10, reducing slow start impact.
- If inter-service latency is a problem within a data center, use `h2c` (cleartext) instead of TLS — eliminates TLS handshake latency and offloads encryption overhead.
- Consider connection pooling at the gRPC channel level — multiple connections per server pair increases aggregate cwnd faster than one connection for very high throughput scenarios.

**Q26. "Compare HTTP/1.1, HTTP/2, and HTTP/3 on the following dimensions: multiplexing, HOL blocking, header compression, connection setup latency, and packet loss resilience."**
A:

| Dimension                  | HTTP/1.1                                     | HTTP/2                                            | HTTP/3 (QUIC)                                       |
|---                         |---                                           |---                                                |---                                                  |
| Multiplexing               | None (one request per connection); workaround: 6–8 connections | Full — unlimited concurrent streams on one TCP connection | Full — concurrent streams on one QUIC connection   |
| HOL blocking               | Application-layer (one request blocks others on same connection) | Application-layer eliminated; TCP-layer HOL remains | Eliminated at both layers — lost packet stalls only its stream |
| Header compression         | None (full ASCII headers every request)      | HPACK — static + dynamic table + Huffman; ~90% compression on repeated headers | QPACK — HPACK redesigned for out-of-order delivery; similar compression ratio |
| Connection setup latency   | TCP (1 RTT) + TLS 1.2 (2 RTT) = 3 RTT before first byte; TLS 1.3 = 2 RTT | Same as HTTP/1.1 (same TCP+TLS) — 1–2 RTT | QUIC combines transport + crypto: 1 RTT new, 0 RTT resumption |
| Packet loss resilience     | Per-connection; loss stalls one connection   | Per-connection; loss stalls all streams           | Per-stream; loss stalls only the affected stream    |
| Transport                  | TCP                                          | TCP                                               | QUIC (UDP-based)                                    |
| TLS requirement            | No (but recommended)                         | De facto yes (browsers require)                   | Always (QUIC always encrypts)                       |
| Typical improvement        | Baseline                                     | 30–50% faster page loads (varies)                 | 10–30% faster than HTTP/2 on lossy networks         |

The key insight: HTTP/2 solved the application-layer problem; HTTP/3 solves the transport-layer problem. On a reliable, low-latency network, HTTP/2 and HTTP/3 perform similarly. HTTP/3's advantage grows with packet loss rate and RTT — exactly the conditions of mobile networks, which is why Google and Meta (who deployed HTTP/3 early) saw the largest wins.

## Quick Reference

```
HTTP/2 binary frame structure (9-byte header):
  [24-bit length][8-bit type][8-bit flags][1-bit reserved][31-bit stream ID][payload]

Key frame types:
  HEADERS      (0x1) — request/response headers (HPACK compressed)
  DATA         (0x0) — request/response body
  SETTINGS     (0x4) — connection configuration
  WINDOW_UPDATE(0x8) — flow control credit
  PUSH_PROMISE (0x5) — server push announcement
  RST_STREAM   (0x3) — cancel/abort a stream
  GOAWAY       (0x7) — graceful connection shutdown
  PING         (0x6) — keepalive / RTT measurement

Streams:
  Client-initiated: odd IDs (1, 3, 5, …)
  Server push:      even IDs (2, 4, 6, …)
  Connection-level: stream 0 (SETTINGS, PING, GOAWAY, connection WINDOW_UPDATE)
  Stream IDs never reused within a connection

HPACK compression:
  Static table:  indices 1–61 (common headers/values, hardcoded)
  Dynamic table: indices 62+ (built during connection, FIFO eviction)
  Huffman:       30–40% additional compression on string values
  Sensitive headers (Authorization, Cookie): use "literal without indexing"

Flow control (both stream and connection level):
  Initial window: 65535 bytes (default)
  Sender stalls when window exhausted → waits for WINDOW_UPDATE
  Only DATA frames subject to flow control (not HEADERS, SETTINGS, etc.)

SETTINGS key parameters:
  MAX_CONCURRENT_STREAMS: 100–200 typical (unlimited if unset)
  INITIAL_WINDOW_SIZE:    65535 default; increase for high-BDP paths
  HEADER_TABLE_SIZE:      4096 default; higher = better HPACK compression
  MAX_FRAME_SIZE:         16384 default; 16384–16777215 range
  ENABLE_PUSH:            0 = disable server push (recommended now)

HTTP/1.1 optimizations that HURT HTTP/2:
  Domain sharding → creates multiple connections; kills HPACK benefits
  (Resource concatenation and spriting: now trade-off vs cache granularity)

HTTP/2 protocol negotiation:
  TLS ALPN extension: client offers ["h2", "http/1.1"], server selects
  Connection preface: 24-byte magic string + SETTINGS frame
```

## Common Mistakes at a Glance

| Mistake                                                        | Clarification                                                                             |
|---                                                             |---                                                                                        |
| Thinking HTTP/2 eliminates all HOL blocking                    | Eliminates application-layer HOL; TCP-layer HOL remains (HTTP/3 fixes this)              |
| Thinking TLS is required by the HTTP/2 spec                    | Spec allows cleartext (`h2c`); browsers require TLS in practice                          |
| Applying HTTP/1.1 domain sharding to HTTP/2                    | Sharding creates multiple connections, breaks HPACK coalescing, hurts performance         |
| Confusing stream flow control with connection flow control     | Both exist; actual sendable bytes = min(stream_window, connection_window)                 |
| Assuming server push is a good default to enable               | Push is largely deprecated; Chrome removed it in 2022; use `103 Early Hints` instead     |
| Thinking HPACK uses gzip/deflate                               | HPACK uses a static+dynamic table plus static Huffman — no LZ77 sliding window (CRIME defense) |
| Confusing HPACK dynamic table with HTTP cache                  | HPACK dynamic table is connection-scoped (in-memory, per-connection); not the HTTP cache  |
| Thinking client stream IDs and server push IDs follow the same sequence | Client: odd (1,3,5…); server push: even (2,4,6…); connection: 0               |
| Assuming `ENABLE_PUSH = 1` means push will work correctly      | Push requires correct implementation on server, correct timing, cache awareness — hard in practice |
| Confusing `MAX_CONCURRENT_STREAMS` limit with a connection limit | It limits streams per connection, not connections per server                             |

**Tip for the interview:** At 5 YOE, HTTP/2 questions surface as: "why is your HTTP/2 server not faster than HTTP/1.1 in production?" (domain sharding, misconfigured `MAX_CONCURRENT_STREAMS`, server push wasting bandwidth), "explain why HTTP/3 exists if HTTP/2 already has multiplexing" (TCP HOL blocking — the one sentence answer is "a dropped TCP packet stalls all HTTP/2 streams; QUIC makes loss per-stream"), or "design the asset delivery strategy for a high-traffic web application" (Early Hints over push, cache-granular bundles, connection coalescing via wildcard certs). Know the binary frame structure well enough to draw it — stream ID in every frame is the whole point of multiplexing. Know HPACK's two-table model and why it can't use gzip. Know why server push failed and what replaced it. Those are the questions that separate candidates who've read the RFC from candidates who've deployed HTTP/2 in production.
