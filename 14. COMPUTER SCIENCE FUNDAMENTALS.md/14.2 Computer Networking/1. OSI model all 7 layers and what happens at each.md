# OSI Model: All 7 Layers and What Happens at Each — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the OSI model, and why does it exist?**
A: The OSI (Open Systems Interconnection) model is a conceptual framework published by ISO in 1984 that divides network communication into seven discrete layers. Each layer has a well-defined responsibility and communicates only with the layers immediately above and below it through standardised interfaces. The model exists for three reasons:

**Modularity:** Breaking a complex problem (two applications on different continents exchanging data reliably) into seven independent layers means each can be designed, implemented, tested, and replaced independently. You can swap Ethernet for Wi-Fi (Layer 2) without touching TCP (Layer 4) or HTTP (Layer 7).

**Interoperability:** Any vendor implementing Layer 3 (IP) correctly can route packets between any other vendor's Layer 3 implementations. The model defines the contract between layers, not the implementation — which is why a Node.js server running on Linux can talk to a Python client running on Windows over a Cisco router, a Juniper switch, and a Huawei Wi-Fi access point.

**Vocabulary for diagnosis:** When a network problem occurs, the model provides a systematic diagnostic framework. "Is this a Layer 2 problem (MAC addresses, VLAN tagging)? Or Layer 4 (TCP connection not establishing)? Or Layer 7 (HTTP response format)?" — these questions lead to different tools and fixes.

The OSI model is a reference model, not a strict implementation specification. Real-world protocols don't always cleanly map to exactly one layer — TLS sits between Layer 4 and Layer 7 depending on who you ask; HTTP/2 collapses some distinctions. But the model remains the universal vocabulary for discussing network communication.

**Q2. What is the TCP/IP model, and how does it map to OSI?**
A: The TCP/IP model (also called the Internet model or DoD model) is the practical, implemented model on which the modern Internet runs. It was developed by DARPA in the 1970s — earlier than OSI — and collapses the OSI 7-layer model into 4 layers:

```
OSI Model                     TCP/IP Model
─────────────────────         ─────────────────────
7. Application    ┐
6. Presentation   ├──────────▶  4. Application
5. Session        ┘              (HTTP, DNS, SMTP, SSH, TLS)

4. Transport      ───────────▶  3. Transport
                                 (TCP, UDP, QUIC)

3. Network        ───────────▶  2. Internet
                                 (IP, ICMP, ARP)

2. Data Link      ┐
1. Physical       ├──────────▶  1. Network Access
                  ┘              (Ethernet, Wi-Fi, PPP)
```

The TCP/IP model is what actually runs on every device connected to the Internet. OSI is the reference model used for teaching, troubleshooting, and standards discussion. When a backend engineer says "this is a Layer 4 problem," they mean TCP/UDP in the OSI sense — which maps to TCP/IP Layer 3 (Transport). Context determines which numbering is in use; at 5 YOE you're expected to know both.

**Q3. What is encapsulation and decapsulation, and how do they work across all 7 layers?**
A: Encapsulation is the process by which each layer wraps the data it receives from the layer above with its own header (and sometimes trailer), forming a new protocol data unit (PDU). Decapsulation is the reverse — each layer on the receiving side strips its own header and passes the payload up. Data moves down the sender's stack (encapsulation) and up the receiver's stack (decapsulation):

```
Sender side (encapsulation — wrapping downward)
──────────────────────────────────────────────
L7  Application  │ HTTP request body          │  = Data
L6  Presentation │ [TLS header] HTTP body     │  = Data (encrypted)
L5  Session      │ (handled within TLS/HTTP)  │
L4  Transport    │ [TCP header] [TLS+HTTP]    │  = Segment
L3  Network      │ [IP header] [TCP+TLS+HTTP] │  = Packet
L2  Data Link    │ [ETH header] [IP+...] [FCS]│  = Frame
L1  Physical     │ 01011010100110...          │  = Bits

Receiver side (decapsulation — unwrapping upward)
──────────────────────────────────────────────────
L1  → strips physical encoding    → gives L2 a frame
L2  → strips Ethernet header/FCS  → gives L3 a packet
L3  → strips IP header            → gives L4 a segment
L4  → strips TCP header           → gives L5/L6 a stream
L6  → strips TLS, decrypts        → gives L7 plaintext HTTP
L7  → parses HTTP                 → gives the application the request
```

Each PDU name: Application data → Segment (L4) → Packet (L3) → Frame (L2) → Bits (L1). The mnemonic "All People Seem To Need Data Processing" (Application, Presentation, Session, Transport, Network, Data Link, Physical) is standard for recalling the layer order top-to-bottom.

The key insight: **each layer only knows about its own header and the opaque payload from above.** The IP layer doesn't know whether the payload contains TCP or UDP — it only sees the Protocol field in the IP header. The TCP layer doesn't know whether its payload is HTTP or TLS — it only sees port numbers. This strict layering is what makes the Internet composable and evolvable.

## Section 2: The Seven Layers in Detail

**Q4. What is Layer 1 (Physical), and what exactly does it do?**
A: Layer 1 (Physical) is the bottom layer — it deals with the raw transmission of bits over a physical medium. It has no concept of addresses, packets, or error correction — just the electrical, optical, or radio signals that represent 0s and 1s.

**What Layer 1 defines:**
- **Signal encoding** — how bits are represented: voltage levels (Ethernet), light pulses (fibre optic), radio waves (Wi-Fi), amplitude/frequency/phase modulation.
- **Bit timing** — the clock rate (baud rate). Both ends must agree on how fast bits are transmitted. 1 Gbps Ethernet sends one bit every nanosecond.
- **Physical medium** — copper wire (Cat5e/Cat6 for Ethernet), single-mode or multimode optical fibre, coaxial cable, radio spectrum (Wi-Fi bands: 2.4GHz, 5GHz, 6GHz).
- **Connector types** — RJ-45 for Ethernet, SC/LC for fibre, SMA for coaxial.
- **Duplex mode** — half-duplex (one direction at a time, like early Ethernet hubs) vs full-duplex (simultaneous bidirectional, like modern switched Ethernet).
- **Signal amplification and repeating** — physical repeaters boost signal strength for longer cable runs; they don't understand frames or packets.

**What Layer 1 does NOT do:**
- No error detection (that's L2).
- No addressing (that's L2 for MAC, L3 for IP).
- No knowledge of what the bits mean.

**Layer 1 devices:** Hubs (repeat bits to all ports), repeaters, cables, antennas, transceivers (SFP modules converting electrical to optical).

**Relevance for backend engineers:** Layer 1 problems manifest as: physical cable unplugged (`link down` on a NIC), SFP transceiver mismatch between server and switch (one uses single-mode, the other expects multimode), duplex mismatch (one end negotiates full-duplex, the other half-duplex — causing collisions and packet loss). In AWS/cloud: Layer 1 is abstracted away; you never touch it. In bare-metal or colo deployments: NIC selection (10G vs 25G vs 100G), cable quality, and transceiver compatibility are real operational concerns.

**Q5. What is Layer 2 (Data Link), and what problem does it solve that Layer 1 cannot?**
A: Layer 2 (Data Link) takes the raw bit stream from Layer 1 and organises it into structured frames — discrete units with a defined start, payload, and end. It adds two critical capabilities Layer 1 lacks: **addressing** (who is this frame for on this local segment?) and **error detection** (was this frame corrupted in transit?).

Layer 2 is further divided into two sublayers:
- **MAC (Media Access Control)** — addressing and medium access control (who gets to transmit when; collision avoidance).
- **LLC (Logical Link Control)** — framing and multiplexing (identifying which Layer 3 protocol is carried in the payload).

**Ethernet frame structure (the dominant Layer 2 protocol):**
```
┌────────────┬─────────────┬──────┬─────────────────────┬──────────────┐
│ Preamble   │ Destination │ Src  │ EtherType / 802.1Q  │   Payload    │ FCS │
│ (7B + SFD) │ MAC (6B)    │ MAC  │ (2B: 0x0800=IPv4,   │ (46–1500B)  │(4B) │
│            │             │ (6B) │  0x86DD=IPv6,        │             │     │
│            │             │      │  0x8100=VLAN tag)    │             │     │
└────────────┴─────────────┴──────┴─────────────────────┴──────────────┘
```

**MAC addresses:** 6-byte (48-bit) hardware addresses burned into NICs by manufacturers, globally unique (in theory). Format: `AA:BB:CC:DD:EE:FF`. The first 3 bytes are the OUI (Organisationally Unique Identifier) — identify the manufacturer. MAC addresses are local to one network segment — they don't survive routing.

**FCS (Frame Check Sequence):** A 4-byte CRC-32 checksum over the frame contents. The receiver recomputes the CRC and discards frames that don't match. Error detection, not correction — L2 detects bit errors but doesn't retransmit (that's L4 TCP's job).

**Switches** are Layer 2 devices — they read the destination MAC address of each frame and forward it out only the port leading to that MAC (learned from the source MAC of incoming frames, stored in the MAC address table). This is more efficient than a hub's broadcast-to-all.

**VLANs (802.1Q):** A 4-byte VLAN tag inserted into the Ethernet frame carries the VLAN ID (12 bits → 4094 VLANs). The switch uses this to keep traffic logically separated on the same physical infrastructure.

**ARP (Address Resolution Protocol):** Translates Layer 3 IP addresses to Layer 2 MAC addresses on the local segment. "Who has IP 192.168.1.1? Tell 192.168.1.50." The owner of that IP replies with its MAC. The mapping is cached in the ARP table.

**Relevance for backend engineers:** Layer 2 issues: ARP poisoning / ARP spoofing (a machine claims another's IP → intercepts traffic; mitigated by Dynamic ARP Inspection on managed switches), MAC address table overflow (switch reverts to hub behaviour, flooding all frames → traffic interception), VLAN misconfiguration (servers can't reach each other even on the same switch because they're on different VLANs), jumbo frames not enabled end-to-end causing MTU issues with large packets.

**Q6. What is Layer 3 (Network), and what does it add over Layer 2?**
A: Layer 3 (Network) provides end-to-end logical addressing and routing — the ability to get a packet from a host on one network to a host on a completely different network, across any number of intermediate routers. Layer 2 only works within a single broadcast domain (one subnet). Layer 3 transcends network boundaries.

**The fundamental problem Layer 3 solves:** On a local Ethernet segment, frames are delivered by MAC address — fine for 250 devices on one switch. But there are billions of hosts on the Internet, they're on millions of different physical segments, and MAC addresses have no hierarchical structure useful for routing. IP addresses solve this with hierarchical, routable addressing.

**IPv4 packet structure (key fields):**
```
┌──────────────────────────────────────────────────────────────────────┐
│ Version(4) │ IHL │ DSCP/ECN │      Total Length (16b)               │
├────────────┴─────┴──────────┴────────────────────────────────────────┤
│     Identification (16b)     │ Flags │    Fragment Offset (13b)      │
├──────────────────────────────┴───────┴────────────────────────────────┤
│  TTL (8b)  │  Protocol (8b) │       Header Checksum (16b)           │
├────────────┴────────────────┴────────────────────────────────────────┤
│                    Source IP Address (32b)                           │
├──────────────────────────────────────────────────────────────────────┤
│                 Destination IP Address (32b)                         │
└──────────────────────────────────────────────────────────────────────┘
```

Key fields:
- **TTL (Time to Live):** Decremented by 1 at each router hop. When it reaches 0, the router discards the packet and sends an ICMP "Time Exceeded" message back. Prevents routing loops from circulating packets forever. Default TTL: 64 (Linux), 128 (Windows), 255 (some routers). `traceroute` exploits TTL — it sends packets with TTL=1, 2, 3... and uses the resulting "Time Exceeded" ICMP replies to map each hop.
- **Protocol:** Identifies the Layer 4 protocol in the payload: 6 = TCP, 17 = UDP, 1 = ICMP, 89 = OSPF.
- **Fragmentation (Flags + Fragment Offset):** If a packet is too large for a link's MTU, IP can fragment it into smaller pieces. Each fragment is reassembled at the destination. In practice, fragmentation is avoided (it's inefficient and drops the entire original packet if any fragment is lost) — TCP uses Path MTU Discovery (PMTUD) to find the maximum packet size that works end-to-end.

**Routing:** Routers maintain routing tables mapping destination IP prefixes to next-hop addresses and egress interfaces. Longest-prefix match: a router with entries for `10.0.0.0/8` and `10.1.0.0/16` forwards packets to `10.1.2.3` via the `/16` entry (more specific). Routing protocols (OSPF, BGP, EIGRP) populate routing tables dynamically.

**CIDR (Classless Inter-Domain Routing):** Modern IP addressing uses variable-length subnet masks. `192.168.1.0/24` means the first 24 bits are the network, the last 8 bits are hosts (254 usable: `.1` to `.254`). `10.0.0.0/8` is a large private block. AWS VPC uses CIDR for subnet definition.

**ICMP (Internet Control Message Protocol):** A Layer 3 control protocol (Protocol number 1 in IP header) used for diagnostics and error reporting: `ping` (echo request/reply), `traceroute` (TTL exceeded), "Destination Unreachable" (no route to host, port closed), "Fragmentation Needed" (PMTUD).

**Layer 3 devices:** Routers, Layer 3 switches (switch with routing capabilities), firewalls (inspect IP headers and above).

**Relevance for backend engineers:** IP routing is fundamental for AWS VPC design (subnets, route tables, NAT gateway), security groups (Layer 3/4 filtering on source/destination IP and port), VPC peering, Transit Gateway, and inter-service communication. ICMP being blocked by security groups is a common reason `ping` fails even when HTTP works. MTU issues (1500 bytes Ethernet vs 9001 bytes AWS jumbo frames vs 8500 bytes inside VPC tunnels) cause silent packet drops for large payloads.

**Q7. What is Layer 4 (Transport), and what are the key differences between TCP and UDP?**
A: Layer 4 (Transport) provides end-to-end communication services between applications — not just host-to-host (Layer 3) but process-to-process. It adds port numbers to distinguish multiple applications on the same host, and — for TCP — reliability, ordering, and flow control on top of the unreliable IP layer.

**Port numbers:** 16-bit integers (0–65535) identifying the application endpoint. Source port is ephemeral (randomly assigned by the OS, typically 32768–60999 on Linux). Destination port identifies the service: 80=HTTP, 443=HTTPS, 5432=PostgreSQL, 6379=Redis, 3000=typical Node.js.

**TCP (Transmission Control Protocol):**
- **Connection-oriented:** Three-way handshake (SYN → SYN-ACK → ACK) before data exchange; four-way teardown (FIN → ACK → FIN → ACK) or RST.
- **Reliable, ordered delivery:** Every byte is sequenced. The receiver sends ACKs; the sender retransmits unacknowledged segments after a timeout or three duplicate ACKs (fast retransmit).
- **Flow control:** The receiver advertises a receive window size — how many bytes it can buffer. The sender cannot send more than the window. Prevents a fast sender from overwhelming a slow receiver.
- **Congestion control:** TCP detects network congestion (packet loss, ECN signals) and reduces the sending rate. Algorithms: CUBIC (Linux default), BBR (Google, used in modern Linux and QUIC), Reno.
- **Head-of-line blocking:** If a segment is lost, all subsequent segments are held in the receive buffer until the missing one is retransmitted. Even if later segments arrive in order, they wait. This is why HTTP/1.1 has head-of-line blocking at the application level, and why HTTP/2 multiplexing still suffers from TCP-level head-of-line blocking (motivating QUIC/HTTP/3's per-stream reliability without this cross-stream blocking).

**UDP (User Datagram Protocol):**
- **Connectionless:** No handshake; send a datagram and forget it.
- **No reliability:** Datagrams may be lost, reordered, or duplicated. No retransmission.
- **No flow control or congestion control:** UDP can send as fast as the application wants — which is why a misbehaving UDP application can flood a network link.
- **Message boundaries preserved:** Each `sendto()` produces exactly one datagram received by `recvfrom()`. Unlike TCP's byte stream, UDP preserves message structure.
- **Low overhead:** 8-byte header vs TCP's 20-byte minimum header. No connection state; less kernel overhead per "connection."

**Choosing TCP vs UDP:**

| Use case | Protocol | Reason |
|---|---|---|
| HTTP, database, SSH, SMTP | TCP | Reliability required; loss is unacceptable |
| DNS queries | UDP (primarily) | Single request/response; low latency matters; retried at application level |
| Video streaming (RTP) | UDP | Stale retransmitted frames are useless; loss is preferable to delay |
| Online gaming (real-time) | UDP | Position updates are superseded by newer ones; old retransmissions are harmful |
| VoIP | UDP | Similar to video — prefer gaps to delays |
| QUIC / HTTP/3 | UDP (with reliability on top) | UDP for low latency connection setup; per-stream reliability implemented in QUIC layer above |
| NTP | UDP | Single datagram; fire-and-forget acceptable |
| Internal service mesh | TCP (gRPC) or QUIC | Depends on latency requirements and HOL blocking sensitivity |

**Relevance for backend engineers:** TCP tuning (`SO_REUSEADDR`, `SO_REUSEPORT`, `TCP_NODELAY`, `SO_KEEPALIVE`, send/receive buffer sizes) directly affects throughput and latency for backend services. `TCP_NODELAY` disables Nagle's algorithm — critical for low-latency request/response patterns (database clients, Redis) where batching small writes adds unwanted delay. AWS Security Groups filter at Layer 4 (TCP/UDP + port). ALB operates at Layer 7; NLB at Layer 4.

**Q8. What is Layer 5 (Session), and does it have a clear modern equivalent?**
A: Layer 5 (Session) is responsible for establishing, managing, and terminating sessions — persistent logical connections between applications beyond the lifetime of individual transport connections. It provides dialogue control (who can send when) and synchronisation (checkpoints to resume interrupted transfers from a known point).

**What Layer 5 was designed for:**
- **Session establishment and teardown:** Negotiating session parameters before data exchange.
- **Dialogue control:** Half-duplex vs full-duplex coordination between applications.
- **Synchronisation points:** Marking points in a long data transfer that can be used to resume from if the transfer is interrupted, rather than starting over. Example: a file transfer interrupted at 80% resumes from the checkpoint, not from 0%.
- **Session recovery:** Re-establishing a broken transport connection and resuming the session from the last synchronisation point.

**Why Layer 5 is often called "the forgotten layer":** In practice, modern protocols blend session concepts into other layers:
- TCP connections (Layer 4) provide session-like state but don't offer checkpointing.
- TLS (often categorised as between Layer 4 and 7) provides session resumption (TLS session tickets, TLS 1.3 0-RTT) — a Layer 5 concept implemented in a security protocol.
- HTTP cookies and session tokens (Layer 7 application logic) maintain session state across multiple TCP connections.
- NetBIOS, RPC (DCE/RPC), and SIP are examples of true Layer 5 protocols.
- SQL database connections — the concept of a persistent session (authentication, transaction state, prepared statements) is a Layer 5 abstraction even though it's implemented over TCP (Layer 4) and a DB-specific wire protocol (often considered Layer 7).

**Modern mapping:** In the TCP/IP model, Layers 5, 6, and 7 all collapse into the Application layer. When a backend engineer encounters Layer 5 in an interview, the expected answer is: session management concepts (multiplexing multiple logical conversations over one connection, stateful session resumption, synchronisation checkpoints) exist today within application protocols (HTTP/2 streams, TLS session resumption, WebSocket message framing) rather than as a distinct protocol layer.

**Relevance for backend engineers:** TLS session resumption (TLS tickets vs session IDs) directly affects HTTPS handshake latency — a resumed session avoids the full certificate exchange, saving one RTT. Node.js TLS server: `tls.createServer({ sessionTimeout: 300 })` controls how long session state is cached. HTTP/2's multiplexing of multiple request/response streams over one TCP connection is a Layer 5 concept — multiple logical sessions over one transport connection.

**Q9. What is Layer 6 (Presentation), and what does it handle?**
A: Layer 6 (Presentation) is responsible for translating data between the format the application uses and the format suitable for network transmission. It handles three concerns: **encoding/decoding**, **encryption/decryption**, and **compression/decompression**.

**Encoding and translation:**
Different systems represent data differently. Layer 6 provides a common format:
- **Character encoding:** ASCII vs EBCDIC (IBM mainframes) vs UTF-8. A Layer 6 function translates between them so a UTF-8 Node.js app can communicate with an EBCDIC mainframe.
- **Data format negotiation:** JSON vs XML vs Protocol Buffers — in modern systems, this is an application-level concern, but it's conceptually a Layer 6 function.
- **Byte ordering (endianness):** Network byte order is big-endian (most significant byte first). x86 systems are little-endian. `htons()` / `ntohs()` (host-to-network-short / network-to-host-short) in C are Layer 6 operations — converting integers between host and network byte order.

**Encryption and decryption (TLS):**
TLS is the most prominent modern Layer 6 implementation. It sits above TCP (Layer 4) and below the application protocol (Layer 7):
- Provides confidentiality (symmetric encryption: AES-256-GCM), integrity (HMAC or AEAD), and authentication (X.509 certificates, asymmetric cryptography for key exchange).
- TLS 1.3 (current standard): 1-RTT handshake (down from 2-RTT in TLS 1.2); 0-RTT for resumed sessions; removed weak cipher suites.
- In Node.js: `https.createServer({ key, cert })` or Fastify/NestJS TLS config — Layer 6 handled by the `tls` module.

**Compression:**
- HTTP/1.1 `Content-Encoding: gzip / br (Brotli)` — response body compression.
- HTTP/2 HPACK — header compression (reduces overhead from repeated headers like `Authorization`, `Content-Type`).
- These are conceptually Layer 6 but implemented in the application protocol.

**Why Layer 6 is also "blurry" in practice:** Like Layer 5, modern protocols absorb Layer 6 concerns. TLS is called "above Layer 4" or "below Layer 7" depending on perspective. JSON parsing is application code. UTF-8 encoding is ubiquitous. The OSI model designed Layer 6 when encoding heterogeneity was a serious problem (1984 — ASCII and EBCDIC coexistence was a real engineering challenge). Today, UTF-8 and JSON are near-universal.

**Relevance for backend engineers:** TLS configuration is a real Layer 6 concern: cipher suite selection (prefer ECDHE + AES-GCM; disable RC4, DES, MD5), certificate management (Let's Encrypt, ACM), mutual TLS (mTLS) for service-to-service authentication in microservices, TLS termination (at the load balancer vs end-to-end). Content compression (Brotli vs gzip, compression level tradeoff against CPU cost). Protobuf vs JSON vs MessagePack — choosing binary vs text encoding for APIs.

**Q10. What is Layer 7 (Application), and what happens at this layer?**
A: Layer 7 (Application) is the topmost layer — the interface between the network stack and the actual application. It provides application-specific protocols that define how applications request services, format data, and exchange messages. Layer 7 is where HTTP, DNS, SMTP, WebSocket, gRPC, and every other application protocol live.

Layer 7 is not the application itself — it's the protocol the application uses to communicate. A Node.js HTTP server is an application; HTTP is the Layer 7 protocol it implements.

**HTTP/1.1 — the foundational Layer 7 protocol for the web:**
```
Request:                          Response:
GET /v1/payments/txn_001 HTTP/1.1 HTTP/1.1 200 OK
Host: api.example.com             Content-Type: application/json
Authorization: Bearer <token>     Content-Length: 87
Accept: application/json          Cache-Control: no-store

                                  {"txnId":"txn_001","status":"completed"}
```
HTTP is a request-response, stateless, text-based protocol over TCP. Every element — method (GET/POST/PUT/PATCH/DELETE), status codes (2xx/3xx/4xx/5xx), headers, body — is a Layer 7 concept. HTTP/1.1 issues: head-of-line blocking (a slow response blocks the connection), high header overhead (repeated headers per request), no server push.

**HTTP/2 improvements:**
- **Binary framing:** HTTP/2 replaces text with binary frames — more efficient to parse; frames have type, length, stream ID, flags.
- **Multiplexing:** Multiple request/response pairs share one TCP connection simultaneously via stream IDs. No head-of-line blocking at the HTTP level (though TCP still has it).
- **Header compression (HPACK):** Maintains a header table on both sides; repeated headers are sent as references rather than full strings.
- **Server push:** The server can proactively send resources the client will need before the client requests them.

**DNS — the Layer 7 protocol everyone uses but few think about:**
```
Query:  Who is api.example.com?   (UDP or TCP to port 53)
Answer: api.example.com → A record → 203.0.113.42
        TTL: 300 seconds
```
DNS resolution happens before every TCP connection. A single Node.js `https.request("https://api.example.com/...")` involves: DNS lookup (Layer 7, UDP/TCP, ~1–50ms), TCP handshake (Layer 4, ~1 RTT), TLS handshake (Layer 4/6, 1–2 RTTs), HTTP request/response (Layer 7). DNS caching (OS resolver, Node.js `dns.lookup` caches, TTL-based) reduces the lookup overhead. `dns.setDefaultResultOrder("ipv4first")` in Node.js 17+ controls whether IPv4 or IPv6 addresses are preferred when both are available.

**WebSocket — a Layer 7 protocol built on top of HTTP:**
WebSocket starts as an HTTP/1.1 upgrade request then switches protocols:
```
Client → Server:
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

Server → Client:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

[TCP connection remains open; WebSocket frames flow bidirectionally]
```
After the upgrade, the TCP connection stays open and WebSocket frames (binary Layer 7 PDUs with opcode, masking, payload length) replace HTTP request/response pairs. Fully bidirectional; the server can push frames without a client request.

**gRPC — a modern Layer 7 RPC protocol:**
gRPC uses HTTP/2 for transport and Protocol Buffers for serialisation. Each RPC call is an HTTP/2 stream (POST to a path like `/payments.PaymentService/InitiatePayment`). HTTP/2 multiplexing means multiple concurrent RPCs share one TCP connection without head-of-line blocking at the HTTP level. Binary Protobuf encoding is more compact than JSON. Streaming RPCs (client streaming, server streaming, bidirectional streaming) use HTTP/2 stream continuations.

## Section 3: What Happens When You Make an HTTP Request

**Q11. Walk through every layer involved when a Node.js backend calls `https://api.payment.com/v1/charge` for the first time.**
A: This is the canonical OSI interview question — tracing a real request through all 7 layers:

**Layer 7 — Application:**
Node.js's `https.request()` constructs an HTTP/1.1 (or HTTP/2) request. Before it can send, it needs to resolve `api.payment.com` to an IP address. Node.js calls `dns.lookup("api.payment.com")`, which queries the OS resolver. The OS resolver checks its cache, then queries the configured DNS server (Layer 7, UDP to port 53). The DNS server responds with an A record: `203.0.113.42`, TTL 300s.

**Layer 4 — Transport (TCP + TLS):**
Node.js initiates a TCP connection to `203.0.113.42:443`. The kernel sends a SYN segment (Layer 4 header: src port ephemeral, dst port 443, sequence number, SYN flag). After the three-way handshake establishes the TCP connection, Node.js initiates the TLS 1.3 handshake:
- ClientHello: TLS version, cipher suites, key share (ECDHE public key), SNI (`api.payment.com`).
- ServerHello + Certificate + CertificateVerify + Finished: server's key share, X.509 cert, signature.
- Client Finished: client confirms. Symmetric session keys derived.
Total: 1 RTT for TLS 1.3 (2 RTT for TLS 1.2).

**Layer 6 — Presentation (TLS encryption):**
After the handshake, all Layer 7 data (the HTTP request) is encrypted by TLS using the negotiated symmetric key (AES-256-GCM). The HTTP request bytes become ciphertext. On the receiving side, TLS decrypts the ciphertext back to the HTTP request before handing it to the application.

**Layer 3 — Network (IP):**
The Node.js kernel wraps the TCP segment in an IP packet: source IP (the server's NIC IP), destination IP (`203.0.113.42`), TTL=64, Protocol=6 (TCP). The kernel consults its routing table: is `203.0.113.42` on the local subnet? No → send to the default gateway (e.g., `10.0.0.1`).

**Layer 2 — Data Link (Ethernet):**
To send to the default gateway, the kernel needs its MAC address. ARP: "Who has `10.0.0.1`?" → the gateway replies with its MAC. The kernel wraps the IP packet in an Ethernet frame: destination MAC (gateway's MAC), source MAC (this NIC's MAC), EtherType=0x0800 (IPv4), payload (IP packet), FCS (CRC-32).

**Layer 1 — Physical:**
The NIC serialises the Ethernet frame as electrical signals (voltage transitions on Cat6 cable) or light pulses (if connected via SFP to a fibre uplink). The switch receives the bits, reassembles the frame, looks up the destination MAC in its table, and forwards the frame out the correct port toward the gateway.

**The reverse path (response):**
The server at `203.0.113.42` receives the request through the same layer-by-layer process in reverse. The HTTP response travels back down the server's stack, across the network, and up Node.js's stack — Layer 1 delivers bits, Layer 2 delivers the frame, Layer 3 delivers the packet, Layer 4 delivers the TCP segment and passes the stream to TLS, Layer 6 decrypts it, Layer 7 parses the HTTP response.

**Q12. What changes in this walkthrough when HTTP/2 is used instead of HTTP/1.1?**
A: The lower layers (Physical through Transport) are identical — HTTP/2 still runs over TCP and TLS. The differences are all at Layer 7 and Layer 6:

**Layer 7:**
- HTTP/2 uses binary frames instead of text. The HTTP/2 connection starts with a `PRI * HTTP/2.0` preface (the connection preface), then SETTINGS frames exchanged by both sides.
- Each request/response is a stream identified by a stream ID (odd numbers for client-initiated). The Node.js HTTP/2 client (`http2.connect()`) can send multiple requests simultaneously without waiting for responses:
  ```javascript
  const client = http2.connect("https://api.payment.com");
  const stream1 = client.request({ ":method": "POST", ":path": "/v1/charge" });
  const stream2 = client.request({ ":method": "GET",  ":path": "/v1/status/txn_001" });
  // Both requests are in flight simultaneously over the same TCP connection
  ```
- HPACK header compression: if the `Authorization` header was sent in stream 1, stream 2 can reference it by index rather than resending the full string.

**Layer 6:**
- TLS still provides encryption, but TLS ALPN (Application-Layer Protocol Negotiation) extension in the ClientHello lets the client signal "I support h2" (HTTP/2) and "http/1.1". The server picks the highest mutually supported protocol.

**Layer 4:**
- Still TCP — which is why HTTP/2 still suffers from TCP-level head-of-line blocking. If a segment carrying stream 1's data is lost and retransmitted, streams 2, 3, and 4 (whose segments arrived successfully) wait in the TCP receive buffer until the missing segment is delivered. HTTP/3 (QUIC) solves this by implementing per-stream reliability over UDP — stream 2's data doesn't wait for stream 1's lost retransmission.

## Section 4: Layer-by-Layer Troubleshooting

**Q13. A request from a Node.js service to an external payment API is timing out intermittently. How do you diagnose it layer by layer?**
A: Work from the bottom up — lower layer problems cause higher layer symptoms. Ruling out each layer narrows the cause:

**Layer 1 / Layer 2 — Physical and Data Link:**
```bash
# Check for physical link errors on the NIC
ethtool eth0               # link detected? speed/duplex negotiated correctly?
ip link show eth0          # UP? RX/TX packet counts growing?
ifconfig eth0              # rx errors, tx errors, dropped packets?
netstat -s | grep errors   # socket-level error counts
```
High `rx_dropped` or `rx_errors` indicate Layer 1/2 problems. If running in AWS/cloud, these are abstracted — move to Layer 3.

**Layer 3 — Network:**
```bash
# Can we reach the destination IP at all?
ping api.payment.com              # ICMP echo — tests Layer 3 reachability
traceroute api.payment.com        # shows each hop; identifies where packets stop
mtr api.payment.com               # continuous traceroute; shows packet loss per hop

# Check routing table
ip route get 203.0.113.42         # which interface and gateway is used?

# AWS-specific: security group rules, NACLs, route tables
aws ec2 describe-security-groups
```
ICMP blocked (no `ping` response) doesn't mean the service is down — check TCP specifically.

**Layer 4 — Transport:**
```bash
# Can we establish a TCP connection?
telnet api.payment.com 443         # opens TCP connection to port 443
nc -zv api.payment.com 443         # netcat TCP probe
curl -v --connect-timeout 5 https://api.payment.com/health   # full cycle

# Check for connection timeouts vs RSTs
ss -tn state time-wait             # TIME_WAIT sockets (exhausted ephemeral ports?)
ss -tn | grep 443                  # established connections to this service
cat /proc/sys/net/ipv4/ip_local_port_range  # ephemeral port range

# TCP retransmission rate
netstat -s | grep retransmit       # high retransmission = packet loss on path
ss -ti dst 203.0.113.42            # TCP info: RTT, congestion window, retrans count
```
Intermittent TCP timeouts but successful `ping`: Layer 4 issue (firewall blocking TCP, port exhaustion, half-open connection accumulation).

**Layer 6 — Presentation (TLS):**
```bash
# TLS handshake analysis
openssl s_client -connect api.payment.com:443 -tls1_3  # TLS 1.3 handshake
openssl s_client -connect api.payment.com:443 -msg     # show all TLS messages
curl -v --tlsv1.3 https://api.payment.com/health       # TLS version negotiation

# Certificate validity
openssl s_client -connect api.payment.com:443 </dev/null | \
  openssl x509 -noout -dates     # check expiry
```
TLS handshake timeout: certificate expired, CA chain misconfigured, cipher suite mismatch, client certificate required but not provided (mTLS).

**Layer 7 — Application:**
```bash
# Full HTTP request/response trace
curl -v --trace-time https://api.payment.com/v1/health
# Shows DNS time, connect time, TLS time, first byte time (TTFB), transfer time

# In Node.js: timing breakdown
const https = require("https");
const start = {};
const req = https.request(url, (res) => {
  console.log("status:", res.statusCode);
  console.log("TTFB:", Date.now() - start.connected, "ms");
});
req.on("socket", (socket) => {
  socket.on("lookup",  () => (start.lookup  = Date.now()));
  socket.on("connect", () => (start.connected = Date.now()));
  socket.on("secureConnect", () => console.log("TLS:", Date.now() - start.connected, "ms"));
});
```
Layer 7 diagnosis: HTTP 429 (rate limited), HTTP 503 (service unavailable), large response body causing timeout before full read, DNS returning stale IP (TTL too long), connection keep-alive expiring on the server side while Node.js reuses the connection.

**Q14. What is an MTU, and how does an MTU mismatch cause mysterious packet loss?**
A: MTU (Maximum Transmission Unit) is the largest Layer 3 packet (IP datagram) that a network link can carry without fragmentation. It's defined at Layer 2 — Ethernet's MTU is 1500 bytes. Jumbo frames (AWS VPC, data centre switches) allow 9000–9001 bytes. The Path MTU is the smallest MTU across all hops between source and destination.

MTU mismatch scenario — the "black hole" problem:
```
Node.js server           AWS NAT Gateway          Internet Router
MTU = 9001 (jumbo)       MTU = 1500               MTU = 1500
     │                        │                        │
     │  IP packet 8000 bytes  │                        │
     │ ──────────────────────▶│                        │
     │                        │ ICMP "Fragmentation    │
     │                        │ Needed" (DF bit set)   │
     │                        │ ◀──────────────────────│
     │                        │                        │
     │ ICMP blocked by        │                        │
     │ security group!        │                        │
     │ ◀─  ✗  ─────────────  │                        │
     │                        │                        │
     │ TCP retransmits 8000-byte segment repeatedly   │
     │ — never gets smaller — connection hangs         │
```

TCP uses Path MTU Discovery (PMTUD): sends packets with the "Don't Fragment" (DF) bit set in the IP header. If a router can't forward the packet without fragmenting it, it returns an ICMP "Fragmentation Needed" message with the allowed MTU size. TCP reduces its MSS (Maximum Segment Size) and retransmits. But if a firewall (AWS Security Group, network ACL) blocks ICMP, the PMTUD fails silently — TCP keeps sending large packets, they're silently dropped by the MTU-limited hop, TCP retransmits indefinitely, the connection hangs.

Symptoms: connections work for small requests/responses but hang for large payloads; `ping` works; HTTP `HEAD` works but `GET` (large response) times out.

Fix:
```bash
# Clamp TCP MSS at the firewall/NAT to prevent oversized segments
# (Linux iptables — on the gateway)
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu

# Or: allow ICMP type 3 (Destination Unreachable) in AWS Security Groups
# — specifically code 4 (Fragmentation Needed)

# Test: send a large ICMP ping with DF bit set
ping -M do -s 1400 api.payment.com   # -M do = DF bit; -s 1400 bytes payload
```

## Section 5: Modern Protocol Context

**Q15. Where does TLS fit in the OSI model, and why is there debate?**
A: TLS (Transport Layer Security) doesn't fit cleanly into one OSI layer — it spans multiple:

**Arguments for Layer 4 (Transport):** TLS sits directly above TCP and below any application protocol. From TCP's perspective, TLS is application data. From the application's perspective, TLS provides a reliable, ordered, encrypted byte stream — the same abstraction TCP provides for unencrypted data. TLS handles connection establishment (handshake), session management (session resumption), and teardown — transport-like concerns.

**Arguments for Layer 6 (Presentation):** TLS provides encryption (data transformation from plaintext to ciphertext — a Presentation layer function), authentication (certificate validation), and session management (Layer 5). It translates the application's plaintext into the encrypted form suitable for network transmission — exactly what Layer 6 is defined to do.

**Arguments for Layer 5 (Session):** TLS session resumption (TLS tickets, session IDs) is a Layer 5 function — maintaining session state across connections.

**The pragmatic answer:** TLS is a Layers 5-6 protocol that operates between TCP (Layer 4) and the application protocol (Layer 7). Most working engineers describe it as "above TCP, below HTTP" or simply "Layer 4.5" — acknowledging that the real world doesn't map cleanly to the OSI model. In Node.js: the TLS implementation (`tls` module) wraps a TCP socket and presents a `TLSSocket` interface that HTTP, gRPC, WebSocket, and other Layer 7 protocols use without awareness of the encryption below.

**Q16. What is QUIC, and how does it change the layer model?**
A: QUIC (Quick UDP Internet Connections) is a transport protocol developed by Google and standardised as RFC 9000. It implements all the reliability features of TCP, multiplexing without head-of-line blocking, and TLS 1.3 encryption — all in a single protocol built on UDP. HTTP/3 runs over QUIC.

```
HTTP/1.1 and HTTP/2 stack:   HTTP/3 (QUIC) stack:
─────────────────────────    ────────────────────────
L7: HTTP                     L7: HTTP/3
L6: TLS 1.2 / 1.3           L6: TLS 1.3 (built into QUIC)
L4: TCP                      L4: QUIC (over UDP)
L3: IP                       L3: IP
```

Why QUIC changes things:
- **0-RTT connection establishment (often):** QUIC combines the TLS handshake with the connection setup — first connection is 1-RTT; resumed connections can send data immediately (0-RTT). HTTP/2 over TCP + TLS 1.3 is also 1-RTT for the connection (if TCP Fast Open is used) but typically requires the TCP handshake first.
- **No TCP head-of-line blocking:** QUIC streams are independent — a lost packet retransmission for stream 1 doesn't block stream 2's data from being delivered to the application. HTTP/2 over TCP can't achieve this because TCP must deliver bytes in order.
- **Connection migration:** A QUIC connection has a connection ID independent of the IP:port 4-tuple. If a mobile client switches from Wi-Fi to cellular (IP changes), the QUIC connection continues without re-handshaking. TCP connections are tied to the 4-tuple — any IP/port change breaks them.
- **Encrypted by default:** There is no unencrypted QUIC (unlike TCP, where TLS is optional). QUIC always encrypts — even the packet headers are protected.

Node.js QUIC: experimental support via `node:net` with QUIC flag or the `@failing-test/quic` packages. AWS CloudFront and ALB support HTTP/3. For backend-to-backend service mesh, QUIC/HTTP/3 is not yet standard — gRPC still primarily uses HTTP/2 over TLS/TCP.

**Q17. How does DNS resolution work across all relevant OSI layers?**
A: DNS is a Layer 7 protocol that uses UDP (Layer 4) primarily, with TCP (Layer 4) as a fallback for large responses. Tracing a DNS lookup for `api.payment.com`:

```
Node.js calls dns.lookup("api.payment.com")
    │
    ▼
OS stub resolver checks:
  1. /etc/hosts (local file — no network)
  2. Local resolver cache (OS DNS cache — no network)
  3. If cache miss → query the recursive resolver
    │
    ▼ UDP port 53 to 8.8.8.8 (Google DNS) or VPC DNS resolver
Layer 7: DNS query message
  {
    QType: A (IPv4 address),
    QName: api.payment.com,
    ID: 0x1234 (to match response to query),
    RD: 1 (recursion desired)
  }
Layer 4: UDP datagram (src: ephemeral port, dst: 53)
Layer 3: IP packet (src: instance IP, dst: 8.8.8.8)
Layer 2: Ethernet frame → to default gateway
Layer 1: bits on the wire

Recursive resolver (8.8.8.8) does iterative resolution:
  → Queries root nameservers: "Who handles .com?"
  → Queries .com TLD servers: "Who handles payment.com?"
  → Queries payment.com authoritative nameserver: "What's api.payment.com?"
  → Receives: api.payment.com A 203.0.113.42 TTL=300

Response travels back through the same layers to Node.js:
  Node.js receives the IP: 203.0.113.42
  → proceed with TCP connection
```

DNS over TCP (fallback): If the DNS response exceeds 512 bytes (or 4096 bytes with EDNS0 extension), the resolver sets the TC (truncated) bit and the client retries over TCP. DNSSEC responses often exceed 512 bytes due to digital signatures.

DNS over HTTPS (DoH) and DNS over TLS (DoT): modern encrypted DNS protocols that prevent ISP interception of DNS queries. Not standard in backend services yet but increasingly relevant for privacy-sensitive deployments.

**Relevance for backend engineers:** DNS TTL tuning for blue-green deployments and failover (low TTL during migrations → more DNS queries but faster failover). DNS caching in Node.js — `dns.lookup` caches results for the process lifetime by default (no TTL respect). Use `dns.resolve` (which does respect TTL) or set `family` and `hints` explicitly. AWS Route 53 health checks + failover routing for multi-region HA.

## Section 6: Layer Violations and Real-World Blurring

**Q18. What are common examples of protocols that violate clean OSI layer separation?**
A: The OSI model is a reference, not a law. Real protocols frequently blur or skip layers — which is useful to recognise rather than treat as "wrong":

**ARP — operates between Layer 2 and Layer 3:**
ARP translates Layer 3 IP addresses to Layer 2 MAC addresses. It uses Ethernet frames (Layer 2) but carries IP addresses (Layer 3 information). It's often described as "Layer 2.5" or "between L2 and L3." IPv6 replaces ARP with NDP (Neighbor Discovery Protocol), which runs over ICMPv6 (Layer 3).

**ICMP — lives at Layer 3 but serves Layers 3 and 4:**
ICMP is encapsulated in IP packets (Layer 3) and is used for network diagnostics (ping, traceroute — Layer 3 concerns) and to communicate TCP errors to senders (ICMP "Port Unreachable" in response to UDP sent to a closed port — a Layer 4 event communicated via a Layer 3 message).

**TLS — spans Layers 4–6:**
As discussed in Q15. TLS is simultaneously transport-security (L4 concern), session management (L5), and encryption/encoding (L6).

**HTTP/2 — Layer 7 absorbing Layer 5 and 6:**
HTTP/2's stream multiplexing is a Layer 5 (session) function. HPACK header compression is a Layer 6 (presentation) function. Both are implemented entirely within what is nominally a Layer 7 protocol.

**VXLAN — Layer 2 over Layer 3/4:**
VXLAN (Virtual Extensible LAN) encapsulates Layer 2 Ethernet frames inside UDP (Layer 4) packets. This is "L2 over L3+L4" — used for overlay networks in data centres and AWS VPC (internally). It allows Layer 2 broadcast domains to span Layer 3 boundaries — logical VLANs that span physical data centres.

**IPsec — Layer 3 encryption:**
IPsec encrypts and authenticates IP packets (Layer 3), not transport segments or application data. An IPsec VPN appears as a Layer 3 network path — all traffic between two networks is encrypted at the IP layer without any application knowledge.

**Q19. How do load balancers operate at different OSI layers, and what are the tradeoffs?**
A: Load balancers are categorised by which layer's information they use for routing decisions:

**Layer 4 Load Balancer (Transport LB):**
Routes based on TCP/UDP headers — source/destination IP, port, and TCP connection state. Does not inspect the payload.

- **Pros:** Extremely fast (no payload parsing); handles any TCP/UDP protocol (HTTPS, gRPC, custom binary protocols); lower latency than L7.
- **Cons:** Cannot route based on URL path, HTTP headers, cookies, or request body; cannot terminate TLS (routes encrypted bytes without seeing them); cannot add/remove headers; no HTTP-aware health checks.
- **Examples:** AWS NLB, HAProxy in TCP mode, Linux `ipvs` (used by Kubernetes kube-proxy).
- **Use cases:** Ultra-low-latency routing (financial trading), non-HTTP protocols, when the backend handles TLS termination.

**Layer 7 Load Balancer (Application LB):**
Terminates the client's TCP + TLS connection, parses the Layer 7 protocol (HTTP/gRPC), and makes routing decisions based on URL path, hostname, HTTP headers, cookies, or body content. Establishes a new TCP connection to the chosen backend.

- **Pros:** Content-based routing (`/api/payments` → PaymentService, `/api/users` → UserService); SSL termination; header manipulation (add `X-Request-ID`, strip internal headers); HTTP health checks; session affinity (sticky sessions via cookie); WebSocket upgrades.
- **Cons:** Higher latency than L4 (must parse HTTP before forwarding); must handle TLS termination (adds CPU for certificate management); cannot route non-HTTP protocols without reconfiguration.
- **Examples:** AWS ALB, nginx (in HTTP proxy mode), HAProxy in HTTP mode, Envoy, Traefik.
- **Use cases:** HTTP microservices, API gateways, blue-green deployments (route % of traffic by header), A/B testing.

**AWS NLB vs ALB — the canonical backend interview comparison:**

| Dimension | NLB (Layer 4) | ALB (Layer 7) |
|---|---|---|
| **Protocol** | TCP, UDP, TLS passthrough | HTTP, HTTPS, WebSocket, gRPC |
| **Latency** | < 1ms (ultra-low) | ~1–5ms (HTTP parsing overhead) |
| **TLS termination** | Optional (passthrough or terminate) | Always terminates |
| **Content routing** | No | Yes (path, host, header, query) |
| **Source IP preservation** | Yes (proxy protocol or direct) | Via `X-Forwarded-For` header |
| **Static IP / Elastic IP** | Yes | No (DNS name only) |
| **WebSocket** | Yes (any TCP) | Yes (explicit support) |
| **Health checks** | TCP / HTTP | HTTP / HTTPS (path-based) |
| **Cost** | Lower | Higher (more processing) |

## Section 7: Scenario / System Design Style Questions

**Q20. "Your Node.js payment API service is randomly dropping 0.1% of requests with connection reset errors (ECONNRESET). How do you diagnose which OSI layer is responsible?"**
A: ECONNRESET means a TCP RST was received — the remote end abruptly terminated the connection. Work through the layers:

**Layer 1/2 — Physical/Data Link:**
```bash
ethtool -S eth0 | grep -i error   # NIC hardware error counters
ip -s link show eth0               # rx_errors, tx_dropped
```
NIC errors at Layer 1/2 → packet loss → TCP retransmission → eventual RST if timeout exceeded. AWS instances: check CloudWatch `NetworkPacketsIn/Out` and look for drops.

**Layer 3 — Network:**
0.1% loss suggests a specific path issue. Check with `mtr` over time:
```bash
mtr --report --report-cycles 1000 <destination>  # 1000 packets, show loss per hop
```
If a specific intermediate hop shows consistent 0.1% loss → routing or hardware issue on that path. AWS: check VPC Flow Logs for rejected packets, check NAT gateway metrics.

**Layer 4 — Transport:**
RSTs are a TCP-level event. Common Layer 4 causes:
- **Load balancer idle timeout:** AWS ALB has a 60-second idle timeout. A connection idle for >60s receives a RST from the ALB. Fix: `net.Socket.setKeepAlive(true, 30000)` in Node.js — keepalive probes prevent idle detection; or reduce the connection pool idle timeout below 60s.
- **Server-side connection pool limit:** Backend exhausts its connection pool; new connections get RST immediately.
- **Ephemeral port exhaustion:** `ss -s` shows many TIME_WAIT sockets consuming ephemeral ports.
- **Firewall stateful session table overflow:** Stateful firewalls track connections; overflow drops packets → one side sees an RST.

```bash
ss -tn state time-wait | wc -l     # count TIME_WAIT sockets
cat /proc/sys/net/ipv4/tcp_tw_reuse  # can TIME_WAIT sockets be reused?
netstat -s | grep "connection resets"
```

**Layer 7 — Application:**
0.1% could be specific requests (large payloads hitting ALB's 1MB body limit, specific endpoints triggering a bug). Check access logs for correlation:
```javascript
// Node.js: log which requests get ECONNRESET
http.request(options)
  .on("error", (err) => {
    if (err.code === "ECONNRESET") {
      console.error("ECONNRESET on", options.path, err.message);
    }
  });
```

Most likely cause for 0.1% ECONNRESET with a payment API behind an ALB: the ALB idle timeout is shorter than the connection pool's idle timeout. A pooled connection that has been idle for >60s (ALB's default) is reset by the ALB when the next request tries to reuse it. Fix: set `idleTimeoutMillis: 50000` (50s < 60s ALB timeout) in the HTTP agent's `keepAlive` options.

**Q21. "Design the networking layer for a payment processing system that must meet PCI DSS requirements. Walk through which OSI layers each control applies to."**
A: PCI DSS (Payment Card Industry Data Security Standard) mandates specific controls that map to specific OSI layers:

**Layer 1/2 — Physical and Data Link: Network Segmentation**
- Payment servers (cardholder data environment, CDE) must be on a separate VLAN from other systems. 802.1Q VLAN tagging isolates L2 broadcast domains — a compromised non-CDE host cannot ARP-spoof payment hosts on a different VLAN.
- AWS: separate VPC or isolated subnets with no route table entries between CDE and non-CDE subnets. Security groups act as the isolation boundary.

**Layer 3 — Network: Firewall Rules (Requirement 1)**
- Inbound to CDE: only allowed source IPs and protocols. Restrict to specific source CIDR ranges; deny all else.
- Outbound from CDE: restrict to only necessary destinations (payment gateway IP ranges, database, logging).
- AWS: NACLs (Network Access Control Lists) provide stateless L3/L4 filtering; Security Groups provide stateful L4 filtering per instance.
- No direct internet access to CDE hosts — all traffic through a WAF and L7 load balancer.

**Layer 4 — Transport: TLS Everywhere (Requirement 4)**
- All cardholder data in transit must be encrypted with TLS 1.2+ (TLS 1.3 preferred). TLS 1.0 and 1.1 are explicitly prohibited.
- Internal service-to-service: mutual TLS (mTLS) — both client and server present certificates. The payment microservice verifies that only the API service (not a compromised internal service) can send requests.
- Database connections: PostgreSQL `sslmode=require` with certificate verification.
- Node.js: `tls.createServer({ minVersion: "TLSv1.2", requestCert: true, rejectUnauthorized: true })`.

**Layer 6 — Presentation: Encryption and Key Management (Requirement 3)**
- Stored PAN (Primary Account Number — the card number) must be rendered unreadable. Not a Layer 6 network concern, but the same cryptographic primitives: AES-256 encryption, RSA for key transport, HMAC for integrity.
- TLS cipher suites: only AEAD ciphers (AES-GCM, ChaCha20-Poly1305). Forward secrecy required (ECDHE key exchange — session keys are ephemeral; past sessions can't be decrypted even if the private key is later compromised).

**Layer 7 — Application: WAF, Rate Limiting, Audit Logging (Requirements 6, 7, 10)**
- WAF (Web Application Firewall) at Layer 7: blocks SQLi, XSS, directory traversal attempts. AWS WAF attached to ALB.
- Rate limiting at Layer 7: per-IP and per-account limits on payment endpoints to prevent credential stuffing and enumeration.
- Audit logging: every HTTP request to the CDE — source IP, timestamp, URL, response code, user ID — logged with tamper-evident hash chaining (CERT-In requirement for financial services). Layer 7 application logs, stored in S3 with CloudWatch Logs, replicated to a separate logging account with write-once policy.
- API versioning with deprecation of weak authentication endpoints.

**Q22. "Explain what happens at each OSI layer when a WebSocket connection is established from a browser client to your Node.js server."**
A: WebSocket is a Layer 7 protocol that begins as HTTP and upgrades. Tracing each layer:

**Layer 1 — Physical:** The client's NIC encodes bits on the wire (Wi-Fi radio, Ethernet cable). Nothing WebSocket-specific.

**Layer 2 — Data Link:** Ethernet frames carry IP packets between the client and the first-hop router. The browser's OS constructs Ethernet frames using the router's MAC address (obtained via ARP). No WebSocket awareness.

**Layer 3 — Network:** IP packets route the client's segments from its IP to the server's IP across potentially many hops. TTL decrements at each router. The server IP is resolved via DNS before this step.

**Layer 4 — Transport (TCP):** The browser initiates a TCP connection (three-way handshake) to the server's IP on port 443 (WSS) or 80 (WS). TCP provides the reliable byte stream that HTTP and then WebSocket will use. After the WebSocket upgrade, the same TCP connection stays open indefinitely for bidirectional frame exchange.

**Layer 6 — Presentation (TLS for WSS):** For `wss://` (WebSocket Secure), TLS is negotiated after the TCP handshake. The TLS handshake authenticates the server certificate and establishes symmetric encryption keys. All subsequent data (including the HTTP upgrade request and all WebSocket frames) is encrypted.

**Layer 7 — Application (HTTP upgrade + WebSocket frames):**

Step 1: HTTP upgrade request:
```
GET /ws HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

Step 2: Server's HTTP 101 response:
```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```
(`Sec-WebSocket-Accept` = base64(SHA1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11")))

Step 3: WebSocket frame exchange (both directions simultaneously):
```
WebSocket frame structure:
┌──┬──┬──┬──┬──────┬──────┬────────────────────────────────────────┐
│FIN│RSV│RSV│RSV│Opcode│MASK │  Payload Length  │ Masking Key │ Payload │
│(1)│(1)│(1)│(1)│ (4b) │ (1b)│     (7/23/71b)  │   (0/4B)   │         │
└──┴──┴──┴──┴──────┴──────┴────────────────────────────────────────┘
```
Opcodes: 0x1 = text frame, 0x2 = binary frame, 0x8 = close, 0x9 = ping, 0xA = pong.
Client-to-server frames must be masked (MASK=1); server-to-client frames are unmasked.

Node.js WebSocket handling:
```javascript
const { WebSocketServer } = require("ws");
const wss = new WebSocketServer({ server: httpsServer });

wss.on("connection", (ws, req) => {
  // TCP connection established, HTTP upgrade complete, WebSocket session open
  // All of this is Layer 7; the layers below are invisible here

  ws.on("message", (data) => {
    // data is a Buffer or string — one complete WebSocket frame's payload
    // WebSocket frame boundaries are handled by the ws library (Layer 7)
    const event = JSON.parse(data);
    ws.send(JSON.stringify({ ack: event.id }));
  });

  ws.on("close", (code, reason) => {
    // WebSocket close frame received (opcode 0x8)
    // TCP connection may or may not close immediately after
  });
});
```

## Quick Reference: OSI Layer Cheat Sheet

```
Layer 7 — Application
  PDU:      Data
  Protocols: HTTP/1.1, HTTP/2, HTTP/3, DNS, SMTP, FTP, SSH, WebSocket,
             gRPC, MQTT, AMQP, LDAP, SNMP
  Devices:  Application servers, API gateways, WAF, reverse proxies
  Key concept: Application-specific message formats and semantics

Layer 6 — Presentation
  PDU:      Data (transformed)
  Protocols: TLS/SSL, MIME, ASCII/UTF-8, JSON, XML, Protobuf, JPEG, MPEG
  Devices:  (Handled by protocol libraries, not dedicated hardware)
  Key concept: Encoding, encryption, compression

Layer 5 — Session
  PDU:      Data (with session context)
  Protocols: TLS session resumption, NetBIOS, RPC, SQL sessions, NFS
  Devices:  (Handled within application and TLS implementations)
  Key concept: Session establishment, management, synchronisation

Layer 4 — Transport
  PDU:      Segment (TCP) / Datagram (UDP)
  Protocols: TCP, UDP, QUIC, SCTP, DCCP
  Devices:  Load balancers (L4), firewalls (stateful), NAT gateways
  Key concept: Port numbers, reliability, flow control, congestion control

Layer 3 — Network
  PDU:      Packet
  Protocols: IPv4, IPv6, ICMP, ICMPv6, OSPF, BGP, ARP, IGMP
```

**Tip for the interview:** At 5 YOE, OSI layer questions don't come as "recite all 7 layers" — they come embedded in debugging scenarios ("ECONNRESET on 0.1% of requests — where do you look?"), design questions ("how do ALB and NLB differ, and when do you use each?"), or incident post-mortems ("why did large payloads silently hang but small ones worked?" — MTU and ICMP blocking). The answers that land demonstrate using the model as a systematic diagnostic framework: start at Layer 1/2 for physical issues, Layer 3 for routing/firewall, Layer 4 for TCP semantics and port exhaustion, Layer 6 for TLS misconfiguration, Layer 7 for HTTP protocol and application logic. Have one concrete story ready — an MTU issue, an ECONNRESET from ALB idle timeout, a DNS TTL misconfiguration — and trace it through the relevant layers. That's the framing that signals senior-level networking literacy.
