# Networking / Computer Science: TCP vs HTTP Keep-Alive — Don't Confuse These — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. Why is "keep-alive" one of the most reliably confused terms in networking interviews?**
A: Because it is genuinely two completely different mechanisms that share the same name, operate at different OSI layers, solve different problems, are configured differently, and have different failure modes — yet both appear in production systems constantly, and developers encounter both without always realising they are distinct things.

The confusion is compounded by the fact that HTTP/1.1 overloaded the term with its `Connection: keep-alive` and `Keep-Alive:` headers, while TCP's keep-alive is configured entirely at the socket/OS level and is invisible to HTTP. A developer who writes `keepAlive: true` in a Node.js `http.Agent` is enabling HTTP connection reuse. A developer who calls `socket.setKeepAlive(true)` on the same machine is enabling TCP-level probe packets. Both are called "keep-alive." Neither is the other.

The single-sentence distinction to memorise first and build everything else from:

> **TCP keep-alive** detects dead connections by sending probe packets at the OS level.
> **HTTP keep-alive** reuses TCP connections across multiple HTTP requests at the application level.

**Q2. At what layer does each mechanism operate?**
A: Placing them in the network stack makes the separation concrete:

```
OSI Layer 7 — Application
  HTTP keep-alive (Connection: keep-alive, Keep-Alive: header)
  ↕ HTTP request/response messages
─────────────────────────────────────────────────────────────
OSI Layer 4 — Transport
  TCP keep-alive (SO_KEEPALIVE socket option, kernel probe packets)
  ↕ TCP segments, ACKs
─────────────────────────────────────────────────────────────
OSI Layer 3 — Network
  IP datagrams
─────────────────────────────────────────────────────────────
OSI Layer 1/2 — Physical / Data Link
  Ethernet frames, Wi-Fi frames
```

HTTP keep-alive is a feature of the HTTP protocol — it is expressed in HTTP headers and controls whether the HTTP library closes or reuses the underlying TCP socket after a response is delivered. TCP keep-alive is a feature of the TCP/IP stack — it is enabled by a socket option and causes the kernel to send periodic probe segments when the connection has been idle, completely independently of what the application is doing.

An HTTP keep-alive connection can have TCP keep-alive disabled. A non-HTTP TCP socket (a database connection, a raw socket, a game server connection) can have TCP keep-alive enabled. The two are orthogonal.

**Q3. What problem does each one solve?**
A: The problems are as different as the layers:

**HTTP keep-alive** solves the **connection setup overhead problem**. In HTTP/1.0, every request required a new TCP connection: TCP three-way handshake (1 RTT), optionally TLS handshake (1–2 RTT), slow-start ramp-up, then the actual request. For a page with 30 assets, that is 30 × (1–3 RTT) of pure overhead before any useful data. HTTP keep-alive reuses the established connection for subsequent requests — paying the setup cost once.

**TCP keep-alive** solves the **half-open connection detection problem**. When one end of a TCP connection crashes, reboots, or is silently disconnected (NAT table expiry, cable unplugged), the other end has no way to know. It holds a socket in ESTABLISHED state, waiting indefinitely for data that will never come. TCP keep-alive sends probe packets during idle periods; if the peer does not respond, the connection is declared dead and closed, freeing resources and allowing the application to reconnect.

```
HTTP keep-alive:  "Don't close this TCP connection after the response —
                   I want to reuse it for the next HTTP request."

TCP keep-alive:   "Is this connection still alive? Send me something.
                   I haven't heard from you in two hours."
```

## Section 2: TCP Keep-Alive

**Q4. How does TCP keep-alive work mechanically?**
A: TCP keep-alive is implemented entirely in the kernel. When a socket has `SO_KEEPALIVE` enabled and the connection has been idle (no data sent or received) for a configured interval, the kernel sends a **keep-alive probe** — a TCP segment with no payload (or a single zero byte in some implementations) and an ACK number equal to the current sequence number minus one (or the sequence number of the last byte sent, depending on implementation). This segment will not advance the receiver's sequence number — it is designed solely to elicit an ACK.

Three kernel parameters control the behaviour:

```
tcp_keepalive_time    — idle time before the first probe is sent
                        Linux default: 7200 seconds (2 hours)
                        Typical production tuning: 60–300 seconds

tcp_keepalive_intvl   — interval between successive probes if no response
                        Linux default: 75 seconds

tcp_keepalive_probes  — number of unanswered probes before declaring connection dead
                        Linux default: 9
```

The timeline with Linux defaults:

```
t=0:       Last data exchanged. Connection goes idle.
t=7200s:   First probe sent. Peer responds with ACK → timer resets.
t=14400s:  Another probe if idle again.

If peer is gone:
t=7200s:   First probe. No response.
t=7275s:   Second probe. No response.
t=7350s:   Third probe. No response.
...
t=7875s:   Ninth probe. No response.
t=7875s:   Kernel closes connection with ETIMEDOUT.
             Application's next read/write gets ECONNRESET or EPIPE.
```

With Linux defaults, a dead connection is not detected for **over 2 hours**. This is fine for long-lived database connections where both sides are actively exchanging heartbeats at the application level. It is unacceptable for NAT-traversal scenarios where NAT tables expire in minutes — requiring much shorter `tcp_keepalive_time` values.

**Q5. What is a half-open connection, and why does TCP keep-alive exist to address it?**
A: A half-open connection is a TCP connection that one side believes is ESTABLISHED while the other side has no record of it (because it crashed, rebooted, or was silently interrupted). The side that still has connection state will sit in ESTABLISHED forever, consuming a socket and memory, unable to proceed.

Classic scenario:

```
t=0:     Client and server establish a TCP connection (database connection pool).
t=100s:  Server-side network switch is replaced. Server's kernel connection state is lost.
t=100s:  Server reboots with no memory of the connection.
t=100s:  Client still shows connection as ESTABLISHED — it hasn't tried to send yet.
t=3600s: Application on the client tries to execute a SQL query.
         Sends data on the "established" connection.
         Server receives data with no matching connection → sends RST.
         Client gets ECONNRESET. Query fails.
```

Without TCP keep-alive, the stale connection is only discovered when the application tries to use it. With TCP keep-alive, the kernel would have detected the dead connection during the idle period and notified the application hours before the query attempt.

Other causes of half-open connections:
- **NAT table expiry**: a NAT device (home router, cloud NAT gateway) silently removes a mapping for an idle connection. Both endpoints still think the connection is alive; packets from either side are silently dropped by the NAT. TCP keep-alive probes, if sent before the NAT timeout, keep the mapping alive.
- **Firewalls with stateful inspection**: similar to NAT — idle connections are evicted from the state table.
- **Process crash without FIN**: a process that crashes without calling `close()` on its sockets — the kernel sends FIN on behalf of the exiting process in most cases, but a kernel panic or SIGKILL can prevent even this.

**Q6. How do you enable and configure TCP keep-alive at the application level?**
A: TCP keep-alive is enabled per-socket via the `SO_KEEPALIVE` socket option, and tuned per-socket via `TCP_KEEPIDLE`, `TCP_KEEPINTVL`, and `TCP_KEEPCNT` (Linux) which override the system-wide kernel parameters for that specific socket.

**In C (POSIX):**
```c
int fd = socket(AF_INET, SOCK_STREAM, 0);

int enable = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &enable, sizeof(enable));

int idle    = 60;  // seconds before first probe
int intvl   = 10;  // seconds between probes
int cnt     = 5;   // number of probes before giving up
setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE,  &idle,  sizeof(idle));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &intvl, sizeof(intvl));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT,   &cnt,   sizeof(cnt));
```

**In Node.js:**
```js
const net = require("net");
const socket = new net.Socket();

// Enable TCP keep-alive with initial delay of 60 seconds
// (sets SO_KEEPALIVE; the delay maps to TCP_KEEPIDLE on Linux)
socket.setKeepAlive(true, 60000); // 60,000ms = 60s idle before first probe
```

**In Go:**
```go
// net.Dialer enables TCP keep-alive by default since Go 1.13
dialer := &net.Dialer{
    KeepAlive: 30 * time.Second, // TCP_KEEPIDLE equivalent
}
conn, err := dialer.Dial("tcp", "db.example.com:5432")
```

**In Python:**
```python
import socket

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE,  60)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT,    5)
```

**Q7. What are the limitations of TCP keep-alive?**
A: TCP keep-alive is powerful but has real constraints that drive applications to implement their own heartbeat mechanisms:

- **Two-hour default is useless for NAT traversal.** Most NAT devices expire idle UDP/TCP entries after 30–300 seconds. The Linux default `tcp_keepalive_time` of 7200 seconds means the first probe fires long after the NAT entry is gone. Per-socket tuning to 15–30 seconds is required, but this adds probe traffic for every idle connection.
- **Does not detect application-level failure.** TCP keep-alive verifies the TCP stack on the other end is responding. It does not verify the application is healthy. A database server whose kernel is running but whose Postgres process is deadlocked will respond to TCP keep-alive probes perfectly — the connection appears alive while every query hangs. Application-level heartbeats (SELECT 1, PING, custom health frames) are needed for this.
- **Not universally respected by middleboxes.** Some enterprise firewalls and load balancers drop keep-alive probes or reset connections that send them. Production systems in such environments must rely on application-level heartbeats instead.
- **No acknowledgement at the application layer.** The kernel handles probes silently. The application only learns about connection death when a subsequent `read()` or `write()` fails with `ECONNRESET` or `ETIMEDOUT` — it cannot register a callback for "probe failed."
- **Shared vs per-socket parameters.** The system-wide kernel parameters (`tcp_keepalive_time` etc.) apply to all sockets that have `SO_KEEPALIVE` but no per-socket overrides. A system running both database connections (want 30s keep-alive) and long-lived idle admin connections (want 600s keep-alive) must set per-socket parameters for each.

## Section 3: HTTP Keep-Alive

**Q8. What is HTTP keep-alive, and what problem does it solve?**
A: HTTP keep-alive (also called HTTP persistent connections) allows multiple HTTP request-response exchanges to be sent over a single TCP connection. Without it, each HTTP request requires:

```
Without keep-alive (HTTP/1.0 default):
  Request 1: TCP SYN → SYN-ACK → ACK         (1 RTT)
             [TLS handshake if HTTPS]          (1-2 RTT)
             GET /index.html → 200 OK          (1 RTT)
             TCP FIN → FIN-ACK → ACK          (close)

  Request 2: TCP SYN → SYN-ACK → ACK         (1 RTT again)
             [TLS handshake again]             (1-2 RTT again)
             GET /style.css → 200 OK           (1 RTT)
             TCP FIN → FIN-ACK → ACK

  Request 3: (same overhead again)
  ...
  30 requests = 30 × (3-5 RTT setup overhead) before any useful data
```

With keep-alive, the TCP connection established for request 1 is reused for requests 2, 3, … N. The handshake overhead is paid once.

```
With keep-alive (HTTP/1.1 default):
  TCP SYN → SYN-ACK → ACK                    (1 RTT, once)
  [TLS handshake]                             (1-2 RTT, once)
  GET /index.html → 200 OK                   (1 RTT)
  GET /style.css  → 200 OK                   (1 RTT, same connection)
  GET /app.js     → 200 OK                   (1 RTT, same connection)
  ...
  GET /image30.png → 200 OK                  (1 RTT, same connection)
  TCP FIN                                    (once, at the end)

  30 requests = 3-5 RTT setup + 30 RTT for requests
  (vs 30 × 3-5 RTT + 30 RTT without keep-alive)
```

**Q9. How is HTTP keep-alive negotiated in HTTP/1.0 vs HTTP/1.1?**
A: The defaults are opposite in each version, which is a source of bugs in systems that mix HTTP versions:

**HTTP/1.0**: connections are **closed by default** after each response. To opt into persistence, the client sends:
```
Connection: keep-alive
```
And the server responds with:
```
Connection: keep-alive
Keep-Alive: timeout=5, max=100
```
If the server does not include `Connection: keep-alive` in its response, the client must close the connection after receiving the response.

**HTTP/1.1**: connections are **persistent by default**. No header is required to keep the connection alive. To close after a response, either side sends:
```
Connection: close
```
This asymmetry matters: an HTTP/1.1 client connecting to a server that behaves like HTTP/1.0 (closes after each response without advertising keep-alive) will incorrectly try to reuse the connection and get `ECONNRESET` on the next request.

**The `Keep-Alive` header:**
```
Keep-Alive: timeout=5, max=100
```
- `timeout=5`: the server will keep the connection open for 5 seconds of inactivity before closing it.
- `max=100`: the server will allow at most 100 requests on this connection before closing it.

These are advisory — the server can close the connection earlier (under load, reaching a resource limit, etc.) and the client must handle that. The `Keep-Alive` header is only meaningful when `Connection: keep-alive` is present; it is not defined for HTTP/1.1's default persistent connections and is ignored by most HTTP/2 implementations.

**Q10. How does HTTP keep-alive interact with HTTP pipelining?**
A: HTTP pipelining is an HTTP/1.1 feature that allows a client to send multiple requests on a keep-alive connection without waiting for each response:

```
Without pipelining (HTTP/1.1 keep-alive, sequential):
  → GET /a
  ← 200 response for /a
  → GET /b        (waits for /a's response before sending)
  ← 200 response for /b
  → GET /c
  ← 200 response for /c

With pipelining (HTTP/1.1 keep-alive + pipelining):
  → GET /a
  → GET /b        (sent without waiting for /a's response)
  → GET /c        (sent without waiting for /b's response)
  ← 200 response for /a
  ← 200 response for /b
  ← 200 response for /c
```

Pipelining reduces latency by eliminating the idle time between sending a request and receiving the previous response. However, pipelining is subject to **response-order HOL blocking** — responses must be returned in the same order as requests. If `/a` takes a long time to process, responses `/b` and `/c` queue behind it even if they're ready. A slow response at the front of the pipeline blocks all subsequent responses.

Because of this and because servers and proxies implemented pipelining inconsistently (many proxies broke it), pipelining was effectively abandoned. Major browsers disabled it by default. HTTP/2 multiplexing solves the same problem correctly — responses can be interleaved in any order on different streams, eliminating HOL blocking entirely.

**The relationship**: HTTP keep-alive is a prerequisite for HTTP pipelining — you can't pipeline on a connection that closes after each response. But keep-alive without pipelining (sequential requests on a persistent connection) is the standard HTTP/1.1 behaviour.

**Q11. How do you configure HTTP keep-alive in common HTTP servers and clients?**
A: Configuration lives at the application/library layer:

**nginx (server):**
```nginx
http {
    keepalive_timeout  65;    # close idle keep-alive connections after 65s
    keepalive_requests 1000;  # max requests per connection before closing

    # For nginx acting as a reverse proxy upstream to backend servers:
    upstream backend {
        server backend1:8080;
        keepalive 32;          # keep 32 idle connections to backend in pool
    }

    server {
        location / {
            proxy_http_version 1.1;                # required for upstream keep-alive
            proxy_set_header Connection "";         # remove "Connection: close" from client
            proxy_pass http://backend;
        }
    }
}
```

**Node.js (HTTP client):**
```js
const http  = require("http");
const https = require("https");

// Default http.Agent has keepAlive: false — creates new connection per request
// This is the most common Node.js HTTP keep-alive mistake

// Correct: create an agent with keepAlive: true
const agent = new http.Agent({
    keepAlive: true,
    maxSockets: 50,           // max concurrent connections per host
    maxFreeSockets: 10,       // max idle connections kept in pool
    timeout: 60000,           // socket timeout (ms)
    keepAliveMsecs: 30000,    // initial delay for TCP keep-alive probes (sets SO_KEEPALIVE)
});

// Use the agent in requests
http.get({ hostname: "api.example.com", path: "/data", agent }, (res) => { … });

// Or set as the global default agent
http.globalAgent = new http.Agent({ keepAlive: true, maxSockets: 50 });
```

**Go (HTTP client):**
```go
// http.DefaultTransport already has keep-alive enabled and a connection pool
// For custom configuration:
transport := &http.Transport{
    MaxIdleConns:        100,             // max idle connections across all hosts
    MaxIdleConnsPerHost: 10,              // max idle connections per host
    IdleConnTimeout:     90 * time.Second,// close idle connections after 90s
    DisableKeepAlives:   false,           // keep-alive enabled (default)
}
client := &http.Client{Transport: transport}
```

**Python (requests library):**
```python
import requests

# requests.Session() automatically uses HTTP keep-alive with connection pooling
session = requests.Session()
session.mount("https://", requests.adapters.HTTPAdapter(
    pool_connections=10,   # connection pools per host
    pool_maxsize=50,       # max connections per pool
))

# Both of these reuse the same TCP connection:
r1 = session.get("https://api.example.com/users")
r2 = session.get("https://api.example.com/orders")
```

**Q12. What is the HTTP keep-alive connection pool, and what happens when it is exhausted?**
A: A connection pool is a set of pre-established, reusable TCP connections to a specific host maintained by the HTTP client library. When a request is made:

1. Check the pool for an idle connection to the target host.
2. If found: reuse it (send the request immediately, no TCP/TLS handshake).
3. If not found and pool is below `maxSockets`: open a new connection, add to pool.
4. If not found and pool is at `maxSockets`: **queue the request** until a connection becomes available or a timeout fires.

Pool exhaustion (all `maxSockets` connections are in use) causes requests to queue. In high-concurrency services, an exhausted pool means latency spikes — requests sit idle waiting for a connection to free up, not waiting for network I/O. This is a common production incident pattern: a slow upstream API causes requests to take longer, the connection pool saturates, new requests queue, the queue grows, end-to-end latency spirals.

```
Healthy pool:       [conn1: idle] [conn2: idle] [conn3: in-use]
                    New request → grabs conn1, no wait

Saturated pool:     [conn1: in-use, waiting for slow API response]
                    [conn2: in-use, waiting for slow API response]
                    [conn3: in-use, waiting for slow API response]
                    New request → QUEUED. Waits until one frees up.
                    More requests arrive → queue grows → latency spike
```

Detection: monitor `http.Agent` metrics (in Node.js: `agent.sockets` vs `agent.freeSockets`), HTTP client connection pool metrics in your APM tool. Alert when free sockets approach zero.

## Section 4: The Confusion — Why They Are Consistently Mixed Up

**Q13. What specific code and configuration patterns cause developers to confuse the two?**
A: The naming collision manifests in at least five distinct ways in real codebases:

**Pattern 1 — `keepAlive` in Node.js `http.Agent` controls HTTP connection reuse, NOT TCP probes:**
```js
// This enables HTTP keep-alive (connection pooling/reuse):
const agent = new http.Agent({ keepAlive: true });

// This enables TCP keep-alive (OS-level probe packets) on the socket:
socket.setKeepAlive(true, 30000);

// They look similar. They do completely different things.
// You can set both. They are independent.
```

**Pattern 2 — `keepAlive` in database client libraries can mean either or both:**
```js
// pg (node-postgres) — keepAlive is TCP keep-alive (SO_KEEPALIVE):
const pool = new Pool({ keepAlive: true, keepAliveInitialDelayMillis: 10000 });

// axios — keepAlive is HTTP connection reuse (http.Agent):
const client = axios.create({ httpAgent: new http.Agent({ keepAlive: true }) });

// Same option name. Completely different mechanisms depending on the library.
```

**Pattern 3 — The HTTP `Connection: keep-alive` header is unrelated to TCP keep-alive:**
```http
GET /api/data HTTP/1.1
Host: api.example.com
Connection: keep-alive      ← this is HTTP keep-alive (application layer)
                              tells the server not to close the TCP connection
                              after responding. Has nothing to do with TCP probes.
```

**Pattern 4 — nginx `keepalive_timeout` is HTTP idle timeout, not TCP probe timing:**
```nginx
keepalive_timeout 65;   # close idle HTTP connections after 65s (HTTP layer)
                        # nothing to do with SO_KEEPALIVE or tcp_keepalive_time
```

**Pattern 5 — HAProxy / load balancer "keep-alive" can mean both simultaneously:**
```
option http-server-close   ← HTTP keep-alive with client, close with backend
option http-keep-alive     ← HTTP keep-alive on both sides
timeout client   30s       ← HTTP layer idle timeout
timeout server   30s       ← HTTP layer idle timeout
option tcpka               ← Enable TCP keep-alive (SO_KEEPALIVE) on all sockets
```
HAProxy has separate configurations for HTTP-level persistence and TCP-level probing, but both are in the same config file and the terminology overlaps.

**Q14. What is the most dangerous practical consequence of confusing the two?**
A: The most dangerous consequence is believing TCP keep-alive substitutes for HTTP connection management (or vice versa), leading to resource exhaustion and stale connection bugs in production:

**Bug 1 — Node.js service leaking connections (HTTP keep-alive disabled when it should be on):**
```js
// Common mistake: using http.request without a keep-alive agent
// Every outbound request creates a new TCP connection — never reused
http.get("https://api.downstream.com/data", callback);
// Under load: creates thousands of TCP connections per second
// OS runs out of ephemeral ports → EADDRNOTAVAIL
// Downstream server gets SYN-flooded with connection setup overhead
```

**Bug 2 — Database connection pool returning stale connections (TCP keep-alive disabled):**
```
Client holds 10 database connections in a pool.
NAT gateway expires idle connections after 350 seconds.
Application runs a batch job that doesn't touch the DB for 600 seconds.
Job finishes; application pulls a "connection" from the pool.
The "connection" is a half-open TCP socket — NAT threw away the mapping.
First query: ECONNRESET. Pool must create a new connection.
Without TCP keep-alive: happens silently; application retries.
Without proper retry logic: query fails with a cryptic network error.
```

**Bug 3 — Believing `Connection: close` in HTTP responses means the TCP connection has TCP keep-alive disabled:**
```
Server responds with Connection: close.
TCP connection is closed after the response (HTTP-level close).
TCP keep-alive was irrelevant — the connection didn't live long enough
for keep-alive probes to fire anyway.
A developer "fixes" a NAT timeout issue by adding Connection: keep-alive
to HTTP headers, but does not enable SO_KEEPALIVE on the socket.
HTTP now reuses connections — but the underlying TCP sockets still go
stale after NAT timeout during idle periods. The bug resurfaces on the
next idle connection reuse attempt.
```

**Q15. What is the right mental model to carry into any debugging or configuration session involving "keep-alive"?**
A: Ask two questions immediately, in order:

**Question 1 — Which layer am I at?**
- Am I reading/writing HTTP headers, configuring an HTTP library, or setting `Connection:` headers? → HTTP keep-alive. Affects connection reuse, request multiplexing, idle connection timeouts at the application layer.
- Am I configuring socket options, kernel parameters (`sysctl`), or a connection pool's TCP behaviour? → TCP keep-alive. Affects dead connection detection, NAT traversal, OS-level probe packets.

**Question 2 — What problem am I solving?**
- "I want to avoid paying TCP/TLS handshake overhead on every request." → HTTP keep-alive. Enable connection pooling in the HTTP client library.
- "I want to detect dead connections before my application tries to use them." → TCP keep-alive. Enable `SO_KEEPALIVE` and tune `TCP_KEEPIDLE` to be shorter than the NAT timeout.
- "My connections go stale after a few minutes of idle time." → Both. TCP keep-alive to prevent NAT expiry; HTTP keep-alive timeout to close connections that won't be reused.
- "My service is opening too many TCP connections." → HTTP keep-alive is disabled or the connection pool is misconfigured. Not a TCP keep-alive problem.

## Section 5: Interaction Effects

**Q16. How do HTTP keep-alive timeouts and TCP keep-alive probes interact in practice?**
A: The two timeouts operate independently and must be coordinated to avoid a class of bugs where the server closes the HTTP connection before the TCP keep-alive mechanism fires:

```
Scenario: nginx keepalive_timeout=65s, TCP tcp_keepalive_time=7200s

At t=0:   Client sends request. Connection established.
At t=30:  Response sent. Connection is now idle (keep-alive reuse waiting).
At t=95:  nginx keepalive_timeout fires → nginx sends FIN, closes HTTP connection.
At t=7200: TCP keep-alive would have sent its first probe — but the connection
           is already closed. TCP keep-alive never fired. Correct behaviour.

Scenario: nginx keepalive_timeout=600s, TCP tcp_keepalive_time=300s

At t=0:   Client sends request. Response sent. Connection idle.
At t=300: TCP keep-alive fires → sends probe. Peer responds. Timer resets.
At t=600: nginx keepalive_timeout fires → server closes connection.
          TCP keep-alive kept the connection alive to the 600s mark. Correct.

Problem scenario: Load balancer idle timeout=60s, HTTP keep-alive timeout=120s

At t=0:   Client sends request through load balancer. Connection established.
At t=30:  Response delivered. HTTP connection stays open for reuse.
At t=60:  Load balancer silently closes connection (idle timeout).
At t=90:  Client tries to reuse the "open" HTTP connection.
          Sends request. Gets ECONNRESET or EPIPE.
          The HTTP library either crashes or (if well-written) retries on a new connection.

Fix: set HTTP keepalive_timeout < load balancer idle timeout.
     nginx: keepalive_timeout 55s (< 60s LB timeout)
     Client library idle timeout: 50s
     Hierarchy: client timeout < server timeout < load balancer timeout
```

The general rule: HTTP idle timeouts should be shorter on the client than on the server, shorter on the server than on any load balancer or proxy between them. This ensures connections are retired in a predictable order rather than being forcibly reset mid-reuse.

**Q17. Does HTTP/2 have a keep-alive mechanism, and does it replace TCP keep-alive?**
A: HTTP/2 has its own connection liveness mechanism — **PING frames** — and a graceful shutdown mechanism — **GOAWAY frames**. Neither is the same as TCP keep-alive:

**HTTP/2 PING frames:**
```
Client → Server: PING frame (8-byte opaque data)
Server → Client: PING frame (ACK flag, same opaque data echoed)
```
PING frames measure round-trip latency and confirm the connection is alive at the HTTP/2 application layer — more reliable than TCP keep-alive because they confirm the HTTP/2 stack (not just the TCP stack) is responsive. gRPC uses PING frames as its built-in keepalive (configurable via `keepalive_time`, `keepalive_timeout` in the gRPC channel options — again, these are HTTP/2 PINGs, not TCP probes).

**The relationship:**
- HTTP/2 PING frames operate at the HTTP/2 frame layer (above TCP).
- TCP keep-alive probes operate at the TCP segment layer (below HTTP/2).
- They are complementary: TCP keep-alive detects network-level failures (NAT expiry, cable unplug); HTTP/2 PINGs detect application-level failures (hung process, frozen event loop).
- Neither replaces the other. A well-configured HTTP/2 deployment uses both.

**HTTP/2 and the `Connection: keep-alive` header:**
The `Connection` header is explicitly forbidden in HTTP/2 (RFC 7540 §8.1.2.2). HTTP/2 connections are always persistent by definition — multiplexing makes the concept of "closing after one request" meaningless. The `Connection: keep-alive` header from HTTP/1.1 must not be sent in HTTP/2 and must be stripped by HTTP/2 implementations.

**Q18. What happens when a reverse proxy sits between the HTTP client and the server, and how does keep-alive need to be configured at each hop?**
A: A reverse proxy creates two separate TCP connections: client → proxy, and proxy → backend. Keep-alive must be configured at both hops independently:

```
Browser ──[conn A]── nginx (reverse proxy) ──[conn B]── Backend server

Connection A (browser ↔ nginx):
  - HTTP/2 or HTTP/1.1 keep-alive from browser
  - Controlled by nginx's keepalive_timeout, keepalive_requests
  - Browser manages its own connection pool to nginx's IP

Connection B (nginx ↔ backend):
  - nginx acts as HTTP client to backend
  - Requires explicit configuration: proxy_http_version 1.1 + keepalive in upstream block
  - Without this: nginx uses HTTP/1.0 to backend → new TCP connection per request
  - With keepalive 32: nginx maintains a pool of up to 32 idle connections to backend
```

**The classic nginx misconfiguration:**
```nginx
# BROKEN: nginx sends HTTP/1.0 requests to backend by default
# Each proxied request opens a new connection to backend
upstream backend {
    server 10.0.0.1:8080;
    # no keepalive directive
}

# CORRECT: enable keep-alive to backend
upstream backend {
    server 10.0.0.1:8080;
    keepalive 32;  # pool of 32 idle connections
}

server {
    location / {
        proxy_http_version 1.1;          # required — keepalive needs HTTP/1.1
        proxy_set_header Connection "";  # strip "Connection: close" from client headers
        proxy_pass http://backend;
    }
}
```

This is one of the most common nginx performance misconfigurations. A system with 1000 req/s to a backend with 50ms average response time would need 50 connections in the pool to avoid creating new ones (`Little's Law: N = λ × W = 1000 × 0.05 = 50`). Without the `keepalive` directive, all 1000 req/s each create and immediately destroy a TCP connection — 1000 TCP handshakes per second of pure overhead.

## Section 6: Scenario / System Design Style Questions

**Q19. "Your Node.js service makes 500 requests per second to a downstream REST API. Monitoring shows high latency and ephemeral port exhaustion (`EADDRNOTAVAIL`). What is the root cause and fix?"**
A: The root cause is almost certainly that HTTP keep-alive is disabled in the HTTP client — every request is creating a new TCP connection, exhausting the ephemeral port range.

Diagnosis:
```bash
# Check for TIME_WAIT accumulation (hallmark of per-request connections)
ss -s
# Output: TIME-WAIT: 28423   ← 28,000 TIME_WAIT sockets
#         ESTAB: 12           ← only 12 established connections

# Confirm ephemeral port range
cat /proc/sys/net/ipv4/ip_local_port_range
# 32768 60999  ← 28,231 ports available
# 28,423 TIME_WAIT sockets nearly exhausted

# Watch the rate of new connections (should be near 0 with keep-alive)
watch -n1 "ss -s | grep TIME-WAIT"
```

Root cause confirmed: 500 req/s × 60s (TIME_WAIT duration) ≈ 30,000 TIME_WAIT sockets. The ephemeral port range holds ~28,000 ports. Overflow → `EADDRNOTAVAIL`.

Fix:
```js
// Before (broken): default Agent has keepAlive: false
const response = await fetch("https://api.downstream.com/data");
// Each call: new TCP connection → request → FIN → TIME_WAIT

// After (fixed): create an agent with keep-alive enabled
const https = require("https");
const agent = new https.Agent({
    keepAlive: true,
    maxSockets: 50,          // cap concurrent connections
    maxFreeSockets: 10,      // keep 10 idle connections ready
    timeout: 30000,
});

// Reuse the agent across all requests
const response = await fetch("https://api.downstream.com/data", { agent });
// Each call: reuse existing connection → no new TCP handshake → no TIME_WAIT growth
```

Also enable TCP keep-alive on the pooled sockets to prevent NAT expiry of idle connections:
```js
const agent = new https.Agent({
    keepAlive: true,
    keepAliveMsecs: 30000,   // TCP keep-alive idle time: 30s (shorter than most NAT timeouts)
    maxSockets: 50,
});
```

**Q20. "You're running a database connection pool. Connections work fine during the day but fail with ECONNRESET on Monday mornings after the weekend. What is causing this and how do you fix it?"**
A: Classic NAT/firewall idle connection expiry problem. During the weekend, the application makes few database queries — connections in the pool are idle for hours. The NAT gateway between the application servers and the database server expires idle TCP entries (typically after 300–900 seconds). On Monday morning, the application pulls a "healthy" connection from the pool and tries to query — but the NAT mapping is gone. The database server never receives the query; the application gets silence, then eventually a timeout or RST.

**Fix layer 1 — TCP keep-alive on the database connections:**
```js
// pg (node-postgres)
const pool = new Pool({
    host: "db.internal",
    database: "myapp",
    keepAlive: true,                    // enables SO_KEEPALIVE
    keepAliveInitialDelayMillis: 60000, // first probe after 60s of idle (60,000ms)
    // ensure this is < NAT timeout (typically 300s)
    // probes will keep the NAT entry alive every ~60s
});
```

**Fix layer 2 — Connection validation before use (belt-and-suspenders):**
```js
// Test connections before returning them from the pool
const pool = new Pool({
    // pg validates with SELECT 1 on checkout if connection has been idle
    idleTimeoutMillis: 600000,   // remove connections idle >10 minutes from pool
    connectionTimeoutMillis: 5000,
});
```

**Fix layer 3 — Reduce idle time with application-level heartbeat:**
```js
// Send a keepalive query on idle connections
setInterval(async () => {
    const client = await pool.connect();
    try {
        await client.query("SELECT 1");
    } finally {
        client.release();
    }
}, 120000); // every 2 minutes — well under the NAT timeout
```

The TCP keep-alive fix is cleanest — it requires no application logic and works at the transport layer before NAT entries expire. The application-level heartbeat is a belt-and-suspenders fallback for environments where TCP keep-alive probes are blocked.

**Q21. "Explain what happens, at every layer, from the moment a browser opens the fifth connection to a website that uses HTTP/1.1 with keep-alive, assuming four requests have already been made on the same connection."**
A: The fifth request demonstrates the entire lifecycle of HTTP keep-alive in operation:

```
State entering the fifth request:
  - TCP connection to example.com:443 is ESTABLISHED (from request 1)
  - TLS session is active (from request 1)
  - HTTP/1.1 keep-alive is active (server responded with Connection: keep-alive)
  - Four requests and responses have already traversed this connection
  - TCP sequence numbers have advanced (reflecting bytes of all prior exchanges)
  - HPACK dynamic table (if this were HTTP/2 — but this is HTTP/1.1, so no compression state)
  - Browser's connection pool shows this socket as idle (free to reuse)

Step 1 — Browser issues the fifth request:
  Application layer: browser picks up the idle socket from its connection pool.
                     No DNS lookup (already resolved for this origin).
                     No TCP handshake (connection already established).
                     No TLS handshake (session already active).

  HTTP layer: browser formats the request:
    GET /asset5.png HTTP/1.1\r\n
    Host: example.com\r\n
    Connection: keep-alive\r\n      ← optional in HTTP/1.1; included by most browsers
    Accept: image/png\r\n
    \r\n

  TLS layer: the request bytes are encrypted with the current session keys.

  TCP layer: browser's kernel takes the encrypted bytes, wraps them in TCP segment(s).
             Sequence number picks up from where the fourth response left off.
             Segment sent to the server's IP:443.

Step 2 — Network transit:
  IP layer: TCP segment(s) routed across the internet.
  No connection setup. No slow-start from scratch.
  TCP congestion window is already open from prior requests — full-speed delivery.

Step 3 — Server receives the request:
  TCP layer: kernel acknowledges the received bytes (ACK sent back).
  TLS layer: kernel decrypts using the established session keys.
  HTTP layer: server's HTTP parser reads the request line and headers.
              Sees GET /asset5.png — routes to the asset handler.

Step 4 — Server sends response:
  HTTP layer: constructs HTTP/1.1 200 OK response with headers + PNG body.
              Includes Connection: keep-alive (server wants to keep reusing this connection).
  TLS layer: response encrypted.
  TCP layer: sent in segment(s). The fifth request and response share the same
             TCP stream as the first four — sequence numbers are continuous.

Step 5 — Browser receives response:
  TCP layer: reassembles segments in order.
  TLS layer: decrypts.
  HTTP layer: parser finds the response boundary (Content-Length or chunked encoding).
              Delivers response body to the browser's rendering engine.
              Marks socket as idle in the connection pool — ready for request six.

What did NOT happen:
  - No TCP SYN/SYN-ACK/ACK (no new connection)
  - No TLS ClientHello/ServerHello (no new handshake)
  - No slow-start ramp (congestion window already open)
  - No DNS query
  - No ephemeral port allocation (same port used throughout)
```

The fifth request is indistinguishable from an in-session request after the first — the entire overhead of connection establishment, paid once for request one, amortises across all subsequent requests.

## Quick Reference

```
TCP KEEP-ALIVE                          HTTP KEEP-ALIVE
──────────────────────────────────────  ────────────────────────────────────────────
Layer:    Transport (Layer 4)           Application (Layer 7)
Purpose:  Detect dead connections       Reuse connections across requests
Mechanism: OS sends probe TCP segments  HTTP library reuses existing TCP sockets
Configured: setsockopt(SO_KEEPALIVE)    HTTP library/server settings
Visible to HTTP: No (transparent)      Yes (Connection: keep-alive header)
Linux defaults: idle=7200s, 9 probes   nginx default: keepalive_timeout=75s

TCP keep-alive kernel parameters (Linux):
  tcp_keepalive_time    = 7200   # idle seconds before first probe
  tcp_keepalive_intvl   = 75     # seconds between probes
  tcp_keepalive_probes  = 9      # probes before ETIMEDOUT

Per-socket override (Linux):
  TCP_KEEPIDLE   ← overrides tcp_keepalive_time for this socket
  TCP_KEEPINTVL  ← overrides tcp_keepalive_intvl
  TCP_KEEPCNT    ← overrides tcp_keepalive_probes

HTTP keep-alive header negotiation:
  HTTP/1.0: closed by default → opt-in with Connection: keep-alive
  HTTP/1.1: persistent by default → opt-out with Connection: close
  HTTP/2:   always persistent (Connection header forbidden)

Key timeouts to coordinate (shortest → longest):
  Client HTTP idle timeout
  < Server HTTP idle timeout (keepalive_timeout)
  < Load balancer idle timeout
  (prevents RST on connection reuse)

Common names for HTTP keep-alive in libraries:
  http.Agent({ keepAlive: true })         — Node.js
  Transport{ MaxIdleConns: 100 }          — Go
  requests.Session()                      — Python (automatic)
  keepalive 32; in upstream {}            — nginx upstream

Common names for TCP keep-alive in libraries:
  socket.setKeepAlive(true, delayMs)      — Node.js
  net.Dialer{ KeepAlive: 30*time.Second } — Go
  setsockopt(SO_KEEPALIVE)                — C/POSIX
  Pool({ keepAlive: true })               — node-postgres
```

## Common Mistakes at a Glance

| Mistake                                                         | Clarification                                                                           |
|---                                                              |---                                                                                      |
| Treating `Connection: keep-alive` as enabling TCP probes        | It is HTTP-level connection reuse only — no effect on SO_KEEPALIVE or probe packets     |
| Treating `SO_KEEPALIVE` as enabling HTTP connection reuse       | TCP probes detect dead connections — they do not reuse connections across HTTP requests  |
| Setting `keepAlive: true` in `http.Agent` thinking TCP probes are set | `keepAlive` in `http.Agent` is HTTP reuse; `socket.setKeepAlive()` is TCP probes   |
| Assuming HTTP/2 does not need TCP keep-alive                    | HTTP/2 PING frames detect app-level failure; TCP keep-alive detects network-level failure; both needed |
| Setting HTTP idle timeout longer than load balancer timeout     | Causes RST on connection reuse attempts — always: client < server < load balancer      |
| Using `tcp_keepalive_time=7200` (default) with a NAT gateway    | Most NAT tables expire at 300–900s; 7200s means probes fire after NAT entry is gone     |
| Assuming TCP keep-alive validates the application is healthy    | Probes only test the TCP stack responds — a deadlocked app still passes TCP probes      |
| Disabling nginx upstream keep-alive with HTTP/1.1 proxy         | nginx defaults to HTTP/1.0 upstream requests; must add `proxy_http_version 1.1`        |
| Confusing HTTP pipelining with HTTP keep-alive                  | Keep-alive = reuse connection; pipelining = send multiple requests without waiting for each response |
| Thinking `Connection: close` in a response disables TCP keep-alive | It only closes the HTTP connection after this response; TCP keep-alive is a socket option |

**Tip for the interview:** At 5 YOE, the keep-alive confusion surfaces in three forms: a direct "what is the difference between TCP and HTTP keep-alive?" (answer with the two-sentence distinction and the layer diagram), a debugging scenario ("connections work during the day but fail overnight" — TCP keep-alive / NAT expiry), or a performance scenario ("service is opening too many connections and running out of ports" — HTTP keep-alive pool misconfigured). The tell-tale sign of a strong answer is immediately asking "which layer are we at?" before diving into any configuration. Candidates who jump to `Connection: keep-alive` headers when asked about a NAT timeout problem, or who reach for `SO_KEEPALIVE` when asked about connection pool exhaustion, are conflating the two — and interviewers who know networking will catch it instantly. Know both mechanisms cold, know exactly what each one does and does not do, and name the layer first.
