# IP Addressing: CIDR Notation, Private IP Ranges, Subnetting — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is an IP address, and what two things does it identify?**
A: An IP address is a 32-bit (IPv4) or 128-bit (IPv6) number assigned to a network interface. It identifies two things simultaneously — and this dual role is the source of much subnet math:

**The network it belongs to:** The high-order bits of the IP address identify the network (or subnet). All devices on the same network share the same network prefix. Routers use this prefix to forward packets toward the correct network without needing to know individual host addresses.

**The host within that network:** The low-order bits identify the specific host (or interface) within the network. These bits must be unique within the subnet.

The boundary between network bits and host bits is defined by the **subnet mask** (or equivalently, the CIDR prefix length). Everything to the left of that boundary is the network portion; everything to the right is the host portion:

```
IP address:    192  . 168  .  1   . 45
Binary:     11000000.10101000.00000001.00101101
                                                 ↑
Subnet mask:   255  . 255  . 255  .  0           │ prefix /24
Binary:     11111111.11111111.11111111.00000000   │
                                                 ↑
Network bits (24): 192.168.1     → the subnet
Host bits    (8):             45 → this specific host on that subnet
```

This dual identification is what makes routing work: a router doesn't need a table entry for every host on the Internet — only for every network. Within the network, local delivery handles the host portion.

**Q2. What is dotted-decimal notation, and how does it represent a 32-bit integer?**
A: IPv4 addresses are 32-bit unsigned integers. Dotted-decimal notation represents this 32-bit number as four 8-bit groups (octets) written in decimal, separated by dots. Each octet ranges from 0 to 255 (2⁸ − 1):

```
Binary:    11000000 . 10101000 . 00000001 . 00101101
Decimal:     192    .   168    .    1     .   45
             └─8 bits─┘ └─8 bits─┘ └─8 bits─┘ └─8 bits─┘
                      = 3,232,235,821 as a 32-bit integer
```

Converting a single octet from binary to decimal (and back) is the core skill for subnet arithmetic:

```
Binary:   128  64  32  16   8   4   2   1
Value:    2⁷   2⁶  2⁵  2⁴  2³  2²  2¹  2⁰

Examples:
11111111 = 128+64+32+16+8+4+2+1 = 255
11111110 = 128+64+32+16+8+4+2+0 = 254
11000000 = 128+64+0+0+0+0+0+0   = 192
10101000 = 128+0+32+0+8+0+0+0   = 168
```

The minimum IP address is `0.0.0.0` (all 32 bits zero) and the maximum is `255.255.255.255` (all 32 bits one). The Internet address space has 2³² = 4,294,967,296 possible IPv4 addresses.

**Q3. What is CIDR notation, and what problem did it solve over classful networking?**
A: CIDR (Classless Inter-Domain Routing, RFC 4632, 1993) is a method for representing IP addresses and their associated network masks as a single compact notation: the IP address followed by a forward slash and the number of bits in the network prefix:

```
192.168.1.0/24    → network 192.168.1.0, prefix length 24 bits
10.0.0.0/8        → network 10.0.0.0, prefix length 8 bits
172.16.0.0/12     → network 172.16.0.0, prefix length 12 bits
10.0.1.0/28       → network 10.0.1.0, prefix length 28 bits (14 hosts)
```

**The problem CIDR solved — classful networking waste:**
Before CIDR (prior to 1993), IPv4 addresses were divided into fixed classes:

| Class | First bits | Address range | Default prefix | Hosts per network |
|---|---|---|---|---|
| A | 0 | 0.0.0.0 – 127.255.255.255 | /8 | 16,777,214 |
| B | 10 | 128.0.0.0 – 191.255.255.255 | /16 | 65,534 |
| C | 110 | 192.0.0.0 – 223.255.255.255 | /24 | 254 |

A company needing 500 hosts had to be allocated a Class B (/16 — 65,534 hosts) because Class C (/24 — 254 hosts) was too small. 65,034 addresses were wasted per allocation. With ~65,536 Class B networks globally and the Internet growing explosively, this waste was rapidly exhausting the address space and bloating routing tables.

CIDR allows variable-length subnet masks — any prefix length from /0 to /32. A company needing 500 hosts gets a `/23` (510 usable hosts). The Internet's routing table aggregates ranges: instead of separate entries for 256 consecutive Class C networks (`192.168.0.0/24` through `192.168.255.0/24`), one CIDR entry `192.168.0.0/16` covers all 256. This route aggregation (supernetting) was critical to preventing routing table explosion.

## Section 2: CIDR Notation in Depth

**Q4. How do you calculate the network address, broadcast address, and host range from a CIDR block?**
A: Given a CIDR block, four values are derived mechanically:

**Example: `192.168.5.130/26`**

**Step 1 — Determine the subnet mask from the prefix length:**
/26 means 26 ones followed by 6 zeros in the 32-bit mask:
```
11111111.11111111.11111111.11000000 = 255.255.255.192
```

**Step 2 — Calculate the network address (AND the IP with the mask):**
```
IP address:    11000000.10101000.00000101.10000010  (192.168.5.130)
Subnet mask:   11111111.11111111.11111111.11000000  (255.255.255.192)
AND result:    11000000.10101000.00000101.10000000  (192.168.5.128)
```
Network address: `192.168.5.128`

**Step 3 — Calculate the number of host addresses:**
The host portion is 32 − 26 = 6 bits → 2⁶ = 64 total addresses.
Usable hosts = 64 − 2 = **62** (subtract network address and broadcast address).

**Step 4 — Calculate the broadcast address (set all host bits to 1):**
```
Network address:   11000000.10101000.00000101.10000000
Host bits to 1:                                ++++++
Broadcast address: 11000000.10101000.00000101.10111111  (192.168.5.191)
```

**Step 5 — Usable host range:**
First host: network address + 1 = `192.168.5.129`
Last host:  broadcast address − 1 = `192.168.5.190`

**Summary:**
```
Block:             192.168.5.130/26
Network address:   192.168.5.128      (not assignable)
First usable host: 192.168.5.129
Last usable host:  192.168.5.190
Broadcast address: 192.168.5.191      (not assignable)
Total addresses:   64
Usable hosts:      62
```

**The block size shortcut:** For a /n prefix, the block size is 2^(32-n). A /26 has block size 64. Block boundaries fall at multiples of 64 in the last octet: `.0`, `.64`, `.128`, `.192`. A host at `.130` falls in the `.128` block (the third block).

**Q5. What are the common prefix lengths, and what does each mean in practice?**
A:

| Prefix | Hosts (usable) | Block size | Common use |
|---|---|---|---|
| /8 | 16,777,214 | 16,777,216 | Entire private Class A range (10.0.0.0/8) |
| /16 | 65,534 | 65,536 | Entire private Class B range; large VPC |
| /17 | 32,766 | 32,768 | Half a /16; large region in a VPC |
| /20 | 4,094 | 4,096 | AWS default VPC subnet size |
| /21 | 2,046 | 2,048 | Medium subnet |
| /22 | 1,022 | 1,024 | Medium subnet |
| /23 | 510 | 512 | Small-medium subnet |
| /24 | 254 | 256 | Standard subnet; one "Class C" |
| /25 | 126 | 128 | Half a /24 |
| /26 | 62 | 64 | Quarter of a /24 |
| /27 | 30 | 32 | Eighth of a /24 |
| /28 | 14 | 16 | Small subnet (database tier, NAT gateway) |
| /29 | 6 | 8 | Point-to-point links with multiple hosts |
| /30 | 2 | 4 | Point-to-point link (2 hosts, used for router-to-router) |
| /31 | 2 (no broadcast) | 2 | Point-to-point (RFC 3021 — no net/broadcast) |
| /32 | 1 host (no subnet) | 1 | Single host route; security group rule for one IP |

**AWS-specific note:** AWS reserves 5 IP addresses per subnet (not the standard 2). For a /24: AWS reserves `.0` (network), `.1` (VPC router), `.2` (DNS), `.3` (future use), `.255` (broadcast) — leaving 251 usable addresses. For a /28: 16 − 5 = 11 usable. When sizing AWS subnets, account for this 5-address overhead.

**Q6. How do you quickly determine if two IP addresses are on the same subnet?**
A: Two IPs are on the same subnet if and only if their network addresses are identical when ANDed with the subnet mask. In practice:

**Mental method (for powers-of-2 boundaries):**

For a /24: the network address is the first three octets. `10.0.1.45` and `10.0.1.200` are on the same `/24` (both on `10.0.1.0/24`). `10.0.1.45` and `10.0.2.45` are not (different third octet).

For a /16: the first two octets. `10.0.45.1` and `10.0.200.1` are on the same `/16` (`10.0.0.0/16`). `10.1.0.1` is not.

For a /25 or /26 (requires checking within an octet):
```
IP1: 192.168.1.60     → binary last octet: 00111100
IP2: 192.168.1.130    → binary last octet: 10000010

/25 (mask .128 = 10000000):
  IP1 & mask: 00000000 = .0 → network 192.168.1.0/25
  IP2 & mask: 10000000 = .128 → network 192.168.1.128/25
  Different networks → NOT on the same /25 subnet

/24:
  Both have same first three octets → SAME /24 subnet
```

**Programmatic check in Node.js:**
```typescript
function sameSubnet(ip1: string, ip2: string, prefixLen: number): boolean {
  const toInt = (ip: string) =>
    ip.split(".").reduce((acc, oct) => (acc << 8) | parseInt(oct), 0) >>> 0;

  const mask   = prefixLen === 0 ? 0 : (~0 << (32 - prefixLen)) >>> 0;
  const net1   = (toInt(ip1) & mask) >>> 0;
  const net2   = (toInt(ip2) & mask) >>> 0;
  return net1 === net2;
}

sameSubnet("10.0.1.45", "10.0.1.200", 24);  // true
sameSubnet("10.0.1.45", "10.0.2.45",  24);  // false
sameSubnet("192.168.1.60", "192.168.1.130", 25); // false
```

## Section 3: Private IP Ranges

**Q7. What are the private IP address ranges, why do they exist, and who defined them?**
A: RFC 1918 (1996) defines three blocks of IPv4 addresses reserved for private use — not routable on the public Internet. Any device can use these addresses internally; they are never forwarded by Internet routers:

| Range | CIDR | Class legacy | Total addresses |
|---|---|---|---|
| `10.0.0.0` – `10.255.255.255` | 10.0.0.0/8 | Class A | 16,777,216 |
| `172.16.0.0` – `172.31.255.255` | 172.16.0.0/12 | Class B range | 1,048,576 |
| `192.168.0.0` – `192.168.255.255` | 192.168.0.0/16 | Class C range | 65,536 |

**Why they exist:**
In the early 1990s it became clear that 4.3 billion IPv4 addresses would be exhausted before IPv6 was widely adopted (IPv6 is now standardised but adoption is still incomplete). RFC 1918 reserves large blocks that any organisation can reuse internally. Company A and Company B can both use `10.0.0.0/8` internally without conflict — because packets from these addresses never leave their respective networks. A NAT (Network Address Translation) gateway translates private addresses to a single public IP when sending traffic to the Internet.

**Additional special-purpose ranges worth knowing:**

| Range | CIDR | Purpose |
|---|---|---|
| 127.0.0.0/8 | Loopback — `localhost`. Never leaves the host. |
| 169.254.0.0/16 | APIPA (Automatic Private IP Addressing) — self-assigned when DHCP fails; also AWS instance metadata (`169.254.169.254`), AWS VPC DNS (`169.254.169.253`). |
| 100.64.0.0/10 | Shared address space (RFC 6598) — used by ISPs for carrier-grade NAT (CGN). Not routable on the public Internet; not for private use. |
| 0.0.0.0/8 | "This network" — used as a placeholder (0.0.0.0 = default route, DHCP discover source). |
| 255.255.255.255/32 | Limited broadcast — sent to all hosts on local network; not forwarded by routers. |
| 224.0.0.0/4 | Multicast — addresses for group communication (not individual hosts). |
| 240.0.0.0/4 | Reserved for future use — historically unused; some proposals to open for private use. |

**Q8. What is NAT, and why is it necessary with private IP ranges?**
A: NAT (Network Address Translation) is the mechanism by which a router translates private IP addresses (from RFC 1918) to a public IP address (and back) so that privately-addressed hosts can communicate with the public Internet:

```
Internal hosts           NAT Router              Internet
192.168.1.10  ──┐       (public: 203.0.113.1)
192.168.1.11  ──┤  ──▶  src: 203.0.113.1:54321 ──▶ api.example.com
192.168.1.12  ──┘        (port uniquely identifies each internal host)

Return traffic:
api.example.com ──▶ 203.0.113.1:54321 ──▶ NAT router
  NAT looks up 54321 → 192.168.1.10:49152 ──▶ internal host
```

**How NAT works (NAPT — Network Address Port Translation, the common form):**
1. An internal host (`192.168.1.10:49152`) sends a packet to an external host.
2. The NAT router rewrites the source: `192.168.1.10:49152` → `203.0.113.1:54321` (unique port assigned by NAT).
3. The NAT router stores the mapping: `203.0.113.1:54321 ↔ 192.168.1.10:49152` in its NAT table.
4. The external server responds to `203.0.113.1:54321`.
5. The NAT router looks up `:54321`, rewrites destination back to `192.168.1.10:49152`, forwards to internal host.

**NAT in AWS:**
- **NAT Gateway:** Allows instances in private subnets to initiate outbound connections to the Internet (software updates, API calls) without being directly reachable from the Internet. One public IP per NAT Gateway; many private hosts share it. Charged per hour and per GB of data processed.
- **Internet Gateway (IGW):** A true gateway — routes traffic between the VPC and the Internet. Instances with public IPs use the IGW directly (no NAT). The IGW performs one-to-one NAT for instances with Elastic IPs: `10.0.1.45 ↔ 54.x.y.z`.

**NAT breaks peer-to-peer:** As discussed in the UDP guide — NAT mapping is created by outbound packets. Inbound packets to a private IP with no existing NAT mapping are dropped. This is why gaming, WebRTC, and file-sharing protocols need NAT traversal (STUN/TURN/hole punching).

## Section 4: Subnetting

**Q9. What is subnetting, and what are the practical reasons to create subnets?**
A: Subnetting is the process of dividing a larger IP network into smaller, more specific networks (subnets). A `/16` network can be divided into 256 `/24` subnets, or 65,536 `/32` host routes, or any combination of prefix lengths that fit within the parent block.

**Practical reasons to subnet:**

**Security isolation:** Different trust zones need different subnets to allow firewall rules (security groups, NACLs) to control traffic between them. A payment API server and a database server on the same `/24` subnet can communicate directly; placing the database in a separate `/24` (or a different VPC subnet) allows a subnet-level rule that only permits database traffic from the application subnet.

**Reducing broadcast domains:** IPv4 broadcasts (ARP, DHCP) are sent to all hosts on a subnet. A `/16` subnet with 65,534 hosts generates enormous broadcast traffic that every host must process. Dividing into `/24` subnets limits broadcasts to 254 hosts, reducing noise.

**Route aggregation:** A transit network (ISP, data centre) only needs to know the /16 parent block to route to an organisation — not the individual /24 subnets inside. Aggregation reduces routing table size.

**Resource organisation:** Different subnets for different tiers (public, private, database), different availability zones, different environments (prod, staging) within the same VPC.

**Controlling IP allocation:** Assigning a `/28` (14 hosts) to a small service prevents it from consuming addresses from a larger pool unnecessarily.

**Q10. Walk through dividing a `/24` into four equal subnets.**
A: Dividing a `/24` into four equal subnets requires borrowing 2 bits from the host portion (2² = 4):

**Original network:** `192.168.10.0/24`
- Host bits: 8 (last octet)
- Borrow 2 bits → new prefix: /26
- Each subnet has 2⁶ = 64 addresses (62 usable)

```
Original:    192.168.10.0/24
             |←── 24 network bits ──→|←── 8 host bits ──→|

Split into:  192.168.10.0/26
             |←────── 26 network bits ──────→|←─6 host─→|

The 2 borrowed bits take values 00, 01, 10, 11:

Subnet 1:  192.168.10.0/26
  Network:   192.168.10.0   (bits: ...00 000000)
  Broadcast: 192.168.10.63  (bits: ...00 111111)
  Hosts:     192.168.10.1  – 192.168.10.62  (62 hosts)

Subnet 2:  192.168.10.64/26
  Network:   192.168.10.64  (bits: ...01 000000)
  Broadcast: 192.168.10.127 (bits: ...01 111111)
  Hosts:     192.168.10.65 – 192.168.10.126 (62 hosts)

Subnet 3:  192.168.10.128/26
  Network:   192.168.10.128 (bits: ...10 000000)
  Broadcast: 192.168.10.191 (bits: ...10 111111)
  Hosts:     192.168.10.129 – 192.168.10.190 (62 hosts)

Subnet 4:  192.168.10.192/26
  Network:   192.168.10.192 (bits: ...11 000000)
  Broadcast: 192.168.10.255 (bits: ...11 111111)
  Hosts:     192.168.10.193 – 192.168.10.254 (62 hosts)
```

**Verification:** 4 subnets × 64 addresses = 256 addresses = the original /24. No gaps, no overlaps.

**The pattern:** The block size for a /26 is 64. Subnets start at multiples of 64 within the last octet: 0, 64, 128, 192. This is the general rule — subnets always start at multiples of the block size.

**Q11. How do you subnet across octet boundaries — for example, dividing a `/20`?**
A: When the prefix length falls in the middle of an octet (e.g., /20 in the third octet), the math extends across the octet boundary. This is where many engineers struggle:

**Example: Divide `10.0.0.0/20` into 8 equal subnets.**

`10.0.0.0/20` → borrow 3 bits to create 8 subnets → new prefix: /23.

/23 subnet size: 2^(32-23) = 2^9 = 512 addresses (510 usable).

The host portion spans parts of the 3rd and 4th octets (23 bits network → 9 bits host: 1 bit in 3rd octet + 8 bits in 4th octet):

```
10.0.0.0/20 binary:
  00001010.00000000.0000 0000.00000000
                    ↑24──prefix─/20──→
                         ↑ 4 host bits in 3rd octet + all 8 in 4th

/23 subnets (9 host bits: 1 in 3rd octet + 8 in 4th):

Subnet 1:  10.0.0.0/23    hosts: 10.0.0.1  – 10.0.1.254
Subnet 2:  10.0.2.0/23    hosts: 10.0.2.1  – 10.0.3.254
Subnet 3:  10.0.4.0/23    hosts: 10.0.4.1  – 10.0.5.254
Subnet 4:  10.0.6.0/23    hosts: 10.0.6.1  – 10.0.7.254
Subnet 5:  10.0.8.0/23    hosts: 10.0.8.1  – 10.0.9.254
Subnet 6:  10.0.10.0/23   hosts: 10.0.10.1 – 10.0.11.254
Subnet 7:  10.0.12.0/23   hosts: 10.0.12.1 – 10.0.13.254
Subnet 8:  10.0.14.0/23   hosts: 10.0.14.1 – 10.0.15.254
```

Block size of a /23 = 512. But 512 spans 2 full third octets (each holds 256 addresses). So the step between subnet starts is 2 in the 3rd octet: 0, 2, 4, 6, 8, 10, 12, 14. And each subnet spans two consecutive values of the 3rd octet (0-1, 2-3, 4-5...) with all values 0-255 in the 4th octet.

**The key insight for cross-octet subnetting:** Identify which octet the prefix boundary falls in, determine the block size, and compute the step as `block_size / (256^n)` where n is the number of full octets to the right of the boundary octet. For /23: block_size = 512; 3rd octet boundary; 1 full octet to the right → step = 512 / 256 = 2 in the 3rd octet.

**Q12. What is VLSM (Variable Length Subnet Masking), and when do you use it?**
A: VLSM is the practice of using different subnet sizes within the same parent network — giving each subnet exactly the size it needs rather than dividing into equal pieces. It's the standard approach for real-world network design where different segments have wildly different host requirements:

**Scenario:** You have `172.16.0.0/20` (4096 addresses, 4094 usable) and need to allocate it for:
- Web tier: 500 hosts
- App tier: 250 hosts
- Database tier: 50 hosts
- Management: 20 hosts
- Point-to-point link (router-to-router): 2 hosts

**Equal division would waste space.** VLSM allocates minimum sizes:

```
Segment      Hosts needed  Prefix  Block  Addresses  Assigned range
──────────────────────────────────────────────────────────────────────
Web tier       500         /23     512    510 usable  172.16.0.0/23
App tier       250         /24     256    254 usable  172.16.2.0/24
Database        50         /26      64     62 usable  172.16.3.0/26
Management      20         /27      32     30 usable  172.16.3.64/27
Point-to-point   2         /30       4      2 usable  172.16.3.96/30

Remaining:                                           172.16.3.100 – 172.16.15.255
```

**Sizing rule:** Choose the smallest prefix that fits ≥ (hosts_needed + 2) hosts (for network and broadcast addresses). AWS adds 3 more (router, DNS, future), so for AWS: smallest prefix fitting ≥ (hosts_needed + 5).

**VLSM in AWS VPC design:**
AWS VPCs are the canonical real-world VLSM exercise. A typical three-tier architecture across three AZs:

```
VPC: 10.0.0.0/16 (65,536 addresses)

Public subnets (load balancers, NAT gateways — few instances needed):
  10.0.0.0/24   AZ-a public   (251 usable)
  10.0.1.0/24   AZ-b public
  10.0.2.0/24   AZ-c public

Private subnets (application servers — many instances):
  10.0.10.0/23  AZ-a private  (507 usable)
  10.0.12.0/23  AZ-b private
  10.0.14.0/23  AZ-c private

Database subnets (RDS instances — very few, static):
  10.0.20.0/28  AZ-a database (11 usable after AWS reservations)
  10.0.20.16/28 AZ-b database
  10.0.20.32/28 AZ-c database

Reserved for future expansion:
  10.0.32.0/19 through 10.0.255.0/24 (most of the /16 is unallocated)
```

## Section 5: VPC Networking in AWS

**Q13. How does AWS VPC subnetting work, and what makes a subnet "public" vs "private"?**
A: An AWS VPC (Virtual Private Cloud) is a logically isolated network within AWS, backed by a CIDR block you choose (e.g., `10.0.0.0/16`). Subnets are subdivisions of the VPC's CIDR block — each subnet is associated with exactly one Availability Zone.

**Public vs private subnet — it's about route tables, not names:**

A **public subnet** has a route in its route table that sends traffic destined for `0.0.0.0/0` (all non-local destinations) to an Internet Gateway (IGW). Instances in a public subnet with public or Elastic IPs can initiate and receive connections from the Internet:
```
Public subnet route table:
  Destination    Target
  10.0.0.0/16   local       ← traffic to any VPC subnet stays local
  0.0.0.0/0     igw-abc123  ← everything else → Internet Gateway
```

A **private subnet** has NO route to an Internet Gateway. Its default route goes to a NAT Gateway (for outbound-only Internet access) or has no Internet route at all:
```
Private subnet route table:
  Destination    Target
  10.0.0.0/16   local
  0.0.0.0/0     nat-xyz789  ← outbound only via NAT Gateway in public subnet
                              (NAT Gateway has a public IP; instances in private subnet do not)
```

A **database subnet** (also private) often has no Internet route at all — only local VPC traffic, typically from the application tier's subnet. RDS, ElastiCache, and other managed services that should never be Internet-accessible live here.

**What makes a subnet "public" is solely the route table entry pointing to the IGW** — the word "public" is a convention, not a special AWS configuration option.

**Q14. What are the five addresses AWS reserves in every subnet, and why?**
A: For a subnet `10.0.1.0/24`, AWS reserves:

| Address | Purpose |
|---|---|
| `10.0.1.0` | Network address (standard — cannot assign to any resource) |
| `10.0.1.1` | AWS VPC router — the default gateway for all instances in this subnet |
| `10.0.1.2` | AWS DNS server — provides DNS resolution for the VPC (Route 53 Resolver) |
| `10.0.1.3` | Reserved for future AWS use |
| `10.0.1.255` | Broadcast address (standard — cannot assign; though AWS doesn't support broadcast, the address is still reserved) |

This means a `/24` subnet (256 addresses) has 251 usable IP addresses in AWS — not 254 (the RFC-standard calculation). For small subnets, this matters significantly:

| Prefix | Total | RFC usable | AWS usable |
|---|---|---|---|
| /28 | 16 | 14 | 11 |
| /27 | 32 | 30 | 27 |
| /26 | 64 | 62 | 59 |
| /24 | 256 | 254 | 251 |

For Lambda functions in a VPC: AWS also creates Elastic Network Interfaces (ENIs) for Lambda in the subnet — each ENI consumes an IP. A burst of Lambda invocations in a /28 subnet (11 usable IPs) will rapidly exhaust the address space and start failing with `ENI_LIMIT_EXCEEDED`. For Lambda, use /24 subnets or larger.

**Q15. What is VPC CIDR range planning, and what are the constraints you must plan for upfront?**
A: VPC CIDR ranges are difficult to change after creation — in practice, you add secondary CIDR blocks rather than changing the primary. The choice at VPC creation time has long-lasting consequences:

**Constraints:**

**Minimum VPC size:** /28 (16 addresses). Maximum VPC size: /16 (65,536 addresses). For anything non-trivial, /16 is the standard starting point.

**Non-overlapping with on-premises and VPC peers:**
If the VPC will be connected to an on-premises network (Direct Connect, VPN) or peered with other VPCs, the CIDR ranges must not overlap. Overlapping CIDRs prevent peering and create routing conflicts:
```
VPC A: 10.0.0.0/16
VPC B: 10.1.0.0/16     ← can be peered (non-overlapping)
On-premises: 10.0.0.0/8 ← CONFLICT with VPC A — cannot route between them
```

**RFC 1918 blocks only (recommended):** Using non-private ranges for VPCs creates routing conflicts with those real Internet addresses. Always use 10.x, 172.16-31.x, or 192.168.x.

**Subnet size for ENIs and Lambda:**
Lambda in VPC creates one ENI per concurrent execution (up to the burst limit). A service that bursts to 100 concurrent Lambda executions needs at least 3 subnets across 3 AZs with enough IPs each (e.g., 3 × /24 subnets = 753 usable IPs total). Under-sizing kills Lambda scaling.

**Future growth:**
An EKS (Kubernetes) cluster in a VPC assigns one IP per pod (AWS VPC CNI). A cluster with 500 pods in one AZ consumes 500 IPs from that AZ's subnet. Plan /22 or /21 subnets for Kubernetes node groups and pod subnets.

**Recommended VPC CIDR planning pattern (Production):**
```
VPC: 10.0.0.0/16

Plan the space in quarters:
10.0.0.0/18   → Availability Zone A (16,384 addresses)
10.0.64.0/18  → Availability Zone B
10.0.128.0/18 → Availability Zone C
10.0.192.0/18 → Reserved for future (expansion, special subnets)

Within each AZ block (e.g., 10.0.0.0/18):
10.0.0.0/20   → Public subnet    (4096 - 5 = 4091 usable)
10.0.16.0/20  → Private subnet   (4091 usable)
10.0.32.0/20  → Database subnet  (4091 usable)
10.0.48.0/20  → Reserved
```

## Section 6: IPv6 Addressing

**Q16. How does IPv6 addressing differ from IPv4, and what are the key notations?**
A: IPv6 uses 128-bit addresses — 4 times larger than IPv4's 32 bits. The total address space is 2¹²⁸ ≈ 3.4 × 10³⁸ addresses. At a rate of a trillion addresses per second, exhausting the IPv6 space would take longer than the current age of the universe — IPv4 exhaustion drove the creation of IPv6.

**IPv6 notation:**
IPv6 addresses are written as 8 groups of 4 hexadecimal digits, separated by colons:
```
2001:0db8:0000:0000:0000:8a2e:0370:7334
```

Two compression rules shorten representations:
1. **Leading zeros within a group can be omitted:** `0db8` → `db8`, `0000` → `0`
2. **One or more consecutive groups of all zeros can be replaced with `::`** (only once per address):
```
2001:0db8:0000:0000:0000:8a2e:0370:7334
     ↓ remove leading zeros
2001:db8:0:0:0:8a2e:370:7334
     ↓ collapse consecutive zeros
2001:db8::8a2e:370:7334
```

**IPv6 prefix notation (still CIDR):**
`2001:db8::/32` — a /32 prefix for documentation purposes.
`2001:db8:1234::/48` — a typical organisational prefix.
`2001:db8:1234:5678::/64` — a typical subnet (a /64 is the standard subnet size in IPv6).

**Key IPv6 special addresses:**

| Address | Purpose |
|---|---|
| `::1/128` | Loopback (equivalent to IPv4's `127.0.0.1`) |
| `fe80::/10` | Link-local (auto-configured, not routable; one per interface) |
| `fc00::/7` | Unique local addresses (RFC 4193 — equivalent to RFC 1918; `fd00::/8` is the usable range) |
| `2000::/3` | Global unicast (the routable Internet address space) |
| `ff00::/8` | Multicast |
| `::ffff:0:0/96` | IPv4-mapped IPv6 addresses (used in dual-stack transitions) |

**Why IPv6 doesn't need NAT:** Every device gets a globally unique routable address — the scarcity that made NAT necessary in IPv4 doesn't exist. This restores the original end-to-end Internet model where every device is directly addressable. Security policies (firewalls, security groups) replace NAT as the mechanism for controlling inbound access.

**AWS VPC and IPv6:**
AWS assigns a `/56` IPv6 CIDR block to each VPC (256 `/64` subnets). Each subnet gets a `/64` block. IPv6 in AWS VPCs uses global unicast addresses — they are publicly routable. An "IPv6-only" subnet has no IPv4 addresses; "dual-stack" subnets have both. An Egress-Only Internet Gateway (EIGW) provides outbound-only IPv6 access (equivalent to NAT Gateway for IPv6) for private subnets.

## Section 7: Scenario / System Design Style Questions

**Q17. "You're designing the VPC architecture for a three-tier payment processing application (web, app, database) across three Availability Zones. Walk through your CIDR design."**
A: A structured approach, starting from requirements:

**Requirements:**
- 3 AZs for high availability.
- 3 tiers: public (ALB, NAT), private (ECS/EC2 app servers), database (RDS).
- Future expansion: Kubernetes pods, Lambda, additional services.
- No overlap with on-premises (uses `10.1.0.0/8` block).
- Must support VPC peering with shared services VPC (`10.2.0.0/16`).

**VPC selection:** Use `10.0.0.0/16` — non-overlapping with `10.1.0.0/8` and `10.2.0.0/16`, maximum size, room to grow.

**Dividing the VPC into AZ bands:**
```
10.0.0.0/16 total space (65,536 addresses)

AZ-a: 10.0.0.0/18    (16,384 addresses — addresses .0.0 to .63.255)
AZ-b: 10.0.64.0/18   (16,384 addresses — addresses .64.0 to .127.255)
AZ-c: 10.0.128.0/18  (16,384 addresses — addresses .128.0 to .191.255)
Spare:10.0.192.0/18  (16,384 reserved for future)
```

**Dividing each AZ band into tier subnets (using AZ-a as example):**
```
AZ-a band: 10.0.0.0/18

Public (ALB, NAT GW — few static resources):
  10.0.0.0/24    → 251 usable (ALB ENIs, NAT Gateway allocation)

Private App (ECS tasks, EC2 — many, auto-scaling):
  10.0.8.0/21   → 2043 usable (room for ECS scaling bursts)

Database (RDS — small, static):
  10.0.16.0/24  → 251 usable (RDS primary + replica instances)

Future (EKS pods, Lambda, new tiers):
  10.0.17.0/24  through 10.0.63.255 → reserved
```

**Applying same pattern to AZ-b and AZ-c:**
```
AZ-b: 10.0.64.0/24 public, 10.0.72.0/21 private, 10.0.80.0/24 database
AZ-c: 10.0.128.0/24 public, 10.0.136.0/21 private, 10.0.144.0/24 database
```

**Route tables:**
- Public subnets: `0.0.0.0/0 → igw-*` (Internet Gateway)
- Private app subnets: `0.0.0.0/0 → nat-*-a/b/c` (NAT Gateway in same AZ — for AZ-local resilience)
- Database subnets: no Internet route; only VPC-local traffic allowed

**Security groups (not subnet-level, but part of the design):**
- ALB SG: inbound 443 from 0.0.0.0/0; outbound to app SG on port 3000
- App SG: inbound from ALB SG on 3000; outbound to DB SG on 5432
- DB SG: inbound from App SG on 5432 only; no Internet outbound

**Q18. "A Node.js service in a private subnet needs to call an external payment gateway API. Walk through the network path."**
A:

```
Node.js instance (10.0.8.15 in private subnet 10.0.8.0/21, AZ-a)
  │
  ▼
Route table lookup for destination (api.juspay.in → 203.0.113.42):
  10.0.0.0/16 → local    (203.0.113.42 is NOT in this range → no match)
  0.0.0.0/0  → nat-gateway-a (10.0.0.42, in public subnet AZ-a)
  → packet forwarded to NAT Gateway

NAT Gateway (10.0.0.42, private IP / 54.x.y.z Elastic IP):
  → Translates source: 10.0.8.15:54321 → 54.x.y.z:48291 (NAT mapping)
  → Route table of public subnet: 0.0.0.0/0 → igw-*
  → Packet forwarded to Internet Gateway

Internet Gateway:
  → Routes packet to public Internet toward 203.0.113.42

[Internet routing — BGP paths across ISPs]

JusPay API server (203.0.113.42):
  → Receives request from 54.x.y.z:48291
  → Sends HTTP response to 54.x.y.z:48291

Return path:
  203.0.113.42 → 54.x.y.z:48291
  → Internet Gateway → NAT Gateway
  → NAT Gateway looks up 48291 → 10.0.8.15:54321
  → Translated and forwarded to Node.js instance

Node.js receives the response — https.request() callback fires
```

**Key observations:**
- The JusPay API only ever sees the NAT Gateway's public IP (`54.x.y.z`). The Node.js instance's private IP (`10.0.8.15`) is never visible externally.
- JusPay can whitelist `54.x.y.z` as the source IP — common for payment gateway IP allowlisting.
- If the NAT Gateway in AZ-a fails, traffic from AZ-a's private subnets loses Internet connectivity until a route table update points to a NAT Gateway in another AZ (this is why production architectures deploy one NAT Gateway per AZ and configure per-AZ route tables).

**Q19. "You receive an alert: a service can't reach its RDS database. The error is `ETIMEDOUT`. Walk through diagnosing using subnet and security group knowledge."**
A: ETIMEDOUT at the application level means a TCP connection attempt timed out — either the packet never reached the RDS instance, or the response never returned. Systematically check the layers:

**Step 1 — Verify basic connectivity from within the VPC:**
```bash
# From the application EC2 instance or a bastion host in the same VPC:
nc -zv <rds-endpoint> 5432     # TCP probe to PostgreSQL port
# If timeout: routing/security group issue
# If "Connection refused": port open but PostgreSQL rejecting

# Resolve the RDS endpoint to its private IP (should be in the DB subnet):
dig <rds-endpoint>
# Expected: 10.0.16.x or similar (private DB subnet IP)
# If returns 0.0.0.0 or no answer: DNS resolution issue within VPC
```

**Step 2 — Check security groups (most common cause):**
```bash
# RDS security group — does it allow inbound on port 5432 from the app's security group?
aws ec2 describe-security-groups --group-ids <rds-sg-id>

# Expected rule:
# Type: PostgreSQL (TCP 5432)
# Source: <app-sg-id>  ← must be the app server's security group, not its IP
#         (SG-to-SG rules are preferred over IP-based rules for dynamic EC2 IPs)

# If the rule uses an IP range instead of an SG, and the app's IP changed (new EC2 launch):
# The old IP rule won't match the new instance
```

**Step 3 — Check subnets and route tables:**
```bash
# Which subnet is the RDS instance in?
aws rds describe-db-instances --query 'DBInstances[*].DBSubnetGroup'

# Are the app subnet and DB subnet in the same VPC?
aws ec2 describe-subnets --subnet-ids <app-subnet-id> <db-subnet-id> \
  --query 'Subnets[*].{SubnetId,VpcId,CidrBlock}'
# Both must be in the same VPC — traffic between VPC subnets uses "local" route, no NAT

# Check route table for the app subnet:
aws ec2 describe-route-tables --filters "Name=association.subnet-id,Values=<app-subnet-id>"
# For intra-VPC traffic, the "local" route (VPC CIDR → local) handles it
# No route needed; if this is missing → serious misconfiguration
```

**Step 4 — Check NACLs (Network Access Control Lists — subnet-level, stateless):**
```bash
# NACLs are stateless — must allow both inbound AND outbound (unlike security groups which are stateful)
aws ec2 describe-network-acls --filters "Name=association.subnet-id,Values=<db-subnet-id>"

# Common NACL misconfiguration: outbound rules on the DB subnet block the response
# Even if inbound 5432 is allowed, if outbound ephemeral ports (1024-65535) are blocked,
# the RDS response never reaches the app server
```

**Step 5 — VPC Flow Logs:**
```bash
# If all the above look correct but ETIMEDOUT persists:
# Enable VPC Flow Logs on the VPC or specifically on the DB subnet's ENI

# Look for REJECT entries:
aws logs filter-log-events \
  --log-group-name /aws/vpc/flowlogs \
  --filter-pattern "REJECT" \
  --start-time $(date -d '30 minutes ago' +%s000)
# A REJECT log for traffic from app IP to RDS IP on port 5432 → security group or NACL blocking
# An ACCEPT log but ETIMEDOUT → application-level issue (wrong connection string, DB overloaded)
```

**Most common root causes ranked:**
1. Security group on RDS doesn't allow the app's security group or IP — most common.
2. RDS endpoint resolving to wrong IP (wrong AWS region, wrong VPC DNS setting).
3. NACL blocking ephemeral port return traffic — often overlooked because NACLs are stateless.
4. Different VPC — the app and RDS are in different VPCs with no peering.
5. Wrong port in the connection string — app tries 5432 but MySQL RDS is on 3306.

## Quick Reference: Subnet Math Cheat Sheet

```
Prefix length → block size (2^(32-prefix)):
  /24 → 256    /25 → 128   /26 → 64    /27 → 32
  /28 → 16     /29 → 8     /30 → 4     /31 → 2
  /20 → 4096   /21 → 2048  /22 → 1024  /23 → 512
  /16 → 65536  /17 → 32768 /18 → 16384 /19 → 8192

Usable hosts (RFC) = block size - 2 (network + broadcast)
Usable hosts (AWS) = block size - 5 (network, router, DNS, future, broadcast)

Converting prefix to subnet mask:
  /24 → 255.255.255.0     /25 → 255.255.255.128
  /26 → 255.255.255.192   /27 → 255.255.255.224
  /28 → 255.255.255.240   /29 → 255.255.255.248
  /30 → 255.255.255.252   /20 → 255.255.240.0
  /16 → 255.255.0.0       /8  → 255.0.0.0

Network address = IP AND mask
Broadcast = network OR (NOT mask)  [set all host bits to 1]
First host = network + 1
Last host = broadcast - 1

Subnets created by borrowing N bits = 2^N
Block starts at multiples of block_size in the relevant octet

RFC 1918 private ranges:
  10.0.0.0/8         (16,777,216 addresses)
  172.16.0.0/12      (1,048,576  addresses)  [172.16–172.31]
  192.168.0.0/16     (65,536     addresses)

AWS-specific:
  169.254.169.254/32 — instance metadata service (IMDS)
  169.254.169.253/32 — VPC DNS resolver (Route 53 Resolver)
  169.254.0.0/16     — link-local (APIPA, used internally by AWS)

CIDR notation quick checks:
  Is x.y.z.w in 10.0.0.0/8?
    → x must equal 10 ✓
  Is 172.20.0.1 in 172.16.0.0/12?
    → 172.16–172.31 range; 20 is in range ✓
  Is 192.168.5.130 in 192.168.5.128/26?
    → block starts at .128, size 64, ends at .191; .130 is in range ✓
```

**Tip for the interview:** At 5 YOE, IP addressing questions don't come as "what is the broadcast address of 192.168.1.0/24?" — they come as architecture problems ("design the VPC CIDR layout for a multi-AZ payment platform"), debugging scenarios ("the app can't reach RDS — walk me through your diagnosis"), or AWS-specific gotchas ("why does a Lambda function in a /28 subnet fail to scale?"). The calculations that matter are: determining subnet size from prefix length (block size = 2^(32-prefix)), knowing the five AWS reserved addresses, planning non-overlapping CIDR ranges for VPC peering, and understanding that "public vs private subnet" is entirely a routing table decision. Have one concrete story ready about a VPC design choice or a subnet-related incident — NACL blocking return traffic is the classic gotcha — and explain it in terms of addresses, masks, and routing.
