# CDN Internals: Anycast Routing, PoPs & Origin Shield — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a CDN, and what problems does it solve that a single-origin server cannot?**
A: A CDN (Content Delivery Network) is a geographically distributed network of servers that caches and delivers content to users from locations physically near them, rather than from a single central origin server. The fundamental problems it solves are rooted in the physics of networking — the speed of light imposes a hard lower bound on latency proportional to physical distance:

- **Latency** — a user in Chennai requesting content from a server in Virginia (USA) faces at minimum ~180ms RTT just from signal propagation time (~9,000km at ~200,000km/s through fibre). Serving from a Mumbai PoP reduces that to ~5ms. CDNs place servers near users, collapsing the physics problem.
- **Throughput and bandwidth** — a single origin server's network uplink is a shared resource. A CDN distributes that bandwidth across hundreds of PoPs, each serving nearby users independently. Capacity scales horizontally with the network.
- **Origin load** — without a CDN, every user request hits the origin. With a CDN, cache-hit requests never reach the origin. An origin that serves 10,000 RPS with a 90% cache hit rate actually receives only 1,000 RPS — a 10× reduction in origin load.
- **Availability** — a CDN's distributed topology provides resilience. A DDoS attack or origin failure affecting one region can be absorbed by the CDN layer while other PoPs continue serving cached content. The CDN is a buffer between the internet and the origin.
- **Last-mile performance** — CDN providers maintain high-bandwidth peering agreements with ISPs and carrier networks. Content served from within an ISP's network or from a nearby exchange point is faster than content traversing the open internet.

**Q2. What is anycast routing, and how does it differ from unicast?**
A: Anycast is a network addressing and routing scheme in which a single IP address is simultaneously announced from multiple physical locations. The internet's routing infrastructure (BGP) automatically directs each packet to the topologically nearest node advertising that address.

**Unicast (standard):**
One IP address → one physical destination. A packet sent to `54.239.28.85` always arrives at the same server, regardless of the sender's location. All users worldwide route to that one machine.

**Anycast:**
One IP address → many physical destinations. A packet sent to `1.1.1.1` arrives at the Cloudflare server nearest to the sender — the same IP routes to a different physical machine depending on where the request originates.

```
Unicast:
User (Mumbai)    ──────────────────────────────────────► Server (Virginia, 54.1.2.3)
User (Berlin)    ──────────────────────────────────────► Server (Virginia, 54.1.2.3)
User (Tokyo)     ──────────────────────────────────────► Server (Virginia, 54.1.2.3)
All users share one physical server despite geography

Anycast:
User (Mumbai)    ──────────────────────► PoP Mumbai (104.16.0.1)    ← same IP, nearest server
User (Berlin)    ──────────────────────► PoP Frankfurt (104.16.0.1) ← same IP, nearest server
User (Tokyo)     ──────────────────────► PoP Tokyo (104.16.0.1)     ← same IP, nearest server
Each user served by the physically closest server despite identical IP
```

**The BGP mechanism:**
Each CDN PoP runs BGP (Border Gateway Protocol) and announces the same IP prefix (e.g., `104.16.0.0/12`) to its upstream ISPs. BGP's path selection algorithm, combined with the shortest-AS-path preference, causes routers worldwide to route packets toward the topologically nearest announcement. When a user's ISP router has a choice between a route to the anycast IP via a local CDN PoP or via a distant backbone, it chooses the shorter path — the local PoP.

**Q3. What is a Point of Presence (PoP), and what components does it typically contain?**
A: A Point of Presence is a physical datacenter facility where a CDN provider has deployed its edge infrastructure. It is the physical location to which user requests are routed via anycast, and from which cached content is served.

**Typical PoP components:**

- **Edge servers (cache nodes)** — the primary serving layer. Each cache node holds a portion of the CDN's cached content in memory (L1 cache) and on NVMe SSDs (L2 cache). Multiple cache nodes within a PoP form a cluster; consistent hashing distributes cache keys across nodes so any node in the PoP can forward a miss to the correct peer before going to origin.

- **BGP routers / anycast infrastructure** — announce the CDN's IP prefixes to the local ISP and internet exchange point (IXP) peering partners. Responsible for routing user packets into the PoP.

- **Load balancers** — distribute incoming connections across cache nodes within the PoP. May be hardware (F5, Juniper) or software (Nginx, Envoy, proprietary).

- **TLS termination** — TLS handshakes are CPU-intensive. Large PoPs may have dedicated TLS termination hardware (Intel QAT, Marvell NITROX) or offload TLS to dedicated software instances. Terminating TLS at the PoP means the user's TLS session ends in the nearby city, not at the distant origin — significantly reducing TLS handshake latency.

- **Network interconnect** — the PoP connects to local ISPs via peering (direct physical connections at IXPs) and transit (paid upstream bandwidth providers). Cloudflare peers with 10,000+ networks; this peering density means CDN-served traffic often stays within the ISP's own network.

- **Health monitoring / control plane** — local agents report PoP health to the global CDN control plane. If a PoP's origin connectivity degrades or a cache node fails, the control plane can withdraw the anycast announcement for that PoP, diverting traffic to neighbouring PoPs.

PoP sizes vary from "mega-PoPs" (Cloudflare's core locations — hundreds of servers, multi-hundred-gigabit connectivity) to "micro-PoPs" or "edge nodes" embedded in ISP networks (a handful of servers providing last-mile cache hits).

**Q4. How does a CDN decide what to cache, and what is a cache hit vs a cache miss?**
A: CDN caching behaviour is determined by a combination of HTTP response headers from the origin, CDN-specific configuration rules, and content-type heuristics:

**Cache decision hierarchy:**
1. **`Cache-Control` header** (highest priority) — `public, max-age=3600` tells the CDN to cache the response for 3600 seconds. `private` or `no-store` tells the CDN not to cache at all.
2. **`Surrogate-Control` / `s-maxage`** — CDN-specific TTL that overrides `max-age` for CDN caches (but not browser caches): `Cache-Control: public, max-age=60, s-maxage=3600` — browsers cache for 60s, CDN caches for 3600s.
3. **`Vary` header** — instructs the CDN to cache separate copies based on request headers: `Vary: Accept-Encoding` means the CDN stores separate copies for gzip and br compressed responses. `Vary: Cookie` effectively disables caching (too many variants).
4. **CDN configuration rules** — cache rules defined in the CDN dashboard override origin headers. A rule like "cache all `*.js` files for 1 year, ignore `Cache-Control`" enforces caching policy regardless of what the origin says.
5. **Default behaviour** — uncacheable by default: responses with cookies, `Authorization` headers, non-GET/HEAD methods, and responses with no `Cache-Control` header (varies by CDN — Cloudflare applies heuristics; others return uncacheable by default).

**Cache hit vs cache miss:**

- **Cache hit** — the requested content is in the PoP's cache, fresh (within TTL). Served directly from the cache node in milliseconds. The origin is not contacted. `X-Cache: HIT` header in the response.
- **Cache miss** — the content is not in the PoP's cache (never been cached, or TTL expired). The PoP must fetch it from the origin (or from the origin shield — see Section 3). `X-Cache: MISS` header; higher latency (origin RTT added).
- **Stale** — cached but TTL expired. The CDN may serve the stale response while asynchronously revalidating with the origin (stale-while-revalidate), or may block the response until the origin confirms freshness (must-revalidate).

## Section 2: Anycast Routing In Depth

**Q5. How does BGP anycast routing work, and what determines which PoP a user's request reaches?**
A: BGP (Border Gateway Protocol) is the routing protocol of the internet — it propagates reachability information between autonomous systems (ASes), the independent networks operated by ISPs, CDNs, and large enterprises. Anycast exploits BGP's path-selection algorithm to achieve proximity-based routing.

**The mechanics:**

Each CDN PoP is part of the CDN's autonomous system (AS). The CDN announces the same IP prefix from every PoP:
```
Cloudflare AS13335 announces 104.16.0.0/12 from:
  - Frankfurt PoP  → to Deutsche Telekom, Frankfurt IXP (DE-CIX)
  - Mumbai PoP     → to Airtel, Tata, Mumbai IXP (Mumbai-IX)
  - Tokyo PoP      → to NTT, KDDI, Tokyo IXP (JPNAP)
  - São Paulo PoP  → to Embratel, TIM, São Paulo IXP (IX.br)
```

When a packet destined for `104.16.4.77` (a Cloudflare IP) arrives at a router in Airtel's Indian network, Airtel's BGP table shows two paths to `104.16.0.0/12`:
- Via Mumbai peering with Cloudflare (1 AS hop: Airtel → AS13335)
- Via transit to the US (4 AS hops: Airtel → transit → ... → AS13335)

BGP prefers the shorter AS path → packets are sent to the Mumbai PoP. A router in Germany's Deutsche Telekom makes the same decision and sends to Frankfurt.

**What can override shortest-AS-path:**
- **BGP local preference** — an ISP can configure a higher local preference for a peering relationship, overriding AS-path length. Some ISPs prefer sending traffic over a paid transit provider even when a direct peering exists (often due to capacity agreements).
- **MED (Multi-Exit Discriminator)** — a CDN can signal to a peer which of its multiple connections should be preferred for inbound traffic.
- **Routing policy** — CDNs can "deprefer" a PoP by prepending their AS number multiple times in the announcement (`AS13335 AS13335 AS13335 104.16.0.0/12`), making the path appear longer and causing routers to prefer alternative PoPs. Used during maintenance or when a PoP is overloaded.
- **Traffic engineering / congestion** — modern CDNs continuously measure latency and packet loss between PoPs and user networks. Cloudflare's "Argo Smart Routing" and Fastly's "network learning" adjust routing dynamically based on measured path quality, not just BGP topology.

**Q6. What are Internet Exchange Points (IXPs), and why do CDNs prioritise peering at them?**
A: An Internet Exchange Point is a physical facility where multiple networks (ISPs, CDNs, content providers) interconnect directly, exchanging traffic without routing through a third-party transit provider. The exchange is facilitated by a shared switching fabric (a large Ethernet switch) to which all members connect their routers.

**Why CDNs prioritise IXP peering:**

- **Latency reduction** — traffic exchanged at an IXP stays within the facility and is delivered to the peer network without traversing the open internet. A packet from a Cloudflare server at DE-CIX Frankfurt to a Deutsche Telekom user in Frankfurt travels a few hundred metres through the IXP switch, rather than potentially bouncing through a US transit provider.

- **Cost reduction** — transit bandwidth (paying an upstream provider to carry traffic) is expensive. Peering at an IXP eliminates transit costs for traffic exchanged with peering partners. Large IXPs (DE-CIX in Frankfurt, AMS-IX in Amsterdam, LINX in London, DECIX Mumbai) exchange tens of terabits per second.

- **Independence from transit providers** — a CDN relying solely on transit providers is subject to their congestion, routing decisions, and pricing. Peering diversifies the network path portfolio.

- **Last-mile proximity** — major ISPs peer at the same IXPs. A CDN at DE-CIX Frankfurt can exchange traffic directly with Deutsche Telekom, Vodafone, Telefónica, and hundreds of other German networks — ensuring CDN-served content is delivered over the ISP's own network for the final hop to the user.

**IXP membership and reach:**
Cloudflare peers at 300+ IXPs globally. Fastly and Akamai have similar reach. This density of peering is one reason major CDNs can make "serve from within the user's ISP" claims — when the CDN peers with the user's ISP at an IXP, the content effectively enters the ISP's network before reaching the user, experiencing no open-internet latency.

**Q7. How does anycast handle TCP connections, and what happens when a PoP failover occurs mid-connection?**
A: Anycast was originally designed for UDP protocols (DNS, NTP) where each query/response is independent — if one anycast node fails, the next query goes to a different node with no problem. TCP complicates this significantly because TCP connections are stateful:

**The TCP anycast problem:**
A TCP connection is identified by the 4-tuple `(src_IP, src_port, dst_IP, dst_port)`. The server-side state (TCP sequence numbers, TLS session keys, HTTP/2 stream state) lives in one specific server. If a BGP route change causes subsequent packets from the same client to arrive at a different PoP (a different physical machine), that machine has no TCP state for the connection — it sends a TCP RST (connection reset) to the client.

**Why this works in practice:**

BGP route changes are infrequent and slow-propagating (minutes, not milliseconds). A typical HTTP or HTTPS connection lasts seconds to minutes — far shorter than the timescale of BGP convergence. The probability of a BGP route change occurring during a specific short TCP connection is very low.

Within a PoP, anycast routes traffic to one of many physical servers. The load balancer distributes incoming connections consistently using the 4-tuple — all packets from one TCP connection land on the same server within the PoP. Anycast brings traffic to the right PoP; the PoP's internal load balancer ensures session affinity within the PoP.

**PoP-level failover:**
If an entire PoP fails (power outage, network partition), BGP withdrawal of the anycast announcement causes routing to reconverge. New connections go to the next-nearest PoP. Existing connections are reset; clients experience an error and reconnect, which the next-nearest PoP handles. This reconvergence takes 30–300 seconds (BGP convergence time), during which some clients are disrupted.

**Mitigations:**
- **ECMP (Equal Cost Multi-Path)** within the PoP — traffic is distributed across multiple cache nodes using consistent hashing on the 4-tuple, ensuring the same client always reaches the same cache node for a given connection.
- **Graceful drain** during planned PoP maintenance — the CDN gradually shifts the BGP announcement to deprioritise the PoP (AS-path prepending), causing new connections to go to neighbouring PoPs while existing connections drain naturally.
- **QUIC (HTTP/3)** — QUIC connections are identified by a connection ID rather than a 4-tuple, making them more resilient to IP address changes (client switching from Wi-Fi to cellular) and theoretically enabling future anycast-aware connection migration.

**Q8. What is GeoDNS, and how does it complement or differ from anycast?**
A: GeoDNS and anycast solve the same problem (route users to the nearest server) at different layers of the stack:

- **Anycast** operates at the network/routing layer (Layer 3). The same IP address is announced from multiple locations; BGP routing determines which physical server receives the packet. GeoDNS is not involved — the DNS response contains one IP, and anycast handles the rest.

- **GeoDNS** operates at the application layer (DNS). Different IP addresses are returned in DNS responses based on the querying resolver's geographic location. A user in India gets `13.234.89.12` (Mumbai); a user in Germany gets `52.28.45.88` (Frankfurt). The routing is explicit — different IPs for different locations.

| Property | Anycast | GeoDNS |
|--|--|--|
| Layer | Network (BGP routing) | Application (DNS) |
| User sees | Same IP regardless of location | Different IPs per region |
| Granularity | BGP topology (AS-level) | DNS resolver geography |
| Failover speed | BGP convergence (30–300s) | DNS TTL (seconds to minutes) |
| Stickiness | TCP-connection scoped | DNS TTL scoped |
| Implementation complexity | Requires BGP infrastructure | Requires GeoDNS provider |
| Who uses it | CDN edge networks (Cloudflare, Fastly) | Origin load balancing (Route53), DNS resolvers |

**Typical usage:**
- CDNs use anycast for their edge network — all edge PoPs share the same IP block, anycast handles proximity.
- CDNs use GeoDNS for routing to their own PoPs in some architectures, or for directing traffic from CDN edge back to origin servers in specific regions.
- Application backends use GeoDNS (Route53 latency routing, Cloudflare Load Balancer) to direct users to the nearest regional deployment.

**They are complementary:** a global application might use GeoDNS to direct users to one of three regional CDN deployments (APAC, EU, US), with each regional deployment using anycast internally to route to the nearest PoP within the region.

## Section 3: Origin Shield

**Q9. What is an origin shield, and what problem does it solve?**
A: An origin shield (also called a "shield PoP," "parent cache," or "mid-tier cache") is an additional caching layer placed between the CDN's edge PoPs and the origin server. Without an origin shield, every PoP that has a cache miss for a resource independently fetches that resource from the origin — a "thundering herd" problem at the origin level.

**The problem without origin shield:**
```
Scenario: 500 CDN PoPs worldwide, cache for a new blog post expires simultaneously.
Result:   500 cache misses → 500 simultaneous requests to the origin server.
          (The post was popular — every PoP had it cached, all expired at once.)
```

Even for moderately popular content, if 50 PoPs each have a cache miss for the same URL within a short window, the origin receives 50 requests that it must handle. For an origin with 100 RPS capacity, 50 simultaneous cache-miss fetches consume half its capacity for that one resource.

**With origin shield:**
```
Edge PoP (Mumbai)    ──miss──► Origin Shield (Singapore) ──hit──► response
Edge PoP (Chennai)   ──miss──► Origin Shield (Singapore) ──hit──► response
Edge PoP (Kolkata)   ──miss──► Origin Shield (Singapore) ──miss──► Origin Server
                                (Only one request reaches origin,
                                 regardless of how many PoPs have a cache miss)
```

The origin shield acts as a second-level cache. All edge PoPs in a region route their cache misses to a designated shield PoP for that region. If the shield has the content, it serves it — one shield hit serves dozens of edge PoPs. If the shield also misses, it fetches from the origin once — collapsing all simultaneously-missing edge PoPs into a single origin request.

**Q10. How does origin shield reduce origin load, and what are the tradeoffs?**
A: Origin shield reduces origin load through two mechanisms:

**Mechanism 1 — Request collapsing (request coalescing):**
When multiple edge PoPs simultaneously request the same uncached resource, the shield serialises them — it forwards only one request to the origin and fans out the single response to all waiting edge PoPs:

```
Edge PoPs simultaneously requesting /popular-article (all cache miss):
  PoP-Mumbai:   "GET /popular-article" ──► Shield: forwarding to origin...
  PoP-Chennai:  "GET /popular-article" ──► Shield: request in-flight, queuing your response
  PoP-Delhi:    "GET /popular-article" ──► Shield: request in-flight, queuing your response
  PoP-Pune:     "GET /popular-article" ──► Shield: request in-flight, queuing your response

Origin receives: 1 request (not 4)
Origin responds: response delivered to shield
Shield delivers: response to all 4 waiting PoPs simultaneously
```

This is "request coalescing" or "request collapsing" — N simultaneous identical requests collapse into 1 origin request. In Fastly's implementation, this is called "request shielding"; in Cloudflare, "Argo Tiered Caching"; in Varnish (the open-source cache that underlies Fastly), it is a core feature called "grace" combined with "request queueing."

**Mechanism 2 — Increased effective cache hit rate:**
A single shield PoP serving an entire region accumulates more cache hits than any individual edge PoP. An edge PoP in Chennai might serve 10,000 users, caching popular content effectively. But for a long-tail URL requested once per day from Chennai and once from Mumbai, each edge PoP caches it independently — and the Chennai PoP might evict it before it's requested again. The shield PoP serves all Chennai + Mumbai + Delhi + Pune requests, so the long-tail URL is requested 4× per day rather than 1× — much more likely to stay warm in cache.

**Tradeoffs:**

- **Added latency for cache misses** — a request that misses at the edge must travel to the shield before reaching the origin. Edge → Shield → Origin adds one extra network hop vs Edge → Origin directly. For content that the shield also misses (cache miss at both layers), the total latency is higher than without shield.
- **Shield PoP as a single point of failure** — if the shield PoP for a region is unavailable, all edge PoPs in that region lose their second-level cache. Most CDNs mitigate this by using multiple shield PoPs per region or by allowing edge PoPs to fall back to direct origin connections.
- **Complexity** — cache invalidation must propagate through two layers. Purging a resource from the CDN must purge both edge caches and the shield cache, or edge PoPs will re-cache the stale resource from the shield.
- **Shield placement matters** — the shield should be geographically close to the origin (to minimise Shield → Origin latency) and well-connected to edge PoPs (to minimise Edge → Shield latency). Cloudflare allows customers to choose which PoP acts as the shield; Fastly's "shield" is a customer-configurable PoP selection.

**Q11. How does origin shield interact with cache invalidation (purging)?**
A: Cache invalidation with an origin shield is more complex than without — there are now two cache layers to invalidate, and the ordering matters:

**The dual-layer invalidation problem:**
```
Without shield:
  Purge request → CDN invalidates resource across all edge PoPs
  Next request: edge PoP → origin (cache miss) → fresh content cached

With shield:
  Scenario A — Purge edge only (wrong order):
    Edge purge → edge cache cleared
    Next request: edge miss → shield hit → stale content served from shield!
    Shield still has old content → edge re-caches stale content from shield

  Scenario B — Purge shield only (wrong order):
    Shield purge → shield cache cleared
    Edge still has cached content → serves stale from edge for remaining TTL

  Correct order — Purge edge first, then shield:
    Edge purge → edge caches cleared
    Shield purge → shield cache cleared
    Next request: edge miss → shield miss → origin → fresh content
    Fresh content propagates back up: origin → shield → edge
```

**CDN-managed invalidation:**
Production CDNs handle this automatically when you issue a purge via API:
```bash
# Cloudflare Cache Purge API — purges both edge and shield automatically
curl -X DELETE "https://api.cloudflare.com/client/v4/zones/{zone_id}/purge_cache" \
  -H "Authorization: Bearer {token}" \
  -d '{"files": ["https://example.com/api/config.json"]}'

# Fastly Purge API
curl -X PURGE "https://www.example.com/api/config.json" \
  -H "Fastly-Soft-Purge: 1"   # soft purge: mark stale, serve while revalidating
                                # vs hard purge: remove immediately, wait for origin
```

**Soft purge vs hard purge:**
- **Hard purge** — immediately removes the cached object. Next request is a cache miss and waits for origin response. Can cause a thundering herd if many users request the resource simultaneously after a hard purge.
- **Soft purge** (Fastly) / **stale-while-revalidate** — marks the object as stale but continues serving it while asynchronously fetching a fresh copy from the origin. No interruption to users; the update propagates smoothly. The tradeoff: some users see slightly stale content during the brief revalidation window.

**Surrogate keys / cache tags:**
For complex invalidation, CDNs support "cache tags" — metadata attached to cached objects that enables bulk invalidation by tag rather than by URL:
```typescript
// Origin response headers with cache tags
res.setHeader('Cache-Tag', 'product:123 category:electronics featured-items');
res.setHeader('Surrogate-Key', 'product:123 category:electronics'); // Fastly syntax

// Later: product 123 is updated — purge all cached objects tagged with product:123
// Invalidates: product page, category listing, featured items carousel — all at once
// Without cache tags: would need to enumerate every URL containing product 123
```

## Section 4: CDN Caching Mechanics

**Q12. What is the CDN cache key, and what can go wrong with default cache key construction?**
A: A cache key is the identifier used to look up a cached response. The default cache key is typically the full URL (`scheme + host + path + query string`). Two requests with the same cache key are considered the same resource — the CDN returns the same cached response for both.

**Default cache key:**
`https://api.example.com/products?sort=price&page=1`

**Problems with the default cache key:**

**Problem 1 — Query string parameter ordering:**
```
Request A: /products?sort=price&page=1
Request B: /products?page=1&sort=price
```
Both requests return the same content, but the default cache key treats them as different — two separate cache entries, twice the origin load on a miss. Fix: normalise query string parameter ordering in the CDN configuration.

**Problem 2 — Tracking parameters polluting the cache:**
```
Request A: /products?sort=price&utm_source=google&utm_campaign=summer
Request B: /products?sort=price&utm_source=facebook&utm_campaign=winter
```
Different `utm_*` parameters (marketing tracking) cause the CDN to store separate copies of identical content — cache fragmentation that drastically reduces hit rate. Fix: configure the CDN to ignore `utm_*`, `fbclid`, `gclid`, and other tracking parameters when constructing the cache key.

**Problem 3 — Vary header causing over-variation:**
`Vary: Accept-Language` in the origin response causes the CDN to store separate cached copies per language header value. If the CDN receives requests with 50 different `Accept-Language` values (en-US, en-GB, en-IN, ...), it stores 50 copies of content that might be identical. Fix: be explicit — either strip the `Vary` header at the CDN if language variants don't exist, or include language detection in the cache key explicitly.

**Problem 4 — Cookie-based personalisation leaking into cache:**
If the origin includes `Vary: Cookie` or the CDN is configured to vary on cookies, every unique cookie combination is a separate cache key — effectively disabling caching entirely for authenticated sessions. Fix: separate cacheable and non-cacheable content paths; serve personalised content from uncached API responses and cache the static frame/shell separately.

**Q13. What is cache warming, and when is it necessary?**
A: Cache warming is the process of pre-populating a CDN cache with content before users request it — avoiding cold-start cache misses that result in high origin load and poor user latency.

**When cache warming is necessary:**

- **New CDN deployment or migration** — switching from one CDN to another starts with an entirely cold cache. Every request is a cache miss until natural traffic warms the cache organically.
- **After a mass purge** — if all cache entries are purged (configuration change, major content update), the cache is cold and must re-warm from traffic.
- **Product launches or scheduled events** — a flash sale or a major content release (a movie trailer, a product announcement) is announced for a specific time. The CDN cache should be warm before the flood of traffic arrives.
- **Long-tail content with low organic traffic** — content requested rarely may never warm naturally if TTL expires before the next organic request.

**Cache warming strategies:**

```typescript
// Programmatic cache warming — pre-fetch a list of URLs through the CDN
async function warmCache(urls: string[], concurrency = 10): Promise<void> {
  const limit = pLimit(concurrency);
  await Promise.all(
    urls.map(url => limit(async () => {
      const response = await fetch(url, {
        headers: {
          // Send requests that mimic real users (correct Accept headers, etc.)
          'Accept': 'text/html,application/json',
          // Force CDN to fetch from origin (bypass its cache) — vary by CDN
          'Cache-Control': 'no-cache',  // Cloudflare: purges and re-fetches
        }
      });
      const cacheStatus = response.headers.get('cf-cache-status') ||
                          response.headers.get('x-cache');
      console.log(`${url}: ${cacheStatus}`);
    }))
  );
}
```

**Cloudflare's "Cache Reserve" and "Always Online"** — Cloudflare stores a persistent copy of content in R2 object storage as a fallback, warming from R2 instead of origin. This also protects against origin outages.

**Q14. What is a CDN "stale-while-revalidate" strategy, and how does it differ from "stale-if-error"?**
A: Both are cache directives that allow CDNs to serve content beyond its TTL in specific circumstances, trading staleness for availability:

**`stale-while-revalidate`:**
```
Cache-Control: max-age=300, stale-while-revalidate=60
```
After the 300s TTL expires, the CDN may serve the stale cached response for an additional 60 seconds while it asynchronously revalidates with the origin in the background. The user receives a response immediately (no cache-miss latency); the background fetch updates the cache for subsequent requests.

```
t=0s:   Origin responds with content. Cached with max-age=300.
t=300s: Cache TTL expires. Next request received.
        CDN serves stale response immediately (no latency for user)
        CDN simultaneously fetches fresh response from origin (background)
t=301s: Background fetch completes. Cache updated with fresh content.
t=360s: stale-while-revalidate window expires. If still not refreshed: blocking cache miss.
```

**`stale-if-error`:**
```
Cache-Control: max-age=300, stale-if-error=86400
```
If the origin returns a 5xx error or is unreachable, the CDN serves the stale cached response for up to 86400 additional seconds (24 hours). The user sees potentially stale content rather than a 502/503 error page.

```
t=0s:    Origin responds with content. Cached with max-age=300.
t=300s:  Cache TTL expires. Next request received. CDN fetches from origin.
t=300s:  Origin returns 503 (overloaded).
         Without stale-if-error: CDN returns 503 to user.
         With stale-if-error:    CDN serves stale response. User sees content, not error.
         CDN retries origin on subsequent requests.
t=86400s: stale-if-error window expires. Next origin failure → error returned to user.
```

**Practical application for a fintech API:**
```typescript
// For non-sensitive, infrequently changing data (exchange rates, product catalogue):
res.setHeader('Cache-Control', 'public, max-age=60, stale-while-revalidate=300, stale-if-error=3600');
// Users always get fast responses; origin failures are hidden for up to 1 hour

// For sensitive data (account balance, transaction history):
res.setHeader('Cache-Control', 'private, no-store');
// Never cached — always fresh from origin, never stale
```

## Section 5: Tradeoffs, Security & Advanced Patterns

**Q15. What are the security functions a CDN provides, and what are their limitations?**
A: CDNs sit between users and the origin, making them a natural enforcement point for security functions:

**DDoS mitigation:**
CDN PoPs collectively have enormous network capacity (Cloudflare's network capacity exceeds 100 Tbps). A volumetric DDoS attack (flooding with bandwidth) is absorbed by the CDN's distributed network — the attack traffic is distributed across hundreds of PoPs, each of which has the capacity to handle it. The origin, shielded behind the CDN, never sees the attack traffic. Cloudflare has mitigated attacks exceeding 3 Tbps without origin impact.

**Web Application Firewall (WAF):**
CDN WAFs inspect HTTP requests at the edge and block malicious patterns (SQL injection, XSS, path traversal) before they reach the origin. Rules are updated centrally and deployed to all PoPs simultaneously. The tradeoff: WAF rules require maintenance and can produce false positives (blocking legitimate requests).

**Bot management:**
CDNs maintain databases of known-malicious IP addresses, ASes, and bot fingerprints. Requests from these sources can be challenged (CAPTCHA), rate-limited, or blocked at the edge. JavaScript challenge injection (Cloudflare's "Bot Fight Mode") distinguishes browser from headless clients by requiring JavaScript execution.

**TLS offloading and certificate management:**
The CDN terminates TLS at the edge PoP, meaning the origin only needs to handle HTTPS from the CDN (not from every user). CDNs can manage certificate issuance (via Let's Encrypt or their own CA) automatically. The tradeoff: the CDN can decrypt all traffic between user and origin — the user must trust the CDN provider with their data (a significant trust assumption for sensitive applications like banking).

**Limitations:**
- **Origin exposure** — if an attacker discovers the origin's IP (via historical DNS records, email headers, server error messages), they can bypass the CDN and attack the origin directly. Mitigation: hide the origin IP, use Cloudflare Tunnel or similar to ensure only CDN traffic reaches the origin.
- **Trust boundary** — the CDN is in the trust chain. A compromised CDN provider could read all user traffic. End-to-end encryption (where the CDN cannot decrypt — mTLS from user to origin with CDN as a pass-through) sacrifices CDN capabilities for stronger privacy guarantees.
- **False positive WAF rules** — an overly aggressive WAF rule blocks legitimate API clients. Requires WAF rule tuning; the CDN is now in the critical path for API availability.

**Q16. What is CDN "edge computing" and how does it change the CDN model?**
A: Traditional CDNs serve cached static content — they are caches, not compute environments. Edge computing extends CDNs to run arbitrary code at PoP locations, enabling dynamic behaviour without round-tripping to the origin:

**Platforms:**
- **Cloudflare Workers** — V8 JavaScript isolates running at every Cloudflare PoP. No cold start (isolates, not containers). Sub-millisecond startup. Can serve responses, modify requests/responses, interact with KV storage and Durable Objects.
- **Fastly Compute@Edge** — WebAssembly-based, supporting Rust, Go, JavaScript. Stronger isolation model than shared JavaScript.
- **AWS Lambda@Edge** — Lambda functions triggered by CloudFront events (viewer request, origin request, origin response, viewer response). Longer cold start (container-based); higher latency than Workers.
- **Vercel Edge Functions, Netlify Edge Functions** — higher-level developer abstractions built on the same underlying technologies.

**What edge computing enables:**
```typescript
// Cloudflare Worker example — personalisation without origin round trip
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const country = request.cf?.country;
    const url = new URL(request.url);

    // Modify request before forwarding to origin
    if (country === 'IN') {
      url.searchParams.set('currency', 'INR');
      url.searchParams.set('region', 'south-asia');
    }

    // A/B test routing at the edge — no origin involvement
    const variant = Math.random() < 0.1 ? 'B' : 'A';
    url.searchParams.set('variant', variant);

    // Fetch from origin with modified URL
    const response = await fetch(url.toString(), request);

    // Modify response before returning to client
    const modifiedResponse = new Response(response.body, response);
    modifiedResponse.headers.set('X-Variant', variant);
    return modifiedResponse;
  }
};
```

**Edge computing use cases:**
- **A/B testing** — split traffic at the edge without origin involvement.
- **Authentication at the edge** — validate JWT tokens at the PoP, reject unauthenticated requests before they reach the origin.
- **Request/response transformation** — add headers, rewrite URLs, inject personalisation tokens.
- **Dynamic caching rules** — compute cache keys programmatically based on request properties.
- **Bot detection** — run bot scoring logic at the edge without round-tripping to a centralised bot detection service.

**The tradeoff:** edge functions add complexity and debugging difficulty (distributed execution, limited runtime APIs). They work best for stateless transformations — functions that read from the request and produce a response without requiring heavy compute or large data stores.

**Q17. What is "cache poisoning," and how do CDNs defend against it?**
A: Cache poisoning is an attack where an attacker manipulates a CDN's cache to store a malicious response that is then served to other users. It exploits a discrepancy between what the CDN uses as the cache key and what the origin uses to generate the response:

**How it works:**
```
Normal behaviour:
  Request: GET /api/config HTTP/1.1
           Host: example.com
  Cache key: https://example.com/api/config
  Origin generates response based on: path only

Cache poisoning attack:
  Malicious request: GET /api/config HTTP/1.1
                     Host: example.com
                     X-Forwarded-Host: evil.com
  CDN cache key: https://example.com/api/config (same as normal — CDN ignores X-Forwarded-Host)
  Origin generates response using: X-Forwarded-Host header → response contains evil.com links

Result: CDN caches the malicious response under the legitimate cache key.
        All subsequent users requesting /api/config receive the poisoned response.
```

**Defense mechanisms:**

- **Normalise and validate cache keys** — CDNs should only include headers in the cache key that are explicitly listed in `Vary`. Unknown headers from clients should not affect cache key construction.
- **Origin must not reflect unvalidated headers** — origins should not use `X-Forwarded-Host`, `X-Original-URL`, or similar headers to generate response content without strict validation. If the origin always responds identically regardless of these headers, there is nothing to poison.
- **Strip unrecognised headers at the CDN** — configure the CDN to strip headers (like `X-Forwarded-Host`, `X-Original-URL`) before forwarding to the origin, unless explicitly required.
- **`Vary: *`** — marks a response as non-cacheable (no CDN should cache a response with `Vary: *`), appropriate for responses that are sensitive to request variation.
- **Cache-Control: no-store** — prevents CDN from caching the response at all for sensitive or personalised content.

## Section 6: Scenario / System Design Style Questions

**Q18. "Design the CDN architecture for a video streaming platform serving 50 million users across India with 4K video content."**
A: A video streaming CDN architecture must solve three distinct problems: massive object sizes (4K video files are 20–80GB), high concurrency (millions of simultaneous streams), and geographic distribution across India's varied connectivity landscape:

**Tier 1 — Edge PoPs in major metro areas:**
Deploy edge PoPs in Mumbai, Delhi, Bangalore, Chennai, Hyderabad, Kolkata, and Pune — covering 80% of India's internet users within 20ms network latency:

```
PoP specifications (per metro):
  - 10–50 Gbps network uplink (peering at local IXP + transit)
  - 500TB–2PB NVMe SSD cache (video files are large; RAM cache is insufficient)
  - Aggressive prefetching: when a user requests episode 1, pre-warm episodes 2–3
  - Adaptive bitrate (ABR) segment caching: cache all bitrate variants of each segment
  - Long TTL for video segments: 24h–7d (video content is immutable once published)
```

**Tier 2 — Origin shield in Mumbai (closest to origin):**
A single shield PoP in Mumbai (or Singapore for lower origin latency) sits between edge PoPs and the origin:
```
All 7 edge PoPs route cache misses → Mumbai Shield PoP
Shield PoP routes misses → Origin (video storage: S3, GCS, or custom)

Benefits:
  - Shield has 5–10× the cache capacity of any single edge PoP
  - Long-tail content (older episodes, regional language content) stays warm at shield
  - Origin bandwidth reduced 95%+ (only genuine cache misses in shield reach origin)
```

**Content organisation and caching strategy:**
```typescript
// Video segment cache headers (immutable content addressed by hash/timestamp)
res.setHeader('Cache-Control', 'public, max-age=604800, immutable');  // 7 days
res.setHeader('Cache-Tag', `show:${showId} episode:${episodeId} season:${seasonId}`);

// Manifest files (change frequently — new segments added for live content)
res.setHeader('Cache-Control', 'public, max-age=2, stale-while-revalidate=10');

// Thumbnails and metadata (moderately stable)
res.setHeader('Cache-Control', 'public, max-age=3600, stale-while-revalidate=600');
```

**Handling regional content:**
India has 22 official languages. Content in regional languages (Tamil, Telugu, Bengali, Marathi) has concentrated geographic demand. Configure GeoDNS or request routing to serve Tamil content preferentially from the Chennai PoP (nearest to Tamil Nadu) — increasing cache hit rate for regional content.

**Live streaming:**
Live stream segments (HLS/DASH) have 2–10 second TTLs. At 50 million users, even 2-second segments create 25 million requests per second for live content. Solution: use the origin shield for live stream "segment coalescing" — all edge PoPs requesting the same live segment hit the shield once, which fetches from the live packaging origin once. The shield then serves the same segment to all edge PoPs.

**Fallback behaviour:**
```
If edge PoP cache miss → shield miss → origin failure:
  1. Serve last known good segment (stale-if-error: 30s for live, 7d for VOD)
  2. Reduce video bitrate (ABR player adjusts to lower quality variant that may be cached)
  3. Surface error to player only after exhausting all cached alternatives
```

**Q19. "Our CDN cache hit rate is 45%. The target is 80%. How do you diagnose what's hurting the cache hit rate and systematically improve it?"**
A: A 45% hit rate means 55% of requests are missing the cache and hitting the origin — likely a combination of misconfigured cache keys, short TTLs, personalised content leaking into the cache path, and query string fragmentation.

**Step 1 — Segment traffic by cache miss reason**
```bash
# Cloudflare analytics — segment by cf-cache-status
# MISS: genuine miss (not in cache)
# BYPASS: CDN configured to skip cache (Cookie header, Authorization header, etc.)
# DYNAMIC: response marked uncacheable (Cache-Control: private or no-store)
# EXPIRED: was cached but TTL elapsed
# REVALIDATED: was stale but origin confirmed still fresh (304 response)

# Query Cloudflare Logs via R2 or Logpush:
SELECT cf_cache_status, count(*), count(*)/total * 100 as pct
FROM cdn_logs
GROUP BY cf_cache_status
ORDER BY count DESC;
```

**Step 2 — Identify the top cache-miss URLs**
```bash
# Find the most frequently missed URLs — these are high-impact targets
SELECT url, count(*) as miss_count
FROM cdn_logs
WHERE cf_cache_status = 'MISS'
GROUP BY url
ORDER BY miss_count DESC
LIMIT 50;
```

Common patterns to look for:
- `/api/user/profile` — personalised content, correctly uncacheable. Don't try to cache.
- `/api/products?sort=price&page=1&utm_source=google` — UTM parameters fragmenting the cache key.
- `/static/app.js?v=1.0.0` with Cookie header — static asset bypassing cache due to cookie presence.
- `/api/config` with `Cache-Control: no-cache` — origin misconfigured, should be cacheable.

**Step 3 — Fix query string fragmentation**
```
# CDN configuration: ignore tracking parameters in cache key
Cache Key Rules:
  - Remove: utm_source, utm_medium, utm_campaign, utm_content, utm_term
  - Remove: fbclid, gclid, msclkid (ad platform tracking)
  - Normalise: sort query parameters alphabetically
  - Result: /products?page=1&sort=price (same cache key for all marketing variants)
```

**Step 4 — Fix cookie bypass**
```nginx
# Many CDNs bypass cache when Cookie header is present (default behaviour)
# Fix: strip non-session cookies from requests before cache key evaluation

# Cloudflare Page Rule:
# Cache Level: Cache Everything
# Edge Cache TTL: 2 hours
# For: *.example.com/static/*

# Strip session cookies from static asset requests at the CDN edge
# (Worker or Page Rule that removes Cookie from the request before cache lookup)
```

**Step 5 — Extend TTLs for stable content**
```
# Audit current TTLs against content change frequency:
# Static JS/CSS (versioned): max-age=31536000 (1 year, with content-addressed filenames)
# Product catalogue: max-age=300 → increase to 3600 (updates are batch, not real-time)
# API health check: max-age=10 → already short, leave it
# User avatar images: max-age=86400 → appropriate, leave it
```

**Step 6 — Implement origin shield**
If not already in place, a shield PoP dramatically increases hit rate for long-tail content:
```
Before shield: Edge PoP serves 10,000 users, caches top 1,000 URLs well.
               Long-tail URLs miss frequently (requested < 1/TTL).
After shield:  Shield serves all edge PoPs. Sees 100,000 users across region.
               Long-tail URLs now requested 10× more frequently → stay warm.
               Effective hit rate improvement: 10–20 percentage points.
```

**Expected outcome after all fixes:**
- Tracking parameter fix: +10–15% hit rate (eliminates cache fragmentation)
- Cookie bypass fix: +5–10% (static assets now cached)
- TTL extension: +5–10% (fewer expired-then-missed entries)
- Origin shield: +5–15% (long-tail content now cached)
- Combined: 45% → 75–90% hit rate

**Q20. "How does a CDN handle HTTPS — specifically, where does TLS terminate, and what are the security implications?"**
A: TLS termination at the CDN edge is the standard model, and it has significant security implications that a backend engineer needs to understand:

**The TLS model:**
```
Browser ──[TLS session A]──► CDN Edge PoP ──[TLS session B]──► Origin Server

Session A: User's browser ↔ CDN PoP (e.g., Cloudflare Mumbai)
  - Certificate: example.com cert issued to Cloudflare (or customer-provided)
  - Encrypted: YES — all user data is encrypted in transit to the PoP
  - Who can decrypt: ONLY Cloudflare (holds the private key)

Session B: CDN PoP ↔ Origin server
  - Certificate: origin's own certificate (or self-signed, verified by CDN)
  - Encrypted: YES (if HTTPS to origin is configured — always recommended)
  - Who can decrypt: Cloudflare AND the origin server
```

**Security implication — CDN is a TLS MITM:**
The CDN necessarily terminates the user's TLS connection to inspect the HTTP request (for caching, WAF, routing). From a cryptographic standpoint, the CDN is a man-in-the-middle — it can read all plaintext content. Users see `https://example.com` and a valid certificate, but the TLS session terminates at a CDN server, not at the origin.

This is a deliberate trust decision: the user trusts the CDN (Cloudflare, Fastly, Akamai) as much as they trust the origin server. For most applications, this is an acceptable tradeoff — CDNs have strong contractual and legal obligations, audited infrastructure, and are GDPR-compliant data processors.

**For highly sensitive applications (financial, healthcare):**
Options to mitigate CDN access to plaintext:
- **Keyless SSL** — Cloudflare's Keyless SSL keeps the private key on the customer's infrastructure. For each TLS handshake, Cloudflare sends the encrypted client random to the customer's key server (via a separate TLS connection), which decrypts and returns it. The private key never leaves the customer's control, but Cloudflare still decrypts the HTTP session after the handshake.
- **mTLS from client to origin** — configure the CDN as a pass-through (no caching, no WAF) and use client certificates for end-to-end mTLS between the user's application and the origin. The CDN cannot inspect the payload. Sacrifices all CDN caching and WAF benefits.
- **Certificate Transparency logs** — all CDN-issued certificates are publicly logged. Monitoring CT logs for unexpected certificates issued for your domain detects unauthorized CDN TLS interception.

**Origin pull authentication:**
The CDN-to-origin leg should be authenticated to prevent anyone who discovers the origin IP from bypassing the CDN:
```typescript
// Origin validates that requests come from the CDN, not directly from the internet
// Cloudflare: Authenticated Origin Pulls — CDN presents a client certificate
// Origin verifies the certificate belongs to Cloudflare before processing the request

// Or: shared secret in a custom header
const CDN_SECRET = process.env.CDN_SECRET; // set in CDN config and origin env

app.use((req, res, next) => {
  if (req.headers['x-cdn-auth-token'] !== CDN_SECRET) {
    return res.status(403).json({ error: 'Direct access not permitted' });
  }
  next();
});
```

**Q21. "Explain what happens when a CDN PoP in Mumbai loses network connectivity to the origin in Singapore. Walk through the impact and the CDN's response."**
A: A connectivity failure between a PoP and the origin is one of the most important failure modes to understand — it affects cache misses, origin shield function, and cache expiry handling:

**Immediate impact:**
```
t=0s: Mumbai PoP ─────────────────── Singapore Origin
      [network failure — packets dropped/timeout]

User requests to Mumbai PoP:
  Cache HIT:  ✅ Served normally — no origin needed
  Cache MISS: ❌ PoP attempts origin fetch → timeout → error
  Cache STALE (TTL expired): Depends on CDN stale-if-error configuration
```

**Phase 1 — Serving stale content (first line of defence):**
Most CDNs implement `stale-if-error` — if the origin is unreachable, serve the last cached version beyond its TTL:
```
Cache-Control: max-age=300, stale-if-error=86400

If the cached object's TTL expired 10 minutes ago and the origin is unreachable:
  → Serve the stale object (it was fresh 10 minutes ago — probably still accurate)
  → Return X-Cache: HIT, Age: 610 (600s TTL + 10s since expiry)
  → User sees content with at most 10 minute staleness
```

**Phase 2 — Origin shield fallback:**
If the Mumbai PoP has an origin shield configured (Singapore Shield PoP), cache misses route to the shield, not directly to origin:
```
Mumbai Edge PoP → Singapore Shield PoP:
  Shield HIT: ✅ Shield still has the content cached → returned to Mumbai PoP
  Shield MISS: Shield tries origin → if shield is also isolated, fails
```

If the shield is in Singapore and the origin is also in Singapore, both may be affected by the same failure. A resilient architecture uses geographically separated shield and origin:
```
Origin: Singapore (primary)
Shield: Mumbai (serves Indian edge PoPs, geographically separated from origin)
Fallback Origin: Mumbai / Chennai (separate deployment for DR)
```

**Phase 3 — CDN control plane response:**
The CDN's health monitoring detects that the Mumbai PoP cannot reach the origin:
1. CDN marks origin as "unhealthy" for Mumbai PoP.
2. CDN may route Mumbai's origin requests through another PoP that has origin connectivity (PoP-to-PoP forwarding).
3. Alternatively, CDN may deprioritise Mumbai PoP (BGP AS-path prepending) to divert new users to Singapore or Delhi PoP that has origin connectivity.
4. Alerts are fired to the CDN operations team and the customer's monitoring systems.

**Phase 4 — Content still being served:**
For content with long TTLs (video segments, versioned assets), the PoP continues serving cache-hit responses normally for the duration of the TTL. The origin connectivity failure is invisible to users requesting cached content. Only users requesting content not in cache (or content whose TTL just expired) experience degradation.

**Phase 5 — Recovery:**
When origin connectivity is restored, the CDN resumes normal cache-miss resolution. Content that was served stale is replaced at next TTL expiry. Health checks confirm origin is healthy; BGP routes are restored to normal.

**Q22. "How would you configure CDN caching for a REST API that has a mix of public, authenticated, and real-time endpoints?"**
A: A REST API has fundamentally different caching requirements per endpoint type. The key insight is that caching decisions must be made at the endpoint level, not at the domain level:

```typescript
// NestJS interceptor — set cache headers per endpoint type
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common';

@Injectable()
export class CacheHeaderInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler) {
    const response = context.switchToHttp().getResponse();
    const request = context.switchToHttp().getRequest();
    const handler = context.getHandler();

    const cachePolicy = Reflect.getMetadata('cache-policy', handler);

    return next.handle().pipe(
      tap(() => {
        switch (cachePolicy) {
          case 'public-static':
            // Product catalogue, categories, country list — changes infrequently
            response.setHeader('Cache-Control', 'public, max-age=3600, stale-while-revalidate=600');
            response.setHeader('Surrogate-Key', `resource-type:${resourceType}`);
            break;

          case 'public-short':
            // Exchange rates, stock prices — changes frequently but same for all users
            response.setHeader('Cache-Control', 'public, max-age=30, stale-while-revalidate=10');
            break;

          case 'authenticated':
            // Account balance, transaction history — user-specific, never cache at CDN
            response.setHeader('Cache-Control', 'private, no-store');
            response.setHeader('Pragma', 'no-cache');  // legacy clients
            break;

          case 'real-time':
            // WebSocket fallback, live order book — cannot be cached
            response.setHeader('Cache-Control', 'no-cache, no-store, must-revalidate');
            break;

          default:
            // Safe default: do not cache anything unclassified
            response.setHeader('Cache-Control', 'private, no-store');
        }
      })
    );
  }
}

// Usage on controllers:
@Get('/products')
@SetMetadata('cache-policy', 'public-static')
async getProducts() { ... }

@Get('/account/balance')
@SetMetadata('cache-policy', 'authenticated')
async getBalance() { ... }

@Get('/rates/live')
@SetMetadata('cache-policy', 'real-time')
async getLiveRates() { ... }
```

**CDN-level rules (defence-in-depth — even if origin sends wrong headers):**
```
# Cloudflare Page Rules / Cache Rules:
Rule 1: Path matches /api/account/* OR /api/user/*
  → Cache Level: Bypass (never cache authenticated endpoints)

Rule 2: Path matches /api/products OR /api/categories
  → Cache Level: Cache Everything
  → Edge Cache TTL: 1 hour
  → Origin Cache Control: On (respect origin Cache-Control)

Rule 3: Path matches /api/rates
  → Cache Level: Cache Everything
  → Edge Cache TTL: 30 seconds

# This ensures CDN-level rules prevent accidental caching of private data
# even if a developer forgets to set Cache-Control: private on a new endpoint
```

**Bypassing CDN for authenticated sessions:**
Many REST APIs use cookies or `Authorization: Bearer` headers. CDNs are often configured to bypass cache when these headers are present. This is correct for authenticated endpoints but problematic for public endpoints requested by authenticated users (e.g., the product catalogue loaded while a user is logged in):

```
# Solution: CDN cache rule ignores Authorization header for public endpoints
# while still passing it to the origin for validation

Rule: Path matches /api/products
  → Cache Level: Cache Everything
  → Ignore: Authorization header for cache key (but forward to origin)
  → Origin still validates the token; response is the same for all users
  → CDN caches one response served to all authenticated + unauthenticated users
```

**Q23. "A new video goes viral and your CDN is experiencing a thundering herd — 100,000 simultaneous cache misses for the same object. What happens, and how does the CDN handle it?"**
A: A viral moment creates a thundering herd: millions of users simultaneously request content that was just uploaded and is not yet in any CDN cache. Understanding how the CDN handles this — and how to design against it — is a key senior-level concern.

**What happens without mitigation:**

```
t=0s:   Video goes viral. 100,000 users request the same URL simultaneously.
        None are in CDN cache (just uploaded).

Without request coalescing:
  100,000 cache misses → 100,000 simultaneous requests to origin
  Origin capacity: ~1,000 RPS → queue depth: 99,000 requests
  Queue processing time: 99 seconds (if origin can sustain 1,000 RPS)
  Users see 99-second latency or 503 errors
  Result: cascading origin failure, CDN misses continue, origin overwhelmed
```

**Request coalescing (the CDN's primary defence):**
Modern CDNs coalesce simultaneous cache misses for the same object — only one request is sent to the origin regardless of how many cache misses are waiting:

```
t=0s:   100,000 simultaneous cache misses for /video/viral.mp4

With request coalescing (Varnish/Fastly):
  Request 1 → origin (fetching)
  Requests 2–100,000 → queued at the CDN, waiting for Request 1 to complete

  Origin receives: 1 request (not 100,000)
  Origin responds: streams the video
  CDN: receives stream, caches it, delivers to all 100,000 waiting clients simultaneously

  Result: origin sees 1 request; 100,000 users served
```

**Per-PoP coalescing with origin shield:**
Coalescing at a single PoP still leaves every PoP worldwide making its own request:
```
Without shield:
  Mumbai PoP: 1 coalesced request → origin
  Frankfurt PoP: 1 coalesced request → origin
  Tokyo PoP: 1 coalesced request → origin
  = N PoPs × 1 request = N requests to origin

With origin shield:
  Mumbai PoP miss → Singapore Shield PoP (1 coalesced request per shield)
  Frankfurt PoP miss → Frankfurt Shield PoP
  Tokyo PoP miss → Tokyo Shield PoP
  = 3–5 shield PoPs × 1 request = 3–5 requests to origin
  Much more manageable even for massive viral events
```

**Proactive cache warming for known events:**
For events where virality is predictable (product launches, scheduled drops):
```typescript
// Pre-warm before the event
const videoUrl = 'https://cdn.example.com/video/new-release.mp4';
const edgePops = getEdgePoPs(); // list of PoP URLs or use CDN API

// Pre-fetch through each PoP or use CDN's cache warming API
await cacheWarmingService.warm([videoUrl], {
  regions: ['India', 'US', 'Europe'],
  priority: 'high',
  scheduleFor: launchTime - 300000, // 5 minutes before launch
});
```

**Staggered TTL to prevent simultaneous expiry:**
If 100,000 users cached the same object and all their TTLs expire simultaneously, you get a thundering herd on the cache refresh. Add jitter to the TTL:
```typescript
// Origin response: add random jitter to TTL to desynchronise expiry
const baseTtl = 3600; // 1 hour
const jitter = Math.floor(Math.random() * 300); // 0–5 minutes of jitter
res.setHeader('Cache-Control', `public, max-age=${baseTtl + jitter}`);
// Different users cache for 60–65 minutes; expiry is spread over 5 minutes
// Only ~1/30th of the traffic arrives as cache misses per minute instead of all at once
```

**Q24. "How does a CDN enable zero-downtime deployments for a static web application?"**
A: CDNs, combined with content-addressed filenames, enable atomic zero-downtime deployments without any traffic orchestration complexity:

**The content-addressing pattern:**
```
Traditional (breaks during deployment):
  /static/app.js        → same URL, new content on deploy
  During deploy: some CDN nodes have old content, some have new
  Users get mixed old/new assets → broken application

Content-addressed (zero-downtime):
  /static/app.a1b2c3d4.js  → URL encodes content hash
  /static/app.e5f6g7h8.js  → new file for new content, new URL
  Old and new files coexist in CDN cache indefinitely
```

**Deployment sequence:**
```
Step 1: Build new version
  → Generates: app.e5f6g7h8.js, vendor.k9l0m1n2.js, styles.p3q4r5s6.css

Step 2: Upload to CDN/object storage (origin)
  → Old files still present: app.a1b2c3d4.js, vendor.old.js, styles.old.css
  → New files added: app.e5f6g7h8.js, vendor.new.js, styles.new.css

Step 3: Update index.html (the entry point, not content-addressed)
  → New index.html references new JS/CSS filenames
  → Set short TTL on index.html: Cache-Control: max-age=60

Step 4: At TTL expiry, CDN fetches new index.html from origin
  → New users get new index.html → load new JS/CSS files (e5f6g7h8, etc.)
  → Old users (mid-session) continue using old JS/CSS (a1b2c3d4, etc.) — both in CDN cache
  → No mixed-version state possible (each index.html version references its own consistent JS/CSS)

Step 5 (optional): After old version TTL expires, purge old files from CDN and origin
```

**Cache headers for each type:**
```typescript
// Content-addressed assets (hash in filename): cache forever
// The hash changes when content changes → cache bust is automatic
res.setHeader('Cache-Control', 'public, max-age=31536000, immutable');

// index.html (entry point): short TTL, revalidate
res.setHeader('Cache-Control', 'public, max-age=60, must-revalidate');
res.setHeader('ETag', generateETag(indexHtmlContent));
```

**Instant rollback:**
With content-addressing, rollback is instantaneous — just update index.html to reference the previous version's asset filenames. The old JS/CSS files are still in the CDN cache with a 1-year TTL, immediately available with zero origin load.

**Q25. "Walk me through how Cloudflare serves a request for `https://api.example.com/products` from a user in Delhi — from DNS lookup to response delivery, covering every CDN layer."**
A: The complete request lifecycle through Cloudflare's CDN:

**1 — DNS resolution (Application layer):**
The user's device resolves `api.example.com`. The domain's NS records point to Cloudflare's nameservers (`ns1.cloudflare.com`, `ns2.cloudflare.com`). Cloudflare's DNS returns an **anycast IP** from Cloudflare's `104.16.0.0/12` range — the same IP regardless of geography.

**2 — Network routing to the nearest PoP (Network layer):**
The user's packet destined for the anycast IP leaves their device, traverses Airtel India's network. Airtel's BGP routing table shows Cloudflare's anycast IP is reachable via a direct peering at the Mumbai Internet Exchange (MumbaiIX) — a shorter path than any transit provider. The packet is routed to Cloudflare's Mumbai PoP.

**3 — TLS termination at the Mumbai PoP (Application layer):**
Cloudflare's Mumbai PoP terminates the TLS 1.3 connection:
- If the user has connected to `api.example.com` before (and TLS session is resumed), the handshake is 0-RTT. Otherwise 1-RTT.
- Cloudflare presents `api.example.com`'s TLS certificate (managed by Cloudflare on the customer's behalf, or customer-provided via Cloudflare's Keyless SSL).
- Symmetric encryption keys derived; subsequent request data is encrypted.

**4 — HTTP processing and cache lookup (Application layer):**
Cloudflare parses the HTTP/2 HEADERS frame:
```
:method: GET
:path: /products
:scheme: https
:authority: api.example.com
accept: application/json
accept-encoding: br, gzip
authorization: Bearer eyJ...    ← present! Check cache rules for this endpoint
```
Cloudflare evaluates cache rules (configured in the Cloudflare dashboard):
- Rule: `/products` → Cache Everything, Edge TTL 3600s, ignore Authorization header for cache key
- Cache key constructed: `https://api.example.com/products` (Authorization header excluded)
- Lookup in Mumbai PoP's in-memory cache (L1) → MISS
- Lookup in Mumbai PoP's NVMe SSD cache (L2) → MISS
- Cache status: MISS → must fetch from origin or shield

**5 — Origin shield lookup:**
The customer has configured Cloudflare's "Tiered Cache" with Singapore as the shield PoP. Mumbai PoP sends a request to the Singapore Shield PoP:
- Singapore checks its cache: HIT — the `/products` response is cached with 2847s remaining TTL
- Singapore returns the cached response to the Mumbai PoP

**6 — Response from shield to Mumbai PoP:**
Mumbai PoP receives the response from Singapore Shield PoP:
- Stores it in Mumbai's local cache (L1 memory and L2 SSD) for the remaining TTL
- Response headers include: `CF-Cache-Status: HIT`, `Age: 753` (seconds since shield cached it), `X-Cache: HIT`

**7 — Response delivery to the user:**
Mumbai PoP sends the HTTP/2 DATA frame to the user's device over the established TLS connection:
```
HTTP/2 200 OK
content-type: application/json
content-encoding: br              ← Cloudflare applied Brotli compression at the edge
cache-control: public, max-age=3600, s-maxage=3600
cf-cache-status: HIT
age: 753
cf-ray: 8a1b2c3d4e5f6789-BOM    ← Cloudflare Ray ID, BOM = Mumbai PoP
x-served-by: cache-bom1234-BOM

[Brotli-compressed JSON product list]
```

**8 — Subsequent requests (warm cache):**
The next request from any user in India routed to the Mumbai PoP hits the L1 in-memory cache — response time under 5ms from first byte.

**Total latency breakdown for this request:**
```
DNS resolution (Cloudflare DNS, cached):      ~1ms
Network to Mumbai PoP (anycast BGP routing):  ~5ms
TLS 1.3 resumed session (0-RTT):              0ms
Cache lookup (Mumbai L1/L2 miss):             ~1ms
Shield lookup (Mumbai → Singapore):           ~30ms (only because Mumbai missed)
Response delivery (Mumbai → Delhi):           ~5ms
Total for this shield-hit request:            ~42ms

For a Mumbai L1 cache hit (subsequent requests):
  DNS + network + TLS + L1 cache hit:         ~7ms
```

Without Cloudflare, the same request from Delhi to the origin in Singapore would be:
- DNS + TCP + TLS + HTTP to Singapore: ~150ms
- CDN benefit: ~143ms latency reduction for cached content

## Quick Reference Table

| Component | Role | Failure mode | Mitigation |
|--|--|--|--|
| **Anycast routing** | Routes users to nearest PoP via BGP | BGP convergence delay (30–300s) on PoP failure | AS-path prepending for graceful drain; redundant PoPs |
| **Edge PoP** | Terminates TLS, serves cached content | PoP outage disconnects regional users | Multiple PoPs per region; BGP failover to adjacent PoP |
| **Origin shield** | Second-level cache; collapses origin requests | Shield PoP failure removes L2 cache | Multiple shield PoPs; fallback to direct origin pull |
| **IXP peering** | Low-latency traffic exchange with ISPs | Peering link failure | Transit backup; redundant IXP connections |
| **Cache node (L1)** | In-memory cache within PoP | Node failure evicts cache | Consistent hashing; PoP has multiple nodes |
| **TLS termination** | Encrypts user-to-edge traffic | Certificate expiry | Automated renewal (Let's Encrypt / Cloudflare) |
| **WAF / DDoS** | Filters malicious traffic | False positives block legitimate traffic | Rule tuning; allowlist known good IPs |

| Cache directive | Scope | Meaning |
|--|--|--|
| `Cache-Control: public` | CDN + browser | Both CDN and browser may cache |
| `Cache-Control: private` | Browser only | CDN must NOT cache; browser may |
| `Cache-Control: no-store` | All caches | No caching anywhere |
| `Cache-Control: no-cache` | All caches | Cache but revalidate with origin before serving |
| `s-maxage=N` | CDN only | CDN-specific TTL (overrides max-age for CDN) |
| `stale-while-revalidate=N` | CDN (primarily) | Serve stale for N seconds while revalidating |
| `stale-if-error=N` | CDN (primarily) | Serve stale for N seconds when origin errors |
| `immutable` | Browser | Content will never change; skip revalidation |
| `Surrogate-Key` / `Cache-Tag` | CDN | Tag-based bulk invalidation |
| `Vary: Accept-Encoding` | CDN | Store separate copies per encoding |
