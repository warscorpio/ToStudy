# Networking / Computer Science: TCP — 3-Way Handshake, 4-Way Termination, Sequence Numbers, ACKs, Flow Control, Congestion Control — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is TCP, and what guarantees does it provide that UDP does not?**
A: TCP (Transmission Control Protocol) is a connection-oriented, reliable, ordered, byte-stream transport protocol. It runs on top of IP (which is unreliable and unordered) and provides the following guarantees that UDP does not:

- **Reliability** — every byte sent is acknowledged. If an acknowledgment is not received within a timeout, the segment is retransmitted. Data is never silently lost.
- **Ordering** — the receiver reassembles segments in the correct sequence regardless of what order IP delivered them. The application reads bytes in exactly the order they were sent.
- **Error detection** — each segment carries a checksum. Corrupted segments are discarded and retransmitted.
- **Flow control** — the receiver advertises how much buffer space it has; the sender does not overwhelm it.
- **Congestion control** — the sender adapts its transmission rate to network conditions, avoiding congestion collapse.
- **Full duplex** — data flows in both directions simultaneously on a single connection.

UDP provides none of these — it sends datagrams with no acknowledgment, no ordering, no retransmission, and no congestion control. UDP is appropriate when the application handles reliability itself (QUIC, game engines), when ordering doesn't matter (DNS), or when low latency matters more than reliability (live video, VoIP).

**Q2. What is a TCP segment, and what are its most important header fields?**
A: A TCP segment is the unit of transmission at the transport layer. It consists of a header (minimum 20 bytes) followed by a data payload. The header fields that matter most for understanding TCP behavior:

```
Source Port (16 bits):      identifies the sending application endpoint
Destination Port (16 bits): identifies the receiving application endpoint
Sequence Number (32 bits):  byte offset of the first byte of data in this segment
Acknowledgment Number (32 bits): next byte the receiver expects (cumulative ACK)
Data Offset (4 bits):       header length in 32-bit words (minimum 5 = 20 bytes)
Flags (9 bits):
  SYN  — synchronize sequence numbers (connection setup)
  ACK  — acknowledgment number field is valid
  FIN  — sender has finished sending data (connection teardown)
  RST  — reset the connection (abort)
  PSH  — push data to application immediately (bypass Nagle buffering)
  URG  — urgent pointer field is valid (rarely used)
  ECE  — ECN-Echo (explicit congestion notification)
  CWR  — congestion window reduced
Window Size (16 bits):      receiver's current available buffer space (flow control)
Checksum (16 bits):         error detection over header + data + pseudo-header
Urgent Pointer (16 bits):   offset to urgent data (only meaningful if URG set)
Options (variable):         MSS, window scale, SACK, timestamps, etc.
```

**Q3. What is a TCP connection, and what uniquely identifies one?**
A: A TCP connection is identified by a **4-tuple**: `(source IP, source port, destination IP, destination port)`. Every combination of these four values defines a unique connection. This is why a server can maintain thousands of simultaneous connections on port 443 — each client has a different source IP or source port, making every 4-tuple unique.

A connection is a logical construct: it exists as state (sequence numbers, window sizes, timers, buffers) in the kernel's TCP stack on both endpoints. The connection exists from the completion of the 3-way handshake until both sides have exchanged FINs and the TIME_WAIT timer expires. At any moment, the connection is in exactly one state in the TCP finite state machine (LISTEN, SYN_SENT, SYN_RECEIVED, ESTABLISHED, FIN_WAIT_1, FIN_WAIT_2, TIME_WAIT, CLOSE_WAIT, LAST_ACK, CLOSED).

## Section 2: Sequence Numbers and ACKs

**Q4. What are sequence numbers, and what do they count?**
A: TCP sequence numbers count **bytes**, not segments. The sequence number in a segment header is the byte offset of the first byte of the payload within the overall byte stream. If a segment carries bytes 1000–1499 (500 bytes of payload), its sequence number is 1000. The next segment's sequence number will be 1500.

Sequence numbers are 32-bit unsigned integers — they wrap around from 2³² − 1 back to 0. At a sustained transfer rate of 1 Gbps, a 32-bit sequence space wraps in about 34 seconds — fast enough that the TCP timestamps option (PAWS — Protection Against Wrapped Sequences) is used to distinguish old from new segments on high-speed links.

Each side of a TCP connection has its own sequence number space. The client counts bytes it sends; the server counts bytes it sends. These are independent streams — full duplex means two simultaneous byte streams, each with its own sequence number.

**Q5. What is the Initial Sequence Number (ISN), and why is it random?**
A: The Initial Sequence Number is the sequence number used for the first byte of data in a new connection. It is chosen randomly (or pseudo-randomly) by each side independently during the handshake.

Randomness is a security requirement: if ISNs were predictable (e.g., always starting at 0), an attacker could inject forged TCP segments into an existing connection by guessing the current sequence number. With a random ISN, an attacker would need to guess a 32-bit value — approximately 1 in 4 billion chance per guess. This defends against TCP session hijacking and blind injection attacks.

Modern kernels (Linux, macOS, Windows) use a cryptographically seeded ISN generator. RFC 6528 specifies that the ISN should be computed as a hash of the 4-tuple plus a secret key plus a timestamp component — making it both unpredictable and guaranteed to avoid recent sequence numbers from the same 4-tuple.

**Q6. How do acknowledgment numbers work, and what is cumulative acknowledgment?**
A: The acknowledgment number in a TCP header says: "I have received all bytes up to and including byte N−1; I am expecting byte N next." It is always the next expected byte, not the last received byte. This is **cumulative acknowledgment** — one ACK number covers all previously received contiguous bytes.

```
Sender sends:   Segment 1: seq=1000, len=500  (bytes 1000–1499)
                Segment 2: seq=1500, len=500  (bytes 1500–1999)
                Segment 3: seq=2000, len=500  (bytes 2000–2499)

Receiver sends: ACK ack=1500   (received bytes 1000–1499; expecting 1500)
                ACK ack=2000   (received bytes 1500–1999; expecting 2000)
                ACK ack=2500   (received bytes 2000–2499; expecting 2500)
```

The consequence of cumulative ACKs: if segment 2 is lost but segments 1 and 3 arrive, the receiver sends ACK=1500 (still waiting for segment 2). It cannot acknowledge segment 3 yet — the gap at 1500 means bytes 2000–2499 are in the receiver's buffer but unacknowledged. The sender sees ACK=1500 repeated and knows segment 2 was lost.

**Selective Acknowledgment (SACK)**: a TCP option that extends cumulative ACKs with explicit reports of which out-of-order ranges have been received. The receiver can say "I'm missing 1500–1999, but I have 2000–2499." The sender can then retransmit only the missing segment. SACK is negotiated during the handshake and is standard in modern implementations.

**Q7. What are duplicate ACKs, and why do they signal loss?**
A: A duplicate ACK is an ACK with the same acknowledgment number as a previous ACK — the receiver is re-acknowledging the last contiguous byte received without advancing the ACK number. Duplicate ACKs occur when out-of-order segments arrive:

```
Sender sends:   Seg 1 (seq=1000), Seg 2 (seq=1500), Seg 3 (seq=2000), Seg 4 (seq=2500)
Network drops:  Seg 2

Receiver gets:  Seg 1 → ACK 1500   (normal)
                Seg 3 → ACK 1500   (duplicate — still waiting for 1500)
                Seg 4 → ACK 1500   (duplicate — still waiting for 1500)
```

Three duplicate ACKs (i.e., receiving the 4th ACK for the same value — the original plus three duplicates) is the trigger for **Fast Retransmit**: the sender immediately retransmits the missing segment without waiting for the retransmission timeout. This is much faster than waiting for a timeout (which can be hundreds of milliseconds to seconds). Fast Retransmit was the key insight of TCP Reno (RFC 2581, 1999) and remains the primary loss detection mechanism in all modern TCP variants.

## Section 3: Three-Way Handshake

**Q8. Why does TCP use a three-way handshake rather than two-way?**
A: A two-way handshake would be: Client sends SYN, Server receives SYN and replies SYN-ACK — done. The problem: the client has no way to confirm that the server received the SYN-ACK before sending data. More fundamentally, the server cannot confirm that its SYN-ACK actually reached the client and that the client's sequence number was acknowledged.

The three-way handshake solves two problems that a two-way handshake cannot:

- **Both sides must synchronize their sequence numbers.** The client picks an ISN; the server picks its own ISN. The server must communicate its ISN to the client, and the client must acknowledge it. A two-way handshake lets the server acknowledge the client's ISN, but the client never acknowledges the server's ISN — the server's first byte of data could be misinterpreted as a retransmission from an old connection.
- **Both sides must verify the other's reachability.** The client must know the server received its SYN (confirmed by the SYN-ACK). The server must know the client received the SYN-ACK (confirmed by the ACK). Without the third message, the server can never be sure its SYN-ACK was delivered and the connection is truly established.

A two-way handshake allows a pathological case: an old, delayed SYN (from a previous connection attempt) arrives at the server, which responds with SYN-ACK — establishing a half-open connection from the server's perspective, even though the client has moved on. The three-way handshake handles this: the client receives the unexpected SYN-ACK, has no matching connection, and sends RST.

**Q9. Walk through the three-way handshake in detail.**
A:

```
Client                                    Server
  |                                         |
  |──── SYN (seq=x, SYN=1) ──────────────→ |   [Client: SYN_SENT]
  |                                         |   [Server: SYN_RECEIVED]
  |←─── SYN-ACK (seq=y, ack=x+1, SYN=1, ACK=1) ──|
  |                                         |
  |──── ACK (seq=x+1, ack=y+1, ACK=1) ───→ |   [Both: ESTABLISHED]
  |                                         |
  |  (data transfer can begin here)         |
```

Step by step:

**Step 1 — SYN (Client → Server):**
- Client chooses a random ISN `x` (e.g., 1000).
- Sends a segment with `SYN=1, seq=x`. No data payload.
- Client state transitions: `CLOSED → SYN_SENT`.
- SYN "consumes" one sequence number: the next segment from the client will have `seq=x+1`.

**Step 2 — SYN-ACK (Server → Client):**
- Server receives SYN, chooses its own random ISN `y` (e.g., 5000).
- Replies with `SYN=1, ACK=1, seq=y, ack=x+1`.
  - `ack=x+1`: acknowledges the client's SYN (byte x was received; expecting x+1 next).
  - `seq=y`: server's ISN for its own byte stream.
- Server state: `LISTEN → SYN_RECEIVED`. The server has allocated connection state.
- SYN-ACK also "consumes" one sequence number: the next segment from the server will have `seq=y+1`.

**Step 3 — ACK (Client → Server):**
- Client receives SYN-ACK, acknowledges the server's SYN.
- Sends `ACK=1, seq=x+1, ack=y+1`.
  - `ack=y+1`: acknowledges the server's SYN (byte y was received; expecting y+1 next).
- Client state: `SYN_SENT → ESTABLISHED`.
- Server receives ACK, state: `SYN_RECEIVED → ESTABLISHED`.
- The ACK may carry data (TCP Fast Open allows this). Without Fast Open, it is a bare ACK with no payload.

**Q10. What is a SYN flood attack, and how does SYN cookies defend against it?**
A: A SYN flood is a denial-of-service attack in which an attacker sends massive volumes of SYN packets (often with spoofed source IPs) to a server. The server allocates connection state (a half-open connection in the SYN_RECEIVED state) for each SYN, waiting for the final ACK that never comes. These half-open connections fill the server's SYN backlog queue; legitimate connections are refused with connection timeout.

**SYN cookies** is the defense: instead of allocating state on receiving a SYN, the server encodes all necessary connection state (client IP, client port, server ISN derived from a hash of the 4-tuple + timestamp + secret key) into the ISN sent in the SYN-ACK. The server sends the SYN-ACK and discards all state — it remembers nothing about the half-open connection.

When the legitimate ACK arrives with `ack = server_ISN + 1`, the server decodes the cookie from that value, verifies it (recomputes the hash and checks it matches), and recreates the connection state on the fly. Spoofed SYNs produce no ACK — they consume no persistent server resources.

The cost: SYN cookies can't carry TCP options (MSS, SACK, window scale) because that information can't fit in the ISN. Connections established via SYN cookies lose these optimizations. Linux enables SYN cookies automatically when the SYN backlog is exhausted (`net.ipv4.tcp_syncookies = 1` by default).

**Q11. What is TCP Fast Open (TFO), and how does it reduce latency?**
A: TCP Fast Open (RFC 7413) eliminates the round-trip overhead of the handshake for repeat connections. Normal TCP requires a full round trip (SYN → SYN-ACK → ACK) before any data is transmitted — then another round trip for the request and response. TFO allows data to be sent in the SYN itself on the second and subsequent connections to the same server.

Mechanism:
```
First connection (TFO cookie acquisition):
  Client: SYN + TFO option (empty cookie request)
  Server: SYN-ACK + TFO option (sets a server-generated cookie, keyed to client IP)
  Client: ACK → caches the cookie

Subsequent connections:
  Client: SYN + TFO option (cookie) + HTTP request data   ← data in the SYN!
  Server: validates cookie → SYN-ACK + HTTP response data  ← response without waiting for ACK
  Client: ACK

Result: one round trip instead of two before the response arrives.
```

TFO reduces the latency cost of short-lived TCP connections (common in HTTP/1.1 without keep-alive, and still relevant for the first connection in HTTP/2). It is enabled by default on modern Linux (`net.ipv4.tcp_fastopen = 3`), macOS, and iOS. Security consideration: TFO data can be replayed (the server processes data before the three-way handshake completes), so TFO is only safe for idempotent requests.

## Section 4: Four-Way Termination

**Q12. Why does TCP use a four-way termination rather than two-way?**
A: Because TCP connections are full duplex — two independent byte streams, one in each direction. Each stream must be closed independently. A FIN from one side only closes that side's stream (the sender has no more data); the other side's stream may still be open (the other side may have more data to send).

A two-way close would require both sides to simultaneously have no more data — an unlikely coincidence. The four-way process allows either side to finish sending independently:

```
Side A finishes sending → FIN A
Side B acknowledges     → ACK
Side B finishes sending → FIN B  (may be delayed — B is still sending)
Side A acknowledges     → ACK
```

If B happens to have no more data when it receives A's FIN, it can send FIN+ACK in one segment (a "simultaneous close" or "piggyback" — the FIN-ACK collapses steps 2 and 3 into one, making it effectively a three-way close in the packet trace).

**Q13. Walk through the four-way termination in detail.**
A:

```
Client (active close)                     Server (passive close)
  |                                         |
  |──── FIN (seq=u, FIN=1) ──────────────→ |   [Client: FIN_WAIT_1]
  |                                         |   [Server: CLOSE_WAIT]
  |←─── ACK (ack=u+1) ─────────────────── |   [Client: FIN_WAIT_2]
  |                                         |
  |   (server may send more data here)      |
  |                                         |
  |←─── FIN (seq=v, FIN=1) ─────────────── |   [Server: LAST_ACK]
  |                                         |
  |──── ACK (ack=v+1) ────────────────── → |   [Server: CLOSED]
  |                                         |
  [Client: TIME_WAIT — 2×MSL]
  [Client: CLOSED after 2×MSL expires]
```

**Step 1 — FIN (active closer → passive closer):**
- The client (active closer) has no more data to send. It sends `FIN=1, seq=u`.
- FIN consumes one sequence number (like SYN).
- Client: `ESTABLISHED → FIN_WAIT_1`.
- The client can still receive data from the server — its receive side is open.

**Step 2 — ACK (passive closer → active closer):**
- Server acknowledges: `ACK=1, ack=u+1`.
- Server: `ESTABLISHED → CLOSE_WAIT`. The server application is notified (receives EOF on the socket); it may still have data to send.
- Client: `FIN_WAIT_1 → FIN_WAIT_2`. Waiting for the server's FIN.

**Step 3 — FIN (passive closer → active closer):**
- When the server has finished sending, it sends `FIN=1, seq=v`.
- Server: `CLOSE_WAIT → LAST_ACK`. Waiting for the final ACK.

**Step 4 — ACK (active closer → passive closer):**
- Client sends `ACK=1, ack=v+1`.
- Server: `LAST_ACK → CLOSED`. Server's connection state is freed.
- Client: `FIN_WAIT_2 → TIME_WAIT`. Client waits for 2×MSL before closing.

**Q14. What is TIME_WAIT, why does it exist, and what problems does it cause in production?**
A: TIME_WAIT is the state the active closer (the side that sent the first FIN) enters after sending the final ACK. It lasts for **2×MSL** (Maximum Segment Lifetime — typically 60 seconds, making TIME_WAIT last up to 4 minutes, though Linux defaults to 60 seconds for the combined wait).

**Why it exists — two reasons:**

1. **Ensure the final ACK was delivered.** The server's LAST_ACK state will timeout and retransmit the FIN if the ACK was lost. The client needs to be in TIME_WAIT to receive and re-ACK this retransmitted FIN. If the client closed immediately after sending the ACK, a lost ACK would leave the server stuck in LAST_ACK forever.

2. **Prevent sequence number confusion from old segments.** An old segment from a previous incarnation of the same 4-tuple (same IP addresses and port numbers) could arrive late and be mistaken for data in a new connection on the same 4-tuple. Waiting 2×MSL (one MSL for the segment to die in the network, one MSL for the response to die) ensures no segment from the old connection can survive to confuse the new one.

**Production problems:**
- High-volume servers (load balancers, proxies, HTTP servers) that make many short connections accumulate tens of thousands of TIME_WAIT sockets. Each occupies kernel memory and a local port number.
- `EADDRNOTAVAIL`: if a client exhausts its ephemeral port range (typically 32768–60999) with TIME_WAIT sockets to the same destination, new connections fail.
- Mitigation: `SO_REUSEADDR` (allows binding to a port in TIME_WAIT for server sockets), `net.ipv4.tcp_tw_reuse` (allows reusing TIME_WAIT sockets for new outbound connections if timestamps confirm safety), increasing ephemeral port range (`net.ipv4.ip_local_port_range`), HTTP keep-alive (avoid creating short connections in the first place), or load balancing to spread connections across IPs.

**Q15. What is a TCP RST, and when is it sent?**
A: A RST (reset) segment abruptly terminates a connection without the graceful four-way close. When a host receives a RST, it immediately discards the connection state — no FINs, no ACKs, no TIME_WAIT. Causes:

- **Connection refused**: a SYN arrives at a port with no listening socket → server sends RST. This is `ECONNREFUSED` on the client.
- **Aborting a connection**: an application calls `close()` with `SO_LINGER` option set to linger time 0 → the kernel sends RST instead of FIN, immediately discarding unread data in the receive buffer.
- **Half-open connection**: one side crashes and restarts; it has no memory of the connection. When the other side sends data, the restarted side has no matching connection state and sends RST.
- **Out-of-window segment**: a segment arrives with a sequence number outside the receive window → RST (indicates a confused or malicious sender).
- **Firewall/middlebox injection**: firewalls can inject RST segments to forcibly terminate connections (used by some national firewalls and intrusion prevention systems). `Wireshark` identifies these as RST segments with a TTL inconsistent with the legitimate endpoint's TTL.

RST does not consume a sequence number and triggers no ACK — it is fire-and-forget.

## Section 5: Flow Control and the Sliding Window

**Q16. What is flow control, and what problem does it solve?**
A: Flow control prevents the sender from overwhelming the receiver's buffer. The receiver has a finite amount of memory allocated to buffer incoming data before the application reads it. If the sender transmits faster than the application reads, the buffer fills up, and new incoming data has nowhere to go — it must be dropped (and then retransmitted, wasting bandwidth and adding latency).

Flow control is a receiver-driven mechanism: the receiver continuously advertises how much buffer space it has available (the **receive window**, or `rwnd`). The sender limits the amount of unacknowledged data in flight to at most `rwnd` bytes. As the application reads data and frees buffer space, the receiver advertises a larger window; as the buffer fills, it advertises a smaller window.

This is distinct from **congestion control**, which limits sending rate based on network capacity (not receiver capacity). Both limits apply simultaneously: the actual sending rate is limited by `min(cwnd, rwnd)`.

**Q17. How does the sliding window work?**
A: The sliding window is the mechanism by which both sides track which bytes have been sent, acknowledged, and can be sent next. The sender maintains a window of bytes it is allowed to have "in flight" (sent but not yet acknowledged):

```
Sender's view of the byte stream:
─────────────────────────────────────────────────────────────────────
| Sent &    | Sent but  | Can send  | Cannot send yet           |
| ACK'd     | not ACK'd | (window)  | (beyond window)           |
─────────────────────────────────────────────────────────────────────
            ↑           ↑           ↑
         SND.UNA     SND.NXT   SND.UNA + min(cwnd, rwnd)

SND.UNA  = oldest unacknowledged byte (left edge of window)
SND.NXT  = next byte to send (right edge of in-flight data)
```

The window "slides" as ACKs arrive:
- A new ACK advances `SND.UNA` to the right (bytes before it are acknowledged).
- If the window size allows, `SND.NXT` advances too (new data is sent).
- The window moves forward like a sliding frame over the byte sequence.

The receiver maintains a symmetric window on the receive side:

```
Receiver's view:
─────────────────────────────────────────────────────────────────────
| Received  | Receive buffer (advertised window)      | Future    |
| & read    | In-order  | Out-of-order buffered        | (rwnd=0?) |
─────────────────────────────────────────────────────────────────────
            ↑
         RCV.NXT (= the ACK number sent back to sender)
```

**Q18. What is the window scale option, and why is it necessary?**
A: The TCP window size field is 16 bits — a maximum of 65,535 bytes (64KB). On a network with high bandwidth-delay product (BDP = bandwidth × RTT), 64KB is far too small. For example:
```
100 Mbps link, RTT = 100ms:
BDP = 100,000,000 bits/sec × 0.1 sec / 8 bits/byte = 1,250,000 bytes = 1.2MB
Maximum window: 64KB
Utilization: 64KB / 1.2MB ≈ 5%
```

Without a larger window, the sender must stop and wait for ACKs 20 times per second on a 100ms RTT link — catastrophic throughput.

The **window scale** option (RFC 1323), negotiated in the handshake's SYN/SYN-ACK options, specifies a shift count (0–14). The actual window is `advertised_window << shift_count`. With a shift count of 7, the maximum window becomes 64KB × 2⁷ = 8MB. With shift count 14: 64KB × 2¹⁴ = 1GB — sufficient for high-speed long-distance links.

Window scale is negotiated once during the handshake (in the SYN options) and applies for the life of the connection. If either side does not include the option in its SYN, window scaling is disabled for the connection.

**Q19. What is the zero-window condition, and how is it resolved?**
A: A zero-window condition occurs when the receiver's buffer is full — it has received data faster than the application can read it. The receiver advertises `rwnd = 0`. The sender must stop transmitting data.

The problem: if the receiver's window opens up (the application reads some data), how does the receiver notify the sender? The sender isn't sending (it thinks the window is zero), so it isn't receiving ACKs, so it wouldn't see a window update in a returning ACK.

Resolution — **persist timer and window probe**:
- When the sender receives a zero window, it starts a **persist timer**.
- When the timer fires, the sender transmits a **window probe** — a segment with one byte of data (or zero bytes, depending on implementation), forcing the receiver to send an ACK with the current window size.
- If the window is still zero, the persist timer doubles (exponential backoff) and fires again.
- When the window opens, the receiver sends an ACK with the updated `rwnd`. The sender resumes transmission.

The window probe prevents the deadlock where both sides are waiting for the other: the sender waiting for a window update ACK, the receiver waiting for the sender to send something worth ACKing.

## Section 6: Congestion Control

**Q20. What is TCP congestion control, and why is it necessary?**
A: Congestion control governs how fast TCP injects data into the network — specifically, how much data the sender allows to be in flight in addition to the receiver's flow control limit. It exists because IP networks are shared: multiple flows compete for the same bottleneck links. Without congestion control, senders would continue injecting data until routers drop packets; the resulting retransmissions would inject even more data, causing congestion collapse — a state where nearly all traffic is retransmissions and useful throughput approaches zero. The 1988 Van Jacobson paper that introduced TCP congestion control rescued the early Internet from exactly this collapse.

The sender maintains a **congestion window** (`cwnd`) — the maximum bytes allowed in flight at the sender's discretion. The actual limit on in-flight data is `min(cwnd, rwnd)`. Congestion control algorithms adjust `cwnd` based on observed network signals: packet loss, ACK timing, and (with ECN) explicit congestion notification.

**Q21. What is Slow Start, and why is it named misleadingly?**
A: Slow Start is the initial phase of TCP congestion control. Despite the name, it is not slow — it grows `cwnd` exponentially:

```
Initial state: cwnd = 1 MSS (Maximum Segment Size, typically 1460 bytes)
               ssthresh = initial value (often 65535 bytes or advertised rwnd)

Each ACK received in Slow Start:
  cwnd += 1 MSS per ACK

Effect per RTT (assuming all segments ACK'd):
  RTT 1: cwnd=1 → send 1 segment → receive 1 ACK → cwnd=2
  RTT 2: cwnd=2 → send 2 segments → receive 2 ACKs → cwnd=4
  RTT 3: cwnd=4 → send 4 segments → receive 4 ACKs → cwnd=8
  ...
  cwnd doubles each RTT → exponential growth
```

Slow Start is "slow" relative to the naive alternative of immediately sending at full line rate — it starts from one MSS rather than the full window. It was named in contrast to the behavior before Van Jacobson's 1988 fix, where connections would immediately blast packets at the receiver's window size.

Slow Start exits when either:
1. `cwnd ≥ ssthresh` (slow start threshold) → transitions to Congestion Avoidance.
2. A loss event is detected → `ssthresh = cwnd / 2`, then `cwnd` is reset (to 1 MSS in TCP Tahoe/Reno; to `ssthresh` in TCP Cubic's specific behavior).

Modern Linux starts with `cwnd = 10 MSS` (RFC 6928) rather than 1, reflecting that most connections are short-lived and benefit from a faster initial ramp.

**Q22. What is Congestion Avoidance and AIMD?**
A: Congestion Avoidance is the steady-state phase of TCP, entered when `cwnd ≥ ssthresh`. Growth slows from exponential to linear:

```
Each ACK received in Congestion Avoidance:
  cwnd += MSS × (MSS / cwnd)    ≈ 1 MSS per RTT (additive increase)

Effect per RTT:
  cwnd grows by 1 MSS per RTT regardless of current cwnd size
```

When loss is detected (triple duplicate ACKs):
```
ssthresh = cwnd / 2             (multiplicative decrease)
cwnd     = ssthresh             (TCP Reno: cut to half)
           or 1 MSS             (TCP Tahoe: restart slow start)
```

This is **AIMD** — Additive Increase, Multiplicative Decrease. The name captures the asymmetry:
- **Additive increase** (when no loss): grows linearly — cautiously probing for more bandwidth.
- **Multiplicative decrease** (on loss): cuts by a factor of 2 — aggressively backing off.

AIMD produces a sawtooth pattern of `cwnd` over time: gradual ramp-up, sharp drop on loss, gradual ramp-up again. The asymmetry is intentional: conservative growth avoids congestion; sharp decrease quickly relieves a congested network. AIMD is proven to converge to a fair allocation of bandwidth among competing flows sharing a bottleneck.

```
cwnd
 ^
 |    /|    /|    /|
 |   / |   / |   / |
 |  /  |  /  |  /  |
 | /   | /   | /   |
 |/    |/    |/    |
 +────────────────→ time
      ↑     ↑     ↑
     loss  loss  loss
   (3 dup ACKs or timeout)
```

**Q23. What is the difference between a timeout-based loss detection and triple duplicate ACK loss detection, and why does it matter for `cwnd`?**
A: Two loss detection mechanisms with very different severity signals:

**Triple duplicate ACKs** (fast retransmit trigger):
- Three duplicate ACKs mean segments after the gap are arriving — the network is still delivering packets. Loss was isolated (likely a single dropped packet at a router that was momentarily full).
- Severity: moderate. Response (TCP Reno): `ssthresh = cwnd/2`, `cwnd = ssthresh` (halve). Fast Recovery phase: continue sending (window is still `ssthresh`), retransmit the lost segment, inflate `cwnd` temporarily to account for ACKs arriving during recovery.

**Retransmission timeout (RTO)**:
- No ACKs arriving at all for a full timeout period — severe congestion or path failure. The network may be heavily congested or a router buffer may be full and dropping all packets.
- Severity: severe. Response: `ssthresh = cwnd/2`, `cwnd = 1 MSS` — restart Slow Start from scratch.

```
Triple dup ACK: cwnd cut to ssthresh (e.g., 20 MSS → 10 MSS)
Timeout:        cwnd cut to 1 MSS   (e.g., 20 MSS → 1 MSS)
```

The harsher response to timeout reflects the signal strength: if no ACKs are arriving at all, the network is seriously congested and the sender must back off drastically. Three duplicate ACKs, while indicating loss, show the network is still functioning.

**Q24. What is TCP CUBIC, and how does it differ from AIMD (Reno)?**
A: TCP CUBIC (RFC 8312) is the default congestion control algorithm in Linux since kernel 2.6.19 and is used by most modern servers and clients. It was designed for high-bandwidth, high-latency networks (long fat networks) where AIMD's linear increase is too slow to recover from a loss event.

**The core idea**: instead of growing `cwnd` linearly (1 MSS per RTT), CUBIC grows `cwnd` according to a cubic function of time elapsed since the last congestion event:

```
W(t) = C × (t − K)³ + Wmax

where:
  t    = time elapsed since last window reduction
  Wmax = cwnd at the point of last reduction (the saturation point)
  K    = time it takes to grow back to Wmax (set so W(K) = Wmax)
  C    = scaling constant (default 0.4)
```

The cubic curve has three phases:
1. **Fast recovery**: immediately after a loss, `cwnd` was cut to `Wmax × 0.7` (CUBIC keeps 70% on triple dup ACK, not 50% like Reno). It grows quickly back toward Wmax because the cubic function rises steeply far from Wmax.
2. **Plateau near Wmax**: as `cwnd` approaches Wmax (where congestion was previously detected), growth slows — CUBIC is probing cautiously around the saturation point.
3. **Exploration above Wmax**: after exceeding Wmax (network capacity may have increased since last loss), the cubic function accelerates again, probing for additional bandwidth.

**Key differences from Reno:**
- CUBIC's growth is independent of RTT — it depends on wall-clock time, not ACK count. This gives long-RTT flows (intercontinental) the same aggressiveness as short-RTT flows. Reno grows 1 MSS per RTT, so a 200ms RTT flow grows 10× slower than a 20ms RTT flow competing for the same bottleneck — unfair. CUBIC equalizes this.
- CUBIC retains 70% of `cwnd` on triple dup ACK vs. Reno's 50% — faster recovery.
- CUBIC performs similarly to Reno on small, low-latency networks; significantly better on high-bandwidth, high-latency links.

**Q25. What is Explicit Congestion Notification (ECN), and how does it improve on loss-based congestion signals?**
A: ECN (RFC 3168) allows routers to signal congestion to endpoints before dropping packets — a proactive signal rather than a reactive one.

Standard congestion control learns about congestion only after a packet is dropped — but by the time a packet is dropped, the router's queue is already full, adding latency to every in-flight packet and causing the sudden performance cliff of loss-based recovery. ECN provides an early warning:

```
ECN negotiation (SYN/SYN-ACK):
  Client SYN:     sets ECE + CWR flags (I support ECN)
  Server SYN-ACK: sets ECE flag (I support ECN too)

During data transfer:
  Sender marks packets with ECT (ECN-Capable Transport) in IP header
  Congested router: instead of dropping, sets CE (Congestion Experienced) in IP header
  Receiver: sees CE → sets ECE flag in next ACK (ECN-Echo)
  Sender: sees ECE → reduces cwnd as if a loss occurred (sets CWR in next segment)
```

Benefits: congestion is signaled before any packet is dropped, reducing latency spikes and retransmission overhead. The queue doesn't have to overflow to signal congestion — the router acts when it detects growing queue depth.

Requires support from: the sender (kernel TCP stack), the receiver (kernel TCP stack), and the network path (every router must support ECN marking). Enabled in Linux with `net.ipv4.tcp_ecn = 1`. Used extensively in data center networks (DCTCP — Data Center TCP uses ECN with a modified response to maintain very low queue occupancy).

**Q26. What is BBR (Bottleneck Bandwidth and Round-trip propagation time), and how does it fundamentally differ from loss-based congestion control?**
A: BBR (Google, 2016) is a model-based congestion control algorithm that represents a philosophical departure from loss-based algorithms (Reno, CUBIC). Instead of using packet loss as the congestion signal, BBR directly measures the bottleneck bandwidth and minimum RTT, then sets the sending rate to match the bottleneck without filling the buffers.

**The fundamental insight**: loss-based algorithms fill router buffers until they overflow (dropping packets). This causes **bufferbloat** — the buffers add unnecessary latency (sometimes hundreds of milliseconds) even when the network isn't fully congested. BBR tries to operate at the point where the pipe is full but the buffers are empty:

```
Ideal operating point (BBR target):
  Rate  = bottleneck bandwidth (BtlBw)   — pipe is fully utilized
  Queue = nearly empty                   — no unnecessary buffering latency
  RTT   = base propagation delay (RTprop) — no added queuing delay
```

BBR alternates between two probing phases:
- **BtlBw probe**: periodically sends at 1.25× the estimated bandwidth for one RTT to detect if more bandwidth is available (did the sending rate increase? → bandwidth grew).
- **RTprop probe**: periodically reduces sending rate to drain buffers and re-measure the minimum RTT (which reflects the true propagation delay without queuing).

BBR significantly outperforms CUBIC on:
- **High-loss paths** (cellular, satellite): CUBIC interprets loss as congestion and backs off; BBR ignores moderate loss and maintains throughput.
- **Bufferbloated paths**: CUBIC fills buffers, adding latency; BBR proactively avoids filling them.
- **Long-RTT paths**: BBR's model is RTT-independent; CUBIC's additive increase is RTT-dependent.

BBR is the default in Google's production infrastructure, Android, and is available in Linux kernel 5.x (`net.ipv4.tcp_congestion_control = bbr`). It has been criticized for being less fair to competing CUBIC flows in some scenarios.

## Section 7: Putting It Together

**Q27. What is the bandwidth-delay product (BDP), and why does it matter for TCP performance?**
A: The bandwidth-delay product is the amount of data "in flight" in the network at full utilization:

```
BDP = bottleneck_bandwidth × RTT

Examples:
  Home broadband (100 Mbps, RTT=20ms):  BDP = 250,000 bytes = 244 KB
  Cross-country (1 Gbps, RTT=80ms):     BDP = 10,000,000 bytes = 9.5 MB
  Satellite (50 Mbps, RTT=600ms):       BDP = 3,750,000 bytes = 3.6 MB
```

The BDP is the minimum window size needed to keep the pipe full. If `min(cwnd, rwnd) < BDP`, the sender runs out of window and must stop, leaving the link idle until ACKs return. The fraction of time the link is utilized:

```
Throughput = min(cwnd, rwnd) / RTT
Link utilization = Throughput / Bandwidth = min(cwnd, rwnd) / BDP
```

For a satellite link with BDP = 3.6 MB and a maximum window of 64KB (no window scaling): utilization = 64KB / 3.6MB ≈ 1.8%. The connection achieves less than 2% of the available bandwidth — entirely due to TCP's window size limit. Window scaling and large initial congestion windows are essential for high-BDP paths.

**Q28. What happens to TCP throughput when a connection experiences packet loss, and how does the "square root formula" quantify it?**
A: The Mathis formula (1997) gives the steady-state throughput of a TCP Reno connection under random loss:

```
Throughput ≈ (MSS / RTT) × (1 / √p)

where:
  MSS = maximum segment size (bytes)
  RTT = round-trip time (seconds)
  p   = packet loss rate (fraction, e.g., 0.001 = 0.1%)
```

The inverse square root relationship means loss has a catastrophic effect on throughput:

```
MSS=1460 bytes, RTT=50ms, varying loss rate:
  p=0.0001 (0.01%): Throughput ≈ 1460/0.05 × 1/0.01 = 292 Mbps
  p=0.001  (0.1%):  Throughput ≈ 1460/0.05 × 1/0.0316 = 92 Mbps
  p=0.01   (1%):    Throughput ≈ 1460/0.05 × 1/0.1    = 29 Mbps
  p=0.1    (10%):   Throughput ≈ 1460/0.05 × 1/0.316  = 9 Mbps
```

A 100× increase in loss rate (0.01% → 1%) reduces throughput by ~10× (√100). This is why TCP performs poorly on lossy wireless links — the congestion control algorithm interprets packet loss as congestion and backs off, even if the loss is due to radio interference, not network congestion. BBR's approach of ignoring moderate loss directly addresses this.

**Q29. What is Nagle's algorithm, and when should it be disabled?**
A: Nagle's algorithm (RFC 896, 1984) reduces the problem of "small packet disease" — many tiny segments (e.g., 1-byte Telnet keystrokes) consuming disproportionate network overhead (40-byte TCP+IP header per 1-byte payload = 97.6% overhead).

The rule: a TCP sender may not send a new small segment if there is unacknowledged data in flight, unless the new data fills a full MSS. A small segment waits until either an ACK arrives (then it can be sent) or enough data accumulates to fill an MSS.

```
Nagle's rule (simplified):
  if (new_data_size >= MSS || no_unacked_data):
    send immediately
  else:
    buffer and wait for ACK or enough data to fill MSS
```

**When to disable (TCP_NODELAY):**
- **Interactive protocols with request-response patterns**: HTTP/1.1, database clients, RPC. Nagle causes latency: the client sends a small request, Nagle buffers it waiting for an ACK (which won't come until the server receives the request and responds). The client's request sits in the send buffer for up to one RTT. `TCP_NODELAY` fixes this by sending immediately regardless of unacknowledged data.
- **Real-time applications**: game servers, financial market data feeds — any situation where sending one message immediately is more important than batching for efficiency.
- **Interactive SSH/Telnet**: each keystroke should be sent immediately.

**When to keep Nagle enabled (default):**
- Bulk data transfer (file copying, streaming) — Nagle has no effect because data always fills full segments.
- High-volume small-message producers where batching reduces syscall and packet overhead.

Note: Nagle interacts badly with delayed ACKs (the receiver delays ACKing for up to 200ms to allow ACK piggybacking). Both sender (Nagle) and receiver (delayed ACK) wait for the other — a 200ms deadlock on every small message. The fix: `TCP_NODELAY` on the sender, or `TCP_QUICKACK` on the receiver.

## Section 8: Scenario / System Design Style Questions

**Q30. "You're debugging a service that makes many short-lived HTTP connections to a downstream API. Latency is high and `ss -s` shows thousands of TIME_WAIT sockets. How do you fix it?"**
A: TIME_WAIT accumulation on outbound connections is a classic high-volume client problem. Attack at multiple levels:

1. **HTTP keep-alive (connection reuse)** — the root fix. Instead of creating a new TCP connection per request, reuse the connection for multiple requests. HTTP/1.1 keep-alive is default; ensure the client isn't sending `Connection: close`. Connection pooling (a fixed pool of persistent TCP connections) eliminates most TIME_WAIT accumulation.

2. **`net.ipv4.tcp_tw_reuse = 1`** — allow the kernel to reuse TIME_WAIT sockets for new outbound connections, provided TCP timestamps confirm the old connection's segments are dead. Safe for client-side TIME_WAIT. (Note: `tcp_tw_recycle` was removed in Linux 4.12 — it was unsafe with NAT and is no longer available.)

3. **Expand the ephemeral port range** — `net.ipv4.ip_local_port_range = 1024 65535` (default is 32768–60999). More ports means more simultaneous TIME_WAIT sockets before exhaustion.

4. **Reduce TIME_WAIT duration** — `net.ipv4.tcp_fin_timeout` controls the FIN_WAIT_2 timeout (not the full TIME_WAIT); the actual TIME_WAIT is hardcoded to 2×MSL (60 seconds in Linux). Reducing `tcp_fin_timeout` helps with stuck FIN_WAIT_2 sockets but doesn't directly reduce TIME_WAIT.

5. **Use HTTP/2 or HTTP/3** — HTTP/2 multiplexes all requests over a single TCP connection (or few connections). TIME_WAIT is nearly eliminated because connections are long-lived.

6. **Load balance across source IPs** — if the client has multiple IP addresses (or can use IP aliasing), connections from different source IPs to the same destination create distinct 4-tuples, increasing the effective port space.

**Q31. "Explain what happens in the TCP stack when a 10MB file is transferred over a connection with 50ms RTT, 10 Mbps bandwidth, and an initial cwnd of 10 MSS."**
A: Trace the transfer through the congestion control phases:

```
Given: RTT=50ms, bandwidth=10Mbps, cwnd_init=10 MSS, MSS=1460 bytes
BDP = 10,000,000 bps × 0.05s / 8 = 62,500 bytes ≈ 43 MSS
ssthresh (initial, assumed large): e.g., 64 KB ≈ 45 MSS

Phase 1 — Slow Start (cwnd doubles each RTT until cwnd >= ssthresh or loss):
  RTT 1: cwnd=10 MSS → send 10 segments (14,600 bytes) → receive 10 ACKs → cwnd=20 MSS
  RTT 2: cwnd=20 MSS → send 20 segments (29,200 bytes) → receive 20 ACKs → cwnd=40 MSS
  RTT 3: cwnd=40 MSS → cwnd ≥ ssthresh (45 MSS approaching) → transition to Congestion Avoidance

  Total sent after 3 RTTs: ~10+20+40 = 70 × 1460 bytes ≈ 102 KB
  Time elapsed: 3 × 50ms = 150ms

Phase 2 — Congestion Avoidance (cwnd grows 1 MSS per RTT):
  Remaining data: 10MB − 102KB ≈ 9.9MB ≈ 6,780 MSS
  cwnd at entry: ~43 MSS
  
  Bandwidth at cwnd=43 MSS: 43 × 1460 bytes / 0.05s ≈ 1.26 MB/s
  Link capacity: 10Mbps / 8 = 1.25 MB/s
  → cwnd is approximately at the BDP — link is saturated

  If no loss occurs:
  cwnd grows slowly (1 MSS/RTT); remains near BDP
  Throughput ≈ 1.25 MB/s
  Transfer time for remaining 9.9MB ≈ 9.9/1.25 ≈ 7.9 seconds

Total transfer time: ~150ms (slow start) + ~7.9s (congestion avoidance) ≈ 8.05 seconds
Theoretical minimum (if cwnd were never limiting): 10MB / 1.25MB/s = 8 seconds

Note: the slow start phase adds ~150ms overhead — negligible for a large transfer.
For a small file (e.g., 50KB), slow start dominates: the file fits in 3–4 RTTs of slow start,
so ~150–200ms total — much longer than the 40ms the data would take to send at full speed.
This is why small object HTTP latency is dominated by TCP setup and slow start,
not actual transmission time.
```

**Q32. "A senior engineer says 'just increase the TCP buffer sizes and all your throughput problems will go away.' What's right and wrong about this?"**
A: Partially correct, often misapplied. The full picture:

**What's right:** if the bottleneck is the TCP window size being smaller than the bandwidth-delay product, increasing buffer sizes (and thus the advertised receive window) does directly increase throughput. The kernel's socket buffer sizes (`net.core.rmem_max`, `net.core.wmem_max`, `net.ipv4.tcp_rmem`, `net.ipv4.tcp_wmem`) determine the maximum `rwnd`. If `rwnd < BDP`, the sender is window-limited regardless of available bandwidth. Increasing buffers fixes this specific case.

**What's wrong or incomplete:**

- **Congestion window is the other limit.** `throughput = min(cwnd, rwnd) / RTT`. If `cwnd < rwnd`, increasing `rwnd` does nothing — `cwnd` is the binding constraint. `cwnd` is controlled by the congestion control algorithm (Slow Start, AIMD), not by buffer size settings. A lossy path keeps `cwnd` small regardless of buffer size.
- **Large buffers enable bufferbloat.** Huge receive buffers don't make the network faster — they add queuing latency. A full buffer means every packet in the buffer must be transmitted before new packets can arrive, adding RTT proportional to buffer depth. Larger buffers make TCP *think* the network is less congested (packets aren't dropped) while actually adding hundreds of milliseconds of latency.
- **Memory cost.** TCP socket buffers are allocated per connection. A server with 10,000 connections and 4MB buffers per socket needs 40GB of RAM just for TCP buffers. The kernel's auto-tuning (`tcp_rmem = min default max`) starts buffers small and grows them dynamically — usually better than a single large static size.
- **Root cause.** Throughput problems are usually caused by: RTT (reduce hops, use CDN), packet loss (fix the lossy link, switch to BBR), CPU bottleneck (sendfile, zero-copy), or application design (blocking I/O, too many small writes). Buffer sizes rarely fix any of these.

The correct answer: use the kernel's auto-tuning TCP buffers (default in modern Linux), set `net.core.rmem_max` and `net.core.wmem_max` to allow large windows on high-BDP paths, profile where the actual bottleneck is before tuning.

## Quick Reference

```
Three-way handshake:
  Client → Server: SYN (seq=x)
  Server → Client: SYN-ACK (seq=y, ack=x+1)
  Client → Server: ACK (ack=y+1)
  SYN and FIN each consume one sequence number

Four-way termination:
  Active closer → Passive: FIN (seq=u)  [Active: FIN_WAIT_1]
  Passive → Active:        ACK (ack=u+1) [Active: FIN_WAIT_2, Passive: CLOSE_WAIT]
  Passive → Active:        FIN (seq=v)   [Passive: LAST_ACK]
  Active → Passive:        ACK (ack=v+1) [Active: TIME_WAIT → CLOSED after 2×MSL]

Sequence numbers: count bytes, not segments; 32-bit, wraps around
ACK number:       next expected byte (cumulative); SACK extends with out-of-order ranges

Flow control:  rwnd (receiver window) — receiver's available buffer space
Congestion:    cwnd (congestion window) — sender's network-capacity estimate
Actual limit:  min(cwnd, rwnd)

Slow Start:
  cwnd starts at ~10 MSS (Linux default)
  cwnd += 1 MSS per ACK → doubles per RTT (exponential)
  Exits when cwnd >= ssthresh or loss occurs

Congestion Avoidance (AIMD):
  cwnd += MSS²/cwnd per ACK → +1 MSS per RTT (linear)
  Triple dup ACK: ssthresh = cwnd/2, cwnd = ssthresh (TCP Reno)
  Timeout:        ssthresh = cwnd/2, cwnd = 1 MSS (restart Slow Start)

CUBIC:  W(t) = C(t−K)³ + Wmax  — time-based, RTT-fair, retains 70% on loss
BBR:    model-based (BtlBw × RTprop), avoids filling buffers, ignores moderate loss

BDP = bandwidth × RTT  — minimum window to saturate the link
Mathis: Throughput ≈ MSS / (RTT × √p)  — throughput degrades as √(1/loss_rate)

Key socket options:
  TCP_NODELAY     — disable Nagle's algorithm (send small segments immediately)
  SO_REUSEADDR    — allow binding to TIME_WAIT port (server restart)
  SO_KEEPALIVE    — send keepalive probes to detect dead connections
  TCP_KEEPIDLE    — seconds before first keepalive probe
  TCP_KEEPINTVL   — interval between probes
  TCP_KEEPCNT     — number of probes before giving up
```

## Common Mistakes at a Glance

| Mistake                                                    | Clarification                                                                         |
|---                                                         |---                                                                                    |
| Confusing flow control with congestion control             | Flow control: receiver's buffer limit (rwnd). Congestion: network capacity (cwnd). Both limit sending. |
| Thinking SYN/FIN don't consume sequence numbers            | They do — each consumes 1 byte of sequence space (no data payload, but ISN+1 is the next seq) |
| Assuming TIME_WAIT is a bug or error state                 | It is correct and intentional — protects against delayed segment confusion and lost final ACK |
| Thinking `tcp_tw_recycle` is still available               | Removed in Linux 4.12 — it was unsafe with NAT; use `tcp_tw_reuse` instead            |
| Confusing `mtime` and `ctime` (file systems) with timestamps here | TCP timestamps (TSOPT) are for RTT measurement and PAWS, not file metadata    |
| Assuming `write()` returning means data was sent           | `write()` on a TCP socket copies to the kernel send buffer; TCP sends when cwnd/rwnd allow |
| Thinking larger buffers always improve throughput          | Buffers only help if window-limited; they can add latency (bufferbloat) if overprovisioned |
| Confusing Fast Retransmit threshold (3 dup ACKs) with 3 ACKs | It is 3 *duplicate* ACKs — the 4th ACK for the same value triggers retransmit          |
| Assuming CUBIC and Reno behave identically                 | CUBIC is RTT-fair and retains 70% on loss; Reno is RTT-biased and cuts to 50%          |
| Thinking ECN eliminates packet loss                        | ECN signals congestion early to *prevent* drops; it requires support from all routers in the path |
