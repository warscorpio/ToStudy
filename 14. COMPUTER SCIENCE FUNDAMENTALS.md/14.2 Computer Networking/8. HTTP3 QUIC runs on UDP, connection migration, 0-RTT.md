# Networking: HTTP/3 / QUIC — UDP Transport, Connection Migration, 0-RTT — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is QUIC, and what is its relationship to HTTP/3?**
A: QUIC is a general-purpose transport protocol developed by Google (originally as a UDP-based experiment in Chrome) and standardised by the IETF in RFC 9000 (2021). It runs on top of UDP and reimplements — in userspace — the features that TCP provides in the kernel: reliable delivery, ordered streams, flow control, and congestion control. Additionally, QUIC integrates TLS 1.3 cryptography directly into the transport layer rather than layering it on top.

HTTP/3 (RFC 9114, 2022) is the third major version of the HTTP protocol, and it is defined entirely in terms of QUIC. HTTP/3 is to QUIC what HTTP/2 is to TCP+TLS — it uses QUIC's multiplexed streams as the transport for HTTP request-response pairs. The relationship is strict: you cannot run HTTP/3 over TCP, and you cannot run HTTP/1.1 or HTTP/2 over QUIC. QUIC is the transport; HTTP/3 is the application protocol built on it.

The version numbering reflects this:
- HTTP/1.1 → TCP + optional TLS
- HTTP/2 → TCP + TLS (required)
- HTTP/3 → QUIC (which bundles UDP + TLS 1.3 + reliable delivery)

**Q2. What problems with TCP+TLS motivated the design of QUIC?**
A: Four specific TCP and TLS problems motivated QUIC's design, each with a measurable performance cost:

**Problem 1 — Head-of-line (HOL) blocking at the transport layer:**
HTTP/2 introduced request multiplexing over a single TCP connection — multiple HTTP requests in flight simultaneously. But TCP treats the connection as a single ordered byte stream. If a single packet is lost, TCP stalls the delivery of all subsequent packets in all streams until the lost packet is retransmitted and received. A single packet loss affects every concurrent HTTP/2 request, even those whose data arrived intact but is being held behind the lost packet. QUIC implements independent streams — a packet loss only stalls the one stream that depended on that packet.

**Problem 2 — Connection establishment latency (TCP + TLS handshake):**
A fresh TCP connection requires 1 round-trip (RTT) for the TCP handshake (SYN/SYN-ACK/ACK) before any data can be sent. TLS 1.2 then adds 2 more RTTs for the TLS handshake (total: 3 RTTs before the first HTTP byte). TLS 1.3 reduces this to 1 RTT for TLS (total: 2 RTTs). QUIC combines the transport and cryptographic handshakes — a new QUIC connection to a previously unvisited server requires only 1 RTT. For a previously visited server with cached session tickets, QUIC supports 0-RTT — the first packet can carry application data.

**Problem 3 — TCP connection migration is impossible:**
A TCP connection is identified by a 4-tuple (source IP, source port, destination IP, destination port). When a mobile client switches from WiFi to cellular, its IP address changes — the 4-tuple changes — and the TCP connection is broken. All in-flight requests fail; the application must reconnect. QUIC introduces connection IDs that are independent of the 4-tuple, allowing connections to survive network changes.

**Problem 4 — Ossification of the protocol stack:**
TCP is implemented in operating system kernels, which are slow to update. Middleboxes (firewalls, NATs, load balancers) examine and sometimes modify TCP headers based on assumptions about TCP behaviour. Attempting to extend or modify TCP — even with valid RFC updates — often fails because middleboxes drop packets with unknown options. QUIC runs in userspace, is encrypted (no middlebox inspection of headers), and can be updated and deployed rapidly without kernel changes.

**Q3. Why does QUIC run on UDP rather than implementing a new Layer 4 protocol?**
A: A new transport protocol at Layer 4 (alongside TCP and UDP in the IP stack) would require kernel modifications to every OS, router firmware updates, and middlebox support — a deployment timeline of decades, given how slowly network infrastructure changes. Running on UDP avoids all of these barriers:

- **OS support is universal:** Every OS already has a UDP socket API. A QUIC library runs as user-space code on top of UDP sockets.
- **Middlebox passthrough:** Firewalls and NATs already know how to forward UDP. They do not inspect UDP payloads (which are encrypted in QUIC) — they simply forward the packets based on the 5-tuple (IP, protocol, ports).
- **Rapid deployment:** QUIC is a library in application code (or a reverse proxy). New QUIC versions can be deployed by updating a library, not by patching a kernel. Google deployed QUIC in Chrome and their servers before the IETF standardised it, iterating on the protocol faster than any kernel-level protocol could evolve.

UDP itself provides nothing beyond packet delivery (no reliability, no ordering, no flow control, no congestion control). QUIC implements all of those in user-space on top of UDP's minimal framing. The trade-off: QUIC must re-implement everything TCP does correctly, which is non-trivial. The benefit: full control over the protocol's evolution and behaviour.

**Q4. What does QUIC's encryption cover, and how is it different from TLS-over-TCP?**
A: In TCP+TLS, only the application payload is encrypted. TCP headers (sequence numbers, ACK numbers, flags, window size) are sent in plaintext — visible and modifiable by middleboxes. This is how middleboxes "help" with TCP by intercepting retransmissions, modifying window sizes, or injecting RSTs.

In QUIC, the vast majority of the protocol header — stream IDs, packet numbers, connection IDs (in some configurations), flow control windows, ACK ranges — is encrypted with TLS 1.3. A middlebox can see the UDP src/dst ports and IP addresses, and the QUIC short header's first byte (which includes packet type flags), but nothing else. The payload and most of the header are opaque.

This encryption-first design achieves two goals: privacy (no passive observation of connection metadata) and ossification resistance (middleboxes cannot modify what they cannot see). The cost: debugging and monitoring QUIC connections is harder — tools like `tcpdump` show only encrypted bytes, and analysing a QUIC connection requires the session keys (available via the SSLKEYLOGFILE mechanism, as with TLS).

## Section 2: QUIC Streams and HOL Blocking

**Q5. How does QUIC implement streams, and how do they eliminate transport-layer HOL blocking?**
A: A QUIC connection carries multiple concurrent **streams** — independent, bidirectional or unidirectional byte sequences, each identified by a stream ID. Each HTTP/3 request-response pair occupies one QUIC stream. Streams are multiplexed within a single QUIC connection but are logically independent at the transport layer.

QUIC uses packet numbers (not byte sequence numbers like TCP) to identify and acknowledge packets. Each QUIC packet carries data from one or more streams, tagged by stream ID and offset within that stream. When a packet is lost:

```
QUIC connection with 3 concurrent streams:
Packet 1: Stream A data (bytes 0-1199)
Packet 2: Stream B data (bytes 0-1199)    ← LOST
Packet 3: Stream C data (bytes 0-1199)
Packet 4: Stream A data (bytes 1200-2399)

Stream B is stalled — waiting for retransmission of packet 2.
Stream A and Stream C continue unaffected — their data is delivered and processed.
```

In HTTP/2 over TCP, the same scenario would stall ALL streams — TCP holds packets 3 and 4 in its receive buffer, waiting for packet 2 before delivering any of them to the application. QUIC's receiver delivers packet 1, 3, and 4 to the application immediately while waiting for packet 2's retransmission — only Stream B's application is stalled.

The implementation detail: QUIC's ACK mechanism acknowledges ranges of packet numbers, not a single cumulative ACK. The receiver sends ACK frames listing which packet numbers it received. The sender identifies which streams were in the lost packet and retransmits only those stream bytes, in a new packet with a new packet number. The other streams' data, already received, is not retransmitted.

**Q6. What is the difference between QUIC streams and HTTP/2 streams, and why does HTTP/3 need fewer workarounds?**
A: HTTP/2 streams are an application-layer concept — the HTTP/2 framing layer multiplexes requests over a single TCP byte stream. HOL blocking exists at the TCP layer, below the HTTP/2 stream abstraction — the HTTP/2 implementation cannot fix it. HTTP/2 introduced HPACK header compression with a shared dynamic table — a dependency between streams at the application layer, creating application-level HOL blocking on top of TCP's transport-level HOL blocking.

HTTP/3 streams are QUIC streams — the transport layer provides native stream multiplexing. HTTP/3 uses QPACK for header compression instead of HPACK, specifically designed to avoid application-level HOL blocking:

- **HPACK (HTTP/2):** Header compression uses a shared dynamic table updated by both endpoints. A reference to a not-yet-processed dynamic table entry blocks the current stream.
- **QPACK (HTTP/3):** Uses two unidirectional control streams (encoder and decoder) separate from the request streams. Required insertions into the dynamic table are sent on the control stream. Request streams can use only entries already confirmed as inserted — if an entry isn't yet available, the request is sent without compression for that header. No stream blocks another.

HTTP/3 also removes the need for HTTP/2's server push workarounds, priority dependency trees (replaced with extensible priorities), and the complex SETTINGS frame negotiation — because QUIC's transport layer handles these more cleanly.

## Section 3: Connection Establishment and Handshake

**Q7. Walk through the QUIC handshake for a new connection — what happens in the 1-RTT case?**
A: The QUIC handshake combines the transport connection establishment and the TLS 1.3 cryptographic handshake into a single exchange. TLS 1.3 is not layered on top of QUIC — it is embedded inside QUIC's handshake packets:

```
Client                                          Server
  │                                                │
  │── Initial packet (Client Hello) ─────────────►│  t=0
  │   Contains: QUIC transport parameters          │
  │             TLS ClientHello                    │
  │             Random nonce, supported ciphers    │
  │                                                │
  │◄─ Initial packet (Server Hello) ──────────────│  t=0 + server processing
  │   Contains: TLS ServerHello                   │
  │             Encrypted: Certificate,            │
  │             CertificateVerify, Finished       │
  │◄─ Handshake packet (encrypted) ───────────────│
  │◄─ 1-RTT packet (application data) ────────────│  server can send data now
  │                                                │
  │── Handshake packet (Finished) ────────────────►│  t=1 RTT
  │── 1-RTT packet (HTTP/3 request) ─────────────►│
  │                                                │
  │◄─ 1-RTT packet (HTTP/3 response) ─────────────│
```

Key points: the server can begin sending application data (HTTP/3 response to a server-initiated push, or SETTINGS frames) immediately after its first reply — before the client has confirmed receipt of the Finished message. The client sends its first HTTP/3 request after 1 RTT — the same RTT in which the handshake completes. The total latency before the first HTTP/3 request byte arrives at the server is 1 RTT (vs. 2 RTTs for TLS 1.3 over TCP, which requires TCP handshake first, then TLS handshake).

QUIC transport parameters — stream limits, maximum UDP payload size, connection ID preferences, idle timeout — are exchanged inside the handshake packets, authenticated by TLS. A middlebox that tampers with transport parameters would break the TLS authentication, causing the handshake to fail. This prevents the parameter modification attacks that affected TCP options.

**Q8. What is 0-RTT resumption, how does it work in QUIC, and what are its security limitations?**
A: 0-RTT (zero round-trip time) resumption allows a client to send application data in the very first packet to a previously visited server — before any handshake round-trip completes. The mechanism:

**How it works:**
When a client successfully completes a 1-RTT QUIC connection, the server sends a **session ticket** encrypted with a pre-shared key (PSK). The ticket encodes:
- The cryptographic session state (cipher suite, keys derived from the previous handshake).
- Server-specified configuration (transport parameters, max data, stream limits).
- A ticket lifetime (how long the ticket is valid — typically 24 hours).

On a subsequent connection attempt, the client includes the session ticket in its first packet (the Initial packet) and immediately sends 0-RTT data encrypted with the "early traffic secret" derived from the PSK:

```
Client (has session ticket from previous visit)          Server
  │                                                          │
  │── Initial packet (Client Hello + session ticket) ──────►│  t=0
  │── 0-RTT packet (HTTP/3 request, encrypted) ────────────►│
  │                                                          │
  │◄─ Initial packet (Server Hello) ───────────────────────│  t=1 RTT (handshake completes)
  │◄─ 1-RTT packet (HTTP/3 response) ──────────────────────│  response to 0-RTT request
  │                                                          │
  │── Handshake Finished ───────────────────────────────────►│
```

The 0-RTT data arrives at the server before the handshake is complete — the server processes the 0-RTT HTTP/3 request immediately, begins preparing the response, and sends it back alongside the handshake completion.

**Security limitations — replay attacks:**
0-RTT data is vulnerable to **replay attacks**. A network adversary who captures the Initial packet + 0-RTT data packet can replay them to the server later. The server cannot distinguish the replay from a legitimate duplicate request (the session ticket and early keys are the same). If the 0-RTT request is `GET /price` (idempotent), the replay merely returns a duplicate price — harmless. If the 0-RTT request is `POST /transfer` (non-idempotent, with side effects), the replay executes the transfer twice.

QUIC and TLS 1.3 provide mechanisms to limit (but not eliminate) replay risk:
- **Single-use tickets:** The server tracks used tickets and rejects replays (requires distributed state in multi-server deployments — often impractical).
- **Time-based validity:** Tickets expire after a short window (hours to days); replays after expiry fail.
- **Anti-replay tokens:** The server issues single-use tokens in the session ticket; the client includes the token in 0-RTT data; the server rejects duplicate tokens (again requires distributed state).

The practical rule for production systems: **restrict 0-RTT to idempotent, safe HTTP methods only** — `GET`, `HEAD`, `OPTIONS`. Never send `POST`, `PUT`, `DELETE`, or `PATCH` as 0-RTT data. HTTP/3 clients and servers that implement 0-RTT must enforce this at the application layer. Server-side, configure your QUIC implementation to reject non-idempotent 0-RTT requests or to process all 0-RTT requests idempotently.

## Section 4: Connection Migration

**Q9. What is connection migration, and why is it impossible in TCP?**
A: Connection migration is the ability to continue an established connection after the client's network address (IP and/or port) changes — typically because the device switched networks (WiFi to cellular, cellular handover between towers, VPN connect/disconnect). In TCP, this is impossible:

A TCP connection is bound to its 4-tuple: (client IP, client port, server IP, server port). The server uses this 4-tuple to demultiplex incoming packets to the correct socket. If the client's IP changes (new network), the next packet the client sends has a different source IP — the server's kernel finds no matching TCP socket for the new 4-tuple and sends a RST. The connection is dead. The application must detect the failure (usually via a timeout or a broken pipe error) and re-establish from scratch — re-doing the TCP handshake, TLS handshake, and any application-level authentication.

On a mobile device making a video call, a file download, or a payment API call, a network transition causes:
- TCP: connection drops, request fails, user sees an error or must retry.
- QUIC with connection migration: the connection continues transparently — the download resumes from where it was, the API call completes.

**Q10. How does QUIC implement connection migration using connection IDs?**
A: QUIC introduces **Connection IDs (CIDs)** — opaque, randomly generated byte sequences (8–20 bytes typical) that identify a QUIC connection independently of the IP addresses and ports. Each QUIC packet carries a connection ID in its header. The server demultiplexes incoming QUIC packets by connection ID, not by 4-tuple:

```
Before migration:
  Client IP: 192.168.1.100 (WiFi)
  Server sees packets from: 192.168.1.100:54321 → CID=abc123 → Connection X

Client switches to cellular:
  Client IP: 10.0.0.50 (cellular)
  Client sends packet: 10.0.0.50:61234 → CID=abc123

Server receives packet from new 4-tuple but same CID:
  CID=abc123 → Connection X (still active)
  Server responds to new address: 10.0.0.50:61234
  Connection X continues without interruption
```

The migration process is more nuanced to prevent IP spoofing — a malicious party could send packets with a stolen CID from a forged source address, redirecting the server's response traffic (a reflection attack). QUIC's migration protocol:

1. **Path validation:** When the server sees a new source address for an existing CID, it initiates path validation. It sends a `PATH_CHALLENGE` frame containing a random nonce to the new address.
2. **Client response:** The legitimate client (at the new address) responds with a `PATH_RESPONSE` frame echoing the nonce, proving it controls the new address.
3. **Promotion:** Once the path challenge succeeds, the new path is "promoted" — the server begins using the new address for all subsequent packets to this connection.
4. **Old path retention:** The server may continue using the old path briefly (in case the migration was temporary or path validation fails), then abandons it.

**Connection ID rotation:** QUIC clients and servers each maintain a pool of connection IDs they are willing to accept. To prevent tracking across network changes (a privacy concern — a consistent CID allows correlation of a user's sessions across networks), QUIC clients rotate their connection IDs on migration. The server provides multiple CIDs in `NEW_CONNECTION_ID` frames; the client switches to an unused one from the pool when migrating. Observers on the new network see a different CID than observers on the old network — they cannot trivially link the two sessions.

**Q11. What is NAT rebinding, and how does QUIC handle it differently from TCP?**
A: NAT rebinding occurs when a NAT device (home router, carrier NAT) silently remaps a client's port number without the client changing networks. This happens when:
- The NAT entry expires due to inactivity (UDP NAT timeouts are often 30 seconds, much shorter than TCP's 5 minutes).
- The NAT device reboots or fails over to a backup.
- A different NAT device handles the same public IP after a carrier network change.

From the server's perspective, the client's source port changes suddenly (same IP, new port). This breaks TCP for the same reason as a full IP change — the 4-tuple changes. TCP applications typically implement keep-alive probes specifically to prevent NAT entries from expiring, and even then, NAT rebinding on a different device cannot be recovered.

QUIC handles NAT rebinding as a special case of connection migration. When the server receives a packet from a new source port (same CID, same IP, different port), it initiates path validation exactly as it does for a full migration. If path validation succeeds, the connection continues. If the NAT rebinding causes the client's packets to be lost (the new NAT entry isn't established yet), the client retransmits — QUIC's reliability mechanism handles the loss — and the retransmitted packet, arriving on the new path, triggers path validation.

For UDP's shorter NAT timeout, QUIC's keep-alive mechanism (the `PING` frame) fires before the NAT entry would expire, resetting the NAT timeout. QUIC stacks typically send keep-alive PING frames every 20–25 seconds to prevent 30-second NAT expiry.

## Section 5: QUIC Internals

**Q12. How does QUIC handle congestion control, and is it the same as TCP's?**
A: QUIC implements congestion control in user-space, separate from the kernel's TCP implementation. The QUIC specification (RFC 9002) mandates a CUBIC-equivalent algorithm by default but explicitly allows implementations to use any congestion control algorithm — a flexibility TCP cannot provide without kernel patches.

Current QUIC implementations use:
- **CUBIC** (default, same as Linux TCP) — most widely deployed.
- **BBR (Bottleneck Bandwidth and Round-trip propagation time)** — developed by Google, used in QUIC implementations by Google and Cloudflare. BBR measures the available bandwidth and minimum RTT to maintain a sending rate that fills the pipe without queuing. Better throughput than CUBIC on high-bandwidth, high-latency paths; more aggressive than CUBIC in some topologies.
- **NewReno** — simpler, used in embedded and constrained implementations.

QUIC's congestion control has two key advantages over TCP's:

**1. Accurate RTT measurement:**
TCP has an ambiguity problem (Karn's algorithm): when a packet is retransmitted, which ACK corresponds to which transmission? You can't tell, so retransmitted packets are excluded from RTT estimates, leading to poor RTT accuracy under loss. QUIC uses monotonically increasing packet numbers — a retransmitted stream byte gets a new packet number, so the ACK unambiguously identifies the retransmission. RTT estimates are always accurate, improving congestion control responsiveness.

**2. QUIC-specific signals:**
QUIC's `ACK_ECN` frame reports ECN (Explicit Congestion Notification) marks received from the network — the router marked packets as congestion-experienced without dropping them. QUIC can react to congestion before packets are lost, reducing the throughput penalty of a congestion event.

**Q13. What are QUIC's flow control mechanisms, and how do they work at stream and connection level?**
A: QUIC implements flow control at two levels — connection-level and stream-level — using credit-based flow control (the same model as HTTP/2):

**Stream-level flow control:**
Each stream has a receive window. The receiver advertises how many bytes it is willing to receive (`MAX_STREAM_DATA` frame). The sender may not send beyond the advertised offset. When the receiver processes stream data and its buffer has space, it sends a new `MAX_STREAM_DATA` frame increasing the window. If the sender reaches the window limit and has no new advertisement, it stops sending and waits — this is stream-level backpressure.

**Connection-level flow control:**
The total data across all streams is also bounded by a connection-level window (`MAX_DATA` frame). Even if individual stream windows allow more data, the sender cannot exceed the connection-level limit. This prevents a single connection from consuming excessive memory on the receiver across many streams.

**Stream count limits:**
`MAX_STREAMS` frames limit the total number of concurrent streams (bidirectional and unidirectional separately). This prevents resource exhaustion from excessive stream creation — the equivalent of TCP connection limits applied at the stream level.

The two-level flow control is necessary because stream-level control alone could allow a malicious or buggy sender to open thousands of streams, each slowly consuming memory, while staying within each individual stream's window.

**Q14. What is QUIC's loss recovery mechanism, and how does it differ from TCP's retransmission?**
A: QUIC and TCP both detect loss and retransmit missing data, but the mechanisms differ in important ways:

**Loss detection:**
QUIC uses two mechanisms:
- **ACK-based:** The receiver sends `ACK` frames listing received packet number ranges. Gaps in the reported ranges indicate lost packets. Unlike TCP's cumulative ACK (which only reports the highest contiguous byte received), QUIC's selective ACK is the default — there is no "SACK TCP option" to negotiate.
- **Timer-based:** The Probe Timeout (PTO) — if no ACK is received within a computed timeout (based on smoothed RTT + 4× RTT variance), the sender transmits probe packets to elicit an ACK, even if loss isn't confirmed by gaps.

**Retransmission:**
In TCP, a retransmission sends the same sequence numbers. In QUIC, a retransmission sends the same stream data in a new packet with a new packet number. This distinction:
- Eliminates the retransmission ambiguity problem (Karn's algorithm) — RTT is always measurable.
- Enables loss of the retransmission to be detected independently (a new ACK gap, separate from the original loss).
- Allows the original packet to arrive after the retransmission — both are processed correctly (stream-level deduplication by stream offset, not packet number).

**QUIC's ACK delay:**
QUIC receivers delay ACKs slightly (configurable, default 25ms) to allow batching — instead of ACKing every packet, ACK every N packets or after a delay. This reduces ACK overhead but requires the sender's RTT calculation to account for the delay (`ACK_DELAY` field in the ACK frame). TCP also delays ACKs (TCP delayed ACK, default 40ms) but does not signal the delay to the sender — a source of RTT estimation error.

## Section 6: Deployment and Practical Considerations

**Q15. How is HTTP/3 negotiated, and what is the `Alt-Svc` header's role?**
A: A browser or client cannot know in advance whether a server supports HTTP/3. The negotiation happens out-of-band, using one of two mechanisms:

**Mechanism 1 — `Alt-Svc` header (RFC 7838):**
The server includes an `Alt-Svc` header in an HTTP/1.1 or HTTP/2 response, advertising that an alternative service is available via QUIC on a specific port:
```
Alt-Svc: h3=":443"; ma=86400
```
`h3` is the ALPN token for HTTP/3. `ma=86400` means this advertisement is valid for 86400 seconds (24 hours). On subsequent visits within the validity period, the client attempts HTTP/3 directly. The first visit always uses TCP (HTTP/1.1 or HTTP/2) — there is inherently at least one TCP connection before HTTP/3 is used with a new server.

**Mechanism 2 — DNS HTTPS record (RFC 9460):**
A `HTTPS` DNS record (type 65) can advertise HTTP/3 support alongside the server's address:
```
_https._tcp.example.com. IN HTTPS 1 . alpn="h3,h2" port=443
```
Clients that resolve this record before connecting can attempt HTTP/3 from the first connection — no initial TCP connection required. This is the preferred mechanism for avoiding the "first visit is always TCP" problem, but requires DNS resolver and client support (Chrome, Firefox, and Safari support it; most enterprise DNS resolvers now support HTTPS records).

**Happy Eyeballs for HTTP/3:**
Modern clients implement a race between HTTP/3 (QUIC/UDP) and HTTP/2 (TCP/TLS) connection attempts. If the QUIC attempt succeeds within a short window (typically 250ms), it wins. If the TCP connection establishes first, it is used and the QUIC connection is abandoned. This ensures that QUIC failures (firewall blocking UDP port 443, middle-box interference) do not degrade the user experience — the TCP fallback kicks in automatically.

**Q16. What infrastructure changes does an organisation need to support HTTP/3?**
A: Supporting HTTP/3 requires changes at multiple layers:

**Network / firewall layer:**
UDP port 443 must be open inbound (for servers) and outbound (for clients). Many enterprise firewalls block UDP traffic beyond DNS (port 53) and DTLS. A firewall that blocks UDP 443 silently causes all HTTP/3 attempts to fail — clients fall back to HTTP/2 via the Happy Eyeballs mechanism, so the failure is invisible to users but prevents QUIC benefits.

**Load balancer / reverse proxy layer:**
The load balancer must understand QUIC to:
- Demultiplex connections by connection ID (not 4-tuple) — standard L4 load balancing by 4-tuple breaks QUIC connection migration.
- Handle the UDP-specific path validation and migration protocols.
- Support TLS termination in the QUIC context.

Nginx supports HTTP/3 from version 1.25.0 (using the `quiche` or `nginx-quic` patch). Caddy has native HTTP/3 support. HAProxy has experimental HTTP/3 support. AWS ALB does not yet support HTTP/3 end-to-end (as of 2025 it supports HTTP/3 between clients and the ALB, but HTTP/2 between ALB and backends). Cloudflare's full-stack supports HTTP/3 natively.

**Application layer:**
Servers must advertise HTTP/3 support via `Alt-Svc` headers or DNS HTTPS records. Application code does not typically need changes — HTTP/3 is transparent at the HTTP semantic level (same request/response model). Performance tuning (stream limits, connection parameters) may need adjustment.

**Observability:**
Standard TCP-based monitoring tools (`tcpdump`, `Wireshark` without QUIC dissectors, many APM agents) cannot inspect QUIC payloads (encrypted) or correctly decode QUIC header fields. HTTP/3 requires QUIC-aware monitoring: Chrome's `chrome://net-internals/#quic`, `qvis` (QUIC visualisation tool), Wireshark with QUIC dissector and session keys, or QUIC implementation-specific logging (quiche's `--qlog` format).

**Q17. What are the practical performance gains of HTTP/3 vs HTTP/2, and when are they most pronounced?**
A: The performance gains of HTTP/3 are not uniform — they depend heavily on network conditions:

**On reliable, low-latency networks (datacenter, office WiFi with 0% packet loss):**
HTTP/3 vs HTTP/2 performance difference is minimal — often within measurement noise. The HOL blocking advantage doesn't materialise (no packet loss to trigger it). The handshake savings (1 RTT vs 2 RTTs) matter only for new connections, and connection reuse (keep-alive) eliminates this advantage for subsequent requests. HTTP/2 may actually be slightly faster because TCP's kernel implementation is more mature and optimised than userspace QUIC.

**On lossy or high-latency networks (mobile, satellite, busy WiFi):**
HTTP/3 wins significantly:
- At 1% packet loss: HTTP/2 throughput degrades by ~60% due to transport-level HOL blocking across all streams. HTTP/3 degrades by ~10–15% (only the affected stream stalls).
- At 2% packet loss: HTTP/2 can become unusably slow; HTTP/3 continues to deliver.
- On high-latency links (satellite: 600ms RTT): the 1 RTT vs 2 RTT handshake saves 600ms per new connection — meaningful for short-lived sessions.

**On mobile networks with frequent network transitions:**
Connection migration eliminates reconnection latency — the user never experiences the 1–2 second delay of TCP reconnection + TLS handshake + application re-authentication when switching between WiFi and cellular. For payment flows, streaming, and other stateful interactions, this is significant.

**Real-world measurements:**
- Google reported 3% improvement in search latency and 30% reduction in rebuffering in YouTube video playback with QUIC vs TCP+TLS on mobile.
- Cloudflare reports 10–15% faster page loads for mobile users.
- Facebook (now Meta) reported significant improvement for users in high-latency regions (Southeast Asia, Africa).

## Section 7: Pitfalls and Anti-patterns

**Q18. Why might UDP port 443 be blocked by firewalls, and what is the fallback behaviour?**
A: Many enterprise firewalls, carrier-grade NATs, and network security appliances were configured with policies that allow TCP 443 (HTTPS) but block UDP 443 (which appeared only with QUIC and has no historical legitimate use). The blocking is often inadvertent — a blanket "block all UDP except DNS and NTP" rule — rather than deliberate HTTP/3 rejection.

The fallback mechanism (Happy Eyeballs with QUIC): when a client attempts QUIC to a server and receives no response (UDP blocked → packets silently dropped, not rejected with ICMP), after a timeout (typically 250–300ms), the client falls back to TCP-based HTTP/2. The user experiences a ~300ms delay on the first connection, then normal HTTP/2 performance. Subsequent connections may re-attempt QUIC periodically.

If QUIC packets are rejected with ICMP Port Unreachable (rare — most firewalls silently drop), the client falls back faster — it detects the rejection immediately rather than waiting for a timeout. Some QUIC implementations cache "QUIC not available" state per server and use TCP immediately on subsequent visits within the cache validity period.

For server operators: ensure UDP 443 is open inbound and that upstream firewalls (CDN, cloud provider, ISP transit) do not silently drop QUIC packets. Verify with `curl --http3` from various network locations. For client operators (enterprise environments): explicitly allow UDP 443 if HTTP/3 benefits are desired, or explicitly block it if QUIC visibility is a security requirement (encrypted QUIC headers prevent some DLP and inspection tools from functioning).

**Q19. What are the memory and CPU cost implications of running QUIC in userspace vs TCP in the kernel?**
A: QUIC's userspace implementation has real CPU and memory overhead compared to TCP's kernel-optimised implementation:

**CPU overhead:**
- **Encryption cost:** Every QUIC packet is encrypted (header protection + payload encryption). TCP with TLS also encrypts, but QUIC encrypts more aggressively — even handshake and ACK packets. The encryption CPU cost is comparable to TLS-over-TCP but applied to more packet types.
- **Userspace packet processing:** TCP runs in the kernel with direct access to hardware receive queues. QUIC receives UDP packets via system calls, copies them to userspace, and processes them in the application's event loop. This adds system call overhead and memory copies compared to the kernel's zero-copy TCP receive path. At 10 Gbps+ line rates, this can consume 1–2 extra CPU cores compared to TCP.
- **ACK processing:** QUIC's selective ACK (SACK-by-default) with packet number ranges requires more per-ACK computation than TCP's cumulative ACK.

**Memory overhead:**
- QUIC maintains per-connection send and receive buffers in user space, duplicating some of what the kernel maintains for TCP sockets. A server with 100,000 QUIC connections needs to allocate and manage these buffers explicitly.
- Connection state in user space is larger than a kernel TCP socket because the QUIC library must maintain its own retransmission queues, congestion state, stream state, and flow control windows — all of which are in kernel memory for TCP.

**Mitigation:** Hardware acceleration via kernel bypass (DPDK, io_uring with zero-copy), kernel-native QUIC implementations (being developed), and XDP (eXpress Data Path) can reduce the CPU cost. Production QUIC servers (Cloudflare, Google, Facebook) run on highly tuned stacks with custom packet processing pipelines.

**Q20. What is QUIC's behaviour when the server's connection ID changes, and how does stateless load balancing work?**
A: QUIC's use of connection IDs for demultiplexing creates a challenge for stateless load balancers that route packets based on 4-tuple (IP + port). A client migrating to a new network gets a new 4-tuple — a stateless L4 load balancer would route the migrated connection to a different backend server, which has no state for that connection ID. The connection would fail.

Solutions:

**Stateful connection tracking (L7 load balancing):**
The load balancer maintains a connection ID → backend mapping table. Incoming packets are routed to the correct backend based on connection ID. This requires the load balancer to be QUIC-aware (parsing the connection ID from the packet header). Nginx with HTTP/3, HAProxy with QUIC support, and QUIC-aware cloud load balancers (Cloudflare) implement this.

**Encoding routing information in the connection ID:**
QUIC connection IDs are opaque to the client — the server chooses the connection ID the client uses to identify the connection (the client provides a set of "preferred" CIDs, but the server issues the ones it wants). A server-side load balancer can encode the backend server index directly in the connection ID (using a portion of the CID bits):
```
CID = [load_balancer_token (4 bytes) | backend_index (2 bytes) | random (10 bytes)]
```
The load balancer reads the backend index from the CID without maintaining per-connection state — routing is stateless but QUIC-aware. This is the approach specified in the IETF draft "QUIC-LB" (Load Balancer-Generated Connection IDs). Cloudflare's production load balancer uses this technique.

## Section 8: Scenario / System Design Style Questions

**Q21. "Your fintech mobile app frequently loses sessions when users switch from WiFi to cellular while completing a payment flow. The backend is a NestJS API behind an AWS ALB. What does the HTTP/3 and QUIC connection migration story look like here, and what would you need to change?"**
A: The current TCP-based session loss is caused by the IP change on network transition — the TCP connection's 4-tuple changes and the connection dies. The client must reconnect, re-authenticate (if the session token was not serialised), and retry the payment API call. If the payment was non-idempotent, the retry may cause a double charge without proper idempotency handling.

**What QUIC connection migration provides:**
The QUIC connection survives the network transition. The connection ID remains valid; the client sends a path validation challenge to the server from the new IP; the server validates and promotes the new path. The TCP reconnection + TLS handshake + re-authentication RTTs are eliminated — the payment API call continues on the existing QUIC connection without the application being aware of the network change.

**What needs to change:**

**Layer 1 — Load balancer:** AWS ALB (as of 2025) supports HTTP/3 on the client-facing side — clients can use QUIC to the ALB. However, the ALB terminates QUIC and uses HTTP/2 or HTTP/1.1 to the NestJS backend. Connection migration at the client-ALB boundary works; the ALB's internal routing is QUIC-aware. If the ALB does not yet support QUIC in the target region, an alternative is terminating QUIC at a Cloudflare or Nginx layer in front of the ALB.

**Layer 2 — Server advertisement:** The NestJS backend itself does not need changes (HTTP/3 semantics are identical to HTTP/2 at the application layer). The ALB must be configured to advertise HTTP/3 support via `Alt-Svc` headers on responses.

**Layer 3 — Idempotency (regardless of QUIC):** Even with connection migration, a payment API should be idempotent. If the migration causes any packet loss during the transition (brief), the request may be retried. The payment endpoint should use an idempotency key (client-generated UUID sent in the request header) and the backend should deduplicate requests with the same key. QUIC migration reduces the probability of needing a retry, but does not eliminate it.

**Layer 4 — Mobile client:** The mobile app's HTTP client library (React Native fetch, Alamofire on iOS, OkHttp on Android) must support HTTP/3 / QUIC. iOS 14+/macOS 11+ support HTTP/3 natively via URLSession. Android supports HTTP/3 via OkHttp 5+ with Cronet or via the Conscrypt QUIC stack. The client does not need application code changes — the HTTP/3 negotiation and connection migration are handled by the HTTP client library.

**Layer 5 — UDP firewall rules:** Ensure that UDP port 443 is allowed on the ALB's security group inbound rules. AWS security groups default-allow by protocol/port — if the rule says `UDP 443 allow`, QUIC will pass. Verify that no WAF or network ACL blocks UDP 443.

**Q22. "A teammate proposes using 0-RTT for the payment confirmation API call to reduce latency for returning users. What do you tell them?"**
A: This is a well-intentioned performance optimisation that introduces a serious security vulnerability. The response:

**Why 0-RTT cannot be used for payment confirmation:**
0-RTT data is vulnerable to replay attacks — an adversary who captures the 0-RTT packets can retransmit them to the server, causing the payment to be executed twice. The server cannot distinguish the replay from a legitimate retry because the early traffic keys are the same for both. A payment confirmation (`POST /payments/confirm`) is definitionally non-idempotent and has financial side effects — exactly the class of request that 0-RTT must never carry.

**The RFC explicitly prohibits this:**
RFC 9001 (QUIC-TLS) section 9.2 states: "Application protocols MUST either not use 0-RTT for data that is not replay safe or require clients to ensure that requests sent in 0-RTT are idempotent." RFC 9114 (HTTP/3) section 4.6.1 states that HTTP methods with safe and idempotent semantics (GET, HEAD, OPTIONS) can use 0-RTT, but methods with side effects (POST, PUT, DELETE) must not be sent as 0-RTT data by conforming clients.

**What 0-RTT is appropriate for:**
For the payment flow, 0-RTT can safely carry idempotent pre-payment requests: `GET /payment-methods` (fetch saved cards), `GET /products/{id}` (fetch item details), `GET /users/me/balance` (check balance). These speed up the pre-payment UI while the payment confirmation itself travels on the post-handshake connection.

**The correct latency optimisation for payment confirmation:**
The 1-RTT handshake is already fast (typically 20–50ms on a mobile network vs WiFi). The bigger latency wins are: connection migration (no reconnection on network change), server-side processing optimisation, and connection pre-warming (establishing the QUIC connection during the checkout flow so the confirmation API call has no handshake latency).

**Q23. "Design the network stack for a high-throughput API gateway that must support HTTP/3 for mobile clients and HTTP/2 for backend microservices, with connection migration support and zero downtime deploys."**
A: A three-tier architecture with clear protocol boundaries:

**Tier 1 — Edge (client-facing QUIC termination):**
```
Mobile clients ──HTTP/3 (QUIC)──► Nginx 1.25+ / Caddy / Cloudflare Workers
                                   (QUIC-aware, connection ID routing)
                                   Terminates QUIC, handles connection migration,
                                   path validation, session ticket issuance
                                   Advertises: Alt-Svc: h3=":443"; ma=86400
                                   DNS: HTTPS record advertising h3,h2
```

QUIC termination at the edge is correct — QUIC's benefits (migration, 0-RTT, HOL blocking elimination) apply to the client-edge segment where packet loss and network transitions are common. The edge-to-backend segment is a datacenter network where TCP's kernel optimisation and maturity outweigh QUIC's benefits.

**Tier 2 — Internal load balancing (HTTP/2 over TCP):**
```
Nginx/Caddy ──HTTP/2 (TCP+TLS)──► Internal load balancer (HAProxy / AWS ALB)
                                    gRPC-compatible
                                    Connection draining for zero-downtime deploy
                                    Health checks via HTTP/2 ping frames
```

HTTP/2 between the edge and internal LB provides stream multiplexing without QUIC's userspace overhead. On a datacenter network (sub-millisecond RTT, <0.01% packet loss), TCP+TLS is optimal.

**Tier 3 — Backend microservices (HTTP/2 or gRPC):**
```
Internal LB ──gRPC (HTTP/2)──► NestJS microservices
                                 Connection pooling per service
                                 Keep-alive: 75s (< LB idle timeout of 90s)
                                 Max concurrent streams: 100 per connection
```

**Zero-downtime deploys with QUIC:**
QUIC connections cannot be seamlessly migrated server-side (only client-side migration is defined in RFC 9000). For server restarts, use connection draining:
1. The old server stops accepting new QUIC connections (no new CIDs issued) and stops advertising via Alt-Svc.
2. Existing QUIC connections are allowed to complete naturally, up to a drain timeout (e.g., 30 seconds).
3. After the drain timeout, the old server sends a QUIC `CONNECTION_CLOSE` frame with a `NO_ERROR` code to remaining connections — clients reconnect to the new server.
4. The new server starts, binds to the same port, and begins accepting new QUIC connections.

QUIC's session tickets (for 0-RTT resumption) must be transferable between server instances. If session tickets are encrypted with a server-specific key and the key is not shared, migrating clients cannot resume with 0-RTT on the new server. Solution: use a shared session ticket encryption key across all server instances (stored in Redis or AWS Parameter Store, rotated regularly). All instances can decrypt any session ticket and issue 0-RTT data.

## Quick Reference: TCP+TLS vs QUIC/HTTP3

| Dimension                          | HTTP/2 (TCP + TLS 1.3)                         | HTTP/3 (QUIC)                                          |
|------------------------------------|------------------------------------------------|--------------------------------------------------------|
| Transport layer                    | TCP (kernel)                                   | QUIC (userspace, on top of UDP)                        |
| Encryption                         | TLS 1.3 over TCP (headers in plaintext)        | TLS 1.3 integrated — most headers encrypted            |
| New connection latency             | 2 RTTs (TCP 1 + TLS 1)                        | 1 RTT                                                  |
| Repeat connection latency          | 1 RTT (TLS 1.3 session resumption)            | 0 RTT (0-RTT data with session ticket)                 |
| HOL blocking                       | Transport-level (TCP stalls all streams)       | None at transport — stream-independent                 |
| Connection identification          | 4-tuple (src IP, src port, dst IP, dst port)  | Connection ID (independent of IP/port)                 |
| Network migration                  | Not supported — IP change = connection drop   | Supported — path validation + CID continuity           |
| NAT rebinding                      | Breaks connection                              | Handled as migration (path validation)                 |
| Congestion control                 | CUBIC/BBR in kernel — cannot change per-app   | CUBIC/BBR in userspace — per-connection choice         |
| RTT estimation accuracy            | Karn's algorithm — retransmissions excluded   | Always accurate — new packet number per retransmit     |
| Multiplexing                       | HTTP/2 frames over one TCP stream             | QUIC streams — native transport multiplexing           |
| Header compression                 | HPACK (shared dynamic table — HOL risk)       | QPACK (separate control streams — no HOL risk)         |
| CPU overhead (server)              | Low — kernel TCP + TLS hardware offload       | Higher — userspace packet processing                   |
| Protocol updateability             | Slow — kernel changes required                | Fast — userspace library update                        |
| Firewall compatibility             | Universal — TCP 443                           | UDP 443 may be blocked — Happy Eyeballs fallback       |
| Middlebox interference             | Common — middleboxes modify TCP headers       | Prevented — headers encrypted                          |
| Debugging                          | Standard tools (tcpdump, Wireshark)           | Requires QUIC-aware tools + session keys               |
| Best environment                   | Datacenter, reliable networks                 | Mobile, lossy networks, high-latency links             |
| Standardised                       | RFC 7540 (2015)                               | RFC 9000/9001/9114 (2021/2022)                         |

**Tip for the interview:** At 5 YOE, HTTP/3 and QUIC questions come in two flavours: protocol mechanics ("explain how QUIC eliminates HOL blocking," "how does connection migration work") and system design trade-offs ("should we adopt HTTP/3 for our API gateway," "why can't we use 0-RTT for payment APIs," "what changes when we put QUIC in front of our Kubernetes cluster"). The mechanics answer requires tracing the problem from TCP's single byte stream through HTTP/2's application-layer workarounds to QUIC's native stream independence. The trade-off answer requires knowing when QUIC helps (mobile, lossy networks, frequent IP changes) vs when it doesn't (datacenter links, CPU-constrained servers) and what operationalises it (UDP firewall rules, QUIC-aware load balancers, session ticket sharing). Have one concrete angle ready — the payment session loss on network transitions that QUIC migration solves, or the 0-RTT replay attack argument for why you'd reject a naive "make everything faster with 0-RTT" proposal. That's the depth that lands at this level.
