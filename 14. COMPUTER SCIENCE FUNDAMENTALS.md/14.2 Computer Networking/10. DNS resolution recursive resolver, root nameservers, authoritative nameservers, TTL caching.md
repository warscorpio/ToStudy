# DNS Resolution: Recursive Resolver, Root Nameservers, Authoritative Nameservers & TTL Caching — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is DNS, and why is it necessary?**
A: DNS (Domain Name System) is a globally distributed, hierarchical database that translates human-readable domain names (`api.example.com`) into IP addresses (`151.101.65.121`) that routers and network stacks use to deliver packets. It is a fundamental piece of internet infrastructure — without it, every application would need to hard-code IP addresses, and changing a server's IP would require updating every client simultaneously.

DNS is necessary for three reasons beyond simple name-to-IP translation:

- **Indirection** — a domain name is a stable identifier. The IP address behind it can change (server migrations, failovers, load balancing) without clients needing to update anything. DNS is the layer of indirection that makes this possible.
- **Load distribution** — a single domain can return multiple IP addresses (round-robin DNS) or different IPs based on the client's geography (GeoDNS), distributing traffic across servers.
- **Service discovery** — SRV records encode port numbers and priorities, enabling applications (Kubernetes, Consul, etcd) to discover service endpoints dynamically without hard-coded configuration.

DNS operates predominantly over UDP port 53 (for queries up to 512 bytes, or 4096 bytes with EDNS), switching to TCP port 53 for responses that exceed the UDP limit or for zone transfers. DNS over HTTPS (DoH) and DNS over TLS (DoT) encrypt queries to prevent eavesdropping — port 443 and 853 respectively.

**Q2. What are the four actors in a DNS resolution, and what is each one's role?**
A: A full DNS resolution involves four distinct components, each serving a different function:

- **DNS client (stub resolver)** — the minimal DNS implementation built into every operating system. It does not perform iterative lookups itself — it simply forwards queries to the configured recursive resolver and waits for a complete answer. Applications call the OS's `getaddrinfo()` or `gethostbyname()` function, which the stub resolver handles. It maintains a small local cache.

- **Recursive resolver** (also called a full-service resolver or recursive nameserver) — the workhorse of DNS. When the stub resolver queries it with `api.example.com`, the recursive resolver takes responsibility for finding the answer by iterating through the DNS hierarchy: querying root nameservers, then TLD nameservers, then authoritative nameservers. It caches results for their TTL duration and returns the final answer to the stub resolver. Most users' recursive resolvers are their ISP's resolvers or public resolvers (Google's `8.8.8.8`, Cloudflare's `1.1.1.1`).

- **Root nameservers** — the top of the DNS hierarchy. There are 13 root nameserver identities (labelled `a.root-servers.net` through `m.root-servers.net`), operated by 12 different organisations, and served by hundreds of physical servers worldwide via anycast. Root nameservers do not know the IP address of `api.example.com` — they know which nameservers are authoritative for the `.com` TLD, and they respond with those TLD nameserver addresses. They are the starting point for every iterative resolution.

- **Authoritative nameserver** — the definitive source of truth for a specific domain. When a domain owner registers `example.com`, they designate authoritative nameservers (e.g., `ns1.example.com`, `ns2.example.com`) and upload DNS records to them. When queried, an authoritative nameserver answers with the actual records (A, AAAA, CNAME, MX, etc.) from its zone file without deferring to anyone else. It sets the TTL on each record, controlling how long resolvers may cache the answer.

**Q3. Walk through a complete DNS resolution for `api.example.com` from first principles, assuming no caches are warm.**
A: A full iterative resolution from a cold cache:

```
Application: fetch('https://api.example.com/orders')
    │
    ▼
1. OS stub resolver checks:
   - Local /etc/hosts → not found
   - Local DNS cache → empty (cold)
   - Forwards to recursive resolver (e.g., 8.8.8.8)

2. Recursive resolver (8.8.8.8) checks its cache → empty
   Begins iterative resolution:

   Step A — Query a root nameserver:
   Resolver → a.root-servers.net: "Who is authoritative for api.example.com?"
   Root responds: "I don't know api.example.com, but here are the .com TLD servers:
                   a.gtld-servers.net (192.5.6.30)
                   b.gtld-servers.net (192.33.14.30)
                   ..."
   (Referral response — not an authoritative answer)

   Step B — Query the .com TLD nameserver:
   Resolver → a.gtld-servers.net: "Who is authoritative for api.example.com?"
   TLD responds: "I don't know api.example.com, but here are example.com's nameservers:
                  ns1.example.com (205.251.196.1)
                  ns2.example.com (205.251.197.1)"
   (Another referral)

   Step C — Query example.com's authoritative nameserver:
   Resolver → ns1.example.com: "What is the A record for api.example.com?"
   Authoritative responds: "api.example.com. 300 IN A 151.101.65.121"
                            └─────────────────────────────────────────┘
                            name  TTL  class  type  value
   (Authoritative answer — the AA flag is set in the DNS response)

3. Recursive resolver caches: api.example.com → 151.101.65.121 for 300 seconds
   Returns 151.101.65.121 to the stub resolver.

4. OS stub resolver caches the answer, returns 151.101.65.121 to the application.

5. Application opens a TCP connection to 151.101.65.121:443.
```

**Total round trips** (cold cache, typical internet latency):
- Root query: ~20ms (root servers are highly anycast-distributed)
- TLD query: ~20ms
- Authoritative query: ~30ms (may be geographically closer or further)
- **Total DNS time: ~70ms** before any TCP connection begins

With a warm recursive resolver cache (the common case): the resolver answers immediately from cache — **~1–5ms** total DNS time.

**Q4. What is the difference between a recursive query and an iterative query?**
A: The distinction is in who does the work of traversing the DNS hierarchy:

- **Recursive query** — the querying party asks the resolver to do all the work and return a complete answer. The stub resolver sends a recursive query to the recursive resolver: "Find me the IP for `api.example.com`, and do whatever it takes." The stub resolver waits; the recursive resolver does all the leg work.

- **Iterative query** — the querying party does the work itself, one step at a time. Each nameserver it contacts either answers or refers it to another nameserver. The querying party follows each referral. This is what the **recursive resolver** does when it talks to root and TLD nameservers — it sends iterative queries and follows referrals.

```
Stub resolver → Recursive resolver: "What is api.example.com?" (RECURSIVE)
                ↓ recursive resolver does all iteration internally
Recursive resolver → Root NS:    "api.example.com?" → "Ask .com TLD" (ITERATIVE)
Recursive resolver → .com TLD:   "api.example.com?" → "Ask example.com NS" (ITERATIVE)
Recursive resolver → example.com NS: "api.example.com?" → "151.101.65.121" (ITERATIVE)
                ↑ recursive resolver returns complete answer
Stub resolver ← Recursive resolver: "151.101.65.121" (complete answer)
```

The recursive resolver is named for the recursive query it accepts from the stub resolver — not for the iterative queries it itself sends to authoritative nameservers.

**Q5. What does the DNS hierarchy look like, and how are zones of authority divided?**
A: The DNS namespace is a tree with the root at the top, branching into top-level domains (TLDs), then second-level domains, then subdomains:

```
                    . (root)
                   /|\
               com  org  net  in  io  ...  (TLDs)
              /                \
         example              wikipedia
        /       \
      api       www          (subdomains of example.com)
```

The hierarchy is divided into **zones** — contiguous portions of the namespace managed by a single administrative entity. Zone boundaries are where authority is **delegated**:

- The root zone is managed by IANA/ICANN. It delegates authority for `.com` to Verisign.
- Verisign's `.com` zone delegates authority for `example.com` to whoever registered it (which specifies authoritative nameservers in their NS records).
- The `example.com` zone owner can further delegate `api.example.com` to different nameservers (creating a sub-zone), or can manage it as part of the `example.com` zone.

Each zone has:
- **NS records** — identify the authoritative nameservers for the zone.
- **SOA record** (Start of Authority) — metadata about the zone: primary nameserver, responsible email address, serial number (used for zone transfer synchronisation), and timing parameters (refresh, retry, expire, minimum TTL).

```bash
dig SOA example.com
# example.com. 3600 IN SOA ns1.example.com. admin.example.com. (
#   2024011501  ; serial (YYYYMMDDNN — date + sequence)
#   7200        ; refresh (secondary checks for updates every 2h)
#   1800        ; retry (if refresh fails, retry after 30m)
#   1209600     ; expire (secondary stops answering after 14 days without update)
#   300         ; minimum TTL (negative caching TTL for NXDOMAIN responses)
# )
```

## Section 2: Recursive Resolvers

**Q6. What does a recursive resolver actually do, and what makes a good one?**
A: A recursive resolver is a server that accepts DNS queries from stub resolvers and takes complete responsibility for producing a final answer. Its operations:

**Resolution:** For uncached queries, it performs iterative lookups starting from root nameservers (which it knows from a hard-coded "hints file" — a list of root nameserver IP addresses baked into the resolver software). It follows NS record referrals down the hierarchy until it reaches an authoritative answer.

**Caching:** Every answer received is cached for its TTL. This is the resolver's most impactful function — a heavily used resolver serving millions of users will have most popular domains cached at all times, eliminating iterative lookup latency for the vast majority of queries.

**Negative caching:** When a domain does not exist, the resolver caches the NXDOMAIN response for the SOA record's minimum TTL. Subsequent queries for the same non-existent name return NXDOMAIN from cache without hitting the authoritative nameserver.

**DNSSEC validation:** A validating resolver verifies the cryptographic signatures on DNS responses, ensuring records were not tampered with in transit. Each zone signs its records with a private key; the resolver verifies using the published public key, chaining up to the root's trust anchor.

**What makes a good recursive resolver:**
- **Low latency** — anycast routing to bring resolver nodes geographically close to users. Cloudflare's `1.1.1.1` cites median query response under 15ms.
- **High cache hit rate** — serving many users means popular domains are almost always cached.
- **Privacy** — `1.1.1.1` (Cloudflare) and `8.8.8.8` (Google) commit to not logging or selling query data. ISP resolvers historically did not make this commitment.
- **DoH/DoT support** — encrypted transport prevents eavesdropping by ISPs and network intermediaries.
- **DNSSEC validation** — protection against DNS spoofing attacks.

**Q7. What is the difference between `8.8.8.8`, `1.1.1.1`, and an ISP resolver? When would you change the resolver?**
A: All three are recursive resolvers — they perform the same function. They differ in operator, privacy policy, performance, and features:

| Property | Google `8.8.8.8` | Cloudflare `1.1.1.1` | ISP resolver |
|--|--|--|--|
| Operator | Google | Cloudflare | Your ISP |
| Latency | Low (global anycast) | Very low (largest anycast network) | Low for local users (often nearby) |
| Privacy | Logs queries (used for diagnostics, 24–48h retention) | Audited not to log IPs; KPMG audited | Often logs and monetises query data |
| DNSSEC | Yes | Yes | Varies |
| DoH/DoT | Yes | Yes | Rarely |
| Filtering | No (unfiltered) | No (1.1.1.1); family filtering (1.1.3.3) | Sometimes (ISP filtering policies) |
| Cache size | Very large (serves billions of queries) | Very large | Smaller (fewer users) |

**When to change the default ISP resolver:**

- **Privacy concerns** — ISP resolvers see all your DNS queries and in many jurisdictions can sell this data. Switching to `1.1.1.1` or `8.8.8.8` moves that visibility to a company with a stronger public privacy commitment.
- **Performance** — if the ISP resolver is slow or unreliable. `dig` query times to different resolvers reveal which is fastest from your network.
- **Filtering bypass** — ISP resolvers sometimes block domains (legal requirements, parental controls). Public resolvers are typically unfiltered.
- **Developer testing** — testing DNS changes requires bypassing caches. Switching to a resolver that doesn't cache locally (or using `dig @ns1.example.com` to query the authoritative directly) shows live DNS state.

In containerised environments and Kubernetes, the default DNS resolver is controlled at the cluster level (CoreDNS in Kubernetes). In production services, the resolver is typically the OS default — but services making many DNS queries may benefit from embedding a caching resolver (e.g., `dnsmasq`, `unbound`) locally to reduce latency for repeated lookups.

**Q8. How does a recursive resolver handle a query for a name that does not exist?**
A: For a non-existent name (e.g., `doesnotexist.example.com`), the resolution process proceeds normally through the hierarchy until the authoritative nameserver is reached — but the authoritative nameserver returns an NXDOMAIN (Non-Existent Domain) response instead of an A record:

```
Recursive resolver queries ns1.example.com: "doesnotexist.example.com?"
ns1.example.com responds:
  Status: NXDOMAIN (response code 3)
  Authority section: example.com. 3600 IN SOA ns1.example.com. admin.example.com. ...
  (The SOA record's minimum TTL field governs how long to cache this NXDOMAIN)
```

The recursive resolver caches the NXDOMAIN response for the SOA minimum TTL (e.g., 300 seconds). For the next 300 seconds, any query for `doesnotexist.example.com` returns NXDOMAIN from cache without querying the authoritative nameserver — **negative caching** (RFC 2308).

This matters operationally:
- A misconfigured service that queries a non-existent hostname repeatedly will hit the cache rather than hammering the authoritative nameserver.
- If you create a new DNS record but the NXDOMAIN is already cached, the positive record will not be seen until the negative cache TTL expires. For this reason, SOA minimum TTLs should be short (60–300 seconds) on zones where records are actively changed.

```bash
# Observe NXDOMAIN response and its TTL
dig doesnotexist.example.com

# ;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 12345
# ;; AUTHORITY SECTION:
# example.com.  300  IN  SOA  ns1.example.com. admin.example.com. 2024011501 7200 1800 1209600 300
#                ↑
#   SOA minimum TTL (300s) — governs negative caching duration
```

## Section 3: Root Nameservers

**Q9. What are root nameservers, how many are there, and how do they scale globally?**
A: Root nameservers are the authoritative source for the DNS root zone — the top of the entire DNS hierarchy. They answer queries about which nameservers are authoritative for each TLD (`.com`, `.org`, `.in`, `.io`, etc.).

**The 13 root server identities:**
There are exactly 13 root nameserver identities, named `a.root-servers.net` through `m.root-servers.net`. The limit of 13 is historical — it is the maximum that fits in a single 512-byte UDP DNS response (each IPv4 address takes 32 bytes; with names and overhead, 13 is the practical limit). With IPv6 and EDNS(0) (which extends the UDP payload limit to 4096 bytes), this constraint no longer applies, but the 13-identity convention remains.

**Anycast — the scaling solution:**
Each of the 13 identities is served by many physical servers distributed globally via **anycast**. With anycast, multiple servers share the same IP address, and BGP routing sends each query to the topologically nearest server. As of 2024, the 13 root server identities are served by over 1,700 physical server instances worldwide.

```
a.root-servers.net (198.41.0.4) — operated by Verisign
b.root-servers.net (199.9.14.201) — operated by ISC (Internet Systems Consortium)
c.root-servers.net (192.33.4.12) — operated by Cogent Communications
...
m.root-servers.net (202.12.27.33) — operated by WIDE Project (Japan)
```

When a resolver queries `198.41.0.4`, BGP routes the packet to the nearest server with that anycast IP — which might be in Mumbai rather than the US-based origin of the IP range. The client never knows (or needs to know) which physical server answered.

**How often root nameservers are queried in practice:**
Almost never for popular domains. The `.com` TLD nameservers and popular authoritative nameservers are cached by recursive resolvers at all times. Root nameservers receive queries primarily for:
- First-time lookups by newly started resolvers with empty caches.
- Novel TLDs or domains that have never been queried before.
- Negative caching expiry for rare domains.

Estimates suggest root nameservers receive a tiny fraction of total DNS queries (perhaps 1–5%) because caching eliminates most iterative lookups before they reach the root.

**Q10. What is a "hints file" and how does a recursive resolver know where to start?**
A: A recursive resolver must know the IP addresses of root nameservers to begin iterative resolution — but it cannot use DNS to discover them (that would be circular: you need DNS to find the DNS root). The solution is a **hints file** (also called `named.root` or `root.hints`): a file containing the NS records and glue A/AAAA records for all 13 root server identities, hard-coded into the resolver software or its configuration.

```
# Excerpt from a root hints file (BIND format)
.                        3600000      NS    A.ROOT-SERVERS.NET.
A.ROOT-SERVERS.NET.      3600000      A     198.41.0.4
A.ROOT-SERVERS.NET.      3600000      AAAA  2001:503:ba3e::2:30

.                        3600000      NS    B.ROOT-SERVERS.NET.
B.ROOT-SERVERS.NET.      3600000      A     199.9.14.201
...
```

The hints file is not queried on every resolution — it is a bootstrap. Once the resolver starts up and resolves any query, it refreshes its knowledge of root nameserver addresses by querying the root zone directly (`dig . NS @a.root-servers.net`). The refreshed answers are cached and authoritative; the hints file is only the starting point for a cold resolver.

BIND, Unbound, PowerDNS, and CoreDNS all ship with embedded or configurable hints files. Operators should update hints files periodically (the IANA publishes the canonical file at https://www.internic.net/zones/named.root), but changes to root server addresses are extremely rare and always backward-compatible.

## Section 4: Authoritative Nameservers

**Q11. What is an authoritative nameserver, and what records does it serve?**
A: An authoritative nameserver is the definitive source of truth for a DNS zone. When it answers a query, the response has the **AA (Authoritative Answer)** flag set — distinguishing it from a cached response from a recursive resolver. Authoritative nameservers are configured by the domain owner and populated with the domain's DNS records.

**Common DNS record types served by authoritative nameservers:**

| Record | Purpose | Example |
|--|--|--|
| **A** | Domain → IPv4 address | `api.example.com. 300 IN A 151.101.65.121` |
| **AAAA** | Domain → IPv6 address | `api.example.com. 300 IN AAAA 2606:2800:220:1:248:1893:25c8:1946` |
| **CNAME** | Alias to another domain | `www.example.com. 3600 IN CNAME example.com.` |
| **MX** | Mail exchange server | `example.com. 3600 IN MX 10 mail.example.com.` |
| **NS** | Authoritative nameservers for a zone | `example.com. 86400 IN NS ns1.example.com.` |
| **TXT** | Arbitrary text (SPF, DKIM, domain verification) | `example.com. 3600 IN TXT "v=spf1 include:_spf.google.com ~all"` |
| **SRV** | Service discovery (host + port + priority) | `_https._tcp.example.com. 300 IN SRV 0 5 443 api.example.com.` |
| **PTR** | Reverse DNS (IP → domain) | `121.65.101.151.in-addr.arpa. 300 IN PTR api.example.com.` |
| **CAA** | Certificate Authority Authorisation | `example.com. 3600 IN CAA 0 issue "letsencrypt.org"` |
| **SOA** | Zone authority metadata | (see Q5) |

**CNAME constraints:** A CNAME record cannot coexist with other record types for the same name. This makes `CNAME` at the zone apex (the root of the domain, e.g., `example.com` itself) impossible — the apex must have NS and SOA records, which would conflict with a CNAME. Many DNS providers (Cloudflare, Route53, NS1) offer proprietary "CNAME flattening" or "ALIAS" record types that resolve the CNAME target and return the resulting A records, working around this constraint at the apex.

**Q12. What is the difference between a primary and secondary authoritative nameserver?**
A: DNS high availability requires multiple authoritative nameservers — the ICANN requires at least two for domain registration. Primary and secondary are roles in the zone data synchronisation model:

- **Primary nameserver** (also called master) — holds the master copy of the zone file. DNS administrators make record changes here. It is the source of truth for the zone's data. Identified in the SOA record's MNAME field.

- **Secondary nameserver** (also called slave) — holds a read-only copy of the zone file, obtained from the primary via **zone transfer**. It serves queries identically to the primary but does not accept direct record changes. Multiple secondaries provide redundancy and geographic distribution.

**Zone transfer mechanisms:**
- **AXFR (Authoritative Zone Transfer)** — full zone transfer. The secondary requests the complete zone file from the primary. Used when the secondary's copy is absent or significantly out of date.
- **IXFR (Incremental Zone Transfer)** — incremental zone transfer. The secondary sends its current SOA serial number; the primary responds with only the changes since that serial. More efficient for large zones with frequent small updates.

```bash
# Perform an AXFR zone transfer (if allowed by the primary's ACL)
dig @ns1.example.com example.com AXFR

# SOA serial comparison:
# Secondary checks primary's SOA serial vs its own (every 'refresh' seconds from SOA)
# If primary serial > secondary serial → initiate IXFR/AXFR
dig @ns1.example.com example.com SOA
```

**Modern managed DNS providers** (Route53, Cloudflare, NS1) abstract away the primary/secondary model entirely — they synchronise record changes across their distributed infrastructure internally and present a unified API for record management. The concept of AXFR zone transfers becomes irrelevant to the operator, though the provider implements similar internal replication.

**Q13. What is "glue record," and why is it needed?**
A: A glue record is an A or AAAA record for a nameserver that is **within the zone it is authoritative for** — a circular dependency that would otherwise make resolution impossible.

The problem:
```
To resolve example.com, I need to find ns1.example.com (the authoritative nameserver).
To find ns1.example.com, I need to resolve example.com.
→ Circular dependency — resolution is impossible without a shortcut.
```

The solution — glue records: when the TLD registry (Verisign for `.com`) stores the NS records for `example.com`, it also stores the IP addresses of those nameservers as glue records in the `.com` zone file:

```
# In the .com TLD zone (Verisign's servers):
example.com.     86400  IN  NS   ns1.example.com.
example.com.     86400  IN  NS   ns2.example.com.
ns1.example.com. 86400  IN  A    205.251.196.1    ← glue record
ns2.example.com. 86400  IN  A    205.251.197.1    ← glue record
```

When a recursive resolver asks the `.com` TLD nameserver about `example.com`, the response includes both the NS records AND the glue A records in the Additional section. The resolver can directly contact `205.251.196.1` without needing to resolve `ns1.example.com` first.

Glue records are required when the nameserver hostname is in the same or a child zone of the domain being delegated. They are stored at the parent zone (registrar/TLD level) and must be kept in sync with the nameserver's actual IP address — outdated glue records are a common cause of DNS resolution failure during nameserver IP changes.

## Section 5: TTL Caching

**Q14. What is TTL in DNS, and who controls it?**
A: TTL (Time To Live) is a 32-bit integer on every DNS resource record that specifies, in seconds, how long a recursive resolver or client may cache that record before it must be considered stale and re-queried from the authoritative nameserver.

**Who controls TTL:**
The **domain owner** sets the TTL on each record in the zone file at their authoritative nameserver. The TTL travels with the record in every DNS response. Resolvers and clients honour it — they may not cache longer than the TTL, though they are permitted to cache for less.

**TTL value tradeoffs:**

| TTL | Name | Characteristics | Use cases |
|--|--|--|--|
| 30–60s | Very short | Changes propagate in 1 minute; high query load on authoritative servers | Active failover, blue/green deployments, disaster recovery |
| 300s (5m) | Short | Reasonable propagation speed; moderate load | APIs with changing backends, staging environments |
| 3600s (1h) | Medium | Balanced — most common production choice | Standard web services, API endpoints |
| 86400s (1d) | Long | Minimal authoritative server load; slow propagation | Stable infrastructure (mail servers, rarely-changing records) |
| 604800s (1w) | Very long | Maximum caching efficiency | Static IP infrastructure, root/TLD records |

**TTL is not a strict expiry:** resolvers may start re-querying slightly before TTL expiry (pre-emptive refresh) or slightly after (grace period to avoid thundering herd). Some resolvers implement "stale-while-revalidate" — they serve an expired record while asynchronously refreshing it, reducing latency at the cost of briefly serving potentially stale data.

**Q15. What is the practical impact of TTL on deployments and how do you manage it?**
A: TTL is the DNS equivalent of a deployment propagation delay — you cannot make DNS changes take effect faster than the lowest TTL currently cached by resolvers worldwide:

**Pre-deployment TTL reduction (the standard pattern):**
```
Normal operations:   api.example.com. 3600 IN A 54.239.28.85   (TTL 1 hour)

Step 1 (24–48h before deployment):
  Reduce TTL:        api.example.com. 60 IN A 54.239.28.85    (TTL 60 seconds)
  Wait 1 hour for the old 3600s TTL to expire everywhere
  Now: all resolvers hold the record for at most 60 seconds

Step 2 (at deployment time):
  Change the IP:     api.example.com. 60 IN A 18.183.49.12    (new server)
  Maximum propagation delay: 60 seconds (the new short TTL)
  Most clients see the change in < 1 minute

Step 3 (after deployment is stable):
  Restore TTL:       api.example.com. 3600 IN A 18.183.49.12  (back to 1 hour)
```

If you skip Step 1 and change the IP directly with a 3600s TTL, some resolvers will continue sending traffic to the old IP for up to an hour — causing errors for any clients whose resolver cached the old record near the start of the TTL.

**Weighted routing and DNS-based load balancing:**
Route53, Cloudflare, and other GeoDNS providers use short TTLs (60–300s) to enable traffic shifting:
```
# Route53 weighted routing:
api.example.com. 60 IN A 54.239.28.85  (weight 90 — 90% of traffic)
api.example.com. 60 IN A 18.183.49.12  (weight 10 — 10% of traffic, canary)
```
The short TTL ensures that weight changes are reflected across clients within minutes, not hours.

**Q16. How does DNS caching work at multiple levels, and which level's cache does a request hit first?**
A: DNS resolution involves a cache hierarchy — each layer checks its cache before querying the next:

```
1. Browser DNS cache
   - Chrome, Firefox maintain their own DNS cache independent of the OS
   - Chrome: chrome://net-internals/#dns — view and flush cache
   - TTL respected; typically also has a minimum 1-second TTL floor
   - Checked first — fastest possible resolution

2. OS stub resolver cache
   - macOS: mDNSResponder / systemd-resolved (Linux)
   - Windows: DNS Client service
   - Checked second if not in browser cache
   - Command to flush:
     macOS: sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder
     Linux: sudo systemd-resolve --flush-caches
     Windows: ipconfig /flushdns

3. Local DNS server / dnsmasq / company resolver
   - Enterprise networks often run a local caching resolver
   - Checked third — still on local network, very fast

4. Recursive resolver (ISP / 8.8.8.8 / 1.1.1.1)
   - If none of the above has the answer, query the configured recursive resolver
   - Resolver checks its own cache (potentially huge — serves millions of queries)
   - Cache hit: returns answer in ~1–5ms
   - Cache miss: performs full iterative resolution (~50–150ms)

5. Authoritative nameserver
   - Only reached if recursive resolver's cache is cold
   - Returns the definitive answer with the TTL
```

**Practical implications for developers:**
- Flushing the browser cache and OS cache does not bypass the recursive resolver's cache. If you need to see a DNS change immediately, query the authoritative nameserver directly:
```bash
# Query authoritative nameserver directly (bypass all caches)
dig @ns1.example.com api.example.com A

# Query the recursive resolver (shows what the resolver has cached)
dig @8.8.8.8 api.example.com A

# Check current TTL remaining in the recursive resolver's cache
dig @8.8.8.8 api.example.com A | grep -i ttl
# The TTL in the response counts down — if you set 300s and the resolver cached 200s ago,
# the response shows TTL: 100 (300 - 200 elapsed seconds)
```

**Q17. What is negative caching, and what problems does it create?**
A: Negative caching is the caching of NXDOMAIN (non-existent domain) responses — when a domain does not exist, resolvers cache this fact for the duration specified by the SOA record's minimum TTL field.

**Why it exists:** without negative caching, every typo or probe for a non-existent domain would require a full iterative resolution to reach the authoritative nameserver. For popular non-existent names (misspellings of common domains), this would create unnecessary load.

**Problems negative caching creates:**

**Problem 1 — Newly created records not visible:**
```
Scenario:
  09:00 — Someone queries api.example.com. It doesn't exist yet → NXDOMAIN cached for 300s.
  09:01 — You create the A record for api.example.com.
  09:03 — The same resolver is queried for api.example.com.
           Resolver returns NXDOMAIN from cache (expires at 09:05).
           The record exists but is invisible to this resolver for 2 more minutes.
```
Fix: keep SOA minimum TTL short (60–300s) on zones where records are actively added. After a record is created, clients may need to wait up to the minimum TTL before they see it.

**Problem 2 — Kubernetes service discovery:**
Kubernetes uses DNS for service discovery. A new Service object creates a DNS record in CoreDNS. Pods that queried for the service name before it existed may have a cached NXDOMAIN for the duration of CoreDNS's negative cache TTL. Affected pods must wait or restart to clear the local DNS cache.

**Problem 3 — Wildcard DNS and NXDOMAIN:**
Some applications use wildcard DNS records (`*.example.com → 10.0.0.1`) expecting that any subdomain resolves. But NXDOMAIN is cached per-name — if a specific name (`temp.example.com`) was negatively cached before the wildcard was added, the wildcard won't be seen by that resolver until the negative cache expires.

## Section 6: Scenario / System Design Style Questions

**Q18. "A production deployment changed the IP address in DNS but users are still hitting the old server an hour later. Walk through what's happening and how to prevent it next time."**
A: This is a TTL propagation problem. The deployment changed the A record IP, but the record had a 3600s (1 hour) TTL. Resolvers that queried the old record at the start of the TTL window will continue to use the cached old IP for up to 60 more minutes, regardless of what the authoritative nameserver now says.

**What is happening:**
```
09:00 — Resolver A caches: api.example.com → 54.239.28.85, TTL 3600s (expires 10:00)
09:01 — Resolver B caches: api.example.com → 54.239.28.85, TTL 3600s (expires 10:01)
...
09:45 — DNS change: api.example.com → 18.183.49.12
09:46 — Resolver A queries api.example.com → returns 54.239.28.85 (cached until 10:00)
         User hits old server → error
09:46 — Resolver C (cold cache) queries api.example.com → 18.183.49.12 (new record)
         User hits new server → works
```

The divergence — some users on old, some on new — persists until all caches expire.

**How to diagnose:**
```bash
# Check what different resolvers currently have cached
dig @8.8.8.8 api.example.com A
dig @1.1.1.1 api.example.com A
dig @208.67.222.222 api.example.com A  # OpenDNS

# Query the authoritative nameserver directly (bypass all caches)
dig @$(dig api.example.com NS +short | head -1) api.example.com A

# Observe the TTL countdown — if < 3600s, it was cached before the change
dig @8.8.8.8 api.example.com A | grep -A1 "ANSWER"
# api.example.com. 2847 IN A 54.239.28.85
#                  ↑ 2847 seconds remaining on the old record
```

**Prevention — pre-deployment TTL reduction:**
```
T-48h: reduce TTL from 3600s to 60s on the A record
T-01h: all caches that held the 3600s TTL have expired and re-cached with 60s TTL
T+00h: deploy — change the IP
T+01m: propagation complete (max 60s TTL)
T+24h: restore TTL to 3600s
```

**Emergency mitigation if TTL reduction was not done:**
There is no way to force resolvers to evict cached records — TTL is a client-side expiry, not a server-side invalidation. Options:
- Keep both old and new servers running until all caches expire (max one TTL period).
- If the old server is inaccessible, configure it to redirect to the new server (if it is partially working) so users are bounced to the new IP.
- For services under your control, push a configuration update that overrides DNS (hard-coded new IP) — useful for mobile apps or internal services.

**Q19. "Design a DNS architecture for a high-availability fintech API that serves users across India with sub-50ms DNS resolution."**
A: A multi-layer DNS architecture optimised for latency and availability:

**Layer 1 — Authoritative DNS with GeoDNS:**
Use Route53 or Cloudflare (both have Indian PoPs) as the authoritative DNS provider. Configure latency-based or geolocation routing:
```
# Route53 latency routing:
api.example.com. 60 IN A 13.234.89.12   # ap-south-1 (Mumbai) — for Indian users
api.example.com. 60 IN A 52.221.30.45   # ap-southeast-1 (Singapore) — for SEA users
api.example.com. 60 IN A 52.54.218.49   # us-east-1 — for US users
```
Route53 returns the IP of the region with lowest measured latency to the querying resolver's location. Users in Delhi get the Mumbai IP; Route53's infrastructure is globally distributed and anycast — the authoritative query itself is answered from a nearby PoP.

**Layer 2 — Multiple authoritative nameservers:**
Register at least two NS records (Route53 provides 4 by default). All must be capable of answering independently. NS records have long TTLs (86400s) — changes to which nameservers are authoritative propagate slowly, so choose carefully.

**Layer 3 — Short TTLs for critical records:**
```
api.example.com.     60  IN A  13.234.89.12  # short TTL for fast failover
health.example.com.  30  IN A  13.234.89.12  # very short for health check records
mail.example.com.  3600  IN MX 10 smtp.example.com.  # stable — longer TTL fine
```

**Layer 4 — DNS health checks and failover:**
Route53 health checks monitor the endpoint. If `api.example.com` in Mumbai becomes unhealthy:
```
Route53 failover routing:
  Primary:  api.example.com → 13.234.89.12 (Mumbai) [health check: healthy]
  Secondary: api.example.com → 52.221.30.45 (Singapore) [promoted if primary fails]
```
With TTL=60, failover propagates within 60 seconds of Route53 detecting the failure.

**Layer 5 — Reduce DNS latency for clients:**
For mobile apps and internal services that make many DNS queries:
```
# Embed a local caching resolver in each service instance (reduces repeated lookup latency)
# Kubernetes: configure CoreDNS with appropriate cache TTL
# Mobile apps: cache resolved IPs in app memory for connection reuse
```

**Layer 6 — DNSSEC:**
Sign the zone with DNSSEC. Cloudflare and Route53 both provide managed DNSSEC. This is particularly important for a fintech service where DNS hijacking could redirect users to a fraudulent endpoint.

**Expected performance:**
- Warm cache (common case): ~1–5ms (resolver returns from cache)
- Cold cache, Route53 anycast: ~10–20ms to the authoritative server, ~50ms total resolution
- Sub-50ms target met for the majority of queries via caching and Indian PoP proximity

**Q20. "A microservice in Kubernetes is failing because DNS resolution for an internal service times out intermittently. How do you diagnose and fix this?"**
A: Kubernetes DNS is served by CoreDNS, which all pods use as their resolver. Intermittent timeouts in Kubernetes DNS are a well-documented operational problem with several known causes:

**Step 1 — Confirm DNS is the bottleneck**
```bash
# From inside the affected pod:
kubectl exec -it pod/service-pod -- bash

# Time a DNS query
time nslookup order-service.default.svc.cluster.local
# If this times out or takes > 100ms, DNS is the issue

# Check /etc/resolv.conf inside the pod
cat /etc/resolv.conf
# nameserver 10.96.0.10       ← CoreDNS cluster IP
# search default.svc.cluster.local svc.cluster.local cluster.local
# options ndots:5             ← KEY: ndots value
```

**Step 2 — The `ndots:5` problem (most common cause)**
Kubernetes sets `ndots:5` by default. This means: if a hostname has fewer than 5 dots, the resolver appends each search domain before trying the name as-is:
```
Query for: "order-service"
Attempts in order:
1. order-service.default.svc.cluster.local   ← success (1 lookup)
   (would resolve here — no problem in this case)

Query for: "api.external.example.com" (3 dots < 5)
Attempts in order:
1. api.external.example.com.default.svc.cluster.local → NXDOMAIN
2. api.external.example.com.svc.cluster.local         → NXDOMAIN
3. api.external.example.com.cluster.local             → NXDOMAIN
4. api.external.example.com                           → success (4th lookup!)
```
Every external DNS query makes 3 extra NXDOMAIN lookups before finding the answer. Under load, this triples the DNS query rate to CoreDNS and increases latency.

**Fix for ndots:**
```yaml
# In pod spec — use a trailing dot to force absolute lookup
# Or configure ndots explicitly
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "1"    # reduce from 5 to 1 for services making external calls
```
Or use fully qualified domain names (trailing dot) in code:
```typescript
// External: append trailing dot to bypass search domain expansion
const response = await fetch('https://api.external.example.com./orders');
// Internal: use full Kubernetes FQDN
const db = await connect('postgres-service.default.svc.cluster.local');
```

**Step 3 — CoreDNS conntrack table exhaustion (Linux kernel issue)**
A known kernel bug causes DNS packets to be dropped when the conntrack table is full. Symptoms: intermittent timeouts, not consistent, correlated with high pod count.
```bash
# Check conntrack table on the node
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
# If count ≈ max → conntrack exhaustion

# Fix: increase conntrack table size or switch CoreDNS to hostNetwork
# Alternative: use TCP for DNS (conntrack handles TCP better)
```

**Step 4 — CoreDNS resource limits**
If CoreDNS pods are CPU or memory throttled, DNS latency increases:
```bash
kubectl top pod -n kube-system -l k8s-app=kube-dns
# If CPU throttled: increase CoreDNS resource limits / add more CoreDNS replicas
```

**Step 5 — NodeLocal DNSCache**
The permanent fix for Kubernetes DNS performance: run a DNS cache on each node using a DaemonSet. Pods query the local cache (same node, sub-millisecond) instead of going to CoreDNS across the network:
```
Pod → NodeLocal DNSCache (node-local, 169.254.20.10)
      ├── Cache hit: ~0.1ms (no network hop)
      └── Cache miss: NodeLocal queries CoreDNS → returns and caches
```
NodeLocal DNSCache eliminates the conntrack issue (UDP to a link-local address doesn't go through conntrack) and reduces CoreDNS load by ~80% for cache-hit queries.

**Q21. "What is DNS hijacking, and how do DNSSEC and DoH/DoT prevent it?"**
A: DNS hijacking is the manipulation of DNS responses to redirect clients to different IP addresses than the domain owner intended. Attackers insert themselves into the DNS resolution path and return fraudulent answers:

**Attack vectors:**
- **Cache poisoning (Kaminsky attack)** — an attacker floods a recursive resolver with forged DNS responses containing a false IP for a target domain, hoping one arrives before the legitimate response. Once the resolver's cache is poisoned, all clients using it are misdirected.
- **Rogue resolver** — an attacker compromises the recursive resolver itself (ISP resolver hack, malware changing `/etc/resolv.conf`).
- **BGP hijacking** — an attacker announces a more specific route to the authoritative nameserver's IP, intercepting queries before they reach the real nameserver.
- **Man-in-the-middle** — on an untrusted network (public Wi-Fi), an attacker intercepts plaintext DNS queries and returns crafted responses.

**DNSSEC — cryptographic authentication of DNS data:**
DNSSEC adds digital signatures to DNS records. Each zone signs its records with a private key; the corresponding public key (DNSKEY record) is published in DNS and signed by the parent zone, forming a chain of trust from the root to the target domain:
```
Root zone signs → .com zone's DNSKEY
.com zone signs → example.com's DNSKEY
example.com signs → individual records (A, MX, etc.)

Validating resolver verifies the signature chain before trusting the response.
A forged or tampered response has an invalid or missing signature → rejected.
```
DNSSEC prevents cache poisoning and BGP-based record tampering, but does not encrypt queries — an eavesdropper can still see which domains are being queried.

**DoH (DNS over HTTPS) and DoT (DNS over TLS) — encrypted transport:**
Both encrypt DNS queries and responses between the stub resolver and the recursive resolver:
- **DoT** — DNS queries wrapped in TLS, port 853. Simple encryption; identifiable as DNS by DPI (Deep Packet Inspection) because it uses a dedicated port.
- **DoH** — DNS queries wrapped in HTTPS (looks like regular web traffic), port 443. Indistinguishable from HTTPS traffic by network observers; harder for ISPs or firewalls to block.

```
Without DoH/DoT:
  Client → [plaintext DNS query] → Resolver
  ISP/attacker can see: "User queried api.example.com"
  MITM can inject false response

With DoH/DoT:
  Client → [encrypted DNS query] → Resolver (8.8.8.8 or 1.1.1.1)
  ISP sees: encrypted HTTPS traffic (DoH) or TLS stream on port 853 (DoT)
  MITM cannot inject — TLS certificate validation prevents it
```

**Combined defence:** DNSSEC + DoH/DoT together provide both data authenticity (DNSSEC — the record hasn't been tampered with) and transport privacy (DoH/DoT — no one can see what you're querying). Neither alone is sufficient: DNSSEC without encryption reveals your queries to observers; DoH without DNSSEC protects the transport but not against a compromised resolver returning false data.

**Q22. "How does DNS-based service discovery work in a microservice architecture, and what are its limitations?"**
A: DNS-based service discovery uses DNS as the registry for service endpoints. When a service is deployed, it registers a DNS record; clients discover the service's address by resolving its name.

**Kubernetes service discovery:**
Every Kubernetes Service automatically gets a DNS record in CoreDNS:
```
service-name.namespace.svc.cluster.local → ClusterIP (virtual IP)

# Service: order-service in namespace: production
order-service.production.svc.cluster.local → 10.96.45.123

# Headless service (no ClusterIP) — returns individual pod IPs directly
order-service-headless.production.svc.cluster.local → 10.244.1.5, 10.244.2.8, ...
```

**SRV records for port discovery:**
SRV records encode both the hostname and port, enabling clients to discover the service's port without hardcoding it:
```
_grpc._tcp.order-service.production.svc.cluster.local →
  SRV 0 5 50051 order-service.production.svc.cluster.local
  ↑priority ↑weight ↑port ↑hostname
```
gRPC clients can perform SRV lookups to discover service endpoints and their ports dynamically.

**DNS round-robin for load balancing:**
A DNS name can return multiple A records — clients typically use the first, or cycle through them:
```
api.example.com → 10.0.1.1, 10.0.1.2, 10.0.1.3  (three backend instances)
```
This is simple load distribution but has significant limitations.

**Limitations of DNS-based service discovery:**

- **TTL propagation delay** — when a backend is removed (scaling down, failure), the DNS record is updated but clients that cached the old record continue trying to connect to the removed instance for up to TTL seconds. Health checks in the client (not DNS) must handle this.
- **No health awareness** — standard DNS returns all records regardless of health. A DNS round-robin that includes an unhealthy backend continues sending ~33% of traffic to it until the TTL expires and the record is removed. Proper health-aware load balancing requires a service mesh or L7 load balancer.
- **No connection-level load balancing** — DNS load balancing happens at connection time (one lookup → one IP). A client that holds one long-lived connection to one backend is not load-balanced across the pool.
- **Negative caching for new services** — as discussed in Q17, a client that queried for a service name before it existed may have a cached NXDOMAIN, delaying discovery of new services.
- **No metadata** — DNS records carry IP:port but no additional metadata (health status, version, canary weight). Service meshes (Istio, Linkerd) add this metadata via control plane configuration rather than DNS.

**Q23. "What happens to DNS resolution when there is a network partition between a service and its recursive resolver?"**
A: A network partition between a service and its recursive resolver is a surprisingly common failure mode — the resolver (often a VPC-internal DNS server) becomes unreachable while the service itself has internet connectivity through a different path.

**Immediate impact:**
New DNS queries time out. The OS resolver typically retries 2–3 times with increasing timeouts before returning `SERVFAIL` or a timeout error to the application. In Node.js, this manifests as `ENOTFOUND` or `EAI_AGAIN`; in Java, as `UnknownHostException`.

**What is NOT immediately broken:**
OS and application-level DNS caches continue serving cached records for their remaining TTL. A service that successfully resolved `order-service.example.com` 10 minutes ago and cached the result with a 300s TTL will continue working for the remaining TTL — then fail as caches expire.

**Mitigation strategies:**

**1 — Local DNS cache (dnsmasq, Unbound, systemd-resolved):**
Running a caching resolver locally extends the effective cache lifetime and provides a local fallback:
```
# systemd-resolved caches aggressively and can serve stale records
# When upstream resolver is unreachable, it serves the last known answer
```

**2 — Multiple resolvers configured:**
Configure multiple nameservers in `/etc/resolv.conf`:
```
nameserver 10.0.0.2   # primary (VPC resolver)
nameserver 8.8.8.8    # fallback (public resolver)
nameserver 1.1.1.1    # second fallback
options timeout:1 attempts:2
```
If the first resolver times out after 1 second, the OS retries with the next.

**3 — Application-level DNS caching:**
Cache resolved IPs in the application layer with TTL tracking:
```typescript
const dnsCache = new Map<string, { ip: string; expiresAt: number }>();

async function resolveWithCache(hostname: string): Promise<string> {
  const cached = dnsCache.get(hostname);
  if (cached && Date.now() < cached.expiresAt) return cached.ip;

  const { address, ttl } = await dns.promises.resolve4(hostname, { ttl: true });
  dnsCache.set(hostname, { ip: address[0], expiresAt: Date.now() + ttl * 1000 });
  return address[0];
}
```

**4 — Pre-resolve and connection pooling:**
HTTP connection pools that reuse connections avoid DNS for every request — once a connection to `order-service` is established, subsequent requests on the same connection don't need DNS. A partition that starts after connections are established is invisible to the application until those connections are recycled.

**5 — Graceful degradation:**
Design services to degrade gracefully when dependencies become temporarily unresolvable — return cached responses, serve from local state, queue writes for retry — rather than failing hard on DNS timeout.

**Q24. "Explain how Route53's latency-based routing and health checks work together to implement DNS failover."**
A: Route53 latency-based routing with health checks implements automatic DNS-level failover — the combination of "return the lowest-latency endpoint" and "don't return endpoints that are failing":

**How latency routing works:**
Route53 measures and maintains a latency database between AWS regions and resolver locations worldwide. When a recursive resolver in, say, Delhi queries for `api.example.com`, Route53 uses the resolver's IP to determine that Delhi resolvers have lower latency to `ap-south-1` (Mumbai) than to `us-east-1` (Virginia) and returns the Mumbai IP:

```
Route53 latency routing records:
api.example.com. 60 IN A 13.234.89.12   # ap-south-1 (Mumbai)    — returned to Indian resolvers
api.example.com. 60 IN A 54.239.28.85   # us-east-1 (Virginia)   — returned to US resolvers
api.example.com. 60 IN A 52.221.30.45   # ap-southeast-1 (Singapore) — returned to SEA resolvers
```

**How health checks integrate:**
Each latency routing record can be associated with a Route53 health check:
```
Health check for 13.234.89.12:
  Protocol: HTTPS
  Path: /health
  Check interval: 30s
  Failure threshold: 3 consecutive failures → unhealthy
  Success threshold: 2 consecutive successes → healthy
```

When the Mumbai endpoint becomes unhealthy (health check fails 3 consecutive times):
1. Route53 marks the Mumbai record as unhealthy.
2. Subsequent DNS queries from Indian resolvers receive the next lowest-latency healthy record — Singapore or US, depending on latency measurements.
3. The short TTL (60s) means this failover is visible to new connections within 60 seconds.
4. When Mumbai recovers (2 consecutive successes), Route53 marks it healthy and Indian resolvers return to receiving the Mumbai IP.

**Limitations of DNS failover:**
- **TTL-bounded failover time** — even with 60s TTL, clients that cached the Mumbai IP just before it failed will continue hitting it for up to 60 seconds. DNS failover is not instant.
- **Cached IP in applications** — application-level DNS caches (HTTP connection pools, OS cache) may hold the failing IP beyond the DNS TTL. Connection-level health checks (TCP keepalive, HTTP keepalive timeouts) are needed to detect and replace failed connections.
- **Resolver propagation** — Route53's change is near-instant, but resolvers worldwide must expire their caches before seeing the new record. This is why 60s TTL is necessary for effective DNS failover — 3600s TTL makes DNS failover nearly useless.
- **DNS is not a health router** — DNS returns an IP; the client's TCP stack must still establish a connection and discover if the server is actually responsive. True zero-downtime failover requires L4/L7 health checking at the connection level, not just DNS level.

**Q25. "Walk me through what a backend engineer needs to understand about DNS to debug the full lifecycle of a failed API call from a mobile app in India."**
A: A mobile app in Mumbai calling `https://api.mypayments.in/transfer` that fails — the DNS component of that failure investigation:

**Step 1 — Identify if DNS is involved**
```
Error: "Network request failed" / "ERR_NAME_NOT_RESOLVED" / "UnknownHostException"
→ DNS failed to resolve the hostname
→ Distinct from: "Connection refused" (DNS worked, but nothing listening at the IP)
→ Distinct from: "Connection timed out" (DNS worked, IP unreachable at network level)
→ Distinct from: "SSL certificate error" (DNS worked, connection established, TLS failed)
```

**Step 2 — Identify which DNS layer failed**
```bash
# From a machine with similar connectivity to the mobile user:

# 1. Can we resolve via the recursive resolver?
dig @1.1.1.1 api.mypayments.in A
# If SERVFAIL or timeout → recursive resolver can't reach authoritative
# If NXDOMAIN → domain doesn't exist (or negative cache)
# If answer → DNS is working, problem is elsewhere

# 2. Is the authoritative nameserver reachable?
dig api.mypayments.in NS     # find the authoritative nameservers
dig @ns1.mypayments.in api.mypayments.in A  # query authoritative directly
# If different from what recursive resolver returns → cache issue or DNSSEC failure

# 3. What TTL is remaining?
dig @1.1.1.1 api.mypayments.in A | grep -i "answer section" -A 5
# api.mypayments.in. 45 IN A 13.234.89.12
#                    ↑ 45 seconds remaining — was cached 255s ago (TTL=300)
```

**Step 3 — Check for DNSSEC issues**
```bash
# Validate DNSSEC chain
dig +dnssec api.mypayments.in A
# If AD (Authenticated Data) flag is set → DNSSEC validated
# If SERVFAIL with +dnssec → DNSSEC validation failed (misconfigured DNSSEC)

# Use DNSSEC debugger
delv @1.1.1.1 api.mypayments.in A +rtrace
```

**Step 4 — Check GeoDNS and what Indian resolvers see**
```bash
# Use a resolver known to be in India to simulate mobile user's DNS
dig @103.87.68.68 api.mypayments.in A    # BSNL resolver (India)
dig @122.160.0.1 api.mypayments.in A     # Airtel India resolver

# Compare with US resolver — GeoDNS should return different IPs
dig @8.8.8.8 api.mypayments.in A
```

**Step 5 — Check TTL and propagation if recent change**
```bash
# Was a DNS change made recently?
# Check the SOA serial number — higher than expected → recent change
dig api.mypayments.in SOA

# Check what TTL the authoritative nameserver is advertising
dig @ns1.mypayments.in api.mypayments.in A
# If TTL=3600 and a change was made 30 minutes ago → some resolvers still have old IP

# Check if old IP is still responding
curl -v --resolve api.mypayments.in:443:OLD_IP https://api.mypayments.in/health
```

**Step 6 — Mobile-specific considerations**
Mobile apps often cache DNS resolutions in the HTTP client layer beyond the OS DNS TTL. OkHttp (Android), NSURLSession (iOS), and Retrofit all have connection pools that reuse connections without re-resolving DNS for each request. A mobile user whose app established a connection before a failover may not see the new IP until the connection is recycled (app restart, connection timeout, or explicit connection close).

**Remediation:**
- If DNSSEC is misconfigured → fix the DS record at the registrar or disable DNSSEC temporarily.
- If a TTL issue → wait for TTL expiry; consider pre-emptive TTL reduction before future changes.
- If GeoDNS is returning wrong region → check Route53 health check status; verify latency routing configuration.
- If the authoritative nameserver is unreachable → check NS records, verify nameserver is running and reachable on UDP/53.
- If mobile app DNS cache → implement in-app health checks and connection retry logic that forces re-resolution on repeated failure.

The strongest answers treat TTL not as a configuration detail but as a first-class operational constraint — knowing that a 3600s TTL means a 1-hour migration window, and that pre-deployment TTL reduction to 60s is the standard mitigation. Have a concrete story: a deployment where the DNS change propagated within 2 minutes because you reduced the TTL 48 hours in advance, the `dig +trace` output that revealed a DNSSEC misconfiguration, or the Kubernetes `ndots:5` problem that tripled CoreDNS query load — those contextualised answers are what land at 5 YOE.
