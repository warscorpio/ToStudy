# AWS IAM: Users, Roles, Policies, Assume Role, Instance Profiles, Least Privilege — Interview Q&A (5 YOE Level)

---

## Section 1: IAM Fundamentals — Identities and the Authorization Model

**Q1. What is the IAM authorization model, and what are the core components?**
A: IAM (Identity and Access Management) is AWS's global authorization system. Every API call in AWS goes through IAM — no action on any resource can occur without IAM evaluating whether the calling principal is authorized. The model has four core components: principals, policies, resources, and the policy evaluation logic.

**The IAM request evaluation model:**

```
Every AWS API call produces an authorization context:
  Principal:  WHO is making the request?
              (IAM user, IAM role, AWS service, federated identity)
  Action:     WHAT are they trying to do?
              (s3:GetObject, ec2:RunInstances, sts:AssumeRole)
  Resource:   ON WHAT are they doing it?
              (arn:aws:s3:::my-bucket/*, arn:aws:ec2:*:*:instance/*)
  Conditions: UNDER WHAT CIRCUMSTANCES?
              (source IP, MFA present, time of day, request tag values)

IAM evaluates all applicable policies and makes a binary decision: ALLOW or DENY.

Default: IMPLICIT DENY
  If no policy explicitly allows an action → request is denied.
  You must explicitly grant every permission you want to allow.

Explicit DENY wins over everything:
  Even if 10 policies allow s3:DeleteBucket, a single policy with an
  explicit Deny on s3:DeleteBucket blocks the action.
  Explicit Deny is the mechanism for guardrails (SCPs, permission boundaries).
```

**The full policy evaluation order:**

```
For every API call, IAM evaluates in this order:

1. Service Control Policies (SCPs) — Organization-level guardrails
   If SCP doesn't allow the action → DENY (regardless of IAM policies)
   SCPs are a ceiling, not a grant — they restrict what's possible,
   they do not grant permissions themselves.

2. Resource-based policies (S3 bucket policy, KMS key policy, SQS queue policy)
   Evaluated alongside identity policies for cross-account access.

3. IAM permission boundaries
   If a boundary is set on a principal, effective permissions =
   intersection of identity policies AND boundary.
   A policy grants s3:* but boundary only allows s3:GetObject →
   effective permission: s3:GetObject only.

4. Identity-based policies (attached to the IAM user or role)
   Inline policies + managed policies attached to the principal.

5. Session policies (for assumed roles)
   When a role is assumed with --policy flag, that session policy
   further restricts permissions for that session only.

6. Explicit DENY at any layer → final result: DENY
   ALLOW only if: no explicit deny at any layer AND at least one
   explicit allow in the applicable policies.
```

**Q2. What is the difference between an IAM User and an IAM Role?**
A: Both are IAM principals — entities that can make authenticated AWS API calls. The key distinction is how they authenticate and how long their credentials live.

**IAM User:**

```
A long-lived identity associated with a specific human or application.
Credentials:
  Password:          for AWS Console access
  Access Key ID +
  Secret Access Key: for programmatic access (CLI, SDK)

Properties:
  Static credentials — the same key pair until rotated or deleted.
  Credentials live forever unless explicitly rotated or deactivated.
  Belong to one AWS account; cannot span accounts natively.
  Can have MFA device attached for Console login enforcement.

When to use IAM Users:
  Human administrators who need Console access.
  Legacy CI/CD pipelines that cannot use role assumption.
  Third-party tools that require static access keys and cannot use roles.

When NOT to use IAM Users (most modern cases):
  EC2 instances, Lambda, ECS tasks → use IAM Roles (instance profiles / task roles).
  CI/CD pipelines (GitHub Actions, GitLab) → use OIDC federation → role assumption.
  Cross-account access → use IAM Roles, not user credentials shared across accounts.
  The fundamental problem with IAM Users: static credentials get leaked.
  A rotated key still has a window; a leaked key is compromised until deactivated.
```

**IAM Role:**

```
A temporary identity assumed by a principal (user, service, account, OIDC provider).
Credentials:
  Temporary Security Credentials issued by AWS STS:
    AccessKeyId      — changes every session
    SecretAccessKey  — changes every session
    SessionToken     — required on all API calls; ties to this session
    Expiration       — default 1 hour; configurable 15 min – 12 hours

Properties:
  No long-term credentials — no password, no permanent access key.
  Assumed by principals that meet the Trust Policy conditions.
  Can be assumed from any account (cross-account roles) or service.
  Each assumption creates a fresh session with fresh credentials.

Why roles are fundamentally safer than users:
  A leaked temporary credential expires in 1–12 hours max.
  A leaked IAM User access key is valid indefinitely until deactivated.
  Roles enable the principle of no long-lived static credentials.
```

**Side-by-side comparison:**

| Dimension               | IAM User                          | IAM Role                                    |
|-------------------------|-----------------------------------|---------------------------------------------|
| Credential type         | Static (long-lived)               | Temporary STS tokens (15 min – 12 hours)    |
| Who uses it             | Humans, legacy apps               | Services, applications, CI/CD, cross-account |
| Credential rotation     | Manual or automated (key rotation) | Automatic (STS issues fresh creds per session) |
| Cross-account access    | Share keys (insecure)             | Native (assume role across accounts)        |
| Credential leakage risk | High (permanent until rotated)    | Low (self-expires)                          |
| MFA enforcement         | Per-user MFA device               | MFA condition in trust or session policy    |
| AWS recommendation      | Minimize usage                    | Prefer for all non-human access             |

## Section 2: IAM Policies — Identity vs Resource

**Q3. What is the difference between identity-based policies and resource-based policies?**
A: The distinction determines where the policy is attached and which direction the authorization flows. Identity-based policies travel with the principal; resource-based policies are attached to the resource itself.

**Identity-based policies:**

```
Attached to: IAM user, IAM group, IAM role.
Defines: what the attached principal CAN do and to which resources.

Example — identity policy attached to a NestJS API role:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadAppConfig",
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParametersByPath"
      ],
      "Resource": "arn:aws:ssm:ap-south-1:123456789012:parameter/prod/nestjs-api/*"
    },
    {
      "Sid": "WriteMetrics",
      "Effect": "Allow",
      "Action": "cloudwatch:PutMetricData",
      "Resource": "*"
    },
    {
      "Sid": "ReadS3Assets",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::prod-nestjs-assets",
        "arn:aws:s3:::prod-nestjs-assets/*"
      ]
    }
  ]
}

The role carrying this policy can:
  ✅ Read SSM parameters under /prod/nestjs-api/
  ✅ Put CloudWatch metrics
  ✅ Read objects from prod-nestjs-assets S3 bucket
  ❌ Anything else (implicit deny)
```

**Resource-based policies:**

```
Attached to: the resource itself (S3 bucket, SQS queue, KMS key,
             Lambda function, SNS topic, ECR repository, etc.)
Defines: which principals can act on this resource.

A principal field is REQUIRED — resource policies must name who is allowed.

Example — S3 bucket policy:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowNestjsAPIReadAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/NestjsApiRole"
      },
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::prod-nestjs-assets",
        "arn:aws:s3:::prod-nestjs-assets/*"
      ]
    },
    {
      "Sid": "DenyPublicAccess",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::prod-nestjs-assets/*",
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    }
  ]
}

Resource policies answer: "who is allowed to come to me?"
Identity policies answer: "where is this principal allowed to go?"
```

**The key authorization interaction between identity and resource policies:**

```
Same account (principal and resource in the same AWS account):
  Access is granted if EITHER the identity policy OR the resource policy allows it.
  (They complement each other — only one needs to grant access.)

  Example: NestJS role has NO identity policy for S3, but the S3 bucket
  policy explicitly allows NestjsApiRole → ACCESS GRANTED.

Cross account (principal in Account A, resource in Account B):
  BOTH must allow the access:
    Identity policy in Account A must allow the action on the resource in Account B.
    Resource policy in Account B must allow the principal from Account A.
  If either is missing → ACCESS DENIED.

  This two-lock model is intentional: Account B cannot unilaterally grant
  access to Account A principals without Account A's identity policy also
  permitting the cross-account action.

Services with resource-based policies:
  S3 (bucket policies)       KMS (key policies — mandatory; no identity-only access)
  SQS (queue policies)       Lambda (function policies — for cross-account invocation)
  SNS (topic policies)       ECR (repository policies — cross-account image pull)
  API Gateway (resource policy)  Secrets Manager (secret resource policy)

Services WITHOUT resource-based policies (identity policy only):
  EC2, RDS, DynamoDB, ElastiCache, EKS — access is controlled via
  identity policies on the principal, not policies on the resource.
```

**Q4. What are managed policies vs inline policies, and when do you use each?**
A: Managed policies are standalone IAM policy documents that can be attached to multiple principals. Inline policies are embedded directly into a single principal and exist only as long as that principal exists.

**AWS Managed Policies:**

```
Created and maintained by AWS. Examples:
  AmazonS3ReadOnlyAccess
  AmazonEC2FullAccess
  CloudWatchAgentServerPolicy
  AWSLambdaBasicExecutionRole

Use when:
  The policy represents a well-known, generic permission set.
  AWS keeps them updated when new service features launch.

Do NOT use AWS Managed policies for production applications:
  AmazonS3ReadOnlyAccess allows s3:GetObject on ALL buckets in your account.
  This violates least privilege — your NestJS API should only read
  the specific buckets it needs, not every S3 bucket in the account.
  AWS Managed policies are broad by design (they suit everyone → too permissive for anyone).
```

**Customer Managed Policies (recommended for production):**

```
You create and maintain them. Reusable across multiple roles.

When to use:
  Permission sets shared across multiple roles:
    "All our API services need SSM read access" → one policy, attached to all API roles.
  Permission sets that need version control and change tracking.
  Any production application with a defined permission surface.

Best practice:
  Store policy JSON in your IaC (Terraform, CDK).
  Version control the policy document alongside the service it governs.
  Name policies semantically: NestjsApiSSMReadPolicy, KafkaConsumerSQSPolicy.

Limit: 10 managed policies per principal (IAM soft limit, adjustable).
       Policy document size: 6,144 characters (managed) / 2,048 (inline).
```

**Inline Policies:**

```
Embedded directly into one user, group, or role.
Deleted when the parent principal is deleted.

When to use:
  One-off permissions that should never be reused elsewhere.
  Ensuring a specific permission is tightly coupled to one principal's lifecycle.
  Enforcement that a permission should NOT be shared.

When NOT to use:
  As a substitute for customer managed policies on shared permission sets.
  Large permission sets — they are harder to audit (not searchable/listable
  without iterating every principal).

Terraform example:
  resource "aws_iam_role_policy" "inline" {  # inline
    role   = aws_iam_role.api.name
    policy = data.aws_iam_policy_document.api_ssm.json
  }
  resource "aws_iam_policy" "managed" {  # managed (reusable)
    name   = "NestjsApiSSMReadPolicy"
    policy = data.aws_iam_policy_document.api_ssm.json
  }
  resource "aws_iam_role_policy_attachment" "attach" {
    role       = aws_iam_role.api.name
    policy_arn = aws_iam_policy.managed.arn
  }
```

## Section 3: IAM Roles — Trust Policies and Assume Role

**Q5. What is a Trust Policy, and how does it work with AssumeRole?**
A: A Trust Policy (also called the assume-role policy document) is a resource-based policy attached to an IAM role that defines WHO is allowed to assume the role. Without a trust policy, no principal can assume the role regardless of what permissions the role carries.

**Trust Policy anatomy:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowEC2Assumption",
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    },
    {
      "Sid": "AllowCrossAccountDevops",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::987654321098:role/DevopsDeployRole"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "Bool": {
          "aws:MultiFactorAuthPresent": "true"
        }
      }
    },
    {
      "Sid": "AllowGitHubOIDC",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:myorg/nestjs-api:*"
        }
      }
    }
  ]
}
```

**Principal types in trust policies:**

```
AWS Service:
  "Principal": { "Service": "ec2.amazonaws.com" }
  Used for: EC2 instance profiles, Lambda execution roles, ECS task roles,
            any AWS service that needs to assume the role on your behalf.
  Common services: ec2.amazonaws.com, lambda.amazonaws.com,
                   ecs-tasks.amazonaws.com, apigateway.amazonaws.com,
                   scheduler.amazonaws.com (EventBridge Scheduler).

AWS IAM Principal:
  "Principal": { "AWS": "arn:aws:iam::ACCOUNT:role/RoleName" }
  "Principal": { "AWS": "arn:aws:iam::ACCOUNT:user/UserName" }
  "Principal": { "AWS": "arn:aws:iam::ACCOUNT:root" }  ← entire account (use carefully)
  Used for: cross-account access, role chaining, human assumption with MFA.

Federated / OIDC provider:
  "Principal": { "Federated": "arn:aws:iam::ACCOUNT:oidc-provider/..." }
  Action: sts:AssumeRoleWithWebIdentity
  Used for: GitHub Actions, GitLab CI, Google Workload Identity, Kubernetes IRSA.
  Eliminates static access keys for CI/CD pipelines entirely.
```

**The AssumeRole API call and credential lifecycle:**

```
Caller (e.g., a DevOps engineer's CLI session or a GitHub Actions runner):

aws sts assume-role \
  --role-arn arn:aws:iam::123456789012:role/ProdDeployRole \
  --role-session-name "github-deploy-$(date +%s)" \
  --duration-seconds 3600

Response from STS:
{
  "Credentials": {
    "AccessKeyId":     "ASIA...",        # Temporary; starts with ASIA
    "SecretAccessKey": "wJalrXUtn...",   # Changes every session
    "SessionToken":    "AQoDYXdz...",    # Must be passed on every API call
    "Expiration":      "2026-08-07T10:00:00Z"
  },
  "AssumedRoleUser": {
    "AssumedRoleId": "AROA...:github-deploy-1723006800",
    "Arn": "arn:aws:iam::123456789012:assumed-role/ProdDeployRole/github-deploy-1723006800"
  }
}

The caller then uses these temporary credentials for the session duration.
All CloudTrail events show the AssumedRoleUser ARN — you can trace which session
(github-deploy-...) performed which action, even though many sessions share one role.

Session duration:
  Minimum: 900 seconds (15 minutes)
  Default:  3600 seconds (1 hour)
  Maximum:  43200 seconds (12 hours) — only if the role's MaxSessionDuration allows it
            (configurable per role; default max is 1 hour)

Role chaining:
  Role A assumes Role B assumes Role C.
  Maximum chained session duration: 1 hour (cannot exceed, regardless of MaxSessionDuration).
  Each hop in a chain reduces the remaining session duration.
  Avoid deep role chains — they increase latency and complicate debugging.
```

**Q6. What is cross-account role assumption, and how is it configured?**
A: Cross-account role assumption is the mechanism for granting principals in one AWS account (Account A) permission to act in another AWS account (Account B) without sharing any credentials. It is the foundational pattern for multi-account AWS architectures.

**The two-sided handshake:**

```
Account A (111111111111): DevOps team, CI/CD pipelines
Account B (222222222222): Production environment

Step 1 — Account B creates a role with a trust policy allowing Account A:
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::111111111111:role/CiCdPipelineRole"
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "a94f5374-ffc4-4b7b-89e7-9cf291c4"
      }
    }
  }]
}

The role in Account B (ProdDeployRole) has permissions to deploy:
  ec2:CreateLaunchTemplateVersion, autoscaling:StartInstanceRefresh,
  s3:PutObject on the prod artifact bucket, etc.

Step 2 — Account A's role must have permission to call AssumeRole:
Identity policy on CiCdPipelineRole in Account A:
{
  "Statement": [{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::222222222222:role/ProdDeployRole"
  }]
}

Step 3 — Account A's principal calls AssumeRole:
aws sts assume-role \
  --role-arn     arn:aws:iam::222222222222:role/ProdDeployRole \
  --role-session-name "ci-deploy" \
  --external-id  "a94f5374-ffc4-4b7b-89e7-9cf291c4"

The ExternalId condition (confused deputy prevention):
  Without ExternalId: if Account A's role ARN is known, any service that can
  call AssumeRole as Account A can assume the prod role — including a malicious
  service that tricks Account A into deploying to prod on its behalf.
  With ExternalId: only callers that know the secret ExternalId value can assume
  the role. The ExternalId is agreed between Account A and Account B out of band.
  Mandatory when granting cross-account access to third-party services
  (e.g., a monitoring SaaS, a security scanning vendor).
```

**Common multi-account patterns:**

```
Hub-and-spoke (most common in fintech):
  Account 0 (Management/Root): AWS Organizations, SCPs, billing
  Account 1 (Security):        CloudTrail aggregation, GuardDuty master,
                                SecurityHub, Config rules
  Account 2 (Shared Services): ECR, Route53 private zones, Transit Gateway
  Account 3 (Dev):             Developer sandboxes
  Account 4 (Staging):         Pre-prod environment
  Account 5 (Production):      Production workloads

Role assumption flow:
  DevOps in Account 1 (Security) assumes roles in Account 4 and Account 5
  to perform deployments. No credentials ever cross account boundaries.
  CloudTrail in Account 1 records the cross-account assumption;
  CloudTrail in Account 5 records what the assumed role did in production.
```

## Section 4: Instance Profiles

**Q7. What is an EC2 Instance Profile, and how does it work?**
A: An EC2 Instance Profile is a container that holds exactly one IAM Role and passes that role's credentials to an EC2 instance. It is the mechanism that allows EC2 instances (and the applications running on them) to make AWS API calls without any static access keys on the instance.

**How Instance Profile credential delivery works:**

```
EC2 Launch:
  Instance launches with an Instance Profile assigned.
  EC2 service calls sts:AssumeRole internally, using the ec2.amazonaws.com
  service principal (which is why the role's trust policy must allow ec2.amazonaws.com).
  Temporary credentials are delivered to the EC2 Instance Metadata Service (IMDS).

Application retrieves credentials:
  AWS SDKs and CLI automatically query IMDS for credentials — no code change needed.
  IMDSv2 (required in secure deployments):

  TOKEN=$(curl -sf -X PUT http://169.254.169.254/latest/api/token \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

  curl -sf http://169.254.169.254/latest/meta-data/iam/security-credentials/ \
    -H "X-aws-ec2-metadata-token: $TOKEN"
  # Returns: NestjsApiRole

  curl -sf http://169.254.169.254/latest/meta-data/iam/security-credentials/NestjsApiRole \
    -H "X-aws-ec2-metadata-token: $TOKEN"
  # Returns:
  # {
  #   "AccessKeyId":     "ASIA...",
  #   "SecretAccessKey": "...",
  #   "Token":           "...",
  #   "Expiration":      "2026-08-07T10:00:00Z"
  # }

Credential rotation:
  EC2 automatically rotates the credentials before expiration.
  The application (via SDK) transparently picks up the new credentials.
  No application restart, no deployment needed.
  The credentials rotate approximately every 6 hours (AWS internal policy).
```

**Instance Profile vs IAM Role — the distinction:**

```
IAM Role:  the permission set (policies attached; trust policy defined).
Instance Profile: the wrapper that binds the role to an EC2 instance.

In the AWS Console, creating a role with EC2 as the trusted service
automatically creates a matching Instance Profile.

In Terraform/CloudFormation, you must create both explicitly:

# Terraform
resource "aws_iam_role" "nestjs_api" {
  name = "NestjsApiRole"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
      Action    = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_instance_profile" "nestjs_api" {
  name = "NestjsApiInstanceProfile"
  role = aws_iam_role.nestjs_api.name
  # One role per instance profile; one instance profile per EC2 instance
}

resource "aws_launch_template" "nestjs_api" {
  iam_instance_profile {
    arn = aws_iam_instance_profile.nestjs_api.arn
  }
}

Error seen in prod if you forget to create the Instance Profile:
  "No instance profile defined" when using a Launch Template,
  or "InvalidParameterValue: Value must be an ARN" when specifying
  the role ARN directly (you must use the instance profile ARN, not the role ARN).
```

**Q8. What permissions does an EC2 instance actually need for a typical NestJS API?**
A: Start with zero permissions and add only what the application's code actually calls. The pattern is: trace every AWS SDK call in the application → grant exactly those actions on exactly those resources.

**Minimum viable role for a NestJS API on EC2:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SSMParameterRead",
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParametersByPath"
      ],
      "Resource": "arn:aws:ssm:ap-south-1:123456789012:parameter/prod/nestjs-api/*"
    },
    {
      "Sid": "SecretsManagerRead",
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:ap-south-1:123456789012:secret:prod/nestjs-api/*"
    },
    {
      "Sid": "S3AssetsBucketRead",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::prod-nestjs-assets",
        "arn:aws:s3:::prod-nestjs-assets/*"
      ]
    },
    {
      "Sid": "S3UploadsBucketWrite",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::prod-nestjs-uploads/*"
    },
    {
      "Sid": "SQSJobQueue",
      "Effect": "Allow",
      "Action": [
        "sqs:SendMessage",
        "sqs:ReceiveMessage",
        "sqs:DeleteMessage",
        "sqs:GetQueueAttributes"
      ],
      "Resource": "arn:aws:sqs:ap-south-1:123456789012:prod-nestjs-jobs"
    },
    {
      "Sid": "CloudWatchMetrics",
      "Effect": "Allow",
      "Action": "cloudwatch:PutMetricData",
      "Resource": "*"
    },
    {
      "Sid": "CloudWatchAgentLogs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "logs:DescribeLogStreams"
      ],
      "Resource": "arn:aws:logs:ap-south-1:123456789012:log-group:/prod/nestjs-api:*"
    },
    {
      "Sid": "XRayTracing",
      "Effect": "Allow",
      "Action": [
        "xray:PutTraceSegments",
        "xray:PutTelemetryRecords"
      ],
      "Resource": "*"
    }
  ]
}
```

**What NOT to include (and why):**

```
❌ s3:* on "*" — grants access to every bucket in the account.
   If the instance is compromised, attackers exfiltrate everything.

❌ iam:PassRole — grants ability to assign arbitrary IAM roles to resources.
   An attacker with iam:PassRole + ec2:RunInstances can launch an instance
   with an admin role and use it to escalate privileges.

❌ iam:CreatePolicy, iam:AttachRolePolicy — privilege escalation vectors.
   If the NestJS API needs to manage IAM, something is wrong with the architecture.

❌ sts:AssumeRole without a specific Resource ARN.
   If the service needs to assume a role, specify exactly which role:
   "Resource": "arn:aws:iam::ACCOUNT:role/NestjsApiWorkerRole"

❌ ec2:* or autoscaling:* — the API tier doesn't manage its own infrastructure.
   If ASG management is needed (lifecycle signals), scope it tightly:
   Action: autoscaling:CompleteLifecycleAction
   Resource: arn:aws:autoscaling:region:account:autoScalingGroup:*:autoScalingGroupName/nestjs-api-*
```

## Section 5: Least Privilege Principle

**Q9. What is the Least Privilege Principle, and how do you implement it systematically?**
A: Least privilege means granting each principal exactly the permissions required to perform its function — no more. In practice it is implemented through a combination of narrow action scoping, resource ARN scoping, condition constraints, permission boundaries, and continuous review.

**The four dimensions of least privilege:**

```
1. Action scoping (narrow actions):
   Wrong:    "Action": "s3:*"
   Better:   "Action": ["s3:GetObject", "s3:PutObject"]
   Best:     "Action": ["s3:GetObject", "s3:PutObject"]
             with specific operations the service actually calls.

   Use IAM Access Analyzer or CloudTrail to discover which actions
   are actually being called; remove the rest.

2. Resource ARN scoping (narrow resources):
   Wrong:    "Resource": "*"
   Better:   "Resource": "arn:aws:s3:::prod-*"
   Best:     "Resource": "arn:aws:s3:::prod-nestjs-uploads/*"
             Specific bucket, specific prefix if possible.

   For regional resources:
     Wrong:  arn:aws:ssm:*:*:parameter/*
     Best:   arn:aws:ssm:ap-south-1:123456789012:parameter/prod/nestjs-api/*

3. Condition constraints (time, network, MFA, tags):
   Restrict by source VPC:
   "Condition": {
     "StringEquals": { "aws:SourceVpc": "vpc-0abc1234" }
   }
   Restrict by source IP range:
   "Condition": {
     "IpAddress": { "aws:SourceIp": ["10.0.0.0/8"] }
   }
   Require MFA for sensitive actions:
   "Condition": {
     "Bool": { "aws:MultiFactorAuthPresent": "true" }
   }
   Restrict to specific time window (maintenance windows):
   "Condition": {
     "DateGreaterThan": { "aws:CurrentTime": "2026-08-07T02:00:00Z" },
     "DateLessThan":    { "aws:CurrentTime": "2026-08-07T04:00:00Z" }
   }

4. Separation of principals:
   Wrong:  One IAM role for the entire application stack.
   Right:  Separate roles per service component:
     NestjsApiRole         → S3, SSM, SQS, CloudWatch
     NestjsWorkerRole      → SQS, RDS secrets, specific S3 prefixes
     NestjsBatchRole       → S3 full bucket write, Glue, DynamoDB
     NestjsSchedulerRole   → EventBridge PutEvents only
   If one component is compromised, the blast radius is contained to
   that component's permissions only.
```

**Q10. What are IAM Permission Boundaries and when do you need them?**
A: A Permission Boundary is a managed policy attached to an IAM principal that sets the maximum permissions that principal can ever have — regardless of what identity policies are attached to it. The effective permissions are the intersection of the identity policies and the boundary.

**The problem Permission Boundaries solve:**

```
Scenario: you delegate IAM role creation to a team (e.g., the ML team
can create their own roles for SageMaker jobs). Without boundaries:
  The ML team creates a role with AdministratorAccess attached.
  That role has full admin privileges — privilege escalation.

With Permission Boundaries:
  You grant the ML team iam:CreateRole and iam:AttachRolePolicy.
  But you add a condition:
  "Condition": {
    "StringEquals": {
      "iam:PermissionsBoundary": "arn:aws:iam::ACCOUNT:policy/MLTeamBoundary"
    }
  }
  The ML team can only create roles that have MLTeamBoundary as their boundary.
  MLTeamBoundary allows sagemaker:*, s3:* on ml-*, cloudwatch:* only.
  Even if the ML team attaches AdministratorAccess to a role they create,
  the effective permissions are:
    AdministratorAccess ∩ MLTeamBoundary = sagemaker:*, s3:* on ml-*, cloudwatch:*
  They cannot escalate beyond what MLTeamBoundary allows.

Permission Boundary is a ceiling, not a grant:
  A boundary of s3:* does NOT grant s3:* — it only allows identity policies
  to grant up to s3:*. An identity policy must still explicitly allow the action.
  Boundary: allows s3:GetObject
  Identity policy: no S3 statements
  Effective: no S3 access (boundary does not grant; identity policy must also allow)
```

**Permission Boundary for a developer sandbox role:**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCommonDevServices",
      "Effect": "Allow",
      "Action": [
        "s3:*", "dynamodb:*", "lambda:*",
        "sqs:*", "sns:*", "cloudwatch:*", "logs:*",
        "ec2:Describe*", "ecr:*"
      ],
      "Resource": "*"
    },
    {
      "Sid": "DenyProductionAndSecurity",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/Environment": "production"
        }
      }
    },
    {
      "Sid": "DenyIAMEscalation",
      "Effect": "Deny",
      "Action": [
        "iam:CreateUser",
        "iam:DeleteUserPolicy",
        "iam:AttachUserPolicy",
        "iam:PutUserPolicy",
        "iam:CreateAccessKey",
        "organizations:*",
        "account:*"
      ],
      "Resource": "*"
    }
  ]
}
```

**Q11. How do you use IAM Access Analyzer and CloudTrail to achieve least privilege in practice?**
A: The two tools work in complementary ways: CloudTrail records what permissions are actually used; IAM Access Analyzer identifies what external access is possible. Together they enable data-driven right-sizing of IAM policies.

**CloudTrail-based policy right-sizing:**

```
Step 1: Grant a broad temporary policy to a new service role (scoped to resource ARNs
        but with most actions allowed). Deploy to staging.

Step 2: Run the service through its full test suite and representative traffic.
        Every AWS API call generates a CloudTrail event.

Step 3: Use IAM Access Analyzer to generate a policy from CloudTrail:
  aws accessanalyzer create-access-preview ... # or use the Console
  IAM → Role → Generate policy based on CloudTrail activity

  Input:  CloudTrail trail, time window (e.g., last 7 days), role ARN
  Output: minimal policy JSON containing only the actions actually called,
          scoped to the resources actually accessed.

Step 4: Review the generated policy. Remove any actions you know are not
        needed in production. Add missing actions for code paths not exercised
        in the test window (e.g., error handling paths, rarely-triggered features).

Step 5: Replace the broad staging policy with the right-sized policy.
        Deploy to production.

Ongoing: re-run Access Analyzer policy generation quarterly.
         When new features add new AWS API calls, the policy needs updating.
         When features are removed, the policy should be trimmed.
```

**IAM Access Analyzer for external access detection:**

```
IAM Access Analyzer continuously scans all resource-based policies in your account
(S3 buckets, KMS keys, SQS queues, Lambda functions, ECR repos, Secrets Manager,
IAM roles that trust external principals) and flags any resource accessible from
outside your AWS Organization or account.

Finding types:
  PUBLIC:       S3 bucket policy allows Principal: "*" → accessible by anyone on internet.
  CROSS_ACCOUNT: KMS key policy allows Principal from account 999999999999.
                 If that account is not in your org → external access finding.
  CROSS_ORG:    A role trusts a principal in your org but outside your OU.

For each finding, Access Analyzer tells you:
  Which resource is exposed.
  Which principal (account, org) has access.
  Which specific actions are allowed.
  Whether a condition restricts access (e.g., aws:SourceVpc).

Integrate into CI/CD:
  aws accessanalyzer validate-policy --policy-document file://policy.json
  Returns findings before the policy is deployed — catches overly broad policies
  before they reach production.
  Return code 0 = no findings. Non-zero = findings exist (block the pipeline).
```

## Section 6: Advanced IAM Patterns

**Q12. How does OIDC federation work for GitHub Actions, and why is it better than access keys?**
A: OIDC (OpenID Connect) federation allows GitHub Actions workflows to assume an IAM role by exchanging a GitHub-issued JWT token for AWS temporary credentials — no static access keys stored as GitHub Secrets.

**The OIDC flow:**

```
1. GitHub Actions starts a workflow run.
   GitHub's OIDC provider issues a JWT token for that run.
   The JWT contains claims:
     iss:  https://token.actions.githubusercontent.com
     sub:  repo:myorg/nestjs-api:ref:refs/heads/main
     aud:  sts.amazonaws.com
     iat, exp, jti (standard JWT fields)

2. The workflow calls aws-actions/configure-aws-credentials with:
   role-to-assume: arn:aws:iam::123456789012:role/GithubActionsDeployRole
   aws-region:     ap-south-1

3. The action calls STS AssumeRoleWithWebIdentity, passing the GitHub JWT.
   STS validates the JWT against the registered OIDC provider endpoint.
   GitHub's public keys are fetched from:
     https://token.actions.githubusercontent.com/.well-known/jwks

4. STS issues temporary credentials.
   The workflow uses them to deploy (push to S3, start Instance Refresh, etc.).

No AWS access keys are stored in GitHub Secrets.
The temporary credentials expire when the workflow run ends.

GitHub Actions workflow:
  jobs:
    deploy:
      permissions:
        id-token: write   # Required: allows the workflow to request a JWT
        contents: read
      steps:
        - uses: aws-actions/configure-aws-credentials@v4
          with:
            role-to-assume: arn:aws:iam::123456789012:role/GithubActionsDeployRole
            aws-region: ap-south-1
        - run: aws s3 sync ./dist s3://prod-nestjs-assets/

IAM role trust policy (set up once in Terraform):
  resource "aws_iam_openid_connect_provider" "github" {
    url             = "https://token.actions.githubusercontent.com"
    client_id_list  = ["sts.amazonaws.com"]
    thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
  }

  Trust policy condition — lock down to specific repo and branch:
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub":
        "repo:myorg/nestjs-api:ref:refs/heads/main"
    }
  }

  Without the sub condition, ANY GitHub repo could assume this role.
  Always scope the sub condition to your org/repo/branch.
```

**Q13. What is IAM Roles Anywhere, and when is it useful?**
A: IAM Roles Anywhere extends IAM role assumption to workloads running outside AWS (on-premises servers, other clouds, IoT devices) using X.509 certificates issued by a trusted Certificate Authority instead of AWS-internal trust mechanisms.

```
Use case: On-premises NestJS microservice that needs to read from an S3 bucket
          or write to SQS without an IAM user or static access key.

Setup:
  1. Create a Private CA in AWS Certificate Manager (ACM PCA) or bring your own CA.
  2. Register the CA as a Trust Anchor in IAM Roles Anywhere.
  3. Create a Profile: map a Trust Anchor + IAM role to a session configuration.
  4. Issue X.509 certificates signed by the CA to your on-premises servers.
  5. On-premises server uses the AWS Roles Anywhere credential helper:
       ./aws_signing_helper credential-process \
         --certificate /path/to/cert.pem \
         --private-key  /path/to/key.pem \
         --trust-anchor-arn arn:aws:rolesanywhere:...:trust-anchor/... \
         --profile-arn     arn:aws:rolesanywhere:...:profile/... \
         --role-arn        arn:aws:iam::123456789012:role/OnPremNestjsRole

     The helper exchanges the certificate for temporary STS credentials.
     AWS SDKs use the credential-process output natively.

Certificate rotation = credential security:
  Certificate validity: set to 24 hours (short-lived) or up to 1 year.
  On certificate expiry, the server can no longer assume the role.
  No static AWS credentials anywhere — the CA is the trust root.

When Roles Anywhere is overkill:
  EC2 instances          → Instance Profile (use this instead)
  Lambda functions       → Execution role (use this instead)
  ECS tasks              → Task role (use this instead)
  GitHub Actions / CI    → OIDC federation (use this instead)

Roles Anywhere is specifically for truly external compute that has no
other AWS credential mechanism available.
```

**Q14. What are Service Control Policies (SCPs), and how do they interact with IAM?**
A: Service Control Policies are AWS Organizations-level controls that set the maximum available permissions for all principals in an organizational unit (OU) or account. Unlike IAM policies, SCPs apply to the entire account — including the root user (with narrow exceptions).

**SCP behavior:**

```
SCPs are permission guardrails:
  An SCP does NOT grant permissions — it restricts what CAN be granted.
  If an SCP doesn't allow s3:DeleteBucket, no IAM policy can grant it,
  even AdministratorAccess.

  SCP effect = intersection of SCP allowed actions ∩ IAM policy allowed actions.

  Management account (root org account) is NOT affected by SCPs.
  Root user IS affected by SCPs (unique to SCPs vs IAM policies).

SCP modes:
  Deny list (default, recommended):
    AWS applies a default AWS FullAccess SCP to all accounts.
    You add Deny statements for what you want to block.
    Simple to manage; new services are automatically accessible.

  Allow list:
    Remove the default FullAccess SCP.
    Add explicit Allow statements for each permitted service.
    Strict but burdensome: every new service must be explicitly allowed.

Common SCP patterns for fintech:
  1. Prevent leaving AWS Organizations:
  {
    "Effect": "Deny",
    "Action": ["organizations:LeaveOrganization"],
    "Resource": "*"
  }

  2. Restrict to approved AWS regions (data residency):
  {
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": ["ap-south-1", "ap-southeast-1"]
      },
      "ArnNotLike": {
        "aws:PrincipalARN": "arn:aws:iam::*:role/BreakGlassAdmin"
      }
    }
  }

  3. Prevent disabling CloudTrail:
  {
    "Effect": "Deny",
    "Action": [
      "cloudtrail:DeleteTrail",
      "cloudtrail:StopLogging",
      "cloudtrail:UpdateTrail"
    ],
    "Resource": "*",
    "Condition": {
      "ArnNotLike": {
        "aws:PrincipalARN": "arn:aws:iam::*:role/SecurityAuditRole"
      }
    }
  }

  4. Require encryption on all S3 objects:
  {
    "Effect": "Deny",
    "Action": "s3:PutObject",
    "Resource": "*",
    "Condition": {
      "StringNotEqualsIfExists": {
        "s3:x-amz-server-side-encryption": ["aws:kms", "AES256"]
      }
    }
  }

SCPs do not appear in IAM policy simulation:
  aws iam simulate-principal-policy does NOT evaluate SCPs.
  Use AWS Organizations → Policies → Simulate to include SCP evaluation.
  A policy that passes simulate-principal-policy may still be blocked by an SCP.
```

**Q15. "Design the IAM architecture for a multi-account fintech AWS organization with dev, staging, and production environments."**
A:

```
Organization structure:
  Root
  ├── Management OU
  │   └── Account: org-management (billing, consolidated trail, SCPs only)
  ├── Security OU
  │   └── Account: security-hub (GuardDuty master, SecurityHub, Config aggregator,
  │                               CloudTrail S3 bucket, IAM Access Analyzer)
  ├── Shared Services OU
  │   └── Account: shared-services (ECR, Route53 private hosted zones,
  │                                   Transit Gateway, Secrets Manager shared secrets)
  └── Workloads OU
      ├── Dev OU
      │   └── Account: dev (developer sandboxes, feature environments)
      ├── Staging OU
      │   └── Account: staging (pre-production, integration testing)
      └── Production OU
          └── Account: production (NACH batch, KYC pipeline, NestJS API)

SCP hierarchy:
  Root:           Deny leave-org, deny disable-CloudTrail, require ap-south-1 region
  Production OU:  Deny iam:CreateAccessKey (no long-lived keys in prod),
                  Deny public S3 ACLs, require KMS encryption on all EBS and S3

IAM role design per account:

  Production account roles:
    NestjsApiRole           → EC2 instance profile; S3, SSM, SQS, CloudWatch
    NestjsWorkerRole        → EC2 instance profile; SQS, Secrets Manager, S3 batch prefix
    KafkaConsumerRole       → EC2 instance profile; SQS DLQ, CloudWatch
    NachBatchRole           → EC2/Lambda; S3 batch results, DynamoDB, SFN
    ProdDeployRole          → Assumed by GitHub Actions OIDC; ec2:*, autoscaling:*, s3:PutObject

  Cross-account roles (in Production, trusted by other accounts):
    SecurityReadRole        → trusted by security account; read CloudTrail, VPC flow logs
    MonitoringRole          → trusted by shared-services; CloudWatch read, X-Ray read
    DevReadonlyRole         → trusted by dev account with MFA; Describe* only; no write

  GitHub Actions roles (per environment):
    GithubActionsDevRole    → trusted by OIDC for dev/* branches; dev account only
    GithubActionsStagingRole → trusted by OIDC for main branch; staging account only
    GithubActionsProdRole   → trusted by OIDC for release/* tags only; prod account only

Secrets management:
  All secrets in AWS Secrets Manager (not SSM SecureString for secrets).
  Secret ARNs scoped per environment: arn:aws:secretsmanager:*:*:secret:prod/*
  NestjsApiRole has secretsmanager:GetSecretValue on prod/* only.
  Rotation enabled for all database credentials (RDS automatic rotation Lambda).
  No secrets in environment variables; no secrets in CloudFormation/Terraform state.

Audit and access review:
  CloudTrail enabled in all accounts; logs centralized to security account S3.
  IAM Access Analyzer enabled in every account with Organization as the zone of trust.
  Quarterly: aws iam generate-credential-report → audit unused credentials.
  Quarterly: IAM Access Analyzer policy generation from CloudTrail → right-size roles.
  Alert: CloudWatch alarm on iam:CreateAccessKey in production account (SCP blocks it,
         but alarm provides defense-in-depth notification).
```

**Q16. "An incident report says a Lambda function exfiltrated data from an S3 bucket it should not have access to. Walk through how this happened and how to prevent it."**
A:

```
How the exfiltration likely occurred — common attack paths:

Path 1: Overly broad Lambda execution role
  Lambda role had s3:GetObject on Resource: "*"
  Developer added "*" because they weren't sure which bucket ARN to use.
  Attackers achieved code execution in the Lambda (via a dependency vulnerability
  or event injection) and called S3 GetObject on the sensitive bucket.

  Finding: CloudTrail shows ListBuckets call from Lambda role ARN,
            then GetObject on a bucket not in the application's intended scope.

Path 2: Trust policy misconfiguration
  A resource-based policy on the S3 bucket had:
    "Principal": { "AWS": "arn:aws:iam::ACCOUNT:root" }
  This allows every principal in the account (including the Lambda role)
  to access the bucket — not just the intended role.

Path 3: iam:PassRole exploitation
  The Lambda role had iam:PassRole + lambda:CreateFunction.
  An attacker who could invoke the Lambda injected a payload that called
  CreateFunction with an admin role passed to the new function,
  then invoked that function to access any resource.

Remediation:

1. Immediate: Revoke the Lambda role's current session
   aws iam put-role-policy \
     --role-name LambdaExecutionRole \
     --policy-name DenyAll \
     --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"*","Resource":"*"}]}'
   This inline deny overrides any attached policies immediately.
   Detach the role from Lambda once the deny is in place.

2. Scope the Lambda execution role to minimum permissions:
   Before:  s3:GetObject on "*"
   After:   s3:GetObject on "arn:aws:s3:::prod-lambda-input/*" only
   Verify with IAM Access Analyzer: validate-policy should return 0 findings.

3. Fix any overly broad resource-based policies:
   Run IAM Access Analyzer findings → identify all resources with
   "Principal: *" or "Principal: root" — review and tighten each.

4. Add S3 VPC endpoint + bucket policy condition:
   "Condition": {
     "StringEquals": { "aws:SourceVpc": "vpc-prod-0abc" }
   }
   Requests from outside the VPC (including Lambda in a different VPC
   or compromised credentials used from the internet) are rejected.

5. Enable S3 Object-level logging in CloudTrail:
   Object-level logging (data events) is off by default — costs extra.
   For sensitive buckets (PII, financial records), enable it.
   Without it, GetObject calls do not appear in CloudTrail.

6. Enable Amazon Macie on sensitive buckets:
   Macie continuously scans for sensitive data (PAN, Aadhaar, bank account numbers)
   and alerts on unusual access patterns (bulk downloads, access from new principals).

Prevention going forward:
  IAM: never use Resource: "*" in Lambda execution roles without explicit justification.
  Process: policy review in PR pipeline (aws accessanalyzer validate-policy in CI).
  Monitoring: CloudWatch alarm on any S3 GetObject from a non-whitelisted role ARN
              on the sensitive buckets.
  Architecture: sensitive data in separate AWS accounts; cross-account role assumption
                requires deliberate, audited action — accidental access becomes impossible.
```

| IAM principal | Credential type | Use case |
|---|---|---|
| IAM User | Static (password + access key) | Human Console access, legacy apps |
| IAM Role | Temporary STS tokens (auto-rotate) | Services, CI/CD, cross-account, OIDC |
| IAM Group | N/A (not a principal; holds policies) | Group permissions for IAM users |
| Federated identity | Short-lived via OIDC / SAML | GitHub Actions, Google, corporate SSO |

| Policy type | Attached to | Scope |
|---|---|---|
| Identity-based | IAM user, group, role | What the principal can do |
| Resource-based | Resource (S3, SQS, KMS, etc.) | Who can act on the resource |
| SCP | AWS Org OU or account | Maximum allowed permissions (ceiling) |
| Permission Boundary | IAM principal | Maximum effective permissions (ceiling) |
| Session Policy | Assumed role session | Further restrict a specific session |

| Scenario | IAM pattern |
|---|---|
| EC2 needs AWS API access | Instance Profile → IAM Role |
| Lambda needs AWS API access | Execution Role |
| GitHub Actions needs to deploy | OIDC federation → AssumeRoleWithWebIdentity |
| On-premises server needs AWS access | IAM Roles Anywhere + X.509 cert |
| Account A needs to act in Account B | Cross-account role + ExternalId |
| Developer sandbox with guardrails | Permission Boundary scoped to safe services |
| Block production IAM key creation | SCP: Deny iam:CreateAccessKey on prod OU |
| Discover over-permissive roles | IAM Access Analyzer + CloudTrail policy gen |

| Common IAM Mistake | Symptom | Fix |
|---|---|---|
| `Resource: "*"` on S3 actions | Role can access every bucket | Scope to specific bucket ARNs |
| `Principal: root` in resource policy | Every account principal has access | Scope to specific role ARN |
| IAM User access keys in code | Leaked key = permanent compromise | Replace with instance profile or OIDC |
| No ExternalId on cross-account trust | Confused deputy attack possible | Add ExternalId condition |
| `$Latest` Lambda alias without boundary | Over-permissive function assumed | Add permission boundary |
| No OIDC sub condition on GitHub trust | Any GitHub repo can assume the role | Scope sub to org/repo/branch |
| Trust policy allows `iam:PassRole "*"` | Privilege escalation to admin | Scope Resource to specific role ARN |
| Missing S3 data event logging | S3 GetObject not in CloudTrail | Enable data events on sensitive buckets |
| SCP blocking legitimate action | Action denied despite IAM policy allowing | Check SCP; update SCP or use exception condition |
| Overly long role session on chained roles | Session token expires mid-chain | Chained sessions cap at 1 hour; redesign to avoid deep chains |

## The Core Mental Model

```
Every AWS API call is a question to IAM:
  "Can principal P perform action A on resource R under conditions C?"
  Default answer: NO.
  IAM looks for a reason to say YES and a reason to say NO.
  Any explicit DENY wins. Allow only if no deny exists AND at least one allow exists.

Identity vs Resource policies — think of two locks:
  Same account: one key opens the door (either policy can grant access).
  Cross account: both locks must be open (identity policy in Account A
                 AND resource policy in Account B must both allow the access).
  This is why cross-account S3 access requires changes in BOTH accounts.

The credential hierarchy: prefer shorter-lived over longer-lived.
  Static IAM user key:  lives until rotated (highest risk)
  Instance Profile:     rotated ~every 6 hours automatically (preferred for EC2)
  OIDC session:         lives for the workflow run duration (preferred for CI/CD)
  Role assumption:      15 min – 12 hours (scoped per session need)
  Never put AWS access keys in source code, Docker images, or environment
  variables baked into an AMI. The credential belongs to the runtime identity.

Trust policies answer "who can wear this costume":
  The IAM Role is a set of permissions (the costume).
  The Trust Policy controls who is allowed to put it on.
  An ec2.amazonaws.com trust → EC2 instances can assume the role (instance profile).
  A GitHub OIDC trust → GitHub Actions can assume the role (no keys needed).
  A cross-account trust + ExternalId → specific role in another account can assume it.

Least privilege is a process, not a one-time config:
  Start broad in dev → generate policy from CloudTrail → tighten → review quarterly.
  Use IAM Access Analyzer validate-policy in your CI/CD pipeline.
  Resource: "*" on any read action is a red flag; on write/delete, a critical finding.
  The question is not "does this work?" but "does this work with the minimum grants needed?"

Permission Boundary = the delegation pattern:
  You grant iam:CreateRole to a team.
  Without a boundary condition: they can create roles with AdministratorAccess.
  With a boundary: even if they attach AdministratorAccess, effective permissions
  are bounded by what you permit them to delegate.
  Use boundaries whenever you delegate IAM management to a team or automation.

SCPs are account-level guardrails:
  They restrict what's achievable, not what's granted.
  A role with AdministratorAccess in an account with an SCP that denies
  ec2:* cannot create any EC2 resources — regardless of their IAM permissions.
  Never mistake "IAM policy allows it" for "the action will succeed" —
  SCPs, permission boundaries, VPC endpoint policies, and resource policies
  all intervene before the action executes.

CloudTrail is the source of truth for IAM forensics:
  Every assume-role call, every failed authorization, every policy change is in CloudTrail.
  Enable CloudTrail in every account. Centralize to a separate security account.
  Enable S3 object-level data events for sensitive buckets (not on by default).
  When investigating an incident: search CloudTrail for the role ARN,
  including the session name (AssumedRoleUser.Arn) to trace individual sessions.
```
