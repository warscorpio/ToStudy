## Section 1: RDS Architecture Fundamentals

**Q1. What is Amazon RDS and what does it manage on your behalf compared to self-managed EC2 databases?**
A: RDS is a managed relational database service that runs PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, and Amazon Aurora. "Managed" means AWS handles the operational layer — OS patching, database software upgrades (optionally), storage provisioning, automated backups, and hardware failure recovery — while you retain control of the database layer: schema, queries, indexes, parameter tuning, and access control.

**What RDS manages vs what you manage:**

```
AWS manages:
  OS installation and patching (you never SSH into an RDS instance)
  Database engine installation and minor version upgrades (optionally automated)
  Hardware provisioning and replacement (EBS volume failure, host failure)
  Automated backups (daily snapshot + continuous transaction log archival)
  Multi-AZ replication setup and failover orchestration
  Storage auto-scaling (if enabled; expands volume when free space < threshold)
  Encryption at rest (KMS) and in transit (TLS)
  Monitoring via CloudWatch (CPUUtilization, DatabaseConnections, FreeStorageSpace, etc.)

You manage:
  Database engine configuration (parameter groups)
  Schema design, indexes, queries, stored procedures
  Application-level connection pooling (RDS Proxy or PgBouncer)
  IAM database authentication or master password rotation
  Read replica promotion decisions
  Major version upgrades (manually triggered; AWS handles the mechanics)
  VPC placement, subnet groups, security group rules
  Backup retention period (1–35 days)
  Point-in-time recovery decisions (RPO within the retention window)
```

**The operational trade-off:**
You pay a premium (RDS typically costs 30–50% more than equivalent EC2 + EBS for the same database workload) in exchange for eliminating the operational burden of database administration. For most application teams without dedicated DBAs, this trade-off is strongly positive. The breakeven calculation: DBA cost + operational risk + downtime from manual failover vs RDS premium.

**Q2. How does RDS storage work, and what are the differences between gp2, gp3, io1, and io2?**
A: RDS uses Amazon EBS as its storage layer. Storage is provisioned at instance creation and can be expanded (never shrunk) while the instance is running. The storage type determines IOPS characteristics and cost.

**Storage types:**

```
gp2 (General Purpose SSD — legacy):
  Baseline IOPS: 3 IOPS per GiB (minimum 100, maximum 16,000)
  Burst: volumes < 1 TiB can burst to 3,000 IOPS using a credit model
          (identical concept to T-series CPU credits — credit exhaustion throttles I/O)
  Throughput: up to 250 MiB/s
  Cost: ~$0.115/GiB-month
  Problem: IOPS tied to storage size; to get 6,000 IOPS you must provision 2 TiB even
           if you only need 200 GiB of data. Wastes money.

gp3 (General Purpose SSD — current, recommended default):
  Baseline IOPS: 3,000 IOPS regardless of volume size (decoupled from storage)
  Provisioned IOPS: up to 16,000 IOPS (independently configured; extra cost)
  Throughput: up to 1,000 MiB/s (independently configured; extra cost)
  Cost: ~$0.08/GiB-month (30% cheaper than gp2) + $0.005/provisioned IOPS above 3,000
  Advantage: storage and IOPS are independent — provision only what you need

io1 (Provisioned IOPS SSD — legacy):
  IOPS: 100–64,000 (up to 256,000 on Nitro instances)
  IOPS:GiB ratio: maximum 50:1 (64,000 IOPS requires at least 1,280 GiB)
  Cost: ~$0.125/GiB-month + $0.065/provisioned IOPS-month
  Use: high-IOPS databases (busy OLTP PostgreSQL, MySQL) needing > 16,000 IOPS

io2 Block Express (Provisioned IOPS SSD — current high-performance):
  IOPS: up to 256,000
  IOPS:GiB ratio: maximum 1,000:1 (extremely flexible)
  Durability: 99.999% (vs 99.8–99.9% for gp3/io1)
  Latency: sub-millisecond
  Cost: higher than io1 but superior durability and flexibility
  Use: mission-critical databases; SAP HANA; financial transaction databases

Storage auto-scaling:
  Enable on any RDS instance.
  Set a Maximum Storage Threshold (e.g., 1 TiB).
  When free storage drops below 10% of allocated storage: RDS automatically
  expands the volume (in 5 GiB or 10% increments, whichever is larger).
  Prevents "out of disk space" incidents; no downtime during expansion.
  Cannot auto-shrink — storage only grows.
```

**The gp3 selection rule for fintech:**
```
Default choice: gp3 with 3,000 baseline IOPS
PostgreSQL OLTP (loan applications, KYC records):
  Profile: random reads/writes, moderate concurrency, ~500 IOPS average
  Selection: gp3, 500 GiB, 3,000 IOPS (baseline covers it; ~$40/month storage)

PostgreSQL analytics / reporting (EMI calculations, portfolio summaries):
  Profile: sequential scans, high throughput, occasional 10,000+ IOPS bursts
  Selection: gp3, 1 TiB, provision 6,000 IOPS, 500 MiB/s throughput

High-write OLTP (payment processing, NACH batch inserts):
  Profile: sustained 8,000–20,000 IOPS, low latency critical
  Selection: io2, 500 GiB, 10,000 provisioned IOPS
```

## Section 2: RDS Multi-AZ

**Q3. How does RDS Multi-AZ work internally, and what does it protect against?**
A: Multi-AZ is RDS's high-availability mechanism. When enabled, RDS maintains a synchronous standby replica in a different Availability Zone. The primary and standby share no hardware — they run on separate hosts, in separate data centers, connected by a synchronous replication link.

**The replication model:**
```
Multi-AZ with one standby (standard — all engines):

  Primary (AZ-a)                    Standby (AZ-b)
  ┌─────────────────┐               ┌─────────────────┐
  │ PostgreSQL       │               │ PostgreSQL       │
  │ Active, R/W      │               │ Passive (no      │
  │                  │◄─────────────►│ direct access)   │
  │ EBS Volume (AZ-a)│  synchronous  │ EBS Volume (AZ-b)│
  └─────────────────┘  replication   └─────────────────┘
         │
         │ DNS: mydb.cluster.ap-south-1.rds.amazonaws.com
         │ (points to primary)
         ▼
    Application

Synchronous replication means:
  A write transaction commits on the PRIMARY only AFTER it has been
  acknowledged by the STANDBY.
  RPO (Recovery Point Objective) = 0: no data loss on failover.
  The standby is always caught up — no replication lag (unlike read replicas).

What Multi-AZ protects against:
  ✅ Primary instance hardware failure (host crash, hardware fault)
  ✅ Primary EBS volume failure or corruption
  ✅ AZ-level partial outage (network, power within one AZ)
  ✅ OS/database crash on the primary host
  ✅ Manual failover for maintenance (OS patching, minor version upgrades)

What Multi-AZ does NOT protect against:
  ❌ Logical corruption (DROP TABLE, bad migration) — standby replicates the mistake
  ❌ Region-level failure (both AZs in a region affected)
  ❌ Application bugs that corrupt data
  ❌ Read scaling — the standby is not accessible for reads (unlike read replicas)
```

**Multi-AZ with two readable standbys (Aurora and RDS PostgreSQL 14.5+):**
```
RDS Multi-AZ Cluster (preview/newer feature):
  1 writer + 2 readable standby instances across 3 AZs
  Standby instances can serve read traffic (unlike standard Multi-AZ)
  Failover time: ~35 seconds (faster than standard Multi-AZ ~60–120s)
  Not the same as Aurora Multi-AZ; this is native RDS Multi-AZ Cluster
```

**Q4. What happens during an RDS Multi-AZ failover, step by step?**
A: Failover is automatic — RDS detects the primary failure and promotes the standby without manual intervention. Understanding the sequence helps you set correct timeouts and retry logic in your application.

**Failover sequence:**
```
T+0s:  Primary fails (host crash, EBS failure, AZ event)

T+10s: RDS detects the failure via health monitoring
        (health checks run every few seconds internally)

T+20s: RDS determines failover is required
        (distinguishes transient network hiccup from actual failure)

T+30s: RDS begins promotion:
        - Standby promoted to primary (engine starts accepting writes)
        - DNS record for the RDS endpoint updated:
          mydb.ap-south-1.rds.amazonaws.com → new IP (standby's IP)
        - DNS TTL: 5 seconds (very short; intentionally)

T+60s: DNS propagation completes across resolvers
        New primary is fully operational

T+60–120s: Application reconnects
        - Connection pool detects broken connections (TCP reset or timeout)
        - Pool discards stale connections, opens new ones
        - New connections resolve DNS → new primary IP → connect
        - Application resumes normal operation

Total downtime window: 60–120 seconds (typ. ~90s)
RTO (Recovery Time Objective) for RDS Multi-AZ: ~60–120 seconds
RPO: 0 (synchronous replication; no data loss)
```

**What your application must do to survive failover:**
```typescript
// Connection pool configuration for PostgreSQL (pg / node-postgres)
// Must handle the failover window correctly

import { Pool } from 'pg';

const pool = new Pool({
  host:               process.env.DB_HOST,     // RDS endpoint DNS name
  port:               5432,
  database:           process.env.DB_NAME,
  user:               process.env.DB_USER,
  password:           process.env.DB_PASSWORD,
  ssl:                { rejectUnauthorized: true },

  max:                20,                      // max connections in pool
  idleTimeoutMillis:  30_000,                  // close idle connections after 30s
  connectionTimeoutMillis: 5_000,              // fail fast if cannot connect in 5s

  // Critical for Multi-AZ failover:
  // node-postgres does not automatically retry failed connections.
  // Use a wrapper with retry logic:
});

// Retry wrapper for transient failures during failover
async function queryWithRetry(
  text:   string,
  params: unknown[],
  retries = 3,
): Promise<QueryResult> {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await pool.query(text, params);
    } catch (err: any) {
      const isTransient =
        err.code === 'ECONNRESET'      || // TCP reset during failover
        err.code === 'ECONNREFUSED'    || // connection refused (new primary starting)
        err.code === 'ETIMEDOUT'       || // connection timeout
        err.message?.includes('Connection terminated unexpectedly');

      if (isTransient && attempt < retries) {
        const delay = attempt * 1000; // 1s, 2s, 3s backoff
        await sleep(delay);
        continue;
      }
      throw err;
    }
  }
}

// NestJS TypeORM configuration — built-in retry
TypeOrmModule.forRoot({
  type:             'postgres',
  host:             process.env.DB_HOST,
  retryAttempts:    5,
  retryDelay:       2000,  // 2s between retry attempts
  connectTimeoutMS: 5000,
  // TypeORM retries the initial connection; does not auto-retry in-flight queries
  // Use queryWithRetry pattern above for in-flight query failures
});
```

**RDS Proxy for failover improvement:**
```
Without RDS Proxy:
  Failover: application pool loses connections → waits for DNS propagation →
            reconnects → ~60–120 seconds of errors

With RDS Proxy:
  Application connects to Proxy endpoint (never to RDS directly).
  Proxy maintains a warm connection pool to RDS.
  On failover: Proxy reconnects to new primary in ~5–10 seconds.
  Application sees a brief stall (in-flight queries hold) then resume.
  Effective RTO for application: ~20–30 seconds (vs 60–120 without Proxy).

When RDS Proxy is worth it:
  - Lambda functions (thousands of short-lived connections; Proxy pools them)
  - High-concurrency APIs (> 500 concurrent DB connections; Proxy reduces load on RDS)
  - Multi-AZ deployments where 60-second failover is unacceptable
  Cost: ~$0.015/vCPU-hour of the underlying RDS instance
```

**Q5. What are the RDS backup mechanisms, and what is the difference between automated backups and manual snapshots?**
A: RDS provides two backup mechanisms with different retention, cost, and recovery characteristics. Understanding both is critical for designing RPO/RTO commitments.

**Automated backups:**
```
What: Daily full snapshot + continuous transaction log (WAL for PostgreSQL) archival to S3
Retention: 1–35 days (set at instance creation; 0 = disabled, also disables PITR)
PITR: Point-In-Time Recovery to any second within the retention window
      "Restore to 14:32:47 IST on Tuesday" → RDS restores the last snapshot before
      that time + replays WAL logs up to the exact second

Automated backup window:
  30-minute window during which the daily snapshot is taken.
  Brief I/O suspension for non-Aurora engines during snapshot start (seconds).
  Set the window to off-peak hours (e.g., 01:00–02:00 UTC for India workloads).

Automated backup storage:
  Free up to the size of the provisioned RDS storage.
  Beyond that: $0.095/GiB-month (S3 pricing for extra retention).

Automated backup limitations:
  Deleted when the RDS instance is deleted (unless you retain the final snapshot).
  Cannot share across AWS accounts (use manual snapshots for cross-account sharing).
  Not available in the source region for cross-region DR (use manual snapshots or
  enable cross-region automated backup replication — newer RDS feature).
```

**Manual snapshots:**
```
What: On-demand full EBS snapshot of the RDS instance, stored in S3
Triggered: manually via console, CLI, or API (or by RDS before major changes)
Retention: indefinite — manual snapshots persist until you delete them
           (even if the RDS instance is deleted)
Cost: $0.095/GiB-month for snapshot storage

Use cases:
  Before major schema migrations or deployments (restore point if migration fails)
  Before major version upgrades (RDS creates one automatically but you can add yours)
  Cross-account database sharing (share snapshot → restore in target account)
  Cross-region DR copy (copy snapshot to another region)
  Long-term retention beyond 35-day automated backup window
  Archival of database state at a specific point in time (regulatory compliance)

Restoring from snapshot:
  Creates a NEW RDS instance (does not overwrite the running instance)
  New instance has a new endpoint → update application config or use CNAME
  Restore time: proportional to database size; typically 10–30 minutes for 100 GiB
  After restore: replay manual changes made after the snapshot (if any)
```

**The fintech backup strategy:**
```
Automated backups:
  Retention: 14 days (covers 2-week investigation window for fraud/disputes)
  Window: 02:00–03:00 UTC (03:30–04:30 IST; minimum traffic period)
  Enable cross-region replication of automated backups to ap-southeast-1
  (Singapore as DR region for ap-south-1 Mumbai workloads)

Manual snapshots:
  Before every schema migration (via CI/CD pipeline step before migration runs)
  Before every major version upgrade
  Monthly long-term retention snapshot (12 months, for regulatory audit)
  Named convention: rds-snap-{env}-{engine}-{YYYY-MM-DD}-{purpose}

PITR test (quarterly):
  Restore to a specific timestamp in the staging account.
  Verify data integrity and application connectivity.
  Measure actual restore time (document as actual RTO for DR runbook).
```

## Section 3: RDS Read Replicas

**Q6. How do RDS read replicas work, and how do they differ from Multi-AZ standbys?**
A: A read replica is an asynchronous copy of the primary RDS instance that can serve read traffic, offloading the primary and enabling horizontal read scaling. Unlike the Multi-AZ standby, a read replica is directly accessible to the application via its own endpoint.

**Read replica vs Multi-AZ standby — the fundamental difference:**

```
Multi-AZ Standby:               Read Replica:
  Purpose: HA / failover          Purpose: read scaling / offload
  Replication: synchronous        Replication: asynchronous
  RPO: 0 (no data loss)          RPO: seconds to minutes (replica lag)
  Accessible: NO                  Accessible: YES (read-only endpoint)
  Same region: required           Same region or cross-region: both supported
  Failover: automatic             Failover: manual promotion (not automatic)
  Cost: included in instance      Cost: additional instance charge
  Max per primary: 1              Max per primary: 5 (PostgreSQL), 5 (MySQL)

You can have BOTH simultaneously:
  Primary (AZ-a) with Multi-AZ standby (AZ-b)
  + 2 read replicas (AZ-c, cross-region)
  The standbys and replicas are independent configurations.
```

**Replication lag:**
```
Read replica replication is asynchronous:
  Primary commits a write → sends WAL to replica → replica applies WAL
  Time between primary commit and replica apply = replication lag

Monitoring lag:
  CloudWatch metric: ReplicaLag (seconds)
  Typically: < 100ms for same-region, lightly loaded replicas
  Under heavy write load or slow replica: lag can reach seconds to minutes

Application consequence of lag:
  User creates a loan application → write hits primary
  User's next request reads from replica
  If replica lag = 5 seconds → user sees their application as "not found"
  "Read-your-writes" consistency is NOT guaranteed with read replicas

Solution — read-your-writes pattern:
  Option A: Always read from primary for the request immediately after a write
            (route write + subsequent reads within the same transaction to primary)
  Option B: After write, wait for replica to catch up (poll replica lag metric)
            (impractical for user-facing requests)
  Option C: Session pinning — after any write in a session, route all reads to
            primary for that session's duration
            (RDS Proxy supports session pinning automatically)
  Option D: Accept eventual consistency for reads that are not write-dependent
            (dashboard aggregations, reports — lag is acceptable here)
```

**Q7. When do you add read replicas, and how do you route traffic between primary and replicas?**
A: Read replicas are the correct tool when the primary's CPU or I/O is dominated by read queries, not writes. Adding a replica offloads those reads without changing the primary's write throughput.

**Signals that you need a read replica:**
```
Primary CPU > 60% sustained, majority of queries are SELECTs:
  → Read replica routes SELECT load away from primary

pg_stat_activity shows many long-running analytics queries alongside OLTP:
  → Dedicated read replica for analytics; primary handles OLTP exclusively

Report generation causes primary read IOPS to spike:
  → Report queries run against replica; primary IOPS stabilized

Primary connection count approaching max_connections:
  → Read replica provides additional connection capacity (but RDS Proxy is better
     for connection pooling — replicas add read capacity, not connection capacity)
```

**Traffic routing patterns:**

```typescript
// Pattern 1: Application-level routing (simplest)
// Two separate TypeORM connections in NestJS

// database.module.ts
@Module({
  imports: [
    TypeOrmModule.forRoot({
      name:     'primary',
      type:     'postgres',
      host:     process.env.DB_PRIMARY_HOST,   // primary endpoint
      // ... primary config
    }),
    TypeOrmModule.forRoot({
      name:     'replica',
      type:     'postgres',
      host:     process.env.DB_REPLICA_HOST,   // read replica endpoint
      // ... replica config (same credentials, read-only user)
    }),
  ],
})
export class DatabaseModule {}

// In service: explicit connection selection
@Injectable()
export class LoanService {
  constructor(
    @InjectRepository(Loan, 'primary')  private loanRepo:         Repository<Loan>,
    @InjectRepository(Loan, 'replica')  private loanReplicaRepo:  Repository<Loan>,
  ) {}

  // Writes: always primary
  async createLoan(dto: CreateLoanDto): Promise<Loan> {
    return this.loanRepo.save(dto);
  }

  // Reads that tolerate lag: replica
  async getLoanDashboard(merchantId: string): Promise<DashboardSummary> {
    return this.loanReplicaRepo
      .createQueryBuilder('loan')
      .where('loan.merchantId = :merchantId', { merchantId })
      .getMany();
  }

  // Reads that require freshness (immediately after write): primary
  async getLoanById(id: string): Promise<Loan> {
    return this.loanRepo.findOneOrFail({ where: { id } });
  }
}
```

```
Pattern 2: RDS Proxy with read/write splitting
  Single endpoint for application → Proxy routes writes to primary,
  reads to replica automatically based on query type (SELECT → replica).
  Session pinning: after any write, Proxy pins the session to primary
  for read-your-writes consistency.
  Advantage: zero application code change; works transparently.
  Limitation: Proxy's query analysis is not 100% accurate; complex
              transactions may be misrouted. Explicit routing (Pattern 1)
              is more reliable for critical paths.

Pattern 3: PgBouncer with multiple databases
  PgBouncer configured with two pools:
    pool_mode = transaction
    primary_db → primary endpoint
    replica_db → replica endpoint
  Application uses separate connection strings per pool.
  PgBouncer handles connection multiplexing on each.
```

**Cross-region read replicas:**
```
Use cases:
  Disaster recovery in a secondary region (replica promoted to primary if region fails)
  Serving read traffic to users in a geographically distant region
  Offloading analytics to a region with lower compute costs

Setup:
  Primary: ap-south-1 (Mumbai)
  Cross-region replica: ap-southeast-1 (Singapore)
  Lag: typically 100–500ms for cross-region (network RTT between regions)
  Cost: cross-region data transfer charges apply (per-GB)

Promotion to standalone primary (DR scenario):
  aws rds promote-read-replica --db-instance-identifier my-sg-replica
  Replica becomes independent primary (breaks replication; no longer receives updates)
  New primary takes ~5 minutes to finalize promotion
  Application must update its connection string to point to the new primary
  Old primary (if recovered) becomes a standalone instance; data must be re-synced
  manually or via a new replica relationship
```

## Section 4: RDS Parameter Groups

**Q8. What are RDS Parameter Groups and how do you use them for performance tuning?**
A: A Parameter Group is a named collection of database engine configuration settings (equivalent to `postgresql.conf` or `my.cnf`) that you attach to an RDS instance. Instead of editing config files directly (which is not possible in RDS), you modify the Parameter Group and RDS applies the changes.

**Parameter types:**
```
Static parameters:
  Require a database instance reboot to take effect.
  Examples: max_connections, shared_buffers (PostgreSQL)
  RDS marks the instance as "pending-reboot" when a static parameter changes.

Dynamic parameters:
  Applied immediately without a reboot.
  Examples: work_mem, log_min_duration_statement, checkpoint_completion_target
  Changes take effect on new connections (or immediately for session-level parameters).
```

**Critical PostgreSQL parameters for fintech RDS workloads:**

```sql
-- shared_buffers: PostgreSQL's internal cache
-- Rule: 25% of instance RAM
-- t3.medium (4 GiB): 1 GiB
-- r6g.2xlarge (64 GiB): 16 GiB
-- Static — requires reboot
shared_buffers = '16GB'

-- work_mem: memory per sort/hash operation PER QUERY
-- Danger: if 100 connections each run a sort → 100 × work_mem RAM used simultaneously
-- Rule: (RAM × 0.25) / max_connections / typical_sorts_per_query
-- For 200 connections, 64 GiB instance: (64 GiB × 0.25) / 200 / 2 = ~40 MB
-- Dynamic — applies to new connections
work_mem = '40MB'

-- max_connections: hard limit on simultaneous DB connections
-- PostgreSQL uses one process per connection (expensive)
-- Rule: do NOT set to application thread count; use connection pooler
-- Typical: 100–200 for most RDS workloads (PgBouncer/RDS Proxy pools above this)
-- Static — requires reboot
max_connections = 200

-- effective_cache_size: hint to query planner about total available cache
-- (shared_buffers + OS page cache)
-- Rule: 75% of instance RAM
effective_cache_size = '48GB'

-- checkpoint_completion_target: spread checkpoint I/O over this fraction of the
-- checkpoint interval (reduces I/O spikes)
-- Default: 0.9 (spread over 90% of checkpoint_timeout)
-- Dynamic
checkpoint_completion_target = 0.9

-- wal_buffers: write-ahead log buffer (in memory before fsync)
-- Default: auto (-1 = 1/32 of shared_buffers)
-- Set explicitly for high-write workloads
-- Static
wal_buffers = '64MB'

-- log_min_duration_statement: log queries slower than N milliseconds
-- 0 = log all queries (very verbose; for debugging only)
-- 1000 = log queries > 1 second (production baseline)
-- 100 = log queries > 100ms (aggressive query monitoring)
-- Dynamic
log_min_duration_statement = 1000

-- autovacuum settings for high-write tables (payment_transactions, loan_events)
-- Prevent table bloat from dead tuples accumulating
autovacuum_vacuum_scale_factor   = 0.01   -- vacuum when 1% of table is dead tuples
                                           -- (default 20% is too aggressive for large tables)
autovacuum_analyze_scale_factor  = 0.005  -- analyze when 0.5% new/changed rows
autovacuum_vacuum_cost_delay     = 2      -- ms delay between vacuum I/O bursts (throttle)
```

**Custom Parameter Group workflow:**
```
1. Create custom parameter group (never modify the default — it's read-only):
   aws rds create-db-parameter-group \
     --db-parameter-group-name fintech-pg16-production \
     --db-parameter-group-family postgres16 \
     --description "Production PostgreSQL 16 tuning for fintech OLTP"

2. Modify parameters:
   aws rds modify-db-parameter-group \
     --db-parameter-group-name fintech-pg16-production \
     --parameters \
       "ParameterName=shared_buffers,ParameterValue=4GB,ApplyMethod=pending-reboot" \
       "ParameterName=work_mem,ParameterValue=32MB,ApplyMethod=immediate" \
       "ParameterName=log_min_duration_statement,ParameterValue=500,ApplyMethod=immediate"

3. Attach to RDS instance:
   aws rds modify-db-instance \
     --db-instance-identifier fintech-prod-pg \
     --db-parameter-group-name fintech-pg16-production \
     --apply-immediately

4. Reboot for static parameter changes:
   aws rds reboot-db-instance \
     --db-instance-identifier fintech-prod-pg

5. Verify applied parameters:
   SELECT name, setting, unit, context
   FROM pg_settings
   WHERE name IN ('shared_buffers', 'work_mem', 'max_connections')
   ORDER BY name;
```

**Option Groups (separate from Parameter Groups):**
```
Option Groups apply to features that are add-ons to the engine, not configuration:
  Oracle: Advanced Security, Statspack, S3 integration
  SQL Server: SSRS, SSAS, transparent data encryption
  MySQL: MariaDB Audit Plugin, Memcached integration

PostgreSQL uses Parameter Groups only (no Option Groups for core features).
PostgreSQL extensions (pg_stat_statements, pgcrypto, uuid-ossp) are enabled via:
  CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
  -- or via rds.allowed_extensions parameter in newer RDS versions
```

## Section 5: ElastiCache

**Q9. What is ElastiCache and when do you choose Redis vs Memcached?**
A: ElastiCache is AWS's managed in-memory caching service, offering two engines: Redis and Memcached. Both store data in RAM for sub-millisecond access, but they have fundamentally different architectures and capabilities.

**Redis vs Memcached decision:**

| Dimension | Redis | Memcached |
|---|---|---|
| Data structures | Strings, hashes, lists, sets, sorted sets, streams, bitmaps | Strings only |
| Persistence | Optional (RDB snapshots, AOF) | None — restart = empty cache |
| Replication | Yes (primary-replica) | No |
| High availability | Yes (Multi-AZ with auto-failover) | No (single node per shard) |
| Pub/Sub | Yes (PUBLISH / SUBSCRIBE) | No |
| Lua scripting | Yes (EVAL) | No |
| Cluster mode | Yes (sharded, up to 500 nodes) | Yes (multi-threaded, simpler sharding) |
| Multi-threading | Single-threaded per shard (I/O threads in 6.x+) | Multi-threaded natively |
| Horizontal scale | Redis Cluster (manual or ElastiCache sharding) | Add nodes; client hashes keys |
| Transactions | Yes (MULTI/EXEC) | No |
| Use case | Session store, rate limiting, leaderboards, distributed locks, queues, pub/sub | Simple key-value cache, high-throughput read cache |

**When to choose Memcached:**
```
You need pure caching with maximum throughput:
  No persistence needed (cache is fully rebuildable from DB)
  No replication needed (stale cache on node loss is acceptable)
  Multi-threaded performance matters (Memcached scales across all CPU cores;
  Redis is single-threaded per node — at very high command rates, Memcached
  saturates CPU later)
  Data is always strings (no complex data structures needed)
  Horizontal scale via simple sharding (client-side consistent hashing)

Memcached is NOT a good choice for fintech because:
  No persistence = cache warms cold on restart = all requests hit DB simultaneously
  No replication = node failure = 100% cache miss for that shard
  No pub/sub = cannot use for real-time event delivery
  No sorted sets = cannot implement leaderboards or rate limiters efficiently
```

**When to choose Redis (almost always in fintech):**
```
Session store: USER:{userId} → JWT session data, permissions, preferences
  Hash data structure; TTL per key; persistence ensures sessions survive restarts

Rate limiting: INCR + EXPIRE for sliding window; sorted sets for precise windows
  Atomic operations; Lua scripting for compare-and-set

Distributed locks: SET key value NX PX 30000 (Redlock pattern)
  SETNX + PX (expire in milliseconds) = mutex across NestJS instances

Job queues: BullMQ uses Redis lists and sorted sets internally
  Reliable queue with retry, delay, priority

Pub/sub for WebSocket events: PUBLISH / SUBSCRIBE
  (as discussed in the Socket.io Redis adapter topic)

Idempotency key store: SET payment:idempotency:{key} {response} EX 86400
  Deduplicate payment requests; atomic check-and-set

Leaderboard / ranked results: ZADD, ZRANGE with sorted sets
  Merchant transaction volume ranking; KYC risk scoring tiers
```

**Q10. How does ElastiCache Redis cluster mode work, and what is the difference between cluster mode disabled and enabled?**
A: ElastiCache Redis offers two cluster configurations with fundamentally different sharding and failover behaviors.

**Cluster Mode Disabled (replication group — single shard):**
```
Architecture:
  1 primary node + 0–5 read replicas
  All data lives on ONE shard (one primary)
  Replicas are exact copies of the primary (full dataset on each replica)
  Max data size: limited by a single node's RAM

  Primary (us-east-1a)
    ├── Replica 1 (us-east-1b) ← async replication
    └── Replica 2 (us-east-1c) ← async replication

Endpoints:
  Primary endpoint:  reads + writes → always the current primary
  Reader endpoint:   reads only → load-balanced across replicas
  Individual endpoints: per-node (for debugging)

Failover:
  Primary fails → ElastiCache promotes a replica to primary (~30s)
  DNS updated to point primary endpoint to new primary
  Application reconnects via primary endpoint (no config change needed)

Use when:
  Total dataset fits in one node (< 100–200 GiB for most node types)
  You need read replicas for read scaling but not write scaling
  Simplest setup; easiest to manage
  Read-heavy workloads (many replicas share read load)
```

**Cluster Mode Enabled (sharded cluster):**
```
Architecture:
  2–500 shards, each shard is a replication group (1 primary + 0–5 replicas)
  Data is hash-slotted across shards: 16,384 hash slots total
  Each shard owns a range of hash slots
  Keys are assigned to slots by: CRC16(key) % 16384

  Shard 1 (slots 0–5460):       Shard 2 (slots 5461–10922):     Shard 3 (slots 10923–16383):
    Primary (AZ-a)                 Primary (AZ-b)                   Primary (AZ-c)
    Replica (AZ-b)                 Replica (AZ-c)                   Replica (AZ-a)

Endpoints:
  Configuration endpoint: client connects here to discover cluster topology
  No separate primary endpoint per shard — client library handles slot routing

Client requirement:
  Must use a Redis Cluster-aware client:
    Node.js: ioredis in cluster mode
    Java: Lettuce or Jedis cluster
  Client receives the hash slot map on CLUSTER SLOTS command
  Client routes each command to the correct shard based on the key's slot

  const redis = new Redis.Cluster([
    { host: 'cluster.abc.cache.amazonaws.com', port: 6379 }
  ], {
    redisOptions: {
      tls: {},
      password: process.env.REDIS_AUTH_TOKEN,
    },
    scaleReads: 'slave',  // route read commands to replicas
  });

Limitations of cluster mode:
  Multi-key commands only work if all keys are in the SAME slot:
    MGET, MSET: all keys must hash to the same slot
    Cross-slot transactions: NOT supported (MULTI/EXEC across different keys
    on different shards fails)
    Solution: use hash tags to colocate keys: {user:123}:session, {user:123}:cart
              → both hash by 'user:123' → same slot → same shard

  Lua scripts: all keys used in the script must be on the same shard

Use when:
  Dataset exceeds a single node's RAM (cluster scales write throughput + memory)
  Write throughput exceeds what a single primary can handle
  Need > 250 GiB of cache memory
```

**Q11. How do you implement common caching patterns with ElastiCache Redis in a NestJS fintech service?**
A: The four canonical caching patterns each have specific failure modes and consistency implications.

**Cache-Aside (Lazy Loading) — most common:**
```typescript
@Injectable()
export class LoanCacheService {
  constructor(
    @InjectRedis()         private redis:     Redis,
    private readonly repo: LoanRepository,
  ) {}

  async getLoan(loanId: string): Promise<Loan> {
    const cacheKey = `loan:${loanId}`;

    // 1. Check cache
    const cached = await this.redis.get(cacheKey);
    if (cached) return JSON.parse(cached);

    // 2. Cache miss → fetch from DB
    const loan = await this.repo.findOneOrFail({ where: { id: loanId } });

    // 3. Populate cache (TTL: 5 minutes; loan status can change)
    await this.redis.set(cacheKey, JSON.stringify(loan), 'EX', 300);

    return loan;
  }

  // Invalidate on write (cache-aside is NOT write-through)
  async updateLoanStatus(loanId: string, status: LoanStatus): Promise<void> {
    await this.repo.update(loanId, { status });
    await this.redis.del(`loan:${loanId}`); // invalidate; next read repopulates
  }
}
```

**Write-Through — cache always consistent with DB:**
```typescript
async updateLoan(loanId: string, updates: Partial<Loan>): Promise<Loan> {
  // Write to DB first (source of truth)
  const updated = await this.repo.save({ id: loanId, ...updates });

  // Immediately update cache (write-through)
  await this.redis.set(
    `loan:${loanId}`,
    JSON.stringify(updated),
    'EX', 300,
  );

  return updated;
}
// Advantage: cache is always fresh immediately after write
// Disadvantage: write latency increases by one Redis SET
// Risk: if Redis SET fails, cache is stale until TTL expires or next write
//       → use a transaction or accept brief inconsistency
```

**TTL strategy for fintech data:**
```
Data freshness requirements → TTL:

Loan status (can change every few minutes during processing):
  TTL: 60–300 seconds; invalidate explicitly on status change

User profile / KYC data (changes rarely):
  TTL: 3600 seconds (1 hour); invalidate on profile update

NACH mandate status (changes during batch):
  TTL: 30 seconds during batch window; 300 seconds off-peak
  Or: no cache during batch (write-through would be too slow; skip cache entirely)

Exchange rates / market data (changes frequently):
  TTL: 5–30 seconds; accept slight staleness for performance
  Or: use pub/sub to push new rates to a local in-process cache
      (avoid Redis round-trip per rate lookup)

Static reference data (states, product types, fee schedules):
  TTL: 3600–86400 seconds; invalidate on config change
  Can use write-through since changes are admin-driven and rare

Rule: TTL = acceptable staleness × safety factor
  If you can tolerate 5 minutes of stale data: TTL = 300s (not 600s)
  Shorter TTL = fresher data = more DB hits = less cache benefit
  Find the minimum TTL that keeps DB load within acceptable bounds
```

**Distributed rate limiting with Redis:**
```typescript
// Sliding window rate limiter using Redis sorted sets
// 100 requests per minute per user

async function rateLimitCheck(
  redis:    Redis,
  userId:   string,
  limit:    number,
  windowMs: number,
): Promise<{ allowed: boolean; remaining: number }> {
  const key       = `rate:${userId}`;
  const now       = Date.now();
  const windowStart = now - windowMs;

  // Lua script: atomic check-and-increment
  const script = `
    local key        = KEYS[1]
    local now        = tonumber(ARGV[1])
    local windowStart = tonumber(ARGV[2])
    local limit      = tonumber(ARGV[3])
    local ttl        = tonumber(ARGV[4])

    -- Remove entries outside the window
    redis.call('ZREMRANGEBYSCORE', key, '-inf', windowStart)

    -- Count requests in window
    local count = redis.call('ZCARD', key)

    if count < limit then
      -- Add this request
      redis.call('ZADD', key, now, now)
      redis.call('EXPIRE', key, ttl)
      return {1, limit - count - 1}  -- allowed, remaining
    else
      return {0, 0}  -- denied
    end
  `;

  const [allowed, remaining] = await redis.eval(
    script, 1, key,
    now.toString(),
    windowStart.toString(),
    limit.toString(),
    Math.ceil(windowMs / 1000).toString(),
  ) as [number, number];

  return { allowed: allowed === 1, remaining };
}
```

**Q12. How does ElastiCache Redis handle failover and what is the difference between ElastiCache Serverless and provisioned clusters?**
A: ElastiCache Redis failover (cluster mode disabled) works similarly to RDS Multi-AZ — a replica is promoted to primary when the primary fails, with DNS updated to the new primary's address.

**Failover mechanics:**
```
Primary node fails (host crash, AZ event):
  ElastiCache detects failure (~10 seconds)
  Selects replica with least replication lag for promotion
  Promotes replica to primary:
    - Replica stops accepting replication from (now-dead) primary
    - Replica flushes its replication backlog
    - Replica begins accepting writes
  DNS record updated: primary endpoint → new primary IP
  DNS TTL: 1 second (extremely short for fast client recovery)

Failover time: ~30–60 seconds

Application behavior during failover:
  Redis commands in-flight: fail with connection error
  Connection pool: stale connections to old primary → EOF / ECONNRESET
  Recovery: pool reconnects to primary endpoint → resolves new IP → reconnects
  In-flight commands: must be retried by application

ioredis automatic failover handling:
  const redis = new Redis({
    host:                process.env.REDIS_PRIMARY_ENDPOINT,
    port:                6379,
    password:            process.env.REDIS_AUTH_TOKEN,
    tls:                 {},
    maxRetriesPerRequest: 3,     // retry each command 3 times
    retryStrategy: (times) => {
      if (times > 10) return null; // stop retrying after 10 attempts
      return Math.min(times * 200, 2000); // 200ms, 400ms, ... 2s backoff
    },
    reconnectOnError: (err) => {
      // Reconnect on READONLY errors (sent by old primary after promotion)
      return err.message.includes('READONLY');
    },
  });
```

**ElastiCache Serverless:**
```
Launched 2023. Fundamentally different model from provisioned clusters:

Provisioned clusters:
  You choose node type (cache.r7g.large, cache.r6g.xlarge, etc.)
  You choose number of nodes, replication factor, shard count
  You pay per node-hour (regardless of actual cache utilization)
  Capacity planning required: over-provision or risk evictions

ElastiCache Serverless:
  No node selection — AWS manages underlying infrastructure
  Auto-scales capacity up and down (within milliseconds)
  Pay per: GB-hours of data stored + ECPUs (cache processing units) consumed
  No capacity planning — just connect and use
  Maximum data storage: 5 TiB per cache
  VPC: yes (same VPC endpoint model as provisioned)

Cost comparison:
  Low utilization: Serverless is cheaper (no idle node cost)
  High sustained utilization: Provisioned is cheaper (fixed node cost amortizes)
  Breakeven: roughly at 50–70% sustained cache utilization

When Serverless wins:
  Unpredictable traffic (weekend spikes, seasonal fintech campaigns)
  Development / staging environments (low utilization, variable load)
  New services with unknown cache usage patterns
  Teams without Redis expertise for capacity planning

When Provisioned wins:
  Sustained high utilization (> 70% of peak consistently)
  Need specific cluster mode features (complex sharding)
  Cost-sensitive at large scale (> 500 GiB, predictable load)
  Precise IOPS/throughput control for latency-sensitive paths
```

## Section 6: DynamoDB Basics

**Q13. What is DynamoDB and what are its core data model concepts?**
A: DynamoDB is AWS's fully managed NoSQL database — a key-value and document store that delivers single-digit millisecond latency at any scale. Unlike RDS, it has no schema enforcement, no SQL, and no joins — all data access is through primary key lookups or secondary indexes.

**Core data model:**
```
Table:
  The top-level container. No schema definition (except the primary key).
  Items (rows) can have different attributes (columns) within the same table.

Item:
  A single record. Collection of attributes.
  Maximum size: 400 KB per item.

Attribute:
  Key-value pair within an item. Types: String (S), Number (N), Binary (B),
  Boolean (BOOL), Null (NULL), List (L), Map (M), StringSet (SS), NumberSet (NS).

Primary Key — two forms:
  Simple primary key (Partition Key only):
    One attribute uniquely identifies each item.
    Example: { PK: "USER#usr_001" }
    Use when: items are always accessed by this single key.

  Composite primary key (Partition Key + Sort Key):
    Two attributes together uniquely identify each item.
    Partition Key determines which shard stores the item.
    Sort Key enables range queries and ordering within a partition.
    Example: { PK: "USER#usr_001", SK: "LOAN#loan_042" }
    Use when: one-to-many relationships (one user has many loans).

Secondary Indexes:
  Global Secondary Index (GSI):
    Alternative partition key + sort key on the same table.
    Allows querying by attributes that are NOT the primary key.
    Maintains its own partition; eventually consistent with base table.
    Up to 20 GSIs per table.
    Example: GSI on { PK: "MERCHANT#merch_42", SK: "createdAt" }
             to query all loans for a merchant ordered by creation date.

  Local Secondary Index (LSI):
    Same partition key, different sort key.
    Must be defined at table creation time (cannot add later).
    Strongly consistent reads possible (unlike GSI).
    Up to 5 LSIs per table.
    Example: LSI on { PK: "USER#usr_001", SK: "status" }
             to query all of a user's loans filtered by status.
```

**Q14. How does DynamoDB capacity work, and when do you use on-demand vs provisioned mode?**
A: DynamoDB offers two capacity modes that determine how throughput is billed and how the table handles traffic.

**Provisioned Capacity Mode:**
```
You specify:
  Read Capacity Units (RCUs): 1 RCU = 1 strongly consistent read/s of items ≤ 4 KB
                               or 2 eventually consistent reads/s of items ≤ 4 KB
  Write Capacity Units (WCUs): 1 WCU = 1 write/s of items ≤ 1 KB

If you exceed provisioned RCUs/WCUs: DynamoDB returns ProvisionedThroughputExceededException
  (your application must retry with exponential backoff)

Auto Scaling:
  DynamoDB Auto Scaling adjusts RCUs/WCUs based on actual traffic (similar to ASG).
  Target: maintain utilization at a target percentage (default 70%).
  Scaling is not instant — takes 1–2 minutes to scale up.
  Does NOT handle sudden spikes (scale-up lag can cause throttling).

Cost: pay per RCU/WCU-hour provisioned (not consumed)
  → Wasteful if utilization is uneven; efficient at sustained predictable load.

Use when:
  Traffic is predictable (known peak RCU/WCU)
  Cost optimization at sustained high throughput is important
  Long-term committed workload (can pair with Reserved Capacity 1/3-year)
```

**On-Demand Capacity Mode:**
```
DynamoDB handles any traffic level automatically.
No RCU/WCU provisioning required.
You pay per request:
  Read: $0.25 per million read request units
  Write: $1.25 per million write request units

No throttling (DynamoDB scales instantly to handle any request rate).
Exception: cold start after a table has been idle — briefly throttled until
  DynamoDB provisions capacity. Warm tables handle spikes immediately.

Use when:
  Traffic is unpredictable (new application, variable workload, spiky patterns)
  Throughput is unknown (early-stage product)
  Development, staging, or test tables
  Traffic is low and sporadic (on-demand is expensive at sustained high throughput
  compared to provisioned — roughly 5× more expensive per request)

Breakeven: on-demand becomes more expensive than provisioned at roughly
  ~18% sustained table utilization. Above that, provisioned is cheaper.
  Rule: start with on-demand; switch to provisioned once you know your
  steady-state RCU/WCU requirements from 2–4 weeks of on-demand usage data.
```

**Q15. What is the DynamoDB single-table design pattern and when is it appropriate?**
A: Single-table design packs multiple entity types into one DynamoDB table, using generic attribute names (PK, SK) and access-pattern-driven secondary indexes to support all query requirements. It is the idiomatic DynamoDB design pattern recommended by AWS.

**Why single-table:**
```
In relational databases: one table per entity type; JOIN for relationships.
In DynamoDB: joins are not supported; all related data must be co-located
or accessed via separate GetItem calls (expensive if N+1 pattern).

Single-table design:
  All entity types (Users, Loans, Payments, Documents) in ONE table.
  PK and SK structured to support access patterns:
    PK: "USER#usr_001"       SK: "METADATA"          → user record
    PK: "USER#usr_001"       SK: "LOAN#loan_042"      → user's loan (relationship)
    PK: "LOAN#loan_042"      SK: "METADATA"           → loan record
    PK: "LOAN#loan_042"      SK: "PAYMENT#pay_001"    → payment within loan
    PK: "MERCHANT#merch_42"  SK: "LOAN#loan_042"      → merchant's loan list

Access pattern: get all loans for a user
  Query: PK = "USER#usr_001", SK begins_with "LOAN#"
  Returns: all SK values starting with "LOAN#" → all loan references for this user

Access pattern: get all payments for a loan
  Query: PK = "LOAN#loan_042", SK begins_with "PAYMENT#"

Access pattern: get all loans for a merchant
  GSI: PK = "MERCHANT#merch_42", SK begins_with "LOAN#"
  (GSI overloads the GSI PK to serve a different entity's access pattern)
```

**When single-table is appropriate:**
```
Well-suited:
  Access patterns are well-defined and finite (fintech apps with known query needs)
  Relationships between entities must be fetched in one query
  Very high throughput (single table avoids cross-table transaction complexity)
  DynamoDB Transactions (ACID across items in the same table) are needed

Poorly suited:
  Ad-hoc queries (analytics, reporting) — DynamoDB is not a query engine
  Many-to-many relationships with complex filter requirements
  Evolving access patterns (adding new query needs requires new GSIs)
  Team unfamiliar with DynamoDB — learning curve is steep

When NOT to use DynamoDB (prefer RDS/PostgreSQL):
  Complex relational queries (multi-table JOINs, GROUP BY, aggregations)
  Ad-hoc reporting and analytics (DynamoDB has no query optimizer)
  Strong ACID transactions across many entity types
  Full-text search (use OpenSearch/Elasticsearch instead)
  Historical data analysis (Redshift or Athena on S3 is better)

DynamoDB fintech sweet spots:
  Session store (though Redis is better for this use case)
  Idempotency key tracking (write-once, read-once, TTL)
  Audit log (append-only; query by entity ID + timestamp range)
  Feature flags / configuration (small, read-heavy, key-value)
  Event sourcing (immutable event log; query by aggregate ID + sequence)
```

**Q16. What are DynamoDB Streams and how do they enable event-driven architectures?**
A: DynamoDB Streams captures a time-ordered sequence of item-level modifications (INSERT, MODIFY, REMOVE) in a DynamoDB table, retaining them for 24 hours. AWS Lambda can process these stream records with at-least-once delivery semantics.

**Stream event types:**
```
StreamViewType options:
  KEYS_ONLY:     PK and SK of the changed item
  NEW_IMAGE:     entire item after the change
  OLD_IMAGE:     entire item before the change
  NEW_AND_OLD_IMAGES: both before and after (most useful for audit logs)

Stream record example (MODIFY event):
{
  "eventName": "MODIFY",
  "dynamodb": {
    "Keys":     { "PK": { "S": "LOAN#loan_042" }, "SK": { "S": "METADATA" } },
    "NewImage": { "PK": { "S": "LOAN#loan_042" }, "status": { "S": "APPROVED" } },
    "OldImage": { "PK": { "S": "LOAN#loan_042" }, "status": { "S": "PENDING" } },
    "SequenceNumber": "111",
    "SizeBytes": 26,
    "StreamViewType": "NEW_AND_OLD_IMAGES"
  }
}
```

**Event-driven pattern with DynamoDB Streams + Lambda:**
```
                DynamoDB Table
                (loan_events)
                      │
                      │ DynamoDB Stream (24h retention)
                      ▼
              Lambda Function (event processor)
              ├── Extract changed item (NEW_IMAGE)
              ├── Filter: only LOAN status change events
              ├── Publish to EventBridge / SNS / SQS
              │     (decouple downstream consumers)
              └── Consumers:
                    ├── Notification Service → SMS/email to borrower
                    ├── Analytics Service → update data warehouse
                    ├── Audit Service → write to immutable audit log
                    └── WebSocket Gateway → push status to merchant dashboard

Exactly-once guarantee:
  DynamoDB Streams provides AT-LEAST-ONCE delivery (records may be delivered twice
  during Lambda retries or resharding).
  Design downstream consumers as idempotent:
    Check: has this event (SequenceNumber) already been processed?
    → Store processed SequenceNumbers in a DynamoDB idempotency table
    → If already processed: skip; if new: process and record
```

    Cross-region replication: ap-south-1 → ap-southeast-1

  Instance: db.r7g.xlarge (4 vCPU, 32 GiB)

    Loan status cache: loan:{loanId} → JSON, TTL 300s, invalidate on update

    Distributed lock: lock:nachbatch:{date} → SET NX PX 3600000

DynamoDB (audit log, immutable event log):
  Table: platform_events

    PK: ENTITY#<entityType>#<entityId>
    SK: EVENT#<timestamp>#<eventType>
    Attributes: actorId, beforeState, afterState, metadata
  Access patterns:
    All events for a loan:   PK = ENTITY#LOAN#loan_042, SK begins_with EVENT#
    Events in time range:    PK = ENTITY#LOAN#loan_042, SK between EVENT#2024-01-01 and EVENT#2024-12-31
    All events by a user:    GSI: PK = ACTOR#usr_001, SK = timestamp

  Cold (1–7 years):  PostgreSQL table partitioning by month;
                     partitions older than 1 year exported to S3 (Parquet) via DMS

**Q18. "Your RDS primary CPU is at 90% and P99 latency has degraded from 50ms to 800ms. Walk through your diagnosis and remediation."**
A:

```
Immediate triage (first 5 minutes):

Step 1: Identify the query causing CPU spike
  SELECT pid, now() - pg_stat_activity.query_start AS duration,
         query, state, wait_event_type, wait_event
  FROM pg_stat_activity
  WHERE (now() - pg_stat_activity.query_start) > interval '5 seconds'
  ORDER BY duration DESC;

  Look for:
    Long-running SELECTs consuming CPU (missing index → seq scan)
    Many identical short queries (N+1 pattern; high volume)
    Locked queries (wait_event_type = 'Lock')
    Idle in transaction (connections holding locks without active query)

Step 2: Check for lock contention
  SELECT blocked_locks.pid     AS blocked_pid,
         blocked_activity.query AS blocked_query,
         blocking_locks.pid    AS blocking_pid,
         blocking_activity.query AS blocking_query
  FROM pg_catalog.pg_locks blocked_locks
  JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
  JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
  JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
  WHERE NOT blocked_locks.granted;

  If blocking: identify the blocking query → terminate if long-running:
  SELECT pg_terminate_backend(<blocking_pid>);

Step 3: Check CloudWatch metrics timeline
  CPUUtilization  → when did it spike? correlate with deployments, batch jobs
  DatabaseConnections → spike in connections? (connection storm after deploy)
  ReadIOPS / WriteIOPS → disk-bound or CPU-bound?
  ReplicaLag → spike here indicates write amplification
  SwapUsage → > 0 means RAM exhaustion → work_mem too high or shared_buffers too low

Step 4: Check pg_stat_statements (top queries by total time)
  SELECT query, calls, total_exec_time, mean_exec_time,
         rows, 100.0 * shared_blks_hit /
               nullif(shared_blks_hit + shared_blks_read, 0) AS hit_percent
  FROM pg_stat_statements
  ORDER BY total_exec_time DESC
  LIMIT 20;

  hit_percent < 90%: query reading from disk (index missing or buffer pool too small)
  high mean_exec_time: slow query (bad plan, missing index, bad join)
  high calls × mean_exec_time: N+1 pattern or high-frequency unoptimized query

Remediation paths:

Path A — Missing index (seq scan on high-CPU SELECT):
  EXPLAIN (ANALYZE, BUFFERS) <problem query>;
  Look for: Seq Scan with high rows, Filter removing many rows
  Fix: CREATE INDEX CONCURRENTLY idx_loans_merchant_status
         ON loans(merchant_id, status)
         WHERE status IN ('PENDING', 'APPROVED');
  CONCURRENTLY: does not lock the table during index build (safe in production)

Path B — N+1 query pattern:
  pg_stat_statements shows one query called 50,000 times in 5 minutes.
  Root cause: ORM loading entities without eager-loading relations.
  Immediate fix: route to read replica to reduce primary load
  Proper fix: add .leftJoinAndSelect() or query builder JOIN
              rewrite N+1 into one query with JOIN + IN clause

Path C — Connection storm (deploy caused all instances to reconnect simultaneously):
  DatabaseConnections metric spikes to max_connections → queuing
  Immediate fix: verify RDS Proxy is in front of RDS
  If no Proxy: increase max_connections (requires reboot; static parameter)
  Proper fix: deploy RDS Proxy to multiplex connections

Path D — NACH batch overwhelming primary:
  Batch writes + OLTP writes competing on same primary
  Immediate: throttle batch job (reduce parallelism / add sleep between inserts)
  Proper: route batch reads to read replica;
          use COPY (bulk insert) instead of individual INSERTs for batch loads
          Schedule batch for off-peak hours (02:00–04:00 IST)

Path E — work_mem causing OOM → swap:
  SwapUsage > 0; high sort/hash operations in EXPLAIN
  Reduce work_mem (dynamic parameter; applies to new connections immediately):
  aws rds modify-db-parameter-group \
    --db-parameter-group-name fintech-pg16-production \
    --parameters "ParameterName=work_mem,ParameterValue=16MB,ApplyMethod=immediate"
```

|---|---|

| Dynamic parameter | Immediate effect on new connections (e.g., work_mem) |

| ElastiCache concept | Key fact |
|---|---|

| Cluster Mode Enabled | Multi-shard; hash slots; cluster-aware client required |

| READONLY error on failover | Old primary sends READONLY after promotion; reconnect on this error |
| Serverless vs Provisioned | Serverless cheaper at < 50% utilization; Provisioned cheaper above |
| Multi-key commands in cluster | All keys must be in same slot; use hash tags `{user:123}:key` |

|---|---|

|---|---|---|

## The Core Mental Model

```
RDS Multi-AZ vs Read Replica in one sentence each:
  Multi-AZ: synchronous standby you can never query — it exists only to absorb
            the primary's failure transparently (RPO=0, RTO=~90s).
  Read Replica: asynchronous copy you query directly for reads — it reduces
                primary load but lags behind (RPO=seconds, manual promotion).
  You can and should have both: Multi-AZ for HA, replica for read scaling.

The RDS failover survival contract:
  DNS TTL is 5 seconds — but your connection pool must detect the broken
  connection AND re-resolve DNS. Use retry logic (3 attempts, exponential backoff).
  RDS Proxy cuts effective application RTO to ~20–30s and handles this for you.
  Never hardcode the IP — always use the RDS DNS endpoint.

Parameter Group discipline:
  Never modify the default parameter group (it is read-only; applied to all instances).
  Create one custom group per engine-version per environment.
  Static parameters (shared_buffers, max_connections) require a reboot — schedule
  the reboot during a maintenance window; plan for Multi-AZ failover to minimize downtime.
  Dynamic parameters (work_mem, log_min_duration_statement) apply immediately —
  use these for tuning without a maintenance window.

Redis cluster mode key insight:
  Cross-slot commands (MGET with keys on different shards, cross-shard MULTI/EXEC)
  fail silently or throw errors in cluster mode.
  Use hash tags: {user:123}:session and {user:123}:cart → same slot → safe MGET.
  Design key naming conventions before enabling cluster mode — retrofitting is painful.

DynamoDB access pattern discipline:
  Define ALL access patterns before designing the table.
  Every access pattern → either a primary key query or a GSI.
  If you cannot map an access pattern to a primary key or GSI: do not use DynamoDB
  for that workload (use PostgreSQL or add OpenSearch for search patterns).
  The worst DynamoDB mistake: Scan operations on large tables (full table read;
  expensive; slow; defeats the purpose of a key-value store).

The ElastiCache TTL rule for fintech:
  TTL = acceptable staleness × safety factor (never longer than the data's
  business-valid lifetime).
  Payment status (PENDING → APPROVED): TTL 60–300s; invalidate explicitly on change.
  Reference data (product types, fee schedules): TTL 3600–86400s.
  Idempotency keys: TTL 86400s (24h; covers retry window).
  Never cache without a TTL — unbounded cache growth causes eviction of hot keys.

The 7-year retention pattern:
  Do not store 7 years of data in your OLTP PostgreSQL instance.
  Partition by time (monthly) → detach old partitions → export to S3 (Parquet) →
  query via Athena ($5/TB scanned; zero RDS cost; scales to petabytes).
  DynamoDB Streams → Lambda → S3 (Glacier) for immutable audit logs.
  Hot/warm/cold tiering is the only cost-sustainable path for long retention.
```

**Tip for the interview:** Database questions at 5 YOE converge on three depth probes: (1) the Multi-AZ vs read replica distinction — knowing that Multi-AZ replication is synchronous (RPO=0) and the standby is never readable, while read replica replication is asynchronous (RPO=seconds) and the replica serves read traffic, and that these are orthogonal features you should often use together, demonstrates you understand the HA vs scalability axes independently; (2) the read-your-writes problem with replicas — knowing that a user who writes a record and immediately reads it from an asynchronously-lagging replica may see a stale response, and that the solutions (route post-write reads to primary, RDS Proxy session pinning, explicit replica lag waiting) each have different latency and correctness trade-offs, is the production nuance that separates someone who has debugged "my record disappeared" bugs from someone who has only used a single database endpoint; (3) the Parameter Group reboot discipline — knowing which PostgreSQL parameters are static (shared_buffers, max_connections — require reboot) vs dynamic (work_mem, log_min_duration_statement — immediate), why blindly increasing work_mem can cause OOM (100 connections × 256MB work_mem = 25 GiB RAM consumed by sorts alone), and how to safely apply static parameter changes using Multi-AZ failover as the zero-downtime reboot mechanism, shows operational maturity with managed databases. The fintech callout: for NACH batch processing with thousands of daily repayment records, partition loan_repayments by month and use COPY for bulk inserts (100–1000× faster than individual INSERTs) — the combination of table partitioning for query pruning and COPY for write throughput is the production pattern that keeps PostgreSQL performant at fintech scale without migrating to a more complex data store.
