# AWS ECS: Fargate vs EC2 Launch Type, and ECR — Interview Q&A (5 YOE Level)

---

## Section 1: ECS Fundamentals

**Q1. What is ECS and what problem does it solve over running containers directly on EC2?**
A: ECS (Elastic Container Service) is AWS's container orchestration service — it manages the placement, scheduling, health monitoring, scaling, and lifecycle of Docker containers across a fleet of compute resources. Running containers directly on EC2 without an orchestrator produces a set of problems that compound as you scale:

- **Manual placement**: which EC2 instance has enough CPU/memory to run this container? Doing this by hand means either over-provisioning (empty headroom on every instance) or under-provisioning (containers fail to start because the instance is full).
- **No health-driven replacement**: if a container crashes, nothing restarts it automatically. If the EC2 instance itself fails, all containers on it are gone — no rescheduling elsewhere.
- **No rolling deploys**: updating a container image means SSH-ing into instances, stopping the old container, pulling the new image, starting the new container — manually, sequentially, with downtime.
- **No service discovery**: containers get random IPs that change on restart. Load balancers cannot be updated manually fast enough to keep up.
- **No scaling automation**: when traffic spikes, someone must manually launch more instances and start more containers.

ECS solves all of these: it places containers on available compute, replaces unhealthy containers automatically, performs rolling deployments with configurable health check grace periods, integrates with ALB for service discovery, and supports auto-scaling based on CloudWatch metrics. The operator defines the desired state (run 10 copies of this container); ECS continuously reconciles actual state toward desired state.

**Q2. What are the core ECS concepts — cluster, task definition, task, and service — and how do they relate?**
A: ECS has four primary abstractions that compose the full operational model:

**Task Definition** — the blueprint (immutable, versioned):
```json
{
  "family":             "payment-service",
  "revision":           3,
  "cpu":                "512",
  "memory":             "1024",
  "networkMode":        "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "executionRoleArn":   "arn:aws:iam::123:role/ecsTaskExecutionRole",
  "taskRoleArn":        "arn:aws:iam::123:role/paymentServiceTaskRole",
  "containerDefinitions": [
    {
      "name":  "payment-service",
      "image": "123456789.dkr.ecr.ap-south-1.amazonaws.com/payment-service:v1.3.0",
      "portMappings": [{ "containerPort": 3000, "protocol": "tcp" }],
      "environment": [
        { "name": "NODE_ENV",  "value": "production" },
        { "name": "LOG_LEVEL", "value": "info" }
      ],
      "secrets": [
        { "name": "DB_PASSWORD", "valueFrom": "arn:aws:secretsmanager:...:secret:db-password" }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group":         "/ecs/payment-service",
          "awslogs-region":        "ap-south-1",
          "awslogs-stream-prefix": "ecs"
        }
      },
      "healthCheck": {
        "command":     ["CMD-SHELL", "curl -f http://localhost:3000/health || exit 1"],
        "interval":    30,
        "timeout":     5,
        "retries":     3,
        "startPeriod": 60
      }
    }
  ]
}
```

A task definition is an immutable version — changing any field creates a new revision. Task definitions are not running containers; they are specifications.

**Cluster** — the logical grouping of compute resources:
A cluster is a namespace for tasks and services. It contains either Fargate capacity (serverless, no instances to manage) or EC2 instances (self-managed or via Auto Scaling groups). A cluster can contain both launch types simultaneously. One AWS account can have multiple clusters — typically one per environment (dev, staging, prod) or one per application domain.

**Task** — a running instance of a task definition:
A task is one instantiation of a task definition — it is the actual running container(s). Tasks are ephemeral: they start, run, and stop. A task can contain multiple containers (sidecars — a logging agent, a proxy, a config reloader alongside the main app container). All containers in a task share the same network namespace (same IP address, communicate via localhost) and the same lifecycle (if the task stops, all its containers stop).

**Service** — the long-running supervisor:
A service ensures that a specified number of tasks are always running. If a task stops (container crash, health check failure, spot interruption), the service replaces it immediately. Services handle: desired count management, rolling deployments (replace old tasks with new tasks from a new task definition revision), integration with load balancers, and auto-scaling. Services are what you use for application servers, APIs, background processors — anything that should run continuously.

```
Cluster
  └── Service (desired: 10 tasks, running: 10 tasks)
        ├── Task (revision 3, running, healthy)
        ├── Task (revision 3, running, healthy)
        ├── ... (8 more)
        └── [on deploy: revision 4 tasks start, revision 3 tasks drain and stop]
```

## Section 2: Fargate vs EC2 Launch Type

**Q3. What is the Fargate launch type and what does AWS manage on your behalf?**
A: Fargate is a serverless compute engine for containers — you define what to run (task definition: CPU, memory, image) and AWS handles where and how to run it. You never see, manage, or SSH into the underlying EC2 instances that run your containers.

**What AWS manages in Fargate:**
- **Host instance provisioning**: AWS allocates an EC2 instance (from a pool AWS manages) to run your task. You specify CPU and memory; AWS picks an instance with capacity.
- **OS and kernel patching**: the underlying host OS is patched by AWS. You never run `yum update` on a Fargate host.
- **Container runtime**: Docker daemon, containerd, and the container runtime are managed by AWS.
- **Instance-level security**: host isolation between customers is managed by AWS using VM-level isolation (Firecracker microVMs).
- **Capacity management**: no need to manage Auto Scaling groups of EC2 instances to ensure there is always capacity for new tasks.

**What you still manage in Fargate:**
- **Container image**: your Docker image, its OS base layer, and application dependencies.
- **Task definition**: CPU, memory, environment variables, secrets, port mappings.
- **IAM roles**: task execution role (to pull ECR images, write logs) and task role (permissions your application needs — S3, DynamoDB, SQS, etc.).
- **Networking**: VPC, subnets, security groups. Each Fargate task gets its own ENI (Elastic Network Interface) — its own private IP in your VPC.
- **Logging**: configure CloudWatch Logs, Firelens, or another log driver in the task definition.

**Fargate resource model:**
Fargate allocates CPU and memory at the task level (not per container within the task). Valid CPU/memory combinations:

```
CPU (vCPU units)  Memory (GB)
0.25 vCPU         0.5, 1, 2
0.5 vCPU          1–4 (1GB increments)
1 vCPU            2–8 (1GB increments)
2 vCPU            4–16 (1GB increments)
4 vCPU            8–30 (1GB increments)
8 vCPU            16–60 (4GB increments)
16 vCPU           32–120 (8GB increments)
```

Fargate bills per second for the vCPU and memory allocated to the task, from task start until task stop — whether the container is idle or under full load.

**Q4. What is the EC2 launch type and when does the operational overhead justify using it over Fargate?**
A: The EC2 launch type runs ECS tasks on EC2 instances that you provision, register with the ECS cluster, and manage. The ECS agent (a daemon process) runs on each EC2 instance, polls the ECS control plane for task placement instructions, and manages container lifecycle on that instance.

**What you manage in EC2 launch type:**
- **EC2 instance fleet**: instance type, AMI (Amazon ECS-optimized AMI recommended), Auto Scaling group configuration, instance lifecycle.
- **ECS agent**: the agent is pre-installed on ECS-optimized AMIs; you manage updates and configuration.
- **Instance-level security**: OS patching, kernel updates, security agent installation.
- **Capacity management**: ensure the cluster has enough EC2 capacity to place new tasks. ECS Cluster Auto Scaling (Capacity Provider) helps automate this.
- **Instance storage**: local NVMe SSDs on instance types like `i3en` or `c5d` — available to containers on EC2, not available on Fargate.

**When EC2 launch type justifies the overhead:**

**Workloads requiring GPU:**
Fargate does not support GPU. ML inference, video transcoding, and any GPU-accelerated workload requires EC2 launch type with GPU instance types (`g4dn`, `p3`, `g5`).

**Windows containers:**
Fargate for Windows containers is available in limited regions. EC2 launch type with Windows ECS-optimized AMI is more broadly available and gives more control over Windows Server version.

**High-memory or unusual instance types:**
Fargate's largest configuration is 16 vCPU / 120GB memory. If you need `u-6tb1.metal` (6TB RAM) or specific instance families not available in Fargate, EC2 is required.

**Cost optimization at sustained high utilization:**
Fargate charges per-second for allocated CPU/memory. EC2 Reserved Instances or Savings Plans charge for the instance, regardless of container count. At high, sustained utilization — many tasks running 24/7 on well-understood instance types — EC2 Reserved Instances can be 40–60% cheaper than equivalent Fargate capacity.

```
Example: 20 tasks × (1 vCPU, 2GB memory) running 24/7

Fargate cost:
  20 × ($0.04048/vCPU-hour × 24 × 30) = $582/month
  20 × ($0.004445/GB-hour × 2GB × 24 × 30) = $128/month
  Total: ~$710/month

EC2 cost (m6i.4xlarge: 16 vCPU, 64GB — fits 16 tasks, need 2 instances):
  2 × m6i.4xlarge On-Demand: 2 × $0.768/hr × 730hr = $1,121/month
  2 × m6i.4xlarge 1-yr Reserved: 2 × $0.482/hr × 730hr = $704/month
  2 × m6i.4xlarge 3-yr Reserved: 2 × $0.306/hr × 730hr = $447/month
                                                           ↑ 37% cheaper than Fargate

Break-even: EC2 Reserved becomes cheaper than Fargate at ~70% average utilization
            Below that: Fargate is cheaper (pay only for what runs)
```

**Workloads requiring instance-local storage:**
Fargate provides ephemeral storage (20GB default, up to 200GB) but not high-speed NVMe SSDs. Containers that need fast local disk I/O (temporary files, sort buffers, local cache) can use instance NVMe storage on EC2 instance types.

**Network performance requirements:**
Some EC2 instance types (e.g., `c5n.18xlarge`) provide 100 Gbps network. Fargate's maximum network performance is lower and not explicitly specified per task.

**Q5. What is ECS Capacity Providers and how does it bridge the Fargate/EC2 decision?**
A: A Capacity Provider is an ECS abstraction that connects a service to a compute provider — either Fargate, Fargate Spot, or an EC2 Auto Scaling Group. It enables mixed compute strategies within a single service.

**Fargate Capacity Provider:**
```json
{
  "capacityProvider": "FARGATE",
  "weight": 1,
  "base": 2
}
```
Tasks run on standard Fargate. `base: 2` means at least 2 tasks always run on this provider.

**Fargate Spot Capacity Provider:**
Fargate Spot runs tasks on spare AWS compute capacity at up to 70% discount. AWS may reclaim Fargate Spot capacity with a 2-minute warning. Appropriate for fault-tolerant, interruptible workloads:
```json
{
  "capacityProvider": "FARGATE_SPOT",
  "weight": 4,
  "base": 0
}
```

**Mixed strategy — cost optimization with resilience:**
```json
// Service uses both Fargate and Fargate Spot
"capacityProviderStrategy": [
  { "capacityProvider": "FARGATE",      "weight": 1, "base": 2 },
  { "capacityProvider": "FARGATE_SPOT", "weight": 4, "base": 0 }
]
// Result: 2 guaranteed tasks on standard Fargate (base=2)
//         Remaining tasks split 1:4 Fargate:Spot
//         For 10 tasks: 2 on Fargate, 8 on Fargate Spot
//         Spot interruption affects at most 8 tasks; 2 survive
```

**EC2 Auto Scaling Group Capacity Provider:**
Registers an ASG with ECS. ECS Cluster Auto Scaling (CAS) manages the ASG's instance count based on task demand — scale out when tasks cannot be placed (insufficient capacity), scale in when instances are underutilized:

```json
{
  "capacityProvider": "my-asg-capacity-provider",
  "managedScaling": {
    "status": "ENABLED",
    "targetCapacity": 80,   // target 80% utilization of cluster capacity
    "minimumScalingStepSize": 1,
    "maximumScalingStepSize": 10
  },
  "managedTerminationProtection": "ENABLED"
  // Prevents ASG from terminating instances that still have running tasks
}
```

## Section 3: Task Networking and IAM

**Q6. How does ECS task networking work in `awsvpc` mode, and why is it the required mode for Fargate?**
A: ECS supports three network modes for tasks, but Fargate exclusively uses `awsvpc`. Understanding why reveals important architectural properties.

**Network modes:**

`bridge` (EC2 only): Containers share the EC2 host's network namespace via Docker's bridge network. Port mapping translates host ports to container ports. Multiple containers compete for host ports — you cannot run two containers that both want port 3000 on the same instance without port remapping. Used for legacy EC2 workloads.

`host` (EC2 only): Containers share the EC2 host's network namespace directly — the container uses the host's IP and ports directly. No port remapping; maximum network performance; but security isolation between containers is reduced. Rarely used.

`awsvpc` (EC2 and Fargate, required for Fargate): Each task gets its own Elastic Network Interface (ENI) with a private IP address in your VPC subnet. The container communicates directly on the VPC network — no NAT, no port remapping. Security groups are applied at the task level (not the instance level), enabling fine-grained network control per task.

**Why `awsvpc` is required for Fargate:**
Fargate tasks have no accessible host — there is no EC2 instance to share a network with. Each task is an isolated execution environment with its own ENI. The task's IP is a first-class VPC citizen: it appears in VPC Flow Logs, security group rules can reference it, and ALB target groups register the task IP directly.

**Security group model in `awsvpc`:**
```
Traditional EC2 (bridge mode):
  Security group → EC2 instance
  All containers on the instance share one security group

awsvpc mode:
  Security group → task (ENI)
  Each task has its own security group
  Payment service tasks: allow inbound 3000 from ALB security group
  Fraud service tasks: allow inbound 8080 from payment service security group
  → Fine-grained control: fraud service cannot receive traffic from ALB directly
```

**The ENI limit consideration (EC2 launch type):**
Each EC2 instance has a maximum number of ENIs that can be attached — determined by instance type. `t3.medium` supports 3 ENIs; `m5.xlarge` supports 4 ENIs; `c5.18xlarge` supports 15 ENIs. In `awsvpc` mode on EC2, each task consumes one ENI. This limits the number of tasks per instance — an `m5.xlarge` can run at most 4 tasks in `awsvpc` mode, regardless of CPU/memory availability.

**ENI Trunking** (VPC Trunk Interface): enables an EC2 instance to host more tasks than its ENI limit by using one trunk ENI shared across multiple tasks, with traffic separated by VLAN tags. Supported on specific instance types and requires the `AmazonECSInfrastructureRolePolicyForVpcLatticeTrunkingSupport` IAM policy.

**Q7. What are the two IAM roles in ECS and what does each control?**
A: ECS uses two distinct IAM roles per task, and confusing them is one of the most common ECS misconfiguration mistakes.

**Task Execution Role** (`executionRoleArn`):
Used by the **ECS agent and container runtime** — not by your application code. Controls what ECS infrastructure can do on behalf of your task during setup:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage",
        "ecr:GetAuthorizationToken"
      ],
      "Resource": "*"
      // Pull container image from ECR
    },
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:ap-south-1:123:log-group:/ecs/payment-service:*"
      // Write container stdout/stderr to CloudWatch Logs
    },
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "ssm:GetParameters"
      ],
      "Resource": [
        "arn:aws:secretsmanager:ap-south-1:123:secret:prod/db-password*",
        "arn:aws:ssm:ap-south-1:123:parameter/prod/*"
      ]
      // Inject secrets into container environment variables at startup
    }
  ]
}
```

If the execution role is missing or has wrong permissions, tasks fail to start: ECR pull fails (no auth), log stream creation fails (no CloudWatch permission), or secrets injection fails (no Secrets Manager access).

**Task Role** (`taskRoleArn`):
Used by **your application code running inside the container**. This is the role your Node.js/NestJS application assumes when making AWS SDK calls:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::fintech-payment-documents/*"
    },
    {
      "Effect": "Allow",
      "Action": ["sqs:SendMessage", "sqs:ReceiveMessage", "sqs:DeleteMessage"],
      "Resource": "arn:aws:sqs:ap-south-1:123:payment-events"
    },
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:ap-south-1:123:secret:prod/razorpay-key*"
      // For secrets the application fetches at runtime (not injected at startup)
    }
  ]
}
```

The application code accesses these permissions via the ECS metadata endpoint — the AWS SDK automatically retrieves temporary credentials from the task metadata endpoint at `169.254.170.2` without any explicit credential configuration needed in the application.

**The confusion:**
Secrets in `containerDefinitions.secrets` use the **execution role** (injected at container start by ECS infrastructure). Secrets fetched by application code at runtime via `secretsmanager.GetSecretValue()` use the **task role**. Both may need Secrets Manager access, but through different roles. The symptom of confusion: tasks start successfully (execution role works), but the application throws `AccessDeniedException` when trying to read a secret at runtime (task role missing the permission).

## Section 4: ECS Deployments

**Q8. How does ECS rolling deployment work, and what parameters control its behavior?**
A: A rolling deployment in ECS replaces old task definition revision tasks with new revision tasks incrementally, maintaining availability throughout. It is controlled by two parameters in the service's deployment configuration:

**`minimumHealthyPercent`**: the minimum percentage of desired tasks that must remain healthy during deployment.
**`maximumPercent`**: the maximum percentage of desired tasks (including both old and new) that can exist during deployment.

```
Service desired count: 10 tasks
Deployment configuration:
  minimumHealthyPercent: 100  → at least 10 tasks must be healthy at all times
  maximumPercent:        200  → at most 20 tasks can exist simultaneously

Rolling deployment sequence:
  Start:    10 old tasks running
  Step 1:   Start 10 new tasks (total: 20 — at maximumPercent)
  Step 2:   Wait for new tasks to pass health checks
  Step 3:   Terminate 10 old tasks (total: 10 new tasks — back to desired count)
  Duration: time for new tasks to become healthy + ALB deregistration delay

Alternative (zero-downtime with lower cost — some old replaced incrementally):
  minimumHealthyPercent: 50   → at least 5 tasks healthy
  maximumPercent:        150  → at most 15 tasks total

  Step 1: Terminate 5 old tasks (10 → 5; at minimumHealthyPercent)
  Step 2: Start 5 new tasks (5 + 5 = 10; back to desired)
  Step 3: Wait for new tasks to be healthy
  Step 4: Terminate remaining 5 old tasks
  Step 5: Start 5 more new tasks
  Duration: longer (two waves) but uses fewer instances simultaneously
```

**ALB deregistration delay and connection draining:**
When ECS terminates an old task, it first deregisters the task from the ALB target group and waits for the deregistration delay (default: 300 seconds) before stopping the container. During this window, the ALB drains existing connections (stops sending new requests; in-flight requests complete). Only after the delay expires does ECS send SIGTERM to the container process.

```
Sequence for a task being replaced:
  1. ECS sends deregistration request to ALB
  2. ALB stops routing new requests to this task (immediately)
  3. ALB waits for existing connections to finish (deregistration delay: 30–300s)
  4. After delay: ECS sends SIGTERM to container process
  5. Container handles SIGTERM (graceful shutdown: close connections, flush queues)
  6. startPeriod (shutdown timeout, default: 30s): if container still running → SIGKILL
  7. Container exits; task stops; ENI released
```

**Configuring for fast deployments:**
The deregistration delay (300s default) makes deployments slow — 5 minutes per wave. For microservices with short-lived connections (HTTP APIs), reduce it significantly:
```json
// ALB Target Group
"DeregistrationDelay": "30"   // 30 seconds is sufficient for most HTTP APIs
```

**NestJS graceful shutdown for ECS SIGTERM:**
```typescript
// main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(3000);

  // Handle SIGTERM from ECS graceful shutdown
  process.on('SIGTERM', async () => {
    console.log('SIGTERM received: closing HTTP server');
    await app.close(); // Stop accepting new requests; finish in-flight
    process.exit(0);
  });
}
```

**Q9. What is ECS Blue/Green deployment and how does it differ from rolling deployment?**
A: Blue/Green deployment maintains two complete environments (blue = current, green = new) and switches traffic between them atomically via a load balancer rule change. It enables instant rollback — if the green deployment is unhealthy, traffic switches back to blue in seconds, not minutes.

ECS Blue/Green deployments are managed by **CodeDeploy** (not ECS directly). The deployment shifts traffic through three phases:

```
Initial state:
  ALB → Blue Target Group → 10 old tasks (production traffic)
  Green Target Group → 10 new tasks (no traffic)

Test phase (optional):
  ALB test listener (port 8080) → Green Target Group → new tasks
  Run automated smoke tests against test listener
  (reject deployment if tests fail — no production impact)

Traffic shift:
  Linear10PercentEvery1Minute:  shift 10% of traffic to green every minute (10 min total)
  Canary10Percent5Minutes:      shift 10%, wait 5 minutes, then shift remaining 90%
  AllAtOnce:                    immediate full cutover (fastest; less safe)

Final state (if healthy):
  ALB → Green Target Group → 10 new tasks (all production traffic)
  Blue Target Group → 10 old tasks (on standby for rollback — kept for termination delay)

Rollback:
  CodeDeploy switches traffic back to blue target group immediately
  All new traffic goes to old tasks within seconds
  Green tasks are eventually terminated
```

**Blue/Green vs Rolling comparison:**

| Dimension | Rolling | Blue/Green |
|---|---|---|
| Rollback speed | Slow (redeploy old revision) | Instant (traffic switch) |
| Resource cost during deployment | Up to 2× tasks (briefly) | 2× tasks for full deployment |
| Production traffic exposure to new version | Incremental (fraction at a time) | Controlled by traffic shift policy |
| Test before production traffic | No | Yes (test listener) |
| Managed by | ECS | CodeDeploy + ECS |
| Complexity | Low | Medium |
| Zero-downtime guarantee | Near-zero (with correct config) | Yes |

**When to use Blue/Green:**
- Stateful services where mid-deployment state divergence is risky (e.g., a caching service where old and new versions have different cache schemas).
- Regulated environments where every deployment must be auditable with a defined rollback procedure.
- APIs where even a small fraction of traffic seeing a bad deploy is unacceptable — test listener validates before any production traffic touches the new version.
- When deployment velocity is lower but safety requirements are higher.

## Section 5: ECS Service Auto Scaling

**Q10. How does ECS Service Auto Scaling work and what metrics drive it?**
A: ECS Service Auto Scaling adjusts the desired task count of a service up or down in response to demand. It integrates with Application Auto Scaling, which applies scaling policies based on CloudWatch metrics.

**Three scaling policy types:**

**Target Tracking (recommended for most workloads):**
Specify a target value for a metric; ECS adjusts task count to keep the metric near that target. Simple to configure; handles both scale-out and scale-in automatically.

```typescript
// AWS CDK: Target Tracking on ECS service
const scaling = service.autoScaleTaskCount({
  minCapacity: 2,
  maxCapacity: 50,
});

// Scale on CPU utilization
scaling.scaleOnCpuUtilization('CpuScaling', {
  targetUtilizationPercent: 70,    // target: 70% CPU across all tasks
  scaleInCooldown:  Duration.seconds(300),  // wait 5 min before scaling in
  scaleOutCooldown: Duration.seconds(60),   // scale out faster than scale in
});

// Scale on memory utilization
scaling.scaleOnMemoryUtilization('MemoryScaling', {
  targetUtilizationPercent: 80,
});

// Scale on custom metric (e.g., SQS queue depth for worker services)
scaling.scaleOnMetric('QueueDepthScaling', {
  metric: new cloudwatch.Metric({
    namespace:  'AWS/SQS',
    metricName: 'ApproximateNumberOfMessagesVisible',
    dimensions: { QueueName: 'payment-processing-queue' },
    statistic:  'Maximum',
    period:     Duration.minutes(1),
  }),
  scalingSteps: [
    { upper: 0,    change: -1 },   // queue empty → scale in 1 task
    { lower: 100,  change: +2 },   // 100+ messages → scale out 2 tasks
    { lower: 1000, change: +5 },   // 1000+ messages → scale out 5 tasks
  ],
  cooldown: Duration.seconds(120),
});
```

**Step Scaling:**
Defines step adjustments — when metric crosses a threshold, add/remove a fixed number of tasks. More predictable than target tracking for workloads with known load profiles.

**Scheduled Scaling:**
Add tasks before a known peak (end-of-month reconciliation run, daily batch job start time), remove them after:
```typescript
scaling.scaleOnSchedule('ScaleOutForBatch', {
  schedule: Schedule.cron({ hour: '1', minute: '0' }),  // 1 AM daily
  minCapacity: 10,  // ensure at least 10 tasks at 1 AM
});

scaling.scaleOnSchedule('ScaleInAfterBatch', {
  schedule: Schedule.cron({ hour: '5', minute: '0' }),  // 5 AM daily
  minCapacity: 2,   // scale back down after batch completes
});
```

**SQS-based scaling for worker services:**
Worker services (that process messages from SQS) scale most naturally based on queue depth. The target: one task can process N messages per minute; if the queue has M messages, the target task count is M/N:

```typescript
// Custom scaling: target queue backlog per task
const backlogPerTask = new cloudwatch.MathExpression({
  expression: 'queueDepth / runningTasks',
  usingMetrics: {
    queueDepth:   queueDepthMetric,
    runningTasks: runningTasksMetric,
  },
});

scaling.scaleOnMetric('BacklogPerTask', {
  metric: backlogPerTask,
  // Target: 100 messages per task (each task processes 100 msg/min)
  // For 1000 messages: scale to 10 tasks
  // For 500 messages: scale to 5 tasks
});
```

## Section 6: ECR (Elastic Container Registry)

**Q11. What is ECR, how does authentication work, and what are its key features?**
A: ECR (Elastic Container Registry) is AWS's managed Docker container registry — the private registry where you push container images and ECS pulls them from. It is the AWS equivalent of Docker Hub or GitHub Container Registry, but with native IAM authentication, regional availability, and deep ECS integration.

**Authentication — the ECR auth token pattern:**
ECR uses temporary auth tokens rather than long-lived passwords. The token is valid for 12 hours.

```bash
# Authenticate Docker to ECR (generates a 12-hour token)
aws ecr get-login-password --region ap-south-1 \
  | docker login \
      --username AWS \
      --password-stdin \
      123456789.dkr.ecr.ap-south-1.amazonaws.com

# Pull an image
docker pull 123456789.dkr.ecr.ap-south-1.amazonaws.com/payment-service:v1.3.0

# Push an image
docker tag payment-service:latest \
       123456789.dkr.ecr.ap-south-1.amazonaws.com/payment-service:v1.3.0
docker push 123456789.dkr.ecr.ap-south-1.amazonaws.com/payment-service:v1.3.0
```

In ECS Fargate, the ECS agent handles ECR authentication automatically using the task execution role — no manual `docker login` in CI/CD is needed for ECS itself.

**ECR lifecycle policies — automated image cleanup:**

**ECR image scanning:**
ECR integrates with Amazon Inspector for vulnerability scanning of container images:
```json
// Repository scanning configuration
{
  "scanOnPush": true,    // scan every image immediately after push
  "scanFrequency": "CONTINUOUS_SCAN"  // re-scan daily for new CVEs
}
```

Scanning identifies known CVEs in OS packages and language runtime packages within the image. Critical findings can block deployments via CI/CD gate:

```bash
# In CI/CD pipeline: fail if critical vulnerabilities found
SCAN_RESULT=$(aws ecr describe-image-scan-findings \
  --repository-name payment-service \
  --image-id imageTag=v1.3.0 \
  --query 'imageScanFindings.findingSeverityCounts.CRITICAL' \
  --output text)

if [ "$SCAN_RESULT" -gt "0" ]; then
  echo "CRITICAL vulnerabilities found: $SCAN_RESULT. Blocking deployment."
  exit 1
fi
```

**Q12. How does a complete CI/CD pipeline integrate with ECR and ECS?**
A:

```
Pipeline: code push → build → test → push to ECR → deploy to ECS

Step 1: Code push triggers pipeline (GitHub Actions / CodePipeline)

Step 2: Build and tag Docker image
  docker build \
    --build-arg NODE_ENV=production \
    --build-arg BUILD_TIME=$(date -u +"%Y-%m-%dT%H:%M:%SZ") \
    -t payment-service:${GITHUB_SHA} \
    -t payment-service:latest \
    .

Step 3: Run tests (before pushing to ECR)
  docker run --rm payment-service:${GITHUB_SHA} npm test

Step 4: Push to ECR
  aws ecr get-login-password --region ap-south-1 | \
    docker login --username AWS --password-stdin ${ECR_REGISTRY}

  docker tag payment-service:${GITHUB_SHA} \
    ${ECR_REGISTRY}/payment-service:${GITHUB_SHA}
  docker tag payment-service:${GITHUB_SHA} \
    ${ECR_REGISTRY}/payment-service:latest

  docker push ${ECR_REGISTRY}/payment-service:${GITHUB_SHA}
  docker push ${ECR_REGISTRY}/payment-service:latest

Step 5: Image vulnerability scan (block on critical CVEs)
  aws ecr wait image-scan-complete \
    --repository-name payment-service \
    --image-id imageTag=${GITHUB_SHA}

  CRITICAL=$(aws ecr describe-image-scan-findings ...)
  [ "$CRITICAL" -gt 0 ] && exit 1

Step 6: Update ECS service (rolling deploy)
  # Update task definition with new image tag
  NEW_TASK_DEF=$(aws ecs describe-task-definition \
    --task-definition payment-service \
    --query 'taskDefinition' | \
    jq '.containerDefinitions[0].image = "'${ECR_REGISTRY}/payment-service:${GITHUB_SHA}'"' | \
    jq 'del(.taskDefinitionArn, .revision, .status, .requiresAttributes,
             .placementConstraints, .compatibilities, .registeredAt, .registeredBy)')

  NEW_REVISION=$(aws ecs register-task-definition \
    --cli-input-json "$NEW_TASK_DEF" \
    --query 'taskDefinition.taskDefinitionArn' \
    --output text)

  # Update service to use new task definition
  aws ecs update-service \
    --cluster prod-cluster \
    --service payment-service \
    --task-definition $NEW_REVISION \
    --force-new-deployment

Step 7: Wait for deployment to stabilize
  aws ecs wait services-stable \
    --cluster prod-cluster \
    --services payment-service
  # Exits 0 when all tasks running new revision and healthy
  # Exits 1 if deployment fails or times out (default: 40 checks × 15s = 10 minutes)
```

**Q14. "Your ECS Fargate tasks are failing to start. The service shows 'DesiredCount: 5, RunningCount: 0'. Walk through the diagnosis."**
A:

```
Step 1: Check service events (the first place to look)
  aws ecs describe-services \
    --cluster prod-cluster \
    --services payment-service \
    --query 'services[0].events[:10]'

  Common events and what they mean:
    "service payment-service was unable to place a task"
      → Capacity issue (subnet full of ENIs, AZ capacity unavailable in Fargate)
      → Fix: check subnet IP space; try different AZ; use FARGATE_SPOT

    "ECS was unable to assume the role ..."
      → Task execution role not configured or trust policy wrong
      → Fix: verify executionRoleArn; verify trust policy allows ecs-tasks.amazonaws.com

    "CannotPullContainerError: ... access denied"
      → ECR authentication failed
      → Fix: execution role missing ecr:GetAuthorizationToken or ecr:BatchGetImage

    "CannotPullContainerError: ... no basic auth credentials"
      → Image URI doesn't match ECR format, or wrong region
      → Fix: verify full ECR image URI including account ID and region

    "ResourceInitializationError: unable to pull secrets ..."
      → Secrets Manager or SSM permissions missing from execution role
      → Fix: add secretsmanager:GetSecretValue to execution role

Step 2: Check stopped tasks for exit codes
  aws ecs list-tasks \
    --cluster prod-cluster \
    --service-name payment-service \
    --desired-status STOPPED

  aws ecs describe-tasks \
    --cluster prod-cluster \
    --tasks <task-arn> \
    --query 'tasks[0].{stoppedReason: stoppedReason, containers: containers[*].{name: name, exitCode: exitCode, reason: reason}}'

  Exit codes and meanings:
    exitCode: 1   → Application crashed on startup; check CloudWatch Logs
    exitCode: 137 → OOM killed (container exceeded memory limit)
                    Fix: increase memory in task definition
    exitCode: 139 → Segmentation fault
    exitCode: null, reason: "Essential container in task exited"
                  → Container never started; check stoppedReason for root cause

Step 3: Check CloudWatch Logs for application errors
  aws logs get-log-events \
    --log-group-name /ecs/payment-service \
    --log-stream-name ecs/payment-service/<task-id> \
    --limit 50

  Common startup failures:
    "Cannot connect to database" → DB security group doesn't allow task SG
    "AccessDeniedException on GetSecretValue" → task role missing permission
    "Error: listen EADDRINUSE :::3000" → port conflict (shouldn't happen in awsvpc)
    "MODULE_NOT_FOUND" → Docker image build failed to include dependency

Step 4: Check security group and VPC networking
  If tasks start but health checks fail:
    Verify ALB security group allows inbound from internet (port 443)
    Verify task security group allows inbound from ALB SG (port 3000)
    Verify task security group allows outbound to DB SG (port 5432)
    Verify route table for private subnet has NAT Gateway route (for ECR pull)

  Common networking failures:
    Tasks in private subnet cannot pull ECR images
      → Private subnet has no route to internet (NAT Gateway missing)
      → Fix: add NAT Gateway route, or use VPC Endpoint for ECR

Step 5: Check task definition for syntax errors
  aws ecs describe-task-definition --task-definition payment-service
  Verify: image URI format, portMappings, environment, secrets
  Common: secrets valueFrom uses wrong ARN format (SSM: starts with arn:aws:ssm)

Step 6: Verify Fargate capacity (rare but possible)
  If in a specific AZ:
    aws ecs describe-services shows "unable to place task"
    Try deploying to different subnets (different AZs)
    Use FARGATE_SPOT as fallback capacity provider
```

**Q15. "Your payment processor service uses Fargate Spot and you're seeing intermittent task terminations causing payment processing failures. How do you architect around Spot interruptions?"**
A:

```
Problem: Fargate Spot tasks receive a 2-minute warning before termination.
         If a task is mid-processing a payment when interrupted:
           - The SQS message visibility timeout expires
           - The message returns to the queue
           - Another task picks it up and reprocesses
           - If payment processing is not idempotent: DUPLICATE PAYMENT

Solution architecture:

1. Idempotent payment processing (required regardless of Spot)
   Every payment processing operation must be idempotent:

   @SqsMessageHandler('payment-processing-queue')
   async processPayment(message: SQSMessage) {
     const { paymentId, idempotencyKey } = JSON.parse(message.Body);

     // Check if already processed
     const existing = await this.db.payments.findOne({
       where: { idempotencyKey },
     });
     if (existing?.status === 'COMPLETED') {
       // Already processed — ack and skip
       return;
     }

     // Process with external payment gateway
     // JusPay/Razorpay: pass idempotencyKey → they deduplicate on their side
     const result = await this.jusPayClient.createPayment({
       orderId: paymentId,
       idempotencyKey,   // payment gateway deduplicates
     });

     await this.db.payments.upsert({
       idempotencyKey,
       status: result.status,
     });
   }

2. Handle SIGTERM from Spot interruption gracefully
   ECS sends SIGTERM on Spot interruption (2-minute window):

   process.on('SIGTERM', async () => {
     console.log('SIGTERM received — Spot interruption imminent');

     // Stop consuming new messages
     consumer.stop();

     // Wait for current message processing to complete (with timeout)
     await Promise.race([
       currentProcessingPromise,
       new Promise(resolve => setTimeout(resolve, 90_000)) // 90s max (leaves 30s buffer)
     ]);

     // If processing is incomplete: extend visibility timeout so another
     // task picks it up AFTER this task is gone (prevents duplicate processing)
     if (currentMessage && !processingComplete) {
       await sqs.changeMessageVisibility({
         QueueUrl:          QUEUE_URL,
         ReceiptHandle:     currentMessage.ReceiptHandle,
         VisibilityTimeout: 0,  // return to queue immediately for another task
       });
     }

     process.exit(0);
   });

3. SQS visibility timeout configuration
   Visibility timeout: 5 minutes (longer than max processing time of 2 minutes)
   Message retention: 4 days (sufficient for retry and investigation)
   Dead-letter queue after 3 failed processing attempts

   If task is interrupted mid-process:
     Visibility timeout expires after 5 minutes (at most)
     Message returns to queue
     Another task picks it up
     Idempotency key prevents duplicate payment

4. Mixed capacity provider strategy
   Keep a baseline of standard Fargate tasks for in-progress payments:

   "capacityProviderStrategy": [
     { "capacityProvider": "FARGATE",      "weight": 1, "base": 2 },
     { "capacityProvider": "FARGATE_SPOT", "weight": 4, "base": 0 }
   ]

   Interpretation:
     2 tasks always on standard Fargate (interruption-safe)
     Remaining tasks on Spot (4:1 ratio)
     For 10 tasks: 2 Fargate + 8 Spot
     If all 8 Spot tasks are interrupted simultaneously:
       2 Fargate tasks continue processing
       8 SQS messages return to queue within 5 minutes
       New tasks spin up on standard Fargate automatically

5. Monitoring Spot interruptions
   CloudWatch metric: ECS/TaskInterruptionsByFargate
   Alert: if interruption rate > 5% of tasks in 5 minutes → investigate

   ECS sends metadata about Spot interruption to the task metadata endpoint:
   GET http://169.254.170.2/v4/metadata → check for interruption notice

   Preemptive scale-out: if Spot interruptions detected, scale out Fargate tasks
   before the interrupted Spot tasks finish terminating.
```

## The Core Mental Model

```
ECS = desired state controller for containers
  You declare: "run 10 copies of image X with Y CPU and Z memory"
  ECS ensures: actual state continuously reconciles toward desired state
  On task failure: ECS replaces it; on deployment: ECS replaces old with new

Fargate vs EC2 decision:
  Default choice: Fargate
    No instances to manage; pay per task-second; scales to zero
  Switch to EC2 when:
    GPU required (ML inference, video processing)
    Windows containers
    Very high sustained load (Reserved Instances 40-60% cheaper)
    Local NVMe storage required

The two IAM roles (never confuse them):
  Execution role → ECS infrastructure (pulls image, writes logs, injects secrets)
  Task role      → your application code (reads S3, writes SQS, calls APIs)
  Symptom of confusion: task starts but application gets AccessDeniedException

Networking in awsvpc mode (Fargate only option):
  Each task = one ENI = one private IP in your VPC
  Security groups at task level, not instance level
  Private subnet → tasks never directly internet-accessible
  NAT Gateway → tasks can make outbound calls (ECR pull, external APIs)
  VPC Endpoints → avoid NAT for AWS service calls (ECR, S3, Secrets Manager)

Deployment correctness:
  Reduce ALB deregistration delay (300s → 30s) for fast HTTP API deploys
  Handle SIGTERM for graceful shutdown (stop accepting, finish in-flight)
  minimumHealthyPercent=100 for zero-downtime (costs 2× tasks during deploy)
  minimumHealthyPercent=50 for faster/cheaper deploys (some old tasks terminate first)

Fargate Spot safety pattern:
  base=2 on standard Fargate (interruption-safe floor)
  Remaining tasks on Spot (4:1 ratio for cost savings)
  Idempotent processing (required — messages will be reprocessed)
  SIGTERM handler → extend SQS visibility to 0 (return to queue immediately)
  SQS visibility timeout > max processing time (prevents duplicate processing)

ECR in production:
  Lifecycle policy on every repository (or images accumulate forever)
  Scan on push enabled (block critical CVEs in CI/CD)
  OIDC authentication in CI/CD (no long-lived IAM access keys)
  Tag images with git SHA (not 'latest') for reproducible deployments
  Replicate to all regions where ECS runs (avoid cross-region pull latency)
```

**Tip for the interview:** ECS questions at 5 YOE almost always escalate to one of three places: (1) the two IAM roles — being able to immediately state that the execution role is used by ECS infrastructure (for ECR pull and log writing) while the task role is used by the application code, and knowing that the symptom of confusing them is "task starts but application gets AccessDeniedException at runtime" shows production ECS experience rather than documentation reading; (2) Fargate Spot reliability — knowing the 2-minute interruption window, that SIGTERM must be handled to return the SQS message to the queue (not let it time out), that idempotency is non-negotiable for any SQS consumer on Spot, and that a base of standard Fargate tasks provides the safety floor, demonstrates that you have designed fault-tolerant systems rather than just used the happy path; (3) the ECS deployment failure diagnosis sequence — knowing to check service events first (not CloudWatch Logs, which are empty if the container never started), then stopped task exit codes, then application logs, then security group rules, then NAT Gateway routes, and being able to map common error messages ("CannotPullContainerError: access denied" → execution role missing ECR permissions) to their root causes and fixes is the operational depth that separates someone who has debugged production ECS incidents from someone who has only deployed to it successfully.
