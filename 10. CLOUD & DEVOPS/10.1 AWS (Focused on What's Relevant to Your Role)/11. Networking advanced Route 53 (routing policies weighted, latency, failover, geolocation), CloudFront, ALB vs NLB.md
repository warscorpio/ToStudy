# AWS Advanced Networking: Route 53, CloudFront, ALB vs NLB — Interview Q&A (5 YOE Level)

---

## Section 1: Route 53 Fundamentals

**Q1. What is Route 53 and what does it do beyond basic DNS?**
A: Route 53 is AWS's authoritative DNS service — it answers DNS queries for domain names you register or delegate to it. But calling it "just DNS" undersells it: Route 53's routing policies, health checks, and traffic flow features make it an active traffic management layer, not merely a passive name resolver.

At its core, Route 53 manages **hosted zones** (the DNS records for a domain) and answers queries for those records. But where a traditional DNS server returns a fixed IP for a name, Route 53 can:

- **Route based on health**: return only the IPs of healthy endpoints, automatically excluding unhealthy ones from responses.
- **Route based on latency**: return the endpoint that will give the querying client the lowest network latency.
- **Route based on geography**: return different endpoints depending on where in the world the DNS query originates.
- **Route based on weights**: split traffic across endpoints in configured proportions.
- **Route across AWS resources natively**: Alias records resolve to ALB DNS names, CloudFront distributions, S3 static websites, and other AWS resources without the TTL and cost constraints of CNAME records.

**Record types Route 53 supports:**
```
A:      IPv4 address (or Alias to AWS resource)
AAAA:   IPv6 address
CNAME:  Canonical name (cannot be used at zone apex — use Alias instead)
Alias:  AWS extension — maps to an AWS resource DNS name; resolves like an A record;
        no TTL charge; updates when the target's IPs change; can be at zone apex
MX:     Mail exchanger
TXT:    Text (SPF, DKIM, domain verification)
NS:     Name server (delegates subdomain to different hosted zone)
SOA:    Start of Authority (auto-created; defines zone metadata)
SRV:    Service locator (for gRPC service discovery, XMPP, etc.)
CAA:    Certificate Authority Authorization (which CAs can issue certs for this domain)
```

**Alias records vs CNAME — why Alias matters:**
```
CNAME api.example.com → my-alb-123.ap-south-1.elb.amazonaws.com
  Problem 1: Cannot be at zone apex (example.com → CNAME is illegal in DNS spec)
  Problem 2: Each CNAME resolution is a separate DNS query (latency + cost)
  Problem 3: TTL of the CNAME record and the target's A records are independent

Alias api.example.com → my-alb-123.ap-south-1.elb.amazonaws.com
  No extra DNS query: Route 53 resolves the ALB's current IPs inline
  Can be at zone apex: example.com → ALB is valid
  Free: Alias queries to AWS resources are not billed per query
  Auto-updates: when the ALB's IPs change (ALB scales in/out), the Alias resolves correctly
```

## Section 2: Route 53 Routing Policies

**Q2. What are the Route 53 routing policies and what does each do?**
A: A routing policy determines how Route 53 responds when multiple records exist for the same name. Each policy solves a different traffic distribution problem.

**Simple routing:**
Returns one value (or all values in a multi-value response). No health checking at the routing level; no traffic splitting. The default — one record, one destination.
```
api.example.com → A → 10.0.0.1
(Single destination; no conditions applied)
```

**Weighted routing:**
Splits traffic across multiple records in configured proportions. Each record carries a weight (0–255); traffic proportion = weight / sum of all weights.
```
api.example.com → A → 10.0.0.1    weight: 80   → 80% of traffic
api.example.com → A → 10.0.0.2    weight: 20   → 20% of traffic

Weight 0: record exists but receives zero traffic
         (useful for taking an endpoint out of rotation without deleting the record)
```

Use cases: canary deployments (5% to new version, 95% to old), A/B testing, gradual traffic migration between regions.

**Latency-based routing:**
Returns the record whose AWS region has the lowest latency from the querying DNS resolver's perspective. Route 53 measures latency between AWS regions and the locations of DNS resolvers globally and routes accordingly.
```
api.example.com → A → 10.0.0.1   region: ap-south-1   (Mumbai)
api.example.com → A → 54.0.0.2   region: us-east-1    (Virginia)

A user in India:       Mumbai record returned (lower latency to ap-south-1)
A user in New York:    Virginia record returned (lower latency to us-east-1)
```

Important nuance: latency routing uses the DNS resolver's location, not the end user's location. A user in Mumbai using Google's DNS resolver at 8.8.8.8 (a US-based resolver) may be routed to Virginia — the resolver's location, not the user's, determines the routing decision. This is a common source of confusion in latency routing behavior.

**Failover routing:**
Designates a primary and a secondary record. Route 53 returns the primary record when it is healthy; automatically returns the secondary when the primary's health check fails.
```
api.example.com → A → 10.0.0.1   type: PRIMARY    health check: hc-001
api.example.com → A → 10.0.0.2   type: SECONDARY  health check: optional

Normal:          primary returned (health check passing)
Primary fails:   secondary returned (DNS failover — within 60s typically)
Primary recovers: primary returned again (automatic failback)
```

Failover is active-passive: the secondary receives no traffic until the primary fails. Use for disaster recovery: primary is the production environment; secondary is a static error page, a read-only mode, or a warm standby in another region.

**Geolocation routing:**
Routes based on the geographic location of the DNS query origin (continent, country, or US state). Unlike latency routing (which optimizes for network performance), geolocation routing is policy-driven — it enforces where traffic goes, regardless of latency.
```
api.example.com → A → 10.0.0.1   location: India
api.example.com → A → 54.0.0.2   location: United States
api.example.com → A → 46.0.0.3   location: Default  ← catches all unmatched locations

Indian users:     always → 10.0.0.1 (even if US endpoint has lower latency)
US users:         always → 54.0.0.2
Brazilian users:  → Default (46.0.0.3) — no Brazil-specific record
```

Use cases: data residency compliance (EU users must be served by EU endpoints), localized content (different app versions per country), regulatory requirements (payment processing must happen within a jurisdiction).

**Geoproximity routing (Traffic Flow only):**
Routes based on geographic distance from a defined location (an AWS region or a custom latitude/longitude). A bias value (+/-1 to +/-99) expands or shrinks the effective geographic area of an endpoint — increasing bias on a resource routes more traffic toward it even from slightly farther away. Requires Route 53 Traffic Flow (visual routing policy editor) — cannot be configured with plain resource record sets.

**Multivalue answer routing:**
Returns up to 8 healthy records in response to each DNS query (chosen randomly from all healthy records). Similar to simple routing with multiple values, but integrates health checking — unhealthy endpoints are excluded from the response set.
```
api.example.com → A → 10.0.0.1   health check: hc-001
api.example.com → A → 10.0.0.2   health check: hc-002
api.example.com → A → 10.0.0.3   health check: hc-003

All healthy: query returns random 8 of the healthy set
hc-002 failing: query returns only 10.0.0.1 and 10.0.0.3
```

Not a load balancer replacement: the client receives multiple IPs and picks one (usually the first in the list). This is DNS-level load distribution, not request-level. Use when you want clients to have multiple IPs to try if one fails, without requiring a load balancer.

**Q3. How do Route 53 health checks work and what are the failure scenarios?**
A: Route 53 health checks monitor endpoints from Route 53's global network of health checkers (locations worldwide). A health check is associated with a routing policy record — when the health check fails, Route 53 removes that record from DNS responses.

**Health check types:**

**HTTP/HTTPS endpoint health check:**
```json
{
  "Type":             "HTTPS",
  "ResourcePath":     "/health",
  "FullyQualifiedDomainName": "api.example.com",
  "Port":             443,
  "RequestInterval":  30,     // seconds between checks (10 or 30)
  "FailureThreshold": 3,      // consecutive failures before unhealthy
  "MeasureLatency":   true    // record latency in CloudWatch
}
```
Route 53 sends HTTP(S) requests from multiple geographic locations. A 2xx or 3xx response = healthy. 4xx or 5xx = failure. Timeout (4 seconds) = failure. The endpoint is considered unhealthy when the `FailureThreshold` number of health checkers agree it is failing.

**TCP endpoint health check:**
Attempts a TCP connection to the specified port. If the connection succeeds within 10 seconds = healthy. No HTTP request is made — useful for non-HTTP services (databases, gRPC over TCP).

**Calculated health check:**
Combines the results of multiple child health checks with AND/OR logic:
```
payment-api healthy = (
  health-check-ap-south-1 AND
  health-check-us-east-1 AND
  (health-check-db-primary OR health-check-db-replica)
)
```
Useful for complex failover decisions where the service is only healthy if all its dependencies are healthy.

**CloudWatch Alarm health check:**
Triggers based on a CloudWatch alarm state. Enables health checks based on metrics the standard HTTP check cannot observe — error rates, queue depth, CPU saturation:
```
health-check: UNHEALTHY if
  CloudWatch alarm "PaymentErrorRate > 5%" is IN_ALARM
```

**Health check timing and DNS propagation:**
```
RequestInterval: 30s  → health checkers poll every 30 seconds
FailureThreshold: 3   → 3 consecutive failures required

Worst-case time from endpoint failure to DNS propagation:
  30s (poll interval) × 3 (failures) = 90s before Route 53 marks unhealthy
  + TTL of the DNS record (if TTL=60s, clients may cache the old record for 60s more)
  Total worst-case failover time: 90 + 60 = 150 seconds (~2.5 minutes)

Fast failover configuration:
  RequestInterval: 10s  (fast health check — 3× more frequent, 3× more expensive)
  FailureThreshold: 1   (one failure = unhealthy immediately)
  TTL: 60s
  Fastest possible: 10s + 60s = 70 seconds
```

**Q4. How do you combine routing policies to build a multi-region active-active architecture?**
A: Complex routing requirements — serve from the nearest region, fall back to another region if the nearest fails, split a percentage of traffic to a canary — require composing multiple routing policies. Route 53 supports this through policy nesting using health checks and record set hierarchies.

**Multi-region active-active with latency + failover:**
```
Global record (latency):
  api.example.com → ALIAS → api-india.example.com    region: ap-south-1
  api.example.com → ALIAS → api-us.example.com        region: us-east-1

Regional records (failover):
  api-india.example.com → A → 10.0.0.1   type: PRIMARY    health: hc-india-primary
  api-india.example.com → A → 54.0.0.2   type: SECONDARY  health: hc-india-secondary
                                                            (cross-region secondary!)
  api-us.example.com → A → 54.1.0.1      type: PRIMARY    health: hc-us-primary
  api-us.example.com → A → 10.0.0.2      type: SECONDARY  health: hc-us-secondary

Traffic flow:
  Indian user, all healthy:
    Latency → api-india.example.com → PRIMARY (10.0.0.1)

  Indian user, India primary fails:
    Latency → api-india.example.com → SECONDARY (54.0.0.2, cross-region)

  Indian user, all India endpoints fail (health check fails for both):
    Latency → api-india.example.com fails health check
    Route 53 falls through to next latency record → api-us.example.com
    → US PRIMARY (54.1.0.1)
```

**Weighted + latency for canary deployments:**
```
Canary record (5% of traffic goes to new version in same region):
  api.example.com → latency → api-india.example.com     region: ap-south-1   weight: 95
  api.example.com → latency → api-india-v2.example.com  region: ap-south-1   weight: 5

  api-india.example.com    → ALB (old version)
  api-india-v2.example.com → ALB (new version)

5% of Indian users hit the new version; 95% hit old; no geographic split
```

## Section 3: CloudFront

**Q5. What is CloudFront and what problems does it solve beyond "making things faster"?**
A: CloudFront is AWS's Content Delivery Network (CDN) — a globally distributed network of edge locations that cache content closer to users. But its value in production architectures extends well beyond caching:

**Cache hit performance:**
An edge location in Mumbai serving a cached response to a user in Mumbai eliminates the round-trip to an origin server in us-east-1 (200ms+ RTT). The response comes from ~10ms away instead of ~200ms away. For cacheable content (static assets, API responses with appropriate Cache-Control headers), this is a 20× latency improvement.

**Origin shielding (reducing origin load):**
Without CloudFront, every cache miss at an edge location becomes a request to the origin. With 200+ edge locations globally, a cache miss at each of them (cold cache after a deploy) produces 200+ simultaneous origin requests for the same object. Origin Shield designates one intermediate cache as the single origin-facing tier — other edge locations go to the Shield location before hitting the origin. One origin request fills the Shield cache; all other edge locations are served from Shield:
```
Without Shield:
  200 edge locations × 1 miss each = 200 origin requests for the same object

With Origin Shield (Shield in ap-south-1):
  200 edge locations × 1 miss each → 200 Shield requests
  Shield: 1 origin miss → 1 origin request, object cached at Shield
  → 1 origin request total
```

**DDoS protection (AWS Shield Standard, free):**
All CloudFront distributions automatically get AWS Shield Standard, which absorbs many common DDoS attacks (SYN floods, UDP reflection) at the edge — before traffic reaches your origin. This protection is infrastructure-level and requires no configuration.

**Edge-side authentication and WAF:**
AWS WAF (Web Application Firewall) integrates with CloudFront to inspect and filter HTTP requests at the edge — before they reach the origin. Rules block SQL injection, XSS, specific IP ranges, geographic locations, and malicious bots. For a payment API exposed via CloudFront: a WAF rule can block requests from countries you don't operate in, rate-limit by IP, and reject requests with known attack signatures — all at the CDN edge, never touching your origin servers.

**HTTPS termination and certificate management:**
CloudFront terminates HTTPS at the edge using ACM (AWS Certificate Manager) certificates — no cost for the certificate, automatic renewal, supports custom domains. The connection from CloudFront to the origin can be HTTP or HTTPS depending on the origin protocol policy. This offloads TLS computation from origin servers.

**Q6. How does CloudFront caching work, and what determines whether a response is cached?**
A: CloudFront caches responses at edge locations based on the cache key — the combination of attributes that uniquely identify a cacheable response. Understanding the cache key is essential for both cache effectiveness and correctness.

**Default cache key:**
By default, CloudFront's cache key is the URL path only:
```
https://cdn.example.com/payments/pay_001/receipt.pdf
Cache key: /payments/pay_001/receipt.pdf
```

**Cache key components (configurable):**
```
URL path:          always included (cannot be excluded)
Query strings:     by default NOT included; configure to include specific params
Headers:           by default NOT included; configure to include (e.g., Accept-Language)
Cookies:           by default NOT included; configure to include session cookies
HTTP method:       GET and HEAD are cached; POST/PUT/DELETE pass through to origin
```

**The cache key problem:**
If your API returns different content for the same URL based on a header (`Authorization`, `Accept-Language`, `X-User-Id`), but that header is not in the cache key, CloudFront will serve the first user's response to all subsequent users — a catastrophic privacy violation:
```
User A: GET /api/profile  Authorization: Bearer token-A → { name: "Alice" }
CloudFront caches { name: "Alice" } with key: /api/profile

User B: GET /api/profile  Authorization: Bearer token-B
CloudFront: cache hit! → returns { name: "Alice" } to User B ← DATA LEAK
```

**Fix — Cache Policy configuration:**
```json
{
  "CachePolicyConfig": {
    "Name": "PaymentAPIPolicy",
    "DefaultTTL": 0,
    "MaxTTL": 0,
    "MinTTL": 0,
    "ParametersInCacheKeyAndForwardedToOrigin": {
      "EnableAcceptEncodingGzip": true,
      "HeadersConfig": {
        "HeaderBehavior": "none"   // Don't include any headers in cache key
                                    // (and don't forward them)
      },
      "QueryStringsConfig": {
        "QueryStringBehavior": "none"
      },
      "CookiesConfig": {
        "CookieBehavior": "none"
      }
    }
  }
}
```

For the payment API — which is user-specific and must not be cached:
```json
{
  "DefaultTTL": 0,
  "MaxTTL":     0,   // zero TTL = pass-through; no caching
  "MinTTL":     0
}
```

For static assets (JS, CSS, images) with content-addressed filenames:
```json
{
  "DefaultTTL": 86400,    // 24 hours
  "MaxTTL":     31536000, // 1 year
  "MinTTL":     0
}
```
Content-addressed filenames (hash in the filename: `main.abc123.js`) mean the URL changes when the content changes — the old URL can be cached indefinitely without staleness.

**Cache invalidation:**
```bash
# Invalidate specific paths (first 1000 invalidations/month free; $0.005 per path after)
aws cloudfront create-invalidation \
  --distribution-id E1ABCDEF \
  --paths "/api/config/*" "/static/app.js"

# Wildcard invalidation (counts as 1 invalidation)
aws cloudfront create-invalidation \
  --distribution-id E1ABCDEF \
  --paths "/*"
```

Invalidation propagates to all edge locations in ~30 seconds but is eventually consistent — edge locations pick up the invalidation at different times. For versioned assets, invalidation is unnecessary (URL changes = new cache entry). For unversioned assets (e.g., `/api/config`), invalidation is the mechanism to push updates immediately.

**Q7. What is a CloudFront Origin Access Control (OAC) and how does it secure S3 origins?**
A: Origin Access Control (OAC) restricts S3 bucket access so that only CloudFront can read objects — the S3 bucket is not publicly accessible, and clients cannot bypass CloudFront to access S3 directly.

Without OAC: S3 bucket is public or has a resource policy allowing anyone. Clients can construct S3 URLs directly (`https://bucket.s3.amazonaws.com/key`) and bypass CloudFront — bypassing WAF, rate limiting, cache, and geo-blocking.

With OAC:
```
S3 bucket policy:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipal",
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::fintech-static-assets/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123:distribution/E1ABCDEF"
        }
      }
    }
  ]
}
```

The `AWS:SourceArn` condition ensures only this specific CloudFront distribution can read from the bucket — not any CloudFront distribution from any AWS account.

Direct S3 access is blocked (Access Denied). CloudFront access works (IAM condition satisfied).

**CloudFront Functions and Lambda@Edge:**
CloudFront can run lightweight code at the edge for request/response manipulation:
```javascript
// CloudFront Function (lightweight, sub-millisecond, limited APIs)
// Use for: URL rewrites, redirects, header manipulation, simple auth
function handler(event) {
  const request = event.request;

  // Redirect /payments → /api/payments
  if (request.uri.startsWith('/payments')) {
    return {
      statusCode: 301,
      headers: { location: { value: '/api' + request.uri } },
    };
  }

  // Add security headers to all responses
  request.headers['x-forwarded-for'] = { value: event.viewer.ip };
  return request;
}

// Lambda@Edge (full Node.js/Python runtime, runs at regional edge locations)
// Use for: complex auth (JWT validation), A/B testing with cookies,
//          dynamic content from DynamoDB at the edge, image resizing
exports.handler = async (event) => {
  const request = event.Records[0].cf.request;
  const headers = request.headers;

  // Validate JWT at edge (before request reaches origin)
  const authHeader = headers.authorization?.[0]?.value;
  if (!authHeader || !validateJwt(authHeader)) {
    return {
      status:     '401',
      statusDescription: 'Unauthorized',
      body: JSON.stringify({ error: 'Unauthorized' }),
    };
  }

  return request; // forward to origin if valid
};
```

## Section 4: ALB vs NLB

**Q8. What is an Application Load Balancer (ALB) and what are its capabilities?**
A: An ALB is an L7 (application layer) load balancer — it understands HTTP and HTTPS, inspects request content (headers, paths, query strings, host names), and makes routing decisions based on that content. It operates at the HTTP request level, not the TCP connection level.

**ALB request inspection capabilities:**

**Host-based routing:**
```
Host: api.example.com      → Target group: api-service-tg
Host: admin.example.com    → Target group: admin-service-tg
Host: ws.example.com       → Target group: websocket-service-tg
```
Multiple services behind one ALB, differentiated by the Host header. Eliminates the need for separate load balancers per service — significant cost savings.

**Path-based routing:**
```
Path: /api/payments/*   → Target group: payment-service-tg
Path: /api/users/*      → Target group: user-service-tg
Path: /api/reports/*    → Target group: reporting-service-tg
Path: /*                → Target group: default-tg (catch-all)
```
One ALB per domain, routing to different microservices by URL path.

**Header and query string routing:**
```
Header X-Feature-Flag: v2   → Target group: v2-canary-tg
Query string: ?version=beta → Target group: beta-tg
```

**HTTP/2 and WebSocket support:**
ALB natively supports HTTP/2 between clients and the ALB. Between ALB and targets, HTTP/1.1 or HTTP/2 depending on target configuration. WebSocket connections: ALB upgrades the HTTP connection and maintains the WebSocket session on the same target (sticky based on connection, not cookie).

**Target types:**
- **Instance**: EC2 instance ID + port. Traffic routed to instance's primary ENI.
- **IP**: any IP address in your VPC or connected networks (on-premises via VPN/Direct Connect). Used for ECS `awsvpc` (task IPs), Lambda (via Lambda integration), or non-EC2 targets.
- **Lambda**: ALB invokes a Lambda function directly for each HTTP request. Serverless HTTP backend without any EC2 or container infrastructure.

**ALB health checks:**
ALB performs health checks against each registered target on a configurable path and interval. Unhealthy targets are removed from rotation immediately. Unlike Route 53 health checks (which affect DNS), ALB health checks affect request routing — an unhealthy target receives no new connections regardless of DNS.

**Sticky sessions:**
```
Duration-based: ALB sets a cookie (AWSALB) with a configurable expiry.
                The same client always routes to the same target for the cookie duration.
Application-based: ALB uses a cookie your application sets (name configurable).
                   Your application controls session length and content.
```
Sticky sessions are required for stateful applications that store session state in memory (in-process session stores). The production alternative is externalized session state (Redis, DynamoDB) which eliminates the need for sticky sessions and enables true stateless scaling.

**Q9. What is a Network Load Balancer (NLB) and when is it the right choice over ALB?**
A: An NLB is an L4 (transport layer) load balancer — it operates at the TCP/UDP/TLS level, forwarding packets based on IP and port without inspecting application-layer content. It makes routing decisions based on the connection 4-tuple (source IP, source port, destination IP, destination port), not HTTP headers or paths.

**NLB characteristics:**

**Ultra-low latency:**
NLB adds single-digit microseconds of latency — significantly less than ALB's milliseconds. NLB performs minimal processing per packet; ALB buffers and parses full HTTP requests. For latency-critical applications where every microsecond matters, NLB is the right choice.

**Extreme throughput:**
NLB handles millions of requests per second and can process packets at line rate. It scales to handle large volumes of small, fast connections without the overhead of HTTP parsing.

**Static IP addresses:**
Each NLB gets a static IP address per AZ (or Elastic IP if configured). This is NLB's most operationally significant difference from ALB. ALB's IP addresses change as it scales — you can only reference an ALB by DNS name, never by IP. NLB's static IPs enable:
- IP allowlisting in third-party firewall rules (you can tell Razorpay: "allow these 3 IPs").
- Direct IP connections from on-premises networks.
- Clients that cannot do DNS-based load balancing (some legacy systems, IoT devices).

**Preserves source IP:**
NLB passes the client's source IP to the target unchanged (unless using NLB with TLS termination, where Proxy Protocol must be enabled for source IP preservation). ALB replaces the client IP with the ALB's IP and adds `X-Forwarded-For` to HTTP headers. For applications that need the actual client IP for rate limiting, geolocation, or logging:
- NLB: source IP is the real client IP at the socket level.
- ALB: source IP is the ALB's IP; real client IP is in `X-Forwarded-For` header.

**TCP, UDP, TLS, and TCP_UDP protocols:**
NLB supports TCP, UDP, TLS, and combined TCP_UDP listeners. Use cases beyond HTTP:
- gRPC over HTTP/2 with NLB (NLB's TCP passthrough preserves HTTP/2 multiplexing end-to-end).
- MQTT (IoT messaging, port 1883/8883).
- DNS (UDP port 53) — you can put NLB in front of DNS servers.
- Financial market data feeds (UDP multicast-style delivery).
- Any non-HTTP TCP or UDP protocol.

**No HTTP-aware features:**
NLB has no path-based routing, no host-based routing, no header inspection, no WAF integration, no HTTP/2 to HTTP/1.1 translation. It is a packet forwarder, not an HTTP router. If you need any HTTP-layer feature, use ALB.

**Q10. How do ALB and NLB compare across the key operational dimensions?**
A:

```
Dimension              ALB                          NLB
─────────────────────────────────────────────────────────────────────────────
OSI Layer              L7 (HTTP/HTTPS)              L4 (TCP/UDP/TLS)
Latency added          ~1–10ms                      microseconds
Throughput             Very high                    Extreme (millions req/s)
IP addresses           Dynamic (DNS name only)      Static per AZ (or EIP)
Source IP to target    X-Forwarded-For header       Client IP (preserved)
Protocols              HTTP, HTTPS, WebSocket       TCP, UDP, TLS, TCP_UDP
                        HTTP/2, gRPC (limited)
Routing granularity    Host, path, header, query    IP + port only
                        string, HTTP method
WebSocket              Native (session-sticky)       TCP passthrough
gRPC                   Partial (HTTP/2 termination)  Better (TCP passthrough)
WAF integration        Yes (AWS WAF)                No
SSL/TLS termination    Yes (ACM certs, no cost)     Yes (or TLS passthrough)
Health checks          HTTP/HTTPS paths             TCP connection or HTTP path
Sticky sessions        Cookie-based                 Source IP-based (5-tuple)
Target types           Instance, IP, Lambda         Instance, IP
Connection draining    Yes (deregistration delay)   Yes
Cross-zone LB          Enabled by default           Disabled by default (free
                                                     when enabled since 2022)
Pricing                Per LCU (request-based)      Per NLCU (connection-based)
Cost at low volume     Higher (LCU minimum)         Lower
Cost at high volume    Lower (LCUs cover many req)  Depends on connection count

Best for:
  HTTP microservices routing       ✅                ❌
  Path/host-based routing          ✅                ❌
  WebSocket at scale               ✅                ✅
  gRPC (end-to-end HTTP/2)         Limited           ✅ (TCP passthrough)
  Static IP for IP allowlisting    ❌                ✅
  Preserving client IP at L4       ❌                ✅
  Ultra-low latency trading        ❌                ✅
  Non-HTTP protocols (MQTT, DNS)   ❌                ✅
  WAF inspection at LB layer       ✅                ❌
  Lambda as target                 ✅                ❌
```

**The ALB + NLB combination — static IP with HTTP routing:**
A common production pattern where you need both static IPs and HTTP routing:
```
Client → NLB (static IP) → ALB → Target Groups

NLB: provides static IP for allowlisting; TCP passthrough to ALB
ALB: provides path/host routing, WAF, SSL termination, target group routing
```
This is also the pattern used by AWS PrivateLink — NLB as the endpoint for exposing services privately to other VPCs or accounts.

## Section 5: Integration Patterns

**Q11. How do CloudFront and ALB work together for a typical web application architecture?**
A: CloudFront and ALB serve different layers of the traffic path and are almost always used together in production web applications:

```
Architecture:

Users → CloudFront Distribution
         ├── Static assets (S3 origin with OAC)
         │     Cache: max-age=31536000 (content-addressed filenames)
         │     Edge serves directly; origin never hit after first request
         │
         └── API requests (/api/*)
               Origin: ALB (HTTPS, custom origin)
               Cache: no-cache (Authorization header present → not cached)
               WAF: AWS WAF rules for SQLi, XSS, rate limiting
               │
               ALB
               ├── /api/payments/* → payment-service-tg (ECS Fargate tasks)
               ├── /api/users/*    → user-service-tg    (ECS Fargate tasks)
               └── /api/reports/*  → reporting-service-tg (ECS Fargate tasks)
```

**Why CloudFront in front of ALB (not just ALB directly):**
- **Global edge**: CloudFront has 400+ edge locations; ALB exists in one region. CloudFront terminates TLS from the user at the nearest edge, reducing RTT.
- **DDoS absorption**: CloudFront absorbs volumetric attacks at the edge before reaching ALB. ALB has limited DDoS protection.
- **WAF at edge**: AWS WAF on CloudFront blocks malicious requests before they consume ALB capacity or reach origin servers.
- **Static asset offload**: CloudFront serves JS/CSS/images from edge cache; ALB never sees these requests.
- **ALB cost reduction**: fewer requests reach ALB (CloudFront cache hits never hit the ALB), reducing ALB LCU consumption.

**Restricting ALB access to CloudFront only:**
Without restriction, the ALB is directly accessible via its DNS name — bypassing CloudFront and all its protections. Fix with a custom header:

```
CloudFront: adds custom header to all origin requests
  X-CloudFront-Secret: <random-string-in-secrets-manager>

ALB listener rule: condition
  IF header X-CloudFront-Secret = <secret>: forward to target group
  ELSE: return 403 Fixed Response

Result: direct ALB access returns 403; CloudFront access forwards correctly
```

Alternatively, restrict ALB security group to CloudFront's IP ranges (published as a managed prefix list by AWS: `pl-<id>` for `com.amazonaws.global.cloudfront.origin-facing`).

**Q12. How do you use Route 53, CloudFront, and ALB together for a multi-region active-active deployment?**
A:

```
Full stack multi-region architecture:

DNS Layer (Route 53):
  api.example.com → Latency routing
    → cf-india.example.com  (ALIAS → CloudFront India distribution)  region: ap-south-1
    → cf-us.example.com     (ALIAS → CloudFront US distribution)     region: us-east-1

  Health checks on each CloudFront distribution's /health endpoint
  Failover within latency: if India distribution unhealthy → US distribution

CDN Layer (CloudFront per region):
  India CloudFront distribution:
    Origin: India ALB (api-india.internal.example.com)
    Origin Shield: ap-south-1 (reduces origin request count)
    WAF: India-specific WAF rules (block non-Indian IPs if required by regulation)
    TLS: ACM certificate for api.example.com (CloudFront wildcard cert)
    Cache: no-cache for API; long-cache for static assets

  US CloudFront distribution:
    Origin: US ALB (api-us.internal.example.com)
    Same configuration as India distribution

LB Layer (ALB per region):
  India ALB (ap-south-1):
    /api/payments/* → payment-service ECS cluster (ap-south-1)
    /api/users/*    → user-service ECS cluster (ap-south-1)
    Health check: /health → removes unhealthy tasks from rotation

  US ALB (us-east-1):
    Same routing rules → same services in us-east-1

Data Layer:
  RDS Aurora Global Database:
    Primary writer: ap-south-1
    Read replica: us-east-1
    Failover: us-east-1 promoted to writer in ~1 minute (automated)

  Requests to the API always write to the primary region's Aurora writer.
  Read-heavy paths can use the regional read replica.

Failover scenarios:
  Scenario 1: India ECS tasks fail health checks
    ALB removes unhealthy tasks → healthy tasks absorb traffic
    No Route 53 change needed (ALB handles task-level failover)

  Scenario 2: India ALB becomes unhealthy
    CloudFront origin health check fails
    CloudFront can be configured to failover to secondary origin (US ALB)
    Or: Route 53 health check on India CloudFront fails → US CloudFront record returned

  Scenario 3: India region entirely unavailable
    Route 53 health check on India endpoint fails
    Latency routing returns US CloudFront record to Indian users
    (Higher latency: ~200ms additional RTT, but service is available)
    Aurora Global Database failover: US replica promoted to writer
```

**Q14. "Your ALB is receiving traffic from CloudFront but you're seeing client IP addresses as CloudFront's IPs instead of the actual users' IPs in your application logs. Fix this and explain the header chain."**
A:

```
Problem: Application logs show CloudFront edge IPs (e.g., 52.84.x.x)
         instead of real user IPs (e.g., 103.21.x.x from India)

The header chain:
  Real client (103.21.x.x) → CloudFront edge (52.84.x.x) → ALB → ECS task

  CloudFront → ALB connection:
    Source IP: CloudFront edge IP (52.84.x.x) — this is what the ALB sees
    X-Forwarded-For: 103.21.x.x (real client IP — CloudFront adds this)

  ALB → ECS task connection:
    X-Forwarded-For: 103.21.x.x, 52.84.x.x (ALB appends its own IP)
    X-Forwarded-Proto: https
    X-Forwarded-Port: 443

  What arrives at the application:
    X-Forwarded-For: 103.21.x.x, 52.84.x.x (both CloudFront edge AND ALB IP)
    request.ip = ALB IP (the direct TCP connection source)

Fix 1: Read X-Forwarded-For correctly in the application
  The real client IP is the FIRST value in X-Forwarded-For (leftmost):

  // NestJS / Express
  app.set('trust proxy', 1); // trust one proxy (the ALB)
  // req.ip now returns the first X-Forwarded-For value = real client IP

  // But with CloudFront + ALB: two proxies are in chain
  // trust proxy = 2 would trust both CloudFront and ALB:
  app.set('trust proxy', 2);
  // req.ip = 103.21.x.x (real client IP)

  // Manual extraction (safer — explicit about which value you trust):
  function getRealClientIp(req: Request): string {
    const xForwardedFor = req.headers['x-forwarded-for'];
    if (!xForwardedFor) return req.ip;
    // First IP in the list is the original client
    return (xForwardedFor as string).split(',')[0].trim();
  }

Fix 2: Use CloudFront's CloudFront-Viewer-Address header (most reliable)
  CloudFront adds:
    CloudFront-Viewer-Address: 103.21.x.x:54321  (viewer IP:port)
  This cannot be spoofed by the client (CloudFront overwrites it)
  X-Forwarded-For CAN be spoofed (client sends X-Forwarded-For: 1.1.1.1;
  CloudFront appends the real IP, giving: 1.1.1.1, 103.21.x.x)

  // Safest approach:
  function getRealClientIp(req: Request): string {
    const viewerAddress = req.headers['cloudfront-viewer-address'] as string;
    if (viewerAddress) {
      return viewerAddress.split(':')[0]; // remove port
    }
    // Fallback for direct-to-ALB requests (not via CloudFront)
    return (req.headers['x-forwarded-for'] as string)?.split(',')[0]?.trim()
           ?? req.ip;
  }

Fix 3: CloudFront forwarding configuration
  Ensure CloudFront forwards these headers to the origin:
  In CloudFront cache policy / origin request policy:
    Forward headers: X-Forwarded-For, CloudFront-Viewer-Address, CloudFront-Viewer-Country
  These must be in the allowed headers list, otherwise CloudFront strips them

Fix 4: Application logging
  Update log format to include the resolved real IP:
  {
    "timestamp": "...",
    "method": "POST",
    "path": "/api/payments",
    "real_client_ip": "103.21.x.x",          // from CloudFront-Viewer-Address
    "x_forwarded_for": "103.21.x.x, 52.84.x.x",  // full chain
    "alb_source_ip": "10.0.1.45"              // ALB IP (from socket)
  }

Rate limiting fix:
  If rate limiting by req.ip: you're rate-limiting by ALB IP (affects ALL users)
  Rate limit by getRealClientIp(req) instead
```

**Q15. "You need to expose an internal microservice (running on ECS) to a partner company's AWS account without making it publicly accessible. Design this."**
A:

```
Requirement: partner account accesses your service; no public internet exposure;
             no peering (which would expose your entire VPC to them)

Solution: AWS PrivateLink (VPC Endpoint Service)

Architecture:
  Your AWS Account (provider):
    ECS service → NLB (Network Load Balancer) ← required; PrivateLink requires NLB
    NLB → VPC Endpoint Service
    VPC Endpoint Service: arn:aws:vpce-svc:ap-south-1:123:vpc-svc-xxx

  Partner's AWS Account (consumer):
    VPC Endpoint (Interface type) → connects to your Endpoint Service
    Endpoint gets a private IP in the partner's VPC
    Partner's services call your service via this private IP
    Traffic: partner VPC → PrivateLink → your NLB → your ECS tasks
    Traffic never leaves the AWS network (no internet)

Why NLB (not ALB) for PrivateLink:
  PrivateLink only supports NLB as the endpoint backing load balancer
  Static IP per AZ: PrivateLink connections are to specific NLB IPs
  NLB IP preservation: partner sees their own source IPs preserved (for logging)

Setup:
  Step 1: Your account — create NLB in front of ECS service
    aws elbv2 create-load-balancer \
      --name partner-api-nlb \
      --type network \
      --scheme internal \  ← internal NLB (not internet-facing)
      --subnets subnet-a subnet-b subnet-c

  Step 2: Create VPC Endpoint Service from NLB
    aws ec2 create-vpc-endpoint-service-configuration \
      --network-load-balancer-arns arn:aws:elasticloadbalancing:...:loadbalancer/net/... \
      --acceptance-required          ← you manually approve connection requests
      --no-private-dns-name

  Step 3: Share service name with partner
    Service name: com.amazonaws.vpce.ap-south-1.vpce-svc-xxx

  Step 4: Partner creates VPC Endpoint
    aws ec2 create-vpc-endpoint \
      --vpc-endpoint-type Interface \
      --service-name com.amazonaws.vpce.ap-south-1.vpce-svc-xxx \
      --vpc-id vpc-partner \
      --subnet-ids subnet-p1 subnet-p2 \
      --security-group-ids sg-partner-outbound

  Step 5: You approve the connection request
    aws ec2 accept-vpc-endpoint-connections \
      --service-id vpce-svc-xxx \
      --vpc-endpoint-ids vpce-yyy

  Step 6: Partner calls your service
    Endpoint DNS: vpce-yyy-xxx.vpce-svc-xxx.ap-south-1.vpce.amazonaws.com
    → resolves to private IP in partner's VPC
    → Partner's service calls https://vpce-yyy-xxx.vpce-svc-xxx.../api/v1/verify

Security:
  VPC Endpoint Service policy: control which principals can use the endpoint
  {
    "Statement": [{
      "Principal": {
        "AWS": "arn:aws:iam::PARTNER_ACCOUNT_ID:root"
      },
      "Action": "ec2:DescribeVpcEndpoints",
      "Effect": "Allow"
    }]
  }
  NLB security group: allow inbound from PrivateLink IP range only
  Your ECS task security group: allow inbound from NLB only

Monitoring:
  NLB access logs: connection count per partner endpoint
  VPC Flow Logs: monitor traffic from PrivateLink IPs
  CloudWatch: NLB metrics (ActiveFlowCount, NewFlowCount) per partner endpoint
```

## Quick Reference

| Route 53 Policy | Routes based on | Use for |
|---|---|---|
| Simple | Nothing (single record) | Basic DNS |
| Weighted | Configured weight (%) | Canary, A/B, gradual migration |
| Latency | Network latency to AWS region | Multi-region performance |
| Failover | Health check status | Active-passive DR |
| Geolocation | Query origin country/continent | Data residency, localization |
| Geoproximity | Geographic distance + bias | Fine-grained geographic split |
| Multivalue | Health-checked random selection | Client-side load distribution |

| CloudFront feature | What it does |
|---|---|
| Edge locations (400+) | Serve cached content near users |
| Origin Shield | Reduce origin load; one cache layer between edges and origin |
| Cache Policy | Define cache key (path + optional headers/cookies/query strings) |
| Cache invalidation | Purge stale content from all edge locations (~30s) |
| OAC | Restrict S3 bucket to CloudFront-only access |
| CloudFront Functions | Lightweight edge code (redirects, header manipulation) |
| Lambda@Edge | Full runtime at edge (JWT auth, dynamic content) |
| WAF integration | Block attacks at edge before reaching origin |
| HTTPS / ACM | Free TLS certificates with auto-renewal |

| Dimension | ALB | NLB |
|---|---|---|
| Layer | L7 (HTTP) | L4 (TCP/UDP) |
| IP type | Dynamic (DNS only) | Static per AZ |
| Source IP at target | X-Forwarded-For | Preserved (real client IP) |
| Routing | Host, path, header, query | IP + port only |
| Protocols | HTTP/HTTPS/WS | TCP/UDP/TLS |
| WAF | Yes | No |
| Lambda target | Yes | No |
| gRPC (end-to-end HTTP/2) | Limited | Yes (TCP passthrough) |
| Latency overhead | ~ms | ~microseconds |
| PrivateLink compatible | No | Yes |

## The Core Mental Model

```
Route 53 = DNS + traffic management policy
  Simple:      one answer, always
  Weighted:    split traffic by percentage (canary, migration)
  Latency:     lowest-latency AWS region (performance optimization)
  Failover:    primary / standby (disaster recovery)
  Geolocation: by country/continent (compliance, localization)
  Geoproximity: by distance + bias (fine-grained geographic split)

  Health check failover time = (RequestInterval × FailureThreshold) + TTL
  Fastest: 10s interval × 1 threshold + 60s TTL = 70s total
  Typical: 30s interval × 3 threshold + 60s TTL = 150s total

CloudFront = CDN + edge security + TLS offload
  Cache key determines who shares a cached response
  Zero TTL = pass-through to origin (for auth-required API endpoints)
  Max TTL = content-addressed assets (hash in filename → cache forever)
  OAC = block direct S3 access; CloudFront is the only path
  WAF at edge = block attacks before they cost you origin capacity
  Lambda@Edge = auth, A/B, personalization without hitting origin

ALB = HTTP routing intelligence
  Host-based: multiple domains → one ALB
  Path-based: /api/payments → payment-service; /api/users → user-service
  Header/query routing: canary deployments, feature flags at LB level
  Use ALB when you need HTTP-aware routing, WAF, Lambda targets, WebSocket

NLB = raw TCP/UDP performance + static IPs
  Use NLB when:
    Static IP required (IP allowlisting for partners)
    Source IP preservation at L4 (not via header)
    Ultra-low latency (trading, high-frequency processing)
    Non-HTTP protocols (gRPC end-to-end, MQTT, DNS, market data)
    PrivateLink (mandatory — PrivateLink only works with NLB)

The common pattern:
  Internet → Route 53 (geolocation or latency) → CloudFront (edge, WAF, cache)
  → ALB (HTTP routing, target groups) → ECS/Lambda (application)
  
  Static IPs needed? Insert NLB between CloudFront and ALB.
  Partner access without public internet? NLB + PrivateLink.
  Data residency? Geolocation routing + WAF geo-restriction = defense in depth.
```

**Tip for the interview:** Advanced networking questions at 5 YOE almost always escalate to one of three places: (1) the Alias record vs CNAME distinction — knowing that Alias records are free for AWS resource targets, can be placed at the zone apex (where CNAME is illegal in DNS spec), and auto-update when the target's IPs change (like when an ALB scales) is the kind of operational nuance that separates someone who has managed DNS in production from someone who has only read about it; (2) CloudFront cache key correctness — the moment you describe a case where an API returns user-specific data and CloudFront might serve User A's response to User B, you've identified the most dangerous CloudFront misconfiguration; knowing that the fix is TTL=0 (for authenticated APIs) and that Authorization headers must not be in the cache key (but must be forwarded to origin) demonstrates security awareness beyond performance optimization; (3) ALB vs NLB for PrivateLink — knowing that PrivateLink requires NLB (not ALB), that NLB provides static IPs for partner IP allowlisting, and that NLB preserves source IP at the L4 level while ALB uses X-Forwarded-For, is the architectural decision point that shows you understand the network stack rather than just knowing which AWS buttons to click. The fintech-specific callout: data residency with geolocation routing is a regulatory requirement for payment processing in India and UAE — knowing to use geolocation (not latency) routing for compliance, and to add WAF geo-restriction as defense-in-depth (so a DNS misconfiguration cannot accidentally route UAE traffic to India), is the kind of compliance-aware architecture thinking that matters in your domain.
