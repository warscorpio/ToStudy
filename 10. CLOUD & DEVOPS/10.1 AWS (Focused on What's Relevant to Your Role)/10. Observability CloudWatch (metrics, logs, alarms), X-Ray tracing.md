# Observability: CloudWatch (Metrics, Logs, Alarms), X-Ray Tracing — Interview Q&A (5 YOE Level)

---

## Section 1: Observability Fundamentals

**Q1. What are the three pillars of observability and how do CloudWatch and X-Ray cover them?**
A: Observability is the ability to understand the internal state of a system by examining its external outputs. The three pillars — metrics, logs, and traces — each answer different questions about a running system:

**Metrics** — aggregated numerical measurements over time. They answer "what is happening?" and "how much?" at a system level. CloudWatch Metrics stores time-series data: request rates, error rates, CPU utilization, queue depth, latency percentiles. Metrics are cheap to store and query; they alert you that something is wrong.

**Logs** — discrete event records with full context. They answer "what happened specifically?" for a given event. CloudWatch Logs stores structured or unstructured log entries from applications, AWS services, VPC flow logs, and CloudTrail. Logs tell you the details of what occurred once metrics tell you something is wrong.

**Traces** — causal, timing-aware records of a request's path through distributed services. They answer "where did this request spend its time, and which service caused the problem?" X-Ray captures traces across Lambda, ECS, EC2, API Gateway, DynamoDB, SQS, and other services, stitching them into a service map and waterfall view.

```
Alert fires: "Lambda error rate > 5%"    ← Metric detected the problem
    │
    ▼
CloudWatch Logs Insights query:          ← Log tells you which error
  "PAYMENT_GATEWAY_TIMEOUT on 43% of errors"
    │
    ▼
X-Ray trace for a failed request:        ← Trace shows where time was spent
  API Gateway (3ms) → Lambda (29s) → DynamoDB (1ms) → External PSP (29s — TIMEOUT)
```

Together they form a feedback loop: metrics alert, logs diagnose, traces pinpoint.

**Q2. What is the difference between observability and monitoring?**
A: Monitoring is the practice of tracking known failure modes — setting up dashboards and alerts for metrics you already know matter. It answers questions you thought to ask in advance: "Is CPU above 80%?" "Is the error rate above 1%?"

Observability is the ability to ask arbitrary questions about a system's behavior without deploying new instrumentation. An observable system lets you diagnose a novel failure mode — one you didn't predict — by querying existing telemetry. "Why is checkout slower for users in eu-west-2 on Tuesday mornings?" is a question you didn't think to monitor for; an observable system lets you answer it from existing metrics, logs, and traces.

At 5 YOE level, the distinction matters because: monitoring catches known problems; observability catches unknown ones. Production systems fail in ways you didn't anticipate. CloudWatch and X-Ray together provide observability when used correctly — structured logs with consistent fields, distributed traces with full context, and high-cardinality metrics that can be sliced by dimension.

## Section 2: CloudWatch Metrics

**Q3. What is the CloudWatch metrics data model and how are metrics organized?**
A: CloudWatch Metrics stores time-series data points organized by three identifying fields:

**Namespace** — a container for related metrics. AWS services use reserved namespaces: `AWS/Lambda`, `AWS/RDS`, `AWS/ECS`. Custom application metrics use a namespace you define: `MyApp/Payments`, `MyApp/Orders`.

**Metric name** — the name of the measurement within the namespace: `Duration`, `Errors`, `Invocations`, `CPUUtilization`.

**Dimensions** — key-value pairs that further identify the metric and enable filtering. `{FunctionName: "charge-processor"}` distinguishes one Lambda function's metrics from another. A metric is uniquely identified by `namespace + metric name + dimensions`.

```
Namespace:    AWS/Lambda
Metric Name:  Duration
Dimensions:   {FunctionName: "charge-processor", Resource: "charge-processor"}
Data points:  [{timestamp: T1, value: 245.3, unit: Milliseconds}, ...]

Namespace:    MyApp/Payments
Metric Name:  ChargeAttempts
Dimensions:   {Environment: "prod", PaymentMethod: "card", Currency: "USD"}
Data points:  [{timestamp: T1, value: 1247, unit: Count}, ...]
```

Each data point has a timestamp, value, unit, and optional statistics (if using high-resolution metrics with pre-aggregation). CloudWatch stores metrics for 15 months; data is aggregated over time (1-minute resolution retained for 15 days; 5-minute for 63 days; 1-hour for 455 days).

**Q4. How do you publish custom metrics from Lambda and why should you use EMF?**
A: Two approaches to publish custom metrics from Lambda:

**PutMetricData API (standard approach):**
```typescript
import { CloudWatch } from '@aws-sdk/client-cloudwatch';

const cloudwatch = new CloudWatch({});

await cloudwatch.putMetricData({
  Namespace: 'MyApp/Payments',
  MetricData: [{
    MetricName: 'ChargeAttempts',
    Value: 1,
    Unit: 'Count',
    Dimensions: [
      { Name: 'Environment', Value: process.env.ENVIRONMENT },
      { Name: 'PaymentMethod', Value: event.paymentMethod },
    ],
    Timestamp: new Date(),
  }],
});
```

**Problem:** every `PutMetricData` call is a synchronous API call that adds latency to the Lambda function. At high invocation rates, you hit CloudWatch API throttle limits. Cost: $0.01 per 1,000 custom metrics ingested.

**Embedded Metrics Format (EMF) — the production approach:**
EMF is a JSON log format that CloudWatch Logs automatically extracts into metrics — no API call required. The Lambda function writes structured JSON to stdout; CloudWatch Logs ingests it as a log entry AND extracts metric data points from it automatically:

```typescript
// Using aws-embedded-metrics library
import { createMetricsLogger, Unit } from 'aws-embedded-metrics';

exports.handler = async (event) => {
  const metrics = createMetricsLogger();
  metrics.setNamespace('MyApp/Payments');
  metrics.setDimensions({
    Environment: process.env.ENVIRONMENT,
    PaymentMethod: event.paymentMethod,
    Currency: event.currency,
  });

  const start = Date.now();
  try {
    const result = await processCharge(event);

    metrics.putMetric('ChargeSucceeded', 1, Unit.Count);
    metrics.putMetric('ChargeAmount', event.amount, Unit.None);
    metrics.putMetric('ChargeLatency', Date.now() - start, Unit.Milliseconds);

    return result;
  } catch (err) {
    metrics.putMetric('ChargeFailed', 1, Unit.Count);
    throw err;
  } finally {
    await metrics.flush();  // writes JSON to stdout; zero API calls
  }
};
```

The EMF output written to stdout:
```json
{
  "_aws": {
    "Timestamp": 1721740980000,
    "CloudWatchMetrics": [{
      "Namespace": "MyApp/Payments",
      "Dimensions": [["Environment", "PaymentMethod", "Currency"]],
      "Metrics": [
        {"Name": "ChargeSucceeded", "Unit": "Count"},
        {"Name": "ChargeLatency", "Unit": "Milliseconds"}
      ]
    }]
  },
  "Environment": "prod",
  "PaymentMethod": "card",
  "Currency": "USD",
  "ChargeSucceeded": 1,
  "ChargeLatency": 245,
  "orderId": "order-98432",    ← also logged; not extracted as metric
  "customerId": "cust-42"      ← also logged; not extracted as metric
}
```

**EMF advantages:** zero additional API calls (metrics are extracted from log data already being sent), no throttling concerns, same log entry is both a metric data point and a structured log record queryable in Logs Insights, and no extra cost beyond CloudWatch Logs ingestion.

**Q5. What are the most important built-in Lambda metrics and what do they indicate?**
A:

| Metric | Meaning | Alert condition |
|--- |--- |--- |
| `Invocations` | Total number of function calls | Baseline; sudden drop = upstream issue |
| `Errors` | Invocations that threw an unhandled exception | `Errors / Invocations > 1%` → alert |
| `Duration` | Execution time in ms (Average, p50, p99) | `p99 > 80% of timeout` → alert |
| `Throttles` | Invocations rejected due to concurrency limit | Any throttles → alert; increase reserved concurrency |
| `ConcurrentExecutions` | Simultaneous executions at any moment | Close to reserved/account limit → alert |
| `IteratorAge` | (Kinesis/DynamoDB Streams) Age of oldest record in shard | Growing age → consumer falling behind |
| `DeadLetterErrors` | Failed async invocations that couldn't reach DLQ | Any → alert; DLQ itself is failing |
| `InitDuration` | Cold start duration | P99 spikes → cold start issue; consider PC |

**The metrics that matter most for SLAs:**
- `Errors` rate — the primary health signal.
- `Duration p99` — tail latency; this is what users experience at the worst case.
- `Throttles` — any throttling means requests are failing or being delayed; often invisible without this metric.
- `IteratorAge` — for stream processing, this is the "consumer lag" equivalent; growing IteratorAge means processing cannot keep up with the produce rate.

**Q6. What are CloudWatch Metric Math and how do you use it for meaningful alarms?**
A: Metric Math allows you to create new time-series by performing mathematical operations on existing metrics. This enables derived metrics — like error rate — that are more meaningful for alerting than raw counts:

```
Alarm: "Error rate > 5% over the last 5 minutes"

Without Metric Math (wrong approach):
  Alarm on: Errors > 10
  Problem: 10 errors at 10 invocations/min = 100% error rate (critical)
            10 errors at 10,000 invocations/min = 0.1% error rate (fine)
  The count alone doesn't tell you the severity.

With Metric Math (correct approach):
  m1: Invocations (Sum, 5min)
  m2: Errors (Sum, 5min)
  e1: m2 / m1 * 100    ← error rate percentage

  Alarm on: e1 > 5     ← 5% error rate regardless of traffic volume
```

```json
{
  "AlarmName": "LambdaErrorRate",
  "Metrics": [
    {
      "Id": "m1",
      "MetricStat": {
        "Metric": {"Namespace": "AWS/Lambda", "MetricName": "Invocations",
                   "Dimensions": [{"Name": "FunctionName", "Value": "charge-processor"}]},
        "Period": 300,
        "Stat": "Sum"
      }
    },
    {
      "Id": "m2",
      "MetricStat": {
        "Metric": {"Namespace": "AWS/Lambda", "MetricName": "Errors",
                   "Dimensions": [{"Name": "FunctionName", "Value": "charge-processor"}]},
        "Period": 300,
        "Stat": "Sum"
      }
    },
    {
      "Id": "e1",
      "Expression": "m2 / m1 * 100",  // error rate percentage
      "Label": "Error Rate (%)"
    }
  ],
  "ComparisonOperator": "GreaterThanThreshold",
  "Threshold": 5,
  "EvaluationPeriods": 2,    // must be above 5% for 2 consecutive 5-min periods
  "TreatMissingData": "notBreaching"  // no invocations = not an error
}
```

**Other useful Metric Math expressions:**
```
# Lambda: p99 latency approaching timeout (function timeout = 30s)
IF(p99Duration / 30000 > 0.8, 1, 0)   ← alert if p99 > 80% of timeout

# RDS: connection utilization
connectionUtilization = DBConnections / MaxConnections * 100

# SQS: approximate time until queue is drained
drainTime = ApproximateNumberOfMessagesVisible / (NumberOfMessagesSent + 1)
```

## Section 3: CloudWatch Logs

**Q7. How is CloudWatch Logs organized and what are the key concepts?**
A: CloudWatch Logs has a three-level hierarchy:

**Log Group** — a container for log streams that share the same retention policy and access control. Typically one log group per application or service component: `/aws/lambda/charge-processor`, `/ecs/payment-service`, `/aws/rds/instance/prod-db/error`.

**Log Stream** — a sequence of log events from a single source within the log group. For Lambda, each function version/invocation environment gets its own stream. For ECS, each task instance gets its own stream. Multiple parallel executions (Lambda concurrency, ECS replicas) create multiple streams within the same log group.

**Log Event** — a single timestamped record within a stream. Can be plain text or structured JSON.

```
Log Group: /aws/lambda/charge-processor
  Log Stream: 2024/07/23/[$LATEST]abc123def456
    Log Event: [2024-07-23T14:03:00.042Z] START RequestId: req-xyz...
    Log Event: [2024-07-23T14:03:00.043Z] {"level":"info","msg":"Processing charge",...}
    Log Event: [2024-07-23T14:03:00.891Z] {"level":"info","msg":"Charge succeeded",...}
    Log Event: [2024-07-23T14:03:00.892Z] END RequestId: req-xyz...
    Log Event: [2024-07-23T14:03:00.893Z] REPORT RequestId: req-xyz Duration: 849.12 ms...
  Log Stream: 2024/07/23/[$LATEST]789012ghijkl
    [different Lambda execution environment]
```

**Retention policies:** log groups do not expire by default (retain forever, accruing storage cost). Always set a retention policy:
```bash
aws logs put-retention-policy \
  --log-group-name /aws/lambda/charge-processor \
  --retention-in-days 30      # 30 days; adjust per compliance requirement
```

**Q8. What is CloudWatch Logs Insights and how do you use it effectively?**
A: CloudWatch Logs Insights is a query engine for log data. It parses structured JSON logs automatically, enabling SQL-like queries over log fields without manual extraction or regex:

```
# Find all charge failures in the last hour with their error codes
fields @timestamp, orderId, errorCode, customerId
| filter level = "error" and eventType = "charge_failed"
| sort @timestamp desc
| limit 100
```

```
# P99 charge processing latency by payment method in the last 24 hours
filter eventType = "charge_completed"
| stats pct(processingLatencyMs, 99) as p99Latency,
        count() as totalCharges
  by paymentMethod
| sort p99Latency desc
```

```
# Error rate by function version (useful after a deployment)
filter @type = "REPORT"
| stats sum(errorCount) as errors,
        count() as invocations,
        errors / invocations * 100 as errorRate
  by @logStream
| sort errorRate desc
```

```
# Find requests with specific trace ID (from X-Ray, for correlation)
fields @timestamp, @message
| filter @message like "trace-id-abc123"
| sort @timestamp asc
```

**Key Logs Insights functions:**
- `stats ... by field` — aggregate and group (like GROUP BY in SQL).
- `filter field = value` — filter log events.
- `pct(field, 99)` — percentile calculation.
- `parse @message "..." as field` — extract from unstructured logs using regex or glob patterns.
- `sort`, `limit`, `fields` — standard projection and ordering.

**Logs Insights for Lambda REPORT parsing:**
Lambda automatically logs a REPORT line with cold start and billing info:
```
REPORT RequestId: xyz Duration: 849.12 ms Billed Duration: 850 ms
       Memory Size: 512 MB Max Memory Used: 312 MB Init Duration: 234.56 ms
```

```
# Find all cold starts and their duration in the last hour
filter @type = "REPORT" and @initDuration > 0
| stats avg(@initDuration) as avgColdStartMs,
        max(@initDuration) as maxColdStartMs,
        count() as coldStartCount
| sort maxColdStartMs desc
```

**Q9. How do you structure logs for maximum queryability in CloudWatch Logs Insights?**
A: Logs Insights automatically parses JSON log events into fields. Structured JSON logs enable powerful queries without regex extraction:

**Do this (structured JSON):**
```typescript
// Using pino for structured logging in Lambda
import pino from 'pino';

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  // In Lambda, always use sync transport to avoid event loop issues
  transport: undefined,
});

// Enrich all logs with request context
const requestLogger = logger.child({
  requestId: event.requestContext?.requestId,
  traceId: process.env._X_AMZN_TRACE_ID,  // X-Ray trace ID
  functionVersion: context.functionVersion,
  environment: process.env.ENVIRONMENT,
});

requestLogger.info({
  eventType: 'charge_attempt',
  orderId: event.orderId,
  customerId: event.customerId,
  amount: event.amount,
  currency: event.currency,
  paymentMethod: event.paymentMethod,
}, 'Processing charge');

requestLogger.info({
  eventType: 'charge_completed',
  orderId: event.orderId,
  chargeId: result.chargeId,
  processingLatencyMs: Date.now() - start,
  pspReference: result.pspReference,
}, 'Charge succeeded');
```

**Don't do this (unstructured string concatenation):**
```typescript
console.log(`Processing charge for order ${event.orderId} amount ${event.amount}`);
// ← Cannot query by orderId or amount; must use regex to extract
```

**Key fields to always include in every log entry:**
- `requestId` / `correlationId` — links all log entries for one request.
- `traceId` — links to X-Ray trace.
- `level` — filters by severity.
- `eventType` — semantic name for what happened (enables `filter eventType = "..."` queries).
- `environment` — separates prod/staging in shared log groups.
- `userId` / `tenantId` — enables filtering by customer for support queries.

## Section 4: CloudWatch Alarms

**Q10. How do CloudWatch Alarms work and what are the alarm states?**
A: A CloudWatch Alarm monitors a metric or Metric Math expression and transitions between three states based on whether the metric crosses a threshold:

**ALARM** — the metric has breached the threshold for the required number of evaluation periods. Triggers actions: SNS notification, Auto Scaling, EC2 stop/terminate, Lambda invocation.

**OK** — the metric is within acceptable bounds. Triggers actions when transitioning from ALARM to OK (useful for "resolved" notifications).

**INSUFFICIENT_DATA** — not enough data has been received to evaluate the alarm. Occurs at initial creation, after data gaps, or for metrics with low granularity. Configure `TreatMissingData` to control behavior:
- `notBreaching` — treat missing as OK (default; prevents spurious ALARM during low traffic).
- `breaching` — treat missing as ALARM (use when missing data means something is wrong, like a critical service that should always be emitting metrics).
- `ignore` — keep current state.
- `missing` — stay in INSUFFICIENT_DATA.

```
Evaluation window example:
  Period: 60 seconds (1-minute resolution)
  EvaluationPeriods: 5
  DatapointsToAlarm: 3

  → Alarm fires when 3 out of the last 5 one-minute periods breach the threshold
  → Prevents brief spikes from triggering alerts ("M of N" evaluation)
```

The `DatapointsToAlarm` ("M of N") configuration is critical for avoiding alert fatigue from transient spikes: `EvaluationPeriods=5, DatapointsToAlarm=3` means the metric must be above threshold for 3 of the last 5 periods before the alarm fires. A momentary spike that resolves quickly doesn't trigger the alarm.

**Q11. How do you build a useful alerting strategy with CloudWatch Alarms?**
A: A production alerting strategy avoids two failure modes: too many alerts (alert fatigue — oncall ignores everything) and too few (missing real incidents). The strategy has three layers:

**Layer 1: P1 alerts — page immediately (critical, customer-impacting):**
```json
[
  {"metric": "Lambda Errors rate",    "threshold": "> 5% for 2/3 periods",    "action": "PagerDuty P1"},
  {"metric": "Lambda Throttles",      "threshold": "> 0 for 3/5 periods",     "action": "PagerDuty P1"},
  {"metric": "ALB 5xx rate",          "threshold": "> 1% for 2/3 periods",    "action": "PagerDuty P1"},
  {"metric": "Lambda p99 Duration",   "threshold": "> 25s (timeout=30s)",     "action": "PagerDuty P1"},
  {"metric": "SQS DLQ messages",      "threshold": "> 0 for any period",      "action": "PagerDuty P1"},
  {"metric": "Kinesis IteratorAge",   "threshold": "> 300s (5 minutes)",      "action": "PagerDuty P1"}
]
```

**Layer 2: P2 alerts — ticket, investigate next business day:**
```json
[
  {"metric": "Lambda InitDuration p99", "threshold": "> 3s for 5/5 periods",  "action": "Slack + Ticket"},
  {"metric": "RDS CPU",                 "threshold": "> 80% for 10/12 periods","action": "Slack + Ticket"},
  {"metric": "RDS FreeableMemory",      "threshold": "< 1GB for 5/5 periods", "action": "Slack + Ticket"},
  {"metric": "Lambda Errors rate",      "threshold": "> 1% for 5/5 periods",  "action": "Slack + Ticket"}
]
```

**Layer 3: Dashboard-only (informational; never alert):**
- Lambda `ConcurrentExecutions` (trending toward limit — awareness, not emergency).
- `ApproximateNumberOfMessagesVisible` (queue depth for capacity planning).
- `BilledDuration` sum (cost tracking).

**Composite alarms:**
```json
{
  "AlarmName": "PaymentServiceDegraded",
  "AlarmRule": "ALARM(LambdaErrorRateHigh) OR ALARM(LambdaThrottlesHigh) OR ALARM(ALB5xxHigh)",
  // Fire if ANY of the component alarms are in ALARM state
  // Use as the single alarm to page oncall rather than three separate pages
}
```

Composite alarms reduce noise: instead of three separate PagerDuty pages for related symptoms, one composite alarm fires once. The oncall investigates the component alarms to find the root cause.

**Q12. How do you use CloudWatch Anomaly Detection instead of static thresholds?**
A: Anomaly detection trains a machine learning model on a metric's historical patterns to establish a "normal" band. Alarms trigger when the metric falls outside this band — without needing to know the "normal" value in advance. Particularly useful for metrics with strong diurnal (time-of-day) or weekly patterns:

```json
{
  "AlarmName": "UnusualLambdaInvocationRate",
  "Metrics": [
    {
      "Id": "m1",
      "MetricStat": {
        "Metric": {"Namespace": "AWS/Lambda", "MetricName": "Invocations", ...},
        "Period": 300,
        "Stat": "Sum"
      }
    },
    {
      "Id": "e1",
      "Expression": "ANOMALY_DETECTION_BAND(m1, 2)",
      // 2 = number of standard deviations for the band width
      "Label": "Invocations (expected)"
    }
  ],
  "ComparisonOperator": "LessThanLowerOrGreaterThanUpperThreshold",
  "ThresholdMetricId": "e1"
  // Alarm fires when m1 falls outside the expected band
}
```

**Where anomaly detection outperforms static thresholds:**
- Traffic naturally varies by time of day (10x more requests at noon than at 3am). A static threshold that doesn't alarm at noon may alarm at 3am for normal traffic.
- "Traffic dropped unexpectedly" is hard to alert on statically — you'd need to know what the expected traffic is at every time of day. Anomaly detection learns this automatically.
- New metrics without historical baselines — start with anomaly detection while gathering baseline data; switch to static thresholds once patterns are understood.

## Section 5: X-Ray Tracing

**Q13. What is AWS X-Ray and how does it implement distributed tracing?**
A: AWS X-Ray is AWS's managed distributed tracing service. It collects trace data from instrumented services, correlates spans into complete traces, and provides a visual service map showing how requests flow between services and where time is spent.

X-Ray uses the same conceptual model as OpenTelemetry: a **trace** represents one end-to-end request; a **segment** (X-Ray's term for a span) represents one service's contribution to that trace; **subsegments** represent operations within a service (database calls, HTTP calls, custom operations).

```
X-Ray trace for a payment request:

API Gateway [3ms]
  └── Lambda: charge-processor [849ms]
        ├── DynamoDB: GetItem [4ms]        ← subsegment: DB lookup
        ├── PSP API: charge [802ms]        ← subsegment: HTTP call to Stripe
        │     └── (PSP is slow — this is the bottleneck)
        └── DynamoDB: PutItem [8ms]        ← subsegment: write result
```

**X-Ray trace context propagation:**
X-Ray uses the `X-Amzn-Trace-Id` HTTP header to propagate trace context between services. The header contains:
```
X-Amzn-Trace-Id: Root=1-5e272b78-1234567890abcdef12345678;Parent=53995c3f42cd8ad8;Sampled=1
```
- `Root` — the trace ID (globally unique).
- `Parent` — the upstream segment ID (establishes parent-child relationship).
- `Sampled=1` — this trace is being recorded (Sampled=0 means skip).

AWS-managed services (API Gateway, Lambda, SQS, SNS, DynamoDB, etc.) automatically read and propagate this header. For custom HTTP calls between your services, the X-Ray SDK injects and reads the header automatically.

**Q14. How do you instrument a Lambda function with X-Ray?**
A: X-Ray tracing for Lambda has two levels:

**Level 1: Enable active tracing (zero code changes).**
```yaml
# SAM template
MyFunction:
  Type: AWS::Serverless::Function
  Properties:
    Tracing: Active   # enables X-Ray; Lambda automatically creates a segment
```

With `Tracing: Active`, Lambda automatically creates a segment for the function invocation, captures duration, errors, and cold start status. You see the Lambda execution in X-Ray without any code changes. This is the minimum viable tracing configuration.

**Level 2: Add subsegments for internal operations (code changes required).**
Without custom subsegments, the X-Ray segment shows only the total Lambda duration — you can't see how time is distributed between database calls, HTTP calls, and business logic. The X-Ray SDK adds this granularity:

```typescript
import { Tracer } from '@aws-lambda-powertools/tracer';  // Lambda Powertools

const tracer = new Tracer({ serviceName: 'charge-processor' });

export const handler = tracer.captureLambdaHandler(async (event, context) => {
  // Automatically: captures cold start, handler duration, errors

  // Custom subsegment for a database call
  const segment = tracer.getSegment();
  const subsegment = segment!.addNewSubsegment('DynamoDB.GetItem');
  try {
    const order = await dynamodb.get({ TableName: 'Orders', Key: { id: event.orderId } }).promise();
    subsegment.addAnnotation('orderId', event.orderId);   // indexed; filterable
    subsegment.addMetadata('orderData', order.Item);       // not indexed; for context
    return order.Item;
  } catch (err) {
    subsegment.addError(err);
    throw err;
  } finally {
    subsegment.close();
  }
});
```

**Lambda Powertools for TypeScript/Python** — the recommended approach. It provides decorators and utilities that capture handler execution, annotate segments, capture HTTP clients automatically, and integrate with the Tracer:

```typescript
// Powertools automatically captures: AWS SDK calls, HTTP calls, errors
const tracer = new Tracer();
const dynamodb = tracer.captureAWSv3Client(new DynamoDBDocumentClient(new DynamoDBClient({})));
// ↑ All DynamoDB calls are now automatically captured as subsegments
```

**Q15. What are annotations vs metadata in X-Ray and when do you use each?**
A: Both annotations and metadata attach additional information to a segment or subsegment, but they differ critically in queryability:

**Annotations** — indexed key-value pairs. Searchable in the X-Ray console and API using filter expressions. Use for high-cardinality data you need to search by:
```typescript
subsegment.addAnnotation('orderId', event.orderId);
subsegment.addAnnotation('customerId', event.customerId);
subsegment.addAnnotation('paymentMethod', event.paymentMethod);
subsegment.addAnnotation('chargeStatus', 'succeeded');
```

X-Ray filter expression: `annotation.paymentMethod = "card" AND annotation.chargeStatus = "failed"`
→ Find all failed card charges; drill into their traces.

Limitation: annotations can only be strings, numbers, or booleans. Max 50 annotations per trace.

**Metadata** — non-indexed key-value pairs. NOT searchable but can store rich data (objects, arrays). Use for context that's useful when you're already looking at a trace but don't need to search by:
```typescript
subsegment.addMetadata('requestPayload', { amount: event.amount, items: event.items });
subsegment.addMetadata('pspResponse', { authCode: psp.authCode, avsResult: psp.avsResult });
```

**Rule of thumb:** if you ever want to find traces BY this value (filter by orderId, by customer, by error type), use annotation. If you just want to see this value WHEN you're already looking at a trace (full request payload, PSP raw response), use metadata.

**Q16. What is X-Ray sampling and how do you configure it?**
A: Sampling controls what fraction of requests generate a trace. Recording 100% of traces at production scale is prohibitively expensive (storage + analysis cost). Sampling reduces cost while preserving enough traces for meaningful analysis.

**Default sampling rule:** record 5% of requests (the first request per second, then 5% of subsequent requests per second per host).

**Custom sampling rules:**
```json
{
  "version": 2,
  "rules": [
    {
      "description": "Always trace errors",
      "host": "*",
      "http_method": "*",
      "url_path": "*",
      "fixed_target": 0,
      "rate": 1.0,
      "attributes": {"http.status_code": "5*"}
      // Match if status code starts with 5; 100% sample rate for errors
    },
    {
      "description": "High rate for payment endpoints",
      "host": "*",
      "http_method": "POST",
      "url_path": "/charges",
      "fixed_target": 10,   // always record first 10 per second
      "rate": 0.1           // then 10% of remaining
    },
    {
      "description": "Low rate for health checks",
      "host": "*",
      "http_method": "GET",
      "url_path": "/health*",
      "fixed_target": 0,
      "rate": 0.001   // 0.1% — health checks are noise
    },
    {
      "description": "Default for everything else",
      "host": "*",
      "http_method": "*",
      "url_path": "*",
      "fixed_target": 1,
      "rate": 0.05    // 5% default
    }
  ]
}
```

**Key sampling design decisions:**
- Always sample errors at 100% — you need full traces for every failure to debug.
- Sample health checks at < 1% — they generate noise without signal.
- Sample payment/critical endpoints at higher rates (10–20%) — more traces = better latency distribution visibility.
- Use `fixed_target` to guarantee at least N traces per second regardless of rate — ensures you get traces even during low traffic.

**Q17. What is the X-Ray Service Map and how do you use it for incident response?**
A: The X-Ray Service Map is a visual graph where each node is a service (Lambda function, DynamoDB table, external HTTP endpoint, API Gateway stage) and each edge is a connection between services. Node color and edge width indicate health and traffic volume in real time.

```
X-Ray Service Map (incident view):

[Client] ──► [API Gateway] ──► [Lambda: charge-processor] ──► [DynamoDB: Orders] (green)
                                         │
                                         └──► [Stripe API] (RED — high error rate)
                                                    └── Avg latency: 8.2s ← timeout
```

**Using the Service Map during an incident:**

1. Open X-Ray console → Service Map.
2. Look for red nodes (elevated error rate) or thick edges with high latency.
3. Click on the red node to see the error breakdown: what errors? What percentage?
4. Click "View traces" to see individual traces that contain errors.
5. Open a trace → find the failing subsegment → see the exact error message, duration, and call parameters.

This workflow — metric alerts → service map identifies which service → trace pinpoints the exact call and error — is the core X-Ray incident response pattern. Without X-Ray, step 2 (which service?) requires manual log searching across multiple services.

**Q18. How do you correlate X-Ray traces with CloudWatch Logs?**
A: Correlating traces and logs allows you to jump from a slow/failing trace directly to the log entries generated during that request:

**Inject trace ID into all log entries:**
```typescript
import { Logger } from '@aws-lambda-powertools/logger';
import { Tracer } from '@aws-lambda-powertools/tracer';

const logger = new Logger({ serviceName: 'charge-processor' });
const tracer = new Tracer({ serviceName: 'charge-processor' });

export const handler = tracer.captureLambdaHandler(
  logger.injectLambdaContext(async (event, context) => {
    // Lambda Powertools automatically injects into every log entry:
    // - xray_trace_id
    // - cold_start
    // - function_name, function_version
    // - correlation_id (from event if configured)
    logger.info('Processing charge', {
      orderId: event.orderId,
      amount: event.amount,
    });
    // Output: {"level":"INFO","message":"Processing charge","xray_trace_id":"1-5e272b78-...","orderId":"42","amount":10000,...}
  })
);
```

**In CloudWatch Logs Insights:**
```
# Find all log entries for a specific X-Ray trace
fields @timestamp, @message, orderId, level
| filter xray_trace_id = "1-5e272b78-1234567890abcdef12345678"
| sort @timestamp asc
```

**In X-Ray console:**
From a trace, the "Logs" tab shows CloudWatch Logs entries that contain the matching trace ID — one-click navigation from trace to logs.

This bidirectional correlation — trace to logs, logs to trace — is the production workflow for diagnosing specific failing requests. The trace tells you WHERE the latency is; the logs tell you WHY.

**Q19. What makes a good CloudWatch dashboard and what should every production service have?**
A: A useful dashboard answers operational questions at a glance during an incident. It should enable a first-responder to determine: is this service healthy? If not, which component is failing? Without requiring them to know how to query Logs Insights or construct Metric Math expressions under pressure.

Row 1: Service Health (the RED method: Rate, Errors, Duration)

  [Line chart: Error rate % (Metric Math: errors/invocations)]
  [Line chart: p50/p99 latency]

  [Line chart: DynamoDB latency (p99 per table)]

  [Line chart: Charge success rate]

The first row (Rate, Errors, Duration — the RED method) answers "is something wrong?" in 3 seconds. The subsequent rows answer "what specifically is wrong?" Row 4 answers "what is the business impact?" — useful for communicating incident severity to non-technical stakeholders.

**Q20. How do you implement a structured log and metric strategy for a Lambda-based microservice?**
A: A complete observability setup using Lambda Powertools (production-recommended):

```typescript
import { Logger } from '@aws-lambda-powertools/logger';
import { Tracer } from '@aws-lambda-powertools/tracer';
import { Metrics, MetricUnits } from '@aws-lambda-powertools/metrics';

const logger = new Logger({
  serviceName: 'charge-processor',
  logLevel: process.env.LOG_LEVEL as LogLevel || 'INFO',
  persistentLogAttributes: {
    environment: process.env.ENVIRONMENT,
    version: process.env.AWS_LAMBDA_FUNCTION_VERSION,
  },
});

const tracer = new Tracer({ serviceName: 'charge-processor' });

const metrics = new Metrics({
  namespace: 'MyApp/Payments',
  serviceName: 'charge-processor',
  defaultDimensions: { Environment: process.env.ENVIRONMENT || 'unknown' },
});

export const handler =
  tracer.captureLambdaHandler(
    metrics.logMetrics(                     // flushes metrics after each invocation
      logger.injectLambdaContext(           // injects trace ID, cold start flag
        async (event: ChargeEvent, context: Context) => {
          const startTime = Date.now();

          logger.info('Charge request received', {
            eventType: 'charge_request',
            orderId: event.orderId,
            amount: event.amount,
            currency: event.currency,
            paymentMethod: event.paymentMethod,
          });

          try {
            const result = await processCharge(event);
            const latency = Date.now() - startTime;

            logger.info('Charge completed', {
              eventType: 'charge_succeeded',
              orderId: event.orderId,
              chargeId: result.id,
              processingLatencyMs: latency,
            });

            metrics.addMetric('ChargeSucceeded', MetricUnits.Count, 1);
            metrics.addMetric('ChargeLatency', MetricUnits.Milliseconds, latency);
            metrics.addDimension('PaymentMethod', event.paymentMethod);

            return result;

          } catch (err) {
            logger.error('Charge failed', {
              eventType: 'charge_failed',
              orderId: event.orderId,
              error: err.message,
              errorCode: err.code,
            });

            metrics.addMetric('ChargeFailed', MetricUnits.Count, 1);
            metrics.addDimension('ErrorCode', err.code || 'UNKNOWN');

            throw err;
          }
        }
      )
    )
  );
```

This setup provides:
- Structured JSON logs with trace ID, cold start flag, and service metadata on every entry.
- Zero-API-call custom metrics via EMF (flushed by `logMetrics` decorator).
- Automatic X-Ray segments and subsegments for AWS SDK calls.
- Consistent log fields (`eventType`) that enable Logs Insights queries.

## Section 7: Scenario Questions

**Q21. "Your Lambda error rate alarm just fired. Walk me through your investigation using CloudWatch and X-Ray."**
A: A systematic incident response using AWS observability tools:

**Step 1: Establish scope (CloudWatch Metrics — 2 minutes).**
```
CloudWatch console → Metrics → AWS/Lambda → charge-processor
  - When did the error rate start rising? (chart shows T-23min)
  - Is the invocation rate normal? (yes — not a traffic spike)
  - Are there throttles? (no — concurrency is not the issue)
  - What's p99 duration? (spiking to 29.5s — near the 30s timeout!)
  - Is it all invocations or some? (error rate = 43% — not 100%)
```

**Step 2: Identify error pattern (CloudWatch Logs Insights — 5 minutes).**
```
# Query: what errors are occurring?
fields @timestamp, level, eventType, errorCode, error, orderId
| filter level = "ERROR"
| stats count() as errorCount by errorCode
| sort errorCount desc

Results:
  EXTERNAL_TIMEOUT    847    ← most errors are timeouts calling external service
  CARD_DECLINED       23     ← normal; not related to the incident
  INVALID_INPUT       5      ← normal
```

**Step 3: Pinpoint the cause (X-Ray — 3 minutes).**
```
X-Ray console → Service Map:
  API Gateway → Lambda (charge-processor) → [Stripe API] ← RED node, 8.2s avg latency

Click on Stripe API node → "View traces"
→ Filter: error = true, last 30 minutes
→ Open failing trace:
  Lambda: charge-processor [29,847ms]
    DynamoDB: GetItem [3ms] ✓
    Stripe API: charge [29,841ms] ✗   ← TIMEOUT waiting for Stripe
    (DynamoDB PutItem never runs — Lambda timed out)

Annotation: paymentMethod = "card", chargeStatus = "timeout"
```

**Step 4: Correlate with logs (30 seconds).**
```
# From the X-Ray trace, copy the trace ID, then in Logs Insights:
filter xray_trace_id = "1-5e272b78-abc123"
| sort @timestamp asc

Reveals the exact sequence: request received, DynamoDB OK, Stripe call started,
no response for 29 seconds, Lambda timeout — confirms Stripe is the root cause.
```

**Step 5: Remediation.**
```
Immediate: circuit break Stripe calls (manual flag or feature flag)
           Route affected orders to manual processing queue
Short-term: reduce Stripe call timeout to 10s; implement fallback payment processor
            Add alarm on subsegment latency: "Stripe API p99 > 5s for 3/5 periods"
Post-incident: implement circuit breaker pattern for Stripe integration
```

**Q22. "You need to alert when Lambda costs are trending to exceed budget. How do you build this in CloudWatch?"**
A: Lambda billing is based on `BilledDuration` × `MemorySize`. CloudWatch has a `BilledDuration` metric for Lambda; multiply by memory to get GB-seconds:

```
# Metric Math for daily Lambda cost estimate

m1: BilledDuration (Sum, 1d) for all functions in the account
m2: memory_size (from function config — must be a constant or dimension)

# GB-seconds = (BilledDuration in ms / 1000) × (MemorySize in MB / 1024)
e1: (m1 / 1000) * (512 / 1024)    // for a 512MB function
e2: e1 * 0.0000166667              // AWS Lambda price per GB-second (us-east-1)
e3: e2 * 1000000 * 0.0000002       // plus request charges: $0.20 per 1M requests

# Total daily cost estimate
total: e2 + e3
```

**More practical approach: use AWS Budgets + CloudWatch:**
```json
{
  "BudgetName": "Lambda-Monthly",
  "BudgetLimit": {"Amount": "500", "Unit": "USD"},
  "BudgetType": "COST",
  "CostFilters": {"Service": ["AWS Lambda"]},
  "TimeUnit": "MONTHLY",
  "NotificationsWithSubscribers": [
    {
      "Notification": {
        "NotificationType": "FORECASTED",
        "ComparisonOperator": "GREATER_THAN",
        "Threshold": 80   // alert when forecasted to exceed 80% of budget
      },
      "Subscribers": [{"SubscriptionType": "SNS", "Address": "arn:aws:sns:..."}]
    }
  ]
}
```

AWS Budgets uses ML to forecast end-of-month spend and alerts when the forecast exceeds a threshold — more useful than a point-in-time spend alarm because it gives advance warning before the budget is actually exceeded.

For granular cost visibility, tag Lambda functions by team/product and use Cost Explorer filtered by tag to see which functions are driving cost. `BilledDuration` alone is the operational signal; Cost Explorer is the financial signal.

## Quick Reference

| Component | What it does | Key detail |
|--- |--- |--- |
| CloudWatch Metrics | Time-series numerical data | Namespace + metric name + dimensions = unique metric |
| Custom metrics | PutMetricData API or EMF | EMF via stdout is zero-cost in API calls; preferred |
| Metric Math | Derived metrics from existing ones | `m2/m1*100` = error rate; always alarm on rates not counts |
| Anomaly Detection | ML-based normal band | Use for diurnal/weekly patterns; fire on deviation |
| CloudWatch Logs | Log event storage and query | Log group → log streams → log events; set retention |
| Logs Insights | SQL-like log query engine | JSON auto-parsed into fields; `stats ... by field` for aggregation |
| EMF | JSON logs auto-extracted to metrics | Zero API calls; same entry is log + metric |
| CloudWatch Alarms | Metric threshold monitoring | `DatapointsToAlarm` (M of N) prevents transient alert spam |
| Composite alarms | Multi-metric alarm | Single page for related symptoms; component alarms for RCA |
| X-Ray | Distributed tracing | Segments (service) + subsegments (operations) + trace (request) |
| X-Ray annotations | Indexed trace attributes | Searchable; use for orderId, customerId, status |
| X-Ray metadata | Non-indexed trace data | Rich context; not searchable; for payloads, full responses |
| X-Ray Service Map | Visual service dependency graph | Node color = health; click node → traces → logs |
| X-Ray sampling | Fraction of requests traced | Always 100% errors; reduce health checks to < 1% |
| Lambda Powertools | Observability SDK for Lambda | Handles Logger + Tracer + Metrics with zero-boilerplate |
| `TreatMissingData` | Alarm behavior with no data | `notBreaching` for low traffic; `breaching` if missing = problem |

**Tip for the interview:** AWS observability questions at 5 YOE level test whether you know how to connect the three pillars into a coherent incident response workflow — not just what each service does. Lead with the workflow: metric alarm tells you something is wrong, Logs Insights tells you what the error is, X-Ray trace shows where time is spent and which downstream service is failing. The specific details that separate senior answers: knowing that alarms should fire on error rate (Metric Math `errors/invocations`) not raw error count (a static count threshold means different things at different traffic levels), understanding EMF as the production way to emit custom metrics from Lambda (not `PutMetricData` API calls on the hot path), and articulating the annotation vs metadata distinction (annotations are indexed and searchable; metadata is rich context visible only when you're already looking at a trace). If asked about sampling: always 100% for errors, reduce for health checks to near zero — these two rules show you understand the cost-signal trade-off of sampling in production.
