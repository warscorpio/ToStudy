# AWS Messaging: SQS, SNS, EventBridge — Interview Q&A (5 YOE Level)

---

## Section 1: SQS Fundamentals

**Q1. What is SQS and what problem does it solve in a distributed system?**
A: Amazon SQS (Simple Queue Service) is a fully managed message queue that decouples the producer of a message from the consumer. The producer writes to the queue and moves on — it does not wait for the consumer to process the message. The consumer reads from the queue at its own pace. This decoupling solves three specific distributed systems problems:

**Problem 1 — Traffic absorption (buffering):**
```
Without SQS:
  Loan origination service → directly calls KYC service
  KYC service handles 100 req/s; loan origination sends 500 req/s during batch
  Result: KYC service overwhelmed, throws 503s, loan origination fails

With SQS:
  Loan origination → SQS queue (absorbs 500 req/s instantly)
  KYC service polls SQS → processes 100 req/s at its own rate
  Queue depth grows during spike; drains when batch ends
  Neither service fails; loan origination never sees a 503
```

**Problem 2 — Producer/consumer lifecycle independence:**
```
Without SQS:
  Payment service calls notification service via HTTP
  Notification service deploys → 30-second downtime
  Payment service calls during downtime → connection refused → payment record lacks notification

With SQS:
  Payment service → SQS (message persisted durably in queue)
  Notification service deploys → restarts → resumes polling
  Messages sent during downtime are consumed after restart
  Zero message loss despite consumer downtime
```

**Problem 3 — Load leveling across consumer instances:**
```
Without SQS:
  10 upstream services each call 5 downstream workers directly
  Each worker receives messages from multiple sources simultaneously
  Coordination problem: which worker handles which message? Thundering herd.

With SQS:
  All 10 upstream services enqueue into one SQS queue
  5 workers each poll the queue independently
  SQS guarantees each message is delivered to exactly one worker (at a time)
  Adding workers = more throughput; removing workers = messages stay queued
```

**What SQS is not:**
- Not a message broker with routing logic (use SNS or EventBridge for fan-out)
- Not a pub/sub system (one queue → one consumer group, not multiple)
- Not an event stream (no consumer offset, no replay — use Kinesis or Kafka)
- Not a synchronous RPC mechanism (use API Gateway or direct HTTP for request-response)

**Q2. What are the differences between SQS Standard and SQS FIFO queues?**
A: SQS offers two queue types with fundamentally different delivery guarantees. The choice between them affects throughput, ordering, and deduplication behavior.

**Standard Queue:**
```
Delivery: at-least-once
  A message may be delivered MORE than once.
  Cause: distributed infrastructure; after visibility timeout, message becomes
         visible again if the consumer did not delete it in time.
  Requirement: consumers MUST be idempotent (processing the same message twice
               produces the same result as processing it once).

Ordering: best-effort (not guaranteed)
  Messages are generally delivered in the order they were sent, but AWS makes
  no ordering guarantee. High-throughput distributed infrastructure means
  messages can arrive out of order.

Throughput: effectively unlimited
  Default: 3,000 messages/second with batching (10 messages per API call)
           → 30,000 messages/second
  Standard queues scale to any throughput without configuration.

Use when:
  Order does not matter (sending notifications, triggering background jobs)
  Consumer is idempotent (safe to process twice)
  High throughput required (NACH batch event publishing, webhook delivery)
  Maximum throughput > correctness of ordering
```

**FIFO Queue:**
```
Delivery: exactly-once (within a deduplication window)
  Deduplication ID: each message has a MessageDeduplicationId
  If two messages with the same deduplication ID are sent within 5 minutes,
  the second is silently discarded by SQS.
  Prevents duplicate processing even if the producer retries.

Ordering: strict FIFO per message group
  Messages are delivered in the exact order they were sent, per MessageGroupId.
  Different MessageGroupIds are processed independently and in parallel.
  One MessageGroupId = one logical FIFO lane.

Throughput: 3,000 messages/second with batching (300 without)
  Hard limit per FIFO queue. Cannot exceed this without architectural changes.
  For > 3,000 msg/s: shard across multiple FIFO queues (by tenant/merchant ID).

MessageGroupId:
  Determines ordering lane. All messages with the same MessageGroupId are
  delivered in FIFO order to ONE consumer at a time.
  If you use one MessageGroupId for all messages → single-threaded consumption
  (one consumer processes at a time; parallelism = 0).
  Correct pattern: MessageGroupId = entity being processed (loanId, merchantId)
  → Multiple entities processed in parallel; each entity's messages ordered.

Content-based deduplication:
  If enabled: SQS computes SHA-256 of the message body as the deduplication ID.
  Use when: producing identical messages for the same operation (retries).
  Disable when: two different messages happen to have identical bodies but are
                distinct events (rare but possible).

Use when:
  Order matters (NACH mandate status transitions: CREATED → PENDING → ACTIVE)
  Exactly-once processing required (financial transactions, payment events)
  Entity-level FIFO is needed (all events for loan_042 in order)
  Throughput < 3,000 msg/s (or shard by entity for higher throughput)
```

**Comparison table:**

| Dimension | Standard | FIFO |
|---|---|---|
| Delivery guarantee | At-least-once | Exactly-once (5-min dedup window) |
| Ordering | Best-effort | Strict per MessageGroupId |
| Throughput | Unlimited | 3,000 msg/s (batched) |
| Deduplication | None (consumer must handle) | MessageDeduplicationId |
| Parallel consumption | Yes | Yes, per unique MessageGroupId |
| Use case | High-throughput background jobs | Ordered financial state machines |
| Queue name suffix | None | Must end in `.fifo` |

**Q3. How does SQS message visibility work, and what is the visibility timeout?**
A: SQS does not delete messages when they are received — it temporarily hides them. This is the visibility timeout mechanism, which enables at-least-once delivery and failure recovery.

**The visibility timeout lifecycle:**
```
Message sent to queue:
  State: Available (visible to all consumers)

Consumer A calls ReceiveMessage:
  Message delivered to Consumer A
  State: In-flight (invisible to all OTHER consumers)
  Visibility timeout clock starts (default: 30 seconds)

During visibility timeout, two outcomes:

Outcome 1 — Consumer A processes successfully:
  Consumer A calls DeleteMessage (before timeout expires)
  Message deleted permanently from queue
  Other consumers never see this message

Outcome 2 — Consumer A fails (crash, exception, timeout):
  Consumer A does NOT call DeleteMessage
  Visibility timeout expires
  State: Available again (visible to all consumers)
  Consumer B receives the message — processes it
  This is the "at-least-once" delivery: message processed twice

Visibility timeout configuration:
  Default: 30 seconds
  Maximum: 12 hours
  Rule: set to (expected processing time × 3) + buffer
        If processing takes 10s on average, set timeout to 60s minimum
  If set too short: messages reappear before processing completes → duplicates
  If set too long: failed messages take hours to be retried

Extending visibility timeout mid-processing (ChangeMessageVisibility):
  Long-running job: heartbeat pattern
  Every 15 seconds: call ChangeMessageVisibility to extend the timeout
  Prevents timeout expiry during legitimate long processing

  // NestJS: extend visibility during long processing
  async processLargeKycDocument(message: SQSMessage): Promise<void> {
    const heartbeat = setInterval(async () => {
      await this.sqs.changeMessageVisibility({
        QueueUrl:          this.queueUrl,
        ReceiptHandle:     message.ReceiptHandle!,
        VisibilityTimeout: 60,  // extend by 60 more seconds
      }).promise();
    }, 30_000); // every 30 seconds

    try {
      await this.processDocument(message.Body!);
      await this.deleteMessage(message.ReceiptHandle!);
    } finally {
      clearInterval(heartbeat);
    }
  }
```

**Q4. What is the SQS Dead Letter Queue (DLQ) and how do you configure it?**
A: A Dead Letter Queue is a separate SQS queue that receives messages that could not be processed successfully after a configured number of attempts. It captures poison-pill messages (malformed payloads, bugs that cause consistent failures) so they do not block the main queue indefinitely.

**DLQ mechanics:**
```
Main queue: loan-processing-queue
DLQ:        loan-processing-queue-dlq

Configuration: Redrive Policy on the main queue
  maxReceiveCount: 3  ← message moved to DLQ after 3 failed receive attempts
  deadLetterTargetArn: arn:aws:sqs:...:loan-processing-queue-dlq

Flow:
  Message received by consumer → processing fails → consumer does not delete
  Visibility timeout expires → message becomes visible again (attempt 2)
  Processing fails again → timeout expires (attempt 3)
  Processing fails again → SQS moves message to DLQ (attempt count = maxReceiveCount)
  Main queue: message gone (no longer blocking other messages)
  DLQ: message available for inspection, debugging, or replay

maxReceiveCount selection:
  1: any single failure → DLQ (too aggressive; transient failures go to DLQ)
  3–5: typical production setting (allows transient retry, catches persistent failures)
  10+: patient retry (use with exponential backoff between retries)

DLQ retention:
  Set DLQ retention period LONGER than main queue:
  Main queue: 4 days (default)
  DLQ: 14 days (gives time to investigate and replay)

DLQ alarms (critical — always configure):
  CloudWatch alarm: ApproximateNumberOfMessagesVisible on DLQ > 0
  Action: page on-call engineer immediately
  Reason: any message in DLQ means a processing failure that auto-retry could not fix

DLQ redrive (replay after fixing the bug):
  aws sqs start-message-move-task \
    --source-queue-url https://sqs.../loan-processing-queue-dlq \
    --destination-queue-url https://sqs.../loan-processing-queue
  Moves all DLQ messages back to the main queue for reprocessing.
  Only do this AFTER deploying the fix — replaying into a broken consumer
  re-DLQs all messages and wastes the retry count.
```

**Q5. How do you implement SQS consumers in NestJS with proper error handling and backpressure?**
A: NestJS does not have a built-in SQS transport. The production pattern is a polling loop with concurrency control, visibility timeout management, and graceful shutdown.

```typescript
// sqs-consumer.service.ts
import { Injectable, OnApplicationBootstrap, OnApplicationShutdown, Logger } from '@nestjs/common';
import { SQS } from 'aws-sdk';

@Injectable()
export class LoanProcessingConsumer
  implements OnApplicationBootstrap, OnApplicationShutdown {

  private readonly logger = new Logger(LoanProcessingConsumer.name);
  private readonly sqs    = new SQS({ region: process.env.AWS_REGION });
  private readonly queueUrl = process.env.LOAN_QUEUE_URL!;
  private running  = false;
  private inFlight = 0;
  private readonly MAX_CONCURRENCY = 10; // process 10 messages simultaneously

  onApplicationBootstrap() {
    this.running = true;
    this.poll();
  }

  async onApplicationShutdown() {
    this.running = false;
    // Wait for in-flight messages to complete (graceful drain)
    while (this.inFlight > 0) {
      this.logger.log(`Draining: ${this.inFlight} messages in-flight`);
      await sleep(500);
    }
  }

  private async poll(): Promise<void> {
    while (this.running) {
      // Backpressure: do not receive more if at concurrency limit
      if (this.inFlight >= this.MAX_CONCURRENCY) {
        await sleep(100);
        continue;
      }

      try {
        const response = await this.sqs.receiveMessage({
          QueueUrl:              this.queueUrl,
          MaxNumberOfMessages:   Math.min(10, this.MAX_CONCURRENCY - this.inFlight),
          WaitTimeSeconds:       20,     // long polling: wait up to 20s for messages
          VisibilityTimeout:     120,    // 2 minutes per message
          AttributeNames:        ['ApproximateReceiveCount'],
          MessageAttributeNames: ['All'],
        }).promise();

        const messages = response.Messages ?? [];

        // Process messages concurrently (up to MAX_CONCURRENCY)
        for (const message of messages) {
          this.inFlight++;
          this.processMessage(message)
            .finally(() => { this.inFlight--; });
        }

      } catch (err) {
        this.logger.error('SQS receive error', err);
        await sleep(5_000); // back off on receive errors
      }
    }
  }

  private async processMessage(message: SQS.Message): Promise<void> {
    const receiveCount = parseInt(
      message.Attributes?.ApproximateReceiveCount ?? '1', 10
    );

    try {
      const payload = JSON.parse(message.Body!);

      // Exponential backoff for retries (visibility already expired once)
      // Apply artificial delay for retry attempts to avoid hammering downstream
      if (receiveCount > 1) {
        const backoffMs = Math.min(1000 * 2 ** (receiveCount - 1), 30_000);
        await sleep(backoffMs);
      }

      await this.loanService.processLoanApplication(payload);

      // Success: delete from queue
      await this.sqs.deleteMessage({
        QueueUrl:      this.queueUrl,
        ReceiptHandle: message.ReceiptHandle!,
      }).promise();

    } catch (err: any) {
      this.logger.error('Message processing failed', {
        messageId:    message.MessageId,
        receiveCount,
        error:        err.message,
      });

      // Do NOT delete the message — let visibility timeout expire
      // SQS will redeliver; after maxReceiveCount attempts → DLQ
      // For known-unrecoverable errors (bad schema): delete immediately + send to DLQ manually
      if (err instanceof ValidationError) {
        // Poison pill: delete from main queue, send to DLQ manually
        await this.sendToDlq(message, err);
        await this.sqs.deleteMessage({
          QueueUrl:      this.queueUrl,
          ReceiptHandle: message.ReceiptHandle!,
        }).promise();
      }
      // For transient errors (DB unavailable, downstream timeout): let SQS retry
    }
  }

  private async sendToDlq(message: SQS.Message, err: Error): Promise<void> {
    await this.sqs.sendMessage({
      QueueUrl:    process.env.LOAN_DLQ_URL!,
      MessageBody: message.Body!,
      MessageAttributes: {
        FailureReason: {
          DataType:    'String',
          StringValue: err.message,
        },
        OriginalMessageId: {
          DataType:    'String',
          StringValue: message.MessageId!,
        },
      },
    }).promise();
  }
}
```

**Long polling vs short polling:**
```
Short polling (WaitTimeSeconds: 0):
  SQS immediately returns with 0–10 messages (may return 0 even if queue has messages)
  Reason: SQS is distributed; a sample of servers is queried; some may not have your messages
  Cost: each empty ReceiveMessage call is billed ($0.40 per million API calls)
  At 100 polls/second: $34,560/month in polling costs alone for an empty queue

Long polling (WaitTimeSeconds: 1–20, recommended: 20):
  SQS waits up to 20 seconds for a message to arrive before returning
  If a message arrives at second 3: returns immediately with that message
  If no message after 20 seconds: returns empty response
  Eliminates empty polls on idle queues; reduces costs by 95%+
  Recommended for all production SQS consumers
```

## Section 2: SNS — Simple Notification Service

**Q6. What is SNS and how does it differ from SQS?**
A: SNS (Simple Notification Service) is a fully managed pub/sub messaging service. A single message published to an SNS topic is delivered to all subscribed endpoints simultaneously. This is the key architectural difference from SQS: SQS is point-to-point (one message → one consumer), SNS is fan-out (one message → many consumers).

**SQS vs SNS — the conceptual difference:**
```
SQS (queue):
  Producer → Queue → ONE consumer (from a pool of consumers)
  Message is consumed and deleted; other consumers never see it
  Pull model: consumer polls SQS for messages
  Use: background job processing, load leveling, decoupling

SNS (topic):
  Publisher → Topic → ALL subscribers simultaneously
  Same message delivered to EVERY subscriber
  Push model: SNS pushes to subscribers (they do not poll)
  Use: fan-out (one event must trigger many downstream actions)

Example: payment approved event
  SQS only: payment-approved → SQS → notification-worker
            Only the notification worker gets the event.
            Ledger service and analytics service must also poll the same queue
            → all three compete for the same message; only one gets it. WRONG.

  SNS fan-out: payment-approved → SNS topic
               → SQS queue (notification-worker)
               → SQS queue (ledger-worker)
               → SQS queue (analytics-worker)
               All three workers receive the same event independently. CORRECT.
```

**SNS subscription types:**
```
SQS:          SNS pushes to an SQS queue (most common; SQS provides persistence + retry)
HTTP/HTTPS:   SNS POSTs to a URL (webhooks, external services)
Lambda:       SNS invokes a Lambda function directly
Email:        SNS sends email (monitoring alerts, human notification)
SMS:          SNS sends SMS (OTP, critical alerts to on-call)
Mobile push:  SNS pushes to APNS (iOS), FCM (Android) via platform application
Firehose:     SNS delivers to Kinesis Data Firehose (streaming ingestion)

For durable event-driven architectures: always use SNS → SQS (not SNS → Lambda directly)
Reason:
  SNS → Lambda: if Lambda is throttled or errors, SNS retries 3 times then drops the message
  SNS → SQS → Lambda: SQS persists the message; Lambda can retry from SQS;
                      DLQ catches unprocessable messages; no message loss
```

**Q7. What is the SNS + SQS fan-out pattern and when is it the right architecture?**
A: The SNS-SQS fan-out pattern is the standard AWS architecture for events that must trigger multiple independent downstream actions. A single SNS publish fans out to N SQS queues, each owned by a separate consumer.

**The pattern:**
```
                     ┌─── SQS: notification-queue ───► Notification Worker
                     │    (sends SMS/email to borrower)
Payment Service ──► SNS: payment-events ──► SQS: ledger-queue ──────► Ledger Worker
                     │    (records debit/credit entries)
                     └─── SQS: analytics-queue ──────► Analytics Worker
                          (updates merchant dashboard metrics)

Benefits:
  Publishers are decoupled from subscribers: payment service does not know
  how many consumers exist or what they do.
  Adding a new consumer: subscribe a new SQS queue to the SNS topic.
  No change to the payment service. No deployment required.

  Each SQS queue is independent:
    Different visibility timeout (notification: 30s; ledger: 120s)
    Different DLQ configuration (different maxReceiveCount)
    Different scaling (ledger: 1 worker; analytics: 10 workers)
    Independent failure: notification queue backing up does not affect ledger

  Persistence: SNS → SQS means messages are persisted even if downstream consumers
  are briefly unavailable. SNS alone (SNS → Lambda) has no persistence.
```

**SNS message filtering (subscription filter policy):**
```
Without filtering:
  SNS topic receives ALL payment events (approved, rejected, pending, refunded)
  All subscribers receive all events
  Notification worker receives "pending" events → must check and discard → wasteful

With message filtering:
  Add a filter policy to each subscription

  // Notification subscription: only approved and rejected
  {
    "status": ["approved", "rejected"]
  }

  // Ledger subscription: all events (must record all state changes)
  {}  // empty filter = receive everything

  // Fraud-check subscription: only events > 50,000 INR
  {
    "amount": [{ "numeric": [">=", 50000] }]
  }

Filter policy operators:
  Exact match:       { "status": ["approved"] }
  Prefix match:      { "event_type": [{ "prefix": "payment." }] }
  Numeric range:     { "amount": [{ "numeric": [">", 1000, "<=", 50000] }] }
  Exists/not-exists: { "merchant_id": [{ "exists": true }] }
  AND across keys:   { "status": ["approved"], "currency": ["INR"] }
  OR within key:     { "status": ["approved", "rejected"] }

Cost benefit of filtering:
  SNS charges per delivery attempt, not per message received.
  Without filtering: 10,000 messages → 3 subscriptions = 30,000 delivery attempts
  With filtering (50% of messages match each sub): 10,000 messages → ~15,000 attempts
  Filtering also reduces SQS receive calls and Lambda invocations downstream.
```

**Q8. How does SNS handle delivery failures and what are its retry policies?**
A: SNS retry behavior differs by subscription type. Understanding retries is critical for designing reliable fan-out architectures.

**Retry policies by subscription type:**

```
SQS subscription:
  SNS retries delivery to SQS for up to 23 days (exponential backoff).
  If SQS queue is unavailable or returns an error, SNS keeps trying.
  Failure after 23 days: message is permanently lost from SNS's perspective.
  (SQS itself is extremely reliable; this scenario is rare but non-zero.)
  SQS DLQ is NOT triggered by SNS failures — DLQ only catches consumer processing failures.

HTTP/HTTPS subscription:
  Retry policy (configurable):
    Phase 1: immediate (3 retries, no delay)
    Phase 2: pre-backoff (2 retries, 1-second delay)
    Phase 3: backoff (10 retries, 20s → 20min exponential)
    Phase 4: post-backoff (100,000 retries, 20-minute delay)
  Default total retry period: up to 23 days
  Dead letter queue for HTTP: SNS supports a DLQ for failed HTTP deliveries
    (SQS or S3; captures messages that exhausted all retries)

Lambda subscription:
  Retry policy:
    3 total attempts (1 initial + 2 retries), 1-second delay between attempts
    If all 3 attempts fail: message dropped (no more retries from SNS)
    → This is why SNS → Lambda directly is dangerous for critical events
    → Use SNS → SQS → Lambda (SQS provides persistence + configurable retry)

Email/SMS subscription:
  Best-effort delivery; no retry guarantees
  Not suitable for critical business events

SNS delivery status logging:
  Enable for SQS and Lambda subscriptions:
  SNS logs delivery success/failure to CloudWatch Logs
  Log entry includes: message ID, status code, delivery timestamp, error details
  Essential for debugging missed deliveries in fan-out architectures

  aws sns set-subscription-attributes \
    --subscription-arn arn:aws:sns:...:subscription-id \
    --attribute-name DeliveryPolicy \
    --attribute-value '{
      "healthyRetryPolicy": {
        "minDelayTarget": 1,
        "maxDelayTarget": 60,
        "numRetries": 10,
        "backoffFunction": "exponential"
      }
    }'
```

## Section 3: EventBridge

**Q9. What is EventBridge and how does it differ from SNS?**
A: Amazon EventBridge is a serverless event bus that routes events from AWS services, custom applications, and SaaS partners to AWS targets based on event content rules. It is the evolution of CloudWatch Events and offers richer filtering, schema registry, event archiving, and replay capabilities beyond what SNS provides.

**EventBridge vs SNS — the key differences:**

| Dimension | SNS | EventBridge |
|---|---|---|
| Filtering | Per-subscription filter policy | Per-rule filter on any JSON field (richer) |
| Routing logic | Publish to one topic; filter per subscriber | Rules route events to different targets based on content |
| Event sources | Your code only | AWS services + custom + SaaS partners (200+ integrations) |
| Schema registry | No | Yes — auto-discovers and documents event schemas |
| Event archiving | No | Yes — archive all events; replay from archive |
| Cross-account | Yes (topic policy) | Yes (event bus policy) |
| Targets | SQS, Lambda, HTTP, email, SMS, mobile push | 20+ targets: SQS, Lambda, Step Functions, API Gateway, Kinesis, ECS, etc. |
| Throughput limit | 300M messages/second (effectively unlimited) | 10,000 events/second per bus (soft limit; can be increased) |
| Latency | ~5ms | ~500ms (routing overhead; not suitable for sub-100ms requirements) |
| Pricing | $0.50 per million publishes | $1.00 per million events (custom bus) |
| Use case | High-throughput fan-out to known subscribers | Event-driven orchestration, AWS service integration, schema-governed event bus |

**When to use EventBridge over SNS:**
```
Use EventBridge when:
  Events originate from AWS services (EC2 state change, RDS failover, S3 put)
    → EventBridge is the native integration layer for AWS service events
  You need content-based routing (route to different targets based on event body)
    → SNS filter policies filter per-subscription; EventBridge rules route to different targets
  You need event replay (audit, replay after bug fix, backfill)
    → EventBridge archives + replay; SNS has no replay
  You need schema governance (contract between producers and consumers)
    → EventBridge schema registry; SNS has no schema concept
  You need to integrate with SaaS (Datadog, PagerDuty, Zendesk, Shopify)
    → EventBridge has native SaaS partner event sources

Use SNS when:
  You need maximum throughput (> 10,000 events/second without limit increases)
  You need SMS or mobile push notifications
  You need sub-100ms fan-out latency
  Simple pub/sub with minimal routing logic
  Cost is a primary concern (SNS is 2× cheaper per million messages)
```

**Q10. How does EventBridge rule matching work and what filter patterns are available?**
A: EventBridge rules define which events on the bus match the rule and what targets receive matched events. Matching is done by pattern-matching the event JSON — it does not execute code, only matches structure and values.

**Event structure (all events have this envelope):**
```json
{
  "version":     "0",
  "id":          "6a7e8feb-b491-4cf7-a9f1-bf3703467718",
  "source":      "com.fintech.payments",
  "account":     "123456789012",
  "time":        "2024-01-15T14:30:00Z",
  "region":      "ap-south-1",
  "resources":   [],
  "detail-type": "PaymentApproved",
  "detail": {
    "payment_id":  "pay_001",
    "merchant_id": "merch_42",
    "amount":      15000,
    "currency":    "INR",
    "status":      "approved",
    "risk_score":  0.12
  }
}
```

**EventBridge filter patterns:**
```json
// Match by source and detail-type (most common)
{
  "source":      ["com.fintech.payments"],
  "detail-type": ["PaymentApproved"]
}

// Match specific field values in detail
{
  "source": ["com.fintech.payments"],
  "detail": {
    "currency": ["INR"],
    "status":   ["approved", "completed"]
  }
}

// Numeric range filtering
{
  "source": ["com.fintech.payments"],
  "detail": {
    "amount": [{ "numeric": [">=", 100000] }]   // ≥ 1 lakh INR
  }
}

// Prefix matching
{
  "source": [{ "prefix": "com.fintech." }]       // any fintech service
}

// Field existence check
{
  "detail": {
    "merchant_id": [{ "exists": true }],
    "test_flag":   [{ "exists": false }]           // exclude test events
  }
}

// Anything-but (exclusion)
{
  "detail": {
    "status": [{ "anything-but": ["test", "sandbox"] }]
  }
}

// Combining patterns (AND across keys, OR within key values)
{
  "source":      ["com.fintech.payments"],
  "detail-type": ["PaymentApproved", "PaymentCompleted"],  // OR
  "detail": {
    "currency":  ["INR"],               // AND
    "amount":    [{ "numeric": [">", 1000] }]  // AND
  }
}
```

**Routing the same event to different targets via multiple rules:**
```
Event: PaymentApproved for amount = 150,000 INR

Rule 1: all PaymentApproved events
  Pattern: { "detail-type": ["PaymentApproved"] }
  Target: SQS → notification-worker (send SMS to borrower)

Rule 2: high-value payments (> 1 lakh INR) require additional verification
  Pattern: {
    "detail-type": ["PaymentApproved"],
    "detail": { "amount": [{ "numeric": [">=", 100000] }] }
  }
  Target: Lambda → fraud-review-trigger (flag for manual review)

Rule 3: all payment events for audit
  Pattern: { "source": ["com.fintech.payments"] }
  Target: Kinesis Firehose → S3 (audit log archive)

All three rules match the 150,000 INR PaymentApproved event simultaneously.
Each target receives the event independently.
EventBridge delivers to all matching rules in parallel.
```

**Q11. What is the EventBridge Archive and Replay feature, and when does it matter in production?**
A: EventBridge Archive captures all events (or filtered events) published to a bus and stores them durably in S3. Replay re-sends archived events to the bus as if they were published now — triggering all matching rules and targets.

**Archive configuration:**
```
Event bus: default or custom
Archive name: fintech-payments-archive
Event pattern: { "source": ["com.fintech.payments"] }  // filter: only payment events
Retention: 90 days (0 = indefinite)

Events matching the pattern are stored in S3 (managed by EventBridge; not directly accessible)
Storage cost: $0.023 per GB-month (standard S3 rates)
```

**Replay scenarios:**
```
Scenario 1 — Bug fix replay:
  Bug discovered: notification Lambda had a bug for 3 hours; failed silently
  Fix deployed at 14:00
  Replay: re-send all PaymentApproved events from 11:00–14:00
  Notification Lambda re-processes; sends delayed notifications to borrowers
  Without archive: those 3 hours of events are permanently lost

Scenario 2 — New downstream service onboarding:
  New analytics service deployed; needs historical payment events to build dashboard
  Replay: send last 30 days of payment events through EventBridge
  New service's rule activates and processes all historical events
  Without archive: must restore from database dump and transform — complex and slow

Scenario 3 — Disaster recovery (cross-region):
  ap-south-1 (Mumbai) region has extended outage
  DR runbook: replay last N hours from archive to ap-southeast-1 (Singapore) bus
  All rules and targets in Singapore process the replayed events
  Enables event-level cross-region DR without duplicating event buses

How to start a replay:
  aws events start-replay \
    --replay-name fix-notification-replay \
    --event-source-arn arn:aws:events:ap-south-1::archive/fintech-payments-archive \
    --event-start-time 2024-01-15T11:00:00Z \
    --event-end-time   2024-01-15T14:00:00Z \
    --destination '{
      "Arn": "arn:aws:events:ap-south-1:123456789012:event-bus/fintech-payments",
      "FilterArns": ["arn:aws:events:...:rule/payment-approved-notification"]
    }'

Replay rate: configurable (1×, 2×, ... up to EventBridge throughput limit)
Idempotency: consumers MUST handle replayed events idempotently
  (they arrive with the original timestamp in detail.time but replayed now)
  Use the event ID + event time as the idempotency key; never re-send notifications
  for the same payment_id if already sent.
```

**Q12. What is an EventBridge Event Bus and how do you design a multi-bus architecture?**
A: An event bus is the routing layer that receives events and applies rules. AWS provides a default bus (AWS service events) and you create custom buses for your application events. Multi-bus design controls event visibility, cross-account routing, and blast radius.

**Bus types:**
```
Default bus:
  Receives all AWS service events for your account.
  EC2 state changes, RDS failovers, S3 object creation, CodePipeline events, etc.
  Cannot be deleted or modified. You add rules to it.
  Your custom events CAN be sent here, but it is cleaner to use a custom bus.

Custom bus:
  Created by you. Only receives events you explicitly publish.
  Named by your application/domain: "fintech-payments", "fintech-kyc"
  Separate rules, separate archive, separate permissions.
  Cost: $1.00/million events (same as default bus for custom events).

Partner bus (SaaS integrations):
  Created by AWS when you activate a partner event source.
  Example: Stripe → EventBridge partner bus → your rules → targets.
  Stripe publishes payment events directly to EventBridge; you consume them
  with rules — no webhook endpoint to maintain.
```

**Multi-bus architecture for a fintech platform:**
```
Bus: fintech-payments (payment events)
Bus: fintech-kyc      (KYC events)
Bus: fintech-lending  (loan origination events)
Bus: fintech-ops      (operational events: deployments, alerts, scaling events)

Rationale for separation:
  Blast radius: a misconfigured rule on the payments bus does not affect KYC rules
  Permission control: audit team has read access to fintech-payments only
  Throughput: each bus has its own 10,000 events/s limit (additive across buses)
  Archive: separate archive per bus; different retention policies
  Cross-account: lending platform is a separate AWS account; publishes to a shared bus

Cross-account event routing:
  Shared event bus account: fintech-events (centralized)
  Resource policy on shared bus: allow publish from payment account, kyc account, lending account

  // Resource policy on shared bus (fintech-events account):
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::PAYMENT_ACCOUNT_ID:root",
          "arn:aws:iam::KYC_ACCOUNT_ID:root"
        ]
      },
      "Action":   "events:PutEvents",
      "Resource": "arn:aws:events:ap-south-1:EVENTS_ACCOUNT_ID:event-bus/fintech-shared"
    }]
  }

  // Payment service (in payment AWS account) publishes to shared bus:
  await eventBridge.putEvents({
    Entries: [{
      EventBusName: 'arn:aws:events:ap-south-1:EVENTS_ACCOUNT_ID:event-bus/fintech-shared',
      Source:       'com.fintech.payments',

      Detail:       JSON.stringify(paymentEvent),
    }]
  }).promise();
```

## Section 4: Integrating SQS, SNS, and EventBridge

**Q13. How do SQS, SNS, and EventBridge compose together in a production event-driven architecture?**
A: The three services have complementary roles. The production pattern uses them in layers: EventBridge for routing and orchestration, SNS for fan-out to known subscriber groups, and SQS for durable consumption by individual workers.

**The three-layer event architecture:**

```
Layer 1 — Event Ingestion and Routing (EventBridge):
  Source services publish to EventBridge custom bus.
  EventBridge rules filter and route to appropriate targets.
  EventBridge archives for replay.
  This layer handles "which downstream should receive this event" logic.

Layer 2 — Fan-out (SNS):
  EventBridge rule target: SNS topic.
  SNS fans out to multiple SQS queues simultaneously.
  This layer handles "how many consumers receive this event" logic.

Layer 3 — Durable Consumption (SQS):
  Each SQS queue is consumed by one worker service.
  SQS provides persistence, visibility timeout, DLQ, and retry.
  This layer handles "reliable delivery to one consumer" logic.

Full flow for a NACH payment approved event:
  NACH batch service
    │ putEvents
    ▼
  EventBridge: fintech-payments bus
    │
    ├─ Rule: all NACH payment events
    │    Target: SNS topic (nach-payment-events)
    │
    └─ Rule: failed NACH events only
         Target: Lambda (trigger manual review workflow)

  SNS topic (nach-payment-events)
    ├─ SQS: notification-queue → Notification Worker
    │         (sends SMS confirmation to borrower)
    ├─ SQS: ledger-queue → Ledger Worker
    │         (records repayment entry in accounting system)
    └─ SQS: analytics-queue → Analytics Worker
              (updates merchant repayment dashboard)

When to skip the middle layer:
  EventBridge → SQS directly (no SNS):
    Use when: only ONE downstream consumer for this event type
    Reason: SNS fan-out adds cost + complexity with only one subscriber
    EventBridge rule target: SQS queue directly

  SNS → SQS directly (no EventBridge):
    Use when: event source is your application code only (not AWS services)
              no complex routing logic needed
              no need for archive/replay
              high throughput (> 10,000 events/s)
    This is the classic SNS-SQS fan-out pattern from Q7

  EventBridge → Lambda directly (no SQS):
    Use when: event triggers a short-lived, low-volume automation
              (e.g., send a Slack alert when RDS failover occurs)
              not a critical business event (acceptable to lose on Lambda throttle)
```

**Q14. How do you implement idempotent event consumers when using SQS and EventBridge with at-least-once delivery?**
A: SQS Standard queues and EventBridge both provide at-least-once delivery — a message or event may be delivered more than once. Idempotent consumers produce the same result regardless of how many times they process the same message.

**Idempotency implementation patterns:**

```typescript
// Pattern 1: Database-level idempotency key (most robust)
// Store a processed event ID in the database; check before processing

@Injectable()
export class PaymentEventConsumer {
  constructor(
    private readonly db:           DataSource,
    private readonly paymentSvc:   PaymentService,
  ) {}

  async handlePaymentApproved(sqsMessage: SQS.Message): Promise<void> {
    const event     = JSON.parse(sqsMessage.Body!) as PaymentApprovedEvent;
    const eventId   = event.detail?.id ?? sqsMessage.MessageId!;

    await this.db.transaction(async (em) => {
      // Check: has this event been processed?
      const processed = await em.findOne(ProcessedEvent, {
        where: { eventId }
      });

      if (processed) {
        // Already processed → idempotent: skip, delete from SQS, done
        this.logger.log('Duplicate event, skipping', { eventId });
        return;
      }

      // Process the event
      await this.paymentSvc.recordApproval(event.detail, em);

      // Record as processed (within the same transaction)
      await em.save(ProcessedEvent, {
        eventId,
        processedAt: new Date(),
        source:      event.source,
      });
      // Transaction commits: both the business logic and the idempotency record
      // are written atomically. No race condition between check and write.
    });

    // Delete from SQS only after successful transaction commit
    await this.sqs.deleteMessage({
      QueueUrl:      this.queueUrl,
      ReceiptHandle: sqsMessage.ReceiptHandle!,
    }).promise();
  }
}
```

```typescript
// Pattern 2: Redis-based idempotency (for high-throughput, short dedup window)
// Faster than DB check; appropriate when the processing window is known

async handlePaymentApproved(event: PaymentApprovedEvent): Promise<void> {
  const eventId  = event.id;
  const cacheKey = `processed:payment:${eventId}`;
  const TTL      = 86_400; // 24 hours (covers SQS visibility retry window)

  // SET key value NX (only set if not exists) with TTL
  const acquired = await this.redis.set(cacheKey, '1', 'EX', TTL, 'NX');

  if (!acquired) {
    // Key already exists → already processed → skip
    return;
  }

  // Process the event
  try {
    await this.paymentSvc.recordApproval(event);
  } catch (err) {
    // On failure: delete the Redis key so the event can be retried
    await this.redis.del(cacheKey);
    throw err;
  }
}

// Limitation of Pattern 2:
//   If the process crashes AFTER setting the Redis key but BEFORE completing
//   processing, the event is silently skipped on retry (Redis says "processed"
//   but it wasn't). For financial events, use Pattern 1 (DB transaction is atomic).
//   Pattern 2 is appropriate for idempotent notifications (SMS sent twice is annoying;
//   SMS not sent is a problem — Pattern 2 errs toward idempotency over completeness).
```

```typescript
// Pattern 3: Natural idempotency (no extra infrastructure)
// Design the operation itself to be idempotent

// Non-idempotent (dangerous):
await this.db.query(
  'UPDATE loans SET disbursed_amount = disbursed_amount + $1 WHERE id = $2',
  [amount, loanId]
);
// If delivered twice: amount is added twice. Bug.

// Idempotent equivalent:
await this.db.query(`
  INSERT INTO loan_disbursements (loan_id, disbursement_id, amount, created_at)
  VALUES ($1, $2, $3, NOW())
  ON CONFLICT (disbursement_id) DO NOTHING
`, [loanId, disbursementId, amount]);
// ON CONFLICT DO NOTHING: second execution does nothing. Safe.

// Then compute total from the disbursements table (no mutable running total).
```

**Q15. How do you implement the Outbox Pattern to guarantee that database writes and message publishes are atomic?**
A: The dual-write problem: your service writes to PostgreSQL and publishes to SQS/SNS/EventBridge. These are two separate systems — there is no distributed transaction spanning both. If the write succeeds and the publish fails (or vice versa), the systems are inconsistent.

**The problem:**
```
// DANGEROUS: non-atomic dual write
async approveLoan(loanId: string): Promise<void> {
  await this.db.query(
    'UPDATE loans SET status = $1 WHERE id = $2',
    ['approved', loanId]
  );
  // What if this crashes here? DB updated, message not published.
  // Downstream services never know the loan was approved.
  await this.eventBridge.putEvents({
    Entries: [{
      DetailType: 'LoanApproved',
      Detail:     JSON.stringify({ loanId }),
      Source:     'com.fintech.lending',
    }]
  }).promise();
}
```

**The Outbox Pattern:**
```typescript
// Step 1: Write to DB + outbox table in ONE transaction (atomic)
async approveLoan(loanId: string): Promise<void> {
  await this.db.transaction(async (em) => {
    // Business write
    await em.query(
      'UPDATE loans SET status = $1, updated_at = NOW() WHERE id = $2',
      ['approved', loanId]
    );

    // Outbox record (in the same transaction)
    await em.query(`
      INSERT INTO outbox_events
        (id, aggregate_type, aggregate_id, event_type, payload, created_at, published)
      VALUES
        (gen_random_uuid(), 'loan', $1, 'LoanApproved', $2, NOW(), false)
    `, [loanId, JSON.stringify({ loanId, status: 'approved' })]);
    // If the transaction commits: both the loan status and the outbox record are saved.
    // If the transaction rolls back: neither is saved. No inconsistency.
  });
}

// Step 2: Outbox publisher (separate process/cron — polls outbox table)
@Cron('*/5 * * * * *') // every 5 seconds
async publishOutboxEvents(): Promise<void> {
  const events = await this.db.query(`
    SELECT * FROM outbox_events
    WHERE published = false
    ORDER BY created_at ASC
    LIMIT 100
    FOR UPDATE SKIP LOCKED   -- prevents two publisher instances from processing same row
  `);

  for (const event of events) {
    try {
      await this.eventBridge.putEvents({
        Entries: [{
          EventBusName: process.env.EVENT_BUS_NAME,
          Source:       'com.fintech.lending',
          DetailType:   event.event_type,
          Detail:       event.payload,
          Time:         event.created_at,
        }]
      }).promise();

      // Mark as published
      await this.db.query(
        'UPDATE outbox_events SET published = true, published_at = NOW() WHERE id = $1',
        [event.id]
      );
    } catch (err) {
      this.logger.error('Failed to publish outbox event', { eventId: event.id, err });
      // Leave as published=false; will retry on next cron tick
    }
  }
}

// Step 3: Cleanup (archive published events; prevent table growth)
@Cron('0 2 * * *') // daily at 02:00
async archivePublishedEvents(): Promise<void> {
  await this.db.query(`
    DELETE FROM outbox_events
    WHERE published = true
    AND published_at < NOW() - INTERVAL '7 days'
  `);
}
```

**Alternative to cron-based outbox: PostgreSQL logical replication (Debezium):**
```
Debezium captures PostgreSQL WAL (write-ahead log) changes in real-time.
Every INSERT into the outbox table triggers a WAL record.
Debezium reads WAL → publishes to Kafka → Kafka consumer → EventBridge/SQS.

Advantages over cron:
  Near-real-time (milliseconds instead of up to 5 seconds)
  No polling overhead on the database
  Exactly-once with Kafka consumer offsets
  Works even if the outbox publisher service is down (WAL persists)

Infrastructure requirement:
  Debezium connector running (Kafka Connect)
  Kafka cluster (or MSK — managed Kafka on AWS)
  More complex than a cron-based outbox; justified at high event volume
```

## Section 5: Operational Concerns

**Q16. What CloudWatch metrics and alarms should you configure for SQS, SNS, and EventBridge in production?**
A: Observability for messaging infrastructure focuses on queue depth, age of messages, delivery failures, and consumer lag.

**SQS critical metrics:**
```
ApproximateNumberOfMessagesVisible:
  Queue depth: messages waiting to be processed.
  Alert threshold: > expected_max_depth (depends on workload)
  Example: loan-processing-queue depth > 1,000 for 5 minutes → consumer is lagging
  Action: check consumer health; scale consumer instances; check for poison pills

ApproximateAgeOfOldestMessage:
  Age of the oldest unprocessed message in the queue.
  MORE IMPORTANT than queue depth: reveals whether messages are stalling.
  Alert: age > (SLA processing time) → page immediately
  Example: NACH payment events older than 10 minutes → investigation required
  A queue with 10,000 messages all 2 seconds old is fine (processing quickly)
  A queue with 10 messages all 30 minutes old is a problem (stuck consumer)

NumberOfMessagesSent vs NumberOfMessagesDeleted:
  Sent > Deleted over time → queue growing → consumer falling behind
  Deleted > Sent over time → queue draining → consumer catching up

ApproximateNumberOfMessagesVisible on DLQ > 0:
  Any messages in DLQ → immediate alert → investigate
  Do NOT auto-replay DLQ without investigating root cause first

NumberOfMessagesSent (DLQ):
  Rate of DLQ entries → rising rate means consumer failure mode is worsening

// CloudFormation / CDK alarm setup:
new cloudwatch.Alarm(this, 'QueueAgeAlarm', {
  metric: queue.metricApproximateAgeOfOldestMessage({
    period: Duration.minutes(1),
    statistic: 'Maximum',
  }),
  threshold:          600,      // 10 minutes
  evaluationPeriods:  2,
  comparisonOperator: ComparisonOperator.GREATER_THAN_THRESHOLD,
  alarmDescription:   'NACH payment messages stalling in queue',
  actionsEnabled:     true,
}).addAlarmAction(new SnsAction(onCallTopic));
```

**SNS critical metrics:**
```
NumberOfNotificationsFailed:
  Count of failed delivery attempts across all subscriptions.
  Alert: any failures to SQS subscriptions (SQS should always accept)
  Expected zero for SQS subscribers (SQS is always available)

NumberOfNotificationsDelivered:
  Delivery success count. Monitor for sudden drops.
  Drop without corresponding drop in NumberOfMessagesPublished → delivery problem

// Enable SNS delivery status logging for forensics:
aws sns set-topic-attributes \
  --topic-arn arn:aws:sns:...:payment-events \
  --attribute-name SQSSuccessFeedbackRoleArn \
  --attribute-value arn:aws:iam::...:role/SNSFeedbackRole

aws sns set-topic-attributes \
  --topic-arn arn:aws:sns:...:payment-events \
  --attribute-name SQSFailureFeedbackRoleArn \
  --attribute-value arn:aws:iam::...:role/SNSFeedbackRole
```

**EventBridge critical metrics:**
```
FailedInvocations:
  Count of rule targets that EventBridge failed to invoke.
  Zero is the expected value for SQS targets (SQS is always available).
  Non-zero for Lambda targets if Lambda is throttled → serious alert.

ThrottledRules:
  EventBridge throttled your rules due to target throttling (e.g., Lambda throttle).
  Alert: any non-zero value → check downstream target capacity.

MatchedEvents:
  Count of events that matched at least one rule.
  Monitor: sudden drop → events are no longer being published (producer failure)
  Sudden spike → unexpected event volume (debug producer)

IngestionToInvocationStartLatency:
  Time from event ingestion to rule invocation start (P99 should be < 1 second).
  Spike in latency → EventBridge under heavy load or throttling.
```

## Section 6: Scenario / System Design Questions

**Q17. "Design the event-driven messaging architecture for a NACH batch processing system: batch initiates at 09:00 IST, processes 100,000 payment records, notifies merchants on success/failure, and writes to an audit log. The system must handle downstream unavailability gracefully."**
A:

```
Requirements:
  100,000 payment records per batch run
  Multiple downstream consumers: merchant notification, ledger, audit
  Downstream may be unavailable (notification service restarts, etc.)
  Audit log: immutable, retained 7 years
  Processing must be ordered per merchant (all of merchant X's payments in sequence)

Architecture:

Step 1: Batch initiator publishes events (09:00 IST)
  NACH batch service reads 100,000 records from PostgreSQL
  Publishes to EventBridge: fintech-payments bus
  Event: { source: "com.fintech.nach", detail-type: "NachPaymentProcessed" }
  Rate: 100,000 events / 300 seconds = ~333 events/second (within EventBridge limit)

  Outbox pattern:
    NACH batch writes each payment result to PostgreSQL + outbox_events table atomically.
    Outbox publisher reads outbox_events → EventBridge.putEvents (batch of 10).
    EventBridge.putEvents accepts 10 events per API call → 10,000 calls for 100,000 events.

Step 2: EventBridge routing rules

  Rule 1: all NACH payment events → SNS topic (nach-payment-fan-out)
    Pattern: { "source": ["com.fintech.nach"], "detail-type": ["NachPaymentProcessed"] }
    Target: SNS topic

  Rule 2: failed NACH payments → SQS (nach-failure-review-queue)
    Pattern: {
      "source": ["com.fintech.nach"],
      "detail": { "result": ["FAILED", "BOUNCED"] }
    }
    Target: SQS → manual review workflow
    (separate queue for failures; processed by operations team)

  Rule 3: all events → Firehose → S3 (audit archive, 7-year retention)
    Pattern: { "source": ["com.fintech.nach"] }
    Target: Kinesis Data Firehose → S3 (ap-south-1)
    S3 lifecycle: IA after 90 days, Glacier after 1 year, retain 7 years

Step 3: SNS fan-out (nach-payment-fan-out topic)
  Subscriber A: SQS merchant-notification-queue
    Filter: { "detail": { "result": ["SUCCESS", "FAILED"] } }  // all results
    → Notification Worker (sends SMS to borrower, email to merchant)

  Subscriber B: SQS ledger-queue
    Filter: {}  // all NACH events
    → Ledger Worker (records debit/credit entries; reconciliation)

  Subscriber C: SQS analytics-queue
    Filter: {}  // all NACH events
    → Analytics Worker (updates merchant dashboard, repayment rates)

Step 4: SQS queue configurations

  merchant-notification-queue:
    Type: FIFO with MessageGroupId = merchantId
    Reason: notifications for the same merchant in order (batch summary after all payments)
    Visibility timeout: 60s (SMS API is fast)
    DLQ: merchant-notification-dlq, maxReceiveCount: 3
    Alarm: ApproximateAgeOfOldestMessage > 300s

  ledger-queue:
    Type: FIFO with MessageGroupId = merchantId
    Reason: ledger entries must be in order (debit before credit)
    Visibility timeout: 300s (ledger writes may be slow during batch)
    DLQ: ledger-dlq, maxReceiveCount: 5 (more retries; ledger is critical)
    Alarm: ApproximateAgeOfOldestMessage > 600s

  analytics-queue:
    Type: Standard (ordering not critical for analytics)
    Visibility timeout: 120s
    DLQ: analytics-dlq, maxReceiveCount: 3
    Alarm: ApproximateNumberOfMessagesVisible > 50,000 for 10 min

Step 5: Handling downstream unavailability
  Notification service deploys during batch (30s downtime):
    → SQS persists messages during downtime
    → After restart, consumer resumes polling
    → Messages delivered; no loss
    → FIFO ensures merchant's notifications in order

  Ledger service has DB issue (5 minutes):
    → SQS holds messages (visibility timeout keeps them invisible during processing)
    → On error: visibility timeout expires → message redelivered (retry)
    → After 5 retries (if DB still down): DLQ → alert → manual intervention
    → DLQ retention: 14 days (time to fix and replay)

  EventBridge unavailable (rare):
    → Outbox pattern: events in PostgreSQL outbox_events table
    → Outbox publisher retries until EventBridge is available
    → No event loss; delayed delivery only

Throughput math:
  100,000 events → EventBridge: 333/s (within 10,000/s limit)
  SNS: 333 × 3 subscriptions = ~1,000 deliveries/s (within SNS limits)
  SQS receives: 333/s per queue (well within SQS limits)
  Notification consumer: 333 SMS/s → may hit SMS provider rate limit
    → SQS naturally buffers; consumer processes at SMS provider rate (100/s)
    → Queue drains in 1,000 seconds (17 minutes); all notifications sent

EventBridge archive:
  Archive: nach-events-archive, retention: 90 days
  Replay use: if notification bug found after batch, replay last batch
              → notification service re-processes, sends delayed SMS
              → idempotency check: skip if SMS already sent for this payment_id
```

**Q18. "A payment event is published to SNS but the downstream SQS consumer never receives it. Walk through your diagnosis."**
A:

```
Step 1: Verify the SNS publish succeeded
  Check CloudWatch metric: NumberOfMessagesPublished on the SNS topic
  Confirm the publish API call returned success (no exception in application logs)
  If publish failed: check IAM permissions (sns:Publish on the topic ARN)
  Verify the correct topic ARN (typo in topic name → different topic)

Step 2: Check SNS delivery to SQS
  Enable SNS delivery status logging (if not already):
    SQSSuccessFeedbackRoleArn and SQSFailureFeedbackRoleArn on the topic
  CloudWatch Logs group: sns/<region>/<account>/<topic-name>
  Search for the message ID → find the delivery attempt log:
    SUCCESS: { "status": "SUCCESS", "statusCode": 200 }
    FAILURE: { "status": "FAILURE", "statusCode": 403, ... }

  Common failure: 403 SQS Access Denied
    SNS must have permission to send to SQS.
    Check SQS queue access policy:
    {
      "Effect": "Allow",
      "Principal": { "Service": "sns.amazonaws.com" },
      "Action":    "sqs:SendMessage",
      "Resource":  "arn:aws:sqs:...:payment-events-queue",
      "Condition": {
        "ArnEquals": {
          "aws:SourceArn": "arn:aws:sns:...:payment-events"
        }
      }
    }
    If this policy is missing or has the wrong topic ARN → 403 → SNS cannot deliver

Step 3: Check SNS subscription filter policy
  aws sns get-subscription-attributes \
    --subscription-arn arn:aws:sns:...:subscription-id
  Look at FilterPolicy attribute.
  If a filter policy exists and the published message does not have matching
  MessageAttributes: the message is silently dropped by SNS (not an error)

  Common mistake: publishing a message without setting MessageAttributes
  but the subscription has a FilterPolicy expecting those attributes.
  Fix: either add MessageAttributes to the publish call, or remove the FilterPolicy.

  // Publishing with MessageAttributes (required for filter policies):
  await sns.publish({
    TopicArn: topicArn,
    Message:  JSON.stringify(payload),
    MessageAttributes: {
      status: {
        DataType:    'String',
        StringValue: 'approved',
      },
      currency: {
        DataType:    'String',
        StringValue: 'INR',
      },
    },
  }).promise();

Step 4: Check the SQS queue
  aws sqs get-queue-attributes \
    --queue-url https://sqs.../payment-events-queue \
    --attribute-names All
  Check: ApproximateNumberOfMessagesVisible, ApproximateNumberOfMessagesNotVisible
  If messages are NotVisible: consumer received them but hasn't deleted yet
    → check consumer logs for processing status
  If messages are Visible: consumer is not polling
    → check consumer service health (is it running? network issues?)

Step 5: Check SQS queue policy (not just SNS publish permission)
  The SQS queue must allow SNS to SendMessage AND allow your consumer to ReceiveMessage.
  If consumer IAM role lacks sqs:ReceiveMessage, sqs:DeleteMessage: cannot consume.

Step 6: Check for KMS encryption mismatch
  If SQS queue is encrypted with KMS and SNS does not have
  kms:GenerateDataKey + kms:Decrypt on the KMS key:
  SNS publish returns success, but SQS rejects the message silently.
  Fix: grant SNS service principal access to the KMS key.

Step 7: Check dead letter queue
  aws sqs receive-message --queue-url https://sqs.../payment-events-queue-dlq
  If messages are in the DLQ: consumer is receiving but failing to process.
  Examine message body and DLQ message attributes for failure reason.

Systematic prevention:
  Enable SNS delivery status logging on ALL subscriptions (not just when debugging)
  Configure DLQ on every SQS queue in a fan-out architecture
  Add CloudWatch alarm: NumberOfNotificationsFailed on SNS topic > 0
  Test the full flow in staging with an integration test that publishes a test event
  and asserts the SQS consumer received it (end-to-end delivery test)
```

## The Core Mental Model

```
The three services have three distinct jobs:
  SQS:         durable, reliable delivery to ONE consumer at a time
               (point-to-point; persistence; backpressure; retry; DLQ)
  SNS:         fan-out to MANY consumers simultaneously
               (pub/sub; push; no persistence beyond retry window)
  EventBridge: content-based routing and AWS service integration
               (rules; filter; archive; replay; schema registry)

They compose, not compete:
  Producer → EventBridge (routing) → SNS (fan-out) → SQS (consumption)
  Each layer adds what the previous lacks.
  Skip layers when not needed: if only one consumer, EventBridge → SQS directly.

The at-least-once reality:
  SQS Standard and EventBridge deliver at-least-once.
  SQS FIFO delivers exactly-once (within 5-minute dedup window).
  Your consumer MUST be idempotent.
  Idempotency is not optional — it is the consumer's contract with the messaging layer.
  The simplest idempotency: ON CONFLICT DO NOTHING in PostgreSQL.
  The most robust: DB transaction with processed_events table (atomic check + write).

The Outbox Pattern is not optional for financial events:
  Dual-write (DB + message queue) is not atomic.
  Failure between the two writes = inconsistent systems.
  Outbox: write DB + outbox record in one transaction; publish outbox separately.
  This is the only correct pattern for financial event publishing.
  Accept the complexity — the alternative is silent inconsistency.

Queue depth is a lagging indicator; message age is the real signal:
  A queue with 1,000,000 messages at 2 seconds old = consumer is keeping up.
  A queue with 100 messages at 30 minutes old = consumer is stuck.
  Alarm on ApproximateAgeOfOldestMessage, not ApproximateNumberOfMessagesVisible.
  Age tells you whether your SLA is being met; depth tells you the workload.

The DLQ is not the end of the road:
  DLQ = captured, inspectable, replayable failure.
  DLQ = NOT = permanent data loss.
  Always configure DLQ; always alarm on DLQ depth > 0; always investigate before replay.
  The DLQ alarm is the most important alarm in your messaging infrastructure.

FIFO + MessageGroupId correctness:
  MessageGroupId = entityId (loanId, merchantId, paymentId).
  MessageGroupId = constant string → single-threaded consumption → queue never clears.
  Ordering guarantee is per-group, not per-queue.
  Multiple groups = parallel processing with per-group ordering.
  The most common FIFO mistake: using a fixed MessageGroupId in a load-test.
```

**Tip for the interview:** AWS messaging questions at 5 YOE converge on three depth probes: (1) the SNS-SQS fan-out pattern and why SNS → Lambda directly is dangerous for financial events — knowing that SNS retries Lambda only 3 times before dropping the message, and that inserting SQS between SNS and Lambda gives you persistence, configurable retry, and DLQ capture, is the production reliability insight that shows you have designed systems where message loss has business consequences, not just toy demos; (2) the dual-write problem and the Outbox Pattern — explaining that writing to a database and publishing to SQS/SNS/EventBridge is not atomic, that a crash between the two writes causes silent inconsistency, and that the Outbox Pattern resolves this by making the event part of the same database transaction, demonstrates distributed systems design maturity that most candidates at this level gloss over; (3) the idempotent consumer requirement — knowing that at-least-once delivery means your consumer will receive duplicates, that the correct response is an idempotent processing design (ON CONFLICT DO NOTHING, processed_events table, or natural idempotency), and being able to distinguish the failure modes of each idempotency approach (Redis-based idempotency loses the event if the process crashes between setting the key and completing processing; DB transaction-based idempotency is atomic and correct for financial records), shows that you understand the consistency model of the messaging layer you are building on. The fintech callout: for NACH batch processing with 100,000 daily payment events triggering merchant notifications, ledger entries, and analytics — the SNS-SQS fan-out with FIFO queues per downstream service (MessageGroupId = merchantId) ensures each merchant's payment events are processed in order by every consumer independently, while standard queues for analytics handle the throughput without FIFO overhead; the EventBridge archive with 90-day retention is the safety net that lets you replay any batch if a downstream consumer had a bug during processing.
