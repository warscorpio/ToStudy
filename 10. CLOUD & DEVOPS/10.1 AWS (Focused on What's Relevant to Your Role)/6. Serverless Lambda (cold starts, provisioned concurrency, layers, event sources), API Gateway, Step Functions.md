# Serverless: Lambda, API Gateway, Step Functions — Interview Q&A (5 YOE Level)

---

## Section 1: Lambda Fundamentals

**Q1. What is AWS Lambda and what problem does it solve compared to managing EC2 instances?**
A: AWS Lambda is a serverless compute service that executes code in response to events without requiring the provisioning, scaling, or management of servers. You upload a function (a handler file), configure its runtime, memory, and timeout, and AWS handles everything else: the underlying compute, OS patching, scaling from 0 to thousands of concurrent executions, and deallocation when idle.

The problems it solves vs EC2:

**Operational overhead** — EC2 requires AMI management, OS patching, autoscaling configuration, instance right-sizing, capacity planning, and monitoring of the underlying infrastructure. Lambda eliminates all of this — the only thing you manage is your code and its dependencies.

**Idle cost** — an EC2 instance running idle still costs money (24/7 cost). Lambda charges only for the duration code actually runs (measured in 1ms increments) plus the number of requests. A function invoked 1 million times at 100ms each costs ~$0.20 plus $0.20 in request charges — $0.40 total for the month. An equivalent EC2 instance running continuously for the same month costs $8–$50+ depending on instance type.

**Scaling model** — Lambda scales concurrently, not vertically. Each incoming request gets its own execution environment. A sudden spike from 1 to 10,000 concurrent requests is handled automatically (subject to account-level concurrency limits). EC2 autoscaling takes 2–5 minutes to provision a new instance.

**Trade-offs:** Lambda introduces constraints — 15-minute maximum execution timeout, 10GB maximum memory, cold starts, stateless execution environments, no persistent local disk (only `/tmp`, max 10GB), and concurrency limits that must be managed. EC2 is better for: long-running workloads, stateful compute, GPU-intensive tasks, and applications with consistently high, predictable load where the per-request pricing of Lambda exceeds the flat-rate EC2 cost.

**Q2. What is the Lambda execution model — what happens when a function is invoked?**
A: Lambda manages a fleet of execution environments (micro-VMs built on Firecracker). When a function is invoked:

**Cold start path (first invocation or after idle):**
```
1. Lambda service receives invocation request
2. Allocate an execution environment (Firecracker micro-VM)
3. Download the function's deployment package (ZIP or container image)
4. Initialize the runtime (Node.js process, JVM, Python interpreter, etc.)
5. Execute the function's initialization code (module-level code, outside the handler)
6. Execute the handler function
7. Return the result
8. Keep the environment "warm" (frozen) for reuse
```

**Warm invocation (reused environment):**
```
1. Lambda service receives invocation request
2. Thaw an existing, already-initialized environment for this function version
3. Execute the handler function (steps 1–5 are skipped)
4. Return the result
5. Re-freeze the environment
```

The execution environment is reused between invocations of the same function version, providing the warm start optimization. The environment is not shared across concurrent invocations — each concurrent invocation gets its own environment. After a period of inactivity (typically 5–15 minutes, not guaranteed), the environment is reclaimed and the next invocation triggers a cold start.

**Initialization code outside the handler runs once per cold start:**
```javascript
// This code runs ONCE per cold start (initialization phase)
const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DB_URL });
// ↑ Expensive: TCP connection, TLS handshake, auth — do once, reuse across invocations

exports.handler = async (event) => {
  // This code runs on EVERY invocation (handler phase)
  // pool is already initialized and warm — reuse it
  const result = await pool.query('SELECT * FROM orders WHERE id = $1', [event.orderId]);
  return result.rows[0];
};
```

Placing expensive initialization (database connections, SDK clients, large file parsing) outside the handler and in module-level code means it runs once per cold start and is reused across hundreds of warm invocations — a critical performance optimization.

## Section 2: Cold Starts

**Q3. What causes Lambda cold starts and why do they matter?**
A: A cold start is the latency overhead incurred when Lambda must initialize a new execution environment before running your handler. It consists of:

```
Cold start latency breakdown:
  Environment init:    50–200ms    (Firecracker VM allocation)
  Runtime init:        100–500ms   (Node.js/Python/JVM process start)
  Function init:       varies      (your module-level code: DB connections, SDK init)
  Handler execution:   varies      (your actual business logic)

Total cold start:      200ms–10s   (JVM languages have the longest runtime init)
```

Cold starts matter because they add latency to user-facing requests. A web API that normally responds in 50ms may take 500ms on a cold start. For APIs called by users, this is noticeable. For background processing (SQS triggers, Kinesis, S3 events), cold starts are typically acceptable.

**Factors that increase cold start frequency:**
- Low traffic (environments are reclaimed after idle periods).
- High traffic spikes (new environments must be allocated for burst concurrency).
- VPC configuration (adds 1–10+ seconds historically; largely eliminated by hyperplane ENIs since 2019, but VPC cold starts are still slower than non-VPC).
- Large deployment package size (more to download and initialize).
- Memory-hungry runtimes (JVM, .NET) vs lightweight runtimes (Node.js, Python).
- Container image deployment vs ZIP (container images are lazier-loaded but initial pull adds latency).

**Factors that reduce cold start latency:**
- Use Node.js or Python over Java/Kotlin for latency-sensitive functions.
- Minimize deployment package size — fewer dependencies = faster package download.
- Minimize module-level initialization work — load only what's needed.
- Use Lambda SnapStart (Java) — pre-initializes the JVM snapshot before a cold start, reducing Java cold starts from seconds to milliseconds.

**Q4. What is provisioned concurrency and when should you use it?**
A: Provisioned concurrency (PC) pre-initializes a specified number of execution environments so they are always warm and ready to handle invocations immediately. When you configure PC=10, Lambda keeps 10 fully initialized environments running at all times, even with no traffic.

```
Without provisioned concurrency:
  Invocation burst from 0 → 100 concurrent requests:
    First 10 requests: some hit existing warm environments (0ms overhead)
    Next 90 requests: must cold start (200ms–2s overhead each)

With provisioned concurrency = 10:
  First 10 requests: always hit pre-initialized environments (0ms overhead)
  Requests 11–100: still cold start (PC only covers the configured count)

With provisioned concurrency = 100:
  All 100 requests: hit pre-initialized environments ← zero cold starts for burst
```

**When to use provisioned concurrency:**

- **Latency-sensitive user-facing APIs** where cold start latency is noticeable and P99 SLA requirements are strict. A checkout API that must respond in < 300ms P99 cannot tolerate 500ms cold starts.
- **Predictable traffic patterns with known baseline concurrency** — if you know your API handles at least 50 concurrent requests during business hours, provision 50 concurrency for those hours.
- **Java/Kotlin Lambda functions** — cold starts for JVM runtimes can be 2–10 seconds; provisioned concurrency eliminates this entirely.

**When NOT to use provisioned concurrency:**

- Background processing (SQS, Kinesis consumers) — cold start latency is irrelevant when processing queued messages asynchronously.
- Unpredictable or very bursty traffic far above normal levels — PC covers the baseline; above that, cold starts still occur.
- Cost-sensitive scenarios — PC charges for the pre-initialized environments regardless of whether they handle traffic. At $0.000004646/GB-second for PC (vs $0.0000000167 for on-demand), 10 provisioned units of a 1GB function cost ~$3.36/day even at zero traffic.

**Auto Scaling for provisioned concurrency:**
```yaml
# Application Auto Scaling target for provisioned concurrency
# Scales PC between 5 and 50 based on utilization
ScalableTarget:
  MinCapacity: 5
  MaxCapacity: 50
  ScalableDimension: lambda:function:ProvisionedConcurrency

ScalingPolicy:
  TargetTrackingScalingPolicyConfiguration:
    TargetValue: 0.7          # scale out when PC utilization > 70%
    PredefinedMetricType: LambdaProvisionedConcurrencyUtilization
```

This scales PC up when existing provisioned environments are 70% utilized (about to be exhausted) and scales down when utilization drops.

**Q5. What is the Lambda concurrency model and what are reserved vs unreserved concurrency?**
A: Lambda concurrency is the number of function instances executing simultaneously at a given moment. AWS limits concurrency at the account-region level (default: 1,000 concurrent executions across all functions in a region, adjustable to tens of thousands by request).

**Unreserved concurrency** — the pool of concurrency available to functions that have no explicit reservation. Functions compete for this pool; if one function consumes all unreserved concurrency, other functions in the same region throttle.

**Reserved concurrency** — you allocate a specific number of concurrent executions exclusively to one function. The function can never scale beyond this limit (acts as a throttle), and this many executions are always available to it (taken from the account pool):

```typescript
// Set reserved concurrency via AWS SDK
await lambda.putFunctionConcurrency({
  FunctionName: 'payment-processor',
  ReservedConcurrentExecutions: 100,
}).promise();
```

**When to use reserved concurrency:**

- **Throttle a function** — a background image processing function should not consume all account concurrency and starve user-facing APIs. Cap it at 20.
- **Guarantee concurrency for critical functions** — reserve 50 executions for the checkout API so database connection limits are never exceeded (50 Lambda × 1 DB connection each = 50 connections).
- **Protect downstream systems** — a Lambda that calls a third-party API with a rate limit of 100 RPS should be reserved at a concurrency that keeps it within that limit.

Setting reserved concurrency to 0 effectively disables the function (no invocations can execute) — useful for emergency circuit breaking.

## Section 3: Lambda Layers and Deployment

**Q6. What are Lambda layers and what problems do they solve?**
A: A Lambda layer is a ZIP archive containing libraries, dependencies, custom runtimes, or other function dependencies that can be shared across multiple Lambda functions. Layers are attached to functions at deploy time and extracted to `/opt` in the execution environment.

**Problems layers solve:**

**Deployment package size** — Lambda's deployment package size limit is 50MB zipped (250MB unzipped). Large libraries like `aws-sdk`, `sharp` (image processing), or ML inference libraries can easily exceed this. Layers separate dependencies from function code: the function package is tiny (just your code); the layer holds the heavy dependencies and is cached separately.

**Shared dependencies across functions** — a microservice with 30 Lambda functions all using the same internal SDK, logging library, and database client would duplicate those dependencies 30 times without layers. One layer shared by all 30 functions means one place to update a dependency version and one deployment to update it everywhere.

**Custom runtimes** — Lambda supports custom runtimes via layers. If you want to run Ruby, Rust, or a specific version of Node.js not natively supported, publish a runtime layer that implements the Lambda Runtime API.

```
Layer structure:
  layer.zip/
    nodejs/
      node_modules/
        pg/             ← shared postgres client
        lodash/         ← shared utility library
        @company/sdk/   ← internal SDK

Function package (tiny):
  function.zip/
    handler.js          ← just your code; 5KB instead of 50MB
```

```yaml
# Serverless Framework / SAM: attach layers to a function
MyFunction:
  Handler: handler.handler
  Runtime: nodejs20.x
  Layers:
    - arn:aws:lambda:us-east-1:123456789:layer:shared-deps:7
    - arn:aws:lambda:us-east-1:123456789:layer:company-sdk:3
```

**Layer versioning and immutability** — each layer publication creates an immutable version. Functions reference a specific layer version ARN. Updating the layer creates a new version; functions keep using the old version until explicitly updated. This enables safe rollouts of dependency updates.

**Limitations of layers:**
- Maximum 5 layers per function.
- Total unzipped size (function + all layers) must be ≤ 250MB.
- Layers are region-specific (must be published in each region where functions use them).
- Layers do not solve initialization time — all layer contents are extracted on cold start regardless of whether the function uses all of them.

**Q7. What are the Lambda deployment package options and how do you choose between ZIP and container images?**
A:

**ZIP deployment:**
- The traditional approach: ZIP your function code and dependencies; upload to S3; Lambda extracts and executes.
- Size limit: 50MB zipped, 250MB unzipped.
- Fast cold start: Lambda has an optimized loading path for ZIP packages.
- Best for: small to medium functions; when cold start speed is critical; when you don't need Docker-specific build tools.

**Container image deployment:**
- Package your function as a Docker container (up to 10GB); push to ECR; reference in Lambda.
- Size limit: 10GB (vs 250MB for ZIP) — enables large ML models, complex dependencies.
- Uses Lambda Runtime Interface Client (RIC) — a small shim that translates the container's execution into Lambda's invocation model.
- Slightly slower cold starts for initial pulls; subsequent invocations use cached layers.
- Best for: large dependencies (ML models, FFmpeg, browser automation with Chromium); teams already using Docker; functions that share base images with ECS/EKS services.

```dockerfile
# Lambda container image
FROM public.ecr.aws/lambda/nodejs:20

# Copy dependencies and function code
COPY package*.json ./
RUN npm ci --only=production

COPY handler.js ./

# Lambda entrypoint
CMD ["handler.handler"]
```

**Lambda SnapStart (Java only):**
Publishes a snapshot of the initialized execution environment (after the JVM and initialization code have run). Cold starts resume from the snapshot instead of initializing from scratch — reducing Java cold starts from 2–10 seconds to under 1 second. Currently only available for Java 11+ and Managed runtimes (not custom runtimes or containers).

## Section 4: Event Sources

**Q8. What are Lambda event sources and how does the invocation model differ between them?**
A: A Lambda event source is an AWS service or external system that triggers Lambda function invocations. The invocation model — how events are delivered to Lambda — differs critically between event sources:

**Synchronous invocation (caller waits for response):**
The calling service waits for Lambda to return a response. If Lambda throttles or errors, the caller receives the error directly and must handle retry logic.

```
API Gateway → Lambda (synchronous)
  API Gateway sends request; waits for Lambda response; returns response to client
  If Lambda throttles: API Gateway returns 429 to client
  If Lambda errors: API Gateway returns 502 to client
  Retry responsibility: the client
```

**Asynchronous invocation (fire and forget):**
Lambda queues the event internally and returns immediately to the caller. Lambda retries on failure (up to 2 retries by default). Failed events after all retries go to a Dead Letter Queue (SQS or SNS) if configured.

```
S3 event → Lambda (asynchronous)
  S3 sends event notification; Lambda queues it; S3 gets 200 OK immediately
  Lambda retries failed invocations up to 2 times with exponential backoff
  After 3 failures: event sent to DLQ if configured
  Retry responsibility: Lambda (automatically)
```

**Poll-based / stream-based (Lambda polls the source):**
Lambda polls the event source and processes records in batches. Lambda handles retries — it does not advance the stream/queue position until a batch is successfully processed.

```
SQS → Lambda (poll-based)
  Lambda polls SQS; retrieves up to batch_size messages
  Lambda invokes function with the batch
  On success: Lambda deletes the messages from SQS
  On failure: messages become visible again (after visibility timeout); Lambda retries
  Retry responsibility: Lambda + SQS visibility timeout

Kinesis → Lambda (stream-based)
  Lambda polls each shard; retrieves records up to batch_size
  Lambda invokes function with the batch
  On success: Lambda advances the shard iterator (checkpoint)
  On failure: Lambda retries the same batch (blocks the shard until success or max age)
  Retry responsibility: Lambda (blocks shard; careful with poison pills)
```

**Q9. How do you configure an SQS trigger for Lambda and what are the key settings?**
A: SQS is the most common Lambda event source for decoupled async processing. Configuration options that matter in production:

```typescript
// CDK: SQS event source with production settings
import { SqsEventSource } from 'aws-cdk-lib/aws-lambda-event-sources';
import { Queue } from 'aws-cdk-lib/aws-sqs';
import { Duration } from 'aws-cdk-lib';

const processingQueue = new Queue(this, 'ProcessingQueue', {
  visibilityTimeout: Duration.seconds(180),   // must be > Lambda timeout × 6
  receiveMessageWaitTime: Duration.seconds(20), // long polling (reduces API calls)
  deadLetterQueue: {
    queue: new Queue(this, 'DLQ'),
    maxReceiveCount: 3,                        // move to DLQ after 3 failures
  },
});

myLambdaFunction.addEventSource(new SqsEventSource(processingQueue, {
  batchSize: 10,                 // process up to 10 messages per invocation
  maxBatchingWindow: Duration.seconds(5),  // wait up to 5s to fill a batch
  reportBatchItemFailures: true, // partial batch response (retry only failures)
}));
```

**Critical settings:**

**`visibilityTimeout`** must be set to at least 6× the Lambda function timeout. If the Lambda function runs for 30 seconds but the visibility timeout is 30 seconds too, a second Lambda instance picks up the same message before the first finishes — duplicate processing. Rule: `visibility_timeout ≥ 6 × function_timeout`.

**`reportBatchItemFailures`** (partial batch response) — when enabled, the function handler can return a list of failed message IDs, and Lambda only retries those specific messages. Without it, any single failure in a batch of 10 causes all 10 to be retried — even the 9 that succeeded. Implementing partial batch response prevents duplicate processing of successful items:

```typescript
exports.handler = async (event: SQSEvent): Promise<SQSBatchResponse> => {
  const failures: SQSBatchItemFailure[] = [];

  for (const record of event.Records) {
    try {
      await processMessage(JSON.parse(record.body));
    } catch (err) {
      console.error(`Failed to process message ${record.messageId}:`, err);
      failures.push({ itemIdentifier: record.messageId });
    }
  }

  return { batchItemFailures: failures };
  // Only failed messages are retried; successful ones are deleted from SQS
};
```

**`maxBatchingWindow`** — Lambda waits up to this duration to accumulate a full batch before invoking. Without it, Lambda invokes immediately when any message is available, potentially with a batch of 1. A 5-second window can fill a batch of 10, reducing Lambda invocations by 10× and improving throughput.

**Q10. What is the difference between Lambda's handling of SQS vs Kinesis event sources?**
A: The critical difference is in error handling and what happens when processing fails:

**SQS (queue-based):**
- Messages are independent; each has its own visibility timeout and retry counter.
- A failed batch: messages become visible again after the visibility timeout; Lambda retries them independently of other messages.
- A poison pill message (one that always fails) is isolated: after `maxReceiveCount` retries, it goes to the DLQ. Other messages in the queue continue processing.
- Ordering: standard SQS has no ordering guarantee; FIFO SQS preserves per-group order.

**Kinesis (stream-based):**
- Records are ordered within a shard and must be processed in order.
- A failed batch: Lambda retries the SAME batch repeatedly (does not advance past it). The shard is blocked — no new records from that shard are processed until the failed batch succeeds or the records expire.
- A poison pill record (corrupted data that always fails) blocks the entire shard until it ages out of the stream (24 hours to 7 days, depending on retention). This can cause hours of processing delay for all records behind the poison pill.
- Mitigation: use `BisectBatchOnFunctionError: true` — Lambda splits a failing batch in half and retries each half separately, narrowing down the poison pill record. Also set `DestinationConfig.OnFailure` to send failed records to SQS or SNS after maximum retries.

```
Kinesis poison pill scenario:
  Shard 0: [A, B, C (CORRUPT), D, E, F, G, H]

  Without bisect:
    Lambda processes [A, B, C, D, E, F, G, H] → fails on C
    Lambda retries [A, B, C, D, E, F, G, H] → fails on C
    Shard blocked until C expires from stream (up to 7 days!)
    Records D–H never processed during this time

  With BisectBatchOnFunctionError = true:
    Lambda processes [A, B, C, D, E, F, G, H] → fails
    Lambda retries [A, B, C, D] → fails
    Lambda retries [A, B] → succeeds; checkpoint advances
    Lambda retries [C, D] → fails on C
    Lambda retries [C] → fails; sends C to OnFailure destination (SQS)
    Lambda retries [D] → succeeds; checkpoint advances past C
    Lambda continues with [E, F, G, H] → processing resumes
```

## Section 5: API Gateway

**Q11. What is Amazon API Gateway and what are its two main types?**
A: Amazon API Gateway is a fully managed service for creating, publishing, maintaining, monitoring, and securing HTTP APIs. It sits between clients and backend integrations (Lambda, HTTP endpoints, AWS services), handling: request routing, authentication, rate limiting, request/response transformation, caching, and SSL termination.

**REST API (API Gateway v1):**
- Feature-rich: request/response transformation, mapping templates (Velocity Template Language), request validation, usage plans, API keys, resource-based policies.
- Supports: Lambda, HTTP, AWS service integrations, VPC Link.
- Higher latency overhead (~10–15ms).
- More complex configuration; fine-grained control over request/response shapes.
- Best for: complex APIs requiring heavy transformation, usage plans, per-client throttling, or mock integrations.

**HTTP API (API Gateway v2):**
- Simpler, lower latency (~1–3ms), 70% cheaper than REST API.
- Supports: Lambda, HTTP integrations (no direct AWS service integrations).
- Native JWT authorizer (no custom Lambda authorizer needed for standard JWT).
- Automatic CORS configuration.
- No request/response transformation (pass-through only).
- Best for: most new Lambda-backed APIs where transformation is not needed; cost-sensitive APIs; microservices where Lambda handles request shaping.

```
Cost comparison (1 million requests/month):
  REST API:  $3.50/million
  HTTP API:  $1.00/million (71% cheaper)

Latency comparison:
  REST API:  ~15ms added latency
  HTTP API:  ~1–3ms added latency
```

For new deployments, start with HTTP API unless you specifically need REST API features (usage plans, VTL mapping, mock integrations, AWS service proxies).

**Q12. How does API Gateway authenticate requests?**
A: API Gateway supports multiple authentication mechanisms:

**Lambda authorizer (formerly custom authorizer):**
A Lambda function that validates the incoming request's credentials (JWT, API key, custom header) and returns an IAM policy document allowing or denying access. Most flexible; can implement any auth logic:

```typescript
// Lambda authorizer handler
exports.handler = async (event) => {
  const token = event.authorizationToken || event.headers?.authorization;

  try {
    const claims = await verifyJWT(token);

    return {
      principalId: claims.sub,
      policyDocument: {
        Version: '2012-10-17',
        Statement: [{
          Action: 'execute-api:Invoke',
          Effect: 'Allow',
          Resource: event.methodArn,
        }],
      },
      context: {
        userId:   claims.sub,
        tenantId: claims.tenant_id,
        scopes:   claims.scope,
      },
    };
  } catch {
    throw new Error('Unauthorized');  // returns 401
  }
};
```

The returned `context` is passed to the Lambda backend function in `event.requestContext.authorizer`.

**JWT authorizer (HTTP API only):**
Native API Gateway support for JWT validation — no Lambda function needed. Configure the issuer URL and audience; API Gateway validates JWTs automatically:

```yaml
# SAM template JWT authorizer
Auth:
  DefaultAuthorizer: JWTAuthorizer
  Authorizers:
    JWTAuthorizer:
      IdentitySource: $request.header.Authorization
      JwtConfiguration:
        issuer: https://cognito-idp.us-east-1.amazonaws.com/us-east-1_abc123
        audience:
          - my-api-client-id
```

Claims from the JWT are automatically available in `$context.authorizer.claims.sub`, `$context.authorizer.claims.email`, etc.

**IAM authorization:**
Clients sign requests with AWS SigV4. API Gateway validates the signature using the caller's IAM credentials. Best for: service-to-service communication within AWS (ECS → API Gateway → Lambda); never for browser clients (requires AWS credentials).

**API keys:**
Simple string keys passed in the `x-api-key` header. Not authentication (anyone who has the key can call the API) — used for usage tracking and rate limiting per client in REST APIs. Do not use as the sole security mechanism for sensitive APIs.

**Q13. How do you configure API Gateway throttling and rate limiting?**
A: API Gateway throttling operates at two levels:

**Account-level limits (hard):**
- 10,000 requests/second burst limit (account-wide default).
- 5,000 requests/second steady-state default (adjustable by request).
- These are regional limits shared across all APIs in the account.

**Stage-level throttling (configurable):**
```yaml
# Default throttle for the entire stage
StageThrottling:
  ThrottlingBurstLimit: 5000   # max burst (token bucket size)
  ThrottlingRateLimit: 2000    # sustained requests/second

# Per-route throttling (overrides stage-level for specific routes)
RouteThrottling:
  POST /charges:
    ThrottlingBurstLimit: 100
    ThrottlingRateLimit: 50    # limit charge creation to 50 RPS
```

**Usage plans (REST API only):**
Usage plans define per-API-key throttling and quota limits:
```yaml
UsagePlan:
  ApiStages:
    - ApiId: !Ref MyApi
      Stage: prod
  Throttle:
    BurstLimit: 200
    RateLimit: 100    # per API key: 100 RPS
  Quota:
    Limit: 1000000
    Period: MONTH     # 1 million requests per month per key
```

When throttled, API Gateway returns `429 Too Many Requests`. Well-designed clients honor the `Retry-After` header and implement exponential backoff.

**Q14. What is the API Gateway and Lambda proxy integration and what does it pass to the function?**
A: Lambda proxy integration is the standard way to integrate API Gateway with Lambda. With proxy integration, API Gateway passes the entire HTTP request to the Lambda function as a structured event object, and the function returns a complete HTTP response object. API Gateway does not transform the request or response.

```typescript
// Event object Lambda receives from API Gateway (HTTP API format)
interface APIGatewayProxyEventV2 {
  version: '2.0';
  routeKey: string;                       // "POST /charges"
  rawPath: string;                        // "/charges"
  rawQueryString: string;                 // "page=1&limit=20"
  headers: Record<string, string>;        // all HTTP headers
  queryStringParameters?: Record<string, string>;
  pathParameters?: Record<string, string>; // {chargeId: "ch_123"}
  body?: string;                          // request body (always string; parse JSON)
  isBase64Encoded: boolean;
  requestContext: {
    accountId: string;
    apiId: string;
    authorizer?: {
      jwt?: { claims: Record<string, string> };  // JWT claims if JWT authorizer
      lambda?: Record<string, string>;             // context from Lambda authorizer
    };
    http: {
      method: string;
      path: string;
      sourceIp: string;
      userAgent: string;
    };
    requestId: string;                    // unique request ID; use in logs
    routeKey: string;
    time: string;
    timeEpoch: number;
  };
}

// Response object Lambda must return
interface APIGatewayProxyResultV2 {
  statusCode: number;
  headers?: Record<string, string>;
  body?: string;                          // must be a string (JSON.stringify)
  isBase64Encoded?: boolean;
  cookies?: string[];
}

// Handler example
exports.handler = async (event: APIGatewayProxyEventV2): Promise<APIGatewayProxyResultV2> => {
  const userId = event.requestContext.authorizer?.jwt?.claims?.sub;
  const body = event.body ? JSON.parse(event.body) : {};

  // ... business logic

  return {
    statusCode: 201,
    headers: {
      'Content-Type': 'application/json',
      'Location': `/charges/${charge.id}`,
    },
    body: JSON.stringify(charge),
  };
};
```

**Common mistakes with proxy integration:**
- Returning `body` as an object instead of `JSON.stringify(object)` — API Gateway receives the object, which `toString()` to `"[object Object]"`. Always `JSON.stringify` the body.
- Not parsing `event.body` as JSON — the body is always a string.
- Not setting `Content-Type` header — clients receive the response without knowing how to parse it.

## Section 6: Step Functions

**Q15. What is AWS Step Functions and what problem does it solve?**
A: AWS Step Functions is a serverless orchestration service that lets you build multi-step workflows as state machines. It coordinates distributed components (Lambda functions, ECS tasks, SNS, SQS, DynamoDB, HTTP endpoints) into reliable, auditable workflows with built-in error handling, retries, branching, and parallelism — without writing the coordination code yourself.

The problem it solves: complex multi-step processes that would otherwise be implemented as a "saga" pattern in application code — a Lambda that calls another Lambda, checks the result, branches on outcome, retries on failure, and so on. This coordination logic is error-prone, hard to test, and opaque when debugging. Step Functions makes the workflow explicit, visual, and managed.

**When to use Step Functions:**
- Long-running workflows (up to 1 year for Standard Workflows) that exceed Lambda's 15-minute limit.
- Human approval steps (a state waits indefinitely for a callback).
- Complex branching and parallel execution logic.
- Workflows requiring audit trails (every state transition is logged).
- When you need to retry specific steps without restarting the whole workflow.
- Orchestrating calls to multiple services that must be coordinated (order fulfillment: inventory → payment → shipping → notification).

**When NOT to use Step Functions:**
- Simple point-to-point Lambda → SQS → Lambda chains (overkill; SQS alone is better).
- Very high-frequency, short-duration operations where Step Functions' per-state-transition cost adds up ($0.025 per 1,000 state transitions for Standard; $0.00001/1,000 for Express).
- Pure event-driven architectures where EventBridge + SNS + SQS handles the coordination.

**Q16. What are the two types of Step Functions workflows?**
A:

**Standard Workflows:**
- Execution duration: up to 1 year.
- Execution semantics: exactly-once for each state.
- Execution history: full history stored and queryable for 90 days.
- Pricing: $0.025 per 1,000 state transitions (expensive for high-frequency use).
- Use for: long-running, critical workflows (order processing, payment reconciliation, multi-day approval workflows); workflows where you need full audit trail.

**Express Workflows:**
- Execution duration: up to 5 minutes.
- Execution semantics: at-least-once (not exactly-once — states may execute more than once).
- Execution history: not stored by default; must use CloudWatch Logs.
- Pricing: $1.00 per 1,000,000 executions + $0.00001 per GB-second (dramatically cheaper for high-frequency).
- Use for: high-volume, short-lived workflows (IoT event processing, real-time data transformation, streaming pipeline steps); when exactly-once semantics are not required.

```
Cost comparison for 1 million 5-step workflow executions/month:
  Standard:  1,000,000 × 5 steps × $0.025/1000 = $125/month
  Express:   1,000,000 × $1.00/million = $1/month + compute costs
```

**Q17. What is the Amazon States Language (ASL) and what are the key state types?**
A: Amazon States Language (ASL) is a JSON-based language for defining Step Functions state machines. It describes states, transitions, error handling, and parallel execution. Key state types:

**Task state** — invokes a service (Lambda, ECS, DynamoDB, HTTP, etc.):
```json
"ChargePayment": {
  "Type": "Task",
  "Resource": "arn:aws:lambda:us-east-1:123:function:charge-payment",
  "Parameters": {
    "orderId.$": "$.orderId",
    "amount.$": "$.amount"
  },
  "ResultPath": "$.chargeResult",
  "Retry": [{
    "ErrorEquals": ["Lambda.ServiceException", "Lambda.TooManyRequestsException"],
    "IntervalSeconds": 2,
    "MaxAttempts": 3,
    "BackoffRate": 2.0
  }],
  "Catch": [{
    "ErrorEquals": ["PaymentDeclined"],
    "Next": "HandleDecline",
    "ResultPath": "$.error"
  }],
  "Next": "ReserveInventory"
}
```

**Choice state** — conditional branching:
```json
"RouteByOrderType": {
  "Type": "Choice",
  "Choices": [
    {
      "Variable": "$.orderType",
      "StringEquals": "express",
      "Next": "ExpressShipping"
    },
    {
      "Variable": "$.amount",
      "NumericGreaterThan": 1000,
      "Next": "RequireApproval"
    }
  ],
  "Default": "StandardShipping"
}
```

**Parallel state** — execute multiple branches simultaneously:
```json
"NotifyAll": {
  "Type": "Parallel",
  "Branches": [
    {
      "StartAt": "SendEmail",
      "States": {
        "SendEmail": {"Type": "Task", "Resource": "...", "End": true}
      }
    },
    {
      "StartAt": "SendSMS",
      "States": {
        "SendSMS": {"Type": "Task", "Resource": "...", "End": true}
      }
    },
    {
      "StartAt": "UpdateLedger",
      "States": {
        "UpdateLedger": {"Type": "Task", "Resource": "...", "End": true}
      }
    }
  ],
  "Next": "OrderComplete"
}
```

**Wait state** — pause execution for a duration or until a timestamp:
```json
"WaitForSettlement": {
  "Type": "Wait",
  "Seconds": 86400,         // wait 24 hours for bank settlement
  "Next": "CheckSettlement"
}
```

**Map state** — iterate over an array, processing each element:
```json
"ProcessOrderItems": {
  "Type": "Map",
  "ItemsPath": "$.items",
  "MaxConcurrency": 5,        // process up to 5 items in parallel
  "Iterator": {
    "StartAt": "ProcessItem",
    "States": {
      "ProcessItem": {"Type": "Task", "Resource": "...", "End": true}
    }
  },
  "Next": "AggregateResults"
}
```

**Q18. How does Step Functions handle errors and retries?**
A: Error handling is one of Step Functions' strongest features — it is declarative, tested, and does not require application code to implement retry loops.

**Retry configuration on a Task state:**
```json
"Retry": [{
  "ErrorEquals": ["Lambda.ServiceException", "Lambda.AWSLambdaException"],
  "IntervalSeconds": 1,      // initial retry delay
  "MaxAttempts": 3,           // retry up to 3 times
  "BackoffRate": 2.0,         // double the delay each retry: 1s, 2s, 4s
  "JitterStrategy": "FULL"    // add random jitter (recommended to prevent storms)
}]
```

Multiple retry configs can be defined for different error types:
```json
"Retry": [
  {
    "ErrorEquals": ["Lambda.TooManyRequestsException"],
    "IntervalSeconds": 5,
    "MaxAttempts": 5,
    "BackoffRate": 2.0
  },
  {
    "ErrorEquals": ["States.TaskFailed"],
    "IntervalSeconds": 1,
    "MaxAttempts": 2,
    "BackoffRate": 1.5
  }
]
```

**Catch for fallback after retries are exhausted:**
```json
"Catch": [
  {
    "ErrorEquals": ["PaymentDeclined"],
    "ResultPath": "$.paymentError",
    "Next": "NotifyCustomerOfDecline"
  },
  {
    "ErrorEquals": ["States.ALL"],    // catch-all for any error
    "ResultPath": "$.error",
    "Next": "HandleUnexpectedError"
  }
]
```

`ResultPath: "$.paymentError"` merges the error information into the execution state at the specified path, making it available to subsequent states without losing the original input.

**Q19. What is the callback pattern (waitForTaskToken) and when do you use it?**
A: The callback pattern allows a Step Functions workflow to pause indefinitely while waiting for an external system to signal completion — enabling human approval workflows, third-party system callbacks, and long-running asynchronous operations.

```
Standard flow (Step Functions waits for Lambda to return):
  Step Functions → Lambda executes → Lambda returns result → Step Functions continues

Callback pattern (Step Functions waits for external signal):
  Step Functions → Lambda starts async work → sends taskToken to external system
                                              → Lambda returns immediately
  Step Functions WAITS (indefinitely, up to 1 year for Standard)
  External system completes work → calls SendTaskSuccess/SendTaskFailure with taskToken
  → Step Functions continues
```

```json
"WaitForHumanApproval": {
  "Type": "Task",
  "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
  "Parameters": {
    "QueueUrl": "https://sqs.../approval-queue",
    "MessageBody": {
      "taskToken.$": "$$.Task.Token",   // $$.Task.Token is the magic
      "orderId.$": "$.orderId",
      "amount.$": "$.amount",
      "approvalUrl.$": "States.Format('https://approval.example.com/approve?token={}', $$.Task.Token)"
    }
  },
  "HeartbeatSeconds": 3600,   // fail if no heartbeat for 1 hour
  "Next": "ProcessApprovedOrder"
}
```

The approval system receives the `taskToken` via SQS. When the human approves in the UI:

```typescript
// Human approves → UI calls this API → sends signal back to Step Functions
await stepfunctions.sendTaskSuccess({
  taskToken: event.taskToken,
  output: JSON.stringify({ approved: true, approvedBy: 'manager@example.com' }),
}).promise();

// Human rejects:
await stepfunctions.sendTaskFailure({
  taskToken: event.taskToken,
  error: 'ApprovalRejected',
  cause: 'Amount exceeds approval limit for this manager',
}).promise();
```

Step Functions resumes from the `WaitForHumanApproval` state with the output from `SendTaskSuccess` as the state result.

## Section 7: Scenario Questions

**Q20. "Your Lambda function makes 50 API calls to a third-party service. Each call takes 200ms. The function times out at 15 seconds. How do you redesign it?"**
A: 50 calls × 200ms sequential = 10 seconds, close to the 15-second limit with no margin for variance. Three redesign options in order of impact:

**Option 1: Parallelize the API calls (immediate win).**
```typescript
exports.handler = async (event) => {
  const items = event.items;   // 50 items

  // Instead of sequential:
  // for (const item of items) { await callApi(item); }  // 10 seconds

  // Parallel with controlled concurrency (avoid overwhelming the third-party):
  const CONCURRENCY = 10;
  const results = [];

  for (let i = 0; i < items.length; i += CONCURRENCY) {
    const batch = items.slice(i, i + CONCURRENCY);
    const batchResults = await Promise.all(batch.map(item => callApi(item)));
    results.push(...batchResults);
  }
  // 5 batches × 200ms = ~1 second total
  return results;
};
```

**Option 2: Decompose into a fan-out pattern using Step Functions Map state.**
```json
"ProcessAllItems": {
  "Type": "Map",
  "ItemsPath": "$.items",
  "MaxConcurrency": 10,
  "Iterator": {
    "StartAt": "CallThirdParty",
    "States": {
      "CallThirdParty": {
        "Type": "Task",
        "Resource": "arn:aws:lambda:...:function:single-api-call",
        "End": true
      }
    }
  }
}
```
Each Lambda only makes 1 API call; 50 Lambdas run in parallel. No timeout risk.

**Option 3: Queue-based decomposition.**
The main function enqueues 50 SQS messages (one per API call); a worker Lambda processes each message individually. Async; decoupled; retry-friendly. Best when the caller doesn't need all 50 results synchronously.

**Q21. "Your Step Functions workflow processes payment orders but occasionally a Lambda in the middle of the workflow throws an unhandled error. Half the workflow has already completed (inventory reserved, payment charged). How do you design for this?"**
A: This is the saga pattern problem — you need compensating transactions to undo completed steps when a later step fails. Step Functions' Catch mechanism implements this:

```json
{
  "Comment": "Order fulfillment with saga compensation",
  "StartAt": "ReserveInventory",
  "States": {

    "ReserveInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:reserve-inventory",
      "ResultPath": "$.reservationId",
      "Catch": [{
        "ErrorEquals": ["States.ALL"],
        "Next": "OrderFailed",
        "ResultPath": "$.error"
      }],
      "Next": "ChargePayment"
    },

    "ChargePayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:charge-payment",
      "ResultPath": "$.chargeId",
      "Catch": [{
        "ErrorEquals": ["States.ALL"],
        "Next": "CompensateInventory",   // ← compensate if payment fails
        "ResultPath": "$.error"
      }],
      "Next": "CreateShipment"
    },

    "CreateShipment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:create-shipment",
      "Catch": [{
        "ErrorEquals": ["States.ALL"],
        "Next": "CompensatePayment",     // ← compensate if shipment fails
        "ResultPath": "$.error"
      }],
      "Next": "OrderComplete"
    },

    "CompensatePayment": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:refund-payment",
      "Parameters": {"chargeId.$": "$.chargeId"},
      "Next": "CompensateInventory"
    },

    "CompensateInventory": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:release-inventory",
      "Parameters": {"reservationId.$": "$.reservationId"},
      "Next": "OrderFailed"
    },

    "OrderFailed": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:notify-failure",
      "End": true
    },

    "OrderComplete": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:...:function:notify-success",
      "End": true
    }
  }
}
```

The Step Functions state machine is the saga coordinator: each step's `Catch` block routes to the appropriate compensating transactions, which execute in reverse order. The full execution history in the Step Functions console shows exactly which steps ran, which failed, and which compensations executed — invaluable for debugging financial incidents.

## Quick Reference

| Lambda concept | Key detail |
|--- |--- |
| Cold start | Init overhead: environment + runtime + init code; eliminated for configured PC |
| Warm start | Handler-only execution; init code not re-run; reuses connections/clients |
| Provisioned concurrency | Pre-initialized environments; eliminates cold start; charged even at 0 RPS |
| Reserved concurrency | Caps and guarantees concurrency; SG: prevents throttling others; 0 = disable |
| Layers | Shared dependencies in `/opt`; max 5 per function; 250MB total unzipped |
| ZIP vs container | ZIP: faster cold start; 250MB limit. Container: 10GB; Docker tooling |
| SQS trigger | Poll-based; partial batch response; `visibilityTimeout ≥ 6 × timeout` |
| Kinesis trigger | Stream; order preserved per shard; failed batch blocks shard; use `BisectBatch` |
| `PermitWithoutStream` | Not Lambda-specific; gRPC keepalive — skip for Lambda context |

| API Gateway | Key detail |
|--- |--- |
| REST API vs HTTP API | HTTP API: 71% cheaper, 5× lower latency, simpler; REST API: VTL, usage plans |
| Lambda proxy integration | API GW passes raw request; function returns `{statusCode, headers, body}` |
| JWT authorizer | Native HTTP API JWT validation; no Lambda needed; claims in context |
| Lambda authorizer | Custom auth logic; returns IAM policy; result cached by default (TTL: 300s) |
| Throttling | Stage-level and per-route; usage plans per API key; 429 when exceeded |

| Step Functions | Key detail |
|--- |--- |
| Standard vs Express | Standard: exactly-once, 1 year, audit trail. Express: at-least-once, 5 min, cheap |
| Task state | Invokes service; supports `Retry` (backoff) and `Catch` (error routing) |
| Parallel state | Fan-out: all branches execute simultaneously; wait for all to complete |
| Map state | Iterate over array; `MaxConcurrency` controls parallelism |
| waitForTaskToken | Pause workflow indefinitely; external system signals via `SendTaskSuccess` |
| Saga pattern | Compensating transactions in `Catch` blocks; reverse order rollback |

**Tip for the interview:** Serverless questions at 5 YOE level probe whether you understand the operational trade-offs, not just the features. For Lambda: lead with the cold start root cause (Firecracker VM + runtime + init code) and immediately distinguish liveness (provisioned concurrency) vs capability (reserved concurrency) — they have opposite semantics and confusing them is a common mistake. For API Gateway: know that HTTP API is almost always the right choice for new Lambda APIs (cost and latency), and that the proxy integration body must be `JSON.stringify`'d — that bug burns everyone once. For Step Functions: the waitForTaskToken pattern (human approval / external callback) and the saga compensation pattern (compensating transactions in Catch blocks) are the two design patterns that show production depth. If asked about SQS vs Kinesis triggers: the Kinesis poison pill problem (one bad record blocks the shard) and `BisectBatchOnFunctionError` as the mitigation is the specific detail that separates someone who has operated these in production from someone who has only read the docs.
