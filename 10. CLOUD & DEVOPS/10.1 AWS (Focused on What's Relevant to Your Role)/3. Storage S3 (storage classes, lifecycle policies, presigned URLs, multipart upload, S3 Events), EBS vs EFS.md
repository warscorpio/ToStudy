# AWS Storage: S3, EBS, and EFS — Interview Q&A (5 YOE Level)

---

## Section 1: S3 Fundamentals and Storage Classes

**Q1. What is S3's data model and what guarantees does it provide?**
A: S3 (Simple Storage Service) is an object store — not a filesystem, not a block device. Its data model:

- **Object**: the unit of storage. An object is a blob of bytes (the value) plus metadata (key, content-type, user-defined headers, ETag, version ID). Objects are immutable — you cannot append to or partially update an object; you replace the whole thing.
- **Key**: the object's name within a bucket. Keys are strings with no enforced directory structure — `/payments/2024/jan/pay_001.json` is a single flat key that happens to contain slashes. S3 console and most tools render slash-separated keys as a folder hierarchy, but this is a UI convention, not a storage reality.
- **Bucket**: the namespace container. Bucket names are globally unique across all AWS accounts and regions. A bucket lives in one region; objects in it are stored in that region unless explicitly replicated.

**Durability and availability guarantees:**
- **11 nines durability (99.999999999%)**: S3 Standard redundantly stores objects across at least three Availability Zones. Losing all three AZs simultaneously (virtually impossible) is required to lose data.
- **99.99% availability** for S3 Standard: the SLA on being able to read and write objects. Lower storage classes trade availability for cost.
- **Strong read-after-write consistency** (since December 2020): immediately after a successful `PUT`, any subsequent `GET` returns the new object. Immediately after a successful `DELETE`, `GET` returns 404. This applies to new objects and to overwrites of existing objects — no eventual consistency window for any operation.

**What S3 is not:**
S3 is not a filesystem. It has no atomic rename (rename = copy + delete, non-atomic). It has no directory concept (folders are key prefixes). It has no file locking. It has no random-access reads (you read whole objects or byte ranges, not individual records). Attempting to use S3 as a database or filesystem produces correctness problems that are difficult to debug.

**Q2. What are the S3 storage classes and what drives the choice between them?**
A: Storage classes trade cost components against each other: storage price per GB, retrieval price per GB, and minimum storage duration. The right class depends on access frequency and acceptable retrieval latency.

**S3 Standard:**
```
Storage cost:    ~$0.023/GB/month
Retrieval cost:  $0.00/GB (no retrieval fee)
Min duration:    none
Availability:    99.99%
Latency:         milliseconds
Use for:         Actively accessed data — application assets, current payment documents,
                 recently uploaded files, data accessed daily or weekly
```

**S3 Intelligent-Tiering:**
```
Storage cost:    ~$0.023/GB/month (frequent) / ~$0.0125/GB/month (infrequent)
Monitoring fee:  $0.0025 per 1,000 objects (the cost of automatic tiering)
Retrieval cost:  $0.00/GB (no retrieval fee for any tier)
Min duration:    none
Availability:    99.9%
Use for:         Data with unknown or unpredictable access patterns.
                 Automatically moves objects between frequent/infrequent/archive tiers
                 based on access history. If an object is not accessed for 30 days,
                 it moves to the infrequent tier automatically — no configuration required.
                 Pay the monitoring fee only when access patterns are genuinely uncertain.
                 If you know the pattern, use a specific class.
```

**S3 Standard-IA (Infrequent Access):**
```
Storage cost:    ~$0.0125/GB/month (half of Standard)
Retrieval cost:  $0.01/GB
Min duration:    30 days (stored for less = charged for 30 days)
Availability:    99.9%
Latency:         milliseconds
Use for:         Data accessed less than once a month but needs millisecond retrieval.
                 Disaster recovery backups, monthly compliance reports, data retained
                 for audit that is rarely read. The retrieval fee means Standard-IA
                 is more expensive than Standard if accessed frequently — break-even
                 is approximately once per month for typical object sizes.
```

**S3 One Zone-IA:**
```
Storage cost:    ~$0.01/GB/month
Retrieval cost:  $0.01/GB
Min duration:    30 days
Availability:    99.5% (stored in ONE AZ — loss of that AZ = data loss)
Latency:         milliseconds
Use for:         Reproducible infrequent-access data where AZ loss is tolerable.
                 Thumbnail images (re-generatable from originals), processed data
                 that can be recomputed, secondary backups where the primary is
                 in Standard or Glacier. Never for primary copies of important data.
```

**S3 Glacier Instant Retrieval:**
```
Storage cost:    ~$0.004/GB/month
Retrieval cost:  $0.03/GB
Min duration:    90 days
Availability:    99.9%
Latency:         milliseconds (same as Standard — "Glacier" is misleading here)
Use for:         Long-term archive accessed rarely but needing instant retrieval
                 when accessed. Medical records, regulatory archives that must be
                 retrievable on demand but are accessed maybe once per quarter.
```

**S3 Glacier Flexible Retrieval (formerly S3 Glacier):**
```
Storage cost:    ~$0.0036/GB/month
Retrieval cost:  $0.01/GB + retrieval time charges
Min duration:    90 days
Retrieval time:  1–5 minutes (Expedited, expensive), 3–5 hours (Standard), 5–12 hours (Bulk)
Use for:         True long-term cold archive. Annual compliance data, legal hold data,
                 7-year financial records retention. Acceptable retrieval window is hours.
```

**S3 Glacier Deep Archive:**
```
Storage cost:    ~$0.00099/GB/month (~23× cheaper than Standard)
Retrieval cost:  $0.02/GB + time charges
Min duration:    180 days
Retrieval time:  12 hours (Standard), 48 hours (Bulk)
Use for:         Lowest-cost storage for data that must be retained but almost never
                 accessed. 10+ year compliance archives, legal hold data. Retrieval
                 in hours-to-days is acceptable.
```

**The decision rule:**
```
Access frequency:
  Daily/weekly            → Standard
  Unknown pattern         → Intelligent-Tiering
  Monthly, needs ms       → Standard-IA
  Quarterly, needs ms     → Glacier Instant Retrieval
  Yearly, hours OK        → Glacier Flexible Retrieval
  Rarely if ever, days OK → Glacier Deep Archive

Reproducibility:
  Reproducible + infrequent → One Zone-IA (save ~20% over Standard-IA)
  Irreplaceable             → Never One Zone-IA
```

## Section 2: Lifecycle Policies

**Q3. What are S3 lifecycle policies and how do you design one for a financial data retention requirement?**
A: A lifecycle policy is a set of rules that automatically transition objects between storage classes or expire (delete) them based on age, prefix, tags, or object size. It is the mechanism for implementing data retention and cost optimization without manual intervention.

**Policy structure:**
```json
{
  "Rules": [
    {
      "ID":     "PaymentDocumentLifecycle",
      "Status": "Enabled",
      "Filter": {
        "And": {
          "Prefix": "payments/",
          "Tags": [{ "Key": "document_type", "Value": "payment_receipt" }]
        }
      },
      "Transitions": [
        {
          "Days":         30,
          "StorageClass": "STANDARD_IA"
        },
        {
          "Days":         90,
          "StorageClass": "GLACIER_IR"
        },
        {
          "Days":         365,
          "StorageClass": "DEEP_ARCHIVE"
        }
      ],
      "Expiration": {
        "Days": 2557   // 7 years (regulatory retention for financial records)
      }
    }
  ]
}
```

**Designing for a fintech 7-year retention requirement:**
```
Day 0:    Object uploaded to Standard
          (active period: payment processing, reconciliation)

Day 30:   Transition to Standard-IA ($0.023 → $0.0125/GB)
          (payment is settled; documents accessed only for disputes)

Day 90:   Transition to Glacier Instant Retrieval ($0.0125 → $0.004/GB)
          (dispute window closed; accessed only for audits)

Day 365:  Transition to Deep Archive ($0.004 → $0.00099/GB)
          (annual compliance check only; retrieval in days is acceptable)

Day 2557: Expiration (delete) — 7-year retention period ends
          (regulatory minimum met; automatic deletion avoids indefinite storage cost)

Cost profile for 1TB of payment documents at steady state:
  Standard (0–30 days):     $23.00/TB/month
  Standard-IA (30–90 days): $12.50/TB/month
  Glacier IR (90–365 days): $4.00/TB/month
  Deep Archive (1–7 years): $0.99/TB/month
  Blended effective cost:   dramatically less than keeping everything in Standard
```

**Key lifecycle policy constraints:**
- Minimum 30 days in Standard before transitioning to Standard-IA or One Zone-IA (S3 enforces this).
- Minimum 30 days in Standard-IA before transitioning to Glacier classes (S3 enforces this for objects under 128KB — smaller objects are stored as Standard-IA regardless).
- Objects under 128KB are not cost-effective to transition to IA classes — the per-object overhead exceeds the storage savings. Use a filter: `"ObjectSizeGreaterThan": 131072` to exclude small objects from IA transitions.
- Expiration deletes the object permanently. If versioning is enabled, expiration creates a delete marker on the current version — use `"ExpiredObjectDeleteMarker": true` to clean up stale delete markers.
- Lifecycle policies evaluate once per day at midnight UTC — transitions happen the next day after the rule's day count is reached, not at the exact moment.

**Q4. How do lifecycle policies interact with S3 Versioning, and what additional rules are needed?**
A: S3 Versioning keeps every version of every object — a `PUT` to an existing key creates a new version rather than overwriting. This is powerful for accidental deletion protection but creates cost accumulation: old versions continue to be stored and billed indefinitely without explicit cleanup rules.

**Versioning-aware lifecycle rules:**
```json
{
  "Rules": [
    {
      "ID":     "CurrentVersionLifecycle",
      "Status": "Enabled",
      "Filter": { "Prefix": "payments/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 365, "StorageClass": "DEEP_ARCHIVE" }
      ]
    },
    {
      "ID":     "NonCurrentVersionCleanup",
      "Status": "Enabled",
      "Filter": { "Prefix": "payments/" },
      "NoncurrentVersionTransitions": [
        { "NoncurrentDays": 30, "StorageClass": "STANDARD_IA" }
      ],
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": 90  // delete old versions after 90 days
                               // (sufficient for accidental deletion recovery)
      }
    },
    {
      "ID":     "DeleteMarkerCleanup",
      "Status": "Enabled",
      "Filter": { "Prefix": "payments/" },
      "Expiration": {
        "ExpiredObjectDeleteMarker": true  // remove delete markers with no non-current versions
      }
    }
  ]
}
```

Without the `NoncurrentVersionExpiration` rule, every object ever written to a versioned bucket accumulates indefinitely. A bucket that has been in production for 2 years with frequent updates can have 10× the storage of the "visible" objects in non-current versions — a common source of unexpected S3 bills.

## Section 3: Presigned URLs

**Q5. What are presigned URLs, how are they generated, and what security properties do they have?**
A: A presigned URL is a time-limited, credential-embedded URL that grants temporary access to a specific S3 object or operation without requiring the requester to have AWS credentials. The URL contains a cryptographic signature derived from the generating principal's credentials — anyone who has the URL can perform the permitted operation until the URL expires.

**Generation:**
```typescript
// Node.js with AWS SDK v3
import { S3Client, GetObjectCommand, PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

const s3 = new S3Client({ region: 'ap-south-1' });

// Presigned GET URL — allows download of a specific object
async function generateDownloadUrl(key: string): Promise<string> {
  const command = new GetObjectCommand({
    Bucket: 'fintech-payment-documents',
    Key:    key,
    // Optional: force browser to download rather than display
    ResponseContentDisposition: `attachment; filename="${path.basename(key)}"`,
  });

  return getSignedUrl(s3, command, {
    expiresIn: 3600, // URL valid for 1 hour
  });
}

// Presigned PUT URL — allows upload directly to S3 without going through your server
async function generateUploadUrl(key: string, contentType: string): Promise<string> {
  const command = new PutObjectCommand({
    Bucket:      'fintech-payment-documents',
    Key:         key,
    ContentType: contentType,
    // Optional: enforce maximum object size (via conditions, not PutObject itself)
    // For size limits on PUT, use presigned POST with conditions (see Q6)
  });

  return getSignedUrl(s3, command, {
    expiresIn: 900, // upload window: 15 minutes
  });
}
```

**How the signature works:**
The presigned URL contains these query parameters:
```
X-Amz-Algorithm:     AWS4-HMAC-SHA256
X-Amz-Credential:    AKIAIOSFODNN7EXAMPLE/20240115/ap-south-1/s3/aws4_request
X-Amz-Date:          20240115T103000Z
X-Amz-Expires:       3600
X-Amz-SignedHeaders: host
X-Amz-Signature:     <HMAC-SHA256 of canonical request using secret key>
```

S3 recomputes the signature when the URL is used — if the computed signature matches the embedded one, the request is valid. The signature covers the bucket, key, expiry time, and the generating principal's identity. An expired URL fails because the `X-Amz-Expires` value is part of the signed content — changing it invalidates the signature.

**Security properties:**
- **No AWS credentials required from the requester**: the URL is the credential.
- **Operation-scoped**: a GET presigned URL cannot be used for PUT and vice versa.
- **Object-scoped**: a URL for `payments/pay_001.pdf` cannot access `payments/pay_002.pdf`.
- **Time-limited**: expiry is enforced by S3; the URL cannot be extended without re-generating.
- **Not revocable** (without IAM changes): once issued, a presigned URL is valid until expiry unless you rotate the IAM credentials that signed it. If a URL is leaked, rotating the IAM key invalidates all outstanding presigned URLs signed with that key.
- **IAM-principal-bound**: if the IAM user or role that signed the URL loses access to S3 (IAM policy change), existing presigned URLs signed by that principal also stop working — S3 validates the signing principal's current permissions at request time, not at URL generation time.

**The client-side upload pattern (avoiding server as a proxy):**
```
Traditional (server as proxy):
  Client → multipart/form-data POST → Server → Server uploads to S3
  Problems: server memory, bandwidth, upload timeout, server CPU

Presigned URL pattern:
  Client → GET /upload-url?filename=receipt.pdf → Server → presigned PUT URL
  Client → PUT <presigned URL> (directly to S3) → 200 OK
  Client → POST /upload-complete { s3_key: "payments/pay_001/receipt.pdf" }
  Server → validates key exists in S3 → saves reference to DB

Benefits: server handles no file data; S3 handles upload bandwidth;
          client upload speed limited by S3 throughput, not server throughput
```

**Q6. What is a presigned POST and how does it differ from a presigned PUT URL?**
A: A presigned POST is a form-data upload mechanism that allows the server to embed conditions (policy) into the upload authorization — constraining what the client can upload in ways that a presigned PUT URL cannot enforce.

**What presigned PUT cannot do:**
- Enforce maximum file size (the client can upload any size).
- Enforce content-type (the client can set any `Content-Type`).
- Restrict the key pattern (the client can use the exact key signed, no more).

**What presigned POST adds — a policy document:**
```typescript
import { createPresignedPost } from '@aws-sdk/s3-presigned-post';

async function generatePresignedPost(userId: string): Promise<PresignedPost> {
  return createPresignedPost(s3, {
    Bucket:  'fintech-payment-documents',
    Key:     `uploads/${userId}/${Date.now()}-\${filename}`, // key template
    Expires: 900,  // 15 minutes
    Conditions: [
      // Content-type must be PDF or image
      ['starts-with', '$Content-Type', 'application/pdf'],
      // File size: 1KB to 10MB
      ['content-length-range', 1024, 10 * 1024 * 1024],
      // Key must start with this user's prefix (multi-tenant safety)
      ['starts-with', '$key', `uploads/${userId}/`],
    ],
    Fields: {
      'Content-Type': 'application/pdf',
      // Trigger Lambda or notification on upload completion
      'x-amz-meta-uploaded-by': userId,
    },
  });
}

// Returns: { url: "https://bucket.s3.amazonaws.com/", fields: { key, policy, signature, ... } }
```

**Client-side presigned POST usage:**
```javascript
const { url, fields } = await fetch('/api/upload-url').then(r => r.json());

const formData = new FormData();
// All fields from the presigned POST must come BEFORE the file
Object.entries(fields).forEach(([k, v]) => formData.append(k, v));
formData.append('file', selectedFile); // file must be LAST

const response = await fetch(url, { method: 'POST', body: formData });
// 204 No Content: success (S3 returns 204 for presigned POST by default)
// 400 Bad Request: conditions violated (file too large, wrong content-type)
```

**When to use presigned POST over presigned PUT:**
- User-uploaded files where you must enforce size limits (prevent storage abuse).
- Content-type enforcement (prevent uploading malware disguised as a PDF).
- Multi-tenant systems where the key prefix must be scoped to the user — presigned POST policy can enforce `starts-with` on the key, preventing one user from overwriting another's files.
- Form-based upload from HTML `<form>` elements (the native browser form submission model).

## Section 4: Multipart Upload

**Q7. What is multipart upload, when is it required, and how does it work?**
A: Multipart upload splits a large object into discrete parts, uploads each part independently, and then completes the upload by instructing S3 to assemble the parts into the final object. It is the correct mechanism for any object larger than a few hundred megabytes, and is required for objects over 5GB (which cannot be uploaded in a single PUT).

**When to use:**
- Objects > 5GB: single PUT is not allowed by S3.
- Objects > 100MB: multipart upload offers significantly higher throughput (parallel part uploads), better resilience (failed parts can be retried individually without restarting the entire upload), and the ability to pause and resume.
- Streaming data where the final size is unknown: parts can be uploaded as data is generated; the final size is only known when the upload is completed.

**The three-phase protocol:**
```
Phase 1: Initiate — get an upload ID
  POST /<bucket>/<key>?uploads
  Response: <UploadId>xyz123</UploadId>

Phase 2: Upload parts — upload each part with the upload ID
  PUT /<bucket>/<key>?partNumber=1&uploadId=xyz123  (bytes 0–99MB)
  PUT /<bucket>/<key>?partNumber=2&uploadId=xyz123  (bytes 100–199MB)
  PUT /<bucket>/<key>?partNumber=3&uploadId=xyz123  (bytes 200–299MB)
  Response per part: ETag: "abc123" (checksum of the part)

  Parts can be uploaded in parallel — no ordering constraint during upload.
  Parts can be retried individually on failure.
  Minimum part size: 5MB (except the last part, which can be any size).
  Maximum parts: 10,000 (max object size: 10,000 × 5GB = 5TB).

Phase 3: Complete — assemble the parts
  POST /<bucket>/<key>?uploadId=xyz123
  Body: { Parts: [{ PartNumber: 1, ETag: "abc123" }, { PartNumber: 2, ETag: "def456" }, ...] }
  S3 assembles the parts in part number order.
  Response: 200 OK with the final object's ETag and key.
```

**Node.js implementation with the SDK's managed uploader:**
```typescript
import { S3Client } from '@aws-sdk/client-s3';
import { Upload } from '@aws-sdk/lib-storage';
import { createReadStream } from 'fs';

async function uploadLargeFile(
  localPath: string,
  bucket:    string,
  key:       string,
): Promise<string> {
  const fileStream = createReadStream(localPath);

  const upload = new Upload({
    client: s3,
    params: {
      Bucket:      bucket,
      Key:         key,
      Body:        fileStream,
      ContentType: 'application/pdf',
    },
    // Configuration
    partSize:  10 * 1024 * 1024,  // 10MB parts (minimum 5MB)
    queueSize: 4,                  // 4 parallel part uploads
    leavePartsOnError: false,      // abort and clean up on error
  });

  // Progress tracking
  upload.on('httpUploadProgress', (progress) => {
    const pct = Math.round((progress.loaded / progress.total) * 100);
    console.log(`Upload progress: ${pct}%`);
  });

  const result = await upload.done();
  return result.Location; // S3 URL of the completed object
}
```

**Manual implementation (for fine-grained control):**
```typescript
import {
  CreateMultipartUploadCommand,
  UploadPartCommand,
  CompleteMultipartUploadCommand,
  AbortMultipartUploadCommand,
} from '@aws-sdk/client-s3';

async function manualMultipartUpload(bucket: string, key: string, data: Buffer) {
  const PART_SIZE = 10 * 1024 * 1024; // 10MB

  // Phase 1: Initiate
  const { UploadId } = await s3.send(new CreateMultipartUploadCommand({
    Bucket: bucket,
    Key:    key,
  }));

  const parts: { PartNumber: number; ETag: string }[] = [];

  try {
    // Phase 2: Upload parts in parallel
    const uploadPromises = [];
    for (let i = 0; i * PART_SIZE < data.length; i++) {
      const partNumber = i + 1;
      const start      = i * PART_SIZE;
      const end        = Math.min(start + PART_SIZE, data.length);
      const partData   = data.slice(start, end);

      uploadPromises.push(
        s3.send(new UploadPartCommand({
          Bucket:     bucket,
          Key:        key,
          UploadId,
          PartNumber: partNumber,
          Body:       partData,
        })).then(({ ETag }) => ({ PartNumber: partNumber, ETag: ETag! }))
      );
    }

    const completedParts = await Promise.all(uploadPromises);
    parts.push(...completedParts.sort((a, b) => a.PartNumber - b.PartNumber));

    // Phase 3: Complete
    await s3.send(new CompleteMultipartUploadCommand({
      Bucket:          bucket,
      Key:             key,
      UploadId,
      MultipartUpload: { Parts: parts },
    }));

  } catch (err) {
    // Abort to clean up incomplete parts — otherwise billed for dangling parts
    await s3.send(new AbortMultipartUploadCommand({ Bucket: bucket, Key: key, UploadId }));
    throw err;
  }
}
```

**The incomplete multipart upload cost trap:**
Incomplete multipart uploads (parts uploaded but `CompleteMultipartUpload` never called) are stored in S3 and billed at Standard storage rates indefinitely. A server that crashes mid-upload leaves orphaned parts accumulating cost silently.

**The fix — lifecycle rule to abort incomplete uploads:**
```json
{
  "Rules": [{
    "ID":     "AbortIncompleteMultipartUploads",
    "Status": "Enabled",
    "Filter": { "Prefix": "" },
    "AbortIncompleteMultipartUpload": {
      "DaysAfterInitiation": 7
    }
  }]
}
```
This rule instructs S3 to automatically abort any multipart upload that is not completed within 7 days of initiation, deleting the orphaned parts. Every S3 bucket used for multipart uploads should have this rule. Without it, the cost accumulates invisibly — it does not appear in object count metrics, only in storage usage.

## Section 5: S3 Events

**Q8. What are S3 Event Notifications, what events can trigger them, and what are the delivery targets?**
A: S3 Event Notifications push a message to a configured destination whenever specified operations occur on objects in the bucket. They enable event-driven architectures where downstream systems react to S3 changes without polling.

**Triggerable event types:**
```
Object creation:
  s3:ObjectCreated:*           — any creation event
  s3:ObjectCreated:Put         — single-part PUT
  s3:ObjectCreated:Post        — presigned POST upload
  s3:ObjectCreated:Copy        — S3-side copy
  s3:ObjectCreated:CompleteMultipartUpload — multipart upload completed

Object deletion:
  s3:ObjectRemoved:*           — any deletion
  s3:ObjectRemoved:Delete      — permanent delete (versioning disabled)
  s3:ObjectRemoved:DeleteMarkerCreated — delete marker added (versioning enabled)

Object restore (from Glacier):
  s3:ObjectRestore:Post        — restore initiated
  s3:ObjectRestore:Completed   — object available after restore

Replication:
  s3:Replication:*             — replication events

Lifecycle:
  s3:LifecycleTransition       — object transitioned to new storage class
  s3:LifecycleExpiration:*     — object expired or delete marker created by lifecycle
```

**Delivery targets:**
- **SQS**: S3 pushes the event to an SQS queue. Downstream processors poll the queue. At-least-once delivery; durable; decoupled. The recommended target for most use cases.
- **SNS**: S3 pushes to an SNS topic, which fans out to multiple subscribers (SQS queues, Lambda functions, HTTP endpoints, email). Use when one S3 event must trigger multiple downstream processes.
- **Lambda**: S3 invokes a Lambda function directly. Zero infrastructure — but S3-to-Lambda is asynchronous; Lambda is invoked by S3 with no acknowledgment. If Lambda is throttled or fails, S3 retries for up to 24 hours but with no ordering guarantees.
- **EventBridge**: S3 sends events to Amazon EventBridge (CloudWatch Events). More filtering capability; can route to many targets including Step Functions, ECS tasks, and external HTTP endpoints. Higher latency than direct SQS/Lambda.

**Event payload structure:**
```json
{
  "Records": [
    {
      "eventVersion": "2.1",
      "eventSource":  "aws:s3",
      "awsRegion":    "ap-south-1",
      "eventTime":    "2024-01-15T10:30:00.000Z",
      "eventName":    "ObjectCreated:CompleteMultipartUpload",
      "s3": {
        "bucket": {
          "name": "fintech-payment-documents",
          "arn":  "arn:aws:s3:::fintech-payment-documents"
        },
        "object": {
          "key":       "uploads/usr_42/2024/pay_001_receipt.pdf",
          "size":      2048576,
          "eTag":      "d8e8fca2dc0f896fd7cb4cb0031ba249",
          "versionId": "abc123"
        }
      }
    }
  ]
}
```

Note: `Records` is an array — S3 may batch multiple events in one notification (particularly at high PUT rates). Always iterate `Records`, never assume exactly one event per notification.

**Q9. How do you build an event-driven document processing pipeline using S3 Events?**
A:

```
Architecture: merchant uploads payment receipt → OCR processing → data extraction

Step 1: Merchant uploads receipt
  Client → presigned PUT URL → S3 bucket: fintech-receipts
  Object key: uploads/{merchantId}/{timestamp}_{filename}

Step 2: S3 Event triggers processing
  S3:ObjectCreated:CompleteMultipartUpload (or Put)
    → SQS queue: receipt-processing-queue
    (SQS decouples upload rate from processing rate;
     multiple processor instances consume from the queue;
     DLQ handles poison messages after 3 delivery attempts)

Step 3: Lambda/ECS processor consumes from SQS
  - Downloads object from S3 (using SDK, not presigned URL — processor has IAM role)
  - Sends to OCR service (AWS Textract or third-party)
  - Extracts: vendor name, amount, date, line items
  - Validates extracted data against payment record in DB
  - Writes extraction result to DB
  - Moves processed object to processed/ prefix (or tags it)
  - Deletes SQS message on success

Step 4: Notification on completion
  - Processor publishes to SNS topic: receipt-processed
  - SNS delivers to: merchant dashboard (via API polling or WebSocket push)

NestJS SQS consumer implementation:
  @Injectable()
  export class ReceiptProcessorService {
    @SqsMessageHandler('receipt-processing-queue')
    async handleReceiptEvent(message: SQSMessage): Promise<void> {
      const body    = JSON.parse(message.Body);
      const records = JSON.parse(body.Message ?? body).Records; // SNS wraps SQS

      for (const record of records) {
        const bucket = record.s3.bucket.name;
        const key    = decodeURIComponent(record.s3.object.key.replace(/\+/g, ' '));
        // Note: S3 event keys are URL-encoded; must decode before use

        await this.processReceipt(bucket, key);
      }
    }
  }
```

**The key URL-encoding gotcha:**
S3 event notification object keys are URL-encoded — spaces become `+` (not `%20`), and special characters are percent-encoded. If your key is `uploads/usr 42/receipt.pdf`, the event delivers `uploads/usr+42/receipt.pdf`. Always decode: `decodeURIComponent(key.replace(/\+/g, ' '))`.

**S3 Events vs. S3 EventBridge:**
S3's native event notifications (SQS/SNS/Lambda) have limited filtering — you can filter by prefix and suffix, but not by object size, metadata, or complex conditions. S3 → EventBridge enables richer filtering and routing:
```json
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": { "name": ["fintech-receipts"] },
    "object": { "key": [{ "prefix": "uploads/" }] },
    "reason": ["CompleteMultipartUpload"]
  }
}
```
EventBridge is approximately 1–2 seconds higher latency than direct S3 → SQS, but the routing flexibility (one event → multiple targets, complex filtering) often justifies it.

## Section 6: EBS vs EFS

**Q10. What is EBS and what are its characteristics, types, and appropriate use cases?**
A: EBS (Elastic Block Store) is a network-attached block storage device — the AWS equivalent of a physical hard drive, but delivered over the network. It appears to the OS as a raw block device, is formatted with a filesystem (ext4, xfs, NTFS), and is mounted as a volume.

**Key characteristics:**
- **Single-instance attachment** (by default): one EBS volume is attached to one EC2 instance at a time. `io1`/`io2` volumes support Multi-Attach (attaching to up to 16 instances in the same AZ simultaneously) for shared block storage, but this requires applications to manage concurrent access themselves — EBS provides no filesystem-level coordination.
- **AZ-scoped**: an EBS volume exists in one AZ. Moving it to another AZ requires creating a snapshot (stored in S3) and restoring it in the target AZ.
- **Persistent**: data survives EC2 instance stop/start and termination (if `DeleteOnTermination=false`). Root volumes default to `DeleteOnTermination=true`.
- **High performance**: EBS delivers low-latency block I/O measured in microseconds to low milliseconds.

**EBS volume types:**

```
gp3 (General Purpose SSD — current generation):
  Baseline:    3,000 IOPS, 125 MB/s throughput (included in price)
  Configurable: up to 16,000 IOPS, 1,000 MB/s (paid separately from storage)
  Latency:     single-digit milliseconds
  Price:       $0.08/GB/month + optional IOPS/throughput
  Use for:     Default choice for most workloads: boot volumes, application servers,
               databases (moderate IOPS), development environments

gp2 (General Purpose SSD — previous generation):
  IOPS:        3 IOPS/GB, burstable to 3,000; max 16,000 IOPS at 5,334 GB
  Throughput:  128–250 MB/s
  Price:       $0.10/GB/month (IOPS linked to size — less flexible than gp3)
  Use for:     Legacy; prefer gp3 for all new volumes

io2 Block Express (Provisioned IOPS SSD — high performance):
  IOPS:        up to 256,000 IOPS per volume
  Throughput:  up to 4,000 MB/s
  Latency:     sub-millisecond
  Durability:  99.999% (5 nines) vs 99.8–99.9% for gp3
  Price:       $0.125/GB/month + $0.065 per provisioned IOPS
  Use for:     High-performance databases (Oracle, SQL Server, MySQL, PostgreSQL)
               requiring consistent low-latency I/O. Critical transactional systems
               where gp3's burst model is insufficient.

st1 (Throughput Optimized HDD):
  Throughput:  up to 500 MB/s sustained
  IOPS:        up to 500 IOPS
  Latency:     milliseconds (HDD)
  Price:       $0.045/GB/month
  Use for:     Sequential-access workloads: log processing, data warehousing,
               big data (Hadoop, Kafka log segments on brokers).
               NOT for random I/O — HDD seek time makes random access slow.

sc1 (Cold HDD):
  Throughput:  up to 250 MB/s (burst); 12 MB/s baseline
  Price:       $0.015/GB/month (cheapest EBS option)
  Use for:     Infrequently accessed sequential data. Cold data storage where
               the cost savings justify the lower throughput.
```

**EBS snapshots:**
EBS volumes are backed up as snapshots stored in S3 (incremental — only changed blocks since the last snapshot are stored). Snapshots are the mechanism for:
- Backup and point-in-time recovery.
- Copying volumes to another AZ or region (snapshot → restore in new AZ/region).
- Creating AMIs (Amazon Machine Images) from running instances.
- EBS Fast Snapshot Restore (FSR): pre-warms snapshots so restored volumes have full performance immediately (without FSR, a newly restored volume performs slowly until all blocks are read from S3).

**Q11. What is EFS and how does it differ from EBS?**
A: EFS (Elastic File System) is a fully managed NFS (Network File System) — a shared filesystem that multiple EC2 instances and containers can mount and access simultaneously as if it were a local directory.

**Key characteristics:**
- **Multi-instance, multi-AZ access**: EFS is regional — it is accessible from any EC2 instance, ECS task, Lambda function, or EKS pod in the same VPC across all AZs simultaneously. Thousands of instances can mount the same EFS filesystem at the same time.
- **POSIX-compliant filesystem**: supports standard file operations (read, write, append, rename, hard links, directory traversal), file locking, and ownership/permissions. Applications that use a filesystem API transparently benefit from shared access.
- **Elastic capacity**: EFS grows and shrinks automatically — no provisioning of capacity upfront. Storage scales to petabytes; you pay for what you use.
- **Higher latency than EBS**: EFS uses NFS over the network, adding latency compared to a locally attached EBS volume. EFS latency is single-digit milliseconds (vs. sub-millisecond for io2). For latency-sensitive workloads (transactional databases), EFS is not appropriate.

**EFS performance modes and throughput modes:**

```
Performance Modes:
  General Purpose (default):
    Lower latency; max 35,000 read IOPS, 7,000 write IOPS per filesystem
    Use for: web serving, CMS, application shared storage, home directories

  Max I/O:
    Higher aggregate throughput; higher latency (trade-off)
    Use for: big data analytics, media processing with many parallel instances
    (generally prefer Elastic Throughput mode over Max I/O for new filesystems)

Throughput Modes:
  Elastic (recommended for variable workloads):
    Throughput scales automatically with workload
    No provisioning; pay per GB transferred
    Use for: unpredictable access patterns

  Provisioned:
    Set a fixed throughput level regardless of storage size
    Use for: workloads that need higher throughput than Elastic provides
    at their current storage size

  Bursting (legacy):
    Baseline throughput: 50 KB/s per GB stored; burst to 100 MB/s
    Use for: smaller filesystems with bursty access
```

**EFS storage classes:**
```
EFS Standard:        multi-AZ redundancy; always-available; ~$0.30/GB/month
EFS Standard-IA:     infrequent access tier; same redundancy; ~$0.025/GB/month
                     + $0.01/GB retrieval fee
EFS One Zone:        single-AZ; lower cost; data loss if AZ fails; ~$0.16/GB/month
EFS One Zone-IA:     single-AZ + IA; ~$0.01/GB/month + retrieval fee

EFS Lifecycle Management automatically moves files not accessed for 7/14/30/60/90 days
to the IA tier — similar to S3 Intelligent-Tiering but for filesystem files.
```

**Q12. How do you choose between S3, EBS, and EFS for a given use case?**
A: The choice follows from the access pattern, performance requirements, and sharing requirements:

```
Decision framework:

Is the data accessed as objects (whole files, no partial updates, no POSIX)?
  → S3
  Why: cheapest per GB; massively scalable; no servers; lifecycle management;
       CDN integration; event notifications; presigned URLs for direct client access

Is the data a database, OS volume, or application requiring block-level I/O?
  → EBS
  Why: low latency block I/O; single instance; formatted as filesystem;
       highest performance for random I/O (IOPS-intensive workloads)

Is the data a shared filesystem accessed by multiple instances simultaneously?
  → EFS
  Why: POSIX compliance; multi-instance concurrent access; automatic scaling;
       NFS mount semantics; cross-AZ availability

Concrete use cases:

  PostgreSQL database data directory:
    → EBS (gp3 or io2)
    Why: single instance, block I/O, random access, low latency critical
    Not EFS: NFS latency is too high for transactional database I/O
    Not S3: not a filesystem; cannot mount as a block device

  Payment receipt PDFs (merchant uploads):
    → S3
    Why: objects, not files; presigned URLs for direct upload/download;
         lifecycle to Glacier; no EC2 required; CDN-friendly
    Not EBS: requires EC2; single instance
    Not EFS: overpowered and expensive for object storage

  Application config files shared across 20 ECS tasks:
    → EFS
    Why: multiple containers need simultaneous read access; POSIX mount;
         files may be updated by one container and read by others
    Not EBS: cannot be mounted by multiple instances in different AZs
    Not S3: containers expect filesystem API, not S3 API; no instant consistency
             for config files that change frequently

  Kafka broker log segments:
    → EBS (st1 — throughput-optimized HDD)
    Why: Kafka writes sequentially; throughput matters more than IOPS;
         single broker owns its log directory; st1 is cost-effective for sequential I/O
    Not S3: Kafka requires block storage; tiered storage to S3 is a separate feature
    Not EFS: NFS latency and locking semantics conflict with Kafka's I/O model

  Shared ML model weights across training nodes:
    → EFS (or S3 with local caching)
    Why: model files read by multiple training instances simultaneously;
         read-heavy access pattern (weights loaded, not frequently written)
    EFS advantage over S3: file semantics; no need to download the whole object;
    S3 advantage: cheaper if models are large and read infrequently

  Docker container images (ECR):
    → S3 (managed by ECR, transparent to user)
    (ECR stores images in S3 under the hood; this is just for context)

  Jenkins build artifacts (shared between build and deploy agents):
    → EFS
    Why: build agent writes artifact; deploy agent reads it;
         both run on different EC2 instances; filesystem semantics
    Alternative: S3 + explicit upload/download steps (more explicit, less magic)
```

**Cost comparison at 1TB:**
```
S3 Standard:    $23/month
S3 Standard-IA: $12.50/month + retrieval
EBS gp3:        $80/month (+ EC2 instance to attach to)
EBS io2:        $125/month + IOPS charges (+ EC2)
EFS Standard:   $300/month (most expensive per GB; pay for shared access and elasticity)
EFS Standard-IA: $25/month (with lifecycle; ~standard cost for cold data)
```

EFS is 13× more expensive than S3 Standard for the same storage. The price premium pays for: POSIX filesystem semantics, concurrent multi-instance access, and no need for application-level object storage API integration. Pay that premium only when those features are genuinely required.


**Q14. "A merchant reports that a presigned URL for downloading their payment receipt expired before they could use it. They want longer-lived URLs. How do you handle this without a security compromise?"**
A:

```
The request: extend presigned URL TTL from 1 hour to "a few days"

Why this is a security concern:
  A presigned URL is effectively a bearer token — anyone who has it can access the object.
  A 72-hour URL sent by email can be:
    - Forwarded to unauthorized parties intentionally or accidentally
    - Captured in email server logs, proxy logs, or browser history
    - Compromised if the merchant's email account is breached
  PCI-DSS and most fintech compliance frameworks require time-limiting access to
  financial documents. A multi-day URL is a compliance risk.

Analysis of the root cause:
  Why did the URL expire before use?
    Option A: URL generated and immediately put in an email;
              merchant opens email days later → legitimate use case
    Option B: Merchant generates URL in the dashboard,
              doesn't use it immediately → UX friction issue
    Option C: Merchant shares URL with their accountant via a messaging app
              → the real need is delegated access, not a longer URL

Solutions that don't compromise security:

Solution 1 — On-demand URL generation (preferred):
  Don't send the URL in the email.
  Send a link to your application: "Click to download receipt"
  When merchant clicks, your server generates a fresh 15-minute presigned URL
  and redirects them to it.
  TTL: 15 minutes (short; sufficient for the user to click download)
  The URL is fresh on every access; the application controls who can generate it.

  Implementation:
    GET /receipts/{payment_id}/download
    → JwtAuthGuard validates token
    → Verify merchant owns this payment_id
    → Generate presigned GET URL (TTL: 15 minutes)
    → 302 Redirect to the presigned URL
    Merchant never sees the presigned URL; they click a link in your app.

Solution 2 — Longer TTL with access audit logging:
  If the merchant genuinely needs to share access with their accountant:
    Generate URL with 7-day TTL
    Log the generation: who generated it, when, for which document
    Record in your audit trail (required for PCI-DSS)
    Invalidate it via CloudFront signed URL/cookie if suspicious activity detected
  Only for scenarios where the compliance audit trail requirement is met.

Solution 3 — CloudFront Signed URLs for better control:
  Put S3 behind CloudFront.
  Issue CloudFront signed URLs (not S3 presigned URLs).
  CloudFront signed URLs can be invalidated before expiry
  by invalidating the CloudFront distribution cache — unlike S3 presigned URLs,
  which cannot be revoked without rotating the IAM credentials that signed them.

  Benefits over S3 presigned URLs:
    Revocable: CloudFront invalidation stops URL from working mid-TTL
    IP restriction: CloudFront policy can restrict URL to a specific IP range
    Geo-restriction: can block access from certain countries at CDN level
    No S3 requests: CloudFront serves from edge cache; S3 not hit on every download

  Implementation (NestJS):
    import { getSignedUrl } from '@aws-sdk/cloudfront-signer';

    const signedUrl = getSignedUrl({
      url:        `https://d123.cloudfront.net/${key}`,
      keyPairId:  process.env.CLOUDFRONT_KEY_PAIR_ID,
      privateKey: process.env.CLOUDFRONT_PRIVATE_KEY,
      dateLessThan: new Date(Date.now() + 24 * 60 * 60 * 1000).toISOString(),
    });

Recommendation: Solution 1 (on-demand generation via application redirect)
  for all standard merchant access.
  Solution 3 (CloudFront signed URLs) if CDN is already in the architecture
  and revocability is required.
  Never: increase S3 presigned URL TTL to days for financial documents.
```

**Q15. "Your application stores user-generated content (profile images, uploaded documents) on EBS volumes attached to your application servers. You are scaling from 2 to 20 EC2 instances. What breaks and how do you fix it?"**
A:

```
What breaks:
  EBS volumes are attached to one EC2 instance at a time.
  Files uploaded to Instance 1's EBS volume are not visible to Instance 2–20.
  Users hitting Instance 1 see their files; users hitting Instances 2–20 do not.

  Symptoms:
    - Profile images appear for some users, broken for others (depending on which
      instance serves the request)
    - Documents uploaded successfully (200 OK) are not found on next request (404)
      if next request routes to a different instance
    - Sticky sessions mask the problem until an instance restarts or scales in

The architectural problem:
  Local disk is not shared state. Any content that must be accessible from
  multiple instances must live outside of individual instance volumes.

Migration strategy:

Phase 1: Stop writing to EBS, start writing to S3
  Modify application: replace fs.writeFile() with S3 PutObject
  Replace fs.readFile() with presigned URL redirect or S3 GetObject proxy
  Dual-write during transition: write to both EBS and S3 simultaneously
  (ensures content accessible from both old and new instances)

Phase 2: Migrate existing EBS content to S3
  One-time migration script:
    aws s3 sync /mnt/uploads s3://app-user-content/uploads/ --storage-class STANDARD
  Verify: spot-check that files are accessible from S3 after migration
  Set a cutover date: after this date, reads come from S3 only

Phase 3: Update application to read from S3
  Profile images: presigned GET URL (1 hour TTL) or CloudFront URL
    (CloudFront for public profile images — no auth needed; CDN caching reduces S3 requests)
  Private documents: presigned URL (15 min) via application redirect

Phase 4: Remove EBS dependency
  After migration is verified stable (1–2 weeks):
    Stop dual-writing to EBS
    Shrink EBS volumes or use smaller instance types (no large /data volumes)
    EBS retained only for OS and application code (where it belongs)

Final architecture:
  EC2 instances: stateless — no user data stored locally
    Receive upload → validate → PutObject to S3 → return S3 key to DB
    Serve download → validate auth → generate presigned URL → redirect to S3
  S3: all user content, elastically scalable, independently durable
  EBS: OS volumes only (gp3, 20–30GB per instance)
  Load balancer: round-robin (sticky sessions no longer needed)
  Result: 2 → 200 instances without any storage coordination problem

Why not EFS instead of S3:
  EFS works and is a valid solution (mount same filesystem across all instances).
  But for user-generated content (images, documents):
    S3 is cheaper (~$0.023/GB vs EFS Standard ~$0.30/GB — 13× cheaper)
    S3 has lifecycle management, presigned URLs, CDN integration natively
    S3 scales to any size without performance degradation
    EFS is appropriate when the application requires POSIX semantics
    (renaming, hard links, appending, directory traversal) — file hosting does not.
  EFS is the right answer for shared application config, ML model weights,
  or legacy applications that use filesystem APIs you cannot change.
```

## The Core Mental Model

```
S3 = object store (HTTP API, globally accessible, cheapest per GB)
EBS = network block device (one instance, lowest latency, highest IOPS)
EFS = managed NFS (many instances, POSIX filesystem, most expensive)

The access pattern test:
  "Do I need to PUT/GET whole files via HTTP?" → S3
  "Do I need block I/O for a database or OS?" → EBS
  "Do multiple servers need to read/write the same directory?" → EFS

S3 cost optimization in order of impact:
  1. Lifecycle policies: move objects to IA/Glacier as they age
     (most impactful — old data is the majority of storage cost)
  2. Storage class selection: Intelligent-Tiering for unknown patterns
  3. Abort incomplete multipart uploads (lifecycle rule, silent cost)
  4. Non-current version cleanup (lifecycle rule for versioned buckets)

S3 upload patterns:
  Small files (<100MB): single PUT
  Large files (>100MB): multipart upload (managed via SDK Upload class)
  Client → S3 directly: presigned PUT URL or presigned POST
  Presigned PUT: simple, no size enforcement
  Presigned POST: policy-enforced (size limit, content-type, key prefix)

S3 events → event-driven processing:
  S3 Event → SQS (durable, decoupled) → processor (Lambda/ECS)
  Always handle Records as array (batched events possible)
  Always URL-decode object keys from event notifications
  Always add AbortIncompleteMultipartUpload lifecycle rule

Presigned URL security model:
  URL = bearer credential; anyone with it can access the object
  Revocation: impossible without rotating signing IAM key
  Alternative: CloudFront signed URLs (revocable via invalidation)
  For sensitive data: application-mediated redirect (generate URL per-request)
  Never: long-TTL presigned URLs for PII or financial documents in emails

EBS operational rules:
  Always use gp3 (not gp2) for new volumes — cheaper and more flexible
  Use io2 only when you need >16,000 IOPS or 5-nines durability
  Use st1 for Kafka log segments, log archives, sequential workloads
  Snapshot regularly; enable EBS Fast Snapshot Restore for critical volumes
  EBS volume in AZ-A cannot be attached to instance in AZ-B (snapshot → restore to move)

EFS vs S3 for shared storage:
  EFS: when you need POSIX (rename, append, directory, file locking)
  S3: when files are whole-object access (upload once, download whole)
  EFS is 13× more expensive than S3 Standard — justify the premium with POSIX requirement
  For user file hosting, CDN assets, document storage → S3 is almost always correct
```
