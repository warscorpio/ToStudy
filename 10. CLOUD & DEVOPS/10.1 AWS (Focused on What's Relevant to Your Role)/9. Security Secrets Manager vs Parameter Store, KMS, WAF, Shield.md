## Section 1: Secrets Manager

**Q1. What is AWS Secrets Manager and what problems does it solve compared to environment variables?**
A: AWS Secrets Manager is a managed service for storing, rotating, and auditing sensitive credentials — database passwords, API keys, OAuth tokens, and TLS certificates. It solves the secret distribution and rotation problems that environment variables cannot address.

**The environment variable problem:**

```
Environment variable approach (common but flawed):
  DB_PASSWORD=supersecret123 stored in:
    .env files → checked into git by accident → credential leak
    Docker image ENV → baked into layer → visible in image history
    EC2 UserData → stored in instance metadata → readable by anyone with IMDSv1
    CI/CD pipeline variables → visible in build logs on misconfiguration
    Kubernetes ConfigMap → not encrypted at rest by default

  Rotation problem:
    Password must rotate every 90 days (PCI-DSS, SOC2 requirement)
    Rotation requires: generating new password → updating DB → updating all
    application instances → restarting services
    Manual rotation: someone forgets → audit finding → compliance failure
    Automated rotation with env vars: requires coordinated deployment of every
    service that uses the credential → complex, error-prone, causes downtime

Secrets Manager approach:
  Secret stored encrypted in AWS (KMS-backed)
  Application fetches the secret at runtime via API call (never in env var)
  Rotation: Secrets Manager rotates automatically on a schedule
            RDS integration: Secrets Manager rotates the DB password AND
            updates the RDS instance simultaneously → zero downtime rotation
  No secret ever touches disk, .env files, git, or build logs
  Every secret access logged in CloudTrail (who accessed what, when, from where)
```

**What Secrets Manager manages:**
```
Secret types:
  RDS database credentials (native integration with PostgreSQL, MySQL, Aurora)
  Redshift credentials
  DocumentDB credentials
  Generic credentials (API keys, OAuth tokens, custom structured JSON)
  Key/value pairs (structured JSON up to 65 KB per secret value)

Secret versioning:
  Every rotation creates a new version
  Versions are labeled: AWSCURRENT (active), AWSPENDING (during rotation), AWSPREVIOUS (last)
  Applications requesting the secret get AWSCURRENT
  During rotation: AWSPENDING is tested before becoming AWSCURRENT
  AWSPREVIOUS retained for rollback if the new password fails

Secret ARN format:
  arn:aws:secretsmanager:ap-south-1:123456789012:secret:prod/nestjs-api/db-credentials-AbCdEf
  The 6-char suffix (AbCdEf) is random — added to enable multiple secrets with the same name
  across accounts. Use the full ARN in IAM policies, not just the name.
```

**Q2. How does automatic secret rotation work in Secrets Manager, and what is the Lambda rotation function?**
A: Automatic rotation uses a Lambda function that Secrets Manager invokes on a schedule. The Lambda performs the four-step rotation lifecycle: create a new version, set the new credential on the target system, test the new credential works, and finalize by marking it current.

**The four-step rotation lifecycle:**
```
Step 1: createSecret
  Lambda generates a new password (or token)
  Stores it as AWSPENDING version in Secrets Manager
  The existing AWSCURRENT credential is still active — no impact on running application

Step 2: setSecret
  Lambda connects to the target system (RDS, external API, etc.) using
  the AWSCURRENT credential (still valid)
  Sets the new password (AWSPENDING) on the target:
    For RDS: ALTER USER app_user PASSWORD 'newpassword123';
  Both old and new passwords are now valid on the target

Step 3: testSecret
  Lambda connects to the target using the AWSPENDING credential
  Runs a test query (SELECT 1; or equivalent)
  If connection succeeds: rotation proceeds
  If connection fails: rotation aborts; AWSCURRENT remains unchanged; alert sent

Step 4: finishSecret
  Lambda marks AWSPENDING as AWSCURRENT
  Previous AWSCURRENT becomes AWSPREVIOUS
  Old credential (AWSPREVIOUS) still valid for a brief window (allows in-flight
  connections to drain gracefully)
  AWSPREVIOUS is revoked after the configured overlap period

Application behavior during rotation:
  Application caches the DB connection → uses AWSCURRENT password → connection valid
  Secrets Manager rotates → new AWSCURRENT → application has stale cached connection
  Connection pool: existing connections use old password (still valid as AWSPREVIOUS)
  On reconnect: application fetches updated secret from Secrets Manager → new password
  Old credential revoked → any connections using it fail → pool reconnects with new password

This is why applications MUST refresh the secret on connection failure,
not just at startup:
```

```typescript
// NestJS: refresh secret on DB connection failure (rotation-aware)
@Injectable()
export class DatabaseConfigService {
  private cachedSecret: DbCredentials | null = null;
  private cacheExpiresAt = 0;
  private readonly CACHE_TTL_MS = 5 * 60 * 1000; // 5 minutes

  async getCredentials(): Promise<DbCredentials> {
    const now = Date.now();
    if (this.cachedSecret && now < this.cacheExpiresAt) {
      return this.cachedSecret;
    }
    return this.refreshCredentials();
  }

  async refreshCredentials(): Promise<DbCredentials> {
    const client = new SecretsManagerClient({ region: process.env.AWS_REGION });
    const response = await client.send(
      new GetSecretValueCommand({
        SecretId:     process.env.DB_SECRET_ARN!,
        VersionStage: 'AWSCURRENT',
      })
    );

    const secret = JSON.parse(response.SecretString!);
    this.cachedSecret   = secret;
    this.cacheExpiresAt = Date.now() + this.CACHE_TTL_MS;
    return secret;
  }

  // Called when TypeORM/pg encounters an authentication error
  async handleAuthError(): Promise<DbCredentials> {
    // Force cache invalidation — secret may have rotated
    this.cachedSecret   = null;
    this.cacheExpiresAt = 0;
    return this.refreshCredentials();
  }
}

// TypeORM data source factory — re-creates connection on auth failure
async function createDataSource(): Promise<DataSource> {
  const credentials = await dbConfigService.getCredentials();
  const dataSource = new DataSource({
    type:     'postgres',
    host:     credentials.host,
    port:     credentials.port,
    username: credentials.username,
    password: credentials.password,
    database: credentials.dbname,
  });
  await dataSource.initialize();
  return dataSource;
}
```

**RDS native rotation (no custom Lambda needed):**
```
For RDS PostgreSQL/MySQL, Secrets Manager provides a managed rotation function.
Two rotation strategies:

Single-user rotation:
  One user (e.g., app_user) rotated in place.
  Brief window where old password is invalid on the DB but apps still use it.
  Risk: auth errors during the switchover window (milliseconds).
  Use for: development, non-critical services.

Multi-user rotation (recommended for production):
  Two alternating users: app_user_a, app_user_b
  Active user: app_user_a (AWSCURRENT points here)
  Rotation creates new password for app_user_b, tests it, then switches AWSCURRENT to app_user_b
  AWSPREVIOUS still points to app_user_a (valid, allows existing connections to drain)
  No window where all credentials are invalid simultaneously
  Use for: production databases, high-availability requirements
```

## Section 2: Parameter Store

**Q3. What is AWS Systems Manager Parameter Store and how does it differ from Secrets Manager?**
A: Parameter Store is a hierarchical key-value store for application configuration and secrets, integrated with AWS Systems Manager. It is cheaper than Secrets Manager (free tier for standard parameters) but lacks automatic rotation and cross-account secret sharing.

**Structural comparison:**

| Dimension | Secrets Manager | Parameter Store |
|---|---|---|
| Primary use | Sensitive credentials requiring rotation | Config values + non-rotating secrets |
| Encryption | Always KMS-encrypted | Optional (Standard: plaintext; SecureString: KMS) |
| Automatic rotation | Yes (Lambda-backed, native RDS integration) | No (manual only) |
| Versioning | Full version history with stage labels | Up to 100 versions per parameter |
| Cross-account sharing | Yes (resource policy) | No (same account only) |
| Pricing | $0.40/secret/month + $0.05/10,000 API calls | Free (standard); $0.05/10,000 for advanced |
| Parameter size | Up to 65 KB | Standard: 4 KB; Advanced: 8 KB |
| TTL (expiration) | No built-in TTL | Yes (advanced tier; trigger notification on expiry) |
| Hierarchical names | Flat (name is arbitrary string) | `/env/service/key` path hierarchy |
| Audit | CloudTrail | CloudTrail |
| Use in EC2/ECS/Lambda | Yes (SDK) | Yes (SDK + native Lambda env var injection) |

**Parameter Store hierarchy and naming:**
```
Hierarchical naming convention (/environment/service/parameter):
  /prod/nestjs-api/DB_HOST
  /prod/nestjs-api/DB_PORT
  /prod/nestjs-api/DB_NAME
  /prod/nestjs-api/REDIS_URL
  /prod/nestjs-api/RAZORPAY_WEBHOOK_SECRET   ← SecureString (encrypted)
  /staging/nestjs-api/DB_HOST
  /staging/nestjs-api/DB_NAME

Benefits of hierarchy:
  GetParametersByPath: fetch all parameters under /prod/nestjs-api/ in one API call
  IAM policy by path: grant access to /prod/nestjs-api/* without listing every parameter
  Environment isolation: /prod/* vs /staging/* with separate IAM policies

Parameter types:
  String:       Plaintext value (non-sensitive config: DB_HOST, DB_PORT, REGION)
  StringList:   Comma-separated list (e.g., allowed IP ranges, feature flag list)
  SecureString: KMS-encrypted (sensitive but non-rotating: API keys, webhook secrets)

SecureString encryption:
  Default: uses AWS-managed KMS key (aws/ssm) — free, no control over key policy
  Custom KMS key: allows key policy control (who can decrypt), cross-account usage,
                  key rotation (manual), CloudTrail per-key audit
  For PCI-DSS/SOC2: always use a custom KMS key for SecureString parameters
```

**Q4. When do you use Secrets Manager vs Parameter Store for a specific credential?**
A: The decision reduces to three questions: Does the credential rotate automatically? Is it shared across accounts? Does the cost of Secrets Manager justify the use case?

**Decision framework:**

```
Use Secrets Manager when:
  ✅ The credential must rotate automatically
     RDS password, Redis auth token, external API key with rotation API
     → Secrets Manager has native RDS rotation; Parameter Store has none
  ✅ Cross-account sharing is required
     Shared microservice credential accessed from multiple AWS accounts
     → Secrets Manager resource policy; Parameter Store is single-account
  ✅ Multi-region replication is required
     Secrets Manager replicates to multiple regions automatically
     → Parameter Store has no multi-region replication
  ✅ The secret is a database credential in a PCI or SOC2 scope
     Automatic rotation is a compliance requirement, not a convenience

Use Parameter Store (SecureString) when:
  ✅ The value does not rotate (or rotates manually and infrequently)
     RAZORPAY_WEBHOOK_SECRET: changes only when vendor provides a new key
     FEATURE_FLAGS: non-sensitive, changes via deployment
     SMTP_HOST, SMTP_PORT: infrastructure config, not credentials
  ✅ You need a hierarchical config fetch at startup
     Fetch all /prod/nestjs-api/* parameters in one API call → populate process.env
     Cheaper and simpler than one Secrets Manager call per value
  ✅ Cost sensitivity (Parameter Store free tier covers most config needs)
     100 standard parameters → $0/month vs 100 Secrets Manager secrets → $40/month
  ✅ EC2 UserData or SSM Run Command integration
     Parameter Store is natively integrated with SSM agent

Fintech-specific mapping:
  DB password (PostgreSQL RDS):                  → Secrets Manager (rotation required)
  Redis AUTH token (ElastiCache):                → Secrets Manager (rotation supported)
  Razorpay API key (payment gateway):            → Secrets Manager (rotate when compromised)
  Razorpay webhook secret (HMAC validation):     → Parameter Store SecureString (infrequent change)
  NACH NPCI API credentials:                     → Secrets Manager (regulatory rotation)
  JWT signing key (HMAC-256):                    → Secrets Manager (rotate on breach)
  Feature flags (enable_new_kyc_flow: true):     → Parameter Store String (non-sensitive)
  DB host / port / name:                         → Parameter Store String (non-sensitive config)
  Third-party KYC vendor API token:              → Secrets Manager (external credential)
  Internal service-to-service mTLS certs:        → ACM (Certificate Manager) or Secrets Manager
```

**Fetching from both in NestJS at startup:**
```typescript
// config.service.ts — hybrid fetch: Parameter Store for config, Secrets Manager for secrets
@Injectable()
export class AppConfigService implements OnApplicationBootstrap {
  private config: Record<string, string> = {};

  async onApplicationBootstrap(): Promise<void> {
    await Promise.all([
      this.loadParameterStore(),
      this.loadSecrets(),
    ]);
  }

  private async loadParameterStore(): Promise<void> {
    const ssm = new SSMClient({ region: process.env.AWS_REGION });
    let nextToken: string | undefined;

    do {
      const response = await ssm.send(new GetParametersByPathCommand({
        Path:           `/prod/nestjs-api/`,
        WithDecryption: true,              // decrypts SecureString values
        Recursive:      false,
        NextToken:      nextToken,
        MaxResults:     10,
      }));

      for (const param of response.Parameters ?? []) {
        // Strip path prefix: /prod/nestjs-api/DB_HOST → DB_HOST
        const key = param.Name!.split('/').pop()!;
        this.config[key] = param.Value!;
      }
      nextToken = response.NextToken;
    } while (nextToken);
  }

  private async loadSecrets(): Promise<void> {
    const client = new SecretsManagerClient({ region: process.env.AWS_REGION });

    // Fetch structured secret (JSON with multiple fields)
    const dbSecret = await client.send(new GetSecretValueCommand({
      SecretId: process.env.DB_SECRET_ARN!,
    }));
    const db = JSON.parse(dbSecret.SecretString!);
    this.config['DB_PASSWORD'] = db.password;
    this.config['DB_USERNAME'] = db.username;
  }

  get(key: string): string {
    const value = this.config[key];
    if (!value) throw new Error(`Config key not found: ${key}`);
    return value;
  }
}
```

## Section 3: AWS KMS

**Q5. What is AWS KMS and how does envelope encryption work?**
A: AWS Key Management Service (KMS) is a managed service for creating and controlling cryptographic keys. It never exports key material — encryption and decryption operations happen inside KMS's hardware security modules (HSMs). Applications do not handle raw keys; they send plaintext to KMS and receive ciphertext back.

**Envelope encryption — the core concept:**
```
Problem with direct KMS encryption:
  KMS can encrypt data directly, but only up to 4 KB per API call.
  A 100 MB file, a database record, or a batch payload cannot be sent to KMS directly.
  Sending data to KMS for every encrypt/decrypt is also slow (network round-trip per operation).

Envelope encryption solves both problems:

Step 1: Generate a Data Encryption Key (DEK)
  Application calls KMS: GenerateDataKey(KeyId: 'arn:aws:kms:...:key/abc123')
  KMS returns TWO things:
    Plaintext DEK:   raw bytes of the key (used to encrypt your data right now)
    Encrypted DEK:   the same key, encrypted by the KMS CMK (Customer Master Key)
                     (also called the ciphertext blob)

Step 2: Encrypt data locally using the Plaintext DEK
  Application uses the Plaintext DEK + AES-256-GCM to encrypt the data locally
  (no network round-trip; fast; no 4 KB limit)
  After encryption: IMMEDIATELY discard the Plaintext DEK from memory
  Store: Encrypted DEK alongside the encrypted data (in S3, DynamoDB, etc.)

Step 3: Decrypt later
  Application fetches the Encrypted DEK from storage
  Calls KMS: Decrypt(CiphertextBlob: encryptedDek)
  KMS decrypts the DEK using the CMK → returns Plaintext DEK
  Application uses Plaintext DEK to decrypt the data locally
  Discard Plaintext DEK after use

What is protected:
  KMS protects the DEK (encrypted DEK stored with the data)
  DEK protects the data (data encrypted with AES-256)
  CMK never leaves KMS HSM → even AWS employees cannot access the raw key
  If the CMK is deleted or access is revoked: DEK cannot be decrypted → data inaccessible

Visual:
  [CMK in KMS HSM]
       │ protects
       ▼
  [Encrypted DEK] ──stored with──► [S3 object / DynamoDB record / EBS snapshot]
       │                                        │
       │ KMS.Decrypt                           │ decrypted by
       ▼                                        ▼
  [Plaintext DEK] ────────────────────► [Plaintext data]
  (ephemeral; never persisted)
```

**KMS key types:**
```
AWS Managed Keys (aws/service):
  Created and managed by AWS for specific services (aws/s3, aws/rds, aws/ssm).
  You cannot change the key policy or rotate manually.
  Automatic rotation: every 3 years (for most services).
  Cost: free (no per-key charge; only per-API-call charges apply).
  Use when: encryption is required but you do not need fine-grained key control.

Customer Managed Keys (CMK):
  Created by you; you control the key policy.
  Automatic rotation: optional (annual, enabled/disabled by you).
  Cost: $1.00/key/month + $0.03/10,000 API calls.
  Key policy: defines who can use and who can manage the key (separate permissions).
  Use when: compliance requires key ownership proof, cross-service/cross-account
            encryption, or you need to revoke access by deleting/disabling the key.

AWS Owned Keys:
  Fully managed by AWS; not visible in your account.
  Some services use these internally (DynamoDB default encryption).
  No charge; no control; not auditable by you.

Key types by cryptographic algorithm:
  SYMMETRIC_DEFAULT (AES-256-GCM): encrypt/decrypt; most common for envelope encryption
  RSA (2048/3072/4096):            sign/verify OR encrypt/decrypt (not both); for PKI
  ECC (P-256, P-384, secp256k1):   sign/verify only; secp256k1 for blockchain use cases
  HMAC:                            generate/verify MACs; for integrity without PKI overhead
```

**Q6. What is a KMS Key Policy and how does it differ from IAM policies for KMS access?**
A: KMS access is controlled by TWO independent mechanisms: the key policy (attached to the key itself) and IAM policies (attached to users/roles). Both must permit an action for it to succeed. This differs from most AWS services where IAM policy alone is sufficient.

**The two-layer KMS authorization model:**
```
For a KMS action to succeed, BOTH must allow it:
  1. Key Policy: the key must allow the principal
  2. IAM Policy: the principal must have the IAM permission

Exception: the key policy can grant full access to IAM (the default root statement).
  If the key policy contains:
    { "Principal": { "AWS": "arn:aws:iam::123456789012:root" }, "Action": "kms:*" }
  Then IAM policies alone control access for all principals in the account.
  (This is the default key policy AWS creates — it delegates to IAM.)

Without the root statement: key policy MUST explicitly list every principal.
IAM policies alone are insufficient — if the key policy doesn't allow the action,
IAM cannot override it.
```

**Key policy structure:**
```json
{

  "Statement": [
    {
      "Sid": "Enable IAM User Permissions",
      "Effect": "Allow",
      "Principal": {

      },

      "Resource": "*"
    },
    {
      "Sid": "Allow NestJS API to use the key for encryption",

        "kms:Decrypt",
        "kms:GenerateDataKey*",

    }

```

**Separation of duties pattern (critical for fintech):**
```
Key administrators (KeyAdminRole):
  Can manage the key lifecycle (rotate, disable, schedule deletion)
  CANNOT use the key to encrypt/decrypt (no kms:Encrypt, kms:Decrypt)
  Who: security team, infrastructure team

Key users (NestjsApiRole, RdsRole):
  Can use the key to encrypt/decrypt data
  CANNOT manage the key (no kms:Delete, kms:Disable, kms:ScheduleKeyDeletion)
  Who: application roles, AWS service roles

Why this matters for fintech:
  A compromised application role cannot delete the KMS key (data remains decryptable)
  A compromised admin role cannot access encrypted data (cannot call kms:Decrypt)
  Requires two separate role compromises to both destroy the key AND access the data
  This separation is a PCI-DSS and SOC2 audit requirement
```

**Q7. How do you implement field-level encryption for PII data in a fintech application using KMS?**
A: Field-level encryption encrypts individual sensitive fields in a database record rather than encrypting the entire database or disk. It allows non-sensitive fields to be queried normally while PII (Aadhaar number, PAN, bank account) is stored encrypted and only decrypted when explicitly needed.

```typescript
// kms-encryption.service.ts — field-level encryption for PII
import { Injectable }                         from '@nestjs/common';
import { KMSClient, GenerateDataKeyCommand,
         DecryptCommand }                     from '@aws-sdk/client-kms';
import * as crypto                            from 'crypto';

@Injectable()
export class KmsEncryptionService {
  private readonly kmsClient = new KMSClient({ region: process.env.AWS_REGION });
  private readonly kmsKeyId  = process.env.PII_KMS_KEY_ARN!;

  // Encrypt a PII field using envelope encryption
  async encryptField(plaintext: string): Promise<EncryptedField> {
    // 1. Generate a DEK from KMS
    const { Plaintext: plaintextDek, CiphertextBlob: encryptedDek } =
      await this.kmsClient.send(new GenerateDataKeyCommand({
        KeyId:   this.kmsKeyId,
        KeySpec: 'AES_256',
      }));

    // 2. Encrypt the data locally using AES-256-GCM
    const iv         = crypto.randomBytes(12);  // 96-bit IV for GCM
    const cipher     = crypto.createCipheriv('aes-256-gcm', plaintextDek!, iv);
    const encrypted  = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
    const authTag    = cipher.getAuthTag(); // GCM authentication tag (integrity check)

    // 3. Discard the plaintext DEK immediately
    plaintextDek!.fill(0); // zero out the buffer

    // 4. Return: encrypted data + IV + auth tag + encrypted DEK (all stored together)
    return {
      ciphertext:   encrypted.toString('base64'),
      iv:           iv.toString('base64'),
      authTag:      authTag.toString('base64'),
      encryptedDek: Buffer.from(encryptedDek!).toString('base64'),
      keyId:        this.kmsKeyId,       // which KMS key encrypted the DEK
      algorithm:    'AES-256-GCM',
    };
  }

  // Decrypt a PII field
  async decryptField(encrypted: EncryptedField): Promise<string> {
    // 1. Ask KMS to decrypt the DEK
    const { Plaintext: plaintextDek } = await this.kmsClient.send(
      new DecryptCommand({
        CiphertextBlob: Buffer.from(encrypted.encryptedDek, 'base64'),
        KeyId:          encrypted.keyId,  // explicit key ID prevents key confusion attacks
      })
    );

    // 2. Decrypt the data locally
    const decipher = crypto.createDecipheriv(
      'aes-256-gcm',
      plaintextDek!,
      Buffer.from(encrypted.iv, 'base64'),
    );
    decipher.setAuthTag(Buffer.from(encrypted.authTag, 'base64'));

    const plaintext = decipher.update(
      Buffer.from(encrypted.ciphertext, 'base64')
    ).toString('utf8') + decipher.final('utf8');

    // 3. Discard plaintext DEK
    plaintextDek!.fill(0);

    return plaintext;
  }
}

// Usage in a KYC service
@Injectable()
export class KycService {
  constructor(private readonly kmsEncryption: KmsEncryptionService) {}

  async storeKycData(userId: string, kyc: KycInput): Promise<void> {
    // Encrypt PII fields individually
    const [encryptedAadhaar, encryptedPan, encryptedAccountNo] = await Promise.all([
      this.kmsEncryption.encryptField(kyc.aadhaarNumber),
      this.kmsEncryption.encryptField(kyc.panNumber),
      this.kmsEncryption.encryptField(kyc.bankAccountNumber),
    ]);

    // Store encrypted fields as JSON in PostgreSQL
    await this.db.query(`
      INSERT INTO kyc_records
        (user_id, aadhaar_encrypted, pan_encrypted, account_encrypted,
         kyc_status, created_at)
      VALUES ($1, $2, $3, $4, $5, NOW())
    `, [
      userId,
      JSON.stringify(encryptedAadhaar),
      JSON.stringify(encryptedPan),
      JSON.stringify(encryptedAccountNo),
      'PENDING',
    ]);
    // Non-PII fields (kyc_status, timestamps) are queryable without decryption
    // PII fields are blobs — no SQL LIKE or range queries on encrypted data
  }
}

  iv:           string;
```

**KMS DEK caching (for high-throughput scenarios):**
```typescript
// Generating a new DEK per field is expensive (KMS API call per field).
// For high-throughput encryption (NACH batch: 100,000 records):
// Cache the plaintext DEK in memory for a short period; reuse for multiple fields.

@Injectable()
export class KmsDekCacheService {
  private cache: { dek: Buffer; encryptedDek: string; expiresAt: number } | null = null;
  private readonly DEK_TTL_MS = 5 * 60 * 1000; // 5 minutes; rotate DEK frequently

  async getDek(): Promise<{ dek: Buffer; encryptedDek: string }> {
    if (this.cache && Date.now() < this.cache.expiresAt) {
      return { dek: this.cache.dek, encryptedDek: this.cache.encryptedDek };
    }

    const { Plaintext, CiphertextBlob } = await this.kmsClient.send(
      new GenerateDataKeyCommand({ KeyId: this.kmsKeyId, KeySpec: 'AES_256' })
    );

    this.cache = {
      dek:          Buffer.from(Plaintext!),
      encryptedDek: Buffer.from(CiphertextBlob!).toString('base64'),
      expiresAt:    Date.now() + this.DEK_TTL_MS,
    };
    return { dek: this.cache.dek, encryptedDek: this.cache.encryptedDek };
  }
}
// Risk: if the process is killed, the cached DEK is lost (in-memory only).
// Data encrypted with this DEK is still decryptable via the encryptedDek stored with it.
// Never persist the plaintext DEK to disk or database.
```

## Section 4: AWS WAF

**Q8. What is AWS WAF and how does it integrate with CloudFront, ALB, and API Gateway?**
A: AWS WAF (Web Application Firewall) is a Layer 7 firewall that inspects HTTP/HTTPS request content — headers, URI, query strings, body, and cookies — and allows or blocks requests based on configurable rules. It operates in front of your application, before requests reach EC2, Lambda, or containers.

**WAF integration points:**
```
WAF can be attached to:
  Amazon CloudFront (CDN — edge locations globally)
    → Blocks malicious requests at the nearest AWS edge location
    → Lowest latency for end users; blocks before traffic enters your region
    → Required for global DDoS mitigation with Shield Advanced

  Application Load Balancer (ALB — regional)
    → Blocks requests at the regional load balancer
    → Traffic still enters the region before being blocked
    → Use when CloudFront is not in the architecture (internal APIs)

  Amazon API Gateway (REST API — regional or edge-optimized)
    → Directly protects API endpoints
    → Useful for serverless architectures (Lambda backend)

  AWS AppSync (GraphQL API)
    → Protects GraphQL endpoints specifically

  Cognito User Pool
    → Protects authentication endpoints from credential stuffing

One WAF WebACL (Web Access Control List) can be associated with multiple resources
of the SAME type (multiple ALBs, or multiple CloudFront distributions).
CloudFront WebACLs are global (us-east-1); ALB/API Gateway WebACLs are regional.
```

**Q9. What are WAF rule types and how do you build a layered WAF ruleset for a fintech API?**
A: WAF rules can be AWS-managed (Managed Rule Groups) or custom. Production WAF deployments layer both: managed rules for common threats, custom rules for application-specific protection.

**Managed Rule Groups (AWS and third-party):**
```
AWS Managed Rules (free with WAF subscription):
  AWSManagedRulesCommonRuleSet:
    Core protections: XSS, SQL injection, path traversal, common exploits
    Rule count: ~30 rules; blocks the OWASP Top 10 most common attacks
    Mandatory for any WAF deployment

  AWSManagedRulesKnownBadInputsRuleSet:
    Blocks requests with patterns known to be malicious
    (Log4j exploitation patterns, Spring4Shell, SSRF probes)
    Update continuously by AWS when new CVEs emerge

  AWSManagedRulesSQLiRuleSet:
    Dedicated SQL injection protection (more comprehensive than CommonRuleSet)
    Use for APIs with SQL-adjacent input (loan amount, search queries)

  AWSManagedRulesAmazonIpReputationList:
    Blocks IPs known to be bots, scanners, or associated with malicious activity
    Maintained by Amazon threat intelligence
    High-signal: very low false positive rate

  AWSManagedRulesAnonymousIpList:
    Blocks Tor exit nodes, anonymous proxies, VPN services
    Appropriate for financial services (regulatory: KYC must identify the user)
    May cause false positives for legitimate privacy-conscious users

Third-party managed rules (AWS Marketplace):
  F5 Rules, Imperva, Trend Micro, Fortinet
  Specialize in bot protection, API abuse, account takeover patterns
  Evaluated per use case; not universally better than AWS managed rules
```

**WAF Count mode (shadow mode for testing new rules):**
```
Rule actions:
  Allow:  permit the request; stop evaluating rules
  Block:  return 403 (or custom response); stop evaluating rules
  Count:  increment a counter; CONTINUE evaluating rules (do not block)
  CAPTCHA: challenge the user with a CAPTCHA before allowing

Shadow mode pattern (test before enforcing):
  1. Add new rule with Action: Count (not Block)
  2. Monitor CloudWatch metrics: CountedRequests for the rule
  3. Enable sampled requests: examine which requests matched the rule
  4. If legitimate traffic is being counted → rule needs refinement
  5. If only malicious traffic → change action to Block

Never add a new custom rule directly as Block without testing in Count mode first.
A misconfigured Block rule can block all legitimate traffic instantly.
WAF rules are evaluated in priority order; lower number = higher priority.
```

**Q10. What is WAF Bot Control and how do you protect fintech APIs from credential stuffing and scraping?**
A: Bot Control is a WAF managed rule group that classifies requests as human traffic or bot traffic using browser fingerprinting, behavioral analysis, and machine learning. It distinguishes between verified bots (Googlebot, legitimate crawlers) and malicious bots (credential stuffers, scrapers, vulnerability scanners).

**Bot categories WAF identifies:**
```
Category A — Verified good bots (allow):
  Search engine crawlers (Googlebot, Bingbot)
  Security scanners (Qualys, Rapid7 — if you run them)
  Monitoring services (Uptime Robot, Pingdom)
  WAF Bot Control verifies these by IP against published bot lists

Category B — Automated client libraries (challenge or block):
  HTTP libraries without browser fingerprint (requests, axios, curl)
  API clients that do not run JavaScript
  These may be legitimate (your mobile app using axios) or malicious (scrapers)
  Action: CAPTCHA challenge; legitimate clients cannot pass → block them
  Exception: add allow rules for your own API clients with custom headers

Category C — Malicious bots (block):
  Credential stuffers: high-volume login attempts with leaked credential lists
  Account checkers: probe accounts for balance, loan status
  Vulnerability scanners: SQLi, XSS, directory traversal probes
  Form spammers: automated loan applications with synthetic data
  Scalpers: rapid scraping of interest rates, product availability

Credential stuffing protection (critical for fintech):
  Pattern: thousands of login attempts from distributed IPs, rotating user agents
  WAF Bot Control detects: velocity per account across IPs (not just per-IP rate limiting)
  Complement with: Cognito advanced security features (compromised credential check)

Account takeover protection (ATO):
  AWSManagedRulesATPRuleSet (Account Takeover Prevention):
    Inspects login endpoint requests
    Detects credential stuffing patterns (distributed IPs, many accounts)
    Can inject JavaScript challenge to verify human vs bot
    Integrates with Cognito for breach password detection
  Pricing: $10/month + $1/1,000 login attempts (additional to WAF base cost)
```

## Section 5: AWS Shield

**Q11. What is AWS Shield and what is the difference between Shield Standard and Shield Advanced?**
A: AWS Shield is a DDoS protection service. It operates at the network and transport layers (Layer 3/4) and, when combined with WAF, at the application layer (Layer 7). Every AWS account gets Shield Standard automatically and for free.

**Shield Standard (automatic, free):**
```
Automatically applied to:
  All AWS resources: EC2, ELB, CloudFront, Route 53, Global Accelerator
  No configuration required; no opt-in needed

Protection scope:
  Layer 3: IP-level attacks (volumetric floods — UDP amplification, ICMP floods)
  Layer 4: TCP/UDP-level attacks (SYN floods, reflection attacks)

What it does:
  Absorbs and mitigates common network-level DDoS attacks
  Uses AWS's global network capacity (the same infrastructure that protects AWS itself)
  Detection and mitigation happen automatically (no manual intervention)

What it does NOT protect against:
  Layer 7 (application-layer) attacks: HTTP floods, slowloris, API abuse
  Sophisticated volumetric attacks beyond the standard mitigation capacity
  Does not include cost protection (large DDoS → large EC2/data transfer bill)
  No access to DDoS Response Team (DRT)
  No real-time attack visibility (no DDoS event dashboard)
```

**Shield Advanced ($3,000/month/organization, 1-year commitment):**
```
Additional protections over Standard:
  Layer 7 DDoS mitigation:
    Works with WAF to automatically mitigate application-layer attacks
    Can automatically create WAF rules to block attack traffic
    Example: HTTP flood targeting /api/v1/loan/apply → Shield Advanced detects
             pattern → auto-creates WAF rate-limiting rule → attack mitigated
             without manual intervention

  Cost protection (DDoS cost shield):
    AWS credits scaling charges caused by a DDoS attack
    EC2 scale-out triggered by DDoS traffic → WAF/Shield credit the EC2 charges
    Data transfer spike caused by attack → AWS credits the transfer costs
    Eliminates the "bill shock" risk from sustained DDoS attacks

  DDoS Response Team (DRT):
    24/7 access to AWS security engineers during active attacks
    DRT can write custom WAF rules for your specific attack pattern
    DRT proactively contacts you when they detect attacks on your resources

  Real-time attack visibility:
    AWS Shield console: DDoS event dashboard, attack vectors, mitigation status
    CloudWatch metrics: DDoSDetected, DDoSAttackBitsPerSecond, DDoSAttackRequestsPerSecond
    Enables post-attack analysis and forensics

  AWS Health Dashboard integration:
    Active DDoS events appear in your AWS Health Dashboard
    Can trigger EventBridge rules for automated response (SNS alert, Lambda action)

Resources that can be protected (must explicitly add to Shield Advanced protection group):
  Elastic IPs
  CloudFront distributions
  Route 53 hosted zones
  ALBs and NLBs
  EC2 instances (Elastic IP attached)
  Global Accelerator accelerators

Protection group:
  Logical grouping of resources for aggregate protection
  Example: group all resources serving your payments API
  Shield Advanced monitors the group collectively (not just individual resources)
  Useful when an attack targets multiple resources simultaneously
```

**Q12. How do Shield Standard, Shield Advanced, and WAF work together in a DDoS defense architecture?**
A: Effective DDoS defense is layered. Shield handles volumetric network-layer attacks; WAF handles application-layer attacks; architectural patterns (CloudFront, Route 53, anycast) absorb capacity-based attacks.

**Layered DDoS defense architecture:**
```
Attack vectors and their mitigations:

Layer 3/4 volumetric attack (UDP flood, SYN flood — largest attacks):
  Volume: can reach Tbps; exceeds any single server's capacity
  Mitigation: Shield Standard / Advanced + AWS global network absorbs at edge
  Architecture: traffic is absorbed before reaching your region

Layer 7 HTTP flood (many requests, each legitimate-looking):
  Volume: 1M req/s targeting /api/v1/loan/apply
  Mitigation: WAF rate-based rules + Bot Control + Shield Advanced L7 mitigation
  Architecture: WAF at CloudFront edge; rate limit per IP; Bot Control challenge

Slowloris (slow HTTP connections exhausting server thread pool):
  Pattern: many connections, each sending requests one byte per minute
  Mitigation: ALB has a client connection timeout; WAF request body size limit
  Architecture: ALB terminates slow clients; WAF blocks oversized/slow bodies

DNS amplification (attack targeting Route 53):
  Pattern: attacker sends DNS queries to open resolvers with spoofed source (your IP)
  Mitigation: Shield Standard for Route 53; anycast DNS absorbs at edge
  Architecture: Route 53 is always behind Shield; no action needed

API credential stuffing (not volumetric but application-level):
  Pattern: 100,000 login attempts per hour from rotating IP ranges
  Mitigation: WAF ATPRuleSet + Cognito advanced security + rate-based rules
  Architecture: Cognito for authentication; WAF for pre-auth rate limiting

Full defense stack:
                             Internet
                                │
                         Route 53 (DNS)
                         [Shield Standard]
                                │
                          CloudFront (CDN)
                         [Shield Advanced]
                              [WAF]
                         ┌─────────────┐
                         │ WebACL:     │
                         │  AWSCommon  │
                         │  SQLi rules │
                         │  Bot Control│
                         │  Rate limit │
                         │  IP repute. │
                         └─────────────┘
                                │
                       ALB (Regional)
                      [Shield Advanced]
                            [WAF]
                       ┌─────────┐
                       │ WebACL: │
                       │  Same as│
                       │  CDN or │
                       │  subset │
                       └─────────┘
                                │
                     NestJS API Instances
                    (private subnet; no direct internet access)
```

**When Shield Advanced is worth the $3,000/month:**
```
Cost-benefit analysis:

Shield Advanced pays for itself if:
  One DDoS-induced scale-out event costs > $3,000 in EC2/transfer charges
  (For a 10-instance production fleet, a 6-hour DDoS can generate > $10,000 in
   AWS charges from autoscaling triggered by attack traffic)

  OR: your service cannot tolerate Layer 7 DDoS downtime
  (Shield Standard does not protect against HTTP floods; only Advanced + WAF does)

  OR: you require 24/7 DRT access during an active attack
  (Without DRT, you are on your own during a sophisticated attack)

  OR: regulatory/compliance requires documented DDoS protection
  (PCI-DSS 6.4: protect public-facing web applications against known attacks;
   Shield Advanced + WAF satisfies this requirement with documented evidence)

Fintech recommendation:
  Payment processing APIs (public-facing, revenue-critical): Shield Advanced
  Internal admin APIs (not public-facing): Shield Standard sufficient
  Merchant-facing dashboards (public, revenue-adjacent): Shield Advanced
  Cost justification: one prevented outage during peak NACH batch > annual cost
```

## Section 7: Scenario / System Design Questions

**Q14. "Design the complete security architecture for a PCI-DSS compliant payment processing API serving 50,000 merchants, including secret management, encryption, and network protection."**
A:

```
PCI-DSS requirements driving the architecture:
  Req 2.2:  Protect system components from known vulnerabilities (WAF, patching)
  Req 3.4:  Render PAN (payment card numbers) unreadable (field-level encryption)
  Req 4.2:  Prohibit sending unprotected PANs over public networks (TLS everywhere)
  Req 6.4:  Protect public-facing web applications (WAF required)
  Req 7.3:  Least-privilege access to system components (IAM roles)
  Req 8.3:  Secure individual non-consumer authentication (Secrets Manager rotation)
  Req 10.2: Audit log all access to cardholder data (CloudTrail + KMS audit)
  Req 12.3: Protect and manage all technical assets (AWS Shield for availability)

Architecture components:

Network Layer:
  VPC: dedicated for payment processing (no shared VPC with non-PCI workloads)
  Subnets:
    Public:  ALB only (no EC2/RDS in public subnet)
    Private: NestJS API instances (no internet access; outbound via NAT)
    Isolated: RDS PostgreSQL, ElastiCache Redis (no internet, no NAT)
  Security groups:
    ALB SG:         allows 443 inbound from 0.0.0.0/0; 80 redirect only
    API SG:         allows 3000 inbound from ALB SG only; no direct internet
    DB SG:          allows 5432 inbound from API SG only
    Redis SG:       allows 6379 inbound from API SG only
  VPC Flow Logs: enabled; 14-day retention; CloudWatch Logs + S3 archive

DDoS Protection:
  Shield Advanced: attached to CloudFront, ALB, Route 53
  WAF WebACL on CloudFront:
    AWSManagedRulesCommonRuleSet
    AWSManagedRulesKnownBadInputsRuleSet
    AWSManagedRulesSQLiRuleSet
    AWSManagedRulesAmazonIpReputationList
    AWSManagedRulesATPRuleSet (account takeover prevention on /auth/login)
    Custom: rate limit /api/v1/payments/* → 100 req/5min per IP
    Custom: block requests without valid X-API-Key header on merchant endpoints
    Custom: admin endpoints allow-list to office IPs only
  All WAF rules start in Count mode for 72 hours; promote to Block after review

Secret Management:
  DB credentials (PostgreSQL RDS):
    Secrets Manager secret: prod/payments-api/db-credentials
    Rotation: 30 days (PCI-DSS: rotate credentials regularly)
    Strategy: multi-user rotation (app_user_a / app_user_b alternating)
    KMS key: customer-managed CMK (prod-secrets-key)

  Redis AUTH token (ElastiCache):
    Secrets Manager: prod/payments-api/redis-auth-token
    Rotation: 30 days via custom Lambda rotation function

  Payment gateway API keys (Razorpay, payment networks):
    Secrets Manager: prod/payments-api/razorpay-key-id, razorpay-key-secret
    Rotation: manual on vendor notification; automated where API supports it

  JWT signing key (HS256 or RS256 private key):
    Secrets Manager: prod/payments-api/jwt-signing-key
    Rotation: 90 days; coordinate with all services validating JWTs

  Non-rotating config (DB host, Redis endpoint, feature flags):
    Parameter Store SecureString (DB_HOST, REDIS_URL)
    Parameter Store String (LOG_LEVEL, FEATURE_FLAGS)

Encryption:
  Data at rest:
    RDS: encrypted with CMK (prod-rds-key); separate from app CMK
    EBS: all volumes encrypted with CMK
    S3 (documents, exports): SSE-KMS with CMK

  Field-level encryption (PCI cardholder data):
    PAN (card number): encrypted with field-level KMS envelope encryption
    CVV: NEVER stored (PCI-DSS prohibits storing CVV after authorization)
    Expiry date: encrypted if stored for recurring payments
    Cardholder name: encrypted

    Separate KMS CMK for PII (pii-encryption-key):
      Key policy: only payments-api role can Decrypt; only batch-processor can GenerateDataKey
      Encryption context: { "purpose": "pii", "service": "payments-api" }
      Key rotation: annual automatic rotation

  In transit:
    All API endpoints: TLS 1.2 minimum (TLS 1.3 preferred); enforced by ALB policy
    ALB → EC2: HTTPS (internal TLS; certificates from ACM Private CA)
    EC2 → RDS: SSL required (ssl-mode=require in connection string; verify-ca for PCI)
    EC2 → Redis: TLS enabled (ElastiCache in-transit encryption)

KMS CMK Structure (key per data classification):
  prod-secrets-key:   encrypts Secrets Manager secrets, Parameter Store SecureStrings
  prod-rds-key:       encrypts RDS storage, automated backups
  prod-pii-key:       encrypts PAN, cardholder name, account numbers (field-level)
  prod-s3-key:        encrypts S3 objects (loan documents, exported reports)
  prod-logs-key:      encrypts CloudWatch Logs, S3 audit logs

  Each key: separate key policy; admin role ≠ user role; CloudTrail audit per key
  Key deletion: 30-day waiting period (cannot be shortened); MFA required to schedule

IAM:
  NestJS API task role:
    secretsmanager:GetSecretValue on prod/payments-api/* only
    kms:Decrypt, GenerateDataKey on prod-pii-key only (with encryption context condition)
    sqs:ReceiveMessage, DeleteMessage on payment processing queues only
    No s3:*, no ec2:*, no iam:*, no route53:*

  Batch processor role:
    Separate role; access to batch-specific queues and S3 only
    No access to real-time API queues

Audit and Compliance:
  CloudTrail: all regions; management events + data events for S3 and KMS
  CloudTrail log integrity: enabled (hash chain; detect log tampering)
  CloudTrail logs encrypted with prod-logs-key; retained 7 years (S3 Glacier after 1 year)
  KMS CloudTrail events: every Decrypt/GenerateDataKey call logged with:
    Principal (who), KeyId (which key), EncryptionContext (for what purpose)
  Secrets Manager audit: every GetSecretValue call logged (who, when, what secret)
  GuardDuty: enabled; alerts on:
    Unusual KMS key usage (decrypt calls from new IP/region)
    Secrets Manager access from EC2 not in the payments VPC
    Unusual API call patterns suggesting credential compromise
```

**Q15. "Your WAF is blocking legitimate merchant traffic on the payment endpoint. How do you diagnose and fix this without disabling WAF protection?"**
A:

```
Symptom: merchants reporting 403 errors on POST /api/v1/payments/initiate
         The errors started after the last WAF rule deployment.

Step 1: Identify which WAF rule is blocking the traffic

  WAF sampled requests (AWS Console → WAF → WebACL → Rules → View sampled requests):
    Shows the last 100 matched requests with:
      Matched rule name
      Action taken (Block/Count)
      Request details (URI, headers, body snippet, IP)
    Find the rule matching the legitimate merchant requests

  CloudWatch WAF metrics:
    Metric: BlockedRequests per rule (filter by RuleGroupName or RuleName)
    Graph: sudden spike in BlockedRequests from AWSManagedRulesCommonRuleSet
           at the time merchants started complaining
    Identifies the rule group; sampled requests identifies the specific rule

  WAF CloudWatch Logs (if logging enabled to S3/CloudWatch):
    Enable WAF logging: WebACL → Logging → Enable (to CloudWatch Logs or S3)
    Query with Athena (if S3) or CloudWatch Insights:
      fields @timestamp, action, terminatingRuleId, httpRequest.uri
      | filter action = "BLOCK"
      | filter httpRequest.uri like "/api/v1/payments/"
      | stats count(*) by terminatingRuleId
      | sort count desc
    Output: shows which rule ID is blocking the most payment requests

Step 2: Examine the blocked request payload

  Sampled request body (if body inspection is enabled):
    The merchant's payment request may contain a field value that triggers a
    WAF rule. Common false positive causes:
      SQL injection rule: merchant sending "select" or "drop" in a business name
        "Business Name: Select Systems Pvt Ltd" → triggers SQLi rule
      XSS rule: merchant sending HTML in a description field
        "Loan for <construction> of office" → angle brackets trigger XSS rule
      Common rule set: long query strings, encoded characters in payment notes

Step 3: Fix without disabling protection

  Option A: Add a rule exception (scope-down statement)
    Modify the blocking rule's scope-down statement to EXCLUDE specific conditions:
    Example: SQLi rule → add scope-down to NOT apply to the 'business_name' field:

    Instead of: inspect ALL request body fields for SQLi
    Change to:  inspect ALL fields EXCEPT the 'name' JSON path in the body

    In AWS Managed Rule Groups, use "Rule action overrides" to change
    a specific rule within the group to Count (test) or to exclude it:

    Rule group override:
      AWSManagedRulesCommonRuleSet
        SizeRestrictions_BODY: Count (was Block)
        → Allows large payment payloads while keeping other rules active

  Option B: Add a before-rule IP allow-list for the specific endpoint
    If the blocked merchants have static IPs:
      Create an IP set with their IPs
      Add a high-priority Allow rule: IF IP in MerchantAllowList AND URI = /payments/*
      THEN Allow (and stop evaluating rules)
      Priority 1 (before all blocking rules) → these merchants bypass WAF for payments

  Option C: Add a custom header exemption
    Merchants' internal systems can add a custom header (e.g., X-Merchant-SDK: v2.1)
    Add WAF rule: IF header X-Merchant-SDK exists THEN Count (not Block) for this rule
    Requires updating merchant SDK; not immediate but long-term correct solution

Step 4: Verify the fix in Count mode before deploying as Block

  Change the modified rule to Count (not Block)
  Monitor: merchants should stop getting 403 (rule now counts, not blocks)
  Verify: sampled requests show the rule matching but not blocking
  Confirm: CloudWatch BlockedRequests metric drops for this rule
  Deploy: change back to Block (with the corrected scope-down statement)

Step 5: Enable WAF full request logging going forward

  WAF sampling (100 requests) is insufficient for forensics.
  Enable full logging to S3:
    Redact sensitive fields (payment card numbers, passwords) before logging
    Retain: 90 days (cost-effective; rotate to Glacier for long-term)
  This gives you a complete audit trail of all WAF decisions — essential for
  PCI-DSS compliance and future debugging.
```

## The Core Mental Model

```
Secret lifecycle has four phases — all must be covered:
  Storage:     Secrets Manager (encrypted at rest with KMS, never plaintext)
  Access:      IAM role + Secrets Manager resource policy (who can read)
  Rotation:    Automatic (Secrets Manager schedules Lambda); application refreshes on auth error
  Audit:       CloudTrail (every GetSecretValue call logged; who, when, from where)
  Missing any phase = incomplete security posture.

Envelope encryption is not complexity — it is necessity:
  KMS maximum input: 4 KB. Your data is larger.
  KMS per-call latency: ~5ms. Your throughput requires local crypto.
  Solution: KMS protects the DEK (small, < 4 KB); DEK protects your data (any size, local).
  The encrypted DEK is stored with the ciphertext — the data is self-describing.
  To decrypt: fetch encrypted DEK → KMS.Decrypt → plaintext DEK → decrypt data locally.
  Never persist the plaintext DEK; zero it from memory immediately after use.

KMS key policy is not redundant with IAM — it is a separate gate:
  IAM policy alone is insufficient if the key policy doesn't grant access.
  The default key policy (root statement) delegates to IAM — this is the normal case.
  If you remove the root statement: every principal must be explicitly in the key policy.
  Key administrators (who manage keys) should not be key users (who encrypt/decrypt).
  Separation of duties is an audit requirement, not a best practice.

WAF in Count mode before Block — always:
  A misconfigured Block rule can take down your entire API in seconds.
  Count mode: rule matches but does not block; traffic continues; counter increments.
  Test in Count for 72 hours minimum; examine sampled requests; validate no false positives.
  Promote to Block only after confirming only malicious traffic matches.
  This applies to new rules AND changes to existing rules.

Shield Advanced only works at Layer 7 when WAF is attached:
  Shield Standard: blocks volumetric Layer 3/4 attacks on all resources automatically.
  Shield Advanced alone (without WAF): no Layer 7 protection.
  Shield Advanced + WAF: automatically creates WAF rules during L7 DDoS attacks.
  The DRT (DDoS Response Team) writes WAF rules on your behalf during active attacks.
  Without WAF associated to the protected resource: DRT cannot help with L7 attacks.

Parameter Store vs Secrets Manager is a cost and capability decision:
  Secrets Manager: $0.40/secret/month. Use for credentials requiring automatic rotation.
  Parameter Store: free (standard tier). Use for config and non-rotating secrets.
  Avoid the anti-pattern of using Parameter Store SecureString for DB passwords
  just to save $0.40/month — one rotation failure or leaked password costs far more.
  The $4.80/year for Secrets Manager on your DB password is the cheapest insurance
  you will ever buy.

The fintech security checklist in priority order:
  1. IMDSv2 required on all EC2 (blocks SSRF credential theft)
  2. Secrets Manager for all DB passwords and API keys (rotation + audit)
  3. KMS CMK for PII fields (Aadhaar, PAN, bank account — field-level encryption)
  4. WAF with CommonRuleSet + SQLi + IP Reputation on all public APIs
  5. Shield Advanced for public payment endpoints (cost protection + DRT access)
  6. Separate KMS CMKs per data classification (PII, secrets, storage)
  7. Least-privilege IAM roles per service (no wildcard resources; no *)
  8. CloudTrail + KMS data events enabled (audit every decrypt call)
  9. GuardDuty enabled (anomalous KMS usage, credential misuse detection)
  10. DLQ + CloudWatch alarms (security events observable, not silent)
```

**Tip for the interview:** AWS security questions at 5 YOE converge on three depth probes: (1) envelope encryption — knowing that KMS has a 4 KB plaintext limit and per-call latency, that the solution is GenerateDataKey (plaintext DEK for local AES-256 encryption + encrypted DEK stored with the ciphertext), that the plaintext DEK must be zeroed from memory immediately after use and never persisted, and that decryption requires calling KMS.Decrypt on the encrypted DEK to recover the plaintext DEK, demonstrates you understand why every AWS service uses envelope encryption internally rather than sending data to KMS directly; (2) the KMS key policy two-gate model — explaining that IAM policy alone is insufficient to access a KMS key if the key policy doesn't grant access, that the default key policy has a root statement that delegates to IAM (making IAM alone sufficient), and that removing this statement means every principal must be explicitly in the key policy (which enables strict separation of key administrators from key users), shows you understand the security model rather than just the API; (3) WAF Count mode as the mandatory pre-deployment gate — knowing that Block rules take effect immediately and can block all legitimate traffic if misconfigured, that Count mode lets you validate which requests match without blocking, and that sampled requests + CloudWatch metrics give you visibility into what a new rule would block before it does, is the operational discipline that separates someone who has broken a production API with a WAF rule from someone who only knows WAF at the console level. The fintech callout: PCI-DSS field-level encryption for PAN and cardholder data using KMS envelope encryption with AES-256-GCM, with a dedicated CMK with encryption context (to prevent key misuse across services), and with separate key policy roles for administrators and users, is the implementation that a PCI auditor expects to see — and the CVV prohibition (never stored, period) is the detail that signals you understand the standard rather than just the technology.
