## Section 1: EC2 Instance Types — Families, Naming, and Selection

**Q1. How does the EC2 instance type naming scheme work, and what does each part tell you?**
A: Every EC2 instance type name encodes the family, generation, modifiers, and size in a structured format:

```
    c    7    g    n    .    2xlarge
    │    │    │    │         │
    │    │    │    │         └── Size: nano, micro, small, medium,
    │    │    │    │              large, xlarge, 2xlarge … 112xlarge
    │    │    │    └── Additional modifier: n = network-optimized
    │    │    └── Processor modifier: g = Graviton (ARM), a = AMD, i = Intel
    │    └── Generation: 7 (higher = newer; newer gen = better price/perf)
    └── Family: c = compute-optimized

Full example: c7gn.2xlarge
  c   = compute-optimized family
  7   = 7th generation
  g   = Graviton3 (ARM-based, AWS-designed)
  n   = network-optimized (up to 200 Gbps ENA Express)
  2xlarge = 8 vCPU, 16 GiB RAM
```

**Instance families and their primary use:**

| Family | Name | vCPU:RAM ratio | Primary use |
|---|---|---|---|
| `m` | General purpose | 1:4 | Balanced workloads; default choice |
| `c` | Compute optimized | 1:2 | CPU-bound: API servers, batch, encoding |
| `r` | Memory optimized | 1:8 | In-memory DB, caching, analytics |
| `x` | Memory optimized (extreme) | 1:16+ | SAP HANA, large in-memory datasets |
| `i` | Storage optimized | NVMe-focused | High IOPS: databases, search (Elasticsearch) |
| `d` | Dense storage | HDD-focused | Data warehousing, Hadoop, bulk storage |
| `g` / `p` | GPU | GPU-attached | ML training/inference, rendering, CUDA |
| `inf` | Inferentia | AWS Inferentia chip | Cost-optimized ML inference |
| `t` | Burstable | 1:2–4, credits | Dev/test, variable-load services |
| `hpc` | HPC optimized | EFA networking | Tightly coupled HPC, MPI workloads |

**Processor modifiers:**
```
No modifier  → Intel (default in most families)
a            → AMD EPYC (typically 10% cheaper than Intel equivalent)
g            → AWS Graviton (ARM64; typically 20–40% better price/perf ratio)
i            → Intel Ice Lake or Sapphire Rapids (specific Intel gen)
```

**The Graviton selection rule:** For any workload that does not require x86-specific binaries (most NestJS/Node.js, Java, Python, Go workloads compile cleanly for ARM64), prefer `g` (Graviton) instances — same or better performance at 20–40% lower cost. The only blockers are proprietary x86 software, OS images not available for ARM64, or dependencies with no ARM64 build.

**Q2. How do T-series burstable instances work, and when do they hurt you in production?**
A: T-series instances (`t3`, `t4g`) run at a baseline CPU utilization and accumulate CPU credits when below baseline. When CPU demand spikes above baseline, the instance spends credits to burst to full CPU capacity. When credits run out, the instance throttles to baseline — hard.

**The credit math:**

```
t3.medium: 2 vCPU, 4 GiB RAM
  Baseline:          20% of 2 vCPU = 0.4 vCPU continuously
  Credit earn rate:  24 credits/hour (0.4 credit per vCPU per minute × 2 vCPU × 60)
  Max credit balance: 576 credits (24 hours of earning)
  1 CPU credit = 1 vCPU running at 100% for 1 minute

Scenario: Instance idles at 5% CPU for 8 hours, then a batch job runs:
  Credits earned: 8 × 24 = 192 credits
  Batch job at 100% CPU: spends 2 credits/minute (2 vCPUs × 100%)
  Time until credit exhaustion: 192 / 2 = 96 minutes
  After 96 minutes: CPU throttled to 20% baseline — batch slows to a crawl

t3 Unlimited mode:
  Allows bursting beyond the credit balance by paying $0.05/vCPU-hour for
  the excess burst above baseline.
  Risk: a sustained CPU spike on many t3 Unlimited instances creates an
  unexpected bill — the instance runs at full speed but charges accumulate silently.
```

**When T-series instances hurt in production:**

```
Dangerous pattern: using t3.medium for NestJS API servers in production
  Low-traffic hours: idle at 5% CPU, accumulating credits
  Traffic spike / deployment / GC pause: burst to 100%
  If spike lasts > credit buffer: throttled mid-spike
  Symptom: latency spikes to seconds; requests time out; CPU at 20% baseline while
           the event loop is saturated

  t3 Unlimited makes this worse: charges accumulate invisibly until the bill arrives.

Safe use of T-series:
  Dev / staging environments (variable, low sustained load)
  Internal tools, cron schedulers, low-traffic admin services
  Bastion hosts, NAT instances, small monitoring agents
  Any workload where sustained CPU above baseline is never expected

Production rule: if sustained CPU utilization exceeds 15–20% during normal
operation, move to a fixed-performance instance (m, c, r family).
Use CloudWatch metric CPUCreditBalance alarm: alert when credits drop below
20% of max balance — leading indicator before throttling occurs.
```

**Q3. How do you select the right instance type for a NestJS API service, a PostgreSQL RDS-style workload, and a Redis cluster?**
A: Instance selection follows a consistent pattern: profile the workload's bottleneck, then match the instance family to that bottleneck.

**NestJS API service:**
```
Workload profile:
  CPU: moderate; Node.js single-threaded per process; I/O-bound (network, DB calls)
  Memory: low-moderate; Node.js v8 heap typically 256MB–1GB per process
  Network: moderate; many small HTTP request/response pairs
  Disk: ephemeral only (logs, tmp); no local persistence

Instance selection:
  Family: m (general purpose) or c (compute) — API servers are often CPU-bound
          at high concurrency due to JSON serialization, JWT validation, crypto
  Size: start with m7g.large (2 vCPU, 8 GiB) for Graviton ARM64
        or c7g.large (2 vCPU, 4 GiB) if CPU-bound
  Avoid: t3 (burst throttle risk under traffic spikes)
  Scale: horizontal (add instances behind ALB) rather than vertical
         Node.js benefits more from more instances than more vCPU per instance
         because the event loop is single-threaded per process

Recommended: m7g.large (Graviton) with auto-scaling; 2–10 instances
             Run cluster mode (pm2 -i max) to use all vCPUs per instance
```

**PostgreSQL (self-managed on EC2):**
```
Workload profile:
  CPU: low-moderate for OLTP; high for analytics queries
  Memory: critical — PostgreSQL performance is dominated by shared_buffers
          (typically 25% of RAM) and the OS page cache
          More RAM = more data in cache = fewer disk reads
  Disk: critical — IOPS, throughput, latency
  Network: moderate (client connections)

Instance selection:
  Family: r (memory optimized) for OLTP/mixed; r7g.xlarge (4 vCPU, 32 GiB)
          i (storage optimized) for write-heavy / high IOPS workloads
  Storage: io2 Block Express (up to 256K IOPS) for production PostgreSQL
           gp3 with provisioned IOPS for moderate workloads
  Avoid: burstable (t3) — database I/O patterns are sustained, not bursty
         Burstable disk I/O is not a thing — but burstable CPU throttle
         during VACUUM or analytics queries is a real risk

Recommended: r7g.2xlarge (8 vCPU, 64 GiB) for a busy OLTP PostgreSQL
             io2 volume with 16K–32K IOPS provisioned
             Enable EBS-optimized (default on current gen; dedicated EBS bandwidth)
```

**Redis cluster (self-managed on EC2):**
```
Workload profile:
  CPU: low-moderate; Redis is single-threaded per shard (6.0+ has I/O threads)
  Memory: critical — all data in RAM; OOM = data loss or eviction
  Network: high; many small commands; network bandwidth matters at scale
  Disk: only for persistence (AOF/RDB snapshots)

Instance selection:
  Family: r (memory optimized) — Redis is a memory-bound workload
  Size: right-size to fit the dataset + 30% headroom (for replication buffer,
        AOF rewrite buffer, fragmentation)
  Network: choose instances with enhanced networking (ENA); at high command
           rates, network can be the bottleneck before CPU
  Avoid: CPU-optimized families (c) — Redis rarely saturates a single core
         at typical command rates; memory is the constraint

Recommended: r7g.large (2 vCPU, 16 GiB) or r7g.xlarge (4 vCPU, 32 GiB)
             depending on dataset size
             Enable AOF with appendfsync everysec for durability
             Use ElastiCache for Redis (managed) instead of self-managed EC2
             unless you need a feature ElastiCache does not support
```

## Section 2: Launch Templates

**Q4. What is an EC2 Launch Template and how does it differ from a Launch Configuration?**
A: A Launch Template is the versioned specification of everything needed to launch an EC2 instance — AMI, instance type, key pair, security groups, user data, IAM instance profile, EBS volumes, network interfaces, and more. It is the source of truth for instance configuration, used by Auto Scaling Groups, EC2 Fleet, and Spot Fleet.

**Launch Template vs Launch Configuration:**

| Dimension | Launch Template | Launch Configuration |
|---|---|---|
| Versioning | Yes — create new versions, set a default | No — immutable; must create new to change |
| Multiple instance types | Yes (via mixed instances policy) | No — one instance type only |
| Spot + On-Demand mix | Yes (mixed instances policy) | No |
| T2/T3 Unlimited config | Yes | No |
| Placement groups | Yes | No |
| Dedicated hosts | Yes | No |
| AWS recommendation | Current (use this) | Deprecated (do not use for new ASGs) |
| ASG support | Full | Legacy only |

**Launch Configuration is deprecated.** All new Auto Scaling Groups must use Launch Templates. Existing ASGs with Launch Configurations cannot use mixed instances policies or newer EC2 features.

**Q5. What is the structure of a Launch Template and what are the critical fields?**
A: A Launch Template contains two categories of configuration: fields that must be set for every launch, and optional overrides that can be set per-version or overridden by the ASG.

**Core Launch Template structure:**
```json
{
  "LaunchTemplateName": "nestjs-api-lt",
  "VersionDescription": "v3 — Graviton, IMDSv2 required",
  "LaunchTemplateData": {

    "ImageId": "ami-0abcdef1234567890",
    "InstanceType": "m7g.large",

    "KeyName": "prod-bastion-key",

    "IamInstanceProfile": {
      "Arn": "arn:aws:iam::123456789012:instance-profile/NestjsApiRole"
    },

    "NetworkInterfaces": [{
      "AssociatePublicIpAddress": false,
      "DeviceIndex": 0,
      "Groups": ["sg-0api123", "sg-0internal456"]
    }],

    "BlockDeviceMappings": [{
      "DeviceName": "/dev/xvda",
      "Ebs": {
        "VolumeType":           "gp3",
        "VolumeSize":           30,
        "Iops":                 3000,
        "Throughput":           125,
        "DeleteOnTermination":  true,
        "Encrypted":            true,
        "KmsKeyId":             "arn:aws:kms:..."
      }
    }],

    "MetadataOptions": {
      "HttpTokens":              "required",
      "HttpPutResponseHopLimit": 1,
      "InstanceMetadataTags":    "enabled"
    },

    "UserData": "<base64-encoded bootstrap script>",

    "TagSpecifications": [{
      "ResourceType": "instance",
      "Tags": [
        { "Key": "Service",     "Value": "nestjs-api" },
        { "Key": "Environment", "Value": "production" },
        { "Key": "ManagedBy",   "Value": "terraform" }
      ]
    }],

    "Monitoring": { "Enabled": true },

    "EbsOptimized": true
  }
}
```

**Critical fields to get right:**

**`MetadataOptions.HttpTokens: "required"` (IMDSv2):**
```
IMDSv1: curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
        Anyone with network access to the instance can read IAM credentials.
        SSRF vulnerability → credential theft.

IMDSv2: requires a session token; token obtained via PUT request with TTL:
  TOKEN=$(curl -X PUT http://169.254.169.254/latest/api/token \
          -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
  curl http://169.254.169.254/latest/meta-data/... \
       -H "X-aws-ec2-metadata-token: $TOKEN"

Setting HttpTokens: "required" blocks all IMDSv1 requests.
This is a mandatory security hardening step — every production Launch Template
should require IMDSv2.
```

**`UserData` — bootstrap script:**
```bash
#!/bin/bash
set -euo pipefail

# Install CloudWatch agent
yum install -y amazon-cloudwatch-agent

# Pull app config from SSM Parameter Store
aws ssm get-parameter \
  --name "/prod/nestjs-api/env" \
  --with-decryption \
  --query Parameter.Value \
  --output text > /opt/app/.env

# Start the application
cd /opt/app
npm run start:prod

# Signal ASG that instance is healthy (if using lifecycle hooks)
INSTANCE_ID=$(curl -sf http://169.254.169.254/latest/meta-data/instance-id)
aws autoscaling complete-lifecycle-action \
  --lifecycle-hook-name "app-ready" \
  --auto-scaling-group-name "$ASG_NAME" \
  --lifecycle-action-result CONTINUE \
  --instance-id "$INSTANCE_ID"
```

**Launch Template versioning pattern:**
```
Version 1: initial (m6g.large, AL2)
Version 2: upgrade to m7g.large
Version 3: add IMDSv2 requirement, encrypt EBS
           ← set as default version

ASG references: LaunchTemplate latest (tracks default version)
  Or: pin to a specific version for controlled rollouts
      Version $Latest → always uses newest version (risky for production)
      Version $Default → uses the explicitly set default (safer)
```

## Section 3: Auto Scaling Groups

**Q6. How does an Auto Scaling Group work, and what are the key configuration parameters?**
A: An Auto Scaling Group (ASG) maintains a fleet of EC2 instances within configured size bounds, launching and terminating instances in response to scaling policies. It integrates with load balancers for health checks and traffic distribution, and with CloudWatch for metric-driven scaling.

**ASG core parameters:**
```
MinSize:         Minimum instances always running (floor; never scale below this)
MaxSize:         Maximum instances ASG will launch (ceiling; hard limit)
DesiredCapacity: Target number of instances right now (ASG reconciles to this)

If DesiredCapacity > running instances: ASG launches new instances
If DesiredCapacity < running instances: ASG terminates instances (per termination policy)
If an instance fails health check: ASG terminates it and launches a replacement
                                   (maintains DesiredCapacity)

Example:
  MinSize: 2        ← always have at least 2 instances (HA; survive AZ failure)
  MaxSize: 20       ← never exceed 20 (cost guard)
  DesiredCapacity:  starts at 2; scaling policies adjust dynamically
```

**Health checks:**
```
EC2 health check (default):
  EC2 considers the instance healthy if it is in 'running' state.
  Does NOT check if the application is actually serving traffic.
  An instance with a crashed Node.js process remains 'healthy' by EC2 criteria.

ELB health check (recommended for production):
  ALB performs health checks against the application endpoint (e.g., GET /health)
  If the ALB marks the instance unhealthy (HTTP 4xx/5xx or timeout):
    ASG marks it unhealthy → terminates → launches replacement
  This catches application-level failures that EC2 metrics miss.

Health check grace period:
  Time after launch before health checks start (default: 300s)
  Set this to the time your instance needs to complete UserData bootstrap +
  application startup. If grace period is too short: ASG kills healthy
  instances during startup (bootstrap loop). If too long: unhealthy instances
  survive longer than necessary.
```

**Q7. What are the ASG scaling policy types, and when do you use each?**
A: ASG supports three scaling policy families, each suited to a different demand pattern:

**1. Simple Scaling (legacy — avoid):**
```
Rule: if CPUUtilization > 70% for 2 minutes → add 2 instances
      Wait for cooldown (300s) before next action

Problems:
  - Cooldown period means slow response to rapid demand spikes
  - Does not account for the metric value — adds 2 instances whether
    CPU is 71% or 99%
  - Replaced by Target Tracking in all modern architectures
```

**2. Step Scaling:**
```
Rule: if CPUUtilization > 70%: add 1 instance
      if CPUUtilization > 85%: add 3 instances
      if CPUUtilization > 95%: add 5 instances

Better than Simple Scaling: proportional response to severity.
Use when: you need custom step logic that Target Tracking does not cover,
          or scaling on custom metrics with non-linear response required.
```

**3. Target Tracking Scaling (recommended for most workloads):**
```
Rule: maintain CPUUtilization at 60%
      ASG calculates required instance count and scales automatically

How it works:
  ASG observes the metric continuously.
  If metric > target: scale out (add instances) proportionally.
  If metric < target: scale in (remove instances) proportionally.
  AWS manages the math — you set the target, not the steps.

Common target tracking metrics:
  ASGAverageCPUUtilization       ← most common; target 40–60% for API servers
  ALBRequestCountPerTarget       ← requests/second per instance; good for I/O-bound
  ASGAverageNetworkIn/Out        ← network-bound workloads

Custom metric target tracking:
  Publish custom CloudWatch metric (e.g., active_websocket_connections per instance)
  Target tracking policy on that metric: target = 1000 connections per instance
  ASG scales out when any instance exceeds 1000 connections

NestJS API recommendation:
  ALBRequestCountPerTarget: target 500–1000 req/s per instance
  Rationale: request rate is more directly tied to user experience than CPU;
             CPU varies with request complexity; RPS is consistent signal
```

**4. Scheduled Scaling:**
```
Rule: at 08:00 UTC Monday–Friday: set DesiredCapacity = 10
      at 20:00 UTC Monday–Friday: set DesiredCapacity = 3
      at 00:00 UTC Saturday:      set DesiredCapacity = 2

Use when: traffic pattern is highly predictable (business-hours B2B SaaS,
          batch jobs at known times, planned traffic events like sales).
Combine with target tracking: scheduled scaling sets a higher minimum
for known peak periods; target tracking handles the dynamic variation within.

Fintech example:
  NACH batch processing runs 09:00–11:00 IST daily.
  Scheduled scaling: set Min = 8 at 08:45 IST; set Min = 2 at 11:30 IST.
  Target tracking handles variation within the batch window.
```

**Q8. What are ASG lifecycle hooks and why do they matter for production deployments?**
A: Lifecycle hooks pause instance transitions at two points — instance launch and instance termination — to allow custom actions before the transition completes. Without lifecycle hooks, instances move through launch and termination immediately, which can cause traffic drops, incomplete bootstrap, or lost in-flight requests.

**The two hook points:**
```
Launch lifecycle:
  EC2_INSTANCE_LAUNCHING hook
  ASG launches instance → enters PENDING:WAIT state
  Your code runs (download config, warm caches, run integration checks)
  You call complete-lifecycle-action CONTINUE → instance moves to InService
  If you call ABANDON → ASG terminates the instance and tries again
  Timeout (default 3600s): if no action taken, default result (CONTINUE or ABANDON)

Termination lifecycle:
  EC2_INSTANCE_TERMINATING hook
  ASG selects instance for termination → enters TERMINATING:WAIT state
  Your code runs (drain connections, flush buffers, deregister from service mesh)
  You call complete-lifecycle-action CONTINUE → termination proceeds
  Timeout: if no action taken, instance terminates regardless
```

**Launch hook pattern — wait for application readiness:**
```bash
# UserData: signal readiness after full application startup
#!/bin/bash
set -euo pipefail

# Bootstrap: install dependencies, pull config, start app
/opt/bootstrap.sh

# Wait for the application health endpoint to return 200
until curl -sf http://localhost:3000/health; do
  sleep 5
done

# Signal ASG: this instance is ready to receive traffic
INSTANCE_ID=$(curl -sf \
  -H "X-aws-ec2-metadata-token: $(curl -sf -X PUT \
    http://169.254.169.254/latest/api/token \
    -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')" \
  http://169.254.169.254/latest/meta-data/instance-id)

aws autoscaling complete-lifecycle-action \
  --lifecycle-hook-name    "app-ready" \
  --auto-scaling-group-name "${ASG_NAME}" \
  --lifecycle-action-result CONTINUE \
  --instance-id             "${INSTANCE_ID}"
```

**Termination hook pattern — graceful drain:**
```
Problem without termination hook:
  ALB deregisters instance → waits deregistration delay (default 300s)
  After delay, ALB stops sending new requests but in-flight requests
  may still be processing when EC2 terminates the instance → 502/connection reset

  ASG termination can bypass the ALB deregistration delay if the
  instance terminates before the delay expires.

Solution with termination hook:
  1. ASG selects instance → TERMINATING:WAIT
  2. EventBridge rule triggers Lambda
  3. Lambda:
     a. Deregisters instance from ALB target group
     b. Waits for ALB deregistration delay (300s) + polls until
        connection count drops to zero
     c. Sends SIGTERM to application process (starts graceful shutdown)
     d. Calls complete-lifecycle-action CONTINUE
  4. EC2 terminates

NestJS graceful shutdown (receives SIGTERM):
  app.enableShutdownHooks(); // listens for SIGTERM/SIGINT
  // NestJS calls onApplicationShutdown() on all modules
  // Stops accepting new connections, finishes in-flight requests
  // Closes DB connections, Kafka consumers, Redis connections
  // Exits with code 0 when done
```

**Q9. What is the Mixed Instances Policy and how does it work with Launch Templates?**
A: The Mixed Instances Policy allows an ASG to launch instances across multiple instance types and across On-Demand and Spot capacity within the same group. It enables cost optimization (Spot for non-critical capacity) and resilience (multiple instance types reduce Spot interruption risk from any single pool being reclaimed).

**Mixed Instances Policy structure:**
```json
{
  "MixedInstancesPolicy": {
    "LaunchTemplate": {
      "LaunchTemplateSpecification": {
        "LaunchTemplateName": "nestjs-api-lt",
        "Version":            "$Default"
      },
      "Overrides": [
        { "InstanceType": "m7g.large" },
        { "InstanceType": "m6g.large" },
        { "InstanceType": "m7g.xlarge" },
        { "InstanceType": "c7g.large"  }
      ]
    },
    "InstancesDistribution": {
      "OnDemandBaseCapacity":                0,
      "OnDemandPercentageAboveBaseCapacity": 30,
      "SpotAllocationStrategy":             "price-capacity-optimized",
      "SpotInstancePools":                  0
    }
  }
}
```

**The parameters explained:**
```
OnDemandBaseCapacity: 0
  Minimum On-Demand instances guaranteed regardless of the percentage split.
  0 = no guaranteed On-Demand floor; all base capacity can be Spot.
  Set to 2 if you need a minimum stable On-Demand baseline.

OnDemandPercentageAboveBaseCapacity: 30
  Above the base, 30% of capacity is On-Demand; 70% is Spot.
  If ASG has 10 instances: 3 On-Demand, 7 Spot.
  Adjust based on fault tolerance: 0% Spot = all On-Demand, 100% Spot = all Spot.

SpotAllocationStrategy: "price-capacity-optimized"
  AWS selects Spot pools (instance type + AZ combinations) that offer
  both low price and high available capacity.
  High available capacity → lower interruption probability.
  Alternative: "lowest-price" — picks cheapest pools; higher interruption risk.
  Alternative: "capacity-optimized" — maximizes available capacity, ignores price.

Overrides (instance type list):
  ASG can launch any of the listed types depending on availability and price.
  More instance types = more Spot pools = lower probability of all pools
  being reclaimed simultaneously (key resilience pattern).
  Rule of thumb: list 4–6 compatible instance types per ASG.
```

## Section 4: Spot Instances

**Q10. How do Spot Instances work, and what is the interruption model?**
A: Spot Instances are spare EC2 capacity that AWS sells at up to 90% discount compared to On-Demand pricing. The trade-off: AWS can reclaim Spot capacity with a 2-minute warning when that capacity is needed for On-Demand or Reserved Instance customers.

**The Spot capacity model:**
```
AWS maintains pools of spare capacity per instance type per AZ.
When AWS needs capacity back (e.g., spike in On-Demand demand for that pool):
  1. AWS sends a Spot Instance Interruption Notice
  2. The notice appears in the EC2 instance metadata at:
     http://169.254.169.254/latest/meta-data/spot/termination-time
  3. Also delivered as an EventBridge event: EC2 Spot Instance Interruption Warning
  4. 2 minutes after the notice: EC2 terminates the instance

Spot price:
  Fluctuates based on supply and demand per pool.
  You no longer set a maximum bid price (old model) — current model:
    Pay the current Spot price for the pool.
    Interruption probability is a function of capacity availability, not price.
    High available capacity → low interruption probability, not just low price.

Typical interruption frequencies by instance family (approximate):
  m-family, r-family large/xlarge: < 5% interruption rate per month (most pools)
  c-family: 5–15% depending on AZ and region
  Heavily contested pools: 10–20%+
  Check: EC2 Spot Instance Advisor (AWS console) for real-time interruption rates
```

**Handling Spot interruption in a NestJS service:**
```typescript
// Poll instance metadata for interruption notice (every 5 seconds)
// Or: use EventBridge rule → SNS/SQS → Lambda to handle the notice

async function pollSpotInterruptionNotice(): Promise<void> {
  const TOKEN_URL   = 'http://169.254.169.254/latest/api/token';
  const NOTICE_URL  = 'http://169.254.169.254/latest/meta-data/spot/termination-time';

  // Get IMDSv2 token
  const token = await fetch(TOKEN_URL, {
    method:  'PUT',
    headers: { 'X-aws-ec2-metadata-token-ttl-seconds': '60' },
  }).then(r => r.text());

  setInterval(async () => {
    const res = await fetch(NOTICE_URL, {
      headers: { 'X-aws-ec2-metadata-token': token }
    });

    if (res.status === 200) {
      const terminationTime = await res.text();
      logger.warn('Spot interruption notice received', { terminationTime });

      // 2 minutes remain — begin graceful shutdown immediately
      process.emit('SIGTERM'); // trigger NestJS graceful shutdown
      // NestJS drains in-flight requests, closes DB connections, etc.
    }
    // 404 = no interruption notice; continue polling
  }, 5_000);
}
```

**EventBridge-driven interruption handling (more reliable than polling):**
```
AWS emits:
  EventBridge event: aws.ec2 → EC2 Spot Instance Interruption Warning
  { "detail-type": "EC2 Spot Instance Interruption Warning",
    "detail": { "instance-id": "i-0abc...", "instance-action": "terminate" } }

EventBridge rule → Lambda:
  1. Deregister instance from ALB target group immediately
  2. Publish to SQS: "instance i-0abc is shutting down, redistribute its work"
  3. Notify Kafka consumers to rebalance
  4. Log the interruption for capacity planning

This approach is decoupled from the instance itself — it works even if the
instance process is too busy to poll metadata.
```

**Q11. What workloads are suitable for Spot, and which must use On-Demand?**
A: Spot interruption risk makes certain workloads unsuitable unless they are fully designed for arbitrary termination at any point.

**Suitable for Spot:**

```
Batch processing (ideal):
  NACH batch jobs, data transformation, report generation.
  Design: jobs are checkpointed; on interruption, the job resumes from
          the last checkpoint on another instance.
  Savings: 60–80% vs On-Demand for the same throughput.

Stateless web tier behind ALB:
  NestJS API servers in an ASG with On-Demand base capacity.
  On interruption: ALB deregisters the instance; ASG launches a replacement.
  Client requests get 2 minutes to drain; in-flight requests complete.
  Design requirement: application must handle SIGTERM gracefully.

CI/CD workers:
  GitHub Actions self-hosted runners, Jenkins agents, build workers.
  On interruption: build fails and retries on another instance.
  Acceptable: build retries are cheap; On-Demand for runners is expensive.

ML training with checkpointing:
  Long training jobs (hours/days) on GPU instances.
  Checkpoint every N steps to S3; on Spot interruption, restore from checkpoint.
  GPU Spot (p3, g4) is significantly cheaper than On-Demand.

Kafka consumers (stateless partition processing):
  On interruption: consumer leaves the consumer group; Kafka rebalances
  partitions to surviving consumers. Processing resumes within seconds.
  Design: idempotent message processing handles reprocessed messages
          from the last committed offset.
```

**Must use On-Demand:**

```
Databases (any stateful store):
  RDS, self-managed PostgreSQL, MongoDB, Redis with persistence.
  Interruption = data loss or corruption if writes are in-flight.
  Use Reserved Instances for databases (1-year or 3-year commitments;
  30–60% savings vs On-Demand without interruption risk).

ZooKeeper, etcd, Consul (coordination services):
  Quorum-based; losing a node unexpectedly can cause leader election storms.
  On-Demand with Reserved Instance pricing.

Primary Kafka brokers:
  Broker loss causes partition leadership elections and replication lag.
  Acceptable for dev/test Kafka; On-Demand for production brokers.

NAT Gateways, VPN instances:
  Network path for all outbound traffic; interruption drops all connections.
  Use AWS managed NAT Gateway (not EC2-based) for HA.

Anything with a minimum viable instance count < 3:
  If you have 2 instances and both are Spot, simultaneous interruption is
  possible (rare but non-zero). Set OnDemandBaseCapacity to match the
  minimum number of instances required for the service to function.
```

**Q12. What is the `price-capacity-optimized` Spot allocation strategy, and why is it better than `lowest-price`?**
A: When an ASG with a Mixed Instances Policy needs to launch a Spot instance, it must choose which pool (instance type + AZ combination) to use. The allocation strategy determines this choice.

**`lowest-price` (legacy, do not use for production):**
```
Selects the N cheapest Spot pools.
Problem: cheapest pools are cheap because they are heavily contested —
         many customers bid for the same capacity.
         Heavily contested = high interruption probability.
         You save 5% on the hourly rate; you pay with 3× more interruptions.

SpotInstancePools: 2 with lowest-price → picks 2 cheapest pools.
If both are the same popular instance type in the same AZ:
  Simultaneous mass interruption is highly probable during AWS capacity events.
```

**`capacity-optimized` (better, still suboptimal):**
```
Selects pools with the most available spare capacity.
High capacity = AWS has a lot of this type spare = they are unlikely to
reclaim it soon = low interruption probability.
Does not consider price — may pay more for the capacity stability.
```

**`price-capacity-optimized` (recommended):**
```
Balances both: finds pools that are both low-price AND high-capacity.
AWS internal algorithm selects the optimal pool from the overrides list.
SpotInstancePools: 0 must be set (ignored when using price-capacity-optimized).

Why this matters at scale:
  ASG with 4 instance type overrides × 3 AZs = 12 Spot pools available.
  price-capacity-optimized diversifies across pools automatically.
  If one pool is reclaimed, it switches to another from the override list.
  Multiple diverse instance types (m7g + m6g + c7g) have uncorrelated
  interruption events — a capacity crunch in m7g does not affect c7g pools.
```

**Q13. How do you size the On-Demand base capacity vs Spot percentage for a production web service?**
A: The correct split depends on your fault tolerance: how many instances can be simultaneously unavailable before the service degrades?

```
Example: NestJS API service, normal load requires 6 instances

Option A: All Spot (OnDemandBase=0, OnDemandPercent=0)
  Cost: minimum (~70% savings on all capacity)
  Risk: mass interruption event could simultaneously reclaim multiple instances
  Viable if: stateless, graceful degradation acceptable, rapid ASG replacement tolerable

Option B: On-Demand base for minimum viable capacity (recommended)
  OnDemandBaseCapacity:                2   ← 2 On-Demand always running
  OnDemandPercentageAboveBaseCapacity: 20  ← 20% of scale-out capacity is On-Demand

  At 6 instances: 2 On-Demand (base) + 1 On-Demand (20% of 4 above base) + 3 Spot
  Minimum viable even if all Spot interrupted: 3 On-Demand running
  Cost: ~50% savings vs all On-Demand

Option C: Conservative mix
  OnDemandBaseCapacity:                3
  OnDemandPercentageAboveBaseCapacity: 50
  At 6 instances: 3 On-Demand (base) + 1.5 On-Demand (50% of 3) ≈ 4 On-Demand, 2 Spot
  Minimum viable if Spot interrupted: 4 On-Demand
  Cost: ~20% savings vs all On-Demand

Decision rule:
  MinimumViableInstances = instances needed to handle 100% load at degraded perf
  Set OnDemandBaseCapacity = MinimumViableInstances
  Set OnDemandPercent = 0–30% based on cost vs reliability preference
  Everything above the base: maximize Spot for cost savings
```

## Section 5: Operational Concerns and Advanced Patterns

**Q14. How does AZ-aware scaling work, and what happens during an AZ failure?**
A: An ASG distributes instances across Availability Zones in its configured subnet list. The distribution goal is balance — the ASG tries to maintain an equal number of instances across AZs. During an AZ failure or capacity event, the ASG compensates by launching instances in remaining AZs.

**The AZ rebalancing mechanic:**
```
Normal state (MinSize=2, DesiredCapacity=6):
  AZ-a: 2 instances
  AZ-b: 2 instances
  AZ-c: 2 instances

AZ-b has a capacity event (Spot mass interruption, or AZ partial failure):
  AZ-b instances receive interruption notice → terminate
  ASG detects: desired=6, running=4; deficit=2
  ASG launches 2 new instances → places them in AZ-a and AZ-c (balanced)

  AZ-a: 3 instances
  AZ-b: 0 instances
  AZ-c: 3 instances

When AZ-b recovers:
  ASG rebalances: terminates one instance in AZ-a and one in AZ-c
  Launches 2 in AZ-b
  Returns to 2/2/2 distribution

The ALB side:
  ALB health checks detect AZ-b instances as unavailable → stops routing there
  Cross-zone load balancing (enabled on ALB by default) distributes traffic
  across all healthy instances in all AZs — surviving instances absorb AZ-b's load
```

**Configuring subnets for HA:**
```
Always configure ASG with subnets in at least 2 AZs (preferably 3).
Each subnet in its own AZ.
Private subnets for application instances (no direct internet access).
NAT Gateway in each AZ for outbound internet (one NAT per AZ avoids cross-AZ traffic).

Terraform:
  resource "aws_autoscaling_group" "api" {
    vpc_zone_identifier = [
      aws_subnet.private_a.id,
      aws_subnet.private_b.id,
      aws_subnet.private_c.id,
    ]
    # ASG distributes across all three subnets/AZs
  }
```

**Q15. What is the Warm Pool feature and when does it eliminate cold-start latency?**
A: A Warm Pool maintains a pool of pre-initialized EC2 instances in a stopped or running state, ready to be quickly added to the Auto Scaling Group when scaling out is needed. The instances in the warm pool have already completed UserData bootstrap — they do not need to download, install, or start the application when moved to InService.

```
Without Warm Pool — scale-out latency:
  CloudWatch alarm fires (CPU > 70%)
  │  ~1 minute (alarm evaluation period)
  ▼
  ASG launches new instance (pending)
  │  ~30–60 seconds (EC2 boot)
  ▼
  UserData runs (bootstrap):
  │  ~2–5 minutes (download packages, pull config, start app, health check passes)
  ▼
  Instance in service, ALB sends traffic
  Total: 3–7 minutes from alarm to instance serving traffic

With Warm Pool — scale-out latency:
  CloudWatch alarm fires
  │  ~1 minute
  ▼
  ASG moves pre-warmed instance from Warm Pool to InService
  │  ~30 seconds (instance start if stopped; ~10 seconds if running)
  ▼
  Instance in service
  Total: ~90 seconds from alarm to instance serving traffic
```

**Warm Pool configuration:**
```json
{
  "WarmPool": {
    "PoolState":                    "Stopped",
    "MinSize":                      2,
    "MaxGroupPreparedCapacity":     5,
    "InstanceReusePolicy": {
      "ReuseOnScaleIn": true
    }
  }
}
```

```
PoolState: Stopped
  Instances are stopped (no compute cost; EBS charges still apply).
  Start time ~30s when moved to InService.
  Choose Stopped to minimize cost when warm pool instances are rarely used.

PoolState: Running
  Instances are running (full compute cost).
  Move to InService in ~10 seconds.
  Choose Running when you need < 15 second scale-out response.

MinSize: 2
  Always maintain at least 2 instances in the warm pool.

MaxGroupPreparedCapacity: 5
  Total of InService + WarmPool instances never exceeds this.
  With DesiredCapacity=3: up to 2 instances in warm pool.

InstanceReusePolicy.ReuseOnScaleIn: true
  When ASG scales in (removes instances), return them to the warm pool
  instead of terminating. Avoids wasting the bootstrap cost.
```

**When Warm Pools matter for fintech:**
```
Scenario: NACH batch at 09:00 IST causes 3× traffic spike in 5 minutes.
  Without Warm Pool: ASG triggers scale-out; instances take 5+ minutes to bootstrap.
                     Batch traffic hits undersized fleet; latency spikes; timeouts.

  With Warm Pool:    2 pre-warmed instances move to InService in 30s.
                     Scale-out keeps up with the ramp; latency stays flat.

Combine with Scheduled Scaling:
  08:45 IST: scheduled scaling increases MinSize → ASG starts warming pool instances
  09:00 IST: batch traffic arrives; warm pool instances immediately available
  11:30 IST: batch ends; scale in; instances return to warm pool (ReuseOnScaleIn)
```

**Q16. What is the ASG instance refresh feature, and how does it enable zero-downtime deployments?**
A: Instance Refresh is ASG's native rolling replacement mechanism. When you update a Launch Template (new AMI, new UserData, new instance type), Instance Refresh replaces running instances with new instances launched from the updated template — in a controlled, rolling fashion that maintains application availability throughout.

```
Trigger:
  Update Launch Template to version 4 (new AMI with patched OS).
  Start Instance Refresh:
    MinHealthyPercentage: 80  ← keep at least 80% of instances healthy during refresh
    WarmupSeconds:        300 ← wait 5 min after new instance launches before replacing next batch

Refresh sequence (DesiredCapacity=10, MinHealthyPercentage=80%):
  Minimum healthy instances: 80% × 10 = 8

  Batch 1: terminate 2 instances → launch 2 new (with new template)
           Wait 300s for new instances to pass health check
           Running: 8 old + 2 new = 10 ✅ (8 healthy >= 8 minimum)

  Batch 2: terminate 2 more → launch 2 new
           Running: 6 old + 4 new = 10 ✅

  ... continues until all 10 instances are running the new Launch Template

  Total time: (10 / 2) × (launch time + WarmupSeconds) ≈ 5 × 6 min = 30 min

Rollback:
  If any instance fails health check during refresh:
    Instance Refresh can automatically roll back to the previous Launch Template version
    Requires: enabling automatic rollback in the refresh configuration
```

**Checkpointing Instance Refresh (canary pattern):**
```json
{
  "Preferences": {
    "MinHealthyPercentage":    90,
    "WarmupSeconds":           300,
    "CheckpointPercentages":   [10, 50],
    "CheckpointDelay":         3600
  }
}
```

```
CheckpointPercentages: [10, 50]
  Pause at 10% replacement: 1 out of 10 instances replaced → wait 3600s (1 hour)
  During pause: monitor error rates, latency, logs for the 1 new instance
  If acceptable: manually continue → refresh proceeds to 50% → pause again
  If problematic: cancel refresh → old instances still running; no user impact

This is the production canary pattern for high-risk changes (framework upgrades,
major dependency changes, new OS versions) where you want human verification
at each stage.
```

**Q17. "Design the compute layer for a multi-tenant NestJS API serving 500 req/s with burst to 5,000 req/s during business hours, with a 99.9% uptime SLA."**
A:

```
Requirements analysis:
  Normal: 500 req/s — baseline fleet
  Peak:   5,000 req/s — 10× burst; must scale in < 3 minutes
  SLA:    99.9% → 8.7 hours downtime/year; survive single AZ failure
  Cost:   minimize (fintech SaaS; margin matters)

Compute design:

Instance type: m7g.xlarge (4 vCPU, 16 GiB RAM, Graviton3)
  NestJS with pm2 cluster mode: 4 workers per instance
  Each worker: ~500 req/s comfortable (I/O-bound, async)
  Per instance capacity: ~1,500–2,000 req/s at 70% CPU
  At 500 req/s: 1 instance sufficient; run 2 for HA

ASG configuration:
  MinSize:         2   (one per AZ-a, AZ-b; survive AZ failure)
  MaxSize:         20  (5,000 req/s / 1,500 req/s per instance ≈ 4; 20 for headroom)
  DesiredCapacity: 2   (scaled by policy)
  Subnets:         private subnets in ap-south-1a, ap-south-1b, ap-south-1c

Mixed Instances Policy:
  Overrides:
    m7g.xlarge (primary)
    m6g.xlarge (fallback)
    m7g.2xlarge (fallback — different size for pool diversity)
    c7g.xlarge  (fallback — compute-optimized)
  OnDemandBaseCapacity:                2   ← 2 On-Demand always (HA floor)
  OnDemandPercentageAboveBaseCapacity: 20  ← 20% On-Demand above base
  SpotAllocationStrategy: price-capacity-optimized

Scaling policy:
  Target Tracking: ALBRequestCountPerTarget = 800 req/s
    At 500 req/s: 1 instance (below target; but MinSize=2 enforces 2)
    At 1,600 req/s: 2 instances (800 each)
    At 4,000 req/s: 5 instances (800 each)
    At 5,000 req/s: ~7 instances (scale-out in progress)

Scheduled scaling (NACH batch hours):
  08:45 IST Mon-Fri: MinSize = 6
  11:30 IST Mon-Fri: MinSize = 2
  Ensures capacity is pre-provisioned before batch, not scaling reactively

Warm Pool:
  PoolState: Stopped (minimize cost)
  MinSize:   2 (always 2 ready to move InService)
  With Warm Pool: scale-out to next 2 instances in ~30s vs ~5min without

Launch Template:
  UserData: pull config from SSM, start pm2, signal lifecycle hook
  IMDSv2: required
  EBS: gp3 30GiB encrypted
  IAM role: SSM read, CloudWatch put metrics, S3 read (app assets)

Lifecycle hooks:
  Launch:      wait for /health → 200 before marking InService
  Termination: drain ALB connections (300s delay) before terminating

Health checks:
  ALB: GET /health every 30s; 2 failures = unhealthy
  ASG: ELB health check type; grace period = 180s

Spot interruption handling:
  EventBridge rule: EC2 Spot Interruption Warning
  → Lambda: deregister from ALB → complete lifecycle
  Application: polls metadata every 5s; on notice, SIGTERM → graceful shutdown

SLA math:
  2 On-Demand instances across 2 AZs:
  Single AZ failure: 1 instance survives, handles degraded load
  Simultaneous dual-AZ failure: extremely unlikely (< 0.01% historical rate)
  Spot interruption: On-Demand base absorbs; ASG replaces Spot within 30s (Warm Pool)
  Target 99.95% availability achievable with this design
```

**Q18. "You add a new instance type to the Mixed Instances Policy overrides but Spot costs spike instead of decreasing. What's wrong?"**
A: Adding more instance types to overrides should increase Spot pool diversity and reduce interruptions — but if costs spike, the allocation strategy is likely selecting an expensive pool from the new type.

```
Diagnosis:

Step 1: Check which instance type is actually being launched
  aws ec2 describe-instances \
    --filters Name=tag:aws:autoscaling:groupName,Values=nestjs-api-asg \
    --query 'Reservations[].Instances[].[InstanceType,SpotInstanceRequestId]'

  If most instances are the new type → ASG is preferring it.

Step 2: Check the Spot price for the new instance type
  aws ec2 describe-spot-price-history \
    --instance-types m7i.xlarge \
    --product-descriptions Linux/UNIX \
    --start-time $(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%S)

  If price is higher than the previous types → SpotAllocationStrategy
  is selecting this pool despite higher price.

Step 3: Verify allocation strategy is not lowest-price
  aws autoscaling describe-auto-scaling-groups \
    --auto-scaling-group-names nestjs-api-asg \
    --query 'AutoScalingGroups[].MixedInstancesPolicy.InstancesDistribution'

  If SpotAllocationStrategy: "lowest-price" with SpotInstancePools: 1:
    Using lowest-price with 1 pool picks the single cheapest pool.
    If the new instance type's pool happens to be cheapest but has low capacity
    → high interruption rate, ASG constantly replacing instances → costs accumulate
    from launch overhead + per-second billing resets on every replacement.

Root causes:
  A) AllocationStrategy is price-capacity-optimized but the new type has
     high capacity in a more expensive pool → AWS picks it correctly (high capacity
     = low interruption) but it's genuinely more expensive per hour.
     Fix: remove the type from overrides if the cost is unacceptable.

  B) AllocationStrategy is lowest-price with SpotInstancePools: 1.
     The new type is cheapest but has high interruption rate.
     Each interruption: ASG launches a replacement; replacement is billed at
     minimum 1-minute; new instance bootstrap costs compute time.
     Net effect: lower hourly rate, higher actual cost from churn.
     Fix: switch to price-capacity-optimized; set SpotInstancePools: 0.

  C) The new instance type has a different vCPU:memory ratio.
     A m7i.2xlarge costs 2× per hour but doesn't deliver 2× capacity for
     your workload if it's memory-bound, not CPU-bound.
     Fix: ensure all override types are equivalent performance for your workload;
          use instance type equivalence (same vCPU and RAM class across families).

Fix:
  aws autoscaling update-auto-scaling-group \
    --auto-scaling-group-name nestjs-api-asg \
    --mixed-instances-policy '{
      "InstancesDistribution": {
        "SpotAllocationStrategy": "price-capacity-optimized",
        "SpotInstancePools": 0
      }
    }'
```

## The Core Mental Model

```
Instance type selection in three questions:
  1. What is the bottleneck? CPU → c family. Memory → r family. Both → m family.
  2. Is Graviton available for my software? If yes → add g modifier (m7g, r7g, c7g).
  3. Is load sustained or bursty? Sustained → fixed family (m/c/r). Bursty/test → t.

The T-series trap:
  t3 is cheap and looks fine in development.
  In production: credit exhaustion under sustained load → CPU throttled to 20%.
  The symptom (high latency, timeouts) looks like a DB or network problem.
  Monitor CPUCreditBalance; alarm at 20% of max balance.

Launch Template versioning discipline:
  ASG should reference $Default, not $Latest.
  Update the default version deliberately — not automatically on every template change.
  Use Instance Refresh with CheckpointPercentages for risky changes.
  IMDSv2 (HttpTokens: required) is non-negotiable for production templates.

Spot resilience comes from pool diversity, not price:
  More instance type overrides = more Spot pools = lower correlated failure risk.
  price-capacity-optimized picks pools with high available capacity = low interruption.
  lowest-price picks contested pools = high interruption = churn cost exceeds savings.
  OnDemandBaseCapacity = minimum instances needed if all Spot is reclaimed simultaneously.

The scaling latency chain:
  CloudWatch alarm evaluation: 1 minute (default period)
  EC2 launch: 30–60 seconds
  UserData / bootstrap: 2–5 minutes
  Total without Warm Pool: 3–7 minutes
  With Warm Pool: ~90 seconds
  For traffic ramps > 3× in < 3 minutes: Warm Pool + Scheduled Scaling is required.

Graceful shutdown is the contract between ASG and application:
  Lifecycle hook (TERMINATING) → ALB drain → SIGTERM → app finishes in-flight →
  complete-lifecycle-action CONTINUE → EC2 terminates.
  Any link broken = dropped requests = 5xx errors during deployments and scale-in.
  NestJS: app.enableShutdownHooks() + onApplicationShutdown() in each module.

Reserved Instances / Savings Plans for stable baseline:
  Stateful services (PostgreSQL, Redis, Kafka brokers) never use Spot.
  On-Demand for these is expensive at 8,760 hours/year.
  1-year Reserved Instance: 30–40% savings. 3-year: 50–60%.
  Savings Plans (Compute): same discounts, flexible across instance families/regions.
  Rule: if an instance runs > 6,000 hours/year, buy Reserved or Savings Plan.
```

The fintech callout: for NACH batch processing and KYC pipeline workloads, Spot with checkpoint-based job design delivers 60–80% compute cost reduction without reliability compromise — the key design requirement is that every unit of work is idempotent and resumable from the last checkpoint, so a Spot interruption causes a retry, not data loss.
