# GitLab CI: `.gitlab-ci.yml`, Stages, Artifacts, Caching — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is GitLab CI/CD, and how does it differ from GitHub Actions architecturally?**
A: GitLab CI/CD is GitLab's built-in automation platform where pipelines are defined in a single `.gitlab-ci.yml` file at the repo root. The core architectural difference from GitHub Actions is the execution model: GitLab uses **Runners** (registered agents) that poll GitLab for jobs, whereas GitHub Actions provisions ephemeral VMs per job. GitLab pipelines are also more opinionated — the `stages` array enforces a global execution order across all jobs, whereas GitHub Actions has no concept of stages natively (only `needs:` dependencies per job).

**Q2. What is `.gitlab-ci.yml`, and where must it live?**
A: `.gitlab-ci.yml` is the single pipeline definition file that GitLab reads automatically on every push. It must live at the **root of the repository**. It defines stages, jobs, variables, caching, artifacts, rules, and runner selection. Unlike GitHub Actions (which allows multiple workflow files under `.github/workflows/`), GitLab CI has one canonical file per project — though it can include other YAML files via the `include:` keyword to split config across files.

**Q3. What is a pipeline in GitLab CI?**
A: A pipeline is the top-level CI/CD execution unit — a collection of jobs grouped into stages, triggered by an event (push, merge request, schedule, API, etc.). Every pipeline has a unique ID, a ref (branch/tag), and a status (running, passed, failed, canceled). Pipelines are visualized in GitLab's UI as a DAG or stage-based waterfall graph.

**Q4. What is a job in GitLab CI?**
A: A job is the atomic unit of work in a pipeline — a named block in `.gitlab-ci.yml` that defines a `script:` (shell commands), which `stage:` it belongs to, and optionally rules, artifacts, caching, and runner tags. Each job runs in its own isolated environment (container or VM) on a Runner. Jobs within the same stage run in parallel.

**Q5. What triggers a GitLab CI pipeline?**
A: Pipelines are triggered by:
- **Push events** — any branch push (default).
- **Merge requests** — via `rules: - if: $CI_PIPELINE_SOURCE == 'merge_request_event'`.
- **Schedules** — cron-based, configured in GitLab UI under CI/CD → Schedules.
- **Manual triggers** — `when: manual` on a job, or the "Run pipeline" button in the UI.
- **API** — `POST /projects/:id/pipeline`.
- **Upstream pipelines** — via `trigger:` keyword (multi-project pipelines).
- **Parent-child pipelines** — a job generates a child pipeline YAML dynamically.

**Q6. What is a Runner, and how does it relate to a job?**
A: A Runner is an agent (process) registered with GitLab that picks up and executes jobs. GitLab offers **shared runners** (managed by GitLab.com, available to all projects) and **self-managed runners** (registered by you against a specific group or project). Runners are matched to jobs via **tags** — a job with `tags: [docker, prod]` only runs on Runners registered with those tags. Runners support multiple executors: `docker`, `shell`, `kubernetes`, `virtualbox`, etc.

## Section 2: Stages

**Q7. What are stages, and how do they control pipeline execution order?**
A: Stages define a global ordered sequence of execution phases. All jobs in stage N must complete successfully before any job in stage N+1 starts. You declare the order at the top of `.gitlab-ci.yml`:
```yaml
stages:
  - build
  - test
  - deploy
```
Jobs are assigned to a stage via the `stage:` key. Jobs sharing the same stage run in parallel. This is the primary execution ordering mechanism in GitLab CI — it's coarser than GitHub Actions' per-job `needs:` DAG but simpler to reason about.

**Q8. What happens if you don't define `stages:` in `.gitlab-ci.yml`?**
A: GitLab uses a default set of stages: `.pre`, `build`, `test`, `deploy`, `.post`. Jobs that don't specify a `stage:` are assigned to `test` by default. `.pre` always runs first (before any user-defined stage) and `.post` always runs last — these are useful for setup/teardown jobs regardless of custom stage order.

**Q9. What happens when a job in a stage fails?**
A: By default, all subsequent stages are blocked — no jobs from later stages run. Jobs already running in the same stage continue to completion. You can override this with:
- `allow_failure: true` — the job can fail without blocking the pipeline.
- `when: on_failure` — run a job specifically when a prior stage failed (e.g., notification jobs).
- `needs:` with `optional: true` — fine-grained dependency control bypassing stage blocking.

**Q10. Can you bypass stage ordering and run jobs out of sequence?**
A: Yes — using the `needs:` keyword, a job can declare explicit dependencies on other specific jobs rather than waiting for its entire stage. This enables a DAG (Directed Acyclic Graph) pipeline within GitLab, allowing jobs from "later" stages to start as soon as their specific dependencies complete, without waiting for all jobs in the prior stage:
```yaml
deploy-frontend:
  stage: deploy
  needs: [build-frontend]   # doesn't wait for build-backend to finish
```
This is called **DAG pipelines** in GitLab and significantly reduces end-to-end pipeline time.

**Q11. What is the difference between `when: always`, `when: on_failure`, and `when: on_success`?**
A:
- `when: on_success` (default) — job runs only if all prior jobs in the pipeline succeeded.
- `when: on_failure` — job runs only if at least one prior job failed. Common for alerting/cleanup.
- `when: always` — job runs regardless of prior job status. Used for teardown steps that must execute no matter what.
- `when: manual` — job is created but paused; a human must click "Play" in the GitLab UI to trigger it.
- `when: delayed` — job starts after a `start_in:` delay (e.g., for canary deployments with a wait period before rollout).

## Section 3: Artifacts

**Q12. What are artifacts in GitLab CI, and what problem do they solve?**
A: Artifacts are files or directories that a job produces and uploads to GitLab at the end of its execution. They solve the problem of sharing output between jobs across different stages/runners — since each job runs on an isolated environment, files don't persist automatically. GitLab stores artifacts centrally and makes them downloadable via the UI or available to downstream jobs.

**Q13. How do you define artifacts in a job?**
A:
```yaml
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
      - build-report.html
    expire_in: 7 days
```
`paths:` specifies what to upload. `expire_in:` controls retention (default varies by GitLab config; omitting it may keep artifacts indefinitely on self-managed). Artifacts are uploaded even if the job fails unless you add `when: on_success`.

**Q14. How do downstream jobs consume artifacts from upstream jobs?**
A: By default, jobs automatically download artifacts from all jobs in prior stages. You can be explicit about which artifacts to pull using `dependencies:`:
```yaml
deploy:
  stage: deploy
  dependencies:
    - build        # only download artifacts from the 'build' job
  script:
    - aws s3 sync dist/ s3://my-bucket
```
Setting `dependencies: []` (empty list) means the job downloads no artifacts — useful for jobs that don't need prior outputs and should start faster.

**Q15. What is the difference between `artifacts` and `cache` in GitLab CI?**
A:
| | Artifacts | Cache |
|---|---|---|
| **Purpose** | Pass outputs between jobs/stages | Speed up jobs by reusing downloaded deps |
| **Storage** | GitLab server (always uploaded) | Runner-local or distributed cache (may be absent) |
| **Guarantee** | Guaranteed available to downstream jobs | Best-effort; cache miss is handled gracefully |
| **Typical content** | Build outputs, test reports, binaries | `node_modules`, pip packages, Maven `.m2` |
| **Expiry** | Configurable via `expire_in` | Configurable via `cache.policy` and TTL |
| **Cross-pipeline** | Available across pipelines | Available across pipelines (same Runner/cache key) |

The mental model: **artifacts are the output of your work; cache is the scaffolding to do the work faster.**

**Q16. What are `artifacts:reports`, and why are they special?**
A: `artifacts:reports` is a set of structured artifact types that GitLab understands natively and renders in the UI:
```yaml
test:
  script: npm test -- --coverage
  artifacts:
    reports:
      junit: junit-report.xml      # test results shown inline on MR
      coverage_report:
        coverage_format: cobertura
        path: coverage/cobertura-coverage.xml
```
Other report types: `sast`, `dast`, `dependency_scanning`, `terraform`, `dotenv`. These integrate with GitLab's Security Dashboard, MR widgets, and compliance features — you get inline test failure annotations on the MR diff without writing any custom integration.

**Q17. How do you pass variables between jobs using artifacts?**
A: Use `artifacts:reports:dotenv` — a special report type that exports key=value pairs as CI variables available to downstream jobs:
```yaml
build:
  script:
    - echo "IMAGE_TAG=$(git rev-parse --short HEAD)" >> build.env
  artifacts:
    reports:
      dotenv: build.env

deploy:
  needs: [build]
  script:
    - echo "Deploying image $IMAGE_TAG"   # IMAGE_TAG is available here
```
This is the canonical GitLab pattern for passing dynamic values (e.g., a generated image tag) between jobs without hardcoding.

## Section 4: Caching

**Q18. How does caching work in GitLab CI?**
A: Cache is defined per job with a `key` (determines cache identity) and `paths` (what to cache). Before the job script runs, the Runner tries to restore the cache matching the key. After the script, it uploads the cache:
```yaml
install-deps:
  script: npm ci
  cache:
    key: $CI_COMMIT_REF_SLUG-node
    paths:
      - node_modules/
```
Cache is stored on the Runner's local filesystem (for shell/docker executors) or in a distributed object store (S3, GCS) for Kubernetes runners. Unlike artifacts, a cache miss doesn't fail the job — the script just runs without the cache.

**Q19. What is the `cache:key` and what are good strategies for it?**
A: The `cache:key` is a string that identifies a cache bucket. Same key = shared cache. Different keys = separate caches. Common strategies:
- `$CI_COMMIT_REF_SLUG` — per-branch cache (branches don't share, so a feature branch starts fresh).
- `$CI_COMMIT_REF_SLUG-$CI_JOB_NAME` — per-branch-per-job (prevents job A from polluting job B's cache).
- `key: files: [package-lock.json]` — cache key derived from file hash; busts automatically when lockfile changes.
```yaml
cache:
  key:
    files:
      - package-lock.json
  paths:
    - node_modules/
```
The `key.files` form is the most robust for dependency caching — identical to the `hashFiles()` pattern in GitHub Actions.

**Q20. What is `cache:policy`, and when would you set it to `pull` or `push`?**
A: By default (`policy: pull-push`), a job restores the cache before running and uploads it after. This is wasteful when many jobs use the same cache but don't modify it:
- **`policy: pull`** — restore the cache but don't upload it afterward. Use on consumer jobs (e.g., `test`, `lint`) that only read `node_modules`.
- **`policy: push`** — don't restore; only upload. Use on the single job responsible for populating the cache (e.g., `install-deps`).
- **`policy: pull-push`** (default) — restore and upload. Use only for the job that may update the cache.

This pattern — one `push` job and many `pull` jobs — significantly reduces cache upload traffic and Runner overhead.

**Q21. Can cache be shared across branches and pipelines?**
A: Yes, if they share the same `cache:key`. A key with `$CI_COMMIT_REF_SLUG` is branch-scoped (no sharing). Omitting branch-specific variables makes the key global — useful for slow-changing dependencies (e.g., OS-level packages) that all branches can share. The risk is cache poisoning: if one branch corrupts the cache (e.g., installs a bad package), all branches are affected. Branch-scoped keys are safer for application dependencies.

**Q22. How does caching work on Kubernetes runners, and what's different?**
A: Kubernetes runners run each job in a fresh pod, so there's no local filesystem to persist cache between runs. Cache must be configured with a **distributed cache backend** (S3, GCS, or Azure Blob) in the Runner's `config.toml`. The Runner uploads/downloads the cache as a tar archive to/from object storage. This is more reliable at scale but adds latency — a `node_modules` cache of 500MB takes several seconds to download even from S3 in the same region. Minimizing cache size (e.g., excluding `.cache/` subdirs within `node_modules`) matters more in this setup.

## Section 5: Rules, Variables & Advanced Patterns

**Q23. What is the `rules:` keyword, and how does it replace `only/except`?**
A: `rules:` is the modern, expressive way to control when a job runs. It evaluates a list of conditions top-to-bottom and applies the first match:
```yaml
deploy-prod:
  rules:
    - if: $CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "push"
      when: on_success
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: never
    - when: manual
```
`only/except` (legacy) was limited to branch/tag patterns and couldn't combine multiple conditions. `rules:` supports arbitrary CI variable expressions, file path changes (`changes:`), and `exists:` checks — making it substantially more powerful.

**Q24. How do you run a job only when specific files change?**
A: Use `rules: changes:`:
```yaml
frontend-build:
  rules:
    - changes:
        - frontend/**/*
        - package.json
  script: npm run build:frontend
```
If none of the listed paths changed relative to the previous commit, the job is skipped. This is the GitLab equivalent of GitHub Actions' `on.push.paths` filter and is essential for monorepos to avoid running all jobs on every change.

**Q25. What are CI/CD variables in GitLab, and how are they scoped?**
A: Variables are key-value pairs injected into job environments. Scoping levels (highest precedence first):
1. **Trigger/pipeline variables** — passed via API or `trigger:variables`.
2. **Job-level `variables:`** — defined inside a specific job block.
3. **`.gitlab-ci.yml` top-level `variables:`** — global to all jobs in the file.
4. **Group/Project CI/CD settings** — defined in GitLab UI; can be masked (redacted from logs) and protected (only available on protected branches).
5. **Predefined variables** — GitLab-injected (`$CI_COMMIT_SHA`, `$CI_JOB_NAME`, `$CI_REGISTRY_IMAGE`, etc.).

**Q26. What is `include:` and how do you use it to modularize a large `.gitlab-ci.yml`?**
A: `include:` lets you pull in YAML from other files — local, remote, or from GitLab's CI Component Catalog:
```yaml
include:
  - local: '.gitlab/ci/build.yml'
  - local: '.gitlab/ci/deploy.yml'
  - project: 'my-org/shared-ci'
    ref: main
    file: '/templates/docker-build.yml'
  - template: 'Security/SAST.gitlab-ci.yml'   # GitLab-managed template
```
This is the GitLab equivalent of reusable workflows. Large teams typically split `.gitlab-ci.yml` into per-concern files (build, test, security, deploy) and include them from a root file. `include:` files are merged at pipeline creation time — there's no runtime indirection.

**Q27. What are `extends:` and YAML anchors, and when do you use each?**
A: Both reduce duplication.
- **`extends:`** — GitLab-native inheritance; a job can extend a hidden job (prefixed with `.`) to inherit its config, with the child overriding specific keys:
```yaml
.base-deploy:
  image: alpine
  before_script:
    - apk add curl

deploy-staging:
  extends: .base-deploy
  script: ./deploy.sh staging

deploy-prod:
  extends: .base-deploy
  script: ./deploy.sh prod
```
- **YAML anchors (`&`, `*`, `<<`)** — standard YAML feature for referencing and merging blocks. Less readable than `extends:` for deep merges; prefer `extends:` for job inheritance. Anchors are useful for small reusable config fragments (e.g., a shared `retry:` block).

## Section 6: Multi-Project & Parent-Child Pipelines

**Q28. What is a multi-project pipeline, and when would you use it?**
A: A multi-project pipeline triggers a pipeline in a different GitLab project from within a job using `trigger:`:
```yaml
trigger-deploy:
  trigger:
    project: my-org/infrastructure
    branch: main
    strategy: depend   # wait for downstream pipeline to complete
```
Use this for: deploying infrastructure from a separate IaC repo after an app build, triggering downstream service pipelines in a microservices architecture, or enforcing separation between code repos and deployment repos (common in regulated environments).

**Q29. What is a parent-child pipeline, and how does it differ from multi-project?**
A: A parent-child pipeline generates a child pipeline YAML dynamically within the same project:
```yaml
generate-pipeline:
  script: ./scripts/generate-ci.py > generated-pipeline.yml
  artifacts:
    paths: [generated-pipeline.yml]

trigger-child:
  trigger:
    include:
      - artifact: generated-pipeline.yml
        job: generate-pipeline
    strategy: depend
```
Unlike multi-project pipelines (cross-repo), parent-child pipelines stay within the same project. They're useful for monorepos where a script determines which subset of services need to be built/tested based on changed files, dynamically generating a minimal pipeline rather than running every job every time.

## Section 7: Scenario Questions

**Q30. "Your pipeline takes 25 minutes end-to-end. How do you analyze and reduce it?"**
A: Systematic approach:
1. **Profile** — use GitLab's pipeline duration graph and job timing breakdown to find the slowest jobs.
2. **Parallelize within stages** — ensure slow test suites are split across parallel jobs using `parallel:` or matrix-style job splitting.
3. **Use `needs:` (DAG)** — if `deploy-frontend` doesn't need `build-backend`, wire `needs:` so it starts immediately rather than waiting for the full stage.
4. **Cache dependencies** — if `npm ci` takes 3 minutes on every job, fix caching with a `key.files` strategy.
5. **Skip unchanged work** — use `rules: changes:` to skip frontend jobs when only backend files changed.
6. **Reduce artifact size** — large artifacts slow upload/download between stages; be specific with `artifacts.paths`.

**Q31. "How would you structure GitLab CI for a NestJS backend with staging and production deployments, with manual gate before prod?"**
A: Typical structure:
```
stages: [build, test, review, deploy-staging, deploy-prod]

build       → builds Docker image, pushes to GitLab Container Registry with $CI_COMMIT_SHORT_SHA tag
lint/test   → parallel jobs in test stage; artifacts:reports:junit for MR inline test results
deploy-staging → rules: main branch only; deploys to staging K8s namespace; smoke test job after
deploy-prod    → rules: main branch only; when: manual; environment: production; deploys with same image tag
```
The `when: manual` on `deploy-prod` creates a gated job — the pipeline passes staging automatically but waits for a human click before touching prod. Combine with GitLab Environments and deployment tracking for full audit trail.

**Q32. "A job intermittently fails due to a flaky external API call. How do you handle it in `.gitlab-ci.yml`?"**
A: Use `retry:`:
```yaml
integration-test:
  script: npm run test:integration
  retry:
    max: 2
    when:
      - script_failure
      - runner_system_failure
```
`retry.when` scopes retries to specific failure types — `script_failure` catches non-zero exit codes, while `runner_system_failure` handles infrastructure issues. Setting `max: 2` means the job gets up to 3 total attempts. For flakiness at the test level (not job level), consider a test retry flag in the test runner itself (e.g., `jest --retryTimes 2`) rather than retrying the entire job.

**Q33. "How do you securely manage production credentials in GitLab CI?"**
A: Layered approach:
- Store secrets as **masked + protected** CI/CD variables in GitLab project settings. Masked = redacted from logs. Protected = only available on protected branches (e.g., `main`).
- Use **environment-scoped variables** — a variable scoped to `production` environment is only injected into jobs targeting that environment.
- Prefer **OIDC / short-lived credentials** — GitLab supports ID token-based OIDC auth with AWS, GCP, Azure, and Vault. The job requests a JWT (`$CI_JOB_JWT_V2`) and exchanges it for cloud credentials, eliminating static long-lived keys entirely.
- Restrict access: use **protected runners** (tagged runners that only accept jobs from protected branches) so prod deployments physically can't run on feature branch pipelines.

**Q34. "How do you handle a monorepo with 5 services where you only want to build/test changed services?"**
A: Two complementary techniques:
1. **`rules: changes:`** per job — each service's build/test job has `rules: changes: [services/service-a/**]`. Works well for a small number of services.
2. **Dynamic child pipelines** — a root job runs a script that inspects `git diff` to determine changed services, generates a minimal `.gitlab-ci.yml` on the fly, and triggers it as a child pipeline. This scales better for 10+ services and gives full flexibility in the generated YAML (matrix jobs, environment-specific rules).
For NestJS microservices, option 1 is usually sufficient; option 2 is warranted when shared library changes need impact analysis to determine which services to rebuild.

| Job                      | Named unit with `script:`; assigned to a stage; parallel within same stage              |
| `needs:`                 | DAG override — job starts when its specific dependencies finish, bypassing stage wait    |
| Runner                   | Agent that executes jobs; matched via `tags:`; shared or self-managed                   |
| Artifacts                | Job outputs uploaded to GitLab; consumed by downstream jobs; expire via `expire_in`     |
| `artifacts:reports`      | Structured types (junit, cobertura, sast); rendered natively in GitLab MR UI            |

| Cache                    | Dependency reuse across runs; best-effort (miss is not a failure)                       |
| `cache:key.files`        | Hash-based cache key; auto-busts when lockfile changes                                  |
| `cache:policy`           | `pull` (read-only), `push` (write-only), `pull-push` (default)                          |
| `rules:`                 | Modern conditional job execution; replaces `only/except`                                |
| `rules: changes:`        | Skip job if specified paths didn't change — essential for monorepos                     |
| `when: manual`           | Job created but paused; human must click Play — GitLab's approval gate mechanism        |
| `include:`               | Compose pipeline from multiple YAML files; enables reusable CI templates                |
| `extends:`               | Job inheritance from hidden (`.`) jobs; cleaner than YAML anchors for complex configs   |
| Multi-project pipeline   | `trigger: project:` — triggers a pipeline in another GitLab repo                        |
| Parent-child pipeline    | Dynamically generated child pipeline in the same project — ideal for monorepos          |
| Protected variables      | Only injected on protected branches; pair with protected runners for prod safety         |
| OIDC / ID Token          | Short-lived cloud creds via JWT; preferred over static secret variables                 |

**Tip for the interview:** At 5 YOE, interviewers in a fintech context will probe your judgment on two things: **security** (how you prevent credential leakage, especially the difference between masked vs. protected variables, and why OIDC beats static keys) and **pipeline efficiency at scale** (cache policy design, DAG vs. stage ordering trade-offs, monorepo job skipping). Have a concrete example of a pipeline you owned — including a failure mode you debugged (flaky cache, artifact size blowup, stage blocking an unrelated deploy) — and what you changed to fix it.
