# Deployment Strategies: Blue-Green, Canary, Rolling — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a deployment strategy, and why does the choice matter?**
A: A deployment strategy is the mechanism by which a new version of software replaces the old version in a live environment. The choice matters because it directly governs three competing concerns: **downtime** (does traffic get dropped during the switch?), **blast radius** (if the new version is broken, how many users are affected before you catch it?), and **rollback speed** (how quickly can you get back to the known-good state?). A team that ships to production ten times a day needs a different strategy than one doing monthly releases — and a payment processing service with zero-downtime SLAs has different constraints than an internal admin dashboard.

**Q2. What is a "deployment" vs a "release" — are they the same thing?**
A: Not necessarily. A deployment is the act of placing a new version of code onto servers. A release is the act of making that version available to users. Modern deployment strategies deliberately decouple the two:
- **Feature flags** — deploy code to all servers but release the feature to 1% of users.
- **Blue-green** — deploy to the green environment (offline), then release by flipping the load balancer.
- **Canary** — deploy to 5% of servers, release to 5% of traffic, observe, then release to 100%.

Decoupling deployment from release is a core principle of continuous delivery — it removes the big-bang risk of "deploy = immediate impact on all users."

**Q3. What are the key dimensions to evaluate when comparing deployment strategies?**
A:
- **Downtime** — does the strategy require any period where the service is unavailable?
- **Blast radius** — what percentage of users are exposed to a bad deployment before rollback?
- **Rollback speed** — how fast can you revert to the previous version? Seconds (flip LB)? Minutes (re-deploy old image)? Hours (re-run migration)?
- **Infrastructure cost** — does the strategy require running duplicate capacity?
- **Complexity** — what tooling, traffic routing, and observability do you need to operate it?
- **Schema compatibility** — does the strategy require backward-compatible DB schema changes during the transition period?
- **Observability requirements** — canary requires metrics/alerting to compare old vs new; recreate doesn't.

**Q4. What is the "recreate" strategy, and when is it acceptable?**
A: Recreate (also called "stop-start") terminates all instances of the old version, then starts all instances of the new version. It is the simplest possible strategy and causes guaranteed downtime during the gap. Acceptable when:
- The service has a scheduled maintenance window and SLA permits downtime.
- The application is stateful in a way that makes running old and new versions simultaneously impossible (e.g., a schema migration that's incompatible with the old code).
- It's an internal tool, batch processor, or non-customer-facing service where brief downtime is tolerable.
- The team is early-stage and operational simplicity matters more than availability.

It is never acceptable for a customer-facing fintech service with an availability SLA.

**Q5. What is the relationship between deployment strategy and database schema changes?**
A: Database schema changes are the hardest constraint on deployment strategy choice. Unlike stateless application code, the database is shared — both old and new versions of the application read from and write to the same schema during a rolling or canary deployment. This means:
- **Additive changes** (new columns, new tables) are safe — old code ignores new columns; new code uses them.
- **Destructive changes** (drop column, rename column, change type) require a multi-release approach: release new code that doesn't use the old column, verify no traffic reads it, then drop it in a subsequent release.
- **Blue-green** reduces (but doesn't eliminate) this window — if the cutover is instantaneous, old code never sees the new schema. But if the rollback requires reverting the schema too, you're in trouble.

The expand-contract pattern (also called parallel change) is the canonical technique: expand the schema (add new), migrate data, contract the schema (remove old) across separate releases.

## Section 2: Rolling Deployment

**Q6. What is a rolling deployment?**
A: A rolling deployment replaces instances of the old version gradually — one batch at a time — while keeping the rest serving traffic. At no point during the rollout are all instances simultaneously taken down. A typical rollout on 10 instances at 25% batch size:
1. Take 2–3 instances out of the load balancer, deploy new version, health-check, add back.
2. Repeat for the next 2–3 instances.
3. Continue until all instances run the new version.

Throughout the rollout, both old and new versions run simultaneously and serve live traffic. This is the default strategy in Kubernetes (`RollingUpdate` is the default `Deployment` strategy).

**Q7. What are `maxUnavailable` and `maxSurge` in a Kubernetes rolling deployment?**
A: These two parameters control the rollout pace in a Kubernetes `Deployment`:
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1    # max pods that can be unavailable at any time
    maxSurge: 1          # max pods above desired count during rollout
```
- **`maxUnavailable`** — how many old pods can be taken down before new ones are ready. `0` means capacity is never reduced (requires `maxSurge > 0`).
- **`maxSurge`** — how many extra pods can exist above the desired replica count during rollout. Enables bringing new pods up before old ones are taken down.

Example: 10 replicas, `maxUnavailable: 2`, `maxSurge: 2` — at peak rollout, 12 pods exist (10 desired + 2 surge), and 2 old pods are being terminated. The rollout proceeds in waves of 2. Setting both to `0` is invalid.

**Q8. What are the risks of running two versions simultaneously during a rolling deployment?**
A: The dual-version window introduces several risks:
- **API incompatibility** — if v2 changes a request/response format and v1 and v2 talk to each other (microservices), requests can fail during the rollout window. Requires backward-compatible API changes across at least one release cycle.
- **Schema incompatibility** — v1 writing data in the old format while v2 expects the new format, or v2 writing new fields that v1 doesn't know about. Requires the expand-contract pattern.
- **Session affinity** — if a user's session hits v1 for one request and v2 for the next, inconsistent behavior can occur. Requires sticky sessions or stateless session design.
- **Inconsistent feature availability** — users may get different UI or behavior depending on which pod serves them mid-rollout.

**Q9. How does Kubernetes detect that a new pod is ready to receive traffic during a rolling update?**
A: Via **readiness probes**. A pod is not added to the Service's endpoint list (not sent traffic) until its readiness probe returns success. Configured per container:
```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 3000
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 3
```
The probe endpoint should verify the application is truly ready — DB connection established, cache warmed, config loaded — not just that the process started. A readiness probe that returns 200 before the app can actually serve requests causes traffic to be routed to a not-yet-ready pod, manifesting as errors during the rollout window.

**Q10. How do you roll back a Kubernetes rolling deployment?**
A: Kubernetes tracks `Deployment` revision history. Rollback is a first-class operation:
```bash
# View rollout history
kubectl rollout history deployment/my-service

# Roll back to the previous revision
kubectl rollout undo deployment/my-service

# Roll back to a specific revision
kubectl rollout undo deployment/my-service --to-revision=3

# Watch rollback progress
kubectl rollout status deployment/my-service
```
Under the hood, `undo` triggers a new rolling update — replacing new pods with the old image. The rollback takes approximately the same time as the original rollout. If you need an instantaneous rollback, rolling is not the right strategy — blue-green gives you a sub-second flip.

**Q11. What is a `Deployment` pause/resume in Kubernetes, and when would you use it?**
A: You can pause a Kubernetes rollout mid-way, effectively freezing it at a partial rollout state:
```bash
kubectl rollout pause deployment/my-service
# inspect metrics, test the partially rolled-out pods
kubectl rollout resume deployment/my-service
```
Use cases: manual canary-like validation at a fixed percentage (pause at 20% rollout, observe error rates for 30 minutes, resume if healthy), or stopping a rollout when you notice elevated errors before it completes. This is an escape hatch — proper canary tooling (Argo Rollouts, Flagger) is more robust for this use case.

## Section 3: Blue-Green Deployment

**Q12. What is a blue-green deployment?**
A: Blue-green maintains two identical production environments — "blue" (current live) and "green" (new version, idle). The new version is fully deployed and verified in the green environment before any production traffic touches it. Cutover is a single atomic operation — redirecting the load balancer or DNS from blue to green. At the moment of cutover, 100% of traffic shifts from old to new. Blue remains running, enabling instant rollback by flipping back.

```
                 ┌─────────────┐
Users → LB ────▶│  Blue (v1)  │  ← live traffic
                 └─────────────┘
                 ┌─────────────┐
                 │ Green (v2)  │  ← deployed, tested, idle
                 └─────────────┘

After cutover:
                 ┌─────────────┐
                 │  Blue (v1)  │  ← idle (rollback target)
                 └─────────────┘
                 ┌─────────────┐
Users → LB ────▶│ Green (v2)  │  ← now live
                 └─────────────┘
```

**Q13. What are the key advantages of blue-green over rolling?**
A:
- **Zero downtime** — the cutover is instantaneous; no period where capacity is reduced.
- **No dual-version window** — at any moment, 100% of traffic hits either v1 or v2, never a mix. Eliminates API/schema compatibility concerns during the transition.
- **Instant rollback** — flipping back to blue takes seconds, not the minutes required for a rolling re-deployment of the old image.
- **Full pre-production validation** — the green environment runs at full scale with production configuration before receiving any real traffic. You can run smoke tests, load tests, and security checks against green before the cutover.
- **Clean audit trail** — in regulated environments, the cutover event is a discrete, auditable moment with a clear before/after state.

**Q14. What are the costs and limitations of blue-green?**
A:
- **Infrastructure cost** — you maintain two full production environments simultaneously. For large fleets, this can double compute cost during the deployment window. Mitigated by auto-scaling down blue post-cutover, but the spike cost exists.
- **Database coupling** — if both blue and green share the same database (the typical setup), schema changes must still be backward-compatible during the cutover window. Blue-green doesn't eliminate schema migration complexity — it reduces the dual-version window to the cutover duration, but a rollback still requires the old code to work against the (possibly migrated) schema.
- **Stateful sessions** — if users have in-flight sessions pinned to blue pods (websockets, long-lived connections), the cutover will drop them. Requires session externalization (Redis) or graceful connection draining.
- **Environment drift** — green and blue can drift in configuration if not managed carefully. Infrastructure-as-code (Terraform, Helm) applied identically to both is mandatory.
- **Warm-up time** — green pods need to fully start, warm caches, and establish connections before the cutover. A premature cutover routes traffic to a cold environment.

**Q15. How is blue-green implemented in Kubernetes?**
A: Several patterns exist:
- **Two Deployments + Service selector swap** — deploy v2 as a separate Deployment (`my-service-green`), run smoke tests, then patch the Service selector to point at the green pods:
```bash
kubectl patch service my-service \
  -p '{"spec":{"selector":{"version":"green"}}}'
```
Rollback: patch selector back to `blue`. Simple, no extra tooling.

- **Ingress weight-based switching** — use an Ingress controller (NGINX, Traefik) with weight annotations. Set green weight to 100, blue to 0.

- **AWS with ALB/ECS** — ALB listener rules swap target groups. ECS has a native blue-green deployment type integrated with CodeDeploy.

- **Argo Rollouts** — `BlueGreen` rollout strategy with `autoPromotionEnabled: false` for manual gate before cutover; integrates with analysis runs for automated promotion criteria.

**Q16. How do you implement a post-cutover validation and automatic rollback in blue-green?**
A: The pattern is: cutover → observe → promote or rollback.
- **Cutover** — flip traffic to green.
- **Observe** — run automated smoke tests against green; monitor error rate, latency p99, and business metrics (transaction success rate) for a defined bake time (e.g., 5 minutes).
- **Promote** — if metrics are within thresholds, scale down blue and declare the deployment complete.
- **Automatic rollback** — if error rate exceeds threshold during bake time, flip the load balancer back to blue automatically. Tools like Argo Rollouts `AnalysisRun` and Flagger do this natively — querying Prometheus metrics and rolling back without human intervention if a metric crosses a threshold.

In fintech, payment success rate and KYC completion rate are the canonical business metrics to monitor during a bake window — a technical error rate spike may not catch a logic regression that causes 10% of loan applications to fail silently.

## Section 4: Canary Deployment

**Q17. What is a canary deployment?**
A: A canary deployment routes a small, controlled percentage of production traffic to the new version while the majority continues hitting the old version. Named after the "canary in a coal mine" — the new version is exposed to real traffic but the blast radius is limited. If the canary fails, only the canary-percentage of users is affected; rollback brings them back to the old version. A typical progression: 1% → 5% → 25% → 50% → 100%, with observation periods at each step.

**Q18. What is the difference between a canary deployment and A/B testing?**
A: They look similar (both split traffic between two versions) but serve different purposes:
- **Canary** — a deployment risk mitigation technique. Both versions are functionally the same feature set; canary exposes the new version to a subset of users to catch bugs, regressions, or performance issues before full rollout. Traffic split is temporary and based on risk, not user segmentation.
- **A/B testing** — a product experimentation technique. Two versions implement different product decisions (different checkout flow, different pricing display). Traffic is split deliberately by user segment (cohort, region, account type) to measure which version produces better business outcomes. The split is intentional and may run for weeks.

In practice the infrastructure overlaps — both use weighted traffic routing — but the intent, duration, and success criteria differ fundamentally.

**Q19. How is canary traffic splitting implemented at the infrastructure level?**
A: Several layers depending on the stack:
- **Load balancer weights** — ALB weighted target groups, NGINX `split_clients`, HAProxy weights. Simple but coarse (pod-level, not request-level).
- **Service mesh** — Istio `VirtualService` with weighted routing gives precise request-level control:
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-service
spec:
  http:
  - route:
    - destination:
        host: my-service-stable
      weight: 95
    - destination:
        host: my-service-canary
      weight: 5
```
- **Ingress controller annotations** — NGINX Ingress canary annotations (`nginx.ingress.kubernetes.io/canary-weight: "5"`).
- **Argo Rollouts** — `Canary` rollout strategy with `steps:` defining the weight progression and pause durations.
- **Feature flags** — decouple traffic split from infrastructure; route specific user segments to new code paths at the application layer (LaunchDarkly, Unleash, Flagsmith).

**Q20. What observability is required to safely operate a canary deployment?**
A: Canary is only safe if you can compare the new version's behavior against the old version's baseline in real time. Required signals:
- **Error rate** — HTTP 5xx rate per version. A spike in the canary's error rate is the primary signal to abort.
- **Latency** — p50, p95, p99 per version. A canary that's functionally correct but 3× slower needs to be caught.
- **Business metrics** — transaction success rate, payment completion rate, KYC pass rate. Technical metrics alone miss regressions that succeed at the HTTP layer but fail at the business logic layer.
- **Version-aware metrics** — metrics must be tagged with a version label (`version: canary` vs `version: stable`) so you can compare them in Grafana/DataDog. Without version labels, you see an aggregate signal that makes it impossible to tell whether the canary or the stable pods are the source of a spike.

Without this observability, canary is not safer than rolling — it's just a slower rolling deployment.

**Q21. What is progressive delivery, and how does it extend canary?**
A: Progressive delivery is canary with automated, metric-driven promotion gates. Instead of a human deciding when to advance from 5% to 25%, the system makes the decision based on observed metrics:
- **Flagger** — a Kubernetes operator that automates canary promotion/rollback based on Prometheus/Datadog metrics. Defines success criteria as metric thresholds; automatically advances weight or rolls back.
- **Argo Rollouts** — `AnalysisRun` CRDs query metrics at each canary step; step only advances if the analysis passes.

```yaml
# Argo Rollouts canary step example
steps:
- setWeight: 5
- pause: {duration: 5m}
- analysis:
    templates:
    - templateName: error-rate-check
- setWeight: 25
- pause: {duration: 10m}
- setWeight: 100
```
Progressive delivery is the state of the art for high-velocity teams — it combines the blast-radius protection of canary with the speed of automation, removing the human bottleneck at each promotion step while maintaining safety.

**Q22. What is a canary analysis failure, and what triggers an automatic rollback?**
A: An analysis failure occurs when a metric query returns a value that violates the defined success threshold during a canary step's observation period. Examples:
- HTTP 5xx error rate for canary pods exceeds 1% (vs 0.1% baseline).
- p99 latency exceeds 500ms (vs 200ms baseline).
- Payment success rate drops more than 2 percentage points below the stable baseline.

On failure, Argo Rollouts / Flagger automatically set the canary weight back to 0, scales down the canary Deployment, and marks the rollout as degraded. An alert fires. No human intervention required for rollback — the intervention comes afterward to investigate the root cause.

## Section 5: Rollbacks

**Q23. What makes a rollback fast vs slow, and which strategy gives the fastest rollback?**
A: Rollback speed is determined by how much work needs to be undone:
- **Blue-green** — fastest. Rollback is a load balancer flip back to blue. Sub-second in terms of traffic redirect; the blue environment was kept running. No re-deployment needed.
- **Canary** — fast for early-stage canary (1–5% weight, flip back to 0). Slower if the canary has already progressed to 50%+ and issues are discovered there.
- **Rolling** — slowest. Rollback is a new rolling update with the old image — takes the same duration as the original rollout. On Kubernetes, `kubectl rollout undo` triggers a new rolling update.
- **Recreate** — similar to rolling; the old version must be fully re-deployed.

For fintech payment services where an outage costs real money per minute, blue-green's instant rollback is often worth its infrastructure cost.

**Q24. What is a database rollback, and why is it often the hardest part of rolling back a deployment?**
A: Application code rollback is usually trivial — redeploy the old image. Database rollback is where rollbacks fail in practice. The complications:
- **Irreversible migrations** — once you've run `ALTER TABLE ADD COLUMN` or migrated data, the schema is changed. Rolling back the application doesn't undo the schema change. Old code running against the migrated schema may break if it doesn't understand new columns.
- **Data written by the new version** — if v2 wrote records in a new format that v1 doesn't understand, those records are now corrupt from v1's perspective.
- **Down migrations** — most teams write `up` migrations but not `down` migrations, because down migrations on production data are dangerous and rarely tested.

The safe approach: design every release so that rolling back the application code (without touching the schema) is always safe. This means: additive schema changes only per release, expand-contract for destructive changes, never writing data in a format the previous version can't handle.

**Q25. How do you test a rollback in a CI/CD pipeline before it's needed in production?**
A: Rollbacks are almost never tested until a real incident — which is exactly when they fail. Practices to change this:
- **Staging rollback drills** — regularly deploy v(n+1) to staging, then deliberately rollback to v(n), and verify the service functions correctly on the old version against the migrated schema.
- **Down migration tests** — run `migrate:down` in the CI pipeline on a test database and assert the application still boots and passes smoke tests.
- **Chaos/game day exercises** — schedule a quarterly drill where the team performs a production rollback of a minor release to test the muscle memory and tooling.
- **Rollback time SLA** — define and measure rollback time (from "rollback initiated" to "old version serving 100% traffic"). Make it a pipeline metric, not just a theoretical estimate.

## Section 6: Advanced Patterns

**Q26. What is a shadow deployment (traffic mirroring), and when do you use it?**
A: Shadow deployment (also called traffic mirroring or dark launch) copies real production traffic to the new version in parallel — but the new version's responses are discarded. Users only see the old version's responses. The new version processes real production load with real data shapes without any user impact:
```yaml
# Istio traffic mirroring
mirror:
  host: my-service-v2
mirrorPercentage:
  value: 100.0
```
Use cases:
- **Performance validation** — measure how v2 handles real production traffic patterns before any user exposure.
- **Correctness validation** — compare v2's responses against v1's for the same requests (diff testing). Catches logic regressions before they impact users.
- **Load testing with real traffic** — more realistic than synthetic load tests; production traffic has edge cases synthetic tools miss.

Shadow deployment has no blast radius by definition — users are never affected. The cost: running v2 at full production load for the duration of the shadow period.

**Q27. What is a feature flag, and how does it complement deployment strategies?**
A: A feature flag is a runtime configuration switch that enables or disables a code path without a deployment. They complement deployment strategies by decoupling code deployment from feature release:
- **Dark launch** — deploy code with the feature flag off globally. The code is in production but inactive. No user impact.
- **Internal testing** — enable the flag for internal users or a specific tenant ID. Test in production with real data.
- **Gradual rollout** — enable for 1% → 10% → 100% of users via the flag service, independent of any deployment.
- **Kill switch** — if a deployed feature causes issues, flip the flag off instantly — no deployment required. Faster than any rollback strategy.

In fintech, feature flags are critical for regulatory compliance — you can deploy code for a new regulatory requirement ahead of the effective date, then flip the flag on the exact date without an emergency release.

**Q28. What is a deployment freeze, and how do you enforce it in a pipeline?**
A: A deployment freeze is a period during which production deployments are prohibited — typically around high-risk windows: end of financial year, peak trading periods, RBI audit windows, major holidays. Pipeline enforcement:
```yaml
# GitHub Actions — block deploy on frozen dates
- name: Check deployment freeze
  run: |
    CURRENT_DATE=$(date +%Y-%m-%d)
    FREEZE_DATES=("2024-03-31" "2024-04-01")
    for date in "${FREEZE_DATES[@]}"; do
      if [ "$CURRENT_DATE" == "$date" ]; then
        echo "Deployment freeze active. Aborting."
        exit 1
      fi
    done
```
More robustly, freeze logic lives in a centralized deployment service (not scattered across pipeline YAMLs) — pipelines query an API that returns `{"freeze": true}` and abort. This ensures the freeze can be lifted instantly without touching pipeline YAML. In Spinnaker and ArgoCD, deployment freeze windows are first-class configuration.

**Q29. What is GitOps, and how does it relate to deployment strategies?**
A: GitOps is a deployment model where the desired state of production infrastructure is declared in a Git repository, and an operator continuously reconciles the live state to match it. The Git repo is the single source of truth — a deployment is a Git commit (PR merged to the infra repo), not a manual `kubectl apply` or pipeline `helm upgrade`. Tools: ArgoCD, Flux.

Relation to deployment strategies:
- GitOps doesn't replace deployment strategies — it changes who initiates them. Instead of a CI pipeline running `helm upgrade`, a CI pipeline opens a PR updating the image tag in the GitOps repo. ArgoCD detects the change and applies it using whatever strategy is configured in the Kubernetes Deployment/Argo Rollout.
- Rollback = `git revert` of the image tag change. The GitOps operator sees the revert and rolls back the cluster state.
- Full audit trail — every production state change is a Git commit with author, timestamp, and PR approval history.

**Q30. How do deployment strategies differ between microservices and monoliths?**
A: Monolith deployments are simpler in one dimension but harder in another:
- **Monolith** — one artifact, one deployment. Blast radius of a bad deploy is the entire application. Canary is harder because the monolith is not naturally partitioned — you need traffic routing to different server instances, which requires external infra (LB weights). Schema coupling is concentrated in one place.
- **Microservices** — each service deploys independently, so blast radius of any single deploy is limited to that service's functionality. But inter-service API compatibility becomes the critical constraint — a canary of Service A must be compatible with the current version of Services B and C. Deployment ordering matters: consumer services before producers when adding new fields, producers before consumers when deprecating old fields.

In a microservices fintech stack (loan origination, KYC, eNACH as separate services), each service owns its deployment strategy independently — but the overall release coordination across services requires a compatibility contract (API versioning) and potentially a service mesh for traffic management.

## Section 7: Scenario Questions

**Q31. "Your team deploys a new version of the payment processing service and transaction success rates drop from 99.5% to 91%. How does your deployment strategy affect how you respond?"**
A:
- **If rolling** — you're mid-rollout; some pods are v2, some are v1. `kubectl rollout undo` immediately — this triggers a new rolling update reverting to v1, taking 3–8 minutes depending on replica count and health check timeouts. During that window, the 9% failure rate continues. Post-rollback, investigate: were failures coming from v2 pods specifically? Check version-tagged metrics.
- **If blue-green** — flip the load balancer back to blue. Traffic shifts in seconds. Green stays running for investigation. Post-incident, the green environment has the broken version available for debugging without impacting users.
- **If canary with automated analysis** — if error rate analysis was configured, the system should have caught the drop at the 1% or 5% canary step and auto-rolled back before most users were affected. If it reached 91% failure it means: the canary weight was already high (50%+), analysis thresholds were too loose, or business metric monitoring wasn't configured (technical 2xx rate looked fine, but the business logic returned "payment failed" with a 200 status).

The meta-lesson: a 91% failure rate that makes it to production is an observability failure, not just a deployment strategy failure.

**Q32. "You need to deploy a breaking API change to a microservice that has 5 internal consumers. What's your deployment plan?"**
A: A breaking API change cannot be deployed as a single release without coordination. The safe approach:
1. **Version the API** — introduce `v2` of the endpoint alongside `v1` (`/api/v2/loans` alongside `/api/v1/loans`). Both versions run simultaneously in the same service.
2. **Migrate consumers** — each of the 5 consumer services updates to use `v2` independently, deployed via their own rolling/canary strategy. No big-bang coordination required.
3. **Monitor `v1` usage** — instrument how many requests are still hitting `v1`. When usage drops to zero (or only internal monitoring traffic), `v1` is safe to deprecate.
4. **Deprecate `v1`** — remove `v1` in a subsequent release after a defined sunset period (communicate to consumers with deprecation headers `Sunset: Sat, 01 Jun 2025 00:00:00 GMT`).

This is additive API versioning — the expand side of the expand-contract pattern. The alternative (forcing all 5 consumers to deploy simultaneously with a coordinated cutover) is a distributed monolith anti-pattern that eliminates the independence benefits of microservices.

**Q33. "A canary deployment looks healthy on technical metrics (error rate, latency) but is silently failing for a specific user cohort. How do you detect this?"**
A: Technical metrics aggregate across all requests — a bug that affects only users with certain account attributes (e.g., users with a specific loan product type, or users in a specific state/region) can be invisible in aggregate error rate metrics. Detection approaches:
- **Cohort-segmented metrics** — tag metrics with user attributes (`account_type`, `product_type`, `region`) and monitor per-cohort success rates during the canary. A 10% drop in `product_type: gold` success rate is invisible in aggregate if gold users are 5% of traffic.
- **Business event monitoring** — track domain events (`loan_application_submitted`, `kyc_completed`, `enach_registered`) per canary pod. A drop in event emission rate signals a silent failure even when HTTP metrics look healthy.
- **Log-based alerting** — parse application logs for domain-specific error messages (`"loan eligibility check failed"`) and alert on rate spikes.
- **User complaints / support ticket spike** — a lagging but real signal. In fintech, the compliance team often catches silent failures before monitoring does ("3 customers called saying their eNACH registration page is broken").

This is why canary analysis rules should include business metrics, not just infrastructure metrics.

**Q34. "How would you design a zero-downtime deployment for a NestJS service that runs database migrations on startup?"**
A: Running migrations on application startup is the most common source of deployment downtime and rolling-update failures in NestJS/TypeORM apps. The fix:
1. **Decouple migrations from startup** — remove migration execution from the app's `onModuleInit` / startup hook. Migrations are not the app's job; they're the deployment pipeline's job.
2. **Migration job in CI/CD** — add a `migrate` step in the pipeline that runs before the rolling deployment starts:
```yaml
# Pipeline order
run-migrations:
  script: npm run migration:run
  environment: production

deploy-service:
  needs: [run-migrations]
  script: kubectl set image deployment/my-service ...
```
3. **Migrations must be backward-compatible** — since the old version is still running when migrations execute, the migration must not break the old schema. Additive only (new columns with defaults or nullable; new tables). Destructive changes go in a subsequent release.
4. **Idempotent migrations** — migrations must be safe to run multiple times (handle "column already exists" errors) so a pipeline retry doesn't corrupt the schema.
5. **Health check migration awareness** — the readiness probe should verify DB connectivity and schema version before the new pod receives traffic.

With this design: migrations run once as a pipeline step, the rolling update proceeds with both old and new pods compatible with the migrated schema, and no startup-time migration races can occur.

| Aspect                   | Recreate              | Rolling                              | Blue-Green                          | Canary                                     |
|--------------------------|-----------------------|--------------------------------------|-------------------------------------|--------------------------------------------|
| Downtime                 | Yes (guaranteed)      | No (if configured correctly)         | No                                  | No                                         |
| Rollback speed           | Slow (re-deploy)      | Slow (new rolling update)            | Instant (LB flip)                   | Fast at low %, slower at high %            |
| Blast radius             | 100% (after cutover)  | Grows with rollout progress          | 100% (post-cutover only)            | Limited to canary % at any moment          |
| Dual-version window      | No                    | Yes (full rollout duration)          | No (except cutover instant)         | Yes (entire canary duration)               |
| Infrastructure cost      | 1×                    | 1× + surge overhead                  | 2× during deployment window         | 1× + small canary overhead                 |
| Schema compatibility     | Not required          | Required during rollout              | Required only at cutover instant    | Required during entire canary window       |
| Observability needed     | Minimal               | Basic (readiness probes)             | Moderate (smoke tests pre-cutover)  | High (version-tagged metrics + biz KPIs)   |
| Complexity               | Minimal               | Low (Kubernetes default)             | Medium (2 environments to manage)   | High (traffic routing + analysis rules)    |
| Best for                 | Internal tools, batch | Standard web services, microservices | High-value services, instant rollback| Highest-risk deploys, progressive delivery |
| Kubernetes native        | Yes (`Recreate`)      | Yes (`RollingUpdate` default)        | Partial (manual or Argo Rollouts)   | Argo Rollouts / Flagger / service mesh     |

**Tip for the interview:** At 5 YOE in fintech, interviewers will probe whether you understand the **database schema constraint** — it's the part most candidates gloss over. Be ready to explain the expand-contract pattern, why you can't just roll back a destructive migration, and how you've designed migrations to be deployment-strategy-compatible. Second probe area: **observability for canary** — specifically, that business metrics (payment success rate, KYC completion rate) must be tracked per version, not just technical HTTP metrics. Have a concrete example of a deployment that went wrong and how your strategy choice either limited or contributed to the blast radius.
