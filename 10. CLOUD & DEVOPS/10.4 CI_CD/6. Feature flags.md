# JavaScript Core (Infrastructure): Feature Flags (LaunchDarkly, Unleash) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a feature flag, and what problem does it solve?**
A: A feature flag (also called a feature toggle or feature switch) is a configuration-driven conditional that lets you enable or disable a code path at runtime without deploying new code. The core problem it solves is decoupling *deployment* from *release* — you ship the code to production but the feature stays off until you deliberately turn it on, independently of any deploy cycle.

**Q2. What are the four main categories of feature flags?**
A:
- **Release toggles** — short-lived flags that hide an incomplete feature in production until it's ready. Meant to be removed once the feature fully rolls out. Most common type.
- **Experiment toggles (A/B flags)** — route a percentage of users to one variant vs. another to measure outcomes (conversion rate, latency, etc.). Often tied to an analytics/experimentation platform.
- **Ops toggles (Kill switches)** — long-lived flags that allow you to disable a feature fast in an incident without a rollback deploy (e.g., disable a third-party integration that's causing timeouts).
- **Permission toggles** — control access by user segment, plan tier, or role (e.g., only beta users or enterprise customers see a feature). Can be long-lived.

**Q3. What's the difference between client-side and server-side evaluation of feature flags?**
A:
- **Server-side** — flag evaluation happens in your backend process. The SDK connects to the flag service, downloads rules, and evaluates locally (or makes an API call). No flag logic is exposed to the browser. Appropriate for server-rendered content, API gates, and anything security-sensitive.
- **Client-side** — the SDK runs in the browser/app and fetches only the flags relevant to the current user. Faster for UI toggles but the flag rules themselves are visible to a motivated user (e.g., in DevTools). Not suitable for business-logic gates or anything you want to enforce server-side.

**Q4. What is a flag's "targeting rule," and how do platforms like LaunchDarkly or Unleash implement it?**
A: A targeting rule is the logic that determines which variation (on/off, or a named variant) a given user/context receives. Platforms typically let you compose rules like: "if `user.plan === 'enterprise'` → serve variant A; if `user.country === 'IN'` → serve variant B; else → default (off)." Unleash calls these *activation strategies* (e.g., `userWithId`, `gradualRollout`); LaunchDarkly calls them *targeting rules* with attribute-based conditions. Both support fallthrough defaults when no rule matches.

**Q5. What is a flag SDK's "offline" or "local evaluation" mode, and why does it matter for latency?**
A: Most production-grade SDKs (LaunchDarkly, Unleash) operate by downloading the full ruleset for your environment at startup and evaluating flags *in-process* against that cached state. They maintain a streaming or polling connection to stay updated. The upside: flag evaluation is a pure in-memory operation — sub-millisecond latency, no network hop per request. The downside: there's a small window after a flag change where your process holds the old state until the update arrives.

## Section 2: LaunchDarkly Deep-Dive

**Q6. What are LaunchDarkly's core architectural components?**
A:
- **SDK** — runs in your service/app. Available in server-side (Node, Java, Go, etc.) and client-side flavors. Manages the connection to the streaming API and local flag cache.
- **Streaming API (SSE)** — pushes flag updates to all connected SDKs in near-real-time (typically < 200 ms). Server-side SDKs maintain a persistent SSE connection.
- **Relay Proxy** — an optional self-hosted component you run at the edge of your network. All your service instances connect to it instead of directly to LaunchDarkly's SaaS. Reduces outbound connections from N services to 1, and provides offline resilience.
- **Data Export / Experimentation** — LaunchDarkly can stream flag evaluation events to a data pipeline (Kinesis, mParticle, Segment) for experiment analysis.

**Q7. How does LaunchDarkly handle the "SDK goes offline" failure mode?**
A: The SDK bootstraps from a cached state (in-memory or a persistent cache you configure). If it can't reach LaunchDarkly at startup, it falls back to the last known good state from a bootstrap file or a Redis/DynamoDB persistent store you configure (called a "data store"). Flag evaluation continues using stale-but-safe data. Most SDKs also let you define fallback values at each `variation()` call site, used when the flag key doesn't exist at all.

**Q8. What's the difference between `variation()` and `allFlagsState()` in the LaunchDarkly SDK?**
A: `variation(flagKey, context, defaultValue)` evaluates a single flag for a specific user/context and returns the assigned variation value. `allFlagsState(context)` evaluates *all* flags for a context and returns a snapshot — intended for bootstrapping client-side SDKs from a server-side render (you pass the snapshot to the browser so it starts with the correct flag state without an extra round-trip). Don't use `allFlagsState()` for individual checks; it's heavier and bypasses per-flag evaluation tracking.

**Q9. What is a "context" in LaunchDarkly's newer SDK model (v6+), and how is it different from the older "user" model?**
A: Earlier SDK versions only supported a single `user` object with a `key` and attributes for targeting. The v6 multi-context model lets you associate multiple context *kinds* with a single evaluation — e.g., a `user` context (individual person), an `organization` context (the tenant), and a `device` context — all in one request. Targeting rules can now target any of these dimensions without you having to merge them into one flat user object. This is important for B2B fintech scenarios where you want to gate features per company account, not per individual user.

**Q10. In Node.js, what's the correct initialization pattern for the LaunchDarkly server-side SDK to avoid race conditions?**
A:
```js
import LaunchDarkly from '@launchdarkly/node-server-sdk';

const client = LaunchDarkly.init(process.env.LD_SDK_KEY);

// Must await initialization before serving traffic
await client.waitForInitialization({ timeout: 10 }); // seconds

// Then evaluate
const flagValue = await client.variation('my-flag', { kind: 'user', key: userId }, false);
```
Calling `variation()` before `waitForInitialization()` resolves means the SDK may not have downloaded the ruleset yet, so it returns the default value for every flag — silently, with no error. This is a common production bug where flags appear stuck at their default right after deploy.

## Section 3: Unleash Deep-Dive

**Q11. How does Unleash differ architecturally from LaunchDarkly?**
A: The biggest difference is self-hosting vs. SaaS. Unleash is open-source and designed to run on your own infrastructure (a Node.js API server + PostgreSQL), which makes it attractive for companies with data-residency requirements (e.g., RBI-regulated data in Indian fintech that can't leave the country). LaunchDarkly is SaaS-first. Unleash also exposes a simpler, more opinionated activation strategy model vs. LaunchDarkly's more flexible rule builder.

**Q12. What are Unleash's built-in activation strategies?**
A:
- **default** — flag is on for everyone.
- **userWithId** — on only for an explicit list of user IDs.
- **gradualRolloutUserId** — on for a percentage of users, based on a hash of `userId` (same user always gets the same result).
- **gradualRolloutSessionId** — same, but keyed off session ID (appropriate when you don't have stable user IDs).
- **gradualRolloutRandom** — on for a percentage, evaluated randomly per request (not sticky — a given user may flip between on and off).
- **remoteAddress** — on for a list of IP addresses.
- Custom strategies — you define the logic in your SDK, Unleash just passes through the parameters.

**Q13. What is the Unleash Proxy, and when would you use it?**
A: The Unleash Proxy is a lightweight frontend-optimized cache layer that sits between your client-side SDK and the Unleash server. Client-side SDKs shouldn't hit the Unleash server directly (it would expose your full toggle config to browsers). The Proxy fetches all toggles server-side, evaluates them for a given context, and returns only the resulting boolean values to the frontend SDK — never the raw rules. This mirrors LaunchDarkly's client-side SDK model where the browser only sees results, not targeting logic.

**Q14. How does Unleash handle SDK resilience if the Unleash server goes down?**
A: The Unleash client SDK caches the last-known toggle state in memory. If the polling request to the Unleash server fails, the SDK continues using the cached state. You can also configure a bootstrap file (a JSON snapshot of toggles) that's loaded at startup before the first poll completes — this prevents the "all flags off" window on cold start. For production, storing the bootstrap snapshot in an environment variable or a config map (in Kubernetes) is a common pattern.

**Q15. How do you implement a gradual rollout (e.g., 10% → 50% → 100%) in Unleash vs. LaunchDarkly?**
A:
- **Unleash** — use the `gradualRolloutUserId` strategy and set the percentage. To increment, change the percentage in the Unleash UI. Rollout is sticky by user ID (hash-based), so users don't flip between on/off as you increase the percentage.
- **LaunchDarkly** — use a percentage rollout rule in the flag's targeting. LaunchDarkly also supports a "measured rollout" that automatically pauses the rollout if an error metric spikes, which Unleash doesn't have natively.
Both work the same conceptual way: consistent hashing ensures the same user always falls on the same side of the rollout threshold, so the "on" cohort only ever grows as you increase the percentage — you never accidentally turn the feature off for users who already had it.

## Section 4: Implementation Patterns & Trade-offs

**Q16. What is "flag-driven deployment" (trunk-based development with flags), and how does it change the branching model?**
A: In a flags-driven workflow, all engineers commit to `main` continuously (trunk-based development). Incomplete features are wrapped in a flag and shipped dark — they exist in production but serve no users. There are no long-lived feature branches waiting to be merged, which eliminates merge conflicts and integration surprises. The "release" of a feature is a flag flip in production, not a deploy. This is the development model LaunchDarkly and Unleash are optimized for.

**Q17. What is "flag debt," and how do you manage it?**
A: Flag debt is the accumulation of flags that were supposed to be temporary (release toggles) but were never removed after the feature shipped. Each live flag is a branch in your code that has to be read, tested, and reasoned about. Over time, N flags create `2^N` possible states, which is untestable. Management strategies: tag every release toggle with an owner and a deadline in the flag description, track them in your issue tracker, run periodic "flag cleanup sprints," and use LaunchDarkly's code references feature (or a similar grep-based CI check) to find flags in code that no longer exist in the platform (orphaned) or flags in the platform with no corresponding code references (stale).

**Q18. How would you test code that uses feature flags in unit and integration tests?**
A: Three common approaches:
- **Mock the SDK client** — inject a test double that returns deterministic values for specific flag keys. Simple, fast, but brittle if you mock too many flags.
- **Bootstrap with a fixture** — initialize the real SDK in "offline" mode with a fixture JSON file that defines all flag states for the test scenario. More realistic, tests the actual SDK evaluation logic.
- **Test both paths** — for any code gated by a flag, write one test suite where the flag is `true` and one where it's `false`. This ensures neither path rots and keeps coverage honest.
Avoid environment-variable-based flags in tests — they make parallel test runs flaky (shared mutable global state).

**Q19. What are the performance implications of evaluating flags inside a hot code path (e.g., inside a loop processing thousands of loan applications)?**
A: Both LaunchDarkly and Unleash SDKs evaluate flags in-memory (no I/O), so a single `variation()` call is typically sub-millisecond. However, inside a tight loop over thousands of items, even 50µs × 10,000 iterations = 500ms of pure CPU time. The fix: evaluate the flag *once before the loop* and pass the boolean into the loop, not the SDK call. Flags are not designed for per-record evaluation at batch-processing scale — treat the flag value as a constant for the lifetime of a batch job.

**Q20. How do you handle flags in a multi-service architecture where the same flag needs to be consistent across a request that touches 3 services?**
A: This is a tricky distributed consistency problem. Two approaches:
- **Evaluate once at the edge** — the API gateway or BFF evaluates all flags for the incoming request, attaches the resulting flag map to the request context (e.g., as a header or propagated via trace context), and downstream services read the pre-evaluated value rather than re-evaluating. This guarantees consistency within a single request.
- **Accept eventual consistency** — each service evaluates independently and trusts that flag updates propagate fast enough (seconds) that divergence is acceptable. Works for non-critical toggles but risky for anything that needs transactional consistency (e.g., a flag that gates whether a loan is processed by service A or service B — the two services must agree for the same loan).

## Section 5: Ops, Compliance & Real-World Scenarios

**Q21. How do you use feature flags as kill switches in a production incident?**
A: For anything that could need a fast rollback — a new third-party integration, a new pricing calculation, a high-risk DB migration path — wrap the new code path in an ops toggle. The toggle is off by default in non-prod, on in prod once you've validated. During an incident caused by that code path, you flip the flag off in the LaunchDarkly/Unleash UI — no deploy, no PR, no on-call engineer waking someone up for a rollback. Recovery time goes from "20 minutes to revert and deploy" to "30 seconds to flip a flag." The critical discipline: the kill switch must be tested (ensure the old code path still works), and someone must own cleaning it up once the incident is resolved and the new path is re-hardened.

**Q22. In an RBI/PCI-DSS-regulated environment, what compliance concerns do feature flags introduce?**
A: Several:
- **Audit trail** — every flag change (who changed it, when, what it changed from/to) must be logged and retained. LaunchDarkly has an audit log; for self-hosted Unleash you need to ensure the Unleash server's change log is piped to your SIEM.
- **Access control** — flag changes that affect security controls (e.g., a flag that bypasses OTP verification) must be restricted to authorized roles. LaunchDarkly supports RBAC/SCIM; Unleash has project-level roles.
- **Data residency** — if flag evaluation uses PII (user ID, account number) to target segments, that data is sent to the flag service. For SaaS providers like LaunchDarkly this means PII leaves your infra. Use anonymous/hashed context keys, or self-host (Unleash).
- **Change management** — in regulated environments, flag changes to production may need a change ticket and approval workflow, the same as code deploys. LaunchDarkly's approval workflows (Enterprise tier) and Unleash's change requests feature address this.

**Q23. Scenario: "A feature flag was accidentally turned on for all users in production over a weekend. How do you prevent this in the future?"**
A: This is a process + tooling gap. Fixes on multiple levels:
1. **Require approvals** — LaunchDarkly Enterprise and Unleash support "change requests" (similar to a PR review). No one can flip a production flag without another team member approving the change.
2. **Restrict production access** — use RBAC so only a small set of engineers (or a CI pipeline with a service account) can write to the production environment. Developers can edit staging freely.
3. **Flag targeting review** — enforce a policy that "on for everyone" is only a valid state for flags that have passed a staged rollout (10% → 50% → 100%) with metrics review at each step.
4. **Monitoring** — wire an alert to your APM/logging stack whenever a flag's evaluation distribution shifts significantly (e.g., a flag that was serving 10% `true` suddenly serves 100% `true` — alert your on-call).

**Q24. Scenario: "Your Node.js service is seeing slightly different behavior in production for the same user on consecutive requests, even though the feature flag is supposed to be deterministic." What would you investigate?**
A: Determinism bugs in flags usually trace back to one of three causes:
1. **Multiple SDK instances** — if your service accidentally instantiates the LaunchDarkly/Unleash SDK more than once (e.g., once per request, or once per worker in a cluster), and they initialize at different times with slightly different cached states, evaluations can differ until they converge.
2. **Non-sticky rollout strategy** — if Unleash's `gradualRolloutRandom` strategy is used instead of `gradualRolloutUserId`, it's intentionally non-sticky. The fix is to switch to the `userId`-based strategy.
3. **Context key inconsistency** — the "user key" passed to the SDK varies between requests (e.g., sometimes it's the raw UUID, sometimes it's a stringified email). The hash that determines rollout bucket changes, so the user ends up in different buckets. Always canonicalize the context key before passing it to the SDK.

**Q25. How do you safely remove a feature flag once a feature is fully rolled out?**
A: The removal has two parts — code and platform — and the order matters:
1. **Identify all code references** — use LaunchDarkly's code references integration or a repo-wide grep to find every call site of that flag key.
2. **Commit the "flag removal" PR** — inline the `true` branch (the flag-on behavior), delete the `false` branch, and remove all `variation()` calls for that key. This PR should *not* change any behavior — the flag has been on for 100% of users already.
3. **Deploy the PR** — once deployed and verified, the code no longer depends on the flag service for this feature.
4. **Archive the flag in LaunchDarkly/Unleash** — deleting it from the platform while code still references it would cause the SDK to return the default value, which could accidentally disable the feature.
5. **Track cleanup** — close the associated issue, and note it in your flag debt tracker.

## Quick Comparison Table

| Aspect | LaunchDarkly | Unleash |
|---|---|---|
| Hosting | SaaS (Relay Proxy optional) | Self-hosted (OSS) or Unleash Cloud |
| Pricing | Per-seat / per-MAU | Free OSS; paid for Enterprise features |
| Client-side support | First-class (JS, React, mobile SDKs) | Via Unleash Proxy |
| Targeting rules | Rich attribute-based rule builder | Activation strategies (simpler) |
| Gradual rollout | Percentage rollout (user/session hash) | `gradualRolloutUserId` / `SessionId` |
| Experimentation | Built-in (A/B, metric guardrails) | Third-party or manual | 
| Audit log | Built-in, exportable | DB-level; needs external SIEM wiring |
| Approval workflow | Enterprise tier | Change requests (Enterprise) |
| Offline resilience | Bootstrap file + data store plugins | Bootstrap JSON + in-memory cache |
| Data residency concern | PII leaves your infra | Stays in your infra (self-hosted) |
| Code references | Native CI integration | Manual grep / custom tooling |

**Tip for the interview:** At the 5 YOE level, interviewers rarely ask "what is a feature flag" — they assume you know. They'll go straight to: "how would you ensure flag consistency across microservices?", "how would you handle a flag-triggered incident?", or "how do you prevent flag debt in a team of 20 engineers?" Have one real story ready — a kill-switch save, a messy rollout you managed, or a flag-debt cleanup you drove. Also be ready to discuss the self-host vs. SaaS trade-off in the context of compliance — in fintech this comes up almost every time, especially around PII in targeting contexts and audit trail requirements for RBI/PCI-DSS.
