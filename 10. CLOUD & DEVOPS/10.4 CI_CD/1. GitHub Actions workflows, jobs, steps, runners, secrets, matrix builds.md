# GitHub Actions: Workflows, Jobs, Steps, Runners, Secrets, Matrix Builds — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is GitHub Actions, and what problem does it solve?**
A: GitHub Actions is a CI/CD and automation platform built into GitHub. It lets you define event-driven workflows — triggered by pushes, PRs, schedules, or API calls — to automate building, testing, and deploying code. It eliminates the need for a separately managed CI server (like Jenkins) and keeps pipelines co-located with source code.

**Q2. What is a workflow?**
A: A workflow is a YAML file stored in `.github/workflows/` that defines an automated process. It specifies when to run (triggers/events), what to run (jobs and steps), and where to run it (runners). A repo can have multiple workflows, each handling different concerns (e.g., `ci.yml` for tests, `deploy.yml` for deployments).

**Q3. What is a job, and how does it relate to a workflow?**
A: A job is a set of steps that runs on a single runner inside a workflow. Jobs within the same workflow run in parallel by default. You can enforce ordering using `needs:` to declare job dependencies (e.g., `deploy` needs `build` to pass first). Each job gets a fresh runner environment.

**Q4. What is a step, and what types of steps exist?**
A: A step is the smallest unit of execution inside a job. Steps run sequentially within a job. There are two types:
- **`uses:`** — references a pre-built Action (e.g., `actions/checkout@v4`, `actions/setup-node@v4`).
- **`run:`** — executes shell commands directly (bash, powershell, etc.).

**Q5. What is a runner?**
A: A runner is the compute environment that executes a job. GitHub provides hosted runners (Ubuntu, Windows, macOS) that are fresh VMs per job. You can also use **self-hosted runners** — machines you manage yourself — for custom hardware, private network access, or cost control at scale.

**Q6. What triggers a workflow?**
A: Workflows are triggered by `on:` events. Common ones:
- `push` / `pull_request` — on code changes.
- `schedule` — cron-based (e.g., nightly builds).
- `workflow_dispatch` — manual trigger via UI or API.
- `workflow_call` — invoked by another workflow (reusable workflows).
- `release` — on GitHub release creation.

## Section 2: Jobs, Steps & Execution Model

**Q7. How do you make jobs run sequentially instead of in parallel?**
A: Use `needs:` to declare dependencies:
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps: [...]
  test:
    needs: build
    runs-on: ubuntu-latest
    steps: [...]
  deploy:
    needs: [build, test]
    runs-on: ubuntu-latest
    steps: [...]
```
`deploy` will only run if both `build` and `test` succeed.

**Q8. How do you share data (artifacts) between jobs?**
A: Jobs run on isolated runners, so data doesn't persist across them automatically. Use `actions/upload-artifact` and `actions/download-artifact`:
```yaml
# In build job
- uses: actions/upload-artifact@v4
  with:
    name: dist-bundle
    path: dist/

# In deploy job
- uses: actions/download-artifact@v4
  with:
    name: dist-bundle
```
For smaller values (env vars, version strings), use job outputs via `$GITHUB_OUTPUT`.

**Q9. What is `$GITHUB_OUTPUT` and how does it differ from environment variables?**
A: `$GITHUB_OUTPUT` is the mechanism for passing output values from one step to subsequent steps or from one job to dependent jobs. A step writes to it (`echo "sha=$SHA >> $GITHUB_OUTPUT"`), and the value is read via `steps.<step-id>.outputs.<key>` or `needs.<job-id>.outputs.<key>`. Regular environment variables (`$GITHUB_ENV`) persist only within a job, while `$GITHUB_OUTPUT` can cross job boundaries when combined with `jobs.<job-id>.outputs`.

**Q10. How does conditional execution (`if:`) work on jobs and steps?**
A: Both jobs and steps support `if:` conditions using GitHub's expression syntax. Common patterns:
```yaml
- name: Deploy to prod
  if: github.ref == 'refs/heads/main' && github.event_name == 'push'
  run: ./deploy.sh

- name: Notify on failure
  if: failure()
  run: ./notify-slack.sh
```
`failure()`, `success()`, `always()`, and `cancelled()` are built-in status check functions. By default steps are skipped if a prior step fails; `if: always()` overrides this.

**Q11. How do you run cleanup steps even if the job fails?**
A: Use `if: always()` on the step, or define a separate cleanup job with `if: always()` and `needs:` pointing at the main job. This is common for releasing locks, sending failure alerts, or tearing down test infrastructure.

## Section 3: Runners

**Q12. What are GitHub-hosted runners, and what are their limitations?**
A: GitHub-hosted runners are ephemeral VMs provisioned per job. They come pre-configured with common tools (node, python, docker, aws cli, etc.). Limitations:
- Fixed hardware specs (2-core CPU, 7GB RAM for free tier ubuntu).
- No access to private networks/VPCs.
- 6-hour max job duration.
- Storage resets between jobs (no persistent disk).
- Cost at scale (billed per minute for private repos).

**Q13. When would you use self-hosted runners?**
A: 
- **Private network access** — deploying to on-prem or VPC resources without exposing them publicly.
- **Custom hardware** — GPU builds, ARM-native testing, high-memory jobs.
- **Cost control** — at scale, self-hosted on spot instances (EC2/GKE) is cheaper than GitHub-hosted minutes.
- **Specific OS/toolchain** — proprietary tools or OS configurations not available on hosted runners.
- **Compliance** — regulated environments where code can't leave your infrastructure.

**Q14. What are the security risks of self-hosted runners on public repos?**
A: On a public repo, anyone can fork and open a PR, potentially running malicious code on your self-hosted runner (since it's your persistent machine). GitHub strongly recommends self-hosted runners **only for private repos**. For public repos, use hosted runners and treat any untrusted code as a threat.

**Q15. What is a runner group, and why does it matter?**
A: Runner groups allow you to organize self-hosted runners and control which repos or workflows can use them. For example, a "production-deploy" runner group might only be accessible to workflows in the main repo on the `main` branch — preventing test PRs from accidentally accessing prod credentials or network segments.

## Section 4: Secrets & Security

**Q16. How do secrets work in GitHub Actions?**
A: Secrets are encrypted key-value pairs stored at the repo, environment, or org level. They're injected into workflow runs as environment variables:
```yaml
- name: Deploy
  env:
    AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
    AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
  run: aws s3 sync ./dist s3://my-bucket
```
GitHub automatically redacts secret values from logs. Secrets are never exposed to PRs from forks on public repos (by default).

**Q17. What's the difference between repo secrets, environment secrets, and org secrets?**
A:
- **Repo secrets** — scoped to a single repository. Available in all workflows/environments within that repo.
- **Environment secrets** — scoped to a named deployment environment (e.g., `production`, `staging`). Only available when a job targets that environment via `environment:`. Useful for enforcing approval gates.
- **Org secrets** — scoped at the GitHub organization level, optionally restricted to specific repos. Good for shared credentials (e.g., a shared Docker registry token).

**Q18. What is an environment in GitHub Actions, and how does it enable approval gates?**
A: An environment (configured under repo Settings → Environments) is a named target (e.g., `production`) that can have its own secrets, protection rules, and required reviewers. A job that targets an environment must pass its protection rules before executing:
```yaml
jobs:
  deploy:
    environment: production   # triggers approval gate if configured
    runs-on: ubuntu-latest
    steps: [...]
```
This is the GitHub-native way to implement manual approval before production deployments.

**Q19. How do you prevent secret leakage in workflows?**
A: Key practices:
- Never `echo` or `print` secret values directly.
- Don't pass secrets as positional CLI args (they may appear in process lists); use env vars instead.
- Be cautious with `pull_request_target` — it runs with write access and secrets in the context of the base repo, making it a common attack vector.
- Use `permissions:` to restrict the default `GITHUB_TOKEN` scope to only what the workflow needs.
- Rotate secrets regularly; prefer short-lived credentials (OIDC) over long-lived keys.

**Q20. What is OIDC-based authentication, and why is it better than static secrets?**
A: GitHub Actions supports OpenID Connect (OIDC), which lets workflows request short-lived cloud credentials directly from AWS/GCP/Azure without storing long-lived keys as secrets. The workflow presents a signed JWT token to the cloud provider's OIDC endpoint, which validates it and returns temporary credentials. This eliminates the rotation burden and reduces the blast radius if a secret leaks — the token expires in minutes rather than years.

## Section 5: Matrix Builds

**Q21. What is a matrix build?**
A: A matrix build lets you run the same job across multiple configurations (OS, language version, environment) in parallel by defining a `strategy.matrix`. GitHub expands the matrix into N parallel jobs:
```yaml
strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, windows-latest]
```
This creates 6 parallel jobs (3 node versions × 2 OS), each with the respective `matrix.node-version` and `matrix.os` values injected.

**Q22. How do you reference matrix values inside job steps?**
A: Via `${{ matrix.<key> }}`:
```yaml
steps:
  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node-version }}
  - run: npm test
```

**Q23. What is `fail-fast` in matrix strategy, and when would you disable it?**
A: By default, `fail-fast: true` means if any matrix job fails, GitHub cancels all remaining in-progress matrix jobs to save runner minutes. Set `fail-fast: false` when you want to see the full picture — e.g., knowing which specific OS/version combinations fail rather than stopping at the first one:
```yaml
strategy:
  fail-fast: false
  matrix:
    node-version: [16, 18, 20]
```

**Q24. How do you add one-off configurations or exclusions to a matrix?**
A: Use `include` to add extra combinations, and `exclude` to drop specific ones:
```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node: [18, 20]
    include:
      - os: ubuntu-latest
        node: 20
        experimental: true   # extra variable only for this combo
    exclude:
      - os: windows-latest
        node: 18             # skip win + node18 combo
```

**Q25. How do you limit matrix concurrency to avoid overloading resources?**
A: Use `max-parallel` under `strategy`:
```yaml
strategy:
  max-parallel: 3
  matrix:
    node-version: [16, 18, 20, 22]
```
This runs at most 3 matrix jobs simultaneously, useful when downstream resources (test databases, staging environments) have concurrency limits.

## Section 6: Reusable Workflows & Composite Actions

**Q26. What's the difference between a reusable workflow and a composite action?**
A:
- **Reusable workflow** (`workflow_call`) — a full workflow file that can be invoked by other workflows. Can contain multiple jobs, uses its own runners, and supports secrets/inputs. Good for standardizing deployment pipelines across repos.
- **Composite action** — a custom action defined in `action.yml` that groups multiple steps into one reusable `uses:` block. Runs in the caller's job context (no separate runner). Good for extracting repeated step sequences within a workflow.

**Q27. How do you call a reusable workflow?**
A:
```yaml
# In caller workflow
jobs:
  deploy:
    uses: my-org/shared-workflows/.github/workflows/deploy.yml@main
    with:
      environment: production
    secrets: inherit   # passes caller's secrets through
```
`secrets: inherit` forwards all of the caller's secrets to the reusable workflow without enumerating them individually.

**Q28. What are the limitations of reusable workflows?**
A: A workflow can only be nested 4 levels deep. Reusable workflows can't reference other reusable workflows beyond that limit. Also, matrix strategy can't be defined inside a reusable workflow — the matrix must be in the caller. And reusable workflows can't use `if:` at the job level driven by the caller's context without explicitly passing context via `inputs:`.

## Section 7: CI/CD Patterns & Scenario Questions

**Q29. How would you structure a CI/CD pipeline for a Node.js service with staging and production environments?**
A: A typical structure:
```
on: push (main), pull_request

jobs:
  lint-and-test     → runs on every PR and push
  build             → needs: lint-and-test; builds Docker image, pushes to ECR with commit SHA tag
  deploy-staging    → needs: build; environment: staging; deploys to staging ECS/K8s
  integration-test  → needs: deploy-staging; runs E2E tests against staging
  deploy-prod       → needs: integration-test; environment: production (approval gate); deploys to prod
```
Each environment has its own secrets. The production environment requires a manual reviewer approval before the deploy job executes.

**Q30. "Your GitHub Actions workflow is slow — tests take 20 minutes. How do you speed it up?"**
A: Several levers:
- **Parallelism** — split the test suite and use a matrix to run shards in parallel.
- **Caching** — use `actions/cache` to cache `node_modules`, pip packages, or build artifacts across runs.
- **Skip unchanged** — use path filters (`on.push.paths`) so a frontend change doesn't trigger backend tests.
- **Larger runners** — upgrade to 4-core or 8-core GitHub-hosted runners for CPU-bound tasks.
- **Test impact analysis** — only run tests affected by changed files (tools like Nx, Turborepo, or custom scripts).

**Q31. How do you cache dependencies in GitHub Actions?**
A: Use `actions/cache`:
```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
```
The `key` is computed from the lock file hash — a lock file change busts the cache. `restore-keys` gives a fallback to a partial match. Note: `actions/setup-node` with `cache: 'npm'` wraps this automatically for common package managers.

**Q32. How do you handle drift between what works locally and what fails in CI?**
A: The main culprits are environment differences (Node version, OS, timezone, locale) and missing determinism (unlocked dependencies, time-dependent tests). Mitigations:
- Pin runner OS version (use `ubuntu-22.04` not `ubuntu-latest` for stability).
- Use lockfiles and cache them.
- Run CI locally via `act` (a tool that runs GitHub Actions workflows locally using Docker).
- Use the same Docker image for local dev and CI steps.

**Q33. How do you implement a manual approval step before production deployment?**
A: Configure a GitHub Environment with required reviewers in repo Settings → Environments → `production` → Protection Rules. Then target that environment in the deploy job:
```yaml
deploy-prod:
  needs: deploy-staging
  environment: production
  runs-on: ubuntu-latest
  steps:
    - run: ./deploy-prod.sh
```
The job pauses and notifies the required reviewers. The workflow continues only after an approver clicks "Approve" in the GitHub UI.

**Q34. What is the `GITHUB_TOKEN`, and what can it do?**
A: `GITHUB_TOKEN` is an automatically generated short-lived token that GitHub injects into every workflow run. It has permissions scoped to the repository (create releases, comment on PRs, push packages to GHCR, etc.). Its default permissions can be restricted globally or per-workflow using `permissions:`:
```yaml
permissions:
  contents: read
  packages: write
  pull-requests: write
```
It expires when the workflow run ends, making it safer than a personal access token.

## Quick Reference Table

| Concept            | Key Detail                                                                 |
|--------------------|----------------------------------------------------------------------------|
| Workflow           | YAML in `.github/workflows/`; triggered by `on:` events                   |
| Job                | Runs on one runner; parallel by default; ordered via `needs:`              |
| Step               | Sequential within a job; `uses:` (action) or `run:` (shell)               |
| Runner             | Hosted (ephemeral VM) or self-hosted (your machine/infra)                  |
| Secret             | Encrypted; repo / environment / org scoped; redacted from logs             |
| Environment        | Named deploy target with protection rules, secrets, and approval gates     |
| Matrix build       | Expands one job into N parallel jobs across config dimensions              |
| `fail-fast`        | Default `true` — cancel siblings on first failure; set `false` for full insight |
| Artifact           | Cross-job data sharing via `upload-artifact` / `download-artifact`         |
| Reusable workflow  | Full workflow called via `workflow_call`; good for cross-repo standardization |
| Composite action   | Step group in `action.yml`; runs in caller's job context                   |
| OIDC               | Short-lived cloud creds via JWT; preferred over long-lived static secrets  |
| `GITHUB_TOKEN`     | Auto-injected; scoped to repo; expires with run                            |
| `actions/cache`    | Persist deps/build output across runs by key hash                          |
