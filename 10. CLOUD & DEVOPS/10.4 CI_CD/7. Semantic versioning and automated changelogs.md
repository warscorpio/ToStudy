# JavaScript Core (CI/CD): Semantic Versioning & Automated Changelogs — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is semantic versioning, and what do the three numbers mean?**
A: Semantic versioning (SemVer) is a versioning convention with the format `MAJOR.MINOR.PATCH` (e.g., `2.4.1`), governed by the spec at semver.org. Each segment has a defined meaning:
- **MAJOR** — incremented when you introduce a *breaking change* (an existing consumer must change their code to keep working).
- **MINOR** — incremented when you add new functionality in a *backward-compatible* way (existing consumers are unaffected).
- **PATCH** — incremented when you make backward-compatible *bug fixes* only.

The contract is simple: if you follow SemVer correctly, a consumer who pins to `^2.4.1` can safely receive `2.5.0` or `2.4.2` automatically, but never `3.0.0` without opting in.

**Q2. What are pre-release versions and build metadata in SemVer, and when do you use them?**
A:
- **Pre-release** — appended with a hyphen: `2.4.1-alpha.1`, `2.4.1-rc.2`. Indicates the version is not yet stable. npm respects this — `^2.4.1` won't install `2.4.1-alpha.1` unless explicitly requested. Common in library release pipelines where you want to let early adopters test before a stable cut.
- **Build metadata** — appended with a `+`: `2.4.1+build.202`. Purely informational — SemVer spec says two versions that differ only in build metadata have equal precedence. npm ignores build metadata entirely. Rarely used in JS ecosystems; more common in compiled language pipelines where you want to trace a binary back to a specific CI build.

**Q3. What does `0.x.y` versioning signal, and how should consumers treat it?**
A: A MAJOR version of `0` is SemVer's explicit signal that the project is in initial development and the public API is *not* stable. Breaking changes *may* happen on any MINOR bump (e.g., `0.4.0` → `0.5.0` could be breaking). Consumers should pin to an exact version or a narrow `~0.4.0` range, not `^0.4.0`. This is why many teams deliberately stay on `0.x` until they're confident in their API — it's a public commitment to instability, not a sign of immaturity.

**Q4. What is the Conventional Commits specification, and why does it matter for automated versioning?**
A: Conventional Commits is a lightweight commit message format — `<type>(<scope>): <description>` — that makes commit history machine-readable. Types include `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `perf`, and `ci`. A `!` after the type (`feat!: ...`) or a `BREAKING CHANGE:` footer signals a breaking change. Tools like `semantic-release`, `release-please`, and `standard-version` parse these commit messages to *automatically determine* the next SemVer bump (`feat` → MINOR, `fix` → PATCH, `BREAKING CHANGE` → MAJOR) and generate changelogs from the commit descriptions — no human decides the version number.

**Q5. What are version range operators in npm, and what do they actually resolve to?**
A: npm uses a handful of operators that express compatible version ranges:
- `^2.4.1` (caret) — allows changes that don't modify the left-most non-zero digit. For `^2.4.1` that means `>=2.4.1 <3.0.0`. For `^0.4.1` it means `>=0.4.1 <0.5.0` (the leading zero is the left-most non-zero digit).
- `~2.4.1` (tilde) — allows patch-level changes only: `>=2.4.1 <2.5.0`.
- `*` / `x` — any version. Almost never appropriate in production `package.json`.
- Exact (`2.4.1`) — pins to that version precisely. `package-lock.json` does this internally for every transitive dependency.
The practical takeaway: `^` is npm's default (what `npm install` writes), which is why `package-lock.json` exists — it makes `^` installs reproducible by recording the exact resolved version.

## Section 2: Conventional Commits in Practice

**Q6. Walk through the complete Conventional Commits message format with examples.**
A: The full format is:
```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```
Examples by bump type:

```
# PATCH bump
fix(auth): handle expired JWT tokens returning 401 instead of 500

# MINOR bump
feat(loans): add pre-approved offer endpoint for eligible customers

# MAJOR bump — via ! shorthand
feat(api)!: remove deprecated v1 loan application endpoint

# MAJOR bump — via footer
feat(ekyc): migrate KYC provider to Digilocker

BREAKING CHANGE: `kycResult.panVerified` field removed; use `kycResult.documents.pan.verified` instead
```

The `scope` is optional but strongly recommended in a monorepo or multi-domain codebase — it tells the changelog generator (and your team) which package/service/domain the commit touches.

**Q7. What commit types map to which SemVer bumps in tools like `semantic-release`?**
A:

| Commit type | SemVer bump | Notes |
|---|---|---|
| `BREAKING CHANGE` footer or `!` | MAJOR | Overrides everything |
| `feat` | MINOR | New capability |
| `fix` | PATCH | Bug fix |
| `perf` | PATCH | Some tools treat this as PATCH |
| `refactor`, `docs`, `test`, `chore`, `ci`, `style` | None | No release triggered by default |

The "no release" types are important — they let you push documentation updates or internal refactors to `main` without triggering a version bump and publish cycle. Teams often customize this mapping in their tool config (e.g., making `perf` trigger a MINOR bump for a performance-critical library).

**Q8. How do you enforce Conventional Commits in a team setting?**
A: Two layers:
- **Local (pre-commit/commit-msg hook)** — use `commitlint` with `@commitlint/config-conventional` wired to Husky's `commit-msg` hook. It lints the message before the commit is accepted locally. Zero CI minutes wasted.
- **CI validation** — run `commitlint --from origin/main` in your PR pipeline to validate all commits in the branch. This catches developers who bypassed the local hook (e.g., pushed with `--no-verify`). Both layers together make it very hard to accidentally land a non-conforming commit.

```jsonc
// commitlint.config.js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'scope-enum': [2, 'always', ['auth', 'loans', 'kyc', 'nach', 'api', 'infra']],
  }
};
```

**Q9. What's the trade-off between enforcing strict Conventional Commits vs. squash-merging PRs?**
A: Many teams use GitHub's "Squash and merge" — all commits in a PR are squashed into one, and the PR *title* becomes the squash commit message. This means:
- Individual commits during development can be messy (WIP, fixup) — developers write "real" commit messages only for the PR title.
- You enforce `commitlint` on the PR title via a CI check (e.g., `semantic-pull-request` GitHub Action).
- The changelog entries are one line per PR, not per commit — cleaner for large PRs but you lose granularity.
The alternative (linear history, no squash) gives you per-commit changelog granularity and a more accurate audit trail, but demands discipline from every engineer on every commit. Most product teams prefer the squash model; library/SDK teams often prefer linear history for precise changelogs.

**Q10. How do you handle "chore" commits that update dependencies — should they trigger a version bump?**
A: Dependency updates are nuanced. A `chore(deps): bump axios from 1.6.0 to 1.7.2` shouldn't trigger a version bump for your service (it's internal). But if it's a *library* you publish, a transitive dependency upgrade could matter to consumers. The common convention: `chore(deps)` → no release for internal services; `fix(deps)` → PATCH release for published packages (signals "we resolved a vulnerability or broken dep"). Tools like Dependabot and Renovate can be configured to use the right prefix based on whether the upgrade is a patch, minor, or major in the dependency itself.

## Section 3: `semantic-release` Deep-Dive

**Q11. What does `semantic-release` actually do, step by step?**
A: `semantic-release` is a fully automated release pipeline. When triggered (usually on a push to `main`), it:
1. **Analyzes commits** since the last release tag using the configured commit analyzer (default: `@semantic-release/commit-analyzer` — reads Conventional Commits).
2. **Determines the next version** — computes MAJOR/MINOR/PATCH bump.
3. **Generates release notes** — builds a human-readable changelog from the commit messages (`@semantic-release/release-notes-generator`).
4. **Publishes artifacts** — for npm packages: runs `npm publish` (`@semantic-release/npm`). For other targets: Docker images, GitHub releases, etc.
5. **Creates a Git tag** — tags the commit with the new version (`@semantic-release/git`).
6. **Posts a GitHub Release** — with the generated notes attached (`@semantic-release/github`).
All steps are plugin-driven and configurable. The key design principle: *no human runs `npm version` or writes a `CHANGELOG.md` entry manually ever again.*

**Q12. What is the `.releaserc` configuration, and what are the critical settings?**
A:
```jsonc
// .releaserc.json
{
  "branches": ["main", { "name": "next", "prerelease": true }],
  "plugins": [
    "@semantic-release/commit-analyzer",
    "@semantic-release/release-notes-generator",
    ["@semantic-release/changelog", { "changelogFile": "CHANGELOG.md" }],
    ["@semantic-release/npm", { "npmPublish": false }],  // set true for public packages
    ["@semantic-release/git", {
      "assets": ["CHANGELOG.md", "package.json"],
      "message": "chore(release): ${nextRelease.version} [skip ci]"
    }],
    "@semantic-release/github"
  ]
}
```
Critical details: the `[skip ci]` in the release commit message is essential — without it, the CI pipeline triggers again on the `package.json` + `CHANGELOG.md` commit that `semantic-release` just pushed, causing an infinite loop. The `branches` config controls which branches trigger releases and whether they're pre-release channels.

**Q13. How does `semantic-release` handle the "first run" or "no previous tag" scenario?**
A: If no tags exist in the repository, `semantic-release` uses all commits in history to determine the initial version. The result is usually `1.0.0` (if any `feat` or breaking commit exists) or `0.0.1`. To start from a specific version on an existing project, create a Git tag manually: `git tag v2.3.0 && git push --tags`. `semantic-release` will then compute the next bump relative to that tag. This manual bootstrapping is the one human intervention step in an otherwise automated pipeline.

**Q14. How do you set up multi-branch release channels in `semantic-release` (e.g., `beta` and `main`)?**
A:
```jsonc
{
  "branches": [
    "main",
    { "name": "beta", "prerelease": true },
    { "name": "next", "prerelease": "next" }
  ]
}
```
With this config:
- Pushes to `beta` publish `2.5.0-beta.1`, `2.5.0-beta.2`, etc.
- Pushes to `main` publish `2.5.0` (the final stable release).
`semantic-release` tracks each channel's state independently with separate tag namespaces (`v2.5.0-beta.1` vs `v2.5.0`). The merge from `beta` → `main` doesn't re-release — it recognizes the commits were already analyzed on the beta channel and just cuts the stable release.

**Q15. What CI environment variables does `semantic-release` require, and why?**
A: Two categories:
- **`NPM_TOKEN`** — a publish token from npmjs.com (for `@semantic-release/npm`). Must have publish rights to your package. In GitHub Actions, store it as an Actions secret.
- **`GITHUB_TOKEN`** — for creating GitHub Releases, posting PR comments, and pushing the release commit back to the repo. GitHub Actions provides this automatically via `${{ secrets.GITHUB_TOKEN }}`. The token must have `contents: write` permission (declare this in the workflow's `permissions` block, especially for repos using GitHub's default restrictive token policy).

Missing or misconfigured tokens are the #1 cause of `semantic-release` failures in CI — it'll usually say "Authentication failed" or silently skip the GitHub release step.

## Section 4: `release-please` & `standard-version`

**Q16. How does `release-please` differ from `semantic-release` in its release philosophy?**
A: The core difference is *when* the release decision happens:
- **`semantic-release`** — fully automated. Analyzes commits and publishes on every push to `main`. The release is immediate and requires zero human action post-merge.
- **`release-please`** (Google's tool) — creates a **Release PR** that accumulates changelog entries and version bump as commits land on `main`. A human (or automation) merges the Release PR to actually cut the release. This gives teams a "release gate" — you decide *when* to release without being forced to release on every merge.
`release-please` is a better fit for teams that ship on a release cadence (e.g., weekly) rather than continuously.

**Q17. What is `standard-version`, and is it still relevant?**
A: `standard-version` is an older, simpler CLI tool that bumps `package.json`, updates `CHANGELOG.md`, creates a git tag, and commits — all locally. You run it manually or in a script: `npx standard-version --release-as minor`. It doesn't publish to npm or create GitHub Releases on its own — you handle that separately. It was widely used pre-2022 but its maintainers have officially deprecated it in favor of `release-please`. It still works but won't receive updates. For greenfield projects, prefer `semantic-release` or `release-please`; for existing projects using `standard-version`, the migration path to `release-please` is well-documented.

**Q18. When would you choose `release-please` over `semantic-release`?**
A: Choose `release-please` when:
- Your team wants a human-in-the-loop release gate (merge the Release PR = ship).
- You have multiple packages in a monorepo and want per-package Release PRs (release-please's monorepo support is first-class).
- You want the changelog and version bump to be visible and reviewable as a PR diff before merging — useful in regulated environments where change management requires an approval record.
- You're already on Google Cloud / use Google's toolchain where release-please is the standard.
Choose `semantic-release` when you want fully continuous delivery with zero manual steps and you trust your commit discipline to drive version numbers correctly.

## Section 5: CI/CD Integration & Real-World Scenarios

**Q19. Write a minimal GitHub Actions workflow that runs `semantic-release` on push to `main`.**
A:
```yaml
# .github/workflows/release.yml
name: Release

on:
  push:
    branches: [main]

permissions:
  contents: write
  issues: write
  pull-requests: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # semantic-release needs full history to find tags
          persist-credentials: false

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - run: npx semantic-release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```
`fetch-depth: 0` is critical — a shallow clone (`depth: 1`, which is the actions/checkout default) means `semantic-release` can't see previous tags and computes the wrong version. This trips up almost every first-time setup.

**Q20. How do you integrate automated versioning into a monorepo with multiple independently versioned packages?**
A: Two main approaches:
- **`semantic-release` with `multi-semantic-release`** — a community plugin that runs `semantic-release` for each package in the monorepo, scoping commit analysis to each package's directory. Each package gets its own independent version timeline and tag (`@myorg/loans@2.1.0`, `@myorg/kyc@1.4.0`).
- **`release-please` with manifest mode** — `release-please` has native monorepo support via a `release-please-config.json` manifest that lists each package and its versioning strategy. It creates one Release PR per package (or a combined PR) and tracks each independently.
- **Nx/Turborepo with `@jscutlery/semver`** — if you're already using Nx, this plugin wires Conventional Commits into Nx's affected-graph so only packages touched by a commit set get bumped.
Avoid the naive approach of a single version for the entire monorepo unless you're intentionally using "lockstep" versioning (all packages always at the same version, like Angular does).

**Q21. Scenario: "A developer merged a `fix` commit to `main`, but `semantic-release` bumped the MAJOR version unexpectedly. What happened?"**
A: Almost certainly a `BREAKING CHANGE` footer was present in the commit body that the developer didn't notice or intended. `semantic-release` scans the *full* commit message including the body and footers — a commit like:
```
fix(auth): handle null session gracefully

BREAKING CHANGE: session cookie name changed from `sid` to `__session`
```
…will trigger a MAJOR bump regardless of the `fix` type in the header. Debugging steps: run `npx semantic-release --dry-run` locally on that commit, and inspect the analyzer output. Then check your git log with `git log --format="%H %s%n%b" -n 20` to see full commit bodies. Fix going forward: `commitlint` enforcement and a PR template that warns developers about the `BREAKING CHANGE` footer.

**Q22. Scenario: "The CI release job ran twice in quick succession and produced two identical version tags. How do you prevent this?"**
A: This happens when two pushes land on `main` within the same CI queue window before the first release job has pushed its tag back. `semantic-release` reads the latest tag at job start — if neither job has pushed a tag yet, both see the same "last tag" and compute the same next version. Fixes:
1. **Serialize the release job** — use GitHub Actions `concurrency` with `cancel-in-progress: false` so the second run queues behind the first instead of running in parallel:
```yaml
concurrency:
  group: release
  cancel-in-progress: false
```
2. **Branch protection** — enforce linear history on `main` (require PRs, no direct push). This makes simultaneous pushes structurally impossible.
The `concurrency` fix is the immediate patch; branch protection is the long-term discipline.

**Q23. How do you generate and maintain a `CHANGELOG.md` in a way that's both human-readable and machine-generated?**
A: The `@semantic-release/changelog` plugin (or `release-please`'s built-in changelog) writes entries in a structured format — grouped by type (`### Features`, `### Bug Fixes`, `### BREAKING CHANGES`), with each entry linking back to the commit or PR. A good `CHANGELOG.md` entry looks like:
```markdown
## [2.5.0](https://github.com/org/repo/compare/v2.4.1...v2.5.0) (2025-08-10)

### Features

* **loans:** add pre-approved offer endpoint for eligible customers ([a1b2c3d](https://github.com/org/repo/commit/a1b2c3d))

### Bug Fixes

* **auth:** handle expired JWT tokens returning 401 instead of 500 ([e4f5g6h](https://github.com/org/repo/commit/e4f5g6h))
```
Key discipline: never hand-edit `CHANGELOG.md` — once humans start editing it, the automated tool either overwrites changes or produces conflicts. Treat it like a generated file: owned by the tool, read by humans, committed to the repo for discoverability.

**Q24. In an RBI/PCI-DSS regulated environment, what role does automated versioning play in audit trails and change management?**
A: Automated versioning directly supports several compliance requirements:
- **Traceability** — every production artifact (Docker image, npm package, Lambda deployment package) is tagged with an immutable SemVer that maps back to an exact git commit, a set of Conventional Commits, and (via GitHub Releases) a human-readable changelog. Auditors can trace "what changed in v2.5.0" without needing to read raw git diffs.
- **Change management records** — the GitHub Release (or Release PR in `release-please`) serves as a timestamped, attributed change record. In a regulated workflow, requiring a Release PR approval before merge gives you an approval record tied to a named engineer and a timestamp.
- **Reproducibility** — `package-lock.json` + a SemVer tag on every release means you can rebuild the exact artifact from any past version. This matters for incident investigation ("what exact code was running during the March 12 outage?").
- **Segregation of duties** — CI/CD automation (a service account) publishes; no human has npm publish credentials on their laptop. This is a control that auditors look for.

**Q25. Scenario: "Your team ships a Node.js internal SDK used by 6 other services at your fintech. One service is still on v1.x and can't upgrade. How do you manage versioning and backport critical security patches?"**
A: This is a standard multi-track maintenance problem. The approach:
1. **Create a `v1` maintenance branch** from the last `1.x` tag: `git checkout -b v1 v1.8.0`.
2. **Configure `semantic-release` to release from `v1` as a maintenance channel**:
```jsonc
{
  "branches": [
    "main",
    { "name": "v1", "range": "1.x", "channel": "v1" }
  ]
}
```
3. **Backport patches** — cherry-pick the security fix commit onto the `v1` branch. `semantic-release` will bump `1.8.1` on the `v1` channel independently of whatever `main` is at (`2.x`).
4. **Communicate clearly** — document in the README and GitHub Releases that `v1.x` is in security-patch-only maintenance mode with an EOL date, pressuring the lagging service to upgrade.
This pattern is how Node.js itself, Express, and most major open-source projects manage LTS vs. current tracks.

## Quick Comparison Table

| Aspect | `semantic-release` | `release-please` | `standard-version` |
|---|---|---|---|
| Release trigger | Automatic on push to `main` | Merge of Release PR | Manual CLI run |
| Human gate | None | Yes (PR merge) | Yes (manual) |
| Changelog generation | Auto, via plugin | Auto, built-in | Auto, built-in |
| npm publish | Via plugin | Via workflow step | Separate step |
| Monorepo support | Via `multi-semantic-release` | Native (manifest mode) | Limited |
| GitHub Releases | Via plugin | Built-in | Separate step |
| Maintenance/backport | Multi-branch channels | Multi-branch (range config) | Manual |
| Status | Actively maintained | Actively maintained | Deprecated |
| Best for | Continuous delivery | Cadence-based releases | Legacy projects |

**Tip for the interview:** At 5 YOE, interviewers expect you to know *why* versioning conventions matter, not just recite them. Be ready to walk through: "how would you set this up from scratch for a shared internal SDK?" — cover Conventional Commits enforcement (commitlint + Husky), the `semantic-release` CI job, the `fetch-depth: 0` gotcha, and multi-branch channels for pre-release. Also have the `BREAKING CHANGE` footer war story ready — nearly everyone who ships shared libraries has been burned by an unexpected MAJOR bump or by accidentally shipping a breaking change as a PATCH because the commit message was wrong. That story, plus explaining how you'd prevent it, is usually worth more than a perfect definition of SemVer.
