# Docker Image Build and Push in CI — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the role of Docker image build and push in a CI pipeline?**
A: The build-and-push step is the bridge between source code and a deployable unit. The CI pipeline compiles/transpiles source, packages it into an immutable Docker image, and pushes that image to a container registry. Everything downstream — tests against the real image, security scans, staging deploys, production deploys — operates on that exact artifact. The discipline is: **build once, promote everywhere**. Rebuilding the image per environment defeats the guarantee that what you tested is what you shipped.

**Q2. What is a container registry, and what options exist?**
A: A container registry is a versioned storage system for Docker images — analogous to npm for packages or Maven for JARs. Common options:
- **Docker Hub** — public default; free tier rate-limits unauthenticated pulls (100/6hr per IP). Unsuitable as a primary registry for CI at scale.
- **Amazon ECR (Elastic Container Registry)** — tight AWS IAM integration; supports image scanning, lifecycle policies, and cross-account access. Standard choice for AWS-hosted workloads.
- **Google Artifact Registry / GCR** — equivalent for GCP.
- **GitHub Container Registry (GHCR)** — integrated with GitHub repos and Actions; free for public images.
- **GitLab Container Registry** — built into GitLab projects; `$CI_REGISTRY_IMAGE` predefined.
- **Self-hosted (Harbor, Nexus)** — for air-gapped or strict data residency requirements; common in regulated fintech.

**Q3. What is an image tag, and what tagging strategy should you use in CI?**
A: An image tag is a human-readable pointer to a specific image digest. Tags are mutable by default — pushing `myapp:latest` twice overwrites the first. A robust CI tagging strategy uses multiple tags per image:
- **Commit SHA** (`myapp:a3f9c12`) — immutable, unique, the source of truth. Every CI-built image must have this.
- **Branch slug** (`myapp:main`, `myapp:feature-xyz`) — mutable pointer to the latest build from that branch. Useful for staging auto-deploys.
- **Semver** (`myapp:v1.4.2`) — applied at release time, maps a human-readable version to a specific SHA.
- **`latest`** — avoid in production pipelines. It's a mutable pointer with no audit trail; two `latest` images from different commits are indistinguishable.

The SHA tag is what gets promoted through environments — staging and production deploy `myapp:a3f9c12`, not `myapp:latest`.

**Q4. What is a Dockerfile, and what are its key instructions relevant to CI builds?**
A: A Dockerfile is the declarative recipe for building an image. Key instructions:
- `FROM` — base image. Use specific digests (`FROM node:20-alpine@sha256:...`) in production to prevent silent base image updates.
- `WORKDIR` — sets the working directory inside the container.
- `COPY` — copies files from build context into the image. Order matters for layer caching.
- `RUN` — executes commands during build (installs deps, compiles). Each `RUN` creates a layer.
- `ENV` — sets environment variables baked into the image.
- `ARG` — build-time variables passed via `--build-arg`; not persisted in the final image (unlike `ENV`).
- `EXPOSE` — documents the port the container listens on (informational only; doesn't publish).
- `CMD` / `ENTRYPOINT` — defines the default process when the container runs.
- `USER` — sets the running user. Always drop to a non-root user before `CMD` in production images.

**Q5. What is the Docker build context, and why does its size matter in CI?**
A: The build context is the set of files sent from the CI runner to the Docker daemon at build time. Every file in the current directory (unless excluded by `.dockerignore`) is included. A large context (e.g., accidentally including `node_modules/`, `.git/`, or large test fixtures) causes:
- Slow build startup — transferring a 2GB context takes significant time even locally.
- Cache invalidation — any file change in a large context can invalidate layers unnecessarily.
- Bloated images — if `COPY .` is used without precision, dev artifacts end up in the image.

`.dockerignore` is the fix — it works identically to `.gitignore` and should always exclude: `node_modules/`, `.git/`, `*.log`, `coverage/`, `dist/` (if rebuilt inside Docker), test fixtures, and local env files.

## Section 2: Multi-Stage Builds

**Q6. What is a multi-stage Docker build, and why is it essential for CI?**
A: A multi-stage build uses multiple `FROM` instructions in one Dockerfile, where each stage can selectively copy artifacts from prior stages. The final image contains only what the last stage explicitly includes:
```dockerfile
# Stage 1 — dependencies
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production

# Stage 2 — build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 3 — runtime
FROM node:20-alpine AS runtime
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
USER node
CMD ["node", "dist/main.js"]
```
The runtime image excludes: TypeScript source, dev dependencies, test files, build toolchain. A 1.4GB build image becomes a 150MB runtime image. Smaller images = faster pulls in K8s, smaller security scan surface, lower registry storage cost.

**Q7. What is a "build stage" vs a "test stage" inside a multi-stage Dockerfile, and when do you use them?**
A: You can embed test execution inside the Dockerfile itself:
```dockerfile
FROM node:20-alpine AS test
WORKDIR /app
COPY --from=builder /app .
RUN npm test

FROM node:20-alpine AS runtime
# Only reached if test stage exits 0
COPY --from=deps /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/main.js"]
```
If `npm test` fails, the build fails and no image is pushed. This pattern is useful for simpler pipelines where tests are cheap — it guarantees no untested image can be pushed. The downside: test output is embedded in Docker build logs (harder to parse for CI test reports), and you can't easily publish JUnit/coverage artifacts from inside a build stage. For most teams at 5 YOE, running tests as a separate CI job and using the Dockerfile purely for packaging is cleaner and more observable.

**Q8. How does layer caching work in a multi-stage build, and how do you optimize for it?**
A: Docker caches each layer (each `RUN`, `COPY`, `ADD` instruction). If the inputs to a layer haven't changed since the last build, Docker reuses the cached layer instead of re-executing. The cache is invalidated for a layer and all subsequent layers the moment any input changes.

Key optimization: **copy dependency manifests before source code**:
```dockerfile
# Good — deps layer only rebuilds when package-lock.json changes
COPY package*.json ./
RUN npm ci

# Then copy source — this layer rebuilds on every code change
COPY . .
RUN npm run build
```
```dockerfile
# Bad — copies everything first; any source change rebuilds npm ci
COPY . .
RUN npm ci && npm run build
```
In CI, this means a code-only change (no lockfile change) hits cache on the `npm ci` layer and jumps straight to the build step — saving 2–5 minutes per build for large dependency trees.

## Section 3: Registry Authentication & Pushing

**Q9. How does a CI job authenticate to a container registry?**
A: Authentication method depends on the registry:
- **Docker Hub** — username + access token as CI secrets; `docker login -u $DOCKERHUB_USER -p $DOCKERHUB_TOKEN`.
- **ECR** — AWS credentials (access key + secret, or OIDC role) + `aws ecr get-login-password | docker login --username AWS --password-stdin $ECR_REGISTRY`. The ECR token is short-lived (12 hours).
- **GHCR** — `echo $GITHUB_TOKEN | docker login ghcr.io -u $GITHUB_ACTOR --password-stdin`. Uses the built-in `GITHUB_TOKEN` — no extra secrets needed.
- **GitLab Registry** — `docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY`. All three variables are predefined in GitLab CI.

In all cases: credentials must be stored as masked CI secrets, never hardcoded in the YAML or Dockerfile.

**Q10. What is OIDC-based registry authentication, and why is it better than static credentials?**
A: OIDC (OpenID Connect) lets the CI job prove its identity to a cloud provider via a signed JWT token, and exchange it for short-lived credentials — without storing any long-lived secret. For ECR:
```yaml
# GitHub Actions
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/github-actions-ecr
    aws-region: ap-south-1

- uses: aws-actions/amazon-ecr-login@v2
```
No `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` stored anywhere. The IAM role's trust policy restricts which repos/branches can assume it. This eliminates: key rotation toil, blast radius of a leaked secret (token expires in minutes), and the risk of a developer accidentally committing a CI access key. In fintech/PCI-DSS environments, OIDC-based auth is increasingly required — static long-lived keys are a finding.

**Q11. How do you push multiple tags to a registry in one CI step efficiently?**
A: Build once and tag multiple times — don't rebuild the image per tag:
```bash
IMAGE="123456789.dkr.ecr.ap-south-1.amazonaws.com/my-service"
SHA_TAG="${IMAGE}:${GITHUB_SHA::7}"
BRANCH_TAG="${IMAGE}:main"
LATEST_TAG="${IMAGE}:latest"

docker build -t "$SHA_TAG" -t "$BRANCH_TAG" -t "$LATEST_TAG" .
docker push "$SHA_TAG"
docker push "$BRANCH_TAG"
docker push "$LATEST_TAG"
```
Or use `docker buildx imagetools create` to add tags without pulling/re-pushing. Multiple tags pointing to the same image digest cost almost nothing in registry storage — tags are metadata pointers, not copies of the image layers.

**Q12. What is `docker push` actually transferring, and how does layer deduplication work?**
A: `docker push` transfers only layers that don't already exist in the registry. Each layer is identified by its content hash (SHA256). If a layer with that hash is already present (from a previous push, or from the base image), the registry accepts a reference to it rather than the raw data. In practice:
- The `node:20-alpine` base layer is already in most registries — pushing a new image based on it transfers 0 bytes for that layer.
- A code-only change (no dep change) uploads only the changed layers — the `node_modules` layer is reused.
- This means a fast CI push after a code change might transfer only 5–20MB even for a 200MB image.

## Section 4: BuildKit and Advanced Build Features

**Q13. What is Docker BuildKit, and why should you enable it in CI?**
A: BuildKit is Docker's next-generation build engine, enabled with `DOCKER_BUILDKIT=1` or `docker buildx build`. Key advantages over the legacy builder:
- **Parallel stage execution** — independent stages in a multi-stage Dockerfile build concurrently.
- **Better layer caching** — more granular cache invalidation.
- **Cache mounts** — persistent cache directories across builds (e.g., `~/.npm` cache) without baking them into image layers.
- **Secret mounts** — inject secrets at build time without leaving them in any layer.
- **Inline cache** — embed cache metadata in the pushed image for use in subsequent builds.
- **Multi-platform builds** — build ARM and AMD64 images from a single CI runner.

BuildKit is the default in Docker 23+ and is always preferred in CI. Enable explicitly if on older Docker versions: `export DOCKER_BUILDKIT=1`.

**Q14. What are BuildKit cache mounts, and how do they speed up CI builds?**
A: Cache mounts (`--mount=type=cache`) give a `RUN` instruction access to a persistent directory that survives across builds but is never included in the image layer:
```dockerfile
RUN --mount=type=cache,target=/root/.npm \
    npm ci

RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```
Without cache mounts, `npm ci` downloads all packages from the internet on every build (or from a CI-level cache, which requires upload/download overhead). With cache mounts on a persistent runner, the npm cache directory survives on the runner's disk between builds — `npm ci` becomes a fast local resolution for unchanged packages. This can reduce a 3-minute `npm ci` to 15 seconds on cache hit.

**Q15. What are BuildKit secret mounts, and why are they safer than `ARG` for secrets?**
A: Secret mounts (`--mount=type=secret`) inject a secret into a `RUN` step without it persisting in any image layer:
```dockerfile
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
```
```bash
# In CI
docker buildx build \
  --secret id=npm_token,env=NPM_TOKEN \
  -t myapp:latest .
```
With `ARG NPM_TOKEN`, the secret is embedded in the layer history and retrievable via `docker history` or `docker inspect` — a security vulnerability. With `--mount=type=secret`, the secret is available only during that `RUN` step's execution and never written to any layer. Always use secret mounts for private registry credentials, npm tokens, or API keys needed during build.

**Q16. What is `docker buildx` and multi-platform builds, and when do you need them in CI?**
A: `docker buildx` is the CLI plugin for BuildKit's extended build capabilities, including building images for multiple CPU architectures from a single pipeline:
```bash
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myapp:a3f9c12 \
  --push .
```
This produces a multi-arch manifest — `docker pull myapp:a3f9c12` on an ARM machine pulls the ARM variant, on AMD64 it pulls the AMD64 variant. When do you need this:
- **AWS Graviton (ARM64) deployments** — EC2 `t4g`/`m7g` instances are ARM; your AMD64 image won't run on them.
- **Apple Silicon dev parity** — developers on M1/M2 Macs run ARM; building AMD64-only causes performance penalty under Rosetta.
- **Multi-cloud or hybrid** — different regions/clusters may use different architectures.

Multi-platform builds use QEMU emulation (slower, 5–10× penalty for the non-native arch) or native runners (one AMD64 runner + one ARM runner, merged with `buildx imagetools`).

## Section 5: Registry Cache Strategies in CI

**Q17. What is registry-based layer cache (`--cache-from`, `--cache-to`) and when do you use it?**
A: In CI, each job often runs on a fresh ephemeral runner with no local Docker cache. Registry-based caching stores and retrieves cache from the container registry itself:
```bash
docker buildx build \
  --cache-from type=registry,ref=myapp:buildcache \
  --cache-to type=registry,ref=myapp:buildcache,mode=max \
  -t myapp:$SHA .
  --push
```
`mode=max` caches all intermediate layers (not just the final stage), enabling cache hits even when the final output changes. This is the standard approach for ephemeral CI runners (GitHub Actions, GitLab Kubernetes runners) where there's no persistent local disk between jobs. The trade-off: initial push of the build cache takes time and registry storage; subsequent builds that hit the cache are significantly faster.

**Q18. What is `--cache-from` with an inline cache embedded in the image?**
A: Inline cache embeds cache metadata directly in the pushed image rather than a separate cache tag:
```bash
docker buildx build \
  --cache-from myapp:latest \
  --build-arg BUILDKIT_INLINE_CACHE=1 \
  -t myapp:$SHA \
  --push
```
The next build pulls `myapp:latest` and reuses its layer metadata as cache. This is simpler than a separate buildcache tag (no extra cache image to manage) but less effective — it only caches layers in the final stage (`mode=min`). Use inline cache for simple single-stage builds; use `type=registry,mode=max` for complex multi-stage builds where intermediate stage caching matters.

**Q19. What is GitHub Actions' built-in cache for Docker (`actions/cache` with Docker layers), and how does it compare to registry cache?**
A: GitHub Actions provides a local cache store (keyed by a string, stored on GitHub's infrastructure) that can persist Docker layer tarballs between runs:
```yaml
- uses: actions/cache@v4
  with:
    path: /tmp/.buildx-cache
    key: buildx-${{ hashFiles('Dockerfile', 'package-lock.json') }}
    restore-keys: buildx-

- uses: docker/build-push-action@v6
  with:
    cache-from: type=local,src=/tmp/.buildx-cache
    cache-to: type=local,dest=/tmp/.buildx-cache-new,mode=max
```
Comparison to registry cache:
- **GitHub cache** — faster for GitHub Actions (no registry auth, stored close to runners); limited to 10GB per repo; deleted after 7 days of non-use; not available cross-repo.
- **Registry cache** — portable (any CI system can use it), unlimited size (registry storage cost), persistent indefinitely, works across repos sharing the same registry.

For GitHub Actions + ECR/GHCR stacks: use GitHub Actions cache for speed, registry cache as fallback for cross-runner or cross-repo scenarios.

## Section 6: Security and Compliance in CI Image Builds

**Q20. What is image scanning, and where does it fit in the CI pipeline?**
A: Image scanning inspects a built Docker image for known CVEs in OS packages, language runtime packages, and application dependencies. It runs **after the build stage** (needs the image to exist) and **before the deploy stage** (gates deployment on scan results). Tools:
- **Trivy** (Aqua Security) — fast, open-source, scans OS + language packages, supports SARIF/JSON output, integrates with GitHub/GitLab natively.
- **Grype** (Anchore) — similar scope to Trivy; good SBOM integration.
- **AWS ECR scanning** — native ECR feature (basic or enhanced via Inspector); triggers automatically on push.
- **Snyk Container** — commercial; integrates with PR workflows to show diff of new vs. existing vulnerabilities.

```bash
trivy image \
  --exit-code 1 \
  --severity CRITICAL,HIGH \
  --ignore-unfixed \
  myapp:$SHA
```
`--exit-code 1` makes Trivy fail the CI job on findings. `--ignore-unfixed` skips CVEs with no available fix — reducing noise from OS vendor lag.

**Q21. How do you enforce a non-root user in a Docker image, and why does it matter for CI builds?**
A: Running a container as root is a significant security risk — if the container process is compromised, the attacker has root inside the container (and potentially on the host if the container runtime is misconfigured). Enforcement:
```dockerfile
# Create a non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Set file ownership
COPY --chown=appuser:appgroup --from=builder /app/dist ./dist

# Switch to non-root before CMD
USER appuser

CMD ["node", "dist/main.js"]
```
In CI, enforce this as a lint check on the Dockerfile using `hadolint` — it flags `USER root` or a missing `USER` instruction before `CMD`. In Kubernetes, pair with a `securityContext.runAsNonRoot: true` pod spec to reject containers that attempt to run as root at the orchestration layer.

**Q22. What is image signing, and when would you implement it in a CI pipeline?**
A: Image signing cryptographically attests that a specific image digest was produced by a trusted pipeline, not tampered with in transit or in the registry. Tools:
- **Cosign** (Sigstore project) — signs images using keyless signing (OIDC-based, no key management) or a static key:
```bash
# Keyless signing — uses the CI OIDC token as identity
cosign sign --yes myapp@$IMAGE_DIGEST
```
- **Notary v2 / Docker Content Trust** — older standard; more complex to operate.

Verification happens at deploy time — the Kubernetes admission controller (e.g., Kyverno or Sigstore's Policy Controller) rejects any image that isn't signed by the expected identity. Use cases: supply chain integrity (proving no image was injected between CI and prod), compliance attestation (SOC 2, SLSA Level 3). At 5 YOE in fintech, image signing is increasingly relevant — Sigstore/Cosign has made it operationally tractable where Notary was not.

**Q23. What is a distroless or scratch base image, and when should you use one?**
A: A distroless image (Google's `gcr.io/distroless/nodejs`) contains only the language runtime and your application — no shell, no package manager, no OS utilities. A scratch image is completely empty. Benefits:
- **Minimal attack surface** — no `bash`, no `curl`, no `apt` means many common post-exploitation techniques don't work.
- **Fewer CVEs** — fewer OS packages = fewer vulnerability findings in image scans.
- **Smaller size** — distroless Node.js images are ~40MB vs ~170MB for `node:20-alpine`.

Trade-offs:
- **Harder to debug** — `kubectl exec` into a distroless container and you have no shell. Use ephemeral debug containers (`kubectl debug`) or build a separate debug image.
- **Init scripts** — if your startup needs shell scripts, distroless won't work without refactoring to native language equivalents.

In a NestJS fintech service, `node:20-alpine` with a non-root user is a practical middle ground — significantly more secure than the full Debian image, still debuggable.

## Section 7: CI Pipeline Integration Patterns

**Q24. What does a complete Docker build-and-push job look like in GitHub Actions?**
A:
```yaml
jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # for OIDC
      contents: read

    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-ci
          aws-region: ap-south-1

      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr-login

      - uses: docker/setup-buildx-action@v3

      - uses: actions/cache@v4
        with:
          path: /tmp/.buildx-cache
          key: buildx-${{ runner.os }}-${{ hashFiles('Dockerfile','package-lock.json') }}
          restore-keys: buildx-${{ runner.os }}-

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ steps.ecr-login.outputs.registry }}/my-service:${{ github.sha }}
            ${{ steps.ecr-login.outputs.registry }}/my-service:latest
          cache-from: type=local,src=/tmp/.buildx-cache
          cache-to: type=local,dest=/tmp/.buildx-cache-new,mode=max
          build-args: |
            APP_VERSION=${{ github.sha }}

      - name: Move cache
        run: |
          rm -rf /tmp/.buildx-cache
          mv /tmp/.buildx-cache-new /tmp/.buildx-cache
```

**Q25. What does a complete Docker build-and-push job look like in GitLab CI?**
A:
```yaml
build-image:
  stage: build
  image: docker:26
  services:
    - docker:26-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    IMAGE: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - |
      docker buildx build \
        --cache-from type=registry,ref=$CI_REGISTRY_IMAGE:buildcache \
        --cache-to type=registry,ref=$CI_REGISTRY_IMAGE:buildcache,mode=max \
        --tag $IMAGE \
        --tag $CI_REGISTRY_IMAGE:latest \
        --push .
  artifacts:
    reports:
      dotenv: build.env
  after_script:
    - echo "IMAGE_TAG=$CI_COMMIT_SHORT_SHA" >> build.env
```
The `dotenv` artifact makes `IMAGE_TAG` available to all downstream jobs (deploy, scan) without passing it manually.

**Q26. How do you pass the built image reference to downstream pipeline jobs?**
A: The image tag (commit SHA) must be communicated from the build job to deploy/scan jobs. Three patterns:
- **Predictable convention** — derive the tag deterministically from CI variables (`$GITHUB_SHA`, `$CI_COMMIT_SHORT_SHA`). Every job knows the tag without any inter-job communication. Simplest and most robust.
- **Job outputs** — GitHub Actions: `echo "image_tag=$SHA >> $GITHUB_OUTPUT"`; GitLab: `dotenv` artifact. Explicit but adds coupling.
- **Registry label/tag convention** — the build job pushes `myapp:branch-main`; the deploy job always deploys `myapp:branch-main`. Mutable, acceptable for auto-deploy to staging, not for production.

The convention approach (deriving SHA from built-in CI vars) is preferred — it requires no artifact passing and works across parallel jobs that all know the same SHA from the triggering commit.

**Q27. How do you prevent a broken image from being pushed on a failed build?**
A: Several layers of defence:
- **Build failure = no push** — the `docker build` command exits non-zero on any `RUN` instruction that fails. If you separate `build` and `push` as sequential shell commands, a build failure stops execution before push. With `docker buildx build --push`, build and push are atomic — the image is only pushed if the build fully succeeds.
- **Test gate before push** — structure the pipeline so the push job only runs if the test job passes (`needs: [test]` in GitHub Actions, `needs:` in GitLab). Even if the build technically succeeds, an untested image is never pushed.
- **Registry immutability** — configure ECR image tag immutability: once `myapp:a3f9c12` is pushed, it cannot be overwritten. This prevents a broken rebuild from silently replacing a good image with the same tag.

**Q28. How do you handle private npm/pip packages that are needed during `docker build` in CI?**
A: The naive approach — hardcoding an npm token in the Dockerfile or passing it as `ARG` — leaks the token into image layer history. Correct approaches:
- **BuildKit secret mount** — inject the token at build time without persisting it in any layer:
```dockerfile
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
```
```bash
docker buildx build --secret id=npm_token,env=NPM_TOKEN .
```
- **Private registry proxy / pull-through cache** — self-hosted Verdaccio or Nexus proxies the private registry. The CI job authenticates to the proxy with credentials at job startup; the Dockerfile uses the proxy URL with no credentials embedded.
- **Pre-built base image** — build a custom base image (`FROM myorg/node-with-deps:20`) that pre-installs shared private packages. The application Dockerfile only installs application-specific deps. Reduces the secret handling surface to one canonical base image build.

## Section 8: Scenario Questions

**Q29. "Your Docker builds in CI take 12 minutes. How do you diagnose and fix it?"**
A: Systematic diagnosis:
1. **Break down timing** — add `time` before each build step or use BuildKit's `--progress=plain` output to see per-layer timing. Identify the slowest layer.
2. **Common culprits and fixes:**
   - `npm ci` / `pip install` takes 5+ minutes → enable BuildKit cache mounts, or check if CI-level cache is being populated/restored correctly.
   - `COPY . .` before dependency install → reorder: copy lockfile, install deps, then copy source.
   - Large build context → check `.dockerignore`; if context transfer takes 30s+, you're uploading `node_modules/` or `.git/`.
   - Multi-stage build running stages sequentially → enable BuildKit (`DOCKER_BUILDKIT=1`) for parallel stage execution.
   - No registry cache on ephemeral runners → implement `--cache-from type=registry` to pull cache from the last successful build.
3. **Validate fix** — measure before/after. A well-cached build of a NestJS service should be under 2 minutes on a cold runner with registry cache, under 30 seconds with warm cache.

**Q30. "A security scan found a critical CVE in your base image after a production deployment. What's your response and how do you prevent recurrence?"**
A: Incident response:
1. **Assess blast radius** — is the CVE exploitable in your runtime context? (Many OS CVEs are in tools not present at runtime in multi-stage builds.)
2. **Pull a patched base image** — update `FROM node:20-alpine` to the patched version; rebuild and redeploy via the standard pipeline.
3. **Rollback vs patch-forward** — if a patch isn't available yet, evaluate whether the risk warrants rolling back or deploying a mitigation (WAF rule, network policy).

Prevention:
- **Scheduled rebuild pipeline** — run the full build-scan-push pipeline nightly or weekly, even without a code change, to pick up base image patches.
- **Automated base image updates** — Dependabot or Renovate can open PRs when a new `node:20-alpine` digest is available.
- **Pin to digest, not tag** — `FROM node:20-alpine@sha256:abc...` makes base image updates explicit rather than silently pulling a new version.
- **Trivy in CI with `--exit-code 1`** — would have caught this before the production deployment.

**Q31. "How do you ensure the exact same Docker image that passed tests in staging is what gets deployed to production?"**
A: The entire architecture must prevent any image rebuild between staging and production. The mechanism:
1. CI builds `myapp:a3f9c12` and pushes it to the registry **once** in the build stage.
2. The staging deploy job pulls and deploys `myapp:a3f9c12` — not `myapp:latest`, not `myapp:main`.
3. Post-staging smoke tests pass.
4. The production deploy job references the **exact same tag** (`a3f9c12`) — it does not trigger a new build.
5. ECR image tag immutability ensures `myapp:a3f9c12` cannot be overwritten between staging and production deploys.

What to audit: check your pipeline YAML — if the prod deploy job has a `docker build` step, that's the anti-pattern. The prod deploy job should only `docker pull` (implicitly, via `kubectl set image` or a Helm upgrade with the image tag parameter) — never build.

**Q32. "How do you handle Docker-in-Docker (DinD) vs rootless Docker in CI?"**
A: Docker-in-Docker (DinD) runs a Docker daemon inside a CI container — required when the CI executor is itself a Docker container (GitLab Kubernetes runner, GitHub Actions). Modes:
- **Privileged DinD** (`docker:dind` service) — the inner Docker daemon has full host access. Works reliably but is a security risk: a compromised job has root on the runner node. Acceptable on isolated self-hosted runners; avoid on shared runner pools.
- **Rootless Docker / Podman** — builds images without root or privileged access. Podman is daemonless and can run fully rootless in a container; used as a drop-in `docker` replacement in regulated CI environments.
- **`docker buildx` with BuildKit daemon socket** — in GitHub Actions, the `docker/setup-buildx-action` creates a BuildKit builder container. No full DinD required; more secure.
- **Kaniko** — Google's tool for building Docker images inside Kubernetes without a Docker daemon or privileged access at all. Standard choice for GitLab Kubernetes runners in security-sensitive environments:
```yaml
build:
  image:
    name: gcr.io/kaniko-project/executor:latest
    entrypoint: [""]
  script:
    - /kaniko/executor
        --context $CI_PROJECT_DIR
        --dockerfile Dockerfile
        --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

## Quick Reference Table

| Concept                    | Key Detail                                                                                        |
|----------------------------|---------------------------------------------------------------------------------------------------|
| Build once, promote        | One image built per commit; same SHA tag promoted through staging → prod; never rebuild per env   |

| `.dockerignore`            | Always exclude `node_modules/`, `.git/`, `coverage/`, `.env`; large context = slow build         |
| Multi-stage build          | Separates build tools from runtime; runtime image excludes source, dev deps, compiler toolchain   |

| BuildKit                   | Enable always; parallel stages, cache mounts, secret mounts, multi-platform, inline cache         |
| Cache mounts               | `--mount=type=cache` — persistent dep cache on runner disk; never baked into image layer          |
| Secret mounts              | `--mount=type=secret` — secrets available during `RUN` only; never in layer history               |
| `ARG` for secrets          | Anti-pattern — visible in `docker history`; always use secret mounts instead                      |
| Registry auth              | OIDC > static keys; ECR OIDC, GHCR uses `$GITHUB_TOKEN`, GitLab uses predefined vars             |
| `--cache-from/--cache-to`  | Registry-based layer cache; use `mode=max` for multi-stage; essential on ephemeral runners        |
| Image scanning             | Trivy/Grype post-build, pre-deploy; `--exit-code 1` on CRITICAL/HIGH; `--ignore-unfixed`         |
| Non-root user              | Always `USER nonroot` before `CMD`; enforce with `hadolint` in lint stage                         |
| Image signing              | Cosign keyless signing via OIDC; verified at deploy by admission controller                       |
| Distroless/scratch         | Minimal attack surface; no shell (harder to debug); `node:20-alpine` is practical middle ground   |
| ECR tag immutability       | Prevents overwriting a pushed tag; ensures staging image = prod image                             |
| DinD vs Kaniko             | DinD = privileged (simpler, less secure); Kaniko = no daemon, no privilege (K8s CI standard)     |
| Scheduled rebuild          | Nightly pipeline rebuild to pick up base image CVE patches without code changes                   |
| Private package secrets    | BuildKit secret mount or pre-built base image; never `ARG NPM_TOKEN`                             |
