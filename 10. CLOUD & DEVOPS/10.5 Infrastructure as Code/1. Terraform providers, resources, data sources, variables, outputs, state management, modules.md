# Infrastructure (IaC): Terraform — Providers, Resources, Data Sources, Variables, Outputs, State & Modules — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals — Providers & Resources

**Q1. What is a Terraform provider, and what does it actually do under the hood?**
A: A provider is a plugin that translates Terraform's declarative config into API calls for a specific platform (AWS, GCP, Kubernetes, Datadog, etc.). Under the hood, each provider is a separate binary that Terraform downloads on `terraform init`, communicates with the Terraform core via gRPC using the provider protocol. The provider binary implements CRUD operations for each resource type it exposes — when you `terraform apply`, Terraform calls the provider's `Create`, `Read`, `Update`, or `Delete` functions depending on the diff between desired state and current state. You never write provider code yourself in normal usage; you configure it:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  required_version = ">= 1.6.0"
}

provider "aws" {
  region = var.aws_region
}
```

**Q2. What is a Terraform resource, and how does Terraform decide whether to create, update, or destroy it?**
A: A resource block declares a single infrastructure object you want Terraform to manage — an EC2 instance, an S3 bucket, a security group. Terraform decides what action to take by comparing three things: the desired state (your `.tf` config), the current state (recorded in `terraform.tfstate`), and the real-world state (read via a `Refresh` call to the provider API during `plan`). The outcome for each resource is one of: no-op, create, update-in-place, destroy-and-recreate (when an argument is immutable and changed), or destroy. The `terraform plan` output always shows which of these will happen and *why* before you apply.

**Q3. What does `terraform init` actually do, and what does it set up?**
A: `terraform init` is the bootstrapping step that must run before any other Terraform command. It:
1. **Downloads providers** — fetches the provider binaries declared in `required_providers` from the Terraform registry (or a private mirror) into `.terraform/providers/`.
2. **Downloads modules** — fetches any remote module sources into `.terraform/modules/`.
3. **Initializes the backend** — configures the state backend (local file, S3, Terraform Cloud, etc.) and migrates state if the backend config changed.
4. **Generates `.terraform.lock.hcl`** — a provider dependency lock file recording the exact provider versions and their checksums. This file should be committed to git so all team members and CI use identical provider binaries.

**Q4. What is the difference between `terraform plan` and `terraform apply`?**
A: `plan` is a dry-run — it calls the provider's `Read` API to refresh real-world state, diffs it against your config and state file, and prints a human-readable execution plan without making any changes. `apply` executes that plan, making the actual API calls to create/update/destroy resources. In CI/CD pipelines the idiomatic pattern is: run `plan` in a PR pipeline (for review), save the plan to a file (`terraform plan -out=tfplan`), and then in the apply job run `terraform apply tfplan` — this ensures apply executes *exactly* the plan that was reviewed, not a re-computed one that may differ if infra changed between plan and apply.

**Q5. What are `terraform.tfvars` and `*.auto.tfvars` files, and how does Terraform load them?**
A: These files provide variable values without passing `-var` flags on the CLI. Terraform automatically loads:
- `terraform.tfvars` — always auto-loaded if it exists.
- `*.auto.tfvars` — any file matching this glob is auto-loaded, in lexicographic order.
- Files passed explicitly with `-var-file=staging.tfvars` — loaded when specified.

Variable precedence (lowest to highest): default in declaration → `terraform.tfvars` → `*.auto.tfvars` → `-var-file` → `-var` CLI flags → environment variables (`TF_VAR_<name>`). In CI/CD pipelines, injecting secrets via `TF_VAR_db_password` (environment variable) is the standard — it avoids secrets touching the filesystem or appearing in plan output.

## Section 2: Data Sources & Variables

**Q6. What is a data source, and how does it differ from a resource?**
A: A data source is a read-only query against existing infrastructure — it fetches information about something Terraform didn't create (or hasn't created yet in this run) and makes that data available to the rest of your config. A resource *owns* the object: Terraform creates it, manages its lifecycle, and can destroy it. A data source *borrows* data: Terraform reads it during `plan`/`apply` but never modifies or destroys it.

```hcl
# Read an existing VPC created outside this Terraform workspace
data "aws_vpc" "shared" {
  filter {
    name   = "tag:Name"
    values = ["shared-services-vpc"]
  }
}

# Use the fetched data
resource "aws_subnet" "loans_service" {
  vpc_id     = data.aws_vpc.shared.id
  cidr_block = "10.0.4.0/24"
}
```
This is how you bridge between separately-managed Terraform workspaces or between Terraform-managed and manually-created infra — a common pattern when a platform team owns the VPC and each product team owns their own subnets and services.

**Q7. What are the variable types Terraform supports, and when would you use `object` vs `map`?**
A:
- **Primitive types** — `string`, `number`, `bool`.
- **Collection types** — `list(T)`, `set(T)`, `map(T)` — all elements must be the same type `T`.
- **Structural types** — `object({...})` with named attributes of *different* types; `tuple([...])` with positional elements of different types.

Use `map(string)` when you have a homogeneous key-value set with an arbitrary set of keys (e.g., tags). Use `object()` when you have a fixed schema with known attribute names and potentially mixed types:

```hcl
variable "rds_config" {
  type = object({
    instance_class    = string
    allocated_storage = number
    multi_az          = bool
  })
  default = {
    instance_class    = "db.t3.medium"
    allocated_storage = 100
    multi_az          = true
  }
}
```

Use `object()` for structured configuration that benefits from schema validation at plan time — Terraform will error if a caller passes a mismatched type, not silently at runtime.

**Q8. What is variable validation, and when should you use it?**
A: Terraform `variable` blocks support a `validation` sub-block that runs at plan time and rejects invalid inputs with a custom error message. This shifts errors left — rather than discovering an invalid value during an `apply` failure (after 2 minutes of API calls), you catch it immediately during `plan`.

```hcl
variable "environment" {
  type        = string
  description = "Deployment environment"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be one of: dev, staging, prod."
  }
}

variable "cidr_block" {
  type = string
  validation {
    condition     = can(cidrnetmask(var.cidr_block))
    error_message = "Must be a valid CIDR block (e.g. 10.0.0.0/16)."
  }
}
```
In fintech infra, validations on `environment`, CIDR ranges, and instance types prevent engineers from accidentally applying `prod`-scale resources to `dev` accounts and vice versa.

**Q9. What are `sensitive` variables, and how do they affect plan output and state?**
A: Marking a variable `sensitive = true` tells Terraform to redact its value from plan and apply terminal output — you'll see `(sensitive value)` instead of the actual secret. However, this is UI-only redaction: the value is still stored in plaintext in `terraform.tfstate`. This is why state files must be treated as secrets themselves — stored in an encrypted backend (S3 with SSE-KMS, Terraform Cloud, etc.) with restricted IAM access. Never commit a state file to git. The `sensitive` flag is not a security boundary; it's a display convenience that prevents accidental log leakage.

**Q10. What is the `locals` block, and when should you use it instead of variables?**
A: `locals` defines computed, intermediate values within a module — think of them as private constants or derived expressions that you want to name and reuse without exposing as external inputs. Unlike `variable` blocks, locals have no type constraints, no defaults, and callers cannot override them.

```hcl
locals {
  # Build a standardized name prefix for all resources
  name_prefix = "${var.project}-${var.environment}"

  # Compute tags once, reuse everywhere
  common_tags = merge(var.extra_tags, {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
  })
}

resource "aws_s3_bucket" "loan_documents" {
  bucket = "${local.name_prefix}-loan-documents"
  tags   = local.common_tags
}
```
Use `locals` for: computed expressions used in multiple places, tag maps assembled from multiple sources, and logic that belongs inside the module (not exposed to callers). Use `variables` for anything a caller needs to configure. Mixing the two — making a `variable` that callers never set because it has a hardcoded default — is a common code smell that `locals` fixes.

## Section 3: Outputs

**Q11. What are Terraform outputs, and what are their three main use cases?**
A: An `output` block marks a value as an explicit export from a Terraform root module or child module.

```hcl
output "alb_dns_name" {
  value       = aws_lb.api.dns_name
  description = "DNS name of the application load balancer"
}
```

Three use cases:
1. **Human inspection** — values printed after `terraform apply` or retrievable via `terraform output`. Useful for looking up resource attributes (ARNs, IPs, DNS names) without opening the AWS console.
2. **Cross-module data passing** — a child module exposes outputs that a root module reads via `module.networking.alb_dns_name`. This is the primary mechanism for composing modules.
3. **Cross-workspace data sharing** — a platform team's Terraform workspace outputs a VPC ID; a product team's workspace reads it via a `terraform_remote_state` data source (or better, via SSM Parameter Store/AWS Secrets Manager to avoid tight coupling between state files).

**Q12. When should you mark an output `sensitive = true`?**
A: When the output value contains a secret (database password, private key, API token). Marking it sensitive prevents the value from printing in `terraform apply` terminal output and prevents it from appearing in plan diffs when the output is consumed by another module. However — same caveat as sensitive variables — the value is still in the state file in plaintext. A sensitive output consumed by another module also propagates the sensitivity flag, so Terraform will redact it in the consuming module's plan output too, which can be confusing for debugging. Always store actual secrets in a secrets manager (AWS Secrets Manager, Vault) and output only ARNs or references, not the secret values themselves.

**Q13. What is `terraform_remote_state`, and what are its downsides?**
A: `terraform_remote_state` is a data source that reads another workspace's state file and exposes its outputs. It's a common pattern for sharing data between workspaces:

```hcl
data "terraform_remote_state" "networking" {
  backend = "s3"
  config = {
    bucket = "myorg-terraform-state"
    key    = "networking/terraform.tfstate"
    region = "ap-south-1"
  }
}

resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.networking.outputs.private_subnet_id
}
```

Downsides: tight coupling between workspaces — if the networking team renames an output, your workspace breaks at plan time. Also, the consuming workspace needs read access to the *entire* state file of the networking workspace (which may contain sensitive data beyond what you need). A looser alternative: have the producing workspace write outputs to SSM Parameter Store or an S3 config file, and have the consuming workspace read from there — decoupled, and you can grant fine-grained read access per parameter.

## Section 4: State Management

**Q14. What is the Terraform state file, and why is it necessary?**
A: `terraform.tfstate` is a JSON file that records Terraform's knowledge of the real-world resources it manages — their IDs, attributes, dependencies, and metadata. It's necessary because Terraform is declarative: it needs to know *what it already created* to compute the diff between desired and current state. Without state, Terraform would have no way to know that `aws_instance.app` already exists as `i-0abc123def456` and would try to create a duplicate on every `apply`. State is also the source of truth for `terraform destroy` (it knows what to tear down) and `terraform output` (it knows current output values without re-reading the provider).

**Q15. What is remote state, and what backend options are common in AWS-based fintech stacks?**
A: Remote state stores the state file outside the local filesystem, enabling team collaboration (no "who has the state file?" problem) and locking. Common backends:

```hcl
terraform {
  backend "s3" {
    bucket         = "myorg-terraform-state-prod"
    key            = "services/loans-api/terraform.tfstate"
    region         = "ap-south-1"
    encrypt        = true
    kms_key_id     = "arn:aws:kms:ap-south-1:123456789:key/mrk-abc123"
    dynamodb_table = "terraform-state-lock"
  }
}
```

- **S3 + DynamoDB** — the standard AWS pattern. S3 stores the state file (with versioning and SSE-KMS encryption enabled); DynamoDB provides distributed locking (prevents two concurrent `apply` operations corrupting state). Near-mandatory for any team larger than one person.
- **Terraform Cloud / HCP Terraform** — managed backend with locking, run history, policy enforcement (Sentinel), and a UI. Preferred when you want to avoid managing the S3/DynamoDB infra yourself.
- **GitLab-managed state** — GitLab has a built-in Terraform state backend, useful if you're already on GitLab CI.

**Q16. What is state locking, and what happens if a lock is never released?**
A: When `terraform apply` or `terraform plan` starts, Terraform writes a lock entry to DynamoDB (for the S3 backend) containing a unique lock ID, the operation type, and a timestamp. Any concurrent Terraform operation on the same state checks for the lock and blocks, preventing simultaneous modifications that would corrupt state. If a process crashes mid-apply (CI runner killed, laptop dies), the lock remains in DynamoDB and every subsequent plan/apply fails with "Error acquiring the state lock." Resolution: `terraform force-unlock <lock-id>` — but only after confirming no apply is actually running. In CI, always set a timeout on apply jobs and use CI-level safeguards to prevent simultaneous runs on the same workspace (GitHub Actions `concurrency` groups).

**Q17. What is `terraform import`, and what problem does it solve?**
A: `terraform import` brings an existing real-world resource (created manually, by CloudFormation, or by another tool) under Terraform management by mapping it into the state file. The resource must already have a corresponding `resource` block in your config.

```bash
# Import an existing RDS instance into Terraform state
terraform import aws_db_instance.loans_db myorg-loans-db-prod
```

After import, the resource is in state but you must manually write (or copy from `terraform show`) the matching config — `import` doesn't generate HCL for you (though Terraform 1.5+ added a `import` block and `terraform plan -generate-config-out=generated.tf` that can auto-generate config as an experimental feature). The common use case in fintech: "ops created a security group manually during an incident; now we want it in Terraform so it's version-controlled and reproducible."

**Q18. What is `terraform state mv`, and when would you use it?**
A: `terraform state mv` moves a resource from one address in the state to another without destroying and recreating it. Use cases:
- **Renaming a resource** — if you rename `aws_s3_bucket.docs` to `aws_s3_bucket.loan_documents` in your config, Terraform plans a destroy + create. Running `terraform state mv aws_s3_bucket.docs aws_s3_bucket.loan_documents` tells Terraform the resource is the same object under a new name — next `plan` shows no-op.
- **Moving a resource into a module** — if you refactor a root resource into a child module, `terraform state mv aws_s3_bucket.docs module.storage.aws_s3_bucket.loan_documents` avoids the destructive recreate.
- **Splitting workspaces** — moving a resource from one state file to another using `terraform state mv` in combination with `terraform state pull` / `terraform state push`.

**Q19. What is `terraform taint` (and its modern replacement), and when should you use it?**
A: `terraform taint <resource>` marked a resource for forced replacement on the next apply — useful when a resource's real-world state is corrupted or drifted in a way Terraform can't detect. It's been deprecated since Terraform 1.0 in favor of the `-replace` flag:

```bash
terraform apply -replace="aws_instance.app_server"
```

`-replace` is safer because it shows the destroy+create in the plan output *before* you commit to applying. Use it when: an EC2 instance has a corrupted filesystem, an SSL cert needs cycling, or a Kubernetes node needs reprovisioning — cases where the resource's config hasn't changed but the real object needs to be recreated fresh.

**Q20. What is state drift, and how do you detect and reconcile it?**
A: State drift is when the real-world infrastructure diverges from what Terraform's state file records — someone manually changed a security group rule in the console, an auto-scaling event modified an instance, or an external process deleted a resource. Terraform detects drift during `terraform plan` via its `Refresh` step (the provider reads current real-world attributes and compares them to state). The plan output will show unexpected changes to resources you didn't touch in your config. Reconciliation options:
- **Let Terraform fix it** — run `apply` to restore the desired state. Correct if the manual change was wrong.
- **Update the config to match reality** — if the manual change was intentional, update your `.tf` files and run `apply` (which now shows no-op). Then the config reflects truth.
- **`terraform refresh`** — updates state to match reality without changing real infra. Rarely needed now that `plan` does a refresh by default; can be useful to update state after out-of-band changes you want to acknowledge without applying.
For regulated environments: manual console changes should be prohibited via SCP (AWS Service Control Policy) or IAM boundaries — drift is a compliance risk.

## Section 5: Modules

**Q21. What is a Terraform module, and what problem does it solve?**
A: A module is a directory of `.tf` files treated as a reusable, encapsulated unit. Every Terraform config is technically a module — the root module. Child modules are called by the root or other modules via a `module` block:

```hcl
module "loans_rds" {
  source  = "./modules/rds"         # local path
  # source = "terraform-aws-modules/rds/aws"  # Terraform Registry
  # source = "git::https://github.com/myorg/tf-modules.git//rds?ref=v2.1.0"

  db_name        = "loans"
  instance_class = var.rds_instance_class
  subnet_ids     = module.networking.private_subnet_ids
  vpc_id         = module.networking.vpc_id
}
```

Modules solve the DRY problem — instead of copy-pasting 80 lines of RDS config across 5 services, you write it once in a module and call it with different inputs. They also enforce architectural standards: a platform team can publish a `module "rds"` that bakes in encryption, backup retention, and parameter group settings per your RBI/PCI-DSS requirements, so product teams can't accidentally create unencrypted databases.

**Q22. What is the difference between a root module and a child module in terms of state and lifecycle?**
A: Resources in a child module live in the *same* state file as the root module that calls it — a module is not a separate state boundary; it's a namespace in the same state. The resource address in state becomes `module.<name>.<resource_type>.<resource_name>` (e.g., `module.loans_rds.aws_db_instance.this`). This means: destroying the root module destroys everything in child modules too. If you want lifecycle isolation (e.g., the VPC should survive if you destroy the app layer), you need *separate workspaces* (separate state files), not separate modules. Modules = code organization. Workspaces/state files = lifecycle isolation.

**Q23. How do you version modules, and what's the recommended pattern for an internal module registry?**
A: For public modules from the Terraform Registry, pin the version:
```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.1"
}
```
For internal modules in a private git repo, pin to a tag:
```hcl
module "rds" {
  source = "git::https://github.com/myorg/terraform-modules.git//modules/rds?ref=v3.2.0"
}
```
Tag every release of your internal module repo with SemVer. The `?ref=v3.2.0` pinning ensures all callers get a reproducible version — `?ref=main` is dangerous because a module update breaks every caller simultaneously with no pin to roll back to. For teams with many internal modules, Terraform Cloud's private registry (or Spacelift, Atlantis with a module registry) provides a versioned catalog with a UI, similar to an internal npm registry.

**Q24. What are `for_each` and `count` in Terraform, and when do you use each?**
A: Both create multiple instances of a resource or module from a single block.

- **`count`** — creates N instances indexed by integer. Simple but fragile: if you remove item at index 1 from a list of 3, Terraform renumbers index 2 to index 1 and plans an update (or destroy+create) on the shifted resource. Use only when the count is truly a number with no semantic identity.
- **`for_each`** — iterates over a `map` or `set(string)`, keying each instance by a stable string. Removing one key only affects that instance — others are untouched. Strongly preferred for any collection where items have identity.

```hcl
# Prefer for_each for environments with identity
variable "environments" {
  type    = set(string)
  default = ["dev", "staging", "prod"]
}

resource "aws_s3_bucket" "env_configs" {
  for_each = var.environments
  bucket   = "myorg-config-${each.key}"
  tags     = { Environment = each.key }
}

# Access: aws_s3_bucket.env_configs["prod"].arn
```

The `count` vs `for_each` choice matters most for long-lived resources: if you ever add or remove an item, `count` causes cascading plan changes while `for_each` surgically modifies only the affected instance.

**Q25. Scenario: "Your team has grown to 8 engineers deploying to 3 environments (dev, staging, prod). Terraform applies are conflicting and state is getting corrupted. How do you redesign the workspace and state structure?"**
A: This is the classic "monolith state file" problem. The redesign has two axes: *workspace isolation* and *state segmentation*.

**Workspace isolation per environment** — each environment (`dev`, `staging`, `prod`) gets its own state file in its own S3 key (or Terraform Cloud workspace). A push to `main` triggers a plan/apply only in `dev`; promotion to `staging` and `prod` is a separate pipeline step requiring approval. No engineer runs `terraform apply` locally against `prod` — CI/CD is the only applier.

**State segmentation by lifecycle layer** — even within one environment, split state by how frequently components change and who owns them:

```
state/
  networking/           # VPC, subnets, route tables — changes rarely, owned by platform team
  data/                 # RDS, ElastiCache, S3 — changes infrequently
  services/
    loans-api/          # ECS service, ALB, IAM roles — changes per deploy
    kyc-service/
    nach-service/
```

Each layer is a separate Terraform workspace with its own state file. The `services` layer reads VPC/subnet IDs from the `networking` layer via SSM Parameter Store (not `terraform_remote_state` — avoids tight coupling). Each service team owns their own `services/<name>/` workspace and can apply independently without blocking others. Platform team's `networking` changes go through a PR + plan review before apply.

This structure eliminates concurrent apply conflicts (each workspace has independent state and lock), reduces blast radius (a bad `loans-api` apply can't destroy the VPC), and maps ownership cleanly to team boundaries.

## Quick Comparison Table

| Concept | Owns Lifecycle? | In State File? | Modifiable by Terraform? | Primary Use Case |
|---|---|---|---|---|
| `resource` | Yes | Yes | Yes (CRUD) | Create and manage infra |
| `data` source | No | Partially (cached) | No | Read existing infra |
| `module` | Inherits from root | Yes (namespaced) | Yes | Code reuse and encapsulation |
| `variable` | N/A | No | N/A | External input to a module |
| `local` | N/A | No | N/A | Internal computed values |
| `output` | N/A | Yes | N/A | Export values to callers/humans |

| State Backend | Locking? | Encryption | Best For |
|---|---|---|---|
| Local file | No | No | Solo dev / learning |
| S3 + DynamoDB | Yes (DynamoDB) | SSE-KMS | AWS-native teams |
| Terraform Cloud | Yes (built-in) | Yes (managed) | Teams wanting managed platform |
| GitLab HTTP | Yes (built-in) | Yes | GitLab-native CI shops |

(Q25), "how do you handle secrets in Terraform?" (Q9 + Q12), "what's the difference between a module and a workspace?" (Q22), and "how do you handle drift?" (Q20). Also know the `fetch-depth` equivalent for Terraform CI: the `[skip ci]` + `terraform plan -out=tfplan` pattern (Q4) — forgetting to save plan output between the plan and apply steps in CI is how you accidentally apply a different plan than the one reviewed.
