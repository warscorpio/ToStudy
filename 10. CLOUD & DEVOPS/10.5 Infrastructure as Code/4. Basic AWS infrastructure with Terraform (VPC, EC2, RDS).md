# Infrastructure (IaC): Basic AWS Infrastructure with Terraform (VPC, EC2, RDS) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the typical order of resource creation when provisioning VPC, EC2, and RDS with Terraform, and why does order matter?**
A: Terraform resolves the dependency graph automatically based on resource references — you don't declare order explicitly. But the implicit dependency chain for a standard three-tier setup is:

```
VPC
 └─ Subnets (public + private)
     ├─ Internet Gateway → Route Table (public subnets)
     ├─ NAT Gateway (in public subnet) → Route Table (private subnets)
     ├─ Security Groups (reference VPC ID)
     ├─ EC2 instances (reference subnet ID + security group IDs)
     └─ DB Subnet Group → RDS instance (reference private subnet IDs + security group IDs)
```

Terraform builds this graph by analyzing `resource.id` references. If `aws_instance.app` references `aws_security_group.app.id`, Terraform knows the security group must exist before the instance. You only need explicit `depends_on` when a dependency exists outside of a direct attribute reference — for example, if EC2 user-data implicitly relies on a route table being in place (not referenced in the resource block) and Terraform can't infer that.

**Q2. Walk through the minimal Terraform configuration needed to create a production-ready VPC.**
A: A production VPC requires more than just `aws_vpc` — it needs subnets, route tables, and gateways:

```hcl
# VPC
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = { Name = "${var.project}-vpc" }
}

# Public subnets (one per AZ for HA)
resource "aws_subnet" "public" {
  for_each = { for idx, az in var.availability_zones :
    az => { cidr = cidrsubnet("10.0.0.0/16", 8, idx) }
  }

  vpc_id                  = aws_vpc.main.id
  cidr_block              = each.value.cidr
  availability_zone       = each.key
  map_public_ip_on_launch = true

  tags = { Name = "${var.project}-public-${each.key}", Tier = "public" }
}

# Private subnets (for EC2 app tier and RDS)
resource "aws_subnet" "private" {
  for_each = { for idx, az in var.availability_zones :
    az => { cidr = cidrsubnet("10.0.0.0/16", 8, idx + 10) }
  }

  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value.cidr
  availability_zone = each.key

  tags = { Name = "${var.project}-private-${each.key}", Tier = "private" }
}

# Internet Gateway (public traffic)
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "${var.project}-igw" }
}

# Elastic IP + NAT Gateway (private subnet outbound)
resource "aws_eip" "nat" {
  domain = "vpc"
}

resource "aws_nat_gateway" "main" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[var.availability_zones[0]].id
  tags          = { Name = "${var.project}-nat" }
}

# Route tables
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main.id
  }
}

# Route table associations
resource "aws_route_table_association" "public" {
  for_each       = aws_subnet.public
  subnet_id      = each.value.id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "private" {
  for_each       = aws_subnet.private
  subnet_id      = each.value.id
  route_table_id = aws_route_table.private.id
}
```

Note `enable_dns_support` and `enable_dns_hostnames` on the VPC — both are required for RDS endpoint resolution and for EC2 instances to resolve AWS service endpoints (S3, SSM, Secrets Manager) by hostname within the VPC.

**Q3. What is `cidrsubnet()` and how do you use it to carve subnets out of a VPC CIDR without hardcoding?**
A: `cidrsubnet(prefix, newbits, netnum)` divides a CIDR block into smaller subnets. `newbits` is how many additional bits to add to the mask; `netnum` is the index of the subnet within that range:

```hcl
# VPC CIDR: 10.0.0.0/16
cidrsubnet("10.0.0.0/16", 8, 0)  # → 10.0.0.0/24  (public AZ-a)
cidrsubnet("10.0.0.0/16", 8, 1)  # → 10.0.1.0/24  (public AZ-b)
cidrsubnet("10.0.0.0/16", 8, 2)  # → 10.0.2.0/24  (public AZ-c)
cidrsubnet("10.0.0.0/16", 8, 10) # → 10.0.10.0/24 (private AZ-a)
cidrsubnet("10.0.0.0/16", 8, 11) # → 10.0.11.0/24 (private AZ-b)
cidrsubnet("10.0.0.0/16", 8, 12) # → 10.0.12.0/24 (private AZ-c)
```

In a `for_each` loop over AZs, use the AZ index as `netnum` to assign consistent CIDRs across runs. The gap between public (0–2) and private (10–12) indices gives room to add more subnet tiers (database, management) without renumbering. Renumbering in Terraform means destroying and recreating subnets — a destructive operation that takes EC2 and RDS instances with it.

**Q4. How do Security Groups work in Terraform, and what is the difference between inline rules and separate `aws_security_group_rule` resources?**
A: A security group controls inbound and outbound traffic. You can define rules inline within `aws_security_group` or as standalone `aws_security_group_rule` resources — but not both for the same group. Mixing causes conflicts:

```hcl
# Pattern 1 — Inline rules (simpler, single resource)
resource "aws_security_group" "app" {
  name        = "${var.project}-app-sg"
  description = "App tier security group"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]
    description     = "Allow traffic from ALB only"
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
    description = "Allow all outbound"
  }
}

# Pattern 2 — Standalone rules (preferred when rules reference each other)
resource "aws_security_group" "rds" {
  name        = "${var.project}-rds-sg"
  description = "RDS security group"
  vpc_id      = aws_vpc.main.id
  # No inline ingress/egress blocks
}

resource "aws_security_group_rule" "rds_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.app.id
  security_group_id        = aws_security_group.rds.id
  description              = "Allow Postgres from app tier"
}
```

Standalone `aws_security_group_rule` resources avoid circular dependency issues — if `sg-a` allows traffic from `sg-b` and `sg-b` allows traffic from `sg-a`, inline rules create a cycle that Terraform can't resolve. With standalone rules, each rule is an independent resource and Terraform can create the two empty security groups first, then add the cross-referencing rules.

## Section 2: EC2 Instance Configuration

**Q5. What are the key Terraform resources required to launch an EC2 instance in a private subnet with SSM access instead of a bastion host?**
A: SSM Session Manager is the modern alternative to bastions — no SSH, no open port 22, no key pair management. The EC2 instance needs an IAM role, VPC endpoints for SSM, and no public IP:

```hcl
# IAM role for EC2 with SSM access
resource "aws_iam_role" "app" {
  name = "${var.project}-app-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "ec2.amazonaws.com" }
      Action    = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "ssm" {
  role       = aws_iam_role.app.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

resource "aws_iam_instance_profile" "app" {
  name = "${var.project}-app-profile"
  role = aws_iam_role.app.name
}

# EC2 instance in private subnet
resource "aws_instance" "app" {
  ami                    = data.aws_ami.amazon_linux.id
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.private[var.availability_zones[0]].id
  iam_instance_profile   = aws_iam_instance_profile.app.name
  vpc_security_group_ids = [aws_security_group.app.id]

  # No key_name — SSM replaces SSH
  # No public IP — private subnet only

  user_data = base64encode(templatefile("${path.module}/userdata.sh", {
    db_host = aws_db_instance.main.address
    region  = var.aws_region
  }))

  root_block_device {
    volume_type = "gp3"
    volume_size = 30
    encrypted   = true
  }

  tags = { Name = "${var.project}-app" }
}

# VPC endpoints required for SSM (no NAT gateway path to SSM APIs)
resource "aws_vpc_endpoint" "ssm" {
  for_each = toset(["ssm", "ssmmessages", "ec2messages"])

  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.aws_region}.${each.key}"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = values(aws_subnet.private)[*].id
  security_group_ids  = [aws_security_group.vpc_endpoints.id]
  private_dns_enabled = true
}
```

VPC endpoints for `ssm`, `ssmmessages`, and `ec2messages` are all required. If instances are in a fully private subnet with no NAT gateway, missing any one endpoint causes SSM to silently fail to connect.

**Q6. How do you use `data "aws_ami"` to dynamically fetch the latest Amazon Linux AMI instead of hardcoding an AMI ID?**
A: AMI IDs are region-specific and rotate with each new release. Hardcoding them causes `plan` to show no drift but deploys stale AMIs when you `taint` or recreate instances:

```hcl
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }

  filter {
    name   = "state"
    values = ["available"]
  }
}

# Reference in EC2
resource "aws_instance" "app" {
  ami = data.aws_ami.amazon_linux.id
  # ...
}

# Output the resolved AMI for audit
output "ami_id" {
  value       = data.aws_ami.amazon_linux.id
  description = "AMI used by app instances"
}
```

`most_recent = true` picks the latest matching AMI at plan time. This means each `terraform apply` after a new AMI release will show a change (new AMI ID) on EC2 instances — whether that change triggers an in-place update or an instance replacement depends on whether the `ami` argument forces replacement (it does for `aws_instance`). In production, pin the AMI by storing the data source output in a variable and only updating it deliberately, rather than always using `most_recent`.

**Q7. What is `user_data` in EC2, how do you pass dynamic values to it with Terraform, and what are its limitations?**
A: `user_data` is a script or cloud-init configuration that runs once when the instance first boots. In Terraform, `templatefile()` renders a shell script with variable substitution:

```hcl
# userdata.sh (in the same module directory)
#!/bin/bash
set -euo pipefail

# Install app dependencies
yum install -y postgresql15

# Write DB connection config
cat > /etc/app/config.env <<EOF
DB_HOST=${db_host}
DB_PORT=5432
DB_NAME=${db_name}
AWS_REGION=${region}
EOF

# Start the application
systemctl enable app
systemctl start app
```

```hcl
# Terraform resource
resource "aws_instance" "app" {
  user_data = base64encode(templatefile("${path.module}/userdata.sh", {
    db_host = aws_db_instance.main.address
    db_name = var.db_name
    region  = var.aws_region
  }))
  # ...
}
```

Limitations:
- `user_data` is limited to 16 KB. For larger scripts, store them in S3 and have `user_data` fetch and execute.
- `user_data` runs only on first boot. If you change `user_data` in Terraform, the instance must be replaced for the new script to run — it's not re-executed on a running instance. Use `lifecycle { create_before_destroy = true }` to avoid downtime during replacement.
- Errors in `user_data` don't propagate to Terraform — the instance reaches `running` state successfully even if `user_data` failed. Check `/var/log/cloud-init-output.log` on the instance. For reliable bootstrapping, prefer AWS Systems Manager Run Command or Ansible post-provisioning.

## Section 3: RDS Configuration

**Q8. Walk through the complete Terraform resources needed to provision a production-ready RDS PostgreSQL instance.**
A: RDS requires a subnet group spanning private subnets, a parameter group for engine config, and a security group locked to the app tier:

```hcl
# DB Subnet Group — spans all private subnets across AZs
resource "aws_db_subnet_group" "main" {
  name        = "${var.project}-db-subnet-group"
  subnet_ids  = [for s in aws_subnet.private : s.id]
  description = "Private subnets for RDS"

  tags = { Name = "${var.project}-db-subnet-group" }
}

# Parameter Group — engine-specific settings
resource "aws_db_parameter_group" "postgres" {
  name   = "${var.project}-postgres16"
  family = "postgres16"

  parameter {
    name  = "log_connections"
    value = "1"
  }

  parameter {
    name  = "log_min_duration_statement"
    value = "1000"  # Log queries > 1s
  }

  parameter {
    name  = "shared_preload_libraries"
    value = "pg_stat_statements"
  }
}

# RDS instance
resource "aws_db_instance" "main" {
  identifier        = "${var.project}-postgres"
  engine            = "postgres"
  engine_version    = "16.3"
  instance_class    = var.db_instance_class
  allocated_storage = var.db_storage_gb
  storage_type      = "gp3"
  storage_encrypted = true
  kms_key_id        = aws_kms_key.rds.arn

  db_name  = var.db_name
  username = var.db_username
  password = random_password.db.result  # Never hardcode

  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.rds.id]
  parameter_group_name   = aws_db_parameter_group.postgres.name

  multi_az               = var.multi_az           # true for prod
  publicly_accessible    = false
  deletion_protection    = var.deletion_protection # true for prod
  skip_final_snapshot    = false
  final_snapshot_identifier = "${var.project}-final-${formatdate("YYYY-MM-DD", timestamp())}"

  backup_retention_period = var.backup_retention_days  # 7–35 for prod
  backup_window           = "03:00-04:00"
  maintenance_window      = "Mon:04:00-Mon:05:00"

  performance_insights_enabled = true
  monitoring_interval          = 60  # Enhanced monitoring every 60s
  monitoring_role_arn          = aws_iam_role.rds_monitoring.arn

  tags = { Name = "${var.project}-postgres" }

  lifecycle {
    prevent_destroy = true  # Extra guard beyond deletion_protection
  }
}

# Random password managed by Terraform
resource "random_password" "db" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}|;:,.<>?"
}

# Store password in Secrets Manager — EC2 reads from here at runtime
resource "aws_secretsmanager_secret" "db_password" {
  name                    = "${var.project}/rds/password"
  recovery_window_in_days = 7
  kms_key_id              = aws_kms_key.secrets.arn
}

resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id     = aws_secretsmanager_secret.db_password.id
  secret_string = random_password.db.result
}
```

`deletion_protection = true` prevents the RDS instance from being deleted via the AWS console or API — but Terraform's `prevent_destroy` lifecycle rule blocks Terraform itself from destroying it. Both are needed: `deletion_protection` blocks the console; `prevent_destroy` blocks `terraform destroy`.

**Q9. Why should you never put an RDS password in `terraform.tfvars` or commit it to source control, and what is the correct pattern?**
A: `terraform.tfvars` is typically committed to version control. A DB password in that file becomes a permanent secret in git history — removing it from `HEAD` doesn't erase it from previous commits, which are accessible to anyone with repo access. The correct pattern has three parts:

```hcl
# 1. Generate the password inside Terraform
resource "random_password" "db" {
  length  = 32
  special = true
}

# 2. Store it in Secrets Manager (not in state-only)
resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id     = aws_secretsmanager_secret.db_password.id
  secret_string = random_password.db.result
}

# 3. Application reads from Secrets Manager at runtime — not from env vars or config files
# Node.js example:
# const secret = await secretsClient.getSecretValue({ SecretId: '/myapp/rds/password' });
# const password = secret.SecretString;
```

The password still exists in Terraform state (in the `random_password` resource and the `aws_db_instance` resource). State must be encrypted at rest (S3 SSE with KMS) and access-controlled. This is unavoidable — Terraform must know the password to provision the instance. The application should never read the password from state or from `user_data`; it reads from Secrets Manager using the EC2 instance's IAM role.

**Q10. What is `multi_az` on an RDS instance, and how does Terraform handle a Multi-AZ configuration differently from a single-AZ one?**
A: `multi_az = true` tells RDS to provision a synchronous standby replica in a second Availability Zone. AWS manages the standby invisibly — it doesn't appear as a separate `aws_db_instance` resource in Terraform. The single `aws_db_instance` resource with `multi_az = true` provisions both the primary and the standby:

```hcl
resource "aws_db_instance" "main" {
  multi_az = var.environment == "prod" ? true : false
  # All other config is the same regardless of multi_az
}
```

What changes operationally: the `endpoint` output resolves to the primary's DNS name. On failover, AWS updates the DNS record to point to the former standby — the endpoint address stays the same, but connections to the old primary are dropped and must be re-established. Application connection pools should be configured with retry logic and short connection timeouts for smooth failover. Terraform sees no state change during an AWS-initiated failover — the `aws_db_instance` resource still shows the same configuration; only which physical instance is primary has changed behind the scenes.

## Section 4: Outputs, Data Sources, and Cross-Resource References

**Q11. What Terraform outputs should you expose from a VPC + EC2 + RDS module, and why?**
A: Outputs serve two purposes: human inspection (`terraform output`) and cross-module reference (`terraform_remote_state` or module return values). A well-designed output set for this stack:

```hcl
# VPC outputs — consumed by other modules (EKS, ALB, Lambda)
output "vpc_id" {
  value       = aws_vpc.main.id
  description = "VPC ID"
}

output "public_subnet_ids" {
  value       = [for s in aws_subnet.public : s.id]
  description = "Public subnet IDs (for ALB, NAT)"
}

output "private_subnet_ids" {
  value       = [for s in aws_subnet.private : s.id]
  description = "Private subnet IDs (for EC2, RDS, Lambda)"
}

# EC2 outputs
output "app_instance_id" {
  value       = aws_instance.app.id
  description = "App EC2 instance ID (for SSM target)"
}

output "app_security_group_id" {
  value       = aws_security_group.app.id
  description = "App SG ID — reference for adding ingress rules from other services"
}

# RDS outputs — never expose the password as an output
output "rds_endpoint" {
  value       = aws_db_instance.main.address
  description = "RDS host (without port)"
}

output "rds_port" {
  value       = aws_db_instance.main.port
  description = "RDS port"
}

output "rds_secret_arn" {
  value       = aws_secretsmanager_secret.db_password.arn
  description = "Secrets Manager ARN for DB password — grant IAM access to this ARN, not to the password itself"
  sensitive   = false  # The ARN is not sensitive; the secret content is
}
```

Mark an output `sensitive = true` if it contains the actual secret value (prevents it from being printed in CI logs). The password secret ARN is safe to expose — it lets other IAM principals be granted `secretsmanager:GetSecretValue` access to that specific secret.

**Q12. How do you reference another Terraform module's VPC outputs when provisioning EC2 and RDS in a separate module?**
A: Two patterns — module composition (same root module) and remote state reference (separate deployments):

```hcl
# Pattern 1 — Module composition: networking and compute in the same root module
module "networking" {
  source               = "./modules/networking"
  project              = var.project
  availability_zones   = var.availability_zones
}

module "compute" {
  source             = "./modules/compute"
  vpc_id             = module.networking.vpc_id
  private_subnet_ids = module.networking.private_subnet_ids
  public_subnet_ids  = module.networking.public_subnet_ids
}

module "database" {
  source             = "./modules/database"
  vpc_id             = module.networking.vpc_id
  private_subnet_ids = module.networking.private_subnet_ids
  app_sg_id          = module.compute.app_security_group_id
}
```

```hcl
# Pattern 2 — Remote state: networking is a separate Terraform root module
data "terraform_remote_state" "networking" {
  backend = "s3"
  config = {
    bucket = "myorg-terraform-state"
    key    = "platform/networking/terraform.tfstate"
    region = "ap-south-1"
  }
}

resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.networking.outputs.private_subnet_ids[0]
  # ...
}
```

Module composition (Pattern 1) is simpler and lets Terraform plan changes across the entire stack atomically — but puts everything in one state file with one apply gate. Remote state (Pattern 2) allows the networking team to own and evolve the VPC independently, at the cost of tight output coupling — if the networking module renames an output, all consumers break. The SSM Parameter Store pattern mitigates this: networking module writes subnet IDs to SSM, compute module reads from SSM with a `data "aws_ssm_parameter"` source — the coupling is through a named SSM key, not an output name.

## Section 5: State Management and Import

**Q13. How do you import an existing manually-created RDS instance or EC2 instance into Terraform state?**
A: `terraform import` reads the real-world resource's current configuration into your state file, but does **not** generate `.tf` code. After importing, `terraform plan` will show drift if your `.tf` config doesn't match the actual resource attributes:

```bash
# Import syntax: terraform import <resource_address> <aws_resource_id>

# Import RDS instance
terraform import aws_db_instance.main myorg-postgres

# Import EC2 instance
terraform import aws_instance.app i-0a1b2c3d4e5f67890

# Import VPC
terraform import aws_vpc.main vpc-0123456789abcdef0

# Import subnet (must match the resource address)
terraform import 'aws_subnet.private["ap-south-1a"]' subnet-0abc123
```

The workflow for a clean import:
1. Write the `.tf` resource block with the attributes you know (instance type, engine version, etc.).
2. Run `terraform import`.
3. Run `terraform plan` — it will show what attributes differ between your config and the real resource.
4. Update your `.tf` config to match the actual values until `plan` shows no changes.
5. Commit both the imported state (in S3) and the reconciled `.tf` config.

Terraform 1.5+ introduced `import` blocks in `.tf` files, which make the import declarative and part of the plan:

```hcl
import {
  to = aws_db_instance.main
  id = "myorg-postgres"
}
```

Running `terraform plan` with this block shows the import as a planned action — the import happens on `terraform apply`, not as a separate CLI step. This makes imports reviewable and auditable in CI.

**Q14. What is `lifecycle { prevent_destroy = true }` and how does it interact with `terraform destroy`?**
A: `prevent_destroy` is a meta-argument that causes Terraform to error out during plan if the plan includes destroying that resource — regardless of why (explicit destroy, resource replacement due to config change, or `terraform destroy`):

```hcl
resource "aws_db_instance" "main" {
  # ...

  lifecycle {
    prevent_destroy       = true
    create_before_destroy = true  # For instance replacements, create new first
    ignore_changes        = [engine_version]  # Don't flag minor version updates as drift
  }
}
```

`prevent_destroy = true` is appropriate for:
- RDS instances (prevent accidental data loss)
- S3 buckets with critical data
- KMS keys (deleting a KMS key makes all data encrypted with it permanently inaccessible)

It does **not** prevent:
- Removal of the resource block from `.tf` — Terraform will still plan a destroy; `prevent_destroy` blocks it from succeeding
- AWS console or API deletions — `deletion_protection` on the RDS resource is the AWS-side guard

To actually destroy a resource with `prevent_destroy = true`, you must remove the lifecycle block (or set it to `false`), run `apply` to update the state, then run `destroy`. This two-step process is intentional friction.

## Section 6: Security and Fintech-Specific Patterns

**Q15. How do you enforce encryption at rest for EC2 EBS volumes and RDS using Terraform and KMS?**
A: Encryption requires explicit KMS keys — the default AWS-managed keys are acceptable for most workloads, but regulated environments (PCI-DSS, RBI) typically require customer-managed KMS keys for key rotation control and audit visibility:

```hcl
# Customer-managed KMS key for RDS
resource "aws_kms_key" "rds" {
  description             = "RDS encryption key for ${var.project}"
  deletion_window_in_days = 30
  enable_key_rotation     = true  # Automatic annual rotation

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect    = "Allow"
        Principal = { AWS = "arn:aws:iam::${data.aws_caller_identity.current.account_id}:root" }
        Action    = "kms:*"
        Resource  = "*"
      },
      {
        Effect    = "Allow"
        Principal = { Service = "rds.amazonaws.com" }
        Action    = ["kms:GenerateDataKey", "kms:Decrypt"]
        Resource  = "*"
      }
    ]
  })
}

resource "aws_kms_alias" "rds" {
  name          = "alias/${var.project}-rds"
  target_key_id = aws_kms_key.rds.key_id
}

# RDS with KMS
resource "aws_db_instance" "main" {
  storage_encrypted = true
  kms_key_id        = aws_kms_key.rds.arn
  # ...
}

# EC2 EBS with KMS
resource "aws_instance" "app" {
  root_block_device {
    volume_type = "gp3"
    volume_size = 30
    encrypted   = true
    kms_key_id  = aws_kms_key.ec2.arn
  }

  ebs_block_device {
    device_name = "/dev/sdf"
    volume_type = "gp3"
    volume_size = 100
    encrypted   = true
    kms_key_id  = aws_kms_key.ec2.arn
  }
}
```

`enable_key_rotation = true` rotates the KMS key material annually — AWS does this without any downtime or re-encryption; it just means new data is encrypted with a new key version, while old ciphertext remains readable via the previous key version (retained indefinitely). For compliance evidence, this rotation is visible in CloudTrail and in the KMS key's rotation status.

**Q16. How do you prevent EC2 instances from having public IPs, and how do you enforce this as a Terraform convention?**
A: Two layers — resource configuration and (optionally) an SCP-level guardrail:

```hcl
# Resource level — private subnet + no public IP
resource "aws_instance" "app" {
  subnet_id                   = aws_subnet.private[...].id
  associate_public_ip_address = false  # Explicit even though private subnets default to false

  # No key_name — no SSH access even if someone opens port 22
}

# Subnet level — disable public IP map at subnet creation
resource "aws_subnet" "private" {
  map_public_ip_on_launch = false  # Default is false, but explicit is clearer
  # ...
}
```

For Terraform-native policy enforcement, use Sentinel (Terraform Cloud/Enterprise) or Open Policy Agent (OPA) with `conftest`:

```rego
# OPA policy — deny any aws_instance with a public IP
deny[msg] {
  resource := input.planned_values.root_module.resources[_]
  resource.type == "aws_instance"
  resource.values.associate_public_ip_address == true
  msg := sprintf("EC2 instance '%s' must not have a public IP", [resource.address])
}
```

This policy runs in CI against the `terraform plan` JSON output (`terraform plan -out=plan.tfplan && terraform show -json plan.tfplan | conftest test -`), blocking applies that would create public-IP instances.

**Q17. Scenario: "Your fintech team uses Terraform to manage production RDS. A developer accidentally ran `terraform apply` and the plan included `forces replacement` on the RDS instance. How do you prevent this class of accident?"**
A: An RDS replacement destroys the primary instance and creates a new one — data is in the final snapshot, but the outage and recovery time are significant. Prevention is multi-layered:

**Layer 1 — `prevent_destroy` lifecycle (already discussed in Q14):** blocks the apply before it reaches AWS.

**Layer 2 — Plan review in CI:** never allow `terraform apply` directly from an engineer's laptop in production. All applies go through a CI pipeline (Atlantis, GitHub Actions) where the plan output is posted as a PR comment. A `forces replacement` annotation in the plan is visible to reviewers before approval.

**Layer 3 — Detect replacement in CI script:**
```bash
# Parse the plan JSON and fail if any resource is being replaced
PLAN_JSON=$(terraform show -json plan.tfplan)
REPLACEMENTS=$(echo "$PLAN_JSON" | jq -r '
  .resource_changes[]
  | select(.change.actions | contains(["delete", "create"]))
  | .address
')

if [ -n "$REPLACEMENTS" ]; then
  echo "ERROR: The following resources will be replaced:"
  echo "$REPLACEMENTS"
  echo "RDS replacements require explicit approval. Open a change request."
  exit 1
fi
```

**Layer 4 — `ignore_changes` for attributes that trigger unnecessary replacement:**
```hcl
resource "aws_db_instance" "main" {
  lifecycle {
    ignore_changes = [
      password,       # Rotated outside Terraform via Secrets Manager rotation
      engine_version, # Minor version updates done by AWS; don't flag as drift
    ]
  }
}
```

`ignore_changes` tells Terraform to ignore drift in those attributes — if the actual value differs from config, Terraform won't plan a change. Use this for attributes managed outside Terraform's lifecycle (password rotation, minor version patching) to prevent spurious replacement plans.

## Section 7: Module Structure and Reusability

**Q18. How do you structure a reusable Terraform module for this VPC + EC2 + RDS stack, and what goes in `variables.tf` vs `locals.tf`?**
A: A well-structured module separates caller-supplied inputs (`variables.tf`), computed internal values (`locals.tf`), and resource definitions:

```
modules/app-stack/
├── main.tf          # Resource definitions
├── variables.tf     # Input variables (callers must supply or get defaults)
├── locals.tf        # Computed values (not exposed to callers)
├── outputs.tf       # Values exported to parent or remote state
├── versions.tf      # Required provider and Terraform version constraints
└── userdata.sh      # EC2 bootstrap script template
```

```hcl
# variables.tf — what callers configure
variable "project" {
  type        = string
  description = "Project name, used as a prefix for all resource names"
  validation {
    condition     = length(var.project) <= 12 && can(regex("^[a-z0-9-]+$", var.project))
    error_message = "Project name must be lowercase alphanumeric with hyphens, max 12 chars"
  }
}

variable "environment" {
  type    = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod"
  }
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "db_instance_class" {
  type    = string
  default = "db.t3.small"
}

variable "multi_az" {
  type    = bool
  default = false
}
```

```hcl
# locals.tf — computed values not exposed as variables
locals {
  name_prefix = "${var.project}-${var.environment}"

  # Per-environment sizing map — callers don't control this directly
  instance_config = {
    dev     = { type = "t3.micro",  storage = 20 }
    staging = { type = "t3.medium", storage = 50 }
    prod    = { type = "m5.large",  storage = 100 }
  }

  resolved_instance_type = var.instance_type != "t3.micro" ?
    var.instance_type :
    local.instance_config[var.environment].type

  common_tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}
```

`variables.tf` is the public API of the module — callers read this to know what to supply. `locals.tf` is internal — it encapsulates derived logic so `main.tf` stays readable. Never put computed logic in `variables.tf` (variables can't reference other values) and never expose `locals` to callers (they're not outputs unless you explicitly add them to `outputs.tf`).

**Q19. How do `validation` blocks in `variable` declarations improve module safety, and what are their limitations?**
A: `validation` blocks run during `terraform plan` before any API calls, catching bad inputs early:

```hcl
variable "db_storage_gb" {
  type        = number
  description = "Allocated storage in GB for RDS"

  validation {
    condition     = var.db_storage_gb >= 20 && var.db_storage_gb <= 65536
    error_message = "RDS storage must be between 20 GB and 65536 GB"
  }
}

variable "availability_zones" {
  type = list(string)

  validation {
    condition     = length(var.availability_zones) >= 2
    error_message = "At least 2 AZs required for high availability"
  }

  validation {
    condition     = length(var.availability_zones) == length(toset(var.availability_zones))
    error_message = "Availability zones must be unique"
  }
}

variable "allowed_cidr_blocks" {
  type = list(string)

  validation {
    condition = alltrue([
      for cidr in var.allowed_cidr_blocks : can(cidrnetmask(cidr))
    ])
    error_message = "All entries must be valid CIDR blocks (e.g. 10.0.0.0/8)"
  }
}
```

Limitations: `validation` blocks can only reference the variable being validated — not other variables or data sources. You can't write `condition = var.instance_type != "t2.micro" || var.environment != "prod"` because that references `var.environment`. Cross-variable validation must go in `locals` with a null resource or `precondition` blocks (Terraform 1.2+):

```hcl
resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    precondition {
      condition     = !(var.environment == "prod" && !var.multi_az)
      error_message = "Production RDS must have multi_az = true"
    }
  }
}
```

`precondition` can reference any value in the configuration, not just the variable being declared.
