# Infrastructure (IaC): Terraform State — Local vs Remote (S3 + DynamoDB) — Interview Q&A (5 YOE Level)

---

## Section 1: What State Is and Why It Exists

**Q1. Why does Terraform need a state file at all? Can't it just query the provider API every time?**
A: This is the most important conceptual question about Terraform. In theory, Terraform *could* query every provider API on every run and diff the result against your config — but in practice this is infeasible for three reasons:

1. **Identity mapping** — the API doesn't know which real-world resource corresponds to which `resource` block in your HCL. Two EC2 instances can have identical configs; only the state file records "this `aws_instance.app_server` block created `i-0abc123def456`." Without that mapping, Terraform can't update or destroy the right object.
2. **Attributes not returned by the API** — some resource attributes are only available at creation time (initial passwords, private keys, one-time tokens). The API won't return them again on a subsequent read. State preserves them.
3. **Performance** — a complex root module may declare hundreds of resources across dozens of providers. Querying every API on every `plan` would be slow and rate-limit-prone. State provides a cached baseline; Terraform refreshes only what it needs.

State is fundamentally a *mapping layer* between your HCL declarations and real-world resource IDs, plus a *cache* of the last-known attribute values.

**Q2. What does the state file actually look like, and what's inside it?**
A: It's a JSON file. You should never hand-edit it, but understanding its structure helps when debugging:

```json
{
  "version": 4,
  "terraform_version": "1.7.2",
  "serial": 42,
  "lineage": "3a1b2c4d-...",
  "outputs": {
    "alb_dns_name": {
      "value": "myapp-alb-123456.ap-south-1.elb.amazonaws.com",
      "type": "string",
      "sensitive": false
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "aws_s3_bucket",
      "name": "loan_documents",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "id": "myorg-loan-documents-prod",
            "bucket": "myorg-loan-documents-prod",
            "arn": "arn:aws:s3:::myorg-loan-documents-prod",
            "region": "ap-south-1"
            // ... all tracked attributes
          },
          "sensitive_attributes": [],
          "private": "base64-encoded-provider-private-data"
        }
      ]
    }
  ]
}
```

Key fields: `serial` (monotonically incremented on every write — used to detect concurrent modification), `lineage` (a UUID assigned at `terraform init` that never changes — used to detect state file swaps), and the `resources` array mapping HCL addresses to provider IDs and attribute snapshots.

**Q3. What is the `serial` field, and how does it protect against concurrent writes?**
A: Every time Terraform successfully writes state, it increments `serial` by 1. When Terraform is about to write new state, it reads the current state file and checks that the `serial` in the file matches what it read at the start of the operation. If another process wrote state concurrently (bumping `serial`), Terraform detects the mismatch and aborts rather than overwriting the newer state with a stale one. This is a last-resort safety net — it catches races that slip past locking. Locking (DynamoDB) prevents the race from happening; `serial` catches it if locking was bypassed (`force-unlock`) or the backend doesn't support locking at all.

**Q4. What does `terraform refresh` do, and when is it still useful given that `plan` already refreshes state?**
A: `terraform refresh` (and the newer `terraform apply -refresh-only`) reads current real-world resource attributes via the provider API and updates the state file to match, *without* changing any real infrastructure. Since Terraform 0.15+, `terraform plan` does an implicit refresh before computing the diff, so a standalone `terraform refresh` is rarely needed. It's still useful in two scenarios:
- **Acknowledging out-of-band changes without applying** — someone manually fixed a config drift in the console; you want state to reflect the current reality before your next `plan` so the diff is clean, but you're not ready to apply anything else yet.
- **Debugging state vs. reality discrepancies** — when plan output shows unexpected changes and you suspect stale state, a `-refresh-only` plan explicitly shows what would change in state (not in infra), letting you inspect and approve the state update separately from any infra changes.

In regulated pipelines: prefer `terraform apply -refresh-only` over the deprecated `terraform refresh` — it shows a plan for review before writing, which is the safer audit-compliant pattern.

## Section 2: Local State — Mechanics and Limitations

**Q5. How does local state work, and what are its exact failure modes in a team setting?**
A: With the default local backend, Terraform writes state to `terraform.tfstate` in the working directory. On `terraform plan`, it reads that file. On `terraform apply`, it reads it, makes API calls, then writes the updated file back. This works fine for a single engineer on a personal project. In a team, it breaks in three distinct ways:

1. **No shared truth** — each engineer has their own `terraform.tfstate` on their laptop. Engineer A applies and creates `i-0abc123`. Engineer B's state doesn't know about it — their next `apply` may try to create a duplicate, or their `destroy` misses the resource entirely.
2. **No locking** — two engineers run `apply` simultaneously. Both read the state, both make changes, both write back. The second write silently overwrites the first. The `serial` check may catch this, but the result is a failed operation and potentially partially-applied infra with no lock to indicate what happened.
3. **State in git = secrets in git** — teams that try to share state by committing `terraform.tfstate` to the repo leak every sensitive attribute (database passwords, private keys, IAM access keys) into git history. This is a common compliance violation in fintech stacks and nearly impossible to fully remediate once it's happened.

**Q6. What happens if you accidentally commit `terraform.tfstate` to git, and how do you remediate?**
A: The state file contains plaintext values for all resource attributes, including anything marked `sensitive`. Once committed, those secrets are in git history — even if you delete the file in a later commit, they're accessible via `git log` or any clone made before deletion. Remediation steps:
1. **Immediately rotate all exposed secrets** — every DB password, access key, API token referenced in that state file. This cannot wait.
2. **Remove from git history** — use `git filter-repo` (preferred over the deprecated `BFG Repo-Cleaner`) to rewrite history and remove the file. This requires a force-push and all collaborators must re-clone.
3. **Migrate to remote state** — set up S3 + DynamoDB backend before the next `apply` so it never happens again.
4. **Add to `.gitignore`** — add `*.tfstate`, `*.tfstate.backup`, and `.terraform/` to `.gitignore` immediately.
5. **Audit access** — check who has cloned or forked the repo since the commit, and treat all exposed credentials as compromised regardless.

Prevention is far cheaper. Step one of any new Terraform project should be configuring remote state before writing a single resource.

**Q7. What is `terraform.tfstate.backup`, and can you rely on it for recovery?**
A: Before every write, Terraform copies the current state file to `terraform.tfstate.backup`. It's a single backup — a rolling window of depth 1. If the current `apply` corrupts state, you can `cp terraform.tfstate.backup terraform.tfstate` and revert to the pre-apply state. It's a local file, so it has all the same problems as local state: not shared with teammates, lost if the disk is wiped, doesn't help if two applies have run since the corruption. Remote state in S3 with versioning enabled is a far more reliable recovery mechanism — you get a full version history of every state write with a timestamp, and recovery is `aws s3api get-object --version-id <id>`.

## Section 3: Remote State — S3 Backend

**Q8. Walk through the complete S3 backend configuration for a production-grade setup.**
A:
```hcl
# versions.tf
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  backend "s3" {
    bucket         = "myorg-terraform-state-prod"
    key            = "services/loans-api/terraform.tfstate"
    region         = "ap-south-1"

    # Encryption at rest
    encrypt        = true
    kms_key_id     = "arn:aws:kms:ap-south-1:123456789012:key/mrk-abc123def456"

    # Locking
    dynamodb_table = "terraform-state-lock"

    # Access control
    # IAM role assumed by CI/CD; no static credentials in config
    # role_arn = "arn:aws:iam::123456789012:role/TerraformCIRole"
  }
}
```

The key path convention matters — use a hierarchy that reflects your state segmentation: `<layer>/<service>/terraform.tfstate`. All workspaces for the same org should share one bucket (simpler IAM, one place to audit) but use distinct keys.

**Q9. What S3 bucket settings must be enabled for a secure state backend, and how do you bootstrap the bucket itself?**
A: The bucket needs:
- **Versioning** — `aws s3api put-bucket-versioning --versioning-configuration Status=Enabled`. Every state write becomes a recoverable version. Non-negotiable.
- **SSE-KMS encryption** — use a customer-managed KMS key (not `aws:s3` default encryption), so you control key rotation and can audit key usage in CloudTrail. Set as the bucket's default encryption and also specify `kms_key_id` in the Terraform backend config.
- **Block all public access** — all four `BlockPublicAcls`, `IgnorePublicAcls`, `BlockPublicPolicy`, `RestrictPublicBuckets` set to `true`. State files must never be publicly readable.
- **Bucket policy denying non-HTTPS** — add a bucket policy with `aws:SecureTransport: false → Deny` to reject any request not using TLS.
- **Access logging** — enable S3 server access logging to a separate log bucket. Every state read/write is logged — required for PCI-DSS audit trails.

The bootstrapping problem: you can't use Terraform to create the S3 bucket and DynamoDB table that Terraform's own backend needs (chicken-and-egg). The canonical solution is a separate `bootstrap/` Terraform workspace with a *local* backend that creates the bucket and DynamoDB table — run once, by hand, and commit. Some teams use AWS CLI scripts or CloudFormation for this instead.

**Q10. What are the IAM permissions required for the S3 backend, and what's the principle-of-least-privilege breakdown?**
A: The IAM entity running Terraform (CI/CD role) needs:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StateReadWrite",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::myorg-terraform-state-prod/services/loans-api/*"
    },
    {
      "Sid": "StateLock",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:DeleteItem"
      ],
      "Resource": "arn:aws:dynamodb:ap-south-1:123456789012:table/terraform-state-lock"
    },
    {
      "Sid": "StateKMS",
      "Effect": "Allow",
      "Action": [
        "kms:GenerateDataKey",
        "kms:Decrypt"
      ],
      "Resource": "arn:aws:kms:ap-south-1:123456789012:key/mrk-abc123def456"
    },
    {
      "Sid": "StateListing",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::myorg-terraform-state-prod"
    }
  ]
}
```

Scope the `s3:GetObject`/`PutObject` to the specific key prefix for that workspace — the loans-api CI role should not be able to read the networking team's state file. `s3:DeleteObject` is needed because Terraform rewrites state atomically (write new, delete old temp file). `s3:ListBucket` on the bucket (not the prefix) is required for the backend to check if the key exists.

**Q11. How does the S3 backend handle the state write atomically to prevent partial writes?**
A: S3's `PutObject` is atomic at the object level — a PUT either fully succeeds or fully fails; there's no partial-write state visible to concurrent readers. Terraform exploits this: it computes the full new state in memory, then issues a single `PutObject` to write it. If the PUT fails mid-flight (network drop, throttle), the old object remains unchanged — S3 won't surface a partially-written object. This is why S3 is a safe state backend even though it's not a traditional database: object storage's atomic PUT semantics provide the write safety Terraform needs, and DynamoDB provides the mutual-exclusion locking that prevents two processes from starting a PUT simultaneously.

## Section 4: DynamoDB Locking — Deep-Dive

**Q12. How does DynamoDB locking work mechanically in the Terraform S3 backend?**
A: Terraform uses a DynamoDB table with `LockID` as the partition key (string). The lock lifecycle for a single `terraform apply`:

1. **Acquire** — Terraform calls `PutItem` with a `ConditionExpression: attribute_not_exists(LockID)`. This is a conditional write — it only succeeds if no item with that `LockID` exists. If another process holds the lock, the condition fails and Terraform receives a `ConditionalCheckFailedException`, which it surfaces as "Error acquiring the state lock."
2. **Hold** — while the operation runs, the lock item sits in DynamoDB containing the lock ID, who acquired it, when, and what operation type (`OperationTypePlan` or `OperationTypeApply`).
3. **Release** — Terraform calls `DeleteItem` for the `LockID` on success or failure. The `defer`-style cleanup in the Go codebase means release happens even if apply panics.

The DynamoDB table needs no special schema beyond the `LockID` partition key — Terraform creates and manages the full item structure. You only need to create the table itself.

**Q13. What is the exact DynamoDB table configuration needed, and why is on-demand capacity correct here?**
A:
```hcl
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-state-lock"
  billing_mode = "PAY_PER_REQUEST"   # on-demand — lock operations are infrequent bursts
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }

  point_in_time_recovery {
    enabled = true
  }

  server_side_encryption {
    enabled     = true
    kms_key_arn = aws_kms_key.terraform.arn
  }

  tags = {
    Name      = "terraform-state-lock"
    ManagedBy = "terraform"
  }
}
```

On-demand (`PAY_PER_REQUEST`) is correct because lock operations are highly bursty and infrequent — a dozen `apply` runs per day, each holding the lock for 30–300 seconds. Provisioned capacity would require you to guess a throughput number that's almost always either wasteful or hit during a deploy surge. On-demand handles the burst automatically and costs almost nothing at this volume. Point-in-time recovery and KMS encryption are belt-and-suspenders for compliance — the table holds no business data, but in a regulated environment all DynamoDB tables should be encrypted and recoverable.

**Q14. What happens when a lock is never released — and what's the correct recovery procedure?**
A: A lock orphan happens when the Terraform process holding the lock dies abnormally — CI runner OOM-killed, laptop lid closed, `kill -9` during apply, network partition between Terraform and DynamoDB. The lock item remains in DynamoDB indefinitely. Every subsequent `plan` or `apply` fails immediately with:

```
Error: Error acquiring the state lock

  Error message: ConditionalCheckFailedException: The conditional
  request failed

  Lock Info:
    ID:        a1b2c3d4-e5f6-...
    Path:      myorg-terraform-state-prod/services/loans-api/terraform.tfstate
    Operation: OperationTypeApply
    Who:       ci-runner@github-actions
    Version:   1.7.2
    Created:   2025-08-10 14:32:01.123456789 +0000 UTC
    Info:
```

Recovery procedure:
1. **Verify no apply is actually running** — check your CI dashboard, check with the engineer named in the lock `Who` field. Force-unlocking while an apply is genuinely in progress will corrupt state.
2. **Inspect the lock** — `aws dynamodb get-item --table-name terraform-state-lock --key '{"LockID": {"S": "myorg-terraform-state-prod/services/loans-api/terraform.tfstate"}}'`
3. **Force unlock** — `terraform force-unlock a1b2c3d4-e5f6-...` (the Lock ID from the error output). This calls `DeleteItem` directly, bypassing the conditional check.
4. **Verify state integrity** — run `terraform plan` and review carefully. If the aborted apply was mid-flight, some resources may be partially created. The plan will show the delta; inspect it before applying.
5. **Post-mortem** — add CI job timeout limits and `concurrency` groups (GitHub Actions) or equivalent so future runner kills release locks cleanly.

**Q15. Can two different services share a DynamoDB lock table, and is that safe?**
A: Yes, and it's the recommended pattern. The `LockID` for each workspace is the full S3 key path (`bucket/key`), which is unique per workspace. Two workspaces locking against the same DynamoDB table use different `LockID` values — they never contend with each other. Using one shared DynamoDB table for all your Terraform workspaces (across all services) is simpler to manage (one table to monitor, one set of IAM permissions to maintain) and has no correctness downside. The only reason to use separate tables would be if you want per-team IAM boundaries so tight that the loans team's CI role can't even read the networking team's lock items — in practice this level of isolation is rarely necessary and most orgs use a single shared table.

## Section 5: State Operations, Recovery & CI/CD Patterns

**Q16. When would you use `terraform state pull` and `terraform state push`, and what are the risks?**
A: `terraform state pull` downloads the current remote state and prints it as JSON to stdout — useful for inspection, debugging, or extracting it for manual editing:

```bash
terraform state pull > state-backup.json
```

`terraform state push` uploads a local state file to the remote backend, overwriting whatever is there:

```bash
terraform state push fixed-state.json
```

`push` is dangerous — it bypasses locking and `serial` checks (with `-force`), meaning you can overwrite a newer state with an older one and lose track of resources Terraform created after your snapshot. The only legitimate use cases: recovering from a corruption where the remote state is broken beyond what `terraform state mv`/`rm` can fix, or migrating state between backends. Always take a backup before pushing, always verify with `terraform plan` immediately after, and treat it as an emergency operation, not a routine one.

**Q17. How do you migrate from local to S3 remote state without losing anything?**
A: This is a one-time migration that's safe if done carefully:

```hcl
# Step 1: Add the backend config to your Terraform files
terraform {
  backend "s3" {
    bucket         = "myorg-terraform-state-prod"
    key            = "services/loans-api/terraform.tfstate"
    region         = "ap-south-1"
    encrypt        = true
    kms_key_id     = "arn:aws:kms:ap-south-1:..."
    dynamodb_table = "terraform-state-lock"
  }
}
```

```bash
# Step 2: Run init — Terraform detects the backend change and prompts to migrate
terraform init

# Terraform will ask:
# "Do you want to copy existing state to the new backend? yes/no" → yes

# Step 3: Verify — confirm state is now in S3
terraform state list

# Step 4: Confirm the local file is now stale (remove it)
rm terraform.tfstate terraform.tfstate.backup

# Step 5: Add to .gitignore
echo "*.tfstate\n*.tfstate.backup\n.terraform/" >> .gitignore
```

Terraform's `init` handles the copy atomically — it reads local state, writes it to S3, and only proceeds if the S3 write succeeds. If it fails midway, local state is untouched. Do not run `apply` between adding the backend config and running `init` — that would try to initialize with a missing remote state.

**Q18. How do you handle Terraform state in a GitOps / pull-request-driven CI/CD pipeline?**
A: The standard pattern for regulated, team-based pipelines:

```
PR opened →
  terraform fmt -check         (formatting gate)
  terraform validate           (syntax/type check)
  terraform plan -out=tfplan   (plan against remote state, save artifact)
  Post plan diff as PR comment (engineers review what will change)

PR approved + merged to main →
  terraform apply tfplan       (apply the EXACT saved plan — not a new plan)
```

Critical details:
- **Save the plan artifact** — `terraform plan -out=tfplan` serializes the plan to a binary file. `terraform apply tfplan` applies exactly that — no re-planning, no drift between review and apply. Without `-out`, apply re-plans and may behave differently than what was reviewed.
- **Artifact storage** — the `tfplan` file contains state data and should be treated as sensitive. Store in CI artifact storage (GitHub Actions artifacts, S3) with appropriate access controls, not committed to git.
- **One apply per branch** — use CI concurrency controls so only one apply runs at a time per workspace. Concurrent applies will fight over the DynamoDB lock and one will fail.
- **Never `apply` in PR pipelines** — only `plan`. Apply only triggers on merge to `main` (or a release branch). This prevents unapproved infra changes.

**Q19. How do you use Terraform workspaces, and how do they relate to the S3 backend key?**
A: Terraform workspaces (`terraform workspace new staging`) create isolated state files within the same backend configuration. With the S3 backend, workspaces store state at `<key_prefix>/env:/<workspace_name>/terraform.tfstate` rather than the root key. This lets a single set of `.tf` files manage multiple environments:

```bash
terraform workspace new staging
terraform workspace select staging
terraform apply -var-file=staging.tfvars
```

However, the built-in workspace model has a significant limitation: the backend config (bucket, key prefix, DynamoDB table) is shared and hardcoded — you can't use different AWS accounts or regions per workspace without wrapper tooling. For this reason, many teams prefer **separate root modules per environment** (separate directories with separate backend configs) over workspaces — each environment is an independent workspace with its own explicit state path, its own AWS account, and its own CI pipeline. Workspaces are best suited for truly ephemeral environments (per-PR preview environments) where lightweight isolation is enough. For prod/staging/dev with different accounts or compliance requirements, separate root modules give you clearer boundaries.

**Q20. What is `terraform state rm`, and when is it the right tool?**
A: `terraform state rm <address>` removes a resource from the state file without destroying the real-world resource. Terraform simply forgets it ever managed that object. Use cases:
- **Abandoning a resource** — you want to stop managing a resource with Terraform (e.g., a database that ops will now manage manually) without destroying it. Remove it from state, remove it from config, and the next `plan` shows no changes.
- **Recovering from a bad import** — you imported the wrong resource ID. `state rm` it, fix the import, re-import.
- **Moving to a new workspace** — as part of a state split, `state rm` the resource from workspace A (after confirming it's in workspace B's state).

The risk: after `state rm`, the resource is unmanaged. If you subsequently run `apply` on config that still references it, Terraform will try to create a new one (duplicate) rather than adopting the existing one. Always remove both from state *and* from config in the same commit, or immediately follow with `terraform import` to re-adopt under the new address.

## Section 6: Security, Compliance & Advanced Scenarios

**Q21. What sensitive data ends up in Terraform state, and how should you protect it in an RBI/PCI-DSS environment?**
A: Every attribute Terraform tracks for a resource is stored in state in plaintext JSON, regardless of whether the variable or output is marked `sensitive`. In a fintech stack this typically includes:
- RDS master passwords
- IAM access key IDs and secret keys (for resources that generate them, like `aws_iam_access_key`)
- Private TLS certificate keys (for `tls_private_key` resources)
- Initial API tokens from third-party providers
- KMS key IDs and ARNs (not secret, but security-relevant)

Protection layers for PCI-DSS / RBI compliance:
1. **SSE-KMS with CMK** — encrypt the S3 bucket with a customer-managed KMS key. Key usage is logged in CloudTrail. Rotate the key annually (or per policy).
2. **Bucket policy: deny non-HTTPS** — enforce TLS in transit.
3. **IAM: least-privilege per workspace** — each service's CI role can only access its own state key prefix. No wildcard `s3:*`.
4. **Block public access** — all four S3 block public access settings enabled at account and bucket level.
5. **S3 access logging** — every `GetObject` and `PutObject` on the state bucket logged to a separate audit log bucket. Required for PCI-DSS access logging controls.
6. **Avoid storing secrets in state at all** — instead of a `random_password` resource for RDS, generate the password in AWS Secrets Manager and reference its ARN. The secret value never touches Terraform state.
7. **State file access auditing** — periodically audit who has `s3:GetObject` on the state bucket. Engineers should not have direct access; only CI/CD roles should.

**Q22. How do you recover a corrupted or accidentally deleted state file when versioning is enabled on S3?**
A: S3 versioning is your time machine. The recovery procedure:

```bash
# 1. List all versions of the state file to find the last good one
aws s3api list-object-versions \
  --bucket myorg-terraform-state-prod \
  --prefix services/loans-api/terraform.tfstate \
  --query 'Versions[*].[VersionId,LastModified,IsLatest]' \
  --output table

# 2. Download the specific version you want to restore
aws s3api get-object \
  --bucket myorg-terraform-state-prod \
  --key services/loans-api/terraform.tfstate \
  --version-id "abc123XYZ..." \
  restored-state.json

# 3. Inspect it — confirm it's the right state
cat restored-state.json | jq '.serial, (.resources | length)'

# 4. Push the restored state (Terraform must not be running)
terraform state push restored-state.json

# 5. Verify
terraform plan
```

If the state file was deleted (a delete marker exists in S3 versioning), use `aws s3api delete-object --version-id <delete-marker-version-id>` to remove the delete marker, which restores the previous version automatically. This is why S3 versioning is non-negotiable — without it, a deleted or overwritten state file is unrecoverable without an external backup.

**Q23. Scenario: "Two CI pipelines ran `terraform apply` simultaneously against the same workspace. One succeeded, one failed with a lock error. Now `terraform plan` shows resources that shouldn't exist. What happened, and how do you fix it?"**
A: The failing pipeline got the right outcome (lock prevented it from writing conflicting state), but the "shouldn't exist" resources in the plan indicate either (a) the successful apply created something partially (the apply itself may have failed mid-run after some resources were created, before the state write succeeded), or (b) the plan is comparing against state that doesn't yet reflect what the successful apply created (cache/timing issue).

Diagnostic steps:
1. Check the S3 state file's `serial` — if it's behind what you expect, the successful apply's state write may have failed after the API calls succeeded. Real infra exists but state doesn't know about it — this is the classic partial-apply state drift scenario.
2. Run `terraform plan -refresh=true` and review carefully. Resources showing as "to be created" that already exist in the console indicate missing state entries.
3. `terraform import` each orphaned resource back into state.
4. For future prevention: add `concurrency` groups to CI workflows so only one apply runs per workspace at a time, and add timeouts to ensure lock release even on runner failure.

**Q24. What is a `partial` backend configuration, and why is it useful in CI/CD?**
A: A partial backend config leaves some backend arguments empty in the `.tf` file, to be supplied at `terraform init` time via `-backend-config` flags or files. This lets you keep secrets and environment-specific paths out of source code:

```hcl
# versions.tf — committed to git, no secrets
terraform {
  backend "s3" {
    # Intentionally empty — supplied at init time
  }
}
```

```bash
# CI pipeline — values injected from secrets manager
terraform init \
  -backend-config="bucket=myorg-terraform-state-prod" \
  -backend-config="key=services/loans-api/terraform.tfstate" \
  -backend-config="region=ap-south-1" \
  -backend-config="encrypt=true" \
  -backend-config="kms_key_id=${KMS_KEY_ARN}" \
  -backend-config="dynamodb_table=terraform-state-lock"
```

This pattern is particularly useful when: multiple environments use the same `.tf` files but different S3 buckets (different AWS accounts), or when the KMS key ARN is itself a secret fetched from a vault at pipeline runtime. It avoids hardcoding account-specific values into committed code, keeping the repo environment-agnostic.

**Q25. Scenario: "Your fintech platform team manages a shared VPC in one Terraform workspace. Five product teams each have their own workspace and need the VPC ID and private subnet IDs. How do you share that data without coupling everyone to the networking team's state file?"**
A: The naive approach — `terraform_remote_state` in each product team's workspace — creates tight coupling: every product team needs read access to the networking team's entire state file (which may contain sensitive data beyond VPC IDs), and if the networking team renames an output, all five workspaces break simultaneously at plan time.

The decoupled pattern using SSM Parameter Store:

```hcl
# In the networking workspace — write outputs to SSM after apply
resource "aws_ssm_parameter" "vpc_id" {
  name  = "/platform/networking/prod/vpc_id"
  type  = "String"
  value = aws_vpc.shared.id
}

resource "aws_ssm_parameter" "private_subnet_ids" {
  name  = "/platform/networking/prod/private_subnet_ids"
  type  = "StringList"
  value = join(",", aws_subnet.private[*].id)
}
```

```hcl
# In each product team's workspace — read from SSM, no state coupling
data "aws_ssm_parameter" "vpc_id" {
  name = "/platform/networking/prod/vpc_id"
}

data "aws_ssm_parameter" "private_subnet_ids" {
  name = "/platform/networking/prod/private_subnet_ids"
}

resource "aws_ecs_service" "loans_api" {
  network_configuration {
    subnets = split(",", data.aws_ssm_parameter.private_subnet_ids.value)
  }
}
```

Benefits: product teams only need `ssm:GetParameter` on the specific path, not access to the state file; the networking team can restructure their internal Terraform without breaking consumers (as long as SSM paths are stable); SSM parameter changes are logged in CloudTrail; and you can use SSM path-based IAM policies to enforce that `dev` workspaces only read `dev` parameters and `prod` workspaces only read `prod` parameters — an important environment isolation control in a regulated stack.

## Quick Comparison Table

| Aspect | Local Backend | S3 + DynamoDB Backend |
|---|---|---|
| State location | `terraform.tfstate` on disk | S3 object at configured key |
| Team collaboration | ✗ — each engineer has own state | ✓ — shared single source of truth |
| Locking | ✗ — no locking, race conditions possible | ✓ — DynamoDB conditional writes |
| Encryption at rest | ✗ — plaintext JSON on disk | ✓ — SSE-KMS with CMK |
| Encryption in transit | N/A | ✓ — HTTPS only (enforce via bucket policy) |
| Versioning / recovery | ✗ — only `.tfstate.backup` (depth 1) | ✓ — S3 versioning (full history) |
| Access auditing | ✗ — filesystem, no audit trail | ✓ — S3 access logs + CloudTrail |
| CI/CD compatibility | ✗ — state not accessible to runners | ✓ — runners access via IAM role |
| Secrets exposure risk | High (file on disk, often in git) | Lower (encrypted, IAM-gated) |
| Setup cost | Zero | One-time bootstrap (S3 + DynamoDB + KMS) |
| Appropriate for | Solo local dev / learning | Any team, any production workload |
