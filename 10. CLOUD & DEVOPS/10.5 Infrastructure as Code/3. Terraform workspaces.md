# Infrastructure (IaC): Terraform Workspaces — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a Terraform workspace, and what problem does it solve?**
A: A Terraform workspace is an isolated state namespace within a single backend configuration. Every Terraform project starts with one workspace called `default`. Creating additional workspaces (`terraform workspace new staging`) gives you separate state files — one per workspace — all stored in the same backend (same S3 bucket, same DynamoDB lock table), but at different keys. The same `.tf` configuration files are used across all workspaces; what changes is the state each workspace tracks and, typically, the variable values you supply per workspace.

The problem it solves: running the same infrastructure configuration against multiple environments (dev, staging, prod) without copy-pasting `.tf` files and without one environment's state bleeding into another's. Instead of three separate directories each with their own backend config, you have one directory and three workspaces.

**Q2. What is the `default` workspace, and is it safe to use in production?**
A: `default` is the workspace Terraform initializes automatically on every new project. It cannot be deleted. Structurally it behaves identically to any other workspace — it's just a state namespace. Whether it's "safe" for production is a team convention question, not a technical one. The risk is accidental: engineers who don't think about workspaces tend to do all their work in `default`, which means prod and dev infra share the same workspace (no isolation). The common convention is: treat `default` as unused or as a scratchpad, and always explicitly create named workspaces (`dev`, `staging`, `prod`) so the current workspace is always meaningful and deliberate.

**Q3. Walk through the core workspace CLI commands.**
A:
```bash
# List all workspaces (* marks the currently selected one)
terraform workspace list
# Output:
#   default
# * dev
#   staging
#   prod

# Create a new workspace and switch to it
terraform workspace new staging

# Switch to an existing workspace
terraform workspace select prod

# Show the currently selected workspace
terraform workspace show
# Output: prod

# Delete a workspace (must not be currently selected; state must be empty or force-deleted)
terraform workspace select default
terraform workspace delete staging
```

`terraform workspace delete` will refuse if the workspace still has state (managed resources). Use `-force` to delete the state along with the workspace — this is a destructive, irreversible operation. Always run `terraform destroy` inside the workspace before deleting it in a production setting.

**Q4. How does the S3 backend store state for multiple workspaces, and what does the key structure look like?**
A: With the S3 backend, Terraform stores workspace state at a path derived from the configured `key` and the workspace name. For the `default` workspace, it uses the `key` exactly as configured. For all other workspaces, it stores state under a `env:/` prefix:

```
# Backend config
backend "s3" {
  bucket = "myorg-terraform-state"
  key    = "services/loans-api/terraform.tfstate"
  region = "ap-south-1"
}

# Resulting S3 keys:
# default workspace:
#   services/loans-api/terraform.tfstate

# staging workspace:
#   env:/staging/services/loans-api/terraform.tfstate

# prod workspace:
#   env:/prod/services/loans-api/terraform.tfstate
```

This means all workspaces share the same S3 bucket and DynamoDB lock table — the lock table's `LockID` includes the full S3 key, so `staging` and `prod` can be locked independently without interfering with each other. The `env:/` prefix convention is fixed by the S3 backend implementation; you cannot change it.

**Q5. What is `terraform.workspace`, and how do you use it in configuration?**
A: `terraform.workspace` is a built-in string variable that always contains the name of the currently selected workspace. You can reference it anywhere in your `.tf` files:

```hcl
locals {
  # Use workspace name as the environment identifier
  environment = terraform.workspace

  # Size resources differently per environment
  instance_type = {
    dev     = "t3.micro"
    staging = "t3.medium"
    prod    = "m5.large"
  }[terraform.workspace]

  # Build resource names that include the environment
  name_prefix = "myorg-${terraform.workspace}"
}

resource "aws_instance" "app" {
  instance_type = local.instance_type
  tags = {
    Name        = "${local.name_prefix}-app"
    Environment = local.environment
  }
}
```

This is the primary mechanism for differentiating resource configuration between workspaces without duplicating `.tf` files. The pattern of indexing a map with `terraform.workspace` is idiomatic Terraform for environment-specific values.

## Section 2: State Isolation and the Workspace–State Relationship

**Q6. If workspaces share the same `.tf` files and the same backend, what exactly is isolated between them?**
A: Only the state file is isolated. Everything else is shared:
- **Shared** — `.tf` configuration files, provider versions (`.terraform.lock.hcl`), module sources, variable *definitions* (types, descriptions, defaults).
- **Isolated** — the state file (which real-world resources each workspace tracks), and whatever variable *values* you supply per workspace (via `-var-file`, environment variables, or workspace-aware locals).

This shared-config/isolated-state model is both the strength and the limitation of workspaces. The strength: one set of files governs all environments. The limitation: if all environments truly need identical configuration structure, workspaces work well. If `prod` needs fundamentally different resources (an extra RDS read replica, a WAF, a separate VPC), cramming that into `terraform.workspace` conditionals makes the config increasingly hard to read and reason about.

**Q7. Demonstrate how you'd use `terraform.workspace` to conditionally create a resource only in production.**
A:
```hcl
# Create a read replica only in prod
resource "aws_db_instance" "read_replica" {
  count = terraform.workspace == "prod" ? 1 : 0

  identifier          = "${local.name_prefix}-replica"
  replicate_source_db = aws_db_instance.primary.id
  instance_class      = "db.r5.large"
  skip_final_snapshot = true
}

# Create a WAF only in prod and staging
resource "aws_wafv2_web_acl" "api" {
  count = contains(["prod", "staging"], terraform.workspace) ? 1 : 0

  name  = "${local.name_prefix}-waf"
  scope = "REGIONAL"
  # ...
}
```

This works but should be used sparingly. Every conditional resource is a divergence between environments — if `dev` never has the WAF, you never test WAF config in dev, and `prod` may behave differently in ways you can't catch until production. The rule of thumb: use conditionals for *scale* differences (instance size, replica count, retention period), not for *structural* differences (entirely different resource types or architectures). Structural differences are a signal that the environments have diverged enough to warrant separate root modules.

**Q8. What happens to the DynamoDB lock when two engineers run `terraform apply` in different workspaces simultaneously?**
A: They don't interfere. The DynamoDB lock key is the full S3 state path — `myorg-terraform-state/env:/staging/services/loans-api/terraform.tfstate` for staging and `myorg-terraform-state/env:/prod/services/loans-api/terraform.tfstate` for prod. These are different lock items in the same DynamoDB table. Two applies in different workspaces can run concurrently without either blocking or corrupting the other. However, two applies in the *same* workspace from two different engineers will correctly contend on the lock — one proceeds, one blocks with the "state lock" error. This per-workspace locking is one of the genuine benefits of the workspace model over per-engineer local state.

**Q9. Can a `terraform_remote_state` data source read from a specific workspace of another backend?**
A: Yes. The `terraform_remote_state` data source accepts a `workspace` argument:

```hcl
data "terraform_remote_state" "networking" {
  backend   = "s3"
  workspace = "prod"

  config = {
    bucket = "myorg-terraform-state"
    key    = "platform/networking/terraform.tfstate"
    region = "ap-south-1"
  }
}

# Reads from:
# env:/prod/platform/networking/terraform.tfstate
```

This lets you cross-reference workspace-specific state from another module. The caveats discussed in the state guide still apply: the consuming workspace needs read access to the entire state file of the producing workspace, and renaming outputs in the producing workspace breaks consumers. The SSM Parameter Store pattern remains the better decoupling approach for cross-team sharing.

## Section 3: Workspaces vs. Separate Root Modules — The Core Trade-off

**Q10. What are the limitations of built-in Terraform workspaces that lead teams to use separate root modules instead?**
A: Built-in workspaces have five meaningful limitations:

1. **Same backend, same account** — the S3 backend config (bucket, region, KMS key) is shared across all workspaces. You can't use a different AWS account for `prod` vs `dev` without wrapper tooling. For strong environment isolation (separate AWS accounts per environment — the recommended pattern for regulated workloads), workspaces alone are insufficient.

2. **No per-workspace provider config** — the `provider "aws" {}` block is shared. If `prod` needs a different IAM role assumption or a different region, you can't express that cleanly within a single workspace setup without hacky variable-driven provider aliasing.

3. **Risk of accidental cross-environment apply** — there's no structural barrier preventing an engineer from selecting the wrong workspace and running `apply`. The only protection is the engineer noticing `terraform workspace show` output. Separate directories with separate CI pipelines make this class of mistake much harder.

4. **Config divergence becomes spaghetti** — as environments accumulate differences, `terraform.workspace` conditionals spread across files. After a year, reading a `.tf` file requires mentally simulating "what does this look like in dev? in prod?" — a significant cognitive load compared to separate files where prod config is just... the prod config file.

5. **No visibility into all-environment state at once** — there's no native command to see "what is the state of all workspaces?" You must switch into each one and inspect. Tools like Atlantis and Spacelift partially address this, but it's a genuine operational blind spot.

**Q11. When are built-in workspaces the right tool, and when are separate root modules the right tool?**
A: The decision comes down to how similar your environments actually are and what isolation guarantees you need.

**Use workspaces when:**
- Environments are structurally identical — same resources, same architecture, just different sizes or counts.
- All environments live in the same AWS account (acceptable for small teams or non-regulated workloads).
- You need lightweight, short-lived ephemeral environments (per-PR preview environments, developer sandboxes) where fast creation and teardown matters more than strict isolation.
- The team is small enough that accidental workspace selection is a low-probability risk.

**Use separate root modules when:**
- Environments live in separate AWS accounts (the recommended security boundary for prod in regulated fintech).
- `prod` has structural differences from `dev` (additional services, different networking topology, compliance-required resources like CloudTrail, Config, GuardDuty only in prod).
- Different teams own different environments and need independent change velocity — the loans team can deploy to `dev` and `staging` without touching the platform team's `prod` module.
- You want CI/CD pipelines where the `prod` pipeline has mandatory approval gates and the `dev` pipeline is fully automated — this maps cleanly to separate directories, less cleanly to workspace selection logic in a shared pipeline.

In practice, most mature fintech teams use: **workspaces for ephemeral environments** (one workspace per feature branch or PR), **separate root modules for long-lived environments** (dev, staging, prod as separate directories with separate backends).

**Q12. What is the "directory-per-environment" pattern, and how does it compare structurally to workspaces?**
A: The directory-per-environment pattern gives each environment its own root module directory with its own `backend.tf` and `terraform.tfvars`:

```
infrastructure/
├── modules/                    # Shared child modules
│   ├── rds/
│   ├── ecs-service/
│   └── networking/
├── environments/
│   ├── dev/
│   │   ├── main.tf             # Calls shared modules
│   │   ├── backend.tf          # Points to dev S3 bucket/key
│   │   ├── variables.tf
│   │   └── terraform.tfvars    # Dev-specific values
│   ├── staging/
│   │   ├── main.tf
│   │   ├── backend.tf          # Points to staging S3 bucket/key
│   │   └── terraform.tfvars
│   └── prod/
│       ├── main.tf
│       ├── backend.tf          # Points to prod S3 bucket/key (different account)
│       └── terraform.tfvars
```

Compared to workspaces: the directory pattern makes environment differences explicit and readable (open `prod/main.tf` to see exactly what prod has), makes accidental cross-environment applies structurally hard (you'd have to `cd` into the wrong directory), and supports per-environment AWS accounts with different backend configs. The cost: more duplication in `main.tf` across environments — mitigated by calling shared child modules, so the duplication is mostly `module` block invocations with different variable values, not full resource blocks.

## Section 4: Ephemeral Workspaces and CI/CD Patterns

**Q13. How do you use workspaces for per-PR ephemeral environments, and what does the CI/CD flow look like?**
A: Per-PR ephemeral environments are one of the strongest use cases for built-in workspaces. The pattern:

```bash
# On PR opened — CI pipeline creates a workspace named after the PR/branch
PR_WORKSPACE="pr-${PR_NUMBER}"  # e.g., pr-142

terraform workspace select "$PR_WORKSPACE" 2>/dev/null || \
  terraform workspace new "$PR_WORKSPACE"

terraform apply -var-file=dev.tfvars -auto-approve

# Post-apply: output the preview URL
terraform output -raw app_url
# → https://pr-142.preview.myorg.internal
```

```bash
# On PR closed/merged — CI pipeline destroys the workspace
terraform workspace select "$PR_WORKSPACE"
terraform destroy -var-file=dev.tfvars -auto-approve
terraform workspace select default
terraform workspace delete "$PR_WORKSPACE"
```

Key considerations:
- Use a separate S3 key prefix for ephemeral workspaces to keep them visually separated from long-lived state: `key = "preview/terraform.tfstate"` → results in `env:/pr-142/preview/terraform.tfstate`.
- Set resource names to include the workspace name so ephemeral resources don't collide with dev/staging: `name = "${terraform.workspace}-loans-api"`.
- Put a TTL-based cleanup job in CI that destroys any workspace with a name matching `pr-*` where the corresponding PR is closed — guards against leaked environments from failed pipelines.
- Cost-control: restrict ephemeral environments to cheap instance sizes via workspace-aware locals, same pattern as Q5.

**Q14. How do you prevent an engineer from accidentally applying to the wrong workspace in CI?**
A: Several layers:

**Explicit workspace assertion in the pipeline script:**
```bash
EXPECTED_WORKSPACE="${ENVIRONMENT}"  # e.g., "prod" for the prod pipeline

ACTUAL_WORKSPACE=$(terraform workspace show)
if [ "$ACTUAL_WORKSPACE" != "$EXPECTED_WORKSPACE" ]; then
  echo "ERROR: Expected workspace '$EXPECTED_WORKSPACE', got '$ACTUAL_WORKSPACE'. Aborting."
  exit 1
fi
```

**Separate CI pipelines per environment** — the `prod` pipeline is a separate GitHub Actions workflow that only triggers on pushes to `main` after PR approval. It always selects the `prod` workspace explicitly as its first step. Engineers never manually select workspaces in prod pipelines.

**IAM role scoping** — the CI role for the `dev` pipeline only has S3 access to `env:/dev/*` keys and can't read or write `env:/prod/*`. Even if the wrong workspace is selected, the IAM boundary prevents the apply from affecting prod state.

**Required approval gates** — for `prod`, use GitHub Actions `environment` protection rules with required reviewers. The workspace selection happens inside the protected environment. An engineer running `terraform apply` locally against prod must have explicit credentials for the prod IAM role, which is restricted.

**Q15. How do Terraform workspaces interact with tools like Atlantis or Spacelift?**
A: Both tools are workspace-aware and add the human-approval and audit-trail layer that raw workspace CLI lacks.

**Atlantis** — open-source Terraform automation via pull requests. Configured via `atlantis.yaml`, it can map different PR labels or directories to workspace selections. On a PR, Atlantis runs `terraform plan` in the specified workspace and posts the output as a PR comment. Merge requires `atlantis apply` approval from a code owner. Workspace selection is explicit in the config — no engineer picks the workspace manually.

```yaml
# atlantis.yaml
projects:
  - name: loans-api-staging
    dir: infrastructure/services/loans-api
    workspace: staging
    autoplan:
      when_modified: ["*.tf", "*.tfvars"]
  - name: loans-api-prod
    dir: infrastructure/services/loans-api
    workspace: prod
    apply_requirements: [approved, mergeable]
```

**Spacelift** — a more opinionated SaaS alternative. Each "stack" maps to a workspace. Stacks have explicit trigger policies, approval workflows, and dependency graphs (run the networking stack before the services stack). Better audit logging and RBAC than raw Atlantis. Worth the cost for teams that want workspace management without building their own CI tooling around Terraform.

## Section 5: Advanced Patterns and Failure Scenarios

**Q16. How do you use `for_each` on a module to stamp out identical infrastructure across multiple workspaces' worth of environments without actually using workspaces?**
A: This is the "single workspace, for_each environments" pattern — an alternative to workspaces where you manage all environments from one root module using `for_each`:

```hcl
variable "environments" {
  type = map(object({
    instance_type     = string
    min_capacity      = number
    max_capacity      = number
    db_instance_class = string
  }))
  default = {
    dev = {
      instance_type     = "t3.micro"
      min_capacity      = 1
      max_capacity      = 2
      db_instance_class = "db.t3.small"
    }
    staging = {
      instance_type     = "t3.medium"
      min_capacity      = 2
      max_capacity      = 4
      db_instance_class = "db.t3.medium"
    }
  }
}

module "loans_api" {
  for_each = var.environments
  source   = "./modules/ecs-service"

  environment       = each.key
  instance_type     = each.value.instance_type
  min_capacity      = each.value.min_capacity
  max_capacity      = each.value.max_capacity
  db_instance_class = each.value.db_instance_class
}
```

This approach keeps everything in one state file and one apply command. It works well for tightly coupled, truly-identical environments managed by one team. The downsides: one slow `apply` touches all environments simultaneously (no independent deploy velocity), one broken config affects all environments, and you can't easily apply only to `staging` without also re-evaluating `dev` and `prod`. Use this for non-production environment sets only.

**Q17. What goes wrong if you change a workspace name after resources are already created in it?**
A: You can't rename a workspace — Terraform has no `workspace rename` command. If you need to rename, the procedure is:
1. Create the new workspace: `terraform workspace new loans-api-prod` (from old `prod`).
2. Pull state from the old workspace and push to the new one:
   ```bash
   terraform workspace select prod
   terraform state pull > old-state.json
   terraform workspace select loans-api-prod
   terraform state push old-state.json
   ```
3. Verify with `terraform plan` in the new workspace — should show no changes.
4. Destroy the old workspace: `terraform workspace select default && terraform workspace delete -force prod`.

The practical risk: if `terraform.workspace` was used in resource names (e.g., `name = "myorg-${terraform.workspace}-rds"`), the resource names in state still reflect the old workspace name, but the new workspace name would compute a different name — `plan` will show destroy + recreate for every resource that embedded the workspace name. You must also update all resource name references if you rename. This is a strong argument for *not* embedding `terraform.workspace` directly in resource names — use a separate `var.environment` that you explicitly set per workspace instead, so renaming workspaces doesn't force resource recreation.

**Q18. How does workspace state isolation affect `terraform destroy`?**
A: `terraform destroy` in a workspace only destroys resources tracked in *that workspace's* state file. Running `terraform destroy` in `staging` will never touch `prod` resources, even if they were created from the same `.tf` files. This is the correct safety behavior. The workflow for tearing down a full environment:

```bash
# Tear down staging completely
terraform workspace select staging
terraform destroy -var-file=staging.tfvars

# Confirm state is empty
terraform state list  # Should return nothing

# Delete the workspace itself
terraform workspace select default
terraform workspace delete staging
```

If you run `terraform destroy` in `default` while other workspaces exist and have resources, only the `default` workspace's state is affected. The other workspaces' resources are untouched. This per-workspace isolation is what makes workspaces viable for ephemeral environments — you can destroy a PR environment without any risk of affecting dev or staging.

**Q19. Scenario: "An engineer ran `terraform apply` in the `prod` workspace when they meant to use `staging`. Resources were created in production. How do you handle this?"**
A: This is a real incident requiring immediate structured response:

**Immediate (< 5 minutes):**
1. Do not run `terraform destroy` yet — destroying production resources may cause more damage than the accidental creation.
2. Assess what was created: `terraform workspace select prod && terraform state list` — identify the new resources.
3. Check if the accidental resources are serving traffic or affecting live systems (e.g., an accidental security group rule change that opened ports to the internet is urgent; an extra EC2 instance sitting idle is not).

**Short-term (< 1 hour):**
4. If the resources are safe to remove (no traffic, no data), run a targeted destroy: `terraform destroy -target=aws_instance.accidental_resource` — remove only what was accidentally created without touching the rest of prod state.
5. If removing them would cause disruption, leave them and remove them in a proper change window.
6. Audit CloudTrail to confirm the scope of what was created/modified.

**Prevention (post-incident):**
7. Add the IAM workspace scoping from Q14 — the prod CI role cannot write to the staging workspace's state and vice versa. If prod and staging use separate AWS accounts (recommended), this is automatic — the wrong credentials simply can't affect the other account.
8. Add the explicit workspace assertion check from Q14 to every pipeline.
9. Require `TF_WORKSPACE` environment variable in CI instead of relying on `terraform workspace select` — makes the intended workspace explicit in every job definition.

**Q20. What is `TF_WORKSPACE`, and how does it differ from `terraform workspace select`?**
A: `TF_WORKSPACE` is an environment variable that Terraform reads at startup to select the workspace, before any CLI command runs. It's equivalent to `terraform workspace select <name>` but happens implicitly:

```bash
# These are equivalent
terraform workspace select prod && terraform plan

TF_WORKSPACE=prod terraform plan
```

In CI/CD, `TF_WORKSPACE` is preferred over `terraform workspace select` for two reasons:
1. **Explicitness in the job definition** — the workspace is visible as an environment variable in the pipeline YAML, not buried in a shell script. Reviewers can see at a glance which workspace each job targets.
2. **No race condition** — `terraform workspace select` writes the selection to `.terraform/environment` on disk. In ephemeral CI containers this is fine, but in shared CI agents it could theoretically be overwritten by a concurrent job. `TF_WORKSPACE` is process-scoped (an environment variable), so it's isolated to the current job.

```yaml
# GitHub Actions — workspace is explicit and reviewable
- name: Terraform Apply (Staging)
  env:
    TF_WORKSPACE: staging
    AWS_ROLE_ARN: arn:aws:iam::STAGING_ACCOUNT:role/TerraformCI
  run: terraform apply -auto-approve -var-file=staging.tfvars
```

## Section 6: Compliance, Security & Real-World Fintech Patterns

**Q21. In a PCI-DSS or RBI-regulated environment, can you use one Terraform workspace per environment within a single AWS account?**
A: Technically yes, practically inadvisable for `prod` isolation. PCI-DSS and RBI data localization guidelines push toward strong environment segmentation — ideally separate AWS accounts per environment. With a single AWS account and workspace-based isolation, the protection is only at the state level (workspaces don't know about each other's resources) and at the IAM level (CI roles scoped per workspace). But there is no account-level blast radius containment: a misconfigured IAM policy, a compromised CI secret, or a Terraform provider bug could affect all environments. The RBI Cybersecurity Framework's principle of segregation of duties maps more cleanly to separate AWS accounts — prod resources live in an account that dev engineers and dev pipelines cannot access by construction, not just by policy. Recommendation: use workspace-per-environment only for `dev`/`staging`; put `prod` in a separate AWS account with its own backend, own CI role, and own KMS key.

**Q22. How do you enforce that resource tags always include the workspace name for cost allocation and compliance?**
A: Use a `default_tags` block on the AWS provider combined with `terraform.workspace`:

```hcl
provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      Environment = terraform.workspace
      ManagedBy   = "terraform"
      Project     = var.project
      CostCenter  = var.cost_center
    }
  }
}
```

`default_tags` applies the specified tags to every AWS resource the provider creates, without you having to add a `tags` block to each resource. If a resource also has its own `tags` block, those are merged — resource-level tags take precedence on key conflicts. This is the cleanest enforcement mechanism: even if an engineer forgets to tag a resource, the provider-level default tags apply. For PCI-DSS, mandatory tags like `DataClassification`, `ComplianceScope`, and `Environment` can all go here — every resource in the `prod` workspace is automatically tagged `Environment = prod`.

**Q23. How do you audit which resources live in which workspace, and how do you detect workspace sprawl?**
A: There's no native Terraform command to list all workspaces across all backends or all resources across all workspaces. Auditing requires external tooling:

**S3-based audit** — list all state files in the S3 bucket to discover all workspaces:
```bash
aws s3 ls s3://myorg-terraform-state/env:/ --recursive | \
  grep terraform.tfstate | \
  awk '{print $4}'
# Output:
# env:/pr-142/services/loans-api/terraform.tfstate
# env:/pr-199/services/loans-api/terraform.tfstate  ← leaked PR environment
# env:/staging/services/loans-api/terraform.tfstate
# env:/prod/services/loans-api/terraform.tfstate
```

This reveals workspace sprawl — `pr-142` and `pr-199` are leaked PR environments whose pipelines failed before running `terraform destroy`. Add this S3 listing to a weekly cleanup cron job that checks each `pr-*` workspace against the GitHub API (is that PR still open?) and destroys any orphaned ones.

**AWS Config + resource tags** — if you enforce the `Environment` tag from Q22, AWS Config can generate a report of all resources per environment tag value. Cross-referencing this with your Terraform workspace list reveals any resources not managed by Terraform (created manually, escaped the tagging, or in a state file that got deleted without a destroy).

**Q24. What is the workspace metadata file `.terraform/environment`, and what happens if it gets corrupted or contains the wrong workspace?**
A: After running `terraform workspace select <name>`, Terraform writes the workspace name to `.terraform/environment` — a plain text file containing just the workspace name. On subsequent Terraform commands, it reads this file to determine the current workspace. If `.terraform/environment` is missing, Terraform defaults to `default`. If it contains the wrong workspace name (corrupted, stale from a previous run, copied from another directory), every `plan` and `apply` runs against the wrong state — silently.

In ephemeral CI containers this is not a concern (the `.terraform/` directory is freshly initialized each run). In persistent CI agents or local development, it can cause subtle workspace confusion. The safe practices: always run `terraform workspace show` as the first step of any Terraform script to assert the workspace before proceeding, and prefer `TF_WORKSPACE` (Q20) which bypasses this file entirely. The explicit assertion script from Q14 also catches this — comparing `TF_WORKSPACE` or `ENVIRONMENT` against `terraform workspace show` output before any destructive command.

**Q25. Scenario: "Your team is migrating from a single-workspace setup (everything in `default`) to a workspace-per-environment model. What is the migration path, and what are the risks?"**
A: Migrating from `default` to named workspaces without destroying and recreating resources requires carefully moving state. The full procedure:

**Step 1 — Snapshot current state:**
```bash
terraform workspace select default
terraform state pull > default-state-backup.json
# Store this in S3 as a manual backup before touching anything
```

**Step 2 — Create target workspaces:**
```bash
terraform workspace new dev
terraform workspace new staging
terraform workspace new prod
```

**Step 3 — For each environment currently tracked in `default`, split the state:**
If `default` tracks resources from all environments (a common anti-pattern where tags differentiate but state is shared), you need to `state rm` resources from `default` and `state push` them into the appropriate workspace. This is workspace migration, not just renaming:
```bash
# Pull the default state
terraform workspace select default
terraform state pull > split-source.json

# Switch to the target workspace
terraform workspace select prod

# Import or push specific resources using targeted state surgery
# (terraform state mv doesn't work cross-workspace — use pull/push)
terraform state push <carefully edited state JSON containing only prod resources>
```

**Risk 1 — Resource name drift** — if `terraform.workspace` is now embedded in resource names, resources created in `default` were named `myorg-default-rds`. Moving state to `prod` workspace means Terraform now expects `myorg-prod-rds`. The plan will show destroy + recreate. Mitigation: use `var.environment` instead of `terraform.workspace` for resource names, and set `var.environment = "prod"` via `tfvars` — decouples the workspace name from the resource name.

**Risk 2 — Parallel apply window** — during migration, the `default` workspace and new workspaces briefly both have references to the same real-world resources. If anyone runs apply in `default` during migration, they may try to modify resources now managed by `prod`. Solution: block all applies in `default` (revoke CI role permissions for default workspace state key) before beginning migration.

**Risk 3 — Incomplete migration** — if the split fails partway through and both `default` and `prod` have overlapping state for the same resources, the next apply in either workspace will try to manage the same real-world object and one will win destructively. Always verify `terraform plan` shows zero changes in the new workspace before removing resources from `default`.

Post-migration: run `terraform plan` in each new workspace and confirm it shows no changes. Then remove all resources from `default` state (`terraform state rm`) and leave `default` empty as a convention marker that the migration is complete.

## Quick Comparison Table

| Aspect | Built-in Workspaces | Separate Root Modules |
|---|---|---|
| State isolation | Per-workspace state file | Per-directory/backend state file |
| Config sharing | Same `.tf` files for all envs | Shared via child modules; env dirs call modules |
| Backend config | Shared (same S3 bucket/DynamoDB) | Per-environment (can differ per account/region) |
| AWS account isolation | ✗ — all envs in same account | ✓ — each env can use a different account |
| Accidental cross-env apply | Possible (wrong `workspace select`) | Hard (must `cd` to wrong directory) |
| Env-specific resources | `terraform.workspace` conditionals | Explicit in each env's `main.tf` |
| Best for | Ephemeral / identical envs | Long-lived / structurally different envs |
| CI/CD mapping | Workspace selection in shared pipeline | Separate pipelines per environment dir |
| Tooling (Atlantis/Spacelift) | `workspace` field in project config | Directory-based project config |
| Rename flexibility | No rename command | Just rename the directory |

**Tip for the interview:** At 5 YOE, the workspace question is almost never "what is a workspace?" — it's "when would you use workspaces versus separate root modules?" (Q11) and "what goes wrong with workspaces at scale?" (Q10). Have a crisp answer: workspaces for ephemeral/identical environments, separate root modules for long-lived prod with compliance requirements or structural env differences. Be ready to explain the `env:/` S3 key structure (Q4) — it signals you've actually debugged workspace state issues. The accidental-apply-to-prod scenario (Q19) and the migration scenario (Q25) are common senior-level follow-ups. Also know `TF_WORKSPACE` (Q20) and why it's safer than `terraform workspace select` in CI — that's a detail that separates people who've run Terraform in production from people who've only read the docs.
