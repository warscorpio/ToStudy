# `.dockerignore`: Build Context, Pattern Syntax, and Production Patterns — Interview Q&A (5 YOE Level)

---

## Section 1: The Build Context and Why `.dockerignore` Exists

**Q1. What is the Docker build context, and what happens before the first Dockerfile instruction executes?**
A: When you run `docker build .`, the `.` is not "the current directory" from Docker's perspective — it is the **build context**: an archive of files that the Docker CLI packages and streams to the Docker daemon (or BuildKit) before any Dockerfile instruction executes. Every file in the build context is transferred in full, regardless of whether any `COPY` instruction ever references it.

**The build context transfer sequence:**

```
Developer runs: docker build -t nestjs-api:latest .

Step 1: Docker CLI scans the build context directory (.)
        Applies .dockerignore rules to produce the inclusion list.
        Tarballs the remaining files into a single archive.

Step 2: The tarball is sent over the Docker socket (/var/run/docker.sock)
        to the Docker daemon (or BuildKit daemon).
        This transfer happens entirely before FROM executes.

Step 3: The daemon extracts the tarball into a temporary directory.
        This directory is the "context" that COPY and ADD instructions
        read from during the build.

Step 4: Dockerfile instructions execute, reading from the extracted context.

The critical implication:
  COPY src/ ./src/  copies from the daemon's extracted context, NOT from
  the developer's live filesystem. The context is a snapshot taken at
  docker build time.

  If a file is not in the context (excluded by .dockerignore or simply
  not present in the build context directory), no COPY instruction
  can include it — even if you write COPY secret.key ./
  → "COPY failed: file not found in build context: secret.key"
```

**What the transfer looks like without .dockerignore:**

```
$ docker build . 2>&1 | head -3
Sending build context to Docker daemon  1.04GB   ← entire project directory

Breakdown of that 1.04 GB:
  node_modules/       847 MB   (npm packages; built for host OS)
  .git/               156 MB   (full git history, all branches, all objects)
  dist/                42 MB   (previous TypeScript compile output)
  coverage/            11 MB   (Jest coverage HTML reports)
  .env                <1 KB    (database passwords, API keys — sent to daemon)
  src/                 8 MB    (actual source code — the only part needed)

Transfer time on a developer laptop: 15–45 seconds
Transfer time in CI (daemon on same host): 5–15 seconds

What the daemon does with node_modules/:
  Receives 847 MB. Stores it in its temporary context directory.
  If the Dockerfile has COPY . . → copies into the image layer
    → image now contains both the host's node_modules AND the one installed
       by RUN npm ci inside the container.
    → The host's node_modules (compiled for macOS/Windows) overwrites
       the container's (compiled for linux/amd64).
    → Native addons (.node files) crash at runtime:
       "Error: .../bcrypt_lib.node: invalid ELF header"
  If the Dockerfile does NOT have COPY . . :
    → 847 MB transferred and stored, then immediately discarded. Pure waste.
```

**The .dockerignore contract:**

```
.dockerignore tells the Docker CLI which files to EXCLUDE from the tarball
before it is sent to the daemon.

Excluded files:
  - Are never transferred (bandwidth and time saved)
  - Are never stored in the daemon's context directory
  - Cannot be referenced by any COPY or ADD instruction
  - Are never accidentally included in an image layer
  - Cannot leak secrets into the image

.dockerignore is read by the Docker CLI, not the daemon.
The daemon never sees excluded files — they do not exist as far as the
build is concerned.

Location: must be in the build context root (same directory as the Dockerfile
          when using the default build context path).
          Named exactly: .dockerignore (no extension; dot-prefixed)

Custom location (BuildKit only):
  docker buildx build --file Dockerfile.prod \
                      --build-context .=./app \
                      .
  .dockerignore is still read from the context root, not the Dockerfile location.
```

**Q2. How does the absence of a `.dockerignore` affect layer caching specifically?**
A: The build cache key for a `COPY` instruction is computed from the content hash of every file it matches. If `COPY . .` matches files that change on every build (IDE metadata, test output, git objects), the cache is invalidated on every build — even if the source code itself is unchanged.

**Cache invalidation from missing .dockerignore:**

```
Dockerfile:
  COPY package.json package-lock.json ./   ← Layer A
  RUN npm ci                               ← Layer B (87 MB; ~60s)
  COPY . .                                 ← Layer C
  RUN npm run build                        ← Layer D

Without .dockerignore, Layer C's cache key includes:
  .git/COMMIT_EDITMSG          ← changes on every git commit
  .git/index                   ← changes on every git add
  coverage/lcov.info           ← changes on every test run
  dist/main.js                 ← changes on every build (previous output)
  .vscode/settings.json        ← changes when developer updates IDE settings
  node_modules/.cache/...      ← changes constantly

Result:
  Layer C: cache MISS on almost every build
  Layer D: cache MISS (parent missed)
  Wasted: RUN npm run build re-executes even if only .vscode/settings.json changed.

With correct .dockerignore:
  Layer C's cache key includes ONLY:
    src/**/*.ts
    test/**/*.ts
    nest-cli.json
    tsconfig*.json
  Layer C: cache MISS only when actual source files change
  Layer D: cache MISS only when source files change
  Result: RUN npm run build is correctly skipped when only a git commit
          or test output changes.

The hidden performance multiplier:
  Without .dockerignore: npm ci cache is effectively useless in CI.
    Every build: COPY . . misses → npm run build runs → even if dependencies
    haven't changed, the compile runs again.
  With .dockerignore: npm ci cache hit rate approaches 90%+ for typical
    feature development where package.json rarely changes.
```

## Section 2: `.dockerignore` Pattern Syntax

**Q3. What is the complete `.dockerignore` pattern syntax, and how does it differ from `.gitignore`?**
A: `.dockerignore` uses a pattern syntax derived from Go's `filepath.Match` with some additions borrowed from `.gitignore`. The two are similar but not identical — several `.gitignore` features do not work in `.dockerignore`, and the negation semantics differ in important ways.

**Pattern syntax reference:**

```
# Comment line (hash at start of line)
  Any line beginning with # is ignored entirely.

*
  Matches any sequence of non-separator characters in a single path component.
  Does NOT cross directory boundaries.

  node_modules     → matches node_modules at the root
  *.log            → matches any .log file in the root directory ONLY
                     does NOT match logs/app.log
  *.test.ts        → matches user.test.ts but NOT src/user.test.ts

**
  Matches any number of directories, including zero.
  Crosses directory boundaries.

  **/*.test.ts     → matches user.test.ts AND src/user.test.ts
                     AND src/modules/user/user.test.ts
  **/node_modules  → matches node_modules/ at any depth
  logs/**          → matches everything inside logs/ at any depth

?
  Matches exactly one non-separator character.

  Dockerfile.?     → matches Dockerfile.1, Dockerfile.v, Dockerfile.p
                     does NOT match Dockerfile.prod (more than one char)

[abc] / [a-z]
  Character class — matches one character from the set or range.

  [Dd]ockerfile    → matches Dockerfile or dockerfile
  *.[oa]           → matches file.o and file.a

Trailing /
  Forces the pattern to match directories only, not files.

  dist/            → matches the dist/ directory but not a file named dist
  Note: in practice .dockerignore matches both; trailing / is advisory.
  Omit the trailing slash — it works without it and avoids confusion.

Leading /
  Anchors the pattern to the context root.

  /dist            → matches dist/ at root only
                     does NOT match src/dist/ or packages/api/dist/
  dist             → matches dist/ at root AND src/dist/ AND any nested dist/

! (negation / re-inclusion)
  Lines starting with ! re-include files that were previously excluded.
  Order matters: the LAST matching rule wins.

  .env*            → exclude all .env files
  !.env.example    → re-include .env.example specifically
  This works because .env.example is matched by .env* (excluded),
  then matched by !.env.example (re-included). Last rule wins.

  Negation only re-includes within what the parent directory allows:
  If a parent directory is excluded, negation of its children has no effect.

  node_modules     → exclude node_modules/
  !node_modules/sharp  → has NO effect — parent dir is excluded
                         The entire node_modules/ directory is already gone
                         from the context; its contents cannot be re-included.
  To re-include a subdirectory: you must NOT exclude the parent.
```

**Critical differences from `.gitignore`:**

```
Feature                    .gitignore         .dockerignore
──────────────────────────────────────────────────────────────
Pattern engine             Git pathspec       Go filepath.Match + extensions
Negation semantics         Works deeply       Parent exclusion blocks child negation
Trailing **                Supported          Supported
Anchoring (leading /)      Supported          Supported
Per-directory files        Yes (.gitignore    No — single file at context root only
                           at any level)
Pattern: [!abc]            Negated char class NOT supported (use [^abc] or avoid)
Pattern: \                 Escape character   Treated as escape (use sparingly)
Blank lines                Ignored            Ignored
Comments (#)               Supported          Supported
Order of rules             Last match wins    Last match wins
```

**Verification — test your .dockerignore before building:**

```bash
# Method 1: Check build context size before building
# (BuildKit reports context size before transfer)
docker buildx build --no-cache --progress=plain . 2>&1 | grep "transferring context"
# → #1 [internal] load build context
# → #1 transferring context: 1.2MB 0.1s ← good
# → #1 transferring context: 892MB 12s  ← .dockerignore missing or wrong

# Method 2: Use a throwaway image to list context contents
docker build -t ctx-check - << 'EOF'
FROM busybox
COPY . /context
RUN find /context -type f | sort
EOF
# Every file listed was in the build context.
# Anything you don't want to see here needs to be in .dockerignore.

# Method 3: dockerignore linting
# There is no official lint tool, but you can use:
npx dockerignore-checker .dockerignore .
# Or manually audit with the throwaway image approach above.

# Method 4: BuildKit --progress=plain shows exactly which files are transferred
DOCKER_BUILDKIT=1 docker build --progress=plain . 2>&1 | grep "COPY"
```

**Q4. What is the "last rule wins" evaluation model, and what are the common ordering mistakes?**
A: `.dockerignore` evaluates patterns from top to bottom. For any given file path, ALL patterns are tested, and the last pattern that matches determines whether the file is included or excluded. This differs from how many developers intuitively read the file (assuming first-match or include-by-default semantics).

**Last rule wins — worked examples:**

```
.dockerignore:
  *.env          ← Rule 1: exclude files matching *.env
  !.env.example  ← Rule 2: re-include .env.example

  File: .env.production
    Rule 1 matches (*.env) → excluded
    Rule 2 does NOT match  → still excluded
    Result: EXCLUDED ✅

  File: .env.example
    Rule 1 matches (*.env) → excluded
    Rule 2 matches (!.env.example) → re-included (last rule wins)
    Result: INCLUDED ✅

  File: .env
    Rule 1 matches (*.env) → excluded
    Rule 2 does NOT match  → still excluded
    Result: EXCLUDED ✅
```

**Common mistake 1: negation after a parent exclusion:**

```
.dockerignore:
  node_modules/          ← excludes entire node_modules/ directory
  !node_modules/sharp/   ← INTENDED: re-include sharp for a specific reason

  Result: the negation has NO effect.
  When node_modules/ is excluded, the directory is removed from the context.
  Its children (node_modules/sharp/) no longer exist in the context to be re-included.

  There is no workaround for this within .dockerignore alone.
  Solution: do not exclude node_modules/ at the parent level if you need
  a child. Instead, exclude specific subdirectories:

  node_modules/*           ← exclude all direct children of node_modules
  !node_modules/sharp      ← re-include sharp (this works — parent not excluded)

  But: this is almost never the right answer.
  The correct solution is multi-stage builds: never COPY node_modules from
  the host at all. Run npm ci inside the container. Then node_modules
  from the host is irrelevant and should be fully excluded.
```

**Common mistake 2: broad glob that re-includes secrets:**

```
.dockerignore:
  **/.env*          ← exclude all .env files at any depth
  !**/.env.example  ← re-include .env.example at any depth

  Looks correct. But watch for:
  .env.example.bak  → matched by .env* (excluded)
                      NOT matched by !**/.env.example
                      Result: EXCLUDED ✅ (accidental but safe)

  src/.env.test     → matched by **/.env* (excluded)
  NOT re-included.
  If test code needs src/.env.test as a fixture:
    !src/.env.test  ← add explicit re-inclusion

  Rule: be explicit with negations. Broad re-inclusions (!**/.env*)
  can accidentally re-include real .env files. Narrow re-inclusions
  (!.env.example) are safer and more auditable.
```

**Common mistake 3: forgetting that patterns without ** only match the root:**

```
.dockerignore:
  *.log    ← excludes app.log at root
             does NOT exclude logs/app.log
             does NOT exclude src/errors.log

  Symptom: log files in subdirectories appear in the image layer
           and inflate image size.

  Fix:
  **/*.log    ← excludes .log files at any depth
  logs/       ← excludes the entire logs/ directory specifically

  .dockerignore:
  **/*.log
  logs/
  *.log       ← redundant but harmless; documents intent for root-level logs
```

## Section 3: Production `.dockerignore` Patterns

**Q5. What does a complete production `.dockerignore` look like for a NestJS/Node.js project?**
A: A production `.dockerignore` is built around five categories: dependency artifacts (reinstalled inside the container), build outputs (rebuilt inside the container), development and test files (not needed at runtime), secrets and environment files (must never enter an image), and tooling configuration (irrelevant to the runtime).

**Complete production `.dockerignore` for a NestJS project:**

```dockerignore
# =============================================================================

# Host node_modules may be compiled for the wrong OS/arch.
node_modules/
.npm/

.yarn/cache/
.yarn/unplugged/

# Including stale dist/ output would pollute COPY . . layers.

# TypeScript incremental compilation info (specific to local machine)
*.tsbuildinfo

# Test coverage — large HTML/lcov reports irrelevant to runtime.
```

**What to NOT put in .dockerignore (common overcorrections):**

```
❌ Do not exclude: package.json, package-lock.json
   These are explicitly COPYed early in the Dockerfile for layer caching.
   If excluded from the context, COPY package*.json ./ fails.

❌ Do not exclude: tsconfig.json, tsconfig*.json
   RUN npm run build (tsc) reads tsconfig.json from the working directory.
   Excluding it breaks the TypeScript compilation step.

❌ Do not exclude: nest-cli.json
   NestJS CLI reads this during the build step. Excluding it breaks
   RUN npm run build for NestJS projects.

❌ Do not exclude: .npmrc (unless it has no tokens)
   If your .npmrc only contains registry settings (no auth tokens),
   the container may need it to resolve the correct npm registry.
   Only exclude .npmrc if it contains credentials — use BuildKit
   secret mounts for the auth token instead.

❌ Do not exclude: src/
   This is your source code. Excluding it means COPY src/ ./src/ fails.

❌ Do not exclude: public/ or assets/ (if served by the app)
   Static assets served by your NestJS app at runtime must be in the image.
   Exclude static assets only if they are served from a CDN/S3, not from
   the container's filesystem.

The test for whether something should be in .dockerignore:
   "Would including this file change what the application does at runtime?"
   If NO → exclude it.
   If YES (public/, locales/, static/) → include it.
```

**Q6. How does `.dockerignore` interact with multi-stage builds, and do you need different ignore rules per stage?**
A: `.dockerignore` applies to the entire build context — there is no per-stage filtering. Every file excluded by `.dockerignore` is unavailable to ALL stages. Every file included is available to ALL stages. This has practical implications for test files, documentation, and tooling config that some stages need but the runtime stage doesn't.

**The single-context constraint:**

```
Dockerfile (multi-stage):
  FROM node:20-alpine AS builder
  COPY . .              ← gets context minus .dockerignore exclusions
  RUN npm run build

  FROM node:20-alpine AS test
  COPY . .              ← same context; same exclusions
  RUN npm test          ← needs test files

  FROM node:20-alpine AS runtime
  COPY --from=builder /app/dist ./dist
  # Does NOT use COPY . . — no context files needed here

If .dockerignore excludes **/*.test.ts:
  → The test stage cannot COPY test files → RUN npm test fails.

If .dockerignore does NOT exclude **/*.test.ts:
  → Test files are in the context → both builder and test stages can use them
  → But builder stage does COPY . . which now includes test files
  → tsc may compile test files into dist/ (depends on tsconfig exclude config)
  → This is a tsconfig problem, not a .dockerignore problem:

  tsconfig.build.json (used by npm run build, not npm test):
  {
    "extends": "./tsconfig.json",
    "exclude": [
      "node_modules",
      "test",
      "dist",
      "**/*spec.ts",
      "**/*.test.ts"
    ]
  }

  package.json:
  {
    "scripts": {
      "build": "nest build --config nest-cli.json",
      "test": "jest"
    }
  }

  With this split:
    npm run build uses tsconfig.build.json → excludes test files at compile time
    npm test uses tsconfig.json + jest.config → includes test files
    .dockerignore does NOT need to exclude test files
    The runtime image only contains dist/ (COPYed from builder)
    Test files exist in the builder stage's COPY . . layer but are never compiled
    into dist/ and are never in the final runtime image.
```

**When you want different ignore rules per stage — using build contexts:**

```bash
# BuildKit supports named build contexts — each can have its own directory
# and implicitly its own .dockerignore

# Dockerfile using named contexts:
# FROM scratch AS source
# COPY --from=source . .   ← reads from the named context, not the default one

docker buildx build \
  --file Dockerfile \
  --build-context source=./src \     # named context: only src/
  --build-context config=./config \  # named context: only config/
  .

# In Dockerfile:
FROM node:20-alpine AS builder
COPY --from=source . ./src/     # only src/ — no need to exclude other dirs
COPY --from=config . ./config/  # only config/

# This is more surgical than .dockerignore and eliminates the single-context
# limitation for complex monorepos where different stages genuinely need
# different subsets of the filesystem.
```

**Monorepo-specific .dockerignore strategy:**

```
Monorepo structure:
  apps/
    nestjs-api/
    nestjs-worker/
    nextjs-frontend/
  packages/
    shared-types/
    ui-components/
  terraform/
  docs/

Building just nestjs-api from the monorepo root:
  docker build -f apps/nestjs-api/Dockerfile .

  Build context = entire monorepo root = potentially 2+ GB.

  .dockerignore at monorepo root:
    # Exclude apps we are NOT building right now
    apps/nestjs-worker/
    apps/nextjs-frontend/
    # Keep apps/nestjs-api/ (needed by the build)
    # Keep packages/ (shared types needed by all apps)

    # Standard exclusions
    **/node_modules/
    **/dist/
    **/coverage/
    .git/
    terraform/
    docs/

  Better alternative: set build context to the minimum required subtree
    docker build \
      -f apps/nestjs-api/Dockerfile \
      --build-context .=./ \   # still root for workspace-level package.json
      .
  Or use per-app Dockerfiles with relative context:
    cd apps/nestjs-api && docker build .
    (requires apps/nestjs-api to have its own .dockerignore)
```

## Section 4: Security Implications

**Q7. What are the security consequences of a missing or incomplete `.dockerignore`, and how do you audit an image for accidentally included secrets?**
A: A missing `.dockerignore` is a secret leakage vector. Secrets included in the build context can reach the image layer via `COPY . .` — and once in a layer, they persist in the image manifest and are visible via `docker history`, even if a subsequent `RUN rm -f .env` deletes them. The delete only marks the file as deleted in the union filesystem; the underlying layer still contains the file.

**How secrets reach a built image:**

```
Scenario: developer's .env contains:
  DATABASE_URL=postgresql://admin:prod_password@rds.internal:5432/payments
  STRIPE_SECRET_KEY=sk_live_abc123...
  AWS_SECRET_ACCESS_KEY=wJalrXUtn...

Dockerfile:
  FROM node:20-alpine
  WORKDIR /app
  COPY . .              ← .env is in the build context → copied into this layer
  RUN rm -f .env        ← creates a NEW layer that marks .env as deleted
  RUN npm ci
  CMD ["node", "dist/main.js"]

The image now has:
  Layer 3 (COPY . .):  contains .env with all secrets ← this layer is permanent
  Layer 4 (RUN rm):    marks .env as whiteout (deleted in OverlayFS view)
  The user sees no .env in a running container — but the secret is in Layer 3.

Attacker extracts the secret:
  Method 1: docker history --no-trunc nestjs-api:latest
    Shows every RUN command. If credentials were passed via ENV or RUN echo,
    they appear here in plaintext.

  Method 2: docker save nestjs-api:latest | tar -x
    Produces a directory of layer tarballs. The layer from COPY . . still
    contains .env. Extract it:
    tar -xf <layer-hash>/layer.tar ./app/.env
    cat .env  → DATABASE_URL=postgresql://admin:prod_password@...

  Method 3: If the image is pushed to a registry:
    Anyone with registry pull access can pull the image and extract secrets.
    This includes: developers, CI/CD systems, ECS task execution roles,
    ECR image scanning services, and anyone who compromises any of these.

  The secret is exposed to everyone who can pull the image — now and forever
  (image manifests are immutable; layers are content-addressed by digest).
  The only remediation: delete the image from all registries and rotate
  every secret that was in the layer.
```

**Auditing an image for accidentally included secrets:**

```bash
# Method 1: docker history (shows RUN commands; catches ENV secrets)
docker history --no-trunc nestjs-api:latest | grep -i -E "key|secret|password|token"

# Method 2: Extract and search all layers
docker save nestjs-api:latest -o image.tar
mkdir image-extracted && tar -xf image.tar -C image-extracted

# Search all layer contents for common secret patterns
for layer_tar in image-extracted/*/layer.tar; do
  tar -tf "$layer_tar" 2>/dev/null | grep -i -E "\.env|secret|credentials|\.pem|\.key"
done

# Method 3: Trivy secret scanning (automated; catches common patterns)
trivy image --scanners secret nestjs-api:latest
# Trivy scans all layers for:
#   AWS access keys (AKIA..., ASIA...)
#   Private key headers (-----BEGIN RSA PRIVATE KEY-----)
#   Generic high-entropy strings matching secret patterns
#   .env file content patterns (KEY=value with sensitive key names)

# Method 4: Grype (vulnerability + secret scanning)
grype nestjs-api:latest

# Method 5: Trufflehog for deep layer scanning
trufflehog docker --image nestjs-api:latest

# Integrate into CI — fail the pipeline if secrets are detected:
trivy image --scanners secret --exit-code 1 nestjs-api:latest
# exit code 1 = secrets found → pipeline fails → image is not pushed to registry
```

**Defense-in-depth: .dockerignore is the first line, not the only line:**

```
Layer 1 — .dockerignore: exclude .env* before it reaches the daemon.
  The file never enters the build context. Cannot be COPYed accidentally.

Layer 2 — BuildKit secret mounts: for build-time secrets (NPM_TOKEN, etc.)
  --mount=type=secret,id=npm_token
  Secret is available inside the RUN instruction but written to NO layer.

Layer 3 — Runtime secret injection: pull from SSM/Secrets Manager at startup.
  The image contains no secrets. At runtime, UserData or the entrypoint
  script fetches secrets from SSM Parameter Store or Secrets Manager.
  Credentials are only in the container's environment at runtime,
  not in the image layer.

Layer 4 — Image scanning in CI: Trivy secret scan before registry push.
  Catches accidents that slipped through layers 1–3.
  Pipeline fails; image is not pushed; engineer is notified.

Layer 5 — ECR image scanning: automatic scan on push (ECR enhanced scanning).
  Secondary gate after CI; catches anything that reached the registry.

Layer 6 — Least privilege registry access: ECR resource policies.
  Only authorized roles (ECS task execution, specific CI roles) can pull.
  Limits exposure if a secret does reach a registry layer.

If ALL six layers are in place, a .env file accidentally left off
.dockerignore will:
  1. Not be excluded by .dockerignore (miss in layer 1)
  2. Be detected by Trivy in CI (caught in layer 4)
  3. Fail the pipeline; not pushed to registry
  4. Engineer is paged; .dockerignore is updated; secret is rotated
```

## Section 5: Advanced Patterns and Edge Cases

**Q8. How do you handle `.dockerignore` for projects with assets that the application needs at runtime?**
A: Not all non-code files should be excluded. Static files served by the application, locale strings, email templates, and migration SQL files are needed at runtime and must be included. The rule is: exclude files that change the build process but not the runtime behavior; include files that the running application reads from disk.

**Files that must be in the image (do not exclude):**

```
public/                Static files served by NestJS ServeStaticModule
  public/index.html
  public/favicon.ico
  public/robots.txt
  → If excluded: 404 on all static file requests at runtime.

src/templates/         Handlebars/Pug email templates loaded at runtime
  email/welcome.hbs
  email/reset-password.hbs
  → If using fs.readFileSync('./templates/welcome.hbs') at runtime
    and templates are excluded: ENOENT at runtime.
  → Prefer embedding templates in dist/ via TypeScript import() or
    nest-cli.json assets configuration:
    "assets": [{ "include": "**/*.hbs", "outDir": "dist/templates" }]
    This copies templates into dist/ during npm run build →
    they end up in the image via COPY --from=builder /app/dist ./dist
    without needing to COPY the src/templates/ directory separately.

migrations/            Database migration SQL or TypeScript migration files
  0001_initial.sql
  0002_add_users.sql
  → If migrations run at container startup (not recommended, but common):
    migrations/ must be in the image.
  → Better: run migrations as a separate Job (Kubernetes) or
    a one-off task before deployment. The migration runner container
    can include migrations/; the API runtime container does not need them.

locales/               i18n translation files loaded at runtime
  en.json
  hi.json
  → Exclude from .dockerignore only if translations are bundled into
    dist/ by the build step. Otherwise include them and COPY explicitly.

prisma/schema.prisma   If using Prisma, the schema is needed at runtime
                       for query engine initialization.
  → COPY prisma/ ./prisma/ explicitly, or include in the context.
```

**Strategy: explicit COPY over COPY . . for runtime assets:**

```dockerfile
# Instead of COPY . . (which requires careful .dockerignore) use explicit COPYs:
FROM node:20-alpine AS runtime
WORKDIR /app

# Production dependencies
COPY --from=prod-deps /app/node_modules ./node_modules

# Compiled application
COPY --from=builder /app/dist ./dist

# Runtime assets (explicit; nothing is accidentally included or excluded)
COPY public/              ./public/
COPY locales/             ./locales/
COPY prisma/schema.prisma ./prisma/schema.prisma

# Metadata
COPY package.json ./

# No COPY . . → .dockerignore exclusions are irrelevant for the runtime stage
# because we never copy the raw source context into it.
# .dockerignore still matters for the builder stage where COPY . . is used.
```

**Q9. What are the `.dockerignore` considerations for a Turborepo or Nx monorepo?**
A: Monorepos compound the build context problem because the repository root contains multiple applications and packages, only a subset of which are needed for any single Docker build. Without careful `.dockerignore` configuration, building a single microservice pulls in the entire monorepo — including other services' `node_modules`, build outputs, and source code.

**Monorepo context size without .dockerignore:**

```
Turborepo structure:
  apps/api/           (NestJS — the service being built)
  apps/web/           (Next.js — not needed for this build)
  apps/worker/        (NestJS worker — not needed)
  packages/ui/        (React component library — not needed for API)
  packages/shared/    (TypeScript utilities — needed by API)
  packages/db/        (Prisma schema + client — needed by API)
  node_modules/       (hoisted dependencies — 1.4 GB)
  .turbo/             (Turborepo cache — 200 MB)
  dist/ (×3 apps)     (450 MB combined build outputs)

docker build -f apps/api/Dockerfile .
Build context without .dockerignore: ~2.1 GB
Build context with correct .dockerignore: ~15 MB
```

**Monorepo `.dockerignore` strategy:**

```dockerignore
# =============================================================================
# MONOREPO ROOT .dockerignore
# =============================================================================

# Hoisted node_modules — reinstalled inside the container
node_modules/

# All build outputs — rebuilt inside the container
**/dist/
**/.next/
**/.turbo/
**/.nx/

# Apps not being built (exclude their entire directory)
apps/web/
apps/worker/

# Packages not needed by the API
packages/ui/

# Keep:
#   apps/api/          (the service being built)
#   packages/shared/   (needed by apps/api)
#   packages/db/       (Prisma schema needed by apps/api)
#   package.json       (root workspace manifest)
#   pnpm-workspace.yaml or turbo.json

# Standard exclusions
.git/
.github/
**/.env*
!**/.env.example
**/coverage/
**/*.log
terraform/
docs/
*.md
```

**Per-app Dockerfile with root context vs scoped context:**

```bash
# Option A: Build from monorepo root (allows workspace resolution)
cd /repo/root
docker build -f apps/api/Dockerfile .
# .dockerignore at /repo/root/.dockerignore applies

# Option B: Scoped context with additional context mount (BuildKit)
docker buildx build \
  --file apps/api/Dockerfile \
  --build-context root=. \              # root for workspace package.json
  --build-context api=./apps/api \      # only the API source
  --build-context shared=./packages/shared \  # only shared package
  apps/api/
# Dockerfile uses COPY --from=root, --from=api, --from=shared

# Option C: Each app has its own Dockerfile and .dockerignore
# apps/api/.dockerignore exists; build context is apps/api/
# Limitation: cannot access monorepo root package.json for workspace setup
# Solution: apps/api/package.json has no workspace references; standalone install
```

**Q10. How do you handle `.dockerignore` when the Dockerfile is not in the build context root?**
A: By default, `.dockerignore` is read from the root of the build context, regardless of where the Dockerfile is located. If you specify a custom Dockerfile path with `-f`, the `.dockerignore` is still read from the build context root — not from the directory containing the Dockerfile.

**Default behavior with `-f`:**

```bash
# Dockerfile is in infra/docker/Dockerfile.prod
# Build context is the project root (.)
docker build -f infra/docker/Dockerfile.prod .

# .dockerignore read from: ./  (context root) ← correct
# NOT from: ./infra/docker/   (Dockerfile directory)

# This means:
# If .dockerignore is at ./infra/docker/.dockerignore → it is IGNORED
# .dockerignore must be at ./.dockerignore to take effect
```

**Per-Dockerfile `.dockerignore` (BuildKit feature):**

```bash
# BuildKit supports a naming convention for per-Dockerfile .dockerignore:
# Dockerfile.prod → .dockerignore.prod (same name, different extension convention)
# Note: this is NOT standard Docker behavior — it requires BuildKit and
# the DOCKER_BUILDKIT=1 environment variable or buildx.

# Dockerfile: Dockerfile.prod
# .dockerignore: Dockerfile.prod.dockerignore  ← BuildKit reads this first
#                Falls back to .dockerignore if not found

DOCKER_BUILDKIT=1 docker build -f Dockerfile.prod .
# BuildKit looks for: Dockerfile.prod.dockerignore → .dockerignore

# Practical use:
# .dockerignore         → shared base rules (node_modules/, .git/, .env*)
# Dockerfile.test.dockerignore → re-include test files for the test build
# Dockerfile.prod.dockerignore → stricter exclusions for production
```

**When multiple Dockerfiles need different ignore rules:**

```
apps/api/
  Dockerfile            ← production image
  Dockerfile.dev        ← development image (includes devDependencies)
  Dockerfile.test       ← test runner image (needs test files)
  .dockerignore                   ← base exclusions (node_modules, .git)
  Dockerfile.dev.dockerignore     ← extends base; re-includes dev config
  Dockerfile.test.dockerignore    ← extends base; re-includes test fixtures

.dockerignore (base):
  node_modules/
  dist/
  .git/
  .env*
  !.env.example
  coverage/

Dockerfile.test.dockerignore:
  node_modules/
  dist/
  .git/
  .env*
  !.env.example
  !.env.test.example
  # DO NOT exclude test files — the test Dockerfile needs them
  # coverage/ still excluded (rebuilt by the test run)
  coverage/

Dockerfile.prod.dockerignore:
  node_modules/
  dist/
  .git/
  .env*
  !.env.example
  coverage/
  # Additionally exclude test files from production build context
  **/*.test.ts
  **/*.spec.ts
  **/*.e2e-spec.ts
  __tests__/
  __mocks__/
  jest.config.*
  test/
```

## Section 6: Scenario and Debugging Questions

**Q11. "Your CI build is 8 minutes but a colleague's local build is 45 seconds for the same commit. What do you investigate?"**
A:

```
The most common cause of this gap is build context transfer time and
cache availability. Investigate in this order:

Step 1: Compare build context sizes
  Colleague (local):
    docker build . 2>&1 | head -1
    → Sending build context to Docker daemon  1.2MB (0.1s)

  CI (GitHub Actions fresh runner):
    Build logs: "Sending build context to Docker daemon  892MB (23s)"
    → Missing or wrong .dockerignore in CI

  Why different? Colleague has correct .dockerignore; CI is running from
  a directory that includes .git/ or the runner has files not in .gitignore.

  Fix: ensure .dockerignore is committed to the repository.
       (If .dockerignore is in .gitignore, it won't be checked out in CI.)
       Verify: git ls-files .dockerignore → should show the file.

Step 2: Check cache availability in CI
  Colleague (local): Docker daemon has cached layers from previous builds.
    npm ci layer: CACHED (0s)

  CI (fresh runner): no cache; every layer rebuilt.
    npm ci layer: RUN npm ci ... 87s

  Fix:
    Add --cache-from / --cache-to with ECR registry cache:
    --cache-from type=registry,ref=$ECR:cache
    --cache-to   type=registry,ref=$ECR:cache,mode=max

    First CI run: no cache → full build → pushes cache to ECR
    Subsequent CI runs: pull npm ci layer from ECR → ~5s instead of 87s

Step 3: Check build platform mismatch
  Colleague: native amd64 machine → amd64 build (fast)
  CI: --platforms linux/amd64,linux/arm64 → QEMU emulation for arm64

  Building arm64 under QEMU on an amd64 CI runner is 3–5× slower than
  native. npm ci under QEMU: ~4 minutes vs ~60 seconds native.

  Fix:
    Use native arm64 runners for the arm64 stage:
    jobs:
      build-amd64:
        runs-on: ubuntu-latest          # native amd64
      build-arm64:
        runs-on: ubuntu-24.04-arm       # native arm64 (GitHub-hosted)
    Then merge manifests with docker buildx imagetools create.

Step 4: Check for BuildKit availability
  Without BuildKit: layers are built sequentially; no parallelism.
  With BuildKit:    independent stages build in parallel.
  Verify: DOCKER_BUILDKIT=1 or using docker buildx build.

Step 5: Check for network latency in CI region
  apk add, npm ci, pulling base image: all network calls.
  If CI runner is in us-east-1 but ECR is in ap-south-1:
    Base image pull: slow (cross-region)
    npm registry: slow if not using a regional mirror
  Fix: run CI runners in the same region as the registry;
       use a regional npm mirror or Verdaccio cache.
```

**Q12. "A security audit finds that the production Docker image contains TypeScript source files. Walk through how this happened and how to fix it."**
A:

```
Root cause analysis:

The image contains TypeScript source files (.ts) in the final layer.
This means either:
  A) The build is single-stage — COPY . . in the only stage copies everything,
     including src/*.ts. No multi-stage build to discard source.

  B) Multi-stage build exists but the runtime stage has:
     COPY --from=builder /app ./
     This copies the ENTIRE /app directory from the builder — including
     /app/src/ (TypeScript source). The correct instruction is:
     COPY --from=builder /app/dist ./dist
     Only the compiled output, not the whole workspace.

  C) COPY . . in the runtime stage is not filtered by .dockerignore.
     Even with a multi-stage build, if the runtime stage uses COPY . .
     and .dockerignore does not exclude src/, source files are included.

Diagnosis:
  docker history --no-trunc nestjs-api:prod | grep COPY
  → COPY . . ← single-stage: problem A
  → COPY --from=builder /app ./ ← multi-stage but wrong source: problem B

  docker run --rm nestjs-api:prod find /app/src -name "*.ts" | head -5
  → /app/src/main.ts ← source files confirmed in image

Why source files in the image are a security risk:
  Source code reveals business logic, internal API structures, and
  sometimes embedded comments with credentials or architecture notes.
  An attacker with container exec access or who pulls the image can read
  all TypeScript source, making reverse engineering trivial.
  Compiled dist/ reveals the same logic but is harder to read and
  contains no TypeScript-specific metadata.

Fix (multi-stage + explicit COPY):

  # ❌ Before (problem B):
  FROM node:20-alpine AS runtime
  COPY --from=builder /app ./          # copies entire /app including src/

  # ✅ After (explicit, minimal COPY):
  FROM node:20-alpine AS runtime
  COPY --from=builder   /app/dist         ./dist
  COPY --from=prod-deps /app/node_modules ./node_modules
  COPY                  package.json      ./
  # src/ is never referenced → never in the image

  # Add to CI pipeline to prevent regression:
  - name: Verify no source files in image
    run: |
      COUNT=$(docker run --rm $IMAGE find /app -name "*.ts" 2>/dev/null | wc -l)
      if [ "$COUNT" -gt "0" ]; then
        echo "ERROR: TypeScript source files found in production image"
        docker run --rm $IMAGE find /app -name "*.ts"
        exit 1
      fi
```

## Quick Reference

| Pattern | Matches | Does NOT match |
|---|---|---|
| `node_modules` | `node_modules/` at root | `pkg/node_modules/` |
| `**/node_modules` | `node_modules/` at any depth | Nothing (universal) |
| `*.log` | `app.log` at root | `logs/app.log` |
| `**/*.log` | `app.log` and `logs/app.log` | — |
| `dist/` | `dist/` directory | A file named `dist` |
| `.env*` | `.env`, `.env.prod`, `.env.local` | Subdirectory `.env` files |
| `**/.env*` | `.env` files at any depth | — |
| `!.env.example` | Re-includes `.env.example` | Only works after an exclusion rule |

| File / directory | Exclude? | Reason |
|---|---|---|
| `node_modules/` | ✅ Always | Reinstalled in container; host binaries wrong arch |
| `dist/` / `build/` | ✅ Always | Rebuilt in container; stale output pollutes cache |
| `.git/` | ✅ Always | 100–500 MB; never needed in image |
| `.env` / `.env.*` | ✅ Always | Secrets must never enter the build context |
| `coverage/` | ✅ Always | Test output; irrelevant to runtime |
| `**/*.test.ts` | ⚠️ Maybe | Exclude from prod; keep for test stage if needed |
| `package.json` | ❌ Never | Needed by `COPY package*.json ./` |
| `package-lock.json` | ❌ Never | Needed by `COPY package*.json ./` |
| `tsconfig*.json` | ❌ Never | Needed by `RUN npm run build` |
| `src/` | ❌ Never | Source code — needed by the builder stage |
| `public/` | ❌ Maybe | Include if served at runtime; exclude if CDN-hosted |
| `migrations/` | ❌ Maybe | Include if migrations run at startup |
| `.npmrc` (no tokens) | ❌ Maybe | May be needed for registry config |
| `.npmrc` (with tokens) | ✅ Yes | Use BuildKit `--mount=type=secret` instead |

| Symptom | Likely cause | Fix |
|---|---|---|
| `Sending build context: 892MB` | Missing `.dockerignore` | Add `node_modules/`, `.git/`, `dist/` to `.dockerignore` |
| `npm ci` runs on every code change | `COPY . .` before `COPY package*.json` | Reorder: manifests first, source second |
| Native addon `invalid ELF header` | Host `node_modules/` copied into image | Add `node_modules/` to `.dockerignore`; let container install |
| `COPY failed: file not found` | File excluded by `.dockerignore` | Remove the exclusion for that file |
| Secrets found by Trivy in image | `.env` not in `.dockerignore` | Add `.env*` to `.dockerignore`; rotate secrets |
| TypeScript source in production image | `COPY --from=builder /app ./` | Change to `COPY --from=builder /app/dist ./dist` |
| CI build 5× slower than local | No registry cache; fresh runner | Add `--cache-from`/`--cache-to` registry cache in CI |
| Negation `!node_modules/pkg` has no effect | Parent `node_modules/` excluded | Cannot re-include children of excluded directories |
| `.dockerignore` ignored in CI | File not committed to git | `git ls-files .dockerignore`; remove from `.gitignore` |

## The Core Mental Model

```
.dockerignore is a gate at the build context boundary.
It runs before any Dockerfile instruction.
Files that do not pass the gate cannot be COPYed — by any stage, in any Dockerfile.
Files that do pass the gate are available to all stages equally.

The three jobs of .dockerignore:

  1. Speed: reduce build context size and transfer time.
     node_modules/ (800 MB) and .git/ (150 MB) are the two highest-value exclusions.
     Together they often account for 90% of an accidental build context.

  2. Cache integrity: exclude files that change frequently but are irrelevant to
     the build output.
     .git/COMMIT_EDITMSG, coverage/, .vscode/ — if these reach COPY . .,
     the layer cache is invalidated on changes that have nothing to do with
     the application. Every cache miss on a 60-second npm ci step is a wasted minute.

  3. Security: prevent secrets from entering the build context.
     A secret in the build context can reach an image layer via COPY . .
     A secret in an image layer is permanent — visible in docker history,
     extractable from any layer tarball, exposed to everyone with registry access.
     .dockerignore is the first line of defense; image scanning in CI is the second.

"Last rule wins" is the only evaluation model:
  Read the file bottom-up to understand what the final state of any
  given file is. A file excluded near the top and re-included near the bottom
  is included. A file included by default and excluded near the bottom is excluded.
  When debugging: add the file you're investigating as the last line to force-include,
  or add !filename to force-exclude. Test with the throwaway busybox image.

The parent exclusion trap:
  Excluding a directory excludes all its descendants permanently.
  No negation rule can re-include a child of an excluded directory.
  If you need a child: exclude the parent's children individually,
  or restructure your directory layout.
  In practice: the correct solution for node_modules/ is always multi-stage builds
  (install inside the container) — never selective re-inclusion from the host.

.dockerignore and multi-stage builds are complementary, not alternatives:
  .dockerignore controls what enters the build context (available to all stages).
  COPY --from= controls what moves between stages (what reaches the final image).
  .dockerignore: "don't send node_modules/ to the daemon at all."
  Multi-stage: "even if it's in the context, don't copy it into the runtime image."
  Both defenses together: source code and test files exist in the builder stage
  but are never referenced by COPY --from=builder in the runtime stage.
  The runtime image contains only what you explicitly promote with COPY --from=.
```

**Tip for the interview:** `.dockerignore` questions at 5 YOE converge on three areas: (1) build context mechanics — explaining that the tarball is sent to the daemon BEFORE any Dockerfile instruction executes, that excluded files are unavailable to ALL stages (not just the final one), and that the daemon never sees excluded files, demonstrates you understand the system rather than just knowing which patterns to copy-paste; (2) the cache invalidation link — connecting `.git/COMMIT_EDITMSG` changing on every commit to a `COPY . .` cache miss to `npm ci` re-running for 60 seconds shows you have diagnosed this in a real CI pipeline and understand that `.dockerignore` is as much a cache tool as a security tool; (3) the secret layer persistence problem — explaining that `RUN rm -f .env` after `COPY . .` does NOT remove the secret from the image (it creates a deletion marker in a new layer; the original layer still contains the file and is visible via `docker save` + `tar`) is the security insight that separates someone who has participated in a real secrets rotation incident from someone who learned Docker from a tutorial. The fintech callout: for services handling payment data or KYC documents, a `.env` file in a production image layer is a compliance incident under PCI-DSS and the DPDP Act — it must be reported, all affected images deleted from all registries, and all credentials rotated. The `.dockerignore` entry for `.env*` is a control in your audit evidence, not just a developer convenience.
