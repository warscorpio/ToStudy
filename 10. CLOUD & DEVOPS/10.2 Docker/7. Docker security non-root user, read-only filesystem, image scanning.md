# Docker Security: Non-Root User, Read-Only Filesystem, Image Scanning — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Container Security Is Different

**Q1. What are the unique security risks that containers introduce compared to running processes directly on a host?**
A: Containers share the host OS kernel — unlike virtual machines, which have separate kernels and hardware-level isolation. This shared kernel boundary is the root of every container security concern:

- **Kernel exploits are shared**: a vulnerability in the Linux kernel is exploitable from inside a container. A process running in a VM must first escape the hypervisor before reaching the host kernel; a process in a container only needs to exploit one kernel to affect the host and every other container running on it. The container's Linux namespaces (PID, network, filesystem, IPC) provide isolation at the process level, but they are kernel features — a sufficiently privileged container process can manipulate these namespace boundaries.

- **Root inside a container has host implications**: by default, Docker containers run as root (UID 0). If a container process runs as root and exploits a kernel vulnerability or escapes the container via a misconfiguration, it arrives on the host as root. The damage potential is unlimited: reading all files on the host filesystem, manipulating other containers, modifying the Docker daemon.

- **Image supply chain risk**: container images are layered tarballs pulled from registries (Docker Hub, ECR, GCR). Any layer can contain malicious code, known vulnerabilities in OS packages, or embedded secrets that were never cleaned from the image history. An application that would otherwise be secure can be compromised entirely by a vulnerable base image or a dependency with a known CVE.

- **Capability abuse**: Docker grants a default set of Linux capabilities to containers (a subset of root's full capability set). These defaults allow things like `NET_RAW` (raw socket access, useful for ARP spoofing), `SYS_CHROOT` (change root), and `MKNOD` (create device files). A container process that exploits its allowed capabilities can do significant damage without ever needing a kernel exploit.

- **Container escape via misconfiguration**: common misconfigurations — mounting the host's `/` into the container, running with `--privileged`, mounting the Docker socket, `SYS_ADMIN` capability — trivially allow container escape to root on the host. These are not exotic exploits; they are operational mistakes that happen in real deployments.

The security model for containers therefore must be layered: minimize what runs as root, minimize what the filesystem exposes, minimize what capabilities are granted, and continuously validate the supply chain of images.

**Q2. What is the Linux capability model and how does it apply to Docker containers?**
A: Traditional Unix security is binary: a process is either root (UID 0, can do anything) or non-root (limited). Linux capabilities replace this binary model with a fine-grained permission set — root's abilities are divided into ~40 distinct capabilities that can be granted or denied independently.

Docker containers run with a restricted set of capabilities by default — more than a non-root process but less than full root:

**Default capabilities Docker grants:**
```
AUDIT_WRITE      Write to kernel audit log
CHOWN            Change file ownership (chown)
DAC_OVERRIDE     Bypass file read/write/execute permission checks
FOWNER           Bypass permission checks for file operations
FSETID           Set file SUID/SGID bits
KILL             Send signals to processes (kill)
MKNOD            Create device files
NET_BIND_SERVICE Bind to ports < 1024 (e.g., port 80)
NET_RAW          Use raw sockets (ping, ARP spoofing potential)
SETFCAP          Set file capabilities
SETGID           Change GID
SETPCAP          Transfer capabilities to/from permitted set
SETUID           Change UID (su, sudo)
SYS_CHROOT       Change root directory (chroot)
```

**Capabilities Docker does NOT grant by default (require --cap-add):**
```
SYS_ADMIN        System administration (mount, sethostname, kernel modules...)
SYS_PTRACE       ptrace() other processes (debugging tools, strace)
NET_ADMIN        Network administration (iptables, interface config)
SYS_MODULE       Load kernel modules
SYS_RAWIO        Direct I/O to hardware
DAC_READ_SEARCH  Bypass file read permission checks
```

**Why the defaults still matter:**
`NET_RAW` (included by default) allows crafting raw network packets — useful for `ping` but also for ARP spoofing attacks within the container's network namespace. `SYS_CHROOT` can be used to escape into a different filesystem view. `SETUID`/`SETGID` allow privilege escalation within the container.

**The correct approach — drop all, add only what's needed:**
```dockerfile
# In production, drop all capabilities and add back only what the application needs
# (This is configuration in Docker run / Compose / Kubernetes, not Dockerfile)
```

```yaml
# docker-compose.yml
services:
  payment-api:
    cap_drop:
      - ALL                    # drop every capability
    cap_add:
      - NET_BIND_SERVICE       # only if binding to port < 1024
                               # Most Node.js apps on port 3000 don't need this
    security_opt:
      - no-new-privileges:true # prevent privilege escalation via setuid binaries
```

```yaml
# Kubernetes Pod spec
securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]  # only if needed
  allowPrivilegeEscalation: false
```

## Section 2: Non-Root Users in Containers

**Q3. What is the risk of running containers as root and how does a container-level root escape to the host?**
A: When a Docker container runs as root (UID 0), the container process has the full set of capabilities Docker grants by default. If a vulnerability in the application, the container runtime, or the kernel allows the container process to break out of its namespace isolation, it arrives on the host as UID 0 — root.

**Concrete escape paths that have existed in real systems:**

**Path 1 — Mounted host volume with writable root:**
```bash
# A common development pattern that is catastrophic in production
docker run -v /:/host -it ubuntu bash
# Now inside container:
chroot /host                    # pivot root into the host filesystem
ls /etc/shadow                  # read all host credential files
crontab -e                      # add a cron job that runs on the host
# Root in container = root on host when the host filesystem is mounted
```

**Path 2 — `--privileged` flag:**
`docker run --privileged` grants all capabilities including `SYS_ADMIN`, removes seccomp restrictions, and disables AppArmor. From a privileged container, escaping to the host is straightforward:
```bash
# Inside a --privileged container:
fdisk -l                        # enumerate host disk devices
mkdir /mnt/host
mount /dev/xvda1 /mnt/host     # mount the host disk directly
cat /mnt/host/etc/shadow        # read host credentials
# Or: write an SSH key to /mnt/host/root/.ssh/authorized_keys
```

**Path 3 — CVE-2019-5736 (runc container escape):**
This real vulnerability allowed a malicious container (running as root inside the container) to overwrite the `runc` binary on the host, gaining code execution as root on the host — through the container runtime's process itself. Running as non-root inside the container is not sufficient to exploit this (it requires executing a process in the container as root). The fix: run containers as non-root users.

**What non-root achieves:**
If the container process runs as UID 1000 (non-root) and a container escape vulnerability exists, the attacker arrives on the host as UID 1000 — still significant, but:
- Cannot read files owned by root or other users (unless world-readable).
- Cannot bind to privileged ports (< 1024) on the host.
- Cannot modify system files, install software, or modify other users' data.
- Limited lateral movement compared to arriving as root.

Non-root is not a silver bullet — it reduces the blast radius of an escape, not the probability. But reducing blast radius in a defense-in-depth model is valuable.

**Q4. How do you correctly configure a non-root user in a Dockerfile?**
A: Configuring non-root in a Dockerfile requires creating the user, setting file permissions correctly, and ensuring the application can write to whatever it needs to write to.

**Complete, production-correct Dockerfile for a NestJS application:**
```dockerfile
# Multi-stage build: build stage
FROM node:20-alpine AS builder

WORKDIR /app

# Copy package files (owned by root — this is fine in build stage)
COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

# ─────────────────────────────────────────────────
# Production stage: minimal image, non-root user
FROM node:20-alpine AS production

# Install dumb-init: PID 1 signal forwarding (critical for graceful shutdown)
RUN apk add --no-cache dumb-init

WORKDIR /app

# Create a non-root user and group
# Use a specific UID/GID (not a name-only user) for consistency across images
# UID/GID 1001: chosen to avoid conflicts with common system accounts
RUN addgroup --system --gid 1001 nodejs && \
    adduser  --system --uid 1001 --ingroup nodejs --no-create-home nestjs

# Copy built application from builder stage
# chown to the non-root user DURING the COPY (more efficient than a separate RUN chown)
COPY --from=builder --chown=nestjs:nodejs /app/node_modules ./node_modules
COPY --from=builder --chown=nestjs:nodejs /app/dist         ./dist
COPY --from=builder --chown=nestjs:nodejs /app/package.json ./package.json

# Create directories the application needs to write to
# (if any — ideally, the app writes to volumes or external storage, not local disk)
RUN mkdir -p /app/tmp && chown nestjs:nodejs /app/tmp

# Switch to non-root user BEFORE the final CMD
# Everything from this point runs as nestjs (UID 1001)
USER nestjs

# Expose the application port (documentation only — does not publish)
EXPOSE 3000

# Health check: runs as the non-root user
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
  CMD wget -q --spider http://localhost:3000/health || exit 1

# dumb-init as PID 1: properly forwards signals to the Node process
# Without dumb-init: Docker SIGTERM → PID 1 (node) but node doesn't forward to children
# With dumb-init: Docker SIGTERM → dumb-init → node → all child processes
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]
```

**Key details and why each matters:**

**`addgroup` + `adduser` with explicit GID/UID:**
Using a specific numeric UID (1001) rather than just a name ensures the UID is consistent — if another image in your organization also uses UID 1001 for a non-root user, they agree on the identity. Kubernetes and other orchestrators often refer to UIDs numerically in security policies.

**`--no-create-home`:**
The application user does not need a home directory. Creating one is an unnecessary filesystem surface — environment variables could write to `~/.bashrc`, history files, etc. Omit it.

**`COPY --chown` rather than a separate `RUN chown`:**
Each `RUN chown` creates a new image layer that doubles the size of the affected files — the original layer still contains the files owned by root, and the new layer contains the same files with new ownership. `COPY --chown` sets ownership at copy time, producing one layer with correct ownership and no size doubling.

**`USER nestjs` before `CMD`:**
The `USER` instruction sets the user for all subsequent `RUN`, `CMD`, `ENTRYPOINT` instructions. Placing it after the application files are in place (and before `CMD`) ensures: (a) the application runs as the non-root user, (b) any subsequent `RUN` commands in derived images also run as non-root.

**`dumb-init` as PID 1:**
This is not strictly a non-root concern but is architecturally coupled to it. When Docker sends SIGTERM (graceful shutdown), it sends it to PID 1. If `node` is PID 1, SIGTERM is received — but Node.js does not forward signals to child processes by default. `dumb-init` is a minimal init process that properly forwards signals. Without it, `SIGTERM` reaches Node.js but its child workers keep running until SIGKILL (9 seconds later with Docker's default timeout), causing ungraceful shutdown and potential data loss.

**Q5. What is the `no-new-privileges` security option and why is it important when running as non-root?**
A: `no-new-privileges` is a Linux security flag (`PR_SET_NO_NEW_PRIVS`) that prevents any process in the container from gaining additional privileges through `setuid` binaries or `setgid` binaries — even if the binary has the setuid bit set.

**The problem it solves:**
Even if your container runs as non-root (UID 1001), if the container image contains a setuid binary (a binary with the setuid permission bit, which causes it to run as its owner, typically root), a container process can execute that binary and temporarily escalate to root within the container:

```bash
# Inside a container running as UID 1001:
ls -la /usr/bin/su
# -rwsr-xr-x  root root  /usr/bin/su  ← setuid bit (s) means: run as owner (root)

# Without no-new-privileges:
/usr/bin/su -c "id"
# uid=0(root)  ← privilege escalation within the container

# With no-new-privileges:
/usr/bin/su -c "id"
# su: Authentication failure (blocked)
# The setuid bit is ignored; process stays as UID 1001
```

**Applying `no-new-privileges`:**
```yaml
# docker-compose.yml
services:
  payment-api:
    security_opt:
      - no-new-privileges:true

# docker run:
docker run --security-opt no-new-privileges:true payment-api:latest

# Kubernetes:
securityContext:
  allowPrivilegeEscalation: false   # equivalent to no-new-privileges
```

**Why this matters even in a "clean" image:**
Base images (Alpine, Ubuntu, Debian) often contain setuid binaries in `/usr/bin` and `/bin`. Even if you don't intend to use them, they exist in the image. Without `no-new-privileges`, they are exploitable by any process running in the container — your application code, a dependency, or a compromised package. With `no-new-privileges`, they are inert regardless of the setuid bit.

**Finding setuid binaries in an image:**
```bash
# Find all setuid/setgid binaries in the image
docker run --rm payment-api:latest \
  find / -perm /4000 -o -perm /2000 2>/dev/null
# /usr/bin/passwd (setuid)
# /usr/bin/su     (setuid)
# /usr/bin/newgrp (setuid)

# In production: the answer should be: no output
# Alpine-based images typically have fewer setuid binaries than Debian/Ubuntu
```

## Section 3: Read-Only Filesystem

**Q6. What is a read-only container filesystem and what does it protect against?**
A: Running a container with a read-only root filesystem (`--read-only`) mounts the container's filesystem in read-only mode. The container process cannot write anywhere on the filesystem except explicitly designated writable volumes or tmpfs mounts.

**What read-only filesystem prevents:**

**Malicious code dropping payloads:**
A compromised dependency or malicious package in the container's supply chain might attempt to write a persistent backdoor to disk — a cron job script, a modified binary, an SSH authorized_keys file. With a read-only filesystem, these write attempts fail immediately with `EROFS` (Read-only file system). The malicious code cannot persist anything.

**Log file manipulation:**
If an attacker can write to log files, they can cover their tracks by truncating or modifying audit logs. A read-only filesystem means logs must go somewhere external (stdout → CloudWatch, Fluentd) — the container cannot modify its own audit trail.

**Binary tampering:**
Without read-only filesystem, a compromised process could overwrite `node` with a modified binary, or replace a library with a malicious version — affecting all subsequent executions in the same container. Read-only filesystem makes this impossible.

**Temporary escalation survival across restarts:**
Even if an attacker achieves temporary code execution in a container, read-only filesystem ensures they cannot write anything that would survive a container restart — no persistent foothold.

**What read-only filesystem does NOT prevent:**
- In-memory attacks (code injection, ROP chains) — read-only is a filesystem control, not a memory control.
- Network-based attacks (the container can still make outbound connections).
- Writes to explicitly mounted volumes (these are writable by design).
- Writes to tmpfs mounts (in-memory, lost on restart but writable).

**Q7. How do you implement a read-only filesystem in a real NestJS application that needs some writable space?**
A: Most applications need to write somewhere — temporary files, PID files, npm's `.npm_cache`, Node.js's V8 code cache, or application-generated artifacts. Read-only root filesystem + targeted tmpfs mounts for these needs is the pattern:

```yaml
# docker-compose.yml
services:
  payment-api:
    image: payment-api:latest
    read_only: true           # root filesystem is read-only
    tmpfs:
      - /tmp:size=64m,mode=1777         # temporary files (world-writable with sticky bit)
      - /app/tmp:size=32m,uid=1001,gid=1001  # app-specific temp (owned by app user)
      - /run:size=8m,uid=1001,gid=1001   # PID files, runtime state
    volumes:
      - type: bind
        source: ./logs
        target: /app/logs    # if the app writes logs to disk (prefer stdout instead)
    environment:
      # Tell Node.js where to put its code cache
      NODE_V8_COVERAGE: /tmp/v8-coverage
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
```

```bash
# docker run equivalent
docker run \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --tmpfs /app/tmp:size=32m,uid=1001 \
  --tmpfs /run:size=8m \
  --security-opt no-new-privileges:true \
  --cap-drop ALL \
  payment-api:latest
```

**Kubernetes equivalent:**
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
        - name: payment-api
          image: payment-api:latest
          securityContext:
            readOnlyRootFilesystem:    true
            allowPrivilegeEscalation:  false
            runAsNonRoot:              true
            runAsUser:                 1001
            runAsGroup:                1001
            capabilities:
              drop: ["ALL"]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
            - name: app-tmp
              mountPath: /app/tmp
      volumes:
        - name: tmp
          emptyDir:
            medium: Memory          # tmpfs — in-memory, lost on restart
            sizeLimit: 64Mi
        - name: app-tmp
          emptyDir:
            medium: Memory
            sizeLimit: 32Mi
```

**Discovering what your application writes at runtime:**
Before adding `--read-only`, run the application with write monitoring to find what it needs to write:
```bash
# Run with strace to monitor filesystem write calls
docker run --rm \
  --cap-add SYS_PTRACE \
  payment-api:latest \
  strace -f -e trace=openat,open,write,creat -o /tmp/writes.log node dist/main.js

# OR: Run normally and use inotifywait to watch for writes
docker run -it --rm payment-api:latest bash -c "
  inotifywait -r -m --format '%w%f %e' / 2>/dev/null &
  node dist/main.js
"

# Common Node.js write locations:
# /tmp                    (os.tmpdir() — use tmpfs)
# /root/.npm              (npm cache — not needed in production)
# /root/.node_repl_history (REPL history — not applicable in production)
# app's log directory     (redirect to stdout instead)
```

**Verifying the read-only filesystem is effective:**
```bash
# After enabling --read-only, test that writes fail:
docker run --read-only payment-api:latest \
  touch /tmp-test-file 2>&1
# touch: /tmp-test-file: Read-only file system ← correct

docker run --read-only --tmpfs /tmp payment-api:latest \
  touch /tmp/test-file && echo "tmpfs write succeeded"
# tmpfs write succeeded ← tmpfs is writable as expected

docker run --read-only payment-api:latest \
  touch /app/test-file 2>&1
# touch: /app/test-file: Read-only file system ← app directory is read-only
```

## Section 4: Image Scanning

**Q8. What does container image scanning detect and what are its limitations?**
A: Container image scanning analyzes the contents of a Docker image — its layer filesystems and package manifests — against databases of known vulnerabilities (CVEs). It answers: "do any of the packages in this image have known security vulnerabilities?"

**What scanners detect:**

**OS package vulnerabilities:**
Packages installed via `apt`, `apk`, `yum`, `dnf` — libc, openssl, curl, bash, and their dependencies. These are cross-referenced against CVE databases (NVD, Debian Security Tracker, Alpine SecDB, RedHat OVAL).

```
Example finding:
  Package: libssl3 (3.0.7-1)
  CVE:     CVE-2023-0286
  Severity: HIGH
  Fixed in: 3.0.8-1
  Description: X.400 address type confusion in X.509 GeneralName
```

**Language runtime vulnerabilities:**
Node.js packages (from `package.json`/`package-lock.json`), Python packages (`requirements.txt`), Java JARs (from `pom.xml`, Maven repository structure). Scanners parse these manifests and cross-reference against language-specific vulnerability databases (npm Advisory Database, PyPI advisories, OSV).

**Secrets embedded in images:**
Some scanners (Trivy with `--scanners secret`, Trufflehog, GitLeaks) scan image layers for:
- Hard-coded API keys, tokens, passwords in environment variables.
- Private keys embedded in files.
- AWS access key patterns (`AKIA[0-9A-Z]{16}`).
- `.env` files that were accidentally copied into the image.

**Misconfigurations:**
Checkov, Hadolint, Dockle scan the Dockerfile for security misconfigurations:
- Running as root (no `USER` instruction).
- Latest tag usage (`FROM node:latest` instead of `FROM node:20.9.0`).
- `ADD` instead of `COPY` (ADD can fetch remote URLs and extract archives).
- Secrets in `ENV` instructions (visible in `docker inspect`).
- `COPY . .` without a `.dockerignore` (risk of copying `.env`, secrets files).

**What image scanning does NOT detect:**
- **Runtime behavior**: a package with no known CVE can still contain malicious code. Scanning is signature-based — it finds what's in the database, nothing more.
- **Zero-day vulnerabilities**: CVEs that haven't been disclosed yet.
- **Logic vulnerabilities in application code**: your own code's security flaws are invisible to scanners.
- **Runtime configuration mistakes**: wrong environment variables, insecure TLS settings, incorrect CORS policies — these are not in the image.
- **Supply chain attacks on untainted packages**: a popular package that was recently compromised but not yet reported (SolarWinds-style attack) passes scanning.

**Q9. What are the main image scanning tools and how do they compare?**
A:

**Trivy (by Aqua Security — recommended open source):**
```bash
# Install
brew install trivy   # macOS
apt-get install trivy  # Debian/Ubuntu

# Scan a local image
trivy image payment-api:latest

# Scan with specific severity filter
trivy image --severity HIGH,CRITICAL payment-api:latest

# Scan with secret detection
trivy image --scanners vuln,secret,config payment-api:latest

# Scan a Dockerfile for misconfigurations
trivy config ./Dockerfile

# Output as JSON for CI integration
trivy image --format json --output trivy-report.json payment-api:latest

# Fail CI pipeline if HIGH or CRITICAL vulnerabilities found
trivy image --exit-code 1 --severity HIGH,CRITICAL payment-api:latest
```

**Q10. How do you integrate image scanning into a CI/CD pipeline to block deployments with critical vulnerabilities?**
A: The pipeline must: scan after build, evaluate findings against policy, block deployment on policy violation, and report results for visibility.

```yaml
# GitHub Actions workflow with Trivy scanning
name: Build, Scan, and Deploy

on:
  push:
    branches: [main]

env:
  ECR_REGISTRY: 123456789.dkr.ecr.ap-south-1.amazonaws.com
  ECR_REPOSITORY: payment-api

jobs:
  build-and-scan:
    runs-on: ubuntu-latest
    permissions:
      id-token: write      # OIDC for AWS
      contents: read
      security-events: write  # for uploading SARIF to GitHub Security tab

    steps:
      - uses: actions/checkout@v4

      - name: Build Docker image
        run: |
          docker build \
            --tag $ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }} \
            --tag $ECR_REGISTRY/$ECR_REPOSITORY:latest \
            .

      # Step 1: Scan for vulnerabilities
      - name: Trivy vulnerability scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref:     ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
          format:        sarif
          output:        trivy-results.sarif
          severity:      CRITICAL,HIGH
          exit-code:     1          # fail the pipeline on HIGH or CRITICAL findings
          ignore-unfixed: true      # ignore CVEs that have no fix available yet

      # Step 2: Upload results to GitHub Security tab (even if scan fails)
      - name: Upload Trivy results to GitHub Security
        if: always()               # run even if Trivy step failed
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: trivy-results.sarif

      # Step 3: Secret scanning
      - name: Trivy secret scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref:  ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
          scanners:   secret
          exit-code:  1          # fail pipeline if any secrets found in image
          format:     table

      # Step 4: Dockerfile configuration check
      - name: Trivy config scan
        uses: aquasecurity/trivy-action@master
        with:
          scan-type:  config
          scan-ref:   ./Dockerfile
          exit-code:  1
          severity:   HIGH,CRITICAL

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123:role/github-actions-deploy
          aws-region:     ap-south-1

        run: |
          aws ecr get-login-password --region ap-south-1 | \
            docker login --username AWS --password-stdin $ECR_REGISTRY
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }}
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:latest

      - name: Deploy to ECS
        run: |
          # ... ECS deployment steps (only reached if all scans passed)
```

**Handling vulnerability exceptions:**
Not every CVE requires immediate blocking — some have no fix, some are in code paths you don't use, some have been assessed and accepted as low risk. The `.trivyignore` file documents accepted exceptions:

```
CVE-2023-5678
```


**Q11. What is a Software Bill of Materials (SBOM) and why is it becoming a compliance requirement?**
A: An SBOM (Software Bill of Materials) is a formal, machine-readable inventory of every software component in an artifact — OS packages, language packages, frameworks, libraries, and their versions. It is the software equivalent of an ingredients list on food packaging.

**Why SBOMs matter:**
When a new critical vulnerability is disclosed (e.g., Log4Shell in December 2021), every organization needs to answer: "which of our running services contain Log4j?" Without an SBOM, this requires re-scanning every image in production — potentially thousands of images across dozens of registries. With an SBOM, you query the inventory: "which SBOMs contain log4j-core between version 2.0 and 2.14?"

**US Executive Order 14028 (2021)** mandates SBOM generation for software sold to the US federal government. The CISA (Cybersecurity and Infrastructure Security Agency) publishes minimum elements for SBOMs. Financial services regulators are beginning to follow.

**Generating SBOMs:**
```bash
# Generate SBOM using Syft (open source, by Anchore)
syft payment-api:latest -o spdx-json > payment-api-sbom.spdx.json
syft payment-api:latest -o cyclonedx-json > payment-api-sbom.cyclonedx.json

# SPDX and CycloneDX are the two standard SBOM formats
# CycloneDX: OWASP standard; machine-readable; widely supported
# SPDX: Linux Foundation standard; also widely supported; original format

# Trivy can generate SBOMs:
trivy image --format cyclonedx payment-api:latest > sbom.cyclonedx.json

# Scan an existing SBOM against current vulnerability databases:
grype sbom:./sbom.cyclonedx.json
```

**SBOM in the CI/CD pipeline:**
```yaml
- name: Generate SBOM
  run: |
    syft $ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }} \
      -o cyclonedx-json \
      > payment-api-${{ github.sha }}.cyclonedx.json

- name: Attach SBOM to ECR image
  run: |
    # Store SBOM as an OCI artifact alongside the image
    aws ecr put-image \
      --repository-name $ECR_REPOSITORY \
      --image-manifest-media-type "application/vnd.cyclonedx+json" \
      --image-manifest "$(cat payment-api-${{ github.sha }}.cyclonedx.json)"

- name: Upload SBOM to S3 for auditability
  run: |
    aws s3 cp payment-api-${{ github.sha }}.cyclonedx.json \
      s3://fintech-sboms/payment-api/${{ github.sha }}.cyclonedx.json
```

## Section 5: Dockerfile Security Best Practices

**Q12. What are the Dockerfile-level security best practices and what does each prevent?**
A:

**Use minimal base images:**
```dockerfile
# Bad: full Ubuntu with hundreds of packages, many with CVEs
FROM ubuntu:22.04

# Better: Debian slim (smaller, fewer packages)
FROM node:20-slim

# Best: Alpine (musl libc, minimal packages, ~5MB)
FROM node:20-alpine

# Distroless (Google): contains only the runtime, no shell, no package manager
FROM gcr.io/distroless/nodejs20-debian12
# Advantage: no shell means no interactive access even if container is compromised
# Disadvantage: harder to debug (no bash, no apt, no curl)
```

Fewer packages = smaller attack surface. Alpine images typically have 3–5× fewer CVEs than equivalent Debian images for the same application.

**Pin exact versions — never use `latest`:**
```dockerfile
# Bad: unpredictable; "latest" changes with every registry push
FROM node:latest

# Bad: minor version may change
FROM node:20

# Good: exact patch version; reproducible builds
FROM node:20.9.0-alpine3.18

# Better: pin by digest (immune to tag mutation)
FROM node:20.9.0-alpine3.18@sha256:a0b5c8d7e6f2...
# Image digest is the SHA256 hash of the image manifest — immutable
# Even if the registry is compromised, the digest can't be spoofed
```

**Never put secrets in ENV or ARG:**
```dockerfile
# CRITICAL BAD: visible in `docker inspect`, in image history, in any layer
ENV API_KEY=sk-live-xxxxxxxxxxxx
ARG DB_PASSWORD=secret

# The history is not cleanable:
docker history payment-api:latest
# ... RUN /bin/sh -c #(nop) ENV API_KEY=sk-live-xxxxxxxxxxxx

# Correct: pass secrets at runtime, not build time
# At runtime: docker run -e API_KEY=... (from environment, not image)
# At runtime: Docker secrets (Swarm) or Kubernetes Secrets
# At runtime: Fetch from AWS Secrets Manager at startup
```

**Multi-stage builds to minimize final image:**
```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                    # includes devDependencies for build
COPY . .
RUN npm run build
RUN npm prune --production    # remove devDependencies after build

FROM node:20-alpine AS production
WORKDIR /app
# Copy only the production output — none of the build tools, test files, or devDeps
COPY --from=builder --chown=node:node /app/node_modules ./node_modules
COPY --from=builder --chown=node:node /app/dist         ./dist
# typescript compiler, @types/*, jest, eslint — none of these are in the final image
# Surface area reduced; CVE exposure reduced
USER node
CMD ["node", "dist/main.js"]
```

**Use `.dockerignore` to prevent secrets from being copied:**
```dockerignore
# .dockerignore — prevent accidental inclusion of sensitive files
.env
.env.local
.env.production
.env.*
*.pem
*.key
id_rsa
id_rsa.pub
.ssh/
.aws/
secrets/
node_modules/     # don't copy host node_modules; reinstall inside container
.git/             # git history may contain committed secrets
coverage/
*.test.ts
*.spec.ts
Dockerfile*
docker-compose*.yml
.dockerignore
README.md
```

Without `.dockerignore`, `COPY . .` copies the entire build context including `.env` files, private keys, and the git repository (which may contain secrets in its history).

**Avoid `ADD` for local files — use `COPY`:**
```dockerfile
# Bad: ADD can fetch remote URLs and auto-extract archives
ADD https://example.com/setup.sh /setup.sh   # downloads from internet during build
ADD my-app.tar.gz /app/                       # auto-extracts — may have path traversal

# Good: COPY only copies local files, nothing more
COPY my-app/ /app/
```

**One process per container, avoid running multiple services:**
```dockerfile
# Bad: running nginx + node + cron in one container (supervisord pattern)
RUN apt-get install -y supervisor nginx
COPY supervisord.conf /etc/supervisor/conf.d/
CMD ["/usr/bin/supervisord"]

# Good: separate containers per service
# nginx in one container, node in another
# If the node process crashes: only that container restarts; nginx keeps serving
```

## Section 6: Runtime Security and Seccomp

**Q13. What is seccomp and how does Docker use it to restrict container system calls?**
A: Seccomp (Secure Computing mode) is a Linux kernel feature that restricts which system calls a process can make. Docker applies a default seccomp profile to every container — a whitelist of ~300 of the ~400+ Linux system calls. Calls not on the whitelist cause the kernel to kill the process with `SIGSYS`.

**Why system call restriction matters:**
Container escapes and kernel exploits typically exploit specific system calls that should not be needed by application code — `mount`, `ptrace`, `kexec_load`, `bpf`, `clone3` (for user namespace manipulation). Blocking these calls at the kernel level means a container process cannot make them even if it has a bug that would otherwise allow it.

**Docker's default seccomp profile blocks:**
```
kexec_load       load a new kernel (obvious privilege escalation)
mount            mount filesystems
umount2          unmount filesystems
syslog           read kernel message buffer
reboot           reboot the system
swapon/swapoff   manage swap
clone (restricted) with CLONE_NEWUSER flag (user namespace creation)
unshare (restricted)
ptrace           debugging other processes
perf_event_open  performance counters (kernel exploit vector)
...and many more
```

**Applying custom seccomp profiles:**
```bash
# Use the default seccomp profile (applied automatically)
docker run payment-api:latest   # default seccomp is applied

# Disable seccomp (never in production)
docker run --security-opt seccomp=unconfined payment-api:latest

# Apply a custom profile
docker run --security-opt seccomp=./payment-api-seccomp.json payment-api:latest
```

**Custom seccomp profile (more restrictive than default):**
```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": [
        "accept4", "bind", "connect", "socket",   // networking
        "read", "write", "open", "openat",         // file I/O
        "close", "fstat", "lstat", "stat",
        "epoll_wait", "epoll_ctl", "epoll_create1",
        "futex", "nanosleep",                      // synchronization
        "exit", "exit_group",                      // process termination
        "getpid", "getuid", "getgid",              // identity
        "mmap", "mprotect", "munmap",              // memory
        "brk",
        "clone",                                   // thread creation (not user ns)
        "clone3"
      ],
      "action": "SCMP_ACT_ALLOW"
    }
  ]
}
```

A minimal seccomp profile for a Node.js HTTP server needs far fewer syscalls than Docker's default 300. Generating one from first principles: run the container with `strace` to record all syscalls made during normal operation, then whitelist exactly those.

**Q14. How do you build a complete security hardening checklist for a production container?**
A:

```dockerfile
# ─── Dockerfile security checklist ─────────────────────────────────────────

# ✅ Pinned, minimal base image
FROM node:20.9.0-alpine3.18@sha256:<digest>

# ✅ No secrets in ENV or ARG
# (secrets come from runtime environment injection or Secrets Manager)

# ✅ Install only what's needed; clean up in same RUN layer
RUN apk add --no-cache dumb-init \
 && apk upgrade  # ← upgrade base image packages at build time to reduce CVEs

# ✅ Non-root user created explicitly
RUN addgroup --system --gid 1001 nodejs \
 && adduser  --system --uid 1001 --ingroup nodejs --no-create-home nestjs

WORKDIR /app

# ✅ Application files copied with correct ownership (not chown after copy)
COPY --chown=nestjs:nodejs package*.json ./
RUN npm ci --only=production

COPY --from=builder --chown=nestjs:nodejs /app/dist ./dist

# ✅ No unnecessary packages or tools in final image

# ✅ Switch to non-root user before CMD
USER nestjs

EXPOSE 3000

# ✅ HEALTHCHECK defined
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
  CMD wget -q --spider http://localhost:3000/health || exit 1

# ✅ dumb-init for signal handling
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]
```

```yaml
# ─── Runtime security checklist (docker-compose.yml) ─────────────────────

services:
  payment-api:
    image: payment-api:20.9.0-sha256abc

    # ✅ Read-only root filesystem
    read_only: true

    # ✅ Writable tmpfs only where needed
    tmpfs:
      - /tmp:size=64m,mode=1777
      - /run:size=8m,uid=1001

    # ✅ Drop all capabilities, add back only what's needed
    cap_drop:
      - ALL
    cap_add: []         # Node.js on port 3000 needs zero capabilities

    # ✅ Prevent privilege escalation
    security_opt:
      - no-new-privileges:true
      - seccomp:./payment-api-seccomp.json   # custom minimal seccomp profile

    # ✅ No privileged mode (ever)
    # privileged: false  ← this is the default; never set to true

    # ✅ Resource limits (prevent resource exhaustion attacks)
    deploy:
      resources:
        limits:
          cpus:   "1.0"
          memory: "512M"
        reservations:
          cpus:   "0.25"
          memory: "128M"

    # ✅ Non-root user confirmed at runtime (belt-and-suspenders)
    user: "1001:1001"

    # ✅ Network isolation
    networks:
      - backend          # not on dmz or database directly

    # ✅ No Docker socket mounted
    # volumes: []        # if volumes are needed, use named volumes; never /var/run/docker.sock

    # ✅ Health check for orchestrator restarts
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost:3000/health"]
      interval: 30s
      timeout:  5s
      retries:  3
      start_period: 60s
```

```bash

docker push payment-api:$COMMIT_SHA

# ✅ ECR lifecycle policy to clean old images
# ✅ ECR Enhanced Scanning enabled for ongoing CVE monitoring
```

## Section 7: Scenario / System Design Style Questions

**Q15. "A security audit finds that all your production containers are running as root. You have 15 microservices. Design a migration plan."**
A:

```
Risk assessment first — prioritize by blast radius:

Priority 1 (highest risk): services with external network exposure
  - API gateway, public-facing APIs
  - Any service that processes untrusted user input
  - Services with internet-accessible ports

Priority 2: services with database or payment gateway access
  - Services that can read/write payment data
  - Services with privileged IAM roles

Priority 3: internal services with limited external input
  - Reporting services, background jobs, cron tasks

Migration approach per service:

Phase 1: Inventory (Week 1)
  For each service, determine:
    What UID does the container run as?
      docker inspect <container> --format '{{.Config.User}}'
      # If empty or "root" → needs migration

    What does it write to the filesystem?
      Run with inotifywait to capture write locations

    What ports does it bind?
      If < 1024: needs NET_BIND_SERVICE cap or port change

    Does it use any setuid binaries?
      docker run <image> find / -perm /4000 2>/dev/null

Phase 2: Fix Dockerfiles (Weeks 2-4, highest priority first)

  For each service:
  1. Add to Dockerfile (at end, after all COPY commands):
       RUN addgroup --system --gid 1001 appgroup \
        && adduser  --system --uid 1001 --ingroup appgroup --no-create-home appuser
       USER appuser

  2. Fix ownership of copied files:
       COPY --chown=appuser:appgroup . .

  3. Fix port if < 1024:
       Change from port 80 → 3000 (no capability needed)
       Update load balancer / nginx config to forward to new port

  4. Test locally:
       docker run --user 1001:1001 <image> → does it start?
       Run test suite → any file permission errors?

  5. Add tmpfs for any write needs identified in Phase 1

Phase 3: Add runtime hardening (alongside Dockerfile fix)
  In docker-compose.yml / ECS task definition / Kubernetes deployment:
    - Add: security_opt: [no-new-privileges:true]
    - Add: cap_drop: [ALL]
    - Add: read_only: true + tmpfs mounts
    - Add: user: "1001:1001" (belt-and-suspenders)

Phase 4: CI/CD gates (Week 5)
  Add to all pipelines:
    # Fail if container runs as root
    USER=$(docker inspect $IMAGE --format '{{.Config.User}}')
    if [ -z "$USER" ] || [ "$USER" = "root" ] || [ "$USER" = "0" ]; then
      echo "ERROR: Container runs as root. Fix before deploying."
      exit 1
    fi

  Add hadolint to lint Dockerfiles:
    hadolint --failure-threshold error Dockerfile
    # DL3002: Last USER should not be root ← fails if USER not set or is root

Phase 5: Verification (Week 6)
  For each migrated service, verify in staging:
    - Container starts and passes health check
    - All application functionality works
    - Cannot write to / (only to tmpfs mounts)
    - Security scanner shows no root process
    - Logs flow correctly (stdout → CloudWatch)

Rollback plan per service:
  Keep the old Dockerfile and image tagged with `-root` suffix
  Feature flag: ECS service can be rolled back to previous task definition
  Test in staging for 1 week before production
  Migrate one service per week to limit blast radius of any migration issues

Communication:
  Notify on-call team before each service migration
  Document the new UID (1001) in team runbooks
  Update any monitoring that checks process ownership
```

**Q16. "Your image scanning CI gate is blocking a deployment because of a CVE in `libssl` that has no fix available yet. How do you handle this?"**
A:

```
Situation: CVE-YYYY-XXXXX in libssl3 3.0.7, severity: HIGH
           Fixed in: not yet released
           Your current image: uses libssl3 3.0.7 (from Alpine 3.18.4)

Step 1: Assess actual risk (is this CVE relevant to your use case?)

  Read the CVE description:
    "Vulnerability in X.509 certificate parsing. Exploitable when
     processing certificates received from untrusted sources."

  Questions to answer:
    Does your application process X.509 certificates from untrusted sources?
      → Payment API: no. We receive certs from payment gateways (trusted sources).
      → If yes: risk is real; cannot simply accept it

    Is the affected code path reachable from your application?
      → Your Node.js app calls libssl for TLS connections as a client.
         Client-side TLS cert handling may not use the vulnerable code path.
      → Check: does your app call OpenSSL's vulnerable X.509 parsing functions?

    What is the CVSS score and attack vector?
      → AV:N (network) AC:H (high complexity) → requires specific conditions
      → Exploitability is not trivial

Step 2: Determine if a workaround exists

  Can you upgrade the base image to one that has the fix?
    → Check: is there an Alpine 3.18.5 or Alpine 3.19 that fixes it?
      docker run alpine:3.19 apk info libssl3  # what version?
    → If a newer Alpine version has the fix: upgrade the base image

  Can you upgrade just the package without upgrading Alpine?
    → If the fix is backported:
      RUN apk update && apk upgrade libssl3   # get the patched version
    → If no backport: cannot fix without changing base image version

  Is distroless an option?
    → Distroless images have minimal packages; may not include libssl at all
      or may have a patched version
    → Tradeoff: distroless is harder to debug

Step 3: If no fix is available — document and accept

  Create a tracked exception:

  # .trivyignore
  # CVE-YYYY-XXXXX: libssl3 vulnerability in X.509 certificate parsing
  # Assessment: payment-api does not process certificates from untrusted sources.
  #             Vulnerable code path (X.509 cert parsing from external input) is not
  #             reached by this application's usage of TLS (client-only, to trusted gateways).
  # Risk: LOW for this specific application
  # Review date: check for fix availability in 30 days
  # Approved by: [security team lead]
  # JIRA ticket: SEC-1234
  # Date added: 2024-01-15
  CVE-YYYY-XXXXX

  Update pipeline to use the ignore file:
    trivy image --trivyignores .trivyignore \
                --exit-code 1 \
                --severity CRITICAL,HIGH \
                payment-api:latest

Step 4: Set a review schedule

  Create a JIRA/Linear ticket:
    Title: "Review CVE-YYYY-XXXXX exception in payment-api"
    Due: 30 days from today
    Action: check if fix is available in Alpine; upgrade if so; re-assess if not

  Configure ECR Enhanced Scanning or Snyk monitoring:
    When the fix becomes available (new Alpine package version), the scanner
    will detect that the CVE is now fixable and the `--ignore-unfixed: true` flag
    in the CI config will stop suppressing it → pipeline fails → team notified

  This creates a self-correcting system: unfixed CVEs are ignored until a fix
  is available; when a fix becomes available, the pipeline automatically breaks
  again, prompting the team to apply the fix.

Step 5: Compensating controls

  Document what other controls reduce the risk:
    - Network policy: payment-api only communicates with known endpoints
                      (not arbitrary untrusted sources)
    - WAF: blocks malformed certificate-bearing requests at the edge
    - Non-root user: reduces blast radius if exploit is achieved
    - Read-only filesystem: prevents persistence if exploit is achieved

  Compensating controls don't eliminate the CVE but reduce overall risk
  to an acceptable level while awaiting the fix.

What NOT to do:
  ❌ Disable vulnerability scanning entirely
  ❌ Set all CVE severities to ignored without per-CVE assessment
  ❌ Accept a CRITICAL severity CVE that has no compensating controls
  ❌ Forget to review — the ignored CVE must have a tracked review date
```

## Quick Reference

| Security control | What it prevents | How to apply |
|---|---|---|
| Non-root user (`USER`) | Root-level host access on escape | `USER 1001` in Dockerfile; `user: "1001:1001"` in Compose |
| `no-new-privileges` | setuid binary privilege escalation | `security_opt: [no-new-privileges:true]` |
| `cap_drop: ALL` | Capability-based attacks | `cap_drop: [ALL]` + `cap_add: []` in Compose |
| `read_only: true` | Payload persistence, binary tampering | `read_only: true` + tmpfs for write needs |
| Minimal base image | Large CVE attack surface | `node:20-alpine` not `node:20` |
| Pinned image digest | Supply chain attacks via tag mutation | `FROM image@sha256:<digest>` |
| No secrets in ENV | Credential exposure in `docker inspect` | Runtime injection or Secrets Manager |
| `.dockerignore` | `.env` files copied into image | Add `.env*`, `.ssh/`, `*.pem` to `.dockerignore` |
| Multi-stage build | Dev tools and CVEs in final image | Builder stage for build; minimal stage for runtime |
| Image scanning (Trivy) | Known CVE packages | `trivy image --exit-code 1 --severity HIGH,CRITICAL` |
| Secret scanning | Embedded credentials in layers | `trivy image --scanners secret` |
| SBOM generation | Unknown component inventory | `syft image -o cyclonedx-json > sbom.json` |
| Seccomp profile | Kernel syscall exploitation | `security_opt: [seccomp:./profile.json]` |
| Resource limits | DoS from CPU/memory exhaustion | `deploy.resources.limits` in Compose |

| Dockerfile anti-pattern | Risk | Fix |
|---|---|---|
| `FROM node:latest` | Unpredictable; CVEs | Pin to exact version + digest |
| `ENV API_KEY=secret` | Credential exposure | Runtime injection |
| No `USER` instruction | Runs as root | Add `USER 1001` |
| `COPY . .` without `.dockerignore` | Copies `.env`, keys | Add `.dockerignore` |
| `ADD https://...` | Remote code in build | Use `COPY`; download separately |
| Single-stage build | Large image; dev deps | Multi-stage: builder + production |
| `RUN apt-get install ...` (no cleanup) | Layer bloat; stale package cache | `apt-get install -y pkg && rm -rf /var/lib/apt/lists/*` |

## The Core Mental Model

```
Container security = reduce attack surface × reduce blast radius

Attack surface reduction:
  Minimal base image → fewer packages → fewer CVE-bearing components
  Multi-stage build  → no dev tools, compilers, or test frameworks in production
  .dockerignore      → no secrets accidentally included in the image
  Pinned digests     → immune to supply chain attacks via tag mutation
  Image scanning     → catch known CVEs before deployment; block on HIGH/CRITICAL

Blast radius reduction:
  Non-root user      → escape lands as UID 1001, not UID 0 (root)
  Read-only filesystem → cannot write payloads, modify binaries, or persist
  cap_drop: ALL      → cannot exploit capability-based attack vectors
  no-new-privileges  → setuid binaries are inert; su/sudo cannot escalate
  Seccomp profile    → cannot call sensitive syscalls (mount, ptrace, kexec_load)
  Resource limits    → resource exhaustion attacks are bounded

The defense-in-depth stack (each layer independent):
  Layer 1: Image scanning → no known vulnerable packages reach production
  Layer 2: Non-root user  → if compromised, not root on the host
  Layer 3: Read-only fs   → cannot persist or tamper with binaries
  Layer 4: cap_drop:ALL  → cannot exploit kernel capabilities
  Layer 5: Seccomp       → cannot make dangerous kernel syscalls
  Layer 6: Network isolation → cannot reach unintended services even if compromised
  Layer 7: no-new-privileges → setuid escalation is blocked

None of these alone is sufficient:
  Scanner misses zero-days; non-root doesn't prevent in-memory attacks;
  read-only doesn't prevent network attacks; caps don't prevent CVE exploitation.
  Together: an attacker who defeats one layer still faces the others.

The three scanning imperatives:
  1. Scan on build (in CI): catch CVEs before they enter production
  2. Block on CRITICAL/HIGH (with exceptions documented): CVEs have a hard stop
  3. Scan continuously in registry (ECR Enhanced / Snyk): catch new CVEs in
     images already deployed — a package with no CVE today may have one tomorrow

SBOM = the ingredient list for incident response:
  New critical CVE announced → query SBOM inventory → "which images contain this?"
  Without SBOM: re-scan all images (slow, may miss running containers)
  With SBOM: instant answer; targeted remediation
```

---

**Tip for the interview:** Docker security questions at 5 YOE almost always escalate to one of three places: (1) the non-root + read-only + `no-new-privileges` trinity — being able to explain that non-root reduces blast radius (not attack probability), that read-only filesystem prevents payload persistence, and that `no-new-privileges` makes the non-root guarantee meaningful by blocking setuid escalation (the common way attackers escape from non-root to root within a container) shows that you understand these as a coherent layered model rather than independent checkboxes; (2) `COPY --chown` vs `RUN chown` — knowing that `RUN chown -R user:group /app` creates a new image layer that doubles the storage of the affected files (both the root-owned original layer and the re-owned layer are stored) while `COPY --chown=user:group` achieves the same result in one layer with no duplication is the kind of build-efficiency nuance that signals you have operated containers at scale where image size matters; (3) handling unfixed CVEs — knowing that the correct response is not "disable scanning" but rather: assess exploitability for your specific code path, document the exception in `.trivyignore` with a review date and approver, configure `--ignore-unfixed: true` for the pipeline, and set up continuous re-scanning to automatically re-alert when the fix becomes available, is the security program maturity that separates someone who has built a real security pipeline from someone who has only added a scanning step.
