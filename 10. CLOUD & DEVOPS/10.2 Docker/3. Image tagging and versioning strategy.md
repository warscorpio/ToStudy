# Container Image Tagging and Versioning Strategy — Interview Q&A (5 YOE Level)

---

## Section 1: Why Image Tagging Strategy Matters

**Q1. What breaks when teams use only the `latest` tag in production, and what are the specific failure modes?**
A: The `latest` tag is a mutable pointer — it moves every time a new image is pushed. No contract exists between what `latest` meant yesterday and what it means today. In production this creates a class of failures that are extremely difficult to diagnose because the deployed artifact changes silently.

**Failure mode 1 — Silent drift across instances:**
```
Deployment: all 10 ASG instances start with latest = v1.4.2 image
Auto Scaling event at 03:00: one instance terminated; replacement launched
At 03:00 the CI pipeline has pushed v1.4.3 (bug fix for a minor issue)
latest now resolves to v1.4.3

Result:
  9 instances: running v1.4.2
  1 instance:  running v1.4.3 (newer code with different behaviour)

ALB routes 10% of traffic to the v1.4.3 instance.
If v1.4.3 has a schema migration dependency not yet applied:
  → 10% of requests error; P99 latency spikes; engineers cannot reproduce
    because their test instance runs v1.4.2.

The fleet is never homogeneous again until the next deliberate deployment.
```

**Failure mode 2 — Rollback is not rollback:**
```
Incident: v1.4.3 deployment causes payment failures.
Engineer runs: kubectl rollout undo deployment/payments-api
Kubernetes sets the deployment back to the previous ReplicaSet spec.
The previous spec contains: image: payments-api:latest

latest still resolves to v1.4.3 (the broken image).
The "rollback" re-deploys the broken image.
The incident continues.

With immutable tags:
  Rollback spec contains: image: payments-api:1.4.2-abc1234
  Kubernetes pulls exactly that image.
  Rollback is deterministic and instant.
```

**Failure mode 3 — Build cache invalidation on every pull:**
```
Docker layer caching relies on the image digest, not the tag.
If latest changes between builds, every FROM payments-api:latest in a
dependent Dockerfile invalidates the layer cache — even if the image
content is the same as the last build.
Build times increase; the cache provides no benefit.
```

**Failure mode 4 — Audit and compliance gaps:**
```
PCI-DSS Requirement 10.2.7: log all access to system components.
SOC2 CC6.1: logical access controls include knowing what is running.
Security audit question: "What exact code was running in your payment
service on January 14th at 14:30 IST?"

With latest: no answer. latest at that moment is unknowable in retrospect.
With immutable tags (SHA-256 digest + semantic tag): exact image digest
retrievable from CloudWatch Logs (ECS task definition) or kubectl describe pod.
```

**The root cause:**
```
latest is not a version — it is a floating alias.
Treating it as a version violates the fundamental contract of a deployment:
  "Deploy exactly this artifact to these instances."
latest cannot satisfy this contract because "exactly this artifact" changes
as soon as the next build runs.

Rule: latest is acceptable for local development convenience.
      latest must never appear in a production deployment manifest, ECS task
      definition, Helm values file, or Terraform resource definition.
```

## Section 2: Tagging Strategies

**Q2. What are the canonical image tagging strategies and when do you use each?**
A: Five strategies are in common use, each encoding different information in the tag. Production systems combine two or three strategies to satisfy different consumers of the image.

**Strategy 1 — Semantic Version (SemVer):**
```
Format: MAJOR.MINOR.PATCH
Examples:
  payments-api:1.0.0
  payments-api:1.4.2
  payments-api:2.0.0-rc.1

MAJOR: incompatible API change (breaking change for clients)
MINOR: new backward-compatible feature
PATCH: backward-compatible bug fix

Multiple tags per release (floating aliases):
  payments-api:1.4.2   ← exact; immutable; never changes
  payments-api:1.4     ← moves forward with each patch release
  payments-api:1       ← moves forward with each minor release
  payments-api:latest  ← moves forward with each major release (do not use)

Who uses which tag:
  Production deployments: always pin to 1.4.2 (exact patch version)
  Automated dependency update bots (Renovate, Dependabot): follow 1.4 (minor)
  Development environments: follow 1 (any stable in this major)

Advantage: human-readable; communicates change significance; integrates with
           changelogs and release notes
Limitation: requires disciplined versioning (every build must produce a version);
            does not encode the git commit (cannot trace image back to code without
            a separate lookup)
```

**Strategy 2 — Git Commit SHA:**
```
Format: first 7–12 characters of the git commit hash (short SHA)
        or full 40-character SHA for maximum uniqueness
Examples:
  payments-api:abc1234
  payments-api:abc1234def56

Properties:
  Immutable: a commit SHA is permanent; it never refers to a different commit
  Traceable: given the image tag, git log abc1234 shows the exact code
  Automatic: CI generates this without human decision (no version bump required)
  Non-sequential: tells you nothing about ordering or change significance

Who uses this tag:
  Internal deployment systems (Kubernetes deployment manifests, ECS task definitions)
  Audit trails (what code was running?)
  Rollback tooling (roll back to the SHA before the incident)

Combination pattern (most common):
  payments-api:1.4.2-abc1234
  Encodes both semantic version AND git commit
  Human-readable (1.4.2) + machine-traceable (abc1234)
  This is the tag applied to production deployments
```

**Strategy 3 — Git Branch + SHA:**
```
Format: branch-name-shortsha
Examples:
  payments-api:main-abc1234
  payments-api:feature-kyc-validation-def5678
  payments-api:release-1.4-ghi9012

Use: non-production environments
  main-abc1234: latest merged code; deploy to staging
  feature-kyc-validation-def5678: feature branch build; deploy to feature environment
  release-1.4-ghi9012: release branch build; deploy to UAT

Policy: branch-tagged images are never deployed to production
        only semver or commit SHA images go to production
        branch tags are mutable (main-abc1234 becomes main-def5678 on next merge)
        acceptable for ephemeral environments; unacceptable for production
```

**Strategy 4 — Timestamp:**
```
Format: YYYYMMDD-HHMMSS or ISO 8601
Examples:
  payments-api:20240115-143022
  payments-api:2024-01-15T14:30:22Z

Advantage: chronological sort in registries; immediate answer to "which is newer"
Limitation: no traceability (cannot go from timestamp to git commit without a lookup)
            no semantic meaning (is this a breaking change or a typo fix?)
            timezone ambiguity (UTC required; local time causes ordering bugs)

Use: log analysis tags, nightly build archives
     Combined: payments-api:1.4.2-abc1234-20240115 (full context)
     Not used in isolation for production deployments
```

**Strategy 5 — Environment Tags:**
```
Format: environment name
Examples:
  payments-api:prod
  payments-api:staging
  payments-api:uat

Properties:
  Mutable: prod tag moves to each production release
  Readable: CD system checks "what is currently deployed to prod"
  Dangerous: if confused with immutable tags; promotes mutable-tag anti-pattern

Correct use: read-only; populated by CD pipeline after deployment succeeds
  CD flow: deploy 1.4.2-abc1234 to prod → if healthy: retag as prod
  Never deploy using the environment tag (same problem as latest)
  Use environment tag only to answer "what version is in prod right now?"
```

**Q3. What is the recommended tagging structure for a CI/CD pipeline serving multiple environments?**
A: The canonical production tagging structure applies multiple tags to each image build, serving different consumers without rebuilding the image.

**Complete tag set per build:**
```
Image: payments-api
Git SHA: abc1234
SemVer: 1.4.2
Branch: main
Build time: 2024-01-15T14:30:22Z
Build number: 847 (CI pipeline run number)

Tags applied to this single image (one push, multiple tags):

  1. payments-api:1.4.2-abc1234       ← production deployment tag
     Immutable; semantic version + commit; human + machine readable

  2. payments-api:1.4.2               ← semver exact; for release tooling
     Immutable for this patch version

  3. payments-api:1.4                 ← semver minor; moves per patch
     Mutable; for auto-update bots tracking the 1.4.x series

  4. payments-api:abc1234             ← commit SHA only; for traceability
     Immutable; for rollback tooling, audit queries

  5. payments-api:main-abc1234        ← branch + SHA; for staging auto-deploy
     Immutable for this commit; main- prefix signals non-production origin

  6. payments-api:latest              ← floating alias; local development only
     Mutable; never referenced in any deployment configuration

  7. payments-api:build-847           ← CI build number; for pipeline correlation
     Immutable; correlates image to CI logs, test results, artifact links

All 7 tags point to the same image digest (the same layers, the same bytes).
Tagging is a registry metadata operation — no rebuilding, no additional storage
beyond a metadata record.
```

**CI pipeline implementation (GitHub Actions + Amazon ECR):**
```yaml
# .github/workflows/build-push.yml
name: Build and Push Image

on:
  push:
    branches: [main, 'release/**']
    tags:     ['v*.*.*']

env:
  ECR_REGISTRY:   123456789012.dkr.ecr.ap-south-1.amazonaws.com
  ECR_REPOSITORY: payments-api
  AWS_REGION:     ap-south-1

jobs:
  build-push:
    runs-on: ubuntu-latest
    permissions:
      id-token: write  # OIDC for keyless AWS authentication
      contents: read

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # full history for git describe

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsEcrPush
          aws-region:     ${{ env.AWS_REGION }}

      - name: Login to ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Compute tags
        id: tags
        run: |
          SHA_SHORT=$(git rev-parse --short=8 HEAD)
          BRANCH=$(git rev-parse --abbrev-ref HEAD | sed 's|/|-|g')
          BUILD_NUM=${{ github.run_number }}
          TIMESTAMP=$(date -u +%Y%m%d-%H%M%S)
          REGISTRY="${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}"

          # Semver from git tag (if on a version tag)
          SEMVER=$(git describe --tags --exact-match 2>/dev/null || echo "")

          # Always-present tags
          TAGS="${REGISTRY}:${SHA_SHORT}"
          TAGS="${TAGS},${REGISTRY}:${BRANCH}-${SHA_SHORT}"
          TAGS="${TAGS},${REGISTRY}:build-${BUILD_NUM}"
          TAGS="${TAGS},${REGISTRY}:latest"

          # Semver tags (only on git version tags)
          if [[ -n "${SEMVER}" ]]; then
            VERSION="${SEMVER#v}"       # strip 'v' prefix: v1.4.2 → 1.4.2
            MINOR="${VERSION%.*}"       # 1.4.2 → 1.4
            MAJOR="${MINOR%.*}"         # 1.4   → 1

            TAGS="${TAGS},${REGISTRY}:${VERSION}"
            TAGS="${TAGS},${REGISTRY}:${VERSION}-${SHA_SHORT}"
            TAGS="${TAGS},${REGISTRY}:${MINOR}"
            TAGS="${TAGS},${REGISTRY}:${MAJOR}"
          fi

          echo "tags=${TAGS}" >> $GITHUB_OUTPUT
          echo "sha_short=${SHA_SHORT}" >> $GITHUB_OUTPUT
          echo "semver=${SEMVER}" >> $GITHUB_OUTPUT

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context:     .
          file:        ./Dockerfile
          push:        true
          tags:        ${{ steps.tags.outputs.tags }}
          cache-from:  type=gha
          cache-to:    type=gha,mode=max
          # Embed build metadata in image labels
          labels: |
            org.opencontainers.image.created=${{ github.event.head_commit.timestamp }}
            org.opencontainers.image.revision=${{ github.sha }}
            org.opencontainers.image.source=${{ github.repositoryUrl }}
            org.opencontainers.image.version=${{ steps.tags.outputs.semver }}
            com.fintech.git-sha=${{ steps.tags.outputs.sha_short }}
            com.fintech.build-number=${{ github.run_number }}
            com.fintech.pipeline-url=${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

## Section 3: Image Digests and Immutability

**Q4. What is the difference between an image tag and an image digest, and why do production deployments use digests?**
A: A tag is a mutable human-readable pointer. A digest is the immutable SHA-256 hash of the image manifest — it is computed from the image content and changes if any layer or metadata changes. Two identical images always produce the same digest; any change to the image, however small, produces a completely different digest.

**Tag vs digest mechanics:**
```
Tag (mutable pointer):
  docker pull payments-api:1.4.2
  → Registry looks up the tag "1.4.2"
  → Returns whichever image the tag currently points to
  → If someone retags: docker tag new-image payments-api:1.4.2
     the next pull gets the new image, not the original
  → You cannot know if you got the same image as yesterday

Digest (immutable content address):
  docker pull payments-api@sha256:a3b4c5d6e7f8...
  → Registry fetches the image with exactly this digest
  → If the digest does not exist: pull fails (no silent substitution)
  → SHA-256 collision is computationally infeasible:
     if the digest matches, the content is byte-for-byte identical

Obtaining the digest:
  # After push, GitHub Actions build-push outputs the digest:
  docker buildx imagetools inspect payments-api:1.4.2 --format '{{.Manifest.Digest}}'
  → sha256:a3b4c5d6e7f8901234567890abcdef...

  # ECR returns the digest on push:
  aws ecr describe-images \
    --repository-name payments-api \
    --image-ids imageTag=1.4.2 \
    --query 'imageDetails[0].imageDigest'

  # Docker inspect on a pulled image:
  docker inspect payments-api:1.4.2 --format '{{index .RepoDigests 0}}'
  → 123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api@sha256:a3b4c5d6...
```

**Using digests in deployment manifests:**
```yaml
# Kubernetes deployment — production (digest-pinned)
spec:
  containers:
    - name: payments-api
      # Human-readable tag for context; digest for immutability
      image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api:1.4.2@sha256:a3b4c5d6e7f8...
      # When both tag and digest are specified:
      # Docker/Kubernetes use the digest; tag is purely documentation
      # If the registry serves a different image for that digest: pull fails (integrity check)
```

```json
// ECS Task Definition — production (digest-pinned)
{
  "containerDefinitions": [{
    "name": "payments-api",
    "image": "123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api@sha256:a3b4c5d6e7f8...",
    "essential": true
  }]
}
// ECS uses the digest directly; immune to tag mutation
```

**ECR image tag immutability (registry-level enforcement):**
```
AWS ECR feature: Image Tag Immutability

When enabled on a repository:
  aws ecr create-repository \
    --repository-name payments-api \
    --image-tag-mutability IMMUTABLE

  OR for existing repo:
  aws ecr put-image-tag-mutability \
    --repository-name payments-api \
    --image-tag-mutability IMMUTABLE

Effect:
  Pushing a tag that already exists → FAILS with ImageAlreadyExistsException
  Cannot overwrite payments-api:1.4.2 with a different image
  Enforces: one version = one image, permanently

Exception for mutable tags (latest, staging, environment tags):
  Create a separate ECR repository for mutable aliases:
    payments-api           → IMMUTABLE (versioned production images)
    payments-api-aliases   → MUTABLE   (latest, staging pointers)
  OR: accept that latest is mutable; never reference it in deployments

This is the single most important ECR configuration for production security.
A supply chain attack that replaces 1.4.2 with a backdoored image is
impossible when the repository is IMMUTABLE.
```

## Section 4: Multi-Architecture and Multi-Stage Builds

**Q5. How do you tag and publish multi-architecture images, and why does this matter for AWS Graviton (ARM64) deployments?**
A: A multi-architecture image (manifest list / Docker manifest v2 list) is a single tag that resolves to different image variants depending on the CPU architecture of the pulling host. This is the mechanism that makes `docker pull ubuntu:22.04` work identically on x86_64 laptops, ARM64 Graviton EC2 instances, and Apple Silicon Macs.

**Why this matters for Graviton:**
```
AWS Graviton (m7g, r7g, c7g) instances use ARM64 (aarch64) architecture.
If you deploy an x86_64 image to a Graviton instance:
  Option A (default): Docker runs x86_64 binary via QEMU emulation
    → Works but: 20–40% performance penalty; QEMU overhead defeats Graviton savings
  Option B: Image simply refuses to run
    → exec format error: binary was compiled for a different architecture

For Graviton savings (20–40% better price/performance) to materialize:
  The container image must contain ARM64 binaries.
  Node.js binaries from the official node:18-alpine image are architecture-specific.
  Pull node:18-alpine on ARM64 → gets ARM64 binary automatically (if multi-arch).
  Pull payments-api:1.4.2 on ARM64 → must also get ARM64 binary (your image).
```

**Building and pushing a multi-architecture image:**
```yaml
# GitHub Actions: build for linux/amd64 AND linux/arm64 simultaneously
- name: Set up QEMU (for cross-compilation)
  uses: docker/setup-qemu-action@v3
  # QEMU enables building ARM64 images on x86_64 CI runners

- name: Set up Docker Buildx
  uses: docker/setup-buildx-action@v3
  # Buildx: Docker builder with multi-platform support

- name: Build and push multi-arch image
  uses: docker/build-push-action@v5
  with:
    context:   .
    platforms: linux/amd64,linux/arm64
    push:      true
    tags:      ${{ steps.tags.outputs.tags }}
    # Buildx builds both architectures and pushes a manifest list
    # The manifest list (index) is what the tag points to
    # docker pull payments-api:1.4.2 on amd64 → gets amd64 variant
    # docker pull payments-api:1.4.2 on arm64 → gets arm64 variant
    # Same tag; different image layers; selected automatically by the Docker daemon
```

**Manifest list structure (what the registry stores):**
```
payments-api:1.4.2 (manifest list / image index)
├── payments-api@sha256:amd64digest... (linux/amd64)
│     layers: [node:18-alpine amd64 layers] + [app layers compiled for amd64]
└── payments-api@sha256:arm64digest... (linux/arm64)
      layers: [node:18-alpine arm64 layers] + [app layers compiled for arm64]

The tag 1.4.2 points to the manifest list (sha256:indexdigest...)
The manifest list has its own digest (different from each architecture's digest)

Production deployment: pin to the manifest list digest
  → Docker resolves to the correct architecture variant automatically
  → Works on mixed fleets (some x86_64 for existing instances, some arm64 for new Graviton)

Inspecting:
  docker buildx imagetools inspect payments-api:1.4.2
  # Shows: manifest list with all platform variants and their individual digests
```

**Dockerfile multi-stage build for efficient multi-arch images:**
```dockerfile
# Dockerfile — multi-stage, multi-arch compatible
# syntax=docker/dockerfile:1

# Stage 1: dependency installation (cacheable layer)
FROM node:20-alpine AS deps
WORKDIR /app

# Copy only dependency files first (layer cache: only invalidated on dep changes)
COPY package.json package-lock.json ./
# npm ci: reproducible install from lockfile; fails if lockfile is out of sync
RUN npm ci --only=production && \
    npm cache clean --force

# Stage 2: build (TypeScript compilation, asset bundling)
FROM node:20-alpine AS builder
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci  # install ALL deps (including devDependencies for build)

COPY tsconfig*.json ./
COPY src/ ./src/
RUN npm run build  # tsc: compiles src/ → dist/

# Stage 3: production runtime (minimal image)
FROM node:20-alpine AS runtime

# Security: run as non-root user
RUN addgroup --system --gid 1001 nodejs && \
    adduser  --system --uid 1001 --ingroup nodejs nestjs

WORKDIR /app

# Copy production node_modules from deps stage (no devDependencies)
COPY --from=deps    --chown=nestjs:nodejs /app/node_modules ./node_modules
# Copy compiled output from builder stage (no TypeScript source)
COPY --from=builder --chown=nestjs:nodejs /app/dist         ./dist
COPY --chown=nestjs:nodejs package.json ./

USER nestjs

# Document the port (does not publish; docker run -p or ECS port mapping does that)
EXPOSE 3000

# Use exec form (not shell form): receives SIGTERM directly (graceful shutdown)
# Shell form: SIGTERM goes to shell wrapper, not Node.js process
CMD ["node", "dist/main.js"]

# OCI image labels (searchable metadata in registry)
ARG BUILD_DATE
ARG GIT_SHA
ARG VERSION
LABEL org.opencontainers.image.created="${BUILD_DATE}" \
      org.opencontainers.image.revision="${GIT_SHA}"   \
      org.opencontainers.image.version="${VERSION}"    \
      org.opencontainers.image.title="payments-api"   \
      org.opencontainers.image.vendor="Fintech Corp"
```

**Why exec form CMD matters for graceful shutdown:**
```
Shell form:   CMD node dist/main.js
  Process tree: /bin/sh -c "node dist/main.js"
                └── node dist/main.js (PID != 1)
  SIGTERM from Docker/Kubernetes → sent to PID 1 (/bin/sh)
  /bin/sh does NOT forward SIGTERM to child processes
  Node.js never receives SIGTERM → process killed with SIGKILL after timeout
  ECS/Kubernetes graceful shutdown: 30-second window wasted; connections dropped

Exec form:    CMD ["node", "dist/main.js"]
  Process tree: node dist/main.js (PID 1)
  SIGTERM from Docker/Kubernetes → sent to PID 1 (node directly)
  NestJS app.enableShutdownHooks() receives SIGTERM → graceful drain → clean exit
  Connections drained; DB connections closed; in-flight requests complete
```

## Section 5: Registry Management and Lifecycle Policies

**Q6. How do you manage ECR image lifecycle to prevent unbounded registry storage growth?**
A: Without lifecycle policies, an active CI/CD pipeline that builds on every commit generates thousands of images per month. Each image is stored indefinitely, and ECR charges $0.10/GB-month. A medium-sized NestJS image (200 MB compressed) across 100 builds/month = 20 GB/month = $2/month — and it compounds. After a year without cleanup: 240 GB = $24/month, and most images are never deployed.

**ECR lifecycle policy structure:**
```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Keep production semver releases indefinitely (no expiry)",
      "selection": {
        "tagStatus":     "tagged",
        "tagPrefixList": ["v", "1.", "2.", "3."],
        "countType":     "imageCountMoreThan",
        "countNumber":   9999
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 10,
      "description": "Keep last 10 images per feature branch",
      "selection": {
        "tagStatus":     "tagged",
        "tagPrefixList": ["feature-", "fix-", "chore-"],
        "countType":     "imageCountMoreThan",
        "countNumber":   10
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 20,
      "description": "Keep last 30 main branch builds (30 days of daily builds)",
      "selection": {
        "tagStatus":     "tagged",
        "tagPrefixList": ["main-"],
        "countType":     "imageCountMoreThan",
        "countNumber":   30
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 30,
      "description": "Expire untagged images after 7 days",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 7
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 40,
      "description": "Expire build-number and timestamp tags after 90 days",
      "selection": {
        "tagStatus":     "tagged",
        "tagPrefixList": ["build-", "20"],
        "countType":     "sinceImagePushed",
        "countUnit":     "days",
        "countNumber":   90
      },
      "action": { "type": "expire" }
    }
  ]
}
```

**Critical lifecycle policy rules:**
```
Rule priority: lower number = evaluated first; first matching rule wins.

Rule 1 (priority 1) — protect production releases:
  Must be the highest-priority rule (lowest number).
  Tags starting with 'v' or semver prefixes (1., 2.) are kept forever.
  Rationale: you must be able to roll back to any previously deployed version.
  Do not expire production images; storage cost is negligible vs rollback safety.

Untagged images:
  Docker layer pushes sometimes leave intermediate untagged images.
  Untagged images have no tag; they are not pullable by any tag (only by digest).
  If they are not referenced by any manifest list: they are orphaned.
  Expire after 7 days: short enough to save cost; long enough that in-progress
  builds are not deleted mid-push.

Feature branch images:
  Expire after N images per branch (not by time): prevents a dead branch from
  lingering forever; keeps the last N for debugging if needed.
  countNumber: 10 = last 10 builds per feature branch retained.

Lifecycle policy dry run (validate before applying):
  aws ecr get-lifecycle-policy-preview \
    --repository-name payments-api \
    --lifecycle-policy-text file://lifecycle-policy.json \
    --image-count-option COUNTED_IMAGES_RETURNED
  Shows which images WOULD be deleted without actually deleting them.
  Always run dry run before applying a new lifecycle policy.
```

**Q7. What is ECR image scanning and how do you integrate vulnerability scanning into the tagging workflow?**
A: ECR offers two scanning modes: Basic Scanning (CVE database scan on push) and Enhanced Scanning (continuous scanning via Amazon Inspector, re-scans when new CVEs are published for existing images). Both generate findings that can gate deployments.

**Scanning integration in CI/CD:**
```yaml
# GitHub Actions: scan image after push; fail if CRITICAL CVEs found
- name: Scan image for vulnerabilities
  id: scan
  run: |
    IMAGE_TAG="${{ steps.tags.outputs.sha_short }}"
    REPO="${{ env.ECR_REPOSITORY }}"

    # Wait for ECR scan to complete (Basic Scanning is asynchronous)
    echo "Waiting for ECR image scan..."
    aws ecr wait image-scan-complete \
      --repository-name "${REPO}" \
      --image-id imageTag="${IMAGE_TAG}" \
      --region ${{ env.AWS_REGION }}

    # Get scan findings
    FINDINGS=$(aws ecr describe-image-scan-findings \
      --repository-name "${REPO}" \
      --image-id imageTag="${IMAGE_TAG}" \
      --query 'imageScanFindings.findingSeverityCounts' \
      --output json)

    echo "Scan findings: ${FINDINGS}"

    # Fail if CRITICAL vulnerabilities found
    CRITICAL=$(echo "${FINDINGS}" | jq -r '.CRITICAL // 0')
    HIGH=$(echo "${FINDINGS}" | jq -r '.HIGH // 0')

    echo "critical=${CRITICAL}" >> $GITHUB_OUTPUT
    echo "high=${HIGH}" >> $GITHUB_OUTPUT

    if [[ "${CRITICAL}" -gt 0 ]]; then
      echo "::error::Image has ${CRITICAL} CRITICAL vulnerabilities. Deployment blocked."
      exit 1
    fi

    if [[ "${HIGH}" -gt 5 ]]; then
      echo "::warning::Image has ${HIGH} HIGH vulnerabilities. Review required."
      # Do not fail — HIGH threshold is a warning; CRITICAL is a hard block
    fi
```

**Tagging convention for scan-gated images:**
```
Without scan gate:
  Build → push payments-api:1.4.2-abc1234 → deploy to production
  If image has CRITICAL CVEs: production runs vulnerable code

With scan gate (scan before promoting to production tag):
  Build → push payments-api:1.4.2-abc1234-candidate (candidate tag)
  Scan → if CRITICAL: pipeline fails; no production tag applied
  Scan → if clean: retag as 1.4.2-abc1234 (production tag applied)
  Deploy from production tag

Alternatively: tag-based policy in ECR
  ECR lifecycle policy + EventBridge:
    On scan complete → Lambda checks findings → if clean: apply production tag
    → if findings: open Jira ticket + Slack alert; block deployment
```

## Section 6: Security and Supply Chain

**Q8. What is image signing and how does it prevent supply chain attacks on your container images?**
A: Image signing creates a cryptographic attestation that a specific image digest was produced by a known identity (your CI pipeline, your security team). A policy-enforcing admission controller (in Kubernetes) or registry policy (in ECR) rejects images that cannot present a valid signature. This prevents an attacker who gains write access to your registry from deploying a backdoored image.

**The supply chain attack without signing:**
```
Scenario:
  Attacker gains write access to ECR (via leaked AWS credentials, SSRF, etc.)
  Attacker overwrites payments-api:1.4.2 with a backdoored image
    (ECR image tag mutability must be MUTABLE for this to work — another reason
     to use IMMUTABLE tag mutability)
  With MUTABLE tags: possible (tag points to attacker's image)
  With IMMUTABLE tags: impossible (push rejected with ImageAlreadyExistsException)

  If IMMUTABLE is not set:
    Attacker pushes backdoored image with a new legitimate-looking tag
    Modifies ECS task definition or Kubernetes deployment to use new tag
    Deployment proceeds; backdoored code runs in production

Signing prevents this even if IMMUTABLE is not set:
  Attacker pushes backdoored image → no valid signature (they don't have the signing key)
  Admission controller checks signature → rejects the unsigned image → deployment blocked
```

**AWS Signer + ECR image signing:**
```bash
# 1. Create a signing profile in AWS Signer
aws signer put-signing-profile \
  --profile-name payments-api-signing-profile \
  --platform-id Notation-OCI-SHA384-ECDSA \
  --signature-validity-period 'value=12,type=MONTHS'

# 2. Sign the image after push (in CI pipeline)
# Using AWS Signer with Notation (CNCF container signing standard)
notation sign \
  --signer arn:aws:signer:ap-south-1:123456789012:/signing-profiles/payments-api-signing-profile \
  123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api:1.4.2-abc1234

# Signature is stored as a referrer artifact in ECR (alongside the image)
# The signature contains: image digest + signer identity + timestamp + AWS Signer chain

# 3. Verify a signature before deployment
notation verify \
  --trust-policy trust-policy.json \
  123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api:1.4.2-abc1234
# Returns 0 if signature is valid; non-zero if tampered or unsigned
```

**Cosign (open-source alternative, SLSA supply chain):**
```bash
# Keyless signing using GitHub Actions OIDC (Sigstore/Fulcio)
# No private key to manage; identity is the GitHub Actions OIDC token

- name: Install Cosign
  uses: sigstore/cosign-installer@v3

- name: Sign image (keyless, OIDC-based)
  env:
    COSIGN_EXPERIMENTAL: "true"  # keyless mode
  run: |
    cosign sign \
      --yes \
      ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}@${{ steps.build.outputs.digest }}
    # Signature published to Rekor transparency log (public, auditable)
    # Anyone can verify the signature was produced by github.com/your-org/payments-api CI
    # at exactly the commit SHA embedded in the OIDC token

# Verify (in CD pipeline before deployment):
- name: Verify image signature
  run: |
    cosign verify \
      --certificate-identity-regexp "https://github.com/your-org/payments-api" \
      --certificate-oidc-issuer   "https://token.actions.githubusercontent.com" \
      ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}@${{ steps.digest.outputs.digest }}
    # Fails if: no signature, signature by wrong identity, or tampering detected
```

**SBOM (Software Bill of Materials) attestation:**
```bash
# Generate SBOM and attach as attestation to the image
# SBOM lists every package and version in the image (compliance + CVE tracking)

- name: Generate SBOM with Syft
  uses: anchore/sbom-action@v0
  with:
    image: ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ steps.tags.outputs.sha_short }}
    output-file: sbom.spdx.json
    format: spdx-json

- name: Attach SBOM as cosign attestation
  run: |
    cosign attest \
      --yes \
      --predicate sbom.spdx.json \
      --type spdxjson \
      ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}@${{ steps.build.outputs.digest }}
    # SBOM stored in registry alongside the image
    # Auditors can retrieve the SBOM for any deployed image digest
    # Enables: "what packages were running in our payment service on January 14th?"
```

## Section 7: Promotion Flow and Environment Strategy

**Q9. How do images move through environments, and what is the image promotion pattern?**
A: Image promotion means taking an image that has passed validation in one environment and making it the candidate for the next environment — without rebuilding. The same image bytes (same digest) move through dev → staging → UAT → production, ensuring what was tested is what is deployed.

**The promotion anti-pattern (build per environment):**
```
Anti-pattern:
  Dev build:     npm run build → docker build → push payments-api:dev-abc1234
  Staging build: npm run build → docker build → push payments-api:staging-abc1234
  Prod build:    npm run build → docker build → push payments-api:prod-abc1234

Problems:
  Three builds of the same commit → three different image digests
  Non-deterministic build: npm install may resolve different patch versions
  A build that passes staging tests may differ from the prod build
  "Works in staging" may not actually be what was tested
  Build time wasted 3× per commit
```

**The promotion pattern (build once, promote):**
```
Build once (on every commit to main):
  docker build → push payments-api:abc1234 (commit SHA tag)
  Run automated tests against payments-api:abc1234

Promote to staging (after tests pass):
  CD pipeline adds tag: payments-api:staging (mutable; points to current staging image)
  Deploys payments-api:abc1234 to staging environment (using immutable tag)
  Human or automated validation runs

Promote to UAT (after staging passes):
  CD pipeline adds tag: payments-api:uat
  Deploys payments-api:abc1234 to UAT
  Business acceptance testing

Promote to production (after UAT sign-off):
  Tag the commit as a semver release: git tag v1.4.2
  CI pipeline re-tags: payments-api:abc1234 → payments-api:1.4.2
                       payments-api:abc1234 → payments-api:1.4.2-abc1234
                       payments-api:abc1234 → payments-api:1 (major alias)
                       payments-api:abc1234 → payments-api:1.4 (minor alias)
  CD pipeline deploys payments-api:1.4.2-abc1234 to production
  Applies environment alias: payments-api:prod → payments-api:1.4.2-abc1234

At every stage: same image bytes (same digest). Only the tags change.
ECR re-tag command (zero storage cost — only metadata operation):
  MANIFEST=$(aws ecr batch-get-image \
    --repository-name payments-api \
    --image-ids imageTag=abc1234 \
    --query 'images[0].imageManifest' \
    --output text)

  aws ecr put-image \
    --repository-name payments-api \
    --image-tag         1.4.2 \
    --image-manifest    "${MANIFEST}"
  # No new bytes stored; just a new tag pointing to the existing manifest
```

**Environment-specific configuration (not in the image):**
```
What goes IN the image (build-time, environment-agnostic):
  Compiled application code (dist/)
  Production node_modules (no devDependencies)
  Static assets
  Health check script
  Entrypoint / CMD

What goes OUTSIDE the image (runtime injection):
  Database host, port, credentials     → Secrets Manager / Parameter Store
  Redis endpoint, auth token           → Secrets Manager / Parameter Store
  Log level                            → ECS task definition environment variable
  Feature flags                        → Parameter Store / LaunchDarkly
  AWS region                           → ECS task definition / instance metadata
  Environment name (prod/staging)      → ECS task definition environment variable

The image is environment-agnostic. The same image:1.4.2-abc1234 runs in
staging (connected to staging RDS) and production (connected to prod RDS)
by injecting different Secrets Manager ARNs at runtime.
This is what makes image promotion safe: no environment-specific bytes in the image.
```

**Q10. How do you implement a rollback strategy using image tags?**
A: Rollback is the ability to revert a running deployment to a known-good previous version. With immutable image tags, rollback is deterministic: redeploy the previous immutable tag. Without them, rollback is undefined.

**Rollback implementation per deployment target:**

```bash
# ECS rollback — revert to previous task definition revision
# Each ECS deployment creates a new task definition revision pointing to the new image
# Rollback: activate the previous revision

CLUSTER="fintech-prod"
SERVICE="payments-api"

# Find the previous task definition revision
CURRENT_REVISION=$(aws ecs describe-services \
  --cluster "${CLUSTER}" --services "${SERVICE}" \
  --query 'services[0].taskDefinition' --output text)
# → arn:aws:ecs:...:task-definition/payments-api:47

PREVIOUS_REVISION=$(aws ecs describe-task-definition \
  --task-definition payments-api \
  --query 'taskDefinition.revision' --output text)
# Decrement revision number for rollback

ROLLBACK_REVISION=$((${PREVIOUS_REVISION} - 1))
# → payments-api:46 (the revision deployed before the broken one)

# Rollback: update service to previous revision
aws ecs update-service \
  --cluster "${CLUSTER}" \
  --service  "${SERVICE}" \
  --task-definition "payments-api:${ROLLBACK_REVISION}" \
  --force-new-deployment

# ECS performs rolling update from revision 47 → revision 46
# Blue-green if CodeDeploy; rolling by default
```

```bash
# Kubernetes rollback — kubectl rollout undo
# Each deployment update creates a new ReplicaSet; Kubernetes retains history

# Immediate rollback to previous ReplicaSet (default)
kubectl rollout undo deployment/payments-api -n production

# Rollback to a specific revision (view history first)
kubectl rollout history deployment/payments-api -n production
# REVISION  CHANGE-CAUSE
# 44        payments-api:1.4.0-abc0000
# 45        payments-api:1.4.1-def1111
# 46        payments-api:1.4.2-ghi2222  ← current (broken)

kubectl rollout undo deployment/payments-api \
  --to-revision=45 -n production
# Rolls back to payments-api:1.4.1-def1111 specifically

# Verify rollback succeeded
kubectl rollout status deployment/payments-api -n production
kubectl describe deployment payments-api -n production | grep Image:
# → Image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/payments-api:1.4.1-def1111@sha256:...
```

**Rollback runbook entry (production standard):**
```
Rollback decision criteria:
  Error rate > 5% above baseline for > 3 minutes after new deployment
  P99 latency > 2× baseline for > 5 minutes
  Any CRITICAL exception in payment processing (zero tolerance)
  On-call engineer judgment for ambiguous degradation

Rollback procedure:
  1. Notify #incidents Slack channel: "Rolling back payments-api to v1.4.1"
  2. Execute rollback command (ECS: update-service; K8s: rollout undo)
  3. Monitor: error rate should drop within 2 minutes of rollback completing
  4. Confirm: check Datadog/CloudWatch that P99 and error rate return to baseline
  5. Post-mortem: identify why v1.4.2 caused the regression
  6. Do NOT re-deploy the broken version without understanding and fixing the root cause

What makes rollback fast and safe:
  Immutable image tags: the rollback target image is guaranteed unchanged
  Pre-pulled images: ECS/Kubernetes may have the previous image cached locally
  Task definition history (ECS) / ReplicaSet history (K8s): rollback is one command
  No rebuilding: the previous image is already in ECR; no wait for CI
```

## The Core Mental Model

```
An image tag is a contract: "this tag always refers to this exact artifact."
  Mutable tags break the contract: latest today ≠ latest tomorrow.
  Immutable tags keep the contract: 1.4.2-abc1234 is the same bytes forever.
  The entire downstream system (rollback, audit, reproducibility) depends on
  this contract being unbreakable. ECR IMMUTABLE tag mutability enforces it at
  the registry level so no human error can violate it.

Build once, promote everywhere:
  Every rebuild introduces non-determinism (different npm resolve, different cache,
  different base image pulled mid-build).
  The image that passed your staging tests must be byte-for-byte identical to what
  runs in production. The same digest. Not "same code, fresh build." Same digest.
  Promotion = re-tagging an existing image (zero bytes transferred; pure metadata).
  Rebuild = a new artifact that has never been tested in the environment it is being deployed to.

The tag hierarchy serves different consumers:
  1.4.2-abc1234  → production deployment systems (immutable; human+machine readable)
  abc1234        → rollback tooling and audit queries (immutable; machine key)
  1.4.2          → release notes, changelogs, Helm chart versions (immutable; human key)
  1.4            → automated dependency update bots (mutable; tracks patch series)
  main-abc1234   → staging CD trigger (immutable; ephemeral; expires in 30 days)
  latest         → local developer convenience only (mutable; never in any manifest)
  All tags point to the same digest. Tags are aliases; the digest is the truth.

The exec form CMD is not a style choice — it is a correctness requirement:
  Shell form routes SIGTERM to /bin/sh, which does not forward to Node.js.
  Your graceful shutdown hook (app.enableShutdownHooks()) never fires.
  Every deployment/scale-in/restart is a hard kill after the timeout expires.
  30 seconds of in-flight requests dropped on every deployment.
  One line in the Dockerfile prevents this permanently.

The promotion gate order (and what each gate validates):
  Unit tests   → logic correctness (runs in < 5 min; no infra needed)
  CVE scan     → known vulnerabilities (automated; ECR Enhanced Scanning)
  Image sign   → provenance (signed by this repo's CI; not a foreign image)
  Integration  → runtime correctness against real dependencies
  Staging      → system-level correctness in a production-like environment
  UAT          → business correctness (product/QA sign-off)
  Canary       → production correctness under real traffic (10% for 5 minutes)
  Each gate eliminates a class of failure. Skipping a gate moves the failure
  to the next environment — where the cost of discovery is higher.

For PCI-DSS and SOC2 audit readiness:
  The auditor's question: "What exact code was running in your payment service
  on January 14th at 14:30 IST, and how do you know it wasn't modified?"
  The answer requires: immutable tag in ECS task definition + image digest in
  CloudTrail + cosign signature verifiable against Rekor transparency log +
  SBOM attestation showing every package in the image.
  Any missing component = incomplete answer = audit finding.
  The tagging strategy IS the audit trail infrastructure.
```

**Tip for the interview:** Image tagging questions at 5 YOE converge on three depth probes: (1) the `latest` failure modes in a distributed fleet — knowing that auto-scaling replacements pull whatever `latest` points to at launch time (not what was deployed initially), that this silently creates heterogeneous fleets with different code running on different instances, and that rollback to `latest` re-deploys the broken image because the tag still points to it, demonstrates you have actually operated a production system rather than just deployed to a single instance; (2) the tag vs digest distinction — knowing that a tag is a mutable pointer (it can be rewritten to point to a different image) while the SHA-256 digest is a content-addressed immutable identifier computed from the image bytes (a different image always produces a different digest, making tampering detectable), and that production Kubernetes and ECS manifests should pin to the digest (or at minimum an immutable-tagged registry) to make supply chain attacks impossible, shows infrastructure security maturity; (3) the build-once-promote pattern and why rebuilding per environment is a reliability anti-pattern — explaining that each rebuild introduces non-determinism through package resolution, layer cache misses, and base image updates, meaning "the same code built twice" produces two different artifacts with potentially different behaviors, and that the staging environment tests are meaningless if a fresh build is deployed to production (because the tested artifact is not what is running), demonstrates that you understand continuous delivery as a correctness property, not just a speed property. The fintech callout: for PCI-DSS compliance, immutable ECR tags + image signing (cosign/Notation) + SBOM attestations form the artifact provenance chain that answers the auditor's question — "what exact verified artifact was running in your payment processing environment on this date" — and the inability to answer this question is a compliance finding, not a best-practice gap.
