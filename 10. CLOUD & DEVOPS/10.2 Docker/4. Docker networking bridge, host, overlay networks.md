# Docker Networking: Bridge, Host, and Overlay Networks — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Docker Networking Exists

**Q1. What networking problem does Docker solve, and why can't containers just use the host network by default?**
A: A container is a process running on the host OS with namespace isolation — it has its own PID namespace, filesystem namespace, and importantly, its own network namespace. The network namespace gives the container the illusion of being a separate machine: its own network interfaces, its own IP address, its own routing table, and its own port space.

Without network namespaces, all containers on a host would compete for the same port space. Running two web servers, both wanting port 80, on the same host without isolation is impossible — the second `bind(80)` call fails because the port is already taken. Network namespaces make each container's port space independent: container A can bind port 80, and container B can also bind port 80 on the same host simultaneously, because each has its own isolated port space.

The problem this creates: isolated network namespaces can't talk to each other by default. If container A (IP: isolated) and container B (IP: isolated) both have their own network stacks with no connection between them, they're as unreachable from each other as two machines with no network cable. Docker's networking subsystem solves this by creating virtual network infrastructure — virtual bridges, virtual Ethernet pairs (veth pairs), network address translation (NAT) — that connects container network namespaces to each other and to the outside world in controlled, configurable ways.

The reason containers don't use the host network by default: isolation is the point. If every container directly used the host's network namespace, any two containers wanting the same port would conflict, a compromised container could sniff all host network traffic, and the abstraction of "this container is an independent service" collapses. The default bridge network provides isolation while still enabling connectivity.

**Q2. What is a veth pair and how does Docker use it to connect containers to bridges?**
A: A veth (virtual Ethernet) pair is a connected pair of virtual network interfaces — think of it as a virtual network cable with two ends. Anything written to one end of the pair immediately appears at the other end, and vice versa. The kernel creates veth pairs as a mechanism for bridging different network namespaces.

Docker uses veth pairs to connect container network namespaces to bridge networks:

```
Host network namespace                    Container network namespace
─────────────────────────────            ──────────────────────────────
docker0 bridge (172.17.0.1)              eth0 (172.17.0.2)
      │                                       │
      └── veth5a3b2c (host end) ←────────→ vethcontainer (container end,
                                              renamed to eth0 inside the container)
```

The mechanics:
1. Docker creates a veth pair: `veth5a3b2c` ↔ `vethcontainer`.
2. Docker moves `vethcontainer` into the container's network namespace (where it appears as `eth0`).
3. Docker attaches `veth5a3b2c` (the host end) to the `docker0` bridge.
4. Docker assigns an IP to the container's `eth0` (e.g., 172.17.0.2) from the bridge's subnet.

Now the container has a network interface (`eth0`) that is connected, via the veth pair, to the `docker0` bridge in the host namespace. The bridge can forward packets between multiple containers attached to it, and can route packets to the host's physical network interface for external connectivity.

```bash
# On the host, you can see the veth pairs:
ip link show | grep veth
# veth5a3b2c@if8: link/ether ... (the host end, attached to docker0)

# Inside the container:
docker exec <container> ip link show
# eth0@if9: link/ether ... (the container end; if9 references the peer's interface index)
```

## Section 2: Bridge Networks

**Q3. What is the default bridge network (`docker0`) and what are its properties?**
A: When Docker is installed, it creates a default bridge network called `bridge` (the network interface on the host is `docker0`). Every container that does not specify a network is attached to this default bridge.

```bash
# The docker0 bridge on the host
ip addr show docker0
# docker0: ... inet 172.17.0.1/16 ...
# Subnet: 172.17.0.0/16 (65,534 host addresses)
# Docker assigns addresses from this subnet to containers

# Default network properties
docker network inspect bridge
```

```json
{
  "Name": "bridge",
  "Driver": "bridge",
  "IPAM": {
    "Config": [{ "Subnet": "172.17.0.0/16", "Gateway": "172.17.0.1" }]
  },
  "Options": {
    "com.docker.network.bridge.default_bridge": "true",
    "com.docker.network.bridge.enable_icc":     "true",
    "com.docker.network.bridge.enable_ip_masquerade": "true",
    "com.docker.network.bridge.host_binding_ipv4": "0.0.0.0",
    "com.docker.network.bridge.name": "docker0"
  }
}
```

**Key properties of the default bridge:**

**Automatic DNS is absent**: containers on the default bridge network cannot resolve each other by name. If container A wants to reach container B, it must use container B's IP address (which changes on every restart) or use `--link` (a legacy feature that inserts entries into `/etc/hosts`). This is the critical operational limitation of the default bridge that user-defined bridges fix.

**IP masquerade (NAT) for outbound**: when a container sends a packet to an external IP, Docker rewrites the source IP to the host's IP using iptables MASQUERADE rules. The external server sees traffic from the host IP, not the container IP. Return packets arrive at the host, which NATTs them back to the container.

**Port publishing with -p**: containers are not reachable from outside the host unless ports are explicitly published. `docker run -p 8080:3000 myapp` creates an iptables DNAT rule: incoming packets on host port 8080 are rewritten to the container IP port 3000.

```bash
# See the iptables NAT rules Docker creates:
iptables -t nat -L DOCKER -n --line-numbers
# Chain DOCKER (4 references)
# DNAT  tcp  -- anywhere  anywhere  tcp dpt:8080 to:172.17.0.2:3000
```

**Inter-container communication (ICC)**: by default, containers on the same bridge can reach each other directly by IP (ICC is enabled). A container at 172.17.0.2 can `curl 172.17.0.3:3000` to reach another container. This works because both are attached to the same bridge — the bridge forwards packets between them at L2 (Ethernet frame level).

**Q4. What is a user-defined bridge network and what does it add over the default bridge?**
A: A user-defined bridge is a bridge network you create explicitly with `docker network create`. It uses the same Linux bridge mechanism as `docker0` but adds critical features that make it the correct choice for almost all application networking:

```bash
# Create a user-defined bridge network
docker network create \
  --driver bridge \
  --subnet 172.20.0.0/16 \
  --gateway 172.20.0.1 \
  --opt com.docker.network.bridge.name=br-payments \
  payments-network

# Run containers attached to this network
docker run -d --name payment-service \
  --network payments-network \
  payment-service:latest

docker run -d --name postgres \
  --network payments-network \
  postgres:15
```

**What user-defined bridges add:**

**Automatic DNS resolution (the most important difference):**
Docker's embedded DNS server (`127.0.0.11`) handles name resolution for user-defined networks. Containers can reach each other by service name:
```bash
# Inside payment-service container, on user-defined network:
curl http://postgres:5432    # "postgres" resolves to the postgres container's IP
curl http://redis:6379       # name-based resolution, not IP-based

# On the default bridge (docker0):
curl http://postgres:5432    # FAILS — no automatic DNS on default bridge
```

This is architecturally significant: with user-defined networks, connection strings in application code can use container names (`DATABASE_URL=postgresql://postgres:5432/payments`). On the default bridge, they would need IPs that change on every container restart.

**Network-level isolation between application stacks:**
Containers on different user-defined networks cannot reach each other by default:
```
payments-network:  payment-service, postgres, redis  (can all talk to each other)
reporting-network: reporting-service, clickhouse     (isolated from payments-network)

payment-service cannot reach clickhouse directly
reporting-service cannot reach postgres directly
```

This isolation is a security boundary — a compromised reporting service cannot directly query the payments database. Compared to the default bridge (where all containers can reach all other containers by IP), user-defined networks enforce service-level isolation.

**A container can join multiple networks:**
```bash
# API gateway needs to reach both service networks
docker network connect payments-network  api-gateway
docker network connect reporting-network api-gateway

# api-gateway now has two network interfaces:
#   eth0: connected to payments-network  (172.20.x.x)
#   eth1: connected to reporting-network (172.21.x.x)
# It can reach both postgres and clickhouse
# postgres and clickhouse still cannot reach each other
```

**Configurable ICC:**
```bash
# Create a network with ICC disabled (containers cannot directly reach each other)
# All traffic must go through the gateway (useful for strict isolation)
docker network create \
  --opt com.docker.network.bridge.enable_icc=false \
  strict-network
```

**Q5. How does Docker Compose use networks and what is the default behavior?**
A: Docker Compose automatically creates a user-defined bridge network for each project. All services in a `docker-compose.yml` are connected to this network by default, enabling service-name DNS resolution between them.

```yaml
# docker-compose.yml
version: "3.9"
services:
  payment-api:
    image: payment-api:latest
    ports:
      - "3000:3000"      # published to host; external traffic enters here
    environment:
      DATABASE_URL: postgresql://postgres:5432/payments  # "postgres" resolves via Docker DNS
      REDIS_URL:    redis://redis:6379                   # "redis" resolves via Docker DNS
    networks:
      - backend          # custom network; not on frontend

  postgres:
    image: postgres:15
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend          # backend only; no direct external access

  redis:
    image: redis:7-alpine
    networks:
      - backend

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    networks:
      - frontend         # external-facing
      - backend          # can reach payment-api
    depends_on:
      - payment-api

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    # No published ports; no external access; only backend containers communicate here

volumes:
  pgdata:
```

**Network topology this creates:**
```
External traffic (port 80/443)
    ↓
nginx (frontend + backend networks)
    ↓ (via backend network)
payment-api (backend only)
    ↓ (via backend network)
postgres, redis (backend only — not reachable from external)

Isolation:
  postgres has no published ports → not reachable from outside the host
  redis has no published ports    → not reachable from outside the host
  payment-api not on frontend     → not directly reachable from outside; nginx proxies
```

**The default network name:**
When no networks are defined, Compose creates a single network named `<project-name>_default`. The project name is the directory name or the `-p` flag value. All services join this network automatically.

```bash
# Network created by Compose for a project in /app/payments directory:
docker network ls | grep payments
# payments_default     bridge
# payments_backend     bridge  (if you defined networks)
# payments_frontend    bridge
```

## Section 3: Host Network

**Q6. What is the host network mode and when should you use it?**
A: In host network mode, the container shares the host's network namespace entirely — no separate network stack, no veth pair, no bridge. The container's processes bind directly to the host's network interfaces and port space.

```bash
# Container uses host networking
docker run --network host nginx

# On the host:
ss -tlnp | grep nginx
# *:80    # nginx is bound directly to host port 80, not via port mapping
# The container has NO port mapping (-p) with host mode — it's unnecessary
# because the container IS using the host's ports directly
```

**What host network mode means technically:**
```
Bridge mode:                    Host mode:
  Container network namespace     No separate container namespace
  └── eth0 (container, 172.17.x)  Container processes bind to:
       ↕ (veth pair)               └── eth0 (host physical, 192.168.1.10)
  docker0 (host bridge)           └── lo (host loopback, 127.0.0.1)
       ↕
  eth0 (host physical, 192.168.1.10)
```

The container has no IP address of its own — it uses the host's IP directly.

**Performance characteristics:**
Host networking eliminates all virtual networking overhead:
- No veth pair packet copying.
- No bridge forwarding decisions.
- No iptables NAT processing.
- No IP masquerade for outbound packets.

This makes host networking the fastest Docker networking option — it is effectively identical to running the process directly on the host without any container networking abstraction.

**When to use host networking:**

**Network performance benchmarking**: when you need to measure the actual performance of your application without Docker networking overhead, run with `--network host` to eliminate the variable.

**Applications that require very high packet rates**: network monitoring tools, packet capture tools, high-frequency trading processes, or any application where the 10–15% throughput reduction from bridge networking is unacceptable.

**Applications that bind to all interfaces and need host port access**: a container running a network sniffer (tcpdump, Wireshark) needs access to all host network interfaces. With bridge networking, it can only see the container's virtual interface.

**When not to use host networking:**

**Security-sensitive applications**: with host networking, a container can bind to any host port, can reach services listening on `127.0.0.1` (localhost), and can observe all host network traffic. A compromised container has full network access equivalent to a process running as root on the host.

**Multiple containers needing the same port**: two containers with `--network host` both wanting port 3000 will conflict — the second one fails to start. Bridge networking resolves this by giving each container its own port space.

**Portable deployments**: host networking behavior depends on the host's network configuration. A container that works with host networking on your development machine may not work the same way on a different host (different interface names, different IP ranges, firewall rules). Bridge networking provides a consistent environment regardless of the host network.

**Host networking and Kubernetes**: Kubernetes has its own networking model (pods with shared network namespaces, CNI plugins). `hostNetwork: true` in Kubernetes is available but highly restricted in production clusters — most security policies prohibit it.

## Section 4: Overlay Networks

**Q7. What is an overlay network and what problem does it solve that bridge networks cannot?**
A: An overlay network creates a virtual L2 network spanning multiple Docker hosts, enabling containers on different physical machines to communicate as if they were on the same LAN — without requiring changes to the underlying physical network infrastructure.

Bridge networks are host-local — they exist within one Docker host. A container on Host A (bridge 172.20.0.0/16) cannot reach a container on Host B (bridge 172.20.0.0/16) without routing configuration at the host level, and even then, the address spaces would conflict. Overlay networks solve this:

```
Without overlay (bridge, host-local):
  Host A:
    Container A1 (172.20.0.2) ─── docker0 ─── Host A eth0 (10.0.0.1)
  Host B:
    Container B1 (172.20.0.3) ─── docker0 ─── Host B eth0 (10.0.0.2)

  Can Container A1 reach Container B1?
  Not directly — different hosts, no routing between 172.20.x.x subnets

With overlay network (ingress-network or custom overlay):
  Container A1 (10.0.1.2) ──┐
                             ├── overlay network (10.0.1.0/24)
  Container B1 (10.0.1.3) ──┘
  Both see each other as being on the same subnet, regardless of host
```

**How overlay networks work — VXLAN encapsulation:**
Overlay networks use VXLAN (Virtual Extensible LAN) to encapsulate L2 Ethernet frames inside UDP packets. A container's network traffic (L2 frame destined for another container's MAC address) is:

1. Intercepted by the overlay network driver on the sending host.
2. Encapsulated in a VXLAN UDP packet (source: sending host IP, destination: receiving host IP, UDP port 4789).
3. Sent across the physical network to the receiving host.
4. Decapsulated on the receiving host.
5. Delivered to the destination container's network interface.

```
Container A1 sends:  [Ethernet frame: dst MAC = B1's MAC | IP: 10.0.1.3 | payload]
                          │
                    VXLAN encapsulation
                          │
Host A sends:        [UDP: src=10.0.0.1, dst=10.0.0.2, port=4789 | VXLAN header | original frame]
                          │
                    Physical network (10.0.0.0/24)
                          │
Host B receives:     [UDP packet]
                          │
                    VXLAN decapsulation
                          │
Container B1 receives: [Ethernet frame: IP: 10.0.1.3 | payload]
```

The physical network sees only UDP packets between host IPs. The overlay network's subnet (10.0.1.0/24) is completely invisible to the physical network infrastructure — no routing changes needed on routers or switches.

**Q8. What is Docker Swarm and how does it use overlay networks?**
A: Docker Swarm is Docker's built-in container orchestration mode. When you initialize a Swarm (`docker swarm init`), Docker creates a distributed key-value store (based on Raft consensus) that all Swarm nodes share. Overlay networks in Swarm use this distributed store to track which containers are on which hosts and to distribute MAC address tables across the cluster.

```bash
# Initialize a Swarm (on the first manager node)
docker swarm init --advertise-addr 10.0.0.1

# Join worker nodes
docker swarm join --token SWMTKN-... 10.0.0.1:2377

# Create an overlay network
docker network create \
  --driver overlay \
  --subnet 10.0.1.0/24 \
  --attachable \           # allow standalone containers (not just services) to attach
  payments-overlay

# Deploy a service across the swarm
docker service create \
  --name payment-service \
  --replicas 3 \
  --network payments-overlay \
  payment-service:latest

# The 3 replicas are distributed across swarm nodes
# All can communicate via the overlay network regardless of which host they're on
```

**What Swarm manages for overlay networks:**

**Distributed MAC table (VTEP — VXLAN Tunnel Endpoint)**: each Swarm node is a VTEP. The Swarm control plane distributes information about which container MAC addresses are on which host. When container A1 on Host A wants to reach container B1 on Host B, Host A's VTEP knows to send the VXLAN packet to Host B's IP.

**Service VIPs (Virtual IPs)**: Docker Swarm assigns each service a Virtual IP — a stable IP address for the service that doesn't change even as replicas come and go. Internal DNS for the service name resolves to the VIP. The VIP is handled by IPVS (IP Virtual Server) in the kernel — it load-balances requests across all healthy replicas.

```
payment-service:
  VIP: 10.0.1.254 (stable — assigned to the service, not a specific replica)
  DNS: payment-service → 10.0.1.254

  Replicas (actual containers):
    payment-service.1 on Host A: 10.0.1.2
    payment-service.2 on Host B: 10.0.1.3
    payment-service.3 on Host C: 10.0.1.4

  Request to payment-service → VIP 10.0.1.254 → IPVS → one of the replicas
```

**Ingress network (routing mesh):**
Swarm creates a special overlay network called `ingress` for the routing mesh. When a port is published for a service (`--publish 80:3000`), any Swarm node can accept traffic on port 80, even if no replica is running on that node — the ingress network routes traffic to a node that has a replica.

```
External traffic → port 80 on ANY Swarm node
                          │
                   ingress overlay network
                          │
               IPVS load balancing → replica on correct host
```

**Q9. What are the security properties of overlay networks and how do you encrypt overlay traffic?**
A: Overlay traffic is encapsulated in VXLAN UDP packets that traverse the physical network. Without encryption, this traffic is plaintext — readable by anyone with access to the physical network path between hosts. In a shared data center or multi-tenant cloud environment, this means:

- Network administrators can see inter-container traffic.
- A compromised host on the same network segment could capture and read container-to-container traffic.
- Man-in-the-middle attacks between hosts are theoretically possible.

**Enabling IPsec encryption for overlay traffic:**
Docker Swarm supports encrypting overlay network traffic using IPsec (specifically, the Linux kernel's `xfrm` IPsec implementation with AES-GCM encryption):

```bash
# Create an encrypted overlay network
docker network create \
  --driver overlay \
  --opt encrypted \
  --subnet 10.0.2.0/24 \
  payments-overlay-encrypted
```

With `--opt encrypted`, Docker automatically:
1. Generates and distributes AES-GCM keys to all Swarm managers.
2. Configures IPsec security associations between all Swarm nodes.
3. All VXLAN traffic on this network is encrypted end-to-end between hosts.

**Trade-offs of overlay encryption:**
- **CPU overhead**: AES-GCM encryption/decryption adds CPU cost, particularly for high-throughput traffic. On modern CPUs with AES-NI hardware instructions, this is typically 5–15% throughput reduction.
- **Key management**: keys are managed by Docker automatically. Key rotation requires manual intervention (recreating the network or using Docker Secrets-based key management).
- **Debugging difficulty**: encrypted traffic cannot be inspected with tcpdump on the wire — you can only capture at the container interface level.

**Alternatives for overlay security:**
In practice, many production Swarm/Kubernetes clusters run on private VPCs where the physical network between nodes is already trusted (e.g., within an AWS VPC, the network between EC2 instances is already isolated from other tenants). In these environments, overlay encryption is often not enabled — TLS within applications (service-to-service TLS) is preferred because it provides end-to-end encryption that doesn't trust the network infrastructure even within the cluster.

## Section 5: Network Drivers and Advanced Configuration

**Q10. What are the Docker network drivers and what are their use cases?**
A: Docker uses a pluggable network driver architecture. The driver determines how the virtual network is implemented. Built-in drivers:

**`bridge` (default for single-host):**
Linux bridge-based networking. Virtual switches in software. All containers on the same bridge can communicate. The correct default for single-host deployments and Docker Compose. Creates `docker0` (default) or custom bridges (user-defined).

**`host`:**
No network isolation — container uses host's network namespace directly. Maximum performance; no isolation. Appropriate for specific performance-critical or network-tool use cases.

**`overlay` (multi-host, requires Swarm or external key-value store):**
VXLAN-based virtual L2 network spanning multiple hosts. Required for multi-host container communication without routing changes. The networking layer for Docker Swarm services.

**`macvlan`:**
Assigns a MAC address to each container and makes it appear as a physical device on the network. Containers get IPs from the physical network's subnet — they look like physical machines to routers and other network devices. The host cannot communicate directly with macvlan containers (kernel limitation — a macvlan parent interface cannot communicate with its children).

```bash
# macvlan network: containers appear as physical machines on 192.168.1.0/24
docker network create \
  --driver macvlan \
  --subnet 192.168.1.0/24 \
  --gateway 192.168.1.1 \
  --opt parent=eth0 \        # physical interface to attach to
  macvlan-net

docker run --network macvlan-net \
           --ip 192.168.1.100 \  # assign a specific physical-network IP
           myapp
```

Macvlan use cases: legacy applications that expect to be directly on the physical network; applications that require a specific physical-network IP; environments where the network team controls IP allocation and containers must participate in the physical IP scheme.

**`ipvlan`:**
Similar to macvlan but all containers share the parent interface's MAC address — uses IP-level (L3) routing instead of MAC-level (L2) switching. Works in environments where switches limit the number of MAC addresses per port (some cloud virtual switches). Two modes: L2 (similar to macvlan behavior) and L3 (container acts as a router; no broadcast traffic; more scalable).

**`none`:**
Container has only a loopback interface (`lo`, 127.0.0.1) — completely isolated from all network communication. Used for containers that must not have network access for security reasons, or containers that provide network access themselves via some other mechanism.

```bash
docker run --network none security-scanner:latest
# Container has NO network access whatsoever
# Can still access mounted volumes and process data, but cannot make any network calls
```

**Third-party network plugins (CNI-compatible):**
Kubernetes uses CNI (Container Network Interface) plugins rather than Docker's native networking. Popular CNI plugins: Calico (L3 routing, network policy enforcement), Flannel (VXLAN overlay, simple), Weave Net (encrypted overlay, multi-host), Cilium (eBPF-based, high performance, network policies). These replace Docker's networking entirely when running under Kubernetes.

**Q11. How does DNS resolution work inside Docker containers, and what is the embedded DNS server?**
A: Docker's embedded DNS server is one of its most important but least visible features. Every container on a user-defined network has its DNS configuration automatically set to use Docker's embedded DNS resolver at `127.0.0.11` (a special loopback address reserved for this purpose).

**Resolution flow:**
```
Container process: curl http://payment-service:3000
    │
    ↓ DNS query: payment-service (A record?)
    │
127.0.0.11 (Docker embedded DNS, inside container)
    │
    ├── If name is a container/service on same network:
    │     Return container's IP (172.20.0.4)
    │
    ├── If name matches a network alias or service alias:
    │     Return aliased container's IP
    │
    └── If name not found in Docker's records:
          Forward to host's DNS resolver (/etc/resolv.conf's nameserver)
              │
              ↓ (external resolution)
          8.8.8.8 or VPC DNS resolver
```

**What the embedded DNS knows about:**
- Container names on user-defined networks (`payment-service` → IP of container named `payment-service`).
- Network aliases (`--network-alias old-name` → same IP as the container, accessible by the alias).
- Docker Swarm service names → VIP of the service.
- Docker Compose service names (which are the keys in `docker-compose.yml`).

**Custom DNS configuration:**
```bash
# Override DNS for a container
docker run \
  --dns 10.0.0.53 \           # use internal corporate DNS
  --dns-search example.com \   # append to unqualified hostnames
  --dns-opt ndots:5 \          # DNS search policy
  myapp

# In docker-compose.yml:
services:
  payment-api:
    dns:
      - 10.0.0.53
      - 8.8.8.8
    dns_search:
      - payments.internal
```

**The `/etc/resolv.conf` inside containers:**
Docker writes `/etc/resolv.conf` in the container to point to the embedded DNS:
```
nameserver 127.0.0.11
options ndots:0
```
On user-defined networks: `127.0.0.11` first (Docker DNS for service names), then falls through to external DNS for unresolved names. On the default bridge: `/etc/resolv.conf` contains the host's DNS servers (no Docker DNS, no automatic service name resolution).

**Q12. What are the performance implications of different Docker network modes, and how do you measure them?**
A: Docker networking adds overhead compared to native Linux processes. The overhead depends on the network driver and the processing path each packet must traverse.

**Overhead by network mode:**

**`host` networking (baseline — no overhead):**
Packets travel directly between the host's physical interface and the process. No veth, no bridge, no NAT. Performance is identical to a non-containerized process.

**`bridge` networking (typical overhead: 10–20% throughput reduction, ~50–100µs additional latency per packet):**
Each packet traverses:
1. Container's `eth0` (veth container end).
2. veth pair copy to host end.
3. `docker0` bridge forwarding decision.
4. For external traffic: iptables NAT (masquerade) processing.
5. Physical interface.

The bridge forwarding (step 3) involves MAC address table lookups. The iptables NAT (step 4) involves netfilter rule traversal. These add latency and reduce throughput compared to direct physical-interface access.

**`overlay` networking (highest overhead: 20–30% throughput reduction, ~100–200µs additional latency):**
Each packet traverses the bridge path plus:
1. VXLAN encapsulation (adding 50 bytes of VXLAN/UDP/IP headers).
2. Kernel VTEP processing.
3. Decapsulation on the receiving host.
4. Second bridge traversal.

The encapsulation adds bytes (reducing effective MTU) and CPU cycles (header processing).

**MTU considerations for overlay networks:**
Physical network MTU is typically 1500 bytes. VXLAN adds 50 bytes of overhead, leaving 1450 bytes for the payload. But the container's network interface also has an MTU of 1500 bytes by default — meaning a container can generate 1500-byte packets that, after VXLAN encapsulation, become 1550-byte packets that exceed the physical network MTU and are fragmented (or dropped if the physical network sets "don't fragment").

```bash
# Fix: set the overlay network's MTU to 1450 (1500 - 50 bytes VXLAN overhead)
docker network create \
  --driver overlay \
```

## Section 6: Security

**Q13. What are the network security risks in Docker and how do you mitigate them?**
A: Docker networking introduces several security surfaces that differ from traditional server security:

**Risk 1 — Default bridge ICC (inter-container communication):**
On the default bridge (`docker0`), all containers can reach all other containers by IP, regardless of intent. A compromised nginx container can directly query the postgres database at 172.17.0.3:5432 — bypassing any application-level access control.

```bash
# Mitigation: use user-defined networks with ICC disabled
docker network create \
  --opt com.docker.network.bridge.enable_icc=false \
  isolated-net

# OR: use separate user-defined networks per application tier
# (containers on different user-defined networks cannot communicate by default)
```

**Risk 2 — Port publishing to 0.0.0.0:**
`docker run -p 8080:3000` binds the host port to `0.0.0.0:8080` — all network interfaces, including public-facing ones. If the host has a public IP, the container service is accessible from the internet, even if you intended it to be internal.

```bash
# Mitigation: bind to specific interfaces
docker run -p 127.0.0.1:8080:3000 myapp  # localhost only
docker run -p 10.0.0.1:8080:3000 myapp   # internal network interface only

# Never: docker run -p 0.0.0.0:5432:5432 postgres  (postgres on public internet)
```

**Risk 3 — Docker daemon socket exposure:**
Mounting the Docker socket into a container (`-v /var/run/docker.sock:/var/run/docker.sock`) gives the container full control over the host's Docker daemon — equivalent to root access on the host. This is a common technique for CI/CD runners but must be treated as a critical security escalation path.

```bash
# Mitigation: use Docker-in-Docker (dind) as a sidecar instead of socket mounting
# Or: use Kaniko, Buildah, or Podman for container builds in CI without socket access
# Or: restrict socket with a proxy (docker-socket-proxy) that limits allowed operations
```

**Risk 4 — Container network traffic visibility:**
On a bridged network, all containers attached to the same bridge can see each other's broadcast traffic and ARP requests. A container running in promiscuous mode could potentially sniff traffic of other containers on the same bridge.

```bash
# Mitigation: use separate user-defined networks (isolates broadcast domains)
# Each user-defined bridge is a separate broadcast domain
# Containers on payments-net cannot sniff containers on reporting-net
```

**Risk 5 — Overlay network unencrypted by default:**
Overlay network traffic traverses the physical network as plaintext VXLAN. Internal network observers can capture container-to-container traffic.

```bash
# Mitigation: enable overlay encryption
docker network create --driver overlay --opt encrypted sensitive-overlay

# OR (preferred): use TLS within applications
# Each service uses TLS for its connections regardless of network layer encryption
```

**Network security best practices:**
```yaml
# docker-compose.yml secure network configuration
services:
  nginx:
    networks: [dmz, backend]          # nginx bridges external and internal
  payment-api:
    networks: [backend]               # internal only; no direct external access
  postgres:
    networks: [database]              # separate network; only payment-api can reach it
  payment-api-to-db-bridge:          # fictional — in compose, just add payment-api to database network
    networks: [backend, database]     # bridge service if needed

networks:
  dmz:
    driver: bridge
    # Public-facing: nginx only
  backend:
    driver: bridge
    internal: true                    # no external connectivity; containers only
  database:
    driver: bridge
    internal: true                    # no external connectivity; DB isolated
```

The `internal: true` option prevents the network from having external connectivity — no NAT, no internet access, no published ports. Containers on this network can only communicate with other containers on the same network.

## Section 7: Scenario / System Design Style Questions

**Q14. "You have a multi-container application: nginx (reverse proxy), a NestJS API, PostgreSQL, and Redis. Design the Docker network topology for local development and explain why."**
A:

```yaml
# docker-compose.yml — local development setup
version: "3.9"

services:

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"         # Published: external traffic enters here
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    networks:
      - frontend        # Receives external traffic
      - backend         # Proxies to nestjs-api
    depends_on:
      - nestjs-api

  nestjs-api:
    build: .
    environment:
      DATABASE_URL: postgresql://postgres:postgres@postgres:5432/payments
      REDIS_URL:    redis://redis:6379
      NODE_ENV:     development
    networks:
      - backend         # Receives from nginx
      - database        # Connects to postgres and redis
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy

  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB:       payments
      POSTGRES_USER:     postgres
      POSTGRES_PASSWORD: postgres
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - database        # Database network only; not reachable from frontend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    networks:
      - database        # Same isolation as postgres
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 5s
      retries: 5

networks:
  frontend:
    driver: bridge
    # nginx is on this network (receives external port 80/443)
    # nestjs-api is NOT on this network (not directly exposed)

  backend:
    driver: bridge
    # nginx and nestjs-api communicate here
    # postgres and redis are NOT here (not reachable from nginx)

  database:
    driver: bridge
    internal: true      # NO external connectivity
    # nestjs-api, postgres, redis
    # nginx is NOT here (nginx cannot directly query postgres)

volumes:
  pgdata:

# Network topology:
#
# [Port 80/443]
#     │
#   nginx ──(frontend)─── (receives external traffic)
#     │
#   (backend)
#     │
# nestjs-api ──(database)─── postgres
#                        └── redis
#
# Security properties:
#   nginx cannot directly reach postgres or redis (different networks)
#   postgres is on internal:true network (no internet access)
#   redis is on internal:true network (no internet access)
#   nestjs-api has no published ports (not directly accessible from outside)
#   Only nginx has published ports (port 80 and 443)
#
# DNS resolution:
#   nestjs-api → postgres:5432 (resolves via Docker DNS)
#   nestjs-api → redis:6379    (resolves via Docker DNS)
#   nginx → nestjs-api:3000    (resolves via Docker DNS, on backend network)
```

**Design justifications:**

Three networks enforce defense-in-depth: even if nginx is compromised, it cannot directly access the database. Even if the API is compromised, the database has no external connectivity (`internal: true`). Published ports only on nginx means the attack surface is limited to one container.

User-defined networks (not default bridge) provide automatic DNS resolution — application connection strings use service names (`postgres:5432`) not IPs, making the configuration portable and independent of container IP allocation.

**Q15. "Explain what happens at the network level when two containers on the same user-defined bridge network communicate with each other."**
A:

```
Scenario:
  nestjs-api (172.20.0.3, eth0) sends HTTP request to postgres (172.20.0.4, eth0)
  Both on user-defined bridge network "payments-backend" (172.20.0.0/24)

Step 1: DNS resolution
  Application: new PgClient({ host: 'postgres', port: 5432 })
  Kernel DNS query to 127.0.0.11 (Docker embedded DNS): "postgres"
  Docker DNS: looks up "postgres" in payments-backend network
            → returns 172.20.0.4
  Application now has: connect to TCP 172.20.0.4:5432

Step 2: TCP connection initiation (SYN packet)
  nestjs-api process: connect(fd, {172.20.0.4, 5432})
  Kernel routing table in nestjs-api's network namespace:
    172.20.0.0/24 is on eth0 (same subnet — local delivery, no gateway)
  SYN packet: [src: 172.20.0.3:random_port, dst: 172.20.0.4:5432]
  Kernel needs dst MAC address for 172.20.0.4 (same subnet)

Step 3: ARP resolution (L2 address discovery)
  nestjs-api's eth0 sends ARP broadcast: "Who has 172.20.0.4?"
  The bridge (br-payments-backend) receives the broadcast
  Bridge forwards ARP broadcast to all ports (including postgres's veth pair end)
  postgres receives ARP, replies: "172.20.0.4 is at mac:address:of:postgres:eth0"
  Bridge learns: 172.20.0.4 → veth-postgres-host-end
  nestjs-api caches ARP reply; now knows postgres's MAC address

Step 4: Packet delivery
  nestjs-api sends Ethernet frame:
    [dst MAC: postgres_mac | src MAC: nestjs_mac | IP: dst=172.20.0.4 | TCP SYN]
  Frame enters eth0 in nestjs-api's network namespace
  Crosses veth pair to the host namespace (veth-nestjs-host-end)
  Arrives at br-payments-backend (the Linux bridge)
  Bridge looks up dst MAC (postgres_mac) in its forwarding table
  Bridge found it: send to veth-postgres-host-end
  Frame crosses veth pair into postgres's network namespace
  Arrives at postgres's eth0 (172.20.0.4)
  Kernel delivers to process listening on :5432

Step 5: Response path (SYN-ACK)
  Same path in reverse: postgres → its veth → bridge → nestjs veth → nestjs

Key observations:
  - No iptables NAT processing (same bridge; no routing between networks)
  - No iptables MASQUERADE (no address translation; src IP unchanged)
  - Bridge operates at L2 (Ethernet) level; uses MAC table, not IP routing
  - Bridge flooding on first packet (ARP); unicast forwarding after ARP learned
  - RTT: one veth crossing each way + bridge forwarding ≈ 50-100 microseconds

Contrast: container to external IP (e.g., api.example.com):
  - Packet goes to bridge gateway (172.20.0.1 — the bridge interface on the host)
  - Host routing: 0.0.0.0/0 via host's physical gateway
  - iptables MASQUERADE: src IP rewritten from 172.20.0.3 to host's public IP
  - Packet leaves host's physical interface
  - Return packets: MASQUERADE table reverse-translates dst IP back to 172.20.0.3
```

**Q16. "Your Docker Swarm services need to communicate across three EC2 instances. Walk through the overlay network setup and explain what happens to a packet sent between containers on different hosts."**
A:

```
Setup:
  EC2 Instance 1 (10.0.0.1): payment-api replica 1 (overlay IP: 10.10.0.2)
  EC2 Instance 2 (10.0.0.2): payment-api replica 2 (overlay IP: 10.10.0.3)
  EC2 Instance 3 (10.0.0.3): postgres (overlay IP: 10.10.0.4)

Overlay network: payments-swarm (10.10.0.0/24)

Infrastructure setup:
  docker swarm init --advertise-addr 10.0.0.1   (on Instance 1)
  docker swarm join --token ... 10.0.0.1:2377   (on Instances 2 and 3)

  docker network create \
    --driver overlay \
    --subnet 10.10.0.0/24 \
    payments-swarm

  # Swarm control plane (Raft) distributes:
  #   - Which containers are on which hosts
  #   - MAC-to-host mappings (VTEP table)
  #   - Service VIPs

Packet journey: payment-api.1 (10.0.0.1) → postgres (10.0.0.3)
  Application: connect to 'postgres:5432' (service DNS name)
  Swarm DNS: postgres → VIP 10.10.0.254 → IPVS → postgres container IP: 10.10.0.4

Step 1: Inside the container on Instance 1
  Container sends TCP SYN: [src: 10.10.0.2:rand, dst: 10.10.0.4:5432]
  Container's eth0 is a veth pair; other end on Instance 1's host network namespace

Step 2: Overlay network driver intercepts
  VTEP (VXLAN Tunnel Endpoint) on Instance 1 receives the frame from the container's veth
  VTEP looks up: "Who has 10.10.0.4?" → consults Swarm-distributed VTEP table
  Result: 10.10.0.4 is on Instance 3 (EC2 10.0.0.3)
  VTEP now performs VXLAN encapsulation:
    Inner frame: [dst MAC: postgres_mac | IP: 10.10.0.4 | TCP SYN | payload]
    VXLAN header: VNI (VXLAN Network Identifier for this overlay network)
    Outer UDP:    [src: 10.0.0.1:random, dst: 10.0.0.3:4789]
    Outer IP:     [src: 10.0.0.1, dst: 10.0.0.3]

  Total packet: [Eth | IP(10.0.0.1→10.0.0.3) | UDP:4789 | VXLAN | Eth | IP(10.10.0.2→10.10.0.4) | TCP | payload]
  Size: original payload + ~50 bytes VXLAN overhead

Step 3: Physical network transit
  Packet leaves Instance 1's eth0 as a normal UDP packet
  AWS VPC routes it: 10.0.0.3 is in the same VPC subnet → direct delivery
  No routing changes needed in VPC; it looks like ordinary UDP to the network

Step 4: VXLAN decapsulation on Instance 3
  Instance 3's kernel receives UDP packet on port 4789
  VTEP on Instance 3 recognizes VXLAN header; strips outer IP/UDP/VXLAN headers
  Inner frame: [dst MAC: postgres_mac | IP: 10.10.0.4 | TCP SYN]
  VTEP injects the inner frame into the overlay bridge on Instance 3
  Bridge forwards to postgres container's veth pair
  postgres's eth0 receives the TCP SYN at 10.10.0.4:5432

Step 5: Response
  postgres sends TCP SYN-ACK: [src: 10.10.0.4:5432, dst: 10.10.0.2:rand]
  Same path in reverse: VTEP on Instance 3 encapsulates, sends to Instance 1
  VTEP on Instance 1 decapsulates, delivers to payment-api container

Latency budget:
  No overlay:      EC2 to EC2 in same VPC: ~0.1ms RTT
  With overlay:    ~0.1ms physical + ~0.1ms encap/decap overhead = ~0.2ms RTT
  (VXLAN in kernel is fast; encap/decap is microseconds on modern CPUs)

MTU note:
  Physical MTU: 1500 bytes
  VXLAN overhead: 50 bytes
  Effective container MTU: 1450 bytes (must set this or fragmentation occurs)
  AWS Jumbo Frames: 9001 bytes MTU within VPC → overlay MTU can be 8951 bytes
    → In AWS VPC: set overlay MTU to 8951 for near-full throughput
```

## Quick Reference

| Driver | Scope | Use case | IP visibility | Performance |
|---|---|---|---|---|
| `bridge` (default) | Single host | Development, single-host apps | Private (NAT for external) | Good |
| `bridge` (user-defined) | Single host | Compose, isolated microservices | Private + DNS | Good |
| `host` | Single host | Performance-critical, network tools | Host IP directly | Best |
| `overlay` | Multi-host (Swarm) | Swarm services, multi-host apps | Private overlay subnet | Moderate |
| `macvlan` | Single host | Legacy apps, physical network integration | Physical network IP | Best (no NAT) |
| `ipvlan` | Single host | Cloud environments, limited MACs | Physical network IP | Best |
| `none` | Single host | Air-gapped security, custom networking | Loopback only | N/A |

| Feature | Default bridge | User-defined bridge |
|---|---|---|
| Automatic DNS | ❌ (IPs only) | ✅ (container name resolves) |
| Network isolation | ❌ (all containers share) | ✅ (per-network isolation) |
| ICC control | Global setting | Per-network setting |
| Multiple networks per container | Limited | ✅ (connect to multiple) |
| Production recommended | ❌ | ✅ |

| Network concern | Solution |
|---|---|
| DB accessible from internet | No published ports; `internal: true` network |
| ICC between unrelated services | Separate user-defined networks |
| Overlay traffic exposed | `--opt encrypted` or application-level TLS |
| Container can reach host localhost | Use bridge (isolated); avoid `--network host` |
| Port binding to public interface | `-p 127.0.0.1:port:port` (bind to localhost) |
| MTU mismatch on overlay | Set MTU to 1450 (or 8951 in AWS VPC with jumbo frames) |

## The Core Mental Model

```
Docker networking = virtual network infrastructure in software

veth pair = virtual cable between container namespace and host namespace
bridge   = virtual switch forwarding packets between veth endpoints
NAT      = iptables masquerade for container → external communication
overlay  = VXLAN tunnel punching a virtual L2 across physical L3 network

The three network modes by intent:
  bridge:  I want containers isolated from each other but able to communicate
           on the same host via a virtual switch — the default for everything
  host:    I need maximum performance or host-network access — give up isolation
  overlay: I need containers on different hosts to communicate — VXLAN encapsulation

Bridge network decision:
  Default bridge: avoid in production
    - No automatic DNS (service names don't resolve)
    - All containers share one broadcast domain
    - No isolation between unrelated services

  User-defined bridge: use for everything
    - DNS resolution by container name
    - Per-network isolation
    - Multiple networks per container for multi-tier topologies
    - `internal: true` for networks that must not have external access

Overlay network requirements:
  Needs Docker Swarm (or external key-value store)
  MTU must be set: 1500 - 50 (VXLAN) = 1450 bytes (or 8951 in AWS with jumbo frames)
  Encryption optional: --opt encrypted (CPU overhead); prefer app-level TLS in production
  VTEP handles encap/decap; Raft distributes MAC-to-host mappings

Security in layers:
  1. Separate user-defined networks per tier (nginx, api, database)
  2. `internal: true` on database network (no external connectivity)
  3. Published ports only where necessary (nginx only; not api or database)
  4. Bind published ports to specific interfaces (127.0.0.1, not 0.0.0.0)
  5. Never expose database ports to the public internet
  6. TLS within applications (don't trust the network layer even within Docker)

DNS resolution:
  Only works on user-defined networks (not default bridge)
  Embedded DNS at 127.0.0.11 (visible in /etc/resolv.conf inside container)
  Resolves: container names, network aliases, Swarm service names → VIPs
  Falls through to host's DNS for external names
  Service names in connection strings (postgresql://postgres:5432) not IPs
```

---

**Tip for the interview:** Docker networking questions at 5 YOE almost always escalate to one of three places: (1) default bridge vs user-defined bridge — knowing immediately that the default bridge has no automatic DNS (containers can only reach each other by IP, which changes on restart) while user-defined bridges provide DNS resolution by container name, and that this is the reason you should never use the default bridge for multi-container applications, signals production Docker experience rather than tutorial knowledge; (2) the veth pair and bridge mechanics — being able to explain that a packet from container A to container B on the same bridge never touches iptables NAT (it goes: container A's eth0 → veth pair → docker0 bridge → veth pair → container B's eth0, entirely at L2), while a packet from container A to the internet goes through iptables MASQUERADE, shows you understand what's actually happening in the kernel rather than treating Docker networking as a black box; (3) overlay MTU — knowing that VXLAN adds 50 bytes of overhead and that leaving the overlay network MTU at 1500 bytes (the default) causes either packet fragmentation or dropped packets for any payload larger than 1450 bytes, and that in AWS you should use 8951 bytes (taking advantage of jumbo frames within VPC), is the operational gotcha that catches teams running overlay networks for the first time and explains mysterious connection failures under load.
