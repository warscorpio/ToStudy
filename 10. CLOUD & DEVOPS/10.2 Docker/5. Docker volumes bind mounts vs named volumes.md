# Docker Volumes: Bind Mounts vs Named Volumes — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What problem do Docker volumes solve?**
A: Docker containers have an ephemeral filesystem — when a container stops or is removed, any data written inside it is lost. This is by design: containers are meant to be stateless and reproducible. But real applications need to persist data (database files, uploaded files, logs) and share data between containers or between the host and a container.

Docker volumes solve this by mounting external storage into the container's filesystem at a specified path. The container reads and writes to this path as if it were local, but the actual data lives outside the container's lifecycle — it survives container stops, restarts, and removal.

Three types of mounts exist in Docker:
- **Named volumes** — managed by Docker; stored in Docker's own storage directory.
- **Bind mounts** — mount a specific host directory or file into the container.
- **tmpfs mounts** — in-memory only; not persisted; not covered here.

The choice between named volumes and bind mounts is one of the most common Docker design decisions, and each has a distinct appropriate use case.

**Q2. What is the Docker filesystem layering model and why does it make volumes necessary?**
A: Docker images are built from layers — each instruction in a Dockerfile (`RUN`, `COPY`, `ADD`) adds an immutable layer. When a container starts, Docker adds a thin writable layer on top of the image's read-only layers. All filesystem writes go into this writable layer:

```
Container filesystem:
  ┌──────────────────────────────┐
  │  Writable container layer    │  ← writes go here; lost when container is removed
  ├──────────────────────────────┤
  │  Image layer 3 (COPY app/)   │  ← read-only
  ├──────────────────────────────┤
  │  Image layer 2 (RUN npm ci)  │  ← read-only
  ├──────────────────────────────┤
  │  Image layer 1 (FROM node)   │  ← read-only
  └──────────────────────────────┘
```

When the container is removed (`docker rm`), the writable layer is deleted. A new container from the same image starts with a fresh writable layer — any data written by the previous container is gone.

Volumes bypass this mechanism entirely: they mount external storage directly into the container's filesystem at a specified path, bypassing the copy-on-write layer. Reads and writes to a mounted path go directly to the volume, not the writable layer. The data persists independently of the container's lifecycle.

## Section 2: Named Volumes

**Q3. What is a named volume and how does Docker manage it?**
A: A named volume is a storage unit created and managed by Docker. It has a name you assign (or Docker generates), and Docker stores its contents in a directory on the host that Docker manages — typically `/var/lib/docker/volumes/<volume-name>/_data` on Linux. You reference it by name; Docker handles the underlying path.

```bash
# Create a named volume explicitly
docker volume create postgres-data

# Or let Docker create it implicitly on container start
docker run \
  --volume postgres-data:/var/lib/postgresql/data \
  postgres:16

# List volumes
docker volume ls
# DRIVER    VOLUME NAME
# local     postgres-data

# Inspect: see where Docker stores the data on the host
docker volume inspect postgres-data
# [
#   {
#     "Name": "postgres-data",
#     "Driver": "local",
#     "Mountpoint": "/var/lib/docker/volumes/postgres-data/_data",
#     "Labels": {},
#     "Scope": "local"
#   }
# ]

# Remove a volume (only after no container uses it)
docker volume rm postgres-data

# Remove all unused volumes
docker volume prune
```

Named volumes in Docker Compose:

```yaml
version: '3.9'
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: myapp
      POSTGRES_PASSWORD: secret
    volumes:
      - postgres-data:/var/lib/postgresql/data   # named volume mount

  redis:
    image: redis:7
    volumes:
      - redis-data:/data

volumes:
  postgres-data:   # declares the named volume at the top level
  redis-data:
```

Docker Compose creates the volumes if they don't exist and reuses them on subsequent `docker compose up` runs. The data persists across `docker compose down` (which stops and removes containers but not volumes). Only `docker compose down --volumes` removes the volumes.

**Q4. What are the advantages of named volumes over bind mounts?**
A:

**Portability** — named volumes are entirely managed by Docker and are agnostic to the host's directory structure. A `docker-compose.yml` with a named volume works identically on macOS, Linux, and Windows, regardless of where Docker stores its data internally. A bind mount references a specific host path (`/home/aditya/projects/myapp/data`) which may not exist on a different machine.

**Performance on macOS and Windows** — Docker on macOS and Windows runs containers in a Linux VM. Bind mounts cross the VM boundary for every I/O operation — reads and writes must cross from the container (in the VM) to the host filesystem, which is dramatically slower than native Linux I/O. Named volumes store data inside the Linux VM's filesystem, so I/O stays within the VM — much faster. For database volumes, this difference is significant: a PostgreSQL container with a bind mount on macOS can be 10–100× slower than with a named volume.

**Docker-managed lifecycle** — Docker knows about named volumes and can back them up, migrate them, and clean them up (`docker volume prune`). Bind mount directories are just directories; Docker has no visibility into them.

**Initialization behavior** — if a named volume is empty when a container first mounts it, and the container image has data at that path (e.g., a database image with initial configuration files), Docker copies the image's data into the volume. Bind mounts do not do this — if the host directory is empty, the container sees an empty directory even if the image had files there.

**Volume drivers** — named volumes support pluggable drivers: `local` (default, stores on host), `nfs` (network-attached storage), `aws/efs` (Amazon EFS), `portworx`, etc. You can mount a volume backed by a network filesystem or cloud storage using the same `--volume name:/path` syntax. Bind mounts can only use the local host filesystem.

**Q5. When should you use named volumes?**
A: Named volumes are the correct choice for:

**Stateful services in any environment** — databases (PostgreSQL, MySQL, MongoDB, Redis), message queue storage (Kafka logs), search indexes (Elasticsearch data). These need persistence without caring about the host path.

**Any environment that is not the developer's local machine** — staging, CI/CD, production, or a colleague's machine. Named volumes work identically everywhere.

**High I/O services on macOS or Windows** — databases, file-heavy workloads. The performance difference vs bind mounts is significant enough to be a correctness concern (slow enough to fail health checks or cause timeouts).

**When Docker manages the data lifecycle** — you want `docker volume prune` to clean up, or you want to use `docker run --volumes-from` to share a volume between containers.

## Section 3: Bind Mounts

**Q6. What is a bind mount and how does it work?**
A: A bind mount mounts a specific directory or file from the host filesystem directly into the container. The container sees and can modify the exact files that exist at that host path — it is not a copy; both the host and container are reading from and writing to the same underlying inodes.

```bash
# Bind mount: host path → container path
docker run \
  --volume /absolute/host/path:/container/path \
  myimage

# With Docker Compose
services:
  app:
    image: myapp:latest
    volumes:
      - ./src:/app/src          # relative host path (resolved to absolute by Compose)
      - ./config/nginx.conf:/etc/nginx/nginx.conf:ro   # :ro = read-only mount
```

The `./src` relative path is resolved relative to the `docker-compose.yml` file's directory. Using relative paths makes the Compose file portable across team members' machines as long as they check out the repository to the same relative structure.

**Read-only bind mounts (`:ro`):**
Adding `:ro` makes the mount read-only inside the container — the container can read the files but cannot modify them. Use for configuration files, secrets, and certificate files that the container should consume but never change:

```yaml
volumes:
  - ./nginx.conf:/etc/nginx/nginx.conf:ro
  - ./certs:/etc/ssl/certs:ro
```

**Q7. What are the advantages of bind mounts over named volumes?**
A:

**Live code reloading for development** — the killer use case. Mount the source code directory from the host into the container. The container's process (Node.js with `nodemon`, Python with `watchdog`, webpack dev server) watches for file changes. When you edit a file in your IDE on the host, the change is immediately visible inside the container — no rebuild required. This is the foundation of the "develop inside a container" workflow.

```yaml
services:
  app:
    image: node:20
    working_dir: /app
    command: npm run dev       # nodemon watches for changes
    volumes:
      - ./src:/app/src         # host source code → container
      - ./package.json:/app/package.json
      - node_modules:/app/node_modules  # named volume: don't overwrite node_modules
    ports:
      - "3000:3000"
```

**Host-visible output** — log files, generated reports, compiled artifacts that you need to read from the host. Mount a host directory for the container to write into; the files appear immediately on the host without `docker cp`.

**Host configuration files** — inject configuration files into the container that differ per environment or per developer:
```yaml
volumes:
  - ./config/local.env:/app/.env:ro   # developer-specific config
```

**Precise control over what is mounted** — bind mounts let you mount a single file, not just a directory. Mount only the nginx config file rather than an entire directory:
```yaml
- ./nginx.conf:/etc/nginx/nginx.conf:ro
```

**Q8. When should you use bind mounts?**
A: Bind mounts are the correct choice for:

**Local development only** — source code hot-reloading, config file injection, log inspection. In production, code and config are baked into the image; bind mounts are not used.

**Injecting host-specific files** — SSH keys, developer-specific credentials, local environment variables:
```yaml
volumes:
  - ~/.ssh:/root/.ssh:ro            # SSH keys for git operations inside container
  - /var/run/docker.sock:/var/run/docker.sock  # Docker socket for DinD (Docker-in-Docker)
```

**CI/CD artifact collection** — mount a host directory for the container to write test reports, coverage output, or build artifacts into. The CI runner picks up the files from the host path.

```yaml
# In CI: collect test results
docker run \
  --volume $(pwd)/test-results:/app/test-results \
  myapp:test
```

**When you need the container to modify host files** — a code formatter container that reads and writes source files on the host, a build container that writes compiled output to a host directory for deployment.

## Section 4: Key Differences and Trade-offs

**Q9. What are the key differences between named volumes and bind mounts?**
A:

| Aspect | Named Volume | Bind Mount |
|--- |--- |--- |
| Host path | Docker-managed (`/var/lib/docker/volumes/...`) | Explicit host path (`/home/user/project/`) |
| Portability | Fully portable (no host path assumption) | Requires matching host paths |
| Performance (macOS/Windows) | Fast (stays in Linux VM) | Slow (crosses VM boundary) |
| Initialization | Copies image data into empty volume | Empty host dir = empty container dir |
| Lifecycle management | `docker volume prune`, `docker volume rm` | Manual; Docker has no visibility |
| Volume drivers | Supported (NFS, EFS, cloud storage) | Not applicable (local filesystem only) |
| Use case | Persistent data; any environment | Dev hot-reload; host file injection |
| Compose syntax | `volume-name:/container/path` | `./host/path:/container/path` |

**Q10. What is the "node_modules problem" and how do volumes solve it?**
A: A classic Docker development pain point: you bind-mount your source code into a container for live reloading, but you also have a `node_modules` directory on the host. The bind mount overwrites the container's `node_modules` — which was compiled for the container's OS — with the host's `node_modules` — compiled for the host OS. On macOS, native Node.js add-ons (bcrypt, sharp, canvas) compiled for macOS cannot run inside a Linux container, causing cryptic import errors.

```
Problem scenario:
  Host:      ./node_modules/ (macOS native binaries)
  Bind mount: ./:/app
  Container sees: /app/node_modules/ with macOS binaries → crashes on Linux
```

**Solution: anonymous or named volume for node_modules.**
Mount the source code directory but override `node_modules` with a separate named volume:

```yaml
services:
  app:
    image: node:20-alpine
    working_dir: /app
    command: npm run dev
    volumes:
      - ./:/app                       # bind mount: source code from host
      - node_modules:/app/node_modules # named volume: OVERRIDES the bind mount for this path
    ports:
      - "3000:3000"

volumes:
  node_modules:
```

Docker evaluates volume mounts in order. The bind mount (`./:app`) mounts the entire source directory. The named volume (`node_modules:/app/node_modules`) then overrides just the `node_modules` subdirectory. The container's `node_modules` is populated by `npm ci` during the image build, stored in the named volume, and never overwritten by the host's `node_modules`. The host's `node_modules` (if it exists) is invisible inside the container.

This pattern applies to any build artifact directory: `vendor` (PHP Composer), `.venv` (Python), `target` (Rust), `_build` (Elixir), `dist` — any directory that contains platform-specific compiled artifacts.

**Q11. What happens when you bind-mount a host directory over a container directory that already has files?**
A: The bind mount completely shadows the container directory's contents. The container path shows only the host directory's contents — the image's files at that path are hidden (not deleted; they're in the image layer, just inaccessible while the mount is active).

```
Image has: /app/config/default.json (baked into the image during build)
Host has:  /home/user/project/config/ (empty directory)

After bind mount ./config:/app/config:
  Container sees: /app/config/ is EMPTY
  The image's default.json is hidden by the mount
```

This is the opposite of named volumes, which copy image data into an empty volume. Bind mounts shadow everything.

**Implication:** if your entrypoint script references a file that was in the image at the mounted path, and you bind-mount an empty host directory there, the file is gone from the container's perspective. This is a common source of confusing failures when first setting up development containers.

## Section 5: Advanced Patterns

**Q12. How do you share data between multiple containers?**
A: Two containers cannot mount the same bind mount path simultaneously unless the host directory is writable by both. Named volumes are the natural solution for inter-container data sharing:

```yaml
services:
  app:
    image: myapp
    volumes:
      - shared-uploads:/app/uploads   # app writes files here

  nginx:
    image: nginx:alpine
    volumes:
      - shared-uploads:/usr/share/nginx/html/uploads:ro  # nginx serves them read-only

volumes:
  shared-uploads:
```

Both containers mount the same named volume. Files written by `app` to `/app/uploads` are immediately visible to `nginx` at `/usr/share/nginx/html/uploads`. The `:ro` on nginx's mount ensures nginx cannot accidentally modify uploaded files.

**Alternative: `--volumes-from` (Docker CLI only):**
```bash
docker run --name data-container -v shared-data:/data busybox
docker run --volumes-from data-container app1   # inherits all volumes from data-container
docker run --volumes-from data-container app2
```

`--volumes-from` mounts all volumes from another container. Less explicit than declaring volumes in Compose; rarely used in modern setups.

**Q13. How do you back up and restore a named volume?**
A: Since Docker manages named volume contents in `/var/lib/docker/volumes/`, you cannot directly copy them on macOS or Windows (they're inside the Docker VM). The portable approach uses a temporary container to access the volume and stream data to/from the host:

```bash
# Backup: run a temporary container with the volume + host bind mount
# Tar the volume contents and write to the host
docker run --rm \
  --volume postgres-data:/source:ro \
  --volume $(pwd)/backups:/backup \
  alpine \
  tar czf /backup/postgres-data-$(date +%Y%m%d).tar.gz -C /source .

# Restore: untar from the host backup into the volume
docker run --rm \
  --volume postgres-data:/target \
  --volume $(pwd)/backups:/backup:ro \
  alpine \
  sh -c "cd /target && tar xzf /backup/postgres-data-20240723.tar.gz"
```

This pattern — a temporary `alpine` container with both the volume and a bind mount — bridges the gap between named volume data (inside Docker's management) and the host filesystem.

**For production database backups**, use database-native tools rather than volume-level backups: `pg_dump` for PostgreSQL, `mongodump` for MongoDB. These produce consistent backups (volume-level backup of a running database may capture an inconsistent state).

**Q14. What are volume drivers and when would you use them in production?**
A: Volume drivers extend the `docker volume create` interface to provision storage from non-local sources. The same `volume-name:/path` syntax works regardless of driver:

```bash
# Local driver (default)
docker volume create --driver local postgres-data

# NFS driver: mount a network filesystem
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=192.168.1.100,rw \
  --opt device=:/exports/data \
  nfs-data

# AWS EFS (via Docker plugin or Kubernetes CSI driver)
docker volume create \
  --driver amazon/efs \
  --opt efsId=fs-abc123 \
  efs-data
```

**Production use cases for volume drivers:**

**NFS volumes** — multiple containers on different hosts (Docker Swarm nodes) mount the same NFS share. Shared state across hosts without a dedicated distributed storage system. Appropriate for: shared config files, shared media uploads across stateless app replicas.

**AWS EFS (Elastic File System)** — in ECS or EKS, multiple tasks/pods on different EC2 instances mount the same EFS filesystem. EFS auto-scales, is multi-AZ, and integrates with IAM. Appropriate for: shared state between ECS tasks, ML model files shared across inference containers, WordPress media in a containerized CMS.

**Cloud block storage (AWS EBS, GCP Persistent Disk)** — a single container on a single host mounts a dedicated block device. Appropriate for: databases where only one instance writes at a time; higher IOPS than EFS; StatefulSets in Kubernetes.

In Kubernetes, this entire system is replaced by Persistent Volumes (PVs) and Persistent Volume Claims (PVCs), which are the Kubernetes-native abstraction over the same concepts. Volume drivers are more common in Docker Swarm or standalone Docker environments.

## Section 6: Security Considerations

**Q15. What are the security implications of bind mounts?**
A: Bind mounts are the most powerful and most dangerous Docker feature from a security perspective. A container with a bind mount to a sensitive host path can read or modify anything in that directory:

**Docker socket bind mount — extreme risk:**
```yaml
volumes:
  - /var/run/docker.sock:/var/run/docker.sock
```
This is commonly used for Docker-in-Docker (CI runners, container management tools). But a container with access to the Docker socket has full control over the Docker daemon — it can start, stop, or inspect any container on the host, read any volume, mount any host path, and effectively escape container isolation. Any vulnerability in the containerized application becomes a full host compromise. Alternatives: Docker-out-of-Docker (DooD) with careful socket permissions, or rootless Docker.

**Root directory bind mount — critical risk:**
```yaml
volumes:
  - /:/host         # mount the entire host filesystem
```
Seen in security tools (container scanners, backup agents) that legitimately need host access. A compromised container with this mount has full read/write access to the host OS, including `/etc/shadow`, SSH keys, and kernel modules.

**Principle of least privilege for bind mounts:**
- Always use `:ro` for configuration files, secrets, and certificates.
- Mount the narrowest possible scope — a specific file, not a whole directory.
- Never mount `/var/run/docker.sock` in production application containers; only in trusted infrastructure containers (CI runners, monitoring agents) with controlled access.
- Audit all bind mounts in Compose files and Kubernetes pod specs during code review.

**Named volume security:**
Named volumes are inherently more secure than bind mounts — they can only be accessed by containers that explicitly mount them, not by arbitrary host processes with filesystem access. However, Docker's volume directory (`/var/lib/docker/volumes/`) is owned by root and readable only by root on the host — still secure, but requires root access to read directly.

**Q16. How do file permission conflicts arise with bind mounts and how do you resolve them?**
A: Bind mounts expose a common pain point: the user inside the container may not have the same UID as the file owner on the host. Docker runs as root by default (UID 0 inside the container), but files on the host may be owned by a different UID. Conversely, running as a non-root user inside the container (best practice) may cause permission denied errors on bind-mounted files owned by root or another user.

**Scenario: container user UID ≠ host file owner UID**
```
Host: files in ./data owned by user aditya (UID 1000)
Container: runs as node user (UID 1000 in official node image) — works ✓

Host: files in ./data owned by root (UID 0)
Container: runs as node user (UID 1000) — permission denied ✗

Host: files in ./data owned by aditya (UID 1000)
Container: runs as root (UID 0) — can read all files, but creates files owned by root
           When the container writes files, host sees files owned by root
           Host user (aditya) cannot modify these files without sudo ✗
```

**Solutions:**

**Match UIDs explicitly:**
```dockerfile
# Dockerfile: create a user with a specific UID matching the host developer's UID
ARG UID=1000
RUN adduser --uid ${UID} --disabled-password appuser
USER appuser
```
```bash
# Pass your UID at build time
docker build --build-arg UID=$(id -u) -t myapp .
```

**`user` in Docker Compose:**
```yaml
services:
  app:
    image: myapp
    user: "${UID}:${GID}"   # run as the host user's UID:GID
    volumes:
      - ./:/app
```
```bash
UID=$(id -u) GID=$(id -g) docker compose up
```

**For development, run as root in the container (less secure but practical):**
Acceptable in ephemeral development containers where the container is not internet-facing and the surface area of "developer's laptop" is already trusted.

## Section 7: Scenario Questions

**Q17. "Your team is setting up a local development environment with a Node.js app, PostgreSQL, and Redis. Design the Docker Compose volume configuration."**
A: Each service has different storage requirements requiring different volume types:

```yaml
version: '3.9'

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev
    command: npm run dev
    ports:
      - "3000:3000"
    volumes:
      # Bind mount: source code for hot-reloading
      - ./src:/app/src
      - ./package.json:/app/package.json
      - ./tsconfig.json:/app/tsconfig.json
      # Named volume: node_modules (prevent macOS/Linux binary mismatch)
      - node_modules:/app/node_modules
    environment:
      - DATABASE_URL=postgres://myapp:secret@postgres:5432/myapp
      - REDIS_URL=redis://redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: myapp
      POSTGRES_PASSWORD: secret
    volumes:
      # Named volume: DB data must persist and needs fast I/O
      - postgres-data:/var/lib/postgresql/data
      # Bind mount: SQL init scripts (read-only; run on first start)
      - ./db/init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myapp"]
      interval: 5s
      timeout: 5s
      retries: 5
    ports:
      - "5432:5432"    # expose to host for DB GUI tools (TablePlus, DBeaver)

  redis:
    image: redis:7-alpine
    volumes:
      # Named volume: Redis RDB/AOF persistence
      - redis-data:/data
    command: redis-server --appendonly yes
    ports:
      - "6379:6379"

volumes:
  # Declare all named volumes
  node_modules:
  postgres-data:
  redis-data:
```

**Design decisions and rationale:**
- `src`, `package.json`, `tsconfig.json` → bind mounts (live editing on host).
- `node_modules` → named volume (prevents macOS binary incompatibility).
- `postgres-data` → named volume (performance on macOS; persistence; DB manages its own files).
- `db/init` → read-only bind mount (SQL files on host, executed once on first container start).
- `redis-data` → named volume (persistence for development state; AOF enabled for durability).
- PostgreSQL and Redis ports exposed to host — developers can connect from host tools like TablePlus or redis-cli without entering the container.

**Q18. "A developer on your team reports that their local Docker environment is slow — the Node.js app takes 30 seconds to start and file changes take 5 seconds to be detected. What is the likely cause and how do you fix it?"**
A: Both symptoms — slow startup and slow file change detection — are classic signs of bind mount performance problems on macOS (or Windows). The developer is almost certainly on macOS with Docker Desktop.

**Root cause:**
When you bind-mount source code on macOS, every filesystem operation (read, write, directory listing, file watch) crosses the Docker VM boundary. Node.js's `require()` on startup reads dozens of files from `node_modules` — each read is a cross-VM syscall. A module that loads in 200ms on Linux takes 3–5 seconds on macOS with a bind mount. File watchers (chokidar, fs.watch) poll across the VM boundary — detection latency multiplies.

**Diagnosis:**
```bash
# Time a simple Node.js startup inside the container
time docker compose exec app node -e "require('./node_modules/express')"
# If this takes > 1s, the bind mount is the bottleneck (native: < 100ms)
```

**Fixes in order of impact:**

**Fix 1: Named volume for `node_modules` (if not already done):**
```yaml
volumes:
  - ./:/app                         # bind mount for source code
  - node_modules:/app/node_modules  # named volume: eliminates the biggest I/O bottleneck
```
`node_modules` is the largest contributor to startup time because `require()` reads hundreds of files from it. Moving it to a named volume (inside the Linux VM) eliminates the cross-VM I/O for dependency loading.

**Fix 2: Use Docker Desktop's VirtioFS file sharing (macOS):**
Docker Desktop 4.6+ supports VirtioFS as the file sharing implementation, replacing the older gRPC-FUSE. VirtioFS is significantly faster for bind mounts — file change latency drops from 1–5 seconds to near-native. Enable in Docker Desktop → Settings → General → "VirtioFS".

**Fix 3: Sync-based tools for heavy bind mounts:**
For projects with many files where even VirtioFS is insufficient, use `mutagen` or Docker Desktop's built-in file sync. These tools maintain a copy of the source directory inside the VM, synced in the background. The container reads from the fast VM copy; changes on the host are synced asynchronously (millisecond latency for file detection).

**Fix 4: Mount only what changes:**
Instead of mounting the entire project root, mount only the directories that change during development:
```yaml
volumes:
  - ./src:/app/src              # only the source directory
  - node_modules:/app/node_modules
  # Don't mount: package.json, node_modules, .git, build/, dist/
```
Reduce the bind mount scope to reduce the surface area of cross-VM I/O.

**Q19. "You need to run a PostgreSQL container in production on an EC2 instance. How do you configure storage, and what happens if the container is replaced?"**
A: In production, containerized databases on a single EC2 instance use named volumes backed by the host's block storage:

```yaml
# Production docker-compose.yml (single-host, EC2)
version: '3.9'
services:
  postgres:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - postgres-data:/var/lib/postgresql/data
    # No port exposure: only accessible from other containers on this host
    # or via an SSH tunnel

volumes:
  postgres-data:
    driver: local

# Result: data stored at /var/lib/docker/volumes/postgres-data/_data on the EC2 instance
```

**What happens when the container is replaced:**
```
docker compose pull postgres      # pulls postgres:16 image update
docker compose up -d postgres     # stops old container, starts new one
  → New container mounts the SAME named volume (postgres-data)
  → PostgreSQL starts and finds its existing data files
  → All data is preserved ✓
```

The named volume is independent of the container. Docker creates a new container; the container mounts the existing named volume; PostgreSQL finds its data and starts normally. The container can be updated, recreated, or moved to a new image version — as long as it mounts the same named volume, data persists.

**Production concerns:**
- The EC2 instance itself is a single point of failure. If the instance is terminated, the data is lost (it's on instance storage, not EBS). Use an EBS volume mounted to the EC2 instance at `/var/lib/docker/volumes` — or better, use RDS and avoid containerizing databases in production entirely.
- Named volumes are not automatically backed up. Implement a backup job (a cron container using the `pg_dump` + bind-mount-to-S3 pattern).
- For production database workloads: use RDS or Aurora (managed), not a Docker container on EC2. The operational benefits of managed databases (automated backups, Multi-AZ, patching, monitoring) far outweigh the cost in all but the smallest deployments.

## Quick Reference

| Aspect | Named Volume | Bind Mount |
|--- |--- |--- |
| Syntax | `volume-name:/container/path` | `./host/path:/container/path` |
| Host location | Docker-managed (`/var/lib/docker/volumes/`) | Explicit host path |
| Portability | Fully portable | Requires matching host directory structure |
| macOS/Windows performance | Fast (stays in Linux VM) | Slow (crosses VM boundary for every I/O) |
| Empty volume behavior | Copies image data into volume | Shows empty if host dir is empty |
| Lifecycle | `docker volume rm`, `docker volume prune` | Manual; Docker has no visibility |
| Volume drivers | Supported (NFS, EFS, cloud) | Local filesystem only |
| Best for | Persistent data; databases; any env | Dev hot-reload; host file injection; CI artifacts |
| Security | More isolated | Can expose sensitive host paths |
| Read-only | Not typically | `:ro` suffix; use for config and certs |
| Inspect | `docker volume inspect name` | `ls /host/path` on host |

**Tip for the interview:** Docker volume questions at 5 YOE level usually come up in the context of setting up development environments or discussing stateful container deployments. Lead with the core distinction: named volumes are Docker-managed and portable (use for databases and any non-development environment); bind mounts expose the host filesystem (use for development hot-reloading and host file injection). The two details that separate senior answers: knowing that bind mounts on macOS/Windows cross the Docker VM boundary and cause significant I/O performance degradation (the "why is my dev container slow?" answer), and explaining the `node_modules` override pattern (bind mount the source directory but name-volume the `node_modules` subdirectory to prevent macOS/Linux binary conflicts). If asked about production: named volumes for data persistence, but the real answer for production databases is "use a managed service like RDS rather than containerizing the database" — that shows operational maturity beyond just knowing Docker syntax.
