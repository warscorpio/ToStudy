# Docker Compose: Service Dependencies, Environment Files, Health Checks, Resource Limits — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is Docker Compose and what problem does it solve?**
A: Docker Compose is a tool for defining and running multi-container Docker applications. A single `docker-compose.yml` file declares all the services (containers), networks, volumes, and configuration needed to run the full application stack — and a single `docker compose up` command starts everything.

The problem it solves: a real application is not one container. It is a web server, an application server, a database, a cache, a message queue, a background worker, and possibly more. Without Compose:

```bash
# Without Compose: manual and error-prone
docker network create myapp-network
docker volume create postgres-data

docker run -d \
  --name postgres \
  --network myapp-network \
  --volume postgres-data:/var/lib/postgresql/data \
  --env POSTGRES_PASSWORD=secret \
  postgres:16

docker run -d \
  --name redis \
  --network myapp-network \
  redis:7

docker run -d \
  --name app \
  --network myapp-network \
  --port 3000:3000 \
  --env DATABASE_URL=postgres://postgres:secret@postgres:5432/myapp \
  --env REDIS_URL=redis://redis:6379 \
  myapp:latest

# If anything changes, redo all of this manually
```

With Compose:
```bash
docker compose up -d    # starts everything correctly, every time
docker compose down     # stops and removes everything
docker compose logs -f  # tails all service logs
```

Compose also provides: automatic service discovery (containers in the same Compose project are on a shared network and resolve each other by service name), dependency ordering, health-check-aware startup, and environment variable management.

**Q2. What is the structure of a `docker-compose.yml` file?**
A: The file has four top-level sections:

```yaml
version: '3.9'     # Compose file format version (optional in modern Docker Compose)

services:          # each service is one container (or set of replicas)
  app:             # service name; also the DNS hostname within the Compose network
    image: ...
    build: ...
    ports: ...
    volumes: ...
    environment: ...
    depends_on: ...
    healthcheck: ...
    deploy: ...

networks:          # custom networks (optional; Compose creates a default network)
  backend:
  frontend:

volumes:           # named volumes (optional; required to declare volumes used by services)
  postgres-data:
  redis-data:

configs:           # external config files (Docker Swarm feature; rarely used in Compose)
secrets:           # external secrets (Docker Swarm; for local dev use env_file instead)
```

Every service in a Compose file is automatically placed on a default bridge network named `<project>_default` (where `<project>` is the directory name or `--project-name`). Services can reach each other using the service name as hostname — `postgres` resolves to the postgres container's IP on the shared network without any manual DNS configuration.

## Section 2: Service Dependencies

**Q3. What is `depends_on` and what does it guarantee?**
A: `depends_on` declares that one service must start before another. By default it only guarantees container start order — it does NOT wait for the service to be ready (accepting connections):

```yaml
services:
  app:
    image: myapp
    depends_on:
      - postgres   # basic: start postgres container before app container
      - redis

  postgres:
    image: postgres:16

  redis:
    image: redis:7
```

**The critical limitation of basic `depends_on`:** Docker starts the `postgres` container and immediately starts the `app` container. PostgreSQL takes several seconds to initialize — during this time, the app tries to connect and fails. The app may crash, retry successfully (if it has retry logic), or fail to start at all.

**The solution: `condition: service_healthy`** — wait until the dependency passes its health check before starting the dependent service:

```yaml
services:
  app:
    image: myapp
    depends_on:
      postgres:
        condition: service_healthy    # wait until postgres is healthy
      redis:
        condition: service_healthy    # wait until redis is healthy

  postgres:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3
```

With `condition: service_healthy`, Compose polls the health check of each dependency and only starts the dependent service once all dependencies report `healthy`. This correctly handles slow-starting dependencies.

**Q4. What are all the `depends_on` condition types?**
A: Three condition values, each waiting for a different state:

**`condition: service_started`** (default):
```yaml
depends_on:
  postgres:
    condition: service_started    # starts when postgres container is running
```
Waits only for the container to be in "running" state — the process has started. No readiness guarantee. Equivalent to basic `depends_on: [postgres]`. Use when the dependency has no health check and you accept the race condition risk.

**`condition: service_healthy`**:
```yaml
depends_on:
  postgres:
    condition: service_healthy    # starts when postgres passes its health check
```
Requires the dependency to have a `healthcheck` defined. Compose waits until `health_status == healthy`. Use for all databases, caches, and message queues — anything that takes time to initialize.

**`condition: service_completed_successfully`**:
```yaml
depends_on:
  db-migrations:
    condition: service_completed_successfully  # wait for migration to finish (exit 0)
  app:
    condition: service_started

services:
  db-migrations:
    image: myapp
    command: npm run migrate    # runs migrations then exits with code 0
  app:
    image: myapp
    command: npm start
```
Waits for the dependency container to exit with code 0. Use for one-shot initialization tasks: database migrations, seed data loading, schema creation. The migration container runs, completes, and exits; then the application starts. This is the correct pattern for migration-before-startup, avoiding the anti-pattern of running migrations inside the application's startup code.

**Q5. How do you handle circular dependencies and complex startup ordering?**
A: Docker Compose resolves dependencies topologically — each service starts after all its dependencies are healthy/started/completed. Circular dependencies (`A depends_on B, B depends_on A`) are rejected with an error at `docker compose up` time.

For complex real-world startup sequences:

```yaml
services:
  # 1. Infrastructure starts first (no dependencies)
  postgres:
    image: postgres:16
    healthcheck: { test: [...], interval: 5s, retries: 5 }

  redis:
    image: redis:7
    healthcheck: { test: [...], interval: 3s, retries: 5 }

  kafka:
    image: confluentinc/cp-kafka:7.6.0
    healthcheck:
      test: ["CMD-SHELL", "kafka-topics --bootstrap-server localhost:9092 --list"]
      interval: 10s
      retries: 10
      start_period: 30s

  # 2. Schema/migration runs after DB is healthy
  db-migrations:
    image: myapp:latest
    command: ["node", "scripts/migrate.js"]
    depends_on:
      postgres:
        condition: service_healthy

  # 3. Application starts after migration completes and all infra is healthy
  app:
    image: myapp:latest
    depends_on:
      db-migrations:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
      kafka:
        condition: service_healthy
    ports:
      - "3000:3000"

  # 4. Worker starts after app infrastructure is ready
  worker:
    image: myapp:latest
    command: ["node", "worker.js"]
    depends_on:
      db-migrations:
        condition: service_completed_successfully
      kafka:
        condition: service_healthy
```

Startup order guaranteed by this configuration:
1. `postgres`, `redis`, `kafka` start simultaneously (no dependencies).
2. `db-migrations` starts after `postgres` is healthy.
3. `app` and `worker` start after `db-migrations` exits successfully AND `redis`/`kafka` are healthy.

## Section 3: Environment Files

**Q6. What are the different ways to provide environment variables in Compose and when do you use each?**
A: Four mechanisms, each for different use cases:

**1. `environment` key (inline in Compose file):**
```yaml
services:
  app:
    environment:
      NODE_ENV: production
      PORT: "3000"
      LOG_LEVEL: info
```
Use for: non-sensitive values that are the same across all environments where this Compose file is used. Committed to version control. Not for secrets.

**2. `environment` with value from host:**
```yaml
services:
  app:
    environment:
      - AWS_ACCESS_KEY_ID       # no value: inherits from the host shell's environment
      - AWS_SECRET_ACCESS_KEY   # same: inherited from host
      - NODE_ENV=production      # has value: always this value regardless of host
```
Use for: developer-specific values or CI secrets that are set in the shell/CI environment. The variable is passed through from the host shell to the container. If the variable is not set in the host shell, the container sees an empty string (not an error).

**3. `env_file` (separate file):**
```yaml
services:
  app:
    env_file:
      - .env              # base environment
      - .env.local        # local overrides (gitignored)
      - .env.${COMPOSE_ENV:-development}  # environment-specific
```
The referenced files contain `KEY=VALUE` pairs:
```bash
# .env (committed to git — safe defaults, no secrets)
NODE_ENV=development
PORT=3000
LOG_LEVEL=debug
DATABASE_URL=postgres://myapp:dev_password@postgres:5432/myapp_dev

# .env.local (gitignored — developer-specific overrides)
LOG_LEVEL=trace
```
Use for: grouping related environment variables, environment-specific configuration files, separating committed defaults from gitignored secrets.

**4. Compose file variable substitution from the `.env` file:**
```yaml
# The .env file in the project root is automatically loaded by Compose
# to substitute variables in docker-compose.yml itself (not injected into containers)

services:
  app:
    image: myapp:${APP_VERSION:-latest}  # substituted from .env
    ports:
      - "${APP_PORT:-3000}:3000"
```
```bash
# .env (loaded by Compose itself)
APP_VERSION=1.4.2
APP_PORT=3000
POSTGRES_PASSWORD=dev_only_secret
```
This `.env` file is used for Compose file variable interpolation — it controls the Compose file itself (image tags, ports, resource limits) rather than injecting variables into containers. The distinction is subtle: `env_file` injects into containers; the project `.env` configures the Compose file.

**Q7. What is the `.env` file and what are best practices for managing it?**
A: The `.env` file in the same directory as `docker-compose.yml` is automatically loaded by Compose for variable substitution in the Compose file. It is distinct from env_file (which injects into containers).

**The three-file pattern for environment management:**

```bash
# .env.example (committed to git — template with all keys, no real values)
DATABASE_URL=postgres://myapp:CHANGEME@postgres:5432/myapp
REDIS_URL=redis://redis:6379
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
STRIPE_API_KEY=
NODE_ENV=development
LOG_LEVEL=info

# .env (gitignored — developer fills in from .env.example)
DATABASE_URL=postgres://myapp:mysecretpassword@postgres:5432/myapp
REDIS_URL=redis://redis:6379
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=abc123...
STRIPE_API_KEY=sk_test_...
NODE_ENV=development
LOG_LEVEL=debug

# docker-compose.override.yml (gitignored — developer-specific Compose overrides)
services:
  app:
    ports:
      - "9229:9229"    # Node.js debugger port for this developer only
```

**Gitignore rules:**
```
# .gitignore
.env
.env.local
.env.*.local
docker-compose.override.yml
```

**`.env.example` is always committed** — it documents all required environment variables, their format, and which are optional (with empty or default values). New team members copy it to `.env` and fill in their values. Without `.env.example`, new developers don't know what environment variables the application needs.

**Never commit `.env`** — it contains credentials, API keys, and developer-specific configuration. A committed `.env` file in a public repository is a security incident waiting to happen. GitHub secret scanning actively looks for this.

**Q8. How do you manage environment variables differently across environments (dev/staging/prod)?**
A: The key principle: the Compose file is environment-agnostic; environment-specific configuration comes from environment variables or separate files loaded at runtime.

**Pattern 1: Multiple env files loaded in order (overriding):**
```yaml
# docker-compose.yml (base; environment-agnostic)
services:
  app:
    image: myapp:${APP_VERSION}
    env_file:
      - .env.base          # committed: safe defaults
      - .env.${APP_ENV}    # environment-specific: .env.development, .env.staging
      - .env.local         # gitignored: developer overrides (optional)
```

```bash
# .env.base (committed — base configuration all environments share)
NODE_ENV=production
LOG_FORMAT=json
PORT=3000

# .env.development (committed — development overrides)
NODE_ENV=development
LOG_FORMAT=pretty
LOG_LEVEL=debug
DATABASE_URL=postgres://myapp:devpass@postgres:5432/myapp_dev

# .env.staging (committed — staging overrides; no real secrets)
DATABASE_URL=postgres://myapp:STAGING_DB_PASS@staging-db:5432/myapp
# STAGING_DB_PASS injected by CI/CD pipeline, not in this file

APP_ENV=staging docker compose up    # loads .env.staging
```

**Pattern 2: docker-compose.override.yml for development additions:**
```yaml
# docker-compose.yml (base; works in all environments)
services:
  app:
    image: myapp:latest
    ports:
      - "3000:3000"

# docker-compose.override.yml (gitignored; development-only additions)
# Automatically merged when running `docker compose up` locally
services:
  app:
    build:
      context: .             # in dev: build from source instead of pulling image
    volumes:
      - ./src:/app/src        # hot-reload in dev
    environment:
      NODE_ENV: development
    ports:
      - "9229:9229"           # debugger port in dev only
```

`docker-compose.override.yml` is automatically merged with `docker-compose.yml` when running `docker compose` commands. In production CI/CD, explicitly specify only the base file: `docker compose -f docker-compose.yml up`.

## Section 4: Health Checks

**Q9. What is a Docker health check and what are the configuration options?**
A: A Docker health check is a command that Docker runs periodically inside a running container to determine whether the container is healthy. The health status (`starting`, `healthy`, `unhealthy`) is used by Compose (for `depends_on condition: service_healthy`), Docker Swarm, and Kubernetes (when using Docker health checks) for routing decisions.

```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
  # or: test: ["CMD-SHELL", "pg_isready -U postgres"]
  # or: test: ["NONE"]  ← disables health check from image

  interval: 30s       # how often to run the check (default: 30s)
  timeout: 10s        # max time for the check to complete before counting as failed (default: 30s)
  retries: 3          # consecutive failures before marking UNHEALTHY (default: 3)
  start_period: 40s   # grace period after container start before failures count (default: 0s)
  start_interval: 5s  # how often to check during start_period (Compose v3.9+; default: 5s)
```

**`test` formats:**
- `["CMD", "executable", "arg1", "arg2"]` — run the executable directly; no shell interpretation; preferred.
- `["CMD-SHELL", "shell-command"]` — run via `/bin/sh -c`; allows pipes and shell features.
- `["NONE"]` — disables any health check defined in the base image.

**`start_period`** is the most important and most overlooked parameter. During `start_period`, health check failures do not count toward `retries` — the container is given time to initialize. After `start_period`, the check must succeed within `retries` consecutive attempts. Without `start_period`, a slow-starting service (JVM, large model loading) fails its health check during startup and is marked unhealthy before it has finished initializing.

```
Timeline for a slow-starting service:
  start_period: 60s, interval: 10s, retries: 3

  T=0:  Container starts
  T=5:  Health check runs → FAILS (app not ready) ← doesn't count (in start_period)
  T=15: Health check runs → FAILS ← doesn't count
  T=25: Health check runs → FAILS ← doesn't count
  ...
  T=60: start_period ends
  T=65: Health check runs → FAILS ← counts as failure 1/3
  T=70: App finishes starting
  T=75: Health check runs → PASSES ← resets failure count; status = healthy ✓
```

**Q10. What are practical health checks for common services?**
A:

**PostgreSQL:**
```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-postgres} -d ${POSTGRES_DB:-postgres}"]
  interval: 5s
  timeout: 5s
  retries: 5
  start_period: 10s
```
`pg_isready` is the correct tool — it checks that PostgreSQL is accepting connections, not just that the process is running.

**MySQL / MariaDB:**
```yaml
healthcheck:
  test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-p${MYSQL_ROOT_PASSWORD}"]
  interval: 5s
  timeout: 5s
  retries: 5
  start_period: 30s
```

**Redis:**
```yaml
healthcheck:
  test: ["CMD", "redis-cli", "ping"]
  interval: 5s
  timeout: 3s
  retries: 3
```
`redis-cli ping` returns `PONG` if Redis is accepting commands. If Redis requires a password: `redis-cli -a ${REDIS_PASSWORD} ping`.

**Elasticsearch:**
```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -sf http://localhost:9200/_cluster/health | grep -v '\"status\":\"red\"'"]
  interval: 10s
  timeout: 10s
  retries: 10
  start_period: 60s   # ES takes a long time to start
```
Checks cluster health and fails if status is `red`.

**Node.js / Express application:**
```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -sf http://localhost:3000/health/live || exit 1"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 20s
```
Use `curl -sf` — `-s` suppresses output (no noise in Docker logs), `-f` fails with non-zero exit on HTTP errors (4xx/5xx). Add `|| exit 1` to ensure non-zero exit on failure.

**RabbitMQ:**
```yaml
healthcheck:
  test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
  interval: 10s
  timeout: 10s
  retries: 5
  start_period: 30s
```

**Kafka:**
```yaml
healthcheck:
  test: ["CMD-SHELL", "kafka-topics.sh --bootstrap-server localhost:9092 --list > /dev/null 2>&1"]
  interval: 10s
  timeout: 10s
  retries: 10
  start_period: 30s
```

**Q11. What is `curl` not available in the container and how do you write health checks without it?**
A: Minimal base images (Alpine, distroless) often don't include `curl` or `wget`. Three solutions:

**Option 1: Use a native binary included in the image.**
Most database images include their own CLI tools: `pg_isready` (PostgreSQL), `redis-cli` (Redis), `mysql` (MySQL). Prefer these over `curl` for database health checks.

**Option 2: Use `wget` (available in Alpine by default).**
```yaml
healthcheck:
  test: ["CMD-SHELL", "wget -qO- http://localhost:3000/health || exit 1"]
```

**Option 3: Use `/proc/net/tcp` for TCP-only check (no HTTP tool needed).**
```yaml
# Check if port 3000 is listening (works in any Linux container)
healthcheck:
  test: ["CMD-SHELL",
    "cat /proc/net/tcp | awk '{print $2}' | grep -q $(printf '%04X' 3000) && exit 0 || exit 1"]
```
Brittle; only confirms the port is open, not that the application is responding correctly.

**Option 4: Add `curl` to the image or use a multi-stage build.**
```dockerfile
FROM node:20-alpine
RUN apk add --no-cache curl   # add curl to Alpine
```
Adding `curl` to an Alpine image adds ~2MB. Acceptable for development images.

**Option 5: Write a health check binary in the application language.**
```dockerfile
# healthcheck binary compiled into the container
COPY healthcheck.js /app/healthcheck.js
HEALTHCHECK CMD ["node", "/app/healthcheck.js"]
```
```javascript
// healthcheck.js
const http = require('http');
const options = { host: 'localhost', port: 3000, path: '/health', timeout: 2000 };
const req = http.request(options, res => {
  process.exit(res.statusCode === 200 ? 0 : 1);
});
req.on('error', () => process.exit(1));
req.on('timeout', () => process.exit(1));
req.end();
```
This adds no extra binaries; uses the same Node.js runtime already in the container.

## Section 5: Resource Limits

**Q12. Why should you set resource limits on containers and what happens without them?**
A: Without resource limits, a container can consume all available CPU and memory on the host, starving other containers. On a shared host:

```
Host: 8 CPUs, 16GB RAM
Running: postgres, redis, app, worker, nginx (5 containers)

Without limits:
  A memory leak in the app container consumes 14GB RAM
  → Redis gets OOM-killed by the kernel (lowest priority)
  → Database starts thrashing to disk (swapping)
  → System becomes unresponsive
  → All services affected by one container's bug

With limits:
  app container: memory limit = 512MB
  A memory leak hits 512MB → Docker OOM-kills ONLY the app container
  → Docker restarts the app (restart: unless-stopped)
  → Redis and postgres are completely unaffected
```

Resource limits also give you capacity planning: if you know each service's limits, you can calculate exactly how many containers a host can run, and you have guarantees about your services' minimum resource allocation.

**Q13. How do you configure resource limits and reservations in Docker Compose?**
A: Resource limits are configured under the `deploy` key for Compose files using the v3+ format:

```yaml
services:
  app:
    image: myapp:latest
    deploy:
      resources:
        limits:
          cpus: '1.0'         # max 1 CPU core (can use fractions: '0.5' = 50% of one core)
          memory: 512M        # max 512MB RAM; OOM-killed if exceeded
        reservations:
          cpus: '0.25'        # guaranteed minimum: 25% of one core
          memory: 128M        # guaranteed minimum: 128MB RAM

  postgres:
    image: postgres:16
    deploy:
      resources:
        limits:
          cpus: '2.0'
          memory: 2G
        reservations:
          cpus: '0.5'
          memory: 512M

  redis:
    image: redis:7
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 256M
        reservations:
          cpus: '0.1'
          memory: 64M
```

**Limits vs reservations:**
- **`limits`** — hard ceiling. If the container exceeds `memory`, the Linux OOM killer terminates the container process (Docker then restarts it if `restart: on-failure` or `restart: unless-stopped` is configured). If CPU usage exceeds `cpus`, the process is throttled (not killed).
- **`reservations`** — guaranteed minimum. Docker will not start a container if the host cannot provide at least this much. In Docker Swarm, the scheduler uses reservations for placement decisions. In standalone Docker Compose, reservations are tracked but don't prevent scheduling on an under-resourced host.

**Memory unit suffixes:**
- `b` — bytes.
- `k` or `K` — kilobytes.
- `m` or `M` — megabytes.
- `g` or `G` — gigabytes.
- `M` = 1,000,000 bytes (SI); `Mi` = 1,048,576 bytes (binary) — Docker accepts both.

**Q14. Does the `deploy` key work with `docker compose up` (non-Swarm)?**
A: This is a common source of confusion. In Docker Compose v2 (the modern `docker compose` CLI, not the old `docker-compose`):

- `deploy.resources` **is respected** by `docker compose up` — resource limits and reservations are applied to containers.
- Other `deploy` keys (`replicas`, `placement`, `update_config`, `rollback_config`) are **ignored** — they are Swarm-only and have no effect in standalone Compose.

```yaml
deploy:
  replicas: 3           # IGNORED in docker compose up (Swarm only)
  resources:
    limits:
      memory: 512M      # RESPECTED in docker compose up ✓
  update_config:        # IGNORED in docker compose up (Swarm only)
    parallelism: 1
  restart_policy:       # IGNORED — use top-level `restart` key instead
    condition: on-failure
```

For standalone Compose, use the top-level `restart` key (not inside `deploy`):
```yaml
services:
  app:
    restart: unless-stopped   # always restart unless manually stopped
    # restart: always         # restart unconditionally (even on docker compose stop — usually wrong)
    # restart: on-failure     # restart only on non-zero exit code
    # restart: no             # don't restart (default)
```

**Q15. How do you set CPU limits precisely and what do the values mean?**
A: CPU limits in Docker use the concept of CPU shares and quotas:

```yaml
cpus: '1.0'    # can use up to 1 full CPU core
cpus: '0.5'    # can use up to 50% of 1 CPU core
cpus: '2.5'    # can use up to 2.5 CPU cores (on an 8-core host)
cpus: '0.1'    # can use up to 10% of 1 CPU core (very constrained)
```

`cpus: '1.0'` does NOT pin the container to a specific core — it limits the total CPU time the container can use across all cores. A `cpus: '2.0'` container on an 8-core host can run at 25% utilization on each of 8 cores, or 100% on 2 cores, or any combination totaling 2 core-equivalents.

**CPU reservations vs limits for a shared host:**
```
Host: 4 CPUs

Service  cpus.limit  cpus.reservation
postgres    2.0           0.5
app         1.0           0.25
redis       0.5           0.1
nginx       0.5           0.1

Total limits:        4.0 CPUs  (= host capacity; cannot all be maxed simultaneously)
Total reservations:  0.95 CPUs (guaranteed minimum; leaves 3.05 CPUs for burst)
```

Setting limits to the total host capacity is the right approach: each service CAN use its limit, but when multiple services burst simultaneously, they share the available CPU proportional to their limits.

## Section 6: Complete Production-Ready Example

**Q16. What does a complete, production-ready `docker-compose.yml` look like for a typical web application stack?**
A: Combining all discussed features into a coherent configuration:

```yaml
version: '3.9'

# ─────────────────────────────────────────────────────────
# SERVICES
# ─────────────────────────────────────────────────────────
services:

  # ── PostgreSQL ──────────────────────────────────────────
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped

      interval: 30s
      timeout: 10s
      retries: 3
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 128M
    networks:
      - frontend

# NETWORKS
# ─────────────────────────────────────────────────────────
networks:
  backend:
    driver: bridge
    # postgres, redis, app, worker: all on backend network
    # postgres and redis are NOT on frontend; nginx cannot reach them directly
  frontend:
    driver: bridge
    # nginx and app: on frontend network
    # nginx can only reach app, not directly reach postgres/redis

# ─────────────────────────────────────────────────────────
# VOLUMES
# ─────────────────────────────────────────────────────────
volumes:
  postgres-data:
  redis-data:
  static-files:
```

**Design decisions in this configuration:**
- `${VAR:?error message}` syntax — Compose fails with an error if a required variable is not set.
- `${VAR:-default}` syntax — uses a default value if the variable is not set.
- Separate `backend` and `frontend` networks — nginx cannot accidentally reach postgres directly; network segmentation even within a single host.
- `restart: "no"` for `db-migrations` — a one-shot container that fails should not be automatically restarted (which could run migrations multiple times).
- `APP_VERSION` variable in image tags — enables `APP_VERSION=1.4.2 docker compose up` to deploy a specific version without editing the Compose file.

## Section 7: Scenario Questions

**Q17. "Your app container starts before PostgreSQL is ready and crashes. How do you fix this?"**
A: The root cause is `depends_on` without a health condition — the app starts as soon as the postgres container is running, before PostgreSQL has finished initializing. Three layers of fixes, applied together:

**Fix 1: Add health check to postgres and use `condition: service_healthy`.**

This is the correct Compose-native solution:

```yaml
services:
  postgres:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s   # grace period for postgres to start

  app:
    image: myapp
    depends_on:
      postgres:
        condition: service_healthy  # app waits until postgres is accepting connections
```

**Fix 2: Add connection retry logic in the application.**

Even with health-check-based depends_on, network conditions may cause transient failures after startup. The application should retry database connections:

```typescript
// Connection with retry (using pg with backoff)
async function connectWithRetry(maxAttempts = 10): Promise<Pool> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      const pool = new Pool({ connectionString: process.env.DATABASE_URL });
      await pool.query('SELECT 1');   // test the connection
      console.log('Database connected successfully');
      return pool;
    } catch (err) {
      if (attempt === maxAttempts) throw err;
      const delay = Math.min(1000 * Math.pow(2, attempt - 1), 30_000);
      console.log(`Database connection failed (attempt ${attempt}/${maxAttempts}); retrying in ${delay}ms`);
      await sleep(delay);
    }
  }
  throw new Error('Could not connect to database');
}
```

Both fixes together: Compose delays startup until postgres is healthy (eliminates the most common failure), and the app retries if a transient error occurs anyway (defense in depth).

**Fix 3 (legacy/alternative): `wait-for-it.sh` or `dockerize`.**
Before health checks were added to Compose, teams used wrapper scripts:
```yaml
command: ["./wait-for-it.sh", "postgres:5432", "--", "node", "server.js"]
```
These poll TCP connectivity rather than application-level health. Functional but inferior to health checks — they confirm the port is open, not that PostgreSQL is actually accepting queries. Avoid for new projects; use health checks instead.

**Q18. "How do you pass secrets to containers securely in Docker Compose without committing them to git?"**
A: Several approaches in increasing order of security:

**Approach 1: `.env` file (gitignored) — standard for local dev.**
```bash
# .env (gitignored)
POSTGRES_PASSWORD=supersecretpassword
STRIPE_API_KEY=sk_live_abc123
```
```yaml
services:
  app:
    env_file:
      - .env
```
The `.env` file is on the developer's machine only. In CI/CD, the CI system injects secrets as environment variables that override or supplement the `.env`. Never commit `.env`.

**Approach 2: Host environment variables (CI/CD).**
```yaml
services:
  app:
    environment:
      - POSTGRES_PASSWORD    # no value: inherited from the host shell/CI environment
      - STRIPE_API_KEY
```
In GitHub Actions:
```yaml
- name: Deploy
  env:
    POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }}
    STRIPE_API_KEY: ${{ secrets.STRIPE_API_KEY }}
  run: docker compose up -d
```
The host shell's environment variables are injected into the container. Secrets never touch the filesystem; they're in memory only.

**Approach 3: Docker Secrets (Swarm / production).**
Docker Secrets provides a secure in-memory filesystem at `/run/secrets/<secret-name>` inside the container. The application reads the secret from the file:
```yaml
services:
  app:
    secrets:
      - postgres_password
      - stripe_key

secrets:
  postgres_password:
    external: true    # created via: docker secret create postgres_password <(echo 'secret')
  stripe_key:
    file: ./secrets/stripe_key.txt   # loaded from a file (don't commit this file)
```
```typescript
// Application reads from the secrets filesystem
const password = fs.readFileSync('/run/secrets/postgres_password', 'utf8').trim();
```
Docker Secrets are encrypted at rest and in transit (Swarm). They're not shown in `docker inspect`, `docker logs`, or environment variable listings. This is the most secure option but requires Docker Swarm or Kubernetes for the `external: true` secrets.

**Approach 4: AWS Secrets Manager / HashiCorp Vault (production best practice).**
At runtime, the container fetches secrets from a secrets manager using IAM role-based authentication. No secrets in environment variables, files, or Compose configuration:
```typescript
const secretsManager = new SecretsManagerClient({});
const secret = await secretsManager.send(
  new GetSecretValueCommand({ SecretId: 'myapp/postgres/password' })
);
```
The EC2 instance or ECS task has an IAM role that permits `secretsmanager:GetSecretValue`. No secrets in the Docker image, Compose file, or environment — the most secure production approach.

**Q19. "You want to run integration tests in CI using Docker Compose. How do you structure it?"**
A: A reliable CI integration test setup using Docker Compose:

```yaml
# docker-compose.test.yml
version: '3.9'

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp_test
      POSTGRES_USER: myapp
      POSTGRES_PASSWORD: test_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myapp"]
      interval: 2s
      timeout: 2s
      retries: 10
      start_period: 5s

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 2s
      retries: 5

  db-migrations:
    image: myapp:${APP_VERSION:-latest}
    command: ["node", "scripts/migrate.js"]
    environment:
      DATABASE_URL: postgres://myapp:test_password@postgres:5432/myapp_test
    depends_on:
      postgres:
        condition: service_healthy
    restart: "no"

  test-runner:
    image: myapp:${APP_VERSION:-latest}
    command: ["npm", "run", "test:integration"]
    environment:
      DATABASE_URL: postgres://myapp:test_password@postgres:5432/myapp_test
      REDIS_URL: redis://redis:6379
      NODE_ENV: test
    depends_on:
      db-migrations:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
    # Mount test results directory for CI artifact collection
    volumes:
      - ./test-results:/app/test-results
```

**CI script (GitHub Actions):**
```yaml
- name: Run integration tests
  run: |
    docker compose -f docker-compose.test.yml up \
      --abort-on-container-exit \     # exit when any container exits
      --exit-code-from test-runner \  # use test-runner's exit code as the job exit code
      --timeout 120

- name: Collect test artifacts
  if: always()    # collect results even if tests failed
  uses: actions/upload-artifact@v3
  with:
    name: test-results
    path: test-results/

- name: Cleanup
  if: always()
  run: docker compose -f docker-compose.test.yml down --volumes
```

**Key CI patterns:**
- `--abort-on-container-exit` — the Compose process exits when any container exits. Without this, `docker compose up` would wait forever after the test-runner exits.
- `--exit-code-from test-runner` — the exit code of the entire `docker compose up` command mirrors the test runner's exit code. CI passes or fails based on the test results.
- `--timeout 120` — kill everything if it doesn't complete in 2 minutes (prevents hung CI jobs).
- `docker compose down --volumes` in an `always()` step — clean up volumes after every run to prevent test pollution between CI jobs.

## Quick Reference

| Feature | Syntax | Key detail |
|--- |--- |--- |
| Basic dependency | `depends_on: [service]` | Container start order only; no readiness wait |
| Healthy dependency | `depends_on: service: condition: service_healthy` | Requires health check on dependency |
| Completed dependency | `depends_on: service: condition: service_completed_successfully` | For one-shot init containers (migrations) |
| Inline env | `environment: KEY: value` | Committed to git; non-sensitive only |
| Host env passthrough | `environment: - KEY` (no value) | Inherits from host shell |
| Env file | `env_file: - .env` | Gitignored; developer secrets |
| Required variable | `${VAR:?error}` | Compose fails if VAR is not set |
| Variable with default | `${VAR:-default}` | Uses default if VAR is not set |
| Health check test | `["CMD", "executable", "args"]` or `["CMD-SHELL", "cmd"]` | CMD preferred; CMD-SHELL for pipes |
| start_period | `start_period: 30s` | Grace period; failures don't count |
| Memory limit | `deploy.resources.limits.memory: 512M` | OOM-kill if exceeded |
| CPU limit | `deploy.resources.limits.cpus: '1.0'` | Throttle (not kill) if exceeded |
| Reservation | `deploy.resources.reservations.*` | Guaranteed minimum |
| Restart policy | `restart: unless-stopped` | Top-level key (not in deploy) for standalone Compose |
| One-shot container | `restart: "no"` | Migrations, seed scripts |
| Network segmentation | Multiple networks in `networks:` | Services only see services on shared networks |
| CI exit code | `--exit-code-from service` | `docker compose up` inherits service exit code |

**Tip for the interview:** Docker Compose questions at 5 YOE level test whether you understand the operational reality of multi-container applications, not just the YAML syntax. Lead with the `depends_on` limitation — basic `depends_on` only waits for container start, not readiness, and every production setup needs `condition: service_healthy` with proper health checks. The specific details that separate senior answers: knowing that `start_period` is the most important and most overlooked health check parameter (prevents slow-starting services from being marked unhealthy during initialization), explaining `condition: service_completed_successfully` for database migrations (and why this beats running migrations in the application startup code), and the `.env.example` pattern for documenting required environment variables while keeping secrets out of git. If asked about CI: `--abort-on-container-exit` combined with `--exit-code-from test-runner` is the production pattern that makes Compose-based integration tests work correctly in CI pipelines.
