# Ingress and Ingress Controllers (Nginx) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is a Kubernetes Ingress and what problem does it solve?**
A: A Kubernetes Ingress is an API object that defines HTTP and HTTPS routing rules — mapping external requests to internal Services based on hostname, path, or both. It solves the problem of exposing multiple services through a single external entry point without creating a separate `LoadBalancer` Service for each one.

Without Ingress, exposing three services externally requires three cloud load balancers:
```
Internet → LoadBalancer ($0.025/hr) → user-service:80
Internet → LoadBalancer ($0.025/hr) → order-service:80
Internet → LoadBalancer ($0.025/hr) → payment-service:80
Total: 3 load balancers × $0.025/hr = $18/month just for LB cost
```

With Ingress, one load balancer routes to all three:
```
Internet → LoadBalancer ($0.025/hr) → Ingress Controller
                                          ├── api.example.com/users    → user-service:80
                                          ├── api.example.com/orders   → order-service:80
                                          └── api.example.com/payments → payment-service:80
Total: 1 load balancer = $18/month for all services
```

Beyond cost: Ingress centralizes TLS termination (one certificate for all services), rate limiting, authentication, CORS headers, and access logging — cross-cutting concerns that would otherwise be duplicated in every service or every `LoadBalancer` Service.

**Q2. What is the relationship between an Ingress resource and an Ingress Controller?**
A: An Ingress resource is a Kubernetes API object — a declaration of routing rules stored in etcd. It is inert on its own: creating an Ingress resource does nothing until an Ingress Controller reads it and acts on it.

An Ingress Controller is a pod (or set of pods) running inside the cluster that:
1. Watches the Kubernetes API for Ingress resources.
2. Translates Ingress rules into its native configuration (Nginx config, HAProxy config, Envoy routes, etc.).
3. Configures a running proxy (or IS the proxy) to route traffic according to those rules.
4. Provisions or updates the external load balancer (cloud LB, NodePort, HostPort) that directs traffic to the controller pods.

```
Kubernetes API Server
  │
  │  (watch for Ingress/Service/Endpoint changes)
  ▼
Ingress Controller Pod (nginx-ingress-controller)
  │
  │  (translates Ingress rules → nginx.conf)
  │  (reloads nginx without dropping connections)
  ▼
Nginx process (running inside the controller pod)
  │
  ├── routes api.example.com/users to user-service ClusterIP
  ├── routes api.example.com/orders to order-service ClusterIP
  └── terminates TLS; forwards HTTP to backends
```

The separation means Ingress resources are controller-agnostic declarations; the controller implements them. You can swap the controller (from Nginx to Traefik) without changing your Ingress resources (mostly — some annotations are controller-specific).

**Q3. What Ingress Controllers are available and how do you choose?**
A: The major options and their use cases:

**Nginx Ingress Controller (kubernetes/ingress-nginx)** — the most widely deployed. Nginx is the underlying proxy; the controller manages its config. Two flavors:
- `kubernetes/ingress-nginx` — community-maintained; open source; the de facto standard.
- `nginxinc/nginx-ingress` — NGINX Inc.'s commercial offering; supports NGINX Plus features (active health checks, session persistence, JWT validation natively).

**Traefik** — cloud-native; automatic service discovery; built-in Let's Encrypt integration; rich dashboard. Favored in environments where simplicity and automatic TLS outweigh Nginx's performance and feature set.

**AWS Load Balancer Controller** — creates AWS ALB or NLB resources directly from Ingress/Service objects. The load balancer is outside the cluster; no controller pods handling traffic. Correct choice for AWS EKS when you want AWS-native load balancing (AWS WAF integration, native SSL certificates from ACM, better integration with AWS security groups).

**Istio Gateway / Envoy-based** — when you already have a service mesh; the mesh's gateway handles ingress traffic with full mTLS, traffic shaping, and observability.

**Choosing at 5 YOE level:** `ingress-nginx` for general Kubernetes; AWS Load Balancer Controller for EKS (AWS-native features); Traefik for simplicity or automatic cert management in smaller clusters.

## Section 2: Ingress Resource Specification

**Q4. What is the structure of an Ingress resource?**
A: The core structure with all major fields:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  namespace: production
  annotations:
    # Controller-specific configuration goes here
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx          # which controller handles this Ingress
  tls:
    - hosts:
        - api.example.com
      secretName: api-tls-secret   # Secret containing tls.crt and tls.key
  rules:
    - host: api.example.com        # hostname matching (omit for wildcard)
      http:
        paths:
          - path: /users
            pathType: Prefix       # Prefix | Exact | ImplementationSpecific
            backend:
              service:
                name: user-service
                port:
                  number: 80
          - path: /orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
          - path: /                # catch-all: must be last (most specific first)
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```

**`ingressClassName`** — specifies which Ingress Controller should handle this resource. Required in modern Kubernetes (1.18+). Previously, controllers used annotations (`kubernetes.io/ingress.class: nginx`). Without this field, the resource may be ignored by all controllers or claimed by all of them (undesired).

**`pathType` values:**
- `Exact` — the path must match exactly: `/users` matches `/users` only, not `/users/42`.
- `Prefix` — path prefix match: `/users` matches `/users`, `/users/42`, `/users/42/orders`.
- `ImplementationSpecific` — the controller decides the matching semantics (often Nginx's regex).

**Q5. How does Nginx Ingress path routing work and what are common routing patterns?**
A: Nginx Ingress evaluates rules in order: most specific path first, then by order in the spec. Path matching depends on `pathType` and any `rewrite-target` annotation.

**Host-based routing (virtual hosting):**
```yaml
# Route based on subdomain — different hosts to different services
rules:
  - host: api.example.com
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service: { name: api-service, port: { number: 80 } }

  - host: admin.example.com
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service: { name: admin-service, port: { number: 80 } }

  - host: "*.example.com"         # wildcard: any subdomain not matched above
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service: { name: default-service, port: { number: 80 } }
```

**Path-based routing with URL rewriting:**
```yaml
# Strip the path prefix before forwarding to backend
# External: api.example.com/users/42  → Internal: user-service/42
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2   # capture group $2 from path regex

spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /users(/|$)(.*)     # regex: captures the rest of the path as $2
            pathType: ImplementationSpecific
            backend:
              service: { name: user-service, port: { number: 80 } }
          - path: /orders(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service: { name: order-service, port: { number: 80 } }
```

With `rewrite-target: /$2`:
- Request `/users/42/profile` → `user-service` receives `/42/profile`
- Request `/orders` → `order-service` receives `/`
- Request `/orders/` → `order-service` receives `/`

Without rewriting, `order-service` would receive `/orders/123` — which it may not have a route for if it's internally organized around `/123`.

**Default backend:**
```yaml
spec:
  defaultBackend:           # handles all requests that don't match any rule
    service:
      name: 404-service
      port:
        number: 80
```

## Section 3: TLS and SSL Termination

**Q6. How does TLS termination work with Nginx Ingress?**
A: TLS termination means the Ingress Controller decrypts HTTPS traffic and forwards plain HTTP to backend Services. Backends don't need TLS certificates; the controller handles the encryption layer.

```
Client                    Ingress Controller           Backend Service
  │                            │                            │
  │── HTTPS (encrypted) ──────►│                            │
  │   TLS certificate served   │  (terminate TLS here)      │
  │   by Nginx Ingress         │                            │
  │                            │── HTTP (plaintext) ────────►│
  │                            │   (internal cluster         │
  │                            │    traffic; trusted network)│
```

**Configuring TLS in Ingress:**
```yaml
spec:
  tls:
    - hosts:
        - api.example.com
        - admin.example.com
      secretName: api-tls-secret     # one Secret can cover multiple hosts (SAN cert)
    - hosts:
        - internal.example.com
      secretName: internal-tls-secret

  rules:
    - host: api.example.com
      ...
```

**Creating the TLS Secret:**
```bash
# From existing certificate files
kubectl create secret tls api-tls-secret \
  --cert=path/to/api.example.com.crt \
  --key=path/to/api.example.com.key \
  --namespace production

# The Secret contains:
# data:
#   tls.crt: <base64 encoded certificate chain>
#   tls.key: <base64 encoded private key>
```

**Automatic HTTP → HTTPS redirect:**
```yaml
annotations:
  nginx.ingress.kubernetes.io/ssl-redirect: "true"      # redirect HTTP to HTTPS (default: true when TLS configured)
  nginx.ingress.kubernetes.io/force-ssl-redirect: "true" # even if behind another proxy
```

**Q7. How do you use cert-manager with Nginx Ingress for automatic certificate management?**
A: cert-manager is a Kubernetes controller that automatically provisions and renews TLS certificates from Let's Encrypt (or other CAs). Combined with Nginx Ingress, it provides zero-configuration HTTPS:

```bash
# Install cert-manager
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.14.0/cert-manager.yaml
```

```yaml
# ClusterIssuer: defines how cert-manager obtains certificates
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@example.com
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
      - http01:                      # HTTP-01 challenge: Let's Encrypt verifies ownership via HTTP
          ingress:
            class: nginx
      # Alternative: DNS-01 challenge (for wildcard certs, private clusters)
      # - dns01:
      #     cloudflare:
      #       apiTokenSecretRef:
      #         name: cloudflare-api-token-secret
      #         key: api-token
```

```yaml
# Ingress with cert-manager annotation
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # ← cert-manager watches this
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.example.com
      secretName: api-tls-cert      # cert-manager creates and populates this Secret
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: api-service, port: { number: 80 } }
```

cert-manager sees the `cert-manager.io/cluster-issuer` annotation, creates a `Certificate` resource, completes the ACME HTTP-01 challenge (Nginx Ingress automatically serves the challenge response), stores the certificate in `api-tls-cert`, and renews it automatically 30 days before expiry. The entire lifecycle requires zero manual certificate management.

## Section 4: Nginx Ingress Controller Installation and Configuration

**Q8. How do you install and configure the Nginx Ingress Controller?**
A: The recommended installation method is Helm:

```bash
# Add the ingress-nginx Helm chart repository
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update

# Install in its own namespace with production-appropriate settings
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace \
  --set controller.replicaCount=2 \                        # HA: 2 replicas
  --set controller.nodeSelector."kubernetes\.io/os"=linux \
  --set controller.service.type=LoadBalancer \             # creates cloud LB
  --set controller.metrics.enabled=true \                  # Prometheus metrics
  --set controller.podDisruptionBudget.enabled=true        # PDB for safe rolling updates
```

**Full Helm values for production:**
```yaml
# values-production.yaml
controller:
  replicaCount: 2

  # Resource limits
  resources:
    requests:
      cpu: 100m
      memory: 90Mi
    limits:
      cpu: "1"
      memory: 512Mi

  # Pod anti-affinity: spread replicas across nodes
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app.kubernetes.io/name
                operator: In
                values: [ingress-nginx]
          topologyKey: kubernetes.io/hostname

  # PodDisruptionBudget: keep at least 1 replica during node drains
  podDisruptionBudget:
    enabled: true
    minAvailable: 1

  # Prometheus metrics endpoint
  metrics:
    enabled: true
    service:
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "10254"

  # ConfigMap for global Nginx settings
  config:
    use-forwarded-headers: "true"           # trust X-Forwarded-For from upstream LB
    compute-full-forwarded-for: "true"      # build full IP chain
    use-gzip: "true"                        # enable response compression
    gzip-level: "5"
    keep-alive: "75"                        # keepalive timeout in seconds
    proxy-body-size: "50m"                  # max request body size (override per-ingress with annotation)
    proxy-connect-timeout: "10"             # seconds to connect to backend
    proxy-read-timeout: "60"               # seconds to wait for backend response
    proxy-send-timeout: "60"
    ssl-protocols: "TLSv1.2 TLSv1.3"      # disable TLS 1.0 and 1.1
    ssl-ciphers: "ECDHE-ECDSA-AES128-GCM-SHA256:..."  # modern cipher suite

  service:
    type: LoadBalancer
    annotations:
      # AWS: use NLB instead of CLB (better performance)
      service.beta.kubernetes.io/aws-load-balancer-type: nlb
      service.beta.kubernetes.io/aws-load-balancer-cross-zone-load-balancing-enabled: "true"
```

**Q9. What are the most important Nginx Ingress annotations?**
A: Annotations extend the Ingress resource with controller-specific behavior. Key ones for Nginx:

**Rate limiting:**
```yaml
annotations:
  nginx.ingress.kubernetes.io/limit-rps: "100"            # 100 req/second per source IP
  nginx.ingress.kubernetes.io/limit-connections: "10"     # max 10 simultaneous connections per IP
  nginx.ingress.kubernetes.io/limit-rpm: "600"            # 600 req/minute per source IP
  # On limit exceeded: returns 429 Too Many Requests
```

**Request/response configuration:**
```yaml
annotations:
  nginx.ingress.kubernetes.io/proxy-body-size: "100m"     # max upload size for this route
  nginx.ingress.kubernetes.io/proxy-read-timeout: "120"   # 120s read timeout (override global)
  nginx.ingress.kubernetes.io/proxy-connect-timeout: "5"
  nginx.ingress.kubernetes.io/proxy-send-timeout: "120"
```

**Authentication:**
```yaml
annotations:
  # Basic auth
  nginx.ingress.kubernetes.io/auth-type: basic
  nginx.ingress.kubernetes.io/auth-secret: basic-auth-secret   # Secret with htpasswd data
  nginx.ingress.kubernetes.io/auth-realm: "Protected Area"

  # OAuth2 via external auth service
  nginx.ingress.kubernetes.io/auth-url: "https://oauth2-proxy.example.com/oauth2/auth"
  nginx.ingress.kubernetes.io/auth-signin: "https://oauth2-proxy.example.com/oauth2/start"
```

**CORS:**
```yaml
annotations:
  nginx.ingress.kubernetes.io/enable-cors: "true"
  nginx.ingress.kubernetes.io/cors-allow-origin: "https://app.example.com"
  nginx.ingress.kubernetes.io/cors-allow-methods: "GET, POST, PUT, DELETE, OPTIONS"
  nginx.ingress.kubernetes.io/cors-allow-headers: "Authorization, Content-Type"
  nginx.ingress.kubernetes.io/cors-allow-credentials: "true"
  nginx.ingress.kubernetes.io/cors-max-age: "86400"
```

**Canary routing:**
```yaml
# Main Ingress: routes to stable service
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress-stable
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: api-service-v1, port: { number: 80 } }
---
# Canary Ingress: routes 10% of traffic to new version
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"   # 10% of traffic to v2
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: api-service-v2, port: { number: 80 } }
```

Other canary strategies:
```yaml
# Route based on header (for testing specific users)
nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
nginx.ingress.kubernetes.io/canary-by-header-value: "true"

# Route based on cookie (for A/B test session stickiness)
nginx.ingress.kubernetes.io/canary-by-cookie: "canary-cookie"
```

**Custom Nginx configuration (snippet):**
```yaml
annotations:
  nginx.ingress.kubernetes.io/configuration-snippet: |
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    more_set_headers "X-Robots-Tag: noindex";
```

## Section 5: Traffic Flow and Networking

**Q10. How does traffic flow from the internet to a pod through Nginx Ingress?**
A: End-to-end traffic flow through a complete stack:

```
Internet (client browser)
  │
  │  DNS: api.example.com → 52.1.2.3 (cloud load balancer IP)
  ▼
Cloud Load Balancer (AWS NLB / GCP LB / Azure LB)
  │  Layer 4: TCP passthrough to controller pods
  │  Distributes across Nginx Ingress Controller pods
  ▼
Nginx Ingress Controller Pod (port 443)
  │  1. TLS termination: decrypts HTTPS
  │  2. Host matching: api.example.com → this Ingress
  │  3. Path matching: /users/42 → Prefix /users
  │  4. Backend resolution: user-service → ClusterIP 10.96.1.50:80
  │  5. Load balancing: select an endpoint (pod IP) from the Endpoints
  │     (Nginx uses its own upstream balancing, not kube-proxy)
  ▼
user-service Pod (10.244.2.15:8080)
  │  Receives plain HTTP with headers:
  │    X-Forwarded-For: client IP
  │    X-Forwarded-Proto: https
  │    X-Real-IP: client IP
  │    Host: api.example.com
  ▼
Response returned through same path
```

**Key detail:** Nginx Ingress communicates directly with pod IPs (via the Endpoints API), bypassing kube-proxy and iptables rules. This is more efficient than going through the Service's ClusterIP. The controller watches the Endpoints object for each backend Service and maintains an upstream pool of ready pod IPs — when a pod is added or removed, Nginx updates its upstream list without a full configuration reload.

**Q11. What happens during a Nginx configuration reload and how are live connections handled?**
A: When an Ingress resource changes (new rule added, annotation updated, backend pod list changes), the Nginx Ingress Controller must reload Nginx's configuration. Nginx's reload is graceful:

```
1. Controller detects Ingress/Endpoint change
2. Controller generates new nginx.conf from current state
3. Controller validates the new config (nginx -t)
4. Controller sends SIGHUP to the master Nginx process
5. Nginx master starts new worker processes with the new config
6. Nginx master sends SIGQUIT to old worker processes
7. Old workers finish processing in-flight requests then exit
8. New requests go to new worker processes

Total reload time: ~100ms
In-flight requests: completed by old workers (zero dropped)
```

**Endpoint changes (pod added/removed) do NOT require a full nginx reload** in modern versions — they use Lua-based dynamic upstream updates. When a pod becomes ready or terminates, the controller updates Nginx's upstream pool via the Lua API without reloading the entire configuration. This is critical for autoscaling scenarios where pods are constantly being added and removed.

## Section 6: IngressClass

**Q12. What is an IngressClass and why does it matter?**
A: An IngressClass is a Kubernetes resource that represents a class of Ingress Controller. It allows multiple Ingress Controllers to run in the same cluster, each responsible for only the Ingress resources that reference its class.

```yaml
# IngressClass resource (usually created by the controller's Helm chart)
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: nginx
  annotations:
    ingressclass.kubernetes.io/is-default-class: "true"  # make this the default
spec:
  controller: k8s.io/ingress-nginx
```

```yaml
# Ingress references the class by name
spec:
  ingressClassName: nginx      # this Ingress is handled by the 'nginx' IngressClass
```

**Multiple controllers in one cluster:**
```
Cluster running:
  - ingress-nginx (IngressClass: nginx)  ← handles most applications
  - aws-load-balancer-controller (IngressClass: alb) ← handles specific services needing ALB features

Ingress A: ingressClassName: nginx  → handled by nginx controller
Ingress B: ingressClassName: alb    → handled by AWS LB controller; creates an ALB
```

**Default IngressClass:** when `ingressclass.kubernetes.io/is-default-class: "true"` is set, any Ingress without an explicit `ingressClassName` is handled by this controller. Only one IngressClass should be the default in a cluster.

## Section 7: Observability and Troubleshooting

**Q13. What metrics does Nginx Ingress expose and how do you monitor it?**
A: Nginx Ingress Controller exposes Prometheus metrics on port 10254 at `/metrics`. Key metrics:

```
# Request rate per ingress
nginx_ingress_controller_requests{ingress="api-ingress", namespace="production", status="200"}

# Request latency histogram
nginx_ingress_controller_request_duration_seconds_bucket{ingress="api-ingress", le="0.1"}

# Upstream response time
nginx_ingress_controller_response_duration_seconds_bucket{ingress="api-ingress", le="0.5"}

# SSL certificate expiry (days until expiry)
nginx_ingress_controller_ssl_expire_time_seconds{host="api.example.com"}
# Alert if (value - time()) / 86400 < 30 → cert expires in less than 30 days

# Config reloads
nginx_ingress_controller_config_last_reload_successful
nginx_ingress_controller_config_last_reload_successful_timestamp_seconds

# Connection counts
nginx_ingress_controller_nginx_process_connections{state="active"}
```

**Alerting rules (Prometheus):**
```yaml
groups:
  - name: nginx-ingress
    rules:
      - alert: NginxIngressHighErrorRate
        expr: |
          sum(rate(nginx_ingress_controller_requests{status=~"5.."}[5m]))
          /
          sum(rate(nginx_ingress_controller_requests[5m])) > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Nginx Ingress 5xx error rate > 5%"

      - alert: NginxIngressCertExpiringSoon
        expr: |
          (nginx_ingress_controller_ssl_expire_time_seconds - time()) / 86400 < 30
        labels:
          severity: warning
        annotations:
          summary: "SSL certificate for {{ $labels.host }} expires in {{ $value | humanizeDuration }}"

      - alert: NginxIngressHighLatency
        expr: |
          histogram_quantile(0.99,
            sum(rate(nginx_ingress_controller_request_duration_seconds_bucket[5m]))
            by (ingress, le)
          ) > 2
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "P99 latency > 2s for ingress {{ $labels.ingress }}"

      - alert: NginxConfigReloadFailed
        expr: nginx_ingress_controller_config_last_reload_successful == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Nginx Ingress config reload has been failing for 2 minutes"
```

**Q14. How do you troubleshoot a request that isn't routing correctly?**
A: Systematic diagnosis for routing failures:

**Step 1: Check the Ingress resource.**
```bash
kubectl describe ingress api-ingress -n production

# Look for:
# Events: showing if the controller acknowledged the Ingress
# Spec: confirm the rules are correct
# TLS: confirm the secret name matches
```

**Step 2: Verify the IngressClass.**
```bash
kubectl get ingressclass
# NAME    CONTROLLER             PARAMETERS   AGE
# nginx   k8s.io/ingress-nginx   <none>       30d

kubectl get ingress api-ingress -n production -o jsonpath='{.spec.ingressClassName}'
# Should output: nginx
```

**Step 3: Check controller logs.**
```bash
kubectl logs -n ingress-nginx \
  -l app.kubernetes.io/name=ingress-nginx \
  --tail=100 -f

# Look for:
# "Updating ingress api-ingress" ← controller saw the Ingress
# "Error obtaining Endpoints for service user-service" ← backend issue
# "SSL certificate not found" ← TLS Secret missing
```

**Step 4: Check the generated Nginx config.**
```bash
# Exec into the controller pod
kubectl exec -n ingress-nginx \
  $(kubectl get pod -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx -o jsonpath='{.items[0].metadata.name}') \
  -- cat /etc/nginx/nginx.conf | grep -A 20 "api.example.com"

# Verify the upstream servers (pod IPs) are present
# Verify the location blocks match expected paths
```

**Step 5: Check backend Services and Endpoints.**
```bash
# Is the Service correct?
kubectl get service user-service -n production

# Do Endpoints exist? (if empty, no pods are ready)
kubectl get endpoints user-service -n production

```

## Section 8: Scenario Questions

**Q15. "You have three services: a React frontend, a REST API, and a GraphQL API. Design the Ingress configuration."**
A: Complete multi-service Ingress with host and path routing:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/use-regex: "true"

    # Security headers on all responses
    nginx.ingress.kubernetes.io/configuration-snippet: |
      add_header X-Frame-Options "SAMEORIGIN" always;
      add_header X-Content-Type-Options "nosniff" always;
      add_header X-XSS-Protection "1; mode=block" always;
      add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # Rate limiting: protect APIs from abuse
    nginx.ingress.kubernetes.io/limit-rps: "100"

    cert-manager.io/cluster-issuer: letsencrypt-prod

spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - example.com
        - api.example.com
        - graphql.example.com
      secretName: example-com-tls

  rules:
    # Frontend: example.com → React SPA
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

    # REST API: api.example.com → API service
    - host: api.example.com
      http:
        paths:
          - path: /v1
            pathType: Prefix
            backend:
              service:
                name: rest-api-service
                port:
                  number: 80
          - path: /v2
            pathType: Prefix
            backend:
              service:
                name: rest-api-v2-service     # different version on different path
                port:
                  number: 80
          - path: /health
            pathType: Exact
            backend:
              service:
                name: rest-api-service
                port:
                  number: 80

    # GraphQL: graphql.example.com → GraphQL service
    # Separate host: GraphQL needs different timeout (long-running subscriptions)
    - host: graphql.example.com
      http:
        paths:
          - path: /graphql
            pathType: Exact
            backend:
              service:
                name: graphql-service
                port:
                  number: 4000
          - path: /subscriptions     # WebSocket for GraphQL subscriptions
            pathType: Prefix
            backend:
              service:
                name: graphql-service
                port:
                  number: 4000
---
# Separate Ingress for GraphQL: needs longer timeouts for subscriptions
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: graphql-ws-ingress
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/proxy-read-timeout: "3600"     # 1 hour for subscriptions
    nginx.ingress.kubernetes.io/proxy-send-timeout: "3600"
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"
    nginx.ingress.kubernetes.io/upstream-hash-by: "$http_upgrade $connection_upgrade"
spec:
  ingressClassName: nginx
  tls:
    - hosts: [graphql.example.com]
      secretName: example-com-tls
  rules:
    - host: graphql.example.com
      http:
        paths:
          - path: /subscriptions
            pathType: Prefix
            backend:
              service:
                name: graphql-service
                port:
                  number: 4000
```

The GraphQL subscriptions need a separate Ingress because WebSocket connections (long-lived) need extended timeouts that would be inappropriate for the REST API (where long-running connections might indicate hung requests).

**Q16. "Your Nginx Ingress is serving 10,000 RPS and showing elevated P99 latency. How do you diagnose and tune it?"**
A: Systematic performance investigation:

**Step 1: Identify the bottleneck layer.**
```bash
# Check Nginx Ingress P99 request duration (end-to-end including upstream)
# vs upstream response time (backend only)
# Large gap = Nginx overhead; Small gap = backend is slow

# Prometheus query:
histogram_quantile(0.99, sum(rate(
  nginx_ingress_controller_request_duration_seconds_bucket[5m])) by (le, ingress))
# vs:
histogram_quantile(0.99, sum(rate(
  nginx_ingress_controller_response_duration_seconds_bucket[5m])) by (le, ingress))
```

If `request_duration p99 >> response_duration p99`, the bottleneck is Nginx itself (queuing, SSL overhead). If they're similar, the backend is slow.

**Step 2: Check Nginx worker and connection metrics.**
```bash
nginx_ingress_controller_nginx_process_connections{state="waiting"}   # idle keepalive connections
nginx_ingress_controller_nginx_process_connections{state="active"}    # active requests
nginx_ingress_controller_nginx_process_connections{state="reading"}   # reading request
nginx_ingress_controller_nginx_process_connections{state="writing"}   # sending response
```

If `active` connections are near `worker_connections` limit (default: 16384), Nginx is saturated.

**Step 3: Tune Nginx worker configuration (via ConfigMap).**
```yaml
# ingress-nginx ConfigMap tuning
data:
  # Worker processes (default: auto = number of CPUs)
  worker-processes: "auto"

  # Max connections per worker process
  max-worker-connections: "16384"

  # Enable keepalive to backends (dramatically reduces connection overhead)
  upstream-keepalive-connections: "200"    # keep 200 connections open to each upstream
  upstream-keepalive-requests: "10000"     # requests per keepalive connection
  upstream-keepalive-timeout: "60"         # seconds to keep idle upstream connections

  # Enable HTTP/2 for clients (multiplexes many requests over one connection)
  use-http2: "true"

  # Tuned buffer sizes for large response headers (avoid disk I/O for headers)
  proxy-buffer-size: "16k"
  proxy-buffers-number: "4"

  # Reduce SSL handshake overhead with session caching
  ssl-session-cache: "shared:SSL:10m"
  ssl-session-timeout: "10m"
  ssl-session-tickets: "true"
```

**Step 4: Scale the Ingress Controller horizontally.**
```bash
kubectl scale deployment ingress-nginx-controller \
  -n ingress-nginx \
  --replicas=4    # more controller pods = more Nginx processes = more throughput

# Or configure HPA:
kubectl autoscale deployment ingress-nginx-controller \
  -n ingress-nginx \
  --cpu-percent=70 \
  --min=2 \
  --max=10
```

**Step 5: Check for excessive config reloads.**
```bash
# High reload count = Endpoints changing frequently (pods scaling up/down)
# Each reload is ~100ms of elevated latency
nginx_ingress_controller_config_last_reload_successful_timestamp_seconds
# Check the rate: if reloading every few seconds, investigate pod churn
```

## Quick Reference

| Concept | Definition | Key detail |
|--- |--- |--- |
| Ingress resource | K8s object declaring routing rules | Inert without a controller |
| Ingress Controller | Pod implementing Ingress rules | Nginx, Traefik, ALB — you choose |
| IngressClass | Links Ingress resources to a controller | Required in K8s 1.18+; one default per cluster |
| `pathType: Prefix` | Prefix path matching | `/users` matches `/users`, `/users/42` |
| `pathType: Exact` | Exact path match only | `/users` matches `/users` ONLY |
| `rewrite-target` | Strip/rewrite path before forwarding | Use `$2` capture group with regex path |
| TLS termination | Decrypt HTTPS at controller; forward HTTP | Cert in Secret (`tls.crt`, `tls.key`) |
| cert-manager | Auto-provision Let's Encrypt certs | `cert-manager.io/cluster-issuer` annotation |
| Canary routing | Split traffic by weight/header/cookie | Two Ingresses: stable + canary annotation |
| Rate limiting | `limit-rps`, `limit-connections` | Returns 429 when exceeded |
| `configuration-snippet` | Inject raw Nginx config | Security headers, custom directives |
| Endpoint updates | Pod IP changes in upstream pool | Dynamic; no full reload needed |
| Config reload | Ingress rule changes trigger reload | Graceful; in-flight requests complete |
| `upstream-keepalive-connections` | Persistent connections to backends | Critical for high-throughput; reduces TCP overhead |
| `proxy-read-timeout` | Backend response wait timeout | Override per-Ingress for long operations |

---

**Tip for the interview:** Ingress questions at 5 YOE level test whether you understand the controller/resource split (the Ingress resource is just a declaration; the controller makes it real), and whether you've operated an Ingress in production. The specific details that separate senior answers: knowing that `pathType: Prefix` and `Exact` are the correct fields (not annotations), explaining that Nginx reloads are graceful (in-flight requests aren't dropped), and being specific about the `rewrite-target` annotation pattern using capture groups (`$2`) for path stripping. For TLS: cert-manager with `cert-manager.io/cluster-issuer` is the production answer (not manually managing certificate secrets). For performance: `upstream-keepalive-connections` is the single most impactful tuning parameter for high-throughput services — persistent connections to backends eliminate per-request TCP handshake overhead. If asked about troubleshooting: the five-step sequence (describe ingress → check class → controller logs → nginx.conf → endpoints) shows systematic debugging instinct rather than guessing.
