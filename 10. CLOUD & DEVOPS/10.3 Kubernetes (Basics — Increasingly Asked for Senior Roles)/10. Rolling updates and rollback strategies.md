# Kubernetes Rolling Updates and Rollback Strategies: Deployment Mechanics, Probes, and Zero-Downtime Patterns — Interview Q&A (5 YOE Level)

---

## Section 1: The Deployment Controller and Update Mechanics

**Q1. How does the Kubernetes Deployment controller manage a rolling update at the ReplicaSet level, and what exactly happens during `kubectl apply`?**
A: A Deployment does not manage Pods directly. It manages ReplicaSets, and ReplicaSets manage Pods. A rolling update is the Deployment controller creating a new ReplicaSet (for the new version), then incrementally scaling it up while scaling the old ReplicaSet down — subject to the `maxSurge` and `maxUnavailable` constraints. Understanding this two-ReplicaSet model is the foundation for understanding rollbacks, revision history, and why certain failure modes occur.

**The object hierarchy:**

```
Deployment: nestjs-api
  ├── ReplicaSet: nestjs-api-7d9f8b6c4  (revision 3 — current)
  │     ├── Pod: nestjs-api-7d9f8b6c4-xk2p9
  │     ├── Pod: nestjs-api-7d9f8b6c4-m7qr1
  │     └── Pod: nestjs-api-7d9f8b6c4-n3ts8
  └── ReplicaSet: nestjs-api-5c8d9e7f2  (revision 2 — previous; scaled to 0)
        (no Pods — scaled down after revision 3 completed)

  ReplicaSet: nestjs-api-3b4c5d6e1  (revision 1 — older; scaled to 0)

The Deployment controller continuously reconciles:
  "Desired state" (Deployment spec) vs "actual state" (running Pods).
  If they differ: the controller acts to close the gap.
```

**Step-by-step anatomy of `kubectl apply -f deployment.yaml`:**

```
Before: Deployment at revision 3, 5 replicas running.
  ReplicaSet-v3: desired=5, ready=5
  ReplicaSet-v2: desired=0, ready=0

kubectl apply -f deployment.yaml  (new image tag: v4)

Step 1: kube-apiserver receives the updated Deployment spec.
  The Deployment spec's pod template has changed (new image).
  A template hash is computed from the pod template:
    hash = fnv32a(pod_template_spec)
  This hash is used as a label on the ReplicaSet and its Pods:
    pod-template-hash: 9e2f1a3b5

  The Deployment controller compares the new hash with existing ReplicaSets.
  No existing ReplicaSet has this hash → new ReplicaSet is created.

Step 2: New ReplicaSet created (revision 4), desired=0.
  ReplicaSet-v4: desired=0, ready=0   ← exists but not yet scaling up
  ReplicaSet-v3: desired=5, ready=5   ← old; still serving traffic

Step 3: Deployment controller starts the rolling update.
  Constraint: maxSurge=1, maxUnavailable=0 (default for RollingUpdate strategy).
  Total desired: 5 Pods.
  With maxSurge=1: up to 6 Pods can exist simultaneously (5 + 1).
  With maxUnavailable=0: at least 5 Pods must be available at all times.

  Iteration 1:
    Scale up ReplicaSet-v4: desired=1 (surge)
    ReplicaSet-v4 creates Pod-v4-1.
    Pod-v4-1 enters Pending → Running → passes readiness probe.
    Now: 6 Pods total, 6 available (5 old + 1 new).
    maxUnavailable=0 satisfied (6 ≥ 5). Can remove one old Pod.
    Scale down ReplicaSet-v3: desired=4
    ReplicaSet-v3 terminates Pod-v3-1 (graceful; SIGTERM).
    Now: 5 Pods total, 5 available (4 old + 1 new). ✅

  Iteration 2:
    Scale up ReplicaSet-v4: desired=2
    Pod-v4-2 starts, passes readiness.
    Scale down ReplicaSet-v3: desired=3
    Pod-v3-2 terminates.

  ... (continues until) ...

  Iteration 5:
    Scale up ReplicaSet-v4: desired=5
    Pod-v4-5 starts, passes readiness.
    Scale down ReplicaSet-v3: desired=0
    Last old Pod terminates.

Step 4: Update complete.
  ReplicaSet-v4: desired=5, ready=5  ← serving all traffic
  ReplicaSet-v3: desired=0, ready=0  ← retained for rollback (revision history)
  ReplicaSet-v2: desired=0, ready=0  ← retained
  ReplicaSet-v1: deleted             ← pruned (beyond revisionHistoryLimit)

The old ReplicaSet (v3) is NOT deleted after the update.
It is scaled to 0 and retained.
This is what makes instant rollback possible: the ReplicaSet with the old
Pod template still exists. Rollback = scale ReplicaSet-v3 back to 5.
```

**What triggers a new ReplicaSet vs reusing an existing one:**

```
A new ReplicaSet is created ONLY when the Pod template changes:
  - Image tag or digest change
  - Environment variable change
  - ConfigMap or Secret reference change
  - Resource requests/limits change
  - Labels or annotations on the Pod template change

A new ReplicaSet is NOT created when:
  - Deployment metadata (labels, annotations not in pod template) changes
  - Deployment replicas count changes (scales existing ReplicaSet)
  - HPA adjusts replica count (same)

Rollback shortcut:
  If you roll back to a revision whose pod template matches an existing
  (scaled-to-0) ReplicaSet: the controller simply scales that ReplicaSet
  back up — no new ReplicaSet created, no new image pull.
  This makes rollbacks faster than forward deployments:
    Forward: pull new image + start container + warmup
    Rollback: start container (image already cached on node) + warmup
```

**Q2. What are `maxSurge` and `maxUnavailable`, and how do different combinations affect update speed and availability?**
A: `maxSurge` and `maxUnavailable` are the two knobs that control the rolling update's speed and availability guarantee. They are defined as absolute numbers or percentages of the desired replica count, and their interaction determines how many Pods can be in transition at any moment.

**Definition:**

```
maxSurge:
  Maximum number of Pods that can exist ABOVE the desired count during update.
  Controls how fast the new ReplicaSet can scale up.
  Higher maxSurge = faster update (more new Pods start simultaneously).
  Higher maxSurge = more resource usage during transition.
  Can be 0 only if maxUnavailable > 0.

maxUnavailable:
  Maximum number of Pods that can be UNAVAILABLE (not ready) during update.
  Controls the minimum availability guarantee.
  0 = zero-downtime update (no capacity reduction ever).
  Higher maxUnavailable = faster update (old Pods removed faster).
  Can be 0 only if maxSurge > 0.
  Both cannot be 0 simultaneously → update would be stuck (can't add, can't remove).

Percentage vs absolute:
  "25%" of 10 replicas = 2.5 → rounds DOWN for maxUnavailable (floor)
                              → rounds UP for maxSurge (ceiling)
  maxUnavailable: "25%" of 10 = 2 (floor: can remove 2 old Pods)
  maxSurge:       "25%" of 10 = 3 (ceil: can add 3 new Pods)

Default (when strategy is RollingUpdate but values not set):
  maxSurge:       "25%"
  maxUnavailable: "25%"
  For 10 replicas: maxSurge=3, maxUnavailable=2
  → At most 13 Pods during update; at least 8 available at any time.
```

**Four common configurations and their trade-offs:**

```
Configuration 1: Zero-downtime (production standard for stateless APIs)
  maxSurge:       1
  maxUnavailable: 0

  Behavior (10 replicas):
    New Pod starts → waits for readiness → old Pod removed.
    One at a time. 10 iterations. Slow but guaranteed no capacity drop.
    Total Pods during update: always 10–11.
    Minimum available: always 10. ← zero downtime

  Speed: slowest (one Pod at a time)
  Availability: highest (never below desired count)
  Resource cost: 1 extra Pod during update (+10% temporarily)
  Use for: production APIs, payment processors, anything with SLA

Configuration 2: Fast update with surge (parallel rollout)
  maxSurge:       5
  maxUnavailable: 0

  Behavior (10 replicas):
    5 new Pods start simultaneously → all pass readiness → 5 old Pods removed.
    2 iterations. Faster.
    Total Pods during update: up to 15 (50% more capacity needed).
    Minimum available: always 10. ← zero downtime, but expensive

  Speed: fast (half the fleet replaced at once)
  Availability: highest
  Resource cost: 50% surge (5 extra Pods; requires node capacity)
  Use for: when update speed matters and you have headroom

Configuration 3: Recreate-like fast (acceptable brief unavailability)
  maxSurge:       0
  maxUnavailable: 3

  Behavior (10 replicas):
    3 old Pods removed → 3 new Pods start (no surge; same slot used).
    ~3 iterations.
    Total Pods during update: drops to 7 during transition.
    Minimum available: 7 (30% capacity reduction). ← not zero-downtime

  Speed: medium
  Availability: reduced (downgrade from 10 to 7 during transition)
  Resource cost: no extra capacity needed (no surge)
  Use for: batch workers, non-production, cost-constrained environments
           where brief capacity reduction is acceptable

Configuration 4: Maximum speed (canary validation not needed)
  maxSurge:       10
  maxUnavailable: 10

  Behavior (10 replicas):
    All 10 new Pods start simultaneously; all 10 old Pods terminate.
    Effectively a Recreate strategy but within RollingUpdate framework.
    ~ equivalent to strategy: Recreate but with readiness checks.
    Total Pods during update: up to 20. Then drops to 0 until new ones ready.
    Minimum available: 0. ← NOT zero-downtime

  Speed: fastest possible
  Availability: potentially zero during transition
  Resource cost: doubles fleet temporarily
  Use for: development environments, stateful sets requiring coordinated restart

The Recreate strategy (separate from RollingUpdate):
  strategy:
    type: Recreate
  Behavior: ALL old Pods terminated before ANY new Pod is created.
  Total unavailability: entire fleet is down until new Pods start.
  Use for: applications that CANNOT run two versions simultaneously
           (shared database schema migration, singleton processes,
            applications with exclusive locks or single-writer constraints).
  Never use for production stateless APIs.
```

## Section 2: Probes — The Gate for Rolling Updates

**Q3. What are the three probe types, and how do they interact with rolling updates to ensure zero downtime?**
A: The three probe types — `startupProbe`, `livenessProbe`, and `readinessProbe` — serve entirely different purposes and fire at different points in a container's lifecycle. Misconfiguring them is the most common cause of rolling update incidents: either the update stalls (probe too strict during startup) or traffic is sent to unready Pods (probe too lenient).

**The three probes and their purposes:**

```
startupProbe:
  Purpose: give a slow-starting container time to initialize before
           liveness and readiness probes begin.
  Timing:  runs FIRST, from container start, until it succeeds.
           While startupProbe is running: liveness and readiness probes
           are SUSPENDED. The container cannot be killed by liveness failure.
  On success: startupProbe stops running; liveness and readiness begin.
  On failure (after failureThreshold attempts): container killed → restart.
  Use for: JVM applications (slow startup), applications that download
           large model weights, NestJS apps with many modules to initialize.

livenessProbe:
  Purpose: detect if the container is stuck in a deadlock, infinite loop,
           or other unrecoverable state where the process is running but
           cannot make progress.
  Timing:  runs continuously after startupProbe succeeds (or from start
           if no startupProbe).
  On failure: container killed (SIGTERM → grace period → SIGKILL) and restarted.
  Critical rule: liveness should check ONLY the container's own health,
                 not external dependencies (database, cache, downstream APIs).
                 If the database goes down: liveness probe failing on all Pods
                 kills ALL Pods → entire fleet restarts → thundering herd → worse.
  Correct liveness checks: event loop alive, process not deadlocked,
                            basic in-process health (memory not critically high).

readinessProbe:
  Purpose: signal to the Service/Endpoints controller whether this Pod
           should receive traffic.
  Timing:  runs continuously after startupProbe succeeds.
  On failure: Pod removed from Service Endpoints (no new traffic routed to it).
              Pod is NOT restarted. It continues running but receives no traffic.
              Pod returns to Endpoints when probe succeeds again.
  Critical rule for rolling updates: a new Pod is considered "available"
           ONLY when its readinessProbe succeeds.
           maxUnavailable=0 means: don't remove an old Pod until a new Pod
           is ready (readiness succeeded). Without a readinessProbe: the Pod
           is considered ready immediately when the container starts — before
           the application has finished initializing.
  Correct readiness checks: HTTP /health endpoint returns 200, database
                             connection pool established, cache warmed,
                             all downstream dependencies reachable.
```

**The interaction between probes and rolling updates:**

```
Scenario: rolling update with maxSurge=1, maxUnavailable=0, 3 replicas.

Without readinessProbe (dangerous):
  New Pod starts → container starts → Kubernetes immediately considers it Ready.
  Old Pod is removed (maxUnavailable=0 satisfied: 3 still "ready").
  But the application takes 10 seconds to finish initialization.
  During those 10 seconds: traffic is sent to the new Pod → connection refused
  or 503 errors. The rolling update causes downtime despite maxUnavailable=0.

  The maxUnavailable=0 guarantee is meaningless without a readinessProbe.
  It only guarantees that Kubernetes considers the replacement "ready" —
  and without a probe, "ready" means nothing.

With correct readinessProbe (safe):
  New Pod starts → container starts → readinessProbe begins.
  readinessProbe: GET /health → 503 (app still initializing) → Not Ready.
  Kubernetes does NOT add this Pod to Service Endpoints.
  Kubernetes does NOT remove the old Pod (maxUnavailable=0: new Pod not ready yet).
  After 10 seconds: app fully initialized → GET /health → 200 → Ready.
  Pod added to Service Endpoints. Old Pod removed. Zero-downtime guaranteed.

Without startupProbe (dangerous for slow starters):
  NestJS app with many modules: takes 25 seconds to initialize.
  livenessProbe: GET /health, initialDelaySeconds=10, periodSeconds=5.
  At second 10: liveness fires → app still initializing → 503 → fail.
  At second 15: liveness fires → fail (failureThreshold=3).
  At second 20: liveness fires → fail → container killed.
  App never starts. CrashLoopBackOff. Update stalls.

With startupProbe (correct):
  startupProbe: GET /health, periodSeconds=5, failureThreshold=12.
  → 12 × 5s = 60 seconds total window for startup.
  At seconds 5, 10, 15, 20, 25: probe fires → fail (app still starting).
  At second 25: app ready → probe succeeds → startupProbe stops.
  livenessProbe begins. readinessProbe begins. Normal operation.
```

**Complete production probe configuration for NestJS:**

```yaml
spec:
  containers:
    - name: nestjs-api
      image: nestjs-api:sha256-abc123

      # startupProbe: generous window for initialization
      startupProbe:
        httpGet:
          path: /health/startup    # lightweight check: "is the HTTP server up?"
          port: 3000
          httpHeaders:
            - name: Accept
              value: application/json
        initialDelaySeconds: 5     # wait 5s before first attempt (avoid immediate failure)
        periodSeconds: 5           # check every 5 seconds
        failureThreshold: 24       # 24 × 5s = 120s total window before giving up
        successThreshold: 1        # one success is enough

      # livenessProbe: is the process responsive?
      livenessProbe:
        httpGet:
          path: /health/liveness   # checks: event loop not blocked, process running
          port: 3000
        initialDelaySeconds: 0     # startupProbe handled the delay; liveness starts immediately after
        periodSeconds: 10          # check every 10 seconds
        failureThreshold: 3        # 3 consecutive failures = 30s of unresponsiveness → restart
        successThreshold: 1
        timeoutSeconds: 5          # individual probe must respond within 5 seconds

      # readinessProbe: is the Pod ready to serve traffic?
      readinessProbe:
        httpGet:
          path: /health/readiness  # checks: DB connected, cache connected, dependencies up
          port: 3000
        initialDelaySeconds: 0
        periodSeconds: 5           # check every 5s; faster to detect recovery
        failureThreshold: 3        # 3 failures = 15s before removed from endpoints
        successThreshold: 1        # 1 success = re-added to endpoints
        timeoutSeconds: 3
```

**Three health endpoints in NestJS (correct separation):**

```typescript
// health.controller.ts
import { Controller, Get } from '@nestjs/common';
import {
  HealthCheck,
  HealthCheckService,
  HttpHealthIndicator,
  TypeOrmHealthIndicator,
  MemoryHealthIndicator,
} from '@nestjs/terminus';

@Controller('health')
export class HealthController {

  constructor(
    private health: HealthCheckService,
    private http: HttpHealthIndicator,
    private db: TypeOrmHealthIndicator,
    private memory: MemoryHealthIndicator,
  ) {}

  // startupProbe target: is the HTTP server listening?
  // Fastest possible check — just proves the event loop is running
  // and accepting connections. No dependencies checked.
  @Get('startup')
  startup() {
    return { status: 'ok' };
  }

  // livenessProbe target: is the process healthy (not deadlocked)?
  // Check only in-process state. NEVER check external dependencies here.
  // If liveness fails on all Pods simultaneously → mass restart cascade.
  @Get('liveness')
  @HealthCheck()
  liveness() {
    return this.health.check([
      // Memory check: if RSS > 90% of limit, process is likely leaking
      () => this.memory.checkRSS('memory_rss', 460 * 1024 * 1024), // 460 MiB of 512 MiB limit
      // Heap check: V8 heap not critically full
      () => this.memory.checkHeap('memory_heap', 350 * 1024 * 1024),
    ]);
  }

  // readinessProbe target: is this Pod ready to serve user traffic?
  // Check all dependencies required to handle a real request.
  // Failure here removes the Pod from the load balancer — correct behavior.
  @Get('readiness')
  @HealthCheck()
  readiness() {
    return this.health.check([
      // Database: can we query?
      () => this.db.pingCheck('database', { timeout: 2000 }),
      // Cache: can we reach Redis?
      () => this.http.pingCheck('redis', 'http://redis-sentinel:26379/'),
      // Downstream: critical internal service reachable?
      () => this.http.pingCheck('payment-service', 'http://payment-service/health'),
    ]);
  }
}

// Why separation matters:
// During a database outage:
//   readiness fails → all Pods removed from endpoints → no traffic → correct
//   liveness is unaffected → no Pods killed → correct (problem is external)
//
// During a memory leak reaching critical levels:
//   liveness fails → individual Pod killed and restarted → correct
//   readiness is unaffected until the Pod is actually killed → correct
//
// If you check the database in liveness:
//   DB goes down → liveness fails on all Pods → all Pods killed simultaneously
//   → entire fleet restarts → connection spike to DB during recovery → worse
```

**Q4. What is `minReadySeconds`, and how does it add a stabilization gate to rolling updates?**
A: `minReadySeconds` specifies how long a newly created Pod must be continuously ready (no probe failures) before the Deployment controller considers it "available" and moves on to replacing the next old Pod. It is a stabilization buffer on top of the readiness probe.

```yaml
spec:
  minReadySeconds: 30    # default: 0 (available immediately upon readiness)
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
```

**What minReadySeconds adds that readinessProbe alone does not:**

```
readinessProbe: checks if the Pod BECAME ready at a point in time.
  A Pod that passes one readiness check is immediately considered available.
  If the probe passes once then fails (flapping Pod): the Pod was momentarily
  available, triggered the next old Pod's removal, then became unavailable.
  Net result: fewer available Pods than intended.

minReadySeconds: requires the Pod to STAY ready for a duration.
  Even if readinessProbe passes, the Pod must remain continuously ready
  for minReadySeconds before it counts as "available."
  If the Pod flaps within the minReadySeconds window:
    Timer resets. Old Pod is not removed. Update waits.

Example:
  New Pod passes readiness probe at T=10s.
  minReadySeconds=30.
  At T=15s: Pod fails readiness (application error during warmup).
  Timer resets. Pod is not yet "available."
  At T=30s: readiness passes again. Timer starts from T=30s.
  At T=60s: Pod has been ready for 30 continuous seconds → available.
  Old Pod is removed.

  Total update time per Pod: ~60s instead of ~10s.
  But: much more confidence that the new Pod is stable before removing old.

When to use minReadySeconds:
  Applications with warm-up phases where they accept traffic but serve errors
  for the first N seconds (cache warming, JIT compilation, connection pool
  establishment). Even with readiness checking external dependencies, there
  may be internal state that takes seconds to fully prepare.

  Production recommendation: 10–60 seconds depending on application behavior.
  For NestJS with cache warming: 15–30 seconds.
  For Java services with JIT warmup: 30–60 seconds.
  For Go services: 5–10 seconds (fast startup, minimal warmup).

  Trade-off: each Pod added minReadySeconds to the update duration.
  10 replicas × 30s minReadySeconds = 5 additional minutes of update time.
  Acceptable for critical production services; may be reduced for less critical ones.
```

## Section 3: Rollback — Mechanics, Strategies, and Automation

**Q5. How does `kubectl rollout undo` work under the hood, and what is the revision history model?**
A: `kubectl rollout undo` does not rebuild anything from scratch. It identifies the ReplicaSet for the target revision and updates the Deployment's pod template to match that ReplicaSet's pod template. The Deployment controller then treats this as a new update: it creates (or reuses) a ReplicaSet and performs a rolling update back to the previous version.

**Revision history mechanics:**

```
Revision history is stored as annotations on ReplicaSets:
  ReplicaSet: nestjs-api-7d9f8b6c4
    annotations:
      deployment.kubernetes.io/revision: "4"
      deployment.kubernetes.io/revision-history: "2,3"

  ReplicaSet: nestjs-api-5c8d9e7f2
    annotations:
      deployment.kubernetes.io/revision: "3"

  ReplicaSet: nestjs-api-3b4c5d6e1
    annotations:
      deployment.kubernetes.io/revision: "2"

Viewing revision history:
  kubectl rollout history deployment/nestjs-api -n production

  Output:
    REVISION  CHANGE-CAUSE
    2         kubectl apply --filename=deploy.yaml --record (deprecated)
    3         image update to sha256-xyz: fix memory leak
    4         image update to sha256-abc: add payment feature

  Note: CHANGE-CAUSE is populated only if:
    a) --record flag was used (deprecated in Kubernetes 1.22+)
    b) kubernetes.io/change-cause annotation is set on the Deployment:
       kubectl annotate deployment/nestjs-api \
         kubernetes.io/change-cause="v2.4.1: fix memory leak in payment handler" \
         -n production
       Set this annotation in your CI/CD pipeline as part of the deploy step.
       Without it: all CHANGE-CAUSE entries show <none>.

Viewing a specific revision:
  kubectl rollout history deployment/nestjs-api \
    --revision=3 -n production

  Output:
    Pod Template:
      Labels:  app=nestjs-api
               pod-template-hash=5c8d9e7f2
      Containers:
        nestjs-api:
          Image: nestjs-api@sha256-xyz
          Ports: 3000/TCP
          Environment: ...
          Limits: ...

  This shows exactly what was running at revision 3.
  Use this before rolling back to verify you're reverting to the right version.

revisionHistoryLimit:
  spec:
    revisionHistoryLimit: 10  # default: 10; how many old ReplicaSets to retain

  When a new revision is created and the number of retained ReplicaSets
  exceeds revisionHistoryLimit, the oldest (lowest revision number) ReplicaSet
  is garbage collected.
  Set to 0: no history retained; rollback is impossible. Never do this in production.
  Set to 5–10: typical production value; covers the last 5–10 deployments.
  Cost: old ReplicaSets consume no compute (scaled to 0) but count toward
        API object limits. 10 is a safe and sensible default.
```

**`kubectl rollout undo` step by step:**

```
Current state:
  Revision 4 (current):  ReplicaSet-v4, running 5 Pods with image sha256-abc (bad)
  Revision 3 (previous): ReplicaSet-v3, scaled to 0, image sha256-xyz (good)

kubectl rollout undo deployment/nestjs-api -n production
  ← rolls back to revision 3 (the immediately previous revision)

kubectl rollout undo deployment/nestjs-api --to-revision=2 -n production
  ← rolls back to a specific revision

What happens:
  1. Deployment controller reads ReplicaSet-v3's pod template.
  2. Updates the Deployment's spec.template to match ReplicaSet-v3's template.
  3. A new revision number is assigned: revision 5.
     (The Deployment revision always increases — rollback creates a new revision.)
  4. The pod template hash is recomputed.
     Hash matches ReplicaSet-v3's hash exactly (same template = same hash).
  5. The existing ReplicaSet-v3 (with that hash) is reused.
     No new ReplicaSet is created. ReplicaSet-v3 is scaled back up.
  6. Normal rolling update begins:
     Scale ReplicaSet-v3: 0 → 1 → 2 → 3 → 4 → 5
     Scale ReplicaSet-v4: 5 → 4 → 3 → 2 → 1 → 0
     Subject to maxSurge and maxUnavailable constraints.

After rollback:
  Revision 5 (current):  ReplicaSet-v3 (reused), running 5 Pods, sha256-xyz
  Revision 4 (previous): ReplicaSet-v4, scaled to 0, sha256-abc (the bad version)
  Revision 2:            ReplicaSet-v2, scaled to 0

  Note: revision 3 is no longer in the history as a separate entry.
  It has become revision 5. The history shows the current state, not
  a linear sequence of all past states.

Rollback speed advantage:
  Forward deployment: image pull (if not cached) + container start + warmup
  Rollback: container start + warmup (image almost certainly cached from last run)
  Rollback is typically 2–3× faster than a forward deployment.
  The image sha256-xyz was running minutes ago; it's cached on every node.

Rollback failure modes:
  The rollback is also a rolling update. It can also fail.
  If revision 3 had a broken readiness probe: the rollback stalls too.
  Always verify the target revision is known-good before rolling back.
  kubectl rollout history --revision=3 shows the image; check it is the intended one.
```

**Q6. How do you implement automated rollback based on metrics, and what does a production-grade rollout pipeline look like?**
A: Manual rollback with `kubectl rollout undo` is too slow for production incidents — it requires a human to notice the problem, diagnose it, and act. Automated rollback integrates health signals (error rate, latency, crash rate) into the deployment pipeline and triggers rollback without human intervention if the new version fails canary validation.

**Automated rollback pattern — CI/CD pipeline with Prometheus gate:**

```bash
#!/usr/bin/env bash
# deploy-with-autorollback.sh
set -euo pipefail

NAMESPACE="production"
DEPLOYMENT="nestjs-api"
NEW_IMAGE="nestjs-api@sha256-${GIT_SHA}"
CANARY_DURATION=300          # 5 minutes of canary observation
ERROR_RATE_THRESHOLD=0.01    # 1% error rate triggers rollback
P99_LATENCY_THRESHOLD_MS=500 # p99 > 500ms triggers rollback
PROMETHEUS_URL="http://prometheus.monitoring.svc:9090"

# Step 1: Record current revision before deploying
PREVIOUS_REVISION=$(kubectl rollout history deployment/${DEPLOYMENT} \
  -n ${NAMESPACE} | tail -2 | head -1 | awk '{print $1}')

echo "Deploying ${NEW_IMAGE}. Previous revision: ${PREVIOUS_REVISION}"

# Step 2: Set the change cause annotation (for audit trail)
kubectl annotate deployment/${DEPLOYMENT} \
  kubernetes.io/change-cause="${NEW_IMAGE}: ${DEPLOY_REASON:-CI deploy}" \
  -n ${NAMESPACE} --overwrite

# Step 3: Apply the new image
kubectl set image deployment/${DEPLOYMENT} \
  ${DEPLOYMENT}=${NEW_IMAGE} \
  -n ${NAMESPACE}

# Step 4: Wait for rollout to complete (all new Pods ready)
echo "Waiting for rollout to complete..."
if ! kubectl rollout status deployment/${DEPLOYMENT} \
     -n ${NAMESPACE} --timeout=600s; then
  echo "ROLLOUT FAILED: Deployment did not complete within 10 minutes."
  echo "Triggering automatic rollback to revision ${PREVIOUS_REVISION}..."
  kubectl rollout undo deployment/${DEPLOYMENT} \
    --to-revision=${PREVIOUS_REVISION} -n ${NAMESPACE}
  kubectl rollout status deployment/${DEPLOYMENT} -n ${NAMESPACE} --timeout=300s
  exit 1
fi

echo "Rollout complete. Starting ${CANARY_DURATION}s canary observation..."

# Step 5: Observe metrics for the canary period
sleep 10  # brief settle time for metrics to populate

ROLLBACK_TRIGGERED=false
END_TIME=$(($(date +%s) + CANARY_DURATION))

while [ $(date +%s) -lt ${END_TIME} ]; do

  # Check error rate (HTTP 5xx / total requests over last 60s)
  ERROR_RATE=$(curl -sf "${PROMETHEUS_URL}/api/v1/query" \
    --data-urlencode "query=
      sum(rate(http_requests_total{
        namespace=\"${NAMESPACE}\",
        job=\"${DEPLOYMENT}\",
        status=~\"5..\"
      }[60s])) /
      sum(rate(http_requests_total{
        namespace=\"${NAMESPACE}\",
        job=\"${DEPLOYMENT}\"
      }[60s]))" \
    | jq -r '.data.result[0].value[1] // "0"')

  # Check p99 latency
  P99_LATENCY=$(curl -sf "${PROMETHEUS_URL}/api/v1/query" \
    --data-urlencode "query=
      histogram_quantile(0.99,
        sum(rate(http_request_duration_seconds_bucket{
          namespace=\"${NAMESPACE}\",
          job=\"${DEPLOYMENT}\"
        }[60s])) by (le)
      ) * 1000" \
    | jq -r '.data.result[0].value[1] // "0"')

  # Check OOMKills in the last 60 seconds
  OOMKILLS=$(curl -sf "${PROMETHEUS_URL}/api/v1/query" \
    --data-urlencode "query=
      sum(increase(kube_pod_container_status_restarts_total{
        namespace=\"${NAMESPACE}\",
        pod=~\"${DEPLOYMENT}-.*\"
      }[60s]))" \
    | jq -r '.data.result[0].value[1] // "0"')

  echo "Canary metrics — Error rate: ${ERROR_RATE} | P99 latency: ${P99_LATENCY}ms | Restarts: ${OOMKILLS}"

  # Evaluate thresholds
  if (( $(echo "${ERROR_RATE} > ${ERROR_RATE_THRESHOLD}" | bc -l) )); then
    echo "ERROR: Error rate ${ERROR_RATE} exceeds threshold ${ERROR_RATE_THRESHOLD}"
    ROLLBACK_TRIGGERED=true
    break
  fi

  if (( $(echo "${P99_LATENCY} > ${P99_LATENCY_THRESHOLD_MS}" | bc -l) )); then
    echo "ERROR: P99 latency ${P99_LATENCY}ms exceeds threshold ${P99_LATENCY_THRESHOLD_MS}ms"
    ROLLBACK_TRIGGERED=true
    break
  fi

  if (( $(echo "${OOMKILLS} > 0" | bc -l) )); then
    echo "ERROR: OOMKills detected in the canary window"
    ROLLBACK_TRIGGERED=true
    break
  fi

  sleep 15  # check every 15 seconds
done

# Step 6: Rollback if any threshold was exceeded
if [ "${ROLLBACK_TRIGGERED}" = true ]; then
  echo "Triggering automatic rollback to revision ${PREVIOUS_REVISION}..."
  kubectl rollout undo deployment/${DEPLOYMENT} \
    --to-revision=${PREVIOUS_REVISION} -n ${NAMESPACE}
  kubectl rollout status deployment/${DEPLOYMENT} -n ${NAMESPACE} --timeout=300s
  # Notify: PagerDuty, Slack, etc.
  curl -sf -X POST "${SLACK_WEBHOOK}" \
    -d "{\"text\": \"🚨 Auto-rollback triggered for ${DEPLOYMENT} in ${NAMESPACE}. Reverted to revision ${PREVIOUS_REVISION}.\"}"
  exit 1
fi

echo "Canary observation passed. Deployment ${NEW_IMAGE} is stable."
curl -sf -X POST "${SLACK_WEBHOOK}" \
  -d "{\"text\": \"✅ ${DEPLOYMENT} deployed successfully: ${NEW_IMAGE}\"}"
```

## Section 4: Advanced Deployment Patterns

**Q7. What is a Blue-Green deployment, and how is it implemented in Kubernetes?**
A: Blue-Green deployment runs two complete, identical environments simultaneously — the current version (Blue) and the new version (Green). Traffic is switched instantly from Blue to Green by updating the Service selector, not by replacing Pods incrementally. Rollback is equally instant: switch the selector back to Blue.

**Blue-Green implementation:**

```yaml
# Blue Deployment (current version — serving traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api-blue
  namespace: production
spec:
  replicas: 5
  selector:
    matchLabels:
      app: nestjs-api
      version: blue
  template:
    metadata:
      labels:
        app: nestjs-api
        version: blue
    spec:
      containers:
        - name: nestjs-api
          image: nestjs-api@sha256-xyz  # v2.3.0 — current stable

---
# Green Deployment (new version — deployed but not receiving traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api-green
  namespace: production
spec:
  replicas: 5
  selector:
    matchLabels:
      app: nestjs-api
      version: green
  template:
    metadata:
      labels:
        app: nestjs-api
        version: green
    spec:
      containers:
        - name: nestjs-api
          image: nestjs-api@sha256-abc  # v2.4.0 — new version

---
# Service: selector determines which version gets traffic
apiVersion: v1
kind: Service
metadata:
  name: nestjs-api
  namespace: production
spec:
  selector:
    app: nestjs-api
    version: blue    # ← currently points to Blue
  ports:
    - port: 80
      targetPort: 3000
```

**The cutover and rollback sequence:**

```bash
# Pre-deployment: Green is already running (all 5 Pods healthy)
# Verify Green is healthy before touching the Service:
kubectl rollout status deployment/nestjs-api-green -n production
# → Successfully rolled out

# Run smoke tests against Green directly (bypassing the Service):
# Port-forward to a Green Pod:
kubectl port-forward deployment/nestjs-api-green 8080:3000 -n production &
curl http://localhost:8080/health/readiness
curl http://localhost:8080/api/v1/payments/health
# Run integration test suite against localhost:8080

# Cutover: switch Service selector from Blue to Green
# This is atomic — all new requests go to Green; in-flight Blue requests complete
kubectl patch service nestjs-api -n production \
  -p '{"spec":{"selector":{"app":"nestjs-api","version":"green"}}}'

# Verify: Service now routes to Green
kubectl get endpoints nestjs-api -n production
# → Endpoints should show Green Pod IPs

# Observe metrics for 5–10 minutes (error rate, latency, throughput)
# If metrics are healthy: scale down Blue (optional; keep for quick rollback)

# Rollback (if something goes wrong): single command, instant
kubectl patch service nestjs-api -n production \
  -p '{"spec":{"selector":{"app":"nestjs-api","version":"blue"}}}'
# Traffic instantly returns to Blue. All Green traffic stops.
# No rolling update. No Pod restarts. Sub-second cutover.

# Cleanup (after Green is stable for 24–48 hours):
kubectl delete deployment nestjs-api-blue -n production
```

**Blue-Green trade-offs:**

```
Advantages:
  Instant cutover and rollback (Service selector patch = microseconds).
  Zero-downtime even for applications that cannot handle rolling updates
  (shared database locks, singleton processes, coordinated restarts).
  Green can be fully validated (smoke tests, integration tests) before
  any production traffic touches it.
  Complete isolation: Blue and Green never share Pods.

Disadvantages:
  Requires 2× the compute resources during the transition period.
  Both Blue and Green must be able to share the same database schema
  simultaneously (during the period when both exist).
    If Green requires a database migration that breaks Blue's queries:
    → Must use backwards-compatible migrations (add column before using it;
      remove column after Blue is gone).
    → Blue-Green is not a solution to database migration challenges —
      it defers the problem but does not eliminate it.
  State management: active user sessions, in-flight requests, long-polling
  connections on Blue are dropped when traffic switches to Green.
  ALB/Ingress configuration: some load balancers require Ingress changes
  rather than just Service selector changes for proper traffic switching.
  Cost: double fleet for the transition window (minutes to hours).

When to use Blue-Green:
  Applications with strict "no rolling mix of versions" requirements.
  Database schema changes that require coordinated cutover.
  Releases requiring pre-production smoke testing against real infrastructure.
  Teams that need instant, reliable rollback with zero coordination.

When NOT to use Blue-Green:
  High-replica-count services where 2× cost during transition is significant.
  Services with persistent local state (use StatefulSet rolling updates instead).
  Frequent deployments (multiple per day) — the overhead of managing two
  environments becomes operationally burdensome.
```

**Q8. What is a canary deployment, and how does it differ from a rolling update in risk profile?**
A: A canary deployment routes a small percentage of production traffic to the new version while the old version continues serving the majority. Unlike a rolling update (which replaces the entire fleet incrementally), a canary exposes only a fraction of users to the new version at once — limiting the blast radius if the new version is defective.

**Canary with a single Deployment (simple; percentage via replica ratio):**

```yaml
# Stable: 9 Pods
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api-stable
  namespace: production
spec:
  replicas: 9
  selector:
    matchLabels:
      app: nestjs-api
      track: stable
  template:
    metadata:
      labels:
        app: nestjs-api
        track: stable
    spec:
      containers:
        - name: nestjs-api
          image: nestjs-api@sha256-xyz   # v2.3.0

---
# Canary: 1 Pod (≈ 10% of traffic if Service selects both)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api-canary
  namespace: production
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nestjs-api
      track: canary
  template:
    metadata:
      labels:
        app: nestjs-api
        track: canary
    spec:
      containers:
        - name: nestjs-api
          image: nestjs-api@sha256-abc   # v2.4.0 — new version

---
# Service: selects BOTH stable and canary (no track label)
apiVersion: v1
kind: Service
metadata:
  name: nestjs-api
  namespace: production
spec:
  selector:
    app: nestjs-api   # matches both stable (9) and canary (1)
  ports:
    - port: 80
      targetPort: 3000
# Traffic distribution: proportional to Pod count.
# 9 stable Pods + 1 canary Pod = 10% canary traffic.
# Service load balances equally across all 10 Pods.
```

**Progressive canary with ALB weighted target groups (AWS):**

```yaml
# Ingress with ALB annotations for weight-based traffic splitting
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nestjs-api-ingress
  namespace: production
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/actions.forward-action: |
      {
        "type": "forward",
        "forwardConfig": {
          "targetGroups": [
            {
              "serviceName": "nestjs-api-stable",
              "servicePort": 80,
              "weight": 95
            },
            {
              "serviceName": "nestjs-api-canary",
              "servicePort": 80,
              "weight": 5
            }
          ]
        }
      }
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: forward-action
                port:
                  name: use-annotation

# This sends exactly 5% of traffic to canary regardless of Pod count.
# The replica-ratio approach (above) can drift as HPA adjusts counts.
# ALB weighted routing is more precise and does not require matching Pod counts.

# Progressive rollout:
# Day 1: weight canary=5%   → observe 1 hour → metrics pass
# Day 1: weight canary=10%  → observe 1 hour → metrics pass
# Day 1: weight canary=25%  → observe 2 hours → metrics pass
# Day 2: weight canary=50%  → observe 4 hours → metrics pass
# Day 2: weight canary=100% → canary becomes new stable → delete old stable
```

**Canary vs Rolling Update risk profile:**

```
Rolling Update (10 replicas, maxSurge=1, maxUnavailable=0):
  After iteration 1: 10% canary, 90% stable.
  After iteration 5: 50% canary, 50% stable.
  After iteration 10: 100% canary.
  No way to pause at a specific percentage (update continues automatically).
  If the new version is defective at iteration 5: 50% of users are affected.
  Rollback at that point: 5 Pods to replace back to old version (slow).

Canary (explicit 5% → 10% → 25% progression):
  Initially: only 5% of users see the new version.
  If defective: 5% impact, not 50%.
  Can pause at any step to observe metrics.
  Can abandon (route 0% to canary) without touching the stable fleet.
  Blast radius: controlled by the canary weight, not by update progress.

The canary advantage is most pronounced for:
  High-risk changes (new payment logic, auth changes, data migrations).
  Changes affecting specific user segments (test with 5% first).
  Services where "5 minutes of 50% degradation" is unacceptable.

The canary overhead:
  Requires either Argo Rollouts, Flagger, or manual traffic weight management.
  Two Deployments to maintain (stable + canary).
  Session affinity considerations: a user's request might go to stable for
  one call and canary for the next. If the two versions return different
  data shapes, the client may see inconsistency.
  Fix: use cookie-based sticky routing (ALB target group stickiness) to
  ensure a given user consistently hits either stable or canary.
```

## Section 5: PodDisruptionBudgets and Update Safety

**Q9. What is a PodDisruptionBudget, and how does it protect rolling updates and cluster operations?**
A: A PodDisruptionBudget (PDB) defines the minimum number of Pods that must remain available during voluntary disruptions — node drains, cluster upgrades, manual kubectl delete pod, and rolling updates. It is the primary mechanism for ensuring that maintenance operations respect application availability requirements.

**PDB structure:**

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: nestjs-api-pdb
  namespace: production
spec:
  # Choose ONE of: minAvailable OR maxUnavailable (not both)

  # Option A: minimum Pods that must remain available
  minAvailable: 3     # at least 3 Pods must be running at all times
                      # can also be a percentage: "80%"

  # Option B: maximum Pods that can be simultaneously unavailable
  # maxUnavailable: 1   # at most 1 Pod can be down at a time
  #                     # can also be a percentage: "20%"

  selector:
    matchLabels:
      app: nestjs-api
```

**How PDB interacts with rolling updates and node drains:**

```
Scenario: nestjs-api has 5 replicas; PDB minAvailable=3.

Rolling update interaction:
  The Deployment controller's rolling update respects the PDB.
  maxUnavailable=1 in the Deployment + minAvailable=3 in PDB:
    The controller checks: "Can I remove this Pod without violating the PDB?"
    If removing 1 Pod would drop available count below 3: wait.
    In practice: with 5 replicas and minAvailable=3, the Deployment can
    remove up to 2 Pods simultaneously — both Deployment maxUnavailable
    and PDB minAvailable must be satisfied.
    The more restrictive constraint wins.

Node drain interaction:
  kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
  → node-1 is being cordoned and its Pods evicted.
  → The drain process calls the Pod eviction API (not kubectl delete pod).
  → The eviction API checks the PDB before allowing the eviction.

  With PDB minAvailable=3 and 5 Pods on node-1 (all 5 on the same node):
    Attempt to evict Pod 1: 4 remaining → 4 ≥ 3 ✅ → eviction allowed.
    Attempt to evict Pod 2: 3 remaining → 3 ≥ 3 ✅ → eviction allowed.
    Attempt to evict Pod 3: 2 remaining → 2 < 3 ❌ → eviction DENIED.
    Drain stalls. kubectl drain hangs until the 2 evicted Pods are
    rescheduled on other nodes and become ready.
    Once rescheduled: drain retries Pod 3 eviction → 4 ≥ 3 ✅ → allowed.
    And so on.

  Without PDB:
    kubectl drain evicts all 5 Pods simultaneously.
    nestjs-api is completely unavailable during the drain.
    This is the production consequence of missing PDBs.

  EKS node group upgrades:
    AWS EKS node group rolling update → drains old nodes → respects PDBs.
    If PDB cannot be satisfied (e.g., minAvailable=5 but only 5 total replicas):
      Drain is blocked indefinitely. Node group upgrade stalls.
      Fix: ensure minAvailable < total replicas, OR
           scale up replicas before the upgrade, OR
           use maxUnavailable instead of minAvailable.
```

**PDB sizing for common patterns:**

```
Pattern 1: Stateless API (most common)
  Replicas: 5
  PDB: minAvailable: 3   (60% must remain — survives 2 simultaneous evictions)
  Allows: rolling update, node drains with graceful rescheduling
  Blocks: draining all Pods simultaneously

Pattern 2: Strict SLA (no more than 1 Pod down)
  Replicas: 5
  PDB: maxUnavailable: 1
  Allows: one Pod evicted at a time
  Blocks: any operation that would make 2+ Pods unavailable simultaneously
  Cost: slower node drains (must wait for rescheduling between each eviction)

Pattern 3: Minimum viable capacity
  Replicas: 5; normal load requires 3 Pods for acceptable latency
  PDB: minAvailable: 3
  Combined with HPA: HPA can scale above 5 during node drain
    → more Pods = more flexibility for evictions while maintaining minAvailable.

Pattern 4: Singleton / leader-elected process
  Replicas: 1
  PDB: minAvailable: 1
  Effect: kubectl drain NEVER evicts this Pod voluntarily.
          The drain waits forever.
  This is intentional for processes that cannot be interrupted (e.g., a job
  mid-execution). The drain operator must manually delete the Pod or
  use --force --disable-eviction to override the PDB.
  For most singletons: prefer StatefulSet with proper leadership transfer.

Anti-pattern: PDB that makes drains impossible
  Replicas: 3
  PDB: minAvailable: 3
  → No Pod can ever be voluntarily evicted.
  → Node drains hang permanently.
  → EKS node upgrades stall permanently.
  Rule: minAvailable must always be < total replicas.
        maxUnavailable must always be ≥ 1 for voluntary disruptions to work.

Verify PDB is not blocking operations:
  kubectl get pdb -n production
  Output:
    NAME              MIN AVAILABLE  MAX UNAVAILABLE  ALLOWED DISRUPTIONS  AGE
    nestjs-api-pdb    3              N/A              2                    5d
    ← ALLOWED DISRUPTIONS: 2 means 2 Pods can currently be evicted.
      If ALLOWED DISRUPTIONS is 0: PDB is currently blocking all disruptions.
      Check if this is expected (e.g., during a rolling update) or a problem.
```

## Section 6: Scenario Questions

**Q10. "Your rolling update has stalled — new Pods are stuck in a not-ready state and old Pods are not being removed. Walk through the full diagnosis."**
A:

```
Observation:
  kubectl rollout status deployment/nestjs-api -n production
  → Waiting for deployment "nestjs-api" rollout to finish:
    1 out of 5 new replicas have been updated...
  (Stuck; not progressing after 10+ minutes)

Diagnosis:

Step 1: Check the new Pod's status.
  kubectl get pods -n production -l app=nestjs-api
  Output:
    nestjs-api-7d9f8b6c4-xk2p9  Running   0/1   10m   ← new Pod; 0 containers ready
    nestjs-api-5c8d9e7f2-m7qr1  Running   1/1   2d    ← old Pod; ready
    nestjs-api-5c8d9e7f2-n3ts8  Running   1/1   2d    ← old Pod; ready
    ...

  The new Pod (xk2p9) is Running but 0/1 containers ready.
  This means: container is running but readinessProbe is failing.

Step 2: Describe the new Pod to see events and probe failures.
  kubectl describe pod nestjs-api-7d9f8b6c4-xk2p9 -n production

  Key sections to check:

  Conditions:
    Type              Status
    Initialized       True
    Ready             False   ← container is NOT ready
    ContainersReady   False
    PodScheduled      True

  Events:
    Warning  Unhealthy  5m  kubelet
      Readiness probe failed: HTTP probe failed with statuscode: 503
    Warning  Unhealthy  4m  kubelet
      Readiness probe failed: HTTP probe failed with statuscode: 503
    Warning  Unhealthy  3m  kubelet
      Readiness probe failed: Get "http://10.0.0.45:3000/health/readiness": dial tcp 10.0.0.45:3000: connect: connection refused

  → Readiness probe is hitting /health/readiness and getting 503 or connection refused.

Step 3: Check what the application is actually doing.
  kubectl logs nestjs-api-7d9f8b6c4-xk2p9 -n production --tail=50

  Possible log outputs:

  Case A: Application crash loop (no startup logs visible)
    → Container keeps restarting. Check:
       kubectl describe pod ... → Last State: Terminated, Reason: Error, Exit Code: 1
    → Application crashing at startup. Check the image.
       kubectl get pod -o jsonpath='{.spec.containers[0].image}'
       → Was the image pushed correctly? Does it exist in ECR?
       → Symptom: ImagePullBackOff or ErrImagePull in events.

  Case B: Application started but readiness dependency failing
    Logs: "Database connection failed: ECONNREFUSED 10.0.1.23:5432"
    → readinessProbe checks DB; DB is unreachable from this Pod.
    → Network policy blocking new Pod from reaching DB?
       kubectl get networkpolicy -n production
       kubectl describe networkpolicy allow-db -n production
       → Check if the new Pod's labels match the NetworkPolicy's podSelector.
       → New Pods may have new labels (pod-template-hash changed) not
         covered by the NetworkPolicy. Update the NetworkPolicy.

  Case C: Application slow startup (not a crash; just slow)
    Logs: "NestJS dependencies loading... [45/120 modules loaded]"
    → Application is initializing but readinessProbe fires before it's done.
    → failureThreshold too low or initialDelaySeconds too short.
    → Fix: increase failureThreshold or add/tune startupProbe.

  Case D: New feature requires environment variable not set
    Logs: "Error: Required environment variable PAYMENT_GATEWAY_KEY not set"
    → New code requires a config value that is not in the ConfigMap or Secret.
    → Fix: add the missing config before re-deploying.

Step 4: Check if the rollout has a ProgressDeadlineExceeded.
  kubectl describe deployment nestjs-api -n production | grep -A5 "Conditions"
  Output:
    Conditions:
      Type           Status  Reason
      Available      True    MinimumReplicasAvailable
      Progressing    False   ProgressDeadlineExceeded

  ProgressDeadlineExceeded: the Deployment has a spec.progressDeadlineSeconds
  (default: 600s = 10 minutes). If the rollout does not progress within this
  window, the Deployment is marked as failed (Progressing=False).
  The rollout does NOT automatically roll back on ProgressDeadlineExceeded.
  You must manually roll back:
    kubectl rollout undo deployment/nestjs-api -n production

Step 5: Execute the fix.
  Depending on root cause:
    A) Bad image: fix the image, push a corrected version, re-deploy.
    B) Missing config: add the env var/ConfigMap key, re-deploy.
    C) NetworkPolicy: update the policy, re-deploy (Pods may start passing readiness).
    D) Probe too strict: update probe config, re-deploy.

  While fixing: the stalled rollout keeps old Pods running.
  Users are not impacted (old Pods are healthy; traffic stays there).
  This is the correct behavior of maxUnavailable=0: stall safely rather
  than remove old Pods before new Pods are confirmed ready.

Step 6: Cancel the bad rollout (optional, before pushing a fix).
  kubectl rollout undo deployment/nestjs-api -n production
  → Removes the new (bad) ReplicaSet Pods.
  → Scales the old ReplicaSet back to 5.
  → Restores clean state; reduces noise while debugging.
  OR: leave the stalled rollout in place (old Pods still serving)
  and push a corrected deployment directly.
```

**Q11. "You need to deploy a breaking database schema migration alongside a new application version with zero downtime. Walk through the strategy."**
A:

```
The problem:
  Old application (v2.3): reads column "user_name"
  New application (v2.4): reads column "full_name" (renamed from user_name)
  Migration: ALTER TABLE users RENAME COLUMN user_name TO full_name;

  If you run the migration and deploy simultaneously:
    During rolling update: some Pods run v2.3, some run v2.4.
    v2.3 Pods query "user_name" → column is gone → SQL error → 500s.
    OR: v2.4 Pods query "full_name" → column doesn't exist yet → 500s.
    There is no safe moment during a rolling update to flip the schema.

The solution: expand-contract pattern (3-phase deployment)

Phase 1: Expand — add the new column, keep the old one (backwards-compatible migration)
  Migration SQL:
    -- Add new column (nullable; no default required immediately)
    ALTER TABLE users ADD COLUMN full_name TEXT;
    -- Copy existing data to new column
    UPDATE users SET full_name = user_name;
    -- Add trigger to keep both in sync during transition
    CREATE OR REPLACE FUNCTION sync_user_name()
    RETURNS TRIGGER AS $$
    BEGIN
      IF NEW.user_name IS DISTINCT FROM OLD.user_name THEN
        NEW.full_name = NEW.user_name;
      END IF;
      IF NEW.full_name IS DISTINCT FROM OLD.full_name THEN
        NEW.user_name = NEW.full_name;
      END IF;
      RETURN NEW;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER sync_columns
    BEFORE UPDATE ON users
    FOR EACH ROW EXECUTE FUNCTION sync_user_name();

  After this migration:
    Both "user_name" and "full_name" exist and are kept in sync by the trigger.
    v2.3 still reads "user_name" → works ✅
    v2.4 will read "full_name" → works ✅ (column exists, populated)
    The migration can be applied while v2.3 is running. No downtime.

Phase 2: Deploy v2.4 (rolling update — safe because both columns exist)
  v2.4 application reads "full_name" instead of "user_name".
  During rolling update: v2.3 and v2.4 Pods coexist.
  Both versions work correctly because both columns exist and are synchronized.
  Complete the rolling update to v2.4. All Pods now on v2.4.
  Observe for 24–48 hours. Confirm no issues.

Phase 3: Contract — remove the old column
  Only after 100% of Pods are on v2.4 AND v2.3 is fully gone:
    DROP TRIGGER sync_columns ON users;
    DROP FUNCTION sync_user_name();
    ALTER TABLE users DROP COLUMN user_name;

  v2.4 no longer references "user_name". Safe to drop.
  The column removal is a separate migration, separate deployment.

The three-phase timeline:
  Day 1, T+0:   Apply Phase 1 migration (expand). v2.3 still running. No downtime.
  Day 1, T+30m: Deploy v2.4 (rolling update). Both versions safe with both columns.
  Day 1, T+60m: v2.4 fully deployed. Monitor.
  Day 2, T+0:   Apply Phase 3 migration (contract). v2.4 only. Drop old column.

Additional pattern: feature flag for schema-dependent features
  v2.4 includes the new feature behind a feature flag:
    FEATURE_USE_FULL_NAME=false  (disabled by default)
  Phase 1 migration runs. v2.4 deploys. Feature flag remains false.
  Phase 3 migration runs.
  Feature flag enabled: FEATURE_USE_FULL_NAME=true (ConfigMap update).
  This decouples the code deployment from the feature activation.
  If Phase 3 migration causes any issue: disable flag, investigate, retry.

What NOT to do:
  ❌ Run the destructive migration (RENAME/DROP) before deploying v2.4.
     Old Pods crash immediately. Downtime.

  ❌ Deploy v2.4 before adding the new column.
     New Pods crash (column doesn't exist). Rollout stalls. Old Pods still up.
     No downtime, but the deployment fails.

  ❌ Use Recreate strategy to avoid the mixed-version problem.
     Recreate causes downtime. Solves the version-mixing problem by
     trading it for guaranteed unavailability. Not a solution.

  ❌ Init container to run migration before the Pod starts.
     Init container runs on every new Pod during the rolling update.
     Migration runs N times (once per new Pod). Most migrations are not
     idempotent and fail on re-run. Or they are idempotent (CREATE TABLE IF NOT EXISTS)
     but that's managing migrations in init containers, which is an anti-pattern:
     if 3 Pods start simultaneously, 3 init containers run the migration simultaneously
     → race condition. Use a pre-deploy Job instead.

Correct: pre-deploy Job for migrations
  In CI/CD pipeline, before kubectl apply -f deployment.yaml:
    kubectl apply -f migration-job.yaml
    kubectl wait --for=condition=complete job/migration-v2-4 \
      -n production --timeout=300s
    # Only then deploy:
    kubectl apply -f deployment.yaml

  The Job runs once, completes, and is verified before any new Pods start.
  If the Job fails: do not deploy. Fix the migration first.
  Jobs have parallelism=1 and completions=1 by default: runs exactly once.
```

| Setting | Default | Effect |
|---|---|---|
| `strategy.type` | `RollingUpdate` | `Recreate` for all-at-once replacement |
| `maxSurge` | `25%` | Max Pods above desired during update |
| `maxUnavailable` | `25%` | Max Pods below desired during update |
| `minReadySeconds` | `0` | Seconds a new Pod must be continuously ready before "available" |
| `progressDeadlineSeconds` | `600` | Seconds before Deployment is marked failed |
| `revisionHistoryLimit` | `10` | Old ReplicaSets retained for rollback |
| `terminationGracePeriodSeconds` | `30` | Seconds before SIGKILL after SIGTERM |

| Probe | Purpose | Failure action | Check external deps? |
|---|---|---|---|
| `startupProbe` | Gate liveness/readiness until app is up | Kill container | No |
| `livenessProbe` | Detect deadlocks / unrecoverable state | Kill container + restart | Never |
| `readinessProbe` | Control traffic routing | Remove from Endpoints | Yes |

| Deployment pattern | Rollback speed | Blast radius | Resource cost | Use for |
|---|---|---|---|---|
| Rolling Update | ~minutes (re-rolling) | Full fleet eventually | Minimal surge | Standard stateless API updates |
| Blue-Green | Instant (selector patch) | Zero (traffic at switch point) | 2× during transition | Zero-risk cutover; schema migrations |
| Canary | Instant (weight to 0%) | % of users (controlled) | Minor overhead | High-risk changes; gradual validation |
| Recreate | Fast (not rolling) | 100% downtime during switch | None | Applications requiring exclusive access |

| Failure mode | Symptom | Root cause | Fix |
|---|---|---|---|
| Rollout stalls | New Pods `0/1 Ready`; old Pods not removed | readinessProbe failing on new Pods | Check app logs; fix probe or app config |
| Rollout loops | Pod restarts repeatedly during update | livenessProbe too strict; app crash | Add startupProbe; fix liveness threshold |
| ProgressDeadlineExceeded | Deployment Condition: `Progressing=False` | Rollout stalled > 600s | `kubectl rollout undo`; fix root cause |
| PDB blocks drain | `kubectl drain` hangs | `minAvailable == replicas` | Ensure `minAvailable < replicas` |
| Post-deploy errors, can't rollback | `kubectl rollout undo` has no effect | `revisionHistoryLimit: 0` | Set `revisionHistoryLimit: 5`+ |
| Mixed-version errors during rolling update | 500s during deployment | Backwards-incompatible schema change | Expand-contract migration pattern |
| Canary traffic not splitting correctly | All traffic going to stable | Service selector matches all labels incl. version | Remove `version` label from Service selector |
| New Pods ready before app initialized | Brief 503s after each Pod replacement | No readinessProbe or probe too lenient | Add readinessProbe; check real dependencies |

## The Core Mental Model

```
A rolling update is a reconciliation loop, not a script.
The Deployment controller continuously asks: "Does actual state match desired state?"
Every action it takes is to close the gap between them.
It operates through two ReplicaSets: scaling one up, scaling the other down,
subject to maxSurge and maxUnavailable. The old ReplicaSet is never deleted
during the update — it is scaled to zero and retained for rollback.

maxUnavailable=0 guarantees nothing without a readinessProbe.
"Unavailable" means "readiness probe failed or not yet run."
Without a probe: every new Pod is immediately "available" — even a Pod
whose application is still initializing. The old Pod is removed.
The application serves traffic to an uninitialized container → 503s.
maxUnavailable=0 + no readinessProbe = false confidence of zero downtime.
The readinessProbe is what gives maxUnavailable=0 its meaning.

The three probes have three completely different jobs:
  startupProbe: "give me time to start; don't kill me while I'm initializing"
  livenessProbe: "kill me and restart me if I'm stuck; never check external deps"
  readinessProbe: "send me traffic only when I'm fully ready; check everything"
  The liveness rule is the most commonly violated: checking the database
  in livenessProbe means a database outage kills every Pod simultaneously.
  The thundering herd that follows is worse than the outage itself.

Rollback is a forward operation disguised as a backward one.
kubectl rollout undo does not rewind anything. It updates the Deployment's
pod template to match a previous ReplicaSet's template, then performs
a new rolling update (revision N+1) using the old ReplicaSet.
This is why rollback is faster: the old image is cached on every node.
This is also why a rollback can fail: if the previous revision had broken
probes, the rollback will stall too. Always verify the target revision first.

PodDisruptionBudget is not optional for production.
Without a PDB: kubectl drain (node upgrades, CA scale-down, manual maintenance)
evicts all Pods from the node simultaneously. The service goes down.
With minAvailable correctly set (< replicas): drains respect the constraint,
evicting one Pod at a time and waiting for rescheduling. Zero disruption.
Anti-pattern: minAvailable == replicas. This makes the node permanently
undrain-able. EKS node group upgrades stall forever.

Schema migrations are the hardest part of zero-downtime deployments.
The rolling update itself is straightforward. The challenge is when the
new code requires database schema changes that break the old code.
The expand-contract pattern is the only reliable solution:
  1. Add the new column/table (old code unaffected; new code compatible).
  2. Deploy the new application (both old and new code work during rollout).
  3. Remove the old column/table (only after old code is completely gone).
Each phase is a separate deployment. Each is safe individually.
Running a migration in an init container is an anti-pattern:
races on parallel Pod startup, repeated runs, and coupling migration to
Pod lifecycle instead of the deployment pipeline.

Blue-Green for instant rollback; canary for controlled blast radius:
  If you need sub-second rollback: Blue-Green (Service selector flip).
  If you need to limit user impact to 5%: Canary (traffic weighting).
  If neither of these is a requirement: Rolling Update is simpler to operate.
  All three patterns coexist in a mature platform:
    Routine updates: rolling update (fast, simple, safe).
    High-risk features: canary (limited exposure, metric-gated).
    Schema migrations: blue-green or expand-contract (coordinated cutover).
```

**Tip for the interview:** Rolling update questions at 5 YOE converge on three areas: (1) the two-ReplicaSet model and what actually happens during `kubectl rollout undo` — explaining that rollback reuses the existing scaled-to-zero ReplicaSet (same pod-template-hash → same ReplicaSet, just scaled back up), that rollback creates revision N+1 (not N-1), and that rollback speed comes from image caching (not from anything special about the rollback path itself), demonstrates you understand the controller model rather than just knowing the kubectl commands; (2) the probe separation rule — being able to explain why a database connectivity check belongs in readinessProbe but never in livenessProbe, with the specific failure mode (database outage → liveness fails on all Pods → mass restart → thundering herd → worse than the original outage), and why startupProbe exists independently (suspends liveness checks during slow startup, preventing a CrashLoopBackOff for a perfectly healthy application that just takes 45 seconds to initialize), shows you have debugged a probe misconfiguration incident in production; (3) the schema migration problem — walking through why a RENAME or DROP during a rolling update causes 500s on half the fleet and explaining the expand-contract pattern (add new column → deploy new code → drop old column as three separate operations) shows you have shipped a breaking schema change to a production system without downtime. The fintech callout: for NACH batch processing windows (09:00–11:00 IST), a PodDisruptionBudget with `minAvailable` set to the minimum viable batch capacity plus a `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"` annotation on Pods that are mid-batch ensures that node group rolling upgrades scheduled during off-hours do not accidentally interrupt a batch job that started early or runs long — the PDB makes the cluster operation wait rather than killing the batch, and the annotation is the belt-and-suspenders guarantee.
