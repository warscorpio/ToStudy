# Kubernetes Horizontal Pod Autoscaler (HPA) — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why HPA Exists

**Q1. What problem does HPA solve and why can't you just set a fixed replica count?**
A: A fixed replica count is a static answer to a dynamic problem. Traffic to a payment API is not constant — it spikes during business hours, drops at night, surges during sale events, and collapses on weekends. Setting replicas to handle peak load wastes compute during off-peak hours (paying for idle Pods); setting replicas to handle average load risks exhaustion during spikes (requests queue, timeouts, failures).

The operational reality without HPA:

- **Manual scaling**: an engineer watches dashboards and adjusts replicas. This is reactive (scaling happens after the spike starts), requires human attention 24/7, and is error-prone (forget to scale back → wasted cost).
- **Over-provisioning**: set replicas high enough to handle any foreseeable spike. Safe but expensive — at 3× average traffic as the peak multiplier, you pay for 3× compute constantly, with 66% idle capacity most of the time.
- **Under-provisioning**: set replicas to average load. Works until any spike — then SLOs break, payments time out, and merchants complain.

HPA solves this by continuously observing a metric (CPU, memory, custom queue depth) and automatically adjusting the replica count to maintain a target value. The system is always as small as it can be while remaining responsive — a self-tuning balance between cost and performance.

The deeper insight: HPA is not about reacting to problems, it's about maintaining a relationship between load and capacity. If the target is 70% CPU utilization per Pod, HPA doesn't wait for CPUs to be at 95% before scaling — it continuously adjusts replicas to keep the average close to 70%, scaling out slightly ahead of overload and scaling in gradually after load drops.

**Q2. What is the relationship between HPA, the Metrics Server, and custom metrics providers?**
A: HPA does not collect metrics itself — it queries a metrics API and uses the returned values to compute the desired replica count. Three metrics APIs exist, each backed by a different source:

**Resource metrics API (`metrics.k8s.io`):**
Backed by the Metrics Server — a lightweight aggregator that scrapes resource usage (CPU, memory) from the Kubelet on each node. The Kubelet collects these from the container runtime (cgroup statistics) every 15 seconds. The Metrics Server aggregates and exposes them via the `metrics.k8s.io` API. HPA queries this API for CPU and memory metrics.

```bash
# Verify Metrics Server is running (required for CPU/memory HPA)
kubectl get deployment metrics-server -n kube-system

# Check that metrics are flowing
kubectl top pods -n payments
# NAME                            CPU(cores)   MEMORY(bytes)
# payment-api-abc12               45m          128Mi
# payment-api-def34               52m          134Mi
```

**Custom metrics API (`custom.metrics.k8s.io`):**
Backed by an adapter that bridges an external metrics source (Prometheus, Datadog, Stackdriver) to the Kubernetes metrics API. The adapter is deployed separately — Prometheus Adapter being the most common for self-hosted clusters. HPA queries this for application-specific metrics (requests per second, queue depth, active connections, business metrics like payments per minute).

**External metrics API (`external.metrics.k8s.io`):**
For metrics that don't correspond to any Kubernetes object — SQS queue depth, CloudWatch metrics, Pub/Sub subscription backlog. The same adapters (Prometheus Adapter, Keda, KEDA) can serve this API.

```
HPA control loop:
  Every 15 seconds:
    1. Query metrics API for current metric value across all target Pods
    2. Compute desired replicas = ceil(current replicas × current metric / target metric)
    3. Apply scale limits (minReplicas, maxReplicas, scaling policies)
    4. Update Deployment/StatefulSet replica count if it changed
```

## Section 2: HPA Configuration

**Q3. What does an HPA resource look like and what does each field control?**
A: The HPA resource (`autoscaling/v2`, the current API version since Kubernetes 1.23) is a declarative specification of scaling behavior:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api-hpa
  namespace: payments
spec:
  # Target: the Deployment/StatefulSet to scale
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api

  # Scale bounds: never fewer than 3, never more than 50
  minReplicas: 3
  maxReplicas: 50

  # Metrics: what to scale on (can be multiple — HPA picks the highest replica count)
  metrics:
    # CPU utilization: keep average CPU below 70% of the container's CPU request
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70    # percent of CPU request

    # Memory: keep average memory below 80% of request
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

    # Custom metric: requests per second per Pod
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"       # target: 100 RPS per Pod

  # Scaling behavior: how fast to scale out and scale in
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0      # scale up immediately (no delay)
      policies:
        - type: Percent
          value: 100                     # double replicas at most per period
          periodSeconds: 60
        - type: Pods
          value: 5                       # or add at most 5 Pods per period
          periodSeconds: 60
      selectPolicy: Max                  # use whichever policy allows MORE Pods

    scaleDown:
      stabilizationWindowSeconds: 300    # wait 5 minutes before scaling in
      policies:
        - type: Percent
          value: 10                      # remove at most 10% of Pods per period
          periodSeconds: 60
      selectPolicy: Min                  # use whichever policy removes FEWER Pods
```

**Key field explanations:**

**`minReplicas`**: the floor — HPA never scales below this. Set to match the minimum capacity needed to handle baseline traffic with acceptable latency, and to provide high availability (≥ 2 for redundancy; ≥ 3 for zone distribution with `topologySpreadConstraints`).

**`maxReplicas`**: the ceiling — HPA never scales above this. Set to the maximum your downstream systems (databases, payment gateways) can handle, your cost budget allows, and your cluster has node capacity for. A misconfigured HPA without a realistic `maxReplicas` can attempt to scale a service to 500 replicas, overwhelming the database connection pool and creating a cascading failure.

**`averageUtilization`**: percent of the Pod's CPU/memory *request* (not limit). If a Pod's CPU request is `500m` and `averageUtilization` is `70`, HPA tries to keep average CPU usage at `350m` (70% of 500m). This relationship to the request — not the actual node capacity — is why correctly setting resource requests is a prerequisite for effective HPA.

**Multiple metrics**: when multiple metrics are specified, HPA independently computes the desired replica count for each metric and takes the **maximum**. This is deliberate — if CPU says 10 replicas and queue depth says 20 replicas, HPA uses 20. The system is never under-provisioned for any of the metrics it watches.

**Q4. What is the HPA scaling formula and how does it compute the desired replica count?**
A: HPA's core calculation is:

```
desiredReplicas = ceil(currentReplicas × (currentMetricValue / desiredMetricValue))
```

For CPU utilization with `averageUtilization: 70`:
```
currentReplicas: 5
currentMetricValue: average CPU across 5 Pods = 85% (of CPU request)
desiredMetricValue: 70%

desiredReplicas = ceil(5 × (85 / 70))
               = ceil(5 × 1.214)
               = ceil(6.07)
               = 7

HPA scales from 5 → 7 Pods
```

For scale-in (CPU drops):
```
currentReplicas: 7
currentMetricValue: average CPU = 30%
desiredMetricValue: 70%

desiredReplicas = ceil(7 × (30 / 70))
               = ceil(7 × 0.428)
               = ceil(3.0)
               = 3

HPA wants to scale from 7 → 3 Pods
(subject to stabilization window — won't happen immediately)
```

**The tolerance band (±10%):**
HPA does not act if the ratio of current to desired metric is within 10% of 1.0. This prevents constant micro-adjustments from minor metric fluctuations:

```
currentMetricValue / desiredMetricValue is in range [0.9, 1.1]:
  → HPA takes no action (metric is close enough to target)

Outside this band:
  → HPA computes desiredReplicas and acts
```

This 10% tolerance is not configurable. It means HPA won't scale until the metric is at least 10% above or below target — a metric at 75% against a 70% target does not trigger scaling.

**Handling unready and missing Pods:**
HPA is cautious about Pods that are not yet ready or have missing metrics:
- **Starting Pods** (not yet Ready): treated as having 0 usage for scale-out calculations, ensuring HPA doesn't over-scale while new Pods are still starting. If the average usage would drop once these Pods are running, HPA waits.
- **Pods with missing metrics**: if a Pod can't report metrics (Metrics Server hasn't scraped it yet), HPA assumes it's at 100% utilization for scale-out (conservative) and at 0% for scale-in (conservative in the other direction). This prevents premature scale-in of a Pod whose metrics are temporarily unavailable.

## Section 3: Scaling Behavior and Policies

**Q5. What is the stabilization window and why does scale-in need it but scale-out does not?**
A: The stabilization window is a lookback period during which HPA evaluates whether to act. Before scaling, HPA examines the recommendations it would have made over the past `stabilizationWindowSeconds` seconds and applies a conservative rule:
- For **scale-up**: use the **minimum** recommendation in the window (don't over-scale).
- For **scale-down**: use the **maximum** recommendation in the window (don't under-scale / don't scale in too aggressively).

Wait — that seems backwards. Here's why it makes sense:

**Scale-up stabilization (default: 0 seconds — scale up immediately):**
When the metric exceeds the target, respond immediately. A payment API experiencing a traffic spike needs more capacity now — waiting to confirm the spike is persistent just means more requests timing out. The cost of a false positive (scaling up unnecessarily for a transient spike) is small: a few extra Pods running for a short time.

**Scale-down stabilization (default: 300 seconds — wait 5 minutes):**
When the metric drops below the target, wait before scaling in. Traffic spikes are often bursty — a 5-minute low may be followed immediately by another spike. Scaling in 10 Pods and immediately needing to scale back out wastes time (Pod startup takes 30–60 seconds) and creates instability. The 5-minute window ensures HPA only scales in when the low load is sustained, not momentary.

```
Traffic pattern:     spike → drop → spike → drop → sustained low

Without stabilization window:
  Scale out: ✅ immediate
  Scale in:  10 → 3 → 10 → 3 → 10 → 3 → 5 (thrashing)
  Every spike: 30-60s of reduced capacity while Pods restart

With 5-minute stabilization window:
  Scale out: ✅ immediate
  Scale in:  waits until load has been low for 5 consecutive minutes
  10 → 10 → 10 → 10 → 5 (stable; no thrashing)
```

**Configuring stabilization windows:**
```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0       # respond immediately to load increases
  scaleDown:
    stabilizationWindowSeconds: 300     # wait 5 minutes before scaling in
                                        # (default; tunable per workload)
```

For batch job workers that process from a queue: a shorter scale-down window (60 seconds) makes sense — when the queue empties, there's no reason to keep workers running. For API servers: the default 300 seconds is appropriate given traffic burst patterns.

**Q6. What are scaling policies and how do they limit the rate of scaling?**
A: Scaling policies control how aggressively HPA can change the replica count in any single scaling step. They prevent runaway scaling — both the dangerous kind (a metric spike causing HPA to request 1000 replicas) and the disruptive kind (rapid Pod churn from aggressive scale-in).

**Policy types:**
```yaml
behavior:
  scaleUp:
    policies:
      - type: Percent          # add at most X% of current replicas per period
        value: 100             # double the replica count per minute max
        periodSeconds: 60

      - type: Pods             # add at most X Pods per period
        value: 10              # add at most 10 Pods per minute
        periodSeconds: 60

    selectPolicy: Max          # Max: pick whichever allows MORE Pods (aggressive scale-up)
                               # Min: pick whichever allows FEWER Pods (conservative)
                               # Disabled: don't scale up at all (freeze)

  scaleDown:
    policies:
      - type: Percent
        value: 10              # remove at most 10% of Pods per minute
        periodSeconds: 60

      - type: Pods
        value: 2               # or remove at most 2 Pods per minute
        periodSeconds: 60

    selectPolicy: Min          # Min: pick whichever removes FEWER Pods (gentle scale-in)
```

**Worked example — scale-up policy:**
```
Current: 10 replicas
Desired: 40 replicas (metric is 4× the target)
Policies:
  Percent 100 per 60s: add at most 10 (100% of 10) → 10 + 10 = 20
  Pods 10 per 60s:     add at most 10 → 10 + 10 = 20
selectPolicy: Max → use whichever allows MORE Pods → both say 20

Minute 1: 10 → 20 Pods
Minute 2: 20 → 40 Pods (if metric still demands 40)

Without policies: 10 → 40 in one step (pod churn; node pressure; scheduling delays)
With policies:    10 → 20 → 40 over 2 minutes (controlled ramp-up)
```

**Why `Percent` and `Pods` policies coexist:**
At low replica counts, a `Percent` policy is too slow (10% of 2 Pods = 0.2 → rounds to 0 → no scaling). At high replica counts, a `Pods` policy is too slow (adding 2 Pods per minute when you need 100 more takes 50 minutes). The combination — `selectPolicy: Max` — uses `Percent` when it's larger (high replica count scenarios) and the absolute `Pods` count when it's larger (low replica count scenarios), giving fast scaling at any scale.

## Section 4: Resource Requests — The Hidden Prerequisite

**Q7. Why are CPU and memory requests mandatory for HPA to work correctly, and what breaks without them?**
A: HPA's CPU and memory scaling targets are defined as percentages of the Pod's **resource request** — not of the node's capacity, not of the container's limit, and not of some absolute value. If a container has no CPU request, the denominator in HPA's calculation is undefined — HPA cannot compute utilization.

**What happens without resource requests:**
```yaml
# Deployment WITHOUT CPU request — HPA cannot function
containers:
  - name: payment-api
    image: payment-api:latest
    # resources: (not specified)
```

```bash
kubectl get hpa payment-api-hpa
# NAME              REFERENCE           TARGETS         MINPODS  MAXPODS  REPLICAS
# payment-api-hpa   Deployment/payment  <unknown>/70%   3        50       3
#                                        ↑
# <unknown>: HPA cannot determine CPU utilization without a request to compare to
# HPA will NOT scale — it cannot compute the ratio
```

**Why requests are the denominator (not limits or node capacity):**
Resource requests are the scheduling guarantee — the amount of CPU/memory Kubernetes promises to reserve on the node for this Pod. They represent the expected operating cost of one Pod instance. If a Pod's CPU request is `500m` and `averageUtilization: 70`, the target is `350m` of CPU per Pod — a level at which the Pod is working normally without being overloaded. The gap between `350m` (target) and `500m` (request) is headroom for request bursts.

Limits are the hard ceiling — a Pod at its CPU limit is being throttled. Using limits as the denominator would mean "scale when throttling occurs," which is too late. Requests as denominator means "scale before throttling occurs."

**Setting correct requests is a prerequisite for effective HPA:**
```yaml
containers:
  - name: payment-api
    image: payment-api:latest
    resources:
      requests:
        cpu:    "500m"    # 0.5 vCPU — what the app normally uses
        memory: "512Mi"   # 512MB — what the app normally uses
      limits:
        cpu:    "2000m"   # 2 vCPU — burst ceiling (throttled if exceeded)
        memory: "1024Mi"  # 1GB — OOM killed if exceeded
```

**Requests should reflect actual usage, not aspirational values:**
Setting `cpu: requests: 100m` when the app actually uses `400m` at idle means:
- HPA target is 70% of 100m = 70m (below what the app uses even at idle)
- HPA constantly tries to scale out to lower CPU "utilization"
- Replicas grow to maxReplicas; each new Pod still uses 400m
- HPA is confused; no amount of scaling resolves the miscalibration

The correct approach: run the application under realistic load, observe actual CPU/memory usage with `kubectl top pods`, set requests slightly above the observed idle usage, and set limits at the burst ceiling.

## Section 5: Custom and External Metrics

**Q8. How do you configure HPA to scale on custom metrics like RPS or SQS queue depth?**
A: Scaling on CPU alone is insufficient for many workloads. A payment API that does significant I/O (waiting on database queries, external payment gateway calls) may have low CPU utilization even while its Pod is overloaded — request queues growing, latencies increasing, but CPU sitting at 20%. Custom metrics directly represent load at the application level.

**Metric types in HPA v2:**

**`Pods` type** — metric per Pod, aggregated by average:
```yaml
- type: Pods
  pods:
    metric:
      name: http_requests_per_second    # Prometheus metric name (via adapter)
    target:
      type: AverageValue
      averageValue: "100"               # target: 100 RPS per Pod
                                        # 500 RPS total with 5 Pods → scale out
```

**`Object` type** — metric from a specific Kubernetes object:
```yaml
- type: Object
  object:
    metric:
      name: requests-per-second
    describedObject:
      apiVersion: networking.k8s.io/v1
      kind:       Ingress
      name:       payments-ingress       # metric from the Ingress object
    target:
      type:  Value
      value: "10k"                       # total RPS across all Pods
```

**`External` type** — metric not associated with any Kubernetes object:
```yaml
- type: External
  external:
    metric:
      name: sqs_queue_depth
      selector:
        matchLabels:
          queue: payment-processing
    target:
      type:  AverageValue
      averageValue: "50"                 # target: 50 messages per Pod
                                         # 500 messages → 10 Pods
```

**Complete example — payment processor scaling on SQS queue depth:**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-processor-hpa
  namespace: payments
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-processor

  minReplicas: 1
  maxReplicas: 30

  metrics:
    # Primary: SQS queue depth (1 Pod per 50 messages)
    - type: External
      external:
        metric:
          name: sqs_approximate_number_of_messages_visible
          selector:
            matchLabels:
              queue_name: payment-processing-queue
        target:
          type: AverageValue
          averageValue: "50"

    # Safety net: CPU (prevent runaway if queue metric is unavailable)
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 80

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0     # respond immediately to queue growth
      policies:
        - type: Pods
          value: 5
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 120   # 2 minutes: shorter than API (queue drains fast)
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
```

**Prometheus Adapter configuration (bridges Prometheus → HPA):**
```yaml
# prometheus-adapter ConfigMap
rules:
  - seriesQuery: 'http_requests_total{namespace!="",pod!=""}'
    resources:
      overrides:
        namespace: { resource: namespace }
        pod:       { resource: pod }
    name:
      matches:     "^(.*)_total$"
      as:          "${1}_per_second"
    metricsQuery:  'sum(rate(<<.Series>>{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)'
    # Exposes: http_requests_per_second (rate over 2-minute window)
    # Accessible at: custom.metrics.k8s.io/namespaces/payments/pods/*/http_requests_per_second
```

**Q9. What is KEDA (Kubernetes Event-Driven Autoscaling) and when does it replace HPA?**
A: KEDA is a Kubernetes autoscaler that extends HPA's custom metrics support with pre-built scalers for dozens of event sources — SQS, Kafka, RabbitMQ, Redis, Azure Service Bus, GCP Pub/Sub, and more. Instead of deploying a custom Prometheus Adapter and writing PromQL queries, you configure a `ScaledObject` that KEDA translates into HPA resources automatically.

**Why KEDA over HPA + custom metrics:**
- **Scale to zero**: HPA has a minimum of `minReplicas: 1` (effectively; setting 0 is allowed but HPA won't scale back up without a trigger). KEDA natively scales deployments to zero when there are no messages to process and back up when messages arrive — critical for cost in batch/event processing workloads.
- **Pre-built scalers**: no Prometheus Adapter configuration needed. KEDA connects directly to SQS, Kafka, Redis, etc.
- **Simpler configuration**: one `ScaledObject` vs three separate resources (HPA + adapter ConfigMap + ServiceAccount).

```yaml
# KEDA ScaledObject: scale payment processor based on SQS queue depth
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: payment-processor-scaledobject
  namespace: payments
spec:
  scaleTargetRef:
    name: payment-processor           # Deployment to scale

  minReplicaCount: 0                  # scale to ZERO when queue is empty
  maxReplicaCount: 30

  pollingInterval:  15                # check queue depth every 15 seconds
  cooldownPeriod:   120               # wait 2 min before scaling to zero

  triggers:
    - type: aws-sqs-queue
      authenticationRef:
        name: keda-aws-credentials    # IRSA or explicit credentials
      metadata:
        queueURL:          https://sqs.ap-south-1.amazonaws.com/123/payment-processing
        queueLength:       "50"       # target: 50 messages per Pod replica
        awsRegion:         ap-south-1
        identityOwner:     pod        # use Pod's IRSA role
```

**What KEDA creates under the hood:**
KEDA creates an HPA resource automatically for the `ScaledObject`, with KEDA acting as the custom metrics provider (implementing `external.metrics.k8s.io`). The HPA you see in `kubectl get hpa` is KEDA-managed — don't edit it directly.

```bash
kubectl get hpa -n payments
# NAME                                    REFERENCE                        TARGETS
# keda-hpa-payment-processor-scaledobject Deployment/payment-processor    0/50 (SQS depth per Pod)
```

**Scale-to-zero flow:**
```
SQS queue empty for 120 seconds (cooldownPeriod):
  KEDA scales payment-processor Deployment to 0 replicas
  No Pods running; no compute cost

First message arrives in SQS:
  KEDA detects queue depth > 0
  KEDA scales Deployment to 1 replica (or more, based on queue depth)
  Pod starts (30–60 seconds for Node.js startup)
  Pod begins consuming messages

Queue grows to 500 messages:
  500 / 50 (queueLength) = 10 desired replicas
  KEDA/HPA scales to 10 replicas
  All processing in parallel
```

**Scale-to-zero is ideal for:**
- Batch payment processors (daily reconciliation jobs).
- Webhook delivery workers (active only when events arrive).
- Scheduled report generators.
- Any worker that should not consume compute when idle.

**Scale-to-zero is NOT appropriate for:**
- API servers (must be always ready to serve traffic).
- Services on the critical path (the startup latency of going from 0 → 1 is unacceptable for user-facing requests).

## Section 6: Interaction with Cluster Autoscaler

**Q10. How does HPA interact with the Cluster Autoscaler (CA) and what happens when HPA wants more Pods than the cluster has capacity for?**
A: HPA and Cluster Autoscaler (CA) are complementary — they operate at different layers:
- **HPA**: scales Pods within the cluster (adjusts replica counts).
- **CA**: scales nodes in the cluster (adjusts node counts to fit Pod demands).

**The interaction loop:**
```
Step 1: HPA detects high CPU, scales payment-api from 5 → 15 Pods

Step 2: Scheduler tries to place 10 new Pods:
  Node 1: capacity for 3 more Pods → scheduled
  Node 2: capacity for 2 more Pods → scheduled
  Node 3: full
  5 Pods placed, 5 Pods remain Pending (no capacity)

Step 3: Cluster Autoscaler detects Pending Pods
  CA: "There are Pending Pods that can't be scheduled due to insufficient resources"
  CA calls cloud API: add 2 new nodes to the Auto Scaling Group

Step 4: New nodes join the cluster (2–5 minutes)
  New nodes register with Kubernetes
  5 Pending Pods scheduled on new nodes

Step 5: All 15 Pods running, metrics normalizing
  Eventually, if load drops and HPA scales back to 5 Pods:
  CA detects underutilized nodes (nodes with only 1–2 Pods, below 50% utilization)
  CA removes underutilized nodes (with Pod eviction grace period)
```

**The timing gap — Pods pending while nodes provision:**
The 2–5 minute node provisioning delay is the critical vulnerability. During a sudden traffic spike:
```
T=0s:   Traffic spike begins; all 5 Pods at 95% CPU
T=15s:  HPA detects (first metrics scrape)
T=30s:  HPA scales to 15 Pods
T=30s:  5 Pods scheduled on existing nodes; 10 Pods Pending
T=30s:  CA detects Pending Pods; requests new nodes from cloud API
T=3min: New nodes join the cluster
T=3.5min: 10 Pending Pods scheduled; all 15 Pods serving traffic

During T=30s to T=3.5min: only 10 Pods serving traffic
  If original 5 Pods were at 95% CPU and load doubled:
  10 Pods each at ~95% CPU — still overloaded for 3 minutes
```

**Mitigation — cluster overprovisioning:**
Pre-warm spare node capacity using a low-priority "placeholder" Deployment:

```yaml
# Placeholder Deployment: occupies node capacity with PriorityClass Pause
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-overprovisioner
spec:
  replicas: 5              # 5 placeholder Pods
  template:
    spec:
      priorityClassName: overprovisioning  # very low priority
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.9
          resources:
            requests:
              cpu:    "500m"
              memory: "1Gi"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: overprovisioning
value: -1                  # below zero = below any regular Pod
globalDefault: false
preemptionPolicy: Never
```

When new real Pods need scheduling and no node capacity exists:
1. Real Pods (with default priority 0) preempt the placeholder Pods (priority -1).
2. Placeholder Pods are evicted and go Pending.
3. Real Pods are immediately scheduled on the freed capacity.
4. CA sees the now-Pending placeholder Pods as the trigger to add new nodes.
5. New nodes join; placeholder Pods are rescheduled on the new nodes.

Result: real Pods get capacity in seconds (preemption), not minutes (node provisioning). The node provisioning lag is absorbed by the placeholder Pods.

**Node provisioning can also be accelerated with:**
- **Karpenter** (AWS): provisions individual EC2 instances per-Pod-requirement in ~30–60 seconds (vs CA's 2–5 minutes), selecting instance types automatically.
- **Spot/Preemptible instances with warm pools**: pre-started instances waiting to join the cluster within seconds.

## Section 7: Common Pitfalls and Operational Issues

**Q11. What are the most common HPA misconfiguration mistakes and their symptoms?**
A:

**Pitfall 1 — No resource requests (or incorrect requests):**
```
Symptom: TARGETS shows <unknown>/70% or wildly oscillating numbers
Cause:   No CPU request → HPA cannot compute utilization denominator
         Too-low requests → HPA perceives 400% utilization and scales immediately to maxReplicas
Fix:     Set requests based on actual observed usage (kubectl top pods)
```

**Pitfall 2 — maxReplicas too high, database connection pool exhausted:**
```
Symptom: HPA scales to 100 Pods; database returns "too many connections"; all Pods fail
Cause:   Each Pod opens N connections to PostgreSQL; 100 Pods × 10 connections = 1000
         PostgreSQL default max_connections: 100 → connection refused errors
Fix:
  Option A: Add PgBouncer as a connection pooler between Pods and PostgreSQL
  Option B: Set maxReplicas = floor(max_db_connections / connections_per_pod)
            e.g., 100 connections / 5 per Pod = max 20 Pods
  Option C: Use RDS Proxy (AWS) to multiplex connections transparently
```

**Pitfall 3 — HPA fighting with a manual replica change:**
```
Symptom: You manually set replicas to 20 (kubectl scale); HPA immediately changes it back to 5
Cause:   HPA continuously reconciles replicas toward its computed value
         Manual replica changes are overridden by HPA within 15–30 seconds
Fix:
  Never manually scale a Deployment managed by HPA
  To temporarily pause: kubectl patch hpa <name> -p '{"spec":{"maxReplicas":0}}'
  (Setting maxReplicas to 0 effectively freezes HPA)
  Or: temporarily annotate the HPA with 'kubectl annotate hpa <name> kubectl.kubernetes.io/last-applied-configuration='
```

**Pitfall 4 — Thrashing (rapid scale-up and scale-down):**
```
Symptom: Replicas oscillate every few minutes: 5 → 15 → 5 → 15 → 5
Cause:   Traffic is bursty; scale-down stabilization window too short
         New Pods starting causes metric to drop; HPA scales in; metric rises again
Fix:
  Increase scaleDown stabilizationWindowSeconds (default 300, try 600 for bursty traffic)
  Add scale-down policies to limit rate: at most 10% per minute
  Ensure Pods have startup time to register their metrics before HPA re-evaluates
```

**Pitfall 5 — HPA scaling on memory: dangerous in most cases:**
```
Symptom: HPA scales out; new Pods also fill memory; cascade to maxReplicas
Cause:   Memory is not compressible (unlike CPU). If a Pod has a memory leak,
         adding more Pods just adds more leaking Pods — memory usage per Pod
         doesn't decrease; it increases. HPA scaling on memory treats a leak
         as a load problem and makes it worse.
Fix:
  Investigate whether memory growth is a leak or legitimate working-set growth
  For legitimate growth (caches, data loading): consider scaling on RPS or queue depth instead
  For memory leaks: fix the leak; restart Pods periodically as a bandaid (not HPA)
  Memory HPA is appropriate only for stateless apps where memory usage is
  proportional to request load and not subject to leaks
```

**Pitfall 6 — Slow Pod startup masking scaling effectiveness:**
```
Symptom: HPA scales to 15 Pods; after 5 minutes, traffic is still high;
         checking kubectl get pods shows many Pods in ContainerCreating
Cause:   Pod startup takes 60–120 seconds (image pull + JVM warmup + health check startPeriod)
         During startup, new Pods accept no traffic; load remains on old Pods
Fix:
  Reduce image size (pull time)
  Use pre-pulled images (DaemonSet pull or node-level image cache)
  Implement readiness probes carefully — Pod should only become Ready when it can
  handle full traffic (cache warmed, connections established)
  Consider startup probes (separate from readiness) for slow initialization
  Scale up earlier by reducing target utilization (60% instead of 80%)
```

**Q12. How do you debug an HPA that is not scaling when you expect it to?**
A:

```bash
# Step 1: Check HPA status — is it seeing metrics?
kubectl describe hpa payment-api-hpa -n payments

# Look for in Events section and Status:
# Normal   SuccessfulRescale   New size: 8; reason: cpu resource utilization
# Warning  FailedGetScale      Unable to fetch metrics
# Warning  DesiredReplicasComputed  computed desired replicas: 8; limiting to max 5

# Step 2: Check if metrics are flowing
kubectl get --raw "/apis/metrics.k8s.io/v1beta1/namespaces/payments/pods" | jq .

# Verify Metrics Server is running:
kubectl get pods -n kube-system | grep metrics-server
kubectl top pods -n payments           # if this fails, HPA cannot get CPU metrics

# Step 3: Check if metric is above the scaling threshold
kubectl describe hpa payment-api-hpa | grep -A5 "Metrics:"
# Metrics:    ( current / target )
#   resource cpu on pods  (as a percentage of request):  65% (325m) / 70%
#                                                          ↑
# 65% is within 10% of 70% target → HPA will NOT scale (tolerance band)
# Would need to exceed 70% × 1.1 = 77% to trigger scale-up

# Step 4: Check if at maxReplicas
kubectl get hpa payment-api-hpa -n payments
# REPLICAS: 5   MAXPODS: 5
# Already at max — HPA cannot scale further even if metric is high
# Fix: increase maxReplicas

# Step 5: Check scaling behavior constraints
kubectl describe hpa payment-api-hpa | grep -A20 "Conditions:"
# AbleToScale: True / False
# ScalingActive: True / False
# ScalingLimited: True   ← scaling is being limited (by policy or min/max)

# Step 6: Check for Pods in non-Ready state (suppresses scaling)
kubectl get pods -n payments | grep -v Running

# Step 7: Check Events for specific error messages
kubectl get events -n payments --field-selector reason=FailedGetScale
# failed to get cpu utilization: missing request for cpu in container payment-api

# Step 8: For custom metrics, verify the metric is accessible
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1/namespaces/payments/pods/*/http_requests_per_second"

# 200 with data: metric flowing correctly
```

## Section 8: Scenario / System Design Style Questions

**Q13. "Design the HPA configuration for a payment API that must handle a 10× traffic spike within 2 minutes without overwhelming the database."**
A:

```
Constraints:
  Normal traffic:  100 RPS, 5 Pods, each at ~60% CPU
  Peak traffic:    1000 RPS (10× spike during end-of-month reconciliation)
  Database limit:  100 PostgreSQL connections (10 per Pod, 10 Pods max without pooler)
  Startup time:    ~45 seconds (NestJS + DB connection pool warmup)
  Target:          Handle 10× spike within 2 minutes

Analysis:
  At 10× traffic: need ~50 Pods (each handling 20 RPS at 60% CPU)
  But database limits us to 10 Pods (100 connections / 10 per Pod)
  Solution: add PgBouncer connection pooler → removes DB connection constraint
  With PgBouncer: 100 application connections → 100 PgBouncer connections → 10 PostgreSQL

Updated constraints with PgBouncer:
  Max Pods: 50 (cluster capacity)
  Pod CPU request: 500m (observed baseline: 300m, request set above that)
  Target: 60% CPU utilization (300m / 500m = 60% at normal load)
  Startup time: 45 seconds

HPA design:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-api-hpa
  namespace: payments
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-api

  minReplicas: 5     # always-on: enough for baseline traffic + zone redundancy
  maxReplicas: 50    # spike headroom; constrained by cluster capacity

  metrics:
    # CPU: primary scaling signal
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60   # 60% of 500m request = 300m target
                                   # Lower than typical 70% to provide headroom;
                                   # at 60% CPU, 40% headroom absorbs burst
                                   # before next scaling step completes

    # RPS: scale before CPU saturates (I/O-heavy payments may max out before CPU)
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "20"       # 20 RPS per Pod; at 1000 RPS → 50 Pods

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0    # respond immediately — every second matters
      policies:
        - type: Percent
          value: 200                   # triple replicas per step (aggressive)
          periodSeconds: 30            # shorter period: 5→15→45 in 60 seconds
        - type: Pods
          value: 10
          periodSeconds: 30
      selectPolicy: Max                # use whichever is more aggressive

    scaleDown:
      stabilizationWindowSeconds: 600  # 10 minutes: spikes often return
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
      selectPolicy: Min

  # With this configuration:
  # T=0s:    Spike begins; 5 Pods at 100% CPU (200% of target)
  # T=15s:   HPA detects (metrics scrape)
  # T=15s:   Desired = ceil(5 × (100/60)) = ceil(8.33) = 9 Pods
  #           Percent policy 200%: add 10 Pods → 15 Pods
  #           Pods policy: add 10 Pods → 15 Pods
  #           selectPolicy Max → 15 Pods
  # T=30s:   Scheduler places 10 new Pods (assume cluster has capacity)
  # T=30s:   HPA re-evaluates with 15 Pods: still high → scale to 35
  # T=60s:   All 35 Pods serving; CPU dropping toward target
  # T=90s:   CPU near 60%; HPA stabilizes around 45-50 Pods

  # Cluster overprovisioner (separate):
  # Pre-warm 10 spare nodes with placeholder Pods
  # Ensures new Pods are placed immediately without CA delay

Supporting infrastructure:
  PgBouncer (pool_mode=transaction, pool_size=10 per app Pod):
    Application Pool: payment-api → PgBouncer → PostgreSQL
    Each payment-api Pod connects to PgBouncer, not PostgreSQL directly
    PgBouncer multiplexes: 50 Pods × 5 connections = 250 PgBouncer connections
    PgBouncer → PostgreSQL: maintains 100 connections regardless of Pods

  Pod resource spec:
    resources:
      requests:
        cpu:    "500m"     # observed usage: ~300m baseline
        memory: "512Mi"    # observed usage: ~350Mi
      limits:
        cpu:    "2000m"    # burst: can use up to 2 vCPU (throttled, not killed)
        memory: "1024Mi"   # OOM killed at 1GB

  Readiness probe (critical — controls when traffic reaches new Pods):
    httpGet:
      path: /health/ready
      port: 3000
    initialDelaySeconds: 10
    periodSeconds:       5
    failureThreshold:    3
    # /health/ready returns 200 only when:
    #   - DB connection pool established
    #   - Startup migrations complete
    #   - Cache warmed (if applicable)
    # Ensures new Pods don't receive traffic until truly ready
```

**Q14. "HPA is scaling your payment processor to 100 Pods but performance is not improving. The queue depth is still growing. What is happening and how do you fix it?"**
A:

```
Symptom: 100 Pods running; SQS queue depth still growing; HPA at maxReplicas
         Individual Pods are processing messages, but the queue isn't draining

Diagnosis tree:

Check 1: Are the Pods actually processing?
  kubectl logs -l app=payment-processor -n payments --tail=50 | grep "processed"
  If logs show processing: Pods are working but throughput is insufficient
  If no processing logs: Pods are running but not consuming from the queue

Check 2: Is the bottleneck in the Pods or downstream?
  kubectl top pods -l app=payment-processor -n payments
  If CPU < 20%: Pods are waiting on something (DB, external API, network)
  If CPU > 80%: Pods are compute-bound; need more CPU or more efficient code

  Check DB latency:
  kubectl exec -it payment-processor-xxx -- psql $DATABASE_URL -c "
    SELECT mean_exec_time, calls, query
    FROM pg_stat_statements
    ORDER BY mean_exec_time DESC LIMIT 5"
  If DB queries slow (> 100ms): DB is the bottleneck, not Pods

  Check external API latency:
  Look at application metrics: p99 latency for JusPay/Razorpay API calls
  If > 500ms: payment gateway is throttling you

  Common cause in fintech: payment gateway rate limit
    Each payment processor Pod makes API calls to JusPay/Razorpay
    100 Pods × 10 req/s per Pod = 1000 req/s to payment gateway
    Payment gateway rate limit: 500 req/s per account
    500 req/s rate-limited → 500 requests/s queued/retried
    Queue grows even with 100 Pods because gateway limits throughput

Fix 1: If DB is the bottleneck
  Add read replicas for read-heavy payment lookups
  Add PgBouncer (if connection pool is exhausted)
  Add indexes for payment lookup queries
  maxReplicas should be set to: floor(max_db_connections / connections_per_pod)

Fix 2: If payment gateway is rate-limiting
  Reduce maxReplicas to: floor(gateway_rate_limit / requests_per_pod)
  e.g., 500 req/s limit / 10 req/s per Pod = max 50 Pods (not 100)
  Implement exponential backoff in the processor for 429 responses
  Consider batching payment requests if gateway supports bulk API

Fix 3: If Pods are compute-bound at 100 Pods
  Current maxReplicas is cluster ceiling; need more node capacity
  Increase CA node group maxSize
  Or: optimize the payment processing code (CPU profiling)
  Or: increase Pod CPU limits/requests to use larger instance types

Fix 4: If Pods are idle (CPU < 20%) and queue is growing
  Concurrency issue: each Pod processes messages serially (one at a time)
  Each message takes 5 seconds; Pod processes 12 messages/minute
  100 Pods × 12 msg/min = 1200 msg/min; queue growing at 2000 msg/min
  
  Fix: increase concurrency within each Pod
  // process multiple messages concurrently within one Pod
  const CONCURRENCY = 10;  // process 10 messages in parallel per Pod
  
  const consumer = new SqsConsumer({
    queueUrl: QUEUE_URL,
    batchSize: 10,              // fetch 10 messages at once
    handleMessage: processPayment,
    handleMessageBatch: undefined,
  });
  
  // Or: use SQS batch processing
  // 100 Pods × 10 concurrent × 12 msg/min = 12,000 msg/min capacity
  
  Re-evaluate KEDA configuration:
  queueLength: 50 means 1 Pod per 50 messages
  If each Pod processes only 12 msg/min, queue drains in 50/12 ≈ 4 minutes
  For queue growing at 2000 msg/min, need: 2000/12 = 167 Pods
  But maxReplicas is 100 → raise maxReplicas or increase Pod throughput

Fix 5: maxReplicas is the hard limit you've hit
  Accept: the system processes at 100 Pods × throughput; queue will drain eventually
  Reduce SQS message send rate (backpressure to upstream)
  Implement priority queue: process high-value payments first
  Increase maxReplicas (if infrastructure supports it)
  Consider: is the current maxReplicas incorrectly set too low?
```

## Quick Reference

| Metric type | Target type | Example | Use when |
|---|---|---|---|
| `Resource` (CPU) | `Utilization` (% of request) | `averageUtilization: 70` | Application is CPU-bound |
| `Resource` (memory) | `Utilization` (% of request) | `averageUtilization: 80` | Memory proportional to load (not leaks) |
| `Pods` | `AverageValue` | `averageValue: "100"` | Per-Pod custom metric (RPS, connections) |
| `Object` | `Value` or `AverageValue` | `value: "10k"` | Metric from a K8s object (Ingress RPS) |
| `External` | `Value` or `AverageValue` | `averageValue: "50"` | SQS depth, CloudWatch metric |

| Behavior field | Default | Effect |
|---|---|---|
| `scaleUp.stabilizationWindowSeconds` | `0` | Scale up immediately |
| `scaleDown.stabilizationWindowSeconds` | `300` | Wait 5 min before scaling in |
| `scaleUp.selectPolicy: Max` | — | Use most aggressive scale-up policy |
| `scaleDown.selectPolicy: Min` | — | Use most conservative scale-in policy |
| `type: Percent` policy | — | Scale by % of current replicas |
| `type: Pods` policy | — | Scale by absolute Pod count |

| Symptom | Likely cause | Fix |
|---|---|---|
| `TARGETS: <unknown>` | No resource requests | Add `resources.requests.cpu` |
| HPA stuck at maxReplicas | Too-low maxReplicas or DB bottleneck | Raise maxReplicas; add PgBouncer |
| Replica thrashing | Scale-down window too short | Increase `stabilizationWindowSeconds` |
| HPA ignores high metric | Within ±10% tolerance band | Lower target utilization |
| HPA overriding manual scale | HPA reconciles continuously | Never manual-scale HPA-managed Deployments |
| Scale-up slow during spikes | CA node provisioning delay | Cluster overprovisioner (placeholder Pods) |

## The Core Mental Model

```
HPA = continuous feedback loop maintaining a metric at a target value

The formula:
  desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric)
  Applied every 15 seconds; ±10% tolerance band prevents micro-adjustments

The prerequisite chain:
  CPU requests set correctly → Metrics Server → metrics.k8s.io → HPA computes ratio
  Custom metrics → Prometheus → Adapter → custom.metrics.k8s.io → HPA computes ratio
  External metrics → KEDA/Adapter → external.metrics.k8s.io → HPA computes ratio
  Any gap in this chain → HPA either cannot scale or scales incorrectly

The two-speed rule:
  Scale up FAST (stabilizationWindowSeconds: 0)   → every second of overload costs latency
  Scale down SLOW (stabilizationWindowSeconds: 300) → premature scale-in causes thrashing

The maxReplicas checklist:
  Does your database have enough connections? (max_db_connections / per_pod)
  Does your payment gateway have enough rate limit? (gateway_limit / per_pod_rps)
  Does your cluster have enough node capacity? (CA or Karpenter must provision)
  Does your downstream have enough capacity? (every dependency has a limit)
  maxReplicas is the minimum of all these constraints

CPU vs custom metrics:
  CPU: simple, always available, wrong for I/O-bound services
  RPS: better for web services (scales on actual load, not compute consumption)
  Queue depth: best for worker services (directly measures backlog to drain)
  Combination: CPU as safety net + RPS or queue depth as primary

KEDA for event-driven scaling:
  Scale to ZERO: workers cost nothing when idle (critical for batch processing)
  Pre-built scalers: SQS, Kafka, RabbitMQ — no custom adapter needed
  Use KEDA for: payment processors, webhook workers, report generators
  Use HPA for: API servers (must never scale to zero)

The cluster capacity gap:
  HPA scales Pods → CA scales Nodes → 2-5 minute provisioning gap
  Gap mitigation: cluster overprovisioner (placeholder Pods absorb real traffic
  via preemption; CA triggered by displaced placeholder Pods, not real Pods)
  Or Karpenter: provisions nodes in ~60 seconds (10× faster than CA)
```

**Tip for the interview:** HPA questions at 5 YOE almost always escalate to one of three places: (1) the resource request prerequisite — knowing immediately that `TARGETS: <unknown>` means no CPU request is set, that HPA targets are percentages of the request (not the limit or node capacity), and that an incorrectly low request (e.g., `100m` for an app that uses `400m` idle) causes HPA to perceive constant 400% utilization and immediately scale to maxReplicas is the operational nuance that separates someone who has debugged HPA in production from someone who has only read the docs; (2) the scale-down stabilization window and thrashing — being able to explain that the default 300-second stabilization window exists because a 5-minute low in traffic is often followed by another spike (so scaling in would just require scaling back out 60 seconds later, wasting the 45-second Pod startup time), and that the solution to thrashing is increasing the window or adding rate-limiting scale-down policies, shows you understand the control theory behind HPA rather than just its configuration; (3) the maxReplicas cascade failure pattern — knowing that scaling to 100 Pods when your PostgreSQL only has 100 connections causes every Pod to fail simultaneously (connection refused, cascade to all 100 Pods), and that the fix is either PgBouncer/RDS Proxy to multiplex connections or correctly setting maxReplicas to floor(max_connections / per_pod_connections), is the fintech-specific operational awareness that shows you've thought about the full system, not just the autoscaler in isolation.
