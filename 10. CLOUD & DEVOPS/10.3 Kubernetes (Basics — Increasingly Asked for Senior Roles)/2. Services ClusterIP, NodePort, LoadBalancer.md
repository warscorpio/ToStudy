# Kubernetes Services: ClusterIP, NodePort, LoadBalancer — Interview Q&A (5 YOE Level)

---

## Section 1: The Problem — Why Kubernetes Services Exist

**Q1. What problem does a Kubernetes Service solve that Pod IPs cannot?**
A: Pods are ephemeral — they are created and destroyed constantly by deployments, rollouts, autoscalers, and node failures. Every time a Pod is created, it gets a new IP address assigned from the cluster's Pod CIDR. A Pod that was at `10.0.1.5` yesterday may be at `10.0.2.12` today after a rolling update. A Pod that is at `10.0.1.5` right now will get a different IP when it restarts after a crash.

If Pod A needs to call Pod B, it cannot hard-code Pod B's IP — that IP is gone after the next restart. The naive solution — service discovery via polling the Kubernetes API for current Pod IPs — works but creates tight coupling between every service and the Kubernetes API, and requires every client to implement its own discovery logic.

A Kubernetes Service is a stable network identity for a set of Pods. It has:
- A **stable virtual IP** (ClusterIP) that never changes for the lifetime of the Service.
- A **stable DNS name** (`<service-name>.<namespace>.svc.cluster.local`) that resolves to that virtual IP.
- A **selector** that dynamically tracks which Pods belong to the Service, updating as Pods come and go.

The client calls `payment-service:3000` — a DNS name that resolves to a stable virtual IP — and never thinks about which Pod IPs are currently healthy. The Service handles that abstraction.

**Q2. What is kube-proxy and how does it implement Service routing?**
A: kube-proxy is a Kubernetes component that runs on every node in the cluster. It watches the Kubernetes API for Service and Endpoint objects and configures the node's network to implement the routing rules those objects define.

**What kube-proxy configures:**

**iptables mode (most common):**
kube-proxy writes iptables DNAT (Destination NAT) rules for each Service. When a packet is sent to the Service's ClusterIP, iptables intercepts it and rewrites the destination IP to one of the healthy Pod IPs (chosen randomly from the current Endpoints list):

```
Packet: dst=10.96.0.50:3000 (ClusterIP)
iptables DNAT rule:
  IF dst=10.96.0.50:3000:
    33% chance → rewrite dst to 10.0.1.5:3000 (Pod A)
    33% chance → rewrite dst to 10.0.1.6:3000 (Pod B)
    33% chance → rewrite dst to 10.0.2.2:3000 (Pod C)
```

When a Pod is unhealthy (fails readiness probe), kube-proxy removes its IP from the DNAT rule — traffic stops going to it within seconds of the Endpoint being removed.

**IPVS mode (better at scale):**
Instead of iptables chains (which are O(n) to traverse), IPVS (IP Virtual Server) uses a hash table for O(1) lookups. At hundreds of Services and thousands of endpoints, IPVS dramatically reduces iptables rule processing overhead. IPVS also supports more load balancing algorithms (round-robin, least connections, destination hashing) compared to iptables' random selection.

**eBPF mode (e.g., Cilium):**
Some CNI plugins replace kube-proxy entirely with eBPF programs attached to network interfaces. eBPF bypasses the iptables/IPVS stack entirely, offering the lowest latency and most flexibility but requiring a compatible CNI.

**How DNS fits in:**
CoreDNS (the cluster DNS server) resolves `payment-service.default.svc.cluster.local` to the Service's ClusterIP. The client has a stable DNS name → resolves to stable ClusterIP → kube-proxy DNAT routes to a healthy Pod IP. Each layer is independently stable: the DNS name never changes, the ClusterIP never changes, but the Pod IPs it routes to change as Pods come and go.

## Section 2: ClusterIP

**Q3. What is a ClusterIP Service and what exactly does it provide?**
A: ClusterIP is the default Service type — it exposes the Service on a stable virtual IP that is reachable only from within the cluster. The ClusterIP is allocated from a reserved IP range (typically `10.96.0.0/12` by default) that is separate from both Pod IPs and Node IPs.

```yaml
# ClusterIP Service (minimal definition)
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  namespace: payments
spec:
  type: ClusterIP          # default; can be omitted
  selector:
    app: payment-api       # matches Pods with this label
  ports:
    - name: http
      port: 3000           # port exposed by the Service (what clients call)
      targetPort: 3000     # port on the Pod (what the container listens on)
      protocol: TCP
```

**What this creates:**
```
Service:     payment-service.payments.svc.cluster.local
ClusterIP:   10.96.45.128   ← stable; never changes
Port:        3000

Endpoints (dynamic; updated as Pods start/stop):
  10.0.1.5:3000   (Pod payment-api-abc12, Running, Ready)
  10.0.1.6:3000   (Pod payment-api-def34, Running, Ready)
  10.0.2.2:3000   (Pod payment-api-ghi56, Running, Ready)
```

**How clients use it (inside the cluster):**
```javascript
// NestJS: connect to payment-service from another service
// Option 1: short name (same namespace)
const url = 'http://payment-service:3000';

// Option 2: fully qualified (cross-namespace)
const url = 'http://payment-service.payments.svc.cluster.local:3000';

// Option 3: environment variable (Kubernetes injects these automatically)
// K8s injects: PAYMENT_SERVICE_SERVICE_HOST=10.96.45.128
//              PAYMENT_SERVICE_SERVICE_PORT=3000
const url = `http://${process.env.PAYMENT_SERVICE_SERVICE_HOST}:${process.env.PAYMENT_SERVICE_SERVICE_PORT}`;
```

**DNS resolution detail:**
Kubernetes configures each Pod's `/etc/resolv.conf` with:
```
nameserver 10.96.0.10        # CoreDNS ClusterIP
search payments.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

The `search` domain list means `payment-service` (unqualified) is tried as `payment-service.payments.svc.cluster.local` before falling through to external DNS. `ndots:5` means names with fewer than 5 dots try all search domains first — which is why `curl http://payment-service:3000` works without the full qualified name.

**Port vs targetPort:**
```yaml
ports:
  - port:       80           # Service port (what clients call)
    targetPort: 3000         # Container port (what the app listens on)
```
`port` is what the client uses; `targetPort` is where traffic lands on the Pod. They can differ — a common pattern is exposing port 80 externally while the application binds port 3000 internally. `targetPort` can also be a named port (referencing a port name defined in the Pod spec) rather than a number.

**Q4. What is a Headless Service and when is it used instead of ClusterIP?**
A: A Headless Service is a ClusterIP Service with `clusterIP: None`. Instead of a single stable virtual IP with kube-proxy-based load balancing, a Headless Service's DNS resolves directly to the IPs of all the matching Pods — returning a DNS A record per Pod.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: kafka-headless
spec:
  clusterIP: None            # headless — no virtual IP
  selector:
    app: kafka
  ports:
    - port: 9092
```

**DNS behavior:**
```
Normal ClusterIP:
  kafka.default.svc.cluster.local → 10.96.45.128 (single virtual IP)

Headless:
  kafka-headless.default.svc.cluster.local →
    10.0.1.2   (kafka-0 Pod IP)
    10.0.1.3   (kafka-1 Pod IP)
    10.0.2.1   (kafka-2 Pod IP)
  All three IPs returned; client selects one (usually round-robin by DNS client)
```

**Individual Pod DNS (StatefulSet-specific):**
For StatefulSets, a Headless Service enables stable per-Pod DNS names:
```
kafka-0.kafka-headless.default.svc.cluster.local → 10.0.1.2 (always kafka-0's IP)
kafka-1.kafka-headless.default.svc.cluster.local → 10.0.1.3 (always kafka-1's IP)
kafka-2.kafka-headless.default.svc.cluster.local → 10.0.2.1 (always kafka-2's IP)
```
These names are stable even as Pods restart (kafka-0 always gets its own DNS name pointing to its current IP). This is what makes StatefulSets viable for stateful distributed systems like Kafka, ZooKeeper, and Cassandra — each node has a stable identity and other nodes can refer to it by name.

**When to use Headless over ClusterIP:**
- **StatefulSets**: always use a Headless Service for peer-to-peer discovery (Kafka brokers discovering each other, Cassandra nodes forming a ring).
- **Client-side load balancing**: gRPC with client-side round-robin needs to know all Pod IPs, not just the virtual IP (kube-proxy's DNAT breaks HTTP/2 multiplexing by pinning all streams to one Pod — see the gRPC vs REST guide). Headless + gRPC client resolves all Pod IPs and distributes RPCs across them.
- **Custom load balancing logic**: when the client (e.g., a database driver with read/write splitting) needs to know individual Pod IPs to make intelligent routing decisions.

## Section 3: NodePort

**Q5. What is a NodePort Service and how does it differ from ClusterIP?**
A: A NodePort Service extends ClusterIP by additionally opening a port on every node in the cluster. External traffic reaching any node on that port is forwarded to the Service, which distributes it to healthy Pods — regardless of which node the Pod is running on.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-api-nodeport
spec:
  type: NodePort
  selector:
    app: payment-api
  ports:
    - port:       3000       # ClusterIP port (still created)
      targetPort: 3000       # Pod port
      nodePort:   30080      # port opened on every node (30000–32767)
      protocol: TCP
```

**What NodePort creates (cumulative — it includes everything ClusterIP creates):**
```
ClusterIP:   10.96.45.128:3000    ← still exists; internal cluster access unchanged
NodePort:    <any-node-ip>:30080  ← new; external access via any node's IP

Traffic flow (external client):
  Client → Node1-IP:30080
           │
           iptables DNAT on Node1:
             randomly select a healthy Pod IP from all nodes
           │
           → Pod on Node1: 10.0.1.5:3000   (local)
           → Pod on Node2: 10.0.1.6:3000   (proxied across nodes)
           → Pod on Node3: 10.0.2.2:3000   (proxied across nodes)
```

**The NodePort range:**
By default, NodePort allocates from `30000–32767`. This range is configurable in the kube-apiserver's `--service-node-port-range` flag but changing it requires a cluster restart and is rarely done. The restricted range avoids conflicts with well-known ports (< 1024) and the ephemeral port range (typically 32768–60999).

You can specify an exact nodePort value or let Kubernetes assign one:
```yaml
nodePort: 30080  # explicit assignment (must be in range and not in use)
# omit nodePort: Kubernetes assigns a random available port in the range
```

**Cross-node routing:**
When a NodePort packet arrives at Node1 but the selected Pod is on Node2, Node1 proxies the packet to Node2 via its cluster network. This cross-node hop adds latency. To avoid it and keep traffic local to the node handling it:

```yaml
spec:
  externalTrafficPolicy: Local   # only route to Pods on the same node
```

With `externalTrafficPolicy: Local`:
- Traffic to Node1 only reaches Pods on Node1.
- If Node1 has no ready Pods, traffic to Node1 is dropped (no cross-node proxy).
- Benefit: no extra network hop; client source IP is preserved (not rewritten).
- Risk: uneven load distribution if Pods are unevenly distributed across nodes.

With `externalTrafficPolicy: Cluster` (default):
- Traffic to any node reaches Pods on any node.
- Balanced load distribution regardless of Pod placement.
- Client source IP is replaced with the node's IP (because kube-proxy rewrites it for cross-node routing).

**When to use NodePort:**
NodePort is the mechanism rather than the destination — it is the building block that LoadBalancer and Ingress use internally. Direct NodePort use is appropriate for:
- **Development and testing**: quickly expose a service without a cloud load balancer.
- **On-premises clusters** without a cloud provider's load balancer integration.
- **External load balancers you manage yourself**: point a HAProxy or Nginx at all node:nodePort addresses; NodePort provides the stable port entry point.

**What NodePort does NOT provide:**
- A single stable IP (node IPs change if nodes are replaced).
- SSL termination.
- Path-based routing.
- Health check integration (a failed node still has the port open; external LB must check node health separately).

## Section 4: LoadBalancer

**Q6. What is a LoadBalancer Service and what does it provision?**
A: A LoadBalancer Service extends NodePort by additionally provisioning a cloud-provider load balancer that has a stable external IP and automatically sends traffic to the NodePort on healthy nodes.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-api
  annotations:
    # AWS-specific: provision an NLB instead of CLB (Classic)
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    # Make it internal (private VPC only; no public IP)
    service.beta.kubernetes.io/aws-load-balancer-internal: "true"
    # Assign specific Elastic IPs to the NLB (for IP allowlisting by partners)
    service.beta.kubernetes.io/aws-load-balancer-eip-allocations: "eipalloc-abc123,eipalloc-def456"
spec:
  type: LoadBalancer
  selector:
    app: payment-api
  ports:
    - port:       443        # external port on the load balancer
      targetPort: 3000       # Pod port
      protocol: TCP
  # Optional: restrict which source IPs can reach the load balancer
  loadBalancerSourceRanges:
    - "203.0.113.0/24"       # partner office IP range
    - "10.0.0.0/8"           # internal VPC range
```

**What LoadBalancer creates (cumulative — includes ClusterIP AND NodePort):**
```
ClusterIP:    10.96.45.128:443   ← still exists
NodePort:     <all-nodes>:30123  ← Kubernetes-assigned (not exposed directly to users)
LoadBalancer: 52.66.10.5:443     ← cloud LB with stable external IP
              (AWS ELB, GCP Load Balancer, Azure Load Balancer)

Traffic flow:
  External client → 52.66.10.5:443 (cloud LB)
                   │ LB health-checks nodes; routes to healthy nodes
                   → Node1:30123 (NodePort)
                   │ kube-proxy DNAT
                   → Pod:3000
```

**Cloud controller manager — what provisions the load balancer:**
The cloud controller manager (running in the control plane) watches for Services of type LoadBalancer and makes the appropriate cloud API calls:
- On AWS: creates an Elastic Load Balancer (Classic, ALB, or NLB via annotations).
- On GKE: creates a Google Cloud TCP/UDP Load Balancer.
- On AKS: creates an Azure Load Balancer.
- On bare metal: does nothing (no cloud provider) — see Q8 for solutions.

The load balancer's IP appears in the Service's status:
```bash
kubectl get service payment-api
# NAME          TYPE           CLUSTER-IP     EXTERNAL-IP    PORT(S)
# payment-api   LoadBalancer   10.96.45.128   52.66.10.5    443:30123/TCP
```

**AWS Load Balancer Controller (modern approach):**
The in-tree AWS cloud provider creates Classic Load Balancers (CLB) by default — an outdated load balancer type. The AWS Load Balancer Controller (a separate Kubernetes controller) provides ALB and NLB provisioning with modern annotations:

```yaml
# Using AWS Load Balancer Controller for NLB
metadata:
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "external"
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: "ip"
    # "ip" mode: NLB sends directly to Pod IPs, bypassing NodePort and kube-proxy
    # More efficient; source IP preserved at Pod level
```

**Q7. What is the cost implication of LoadBalancer Services, and what is the Ingress alternative?**
A: Each LoadBalancer Service provisions a separate cloud load balancer with a separate external IP. At AWS, an NLB costs approximately $0.008/hour ($5.84/month) plus data processing charges. If you have 20 microservices each with a LoadBalancer Service:

```
20 services × $5.84/month = $116.80/month in load balancer costs alone
(before data processing charges, which can be significant at high traffic volumes)
```

Beyond cost, each LoadBalancer Service exposes one IP:one service — no path-based routing, no host-based routing, no SSL termination at the load balancer level (unless annotated).

**The Ingress alternative:**
An Ingress resource routes HTTP/HTTPS traffic to multiple Services through a single load balancer, using host-based and path-based routing rules:

```yaml
# One Ingress → one cloud load balancer → many services
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: payments-ingress
  annotations:
    kubernetes.io/ingress.class: "alb"  # use AWS ALB Ingress Controller
    alb.ingress.kubernetes.io/scheme: "internet-facing"
    alb.ingress.kubernetes.io/certificate-arn: "arn:aws:acm:ap-south-1:123:certificate/abc"
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path:     /payments
            pathType: Prefix
            backend:
              service:
                name: payment-service
                port:
                  number: 3000
          - path:     /users
            pathType: Prefix
            backend:
              service:
                name: user-service
                port:
                  number: 3000
          - path:     /reports
            pathType: Prefix
            backend:
              service:
                name: reporting-service
                port:
                  number: 3000
```

**Cost comparison:**
```
LoadBalancer per service:    20 services × $5.84/month = $116.80/month
Ingress (single ALB):        1 ALB × $16.20/month      = $16.20/month

Savings: $100.60/month — 86% reduction
```

The Ingress controller (e.g., AWS ALB Ingress Controller, nginx-ingress) is itself typically exposed via one LoadBalancer Service — the single external entry point. All routing decisions happen inside the cluster or at the cloud load balancer level based on Ingress rules.

**When to still use LoadBalancer Services despite Ingress:**
- Non-HTTP traffic (gRPC end-to-end over TCP, MQTT, database protocols) — Ingress handles HTTP only.
- NLB for static IPs (for IP allowlisting by partners).
- Services that must not share a load balancer for compliance or isolation reasons.
- Internal services accessed via PrivateLink (which requires NLB).

## Section 5: Service Internals and Endpoints

**Q8. What is an Endpoints object and how does it relate to a Service?**
A: Every Service that has a selector automatically gets a corresponding Endpoints object — a list of the IP:port pairs of all Pods currently matching the selector and passing their readiness probe. kube-proxy reads the Endpoints object (not the Service itself) to configure DNAT rules.

```bash
kubectl get endpoints payment-service -n payments
# NAME              ENDPOINTS                                   AGE
# payment-service   10.0.1.5:3000,10.0.1.6:3000,10.0.2.2:3000  5d

kubectl describe endpoints payment-service -n payments
# Name:         payment-service
# Namespace:    payments
# Subsets:
#   Addresses:   10.0.1.5,10.0.1.6,10.0.2.2
#   NotReadyAddresses: 10.0.3.1     ← Pod failing readiness probe; not in rotation
#   Ports:       3000/TCP
```

The `NotReadyAddresses` field is critical — a Pod that exists (is Running) but is failing its readiness probe is listed here, not in `Addresses`. kube-proxy only routes traffic to Pods in `Addresses`. This is the mechanism by which a new Pod is not sent traffic until it's ready, and a Pod that starts failing is removed from rotation immediately.

**The Endpoints controller loop:**
```
Pod labeled app=payment-api starts on Node1 (IP: 10.0.1.5)
  ↓
Endpoints controller sees new Pod matches Service selector
  ↓
Pod passes readiness probe (/health returns 200)
  ↓
Endpoints controller adds 10.0.1.5:3000 to Endpoints object
  ↓
kube-proxy on all nodes detects Endpoints change via API watch
  ↓
kube-proxy updates iptables DNAT rules on all nodes to include 10.0.1.5:3000
  ↓
Traffic can now reach 10.0.1.5:3000

Pod fails readiness probe (/health returns 500):
  ↓
Endpoints controller moves 10.0.1.5:3000 from Addresses → NotReadyAddresses
  ↓
kube-proxy removes 10.0.1.5:3000 from DNAT rules on all nodes
  ↓
No new traffic reaches 10.0.1.5 (in-flight connections may still complete)
```

**EndpointSlices (modern replacement for Endpoints):**
At scale (services with thousands of endpoints), the monolithic Endpoints object becomes a scalability problem — every change to the object (one Pod restart) triggers a full object update propagated to every kube-proxy on every node. EndpointSlices split the endpoints into chunks of 100 Pods per slice, so a single Pod change only updates one slice. Kubernetes 1.21+ uses EndpointSlices by default.

```bash
kubectl get endpointslices -n payments -l kubernetes.io/service-name=payment-service
# NAME                     ADDRESSTYPE   PORTS   ENDPOINTS   AGE
# payment-service-abc12    IPv4          3000    3           5d
```

**Endpoints without a selector (ExternalName and manual endpoints):**
Services can exist without a selector — useful for pointing to external services:

```yaml
# ExternalName: map a cluster-internal DNS name to an external DNS name
apiVersion: v1
kind: Service
metadata:
  name: razorpay-api
spec:
  type: ExternalName
  externalName: api.razorpay.com
  # DNS: razorpay-api.default.svc.cluster.local → CNAME → api.razorpay.com
  # No ClusterIP; no Endpoints; pure DNS alias
```

```yaml
# Manual endpoints: point a Service at a specific external IP
apiVersion: v1
kind: Service
metadata:
  name: legacy-payment-db
spec:
  ports:
    - port: 5432
# No selector — create Endpoints manually:
---
apiVersion: v1
kind: Endpoints
metadata:
  name: legacy-payment-db    # must match the Service name
subsets:
  - addresses:
      - ip: 10.100.0.50     # on-premises DB IP (accessible via VPN/Direct Connect)
    ports:
      - port: 5432
```

This pattern lets in-cluster applications connect to `legacy-payment-db:5432` (a stable cluster-internal name) even though the actual database is not in Kubernetes.

## Section 6: Service Discovery and DNS

**Q9. How does Kubernetes service discovery work end-to-end, from DNS query to Pod connection?**
A: Service discovery in Kubernetes is DNS-based — the only thing a client needs to know is a service name. The full resolution chain:

```
Client Pod (payment-api) wants to call fraud-service:8080

Step 1: DNS resolution
  Application: new URL('http://fraud-service:8080/score')
  OS: glibc performs DNS lookup for 'fraud-service'
  /etc/resolv.conf in Pod:
    nameserver 10.96.0.10      ← CoreDNS ClusterIP
    search payments.svc.cluster.local svc.cluster.local cluster.local

  DNS query sent to 10.96.0.10 (CoreDNS):
    Query: fraud-service.payments.svc.cluster.local (A record)
    Response: 10.96.72.30 (ClusterIP of fraud-service)

  (ndots:5 causes unqualified name to first try search domains;
   'fraud-service' has 0 dots, so search domains tried in order:
   fraud-service.payments.svc.cluster.local ← hits immediately if in same namespace)

Step 2: TCP connection to ClusterIP
  Client TCP SYN: dst=10.96.72.30:8080

Step 3: kube-proxy iptables intercepts (on the same node as the client Pod)
  iptables PREROUTING chain:
    Match: dst=10.96.72.30:8080
    DNAT: randomly select endpoint from {10.0.1.7:8080, 10.0.2.3:8080}
    Rewrite: dst=10.0.2.3:8080 (selected Pod IP on Node2)

Step 4: Packet routed to Node2
  CNI plugin routes 10.0.2.3 to Node2 (via overlay, BGP, or VPC routing)
  Node2's CNI delivers packet to fraud-service Pod at 10.0.2.3:8080

Step 5: Connection established
  fraud-service Pod: receives TCP SYN at :8080
  Sends SYN-ACK back to 10.0.1.5 (payment-api Pod IP)
  kube-proxy reverse-NATTs on return path: src=10.0.2.3 rewritten to 10.96.72.30
  payment-api Pod sees connection from 10.96.72.30:8080 (the ClusterIP)

Total path:
  payment-api Pod → (DNS) → CoreDNS → ClusterIP
                  → (iptables DNAT) → Pod IP
                  → (CNI routing) → fraud-service Pod
```

**DNS caching and TTL considerations:**
Kubernetes DNS records have a short TTL (typically 5 seconds). This means Endpoint changes propagate quickly to DNS caches. However, glibc in many Linux distributions caches DNS responses indefinitely by default — override with `ndots` and `options` in `/etc/resolv.conf`, or use a DNS client library that respects TTLs.

For Java applications (which have their own DNS caching): the JVM caches DNS lookups for 30 seconds by default (`networkaddress.cache.ttl=30` in `$JAVA_HOME/jre/lib/security/java.security`). This means Java applications may hold on to stale ClusterIP resolutions for 30 seconds after an Endpoint change — usually acceptable.

**Q10. How do you expose a Service outside the cluster on bare-metal Kubernetes (no cloud provider)?**
A: On bare-metal clusters (on-premises, in a private data center), cloud-provided LoadBalancer Services don't work — there's no cloud API to call. Two open-source solutions fill this gap:

**MetalLB:**
MetalLB is a Kubernetes load balancer implementation for bare-metal clusters. It watches for LoadBalancer Services and assigns them an IP from a configured address pool, then announces that IP on the network:

```yaml
# MetalLB configuration
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: production-pool
  namespace: metallb-system
spec:
  addresses:
    - 192.168.1.200-192.168.1.250    # IP range MetalLB can assign
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: l2-advert
  namespace: metallb-system
spec:
  ipAddressPools:
    - production-pool
```

MetalLB operates in two modes:
- **Layer 2 (ARP/NDP)**: one node announces the IP via ARP (IPv4) or NDP (IPv6). All traffic goes to that node, which distributes via kube-proxy. No BGP router required. Simple but single-node bottleneck.
- **BGP**: MetalLB peers with a BGP router and announces the service IP via BGP. The router load-balances traffic across all nodes with ready Pods via ECMP (Equal-Cost Multi-Path). Higher performance; requires BGP-capable router.

**kube-vip:**
kube-vip uses a Virtual IP that floats between nodes. Leader election determines which node owns the VIP at any time — if the current owner node fails, another node takes the VIP within seconds. Uses either ARP (like MetalLB L2) or BGP for IP announcement.

## Section 7: Advanced Service Configuration

**Q11. What is `sessionAffinity` and when do you use it?**
A: Session affinity (sticky sessions) configures the Service to consistently route traffic from the same client to the same Pod, rather than randomly distributing each request. This is implemented in kube-proxy by creating iptables rules that track the source IP and route it to the same endpoint for a configured duration.

```yaml
spec:
  type: ClusterIP
  sessionAffinity: ClientIP        # default is None (random)
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 1800         # same client IP → same Pod for 30 minutes
  selector:
    app: payment-api
```

**When session affinity is needed:**
- **In-memory session state**: if user session data (authentication tokens, shopping cart) is stored in the Pod's memory rather than in Redis or a database, subsequent requests from the same user must reach the same Pod that has their session. The correct fix is to externalize session state (Redis, DynamoDB) — then session affinity is unnecessary. If you can't externalize, session affinity is the workaround.
- **Stateful processing where order matters**: a streaming API that processes events for a user in order needs each event from that user to go to the same Pod (which holds the in-progress state for that stream).

**When not to use session affinity:**
- It defeats the purpose of load balancing — one Pod may be overloaded while others are idle if all of a user's high-volume traffic is pinned to one Pod.
- Client IP is unreliable as a session identifier when multiple users share an IP (corporate NAT, IPv6 privacy addresses).
- It has no knowledge of Pod health during the affinity window — if the Pod is unhealthy within the affinity period, the request fails (it takes a new DNAT selection after the affinity expires).

**Q12. How do topology-aware routing and `topologyKeys` work to keep traffic local?**
A: Topology-aware routing (formerly `topologyKeys`) is a feature that prefers routing traffic to endpoints in the same zone or region as the source, only routing cross-zone when no local endpoint is available. This reduces cross-AZ data transfer costs (in cloud environments, cross-AZ traffic is billed) and latency.

```yaml
# Topology-aware routing (Kubernetes 1.21+)
apiVersion: v1
kind: Service
metadata:
  name: payment-service
  annotations:
    service.kubernetes.io/topology-mode: "Auto"
    # "Auto": Kubernetes automatically balances local vs cross-zone routing
    #          based on endpoint topology; only applies hints when it's beneficial
```

With `topology-mode: Auto`, kube-proxy assigns topology hints (preferred zone for each endpoint) to EndpointSlices. Each node's kube-proxy prefers endpoints in its own zone:

```
Node in ap-south-1a:
  Prefers: Pods in ap-south-1a
  Falls back to: Pods in ap-south-1b, ap-south-1c (if no healthy local Pods)

Node in ap-south-1b:
  Prefers: Pods in ap-south-1b
  Falls back to: Pods in ap-south-1a, ap-south-1c
```

**Cost implications in AWS EKS:**
Cross-AZ data transfer within a region costs $0.01/GB. For a service transferring 1TB/day of data between Pods, if 50% of that traffic crosses AZs:
```
Without topology-aware routing: 500GB/day × $0.01 = $5/day = $150/month in cross-AZ costs
With topology-aware routing:    100GB/day × $0.01 = $1/day = $30/month (80% reduction)
```

This assumes Pods are distributed across AZs (which is correct for availability) and topology-aware routing keeps most traffic within the same AZ.

**Design decisions explained:**

Payment API uses ClusterIP + Ingress (not LoadBalancer) — one cloud load balancer serves all HTTP services, reducing cost from ~$116/month (one LB per service) to ~$16/month.

Fraud service uses Headless (not ClusterIP) — gRPC's HTTP/2 multiplexing pins all requests to one Pod when routed through ClusterIP's single virtual IP and kube-proxy's DNAT. Headless returns all Pod IPs; the gRPC client distributes RPCs across all of them.

PostgreSQL uses both Headless (for StatefulSet stable DNS) and a separate ClusterIP for read replicas — primary is addressed directly by pod name for writes; the ClusterIP provides load-balanced read distribution across replicas.

NetworkPolicies complement Services — Services provide routing; NetworkPolicies provide access control. Together: the Ingress controller can call payment-api; payment-api can call fraud-service and postgres; nothing else can reach these services.

**Q14. "A developer reports that their gRPC calls to a ClusterIP Service are all going to the same Pod, defeating load balancing. Explain why and fix it."**
A:

```
Root cause: HTTP/2 multiplexing + kube-proxy DNAT = connection pinning

Sequence of events:
  1. gRPC client establishes ONE HTTP/2 connection to fraud-service ClusterIP (10.96.72.30:50051)
  2. kube-proxy DNAT: first connection → rewritten to Pod A IP (10.0.1.7:50051)
     This DNAT rule is tracked in conntrack — the same client IP+port pair
     always routes to the same Pod (connection tracking in iptables DNAT)

  3. gRPC client multiplexes all RPCs over this ONE connection:
     Stream 1: ScorePayment(pay_001) → Pod A
     Stream 3: ScorePayment(pay_002) → Pod A (same connection, same Pod)
     Stream 5: ScorePayment(pay_003) → Pod A (same connection, same Pod)
     Pod B and Pod C receive zero traffic

Why HTTP/1.1 works but gRPC doesn't:
  HTTP/1.1: one connection per request (or short-lived keepalive pool)
  Each new connection to ClusterIP → new conntrack entry → may select different Pod
  Result: connections distributed across Pods over time

  gRPC / HTTP/2: persistent connections; all multiplexed over ONE long-lived connection
  That one connection is conntrack-pinned to one Pod
  Result: all traffic to one Pod indefinitely

Fix Option 1: Headless Service (recommended)
  Change fraud-service from ClusterIP to Headless:

  spec:
    clusterIP: None    ← headless

  DNS now returns: 10.0.1.7, 10.0.1.8, 10.0.2.3 (all Pod IPs)

  Configure gRPC client with round-robin load balancing:

  // Node.js (grpc-js)
  const client = new FraudServiceClient(
    'dns:///fraud-service.payments.svc.cluster.local:50051',
    grpc.credentials.createInsecure(),
    {
      'grpc.service_config': JSON.stringify({
        loadBalancingConfig: [{ round_robin: {} }]
      })
    }
  );
  // 'dns:///' prefix: gRPC resolves ALL A records and distributes RPCs
  // round_robin: each RPC goes to the next Pod in rotation
  // gRPC client maintains connections to ALL Pods; distributes at the RPC level

Fix Option 2: Service Mesh (Istio/Linkerd)
  Install Istio; it injects Envoy sidecars into each Pod.
  Envoy handles load balancing at the connection level (not iptables):
    - Each Envoy sidecar knows all Pod IPs (from xDS API)
    - Load balancing happens in Envoy, not in iptables
    - Works with HTTP/2 and gRPC natively (RPC-level distribution, not connection-level)
    - No application code changes required

  Istiio VirtualService for gRPC:
    apiVersion: networking.istio.io/v1alpha3
    kind: DestinationRule
    spec:
      trafficPolicy:
        loadBalancer:
          simple: ROUND_ROBIN   # or LEAST_CONN for more sophisticated balancing

Fix Option 3: gRPC server-side streaming with client-side reconnect
  Configure gRPC max_connection_age: force clients to reconnect periodically
  Each reconnect gets a new conntrack entry → may select a different Pod

  // Server-side (Go gRPC server example)
  grpc.NewServer(
    grpc.KeepaliveParams(keepalive.ServerParameters{
      MaxConnectionAge:      30 * time.Second,   // close connection after 30s
      MaxConnectionAgeGrace: 5 * time.Second,    // give 5s for RPCs to finish
    }),
  )
  // Client reconnects every 30s → conntrack DNAT re-selects → distributes over time
  // Imperfect: still uneven during the 30s window; headless is better

Verification after fix:
  kubectl exec -it payment-api-pod -- bash
  # Make 100 gRPC calls via grpcurl
  for i in $(seq 100); do
    grpcurl -plaintext fraud-service.payments.svc.cluster.local:50051 \
      com.example.FraudService/ScorePayment '{"payment_id": "'$i'"}'
  done

  # Check which Pods received requests:
  kubectl logs -l app=fraud-service -n payments | grep "ScorePayment" | wc -l
  # Before fix: one Pod shows 100 log lines; others show 0
  # After fix:  ~33 log lines on each of the 3 Pods
```

**Q15. "Your LoadBalancer Service shows EXTERNAL-IP as `<pending>` after 10 minutes. Diagnose it."**
A:

```
Symptom: kubectl get service payment-api shows EXTERNAL-IP: <pending>

This means the cloud controller manager has not (or cannot) provision a load balancer.

Diagnosis steps:

Step 1: Check the Service events for errors
  kubectl describe service payment-api
  # Look at Events section:
  # Normal   EnsuringLoadBalancer  Creating load balancer
  # Warning  SyncLoadBalancerFailed  Error syncing load balancer: ...

  Common error messages:
    "error creating load balancer: ... subnet ... not found"
      → EKS cluster not tagged correctly; LB controller can't find subnets
      Fix: tag public subnets with kubernetes.io/role/elb=1
           tag private subnets with kubernetes.io/role/internal-elb=1

    "error creating load balancer: ... You must specify a region"
      → Cloud controller manager not configured; missing --cloud-provider flag
      → In EKS: may be a Fargate cluster (Fargate doesn't support LoadBalancer Services;
                 use Ingress with ALB Ingress Controller instead)

    "error creating load balancer: ... not authorized to perform: elasticloadbalancing:CreateLoadBalancer"
      → IAM role for the cloud controller manager lacks LB permissions
      Fix: add AmazonEKSLoadBalancingPolicy to the node IAM role
           or configure the AWS Load Balancer Controller with its own IAM role

Step 2: Check the cloud controller manager logs
  kubectl logs -n kube-system -l component=cloud-controller-manager
  # OR for EKS with AWS Load Balancer Controller:
  kubectl logs -n kube-system -l app.kubernetes.io/name=aws-load-balancer-controller

Step 3: Check if you're on a bare-metal cluster
  kubectl get nodes -o wide
  # If EXTERNAL-IP for nodes is <none>: bare-metal cluster; no cloud provider
  # LoadBalancer Services won't work without MetalLB or kube-vip
  # Fix: install MetalLB with an IP pool, or change Service type to NodePort

Step 4: Check cloud provider configuration
  # EKS: check if the cluster has the correct cloud provider tag
  kubectl describe node <node-name> | grep providerID
  # Should show: providerID: aws:///ap-south-1a/i-0abc123def456
  # If empty: cloud provider not configured; LoadBalancer won't work

Step 5: Check VPC/subnet requirements (AWS-specific)
  # EKS: subnets must have correct tags and sufficient IPs
  aws ec2 describe-subnets \
    --filters "Name=tag:kubernetes.io/cluster/<cluster-name>,Values=shared"
  # If no subnets returned: subnets not tagged for EKS; LB can't be provisioned

  # Check subnet IP availability:
  aws ec2 describe-subnets --subnet-ids <subnet-id> \
    --query 'Subnets[0].AvailableIpAddressCount'
  # If 0: subnet is full; NLB can't allocate IPs
  # Fix: use a different subnet or expand the subnet's CIDR

Step 6: Check if the LoadBalancer was created in AWS but not connected
  aws elbv2 describe-load-balancers --query 'LoadBalancers[*].{Name:LoadBalancerName,DNS:DNSName,State:State.Code}'
  # If the LB exists with State=active but Kubernetes still shows <pending>:
  # The cloud controller manager created the LB but lost track of it
  # Fix: delete and recreate the Service to trigger fresh provisioning

Step 7: Workaround while diagnosing
  # Use kubectl port-forward for immediate testing (bypasses the LB issue)
  kubectl port-forward service/payment-api 3000:3000 -n payments
  # Accessible at localhost:3000 for testing; not a production solution
```

## Quick Reference

| Service type | Reachable from | How | Provisions cloud LB |
|---|---|---|---|
| ClusterIP | Inside cluster only | ClusterIP + kube-proxy DNAT | No |
| Headless | Inside cluster (Pod IPs directly) | DNS returns all Pod IPs | No |
| NodePort | Inside cluster + via node IPs | NodePort on all nodes (30000–32767) | No |
| LoadBalancer | Inside cluster + externally | Cloud LB → NodePort → kube-proxy | Yes |
| ExternalName | Inside cluster | DNS CNAME to external name | No |

| Concept | What it is |
|---|---|
| ClusterIP | Stable virtual IP; only inside cluster; kube-proxy DNAT routes to Pod IPs |
| NodePort | Port opened on every node; external traffic enters via any node IP |
| Endpoints | Dynamic list of healthy Pod IPs backing a Service; updated by Endpoints controller |
| EndpointSlices | Chunked Endpoints (100 Pods per slice); scalable for large deployments |
| kube-proxy | Runs on every node; configures iptables/IPVS to implement Service routing |
| CoreDNS | Cluster DNS server; resolves service names to ClusterIPs |
| Headless Service | `clusterIP: None`; DNS returns Pod IPs directly; no kube-proxy load balancing |
| ExternalName | Maps cluster DNS name to external DNS name; no ClusterIP; no Endpoints |
| sessionAffinity | Routes same client IP to same Pod; for in-memory session state |
| externalTrafficPolicy | `Local`: no cross-node hop, preserves source IP; `Cluster`: balanced, rewrites IP |
| Topology-aware routing | Prefers Pods in same zone as client; reduces cross-AZ traffic cost |

| gRPC + Service type | Result |
|---|---|
| gRPC + ClusterIP | All RPCs go to one Pod (HTTP/2 connection pinned by conntrack DNAT) |
| gRPC + Headless | Client gets all Pod IPs; round-robin distributes RPCs ✅ |
| gRPC + Service mesh | Envoy sidecar handles RPC-level LB transparently ✅ |

## The Core Mental Model

```
Service = stable network identity for a dynamic set of Pods

The three levels of stability:
  DNS name:   payment-service.payments.svc.cluster.local  ← never changes
  ClusterIP:  10.96.45.128                                ← never changes
  Pod IPs:    10.0.1.5, 10.0.1.6, 10.0.2.2              ← change constantly

DNS → ClusterIP (CoreDNS) → Pod IP (kube-proxy iptables DNAT)
The client only knows the DNS name; everything else is infrastructure.

Service type selection:
  ClusterIP:    internal microservice communication (the default; use for everything internal)
  Headless:     StatefulSets (stable per-Pod DNS) OR gRPC (client-side LB)
  NodePort:     dev/testing, or bare-metal with external LB
  LoadBalancer: external access with cloud LB (one per Service — expensive)
  Ingress:      multiple HTTP services behind one cloud LB (the correct production pattern)

The gRPC ClusterIP problem (always comes up):
  HTTP/2 persistent connections + iptables conntrack = connection pinned to one Pod
  Fix: Headless Service + gRPC client round-robin resolver
  Fix: Service mesh (Istio/Linkerd) with Envoy sidecar
  Never: ClusterIP for gRPC without one of these fixes

The Endpoints lifecycle (understand this to debug Service routing issues):
  Pod starts + passes readiness probe
    → Endpoints controller adds Pod IP to Endpoints object
    → kube-proxy updates DNAT rules on all nodes
    → Traffic reaches the new Pod
  Pod fails readiness probe
    → Endpoints controller moves Pod IP to NotReadyAddresses
    → kube-proxy removes Pod IP from DNAT rules
    → No new traffic; in-flight connections drain

Cost optimization:
  One LoadBalancer Service = one cloud LB = ~$5–16/month
  10 services × LoadBalancer = $50–160/month
  Ingress + 1 LoadBalancer = ~$16/month for ALL HTTP services
  Always: expose HTTP services via Ingress; use LoadBalancer only for non-HTTP
           or when static IPs are required (NLB for partner IP allowlisting)

EXTERNAL-IP <pending> diagnosis order:
  1. kubectl describe service → check Events for error message
  2. Cloud controller manager logs → check for IAM/subnet/tagging errors
  3. Bare metal? → install MetalLB
  4. EKS Fargate? → use Ingress with ALB controller (no LoadBalancer Services)
  5. Subnet tags? → tag subnets kubernetes.io/role/elb=1
```

**Tip for the interview:** Kubernetes Service questions at 5 YOE almost always escalate to one of three places: (1) the gRPC + ClusterIP problem — being able to explain immediately that HTTP/2's persistent connections are tracked by iptables conntrack and pinned to a single Pod, that this makes ClusterIP load balancing ineffective for gRPC, and that the fix is a Headless Service with a gRPC client configured for DNS round-robin resolution is the nuance that separates someone who has operated gRPC in Kubernetes from someone who has only read about it; (2) the Endpoints controller lifecycle — knowing that a Pod that is Running but failing its readiness probe appears in `NotReadyAddresses` (not `Addresses`) in the Endpoints object, and therefore receives no traffic, and that this is the mechanism by which rolling deployments avoid sending traffic to Pods that haven't finished starting up, shows you understand the full system rather than just the Service abstraction; (3) Ingress vs LoadBalancer cost — knowing that each LoadBalancer Service provisions a separate cloud load balancer with a separate billing line, and that Ingress consolidates all HTTP services behind one load balancer at a fraction of the cost, is the architectural judgment that shows infrastructure awareness beyond just "it works." The fintech-specific callout: for the fraud scoring service called via gRPC by the payment service, a Headless Service is not optional — a ClusterIP Service will pin all fraud scoring traffic to one Pod under load, defeating horizontal scaling precisely when you need it most (during payment spikes).
