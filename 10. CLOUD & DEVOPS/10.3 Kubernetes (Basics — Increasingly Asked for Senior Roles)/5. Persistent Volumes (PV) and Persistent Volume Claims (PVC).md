# Kubernetes Persistent Volumes and Persistent Volume Claims — Interview Q&A (5 YOE Level)

---

## Section 1: The Storage Problem Kubernetes Solves

**Q1. What problem do PersistentVolumes solve that container volumes (emptyDir, hostPath) cannot?**
A: Container-native volumes are ephemeral or node-local. They cannot survive Pod rescheduling, node failure, or cluster operations that move workloads between nodes. PersistentVolumes decouple storage lifecycle from Pod lifecycle — the data outlives the Pod that created it.

**The three storage problems and their solutions:**

```
Problem 1 — emptyDir is ephemeral:
  emptyDir lives as long as the Pod. Pod deleted → data gone.
  Pod rescheduled to a different node → starts with empty volume.

  Use case that fails: PostgreSQL using emptyDir for /var/lib/postgresql/data
    Node fails → Pod rescheduled → empty database → data loss

  PV solution: the volume exists independently of the Pod.
    PostgreSQL Pod deleted → PV (EBS volume) remains.
    New PostgreSQL Pod scheduled (anywhere in the AZ) → mounts the same PV → data intact.

Problem 2 — hostPath is node-local:
  hostPath mounts a directory from the node's filesystem.
  Data lives on one specific node.
  Pod rescheduled to a different node → cannot find the data.

  Use case that fails: Redis using hostPath for /data
    Pod scheduled on node-1 → data at /data/redis on node-1
    node-1 maintenance → Pod rescheduled to node-2 → /data/redis on node-2 is empty
    Redis starts fresh → entire cache lost → thundering herd on downstream DB

  PV solution: EBS volume (or NFS, EFS) is network-attached.
    Detaches from node-1 → re-attaches to node-2 → same data visible.
    Works across nodes (within AZ for EBS; across AZs for EFS/NFS).

Problem 3 — storage provisioning is manual without PVs:
  Without PVs: DevOps team manually creates EBS volumes, formats them,
               maintains a spreadsheet of which volume is for which service.
  Pod spec: must hardcode the volume ID (vol-0abc123...) → not portable.
  New cluster? Different region? Volume IDs are invalid.

  PV + StorageClass solution: developer requests "I need 100Gi of gp3 storage"
    StorageClass automatically provisions an EBS volume → no manual steps.
    PVC is portable: same YAML works in dev, staging, and production clusters.
    Volume ID is an implementation detail hidden from the application.
```

**The storage abstraction layers:**
```
Application (Pod)
    │ uses
    ▼
PersistentVolumeClaim (PVC)
    │ binds to
    ▼
PersistentVolume (PV)
    │ backed by
    ▼
Storage Backend (EBS, EFS, NFS, Ceph, local disk...)

Each layer has a distinct responsibility:
  Pod:  declares "I need a volume named 'data' mounted at /var/lib/postgresql/data"
  PVC:  declares "I need 100Gi, ReadWriteOnce, gp3 storage class"
  PV:   represents the actual provisioned storage resource (created manually or dynamically)
  Backend: the physical or network storage that holds the bytes
```

## Section 2: PersistentVolume and PersistentVolumeClaim Anatomy

**Q2. What are the key fields of a PersistentVolume and PersistentVolumeClaim, and how does binding work?**
A: A PV is a cluster-scoped resource representing a piece of storage. A PVC is a namespace-scoped resource representing a request for storage. Kubernetes binds a PVC to a PV when the PV satisfies the PVC's requirements — capacity, access mode, storage class, and optional label selectors.

**PersistentVolume anatomy:**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: postgres-pv-prod
  labels:
    environment: production
    tier:        database
spec:
  # Capacity: how much storage this PV provides
  capacity:
    storage: 500Gi

  # Access modes: how the volume can be mounted
  accessModes:
    - ReadWriteOnce   # can be mounted read-write by ONE node at a time

  # Reclaim policy: what happens to the PV when the PVC is deleted
  persistentVolumeReclaimPolicy: Retain

  # Storage class: which StorageClass this PV belongs to
  # PVCs with storageClassName: gp3-encrypted will match this PV
  storageClassName: gp3-encrypted

  # Volume plugin: the actual storage backend
  csi:
    driver:       ebs.csi.aws.com
    volumeHandle: vol-0abc123def456789   # the EBS volume ID
    fsType:       ext4
    volumeAttributes:
      type: gp3
      iops: "10000"
      throughput: "500"

  # Node affinity: restrict which nodes can mount this volume
  # EBS volumes are AZ-specific — must schedule Pod in the same AZ
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key:      topology.kubernetes.io/zone
              operator: In
              values:   [ap-south-1a]   # EBS volume is in this AZ only
```

**PersistentVolumeClaim anatomy:**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name:      postgres-data
  namespace: production
spec:
  # Access mode must be supported by the PV
  accessModes:
    - ReadWriteOnce

  # Storage class: must match a StorageClass (or a PV's storageClassName)
  storageClassName: gp3-encrypted

  # Requested capacity: PV capacity must be >= this value
  resources:
    requests:
      storage: 500Gi

  # Optional: select a specific PV by label (static provisioning)
  selector:
    matchLabels:
      environment: production
      tier:        database
```

**Binding rules — when does a PVC bind to a PV?**
```
Kubernetes evaluates these criteria IN ORDER to find a matching PV:

1. storageClassName must match (or both empty for default class)
2. accessModes: PV must support all modes the PVC requests
3. capacity: PV capacity must be >= PVC requested capacity
4. selector: PVC label selector must match PV labels (if specified)
5. volumeName: PVC can specify an exact PV name to bind to

Binding is one-to-one: one PVC binds to exactly one PV.
Once bound: the PV is exclusively reserved for that PVC (no other PVC can bind it).
Even if the PV has 1 TiB and the PVC requests 100Gi: the entire PV is reserved.
The unused 900 GiB is wasted — choose PV size carefully, or use dynamic provisioning.

Binding states:
  Available: PV exists, not yet bound to any PVC
  Bound:     PV is bound to a PVC (both PV and PVC show Bound status)
  Released:  PVC was deleted; PV is not yet Available (reclaim policy pending)
  Failed:    automatic reclamation failed

kubectl get pvc -n production
  NAME            STATUS   VOLUME          CAPACITY   ACCESS MODES   STORAGECLASS    AGE
  postgres-data   Bound    postgres-pv-prod  500Gi    RWO            gp3-encrypted   4d
  redis-data      Bound    pvc-abc123...     20Gi     RWO            gp3             2d

kubectl get pv
  NAME              CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM
  postgres-pv-prod  500Gi      RWO            Retain           Bound    production/postgres-data
  pvc-abc123...     20Gi       RWO            Delete           Bound    production/redis-data
```

**Q3. What are the access modes and which storage backends support each?**
A: Access modes define how many nodes can mount the volume simultaneously and with what permissions. The mode is enforced by the volume plugin — it is not a Kubernetes-level lock but a capability declaration.

```
ReadWriteOnce (RWO):
  Mounted read-write by ONE node at a time.
  Other nodes cannot mount the same volume while it is mounted RWO.
  Most common: databases, stateful services.
  Supported by: EBS, local disk, most block storage.

  Kubernetes 1.22+: ReadWriteOncePod (RWOP):
    Mounted read-write by ONE POD at a time (stricter than RWO).
    RWO allows multiple Pods on the same node to mount the same volume.
    RWOP allows exactly ONE Pod, regardless of node.
    Use for: single-instance databases where even same-node multi-Pod access is wrong.

ReadOnlyMany (ROX):
  Mounted read-only by MANY nodes simultaneously.
  Multiple Pods on different nodes can read the same volume.
  Supported by: EFS, NFS, CephFS, some object storage.
  Use for: shared static assets, ML model weights, reference data.

ReadWriteMany (RWX):
  Mounted read-write by MANY nodes simultaneously.
  Multiple Pods can write to the same volume concurrently.
  The application must handle concurrent write conflicts (filesystem-level locking).
  Supported by: EFS (NFS-based), NFS, CephFS, Azure Files, GCS Fuse.
  NOT supported by: EBS (block device; one node mount only).
  Use for: shared upload directories, distributed file processing.

AWS storage and access mode compatibility:
  EBS (gp3, io2):    RWO only        (block device; one attachment point)
  EFS:               RWX, ROX, RWO   (NFS; multi-node mount supported)
  FSx for Lustre:    RWX             (high-performance parallel filesystem)
  FSx for NetApp:    RWX, ROX        (enterprise NFS/SMB)

Common mistakes:
  Using EBS with RWX: not supported; Pod will fail to mount
  Using EBS across AZs: not supported; EBS is AZ-local
    → Pod in ap-south-1b cannot mount an EBS volume in ap-south-1a
    → Solution: EFS for cross-AZ shared storage; or StatefulSet with AZ affinity
```

## Section 3: StorageClass and Dynamic Provisioning

**Q4. How does dynamic provisioning work with StorageClass, and why is it preferred over static PV creation?**
A: Dynamic provisioning eliminates the operational step of manually creating PVs before Pods can use storage. A StorageClass defines a "type" of storage (which provisioner to use, what parameters to pass) and when a PVC referencing that StorageClass is created, the provisioner automatically creates the underlying storage resource (EBS volume, EFS access point, etc.) and a corresponding PV.

**StorageClass anatomy:**
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3-encrypted
  annotations:
    # Make this the default StorageClass (PVCs without storageClassName use this)
    storageclass.kubernetes.io/is-default-class: "true"

# The CSI driver that handles provisioning
provisioner: ebs.csi.aws.com

# Parameters passed to the provisioner
parameters:
  type:       gp3
  iops:       "3000"         # baseline IOPS (additional IOPS provisioned separately)
  throughput: "125"          # MiB/s throughput
  encrypted:  "true"         # encrypt the EBS volume
  kmsKeyId:   "arn:aws:kms:ap-south-1:123456789012:key/prod-ebs-key-id"
  fsType:     ext4

# What happens to the PV (and underlying EBS volume) when the PVC is deleted
reclaimPolicy: Delete        # Delete = destroy EBS volume on PVC deletion
                             # Retain = keep EBS volume (manual cleanup required)

# Whether volume can be expanded after creation
allowVolumeExpansion: true

# Binding mode: when is the PV provisioned?
volumeBindingMode: WaitForFirstConsumer
# Immediate:          provision EBS volume as soon as PVC is created
#                     Problem: EBS volume created in a random AZ before Pod is scheduled
#                     Pod scheduled in a different AZ → cannot mount → Pending forever
# WaitForFirstConsumer: wait until a Pod is scheduled, then provision in the Pod's AZ
#                     Critical for EBS: ensures volume and Pod are in the same AZ

# Allowed topologies: restrict which AZs volumes can be provisioned in
allowedTopologies:
  - matchLabelExpressions:
      - key:    topology.kubernetes.io/zone
        values: [ap-south-1a, ap-south-1b, ap-south-1c]
```

**Multiple StorageClasses for different workloads:**
```yaml
# gp3: default; balanced IOPS for most workloads
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type:      gp3
  encrypted: "true"
reclaimPolicy:       Delete
allowVolumeExpansion: true
volumeBindingMode:   WaitForFirstConsumer

# io2: high IOPS for production databases (PostgreSQL, MySQL)
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: io2-high-iops
provisioner: ebs.csi.aws.com
parameters:
  type:       io2
  iops:       "10000"
  encrypted:  "true"
  kmsKeyId:   "arn:aws:kms:...:key/prod-ebs-key"
reclaimPolicy:       Retain   # Retain for databases: never auto-delete production data
allowVolumeExpansion: true
volumeBindingMode:   WaitForFirstConsumer

# efs-shared: EFS for cross-AZ shared read-write storage
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: efs-shared
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap              # use EFS Access Points (per-PVC isolation)
  fileSystemId:     fs-0abc123def456789
  directoryPerms:   "700"
  gidRangeStart:    "1000"
  gidRangeEnd:      "2000"
  basePath:         "/dynamic_provisioning"
reclaimPolicy:       Delete
volumeBindingMode:   Immediate   # EFS is multi-AZ; no AZ constraint
```

**Dynamic provisioning flow:**
```
Developer creates PVC:
  kubectl apply -f postgres-pvc.yaml
  PVC: name=postgres-data, storageClass=io2-high-iops, size=500Gi

Kubernetes PVC controller:
  No matching PV exists → StorageClass provisioner must create one
  Calls EBS CSI driver: create a 500Gi io2 EBS volume with iops=10000

EBS CSI driver (running in the cluster):
  Calls AWS EC2 API: aws ec2 create-volume \
    --volume-type io2 --size 500 --iops 10000 --encrypted \
    --availability-zone <determined by WaitForFirstConsumer>
  Returns: vol-0newvolumeid123

Kubernetes:
  Creates PV object: capacity=500Gi, volumeHandle=vol-0newvolumeid123
  Binds PVC to the new PV

Pod (StatefulSet, Deployment):
  References the PVC → Kubernetes attaches the EBS volume to the Pod's node
  kubelet mounts the volume at the specified mountPath
  Container: sees /var/lib/postgresql/data backed by the EBS volume

Total operator intervention: zero (PVC creation is the only step)
```

## Section 4: Reclaim Policy and Volume Lifecycle

**Q5. What are the reclaim policies and what are the consequences of choosing each in production?**
A: The reclaim policy determines what happens to a PV (and its underlying storage) after the PVC that was bound to it is deleted. This is one of the most consequential settings in production Kubernetes storage — the wrong choice causes either data loss or runaway storage costs.

**The three reclaim policies:**

```
Delete:
  When PVC is deleted:
    Kubernetes deletes the PV object
    The provisioner deletes the underlying storage resource (EBS volume, EFS access point)
    Data is permanently destroyed — no recovery possible
  Use when:
    Storage is ephemeral by design (cache, temp files, build artifacts)
    Data has no value beyond the lifecycle of the PVC
    Dynamic provisioning with StorageClass (Delete is usually the default)
  DANGER for production databases:
    kubectl delete pvc postgres-data → EBS volume destroyed → data gone
    If someone deletes a PVC by mistake (or a helm uninstall): instant data loss
    Protection: set reclaimPolicy: Retain for all database StorageClasses

Retain:
  When PVC is deleted:
    PVC object is deleted
    PV object moves to Released state (not Available)
    Underlying storage (EBS volume) is NOT deleted — data is preserved
    The PV is NOT automatically available for a new PVC to bind
    Operator must manually: inspect data, create a new PV referencing the same volume,
    or delete the PV to release the storage
  Use when:
    Production databases (PostgreSQL, MySQL, MongoDB, Kafka)
    Any data that must survive PVC deletion
    Regulatory requirements (7-year data retention for financial records)
  Operational overhead:
    Released PVs accumulate in the cluster (they cannot auto-rebind)
    Operator must monitor Released PVs and manually clean up or reclaim
    Released PV workflow:
      1. kubectl get pv → find Released PVs
      2. kubectl describe pv <name> → confirm the data is safe / not needed
      3. kubectl patch pv <name> -p '{"spec":{"claimRef":null}}' → reset to Available
         (or: kubectl delete pv <name> → deletes the PV object; EBS volume still exists)

Recycle (deprecated — do not use):
  Kubernetes used to wipe the volume (rm -rf /volume/*) and make it Available again.
  This is insecure (data may have been insufficiently wiped) and unmaintained.
  StorageClasses with Recycle policy are rejected in modern Kubernetes.
  If seen in the wild: migrate to Delete or Retain + a cleanup Job.
```

**Production reclaimPolicy decision matrix:**
```
StorageClass: gp3 (general purpose, dev/staging):
  reclaimPolicy: Delete
  Reason: dev data is disposable; automatic cleanup avoids orphaned volumes

StorageClass: io2-high-iops (production databases):
  reclaimPolicy: Retain
  Reason: production database data must NEVER be auto-deleted

StorageClass: efs-shared (shared application storage):
  reclaimPolicy: Retain
  Reason: shared documents, uploads, and files must survive PVC deletion

StatefulSet volumeClaimTemplates (Kafka, Redis):
  Default inherits from StorageClass → use Retain StorageClass for stateful sets
  Or: set PVC retention policy on the StatefulSet directly (Kubernetes 1.27+):
    spec:
      persistentVolumeClaimRetentionPolicy:
        whenDeleted:  Retain   # PVC kept when StatefulSet is deleted
        whenScaled:   Delete   # PVC deleted when StatefulSet scales down
                                # (scale-down = Pod removed permanently)
```

**Recovering from accidental PVC deletion (Retain policy):**
```
Scenario: helm uninstall accidentally deleted PVC postgres-data
  reclaimPolicy: Retain → EBS volume vol-0abc123 still exists

Step 1: Identify the EBS volume
  kubectl get pv
  NAME              CAPACITY   STATUS    CLAIM                    RECLAIM POLICY
  pvc-xyz-prod-db   500Gi      Released  production/postgres-data  Retain
  # Released: PVC is gone, PV remains

  kubectl describe pv pvc-xyz-prod-db
  # Source.VolumeHandle: vol-0abc123...  ← the EBS volume ID

Step 2: Create a new PVC and manually bind it to the existing PV
  # Patch the PV to remove the stale claimRef (marks it Available again)
  kubectl patch pv pvc-xyz-prod-db \
    -p '{"spec":{"claimRef":null}}'
  # PV status: Available

  # Create PVC with volumeName to bind to this specific PV
  cat <<EOF | kubectl apply -f -
  apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: postgres-data
    namespace: production
  spec:
    storageClassName: io2-high-iops
    accessModes: [ReadWriteOnce]
    resources:
      requests:
        storage: 500Gi
    volumeName: pvc-xyz-prod-db   # bind to this specific PV
  EOF

Step 3: Redeploy the StatefulSet/Deployment
  kubectl apply -f postgres-statefulset.yaml
  # Pod mounts the PVC → PV → original EBS volume → data intact
```

## Section 5: Volume Expansion

**Q6. How do you expand a PersistentVolumeClaim online, and what are the constraints?**
A: Volume expansion allows increasing the size of a PVC without downtime — the underlying EBS volume is resized and the filesystem is extended, all while the Pod is running. The StorageClass must have `allowVolumeExpansion: true`.

**Online volume expansion flow:**
```
Current state: PVC postgres-data = 500Gi; PostgreSQL Pod is Running

Step 1: Edit the PVC (increase the storage request)
  kubectl patch pvc postgres-data -n production \
    -p '{"spec":{"resources":{"requests":{"storage":"1Ti"}}}}'
  # Kubernetes accepts the change: PVC status shows resize pending

Step 2: EBS CSI driver resizes the volume
  EBS CSI driver calls: aws ec2 modify-volume --volume-id vol-0abc --size 1000
  AWS resizes the EBS volume (takes seconds to minutes for gp3)
  EBS volume is now 1 TiB; but the filesystem on it still says 500 GiB

Step 3: Filesystem expansion (online, if supported by CSI driver)
  EBS CSI driver: triggers online filesystem resize on the mounted volume
  For ext4/xfs: resize2fs / xfs_growfs runs while Pod is Running
  Filesystem expands to fill the new volume size
  No Pod restart required for EBS with ext4/xfs on modern Kubernetes (1.24+)

Step 4: Verify
  kubectl get pvc postgres-data -n production
  NAME            STATUS   CAPACITY   ...
  postgres-data   Bound    1Ti        ← capacity updated

  # Inside the Pod:
  kubectl exec -it postgres-0 -- df -h /var/lib/postgresql/data
  Filesystem      Size  Used Avail Use% Mounted on
  /dev/nvme1n1    1.0T  480G  520G  48% /var/lib/postgresql/data

Constraints and failure modes:

Cannot shrink: Kubernetes does not support volume shrinkage
  kubectl patch pvc postgres-data -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
  Error: spec.resources.requests.storage: Forbidden: field is immutable after claim creation
  If you need to shrink: create a new PVC, copy data, migrate the application

Expansion requires StorageClass allowVolumeExpansion: true:
  kubectl describe storageclass io2-high-iops | grep AllowVolumeExpansion
  AllowVolumeExpansion: True
  If False: kubectl patch pvc → no error, but expansion silently does nothing

Node must not be cordoned during expansion:
  The CSI driver needs the node to be reachable to trigger filesystem resize
  If the node is cordoned or NotReady: filesystem resize may be deferred
  until a Pod restart (a brief window where the Pod sees old size on restart)

EFS expansion: unlimited (EFS is elastic by design; no expansion needed)
  EFS PVCs: storage size in the PVC spec is ignored by EFS (set any value; it is elastic)
  Billing: EFS charges per GB actually stored (not per provisioned capacity)
```

## Section 6: StatefulSet Storage Patterns

**Q7. How do StatefulSet `volumeClaimTemplates` work and how do they differ from referencing a PVC directly?**
A: StatefulSet `volumeClaimTemplates` create a unique, automatically-named PVC for each Pod replica. Each replica gets its own exclusive storage — not shared with other replicas. This is fundamental to running distributed stateful systems (Kafka, Cassandra, PostgreSQL replicas) where each instance needs its own data directory.

**volumeClaimTemplates vs direct PVC reference:**
```yaml
# WRONG: Deployment referencing a shared PVC
# (all Pods share one PVC — concurrent writes corrupt the database)
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3
  template:
    spec:
      volumes:
        - name:                 data
          persistentVolumeClaim:
            claimName: postgres-data  # ALL 3 Pods mount the SAME PVC
            # Result: 3 PostgreSQL processes writing to the same data directory = corruption

# CORRECT: StatefulSet with volumeClaimTemplates
# (each Pod gets its own dedicated PVC)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  replicas: 3
  volumeClaimTemplates:
    - metadata:
        name: data             # PVC name prefix
      spec:
        storageClassName: io2-high-iops
        accessModes:     [ReadWriteOnce]
        resources:
          requests:
            storage: 500Gi
  template:
    spec:
      containers:
        - name: postgres
          volumeMounts:
            - name:      data
              mountPath: /var/lib/postgresql/data
```

```
PVCs created automatically by StatefulSet (naming: {template-name}-{statefulset-name}-{ordinal}):
  data-postgres-0   → 500Gi EBS in ap-south-1a  (bound to postgres-0 Pod)
  data-postgres-1   → 500Gi EBS in ap-south-1b  (bound to postgres-1 Pod)
  data-postgres-2   → 500Gi EBS in ap-south-1c  (bound to postgres-2 Pod)

Each PVC:
  Exclusively mounted by its corresponding Pod
  Persists when the Pod is deleted (rescheduled, crashed, updated)
  The NEW Pod (after restart) mounts the SAME PVC → same data → stateful identity restored

StatefulSet scale-down:
  Scale from 3 → 2: Pod postgres-2 is deleted
  PVC data-postgres-2: NOT deleted (Retain policy, or whenScaled: Retain)
  Scale back up 2 → 3: Pod postgres-2 re-created → mounts data-postgres-2 again
  The scale-down/up cycle is safe: data is preserved

StatefulSet deletion:
  kubectl delete statefulset postgres:
    Pods deleted
    PVCs: behavior depends on persistentVolumeClaimRetentionPolicy
      whenDeleted: Retain  → PVCs survive (safe; operator must manually clean up)
      whenDeleted: Delete  → PVCs deleted → EBS volumes deleted → data gone
    Default (before Kubernetes 1.27): PVCs always Retained on StatefulSet deletion
    Kubernetes 1.27+: configure explicitly with persistentVolumeClaimRetentionPolicy
```

**Kafka StatefulSet with volumeClaimTemplates (production example):**
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
  namespace: production
spec:
  serviceName: kafka-headless
  replicas:    3
  selector:
    matchLabels:
      app: kafka
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1

  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain    # PVCs survive StatefulSet deletion
    whenScaled:  Retain    # PVCs survive scale-down (data preserved for re-scale)

  template:
    metadata:
      labels:
        app: kafka
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values: [kafka]
              topologyKey: kubernetes.io/hostname   # one broker per node

      containers:
        - name:  kafka
          image: confluentinc/cp-kafka:7.5.0
          volumeMounts:
            - name:      kafka-data
              mountPath: /var/lib/kafka/data
            - name:      kafka-logs
              mountPath: /var/log/kafka

  volumeClaimTemplates:
    - metadata:
        name: kafka-data
      spec:
        storageClassName: io2-high-iops    # high IOPS for Kafka write throughput
        accessModes:     [ReadWriteOnce]
        resources:
          requests:
            storage: 200Gi

    - metadata:
        name: kafka-logs
      spec:
        storageClassName: gp3              # logs don't need high IOPS
        accessModes:     [ReadWriteOnce]
        resources:
          requests:
            storage: 50Gi

# PVCs created:
#   kafka-data-kafka-0, kafka-data-kafka-1, kafka-data-kafka-2  (200Gi io2 each)
#   kafka-logs-kafka-0, kafka-logs-kafka-1, kafka-logs-kafka-2  (50Gi gp3 each)
# Total: 6 PVCs, 750Gi io2 + 150Gi gp3
```

## Section 7: EFS and Shared Storage

**Q8. When do you use EFS instead of EBS for Kubernetes persistent storage, and how does the EFS CSI driver differ from EBS?**
A: EFS (Elastic File System) is an NFS-based managed file system that supports concurrent mounts from multiple nodes simultaneously (ReadWriteMany). EBS is a block device that can only be attached to one node at a time (ReadWriteOnce). The choice is driven by whether multiple Pods — potentially on different nodes — need concurrent read-write access to the same data.

**EBS vs EFS comparison:**

| Dimension | EBS (gp3, io2) | EFS |
|---|---|---|
| Access mode | RWO only | RWX, ROX, RWO |
| Multi-node mount | No | Yes |
| AZ scope | Single AZ | Multi-AZ (regional) |
| Performance | Higher IOPS/throughput | Lower IOPS; higher latency (~1ms vs 0.1ms) |
| Pricing | Per provisioned GB/IOPS | Per GB actually stored |
| Scaling | Manual resize (expandable) | Automatic (elastic) |
| Use case | Databases, single-writer stateful | Shared files, multi-writer, cross-AZ |
| CSI driver | `ebs.csi.aws.com` | `efs.csi.aws.com` |
| Backup | EBS snapshots | EFS Backup (AWS Backup) |

**When EFS is the right choice:**
```
Multi-Pod shared read-write access:
  Scenario: document processing pipeline
    Upload service (multiple Pods) → writes PDFs to /uploads
    OCR service (multiple Pods) → reads PDFs from /uploads, writes results to /processed
    NLP service (multiple Pods) → reads from /processed
    All services need concurrent access to the same filesystem
    EBS: cannot be mounted by multiple nodes → cannot scale any service horizontally
    EFS: all services mount the same EFS filesystem → no coordination needed

Cross-AZ Pod access to the same data:
  Scenario: ML model serving
    Model weights stored once; multiple inference Pods across 3 AZs read them
    EBS: volume in ap-south-1a → only Pods in ap-south-1a can mount it
    EFS: regional; Pods in ap-south-1a, 1b, 1c all mount the same weights

Kubernetes EFS CSI setup:
  Unlike EBS (where each PVC = one EBS volume):
  EFS CSI driver uses Access Points (one per PVC) within a single EFS filesystem
  All PVCs share the same underlying EFS but get isolated directory roots

EFS StorageClass (dynamic provisioning):
  provisioner: efs.csi.aws.com
  parameters:
    provisioningMode: efs-ap        # use Access Points for isolation
    fileSystemId:     fs-0abc123
    directoryPerms:   "755"

Example PVC (shared ML model weights):
  apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: model-weights
    namespace: production
  spec:
    storageClassName: efs-shared
    accessModes:     [ReadWriteMany]  # multiple Pods can mount this
    resources:
      requests:
        storage: 100Gi               # EFS ignores this; billed per actual usage

Usage in Deployment (not StatefulSet):
  spec:
    template:
      spec:
        volumes:
          - name: model-weights
            persistentVolumeClaim:
              claimName: model-weights
              readOnly:  true     # ReadOnlyMany when only reading
        containers:
          - name: inference-server
            volumeMounts:
              - name:      model-weights
                mountPath: /models
                readOnly:  true
  # All 10 inference Pods across 3 AZs mount the same PVC simultaneously
```

**EFS performance considerations:**
```
EFS latency: ~1–2ms per operation (vs EBS gp3: ~0.1ms)
  Reason: NFS over network; additional protocol overhead
  Impact: PostgreSQL on EFS = 10–20× slower than PostgreSQL on EBS
  NEVER use EFS for: databases, Kafka, Elasticsearch, Redis
  Use EFS for: files that are read/written sequentially; not random I/O

EFS throughput modes:
  Bursting (default): throughput scales with filesystem size
    Small EFS (<1 TiB stored): baseline 50 MiB/s; burst to 100 MiB/s
    Larger EFS: more throughput; burst credit system (like T3 CPU credits)
  Provisioned: pay for fixed throughput regardless of size
    Use when: application needs consistent throughput; size is small but I/O is high
  Elastic (recommended for Kubernetes): auto-scales to meet demand
    No capacity planning; pay per GB transferred

EFS performance mode:
  General Purpose (default): lower latency; max 35,000 IOPS
  Max I/O: higher IOPS (100,000+) but higher latency; for highly parallel workloads
  For Kubernetes shared storage: General Purpose is almost always correct
```

## Section 8: CSI Drivers and Volume Snapshots

**Q9. What is a CSI driver and how do volume snapshots enable backup and disaster recovery?**
A: CSI (Container Storage Interface) is a standard API that allows storage vendors to write plugins that work with any CSI-compatible container orchestrator (Kubernetes, Nomad, etc.) without modifying Kubernetes core code. AWS provides CSI drivers for EBS (`ebs.csi.aws.com`) and EFS (`efs.csi.aws.com`).

**CSI driver components:**
```
CSI Driver = three components deployed in the cluster:

1. Controller plugin (Deployment — runs once or twice for HA):
   Handles cluster-level operations:
   - CreateVolume:      creates EBS volume on provision
   - DeleteVolume:      deletes EBS volume on PV deletion
   - ControllerPublish: attaches EBS volume to a specific EC2 node
   - CreateSnapshot:    creates EBS snapshot from a PV

2. Node plugin (DaemonSet — runs on every node):
   Handles node-local operations:
   - NodeStageVolume:   formats the device and mounts to a staging path
   - NodePublishVolume: bind-mounts from staging path to Pod's volume path
   - NodeUnpublish:     unmounts from Pod
   - NodeUnstage:       unmounts from staging path

3. CSI Sidecar containers (shipped with the driver):
   external-provisioner:  watches for new PVCs; calls CreateVolume
   external-attacher:     watches for Pod scheduling; calls ControllerPublish
   external-resizer:      watches for PVC size changes; calls ControllerExpandVolume
   external-snapshotter:  watches for VolumeSnapshot objects; calls CreateSnapshot

Installing EBS CSI driver on EKS:
  aws eks create-addon \
    --cluster-name fintech-prod \
    --addon-name aws-ebs-csi-driver \
    --service-account-role-arn arn:aws:iam::123456789012:role/AmazonEKS_EBS_CSI_DriverRole
  # The role needs: ec2:CreateVolume, ec2:AttachVolume, ec2:DeleteVolume, ec2:CreateSnapshot
```

**Volume Snapshots for backup:**
```yaml
# VolumeSnapshotClass: defines how snapshots are taken (which CSI driver)
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-vsc
  annotations:
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver:         ebs.csi.aws.com
deletionPolicy: Retain    # keep the EBS snapshot even if VolumeSnapshot object is deleted

---
# VolumeSnapshot: take a snapshot of a specific PVC
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: postgres-snapshot-2024-01-15
  namespace: production
spec:
  volumeSnapshotClassName: ebs-vsc
  source:
    persistentVolumeClaimName: postgres-data   # snapshot this PVC
```

```
What happens when VolumeSnapshot is created:
  Kubernetes external-snapshotter sidecar: watches for new VolumeSnapshot objects
  Calls EBS CSI driver: CreateSnapshot(sourceVolumeId: vol-0abc123)
  AWS: creates EBS snapshot (snap-0xyz789...)
  Kubernetes: creates VolumeSnapshotContent object (cluster-scoped; represents the EBS snapshot)
  VolumeSnapshot status: readyToUse: true

Snapshot to restore workflow:
  # Create a new PVC from the snapshot (for restore or clone)
  apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: postgres-data-restore
    namespace: production
  spec:
    storageClassName:  io2-high-iops
    accessModes:       [ReadWriteOnce]
    resources:
      requests:
        storage: 500Gi
    dataSource:
      name:     postgres-snapshot-2024-01-15
      kind:     VolumeSnapshot
      apiGroup: snapshot.storage.k8s.io
  # EBS CSI driver: creates a new EBS volume from the snapshot
  # New PVC bound to new PV → attach to a restore Pod → data from snapshot time

Automated snapshot CronJob (backup strategy):
  apiVersion: batch/v1
  kind: CronJob
  metadata:
    name: postgres-snapshot
    namespace: production
  spec:
    schedule: "0 2 * * *"    # 02:00 UTC daily (07:30 IST)
    concurrencyPolicy: Forbid
    jobTemplate:
      spec:
        template:
          spec:
            restartPolicy:      OnFailure
            serviceAccountName: snapshot-sa   # needs VolumeSnapshot create permission
            containers:
              - name: snapshot-creator
                image: bitnami/kubectl:latest
                command:
                  - /bin/sh
                  - -c
                  - |
                    DATE=$(date +%Y-%m-%d)
                    kubectl apply -f - <<EOF
                    apiVersion: snapshot.storage.k8s.io/v1
                    kind: VolumeSnapshot
                    metadata:
                      name: postgres-snapshot-${DATE}
                      namespace: production
                    spec:
                      volumeSnapshotClassName: ebs-vsc
                      source:
                        persistentVolumeClaimName: postgres-data
                    EOF
                    # Delete snapshots older than 30 days
                    kubectl get volumesnapshot -n production \
                      -l backup=daily \
                      --sort-by=.metadata.creationTimestamp \
                      -o name | head -n -30 | xargs kubectl delete -n production
```

## Section 9: Troubleshooting Storage

**Q10. How do you diagnose a Pod stuck in `Pending` state due to storage issues?**
A: Storage-related Pod scheduling failures are among the most common Kubernetes issues in production. The diagnosis follows a systematic path from Pod events to PVC status to PV status to the underlying storage backend.

**Systematic diagnosis:**
```
Step 1: Check Pod events
  kubectl describe pod postgres-0 -n production

  Common storage-related events:
    "0/3 nodes are available: 3 node(s) had volume node affinity conflict."
    → EBS volume is in ap-south-1a; no nodes available in ap-south-1a
    → Fix: check node availability in the volume's AZ; add nodes or move volume

    "AttachVolume.Attach failed for volume: Multi-Attach error for volume
     only one node may attach"
    → EBS volume is still attached to the old (now-deleted) node
    → Fix: wait for AWS to detach the volume (force-detach if node is truly gone):
      aws ec2 detach-volume --volume-id vol-0abc123 --force

    "waiting for a volume to be created, either by external provisioner
     or manually created by system administrator"
    → StorageClass provisioner cannot create the volume
    → Fix: check CSI driver Pod health; check IAM permissions for the CSI driver role

    "persistentvolumeclaim 'postgres-data' not found"
    → PVC does not exist in this namespace
    → Fix: create the PVC; check namespace spelling; check if PVC was accidentally deleted

Step 2: Check PVC status
  kubectl get pvc postgres-data -n production

  STATUS = Pending:
    Not yet bound to a PV.
    Could be: waiting for a matching PV (static), or CSI driver is provisioning

  kubectl describe pvc postgres-data -n production
    Events:
      "no persistent volumes available for this claim and no storage class is set"
      → No StorageClass specified and no default StorageClass exists
      → Fix: add storageClassName to PVC spec, or set a default StorageClass

      "storageclass.storage.k8s.io 'io2-high-iops' not found"
      → Referenced StorageClass does not exist
      → Fix: kubectl apply -f storageclass.yaml

      "waiting for first consumer to be created before binding"
      → volumeBindingMode: WaitForFirstConsumer; no Pod scheduled yet
      → Not an error: PVC binds when Pod is scheduled (normal for EBS)

      "failed to provision volume with StorageClass 'io2-high-iops':
       rpc error: code = Internal ... AccessDeniedException"
      → CSI driver IAM role lacks ec2:CreateVolume permission
      → Fix: update the IAM role for the EBS CSI driver service account

Step 3: Check PV status (if PV exists)
  kubectl get pv
  kubectl describe pv <pv-name>

  STATUS = Released (not Available):
    PV has a stale claimRef pointing to a deleted PVC
    Fix: kubectl patch pv <pv-name> -p '{"spec":{"claimRef":null}}'

  STATUS = Failed:
    Reclamation failed (for Delete policy)
    Fix: manually delete the PV and underlying storage; re-provision

Step 4: Check CSI driver Pod health
  kubectl get pods -n kube-system -l app=ebs-csi-controller
  kubectl get pods -n kube-system -l app=ebs-csi-node

  kubectl logs -n kube-system ebs-csi-controller-xxx -c csi-provisioner
  # Look for: CreateVolume errors, API throttling, permission errors

Step 5: Check AWS-level
  aws ec2 describe-volumes --volume-ids vol-0abc123
  # Confirm: State = available (not in-use by a terminated instance)
  # Confirm: AvailabilityZone matches the node where the Pod is scheduled

  aws ec2 describe-volume-status --volume-ids vol-0abc123
  # Check for volume impairment events

Common resolution matrix:
  Multi-Attach error        → force-detach from AWS CLI; wait for volume to detach
  Volume node affinity      → check AZ of volume and nodes; add nodes in correct AZ
  AccessDeniedException     → update IAM role policy for CSI driver
  StorageClass not found    → create the StorageClass
  PVC Pending indefinitely  → check volumeBindingMode; check if Pod exists (WaitForFirstConsumer)
  Released PV               → patch claimRef to null; rebind
```

**Q12. "A StatefulSet scale-down from 5 to 3 replicas left orphaned PVCs. The team wants to scale back up and have the new Pods find their original data. Walk through what happens and what the team needs to do."**
A:

```
Situation:
  kafka StatefulSet was at 5 replicas:
    kafka-0, kafka-1, kafka-2, kafka-3, kafka-4
    PVCs: kafka-data-kafka-0 through kafka-data-kafka-4

  Scale-down to 3 replicas:
    kubectl scale statefulset kafka --replicas=3
    Pods kafka-4 → kafka-3 deleted (in reverse ordinal order)
    PVCs kafka-data-kafka-4 and kafka-data-kafka-3: STATUS?

Step 1: Determine PVC retention policy

  Case A: persistentVolumeClaimRetentionPolicy.whenScaled = Delete (dangerous default in older clusters)
    PVCs kafka-data-kafka-3 and kafka-data-kafka-4 are DELETED on scale-down
    EBS volumes DESTROYED (if StorageClass reclaimPolicy: Delete)
    Scale back up: new Pods kafka-3 and kafka-4 get EMPTY new PVCs
    Kafka brokers 3 and 4 start fresh → topic data lost → replication from other brokers
    This is the WRONG configuration for production Kafka

  Case B: persistentVolumeClaimRetentionPolicy.whenScaled = Retain (correct configuration)
    PVCs kafka-data-kafka-3 and kafka-data-kafka-4 PERSIST after scale-down
    EBS volumes still exist

  Check which case applies:
    kubectl describe statefulset kafka | grep -A4 "PVC Retention"
    Or: kubectl get statefulset kafka -o yaml | grep -A4 persistentVolumeClaimRetentionPolicy

Step 2: If PVCs are Retained (correct case) — scale back up

  kubectl scale statefulset kafka --replicas=5
  StatefulSet controller:
    Creates Pod kafka-3 → looks for PVC kafka-data-kafka-3 → FOUND → binds
    Creates Pod kafka-4 → looks for PVC kafka-data-kafka-4 → FOUND → binds
  Kafka brokers 3 and 4 restart with their original data intact
  Kafka re-joins the cluster as brokers with existing partition data
  No data loss; replication catches up on any missed messages since scale-down

Step 3: If PVCs were Deleted (dangerous case) — recovery options

  Option A: Restore from VolumeSnapshot (if daily snapshots were configured)
    # Create PVCs from the most recent snapshots before scale-down
    for ORDINAL in 3 4; do
      kubectl apply -f - <<EOF
      apiVersion: v1
      kind: PersistentVolumeClaim
      metadata:
        name: kafka-data-kafka-${ORDINAL}
        namespace: production
      spec:
        storageClassName: io2-database
        accessModes: [ReadWriteOnce]
        resources:
          requests:
            storage: 200Gi
        dataSource:
          name:     kafka-snapshot-pre-scaledown
          kind:     VolumeSnapshot
          apiGroup: snapshot.storage.k8s.io
      EOF
    done
    # Scale back up: Pods find the newly created PVCs
    kubectl scale statefulset kafka --replicas=5

  Option B: Let Kafka self-heal (if replication factor ≥ 2)
    Scale up without any PVC pre-creation → new PVCs created empty
    Kafka broker joins with empty log → replicates topic partitions from surviving brokers
    Time: proportional to data size; potentially hours for large clusters
    This works only if all partitions have at least one surviving replica (RF ≥ 2)

Step 4: Fix the configuration to prevent recurrence

  # Add explicit retention policy to the StatefulSet
  kubectl patch statefulset kafka --type=merge -p '{
    "spec": {
      "persistentVolumeClaimRetentionPolicy": {
        "whenDeleted": "Retain",
        "whenScaled":  "Retain"
      }
    }
  }'

  # Verify:
  kubectl get statefulset kafka \
    -o jsonpath='{.spec.persistentVolumeClaimRetentionPolicy}'
  # {"whenDeleted":"Retain","whenScaled":"Retain"}

  # Also protect the StorageClass:
  # Change reclaimPolicy from Delete to Retain for io2-database StorageClass
  # (cannot patch existing StorageClass reclaimPolicy; create a new one and migrate)

Prevention checklist for stateful workloads:
  ✅ StorageClass reclaimPolicy: Retain for all production databases and queues
  ✅ StatefulSet persistentVolumeClaimRetentionPolicy: whenScaled=Retain
  ✅ StatefulSet persistentVolumeClaimRetentionPolicy: whenDeleted=Retain
  ✅ Daily VolumeSnapshot CronJob for all critical PVCs
  ✅ Alert on VolumeSnapshot failures
  ✅ Quarterly DR drill: restore from snapshot to a test namespace, verify data
  ✅ RBAC: restrict who can delete PVCs in production namespace (separate from general kubectl access)
```

## Quick Reference

| Object | Scope | Created by | Who binds |
|---|---|---|---|
| PersistentVolume | Cluster-wide | Admin (static) or CSI provisioner (dynamic) | Kubernetes controller |
| PersistentVolumeClaim | Namespace | Developer / Helm / StatefulSet | Kubernetes controller |
| StorageClass | Cluster-wide | Admin | Referenced by PVC |
| VolumeSnapshot | Namespace | Admin / CronJob | VolumeSnapshotContent |

| Access mode | Abbreviation | Multi-node | Supported backends |
|---|---|---|---|
| ReadWriteOnce | RWO | No (one node) | EBS, local, most block |
| ReadWriteOncePod | RWOP | No (one Pod) | EBS CSI (K8s 1.22+) |
| ReadOnlyMany | ROX | Yes (read only) | EFS, NFS, CephFS |
| ReadWriteMany | RWX | Yes (read+write) | EFS, NFS, CephFS |

| Reclaim policy | On PVC delete | On PV delete | Use for |
|---|---|---|---|
| Delete | PV + storage deleted | Storage deleted | Dev, ephemeral, cache |
| Retain | PV moves to Released | Storage kept | Production databases |
| Recycle | (deprecated) | — | Never |

| volumeBindingMode | When PV is provisioned | Use for |
|---|---|---|
| Immediate | On PVC creation | EFS (multi-AZ; no AZ constraint) |
| WaitForFirstConsumer | When Pod is scheduled | EBS (AZ-local; must match Pod's AZ) |

| Storage type | IOPS | Latency | Max size | Access | Use for |
|---|---|---|---|---|---|
| EBS gp3 | 3K–16K | ~0.1ms | 16 TiB | RWO | General workloads |
| EBS io2 | Up to 256K | ~0.1ms | 16 TiB | RWO | Databases, Kafka |
| EFS | Up to 35K | ~1–2ms | Elastic | RWX/ROX | Shared files, ML models |
| emptyDir | Node disk | ~0.1ms | sizeLimit | Pod-local | Scratch, temp, sidecar sharing |

| Failure mode | Symptom | Fix |
|---|---|---|
| AZ mismatch (EBS) | Pod Pending: volume node affinity conflict | Use WaitForFirstConsumer; add nodes in correct AZ |
| Multi-Attach error | Pod Pending: volume already attached | Force-detach from AWS CLI |
| PVC Pending forever | No matching PV; StorageClass issues | Check StorageClass exists; check CSI driver logs |
| Released PV | PVC cannot rebind to Released PV | Patch PV claimRef to null; rebind via volumeName |
| Data loss on scale-down | New Pods get empty PVCs | Set whenScaled: Retain on StatefulSet |
| StorageClass Delete + accident | PVC deleted → EBS volume gone | Use Retain reclaimPolicy for all production storage |
| EBS cross-AZ | Pod cannot mount EBS from different AZ | Use EFS for cross-AZ; or constrain Pods to one AZ |

## The Core Mental Model

```
The storage abstraction ladder — each layer hides complexity from the layer above:
  Pod spec:  "I want a volume named 'data' at /var/lib/postgresql/data"
             (knows nothing about EBS, AZs, volume IDs)
  PVC:       "I want 500Gi of io2 storage, ReadWriteOnce"
             (knows storage class and size; knows nothing about EBS volume IDs)
  PV:        "Here is EBS volume vol-0abc123, 500Gi, in ap-south-1a"
             (the actual resource; bridges Kubernetes and AWS)
  EBS:       the physical bits on AWS infrastructure
  This separation means: the same Pod spec works in dev (with a local-path StorageClass)
  and production (with io2 StorageClass) without any changes.

Reclaim policy is the most consequential storage decision:
  Delete = "this data is disposable; destroy it automatically when I'm done"
  Retain = "this data matters; preserve it until a human explicitly cleans it up"
  Wrong choice: Delete on a production database StorageClass
  One accidental `kubectl delete pvc` or `helm uninstall` → EBS volume gone → data lost
  Rule: every StorageClass that a StatefulSet uses for a production database must be Retain.

WaitForFirstConsumer is not optional for EBS:
  Immediate binding provisions the EBS volume before the Pod is scheduled.
  EBS volumes are AZ-specific. The volume may be provisioned in ap-south-1a.
  The Pod scheduler may place the Pod in ap-south-1b (no nodes in 1a, or better fit in 1b).
  Result: Pod Pending forever (volume node affinity conflict).
  WaitForFirstConsumer: waits for scheduler to pick a node → provisions EBS in that node's AZ.
  Always use WaitForFirstConsumer for EBS-backed StorageClasses.

StatefulSet PVC naming is deterministic and that is the point:
  kafka-data-kafka-0 will always be the PVC for kafka-0.
  If kafka-0 is deleted and recreated: it finds kafka-data-kafka-0 again.
  If the StatefulSet is deleted and recreated: kafka-0 finds kafka-data-kafka-0 again
  (as long as reclaimPolicy: Retain and whenDeleted: Retain are set).
  This deterministic naming is what makes StatefulSet Pods stateful.

emptyDir for truly temporary data; PVC for anything that needs to outlive a Pod:
  NACH batch scratch files (intermediate computation): emptyDir
  PostgreSQL data directory: PVC
  Redis RDB/AOF files: PVC
  Container log files shipped by a sidecar: emptyDir
  Kafka topic data: PVC
  ML model weights (shared across Pods): EFS PVC with RWX
  If you are not sure: ask "does this data need to survive Pod restart?"
  Yes → PVC. No → emptyDir. Shared across Pods on different nodes → EFS RWX PVC.

VolumeSnapshots are your filesystem-level backup; treat them like database backups:
  Snapshot frequency: match your RPO (recovery point objective)
    RPO = 24 hours → daily snapshot CronJob
    RPO = 1 hour → hourly snapshot (EBS snapshots are incremental; cost is manageable)
  Test your snapshots quarterly: restore to a test namespace, verify data integrity
  An untested backup is not a backup — it is a false sense of security
  CloudWatch alarm: VolumeSnapshot readyToUse != true after N minutes → alert
```

**Tip for the interview:** PV/PVC questions at 5 YOE converge on three depth probes: (1) `WaitForFirstConsumer` and the EBS AZ affinity problem — knowing that EBS volumes are AZ-local, that `Immediate` binding mode provisions the volume before the Pod is scheduled (potentially in the wrong AZ, causing a `volume node affinity conflict` that leaves the Pod Pending forever), and that `WaitForFirstConsumer` resolves this by delaying provisioning until the scheduler picks a node, shows you have debugged the single most common EKS storage failure mode rather than just reading about access modes; (2) the Retain vs Delete reclaim policy tradeoff — explaining that `Delete` is correct for ephemeral workloads (automatic cleanup, no orphaned volumes) but catastrophic for production databases (one accidental `kubectl delete pvc` destroys the data), and that the fix is `reclaimPolicy: Retain` on the StorageClass plus `persistentVolumeClaimRetentionPolicy: whenDeleted: Retain` on the StatefulSet, demonstrates you understand where data can be silently destroyed in a Kubernetes cluster; (3) the StatefulSet `volumeClaimTemplates` naming scheme — knowing that PVCs are named `{template}-{statefulset}-{ordinal}` deterministically, that this naming is what allows kafka-0 to always find `kafka-data-kafka-0` after a restart or rescheduling, and that deleting the StatefulSet does not delete the PVCs (with Retain policy), shows you understand why StatefulSets are stateful in a way that Deployments are not. The fintech callout: `reclaimPolicy: Retain` on all StorageClasses used by production databases, combined with `persistentVolumeClaimRetentionPolicy: whenDeleted: Retain, whenScaled: Retain` on all StatefulSets, and a daily `VolumeSnapshot` CronJob with a 30-day retention window, is the storage safety net that satisfies both operational reliability requirements and the 7-year data retention obligations of a PCI-DSS or RBI-regulated fintech platform.
