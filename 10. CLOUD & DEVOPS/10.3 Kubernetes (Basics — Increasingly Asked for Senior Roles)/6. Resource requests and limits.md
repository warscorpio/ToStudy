# Kubernetes Resource Requests and Limits: CPU, Memory, QoS, and Production Sizing — Interview Q&A (5 YOE Level)

---

## Section 1: The Resource Model — What Requests and Limits Actually Mean

**Q1. What are resource requests and limits, and what is the fundamental distinction between them?**
A: Requests and limits are two separate numbers that together define a container's relationship with the node's resources. They are often confused because they sit in the same YAML block, but they answer entirely different questions and are enforced by entirely different mechanisms.

**The conceptual distinction:**

```
Request: "How much resource does this container need to run correctly?"
  → Used by the SCHEDULER to decide which node to place the Pod on.
  → The node must have at least this much unallocated capacity.
  → The container is GUARANTEED this amount at runtime.
  → Does not cap what the container can use — only guarantees a floor.

Limit: "How much resource is this container allowed to consume at most?"
  → Used by the KUBELET (and the Linux kernel) to enforce a ceiling.
  → Exceeding the limit triggers enforcement — different for CPU vs memory.
  → Does not affect scheduling — the scheduler only looks at requests.

These two numbers operate at different layers of the system:
  Requests → kube-scheduler (cluster level; which node gets the Pod)
  Limits   → kubelet + kernel (node level; what the container can do once placed)
```

**How the scheduler uses requests:**

```
Node A: 4 CPU cores, 16 GiB RAM
  Already allocated (sum of requests from all running Pods):
    CPU:    3200m (3.2 cores)
    Memory: 12 GiB

  Available for scheduling:
    CPU:    800m  (0.8 cores)
    Memory: 4 GiB

New Pod: requests 500m CPU, 2 GiB memory
  Scheduler check: 500m ≤ 800m ✅ and 2 GiB ≤ 4 GiB ✅
  → Node A is a viable candidate.

New Pod: requests 1000m CPU, 2 GiB memory
  Scheduler check: 1000m > 800m ❌
  → Node A is NOT a viable candidate, even if the node's actual CPU
    utilization is only 10% (the existing Pods are idle but their
    requests are still counted against the node's allocatable capacity).

Critical insight:
  A node can be 10% utilized but "full" from the scheduler's perspective
  if its allocatable CPU capacity is exhausted by requests.
  Requests define the scheduler's view of node capacity — not actual usage.
  This is why over-requesting (setting requests too high) wastes cluster capacity
  even when workloads are idle.
```

**How limits are enforced — CPU vs memory (fundamentally different):**

```
CPU limit enforcement (throttling — non-fatal):
  Implemented via Linux cgroups CPU quota (cpu.cfs_quota_us / cpu.cfs_period_us).
  The kernel tracks CPU time in periods (default 100ms).
  If a container's limit is 500m (0.5 CPU):
    In each 100ms period, it may use 50ms of CPU time.
    If it consumes 50ms in the first 10ms of the period:
      → Throttled for the remaining 90ms.
      → The process is runnable but gets no CPU time.
      → From the application's perspective: everything slows down.
      → The process does NOT die. The container does NOT restart.
  CPU throttling is silent and invisible in basic monitoring.
  Symptom: high latency, slow response times with low CPU utilization metric.
  Detection: container_cpu_cfs_throttled_periods_total in Prometheus.

Memory limit enforcement (OOMKill — fatal):
  Implemented via Linux cgroups memory.limit_in_bytes.
  If a container tries to allocate memory beyond its limit:
    The Linux OOM killer is invoked.
    The process is killed with signal 9 (SIGKILL) — untrappable.
    The container restarts (assuming restartPolicy: Always).
    No graceful shutdown. No cleanup. Connection reset to all clients.
  Memory limits are hard. There is no "memory throttling" — only death.
  Symptom: CrashLoopBackOff, OOMKilled in kubectl describe pod events.
  Detection: kube_pod_container_status_last_terminated_reason == OOMKilled.

The asymmetry matters enormously for production:
  Setting a CPU limit too low: application slows down; requests take longer.
  Setting a memory limit too low: application crashes and restarts.
  These have very different production consequences.
```

**Q2. What is the CPU unit (millicores), and how does it map to physical hardware?**
A: Kubernetes measures CPU in millicores (m), where 1000m equals 1 physical CPU core (or 1 vCPU in cloud environments). The unit is consistent regardless of the underlying hardware — 500m always means half a CPU core.

**CPU unit mechanics:**

```
Unit equivalences:
  1000m  = 1 CPU core = 1 vCPU = 1 AWS vCPU = 1 GCP vCPU
  500m   = 0.5 CPU core (half a core)
  100m   = 0.1 CPU core (one-tenth of a core)
  1m     = 0.001 CPU core (minimum meaningful unit)

  You can write: "1" or "1000m" — both mean 1 full core.
  You CANNOT write "0.5" — use "500m".
  You CANNOT use fractional millicores ("0.5m") — 1m is the minimum.

What "using 500m CPU" means physically:
  On a 4-core node, one process using 500m uses 12.5% of total node CPU.
  On an 8-core node, one process using 500m uses 6.25% of total node CPU.
  The millicore abstraction hides hardware heterogeneity.

Node allocatable CPU (what the scheduler sees):
  A node with 4 vCPU does NOT have 4000m available for Pods.
  The kubelet, kube-proxy, OS processes, and system daemons reserve some.
  Typical reserved CPU:
    kubelet --kube-reserved: 100m (kubelet itself)
    kubelet --system-reserved: 100m (OS processes)
    Effective allocatable: 4000m - 200m = 3800m for Pods.
  EKS node (m7g.large, 2 vCPU = 2000m):
    Allocatable CPU: ~1930m (after reservations).

CPU request vs actual usage — the overcommit model:
  CPU is a COMPRESSIBLE resource.
  Multiple containers can share a CPU core — the kernel time-slices.
  If 10 containers each request 100m CPU on a 1-core node:
    Total requested: 1000m = 100% of the core.
    If all 10 are idle: each can burst to use the full core.
    If all 10 are busy simultaneously: each gets ~100m (time-sliced equally).
    The kernel uses CPU shares (proportional to requests) to arbitrate.
  CPU overcommit is safe because throttling, not crashing, is the consequence.

  Memory is an INCOMPRESSIBLE resource.
  You cannot time-slice memory — a byte used by one process is unavailable to another.
  Memory overcommit (limits > requests, summed across Pods) is risky:
    If all Pods simultaneously need their limit amount of memory:
      The node runs out of memory → kubelet evicts Pods.
  This asymmetry between CPU and memory drives different limit-setting strategies.
```

**Q3. What are the memory units in Kubernetes, and what is the difference between Mi and M?**
A: Kubernetes supports both SI (decimal) and IEC (binary) memory units, and confusing them causes silent misconfiguration that is difficult to spot.

**Memory unit reference:**

```
IEC (binary — powers of 2): use these for memory
  Ki = Kibibyte  = 1,024 bytes         (≈ 1 KB)
  Mi = Mebibyte  = 1,048,576 bytes     (≈ 1.05 MB)
  Gi = Gibibyte  = 1,073,741,824 bytes (≈ 1.07 GB)
  Ti = Tebibyte  = 1,099,511,627,776 bytes

SI (decimal — powers of 10): use for storage/network bandwidth
  K  = Kilobyte  = 1,000 bytes
  M  = Megabyte  = 1,000,000 bytes
  G  = Gigabyte  = 1,000,000,000 bytes

The dangerous confusion:
  256M  = 256,000,000 bytes (256 million bytes)
  256Mi = 268,435,456 bytes (256 × 1,048,576 bytes)

  Difference: 12,435,456 bytes (~12 MB, or about 4.6% more for Mi)

  If you intend 256 MiB but write 256M:
    Your limit is 256,000,000 bytes (~244 MiB in practice)
    Your application may be sized to use 256 MiB
    At peak: OOMKilled when the app uses 245–256 MiB
    The crash appears spurious — the limit "should be enough"

  Convention: always use Mi and Gi for memory.
              The Kubernetes community, Prometheus, and all tooling use binary units.
              256Mi means what you think it means.

Practical memory sizing examples:
  Node.js / NestJS process:
    Heap:        128Mi–512Mi (controlled by --max-old-space-size)
    Stack:       ~8Mi per thread (Node.js is single-threaded; negligible)
    Native libs: 30Mi–80Mi (V8 runtime, libuv, OpenSSL)
    Total:       256Mi–700Mi typical for a production NestJS service

  Java (JVM) process:
    Heap:        set via -Xmx (e.g., -Xmx1g)
    Non-heap:    Metaspace + Code cache + Direct memory + Threads
                 Typically 300Mi–500Mi additional beyond heap
    Total:       JVM with -Xmx1g: set limit to 1.5Gi–1.8Gi
    Critical:    -Xmx must be set lower than the container memory limit.
                 Without it: JVM sizes heap relative to node memory (not container limit).
                 A JVM on a 64 GiB node with a 2 GiB container limit:
                   JVM thinks it has 64 GiB available.
                   Sets -Xmx to ~50 GiB.
                   Container hits 2 GiB limit → OOMKilled immediately.
                 Fix: -XX:+UseContainerSupport (Java 10+; default in Java 11+)
                      JVM reads cgroup memory limit; sizes heap appropriately.

  Python process:
    Interpreter overhead: ~30Mi
    Loaded libraries (pandas, numpy): 200Mi–500Mi
    Application data: workload-dependent
    Total: size for peak in-memory data + 200Mi overhead

  Go binary:
    Runtime overhead: 10Mi–30Mi
    Very efficient; goroutines are lightweight (~4KB stack initial size)
    Total: often 50Mi–200Mi for microservices
```

## Section 2: Quality of Service Classes

**Q4. What are the three QoS classes, how are they assigned, and why do they matter during node memory pressure?**
A: Kubernetes assigns every Pod a Quality of Service (QoS) class based on the relationship between its containers' requests and limits. The QoS class determines the order in which Pods are evicted when a node runs low on memory — it is the kubelet's triage mechanism.

**QoS class assignment rules:**

```
Guaranteed (highest priority — last to be evicted):
  Condition: for EVERY container in the Pod:
    - CPU request == CPU limit (must be set and equal)
    - Memory request == Memory limit (must be set and equal)
  Containers with no limit but a request do NOT qualify.
  Containers with no request and no limit do NOT qualify.

  Example:
    resources:
      requests:
        cpu: "500m"
        memory: "256Mi"
      limits:
        cpu: "500m"     ← same as request
        memory: "256Mi" ← same as request
  → QoS: Guaranteed

Burstable (medium priority):
  Condition: does not meet Guaranteed criteria, AND
    at least one container has a request OR limit set.
  The most common class in production.

  Example A (request set, no limit):
    resources:
      requests:
        cpu: "200m"
        memory: "128Mi"
      # no limits
  → QoS: Burstable

  Example B (request < limit):
    resources:
      requests:
        cpu: "200m"
        memory: "128Mi"
      limits:
        cpu: "1000m"
        memory: "512Mi"
  → QoS: Burstable

BestEffort (lowest priority — first to be evicted):
  Condition: NO container in the Pod has any request or limit set.
  resources: {}   OR   resources section entirely absent

  → QoS: BestEffort
  These Pods get whatever resources happen to be available.
  Under any memory pressure: evicted first, immediately.
  Appropriate only for: batch jobs that can be safely interrupted,
  non-critical DaemonSet agents, development workloads.
  Never run production services as BestEffort.
```

**How QoS determines eviction order under memory pressure:**

```
Scenario: Node is at 95% memory utilization. kubelet starts eviction.

Eviction order:
  1. BestEffort Pods → evicted first (no resources committed to them)
  2. Burstable Pods that have exceeded their requests → evicted next
     (ordered by how far above their request they are using)
  3. Burstable Pods that are within their requests → evicted after
  4. Guaranteed Pods → evicted last (only if no other option)

The OOM killer (kernel-level):
  If kubelet eviction is too slow and the node runs completely out of memory:
    The Linux OOM killer activates.
    It kills the process with the highest OOM score.
    OOM score is influenced by: memory usage, QoS class, and oom_score_adj.
    Kubernetes sets oom_score_adj based on QoS:
      Guaranteed:   oom_score_adj = -997  (very unlikely to be killed)
      Burstable:    oom_score_adj = min(max(2, 1000 - 1000×(request/limit)), 999)
                    → higher request-to-limit ratio = lower OOM score = safer
      BestEffort:   oom_score_adj = 1000  (most likely to be killed first)

  Practical implication:
    A Guaranteed Pod will not be OOMKilled by the kernel unless ALL
    Burstable and BestEffort processes are already dead.
    A BestEffort Pod is the first casualty on any memory-pressured node.

The Guaranteed QoS trade-off:
  Guaranteed requires requests == limits for ALL containers.
  CPU: request == limit means no CPU bursting allowed.
    The container is throttled if it ever tries to use more than its limit.
    This reduces performance for bursty workloads (startup spike, GC pause).
  Memory: request == limit means the full memory is "counted" against the node.
    The scheduler reserves the full limit amount at scheduling time.
    Less efficient use of node memory — cannot overcommit.

  Use Guaranteed for:
    Latency-sensitive services where predictability > peak throughput.
    Services with very stable, measured resource usage (no spikes).
    Control plane components (kube-apiserver, etcd, CoreDNS).

  Use Burstable for:
    Most production application Pods.
    Workloads with bursty CPU (startup, compilation, GC).
    Memory-variable workloads (caches that grow and shrink).
    The requests protect against eviction; the limits cap runaway usage.
```

**Q5. What happens when you set a CPU limit vs when you don't set one, and is the conventional wisdom to always set limits correct?**
A: Whether to set a CPU limit is one of the most actively debated topics in Kubernetes production operations. The conventional "always set limits" advice is incorrect for CPU — setting no CPU limit and relying on requests is often the better production choice for latency-sensitive services.

**CPU limit set — what actually happens:**

```
resources:
  requests:
    cpu: "500m"
  limits:
    cpu: "500m"

The kernel enforces via CFS (Completely Fair Scheduler) quota:
  cpu.cfs_period_us = 100,000  (100ms period)
  cpu.cfs_quota_us  = 50,000   (50ms of CPU time per 100ms period)

If the process tries to use 100ms of CPU in a 100ms window:
  First 50ms: runs normally.
  Remaining 50ms: throttled (process is runnable but not scheduled).

This throttling occurs even when the node has spare CPU capacity.
Even if the node is 5% utilized, a container with a 500m limit is throttled
when it tries to use more than 500m — regardless of available capacity.

When CPU throttling causes real production problems:
  Node.js event loop:
    The event loop is single-threaded. If it needs 800ms of CPU for a GC
    cycle but is limited to 500m, the GC takes 1.6× longer wall-clock time.
    During this time: all requests queued behind the GC are delayed.
    Observable as: p99 latency spike every ~30 seconds (GC interval).

  Java startup:
    JVM startup (class loading, JIT compilation) is CPU-intensive.
    A JVM with a 500m CPU limit can take 3–5× longer to start than on bare metal.
    Readiness probe fails during slow startup → Pods killed and restarted.
    → CrashLoopBackOff from a too-low CPU limit during startup.

  Kotlin / Scala compilation:
    Similar to Java startup — burst of CPU needed, then normal usage.
    A CI build runner with a 500m limit compiles in 10 minutes.
    Without a limit (or with 4000m limit): compiles in 90 seconds.

  Python ML inference:
    NumPy/SciPy operations burst to use all available cores for matrix operations.
    A 1000m limit throttles these to 1 core even when the node has 32 cores idle.

Prometheus metric for detecting CPU throttling:
  container_cpu_cfs_throttled_periods_total
  container_cpu_cfs_periods_total

  Throttle ratio:
    rate(container_cpu_cfs_throttled_periods_total[5m]) /
    rate(container_cpu_cfs_periods_total[5m])

  > 25% throttle ratio = CPU limit is likely causing latency problems.
  > 50% throttle ratio = CPU limit is definitely causing problems; raise or remove.
```

**CPU limit not set — what actually happens:**

```
resources:
  requests:
    cpu: "500m"
  # no limits

The container can use any amount of CPU available on the node.
CPU time is distributed proportionally to requests when there is contention:
  Container A: 500m request → gets 50% of contested CPU
  Container B: 500m request → gets 50% of contested CPU
  Container C: 250m request → gets 25% of contested CPU (relative weighting)

When the node is not under CPU contention:
  ALL containers can burst to use 100% of available cores.
  A Node.js GC cycle that wants 2 CPU cores gets 2 CPU cores.
  JVM startup completes at full speed.

When the node IS under CPU contention:
  CPU is shared proportionally to requests.
  Container with 500m request gets approximately 500m of CPU.
  This is exactly what the request guarantees.

The argument against unsetting CPU limits:
  A runaway process (infinite loop, recursive function, memory leak
  causing excessive GC) can consume all CPU on the node, starving
  other Pods — even those with higher requests.
  The CPU proportional scheduling only guarantees minimums when BOTH
  pods are competing; a runaway pod competing with idle pods gets everything.

The practical recommendation (widely used in production):
  Set CPU requests accurately (sized for normal sustained load).
  Set CPU limits high (3–10× the request) or omit them.
  Use LimitRange to set default limits so BestEffort Pods don't emerge.
  Monitor container_cpu_cfs_throttled_periods_total.
  If throttle ratio > 25%: the limit is too low; raise it.

  For NestJS/Node.js API services specifically:
    requests.cpu: "200m"–"500m" (normal sustained load)
    limits.cpu:   "2000m"       (allow bursting for GC, startup, traffic spikes)
    Or:           no CPU limit  (preferred if cluster has node auto-scaling
                                 and you trust the request-based scheduler)
```

## Section 3: Setting Requests and Limits in Practice

**Q6. How do you determine the correct request and limit values for a new service?**
A: There is no formula that produces correct values without measurement. The process is: deploy with generous limits and no initial requests tuned, observe actual usage under production-representative load, then set requests at the P95 of observed usage and limits based on the acceptable ceiling.

**The sizing process:**

```
Phase 1: Initial deployment (over-provisioned intentionally)
  Deploy with generous resources to avoid artificial constraints during profiling.
  Set requests low enough to schedule; set limits high enough to not interfere.

  resources:
    requests:
      cpu:    "100m"     # low enough to always schedule
      memory: "128Mi"    # low enough to always schedule
    limits:
      cpu:    "4000m"    # high; won't throttle anything
      memory: "2Gi"      # high; won't OOMKill anything

  Deploy to a staging environment under production-representative load.
  Run for at least 24–72 hours to capture diurnal patterns (day/night variation).

Phase 2: Observe with Prometheus + Grafana
  Key metrics to capture:

  Actual CPU usage (rate, not gauge):
    rate(container_cpu_usage_seconds_total{
      container="nestjs-api",
      namespace="staging"
    }[5m])
    → time series of CPU cores used

  Actual memory usage (working set — what matters for OOM):
    container_memory_working_set_bytes{
      container="nestjs-api",
      namespace="staging"
    }
    → NOT container_memory_usage_bytes (includes reclaimable cache)
    → working_set is what the kernel counts against the OOM limit

  CPU throttle ratio:
    rate(container_cpu_cfs_throttled_periods_total[5m]) /
    rate(container_cpu_cfs_periods_total[5m])
    → should be near 0 during phase 1 (limits are high)

Phase 3: Analyze the distribution
  CPU usage distribution (over 7 days):
    P50:  150m  (half the time, uses 150m)
    P90:  320m  (90% of the time, uses ≤ 320m)
    P95:  480m  (95% of the time, uses ≤ 480m)
    P99:  850m  (99% of the time, uses ≤ 850m)
    Max:  1200m (peak observed — likely startup or traffic spike)

  Memory usage distribution (over 7 days):
    P50:  180Mi
    P90:  230Mi
    P95:  260Mi
    P99:  310Mi
    Max:  380Mi (likely after a large batch request or memory spike)

Phase 4: Set requests and limits
  CPU request: P90 of observed usage → 320m (rounds to 300m or 350m)
    Rationale: the scheduler needs to know "typical" CPU need.
    Setting to P50 means the Pod runs above its request 50% of the time
    (acceptable; request is a floor, not an average).
    Setting to P99 wastes cluster capacity.

  CPU limit: 3–4× the request, or omit
    If setting a limit: 1000m–1200m (covers the observed max with headroom)
    If omitting: acceptable if the node has spare capacity and you trust
                 the proportional scheduler for contention scenarios.

  Memory request: P95 of observed usage → 260Mi (round to 256Mi)
    Rationale: the scheduler reserves this. Setting too low means the Pod
    can be scheduled on a node with 256Mi free but then use 380Mi,
    potentially contributing to node memory pressure.

  Memory limit: max × 1.3–1.5 headroom → 380Mi × 1.4 ≈ 512Mi (round to 512Mi)
    Rationale: memory can spike during unusual requests or batch operations.
    Headroom absorbs spikes without OOMKilling.
    Too low: OOMKill on legitimate traffic spikes.
    Too high: no protection against memory leaks (they grow unchecked).

Final values:
  resources:
    requests:
      cpu:    "300m"
      memory: "256Mi"
    limits:
      cpu:    "1000m"   # or omit; your call based on cluster policy
      memory: "512Mi"

Phase 5: Validate in staging under peak load
  Load test at 2× expected production traffic.
  Check: CPU throttle ratio < 10%? Memory below limit? No OOMKills?
  Adjust if needed. Then promote to production.
```

**Vertical Pod Autoscaler (VPA) for automated recommendation:**

```
VPA in Recommendation mode (does not change Pods; only reports):
  apiVersion: autoscaling.k8s.io/v1
  kind: VerticalPodAutoscaler
  metadata:
    name: nestjs-api-vpa
    namespace: production
  spec:
    targetRef:
      apiVersion: apps/v1
      kind: Deployment
      name: nestjs-api
    updatePolicy:
      updateMode: "Off"   # Recommendation only; do not mutate Pods

After 24+ hours of data:
  kubectl describe vpa nestjs-api-vpa -n production

  Output:
    Recommendation:
      Container Recommendations:
        Container Name: nestjs-api
          Lower Bound:
            CPU:    100m
            Memory: 200Mi
          Target:              ← use these as your requests
            CPU:    310m
            Memory: 262Mi
          Uncapped Upper Bound:
            CPU:    1200m
            Memory: 512Mi
          Upper Bound:         ← use these as your limits
            CPU:    1000m
            Memory: 512Mi

VPA modes:
  Off:      recommendation only (safe; use in production initially)
  Initial:  sets requests/limits only at Pod creation time; no eviction
  Auto:     evicts and recreates Pods to apply new values (use carefully;
            can cause availability issues if min replicas is 1)
  Recreate: same as Auto but without in-place updates

VPA + HPA compatibility:
  VPA and HPA should NOT both manage the same metric.
  VPA managing CPU + HPA scaling on CPU → they fight each other.
  Safe combination:
    VPA manages CPU and memory sizing (vertical).
    HPA scales on custom metrics (request rate, queue depth) — not CPU.
  Or: use only HPA with manually tuned requests (most common in production).
```

**Q7. What is the LimitRange object, and when is it essential?**
A: A `LimitRange` is a namespace-scoped policy that sets default, minimum, and maximum values for resource requests and limits on Pods and containers within that namespace. It prevents BestEffort Pods (no resources set) from emerging and prevents individual Pods from monopolizing node resources.

**LimitRange structure and effects:**

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: nestjs-namespace-limits
  namespace: production
spec:
  limits:
    # Per-container defaults and bounds
    - type: Container
      default:            # applied if container has NO limit set
        cpu:    "500m"
        memory: "256Mi"
      defaultRequest:     # applied if container has NO request set
        cpu:    "100m"
        memory: "128Mi"
      max:                # maximum allowed limit per container
        cpu:    "4000m"
        memory: "4Gi"
      min:                # minimum allowed request per container
        cpu:    "50m"
        memory: "64Mi"
      maxLimitRequestRatio:  # max allowed ratio of limit to request
        cpu:    "10"         # limit cannot be more than 10× the request
        memory: "4"          # memory limit cannot be more than 4× request

    # Per-Pod bounds (sum across all containers in the Pod)
    - type: Pod
      max:
        cpu:    "8000m"   # no single Pod can request > 8 CPU cores total
        memory: "8Gi"
      min:
        cpu:    "100m"
        memory: "128Mi"

    # Per-PersistentVolumeClaim bounds
    - type: PersistentVolumeClaim
      max:
        storage: "50Gi"
      min:
        storage: "1Gi"
```

**How LimitRange defaults work in practice:**

```
Without LimitRange:
  A developer deploys a Pod with no resources section.
  → QoS: BestEffort.
  → Scheduler places it anywhere (no capacity reservation).
  → Under memory pressure: evicted first (possibly killing a user request).
  → Can consume all CPU on the node if nothing else is running.

With LimitRange (defaultRequest + default set):
  Same Pod with no resources section is submitted.
  → Admission controller (LimitRanger) mutates the Pod spec.
  → Container gets: requests.cpu=100m, requests.memory=128Mi,
                     limits.cpu=500m, limits.memory=256Mi
  → QoS: Burstable (request < limit).
  → Pod is scheduled with capacity reservation.
  → Memory pressure: not the first to be evicted (Guaranteed Pods are safer).

maxLimitRequestRatio enforcement:
  A developer submits:
    requests.memory: "64Mi"
    limits.memory:   "8Gi"  ← ratio: 128× (8192 / 64)
  LimitRange has maxLimitRequestRatio.memory: "4"
  → Admission rejected: "max memory limit to request ratio per Container is 4"

  Why this matters:
    A Pod with a 64Mi request but 8Gi limit:
    - Scheduled on a node with only 64Mi available
    - Runs fine initially (only using 64Mi)
    - Spikes to 4Gi memory usage (maybe during a large request)
    - Other Pods on the node start getting OOMKilled or evicted
    - The node had no idea this Pod could use 4Gi — the scheduler saw 64Mi
  maxLimitRequestRatio prevents the scheduling illusion from being too extreme.

LimitRange is namespace-scoped:
  production namespace: maxLimitRequestRatio.memory: "2" (strict)
  staging namespace:    maxLimitRequestRatio.memory: "8" (lenient)
  development namespace: no LimitRange (developers experiment freely)

LimitRange does NOT affect existing Pods:
  It is enforced at admission time (when the Pod is created).
  Changing a LimitRange does not mutate running Pods.
  To apply new LimitRange defaults to running Pods: rolling restart.
```

**Q8. What is a ResourceQuota, and how does it interact with LimitRange?**
A: A `ResourceQuota` sets a total cap on the aggregate resource consumption within a namespace — the sum of requests and limits across all Pods. Where `LimitRange` constrains individual containers, `ResourceQuota` constrains the namespace as a whole.

**ResourceQuota structure:**

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    # Total CPU and memory REQUESTS across all Pods in the namespace
    requests.cpu:    "20"       # no more than 20 CPU cores requested in total
    requests.memory: "40Gi"     # no more than 40 GiB requested in total

    # Total CPU and memory LIMITS across all Pods in the namespace
    limits.cpu:      "40"       # no more than 40 CPU cores limited in total
    limits.memory:   "80Gi"     # no more than 80 GiB limited in total

    # Object count quotas
    pods:                "100"  # no more than 100 Pods in the namespace
    services:            "20"
    secrets:             "50"
    configmaps:          "50"
    persistentvolumeclaims: "20"

    # Storage quotas
    requests.storage:              "500Gi"
    storageclass.storage.k8s.io/gp3.requests.storage: "200Gi"
```

**ResourceQuota enforcement and interaction with LimitRange:**

```
When ResourceQuota is present, ALL Pods MUST have requests and limits set.
  If a namespace has a ResourceQuota on requests.cpu but a Pod has no
  requests.cpu set: → admission rejected, even if LimitRange would default it.

  Order of operations:
    1. LimitRange defaults are applied first (if the field is unset).
    2. ResourceQuota is checked against the post-defaulting spec.
    If LimitRange defaults are set AND ResourceQuota is set:
      → Pods without explicit resources get LimitRange defaults applied.
      → Those defaults count against the ResourceQuota.
    If ResourceQuota is set but LimitRange is NOT:
      → Pods must explicitly set resources; no defaults are applied.
      → A Pod with no resources section is rejected.

  Production best practice: always deploy LimitRange and ResourceQuota together.
    LimitRange: ensures every Pod has sane defaults (no BestEffort).
    ResourceQuota: ensures the namespace can't consume unbounded cluster resources.

Checking quota usage:
  kubectl describe resourcequota production-quota -n production

  Output:
    Name:            production-quota
    Namespace:       production
    Resource         Used    Hard
    ──────────────── ─────── ─────
    limits.cpu       8500m   40
    limits.memory    17Gi    80Gi
    pods             23      100
    requests.cpu     3100m   20
    requests.memory  8Gi     40Gi

  When a new Deployment tries to scale from 3 → 10 replicas:
    Each replica: requests.cpu=300m, requests.memory=256Mi
    Additional 7 replicas: 7 × 300m = 2100m CPU, 7 × 256Mi = 1792Mi memory
    Current used: 3100m CPU, 8Gi memory
    After scale: 5200m CPU (< 20 ✅), 9.75Gi memory (< 40Gi ✅)
    → Scaling allowed.

  When the same Deployment tries to scale to 50 replicas:
    Additional 47 replicas: 47 × 300m = 14100m CPU
    After scale: 17200m CPU > 20000m ❌
    → Admission rejected: "exceeded quota: production-quota,
       requested: requests.cpu=14100m, used: requests.cpu=3100m,
       limited: requests.cpu=20"
    → The Deployment stays at its current replica count; events show the error.
    → New Pods fail to create; existing Pods continue running.
```

## Section 4: Node Pressure, Eviction, and the Relationship to Cluster Autoscaler

**Q9. How does the kubelet's eviction mechanism work, and what thresholds trigger it?**
A: The kubelet continuously monitors node-level resources (memory, disk, PID count) against configurable thresholds. When a threshold is crossed, the kubelet evicts Pods — ordered by QoS class — to reclaim resources and prevent the node from becoming completely unavailable.

**Eviction threshold types:**

```
Soft eviction thresholds:
  The node has exceeded the threshold, but the kubelet waits for a
  grace period before evicting. The grace period allows temporary spikes
  to resolve without unnecessary evictions.

  Example:
    --eviction-soft=memory.available<500Mi
    --eviction-soft-grace-period=memory.available=90s
  → If available memory drops below 500Mi for 90 consecutive seconds: evict.
  → If it recovers within 90 seconds: no eviction.

Hard eviction thresholds:
  The kubelet evicts immediately when the threshold is crossed.
  No grace period.

  Example:
    --eviction-hard=memory.available<100Mi
  → If available memory drops below 100Mi: immediate eviction.

EKS default eviction thresholds (typical managed Kubernetes):
  memory.available:   100Mi (hard), 500Mi (soft with 90s grace)
  nodefs.available:   10%  (hard) — root filesystem
  nodefs.inodesFree:  5%   (hard)
  imagefs.available:  15%  (hard) — container image filesystem

What "memory.available" means:
  memory.available = node total memory
                   - memory used by Pods (working set)
                   - memory used by system processes
                   - kubelet reserved memory

  It does NOT equal: node total memory - container memory limits
  It reflects ACTUAL usage, not scheduled limits.
```

**The eviction sequence:**

```
Node memory: 16 GiB total
  System + kubelet reserved: 1 GiB
  Currently used by Pods: 14.8 GiB (working set)
  Available: 0.2 GiB = 200 MiB

  Hard eviction threshold: 100 MiB → not yet triggered.
  Soft eviction threshold: 500 MiB → TRIGGERED (200 MiB < 500 MiB)

  kubelet starts 90-second grace period.
  After 90 seconds, still < 500 MiB: eviction begins.

Step 1: kubelet signals eviction via condition NodeMemoryPressure=True.
  New Pods cannot be scheduled to this node (NoSchedule effect).

Step 2: kubelet ranks Pods for eviction:
  1. BestEffort Pods (any usage) → evicted first
  2. Burstable Pods whose usage > request (furthest over request, first)
  3. Burstable Pods whose usage ≤ request
  4. Guaranteed Pods (only if above categories insufficient)

Step 3: kubelet sends SIGTERM to the highest-ranked eviction candidate.
  Pod terminationGracePeriodSeconds applies (default 30s).
  After grace period: SIGKILL.
  kubelet re-checks memory after each eviction; stops when above threshold.

Step 4: Evicted Pod's status:
  kubectl get pod <pod> -n production
  → STATUS: Evicted
  kubectl describe pod <pod> -n production
  → Reason: Evicted
    Message: The node had condition: [MemoryPressure]

  The Pod object remains as a record (unlike Completed Pods, which are
  cleaned up by the garbage collector after ttlSecondsAfterFinished).
  Clean up evicted Pod objects:
    kubectl get pods -n production -o json | \
      jq '.items[] | select(.status.reason == "Evicted") | .metadata.name' | \
      xargs kubectl delete pod -n production

  The Deployment controller notices the evicted Pod and creates a replacement.
  The replacement is scheduled elsewhere (the pressured node is NoSchedule).
```

**The relationship between limits, requests, and eviction pressure:**

```
Common misunderstanding: "setting limits prevents eviction"

Reality:
  Limits are enforced at the container level by cgroups.
  Eviction is a node-level response to actual resource pressure.

  A node with 10 Pods, each with memory limit=2Gi, request=256Mi:
    Total limits:   10 × 2Gi = 20Gi
    Total requests: 10 × 256Mi = 2.56Gi
    Node memory:    16Gi

    The scheduler sees: 16Gi available - 2.56Gi requested = 13.44Gi free.
    Schedules the 10 Pods here (requests fit).

    All 10 Pods simultaneously spike to 1.5Gi memory each:
      Total actual usage: 15Gi
      Node available memory: 16Gi - 1Gi reserved - 15Gi used = 0 GiB
      Hard eviction: 100 MiB threshold crossed.
      Kubelet evicts Burstable Pods that are furthest above their 256Mi requests.
      ALL of these Pods are far above their request (1.5Gi vs 256Mi request).

  The limit (2Gi per Pod) did not prevent eviction because:
    The limit is per-container; the eviction is based on the aggregate node state.
    Setting limits prevents one container from exceeding 2Gi.
    It does NOT prevent 10 containers from collectively exhausting node memory.

  The correct protection against eviction:
    Set requests close to actual usage (not artificially low).
    Memory request = P95 of observed working_set usage.
    This gives the scheduler an honest view of memory needs.
    Pods are placed on nodes that genuinely have enough memory.
    When all Pods use their expected memory: no eviction.
```

**Q10. How does the Cluster Autoscaler interact with requests and limits, and why does over-requesting block scale-down?**
A: The Cluster Autoscaler (CA) adds nodes when Pods cannot be scheduled (insufficient capacity based on requests), and removes nodes when they are underutilized (all Pods on the node could be accommodated on other nodes). Both decisions are based on requests, not actual usage.

**Scale-up trigger:**

```
Condition: a Pod is Pending because no node has enough capacity
           to satisfy its requests.

CA detects the Pending Pod.
CA simulates scheduling the Pod on each available node type.
If no existing node can fit the Pod: CA provisions a new node.

After new node is Ready (~2–5 minutes for cloud provider):
  CA marks the node as schedulable.
  kube-scheduler places the Pending Pod on the new node.

What CA evaluates:
  Can the new Pod's requests fit on an existing node, given existing Pods' requests?
  This is the same calculation the scheduler makes.
  It is based entirely on REQUESTS, not actual CPU/memory usage.

Implication:
  A node running at 5% actual CPU utilization can still trigger scale-up
  if its CPU requests are 95% allocated.
  Wasted capacity (high requests, low actual use) directly causes
  premature scale-up → more nodes → higher cloud cost.
```

**Scale-down trigger and the blocker:**

```
Condition: a node is underutilized by CA's definition:
  CPU requests / allocatable CPU < 50% (default threshold)
  AND memory requests / allocatable memory < 50%
  AND all Pods on the node can be placed on other nodes.

CA attempts to evict all Pods from the node → drain the node →
terminate the cloud instance.

Why over-requesting blocks scale-down:
  Node X: 8 CPU cores allocatable (8000m)
    Running Pods' CPU requests: 4200m (53% utilization)
    CA threshold: 50% → Node X is NOT eligible for scale-down (53% > 50%).
    Actual CPU usage: 400m (5%) — the Pods are largely idle.

  All the excess CPU request is wasted capacity that prevents scale-down.
  At scale (100 nodes): even 5% average over-requesting can prevent
  10–15 nodes from scaling down → significant cost waste.

  The fix: set requests to reflect actual usage.
    If actual CPU use is 400m on average: request 400m, not 4000m.
    Node X CPU requests: 420m (5.25% of 8000m) — far below 50% threshold.
    CA evicts Pods to other nodes → drains Node X → terminates instance.
    Cluster: 8 nodes → 7 nodes. Cost: -1 instance/hour perpetually.

Scale-down blockers (non-resource):
  Pods with no PodDisruptionBudget that disallow eviction.
  Pods with local storage (emptyDir with data; hostPath).
  Pods that are not managed by a controller (standalone Pods; no ReplicaSet).
  Pods with annotations: cluster-autoscaler.kubernetes.io/safe-to-evict: "false"
  DaemonSet Pods (CA never evicts DaemonSet Pods for scale-down).

  Check why a node is not scaling down:
  kubectl describe node <node-name> | grep -A5 "cluster-autoscaler"
  # OR check CA logs:
  kubectl logs -n kube-system -l app=cluster-autoscaler | grep "scale-down"
  # CA logs explicitly state which Pod blocks scale-down and why.
```

## Section 5: Advanced Patterns and Production Scenarios

**Q11. How do you handle resource sizing for a Node.js / NestJS service with a JVM-style memory model, and what are the Node.js-specific pitfalls?**
A: Node.js has a heap managed by V8 with a default maximum that does not adapt to the container's memory limit. Without explicit configuration, a NestJS service in a 512Mi container can crash at startup or leak memory silently before hitting the container limit.

**Node.js memory anatomy inside a container:**

```
A NestJS process's memory footprint:

1. V8 Heap (JS objects, closures, buffers):
   Default heap limit: 1.5 GiB on 64-bit systems (not container-aware).
   If the container limit is 512Mi: V8 allows up to 1.5 GiB heap
   but the container limit is 512Mi.
   The cgroup OOMKill fires at 512Mi, before V8's own GC would trigger.
   Result: process OOMKilled while V8 thinks it has headroom.

   Fix: set --max-old-space-size to ~75% of the container memory limit:
     Container limit: 512Mi
     --max-old-space-size=384  (in MB; 384 MB = ~75% of 512 MiB)
     V8 starts GC aggressively before reaching 384 MB.
     The remaining 128 MiB is headroom for non-heap memory.

2. Non-heap memory (not controlled by --max-old-space-size):
   V8 code cache:      20Mi–50Mi
   V8 native memory:   10Mi–30Mi
   libuv handles:      small (sockets, file descriptors)
   Node.js Buffer:     allocated outside the heap (Buffer.alloc uses native mem)
   OpenSSL:            TLS session cache; 20Mi–50Mi for busy HTTPS services
   Native addons:      variable (bcrypt, sharp add native memory)

   Total non-heap: typically 50Mi–150Mi for a typical NestJS service.
   If using Prisma (native Rust query engine): add 50Mi–80Mi.
   If using Sharp (native libvips): add 30Mi–100Mi depending on usage.

Recommended memory configuration for NestJS:
  Container memory limit: 512Mi
    --max-old-space-size=360  (360 MB: ~70% of 512 MiB, leaves 150 MiB non-heap)

  Container memory limit: 256Mi
    --max-old-space-size=180  (leaves 75 MiB non-heap — very tight; prefer 512Mi)

  Container memory limit: 1Gi
    --max-old-space-size=768  (leaves 256 Mi non-heap; comfortable)

  Set via environment variable (preferred; no Dockerfile change needed):
    env:
      - name: NODE_OPTIONS
        value: "--max-old-space-size=360"

  Or via Downward API (dynamically sized to container limit):
    env:
      - name: MEMORY_LIMIT_MIB
        valueFrom:
          resourceFieldRef:
            containerName: nestjs-api
            resource: limits.memory
            divisor: 1Mi
      - name: NODE_OPTIONS
        value: "--max-old-space-size=$(expr $MEMORY_LIMIT_MIB '*' 70 '/' 100)"
    Note: the expr calculation in value is NOT evaluated by the shell at injection.
    Use an entrypoint script instead:
      #!/bin/sh
      LIMIT_MIB=$(cat /sys/fs/cgroup/memory/memory.limit_in_bytes | awk '{print $1/1048576}')
      HEAP_MIB=$(echo "$LIMIT_MIB * 0.70" | bc | cut -d. -f1)
      exec node --max-old-space-size=$HEAP_MIB dist/main.js
```

**Node.js-specific memory pitfalls in containers:**

```
Pitfall 1: Buffer pool not counted in heap metrics
  Node.js Buffer uses native memory (malloc, outside V8 heap).
  process.memoryUsage().heapUsed shows V8 heap only.
  A service that processes large file uploads using Buffer.alloc():
    heapUsed: 200 MB (V8 metrics look fine)
    Native buffer memory: 400 MB (not in heapUsed)
    Total RSS: 600 MB → container limit 512Mi → OOMKilled
  Detection: monitor container_memory_working_set_bytes (cgroup level),
             not process.memoryUsage().heapUsed (V8 level only).

Pitfall 2: Worker threads each have their own heap
  Each Worker thread has its own V8 heap.
  --max-old-space-size applies per-thread.
  A NestJS service with 4 Worker threads, each with --max-old-space-size=360:
    Potential heap: 4 × 360 MB = 1440 MB → well above a 512Mi container limit.
  Fix: account for workers in total memory budget.
       With 4 workers in a 512Mi container:
       Per-worker heap: (512 × 0.7) / 4 = ~90 MB per worker.
       --max-old-space-size=90 per worker.

Pitfall 3: require() cache memory not released
  Every require()d module stays in memory for the process lifetime.
  A large dependency tree (common in NestJS with many modules) consumes
  30–100 MB of heap for module cache alone.
  This is baseline memory that exists from the first request.
  Account for it: the "empty" memory usage after startup is the baseline.
  Memory request should be at least: baseline + P95(request processing overhead).

Pitfall 4: pm2 cluster mode multiplies memory
  pm2 -i max starts one worker process per CPU core.
  On a 4-core node: 4 worker processes.
  Each process has its own heap.
  Memory limit applies to the CONTAINER, not per-process.
  pm2 with 4 workers × 200Mi per worker = 800Mi needed.
  Container limit of 512Mi → OOMKilled when all 4 workers are active.
  Fix: set pm2 instances to a number compatible with the container limit:
       instances: 2 (with a 512Mi container, 2 workers fit comfortably).
```

**Q12. Describe a production incident caused by resource misconfiguration and how you would diagnose it.**
A:

```
Incident: NestJS API service experiencing intermittent 503 errors.
  Pattern: errors occur during business hours; service recovers without action;
           no code was deployed; no external dependencies changed.
  Alert: p99 latency > 5 seconds; error rate > 2%.

Diagnosis:

Step 1: Check Pod health
  kubectl get pods -n production -l app=nestjs-api
  → All Pods show Running. No CrashLoopBackOff. Looks healthy.

Step 2: Check recent events
  kubectl get events -n production --sort-by='.lastTimestamp' | grep nestjs-api
  → Events show: "Killing container with id ...: Need to kill Pod"
    "OOMKilling" on several Pods in the past 6 hours.
    Pods were OOMKilled and restarted. Now Running → looks healthy.
    But during restart: the Deployment had fewer ready Pods →
    ALB/ingress sent requests to insufficient capacity → 503s.

Step 3: Confirm OOMKill
  kubectl describe pod <pod-name> -n production
  → Containers:
      nestjs-api:
        Last State: Terminated
          Reason: OOMKilled
          Exit Code: 137        ← 128 + 9 (SIGKILL)
          Started: Mon, 07 Aug 2026 09:15:33
          Finished: Mon, 07 Aug 2026 09:47:19
  
  Prometheus:
    kube_pod_container_status_last_terminated_reason{
      reason="OOMKilled",
      container="nestjs-api",
      namespace="production"
    }
    → Shows spike at 09:15 and 11:30 (business hours peaks)

Step 4: Analyze memory usage over time
  container_memory_working_set_bytes{container="nestjs-api"}
  → Trend: memory grows steadily from 200Mi at 09:00 to 490Mi at 09:47.
    Container limit: 512Mi.
    OOMKill at 09:47 when working set hit 512Mi.

  Pattern: memory grows over time without releasing → memory leak.
  Additional: growth is faster during business hours (more requests) →
  leak is proportional to request rate.

Step 5: Identify the leak
  Add heapdump on SIGUSR2 to the NestJS process:
    import * as v8 from 'v8';
    process.on('SIGUSR2', () => {
      const filename = `/tmp/heap-${Date.now()}.heapsnapshot`;
      v8.writeHeapSnapshot(filename);
    });
  kubectl exec -it <pod> -n production -- kill -USR2 1
  kubectl cp <pod>:/tmp/heap-<timestamp>.heapsnapshot ./heap.heapsnapshot
  Open in Chrome DevTools → Memory → Load snapshot
  → Find: EventEmitter listeners accumulating; 50,000 listeners added over 2 hours.
    Root cause: a third-party SDK adds a listener on every request but never removes it.
    Fix: call emitter.removeListener() or use emitter.once() for single-use listeners.

Immediate mitigation (before fix deployment):
  Increase memory limit temporarily:
    kubectl set resources deployment/nestjs-api \
      -c nestjs-api --limits=memory=1Gi -n production
  Add liveness probe restart on threshold:
    livenessProbe:
      exec:
        command:
          - /bin/sh
          - -c
          - "node -e \"const m=process.memoryUsage(); if(m.rss>900*1024*1024) process.exit(1)\""
      periodSeconds: 30
      failureThreshold: 2
  (Liveness probe kills the container before the OOMKill; allows graceful shutdown
  via SIGTERM rather than abrupt SIGKILL — NestJS onApplicationShutdown() runs.)

Long-term fix:
  Fix the EventEmitter leak in the SDK usage.
  Set memory request to observed P95 (260Mi).
  Set memory limit to 512Mi (the actual requirement without the leak).
  Add Prometheus alert: memory_working_set > 80% of limit for > 5 minutes.
  This fires before the OOMKill, giving time to investigate.

Correct Prometheus alerting rule:
  - alert: ContainerMemoryNearLimit
    expr: |
      (
        container_memory_working_set_bytes{container!="", namespace="production"}
        /
        container_spec_memory_limit_bytes{container!="", namespace="production"}
      ) > 0.80
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "Container {{ $labels.container }} in {{ $labels.pod }} is using > 80% of memory limit"
      description: "Memory usage {{ $value | humanizePercentage }} of limit"

  - alert: ContainerOOMKilled
    expr: |
      kube_pod_container_status_last_terminated_reason{
        reason="OOMKilled",
        namespace="production"
      } == 1
    for: 0m
    labels:
      severity: critical
    annotations:
      summary: "Container {{ $labels.container }} OOMKilled in {{ $labels.pod }}"
```

## Quick Reference

| Setting | Controls | Enforced by | Effect when exceeded |
|---|---|---|---|
| `requests.cpu` | Scheduling guarantee | kube-scheduler | Pod not scheduled if no node has capacity |
| `requests.memory` | Scheduling guarantee + eviction order | kube-scheduler + kubelet | Pod not scheduled; used to rank eviction candidates |
| `limits.cpu` | CPU ceiling | Linux CFS cgroups | Throttled (slowed, not killed) |
| `limits.memory` | Memory ceiling | Linux cgroups OOM killer | Process killed (OOMKill); container restarts |

| QoS Class | Requirement | Eviction priority | OOM score |
|---|---|---|---|
| Guaranteed | requests == limits for ALL containers | Last | -997 (safest) |
| Burstable | At least one request or limit set | Middle | 2–999 (proportional) |
| BestEffort | No requests or limits | First | 1000 (evicted first) |

| Metric | What it measures | Use for |
|---|---|---|
| `container_cpu_usage_seconds_total` | Actual CPU used | Setting CPU requests |
| `container_cpu_cfs_throttled_periods_total` | CPU throttling events | Detecting too-low CPU limits |
| `container_memory_working_set_bytes` | Active memory (what OOM uses) | Setting memory requests and limits |
| `container_memory_usage_bytes` | Total memory incl. cache | Misleading; prefer working_set |
| `kube_pod_container_status_last_terminated_reason` | Why the container last died | Detecting OOMKills |

| Sizing guideline | Rule |
|---|---|
| CPU request | P90 of observed `container_cpu_usage_seconds_total` over 7 days |
| CPU limit | 3–10× request, or omit; monitor throttle ratio |
| Memory request | P95 of `container_memory_working_set_bytes` over 7 days |
| Memory limit | Max observed × 1.3–1.5 headroom; round to nearest Mi boundary |
| Node.js `--max-old-space-size` | ~70% of container memory limit (in MB) |
| JVM `-Xmx` | Container memory limit × 0.5–0.75; enable `-XX:+UseContainerSupport` |

| Failure mode | Symptom | Root cause | Fix |
|---|---|---|---|
| OOMKilled | Exit code 137; CrashLoopBackOff | Memory limit too low OR memory leak | Increase limit; fix leak; add memory alert |
| High p99 latency | Slow requests; CPU looks low | CPU throttling | Raise or remove CPU limit; check throttle metric |
| Pod stuck Pending | No node available | Requests too high; node capacity exhausted | Right-size requests; add nodes |
| Node full but low utilization | Pods can't schedule; nodes idle | Over-requesting (requests >> actual use) | Lower requests to match actual usage; use VPA |
| CA won't scale down | Nodes persist; cost doesn't drop | Over-requesting blocks CA underutil threshold | Lower requests; remove CA blockers |
| JVM OOMKilled at startup | Immediate OOMKill; container never Ready | JVM sized heap to node memory, not container | Set `-XX:+UseContainerSupport`; set `-Xmx` explicitly |
| Node.js silent OOMKill | OOMKill without V8 GC triggering | `--max-old-space-size` not set; V8 headroom > container limit | Set `--max-old-space-size` to 70% of container limit |
| BestEffort Pods evicted constantly | Pods restart under any load | No requests or limits set | Add LimitRange defaults; set explicit resources |
| Quota exceeded on scale | Deployment stuck at current replica count | ResourceQuota exhausted | Increase quota or reduce per-Pod requests |
| subPath config not updating | Stale config despite ConfigMap update | subPath breaks live propagation | Unrelated to resources; see ConfigMap doc |

## The Core Mental Model

```
Requests and limits are enforced at completely different layers of the system.
Forgetting this causes almost every resource misconfiguration incident.

  Requests: the scheduler's currency.
    The scheduler sums requests across all Pods on a node.
    A node is "full" when its request sum equals allocatable capacity —
    regardless of actual usage. CPU at 5%, requests at 95% → full.
    Set requests to actual usage, not to the maximum conceivable usage.
    Over-requesting wastes cluster capacity and prevents CA scale-down.

  Limits: the kernel's enforcement.
    CPU limits: throttle (non-fatal; silent; causes latency).
    Memory limits: kill (fatal; container restarts; causes 503s during restart).
    The asymmetry is critical: a CPU limit that's too low is annoying;
    a memory limit that's too low causes production incidents.

The three sizing inputs, in order of importance:
  1. container_memory_working_set_bytes (P95 over 7 days) → memory request
  2. container_cpu_usage_seconds_total (P90 over 7 days)  → CPU request
  3. container_cpu_cfs_throttled_periods_total (ratio)    → tells you if CPU limit is wrong
  Without these measurements, any numbers you set are guesses.

QoS class is determined by your settings, not by declaration:
  You do not set QoS. Kubernetes derives it.
  requests == limits (all containers) → Guaranteed (safe from eviction; no bursting).
  requests < limits (any container)   → Burstable (can burst; evicted before Guaranteed).
  nothing set                         → BestEffort (evicted first; never for production).
  Every production Pod should be at least Burstable.
  Guaranteed is correct for control-plane-like components with predictable, stable load.

Node.js in containers requires explicit V8 heap configuration:
  V8 does not read cgroup limits. It sizes the heap for the machine, not the container.
  On a 64 GiB node: V8 default max heap ≈ 1.5 GiB.
  In a 512Mi container: OOMKill before V8 GC even triggers.
  Always set --max-old-space-size ≈ 0.70 × (container memory limit in MB).
  Always monitor container_memory_working_set_bytes, not process.memoryUsage().heapUsed.

LimitRange + ResourceQuota is the namespace governance pair:
  LimitRange: per-container defaults and bounds.
    Prevents BestEffort (no resources). Caps individual containers.
    Applied at admission: every Pod gets sane defaults even if the developer forgot.
  ResourceQuota: per-namespace aggregate cap.
    Prevents a single namespace from consuming unbounded cluster resources.
    Forces all Pods to have resources set (otherwise quota enforcement fails).
  Deploy both together. They are complementary, not alternatives.

The CA scale-down rule: if over-requesting, you pay for idle nodes.
  CA only removes a node if its Pods' total requests fit elsewhere.
  A node at 5% actual utilization but 60% requested utilization is NOT removed.
  The direct cost of over-requesting: idle cloud instances that cannot be reclaimed.
  Right-sizing requests is the highest-ROI cluster cost optimization available.
  VPA in Off mode gives you the right numbers without risk.
```

**Tip for the interview:** Resource requests and limits questions at 5 YOE converge on three areas: (1) the request vs limit distinction at the mechanism level — being able to explain that requests are consumed by the kube-scheduler (cluster-level placement) while limits are enforced by the Linux cgroup subsystem on the node, that CPU limits cause throttling (non-fatal; the process slows down) while memory limits cause OOMKill (fatal; SIGKILL; no graceful shutdown), and that `container_cpu_cfs_throttled_periods_total` is the metric that reveals silent CPU throttling which `kubectl top` never shows, demonstrates you have debugged a "CPU is low but latency is high" incident caused by CPU throttling rather than just knowing the YAML fields; (2) QoS class mechanics and their eviction consequences — explaining that QoS is derived from the relationship between requests and limits (not declared), that BestEffort Pods are the first casualty under any node memory pressure, that the `oom_score_adj` for Guaranteed Pods is -997 (making them nearly immune to kernel OOMKill), and that a Guaranteed QoS Pod trades burst ability for eviction safety, shows you understand why the kubelet's eviction ordering matters for multi-tenant production clusters; (3) the Node.js heap sizing problem — explaining that V8 sizes its heap relative to the machine's total memory (not the cgroup limit), that `--max-old-space-size` must be set to ~70% of the container memory limit or OOMKills occur before V8 GC triggers, and that `container_memory_working_set_bytes` (not `process.memoryUsage().heapUsed`) is the correct signal for container memory because it includes native/Buffer memory outside the V8 heap, demonstrates that you have actually debugged a Node.js OOMKill incident in a container rather than just knowing that limits exist. The fintech callout: for NACH batch processing services that spike to 10× normal memory during batch window, the correct pattern is Burstable QoS with a memory request sized to normal operation (256Mi) and a memory limit sized to peak batch operation (2Gi), combined with a Prometheus alert at 80% of the limit, and a PodDisruptionBudget that prevents eviction during the batch window — the CA is configured to not scale down nodes hosting batch Pods during 09:00–11:00 IST via node selectors and anti-affinity, ensuring the batch completes without interruption.
