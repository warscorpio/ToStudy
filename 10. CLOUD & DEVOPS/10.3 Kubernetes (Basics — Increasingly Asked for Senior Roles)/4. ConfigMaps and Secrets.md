# Kubernetes ConfigMaps and Secrets: Storage, Injection, Rotation, and Security — Interview Q&A (5 YOE Level)

---

## Section 1: ConfigMaps — Structure, Purpose, and the Configuration Separation Principle

**Q1. What is a ConfigMap, what problem does it solve, and how does it fit into the Kubernetes configuration model?**
A: A ConfigMap is a Kubernetes API object that stores non-confidential configuration data as key-value pairs. It decouples environment-specific configuration from the container image, so the same image can be deployed to dev, staging, and production by changing the ConfigMap — not by rebuilding the image.

**The configuration separation principle:**

```
Without ConfigMaps (anti-pattern):
  Image: nestjs-api:prod contains:
    ENV DATABASE_HOST=prod-rds.internal
    ENV LOG_LEVEL=warn
    ENV MAX_CONNECTIONS=100

  To change LOG_LEVEL for debugging: rebuild the image, push to ECR,
  roll the deployment. A 5-minute pipeline for a one-line config change.

  Worse: dev and prod use different images only because of config differences.
  Image promotion (dev → staging → prod) is impossible; the image carries
  its environment baked in.

With ConfigMaps (correct pattern):
  Image: nestjs-api:sha256-abc123 (identical across all environments)
  ConfigMap/dev:  LOG_LEVEL=debug, MAX_CONNECTIONS=5
  ConfigMap/prod: LOG_LEVEL=warn,  MAX_CONNECTIONS=100

  To change LOG_LEVEL in prod:
    kubectl edit configmap nestjs-api-config -n production
    kubectl rollout restart deployment/nestjs-api -n production
    No image rebuild. No CI pipeline. 30 seconds.

  The image is environment-agnostic. The same image digest runs in dev,
  staging, and production. Configuration lives outside the image.
```

**ConfigMap API object structure:**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nestjs-api-config
  namespace: production
  labels:
    app: nestjs-api
    managed-by: terraform
  annotations:
    # Track the last time this was updated (useful for audit)
    last-updated-by: "ci-deploy-pipeline"
    last-updated-at: "2026-08-07T09:00:00Z"

data:
  # Simple key-value pairs (most common)
  LOG_LEVEL: "warn"
  NODE_ENV: "production"
  PORT: "3000"
  MAX_CONNECTIONS: "100"
  CORS_ORIGINS: "https://app.example.com,https://admin.example.com"

  # Multi-line value: entire config file as a single key
  app.yaml: |
    server:
      port: 3000
      timeout: 30s
    database:
      pool:
        min: 2
        max: 100
      idle_timeout: 600s
    logging:
      level: warn
      format: json

  # Another file-style key
  .env.defaults: |
    FEATURE_FLAG_NEW_CHECKOUT=false
    FEATURE_FLAG_DARK_MODE=true
    CACHE_TTL_SECONDS=3600

binaryData:
  # Base64-encoded binary content (rare for ConfigMaps; more common in Secrets)
  logo.png: <base64-encoded-bytes>
```

**What ConfigMaps are and are not for:**

```
Use ConfigMaps for:
  Application configuration (log levels, feature flags, timeouts, pool sizes)
  File-format config (nginx.conf, application.yaml, prometheus.yml)
  Environment-specific URLs (internal service endpoints, not secrets)
  Tunable parameters that ops teams adjust without developer involvement

Do NOT use ConfigMaps for:
  Passwords, API keys, tokens, certificates, private keys
    → Use Secrets (and ideally external secret managers — see Section 3)
  Large binary assets (>1 MB is a strong signal to use an object store)
  Data that changes at sub-minute frequency
    → ConfigMaps are not a message bus or a cache
  Configuration that needs audit history per-change
    → Use a GitOps workflow (Argo CD / Flux) where the ConfigMap source
       is version-controlled and every change has a git commit

ConfigMap size limit:
  1 MiB total across all keys in a single ConfigMap.
  If configuration exceeds this: split into multiple ConfigMaps by domain
  (nestjs-api-server-config, nestjs-api-db-config, nestjs-api-features-config).
```

**Q2. What are the three ways to create a ConfigMap, and when do you use each?**
A: ConfigMaps can be created from literal values, from files, or from a YAML manifest. The creation method determines the key names and values in the resulting object.

**Method 1: From literal values (`--from-literal`)**

```bash
kubectl create configmap nestjs-api-config \
  --from-literal=LOG_LEVEL=warn \
  --from-literal=PORT=3000 \
  --from-literal=NODE_ENV=production \
  --namespace=production

# Resulting ConfigMap data:
# data:
#   LOG_LEVEL: warn
#   PORT: "3000"
#   NODE_ENV: production

# Use when:
#   Quick debugging or one-off config creation.
#   Teaching or demos.
# Do NOT use in production: not version-controlled; not reproducible.
```

**Method 2: From files (`--from-file`, `--from-env-file`)**

```bash
# --from-file: key = filename, value = file contents
kubectl create configmap nestjs-api-config \
  --from-file=app.yaml=./config/app.yaml \
  --from-file=nginx.conf=./config/nginx.conf \
  --namespace=production

# Resulting ConfigMap data:
# data:
#   app.yaml: |
#     server:
#       port: 3000
#     ...
#   nginx.conf: |
#     server {
#       listen 80;
#     ...

# --from-env-file: parses a .env file; each line becomes a key-value pair
kubectl create configmap nestjs-api-config \
  --from-env-file=./config/production.env \
  --namespace=production

# production.env:
#   LOG_LEVEL=warn
#   PORT=3000
#   NODE_ENV=production
#
# Resulting ConfigMap data:
# data:
#   LOG_LEVEL: warn
#   PORT: "3000"
#   NODE_ENV: production

# Use when:
#   Config already lives in a file format (nginx.conf, prometheus.yml).
#   Migrating from a .env-based deployment.
# Still prefer declarative YAML manifests for production.
```

**Method 3: Declarative YAML manifest (recommended for production)**

```yaml
# config/nestjs-api-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nestjs-api-config
  namespace: production
data:
  LOG_LEVEL: "warn"
  PORT: "3000"
  NODE_ENV: "production"
  MAX_CONNECTIONS: "100"
```

```bash
kubectl apply -f config/nestjs-api-configmap.yaml

# Use when: always, in production.
# Advantages:
#   Version-controlled in git.
#   Reviewed in pull requests.
#   Applied by CI/CD pipeline (Argo CD syncs automatically).
#   Reproducible: same YAML → same ConfigMap on every cluster.
#   Diffable: kubectl diff -f configmap.yaml shows what will change.
```

## Section 2: Injecting ConfigMaps into Pods

**Q3. What are the two injection mechanisms for ConfigMaps, and what are the trade-offs between them?**
A: ConfigMap data can be injected into a Pod as environment variables or as files mounted into the container's filesystem via a Volume. The mechanism determines how the application reads the configuration and whether live updates are reflected without a Pod restart.

**Mechanism 1: Environment variables**

```yaml
# Option A: inject specific keys as named env vars
spec:
  containers:
    - name: nestjs-api
      image: nestjs-api:sha256-abc123
      env:
        - name: LOG_LEVEL           # env var name in the container
          valueFrom:
            configMapKeyRef:
              name: nestjs-api-config   # ConfigMap name
              key: LOG_LEVEL            # key within the ConfigMap
              optional: false           # fail Pod startup if key missing
        - name: NODE_ENV
          valueFrom:
            configMapKeyRef:
              name: nestjs-api-config
              key: NODE_ENV

# Option B: inject ALL keys from a ConfigMap as env vars (envFrom)
spec:
  containers:
    - name: nestjs-api
      envFrom:
        - configMapRef:
            name: nestjs-api-config
            optional: false
        # All keys in nestjs-api-config become env vars with the same names:
        # LOG_LEVEL=warn, PORT=3000, NODE_ENV=production

        # Multiple ConfigMaps: later values win on key collision
        - configMapRef:
            name: nestjs-api-overrides   # overrides specific keys

      # You can combine envFrom with explicit env (explicit wins on collision):
      env:
        - name: LOG_LEVEL
          value: "debug"    # overrides LOG_LEVEL from configMapRef above
```

**Environment variable trade-offs:**

```
Advantages:
  Simple: process.env.LOG_LEVEL works without any file-reading code.
  Universal: every language and framework reads environment variables.
  Familiar: same pattern as .env files; easy migration from non-Kubernetes setups.

Critical limitation — NO live updates:
  Environment variables are set when the container starts.
  If the ConfigMap is updated, running containers DO NOT see the change.
  The Pod must be restarted to pick up the new values.
  kubectl rollout restart deployment/nestjs-api

  This is a fundamental property of Unix processes: a child process
  inherits its parent's environment at fork time. Environment variables
  are not references to external state — they are copied values.

Other limitations:
  Key name constraints: env var names must match [A-Za-z_][A-Za-z0-9_]*
  A ConfigMap key named "app.config" cannot be an env var name (dot is invalid).
  Use envFrom only with ConfigMaps whose keys are valid env var names.

  No structure: multi-line file content (app.yaml) becomes a single
  env var with embedded newlines — not useful for file-format config.
  Use volume mounts for file-format configuration.
```

**Mechanism 2: Volume mounts**

```yaml
spec:
  volumes:
    - name: app-config-vol
      configMap:
        name: nestjs-api-config
        # Optional: mount only specific keys as specific filenames
        items:
          - key: app.yaml         # ConfigMap key
            path: application.yaml  # filename inside the mounted directory
          - key: .env.defaults
            path: .env.defaults
        # defaultMode: 0444 — read-only for all users (default: 0644)
        defaultMode: 0444

    - name: full-config-vol
      configMap:
        name: nestjs-api-config
        # Without items: ALL keys become files named after the key
        # LOG_LEVEL → /config/LOG_LEVEL (file containing "warn")
        # app.yaml  → /config/app.yaml (file containing YAML content)

  containers:
    - name: nestjs-api
      image: nestjs-api:sha256-abc123
      volumeMounts:
        - name: app-config-vol
          mountPath: /app/config    # directory where files appear
          readOnly: true            # strong recommendation: always readOnly

        # Mount a single key to a specific file path (subPath)
        - name: full-config-vol
          mountPath: /app/.env.defaults
          subPath: .env.defaults    # mount only this key, not the whole directory
          readOnly: true
```

**Volume mount trade-offs:**

```
Advantages:
  Live updates (with caveats):
    When a ConfigMap is updated, Kubernetes propagates the new content
    to the mounted volume within the kubelet sync period (default: 60 seconds).
    The file on disk is updated; the application can detect the change
    with a filesystem watcher (fs.watch, inotify) and reload config.

    NestJS hot config reload example:
      import * as fs from 'fs';
      const configPath = '/app/config/application.yaml';

      fs.watch(configPath, () => {
        const newConfig = yaml.parse(fs.readFileSync(configPath, 'utf8'));
        configService.update(newConfig);
        logger.log('Config reloaded from disk');
      });

  Supports file-format config:
    nginx.conf, prometheus.yml, application.yaml — complex multi-line
    config that cannot live in an environment variable.

  No naming constraints:
    ConfigMap keys with dots (app.config, nginx.conf) are valid filenames.

Live update caveats:
  subPath mounts do NOT receive live updates.
    If you mount a specific file with subPath, the file is NOT updated
    when the ConfigMap changes. The file is a copy made at Pod startup.
    Use directory mounts (without subPath) for live updates.
    This is a common gotcha — many teams discover it when wondering why
    their "live" config reload is not working.

  Application must support config reload:
    Most applications do not watch config files by default.
    A live-updated file on disk does nothing if the application has
    already read and cached its configuration at startup.
    You must implement the reload logic, or use a sidecar (config-reloader).

  ~60 second propagation delay:
    The kubelet syncs ConfigMap changes to mounted volumes on its sync period.
    Default: 60 seconds. Configurable via kubelet --sync-frequency.
    Applications must tolerate stale config for up to ~60 seconds after an update.
```

**Q4. How do immutable ConfigMaps work, and when should you use them?**
A: Setting `immutable: true` on a ConfigMap permanently prevents any changes to its `data` or `binaryData` fields. The object can only be deleted and recreated. Kubernetes stops watching immutable ConfigMaps for changes, which reduces apiserver load at scale.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nestjs-api-config-v3   # version in the name — key pattern for immutable
  namespace: production
immutable: true                 # cannot be changed after creation
data:
  LOG_LEVEL: "warn"
  NODE_ENV: "production"
```

**Why immutable ConfigMaps improve reliability:**

```
Problem with mutable ConfigMaps:
  A ConfigMap update propagates to all Pods using it within ~60 seconds.
  If a bad config value is pushed (LOG_LEVEL=invalid, PORT=abc):
    All running Pods receive the bad config.
    If the application reloads config from the filesystem: all Pods break.
    No rollback mechanism on the ConfigMap itself — you must push another update.

  In large clusters (1000+ Pods using the same ConfigMap):
    The kubelet on every node watches the ConfigMap for changes.
    High-frequency ConfigMap updates generate significant apiserver load.
    Each change: apiserver notifies all kubelets → all kubelets update files.

Immutable ConfigMap pattern (versioned names):
  nestjs-api-config-v1  → immutable (in use by deployment v1)
  nestjs-api-config-v2  → immutable (in use by deployment v2)
  nestjs-api-config-v3  → immutable (in use by deployment v3, current)

  To "update" config:
    Create nestjs-api-config-v4 with new values (immutable: true).
    Update Deployment to reference nestjs-api-config-v4.
    kubectl apply → rolling update replaces Pods (they start with v4 config).
    v3 ConfigMap remains; can be referenced by any rollback deployment revision.

  Rollback:
    kubectl rollout undo deployment/nestjs-api
    → Reverts to previous ReplicaSet which references nestjs-api-config-v3.
    → Rolled-back Pods start with v3 config.
    Config and code rollback are atomic.

  Cleanup:
    kubectl delete configmap nestjs-api-config-v1 nestjs-api-config-v2
    when those deployment revisions are pruned.

  Apiserver load:
    Immutable ConfigMaps: kubelet does not watch them. Zero per-change fanout.
    At 1000 Pods: mutable ConfigMap update → 1000 kubelet notifications.
                  Immutable: 0 notifications (no change is possible).

When to use immutable vs mutable:
  Immutable (versioned name):
    Production environments where config changes trigger a deployment.
    Large clusters (100+ Pods using the same ConfigMap).
    Config that should be atomically tied to code version.
    Compliance environments requiring audit history per config version.

  Mutable (live updates):
    Feature flags that need to update without a deployment.
    Operational toggles (log level adjustment during an incident).
    Config that must update faster than a rolling deployment allows.
    Development environments where iteration speed matters more than safety.
```

## Section 3: Secrets — Structure, Types, and the Security Gap

**Q5. What is a Kubernetes Secret, how does it differ from a ConfigMap, and what is the critical security limitation you must know?**
A: A Kubernetes Secret is an API object that holds sensitive data — passwords, tokens, certificates, keys. It has the same key-value structure as a ConfigMap but is handled differently by Kubernetes: Secrets are base64-encoded in the API (not encrypted by default), can be restricted by RBAC independently from ConfigMaps, and are only sent to nodes that have Pods requesting them.

**Secret structure:**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: nestjs-api-secrets
  namespace: production
  annotations:
    # For externally managed secrets (External Secrets Operator):
    reloader.stakater.com/match: "true"   # trigger Pod restart on Secret change
type: Opaque    # generic secret (most common); other types below

# data: values must be base64-encoded
data:
  DATABASE_PASSWORD: cHJvZF9wYXNzd29yZF8xMjM=   # base64("prod_password_123")
  STRIPE_SECRET_KEY: c2tfbGl2ZV9hYmMxMjM=        # base64("sk_live_abc123")
  JWT_SECRET: bXlfc3VwZXJfc2VjcmV0X2p3dF9rZXk=  # base64("my_super_secret_jwt_key")

# stringData: plaintext convenience field; Kubernetes base64-encodes on write
# Use stringData in manifests (readable); data in API responses (base64)
stringData:
  REDIS_URL: "redis://:password@redis.internal:6379/0"
  # On apply: Kubernetes base64-encodes this and stores it in data.REDIS_URL
  # stringData is write-only; kubectl get secret shows base64 in data, not stringData
```

**Secret types:**

```
Opaque (type: Opaque)
  Generic; no structural validation. Use for: application secrets,
  API keys, passwords, connection strings, JWT keys.

kubernetes.io/service-account-token
  Automatically created for ServiceAccounts.
  Contains: token, ca.crt, namespace.
  Mounted automatically into Pods at /var/run/secrets/kubernetes.io/serviceaccount/

kubernetes.io/dockerconfigjson
  Registry pull credentials. Used by imagePullSecrets in Pod spec.
  kubectl create secret docker-registry ecr-pull \
    --docker-server=123456789012.dkr.ecr.ap-south-1.amazonaws.com \
    --docker-username=AWS \
    --docker-password=$(aws ecr get-login-password)

kubernetes.io/tls
  TLS certificate and private key.
  Keys: tls.crt (certificate), tls.key (private key).
  Used by Ingress controllers for HTTPS termination.
  kubectl create secret tls nestjs-api-tls \
    --cert=path/to/cert.pem \
    --key=path/to/key.pem

kubernetes.io/basic-auth
  username and password fields. Used by some Ingress controllers.

kubernetes.io/ssh-auth
  ssh-privatekey field. Used for SSH-based git pulls.

bootstrap.kubernetes.io/token
  Node bootstrap tokens. Managed by kubeadm; not used directly.
```

**The critical security limitation — base64 is NOT encryption:**

```
A common and dangerous misconception: Secrets are "encrypted" because
the values look like gibberish (base64).

Reality:
  echo "cHJvZF9wYXNzd29yZF8xMjM=" | base64 -d
  → prod_password_123

  base64 is an encoding, not encryption. It is trivially reversible.
  Anyone who can read the Secret object (via kubectl, the API, or etcd)
  sees the plaintext value after decoding.

Where Secrets live in the cluster and who can read them:

  1. etcd (cluster datastore):
     By DEFAULT: Secrets are stored in etcd as base64-encoded plaintext.
     Anyone with etcd access (etcd admin, backup files, etcd snapshots)
     reads all Secrets in plaintext.
     Fix: enable Encryption at Rest (EncryptionConfiguration in kube-apiserver).

  2. kube-apiserver:
     Every kubectl get secret / API call returns the Secret in base64.
     Fix: RBAC — restrict who can get/list/watch Secrets (see Q10).

  3. Nodes (kubelet):
     Secrets are sent to a node only when a Pod on that node needs them.
     On the node: stored in a tmpfs (in-memory) volume; not written to disk.
     But: node root access → read the tmpfs → read all Secrets on that node.
     Fix: node isolation (don't mix sensitive and untrusted workloads on same node).

  4. Pod environment / filesystem:
     Environment variable: visible in /proc/<pid>/environ for any process
     with ptrace access (same Pod). Also visible in `kubectl describe pod`.
     Volume mount: tmpfs; visible to any process in the Pod with read access.

  The Kubernetes Secret is a better option than a ConfigMap for sensitive data
  (RBAC can distinguish them; they're sent to nodes on-demand; tmpfs storage)
  but a Kubernetes Secret alone is NOT a secure secret management solution
  for production. Use External Secrets Operator + AWS Secrets Manager / Vault.
```

**Q6. How are Secrets injected into Pods, and which injection method is more secure?**
A: Secrets use the same two injection mechanisms as ConfigMaps — environment variables and volume mounts — but the security properties differ in ways that matter for production.

**Injection via environment variables:**

```yaml
spec:
  containers:
    - name: nestjs-api
      env:
        - name: DATABASE_PASSWORD
          valueFrom:
            secretKeyRef:
              name: nestjs-api-secrets
              key: DATABASE_PASSWORD
              optional: false

      envFrom:
        - secretRef:
            name: nestjs-api-secrets   # all keys become env vars
```

**Injection via volume mount (more secure for most cases):**

```yaml
spec:
  volumes:
    - name: secrets-vol
      secret:
        secretName: nestjs-api-secrets
        defaultMode: 0400    # owner read-only; no group/other access
        items:
          - key: DATABASE_PASSWORD
            path: db-password    # file: /secrets/db-password
          - key: STRIPE_SECRET_KEY
            path: stripe-key     # file: /secrets/stripe-key

  containers:
    - name: nestjs-api
      volumeMounts:
        - name: secrets-vol
          mountPath: /secrets
          readOnly: true

  # Application reads the secret:
  # const dbPassword = fs.readFileSync('/secrets/db-password', 'utf8').trim();
```

**Security comparison — env vars vs volume mounts:**

```
Environment variables — risks:
  1. Visible in process listings:
     cat /proc/$(pgrep node)/environ | tr '\0' '\n' | grep PASSWORD
     → DATABASE_PASSWORD=prod_password_123
     Any process in the same Pod with /proc access sees all env vars.

  2. Visible in kubectl describe:
     kubectl describe pod nestjs-api-xyz  (requires get pod permission, not get secret)
     → Environment:
          DATABASE_PASSWORD: <set to the key 'DATABASE_PASSWORD' in secret 'nestjs-api-secrets'>
     The value itself is not shown, but the reference is — and some logging
     and error reporting tools accidentally dump the full environment.

  3. Child process inheritance:
     All child processes spawned by node (child_process.spawn, exec) inherit
     the parent environment. A compromised child process has access to all secrets.

  4. Logging accidents:
     console.log(process.env) — a single debug line leaks every secret to logs.
     Structured loggers that serialize context objects may log process.env
     if it's passed to a logger as context.

  5. Crash dump exposure:
     Some APM tools capture environment variables in crash reports.
     The crash report (sent to a third-party service) contains all secrets.

Volume mounts — advantages:
  1. Not in /proc/environ: file-based secrets are not environment variables.
     Scanning /proc/<pid>/environ does not reveal them.

  2. Automatic rotation pickup (with caveats):
     When the Secret is updated, the mounted file updates within ~60 seconds
     (same kubelet sync behavior as ConfigMaps; same subPath caveat applies).
     The application can detect the file change and reload without restart.

  3. File permissions (defaultMode: 0400):
     Only the owning process can read the file.
     Other processes in the Pod (different UID) cannot read it.
     chmod is enforced by the kernel, not by Kubernetes.

  4. Scoped access:
     RBAC on the Secret object controls who can create/update the Secret.
     The mounted file is read by the application process only.
     A side process (logging agent, monitoring sidecar) with a different UID
     cannot read the secret file if defaultMode is 0400 and it runs as a
     different user.

Volume mount — limitations:
  Code must read from a file, not from process.env.
  Adds boilerplate: fs.readFileSync vs process.env.SECRET.
  Some third-party libraries only read from environment variables —
  you must set env vars from the file in the entrypoint script:
    export DATABASE_PASSWORD=$(cat /secrets/db-password)
  This reintroduces the env var exposure, negating some of the benefit.

Recommendation:
  Use volume mounts for secrets that can be read from files
  (database passwords, API keys that the application reads explicitly).
  Use environment variables for secrets required by libraries that only
  read from process.env and cannot be changed.
  Never use envFrom for secrets in production — it injects ALL secrets
  into the environment, including any that are not needed by the container.
  Principle of least privilege: inject only the specific secrets each
  container needs, via secretKeyRef or specific volume mount items.
```

## Section 4: Encryption at Rest and the External Secrets Pattern

**Q7. What is Encryption at Rest for Secrets, and how do you configure it?**
A: By default, Kubernetes stores Secrets in etcd as base64-encoded plaintext. Encryption at Rest adds an encryption layer between the kube-apiserver and etcd, so the data written to etcd disk is ciphertext. Without it, anyone with access to etcd data (backups, snapshots, etcd node filesystem) can read all Secrets.

**EncryptionConfiguration — how it works:**

```yaml
# /etc/kubernetes/encryption-config.yaml (on kube-apiserver nodes)
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets          # encrypt the Secrets resource type
      - configmaps       # optionally encrypt ConfigMaps too
    providers:
      # Providers are tried in order for decryption.
      # The FIRST provider is used for encryption.

      # Option 1: AWS KMS (recommended for EKS)
      - kms:
          apiVersion: v2
          name: aws-kms-provider
          endpoint: unix:///var/run/kmsplugin/socket.sock
          # A DaemonSet runs the KMS plugin on each control plane node.
          # The plugin calls AWS KMS GenerateDataKey to encrypt each Secret.
          # Data keys are cached; not every Secret write calls KMS.
          cachesize: 1000
          timeout: 3s

      # Option 2: AES-CBC with a static key (simpler; less secure)
      # - aescbc:
      #     keys:
      #       - name: key1
      #         secret: <base64-encoded-32-byte-key>

      # Option 3: identity (no encryption — plaintext)
      # Always include as the LAST provider for reading unencrypted data
      # that existed before encryption was enabled.
      - identity: {}

# kube-apiserver flag to load this config:
# --encryption-provider-config=/etc/kubernetes/encryption-config.yaml
```

**EKS (managed Kubernetes) — enabling envelope encryption:**

```bash
# EKS uses AWS KMS for envelope encryption of Secrets.
# Enable at cluster creation:
aws eks create-cluster \
  --name prod-cluster \
  --encryption-config '[{
    "resources": ["secrets"],
    "provider": {
      "keyArn": "arn:aws:kms:ap-south-1:123456789012:key/mrk-abc123"
    }
  }]'

# Enable on existing cluster:
aws eks associate-encryption-config \
  --cluster-name prod-cluster \
  --encryption-config '[{
    "resources": ["secrets"],
    "provider": {
      "keyArn": "arn:aws:kms:ap-south-1:123456789012:key/mrk-abc123"
    }
  }]'
# This re-encrypts all existing Secrets with the KMS key.
# After this, every Secret write → kube-apiserver → KMS GenerateDataKey →
# Secret encrypted with data key → data key encrypted with CMK → stored in etcd.
# etcd contains only ciphertext. KMS key deletion = all Secrets permanently unreadable.

# Verify encryption:
# Read a Secret directly from etcd (not via kubectl, which decrypts):
ETCDCTL_API=3 etcdctl get /registry/secrets/default/my-secret \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/healthcheck-client.crt \
  --key=/etc/kubernetes/pki/etcd/healthcheck-client.key \
  | hexdump -C | head
# Output should start with: k8s:enc:kms:v2:  (encrypted)
# Not encrypted output starts with: k8s\n\n\nv1Secret  (plaintext)
```

**What Encryption at Rest does and does not protect:**

```
Does protect:
  etcd data files on disk (if etcd node is compromised or disk is stolen).
  etcd backups and snapshots stored in S3/object storage.
  etcd WAL (write-ahead log) entries.

Does NOT protect:
  Secrets in transit between kube-apiserver and etcd (protect with etcd TLS).
  Secrets returned by the kube-apiserver to kubectl / controllers / Pods
    (the apiserver decrypts before returning; RBAC controls access here).
  Secrets mounted into Pod filesystems (readable by the container process).
  Secrets in environment variables (readable via /proc).
  Secrets in kube-apiserver memory (in-process decryption buffer).
  Audit logs that may record Secret values in request/response bodies.

Encryption at Rest is one control in a defense-in-depth strategy.
It is NOT a substitute for RBAC, external secret management, or
network policies. It is a mandatory baseline for compliance
(PCI-DSS, SOC 2, RBI IT framework) but insufficient on its own.
```

**Q8. What is the External Secrets Operator pattern, and why is it the production standard for secret management?**
A: The External Secrets Operator (ESO) is a Kubernetes controller that reads secrets from external secret stores (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager, Azure Key Vault) and automatically creates and keeps Kubernetes Secret objects synchronized. It decouples secret storage from Kubernetes entirely — the source of truth lives in a purpose-built secret manager, not in etcd.

**The problem with native Kubernetes Secrets at scale:**

```
Problem 1: Secrets in git (the original sin)
  To apply a Secret to a cluster, someone must kubectl apply -f secret.yaml.
  If that YAML is in git (even a private repo), the secret is version-controlled.
  Git history is permanent. A secret committed and "deleted" is still in git log.
  Secret scanning tools (trufflehog, gitleaks) find these — so do attackers.

Problem 2: Secret rotation requires manual Kubernetes updates
  AWS RDS rotates the database password automatically.
  The new password is in AWS Secrets Manager.
  But the Kubernetes Secret object still has the old password.
  You must manually update the Kubernetes Secret, then restart the Pods.
  During the window between rotation and update: the application fails to
  authenticate to the database.

Problem 3: No audit trail for Secret values
  kubectl get secret nestjs-api-secrets -o yaml → displays all values (base64).
  kubectl does not log this access at the application level.
  Kubernetes audit logs record the API call, but not the plaintext value read.
  AWS Secrets Manager / Vault record every read with: who, when, from where.

Problem 4: Cross-cluster secret consistency
  Multiple clusters (dev, staging, prod, DR) need the same or similar secrets.
  Maintaining Kubernetes Secrets across clusters is manual, error-prone,
  and creates drift between environments.
```

**External Secrets Operator architecture:**

```
AWS Secrets Manager          Kubernetes Cluster
─────────────────            ──────────────────────────────────────
prod/nestjs-api/db      ←── SecretStore (ClusterSecretStore)
  password: "abc123"         │ IAM Role: ExternalSecretsRole
  username: "api_user"       │ (IRSA annotation on ESO ServiceAccount)
                             │
prod/nestjs-api/stripe  ←── ExternalSecret
  key: "sk_live_xyz"         │ refreshInterval: 1h
                             │ target.name: nestjs-api-secrets
                             ↓
                         Kubernetes Secret
                         nestjs-api-secrets:
                           DATABASE_PASSWORD: abc123
                           DATABASE_USERNAME: api_user
                           STRIPE_SECRET_KEY: sk_live_xyz
                             ↓
                         Pod
                         (reads Secret as normal — env var or volume)
```

**ESO manifest setup:**

```yaml
# 1. ClusterSecretStore: connection to AWS Secrets Manager
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: ap-south-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
            namespace: external-secrets
          # external-secrets-sa has IRSA annotation:
          # eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/ExternalSecretsRole
          # ExternalSecretsRole has: secretsmanager:GetSecretValue on prod/nestjs-api/*

---
# 2. ExternalSecret: maps AWS Secrets Manager secret → Kubernetes Secret
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: nestjs-api-secrets
  namespace: production
spec:
  refreshInterval: 1h          # ESO re-reads from Secrets Manager every hour
                               # Set lower (5m) for secrets that rotate frequently

  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore

  target:
    name: nestjs-api-secrets   # Kubernetes Secret to create/update
    creationPolicy: Owner      # ESO owns the Secret; deletes it if ExternalSecret deleted
    deletionPolicy: Retain     # Retain the Secret if ExternalSecret deleted (safer)

    # Optional: transform the secret data
    template:
      engineVersion: v2
      data:
        # Compose a connection string from multiple secret fields
        DATABASE_URL: "postgresql://{{ .username }}:{{ .password }}@prod-rds.internal:5432/payments"
        REDIS_URL:    "redis://:{{ .redis_password }}@redis.internal:6379/0"

  data:
    # Map individual fields from Secrets Manager JSON to Kubernetes Secret keys
    - secretKey: DATABASE_PASSWORD    # key in Kubernetes Secret
      remoteRef:
        key: prod/nestjs-api/db       # Secrets Manager secret name
        property: password            # JSON field within the secret value
                                      # Secrets Manager value: {"username":"api_user","password":"abc123"}

    - secretKey: DATABASE_USERNAME
      remoteRef:
        key: prod/nestjs-api/db
        property: username

    - secretKey: STRIPE_SECRET_KEY
      remoteRef:
        key: prod/nestjs-api/stripe
        property: key

  # Or: copy an entire Secrets Manager secret (all JSON fields) as-is
  dataFrom:
    - extract:
        key: prod/nestjs-api/app-secrets
        # All JSON fields in app-secrets become keys in the Kubernetes Secret
```

**Automatic secret rotation flow with ESO:**

```
T+0:   AWS RDS rotates database password (Lambda rotation function).
       New password stored in Secrets Manager: prod/nestjs-api/db.password = "new_pass"

T+5m:  ESO refreshInterval triggers (if set to 5m).
       ESO calls secretsmanager:GetSecretValue for prod/nestjs-api/db.
       ESO updates Kubernetes Secret: nestjs-api-secrets.DATABASE_PASSWORD = "new_pass"

T+5m+60s: kubelet detects Secret update (if volume-mounted).
           Mounted file /secrets/db-password updated to "new_pass".
           Application's fs.watch fires → reads new password → reconnects to DB.
           Zero-downtime rotation. No Pod restart required.

If env var injection is used instead of volume mount:
  The env var is NOT updated automatically. Pod restart required.
  The Stakater Reloader controller watches for Secret updates and
  automatically triggers rolling restarts of Deployments that reference
  the updated Secret:
    Deployment annotation: reloader.stakater.com/auto: "true"
    → When nestjs-api-secrets changes, Reloader restarts the Deployment.

Full rotation timeline with env vars + Reloader:
  T+0:    Rotation in Secrets Manager.
  T+5m:   ESO syncs Kubernetes Secret.
  T+5m+x: Reloader detects Secret change → starts rolling restart.
  T+5m+x+boot: New Pods start with new password in env var.
  Total: ~6–10 minutes from rotation to fully updated fleet.
  During rolling restart: old Pods still use old password (still valid during
  rotation window); new Pods use new password. Zero downtime.
```

## Section 5: RBAC for ConfigMaps and Secrets

**Q9. How do you restrict access to Secrets with RBAC, and what are the common misconfigurations?**
A: Kubernetes RBAC controls which principals (users, ServiceAccounts) can perform which verbs (get, list, watch, create, update, delete) on which resources (secrets, configmaps) in which namespaces. Secrets require stricter RBAC than ConfigMaps because a single misconfigured binding can expose every Secret in a namespace.

**The `list` and `watch` verbs are as dangerous as `get`:**

```
Common misconception: "read access" to Secrets means only get.

Reality:
  get:   read a specific Secret by name → returns the Secret value.
  list:  list all Secrets in a namespace → returns ALL Secrets with ALL values.
  watch: stream all Secret changes → receives every Secret create/update/delete
         including full Secret content.

  A principal with secrets/list can dump every Secret in the namespace
  with a single API call:
    kubectl get secrets -n production -o yaml
    → returns ALL Secrets with base64-encoded values.

  A principal with secrets/watch can set up a long-lived stream and receive
  every Secret update as it happens.

The principle for Secret RBAC:
  Default: no access to Secrets for any ServiceAccount.
  Grant get only for the specific Secret name(s) a ServiceAccount needs.
  Never grant list or watch on secrets to application ServiceAccounts.
  Audit: any ClusterRoleBinding granting secrets/* is a critical finding.
```

**Minimal RBAC for an application ServiceAccount:**

```yaml
# ServiceAccount for the NestJS API
apiVersion: v1
kind: ServiceAccount
metadata:
  name: nestjs-api-sa
  namespace: production
  annotations:
    # IRSA: allows this ServiceAccount to assume the AWS IAM role
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/NestjsApiRole

---
# Role: minimal permissions for the application
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: nestjs-api-role
  namespace: production
rules:
  # The application reads its own ConfigMap (optional; usually env vars are sufficient)
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["nestjs-api-config"]   # specific ConfigMap only
    verbs: ["get"]                          # read only; no list/watch/update

  # If the application manages its own lease (leader election):
  - apiGroups: ["coordination.k8s.io"]
    resources: ["leases"]
    resourceNames: ["nestjs-api-leader"]
    verbs: ["get", "create", "update"]

  # NOT included (application does not need these):
  # secrets: get/list/watch → secrets injected via volume mount or env var
  # pods: list/watch → not needed by the application
  # deployments: * → never for application ServiceAccounts

---
# RoleBinding: bind the Role to the ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: nestjs-api-rolebinding
  namespace: production
subjects:
  - kind: ServiceAccount
    name: nestjs-api-sa
    namespace: production
roleRef:
  kind: Role
  apiGroup: rbac.authorization.k8s.io
  name: nestjs-api-role
```

**RBAC for the External Secrets Operator ServiceAccount:**

```yaml
# ESO needs to create/update/delete the Kubernetes Secrets it manages.
# This is a privileged ServiceAccount — restrict to the ESO namespace only.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: external-secrets-role
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
    # ESO needs full CRUD on secrets in the namespaces it manages.
    # Without resourceNames restriction — it can access ALL secrets.
    # This is the required privilege for ESO to function.
    # Mitigate with: ESO runs in its own namespace; namespace isolation limits blast radius.

  - apiGroups: [""]
    resources: ["events"]
    verbs: ["create", "patch"]
```

**Common RBAC misconfigurations for Secrets:**

```
Misconfiguration 1: Wildcard on secrets at cluster level
  rules:
  - apiGroups: ["*"]
    resources: ["secrets"]
    verbs: ["*"]
  This grants full Secret access across all namespaces.
  Any compromised Pod with this ServiceAccount reads every Secret in the cluster.

Misconfiguration 2: ClusterRole with secrets/list bound to a developer group
  A developer with kubectl get secrets -n production -o yaml reads
  the Stripe secret key, the database password, and the JWT signing key.
  Fix: developers should use kubectl exec + application logs for debugging,
       not direct Secret access. Secrets should only be accessible to:
         - ESO ServiceAccount (to create/update)
         - Specific application ServiceAccounts (via projected volume; no RBAC needed)
         - Break-glass admin role (MFA-gated; audited)

Misconfiguration 3: secrets/watch in a long-running controller
  A custom controller with secrets/watch establishes a persistent stream.
  If the controller is compromised, the attacker has a real-time feed
  of every Secret in the namespace, including rotated values as they arrive.
  Fix: controllers that need Secret data should get specific secrets by name.
       Watch is rarely needed for application controllers.

Misconfiguration 4: Default ServiceAccount has Secret access
  By default, every Pod in a namespace uses the default ServiceAccount.
  If the default ServiceAccount has been granted secrets/get:
    Every Pod in the namespace — including untrusted third-party workloads —
    can read Secrets.
  Fix: never grant permissions to the default ServiceAccount.
       Always create named ServiceAccounts for each application.
       Set automountServiceAccountToken: false on the default ServiceAccount
       and on any ServiceAccount that does not need to call the Kubernetes API:

  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: nestjs-api-sa
    namespace: production
  automountServiceAccountToken: false
  # The Pod will not have /var/run/secrets/kubernetes.io/serviceaccount/ mounted.
  # If the application does not call the Kubernetes API, this is always correct.
```

## Section 6: Operational Patterns and Advanced Topics

**Q10. How do you trigger Pod restarts when a ConfigMap or Secret changes?**
A: Kubernetes does not automatically restart Pods when a referenced ConfigMap or Secret changes — not even when the change is critical. You must implement a restart mechanism explicitly. Three patterns exist, with different trade-offs.

**Pattern 1: Checksum annotation (simplest; GitOps-compatible)**

```yaml
# In the Deployment spec, add an annotation with a hash of the ConfigMap content.
# When the ConfigMap changes, the hash changes → Deployment spec changes
# → Kubernetes triggers a rolling update automatically.

# Helm template (most common implementation):
spec:
  template:
    metadata:
      annotations:
        # sha256sum of the ConfigMap content; recomputed on every helm upgrade
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
        checksum/secret: {{ include (print $.Template.BasePath "/secret.yaml") . | sha256sum }}

# Raw kubectl (manual):
CONFIG_HASH=$(kubectl get configmap nestjs-api-config -o yaml | sha256sum | cut -d' ' -f1)
kubectl patch deployment nestjs-api \
  -p "{\"spec\":{\"template\":{\"metadata\":{\"annotations\":{\"config-hash\":\"$CONFIG_HASH\"}}}}}"
# Patching the annotation changes the Pod template → rolling restart begins.

# Advantage:  no additional controller needed; works with any Kubernetes cluster.
# Disadvantage: the restart is tied to the Deployment update, not the live
#               ConfigMap value. Requires a deployment pipeline step to recompute.
```

**Pattern 2: Stakater Reloader (recommended for production)**

```yaml
# Install Reloader:
helm install reloader stakater/reloader -n reloader --create-namespace

# Annotate the Deployment:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api
  annotations:
    # Watch specific ConfigMaps and Secrets; restart on change:
    configmap.reloader.stakater.com/reload: "nestjs-api-config"
    secret.reloader.stakater.com/reload: "nestjs-api-secrets"
    # Or: watch ALL ConfigMaps and Secrets referenced by the Deployment:
    reloader.stakater.com/auto: "true"

# How it works:
# Reloader runs as a Deployment in the cluster.
# It watches all ConfigMaps and Secrets for changes (using the Kubernetes watch API).
# When a watched resource changes, Reloader patches the Deployment's Pod template
# annotation (adds/updates a timestamp annotation).
# The patch triggers Kubernetes' normal rolling update mechanism.
# No custom restart logic in the application required.

# Advantage: automatic; no pipeline changes needed; works with ESO rotation.
# Disadvantage: Reloader must be trusted with secrets/watch cluster-wide.
#               Evaluate its RBAC footprint before installing in security-sensitive clusters.
```

**Pattern 3: Application-level config reload (no restart needed)**

```typescript
// NestJS: watch the mounted config file and reload without restart
// Only viable when using volume mounts (not env vars)

import * as fs from 'fs';
import * as yaml from 'js-yaml';
import { Injectable, OnModuleInit, Logger } from '@nestjs/common';

@Injectable()
export class DynamicConfigService implements OnModuleInit {
  private readonly logger = new Logger(DynamicConfigService.name);
  private config: Record<string, unknown> = {};
  private readonly configPath = '/app/config/application.yaml';

  onModuleInit() {
    this.loadConfig();
    this.watchConfig();
  }

  private loadConfig() {
    try {
      const content = fs.readFileSync(this.configPath, 'utf8');
      this.config = yaml.load(content) as Record<string, unknown>;
      this.logger.log('Config loaded successfully');
    } catch (err) {
      this.logger.error('Failed to load config', err);
    }
  }

  private watchConfig() {
    // Kubernetes updates the symlink target, not the file itself.
    // Watch the directory, not the file — inotify catches symlink swaps.
    const configDir = '/app/config';
    fs.watch(configDir, (event, filename) => {
      if (filename === 'application.yaml' && event === 'rename') {
        // 'rename' fires when Kubernetes atomically swaps the symlink
        // Small delay to let the new symlink settle
        setTimeout(() => {
          this.logger.log('Config file changed; reloading...');
          this.loadConfig();
        }, 100);
      }
    });
  }

  get<T>(key: string): T {
    return this.config[key] as T;
  }
}

// Why watch for 'rename' not 'change':
// Kubernetes updates mounted ConfigMap files atomically via symlink swap.
// The directory contains: application.yaml -> ..data/application.yaml
//                         ..data -> ..2026_08_07_09_00_00.000000000
// On update: a new timestamped directory is created, ..data symlink is
// atomically swapped to point to it. This appears as a 'rename' event
// on the symlink, not a 'change' event on the file content.
// Watching the file directly with fs.watch misses the update on some platforms.
```

**Q11. What is the projected volume pattern, and how does it combine multiple sources?**
A: A Projected Volume combines multiple volume sources (Secrets, ConfigMaps, ServiceAccount tokens, the downward API) into a single directory. It reduces the number of volume mounts required and enables atomic presentation of related configuration and secrets.

```yaml
spec:
  volumes:
    - name: app-config
      projected:
        defaultMode: 0440    # applies to all sources unless overridden
        sources:
          # Source 1: ConfigMap
          - configMap:
              name: nestjs-api-config
              items:
                - key: app.yaml
                  path: app.yaml     # appears as /config/app.yaml

          # Source 2: Secret
          - secret:
              name: nestjs-api-secrets
              items:
                - key: DATABASE_PASSWORD
                  path: secrets/db-password    # /config/secrets/db-password
                  mode: 0400                   # stricter: only owner reads
                - key: STRIPE_SECRET_KEY
                  path: secrets/stripe-key
                  mode: 0400

          # Source 3: ServiceAccount token (short-lived; auto-rotated)
          - serviceAccountToken:
              path: token             # /config/token
              expirationSeconds: 3600 # 1-hour token; kubelet rotates before expiry
              audience: "https://kubernetes.default.svc"

          # Source 4: Downward API (Pod metadata as files)
          - downwardAPI:
              items:
                - path: pod-name
                  fieldRef:
                    fieldPath: metadata.name     # /config/pod-name
                - path: pod-namespace
                  fieldRef:
                    fieldPath: metadata.namespace
                - path: node-name
                  fieldRef:
                    fieldPath: spec.nodeName
                - path: cpu-limit
                  resourceFieldRef:
                    containerName: nestjs-api
                    resource: limits.cpu
                    divisor: "1m"

  containers:
    - name: nestjs-api
      volumeMounts:
        - name: app-config
          mountPath: /config
          readOnly: true
      # All four sources are available under /config/:
      # /config/app.yaml
      # /config/secrets/db-password
      # /config/secrets/stripe-key
      # /config/token
      # /config/pod-name
      # /config/pod-namespace
```

**Downward API — useful configuration from Pod metadata:**

```
The Downward API exposes Pod and container metadata to the running container
without querying the Kubernetes API. Available via:
  - Environment variables (fieldRef, resourceFieldRef in env)
  - Projected volume files (as above)

Common uses:
  Pod name → include in log records for tracing (which Pod logged this?)
  Namespace → multi-tenant apps that need to know their own namespace
  Node name → locality-aware routing (prefer requests to same-node services)
  Pod IP → register with a service mesh or service discovery system
  CPU/memory limits → Node.js --max-old-space-size should be set relative
                      to container memory limit, not the node's total RAM:

  env:
    - name: NODE_OPTIONS
      value: "--max-old-space-size=$(MEMORY_LIMIT_MB)"
    - name: MEMORY_LIMIT_MB
      valueFrom:
        resourceFieldRef:
          containerName: nestjs-api
          resource: limits.memory
          divisor: 1Mi    # convert bytes to MiB for Node.js flag
```

**Q12. "A developer reports that updating a ConfigMap did not take effect in the running Pods. Walk through the full diagnostic."**
A:

```
Diagnostic tree:

Step 1: Confirm the ConfigMap was actually updated.
  kubectl get configmap nestjs-api-config -n production -o yaml
  → Check that the new value appears in data.

  If the value is wrong: the update did not apply correctly.
    kubectl apply -f configmap.yaml may have silently failed if the file
    was malformed or the user lacked permission.
    Check: kubectl describe configmap nestjs-api-config — look at events.
    Check: kubectl auth can-i update configmap --as=<user> -n production

Step 2: Determine how the ConfigMap is consumed by the Pod.

  Case A: Environment variable injection (envFrom / env.valueFrom)
    Environment variables are set at container start time. They NEVER
    update in a running container, regardless of ConfigMap changes.
    This is expected behavior, not a bug.
    Fix: restart the Pods.
      kubectl rollout restart deployment/nestjs-api -n production
    Verify: kubectl exec -it <pod> -- env | grep LOG_LEVEL
    After restart, the new value appears.

  Case B: Volume mount (without subPath)
    The ConfigMap should propagate to the mounted file within ~60 seconds
    (kubelet sync period).
    Check how long ago the ConfigMap was updated:
      kubectl get configmap nestjs-api-config -n production \
        -o jsonpath='{.metadata.resourceVersion}'
    Check the file inside the running Pod:
      kubectl exec -it <pod-name> -n production -- cat /app/config/LOG_LEVEL
      → If the old value appears: wait 60 seconds and check again.
      → If the new value appears: the file is updated; the application
        has not reloaded it.
        Does the application watch the file for changes?
        If no: the application read the config at startup and cached it.
          Fix: restart the Pod, or implement config watching.
        If yes: check the fs.watch implementation.
          Common bug: watching the file directly instead of the directory.
          Kubernetes updates via symlink swap → 'rename' event on the directory.
          fs.watch('/app/config/app.yaml') may miss this.
          Fix: fs.watch('/app/config', ...) and filter by filename.

  Case C: Volume mount with subPath
    subPath mounts are a COPY at Pod start time, not a live reference.
    The file is NEVER updated when the ConfigMap changes.
    This is documented Kubernetes behavior, not a bug.
    Fix: remove subPath; mount the entire directory instead.
         Or: restart the Pod after every ConfigMap change (use Reloader).

Step 3: Verify the Pod is actually using the expected ConfigMap.
  kubectl describe pod <pod-name> -n production | grep -A5 "Volumes:"
  → Confirms which ConfigMap and which version is mounted.
  kubectl describe pod <pod-name> -n production | grep -A5 "Environment:"
  → Confirms which Secret/ConfigMap keys are injected as env vars.

  If the Pod references the wrong ConfigMap name: the Deployment spec
  was not updated when the ConfigMap was renamed or versioned.

Step 4: Check if the Pod is in a state where it could receive updates.
  kubectl get pod -n production -l app=nestjs-api
  → All Pods should be Running.
  If any Pod is in Pending or CrashLoopBackOff: the update may not reach it.
  An Evicted Pod will be replaced with a new one that reads the latest ConfigMap.

Step 5: Check kubelet logs on the node (if volume mount still not propagating).
  kubectl get pod <pod-name> -n production -o jsonpath='{.spec.nodeName}'
  → Get the node name.
  On the node (or via node debug):
    journalctl -u kubelet | grep "nestjs-api-config" | tail -20
  Look for: errors syncing configmap, failed to update volume.
  Rare but possible: kubelet cannot reach the apiserver → stale mount.

Root causes summary:
  Env var not updated        → expected; restart Pod
  Volume mount: 60s delay    → expected; wait or reduce kubelet sync period
  Volume mount: subPath      → expected; remove subPath or restart Pod
  App not reloading file     → application bug; implement fs.watch on directory
  Wrong ConfigMap referenced → Deployment misconfiguration; update spec
  ConfigMap not actually updated → kubectl apply failed silently; verify RBAC
```

## Quick Reference

| Feature | ConfigMap | Secret |
|---|---|---|
| Purpose | Non-sensitive config | Sensitive data (passwords, keys) |
| Storage in etcd | Plaintext | Base64 (plaintext unless encryption at rest enabled) |
| RBAC default | Same as other resources | Should be stricter; restrict list/watch |
| Size limit | 1 MiB | 1 MiB |
| Node delivery | Always available to scheduled Pods | Only sent to nodes running Pods that reference them |
| tmpfs storage on node | No | Yes (in-memory; not written to disk) |
| Immutability | `immutable: true` supported | `immutable: true` supported |
| Live update (volume) | ~60s propagation | ~60s propagation (same mechanism) |
| Live update (env var) | Never | Never |
| subPath live update | Never | Never |

| Injection method | Live update? | Secure for secrets? | Use when |
|---|---|---|---|
| `env.valueFrom.configMapKeyRef` | ❌ Never | N/A | Simple key-value config, libraries that only read env |
| `envFrom.configMapRef` | ❌ Never | N/A | Bulk config injection (use carefully; may inject unneeded keys) |
| `env.valueFrom.secretKeyRef` | ❌ Never | ⚠️ Visible in /proc | Libraries that only read env vars |
| `envFrom.secretRef` | ❌ Never | ❌ All secrets exposed | Avoid in production |
| Volume mount (directory) | ✅ ~60s | ✅ tmpfs + 0400 mode | Preferred for secrets; file-format config |
| Volume mount (subPath) | ❌ Never | ✅ | Single file needed; accept no live update |
| Projected volume | ✅ ~60s | ✅ | Multiple sources in one mount |

| Problem | Cause | Fix |
|---|---|---|
| Config change not reflected in running Pod | Env var injection; never live-updates | `kubectl rollout restart deployment/<name>` |
| Volume-mounted config stale for >60s | kubelet sync delay | Wait; or check kubelet connectivity to apiserver |
| subPath mount never updates | Design limitation of subPath | Remove subPath; mount directory; or use Reloader |
| Application doesn't pick up updated file | No file watch implemented | Implement `fs.watch` on directory (not file) with 'rename' event |
| `COPY failed: secret not found` in Dockerfile | Confusion between Docker and Kubernetes | Kubernetes Secrets are not Docker build-time concepts; use ESO + volume mount |
| Secret value visible in `kubectl describe pod` | Env var injection; describe shows key name | Switch to volume mount; describe shows mount path, not value |
| `base64 -d` decodes a Kubernetes Secret | base64 is encoding, not encryption | Enable KMS Encryption at Rest; use External Secrets Operator |
| All Pods get old Secret after rotation | Env var injection; no restart triggered | Use Stakater Reloader or volume mount with fs.watch |
| `list` secrets reveals all values | Over-permissive RBAC | Restrict to `get` on specific resourceNames only |
| Secret committed to git | Storing YAML manifest with stringData in git | Use ESO; never store Secret YAML in git; use Sealed Secrets or SOPS for GitOps |

| Pattern | When to use |
|---|---|
| Mutable ConfigMap + Reloader | Feature flags, operational toggles needing live update without deployment |
| Immutable ConfigMap (versioned name) | Production config tied to code version; atomic rollback; large clusters |
| External Secrets Operator | Always for production secrets; automatic rotation; audit trail |
| Projected volume | Multiple config sources (ConfigMap + Secret + SA token) in one mount |
| Checksum annotation | GitOps/Helm workflows; restart on config change without Reloader |
| `automountServiceAccountToken: false` | Any Pod that does not call the Kubernetes API |
| `defaultMode: 0400` on secret volumes | Prevent other processes in Pod from reading secret files |

## The Core Mental Model

```
ConfigMaps and Secrets are both API objects with the same key-value structure.
The difference is in how Kubernetes handles them: Secrets get node-local tmpfs
storage, independent RBAC, and (optionally) encryption at rest. Neither provides
true secret security by itself — treat them as the Kubernetes plumbing layer,
not the security layer.

The two injection mechanisms have one rule that overrides everything else:
  Environment variables are fixed at container start. They never change.
  Volume-mounted files update in ~60 seconds. subPath breaks this.
  Know which you are using before debugging a "config not updating" incident.
  The answer to "why didn't my config change take effect?" is always one of:
    a) Env var — restart the Pod.
    b) Volume mount, subPath — restart the Pod; or remove subPath.
    c) Volume mount, directory — wait 60 seconds; check fs.watch implementation.
    d) Application doesn't reload — implement watching or restart.

Secrets in Kubernetes are not secret by default:
  base64 is encoding, not encryption.
  Without KMS Encryption at Rest: etcd contains plaintext.
  Without RBAC: any ServiceAccount can list all Secrets in the namespace.
  Without External Secrets: Secrets live in etcd, not in a purpose-built store.
  The minimum production baseline:
    1. KMS Encryption at Rest (EKS: enable envelope encryption).
    2. RBAC: no secrets/list or secrets/watch for application ServiceAccounts.
    3. External Secrets Operator + AWS Secrets Manager (or Vault).
    4. automountServiceAccountToken: false on all application ServiceAccounts.
    5. Trivy/Falco: scan for Secrets in ConfigMaps, log for Secret access patterns.

Immutable + versioned naming is the production ConfigMap pattern:
  nestjs-api-config-v3 (immutable) → Deployment v3
  Config change = create v4 → update Deployment → rolling update
  Rollback = undo Deployment → reverts to v3 ConfigMap reference
  Config and code move together atomically. No accidental live mutation.
  At scale (100+ Pods): immutable ConfigMaps eliminate kubelet watch fanout.

External Secrets Operator is the production secret pattern:
  Source of truth: AWS Secrets Manager (versioned, audited, rotatable).
  Kubernetes Secret: a synchronized copy managed by ESO.
  Application: reads the Kubernetes Secret (env var or volume) — unchanged.
  Rotation: Secrets Manager rotates → ESO syncs → Reloader restarts Pods.
  GitOps: ExternalSecret manifests are in git (safe — they contain no values).
          Kubernetes Secret objects are NOT in git (they contain values).
  The developer never touches the Kubernetes Secret directly.
  RBAC for the Kubernetes Secret is granted only to ESO's ServiceAccount.

The subPath trap is the most common ConfigMap/Secret operational mistake:
  subPath gives you a clean single-file mount.
  subPath breaks live updates permanently.
  You will discover this during an incident when a config change
  "doesn't work" and the deadline is approaching.
  Either accept no live updates and use Reloader, or mount the directory
  and let the application address the specific file within it.
```

**Tip for the interview:** ConfigMap and Secret questions at 5 YOE converge on three areas: (1) the env var vs volume mount distinction and the subPath live-update trap — being able to explain that environment variables are frozen at container start, that volume-mounted files update in ~60 seconds unless subPath is used, and that Kubernetes updates mounted files via atomic symlink swap (which requires watching the directory for 'rename', not the file for 'change') shows you have debugged the "my config change didn't work" incident in a real cluster rather than just reading the docs; (2) the "Secrets are not secret" reality — explaining that base64 is encoding not encryption, walking through the five places a Secret value is exposed (etcd, apiserver, node tmpfs, /proc/environ, kubectl describe), and knowing that the fix is KMS Encryption at Rest plus External Secrets Operator plus RBAC that restricts list/watch on the secrets resource, demonstrates you understand the actual threat model rather than assuming Kubernetes handles security for you; (3) the External Secrets Operator rotation flow — tracing the path from an AWS Secrets Manager rotation event through ESO's refreshInterval sync to Kubernetes Secret update to Stakater Reloader triggering a rolling restart, and knowing that volume-mounted secrets can update without a restart while env-var-injected secrets cannot, shows you have designed a zero-downtime secret rotation architecture for a real production service. The fintech callout: for services handling payment data under PCI-DSS or customer PII under the DPDP Act, the combination of KMS-encrypted etcd, ESO-managed Secrets (never in git), RBAC with no secrets/list permission for application ServiceAccounts, and Falco alerting on unexpected Secret access is the minimum control set that satisfies an external auditor — each layer answers a specific audit question about where secrets are stored, who can read them, and how access is logged.
