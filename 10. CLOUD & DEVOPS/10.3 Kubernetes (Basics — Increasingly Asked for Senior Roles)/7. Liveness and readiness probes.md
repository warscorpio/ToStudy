# Kubernetes Liveness and Readiness Probes — Interview Q&A (5 YOE Level)

---

## Section 1: Why Probes Exist

**Q1. What problem do liveness and readiness probes solve that Kubernetes cannot solve on its own?**
A: Kubernetes can detect that a container's process has exited (exit code non-zero) and restart it. What it cannot detect without probes is a container whose process is running but whose application is broken — a deadlocked Node.js event loop, a goroutine leak, a database connection pool exhausted with no error, or a service that is alive but cannot currently handle traffic. Probes give Kubernetes a mechanism to ask the application directly whether it is healthy.

**The two distinct failure modes probes address:**

```
Failure mode 1 — Process running, application broken (liveness):

  NestJS API: process is running (pid exists, port 3000 is bound)
  Reality: event loop is deadlocked (a synchronous call blocked the loop)
  Kubernetes without liveness probe:
    Container: Running ✅ (from Kubernetes' perspective)
    Requests: all hang indefinitely (no response from the application)
    Resolution: manual operator intervention (kubectl delete pod)

  With liveness probe:
    Probe: GET /health/live → timeout (deadlocked event loop cannot respond)
    After 3 consecutive failures: Kubernetes kills the container → restarts it
    Event loop is fresh → application recovers
    Resolution: automatic, within probe period × failure threshold seconds

Failure mode 2 — Process running, temporarily unable to serve (readiness):

  NestJS API: just started; process is running; port 3000 is bound
  Reality: TypeORM is establishing connection pool; DB migrations running
  Duration: 15–30 seconds until ready
  Kubernetes without readiness probe:
    Service endpoints: include this Pod immediately on startup
    Client requests: arrive before the app is ready → 503 / ECONNRESET
    Resolution: client sees errors during every deployment

  With readiness probe:
    Probe: GET /health/ready → 503 (DB not connected yet)
    Pod removed from Service endpoint list until probe passes
    Clients: never routed to this Pod until it is truly ready
    Resolution: zero client-visible errors during deployments

  Second scenario — same container, different problem:
    Application started, serving traffic normally
    Redis connection pool exhausted (all connections busy)
    Application: can still respond to simple requests but cannot process
                 any request requiring Redis (payment sessions, rate limiting)
    Liveness probe: passes (process is alive, event loop is running)
    Readiness probe: fails (Redis check times out)
    Result: Pod removed from Service endpoints until Redis recovers
            Other Pods (with working Redis connections) absorb the traffic
            This Pod: not killed, not restarted — just taken out of rotation
            When Redis pool recovers: readiness passes → Pod added back automatically
```

**Why process exit detection alone is insufficient:**
```
Scenario: NestJS API with a memory leak
  Memory usage: grows 10 MB per hour
  After 24 hours: 240 MB used (limit: 512 MB) — still within limits, still "running"
  After 48 hours: 480 MB — approaching limit; GC pressure causes latency spikes
  After 51 hours: 510 MB — GC thrashing; P99 latency: 10 seconds
  After 52 hours: 513 MB — OOMKilled (exit code 137)
  Kubernetes: detects exit → restarts container → fresh memory → cycle repeats

  With liveness probe (latency-based):
    Custom metric: if P99 latency > 5s for last 60s → return 503
    After ~48 hours: GC pressure → latency spike → liveness fails → restart
    Memory leak is "self-healing" every 48 hours
    (Real fix: find and fix the memory leak; probe buys time)

  With liveness probe (memory-based, exec):
    command: check if /sys/fs/cgroup/memory.current exceeds 450MB → exit 1
    Proactive restart before OOMKill; avoids the hard kill at 512 MB
```

## Section 2: Probe Types and Configuration

**Q2. What are the three probe mechanisms (httpGet, exec, tcpSocket) and when do you use each?**
A: Every probe — liveness, readiness, and startup — can use one of three mechanisms to check container health. The mechanism determines how Kubernetes inspects the container.

**Mechanism 1 — httpGet:**
```yaml
livenessProbe:
  httpGet:
    path:   /health/live
    port:   3000
    scheme: HTTP       # HTTP (default) or HTTPS
    httpHeaders:       # optional: add custom headers
      - name:  X-Internal-Check
        value: "true"
  # Kubernetes makes an HTTP GET request to http://[pod-ip]:3000/health/live
  # Success: HTTP status code 200–399
  # Failure: HTTP status code 400–599, connection refused, or timeout
```

```
When to use httpGet:
  Any HTTP/HTTPS service (NestJS, Express, Spring Boot, FastAPI, etc.)
  Most common probe mechanism for web services
  Advantages:
    Can check multiple conditions in one endpoint (DB, Redis, dependency health)
    Response body ignored by Kubernetes (only status code matters)
    Custom headers can authenticate the probe (avoid logging probe traffic)
    HTTPS with self-signed cert: set scheme: HTTPS (Kubernetes does not verify the cert)
  Disadvantage:
    Requires the HTTP server to be running before any probe can pass
    If the HTTP server itself fails to start: use startup probe with exec first
```

**Mechanism 2 — exec:**
```yaml
livenessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - "pg_isready -U postgres -h localhost -p 5432"
  # Kubernetes runs this command INSIDE the container
  # Success: command exits with code 0
  # Failure: command exits with non-zero code, or timeout
```

```
When to use exec:
  Non-HTTP services (PostgreSQL, Redis, Kafka, custom TCP protocols)
  When the check is best expressed as a shell command or script
  When a lightweight binary can do the check without starting an HTTP server

PostgreSQL liveness:
  command: ["pg_isready", "-U", "postgres"]
  pg_isready: returns 0 if PostgreSQL is ready to accept connections

Redis liveness:
  command: ["redis-cli", "ping"]
  Returns 0 if Redis responds with PONG; non-zero if Redis is down

Kafka broker liveness:
  command: ["/bin/sh", "-c",
    "kafka-broker-api-versions.sh --bootstrap-server localhost:9092"]

Custom NestJS liveness (alternative to HTTP):
  command: ["/bin/sh", "-c",
    "curl -sf http://localhost:3000/health/live || exit 1"]
  (Not preferred over httpGet — adds curl dependency; use httpGet instead)

Disadvantages of exec:
  Spawns a new process for every probe check (CPU overhead at high frequency)
  Shell injection risk if command includes untrusted input
  Command must exist in the container image (add curl, pg_isready to Dockerfile if needed)
  Avoid complex shell scripts — hard to debug; use a dedicated health check binary
```

**Mechanism 3 — tcpSocket:**
```yaml
livenessProbe:
  tcpSocket:
    port: 9092   # Kafka broker port
  # Kubernetes opens a TCP connection to [pod-ip]:9092
  # Success: TCP connection established (3-way handshake completes)
  # Failure: connection refused, or timeout
  # Connection is immediately closed after the check
```

```
When to use tcpSocket:
  Services where port being open is sufficient health signal
  Non-HTTP, non-scriptable services
  As a lightweight alternative when exec would be expensive

What tcpSocket does NOT check:
  Whether the service can actually process requests
  A port can be LISTEN but the application behind it is deadlocked
  TCP connection succeeds → probe passes → but actual requests hang

When it is sufficient:
  Kafka: broker port 9092 open = broker is alive (full check via exec is expensive)
  Zookeeper: port 2181 open = ZK is accepting connections
  Custom TCP services where port open implies functional service

Comparison:
  httpGet   → most information (status code, can check application logic)
  exec      → flexible (any check expressible as a command)
  tcpSocket → least information (port open = alive; nothing more)
```

**Q3. What are all the probe configuration parameters and what are the correct values for a production NestJS API?**
A: Each probe shares the same set of tuning parameters. Incorrect values are one of the most common sources of unnecessary Pod restarts (values too aggressive) or missed failures (values too lenient).

**All probe parameters explained:**
```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 3000

  # How long to wait before starting probe checks after container starts
  # Default: 0 (start immediately)
  # Problem with 0: probe starts before the HTTP server is bound to port 3000
  #                 → connection refused → probe fails → container killed before it starts
  # With startupProbe: set initialDelaySeconds to 0 (startupProbe handles the delay)
  # Without startupProbe: set to estimated startup time + buffer
  initialDelaySeconds: 0

  # How often to run the probe (seconds)
  # Default: 10
  # Lower = faster detection; higher = less kubelet CPU overhead
  # For liveness: 10–30s (failures are acted on quickly regardless)
  # For readiness: 5–10s (affects how quickly traffic resumes after recovery)
  periodSeconds: 10

  # How long to wait for the probe to respond before counting it as a failure
  # Default: 1 second — dangerously short for many applications
  # If /health/ready checks DB + Redis: both must respond within this timeout
  # Set to: max(expected_check_duration) × 2
  # For a DB + Redis check: 2–5 seconds is safe
  timeoutSeconds: 5

  # How many consecutive FAILURES before taking action
  # Default: 3
  # Liveness: 3 × periodSeconds = 30s before restart (avoids flapping on transient blips)
  # Readiness: 2 × periodSeconds = 10–20s before removing from endpoints
  # Too low: flapping (transient DB hiccup → Pod restarted unnecessarily)
  # Too high: slow detection of real failures
  failureThreshold: 3

  # How many consecutive SUCCESSES to consider the probe passing
  # Default: 1
  # Liveness: always 1 (one success = healthy; no reason to require more)
  # Readiness: 1 or 2
  #   1: Pod added to endpoints on first success (may still be warming up)
  #   2: Pod added only after two consecutive successes (more conservative; avoids flapping)
  successThreshold: 1
```

**Production NestJS API probe configuration:**
```yaml
spec:
  containers:
    - name: nestjs-api
      image: nestjs-api:2.5.0

      # Startup probe: allows slow startup without triggering liveness kills
      # Guards: initialDelaySeconds in liveness/readiness can be set to 0
      # Maximum startup time: failureThreshold × periodSeconds = 24 × 5 = 120 seconds
      startupProbe:
        httpGet:
          path: /health
          port: 3000
        initialDelaySeconds: 0      # start checking immediately
        periodSeconds:       5      # check every 5 seconds
        failureThreshold:    24     # allow up to 120s for startup
        successThreshold:    1      # one success → startup complete; hand off to liveness
        timeoutSeconds:      3

      # Liveness probe: detect deadlock, infinite loop, fatal degradation
      # Only active AFTER startupProbe passes
      # Checks: is the event loop responsive? Nothing more.
      livenessProbe:
        httpGet:
          path: /health/live        # lightweight; only checks event loop responsiveness
          port: 3000
        initialDelaySeconds: 0
        periodSeconds:       15     # check every 15 seconds (liveness is not time-critical)
        failureThreshold:    3      # 3 × 15 = 45 seconds before restart
        successThreshold:    1
        timeoutSeconds:      5

      # Readiness probe: control traffic routing
      # Checked independently of liveness; both run simultaneously after startup
      readinessProbe:
        httpGet:
          path: /health/ready       # thorough check: DB, Redis, downstream deps
          port: 3000
        initialDelaySeconds: 0
        periodSeconds:       5      # check every 5 seconds (traffic routing is time-sensitive)
        failureThreshold:    2      # 2 × 5 = 10 seconds before removing from endpoints
        successThreshold:    2      # 2 consecutive successes before adding back to endpoints
        timeoutSeconds:      5      # DB + Redis check must complete in 5 seconds

  # Grace period for in-flight request draining on Pod shutdown
  terminationGracePeriodSeconds: 60
```

## Section 3: The Startup Probe

**Q4. What is the startup probe, why was it introduced, and when is it strictly necessary?**
A: The startup probe was introduced in Kubernetes 1.18 to solve the `initialDelaySeconds` dilemma: setting it too low kills containers during legitimate slow startup; setting it too high delays detection of real failures after the container has started. The startup probe separates the two concerns entirely.

**The initialDelaySeconds dilemma (without startup probe):**
```
Application startup time: variable (10–60 seconds depending on:
  - TypeORM connection pool establishment
  - Database migration execution time
  - Redis warmup
  - External service health checks at startup)

Without startup probe — Option A: short initialDelaySeconds
  initialDelaySeconds: 10
  livenessProbe periodSeconds: 10, failureThreshold: 3
  → Total tolerance: 10 + (3 × 10) = 40 seconds before restart
  → If startup takes 45 seconds: container killed at 40 seconds
  → CrashLoopBackOff: container never starts successfully
  → Symptom: container keeps restarting; logs show startup in progress then SIGKILL

Without startup probe — Option B: long initialDelaySeconds
  initialDelaySeconds: 120   (safely covers worst-case startup)
  livenessProbe periodSeconds: 10, failureThreshold: 3
  → Container can start in 5 seconds; liveness probe does not start until 120s
  → If the application deadlocks at second 10:
       Liveness probe inactive for 110 more seconds
       Operators wonder why the stuck container is not being restarted
  → Slow detection of real post-startup failures

With startup probe — clean separation:
  startupProbe: failureThreshold: 24, periodSeconds: 5
  → Up to 120 seconds for startup; no liveness interference
  → startupProbe passes at second 15 (after TypeORM connects)
  → Liveness probe activates at second 15 with periodSeconds: 10
  → Deadlock at second 20 → liveness fails → restart at second 50
  → Fast detection; zero interference with startup

When startup probe is strictly necessary:
  1. Startup time is highly variable (migrations: 5s on empty DB; 60s on schema changes)
  2. Startup time exceeds: initialDelaySeconds + (periodSeconds × failureThreshold)
     that you would set on the liveness probe alone
  3. Any Java application (JVM warm-up), any application running DB migrations on startup,
     any application connecting to many external services before declaring itself ready
  4. When you see CrashLoopBackOff on a healthy application: the startup probe
     (or insufficient initialDelaySeconds) is almost always the cause
```

**Startup probe interaction with liveness and readiness:**
```
Timeline:

Container starts (T=0)
  ├── startupProbe: begins checking every 5s
  ├── livenessProbe: SUSPENDED (not running while startupProbe is active)
  └── readinessProbe: SUSPENDED (not running while startupProbe is active)

startupProbe passes at T=18s (NestJS bound to port 3000, DB connected)
  ├── startupProbe: STOPS (never runs again for the life of this container)
  ├── livenessProbe: ACTIVATES (begins checking every 15s)
  └── readinessProbe: ACTIVATES (begins checking every 5s)

Readiness fails at T=23s (Redis connection pool momentarily exhausted):
  Pod removed from Service endpoints
  Liveness: still passing (event loop is responsive)
  At T=33s: readiness passes again (Redis pool recovered)
  Pod added back to Service endpoints

Liveness fails at T=180s (event loop deadlocked):
  3 × 15s = 45s of failures required
  Container killed at T=225s
  Container restarted
  startupProbe: activates again for the new container instance
```

## Section 4: Health Check Endpoint Implementation

**Q5. How do you implement production-grade health check endpoints in NestJS, and what should each endpoint check?**
A: Health check endpoints are part of the application contract with Kubernetes. The three endpoints — `/health` (startup), `/health/live` (liveness), and `/health/ready` (readiness) — have different check depths and different failure consequences, so they must be implemented differently.

```typescript
// health.controller.ts
import {
  Controller, Get, ServiceUnavailableException,
  Logger, Dependencies
} from '@nestjs/common';
import { InjectDataSource }  from '@nestjs/typeorm';
import { DataSource }        from 'typeorm';
import { InjectRedis }       from '@nestjs-modules/ioredis';
import { Redis }             from 'ioredis';

@Controller('health')
export class HealthController {
  private readonly logger = new Logger(HealthController.name);

  constructor(
    @InjectDataSource() private readonly db:    DataSource,
    @InjectRedis()      private readonly redis: Redis,
  ) {}

  // ─── Startup / basic liveness ──────────────────────────────────────────────
  // Used by: startupProbe (path: /health)
  // Checks: is the HTTP server bound and responding?
  // Must pass: as soon as the HTTP server is ready (before DB connection)
  // Does NOT check: DB, Redis, downstream services
  @Get()
  healthCheck(): { status: string; timestamp: string } {
    return {
      status:    'ok',
      timestamp: new Date().toISOString(),
    };
  }

  // ─── Liveness ──────────────────────────────────────────────────────────────
  // Used by: livenessProbe (path: /health/live)
  // Checks: is the Node.js event loop responsive and unblocked?
  // Failure action: container is KILLED and RESTARTED
  // Rule: check ONLY the process itself — NO external dependencies
  //
  // Critical reasoning: if the database is down, a failing liveness probe
  // kills and restarts ALL Pods simultaneously. This causes:
  //   1. Service outage (all Pods restart at once under rolling update limits)
  //   2. Connection storm (all Pods try to reconnect to DB simultaneously)
  //   3. Makes a bad situation (DB down) catastrophically worse
  //
  // Liveness should fail ONLY when the process is so broken that restart is
  // the only recovery option (deadlock, infinite loop, unrecoverable corruption).
  @Get('live')
  liveness(): { status: string } {
    // This endpoint itself is the check.
    // If the event loop is deadlocked: this endpoint never responds → timeout → failure.
    // If this endpoint responds at all: the event loop is alive.
    return { status: 'ok' };
    // Optional: check for known deadlock indicators without external I/O
    // Example: check process memory usage (if > 90% of limit, consider restart)
  }

  // ─── Readiness ─────────────────────────────────────────────────────────────
  // Used by: readinessProbe (path: /health/ready)
  // Checks: can this Pod serve production traffic right now?
  // Failure action: Pod REMOVED from Service endpoints (NOT killed)
  // Rule: check all dependencies required for request handling
  //
  // On failure: other healthy Pods continue serving traffic.
  // This Pod: stays alive; resumes traffic when dependencies recover.
  // This is the correct behavior for transient dependency failures.
  @Get('ready')
  async readiness(): Promise<{
    status: string;
    checks: Record<string, 'ok' | 'error'>;
    latencyMs: number;
  }> {
    const startedAt = Date.now();
    const checks: Record<string, 'ok' | 'error'> = {};
    let allHealthy = true;

    // Check 1: PostgreSQL connection pool
    try {
      // Use a query with a short statement timeout to avoid blocking the probe
      await this.db.query('SELECT 1', [], {
        queryTimeout: 2000,  // fail fast if DB is slow
      });
      checks.database = 'ok';
    } catch (err) {
      this.logger.warn('Readiness: database check failed', { err });
      checks.database = 'error';
      allHealthy = false;
    }

    // Check 2: Redis connectivity
    try {
      const pong = await Promise.race([
        this.redis.ping(),
        new Promise((_, reject) =>
          setTimeout(() => reject(new Error('Redis ping timeout')), 2000)
        ),
      ]);
      checks.redis = pong === 'PONG' ? 'ok' : 'error';
      if (checks.redis === 'error') allHealthy = false;
    } catch (err) {
      this.logger.warn('Readiness: Redis check failed', { err });
      checks.redis = 'error';
      allHealthy = false;
    }

    // Check 3: Critical downstream service (e.g., payment gateway reachability)
    // Only check if your service CANNOT function without it
    // Omit checks for services you can gracefully degrade without
    // (checking too many deps = frequent false readiness failures)

    const latencyMs = Date.now() - startedAt;

    if (!allHealthy) {
      // 503 Service Unavailable: readiness probe counts this as a failure
      throw new ServiceUnavailableException({
        status:    'degraded',
        checks,
        latencyMs,
        timestamp: new Date().toISOString(),
      });
    }

    return { status: 'ok', checks, latencyMs };
  }
}
```

**What to include in readiness vs what to exclude:**
```
INCLUDE in readiness check (failing these prevents serving requests):
  ✅ Primary database connection pool
     Reason: every API request hits the DB; DB down = cannot serve
  ✅ Redis (if used for session, rate limiting, idempotency — critical path)
     Reason: payment requests require Redis for idempotency check
  ✅ Required message queue connection (if reads from queue in critical path)

EXCLUDE from readiness check (failing these should NOT stop traffic):
  ❌ Optional third-party APIs (analytics, logging, monitoring)
     Reason: these should be non-blocking; requests should succeed without them
  ❌ Downstream services that can be cached or degraded gracefully
     Reason: if SMS gateway is down, loan applications should still work
  ❌ Admin-only features not in the normal request path
     Reason: admin feature unavailability ≠ API unavailability
  ❌ Background job processors (separate process; not in request path)
  ❌ Read replicas (fail open: use primary if replica is unavailable)

NEVER include in liveness check:
  ❌ Database connectivity
  ❌ Redis connectivity
  ❌ Any external service
  Reason: external dependency down + liveness check = all Pods restart simultaneously
          = service outage caused by the health check itself
```

**Preventing probe traffic from polluting logs:**
```typescript
// Middleware: suppress health check log entries
// (Kubernetes probes check /health every 5-10 seconds; 86,400 log lines/day per Pod)
import { Injectable, NestMiddleware } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';

@Injectable()
export class SuppressProbeLogsMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    if (req.path.startsWith('/health')) {
      // Disable Morgan/Winston request logging for probe endpoints
      req['skipLogging'] = true;
    }
    next();
  }
}

// In AppModule:
configure(consumer: MiddlewareConsumer) {
  consumer
    .apply(SuppressProbeLogsMiddleware)
    .forRoutes('*');
}

// In Winston/Pino logger: skip logging if req.skipLogging is true
// This removes ~500,000 health check log entries per day per Pod from CloudWatch
// Significant cost reduction in CloudWatch Logs ingestion charges
```

## Section 5: Graceful Shutdown and Probe Coordination

**Q6. How do readiness probes and `terminationGracePeriodSeconds` coordinate to achieve zero-downtime Pod shutdown?**
A: Pod shutdown is a multi-step process where probes play a critical role. Without correct coordination between the readiness probe, the ALB deregistration delay, and `terminationGracePeriodSeconds`, in-flight requests are dropped mid-processing.

**The Pod shutdown sequence:**
```
Event: Pod is selected for termination (scale-in, rolling update, node drain)

T+0s:  Kubernetes sends two simultaneous signals:
         Signal A → kubelet: begin Pod termination
         Signal B → kube-proxy / endpoints controller: remove Pod from
                    Service Endpoints (stop routing new traffic)

T+0s–2s: Endpoint removal propagates through the cluster
           kube-proxy on all nodes: updates iptables/ipvs rules
           AWS Load Balancer Controller: starts ALB target deregistration

T+0s:  kubelet sends SIGTERM to all containers in the Pod

T+0s–30s: ALB deregistration delay (default 300s; configurable)
           During this time: ALB is draining existing connections to this Pod
           New connections: not routed here (endpoint removed)
           In-flight requests: allowed to complete

T+0s:  NestJS receives SIGTERM → app.enableShutdownHooks() fires
        → onApplicationShutdown() called on all modules
        → HTTP server: stops accepting new connections
        → In-flight requests: allowed to complete (keep-alive connections drain)
        → DB pool: gracefully closes connections after current queries finish
        → Kafka consumers: complete current message processing, commit offsets
        → Redis connections: close cleanly

T+60s: terminationGracePeriodSeconds expires
        If container has not exited: SIGKILL (force kill)
        Any in-flight work at this point: lost

The race condition:
  SIGTERM is sent at T+0s
  Endpoint removal propagates at T+0s–2s (not instantaneous)
  During those 0–2 seconds: ALB can still route new requests to this Pod
  Container receives SIGTERM → starts shutdown → refuses new connections
  New request arrives during the propagation gap → connection refused → 502

Solution: preStop hook (delay shutdown until traffic stops):
  lifecycle:
    preStop:
      exec:
        command: ["/bin/sh", "-c", "sleep 5"]
  This adds 5 seconds between SIGTERM and actual shutdown start
  5 seconds > propagation time → no new requests arrive at a shutting-down Pod
  Then: NestJS receives SIGTERM → shuts down cleanly
```

**Complete shutdown configuration:**
```yaml
spec:
  terminationGracePeriodSeconds: 90   # must be > preStop delay + longest request duration

  containers:
    - name: nestjs-api
      image: nestjs-api:2.5.0

      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
            # 10 seconds: safely covers endpoint propagation (~2s) with buffer
            # During these 10s: Pod is still Running; SIGTERM not yet sent to app
            # After 10s: SIGTERM sent; NestJS graceful shutdown begins

  # ALB annotation: deregistration delay must be < terminationGracePeriodSeconds
  # (set on the Service or TargetGroupBinding, not the Pod)
  # deregistrationDelay: 30s (shorter than 90s grace period)
```

```typescript
// NestJS graceful shutdown implementation
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.enableShutdownHooks(); // listen for SIGTERM, SIGINT

  await app.listen(3000);
}

// In each module that needs cleanup:
@Module({})
export class DatabaseModule implements OnApplicationShutdown {
  constructor(private readonly dataSource: DataSource) {}

  async onApplicationShutdown(signal: string): Promise<void> {
    this.logger.log(`Shutdown signal received: ${signal}`);

    // Stop accepting new DB queries (TypeORM does this automatically on destroy)
    // Wait for in-flight queries to complete
    await this.dataSource.destroy();
    this.logger.log('Database connections closed');
  }
}

@Module({})
export class KafkaModule implements OnApplicationShutdown {
  constructor(private readonly consumer: KafkaConsumer) {}

  async onApplicationShutdown(): Promise<void> {
    // Finish processing the current message batch
    // Commit offsets for processed messages
    // Disconnect consumer (triggers partition rebalance in the consumer group)
    await this.consumer.disconnect();
    this.logger.log('Kafka consumer disconnected');
  }
}
```

**Readiness probe and rolling update interaction:**
```
Rolling update with maxUnavailable: 0, maxSurge: 1:

T=0:  Deployment updated (new image: nestjs-api:2.5.0)
      Kubernetes creates 1 new Pod (surge)

T=0–18s: New Pod: startupProbe checking every 5s
          readinessProbe: SUSPENDED
          Traffic: all 3 old Pods serving (no new Pod yet)

T=18s: startupProbe passes
        readinessProbe: ACTIVATES

T=18–28s: readinessProbe: checking every 5s
           First 2 checks pass (successThreshold: 2)
           New Pod: NOT in Service endpoints yet

T=28s: readinessProbe passes (2 consecutive successes)
        New Pod ADDED to Service endpoints
        Now: 4 Pods serving traffic (3 old + 1 new)

T=28s: Kubernetes terminates 1 old Pod (SIGTERM)
        old Pod preStop: sleep 10s
        old Pod SIGTERM: NestJS drains

T=38s: Old Pod exits cleanly
        Traffic: 3 Pods serving (2 old + 1 new)

Repeat for remaining 2 old Pods
Result: zero dropped requests throughout the rolling update
         every request is handled by a ready Pod
```

## Section 6: Common Failure Modes and Anti-Patterns

**Q7. What are the most common probe misconfiguration patterns and what symptoms do they produce?**
A: Probe misconfiguration is responsible for a large class of production incidents: unnecessary Pod restarts, traffic drops during deployments, and cascading failures. Each pattern has a distinct symptom.

**Anti-pattern 1 — Database check in liveness probe:**
```
Configuration:
  livenessProbe:
    httpGet:
      path: /health/live   # endpoint checks DB connectivity
    failureThreshold: 3
    periodSeconds: 10

Scenario: RDS Multi-AZ failover (60-second downtime)
  T=0:   RDS primary fails; failover begins
  T=10s: First liveness probe failure (DB unreachable)
  T=20s: Second failure
  T=30s: Third failure → ALL Pods killed simultaneously
  T=30s: 6 Pods restart → all try to connect to RDS → connection storm
  T=30s: RDS still in failover → all 6 Pods fail liveness again
  T=90s: RDS failover complete; but now all 6 Pods are in CrashLoopBackOff
         (Kubernetes backs off: 10s, 20s, 40s, 80s, 160s...)
  T=90s: Service unavailable for 60s of RDS failover + 5+ minutes of CrashLoopBackOff

Correct behavior with DB ONLY in readiness probe:
  T=0:   RDS primary fails; failover begins
  T=10s: readinessProbe fails → all Pods removed from Service endpoints
  T=10s: ALB: 503 to clients (better than CrashLoopBackOff; all Pods still alive)
  T=60s: RDS failover complete; DB available
  T=70s: readinessProbe passes → Pods added back to Service endpoints
  T=70s: Normal service resumes
  Total impact: 70 seconds of 503s (unavoidable during DB failover)
                vs minutes of CrashLoopBackOff (avoidable with correct probe design)
```

**Anti-pattern 2 — timeoutSeconds too short:**
```
Configuration:
  readinessProbe:
    timeoutSeconds: 1   # default; often left at the Kubernetes default

Scenario: PostgreSQL is healthy but under load
  Probe: SELECT 1 with a loaded connection pool
  DB response time: 1.1 seconds (slightly over timeout)
  Result: probe times out → counted as failure
  After 2 failures: Pod removed from endpoints
  Fewer Pods serving traffic → more load on remaining Pods
  Remaining Pods' DB queries also take > 1s → they also fail readiness
  Cascading: all Pods removed from endpoints → total service outage
  Root cause: timeoutSeconds: 1 on a probe that checks a loaded DB

Fix:
  readinessProbe:
    timeoutSeconds: 5   # allow 5 seconds for DB + Redis checks
  Also: use a statement_timeout in the probe query:
    SET LOCAL statement_timeout = '2s'; SELECT 1;
  If the DB is so loaded that SELECT 1 takes > 5s: that is a real problem;
  readiness failing in this case is correct (Pod cannot serve traffic either)
```

**Anti-pattern 3 — No startup probe with slow startup:**
```
Configuration:
  livenessProbe:
    initialDelaySeconds: 30
    periodSeconds:       10
    failureThreshold:    3
  # No startupProbe

Scenario: Database schema migration takes 45 seconds on deployment
  T=0:   Container starts; TypeORM migration begins
  T=30s: livenessProbe starts (initialDelaySeconds=30)
  T=30s: /health/live: returns 200 (HTTP server is up, migration still running)
  Actually fine for this probe... but:

  Scenario 2: Migration takes 75 seconds
  T=30s: First liveness check — migration still running; /health/live returns 200 ✅
  T=40s: Second check ✅ (migration still running)
  T=60s: Third check — migration still running but HTTP server has a brief hang
         during a schema lock → /health/live times out → FAILURE
  T=70s: Second failure
  T=80s: Third failure → container killed at T=80s
         Migration: 80% complete; database schema in inconsistent state
         New Pod starts → tries to run migration again → finds partial migration
         → migration may fail (partially applied schema) → Pod CrashLoopBackOff

Fix:
  startupProbe:
    httpGet:
      path: /health
      port: 3000
    failureThreshold: 36    # 36 × 5s = 180s maximum startup window
    periodSeconds:    5
  # livenessProbe.initialDelaySeconds: 0 (startupProbe handles the delay)
  # Migration can take up to 180 seconds; liveness only activates after migration completes
```

**Anti-pattern 4 — successThreshold > 1 on liveness:**
```
Configuration:
  livenessProbe:
    successThreshold: 3   # requires 3 consecutive successes to be "healthy"
    periodSeconds:    10

Problem:
  Container is healthy → liveness probe is running
  One transient failure (network hiccup) → status resets to "unhealthy"
  Now requires 3 more consecutive successes (30 more seconds) before "healthy" again
  During those 30 seconds: liveness is in "unhealthy" state
  If 3 more failures occur in those 30 seconds: container is killed

  Kubernetes documentation: successThreshold must be 1 for liveness probes
  (The API allows other values but it is semantically wrong for liveness)
  Liveness: one success = alive; no reason to require multiple
  Readiness: successThreshold: 2 is reasonable (avoid flapping from single success)

Fix:
  livenessProbe:
    successThreshold: 1   # always 1 for liveness
  readinessProbe:
    successThreshold: 2   # 2 is fine; prevents adding back to endpoints on single blip
```

**Anti-pattern 5 — Same endpoint for liveness and readiness:**
```
Configuration:
  livenessProbe:
    path: /health          # checks DB, Redis, everything
  readinessProbe:
    path: /health          # same endpoint

Problem:
  DB is down → /health returns 503
  livenessProbe: fails → container killed → restart
  readinessProbe: fails → removed from endpoints
  BOTH actions taken simultaneously
  Result: Pods are both killed AND removed from endpoints
  → CrashLoopBackOff while DB is down (same anti-pattern 1)

Fix:
  livenessProbe:  /health/live  (process-only; no external deps)
  readinessProbe: /health/ready (full dependency check)
  Two distinct endpoints with distinct purposes
```

## Section 7: Advanced Probe Patterns

**Q8. How do you implement a readiness probe that accounts for connection pool warmup without triggering false failures during normal operation?**
A: Connection pools take time to establish their full set of connections after startup. A readiness probe that checks pool metrics too aggressively will keep the Pod out of rotation until the pool is fully warmed, which may take longer than desired. The correct approach is to distinguish between "pool is establishing" (acceptable) and "pool is exhausted" (not acceptable).

```typescript
// health.service.ts — pool-aware readiness checks
@Injectable()
export class HealthService {
  private startedAt = Date.now();
  private readonly WARMUP_WINDOW_MS = 30_000; // 30-second warmup window

  constructor(
    @InjectDataSource() private readonly db:    DataSource,
    @InjectRedis()      private readonly redis: Redis,
  ) {}

  async checkReadiness(): Promise<ReadinessResult> {
    const isWarmingUp = Date.now() - this.startedAt < this.WARMUP_WINDOW_MS;
    const checks: Record<string, CheckResult> = {};
    let allCriticalHealthy = true;

    // Database check: distinguish between "connecting" and "exhausted"
    const dbPoolInfo = this.db.driver['pool'];  // TypeORM internal pool
    const totalConnections  = dbPoolInfo?.totalCount ?? 0;
    const idleConnections   = dbPoolInfo?.idleCount  ?? 0;
    const waitingRequests   = dbPoolInfo?.waitingCount ?? 0;

    if (waitingRequests > 0 && idleConnections === 0) {
      // Pool is exhausted: all connections in use, requests queuing
      // This is a real problem regardless of warmup window
      checks.database = { status: 'error', reason: 'pool_exhausted', waitingRequests };
      allCriticalHealthy = false;
    } else if (totalConnections === 0 && isWarmingUp) {
      // Pool has zero connections but we are in the warmup window
      // This is expected during the first few seconds of startup
      checks.database = { status: 'warming', reason: 'pool_initializing' };
      // NOT counted as a failure during warmup
    } else {
      // Verify with an actual query
      try {
        await this.db.query('SELECT 1');
        checks.database = { status: 'ok', connections: totalConnections };
      } catch (err) {
        checks.database = { status: 'error', reason: err.message };
        allCriticalHealthy = false;
      }
    }

    // Redis check
    try {
      await this.redis.ping();
      checks.redis = { status: 'ok' };
    } catch (err) {
      checks.redis = { status: 'error', reason: err.message };
      allCriticalHealthy = false;
    }

    return { healthy: allCriticalHealthy, checks, isWarmingUp };
  }
}
```

**Q9. How do you implement a circuit-breaker-aware readiness probe for external dependencies?**
A: A readiness probe should reflect whether the Pod can serve traffic, not whether external services are healthy. When a circuit breaker opens (tripping after N failures), the Pod can still serve requests that don't require the broken dependency. The probe should reflect the degraded-but-functional state, not go fully unhealthy.

```typescript
// Circuit breaker integration with readiness probe
@Controller('health')
export class HealthController {

  @Get('ready')
  async readiness(): Promise<object> {
    const checks: Record<string, any> = {};
    let canServeTraffic = true;

    // Check 1: Critical path — DB (cannot serve any request without it)
    try {
      await this.db.query('SELECT 1');
      checks.database = 'ok';
    } catch (err) {
      checks.database = 'error';
      canServeTraffic = false;  // DB down = cannot serve any traffic
    }

    // Check 2: Non-critical path — payment gateway (circuit breaker state)
    const gatewayCircuit = this.circuitBreakerService.getState('payment-gateway');
    if (gatewayCircuit === 'open') {
      // Circuit is open: payment gateway calls are failing
      // BUT: the circuit breaker HANDLES this — requests return cached responses
      //      or graceful errors; the Pod can still serve traffic
      checks.paymentGateway = 'circuit_open';
      // canServeTraffic remains true — we can still serve (with degraded behavior)
    } else {
      checks.paymentGateway = gatewayCircuit; // 'closed' or 'half_open'
    }

    // Check 3: Redis (critical for payment idempotency; degrade if missing)
    try {
      await this.redis.ping();
      checks.redis = 'ok';
    } catch {
      checks.redis = 'error';
      // Policy: if Redis is down, block new payment initiation (idempotency at risk)
      // but still serve read requests (loan status, merchant dashboard)
      // This is a business decision; for strict idempotency requirements:
      canServeTraffic = false;
    }

    if (!canServeTraffic) {
      throw new ServiceUnavailableException({ status: 'degraded', checks });
    }

    // Return 200 even with circuit_open for payment gateway
    // Kubernetes: routes traffic to this Pod
    // Application: handles payment gateway failures via circuit breaker
    return { status: 'ok', checks };
  }
}
```

## Section 8: Scenario / System Design Questions

**Q10. "Design the complete probe configuration for a NestJS payment API that: takes 20–60 seconds to start (migrations + pool warmup), connects to RDS PostgreSQL and ElastiCache Redis, calls an external payment gateway, and must handle RDS Multi-AZ failover (~60 seconds) without service outage."**
A:

```yaml
# Complete probe configuration for NestJS payment API
spec:
  terminationGracePeriodSeconds: 90

  containers:
    - name: payments-api
      image: payments-api:3.1.0

      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
            # 10s: allows endpoint removal propagation before SIGTERM

      # ── Startup probe ─────────────────────────────────────────────────────
      # Purpose: allow 20–60s migration + warmup window without liveness interference
      # Max startup time: 30 × 5 = 150 seconds (covers worst-case migrations)
      # Checks: HTTP server is bound (not DB — migrations still running)
      startupProbe:
        httpGet:
          path:   /health          # responds as soon as NestJS HTTP server is up
          port:   3000             # before migrations complete; migrations run in background
                                   # OR: wait for migrations to complete, then bind HTTP
        initialDelaySeconds: 0
        periodSeconds:       5
        failureThreshold:    30    # 150 seconds maximum startup window
        successThreshold:    1
        timeoutSeconds:      3

      # ── Liveness probe ────────────────────────────────────────────────────
      # Purpose: detect deadlock, infinite loop, memory exhaustion
      # Checks: event loop responsiveness ONLY — no DB, no Redis, no external calls
      # Failure: container killed and restarted
      # Does NOT check: RDS, Redis, payment gateway
      # Reasoning: RDS failover (60s) must NOT trigger liveness failures
      #            If RDS is in /health/live → 60s of RDS downtime → 3 failures at 20s intervals
      #            → all 6 Pods killed simultaneously → connection storm → extended outage
      livenessProbe:
        httpGet:
          path:   /health/live
          port:   3000
        initialDelaySeconds: 0     # startupProbe handles startup delay
        periodSeconds:       20    # check every 20 seconds
        failureThreshold:    3     # 60 seconds before restart (3 × 20s)
        successThreshold:    1
        timeoutSeconds:      5

      # ── Readiness probe ───────────────────────────────────────────────────
      # Purpose: control traffic routing based on dependency health
      # Checks: RDS + Redis (required for payment processing)
      # Failure: Pod removed from Service endpoints (NOT killed)
      # Handles RDS failover correctly:
      #   RDS failover (60s): readiness fails → Pods removed from endpoints
      #   RDS recovered: readiness passes → Pods added back to endpoints
      #   Pods: never killed during RDS failover (liveness is unaffected)
      # Payment gateway: checked via circuit breaker state, not direct HTTP call
      #   (direct HTTP call to gateway in readiness = gateway slowness = false failures)
      readinessProbe:
        httpGet:
          path:   /health/ready
          port:   3000
        initialDelaySeconds: 0
        periodSeconds:       5     # check every 5s (quick recovery from transient failures)
        failureThreshold:    2     # 10 seconds before removing from endpoints
        successThreshold:    2     # 10 seconds before adding back to endpoints
        timeoutSeconds:      5     # RDS + Redis checks must complete in 5s

# Health endpoint implementations:
# GET /health:
#   Returns 200 as soon as NestJS HTTP server is ready (even before DB connects)
#   Used by: startupProbe
#
# GET /health/live:
#   Returns 200 if event loop is responsive
#   Returns 503 only if the process is so degraded that restart is warranted
#   Used by: livenessProbe
#
# GET /health/ready:
#   Checks:
#     1. RDS: await db.query('SELECT 1') with 2s timeout
#     2. Redis: await redis.ping() with 2s timeout
#     3. Payment gateway: circuit breaker state (NOT a live HTTP call)
#        → circuit closed/half_open = healthy (gateway reachable)
#        → circuit open = 'degraded' status but still 200 (circuit handles failures)
#     4. Connection pool: not exhausted (waitingCount == 0)
#   Returns 200 if all critical checks pass
#   Returns 503 if RDS or Redis are unreachable
#   Used by: readinessProbe

# RDS failover behavior with this configuration:
#   T=0:   RDS primary fails; failover begins
#   T=5s:  First readiness check: SELECT 1 fails → check 1 failure
#   T=10s: Second failure → Pod removed from endpoints (failureThreshold: 2)
#   T=10s–60s: All 6 Pods have failed readiness → no Pod in Service endpoints
#              ALB: returns 503 to clients (correct; no bad data served)
#              Liveness: still passing (event loops alive; no kills)
#   T=60s: RDS failover complete; new primary available
#   T=65s: readiness passes on some Pods (within 5s of RDS recovery)
#   T=70s: second consecutive success → Pods added back to endpoints
#   T=70s: Payment API resumes normal operation
#   Total client-visible impact: 70 seconds of 503 (the RDS failover window)
#   Zero additional impact from probe misconfiguration
```

**Q11. "A NestJS Pod is stuck in `0/1 Running` (Running but not Ready) for 30 minutes. The liveness probe is passing. Walk through your diagnosis."**
A:

```
State: Pod is Running (process alive; liveness passing)
       Pod is not Ready (readiness failing; excluded from Service endpoints)
       Duration: 30 minutes (not a transient issue)

Step 1: Get the readiness probe failure reason
  kubectl describe pod payments-api-abc123 -n production

  Events section:
    Readiness probe failed: HTTP probe failed with statuscode: 503
    OR: Readiness probe failed: Get "http://10.0.1.42:3000/health/ready": dial tcp: connection refused
    OR: Readiness probe failed: Get "http://10.0.1.42:3000/health/ready": context deadline exceeded

  Event: connection refused → HTTP server on port 3000 is not running
  Event: deadline exceeded → endpoint is not responding within timeoutSeconds

Step 2: Check the readiness endpoint directly
  kubectl exec -it payments-api-abc123 -n production -- \
    curl -sv http://localhost:3000/health/ready

  Response body reveals which check is failing:
    {"status":"degraded","checks":{"database":"ok","redis":"error"}}
    → Redis is unreachable from this Pod

  Response: connection refused
    → NestJS HTTP server is not running on port 3000
    → Check application logs: why is port 3000 not bound?

Step 3: Check application logs for the failing check
  kubectl logs payments-api-abc123 -n production --tail=100

  Log pattern: "Redis check failed: Error: connect ECONNRESET"
    → Redis endpoint is wrong, or Redis is down, or this Pod cannot reach Redis

  Log pattern: "Database connection pool exhausted: waitingCount=50"
    → The DB connection pool has 50 requests queuing with no idle connections
    → This Pod is under a connection storm; readiness correctly failing

  Log pattern: "Error: ENOTFOUND redis.production.svc.cluster.local"
    → DNS resolution for Redis service is failing
    → Check: does the Redis Service exist in the production namespace?
      kubectl get svc -n production | grep redis

Step 4: Check the dependency directly
  (For Redis unreachability scenario)
  kubectl exec -it payments-api-abc123 -n production -- \
    redis-cli -h $REDIS_HOST -p 6379 -a $REDIS_PASSWORD ping

  → PONG: Redis is reachable from this Pod; readiness endpoint is wrong
  → Error: i/o timeout: Redis is not reachable (network policy? wrong host?)
  → Error: WRONGPASS: wrong password configured

Step 5: Check if this is only one Pod or all Pods
  kubectl get pods -n production -l app=payments-api
  NAME                         READY   STATUS    RESTARTS
  payments-api-abc123          0/1     Running   0         ← not ready
  payments-api-def456          1/1     Running   0         ← ready
  payments-api-ghi789          1/1     Running   0         ← ready

  All Pods failing: cluster-wide dependency issue (Redis is down)

  For one Pod failing:

      kubectl get pod payments-api-abc123 -n production -o wide
      NODE: node-4

      kubectl describe node node-4 | grep -A5 Conditions

  Redis unreachable (network policy):

  Redis down:

  Connection pool exhausted:
```

## Quick Reference

| Probe | Failure action | Checks | Never check |
|---|---|---|---|
| startupProbe | Kill + restart | HTTP server bound | DB, Redis, external |
| livenessProbe | Kill + restart | Event loop responsive | DB, Redis, external |
| readinessProbe | Remove from endpoints | DB, Redis, critical deps | Payment gateway directly |

| Parameter | Default | Liveness recommendation | Readiness recommendation |
|---|---|---|---|
| initialDelaySeconds | 0 | 0 (use startupProbe) | 0 (use startupProbe) |
| periodSeconds | 10 | 15–20 | 5–10 |
| timeoutSeconds | 1 | 5 | 5 |
| failureThreshold | 3 | 3 | 2 |
| successThreshold | 1 | 1 (always) | 1–2 |

| Mechanism | Success condition | Use for |
|---|---|---|
| httpGet | Status code 200–399 | Any HTTP/HTTPS service |
| exec | Exit code 0 | Non-HTTP (PostgreSQL, Redis, custom) |
| tcpSocket | TCP connection established | Port-open sufficient; no app check needed |

| Failure mode | Symptom | Fix |
|---|---|---|
| DB in liveness probe | All Pods in CrashLoopBackOff during DB failover | Move DB check to readiness only |
| timeoutSeconds too low | False readiness failures under load; cascading outage | Increase to 5s; add query timeout in check |
| No startup probe | CrashLoopBackOff during slow startup (migrations) | Add startupProbe with generous failureThreshold |
| Same endpoint for live + ready | DB down → Pods killed AND removed → extended outage | Separate /health/live and /health/ready |
| successThreshold > 1 on liveness | Slow recovery from transient blip; premature kill risk | Set successThreshold: 1 for liveness always |
| Missing preStop sleep | Requests dropped at start of shutdown (endpoint propagation gap) | Add preStop: sleep 10 |

## The Core Mental Model

```
Liveness and readiness answer different questions with different consequences:
  Liveness:  "Is this container so broken that restarting it is the only fix?"
             Failure → KILL and RESTART
             Must be conservative: a false positive kills a healthy container
             Must only check: things that ONLY a restart can fix (deadlock, OOM spiral)
             Must NEVER check: external dependencies (restarting won't fix a DB outage)

  Readiness: "Can this container serve production traffic right now?"
             Failure → REMOVE from load balancer (not killed; not restarted)
             Can be more liberal: a false positive just temporarily reduces capacity
             Should check: all dependencies required for request handling
             Correct for: transient failures (DB overload, Redis hiccup, connection exhaustion)

  The golden rule:
    If a dependency goes down, you want:
      - ALL Pods removed from the load balancer (readiness failing) ✅
      - ZERO Pods killed and restarted (liveness should be unaffected) ✅
    Not:
      - ALL Pods killed simultaneously → connection storm → extended outage ❌
    This golden rule requires DB/Redis to be in readiness ONLY, never in liveness.

Startup probe is the solution to the initialDelaySeconds dilemma:
  Without it: either CrashLoopBackOff (delay too short) or slow failure detection (delay too long)
  With it: startup can be as slow as needed; liveness only activates after startup completes
  If you see CrashLoopBackOff on first deployment and the app "works fine locally":
    the startup probe (or initialDelaySeconds) is almost certainly the cause.

The shutdown sequence has a race condition; preStop sleep fixes it:
  SIGTERM and endpoint removal happen simultaneously, not sequentially.
  Endpoint removal propagates in 1–5 seconds (not instant).
  During propagation: ALB still routes new requests to the shutting-down Pod.
  preStop: sleep 10 holds the Pod in Running state for 10 seconds after the delete signal,
  giving endpoint removal time to propagate before SIGTERM is sent to the application.
  Without it: the first few seconds of every shutdown drop some requests.

terminationGracePeriodSeconds must accommodate preStop + application drain:
  terminationGracePeriodSeconds: 90
    preStop sleep: 10s
    SIGTERM sent:  at 10s
    NestJS drain:  up to 60s (finish in-flight requests, close DB connections)
    Buffer:        20s
  If terminationGracePeriodSeconds < (preStop + drain time): SIGKILL interrupts drain → dropped requests

Health endpoint noise is a real cost:
  6 Pods × 2 probes (liveness + readiness) × (1/15s + 1/5s) = 6 × 2 × 0.27 = ~3 requests/second
  Per day: ~260,000 health check requests
  Per month: ~7.8 million requests → visible in CloudWatch, APM, and access logs
  Suppress health check logging at the middleware level.
  Do not include probe endpoints in APM transaction tracing (creates noise in error rates).
  Exclude /health/* from WAF rate limiting rules (probe traffic should never be rate-limited).
```

**Tip for the interview:** Probe questions at 5 YOE converge on three depth probes: (1) the liveness vs readiness distinction for database health — knowing that putting the database check in the liveness probe causes all Pods to be killed simultaneously during a DB failover (because all liveness probes fail at the same time), creating a connection storm and CrashLoopBackOff that outlasts the original failover by minutes, while putting it only in the readiness probe gracefully removes Pods from the load balancer and re-adds them after recovery, demonstrates you understand how Kubernetes failure modes compound rather than just the probe API surface; (2) the startup probe motivation — explaining the `initialDelaySeconds` dilemma (too short → CrashLoopBackOff on legitimate slow startups; too long → slow detection of real post-startup failures) and that the startup probe resolves it by cleanly separating "is the container starting up?" from "is the running container alive?", shows you have debugged the most common first-deployment failure mode in Kubernetes; (3) the preStop sleep and shutdown race condition — knowing that SIGTERM and endpoint removal are sent simultaneously (not sequentially), that endpoint removal takes 1–5 seconds to propagate through kube-proxy and the ALB, that new requests can arrive at a shutting-down Pod during that window, and that `preStop: exec: command: sleep 10` holds the Pod alive during propagation, is the operational detail that explains why zero-downtime deployments require more than just a rolling update strategy. The fintech callout: for a payment API, the readiness probe failure during an RDS Multi-AZ failover (60 seconds of DB unavailability) should produce 60 seconds of 503 responses to clients — not a CrashLoopBackOff that lasts 5–10 minutes — and the difference is entirely determined by whether the DB check is in the liveness probe (catastrophic) or only in the readiness probe (correct).
