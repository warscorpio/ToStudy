## Section 1: The Pod — Kubernetes' Atomic Unit

**Q1. What is a Pod and what does it mean for containers within a Pod to share a network namespace?**
A: A Pod is the smallest deployable unit in Kubernetes — a logical host for one or more containers that run together on the same node and share the same network namespace, IPC namespace, and (optionally) PID namespace. The Pod is not a container; it is the environment in which containers run.

**Shared network namespace — the concrete implications:**
```
Pod with two containers: nestjs-api and nginx-sidecar

Without shared network namespace (separate containers):
  nestjs-api:    127.0.0.1:3000 (its own loopback)
  nginx-sidecar: 127.0.0.1:80   (its own loopback)
  They cannot reach each other via localhost — different network stacks

With shared network namespace (same Pod):
  Both containers share ONE network interface, ONE IP address, ONE loopback
  nestjs-api:    binds 0.0.0.0:3000
  nginx-sidecar: connects to 127.0.0.1:3000  ← same loopback, works
  From outside: Pod IP:80 → nginx-sidecar → localhost:3000 → nestjs-api

Practical consequence:
  Containers in a Pod communicate via localhost (not via Kubernetes Service DNS)
  Port conflict: two containers in the same Pod cannot bind the same port
    nestjs-api:3000 + another-app:3000 in the same Pod → crash (EADDRINUSE)
  Network policies apply at Pod level (the shared IP), not per-container

Pod IP:
  Each Pod gets one IP address from the cluster's pod CIDR (e.g., 10.0.1.42)
  The IP is assigned when the Pod is scheduled; released when the Pod is deleted
  Pod IPs are ephemeral — do not hardcode them (use Services instead)
```

**Shared volumes — inter-container communication:**
```yaml
# emptyDir volume: shared scratch space between containers in a Pod
# Common for sidecar patterns (log shipper reads app's log files)
apiVersion: v1
kind: Pod
metadata:
  name: nestjs-with-log-shipper
spec:
  volumes:
    - name: app-logs
      emptyDir: {}           # lives as long as the Pod; deleted with the Pod

  containers:
    - name: nestjs-api
      image: nestjs-api:2.4.1
      volumeMounts:
        - name:      app-logs
          mountPath: /var/log/app   # app writes logs here

    - name: fluent-bit                # log shipper sidecar
      image: fluent/fluent-bit:2.2
      volumeMounts:
        - name:      app-logs
          mountPath: /var/log/app    # reads from same directory
      # fluent-bit tails /var/log/app/*.log → ships to CloudWatch/Elasticsearch

  # init container: runs to completion BEFORE the main containers start
  initContainers:
    - name: run-migrations
      image: nestjs-api:2.4.1
      command: ['npm', 'run', 'migration:run']
      env:
        - name:  DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key:  url
      # If migration fails (exit code != 0): Pod stays in Init state; main containers never start
      # Safe: database is always migrated before app starts
```

**Pod lifecycle phases:**
```
Pending:     Pod accepted by API server; waiting for node scheduling or image pull
Running:     Pod bound to a node; at least one container is running
Succeeded:   All containers exited with code 0 (terminal; for Jobs)
Failed:      All containers have exited; at least one with non-zero code (terminal)
Unknown:     Pod state cannot be determined (usually: node communication lost)

Container states (within a Running Pod):
  Waiting:    container not running; pulling image, or waiting for init container
  Running:    container is executing
  Terminated: container has exited (with exit code)

restartPolicy (Pod-level):
  Always:     restart on any exit (default; used for long-running services)
  OnFailure:  restart only on non-zero exit code (used for Jobs)
  Never:      never restart (used for one-shot containers)

Note: Deployment/ReplicaSet/DaemonSet Pods always use restartPolicy: Always
      Job Pods always use restartPolicy: OnFailure or Never
      You cannot mix these — the controller enforces the restartPolicy
```

**Q2. What are Pod resource requests and limits, and what happens when a container exceeds them?**
A: Resource requests tell the scheduler how much CPU and memory the container needs — the scheduler uses requests to find a node with sufficient free capacity. Limits cap the maximum resources the container can consume. These are separate values with different enforcement mechanisms.

**Request vs Limit — the distinction:**
```
Request:
  Used by: kube-scheduler (finds a node where sum(requests) ≤ node allocatable)
  Enforced by: Linux cgroup soft limit (guaranteed allocation; not a hard cap)
  Effect: the container is guaranteed AT LEAST this much resource
  Setting requests too low: scheduler places too many Pods on one node
                            → Pods compete for resources → unpredictable latency

Limit:
  CPU limit:    enforced by cgroup CPU quota (hard throttle — container cannot use more)
  Memory limit: enforced by cgroup memory limit (hard cap — exceed it → OOMKilled)
  Effect: the container cannot use more than this amount

CPU behavior at the limit:
  CPU is COMPRESSIBLE: container is throttled (slowed) but not killed
  CPUThrottling = container wanted CPU but was denied because it hit the cgroup quota
  High CPU throttling → increased latency (container is waiting for CPU time)
  Symptom: P99 latency spikes even though CPU utilization looks "low" on dashboards
           (because throttled time is invisible to standard CPU % metrics)

Memory behavior at the limit:
  Memory is INCOMPRESSIBLE: container is killed (OOMKilled) if it exceeds the limit
  OOMKilled exit code: 137 (128 + 9, SIGKILL)
  Pod restartPolicy: Always → container restarts after OOMKill
  Repeat OOMKill → CrashLoopBackOff (Kubernetes backs off restarts exponentially)

QoS classes (derived from request/limit relationship):
  Guaranteed: requests == limits for ALL containers in the Pod
    → Highest priority; last to be evicted under node memory pressure
    → Use for: production databases, critical API services
    → CPU throttling still applies at the limit

  Burstable: at least one container has requests != limits (or limits not set)
    → Medium priority; evicted after BestEffort but before Guaranteed
    → Common pattern: set requests for scheduling, limits for safety

  BestEffort: NO requests or limits set on any container
    → Lowest priority; first evicted under node pressure
    → Never use in production
```

```yaml
# Resource configuration for production NestJS API
apiVersion: v1
kind: Pod
spec:
  containers:
    - name: nestjs-api
      image: nestjs-api:2.4.1
      resources:
        requests:
          cpu:    "250m"      # 0.25 vCPU guaranteed for scheduling
          memory: "256Mi"     # 256 MiB guaranteed
        limits:
          cpu:    "1000m"     # 1 vCPU maximum (throttled, not killed)
          memory: "512Mi"     # 512 MiB maximum (OOMKilled if exceeded)

      # CPU throttling visibility: use this metric in Grafana
      # container_cpu_cfs_throttled_seconds_total / container_cpu_cfs_periods_total
      # Alert if > 25% of CPU periods are throttled
```

## Section 2: Deployment and ReplicaSet

**Q3. What is the relationship between a Deployment, a ReplicaSet, and Pods?**
A: A Deployment is a declarative description of a desired state for a stateless application. The Deployment controller creates and manages ReplicaSets. ReplicaSets create and manage Pods. The three form a strict ownership hierarchy: Deployment owns ReplicaSets; each ReplicaSet owns a set of Pods.

**The ownership chain:**
```
Deployment: nestjs-api
  ├── ReplicaSet: nestjs-api-7d9f4b8c6  (current — image: nestjs-api:2.4.1)
  │     ├── Pod: nestjs-api-7d9f4b8c6-xk9p2  (Running)
  │     ├── Pod: nestjs-api-7d9f4b8c6-m3r8t  (Running)
  │     └── Pod: nestjs-api-7d9f4b8c6-qz7w1  (Running)
  │
  └── ReplicaSet: nestjs-api-6c8d3a4b9  (previous — image: nestjs-api:2.3.0)
        └── (0 Pods — scaled down after successful rollout to 2.4.1)

Each ReplicaSet corresponds to ONE version of the Pod template.
Changing anything in the Pod template (image, env var, resource limits, labels)
creates a NEW ReplicaSet and triggers a rolling update.
The old ReplicaSet is scaled to 0 but retained (for rollback — see Q5).

Why this design?
  Rollback = scale old ReplicaSet back up + scale new ReplicaSet down
  No new image pull required; the old image is already on the node (or in registry)
  Instant rollback: Kubernetes simply changes the desired replica count per ReplicaSet
```

**Why you should never manage ReplicaSets directly:**
```
Direct ReplicaSet management:
  You create: ReplicaSet replicas=3, image: nestjs-api:2.4.1
  To update image: you must delete the ReplicaSet and create a new one
  During the delete-create: 0 Pods running (downtime)
  No history, no rollback, no rolling update strategy

Deployment management:
  You create: Deployment image: nestjs-api:2.4.1
  To update image: kubectl set image deployment/nestjs-api nestjs-api=nestjs-api:2.5.0
  Deployment: creates new ReplicaSet (2.5.0), scales it up while scaling down 2.4.1 ReplicaSet
  During update: always (replicas - maxUnavailable) Pods running
  History: 10 revisions by default (revisionHistoryLimit); rollback with kubectl rollout undo

The only reason to inspect ReplicaSets directly:
  kubectl get rs → see revision history and current/previous Pod template hashes
  kubectl describe rs <rs-name> → debug why Pods are not starting in a specific revision
```

**Q4. How does a Deployment rolling update work, and what do `maxSurge` and `maxUnavailable` control?**
A: A rolling update replaces old Pods with new Pods incrementally, maintaining application availability throughout. `maxSurge` controls how many extra Pods can exist above the desired replica count; `maxUnavailable` controls how many Pods can be unavailable below the desired count.

**Rolling update mechanics:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nestjs-api
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       2    # can have up to 8 Pods total during update (6 desired + 2 surge)
      maxUnavailable: 1    # at least 5 Pods must be Running and Ready at all times

  template:
    spec:
      containers:
        - name:  nestjs-api
          image: nestjs-api:2.5.0    # changed from 2.4.1
```

```
Update sequence (replicas=6, maxSurge=2, maxUnavailable=1):

Before update:
  Old ReplicaSet (2.4.1): 6 Pods Running ✅

Step 1: Create 2 new Pods (maxSurge=2 → can go up to 8 total)
  Old (2.4.1): 6 Running
  New (2.5.0): 2 Pending → Running → Ready
  Total: 8 Pods (6+2 = desired + maxSurge; allowed)

Step 2: Terminate 3 old Pods (bringing total to 5 old + 2 new = 7, min 5 ready satisfied)
  Old (2.4.1): 3 Running (6-3=3)
  New (2.5.0): 2 Running + 2 more starting (surge used for new batch)
  At minimum: 5 Ready (6 desired - 1 maxUnavailable)

Step 3: Continue until old ReplicaSet has 0 Pods
  New (2.5.0): 6 Running ✅
  Old (2.4.1): 0 Pods (ReplicaSet scaled to 0, retained for rollback)

Total downtime: 0 (at least 5 of 6 Pods available throughout)
Total update time: depends on Pod startup time × number of batches
```

**maxSurge and maxUnavailable tradeoffs:**
```
maxSurge=0, maxUnavailable=1 (no extra capacity):
  Terminates one old Pod, waits for it to leave, starts one new Pod
  Slowest update (one Pod at a time); minimum resource usage
  Risk: if the new Pod is slow to start, service capacity drops by 1/N during each step

maxSurge=N, maxUnavailable=0 (blue-green style):
  Starts all new Pods first, then terminates all old Pods
  Fastest update; requires 2× compute capacity momentarily
  Zero downtime guaranteed (new Pods ready before old ones terminate)
  Use for: critical services where even 1 Pod unavailability is unacceptable

maxSurge=25%, maxUnavailable=25% (Kubernetes default):
  Percentage-based; scales with replica count
  replicas=8: maxSurge=2, maxUnavailable=2
  Balanced: reasonable speed, moderate resource overhead

For fintech payment APIs (default recommendation):
  maxSurge: 1
  maxUnavailable: 0
  → Never reduce capacity below desired; accept 1 extra Pod cost during update
  → Safe for services where every Pod matters for throughput
```

**Q5. How does `kubectl rollout undo` work, and what is `revisionHistoryLimit`?**
A: `kubectl rollout undo` reactivates a previous ReplicaSet by scaling it back up and scaling the current ReplicaSet down to zero — identical to a rolling update but in reverse, and using an already-existing ReplicaSet (no new image pull required).

```bash
# View rollout history
kubectl rollout history deployment/nestjs-api
# REVISION  CHANGE-CAUSE
# 1         feat: initial deployment
# 2         feat: add UPI payment method
# 3         fix: correct NACH retry logic   ← current

# Rollback to previous revision (revision 2)
kubectl rollout undo deployment/nestjs-api
# Equivalent to: kubectl rollout undo deployment/nestjs-api --to-revision=2

# Rollback to a specific revision
kubectl rollout undo deployment/nestjs-api --to-revision=1

# After rollback: revision history
kubectl rollout history deployment/nestjs-api
# REVISION  CHANGE-CAUSE
# 1         feat: initial deployment
# 3         fix: correct NACH retry logic    ← (now at 3, was current)
# 4         feat: add UPI payment method     ← (revision 2 becomes 4 after undo)
# Note: rolled-back revision becomes the new highest revision number

# Monitor rollback progress
kubectl rollout status deployment/nestjs-api --watch
```

**revisionHistoryLimit:**
```yaml
spec:
  revisionHistoryLimit: 10   # default; retain last 10 ReplicaSets (for rollback)
  # revisionHistoryLimit: 3  # keep only last 3 revisions (saves etcd space)
  # revisionHistoryLimit: 0  # keep no history (rollback impossible; do not use)
```

```
What revisionHistoryLimit controls:
  Number of OLD (scaled-to-zero) ReplicaSets retained
  Each retained ReplicaSet = one possible rollback target
  Each retained ReplicaSet also stores the full Pod template (image, env, resources, etc.)

Cost of high revisionHistoryLimit:
  etcd storage: each ReplicaSet object is small (~5 KB) → 10 revisions = ~50 KB per Deployment
  Negligible for most clusters; can matter at very large scale (thousands of Deployments)
  Default (10) is correct for most production deployments

When rollback fails:
  The rollback target image no longer exists in ECR (lifecycle policy deleted it)
  → ImagePullBackOff on the rolled-back Pods
  → "Rollback" appears to complete but Pods cannot start
  Prevention: ECR lifecycle policy must retain images that are rollback targets
              (keep last 10 semver-tagged images to match revisionHistoryLimit: 10)
```

## Section 3: StatefulSet

**Q6. What problems does StatefulSet solve that Deployment cannot, and what guarantees does it provide?**
A: A StatefulSet manages Pods that require stable, persistent identity — each Pod gets a consistent name, a consistent DNS hostname, and its own PersistentVolumeClaim that is not shared with other Pods and is not deleted when the Pod is deleted or rescheduled.

**The three StatefulSet guarantees:**

**Guarantee 1 — Stable, unique Pod names:**
```
Deployment Pods (unstable names):
  nestjs-api-7d9f4b8c6-xk9p2   (random suffix; changes on every Pod restart)
  nestjs-api-7d9f4b8c6-m3r8t
  nestjs-api-7d9f4b8c6-qz7w1

StatefulSet Pods (ordinal, stable names):
  kafka-0    (always kafka-0; same name after restart, reschedule, update)
  kafka-1    (always kafka-1)
  kafka-2    (always kafka-2)

Why stability matters:
  Kafka broker ID = 0, 1, 2 → tied to persistent data on the disk
  kafka-0 must always find ITS data (topic partitions, consumer group offsets)
  If the name changed on restart: broker would start fresh, data orphaned
  Stable names → stable identity → correct data binding
```

**Guarantee 2 — Stable network identity (headless Service DNS):**
```yaml
# Headless Service for StatefulSet DNS
apiVersion: v1
kind: Service
metadata:
  name: kafka
spec:
  clusterIP: None       # headless: no VIP; DNS returns Pod IPs directly
  selector:
    app: kafka
  ports:
    - port: 9092

# StatefulSet references the headless Service
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: kafka
spec:
  serviceName: "kafka"   # must match the headless Service name
  replicas: 3
  selector:
    matchLabels:
      app: kafka
  template:
    metadata:
      labels:
        app: kafka
    spec:
      containers:
        - name:  kafka
          image: confluentinc/cp-kafka:7.5.0
```

```
DNS entries created by the headless Service + StatefulSet:
  kafka-0.kafka.default.svc.cluster.local → Pod kafka-0's IP
  kafka-1.kafka.default.svc.cluster.local → Pod kafka-1's IP
  kafka-2.kafka.default.svc.cluster.local → Pod kafka-2's IP

  Kafka broker configuration:
    KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka-0.kafka:9092
  Kafka broker 0 advertises itself as kafka-0.kafka — stable DNS name
  Even if kafka-0 is rescheduled to a different node:
    New Pod is named kafka-0 (ordinal preserved)
    DNS kafka-0.kafka still resolves (to the new Pod's IP)
    Other brokers reconnect to kafka-0.kafka → find the same broker (different IP, same identity)
```

**Guarantee 3 — Stable persistent storage (PVC per Pod):**
```yaml
spec:
  volumeClaimTemplates:           # creates ONE PVC per Pod (not shared)
    - metadata:
        name: kafka-data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: gp3
        resources:
          requests:
            storage: 100Gi

# PVCs created automatically:
#   kafka-data-kafka-0   (bound to kafka-0 exclusively)
#   kafka-data-kafka-1   (bound to kafka-1 exclusively)
#   kafka-data-kafka-2   (bound to kafka-2 exclusively)

# When kafka-1 is deleted (node failure, reschedule):
#   New kafka-1 Pod is created
#   Kubernetes binds it to the EXISTING kafka-data-kafka-1 PVC
#   New Pod finds its data exactly where it left off
#   PVC is NOT deleted when the Pod is deleted (unlike emptyDir)
#   PVC is NOT deleted when the StatefulSet is deleted (manual cleanup required)
```

**StatefulSet update ordering:**
```
Deployment: updates Pods in any order (random selection from the ReplicaSet)

StatefulSet: updates in reverse ordinal order (highest first)
  3 replicas: updates kafka-2 → then kafka-1 → then kafka-0
  Reason: in most distributed systems (Kafka, Zookeeper, etcd), the leader
          is Pod 0; updating followers first avoids leader disruption

  Each Pod: wait for Running + Ready before updating the next
  If kafka-2 fails to become Ready: update pauses
  kafka-1 and kafka-0 are NOT updated → cluster remains stable
  Operator must investigate and either fix or force-continue

Scale-down ordering: also reverse ordinal (kafka-2 deleted first)
Scale-up ordering: ordinal order (kafka-3 created after 0, 1, 2 are Ready)
```

**Q7. When do you use StatefulSet vs Deployment for a Redis cluster in Kubernetes?**
A: The decision comes down to whether the application requires stable identity for correctness, or whether any Pod can replace any other Pod.

```
Redis Standalone (no cluster, no replication) → Deployment:
  One Pod; no identity requirements; restart on any node is fine
  State: single PVC attached to the Deployment (via PersistentVolumeClaim directly)
  Limitation: downtime during Pod restart (the single Pod is unavailable)
  Use for: dev/staging Redis; low-availability requirements

Redis Sentinel (1 primary + 2 replicas with automatic failover) → StatefulSet:
  redis-0: primary (stable name; Sentinel knows it as redis-0.redis)
  redis-1: replica 1
  redis-2: replica 2
  Sentinel: discovers topology via stable DNS names
  On primary failure: Sentinel promotes redis-1 to primary
  redis-0 restarts: rejoins as replica (finds redis-1.redis → new primary)
  Stable names required: Sentinel config references redis-0.redis etc.

Redis Cluster (sharded, distributed) → StatefulSet:
  redis-0 through redis-5 (3 shards × 2 replicas)
  Each shard has its own data; shard assignment tied to node ID
  Node ID is stored in the PVC (redis uses /data/nodes.conf)
  Pod restart must find its own /data/nodes.conf → PVC per Pod required
  StatefulSet provides both stable name AND dedicated PVC

When ElastiCache is better than self-managed Redis in Kubernetes:
  ElastiCache: managed failover, patching, monitoring, Multi-AZ → no operational burden
  Self-managed in Kubernetes: needed only for features ElastiCache does not support
  (e.g., Redis modules like RediSearch, RedisTimeSeries, or specific version requirements)
  For most fintech workloads: ElastiCache Redis is the right choice
  Self-managed Redis StatefulSet: justified when ElastiCache limitations are hit
```

## Section 4: DaemonSet

**Q8. What is a DaemonSet and what are the canonical use cases for it?**
A: A DaemonSet ensures that exactly one copy of a Pod runs on every node (or every node matching a node selector) in the cluster. When a new node joins the cluster, the DaemonSet controller automatically schedules the Pod on it. When a node is removed, its DaemonSet Pod is garbage-collected.

**DaemonSet anatomy:**
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
  namespace: logging
spec:
  selector:
    matchLabels:
      app: fluent-bit

  updateStrategy:
    type: RollingUpdate     # update one node at a time (default)
    rollingUpdate:
      maxUnavailable: 1     # one DaemonSet Pod unavailable during update

  template:
    metadata:
      labels:
        app: fluent-bit
    spec:
      # DaemonSets often need to run on control plane nodes and tolerate taints
      tolerations:
        - key:      node-role.kubernetes.io/control-plane
          operator: Exists
          effect:   NoSchedule

      # hostPath volumes: access node filesystem directly
      volumes:
        - name: varlog
          hostPath:
            path: /var/log
        - name: varlibdockercontainers
          hostPath:
            path: /var/lib/docker/containers

      containers:
        - name:  fluent-bit
          image: fluent/fluent-bit:2.2
          volumeMounts:
            - name:      varlog
              mountPath: /var/log
              readOnly:  true
            - name:      varlibdockercontainers
              mountPath: /var/lib/docker/containers
              readOnly:  true
          # Fluent Bit reads container logs from the node filesystem
          # → ships to CloudWatch Logs / Elasticsearch / Loki
```

**Canonical DaemonSet use cases:**
```
Node-level observability (must run on every node to collect all data):
  Log collection:     Fluent Bit, Fluentd → collects all container logs on the node
  Metrics collection: Prometheus node-exporter → node CPU, memory, disk, network
  Tracing agent:      Datadog agent, Dynatrace agent, OTEL collector (node mode)

Node-level networking:
  CNI plugins:        Calico, Cilium, Weave (installed by kubeadm; DaemonSet managed)
  Network proxy:      kube-proxy (Kubernetes built-in; manages iptables/ipvs rules)
  Service mesh:       Istio node agent (though Istio uses sidecar injection more commonly)

Node-level security:
  Falco:              runtime security monitoring; reads Linux kernel syscalls via eBPF
  Amazon GuardDuty:   EKS node-level threat detection agent
  NeuVector:          container security; runs on every node to monitor all Pods

Node-level storage:
  CSI node plugins:   EBS CSI driver node plugin (handles volume attachment on each node)
  Ceph:               Rook Ceph OSD (one per node participating in the Ceph cluster)

Node maintenance:
  AWS Node Termination Handler:
    DaemonSet that polls EC2 instance metadata for Spot interruption notices
    On interruption notice: cordons the node, drains Pods, sends lifecycle action
    Critical for Spot instance clusters — must run on EVERY node to catch all interruptions
```

**DaemonSet vs Deployment for the same workload:**
```
Scenario: deploy a log shipper for a 20-node cluster

Deployment (wrong approach):
  Deployment replicas=20 → 20 Pods; sounds correct
  Problem: Kubernetes schedules Pods wherever there is capacity
           → could place 5 Pods on node-1, 0 on node-2
           → node-2's container logs are never collected
           → when node count changes (autoscaling): manual update of replicas required

DaemonSet (correct approach):
  One Pod per node: guaranteed by the DaemonSet controller
  New node added: DaemonSet Pod automatically scheduled on it
  Node removed: DaemonSet Pod deleted automatically
  Node selector / affinity: target only specific nodes (e.g., only worker nodes)

Node selector for DaemonSet (partial deployment):
  spec:
    template:
      spec:
        nodeSelector:
          node-type: worker   # only schedule on nodes labeled node-type=worker
                              # skips control plane nodes (if labeled differently)
```

## Section 5: Job and CronJob

**Q9. How does a Kubernetes Job differ from a Deployment for running batch workloads?**
A: A Job creates one or more Pods to execute a finite task and tracks their completion. Unlike a Deployment (which restarts Pods to keep them running indefinitely), a Job succeeds when its Pods complete successfully and does not restart them after success.

**Job specification and completion semantics:**
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: nach-batch-reconciliation
spec:
  completions:  1          # total successful completions required (default: 1)
  parallelism:  1          # Pods running simultaneously (default: 1)
  backoffLimit: 3          # retry up to 3 times on failure before marking Job failed
  activeDeadlineSeconds: 3600  # fail the Job if not completed within 1 hour

  # TTL: delete the Job (and its Pods) N seconds after completion
  ttlSecondsAfterFinished: 86400   # delete after 24 hours (keeps logs accessible)

  template:
    spec:
      restartPolicy: OnFailure    # REQUIRED for Job Pods (Never or OnFailure; not Always)
      containers:
        - name:  nach-reconciler
          image: nach-processor:1.2.0
          command: ['node', 'dist/batch/nach-reconcile.js']
          env:
            - name:  BATCH_DATE
              value: "2024-01-15"
            - name:  DB_SECRET_ARN
              value: "arn:aws:secretsmanager:..."
          resources:
            requests:
              cpu:    "500m"
              memory: "1Gi"
            limits:
              cpu:    "2000m"
              memory: "2Gi"
```

**Job completion modes:**
```
Non-indexed completion (default, completions=1, parallelism=1):
  One Pod runs the task. If it fails: restart (up to backoffLimit).
  Success: Pod exits 0 → Job marked Complete
  Use: single task (run one migration, process one batch file)

Fixed completion count (completions=N, parallelism=P):
  Run N successful completions total, P at a time
  completions=100, parallelism=10 → 10 Pods at a time; each processes one unit
  Job completes when 100 Pods have exited successfully
  Use: process 100 loan application files, 10 at a time

Indexed completion (completionMode: Indexed):
  Each Pod gets a unique index (JOB_COMPLETION_INDEX env var: 0, 1, ..., N-1)
  Pod 0: processes records 0-999
  Pod 1: processes records 1000-1999
  ... etc.
  Use: partition a large dataset; each worker knows its slice without coordination
  Example: NACH batch with 100,000 records, 10 workers:
    Worker 0: records [0, 10000)
    Worker 1: records [10000, 20000)
    Workers derive their range from JOB_COMPLETION_INDEX

Work queue pattern (parallelism=P, completions not set):
  All Pods pull work items from an SQS queue / Redis list
  Pods exit 0 when the queue is empty
  Job completes when one Pod exits 0 (first worker to drain the queue)
  Other Pods: receive signal from the shared queue being empty → also exit 0
  Use: when work items arrive dynamically or total count unknown at Job creation
```

**Job failure handling:**
```
backoffLimit: 3
  If a Pod exits with non-zero code (or is OOMKilled):
    Attempt 1: new Pod created immediately (or after brief delay)
    Attempt 2: 10s delay
    Attempt 3: 20s delay (exponential backoff)
    Attempt 4: Job marked Failed; no more Pods created
    Alert: Job failure → PagerDuty / CloudWatch alarm

Pod failure policy (Kubernetes 1.26+):
  Can distinguish between pod failure reasons:
    FailJob:  certain exit codes (e.g., exit 1 = business logic failure) → fail Job immediately
    Ignore:   node preemption, node failure → don't count against backoffLimit
    Count:    transient errors → count against backoffLimit (default behavior)

  spec:
    podFailurePolicy:
      rules:
        - action: FailJob
          onExitCodes:
            containerName: nach-reconciler
            operator:       In
            values:         [42]    # exit code 42 = unrecoverable data error → fail immediately
        - action: Ignore
          onPodConditions:
            - type: DisruptionTarget  # node eviction; Spot interruption → don't count as failure
```

**Q10. What is a CronJob and what are the critical edge cases around `concurrencyPolicy` and `startingDeadlineSeconds`?**
A: A CronJob creates a Job on a schedule (cron syntax). The critical production edge cases are: what happens when the previous Job is still running when the next schedule fires, and what happens if the Kubernetes control plane is unavailable during a scheduled run.

**CronJob specification:**
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nach-batch-processor
spec:
  schedule: "30 3 * * *"    # 03:30 UTC daily (09:00 IST)
  timeZone: "Asia/Kolkata"   # Kubernetes 1.27+: specify timezone explicitly
                              # Without timeZone: schedule is in UTC
  concurrencyPolicy:    Forbid  # see Q10 for options
  startingDeadlineSeconds: 300  # if missed by > 5 min, skip this run
  successfulJobsHistoryLimit: 3  # retain last 3 successful Job objects
  failedJobsHistoryLimit:    5   # retain last 5 failed Job objects

  jobTemplate:
    spec:
      backoffLimit:            2
      activeDeadlineSeconds:   7200   # 2 hours max runtime
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name:  nach-processor
              image: nach-processor:1.2.0
              command: ['node', 'dist/batch/nach-daily.js']
```

**`concurrencyPolicy` — the critical production setting:**
```
Allow (default):
  A new Job is created on schedule even if the previous Job is still running
  Result: two NACH batch jobs running simultaneously
    → Both read the same unprocessed records
    → Both attempt to post the same payment to NPCI
    → Duplicate payments, incorrect reconciliation, compliance violation
  Use only when: runs are fully independent and idempotent (rare for batch jobs)

Forbid:
  If the previous Job is still running when the schedule fires: SKIP this run
  The skipped run is logged but no Job is created
  Use when: runs must not overlap (NACH batch — each run processes the previous day's data)
  Risk: if the Job always takes longer than the schedule interval:
    → Every scheduled run is skipped (Job perpetually running)
    → Monitor: CronJob lastScheduleTime vs current time; alert on long-running Jobs

Replace:
  If the previous Job is still running: DELETE it, create a new Job
  Use when: the previous run is stale/stuck and the new run supersedes it
  Risk: partial work from the previous run is abandoned (may leave data in inconsistent state)
  Use only when: the operation is idempotent (re-running from scratch is safe)

Fintech recommendation: Forbid for all financial batch jobs
  NACH processing, EMI collection, reconciliation:
    Forbid → never overlapping → no duplicate transactions
    Alert if Job runtime approaches schedule interval (business risk)
```

**`startingDeadlineSeconds` — missing the schedule window:**
```
Scenario: Kubernetes control plane unavailable 03:28–03:35 UTC
  CronJob scheduled: 03:30 UTC
  Control plane recovers at 03:35 UTC

Without startingDeadlineSeconds:
  CronJob controller re-evaluates all missed schedules since last run
  If > 100 missed schedules (due to extended outage): controller marks CronJob as failed
  (This is a Kubernetes bug/behavior: extended downtime → CronJob stops scheduling)

With startingDeadlineSeconds: 300 (5 minutes):
  Controller checks: is it within 5 minutes of the scheduled 03:30?
  03:35 UTC: yes (03:35 - 03:30 = 5 min ≤ 300s) → creates the Job
  03:36 UTC: no (03:36 - 03:30 = 6 min > 300s) → skip this run; wait for next schedule

  Effect: 5-minute tolerance window for control plane unavailability
  Missed runs beyond the window: skipped (treated as concurrencyPolicy: skip logic)

startingDeadlineSeconds vs activeDeadlineSeconds:
  startingDeadlineSeconds: time after scheduled start within which Job CREATION is allowed
  activeDeadlineSeconds:   time after Job CREATION within which the Job must COMPLETE
  Both should be set for production CronJobs:
    startingDeadlineSeconds: 300   (tolerate 5-min control plane hiccup)
    activeDeadlineSeconds:   7200  (Job must finish within 2 hours or be killed)
```

**CronJob monitoring checklist:**
```
Metric 1: kube_cronjob_next_schedule_time - kube_cronjob_status_last_schedule_time
  Alert if > schedule_interval + startingDeadlineSeconds → CronJob missed without creating a Job

Metric 2: kube_job_status_active > 0 for duration > (expected_runtime × 1.5)
  Alert: Job taking longer than expected → may block next CronJob run (Forbid policy)

Metric 3: kube_job_failed > 0
  Alert immediately: batch job failed → manual investigation required

CloudWatch EventBridge rule for Job completion:
  Event: EKS control plane → Job status change → Complete or Failed
  Target: SNS → alert ops team
  For NACH batch: any failure → immediate PagerDuty alert (financial SLA)
```

## Section 6: Controllers and Control Loop

**Q11. What is the Kubernetes control loop and how do all the workload objects fit into it?**
A: Kubernetes is a control-loop system. Every workload object (Deployment, StatefulSet, DaemonSet, Job, CronJob) has a controller — a reconciliation loop that continuously compares the observed state of the cluster to the desired state declared in the object, and takes action to close the gap.

**The control loop pattern:**
```
for ever:
  desired  = read the object's spec from etcd (what the user declared)
  observed = inspect the actual cluster state (what is actually running)
  if desired != observed:
    take action to move observed closer to desired
  sleep briefly
  repeat

Deployment controller:
  desired:  spec.replicas = 3, image = nestjs-api:2.5.0
  observed: 2 Running Pods (one crashed), image = nestjs-api:2.4.1
  action:   create a new ReplicaSet for 2.5.0, start scaling it up,
            scale down the 2.4.1 ReplicaSet

StatefulSet controller:
  desired:  3 replicas, each with its own PVC
  observed: kafka-1 is missing (node failure)
  action:   create a new Pod named kafka-1, bind it to the existing kafka-data-kafka-1 PVC

DaemonSet controller:
  desired:  one Pod per node (matching node selector)
  observed: new node node-7 joined; no fluent-bit Pod on it
  action:   schedule fluent-bit Pod on node-7

Job controller:
  desired:  1 successful completion
  observed: Pod exited with code 1 (failure); backoffLimit not reached
  action:   create a new Pod (retry attempt 2)

CronJob controller:
  desired:  Job created at 03:30 UTC daily
  observed: it is 03:30 UTC; no Job created yet for today
  action:   create a new Job from the jobTemplate

This is why Kubernetes is eventually consistent, not transactional:
  The controller loop runs continuously and asynchronously
  Actions are not atomic: create Pod → scheduler assigns node → kubelet starts container
  Each step is a separate reconciliation cycle
  The system converges to desired state, but not instantly
```

**Object ownership and garbage collection:**
```
Ownership chain (ownerReferences):
  CronJob     owns → Job
  Deployment  owns → ReplicaSet
  ReplicaSet  owns → Pod
  StatefulSet owns → Pod + PVC (PVC retention depends on policy)

  kubectl get pod <pod-name> -o yaml | grep -A5 ownerReferences
  ownerReferences:
    - apiVersion: apps/v1
      blockOwnerDeletion: true
      controller: true
      kind: ReplicaSet
      name: nestjs-api-7d9f4b8c6
      uid: abc-123-...

Garbage collection:
  Deleting a Deployment: Kubernetes deletes all owned ReplicaSets → all owned Pods
  Deleting a StatefulSet: Pods deleted; PVCs are NOT deleted by default
    (PVC retention policy: Retain → manual cleanup; Delete → auto-delete on scale-down)
  Deleting a Job: Pods deleted; completion record retained until TTL expires
  Deleting a CronJob: all owned Jobs deleted (including running Jobs)

Cascading delete options:
  kubectl delete deployment nestjs-api                      # default: cascade=foreground
  kubectl delete deployment nestjs-api --cascade=background # delete owner; GC cleans owned
  kubectl delete deployment nestjs-api --cascade=orphan     # delete owner; keep owned Pods
    (orphan: Pods continue running without a controller; useful for live migration)
```

## Section 7: Probes and Lifecycle

**Q12. What are the three types of Kubernetes probes and how do they affect Pod scheduling and traffic routing?**
A: Kubernetes uses three probes to determine container health at different lifecycle phases. Each affects a different aspect of how traffic and scheduling interact with the container.

**The three probes:**
```yaml
spec:
  containers:
    - name: nestjs-api
      image: nestjs-api:2.4.1

      # Startup probe: gives slow-starting containers time to initialize
      # Checked repeatedly until it passes; other probes disabled until then
      # If fails after failureThreshold × periodSeconds: container is killed (restartPolicy applies)
      startupProbe:
        httpGet:
          path: /health
          port: 3000
        initialDelaySeconds: 0      # start checking immediately
        periodSeconds:       5      # check every 5 seconds
        failureThreshold:    24     # allow up to 24 × 5 = 120 seconds for startup
        successThreshold:    1

      # Liveness probe: is the container still alive? (detect deadlock, infinite loop)
      # If fails: container is killed and restarted (restartPolicy: Always)
      # Only checked AFTER startupProbe has passed
      livenessProbe:
        httpGet:
          path: /health/live        # lightweight check: "is the process responsive?"
          port: 3000
        initialDelaySeconds: 0
        periodSeconds:       10
        failureThreshold:    3      # 3 consecutive failures → kill and restart
        successThreshold:    1      # 1 success after failure → healthy

      # Readiness probe: should traffic be sent to this container?
      # If fails: Pod removed from Service endpoint list (no traffic)
      # Container NOT killed; just excluded from load balancer rotation
      # Useful: Pod is alive but temporarily unable to serve (warming cache, high load)
      readinessProbe:
        httpGet:
          path: /health/ready       # thorough check: "can I serve traffic?"
          port: 3000
        initialDelaySeconds: 0
        periodSeconds:       5
        failureThreshold:    2      # 2 failures → remove from Service endpoints
        successThreshold:    2      # 2 consecutive successes → add back to endpoints
```

**What each probe endpoint should check:**

```typescript
// NestJS health controller
@Controller('health')
export class HealthController {

  // Startup / Liveness: is the process alive and not deadlocked?
  // FAST: no external dependencies; just check the process is responsive
  @Get('live')
  liveness(): { status: string } {
    return { status: 'ok' };
    // If this endpoint is unreachable or hangs: liveness probe fails → container restart
    // Do NOT check DB/Redis here: if DB is down, you do not want ALL Pods restarted
    // (restarting Pods doesn't fix a DB outage; it makes things worse)
  }

  // Readiness: can this Pod serve production traffic?
  // More thorough: check dependencies required for request handling
  @Get('ready')
  async readiness(): Promise<{ status: string; checks: Record<string, string> }> {
    const checks: Record<string, string> = {};
    let allHealthy = true;

    // Check DB connection pool has available connections
    try {
      await this.db.query('SELECT 1');
      checks.database = 'ok';
    } catch {
      checks.database = 'error';
      allHealthy = false;
    }

    // Check Redis connectivity
    try {
      await this.redis.ping();
      checks.redis = 'ok';
    } catch {
      checks.redis = 'error';
      allHealthy = false;
    }

    if (!allHealthy) {
      // Return 503: readiness probe fails → Pod removed from Service endpoints
      // Other healthy Pods continue serving traffic
      // This Pod: still alive (liveness ok) but not receiving traffic (readiness failing)
      throw new ServiceUnavailableException({ status: 'degraded', checks });
    }

    return { status: 'ok', checks };
  }
}
```

**Probe failure consequences:**
```
Liveness failure:
  Container is killed (SIGTERM → wait terminationGracePeriodSeconds → SIGKILL)
  restartPolicy: Always → container restarted
  CrashLoopBackOff if it keeps failing: 10s, 20s, 40s, 80s, 160s, 300s (capped)

Readiness failure:
  Pod's IP removed from the Endpoints object for all Services that select this Pod
  ALB/NLB (via AWS Load Balancer Controller): deregisters the Pod from target group
  Existing connections: may be mid-request and continue; new connections not routed here
  Pod NOT killed: stays running, stays in the cluster, continues liveness checks
  If readiness recovers: Pod added back to endpoints (without restart)

Startup failure:
  Same as liveness failure (container killed and restarted)
  Purpose: prevent liveness probe from killing a legitimately slow-starting container
  Without startupProbe: livenessProbe starts immediately → kills container before it finishes
                         NestJS startup (load TypeORM, connect to DB): can take 10-30s
  With startupProbe(failureThreshold=24, period=5): allows 120s for startup, then
    liveness takes over with normal periodSeconds=10

terminationGracePeriodSeconds (Pod-level, default: 30s):
  On Pod deletion (or liveness failure):
    Kubernetes sends SIGTERM to container
    Container must finish in-flight requests and exit cleanly
    After terminationGracePeriodSeconds: SIGKILL (force kill)
  NestJS: app.enableShutdownHooks() → onApplicationShutdown() called on SIGTERM
  Set terminationGracePeriodSeconds to: max(expected request duration) × 2
    If P99 request < 5s: set 30s (default is fine)
    If long-running requests (report generation: 60s): set 120s
```

**Q14. "A Deployment rollout is stuck — `kubectl rollout status` says 'Waiting for deployment to finish: 2 out of 3 new replicas have been updated.' It has been 10 minutes. Walk through your diagnosis."**
A:

```
Observation: 2/3 new Pods updated; 1 old Pod remaining; 10 minutes elapsed.
             maxUnavailable=0 means the old Pod won't be terminated until a new one is Ready.
             The stuck new Pod is not becoming Ready.

Step 1: Find the stuck Pod
  kubectl get pods -l app=nestjs-api
  NAME                           READY   STATUS             RESTARTS   AGE
  nestjs-api-7d9f4b8c6-xk9p2    1/1     Running            0          4h    ← old
  nestjs-api-abc123def-q7w2e     1/1     Running            0          8m    ← new, Ready
  nestjs-api-abc123def-r8e3t     1/1     Running            0          7m    ← new, Ready
  nestjs-api-abc123def-s9f4u     0/1     CrashLoopBackOff   4          6m    ← stuck

Step 2: Inspect the stuck Pod
  kubectl describe pod nestjs-api-abc123def-s9f4u

  Look for in Events:
    "Back-off restarting failed container" → container is crashing
    "OOMKilled" → container exceeds memory limit
    "ImagePullBackOff" → cannot pull image (wrong tag, ECR auth issue)
    "Pending" → cannot be scheduled (insufficient node resources)
    "0/4 nodes are available: 4 Insufficient memory" → resource constraint

  Look for in Containers section:
    Last State:  Terminated  Reason: OOMKilled  Exit Code: 137
    Last State:  Terminated  Reason: Error      Exit Code: 1

Step 3: Check container logs (last crash)
  kubectl logs nestjs-api-abc123def-s9f4u --previous
  # --previous: shows logs from the LAST (crashed) container instance

  Common findings:
    "Cannot read property 'x' of undefined" → JS runtime error in new code
    "Error: connect ECONNREFUSED 10.0.0.5:5432" → DB connection failing
    "Invalid environment variable DB_PASSWORD" → missing secret / wrong key name
    "JavaScript heap out of memory" → memory limit too low for new code

Step 4: Check readiness probe failures (if container is Running but not Ready)
  kubectl describe pod nestjs-api-abc123def-s9f4u
  Events:
    Readiness probe failed: HTTP probe failed with statuscode: 503
    → Container is running but /health/ready returns 503
    → DB is unreachable (new version checks DB in readiness; old version did not)
    → Redis is unreachable
    → New endpoint /health/ready was added but returns 404 (not yet deployed in code)

Step 5: Determine action

  If it is a code bug (crash on startup):
    Roll back immediately:
      kubectl rollout undo deployment/nestjs-api
    → Old Pod survives; new Pods scaled back to old ReplicaSet
    → Zero additional downtime (old Pod never terminated)

  If it is a resource limit too low (OOMKilled):
    Patch the Deployment with higher limits (triggers new rollout with correct limits):
      kubectl set resources deployment/nestjs-api \
        --containers=nestjs-api \
        --limits=memory=1Gi

  If it is a missing Secret/ConfigMap (env var not found):
    Create the missing secret:
      kubectl create secret generic new-feature-secret --from-literal=API_KEY=xxx
    Once the secret exists: the pending Pod is recreated automatically

  If it is a readiness probe misconfiguration (endpoint changed path):
    Patch the probe:
      kubectl patch deployment nestjs-api --patch '
        {"spec":{"template":{"spec":{"containers":[{
          "name":"nestjs-api",
          "readinessProbe":{"httpGet":{"path":"/health/ready"}}
        }]}}}}'

  If it is insufficient node resources:
    Cordon one node and drain non-critical Pods to free up space:
      kubectl cordon node-3
      kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data
    OR: add a new node to the cluster (if using managed node group / Cluster Autoscaler)

Prevention:
  Always test the new image locally with the exact same environment variables
  and resource limits before pushing to production.
  Add a pre-deployment smoke test in CI: deploy to a single Pod in a test namespace,
  verify readiness probe passes, then allow the production rollout to proceed.
```

## Quick Reference

| Object | Controller manages | Pod naming | State | restartPolicy |
|---|---|---|---|---|
| Pod | (none — manual) | Random suffix | Ephemeral | Any |
| Deployment | ReplicaSet → Pods | Random suffix | Stateless | Always |
| ReplicaSet | Pods | Random suffix | Stateless | Always |
| StatefulSet | Pods + PVCs | Ordinal (app-0, app-1) | Stateful | Always |
| DaemonSet | Pods (one per node) | Node-name suffix | Per-node | Always |
| Job | Pods (to completion) | Random suffix | Batch | OnFailure / Never |
| CronJob | Jobs → Pods | Schedule-derived | Scheduled batch | OnFailure / Never |

| Probe | Failure action | What to check |
|---|---|---|
| startupProbe | Kill container (restart) | Basic liveness only; allow slow start |
| livenessProbe | Kill container (restart) | Is process responsive? No external deps |
| readinessProbe | Remove from Service endpoints | Can Pod serve traffic? Check DB, Redis |

| StatefulSet guarantee | Mechanism |
|---|---|
| Stable Pod name | Ordinal suffix; persists across restarts |
| Stable DNS | Headless Service; `pod-0.svc.namespace.svc.cluster.local` |
| Stable storage | PVC per Pod; not deleted on Pod delete |
| Ordered updates | Reverse ordinal (N-1 first); wait for Ready before next |

| CronJob setting | Options | When to use each |
|---|---|---|
| concurrencyPolicy | Allow | Independent, idempotent runs |
| concurrencyPolicy | Forbid | Financial batch (NACH, EMI) — never overlap |
| concurrencyPolicy | Replace | Stale runs superseded by new run |
| startingDeadlineSeconds | 60–600 | Tolerate control plane downtime |

| Failure mode | Symptom | Fix |
|---|---|---|
| OOMKilled | exit code 137; CrashLoopBackOff | Increase memory limit; fix memory leak |
| CPU throttling | High P99 latency; CPU usage looks low | Increase CPU limit or request; remove limit |
| Readiness failing | Pod Running but 0/1 Ready; no traffic | Fix /health/ready endpoint or its dependencies |
| Rollout stuck | N-1 new Pods ready; one stuck | kubectl describe pod; check logs --previous |
| StatefulSet PVC not bound | Pod Pending; PVC in Pending | Check StorageClass, PV availability, quota |
| Job not firing | CronJob lastScheduleTime stale | Check startingDeadlineSeconds; control plane health |
| NACH batch overlapping | Duplicate transactions | concurrencyPolicy: Forbid on CronJob |

## The Core Mental Model

```
Every workload object answers two questions: "how many?" and "which ones?":
  Deployment:   how many = spec.replicas (any N identical Pods)
  StatefulSet:  how many = spec.replicas; which ones = Pod-0, Pod-1, ..., Pod-N (identity matters)
  DaemonSet:    how many = one per node (count derived from cluster topology)
  Job:          how many = spec.completions (run until N successful completions)
  CronJob:      how many = one Job per schedule tick (orchestrated by the cron schedule)

The hierarchy of controllers (who creates what):
  CronJob → Job → Pod
  Deployment → ReplicaSet → Pod
  StatefulSet → Pod + PVC (directly; no intermediate ReplicaSet)
  DaemonSet → Pod (directly; one per node)
  Never bypass the hierarchy: manage the top-level object, not Pods directly.

Deployment vs StatefulSet decision rule:
  Ask: "If I delete Pod X and create a new one, does it need to be Pod X specifically?"
    No → any Pod can replace any other → Deployment
    Yes (needs stable name, DNS, or storage) → StatefulSet
  NestJS API: No (any Pod can serve any request) → Deployment
  Kafka broker: Yes (broker-0 must rejoin as broker-0 with its data) → StatefulSet
  PostgreSQL: Yes (single primary must rejoin with its data) → StatefulSet

Liveness vs readiness: the most confused distinction in Kubernetes:
  Liveness: "kill me and restart if I answer false"
    → Check ONLY process health (no external deps)
    → If DB is down: don't fail liveness (restarting won't fix the DB; it makes load worse)
  Readiness: "take me out of rotation if I answer false"
    → Check whether I can serve traffic (DB, Redis, downstream deps)
    → If DB is down: fail readiness (other Pods with working DB connections serve traffic)
    → Container stays alive (can recover when DB returns); just takes no traffic

The restartPolicy contract:
  Deployment/StatefulSet/DaemonSet: restartPolicy MUST be Always
    (these controllers expect Pods to run indefinitely; they manage restarts)
  Job/CronJob: restartPolicy MUST be OnFailure or Never
    (Job controller manages retries via backoffLimit; restartPolicy: Always = infinite loop)
  Kubernetes enforces this: wrong restartPolicy → controller rejects the Pod template

CronJob correctness checklist for financial batch:
  concurrencyPolicy: Forbid (never two NACH runs simultaneously)
  startingDeadlineSeconds: 300 (tolerate brief control plane downtime)
  activeDeadlineSeconds: N (kill the Job if it runs longer than the NACH window)
  backoffLimit: 2 (retry once; alert on any failure)
  Alert on: Job failed, Job runtime approaching activeDeadlineSeconds,
            CronJob missed a scheduled run (lastScheduleTime stale)
```

**Tip for the interview:** Kubernetes workload questions at 5 YOE converge on three depth probes: (1) the Deployment → ReplicaSet → Pod ownership chain and why rollback works instantly — knowing that `kubectl rollout undo` simply scales the old ReplicaSet back up (using an already-existing object with an already-pulled image) rather than creating anything new, and that `revisionHistoryLimit` controls how many old ReplicaSets are retained as rollback targets, demonstrates you understand Kubernetes internals rather than just the CLI commands; (2) the liveness vs readiness probe distinction — explaining that liveness failure kills the container (which is wrong if the problem is an external dependency like the DB being down, since restarting makes things worse by adding connection storms), while readiness failure only removes the Pod from the Service endpoint list (the correct response: other Pods continue serving; this Pod waits for the dependency to recover), is the operational nuance that distinguishes someone who has debugged cascading failures from someone who has only read the documentation; (3) StatefulSet guarantees and when they are necessary — knowing the three guarantees (stable Pod name, stable DNS via headless Service, stable PVC per Pod), why each matters for specific workloads (Kafka needs all three; a stateless NestJS API needs none), and that PVCs are NOT deleted when a StatefulSet Pod is deleted or rescheduled (they persist for the new Pod to find), shows you understand why stateful distributed systems require different primitives than stateless services. The fintech callout: CronJob `concurrencyPolicy: Forbid` is not optional for NACH batch processing — two concurrent NACH batch runs posting the same payment to NPCI produces duplicate transactions, which is a compliance violation and a financial loss; `Forbid` is the single setting that prevents this, and knowing to pair it with `startingDeadlineSeconds` (to tolerate brief control plane unavailability without skipping runs entirely) is the operational depth that shows you have designed scheduled financial workloads in production.
