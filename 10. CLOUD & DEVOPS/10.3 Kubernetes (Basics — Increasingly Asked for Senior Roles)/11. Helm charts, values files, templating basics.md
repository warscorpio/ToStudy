# Helm: Charts, Values Files, and Templating — Interview Q&A (5 YOE Level)

---

## Section 1: What Helm Is and the Problem It Solves

**Q1. What is Helm, what problem does it solve, and what are the core concepts?**
A: Helm is the package manager for Kubernetes. It solves the problem of managing collections of related Kubernetes manifests as a single unit — installing, upgrading, rolling back, and uninstalling them together with a single command, parameterized for different environments. Without Helm, deploying a production NestJS API means maintaining separate YAML files for the Deployment, Service, ConfigMap, HPA, PDB, ServiceAccount, Ingress, and NetworkPolicy — and duplicating or manually diffing them for dev, staging, and production.

**The raw YAML management problem:**

```
Without Helm — "YAML sprawl":
  k8s/
    dev/
      deployment.yaml      ← 80% identical to prod/deployment.yaml
      service.yaml         ← identical
      configmap.yaml       ← different values
      ingress.yaml         ← different host
    staging/
      deployment.yaml      ← 80% identical; 2 replicas
      service.yaml         ← identical
      configmap.yaml       ← different values
      ingress.yaml         ← different host
    production/
      deployment.yaml      ← 5 replicas; different image tag
      service.yaml         ← identical
      configmap.yaml       ← production values
      ingress.yaml         ← production host
      hpa.yaml             ← only in production
      pdb.yaml             ← only in production
      networkpolicy.yaml   ← only in production

  Problems:
    A change to the Deployment (new readiness probe path) must be made
    in 3 files manually. Drift between environments is inevitable.
    "What is actually running in production?" requires diffing files.
    No transactional installs: if ingress.yaml fails to apply, the
    deployment is partially updated with no automatic cleanup.
    No history: kubectl apply leaves no record of what changed and when.

With Helm — single chart, multiple value overrides:
  charts/nestjs-api/         ← one chart
    Chart.yaml               ← chart metadata
    values.yaml              ← defaults (lowest priority)
    templates/
      deployment.yaml        ← parameterized; used for all envs
      service.yaml
      configmap.yaml
      ingress.yaml
      hpa.yaml
      pdb.yaml
      networkpolicy.yaml
      _helpers.tpl           ← reusable template functions

  values/
    dev.yaml                 ← dev overrides (2 keys different)
    staging.yaml             ← staging overrides
    production.yaml          ← production overrides

  Deploy to dev:
    helm upgrade --install nestjs-api ./charts/nestjs-api \
      -f values/dev.yaml -n dev

  Deploy to production:
    helm upgrade --install nestjs-api ./charts/nestjs-api \
      -f values/production.yaml -n production \
      --set image.tag=sha256-abc123

  One change to the chart template propagates to all environments.
  No drift. Full history. Transactional installs.
```

**Core Helm concepts:**

```
Chart:
  A package of Kubernetes manifest templates + metadata + default values.
  The installable unit. Analogous to a Debian package or npm package.
  Can contain: templates/, values.yaml, Chart.yaml, charts/ (dependencies),
               NOTES.txt, _helpers.tpl, crds/.

Release:
  A specific installation of a chart into a Kubernetes namespace.
  One chart can have multiple releases in different namespaces or with
  different names: helm install api-v1 ./chart and helm install api-v2 ./chart
  are two separate releases from the same chart.
  Release state (name, namespace, revision, values, manifest) is stored
  as a Kubernetes Secret in the release namespace.

Revision:
  Every helm upgrade creates a new revision (integer, incrementing).
  Revision 1 = initial install. Revision 2 = first upgrade. And so on.
  helm rollback nestjs-api 3 → restores the manifests and values from revision 3.
  Revisions are stored as Secrets: sh.helm.release.v1.nestjs-api.v1, .v2, .v3...

Repository:
  A server that hosts packaged charts (.tgz files + index.yaml).
  Public: https://charts.helm.sh/stable, https://charts.bitnami.com/bitnami
  Private: ECR (oci://), ChartMuseum, Nexus, Artifactory, GitHub Pages.
  helm repo add bitnami https://charts.bitnami.com/bitnami
  helm install redis bitnami/redis

Values:
  The configuration parameters that customize a chart for an environment.
  Provided via values.yaml (defaults), -f overrides files, and --set flags.
  Values flow into templates via the .Values object.

Template:
  A Go template file that Helm renders into a Kubernetes manifest.
  Uses Go's text/template syntax plus the Sprig function library.
  Helm adds its own functions on top: include, required, tpl, lookup, etc.
```

**Q2. What is the structure of a Helm chart directory, and what does each file do?**
A: A Helm chart is a directory with a prescribed structure. Helm requires `Chart.yaml` and `templates/` at minimum; everything else is conventional but widely adopted.

**Complete chart directory structure:**

```
charts/nestjs-api/
├── Chart.yaml              ← required: chart metadata and dependencies
├── values.yaml             ← required by convention: default values
├── values.schema.json      ← optional: JSON Schema validation for values
├── .helmignore             ← optional: files to exclude from packaging
├── README.md               ← optional: documentation
├── NOTES.txt               ← optional: post-install user instructions
│
├── templates/              ← required: Kubernetes manifest templates
│   ├── _helpers.tpl        ← convention: named templates (partials)
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── serviceaccount.yaml
│   ├── configmap.yaml
│   ├── ingress.yaml
│   ├── hpa.yaml
│   ├── pdb.yaml
│   ├── networkpolicy.yaml
│   └── NOTES.txt          ← optional: rendered and shown after install
│
├── charts/                 ← optional: bundled chart dependencies
│   └── postgresql/         ← a sub-chart (if not using helm dependency update)
│
└── crds/                   ← optional: Custom Resource Definitions
    └── myresource.yaml     ← installed before templates; not templated
```

**`Chart.yaml` — the chart manifest:**

```yaml
apiVersion: v2          # v2 for Helm 3; v1 for legacy Helm 2
name: nestjs-api
description: NestJS API service for the payments platform
type: application       # "application" (installable) or "library" (reusable templates only)
version: 1.4.2          # Chart version — SemVer; increment on any chart change
appVersion: "2.4.1"     # Version of the application being deployed (informational)
                        # Often overridden with image.tag at deploy time

keywords:
  - nestjs
  - api
  - payments

maintainers:
  - name: platform-team
    email: platform@example.com

dependencies:           # Sub-charts (helm dependency update downloads these)
  - name: postgresql
    version: "13.2.x"
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled    # only install if values.postgresql.enabled=true
    tags:
      - database

  - name: redis
    version: "18.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled

# Chart.yaml version vs appVersion:
#   version: the chart's own version. Change this when templates or values change.
#   appVersion: the version of the software packaged. Informational only.
#   A template fix (no app change): bump version (1.4.2 → 1.4.3); appVersion unchanged.
#   A new app release: bump appVersion ("2.4.1" → "2.5.0"); bump version too (1.4.3 → 1.5.0).
```

**`NOTES.txt` — post-install instructions:**

```
{{- $fullName := include "nestjs-api.fullname" . }}
NestJS API has been deployed successfully!

Release:   {{ .Release.Name }}
Namespace: {{ .Release.Namespace }}
Version:   {{ .Chart.AppVersion }}
Image:     {{ .Values.image.repository }}:{{ .Values.image.tag }}

To verify the deployment:
  kubectl rollout status deployment/{{ $fullName }} -n {{ .Release.Namespace }}

To get the application URL:
{{- if .Values.ingress.enabled }}
  https://{{ (index .Values.ingress.hosts 0).host }}
{{- else }}
  kubectl port-forward svc/{{ $fullName }} 8080:{{ .Values.service.port }} \
    -n {{ .Release.Namespace }}
  http://localhost:8080
{{- end }}

To check logs:
  kubectl logs -l app.kubernetes.io/name=nestjs-api \
    -n {{ .Release.Namespace }} --tail=50 -f
```

## Section 2: Values Files — Structure, Hierarchy, and Patterns

**Q3. How does the Helm values hierarchy work, and what is the precedence order?**
A: Helm merges values from multiple sources. When the same key appears in multiple sources, the highest-priority source wins. Understanding this hierarchy is essential for correctly structuring multi-environment deployments.

**The values precedence chain (lowest to highest):**

```
Priority 1 (lowest): values.yaml in the chart
  The chart's built-in defaults. Every configurable parameter should have
  a sensible default here. Enables helm install without any -f flags for
  development/testing.

Priority 2: values.yaml files from parent charts
  If this chart is a sub-chart, the parent chart's values.yaml can
  provide defaults for it.

Priority 3: -f / --values flags (left to right)
  helm install ... -f base.yaml -f production.yaml
  → production.yaml overrides base.yaml, which overrides chart defaults.
  Multiple -f flags: rightmost wins on key collision.

Priority 4 (highest): --set, --set-string, --set-json, --set-file flags
  --set image.tag=sha256-abc123
  → Overrides everything else for that key.
  --set flags are processed after all -f files.
  Multiple --set flags: last one wins on key collision.

Merge semantics — deep vs shallow:
  Values files are deep-merged (recursively):
    values.yaml:        production.yaml:        Result:
    image:              image:                  image:
      repository: ecr     tag: sha256-abc         repository: ecr
      tag: latest                                 tag: sha256-abc
                                                  (both keys present)

  --set flag for a map key does NOT merge — it replaces the entire subtree
  if you use the nested syntax incorrectly.

  WRONG — replaces entire ingress.annotations map:
    --set "ingress.annotations={kubernetes.io/ingress.class: alb}"
    → ingress.annotations is now a string, not a map

  CORRECT — sets one annotation key:
    --set "ingress.annotations.kubernetes\\.io/ingress\\.class=alb"
    → dot in key must be escaped with \\. in --set syntax

  For complex structures: always use -f, not --set.
  --set is for simple scalar overrides (image tag, replica count).
```

**Q4. What is `values.schema.json`, and why should every production chart have one?**
A: `values.schema.json` is a JSON Schema document placed at the root of a chart that Helm validates all provided values against before rendering any templates. It catches misconfigured values at `helm install`/`upgrade` time — before bad values reach the cluster — rather than at runtime when a misconfigured Pod fails to start.

**Values schema for the NestJS API chart:**

```json
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "title": "nestjs-api values",
  "type": "object",
  "required": ["image"],
  "additionalProperties": true,

  "properties": {
    "image": {
      "type": "object",
      "required": ["repository", "tag"],
      "properties": {
        "repository": {
          "type": "string",
          "minLength": 1,
          "description": "ECR repository URI"
        },
        "tag": {
          "type": "string",
          "minLength": 1,
          "description": "Image tag or digest. Must not be empty in production.",
          "not": { "enum": ["latest"] }
        },
        "pullPolicy": {
          "type": "string",
          "enum": ["Always", "IfNotPresent", "Never"]
        }
      }
    },

    "replicaCount": {
      "type": "integer",
      "minimum": 1,
      "maximum": 100
    },

    "resources": {
      "type": "object",
      "properties": {
        "requests": {
          "type": "object",
          "properties": {
            "cpu":    { "type": "string", "pattern": "^[0-9]+(m|\\.[0-9]+)?$" },
            "memory": { "type": "string", "pattern": "^[0-9]+(Ki|Mi|Gi|Ti)$" }
          }
        },
        "limits": {
          "type": "object",
          "properties": {
            "cpu":    { "type": "string", "pattern": "^[0-9]+(m|\\.[0-9]+)?$" },
            "memory": { "type": "string", "pattern": "^[0-9]+(Ki|Mi|Gi|Ti)$" }
          }
        }
      }
    },

    "config": {
      "type": "object",
      "required": ["LOG_LEVEL", "NODE_ENV"],
      "properties": {
        "LOG_LEVEL": {
          "type": "string",
          "enum": ["debug", "info", "warn", "error"]
        },
        "NODE_ENV": {
          "type": "string",
          "enum": ["development", "staging", "production"]
        },
        "PORT": {
          "type": "string",
          "pattern": "^[0-9]+$"
        }
      }
    },

    "podDisruptionBudget": {
      "type": "object",
      "properties": {
        "enabled": { "type": "boolean" },
        "minAvailable": {
          "type": "integer",
          "minimum": 1
        }
      },
      "if": { "properties": { "enabled": { "const": true } } },
      "then": { "required": ["minAvailable"] }
    },

    "autoscaling": {
      "type": "object",
      "properties": {
        "enabled": { "type": "boolean" },
        "minReplicas": { "type": "integer", "minimum": 1 },
        "maxReplicas": { "type": "integer", "minimum": 1 },
        "targetCPUUtilizationPercentage": {
          "type": "integer",
          "minimum": 1,
          "maximum": 100
        }
      },
      "if": { "properties": { "enabled": { "const": true } } },
      "then": {
        "required": ["minReplicas", "maxReplicas"],
        "properties": {
          "minReplicas": true,
          "maxReplicas": true
        },
        "if": {
          "required": ["minReplicas", "maxReplicas"]
        },
        "then": {
          "properties": {
            "maxReplicas": {
              "description": "maxReplicas must be >= minReplicas"
            }
          }
        }
      }
    }
  }
}
```

**Schema validation in action:**

```bash
# Attempt to install with image.tag=latest (forbidden by schema):
helm install nestjs-api ./charts/nestjs-api \
  --set image.tag=latest \
  -n production

# Error output:
# Error: values don't meet the specifications of the schema(s) in the following chart(s):
# nestjs-api:
# - image.tag: Does not match pattern '^(?!latest).*$'
#   (or: Must not be one of ["latest"])

# Attempt to install with invalid LOG_LEVEL:
helm install nestjs-api ./charts/nestjs-api \
  --set config.LOG_LEVEL=verbose \
  -n production

# Error: config.LOG_LEVEL: config.LOG_LEVEL must be one of the following: "debug", "info", "warn", "error"

# Attempt to install with PDB enabled but minAvailable not set:
helm install nestjs-api ./charts/nestjs-api \
  --set podDisruptionBudget.enabled=true \
  -n production

# Error: podDisruptionBudget: minAvailable is required when enabled is true

# These errors fire at helm install/upgrade time, before any manifest is applied.
# Without schema: the template renders, kubectl applies the manifest,
# the Pod starts (or fails to start), and the error appears minutes later.
# With schema: the error appears in the CI pipeline before the cluster is touched.
```

## Section 3: Templating — Go Templates, Sprig, and Helm Functions

**Q5. How does Go template syntax work in Helm, and what are the most important constructs?**
A: Helm templates use Go's `text/template` package syntax. Every template file is rendered by evaluating `{{ }}` delimited actions against a data object (`.`) that contains the release context, values, chart metadata, and capabilities. The output of rendering is a Kubernetes YAML manifest.

**The template data object (`.`):**

```
.Values     → merged values from all sources (values.yaml + -f files + --set)
.Release    → information about the current release
  .Release.Name       → "nestjs-api" (the release name)
  .Release.Namespace  → "production"
  .Release.IsInstall  → true on first install; false on upgrade
  .Release.IsUpgrade  → false on install; true on upgrade
  .Release.Revision   → 1 on install; increments on each upgrade
  .Release.Service    → "Helm"

.Chart      → contents of Chart.yaml
  .Chart.Name         → "nestjs-api"
  .Chart.Version      → "1.4.2"
  .Chart.AppVersion   → "2.4.1"

.Files      → access to non-template files in the chart directory
  .Files.Get "config/app.yaml"  → returns file contents as string
  .Files.AsConfig               → renders files as ConfigMap data
  .Files.AsSecrets              → renders files as base64-encoded Secret data

.Capabilities → Kubernetes cluster capabilities
  .Capabilities.KubeVersion.Major  → "1"
  .Capabilities.KubeVersion.Minor  → "29"
  .Capabilities.APIVersions.Has "networking.k8s.io/v1"  → true/false

.Template   → current template metadata
  .Template.Name     → "nestjs-api/templates/deployment.yaml"
  .Template.BasePath → "nestjs-api/templates"
```

**Core Go template syntax:**

```
{{ expression }}        → output the result (HTML-escaped by default in html/template;
                          Helm uses text/template — no escaping)
{{- expression }}       → trim whitespace BEFORE this action (the - eats preceding newlines/spaces)
{{ expression -}}       → trim whitespace AFTER this action
{{- expression -}}      → trim whitespace on both sides

{{ /* comment */ }}     → template comment; not in rendered output

{{ if condition }}      → conditional block
{{ else if condition }}
{{ else }}
{{ end }}

{{ range .Values.list }}  → iterate over a list; . becomes each element
  - {{ . }}
{{ end }}

{{ range $key, $value := .Values.map }}  → iterate over a map
  {{ $key }}: {{ $value }}
{{ end }}

{{ with .Values.ingress }}  → if .Values.ingress is not empty/nil/false/zero:
  host: {{ .hosts }}        → . is now .Values.ingress (scoped)
{{ end }}

{{ $var := expression }}    → local variable assignment
{{ $var }}                  → use variable

{{ define "mytemplate" }}   → define a named template (usually in _helpers.tpl)
  content
{{ end }}

{{ include "mytemplate" . }}  → render a named template and include output
                               (use include, not template, because include
                                can be piped to other functions)
{{ template "mytemplate" . }} → render a named template (cannot be piped)

Pipelines — chain functions:
  {{ .Values.name | upper | quote }}
  → .Values.name passed to upper(), result passed to quote()
  → output: "MY-API-NAME"

  {{ .Values.replicaCount | default 1 }}
  → if replicaCount is nil/empty/0: use 1
```

**Whitespace control — the most common source of YAML rendering bugs:**

```
Without whitespace control:
  {{ if .Values.ingress.enabled }}
  ingress: true
  {{ end }}
  Renders as:
    (blank line)
    ingress: true
    (blank line)
  The blank lines may be harmless or may break multi-document YAML.

With {{- and -}}:
  {{- if .Values.ingress.enabled }}
  ingress: true
  {{- end }}
  Renders as:
    ingress: true
  No blank lines.

Rules:
  {{- trims all whitespace (spaces, tabs, newlines) BEFORE the action.
  -}} trims all whitespace AFTER the action (until the next non-whitespace).
  Use {{- for action-only lines (if, end, range, define, with) to avoid
  blank lines in output. Do NOT use - on lines that produce output you want
  to keep.

Common mistake — trimming intended indentation:
  containers:
    {{- range .Values.extraContainers }}
    - name: {{ .name -}}   ← -}} trims newline after .name → next line is concatenated
      image: {{ .image }}  ← this line is appended directly to the name value
    {{- end }}
  Result: "- name: sidecarimage: sidecar:latest"  ← broken YAML

  Fix: use {{- only on lines that produce no output:
  containers:
    {{- range .Values.extraContainers }}
    - name: {{ .name }}   ← no trailing -}}; newline preserved
      image: {{ .image }}
    {{- end }}
```

**Q6. What is `_helpers.tpl`, what named templates does it conventionally define, and why is `include` preferred over `template`?**
A: `_helpers.tpl` (the leading underscore means Helm does not render it as a manifest) is a convention file for defining reusable named templates — shared across all templates in the chart. Its primary job is standardizing labels, names, and selectors so they are computed identically everywhere.

**Standard `_helpers.tpl` for a NestJS API chart:**

```
{{/*
Expand the name of the chart.
*/}}
{{- define "nestjs-api.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{/*
Create a default fully qualified app name.
We truncate at 63 chars because some Kubernetes name fields are limited to this.
If the release name contains the chart name, we use the release name directly.
*/}}
{{- define "nestjs-api.fullname" -}}
{{- if .Values.fullnameOverride }}

**Why `include` over `template`:**

```
{{ template "nestjs-api.labels" . }}
  → Renders the named template and inserts the output.
  → Output cannot be further processed.
  → Cannot be piped: {{ template "nestjs-api.labels" . | nindent 4 }} → INVALID SYNTAX

{{ include "nestjs-api.labels" . }}
  → Renders the named template and returns it as a string.
  → Can be piped to any string function.
  → {{ include "nestjs-api.labels" . | nindent 4 }} → VALID; indents the output

This matters because Kubernetes YAML requires correct indentation.
Named templates that produce multiple lines must be indented relative
to their insertion point in the parent template.

Example — the difference in output:

  Template content (_helpers.tpl):
    {{- define "nestjs-api.labels" -}}
    helm.sh/chart: nestjs-api-1.4.2
    app.kubernetes.io/name: nestjs-api
    app.kubernetes.io/instance: my-release
    {{- end }}

  Using template (wrong):
    metadata:
      labels:
    {{ template "nestjs-api.labels" . }}

  Rendered output (broken indentation):
    metadata:
      labels:
    helm.sh/chart: nestjs-api-1.4.2          ← at column 0 — invalid YAML
    app.kubernetes.io/name: nestjs-api
    app.kubernetes.io/instance: my-release

  Using include with nindent (correct):
    metadata:
      labels:
        {{- include "nestjs-api.labels" . | nindent 8 }}

  Rendered output (correct):
    metadata:
      labels:
        helm.sh/chart: nestjs-api-1.4.2      ← 8 spaces indent
        app.kubernetes.io/name: nestjs-api
        app.kubernetes.io/instance: my-release

  nindent N: adds N spaces of indentation to every line AND adds a
             leading newline (so the first line is also indented correctly).
  indent N:  adds N spaces to every line but NO leading newline.
  Use nindent when the template content starts a new line.
  Use indent when the content continues on the current line.
```

**Q7. What are the key Sprig and Helm-specific template functions, and when do you use them?**
A: Helm exposes the full Sprig library (100+ functions for string manipulation, math, crypto, date/time, lists, dicts, encoding, and more) plus Helm-specific functions (`include`, `required`, `tpl`, `lookup`, `toYaml`, `fromYaml`). Knowing the right function prevents reinventing logic in templates.

**Essential functions with production examples:**

```
─── String functions ──────────────────────────────────────────────────────

quote / squote
  {{ .Values.config.LOG_LEVEL | quote }}   → "warn"
  {{ .Values.config.LOG_LEVEL | squote }}  → 'warn'
  Use: wrap all string values in ConfigMap data to prevent YAML type coercion.
  Without quote: LOG_LEVEL: warn (string — OK)
                 PORT: 3000 (integer — may fail string comparison in app)
  With quote:    PORT: "3000" (explicitly string — safe)

upper / lower / title
  {{ .Chart.Name | upper }}     → NESTJS-API
  {{ .Release.Name | lower }}   → my-release

trim / trimSuffix / trimPrefix
  {{ "  my-value  " | trim }}          → my-value
  {{ "nestjs-api-" | trimSuffix "-" }} → nestjs-api

replace
  {{ .Chart.Version | replace "+" "_" }}   → 1.4.2 (no + in this version)
  → Used in chart label to make version safe for label values.

contains / hasPrefix / hasSuffix
  {{- if contains "sha256" .Values.image.tag }}
  → detect digest vs tag format

trunc
  {{ printf "%s-%s" .Release.Name .Chart.Name | trunc 63 }}
  → truncate to 63 chars (Kubernetes name limit)

printf
  {{ printf "%s:%s" .Values.image.repository .Values.image.tag }}
  → string formatting (like fmt.Sprintf)

─── Type conversion ───────────────────────────────────────────────────────

toString
  {{ .Values.service.port | toString }}
  → Converts integer to string. Required when the port value must be a
    string in the template output.

int / int64 / float64
  {{ .Values.replicaCount | int }}
  → Ensures the value is an integer (prevents "1" string being used where int needed).

─── Default and required ──────────────────────────────────────────────────

default
  {{ .Values.image.tag | default "latest" }}
  → if image.tag is nil, empty string, 0, or false: use "latest"
  → Use to provide fallbacks for optional values.

required
  {{ required "image.tag is required" .Values.image.tag }}
  → if image.tag is nil or empty string: fail with the given error message
  → Use for values that have no sensible default and MUST be provided.
  → Combined with empty string in values.yaml: forces the caller to set it.

  values.yaml:    image.tag: ""
  template:       image: {{ required "image.tag must be set" .Values.image.tag }}
  helm install without --set image.tag=...: Error: image.tag must be set

─── YAML serialization ────────────────────────────────────────────────────

toYaml
  {{ .Values.resources | toYaml | nindent 12 }}
  → Serializes a Go map/slice to YAML string.
  → The most common function in Helm templates — used for any block value
    that should be pasted verbatim from values.yaml.

  Template:
    resources:
      {{- toYaml .Values.resources | nindent 10 }}

  values.yaml:
    resources:
      requests:
        cpu: 300m
        memory: 256Mi

  Output:
    resources:
      requests:
        cpu: 300m
        memory: 256Mi

fromYaml / fromJson
  {{- $parsed := .Files.Get "config/app.yaml" | fromYaml }}
  → Parse a YAML string into a Go map for further processing.

toJson / fromJson
  {{ .Values | toJson }}
  → Serialize values to JSON (useful for debugging).

─── Conditional and logic ─────────────────────────────────────────────────

empty
  {{- if not (empty .Values.podAnnotations) }}
  → true if the value is empty (nil, "", 0, false, [], {})
  → Use instead of eq .Values.x "" for multi-type emptiness check.

and / or / not
  {{- if and .Values.ingress.enabled .Values.ingress.tls }}
  → logical AND; both must be truthy

eq / ne / lt / le / gt / ge
  {{- if eq .Values.config.NODE_ENV "production" }}
  → equality check
  {{- if gt .Values.replicaCount 1 }}
  → greater than (works on integers)

ternary
  {{ .Values.ingress.enabled | ternary "enabled" "disabled" }}
  → if true: "enabled"; else: "disabled"
  → Clean one-liner for simple conditional values.

─── List and dict functions ───────────────────────────────────────────────

list
  {{- $ports := list 3000 3001 9229 }}
  → creates a list

first / last / rest
  {{ list 1 2 3 | first }}   → 1
  {{ list 1 2 3 | last }}    → 3

has
  {{- if has "production" (list "staging" "production") }}

dict
  {{- $labels := dict "app" "nestjs-api" "version" "v2" }}

keys / values
  {{- range keys .Values.config | sortAlpha }}

merge / mergeOverwrite
  {{- $merged := merge .Values.podAnnotations (dict "custom/annotation" "value") }}
  → merge two dicts; merge: first value wins; mergeOverwrite: second wins

─── Helm-specific functions ───────────────────────────────────────────────

tpl
  {{ tpl .Values.someTemplateString . }}
  → Renders a string value AS a template (allows values.yaml to contain
    template expressions).
  Example:
    values.yaml:
      nameOverride: "{{ .Release.Name }}-api"
    template:
      name: {{ tpl .Values.nameOverride . }}
    → evaluates the template expression in the value

  WARNING: tpl is a security risk if values come from untrusted sources.
  A malicious value can execute arbitrary template code. Use only when
  the values source is fully trusted.

lookup
  {{- $existing := lookup "v1" "ConfigMap" .Release.Namespace "nestjs-api-config" }}
  {{- if $existing }}
    existing-hash: {{ $existing.data | toYaml | sha256sum }}

  → Returns empty dict {} if not found.

    helm install/upgrade against a live cluster.
  → Use for: referencing existing cluster resources, implementing idempotent
             logic based on current cluster state.

b64enc / b64dec
  {{ "my-password" | b64enc }}   → bXktcGFzc3dvcmQ=
  → Required for Secret data values (must be base64-encoded in manifests).

sha256sum
  {{ .Values.config | toYaml | sha256sum }}
  → Primary use: checksum annotation for triggering Pod restarts on ConfigMap change.
  → Include in Deployment pod template annotations:
    checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}

**Q9. What are the most common Helm templating mistakes and how do you debug them?**
A: Most Helm template bugs fall into four categories: whitespace errors (produces invalid YAML), scope errors (wrong `.` context inside `range`/`with`), type coercion errors (integer where string expected or vice versa), and missing values (nil pointer in template evaluation).

**Debugging toolkit:**

```bash
# Primary debugging command: render templates without installing
helm template nestjs-api ./charts/nestjs-api \
  -f values/production.yaml \
  --set image.tag=sha256-abc123 \
  --namespace production \
  > rendered.yaml

# Inspect the rendered output:
cat rendered.yaml
# Look for: blank lines in unexpected places, wrong indentation,
#           literal "<nil>" or "<no value>" in output, missing sections

# Validate rendered YAML is syntactically correct:
cat rendered.yaml | python3 -m py_compile /dev/stdin  # if Python available
# Or: pipe to a YAML linter:
helm template ... | yamllint -

# Validate rendered manifests against Kubernetes API schemas:
helm template ... | kubeval --strict
helm template ... | kubeconformist -  # kubeconformist is more current

# Dry-run against a live cluster (validates against actual API server):
helm upgrade --install nestjs-api ./charts/nestjs-api \
  -f values/production.yaml \
  --set image.tag=sha256-abc123 \
  --namespace production \
  --dry-run

# Debug single template file:
helm template nestjs-api ./charts/nestjs-api \
  -f values/production.yaml \
  -s templates/deployment.yaml    # render only this template

# See computed values (what .Values contains after merging):
helm template nestjs-api ./charts/nestjs-api \
  -f values/production.yaml \
  --set image.tag=sha256-abc123 \
  --debug 2>&1 | head -50
# --debug dumps the merged values before rendering

# Lint the chart for common issues:
helm lint ./charts/nestjs-api -f values/production.yaml
# Checks: Chart.yaml validity, template syntax, values schema
```

**Common mistake 1: `<no value>` or `<nil>` in output**

```
Symptom:
  image: ecr.amazonaws.com/nestjs-api:<no value>

Cause:
  {{ .Values.image.tag }} where .Values.image.tag is not set.
  Go templates render nil as "<no value>" by default.

Fix A: Use required to fail fast:
  image: {{ required "image.tag must be set" .Values.image.tag }}

Fix B: Use default:
  image: {{ .Values.image.tag | default "latest" }}

Fix C: Check in values.yaml that the key exists (even as empty string):
  image:
    tag: ""   ← key exists; value is empty string; required will catch it

Prevention: helm lint catches some of these; values.schema.json catches more.
```

**Common mistake 2: wrong scope inside `range` and `with`**

```
Template:
  {{- range .Values.extraContainers }}
  - name: {{ .name }}
    image: {{ .image }}
    env:
      - name: RELEASE_NAME
        value: {{ .Release.Name }}   ← BUG: . is now the range element, not root
  {{- end }}

Symptom:
  helm template output: value: <no value>
  .Release is not accessible because . has been rebound to the current
  range element (an extraContainer dict).

Fix: capture root context before entering range:
  {{- $root := . }}
  {{- range .Values.extraContainers }}
  - name: {{ .name }}
    image: {{ .image }}
    env:
      - name: RELEASE_NAME
        value: {{ $root.Release.Name }}   ← access root via $root
  {{- end }}

  OR: use $.Release.Name ($ always refers to the root context):
  {{- range .Values.extraContainers }}
  - name: {{ .name }}
    image: {{ .image }}
    env:
      - name: RELEASE_NAME
        value: {{ $.Release.Name }}   ← $ = root; always valid
  {{- end }}

Same issue with with:
  {{- with .Values.ingress }}
  # . is now .Values.ingress
  host: {{ .hosts }}        ← OK: .hosts = .Values.ingress.hosts
  release: {{ $.Release.Name }}  ← need $ for root context
  {{- end }}
```

**Common mistake 3: integer vs string type coercion**

```
values.yaml:
  service:
    port: 80   ← YAML integer

template:
  port: {{ .Values.service.port }}
  → Renders as: port: 80  (integer — correct for ports)

template:
  - containerPort: "{{ .Values.service.port }}"
  → Renders as: - containerPort: "80"  (string in quotes — wrong; port must be integer)

template:
  env:
    - name: PORT
      value: {{ .Values.service.port }}
  → Renders as: value: 80  (integer — wrong; env var value must be string in K8s)
  → Fix: value: {{ .Values.service.port | quote }}  → value: "80"

Rules:
  Kubernetes fields that are integers (containerPort, replicas): use {{ .Values.x }}
  Kubernetes fields that are strings (env.value, ConfigMap data): use {{ .Values.x | quote }}
  Go template automatically decides based on the Go type; YAML decides based on context.
  When in doubt: quote it and check with helm template | yamllint.
```

**Common mistake 4: HPA + replicas conflict**

```
Template (wrong):
  spec:
    replicas: {{ .Values.replicaCount }}   ← always set replicas

values.yaml:
  replicaCount: 2
  autoscaling:
    enabled: true
    minReplicas: 3
    maxReplicas: 10

What happens:
  HPA scales up to 5 replicas based on CPU.
  Developer runs: helm upgrade ... (no changes to values)
  Helm applies the Deployment manifest with replicas: 2.
  Kubernetes sets replicas to 2. HPA's current count is overwritten.
  Brief period of reduced capacity. HPA scales back up.
  Every helm upgrade against a running auto-scaled Deployment causes
  a capacity dip.

Fix (correct — already shown in deployment.yaml above):
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  When autoscaling is enabled: Helm does not set replicas.
  HPA owns the replica count. Helm upgrades don't interfere.
```

## Section 5: Helm Release Management and CI/CD

**Q10. How do you structure a Helm-based CI/CD pipeline, and what are the key `helm upgrade` flags for production?**
A: A production Helm deploy pipeline has four concerns: idempotency (install or upgrade with one command), safety (atomic installs with rollback on failure), auditability (change-cause annotations, release history), and speed (cache dependencies, skip unnecessary operations).

**The `helm upgrade --install` pattern:**

```bash
#!/usr/bin/env bash
set -euo pipefail

RELEASE_NAME="nestjs-api"
CHART_PATH="./charts/nestjs-api"
NAMESPACE="production"
VALUES_FILE="values/production.yaml"
IMAGE_TAG="${GIT_SHA}"   # set by CI environment

# Update chart dependencies (sub-charts: postgresql, redis)
helm dependency update "${CHART_PATH}"

# Set change-cause annotation before upgrading
kubectl annotate deployment/${RELEASE_NAME} \
  kubernetes.io/change-cause="${IMAGE_TAG}: ${DEPLOY_REASON:-CI deploy}" \
  -n ${NAMESPACE} --overwrite 2>/dev/null || true
# (ignore error if deployment doesn't exist yet — first install)

# Deploy
helm upgrade "${RELEASE_NAME}" "${CHART_PATH}" \
  --install \                     # create release if it doesn't exist
  --namespace "${NAMESPACE}" \
  --create-namespace \            # create namespace if it doesn't exist
  --values "${VALUES_FILE}" \
  --set "image.tag=${IMAGE_TAG}" \
  --set "image.repository=${ECR_URI}" \
  --atomic \                      # roll back automatically if upgrade fails
  --timeout 10m \                 # wait up to 10 minutes for Pods to be ready
  --cleanup-on-fail \             # delete newly created resources on failure
  --history-max 10 \              # keep only 10 revisions
  --wait \                        # wait for all Pods to be Ready before returning
  --wait-for-jobs \               # also wait for Jobs to complete
  --description "${IMAGE_TAG}: ${DEPLOY_REASON:-CI deploy}"
  # --description sets the release description visible in helm history

echo "Deployment complete:"
helm history "${RELEASE_NAME}" -n "${NAMESPACE}" | tail -3
```

**Key flags explained:**

```
--install:
  Makes helm upgrade idempotent: install on first run, upgrade on subsequent runs.
  Without it: helm upgrade fails if the release doesn't exist yet.
  With it: a single command handles both initial deploy and updates.

--atomic:
  If the upgrade fails (Pods don't become Ready within --timeout):
    Automatically rolls back to the previous revision.
    Ensures the cluster never gets stuck in a partially-upgraded state.
  Without --atomic and a failed upgrade:
    Some Pods run the new version; some run the old version.
    The release is in a "failed" state; next helm upgrade must use --force.
  With --atomic: failure = automatic rollback = previous state restored.

--wait:
  helm upgrade returns only after all Pods, PVCs, Services, and minimum
  available Pods are in a Ready state.
  Without --wait: helm upgrade returns as soon as manifests are applied.
    The CI pipeline sees "success" but Pods may still be starting or crashing.
  With --wait: CI pipeline sees "success" only when the app is actually running.
    Combined with --atomic: CI sees "failure" if Pods don't start, and the
    cluster is rolled back. Correct failure detection in the pipeline.

--timeout 10m:
  How long to wait for --wait conditions to be met.
  Should be set to: (max Pod startup time) × (maxSurge + 1) + buffer.
  For a 5-replica Deployment with maxSurge=1 and 2-minute startup:
    ~12 minutes to replace all 5 Pods one at a time.
    Set --timeout 15m.
  Default is 5m — too short for most production services with health checks.

--cleanup-on-fail:
  If the upgrade fails, delete any NEW resources created during this upgrade
  (e.g., a new CRD, a new ConfigMap) before rolling back.
  Prevents orphaned resources from cluttering the namespace.

--history-max 10:
  Limit the number of revisions retained.
  Each revision is stored as a Secret. At scale (many releases, many revisions):
    secrets accumulate → etcd size grows → API list operations slow down.
  Default: 10. Set explicitly to document intent and prevent unbounded growth.

--create-namespace:
  Creates the namespace if it doesn't exist.
  Safe to include always: a no-op if the namespace already exists.

--dry-run:
  Renders templates and shows what WOULD be applied without touching the cluster.
  Different from helm template: --dry-run sends to the API server for validation
  (checks that resource types exist, field names are valid) but does not persist.
  Use in CI for PRs: validate changes before merge, without deploying.
```

**Helm rollback in production:**

```bash
# View release history:
helm history nestjs-api -n production
# REVISION  UPDATED              STATUS    CHART          APP VERSION  DESCRIPTION
# 1         2026-08-01 09:00:00  deployed  nestjs-api-1.4.0  2.3.0    initial install
# 2         2026-08-05 14:23:00  deployed  nestjs-api-1.4.1  2.3.1    sha256-abc: fix memory leak
# 3         2026-08-07 09:15:00  failed    nestjs-api-1.4.2  2.4.0    sha256-xyz: payment feature
#   ^ --atomic already rolled back to revision 2, but revision 3 is recorded as failed

# Manual rollback to specific revision:
helm rollback nestjs-api 2 -n production \
  --wait \
  --timeout 10m

# Rollback to the immediately previous revision:
helm rollback nestjs-api -n production

# Rollback dry-run (see what would change):
helm rollback nestjs-api 2 -n production --dry-run

# After rollback: revision 4 is created (rollbacks increment revision counter)
helm history nestjs-api -n production
# REVISION  STATUS    DESCRIPTION
# 2         superseded
# 3         failed
# 4         deployed  Rollback to 2    ← new revision

# Difference between helm rollback and kubectl rollout undo:
#   kubectl rollout undo: rolls back only the Deployment (Pod template).
#                         Other resources (ConfigMap, Service, HPA) stay at current state.
#   helm rollback:        rolls back ALL resources in the release to their state
#                         at the target revision. ConfigMap values revert too.
#                         This is the correct behavior for a full application rollback.
```

**Q11. What is the difference between `helm template`, `helm install --dry-run`, and `helm lint`, and when do you use each in a CI pipeline?**
A: These three commands operate at different layers of validation and serve different purposes. Using the wrong one in CI gives either false confidence (too shallow) or too many false positives (too strict for the context).

```
helm lint ./charts/nestjs-api -f values/production.yaml
  Layer: chart structure and basic template syntax.
  What it checks:
    Chart.yaml is valid (required fields, SemVer version).
    Values schema validation (if values.schema.json exists).
    Template files are parseable Go templates (no syntax errors).
    Required values are present.
    Basic YAML structural validity of rendered output.
  What it does NOT check:
    Whether the rendered manifests are valid Kubernetes resources.
    Whether the Kubernetes API supports the apiVersion in the templates.
    Whether resource names, labels, or selectors are correct.
  When to use:
    Fast check in every PR and push. Runs in ~1 second.
    First gate in CI: fail fast on chart structure problems.
  Exit code: 0 = no errors; 1 = errors found.

helm template ./charts/nestjs-api -f values/production.yaml > rendered.yaml
  Layer: full template rendering to YAML, without cluster access.
  What it does:
    Renders all templates with the given values.
    Produces the exact YAML that would be applied to the cluster.
    No connection to Kubernetes required.
  What it does NOT check:
    Whether the YAML is valid Kubernetes — kubeval/kubeconformist needed for that.
    Whether the apiVersion exists in the target cluster.
    Whether the rendered manifest would actually work (e.g., references a missing Secret).
  When to use:
    Pipe to yamllint: helm template ... | yamllint -
    Pipe to kubeval: helm template ... | kubeval --strict --kubernetes-version 1.29.0
    Pipe to kubeconformist: helm template ... | kubeconformist -
    Diff against current deployed state:
      helm template ... > new.yaml
      helm get manifest nestjs-api -n production > current.yaml
      diff current.yaml new.yaml
    Store in git for GitOps review: render and commit the output.
  When NOT to use:
    Do not rely on helm template alone for correctness — it cannot detect
    Kubernetes API incompatibilities or missing cluster resources.

helm upgrade --install --dry-run ./charts/nestjs-api -f values/production.yaml
  Layer: template rendering + Kubernetes API server validation.
  What it does:
    Renders templates (same as helm template).
    Sends the rendered manifests to the Kubernetes API server for validation.
    The API server checks: valid apiVersion/kind, required fields, field types.
    Returns what would be applied, with server-side validation applied.
  What it does NOT check:
    Whether the Pods would actually start and pass health checks.
    Whether referenced Secrets/ConfigMaps exist.
    Whether image tags are valid in the registry.
  Requires: kubeconfig pointing to a real cluster (or test cluster).
  When to use:
    Pre-production validation in CI that has cluster access.
    Catching apiVersion deprecations (e.g., autoscaling/v2beta2 → autoscaling/v2).
    Verifying chart works against the actual cluster's API version.
  When NOT to use:
    When no cluster is available (e.g., offline, cost control).
    Do not rely on --dry-run to guarantee a successful deploy — it does not
    run admission webhooks fully and does not check resource quotas.

Complete CI pipeline validation sequence:
  1. helm lint (always; fast; no cluster needed)
  2. helm template | yamllint (YAML syntax)
  3. helm template | kubeconformist (K8s schema validation; no cluster needed)
  4. helm upgrade --dry-run (cluster-aware validation; in staging cluster)
  5. helm upgrade --install --atomic --wait (actual deploy to staging)
  6. Run integration tests against staging
  7. helm upgrade --install --atomic --wait (deploy to production)
```

| `nindent` | Indent with leading newline | `{{ include "x" . \| nindent 4 }}` |
| `tpl` | Render string as template | `{{ tpl .Values.nameOverride . }}` |
| `sha256sum` | Hash for checksum annotations | `{{ include "x" . \| sha256sum }}` |
| `b64enc` | Base64 encode (for Secrets) | `{{ .Values.password \| b64enc }}` |
| `trunc` | Truncate to N chars | `{{ .Release.Name \| trunc 63 }}` |
| `trimSuffix` | Remove suffix | `{{ "name-" \| trimSuffix "-" }}` |
| `ternary` | Inline conditional | `{{ .Values.enabled \| ternary "yes" "no" }}` |
| `lookup` | Query live cluster resource | `{{ lookup "v1" "Secret" .Release.Namespace "name" }}` |

| Values precedence | Priority | Use for |
|---|---|---|
| `values.yaml` in chart | Lowest | Sensible defaults (dev-oriented) |
| `-f base.yaml` | Low | Shared cross-env settings |
| `-f production.yaml` | Medium | Environment-specific overrides |
| `--set key=value` | Highest | Per-deploy overrides (image tag, debug flags) |

| Command | Cluster needed | What it validates | When to use |
|---|---|---|---|
| `helm lint` | No | Chart structure, schema, template syntax | Every PR, every push |
| `helm template \| yamllint` | No | YAML syntax of rendered output | Every PR |
| `helm template \| kubeconformist` | No | K8s resource schema | Every PR |
| `helm upgrade --dry-run` | Yes | API server validation | Staging CI gate |
| `helm upgrade --install --atomic --wait` | Yes | Full deploy + health checks | Actual deploy |

| Failure mode | Symptom | Fix |
|---|---|---|
| `<no value>` in rendered YAML | Blank or `<no value>` in output | Use `required` or `default`; add key to values.yaml |
| Wrong scope inside `range` | Nil values for Release/Chart fields | Use `$` for root context or capture `$root := .` before range |
| HPA fights Deployment replicas | Capacity dips on every upgrade | Wrap `replicas` in `{{- if not .Values.autoscaling.enabled }}` |
| Integer rendered as string (or vice versa) | Kubernetes rejects manifest | Use `\| quote` for strings; use `\| int` for integers |
| Upgrade fails; cluster in partial state | Some Pods on old, some on new | Use `--atomic` flag; always |
| `helm rollback` reverts ConfigMap to bad value | App fails after rollback | Use `--atomic` to avoid needing rollback; fix values before re-deploying |
| Blank lines in YAML break multi-doc | Parser error or unexpected behavior | Use `{{-` on action-only lines to trim whitespace |
| Sub-chart values not applied | Sub-chart uses default values | Values must be nested under sub-chart name: `postgresql.password: ...` |
| `lookup` returns empty in CI | CI uses `helm template` (no cluster) | Wrap lookup results with `if`; handle empty dict case |

## The Core Mental Model

```
Helm is a release manager, not just a template engine.
The template engine (Go text/template + Sprig) renders YAML.
The release manager (helm upgrade --install) installs, tracks, and rolls back
that YAML as a named, versioned unit called a release.
The two jobs are separable: helm template is just the engine.
helm upgrade --install is the full system.

Values flow in one direction and merge deeply:
  chart defaults → base overrides → env overrides → --set flags
  Later values win. Deep merge for maps. Later --set wins for same key.
  The chart's values.yaml is documentation as much as configuration:
  every valid key should be present with a sensible default and a comment.
  An undocumented key that the developer must discover by reading templates
  is a chart design failure.

Named templates in _helpers.tpl are the DRY mechanism:
  Every resource in the chart uses the same fullname, the same labels,
  the same selectorLabels. Define them once in _helpers.tpl.
  Use include (not template) everywhere because include is pipeable.
  Always pipe multi-line output to nindent N for correct indentation.
  The selectorLabels must never change after first install —
  changing them requires deleting and recreating the Deployment.
  Never include mutable fields (version, revision) in selectorLabels.

The three conditional patterns cover 90% of template logic:
  1. {{- if .Values.feature.enabled }} ... {{- end }}
     Conditionally render entire resources (HPA, PDB, Ingress).

  2. {{- with .Values.optionalBlock }} ... {{- end }}
     Render a block only if the value is non-empty; . is rebound to the value.

  3. {{- range .Values.list }} ... {{- end }}
     Render a block for each item in a list; use $ for root context.

The checksum annotation pattern solves ConfigMap drift:
  checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
  When the ConfigMap template renders differently (values changed):
  the checksum changes → the Deployment pod template annotation changes
  → Kubernetes triggers a rolling update.
  Without it: a values change updates the ConfigMap but running Pods
  continue using the old values until they are restarted for other reasons.

--atomic is non-negotiable for production helm upgrades:
  Without --atomic: a failed upgrade leaves the cluster in a mixed state.
  Some Pods on old version; some on new (broken) version.
  The release is marked "failed"; subsequent upgrades require --force.
  With --atomic: failure = automatic rollback = clean previous state.
  The cost: a failed upgrade takes 2× the --timeout (deploy + rollback).
  This is the correct trade-off: clean failure beats partial state.

helm rollback vs kubectl rollout undo:
  kubectl rollout undo: rolls back only the Deployment's pod template.
    All other resources (ConfigMap, Service, HPA, PDB) stay at current state.
    Use when ONLY the Deployment image is wrong (most common case).
  helm rollback: rolls back ALL resources in the release to a previous revision.
    ConfigMap values, Service definitions, HPA settings — all revert.
    Use when the values.yaml change itself caused the problem.
    More complete but also more disruptive (Service changes can interrupt traffic).
```

**Tip for the interview:** Helm questions at 5 YOE converge on three areas: (1) the values hierarchy and merge semantics — being able to explain that values are deep-merged (maps combine; later values win on key collision), that `--set` is highest priority, that `--set` with a dotted key like `ingress.annotations.kubernetes\\.io/class=alb` requires escaping the dots, and that the HPA + replicas conflict (helm always setting `replicas` on a Deployment managed by HPA causes capacity dips on every upgrade, fixed by `{{- if not .Values.autoscaling.enabled }}`) shows you have operated Helm at production scale rather than just reading the docs; (2) the `include` vs `template` distinction with `nindent` — walking through exactly why `{{ template "x" . | nindent 4 }}` is a syntax error (template cannot be piped) while `{{ include "x" . | nindent 4 }}` is correct, and demonstrating that multi-line named template output requires `nindent` (not `indent`) because `nindent` adds the leading newline that positions the first line correctly at the indented level, demonstrates you have debugged a YAML indentation rendering bug in a real chart; (3) `--atomic` and the release failure model — explaining that without `--atomic` a failed Helm upgrade leaves the cluster in a mixed state (some Pods at old version, some at new broken version, release marked `failed`, next upgrade needs `--force`) while `--atomic` makes failure deterministic (upgrade fails → automatic rollback → clean previous state → release stays at last good revision), and distinguishing `helm rollback` (reverts ALL release resources including ConfigMaps) from `kubectl rollout undo` (reverts only the Deployment pod template), shows you understand Helm's release model rather than treating it as a kubectl wrapper. The fintech callout: for services deployed across development, staging, and production with separate AWS accounts and ECR registries, the correct pattern is a single chart with per-environment values files and `--set image.repository=$ECR_URI --set image.tag=$GIT_SHA` injected by the CI pipeline at deploy time — the chart never encodes the registry URI (it changes per account) and the image tag (it changes per commit), making the chart itself environment-agnostic and promotable from staging to production by changing only those two `--set` flags.
