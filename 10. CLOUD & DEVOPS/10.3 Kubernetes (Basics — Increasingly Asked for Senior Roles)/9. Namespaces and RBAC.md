# Kubernetes Namespaces and RBAC — Interview Q&A (5 YOE Level)

---

## Section 1: Namespaces

**Q1. What is a Kubernetes namespace and what does it provide?**
A: A namespace is a virtual cluster within a physical Kubernetes cluster. It provides a scope for names — resource names must be unique within a namespace but can be duplicated across namespaces. A `Service` named `user-service` can exist in both the `production` and `staging` namespaces without conflict.

Namespaces provide four things:

**Name scoping** — resources of the same type can share names across namespaces. Deployments, Services, ConfigMaps, Secrets, Pods, and most other resources are namespace-scoped. A few resources are cluster-scoped (not in any namespace): Nodes, PersistentVolumes, ClusterRoles, ClusterRoleBindings, StorageClasses, IngressClasses.

**Resource quotas** — you can set CPU, memory, and object count limits per namespace. A team's namespace cannot consume more than its allocated share of cluster resources.

**RBAC isolation** — permissions can be scoped to a namespace. A developer can have full access to the `development` namespace and read-only access to `production`.

**Network isolation (partial)** — by default, all pods across all namespaces can communicate. NetworkPolicies (applied per namespace) can enforce isolation — restricting which namespaces or pods can communicate with which others.

**What namespaces do NOT provide:**
- Strong security isolation. A pod with a misconfigured security context or a container image with a vulnerability can escape namespace boundaries. Namespaces are a soft organizational boundary, not a hard security boundary. For strong multi-tenant isolation, separate clusters or node pools are required.
- Network isolation by default. Traffic flows freely between namespaces unless NetworkPolicies are applied.

**Q2. What are the default namespaces in a Kubernetes cluster and what is each for?**
A:

**`default`** — the namespace used when no namespace is specified in `kubectl` commands or resource manifests. Avoid using it for production workloads — put workloads in explicitly named namespaces so resources are clearly organized and RBAC can be scoped correctly. The `default` namespace is a footgun: forgetting to specify `-n production` when running `kubectl delete` can delete a resource you didn't intend to touch.

**`kube-system`** — system components: the Kubernetes control plane components (api-server, scheduler, controller-manager, etcd), DNS (CoreDNS), kube-proxy, and add-ons like the metrics server. Never run application workloads here. Treat it as read-only from an operations perspective.

**`kube-public`** — publicly readable (even by unauthenticated users). Contains one ConfigMap (`cluster-info`) with bootstrap information used during node join. Rarely interacted with directly.

**`kube-node-lease`** — holds Lease objects that node heartbeats use to track node liveness. The kubelet on each node updates its Lease object; the control plane uses these to detect node failures. Do not interact with this namespace.

**Common convention for additional namespaces:**
```
production          ← production workloads
staging             ← staging/pre-prod workloads
development         ← shared development environment
monitoring          ← Prometheus, Grafana, AlertManager
logging             ← Fluentd, Loki, Elasticsearch
ingress-nginx       ← Nginx Ingress Controller
cert-manager        ← cert-manager controller
team-payments       ← payments team's namespace (team isolation)
team-platform       ← platform team's namespace
```

**Q3. How do you create and work with namespaces?**
A:

```bash
# Create a namespace imperatively
kubectl create namespace production

# Or declaratively (preferred — stored in git)
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: production
    team: platform
EOF

# Set a default namespace for your kubectl session
kubectl config set-context --current --namespace=production
# Now all commands apply to 'production' without -n flag

# View all namespaces
kubectl get namespaces

# View resources in a specific namespace
kubectl get pods -n production

# View resources across all namespaces
kubectl get pods --all-namespaces
# or shorter:
kubectl get pods -A
```

**Namespace labels for NetworkPolicy and monitoring:**
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: production     # used by NetworkPolicy selectors
    team: payments              # used for cost allocation / chargeback
    kubernetes.io/metadata.name: production  # auto-added by Kubernetes; usable in NetworkPolicy
```

Labels on namespaces are used by NetworkPolicies to select traffic sources/destinations by namespace identity. The `kubernetes.io/metadata.name` label is automatically set to the namespace name by Kubernetes (added in 1.21) and is the standard way to reference a namespace in NetworkPolicy `namespaceSelector`.

**Q4. What is a ResourceQuota and how does it enforce limits at the namespace level?**
A: A ResourceQuota sets hard limits on the total resources that can be consumed by all resources within a namespace. It prevents one team's namespace from starving others by monopolizing cluster resources.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    # Compute resources
    requests.cpu: "10"          # total CPU requests across all pods ≤ 10 cores
    requests.memory: 20Gi       # total memory requests ≤ 20Gi
    limits.cpu: "20"            # total CPU limits ≤ 20 cores
    limits.memory: 40Gi         # total memory limits ≤ 40Gi

    # Object count limits
    pods: "100"                 # max 100 pods
    services: "20"              # max 20 Services
    persistentvolumeclaims: "10" # max 10 PVCs
    secrets: "50"               # max 50 Secrets
    configmaps: "50"            # max 50 ConfigMaps

    # LoadBalancer Services are expensive; limit them
    services.loadbalancers: "2"
    services.nodeports: "0"     # disallow NodePort services in this namespace
```

**Effect of ResourceQuota:** once a ResourceQuota is set, every Pod in the namespace MUST specify `resources.requests` and `resources.limits`. Pods without resource specifications are rejected by the API server. Pair ResourceQuota with a LimitRange to set defaults:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: production-limits
  namespace: production
spec:
  limits:
    - type: Container
      default:            # applied if container doesn't specify limits
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:     # applied if container doesn't specify requests
        cpu: "100m"
        memory: "128Mi"
      max:                # container cannot exceed these
        cpu: "4"
        memory: "4Gi"
      min:                # container must request at least these
        cpu: "50m"
        memory: "64Mi"
```

With LimitRange, containers that omit resource specifications get sensible defaults rather than being rejected. Without LimitRange, every container definition must explicitly set resources, which is operationally correct but adds friction.

## Section 2: RBAC Fundamentals

**Q5. What is Kubernetes RBAC and what is its authorization model?**
A: RBAC (Role-Based Access Control) is Kubernetes's authorization mechanism. It controls which subjects (users, service accounts, groups) can perform which actions (verbs) on which resources (API objects) in which scope (namespace or cluster-wide).

RBAC follows the principle of least privilege: by default, a subject has NO permissions. Permissions are explicitly granted by binding a Role to a subject. There is no explicit deny — if no rule grants a permission, it is denied.

Four RBAC objects:

**Role** — a set of permissions scoped to a single namespace. Can only grant access to resources within its namespace.

**ClusterRole** — a set of permissions scoped cluster-wide. Can grant access to cluster-scoped resources (Nodes, PVs) and to namespaced resources across all namespaces.

**RoleBinding** — binds a Role (or ClusterRole) to subjects within a specific namespace. Makes the permissions effective in that namespace.

**ClusterRoleBinding** — binds a ClusterRole to subjects cluster-wide. Makes the permissions effective in all namespaces or for cluster-scoped resources.

```
┌─────────────────────────────────────────────────────────┐
│  RBAC Objects and Their Relationships                    │
│                                                          │
│  Role (namespace-scoped)        ClusterRole              │
│  ┌─────────────────────┐        ┌─────────────────────┐  │
│  │ rules:              │        │ rules:              │  │
│  │ - verbs: [get,list] │        │ - verbs: [get,list] │  │
│  │   resources: [pods] │        │   resources: [nodes]│  │
│  └──────────┬──────────┘        └──────────┬──────────┘  │
│             │                              │              │
│  RoleBinding│             ClusterRoleBinding              │
│  (in ns X)  │             (cluster-wide)   │              │
│  ┌──────────▼──────────┐  ┌───────────────▼──────────┐   │
│  │ roleRef: Role/Name  │  │ roleRef: ClusterRole/Name│   │
│  │ subjects:           │  │ subjects:                │   │
│  │ - ServiceAccount    │  │ - User                   │   │
│  │ - User              │  │ - Group                  │   │
│  │ - Group             │  └──────────────────────────┘   │
│  └─────────────────────┘                                  │
└─────────────────────────────────────────────────────────┘
```

**Q6. What are the RBAC verbs and what do they map to in terms of API operations?**
A: Verbs map directly to HTTP methods on the Kubernetes API:

| Verb | HTTP method | Operation |
|--- |--- |--- |
| `get` | GET | Retrieve a specific named resource |
| `list` | GET | List all resources of a type |
| `watch` | GET (with `?watch=true`) | Stream change events for resources |
| `create` | POST | Create a new resource |
| `update` | PUT | Replace an existing resource entirely |
| `patch` | PATCH | Partially modify an existing resource |
| `delete` | DELETE | Delete a specific resource |
| `deletecollection` | DELETE | Delete all resources matching a selector |
| `exec` | POST | `kubectl exec` — execute a command in a container |
| `portforward` | POST | `kubectl port-forward` |
| `proxy` | GET/POST | `kubectl proxy` |
| `bind` | POST | Bind a Pod to a Node (scheduler use) |
| `escalate` | — | Grant permissions you don't have (prevent privilege escalation) |
| `impersonate` | — | Act as another user |

```yaml
# Read-only role: can see pods but not modify them
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

# Developer role: can do most things with pods but not delete them
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  # No "delete" or "deletecollection" — cannot delete pods

# Exec access: can shell into pods but cannot create or delete them
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods/exec"]      # subresource
    verbs: ["create"]             # "create" is the verb for exec
```

**Subresources** — some operations on a resource are treated as subresources with their own RBAC control:
- `pods/exec` — `kubectl exec`
- `pods/log` — `kubectl logs`
- `pods/portforward` — `kubectl port-forward`
- `deployments/scale` — scaling a deployment
- `services/proxy` — proxying to a service

Granting access to `pods` does NOT grant access to `pods/exec`. These must be granted separately, enabling fine-grained control: a user can list pods and read logs but cannot exec into them.

## Section 3: Roles and ClusterRoles

**Q7. How do you write a Role and when do you use Role vs ClusterRole?**
A:

**Role (namespace-scoped):**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production          # ← scoped to this namespace only
rules:
  - apiGroups: [""]              # "" = core API group (pods, services, configmaps, etc.)
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]

  - apiGroups: ["apps"]          # apps API group (deployments, replicasets, daemonsets)
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch"]

  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list"]
    resourceNames: ["app-config", "feature-flags"]  # ← limit to specific named resources
```

`resourceNames` is powerful but often overlooked: it restricts the rule to only those specific named objects. A developer can read `configmaps` named `app-config` and `feature-flags` but cannot read any other ConfigMap (including Secrets masquerading as ConfigMaps).

**ClusterRole (cluster-scoped):**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader              # no namespace field — cluster-scoped
rules:
  - apiGroups: [""]
    resources: ["nodes"]         # cluster-scoped resource; cannot be in a Role
    verbs: ["get", "list", "watch"]

  - apiGroups: [""]
    resources: ["namespaces"]    # cluster-scoped
    verbs: ["get", "list"]

  - apiGroups: ["storage.k8s.io"]
    resources: ["storageclasses", "persistentvolumes"]
    verbs: ["get", "list", "watch"]
```

**When to use Role vs ClusterRole:**

Use a **Role** when permissions should be limited to a specific namespace. A developer Role for the `production` namespace cannot accidentally affect `staging`.

Use a **ClusterRole** when:
- Granting access to cluster-scoped resources (Nodes, PVs, ClusterRoles themselves).
- Creating a reusable permission template that will be bound to multiple namespaces via RoleBindings (one ClusterRole, many RoleBindings — DRY principle).
- Granting admin or read access that spans all namespaces.

**Reusing a ClusterRole with a RoleBinding (namespace-scoped binding of cluster-wide template):**
```yaml
# ClusterRole: template defining what a "pod-reader" can do
kind: ClusterRole
metadata:
  name: pod-reader    # reusable template
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
# RoleBinding in namespace A: grants pod-reader in 'production' only
kind: RoleBinding
metadata:
  name: developer-pod-reader
  namespace: production          # ← restricts scope to this namespace
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole              # references a ClusterRole...
  name: pod-reader
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
# Result: Alice can read pods in 'production' only, not in 'staging' or 'kube-system'
```

**Q8. What built-in ClusterRoles does Kubernetes provide?**
A: Kubernetes ships with several pre-built ClusterRoles:

**`cluster-admin`** — full unrestricted access to every resource in the cluster. Equivalent to root. Should be granted only to cluster administrators, not application developers. Never use this as a shortcut for troubleshooting.

**`admin`** — full access within a namespace: can create and delete Deployments, Services, ConfigMaps, Secrets, etc. Cannot manage quotas or the namespace itself. Appropriate for a team lead who owns a namespace.

**`edit`** — can create, update, and delete most resources in a namespace. Cannot view or modify Roles or RoleBindings (preventing privilege escalation). Appropriate for developers.

**`view`** — read-only access to most resources in a namespace. Cannot view Secrets (intentional — Secrets contain sensitive data). Appropriate for on-call access to production, monitoring systems, or read-only auditing.

```bash
# List all built-in ClusterRoles
kubectl get clusterroles | grep -v "^system:"

# See what the 'edit' ClusterRole allows
kubectl describe clusterrole edit

# Bind the built-in 'edit' role to a developer in their namespace
kubectl create rolebinding alice-editor \
  --clusterrole=edit \
  --user=alice@example.com \
  --namespace=production
```

**Aggregated ClusterRoles** — the built-in `view`, `edit`, and `admin` ClusterRoles are aggregated from smaller ClusterRoles. When you install a Custom Resource Definition (CRD), you can make its resources automatically visible to the standard roles by labeling a new ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: payment-crd-view
  labels:
    rbac.authorization.k8s.io/aggregate-to-view: "true"   # ← auto-adds to 'view' ClusterRole
    rbac.authorization.k8s.io/aggregate-to-edit: "true"   # ← auto-adds to 'edit' ClusterRole
rules:
  - apiGroups: ["payments.example.com"]
    resources: ["charges", "refunds"]
    verbs: ["get", "list", "watch"]
```

With this label, anyone with the `view` ClusterRole in any namespace can now also see `charges` and `refunds` custom resources — without modifying the `view` ClusterRole itself.

## Section 4: Bindings and Subjects

**Q9. What are the three subject types in RBAC bindings?**
A: The `subjects` field of a RoleBinding or ClusterRoleBinding specifies WHO receives the permissions:

**ServiceAccount** — a non-human identity for pods and controllers. The most common subject type in production. Pods run as a ServiceAccount; their in-cluster API calls are authenticated with the ServiceAccount's token.

```yaml
subjects:
  - kind: ServiceAccount
    name: payment-processor       # ServiceAccount name
    namespace: production         # namespace where the SA lives (required for ClusterRoleBinding)
```

**User** — a human user authenticated externally (OIDC, x.509 certificate, webhook). Kubernetes does not manage user accounts internally — users are external identities that Kubernetes trusts based on the authentication mechanism. The `name` must match the username in the authentication token:

```yaml
subjects:
  - kind: User
    name: alice@example.com       # exact match to username from auth provider
    apiGroup: rbac.authorization.k8s.io
```

**Group** — a group of users. If your authentication provider (OIDC, LDAP) includes group claims, you can bind an entire group:

```yaml
subjects:
  - kind: Group
    name: system:masters          # built-in group; members are cluster admins
    apiGroup: rbac.authorization.k8s.io

  - kind: Group
    name: payments-team           # custom group from OIDC provider
    apiGroup: rbac.authorization.k8s.io

  - kind: Group
    name: system:serviceaccounts:production  # all ServiceAccounts in 'production' namespace
    apiGroup: rbac.authorization.k8s.io
```

**Built-in special groups:**
- `system:masters` — cluster administrators (hardcoded bypass of RBAC; always cluster-admin).
- `system:authenticated` — all authenticated users.
- `system:unauthenticated` — all unauthenticated requests.
- `system:serviceaccounts` — all ServiceAccounts in all namespaces.
- `system:serviceaccounts:<namespace>` — all ServiceAccounts in a specific namespace.

**Q10. What is a ServiceAccount and how do pods use it?**
A: A ServiceAccount is a namespaced Kubernetes object that provides an identity for processes running inside pods. Every namespace has a `default` ServiceAccount created automatically; if a Pod doesn't specify a `serviceAccountName`, it runs as the `default` ServiceAccount.

```yaml
# Create a dedicated ServiceAccount for the payment processor
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-processor
  namespace: production
---
# Role with only the permissions the payment processor needs
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: payment-processor-role
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["stripe-api-key", "db-password"]  # only these specific Secrets
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["payment-config"]
    verbs: ["get", "watch"]
---
# RoleBinding: grant the role to the ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payment-processor-binding
  namespace: production
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: payment-processor-role
subjects:
  - kind: ServiceAccount
    name: payment-processor
    namespace: production
---
# Pod: runs as the payment-processor ServiceAccount
apiVersion: v1
kind: Pod
metadata:
  name: payment-processor
  namespace: production
spec:
  serviceAccountName: payment-processor   # ← run as this SA
  automountServiceAccountToken: true       # mount the SA token (default: true)
  containers:
    - name: app
      image: payment-processor:1.4.2
```

**How the pod uses the ServiceAccount token:**
Kubernetes mounts a short-lived ServiceAccount token (via the `TokenRequest` API, valid for ~1 hour, auto-rotated) at `/var/run/secrets/kubernetes.io/serviceaccount/token`. When the pod calls the Kubernetes API:

```typescript
// In-cluster Kubernetes client (Node.js)
import { KubeConfig, CoreV1Api } from '@kubernetes/client-node';

const kc = new KubeConfig();
kc.loadFromCluster();   // reads /var/run/secrets/kubernetes.io/serviceaccount/token
const k8sApi = kc.makeApiClient(CoreV1Api);

// This call is authenticated as the 'payment-processor' ServiceAccount
// RBAC checks: does payment-processor have 'get' on 'secrets/stripe-api-key'? Yes → allow
const secret = await k8sApi.readNamespacedSecret('stripe-api-key', 'production');
```

**`automountServiceAccountToken: false`** — pods that don't need to call the Kubernetes API should disable auto-mounting:
```yaml
spec:
  automountServiceAccountToken: false   # defense in depth: no token if not needed
```

## Section 5: Production RBAC Patterns

**Q11. How do you design a least-privilege RBAC structure for a multi-team cluster?**
A: A production RBAC structure for a cluster shared by multiple teams:

```yaml
# ──────────────────────────────────────────────
# CLUSTER-LEVEL ROLES (ClusterRoles)
# ──────────────────────────────────────────────

# Platform/SRE team: full cluster access
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: platform-team-admin
roleRef:
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: Group
    name: platform-team           # from OIDC provider
    apiGroup: rbac.authorization.k8s.io
---
# Auditors: read-only across all namespaces
kind: ClusterRoleBinding
metadata:
  name: auditor-view
roleRef:
  kind: ClusterRole
  name: view
subjects:
  - kind: Group
    name: security-auditors
    apiGroup: rbac.authorization.k8s.io
---
# CI/CD system: can deploy to any namespace (but not admin)
kind: ClusterRole
metadata:
  name: ci-deployer
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "daemonsets", "statefulsets"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  # Notably absent: delete, secrets management, RBAC modification

# ──────────────────────────────────────────────
# PER-NAMESPACE ROLES (applied for each team namespace)
# ──────────────────────────────────────────────

# Payments team namespace setup
---
apiVersion: v1
kind: Namespace
metadata:
  name: team-payments
  labels:
    team: payments
---
# Payments developers: full edit in their namespace
kind: RoleBinding
metadata:
  name: payments-dev-edit
  namespace: team-payments
roleRef:
  kind: ClusterRole
  name: edit                   # built-in; covers most resources
subjects:
  - kind: Group
    name: payments-developers
    apiGroup: rbac.authorization.k8s.io
---
# Payments developers: cannot view Secrets (Secrets managed by platform team or vault)
kind: Role
metadata:
  name: deny-secrets-view     # Kubernetes RBAC has no explicit deny;
  namespace: team-payments    # use separate tool (OPA/Kyverno) for negative controls
  # Note: this Role doesn't help — it would need to GRANT access to override
  # For secret access restriction, ensure no role grants it, and use separate auditing
---
# CI/CD ServiceAccount for payments team deployments
kind: RoleBinding
metadata:
  name: payments-ci-deployer
  namespace: team-payments
roleRef:
  kind: ClusterRole
  name: ci-deployer
subjects:
  - kind: ServiceAccount
    name: payments-ci
    namespace: ci-cd              # ServiceAccount lives in the CI namespace
```

**Q12. How do you handle RBAC for operators and controllers that need cluster-wide access?**
A: Operators (Prometheus, cert-manager, Argo CD, Istio) require cluster-wide access to watch resources across all namespaces. The pattern:

```yaml
# cert-manager needs to read/write Secrets (for certificates) and watch Ingresses across all namespaces
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cert-manager-controller
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "list", "watch", "create", "update", "delete"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get", "list", "watch", "update"]
  - apiGroups: ["cert-manager.io"]
    resources: ["certificates", "certificaterequests", "issuers", "clusterissuers"]
    verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]
---
kind: ClusterRoleBinding
metadata:
  name: cert-manager-controller
roleRef:
  kind: ClusterRole
  name: cert-manager-controller
subjects:
  - kind: ServiceAccount
    name: cert-manager
    namespace: cert-manager       # SA lives in the cert-manager namespace
```

The key: even though the ClusterRoleBinding is cluster-wide, the subject is a specific ServiceAccount in a specific namespace. cert-manager's pods run as `cert-manager/cert-manager` (namespace/SA name), which has only the permissions defined above — not `cluster-admin`.

## Section 6: Checking and Auditing Permissions

**Q13. How do you check what permissions a subject has in Kubernetes?**
A: The `kubectl auth can-i` command checks whether the current user (or a specified subject) has a specific permission:

```bash
# Can I list pods in the production namespace?
kubectl auth can-i list pods -n production
# yes / no

# Can I delete secrets in production? (should be no for developers)
kubectl auth can-i delete secrets -n production
# no

# Can a specific ServiceAccount get nodes? (cluster-scoped)
kubectl auth can-i get nodes \
  --as=system:serviceaccount:production:payment-processor
# no

# Can a user exec into pods?
kubectl auth can-i create pods/exec \
  --as=alice@example.com \
  -n production
# yes

# List ALL permissions for a ServiceAccount in a namespace
kubectl auth can-i --list \
  --as=system:serviceaccount:production:payment-processor \
  -n production

# Output:
# Resources                Non-Resource URLs  Resource Names   Verbs
# secrets                  []                 [stripe-api-key] [get]
# configmaps               []                 [payment-config] [get watch]
# ...
```

**`kubectl auth can-i --list`** is invaluable for auditing — it shows the complete set of permissions a subject has in a given namespace. Run this for every ServiceAccount before deploying to production to confirm least privilege.

**Visualizing RBAC with `rakkess` (external tool):**
```bash
# Install rakkess
kubectl krew install access-matrix

# Show what all subjects can do with pods in production
kubectl access-matrix --namespace production --resource pods

# Output matrix: rows = verbs, columns = subjects
```

**`kubectl-who-can` (external tool):**
```bash
# Who can delete pods in production? (reverse lookup)
kubectl who-can delete pods -n production
# ServiceAccount/ci-deployer in ci-cd: No
# User/alice@example.com: No
# Group/platform-team: Yes (via cluster-admin)
```

**Q14. How do you audit RBAC to find over-privileged subjects?**
A: RBAC over-provisioning (giving too much access for convenience) is the most common security problem in Kubernetes clusters. Audit approach:

**Step 1: Find all ClusterRoleBindings that grant `cluster-admin`.**
```bash
kubectl get clusterrolebindings -o json | \
  jq '.items[] | select(.roleRef.name=="cluster-admin") | {name: .metadata.name, subjects: .subjects}'
```
Every entry in this output is a subject with unrestricted cluster access. Eliminate or scope down any that aren't strictly necessary.

**Step 2: Find ServiceAccounts with broad permissions.**
```bash
# Find all RoleBindings and ClusterRoleBindings that include ServiceAccounts
kubectl get rolebindings,clusterrolebindings -A -o json | \
  jq '[.items[] | select(.subjects[]?.kind=="ServiceAccount")] |
      .[] | {binding: .metadata.name, ns: .metadata.namespace,
             role: .roleRef.name, subjects: .subjects}'
```

**Step 3: Check for deprecated `serviceaccount:default` bindings.**
```bash
# Find any binding to the 'default' ServiceAccount (anti-pattern)
kubectl get rolebindings,clusterrolebindings -A -o json | \
  jq '.items[] | select(.subjects[]? | .kind=="ServiceAccount" and .name=="default")'
```
Pods running as the `default` ServiceAccount and bound to permissions is an anti-pattern — all pods in the namespace inherit those permissions, including ones that don't need them. Each workload should have its own ServiceAccount with its own minimal permissions.

**Step 4: Find Roles that allow `exec` (risky).**
```bash
kubectl get clusterroles,roles -A -o json | \
  jq '.items[] | select(.rules[]? | .resources[]? == "pods/exec") |
      {name: .metadata.name, ns: .metadata.namespace}'
```
`pods/exec` is a high-risk permission — anyone who can exec into a pod can potentially access secrets mounted in the pod, modify the running process, or pivot to other services.

## Section 7: Common Patterns and Anti-Patterns

**Q15. What are the most common RBAC anti-patterns?**
A: Five anti-patterns seen repeatedly in production clusters:

**1. Granting `cluster-admin` to application workloads.**
The most dangerous. An operator or controller that needs read access to Deployments across all namespaces gets `cluster-admin` "for simplicity." If that pod is compromised, the attacker has full cluster control.
Fix: write the minimum ClusterRole needed and bind only that.

**2. Using the `default` ServiceAccount.**
All pods in a namespace that don't specify a `serviceAccountName` run as `default`. If `default` is bound to any Role, all pods in the namespace get those permissions — including ones that don't need them. A compromise of any pod in the namespace leaks the permissions.
Fix: create a dedicated ServiceAccount per workload; set `automountServiceAccountToken: false` on the `default` ServiceAccount.

```bash
# Disable token auto-mounting on the default ServiceAccount
kubectl patch serviceaccount default \
  -p '{"automountServiceAccountToken": false}' \
  -n production
```

**3. Wildcard verbs or resources.**
```yaml
rules:
  - apiGroups: ["*"]       # all API groups
    resources: ["*"]       # all resources
    verbs: ["*"]           # all verbs — effectively cluster-admin for this scope
```
Seen in custom operators that were given overly broad permissions during development and never tightened. Wildcards are acceptable only for ClusterRoles used by cluster administrators.

**4. Granting access to `secrets` broadly.**
```yaml
rules:
  - apiGroups: [""]
    resources: ["secrets"]    # all secrets in the namespace
    verbs: ["get", "list"]
```
A subject that can `list` secrets can read all secret values — database passwords, API keys, TLS private keys — in the namespace. Use `resourceNames` to limit to specific secrets the workload needs, or use an external secrets manager (AWS Secrets Manager + External Secrets Operator) that provides fine-grained access control outside Kubernetes.

**5. Not using `resourceNames` for fine-grained access.**
A CI/CD system needs to update one specific ConfigMap. Without `resourceNames`, granting `update` on `configmaps` lets it update ALL ConfigMaps in the namespace — including the ones holding security policies or feature flags. Always use `resourceNames` when the workload has a specific, known set of resources it needs to access.

**Q16. How does RBAC interact with Namespace isolation?**
A: RBAC and Namespaces are complementary but orthogonal:

**RBAC without NetworkPolicy:** a subject can be restricted from reading Secrets in namespace B (no RBAC permission), but a pod in namespace A can still make HTTP requests to pods in namespace B over the network (networking is unrestricted without NetworkPolicy). RBAC controls Kubernetes API access; NetworkPolicy controls network traffic.

**Both are needed for real isolation:**
```yaml
# NetworkPolicy: restrict which namespaces can talk to the payments namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-ingress
  namespace: team-payments
spec:
  podSelector: {}    # applies to all pods in the namespace
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: team-orders   # only orders can call payments
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx  # and ingress controller
```

With both RBAC (controls API access) and NetworkPolicy (controls network traffic), `team-orders` can call the payments service over HTTP but cannot read the payments team's Secrets via the Kubernetes API (no RBAC binding), and `team-frontend` cannot call the payments service directly (NetworkPolicy blocks it). Defense in depth.

## Section 8: Scenario Questions

**Q17. "A developer needs to debug a crashing pod in production. What permissions do they need and how do you grant them with minimum privilege?"**
A: Debugging typically requires: reading pod status, viewing logs, and potentially exec-ing into a pod. Grant only these, scoped to production, and time-limit the access:

```yaml
# Temporary debug role — created for the incident; deleted after
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: incident-debug-20240723
  namespace: production
rules:
  # See pod status, events, resource usage
  - apiGroups: [""]
    resources: ["pods", "pods/log", "events"]
    verbs: ["get", "list", "watch"]

  # Exec into the specific crashing pod (not all pods)
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
    resourceNames: ["payment-processor-abc123"]  # specific pod only

  # Read deployment/replicaset to see rollout status
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list"]

  # Read the relevant ConfigMaps (not Secrets — they stay restricted)
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["payment-config", "feature-flags"]
    verbs: ["get"]
---
kind: RoleBinding
metadata:
  name: incident-debug-alice-20240723
  namespace: production
roleRef:
  kind: Role
  name: incident-debug-20240723
subjects:
  - kind: User
    name: alice@example.com
    apiGroup: rbac.authorization.k8s.io
```

**After the incident:**
```bash
# Remove the temporary access
kubectl delete role incident-debug-20240723 -n production
kubectl delete rolebinding incident-debug-alice-20240723 -n production
```

**Better long-term pattern — just-in-time (JIT) access:** use a tool like `kubectl-sudo` (Impersonator operator), Teleport, or Argo CD's `kubectl` access controls to grant time-limited, audit-logged permissions rather than manually creating and deleting RBAC objects. JIT access is the production best practice for human access to sensitive namespaces.

**Q18. "You're setting up a CI/CD pipeline (GitHub Actions) that needs to deploy to Kubernetes. What RBAC setup do you use?"**
A: The CI/CD system needs to create/update Deployments, Services, ConfigMaps, and Ingresses. It should NOT be able to delete arbitrary resources, modify RBAC, or access Secrets (Secrets are managed by the secrets manager, not CI/CD):

```yaml
# Dedicated namespace for CI/CD ServiceAccounts
apiVersion: v1
kind: Namespace
metadata:
  name: ci-cd
---
# ServiceAccount for GitHub Actions
apiVersion: v1
kind: ServiceAccount
metadata:
  name: github-actions-deployer
  namespace: ci-cd
---
# ClusterRole: can deploy but not destroy or elevate
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: deployer
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps", "serviceaccounts"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["autoscaling"]
    resources: ["horizontalpodautoscalers"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  # Deliberately excluded: delete, secrets, roles, rolebindings
---
# RoleBinding: grant deployer role only in production namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: github-actions-deploy
  namespace: production            # ← scoped to production only
roleRef:
  kind: ClusterRole
  name: deployer
subjects:
  - kind: ServiceAccount
    name: github-actions-deployer
    namespace: ci-cd
```

**Generating a kubeconfig for GitHub Actions:**
```bash
# Modern approach: use short-lived tokens (recommended)
# In GitHub Actions workflow:
# 1. Use OIDC to authenticate to AWS/GCP without long-lived credentials
# 2. Use cloud provider's k8s auth (AWS: eks get-token, GCP: gke-cloud-auth-plugin)

# Legacy approach: long-lived ServiceAccount token (avoid for new setups)
kubectl create token github-actions-deployer \
  -n ci-cd \
  --duration=8760h   # 1 year — avoid; prefer short-lived OIDC tokens
```

**GitHub Actions OIDC (preferred — no long-lived secrets):**
```yaml
# GitHub Actions workflow: authenticate to EKS via OIDC
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789:role/github-actions-eks-deployer
    aws-region: us-east-1

- name: Update kubeconfig
  run: aws eks update-kubeconfig --name my-cluster --region us-east-1

- name: Deploy
  run: kubectl apply -f k8s/production/ -n production
```

The IAM role (`github-actions-eks-deployer`) is bound to the Kubernetes ServiceAccount via EKS's IAM Roles for Service Accounts (IRSA) or EKS Pod Identity, and the RBAC RoleBinding above controls what that SA can do in Kubernetes.

## Quick Reference

| Object | Scope | Purpose |
|--- |--- |--- |
| Namespace | Cluster | Virtual cluster; scopes names and quotas |
| ResourceQuota | Namespace | Limits total resource consumption per namespace |
| LimitRange | Namespace | Sets default/min/max resource requests per container |
| Role | Namespace | Permission rules scoped to one namespace |
| ClusterRole | Cluster | Permission rules cluster-wide or reusable template |
| RoleBinding | Namespace | Binds Role or ClusterRole to subjects in one namespace |
| ClusterRoleBinding | Cluster | Binds ClusterRole to subjects cluster-wide |
| ServiceAccount | Namespace | Identity for pods; authenticated via mounted token |

| Verb | Operation | Risk level |
|--- |--- |--- |
| `get`, `list`, `watch` | Read | Low |
| `create`, `update`, `patch` | Write | Medium |
| `delete`, `deletecollection` | Destroy | High |
| `exec` (`pods/exec`) | Shell access | High |
| `escalate`, `impersonate` | Privilege escalation | Critical |
| `*` (wildcard) | Everything | Critical |

| RBAC Pattern | When to use |
|--- |--- |
| Role + RoleBinding | Team/namespace-scoped permissions; developers in their namespace |
| ClusterRole + RoleBinding | Same permission template across multiple namespaces |
| ClusterRole + ClusterRoleBinding | Cluster-admin, operators, cross-namespace access |
| Built-in `view` ClusterRole | Read-only access; on-call; auditors; monitoring |
| Built-in `edit` ClusterRole | Developers with full write access to their namespace |
| Dedicated ServiceAccount per workload | All production pods; never use `default` SA |
| `resourceNames` | Any SA needing access to specific Secrets or ConfigMaps |
| `automountServiceAccountToken: false` | Pods that don't call the Kubernetes API |

**Tip for the interview:** Namespace and RBAC questions at 5 YOE level test whether you understand the security model, not just the syntax. Lead with the key conceptual points: namespaces provide soft organizational boundaries (not strong security isolation — networking is unrestricted without NetworkPolicy), and RBAC is pure allow — there are no explicit deny rules (to restrict access, ensure nothing grants it). The specific details that separate senior answers: knowing that a ClusterRole can be bound with a RoleBinding to limit its scope to one namespace (the ClusterRole-as-template pattern), being able to enumerate the difference between `pods/exec` as a subresource requiring separate permission, and explaining why the `default` ServiceAccount anti-pattern is dangerous (all pods in the namespace inherit its permissions). If asked about production setup: dedicated ServiceAccount per workload, `automountServiceAccountToken: false` on the default SA, `kubectl auth can-i --list` for auditing, and JIT access for humans in production — these four practices together show you've thought about the operational security of a real cluster.
