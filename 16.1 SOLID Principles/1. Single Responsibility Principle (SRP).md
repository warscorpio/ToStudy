# Design Patterns — SOLID Principles: Single Responsibility Principle (SRP) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Single Responsibility Principle?**
A: SRP states that a class (or module, function, or service) should have **one and only one reason to change** — meaning it should be responsible for exactly one part of the system's behavior. The key word is *reason to change*: if two different stakeholders (e.g., the billing team and the compliance team) can independently request changes to the same class, that class has two responsibilities and violates SRP. Robert C. Martin, who formalized SOLID, defines a "responsibility" as "a reason for change" tied to a specific actor or role in the system.

**Q2. Why is "reason to change" a better definition than "does one thing"?**
A: "Does one thing" is too vague — any function at a high level "does one thing" (e.g., "processes a loan application"). The actor-based framing is precise: who in the organization would request a change to this code?
- If the **Risk team** changes underwriting rules → only the risk engine should change.
- If the **Ops team** changes notification templates → only the notification service should change.
- If the **Finance team** changes EMI calculation formulas → only the loan calculation module should change.

When the same class is touched by multiple actor-driven change requests, it violates SRP. This makes SRP testable: ask "how many different job roles could file a bug against this class?"

**Q3. What problems does SRP solve?**
A: SRP directly addresses:
- **Fragility** — changes to one responsibility accidentally break another (e.g., editing a PDF report generation function breaks the data validation logic co-located in the same class).
- **Rigidity** — classes become too large and complex to safely modify; devs fear touching them.
- **Low reusability** — a class that mixes database access, business logic, and HTTP response formatting can't be reused in a CLI tool or a background job without dragging in all three concerns.
- **Poor testability** — unit-testing a class with four responsibilities requires mocking four different systems; isolating the one you care about becomes hard.
- **Merge conflicts** — when multiple developers modify the same class for different reasons simultaneously, git conflicts multiply.

**Q4. Is SRP only about classes? Does it apply to functions and microservices too?**
A: SRP is fractal — it applies at every level of abstraction:
- **Function level** — a function should do one coherent operation. `validateAndSaveAndNotify()` is a red flag.
- **Module/file level** — a NestJS module should own one bounded context (e.g., `LoanModule`, not `LoanAndNotificationAndReportingModule`).
- **Service level** — in a microservices architecture, each service should own one business capability. A `LoanOriginationService` shouldn't also be the canonical source of truth for user KYC status.
- **Class level** — the original formulation, but the principle holds everywhere.

**Q5. What is the difference between SRP and the concept of "separation of concerns"?**
A: They're related but not identical. Separation of concerns (SoC) is the broader architectural principle: different concerns (persistence, business logic, presentation) should be handled by different parts of the system. SRP is a class-level design rule that gives SoC a concrete, actor-centric definition. SRP is essentially SoC applied at the class/module granularity with a specific heuristic for identifying what counts as a distinct concern: who would ask for the change?

## Section 2: Violations & Identification

**Q6. What does a typical SRP violation look like in a NestJS/TypeScript codebase?**
A: A common pattern in fintech backends — a "God service" that mixes multiple concerns:

```typescript
// ❌ Violates SRP — multiple reasons to change
@Injectable()
export class LoanService {
  constructor(
    private readonly db: PrismaService,
    private readonly mailer: MailerService,
    private readonly smsClient: SmsClient,
    private readonly bureauClient: CreditBureauClient,
    private readonly pdfGenerator: PdfService,
  ) {}

  async applyForLoan(dto: LoanApplicationDto): Promise<void> {
    // 1. Validate business rules (Risk team owns this)
    if (dto.income < 25000) throw new BadRequestException('Income too low');

    // 2. Pull credit bureau report (Integrations team owns this)
    const report = await this.bureauClient.fetch(dto.pan);

    // 3. Persist to DB (Data team owns this)
    const loan = await this.db.loan.create({ data: { ...dto, bureau: report } });

    // 4. Generate sanction letter PDF (Ops team owns this)
    const pdf = await this.pdfGenerator.generate(loan);

    // 5. Notify applicant (CX team owns this)
    await this.mailer.sendSanctionLetter(dto.email, pdf);
    await this.smsClient.send(dto.mobile, `Loan ${loan.id} approved`);
  }
}
```

Five different teams could independently file change requests against this single method. Any change by any one of them risks breaking the others.

**Q7. How do you spot an SRP violation during a code review?**
A: Practical heuristics:
- **Method count / line count smell** — a service with 15+ methods or 400+ lines almost always has multiple responsibilities.
- **Mixed import types** — a class that imports both `PrismaService` (persistence) and `MailerService` (notification) and `PdfService` (document generation) is mixing concerns.
- **"And" in the class/method name** — `validateAndPersist()`, `LoanAndNotificationService` — "and" is a compound responsibility signal.
- **Multiple constructor dependencies from different domains** — if the constructor takes a DB client, an HTTP client, a mailer, and a PDF generator, it's doing too much.
- **Shotgun surgery** — when one business change (e.g., "add a new loan product") requires edits in the same class for five different reasons, those reasons should have been separate classes.
- **Untestable private methods** — if a class has large private methods that you wish you could test in isolation, that's often a hidden responsibility screaming to become its own class.

**Q8. What is "shotgun surgery," and how does it relate to SRP?**
A: Shotgun surgery is the refactoring smell where a single change to a business requirement forces you to edit many different classes scattered across the codebase. It's the *inverse* of SRP violation: instead of one class being changed for many reasons, you have one reason causing changes in many classes. Both smells indicate poor responsibility assignment. SRP, when properly applied, collocates things that change together and separates things that change independently — preventing both the God class and the shotgun surgery extremes.

**Q9. Can you over-apply SRP? What does that look like?**
A: Yes — over-decomposition is a real failure mode, sometimes called "class explosion" or taken to an absurd extreme, "single-method classes." Signs you've gone too far:
- Classes so granular they have no state and only one method — these should probably just be standalone functions.
- Abstraction layers that exist only to satisfy SRP on paper but add indirection with no practical benefit.
- A simple CRUD operation that requires navigating 12 files because each operation was split into its own class.

The test: does the split make the code *easier to understand, test, and change* in practice, or does it just feel theoretically pure? SRP is a guideline for managing change and complexity, not a dogma. Martin himself notes that cohesion and coupling are the real underlying forces — SRP is a heuristic for optimizing them.

## Section 3: Refactoring to SRP

**Q10. How would you refactor the `LoanService` violation from Q6 into SRP-compliant code?**
A: Split along actor/responsibility lines:

```typescript
// ✅ SRP-compliant decomposition

// Owned by Risk team — underwriting rules only
@Injectable()
export class LoanEligibilityService {
  assess(dto: LoanApplicationDto): void {
    if (dto.income < 25000) throw new BadRequestException('Income too low');
    // other eligibility checks...
  }
}

// Owned by Integrations team — bureau API contract
@Injectable()
export class CreditBureauService {
  constructor(private readonly client: CreditBureauClient) {}

  async fetchReport(pan: string): Promise<BureauReport> {
    return this.client.fetch(pan);
  }
}

// Owned by Data team — persistence only
@Injectable()
export class LoanRepository {
  constructor(private readonly db: PrismaService) {}

  async create(data: CreateLoanDto): Promise<Loan> {
    return this.db.loan.create({ data });
  }
}

// Owned by Ops team — document generation
@Injectable()
export class SanctionLetterService {
  constructor(private readonly pdf: PdfService) {}

  async generate(loan: Loan): Promise<Buffer> {
    return this.pdf.generate(loan);
  }
}

// Owned by CX team — applicant communication
@Injectable()
export class LoanNotificationService {
  constructor(
    private readonly mailer: MailerService,
    private readonly sms: SmsClient,
  ) {}

  async notifyApproval(loan: Loan, pdf: Buffer): Promise<void> {
    await this.mailer.sendSanctionLetter(loan.email, pdf);
    await this.sms.send(loan.mobile, `Loan ${loan.id} approved`);
  }
}

// Orchestrator — coordinates the workflow, thin by design
@Injectable()
export class LoanApplicationService {
  constructor(
    private readonly eligibility: LoanEligibilityService,
    private readonly bureau: CreditBureauService,
    private readonly repository: LoanRepository,
    private readonly sanctionLetter: SanctionLetterService,
    private readonly notification: LoanNotificationService,
  ) {}

  async apply(dto: LoanApplicationDto): Promise<void> {
    this.eligibility.assess(dto);
    const report = await this.bureau.fetchReport(dto.pan);
    const loan = await this.repository.create({ ...dto, bureau: report });
    const pdf = await this.sanctionLetter.generate(loan);
    await this.notification.notifyApproval(loan, pdf);
  }
}
```

Now each class has exactly one reason to change. The orchestrator (`LoanApplicationService`) changes only when the workflow *sequence* changes — which is a distinct reason owned by the platform/architecture team.

**Q11. How should you structure NestJS modules to reflect SRP at the module level?**
A: Each NestJS `@Module` should encapsulate one bounded context. A domain-aligned module structure for a lending platform:

```
src/
  loan/
    loan.module.ts            # Orchestrates loan domain
    services/
      loan-eligibility.service.ts
      loan-application.service.ts
    repositories/
      loan.repository.ts
  credit-bureau/
    credit-bureau.module.ts   # Owns all bureau integrations
    services/
      credit-bureau.service.ts
    dto/
      bureau-report.dto.ts
  notification/
    notification.module.ts    # Owns all outbound communication
    services/
      loan-notification.service.ts
  document/
    document.module.ts        # Owns PDF/letter generation
    services/
      sanction-letter.service.ts
```

Each module can evolve independently. Adding a new bureau provider touches only `credit-bureau/`; redesigning email templates touches only `notification/`.

**Q12. How does SRP apply to TypeScript interfaces and DTOs?**
A: DTOs and interfaces also benefit from SRP — specifically, avoid multipurpose DTOs that serve different operations:

```typescript
// ❌ One DTO serving too many masters — creates coupling between create and update shapes
export class LoanDto {
  id?: string;              // Only relevant on update/response
  applicantId: string;
  amount: number;
  status?: LoanStatus;      // Only relevant on response/update, not creation
  bureauReport?: BureauData; // Only relevant internally, not in API input
}

// ✅ Purpose-specific DTOs — each has one reason to change
export class CreateLoanDto {
  @IsString() applicantId: string;
  @IsNumber() amount: number;
}

export class UpdateLoanStatusDto {
  @IsEnum(LoanStatus) status: LoanStatus;
}

export class LoanResponseDto {
  id: string;
  applicantId: string;
  amount: number;
  status: LoanStatus;
  createdAt: Date;
}
```

The `CreateLoanDto` changes when the creation API contract changes. The `LoanResponseDto` changes when the response shape changes. They have independent reasons to change.

## Section 4: SRP in Testing

**Q13. How does SRP make unit testing significantly easier?**
A: SRP-compliant classes have narrowly scoped dependencies. Mocking becomes surgical:

```typescript
// Testing LoanEligibilityService — zero external dependencies to mock
describe('LoanEligibilityService', () => {
  let service: LoanEligibilityService;

  beforeEach(async () => {
    const module = await Test.createTestingModule({
      providers: [LoanEligibilityService],
    }).compile();
    service = module.get(LoanEligibilityService);
  });

  it('should reject applicants below income threshold', () => {
    expect(() =>
      service.assess({ income: 10000, pan: 'ABCDE1234F' } as any)
    ).toThrow(BadRequestException);
  });

  it('should pass eligible applicants through', () => {
    expect(() =>
      service.assess({ income: 50000, pan: 'ABCDE1234F' } as any)
    ).not.toThrow();
  });
});
```

Contrast with testing the original `LoanService` God class — you'd need to mock `PrismaService`, `MailerService`, `SmsClient`, `CreditBureauClient`, and `PdfService` just to test the income validation rule. That's five mock setups for one logical test.

**Q14. How does SRP affect integration and contract testing strategies?**
A: SRP-aligned services map cleanly to integration test boundaries. Each service owns exactly the external system it integrates with:
- `CreditBureauService` → one set of integration tests against the bureau API (or Pact contract).
- `LoanNotificationService` → one set of tests verifying email/SMS dispatch.
- `LoanRepository` → one set of tests against the database (Testcontainers with a real Postgres instance).

When these are mixed in a God class, it's impossible to write a focused integration test — every test drags in all external systems, making the suite slow, brittle, and hard to parallelize.

## Section 5: SRP in Real-World Fintech/Lending Contexts

**Q15. How does SRP apply to NACH/UPI mandate management in an Indian lending platform?**
A: NACH mandate lifecycle is a classic multi-actor domain — it's tempting to create one `NachService` that handles everything, but the responsibilities are distinct:

```typescript
// ❌ God service
class NachService {
  registerMandate() { ... }    // Ops/integration concern
  debitEmi() { ... }           // Finance/collections concern
  handleCallback() { ... }     // Platform/integration concern
  generateReport() { ... }     // Compliance/reporting concern
  retryFailedDebit() { ... }   // Collections strategy concern
}

// ✅ SRP-aligned
class NachMandateRegistrationService { ... }  // Ops: mandate lifecycle with NPCI
class EmiCollectionService { ... }            // Finance: when/how to debit
class NachCallbackHandlerService { ... }      // Platform: parse & route NPCI callbacks
class CollectionsRetryService { ... }         // Collections: retry strategies & escalation
class NachComplianceReportService { ... }     // Compliance: audit trail generation
```

Each class is owned by a different team. When RBI changes the NACH callback format, only `NachCallbackHandlerService` changes. When the collections team changes the retry policy, only `CollectionsRetryService` changes.

**Q16. How does SRP interact with the repository pattern in a PostgreSQL-backed NestJS app?**
A: The repository pattern is itself an SRP application — it gives persistence exactly one responsibility. But repositories can also violate SRP internally if they mix query concerns:

```typescript
// ❌ Repository doing too much — mixes persistence with business queries & reporting
@Injectable()
export class LoanRepository {
  async create(data: CreateLoanDto) { ... }
  async findById(id: string) { ... }
  async getOverdueLoansForDashboard() { ... }    // Reporting concern — should be a read model
  async updateStatusWithAuditLog(id: string) { ... } // Audit is a cross-cutting concern
  async computePortfolioStats() { ... }           // Analytics — belongs in a separate service
}

// ✅ Focused repository — only persistence operations
@Injectable()
export class LoanRepository {
  async create(data: CreateLoanDto): Promise<Loan> { ... }
  async findById(id: string): Promise<Loan | null> { ... }
  async updateStatus(id: string, status: LoanStatus): Promise<void> { ... }
  async findByStatus(status: LoanStatus): Promise<Loan[]> { ... }
}

// Separate read model for reporting/dashboard queries
@Injectable()
export class LoanReadModelService {
  async getOverdueLoans(): Promise<OverdueLoanView[]> { ... }
  async getPortfolioStats(): Promise<PortfolioStatsDto> { ... }
}
```

**Q17. How does SRP apply when integrating with external APIs like CIBIL, Experian, or Karza?**
A: Each bureau has a distinct API contract, data format, and failure mode. A single `CreditBureauService` that handles all three violates SRP because changes in the CIBIL API should not require you to touch the Experian integration:

```typescript
// ✅ One class per bureau — each has one reason to change
@Injectable()
export class CibilBureauAdapter implements BureauAdapter {
  async fetchReport(pan: string): Promise<NormalizedBureauReport> {
    // CIBIL-specific HTTP call, response parsing, error handling
  }
}

@Injectable()
export class ExperianBureauAdapter implements BureauAdapter {
  async fetchReport(pan: string): Promise<NormalizedBureauReport> {
    // Experian-specific logic
  }
}

// Factory / strategy — decides which adapter to use; its only job
@Injectable()
export class BureauAdapterFactory {
  constructor(
    private readonly cibil: CibilBureauAdapter,
    private readonly experian: ExperianBureauAdapter,
  ) {}

  get(bureau: BureauProvider): BureauAdapter {
    return bureau === BureauProvider.CIBIL ? this.cibil : this.experian;
  }
}
```

This also makes it trivial to add a third bureau (Karza) without modifying existing adapters.

## Section 6: Scenario / System Design Style Questions

**Q18. "A PR adds a `generateRbiComplianceReport()` method to your existing `LoanService`. How do you respond in code review?"**
A: Decline and explain the SRP violation:
- `LoanService` already has a responsibility (loan lifecycle management); adding compliance reporting gives it a second reason to change — one driven by the Product/Eng team (loan processing changes) and one driven by the Compliance/Legal team (RBI regulation changes).
- The method likely needs its own dependencies (date ranges, aggregation queries, PDF/Excel output) that don't belong in `LoanService`.
- Request the method be extracted to a `RbiComplianceReportService` in a `compliance/` module, with `LoanRepository` as a shared dependency if it needs loan data.
- The `LoanModule` should `export` the repository so the `ComplianceModule` can import and inject it, without coupling the two modules' services directly.

**Q19. "Your team is debating whether to put KYC validation logic inside the `UserService` or extract it to a separate `KycService`. What's your recommendation and rationale?"**
A: Extract to `KycService`. The actors are different:
- `UserService` is owned by the platform team — it changes when user registration flow, authentication, or profile management changes.
- KYC logic is owned by the compliance/risk team — it changes when RBI KYC norms change, when you add a new KYC provider (UIDAI, DigiLocker, PAN verification via Karza), or when document verification rules are updated.

These are independent change drivers. Embedding KYC in `UserService` means every KYC regulation change risks breaking user registration logic, and every user flow change puts KYC at risk. Additionally, `KycService` is likely reused across multiple entry points — new loan application, re-KYC at renewal, co-applicant addition — so it needs to be independently injectable. A clean boundary:

```typescript
// UserService — owns user lifecycle
async register(dto: RegisterDto): Promise<User> {
  const user = await this.userRepository.create(dto);
  await this.kyc.initiateVerification(user.id, dto.pan); // delegates, doesn't own
  return user;
}

// KycService — owns verification rules, provider integration, status tracking
async initiateVerification(userId: string, pan: string): Promise<void> { ... }
async handleWebhook(payload: KycWebhookDto): Promise<void> { ... }
async getStatus(userId: string): Promise<KycStatus> { ... }
```

**Q20. "You're starting a greenfield lending microservice. How do you use SRP to decide the initial service/module boundaries?"**
A: Event-storm the domain first — identify business events and the actors who trigger or respond to them:

| Business Event                  | Actor who drives it          | Module/Service boundary          |
|---------------------------------|------------------------------|----------------------------------|
| Loan application submitted      | Applicant / Sales            | `loan-origination`               |
| KYC documents verified          | Compliance team              | `kyc`                            |
| Credit bureau report pulled     | Risk team                    | `credit-bureau`                  |
| Loan sanctioned / rejected      | Risk / Credit committee      | `underwriting`                   |
| Disbursement initiated          | Finance / Treasury           | `disbursement`                   |
| EMI schedule generated          | Finance                      | `repayment-schedule`             |
| NACH mandate registered         | Ops / Collections            | `nach`                           |
| Delinquency detected            | Collections                  | `collections`                    |
| RBI report generated            | Compliance / Legal           | `compliance-reporting`           |

Each row maps to one microservice or NestJS module. The guiding question for each: "Which team in the org would ask for a change to this code?" If the answer is "multiple teams for different reasons," split further.

## Quick Reference: SRP Smell Checklist

| Signal                                           | What It Suggests                                        |
|--------------------------------------------------|----------------------------------------------------------|
| Class name contains "And" or "Manager"           | Multiple responsibilities bundled together               |
| Constructor takes 5+ injected dependencies       | Class serves too many masters                            |
| Method names span unrelated domains              | Mixed concerns; split into focused services              |
| Changing one feature requires touching this file for multiple unrelated reasons | Classic SRP violation — God class |
| Unit test requires mocking 4+ different systems  | Class has too many external dependencies / responsibilities |
| Two different teams regularly edit this file     | Two actors → two responsibilities → split it            |
| Private methods you wish were testable           | Hidden responsibility screaming to become its own class  |
| File is 500+ lines in a service class            | Strong signal of accumulated responsibility              |

---

**Tip for the interview:** At the 5 YOE level, interviewers won't ask "define SRP" — they'll describe a real system smell and ask what's wrong and how you'd fix it. Know how to identify SRP violations by the *actor/reason-to-change* test (not just "does too many things"), have a concrete refactoring story ready (ideally from your own fintech codebase — NACH, KYC, bureau integrations are perfect examples), and be able to articulate the *cost* of the violation (flaky tests, merge conflicts, teams blocking each other) as well as the *tradeoffs* of splitting (indirection, more files to navigate). The senior differentiator is recognizing that SRP is ultimately about *organizational alignment* — your code boundaries should mirror your team ownership boundaries (Conway's Law in reverse).
