# Design Patterns — SOLID Principles: Open/Closed Principle (OCP) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Open/Closed Principle?**
A: The Open/Closed Principle states that a software entity (class, module, function) should be **open for extension but closed for modification**. Coined by Bertrand Meyer (1988) and later reframed by Robert C. Martin in the context of object-oriented design, it means: you should be able to add new behavior to a system without changing its existing, already-tested source code. New functionality is introduced by *adding* new code, not by *editing* old code.

**Q2. Why does OCP matter in practice?**
A: Every time you modify existing code, you risk breaking behavior that already works and is already tested. The more places code is consumed — by other services, by downstream teams, by existing tests — the higher the blast radius of a change. OCP pushes you toward designs where adding a new feature means writing a new class/function and wiring it in, leaving existing code (and its test coverage) untouched. The result is a system that grows in size rather than in churn — easier to reason about, safer to release, and cheaper to maintain.

**Q3. How is OCP typically achieved in object-oriented languages?**
A: Through **abstraction** — defining a stable interface or abstract base that captures a contract, and letting concrete implementations vary behind it. The two main mechanisms are:
- **Inheritance / abstract classes** — define abstract behavior in a base class; new variants extend it without touching the base.
- **Interfaces / protocols** — define a contract; new implementations fulfill the contract without altering the interface or existing implementors.

The key is that the *consumer* of behavior depends on the abstraction (the stable part), not on a specific concrete type (the changeable part).

**Q4. What did Bertrand Meyer's original formulation mean vs. Martin's OOP reformulation?**
A: Meyer's original OCP (1988) was about compiled modules in languages like Eiffel — once a module was compiled and shipped, it should be "closed" (immutable); to extend it, you created a new module that inherited from it. Martin's reformulation (1996, popularized in *Agile Software Development*) broadened this to mean: depend on abstractions so that the *behavior* of a component can be extended without modifying its *source code*. Martin's version is more relevant today — it's less about compiled artifacts and more about designing flexible seams in your architecture.

**Q5. What is the relationship between OCP and the other SOLID principles?**
A: OCP is deeply entangled with the rest:
- **SRP (Single Responsibility)** — a class with one responsibility is easier to close (it has fewer reasons to change).
- **LSP (Liskov Substitution)** — extensions (subclasses, implementations) must be substitutable for the abstraction; otherwise OCP breaks down in practice.
- **ISP (Interface Segregation)** — narrow interfaces are easier to keep stable (closed); fat interfaces invite modification as requirements evolve.
- **DIP (Dependency Inversion)** — depending on abstractions, not concretions, is *the* mechanism by which OCP is realized. OCP is the goal; DIP is the tool.

## Section 2: OCP Violations & Refactoring

**Q6. What does an OCP violation look like in code?**
A: The most common smell is a `switch` statement (or `if/else if` chain) that branches on a type tag — and that you know you'll have to crack open every time a new type is added:

```ts
// VIOLATION — every new shape type requires editing this function
function getArea(shape: { type: string; radius?: number; width?: number; height?: number }): number {
  switch (shape.type) {
    case "circle":
      return Math.PI * shape.radius! ** 2;
    case "rectangle":
      return shape.width! * shape.height!;
    default:
      throw new Error("Unknown shape");
  }
}
```
Adding a `Triangle` means opening `getArea` and editing the switch — modifying closed code, re-testing the entire function, and risking regressions on `circle` and `rectangle`.

**Q7. How do you refactor the violation in Q6 to comply with OCP?**
A: Introduce an abstraction and push the behavior into implementations:

```ts
// Abstraction — stable, closed
interface Shape {
  area(): number;
}

// Extensions — open, each in its own unit
class Circle implements Shape {
  constructor(private radius: number) {}
  area(): number { return Math.PI * this.radius ** 2; }
}

class Rectangle implements Shape {
  constructor(private width: number, private height: number) {}
  area(): number { return this.width * this.height; }
}

class Triangle implements Shape {   // NEW — zero edits to existing code
  constructor(private base: number, private height: number) {}
  area(): number { return 0.5 * this.base * this.height; }
}

// Consumer — closed, never needs to change
function printArea(shape: Shape): void {
  console.log(shape.area());
}
```
Adding `Triangle` required no edits to `Circle`, `Rectangle`, or `printArea`.

**Q8. Is every `switch` statement an OCP violation?**
A: No. The principle applies when the branching logic is tied to a *type* that is expected to grow over time, and when that branching lives in a layer that should otherwise be stable. A `switch` on a finite, fixed set of values (HTTP status codes, weekdays, player turn in a two-player game) is not an OCP violation — it's just conditional logic. The heuristic: if adding a new "type" in the future would require you to find and edit *multiple* switch blocks across the codebase, that's a violation. One localized switch in a factory is often fine (see Q12).

**Q9. What is the "protected variation" framing of OCP?**
A: Craig Larman describes OCP as a special case of *protected variation* — identifying the points in your design most likely to change, and wrapping them behind a stable interface so that the rest of the system is shielded from those changes. OCP is the principle; protected variation is the broader pattern thinking behind it: find what varies, encapsulate it, stabilize the seam. In a payment system, payment providers vary — so you wrap them behind a `PaymentGateway` interface and the rest of the system never touches provider-specific code.

**Q10. Can OCP be violated through configuration rather than code?**
A: Yes — and this is a subtler form. If adding a new "type" or behavior requires editing a central config file, a database lookup table, or an environment variable that branches into different code paths, you have the same logical violation even if no `.ts` or `.java` file was changed. True OCP compliance means new behavior can be introduced by deploying a new unit (class, plugin, module) without touching existing units — whether that's code, config, or infrastructure.

## Section 3: OCP in Real Architectures

**Q11. How does OCP apply in a microservices or event-driven architecture?**
A: In a microservices system, OCP plays out at the service boundary level:
- A service that publishes events to a message bus (Kafka, SNS) is *closed* — publishers don't change when a new consumer wants to react to their events. You add a new consumer service without touching the producer.
- Contrast with an RPC/REST call chain where every new downstream requirement means adding a new endpoint or request parameter to an upstream service — that's the equivalent of cracking open a closed module.
- Similarly, a plugin architecture (a service that loads handlers from a registry) is open for extension (register a new handler) without modifying the dispatcher — OCP at the service level.

**Q12. How does a factory or registry pattern preserve OCP?**
A: Factories concentrate the "which concrete type do I instantiate?" decision in one place — so when you add a new type, you edit *only* the factory, not every call site. A registry goes further:

```ts
// Registry approach — the switch/if is gone entirely
const shapeRegistry = new Map<string, (data: any) => Shape>();
shapeRegistry.set("circle", (d) => new Circle(d.radius));
shapeRegistry.set("rectangle", (d) => new Rectangle(d.width, d.height));

// Adding Triangle: register it — zero edits to existing code
shapeRegistry.set("triangle", (d) => new Triangle(d.base, d.height));

function createShape(type: string, data: any): Shape {
  const factory = shapeRegistry.get(type);
  if (!factory) throw new Error(`Unknown shape: ${type}`);
  return factory(data);
}
```
New types are registered (extension), not embedded in a conditional (modification).

**Q13. How does the Strategy pattern implement OCP?**
A: The Strategy pattern is one of the most direct expressions of OCP. A context class holds a reference to a `Strategy` interface and delegates behavior to it. Adding a new behavior means writing a new `Strategy` implementation — the context class never changes:

```ts
interface DiscountStrategy {
  calculate(price: number): number;
}

class NoDiscount implements DiscountStrategy {
  calculate(price: number) { return price; }
}

class SeasonalDiscount implements DiscountStrategy {
  calculate(price: number) { return price * 0.9; }
}

class LoyaltyDiscount implements DiscountStrategy {  // NEW — no edits to context
  calculate(price: number) { return price * 0.85; }
}

class OrderPricer {
  constructor(private strategy: DiscountStrategy) {}
  finalPrice(price: number) { return this.strategy.calculate(price); }
}
```
In a fintech context: swap `DiscountStrategy` for `RepaymentScheduleStrategy`, `InterestCalculationStrategy`, or `FraudDetectionStrategy` — same pattern, real-world scale.

**Q14. How does the Decorator pattern relate to OCP?**
A: Decorators extend behavior by wrapping an existing object — without subclassing or modifying the original. Each decorator adds a layer of behavior while delegating the core work to the wrapped instance:

```ts
interface Logger {
  log(message: string): void;
}

class ConsoleLogger implements Logger {
  log(message: string) { console.log(message); }
}

class TimestampLogger implements Logger {        // extends without modifying
  constructor(private inner: Logger) {}
  log(message: string) {
    this.inner.log(`[${new Date().toISOString()}] ${message}`);
  }
}

class RedactingLogger implements Logger {        // another extension layer
  constructor(private inner: Logger) {}
  log(message: string) {
    this.inner.log(message.replace(/pan=\d+/gi, "pan=REDACTED"));
  }
}

const logger = new RedactingLogger(new TimestampLogger(new ConsoleLogger()));
logger.log("Processing pan=4111111111111111");
// → [2026-01-01T00:00:00.000Z] Processing pan=REDACTED
```
Each new cross-cutting concern (rate limiting, async buffering, structured JSON output) is a new decorator — existing classes untouched.

**Q15. How does OCP interact with feature flags?**
A: Feature flags (toggles) can be a pragmatic substitute for OCP in some cases — you add new code paths behind a flag and keep the old path intact. But they're not the same as true OCP compliance: the *branching logic* still grows inside existing code, and flags accumulate technical debt if not cleaned up. True OCP means new behavior is a *new artifact*; a feature flag is new behavior *inside an existing artifact behind a conditional*. For short-term deployment safety, flags are fine. For long-term architecture, they don't replace proper abstractions.

## Section 4: Pitfalls, Over-engineering & Pragmatics

**Q16. What is "premature abstraction," and how does it relate to OCP?**
A: OCP can be misapplied by creating abstractions before you know what varies. If you define a `PaymentProcessor` interface with one implementation and no foreseeable second one, you've added indirection without reducing change risk — you've made the code harder to read for no benefit. The pragmatic rule (often attributed to Martin Fowler's *Refactoring*): **don't abstract until the second time you see the variation**. The first time a new case arrives, handle it concretely. The second time, extract the abstraction and refactor both cases behind it. This is sometimes called "Rule of Three" or the "two strikes" approach.

**Q17. How do you decide when to apply OCP vs just editing the existing code?**
A: Consider:
- **Will this variation point grow?** If you're adding the 5th payment provider, OCP has clear ROI. If this is a one-off special case unlikely to repeat, a targeted edit with good tests is fine.
- **Who else depends on this code?** The more consumers, the higher the value of keeping the existing interface stable.
- **Is the existing code well-tested?** Modifying tested code without OCP means updating tests everywhere. A new class gets new tests without touching old ones.
- **Deployment boundaries** — if the existing code is in a shared library consumed by many services, even a minor change requires coordinated upgrades. OCP saves you there.

**Q18. Is OCP relevant in functional programming?**
A: Yes, though the vocabulary differs. In FP, OCP manifests as:
- **Higher-order functions** — pass a function as a parameter to extend behavior without modifying the consuming function.
- **Type classes / protocols** (Haskell, Rust, Swift) — define a capability; new types implement it without changing existing code.
- **Middleware chains** (Express.js, Redux) — a pipeline where new middleware is added without modifying existing middleware.
- **Pattern matching** — in Haskell/Rust, adding a new variant to a sum type is an "OCP violation" signal because the compiler forces you to handle it everywhere — this is intentional: the exhaustiveness check is a feature, not a bug. Haskell's typeclasses let you define new behavior for existing types without touching them.

**Q19. What is the "Shotgun Surgery" smell, and how does it indicate OCP violation?**
A: Shotgun Surgery (a Martin Fowler refactoring smell) describes the situation where a single logical change requires edits scattered across many files/classes. It's a strong indicator of an OCP violation: if adding `Triangle` means editing `getArea`, `serialize`, `render`, `validate`, and `getPerimeter` all separately, those five switch blocks should each have been replaced by a polymorphic dispatch. The fix is to consolidate the variation behind a single abstraction — one new `Triangle` class handles all five behaviors.

**Q20. Can OCP be applied at the module/package level, not just the class level?**
A: Yes — and this is often more impactful at scale. A well-designed npm package or internal library is "closed": consumers depend on its public API, and the library author doesn't break that contract. Adding new exports is extension; changing existing exports is modification (a semver major bump for good reason). Plugin systems (Webpack, ESLint, NestJS modules, VS Code extensions) are textbook OCP at the module level: the host defines a stable plugin interface; new plugins extend the system without touching the host.

## Section 5: Scenario / System Design Style Questions

**Q21. "You're reviewing a PR that adds a 6th `if/else` branch to a `processPayment` function — one branch per payment provider (JusPay, Razorpay, Stripe, PayU, Paytm, and now HDFC). What do you say?"**
A: This is a textbook OCP violation that's now visible through accumulation. Key points to raise in review:
1. Every new provider means another edit to `processPayment` — a stable function that should never need to know about providers.
2. Testing burden: adding a new branch means you now need to re-test *all* six code paths, not just the new one.
3. The abstraction is obvious: a `PaymentProvider` interface with `initiatePayment`, `verifyPayment`, and `refund` methods. Each provider gets its own class, independently testable.
4. The factory/registry (Q12) maps provider codes to implementations — `processPayment` stays closed forever.
5. If time doesn't allow a full refactor now, at minimum: extract the new HDFC code into an `HdfcPaymentHandler` class and note the tech debt. Don't keep growing the `if/else`.

**Q22. "Your team is building a Business Rules Engine (BRE) for NACH payment eligibility. New rules are added every quarter. How would you design it to comply with OCP?"**
A: This is exactly the use case OCP was made for:

```ts
interface EligibilityRule {
  name: string;
  evaluate(applicant: Applicant): RuleResult;
}

class MinimumIncomeRule implements EligibilityRule {
  name = "MinimumIncome";
  evaluate(applicant: Applicant): RuleResult {
    return applicant.monthlyIncome >= 15000
      ? { passed: true }
      : { passed: false, reason: "Income below threshold" };
  }
}

class BureauScoreRule implements EligibilityRule { /* ... */ }
class DeduplicationRule implements EligibilityRule { /* ... */ }

class BREEngine {
  constructor(private rules: EligibilityRule[]) {}  // closed
  evaluate(applicant: Applicant): EligibilityResult {
    const failures = this.rules
      .map(r => r.evaluate(applicant))
      .filter(r => !r.passed);
    return { eligible: failures.length === 0, failures };
  }
}

// Adding a new rule next quarter: write a new class, register it — zero engine edits
const engine = new BREEngine([
  new MinimumIncomeRule(),
  new BureauScoreRule(),
  new DeduplicationRule(),
  new NewAccountAggregatorRule(),  // Q4 addition
]);
```
The engine is permanently closed. New rules are new classes — independently unit-testable, independently deployable if rules are loaded from a registry.

**Q23. "You have a notification service that currently sends emails. Product asks to add SMS, then push, then WhatsApp — all in the next two sprints. How do you structure this?"**
A: Classic multi-channel notification — textbook OCP:

```ts
interface NotificationChannel {
  send(recipient: string, message: string): Promise<void>;
}

class EmailChannel implements NotificationChannel { /* ... */ }
class SMSChannel implements NotificationChannel { /* ... */ }   // Sprint 1
class PushChannel implements NotificationChannel { /* ... */ }  // Sprint 2
class WhatsAppChannel implements NotificationChannel { /* ... */ } // Sprint 3

class NotificationService {
  constructor(private channels: NotificationChannel[]) {}
  async notify(recipient: string, message: string): Promise<void> {
    await Promise.allSettled(
      this.channels.map(ch => ch.send(recipient, message))
    );
  }
}
```
Each sprint delivers one new class. `NotificationService` never changes. Channels can be feature-flagged at the DI composition root. Each channel is independently unit-tested with a mock. Failure in one channel doesn't cascade (note `allSettled`).

**Q24. "A senior engineer argues that OCP leads to over-abstraction and death-by-interface. How do you respond?"**
A: It's a fair concern when OCP is applied naively or prematurely — but the critique is really about *timing*, not the principle itself:
- OCP is most valuable at *known* variation points — places where the domain itself guarantees growth (new payment providers, new rule types, new notification channels). Abstracting those is not over-engineering.
- Over-abstraction happens when you create interfaces for things that have one implementation and no realistic prospect of a second. That's violating YAGNI ("You Aren't Gonna Need It"), not respecting OCP.
- The right heuristic: let duplication exist once, extract the abstraction on the second instance, formalize it into an interface/pattern by the third. OCP is a design *target* toward which you refactor as variation becomes evident — not a rule that mandates abstraction up front.

**Q25. "After a production incident, a post-mortem reveals that a 'quick fix' to a core payment processing class introduced a regression in an existing flow. What structural change would prevent this in future?"**
A: The incident is a textbook argument for OCP at the architectural level:
1. The fact that a new feature required editing a core class means the class wasn't closed — it had no seam for extension.
2. Immediate fix: extract the variation (the new logic) into its own class behind an interface. The core class delegates to the interface — it no longer needs to be touched for new behavior.
3. Structural enforcement: mark the core class as final (TypeScript's `readonly` pattern or linting rules), require interface-level changes to go through an architecture review.
4. Test coverage: if the class had integration tests per-behavior, the regression would have been caught before release. OCP and testing reinforce each other — closed code with stable tests is the safest code.

## Quick Comparison Table

| Aspect                         | OCP Violation                                   | OCP Compliant Design                             |
|---                             |---                                              |---                                               |
| Adding new behavior            | Edit existing class / function                  | Add new class / implementation                   |
| Risk to existing functionality | High — every edit risks regression              | Low — existing code untouched                    |
| Test impact                    | Must re-test entire modified unit               | New tests only for new class                     |
| Common code smell              | `switch(type)`, `if/else if` chains on type tag | Polymorphic dispatch, strategy, decorator        |
| Key mechanism                  | None — concrete dependencies throughout         | Abstraction (interface / abstract class)         |
| Scales to N new types?         | Linearly more risky                             | O(1) impact on existing code                     |
| Pattern examples               | Monolithic handler functions                    | Strategy, Decorator, Factory, Plugin, Registry   |
| Related principle              | Violates DIP (depends on concretions)           | Enabled by DIP (depends on abstractions)         |

---

**Tip for the interview:** At the 5 YOE level, don't just recite the definition — interviewers want to hear OCP in the context of *your actual work*. Have a story ready: a `switch` on payment provider type that grew to 6 branches, a BRE where new rules arrived every quarter, a notification service you extended without touching the core. The best answers connect OCP to the *cost* of violation (production incidents, slow releases, flaky tests) and the *mechanism* of compliance (which interface you defined, how the factory/registry worked, which design pattern you reached for). Also be ready to push back intelligently: OCP isn't "never edit code" — it's "design so that the *expected* points of growth don't require editing stable code."
