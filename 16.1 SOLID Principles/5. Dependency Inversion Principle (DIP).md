# JavaScript / TypeScript (Design Patterns — SOLID Principles): Dependency Inversion Principle (DIP) — Interview Q&A (5 YOE Level)

---

## Section 1: Fundamentals

**Q1. What is the Dependency Inversion Principle (DIP)?**
A: DIP is the "D" in SOLID, stated by Robert C. Martin as two rules:
1. **High-level modules should not depend on low-level modules. Both should depend on abstractions.**
2. **Abstractions should not depend on details. Details (concrete implementations) should depend on abstractions.**

In plain terms: the parts of your code that contain business logic (high-level) should not directly instantiate or import concrete infrastructure (low-level — databases, HTTP clients, file systems, third-party SDKs). Instead, both sides should talk through an interface or abstract contract. The word *inversion* refers to flipping the conventional dependency direction — instead of high-level code reaching *down* into concrete details, the concrete details *plug up* into abstractions owned by the high-level code.

**Q2. What does "inversion" mean — what exactly is being inverted?**
A: The *direction of the source-code dependency*, not the flow of control. In a naive layered design:
```
OrderService  →  imports  →  MySQLOrderRepository (concrete)
```
`OrderService` (high-level) depends on `MySQLOrderRepository` (low-level detail). If MySQL is swapped for Postgres, `OrderService` must change — a violation.

After DIP, the dependency arrow flips:
```
OrderService  →  depends on  →  IOrderRepository (abstraction)
MySQLOrderRepository  →  implements  →  IOrderRepository
```
Now `OrderService` owns or co-locates the abstraction. `MySQLOrderRepository` depends *on* that abstraction to know what contract to satisfy. The runtime flow of control is the same — `OrderService` still calls the repository — but the *source-code dependency* runs in the opposite direction at the implementation level.

**Q3. What is the difference between DIP and Dependency Injection (DI)?**
A: A very common conflation — they are related but distinct:
- **DIP** is a *design principle* — a rule about which direction dependencies should point (toward abstractions, not concretions).
- **DI (Dependency Injection)** is a *technique* — a way of supplying an object's dependencies from outside rather than having it construct them internally (via constructor injection, setter injection, or method injection).

DI is the most common *mechanism* used to satisfy DIP, but DI alone doesn't guarantee DIP compliance. You can inject a concrete class directly (`new MySQLRepo()` passed in from outside) — that's DI without DIP. DIP requires the injected thing to be an abstraction. Conversely, DIP can theoretically be satisfied without DI (e.g., via a service locator), though DI is the preferred approach.

**Q4. What is an Inversion of Control (IoC) container, and how does it relate to DIP?**
A: IoC is the broader concept: instead of your code controlling when and how dependencies are created, that control is *inverted* to a framework or container. An IoC container (InversifyJS, TSyringe, NestJS DI, Angular's injector) is a runtime registry that:
1. Knows which concrete class satisfies which abstraction token.
2. Instantiates and wires dependencies automatically when a class is resolved.

DIP is what makes IoC containers valuable — if high-level modules depended directly on concretions, there'd be nothing to configure in the container. The container is the runtime machinery that delivers DIP's promise: swap `MySQLOrderRepository` for `InMemoryOrderRepository` in one container binding, and `OrderService` never changes.

**Q5. What does a DIP violation look like in JavaScript/TypeScript?**
A: The tell-tale sign is a high-level class directly importing and constructing a concrete low-level dependency:
```ts
// Violation — OrderService directly depends on a concrete detail
import { MySQLOrderRepository } from "./MySQLOrderRepository";
import { SendGridEmailService }  from "./SendGridEmailService";

class OrderService {
  private repo  = new MySQLOrderRepository();   // hard-coded concrete
  private mailer= new SendGridEmailService();   // hard-coded concrete

  async placeOrder(dto: PlaceOrderDto): Promise<Order> {
    const order = Order.create(dto);
    await this.repo.save(order);
    await this.mailer.sendConfirmation(order);
    return order;
  }
}
```
Problems: `OrderService` cannot be tested without a real MySQL connection and a live SendGrid account. Swapping either requires editing `OrderService` itself. The business logic is coupled to infrastructure choices.

## Section 2: Applying DIP in JavaScript / TypeScript

**Q6. What does a DIP-compliant version of that example look like?**
A: Define abstractions (interfaces), inject concretions from outside:
```ts
// Abstractions — owned by the domain/business layer
interface OrderRepository { save(order: Order): Promise<void>; }
interface EmailService    { sendConfirmation(order: Order): Promise<void>; }

// High-level module depends only on abstractions
class OrderService {
  constructor(
    private repo:   OrderRepository,  // injected
    private mailer: EmailService      // injected
  ) {}

  async placeOrder(dto: PlaceOrderDto): Promise<Order> {
    const order = Order.create(dto);
    await this.repo.save(order);
    await this.mailer.sendConfirmation(order);
    return order;
  }
}

// Low-level details depend on the abstraction (implement it)
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order) { /* MySQL logic */ }
}

class SendGridEmailService implements EmailService {
  async sendConfirmation(order: Order) { /* SendGrid logic */ }
}

// Wired at the composition root
const service = new OrderService(
  new MySQLOrderRepository(),
  new SendGridEmailService()
);
```
`OrderService` has zero imports of infrastructure. Tests inject fakes. Swapping MySQL for Postgres is a one-line change at the composition root.

**Q7. Where should the abstractions (interfaces) live — in the high-level module or the low-level module?**
A: In the **high-level module** (or a shared domain/contracts layer), never in the low-level module. This is where "inversion" manifests in the file system:
```
src/
  domain/
    ports/                     ← abstractions live HERE (owned by domain)
      OrderRepository.ts
      EmailService.ts
    OrderService.ts            ← imports from ports/
  infrastructure/
    MySQLOrderRepository.ts    ← imports from domain/ports/ to implement
    SendGridEmailService.ts    ← imports from domain/ports/ to implement
```
If the interface lived in `infrastructure/`, `OrderService` would have to import from `infrastructure/` — the dependency arrow would still point downward. The interface must live where the *consumer* lives, so the *implementor* depends on the *consumer's* contract, not the other way around.

**Q8. JavaScript has no compile-time interfaces. How do you enforce DIP in plain JS?**
A: You can't enforce it at compile time, but you can practice it structurally:
- **Pass dependencies as constructor arguments** — never `new ConcreteClass()` inside a business function.
- **Document the expected shape** via JSDoc `@param {Object}` with typed properties.
- **Use duck typing consciously** — pass any object with the right methods; tests pass fakes, production passes real implementations.
- **Adopt TypeScript** — the single most effective way to make DIP violations visible as type errors at development time.

```js
// Plain JS — DIP via constructor injection, no interface enforcement
class OrderService {
  constructor(repo, mailer) {
    // repo must have: save(order) => Promise
    // mailer must have: sendConfirmation(order) => Promise
    this.repo   = repo;
    this.mailer = mailer;
  }
  async placeOrder(dto) { /* ... */ }
}

// Test: inject fakes
const fakeRepo   = { save: jest.fn().mockResolvedValue(undefined) };
const fakeMailer = { sendConfirmation: jest.fn().mockResolvedValue(undefined) };
const svc = new OrderService(fakeRepo, fakeMailer);
```

**Q9. What is the "composition root," and why is it important to DIP?**
A: The composition root is the single place in your application where all concrete implementations are instantiated and wired together. It's typically:
- `main.ts` / `index.ts` / `app.ts` in a plain Node app.
- A module registration file in NestJS (`AppModule`).
- The container configuration in InversifyJS.

The composition root is the *only* place that imports concrete low-level classes. Everything else imports only abstractions. This principle — "only the composition root knows about concretions" — is the runtime enforcement of DIP at the architectural level. If you find yourself importing `MySQLOrderRepository` inside `OrderService`, you've leaked composition-root concerns into business logic.

**Q10. How does TypeScript's structural typing affect DIP?**
A: TypeScript's structural (duck) typing makes DIP easier to apply than nominal systems (Java, C#) in one key way: a concrete class doesn't need to explicitly declare `implements IOrderRepository` — if it has the right shape, it satisfies the interface. This means you can retrofit DIP onto existing code without modifying the concrete classes:
```ts
interface OrderRepository { save(order: Order): Promise<void>; }

// Existing class — no 'implements' keyword needed
class MySQLOrderRepository {
  async save(order: Order): Promise<void> { /* ... */ }
}

// TypeScript accepts this — shape matches
const repo: OrderRepository = new MySQLOrderRepository(); // ✓
```
The risk: without explicit `implements`, you lose the compiler's guarantee that `MySQLOrderRepository` stays in sync with the interface when the interface changes. Best practice is to declare `implements` explicitly for documentation and safety, even though TypeScript doesn't require it.

## Section 3: DIP with Frameworks & Patterns

**Q11. How does NestJS implement DIP?**
A: NestJS's entire architecture is built on DIP via its IoC container:
```ts
// Abstraction token
const ORDER_REPOSITORY = "ORDER_REPOSITORY";

// Provider registration — maps token to concrete class
@Module({
  providers: [
    { provide: ORDER_REPOSITORY, useClass: PrismaOrderRepository },
    OrderService,
  ],
})
export class OrderModule {}

// High-level module depends on the token (abstraction)
@Injectable()
class OrderService {
  constructor(
    @Inject(ORDER_REPOSITORY) private repo: OrderRepository
  ) {}
}
```
Swapping `PrismaOrderRepository` for `InMemoryOrderRepository` in tests is a single `useClass` change in the module definition. `OrderService` is never touched.

**Q12. How does DIP apply to React component design?**
A: In React, DIP appears as the practice of passing behaviour (functions, hooks, context values) as props or context rather than importing concrete services directly inside a component:
```tsx
// Violation — component directly imports a concrete API module
import { fetchUser } from "../api/userApi";

const UserProfile: React.FC<{ id: string }> = ({ id }) => {
  const [user, setUser] = useState(null);
  useEffect(() => { fetchUser(id).then(setUser); }, [id]);
  return <div>{user?.name}</div>;
};

// DIP-compliant — behaviour injected via props
interface UserFetcher { fetchUser(id: string): Promise<User>; }

const UserProfile: React.FC<{ id: string; fetcher: UserFetcher }> = ({ id, fetcher }) => {
  const [user, setUser] = useState(null);
  useEffect(() => { fetcher.fetchUser(id).then(setUser); }, [id, fetcher]);
  return <div>{user?.name}</div>;
};

// Test: inject a fake fetcher — no network call
render(<UserProfile id="1" fetcher={{ fetchUser: async () => fakeUser }} />);
```

**Q13. How does DIP relate to the Repository pattern?**
A: The Repository pattern is DIP's canonical application in data access. The domain layer defines a `Repository` interface (the abstraction); the infrastructure layer provides the concrete implementation (Prisma, TypeORM, raw SQL). The domain never knows which database backs it:
```ts
// Domain layer — owns the abstraction
interface ProductRepository {
  findById(id: ProductId): Promise<Product | null>;
  findAll(filter: ProductFilter): Promise<Product[]>;
  save(product: Product): Promise<void>;
}

// Infrastructure layer — depends on domain's abstraction
class PrismaProductRepository implements ProductRepository {
  constructor(private prisma: PrismaClient) {}
  async findById(id: ProductId) { /* Prisma query */ }
  async findAll(filter: ProductFilter) { /* Prisma query */ }
  async save(product: Product) { /* Prisma upsert */ }
}
```
The domain can be unit-tested against an `InMemoryProductRepository` — fast, no DB, no migrations. Production wires in `PrismaProductRepository` at the composition root.

**Q14. How does DIP apply to external HTTP clients and third-party SDKs?**
A: Any third-party SDK is a low-level detail — wrap it behind an interface so your business logic never imports the SDK directly:
```ts
// Abstraction — lives in domain/application layer
interface PaymentGateway {
  charge(amount: Money, token: PaymentToken): Promise<ChargeResult>;
  refund(chargeId: string, amount: Money): Promise<RefundResult>;
}

// Infrastructure — wraps Stripe SDK behind the abstraction
import Stripe from "stripe";
class StripePaymentGateway implements PaymentGateway {
  constructor(private stripe: Stripe) {}
  async charge(amount: Money, token: PaymentToken) {
    const result = await this.stripe.paymentIntents.create({ /* ... */ });
    return mapToChargeResult(result);
  }
  async refund(chargeId: string, amount: Money) { /* ... */ }
}
```
Benefits: switching from Stripe to Braintree is a new `BraintreePaymentGateway` class + one composition-root line. The entire billing domain is testable with a fake `PaymentGateway`. Stripe SDK version upgrades don't ripple into business logic.

**Q15. How does DIP interact with the Hexagonal Architecture (Ports & Adapters)?**
A: Hexagonal Architecture is essentially DIP applied at the architectural level and given vocabulary:
- **Ports** — the interfaces (abstractions) defined by the application core. Primary ports are driven *into* the application (use case interfaces); secondary ports are driven *out of* it (repository, email, payment interfaces). These are DIP's abstractions.
- **Adapters** — the concrete implementations that plug into ports: REST controllers (primary adapters), Prisma repositories (secondary adapters). These are DIP's details.

The "hexagon" represents the application core, which has zero imports from the outside world — every external interaction goes through a port. DIP is the principle that makes the boundary possible; Hexagonal Architecture is the structural pattern that formalizes it.

## Section 4: Pitfalls, Anti-Patterns & Misapplications

**Q16. What is the Service Locator pattern, and why is it considered an anti-pattern relative to DIP?**
A: A Service Locator is a global registry that classes query to find their dependencies:
```ts
// Service Locator — anti-pattern
class OrderService {
  private repo   = ServiceLocator.get<OrderRepository>("OrderRepository");
  private mailer = ServiceLocator.get<EmailService>("EmailService");
}
```
It satisfies DIP's "depend on abstractions" rule (the tokens are abstract) but violates the spirit because:
- Dependencies are **hidden** — you can't tell from `OrderService`'s constructor what it needs. Its contract is opaque.
- **Testing is hard** — you must pre-populate the global locator before each test; it's global mutable state.
- **Coupling to the locator** — `OrderService` is now coupled to `ServiceLocator` itself, a concrete global.
Constructor injection makes dependencies **explicit, visible, and testable** — the preferred DI form under DIP.

**Q17. Can you over-apply DIP? What does that look like?**
A: Yes. Every class having its own interface ("interface-for-everything") is over-engineering when there's only one implementation and no realistic prospect of a second. Signs of over-application:
- Interfaces like `IOrderService` that exist purely to wrap `OrderService` with no other implementor.
- Abstractions so specific they can never realistically be swapped (e.g., `interface PrismaConnectionPool`).
- Adding indirection with no testability or flexibility benefit.

The YAGNI test: *is there a real second implementation today, or is there a realistic test-double need?* If no to both, the interface adds noise. DIP is most valuable at **architectural boundaries** — the seam between domain and infrastructure — not between every class in the same layer.

**Q18. What is "abstraction leakage," and how does it violate DIP?**
A: Abstraction leakage occurs when implementation-specific types or concerns bleed into the interface, coupling the high-level module to the low-level detail through the abstraction itself:
```ts
// Leaky abstraction — interface exposes SQL detail
interface OrderRepository {
  save(order: Order): Promise<void>;
  executeRawSQL(query: string): Promise<unknown>; // ← leaks SQL
  getConnection(): MySQLConnection;               // ← leaks MySQL type
}
```
Now `OrderService` is indirectly coupled to MySQL through the interface — swapping to Postgres breaks the interface contract. The abstraction should speak only the domain's language:
```ts
// Clean abstraction — no infrastructure types
interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: OrderId): Promise<Order | null>;
}
```

**Q19. How does DIP interact with circular dependencies, and how do you avoid them?**
A: A circular dependency (A imports B imports A) is often a sign that the dependency direction is wrong — a DIP violation in disguise. Common scenario:
```
UserService  →  EmailService  →  UserService  (circular!)
```
The fix is usually to introduce an abstraction at the boundary and restructure:
- Extract the interface `UserEmailRecipient` (owned by `EmailService`'s layer or a shared contracts layer).
- `UserService` implements `UserEmailRecipient`; `EmailService` depends on the interface.
- The import cycle is broken because `EmailService` now imports the interface, not `UserService`.

In Node.js/TypeScript, circular imports cause `undefined` values at module load time — a runtime bug that's often traced back to a missing abstraction.

**Q20. What is the difference between DIP and the Strategy pattern?**
A: They're related but distinct:
- **DIP** is a *principle* about dependency direction — high-level modules shouldn't depend on low-level details; both should depend on abstractions.
- **Strategy** is a *pattern* — it encapsulates a family of algorithms behind a common interface, making them interchangeable at runtime.

Strategy is one of the most natural *implementations* of DIP. When you apply DIP to a behaviour that varies (sorting algorithm, payment method, compression format), you often land on the Strategy pattern. But DIP covers all dependency relationships (data access, messaging, logging), not just interchangeable algorithms.

## Section 5: Testing & Dependency Injection

**Q21. How does DIP transform unit testing?**
A: DIP makes unit testing of business logic straightforward by eliminating infrastructure dependencies from the test:
```ts
// Without DIP — test requires real DB and real SMTP server
it("places an order", async () => {
  const svc = new OrderService(); // internally creates MySQLRepo + SendGrid
  await svc.placeOrder(dto);      // hits real MySQL, real SendGrid
});

// With DIP — test uses fakes, runs in milliseconds, no network
it("places an order", async () => {
  const fakeRepo:   OrderRepository = { save: jest.fn().mockResolvedValue(undefined) };
  const fakeMailer: EmailService    = { sendConfirmation: jest.fn().mockResolvedValue(undefined) };
  const svc = new OrderService(fakeRepo, fakeMailer);

  await svc.placeOrder(dto);

  expect(fakeRepo.save).toHaveBeenCalledWith(expect.objectContaining({ status: "pending" }));
  expect(fakeMailer.sendConfirmation).toHaveBeenCalledTimes(1);
});
```
The test is fast, deterministic, and verifies only business behaviour — not infrastructure plumbing.

**Q22. What are the different forms of Dependency Injection, and which is preferred for DIP?**
A: Three main forms:

| Form | Example | DIP suitability |
|---|---|---|
| **Constructor injection** | `constructor(private repo: OrderRepository)` | ✅ Preferred — dependencies explicit, required, visible |
| **Setter injection** | `service.setRepo(repo)` | ⚠️ Optional dependencies only — object is in incomplete state before setter is called |
| **Method/parameter injection** | `placeOrder(dto, repo)` | ⚠️ Good for one-off overrides or functional style, not persistent dependencies |

Constructor injection is preferred because it makes all dependencies visible upfront, enforces them at object construction time (no partial state), and integrates cleanly with IoC containers.

**Q23. How do you use InversifyJS to implement DIP in a TypeScript project?**
A: InversifyJS uses symbols as tokens and decorators to wire the container:
```ts
// tokens.ts — abstract identifiers
const TOKENS = {
  OrderRepository: Symbol("OrderRepository"),
  EmailService:    Symbol("EmailService"),
};

// High-level module
@injectable()
class OrderService {
  constructor(
    @inject(TOKENS.OrderRepository) private repo: OrderRepository,
    @inject(TOKENS.EmailService)    private mailer: EmailService
  ) {}
}

// container.ts — composition root
const container = new Container();
container.bind<OrderRepository>(TOKENS.OrderRepository).to(MySQLOrderRepository);
container.bind<EmailService>(TOKENS.EmailService).to(SendGridEmailService);
container.bind(OrderService).toSelf();

// Resolve — container injects all dependencies automatically
const svc = container.get(OrderService);

// Test — rebind to fakes
container.rebind<OrderRepository>(TOKENS.OrderRepository).to(InMemoryOrderRepository);
```

## Section 6: Scenario / System Design Style Questions

**Q24. "You're onboarding to a codebase and notice that `PaymentService` directly imports `StripeClient` from the npm package and calls it inline. How do you assess this, and what's your refactor plan?"**
A: Assessment:
- `PaymentService` (business logic) is directly coupled to Stripe (infrastructure detail) — a clear DIP violation.
- The service cannot be unit-tested without live Stripe API calls (or `nock`/network-level mocking — fragile).
- A future switch to a different payment provider requires modifying `PaymentService` itself.
- Stripe SDK major version upgrades may break `PaymentService` without any business logic changing.

Refactor plan (incremental, safe):
1. **Define the abstraction** — create `PaymentGateway` interface in the domain/application layer with only the methods `PaymentService` actually uses (`charge`, `refund`).
2. **Create the adapter** — `StripePaymentGateway implements PaymentGateway`, wrapping `StripeClient`. Move all Stripe imports here.
3. **Update `PaymentService`** — change the constructor to accept `PaymentGateway`; remove the direct Stripe import.
4. **Update the composition root** — wire `StripePaymentGateway` as the `PaymentGateway` binding.
5. **Write unit tests** — inject a fake `PaymentGateway`; delete any Stripe-specific test setup.
6. **Integration test the adapter separately** — `StripePaymentGateway` gets its own integration tests against the Stripe sandbox.

**Q25. "Your team is building a notification system that currently only sends emails via SendGrid. The product roadmap has SMS (Twilio) and push notifications in 6 months. How do you design this with DIP from the start?"**
A: Design the abstraction around the *notification act*, not the *transport*:
```ts
// Domain abstraction — what the business cares about
interface NotificationChannel {
  send(recipient: Recipient, message: NotificationMessage): Promise<void>;
}

// Each transport is a separate adapter
class EmailChannel implements NotificationChannel {
  constructor(private sendgrid: SendGridClient) {}
  async send(recipient: Recipient, message: NotificationMessage) { /* ... */ }
}

class SMSChannel implements NotificationChannel {
  constructor(private twilio: TwilioClient) {}
  async send(recipient: Recipient, message: NotificationMessage) { /* ... */ }
}

class PushChannel implements NotificationChannel {
  constructor(private fcm: FCMClient) {}
  async send(recipient: Recipient, message: NotificationMessage) { /* ... */ }
}

// Orchestrator — depends only on the abstraction
class NotificationService {
  constructor(private channels: NotificationChannel[]) {}

  async notify(recipient: Recipient, message: NotificationMessage): Promise<void> {
    await Promise.all(this.channels.map(c => c.send(recipient, message)));
  }
}

// Composition root — add channels without changing NotificationService
const notifier = new NotificationService([
  new EmailChannel(sendgridClient),
  new SMSChannel(twilioClient),     // added in 6 months — zero changes to NotificationService
  new PushChannel(fcmClient),       // added later — same story
]);
```
Adding SMS in 6 months is a new class + one composition-root line. `NotificationService` is open for extension, closed for modification — DIP enabling OCP.

**Q26. "A monolith is being broken into microservices. The `OrderService` currently calls `UserService` directly via a function import. How does DIP apply at the service boundary level?"**
A: The direct function import is a compile-time, in-process dependency — fine in a monolith but incompatible with microservices. DIP applies at the macro level:
- Define an **interface for the interaction** (`UserLookup { findUser(id): Promise<UserSummary> }`) — the abstraction.
- In the monolith: wire the concrete `UserServiceClient` that calls the function directly.
- In the microservice split: wire a `UserServiceHttpClient` or `UserServiceGrpcClient` that makes a network call — the interface doesn't change.
- For resilience: wire a `UserServiceWithFallback` that wraps the HTTP client with a circuit breaker.

`OrderService` never changes through any of these transitions because it depends on `UserLookup`, not on how users are fetched. The migration from monolith to microservice is a composition-root concern, not a business logic concern. This is DIP operating at the architectural seam level.

## Quick Comparison Table (good for a whiteboard summary)

| Aspect | DIP Violation (depends on concretion) | DIP Compliant (depends on abstraction) |
|---|---|---|
| High-level imports | Concrete infrastructure class | Interface / abstract type |
| Testability | Requires real infrastructure | Inject fakes; fast unit tests |
| Swap cost | Edit high-level module | Change one line at composition root |
| Compilation impact | Infrastructure change → high-level recompile | Interface change → only implementations recompile |
| Onboarding clarity | Must trace through concrete code to understand contract | Interface documents the contract explicitly |
| Risk of circular deps | High — layers import each other | Low — dependencies flow one direction |
| Third-party coupling | Business logic knows SDK details | Business logic knows only domain concepts |

## DIP vs Related Principles & Patterns (at a glance)

| Concept | What it is | Relationship to DIP |
|---|---|---|
| **DI (Dependency Injection)** | Technique — supply deps from outside | Primary mechanism to *achieve* DIP |
| **IoC Container** | Runtime registry that wires deps automatically | Automates DI at scale; enforces DIP structurally |
| **ISP** | Principle — keep interfaces narrow | Narrow interfaces are better DIP abstractions; fat interfaces leak detail |
| **OCP** | Principle — open for extension, closed for modification | DIP enables OCP: new behaviours = new implementations, not edits to high-level code |
| **LSP** | Principle — subtypes must be substitutable | DIP is only useful if implementations honour LSP; a broken substitute defeats the abstraction |
| **Repository Pattern** | Pattern — abstract data access behind interface | Canonical DIP application for persistence |
| **Strategy Pattern** | Pattern — encapsulate interchangeable algorithms | Natural DIP application for variable behaviour |
| **Hexagonal Architecture** | Architecture — ports (abstractions) and adapters (details) | DIP applied at the system architecture level; ports are DIP's interfaces |
| **Facade** | Pattern — simplify a complex subsystem | Can wrap a complex low-level system behind a DIP-compliant interface |
| **Adapter** | Pattern — bridge shape mismatches | Used to make existing third-party classes satisfy a DIP abstraction |
| **Service Locator** | Anti-pattern — global registry queried by classes | Partially satisfies DIP (abstractions used) but hides deps; constructor DI preferred |

**Tip for the interview:** At the 5 YOE level, "what is DIP" never appears as a standalone question — it surfaces as: why is this service impossible to unit test, how would you architect the data layer so we can swap ORMs, how do you decouple business logic from a third-party SDK, or how should we structure the notification system to support multiple channels. Know the abstraction-owns-the-interface rule cold (interfaces live in the domain, not the infrastructure), understand the composition root concept, be able to sketch the Hexagonal Architecture vocabulary (ports and adapters), and have a real story about wrapping a third-party SDK behind an interface and writing tests against a fake — that's the level of answer that lands at 5 YOE.
